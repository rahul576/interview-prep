Design a proximity service like Yelp that finds nearby restaurants.

Classic Design Problems · design · levels entry, mid, senior

In one line

A proximity service splits a business service (profiles, reviews) from a read-optimised location search service that uses a geospatial index (geohash, quadtree, PostGIS/Elasticsearch), searches the user's cell plus neighbours, then filters and ranks; heavy caching and replicas handle the read load.

Detailed explanation

Businesses change rarely; searches happen constantly. That asymmetry allows a small, in-memory, heavily replicated index.

Geohash encodes latitude/longitude into a base-32 string; nearby points share prefixes, and precision depends on length (6 chars ≈ 1.2 km × 0.6 km). Querying only the user's cell misses results just across the border, so you also query the eight neighbouring cells. A quadtree subdivides space adaptively, so dense cities get small cells and deserts big ones. Managed options: PostGIS ST_DWithin, Elasticsearch geo_distance, Redis GEOSEARCH.

With ~200M businesses × ~100 bytes for the index, everything fits in memory on each replica.

How it works

  1. Business updates → business DB → event → index rebuild/update (minutes of delay acceptable).
  2. Search (lat, lng, radius, filters) → compute geohash precision from radius → fetch candidates from cell + neighbours.
  3. Compute exact distance, filter by category/open now, rank by distance, rating, relevance.
  4. Cache results for popular cells and queries.

Example

SELECT id, name FROM places
WHERE ST_DWithin(geom::geography, ST_MakePoint(77.5946, 12.9716)::geography, 2000)
  AND category = 'restaurant'
ORDER BY geom <-> ST_MakePoint(77.5946, 12.9716) LIMIT 20;

Common mistakes

  • Searching only one geohash cell.
  • Using straight lat BETWEEN … AND lng BETWEEN … on unindexed columns.
  • Real-time writes to the index for data that changes rarely.

How to answer in the interview

"I'd separate the business CRUD service from a read-only location search service. The search service keeps an in-memory geohash or quadtree index replicated across many nodes. A query searches the user's cell and its neighbours, computes exact distances, filters and ranks by distance and rating. Business updates propagate asynchronously, and popular areas are cached."

Likely follow-up questions

  • Moving objects like drivers? Frequent updates → in-memory index updated per ping, not batch rebuilds.
  • How to pick geohash precision? Based on the search radius.
  • Why neighbours? A point near a cell border may be closer to results in the adjacent cell.
