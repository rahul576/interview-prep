What are the pitfalls of managing Kubernetes resources with Terraform?

Infrastructure as Code · concept · levels mid

In one line

Managing Kubernetes objects with Terraform causes provider bootstrap problems (the cluster must exist before the kubernetes/helm providers can plan), drift from controllers that mutate objects, CRD ordering issues and opaque Helm diffs; the common pattern is Terraform for the cluster and cloud dependencies, GitOps (Argo CD/Flux) for what runs inside.

Detailed explanation

Provider bootstrap. Provider configurations are resolved before resources are planned. If the kubernetes or helm provider takes its host and token from an aws_eks_cluster created in the same configuration, the very first plan has no endpoint; when the cluster is replaced, the provider points at something that is about to disappear. Terraform's own documentation warns against provider configuration that depends on resources managed in the same apply. Short-lived tokens make it worse: a token fetched at plan time can expire before a long apply finishes, so the exec-based auth plugin is preferred.

Drift from mutation. Kubernetes is full of controllers and admission webhooks that add labels, annotations, sidecars, default fields and status. Terraform sees the live object differ from code and either shows endless diffs or fights the controller.

CRDs and ordering. kubernetes_manifest needs the API server at plan time to fetch the schema, so a custom resource cannot be planned until its CRD (from an operator or Helm chart) is installed. That usually forces a two-stage apply.

Helm releases appear in the plan as a values blob; you do not see which Deployments or RBAC rules change, and a failed release can leave Helm and Terraform states disagreeing.

Ownership. Application teams deploy many times a day; routing that through Terraform state and locks is slow and couples them to the platform team.

How it works

  1. Stack 1 (Terraform): VPC, cluster, node groups, IAM roles for workloads, DNS zones, KMS keys.
  2. Stack 1 also installs a minimal bootstrap: managed add-ons (CNI, CoreDNS) and Argo CD or Flux.
  3. Terraform publishes cluster metadata (role ARNs, account IDs) for GitOps to consume.
  4. GitOps repo defines add-ons (ingress controller, cert-manager, external-dns) and workloads.
  5. Argo CD/Flux reconciles continuously, handling CRD ordering with sync waves or dependencies.

Example

# Stack 2 (separate state) reads the existing cluster instead of creating it
data "aws_eks_cluster" "this" { name = "prod-eu" }

provider "helm" {
  kubernetes {
    host                   = data.aws_eks_cluster.this.endpoint
    cluster_ca_certificate = base64decode(data.aws_eks_cluster.this.certificate_authority[0].data)
    exec {
      api_version = "client.authentication.k8s.io/v1beta1"
      command     = "aws"
      args        = ["eks", "get-token", "--cluster-name", "prod-eu"]
    }
  }
}

Common mistakes

  • Creating the cluster and its Helm releases in one root module.
  • Fixing drift with ever-growing ignore_changes instead of rethinking ownership.
  • Letting Terraform and Argo CD both manage the same object.

How to answer in the interview

"The biggest problem is bootstrapping: the kubernetes and helm providers need the cluster endpoint and credentials at plan time, so putting the cluster and its contents in one configuration breaks on the first run and on cluster replacement. Controllers also mutate objects, so Terraform sees constant drift, custom resources need their CRDs installed before they can even be planned, and Helm releases are opaque in the plan. So I use Terraform for the cluster and its cloud dependencies like IAM and DNS, bootstrap Argo CD or Flux, and let GitOps manage add-ons and workloads inside the cluster."

Likely follow-up questions

  • Where would you put add-ons like the ingress controller? In GitOps, with cloud-side IAM roles created by Terraform and passed as metadata.
  • When is Terraform for Kubernetes fine? Small, stable cluster-level objects such as namespaces or a bootstrap secret, in a separate stack.
  • How do you handle CRD ordering in Argo CD? Sync waves, or separate Applications for CRDs and custom resources.
