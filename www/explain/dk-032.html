How does the overlay2 storage driver and copy-on-write work?

Docker · concept · levels mid

In one line

overlay2 uses Linux OverlayFS to stack read-only image layers (lowerdirs) under one writable upper layer per container; modifying an image file triggers copy-up (copy-on-write), deletions create whiteout files, and write-heavy data belongs in volumes.

Detailed explanation

An image is a stack of layers, each a directory of file changes. overlay2, the default storage driver on modern Linux, asks the kernel's OverlayFS to combine them: the image layers become lower directories, the container gets an empty upper directory, and the kernel presents a merged view as the container's root filesystem. Reads are served from the topmost layer containing the file, so many containers can share the same image layers on disk and in the page cache.

When a process modifies a file that exists only in a lower layer, OverlayFS performs a copy-up: it copies the entire file into the upper directory and the change is made to that copy. The image itself is never altered. This is copy-on-write. Copy-up is per file, not per block, so appending one line to a 2 GB file first copies 2 GB, which is slow and wastes space.

Deleting a file from a lower layer cannot actually remove it, because lower layers are read-only. Instead, OverlayFS creates a whiteout (a special character device) in the upper layer that hides the file; deleted directories get an opaque marker. The same mechanism applies when building images: a RUN rm in a later layer only hides the file, and the bytes still ship in the earlier layer, so image size does not shrink.

The writable layer disappears when the container is removed, and its performance is worse than a plain filesystem. Databases, queues, logs and uploads should therefore use volumes or bind mounts, which bypass the overlay.

How it works

  1. Each layer is unpacked once into /var/lib/docker/overlay2/<id>/diff.
  2. Starting a container mounts overlay with lowerdir=..., upperdir=..., workdir=....
  3. Reads go to the highest layer containing the file.
  4. First write to a lower file copies it up, then writes the copy.
  5. Deletion creates a whiteout entry in the upper directory.

Example

docker run -d --name t nginx:1.27
docker inspect -f '{{json .GraphDriver.Data}}' t | jq   # LowerDir, UpperDir, MergedDir
docker exec t sh -c 'echo test >> /etc/nginx/nginx.conf; rm /usr/share/nginx/html/index.html'
docker diff t        # C = changed (copied up), D = deleted (whiteout)
# Wrong: file still in the first layer
RUN curl -o /tmp/big.tar.gz https://example.com/big.tar.gz
RUN rm /tmp/big.tar.gz

Common mistakes

  • Running databases on the container writable layer.
  • Deleting files in a later Dockerfile layer to "shrink" the image.
  • Modifying large image files at runtime and paying the copy-up cost.
  • Expecting writable-layer data to survive docker rm.

How to answer in the interview

"overlay2 uses OverlayFS to combine the read-only image layers, the lower directories, with one writable upper directory per container into a merged view. Reads come from whichever layer has the file. When a container changes a file from the image, it's copied up into the writable layer first and the copy is changed, so the image stays untouched and is shared by many containers. Deleting an image file creates a whiteout that hides it. Copy-up of big files is slow and the writable layer is lost on removal, so write-heavy data like databases and logs goes into volumes."

Likely follow-up questions

  • Why doesn't deleting a file in a later layer shrink the image? The earlier layer still contains it; the whiteout only hides it.
  • What does docker diff show? Added, changed and deleted paths in the writable layer.
  • Which backing filesystems support overlay2? ext4 and xfs (with d_type enabled) are standard.
