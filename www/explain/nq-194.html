What happens during bean initialization and destruction?

Spring Framework · concept · levels mid

In one line

Initialisation runs after construction and injection (@PostConstruct → afterPropertiesSet → init-method, then proxies are applied) to validate, open resources or warm caches; destruction runs on context close (@PreDestroy → destroy() → destroy-method) to release resources; prototypes are not destroyed, and Boot's graceful shutdown drains requests first.

Detailed explanation

Initialisation is the moment when a bean is fully constructed and all its dependencies are injected, so it can safely use them. Typical work: validating configuration (fail fast if a required URL is missing), opening a connection or channel, registering with a registry, compiling templates, or warming a cache. The order is fixed: @PostConstruct, then InitializingBean.afterPropertiesSet(), then a custom initMethod.

Only after that do BeanPostProcessors' after-initialisation hooks run, which is when AOP proxies are created. Two consequences follow. First, code in @PostConstruct runs on the raw object, so calling a @Transactional or @Cacheable method of the same bean there gets no transaction or caching. Second, other beans may not be fully started yet. For work that needs transactions or the whole application, use an ApplicationReadyEvent listener, an ApplicationRunner, or SmartInitializingSingleton. Long-running work in init callbacks also blocks startup, delays readiness and can cause Kubernetes to kill the pod.

Destruction happens when the context closes, normally on application shutdown via the JVM shutdown hook Spring Boot registers. Callbacks run in reverse dependency order: @PreDestroy, DisposableBean.destroy(), then a custom destroy method (inferred close()/shutdown() for @Beans). Use them to close pools, flush buffers, commit offsets, deregister from discovery, and stop threads.

Prototype beans are not tracked after creation, so the container never calls their destroy callbacks. And with graceful shutdown (server.shutdown=graceful), Spring Boot first stops accepting requests and lets in-flight ones finish before beans are destroyed, so resources are not closed under active requests.

How it works

  1. Constructor and dependency injection complete.
  2. @PostConstruct, afterPropertiesSet, init-method.
  3. BeanPostProcessors wrap the bean in proxies.
  4. Application runs.
  5. SIGTERM: graceful shutdown drains web requests, SmartLifecycle beans stop.
  6. @PreDestroy, destroy(), destroy-method; JVM exits.

Example

@Component
class ExchangeRateCache {
    private final RatesClient client;
    private final Map<String, BigDecimal> rates = new ConcurrentHashMap<>();
    private final ScheduledExecutorService refresher = Executors.newSingleThreadScheduledExecutor();

    ExchangeRateCache(RatesClient client) { this.client = client; }

    @PostConstruct
    void init() {
        rates.putAll(client.fetchAll());                       // warm cache, fast call
        refresher.scheduleAtFixedRate(() -> rates.putAll(client.fetchAll()), 5, 5, TimeUnit.MINUTES);
    }

    @PreDestroy
    void shutdown() throws InterruptedException {
        refresher.shutdown();
        refresher.awaitTermination(5, TimeUnit.SECONDS);
    }
}

Common mistakes

  • Calling transactional methods of the same bean from @PostConstruct.
  • Slow remote calls or data migrations in init callbacks, breaking startup probes.
  • Starting threads without stopping them, preventing clean shutdown.
  • Expecting destroy callbacks for prototypes or after kill -9.

How to answer in the interview

"Initialisation happens after the bean is constructed and its dependencies are injected, so it can validate configuration, open resources or warm caches. Callbacks run as @PostConstruct, then afterPropertiesSet, then a custom init method, and only afterwards are proxies applied, so @Transactional doesn't apply inside @PostConstruct. Destruction happens when the context closes: @PreDestroy, DisposableBean.destroy and the destroy method, where I close pools and stop threads. Prototype beans aren't destroyed by the container, and graceful shutdown lets in-flight requests finish first."

Likely follow-up questions

  • Why avoid long work in @PostConstruct? It blocks startup and readiness; run it after ApplicationReadyEvent or asynchronously.
  • When does destruction not happen? On SIGKILL or a JVM crash.
  • Who triggers destruction in Boot? A JVM shutdown hook that closes the context.
