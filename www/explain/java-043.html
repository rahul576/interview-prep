How would you implement API rate limiting for a distributed Spring Boot service?

System Design · design · levels senior, lead

In one line

Distributed rate limiting picks a key (user, API key, IP), an algorithm (token bucket, sliding window, leaky bucket), keeps counters in a shared atomic store like Redis, enforces at the gateway or a filter, and returns HTTP 429 with Retry-After.

Detailed explanation

Rate limiting protects services from abuse, noisy clients and overload, and enforces commercial tiers. With many Spring Boot instances, in-memory counters are wrong: each instance would allow the full limit, so the effective limit scales with replica count. Counters must live in a shared store, usually Redis, updated atomically.

Algorithms:

  • Fixed window: count per minute; simple, but allows 2x bursts at window boundaries.
  • Sliding window log/counter: smoother; the counter variant weights the previous window.
  • Token bucket: tokens refill at a rate up to a capacity; each request takes a token. Allows controlled bursts and is the most common choice.
  • Leaky bucket: requests drain at a constant rate; smooths output, good for protecting downstreams.

Atomicity: the read-compute-write must be one step, via a Lua script in Redis or a library such as Bucket4j (with Lettuce/Redisson backends) or Resilience4j for local limits. Spring Cloud Gateway has a built-in RequestRateLimiter filter backed by Redis using a token bucket.

Placement: enforce at the edge (API gateway, Spring Cloud Gateway) so rejected traffic is cheap; add finer limits in a servlet filter or interceptor where business context exists. Responses use 429 Too Many Requests, a Retry-After header, and informative headers such as X-RateLimit-Remaining (or the IETF RateLimit headers).

Also decide failure behaviour: if Redis is down, fail open (allow, with a local fallback limit) for most APIs, or fail closed for sensitive ones like login.

How it works

  1. Resolve key from the request: API key > user ID > client IP.
  2. Look up tier limits (e.g. free 100/min, pro 1,000/min).
  3. Run an atomic Lua script: refill tokens based on elapsed time, consume if available.
  4. Allowed -> continue and set remaining-quota headers.
  5. Rejected -> 429 with Retry-After; increment a metric.
  6. Dashboards and alerts on rejection rates per key.

Example

spring:
  cloud:
    gateway:
      routes:
        - id: orders
          uri: lb://orders-service
          predicates: [ Path=/api/orders/** ]
          filters:
            - name: RequestRateLimiter
              args:
                redis-rate-limiter.replenishRate: 50     # tokens per second
                redis-rate-limiter.burstCapacity: 100    # bucket size
                redis-rate-limiter.requestedTokens: 1
                key-resolver: "#{@apiKeyResolver}"
@Bean
KeyResolver apiKeyResolver() {
    return exchange -> Mono.justOrEmpty(
        exchange.getRequest().getHeaders().getFirst("X-API-Key")).defaultIfEmpty("anonymous");
}

Common mistakes

  • Per-instance counters in a multi-instance deployment.
  • Non-atomic GET then SET in Redis, allowing races.
  • Limiting only by IP, punishing users behind corporate NAT.
  • Returning 503 or 400 instead of 429 without Retry-After.
  • No plan for Redis being unavailable.

How to answer in the interview

"I'd first choose the key, usually API key or user, and the limits per tier. I'd use a token bucket, which allows controlled bursts, or a sliding window for smoother limits. Because we have many instances, counters live in Redis and are updated atomically with a Lua script, or via Bucket4j or Spring Cloud Gateway's Redis rate limiter. I'd enforce at the gateway, return 429 with Retry-After and quota headers, decide to fail open with a local fallback if Redis is down, and monitor rejections per client."

Likely follow-up questions

  • Legitimately bursty batch client? Larger burst capacity, a separate batch endpoint or quota, or async job submission.
  • Global limits across regions? Per-region budgets, or accept approximate limits with periodic sync.
  • Token bucket vs leaky bucket? Token bucket allows bursts; leaky bucket enforces a steady outflow.
