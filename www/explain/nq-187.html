What are the different bean scopes in Spring?

Spring Framework · concept · levels entry

In one line

Spring core has singleton (default, one per container) and prototype (new instance per request to the container); web contexts add request, session, application and websocket; you set them with @Scope, and injecting a shorter-lived bean into a singleton needs a scoped proxy or ObjectProvider.

Detailed explanation

A bean's scope defines how many instances exist and how long each lives.

singleton is the default: one shared instance per ApplicationContext, created at startup and destroyed when the context closes. Most services, repositories and controllers are singletons, so they must be stateless or thread-safe.

prototype creates a new instance every time the bean is requested from the container (getBean, or each injection point). Spring creates and initialises it but does not manage its destruction.

Web-aware contexts add four more. request: one instance per HTTP request, ideal for request context such as the current user or correlation id. session: one per HTTP session, for example a wizard's state (rarely used in stateless REST APIs). application: one per ServletContext, similar to singleton but visible as a ServletContext attribute and shared across contexts in the same web app. websocket: one per WebSocket session. You can also register custom scopes, for example Spring Batch's step and job scopes or Spring Cloud's refresh scope.

You declare scope with @Scope("prototype"), constants like ConfigurableBeanFactory.SCOPE_PROTOTYPE, or shortcuts such as @RequestScope, @SessionScope and @ApplicationScope.

The important trap is scope mismatch. A singleton is wired once, so if it depends on a prototype or request bean, it keeps the first instance forever (or fails at startup for a request bean with no active request). The fixes are a scoped proxy (proxyMode = ScopedProxyMode.TARGET_CLASS, built into @RequestScope), ObjectProvider<T> lookups, or @Lookup methods.

How it works

  1. The bean definition records its scope.
  2. Singleton: created once and cached in the singleton registry.
  3. Prototype: created fresh on every lookup.
  4. Web scopes: stored in the current request, session or ServletContext attributes.
  5. A scoped proxy resolves the right target instance on every method call.

Example

@Component
@Scope(ConfigurableBeanFactory.SCOPE_PROTOTYPE)
class ReportBuilder { private final List<String> lines = new ArrayList<>(); }

@Component
@RequestScope
class RequestContext { String userId; String correlationId; }

@Service
class ReportService {
    private final ObjectProvider<ReportBuilder> builders;
    private final RequestContext ctx;              // proxy, resolves per request
    ReportService(ObjectProvider<ReportBuilder> b, RequestContext ctx) {
        this.builders = b; this.ctx = ctx;
    }
    Report build() { ReportBuilder rb = builders.getObject(); /* fresh each time */ return rb.build(); }
}

Common mistakes

  • Injecting a prototype into a singleton and expecting new instances.
  • Keeping mutable state in singletons.
  • Using request-scoped beans in @Async or scheduled threads.
  • Relying on session scope in horizontally scaled stateless services.

How to answer in the interview

"Spring core has two scopes: singleton, the default, one shared instance per context, and prototype, a new instance each time it's requested from the container. Web contexts add request, session, application and websocket. I set scope with @Scope or shortcuts like @RequestScope. The trap is injecting a shorter-lived bean into a singleton: it's wired once, so I use a scoped proxy or ObjectProvider to get the right instance each time."

Likely follow-up questions

  • Prototype injected into singleton? Created once at injection; use ObjectProvider or @Lookup.
  • Are singletons thread-safe? Only if you make them so; Spring adds no synchronisation.
  • Refresh scope? Spring Cloud scope that recreates beans when configuration changes.
