When did you last practise a model rollback, and what makes rollbacks fail in ML systems?

MLOps · scenario · levels senior, lead

In one line

Rollbacks must be practised in drills, not just documented; ML rollbacks fail when old artefacts or images were deleted, the feature schema changed so the old model is incompatible, serving input schemas changed, or only one person can do it. The fix is a registry alias switch plus automated redeploy anyone on call can run.

Detailed explanation

An untested rollback plan tends to fail at 3 a.m. I schedule rollback drills, for example quarterly or with each major release, where we actually switch production back to the previous model in staging or even production and time it. If I'm asked when I last practised one, I should be able to give a date and a duration.

Why ML rollbacks fail:

  • Retention policies deleted the previous model artefact, or the container image it needs was garbage-collected from the registry.
  • The feature pipeline changed: the new model needed new or redefined features, and the old features are no longer computed, or a feature changed meaning (for example, a unit change), so the old model is silently wrong.
  • The serving code's input schema changed, and the old model can't parse requests.
  • Permissions or knowledge sit with one person; nobody on call can do it.
  • Stateful dependencies, such as caches of predictions or downstream thresholds tuned for the new model, are not rolled back.

A robust setup keeps several previous versions in the registry with pinned images, keeps feature changes backward compatible or versioned (new features alongside old for a transition period), and makes rollback one automated step: move the production alias back and let the deployment pipeline redeploy. Runbooks, permissions for the on-call rota and post-rollback verification close the gap.

How it works

  1. Retain the last N production models and their images; exclude them from cleanup.
  2. Version features; keep old features computed until the old model is retired.
  3. Implement rollback as an alias change triggering GitOps or CD.
  4. Grant the on-call group the needed permissions.
  5. Drill regularly and record time to restore.
  6. Verify after rollback with smoke tests and metrics.

Example

from mlflow import MlflowClient
c = MlflowClient()
# roll back: point champion alias at the previous version
c.set_registered_model_alias("fraud-model", "champion", version="13")
# CD watches the alias and redeploys version 13 with its pinned image

Common mistakes

  • Only documenting the rollback, never executing it.
  • Image registry cleanup policies that delete old serving images.
  • Breaking feature changes shipped together with a model.
  • Rollback requires the data scientist who trained the model.

How to answer in the interview

"A rollback plan that's never exercised usually fails, so we run drills, for example quarterly, where we actually switch back and time it. The usual failure reasons are that the previous model or its image was deleted by retention, the feature pipeline changed so the old model is incompatible, the serving schema changed, or only one person has the access. So we keep several versions with pinned images, version features with a transition period, and make rollback a single automated step: move the production alias back and redeploy, runnable by anyone on call."

Likely follow-up questions

  • How do you roll back when the new model needed a new feature pipeline? Run old and new feature versions in parallel until the new model is confirmed, so rollback needs no pipeline change.
  • What is a good rollback time target? Minutes, measured in drills.
  • When do you prefer roll-forward? When the issue is a small fix and rollback has higher risk, still within the SLO.
