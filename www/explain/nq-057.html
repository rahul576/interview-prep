How would you create new product objects rather than modifying existing objects?

Coding Exercises · scenario · levels mid

In one line

In the map step, return a new instance — via the constructor, a wither method on a record, or Lombok's toBuilder() — instead of calling setters, so the original objects stay unchanged and the code is safe to share and correct with parallel streams.

Detailed explanation

Immutability means an object's state never changes after construction. Transformations then create new objects rather than modifying old ones. This gives several benefits:

  • Reasoning: a Product you received cannot change behind your back.
  • Thread safety: immutable objects can be shared between threads without locks.
  • Parallel streams and caching: no shared mutable state means no races; immutable objects are safe as map keys and cache values.
  • Auditability: old and new versions both exist, so you can compare or roll back.

Approaches:

  1. Constructor copy — call the full constructor with one value changed. Simple, but noisy and error-prone with many fields.
  2. Record with a wither — records (Java 16+) are immutable data carriers. Add a method like withPrice that returns a copy with one field changed. Callers read naturally: p.withPrice(p.price() * 0.85). (Language-level "withers" for records are being explored in a JDK enhancement proposal, but are not standard yet, so write them by hand.)
  3. Builder with toBuilder — Lombok's @Builder(toBuilder = true) or a hand-written builder: p.toBuilder().price(newPrice).build(). Good for classes with many fields.
  4. Lombok's @With generates wither methods automatically.

The pipeline then becomes products.stream().map(p -> p.withPrice(p.price() * 0.85)).toList(), returning a new list of new objects; the original list and objects are untouched.

Costs: each change allocates an object. For typical business code the cost is negligible — the JVM's young-generation GC handles short-lived objects cheaply. It matters only for very large collections in hot paths, or when objects are large graphs; then you measure.

How it works

  1. Make fields final (or use a record) and drop setters.
  2. Provide a copy method: wither, builder or constructor.
  3. In map, create a new object with the changed value.
  4. Collect into a new list.
  5. Original objects remain valid and unchanged.

Example

record Product(String name, String category, double price, int stock) {
    Product withPrice(double newPrice) {
        return new Product(name, category, newPrice, stock);
    }
}

List<Product> discounted = products.stream()
        .map(p -> p.withPrice(p.price() * 0.85))
        .toList();

// constructor copy for a classic class
.map(p -> new Product(p.getName(), p.getCategory(), p.getPrice() * 0.85, p.getStock()))

// Lombok
@Value @Builder(toBuilder = true)
class Item { String name; String category; double price; int stock; }
.map(i -> i.toBuilder().price(i.getPrice() * 0.85).build())

Common mistakes

  • Records containing mutable fields like a List, which leak mutability; copy with List.copyOf.
  • Forgetting to copy one field in the constructor approach.
  • Creating new objects but then mutating them anyway.
  • Over-worrying about allocation cost without measuring.

How to answer in the interview

"In the map step I return a new instance instead of calling setters, for example new Product with the same fields and price times 0.85. With a record I'd add a wither method like withPrice, so the pipeline reads map(p -> p.withPrice(p.price() * 0.85)). With Lombok, toBuilder or @With does the same. The original list and objects stay unchanged, which makes the code easier to reason about, safe to share between threads, and correct with parallel streams. The cost is extra allocation, which is usually negligible."

Likely follow-up questions

  • What are the costs of new objects per change? Allocation and GC work, usually tiny; relevant only for huge hot-path collections.
  • Are records deeply immutable? No, only shallowly; defensive copies for mutable components.
  • How do JPA entities fit? They are mutable by design; use immutable DTOs outside the persistence layer.
