Can finally ever fail to execute?

Exceptions · concept · levels mid, senior

In one line

Normally finally always runs, even after return, break or an exception; it does not run if the JVM stops (System.exit, Runtime.halt, crash, kill -9, OOM killer), if the try never completes (infinite loop, deadlock), or for daemon threads when the JVM exits.

Detailed explanation

The Java Language Specification guarantees that when control leaves a try block, by any means, the finally block executes. That covers normal completion, return, break, continue and thrown exceptions, including Errors like StackOverflowError (although in severe cases like OOM, the finally itself may fail).

Finally does not run when control never leaves the try block in the normal sense:

  • System.exit(status) starts JVM shutdown: shutdown hooks run, but the calling thread never returns from exit, so its finally blocks don't execute. Runtime.halt() is more abrupt: no hooks either.
  • JVM crash: a native crash (SIGSEGV in JNI code, a JVM bug), producing an hs_err_pid file.
  • Process killed: kill -9 (SIGKILL), the Linux/Kubernetes OOM killer when a container exceeds its memory limit, or the orchestrator forcing termination after the grace period. Note that a normal kill (SIGTERM) triggers shutdown hooks, but not finally blocks of running threads.
  • The try never finishes: infinite loop, deadlock or a thread blocked forever.
  • Daemon threads: when the last non-daemon thread ends, the JVM exits and daemon threads are abandoned mid-execution, finally or not.
  • Hardware or power failure.
  • A thread killed with the deprecated Thread.stop() would actually run finally (it throws ThreadDeath), but stop now throws UnsupportedOperationException in recent JDKs.

So finally is reliable for in-process cleanup (locks, buffers), but not for durable or cross-process guarantees. Use transactions, idempotent operations, write-ahead logs, outbox patterns, leases with expiry for distributed locks, and graceful shutdown handling (shutdown hooks, Spring's graceful shutdown).

How it works

  1. Compiler duplicates finally code on every exit path of the try/catch.
  2. Exceptions are routed via the exception table to the finally handler.
  3. If the thread never reaches an exit path, or the process stops, that code never executes.

Example

try {
    System.out.println("in try");
    System.exit(0);
} finally {
    System.out.println("finally");     // never printed
}

static int value() {
    try { return 1; }
    finally { System.out.println("runs before return"); }  // printed
}

Thread t = new Thread(() -> {
    try { Thread.sleep(10_000); }
    catch (InterruptedException ignored) { }
    finally { System.out.println("daemon finally"); }       // not printed if JVM exits
});
t.setDaemon(true); t.start();          // main ends -> JVM exits

Common mistakes

  • Saying finally "always, 100% runs" with no exceptions.
  • Relying on finally to release a distributed lock with no TTL.
  • Calling System.exit from library or request-handling code.
  • Assuming SIGTERM runs finally blocks of busy threads.

How to answer in the interview

"Normally finally runs even if the try block returns, breaks or throws. It can fail to run in a few cases: if code calls System.exit or Runtime.halt, the JVM shuts down without finishing that thread's finally; if the JVM crashes or the process is killed with kill -9 or by the Kubernetes OOM killer; if the try never completes because of an infinite loop or deadlock; and daemon threads are abandoned when the JVM exits. And obviously power loss. So I use finally for in-process cleanup, but for critical cross-process state I rely on transactions, idempotency and locks with expiry."

Likely follow-up questions

  • What happens if both try and finally contain a return statement? Finally's return wins, discarding the try's value and any exception.
  • Do shutdown hooks run on System.exit? Yes, but not on halt or kill -9.
  • Do finally blocks run on SIGTERM? Not for running threads; shutdown hooks do.
