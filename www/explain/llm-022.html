How do you reduce end-to-end latency of an LLM-powered feature?

LLMOps & RAG · concept · levels mid, senior

In one line

Measure first, then stream for perceived latency, use smaller or faster models where quality allows, cut tokens (especially output), apply prompt caching, parallelise or merge sequential calls, keep retrieval fast, and deploy close to users without cold starts.

Detailed explanation

End-to-end latency of an LLM feature is the sum of network hops, queueing, time to first token (prefill), generation time (output tokens x time per token), and every sequential step around the model: retrieval, reranking, tool calls and extra model calls. Trace it with spans (OpenTelemetry) to know which part dominates before optimising.

Perceived latency. Streaming shows the first words within a second even if the full answer takes ten. Show progress for multi-step agents ("searching documents...").

Generation time. It scales with output length, so ask for concise answers, use max tokens, avoid verbose formats, and for reasoning models choose an appropriate reasoning effort or thinking budget. Use smaller, faster models for simple steps (routing, classification, query rewriting) and keep large models for the final hard step. Providers also offer lower-latency tiers or faster model variants.

Prefill. Long stable prompts benefit from prompt caching, which cuts TTFT substantially. Trim unnecessary context: fewer, better retrieved chunks after reranking.

Workflow shape. Chains of model calls add up. Run independent calls in parallel (for example query rewriting and intent classification, or several retrievals), merge steps into one call when possible, and use speculative execution, such as starting retrieval before the classifier finishes. Avoid unnecessary agent loops when a fixed pipeline works.

Retrieval. Vector search should be milliseconds (ANN index, warm cache); rerankers add tens to hundreds of ms, so limit candidate counts and use fast reranker models.

Infrastructure. Deploy services in the same region as the model endpoint and close to users, reuse HTTP connections, avoid cold starts on serverless and on self-hosted GPUs, and for self-hosting tune batch size versus inter-token latency. Semantic or exact caching of frequent answers eliminates calls entirely.

How it works

  1. Trace a request end to end; find the largest spans.
  2. Enable streaming and progress feedback.
  3. Reduce output and input tokens; enable caching.
  4. Parallelise independent steps; downsize simple ones.
  5. Tune retrieval and infrastructure; re-measure p95.

Example

import asyncio
async def answer(q):
    intent, rewritten = await asyncio.gather(classify(q, model="small"), rewrite(q, model="small"))
    chunks = await hybrid_search(rewritten, k=30)
    top = await rerank(rewritten, chunks, top_n=5)
    async for tok in stream_answer(q, top, model="large", max_tokens=400):
        yield tok

Common mistakes

  • Optimising model choice while the real bottleneck is a slow retriever or tool.
  • Sequential calls that could run in parallel.
  • Verbose outputs and no max tokens.
  • Benchmarking from a different region than production.

How to answer in the interview

"I start by tracing where the time goes: queueing, time to first token, generation and the number of sequential model and tool calls. Streaming fixes most perceived latency in chat. Generation time scales with output length, so I ask for concise outputs, set max tokens and use smaller models for simple steps. Prompt caching cuts time to first token for long stable prompts. I run independent calls in parallel and merge chains where possible, keep retrieval and reranking fast, and deploy close to users and the model endpoint while avoiding cold starts."

Likely follow-up questions

  • Which RAG step dominates? Usually final generation; then reranking or query rewriting calls.
  • Is caching answers safe? For stable, non-personal queries with TTLs and invalidation.
  • Reasoning models and latency? Tune reasoning effort; use them only where needed.
