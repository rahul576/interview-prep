How do you ensure that an API returns the correct HTTP response?

REST & API Design · scenario · levels mid

In one line

Choose status codes deliberately with ResponseEntity or @ResponseStatus, map exceptions centrally in a @RestControllerAdvice (400, 401, 403, 404, 409, 422, 500), return a consistent ProblemDetail (RFC 9457) body, and prove it with MockMvc and contract tests.

Detailed explanation

A correct HTTP response means the right status code, the right headers and a predictable body. Clients, gateways, retries and monitoring all make decisions on the status code, so a 200 with {"error": ...} breaks caching, alerting and retry logic.

On the success path, controllers return ResponseEntity to be explicit: ok for reads, created(location) for a POST that creates a resource, accepted for asynchronous work, noContent for deletes. @ResponseStatus on a method is a lighter option when the code never changes.

On the error path, I never handle exceptions in each controller. A @RestControllerAdvice with @ExceptionHandler methods translates domain and framework exceptions into codes: MethodArgumentNotValidException to 400 with field errors, missing authentication to 401, insufficient rights to 403, not found to 404, duplicates or optimistic-lock version conflicts to 409, semantically invalid business rules often to 422, and anything unexpected to 500 with a generic message and a correlation id, never a stack trace. Spring Framework 6 has ProblemDetail and ErrorResponse, implementing RFC 9457 (which replaced RFC 7807), so every error has type, title, status, detail and instance. Setting spring.mvc.problemdetails.enabled=true makes the built-in exceptions use it too.

Finally I verify: @WebMvcTest with MockMvc asserts status, headers and JSON for success and failure cases, and contract tests check the responses against the OpenAPI specification.

How it works

  1. Define the status codes per endpoint in the OpenAPI contract.
  2. Return ResponseEntity with the matching code and headers (Location, ETag, Retry-After).
  3. Throw meaningful domain exceptions from services.
  4. Map them in one @RestControllerAdvice to ProblemDetail.
  5. Test each path with MockMvc and run contract tests in CI.

Example

@RestControllerAdvice
class ApiErrors {
    @ExceptionHandler(OrderNotFoundException.class)
    ProblemDetail notFound(OrderNotFoundException ex) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
        pd.setTitle("Order not found");
        return pd;
    }
    @ExceptionHandler(OptimisticLockingFailureException.class)
    ProblemDetail conflict() {
        return ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT, "Order was modified, reload and retry");
    }
}

@WebMvcTest(OrderController.class)
class OrderControllerTest {
    @Autowired MockMvc mvc;
    @MockitoBean OrderService service;

    @Test void missingOrderReturns404() throws Exception {
        when(service.find(9L)).thenThrow(new OrderNotFoundException(9L));
        mvc.perform(get("/api/v1/orders/9"))
           .andExpect(status().isNotFound())
           .andExpect(jsonPath("$.title").value("Order not found"));
    }
}

Common mistakes

  • Returning 200 for errors with an error flag in the body.
  • Returning 500 for client mistakes such as invalid input.
  • Mixing up 401 (not authenticated) and 403 (authenticated but not allowed).
  • Leaking stack traces or SQL messages in error responses.
  • Only testing the happy path.

How to answer in the interview

"I treat status codes as part of the contract. Controllers return ResponseEntity explicitly, so a create returns 201 with a Location header, a delete 204. Errors are mapped in one place, a RestControllerAdvice, which turns validation failures into 400 with field errors, missing resources into 404, version conflicts and duplicates into 409, and unknown errors into 500 without leaking internals. The body is always a ProblemDetail, the RFC 9457 format, so clients parse one shape. Then I prove it with WebMvcTest and MockMvc for success and error cases, plus contract tests against the OpenAPI spec."

Likely follow-up questions

  • What status should a business rule violation return? Usually 422 Unprocessable Content, or 409 if it conflicts with current resource state; be consistent.
  • 401 or 403 for an expired token? 401, with a WWW-Authenticate header.
  • How do you add a correlation id to errors? Put the trace id into the ProblemDetail as a property and into logs.
