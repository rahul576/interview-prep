When do you choose batch processing versus stream processing, and what are lambda and kappa architectures?

Distributed Systems · concept · levels mid, senior

In one line

Batch processes bounded data periodically for throughput and simple reprocessing; streaming processes unbounded events continuously for low latency. Lambda runs both layers; Kappa uses one streaming pipeline with replay for reprocessing.

Detailed explanation

Batch (Spark, dbt, warehouse SQL, Airflow-scheduled): fixed input like "yesterday's orders", easy to reason about, easy to re-run, high throughput, latency of minutes to hours. Great for reports, billing, ML training, backfills.

Streaming (Flink, Kafka Streams, Spark Structured Streaming, Beam/Dataflow): events processed as they arrive with seconds of latency. Must handle state, event time vs processing time, late and out-of-order events (watermarks), and exactly-once concerns. Great for fraud detection, alerting, real-time dashboards, personalisation.

Lambda architecture: batch layer recomputes accurate results from all data; a speed layer gives recent approximate results; a serving layer merges. Downside: two code paths to keep consistent.

Kappa architecture: only streaming; to reprocess, start a new job version reading the log (Kafka with long retention or a lakehouse table) from the beginning, then switch over. Modern engines unify batch and stream (Flink, Spark, Beam), making Kappa-style common.

How it works

  1. Events → Kafka (and archived to lakehouse).
  2. Streaming job → real-time outputs.
  3. Need to fix a bug? Deploy v2 reading from offset 0 / table history → catch up → switch consumers → retire v1.
  4. Batch jobs for heavy historical analytics.

Example

-- Flink SQL: revenue per minute by event time
SELECT window_start, SUM(amount) FROM TABLE(
  TUMBLE(TABLE orders, DESCRIPTOR(order_time), INTERVAL '1' MINUTE))
GROUP BY window_start;

Common mistakes

  • Streaming everything when daily batch is enough.
  • Processing-time windows for business metrics.
  • Short Kafka retention making replay impossible.

How to answer in the interview

"I choose by latency need. Reports, billing and model training are batch: simple and easy to rerun. Fraud detection or live dashboards need streaming with event-time windows and watermarks. Lambda runs both and merges, at the cost of two codebases; Kappa uses a single streaming pipeline and reprocesses by replaying the log. Today I'd lean Kappa-style with a unified engine and keep raw events in a lakehouse for replay."

Likely follow-up questions

  • Reprocess six months after a bug? New job version from archived events, side-by-side, then swap outputs.
  • Watermarks? Event-time progress markers that close windows.
  • Micro-batching? Spark Structured Streaming processes small batches; latency ~100 ms–seconds.
