How does graceful shutdown work for containers, and how do you get it right?

Docker · concept · levels senior

In one line

On stop, the runtime sends SIGTERM (or STOPSIGNAL), waits a grace period, then sends SIGKILL; getting it right requires the app to receive the signal (PID 1 / init), handle it by draining work, a grace period longer than the drain, and removing traffic first via load balancer deregistration or readiness.

Detailed explanation

docker stop sends the container's stop signal, SIGTERM by default or whatever the Dockerfile's STOPSIGNAL specifies (nginx uses SIGQUIT for graceful shutdown). It then waits the timeout, 10 seconds by default (--time, --stop-timeout, or stop_grace_period in Compose), and finally sends SIGKILL, which cannot be caught. Kubernetes does the same with terminationGracePeriodSeconds (30 seconds default), after running any preStop hook.

Graceful shutdown needs four pieces to line up. First, signal delivery: the application must be PID 1 through the exec form or exec "$@", or run under an init like tini that forwards signals; a shell PID 1 swallows SIGTERM. Second, handling: on SIGTERM the app stops accepting new connections, finishes in-flight requests, stops consuming from queues, commits offsets or acknowledges messages, flushes buffers and closes database connections. Frameworks help: server.shutdown=graceful with spring.lifecycle.timeout-per-shutdown-phase in Spring Boot, server.close() in Node, Shutdown(ctx) in Go's http.Server, Gunicorn's graceful worker timeout.

Third, the grace period must exceed the drain time; otherwise SIGKILL arrives mid-request, producing errors, duplicated or lost messages. Fourth, traffic removal: the load balancer must stop sending new requests before the app closes. In Kubernetes, endpoint removal and SIGTERM happen in parallel, so a short preStop sleep (5-10 s), or failing readiness, gives kube-proxy, ingress controllers and cloud load balancers time to update. With cloud load balancers, the deregistration delay or connection draining setting must fit inside the grace period.

How it works

  1. Orchestrator marks the instance terminating and starts traffic removal.
  2. Optional preStop hook delays shutdown.
  3. Stop signal reaches the application.
  4. App stops accepting work and drains in-flight work.
  5. App exits 0; if the grace period expires, SIGKILL is sent.

Example

# Kubernetes
spec:
  terminationGracePeriodSeconds: 45
  containers:
    - name: orders
      image: ghcr.io/acme/orders@sha256:<digest>
      lifecycle:
        preStop:
          sleep: { seconds: 10 }      # or exec: ["sleep","10"] on older clusters
      readinessProbe:
        httpGet: { path: /actuator/health/readiness, port: 8080 }
# Spring Boot
server.shutdown=graceful
spring.lifecycle.timeout-per-shutdown-phase=25s
# Compose
services:
  worker:
    stop_grace_period: 60s
    stop_signal: SIGTERM

Common mistakes

  • Shell-form CMD, so the app never sees SIGTERM.
  • Drain timeouts longer than the grace period.
  • Closing the server immediately while the load balancer still routes traffic.
  • Queue consumers that ack messages before finishing work, or never commit offsets on shutdown.

How to answer in the interview

"When a container stops, Docker sends SIGTERM or the STOPSIGNAL, waits the grace period, 10 seconds by default or stop_grace_period in Compose, then sends SIGKILL. To get it right, the app must actually receive the signal, so it must be PID 1 via exec form or run under an init that forwards signals. It must handle SIGTERM by stopping new work, finishing in-flight requests or messages, committing offsets and closing connections, for example server.shutdown=graceful in Spring Boot. The grace period must be longer than that drain time, and traffic must be removed first through load balancer deregistration, a preStop delay or failing readiness."

Likely follow-up questions

  • What happens if the grace period is too short? SIGKILL cuts in-flight requests, causing errors and possibly duplicate or lost work.
  • Why a preStop sleep in Kubernetes? Endpoint removal is asynchronous, so the delay lets proxies stop routing first.
  • How do you test it? Load test while rolling a deployment and watch for errors.
