What is the N+1 query problem in Hibernate/JPA, and how do you fix it?

Spring Data & JPA · concept · levels mid, senior

In one line

The N+1 problem is one query to load N parents plus one extra query per parent when a lazy association is accessed; fix it with JOIN FETCH, @EntityGraph, batch fetching (@BatchSize, default_batch_fetch_size) or DTO projections, and detect it with SQL logging, Hibernate statistics or query-count tests.

Detailed explanation

Suppose you load 100 orders with findAll() and then, in a loop or during JSON serialisation, call order.getCustomer().getName() or order.getLines(). Each association is lazy, so Hibernate fires a separate SELECT for each order: 1 query for the orders plus 100 for the associations. With nested associations it becomes N×M. Each query is fast, but network round trips add up, turning a 20 ms page into seconds and loading the database.

It is caused by lazy loading accessed per entity, often hidden: in a mapper, a toString(), Jackson serialising entities, or with open-session-in-view letting lazy loads happen in the controller. Eager mapping does not fix it; FetchType.EAGER on @ManyToOne still causes N+1 when you query with JPQL, because Hibernate runs the main query and then loads each eager association separately.

Fixes, per use case:

  • JOIN FETCH in JPQL: select o from Order o join fetch o.customer where ... loads both in one SQL join.
  • @EntityGraph(attributePaths = {"customer", "lines"}) on a Spring Data method does the same declaratively.
  • Batch fetching: @BatchSize(size = 50) or hibernate.default_batch_fetch_size=50 makes Hibernate load lazy associations for many parents with one IN (...) query, turning N+1 into 1 + N/50. A good global default.
  • DTO or interface projections selecting only the columns needed, which avoids entities altogether for read views.
  • Subselect fetching (@Fetch(FetchMode.SUBSELECT)) for collections.

Watch out when fetching collections: join fetching one collection multiplies rows (use distinct, which Hibernate 6 applies automatically to entity results), and join fetching two bag collections throws MultipleBagFetchException; with sets it creates a Cartesian product. Fetch one collection per query or rely on batch fetching. Pagination with collection fetch joins happens in memory (Hibernate warns), so paginate IDs first.

How it works

  1. Detect: enable SQL logging or statistics and look for repeated identical SELECTs.
  2. Identify the access path that triggers lazy loads.
  3. Choose a fetch plan for that use case: join fetch, entity graph, batch or projection.
  4. Verify the query count in a test.
  5. Keep associations lazy by default.

Example

public interface OrderRepository extends JpaRepository<Order, Long> {

    @Query("select o from Order o join fetch o.customer where o.status = :status")
    List<Order> findWithCustomer(@Param("status") Status status);

    @EntityGraph(attributePaths = "lines")
    List<Order> findByCustomerId(long customerId);

    @Query("select new com.acme.OrderSummary(o.id, c.name, o.total) from Order o join o.customer c")
    List<OrderSummary> summaries();
}
spring:
  jpa:
    properties:
      hibernate:
        default_batch_fetch_size: 50
        generate_statistics: true   # dev only
logging:
  level:
    org.hibernate.SQL: debug

Common mistakes

  • Switching to EAGER, which spreads the problem everywhere.
  • Join fetching two List collections (MultipleBagFetchException) or causing Cartesian products.
  • Paginating with a collection join fetch.
  • Serialising entities directly in REST responses.

How to answer in the interview

"N+1 is when I load N parents with one query and then accessing a lazy association on each fires one more query per parent. It usually comes from lazy loading in a loop or from serialising entities. I fix it per use case with JOIN FETCH or an EntityGraph, set Hibernate batch fetching so lazy loads are grouped into IN queries, or use DTO projections for read views. I detect it with SQL logging, Hibernate statistics or tests that assert the number of queries."

Likely follow-up questions

  • JOIN FETCH two collections? MultipleBagFetchException for lists, Cartesian product for sets; fetch separately.
  • Pagination with fetch join? Page the IDs, then fetch entities by IDs.
  • Does EAGER solve it? No, it still issues extra queries and can't be turned off per query.
