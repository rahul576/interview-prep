How does state locking work with the S3 and Azure Storage backends today?

Terraform · concept · levels mid, senior

In one line

State locking makes sure only one run writes state at a time; the S3 backend now supports native locking with use_lockfile = true (a .tflock object using S3 conditional writes) and DynamoDB locking is deprecated, while the azurerm backend locks via a blob lease.

Detailed explanation

If two people or pipelines apply against the same state concurrently, both read version N, both make changes, and the second write overwrites the first. The state then misses real resources, and later plans try to recreate them. Locking prevents this: Terraform acquires a lock before operations that may write state (plan, apply, import, state commands), and releases it at the end. If another process holds it, the command fails or waits for -lock-timeout.

For S3, Terraform historically used a separate DynamoDB table with a LockID key. Since S3 added conditional writes, Terraform 1.10 introduced native S3 locking with use_lockfile = true, generally available from 1.11: Terraform creates a <key>.tflock object next to the state only if it does not already exist, which gives atomic lock acquisition without another service. The dynamodb_table argument is deprecated and will be removed in a future version. Teams migrate by enabling both for a transition period, so old and new clients respect the lock, then removing DynamoDB.

For Azure Storage, the azurerm backend acquires a lease on the state blob. The lease is exclusive, so a second run cannot take it. No extra resource is required, and a stuck lease can be broken from the portal or CLI.

Regardless of backend, the store itself needs protection: versioning (S3 versioning, Azure blob versioning or soft delete) so older state versions can be recovered after corruption, encryption at rest, private access, least-privilege IAM/RBAC, and ideally a separate account or subscription, since state contains sensitive values.

How it works

  1. terraform plan or apply starts.
  2. Backend tries to acquire the lock (create .tflock object or take blob lease).
  3. If it exists or is leased, the command fails or waits up to -lock-timeout.
  4. Run reads, modifies and writes state.
  5. Lock is released (object deleted, lease released).

Example

terraform {
  backend "s3" {
    bucket       = "acme-tfstate-prod"
    key          = "network/terraform.tfstate"
    region       = "eu-west-1"
    encrypt      = true
    use_lockfile = true
    # dynamodb_table = "tf-locks"   # keep during migration, then remove
  }
}

Common mistakes

  • No locking configured at all on S3.
  • Removing DynamoDB in one step while older pipelines still use it.
  • Bucket without versioning, so a corrupted state cannot be recovered.
  • Broad read access to the state bucket.
  • Disabling locking with -lock=false to "get past" an error.

How to answer in the interview

"Locking ensures only one run can write the state at a time; Terraform takes the lock before plan or apply and releases it afterwards. For S3, Terraform 1.10 introduced native locking with use_lockfile = true, which writes a .tflock object next to the state using S3 conditional writes, so DynamoDB is no longer needed, and DynamoDB locking is deprecated. During migration I enable both, then remove DynamoDB once every pipeline is on a new version. The azurerm backend locks by taking a lease on the state blob. In both cases I enable versioning, encryption and restricted access, because state contains sensitive data."

Likely follow-up questions

  • Migrating without a gap? Set both use_lockfile and dynamodb_table, upgrade all clients, then drop DynamoDB.
  • What permissions does S3 locking need? Put and delete on the .tflock object in addition to state access.
  • What is -lock-timeout? How long to retry acquiring the lock before failing.
