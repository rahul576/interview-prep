When do you compute features in real time, and when do you precompute them?

MLOps · concept · levels mid, senior

In one line

Precompute in batch slowly changing features, compute at request time features from the current request, and use streaming aggregates for features over very recent events; choose by freshness value versus latency, cost and complexity, always with identical definitions for training.

Detailed explanation

Batch features (customer tenure, 90-day average spend, product attributes, embeddings) change slowly. Compute them in daily or hourly jobs in the warehouse or Spark, materialise to an online store (Redis, DynamoDB, a feature store's online layer) for millisecond lookup, and keep the history in the offline store for training. They're cheap, simple to test and backfill.

Request-time (on-demand) features depend on the request itself: transaction amount, device fingerprint, text of the message, distance between shipping and billing address, or ratios combining request data with stored features. They can only be computed when the request arrives, inside the latency budget.

Streaming features sit between the two: counts or sums over recent windows (logins in the last five minutes, card transactions in the last hour). These are computed continuously from event streams with Flink, Spark Structured Streaming or Kafka Streams (or a feature platform's streaming engine) and written to the online store, with freshness of seconds.

Trade-off: fresher features can improve models significantly (fraud, real-time recommendations), but streaming adds infrastructure, state management, late-event handling and on-call load. I add streaming only where an experiment shows measurable lift.

Consistency: whichever method, training must use the same definitions with point-in-time correct values. Feature stores (Feast, Tecton, Databricks, SageMaker, Vertex) help by defining a feature once and generating both offline (backfilled) and online values. On-demand transformations should be the same code in training and serving.

How it works

  1. List candidate features with their required freshness.
  2. Classify: batch, streaming, or on-demand.
  3. Build batch first; measure model lift from fresher variants offline by simulating freshness.
  4. Add streaming only for features with proven value.
  5. Define all features in one registry; materialise online and offline.
  6. Monitor freshness and online/offline skew.

Example

from feast.on_demand_feature_view import on_demand_feature_view
customer_profile = FeatureView(name="customer_profile", entities=[customer],
    ttl=timedelta(days=2), schema=[Field(name="avg_spend_90d", dtype=Float32)], source=batch_src)

@on_demand_feature_view(sources=[customer_profile, txn_request],
                        schema=[Field(name="amount_vs_avg", dtype=Float64)])

    return pd.DataFrame({"amount_vs_avg": df["amount"] / (df["avg_spend_90d"] + 1)})

Common mistakes

  • Building streaming for everything "just in case".
  • Different code for training and serving features (skew).
  • No point-in-time joins, leaking future values into training.
  • Not monitoring online feature freshness.

How to answer in the interview

"Slowly changing features like tenure or 90-day spend I precompute in batch and push to an online store; that's cheap and easy to test. Features that depend on the current request, like amount or device, are computed at request time. Features over very recent events, like logins in the last five minutes, need streaming aggregates with Flink or Spark Structured Streaming. The trade-off is freshness against latency, cost and complexity, so I only add streaming where it measurably improves the model. Whatever the method, training uses the same definitions with point-in-time correctness, ideally via a feature store."

Likely follow-up questions

  • How do you measure if a fresher feature is worth it? Simulate staleness offline (compute with a 24-hour versus 1-minute lag) and compare lift, then confirm with an online test.
  • What is point-in-time correctness? Joining feature values as they were at each training event's timestamp, never later.
  • What if the online store is slow? Timeouts with defaults and a fallback model trained to tolerate missing features.
