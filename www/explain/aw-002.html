What is the AWS shared responsibility model?

Cloud (AWS) · concept · levels entry

In one line

In the shared responsibility model, AWS secures the cloud (data centres, hardware, network, virtualisation) and the customer secures what they put in the cloud (data, IAM, network rules, OS and applications), with the exact line depending on the service.

Detailed explanation

AWS is responsible for security of the cloud: data centres, hardware, the global network, and the hypervisor and software running managed services. Customers cannot audit these, so AWS provides compliance reports (SOC, ISO 27001, PCI DSS) through AWS Artifact.

The customer is responsible for security in the cloud: their data and its classification and encryption; identity and access management (who has which permissions, MFA, key management); network configuration such as security groups, NACLs and public exposure; and the guest operating system, applications and their patches where they run them.

The line moves with the service type. On EC2 (IaaS) you patch the OS, harden it, run the firewall and secure your software. On RDS AWS patches the OS and database engine within your maintenance window, but you decide who can connect, whether the instance is public, whether storage is encrypted and how long backups are kept. On S3 or Lambda AWS runs everything underneath, yet you still own bucket policies, Block Public Access, function permissions and code vulnerabilities.

Some controls are shared: patch management, configuration management, and awareness and training apply to both sides in their own layers. Most real-world cloud breaches are customer-side misconfigurations: public buckets, overly broad IAM, leaked access keys or open security groups, not failures of AWS infrastructure. Tools like AWS Config, Security Hub, GuardDuty and IAM Access Analyzer help customers fulfil their part.

How it works

  1. Identify the service type: infrastructure, container or abstracted service.
  2. AWS covers physical, hardware and virtualisation layers in every case.
  3. For each service, list what remains yours: data, IAM, network, OS, code.
  4. Apply controls: encryption, least privilege, private networking, patching.
  5. Continuously check configuration with Config rules and Security Hub.

Example

Service   AWS handles                          You handle
EC2       hardware, hypervisor                 OS patches, SG rules, app, data, IAM role
RDS       hardware, OS, DB engine patches      who connects, public access, encryption,
                                               backup retention, DB users
S3        storage infrastructure, durability   bucket policy, Block Public Access,
                                               encryption choice, object data
Lambda    servers, runtime patching            function code, dependencies, IAM role

A team leaves an S3 bucket public by mistake and customer data leaks: that is the customer's responsibility, even though S3 itself worked perfectly.

Common mistakes

  • Assuming "it's in AWS, so AWS secures it".
  • Forgetting to patch EC2 operating systems.
  • Thinking managed services need no IAM or network controls.
  • Not enabling encryption, logging and Block Public Access.

How to answer in the interview

"AWS is responsible for security of the cloud: the data centres, hardware, network and the virtualisation layer behind every service. I'm responsible for security in the cloud: my data and its encryption, IAM users and permissions, security groups and network exposure, and anything I install. Where the line sits depends on the service. On EC2 I patch the OS and secure my apps; on RDS AWS patches the engine, but I control who can connect and whether it's encrypted; on S3 I decide whether a bucket is public. Most cloud breaches are customer misconfigurations, so tools like Config, Security Hub and GuardDuty matter."

Likely follow-up questions

  • Who is responsible for a public S3 bucket leak? The customer, because bucket configuration is in the cloud.
  • Where do you get AWS compliance reports? AWS Artifact.
  • Does Lambda remove patching? OS and runtime patching move to AWS, but your code and dependencies are still yours.
