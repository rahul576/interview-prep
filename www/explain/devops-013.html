What does a load balancer do, and what is the difference between layer 4 and layer 7 load balancing?

Networking · concept · levels entry, mid

In one line

A load balancer spreads traffic across healthy backends using health checks and an algorithm; layer 4 balances TCP/UDP connections by IP and port (fast, protocol-agnostic), while layer 7 understands HTTP and can route by host, path or headers, terminate TLS and balance per request.

Detailed explanation

Load balancers give horizontal scaling (add instances behind one address), availability (failed instances are removed by health checks) and safe operations (connection draining during deploys, weighted canaries).

Layer 4 load balancers operate on the transport layer. They see source and destination IPs and ports and forward the connection to a backend without reading the payload. They're very fast, handle millions of connections, support any TCP/UDP protocol and can preserve the client IP. Examples: AWS Network Load Balancer, Azure Load Balancer, HAProxy in TCP mode, Linux IPVS. Limitation: balancing is per connection, so long-lived HTTP/2 or gRPC connections can pin all requests to one backend.

Layer 7 load balancers parse HTTP. They can route by host (api.example.com versus www), path (/api versus /static), headers or cookies, terminate TLS, add headers like X-Forwarded-For, do redirects and rewrites, sticky sessions via cookies, retries, rate limiting and WAF integration, and balance per request. Examples: AWS Application Load Balancer, Azure Application Gateway, NGINX, HAProxy (HTTP mode), Envoy, Kubernetes Ingress controllers and Gateway API implementations. They cost more CPU per request.

Algorithms: round robin (equal turns), weighted round robin (bigger instances or canaries), least connections or least outstanding requests (uneven request durations), IP hash / consistent hashing (affinity, caches), and random with two choices.

Health checks: active checks probe an endpoint like /healthz; passive checks eject backends after errors. A good health check tests real readiness, not just "process is up".

How it works

  1. Clients resolve DNS to the load balancer address.
  2. L4 forwards the connection; L7 terminates TLS and parses HTTP.
  3. The LB filters backends that pass health checks.
  4. It picks one using the algorithm and forwards the request.
  5. Unhealthy backends are removed; draining ones get no new traffic.
  6. The LB itself runs redundantly across zones.

Example

upstream app {
    least_conn;
    server 10.0.1.10:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.11:8080 max_fails=3 fail_timeout=10s;
}
server {
    listen 443 ssl;
    server_name shop.example.com;
    location /api/    { proxy_pass http://app; }
    location /static/ { root /var/www; }
}

Common mistakes

  • Health checks that don't reflect the app's ability to serve.
  • Using L4 for gRPC and overloading one backend.
  • Relying on sticky sessions instead of stateless services.
  • Forgetting the LB's own redundancy.

How to answer in the interview

"A load balancer distributes traffic across multiple backends so none is overloaded, and it removes unhealthy ones through health checks, giving availability and horizontal scaling. A layer 4 balancer works at the transport level, routing TCP or UDP connections by IP and port without looking inside, so it's very fast, like the AWS NLB. A layer 7 balancer understands HTTP, so it can route by host, path or headers, terminate TLS, do sticky sessions and balance per request, like the ALB or NGINX. Common algorithms are round robin, least connections and IP hash."

Likely follow-up questions

  • When are sticky sessions a problem? They unbalance load, break when an instance dies and hide state that should be external, such as in Redis.
  • How do you deploy without dropping requests? Readiness checks plus connection draining (deregistration delay).
  • How does the client IP reach the app? X-Forwarded-For at L7, or the PROXY protocol or IP preservation at L4.
