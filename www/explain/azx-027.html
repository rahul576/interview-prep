Which Azure Container Registry features matter for production use?

Azure · concept · levels mid, senior

In one line

For production ACR use Premium for geo-replication and private endpoints, authenticate with managed identities (AcrPull/AcrPush) and disable the admin user, use ACR Tasks for builds and base image update triggers, clean up with retention and purge, and scan with Defender for Containers; plus signing, artifact cache and artifact streaming where needed.

Detailed explanation

Premium SKU unlocks the features that matter at scale: geo-replication (one registry name with replicas in several regions, so AKS clusters pull from a nearby replica and survive a regional issue), private endpoints and firewall rules, zone redundancy, higher throughput, and content trust and retention features.

Authentication: AKS uses its kubelet identity with the AcrPull role (az aks update --attach-acr), pipelines use workload identity federation with AcrPush, and the admin user (a shared username and password) is disabled. You can also turn off anonymous pull and, with private endpoints, disable public network access. Newer ABAC repository permissions let you scope roles to repositories.

ACR Tasks build images in Azure (az acr build), run multi-step tasks, and can trigger rebuilds when a base image is updated (for example a patched mcr.microsoft.com/dotnet/aspnet image), which is a big help for keeping images patched. Artifact cache lets you cache upstream images from Docker Hub or MCR in your registry, avoiding rate limits and runtime dependency on public registries; alternatively import approved images.

Housekeeping: a retention policy for untagged manifests and scheduled acr purge tasks delete old tags, controlling storage cost. Locking important tags (write-enabled false) prevents overwrites.

Security: Defender for Containers scans images in ACR for vulnerabilities and reports them; Notation with Azure Key Vault or Trusted Signing signs images, and Ratify with Azure Policy in AKS can verify signatures before admission. Artifact streaming lets AKS start pods from large images before the full image is downloaded.

How it works

  1. Create Premium registry, enable zone redundancy and replicas in each cluster region.
  2. Private endpoints; disable public access and admin user.
  3. Grant AcrPull to clusters, AcrPush to CI identities.
  4. Configure ACR Tasks with base image triggers.
  5. Retention and purge tasks; lock release tags.
  6. Enable Defender scanning and signature verification.

Example

az acr update -n acrprod --admin-enabled false --public-network-enabled false
az acr replication create -r acrprod -l northeurope
az aks update -g rg-aks -n aks-prod --attach-acr acrprod
az acr task create -r acrprod -n purge-old --schedule "0 3 * * *" \
  --cmd "acr purge --filter 'orders/.*:.*' --ago 30d --untagged --keep 10" \
  --context /dev/null

Common mistakes

  • Using the admin user in pipelines and clusters.
  • Pulling directly from Docker Hub at runtime (rate limits, supply chain risk).
  • Mutable latest tags in production.
  • No cleanup, so storage grows forever.

How to answer in the interview

"For production I use Premium, mainly for geo-replication to every region where clusters run and for private endpoints. Clusters pull with their managed identity and AcrPull, pipelines push with federated identities, and the admin user is disabled. ACR Tasks build images and rebuild them automatically when base images are patched. Retention and purge tasks clean old images, and Defender for Containers scans for vulnerabilities. I import or cache public images instead of pulling from Docker Hub, and I sign images and verify signatures at admission, so only scanned, signed images run."

Likely follow-up questions

  • Ensure only signed images deploy? Sign with Notation, verify with Ratify and Azure Policy in AKS.
  • Why immutable tags? Guarantee that what was tested is what runs.
  • Geo-replication vs separate registries? One name and one set of permissions, automatic sync.
