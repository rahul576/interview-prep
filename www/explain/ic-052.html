How do you handle errors in Ansible playbooks?

Configuration Management · concept · levels mid

In one line

Use block / rescue / always for try-catch-finally with rollback and cleanup, failed_when and (sparingly) ignore_errors to define failure, any_errors_fatal and max_fail_percentage with serial to stop bad rollouts, and until/retries for transient errors.

Detailed explanation

By default, when a task fails on a host, Ansible stops running further tasks for that host, while other hosts continue; the play recap shows it as failed. That is reasonable for configuration, but deployments need more control.

block / rescue / always groups tasks like try/catch/finally. If any task in block fails, the rescue tasks run, for example restoring the previous configuration, switching a symlink back to the last release or rolling back a package version. Inside rescue, ansible_failed_task and ansible_failed_result describe what went wrong. always runs whether the block succeeded or failed, which is the place for cleanup such as re-enabling the host in the load balancer or removing a maintenance flag. If rescue succeeds, the host is not counted as failed (it shows as rescued), so add an explicit fail at the end of rescue if you want the run to be red.

failed_when defines what failure means for a task, beyond the exit code, such as a specific string in output. ignore_errors: true continues past an error, but it hides problems and should be reserved for genuinely expected failures; failed_when is usually more precise. ignore_unreachable handles hosts that cannot be contacted.

Rolling updates need to stop early. With serial: 2 or serial: "10%", hosts are updated in batches. max_fail_percentage aborts the play when more than the given percentage of a batch fails, and any_errors_fatal: true aborts the whole play as soon as any host fails, preventing a bad change from reaching the entire fleet.

until / retries / delay retry transient failures, such as waiting for a service to become healthy or an API to respond.

How it works

  1. Task fails → host marked failed, skipped for later tasks (default).
  2. Within a block, failure jumps to rescue.
  3. always runs in every case.
  4. Batch-level thresholds decide whether the play continues.
  5. Retries handle transient conditions before declaring failure.

Example

- hosts: web
  serial: 2
  max_fail_percentage: 0
  become: true
  tasks:
    - name: Deploy with rollback
      block:
        - name: Take out of load balancer
          ansible.builtin.command: /usr/local/bin/lb drain {{ inventory_hostname }}
          delegate_to: localhost
        - name: Deploy new config
          ansible.builtin.template:
            src: app.conf.j2
            dest: /etc/app/app.conf
            backup: true
          register: cfg
        - name: Restart app
          ansible.builtin.service: { name: app, state: restarted }
        - name: Wait for health
          ansible.builtin.uri: { url: "http://localhost:8080/health" }
          register: health
          until: health.status == 200
          retries: 10
          delay: 3
      rescue:
        - name: Restore previous config
          ansible.builtin.copy:
            src: "{{ cfg.backup_file }}"
            dest: /etc/app/app.conf
            remote_src: true
          when: cfg.backup_file is defined
        - name: Restart with old config
          ansible.builtin.service: { name: app, state: restarted }
        - name: Mark host as failed
          ansible.builtin.fail:
            msg: "Deployment failed at {{ ansible_failed_task.name }}; rolled back"
      always:
        - name: Return to load balancer
          ansible.builtin.command: /usr/local/bin/lb enable {{ inventory_hostname }}
          delegate_to: localhost

Common mistakes

  • Sprinkling ignore_errors instead of fixing or defining failure.
  • Rescue blocks that hide failures, leaving runs green.
  • No serial or failure threshold, so a bad change hits every host.
  • Cleanup placed after the block instead of in always.

How to answer in the interview

"By default a failed task stops further tasks for that host while others continue. For more control I use block, rescue and always: rescue runs if any task in the block fails, like a catch, so I can roll back to the previous config, and always runs regardless, for cleanup like putting the server back in the load balancer. failed_when defines what counts as failure, and ignore_errors is only for expected failures. For rolling updates I use serial with max_fail_percentage or any_errors_fatal so a bad change stops before it reaches the whole fleet, and until with retries for transient issues like waiting for a service."

Likely follow-up questions

  • How would you safely roll back a failed configuration change on a web server? block with a backed-up template, rescue restoring the backup and restarting, always re-enabling the host, serial batches with a zero failure threshold.
  • Does a rescued host count as failed? No, unless you add an explicit fail task.
  • any_errors_fatal vs max_fail_percentage? Abort on the first failure versus abort past a percentage threshold.
