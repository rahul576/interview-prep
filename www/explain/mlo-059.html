How do you manage ML platform infrastructure as code?

MLOps · concept · levels mid, senior

In one line

Manage the ML platform with Terraform or Bicep for workspaces, storage, registries, key vaults, private networking and GPU pools with quotas, deploy Kubernetes components via GitOps (Helm, Argo CD/Flux), promote through dev, staging and prod, bake secure defaults into modules, offer self-service project templates, and define pipelines, endpoints and monitoring as code in project repos.

Detailed explanation

An ML platform is infrastructure and deserves the same rigour: reproducible, reviewed, versioned and recoverable.

Cloud resources via Terraform (or OpenTofu) or Bicep on Azure: ML workspaces (Azure ML workspaces, SageMaker domains, Vertex AI resources), storage accounts or buckets for data and artefacts, container registries, key vaults or secret managers, networking with private endpoints and no public access, and compute: GPU node pools on AKS, EKS or GKE, or managed compute clusters with min and max nodes and quotas. Modules encode the organisation's standards.

Kubernetes platform components—Kubeflow Pipelines, KServe, MLflow, Kueue, the NVIDIA GPU Operator, Prometheus and Grafana, cert-manager—are deployed with Helm charts and GitOps (Argo CD or Flux): Git holds the desired state, controllers reconcile and detect drift.

Environments. Separate dev, staging and prod, ideally separate subscriptions or accounts, with the same modules and different variables. Changes are planned in pull requests (terraform plan output reviewed), applied to dev, then promoted.

Secure defaults built into modules: private networking, managed identities or workload identity instead of keys, encryption with customer-managed keys where required, diagnostic logging, tagging for cost allocation and policy enforcement (Azure Policy, OPA Gatekeeper).

Self-service. Teams onboard through a template or a pull request to a small config file, which creates their namespace or workspace, storage, permissions, quotas and budget alerts.

Project-level as code. Training pipelines, endpoint definitions (KServe InferenceService YAML, Azure ML endpoint YAML), monitoring and alert configuration live in each project repo and deploy through CI/CD, making a model deployment reviewable and repeatable.

How it works

  1. Write reusable modules for workspace, storage, network, compute.
  2. Compose per-environment stacks with remote state and locking.
  3. Plan in PRs; apply via pipelines with approvals for prod.
  4. Install cluster components through GitOps.
  5. Onboard teams via self-service config and templates.
  6. Keep project pipelines and endpoints as code; detect drift.

Example

module "ml_team" {
  source        = "git::https://git.internal/platform/terraform-ml-team.git?ref=v3.2.0"
  team          = "search"
  environment   = "prod"
  gpu_quota     = 8
  monthly_budget_inr = 900000
  private_only  = true
}

resource "azurerm_kubernetes_cluster_node_pool" "gpu" {
  name                  = "gpuh100"
  kubernetes_cluster_id = azurerm_kubernetes_cluster.ml.id
  vm_size               = "Standard_NC40ads_H100_v5"
  auto_scaling_enabled  = true
  min_count             = 0
  max_count             = 6
  node_taints           = ["nvidia.com/gpu=present:NoSchedule"]
}

Common mistakes

  • Creating workspaces and GPU pools by hand in the portal.
  • Public endpoints on storage and registries by default.
  • Platform IaC but model endpoints deployed manually.
  • One shared environment for experiments and production.

How to answer in the interview

"I treat the ML platform like any infrastructure. Terraform or Bicep provisions workspaces, storage, registries, key vaults, private networking and GPU node pools with quotas. Kubernetes components like Kubeflow, KServe, MLflow and Kueue are deployed through GitOps with Helm. Dev, staging and prod use the same modules with promotion. Secure defaults—private endpoints, managed identities, encryption, logging and tags—are built into modules. Teams onboard through self-service templates, and their pipelines, endpoints and monitoring are also defined as code in their repos."

Likely follow-up questions

  • Which ML resources are hardest to manage as code? Interactive notebooks, quota requests, and resources whose APIs or providers lag behind the cloud service.
  • How do you handle GPU quota increases? Requested via a tracked process; IaC references approved quotas.
  • How do you detect drift? Scheduled terraform plan and GitOps reconciliation alerts.
