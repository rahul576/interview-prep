How do you run scheduled tasks and asynchronous work safely in a multi-instance Spring Boot service?

Spring Boot · concept · levels senior, lead

In one line

@Scheduled runs methods on a schedule and @Async on another thread, but with several replicas every instance runs the schedule, so use a distributed lock (ShedLock), Quartz clustering, a Kubernetes CronJob or a queue; give @Async a bounded executor, handle exceptions, and make jobs idempotent.

Detailed explanation

@EnableScheduling plus @Scheduled(cron = "0 0 2 * * *") is easy in a single instance. Deployed as three pods, each pod has its own scheduler, so the nightly invoice job runs three times, sending triple emails or charging twice. Options:

  • ShedLock: annotate the job with @SchedulerLock; before running, it inserts or updates a lock row in a shared store (JDBC, Redis, Mongo). Only one instance wins; lockAtMostFor releases the lock if the holder crashes, lockAtLeastFor prevents rapid re-runs caused by clock skew.
  • Quartz in clustered mode: a JDBC job store coordinates instances, with misfire handling, persistent jobs and history. Heavier but more featureful.
  • Kubernetes CronJob: run the job as a separate pod on a schedule with concurrencyPolicy: Forbid, decoupled from the web replicas.
  • Queue-based: a scheduler publishes one message; workers compete for it. Good for fan-out of large work.
  • Leader election (for example Spring Integration's leader support or Kubernetes Leases) if many tasks must run on one node.

@Async pitfalls: Spring Boot auto-configures a ThreadPoolTaskExecutor (or virtual threads when enabled), but its default queue is unbounded, so under load tasks pile up in memory. Define your own executor with a bounded queue and a rejection policy. Exceptions from void async methods are lost unless you register an AsyncUncaughtExceptionHandler; CompletableFuture results must be checked. @Async is proxy-based, so self-invocation runs synchronously. The SecurityContext and MDC are not propagated automatically; use a task decorator.

Above all, jobs must be idempotent and restartable: process in batches, record progress, and tolerate a second run after a failure or a pod kill.

How it works

  1. Scheduler fires on every instance.
  2. ShedLock tries to acquire the named lock in the shared store.
  3. The winner runs the job; others skip.
  4. The lock is released at the end or after lockAtMostFor.
  5. Async work runs on a bounded pool; failures are logged and retried idempotently.

Example

@Configuration
@EnableScheduling
@EnableSchedulerLock(defaultLockAtMostFor = "PT30M")
class SchedulingConfig {
    @Bean
    LockProvider lockProvider(DataSource ds) {
        return new JdbcTemplateLockProvider(JdbcTemplateLockProvider.Configuration.builder()
            .withJdbcTemplate(new JdbcTemplate(ds)).usingDbTime().build());
    }

    @Bean(name = "mailExecutor")
    ThreadPoolTaskExecutor mailExecutor() {
        ThreadPoolTaskExecutor ex = new ThreadPoolTaskExecutor();
        ex.setCorePoolSize(4); ex.setMaxPoolSize(8); ex.setQueueCapacity(500);
        ex.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        ex.setThreadNamePrefix("mail-");
        return ex;
    }
}

@Component
class InvoiceJob {
    @Scheduled(cron = "0 0 2 * * *", zone = "Europe/Berlin")
    @SchedulerLock(name = "invoiceJob", lockAtLeastFor = "PT1M")
    void run() { invoices.createMissingForYesterday(); }   // idempotent
}

Common mistakes

  • Assuming @Scheduled runs once in a cluster.
  • Unbounded async queues hiding overload until OOM.
  • Swallowed exceptions in void @Async methods.
  • Non-idempotent jobs that double-process after a retry.
  • Lock time shorter than the job duration.

How to answer in the interview

"@Scheduled runs a method on a schedule and @Async runs it on another thread. The trap with several replicas is that every instance runs the schedule, so a nightly job executes three times. I use a distributed lock like ShedLock backed by the database or Redis, or move the job to Quartz in cluster mode, a Kubernetes CronJob, or a queue where workers compete. For @Async I configure a bounded thread pool with a rejection policy instead of relying on defaults, and handle exceptions, because they're otherwise lost. And jobs are idempotent and process in batches, so a retry after a failure is safe."

Likely follow-up questions

  • What happens to an @Async task if the pod is terminated mid-way? It is lost unless you use graceful shutdown with await-termination, or persist work in a queue or outbox.
  • ShedLock vs Quartz? ShedLock is a simple lock for existing @Scheduled methods; Quartz adds persistent jobs and misfire handling.
  • How do you monitor jobs? Metrics for last success time and duration, alert if stale.
