You get a merge conflict. How do you resolve it?

Git · scenario · levels entry, mid

In one line

A merge conflict happens when both branches changed the same lines (or one deleted a file the other edited); I find conflicted files with git status, understand both changes, edit to the correct combined result, remove the <<<<<<< ======= >>>>>>> markers, git add, finish the merge or rebase, and run the tests.

Detailed explanation

Git merges automatically when changes touch different parts of a file. It stops only when it cannot decide: both branches edited the same lines, or one modified a file the other deleted or renamed. The merge, rebase or cherry-pick pauses with the conflicted files left for you.

Inside each file Git writes conflict markers: between <<<<<<< HEAD and ======= is your branch's version, between ======= and >>>>>>> branch-name the incoming one. Setting merge.conflictStyle to zdiff3 also shows the base version, making each side's change clearer.

Resolving is not mechanically choosing "mine" or "theirs": understand the intent of both changes and write code that does both, asking the other author if unclear. Remove the markers, git add the file, then git commit or git rebase --continue. Then run the tests, because a textually clean merge can still be logically broken. git merge --abort or git rebase --abort returns to the starting state.

Prevention: small pull requests, short-lived branches and syncing with main often.

How it works

  1. Merge or rebase stops and reports conflicts.
  2. git status lists files under "both modified".
  3. Open each file (or IDE merge tool), compare ours, theirs and base.
  4. Write the correct combined code and delete the markers.
  5. git add each resolved file.
  6. git commit or git rebase --continue.
  7. Run build and tests, then push.

Example

<<<<<<< HEAD
const TIMEOUT_MS = 5000;
=======
const TIMEOUT_MS = 3000;
const MAX_RETRIES = 3;
>>>>>>> feature/retries

Main raised the timeout to 5 s for a slow partner; the feature branch added retries. The correct result keeps both intents:

# edited file now contains:
#   const TIMEOUT_MS = 5000;
#   const MAX_RETRIES = 3;
git add src/client.js
git commit            # or: git rebase --continue
npm test

Common mistakes

  • Blindly accepting one side and silently losing a teammate's change.
  • Leaving conflict markers in the code.
  • Not running tests after resolving.
  • Using --theirs/--ours for whole files without reading them.
  • Long-lived branches that make conflicts huge.

How to answer in the interview

"A conflict means both branches changed the same lines. I run git status to find the files, then use my IDE's three-way view showing my side, theirs and the base. I work out what each change intended and write code that keeps both, asking the other developer if needed. Then I remove the markers, git add, finish with git commit or git rebase --continue, and run the tests before pushing. git merge --abort gets me out of a mess. To avoid conflicts I keep branches short."

Likely follow-up questions

  • How do IDE merge tools help? They show ours, theirs and base side by side and let you accept parts per hunk.
  • What is git rerere? It remembers how you resolved a conflict and reapplies it automatically next time.
  • Conflicts during rebase vs merge? Rebase may stop once per replayed commit; merge resolves everything once.
