What is training-serving skew, and how do you prevent it?

MLOps · concept · levels mid, senior, lead

In one line

Training-serving skew is a difference between the features a model was trained on and those it sees in production, caused by duplicate implementations, different data sources or timing; prevent it with shared transformation code or a feature store, and detect it by logging online features and monitoring distributions.

Detailed explanation

A model learns relationships between inputs and outcomes. If production inputs are computed differently, the model receives values it was never trained on and silently performs worse than offline evaluation suggested.

Common causes:

  • Two implementations of the same feature: Python or SQL in the training pipeline and Java or Go in the online service, differing in window boundaries (inclusive or exclusive), null handling, rounding, units, categorical encodings or time zones.
  • Different data sources: training reads a cleaned, deduplicated warehouse table, while serving reads raw events or a cache with different semantics.
  • Timing: training uses data that arrived late but was available by the time the table was built, while at prediction time it did not exist yet. This is closely related to leakage and is solved by point-in-time correct feature construction.

Prevention starts with design: use one implementation of each transformation for both paths, via shared libraries, a feature store that serves both offline and online, or by packaging preprocessing with the model (for example a scikit-learn Pipeline or transformations inside the model graph), so serving passes raw inputs and the artefact does the rest.

Verification makes skew measurable. Log the actual feature vectors used at inference with entity ID and timestamp, recompute the same features offline for the same entity and time, and compare them, reporting mismatch rates per feature. Also monitor production feature distributions against the training distribution with metrics such as PSI,.

How it works

  1. Identify where each feature is computed for training and serving.
  2. Consolidate into shared code, a feature store, or model-embedded preprocessing.
  3. Log online feature vectors with keys and timestamps.
  4. Recompute offline for the same keys and compare.
  5. Monitor distributions and alert on skew thresholds.

Example

# Preprocessing travels with the model, so serving cannot diverge
from sklearn.pipeline import Pipeline
from sklearn.compose import ColumnTransformer
from sklearn.preprocessing import OneHotEncoder, StandardScaler
from sklearn.linear_model import LogisticRegression

prep = ColumnTransformer([
    ("num", StandardScaler(), ["amount", "spend_30d"]),
    ("cat", OneHotEncoder(handle_unknown="ignore"), ["country", "channel"]),
])
model = Pipeline([("prep", prep), ("clf", LogisticRegression(max_iter=1000))]).fit(X_raw, y)
# serving: model.predict_proba(raw_request_df)

Common mistakes

  • Reimplementing features in the serving language by hand.
  • Trusting offline metrics without checking production inputs.
  • Confusing skew with drift and retraining when the bug is in serving code.
  • Not logging online features, so skew cannot be measured.

How to answer in the interview

"Training-serving skew means the features the model sees in production differ from those it was trained on, so it does worse than offline evaluation suggested. Common causes are features implemented twice, once in Python or SQL for training and again in another language for serving, with differences in windows, nulls or time zones; different data sources, like a cleaned warehouse table versus raw events; or timing, where late data was available in training but not at prediction time. I prevent it by sharing transformation code, a feature store or packaging preprocessing with the model, then verify by logging online features, comparing them with offline recomputation and monitoring distributions."

Likely follow-up questions

  • How would you measure skew rather than debug it by inspection? Join logged online features with offline recomputed ones by entity and timestamp and report per-feature mismatch rates.
  • How is skew different from drift? Skew is a pipeline difference; drift is the real world changing.
  • What is PSI? Population Stability Index, a measure of how much a distribution has shifted.
