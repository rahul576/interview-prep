What is the difference between system-assigned and user-assigned managed identities, and when do you use each?

Azure · concept · levels entry, mid, senior

In one line

A system-assigned managed identity is created and deleted with one resource; a user-assigned identity is a standalone resource you can pre-create, grant roles to, and attach to many resources, which also makes it the usual choice for workload identity federation (AKS, GitHub Actions); either way grant least privilege.

Detailed explanation

Managed identities are Entra ID service principals whose credentials Azure manages and rotates, so code obtains tokens from the local identity endpoint (via DefaultAzureCredential or ManagedIdentityCredential) without any secret.

System-assigned: enabled on a VM, App Service, Function App and so on. Its lifecycle is tied to that resource: deleting the resource deletes the identity, leaving its role assignments orphaned until cleaned up. It is ideal for a single resource with its own permissions, and cleanup is automatic.

User-assigned: an Microsoft.ManagedIdentity/userAssignedIdentities resource. It is useful when:

  • Several resources need identical access, such as VM scale set instances or multiple function apps processing the same queue.
  • You want to create the identity and its role assignments before the compute resource exists, avoiding RBAC propagation delays that cause first-start failures in deployments.
  • The identity must survive resource recreation (blue-green redeploys, immutable infrastructure), keeping access to Key Vault or SQL.
  • You need federated identity credentials: AKS workload identity maps a Kubernetes service account to a user-assigned identity, and GitHub Actions or Azure DevOps use OIDC federation, avoiding stored secrets. (App registrations can also hold federated credentials.)

Microsoft's guidance now favours user-assigned identities for most production scenarios because of these lifecycle and pre-provisioning benefits, but you must avoid sharing one identity across unrelated apps, which turns it into an over-privileged blast radius.

How it works

  1. Create the identity (system: toggle on resource; user: separate resource).
  2. Assign RBAC roles at the narrowest scope (a vault, a container).
  3. Attach a user-assigned identity to one or more resources.
  4. Code requests a token for a resource audience; Azure returns it.
  5. With federation, an external OIDC token is exchanged for an Entra token.

Example

az identity create -g rg-orders -n id-orders-api
az role assignment create --assignee <principalId> \
  --role "Key Vault Secrets User" --scope <vault-id>
az webapp identity assign -g rg-orders -n app-orders --identities <identity-id>
# Code: new SecretClient(uri, new DefaultAzureCredential(
#   new DefaultAzureCredentialOptions { ManagedIdentityClientId = "<client-id>" }));

Common mistakes

  • One user-assigned identity for many unrelated apps.
  • Granting Contributor at subscription scope "to make it work".
  • Not specifying the client ID when a resource has several identities.
  • Forgetting role propagation delay with system-assigned identities in pipelines.

How to answer in the interview

"A system-assigned identity lives and dies with one resource, which is simple and cleans up automatically. A user-assigned identity is its own resource, so I can create it and its role assignments before deploying, share it across scale set instances or a set of function apps doing the same job, and keep it when resources are recreated. It's also what I use for AKS workload identity and GitHub Actions OIDC federation. In both cases I grant least-privilege roles at the narrowest scope, and I never share one identity across unrelated workloads."

Likely follow-up questions

  • Risk of sharing one identity? Compromise of any app exposes all permissions; auditing is harder.
  • Can a resource have multiple identities? Yes, one system plus several user-assigned.
  • How does DefaultAzureCredential pick? It tries credentials in order; specify client ID for user-assigned.
