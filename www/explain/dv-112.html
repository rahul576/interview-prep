Which kubectl commands do you use most for daily work and debugging?

Kubernetes · concept · levels entry

In one line

Daily work revolves around kubectl get (with -n, -A, -o wide, -o yaml), describe for events, logs (-f, --previous), exec and port-forward for access, and apply -f, rollout status and rollout undo for changes.

Detailed explanation

Most debugging follows the same path: find the object, read its events, read its logs, then get inside if needed.

kubectl get lists resources. -n payments targets a namespace, -A shows all namespaces, -o wide adds node and pod IP, and -o yaml shows the full live object including status. -l app=orders filters by label and -w watches for changes. kubectl describe is the most useful first step for a broken pod: the Events at the bottom show scheduling failures, image pull errors, failed probes and OOM kills, which logs never show.

kubectl logs prints container output; -f follows, -c picks a container, --previous shows the last crashed instance (essential for CrashLoopBackOff), and deploy/orders picks a pod for you. kubectl exec -it pod -- sh opens a shell, and kubectl port-forward svc/orders 8080:80 tunnels a service to your laptop without exposing it. For minimal images without a shell, kubectl debug attaches an ephemeral container.

For changes, kubectl apply -f (or -k for Kustomize) applies manifests declaratively, kubectl diff previews them, kubectl rollout status waits for a Deployment to finish, and kubectl rollout undo returns to the previous revision. kubectl top shows CPU and memory when metrics-server is installed, and kubectl get events --sort-by=.lastTimestamp gives a namespace timeline.

How it works

  1. kubectl get pods -n shop -o wide – spot the failing pod and its node.
  2. kubectl describe pod <pod> – read events.
  3. kubectl logs <pod> --previous – see why it crashed.
  4. kubectl exec or kubectl debug – inspect from inside.
  5. Fix the manifest, kubectl diff, then kubectl apply.
  6. kubectl rollout status; if bad, kubectl rollout undo.

Example

kubectl get pods -n shop -l app=orders -o wide
kubectl describe pod orders-7d9f8-abcde -n shop | tail -20
kubectl logs deploy/orders -n shop -f --since=10m
kubectl logs orders-7d9f8-abcde -n shop --previous
kubectl exec -it orders-7d9f8-abcde -n shop -- sh
kubectl port-forward svc/orders 8080:80 -n shop
kubectl apply -k overlays/staging && kubectl rollout status deploy/orders -n shop
kubectl rollout undo deploy/orders -n shop

Common mistakes

  • Reading logs first and missing the events that explain a Pending pod.
  • Forgetting --previous, so you only see the fresh, healthy restart.
  • Editing live objects with kubectl edit in production instead of changing Git.
  • Running commands without checking the current context and namespace.

How to answer in the interview

"My daily set is kubectl get with -n, -A and -o wide or -o yaml to see resources; describe, mainly for the events at the bottom; logs with -f, and --previous for crash loops; exec and port-forward to get inside or reach a service locally, or kubectl debug when there's no shell. For changes I use apply with manifests or Kustomize, diff first, then rollout status to watch the deployment and rollout undo if something goes wrong. I always check the context before changing anything."

Likely follow-up questions

  • How do you switch clusters and namespaces safely? kubectx/kubens, a context-aware prompt, explicit --context in scripts.
  • How do you see all events in a namespace? kubectl get events --sort-by=.lastTimestamp.
  • What does kubectl explain do? Shows field documentation for any resource schema.
