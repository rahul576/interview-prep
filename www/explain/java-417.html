Kafka or RabbitMQ: when would you choose each?

Microservices · concept · levels mid, senior

In one line

Choose Kafka for event streaming: a retained, replayable, high-throughput distributed log with ordering per partition; choose RabbitMQ for task queues and flexible routing: a broker with exchanges, per-message acks, priorities and messages removed once consumed.

Detailed explanation

Kafka stores messages in partitioned, replicated, append-only logs and retains them for a configured time or size (or forever with compaction), regardless of whether they were consumed. Consumers pull and track their own offsets, so many independent consumer groups can read the same stream at their own pace, and any of them can replay history. It achieves very high throughput through sequential I/O and batching, and guarantees ordering per partition. Parallelism within a group is bounded by the partition count. This makes Kafka ideal for event-driven architectures, event sourcing projections, CDC pipelines, stream processing (Kafka Streams, Flink) and analytics ingestion. Kafka 4.0 also introduced share groups ("queues for Kafka", KIP-932) as an early-access feature for queue-like consumption with per-message acknowledgement, which is maturing in later releases.

RabbitMQ is a traditional message broker (AMQP 0-9-1, plus AMQP 1.0, MQTT and STOMP). Producers publish to exchanges (direct, topic, fanout, headers) that route messages into queues by binding rules. The broker pushes messages to consumers, which acknowledge each message; acked messages are deleted, and nacked ones can be requeued or dead-lettered. Features such as priorities, per-message TTL, dead-letter exchanges and request-reply suit work distribution, background jobs and command-style messaging. Quorum queues (Raft-replicated) are the recommended durable queue type, and RabbitMQ Streams add a Kafka-like replayable log. Ordering is per queue, but competing consumers and requeues can reorder.

Operations. Kafka clusters need capacity planning for partitions, storage and retention, though KRaft removed ZooKeeper. RabbitMQ is simpler for modest volumes. Managed services (Confluent Cloud, Amazon MSK, Azure Event Hubs with Kafka API; Amazon MQ, CloudAMQP) reduce the burden for both.

How it works

  1. Kafka: producer appends to a partition; consumers in each group read by offset; data stays until retention.
  2. RabbitMQ: producer publishes to an exchange; bindings route to queues; broker delivers to consumers; ack deletes.
  3. Kafka scaling: more partitions and consumers per group.
  4. RabbitMQ scaling: more competing consumers per queue, prefetch tuning.

Example

// Kafka: event stream consumed by several groups independently
kafkaTemplate.send("orders.events", order.getId(), new OrderPlaced(order.getId()));

// RabbitMQ: route a job to a work queue by routing key
rabbitTemplate.convertAndSend("jobs.exchange", "pdf.generate", new GeneratePdf(invoiceId));

@RabbitListener(queues = "pdf-jobs")
public void generate(GeneratePdf job) { pdfService.render(job.invoiceId()); }

Common mistakes

  • Using Kafka as a job queue with per-message priorities.
  • Using RabbitMQ when consumers need replay of history.
  • Too many Kafka partitions "just in case".
  • Classic mirrored queues instead of quorum queues for durability in RabbitMQ.

How to answer in the interview

"Kafka is a distributed append-only log: messages are retained, consumers track offsets, many consumer groups can read the same stream and replay it, and it handles very high throughput with ordering per partition. RabbitMQ is a classic broker: exchanges route messages to queues with flexible rules, consumers acknowledge each message and it is then removed, and it offers priorities, per-message TTL and dead-letter exchanges. I pick Kafka for event streaming, event-driven integration, CDC and analytics, and RabbitMQ for task queues, work distribution and request-reply. With managed offerings, operations are less of a deciding factor."

Likely follow-up questions

  • How do you implement delayed retries in each? Kafka: retry topics with delays; RabbitMQ: TTL plus dead-letter exchange, or the delayed-message plugin.
  • Can RabbitMQ replay messages? Not classic queues; RabbitMQ Streams can.
  • Does Kafka support queues now? Share groups (KIP-932) add queue semantics, introduced as early access in Kafka 4.0.
