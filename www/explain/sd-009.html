What is a CDN, and how does it improve a system?

SD Fundamentals · concept · levels entry, mid

In one line

A CDN caches content on edge servers near users, cutting latency and origin load; you control it with Cache-Control/TTLs, versioned file names and invalidation.

Detailed explanation

Light travels about 200 km per millisecond in fibre, so a user in Mumbai fetching from Virginia pays well over 100 ms per round trip before any server work. A CDN (Cloudflare, Akamai, CloudFront, Azure Front Door) has hundreds of points of presence. The first request at an edge goes to the origin (cache miss); later requests are served from the edge (cache hit).

Beyond static files, CDNs cache video segments, downloads and even API responses that are identical for many users. They also terminate TLS close to users, absorb DDoS attacks, and increasingly run code at the edge (redirects, auth checks, A/B routing).

How it works

  1. DNS for static.example.com points to the CDN.
  2. Edge checks its cache by URL (and any configured headers).
  3. Miss → fetch from origin (or a regional shield cache), store, return.
  4. Respect Cache-Control: public, max-age=31536000, immutable for hashed files.
  5. Purge/invalidate when content must change before TTL expiry.

Example

GET /assets/app.3f9a1c.js
Cache-Control: public, max-age=31536000, immutable

GET /index.html
Cache-Control: no-cache   (always revalidate, so new releases appear)

Hashed file names mean a new build gets new URLs, so you never need to invalidate old assets.

Common mistakes

  • Caching personalised responses publicly (leaking one user's data to another).
  • Long TTLs on non-versioned files, then users stuck on old JS.
  • Forgetting cache keys: varying on every cookie destroys the hit rate.
  • No origin shield, so a purge triggers a stampede on the origin.

How to answer in the interview

"Static assets, images and video segments go through a CDN with long TTLs and content-hashed file names, so releases never need invalidation. HTML is short-lived or revalidated. For APIs, only public, identical responses are cached at the edge; personalised data is fetched separately. The CDN also handles TLS and DDoS protection."

Likely follow-up questions

  • How do you serve personalised pages with a CDN? Cache the shell publicly; load user data via a separate API call, or use edge-side includes.
  • What is an origin shield? A mid-tier cache that collapses misses from many edges into one origin request.
  • How do you invalidate quickly? Purge APIs with surrogate keys/tags.
