What is the difference between MCP and the A2A protocol, and when would you use each?

MCP Servers · concept · levels mid, senior

In one line

MCP connects an agent to tools and data that it controls; A2A (Agent2Agent) connects agents to other autonomous agents, discovered via agent cards and delegated tasks with a lifecycle; use MCP for a capability, A2A to hand off a goal, and often both together.

Detailed explanation

The two protocols answer different questions. MCP answers "how does my agent use this system?" A server exposes well-defined tools, resources and prompts. The calling agent decides which tool to call with which arguments, gets a result back and stays fully in control of the reasoning. A tool is, in principle, predictable: same input, same kind of output.

A2A, originally introduced by Google and now an open project under the Linux Foundation, answers "how does my agent work with another agent?" A remote agent publishes an agent card, a JSON document describing its name, skills, endpoint and authentication requirements. A client agent discovers it and sends a task: a goal in natural language plus data. The remote agent is opaque and autonomous: it may reason, call its own tools, ask clarifying questions (the task enters an "input required" state), stream progress, and finally return artifacts such as a report or confirmation. The task has a lifecycle: submitted, working, input-required, completed, failed or cancelled.

Rule of thumb: use MCP when you want a capability, such as querying a database, creating a ticket or reading a file. Use A2A when you want to delegate a goal to an agent owned by another team or vendor, such as a supplier's procurement agent or a partner's travel booking agent, without knowing or controlling how it works.

They combine naturally. An orchestrator agent uses MCP servers for its own tools and A2A to delegate to specialist agents, which in turn use their own MCP servers internally. Remote agents are harder to secure and test because their behaviour is non-deterministic and hidden.

How it works

  1. MCP: host lists tools, model chooses one, host calls it, result returns.
  2. A2A: client fetches the agent card (often at /.well-known/agent-card.json).
  3. Client sends a task message; remote agent starts working.
  4. Remote agent streams updates, may request input, and returns artifacts.
  5. Client tracks task state and uses the artifacts.

Example

{
  "name": "Supplier Procurement Agent",
  "description": "Quotes and places purchase orders for industrial parts.",
  "url": "https://agents.supplier.example/a2a",
  "capabilities": { "streaming": true },
  "skills": [
    { "id": "quote", "name": "Get quote", "description": "Price and lead time for SKUs" },
    { "id": "order", "name": "Place order", "description": "Create a purchase order" }
  ],
  "securitySchemes": { "oauth": { "type": "oauth2" } }
}

Common mistakes

  • Wrapping a complex autonomous agent as a single MCP tool and expecting tool-like reliability.
  • Using A2A for simple deterministic lookups.
  • Treating the protocols as rivals.
  • Forgetting that a remote agent's output is untrusted content.

How to answer in the interview

"MCP connects an agent or AI app to tools and data: the server exposes well-defined capabilities and the calling agent decides what to do and keeps control. A2A, the Agent2Agent protocol from Google, now under the Linux Foundation, connects agents to other agents: a client discovers a remote agent through its agent card and delegates a task. The remote agent is opaque and autonomous; it may reason, call its own tools and ask follow-up questions, and the task has a lifecycle with streaming updates and artifacts. I use MCP when I want a capability like querying a database, and A2A when I want to hand a goal to another team's or vendor's agent. They're complementary and often used together."

Likely follow-up questions

  • Why are remote agents harder to secure? Non-deterministic, hidden behaviour, and their outputs can carry injection.
  • Can an A2A agent use MCP internally? Yes, that is the common pattern.
  • How handle clarifying questions? Answer from context or route to a human when the task needs input.
