How do you secure agents that can take real actions?

AI Agents & AIOps · concept · levels senior, lead

In one line

Secure acting agents with least-privilege tools, distinct agent identities with scoped, short-lived credentials, delegated user permissions where acting for someone, sandboxed execution with restricted egress, treating all external content as untrusted (prompt injection), and policy checks, approvals and audit logs enforced in code.

Detailed explanation

Think of an agent as a new kind of employee or service: very fast, tireless, and with imperfect judgment that can be manipulated. Security must therefore not depend on the model behaving well.

Least privilege comes first. Each agent gets only the tools its job requires, and those tools are narrow: restart_deployment(namespace, name) in staging, not "run any shell command in production". OWASP's Top 10 for LLM applications calls the opposite excessive agency.

Identity: each agent has its own identity, such as a workload identity or managed identity, or the emerging agent-identity features in identity providers like Microsoft Entra Agent ID, with scoped, short-lived credentials issued per run rather than long-lived API keys. That makes actions attributable and revocable. When acting for a user, the agent uses delegated permissions (OAuth on-behalf-of or token exchange) so it can never exceed what that user may do.

Sandboxing: code execution and browsing run in containers or micro-VMs with a restricted filesystem, no host credentials and egress allowlists, which limits both damage and data exfiltration.

Untrusted content: web pages, emails, documents, tickets and even tool results may contain prompt injection. Treat them as data, separate them from instructions, and avoid combining access to private data, untrusted content and outbound channels in one agent without controls, the so-called "lethal trifecta".

Policy and oversight: sensitive actions pass through policy checks in code (allowed environments, spending limits, tagging rules), human approval for high-risk operations, and everything is recorded in audit logs. Kill switches allow revoking an agent's credentials immediately.

How it works

  1. Define the agent's job; derive the minimal tool and permission set.
  2. Assign a dedicated identity; issue short-lived, scoped tokens per run.
  3. Use delegated user tokens for user-facing actions.
  4. Run code and browsing in sandboxes with egress allowlists.
  5. Mark external content as untrusted; add injection detection layers.
  6. Enforce policies and approvals in the tool layer; log everything; keep a kill switch.

Example

agent: k8s-remediation-agent
identity: workload-identity/k8s-remediator   # no static keys
token_ttl: 15m
tools:
  - name: restart_deployment
    allowed_namespaces: [staging, preprod]
  - name: scale_deployment
    allowed_namespaces: [staging, preprod, prod]
    max_replicas: 20
    approval_required_in: [prod]
  - name: get_logs                           # read-only
network_egress_allowlist: [kubernetes.default.svc, logs.internal.example.com]
audit_log: siem://agent-actions
kill_switch: revoke identity + disable agent flag

Common mistakes

  • Sharing a human admin's credentials with an agent.
  • Generic shell or SQL tools with broad permissions.
  • Relying on system prompts as the security boundary.
  • Unrestricted internet egress from execution sandboxes.
  • No way to quickly revoke an agent's access.

How to answer in the interview

"I treat an agent like a new kind of employee with very fast hands and imperfect judgment. It gets only the tools and permissions its job needs, nothing like 'run any command in production'. It has its own identity with scoped, short-lived credentials, so its actions are attributable and revocable, and when acting for a user it uses delegated permissions so it can't exceed what the user may do. Code runs in sandboxes with restricted filesystem and network egress. All external content is untrusted because of prompt injection. Sensitive actions go through policy checks in code and human approval, and everything is audited, with a kill switch."

Likely follow-up questions

  • Revoke access quickly? Disable the agent identity or revoke its tokens centrally, plus a feature flag that stops runs.
  • Why are short-lived credentials important? Leaked or misused tokens expire quickly and each run is scoped.
  • Is a guardrail model enough? No, it is an extra layer; permissions and policies in code are the real boundary.
