How does Java code get compiled and executed? Explain the complete lifecycle.

JVM & Performance · concept · levels entry, mid

In one line

javac compiles .java source into platform-neutral bytecode in .class files; at runtime the class loader loads, links (verifies, prepares, resolves) and initialises classes on demand, the execution engine first interprets bytecode and then JIT-compiles hot code to native code, while objects live on the heap and the GC reclaims them.

Detailed explanation

Compile time. javac parses source, checks types, resolves symbols against the classpath or module path, applies desugaring (generics are erased, lambdas become invokedynamic call sites, string concatenation uses invokedynamic since Java 9), and writes bytecode to .class files, one per class, including nested ones. Bytecode is a stack-based instruction set, the same on every platform: "write once, run anywhere". Build tools package classes into jars. Since Java 11 you can also run a single source file directly with java Main.java, which compiles in memory.

JVM startup. java -jar app.jar starts the JVM, which creates its runtime data areas (heap, Metaspace, code cache), starts system threads (GC, JIT compiler, signal handling) and loads the main class.

Class loading. Classes are loaded lazily, when first referenced, through the bootstrap, platform and application class loaders using parent delegation. Linking follows: the bytecode verifier checks the code is well-formed and type-safe (no stack overflows of the operand stack, no illegal casts or jumps), preparation allocates static fields with default values, and resolution links symbolic references. Initialisation runs static initialisers on first active use.

Execution. The interpreter executes bytecode instruction by instruction, starting immediately. The JVM profiles methods; warm ones are compiled by C1, hot ones recompiled by C2 with aggressive optimisations like inlining and escape analysis. Compiled code is stored in the code cache and used for subsequent calls; if speculative assumptions break, the code is deoptimised.

Memory and GC. Each thread has a stack of frames; objects are allocated on the heap; the garbage collector reclaims unreachable objects. The program ends when main and all non-daemon threads finish or System.exit is called, which runs shutdown hooks.

How it works

  1. javac compiles Main.java into Main.class (bytecode).
  2. java Main starts the JVM and creates memory areas.
  3. Class loaders load Main and dependencies on demand.
  4. Verifier checks bytecode; statics are prepared and initialised.
  5. Interpreter runs main; JIT compiles hot methods to native code.
  6. GC reclaims garbage; JVM exits when non-daemon threads finish.

Example

javac -d out src/com/acme/Main.java      # source -> bytecode
javap -c -p out/com/acme/Main.class      # inspect bytecode
java -cp out com.acme.Main               # run on any OS with a JVM

java -Xlog:class+load:file=classes.log -cp out com.acme.Main   # see class loading
java -XX:+PrintCompilation -cp out com.acme.Main               # see JIT compiling
// javap output excerpt

Common mistakes

  • Saying Java is "purely interpreted" or "compiled to machine code by javac".
  • Thinking all classes are loaded at startup.
  • Forgetting the verification step and why it matters for security.
  • Mixing up JDK (tools including javac) and JRE/JVM (runtime).

How to answer in the interview

"First javac compiles the .java source into platform-neutral bytecode in .class files, usually packaged into a jar. When I run the program, the JVM starts and the class loader subsystem loads classes on demand with parent delegation, then links them: the verifier checks the bytecode is safe, static fields are prepared and symbolic references resolved, and static initialisers run on first use. The execution engine starts by interpreting bytecode, profiles which methods are hot, and the JIT compilers, C1 and then C2, turn those into optimised native code. Objects live on the heap, each thread has its own stack, and the garbage collector reclaims unreachable objects until the JVM exits."

Likely follow-up questions

  • What is the difference between the C1 and C2 JIT compilers? C1 compiles fast with basic optimisations; C2 compiles slower but produces highly optimised code using profiles.
  • Why verify bytecode? Class files may come from untrusted or buggy compilers; verification guarantees type and memory safety.
  • What is invokedynamic? A bytecode instruction that links call sites at runtime, used for lambdas and string concatenation.
