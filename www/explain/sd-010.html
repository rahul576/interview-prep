How do you choose between synchronous and asynchronous communication between components?

SD Fundamentals · concept · levels entry, mid, senior

In one line

Use synchronous calls when the caller needs the result now; use asynchronous messaging for work that can happen later, to decouple services, absorb spikes and survive failures.

Detailed explanation

Synchronous REST or gRPC is simple: request in, response out, easy to debug. But it couples services in time. If service A calls B calls C, A's latency is the sum and A's availability is roughly the product: three services at 99.9% each give about 99.7%. A slow C can exhaust A's threads.

Asynchronous communication through a queue or event stream lets the producer continue immediately. The broker buffers work, so spikes don't overload consumers, and consumers can be down briefly without losing messages. New consumers can subscribe to events without changing the producer. The price: eventual consistency, retries and dead-letter queues, idempotent consumers, and harder end-to-end tracing.

How it works

  1. Identify what the user is waiting for (sync) versus side effects (async).
  2. Sync path: timeouts, retries with backoff, circuit breakers.
  3. Async path: publish an event (ideally via the transactional outbox), consumers process at their pace.
  4. Return results of async work via polling, WebSockets, push or webhooks.

Example

Checkout: validate cart, reserve stock and authorise payment synchronously, then return "order placed". Publish OrderPlaced; email, invoice, analytics, loyalty points and warehouse picking consume it asynchronously.

Common mistakes

  • Long synchronous chains across many services.
  • Using async for something the user needs immediately, then polling awkwardly.
  • No idempotency, so redelivered messages cause duplicates.
  • No dead-letter queue, so one poison message blocks processing.

How to answer in the interview

"My rule is: synchronous for whatever the user is waiting on, asynchronous for everything else. In checkout, payment authorisation is synchronous, but emails, invoicing and analytics react to an OrderPlaced event. That keeps the critical path short, absorbs spikes and lets those consumers fail without affecting orders. I'd make consumers idempotent and add tracing with correlation IDs."

Likely follow-up questions

  • How does the user get an async result? Poll a status endpoint, WebSocket/SSE, or push notification.
  • How do you guarantee the event is published? Transactional outbox.
  • What about ordering? Partition by entity key so events for one order stay ordered.
