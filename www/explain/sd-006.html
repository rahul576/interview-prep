What consistency models exist, from strong to eventual consistency?

SD Fundamentals · concept · levels entry, mid, senior

In one line

Consistency models range from linearizable (looks like one copy) through causal and session guarantees to eventual (replicas converge eventually); stronger models cost latency and availability.

Detailed explanation

When data is replicated, the question is what a reader may observe after a write. Linearizability gives the simplest mental model but requires coordination, often a leader or consensus. Sequential consistency keeps one global order but not real-time order. Causal consistency only orders operations that are causally related (a reply always appears after its post) and allows unrelated operations in any order, which allows more concurrency.

Session guarantees are what users actually notice: read-your-writes (I see my own update), monotonic reads (I never see older data after newer), monotonic writes and writes-follow-reads. Eventual consistency promises only convergence if writes stop.

How it works

  1. Strong: route reads to the leader or use quorum reads where R + W > N.
  2. Read-your-writes: route a user's reads to the leader for a short time after they write, or track a write timestamp and only read replicas that have caught up.
  3. Monotonic reads: pin a user's session to one replica.
  4. Eventual: read any replica; conflicts resolved later.

Example

A user edits their profile name and refreshes. With async replicas and random reads, they might see the old name: a read-your-writes violation. Fix: after a write, set a cookie with the write's log position (LSN) and serve that user's reads only from replicas at or beyond it, or from the primary for 5 seconds.

Common mistakes

  • Assuming replicas are always up to date.
  • Using strong consistency everywhere and paying the latency everywhere.
  • Ignoring session guarantees, which cause the most visible user bugs.

How to answer in the interview

"I'd pick the weakest model that still gives correct behaviour. Balances and inventory need linearizable operations. For user profiles, eventual consistency is fine as long as each user gets read-your-writes, which I'd implement by reading from the primary briefly after a write or tracking replication position. Feeds and counters can be eventually consistent."

Likely follow-up questions

  • What is a quorum? Overlapping read and write sets (R + W > N) so reads see the latest write.
  • How does Cassandra offer tunable consistency? Per-query levels like ONE, QUORUM, LOCAL_QUORUM.
  • What anomaly does causal consistency prevent? Seeing a reply before the message it answers.
