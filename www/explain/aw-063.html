What is AWS X-Ray, and how does it relate to OpenTelemetry?

Cloud (AWS) · concept · levels mid

In one line

AWS X-Ray is a distributed tracing service that records traces, segments and subsegments, builds a service map, integrates with Lambda, API Gateway, ECS and EKS, uses sampling rules to control cost, and today is best fed through OpenTelemetry (the AWS Distro for OpenTelemetry or CloudWatch Application Signals).

Detailed explanation

In a microservice system, one user request crosses many services. X-Ray assigns a trace ID, propagated in the X-Amzn-Trace-Id header (or W3C trace context with OpenTelemetry). Each service records a segment with start and end time, status, HTTP details and annotations; calls inside it, such as an SQL query, a DynamoDB call or an HTTP request, become subsegments. Annotations are indexed key-value pairs for filtering traces (customer tier, order ID); metadata is unindexed detail.

X-Ray assembles segments into traces and a service map (now the CloudWatch trace map) showing nodes, latency distributions and error or fault rates, so you can see which dependency causes slowness. Trace analytics and Transaction Search help query spans at scale.

Integrations are built in: Lambda active tracing, API Gateway stage tracing, Step Functions, App Runner, Elastic Beanstalk, and for ECS or EKS a collector sidecar or daemonset. Sampling rules decide what gets traced, the default being the first request each second plus 5 percent of additional requests, configurable per service, path or method, which keeps cost and overhead down.

AWS now recommends OpenTelemetry for instrumentation. The legacy X-Ray SDKs and daemon are in maintenance mode and moving towards end of support. The AWS Distro for OpenTelemetry (ADOT) and the CloudWatch agent collect OTel traces and send them to X-Ray, and can export to other backends too, avoiding vendor lock-in. CloudWatch Application Signals builds on this for service-level dashboards and SLOs.

How it works

  1. A request enters API Gateway, which starts a trace.
  2. Trace context propagates via headers to downstream services.
  3. Each service emits spans (segments) to a collector or the X-Ray API.
  4. X-Ray assembles spans by trace ID and applies sampling.
  5. The trace map and traces reveal latency and errors per hop.

Example

# ADOT / OTel collector config for ECS sidecar
receivers:
  otlp:
    protocols: {grpc: {endpoint: 0.0.0.0:4317}}
processors:
  batch: {}
exporters:
  awsxray: {region: eu-west-1}
service:
  pipelines:
    traces: {receivers: [otlp], processors: [batch], exporters: [awsxray]}
OTEL_SERVICE_NAME=orders-api \
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317 \
OTEL_PROPAGATORS=xray,tracecontext \
java -javaagent:aws-opentelemetry-agent.jar -jar app.jar

Common mistakes

  • Tracing 100 percent of traffic in production and paying for it.
  • Broken propagation through queues or async calls, giving fragmented traces.
  • Starting new projects on the legacy X-Ray SDK instead of OpenTelemetry.
  • Not logging trace IDs, so logs and traces cannot be correlated.

How to answer in the interview

"X-Ray is AWS's distributed tracing service. Each request gets a trace ID, services record segments with subsegments for database, SDK and HTTP calls, and X-Ray builds traces and a service map showing where latency and errors come from. It integrates directly with Lambda, API Gateway, Step Functions, ECS and EKS, and sampling rules limit cost. Today I instrument with OpenTelemetry: the AWS Distro for OpenTelemetry or CloudWatch agent sends traces to X-Ray and can send them elsewhere too, so I am not locked into the X-Ray SDK."

Likely follow-up questions

  • How correlate traces with logs? Log the trace ID in every structured log line and search by it in Logs Insights.
  • How trace through SQS? Propagate context in message attributes; Lambda with SQS links the traces.
  • What do annotations give you? Indexed fields to filter traces, such as all slow traces for one tenant.
