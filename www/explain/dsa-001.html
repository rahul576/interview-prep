How would you solve Two Sum: find two numbers in an array that add up to a target? What is the complexity?

DSA: Arrays & Strings · concept · levels entry, mid

In one line

Use a hash map from value to index. For each element, check whether its complement (target - x) has already been seen. That is a single pass, O(n) time and O(n) space, versus the O(n²) brute force. If the array is sorted, two pointers give O(n) time with O(1) space.

Detailed explanation

Two Sum asks for indices i != j such that nums[i] + nums[j] == target. The brute force checks every pair with two nested loops, which is n(n-1)/2 comparisons, or O(n²). That is fine for 100 elements and far too slow for a million.

The key insight is that for each number x, we know exactly which partner we need: target - x. Instead of searching for it with a loop, we look it up in a hash map in expected O(1). By inserting each number after checking for its complement, we never pair an element with itself, and we handle duplicates correctly. For [3, 3] with target 6, the second 3 finds the first.

Complexity is O(n) time (each element is processed once, with expected O(1) map operations) and O(n) extra space for the map. Hash map operations can degrade with poor hashing, but Java's HashMap turns long buckets into trees, so the worst case per operation is O(log n).

If the input is sorted, or you are allowed to sort and only need values, not original indices, use two pointers: left at the start and right at the end. If the sum is too small, move left right. If it is too big, move right left. That is O(n) time and O(1) space, plus O(n log n) if you have to sort first. Sorting destroys original indices unless you sort index pairs.

How it works

  1. Create an empty map seen (value to index).
  2. For each index i with value x, compute need = target - x.
  3. If need is in seen, return [seen.get(need), i].
  4. Otherwise store seen.put(x, i).
  5. If the loop ends, no pair exists. Say how you would signal that (empty array or exception).

Example

public int[] twoSum(int[] nums, int target) {
    Map<Integer, Integer> seen = new HashMap<>();
    for (int i = 0; i < nums.length; i++) {
        int need = target - nums[i];
        Integer j = seen.get(need);
        if (j != null) return new int[] { j, i };
        seen.put(nums[i], i);
    }
    return new int[0];
}
// nums = [2, 7, 11, 15], target = 9 -> i=1: need 2 found at 0 -> [0, 1]

Common mistakes

  • Inserting before checking, which pairs an element with itself ([3], target 6).
  • Sorting and then returning indices of the sorted array.
  • Not clarifying whether there is exactly one answer, or what to return when there is none.
  • Ignoring integer overflow when values are near the int limits (use long if needed).

How to answer in the interview

"The brute force checks every pair, which is O(n squared). Better, I scan once and keep a hash map from value to index. For each element I compute the complement, target minus the value, and if it's already in the map I return both indices. Otherwise I store the current value. Checking before inserting avoids using the same element twice. That's O(n) time and O(n) space. If the array were already sorted, I'd use two pointers from both ends for O(n) time and constant space."

Likely follow-up questions

  • All unique pairs? Sort, then use two pointers, skipping duplicate values after each match. Or use a set of seen values plus a set of pairs.
  • Three Sum? Sort, fix one element, run two pointers on the rest. O(n²).
  • Data too big for memory? Partition by hash of value and complement, or use sorted external files with two pointers.
