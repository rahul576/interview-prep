What is the difference between a public and a private subnet in a VPC?

Cloud (AWS) · concept · levels entry

In one line

A subnet is public if its route table sends 0.0.0.0/0 to an internet gateway, so resources with a public or Elastic IP are reachable; a private subnet has no such route, so its resources reach the internet only outbound through a NAT gateway and cannot be reached directly from outside.

Detailed explanation

A VPC is your isolated network in a region, divided into subnets, each in one Availability Zone. "Public" and "private" are not checkboxes; they result from routing.

In a public subnet, the route table has 0.0.0.0/0 -> igw-... to the internet gateway. An instance also needs a public IPv4 or Elastic IP; the internet gateway maps it one-to-one to the private IP. Security groups and NACLs still filter traffic.

In a private subnet, the route table has only the local VPC route and perhaps routes to a NAT gateway, VPC endpoints, a Transit Gateway or a VPN. Nothing on the internet can initiate a connection to its instances, even if a security group is misconfigured. For outbound access, for patches or third-party APIs, traffic goes to a NAT gateway in a public subnet. For AWS services, VPC endpoints avoid the internet entirely. For IPv6, an egress-only internet gateway provides outbound-only access.

The standard design spreads subnets across at least two or three AZs: public subnets hold only internet-facing components such as Application Load Balancers and NAT gateways; private subnets hold application servers, containers and EKS nodes; isolated or database subnets with no internet route at all hold RDS and caches. This reduces the attack surface dramatically.

How it works

  1. Create a VPC with a CIDR such as 10.0.0.0/16.
  2. Create public and private subnets in each AZ.
  3. Attach an internet gateway to the VPC.
  4. Public route table: 0.0.0.0/0 -> IGW.
  5. Private route table: 0.0.0.0/0 -> NAT gateway in the same AZ.
  6. Place the ALB in public subnets, apps and databases in private ones.

Example

resource "aws_route_table" "public" {
  vpc_id = aws_vpc.main.id
  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.igw.id
  }
}

resource "aws_route_table" "private_a" {
  vpc_id = aws_vpc.main.id
  route {
    cidr_block     = "0.0.0.0/0"
    nat_gateway_id = aws_nat_gateway.a.id
  }
}

Traffic flow: user -> ALB (public subnet) -> app on ECS (private subnet) -> RDS (database subnet); the app calls a payment API outbound via the NAT gateway.

Common mistakes

  • Thinking a subnet is private because instances lack public IPs, while the route to the IGW remains.
  • Putting databases in public subnets "for easy access".
  • One NAT gateway for all AZs, creating a single point of failure.
  • Using SSH from the internet instead of Session Manager.

How to answer in the interview

"What makes a subnet public is its route table: a public subnet has a 0.0.0.0/0 route to an internet gateway, so instances with a public or Elastic IP can reach and be reached from the internet. A private subnet has no route to the internet gateway, so nothing outside can connect in. If private instances need outbound access, they go through a NAT gateway in a public subnet, and for AWS services I'd use VPC endpoints. My usual layout is load balancers and NAT in public subnets, apps and containers in private subnets, and databases in isolated subnets, across at least two AZs."

Likely follow-up questions

  • How do you SSH into a private instance? Use SSM Session Manager, or a bastion or EC2 Instance Connect Endpoint.
  • Can a public subnet instance be unreachable? Yes, without a public IP or with restrictive security groups.
  • What is an isolated subnet? A subnet with no route to the internet at all, not even via NAT.
