What is Ansible Vault, and how do you use it?

Configuration Management · concept · levels entry

In one line

Ansible Vault encrypts secrets (whole files or single strings) with AES-256 so they can live in Git; manage them with ansible-vault create/edit/encrypt/encrypt_string/rekey, supply the password via prompt, protected file or script, use vault IDs per environment, and prefer external secret managers at scale.

Detailed explanation

Playbooks often need passwords, API tokens or private keys. Storing them in plain YAML in Git is unacceptable, but keeping them outside the repository makes runs hard to reproduce. Vault encrypts the data so the encrypted form can be committed next to the code.

Main commands:

  • ansible-vault create file.yml / edit file.yml: open an encrypted file in your editor.
  • ansible-vault encrypt / decrypt / view: act on existing files, such as group_vars/prod/vault.yml.
  • ansible-vault encrypt_string: encrypt one value to paste inline in an otherwise readable YAML file.
  • ansible-vault rekey: change the password of encrypted files.

At runtime Ansible decrypts transparently in memory when given the password: --ask-vault-pass, --vault-password-file pointing to a file kept outside the repo with tight permissions, or an executable script that fetches the password from a password manager or CI secret. Vault IDs (--vault-id prod@prompt, --vault-id dev@~/.vault_dev) let different environments use different passwords, so dev users cannot decrypt production secrets.

A widely used convention is to keep a readable vars.yml that references vault_-prefixed variables defined in an encrypted vault.yml, so you can grep for variable names without decrypting. Mark tasks that handle secrets with no_log: true so values do not appear in output.

For larger organisations, sharing vault passwords becomes the weak point. Fetching secrets at runtime from HashiCorp Vault, AWS Secrets Manager, Azure Key Vault or similar through lookup plugins (for example community.hashi_vault.hashi_vault) gives central rotation, auditing and per-identity access.

How it works

  1. Encrypt files or strings with ansible-vault.
  2. Commit the encrypted content.
  3. Run playbooks providing the vault password or vault ID.
  4. Ansible decrypts in memory during the run.
  5. Rotate with rekey and update the password source.

Example

ansible-vault create --vault-id prod@prompt group_vars/prod/vault.yml
ansible-vault encrypt_string --vault-id prod@prompt 'S3cr3t!' --name 'vault_db_password'
ansible-playbook site.yml -i inventory/prod --vault-id prod@~/.vault_pass_prod
ansible-vault rekey --vault-id prod@old_pass --new-vault-id prod@new_pass group_vars/prod/vault.yml
# group_vars/prod/vars.yml (readable)
db_password: "{{ vault_db_password }}"

Common mistakes

  • Committing the vault password file next to the encrypted data.
  • One shared vault password for all environments.
  • Printing decrypted secrets in task output without no_log.
  • Encrypting whole variable files so nobody can see which variables exist.

How to answer in the interview

"Ansible Vault encrypts sensitive data, passwords, keys, certificates, so it can be stored in Git with the playbooks. I use ansible-vault create or edit for encrypted files like group_vars/prod/vault.yml, and encrypt_string for single values inline. At runtime I pass the password with --ask-vault-pass, a protected password file outside the repo, or a script that reads it from a secret store, and vault IDs give each environment its own password. For larger setups I'd rather fetch secrets at runtime from HashiCorp Vault or a cloud secret manager through lookup plugins, which avoids sharing vault passwords at all."

Likely follow-up questions

  • How would you rotate the vault password used for production? ansible-vault rekey on all prod files, update the password source in CI, and rotate the underlying secrets if the old password may have leaked.
  • Why use no_log? To keep decrypted values out of logs and callbacks.
  • Is Vault data protected on the target host? No, once deployed it's plain on the host; protect files with permissions.
