How does CompletableFuture handle return values, exceptions, and chained tasks?

Concurrency · concept · levels mid

In one line

Each stage receives the previous result (thenApply, thenCompose, thenCombine, thenAccept); an exception completes the future exceptionally and skips dependent stages until exceptionally, handle or whenComplete deals with it; join() throws CompletionException, get() throws ExecutionException.

Detailed explanation

Return values. A chain is a series of futures, each depending on the one before. thenApply(fn) takes the value and returns a transformed one, synchronously. thenCompose(fn) is for functions that themselves return a CompletableFuture; it flattens the result so you get CompletableFuture<T> instead of a nested future. thenCombine(other, bifn) waits for two independent futures and merges their values. thenAccept consumes the value and returns CompletableFuture<Void>, and thenRun ignores it.

Exceptions. If the supplier or any stage throws, that stage completes exceptionally. Every dependent normal stage (thenApply, thenAccept...) is skipped and also completes exceptionally, typically with the cause wrapped in a CompletionException. The failure flows down until a handler:

  • exceptionally(ex -> fallback) runs only on failure and returns a replacement value, so the chain continues normally.
  • handle((value, ex) -> ...) always runs and can map either outcome to a new value.
  • whenComplete((value, ex) -> ...) always runs but does not change the result: use it for logging or metrics; the original value or exception passes through.
  • Java 12 added exceptionallyCompose for async recovery.

Inside handlers the exception is often a CompletionException; unwrap getCause() before checking its type.

Getting the final value. join() throws an unchecked CompletionException wrapping the cause; get() throws the checked ExecutionException. A timeout from orTimeout appears as a TimeoutException cause.

Placement matters: a handler only covers stages before it. Put exceptionally right after a step to give a step-specific fallback, or at the end to handle any failure in the chain.

How it works

  1. supplyAsync produces a value or exception.
  2. Each then... stage runs only if its source completed normally.
  3. On exception, normal stages are bypassed and the exception propagates.
  4. exceptionally/handle convert the failure into a value; later stages run normally again.
  5. whenComplete observes without changing the outcome; join/get deliver the final result or wrapped exception.

Example

CompletableFuture<String> result = CompletableFuture
        .supplyAsync(() -> orderRepo.find(orderId), pool)          // may throw
        .thenApply(Order::customerId)                              // skipped on failure
        .thenCompose(cid -> customerClient.findAsync(cid))         // async step, flattened
        .thenApply(Customer::email)
        .exceptionally(ex -> {
            Throwable cause = ex instanceof CompletionException ? ex.getCause() : ex;
            log.warn("Lookup failed: {}", cause.toString());
            return "support@example.com";                          // fallback value
        })
        .whenComplete((email, ex) -> metrics.increment("email.lookup"));

String email = result.join();     // never throws here: failure was recovered

CompletableFuture<Integer> h = CompletableFuture.supplyAsync(() -> 10 / divisor)
        .handle((v, ex) -> ex == null ? v : -1);                    // maps both outcomes

Common mistakes

  • Using thenApply with an async function and getting nested futures.
  • Checking ex instanceof MyException without unwrapping CompletionException.
  • Expecting whenComplete to recover from an error.
  • Putting exceptionally too early and then letting later stages fail unhandled.

How to answer in the interview

"Each stage receives the previous stage's result: thenApply transforms it, thenCompose flattens a function returning another CompletableFuture, thenCombine merges two results and thenAccept consumes it. If any stage throws, the future completes exceptionally and the dependent stages are skipped, so the exception propagates down the chain. I recover with exceptionally, which runs only on failure, or handle, which always runs and can map either outcome; whenComplete lets me observe, for logging, without changing the result. join throws an unchecked CompletionException wrapping the cause, while get throws a checked ExecutionException."

Likely follow-up questions

  • Where should exceptionally be placed in a long chain? After the stages it should cover: right after a step for a step-specific fallback, or at the end as a catch-all.
  • Why unwrap CompletionException? Exceptions from earlier stages are wrapped, so the real cause is in getCause().
  • What does exceptionallyCompose do? Recovers with another CompletableFuture, for example calling a fallback service asynchronously.
