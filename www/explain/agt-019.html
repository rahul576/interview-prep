How do long-running agents manage their context window over many steps?

AI Agents & AIOps · concept · levels senior, lead

In one line

Long-running agents manage context with compaction (summarising older history), clearing or truncating old tool outputs, external notes or memory files for progress, sub-agents with fresh contexts, and just-in-time retrieval instead of loading everything upfront.

Detailed explanation

Each agent step adds to the context: tool results, file contents, reasoning and messages. Eventually the context window fills and the run fails, but quality drops well before that. Models attend less precisely to information buried in very long contexts, sometimes called context rot, and stale or irrelevant material distracts them. Cost and latency also grow, because every step resends the whole context. Context engineering, curating what the model sees at each step, is therefore central to long-running agents.

Compaction summarises older history when the context approaches a threshold: decisions made, current state, open problems, files touched, next steps. The agent continues with the summary plus recent turns. Claude Code and several SDKs and APIs provide automatic compaction; the quality of the summary prompt matters.

Tool result clearing removes or truncates old, bulky outputs, like a 2,000-line log from 30 steps ago, keeping only a short note of what was learned. Tools themselves should return concise results with pagination.

External memory: the agent writes structured notes outside the context, such as a PROGRESS.md, a to-do list, test status or a JSON state file, and re-reads them when needed. This lets work continue across compactions, context resets and even separate sessions, and it is how agents sustain multi-hour tasks.

Sub-agents handle exploratory subtasks, such as searching a large codebase, in their own fresh contexts and return only a condensed answer, so the main context stays clean.

Just-in-time retrieval: keep lightweight references (file paths, IDs, URLs) and load content only when needed via tools like grep, read file or search, rather than dumping everything into the prompt upfront.

How it works

  1. Monitor token usage per step against a threshold.
  2. Trim or clear stale tool outputs first.
  3. When near the threshold, compact history into a structured summary.
  4. Persist plan and progress to an external notes file.
  5. Delegate exploration to sub-agents returning summaries.
  6. Retrieve details on demand by reference.

Example

<!-- PROGRESS.md maintained by the agent -->
## Goal
Migrate payment-service from Spring Boot 2.7 to 3.3

## Done
- javax.* -> jakarta.* imports (all modules), commit a1b2c3
- Spring Security config migrated to SecurityFilterChain

## Current
- 4 failing tests in RefundControllerTest (Jackson date format)

## Decisions
- Keep Hibernate 6 default naming; added explicit @Table names

## Next
1. Fix date serialisation  2. Update Dockerfile base image  3. Run full test suite

Common mistakes

  • Letting the context grow until it overflows.
  • Compaction summaries that drop key decisions or constraints.
  • Tools that return huge outputs by default.
  • Loading whole repositories or documents upfront.
  • Sub-agents returning full transcripts instead of summaries.

How to answer in the interview

"Over many steps, the context fills with tool outputs, file contents and history; eventually it overflows, but long before that quality and cost suffer because the model has to attend to lots of stale information. So I use compaction, summarising older history into decisions, state and next steps when we approach the limit. Old tool outputs are cleared or truncated. The agent keeps structured notes outside the context, like a progress file or to-do list, and re-reads them, which lets work continue across resets. Sub-agents explore in fresh contexts and return only condensed results. And information is retrieved just in time, by reading a file or searching, rather than loading everything upfront."

Likely follow-up questions

  • What must survive compaction? The goal, constraints, decisions with reasons, current state, completed side effects and next steps.
  • Why not just use a bigger context window? Cost, latency and attention quality degrade with size.
  • How does prompt caching help? It cuts cost and latency for the stable prefix, but not the attention problem.
