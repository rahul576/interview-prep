What does a HEALTHCHECK instruction do?

Docker · concept · levels entry

In one line

HEALTHCHECK defines a command Docker runs periodically inside the container to test whether the application really works, marking it starting, healthy or unhealthy.

Detailed explanation

A running process is not the same as a working application. A web server can be alive but deadlocked, or a service can be up while still loading data. The HEALTHCHECK instruction in a Dockerfile (or the healthcheck key in Compose) tells Docker how to probe the application from inside the container. Docker runs the command at a fixed interval; exit code 0 means healthy and exit code 1 means unhealthy.

The options tune the behaviour. --interval sets how often the check runs, --timeout how long one check may take, --retries how many consecutive failures turn the status into unhealthy, and --start-period gives slow-starting applications a grace period in which failures do not count. Newer Docker versions also support --start-interval to probe more frequently during that start period. The status is shown in docker ps and the recent check output in docker inspect.

Other tools use this status. Docker Compose can make a service wait for a dependency with depends_on and condition: service_healthy. Docker Swarm replaces tasks that become unhealthy and waits for health during rolling updates. Plain Docker, however, does not restart an unhealthy container by itself. Kubernetes ignores the Dockerfile HEALTHCHECK completely and uses its own liveness, readiness and startup probes defined in the pod spec.

How it works

  1. Docker starts the container and its status is starting.
  2. After each interval Docker executes the check command inside the container.
  3. Exit 0 marks a success; a non-zero exit or timeout counts as a failure.
  4. Failures during the start period are ignored unless a check succeeds.
  5. After retries consecutive failures the status becomes unhealthy.
  6. Compose, Swarm or monitoring react to the status.

Example

FROM eclipse-temurin:21-jre
COPY app.jar /app.jar
HEALTHCHECK --interval=30s --timeout=3s --start-period=40s --retries=3 \
  CMD wget -qO- http://localhost:8080/actuator/health || exit 1
CMD ["java", "-jar", "/app.jar"]
docker inspect --format '{{json .State.Health}}' orders | jq

Common mistakes

  • Checking every downstream dependency, so one database blip marks all services unhealthy.
  • Installing curl just for the check and growing the attack surface; a tiny built-in check or the app binary itself is often better.
  • Forgetting --start-period for slow apps, so they flap to unhealthy at boot.
  • Expecting plain Docker to restart unhealthy containers automatically.

How to answer in the interview

"HEALTHCHECK tells Docker how to test that the application inside the container actually works, not just that the process exists, for example by calling a health endpoint every 30 seconds with a 3 second timeout and 3 retries. Docker marks the container starting, healthy or unhealthy, and start-period gives slow apps time to boot. Compose can wait for a healthy dependency with depends_on and service_healthy, and Swarm replaces unhealthy tasks. Plain Docker doesn't restart unhealthy containers, and Kubernetes ignores HEALTHCHECK and uses its own probes."

Likely follow-up questions

  • Why might adding curl just for the healthcheck be a bad idea? It adds size and CVEs; distroless images have no curl, so use a built-in check instead.
  • Does Kubernetes use HEALTHCHECK? No, it uses liveness, readiness and startup probes.
  • Where do you see the last results? docker inspect under State.Health.
