How do you secure Docker containers and images?

Docker · concept · levels mid, senior

In one line

Secure containers across the lifecycle: minimal, trusted, pinned base images rebuilt regularly; run as non-root, read-only filesystem, dropped capabilities, no-new-privileges; scan for CVEs (Trivy, Grype) in CI; never put secrets in images (use build secret mounts and runtime injection); sign images and never use --privileged or Docker socket mounts.

Detailed explanation

Image security starts with what you build on. Use minimal bases (slim, Alpine, distroless) from trusted publishers, pinned to a version or digest, and rebuild regularly so OS patches flow in. Multi-stage builds keep compilers and tools out of production images. Scan images with Trivy or Grype in CI and fail the build on critical, fixable vulnerabilities; rescan images in the registry because new CVEs appear after build.

Secrets never belong in images: anything in a layer is readable by anyone who can pull it, even if a later layer deletes it, and ARG/ENV values appear in docker history. Use BuildKit secret mounts (RUN --mount=type=secret) at build time and inject secrets at runtime from a secret manager.

Runtime security limits the damage if the app is exploited:

  • Non-root user (USER 10001), ideally with rootless Docker or user namespaces.
  • Read-only root filesystem with tmpfs for temporary paths.
  • Drop all Linux capabilities and add back only what's needed (NET_BIND_SERVICE for ports below 1024).
  • no-new-privileges to block setuid escalation; keep the default seccomp and AppArmor/SELinux profiles.
  • Resource limits (memory, CPU, PIDs).
  • Never --privileged, host namespaces or /var/run/docker.sock mounts, because the socket equals root on the host.

Supply chain: sign images with cosign (Sigstore), generate SBOMs, and let only signed images from your private registry run, enforced by admission policies.

How it works

  1. Build: minimal pinned base, multi-stage, non-root USER, no secrets.
  2. CI: lint (hadolint), scan (Trivy), generate SBOM, sign.
  3. Registry: private, scan on push, immutable tags.
  4. Deploy: verify signatures; apply hardened runtime settings.
  5. Operate: rescan, patch by rebuilding, monitor at runtime (Falco).

Example

# syntax=docker/dockerfile:1
FROM python:3.12-slim
RUN useradd -r -u 10001 app
WORKDIR /app
COPY requirements.txt .
RUN --mount=type=secret,id=pip_conf,target=/etc/pip.conf pip install --no-cache-dir -r requirements.txt
COPY --chown=app . .
USER 10001
CMD ["python", "main.py"]
trivy image --severity CRITICAL,HIGH --exit-code 1 registry.example.com/api:1.2.0
cosign sign --yes registry.example.com/api@sha256:4c1a...
docker run --read-only --cap-drop ALL --security-opt no-new-privileges \
  --pids-limit 100 --memory 256m registry.example.com/api:1.2.0

Common mistakes

  • Copying .env files or cloud keys into the image.
  • Running as root because "it's only a container".
  • Scanning once at build time and never again.
  • Mounting the Docker socket into an app or CI container.
  • Pinning nothing, so builds pull unexpected base changes.

How to answer in the interview

"I secure both the image and the runtime. Images start from minimal, trusted bases pinned to a version or digest, use multi-stage builds, and are rebuilt regularly for patches. CI scans them with Trivy or Grype and fails on critical vulnerabilities. Secrets never go into images or layers, because a secret deleted in a later layer is still in the earlier one; I use BuildKit secret mounts and runtime injection. At runtime containers run as non-root with a read-only filesystem, dropped capabilities and no-new-privileges, never privileged and never with the Docker socket mounted. Finally I sign images with cosign and only deploy signed images from our private registry."

Likely follow-up questions

  • Why is a secret removed in a later layer still exposed? Layers are additive; the earlier layer still contains the file and can be extracted.
  • What does --cap-drop ALL do? Removes all Linux capabilities from root inside the container, limiting kernel-level privileges.
  • Why is the Docker socket dangerous? It lets the holder start privileged containers that mount the host.
