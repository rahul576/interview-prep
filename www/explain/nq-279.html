How would you test a service that interacts with multiple downstream systems?

Testing · scenario · levels mid

In one line

Test the orchestration logic with each downstream client mocked across success and failure combinations, run integration tests with WireMock and Testcontainers to exercise real protocols, timeouts, retries and circuit breakers, use contract tests to keep assumptions aligned with providers, and keep only a few end-to-end tests in staging.

Detailed explanation

A service that calls, say, inventory, payment and shipping has two kinds of risk: its own logic (ordering, compensations, mapping, fallbacks) and the integration (HTTP details, serialisation, timeouts, real error formats). Each needs a different test level.

Unit level: each downstream system sits behind an interface (InventoryClient, PaymentClient, ShippingClient). Mock them and test combinations: all succeed; inventory says out of stock; payment declined; payment times out after stock was reserved (is the reservation released?); shipping fails after payment (is a refund or retry scheduled?); unexpected empty responses. Verify call order with InOrder where it matters and that compensating actions happen. These tests are fast and cover the combinatorial explosion cheaply.

Integration level: start the service with WireMock servers for each HTTP dependency and Testcontainers for its own database and Kafka. Stub realistic responses, then failures: 500, 503 with Retry-After, malformed JSON, and delays longer than the configured timeout (withFixedDelay, withChunkedDribbleDelay). Assert that the real Resilience4j retries, timeouts and circuit breakers behave as configured, using WireMock's verify(exactly(3), ...) for retry counts. Also assert persisted state and published events, especially no partial writes.

Contract level: Pact or Spring Cloud Contract ensures the stubs you wrote match each provider's real API, so the WireMock tests are not testing a fantasy. Ideally stubs are generated from the contracts or OpenAPI specs.

End-to-end: a few critical journeys in staging verify configuration, networking and authentication across real services.

How it works

  1. Define one client interface per downstream system.
  2. Unit test orchestration with mocks for all outcome combinations.
  3. Integration test with WireMock (HTTP) and Testcontainers (DB, Kafka).
  4. Inject faults: errors, delays, malformed payloads.
  5. Verify contracts with providers.
  6. Run a handful of E2E smoke tests post-deployment.

Example

@SpringBootTest
@EnableWireMock(@ConfigureWireMock(name = "payment", baseUrlProperties = "clients.payment.url"))
class CheckoutIT {

    @InjectWireMock("payment") WireMockServer payment;
    @Autowired CheckoutService checkout;
    @Autowired ReservationRepository reservations;

    @Test
    void releasesStockWhenPaymentTimesOut() {
        payment.stubFor(post("/charges")
            .willReturn(okJson("{\"status\":\"OK\"}").withFixedDelay(3_000))); // > 2s timeout

        assertThatThrownBy(() -> checkout.placeOrder(sampleCart()))
            .isInstanceOf(PaymentUnavailableException.class);

        payment.verify(3, postRequestedFor(urlEqualTo("/charges")));  // retries
        assertThat(reservations.findActive()).isEmpty();               // compensated
    }
}

Common mistakes

  • Testing only the happy path where all dependencies succeed.
  • Hand-written stubs that drift from the real provider API.
  • Relying on a shared staging environment for all scenarios.
  • Not testing timeouts, so a slow dependency blocks threads in production.

How to answer in the interview

"At unit level I mock each downstream client interface and test the orchestration: everything succeeds, each one fails, timeouts, empty responses, and I verify compensations and fallbacks happen and calls are made in the right order. At integration level I run the service with WireMock stubbing each HTTP dependency, including 500s and delays longer than the timeout, to prove retries, timeouts and circuit breakers work, with Testcontainers for our database and Kafka, asserting persisted state and events. Contract tests with Pact or Spring Cloud Contract keep my stubs honest, and a few end-to-end tests run in staging."

Likely follow-up questions

  • How do you simulate a slow service? WireMock withFixedDelay or fault injection; Toxiproxy for network-level latency.
  • How do you test a circuit breaker opens? Stub repeated failures, then assert calls stop reaching WireMock and the fallback is used.
  • How do you avoid stub drift? Generate stubs from contracts or OpenAPI and verify them on the provider side.
