For a data warehouse MCP server, should you expose one run_sql tool or several specific tools?

MCP Servers · design · levels mid, senior

In one line

A generic run_sql tool is flexible but risky (expensive, wrong or exfiltrating queries); purpose-built tools like get_metric are safer and easier for models; the best design usually combines curated tools with a constrained SQL tool, backed by a read-only role, limits, schema discovery and per-user authorisation.

Detailed explanation

Generic run_sql. Strong models write decent SQL, so a single tool can answer almost any question. But the risks are large: a model can run a full-table scan costing real money or locking resources; it may join incorrectly and confidently present wrong numbers; and through prompt injection (a malicious string in a document or ticket the agent reads) it can become an exfiltration tool, querying sensitive tables and leaking results. It is also hard to reason about what data is reachable.

Purpose-built tools. get_metric(metric, from, to, granularity, filters), top_customers(by, period, limit), compare_periods(metric, a, b) encode business definitions (what counts as "active user" or "revenue"), return consistent, correct numbers and are much easier for the model to use. They are safer because the query shapes are fixed and parameterised.

Combined approach. Offer curated tools for the common 80% of questions, plus a constrained SQL tool for analysts who need flexibility:

  • runs with a read-only database role limited to allowlisted schemas or views;
  • enforces row limits, statement timeouts and cost guards (e.g. a dry-run estimate on BigQuery or Snowflake warehouse limits);
  • rejects anything but a single SELECT, parsed rather than regex-checked.

Schema discovery via list_tables and describe_table tools, or schema resources, with descriptions of columns and business meaning, cached, so the model writes correct queries without guessing.

Authorisation is the most important point: queries run with the calling user's identity (OAuth token exchange, impersonation or per-user credentials), not a shared service account, so row-level security and column masking still apply and audit logs show who asked.

How it works

  1. Define common metrics in a semantic layer; expose them as tools.
  2. Provide schema discovery tools/resources with business descriptions.
  3. Offer query_sql restricted to read-only, allowlisted views with limits.
  4. Execute as the end user; RLS and masking apply.
  5. Log every query with user, cost and rows returned.

Example

@mcp.tool()
def get_metric(metric: Literal["revenue", "orders", "active_users"],
               start: date, end: date, granularity: Literal["day", "week", "month"] = "day") -> dict:
    """Return a business metric over time using official definitions."""
    return semantic_layer.query(metric, start, end, granularity, user=current_user())

@mcp.tool()
def query_sql(sql: str) -> dict:
    """Run one read-only SELECT against analytics views. Max 1,000 rows, 30 s."""
    stmt = sqlglot.parse_one(sql)
    if stmt.key != "select":
        raise ToolError("Only a single SELECT statement is allowed.")
    with warehouse.connect(as_user=current_user(), role="ANALYST_RO") as c:
        c.execute("SET statement_timeout = '30s'")
        return c.fetch(sql, max_rows=1000)

Common mistakes

  • A shared admin service account behind run_sql.
  • Regex-based "read-only" checks that miss WITH ... DELETE or multiple statements.
  • No row or cost limits.
  • Agents calling list_tables before every query because schema context is not cached.

How to answer in the interview

"A single run_sql tool is flexible, but risky: expensive or wrong queries, and with prompt injection it can become an exfiltration tool. Purpose-built tools like get_metric or top_customers encode business definitions, are safer and easier for the model. In practice I combine them: curated tools for common questions, plus a constrained SQL tool for analysts with a read-only role, allowlisted views, row limits, timeouts and cost guards. Schema discovery comes through describe_table tools or resources, cached. Most importantly, queries run as the calling user, not a shared service account, so row-level security still applies."

Likely follow-up questions

  • Stop list_tables before every query? Provide a schema resource or include a short schema summary in server instructions, with caching hints.
  • How to catch wrong answers? Prefer semantic-layer metrics and evaluate against known results.
  • Which warehouse features help? Row access policies, masking policies, query tags and resource monitors.
