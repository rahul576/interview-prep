What is OpenTofu, and why does it exist?

Infrastructure as Code · concept · levels mid

In one line

OpenTofu is the open-source fork of Terraform created in 2023 after HashiCorp moved Terraform to the Business Source License (BSL); it is governed under the Linux Foundation, stays under the MPL 2.0, is largely drop-in compatible, and has since added its own features such as client-side state encryption.

Detailed explanation

In August 2023 HashiCorp relicensed Terraform (from version 1.6 onwards) from the Mozilla Public License 2.0 to the BSL 1.1, which forbids using it to build products that compete with HashiCorp. Most end users can still use Terraform freely, but vendors of Terraform automation platforms and many companies with strict open-source policies were affected. A group of companies forked the last MPL version as OpenTF, which was renamed OpenTofu and accepted into the Linux Foundation; the first stable release (1.6) arrived in January 2024. HashiCorp itself has since been acquired by IBM.

Compatibility. OpenTofu uses the same HCL language, the same provider plugin protocol and the same state format, so providers such as hashicorp/aws work unchanged, served through the OpenTofu registry. For configurations written for Terraform 1.5 and earlier, migration is usually swapping the terraform binary for tofu, running tofu init and checking that tofu plan shows no changes.

Divergence. Since the fork each project has added features independently. OpenTofu added client-side state and plan encryption, early variable evaluation (variables in backend and module source blocks), provider for_each, the -exclude flag and .tofu files that override .tf files for tool-specific code. Terraform added its own features in newer releases, so configurations using the latest syntax of one tool may not work on the other.

The choice is therefore about licensing and governance, support (HashiCorp/IBM and HCP Terraform versus community or third-party vendors) and the features you need.

How it works

  1. Inventory Terraform version, providers, modules and backend.
  2. Check for Terraform-only features or HCP Terraform dependencies.
  3. Back up state; install tofu in CI.
  4. Run tofu init and tofu plan; expect no changes.
  5. Switch pipelines environment by environment, starting with dev.

Example

terraform {
  encryption {
    key_provider "aws_kms" "main" {
      kms_key_id = "alias/tofu-state"
      region     = "eu-west-1"
      key_spec   = "AES_256"
    }
    method "aes_gcm" "main" {
      keys = key_provider.aws_kms.main
    }
    state { method = method.aes_gcm.main }
  }
}

Common mistakes

  • Assuming the two tools will stay identical forever.
  • Switching without checking HCP Terraform features in use (Sentinel, run tasks, private registry).
  • Mixing both binaries on the same state.
  • Treating it as purely technical when it is mostly a licensing and support decision.

How to answer in the interview

"OpenTofu is the open source fork of Terraform. HashiCorp moved Terraform to the Business Source License in 2023, which restricts competing commercial use, so the community forked the last MPL version under the Linux Foundation. It uses the same HCL, providers and state format, so for most existing code switching is replacing the binary and confirming a clean plan. Since then they've diverged: OpenTofu has features like client-side state encryption and early variable evaluation, Terraform has its own newer features. Teams choose based on licence, support and the features they rely on."

Likely follow-up questions

  • What would you check before switching? Terraform version used, HCP features, CI tooling support, provider availability, and a clean plan per stack.
  • Is state compatible? Yes for the common format, but test, and do not alternate tools on the same state.
  • Does the BSL affect a normal company using Terraform internally? Generally no; it targets competing hosted or embedded offerings.
