What are service control policies and permission boundaries, and when do you use each?

Cloud (AWS) · concept · levels mid

In one line

Service control policies cap permissions for whole accounts or OUs in AWS Organizations and act as organisation guardrails, while permission boundaries cap a single IAM user or role and enable safe delegation of role creation; neither grants anything.

Detailed explanation

SCPs are attached to the organisation root, an organisational unit or an account. They limit every IAM principal in member accounts, including the account root user and administrators, but not the management account or service-linked roles. Typical guardrails deny use of unapproved regions (with exceptions for global services), deny stopping or deleting CloudTrail, GuardDuty or Config, deny leaving the organisation, deny deleting backup vaults or disabling S3 Block Public Access, and deny creating IAM users with access keys. Most organisations keep the default FullAWSAccess and add deny-list statements, which are easier to maintain than allow lists. RCPs complement SCPs by capping access to resources, for example blocking principals outside the organisation.

A permission boundary is a managed policy set as the boundary on a user or role. The effective permissions are the intersection of the identity policies and the boundary. The main use case is delegated administration: platform teams let developers create roles for their Lambda functions or pipelines, but only if those roles carry the company boundary. The developers' own policy has a condition iam:PermissionsBoundary equal to the boundary ARN on iam:CreateRole and iam:PutRolePolicy, and denies removing or editing the boundary. So even if a developer attaches AdministratorAccess to a new role, that role can do no more than the boundary allows, and privilege escalation is blocked.

Use SCPs for broad, non-negotiable rules across many accounts; use boundaries for fine-grained limits inside an account where IAM creation is delegated.

How it works

  1. Organisation admin attaches SCPs to OUs such as Workloads or Sandbox.
  2. Every request in member accounts is checked against the SCP chain.
  3. In an account, the platform team publishes a boundary policy.
  4. Developers may create roles only with that boundary attached.
  5. Effective permissions are identity policy intersected with boundary and SCPs.

Example

SCP denying regions outside the EU (global services excluded):

{
  "Effect": "Deny",
  "NotAction": ["iam:*", "organizations:*", "sts:*", "cloudfront:*", "route53:*", "support:*"],
  "Resource": "*",
  "Condition": {"StringNotEquals": {"aws:RequestedRegion": ["eu-west-1", "eu-central-1"]}}
}

Developer policy forcing the boundary on new roles:

{
  "Effect": "Allow",
  "Action": ["iam:CreateRole", "iam:AttachRolePolicy", "iam:PutRolePolicy"],
  "Resource": "arn:aws:iam::111122223333:role/app-*",
  "Condition": {"StringEquals": {
    "iam:PermissionsBoundary": "arn:aws:iam::111122223333:policy/DevBoundary"}}
}

Common mistakes

  • Thinking SCPs grant permissions or restrict the management account.
  • Region-deny SCPs that forget global services and break IAM or CloudFront.
  • Boundaries without a deny on changing or deleting the boundary itself.
  • Testing SCPs directly on production OUs instead of a test OU.

How to answer in the interview

"SCPs belong to AWS Organizations and apply to accounts or OUs. They set the maximum permissions for everyone in those accounts, even admins, so I use them as guardrails: deny unapproved regions, deny disabling CloudTrail or GuardDuty, deny leaving the organisation. Permission boundaries attach to one user or role and cap that identity. Their main purpose is safe delegation: developers can create roles only with the company boundary attached, so they cannot escalate. Neither grants permissions; they only limit what other policies allow."

Likely follow-up questions

  • How let developers create IAM roles without becoming admins? Require the boundary via the iam:PermissionsBoundary condition and deny changing it.
  • Deny list or allow list SCPs? Deny lists are easier to maintain; allow lists are stricter but break when new services appear.
  • How do you test an SCP safely? Attach it to a test OU first and check CloudTrail for denials.
