What is the PID 1 problem in containers, and how do you solve it?

Docker · concept · levels mid

In one line

The main process is PID 1 in the container's PID namespace, and PID 1 ignores signals without explicit handlers and must reap zombie processes; fix it with exec form / exec so the app is PID 1, SIGTERM handling, and a tiny init such as tini (docker run --init).

Detailed explanation

Inside a container the first process gets PID 1, the role normally held by systemd or init. The kernel treats PID 1 specially in two ways that surprise applications.

First, signals. For PID 1 the kernel does not apply the default action of signals like SIGTERM and SIGINT; if the process has not installed a handler, the signal is simply ignored. Many applications rely on the default "terminate" behaviour, so docker stop sends SIGTERM, nothing happens, and after the timeout (10 seconds) Docker sends SIGKILL. The app never shuts down gracefully: in-flight requests are cut and connections are not closed. The same happens when a shell is PID 1, as with shell-form CMD: /bin/sh does not forward SIGTERM to its child.

Second, zombie reaping. When a process exits, its parent must call wait() to collect its status. If the parent dies first, orphans are re-parented to PID 1, which is expected to reap them. An application that spawns subprocesses (headless browsers, shell scripts, CI agents) but never reaps orphans accumulates zombies, which can exhaust the PID limit.

The solutions combine: use the exec form of CMD/ENTRYPOINT and exec "$@" at the end of entrypoint scripts so the real application is PID 1; implement a SIGTERM handler for graceful shutdown; and when the app spawns children, run a minimal init such as tini or dumb-init as PID 1, which forwards signals and reaps zombies. docker run --init or init: true in Compose injects tini automatically. In Kubernetes, shareProcessNamespace makes the pause container PID 1.

How it works

  1. Docker starts the configured command as PID 1.
  2. docker stop sends SIGTERM to PID 1.
  3. Without a handler, PID 1 ignores it; SIGKILL follows after the grace period.
  4. With tini, tini is PID 1, forwards the signal to the app and reaps orphans.
  5. The app shuts down and exits; the container stops promptly.

Example

FROM node:22-slim
RUN apt-get update && apt-get install -y --no-install-recommends tini && rm -rf /var/lib/apt/lists/*
COPY . /app
ENTRYPOINT ["/usr/bin/tini", "--"]
CMD ["node", "/app/server.js"]
docker run --init myapp        # alternative: Docker injects tini
time docker stop myapp         # should be well under 10 s

Common mistakes

  • Shell-form CMD, making sh PID 1 and swallowing SIGTERM.
  • Entrypoint scripts that run the app without exec.
  • Assuming the app handles SIGTERM because it does so outside containers.
  • Ignoring zombie processes in containers that spawn subprocesses.

How to answer in the interview

"The main process of a container is PID 1 in its namespace, and Linux treats PID 1 specially. Signals like SIGTERM are ignored unless the process installs a handler, so docker stop waits for the timeout and then kills it, with no graceful shutdown. PID 1 also has to reap orphaned children, otherwise zombies pile up. I make the app itself PID 1 with exec-form CMD or exec in entrypoint scripts, make sure it handles SIGTERM, and if it spawns child processes I run tini as init, for example with docker run --init."

Likely follow-up questions

  • How can shell-form CMD block SIGTERM? The shell becomes PID 1 and does not forward signals to the app.
  • What does tini do? Forwards signals to the child and reaps zombies.
  • How do you test it? Time docker stop and check the app logs a graceful shutdown.
