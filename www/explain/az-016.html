How do you connect Azure Pipelines to Azure securely, without long-lived secrets?

Azure DevOps & Pipelines · concept · levels mid, senior

In one line

Use an Azure Resource Manager service connection with workload identity federation (OIDC): each pipeline run gets a short-lived token that Entra ID trusts, so there is no client secret to store or rotate, combined with least-privilege scope and pipeline permissions, approvals and checks on the connection.

Detailed explanation

Pipelines need an identity in Entra ID to deploy to Azure. Traditionally this was a service principal with a client secret, stored in the service connection. Secrets expire (causing failed deployments), must be rotated, and if leaked can be used from anywhere until revoked.

Workload identity federation removes the secret. You create an app registration or a user-assigned managed identity and add a federated identity credential that trusts tokens from Azure DevOps: the issuer is your Azure DevOps organisation's token endpoint, and the subject identifies the specific service connection (organisation, project and connection name). At run time, Azure DevOps issues a short-lived OIDC token for the job; the Azure task exchanges it with Entra ID for an access token. Nothing long-lived exists to leak. Azure DevOps can create this automatically, and existing secret-based connections can be converted.

Least privilege still matters. Scope the identity's role assignment to the specific resource group or subscription, with a role like Contributor or narrower custom roles, rather than Owner on the subscription. Use separate connections and identities per environment, so a dev pipeline cannot touch production.

Protect the service connection itself: disable "grant access to all pipelines" and authorise specific pipelines; add approvals and checks (manual approval, required template, branch control so only main can deploy to production); restrict who can manage the connection. Audit usage through the connection's history.

How it works

  1. Create a service connection of type Azure Resource Manager with workload identity federation.
  2. Entra ID gets an identity with a federated credential for that connection.
  3. Grant the identity a least-privilege role on the target scope.
  4. Configure pipeline permissions, branch control and approvals on the connection.
  5. At run time the job receives an OIDC token and exchanges it for an Azure token.
  6. Tasks such as AzureCLI@2 deploy using that token.

Example

- task: AzureCLI@2
  inputs:
    azureSubscription: sc-orders-prod-wif    # federated service connection
    scriptType: bash
    scriptLocation: inlineScript
    inlineScript: |
      az deployment group create -g rg-orders-prod \
        --template-file infra/main.bicep --parameters env=prod

Federated credential subject format (for reference):

issuer:  https://vstoken.dev.azure.com/<organization-id>
subject: sc://<organization>/<project>/<service-connection-name>

Common mistakes

  • Keeping secret-based service principals with long expiry.
  • One subscription-wide Owner connection shared by every pipeline.
  • Allowing all pipelines to use the production connection.
  • No branch control, so feature branches can deploy to production.
  • Same identity for dev and prod.

How to answer in the interview

"Pipelines authenticate to Azure through an Azure Resource Manager service connection. Instead of a service principal with a client secret that must be rotated, I use workload identity federation: Azure DevOps issues an OIDC token for each run, and Entra ID trusts it through a federated credential tied to that specific service connection, so there is no secret to leak or rotate. The identity is scoped to the specific subscription or resource group with least-privilege roles, and separate per environment. On the connection I restrict pipeline permissions so only approved pipelines can use it, and add approvals, branch control and checks for production."

Likely follow-up questions

  • How is this similar to GitHub Actions OIDC with AWS? Same pattern: the CI platform issues an OIDC token that the cloud trusts via a federated role or credential.
  • How do you migrate existing secret-based connections? Convert them in Azure DevOps to workload identity federation and remove the old secret.
  • What about self-hosted agents in Azure? They can also use a managed identity, but federation per connection gives better separation.
