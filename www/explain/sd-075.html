How do you design for graceful degradation when parts of the system fail?

Scalability & Reliability · concept · levels senior, lead

In one line

Graceful degradation keeps critical journeys working when parts fail: classify critical vs optional features, add fallbacks (cache, defaults, hide), kill switches, read-only/static modes, queue writes for later, and verify it all with chaos engineering.

Detailed explanation

Users forgive a missing "recommended for you" row; they don't forgive a checkout that fails. Design starts by mapping each user journey and labelling each dependency as critical (must work) or optional (nice to have).

For optional dependencies: timeouts + circuit breakers + fallbacks. Fallbacks can be cached values (last known recommendations), static defaults (popular products), reduced functionality (search without personalisation) or hiding the widget.

For overload or severe incidents: feature flags/kill switches to switch off expensive features (live inventory counts, heavy reports); static or read-only modes (serve cached pages from CDN, disable profile edits); queue writes that don't need immediate processing (reviews, analytics events) and process them later.

Degradation paths are code that rarely runs, so they rot. Chaos engineering and game days (inject latency, kill dependencies in staging and carefully in production) prove they work.

How it works

  1. Dependency map per journey; mark critical/optional.
  2. For each optional call: timeout, breaker, fallback, metric.
  3. Kill switches for expensive features, wired into runbooks.
  4. Degraded modes documented and testable.
  5. Regular chaos experiments.

Example

Product page dependencies:
  catalog (critical)        → cache + replica
  price/stock (critical)    → must succeed, else "temporarily unavailable" for buy button
  reviews (optional)        → hide section on failure
  recommendations (optional)→ fall back to "bestsellers" list cached hourly

Common mistakes

  • Treating every dependency as critical.
  • Fallbacks that depend on the same failing system.
  • Never testing degraded modes.
  • Silent degradation without metrics.

How to answer in the interview

"I map each journey's dependencies into critical and optional. Optional ones get timeouts, circuit breakers and fallbacks like cached data, defaults or hiding the feature. Operators have kill switches for expensive features and can put the site into read-only or cached mode, and deferrable writes go to queues. We validate these paths with chaos experiments, because untested fallbacks fail when you need them."

Likely follow-up questions

  • Test fallbacks? Fault injection in staging and controlled production experiments.
  • What can't degrade? Payments, auth, order placement.
  • Communicate degradation to users? Clear banners and status pages.
