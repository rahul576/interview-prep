Design a web crawler that indexes billions of pages.

Classic Design Problems · design · levels mid, senior

In one line

A web crawler is a loop of URL frontier → polite distributed fetchers → parse and extract links → deduplicate (Bloom filters/hashes) → back into the frontier, storing pages in object storage for indexing, with robots.txt, per-host rate limits, DNS caching and trap protection.

Detailed explanation

Frontier: not a simple queue. It has priority queues (important or frequently changing pages first) feeding per-host queues, so each host is fetched by only one worker with a delay between requests (politeness). URLs are partitioned by host hash across crawler nodes.

Fetchers: async HTTP clients with timeouts, size limits, redirect limits, respect for robots.txt (cached per host) and Crawl-delay. DNS resolution is surprisingly slow at this scale, so use a caching resolver.

Dedup: URL normalisation (lowercase host, remove fragments, sort params, strip tracking params) then a seen set: a Bloom filter in memory (fast, tiny false-positive rate) or a distributed KV. Content dedup with hashes (exact) or SimHash (near-duplicates).

Traps: infinite calendars, session IDs in URLs, endless generated pages. Defend with max depth, max URLs per host, URL length limits and pattern detection.

Recrawl: schedule per page based on observed change frequency.

How it works

  1. Seed URLs → frontier.
  2. Worker takes host queue → check robots → fetch → store raw page (WARC) in S3.
  3. Parse → extract & normalise links → dedup → enqueue new URLs with priority.
  4. Indexing pipeline consumes stored pages separately.

Example

Scale: 1B pages/month ≈ 400 pages/s; avg 500 KB → ~500 TB/month raw (compress!)
Seen-set Bloom filter for 10B URLs @1% FP ≈ 12 GB

Common mistakes

  • Hammering a single host.
  • Ignoring robots.txt.
  • No URL normalisation (same page crawled 100 ways).
  • Doing indexing inside the fetch loop.

How to answer in the interview

"A prioritised URL frontier feeds per-host queues so each site is crawled politely, respecting robots.txt. Distributed fetchers with DNS caching download pages to object storage. Parsers extract and normalise links, a Bloom filter or KV store deduplicates them, and new URLs go back with a priority. Content hashes or SimHash detect duplicate pages, depth and per-host caps avoid traps, and indexing runs as a separate pipeline."

Likely follow-up questions

  • Detect traps? Depth limits, URL pattern repetition, per-host page caps.
  • Freshness? Adaptive recrawl intervals based on change history.
  • JavaScript sites? Headless rendering for a subset, much more expensive.
