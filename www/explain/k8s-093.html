How does leader election work for controllers and applications running with multiple replicas on Kubernetes?

Kubernetes · concept · levels mid, senior

In one line

Replicas compete for a Lease object in coordination.k8s.io; the holder is the leader and keeps renewing it, others watch and take over when it expires, giving active-passive operation, with fencing or idempotency needed for the brief overlap a partition can cause.

Detailed explanation

Many controllers must not run their reconcile loop twice at the same time: two schedulers would bind the same pod differently, and two operators might create duplicate cloud resources. Kubernetes solves this with leader election over Lease objects. The Lease records holderIdentity, leaseDurationSeconds, acquireTime and renewTime, and updates rely on the API server's optimistic concurrency (resourceVersion), so only one replica can win a given write.

In client-go the common defaults are a lease duration of 15 seconds, a renew deadline of 10 seconds and a retry period of 2 seconds. The leader renews regularly; if it cannot renew before the deadline, it must stop doing leader work. Followers keep trying to acquire; once renewTime + leaseDuration has passed, one of them updates the Lease and becomes leader. kube-controller-manager, kube-scheduler and nearly every operator built with controller-runtime use this. Your own applications can use the same libraries or a sidecar.

The caveat is that this is time-based, not a perfect lock. A leader stuck in a long GC pause or partitioned from the API server may keep acting for a moment after another replica has taken over. Side effects that must never happen twice need fencing tokens (for example, checking a lease generation on the target system) or idempotent operations.

How it works

  1. Each replica starts and tries to create or update the named Lease.
  2. The successful writer becomes leader and starts its work loops.
  3. The leader renews renewTime every few seconds.
  4. Followers watch the Lease and retry periodically.
  5. If renewals stop, the lease expires and a follower acquires it.
  6. The old leader, on failing to renew, stops work or exits.

Example

kubectl -n kube-system get lease kube-scheduler -o yaml
# spec:
#   holderIdentity: master-2_8f3c...
#   leaseDurationSeconds: 15
#   renewTime: "2026-11-21T09:14:03.120000Z"
mgr, _ := ctrl.NewManager(cfg, ctrl.Options{
    LeaderElection:   true,
    LeaderElectionID: "orders-operator.example.com",
})

Common mistakes

  • Assuming leader election is a strict mutex with zero overlap.
  • Running several replicas of a controller without enabling leader election.
  • Setting very short lease durations, causing flapping under API server latency.
  • Doing heavy work in a way that cannot stop quickly when leadership is lost.

How to answer in the interview

"Kubernetes uses Lease objects in the coordination API. Each replica tries to acquire a named Lease; the winner records its identity and renews it every couple of seconds, with a lease duration of around fifteen seconds. The others watch, and if renewals stop because the leader crashed or lost connectivity, the lease expires and another replica takes over. The scheduler, controller manager and operators all work this way, active-passive, to avoid duplicate work. The caveat is that it is time-based, so during a partition or a long pause the old leader may briefly still act, so critical side effects need fencing tokens or idempotency."

Likely follow-up questions

  • Why is a leader-elected singleton still a scaling and availability concern? Only one replica does the work, so throughput is capped and failover leaves a gap of up to the lease duration.
  • How do you scale beyond one leader? Shard work across leases or use partitioned consumers.
  • What happens if the API server is down? The leader cannot renew and steps down; nothing new is reconciled until it returns.
