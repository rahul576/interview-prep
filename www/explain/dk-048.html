How do you authenticate to private registries such as ECR, ACR or GHCR?

Docker · concept · levels mid

In one line

All registries end in docker login, but credentials differ: aws ecr get-login-password for ECR (12-hour token), az acr login for ACR, a token with package scopes for GHCR; use credential helpers, short-lived OIDC credentials in CI, and node/workload identity or imagePullSecrets in Kubernetes.

Detailed explanation

Registries implement the OCI distribution API with token authentication. docker login exchanges credentials for access and, by default, stores them in ~/.docker/config.json, base64-encoded, which is not encryption. The question is how to get those credentials safely.

For Amazon ECR, aws ecr get-login-password --region eu-west-1 | docker login --username AWS --password-stdin <account>.dkr.ecr.eu-west-1.amazonaws.com uses your AWS identity to fetch a token valid for 12 hours. For Azure Container Registry, az acr login --name myreg uses your Entra ID identity; service principals or managed identities cover automation. Google Artifact Registry uses gcloud auth configure-docker. GHCR accepts a GitHub token with read:packages/write:packages, and in GitHub Actions the built-in GITHUB_TOKEN can push to the repository's packages.

Credential helpers (docker-credential-ecr-login, docker-credential-gcloud, osxkeychain, wincred, pass) fetch or store tokens on demand, so no static password sits in config.json. In CI, use OIDC federation: the pipeline presents a signed identity token to AWS, Azure or GCP and receives short-lived credentials, with no long-lived secret stored in CI variables.

In Kubernetes, nodes on managed clusters usually pull from their own cloud registry using the node identity (EKS node role, AKS kubelet identity with AcrPull, GKE service account). For other registries you create an imagePullSecret of type kubernetes.io/dockerconfigjson and reference it in the pod or service account. Kubelet credential provider plugins can fetch tokens dynamically.

How it works

  1. Client requests a token from the cloud provider using its identity.
  2. docker login presents the token to the registry.
  3. The registry issues scoped access for pull or push.
  4. Tokens expire and are refreshed by helpers.
  5. Kubernetes uses node identity or pull secrets per pod.

Example

aws ecr get-login-password --region eu-west-1 \
  | docker login --username AWS --password-stdin 123456789012.dkr.ecr.eu-west-1.amazonaws.com
az acr login --name acmeregistry
echo "$GHCR_TOKEN" | docker login ghcr.io -u my-bot --password-stdin
kubectl create secret docker-registry regcred \
  --docker-server=registry.partner.com --docker-username=bot --docker-password="$PW"
{ "credHelpers": { "123456789012.dkr.ecr.eu-west-1.amazonaws.com": "ecr-login" } }

Common mistakes

  • Long-lived personal access tokens stored in CI variables.
  • Passing passwords with -p, visible in shell history.
  • Assuming config.json encrypts credentials.
  • Giving CI push rights to every repository instead of scoped permissions.

How to answer in the interview

"Every registry ultimately uses docker login, but credentials differ. For ECR I pipe aws ecr get-login-password into docker login, which gives a 12-hour token; for ACR, az acr login uses my Azure identity; GHCR accepts a token with package permissions. Credential helpers like docker-credential-ecr-login or the OS keychain fetch and store tokens instead of a plain password in config.json. In CI I use OIDC federation to get short-lived cloud credentials. In Kubernetes, nodes or workloads pull with their cloud identity, or with an imagePullSecret for other registries."

Likely follow-up questions

  • Why avoid long-lived registry passwords in CI? They leak, are rarely rotated and grant broad access.
  • How does OIDC federation work? The CI issues a signed token the cloud trusts and exchanges for temporary credentials.
  • Where are Docker credentials stored? ~/.docker/config.json or the configured credential store.
