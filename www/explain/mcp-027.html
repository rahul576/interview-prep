How do you build an MCP server in TypeScript or Node.js?

MCP Servers · concept · levels mid, senior

In one line

Use the official TypeScript SDK (@modelcontextprotocol/sdk): create an McpServer, register tools with registerTool and Zod input schemas, return content blocks and optional structuredContent, connect a StdioServerTransport or mount Streamable HTTP in Express, and distribute via npx or containers.

Detailed explanation

The TypeScript SDK is one of the most complete MCP implementations and usually supports new spec features first.

Server. new McpServer({ name, version }) creates a high-level server that handles capability negotiation and dispatch.

Tools. server.registerTool(name, config, handler) takes a title, description, an inputSchema written with Zod (e.g. { city: z.string().describe("City name") }) and optionally an outputSchema. The SDK converts Zod to JSON Schema for tools/list, validates incoming arguments, and passes typed values to the handler. Handlers return { content: [...] } with text, image or resource-link blocks, plus structuredContent when an output schema exists, or isError: true for execution failures.

Resources and prompts are registered similarly with registerResource (including ResourceTemplate for URI templates with completion) and registerPrompt.

Transports. For local servers, await server.connect(new StdioServerTransport()). For remote servers, create a StreamableHTTPServerTransport and handle POSTs inside an Express (or other HTTP framework) route, adding authentication middleware (bearer token validation, protected resource metadata), Origin checks and rate limiting, and deploy behind TLS. Stateless mode, creating a transport per request without session ids, scales easily behind load balancers.

Distribution. Local servers are typically published to npm and launched by hosts with npx -y package-name; remote servers ship as container images to Kubernetes, Cloud Run or similar. Logging in stdio servers uses console.error, never console.log.

How it works

  1. npm init, npm install @modelcontextprotocol/sdk zod.
  2. Create McpServer, register tools/resources/prompts.
  3. Connect a transport (stdio or Streamable HTTP).
  4. Build with tsc; test with the Inspector.
  5. Publish to npm or build a container; configure in hosts.

Example

import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { z } from "zod";

const server = new McpServer({ name: "weather", version: "1.2.0" });

server.registerTool(
  "get_forecast",
  {
    title: "Get forecast",
    description: "3-day forecast for a city. Use for weather questions.",
    inputSchema: { city: z.string().describe("City name, e.g. Pune") },
    outputSchema: { city: z.string(), highs: z.array(z.number()) },
  },
  async ({ city }) => {
    const f = await fetchForecast(city);
    if (!f) return { isError: true, content: [{ type: "text", text: `Unknown city ${city}.` }] };
    const data = { city, highs: f.highs };
    return { content: [{ type: "text", text: JSON.stringify(data) }], structuredContent: data };
  }
);

console.error("weather server starting");   // stderr only
await server.connect(new StdioServerTransport());

Common mistakes

  • console.log in a stdio server.
  • Hosts launching npx package@latest, silently pulling new, unreviewed versions.
  • No auth middleware on the HTTP route.
  • Returning structuredContent that does not match outputSchema.

How to answer in the interview

"I use the official TypeScript SDK, @modelcontextprotocol/sdk. I create an McpServer with a name and version and register tools with registerTool, giving a title, description and a Zod input schema; the SDK converts it to JSON Schema and validates arguments, so handlers get typed values. Handlers return content blocks and optionally structuredContent matching an output schema. Resources and prompts are registered similarly. Locally I connect a StdioServerTransport; for remote servers I mount the Streamable HTTP transport in Express with auth middleware. Local servers are usually distributed via npm and npx, remote ones as container images."

Likely follow-up questions

  • Security implications of npx with latest? Supply-chain risk: a compromised or changed package runs with user privileges; pin versions and review.
  • Stateful or stateless HTTP? Stateless scales more simply; state goes into explicit handles.
  • How to test? In-memory client-server transport pairs in unit tests, plus the Inspector.
