A colleague ran terraform apply locally with a newer Terraform version, and now the pipeline fails reading the state. How do you fix it and prevent it?

Terraform · scenario · levels mid, senior

In one line

A newer Terraform version may write state an older binary refuses to read; the usual fix is to upgrade the pipeline to the same or newer version (or restore the previous state version only if nothing else changed), and prevent it by pinning required_version, using a version manager, and allowing only pipelines to apply to shared environments.

Detailed explanation

Every state file records the Terraform version that last wrote it, along with provider schema versions for each resource. Terraform guarantees that newer versions can read older state, but not the other way round: an older binary may refuse a state written by a newer one, and providers may have upgraded a resource's schema version, which older providers cannot decode. The pipeline then fails during init or plan, even though nobody changed the code.

The quickest and usually safest fix is to move forward: upgrade the pipeline's Terraform version (and providers if needed) to match or exceed the one that wrote the state, after reading the release notes and running a plan to confirm there are no unexpected changes. Going forward is safer than trying to go back.

If upgrading is not acceptable, for example because the new version has a regression, you can restore the previous state version from backend versioning (S3 object versions, Azure blob versions). That is only safe if the local apply made no real changes or you can re-apply them, because the restored state would not know about resources created or modified in between, leading to duplicates or orphans.

Prevention:

  • Pin required_version in configuration, e.g. ~> 1.14.0, so a mismatched binary refuses to run before touching state.
  • Use tfenv, mise or asdf with a .terraform-version / .mise.toml file in the repo, and the same version in CI images.
  • Commit .terraform.lock.hcl so provider versions match.
  • Remove local apply permissions for shared environments; humans plan locally with read-only roles, pipelines apply.

How it works

  1. Local apply with a newer binary writes state with a newer version.
  2. Pipeline with an older binary reads state and fails.
  3. Decide: upgrade pipeline (preferred) or restore previous version.
  4. Run a plan to verify no unexpected changes.
  5. Add version pinning and permission changes to prevent recurrence.

Example

terraform {
  required_version = "~> 1.14.0"
  required_providers {
    azurerm = { source = "hashicorp/azurerm", version = "~> 4.40" }
  }
}
# .mise.toml
[tools]
terraform = "1.14.0"

Common mistakes

  • Restoring an old state version after real changes were applied.
  • required_version = ">= 1.0", which pins nothing.
  • Letting engineers apply to production from laptops.

How to answer in the interview

"Terraform records the version that last wrote the state, and a newer version may write a format or provider schema an older binary refuses to read. The quickest fix is usually to upgrade the pipeline to the same or newer version after reading the release notes, because moving forward is safer than backwards. If that's not acceptable, I can restore the previous state version from backend versioning, but only if nothing changed in between. To prevent it, I pin required_version like ~> 1.14.0 so mismatched binaries refuse to run, use tfenv or mise so everyone has the same version, commit the lock file, and remove local apply rights so only pipelines apply to shared environments."

Likely follow-up questions

  • Why is restoring an old state dangerous? It forgets resources created or changed after it, causing duplicates or orphans.
  • Does required_version protect state? Yes, Terraform checks it before reading or writing state.
  • How do you roll out a Terraform upgrade? PR updates pin and CI image, plan dev first, then promote.
