How do you implement a thread-safe Singleton in Java, and what are the pitfalls?

Design Patterns · concept · levels entry, mid

In one line

The safest thread-safe singletons in Java are an enum with one constant or the initialization-on-demand holder idiom; double-checked locking also works only with a volatile field, and all hand-written singletons suffer from reflection, serialization and testability pitfalls.

Detailed explanation

A singleton guarantees one instance per class loader with a global access point. The hard part is creating it safely when several threads call getInstance() at once.

Options:

  • Eager static final field: private static final Config INSTANCE = new Config(); The JVM runs class initialisation once, under a lock, so this is thread-safe. It is created when the class is initialised, which is often fine.
  • Holder idiom: a private static nested Holder class contains the instance. It is only initialised when getInstance() first touches it, giving lazy creation with no explicit locking, again relying on JLS class-initialisation guarantees.
  • Double-checked locking: check null, synchronise, check again, create. The field must be volatile, otherwise another thread may see a reference to a partially constructed object due to reordering.
  • Enum: enum Config { INSTANCE; } The JVM guarantees one instance, and enums are protected against reflective instantiation and serialization duplicates. Joshua Bloch calls it the best approach in Effective Java.
  • synchronized getInstance(): correct but takes a lock on every call.

Pitfalls:

  • Reflection: setAccessible(true) on a private constructor can create a second instance; guard by throwing if an instance already exists (enum is immune).
  • Serialization: deserialising creates a new object unless you add readResolve() returning the instance.
  • Multiple class loaders (app servers) can each have their own "singleton".
  • Testability: global mutable state leaks between tests and hides dependencies.

In Spring you rarely write one: beans are singleton-scoped by default, one instance per bean definition per container, injected rather than looked up globally.

How it works

  1. Make the constructor private.
  2. Choose a creation strategy (eager, holder, DCL, enum).
  3. Expose a static accessor or the enum constant.
  4. Protect against reflection and serialization if not using an enum.

Example

public final class AppConfig {
    private AppConfig() {
        if (Holder.INSTANCE != null) throw new IllegalStateException("Already created");
    }
    private static final class Holder {
        static final AppConfig INSTANCE = new AppConfig();
    }
    public static AppConfig getInstance() { return Holder.INSTANCE; }
    private Object readResolve() { return getInstance(); } // if Serializable
}

public enum IdGenerator {
    INSTANCE;
    private final java.util.concurrent.atomic.AtomicLong next = new java.util.concurrent.atomic.AtomicLong();
    public long nextId() { return next.incrementAndGet(); }
}

Common mistakes

  • Double-checked locking without volatile.
  • A lazy if (instance == null) instance = new X(); with no synchronisation.
  • Assuming the singleton's own mutable state is thread-safe just because creation is.
  • Using singletons as hidden service locators that make testing painful.

How to answer in the interview

"The simplest thread-safe singleton is an enum with a single INSTANCE, which also handles serialization and reflection. If I need lazy initialisation I use the holder idiom: a private static nested class holds the instance, and JVM class initialisation guarantees it is created once, without locks. Double-checked locking works too, but only with a volatile field. The pitfalls are reflection and serialization creating extra instances, multiple class loaders, and hidden global state that hurts testing. In Spring I just use singleton-scoped beans."

Likely follow-up questions

  • Why is Spring singleton scope not the GoF Singleton? Spring gives one instance per bean definition per container; you can still create other instances, and it is injected, not globally accessed.
  • Why does the holder idiom need no volatile? Class initialisation is synchronised by the JVM and establishes happens-before.
  • Is the singleton's state thread-safe? Not automatically; mutable fields still need synchronisation or concurrent types.
