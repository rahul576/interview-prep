Design a notification service that sends email, SMS and push notifications at scale.

System Design · design · levels senior, lead

In one line

A notification service exposes an API that validates, applies preferences and enqueues, uses channel-specific workers and providers (email, SMS, push) with failover, guarantees idempotency, retries and DLQs, and uses priorities and rate limits so OTPs are never stuck behind marketing.

Detailed explanation

Many services need to notify users, so a central service avoids duplicating provider integrations, templates and preference logic. The core challenge is reliability at scale while respecting user preferences and provider limits.

Intake: producers call POST /notifications (or publish an event) with user ID, template ID, data, channels and priority. The service checks user preferences (opt-outs, channel choices, quiet hours, regulatory consent such as DND registries for SMS in India), resolves contact details, renders templates with localisation, and stores a notification record with a unique ID.

Queueing: messages go to Kafka topics or queues per channel and priority (e.g. sms.critical, email.bulk). Separating priorities is what guarantees an OTP is not delayed behind a 5-million-email campaign; critical queues get dedicated consumers.

Delivery workers call providers: SES/SendGrid for email, Twilio or local SMS gateways for SMS, FCM/APNs for push. They apply per-provider rate limits, use circuit breakers and failover to a secondary provider. Sends are idempotent on notification ID; transient failures retry with exponential backoff, and exhausted messages go to a dead-letter queue for inspection.

Tracking: provider callbacks (delivered, bounced, opened) update status; invalid tokens and hard bounces are cleaned up. Users are protected from spam with frequency caps.

How it works

  1. API receives request with an idempotency key; dedupe.
  2. Apply preferences, quiet hours and frequency caps; render template.
  3. Persist record (status QUEUED) and publish to channel/priority topic.
  4. Worker consumes, calls provider with timeout, records attempt.
  5. Retry with backoff on 5xx/timeouts; DLQ after N attempts.
  6. Webhooks from providers update status to DELIVERED/BOUNCED.

Example

@KafkaListener(topics = "sms.critical", concurrency = "8")
public void sendSms(NotificationMessage msg) {
    if (!deliveryLog.markInProgress(msg.id())) return;      // idempotent
    try {
        smsRouter.primaryOrFailover().send(msg.to(), msg.body());
        deliveryLog.markSent(msg.id());
    } catch (TransientProviderException e) {
        retryScheduler.schedule(msg, backoff(msg.attempt()));  // or DLQ after max attempts
    }
}

Common mistakes

  • One shared queue for OTPs and marketing.
  • Sending synchronously from the calling service.
  • No idempotency, causing duplicate SMS on retries.
  • Ignoring opt-outs, quiet hours and regulatory rules.
  • Never cleaning up dead push tokens or bounced emails.

How to answer in the interview

"Clients call an API that validates the request, checks user preferences, quiet hours and consent, renders the template and publishes to Kafka topics per channel and priority, so callers aren't blocked. Channel-specific workers call providers like SES, an SMS gateway and FCM or APNs, with rate limits, circuit breakers and failover to a second provider. Every send is idempotent on a notification ID, retries use exponential backoff, and failures end in a dead-letter queue. Critical messages like OTPs have their own high-priority queue and consumers, and delivery status is tracked through provider callbacks."

Likely follow-up questions

  • OTP never delayed by a campaign? Separate topics, dedicated consumers and provider quota reserved for critical traffic.
  • How do you schedule notifications? Store send time; a scheduler enqueues due messages.
  • Batching digests? Aggregate low-priority events per user over a window, then send one message.
