What is OpenTelemetry, and how would you roll it out?

Observability & SRE · concept · levels mid, senior

In one line

OpenTelemetry (OTel) is the vendor-neutral CNCF standard (APIs, SDKs, OTLP protocol and Collector) for traces, metrics and logs; roll it out with auto-instrumentation first, W3C traceparent context propagation, a Collector layer for processing and export, sensible sampling, and semantic conventions for consistent attributes.

Detailed explanation

Components:

  • API and SDKs for most languages (Java, .NET, Python, Go, JavaScript and more) to create spans, metrics and logs.
  • Auto-instrumentation: agents and libraries that instrument common frameworks without code changes, such as the Java agent, .NET and Python auto-instrumentation, Node.js packages, and eBPF-based instrumentation for some languages. In Kubernetes, the OpenTelemetry Operator can inject auto-instrumentation via an annotation.
  • OTLP: the standard wire protocol (gRPC 4317, HTTP 4318).
  • Collector: a pipeline of receivers (OTLP, Prometheus, Jaeger, filelog), processors (batch, memory limiter, k8sattributes to add pod and namespace metadata, attribute filtering and redaction, tail sampling) and exporters (OTLP to Tempo, Jaeger, Prometheus remote write, Loki, Datadog, Azure Monitor, Elastic).
  • Semantic conventions: standard attribute names like service.name, http.request.method, k8s.pod.name.

Context propagation: the W3C Trace Context traceparent header (trace ID, span ID, flags) is passed on every HTTP or gRPC call and through message headers, so spans across services join into one trace. Logs include trace and span IDs for correlation.

Why it matters: instrumentation is written once against a standard; the backend is chosen in Collector configuration, so switching or dual-shipping vendors doesn't require code changes.

Sampling: head-based sampling decides at the start of a trace (for example 10 percent), cheap but blind to outcome. Tail-based sampling in the Collector decides after the trace completes, keeping all errors and slow traces plus a percentage of normal ones; it needs all spans of a trace to reach the same Collector instance (a load-balancing exporter routing by trace ID).

Rollout plan: define naming and resource attributes; deploy Collectors (DaemonSet agents per node plus a gateway deployment); enable auto-instrumentation for a pilot service set; add manual spans for key business operations; configure sampling and redaction of sensitive data; build dashboards and train teams; then expand service by service. Signal maturity varies: traces and metrics are stable, logs are stable in the protocol with SDK support maturing by language.

How it works

  1. Service instrumented by auto-agent or SDK creates spans and metrics.
  2. Incoming traceparent continues the trace; outgoing calls propagate it.
  3. Telemetry goes via OTLP to a node-local Collector.
  4. Collector enriches, filters and batches; gateway applies tail sampling.
  5. Exporters send to chosen backends.
  6. Dashboards correlate traces, metrics and logs.

Example

receivers:
  otlp: { protocols: { grpc: {}, http: {} } }
processors:
  memory_limiter: { check_interval: 1s, limit_percentage: 80 }
  k8sattributes: {}
  tail_sampling:
    policies:
      - { name: errors, type: status_code, status_code: { status_codes: [ERROR] } }
      - { name: slow, type: latency, latency: { threshold_ms: 1000 } }
      - { name: base, type: probabilistic, probabilistic: { sampling_percentage: 10 } }
  batch: {}
exporters:
  otlp/tempo: { endpoint: tempo.observability:4317, tls: { insecure: true } }
service:
  pipelines:
    traces: { receivers: [otlp], processors: [memory_limiter, k8sattributes, tail_sampling, batch], exporters: [otlp/tempo] }

Common mistakes

  • Sending directly from apps to a vendor, losing the Collector's flexibility.
  • Tail sampling across multiple Collectors without trace-ID-aware routing.
  • Broken propagation through queues or proxies, producing fragmented traces.
  • No service.name or inconsistent attributes.

How to answer in the interview

"OpenTelemetry is a vendor-neutral CNCF standard for traces, metrics and logs: APIs, SDKs, the OTLP protocol and the Collector. Services are instrumented with SDKs or auto-instrumentation agents, and context is propagated with the W3C traceparent header so traces connect across services. Telemetry goes to the Collector, which adds Kubernetes metadata, filters and samples, then exports to Tempo, Jaeger, Prometheus or a vendor, so we can switch backends without code changes. I'd roll out auto-instrumentation first on a pilot, use the Operator in Kubernetes, then tail-based sampling in a gateway Collector."

Likely follow-up questions

  • Why tail-based over head-based sampling? It keeps all errors and slow traces while dropping routine ones, at the cost of buffering complete traces.
  • Agent versus gateway Collector? Agents run per node for local collection and enrichment; gateways centralise sampling, routing and export.
  • How do you correlate logs with traces? Inject trace and span IDs into structured logs.
