How do you implement data and model lineage across an ML platform?

MLOps · concept · levels mid, senior

In one line

Lineage records which data, features and code produced each model and which model produced each prediction; capture it automatically from pipelines (for example OpenLineage) and ML platforms, store it in a catalog like Unity Catalog, Purview or DataHub, and use it for impact analysis, debugging and audits.

Detailed explanation

Lineage is a graph: source systems feed raw tables, transformations produce feature tables, training runs consume feature versions and code commits to produce model versions, deployments serve model versions, and predictions are logged with the model version and request ID. Each edge should carry versions, not just names, otherwise you can't reconstruct what actually happened.

Capture automatically, because manual documentation goes stale within weeks:

  • Data pipelines: the OpenLineage standard defines run, job and dataset events; integrations exist for Airflow, Spark, dbt, Flink and others, sending events to a backend such as Marquez or a catalog.
  • ML platforms: MLflow, SageMaker, Vertex AI and Azure ML record links between runs, input datasets, code versions and registered models. Logging dataset versions (Delta table versions, lakeFS commits, DVC hashes) with each run is essential.
  • Catalogs: Databricks Unity Catalog captures table and column lineage automatically for workloads on Databricks, including links to models; Microsoft Purview and DataHub (or OpenMetadata) aggregate lineage across tools and add ownership, glossary terms and classifications such as PII.

Value in two directions:

  • Downstream impact analysis: an upstream table changes schema or has a bad load; the graph shows which features, models and dashboards are affected and who to notify, before or right after the change.
  • Upstream investigation: for an audit or a strange prediction, trace back from prediction to model version to training run to dataset snapshot and code commit.

Lineage is also central evidence for regulation such as the EU AI Act and model risk management.

How it works

  1. Standardise on versioned datasets and immutable model versions.
  2. Enable OpenLineage integrations in orchestrators and Spark.
  3. Log dataset versions and git commit with every training run.
  4. Register models with links to runs; log model version with each prediction.
  5. Aggregate everything in one catalog with owners and classifications.
  6. Use lineage in change reviews and incident response.

Common mistakes

  • Lineage by names only, without versions.
  • Relying on wiki diagrams instead of automatic capture.
  • Gaps at tool boundaries (notebooks, ad-hoc scripts) that break the chain.
  • Not logging model version with predictions, so the last hop is missing.

How to answer in the interview

"Lineage tells me which source data, feature versions and code produced each model, and which model produced each prediction. I capture it automatically: pipelines emit OpenLineage events from Airflow, Spark or dbt, and the ML platform links runs, dataset versions, commits and registered models. A catalog like Unity Catalog, Purview or DataHub stores the graph with ownership and classifications. I use it for impact analysis, seeing which models are affected when an upstream table changes, and for tracing a bad prediction or an audit back to the exact data and code."

Likely follow-up questions

  • Hardest part to capture? Ad-hoc notebooks and custom scripts outside instrumented tools, plus column-level lineage through complex transformations.
  • Table-level or column-level lineage? Column-level is needed for PII tracking and precise impact analysis.
  • How do you enforce it? Platform templates that log lineage by default, and promotion gates requiring dataset versions.
