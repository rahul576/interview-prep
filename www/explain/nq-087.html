How can you wait for multiple concurrent tasks to complete?

Concurrency · scenario · levels mid

In one line

Wait for multiple tasks with Future.get()/invokeAll on an ExecutorService, CompletableFuture.allOf(...).join(), a CountDownLatch, or Thread.join(); on modern Java also try-with-resources executors and structured concurrency; always add timeouts and a failure policy.

Detailed explanation

From low to high level:

Thread.join() on each thread. Works, but you manage raw threads and get no results or exceptions back.

CountDownLatch: each task counts down, the coordinator awaits. Good when the events are not tasks you submitted yourself; results must be passed separately.

ExecutorService with Futures: submit Callables, keep the Futures, call get() on each. Or use invokeAll(tasks, timeout, unit), which waits until all complete (or the timeout expires, in which case unfinished tasks are cancelled) and returns the Futures. Exceptions come out as ExecutionException when you get().

CompletableFuture.allOf(f1, f2, f3) returns a future that completes when all complete; join() it and then read each f.join(). It composes well: allOf(...).thenApply(v -> combine(...)) without blocking. Add orTimeout or completeOnTimeout (Java 9+). Note allOf completes exceptionally if any fails, but only after all have finished; it does not fail fast by itself.

Try-with-resources executor (Java 19+): ExecutorService.close() waits for all submitted tasks, so the end of the try block is a natural join point. Combined with newVirtualThreadPerTaskExecutor() it is very readable.

Structured concurrency (StructuredTaskScope, a preview API since Java 21 whose exact shape has changed between releases) treats subtasks as a unit: fork them, join the scope, and get policies such as "fail fast and cancel the rest when one fails". Being preview, it needs --enable-preview.

Whatever the mechanism, decide on timeouts and failure semantics: should one failure cancel the others, or should you collect partial results?

How it works

  1. Start the tasks on an executor (platform pool or virtual threads).
  2. Keep handles: Futures, CompletableFutures or a latch.
  3. Wait for completion with a bounded timeout.
  4. On completion, read each result; on failure, cancel the rest if required.
  5. Propagate or aggregate errors and clean up the executor.

Example

ExecutorService pool = Executors.newFixedThreadPool(3);

CompletableFuture<User>    user    = CompletableFuture.supplyAsync(() -> users.get(id), pool);
CompletableFuture<List<Order>> orders = CompletableFuture.supplyAsync(() -> orderApi.list(id), pool);
CompletableFuture<Score>   score   = CompletableFuture.supplyAsync(() -> credit.score(id), pool);

Dashboard d = CompletableFuture.allOf(user, orders, score)
        .orTimeout(2, TimeUnit.SECONDS)
        .thenApply(v -> new Dashboard(user.join(), orders.join(), score.join()))
        .join();                                    // CompletionException on failure/timeout

// Alternative: invokeAll with a timeout
List<Future<Integer>> results = pool.invokeAll(jobs, 5, TimeUnit.SECONDS);
for (Future<Integer> f : results) {
    if (!f.isCancelled()) total += f.get();
}

Common mistakes

  • Calling get() with no timeout.
  • Assuming allOf cancels other tasks when one fails.
  • Running blocking calls in supplyAsync without a dedicated executor.
  • Ignoring partially completed results and leaked tasks after a timeout.

How to answer in the interview

"There are options at different levels. I can join each Thread, or use a CountDownLatch counted down by each task. More commonly I submit Callables to an ExecutorService and call get on each Future, or use invokeAll with a timeout. With CompletableFuture I use allOf(f1, f2, f3), then read each result, ideally composing with thenApply instead of blocking. On Java 19+ an executor in try-with-resources waits for its tasks on close, and Java 21's structured concurrency, still a preview, lets a group of subtasks succeed or fail together. In all cases I add timeouts, like orTimeout, and decide whether one failure should cancel the rest."

Likely follow-up questions

  • How would you fail fast if one of the tasks throws? Attach exceptionally/whenComplete to each future that cancels the others, or use a structured-concurrency scope with a fail-on-first-error policy.
  • What does invokeAny do? Returns the first successful result and cancels the remaining tasks.
  • Why does allOf return CompletableFuture<Void>? Because the inputs can have different types; you read each original future afterwards.
