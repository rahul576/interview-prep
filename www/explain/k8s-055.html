Some pods see random 5-second delays on outbound calls. You suspect DNS. How do you prove it and fix it?

Kubernetes · scenario · levels mid, senior, lead

In one line

A delay of almost exactly 5 seconds is the resolver timeout after a lost DNS packet; prove it by timing lookups and checking CoreDNS metrics, then fix the usual causes (ndots:5 search expansion and the conntrack race on parallel A/AAAA UDP queries) with NodeLocal DNSCache, resolver options, FQDNs and scaling CoreDNS.

Detailed explanation

glibc's resolver waits 5 seconds by default before retrying an unanswered query. When latency spikes cluster at about 5 s (or 10 s), packets are being dropped, not just answered slowly.

Two Kubernetes-specific factors cause most of it. First, ndots:5: pod resolv.conf lists search domains like ns.svc.cluster.local, svc.cluster.local, cluster.local, and any name with fewer than five dots is tried against each suffix first. A lookup of api.stripe.com can therefore produce several A and AAAA queries that return NXDOMAIN before the real one, multiplying load on CoreDNS and the chance of a drop.

Second, a long-known Linux conntrack race: glibc sends the A and AAAA queries in parallel from the same UDP socket. Both packets go through DNAT to the CoreDNS Service IP at the same moment; when they race to create conntrack entries, one packet can be dropped. The client then waits for the timeout. musl (Alpine) behaves differently but has its own quirks.

NodeLocal DNSCache runs a caching agent on each node, listening on a link-local IP; pods query it without DNAT, and it talks to CoreDNS over TCP, which removes the race and cuts latency. Other mitigations: options single-request-reopen (glibc), lowering ndots to 2 or so via dnsConfig, using fully qualified names with a trailing dot for external hosts, enabling CoreDNS caching and scaling CoreDNS (replicas or autoscaler) with anti-affinity.

How it works

  1. Reproduce from an affected pod: loop dig or getent hosts with timing.
  2. Check CoreDNS metrics: request rate, latency, errors, NXDOMAIN ratio.
  3. Briefly enable the CoreDNS log plugin to see the search expansion.
  4. Check node conntrack drop counters (conntrack -S insert_failed).
  5. Apply fixes: NodeLocal DNSCache, dnsConfig options, FQDNs, more CoreDNS replicas.
  6. Verify the 5-second tail disappears from p99 latency.

Example

kubectl exec -it deploy/orders -- sh -c 'for i in $(seq 50); do /usr/bin/time -f %e getent hosts api.stripe.com >/dev/null; done' 2>&1 | sort -n | tail -3
# 0.01  5.01  5.02   <- timeouts
spec:
  dnsConfig:
    options:
      - { name: ndots, value: "2" }
      - { name: single-request-reopen }

Common mistakes

  • Blaming the external API without checking DNS.
  • Only scaling CoreDNS when the drop is in conntrack on the client node.
  • Forgetting ndots when calling external domains in hot paths.
  • Rolling out NodeLocal DNSCache without a fallback.

How to answer in the interview

"Five seconds is the default resolver timeout, so it strongly suggests dropped DNS packets. I'd prove it by timing lookups in a loop from an affected pod and checking CoreDNS metrics and conntrack insert failures on the nodes. Two causes are typical: ndots:5, which expands every external name across all search domains and multiplies queries, and the conntrack race where glibc sends A and AAAA in parallel over one UDP socket and one is dropped. I'd deploy NodeLocal DNSCache, which avoids conntrack and caches locally, lower ndots or use trailing-dot FQDNs, add single-request-reopen and scale CoreDNS."

Likely follow-up questions

  • How to roll out NodeLocal DNSCache safely? Canary on a node pool, keep CoreDNS as upstream, monitor DNS latency and errors.
  • Why does the trailing dot help? It marks the name as fully qualified, skipping search domains.
  • Does it affect Alpine images? musl resolves differently; test both base images.
