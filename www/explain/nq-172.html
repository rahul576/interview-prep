What are the Bootstrap, Platform, and Application ClassLoaders?

JVM & Performance · concept · levels mid

In one line

Bootstrap loads java.base and core modules natively (seen as null), Platform loads the other JDK platform modules, and Application loads classpath and module-path code; the parent chain is Application → Platform → Bootstrap.

Detailed explanation

Since Java 9 the JDK is split into modules, and each module is mapped to one of the built-in loaders.

The Bootstrap class loader is part of the JVM itself and written in native code. It loads the most fundamental modules, above all java.base (java.lang, java.util, java.io, java.time, and so on) plus a few other boot modules such as java.logging. It has no Java representation, so Object.class.getClassLoader() returns null, and a null parent in the API means "delegate to bootstrap".

The Platform class loader, obtained with ClassLoader.getPlatformClassLoader(), loads the remaining Java SE and JDK modules, for example java.sql, java.xml.crypto or jdk.httpserver. Before Java 9 the equivalent was the Extension class loader, which read JARs from lib/ext; that directory is gone. Modules loaded here can be granted fewer privileges than boot modules.

The Application class loader, also called the System class loader and returned by ClassLoader.getSystemClassLoader(), loads your application classes and third-party JARs from the classpath and the module path, plus a few JDK tool modules. It is the default parent for custom loaders and the default thread context class loader.

Each loader delegates to its parent first. So when your code asks for java.sql.Connection, the Application loader asks Platform, which finds it; for java.lang.String, Platform asks Bootstrap.

How it works

  1. JVM boots; Bootstrap loads java.base.
  2. Platform loader is created; parent is Bootstrap (represented as null).
  3. Application loader is created; parent is Platform.
  4. The main class is loaded by the Application loader.
  5. Every lookup goes up the chain before searching locally.

Example

public class Loaders {
    public static void main(String[] args) {
        ClassLoader app = ClassLoader.getSystemClassLoader();
        System.out.println(app);                          // jdk.internal.loader.ClassLoaders$AppClassLoader
        System.out.println(app.getParent());              // ...$PlatformClassLoader
        System.out.println(app.getParent().getParent());  // null -> bootstrap
        System.out.println(java.sql.Connection.class.getClassLoader()); // platform
        System.out.println(Loaders.class.getClassLoader());             // app
    }
}
java --show-module-resolution -version   # shows which modules are resolved at startup

Common mistakes

  • Calling the Platform loader "Extension" for modern JDKs, or suggesting lib/ext still works.
  • Thinking a null loader means "not loaded".
  • Assuming classes from -cp can override JDK classes; delegation prevents it.
  • Casting getSystemClassLoader() to URLClassLoader, which fails since Java 9.

How to answer in the interview

"The Bootstrap loader is native code inside the JVM and loads java.base and other core modules, which is why String.class.getClassLoader() returns null. The Platform loader, which replaced the Extension loader in Java 9, loads the other Java SE and JDK modules like java.sql. The Application, or System, loader, from ClassLoader.getSystemClassLoader(), loads my code and libraries from the classpath and module path. The parent chain is Application to Platform to Bootstrap, and each delegates upwards before looking itself."

Likely follow-up questions

  • How do you print a class's loader? MyClass.class.getClassLoader(), and walk getParent() for the chain.
  • Why did casting the system loader to URLClassLoader break in Java 9? The AppClassLoader is now an internal class, not a URLClassLoader.
  • Where do JDBC drivers get loaded? From the classpath by the Application loader, discovered through ServiceLoader.
