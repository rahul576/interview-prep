How does DNS resolution work, and how would you troubleshoot a DNS issue?

Networking · concept · levels mid, senior

In one line

A recursive resolver answers from cache or walks root, TLD and authoritative servers, caching by TTL; troubleshoot with dig against different resolvers and the authoritative server, dig +trace, and by checking caching, TTLs and local resolver configuration (including CoreDNS in Kubernetes).

Detailed explanation

Resolution chain: the application calls the OS stub resolver, which checks local caches and /etc/hosts, then asks the configured recursive resolver (from /etc/resolv.conf, DHCP, a corporate resolver, cloud VPC resolver or a public one). On a cache miss, the resolver asks a root server, which refers it to the TLD servers for .com; those refer it to the domain's authoritative name servers (from the NS records at the registrar), which return the answer. Every response carries a TTL, and each layer caches it; negative answers (NXDOMAIN) are cached too, per the SOA record.

Record types: A (IPv4), AAAA (IPv6), CNAME (alias to another name), MX (mail servers with priority), TXT (verification, SPF, DKIM, DMARC), NS (delegation), SOA (zone metadata), SRV (service locations), CAA (which CAs may issue certificates), PTR (reverse lookups).

Troubleshooting approach:

  • Reproduce with dig name type from the affected host, then from elsewhere.
  • Compare resolvers: local, public (@1.1.1.1, @8.8.8.8) and the authoritative server directly (@ns1.provider.com). If authoritative is right but resolvers are wrong, it's caching: wait for the TTL or flush.
  • dig +trace follows delegation from the root, revealing wrong NS records or broken delegation.
  • Check status codes: NXDOMAIN (name doesn't exist), SERVFAIL (often DNSSEC validation or unreachable authoritative servers), REFUSED.
  • Check split-horizon DNS (private zones answering differently inside a VPC).
  • In Kubernetes, check CoreDNS pods and logs, the search domains and ndots:5 in the pod's resolv.conf (which causes several queries per lookup), and NetworkPolicies blocking port 53.

Migrations: lower the TTL (for example to 60 seconds) a day or more before changing records, then raise it again afterwards.

How it works

  1. App asks the stub resolver; local cache and hosts file are checked.
  2. Recursive resolver checks its cache.
  3. On a miss: root, TLD, authoritative.
  4. Answer is returned and cached for its TTL.
  5. Troubleshooting compares each layer's answer to isolate the faulty one.

Example

dig api.example.com A +noall +answer
dig @1.1.1.1 api.example.com
dig @ns-123.awsdns-45.com api.example.com     # ask the authoritative server
dig +trace api.example.com
kubectl exec -it app-pod -- cat /etc/resolv.conf
kubectl -n kube-system logs -l k8s-app=kube-dns --tail=50

Common mistakes

  • Changing a record with a 24-hour TTL and expecting instant effect.
  • Testing only from your laptop, which uses a different resolver.
  • Forgetting negative caching after creating a record that was queried before.
  • Ignoring ndots and search domains in Kubernetes.

How to answer in the interview

"The client asks a recursive resolver. If it isn't cached, the resolver asks a root server, then the TLD server for com, then the authoritative server, and caches the answer for its TTL. Main records are A, AAAA, CNAME, MX and TXT. To troubleshoot I use dig to query the record, compare answers from different resolvers and directly from the authoritative server, and use dig +trace to follow the delegation. Many issues are caching, so before migrations I lower the TTL in advance. In Kubernetes I also check CoreDNS and the search domains and ndots in resolv.conf."

Likely follow-up questions

  • Why no CNAME at the zone apex? The apex must hold SOA and NS records and a CNAME can't coexist with other records; providers offer ALIAS/ANAME or Route 53 alias records that resolve server-side.
  • What does SERVFAIL usually mean? DNSSEC validation failure or the resolver couldn't reach authoritative servers.
  • What is negative caching? Resolvers cache NXDOMAIN answers for the SOA-defined time.
