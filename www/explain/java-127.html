How does Spring AOP work, and what are its limitations?

Spring Boot · concept · levels mid, senior

In one line

Spring AOP modularises cross-cutting concerns with aspects made of advice (before, after, around) and pointcuts, implemented through runtime proxies (JDK dynamic proxies or CGLIB subclasses); so self-invocation, private and final methods and non-Spring objects are not intercepted, which needs AspectJ weaving.

Detailed explanation

Some concerns cut across many classes: transactions, security checks, logging, metrics, retries, caching. Copying that code into every method is error-prone. Aspect-oriented programming puts it in one aspect.

Vocabulary: a join point is a point in execution; in Spring AOP always a method execution on a bean. A pointcut is an expression selecting join points, for example execution(* com.shop.service..*(..)) or @annotation(com.shop.Timed). Advice is the code to run: @Before, @AfterReturning, @AfterThrowing, @After (finally) and @Around, which wraps the call and decides whether and how to proceed. Spring uses AspectJ's annotation style and pointcut language but not its weaver.

Spring creates a proxy for each bean matched by an aspect during the postProcessAfterInitialization phase. Spring Boot defaults to CGLIB class-based proxies (spring.aop.proxy-target-class=true), which subclass the bean; plain Spring uses a JDK dynamic proxy when the bean implements an interface. Callers get the proxy, which runs the advice chain and then calls the target. @Transactional, @Async, @Cacheable, @PreAuthorize and @Retryable all work this way.

Limitations follow from proxies:

  • Self-invocation: this.otherMethod() inside the bean bypasses the proxy, so its advice does not run.
  • private methods are never advised, and final methods or classes cannot be overridden by CGLIB.
  • Only Spring beans are advised, not objects created with new.
  • Only method execution join points, no field access or constructor advice.
  • A small per-call overhead.

For these cases use AspectJ compile-time or load-time weaving, or restructure: move the method to another bean.

How it works

  1. Declare an @Aspect bean with pointcuts and advice.
  2. At startup the auto-proxy creator checks every bean against the pointcuts.
  3. Matching beans are wrapped in a proxy.
  4. A call on the proxy runs the interceptor chain, then the target method.
  5. Calls the target makes internally go directly to itself.

Example

@Target(ElementType.METHOD) @Retention(RetentionPolicy.RUNTIME)
public @interface Timed {}

@Aspect
@Component
class TimingAspect {
    private final MeterRegistry registry;
    TimingAspect(MeterRegistry registry) { this.registry = registry; }

    @Around("@annotation(com.shop.Timed)")
    Object time(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.nanoTime();
        try {
            return pjp.proceed();
        } finally {
            registry.timer("method.time", "method", pjp.getSignature().toShortString())
                    .record(System.nanoTime() - start, TimeUnit.NANOSECONDS);
        }
    }
}

@Service
class ReportService {
    @Timed public Report build() { return load(); }   // timed when called from outside
    @Timed public Report load()  { ... }               // NOT timed when called via this.load()
}

Common mistakes

  • Expecting @Transactional to work on a method called from the same class.
  • Annotating private methods.
  • Forgetting to call proceed() in around advice, or swallowing exceptions.
  • Overly broad pointcuts that proxy half the application.

How to answer in the interview

"Spring AOP lets me put cross-cutting concerns like transactions, security, logging and metrics in one place. An aspect has advice, the code to run before, after or around a method, and a pointcut that selects which methods it applies to. Spring implements it with runtime proxies: CGLIB subclasses by default in Boot, or JDK dynamic proxies for interfaces. That's why @Transactional and @Cacheable work. The limitations come from the proxy: calls within the same class bypass it, private and final methods can't be advised, and only Spring beans are covered. For those cases you move the method to another bean or use full AspectJ weaving."

Likely follow-up questions

  • How would you write an around advice that measures execution time? As above: record time around pjp.proceed() in a finally block.
  • How do you fix self-invocation? Move the method to another bean, or inject the bean's own proxy (less clean).
  • Order of multiple aspects? Use @Order or implement Ordered.
