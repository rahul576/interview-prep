How do multi-architecture images work, and what pitfalls exist with ARM and x86?

Docker · concept · levels senior

In one line

A multi-architecture image is an OCI image index (manifest list) that maps one tag to per-platform images (for example linux/amd64 and linux/arm64); clients pull the matching one automatically. Build them with docker buildx --platform using QEMU emulation, cross-compilation or native builders, and watch for architecture-specific binaries, missing base variants and untested ARM paths.

Detailed explanation

ARM servers (AWS Graviton, Azure Cobalt, Google Axion, Ampere) and Apple Silicon laptops make arm64 common alongside amd64. A single tag like orders:1.9 should work on both. The registry stores an image index listing several manifests, each with a platform field. When a node pulls the tag, the runtime picks the manifest matching its own OS and architecture, so users never need to choose.

Building: docker buildx build --platform linux/amd64,linux/arm64 --push builds each variant and pushes the index. There are three ways to build the foreign architecture:

  • QEMU emulation (binfmt_misc): simplest, but CPU-heavy steps can be many times slower, often around 5-10x or worse.
  • Cross-compilation: Go, Rust and others can compile for the target from the native builder using the BUILDPLATFORM/TARGETARCH build args, which is fast.
  • Native builders: a buildx builder with an amd64 node and an arm64 node, each building its own platform.

Pitfalls: a Dockerfile that curls an amd64 binary produces an arm64 image that fails with exec format error. Some base images or third-party images have no arm64 variant. Native modules (Node, Python wheels) may need compiling and system headers. Performance and memory behaviour can differ. And tests on x86 do not prove ARM works, so test each architecture.

How it works

  1. Make the Dockerfile architecture-aware with ARG TARGETARCH.
  2. Create a buildx builder (multi-node or with QEMU).
  3. Build all platforms and push the index.
  4. Inspect with docker buildx imagetools inspect.
  5. Run tests on each architecture (ARM CI runners).

Example

# syntax=docker/dockerfile:1
FROM --platform=$BUILDPLATFORM golang:1.23 AS build
ARG TARGETOS TARGETARCH
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH go build -o /out/app ./cmd/app

FROM gcr.io/distroless/static-debian12
COPY --from=build /out/app /app
ENTRYPOINT ["/app"]
docker buildx build --platform linux/amd64,linux/arm64 -t registry.example.com/app:1.9 --push .
docker buildx imagetools inspect registry.example.com/app:1.9

Common mistakes

  • Hard-coding amd64 download URLs in RUN curl steps.
  • Building arm64 under QEMU for heavy compile steps and accepting 40-minute builds.
  • Assuming every base image is multi-arch.
  • Testing only on amd64.

How to answer in the interview

"A multi-arch image is an image index, or manifest list, that points to separate images for each platform, like linux/amd64 and linux/arm64, under one tag, and each node pulls the variant for its own architecture automatically. I build them with docker buildx build --platform, either with QEMU emulation, which is easy but slow, or better with cross-compilation using TARGETARCH, or native builders per architecture. The classic pitfall is downloading an architecture-specific binary in the Dockerfile, which gives exec format error on the other platform. Other pitfalls are base images without ARM variants and native dependencies, so I test on each architecture in CI."

Likely follow-up questions

  • What does exec format error mean? The binary is for a different CPU architecture (or a script lacks a valid shebang).
  • Why move to ARM? Often better price-performance and energy efficiency, for example on Graviton.
  • Can you run amd64 images on arm64? With emulation (QEMU, Rosetta on Macs), but slower and not recommended in production.
