Training crashes with a CUDA out of memory error. What are your options?

MLOps · scenario · levels mid, senior

In one line

GPU memory holds weights, gradients, optimiser state and activations; fix OOM by smaller batches with gradient accumulation, mixed precision (BF16/FP16), activation checkpointing, sharding with FSDP or DeepSpeed ZeRO, fixing memory leaks, and only then bigger or more GPUs.

Detailed explanation

Understanding where memory goes tells you which lever to pull. With the Adam optimiser in mixed precision, each parameter costs roughly 16 bytes (weights, gradients, FP32 master copy and two Adam moments), so a 7-billion-parameter model needs over 100 GB before activations. Activations scale with batch size and sequence length and often dominate for large inputs.

  • Batch size and gradient accumulation: halve the micro-batch and accumulate gradients over two steps; the effective batch size and learning dynamics stay the same.
  • Mixed precision: BF16 (preferred on Ampere and newer GPUs, no loss scaling needed) or FP16 with a gradient scaler roughly halves activation memory and speeds up tensor-core maths.
  • Activation (gradient) checkpointing: store only some activations and recompute the rest in the backward pass, trading about 20-30 percent extra compute for large memory savings.
  • Sharding: FSDP or DeepSpeed ZeRO stages 1-3 shard optimiser state, gradients and parameters across GPUs; ZeRO-Offload moves state to CPU memory. Tensor or pipeline parallelism split the model itself.
  • Memory-efficient optimisers (8-bit Adam, Adafactor) and, for fine-tuning, LoRA/QLoRA shrink optimiser state.
  • Bugs: accumulating loss tensors (with their graphs) in a list instead of loss.item(), keeping references to outputs, evaluating without torch.no_grad(), or fragmentation from varying shapes.

How it works

  1. Read the error: how much was requested and how much is reserved versus allocated.
  2. Measure peak memory for one step with a small batch.
  3. Check for leaks: memory growing every step indicates a bug.
  4. Apply BF16 and activation checkpointing.
  5. Reduce micro-batch and add accumulation.
  6. For large models, shard with FSDP/ZeRO or use parameter-efficient fine-tuning; then consider larger GPUs.

Example

model = torch.compile(model)
model.gradient_checkpointing_enable()          # Hugging Face models
accum = 4
for i, batch in enumerate(loader):
    with torch.autocast("cuda", dtype=torch.bfloat16):
        loss = model(**batch).loss / accum
    loss.backward()
    if (i + 1) % accum == 0:
        optimizer.step(); optimizer.zero_grad(set_to_none=True)
    running_loss += loss.item()               # .item(), not the tensor
print(torch.cuda.max_memory_allocated() / 2**30, "GiB peak")

Common mistakes

  • Reducing batch size without accumulation and silently changing training dynamics.
  • Storing loss tensors instead of Python floats.
  • Running validation without torch.no_grad() or inference_mode().
  • Jumping straight to bigger GPUs without profiling.

How to answer in the interview

"Memory is weights, gradients, optimiser state and activations, so I first see which dominates. The quick fix is a smaller micro-batch with gradient accumulation to keep the effective batch size. I'd enable BF16 mixed precision and activation checkpointing, which trades some compute for a lot of memory. For big models I'd shard parameters, gradients and optimiser state with FSDP or DeepSpeed ZeRO, or use LoRA for fine-tuning. I'd also check for leaks like storing loss tensors in a list. Only after that would I ask for bigger or more GPUs."

Likely follow-up questions

  • How do you measure peak memory to pick a batch size? torch.cuda.max_memory_allocated() or the memory snapshot tool after a few steps, increasing batch size until close to the limit with headroom.
  • BF16 versus FP16? BF16 has FP32's exponent range so no loss scaling; FP16 needs a gradient scaler.
  • What is ZeRO stage 3? Sharding parameters as well as gradients and optimiser states across all data-parallel ranks.
