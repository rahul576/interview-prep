How do you manage database-level objects such as roles, users and grants with Terraform, and what are the caveats?

Terraform · concept · levels mid, senior

In one line

Providers such as postgresql, mysql and mssql can manage roles, users, grants, schemas and extensions, but they need network access to the database, can leak credentials into state, and should live in a separate state from the server; table schemas and migrations belong to the application.

Detailed explanation

Managing database-level objects with Terraform is attractive: every service gets its own least-privilege role, consistently across environments, reviewed in pull requests, and removed when the service is retired. The community cyrilgdn/postgresql provider and similar providers for MySQL and SQL Server expose resources like postgresql_role, postgresql_grant and postgresql_extension.

The caveats are significant. First, network access: unlike cloud resource providers that talk to a public management API, these providers open a real database connection. For a private database this means running Terraform on self-hosted runners inside the network or through a bastion.

Second, secrets in state: a password set on a role is stored in the state file. Prefer identity-based authentication — Entra ID authentication for Azure Database for PostgreSQL or SQL, IAM database authentication on AWS RDS — so services hold no passwords, or use ephemeral values and write-only arguments where your Terraform and provider versions support them, and always protect the state backend.

Third, provider configuration ordering: if the same run creates the database server and configures the provider from its outputs, the provider receives unknown values during plan, and destroy ordering becomes fragile. A separate root module and state for database objects, applied after the server exists, is more reliable.

Finally, drift detection is weaker. Grants are often expanded into many underlying privileges, default privileges behave differently, and changes made by DBAs in SQL may not map cleanly back to resources. Table schemas and data migrations are versioned with the application using Flyway, Liquibase or the framework's migration tool.

How it works

  1. Root module A creates the server, networking and admin identity.
  2. Root module B, a separate state, configures the database provider using outputs or data sources.
  3. B creates per-service roles, schemas and grants, ideally mapped to Entra ID or IAM identities.
  4. B runs on a runner that can reach the private endpoint.
  5. The application pipeline runs migrations with Flyway or Liquibase using its own role.

Example

provider "postgresql" {
  host      = data.azurerm_postgresql_flexible_server.main.fqdn
  username  = var.admin_user
  password  = var.admin_token   # short-lived Entra token
  sslmode   = "require"
  superuser = false
}

resource "postgresql_role" "orders" {
  name  = "orders_app"
  login = true
}

resource "postgresql_grant" "orders_tables" {
  database    = "shop"
  schema      = "orders"
  role        = postgresql_role.orders.name
  object_type = "table"
  privileges  = ["SELECT", "INSERT", "UPDATE"]
}

Common mistakes

  • Creating the server and configuring the database provider in the same state.
  • Storing static passwords for every role in state without protecting the backend.
  • Managing table definitions in Terraform instead of migrations.
  • Running from cloud-hosted runners that cannot reach a private database.

How to answer in the interview

"Providers like postgresql or mssql let me manage roles, users, grants, schemas and extensions, which is great for giving each service a least-privilege role consistently and reviewing it in pull requests. The caveats: Terraform needs a real network connection, so private databases need private runners. Passwords end up in state, so I prefer Entra ID or IAM database authentication, or write-only arguments. I keep database objects in a separate state from the server, because configuring a provider from a resource created in the same run is fragile. And table schemas and migrations stay with the application, using Flyway or Liquibase."

Likely follow-up questions

  • Why do database providers struggle with drift? Grants expand into many privileges, default privileges and manual SQL changes do not map one-to-one to resources.
  • How do you give a pod database access without a password? Workload identity mapped to an Entra ID or IAM database role.
  • Who runs migrations? The application pipeline or an init job, with a migration role separate from the runtime role.
