One node keeps evicting pods because of DiskPressure. How do you investigate and fix it?

Kubernetes · scenario · levels mid, senior

In one line

DiskPressure means the kubelet saw nodefs or imagefs drop below its eviction threshold; find what fills the disk (usually container logs, emptyDir or writable-layer writes, or unused images) and fix it with log rotation, ephemeral-storage requests and limits, image GC tuning and right-sized disks.

Detailed explanation

The kubelet monitors two filesystems: nodefs (kubelet root dir, pod volumes such as emptyDir, and logs) and imagefs (container runtime images and writable layers; often the same disk). Default hard eviction thresholds include nodefs.available<10% and imagefs.available<15%. When crossed, the node gets the DiskPressure condition and a NoSchedule taint, and the kubelet first tries to reclaim space by garbage collecting dead containers and unused images. If that is not enough it evicts pods, ranked by whether they exceed their ephemeral-storage requests and by priority, then usage.

Typical culprits: an application writing huge amounts to stdout (for example debug logging in a tight loop), with kubelet log rotation (containerLogMaxSize, containerLogMaxFiles) left at defaults or a sidecar log shipper that falls behind; pods writing caches, uploads or temp files into emptyDir or the container's writable layer without limits; and many large images accumulating because image GC thresholds (imageGCHighThresholdPercent, imageGCLowThresholdPercent) are too loose or the disk is too small for the image churn.

The key fix is accountability: set ephemeral-storage requests and limits (and sizeLimit on emptyDir). Then the scheduler accounts for disk, and a pod exceeding its limit is evicted on its own rather than the kubelet evicting random neighbours. Also tune log rotation, reduce noisy logging, and size disks for genuine needs.

How it works

  1. kubectl describe node: DiskPressure condition and eviction events.
  2. On the node: df -h, du on /var/log/pods, /var/lib/kubelet/pods, /var/lib/containerd.
  3. crictl images and crictl stats to find big images and writable layers.
  4. Identify the offending pod or image.
  5. Set ephemeral-storage limits, emptyDir sizeLimit, log rotation and GC thresholds.
  6. Increase disk size if the workload legitimately needs it.

Example

sudo du -sh /var/log/pods/* | sort -h | tail -5
sudo du -sh /var/lib/kubelet/pods/*/volumes/kubernetes.io~empty-dir/* | sort -h | tail -5
sudo crictl images | sort -k4 -h | tail
resources:
  requests: { ephemeral-storage: 1Gi }
  limits: { ephemeral-storage: 4Gi }
volumes:
  - name: scratch
    emptyDir: { sizeLimit: 2Gi }

Common mistakes

  • Deleting files by hand and never fixing the source.
  • No ephemeral-storage limits, so innocent pods are evicted.
  • Debug logging left on in production.
  • Tiny root disks on nodes with large images.

How to answer in the interview

"DiskPressure means the kubelet saw nodefs or imagefs fall below its eviction threshold. On the node I check what's using space with du and crictl: usually container logs from a noisy app, pods writing heavily to emptyDir or their writable layer, or lots of unused images when garbage collection thresholds are loose. Fixes are kubelet log rotation, making the noisy app log less, ephemeral-storage requests and limits and emptyDir size limits so the kubelet evicts the offender rather than random pods, tuning image GC, and bigger disks if needed."

Likely follow-up questions

  • Why is ephemeral-storage forgotten? It is not set by default and disk is invisible until it runs out; most templates only cover CPU and memory.
  • Does memory-backed emptyDir count? medium: Memory counts against memory, not disk.
  • What is soft eviction? Thresholds with a grace period before evicting, configured in the kubelet.
