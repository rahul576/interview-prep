What is Domain-Driven Design, and which concepts do you apply in practice?

Architecture · concept · levels senior, lead

In one line

Domain-Driven Design aligns software with the business domain through a ubiquitous language, bounded contexts, aggregates that enforce invariants and define transaction boundaries, entities vs value objects, domain events, and anti-corruption layers at integration points.

Detailed explanation

DDD (Eric Evans, 2003) has two halves. Strategic design deals with large-scale structure: how to split a complex domain and how parts relate. Tactical design gives building blocks for modelling inside one part. In practice, the strategic half delivers most of the value, especially for microservice and modular boundaries.

Ubiquitous language: developers and domain experts use the same terms in conversations, documents and code. If the business says "policy is lapsed", the code has Policy.lapse(), not updateStatus(3). Techniques like event storming workshops build this shared language quickly.

Bounded contexts: a model is only consistent within a boundary. "Customer" in Billing (payment methods, invoices) differs from "Customer" in Shipping (addresses, delivery preferences). Each context owns its model and data and often maps to a service or module and a team. A context map describes relationships (customer/supplier, conformist, shared kernel).

Aggregates: a cluster of objects treated as one unit for changes, with a single aggregate root. The root enforces invariants (an order total cannot exceed the credit limit; no lines can be added after shipping). One transaction changes one aggregate; other aggregates are referenced by ID and updated via events (eventual consistency). Keep aggregates small.

Entities have identity that persists through changes (an Order). Value objects (Money, Address, DateRange) are immutable and compared by value, making code safer and more expressive; Java records are ideal.

Domain events (OrderPlaced) communicate changes within and across contexts. An anti-corruption layer translates external or legacy models so they do not leak into ours.

How it works

  1. Run event storming with domain experts to discover events, commands and terms.
  2. Group them into bounded contexts and draw a context map.
  3. Inside a context, identify aggregates and their invariants.
  4. Model value objects for concepts like money and quantities.
  5. Publish domain events for cross-aggregate and cross-context reactions.
  6. Wrap external systems behind anti-corruption layers.

Example

public record Money(BigDecimal amount, Currency currency) {
    public Money add(Money o) { requireSame(o); return new Money(amount.add(o.amount), currency); }
    private void requireSame(Money o) { if (!currency.equals(o.currency)) throw new IllegalArgumentException(); }
}

public class Order {                                   // aggregate root
    private final OrderId id; private final CustomerId customerId;   // other aggregate by ID
    private final List<OrderLine> lines = new ArrayList<>();
    private OrderStatus status = OrderStatus.DRAFT;
    private final List<DomainEvent> events = new ArrayList<>();

    public void addLine(ProductId p, int qty, Money price) {
        if (status != OrderStatus.DRAFT) throw new IllegalStateException("Order already placed");
        lines.add(new OrderLine(p, qty, price));
    }
    public void place() {
        if (lines.isEmpty()) throw new IllegalStateException("Empty order");
        status = OrderStatus.PLACED;
        events.add(new OrderPlaced(id, customerId, total()));
    }
    public Money total() { return lines.stream().map(OrderLine::subtotal).reduce(Money::add).orElseThrow(); }
}

Common mistakes

  • Applying tactical patterns everywhere while ignoring bounded contexts.
  • Huge aggregates that cause lock contention.
  • Anaemic domain models: entities as data bags, logic in services.
  • Sharing one "Customer" model across all contexts.
  • Updating several aggregates in one transaction by habit.

How to answer in the interview

"DDD focuses the model on the business domain. I always apply a ubiquitous language agreed with domain experts and used in code. Bounded contexts split the domain where a model stays consistent, like billing and shipping, and they often map to services and teams. Inside a context, aggregates group what must be consistent, enforce invariants and define the transaction boundary, like an Order with its lines; other aggregates are referenced by ID. Value objects such as Money are immutable records. Domain events connect contexts, and an anti-corruption layer protects us from external models."

Likely follow-up questions

  • How big should an aggregate be? As small as possible while protecting true invariants; reference others by ID.
  • When is DDD overkill? Simple CRUD apps with little business logic.
  • Bounded context vs microservice? A context is a model boundary; a service is a deployment unit; one context may contain several services.
