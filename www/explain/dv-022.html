What are Git tags, and how do you use them for releases and versioning?

Git · concept · levels mid, senior

In one line

A Git tag is a name that permanently marks a commit, typically a release like v2.3.1; use annotated (ideally signed) tags for releases, follow semantic versioning, push tags explicitly, let tag pushes trigger release pipelines, and never move a released tag.

Detailed explanation

Branches move as commits arrive; tags stay put, so they are the natural way to say "this exact commit is version 2.3.1".

A lightweight tag is just a pointer to a commit. An annotated tag (git tag -a) is a full object with tagger, date and message, and can be signed (git tag -s) so others can verify who created the release. Annotated tags are right for releases; git describe uses them by default.

Most teams use semantic versioning, MAJOR.MINOR.PATCH: major for breaking changes, minor for compatible features, patch for fixes, with pre-release labels like 2.4.0-rc.1.

Tags are not pushed by default: use git push origin v2.3.1 or --follow-tags. A tag push commonly triggers the release pipeline: build once, label the image with the version, publish, and create release notes. Changelogs can be generated from Conventional Commits (feat:, fix:) with semantic-release or release-please, which can also pick the next version.

A released tag must be immutable: consumers and audits rely on v2.3.1 always meaning the same code. If a release is broken, ship v2.3.2; protected tags enforce this.

How it works

  1. Merge the release changes to main.
  2. Create an annotated tag on the release commit.
  3. Push the tag explicitly.
  4. CI pipeline triggers on the tag pattern v*.
  5. It builds, tags the image 2.3.1, publishes and creates release notes.
  6. Fixes become new patch tags; existing tags are never changed.

Example

git switch main && git pull
git tag -a v2.3.1 -m "Release 2.3.1: fix VAT rounding"
git push origin v2.3.1
git tag -l "v2.*"
git describe --tags        # v2.3.1-4-g9f2e1ab (4 commits after the tag)
# GitHub Actions trigger
on:
  push:
    tags: ["v*.*.*"]

Common mistakes

  • Forgetting to push tags, so CI never runs and others cannot see them.
  • Deleting and recreating a tag on a different commit.
  • Using lightweight tags for official releases.
  • Version numbers that ignore semantic meaning (breaking change as a patch).
  • Rebuilding a different artifact for the same version.

How to answer in the interview

"A tag permanently marks a commit, usually a release like v2.3.1. I use annotated, ideally signed, tags because they record who, when and why. We follow semantic versioning: major for breaking changes, minor for features, patch for fixes. I push tags explicitly, and a v* tag triggers the release pipeline, which builds once, versions the image and publishes release notes from conventional commits. A released tag never moves; problems get a new patch version."

Likely follow-up questions

  • How do you generate changelogs automatically? Use Conventional Commits with semantic-release or release-please to group changes and bump versions.
  • Annotated vs lightweight? Annotated tags are objects with metadata and signatures; lightweight tags are plain pointers.
  • How do you tag a hotfix on an old version? Branch from the old tag, fix, and tag a new patch such as v2.2.5.
