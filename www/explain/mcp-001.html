Why does MCP use JSON-RPC 2.0, and what message types does it use?

MCP Servers · concept · levels entry, mid

In one line

MCP uses JSON-RPC 2.0 because it is a small, language-neutral, transport-independent message format; it has three message types: requests (with an id, expecting a response), responses (same id, with result or error) and notifications (no id, no response).

Detailed explanation

MCP needed a way for hosts and servers written in any language to call each other over very different transports: a local subprocess's stdin/stdout, or HTTP to a remote service. JSON-RPC 2.0 fits well. It is tiny (the whole spec is a few pages), human-readable, already supported by libraries in every language, and it says nothing about transport, so exactly the same messages flow over stdio or Streamable HTTP. It also supports bidirectional messaging, which earlier MCP revisions relied on for server-to-client requests such as sampling and elicitation. The Language Server Protocol used the same choice, so the pattern was proven.

Requests contain jsonrpc: "2.0", a method such as tools/list, tools/call or resources/read, optional params, and an id (string or number) that must be unique per sender for in-flight requests. Each request gets exactly one response.

Responses echo the id and contain either a result or an error object with an integer code, a message and optional data, never both.

Notifications have a method and params but no id, and the receiver must not reply. MCP uses them for progress updates, cancellation (notifications/cancelled), list changes (notifications/tools/list_changed) and, in handshake-based revisions, notifications/initialized.

JSON-RPC defines standard error codes that MCP reuses for protocol-level failures: -32700 parse error, -32600 invalid request, -32601 method not found, -32602 invalid params and -32603 internal error. Note that MCP removed support for JSON-RPC batching in the 2025-06-18 revision.

How it works

  1. Sender builds a request with a fresh id and sends it over the transport.
  2. Receiver dispatches by method and validates params.
  3. Receiver returns a response with the same id, containing result or error.
  4. Either side may send notifications at any time; no reply is expected.
  5. The sender matches responses to requests by id, allowing concurrent requests.

Example

{"jsonrpc":"2.0","id":7,"method":"tools/call",
 "params":{"name":"get_weather","arguments":{"city":"Pune"}}}

{"jsonrpc":"2.0","id":7,
 "result":{"content":[{"type":"text","text":"31°C, clear"}],"isError":false}}

{"jsonrpc":"2.0","id":8,
 "error":{"code":-32602,"message":"Unknown tool: get_wether"}}

{"jsonrpc":"2.0","method":"notifications/progress",
 "params":{"progressToken":"abc","progress":40,"total":100}}

Common mistakes

  • Replying to a notification, or sending a request without an id.
  • Returning both result and error in one response.
  • Reporting a failed business operation (e.g. "order not found") as a JSON-RPC error instead of a tool result with isError: true.
  • Reusing id values for concurrent requests.

How to answer in the interview

"MCP uses JSON-RPC 2.0 because it's a small, well-known format that's independent of transport, so the same messages work over stdio pipes or HTTP and there are libraries in every language. There are three message types. Requests have a method, params and an id, and expect exactly one response. Responses echo the id and carry either a result or an error with a code and message. Notifications have no id and get no reply; MCP uses them for progress, cancellation and list-changed events. Protocol failures use the standard codes like -32601 method not found and -32602 invalid params."

Likely follow-up questions

  • Why not report all tool failures as JSON-RPC errors? Execution errors returned as results with isError are shown to the model so it can self-correct; protocol errors usually are not.
  • Why not gRPC? It needs code generation, binary framing and HTTP/2, which complicates simple local subprocess servers.
  • Can requests be concurrent? Yes; ids let responses arrive in any order.
