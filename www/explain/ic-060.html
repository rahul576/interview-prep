Why are Terraform provisioners and null_resource considered a last resort?

Infrastructure as Code · concept · levels mid

In one line

Provisioners (local-exec, remote-exec) and null_resource/terraform_data run scripts Terraform cannot model: their effects are not in state, they are not idempotent, they don't re-run on drift and failures taint resources, so prefer cloud-init/user data, baked images, configuration management or a real provider.

Detailed explanation

Terraform's value comes from its model: every resource has attributes in state, the provider knows how to read, create, update and delete it, and the plan shows exactly what will change. A provisioner is a hole in that model. Terraform knows only that a script ran once at creation (or destruction, with when = destroy); it does not know what the script changed.

The consequences:

  • No drift detection. If someone undoes what the script did, the plan shows nothing.
  • No updates. Changing the script does not re-run it on existing resources.
  • Not idempotent. Re-running may fail or duplicate work.
  • Tainting. If a creation-time provisioner fails, the resource is marked tainted and the next apply destroys and recreates it, which for a database or a server with data is dangerous.
  • Fragile connectivity. remote-exec needs SSH or WinRM from the runner to the instance, bastions, keys and open ports.
  • Plan opacity. Reviewers cannot see the script's impact.

null_resource with triggers (and its built-in replacement terraform_data with triggers_replace, since Terraform 1.4) is commonly used to "run this command when X changes". It has the same problems, plus hidden coupling between unrelated resources.

Better options: user data / cloud-init for first-boot bootstrap, Packer images for software, Ansible or another configuration tool in a separate pipeline step, and a proper provider (there are providers for Kubernetes, Helm, databases, GitHub and most SaaS APIs). HashiCorp's own documentation calls provisioners a last resort.

How it works

  1. Terraform creates the resource through the provider.
  2. Provisioner runs; Terraform records only success or failure.
  3. On failure the resource is tainted (unless on_failure = continue).
  4. Next apply replaces a tainted resource.
  5. Later changes to the script are ignored unless a trigger forces replacement.

Example

# Avoid: configuration through remote-exec
resource "aws_instance" "web" {
  # ...
  provisioner "remote-exec" {
    inline = ["sudo apt-get install -y nginx"]
  }
}

# Prefer: bootstrap with cloud-init, software from the image
resource "aws_instance" "web" {
  ami       = data.aws_ami.web_golden.id
  user_data = file("${path.module}/cloud-init.yaml")
}

Common mistakes

  • Installing software with remote-exec on long-lived servers.
  • Using null_resource triggers as a general-purpose workflow engine.
  • Destroy-time provisioners that depend on resources already deleted.
  • Ignoring that a failed provisioner will recreate the resource next time.

How to answer in the interview

"Provisioners run scripts that Terraform can't model. It doesn't know what they changed, so there's no drift detection, changing the script doesn't re-run it, they're rarely idempotent, remote-exec needs network access to the box, and if one fails the resource is tainted and gets recreated on the next apply. null_resource, now terraform_data, with triggers has the same issues. I use cloud-init or user data for bootstrap, baked images for software, Ansible as a separate pipeline step, or a real provider for the API. I'd only accept local-exec for small, idempotent glue where no provider exists."

Likely follow-up questions

  • When is a local-exec provisioner still acceptable? Small idempotent glue with no provider, such as a one-time notification or registering a resource with an internal tool.
  • What replaced null_resource? The built-in terraform_data resource with triggers_replace and input/output.
  • What does on_failure = continue do? Ignores the failure so the resource is not tainted, at the risk of an unconfigured resource.
