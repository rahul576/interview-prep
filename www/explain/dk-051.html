How do Docker health checks and restart policies work together, and what are the limits?

Docker · concept · levels mid

In one line

In plain Docker, restart policies react only to process exit and an unhealthy container keeps running; Swarm and Kubernetes replace or restart unhealthy containers; on single hosts use an autoheal helper or make the app exit when broken, and keep checks cheap and local.

Detailed explanation

Docker has two independent mechanisms. A restart policy (no, on-failure[:N], always, unless-stopped) tells the daemon what to do when the container's main process exits. A health check periodically runs a command and sets the container's status to healthy or unhealthy. In standalone Docker these are not connected: an unhealthy container stays running and unhealthy indefinitely, and the restart policy never fires because the process is still alive. Many people discover this only when a deadlocked service sits "unhealthy" for hours.

Orchestrators do connect them. Docker Swarm treats an unhealthy task as failed and schedules a replacement, and uses health during rolling updates. Kubernetes ignores Docker health checks and uses its own probes: a failing liveness probe makes the kubelet restart the container, a failing readiness probe removes the pod from Service endpoints without restarting it, and a startup probe protects slow-booting apps.

On a single Docker host or with Compose, there are two common workarounds. A small autoheal container watches the Docker events API and restarts containers labelled for it when they turn unhealthy (it needs socket access, so it is privileged in practice). Alternatively, the application exits itself when an internal watchdog detects it is broken, letting restart: unless-stopped take over.

Health checks must be designed carefully. They should be cheap, have a timeout, and test the process itself (can it serve a request, is the event loop alive) rather than every downstream dependency. If the check calls the database and the database has a brief outage, every instance turns unhealthy and restarts simultaneously, adding a restart storm to the outage.

How it works

  1. Process exits → restart policy decides whether to restart.
  2. Health check fails N times → status unhealthy.
  3. Standalone Docker: no automatic action.
  4. Swarm: task replaced; Kubernetes: liveness restarts, readiness removes traffic.
  5. Autoheal or self-exit bridges the gap on single hosts.

Example

services:
  api:
    image: registry.local/api:1.4
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "/app/healthcheck"]   # local check, no DB call
      interval: 15s
      timeout: 2s
      retries: 3
    labels: ["autoheal=true"]
  autoheal:
    image: willfarrell/autoheal
    environment: [AUTOHEAL_CONTAINER_LABEL=autoheal]
    volumes: ["/var/run/docker.sock:/var/run/docker.sock"]
    restart: always

Common mistakes

  • Expecting restart: always to fix unhealthy containers.
  • Liveness checks that depend on databases or other services.
  • Using the same endpoint for liveness and readiness in Kubernetes.
  • Heavy health checks that consume real capacity.

How to answer in the interview

"In plain Docker they're independent: the restart policy only reacts when the main process exits, and an unhealthy container just keeps running and stays unhealthy. Swarm replaces unhealthy tasks, and Kubernetes uses liveness probes to restart containers and readiness probes to stop routing traffic. On a single host I'd use a small autoheal container or make the application exit itself when it detects it's broken, so the restart policy applies. Health checks should be cheap and check the app itself rather than every dependency, otherwise one database outage restarts everything."

Likely follow-up questions

  • Why can a DB-calling health check cause cascades? All instances fail together and restart simultaneously during a DB blip.
  • always vs unless-stopped? unless-stopped does not restart containers you stopped manually after a daemon restart.
  • Liveness vs readiness? Liveness restarts; readiness only removes traffic.
