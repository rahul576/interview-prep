What is a ReadWriteLock, and how does it differ from ReentrantLock?

Concurrency · concept · levels mid

In one line

A ReadWriteLock (e.g. ReentrantReadWriteLock) has a shared read lock that many threads can hold together and an exclusive write lock; a ReentrantLock is always exclusive, even for readers. It pays off for read-heavy data; StampedLock goes further with optimistic reads.

Detailed explanation

With an exclusive lock, two threads that only read still wait for each other, although reading cannot corrupt anything. A ReadWriteLock exposes two locks: readLock() and writeLock().

  • The read lock is shared: any number of threads can hold it at once as long as no thread holds the write lock.
  • The write lock is exclusive: it waits until all readers have released, and while held it blocks both readers and writers.
  • Both are reentrant. A writer can acquire the read lock (allowing downgrading: take read, release write), but a reader cannot upgrade to the write lock; trying blocks forever if other readers exist, including itself.
  • Memory semantics: releasing the write lock happens-before subsequent read-lock acquisitions.
  • Fairness is optional, as with ReentrantLock. In non-fair mode a constant stream of readers can starve writers (the implementation mitigates this by blocking new readers when a writer is queued first, but only heuristically).

When it helps: data read very often, written rarely, with read operations long enough that parallelism matters, for example an in-memory configuration, routing table or reference-data cache. When it does not: short critical sections or frequent writes, because the read lock's bookkeeping (atomic updates of reader counts) adds overhead and can make it slower than a plain ReentrantLock. Often a ConcurrentHashMap or an immutable snapshot in a volatile/AtomicReference (copy-on-write) is simpler and faster.

StampedLock (Java 8) adds optimistic reads: read without locking, then validate the stamp; fall back to a read lock only if a write happened. Very cheap for read-mostly cases, but not reentrant and without Conditions.

How it works

  1. Readers call rw.readLock().lock(); several proceed together.
  2. A writer calls rw.writeLock().lock() and waits until active readers release.
  3. While the writer holds the lock, new readers and writers wait.
  4. The writer updates the data and calls unlock() in finally.
  5. Waiting readers acquire the read lock together and see the new data.

Example

public class RateTable {
    private final ReadWriteLock rw = new ReentrantReadWriteLock();
    private final Map<String, BigDecimal> rates = new HashMap<>();

    public BigDecimal rate(String currency) {
        rw.readLock().lock();                // many concurrent readers
        try { return rates.get(currency); }
        finally { rw.readLock().unlock(); }
    }

    public void reload(Map<String, BigDecimal> fresh) {
        rw.writeLock().lock();               // exclusive
        try { rates.clear(); rates.putAll(fresh); }
        finally { rw.writeLock().unlock(); }
    }
}
// Often simpler: volatile Map<String, BigDecimal> rates = Map.copyOf(fresh);

Common mistakes

  • Trying to upgrade a read lock to a write lock and deadlocking.
  • Using a read lock while modifying data.
  • Using ReadWriteLock for tiny or write-heavy critical sections.
  • Forgetting writer starvation under constant read load.

How to answer in the interview

"A ReadWriteLock, like ReentrantReadWriteLock, holds a pair of locks: a read lock that many threads can hold at once as long as nobody holds the write lock, and an exclusive write lock that blocks all readers and writers. A ReentrantLock is always exclusive, so even two readers wait for each other. Read-write locks pay off for data that's read often and written rarely, like in-memory config or a cache, where readers can run in parallel. They have more overhead and can starve writers under heavy reading, and StampedLock adds optimistic reads for even cheaper read paths."

Likely follow-up questions

  • Can you upgrade a read lock to a write lock? No with ReentrantReadWriteLock (it deadlocks); you can downgrade from write to read, and StampedLock offers tryConvertToWriteLock.
  • What is a simpler alternative for read-mostly config? An immutable snapshot in a volatile field or AtomicReference, replaced on reload.
  • Does the read lock support Conditions? No; only the write lock supports newCondition.
