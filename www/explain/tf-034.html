Applies against Azure or AWS fail with throttling or rate-limit errors in a large configuration. What do you do?

Terraform · scenario · levels mid, senior

In one line

Large configurations exceed cloud API rate limits because of many parallel calls; short term, lower -parallelism and tune provider retries/backoff; long term, split state to reduce refresh calls, avoid huge list data sources, and stagger pipelines and drift checks.

Detailed explanation

Every plan refreshes every resource in state, each needing one or more API reads, and data sources add more. A configuration with 1,500 resources may make several thousand API calls per plan. With the default 10 parallel operations, multiplied by several pipelines running against the same account or subscription at the same time (scheduled drift checks often all start at 02:00), you can exceed rate limits. AWS throttles per API and account (for example EC2 Describe* calls or IAM), returning ThrottlingException or RequestLimitExceeded; Azure Resource Manager enforces read and write limits per subscription and principal, returning HTTP 429 with Retry-After. Providers retry automatically, but under sustained throttling they eventually give up and the run fails, possibly mid-apply.

Short-term mitigations:

  • Lower -parallelism, for example to 3-5, in the pipeline (TF_CLI_ARGS_plan="-parallelism=4"). Runs get slower but steadier.
  • Provider retry settings: the AWS provider supports max_retries and retry_mode (such as adaptive); AzureRM respects Retry-After and has built-in retries. More retries with backoff ride out short throttling bursts.

Long-term fixes reduce the number of calls:

  • Split large states by layer, team or region, so each run refreshes only a few hundred resources. This also reduces blast radius and plan time.
  • Avoid data sources that enumerate huge collections (all subnets, all instances) on every plan; pass IDs as outputs or variables.
  • Use -refresh=false only in carefully controlled cases, such as a second plan immediately after a refresh, since it hides drift.
  • Stagger schedules and use CI concurrency limits per account.
  • Ask for quota increases where the cloud allows it, and use separate accounts or subscriptions per environment to spread limits.

How it works

  1. Plan triggers refresh calls for every resource, in parallel.
  2. Cloud API returns throttling errors when limits are exceeded.
  3. Provider retries with backoff; persistent throttling fails the run.
  4. Lower parallelism and higher retries smooth the rate.
  5. Smaller states and fewer data source calls reduce total calls.

Example

provider "aws" {
  region      = "eu-west-1"
  max_retries = 15
  retry_mode  = "adaptive"
}
# GitHub Actions: one Terraform run per account at a time, lower parallelism
concurrency: { group: tf-prod-account, cancel-in-progress: false }
env:
  TF_CLI_ARGS_plan: "-parallelism=4"
  TF_CLI_ARGS_apply: "-parallelism=4"

Common mistakes

  • Increasing parallelism to make slow plans faster.
  • Using -refresh=false permanently.
  • All drift-detection jobs scheduled at the same minute.
  • One giant state for an entire organisation.

How to answer in the interview

"Cloud APIs limit request rates per account or subscription, and a big configuration refreshing hundreds of resources with ten parallel operations, times several pipelines at once, hits those limits and gets 429 or throttling errors. Short term, I lower -parallelism to three to five and configure provider retries, like max_retries and adaptive retry mode in the AWS provider, so calls back off. Long term, I reduce the number of calls: split the large state so each run refreshes less, avoid data sources that list huge collections, and use -refresh=false only in controlled cases. I also stagger scheduled drift runs and limit concurrent pipelines per account."

Likely follow-up questions

  • Why is -refresh=false risky permanently? Plans are based on stale state, hiding drift and possibly making wrong changes.
  • How do you find the noisiest calls? TF_LOG=DEBUG logs or CloudTrail/Activity Log by caller.
  • Does splitting state have downsides? More cross-state references and orchestration, so split along clear boundaries.
