Explain retry, timeout, fallback, and bulkhead patterns.

Microservices · concept · levels mid, senior

In one line

Timeout bounds how long you wait, retry repeats transient failures with backoff and jitter (idempotent calls only), fallback returns a degraded response, and bulkhead isolates resources per dependency; with a circuit breaker, they come from Resilience4j in Spring.

Detailed explanation

Remote calls fail in ways local calls do not: they hang, time out, return errors or become slow. These four patterns handle that.

Timeout. Never wait forever. Configure a connect timeout (establishing the connection, usually short, 1-2 s) and a read/response timeout (waiting for data) on every HTTP client, database pool and broker client. Set it from the dependency's normal latency (for example p99 × 2) and the caller's own time budget. Without timeouts, a slow dependency holds threads until the whole service stalls. Resilience4j's TimeLimiter adds timeouts around async calls.

Retry. Repeat a call that failed for a transient reason (connection reset, timeout, 503), with exponential backoff plus jitter and a small maximum (2-3 attempts). Only retry idempotent operations or use idempotency keys; otherwise you may create duplicate orders. Do not retry in every layer, or you amplify an outage.

Fallback. When a call fails, or the circuit is open, return something useful: cached data, a default ("recommendations unavailable"), a reduced feature, or a queued "we will process this later". Fallbacks must be cheap and reliable themselves, and they must be acceptable to the business; for payments, an honest error may be the only correct fallback.

Bulkhead. Limit concurrent calls per dependency with a semaphore or a dedicated thread pool, so one slow dependency can only exhaust its own share and the rest of the service keeps running.

Ordering. In Resilience4j's Spring Boot integration, the default aspect order is Retry ( CircuitBreaker ( RateLimiter ( TimeLimiter ( Bulkhead ( call ) ) ) ) ): retry is outermost, so every attempt passes through, and is counted by, the circuit breaker, and retries stop quickly once it opens. Spring Framework 7 also ships simple @Retryable and @ConcurrencyLimit annotations in the core for basic needs.

How it works

  1. Bulkhead grants a permit or rejects.
  2. Call runs with a timeout.
  3. Failure is recorded by the circuit breaker.
  4. Retry waits with backoff and tries again if allowed.
  5. After final failure or open circuit, fallback runs.

Example

@Retry(name = "catalog")
@CircuitBreaker(name = "catalog", fallbackMethod = "cachedProduct")
@Bulkhead(name = "catalog")
public Product product(String id) {
    return catalogClient.get(id);          // HTTP client has 1s connect / 2s read timeout
}

private Product cachedProduct(String id, Throwable t) {
    return productCache.getOrDefault(id, Product.unavailable(id));
}
resilience4j:
  retry.instances.catalog: { maxAttempts: 3, waitDuration: 200ms, enableExponentialBackoff: true, enableRandomizedWait: true }
  bulkhead.instances.catalog: { maxConcurrentCalls: 25 }
  circuitbreaker.instances.catalog: { failureRateThreshold: 50, slidingWindowSize: 20 }

Common mistakes

  • Default infinite or very long timeouts.
  • Retrying non-idempotent operations or 4xx errors.
  • Fallbacks that call another remote service.
  • Retrying outside a circuit breaker so retries hammer an open dependency.

How to answer in the interview

"These are resilience patterns for remote calls. A timeout bounds how long I wait, so a slow service cannot hold my threads; every call gets connect and read timeouts. A retry repeats transient failures with exponential backoff and jitter, a small maximum, and only for idempotent operations. A fallback returns a degraded response such as cached data or a default when the call fails. A bulkhead limits concurrent calls per dependency with a semaphore or thread pool, so one failing dependency cannot exhaust everything. In Spring I use Resilience4j for all of them together with the circuit breaker, with retry as the outermost layer."

Likely follow-up questions

  • Retry inside or outside the circuit breaker? Outside: each attempt is recorded by the breaker, and once it opens retries fail fast.
  • How do you choose a timeout value? From the dependency's observed p99 latency and the caller's remaining budget.
  • When is no fallback the right answer? When a wrong or stale answer is worse than an error, such as balances or payments.
