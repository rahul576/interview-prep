You must change a production database setting that Terraform says forces replacement. How do you handle it?

Infrastructure as Code · scenario · levels senior

In one line

Never apply a plan that replaces a production database: find why the attribute is immutable, keep prevent_destroy and deletion protection on, and either make the change in place through another path and align the code, or run a planned migration (snapshot/restore or replication, cut-over in a window), with verified backups first.

Detailed explanation

-/+ ... # forces replacement in a plan means the provider cannot update that attribute through the cloud API, so Terraform will destroy the old resource and create a new one. For a database it means downtime and data loss, because the new instance starts empty unless restored from a snapshot.

Understand the cause. Typical immutable settings on AWS RDS are storage_encrypted/kms_key_id, the identifier, the availability zone of a single-AZ instance, and some engine changes. Sometimes the replacement is accidental: a module refactor without moved blocks, a changed count index, or a provider upgrade that changed defaults. Those are fixed in code, not by migrating.

Guards. lifecycle { prevent_destroy = true } makes Terraform refuse any plan that would destroy the resource, and the cloud's deletion protection makes the API refuse as well. Note that prevent_destroy lives in the resource block, so it gives no protection if someone deletes the block entirely.

Options.

  1. Another attribute or API path. Many settings (instance class, storage size, parameter group, Multi-AZ) are in-place modifications, sometimes with apply_immediately = false to wait for the maintenance window.
  2. Migration. Create a new database alongside: restore from a snapshot (for example copying the snapshot with encryption enabled), or use replication or AWS DMS for minimal downtime. Freeze writes, take a final sync, switch the application's endpoint, verify, then retire the old one.
  3. Terraform alignment. Import the new database or point the resource at it, use removed with destroy = false for the old one, and finish with a clean plan.

How it works

  1. Read the plan and identify the attribute marked "forces replacement".
  2. Check for accidental causes (addresses, provider defaults).
  3. Verify a recent snapshot restores successfully.
  4. Choose in-place path or migration; agree a window and rollback plan.
  5. Execute the migration; update Terraform to manage the new database.

Example

resource "aws_db_instance" "orders" {
  identifier          = "orders-prod"
  storage_encrypted   = true
  deletion_protection = true
  apply_immediately   = false
  lifecycle {
    prevent_destroy = true
  }
}
aws rds create-db-snapshot --db-instance-identifier orders-prod --db-snapshot-identifier orders-pre-enc
aws rds copy-db-snapshot --source-db-snapshot-identifier orders-pre-enc \
  --target-db-snapshot-identifier orders-enc --kms-key-id alias/rds-prod

Common mistakes

  • Approving a plan without reading the replace markers.
  • Removing prevent_destroy "just for this apply".
  • Migrating without testing the restore and the application cut-over.

How to answer in the interview

"First I find out why. Some attributes, like encryption, the identifier or certain engine changes, can't be changed in place, so the provider would destroy and recreate the database, which means data loss. I check it's not accidental, like a refactor without moved blocks. prevent_destroy and deletion protection should already make the apply fail, which is the point. Then either the change can be made in place another way and I align the code, or I plan a migration: create the new database from a snapshot or with replication, cut over in a maintenance window, and update Terraform to manage the new one. Backups are verified before anything."

Likely follow-up questions

  • How would you enable encryption on an unencrypted RDS instance? Snapshot, copy the snapshot with a KMS key, restore, cut over; DMS for minimal downtime.
  • Does prevent_destroy stop a removed resource block? No; the protection disappears with the block, so cloud deletion protection matters.
  • Why apply_immediately = false? It defers disruptive modifications to the maintenance window.
