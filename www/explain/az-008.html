How do App Service deployment slots work, and how do you do zero-downtime releases with them?

Azure · concept · levels mid

In one line

Deployment slots are live copies of an App Service app with their own hostname on the same plan; you deploy to staging, warm it up, then swap with production for zero downtime, keep sticky slot settings per slot, and roll back by swapping again.

Detailed explanation

Slots are available on Standard, Premium and Isolated App Service tiers (and Functions on suitable plans). Each slot is a full app with its own hostname, such as orders-api-staging.azurewebsites.net, configuration and deployment, but it shares the App Service plan's compute, so a busy staging slot affects production capacity.

The swap is what makes releases zero-downtime. When you swap staging into production, Azure first applies production's slot-specific settings to the staging instances, restarts them, and warms them up by sending requests to the root path or a custom path (configurable with applicationInitialization or WEBSITE_SWAP_WARMUP_PING_PATH). Only when all instances respond does it switch routing, so production users never hit cold instances. Requests in flight are not dropped.

Sticky (slot) settings stay with the slot instead of moving with the code. Typical sticky settings are connection strings to environment-specific resources, feature flags for testing in staging, and monitoring keys if you separate telemetry. Non-sticky settings travel with the app version.

Swap with preview (multi-phase swap) pauses after applying production settings so you can validate staging with production configuration before completing. Auto swap can swap automatically after each deployment to a slot. Traffic routing can send a percentage of production traffic to a slot for testing in production. Rollback is simply swapping again, because the previous version is now in the staging slot.

How it works

  1. Deploy the new build to the staging slot.
  2. Run smoke tests against the staging hostname.
  3. Start the swap; production settings are applied to staging instances.
  4. Instances restart and are warmed up via the warm-up path.
  5. Routing switches; old version now sits in staging.
  6. If problems appear, swap back immediately.

Example

az webapp deployment slot create -g rg-orders -n orders-api --slot staging
az webapp deploy -g rg-orders -n orders-api --slot staging --src-path app.zip
curl -f https://orders-api-staging.azurewebsites.net/health
az webapp deployment slot swap -g rg-orders -n orders-api \
  --slot staging --target-slot production
# Rollback: run the same swap command again
az webapp config appsettings set -g rg-orders -n orders-api --slot staging \
  --slot-settings FEATURE_TEST_MODE=true

Common mistakes

  • Making database connection strings non-sticky so staging writes to production.
  • Not configuring a warm-up path, so apps with slow startup still cause latency.
  • Forgetting that slots share plan capacity.
  • Database schema changes that are not backward compatible, so swap-back breaks.
  • Using slots as long-lived test environments with heavy load.

How to answer in the interview

"Deployment slots are live apps with their own hostname that share the App Service plan. I deploy the new version to a staging slot, run smoke tests, then swap it with production. During the swap Azure applies production settings to the staging instances and warms them up, and switches routing only when they respond, so there is no downtime and no cold start. Settings marked as slot settings stay with the slot, so staging can keep pointing at staging resources. Rollback is just swapping back. I can also use swap with preview to validate with production config, or route a percentage of traffic to a slot for testing."

Likely follow-up questions

  • Which settings should be sticky, and why? Environment-specific connection strings and test flags, so they do not follow the code into production.
  • How do you handle database migrations with slots? Use backward-compatible, expand-and-contract migrations.
  • What happens to sessions during a swap? In-memory sessions are lost on restart; use a distributed session store.
