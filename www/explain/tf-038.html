You need to move part of a large Terraform configuration into a separate state owned by another team without recreating anything. How do you do it?

Terraform · scenario · levels senior, lead

In one line

Split state by planning the cut and the new interfaces, then use import blocks in the new configuration and removed blocks with destroy = false in the old one, requiring both plans to show no creates or destroys, under a short change freeze with state backups.

Detailed explanation

Moving resources between states is a pure bookkeeping operation: the real cloud objects must not change. The risk is that one side thinks a resource is new (create) or gone (destroy). Since Terraform 1.5 import blocks and since 1.7 removed blocks let you do this declaratively, reviewed in a pull request and visible in plans, instead of running terraform state rm and terraform import by hand.

The design part matters as much as the commands. Resources that move often had direct references from resources that stay, such as a subnet ID used by a VM. After the split those references cross a state boundary, so you need an interface: outputs consumed via terraform_remote_state, or better, data sources or published values in a parameter store. Decide this first, because it determines what code changes on both sides.

Ordering is important. Import into the new state first, so the resources are always managed by at least one state. Then apply the old configuration with removed blocks so it forgets them. Two states briefly managing the same object is acceptable for minutes during a freeze, never longer. Applying the old side first leaves a window where nothing manages the resources, and a mistake there (removed block without destroy = false) would destroy them.

How it works

  1. List the resources that move and their cloud IDs; define the new cross-state interfaces.
  2. Announce a change freeze; back up both states (terraform state pull > backup.tfstate).
  3. In the new configuration, write matching code plus import blocks.
  4. In the old configuration, delete that code and add removed blocks with destroy = false; replace references with data sources.
  5. Plan both: new shows only imports; old shows only "will no longer be managed".
  6. Apply new first, then old; re-plan both and confirm they are clean.

Example

# new-team/network.tf
import {
  to = azurerm_subnet.app
  id = "/subscriptions/.../resourceGroups/rg-net/providers/Microsoft.Network/virtualNetworks/vnet-prod/subnets/snet-app"
}
resource "azurerm_subnet" "app" { /* matching configuration */ }

# old-config/main.tf
removed {
  from = azurerm_subnet.app
  lifecycle { destroy = false }
}
data "azurerm_subnet" "app" {
  name                 = "snet-app"
  virtual_network_name = "vnet-prod"
  resource_group_name  = "rg-net"
}

Common mistakes

  • Forgetting destroy = false, which makes the removed block destroy the resources.
  • Applying the old state first, leaving resources unmanaged or destroyed.
  • Accepting a plan with "update in-place" in the new state; the code does not match reality yet.
  • Skipping backups before touching state.

How to answer in the interview

"I start with design: which resources move and how the two states will share values afterwards, usually data sources instead of direct references. I freeze changes and back up both states. In the new configuration I add the code and import blocks with the cloud IDs; in the old one I delete the code and add removed blocks with destroy set to false. Both plans must show zero creates and destroys: imports on one side, no longer managed on the other. I apply the new state first, then the old, and confirm both plans are clean."

Likely follow-up questions

  • What if the old state is applied first? Resources become unmanaged, or destroyed if destroy = false is missing.
  • Can moved blocks do this? No, moved works only within one state.
  • How do you import many resources? Import blocks support for_each since Terraform 1.7.
