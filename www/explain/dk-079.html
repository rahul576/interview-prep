How do you speed up container startup at scale, for example during autoscaling?

Docker · design · levels lead

In one line

Container startup at scale is dominated by image pull time and application start time: shrink images and share base layers, pre-pull or bake images into node images, keep the registry in-region, use lazy pulling (eStargz, AWS SOCI, GKE image streaming) for large images, and speed up the app itself (CDS/AppCDS, CRaC, GraalVM native image).

Detailed explanation

When the autoscaler adds a node or pod, the critical path is: node provisioning, image pull and unpack, container creation, application startup, and readiness. For many workloads, pull plus unpack takes most of the time: a 1.5 GB image on a fresh node can take a minute. Then a heavy JVM application may need another 30 seconds to warm up.

Pull side:

  • Small images with multi-stage builds and slim bases.
  • Shared base layers across services so nodes already hold most data.
  • Pre-pulling: bake common images into the node image (AMI) or use a DaemonSet that pulls them, so new nodes start "warm".
  • Registry in the same region, with replication, and enough parallel layer downloads (kubelet serializeImagePulls: false with maxParallelImagePulls).
  • Lazy pulling: normally a container cannot start until the whole image is downloaded and unpacked. eStargz with the stargz snapshotter, AWS SOCI (Seekable OCI) and GKE image streaming let it start immediately, fetching files on demand. Research shows containers often read only a small fraction of their image at startup.

Application side: for the JVM, Class Data Sharing (AppCDS), CRaC checkpoint/restore, Spring AOT or GraalVM native images reduce startup from tens of seconds to well under one second in the native case. Tune readiness probes so pods receive traffic as soon as they are really ready, and avoid slow init containers.

How it works

  1. Measure: node ready time, pull time (kubelet events "Pulling"/"Pulled"), container start, readiness.
  2. Reduce image size; standardise bases.
  3. Pre-pull hot images or bake them into node images.
  4. Enable lazy pulling for large images.
  5. Optimise application startup and probes; keep spare capacity (overprovisioning pods) for spikes.

Example

kubectl get events --field-selector reason=Pulled -o custom-columns=MSG:.message
# Successfully pulled image "...orders:1.9" in 41.2s (41.2s including waiting). Image size: 1.3 GB

java -XX:ArchiveClassesAtExit=app.jsa -jar app.jar   # training run creates CDS archive
java -XX:SharedArchiveFile=app.jsa -jar app.jar      # later starts load classes faster

Common mistakes

  • Optimising code while the real delay is a 2 GB image pull.
  • Every service on a different base image, so nothing is cached on nodes.
  • Readiness probes with long initial delays "to be safe".
  • Relying only on autoscaling with no spare buffer for sudden spikes.

How to answer in the interview

"First I'd measure where the time goes, because during scale-out it's usually image pulls and application start. On the image side, I keep images small and built on shared base layers, pre-pull common images through the node image or a DaemonSet, and keep the registry in the same region. For big images, lazy-pulling formats like eStargz, AWS SOCI or GKE image streaming let containers start before the full image is downloaded. On the application side, JVM class data sharing, CRaC or GraalVM native images cut startup dramatically. I'd also tune readiness probes and keep a little overprovisioned capacity for sudden spikes."

Likely follow-up questions

  • How do you measure startup time? Kubelet events for pull duration, pod condition timestamps, and app startup logs or metrics.
  • Trade-off of native images? Very fast start and low memory, but longer builds, reflection configuration and sometimes lower peak throughput.
  • What is overprovisioning? Low-priority placeholder pods that get evicted so real pods schedule instantly while a new node boots.
