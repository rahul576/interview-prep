Design an online coding judge like LeetCode that runs untrusted user code.

Classic Design Problems · design · levels mid, senior

In one line

An online judge queues submissions, runs them in strong sandboxes (gVisor, Firecracker, hardened containers) with strict CPU, memory, time and no-network limits, compares outputs against hidden test cases, returns verdicts asynchronously, and autoscales workers for contests.

Detailed explanation

The defining challenge is running untrusted code safely. Users will try fork bombs, infinite loops, reading /etc/passwd, mining crypto, or attacking the network. Plain Docker shares the host kernel, so a kernel exploit escapes it; stronger isolation uses gVisor (user-space kernel) or Firecracker microVMs (lightweight VMs, used by AWS Lambda). Add seccomp profiles, a read-only filesystem, no network, cgroup limits on CPU time, memory, processes and output size.

Execution is asynchronous: POST /submissions stores the code and enqueues a job, returning an ID immediately. Workers compile, run against each test case, compare output (exact or with a checker for floating-point/multiple answers) and record the verdict: AC, WA, TLE, MLE, RE, CE.

Contests cause 10x spikes in minutes. The queue absorbs bursts; workers autoscale on queue depth, with pre-warmed sandboxes per language to avoid cold start. Test data lives in storage accessible only to workers.

How it works

  1. API validates, stores submission, enqueues {submissionId, problemId, language}.
  2. Worker pulls job, creates sandbox, compiles (with its own time limit).
  3. For each test: run with limits, capture stdout, compare.
  4. Write verdict + runtime + memory; notify client via WebSocket/polling.
  5. Destroy sandbox.

Example

# conceptual limits for one run
timeout 2s prlimit --as=268435456 --nproc=64 --fsize=10485760 \
  runsc --network=none run sandbox-123

Common mistakes

  • Running code in containers with network access or host mounts.
  • Measuring wall time only (CPU time is fairer).
  • Synchronous HTTP request waiting for execution.
  • Exposing test cases in error messages.

How to answer in the interview

"Submissions go on a queue and the API returns an ID. Workers execute code in strongly isolated sandboxes like gVisor or Firecracker, with no network, read-only filesystem and strict CPU, memory, process and output limits. Each hidden test's output is compared and a verdict stored, and the client gets it by polling or WebSocket. Workers autoscale on queue depth with pre-warmed sandboxes for contests."

Likely follow-up questions

  • Prevent test leakage? Only workers can read tests; don't echo expected output; rate-limit submissions.
  • Fair timing across machines? Same instance types, CPU time limits, multiple runs for borderline cases.
  • Plagiarism? Code similarity checks (MOSS-like) after contests.
