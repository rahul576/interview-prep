What are ReentrantLock, ReadWriteLock, and StampedLock?

Concurrency · concept · levels senior, lead

In one line

ReentrantLock is an explicit, reentrant mutual-exclusion lock with tryLock, timeouts, interruptible locking, fairness and Conditions; ReadWriteLock allows many readers or one writer; StampedLock adds optimistic reads validated with a stamp, but is not reentrant.

Detailed explanation

ReentrantLock has the same core semantics as synchronized: mutual exclusion, memory visibility and reentrancy (the owning thread can lock again; it must unlock the same number of times). It adds control: tryLock() and tryLock(timeout) to avoid waiting forever, lockInterruptibly() so cancellation works while waiting, an optional fair mode where the longest waiter goes next, multiple Condition objects (newCondition()), and inspection methods such as isLocked and getQueueLength. The price: you must unlock() in a finally block.

ReadWriteLock, implemented by ReentrantReadWriteLock, manages two locks. The read lock is shared: many threads can hold it while no writer holds the write lock. The write lock is exclusive. This helps read-heavy data with fairly expensive reads, like configuration or reference-data caches. You can downgrade (acquire read while holding write, then release write) but not upgrade read to write, which would deadlock. Under write-heavy or very short critical sections, its extra bookkeeping can make it slower than a plain lock, and non-fair mode can starve writers.

StampedLock (Java 8) offers write, read and optimistic read modes. tryOptimisticRead() returns a stamp without locking; you read fields into locals, then call validate(stamp). If no write happened, you are done with zero locking cost; otherwise fall back to a real read lock. It scales very well for read-mostly data, but it is not reentrant, has no Conditions, and optimistic reads may see inconsistent values, so you must only work on local copies until validation succeeds.

How it works

  1. ReentrantLock: lock() in try, work, unlock() in finally; hold count tracks reentry.
  2. ReentrantReadWriteLock: readers call readLock().lock(), writers writeLock().lock().
  3. A writer waits until all readers release; new readers wait while a writer holds or (in fair mode) waits.
  4. StampedLock: long s = tryOptimisticRead(), read into locals, validate(s).
  5. If validation fails, readLock(), re-read, unlockRead(stamp).

Example

class Point {
    private final StampedLock sl = new StampedLock();
    private double x, y;

    void move(double dx, double dy) {
        long stamp = sl.writeLock();
        try { x += dx; y += dy; } finally { sl.unlockWrite(stamp); }
    }

    double distanceFromOrigin() {
        long stamp = sl.tryOptimisticRead();
        double cx = x, cy = y;                  // copy to locals
        if (!sl.validate(stamp)) {              // a write happened, retry with a lock
            stamp = sl.readLock();
            try { cx = x; cy = y; } finally { sl.unlockRead(stamp); }
        }
        return Math.hypot(cx, cy);
    }
}

ReentrantLock lock = new ReentrantLock();
if (lock.tryLock(200, TimeUnit.MILLISECONDS)) {
    try { /* critical section */ } finally { lock.unlock(); }
}

Common mistakes

  • Forgetting unlock() in finally.
  • Trying to upgrade a read lock to a write lock and deadlocking.
  • Re-entering a StampedLock from the same thread.
  • Using values from an optimistic read before validate().
  • Choosing ReadWriteLock for tiny critical sections where it adds overhead.

How to answer in the interview

"ReentrantLock is an explicit lock with the same semantics as synchronized, including reentrancy, plus extras: tryLock with a timeout, interruptible locking, a fairness option and multiple Conditions. I always unlock in finally. ReadWriteLock, implemented by ReentrantReadWriteLock, allows many readers at once but only one writer, which helps read-heavy data like config caches. StampedLock adds optimistic reads: I read without locking, validate the stamp, and fall back to a real read lock only if a write happened. It's faster under read contention but not reentrant and easier to misuse."

Likely follow-up questions

  • Why can a ReadWriteLock be slower than a plain lock in practice? It tracks reader counts with more expensive atomic operations, so for short critical sections or frequent writes the overhead outweighs the parallelism.
  • Can you upgrade a read lock? Not with ReentrantReadWriteLock; StampedLock offers tryConvertToWriteLock.
  • What does fairness cost? Lower throughput, because threads cannot barge and more context switches occur.
