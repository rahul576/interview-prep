How does autoscaling work in Kubernetes at the pod and node level?

Kubernetes · concept · levels senior, lead

In one line

At pod level the HPA scales replica count on CPU/memory (relative to requests) or custom/external metrics, KEDA scales on event sources (even to zero), and the VPA adjusts requests; at node level the Cluster Autoscaler or Karpenter adds nodes for pending pods and removes underused ones; all depend on correct requests and need PodDisruptionBudgets.

Detailed explanation

Horizontal Pod Autoscaler (HPA). A controller that periodically reads metrics and computes desired = ceil(current × currentMetric / target). Resource metrics (CPU, memory utilisation as a percentage of requests) come from metrics-server; custom metrics (requests per second per pod) and external metrics (queue length) come from adapters such as Prometheus Adapter.

KEDA builds on the HPA with dozens of scalers: Kafka consumer lag, SQS or Service Bus queue depth, Prometheus queries, cron schedules. It can scale deployments to zero and back, which is ideal for event-driven workers.

Vertical Pod Autoscaler (VPA). Recommends or applies better requests and limits based on observed usage. In update modes it recreates pods (newer versions can resize in place where the cluster supports it). Do not let VPA and HPA act on the same CPU/memory metric; a common combination is HPA on a custom metric with VPA on resources, or VPA in recommendation-only mode.

Node autoscaling. The Cluster Autoscaler watches for pods that are Pending because no node fits, simulates which node group could fit them, increases that group's size, and removes nodes whose pods can be moved elsewhere. Karpenter (AWS, and the basis of AKS node auto-provisioning) skips predefined groups: it looks at pending pods' requirements and launches right-sized instances directly, and consolidates by replacing underused nodes with cheaper ones.

Autoscaling only works with accurate requests, sensible readiness probes, and PodDisruptionBudgets so scale-down and consolidation do not take too many replicas at once.

How it works

  1. Load rises; HPA metric exceeds target; replicas increase.
  2. New pods are Pending: no node has room for their requests.
  3. Cluster Autoscaler/Karpenter launches nodes; pods schedule.
  4. Load falls; HPA scales down after its stabilisation window.
  5. Underused nodes are drained (respecting PDBs) and removed.

Example

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: api }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: api }
  minReplicas: 3
  maxReplicas: 30
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 65 } }
  behavior:
    scaleDown: { stabilizationWindowSeconds: 300 }

Common mistakes

  • No requests set, so HPA utilisation and node autoscaling misbehave.
  • HPA and VPA both driven by CPU.
  • No PDBs, so consolidation evicts all replicas at once.
  • Scaling on CPU for I/O-bound or queue-driven workloads.

How to answer in the interview

"At pod level the HPA changes the replica count based on metrics: CPU or memory utilisation relative to requests from metrics-server, or custom metrics like requests per second through an adapter. KEDA scales on event sources such as Kafka lag or queue depth, even to zero. The VPA adjusts requests and limits and shouldn't act on the same metric as the HPA. At node level the Cluster Autoscaler adds nodes when pods are pending and removes underused ones, while Karpenter provisions right-sized nodes directly and consolidates. It all depends on correct requests, and PodDisruptionBudgets keep scale-down from hurting availability."

Likely follow-up questions

  • Pods pending but no new nodes? Node group at max size, no group or instance type fits the requests, selectors or taints don't match, zone-bound volumes, or cloud quota limits; check autoscaler logs and pod events.
  • Why do scale-ups feel slow? Node launch and image pull time; use over-provisioning placeholder pods or smaller images.
  • Scale to zero with HPA? Not by default; KEDA handles it.
