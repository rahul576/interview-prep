What is the difference between synchronized and unsynchronized resources?

Concurrency · concept · levels entry

In one line

A synchronized resource lets only one thread at a time into its critical operations (for example Vector, Hashtable, StringBuffer), which is safe but slower; an unsynchronized resource (ArrayList, HashMap, StringBuilder) allows concurrent access, which is faster but unsafe for shared mutation.

Detailed explanation

"Synchronized" here means the class guards its own methods with a lock. Each call to Vector.add or Hashtable.put acquires the object's monitor, so individual operations do not corrupt the internal state and their effects are visible to other threads. The price is locking overhead and contention: with many threads, they queue on one lock, so throughput can be worse than single-threaded code. Even single-threaded code pays a (small, often optimised) cost.

Unsynchronized classes have no internal locking. They are faster and are the right default for data used by one thread, such as a local list inside a method or a request-scoped builder. But if several threads modify them concurrently, you can get lost elements, ConcurrentModificationException, or corrupted internal structures (before Java 8, concurrent HashMap resizing could even create an infinite loop).

An important subtlety: method-level synchronisation does not make compound operations safe. if (!vector.contains(x)) vector.add(x) is two synchronized calls with a gap between them; another thread can insert in that gap. Iterating a Vector while another thread modifies it also fails unless you lock the whole iteration.

That is why Vector, Hashtable and Collections.synchronizedList are considered legacy approaches. Modern Java uses:

  • unsynchronized classes for confined data,
  • concurrent collections for shared data: ConcurrentHashMap (fine-grained, mostly lock-free reads, atomic computeIfAbsent/merge), CopyOnWriteArrayList for read-mostly lists, ConcurrentLinkedQueue and BlockingQueue implementations,
  • immutable collections (List.of, Map.copyOf) for shared read-only data.

How it works

  1. Synchronized class: each public method acquires the object's monitor.
  2. Other threads calling any synchronized method on that object wait.
  3. Unsynchronized class: all threads run methods simultaneously with no coordination.
  4. Concurrent collections use finer techniques (CAS, per-bin locks) for safety with less contention.
  5. Compound actions still need atomic methods or external locking.

Example

// Local, single-thread use: unsynchronized is correct and fastest
StringBuilder sb = new StringBuilder();
for (String part : parts) sb.append(part).append(',');

// Shared map: legacy synchronized vs modern concurrent
Map<String, Integer> legacy = new Hashtable<>();
if (!legacy.containsKey("a")) legacy.put("a", 1);      // still a race between calls

ConcurrentHashMap<String, Integer> modern = new ConcurrentHashMap<>();
modern.merge("a", 1, Integer::sum);                     // atomic, scalable

Common mistakes

  • Assuming a synchronized collection makes check-then-act safe.
  • Using Vector or Hashtable in new code.
  • Sharing a HashMap or ArrayList between threads "because it is only read" while something writes to it.
  • Using StringBuffer for a local variable where no sharing exists.

How to answer in the interview

"A synchronized resource controls access so only one thread at a time runs its critical methods, like Vector, Hashtable or StringBuffer. That makes single operations thread-safe but adds locking overhead and contention, and compound actions like contains-then-add still aren't safe. Unsynchronized classes like ArrayList, HashMap and StringBuilder let any thread in at any time; they're faster and right for data used by one thread, but they corrupt or lose data when shared and modified. In modern code I use unsynchronized classes for local data and concurrent collections like ConcurrentHashMap for shared data, rather than the old synchronized classes."

Likely follow-up questions

  • Why are Vector and Hashtable considered legacy? They lock every method on one monitor, scale poorly and still do not protect compound actions; collections framework and concurrent classes replaced them.
  • What does Collections.synchronizedList give you? A wrapper that locks each call; you must still lock the list manually while iterating.
  • Why is ConcurrentHashMap faster than Hashtable? Lock-free reads and per-bin locking or CAS for writes, instead of one global lock.
