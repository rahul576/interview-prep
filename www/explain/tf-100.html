A pipeline ran terraform destroy against the wrong environment because of a misconfigured variable. How do you respond and prevent it?

Terraform · scenario · levels mid, senior, lead

In one line

Stop pipelines and declare an incident, assess and recover (re-apply code for stateless resources, restore data from backups and soft delete), then prevent recurrence with per-environment pipeline identities, prevent_destroy and cloud delete locks, explicit destroy approvals with environment checks, and a blameless postmortem.

Detailed explanation

The first priority is to contain: pause or disable all related pipelines so a retry or scheduled run does not make it worse, declare an incident and tell the affected teams and stakeholders. Then assess precisely what was destroyed, using the pipeline log (Terraform prints every destroyed address), the state file history in the versioned backend and the cloud activity log.

Recovery splits into two parts. Stateless infrastructure — networks, compute, app services, IAM — comes back by running terraform apply with the correct environment's configuration. Data is the hard part: databases from point-in-time restore or backups, storage accounts and Key Vaults from soft delete, disks from snapshots, AWS resources from AWS Backup. This is exactly why soft delete, purge protection and tested backups are part of the design. Also check DNS names, IPs and certificates that may have changed on recreation.

Prevention addresses the root cause, not the typo. The real failure is that one identity could reach the wrong environment. Each environment gets its own pipeline identity with rights only on its subscription or account, so a wrong variable leads to an authorisation error instead of destruction. Critical resources get lifecycle { prevent_destroy = true } and cloud-level protection: Azure CanNotDelete locks, RDS deletion protection, S3 object lock, GCP deletion protection. Destroy runs require a separate, explicit approval in a protected environment, and the pipeline runs a preflight check that the backend key, workspace and target subscription match the selected environment. Finally, a blameless postmortem documents the timeline and actions.

How it works

  1. Disable pipelines, declare the incident, communicate.
  2. List destroyed resources from logs, state versions and activity logs.
  3. Restore data from backups, snapshots and soft-deleted resources.
  4. Re-apply infrastructure from the correct configuration and verify.
  5. Separate identities per environment; add locks and prevent_destroy.
  6. Gate destroy behind approval and a preflight environment check.
  7. Hold a blameless postmortem and track actions.

Example

# preflight in the pipeline
expected_sub=$(jq -r ".${ENV}.subscription_id" envs.json)
actual_sub=$(az account show --query id -o tsv)
[ "$expected_sub" = "$actual_sub" ] || { echo "Subscription mismatch for $ENV"; exit 1; }
grep -q "key = \"${ENV}.tfstate\"" "env/${ENV}.backend.hcl" || exit 1
resource "azurerm_management_lock" "db" {
  name       = "no-delete"
  scope      = azurerm_postgresql_flexible_server.main.id
  lock_level = "CanNotDelete"
}

Common mistakes

  • Rushing to re-run the pipeline before understanding what happened.
  • Fixing only the variable and calling it done.
  • Backups that were never tested, or soft delete disabled.
  • A postmortem that blames the engineer instead of the system.

How to answer in the interview

"First I stop all related pipelines and declare an incident. I assess exactly what was destroyed from the run log, state history and activity logs, then recover: stateless resources come back by re-applying the code, data comes from backups, point-in-time restore and soft-deleted resources. For prevention, the real root cause is that one identity could reach the wrong environment, so each environment gets its own pipeline identity scoped to its subscription, making this mistake an authorisation error. Critical resources get prevent_destroy and cloud deletion locks. Destroy requires a separate approval and a preflight check that backend and subscription match the environment. And I run a blameless postmortem."

Likely follow-up questions

  • Which guard would have stopped this most cheaply? Per-environment identities; a wrong variable would simply fail authorisation.
  • Does prevent_destroy stop everything? No, removing the resource from code removes the guard; cloud locks are stronger.
  • Should destroy be allowed in pipelines at all? Only for ephemeral environments; production destroy should be exceptional and gated.
