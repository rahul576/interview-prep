Terraform creates a Key Vault and then fails to create secrets in it with a 403 Forbidden error. Why, and how do you fix it?

Terraform · scenario · levels mid, senior

In one line

Creating the vault uses the control plane, but writing secrets uses the data plane, which needs separate permissions such as Key Vault Secrets Officer; add the role assignment with a dependency, allow for propagation delay, and make sure the vault firewall lets the runner in.

Detailed explanation

Azure separates management (control plane) operations, handled by Azure Resource Manager, from data plane operations handled by the service itself. A pipeline identity with Contributor on the resource group can create, update and delete the Key Vault resource, but Contributor has no data actions, so it cannot read or write secrets, keys or certificates. The request reaches the vault and is rejected with 403 Forbidden.

With the Azure RBAC permission model (now the default and recommended model for new vaults), the fix is to give the deployer identity a data-plane role on the vault, such as Key Vault Secrets Officer for managing secrets, and give applications narrower roles like Key Vault Secrets User. With the legacy access policy model, you would add an access policy for the deployer instead.

The second subtlety is propagation. A new role assignment can take a minute or more to become effective, so even with the right dependency, the first apply may fail. A time_sleep resource after the assignment, or simply re-running the apply, deals with it.

The third common cause is the network. If the vault has public_network_access_enabled = false, or a firewall with default action deny, a cloud-hosted runner on the internet is blocked, also with a 403. The runner must be inside a VNet with a private endpoint and private DNS, or its IP must be explicitly allowed. This is one reason teams use self-hosted runners for private resources.

How it works

  1. Terraform creates the vault with enable_rbac_authorization = true (newer azurerm uses rbac_authorization_enabled).
  2. It creates an azurerm_role_assignment giving the pipeline identity Key Vault Secrets Officer at vault scope.
  3. A time_sleep waits for RBAC propagation.
  4. Secret resources depend on the sleep.
  5. The runner reaches the vault through a private endpoint or an allowed network rule.

Example

data "azurerm_client_config" "current" {}

resource "azurerm_role_assignment" "deployer_secrets" {
  scope                = azurerm_key_vault.main.id
  role_definition_name = "Key Vault Secrets Officer"
  principal_id         = data.azurerm_client_config.current.object_id
}

resource "time_sleep" "rbac" {
  depends_on      = [azurerm_role_assignment.deployer_secrets]
  create_duration = "60s"
}

resource "azurerm_key_vault_secret" "db" {
  name         = "db-connection"
  value        = var.db_connection
  key_vault_id = azurerm_key_vault.main.id
  depends_on   = [time_sleep.rbac]
}

Common mistakes

  • Assuming Owner or Contributor on the subscription includes secret access.
  • Forgetting the explicit dependency, so secrets are created in parallel with the role assignment.
  • Debugging permissions when the real cause is the vault firewall.
  • Giving the deployer Key Vault Administrator when Secrets Officer is enough.

How to answer in the interview

"Creating the vault is a control-plane operation where the pipeline identity has Contributor, but writing secrets is a data-plane operation, and Contributor has no data actions. With the RBAC model I add a role assignment giving the pipeline identity Key Vault Secrets Officer on the vault and make the secrets depend on it. Because role assignments take time to propagate, I add a short time_sleep or retry. The other common cause is the network: if the vault only allows private endpoints, the runner must be inside the network or explicitly allowed, which is why I use self-hosted runners for private vaults."

Likely follow-up questions

  • Why is RBAC preferred over access policies? It uses standard Azure RBAC, supports scopes, PIM and auditing, and separates who manages permissions.
  • How do you tell a permission 403 from a network 403? The error body says ForbiddenByRbac or ForbiddenByFirewall/client address not authorised.
  • Should secret values be in Terraform at all? Only generated ones; values in state need a protected backend, or let apps write their own.
