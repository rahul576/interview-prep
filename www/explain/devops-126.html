Design an observability stack for 40 microservices on Kubernetes.

Observability & SRE · design · levels senior, lead

In one line

Build three correlated pipelines, metrics (Prometheus + Grafana), logs (Fluent Bit or Alloy to Loki/Elasticsearch) and traces (OpenTelemetry to Tempo/Jaeger), all linked by a trace id, with SLO-based alerting, and run the whole thing as a shared platform service.

Detailed explanation

With 40 microservices, nobody can debug by SSH-ing into pods or by reading one service's logs. The stack has to answer three questions quickly: is something wrong (metrics and alerts), where is it (traces) and why (logs). The goal is fast correlation during incidents at a sustainable cost.

Metrics: the kube-prometheus-stack Helm chart (Prometheus Operator, Alertmanager, node-exporter, kube-state-metrics, Grafana) or a managed service such as Amazon Managed Prometheus, Azure Monitor managed Prometheus or Grafana Cloud. Services expose RED metrics; for long retention and multi-cluster views add Thanos or Mimir. Watch cardinality: labels like user id explode storage.

Logs: applications write structured JSON to stdout with the trace id in every line. A DaemonSet agent (Fluent Bit, or Grafana Alloy, which replaces the deprecated Promtail) ships them to Loki (cheap, label-indexed) or Elasticsearch/OpenSearch when full-text search and analytics justify the cost.

Traces: OpenTelemetry SDKs or auto-instrumentation in each service, sending OTLP to an OpenTelemetry Collector (agent plus gateway), which samples (for example tail sampling to keep all errors and slow requests) and exports to Tempo or Jaeger. Grafana then links metric exemplars to traces and traces to logs.

How it works

  1. Platform team installs the stack via GitOps (Argo CD or Flux) in every cluster.
  2. Each service gets a standard library or auto-instrumentation: OTel tracing, Prometheus metrics, JSON logging with trace id.
  3. ServiceMonitors/PodMonitors are created from the service template, so scraping is automatic.
  4. Dashboards per service show golden signals; a fleet overview shows SLO status for all 40.
  5. Alerts are multi-window burn-rate SLO alerts routed by Alertmanager to PagerDuty or Opsgenie, each with a runbook link.
  6. Retention and sampling are tuned per signal to control cost.

Example

# OpenTelemetry Collector gateway: keep errors and slow traces, sample the rest
processors:
  tail_sampling:
    policies:
      - name: errors
        type: status_code
        status_code: { status_codes: [ERROR] }
      - name: slow
        type: latency
        latency: { threshold_ms: 1000 }
      - name: baseline
        type: probabilistic
        probabilistic: { sampling_percentage: 10 }
exporters:
  otlp/tempo:
    endpoint: tempo-distributor.observability:4317

Common mistakes

  • Unstructured logs without trace ids, so correlation is impossible.
  • High-cardinality labels (user id, full URL) in Prometheus.
  • Alerting on CPU and pod restarts instead of user-facing SLOs.
  • No retention or sampling plan, so cost explodes after six months.

How to answer in the interview

"I'd split it into metrics, logs and traces, all tied together by the trace id. Metrics come from kube-prometheus-stack or a managed Prometheus, with Thanos or Mimir if we need long retention, and Grafana dashboards showing golden signals per service. Logs are structured JSON shipped by a Fluent Bit or Alloy DaemonSet to Loki, or Elasticsearch if we really need full-text search. Traces use OpenTelemetry SDKs and a collector with tail sampling, exporting to Tempo. In Grafana you jump from a latency spike via an exemplar to the trace and then to the logs for that trace id. Alerts are SLO burn-rate alerts through Alertmanager to PagerDuty with runbooks, and a platform team owns the stack and bakes the instrumentation into service templates."

Likely follow-up questions

  • How would you budget storage and retention? Short high-resolution retention (15 days) locally, downsampled long-term in object storage, logs 7-30 days by level, traces sampled.
  • Managed or self-hosted? Managed if the team is small; self-hosted when scale makes managed pricing expensive and you have the skills.
  • How do you stop cardinality explosions? Label allowlists, relabelling, per-tenant series limits and cardinality dashboards.
