Tool calls through your MCP integration fail intermittently. What do you check first?

MCP Servers · scenario · levels mid, senior

In one line

First classify the failures using correlated logs and traces, protocol vs transport vs tool execution errors, then check the usual suspects: mismatched timeouts, expired tokens or refresh failures, downstream rate limits and outages, load-balancing and in-memory state problems, and server resource exhaustion.

Detailed explanation

"Intermittent" usually means several causes mixed together, so the first job is to separate them. Correlate each failing call across host, gateway, server and downstream logs with a trace ID, and classify:

  • Protocol errors: JSON-RPC errors such as invalid params, method not found, or "session not found".
  • Transport errors: connection resets, TLS failures, timeouts, 502/503/504 from proxies.
  • Tool execution errors: a successful response with isError: true, carrying the downstream system's error.

Then work through the usual suspects:

Timeouts. The host, client SDK, gateway, server and downstream API each have their own timeout. A downstream call that occasionally takes 35 seconds will fail whenever it exceeds the shortest one in the chain, often a gateway idle timeout of 30 seconds. Fix by aligning timeouts (each hop shorter than its caller), making slow operations async with tasks or progress, and optimising the downstream.

Authentication. Access tokens expire mid-conversation; if refresh fails or races, you get sporadic 401s. Check token lifetimes, refresh logic and clock skew.

Downstream limits and outages. 429s from rate-limited APIs during bursts, or partial 5xx outages. Look at server logs for downstream status codes; add backoff with jitter, caching and per-client limits.

Scaling and state. With several replicas, in-memory sessions, handles or tasks fail when requests hit another instance; failure rate correlates with replica count.

Server resources. Connection pool exhaustion, thread starvation, memory pressure or cold starts on serverless.

Fixing the dominant class usually removes most failures. Finally, make failures actionable: tool errors that tell the agent whether to retry, wait or ask the user.

How it works

  1. Pull failing calls for a time window with trace IDs.
  2. Bucket by error class and by tool, client, replica and downstream.
  3. Look for correlations: time of day, call duration near a timeout value, replica, token age.
  4. Fix the biggest bucket first; verify with metrics.
  5. Add alerts and dashboards per error class.

Common mistakes

  • Adding blanket retries before understanding the cause.
  • Looking only at server logs, not gateway and client logs.
  • Treating isError results as transport failures, or vice versa.
  • Timeouts longer downstream than upstream.

How to answer in the interview

"I start by classifying the failures from logs and traces correlated per call: protocol errors like session not found or invalid params, transport errors like resets and timeouts, or tool execution errors returned with isError from the downstream system. Then the usual suspects. Timeouts: client, gateway, server and downstream all differ, and slow calls exceed the shortest. Authentication: tokens expiring mid-conversation or refresh failing cause sporadic 401s. Downstream rate limits or partial outages, visible as 429 or 5xx. Scaling: with several replicas, in-memory sessions or handles fail on another instance. And server resource limits like connection pool exhaustion. Fixing the dominant class usually resolves most of it."

Likely follow-up questions

  • Make failures helpful to agents? Clear errors stating whether to retry, after how long, or to ask the user.
  • Why align timeouts? Otherwise the caller gives up while work continues, causing retries and duplicates.
  • What dashboard? Error rate per class, per tool and per downstream, with latency histograms.
