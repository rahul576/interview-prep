What is Grafana, and how do you build a useful dashboard?

Observability & SRE · concept · levels entry

In one line

Grafana is an open-source visualisation and alerting tool that queries data sources such as Prometheus, Loki, Tempo or CloudWatch; a useful dashboard starts from the golden signals / RED method, uses variables, a consistent layout and is kept as code.

Detailed explanation

Grafana does not store data itself. It connects to data sources: Prometheus and Mimir for metrics, Loki for logs, Tempo or Jaeger for traces, plus cloud services like CloudWatch and Azure Monitor and databases like PostgreSQL. A dashboard is a set of panels, each running a query in the data source's language (for example PromQL for Prometheus or LogQL for Loki) and rendering it as a time series, stat, gauge, table or heatmap.

The hard part is not drawing graphs but building dashboards that help during an incident. A good service dashboard answers "is this service healthy, and if not, where is it hurting?" within seconds. Start with the RED method at the top: rate of requests, errors as a percentage, and duration as latency percentiles (p50, p95, p99), not averages. Below that, saturation: CPU, memory, thread or connection pool usage, and dependencies. Keep a consistent layout across all services, so an on-call engineer can read any team's dashboard.

Template variables (environment, cluster, service, instance) make one dashboard reusable for everything instead of copying it 40 times. Data links and exemplars let you jump from a latency spike to a trace in Tempo and to related logs in Loki. Finally, treat dashboards as code: store the JSON in Git and provision it automatically (provisioning files, the Grafana Operator, Terraform provider, or libraries such as Grafonnet), so they are reviewed and never lost when someone clicks "delete".

How it works

  1. Add data sources (Prometheus, Loki, Tempo), ideally via provisioning.
  2. Create variables like $env and $service from label values.
  3. Top row: request rate, error percentage, p95/p99 latency, SLO status.
  4. Next rows: saturation (CPU, memory, pools) and key dependencies.
  5. Add links to logs, traces and the runbook.
  6. Export JSON to Git; alert rules use the same queries.

Example

# p95 latency per route for the selected service
histogram_quantile(0.95,
  sum by (le, route) (
    rate(http_request_duration_seconds_bucket{service="$service", env="$env"}[5m])
  )
)

Common mistakes

  • Dashboards with 60 panels that nobody can read under pressure.
  • Showing average latency, which hides slow users.
  • Hard-coding service names instead of using variables.
  • Click-ops dashboards that are lost or drift between environments.
  • Different units and colours per team, causing confusion.

How to answer in the interview

"Grafana is an open-source visualisation and alerting tool that sits on top of data sources like Prometheus, Loki, Tempo or CloudWatch. Each panel runs a query, for example PromQL, and renders it. For a useful service dashboard I start with the RED method: request rate, error percentage and latency as p95 and p99, then saturation like CPU, memory and connection pools. I use variables for environment and service so one dashboard works for every service, keep the same layout across teams and add links to logs and traces. Dashboards are stored as code in Git and provisioned automatically, and alerts use the same queries."

Likely follow-up questions

  • Why percentiles rather than averages? Averages hide the slow tail that real users experience; p99 shows it.
  • Grafana alerting or Prometheus Alertmanager? Either works; Alertmanager rules live next to Prometheus, Grafana alerting can span many data sources.
  • How do you avoid dashboard sprawl? Standard templates per service type, ownership tags and deleting unused dashboards.
