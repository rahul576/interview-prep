What are the main building blocks of Amazon EKS?

Cloud (AWS) · concept · levels mid

In one line

EKS gives you an AWS-managed, highly available Kubernetes control plane; you add worker capacity (managed node groups, Karpenter, Fargate or EKS Auto Mode), networking through the Amazon VPC CNI, pod permissions through IRSA or EKS Pod Identity, and add-ons such as CoreDNS, kube-proxy, the EBS CSI driver and the AWS Load Balancer Controller.

Detailed explanation

The control plane (API servers and etcd) runs in an AWS-owned account across three availability zones. AWS patches, scales and backs it up, and you pay an hourly fee per cluster, higher when a version moves into extended support. You choose a Kubernetes version and must upgrade regularly. Access is managed with EKS access entries mapping IAM principals to Kubernetes permissions, replacing the old aws-auth ConfigMap.

Worker capacity options: managed node groups are EC2 Auto Scaling groups whose AMI updates and draining AWS orchestrates; self-managed nodes give full control; Karpenter watches pending pods and launches right-sized instances, mixing On-Demand, Spot and Graviton, and consolidates under-used nodes; Fargate runs each pod in its own micro-VM with no nodes; EKS Auto Mode lets AWS run compute, Karpenter-based scaling, storage and load balancing for you.

The Amazon VPC CNI gives every pod a real VPC IP from the node's ENIs, which makes pods directly routable and lets security groups for pods work, but consumes addresses quickly. Plan large subnets, use prefix delegation, or add secondary CIDRs (for example from 100.64.0.0/10) with custom networking.

Pods need AWS credentials: IRSA maps a Kubernetes service account to an IAM role through the cluster's OIDC provider; EKS Pod Identity is simpler, using an agent add-on and associations without OIDC trust policies per cluster. Core add-ons include CoreDNS, kube-proxy, the VPC CNI, the EBS CSI driver for persistent volumes, the AWS Load Balancer Controller that turns Ingress into ALBs and Services into NLBs, plus observability agents.

How it works

  1. Create the cluster with subnets in several AZs and an endpoint access mode.
  2. Add capacity: a small managed node group for system pods plus Karpenter, or Auto Mode.
  3. Install managed add-ons: VPC CNI, CoreDNS, kube-proxy, EBS CSI, Pod Identity agent.
  4. Install the AWS Load Balancer Controller for Ingress and Service objects.
  5. Map IAM roles to pods; grant people access through access entries.
  6. Upgrade control plane, add-ons and nodes one minor version at a time.

Example

apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig
metadata: {name: prod, region: eu-west-1, version: "1.33"}
addons:
  - name: vpc-cni
    configurationValues: '{"env":{"ENABLE_PREFIX_DELEGATION":"true"}}'
  - name: coredns
  - name: kube-proxy
  - name: aws-ebs-csi-driver
  - name: eks-pod-identity-agent
managedNodeGroups:
  - name: system
    instanceTypes: [m7g.large]
    minSize: 2
    maxSize: 4
aws eks create-pod-identity-association --cluster-name prod \
  --namespace orders --service-account orders-api \
  --role-arn arn:aws:iam::111122223333:role/orders-api

Common mistakes

  • Small /24 subnets that run out of pod IPs as the cluster grows.
  • Giving the node instance role broad permissions that every pod inherits.
  • Skipping version upgrades until extended support charges or forced upgrades arrive.
  • Running Karpenter on nodes it manages itself, so it can evict its own controller.

How to answer in the interview

"EKS gives me a managed control plane: AWS runs the API servers and etcd across three AZs and I pay per cluster hour. For workers I use managed node groups for system pods and Karpenter for right-sized, Spot-friendly capacity, or Fargate and Auto Mode when I want less to manage. The VPC CNI gives every pod a VPC IP, so I size subnets generously or use prefix delegation. Pods get AWS permissions through IRSA or the newer Pod Identity, and add-ons such as CoreDNS, the EBS CSI driver and the Load Balancer Controller complete the platform."

Likely follow-up questions

  • Why can a busy EKS cluster run out of IP addresses? Every pod takes a VPC IP; fix with prefix delegation, bigger or secondary CIDRs and custom networking.
  • IRSA or Pod Identity? Pod Identity avoids per-cluster OIDC trust edits and reuses roles across clusters.
  • How do you upgrade EKS safely? Check deprecated APIs, upgrade control plane, then add-ons, then nodes, one minor version at a time.
