Your cluster runs many microservices and security asks you to restrict which services can talk to each other. How do you implement and verify it?

Kubernetes · scenario · levels mid, senior

In one line

Use NetworkPolicies enforced by the CNI (Calico, Cilium, cloud network policy) with default deny ingress and egress per namespace and explicit allow rules per service, including DNS; add a service mesh or Cilium L7 policies for identity and HTTP-level rules; verify with test pods and roll out gradually.

Detailed explanation

By default every pod can reach every other pod. A NetworkPolicy selects pods by labels and defines allowed ingress and egress peers by pod selectors, namespace selectors and IP blocks, plus ports.

The policy is only enforced if the CNI plugin supports it: Calico, Cilium, Antrea, or the cloud offerings (Azure network policy or Cilium on AKS, VPC CNI network policy on EKS, Dataplane V2 on GKE). With a CNI that does not, policies are accepted by the API server and silently ignored, which is a classic false sense of security.

The pattern is default deny for ingress and egress in each namespace, then explicit allows: orders pods accept traffic only from the api-gateway namespace on 8080 and may connect only to payments and the database. Egress must allow DNS to CoreDNS on UDP and TCP 53, or every lookup fails.

NetworkPolicy is layer 3/4. For layer 7 rules, such as allowing only GET /prices, and for identity-based security independent of IPs, use a service mesh like Istio with mTLS and AuthorizationPolicies, or Cilium's L7 and identity-aware policies. Verify with probe pods that test allowed and blocked paths, and roll out per namespace, using Calico staged policies, Cilium audit mode or Hubble flow logs to see what would be dropped.

How it works

  1. Confirm the CNI enforces NetworkPolicy.
  2. Map real traffic flows (Hubble, flow logs, mesh telemetry).
  3. Apply default deny ingress and egress per namespace.
  4. Add allow rules per service, including DNS egress.
  5. Add mesh mTLS and L7 authorisation where needed.
  6. Test with probe pods and roll out namespace by namespace.

Example

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny, namespace: orders }
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: orders-allow, namespace: orders }
spec:
  podSelector: { matchLabels: { app: orders } }
  policyTypes: [Ingress, Egress]
  ingress:
    - from:
        - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: api-gateway } }
      ports: [{ port: 8080 }]
  egress:
    - to:
        - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: kube-system } }
          podSelector: { matchLabels: { k8s-app: kube-dns } }
      ports: [{ port: 53, protocol: UDP }, { port: 53, protocol: TCP }]
    - to:
        - podSelector: { matchLabels: { app: payments } }
      ports: [{ port: 8443 }]
kubectl -n orders run probe --rm -it --image=busybox -- wget -qO- -T 3 http://payments:8443

Common mistakes

  • Writing policies on a CNI that does not enforce them.
  • Default-deny egress without a DNS rule.
  • Inconsistent labels, so selectors match nothing or everything.
  • Big-bang rollout across all namespaces without observing flows.

How to answer in the interview

"The building block is NetworkPolicy, which selects pods by labels and namespaces and allows specific ingress and egress. It only works if the CNI enforces it, like Calico or Cilium, otherwise policies are silently ignored. I start with default deny for ingress and egress per namespace and add explicit allows per service, and egress must allow DNS to CoreDNS or everything breaks. Policies live in Git with consistent labels. For layer 7 rules and identity-based security I add a mesh like Istio with mTLS and authorisation policies, or Cilium's L7 features. I verify with test pods and roll out gradually using flow logs or audit modes."

Likely follow-up questions

  • Why do egress default-deny policies often break apps? They block DNS, cloud metadata, external APIs and monitoring endpoints; map flows first and allow them explicitly.
  • Can NetworkPolicy allow by domain name? Not natively; Cilium and Calico offer FQDN-based policies.
  • How do you allow traffic from an ingress controller? Allow its namespace by the kubernetes.io/metadata.name label.
