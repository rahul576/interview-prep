Design a highly available, multi-region setup for an application that depends on Azure OpenAI.

Azure AI & Foundry · design · levels senior, lead

In one line

For a highly available AI app, deploy the model in two or more regions (or use Global deployments), put an API Management gateway in front with priority and health-based routing and failover on 429/5xx, add retries, timeouts and circuit breakers in the app, plan a fallback model or degraded mode, replicate supporting services like AI Search, and monitor per region.

Detailed explanation

Model endpoints fail in ways ordinary APIs rarely do: regional incidents, capacity shortages for popular models, throttling at quota and latency spikes under load. Treat the model as an unreliable dependency.

Redundant capacity: create deployments of the same model and version in at least two regions, in separate resources. Global Standard deployments already spread processing across regions and are a strong primary for availability; for data residency, use Data Zone deployments or regional deployments in multiple regions of the same geography.

Gateway: API Management (itself deployed multi-region or zone-redundant) holds a backend pool. Typical priorities: 1) provisioned capacity for the baseline, 2) Standard/Global deployments, 3) another region. Circuit breakers trip a backend on 429 or 5xx (respecting retry-after), and requests flow to the next. The gateway also enforces auth, token limits and logging.

Application resilience: timeouts (long generations need generous but finite limits, plus streaming), retries with exponential backoff and jitter, idempotency for tool actions and a circuit breaker so the app doesn't pile up waiting threads.

Fallback: a smaller or different model (with prompts tested for it), cached answers for common questions, or a graceful degraded mode ("AI assistant temporarily unavailable, here are the help articles").

Supporting services: RAG needs Azure AI Search with replicas (for its SLA) and a secondary index in another region, replicated data stores, and redundant caches and identity dependencies. Otherwise the model fails over but retrieval doesn't.

Observability: dashboards and alerts on latency, error rate, 429s and quota usage per region and backend, plus regular failover drills.

How it works

  1. Deploy matching model versions in two or more regions.
  2. Configure APIM backends, pool priorities and circuit breakers.
  3. Add retries, timeouts and fallbacks in the app.
  4. Replicate AI Search and data stores.
  5. Monitor per backend; run failover tests.

Example

resource pool 'Microsoft.ApiManagement/service/backends@2024-05-01' = {
  parent: apim
  name: 'openai-pool'
  properties: {
    type: 'Pool'
    pool: {
      services: [
        { id: ptuSweden.id,   priority: 1 }
        { id: globalStd.id,   priority: 2, weight: 1 }
        { id: stdFrance.id,   priority: 3, weight: 1 }
      ]
    }
  }
}
// each backend: circuitBreaker rule tripping on 429 and 5xx, acceptRetryAfter: true

Common mistakes

  • Failing over the model but not AI Search or the database.
  • Different model versions per region, giving inconsistent answers.
  • Gateway in a single region becoming the new single point of failure.
  • No degraded mode, so the whole page breaks.

How to answer in the interview

"I design for the model being unavailable or throttled. Deployments of the same model and version run in at least two regions, or I use Global deployments, with a regional fallback for residency cases. API Management routes by priority and health: provisioned capacity first, then standard, then another region, with circuit breakers failing over on 429 or 5xx. The app uses timeouts, backoff and a fallback such as a smaller model, cached answers or a clear degraded mode. Supporting services like AI Search have replicas and a secondary index, and dashboards track latency, errors and quota per region."

Likely follow-up questions

  • Keeping answers consistent on failover? Same model version and prompts everywhere; evaluate fallback models separately.
  • Active-active or active-passive? Active-active for capacity, with priorities for cost.
  • How to test failover? Disable a backend in APIM in staging and run load tests.
