Design a news feed system like the one on LinkedIn or Twitter.

System Design · design · levels senior, lead

In one line

A news feed stores posts separately and builds per-user timelines of post IDs in Redis, using fan-out on write for normal accounts and fan-out on read for celebrities (a hybrid), then a ranking service orders candidates and the API pages with cursors.

Detailed explanation

Two operations matter: publishing a post and reading a feed. Reads vastly outnumber writes, and users expect the feed in well under 200 ms.

Fan-out on write (push): when a user posts, a background worker inserts the post ID into each follower's precomputed timeline (a Redis list or sorted set capped at, say, 800 entries). Reads are just a cache lookup plus hydration. The problem: an account with 50 million followers creates 50 million writes per post, delaying delivery and wasting work for inactive followers.

Fan-out on read (pull): at read time, fetch recent posts from everyone the user follows and merge them. Writes are cheap but reads are expensive, especially for users following thousands of accounts.

Hybrid: push for normal accounts; for accounts above a follower threshold, skip fan-out and pull their recent posts at read time, merging them with the precomputed timeline. Also skip fan-out to inactive users and rebuild their timeline when they return.

Ranking: modern feeds are not chronological. Candidate generation (timeline + celebrity posts + recommendations) feeds a ranking service that scores with an ML model on features like affinity, engagement, recency and content type, then applies diversity rules.

Storage: posts in a sharded store (Cassandra, MySQL shards) keyed by post ID, media in object storage behind a CDN, social graph in a dedicated store. Cursor pagination (opaque cursor of last score/ID) avoids duplicates as new posts arrive.

How it works

  1. User posts -> stored in posts DB -> event to Kafka.
  2. Fan-out workers fetch followers; if author is not a celebrity, ZADD timeline:{follower} with score = timestamp.
  3. Read: get top N IDs from timeline:{user}, plus recent posts from followed celebrities.
  4. Merge candidates, call ranking, hydrate posts (cache) and authors.
  5. Return page with nextCursor.

Example

public FeedPage getFeed(long userId, String cursor) {
    List<Long> pushed = redis.zrevrangeByScore("timeline:" + userId, Cursor.maxScore(cursor), 200);
    List<Long> pulled = graph.followedCelebrities(userId).stream()
            .flatMap(c -> postsRepo.recentIds(c, 20).stream()).toList();
    List<Post> candidates = postCache.hydrate(union(pushed, pulled));
    List<Post> ranked = rankingClient.rank(userId, candidates).subList(0, 20);
    return new FeedPage(ranked, Cursor.after(ranked.get(ranked.size() - 1)));
}

Common mistakes

  • Pure fan-out on write, ignoring celebrities.
  • Offset pagination that duplicates or skips posts.
  • Storing full posts in every timeline instead of IDs.
  • Fanning out synchronously in the post request.

How to answer in the interview

"Posts go into a sharded posts store, and each user has a precomputed timeline of post IDs in Redis. With fan-out on write, a new post is pushed asynchronously through Kafka to followers' timelines, which makes reads fast but is too expensive for accounts with millions of followers. So I'd use a hybrid: push for normal users and pull celebrity posts at read time, merging them. A ranking service scores the candidates, posts are hydrated from cache, and the API uses cursor-based pagination."

Likely follow-up questions

  • User following 5,000 accounts? Precomputed timeline still works; cap fan-in for pull sources and rely on ranking.
  • Deleting a post? Mark deleted in posts store; filter on hydration, lazily clean timelines.
  • New user with empty feed? Recommendations and popular content as candidates.
