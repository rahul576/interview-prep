What are Docker restart policies?

Docker · concept · levels entry

In one line

The --restart policy tells the Docker daemon what to do when a container exits: no (default), on-failure[:max-retries] (non-zero exit only), always (also after daemon restart) and unless-stopped (like always, but respects a manual stop across reboots); orchestrators handle this in production.

Detailed explanation

Restart policies make a single Docker host self-healing for simple setups.

  • no: never restart. Fine for one-off jobs and development.
  • on-failure: restart only if the process exits with a non-zero code, optionally capped, e.g. on-failure:5. A clean exit (0) stays stopped. Good for batch-like workers that should retry on crashes but finish normally.
  • always: restart whenever the container stops, regardless of exit code. If you stop it manually with docker stop, it stays stopped until the Docker daemon restarts (for example after a host reboot), then it starts again.
  • unless-stopped: like always, except a container you stopped manually stays stopped even after the daemon or host restarts. Usually the most intuitive choice for long-running services.

Set it with docker run --restart unless-stopped …, change it on an existing container with docker update --restart on-failure:3 name, or in Compose with restart: unless-stopped.

Crash loops: if a container with always crashes immediately on every start, Docker does not spin at full speed. It adds an increasing delay, doubling from 100 ms, between restarts and resets the delay once the container stays up for a while. docker ps shows Restarting (1) 3 seconds ago and the restart count grows (docker inspect -f '{{.RestartCount}}'). The root cause, such as a bad config or missing dependency, must still be fixed; check docker logs.

Restart policies do not replace health-based recovery: a hung process that never exits is not restarted. And in production clusters, Kubernetes (restartPolicy, liveness probes, ReplicaSets rescheduling on other nodes) or ECS handles restarts, so you would not rely on Docker policies there.

How it works

  1. Container exits; daemon records exit code.
  2. Daemon checks the policy and whether the stop was manual.
  3. If a restart applies, it waits the back-off delay, then starts the container again.
  4. On daemon start, containers with always (and unless-stopped not manually stopped) are started.

Example

docker run -d --name app --restart unless-stopped -p 80:8080 shop-api:1.4.2
docker run -d --name worker --restart on-failure:5 report-worker:2.0
docker update --restart always app
docker inspect -f '{{.HostConfig.RestartPolicy.Name}} restarts={{.RestartCount}}' worker
services:
  api:
    image: shop-api:1.4.2
    restart: unless-stopped

Common mistakes

  • Using always and being surprised that a manually stopped container comes back after a reboot.
  • Treating restart policies as a fix for crash loops instead of reading logs.
  • Expecting restart policies to recover hung (not exited) processes.

How to answer in the interview

"A restart policy tells the Docker daemon what to do when a container exits. no, the default, never restarts. on-failure restarts only on a non-zero exit code, optionally limited, like on-failure:5. always restarts whenever it stops and also when the daemon starts after a reboot. unless-stopped is like always, except a container I stopped manually stays stopped after a reboot, which is usually what I want for services. I set it with --restart or restart in Compose. It's fine for single-host setups; in production an orchestrator like Kubernetes handles restarts, health checks and rescheduling."

Likely follow-up questions

  • Container with always crashes immediately? It restarts with increasing back-off delays; fix the cause using logs.
  • Restart on a failed health check? Plain Docker does not; orchestrators or tools like autoheal do.
  • Change policy on a running container? docker update --restart.
