What is the difference between NSGs, application security groups and Azure Firewall?

Azure · concept · levels mid, senior

In one line

NSGs are stateful layer 4 allow/deny rules on subnets or NICs, application security groups let those rules target groups of VMs by role instead of IPs, and Azure Firewall is a central managed firewall with FQDN rules, threat intelligence and (Premium) TLS inspection and IDPS, usually in the hub; use NSGs for micro-segmentation and the firewall for central policy.

Detailed explanation

Network security groups (NSGs) contain prioritised rules (100 to 4096) matching source, destination, port and protocol, with allow or deny actions, for inbound and outbound traffic. They are stateful: return traffic for an allowed flow is permitted automatically. They can be attached to a subnet and/or a NIC; for inbound traffic the subnet NSG is evaluated first, then the NIC NSG, and both must allow. Default rules allow VNet-internal traffic and Azure Load Balancer probes, and deny inbound internet. NSGs support service tags such as Storage.WestEurope or AzureLoadBalancer. They are free and the basic building block for micro-segmentation. NSG flow logs are being replaced by VNet flow logs for visibility.

Application security groups (ASGs) are labels you attach to NICs, such as asg-web, asg-api, asg-db. NSG rules then say "allow asg-api to asg-db on 5432" instead of listing IP ranges. When VMs are added or removed, you only change their ASG membership, so rules remain correct and readable.

Azure Firewall is a managed, highly available, auto-scaling firewall deployed in its own subnet (AzureFirewallSubnet), usually in the hub VNet. It supports network rules (IP, port), application rules with FQDN filtering for outbound HTTP/S, DNAT for inbound, threat intelligence filtering, a DNS proxy, and centralised logging. The Premium SKU adds TLS inspection, IDPS, URL filtering and web categories. Rules are managed with Firewall Policy, often via Firewall Manager. User-defined routes send spoke egress and spoke-to-spoke (east-west) traffic through it.

Together: NSGs enforce local segmentation close to workloads (defence in depth), while the firewall provides central inspection, outbound control and audit.

How it works

  1. Create ASGs per application role and assign NICs.
  2. Write NSG rules using ASGs and service tags; deny by default.
  3. Deploy Azure Firewall in the hub with a firewall policy.
  4. Route spoke traffic to the firewall with UDRs.
  5. Allow only approved FQDNs and ports for egress.
  6. Send firewall and flow logs to Log Analytics.

Example

az network asg create -g rg-app -n asg-api
az network asg create -g rg-app -n asg-db
az network nsg rule create -g rg-app --nsg-name nsg-db -n allow-api-to-db \
  --priority 200 --direction Inbound --access Allow --protocol Tcp \
  --source-asgs asg-api --destination-asgs asg-db --destination-port-ranges 5432
az network firewall policy rule-collection-group collection add-filter-collection \
  -g rg-hub --policy-name fwpol-hub --rule-collection-group-name app-rules \
  --name allow-egress --collection-priority 200 --action Allow \
  --rule-type ApplicationRule --rule-name allow-github \
  --source-addresses 10.42.0.0/22 --protocols Https=443 --target-fqdns github.com "*.github.com"

Common mistakes

  • Relying only on NSGs for egress control to the internet.
  • Hard-coding IP addresses instead of ASGs and service tags.
  • Overly broad "allow any" rules at high priority.
  • Forgetting that both subnet and NIC NSGs must allow traffic.
  • Deploying the firewall without routes, so traffic bypasses it.

How to answer in the interview

"NSGs are stateful layer 4 filters with prioritised allow and deny rules on source, destination, port and protocol, attached to subnets or NICs; they are free and the basic building block for micro-segmentation. Application security groups let me group VMs by role, like web or db, and use those groups in NSG rules instead of IP addresses, so rules stay correct as machines change. Azure Firewall is a managed, highly available central firewall, usually in the hub, with FQDN-based application rules, threat intelligence, DNS proxy and central logging, plus TLS inspection and IDPS in Premium. User-defined routes send egress and east-west traffic through it. I use both: NSGs close to workloads and the firewall for central policy."

Likely follow-up questions

  • How would you troubleshoot traffic blocked between a VM and the internet? Network Watcher IP flow verify, effective security rules, effective routes, then firewall logs.
  • Can NSGs filter by domain name? No; use Azure Firewall application rules.
  • When choose Firewall Premium? When you need TLS inspection, IDPS or URL categories.
