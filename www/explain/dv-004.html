How do users, groups and sudo work in Linux?

Linux · concept · levels entry

In one line

Users and groups are identified by UID and GID, stored in /etc/passwd, /etc/shadow and /etc/group, managed with useradd, usermod -aG and groupadd, and sudo grants controlled elevated rights through sudoers (edited with visudo), following least privilege.

Detailed explanation

The kernel only knows numbers: every process runs with a UID and a set of GIDs, and file access is checked against them. UID 0 is root, which bypasses most permission checks.

Account data lives in plain files. /etc/passwd lists each user's name, UID, primary GID, home directory and shell; it is world-readable. /etc/shadow holds the password hashes (yescrypt or SHA-512 on current distributions) and ageing information, readable only by root. /etc/group lists groups and their supplementary members.

Management commands: useradd -m -s /bin/bash alice creates a user with a home directory (adduser is a friendlier wrapper on Debian), passwd alice sets a password, groupadd deploy creates a group, and usermod -aG docker alice appends a supplementary group. The -a is critical: without it, -G replaces all existing supplementary groups.

sudo lets permitted users run commands as root or another user, with their own password, and logs every command. Rules live in /etc/sudoers and drop-in files under /etc/sudoers.d/, which you edit with visudo because it checks syntax before saving; a broken sudoers file can lock everyone out of root. Rules can be narrow, such as letting the deploy group restart one service only. Least privilege means no shared root logins, no direct root SSH, and service accounts with only the access they need.

How it works

  1. Login maps a username to UID and groups.
  2. Processes inherit those IDs; the kernel checks them on file access.
  3. sudo checks sudoers rules for the user and command.
  4. If allowed, it runs the command as the target user and logs it.

Example

sudo useradd -m -s /bin/bash alice
sudo usermod -aG docker alice
id alice        # uid=1001(alice) gid=1001(alice) groups=1001(alice),998(docker)
sudo visudo -f /etc/sudoers.d/deploy
# /etc/sudoers.d/deploy
%deploy ALL=(root) NOPASSWD: /usr/bin/systemctl restart orders.service

Common mistakes

  • usermod -G without -a, removing the user from all other groups.
  • Editing sudoers with a normal editor and breaking sudo.
  • ALL=(ALL) NOPASSWD: ALL for everyone.
  • Adding users to the docker group without realising it is effectively root.

How to answer in the interview

"Every user has a numeric UID and a primary group plus optional secondary groups, each with a GID. Account details are in /etc/passwd, password hashes in /etc/shadow, which only root can read, and groups in /etc/group. I create users with useradd, add them to groups with usermod -aG, and the -a matters because without it you replace their groups. sudo lets permitted users run commands with elevated rights; rules are in sudoers, which I edit with visudo because it checks syntax, and they can be narrow, like restarting one service. I follow least privilege and avoid working as root."

Likely follow-up questions

  • Why edit sudoers with visudo? It locks the file and validates syntax, so a typo cannot break sudo for everyone.
  • Why is the docker group dangerous? Access to the Docker socket allows starting privileged containers, which equals root.
  • How do you lock an account? usermod -L or passwd -l, and set an expired date with chage -E 0.
