How do @Qualifier and @Primary work when there are multiple beans of the same type?

Spring Framework · concept · levels entry, mid

In one line

With several beans of one type, injection by type fails with NoUniqueBeanDefinitionException; @Primary marks the default candidate, @Qualifier picks a specific bean at the injection point (and overrides @Primary), and you can inject a List or Map of all implementations for strategy patterns.

Detailed explanation

Spring resolves dependencies by type first. If an interface PaymentProvider has implementations StripeProvider and PaypalProvider, a constructor parameter PaymentProvider provider is ambiguous and startup fails with NoUniqueBeanDefinitionException: expected single matching bean but found 2.

Ways to resolve it:

  • @Primary on one bean (or @Bean method) declares it the default whenever a single candidate is needed and nothing more specific is said. Typical use: one main DataSource or ObjectMapper, others for special cases.
  • @Qualifier("paypalProvider") at the injection point chooses by bean name or qualifier value. A qualifier is more specific, so it wins over @Primary. You can create custom qualifier annotations (meta-annotated with @Qualifier) for type safety instead of strings.
  • Parameter name fallback: if the parameter name matches a bean name, Spring uses it (this relies on the -parameters compiler flag, which Boot's build plugins enable). Explicit qualifiers are clearer.
  • Collections: inject List<PaymentProvider> to get all of them, ordered by @Order or Ordered, or Map<String, PaymentProvider> keyed by bean name. This is the cleanest base for the strategy pattern: pick an implementation at runtime from a request field without if/else chains, and adding a new provider means just adding a new bean.
  • ObjectProvider<T> offers getIfUnique(), orderedStream() and lazy access.
  • Spring 6.2 also added @Fallback, the inverse of @Primary, marking a bean to use only when no other candidate exists.

How it works

  1. Spring collects all candidate beans of the required type.
  2. If exactly one, inject it.
  3. If several: apply qualifiers at the injection point, then @Primary, then @Fallback and parameter-name matching.
  4. Still ambiguous: throw NoUniqueBeanDefinitionException.
  5. For collection types, inject all candidates.

Example

public interface PaymentProvider { String code(); Receipt charge(Order o); }

@Component @Primary
class StripeProvider implements PaymentProvider { public String code() { return "STRIPE"; } ... }

@Component @Qualifier("paypal")
class PaypalProvider implements PaymentProvider { public String code() { return "PAYPAL"; } ... }

@Service
class RefundService {
    RefundService(PaymentProvider defaultProvider,                 // Stripe via @Primary
                  @Qualifier("paypal") PaymentProvider paypal) { ... }
}

@Service
class CheckoutService {
    private final Map<String, PaymentProvider> byCode;
    CheckoutService(List<PaymentProvider> providers) {
        byCode = providers.stream().collect(Collectors.toMap(PaymentProvider::code, p -> p));
    }
    Receipt pay(Order o, String method) {
        PaymentProvider p = Optional.ofNullable(byCode.get(method))
            .orElseThrow(() -> new UnsupportedPaymentException(method));
        return p.charge(o);
    }
}

Common mistakes

  • Marking more than one bean @Primary for the same type.
  • Typos in string qualifiers that only fail at startup; prefer custom qualifier annotations.
  • Long if/else or switch on types instead of a map of strategies.
  • Renaming a class and breaking name-based injection.

How to answer in the interview

"If two beans implement the same interface and I inject by type, Spring throws NoUniqueBeanDefinitionException because the choice is ambiguous. @Primary marks one bean as the default. @Qualifier at the injection point picks a specific bean by name or by a custom qualifier annotation, and it takes precedence over @Primary. When I need all of them, I inject a List or a Map from bean name to bean, which is perfect for the strategy pattern, for example choosing a payment provider at runtime from a field in the request, and adding a provider is just adding a bean."

Likely follow-up questions

  • How would you choose a strategy at runtime based on a request field? Build a map from a key each implementation exposes, look it up, fail clearly if missing.
  • How is the List ordered? By @Order or Ordered, otherwise registration order.
  • Qualifier on @Bean methods? Yes, put @Qualifier next to @Bean.
