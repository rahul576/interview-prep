What is profiling, and which Java profiling tools have you used?

JVM & Performance · concept · levels mid, senior

In one line

Profiling measures where an application actually spends CPU, memory allocations, lock waits and I/O time; sampling profilers (JFR, async-profiler) are low-overhead and production-safe, instrumentation profilers are precise but slow; I use JFR with JDK Mission Control, async-profiler, VisualVM, commercial tools like YourKit or JProfiler, Eclipse MAT for heap dumps, and continuous profiling for regressions.

Detailed explanation

Performance intuition is often wrong; profiling replaces guessing with data. The main dimensions are CPU (which methods run), allocation (which code creates garbage), heap (what is retained), locks (where threads wait for monitors), and wall-clock time (including I/O and sleeping, key for latency).

Sampling vs instrumentation. A sampling profiler periodically captures stack traces of threads; hot methods appear in more samples. Overhead is low (around 1-2%), so it can run in production, but very short methods may be missed. An instrumentation profiler injects code at method entry and exit, giving exact call counts and timings, but adds significant overhead and can distort the JIT's behaviour, so it suits development and targeted analysis.

Tools I use.

  • Java Flight Recorder (JFR): built into the JDK, records CPU samples, allocation samples, GC, locks, I/O, exceptions and custom events. Start with -XX:StartFlightRecording or jcmd JFR.start; analyse in JDK Mission Control or with the jfr CLI. JFR event streaming (Java 14+) allows live consumption.
  • async-profiler: CPU, allocation, lock and wall-clock modes; produces flame graphs and JFR files; includes native and kernel frames, no safepoint bias.
  • VisualVM: quick local monitoring, thread views, sampling; good for development.
  • YourKit, JProfiler: commercial, polished UIs with both sampling and instrumentation, database and HTTP call views.
  • Eclipse MAT: heap dump analysis with dominator trees and leak suspects.
  • JMH: microbenchmarks with profilers like -prof gc.
  • Continuous profiling: Grafana Pyroscope, Datadog, Elastic and other APM vendors profile all instances all the time, so you can compare before and after a deployment.

Process. Define the question (why is p99 high?), reproduce under realistic load, profile, change one thing, re-measure.

How it works

  1. Define the symptom and metric to improve.
  2. Choose the profiling mode: CPU, allocation, lock or wall-clock.
  3. Record with a low-overhead sampler under realistic load.
  4. Analyse flame graphs or JMC views for the biggest contributors.
  5. Fix, benchmark, and confirm with production metrics.

Example

# JFR: start at launch with continuous recording
java -XX:StartFlightRecording=maxage=6h,settings=profile,filename=/logs/app.jfr -jar app.jar
jcmd <pid> JFR.dump name=1 filename=/tmp/now.jfr      # dump on demand
jfr print --events jdk.ExecutionSample /tmp/now.jfr | head

# async-profiler modes
asprof -e cpu   -d 30 -f cpu.html   <pid>
asprof -e alloc -d 30 -f alloc.html <pid>
asprof -e lock  -d 30 -f lock.html  <pid>
asprof -e wall  -t -d 30 -f wall.html <pid>

Common mistakes

  • Profiling a cold JVM or toy data set.
  • Using instrumenting profilers to judge production latency.
  • Looking only at CPU when the problem is waiting (use wall-clock or lock profiles).
  • Not reproducing before and after on the same workload.

How to answer in the interview

"Profiling is measuring where an application actually spends its resources, CPU time, allocations, locks and I/O waits, instead of guessing. Sampling profilers take stack snapshots periodically with low overhead, so they're usable in production; instrumentation profilers record every call precisely but slow the application down. I've used Java Flight Recorder with JDK Mission Control for CPU, allocations, GC and lock contention; async-profiler for flame graphs of CPU, allocation and wall-clock time; VisualVM for quick local checks; and YourKit and JProfiler. For memory I analyse heap dumps in Eclipse MAT, and continuous profiling with Pyroscope or an APM vendor helps catch regressions after deployments."

Likely follow-up questions

  • How would you profile an application running inside a Kubernetes pod? Use JFR via jcmd in the container or an ephemeral debug container, or attach async-profiler, then copy the file out; or use a continuous profiling agent.
  • What is a flame graph? A visualisation of sampled stacks where width shows how much time each frame accounts for.
  • CPU vs wall-clock profiling? CPU counts only running time; wall-clock includes waiting, which explains latency.
