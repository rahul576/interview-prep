What are the advantages and limitations of virtual threads?

Modern Java (11-21) · concept · levels senior, lead

In one line

Virtual threads give massive concurrency for blocking I/O with simple synchronous code, cheap creation and readable stack traces; limits are no gain for CPU-bound work, pinning (synchronized before Java 24, native calls), costly ThreadLocal use, and downstream resource limits that still apply.

Detailed explanation

Advantages

  • Scalability for I/O-bound services: tens or hundreds of thousands of concurrent requests waiting on HTTP or database calls, without tuning thread pools.
  • Simple code: plain blocking, imperative code instead of callbacks, CompletableFuture chains or reactive operators. Exceptions and try/catch work normally.
  • Cheap: create one per task; no pool sizing.
  • Tooling: they are real Threads, so debuggers, profilers, JFR and stack traces work as expected. Thread dumps can be produced in JSON with jcmd <pid> Thread.dump_to_file -format=json.
  • Framework support: Spring Boot 3.2+ (spring.threads.virtual.enabled=true), Tomcat, Jetty, Helidon, Quarkus.

Limitations

  • CPU-bound work gains nothing; you still have N cores.
  • Pinning: on Java 21-23 a virtual thread that blocks while inside a synchronized block or method cannot unmount, so it holds its carrier. With few carriers, a handful of pinned threads can stall the whole application. Java 24 (JEP 491) removed this for synchronized; blocking inside native code/JNI and some file operations still pins (the JVM may temporarily add carriers for file I/O). On older versions, replace long synchronized sections around I/O with ReentrantLock, and detect pinning with JFR's jdk.VirtualThreadPinned event.
  • ThreadLocal: every virtual thread gets its own copy, so libraries that cache expensive objects per thread (formatters, buffers) multiply memory with a million threads. Prefer scoped values or shared thread-safe objects.
  • Downstream limits: the database connection pool (say 50 connections) is still the bottleneck. 10,000 virtual threads waiting for 50 connections just move the queue. Use semaphores or rate limits to protect dependencies.
  • Never pool them, and do not use them for long-running CPU loops that monopolise carriers (the scheduler is not time-sliced).

How it works

  1. Request arrives; a new virtual thread is created.
  2. Blocking I/O unmounts it; carrier serves others.
  3. Pinned code (synchronized on old JDKs, native) holds the carrier.
  4. Shared resources are bounded separately with pools or semaphores.

Example

private final Semaphore partnerApi = new Semaphore(20); // protect downstream

String quote(String id) throws InterruptedException {
    partnerApi.acquire();
    try { return http.send(req(id), BodyHandlers.ofString()).body(); }
    finally { partnerApi.release(); }
}

// Pinning-safe lock on Java 21
private final ReentrantLock lock = new ReentrantLock();
void update() { lock.lock(); try { repo.save(state); } finally { lock.unlock(); } }
java -XX:StartFlightRecording=filename=rec.jfr -jar app.jar   # look for jdk.VirtualThreadPinned

Common mistakes

  • Expecting a CPU-heavy batch job to speed up.
  • Wrapping virtual threads in a fixed thread pool.
  • Ignoring the DB pool and overwhelming dependencies.
  • Heavy per-thread ThreadLocal caches.

How to answer in the interview

"The advantages are huge concurrency for blocking I/O with plain synchronous code: no callbacks or reactive chains, cheap creation so one thread per task, normal stack traces and debugging, and higher throughput without tuning thread pools. The limitations: no benefit for CPU-bound work; on Java 21 to 23, blocking inside synchronized pins the carrier, so I'd use ReentrantLock there or move to Java 24+, which fixed it, though native calls can still pin; ThreadLocal-heavy libraries waste memory; and downstream limits like the database pool still apply, so I may add semaphores. And I never pool virtual threads."

Likely follow-up questions

  • How do you detect pinning? JFR jdk.VirtualThreadPinned events; on 21-23 also -Djdk.tracePinnedThreads.
  • Why not pool them? Pools exist to limit expensive threads; virtual threads are cheap, use semaphores to limit resources.
  • Does Hibernate/JDBC work? Yes, blocking JDBC is the main use case, bounded by the connection pool.
