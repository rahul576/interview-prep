Why might sorted() not work directly for a custom object?

Coding Exercises · concept · levels entry

In one line

The no-argument sorted() uses natural ordering, so elements must implement Comparable; for a plain Product class it compiles but throws ClassCastException at runtime when the terminal operation runs — fix it by implementing Comparable or, more commonly, passing a Comparator.

Detailed explanation

Stream<T>.sorted() is declared without any bound on T, so the compiler accepts it for any stream, including Stream<Product>. Internally, the sort casts each element to Comparable to call compareTo. If Product does not implement Comparable, the cast fails and you get:

java.lang.ClassCastException: class Product cannot be cast to class java.lang.Comparable

Two details make this confusing for beginners:

  • It fails at runtime, not compile time. Java generics are checked at compile time only where bounds exist; sorted() has no T extends Comparable<T> bound because a Stream<T> is generic over all types, and T might be a subtype that is comparable. The method signature cannot express "only callable when T is comparable", so the check moves to runtime.
  • It fails only when the pipeline runs. Streams are lazy, so the exception appears at the terminal operation (toList(), forEach), which may be several lines later. Also, with zero or one element, no comparison happens, so tests with tiny data may even pass.

Collections.sort(list) behaves differently: its signature is <T extends Comparable<? super T>> void sort(List<T>), so the compiler rejects a List<Product> that is not comparable.

Fixes:

  1. Pass a Comparator — the usual answer: sorted(Comparator.comparing(Product::getName)). It is explicit about the order and flexible.
  2. Implement Comparable<Product> — only if there is one obvious natural order for products, such as by SKU or ID. Then sorted() works everywhere, including in TreeSet and TreeMap.

How it works

  1. sorted() is registered as a stateful step.
  2. The terminal operation starts processing.
  3. The sort buffers elements and compares them.
  4. Comparison casts elements to Comparable.
  5. Non-comparable elements throw ClassCastException.

Example

class Product {                     // no Comparable
    private final String name;
    private final double price;
    // ...
}

// compiles, but fails at runtime (with 2+ elements)
List<Product> sorted = products.stream().sorted().toList();
// ClassCastException: class Product cannot be cast to class java.lang.Comparable

// fix 1: comparator
List<Product> byName = products.stream()
        .sorted(Comparator.comparing(Product::getName))
        .toList();

// fix 2: natural order
class Product implements Comparable<Product> {
    @Override public int compareTo(Product o) { return name.compareTo(o.name); }
}

// Collections.sort rejects non-comparable types at compile time
// Collections.sort(productsList);   // compile error if Product is not Comparable

Common mistakes

  • Assuming compilation guarantees sortability.
  • Testing with one element and missing the exception.
  • Implementing Comparable with an arbitrary order just to make sorted() work.
  • Forgetting to make compareTo consistent with equals.

How to answer in the interview

"The no-argument sorted() sorts by natural ordering, which means each element must implement Comparable. A plain Product class doesn't, so the pipeline compiles but fails at runtime with a ClassCastException — Product cannot be cast to Comparable — when the terminal operation runs. It compiles because the Stream signature can't restrict T to comparable types. The fix is either to make Product implement Comparable if there's one obvious natural order, or more commonly to pass a Comparator, like sorted(Comparator.comparing(Product::getName))."

Likely follow-up questions

  • Why runtime and not compile time? Stream<T>.sorted() has no Comparable bound on T; the cast happens inside the sort.
  • Does it fail with one element? No comparison is needed, so it may not fail.
  • What does Collections.sort do instead? Its generic bound makes the compiler reject non-comparable lists.
