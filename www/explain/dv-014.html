What is the difference between HTTP and HTTPS, and what do HTTP status code classes mean?

Networking · concept · levels entry, mid

In one line

HTTPS is HTTP over TLS, adding encryption, integrity and server authentication (port 443 versus 80); status codes are grouped as 2xx success, 3xx redirect, 4xx client error and 5xx server error, with 502, 503 and 504 the classic proxy and outage codes.

Detailed explanation

HTTP sends requests and responses in plain text, so anyone on the path (public Wi-Fi, a compromised router) can read or modify them. HTTPS wraps the same HTTP messages in a TLS connection: traffic is encrypted (confidentiality), integrity-protected (no tampering) and the server's certificate proves its identity. Browsers mark HTTP pages as insecure, many features require HTTPS, and HTTP/2 in browsers works only over TLS. HSTS tells browsers to use HTTPS only. Default ports: 80 for HTTP, 443 for HTTPS.

Status code classes:

  • 1xx informational: 101 Switching Protocols (WebSocket upgrade), 103 Early Hints.
  • 2xx success: 200 OK, 201 Created, 202 Accepted (async), 204 No Content.
  • 3xx redirection: 301 Moved Permanently, 302 Found (temporary), 304 Not Modified (cache validation), 307/308 temporary/permanent redirects that preserve the method.
  • 4xx client errors: 400 Bad Request, 401 Unauthorized (actually means not authenticated), 403 Forbidden (authenticated but not allowed), 404 Not Found, 405 Method Not Allowed, 409 Conflict, 413 Payload Too Large, 429 Too Many Requests (rate limiting).
  • 5xx server errors: 500 Internal Server Error (unhandled exception), 502 Bad Gateway (proxy got an invalid response or connection failure from upstream), 503 Service Unavailable (overloaded, maintenance, or no healthy backends), 504 Gateway Timeout (upstream didn't respond in time).

In DevOps, the source matters: a 502 from NGINX or a cloud load balancer means look at the upstream (crashed app, wrong port, keep-alive mismatch), while a 504 suggests slow upstreams or too-short proxy timeouts. 5xx rates feed SLOs and alerts; 4xx spikes can indicate a bad client release or an attack.

How it works

  1. Client connects to port 443 and completes the TLS handshake.
  2. It sends an HTTP request inside the encrypted channel.
  3. Proxies and the app process it.
  4. A status line and headers describe the outcome.
  5. Monitoring groups responses by class for error rates.

Example

curl -I http://example.com            # often 301 to https
curl -sv https://example.com -o /dev/null 2>&1 | grep -E "SSL connection|subject:|< HTTP"
curl -s -o /dev/null -w "%{http_code}\n" https://api.example.com/health
# NGINX error log hints
# "connect() failed (111: Connection refused) while connecting to upstream"  -> 502
# "upstream timed out (110: Connection timed out)"                          -> 504

Common mistakes

  • Mixing up 401 and 403.
  • Returning 200 with an error message in the body.
  • Treating all 5xx equally instead of checking which component generated them.
  • Using 302 when a permanent 301 or 308 is intended.

How to answer in the interview

"HTTPS is HTTP over TLS: the traffic is encrypted and protected against tampering, and the certificate proves the server's identity. HTTP uses port 80, HTTPS 443. Status codes come in classes: 2xx success like 200 and 201, 3xx redirects like 301 and 302, 4xx client errors like 400, 401 not authenticated, 403 forbidden and 404, and 5xx server errors like 500. In DevOps the proxy codes matter most: 502 when the proxy gets a bad response or can't connect upstream, 503 when no backend is available, and 504 when the upstream times out."

Likely follow-up questions

  • Most likely cause of a 502 from NGINX? The upstream is down, listening on another port or interface, or closing connections unexpectedly; the NGINX error log shows which.
  • 401 versus 403? 401: no or invalid credentials; 403: valid identity but not permitted.
  • What is HSTS? A header telling browsers to always use HTTPS for the domain.
