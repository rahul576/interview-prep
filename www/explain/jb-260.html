What is Mockito, and how do you mock dependencies?

Testing · concept · levels mid, senior

In one line

Mockito is the standard Java mocking framework: create test doubles with mock() or @Mock (with MockitoExtension), stub with when().thenReturn()/thenThrow(), verify interactions with verify(), inspect arguments with ArgumentCaptor, and use spies sparingly.

Detailed explanation

A unit test for OrderService should not need a real database, payment provider or email server. Mockito generates objects implementing the dependency's type at runtime (using ByteBuddy; since Mockito 5 the inline mock maker is default, so final classes and methods can be mocked too). A mock does nothing by default and returns empty values: null, 0, false, empty collections or Optional.empty().

Creating mocks: Mockito.mock(OrderRepository.class) or a field annotated @Mock in a class with @ExtendWith(MockitoExtension.class). @InjectMocks builds the class under test and injects the mocks, though plain constructor calls are clearer.

Stubbing: when(repo.findById(1L)).thenReturn(Optional.of(order)), thenThrow(new TimeoutException()) to simulate failures, thenAnswer(inv -> ...) for computed responses, consecutive answers for retries. Argument matchers (any(), eq(), argThat()) generalise inputs; if you use one matcher, all arguments must be matchers. BDD style uses given(...).willReturn(...). For void methods use doThrow(...).when(mock).method().

Verification: verify(emailService).send(any()), times(2), never(), verifyNoMoreInteractions (use sparingly). ArgumentCaptor captures the actual argument so you can assert its fields, for example the amount in a payment request.

Strictness: MockitoExtension uses strict stubs, failing tests that stub methods never called, which keeps tests clean.

Spies (spy(realObject) or @Spy) call real methods unless stubbed; stub them with doReturn().when(spy) to avoid invoking the real method.

Good practice: mock types you own at architectural boundaries, not value objects, and prefer verifying outcomes over verifying every call.

How it works

  1. MockitoExtension initialises @Mock, @Spy, @Captor and @InjectMocks fields.
  2. Stubs register answers for specific argument patterns.
  3. The code under test calls the mocks; Mockito records invocations.
  4. verify checks recorded invocations against expectations.
  5. Strict stubs report unused stubbings after the test.

Example

@ExtendWith(MockitoExtension.class)
class OrderServiceTest {
    @Mock OrderRepository repo;
    @Mock PaymentClient payments;
    @Captor ArgumentCaptor<ChargeRequest> charge;

    @Test
    void chargesOrderTotal() {
        var service = new OrderService(repo, payments);
        when(repo.findById(1L)).thenReturn(Optional.of(new Order(1L, new BigDecimal("40.00"))));
        when(payments.charge(any())).thenReturn(ChargeResult.ok());

        service.pay(1L);

        verify(payments).charge(charge.capture());
        assertThat(charge.getValue().amount()).isEqualByComparingTo("40.00");
    }

    @Test
    void marksOrderFailedWhenPaymentTimesOut() {
        var service = new OrderService(repo, payments);
        when(repo.findById(1L)).thenReturn(Optional.of(new Order(1L, BigDecimal.TEN)));
        when(payments.charge(any())).thenThrow(new PaymentTimeoutException());

        assertThatThrownBy(() -> service.pay(1L)).isInstanceOf(PaymentFailedException.class);
        verify(repo).save(argThat(o -> o.status() == Status.PAYMENT_FAILED));
    }
}

Common mistakes

  • Mixing raw values and matchers in one call (when(m.f(any(), 5))), causing an error.
  • Over-verifying every interaction, making tests brittle.
  • Mocking value objects, DTOs or third-party types instead of wrapping them.
  • Using when(spy.method()) on a spy, which calls the real method during stubbing.

How to answer in the interview

"Mockito creates test doubles for a class's dependencies, so I can unit test a service without a database or HTTP client. With JUnit 5 I use MockitoExtension and @Mock fields, then construct the class under test with those mocks. I stub behaviour with when-thenReturn, or thenThrow to simulate failures like timeouts, and after calling the code I verify the important interactions, using an ArgumentCaptor to check what was actually passed. Spies wrap real objects for the rare partial-mock case. I avoid mocking value objects or libraries I don't own, and I keep verification focused on outcomes."

Likely follow-up questions

  • Why is over-mocking a smell? Tests mirror the implementation, break on refactoring and miss integration bugs.
  • Can Mockito mock final or static methods? Final yes with the default inline mock maker; static via mockStatic, ideally only for legacy code.
  • What are strict stubs? A mode that fails on unused or mismatched stubbings, catching sloppy tests.
