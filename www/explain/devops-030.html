How do Helm and GitOps tools like Argo CD fit together in your deployment workflow?

Kubernetes · concept · levels senior, lead

In one line

Helm packages manifests as charts (templates + values) for many environments; GitOps makes Git the source of truth, and Argo CD or Flux inside the cluster pull and render the chart, continuously reconciling and correcting drift, while CI only builds images and updates the version in Git.

Detailed explanation

Helm. A chart contains templated manifests plus a default values.yaml; per-environment values files (values-prod.yaml) change replicas, resources, hostnames and image tags. With the Helm CLI, each install is a release with revision history and helm rollback. Charts are versioned and published to a chart repository or an OCI registry.

GitOps. Desired state for every environment lives in Git: which chart version, which values, which image tag. Changes happen through pull requests, giving review and audit history. A controller in the cluster pulls from Git (no CI system holds cluster credentials), applies the desired state and keeps comparing; manual kubectl edit changes show as OutOfSync and are reverted if self-heal is enabled.

How they combine.

  • Argo CD renders the chart itself (equivalent to helm template) and applies the resulting manifests, so it does not create Helm releases; history and rollback are Argo CD sync history or, better, a git revert. Hooks are mapped to Argo CD sync phases.
  • Flux uses its helm-controller, which performs real Helm installs and upgrades from HelmRelease objects, so Helm release history exists, with automatic remediation on failed upgrades.

Workflow. CI builds and tests the application, pushes an image (ideally an immutable tag or digest), then opens a PR or commits that bumps the tag in the environment's values file, or an image automation tool (Argo CD Image Updater, Flux image automation) does it. The controller syncs. Promotion from staging to production is another PR changing the production values to the same version. Tools such as Kargo can automate promotion pipelines.

How it works

  1. Developer merges code; CI builds api:1.8.3 and pushes it.
  2. CI opens a PR updating envs/staging/values.yaml to 1.8.3.
  3. Merge → Argo CD detects the change, renders the chart, syncs staging.
  4. After verification, a PR promotes 1.8.3 to envs/prod.
  5. Rollback = revert the commit; Argo CD syncs back.

Example

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata: { name: api-prod, namespace: argocd }
spec:
  project: shop
  source:
    repoURL: https://github.com/acme/deploy.git
    path: charts/api
    targetRevision: main
    helm:
      valueFiles: [../../envs/prod/api-values.yaml]
  destination: { server: https://kubernetes.default.svc, namespace: shop }
  syncPolicy:
    automated: { prune: true, selfHeal: true }

Common mistakes

  • CI running helm upgrade against production and a GitOps controller at the same time.
  • Mutable tags like latest, so Git does not describe what runs.
  • Expecting helm list/helm rollback to work for Argo CD-managed apps.
  • Secrets in plain values files.

How to answer in the interview

"Helm packages Kubernetes manifests as charts, templates plus values, so one chart serves many environments with different values files, and the Helm CLI tracks releases with rollback. GitOps adds the workflow: Git is the source of truth for each environment and changes go through pull requests. Argo CD or Flux in the cluster pulls the repo, renders the chart and continuously reconciles, correcting drift. Argo CD renders the templates itself, while Flux's helm-controller does real Helm releases. CI only builds images and bumps the tag in Git, so cluster credentials stay in the cluster, every change is audited and rollback is a git revert."

Likely follow-up questions

  • How do you promote staging to production? A PR that sets production values to the version proven in staging, possibly automated with Kargo or image updater.
  • Where do secrets go? External Secrets Operator or Sealed Secrets, not values files.
  • App-of-apps or ApplicationSets? ApplicationSets generate Applications per cluster or environment from one template.
