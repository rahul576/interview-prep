How do you use ElastiCache for Redis, and which caching patterns do you know?

Cloud (AWS) · concept · levels mid

In one line

ElastiCache provides managed in-memory Valkey, Redis OSS or Memcached with sub-millisecond latency; the main pattern is cache-aside (lazy loading) with TTLs, complemented by write-through, and Redis-style data structures power sessions, rate limiting, leaderboards and queues, run in production with cluster mode, replicas and Multi-AZ failover.

Detailed explanation

Cache-aside is the default: the application reads the cache; on a miss it queries the database, stores the result with a TTL, and returns it. On updates it writes to the database and deletes the cache key. It caches only data that is actually read and survives cache outages (just slower), but the first read after expiry is a miss and stale data is possible until TTL or invalidation.

Write-through writes the cache whenever the database is updated, so reads are always warm and fresh, at the cost of extra write latency and caching data nobody reads; combine it with TTLs. Write-behind batches writes to the database later, faster but risky. Add TTL jitter to avoid mass expiry.

Valkey and Redis data structures enable more than caching: sessions in hashes with expiry, rate limiting with INCR and EXPIRE or sliding windows in sorted sets, leaderboards with sorted sets (ZADD, ZREVRANGE), distributed locks, pub/sub and lightweight queues with lists or streams. Memcached is simpler, multi-threaded and only for plain key-value caching without replication or persistence.

Production setup: cluster mode enabled shards data across node groups for horizontal scaling; each shard has replicas in other AZs and automatic failover; enable encryption in transit and at rest, AUTH or RBAC users, place nodes in private subnets, and size memory with an eviction policy such as allkeys-lru. ElastiCache Serverless removes node sizing entirely. Valkey is the open-source fork AWS now promotes, usually at lower price.

How it works

  1. Request arrives; app computes a key like product:42.
  2. GET from cache; hit returns immediately.
  3. Miss: query the database, SET with TTL plus jitter.
  4. On writes: update database, delete or overwrite the key.
  5. Replicas and Multi-AZ keep the cache available during node failure.

Example

def get_product(pid):
    key = f"product:{pid}"
    cached = r.get(key)
    if cached:
        return json.loads(cached)
    row = db.query("SELECT * FROM products WHERE id=%s", pid)
    r.set(key, json.dumps(row), ex=600 + random.randint(0, 120))
    return row

def allow_request(user_id, limit=100):
    key = f"rate:{user_id}:{int(time.time() // 60)}"
    count = r.incr(key)
    if count == 1:
        r.expire(key, 60)
    return count <= limit

Common mistakes

  • No TTLs, so stale data lives forever and memory fills.
  • Treating the cache as the source of truth for critical data.
  • Same TTL for every key, causing cache stampedes.
  • Using KEYS * or large blocking commands in production.

How to answer in the interview

"ElastiCache is managed in-memory Valkey, Redis OSS or Memcached with sub-millisecond reads. My default is cache-aside: check the cache, on a miss read the database and set the value with a TTL, and on updates delete the key. Write-through keeps the cache fresh by writing on every update, at the cost of caching unread data. Redis structures also give me sessions, rate limiters, leaderboards with sorted sets and simple queues. In production I use cluster mode for sharding, replicas across AZs with automatic failover, encryption and auth."

Likely follow-up questions

  • How prevent a cache stampede? Lock or single-flight on rebuild, serve stale while revalidating, and jitter TTLs.
  • Valkey, Redis or Memcached? Valkey or Redis for data structures and replication; Memcached for simple multi-threaded caching.
  • What happens on failover? A replica is promoted; clients reconnect via the primary endpoint, losing only unreplicated writes.
