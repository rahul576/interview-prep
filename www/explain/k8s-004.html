What are native sidecar containers in Kubernetes, and what problems did they fix?

Kubernetes · concept · levels mid, senior

In one line

Native sidecars are init containers with restartPolicy: Always: they start before the app containers, keep running alongside them, are stopped after them on shutdown, and no longer stop Jobs from completing; the feature is GA since Kubernetes 1.33.

Detailed explanation

Sidecars such as service mesh proxies, log shippers, secret agents and Cloud SQL proxies used to be ordinary entries in containers. Kubernetes treated all regular containers as equals, which caused three long-standing problems:

  1. Start-up order: the app could start before the proxy was ready and fail its first network calls.
  2. Jobs never finished: a Job is complete when all containers exit; the sidecar kept running, so the pod never reached Completed.
  3. Shutdown order: on termination all containers got SIGTERM together, so the proxy could exit while the app was still draining requests.

The native design reuses init containers. A container in initContainers with restartPolicy: Always is a sidecar. The kubelet starts it in order like other init containers but does not wait for it to exit; it waits only for it to be started (and for its startupProbe, if defined), then moves on to the next init container and eventually the app containers. It is restarted if it crashes, can have readiness and liveness probes, and contributes to pod readiness. When the main containers finish (a Job) or the pod is terminated, sidecars are stopped after the main containers, in reverse order.

The feature was beta and enabled by default from 1.29 and graduated to stable in 1.33. Istio and other projects use it when the cluster supports it.

How it works

  1. Regular init containers run to completion.
  2. Sidecar init container starts; startupProbe passes.
  3. App containers start, with the proxy already available.
  4. Sidecar runs for the pod's lifetime and restarts on failure.
  5. App exits (Job) or pod terminates → app stops first.
  6. Sidecars receive SIGTERM afterwards.

Example

apiVersion: batch/v1
kind: Job
metadata: { name: nightly-export }
spec:
  template:
    spec:
      restartPolicy: Never
      initContainers:
      - name: log-shipper
        image: fluent/fluent-bit:3.1
        restartPolicy: Always          # makes it a native sidecar
        volumeMounts: [ { name: logs, mountPath: /logs } ]
      containers:
      - name: export
        image: registry.example.com/export:2.0
        volumeMounts: [ { name: logs, mountPath: /logs } ]
      volumes: [ { name: logs, emptyDir: {} } ]

Common mistakes

  • Still putting sidecars in containers on modern clusters.
  • No startupProbe, so the app starts before the sidecar is really ready.
  • Forgetting the sidecar's resources count for the whole pod lifetime.
  • Assuming old clusters (pre-1.29 defaults) support it.

How to answer in the interview

"Native sidecars are init containers with restartPolicy Always. The kubelet starts them in order before the app containers but doesn't wait for them to exit; they keep running for the pod's lifetime and restart if they crash. On shutdown they're stopped after the main containers, so a mesh proxy or log shipper is still there while the app drains. That fixed the old problems: apps starting before the proxy was ready, Jobs never completing because the sidecar kept running, and bad shutdown ordering. It's GA since 1.33, and Istio and logging agents use it."

Likely follow-up questions

  • Old workarounds for Jobs? The app wrote a file or called the proxy's quit endpoint (for example Istio's /quitquitquit) when done.
  • Do sidecars affect pod readiness? Yes, their readiness probes count towards the pod being Ready.
  • How are sidecar resources counted? They're added to the app containers' requests for scheduling, since they run concurrently.
