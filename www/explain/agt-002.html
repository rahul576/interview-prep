Describe the agent loop and the ReAct pattern.

AI Agents & AIOps · concept · levels entry, mid, senior

In one line

An agent runs a loop: the model reasons about the goal and current state, chooses an action (usually a tool call), the runtime returns an observation, and it repeats until done or a stop condition; ReAct (Reason + Act) formalised interleaving reasoning traces with actions and observations.

Detailed explanation

The agent loop is the core of every agent framework. Each iteration the model receives the system instructions, tool definitions and the full history so far: user goal, previous reasoning, tool calls and their results. It produces either a tool call with structured arguments or a final answer. The runtime, not the model, executes the tool, then appends the result to the context as an observation. The model now reasons with new information and decides again.

ReAct, from a 2022 paper by Yao and colleagues, showed that alternating explicit Thought → Action → Observation steps works better than either pure reasoning (chain-of-thought without access to facts, which hallucinates) or pure acting (tool calls without planning, which wanders). Reasoning helps the model decompose the goal, track progress and handle surprises; actions ground the reasoning in real data.

Modern models changed the mechanics but not the idea. Instead of parsing "Action:" text, providers offer native function or tool calling with JSON arguments, often parallel tool calls. Reasoning models think internally before each action, and some support interleaved thinking between tool calls, so the explicit "Thought:" text of the original prompt format is largely unnecessary.

The loop needs stop conditions outside the model: a maximum number of steps, a token or cost budget, a wall-clock timeout, or a repeated-error threshold. A practical consequence of the loop is that context grows every iteration: each step resends everything, so cost grows roughly quadratically with long runs and quality drops as stale information accumulates. That is why long-running agents use compaction, trimming old tool results, prompt caching and sub-agents.

How it works

  1. Build the context: instructions, tools, goal and history.
  2. Model reasons and returns a tool call or final answer.
  3. Runtime validates and executes the tool, capturing result or error.
  4. Result is appended as an observation.
  5. Check limits; repeat from step 2 or stop and report.

Example

Goal: "Why did checkout error rate spike at 14:05?"

Thought: Check recent deployments first.
Action: list_deployments(service="checkout", since="13:30")
Observation: checkout v4.12.0 deployed 14:02
Thought: Correlates. Look at errors after 14:02.
Action: query_logs(service="checkout", level="ERROR", since="14:00", limit=20)
Observation: 1,240x "NullPointerException at PriceService.applyCoupon"
Thought: New coupon code path. Check the diff.
Action: get_diff(service="checkout", from="v4.11.3", to="v4.12.0", path="PriceService")
Observation: coupon.getRules() now may return null
Final answer: Regression in v4.12.0 (null coupon rules). Recommend rollback to v4.11.3.

Common mistakes

  • Letting the model decide when to stop without hard limits.
  • Ignoring context growth and its effect on cost and quality.
  • Executing tool calls without validating arguments.
  • Assuming you still need text-parsed "Action:" formats with native tool calling.

How to answer in the interview

"An agent runs a loop. The model gets the goal, instructions, tools and history; it reasons about where it is and either calls a tool or gives the final answer. The runtime executes the tool and appends the result as an observation, and the model decides again, until it is done or a stop condition, like a step limit, budget or timeout, kicks in. ReAct, reasoning plus acting, formalised this interleaving of thoughts, actions and observations, which grounds reasoning in real data and makes tool use much better than acting blindly. Today it is implemented with native tool calling and reasoning models. The practical catch is that context grows each iteration, so long runs need compaction to control cost and quality."

Likely follow-up questions

  • How do reasoning models change ReAct? Reasoning happens internally, sometimes interleaved between tool calls, so prompts no longer need explicit thought formats.
  • Why must the runtime execute tools? For validation, permissions, logging and safety; the model only proposes.
  • What are parallel tool calls? The model requests several independent tools in one step to save latency.
