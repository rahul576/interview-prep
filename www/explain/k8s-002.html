What is the difference between kubectl create, kubectl apply and server-side apply?

Kubernetes · concept · levels entry, mid

In one line

kubectl create is imperative and fails if the object exists; kubectl apply is declarative, doing a three-way merge using the last-applied annotation; server-side apply (SSA) moves merging into the API server and tracks field ownership in managedFields, reporting conflicts when managers disagree.

Detailed explanation

kubectl create -f says "make this object". If it already exists you get AlreadyExists. It is fine for one-off tasks, like generating a Secret or a Job, but not for repeatable pipelines.

Client-side kubectl apply says "make the object look like this". kubectl compares three versions: the live object, the new manifest, and the previous manifest stored in the kubectl.kubernetes.io/last-applied-configuration annotation. That three-way merge lets it remove fields you deleted from your file while keeping fields other actors set, such as status or a sidecar injected by a webhook. Its weaknesses are a large annotation, merge logic in the client, and no real notion of who owns what.

Server-side apply (kubectl apply --server-side, GA since 1.22) sends the desired fields to the API server, which merges them and records, per field, which field manager set it, in metadata.managedFields. If another manager already owns a field you try to change, the request fails with a conflict unless you use --force-conflicts to take ownership. This makes shared ownership safe and explicit: Helm or Argo CD owns most of a Deployment, the HPA owns spec.replicas, a mesh webhook owns injected fields. Controllers written with SSA can also apply partial objects, sending only the fields they care about. Argo CD and Flux support SSA, and it is the recommended approach for controllers.

How it works

  1. create: POST the object; error if it exists.
  2. Client-side apply: GET live object, compute three-way patch, PATCH, update annotation.
  3. SSA: PATCH with application/apply-patch+yaml and a field manager name.
  4. API server merges and updates managedFields.
  5. Conflicting ownership → 409 Conflict, unless forced.

Example

kubectl create deployment demo --image=nginx            # imperative
kubectl apply -f deploy.yaml                            # client-side apply
kubectl apply --server-side --field-manager=ci -f deploy.yaml
kubectl get deploy orders --show-managed-fields -o yaml | grep -A3 manager:
# Let the HPA own replicas: simply omit spec.replicas from the applied manifest
spec:
  # replicas: 3   <- removed
  template: ...

Common mistakes

  • Using create in CI and getting failures on reruns.
  • Keeping replicas in manifests while an HPA scales the Deployment.
  • Using --force-conflicts by default, hiding real ownership fights.
  • Mixing kubectl edit with GitOps-managed objects.

How to answer in the interview

"kubectl create is imperative: it creates the object and fails if it exists. kubectl apply is declarative: kubectl does a three-way merge between the live object, the new manifest and the last-applied annotation, so removed fields get removed. Server-side apply moves that into the API server, which tracks which field manager owns each field in managedFields and raises a conflict when two managers try to own the same field. That's what lets a pipeline, Helm and an HPA share an object safely. For repeatable changes I use apply, preferably server-side, from CI or a GitOps tool."

Likely follow-up questions

  • Why does an HPA fight a pipeline with fixed replicas? Each apply resets replicas, then the HPA changes it back; remove replicas from the manifest.
  • How do you migrate from client-side to server-side apply? kubectl handles the ownership transfer; apply with --server-side once.
  • What is a field manager? The identity recorded for each owned field, for example kubectl, helm or a controller name.
