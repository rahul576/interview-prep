How do you evaluate an AI agent, beyond checking its final answer?

AI Agents & AIOps · concept · levels senior, lead

In one line

Evaluate agents on task success rate in realistic, verifiable task suites, trajectory quality (tool choice and order), tool-call accuracy, efficiency (steps, tokens, cost, latency), and safety (unauthorised actions, policy violations), with repeated runs to measure variance and track it across versions.

Detailed explanation

A correct final answer can hide a terrible path: ten unnecessary steps, a destructive command that happened not to matter, or a lucky guess. So agent evaluation has several dimensions.

Task success is the headline metric. Each task has an environment and a verifiable outcome, ideally checked by code: the bug is fixed and the hidden tests pass, the ticket exists with the right fields, the database row has the correct value. Public benchmarks such as SWE-bench Verified, tau-bench and Terminal-Bench follow this idea, but your own tasks, drawn from real usage, matter most.

Trajectory evaluation inspects the path: did the agent choose appropriate tools in a sensible order, avoid redundant steps, recover from errors, and ask for clarification when needed? It can be scored against reference trajectories, by rules ("must call get_customer before refund"), or by an LLM judge with a rubric, calibrated against human ratings.

Tool-call accuracy checks that the right tool was selected and the arguments were valid and correct.

Efficiency measures steps, tokens, cost and latency per task. Two agents with equal success rates can differ fivefold in cost.

Safety checks for unauthorised or destructive actions, policy violations, data leakage and behaviour under adversarial inputs such as prompt injection in tool results.

Because agents are non-deterministic, each task runs several times. Metrics like pass@k (succeeds at least once in k tries) and pass^k (succeeds in all k tries, important for reliability) show consistency. Results are tracked per version of model, prompt and tools, and broken down by task category.

How it works

  1. Collect realistic tasks from real usage, including edge cases and failures.
  2. Build sandboxed environments with programmatic success checks.
  3. Run each task several times per agent version.
  4. Score success, trajectory, tool accuracy, efficiency and safety.
  5. Calibrate LLM judges against human labels.
  6. Compare versions per category; gate releases on thresholds.

Example

task: refund_damaged_item_017
environment: crm_sandbox_fixture_v3
prompt: "Customer anna@example.com says order 8812 arrived broken. Handle it."
success_checks:
  - sql: "SELECT status FROM refunds WHERE order_id=8812"   # expect 'approved'
  - no_calls_to: [delete_customer, update_price]
trajectory_rules:
  - must_call_before: { first: get_order, then: create_refund }
limits: { max_steps: 12, max_cost_usd: 0.50 }
runs: 5
metrics: [success_rate, pass_all_5, avg_steps, avg_cost, safety_violations]

Common mistakes

  • Only checking the final text.
  • Single runs per task, hiding variance.
  • Uncalibrated LLM judges.
  • Toy tasks unlike production traffic.
  • Ignoring cost and latency.

How to answer in the interview

"Final answers hide how the agent got there, so I evaluate several dimensions. The headline is task success on realistic tasks with verifiable outcomes, checked by code in a sandbox, like tests passing or a record being correct. Then trajectory: did it pick the right tools in a sensible order, avoid useless steps and ask for help when appropriate, scored by rules, reference paths or a calibrated LLM judge. Tool-call accuracy checks arguments. Efficiency covers steps, tokens, cost and latency, because equal success can mean five times the cost. Safety checks for unauthorised actions, including under injection. And I run each task several times, because agents vary, and track results across versions."

Likely follow-up questions

  • How do you build a sandbox where actions are verifiable? Containers or seeded test databases and mocked APIs, reset per run, with state checks after.
  • pass@k vs pass^k? pass@k measures capability; pass^k measures reliability across all runs.
  • Where do tasks come from? Production traces, support tickets, failure cases and expert-written edge cases.
