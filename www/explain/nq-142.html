How does double-checked locking work in Singleton implementation?

Design Patterns · concept · levels mid

In one line

Double-checked locking checks the instance without a lock first, then enters a synchronized block and checks again before creating it, so only the first creation pays for locking; the field must be volatile to prevent publishing a half-built object.

Detailed explanation

The goal is lazy initialisation that is thread-safe but cheap after the first call. A fully synchronized getInstance() is correct, yet every call acquires the monitor even though the instance only needs creating once.

Double-checked locking (DCL) splits the work:

  1. First check (no lock): if instance is non-null, return it immediately. After initialisation this is the path every call takes, costing only a volatile read.
  2. Lock: if it is null, enter synchronized (Singleton.class).
  3. Second check (inside the lock): while this thread waited for the lock, another thread may already have created the instance. Checking again prevents creating a second one.
  4. Create and assign if still null; leave the block, releasing the lock.

Why volatile? instance = new Singleton() involves allocating memory, running the constructor and writing the reference. Without volatile, the JIT or CPU may let other threads observe the reference before the constructor's writes are visible. A thread taking the fast path could then use a partially initialised object. Since Java 5 (JSR-133 memory model), a volatile write happens-before every later read of that field, fixing the problem. Before Java 5, DCL was broken even with volatile.

A common refinement reads the volatile field into a local variable once, reducing volatile reads. In practice, the holder idiom or an enum gives the same laziness with simpler, less error-prone code, so DCL is mostly an interview topic and useful for lazily initialised instance fields where holders do not apply.

How it works

  1. Read instance; if non-null, return.
  2. Acquire the class lock.
  3. Read again; if non-null, release and return.
  4. Construct, assign to the volatile field, release the lock.
  5. Later callers see the fully constructed object through the volatile read.

Example

public final class Singleton {
    private static volatile Singleton instance;
    private Singleton() {}

    public static Singleton getInstance() {
        Singleton local = instance;           // one volatile read on fast path
        if (local == null) {                  // 1st check, no lock
            synchronized (Singleton.class) {
                local = instance;
                if (local == null) {          // 2nd check, with lock
                    instance = local = new Singleton();
                }
            }
        }
        return local;
    }
}

Common mistakes

  • Omitting volatile.
  • Omitting the second check, allowing two instances.
  • Synchronising on a different, non-shared object.
  • Using DCL where the holder idiom is simpler.

How to answer in the interview

"getInstance first checks if the instance is null without locking; if it already exists it returns straight away, so the common path is cheap. Only if it's null does the thread synchronise on the class, and inside it checks again, because another thread may have created it while this one was waiting. If still null it creates and assigns it. The field has to be volatile, otherwise another thread could see a non-null reference to a partially constructed object. In practice I'd usually prefer the holder idiom or an enum, which are simpler."

Likely follow-up questions

  • Why is the second null check needed? Two threads can pass the first check; the second, inside the lock, ensures only one creates the object.
  • Why is volatile needed? It prevents reordering and guarantees visibility of the fully constructed object.
  • Why not just synchronise the whole method? Correct but every call pays for the lock.
