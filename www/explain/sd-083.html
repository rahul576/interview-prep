Design an LLM gateway that all teams in a company use to access several model providers.

AI & ML System Design · design · levels senior, lead

In one line

An LLM gateway offers a unified API across providers, central keys and authentication, per-team token quotas and rate limits, cost tracking/chargeback, routing and fallback, caching (including semantic), and guardrails like PII redaction and logging, while staying highly available and streaming-friendly.

Detailed explanation

Without a gateway, every team embeds provider SDKs and API keys, nobody knows total spend, and an outage at one provider breaks every app.

Unified API: often OpenAI-compatible, so apps switch models by name (claude-sonnet, gpt-…, llama-internal). Provider keys live in a vault; teams authenticate with their own identities.

Quotas: limits in tokens per minute and spend per month per team/app, protecting shared provider rate limits and budgets. Priorities ensure interactive traffic beats batch jobs.

Cost tracking: log model, input/output tokens, latency and cost per request; dashboards and chargeback per team.

Routing & fallback: policy-based routing (cheap model for classification, strong model for reasoning), and failover to another region or provider on 429/5xx, with circuit breakers. Beware behaviour differences between models; fallback should be tested per use case.

Caching: exact-match caching for repeated prompts (deterministic settings); semantic caching (embedding similarity) only where answers aren't personalised and slight variation is OK.

Guardrails: PII detection/redaction before data leaves, prompt-injection and content filters, logging with retention rules (and opt-outs for sensitive apps).

How it works

  1. App → gateway (auth, quota check) → policy (model, redaction) → cache lookup.
  2. Provider call (streaming) → response filters → log tokens and cost.
  3. Errors → retry/fallback per policy.

Example

route: summarise-tickets
primary: claude-haiku
fallback: [gpt-mini-eu, llama-internal]
limits: { tokens_per_minute: 200000, monthly_budget_usd: 1500 }
guardrails: { redact_pii: true, log_prompts: true, retention_days: 30 }
cache: { exact: true, semantic: false }

Common mistakes

  • Semantic caching for user-specific answers (data leaks).
  • Gateway that buffers instead of streaming.
  • No per-team limits (one job exhausts the org quota).
  • Blind fallback to a model with different safety or quality.

How to answer in the interview

"All teams call one gateway with an OpenAI-compatible API. It holds provider keys centrally, authenticates teams, enforces token-based quotas and budgets, and logs tokens and cost for chargeback. Routing policies choose models and fail over between providers or regions. It caches identical prompts, and semantic caching only where safe. Guardrails redact PII and filter content, and the gateway must stream and be highly available."

Likely follow-up questions

  • When is semantic caching wrong? Personalised, time-sensitive or precise questions with similar wording.
  • Data residency? Route EU tenants to EU-hosted endpoints.
  • Build or buy? LiteLLM, Portkey, cloud API management as starting points.
