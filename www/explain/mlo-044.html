How do you design an A/B test for a new model, and what statistical pitfalls do you avoid?

MLOps · concept · levels mid, senior

In one line

Randomly assign units (usually users) to control and treatment with consistent assignment, define a primary metric and guardrails upfront, size the test with a power calculation covering full weekly cycles, and avoid peeking, novelty effects, multiple comparisons and interference; judge results on the pre-registered metrics.

Detailed explanation

Offline metrics don't guarantee business impact, so an online A/B test compares the current model (control) with the new one (treatment) on real users.

Randomisation and assignment. Choose the randomisation unit: usually users, sometimes sessions or stores. Assignment must be consistent—hash the user ID with an experiment salt—so a user always sees the same variant. Check for sample ratio mismatch: if you planned 50/50 and see 52/48, assignment or logging is broken.

Metrics before starting. One primary metric (conversion, revenue per user, click-through), guardrail metrics that must not get worse (latency, error rate, complaints, unsubscribes, fraud losses), and the minimum detectable effect worth acting on.

Power and duration. A power calculation (typically 80 percent power, 5 percent significance) gives the sample size; run for full weekly cycles (at least one or two weeks) to cover weekday effects.

Pitfalls. Peeking—checking daily and stopping when significant—inflates false positives far above 5 percent unless you use sequential testing methods (for example always-valid p-values or group-sequential designs). Novelty and primacy effects fade or grow after the first days. Multiple comparisons: testing many metrics and segments and reporting whichever is significant; correct for it or treat as exploratory. Interference: users in different groups share inventory, drivers or ad budgets, violating independence; use cluster or switchback designs. Also beware variance: CUPED (using pre-experiment data) reduces it and shortens tests.

How it works

  1. Write the hypothesis, primary metric, guardrails and MDE.
  2. Compute sample size and duration.
  3. Implement hashing-based assignment and exposure logging.
  4. Check sample ratio and data quality early, without judging results.
  5. Run to planned end or use a sequential method.
  6. Analyse pre-registered metrics; treat segment findings as hypotheses.

Example

import hashlib
from statsmodels.stats.power import NormalIndPower
from statsmodels.stats.proportion import proportion_effectsize

def variant(user_id, exp="ranker-v9", split=0.5):
    h = int(hashlib.sha256(f"{exp}:{user_id}".encode()).hexdigest(), 16) % 10_000
    return "treatment" if h < split * 10_000 else "control"

es = proportion_effectsize(0.042, 0.040)      # 4.0 % -> 4.2 % conversion
n = NormalIndPower().solve_power(es, power=0.8, alpha=0.05)
print(round(n))                               # users needed per arm

Common mistakes

  • Stopping early when the p-value first dips below 0.05.
  • Changing the primary metric after seeing results.
  • Ignoring sample ratio mismatch.
  • Running for three days and missing weekly patterns.

How to answer in the interview

"I randomly assign users to control and treatment with consistent hashing so each user always sees the same model. Before starting, I define the primary metric, guardrails like latency and complaints, and the minimum effect worth detecting, then run a power calculation and cover full weekly cycles. The pitfalls I avoid are peeking and stopping early, unless we use sequential testing; novelty effects; the multiple comparisons problem across metrics and segments; and interference between groups. I check sample ratio mismatch and judge only on pre-registered metrics."

Likely follow-up questions

  • When is a multi-armed bandit better? When you want to minimise regret during the test, such as short campaigns, and care less about precise effect estimates.
  • What is CUPED? Variance reduction using each user's pre-experiment metric.
  • What if guardrails fail but the primary metric wins? Don't ship; investigate the trade-off.
