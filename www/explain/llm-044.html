Design an enterprise knowledge assistant over 50,000 internal documents from several systems.

LLMOps & RAG · design · levels senior, lead

In one line

Build connectors with incremental sync of content and permissions, layout-aware parsing and structure-aware chunking with metadata, a hybrid index with reranking and filters, per-user permission filtering via SSO, grounded answers with citations and "I don't know", and an operating layer of evaluation, feedback, monitoring, cost controls and content ownership.

Detailed explanation

50,000 documents is moderate in size; the hard parts are heterogeneous sources, permissions, quality and operations, not raw scale.

Ingestion. One connector per system (SharePoint/OneDrive via Microsoft Graph, Confluence, file shares, Jira or ServiceNow knowledge) with incremental sync of new, changed and deleted documents and their ACLs. A queue decouples connectors from processing. Documents pass through layout-aware parsing, structure-aware chunking (by headings, with title and section path prepended) and enrichment with metadata: source, owner, language, date, version, status, allowed principals.

Index. A store that supports hybrid search (BM25 plus vectors) and filters: Azure AI Search, OpenSearch/Elasticsearch, or a vector database with keyword support. 50,000 documents may be one to two million chunks, easily handled by one well-sized cluster.

Query path. SSO (Entra ID, Okta) gives the user identity; group memberships are resolved and cached. The question plus chat history is rewritten into a standalone query, metadata filters are extracted, hybrid search runs with the permission filter, a reranker selects the top chunks, and the model answers only from them, citing sources and saying "I don't know" when unsupported. The UI shows citations with links, dates and feedback buttons.

Operations. An evaluation set with regression tests in CI; tracing and user feedback; dashboards for quality, latency, cost and failed syncs; logging with redaction and retention limits; a gateway for model access, quotas and fallbacks; and clear content ownership, since the assistant exposes outdated or contradictory documents that source teams must fix.

How it works

  1. Connectors -> queue -> parse -> chunk -> enrich -> embed -> hybrid index (with ACLs).
  2. User signs in with SSO; groups resolved.
  3. Rewrite query; extract filters.
  4. Hybrid search with permission and metadata filters; rerank.
  5. Grounded generation with citations via LLM gateway.
  6. Trace, collect feedback, evaluate, monitor.

Common mistakes

  • Ignoring permissions until a pilot leaks something.
  • Indexing everything, including outdated and duplicate content.
  • No evaluation set, so quality debates are anecdotal.
  • No owner for content quality.

How to answer in the interview

"I'd build connectors per source with incremental sync of content, deletions and permissions. Documents go through layout-aware parsing, heading-based chunking and metadata enrichment into a hybrid index like Azure AI Search or OpenSearch. Users sign in with SSO; each question is rewritten into a standalone query, filtered by the user's groups and metadata, reranked, and answered only from the top chunks with citations and an honest 'I don't know'. Around it I'd have an evaluation set in CI, tracing and feedback, monitoring of quality, latency, cost and sync health, privacy-aware logging, and content owners in each source team."

Likely follow-up questions

  • Phased rollout? Start with one or two low-risk sources and a pilot group; expand sources and users as evals and feedback allow.
  • Multilingual content? Multilingual embeddings, language metadata, answer in user's language.
  • Duplicates across systems? Near-duplicate detection with hashes or embeddings; prefer canonical source.
