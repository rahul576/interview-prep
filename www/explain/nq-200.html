What is the purpose of the @Transactional annotation?

Spring Framework · concept · levels entry, mid

In one line

@Transactional declares a transaction boundary on a method or class so all database work inside commits or rolls back together; attributes set propagation, isolation, readOnly, timeout and rollback rules, it rolls back on unchecked exceptions by default, and works only for calls through the Spring proxy.

Detailed explanation

A business operation such as "place an order" usually performs several writes: insert the order, insert order lines, reduce stock, record a payment. These must be atomic. @Transactional lets you declare that boundary instead of writing begin, commit and rollback code by hand.

Place it on a method, or on a class to apply to all its public methods (a method-level annotation overrides the class-level one). Spring creates a proxy that starts a transaction before the method, shares the same connection with every repository called inside, and commits at the end.

Key attributes:

  • propagation: REQUIRED (default) joins an existing transaction or creates one; REQUIRES_NEW runs independently.
  • isolation: e.g. READ_COMMITTED or SERIALIZABLE; default uses the database setting.
  • readOnly: optimisation hint for queries.
  • timeout: seconds before the transaction is rolled back.
  • rollbackFor / noRollbackFor: change the default rules.

By default it rolls back on RuntimeException and Error and commits on checked exceptions, so many teams add rollbackFor = Exception.class or use unchecked exceptions.

It belongs on the service layer, where a method represents one business use case. Controllers should not hold transactions across HTTP concerns, and putting it only on repositories would give each call its own transaction, losing atomicity across them (Spring Data repository methods are already transactional individually).

Because it is proxy-based, it applies only when the call comes from outside the bean: internal this.method() calls don't start a transaction, and private methods are never transactional. Use jakarta.transaction.Transactional or Spring's org.springframework.transaction.annotation.Transactional; Spring's version has more attributes.

How it works

  1. Spring finds @Transactional and proxies the bean.
  2. A caller invokes the method through the proxy.
  3. The proxy begins or joins a transaction per propagation.
  4. Repository calls use the thread-bound connection.
  5. Return: commit. Matching exception: rollback.

Example

@Service
public class OrderService {
    @Transactional
    public Order placeOrder(PlaceOrder cmd) {
        Order order = orderRepo.save(new Order(cmd.customerId()));
        cmd.lines().forEach(l -> {
            lineRepo.save(new OrderLine(order, l.sku(), l.qty()));
            stockRepo.decrement(l.sku(), l.qty());   // throws if insufficient -> all rolled back
        });
        return order;
    }

    @Transactional(readOnly = true)
    public List<OrderView> history(long customerId) { return orderRepo.findViews(customerId); }
}

Common mistakes

  • Putting it on controllers or only on repositories.
  • Self-invocation and private methods.
  • Relying on rollback for checked exceptions.
  • Very long transactions spanning remote calls or user think-time.

How to answer in the interview

"@Transactional declares that a method, or all public methods of a class, should run in a transaction, so all database work either commits together or rolls back together. Attributes configure propagation, isolation, timeout, readOnly and rollback rules. By default it rolls back on RuntimeException and Error but commits on checked exceptions unless I add rollbackFor. I put it on service methods that represent a business operation, like placing an order. Because it works through a proxy, it only applies to external calls to the bean; internal calls with this don't start a transaction."

Likely follow-up questions

  • Why service layer, not controller or repository? The service method is the unit of work; repositories alone lose atomicity, controllers mix in web concerns.
  • Class-level vs method-level? Method level overrides class level.
  • Does it work on interfaces? It's recommended on concrete classes; interface annotations work only in some proxy modes.
