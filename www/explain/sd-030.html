Design a ticket booking system like Ticketmaster for high-demand concerts.

Classic Design Problems · design · levels mid, senior, lead

In one line

A high-demand ticketing system serves browsing from caches/CDN, protects booking with a virtual waiting room, uses temporary seat holds with expiry and atomic conditional updates to prevent double booking, and confirms after payment within the hold window.

Detailed explanation

Hundreds of thousands of fans arrive at 10:00 for 40,000 seats. The read side (event pages, seat maps) is cached aggressively; seat availability on the map can be slightly stale. The write side must be strictly correct: one seat, one buyer.

The waiting room (queue-it style) admits users at a rate the booking system can handle and gives fairness (randomised or first-come positions). Once admitted, selecting seats creates a hold: a conditional update status = HELD, holder = u, expires_at = now()+10 min WHERE status = AVAILABLE. Only one transaction can win. Payment must complete before expiry; then the seat becomes SOLD. Expired holds return to AVAILABLE via a sweeper or lazy check.

Seats are partitioned by event (and section) so contention stays local. Bot protection (rate limits, device fingerprinting, verified fan programmes, CAPTCHAs) keeps scalpers from grabbing inventory.

How it works

  1. User joins waiting room → gets token when admitted.
  2. Seat map from cache (refreshed every few seconds / pushed deltas).
  3. Hold seats atomically (DB conditional update or Redis SET NX EX).
  4. Pay with idempotency key → confirm booking in a transaction (HELD by u → SOLD).
  5. Release on expiry or payment failure.

Example

UPDATE seats SET status='HELD', holder=$user, hold_expires=now()+interval '10 min'
WHERE event_id=$e AND seat_id = ANY($seats) AND status='AVAILABLE';
-- if rows updated < requested seats → roll back and tell user some seats are taken

Common mistakes

  • Checking availability then updating in two steps (race).
  • No expiry on holds (inventory locked forever).
  • Letting the full spike hit the database.
  • Exact real-time seat maps for everyone (very expensive; approximate is fine).

How to answer in the interview

"Reads are cached; the hard part is the write spike and correctness. A virtual waiting room meters users in. Selecting seats places a time-limited hold using an atomic conditional update, so two users can't hold the same seat. Payment must finish within the hold window, then the seat is marked sold; otherwise it's released. Seats are partitioned per event and bots are filtered with rate limits and verification."

Likely follow-up questions

  • Keep seat maps fresh cheaply? Cache with short TTL, push deltas over WebSockets, show 'selected seats may be taken'.
  • Payment succeeded but hold expired? Extend holds during payment or refund automatically.
  • General admission vs reserved seats? GA is a counter decrement; reserved needs per-seat state.
