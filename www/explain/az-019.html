How do pods in AKS securely access Azure resources such as Key Vault or Storage?

Azure Kubernetes (AKS) · concept · levels mid, senior

In one line

Use Microsoft Entra Workload ID: the cluster's OIDC issuer issues tokens to a Kubernetes service account, a federated credential on a user-assigned managed identity trusts that service account, and the Azure SDK exchanges the projected token for an Entra token, so no secrets live in the cluster.

Detailed explanation

Pods often need to reach Azure resources: Key Vault for secrets, Storage for files, Service Bus for messages. Storing a client secret in a Kubernetes Secret is risky: secrets are only base64-encoded by default, they leak through manifests or logs, and they need rotation.

Workload identity builds on OIDC federation. When enabled, the AKS cluster exposes an OIDC issuer URL, and Kubernetes issues projected service account tokens signed by the cluster. In Entra ID, you create a user-assigned managed identity (or app registration) and add a federated identity credential that says: "trust tokens from this issuer whose subject is system:serviceaccount:<namespace>:<service-account> with audience api://AzureADTokenExchange".

In the cluster you create a service account annotated with the identity's client ID, and label the pod with azure.workload.identity/use: "true". A mutating webhook then injects environment variables (client ID, tenant ID, token file path) and mounts the projected token. The Azure Identity SDK (DefaultAzureCredential or WorkloadIdentityCredential) reads the token and exchanges it with Entra ID for an access token. Permissions are controlled by RBAC role assignments on the target resource, such as Key Vault Secrets User.

This replaced AAD Pod Identity, which relied on intercepting IMDS calls through a node-level component; it was deprecated and is retired. Workload identity is standards-based, works for any OIDC-trusting service, and scopes identity per service account rather than per node.

How it works

  1. Enable the OIDC issuer and workload identity on the cluster.
  2. Create a user-assigned managed identity; grant RBAC on the target.
  3. Create a federated credential for the namespace and service account.
  4. Create the annotated service account; label pods to use it.
  5. Webhook injects token and environment variables.
  6. SDK exchanges the token for an Entra access token and calls the resource.

Example

az aks update -g rg-aks -n aks-prod --enable-oidc-issuer --enable-workload-identity
ISSUER=$(az aks show -g rg-aks -n aks-prod --query oidcIssuerProfile.issuerUrl -o tsv)
az identity create -g rg-aks -n id-orders
az identity federated-credential create -g rg-aks --identity-name id-orders \
  -n fc-orders --issuer "$ISSUER" \
  --subject system:serviceaccount:orders:orders-sa --audience api://AzureADTokenExchange
apiVersion: v1
kind: ServiceAccount
metadata:
  name: orders-sa
  namespace: orders
  annotations:
    azure.workload.identity/client-id: "<client-id-of-id-orders>"
---
# in the Deployment pod template
metadata:
  labels:
    azure.workload.identity/use: "true"
spec:
  serviceAccountName: orders-sa

Common mistakes

  • Subject mismatch: wrong namespace or service account name in the federated credential.
  • Forgetting the pod label, so no token is injected.
  • Granting the identity broad roles instead of a resource-scoped data role.
  • Using old SDK versions that do not support workload identity.
  • Continuing to use the retired pod identity add-on.

How to answer in the interview

"I use Microsoft Entra Workload ID. The cluster has its OIDC issuer enabled. I create a user-assigned managed identity and a federated credential that trusts tokens for a specific Kubernetes service account in a specific namespace. The service account is annotated with the identity's client ID, pods are labelled to use workload identity, and they receive a projected token that the Azure SDK exchanges for an Entra token. No secrets are stored in the cluster, and access is controlled with least-privilege RBAC on the target resource, like Key Vault Secrets User on one vault. It replaces the deprecated pod identity add-on."

Likely follow-up questions

  • How would you troubleshoot a pod getting 403 from Key Vault? 403 means authenticated but not authorised: check role assignment, scope, vault permission model and network rules; 401 would point to federation issues.
  • Can several service accounts use one identity? Yes, with one federated credential per subject.
  • How does this compare with AWS IRSA? Same OIDC federation pattern.
