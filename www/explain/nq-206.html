What is the difference between GET, POST, PUT, PATCH, and DELETE?

REST & API Design · concept · levels entry

In one line

GET reads (safe, idempotent, cacheable, no body); POST creates with a server-assigned id and 201 (not idempotent); PUT sends the complete representation and replaces it (idempotent, missing fields cleared); PATCH sends only changed fields; DELETE removes (idempotent, 204, a repeat may give 404).

Detailed explanation

Take an order resource to make the differences concrete.

GET /orders/42 returns the order with 200 OK, or 404 if it does not exist. It changes nothing (safe), repeating it is harmless (idempotent), and responses can be cached. It has no request body; filters go in the query string: GET /orders?status=PAID.

POST /orders with a body creates a new order. The server assigns the id and responds 201 Created with Location: /orders/43. Sending the same POST twice creates two orders, so POST is not idempotent. To make retries safe, clients send an Idempotency-Key header.

PUT /orders/42 sends the complete new representation, and the server replaces the stored order with it. If the body omits deliveryNotes, that field is cleared. Sending the same PUT again results in the same state, so PUT is idempotent. It returns 200 with the body or 204; it can return 201 if the resource was created at that URI.

PATCH /orders/42 sends only the fields to change, e.g. {"status":"SHIPPED"} as JSON Merge Patch. Other fields are untouched. It saves bandwidth and avoids overwriting concurrent edits to other fields. It is not guaranteed idempotent (an "append item" operation would add twice).

DELETE /orders/42 removes the order and typically returns 204 No Content. Repeating it leaves the order deleted, so it is idempotent, even though the second call may return 404: idempotency is about server state, not identical responses. Many systems implement soft delete (a deleted flag) for audit reasons; the API semantics stay the same.

Use If-Match with an ETag on PUT/PATCH/DELETE to avoid lost updates, returning 412 if the version changed.

How it works

  1. Pick the method by intent: read, create, replace, modify, remove.
  2. Server applies the change and returns the fitting status.
  3. Idempotent methods may be retried; POST needs a key.
  4. Concurrency handled with ETag and If-Match.

Example

POST /orders                    -> 201 Created, Location: /orders/43
{"customerId": 7, "items": [{"sku": "A1", "qty": 2}], "deliveryNotes": "Ring bell"}

PUT /orders/43                  -> 200 OK  (deliveryNotes omitted, so cleared)
{"customerId": 7, "items": [{"sku": "A1", "qty": 3}], "status": "NEW"}

PATCH /orders/43                -> 200 OK  (only status changes)
Content-Type: application/merge-patch+json
{"status": "SHIPPED"}

DELETE /orders/43               -> 204 No Content
DELETE /orders/43               -> 404 Not Found (state unchanged)

Common mistakes

  • Using PUT for partial updates and wiping data.
  • Returning 200 instead of 201 for creation.
  • Treating a 404 on repeated DELETE as breaking idempotency.
  • Using GET with side effects.

How to answer in the interview

"GET /orders/42 reads the order; it's safe, idempotent and cacheable, with no body. POST /orders creates a new order with a server-assigned id and returns 201 Created; repeating it creates another order, so it isn't idempotent. PUT /orders/42 sends the complete representation and replaces the resource; repeating it gives the same result, so it's idempotent, but missing fields get cleared. PATCH sends only the fields to change, like the status. DELETE removes the order, usually with 204; repeating it leaves it deleted, so it's idempotent even if the second call returns 404."

Likely follow-up questions

  • Which status code should a successful DELETE return? 204 No Content, or 200 if you return a body.
  • How do you prevent lost updates with PUT? ETag with If-Match, returning 412 on mismatch.
  • Can POST be idempotent? With an idempotency key, the server can make it so.
