What is Kubernetes, and what problems does it solve?

Kubernetes · concept · levels entry

In one line

Kubernetes is an open-source container orchestration platform: you declare the desired state of your applications and it schedules containers (in pods) across a cluster of nodes, self-heals them, scales them, rolls out updates, and provides service discovery and load balancing.

Detailed explanation

Running one container with docker run is easy. Running hundreds of containers for dozens of services across fifty servers is not: someone has to choose which server has room, restart processes that crash, replace everything that was on a server that died, add copies under load, update versions without downtime, and let services find each other while their IP addresses keep changing. Doing that with scripts is fragile. Kubernetes, originally from Google and now a CNCF project, automates all of it.

The key idea is declarative desired state. You write YAML that says "run 3 replicas of orders:1.4, each needing 250m CPU and 256Mi memory, reachable as the service orders". You submit it to the API server, which stores it in etcd. Independent controllers constantly compare desired state with actual state and act to close the gap: if a pod dies, the ReplicaSet controller creates another; the scheduler places it on a node with enough capacity; the kubelet on that node starts the containers through the container runtime.

On top of this you get Deployments for rolling updates and rollbacks, Services and DNS for stable names and load balancing, ConfigMaps and Secrets for configuration, PersistentVolumes for storage, and autoscalers for pods and nodes. Kubernetes is not a PaaS: it doesn't build your code or provide databases by itself, and it adds complexity, so very small systems may be better on simpler platforms.

How it works

  1. You apply a Deployment manifest with kubectl apply.
  2. The API server validates it and stores it in etcd.
  3. Controllers create a ReplicaSet and the required pods.
  4. The scheduler assigns each pod to a suitable node.
  5. The kubelet starts the containers and reports status.
  6. Controllers keep reconciling: crashed or lost pods are replaced automatically.

Example

apiVersion: apps/v1
kind: Deployment
metadata: { name: orders }
spec:
  replicas: 3
  selector: { matchLabels: { app: orders } }
  template:
    metadata: { labels: { app: orders } }
    spec:
      containers:
      - name: orders
        image: registry.example.com/orders:1.4.0
        resources: { requests: { cpu: 250m, memory: 256Mi } }
---
apiVersion: v1
kind: Service
metadata: { name: orders }
spec:
  selector: { app: orders }
  ports: [ { port: 80, targetPort: 8080 } ]

Common mistakes

  • Calling Kubernetes a "container runtime"; it orchestrates, containerd runs containers.
  • Thinking pods are permanent; they are disposable and replaced.
  • Assuming Kubernetes is always the right choice, even for one small app.
  • Mixing up Docker images and Kubernetes objects.

How to answer in the interview

"Kubernetes is an open-source container orchestration platform. When you run many containers across many servers, something has to decide where each runs, restart it when it fails, scale it, and update it without downtime. In Kubernetes I describe the desired state in YAML, for example three replicas of a service, and controllers keep the actual state matching it: the scheduler places pods on nodes, failed pods are replaced, Deployments do rolling updates and rollbacks, and Services give stable names and load balancing. It's powerful, but it adds complexity, so it pays off mainly for multi-service systems."

Likely follow-up questions

  • What does desired state mean? The configuration you declared; controllers continuously reconcile reality towards it.
  • What is a pod? The smallest deployable unit: one or more containers sharing network and storage.
  • What runs on the control plane? API server, etcd, scheduler and controller manager.
