How do you pin Terraform and provider versions, and why?

Infrastructure as Code · concept · levels entry

In one line

Pin Terraform core with required_version and providers with required_providers version constraints (~>, >=, <), let the lock file fix exact versions, and upgrade deliberately through reviewed pull requests.

Detailed explanation

The terraform block is where versions are controlled. required_version constrains which Terraform CLI versions may run the configuration; running with a version outside the range fails immediately instead of, for example, upgrading the state format to a version teammates cannot read. required_providers declares each provider with its source address (such as hashicorp/aws) and a version constraint.

Constraint operators: = exact, != exclude, >, >=, <, <=, and the pessimistic operator ~>, which allows only the rightmost given component to increase. ~> 5.40 means >= 5.40, < 6.0: any newer 5.x minor release, but never 6.0. ~> 5.40.0 means >= 5.40.0, < 5.41.0: patch releases only. A range like >= 1.6, < 2.0 is common for required_version.

Reusable modules should declare loose minimum constraints (>= 5.0) describing what they need, because overly tight constraints in modules make them impossible to combine. Root configurations set the tighter constraints and own the lock file, which records the exact versions selected.

Why bother? Major provider releases routinely rename or remove arguments and change defaults, and an unplanned upgrade can suddenly show a huge plan, or worse, replacements. Pinning makes upgrades a conscious decision: a bot such as Renovate or Dependabot opens a PR bumping the version, the pipeline runs plans, and someone reviews them.

How it works

  1. required_version is checked when any command runs.
  2. terraform init chooses the newest provider versions satisfying all constraints from root and modules.
  3. The lock file records them; later inits reuse them.
  4. terraform init -upgrade re-resolves within constraints.
  5. Raising a major version requires editing the constraint itself.

Example

terraform {
  required_version = ">= 1.9, < 2.0"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.40"
    }
    random = {
      source  = "hashicorp/random"
      version = "~> 3.6"
    }
  }
}
{ "extends": ["config:recommended"], "terraform": { "enabled": true } }

Common mistakes

  • No constraints at all, relying on luck.
  • Exact pins inside shared modules, causing conflicts for callers.
  • Pinning but never upgrading, then facing several majors at once.
  • Thinking constraints alone guarantee reproducibility without the lock file.

How to answer in the interview

"In the terraform block, required_version constrains the CLI version and required_providers gives each provider a source and a version constraint. I typically use the pessimistic operator, like ~> 5.40, which allows newer 5.x minor releases but never 6.0. Shared modules use looser minimums, root configurations tighter constraints, and the lock file records the exact versions. Pinning prevents surprises, because a new major provider can rename arguments or change defaults and produce a huge plan. Upgrades become pull requests, ideally opened by Renovate or Dependabot, with plans reviewed."

Likely follow-up questions

  • What does ~> 5.0 allow compared with ~> 5.40.0? Any 5.x versus only 5.40.x patches.
  • Why loose constraints in modules? So multiple modules can agree on one provider version.
  • What if two modules' constraints conflict? init fails; relax one module's constraint.
