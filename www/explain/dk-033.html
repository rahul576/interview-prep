How do you limit CPU and memory for a container, and what happens when the limit is exceeded?

Docker · concept · levels mid

In one line

Docker uses cgroups: --memory sets a hard memory limit and exceeding it gets the process OOM-killed (exit 137, OOMKilled=true); --cpus caps CPU time and --cpu-shares sets relative weight, and exceeding a CPU limit causes throttling, not killing.

Detailed explanation

Without limits, a container can consume all of a host's memory and CPU and starve its neighbours. Docker passes limits to the kernel's control groups, which enforce them.

Memory is incompressible: it cannot be slowed down, only taken away. --memory 512m sets a hard limit for all processes in the container. When the cgroup tries to exceed it and the kernel cannot reclaim page cache, the OOM killer terminates a process in the cgroup, usually the main one, so the container exits with code 137 (128 + SIGKILL) and docker inspect shows OOMKilled: true. --memory-swap sets memory plus swap; setting it equal to --memory disables swap for the container. --memory-reservation is a soft limit used under host pressure.

CPU is compressible. --cpus 1.5 uses the CFS quota to allow 1.5 cores worth of CPU time per scheduling period (100 ms by default). If the container wants more, it is throttled: its threads wait until the next period. Nothing crashes, but latency rises, which is a classic hidden cause of slow p99s, particularly for multi-threaded runtimes. --cpu-shares (or CPU weight on cgroup v2) is only a relative priority applied when CPUs are contended, and --cpuset-cpus pins to specific cores. --pids-limit protects against fork bombs.

Applications must also know their limits. Modern JVMs, Node.js and Go read cgroup limits, but heaps and thread pools still need sensible configuration.

How it works

  1. Docker creates a cgroup for the container with the requested limits.
  2. The kernel accounts memory and CPU per cgroup.
  3. Memory over limit: reclaim, then OOM kill inside the cgroup.
  4. CPU over quota: threads are throttled until the next period.
  5. Counters (memory.events, cpu.stat) expose OOMs and throttling.

Example

docker run -d --name api --memory 512m --memory-swap 512m --cpus 1.5 --pids-limit 200 registry.local/api:1.4
docker stats --no-stream api
docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}}' api
# compose.yaml
services:
  api:
    deploy:
      resources:
        limits: { cpus: "1.5", memory: 512M }

Common mistakes

  • Setting a JVM heap equal to the memory limit, leaving no room for native memory.
  • Expecting CPU limits to kill runaway processes.
  • No limits at all on shared hosts.
  • Very tight CPU limits on latency-sensitive services, causing throttling.

How to answer in the interview

"Docker uses cgroups. --memory 512m is a hard limit; if processes exceed it, the kernel OOM killer terminates the process, the container exits with 137 and docker inspect shows OOMKilled true. --memory-swap controls swap. For CPU, --cpus 1.5 allows one and a half cores of CPU time and --cpu-shares is a relative weight under contention. Exceeding CPU doesn't kill anything; the process is throttled and gets slower, which shows up as latency. Limits protect neighbours on the same host, and the app, like the JVM, must be configured to fit inside them."

Likely follow-up questions

  • How should a JVM respect the limit? Use -XX:MaxRAMPercentage around 70-75% to leave native headroom.
  • How do you detect CPU throttling? nr_throttled and throttled_usec in cpu.stat or cAdvisor metrics.
  • What does --memory-reservation do? A soft limit enforced when the host is under memory pressure.
