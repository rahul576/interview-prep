Design a webhook delivery system that reliably notifies thousands of customer endpoints about events.

Classic Design Problems · design · levels entry, mid, senior

In one line

A webhook system persists events, delivers them asynchronously from queues with per-endpoint isolation, retries with exponential backoff for days, signs payloads with HMAC, guarantees at-least-once delivery with event IDs, and gives customers logs, replay and auto-disable.

Detailed explanation

Webhooks push events to servers we do not control. Those endpoints are slow, down, misconfigured or rate-limited, so the system must be designed around failure. The first rule: the core business flow must never wait on a customer's server. The producer writes the event (ideally via the outbox pattern, in the same transaction as the business change) and delivery happens asynchronously.

Isolation matters most at scale. If all deliveries share one queue, one endpoint timing out for 10 seconds per request ties up workers and delays everyone: a noisy neighbour. Use per-endpoint queues or partitions, per-endpoint concurrency limits, and short timeouts.

Delivery is at-least-once: a request may succeed but the response is lost, so we retry. Each event carries a unique event ID so receivers dedupe (idempotency). Ordering is not guaranteed; receivers should use timestamps or fetch the latest state via API. Payloads are signed with an HMAC-SHA256 of the timestamp plus body using a per-endpoint secret, so receivers verify authenticity and reject replays outside a tolerance window.

How it works

  1. Event is committed and published to a stream (Kafka, SQS).
  2. A fan-out service finds matching subscriptions and creates one delivery task per endpoint.
  3. Delivery workers POST with a 5-10 second timeout; 2xx means success.
  4. Failures are rescheduled with exponential backoff plus jitter (e.g. 1 min, 5 min, 30 min ... up to 3 days) in a durable delay queue.
  5. Every attempt is logged (status, latency, response snippet) for the customer dashboard.
  6. Endpoints failing continuously for days are disabled and the customer notified; failed events can be replayed.

Example

import hmac, hashlib, time, json

def sign(secret: bytes, body: bytes) -> dict:
    ts = str(int(time.time()))
    sig = hmac.new(secret, f"{ts}.".encode() + body, hashlib.sha256).hexdigest()
    return {"Webhook-Id": "evt_01HZX...", "Webhook-Timestamp": ts,
            "Webhook-Signature": f"v1={sig}"}

body = json.dumps({"id": "evt_01HZX...", "type": "payment.succeeded",
                   "data": {"payment_id": "pay_42"}}).encode()
headers = sign(b"whsec_...", body)

Common mistakes

  • Sending webhooks synchronously inside the request that created the event.
  • One shared queue, so a single dead endpoint delays all customers.
  • Retrying immediately in a tight loop and hammering a recovering server.
  • No event ID, leaving receivers unable to handle duplicates.
  • Following redirects or allowing internal IPs, creating an SSRF risk.

How to answer in the interview

"I'd persist each event with an outbox and publish it to a queue, so delivery is decoupled from the business flow. Delivery workers send signed POSTs with short timeouts, and failures retry with exponential backoff and jitter for up to a few days. Each endpoint is isolated with its own queue or concurrency limit, so one slow customer can't block others. Delivery is at-least-once with a unique event ID for idempotency, and customers get delivery logs, manual replay, and automatic disabling with a notification if their endpoint fails for days."

Likely follow-up questions

  • Should webhooks be ordered? Usually no; ordering per endpoint forces serial delivery and head-of-line blocking. Send IDs and timestamps instead.
  • How do you prevent SSRF? Resolve and block private IP ranges, disallow redirects, egress through a proxy.
  • How do you rotate secrets? Support two active secrets and send both signatures during rotation.
