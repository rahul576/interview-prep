Which database technologies have you worked with, including Oracle, MongoDB, DynamoDB, and Cassandra?

Databases & SQL · scenario · levels entry, mid

In one line

Answer with specific projects, not a list: for each database, say what you used it for, why it was chosen, what you did hands-on (modelling, tuning, operations) and what you learned, and be honest about depth where your experience is lighter.

Detailed explanation

This is an experience question, so the interviewer is checking several things at once:

  • Breadth with depth: can you work across relational and NoSQL stores, and do you understand them beyond CRUD?
  • Reasoning: do you know why each database fitted its use case and where it would not?
  • Hands-on skills: query tuning, indexing, data modelling, consistency settings, migrations, incidents.
  • Honesty: overclaiming is easily exposed by one follow-up question.

A good structure for each database is a mini STAR: Situation (system and scale), Task (what the data needed), Action (your design and tuning work), Result (performance, reliability or cost outcome, ideally with numbers), plus one lesson. Order them by relevance to the role: for a Java backend position, lead with your strongest relational experience and the JPA/Hibernate integration, then the NoSQL stores.

Useful details that signal real experience:

  • Oracle/PostgreSQL/MySQL: execution plans, composite indexes, PL/SQL, isolation levels, connection pooling, Flyway/Liquibase migrations, partitioning.
  • MongoDB: embedding vs referencing, compound indexes, aggregation pipelines, schema validation, replica sets.
  • DynamoDB: partition/sort key design, GSIs, single-table design, TTL, Streams with Lambda, throttling and hot keys.
  • Cassandra: query-first tables, partition sizing and bucketing, consistency levels such as LOCAL_QUORUM, tombstones, repair.

If you have not used one of them, say so and connect it to related knowledge: "I haven't run Cassandra in production, but I've studied its data model and used DynamoDB, which has similar partition-key design constraints."

How it works

  1. Pick your two or three strongest databases and one concrete project for each.
  2. Prepare a 20-30 second story per database: use case, why chosen, your actions, result.
  3. Add one lesson or trade-off per database.
  4. State depth honestly for weaker ones.
  5. Prepare for follow-ups on modelling, indexing and consistency.

Example

Sample answer structure:

Oracle    -> system of record for orders/billing; SQL + PL/SQL, read plans,
             composite index cut month-end report from 40 min to 3 min; JPA/Hibernate on top
MongoDB   -> product catalogue, category-specific attributes embedded per product;
             compound index on (category, price); learned to bound array growth
DynamoDB  -> serverless notification service (Lambda); PK=userId, SK=createdAt,
             GSI on status, TTL for 30-day expiry; learned about hot keys
Cassandra -> device event history, table keyed by (deviceId, day); LOCAL_QUORUM;
             lighter experience: I didn't operate the cluster myself

Common mistakes

  • Reciting a list of database names with no context.
  • Claiming expert-level experience in all four.
  • Describing only CRUD via an ORM without any modelling or tuning detail.
  • Not explaining why a database was chosen over alternatives.

How to answer in the interview

"Most of my work has been on relational databases. Oracle was our system of record for orders and billing: I wrote and tuned SQL and PL/SQL, read execution plans and added composite indexes, and we used JPA with Hibernate on top. I used MongoDB for a product catalogue where attributes vary by category, so embedding variants in one document made reads fast. DynamoDB backed a serverless notification service with Lambda, designed around partition and sort keys with a GSI on status and TTL to expire old records. Cassandra I used for high-volume device event history queried by device and time, though I didn't operate the cluster myself, so my experience there is more on the modelling side."

Likely follow-up questions

  • Which would you pick for a new order management system? A relational database such as PostgreSQL, for transactions, constraints and reporting.
  • What was the hardest database problem you solved? Have one incident story ready: a slow query, deadlock or hot partition.
  • How do you decide between MongoDB and PostgreSQL JSONB? Relational needs and transactions favour Postgres; document-centric, horizontally scaled workloads favour MongoDB.
