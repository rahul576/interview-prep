How would you count unique visitors per day across billions of events with limited memory?

DSA: Algorithms & DP · design · levels senior, lead

In one line

An exact set of billions of ids won't fit in memory, so use HyperLogLog (HLL). It estimates cardinality with roughly 1% error in kilobytes, and sketches are mergeable across shards, hours and days. Use a Bloom filter for membership ("seen before?"), and partitioned batch counting when exact numbers are mandatory.

Detailed explanation

With 2 billion events per day and maybe 300 million distinct visitors, an exact HashSet<String> needs tens of GB per day, more again for weekly or monthly windows, and can't be merged cheaply across servers. Most product metrics tolerate ±1–2%, which opens the door to probabilistic sketches.

How HyperLogLog works (intuition). Hash each visitor id to a uniform 64-bit value. In random bits, a run of k leading zeros appears roughly once per 2^k distinct values, so the longest run seen hints at the cardinality. One estimate is very noisy, so HLL splits the hash. The first p bits choose one of m = 2^p registers, and each register stores the maximum leading-zero count of the hashes routed to it. A harmonic mean across registers, plus bias corrections for small and large ranges, gives the estimate. The standard error is about 1.04/√m. With m = 16,384 that is about 0.81%, in roughly 12 KB. Duplicates don't change the result, because the same id always hashes to the same register and value.

Mergeability is the killer feature. The union of two HLLs is the register-wise max. So each shard or hour builds its own sketch, and daily, weekly and monthly uniques are just merges. There is no reprocessing of raw events. (Intersections are only approximate, through inclusion–exclusion, and the error grows.)

Off-the-shelf tools:

  • Redis PFADD/PFCOUNT/PFMERGE: about 12 KB per key, 0.81% standard error.
  • Elasticsearch cardinality aggregation (HLL++).
  • BigQuery APPROX_COUNT_DISTINCT and HLL functions, Spark approx_count_distinct, Druid, and the Apache DataSketches library.

Bloom filter answers a different question: "is this id possibly in the set?". It can give false positives but never false negatives, using about 10 bits per element for 1% FPR. It is good for "is this a new visitor?" checks, not for counting.

Exact counts (billing, legal reporting): partition events by hash(visitorId) so each worker counts distinct ids for its partition independently, then sum. Or run COUNT(DISTINCT) in a batch warehouse job.

How it works

  1. The event stream (Kafka) is consumed by stream processors.
  2. Each processor runs PFADD uv:{day}:{shard} visitorId (or keeps an in-memory sketch).
  3. Periodically merge the shard sketches: PFMERGE uv:{day} uv:{day}:*.
  4. The dashboard calls PFCOUNT uv:{day}. A week is PFCOUNT over 7 keys, which merges internally.
  5. Raw events stay in cheap storage for occasional exact recounts.

Example

PFADD uv:2026-11-21 user:81 user:93 user:81      # duplicate ignored
PFADD uv:2026-11-22 user:93 user:17
PFCOUNT uv:2026-11-21                            # -> 2
PFCOUNT uv:2026-11-21 uv:2026-11-22              # union -> 3
PFMERGE uv:week47 uv:2026-11-21 uv:2026-11-22

Common mistakes

  • Summing daily unique counts to get weekly uniques (it double-counts). Merge sketches instead.
  • Using HLL for small sets where an exact set is cheap.
  • Expecting accurate intersections from HLLs.
  • Using a Bloom filter to count.

How to answer in the interview

"An exact set of billions of ids won't fit in memory, so I'd use HyperLogLog. It hashes each id, routes it to one of thousands of registers, and tracks the maximum number of leading zeros per register. That gives a cardinality estimate with about one percent error in roughly 12 kilobytes, and duplicates don't affect it. Sketches are mergeable, so each shard or hour builds its own and I union them for daily or weekly counts, with Redis PFADD and PFCOUNT or Elasticsearch's cardinality aggregation. For 'have we seen this visitor' I'd use a Bloom filter, and if exact counts were mandatory I'd partition by visitor id and count in batch."

Likely follow-up questions

  • Trade-off of a Bloom filter? Compact and fast, but false positives, no deletes (use counting or cuckoo filters), and no enumeration.
  • Why not sum daily uniques? The same visitor appears on several days. Union the sketches.
  • Error versus memory? Error scales with 1/√m. Four times the registers halves the error.
