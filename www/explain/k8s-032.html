What CronJob settings matter in production, and what can go wrong with schedules?

Kubernetes · concept · levels mid, senior

In one line

In production, set concurrencyPolicy (Allow, Forbid, Replace), startingDeadlineSeconds for missed runs, an explicit timeZone, and history limits; remember that a CronJob may run a schedule twice or not at all, so jobs must be idempotent and monitored for missed or failed runs.

Detailed explanation

A CronJob creates a Job for each schedule tick in standard cron syntax. The defaults are permissive, and most production incidents come from not choosing settings deliberately.

concurrencyPolicy decides what happens if the previous Job is still running when the next tick arrives:

  • Allow (default): both run, which can overload databases or corrupt shared output.
  • Forbid: skip the new run; right for jobs that must never overlap, such as a nightly billing export or a backup.
  • Replace: kill the running Job and start the new one; right when only the latest result matters.

startingDeadlineSeconds: how late a Job may start after its scheduled time (controller down, API unavailable, Forbid skipping). If the deadline passes, that run is counted as missed. Without it, the controller counts all missed schedules since the last run; if more than 100 are missed, it stops creating Jobs for that CronJob and logs an error. Setting a deadline (for example 300 s) bounds that window and avoids the surprise after long outages.

timeZone (for example Europe/London, Asia/Kolkata) interprets the schedule in a named zone rather than the controller manager's zone, which is usually UTC; DST transitions can make a run happen twice or be skipped, so avoid scheduling critical jobs in the DST-ambiguous hour.

successfulJobsHistoryLimit (default 3) and failedJobsHistoryLimit (default 1) keep recent Jobs for debugging; combine with Job-level ttlSecondsAfterFinished sensibly. The suspend field pauses a CronJob during maintenance. All Job reliability settings (backoffLimit, activeDeadlineSeconds, podFailurePolicy) belong in jobTemplate.

The documentation is explicit that CronJob scheduling is approximate: a Job may occasionally be created twice or not at all for a tick. Make jobs idempotent (unique run keys, upserts, locks) and alert on outcomes, not on hopes.

How it works

  1. Controller checks schedules regularly.
  2. At a tick, checks concurrencyPolicy against active Jobs.
  3. Creates a Job from jobTemplate if within startingDeadlineSeconds.
  4. Job runs pods with its own retry and deadline settings.
  5. Old Jobs pruned per history limits.

Example

apiVersion: batch/v1
kind: CronJob
metadata: { name: billing-export }
spec:
  schedule: "15 2 * * *"
  timeZone: "Europe/London"
  concurrencyPolicy: Forbid
  startingDeadlineSeconds: 600
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 5
  jobTemplate:
    spec:
      backoffLimit: 2
      activeDeadlineSeconds: 3600
      template:
        spec:
          restartPolicy: Never
          containers:
          - name: export
            image: registry.example.com/billing-export:2.4

Common mistakes

  • Default Allow on jobs that must not overlap.
  • No startingDeadlineSeconds, then a CronJob silently stops after an outage.
  • Assuming the schedule uses local time.
  • No alert when a critical job didn't run.

How to answer in the interview

"concurrencyPolicy decides what happens when the previous run is still going: Allow runs both, Forbid skips the new one and Replace kills the old one; for a nightly billing export I use Forbid. startingDeadlineSeconds sets how late a missed run may start; without it, more than 100 missed schedules makes the controller stop scheduling, which surprises people after outages. The timeZone field pins the schedule to a named zone. History limits keep a few Jobs for debugging. The docs say a CronJob may occasionally create two Jobs or none, so jobs are idempotent and I alert on missed or failed runs."

Likely follow-up questions

  • How do you monitor a critical CronJob ran? Alert on kube_cronjob_status_last_successful_time age via kube-state-metrics, or a dead man's switch heartbeat.
  • How do you trigger a run manually? kubectl create job --from=cronjob/billing-export manual-1.
  • How do you pause it? Set spec.suspend: true.
