How do you document and design-first an API with OpenAPI?

REST & API Design · concept · levels mid, senior

In one line

OpenAPI is a machine-readable specification of endpoints, parameters, schemas, errors and security; you either generate it code-first (springdoc from controllers) or write it design-first and generate server stubs and clients (OpenAPI Generator), then lint, publish and check breaking changes in CI.

Detailed explanation

An OpenAPI document (YAML or JSON, current versions 3.0 and 3.1, with 3.2 released in 2025) describes an HTTP API completely: paths and operations, parameters, request and response bodies as JSON Schema, status codes and error models, security schemes (OAuth 2, bearer JWT, API keys), examples and descriptions. Because it is machine-readable, tools can render documentation (Swagger UI, Redoc), generate code, mock servers and tests.

Code-first. You write controllers and let springdoc-openapi scan them at runtime, producing /v3/api-docs and Swagger UI. Annotations such as @Operation, @ApiResponse and @Schema enrich it, and Bean Validation constraints become schema rules. It is fast and the spec always matches the code, but API design tends to be an afterthought and the contract only exists after implementation.

Design-first. Teams write and review the spec before coding, often in pull requests with product owners and consumer teams. Then OpenAPI Generator (Maven/Gradle plugin) generates server interfaces (for example Spring interfaces with @RequestMapping) that controllers implement, and client SDKs for consumers in Java, TypeScript, etc. Frontend and backend work in parallel using a mock server (Prism, WireMock). This suits APIs with several consuming teams or external partners.

Governance in CI applies to both approaches:

  • Lint the spec with Spectral or Redocly rules: naming, required descriptions, error formats, pagination conventions.
  • Breaking-change detection with tools such as openapi-diff or oasdiff, comparing against the last released version and failing the build on removed fields or changed types.
  • Publish the spec to a developer portal or API gateway, versioned with the service.
  • Contract tests verify the implementation matches the spec.

How it works

  1. Write (design-first) or generate (code-first) the spec.
  2. Review it like code.
  3. Generate stubs/clients or annotate controllers.
  4. CI lints, diffs against the previous version and runs contract tests.
  5. Publish docs and the spec to the portal.

Example

openapi: 3.1.0
info: { title: Orders API, version: 1.4.0 }
paths:
  /orders/{id}:
    get:
      operationId: getOrder
      parameters:
        - { name: id, in: path, required: true, schema: { type: integer } }
      responses:
        '200': { description: OK, content: { application/json: { schema: { $ref: '#/components/schemas/Order' } } } }
        '404': { description: Not found, content: { application/problem+json: { schema: { $ref: '#/components/schemas/Problem' } } } }
components:
  schemas:
    Order:
      type: object
      required: [id, status]
      properties:
        id: { type: integer }
        status: { type: string, enum: [NEW, PAID, SHIPPED] }
<plugin>
  <groupId>org.openapitools</groupId>
  <artifactId>openapi-generator-maven-plugin</artifactId>
  <configuration>
    <inputSpec>${project.basedir}/api/orders.yaml</inputSpec>
    <generatorName>spring</generatorName>
    <configOptions><interfaceOnly>true</interfaceOnly><useSpringBoot3>true</useSpringBoot3></configOptions>
  </configuration>
</plugin>

Common mistakes

  • Spec and code drifting apart in design-first without generation or tests.
  • No error responses documented, only 200.
  • Treating Swagger UI as the only documentation, with no descriptions or examples.
  • No breaking-change check, so clients break silently.

How to answer in the interview

"OpenAPI is a specification describing endpoints, parameters, request and response schemas, errors and security. Code-first, springdoc generates the spec and Swagger UI from my controllers and annotations, which is quick. Design-first, we agree the spec in a pull request before coding, then generate Spring server interfaces and client SDKs with OpenAPI Generator, and consumers can start against a mock; that's my choice when several teams depend on the API. Either way, I lint the spec with Spectral, publish it to the developer portal, and run a breaking-change diff against the previous version in CI."

Likely follow-up questions

  • How would you keep code and spec from drifting apart? Generate interfaces from the spec so the build fails on mismatch, or generate the spec from code and diff it in CI.
  • What's new in OpenAPI 3.1? Full JSON Schema alignment and webhooks.
  • Where do you document error formats? As shared components, e.g. a Problem Details schema.
