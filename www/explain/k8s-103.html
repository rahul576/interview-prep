A newly deployed pod has been stuck in Pending for ten minutes. Walk through how you troubleshoot it step by step.

Kubernetes · scenario · levels entry, mid

In one line

A Pending pod has not been scheduled, so read the FailedScheduling events in kubectl describe pod: usually insufficient CPU/memory, unsatisfiable selectors, affinity or taints, an unbound PVC, or an autoscaler that cannot add nodes.

Detailed explanation

Pending means the API server accepted the pod but the scheduler has not bound it to a node (or, less often, it is bound but images are still pulling, which shows as ContainerCreating rather than Pending in practice). The scheduler explains itself in events, for example 0/6 nodes are available: 3 Insufficient memory, 3 node(s) had untolerated taint {dedicated: gpu}.

Resources: scheduling uses requests, not actual usage. If the pod asks for 4 CPU and no node has 4 CPU of free allocatable capacity, it waits, even if nodes look idle. Compare with kubectl describe nodes (Allocated resources); kubectl top shows usage, which is a different question.

Scheduling rules: a nodeSelector with a misspelt label, required node affinity nobody satisfies, pod anti-affinity needing more nodes than exist, topology spread with DoNotSchedule, or taints without matching tolerations.

Storage: a PVC that is unbound (missing StorageClass, provisioner failing) or a volume in another zone from all suitable nodes gives messages like volume node affinity conflict.

Capacity and nodes: nodes NotReady, or the cluster autoscaler or Karpenter not adding a node because the max size is reached, no node group matches the pod's requirements, or cloud quota is exhausted. ResourceQuota violations usually stop pod creation entirely, so you see errors on the ReplicaSet rather than a Pending pod.

How it works

  1. kubectl describe pod and read the FailedScheduling event.
  2. Resources message: compare requests with node allocatable.
  3. Taint or affinity message: check node labels and tolerations.
  4. Volume message: check PVC status and zones.
  5. Check node readiness and autoscaler events or logs.
  6. Apply the fix: right-size requests, fix labels, add tolerations, repair storage, add capacity.

Example

kubectl describe pod report-6c9b | sed -n '/Events/,$p'
# Warning FailedScheduling 0/6 nodes are available: 2 Insufficient cpu,
#   4 node(s) didn't match Pod's node affinity/selector.
kubectl get nodes -L workload
kubectl get pod report-6c9b -o jsonpath='{.spec.nodeSelector}'
# {"workload":"bach"}   <- typo, nodes are labelled workload=batch
kubectl get pvc -n reports

Common mistakes

  • Looking at kubectl top usage instead of requests versus allocatable.
  • Deleting and recreating the pod without reading events.
  • Adding tolerations and expecting them to pull pods onto tainted nodes.
  • Forgetting the autoscaler's limits and node group constraints.

How to answer in the interview

"Pending means the pod is accepted but not scheduled, so the answer is almost always in the scheduler events. I run kubectl describe pod and read FailedScheduling, which says how many nodes failed for which reason. Common causes are requests larger than any node's free allocatable capacity, scheduling rules nobody satisfies, such as a misspelt nodeSelector, required affinity or taints without tolerations, and unbound PVCs or zone conflicts. I also check that nodes are Ready and why the autoscaler did not add a node, like max size reached. The fix follows the cause."

Likely follow-up questions

  • How do events differ when the autoscaler is about to add a node? You see a TriggeredScaleUp event or Karpenter nominating a node, followed by scheduling once it joins.
  • Why does an idle cluster refuse a pod? Requests are reserved capacity, regardless of usage.
  • What about pod priority? Higher-priority pods can preempt lower ones to get scheduled.
