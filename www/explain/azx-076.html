How does Azure Policy for AKS work, and what are deployment safeguards?

Azure Kubernetes (AKS) · concept · levels mid, senior

In one line

The Azure Policy add-on runs OPA Gatekeeper in AKS and turns Azure Policy assignments into admission constraints, with compliance reported centrally; deployment safeguards are a curated set of Kubernetes best-practice policies in Warning or Enforcement mode, on by default in AKS Automatic.

Detailed explanation

Governance at scale needs one mechanism for all clusters. With the add-on, a component in the cluster syncs policy definitions assigned in Azure into Gatekeeper ConstraintTemplates and Constraints. Gatekeeper then acts as a validating admission webhook: when someone creates or updates a pod, it evaluates the policies and denies or audits the request. It also audits existing resources periodically.

Built-in policies include: no privileged containers, no host network/PID/IPC namespaces, images only from allowed registries (for example your ACR), CPU and memory limits required, read-only root filesystem, no public load balancers, allowed capabilities and Pod Security Standards baseline or restricted initiatives.

Because the source is Azure Policy, assignments at management group scope apply to every current and future cluster automatically, and compliance appears next to all other Azure resources, in dashboards and in Defender for Cloud. Effects are typically audit first, then deny once teams are ready.

Deployment safeguards package common best practices, such as liveness and readiness probes, resource requests, anti-affinity for replicas, no latest tags and no privileged containers, into a managed policy set. In Warning mode, kubectl shows warnings but allows the deployment; in Enforcement mode, non-compliant resources are rejected (some may be mutated, for example adding default requests). It is enabled by default in AKS Automatic and optional in Standard.

Exemptions for system components that legitimately need privileges are handled with excluded namespaces in the assignment parameters or Azure Policy exemptions, documented and time-limited.

How it works

  1. Enable the add-on on each cluster (or via policy at scale).
  2. Assign initiatives at management group scope with audit effect.
  3. Review compliance and fix workloads.
  4. Switch to deny and enable safeguards in Enforcement.
  5. Grant exemptions for specific namespaces with justification.

Example

az aks enable-addons -g rg-apps -n aks-prod --addons azure-policy
az aks update -g rg-apps -n aks-prod --safeguards-level Warn \
  --safeguards-excluded-ns monitoring,security-agents

kubectl apply -f bad-pod.yaml
# Error from server (Forbidden): admission webhook "validation.gatekeeper.sh" denied the request:
# [azurepolicy-k8sazurev2noprivilege-...] Privileged container is not allowed: app

Common mistakes

  • Starting with deny everywhere and breaking system components.
  • Assigning policies per cluster instead of at management group scope.
  • Excluding whole clusters instead of specific namespaces.
  • Forgetting that policy sync takes several minutes after assignment.

How to answer in the interview

"The Azure Policy add-on installs Gatekeeper in the cluster and syncs Azure Policy assignments into constraints, so Kubernetes resources are governed with the same service as other Azure resources. Built-ins cover privileged containers, allowed registries, limits and read-only filesystems. Compliance is reported centrally, and I assign initiatives at management group scope so every cluster is covered. Deployment safeguards are curated best-practice policies like probes and requests, in warning or enforcement mode; they're on by default in AKS Automatic. I roll out in audit or warning first, then enforce."

Likely follow-up questions

  • How to exempt a privileged agent? Excluded namespaces or an Azure Policy exemption with an expiry.
  • Gatekeeper vs Kyverno? Both admission engines; Gatekeeper is what Azure Policy manages.
  • Does it fix existing pods? No, it audits them; you redeploy compliant manifests.
