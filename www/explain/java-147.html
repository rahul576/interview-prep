What is the difference between mocks, stubs and spies, and when does mocking go too far?

Testing · concept · levels mid, senior

In one line

A stub returns canned answers, a mock also lets you verify interactions, and a spy wraps a real object with selected methods overridden; mocking goes too far when tests mock internals and value objects, so they test implementation instead of behaviour and break on every refactor.

Detailed explanation

These are all test doubles (Gerard Meszaros' term). The difference is in what the test checks.

A stub provides indirect input. when(rates.rateFor("EUR")).thenReturn(0.92) lets the code under test run a specific path; the test then asserts the state or return value. A mock is about indirect output: the test asserts that a collaborator was called correctly, for example verify(mailer).send(eq(customerEmail), any()). In Mockito the same mock() object can act as either, depending on whether you stub or verify. A fake is a working lightweight implementation, such as an in-memory repository. A spy wraps a real object: unstubbed methods run real code, stubbed ones return what you specify, so it is a partial mock.

Mocking is valuable at boundaries: payment gateways, email, clocks, other services, things that are slow, non-deterministic or have side effects. It goes too far when:

  • every collaborator, including simple domain classes and value objects, is mocked;
  • tests verify the exact sequence of internal calls;
  • stubs return mocks that return mocks (train wrecks);
  • types you do not own (HTTP clients, JDBC) are mocked, so tests encode your assumptions about a library rather than its real behaviour.

Such tests are brittle: a harmless refactor breaks them, while a real bug in the wiring passes. Prefer verifying outcomes, use real objects inside the module, wrap third-party APIs in your own adapter interface, and test the adapter with WireMock or Testcontainers.

How it works

  1. Identify the unit's boundaries (ports): repositories, clients, clock.
  2. Stub queries that provide data; assert the result.
  3. Mock and verify only commands with important side effects.
  4. Use real objects for internal collaborators and value types.
  5. Use a spy only for legacy code that cannot yet be split.

Example

@Test
void sendsConfirmationForPaidOrder() {
    PaymentGateway gateway = mock(PaymentGateway.class);
    Mailer mailer = mock(Mailer.class);
    Clock clock = Clock.fixed(Instant.parse("2026-01-10T10:00:00Z"), ZoneOffset.UTC);

    when(gateway.charge(any())).thenReturn(PaymentResult.ok("tx-1"));  // stub
    var service = new CheckoutService(gateway, mailer, clock);

    Order order = service.checkout(cartWith(2, "BOOK"));

    assertThat(order.status()).isEqualTo(PAID);                         // state
    verify(mailer).send(eq("a@b.com"), contains("tx-1"));               // mock
}

Common mistakes

  • Verifying every call, including getters, so tests mirror the code line by line.
  • Mocking value objects or DTOs instead of constructing them.
  • Using spies in new code instead of improving the design.
  • Mocking LocalDateTime.now() with static mocks rather than injecting a Clock.

How to answer in the interview

"A stub just returns canned data so the code can follow a path, and I assert the result. A mock records calls so I can verify an interaction, like an email being sent exactly once. A spy wraps a real object and only overrides some methods, a partial mock that I reserve for legacy code. Mocking goes too far when every collaborator is mocked, including value objects and internal classes, and tests verify call sequences. Then they break on every refactor and don't catch real bugs. I mock only external boundaries, wrap third-party libraries behind my own interfaces, and test those adapters with WireMock or Testcontainers."

Likely follow-up questions

  • How do you test code calling LocalDateTime.now()? Inject a Clock and use Clock.fixed in tests.
  • What is a fake? A real but simplified implementation, like an in-memory repository.
  • Why not mock types you don't own? Your mock encodes assumptions about the library that may be wrong or change on upgrade.
