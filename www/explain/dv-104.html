What are Docker image layers and how does the build cache work?

Docker · concept · levels entry, mid

In one line

An image is a stack of read-only, content-addressed layers, one per filesystem-changing instruction, shared between images; the build cache reuses each layer until an instruction or its inputs change, after which all later layers rebuild, so put dependencies before source code, use .dockerignore, and remember a container adds only a thin writable layer on top.

Detailed explanation

Each RUN, COPY or ADD produces a layer: a set of filesystem changes (added, modified, deleted files) on top of the previous ones. Layers are identified by a digest (hash of their content), so if ten images use the same base, that base is stored and downloaded once. The overlay2 driver stacks them into one filesystem view.

When a container starts, Docker adds a thin writable container layer. Changes are written there using copy-on-write: modifying a file from a lower layer copies it up first. When the container is removed, that layer and its changes are gone, which is why persistent data belongs in volumes.

The build cache works instruction by instruction. For RUN, the cache key is the instruction text plus the parent layer; for COPY/ADD, it also includes a checksum of the copied files. As soon as one instruction misses the cache, that step and every step after it run again. So order matters:

  1. Base image and system packages (rarely change).
  2. Dependency manifest (pom.xml, package.json + lock file) and the install step.
  3. Application source (changes every commit).

A .dockerignore keeps .git, node_modules, build output and secrets out of the build context, which makes the context upload faster and prevents unrelated files from invalidating COPY . ..

How it works

  1. Docker evaluates each instruction and computes its cache key.
  2. Cache hit → reuse the existing layer; cache miss → execute and create a new layer.
  3. All subsequent instructions are executed fresh after the first miss.
  4. Layers are pushed/pulled individually; only missing ones transfer.
  5. At runtime, overlay2 merges layers and adds a writable layer.

Example

FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /src
COPY pom.xml .
RUN mvn -q dependency:go-offline     # cached until pom.xml changes
COPY src ./src
RUN mvn -q package -DskipTests       # rebuilt on code changes only
# .dockerignore
.git
target/
*.log
.env
docker history myapp:1.0    # shows each layer and its size

Common mistakes

  • COPY . . near the top, so any file change reinstalls dependencies.
  • RUN apt-get update in one layer and apt-get install in another, leading to stale package lists.
  • Deleting large files or secrets in a later layer and believing they're gone.
  • No .dockerignore, uploading gigabytes of context.

How to answer in the interview

"An image is a stack of read-only layers, one for each instruction that changes the filesystem, like RUN or COPY. Layers are content-addressed, so images that share a base store and download it only once. On rebuild, Docker reuses each cached layer until it hits an instruction whose text or input files changed; that layer and everything after it is rebuilt. So I copy only the dependency manifest and install dependencies first, then copy the source, and a code change doesn't reinstall everything. A .dockerignore keeps unneeded files out of the context. A running container adds a thin writable layer on top, which is lost when it's removed, so data goes in volumes."

Likely follow-up questions

  • Why do containers lose data when removed? The writable layer is deleted with the container; use volumes or bind mounts.
  • What is copy-on-write? A file from a lower layer is copied into the writable layer the first time it is modified.
  • How do you see layer sizes? docker history or tools like dive.
