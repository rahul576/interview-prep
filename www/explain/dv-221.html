What are the main Azure compute and storage services a fresher should know?

Azure · concept · levels entry

In one line

For compute, know Virtual Machines and VM Scale Sets, App Service, Azure Functions, AKS and Container Apps; for storage, know the storage account services (Blob, Files, Queues, Tables), managed disks, and redundancy options LRS, ZRS and GRS.

Detailed explanation

Azure services sit on a spectrum from IaaS (you manage the OS) to PaaS and serverless (Azure manages more for you). Interviewers want to see that you can pick the right level of control.

Compute:

  • Virtual Machines: full control of the operating system; you patch, secure and scale them. Good for legacy apps or special software.
  • VM Scale Sets: groups of identical VMs with autoscaling and rolling upgrades, behind a load balancer.
  • App Service: managed hosting for web apps and APIs (.NET, Java, Node, Python, containers) with deployment slots, autoscale, TLS and custom domains. Least effort for a typical web API.
  • Azure Functions: serverless, event-driven code triggered by HTTP, timers, queues or events; pay per execution on consumption plans.
  • AKS: managed Kubernetes for many microservices and teams needing full Kubernetes control.
  • Container Apps: serverless containers built on Kubernetes concepts, with scale to zero, revisions and Dapr, without managing a cluster.

Storage account services:

  • Blob storage: objects such as images, logs, backups and static websites; access tiers Hot, Cool, Cold, Archive.
  • Azure Files: SMB or NFS file shares for lift-and-shift apps.
  • Queues: simple message queues between components.
  • Tables: cheap key-value NoSQL storage.

Managed disks are block storage for VMs (Standard HDD, Standard SSD, Premium SSD, Premium SSD v2, Ultra).

Redundancy:

  • LRS: three copies in one datacenter.
  • ZRS: copies across availability zones in a region.
  • GRS / GZRS: additionally replicated to a paired region for disaster recovery (RA- variants allow reading the secondary).

How it works

  1. Choose compute by control vs effort: VM → App Service → Functions/Container Apps.
  2. Create a storage account and choose redundancy.
  3. Use Blob for files, Queues for messaging, Files for shares.
  4. Attach managed disks to VMs as needed.
  5. Use autoscaling and monitoring for production.

Example

az group create -n rg-demo -l centralindia
az appservice plan create -g rg-demo -n plan-demo --sku B1 --is-linux
az webapp create -g rg-demo -p plan-demo -n springapi-demo123 --runtime "JAVA:17-java17"
az storage account create -g rg-demo -n stdemo12345 --sku Standard_ZRS --kind StorageV2
az storage container create --account-name stdemo12345 -n uploads --auth-mode login

Common mistakes

  • Using VMs for everything when PaaS would be simpler.
  • Choosing LRS for data that must survive a zone failure.
  • Confusing Blob storage with Azure Files.
  • Forgetting that Functions on consumption plans have cold starts.

How to answer in the interview

"For compute, VMs give full control and Scale Sets add autoscaling for identical VMs. App Service hosts web apps and APIs as a managed platform, Functions runs serverless code on events, and for containers there's AKS for managed Kubernetes and Container Apps for simpler serverless containers. For storage, a storage account offers Blob for objects, Files for shares, Queues for messaging and Tables for key-value data, VMs use managed disks, and redundancy can be LRS, ZRS or GRS. For a simple Spring Boot API I'd pick App Service or Container Apps."

Likely follow-up questions

  • Least-effort Spring Boot hosting? App Service (Java runtime) or Container Apps with a container image.
  • When choose AKS over Container Apps? When you need full Kubernetes APIs, operators or custom networking.
  • ZRS vs GRS? ZRS protects against zone failure; GRS adds a copy in another region.
