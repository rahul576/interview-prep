How should AI agents make infrastructure changes so that existing controls still apply?

AI Agents & AIOps · design · levels senior, lead

In one line

Agents should change code, not live infrastructure: they open pull requests to IaC or GitOps repositories, where plans, policy checks, scans and reviews apply; agents get read access to environments and write access to branches only, humans approve production merges, and every change links to the agent run.

Detailed explanation

Organisations have built controls around infrastructure change: code review, terraform plan output, policy as code, security scanning, change approvals and audit trails. If an agent gets cloud admin credentials and calls APIs directly, it bypasses all of them, and a single mistaken or manipulated decision can cause a large outage or security hole.

The safe pattern routes agent changes through the same path as human changes. When an agent concludes that a node pool needs more capacity, a firewall rule is missing or a deployment should be rolled back, it edits the Terraform, Helm values or Kubernetes manifests and opens a pull request to the infrastructure or GitOps repository, with an explanation and evidence. CI then runs terraform plan, policy checks (OPA/Conftest, Sentinel), security scanners such as Checkov or tfsec, and cost estimates. Reviewers see exactly what will change. Humans approve merges, at least for production, and the existing pipeline or a GitOps controller (Argo CD, Flux) applies the change.

The agent's identity needs only read access to environments for diagnosis and write access to branches, never apply rights or cloud admin roles. Every PR links to the agent run (trace ID, prompt, evidence), giving a complete audit trail. For urgent incidents, pre-approved runbook actions such as scaling within limits are the exception, still logged.

How it works

  1. Agent diagnoses with read-only access.
  2. Edits IaC in a branch; runs local validation (fmt, validate).
  3. Opens PR with rationale, evidence and run link.
  4. CI: plan, policy checks, security scans, cost estimate.
  5. Code owners review and approve; merge.
  6. Pipeline or GitOps controller applies; agent monitors outcome.

Example

# PR opened by infra-agent (run 7c21…): "Increase checkout node pool max size"
# Evidence: pending pods 45 min/day for 7 days, cluster autoscaler at max (links)
resource "azurerm_kubernetes_cluster_node_pool" "checkout" {
  name       = "checkout"
  min_count  = 3
-  max_count  = 10
+  max_count  = 16
}
deny[msg] {
  input.resource_changes[_].change.actions[_] == "delete"
  input.metadata.author_type == "agent"
  msg := "Agents may not delete infrastructure resources"
}

Common mistakes

  • Giving the agent terraform apply rights in production.
  • Separate "agent path" without the normal checks.
  • Auto-merge for agent PRs because "the agent tested it".
  • PRs without evidence, making review a guessing game.

How to answer in the interview

"Agents should never change live infrastructure directly; they change code. If an agent decides a node pool needs more capacity or a deployment should roll back, it edits the Terraform or manifests and opens a pull request with its reasoning and evidence. Then the normal controls apply: plan, policy checks, security scans and human review, and the pipeline or GitOps controller applies it after merge. The agent only has read access to environments and write access to branches, and every PR links to the agent run for audit. Pre-approved runbook actions are the exception for urgent incidents."

Likely follow-up questions

  • Urgent incident changes? Pre-approved, bounded actions with immediate audit, then reconciled in Git.
  • Drift? GitOps reconciliation reverts manual or agent changes made outside Git.
  • Policy for agent PRs? Stricter rules, such as no deletes and mandatory code owners.
