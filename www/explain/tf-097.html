How do you deal with prerequisites that cannot be created by Terraform, such as purchased domains, quota approvals or manual vendor setup?

Terraform · concept · levels mid, senior

In one line

Make prerequisites outside Terraform explicit: document them in a README and environment runbook, reference them with data sources or variables, fail early with preconditions when they are missing, and automate them wherever an API exists.

Detailed explanation

Some dependencies cannot, or should not, be created by Terraform: a purchased domain, a quota increase awaiting approval, a marketplace agreement, an ExpressRoute or Direct Connect circuit ordered from a provider, a certificate from an external CA, or manual configuration in a vendor portal. The danger is not that they exist, but that they are implicit — a new engineer creates an environment and the apply fails 40 minutes in with an obscure API error, leaving a half-built environment.

First, document them: a "Prerequisites" section in the module README and a checklist in the runbook for creating a new environment, with owners and lead times (quota requests and circuit provisioning can take days).

Second, reference instead of create. Use data sources like azurerm_dns_zone or aws_route53_zone to look up the existing zone, or pass IDs such as a circuit ID as variables. This also makes the dependency visible in code.

Third, fail early. A data source fails at plan time if the object does not exist. For more subtle conditions — enough quota, an accepted agreement, a circuit in the provisioned state — use precondition blocks or check blocks with clear error messages, so the plan stops before anything is created.

Fourth, automate where possible. Many "manual" steps have APIs: Azure Quota API and AWS Service Quotas can be requested programmatically, azurerm_marketplace_agreement accepts terms, and DNS delegation can be automated once the domain exists.

How it works

  1. List every external prerequisite with owner and lead time.
  2. Add it to the README and new-environment runbook.
  3. Reference it with a data source or variable in code.
  4. Add preconditions that check its state with a helpful message.
  5. Automate the step through its API when one exists.
  6. Run a preflight plan for new environments before the real apply.

Example

data "azurerm_dns_zone" "public" {
  name                = var.domain_name
  resource_group_name = var.dns_rg
}

data "azurerm_express_route_circuit" "er" {
  name                = var.circuit_name
  resource_group_name = var.network_rg
}

resource "azurerm_virtual_network_gateway_connection" "er" {
  # ...
  express_route_circuit_id = data.azurerm_express_route_circuit.er.id

  lifecycle {
    precondition {
      condition     = data.azurerm_express_route_circuit.er.service_provider_provisioning_state == "Provisioned"
      error_message = "ExpressRoute circuit is not provisioned by the provider yet. See runbook step 4."
    }
  }
}

Common mistakes

  • Prerequisites known only to one engineer.
  • Hard-coding IDs of external objects instead of looking them up.
  • Discovering quota limits only when the apply fails half-way.
  • Treating steps as manual although an API exists.

How to answer in the interview

"Some things live outside Terraform — buying a domain, a quota approval, a marketplace agreement or a provider-delivered circuit. I make them explicit: documented as prerequisites in the README and in a new-environment runbook. In code I reference them with data sources or variables, like looking up the existing DNS zone or passing the circuit ID, and add preconditions that fail early with a clear message instead of failing deep in an apply. Where APIs exist, I automate even these, like quota requests through the quotas API or accepting marketplace terms with a resource."

Likely follow-up questions

  • How do you avoid a new environment failing halfway on quota? A preflight script or check block querying current usage and limits before apply.
  • Should Terraform buy the domain? Usually not; registration is a business decision, then delegation is automated.
  • Data source or variable? Data source when it can be looked up reliably; variable when it lives in another account or system.
