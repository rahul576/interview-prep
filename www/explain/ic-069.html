How do you detect and remediate infrastructure drift across many Terraform stacks?

Infrastructure as Code · design · levels senior

In one line

Run scheduled plans (or HCP Terraform drift detection) for every stack, alert the owning team when the plan is non-empty, classify each drift as intentional (update code) or unwanted (reapply), reduce causes with read-only consoles and a break-glass process, and track drift metrics.

Detailed explanation

Drift is any difference between what the code and state say and what actually exists: someone scaled a group in the console during an incident, a security group rule was added by hand, another tool changed tags, or a resource was deleted. Undetected drift is dangerous because the next routine apply silently reverts or destroys the manual change, often at a bad moment.

Detection. Each stack gets a scheduled job (nightly or hourly for critical stacks) running terraform plan -refresh-only to see real-world changes, or a normal plan with -detailed-exitcode, which returns 2 when changes exist. HCP Terraform offers drift detection through health assessments; Spacelift, env0 and similar platforms have equivalents. Running hundreds of stacks needs read-only credentials and staggering to respect API limits.

Routing. A non-empty plan creates an alert or ticket for the owner (from CODEOWNERS or a stack catalogue) with a link to the diff. Noise kills these systems, so attributes that legitimately change, such as autoscaling desired counts or tags added by other systems, are excluded with ignore_changes or by moving ownership.

Classification. If the change was intentional, such as emergency scaling, the code is updated to match (codify). If it was not, the stack is reapplied to revert it, after checking nothing depends on the change. Some low-risk categories, such as missing tags or a public-access block, can be auto-remediated.

Reduce causes. Production consoles are read-only for most people; changes go through pipelines; emergency access uses a logged, time-limited break-glass role with a rule to codify within a set time. Tracking drift per team and per cause shows whether the process works.

How it works

  1. Scheduler runs refresh-only plans per stack with a read-only role.
  2. Exit code 2 or a non-empty JSON triggers an alert to the owner.
  3. Owner classifies: codify or revert.
  4. Known categories auto-remediate; others need a human.
  5. Dashboard tracks drift count, age and cause.

Example

terraform plan -refresh-only -detailed-exitcode -out drift.tfplan
rc=$?
if [ "$rc" -eq 2 ]; then
  terraform show -json drift.tfplan > drift.json
  ./notify-owner --stack "$STACK" --diff drift.json
fi

Common mistakes

  • Detection without ownership, so alerts are ignored.
  • Noisy alerts from attributes that are supposed to change.
  • Reverting an emergency fix during an ongoing incident.
  • Fixing drift by hand in the console again.

How to answer in the interview

"Every stack gets a scheduled plan, for example nightly with refresh-only and detailed exit codes, or HCP Terraform's drift detection, and a non-empty plan creates an alert or ticket for the owning team with the diff. Each drift is classified: intentional changes, like emergency scaling during an incident, get codified; unwanted ones are reverted by reapplying. To reduce drift at the source, production consoles are read-only for most people and emergency access uses a logged break-glass role. I track drift counts per team and cause so we can see if it's improving."

Likely follow-up questions

  • Which drift would you auto-remediate? Low-risk, well-understood items like missing tags or a removed public-access block.
  • Refresh-only vs normal plan? Refresh-only shows real-world changes; a normal plan also includes unapplied code changes.
  • How do you avoid noise? Ignore attributes owned by other systems and give each stack a clear owner.
