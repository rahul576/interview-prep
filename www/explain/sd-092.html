For a new API with unpredictable traffic, would you choose serverless functions or containers?

Architecture Trade-offs · scenario · levels mid, senior

In one line

For a new API with unknown, spiky traffic I lean towards serverless (or serverless containers like Cloud Run) for scale-to-zero and no capacity planning, accepting cold starts and limits, and move to containers when load becomes steady, long-running or needs more control.

Detailed explanation

Serverless functions (AWS Lambda, Azure Functions, Google Cloud Functions) run code per event. The platform scales instances automatically, you pay per request and per GB-second, and idle costs nothing. That matches a new API whose traffic is unpredictable: no capacity planning, no over-provisioning, and built-in high availability.

The trade-offs are real. Cold starts add latency when a new instance initialises, worse for JVM and .NET runtimes than for Node, Python or Go (mitigations include provisioned concurrency, Lambda SnapStart for Java, and smaller packages). There are execution limits (Lambda: 15 minutes, memory and payload caps), restricted control of networking and runtime, and vendor-specific tooling that hurts portability.

Cost crosses over: at low or bursty volume serverless is cheaper; at high steady throughput, always-on containers on ECS, EKS or AKS usually win because you pay for capacity you fully use. Containers also suit long-running or stateful work such as WebSockets, streaming and background workers, and give portability across clouds.

A classic serverless pitfall is database connections: thousands of concurrent function instances can exhaust a relational database. Use a pooler like RDS Proxy or PgBouncer, or a serverless-friendly datastore (DynamoDB, HTTP-based drivers). The pragmatic middle ground is serverless containers (Cloud Run, Azure Container Apps, AWS Fargate with autoscaling): standard container images, scale to zero (Cloud Run, Container Apps), and an easy path to Kubernetes later.

How it works

  1. Estimate traffic shape: peak-to-average ratio, idle periods, latency SLO.
  2. Check constraints: request duration, payload size, runtime, persistent connections.
  3. Model cost at expected and 10x volume for both options.
  4. Plan database access: connection pooling or a serverless-native store.
  5. Package as a container so you can move between Cloud Run, Fargate and Kubernetes.
  6. Re-evaluate once traffic stabilises.

Example

# Deploy a container image to Cloud Run, scaling 0..100 instances
gcloud run deploy orders-api \
  --image=europe-docker.pkg.dev/acme/api/orders:1.4.0 \
  --region=europe-west1 \
  --min-instances=0 --max-instances=100 \
  --concurrency=80 --cpu=1 --memory=512Mi

Common mistakes

  • Ignoring cold starts for latency-sensitive Java endpoints.
  • Letting thousands of functions open direct database connections.
  • Assuming serverless is always cheaper, even at high constant traffic.
  • Building a distributed "function per endpoint" maze that is hard to test and trace.

How to answer in the interview

"For a new API with unpredictable traffic I'd start serverless, ideally serverless containers like Cloud Run or Azure Container Apps, because they scale from zero automatically and I don't pay for idle capacity. I'd watch cold starts, execution limits and database connections, using a proxy like RDS Proxy. If traffic grows into a high, steady load, or I need long-running connections like WebSockets, I'd move the same container images to ECS or Kubernetes, which becomes cheaper and gives more control."

Likely follow-up questions

  • How do you reduce Java cold starts? SnapStart or provisioned concurrency, smaller dependencies, GraalVM native images, avoiding heavy reflection at startup.
  • When is serverless more expensive? At sustained high utilisation, where reserved container capacity is cheaper.
  • How do you avoid vendor lock-in? Containers, hexagonal architecture, and keeping cloud-specific triggers at the edges.
