Explain equals(), hashCode(), and toString().

Core Java & OOP · concept · levels mid, senior

In one line

equals defines logical equality (default: reference equality), hashCode gives the bucket index for hash-based collections, and the contract says equal objects must have equal hash codes; toString gives a readable representation; override equals and hashCode together using the same fields.

Detailed explanation

All three are inherited from Object.

equals(Object o) must be an equivalence relation: reflexive (x.equals(x)), symmetric, transitive, consistent across calls, and x.equals(null) is false. The default compares references, which is right for entities with identity but wrong for value objects like Money or Email. A correct implementation checks identity, type (getClass() for strict equality or instanceof for a final class), then compares significant fields with Objects.equals. Mixing subclasses that add fields with instanceof breaks symmetry, a classic pitfall.

hashCode() returns an int. HashMap and HashSet use it to choose a bucket, then use equals to find the exact match within it. The contract:

  1. Equal objects must return the same hash code.
  2. Unequal objects may collide, but fewer collisions mean better performance.
  3. The value must be stable while the object is unchanged.

Break rule 1 by overriding only equals and a HashSet happily stores "duplicates" and map.get(equalKey) returns null, because the lookup goes to the wrong bucket. Also, if fields used in hashCode change while the object is inside a HashSet, it can no longer be found.

toString() should return a concise, informative description for logs, debuggers and error messages. The default com.shop.Order@1b6d3586 is useless. Never include passwords, tokens or full card numbers.

Records generate all three from their components. For JPA entities, be careful: base equality on a stable business key or the id with a consistent hashCode, and avoid including lazy collections in toString.

How it works

  1. map.put(k, v) calls k.hashCode() and spreads it to pick a bucket.
  2. Within the bucket it compares with equals.
  3. map.get(k2) repeats: same hash leads to the same bucket, then equals confirms.
  4. String concatenation and loggers call toString().

Example

public final class Email {
    private final String value;
    public Email(String value) { this.value = value.toLowerCase(Locale.ROOT); }

    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Email other)) return false;
        return value.equals(other.value);
    }
    @Override public int hashCode() { return value.hashCode(); }   // same field as equals
    @Override public String toString() { return "Email[" + value + "]"; }
}

// Equivalent with a record:
record EmailR(String value) {}

Common mistakes

  • Overriding equals without hashCode.
  • Writing equals(Email o) (an overload) instead of equals(Object o).
  • Using mutable fields in hashCode for objects stored in sets.
  • Printing secrets or huge collections in toString.

How to answer in the interview

"All three come from Object. equals defines logical equality; by default it's reference equality, so value objects override it to compare fields. hashCode returns the int that HashMap and HashSet use to pick a bucket. The contract is that equal objects must have the same hash code, while unequal ones may collide. So I always override them together, using the same fields, with Objects.equals and Objects.hash, or I just use a record. If you break it, a HashSet keeps duplicates or a map lookup fails. toString gives a readable representation for logs, but it must never print secrets."

Likely follow-up questions

  • Why should fields used in hashCode not change while the object is in a HashSet? The object stays in the old bucket and lookups miss it.
  • getClass or instanceof in equals? getClass for strict type equality; instanceof for final classes.
  • What does a constant hashCode do? It's legal but makes every lookup O(n) or tree-based.
