How do you enforce policies on agent actions in code rather than relying on prompts?

AI Agents & AIOps · concept · levels senior, lead

In one line

Prompts can be ignored or overridden by injection, so enforce rules in code: a policy layer checks every tool call (tool, arguments, user, environment) before execution, using policy as code (OPA, Cedar) or typed checks, deny by default with allowlists, and logs decisions with human approval for exceptions.

Detailed explanation

"Never delete production resources" written in a system prompt is a request, not a guarantee. Models can misinterpret instructions, follow a user who argues persuasively, or obey prompt injection hidden in a web page, email or log line. For anything that matters, enforcement must live outside the model, between the agent and its tools.

Every tool call is intercepted by a policy enforcement point before execution. It evaluates the tool name, the arguments and the context: which user the agent acts for, the agent identity, the environment, the time, previous actions in the session. Rules are concrete: deployments only to non-production environments; refunds below £100; emails only to the company domain or existing customer addresses; SQL only SELECT on specific schemas; at most five tickets closed per minute.

Rules can be expressed as policy as code with OPA/Rego or Cedar, or as typed checks in the tool layer. The default is deny, with explicit allowlists per agent. A blocked call returns a clear message so the agent can adapt, is logged for audit and monitoring, and may trigger a human approval flow for legitimate exceptions. Tools should also run with credentials scoped to what policy allows, so even a policy bug has a limited blast radius. This makes behaviour predictable regardless of what the model is persuaded to try.

How it works

  1. Agent proposes a tool call with arguments.
  2. Gateway builds a policy input: tool, args, user, agent, environment.
  3. Policy engine returns allow, deny or require-approval.
  4. Allowed calls execute with scoped credentials.
  5. Denied calls return a reason; approvals route to a human.
  6. All decisions logged and monitored.

Example

permit (
  principal is Agent,
  action == Action::"issue_refund",
  resource is Order
) when {
  context.amount_gbp <= 100 &&
  resource.customer == context.on_behalf_of_customer
};

forbid (principal is Agent, action == Action::"delete_resource", resource)
when { resource.environment == "prod" };

Common mistakes

  • Relying on system prompt instructions for critical limits.
  • Checking the tool name but not its arguments.
  • Allow-by-default with a denylist of known bad actions.
  • Policy layer in the agent process that the agent's code can bypass.

How to answer in the interview

"Prompt instructions are guidance, not enforcement: the model can misunderstand them and injection can override them. So I put a policy check between the agent and its tools. Every tool call is evaluated on the tool, its arguments and context like user, agent identity and environment, using policy as code such as OPA or Cedar or typed checks. It's deny by default with explicit allowlists, for example refunds under a limit or deploys only to non-prod. Blocked calls are logged and can go to human approval. That keeps behaviour predictable whatever the model is talked into."

Likely follow-up questions

  • Where in MCP? In a gateway or proxy in front of MCP servers, or inside each server.
  • Rate-based rules? Policy input includes session history and counters.
  • Testing policies? Unit tests with allowed and denied examples in CI.
