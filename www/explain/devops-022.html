What is the difference between liveness, readiness and startup probes?

Kubernetes · concept · levels mid

In one line

Liveness failure makes the kubelet restart the container; readiness failure removes the pod from Service endpoints without restarting; a startup probe holds off the other two until a slow app has started; probes can be HTTP, TCP, exec or gRPC, and liveness must not depend on external services.

Detailed explanation

Probes let Kubernetes distinguish between "this process is broken and needs a restart" and "this process is fine but should not get traffic right now". Mixing them up causes outages.

Liveness probe. Answers is the process healthy enough to keep running? After failureThreshold consecutive failures the kubelet kills and restarts the container. Use it for unrecoverable states such as deadlocks or a wedged event loop. The check should be cheap and local: "my process can respond".

Readiness probe. Answers should this pod receive traffic now? When it fails, the pod is marked not ready and removed from EndpointSlices, so Services and ingress stop routing to it; nothing is restarted. Readiness is used during startup and warm-up (loading caches), during temporary overload, and during shutdown. Readiness may consider critical dependencies carefully, though if every pod depends on the same database, all become unready together.

Startup probe. For slow starters such as large JVM apps or apps running migrations: while it has not yet succeeded, liveness and readiness are not run. Its budget (failureThreshold × periodSeconds) covers the worst-case start time, so liveness can stay aggressive afterwards without killing booting pods.

Mechanisms. httpGet (2xx/3xx is success), tcpSocket, exec (exit code 0) and grpc (the standard gRPC health protocol). Tune initialDelaySeconds, periodSeconds, timeoutSeconds and failureThreshold.

The classic failure. A liveness probe that checks the database: the database has a brief blip, every pod fails liveness, all restart at once, caches are cold and the restart storm becomes an outage.

How it works

  1. Container starts; startup probe runs until success or its budget expires (then restart).
  2. Readiness begins; on success the pod joins endpoints.
  3. Liveness runs periodically; repeated failures restart the container.
  4. Readiness failures remove the pod from endpoints until it recovers.

Example

startupProbe:
  httpGet: { path: /healthz, port: 8080 }
  periodSeconds: 5
  failureThreshold: 36        # up to 3 minutes to start
livenessProbe:
  httpGet: { path: /healthz, port: 8080 }   # process only, no dependencies
  periodSeconds: 10
  failureThreshold: 3
readinessProbe:
  httpGet: { path: /ready, port: 8080 }     # warm-up done, not overloaded
  periodSeconds: 5
  failureThreshold: 2

Common mistakes

  • Checking external dependencies in liveness, causing cascading restarts.
  • Same endpoint and thresholds for liveness and readiness.
  • Long initialDelaySeconds instead of a startup probe.
  • Timeouts too short for a loaded app, so healthy pods restart under load.

How to answer in the interview

"A liveness probe asks whether the container is alive; if it fails repeatedly, the kubelet restarts it, which recovers deadlocked apps. A readiness probe asks whether the pod should get traffic; if it fails, the pod is removed from the Service endpoints but not restarted, which is right for warm-up, overload or shutdown. A startup probe is for slow starters: it disables the other two until it succeeds, so a slow JVM isn't killed while booting. Probes can be HTTP, TCP, exec or gRPC. The big mistake is checking the database in liveness, because a blip then restarts every pod at once."

Likely follow-up questions

  • What if readiness and liveness use the same endpoint? Under overload a pod that should just stop receiving traffic gets restarted, worsening the overload.
  • Can readiness check dependencies? Carefully; a shared dependency failing makes every pod unready together.
  • What happens if there's no readiness probe? The pod is considered ready as soon as its containers start.
