Compare cache-aside, read-through, write-through and write-behind caching.

Caching · concept · levels mid, senior

In one line

Cache-aside has the app load on a miss, read-through lets the cache load from the DB itself, write-through writes cache and DB synchronously, and write-behind writes the cache and flushes to the DB asynchronously; the choice trades consistency and durability against latency.

Detailed explanation

Cache-aside (lazy loading) is the most common pattern with Redis. The application reads the cache; on a miss it queries the database and stores the result with a TTL. On writes it updates the database and deletes the cache key so the next read reloads it. It is simple and resilient: if the cache is down the app is slower but correct. The downsides are a miss penalty and a small window of staleness.

Read-through is the same idea, but the loading logic lives in the cache layer (a CacheLoader in Caffeine, a loader in Hazelcast, or Spring's @Cacheable). The application only talks to the cache, which keeps code clean.

Write-through sends each write to the cache and the database in the same operation, so the cache is always warm and consistent with the DB. Writes are slower, and you may cache data that is never read.

Write-behind (write-back) acknowledges the write once it is in the cache and flushes to the database later, often batched. Writes are very fast and DB load is reduced, but if the cache node fails before flushing, data is lost, and the DB is temporarily behind.

How it works

  1. Read request checks the cache first.
  2. On hit, return the value.
  3. On miss, the app (cache-aside) or the cache (read-through) loads from the DB and stores it with a TTL.
  4. On write, either update DB and invalidate (cache-aside), update both synchronously (write-through), or update cache and queue a DB write (write-behind).
  5. TTLs and event-based invalidation limit staleness.

Example

// Cache-aside with Spring + Redis
public Product get(long id) {
    Product p = redis.opsForValue().get("product:" + id);
    if (p != null) return p;
    p = repo.findById(id).orElseThrow();
    redis.opsForValue().set("product:" + id, p, Duration.ofMinutes(10));
    return p;
}

@Transactional
public void update(Product p) {
    repo.save(p);
    redis.delete("product:" + p.getId());   // invalidate, don't overwrite
}

Common mistakes

  • Updating the cache value on write instead of deleting it, causing races that leave stale data.
  • No TTL, so stale entries live forever.
  • Using write-behind with a non-persistent, non-replicated cache for important data.
  • Same TTL for all keys, causing mass expiry and a stampede.

How to answer in the interview

"Cache-aside is my default: read from the cache, on a miss load from the database and set it with a TTL, and on writes update the database and delete the key. Read-through is the same flow but the cache owns the loading code. Write-through updates cache and database together, so reads are always warm but writes are slower. Write-behind writes only to the cache and flushes later, which is the fastest but can lose data if the cache fails. For a product catalogue I'd use cache-aside with TTL and invalidation events; for a shopping cart I'd keep it in a persistent, replicated Redis or write through to the database rather than risk write-behind."

Likely follow-up questions

  • Why delete rather than update the cache on write? Two concurrent writers can otherwise leave an older value in the cache.
  • How do you prevent a cache stampede? Request coalescing or a short lock, TTL jitter and stale-while-revalidate.
  • Where would you put a local cache? Caffeine in-process for tiny hot data, in front of Redis, with short TTLs.
