Design a document retrieval system for an organisation using MCP.

MCP Servers · design · levels mid, senior, lead

In one line

Put a normal retrieval stack (connectors, chunking, embeddings, hybrid search index with ACL metadata) behind an MCP server that exposes a search tool returning compact, cited snippets, full documents as resources by URI, and per-user permission trimming on every query.

Detailed explanation

MCP does not replace search infrastructure; it is the interface the AI uses to reach it. The hard work sits behind the server. Connectors pull documents from SharePoint, Confluence, Google Drive and file shares, split them into chunks, create embeddings, and store them in a hybrid index (vector similarity plus keyword/BM25) together with metadata: source, owner, department, last-updated date and the access control list copied from the source system. Hybrid search matters because embeddings are good at meaning while keywords catch product codes, ticket numbers and exact names.

The MCP surface should be small and model-friendly. A search_documents tool takes a query, optional filters (source, date range, department) and a limit, and returns a compact page of results: title, short snippet, updated date, a citation and a resource URI, plus a cursor for pagination. Returning whole documents from search would flood the context window. When the model or the user needs the full text, it reads the document as a resource by URI, so content is fetched only on demand.

Security and freshness are what separate a demo from a production system. Every query is permission-trimmed using the user identity from the OAuth access token, so people only find what they could open in the source system. Incremental sync (webhooks or change feeds, plus periodic full reconciliation) keeps the index current and makes sure deletions and permission changes propagate quickly.

How it works

  1. Connectors ingest and sync documents, chunk them, embed them and store chunks with metadata and ACLs.
  2. The client calls search_documents with the user's OAuth token.
  3. The server resolves the user and groups, runs hybrid search with an ACL filter, and optionally re-ranks.
  4. It returns a small page of snippets with titles, dates, citations and URIs, plus a next cursor.
  5. The model reads selected documents via resources/read and answers with citations.

Example

{
  "name": "search_documents",
  "arguments": { "query": "parental leave policy India", "source": "sharepoint", "limit": 5 },
  "result": {
    "items": [
      { "title": "HR Leave Policy 2026", "snippet": "Employees in India are entitled to...",
        "updated": "2026-09-14", "uri": "docs://sharepoint/hr/leave-policy-2026" }
    ],
    "nextCursor": "eyJvZmZzZXQiOjV9"
  }
}

Common mistakes

  • Indexing with a service account and forgetting to filter by the user's permissions.
  • Returning full documents from search and blowing the context budget.
  • Not propagating deletions, so removed or confidential files remain findable.
  • Pure vector search that misses exact identifiers.
  • No dates in results, so the model cites outdated versions.

How to answer in the interview

"Behind the MCP server I'd build a standard retrieval pipeline: connectors that sync SharePoint, Confluence and Drive, chunk and embed documents, and store them in a hybrid index with metadata and ACLs. The server exposes a search tool that returns a small, paginated list of snippets with titles, dates, citations and URIs, and exposes full documents as resources so they're read only when needed. Every query is trimmed to the user's permissions using the identity from their OAuth token, and incremental sync keeps the index fresh, including deletions. Then I'd measure retrieval quality with a labelled test set before rolling it out."

Likely follow-up questions

  • How do you evaluate retrieval quality? Build a labelled query set and track recall@k, MRR or nDCG, plus answer faithfulness and citation accuracy.
  • Why hybrid search? Vectors capture meaning; keywords catch exact codes and names; combining them improves recall.
  • How fast must permission changes apply? Ideally near real time; check ACLs at query time or re-check against the source for sensitive content.
