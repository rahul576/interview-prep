Design a stock exchange order matching engine.

Classic Design Problems · design · levels senior, lead

In one line

An exchange matching engine keeps an in-memory order book per symbol with price-time priority, runs single-threaded and deterministic, receives orders through a sequencer that writes an event log, and uses hot standbys replaying the same log for instant failover; risk checks happen before orders reach it.

Detailed explanation

Requirements are unusual: microsecond latency, strict fairness (who was first matters legally), no lost orders and full auditability.

The order book holds buy orders (bids) sorted by highest price and sell orders (asks) by lowest; within a price level, orders queue by arrival time. An incoming buy at ₹101 matches the best ask ≤ ₹101, oldest first, possibly across several levels.

Single-threaded matching per symbol avoids locks and context switches, gives predictable latency and makes the engine deterministic: the same input sequence always produces the same trades. That enables state machine replication: the sequencer assigns a global sequence number and persists each input to the event log; primary and standby engines consume the identical log, so a standby can take over within milliseconds, and any state can be rebuilt by replay.

Patterns like the LMAX Disruptor (ring buffer, mechanical sympathy) and kernel-bypass networking push throughput to millions of orders per second.

How it works

  1. Gateway: authenticate, validate, pre-trade risk checks (limits, margin).
  2. Sequencer: stamp sequence number, persist/replicate to event log.
  3. Matching engine: update book, emit fills/acks in order.
  4. Outputs: trade confirmations, market data (often UDP multicast), clearing feed.
  5. Standby replays log; failover on heartbeat loss.

Example

Asks: 101.0 × 300 (t1), 101.0 × 200 (t2), 101.5 × 500
Incoming BUY 400 @ 101.0 → fills 300 @ t1, 100 @ t2; remaining ask 101.0 × 100 (t2)

Common mistakes

  • Multi-threaded matching on the same book with locks.
  • Using wall-clock timestamps from different servers for priority.
  • Relying on databases in the hot path.

How to answer in the interview

"Orders pass risk checks in the gateway, then a sequencer stamps and durably logs them, defining the official order. Per symbol, a single-threaded in-memory engine applies price-time priority, which is fast and deterministic. Because it's deterministic, hot standbys consume the same event log and can take over immediately, and we can rebuild state by replay. Fills and market data are published from the engine's output stream."

Likely follow-up questions

  • Why single-threaded is faster? No locks/contention, cache-friendly, predictable.
  • Order types? Limit, market, IOC, FOK, stop: handled in the engine logic.
  • How to scale? Shard symbols across engines.
