What are container jobs and service containers in Azure Pipelines?

Azure DevOps & Pipelines · concept · levels mid, senior

In one line

A container job runs all steps of a job inside a specified container image, giving a reproducible build environment; service containers start sidecar dependencies (PostgreSQL, Redis, brokers) for the job's lifetime, reachable by service name (container job) or mapped localhost ports (host job); both need Docker on the agent, mainly Linux.

Detailed explanation

Container jobs: with container: mcr.microsoft.com/dotnet/sdk:8.0 on a job, the agent pulls the image, starts it, mounts the workspace, and runs every step inside it. The exact SDK, compiler and tool versions are defined by the image, which developers can also use locally or in dev containers, so "works on my machine" problems shrink. Different jobs can use different images on the same agent pool, avoiding tool conflicts on shared self-hosted agents. Images can come from ACR or Docker Hub via a container resource with an endpoint. Requirements: Docker on the agent, Linux agents (Windows container jobs are possible but limited), and images that can run the agent's Node-based task handlers (most standard images work; minimal images may need tweaks). Some steps (like host-level Docker builds) are harder from inside a container.

Service containers: declared under resources.containers and attached to a job with services:. Azure Pipelines starts them before the job and stops them after, creating a Docker network:

  • If the job runs in a container, services are reachable by their name (postgres:5432).
  • If the job runs on the host, map ports (5432:5432) and connect to localhost.

This is ideal for integration tests against a real database, cache or message broker without shared test environments.

Reliability tips: services may start before they're ready, so wait for readiness (a health check loop or pg_isready), use pinned image tags, seed data in a setup step, and keep tests isolated (fresh schema per run). For bigger setups, Testcontainers in the test code or docker compose steps are alternatives.

How it works

  1. Agent pulls the job image and service images.
  2. Creates a Docker network and starts services.
  3. Starts the job container with workspace mounted.
  4. Runs steps inside the job container.
  5. Tears down containers after the job.

Example

resources:
  containers:
  - container: pg
    image: postgres:16
    env: { POSTGRES_PASSWORD: test }
  - container: redis
    image: redis:7
jobs:
- job: integration
  pool: { vmImage: ubuntu-latest }
  container: mcr.microsoft.com/dotnet/sdk:8.0
  services:
    postgres: pg
    cache: redis
  steps:
  - script: |
      until (echo > /dev/tcp/postgres/5432) 2>/dev/null; do sleep 1; done
      dotnet test tests/Integration --logger trx
    env:
      ConnectionStrings__Db: Host=postgres;Username=postgres;Password=test
      Redis__Host: cache:6379

Common mistakes

  • Not waiting for the service to be ready, causing flaky tests.
  • Using localhost from a container job (use the service name).
  • latest tags for service images.
  • Expecting container jobs on macOS or most Windows agents.

How to answer in the interview

"A container job specifies an image, and the agent runs every step inside that container instead of on the host, which gives a reproducible environment with exact SDK and tool versions that developers can use locally too. Service containers are extra containers started alongside the job for dependencies like PostgreSQL or Redis during integration tests; they live for the job and are reachable by service name when the job runs in a container, or through mapped ports on the host. Both need Docker on the agent, so they're mainly for Linux agents. I make tests reliable by waiting for readiness and pinning image versions."

Likely follow-up questions

  • Reliable DB integration tests in CI? Readiness checks, pinned images, fresh schema per run, migrations as part of the test.
  • Container job vs Docker build step? Container job is the execution environment; a Docker step builds images.
  • Testcontainers? Manages containers from test code; works on any Docker-capable agent.
