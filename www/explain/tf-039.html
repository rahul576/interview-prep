A data source in your plan fails because the resource it reads is created in the same apply. How do you fix it?

Terraform · scenario · levels mid, senior

In one line

Terraform reads data sources during plan when all their arguments are known, so a lookup for something created in the same apply fails; the fix is to reference the resource directly, add an explicit dependency only if truly needed, or split configurations when another team owns the object.

Detailed explanation

A data source is a read operation. If its arguments are literal strings or known variables, Terraform executes it during the plan phase, before anything is created. A data source such as data "azurerm_key_vault" "kv" { name = "kv-orders-prod" } therefore runs while the vault does not exist yet, and the plan fails with "not found".

The real problem is a design smell: you are using a data source to look up something this same configuration manages. The resource block already exposes every attribute, so azurerm_key_vault.kv.id gives you the value directly and also creates the correct implicit dependency in the graph.

Sometimes a data source does have value. Then make the data source depend on the resource, either by passing an attribute such as azurerm_kubernetes_cluster.main.name (which is known only after create on first run) or with depends_on. Terraform then defers the read to apply time. The cost is that the data source results are unknown during plan, and anything that uses them shows "known after apply"; with depends_on, Terraform may defer the read on every plan whenever the dependency has pending changes, which can cascade into unexpected replacements in dependent resources.

If the object belongs to another team or lifecycle, it does not belong in the same apply at all: create it in a separate configuration that runs earlier, and look it up with a data source afterwards.

How it works

  1. Plan starts; Terraform evaluates each data source whose arguments are known.
  2. The provider calls the API; the object does not exist, so the read fails.
  3. Replace the data source with direct resource references where possible.
  4. If a data source is still needed, make its inputs depend on the resource so the read is deferred to apply.
  5. For cross-team objects, move creation to an earlier, separate state.

Example

# Bad: fails on first plan because the vault is created in this run
data "azurerm_key_vault" "kv" {
  name                = "kv-orders-prod"
  resource_group_name = "rg-orders"
}

# Good: reference the managed resource directly
resource "azurerm_key_vault_secret" "db" {
  name         = "db-password"
  value        = random_password.db.result
  key_vault_id = azurerm_key_vault.kv.id
}

Common mistakes

  • Adding depends_on to data sources by habit, causing perpetual "known after apply" values.
  • Running apply twice as a workaround instead of fixing the dependency.
  • Mixing resources owned by different teams in one configuration.

How to answer in the interview

"Data sources are read during plan when their arguments are known, so if one looks up a resource created in the same run, it fails with not found. The proper fix is not to use a data source for something I manage: I reference the resource attributes directly, which also creates the dependency. If I really need a data source, I make it depend on the resource so the read is deferred to apply, accepting unknown values in the plan. And if the object is owned by another team, it belongs in a separate configuration applied first."

Likely follow-up questions

  • Why can deferred reads cause replacements? Unknown values flow into force-new arguments, so Terraform must plan a replacement.
  • When are data sources the right tool? For objects managed elsewhere: shared networks, images, existing identities.
  • How do you share values across states? Outputs, data sources or a parameter store.
