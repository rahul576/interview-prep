What is the difference between MCP and native function calling in model APIs?

MCP Servers · concept · levels entry, mid, senior

In one line

Function calling is a model API feature: you send tool definitions, the model returns a call request, and your application executes it; MCP standardises how tools are discovered and served by separate, reusable servers across hosts and models; they are complementary, since hosts convert MCP tools into function definitions.

Detailed explanation

Function calling (also called tool use) works inside a single request-response cycle with a model provider. You pass a list of tool definitions with names, descriptions and JSON Schemas. The model replies with a structured request, "call get_weather with {city: "Pune"}". Your code runs the function, sends the result back, and the model continues. Everything about those tools lives in your application: their definitions, implementation, authentication and hosting. If ten applications need GitHub access, ten teams write ten GitHub integrations, each in the format of whichever model API they use.

MCP standardises the other side of the problem: how tools, plus resources and prompts, are discovered and served by independent servers over a common protocol (JSON-RPC over stdio or HTTP). A GitHub MCP server written once can be used by any MCP-compatible host (desktop chat apps, IDEs, CLI agents, custom agents) with any model. MCP also standardises things function calling does not address: capability negotiation, change notifications, authorization for remote servers, progress, and server-initiated requests like elicitation.

They work together. A typical host connects to MCP servers, calls tools/list, converts each MCP tool into the function definition format of its model API, and sends them with the prompt. When the model emits a function call, the host maps it back to the right server and sends tools/call. The model never "speaks MCP"; it sees function definitions.

You might skip MCP when one application uses one model with a few tools that only it needs: plain function calling is simpler.

How it works

  1. Host connects to MCP servers and lists their tools.
  2. Host translates MCP tool schemas into the model API's tool format.
  3. Model returns a tool call with arguments.
  4. Host routes it to the right server via tools/call.
  5. Host returns the result to the model as a tool result.

Example

# Host side: MCP tools -> model API tools
mcp_tools = await session.list_tools()
api_tools = [{
    "name": t.name,
    "description": t.description,
    "input_schema": t.inputSchema,
} for t in mcp_tools.tools]

response = client.messages.create(model=MODEL, tools=api_tools, messages=history)
for block in response.content:
    if block.type == "tool_use":
        result = await session.call_tool(block.name, block.input)
        history.append(tool_result(block.id, result.content))

Common mistakes

  • Framing them as competitors.
  • Thinking the model talks to MCP servers directly.
  • Building an MCP server for a single internal script that only one app uses.
  • Assuming MCP fixes tool-selection quality; descriptions still matter.

How to answer in the interview

"Function calling is a model API feature: you send tool definitions, the model asks to call one with arguments, your application executes it and sends back the result. All of the tools' definitions, execution and auth live inside your app, so every app that wants GitHub writes its own GitHub tools. MCP standardises the other side: how tools, resources and prompts are discovered and served by separate servers over a common protocol, so one GitHub MCP server works with any MCP host and any model. They're complementary: a host lists tools from its MCP servers, converts them into the function definitions of its model API, and forwards the model's calls to the right server."

Likely follow-up questions

  • When skip MCP? One app, one model, a few private tools.
  • Does the model need MCP support? No, only the host does; the model sees function definitions.
  • What does MCP add beyond tools? Resources, prompts, notifications, auth and server-initiated requests.
