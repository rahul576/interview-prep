Can HashMap contain null keys and null values?

Collections · concept · levels entry, mid

In one line

Yes: HashMap allows one null key (hash treated as 0, so bucket 0) and any number of null values, which makes get() returning null ambiguous; Hashtable and ConcurrentHashMap reject both, and TreeMap rejects a null key with natural ordering.

Detailed explanation

HashMap's internal hash(key) method returns 0 for a null key instead of calling hashCode(), so the null key always lands in bucket 0. Lookups compare keys with == or equals, and null is handled without a NullPointerException. Since keys are unique, a second put(null, x) simply replaces the value. Values are not hashed at all, so many null values are allowed. LinkedHashMap inherits the same behaviour.

This creates an ambiguity: map.get(k) returns null both when k is absent and when k is mapped to null. If the difference matters, use containsKey(k), getOrDefault(k, fallback), or better, avoid storing nulls at all (use Optional in your domain or simply omit the key). Note getOrDefault returns the stored null if the key is present with a null value. Methods like merge, compute and computeIfAbsent treat a null result as "remove/absent", which is another reason to avoid null values.

TreeMap must compare keys, so with natural ordering put(null, v) throws NullPointerException; a null-friendly comparator such as Comparator.nullsFirst(...) allows it. Null values are fine.

Hashtable and ConcurrentHashMap throw NullPointerException for null keys or values. In a concurrent map you cannot do containsKey then get atomically, so null must unambiguously mean "absent". The immutable Map.of also rejects nulls.

How it works

  1. put(null, v) → hash(null) = 0 → index 0.
  2. Search bucket 0 for a key that == null; replace or insert.
  3. get(null) follows the same path.
  4. Null values are stored like any other reference.

Example

Map<String, String> m = new HashMap<>();
m.put(null, "A");
m.put(null, "B");                 // replaces, size 1
m.put("x", null);
m.put("y", null);                 // many null values

m.get("x");                       // null - present with null
m.get("z");                       // null - absent!
m.containsKey("x");               // true

new ConcurrentHashMap<String, String>().put("k", null); // NullPointerException
new TreeMap<String, String>().put(null, "v");           // NullPointerException

Common mistakes

  • Using get(k) == null to test for presence.
  • Assuming all Map implementations accept nulls.
  • Storing null values and then using merge/compute, which treat null as removal.
  • Saying HashMap allows multiple null keys.

How to answer in the interview

"Yes. HashMap allows one null key, which it handles by treating the hash as zero, so it sits in bucket zero, and putting another null key just replaces it. It allows any number of null values. That makes get returning null ambiguous, missing or mapped to null, so I use containsKey or getOrDefault when it matters, or I avoid storing nulls. TreeMap rejects a null key with natural ordering because it has to compare. Hashtable and ConcurrentHashMap reject both null keys and values, because in concurrent code you couldn't safely tell absent from null."

Likely follow-up questions

  • Why does ConcurrentHashMap forbid nulls? A null from get must mean absent; there's no atomic way to check otherwise.
  • Does LinkedHashMap allow null? Yes, same as HashMap.
  • Does Map.of allow nulls? No, it throws NullPointerException.
