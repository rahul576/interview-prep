How do you make containers immutable and read-only at runtime?

Docker · concept · levels senior

In one line

An immutable container is never changed after it starts: you run it with a read-only root filesystem (docker run --read-only or Kubernetes readOnlyRootFilesystem: true), mount tmpfs or volumes only for the paths that must be writable, and ship every change as a new image.

Detailed explanation

By default every container gets a thin writable layer on top of its image. Anything the process writes there, including whatever an attacker drops after exploiting the app, survives until the container is removed. If people "hotfix" a running container with docker exec, replicas drift apart and the image in the registry no longer describes what is actually running.

Immutability fixes both problems. With a read-only root filesystem the kernel refuses writes to the image filesystem, so an attacker cannot install tools, change binaries or plant a cron job, and the app behaves the same in every replica. The rule becomes rebuild and redeploy, never patch in place, which also makes rollbacks trivial: redeploy the previous digest.

Real applications still need a few writable paths: /tmp, a cache, a PID file, or a staging folder for uploads. These are mounted explicitly as tmpfs (in memory, gone on restart, can be sized and marked noexec) or as volumes when the data must persist. Logs go to stdout/stderr, not files. Turning read-only on also works as a test: anything that breaks shows you where the app writes unexpectedly.

How it works

  1. Find where the app writes: run it normally, then docker diff <container> lists added (A) and changed (C) files in the writable layer.
  2. Change the app or image so logs go to stdout and config is read from env or mounted files.
  3. Run with --read-only and add --tmpfs or volume mounts for each legitimate writable path.
  4. Harden further: non-root user, dropped capabilities, no-new-privileges.
  5. In Kubernetes, set readOnlyRootFilesystem: true and use emptyDir (optionally medium: Memory) for scratch space; enforce it with Pod Security or Kyverno policies.

Example

docker run -d --name api --read-only \
  --tmpfs /tmp:rw,noexec,nosuid,size=64m \
  -v api-uploads:/app/uploads \
  --user 10001 --cap-drop ALL --security-opt no-new-privileges \
  myregistry/api:1.8.3
securityContext:
  readOnlyRootFilesystem: true
  runAsNonRoot: true
volumeMounts:
  - { name: tmp, mountPath: /tmp }
volumes:
  - name: tmp
    emptyDir: { medium: Memory, sizeLimit: 64Mi }

Common mistakes

  • Enabling read-only without checking writable paths, then watching the app crash on startup (Nginx cache dirs and Java temp files are classics).
  • Mounting a big writable volume over / or /app, which defeats the purpose.
  • Writing log files inside the container instead of to stdout.
  • Treating docker exec fixes as acceptable in production.

How to answer in the interview

"An immutable container is one we never modify after start; any change is a new image and a redeploy. I enforce that with a read-only root filesystem, --read-only in Docker or readOnlyRootFilesystem: true in Kubernetes. Before turning it on I run the app and use docker diff to see where it writes, then I give it tmpfs or emptyDir for /tmp and caches, and volumes only for data that must persist. Logs go to stdout. The benefits are security, because an attacker can't persist tools or modify binaries, and consistency, because every replica runs exactly what's in the image, so rollbacks are just redeploying the old digest."

Likely follow-up questions

  • How do you find which paths the app writes to? Run it and use docker diff, check errors after enabling read-only, or trace with strace/inotifywait in a test environment.
  • Is tmpfs data safe from attackers? No, it is writable while running; mount it noexec and keep it small, but it is lost on restart, so nothing persists.
  • Does read-only stop all attacks? No; it is one layer alongside non-root, dropped capabilities, seccomp and network policies.
