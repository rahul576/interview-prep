How do you integrate AKS authentication with Entra ID and control access with Azure RBAC?

Azure Kubernetes (AKS) · concept · levels mid, senior

In one line

Use AKS-managed Entra ID integration for authentication, Azure RBAC for Kubernetes authorization (or Kubernetes RBAC bound to Entra groups), disable local accounts, sign in with kubelogin, and protect admin access with Conditional Access and PIM.

Detailed explanation

Authentication: with Entra ID integration, kubectl gets a token from Entra ID, so users sign in with their corporate identity, MFA and device policies. Without it, a shared client certificate (the admin kubeconfig) grants full access to anyone who has the file, which is impossible to audit or revoke individually.

Authorization has two options:

  • Kubernetes RBAC with Entra groups: Roles and RoleBindings reference group object IDs; flexible but managed inside each cluster.
  • Azure RBAC for Kubernetes authorization: built-in roles Azure Kubernetes Service RBAC Reader, Writer, Admin and Cluster Admin are assigned in Azure at cluster or namespace scope (<cluster-id>/namespaces/<ns>). Access is then managed, reviewed and audited like any other Azure permission and can be assigned at scale with IaC. Custom Azure roles can express finer permissions. Users also need Azure Kubernetes Service Cluster User Role to download the kubeconfig.

Disable local accounts (--disable-local-accounts) so az aks get-credentials --admin no longer works and every action is tied to an identity in the audit log.

kubelogin is the client-go credential plugin that obtains Entra tokens. It supports interactive browser login, device code, Azure CLI reuse, service principal, managed identity and workload identity, so pipelines authenticate without static secrets (kubelogin convert-kubeconfig -l azurecli or -l workloadidentity).

Conditional Access applies to sign-ins to the AKS server application, for example requiring compliant devices. PIM provides just-in-time activation of admin roles with approval and time limits, so nobody holds standing cluster-admin rights.

How it works

  1. Enable Entra integration and Azure RBAC; disable local accounts.
  2. Assign Reader/Writer at namespace scope to team groups.
  3. Make Cluster Admin eligible via PIM, not permanent.
  4. Developers run az aks get-credentials and kubelogin.
  5. Pipelines use workload identity or managed identity with kubelogin.

Example

az aks update -g rg-apps -n aks-prod --enable-aad --enable-azure-rbac --disable-local-accounts

az role assignment create --assignee-object-id $TEAM_GROUP_ID \
  --role "Azure Kubernetes Service RBAC Writer" \
  --scope "$AKS_ID/namespaces/orders"

az aks get-credentials -g rg-apps -n aks-prod
kubelogin convert-kubeconfig -l azurecli
kubectl get pods -n orders

Common mistakes

  • Keeping local accounts enabled "just in case".
  • Assigning Cluster Admin at cluster scope to whole teams permanently.
  • Using personal credentials in pipelines instead of managed or workload identity.
  • Forgetting the Cluster User role, so users can't get a kubeconfig.

How to answer in the interview

"I enable AKS-managed Entra ID integration so users authenticate with their own identities and MFA. For authorization I prefer Azure RBAC for Kubernetes, assigning built-in roles like RBAC Reader or Writer at namespace scope to Entra groups, so access is managed and audited in Azure. Local accounts are disabled so the shared admin certificate can't be used. kubelogin handles interactive and non-interactive logins, including workload identity for pipelines. Conditional Access protects sign-ins and PIM gives just-in-time cluster admin."

Likely follow-up questions

  • Break-glass if Entra is unavailable? Emergency Entra accounts excluded from Conditional Access, tightly monitored; re-enabling local accounts via ARM as a last resort.
  • Azure RBAC vs Kubernetes RBAC? Azure RBAC centralises management; Kubernetes RBAC is more granular inside the cluster.
  • How do you audit actions? kube-audit logs include the Entra user identity.
