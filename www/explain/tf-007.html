What are Terraform Stacks, and which problems are they meant to solve?

Terraform · concept · levels senior, lead

In one line

Terraform Stacks are an HCP Terraform feature that declares components (module calls) once and deployments (environments, regions, accounts) separately, then orchestrates them in dependency order, including deferred changes for values unknown until another component is applied.

Detailed explanation

Real infrastructure is rarely one root module. A typical setup has layers (network, Kubernetes cluster, platform add-ons, applications) repeated across many deployments: dev, staging, prod-eu, prod-us, perhaps per customer or account. With plain Terraform, teams handle this with many workspaces wired by run triggers, remote state data sources, wrapper tools such as Terragrunt, or custom pipelines. All of these mean a lot of glue code and manual ordering.

A Stack solves this natively. In component configuration files (.tfcomponent.hcl), you declare component blocks, each calling a module with inputs and providers, and you wire outputs of one component into inputs of another. In deployment configuration files (.tfdeploy.hcl), you declare deployment blocks, each with its own input values and identity tokens for OIDC-based credentials. HCP Terraform then plans and applies each deployment, ordering components by their dependencies.

A notable capability is deferred changes. The classic problem is creating a Kubernetes cluster and deploying Helm charts into it in one go: the Kubernetes provider needs the cluster endpoint, which is unknown before the cluster exists. Stacks can plan what is known, apply the cluster, then plan and apply the deferred components in a follow-up step. Orchestration rules can auto-approve certain plans, and changes roll out across deployments in a controlled way.

Stacks require HCP Terraform (and are coming to Terraform Enterprise); the CLI provides terraform stacks commands for validation. Terragrunt remains the main open-source alternative.

How it works

  1. Write modules as usual.
  2. Declare components and their wiring in .tfcomponent.hcl.
  3. Declare deployments with inputs and credentials in .tfdeploy.hcl.
  4. Connect the repo to a Stack in HCP Terraform.
  5. Each commit creates plans per deployment; components run in dependency order.
  6. Deferred components are planned and applied once their inputs are known.

Example

# components.tfcomponent.hcl
component "cluster" {
  source    = "./modules/eks"
  inputs    = { region = var.region, name = var.name }
  providers = { aws = provider.aws.this }
}

component "apps" {
  source    = "./modules/apps"
  inputs    = { cluster_endpoint = component.cluster.endpoint }
  providers = { kubernetes = provider.kubernetes.this }
}
# deployments.tfdeploy.hcl
deployment "prod_eu" {
  inputs = { region = "eu-west-1", name = "prod-eu", role_arn = var.prod_role }
}
deployment "prod_us" {
  inputs = { region = "us-east-1", name = "prod-us", role_arn = var.prod_role }
}

Common mistakes

  • Treating Stacks as a free open-source CLI feature.
  • Putting every environment into one giant component instead of layering.
  • Migrating everything at once instead of one system first.

How to answer in the interview

"Stacks are an HCP Terraform feature for infrastructure that's repeated across many environments, regions or accounts and split into layers. In component files I declare components, which are module calls like network, cluster and apps, and wire them together. In deployment files I declare deployments like dev, prod-eu and prod-us, each with its own inputs and OIDC credentials. HCP Terraform orchestrates components in dependency order and can defer changes whose values aren't known yet, which solves creating a cluster and deploying into it in one flow. Before Stacks, teams used Terragrunt, workspaces with run triggers or custom pipelines."

Likely follow-up questions

  • Stacks versus Terragrunt? Hosting and cost, vendor lock-in, maturity, team skills and need for deferred changes.
  • What is a deferred change? A component planned later because an input or provider configuration is unknown until another component is applied.
  • Do modules need changes for Stacks? Usually not; providers must be passed in, not configured inside modules.
