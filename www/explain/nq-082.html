What is the purpose of the volatile keyword?

Concurrency · concept · levels mid

In one line

volatile guarantees visibility (every read sees the latest write) and ordering (no reordering across the access, via happens-before) for a single field, but it does not make compound operations like count++ atomic.

Detailed explanation

Modern CPUs have caches and store buffers, and the JIT compiler may keep a field in a register or hoist a read out of a loop. So without any synchronisation, a thread can keep reading an old value forever. The classic bug: while (!stopped) { work(); } in one thread, and stopped = true in another; the JIT can turn the loop into if (!stopped) while (true) and it never ends.

Declaring the field volatile fixes this. Under the Java Memory Model, a write to a volatile variable happens-before every subsequent read of that variable. Two consequences:

  • Visibility: readers always see the most recent write.
  • Ordering and publication: everything the writer did before the volatile write is visible to a reader after it reads that value. So you can prepare an object, then publish it by assigning it to a volatile field, and readers see it fully initialised. The compiler and CPU may not reorder ordinary accesses across the volatile access in a way that breaks this.

What volatile does not do is atomicity of compound actions. count++ on a volatile int is still read, add, write; two threads can interleave and lose an update. Check-then-act on a volatile reference is equally unsafe. For that you need synchronized, a Lock or atomic classes (which internally use volatile semantics plus CAS). Reads and writes of volatile long and double are atomic, unlike non-volatile ones, which may be split on some platforms.

Good uses: stop or status flags, a configuration reference replaced wholesale by one writer, and the instance field in double-checked locking. Volatile access is cheaper than locking but not free, as it limits optimisations.

How it works

  1. Thread A writes ordinary fields, then writes the volatile field.
  2. The JVM inserts memory barriers so those writes become visible no later than the volatile write.
  3. Thread B reads the volatile field and sees A's value.
  4. Because of happens-before, B also sees A's earlier ordinary writes.
  5. No lock is taken; nothing prevents interleaving of multi-step operations.

Example

class Worker implements Runnable {
    private volatile boolean running = true;     // without volatile the loop may never stop

    public void run() { while (running) { doWork(); } }
    public void stop() { running = false; }
}

// Double-checked locking needs volatile
class Config {
    private static volatile Config instance;
    static Config get() {
        Config c = instance;
        if (c == null) {
            synchronized (Config.class) {
                c = instance;
                if (c == null) instance = c = new Config();   // safely published
            }
        }
        return c;
    }
}

volatile int hits;
void hit() { hits++; }   // still NOT atomic: use AtomicInteger

Common mistakes

  • Using volatile for counters or check-then-act logic.
  • Making a reference volatile and assuming the referenced object's fields become thread-safe.
  • Omitting volatile in double-checked locking, risking a partially constructed object.
  • Sprinkling volatile everywhere instead of designing the sharing.

How to answer in the interview

"volatile guarantees visibility and ordering for a field. Without it a thread may keep reading a cached value and never see another thread's update, like a while-not-stopped loop that never ends. A write to a volatile variable happens-before every later read of it, so readers see the latest value and also everything the writer did before that write, and the JVM and CPU can't reorder across it. But it doesn't give atomicity: count++ on a volatile int still loses updates. I use it for simple flags, status fields written by one thread, and the instance field in double-checked locking."

Likely follow-up questions

  • Why is volatile needed in double-checked locking? Without it, the reference can be published before the constructor's writes are visible, so another thread may see a partially constructed object.
  • Is a volatile reference to a mutable list thread-safe? No; only the reference is volatile, not the list's contents.
  • Are long and double writes atomic? Not guaranteed for non-volatile fields; volatile makes them atomic.
