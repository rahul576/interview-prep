How do you handle poison messages and failures in a Kafka consumer?

Kafka · concept · levels mid, senior

In one line

Retry transient failures with backoff, send poison messages to a dead letter topic after retries so they never block the partition, use non-blocking retry topics when ordering allows, and handle deserialization errors explicitly.

Detailed explanation

Kafka consumers process a partition in order, so one record that keeps failing stops everything behind it. That is fine for a few seconds of retry during a downstream blip, but fatal for a record that can never succeed, such as malformed JSON or a reference to a deleted entity. So you must classify failures.

Transient errors (timeouts, 503s, deadlocks) deserve a few retries with exponential backoff. Permanent errors (validation failures, unknown schema, business rule violations) should not be retried at all. After retries are exhausted or for non-retryable exceptions, publish the record to a dead letter topic (DLT) with headers describing the original topic, partition, offset, exception class and message, commit the offset, and move on. Alert on DLT traffic, and build a replay tool so fixed records can be republished.

Blocking retries keep ordering but stall the partition. Non-blocking retry topics (for example orders-retry-10s, orders-retry-1m, then orders-dlt) move the failed record aside so the main partition keeps flowing, at the cost of per-key ordering: a later event for the same key may be processed before the retried one.

Deserialization errors happen before your listener runs, so a bad payload can crash-loop the consumer. In Spring Kafka, wrap the deserializer with ErrorHandlingDeserializer so the error reaches the error handler and the record goes to the DLT. Spring's DefaultErrorHandler with a DeadLetterPublishingRecoverer and @RetryableTopic implement all of this.

How it works

  1. Listener throws an exception.
  2. Error handler checks if it is retryable; if so, back off and retry.
  3. After max attempts, recoverer publishes to topic-dlt with headers.
  4. Offset is committed; partition continues.
  5. Alert fires; engineer inspects and replays.

Example

@Bean
DefaultErrorHandler errorHandler(KafkaTemplate<Object, Object> t) {
  var h = new DefaultErrorHandler(new DeadLetterPublishingRecoverer(t),
      new ExponentialBackOff(1000L, 2.0) {{ setMaxElapsedTime(30_000L); }});
  h.addNotRetryableExceptions(ValidationException.class);
  return h;
}

@RetryableTopic(attempts = "4", backoff = @Backoff(delay = 10_000, multiplier = 3))
@KafkaListener(topics = "orders")
void onOrder(Order o) { service.process(o); }

Common mistakes

  • Infinite retries on a poison message, freezing the partition.
  • DLT records without error headers, making triage impossible.
  • Using non-blocking retries where strict per-key order is required.
  • No alerting or replay process for the DLT.

How to answer in the interview

"I separate transient from permanent failures. Transient ones like a downstream timeout get a few retries with exponential backoff. A poison message must never block the partition, so after retries, or immediately for validation errors, it goes to a dead letter topic with headers about the error, the offset is committed, and an alert fires so someone can fix and replay it. In Spring Kafka that is DefaultErrorHandler with DeadLetterPublishingRecoverer, RetryableTopic for non-blocking retries, and ErrorHandlingDeserializer for bad payloads."

Likely follow-up questions

  • Ordering with retry topics? Lost per key; use blocking retries or park the whole key if order matters.
  • How do you replay from a DLT? A tool or connector republishes after a fix, with idempotent handlers.
  • What if the DLT publish fails? Do not commit; retry or stop the consumer and alert.
