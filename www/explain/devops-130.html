What tools do you use to scan code, dependencies, images and IaC for security issues?

DevSecOps · concept · levels mid, senior

In one line

I layer scanners by target: SAST (Semgrep, CodeQL, SonarQube), SCA (Dependabot/Renovate, Snyk, OWASP Dependency-Check), image scanning (Trivy, Grype), IaC scanning (Checkov, Trivy, KICS) and secret scanning (Gitleaks, TruffleHog), feeding one place with severity thresholds and tracked exceptions.

Detailed explanation

Each scanner type sees a different risk, so one tool rarely covers everything.

SAST reads source code for insecure patterns: injection, unsafe deserialisation, hard-coded credentials. Semgrep is fast with readable custom rules, CodeQL does deep data-flow analysis (free for public repos, part of GitHub Advanced Security otherwise), and SonarQube combines quality and security rules with quality gates.

SCA finds known-vulnerable or badly licensed open-source dependencies. Dependabot or Renovate open update PRs; Snyk, OWASP Dependency-Check, Trivy or Grype report CVEs; OSV-Scanner queries the OSV database. Reachability analysis in some tools tells you whether vulnerable code is actually called.

Image scanning inspects OS packages and language libraries inside container images: Trivy and Grype in CI, plus registry scanning (ECR, Harbor, Artifactory Xray) so images are re-scanned continuously as new CVEs are published.

IaC scanning checks Terraform, CloudFormation, Kubernetes manifests, Helm charts and Dockerfiles for misconfigurations such as public S3 buckets, open security groups, privileged containers or missing encryption: Checkov, KICS, and Trivy's misconfiguration scanner, which has absorbed tfsec.

Secret scanning catches keys and tokens: Gitleaks as a pre-commit hook and in CI, TruffleHog (which can verify whether found credentials are live), and platform push protection.

The practical part is operations: results go to one place (GitHub code scanning via SARIF, DefectDojo, or the vendor dashboard), builds fail only on agreed thresholds such as new critical or high fixable issues, and exceptions are recorded with an owner and expiry.

How it works

  1. Pre-commit: Gitleaks, linters.
  2. Pull request: SAST, SCA diff, IaC scan, secret scan; findings as PR comments.
  3. Build: image scan with a severity gate; SBOM generated.
  4. Registry/runtime: continuous re-scan against new CVEs.
  5. Triage: dedupe, prioritise by severity, exploitability (KEV, EPSS) and exposure.

Example

- name: IaC scan
  run: checkov -d infra/ --framework terraform --soft-fail-on LOW,MEDIUM
- name: Image scan
  run: trivy image --exit-code 1 --severity HIGH,CRITICAL --ignore-unfixed $IMAGE
- name: Secrets
  run: gitleaks detect --source . --redact --exit-code 1
- name: SAST
  run: semgrep scan --config p/owasp-top-ten --sarif -o semgrep.sarif --error

Common mistakes

  • Turning everything on at once and failing every build on legacy findings.
  • Scanning only at build time, never re-scanning deployed images.
  • Dozens of tools with no central triage or ownership.
  • Silencing findings without expiry or justification.

How to answer in the interview

"I use a scanner per layer. SAST on source with Semgrep, CodeQL or SonarQube. For dependencies, Dependabot or Renovate keep versions current and Snyk or Trivy report CVEs. Images are scanned with Trivy or Grype in CI and re-scanned in the registry because new CVEs appear for old images. Terraform and Kubernetes manifests go through Checkov or Trivy's misconfiguration scanning, which replaced tfsec, and Gitleaks runs as a pre-commit hook and in CI. Results go to one place, builds fail only on new high or critical fixable issues, and exceptions have an owner and an expiry date."

Likely follow-up questions

  • Avoid overwhelming teams? Gate on new, fixable, high-severity findings; prioritise with exploitability and reachability.
  • False positives? Tune rules, suppress in code with justification, review suppressions.
  • Who owns fixing? The service team, with security setting policy and SLAs per severity.
