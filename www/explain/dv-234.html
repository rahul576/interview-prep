How does alerting work with Prometheus Alertmanager or similar tools?

Observability & SRE · concept · levels mid, senior

In one line

Prometheus evaluates alert rules (PromQL expression plus a for duration) and sends firing alerts to Alertmanager, which groups, deduplicates, routes them by labels to receivers like PagerDuty or Slack, and supports silences and inhibition.

Detailed explanation

Alerting is split into two components on purpose. Prometheus (or a compatible engine such as Thanos Ruler, Mimir or VictoriaMetrics vmalert) regularly evaluates alerting rules. Each rule is a PromQL expression; when it returns results, the alert becomes pending, and only if it stays true for the for duration does it become firing. That duration filters out short spikes. Rules carry labels (severity, team) and annotations (summary, description, runbook URL).

Alertmanager receives firing alerts from one or more Prometheus servers and decides what to do with them. Grouping combines related alerts, for example all alerts for one cluster and alertname, into a single notification. Deduplication ensures that two HA Prometheus replicas sending the same alert produce one page. The routing tree matches labels to receivers: severity=page to PagerDuty or Opsgenie, severity=ticket to a Jira integration, informational alerts to Slack, email or Microsoft Teams. Timings like group_wait, group_interval and repeat_interval control how quickly and how often notifications are sent.

Silences mute matching alerts for a time window, for planned maintenance. Inhibition rules suppress symptom alerts when a root-cause alert is firing, for example no per-service alerts when the whole cluster is unreachable. Similar concepts exist in Grafana Alerting, Datadog monitors and CloudWatch alarms. Whatever the tool, the rule is the same: page only for urgent, actionable issues, with a runbook.

How it works

  1. Prometheus evaluates rules every evaluation interval (for example 30 s).
  2. Expression true → pending → after for → firing, sent to Alertmanager.
  3. Alertmanager deduplicates and groups by configured labels.
  4. The routing tree picks a receiver; inhibition and silences are applied.
  5. Notification is sent; resolved notifications follow when the condition clears.

Example

# alertmanager.yml (excerpt)
route:
  group_by: [alertname, cluster, service]
  group_wait: 30s
  repeat_interval: 4h
  receiver: slack-default
  routes:
    - matchers: [severity="page"]
      receiver: pagerduty-oncall
inhibit_rules:
  - source_matchers: [alertname="ClusterDown"]
    target_matchers: [severity=~"page|ticket"]
    equal: [cluster]
receivers:
  - name: pagerduty-oncall
    pagerduty_configs: [{ routing_key: "<secret>" }]
  - name: slack-default
    slack_configs: [{ channel: "#alerts", api_url: "<secret>" }]

Common mistakes

  • No for duration, so every blip pages.
  • Running a single Alertmanager instead of a clustered HA pair.
  • No inhibition, so one outage sends hundreds of pages.
  • Silences created without expiry or a comment.
  • Never testing that the route actually reaches the on-call phone.

How to answer in the interview

"In Prometheus I write alert rules: a PromQL expression with a threshold and a for duration, like error rate above five percent for five minutes, so short blips don't page. Firing alerts go to Alertmanager, which deduplicates, groups related alerts and routes them by labels like team and severity: pages to PagerDuty or Opsgenie, low-priority ones to Slack or tickets. Silences mute alerts during planned maintenance and inhibition suppresses symptom alerts when a root cause like a cluster outage is already firing. Every page must be urgent, actionable and link to a runbook."

Likely follow-up questions

  • How do you test an alert? Unit-test rules with promtool test rules, and send a synthetic alert with amtool to verify routing.
  • What if Prometheus itself is down? A dead man's switch ("Watchdog") alert that always fires; its absence pages via an external service.
  • Where do alert rules live? In Git as PrometheusRule resources, reviewed and deployed with GitOps.
