How do you identify excessive object creation in a Java application?

JVM & Performance · scenario · levels senior, lead

In one line

Excessive object creation shows up as a high allocation rate and frequent young GCs; confirm it with GC logs and JVM metrics, find the hot allocation sites with JFR or async-profiler in allocation mode, fix culprits such as boxing, string building, temporary collections and redundant mapping, and verify with JMH -prof gc.

Detailed explanation

Symptoms. CPU partly spent in GC threads, minor GCs several times per second, latency jitter under load, and an allocation rate of hundreds of MB/s or more. The number itself matters less than the trend: an allocation rate that grows faster than traffic points to a regression.

Confirm with data.

  • GC logs (-Xlog:gc*) show young GC frequency and how much Eden is filled between collections; tools like GCeasy calculate allocation and promotion rates.
  • Micrometer exports jvm.gc.memory.allocated (bytes allocated in the young generation) and jvm.gc.pause; graph allocation per request alongside request rate in Prometheus/Grafana.
  • jstat -gc shows Eden filling speed live.

Find the sources.

  • JFR: the jdk.ObjectAllocationSample event (JDK 16+) samples allocations with throttling, cheap enough for production. In JDK Mission Control, the "Allocations" view groups by class and stack trace.
  • async-profiler -e alloc builds an allocation flame graph showing exactly which methods allocate the most bytes.
  • A class histogram (jcmd GC.class_histogram) shows what lives in the heap, not what is allocated, so it is less useful for this.

Typical culprits.

  • Autoboxing in loops and in Map<Long, ...> or List<Integer>.
  • String concatenation for disabled log levels, String.format, toString.
  • Streams and lambdas in very hot, tiny loops (iterators, capturing lambdas), and temporary ArrayLists or Optionals.
  • Layered mapping (entity to DTO to view model) copying large graphs per request.
  • Reading whole payloads into byte arrays and strings instead of streaming; regex Pattern.compile inside methods.
  • new of heavy objects per call (ObjectMapper, DateTimeFormatter, Random) that should be shared.

Verify. Write a JMH benchmark for the hot method and run with -prof gc, which reports gc.alloc.rate.norm (bytes allocated per operation). Compare before and after, then confirm the allocation rate and GC frequency dropped in production.

How it works

  1. Notice frequent young GCs or high GC CPU.
  2. Measure allocation rate from logs or metrics.
  3. Profile allocations with JFR or async-profiler.
  4. Pick the widest allocation frames and fix them.
  5. Verify bytes per operation with JMH and production metrics.

Example

# Short allocation profile in production
jcmd <pid> JFR.start name=alloc duration=120s settings=profile filename=/tmp/alloc.jfr
jfr print --events jdk.ObjectAllocationSample /tmp/alloc.jfr | head

asprof -e alloc -d 60 -f /tmp/alloc.html <pid>

Common mistakes

  • Using a heap histogram to find allocation hot spots.
  • Profiling only in development with unrealistic data.
  • Micro-optimising code that is not hot.
  • Tuning GC flags before reducing allocation.

How to answer in the interview

"The symptom is a high allocation rate, often hundreds of megabytes per second, causing very frequent young GCs and CPU spent in GC. I confirm it with GC logs and the JVM metrics from Micrometer in Prometheus. Then I profile allocations with JFR's allocation sampling or async-profiler in allocation mode, which gives flame graphs of the methods allocating the most bytes. Typical culprits are autoboxing in loops, string concatenation in logging, temporary collections and streams on hot paths, mapping layers copying objects, and heavy objects like ObjectMapper created per call. After fixing them I verify with a JMH benchmark using the GC profiler, which reports allocated bytes per operation."

Likely follow-up questions

  • How do you enable allocation profiling with JFR in production safely? Use the built-in throttled ObjectAllocationSample event with the default or profile settings for a limited duration.
  • Does allocation always hurt? Allocation is cheap; the cost is the GC work and cache misses at high rates.
  • What is gc.alloc.rate.norm? JMH's bytes allocated per benchmark operation.
