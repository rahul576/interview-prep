What is the gossip protocol in Cassandra?

Databases & SQL · concept · levels senior, lead

In one line

Gossip is Cassandra's peer-to-peer protocol for sharing cluster state: every second each node exchanges versioned state with up to three other nodes, spreading membership, status, tokens, load and schema versions, which together with the phi accrual failure detector lets nodes know who is up without a master; seed nodes help new nodes join.

Detailed explanation

Because Cassandra has no central coordinator, every node must learn about every other node by itself. Gossip, inspired by how rumours or epidemics spread, does that efficiently.

Each node keeps endpoint state for every node it knows: a heartbeat (generation number, which changes on restart, plus a version that increments every second) and application state such as status (NORMAL, LEAVING, JOINING), tokens, data centre and rack, schema version, load and release version. Each value is versioned, so when two nodes compare, the newer version wins.

Once per second, the gossiper picks up to three peers: a random live node, possibly an unreachable node (to detect recovery), and possibly a seed. The exchange is a three-message handshake: SYN (digests of what I know), ACK (what you are missing and what I need), ACK2 (the requested data). Information reaches the whole cluster in a logarithmic number of rounds.

Failure detection is separate but fed by gossip. The phi accrual failure detector tracks heartbeat arrival intervals for each peer and computes a suspicion level phi, rather than using a fixed timeout; above phi_convict_threshold (default 8) the node is marked down locally.

Seed nodes are a configured list of addresses. A new node contacts them to get the initial cluster view, and nodes gossip with seeds a bit more often, which speeds convergence. After startup, seeds have no special role in reads or writes.

How it works

  1. A node starts and contacts seed nodes from cassandra.yaml.
  2. It receives the cluster state and announces itself.
  3. Every second it gossips with up to three peers using SYN/ACK/ACK2.
  4. Newer versions replace older ones in each node's state map.
  5. Heartbeat intervals feed the phi accrual detector, which marks peers up or down.
  6. Status changes, such as JOINING or LEAVING, propagate the same way.

Example

# cassandra.yaml
seed_provider:
  - class_name: org.apache.cassandra.locator.SimpleSeedProvider
    parameters:
      - seeds: "10.0.1.10,10.0.2.10"
phi_convict_threshold: 8
nodetool gossipinfo      # per-node state: generation, heartbeat, STATUS, SCHEMA
nodetool describecluster # check schema versions agree

Common mistakes

  • Making all nodes seeds, which slows bootstrap and complicates gossip.
  • Thinking seeds are masters or must always be up for the cluster to work.
  • Lowering phi_convict_threshold on flaky networks, causing nodes to flap.

How to answer in the interview

"Cassandra has no master tracking the cluster, so nodes use gossip to share state. Every second each node exchanges messages with up to three others, sending versioned information about itself and others: heartbeat, status, tokens, load, schema version, data centre and rack. Newer versions win, and information spreads to the whole cluster in a few rounds. Nodes feed gossip heartbeats into the phi accrual failure detector to decide who is down. Seed nodes are known addresses that new nodes use to join and start gossiping, but after startup they aren't special. It's scalable and has no single point of failure."

Likely follow-up questions

  • Are seeds special after startup? No; they only bootstrap the gossip view and get gossiped with slightly more often.
  • What is the phi accrual failure detector? It computes a suspicion level from heartbeat intervals instead of using a fixed timeout.
  • Does gossip carry data? No, only cluster metadata; data travels via the read/write paths and streaming.
