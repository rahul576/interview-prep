A deployment fails with a quota exceeded error for a VM family in a region. How do you handle it now and avoid it later?

Azure · scenario · levels mid, senior

In one line

Quotas are vCPU limits per VM family and region plus a total regional vCPU limit per subscription: right now request an increase (Quotas page or API, often auto-approved) or use another VM family or region; long term monitor quota usage with alerts, plan ahead, and use on-demand capacity reservations where capacity must be guaranteed.

Detailed explanation

Azure enforces several limits per subscription and region: Total Regional vCPUs, per-family vCPUs (for example Standard DSv5 Family vCPUs), plus limits for Spot/low-priority vCPUs, public IPs, and others. A deployment, a scale-out, or an AKS node pool upgrade (which surges extra nodes) fails with QuotaExceeded or OperationNotAllowed when the request would exceed a limit. The error message names the family, region, current usage and limit.

Right now:

  • Open Quotas in the portal (or use the Quota REST API / az quota) and request an increase for that family and region. Many requests are approved automatically within minutes; large jumps or capacity-constrained regions go to support review and may take longer or be denied.
  • If urgent, deploy a different VM size in a family with spare quota, or a different region if the architecture permits. For AKS, reduce maxSurge temporarily.

Avoid it later:

  • Monitor usage: the Quotas page supports alerts at thresholds (for example 80 percent), and usage can be queried by automation.
  • Include quota checks in capacity planning, before migrations, big launches, sales events and DR plans (the DR region needs quota too).
  • Raise quotas proactively in pipeline or landing zone subscription vending.

Quota vs capacity: quota is only permission to use resources. During shortages, a region can still fail allocation (AllocationFailed, SkuNotAvailable) even with quota. On-demand capacity reservations reserve actual VM capacity in a region or zone (billed whether used or not, and combinable with reserved instance discounts), guaranteeing it for critical scale-out or DR.

How it works

  1. Read the error: which family, region, usage, limit.
  2. Request increase via Quotas page or API.
  3. Workaround with another family or region if blocked.
  4. Set quota alerts and dashboards.
  5. Forecast needs and pre-request increases.
  6. Use capacity reservations for must-scale workloads.

Example

az vm list-usage --location westeurope -o table | grep -i "DSv5\|Total Regional"
az quota update --resource-name standardDSv5Family \
  --scope /subscriptions/<sub>/providers/Microsoft.Compute/locations/westeurope \
  --limit-object value=400 --resource-type dedicated
az capacity reservation group create -g rg-cap -n crg-weu --zones 1 2 3

Common mistakes

  • Assuming quota guarantees capacity.
  • Forgetting AKS upgrade surge and blue-green deployments double usage briefly.
  • No quota in the DR region.
  • Waiting until launch day to request increases.

How to answer in the interview

"Subscriptions have vCPU quotas per VM family and region plus a regional total, and the error tells me which one I hit. Immediately, I request an increase through the Quotas page or API; many are approved automatically, large ones need support. If it's urgent I switch to another VM family with free quota or another region. To avoid it, I alert on quota usage around 80 percent, include quotas in capacity planning, including the DR region, and request increases ahead of big events. For workloads that must scale during incidents, I use on-demand capacity reservations, because quota is permission, not guaranteed capacity."

Likely follow-up questions

  • Quota vs capacity? Quota is a limit; capacity is physical availability, guaranteed only by capacity reservations.
  • Why do AKS upgrades hit quota? Surge nodes temporarily add vCPUs.
  • Per-subscription or per-tenant? Quotas are per subscription and region; quota groups can share across subscriptions.
