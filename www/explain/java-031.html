What best practices do you follow when designing a REST API?

REST & API Design · concept · levels mid, senior

In one line

Design resource-oriented URIs with plural nouns, use HTTP methods and status codes correctly, version and evolve backward-compatibly, support pagination, filtering and sorting, validate input with a consistent error format (RFC 9457 Problem Details), secure with HTTPS and OAuth 2/JWT, add rate limiting, and document with OpenAPI.

Detailed explanation

A good API is predictable: once a client has used one endpoint, it can guess the others.

Resources and methods. Model nouns, in plural: /orders, /orders/{id}, /customers/{id}/orders. Let methods express the action: GET reads, POST creates, PUT replaces, PATCH partially updates, DELETE removes. Avoid verbs like /getOrders. For actions outside CRUD, use a sub-resource such as POST /orders/{id}/cancellation.

Status codes. 200 OK, 201 Created with Location, 204 No Content, 400 for validation errors, 401 unauthenticated, 403 forbidden, 404 not found, 409 conflict, 412 precondition failed, 422 where you distinguish semantic errors, 429 rate limited, 5xx for server faults. Never return 200 with "success": false.

Versioning and evolution. Prefer additive, backward-compatible changes: new optional fields, new endpoints. Clients should ignore unknown fields. For breaking changes, introduce a new version, usually in the path (/api/v2) or a header/media type, and deprecate the old one with a timeline (the Deprecation and Sunset headers help).

Collections. Always paginate; use cursor (keyset) pagination for large or fast-changing data, offset for small admin lists. Support filters and sorting via query parameters, with a maximum page size and whitelisted sort fields.

Validation and errors. Validate with Bean Validation (@Valid, @NotNull, @Size) and return a consistent error body, ideally RFC 9457 Problem Details (successor of RFC 7807), which Spring supports via ProblemDetail, with field errors and a trace id.

Security. HTTPS only; OAuth 2.0 with JWT bearer tokens validated for signature, issuer, audience and expiry; authorise per endpoint and per object; rate limiting at the gateway; no sensitive data in URLs or errors.

Operations. Idempotency keys for unsafe retries, ETags for caching and optimistic concurrency, consistent naming (camelCase JSON, ISO 8601 dates), correlation ids, and an OpenAPI contract published and checked in CI.

How it works

  1. Identify resources and relationships.
  2. Map operations to methods and status codes.
  3. Define schemas, errors and pagination in OpenAPI.
  4. Implement validation, security and rate limiting.
  5. Evolve additively; version only for breaking changes.

Example

@RestController
@RequestMapping("/api/v1/orders")
class OrderController {
    @GetMapping
    Page<OrderDto> list(@RequestParam(required = false) OrderStatus status,
                        @PageableDefault(size = 20, sort = "createdAt", direction = DESC) Pageable p) {
        return service.find(status, p);
    }
    @PostMapping
    ResponseEntity<OrderDto> create(@Valid @RequestBody CreateOrder req) {
        OrderDto o = service.create(req);
        return ResponseEntity.created(URI.create("/api/v1/orders/" + o.id())).body(o);
    }
}

Common mistakes

  • Verbs in URLs and everything as POST.
  • 200 OK for errors.
  • Unbounded list endpoints.
  • Breaking changes without versioning or deprecation.
  • Leaking stack traces in error responses.

How to answer in the interview

"I model resources as plural nouns like orders and orders/{id} and use the HTTP methods for actions. I return proper status codes: 201 with Location on create, 400 for validation, 404, 409 for conflicts. I version the API, usually /v1 in the path, but mostly evolve it with backward-compatible additive changes. Collections are paginated, cursor-based for large data, with filtering and sorting. Input is validated with Bean Validation and errors use one format, RFC 9457 Problem Details. Security is HTTPS plus OAuth 2 with JWT, object-level authorisation and rate limiting, and the contract is documented in OpenAPI."

Likely follow-up questions

  • How do you evolve an API without breaking existing clients? Additive changes, tolerant readers, new versions only for breaking changes, deprecation with Sunset dates.
  • Path or header versioning? Path is simple and visible; headers keep URIs stable.
  • What's in a good error body? Type, title, status, detail, field errors and a trace id.
