What is a data source in Terraform, and how is it different from a resource?

Infrastructure as Code · concept · levels entry

In one line

A resource is something Terraform creates, updates and destroys and tracks in state; a data source only reads information about something that already exists (created elsewhere or by another configuration) without managing it, declared with a data block and referenced as data.<type>.<name>.<attribute>, and usually read during plan.

Detailed explanation

Your configuration often needs IDs of things it must not own: the network team's VPC, a KMS key, AWS's latest AMI. That is what data sources are for.

A resource (resource "aws_vpc" "main") has a full lifecycle: Terraform creates it, detects changes, updates or replaces it, and destroys it when removed from code. A data source (data "aws_vpc" "main") is read-only: Terraform queries the provider API, for example "find the VPC tagged Name=shared-prod", and exposes the result as attributes. Removing the data block never deletes anything. Data sources are recorded in state only as cached read results.

Typical examples:

  • aws_ami with most_recent = true and filters to find the latest Amazon Linux image.
  • aws_vpc / aws_subnets by tags, to deploy into a shared network.
  • aws_caller_identity for the current account ID, aws_region for the region.
  • aws_route53_zone, aws_secretsmanager_secret_version, azurerm_key_vault_secret.
  • terraform_remote_state to read outputs from another state.

Timing: data sources are normally read during plan, so their results feed into the diff. If a data source depends on a resource that is not yet created, it is deferred to apply and shows as "known after apply". The important consequence: if the external object changes, the next plan may show changes in resources that depend on it, for example a new "latest AMI" ID causing an EC2 instance replacement. To avoid surprises, pin specific values for critical resources, or use lifecycle { ignore_changes = [ami] } and roll out new images deliberately.

How it works

  1. Declare a data block with filter arguments.
  2. On plan, Terraform asks the provider to look it up (fails if not found, or if multiple match when one is expected).
  3. Attributes become available as data.type.name.attr.
  4. Resources referencing them depend on the data source.
  5. Each plan re-reads; changes in external objects propagate into diffs.

Example

data "aws_caller_identity" "current" {}

data "aws_vpc" "shared" {
  tags = { Name = "shared-prod" }
}

data "aws_subnets" "private" {
  filter {
    name   = "vpc-id"
    values = [data.aws_vpc.shared.id]
  }
  tags = { Tier = "private" }
}

data "aws_ami" "al2023" {
  most_recent = true
  owners      = ["amazon"]
  filter {
    name   = "name"
    values = ["al2023-ami-*-x86_64"]
  }
}

resource "aws_instance" "app" {
  ami           = data.aws_ami.al2023.id
  instance_type = "t3.small"
  subnet_id     = data.aws_subnets.private.ids[0]
  tags          = { account = data.aws_caller_identity.current.account_id }
  lifecycle { ignore_changes = [ami] }
}

Common mistakes

  • Using a "latest" data source for production instances without ignore_changes, causing surprise replacements.
  • Filters that match several objects, making the plan fail.
  • Using a resource block to "reference" shared infrastructure, accidentally taking ownership (and destroying it later).
  • Reading secrets via data sources without realising the values land in state.

How to answer in the interview

"A resource is something Terraform creates, updates and destroys, and it's tracked in state. A data source only reads information about something that already exists, created elsewhere or by another configuration, without managing it. Typical examples are looking up the latest Amazon Linux AMI, an existing VPC by tag, the current account ID with aws_caller_identity, a secret, or a DNS zone. I declare it with a data block, like data \"aws_vpc\" \"main\", and reference attributes as data.aws_vpc.main.id. Data sources are read during plan, so if the external object changes, the next plan can show changes in dependent resources, which is why I'm careful with 'latest AMI' lookups on production instances."

Likely follow-up questions

  • Why can "latest AMI" cause unexpected replacements? A new AMI ID changes the instance's ami argument, which forces replacement.
  • When is a data source read at apply time? When it depends on values not yet known, such as a resource being created in the same run.
  • Do data sources store secrets in state? Yes, read values are saved in state, so protect it.
