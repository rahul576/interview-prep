What is an Ansible role, and what is its directory structure?

Configuration Management · concept · levels entry

In one line

A role packages tasks, handlers, templates, files and variables for one concern into a standard directory structure with main.yml entry points, reused from playbooks via roles: or include_role, shared through Git, Galaxy or collections and tested with Molecule.

Detailed explanation

Playbooks that configure everything inline become long and impossible to reuse. A role is the unit of reuse: everything needed to configure nginx, a Java runtime, a monitoring agent or users lives together, with a predictable layout that Ansible loads automatically.

The standard directories:

  • tasks/main.yml: the entry point; can include other task files.
  • handlers/main.yml: handlers like reloading the service.
  • templates/: Jinja2 .j2 files used by the template module.
  • files/: static files for copy.
  • defaults/main.yml: overridable variables with the lowest precedence, the role's public interface.
  • vars/main.yml: internal constants with high precedence.
  • meta/main.yml: metadata, supported platforms and dependencies on other roles.
  • Optionally meta/argument_specs.yml to validate role inputs, tests/ and molecule/.

ansible-galaxy role init nginx creates the skeleton. Playbooks then become short: a list of roles per host group. Roles can be applied with the play-level roles: keyword, with import_role (static, processed at parse time, so tags and when apply to every task) or with include_role (dynamic, evaluated at runtime, so it can be used in loops and conditions).

For sharing, roles live in their own Git repository or inside a collection, published to Ansible Galaxy or a private Automation Hub, and consumed with pinned versions in requirements.yml. Molecule tests a role in containers or VMs: create, converge, verify, and check idempotence by running it twice.

How it works

  1. Ansible finds the role in roles/, a collection or roles_path.
  2. It loads defaults, vars, handlers and meta dependencies.
  3. Dependencies run first.
  4. tasks/main.yml executes; templates and files are resolved relative to the role.
  5. Notified handlers run at the end.

Example

roles/nginx/
  defaults/main.yml      # nginx_port: 80, nginx_worker_processes: auto
  handlers/main.yml      # Reload nginx
  meta/main.yml
  meta/argument_specs.yml
  tasks/main.yml
  templates/nginx.conf.j2
  files/dhparam.pem
  molecule/default/molecule.yml
- hosts: web
  become: true
  roles:
    - role: nginx
      vars:
        nginx_port: 8080
    - role: node_exporter

Common mistakes

  • Putting configurable values in vars/ instead of defaults/.
  • Roles that do too much, such as "webserver_and_database_and_users".
  • Hard-coding environment-specific values inside the role.
  • No pinned versions, so a change in a shared role breaks every consumer.

How to answer in the interview

"A role packages everything to configure one thing, like nginx or a monitoring agent, into a reusable unit with a standard layout: tasks/main.yml, handlers, templates for Jinja2 files, files for static files, defaults for overridable variables, vars for internal ones, and meta for dependencies. Playbooks then just list roles per host group, or call include_role or import_role inside tasks. I share roles through Git or collections on Galaxy or a private Automation Hub, with pinned versions, and test them with Molecule, including an idempotence check."

Likely follow-up questions

  • How would you structure a role so other teams can reuse it safely? Clear defaults, argument_specs validation, no hard-coded environments, semantic versions, Molecule tests and a README.
  • import_role vs include_role? Static at parse time versus dynamic at runtime.
  • Role vs collection? A collection can bundle many roles plus modules and plugins under a namespace.
