Pods fail with ImagePullBackOff only for images from your private registry. How do you troubleshoot and fix it?

Kubernetes · scenario · levels entry, mid, senior

In one line

Read the exact pull error with kubectl describe pod, then check by category: unauthorized (missing or expired imagePullSecrets, wrong namespace, or node identity lacking registry permissions), not found (name, tag, architecture) or timeout (network, DNS, private endpoint).

Detailed explanation

ImagePullBackOff is a symptom: the kubelet tried to pull, failed (ErrImagePull) and is now backing off. The fact that only private-registry images fail narrows it to authentication, authorisation or network reachability of that registry. The pod events show the container runtime's message, which tells you which one.

For 401/403 unauthorized, the credentials used by the kubelet are wrong. Credentials come either from imagePullSecrets on the pod (or inherited from its ServiceAccount) or from the node's identity via a kubelet credential provider. Secrets are namespaced, so a secret created in default does not help a pod in payments. Tokens expire: an ECR authorisation token lasts 12 hours, so a static docker-registry secret created from it breaks the next day. On managed clusters the node identity normally pulls: EKS node roles need ECR read permissions, AKS needs the AcrPull role on the kubelet identity, GKE node service accounts need Artifact Registry reader.

For not found / manifest unknown, check registry hostname, repository path, tag or digest, and whether the image has a manifest for the node's architecture (an amd64-only image on arm64 nodes). For i/o timeout or TLS errors, check egress firewall rules, NAT, proxy settings, private DNS zones for private endpoints, and certificate trust for self-hosted registries.

How it works

  1. kubectl describe pod and read the Events message.
  2. Unauthorized: check imagePullSecrets on pod and ServiceAccount, and that the secret exists in that namespace.
  3. Decode the secret and verify registry host and credential validity.
  4. Managed clusters: verify node role or managed identity permissions on the registry.
  5. Not found: verify image reference and platform with docker manifest inspect or crane.
  6. Timeout: on the node, test with crictl pull and nslookup to isolate network issues.

Example

kubectl -n payments describe pod api-7c9f | grep -A3 Failed
#  Failed to pull image "myacr.azurecr.io/api:1.8.2": 401 Unauthorized

kubectl -n payments get sa default -o jsonpath='{.imagePullSecrets}'
kubectl -n payments create secret docker-registry regcred \
  --docker-server=registry.example.com --docker-username=ci-bot --docker-password="$TOKEN"
kubectl -n payments patch sa default -p '{"imagePullSecrets":[{"name":"regcred"}]}'

# AKS: let the cluster's kubelet identity pull from ACR
az aks update -n prod-aks -g rg-prod --attach-acr myacr

Common mistakes

  • Creating the pull secret in the wrong namespace.
  • Storing a 12-hour ECR token as a static secret.
  • Ignoring the actual error text and guessing.
  • Forgetting multi-arch images when adding arm64 nodes.

How to answer in the interview

"First I describe the pod, because the event tells me whether it's unauthorized, not found or a timeout. For unauthorized I check the imagePullSecrets on the pod or its service account, that the secret exists in the same namespace, and that the credential hasn't expired, which is common with ECR tokens. On managed clusters I check the node identity, such as AcrPull for AKS or ECR permissions on the node role. For not found I verify name, tag and architecture. For timeouts I test from the node with crictl pull and check DNS, firewall and private endpoints."

Likely follow-up questions

  • How do you survive a registry outage? Pull-through cache or mirror registry, IfNotPresent with immutable tags or digests, and pre-pulled critical images.
  • ServiceAccount vs pod imagePullSecrets? ServiceAccount secrets are added automatically to every pod using it.
  • What is a kubelet credential provider? A plugin that fetches short-lived registry credentials using the node's cloud identity.
