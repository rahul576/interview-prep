How have you migrated, or how would you migrate, a monolithic application to microservices?

Project Experience · design · levels senior, lead

In one line

Migrate incrementally, not big bang: find bounded contexts with DDD, prepare the platform (CI/CD, containers, observability, gateway), extract capabilities one by one with the Strangler Fig pattern, decompose the data carefully with CDC and an anti-corruption layer, and measure progress.

Detailed explanation

Start with why. Microservices solve organisational and scaling problems: teams blocking each other, slow releases, parts with very different load. If the real problem is messy code, a modular monolith may be the better step. Agree on goals and metrics: deployment frequency, lead time, incident rate.

Find boundaries. Use domain-driven design and event storming with domain experts to identify bounded contexts (catalogue, ordering, payment, shipping, notification). Back this with analysis of code dependencies, shared tables and change frequency. Services should follow business capabilities, not technical layers.

Prepare the platform before the first service: CI/CD pipelines, Docker and Kubernetes, centralised logging, metrics, distributed tracing, an API gateway, secrets management and resilience libraries. Without these, ten services are ten times harder to run than one monolith.

Strangle incrementally. Put the gateway in front of the monolith. Choose a first capability that is valuable but loosely coupled, such as notifications or catalogue, build it as a service, route its traffic to it (canary or shadow first), and remove the code from the monolith. Repeat in order of value and risk.

Data is the hard part. Each service should own its data. Steps: separate schemas inside the same database first; then move data; during transition sync via change data capture (Debezium) or events; replace cross-context joins with API calls, events or read models; replace distributed transactions with sagas. An anti-corruption layer translates legacy models so they do not leak into new services.

Organise teams around services (Conway's law) and keep improving the remaining monolith's modularity.

How it works

  1. Define goals, metrics and the case for migration.
  2. Map bounded contexts and coupling.
  3. Build platform foundations.
  4. Extract the first easy, valuable capability behind a gateway.
  5. Split its data with CDC and an anti-corruption layer.
  6. Repeat, measure, and retire monolith code.

Example

Phase 0: gateway -> monolith (100%)
Phase 1: /notifications/** -> notification-service (own DB, consumes OrderPlaced via CDC)
Phase 2: /catalog/**       -> catalog-service (catalog tables moved, monolith reads via API)
Phase 3: ordering + payment saga extracted; monolith order tables become read-only, then dropped
Metrics: deploys/week 1 -> 15, change failure rate 22% -> 8%

Common mistakes

  • Big-bang rewrite with a feature freeze.
  • Services sharing one database schema (distributed monolith).
  • Splitting by technical layer instead of business capability.
  • Starting with the most coupled core domain.
  • No observability before going distributed.

How to answer in the interview

"I wouldn't do a big-bang rewrite. First I'd clarify the goals and then identify bounded contexts with domain-driven design and event storming, backed by code and data coupling analysis. In parallel I'd make the platform ready: CI/CD, containers on Kubernetes, logging, metrics and tracing, and an API gateway. Then I'd apply the Strangler Fig pattern, starting with a valuable but loosely coupled capability like notifications, routing its traffic to the new service and removing it from the monolith. Data is the hardest part: each service gets its own schema, I'd sync with CDC during the transition, use an anti-corruption layer, and replace shared tables and transactions with events and sagas. I'd repeat that while tracking deployment frequency and incidents."

Likely follow-up questions

  • How would you split a shared database during migration? Separate schemas, then move tables, sync with CDC, and replace joins with APIs or read models.
  • When would you not migrate? Small team or product where a modular monolith meets the needs.
  • How do you avoid a distributed monolith? Own data per service, asynchronous events, and backward-compatible contracts.
