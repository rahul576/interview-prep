What are static pods, and where are they used?

Kubernetes · concept · levels mid, senior

In one line

Static pods are run directly by the kubelet from manifest files in a node directory (usually /etc/kubernetes/manifests), not created through the API server or scheduler; the kubelet publishes read-only mirror pods so you can see them, and kubeadm uses them to run the control plane itself.

Detailed explanation

Normal pods follow API server → scheduler → kubelet. That creates a chicken-and-egg problem for the control plane: the API server, scheduler, controller manager and etcd must run before there is an API server to accept or schedule anything. Static pods solve it.

The kubelet is configured with staticPodPath (in its config file). It watches that directory and, for each pod manifest, starts the pod through the container runtime, restarts it if it dies, and recreates it if the file changes. Static pods are bound to that node: no scheduling, no Deployments, no ReplicaSets.

So that operators can see them, the kubelet creates a mirror pod in the API server, named <pod>-<nodename>, for example kube-apiserver-cp-1 in kube-system. The mirror pod is just a reflection: deleting it with kubectl makes it reappear, and editing it has no effect. To change a static pod you edit the file on the node; the kubelet notices and restarts the pod with the new spec. To remove it, move the file out of the directory.

Main use: kubeadm clusters run kube-apiserver, kube-controller-manager, kube-scheduler and (for stacked topology) etcd as static pods on each control plane node. Managed services such as EKS, AKS and GKE hide the control plane entirely, so you rarely see them there. Occasionally static pods are used for node-local agents that must start before the cluster is reachable, though DaemonSets are usually the better choice. Static pods cannot reference other API objects like ConfigMaps or ServiceAccounts in the normal way.

How it works

  1. kubelet starts with staticPodPath: /etc/kubernetes/manifests.
  2. It reads each YAML file and starts the pod locally.
  3. It creates a mirror pod in the API once the API server is reachable.
  4. File changes → kubelet recreates the pod.
  5. File removed → kubelet stops the pod and deletes the mirror.

Example

ls /etc/kubernetes/manifests
# etcd.yaml  kube-apiserver.yaml  kube-controller-manager.yaml  kube-scheduler.yaml
sudo cp /etc/kubernetes/manifests/kube-apiserver.yaml /root/kube-apiserver.yaml.bak
sudo vi /etc/kubernetes/manifests/kube-apiserver.yaml   # e.g. add --audit-log-path=...
crictl ps | grep kube-apiserver                         # watch it restart
kubectl get pod -n kube-system kube-apiserver-cp-1 -o jsonpath='{.metadata.ownerReferences[0].kind}'

Common mistakes

  • Trying to edit or delete a mirror pod with kubectl.
  • Leaving backup copies in the manifests directory, which the kubelet then runs too.
  • Editing all control plane nodes at once instead of one at a time.
  • A syntax error in the file with no backup, taking the API server down.

How to answer in the interview

"Static pods are managed directly by the kubelet from manifest files in a directory on the node, usually /etc/kubernetes/manifests, instead of being created through the API server and scheduled. The kubelet starts them, restarts them if they die, and creates a mirror pod so you can see them with kubectl, but editing or deleting the mirror does nothing; you edit the file. Their main use is bootstrapping the control plane in kubeadm: the API server, controller manager, scheduler and etcd run as static pods because they have to start before any API exists."

Likely follow-up questions

  • How do you change an API server flag on kubeadm? Back up and edit the manifest on each control plane node, one at a time; persist it in the kubeadm ClusterConfiguration for upgrades.
  • Why not DaemonSets for the control plane? DaemonSets need a working API server and controllers.
  • How do you identify a static pod? Owner reference of kind Node and the kubernetes.io/config.mirror annotation.
