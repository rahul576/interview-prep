How does Prometheus work? Explain its data model and pull-based scraping.

Observability & SRE · concept · levels entry, mid

In one line

Prometheus pulls metrics by scraping HTTP /metrics endpoints of targets found via service discovery, stores them as time series identified by metric name and labels, supports counter, gauge, histogram and summary types, is queried with PromQL, and sends rule-based alerts to Alertmanager.

Detailed explanation

Pull model: Prometheus discovers targets through service discovery (Kubernetes pods, services and endpoints, EC2, Consul, file-based or static configs) and scrapes each target's /metrics endpoint every scrape interval (commonly 15-30 seconds). Benefits: Prometheus controls the load, an unreachable target is immediately visible (up == 0), and you can curl an endpoint to see exactly what it exposes. For short-lived batch jobs that can't be scraped, the Pushgateway exists, used sparingly. In Kubernetes the Prometheus Operator configures scraping with ServiceMonitor and PodMonitor resources.

Data model: every series is a metric name plus a set of key-value labels, with timestamped float samples: http_requests_total{method="GET",status="200",service="api"}. Each unique label combination is a separate series, which is why cardinality matters: labels with unbounded values (user IDs, request IDs, full URLs) create millions of series and exhaust memory. Data is stored in the local TSDB in two-hour blocks, compacted over time, with configurable retention.

Metric types:

  • Counter: only increases (resets on restart), such as requests or errors; use rate() or increase().
  • Gauge: goes up and down, such as memory, queue length, temperature.
  • Histogram: observations counted into configurable buckets (_bucket, _sum, _count); percentiles computed server-side with histogram_quantile() and aggregatable across instances. Native histograms offer higher resolution with less configuration.
  • Summary: client-side quantiles, not aggregatable across instances.

PromQL: rate(http_requests_total[5m]) for per-second rates, sum by (service) for aggregation, error ratios, and histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket[5m]))) for p99 latency.

Ecosystem: exporters translate systems into metrics (node exporter for Linux hosts, kube-state-metrics, blackbox exporter for probes, database exporters); applications use client libraries or OpenTelemetry. Recording rules precompute expensive queries; alerting rules evaluate PromQL and send firing alerts to Alertmanager, which deduplicates, groups, silences, inhibits and routes them to Slack, PagerDuty or email. Grafana provides dashboards.

How it works

  1. Service discovery finds targets.
  2. Prometheus scrapes /metrics on each interval and adds target labels.
  3. Samples are written to the TSDB.
  4. Rules are evaluated periodically.
  5. Firing alerts go to Alertmanager for routing.
  6. Grafana and users query via PromQL.

Example

# HELP http_requests_total Total HTTP requests.
# TYPE http_requests_total counter
http_requests_total{method="GET",status="200"} 10231
http_requests_total{method="POST",status="500"} 17
sum by (status) (rate(http_requests_total{job="api"}[5m]))
histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket{job="api"}[5m])))

Common mistakes

  • Putting user IDs or URLs with IDs into labels.
  • Using rate() on gauges, or reading raw counter values as rates.
  • Averaging summaries' quantiles across instances.
  • Very short scrape intervals everywhere, inflating storage.

How to answer in the interview

"Prometheus pulls metrics: it discovers targets, for example through Kubernetes service discovery, and scrapes their metrics endpoint at an interval. Data is stored as time series identified by a metric name and labels, like http_requests_total with method and status. Metric types are counter, which only goes up, gauge, which goes up and down, and histogram and summary for distributions like latency, histograms being aggregatable. I query with PromQL, for example rate over a counter. Exporters like node exporter expose system metrics, and alert rules send alerts to Alertmanager, which deduplicates, groups and routes them."

Likely follow-up questions

  • Why is a user ID label a bad idea? Each value creates a new series, exploding cardinality, memory and query cost.
  • Pull versus push? Pull gives control and easy health detection; push suits short-lived jobs and some network setups.
  • Histogram or summary? Histograms, since they aggregate across instances.
