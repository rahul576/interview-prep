How does ReentrantLock differ from synchronized?

Concurrency · concept · levels mid, senior

In one line

Both synchronized and ReentrantLock give reentrant mutual exclusion with the same visibility guarantees, but ReentrantLock adds tryLock (with timeout), lockInterruptibly, optional fairness and multiple Condition objects, at the cost of unlocking manually in finally; for read-heavy data use ReentrantReadWriteLock or StampedLock.

Detailed explanation

synchronized is built into the language. The JVM acquires the object's monitor on entry and releases it automatically on exit, even when an exception is thrown. It is reentrant (a thread can re-enter a monitor it already holds), and it is well optimised: uncontended locking is cheap. Its limits: a waiting thread cannot time out or be interrupted, there is only one wait set per monitor (wait/notify), and there's no fairness control.

ReentrantLock (in java.util.concurrent.locks) offers the same semantics plus control:

  • tryLock() returns immediately if the lock is busy, and tryLock(timeout) waits for a bounded time, useful to avoid deadlocks and to fail fast.
  • lockInterruptibly() lets a waiting thread respond to interruption, so cancellation works.
  • Fairness: new ReentrantLock(true) grants the lock roughly in arrival order, reducing starvation at the cost of throughput.
  • Multiple Conditions: lock.newCondition() creates separate wait sets, such as notFull and notEmpty in a bounded buffer, so you signal only the threads that care.
  • Introspection: isLocked, getQueueLength, isHeldByCurrentThread.

The price is discipline: you must call unlock() in a finally block, or an exception leaves the lock held forever. Historically ReentrantLock also mattered for virtual threads on Java 21-23, because blocking inside synchronized pinned the carrier; Java 24 fixed that.

For data that is read far more often than written, ReentrantReadWriteLock allows many concurrent readers or one writer. StampedLock (Java 8) adds optimistic reads: read without locking, then validate(stamp) and fall back to a read lock if a write happened. It's faster for read-mostly data but is not reentrant and has no Conditions.

How it works

  1. lock() tries a CAS on an AQS state; on failure the thread enqueues and parks.
  2. Reentry increments a hold count.
  3. unlock() decrements; at zero it releases and unparks the next waiter.
  4. await() on a Condition releases the lock and waits; signal() moves a waiter back to the lock queue.

Example

private final ReentrantLock lock = new ReentrantLock();
private final Condition notEmpty = lock.newCondition();

boolean tryTransfer(Duration wait) throws InterruptedException {
    if (!lock.tryLock(wait.toMillis(), TimeUnit.MILLISECONDS)) return false;
    try {
        while (queue.isEmpty()) notEmpty.await();
        process(queue.poll());
        return true;
    } finally {
        lock.unlock();                     // always in finally
    }
}

// Optimistic read with StampedLock
long stamp = sl.tryOptimisticRead();
double cx = x, cy = y;
if (!sl.validate(stamp)) { stamp = sl.readLock(); try { cx = x; cy = y; } finally { sl.unlockRead(stamp); } }

Common mistakes

  • Forgetting unlock() in finally.
  • Calling lock() inside the try block (unlock without lock on failure).
  • Using fair locks by default and losing throughput.
  • Re-entering a StampedLock, which deadlocks.

How to answer in the interview

"Both give reentrant mutual exclusion and the same memory visibility guarantees. synchronized is simpler and the lock is released automatically. ReentrantLock adds tryLock with a timeout, lockInterruptibly so a waiting thread can be interrupted, an optional fair mode, and multiple Condition objects instead of one wait-notify set. The cost is that I must unlock in a finally block. I default to synchronized for simple critical sections, and choose ReentrantLock when I need timeouts, interruptibility or conditions. For read-heavy data, ReentrantReadWriteLock or StampedLock allow concurrent readers."

Likely follow-up questions

  • When does a StampedLock optimistic read help? Very read-heavy data with short reads, like coordinates or config, where writes are rare.
  • Is synchronized slower? Not meaningfully when uncontended; modern JVMs optimise it well.
  • What is AQS? AbstractQueuedSynchronizer, the framework behind ReentrantLock, Semaphore and CountDownLatch.
