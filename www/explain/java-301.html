What is the difference between @Bean and @Component?

Spring Framework · concept · levels entry, mid

In one line

Both register beans in the container: @Component goes on your own class and is found by component scanning, while @Bean goes on a factory method in a @Configuration class, ideal for third-party classes or custom construction logic.

Detailed explanation

@Component (and its stereotypes @Service, @Repository, @Controller) is declarative at class level. Spring scans the packages, finds the annotated class, and creates it, normally through its constructor with injected dependencies. You need to own the source code to annotate it, and there is one bean definition per class, unless you add more manually.

@Bean is programmatic: a method in a @Configuration class returns an object, and Spring registers the return value as a bean named after the method. This is the right tool when:

  • the class comes from a library you cannot annotate (an ObjectMapper, an S3 client, a Resilience4j registry);
  • construction needs logic: builder calls, values from properties, choosing an implementation;
  • you need several beans of the same type with different configuration (two DataSources);
  • you want to keep framework annotations out of domain classes (clean or hexagonal architecture).

@Bean methods support initMethod/destroyMethod (and infer close() or shutdown() automatically), @Scope, @Primary, @Conditional... and @Profile.

A subtle point: classes with @Configuration are, by default, CGLIB-proxied (proxyBeanMethods = true). If one @Bean method calls another, the proxy intercepts and returns the existing singleton instead of creating a new object. With @Configuration(proxyBeanMethods = false) ("lite mode", used by Boot's own auto-configurations for faster startup and native images), such a call is a plain Java call that creates a new instance, so you should instead inject dependencies as method parameters. @Bean methods in a plain @Component class also run in lite mode.

How it works

  1. Component scanning registers definitions for annotated classes.
  2. Configuration classes are parsed; each @Bean method becomes a definition with a factory method.
  3. The container calls constructors or factory methods, resolving parameters by type.
  4. Both kinds of bean go through the same lifecycle and post-processing.

Example

@Component
class PriceCalculator {               // our own class, found by scanning
    BigDecimal gross(BigDecimal net) { return net.multiply(new BigDecimal("1.19")); }
}

@Configuration(proxyBeanMethods = false)
class ClientsConfig {
    @Bean
    ObjectMapper objectMapper() {     // third-party class
        return JsonMapper.builder().addModule(new JavaTimeModule())
            .disable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS).build();
    }

    @Bean
    S3Client s3Client(@Value("${aws.region}") String region) {
        return S3Client.builder().region(Region.of(region)).build();
    }

    @Bean
    ReportExporter exporter(S3Client s3, ObjectMapper mapper) {   // dependencies as parameters
        return new ReportExporter(s3, mapper);
    }
}

Common mistakes

  • Putting @Component on a class and also defining it with @Bean, creating two beans.
  • Calling @Bean methods directly in lite mode and getting duplicate instances.
  • Putting @Bean methods in classes outside the scanned packages.
  • Using @Bean for everything, losing the simplicity of scanning.

How to answer in the interview

"Both end up as beans in the Spring container. @Component goes on my own class, and component scanning discovers it. @Bean goes on a factory method inside a @Configuration class, and whatever the method returns becomes the bean. I use @Bean for third-party classes I can't annotate, such as an ObjectMapper or a cloud SDK client, when construction needs custom logic or properties, or when I need several beans of the same type. One detail: full @Configuration classes are proxied, so calling one @Bean method from another returns the same singleton; with proxyBeanMethods false you pass dependencies as method parameters instead."

Likely follow-up questions

  • What does proxyBeanMethods = false change? No CGLIB proxy; inter-bean method calls create new objects, but startup is faster.
  • How is a @Bean named? After the method, or via @Bean("name").
  • Can a @Bean be conditional? Yes, with @ConditionalOn... or @Profile.
