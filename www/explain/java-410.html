What are Redis eviction policies and persistence options?

Caching · concept · levels mid, senior

In one line

When Redis hits maxmemory, an eviction policy (such as allkeys-lru, allkeys-lfu, volatile-ttl or noeviction) decides what happens; RDB snapshots and the AOF append-only log provide persistence, and replication with Sentinel or Redis Cluster provides high availability.

Detailed explanation

Eviction policies (set with maxmemory-policy):

  • noeviction: refuse writes with an OOM error when memory is full. Right when data must not silently disappear, like a queue or primary store. It is the default.
  • allkeys-lru / allkeys-lfu: evict any key by approximate least-recently or least-frequently used. Best for a pure cache; LFU suits skewed popularity.
  • volatile-lru / volatile-lfu / volatile-random: evict only keys with a TTL, protecting persistent keys in a mixed instance.
  • volatile-ttl: evict keys closest to expiry first.

Persistence:

  • RDB: point-in-time snapshots via a forked child (BGSAVE, save rules). Compact, fast restarts and good for backups, but you lose writes since the last snapshot; forking a large dataset needs extra memory through copy-on-write.
  • AOF: logs every write command; appendfsync everysec (the usual choice) loses at most about one second, always is safest and slowest. AOF is periodically rewritten to compact it, and since Redis 7 uses a multi-part base plus incremental files.
  • Both can be enabled together; using an RDB preamble in the AOF speeds up loading.

High availability: asynchronous primary-replica replication; Sentinel monitors and promotes a replica on failure; Redis Cluster shards keys over 16,384 hash slots with replicas per shard and automatic failover. Because replication is asynchronous, a failover can lose recently acknowledged writes (WAIT can reduce that window).

How it works

  1. Set maxmemory below the machine's RAM, leaving headroom for forks and buffers.
  2. Choose the policy based on whether the data is a cache or must be kept.
  3. On a write beyond the limit, Redis samples keys and evicts according to the policy.
  4. Persistence writes snapshots and/or the AOF in the background.
  5. Replicas copy the stream; Sentinel or Cluster handles failover.

Example

# Pure cache
maxmemory 6gb
maxmemory-policy allkeys-lfu
save ""               # no snapshots needed
appendonly no

# Session / cart store
maxmemory 6gb
maxmemory-policy volatile-lru   # or noeviction + alerting
appendonly yes
appendfsync everysec
save 900 1

Common mistakes

  • Leaving noeviction on a cache and getting OOM errors on writes.
  • Using volatile-* policies when keys have no TTL, so nothing can be evicted.
  • Setting maxmemory to all RAM, then crashing during a fork for RDB or AOF rewrite.
  • Believing replication alone is a backup.

How to answer in the interview

"When Redis reaches maxmemory, the eviction policy decides what to drop. For a pure cache I'd use allkeys-lru or allkeys-lfu; volatile policies evict only keys with a TTL, and noeviction, the default, returns errors, which suits data that must not vanish. For persistence, RDB takes periodic snapshots, which are compact but lose recent writes, while AOF logs every write and with fsync every second loses at most about a second; many setups use both. For high availability I'd use replicas with Sentinel failover, or Redis Cluster when I also need sharding, keeping in mind replication is asynchronous. For a session store I'd enable AOF and use volatile-lru or noeviction with alerting."

Likely follow-up questions

  • Which policy for a session store? volatile-lru with TTLs on sessions, or noeviction plus memory alerts, with AOF on.
  • Why does RDB need extra memory? The fork uses copy-on-write, so pages changed during the snapshot are duplicated.
  • How is a Redis Cluster key placed? CRC16 of the key modulo 16,384 slots; hash tags {...} keep related keys together.
