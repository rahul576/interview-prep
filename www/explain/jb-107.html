What is the difference between FixedThreadPool, CachedThreadPool, and SingleThreadExecutor?

Concurrency · concept · levels mid, senior

In one line

newFixedThreadPool(n) has n threads and an unbounded queue; newCachedThreadPool() creates threads on demand and reuses idle ones, with no thread limit; newSingleThreadExecutor() runs tasks one at a time in order. In production prefer a bounded ThreadPoolExecutor.

Detailed explanation

All three are convenience factories in Executors that configure a ThreadPoolExecutor differently.

Fixed thread pool: core size = max size = n, with an unbounded LinkedBlockingQueue. Exactly n threads run; everything else waits in the queue. It is predictable and suits CPU-bound work sized to the cores. The danger is the unbounded queue: under overload, tasks pile up, latency grows without limit, and eventually you hit OutOfMemoryError, while nothing pushes back on producers.

Cached thread pool: core size 0, max Integer.MAX_VALUE, a SynchronousQueue (no storage, direct hand-off) and a 60-second keep-alive. A task is handed to an idle thread if one exists, otherwise a new thread is created. Good for many short-lived, bursty tasks. The danger is thread explosion: if tasks are slow (say, a downstream API hangs), every new submission creates another thread, potentially thousands, exhausting memory and native thread limits.

Single thread executor: one worker and an unbounded queue, wrapped so it cannot be reconfigured. Tasks execute sequentially in submission order, which gives you ordering and confinement without locks, for example writing events to a file. If the worker dies from an exception, a new one replaces it. Same unbounded-queue risk.

In production, build a ThreadPoolExecutor explicitly: core and max sizes, a bounded ArrayBlockingQueue, a ThreadFactory with named threads, and an explicit rejection policy. Expose metrics. For blocking I/O on Java 21+, also consider virtual threads with a semaphore.

How it works

  1. A task is submitted to ThreadPoolExecutor.
  2. If fewer than core threads run, a new thread starts for it.
  3. Otherwise the task is offered to the queue.
  4. If the queue is full (or is a SynchronousQueue with no taker) and threads are below max, a new thread starts.
  5. If at max and queue full, the rejection policy runs.

Example

ExecutorService fixed  = Executors.newFixedThreadPool(8);   // 8 threads, unbounded queue
ExecutorService cached = Executors.newCachedThreadPool();   // unbounded threads
ExecutorService single = Executors.newSingleThreadExecutor(); // 1 thread, FIFO

// Production-style bounded pool
ThreadPoolExecutor pool = new ThreadPoolExecutor(
        8, 16,                                   // core, max
        30, TimeUnit.SECONDS,                    // idle keep-alive above core
        new ArrayBlockingQueue<>(500),           // bounded queue = backpressure
        Thread.ofPlatform().name("report-", 0).factory(),
        new ThreadPoolExecutor.CallerRunsPolicy());

Common mistakes

  • Using a cached pool for slow I/O calls and creating thousands of threads.
  • Using a fixed pool under unbounded load with no backpressure.
  • Expecting max pool size to matter with an unbounded queue (it never grows beyond core).
  • Leaving threads unnamed, making thread dumps useless.

How to answer in the interview

"newFixedThreadPool keeps exactly n threads and puts extra tasks in an unbounded queue, good for CPU-bound work, but under overload the queue can grow until OutOfMemoryError. newCachedThreadPool creates a thread on demand when no idle one is free and removes threads idle for 60 seconds; it suits short tasks, but threads are effectively unbounded, so a burst or slow downstream can create thousands. newSingleThreadExecutor has one thread, so tasks run sequentially in submission order. In production I build a ThreadPoolExecutor with a bounded queue, named threads and an explicit rejection policy, and monitor it."

Likely follow-up questions

  • Which rejection policies does ThreadPoolExecutor offer? AbortPolicy (throw, the default), CallerRunsPolicy (caller runs the task, natural backpressure), DiscardPolicy and DiscardOldestPolicy.
  • Why does max pool size not matter with an unbounded queue? New threads beyond core are created only when the queue rejects an offer, which never happens.
  • How do you size a pool? About core count for CPU-bound work; for I/O, cores multiplied by (1 + wait/compute time), capped by downstream limits.
