How does IAM evaluate permissions when several policies apply?

Cloud (AWS) · concept · levels mid

In one line

IAM starts with an implicit deny, an explicit Deny in any applicable policy always wins, and otherwise the request needs an Allow from an identity or resource policy that also falls within every limiting layer: SCPs, RCPs, permission boundaries and session policies.

Detailed explanation

For each request, AWS gathers every policy that applies: identity-based policies on the user, group or role; resource-based policies such as a bucket or key policy; permission boundaries on the identity; session policies passed when assuming a role; service control policies (SCPs) and resource control policies (RCPs) from AWS Organizations; and VPC endpoint policies where traffic passes through an endpoint.

The logic is: if any policy has a matching explicit Deny, the answer is deny. If not, the guardrails must permit it: the SCPs at every level from root to account, the RCPs on the resource, the permission boundary and session policy all have to allow the action. These layers only set maximum permissions; they never grant. Finally, there must be an actual Allow in an identity policy or a resource policy. If nothing allows it, the implicit deny stands.

There are nuances. Within the same account, an allow in either the identity policy or the resource policy is enough (with special cases such as KMS key policies, and role sessions where boundaries apply). For cross-account access, both the caller's identity policy and the resource policy must allow it. SCPs do not apply to the management account or service-linked roles. Conditions such as aws:SourceIp, aws:PrincipalOrgID or aws:SecureTransport are part of matching.

To debug, use the IAM policy simulator, read the CloudTrail event (AccessDenied messages now often state which policy type denied and whether it was explicit or implicit), and use IAM Access Analyzer for policy validation and unused access.

How it works

  1. Request arrives: principal, action, resource, context keys.
  2. Collect all applicable policies.
  3. Any explicit Deny matches: deny.
  4. Check SCPs, RCPs, permission boundary, session policy: any missing allow means deny.
  5. Check identity and resource policies for an Allow (both needed cross-account).
  6. Allow found: permit; otherwise implicit deny.

Example

A role has s3:* on its identity policy, but the bucket policy denies non-TLS traffic and an SCP limits regions:

{
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:*",
  "Resource": ["arn:aws:s3:::reports", "arn:aws:s3:::reports/*"],
  "Condition": {"Bool": {"aws:SecureTransport": "false"}}
}

An HTTP request is denied by the explicit Deny despite the Allow; an HTTPS request is allowed unless the SCP blocks the region.

Common mistakes

  • Believing an Allow can override a Deny.
  • Expecting an SCP or permission boundary to grant access.
  • Forgetting the resource policy is required for cross-account access.
  • Debugging the wrong principal instead of checking get-caller-identity.

How to answer in the interview

"Every request starts as an implicit deny. AWS collects all applicable policies: identity policies, resource policies like bucket policies, permission boundaries, session policies, SCPs and RCPs. If any has a matching explicit Deny, the request is denied. Otherwise it needs an Allow from an identity or resource policy, and that Allow must also sit inside every limiting layer, because SCPs, boundaries and session policies only cap permissions. Cross-account, both sides must allow. To debug I use the policy simulator, CloudTrail error details and Access Analyzer."

Likely follow-up questions

  • Can an SCP grant permissions to a user? No, it only defines the maximum; an identity or resource policy must still allow.
  • Do SCPs affect the management account? No, which is why workloads should not run there.
  • What is an RCP? An Organizations policy that caps what can be done to resources in member accounts, regardless of the caller.
