How do you write idempotent Ansible tasks when you must use command or shell?

Configuration Management · concept · levels mid

In one line

Prefer a dedicated module; when command/shell is unavoidable, use creates/removes to skip completed work, changed_when/failed_when to report accurately, or a read-only check with register followed by a when-guarded change.

Detailed explanation

Modules are idempotent because they inspect state before acting. command and shell cannot: Ansible has no idea what an arbitrary command does, so by default it runs every time and reports changed every time. That causes repeated side effects (running an installer twice, re-initialising a database) and false "changed" reports that trigger handlers and hide real changes. So the first question is always: is there a module? Examples: ansible.builtin.lineinfile instead of echo >>, ansible.builtin.unarchive instead of tar xf, community.postgresql.postgresql_db instead of psql -c "CREATE DATABASE", ansible.builtin.get_url instead of curl.

When a command is truly necessary, make it idempotent:

  • creates: skip the task if a path exists. Works well when the command produces a file or a marker, such as an installer creating /opt/tool/bin/tool.
  • removes: run only if a path exists, for cleanup commands.
  • changed_when: define when the command really changed something, for example changed_when: "'created' in result.stdout" or based on rc. For read-only commands use changed_when: false.
  • failed_when: define failure beyond the exit code, for example tolerate rc == 1 when it means "already exists", or fail when stderr contains a pattern.
  • Check then act: a read-only task with register and changed_when: false inspects state, and the change task runs with when only if needed.

These also make check mode work better: commands with creates/removes can predict whether they would run, and read-only checks can be forced with check_mode: false.

How it works

  1. Search for a module that does the job.
  2. If none, decide how to detect "already done".
  3. Use creates/removes or a registered check.
  4. Report accurately with changed_when/failed_when.
  5. Run the playbook twice; the second run must show changed=0.

Example

- name: Install tool (skip if already installed)
  ansible.builtin.command: /tmp/install-tool.sh --prefix /opt/tool
  args:
    creates: /opt/tool/bin/tool

- name: Check whether the database exists
  ansible.builtin.command: psql -tAc "SELECT 1 FROM pg_database WHERE datname='orders'"
  register: db_exists
  changed_when: false
  check_mode: false
  become: true
  become_user: postgres

- name: Create database
  ansible.builtin.command: createdb orders
  when: db_exists.stdout != "1"
  become: true
  become_user: postgres

- name: Apply migrations
  ansible.builtin.command: /opt/app/bin/migrate up
  register: migrate
  changed_when: "'applied' in migrate.stdout"
  failed_when: migrate.rc != 0 and 'no change' not in migrate.stderr

Common mistakes

  • Using shell for things modules handle.
  • Read-only commands reporting changed and triggering handlers.
  • ignore_errors: true instead of a precise failed_when.
  • Marker files that don't reflect the real state.

How to answer in the interview

"First choice is always a dedicated module, because it knows how to check state. When I must use shell or command, I make it idempotent: creates skips the task if a file already exists, like a binary the installer creates, and removes skips it if a file is absent. changed_when tells Ansible when the command really changed something, for example when the output contains 'created', or false for read-only commands, and failed_when defines failure beyond the exit code. Another pattern is a read-only check with register, then the change task with a when condition. That way repeated runs report ok and don't repeat side effects."

Likely follow-up questions

  • Why is changed_when: false important for read-only commands? Otherwise they always report changed, trigger handlers and make "changed" meaningless.
  • command or shell? command unless you need pipes, redirects or shell features.
  • How do you verify idempotency? Run twice, or Molecule's idempotence test.
