What is the difference between synchronous and asynchronous communication?

Microservices · concept · levels mid

In one line

Synchronous: the caller sends a request and waits (REST, gRPC), simple but temporally coupled; asynchronous: the caller publishes a message and continues (queues, events), resilient and decoupled but eventually consistent and in need of idempotency, retries and DLQs.

Detailed explanation

Synchronous communication is like a phone call. Service A calls B and blocks (logically) until B answers or a timeout expires. It is easy to write and debug, and the caller gets an immediate result to show the user. But it creates temporal coupling: if B is slow, A is slow; if B is down, A's request fails. In chains (A → B → C → D), latencies add up and availability multiplies down, and a slow service can exhaust callers' threads and trigger cascading failures. Hence timeouts, circuit breakers and bulkheads are mandatory.

Asynchronous communication is like sending a letter or a text. A publishes a message or event to a broker (Kafka, RabbitMQ, SQS) and continues immediately. Consumers process it when they are ready. Benefits: A keeps working while consumers are down, the broker absorbs load spikes, failed processing can be retried, and many consumers can react to the same event. Costs: eventual consistency (the effect happens later), idempotent consumers because messages can be delivered more than once, retries and dead-letter queues for failures, ordering concerns, and tracing across events to debug a flow.

A useful rule: use synchronous for queries a user is waiting on (show my orders, check availability, authenticate), and asynchronous for workflows, integration and notifications (fulfil the order, send the confirmation email, update the search index, feed analytics).

When an operation must be asynchronous but a user wants the result, use the asynchronous request-reply pattern: accept with 202 Accepted and a status URL, then let the client poll, or push the result via WebSocket, Server-Sent Events or a notification.

How it works

  1. Sync: request → callee processes → response within timeout → caller continues.
  2. Async: publish → broker persists → caller returns.
  3. Consumer receives → processes idempotently → acknowledges.
  4. Failure → retry with backoff → DLQ after N attempts.
  5. Result → event, status endpoint or push to client.

Example

// Async request-reply over HTTP
@PostMapping("/reports")
ResponseEntity<Void> requestReport(@RequestBody ReportRequest req) {
    UUID jobId = UUID.randomUUID();
    jobs.save(new ReportJob(jobId, "PENDING"));
    kafkaTemplate.send("report.requests", jobId.toString(), req.withJobId(jobId));
    return ResponseEntity.accepted().location(URI.create("/reports/" + jobId)).build();
}

@GetMapping("/reports/{id}")
ReportJob status(@PathVariable UUID id) { return jobs.findById(id).orElseThrow(); } // PENDING / DONE

Common mistakes

  • Assuming async means no error handling.
  • Synchronous fan-out to many services for one request.
  • Not giving users feedback for async operations.
  • Treating non-blocking HTTP clients as asynchronous messaging.

How to answer in the interview

"In synchronous communication the caller sends a request and waits for the answer, as with REST or gRPC. It is simple and gives an immediate result, but it creates temporal coupling: if the callee is slow or down, so is the caller, and long chains add latency and risk cascading failures. In asynchronous communication the caller publishes a message to a broker and continues; consumers process it when they can. That decouples services, absorbs spikes and keeps working when a consumer is down, but we accept eventual consistency and need idempotent consumers, retries, dead-letter queues and tracing. I use sync for queries a user waits on and async for workflows and notifications."

Likely follow-up questions

  • How do you return a result for an async operation? 202 with a status resource, or push via WebSocket, SSE or notification.
  • What is temporal coupling? Both services must be available at the same time for the interaction to succeed.
  • How do you debug an async flow? Propagate trace context in message headers and use distributed tracing.
