Design an IoT platform that ingests telemetry from 10 million devices.

Classic Design Problems · design · levels senior, lead

In one line

An IoT platform for 10 million devices uses MQTT to a scalable broker or managed IoT hub, X.509 device identity, a stream (Kafka) for buffering and fan-out, time-series plus cold storage, device shadows/twins for state and commands, and handles intermittent connectivity and OTA updates.

Detailed explanation

Start with numbers: 10 million devices sending one message per minute is roughly 167,000 messages per second, plus 10 million long-lived connections. That shapes everything: brokers must hold millions of TCP/TLS connections, and ingestion must absorb bursts (for example, all devices reconnecting after a power cut).

MQTT is the standard device protocol: lightweight, publish/subscribe over persistent TCP, with QoS levels (0 at-most-once, 1 at-least-once) and retained messages. Brokers like EMQX or HiveMQ cluster horizontally, or you use AWS IoT Core or Azure IoT Hub to avoid running them.

Security is per device: unique X.509 certificates provisioned at manufacturing (or via a provisioning service), mutual TLS, and topic-level policies so a device can only publish to devices/{its-id}/.... Compromised devices are revoked individually.

The broker forwards into a stream (Kafka, Kinesis, Event Hubs) that decouples ingestion from consumers: rules and alerting, stream aggregation (Flink), and storage. Hot data goes to a time-series database (TimescaleDB, InfluxDB, ClickHouse) for dashboards; raw data lands in object storage / a lakehouse for analytics and ML.

Device shadows (AWS) or device twins (Azure) store reported and desired state, so apps can set "desired: firmware 2.3" even while the device is offline; the device syncs on reconnect.

How it works

  1. Device boots, connects with mTLS to the nearest regional broker.
  2. Publishes telemetry with a device timestamp at QoS 1.
  3. Broker rule forwards messages to Kafka, partitioned by device ID.
  4. Stream processors compute aggregates and alerts; sinks write to time-series and lake storage.
  5. Commands and config go through the shadow; the device receives the delta.
  6. When offline, devices buffer readings locally and upload with original timestamps.
  7. OTA updates roll out in stages (1%, 10%, 100%) with health checks and rollback.

Example

// Topic: devices/thermo-00981/telemetry  (QoS 1)
{"ts": "2026-11-21T08:00:00Z", "temp_c": 21.4, "humidity": 48, "fw": "2.2.1"}

// Shadow document
{"state": {
   "desired":  {"fw": "2.3.0", "report_interval_s": 60},
   "reported": {"fw": "2.2.1", "report_interval_s": 60}},
 "version": 418}

Common mistakes

  • Sharing one credential across a device fleet.
  • Writing directly from the broker into a database with no buffer.
  • Ignoring reconnection storms; devices need jittered backoff.
  • Trusting server arrival time instead of device timestamps for late data.
  • Pushing firmware to all devices at once without rollback.

How to answer in the interview

"Ten million devices at one message a minute is about 170,000 messages per second over long-lived connections. Devices use MQTT with mutual TLS and per-device certificates to a clustered broker or AWS IoT Core. The broker feeds Kafka, which buffers and fans out to alerting, stream aggregation and storage: a time-series database for recent data and a data lake for history. Device shadows hold desired and reported state so commands work offline. Devices buffer locally, reconnect with jittered backoff, and firmware rolls out in stages with automatic rollback."

Likely follow-up questions

  • How do you roll out firmware safely? Signed images, A/B partitions, staged cohorts, health metrics gating each stage.
  • How do you handle a reconnect storm? Jittered exponential backoff on devices, broker connection rate limits, autoscaling.
  • MQTT QoS 2? Exactly-once handshake; costly, rarely needed if consumers are idempotent.
