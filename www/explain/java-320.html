Session-based authentication or JWT: how do you choose?

Security · concept · levels senior, lead

In one line

Sessions keep state on the server and are easy to revoke; JWTs are stateless and portable across services but hard to revoke. For browser apps I usually pick server sessions or a BFF with HttpOnly cookies, and JWT access tokens for APIs and service-to-service calls.

Detailed explanation

With session-based authentication, the server creates a session after login and the browser holds only a random session id in an HttpOnly, Secure, SameSite cookie. The state lives in memory or, when scaled out, in a shared store such as Redis via Spring Session. Logout or "disable this account" takes effect immediately by deleting the session. Costs: a lookup per request, shared storage to operate, and CSRF protection because browsers attach cookies automatically.

With JWTs, the token itself carries identity and authorities, signed by the issuer. Any service with the public key can validate it without a call, which suits microservices, mobile clients and third-party APIs. The downside is revocation: a stolen or outdated token works until exp. Mitigations are short expiry (5-15 minutes), refresh tokens with rotation and reuse detection, and, if needed, a deny-list, which partly brings state back. JWTs also get large with many claims.

Storage matters as much as format. A token in localStorage is readable by any injected script, so one XSS bug leaks it. An HttpOnly cookie is invisible to JavaScript but needs CSRF defences. That is why current guidance (the IETF "OAuth for browser-based apps" document) favours the Backend for Frontend (BFF) pattern: the browser has only a session cookie with the BFF, the BFF performs the OAuth flow and keeps access and refresh tokens server side, and it relays tokens to APIs. Spring Cloud Gateway with TokenRelay is a common BFF implementation.

How it works

  1. Decide who the clients are: browser only, mobile, other services, partners.
  2. Browser app: session cookie (or BFF holding tokens), CSRF protection, Redis-backed sessions for scale.
  3. APIs: validate short-lived JWT access tokens as a resource server.
  4. Refresh tokens are rotated and revocable at the authorization server.
  5. For "log out everywhere", revoke refresh tokens and optionally deny-list active token ids.

Example

# BFF with Spring Cloud Gateway: browser holds a session cookie, gateway relays tokens
spring:
  session:
    redis:
      namespace: bff
  cloud:
    gateway:
      server:
        webflux:
          default-filters:
            - TokenRelay=
            - SaveSession
          routes:
            - id: orders
              uri: http://orders-api
              predicates:
                - Path=/api/orders/**

Common mistakes

  • Choosing JWT just because it is "modern" for a single monolith web app.
  • Long-lived JWTs with no refresh or revocation story.
  • Keeping tokens in localStorage.
  • Disabling CSRF while still using cookies.

How to answer in the interview

"Sessions keep state on the server, usually in Redis with Spring Session, and the browser only holds an HttpOnly cookie, so revoking is instant, at the cost of shared storage and CSRF protection. JWTs are self-contained and any service can validate them, which fits APIs and microservices, but you cannot easily revoke them, so I keep them short-lived with rotating refresh tokens. Storage is the other half of the decision: tokens in localStorage are exposed to XSS. For browser apps I prefer the BFF pattern, where the browser has a session cookie and the backend holds the tokens and relays them to the APIs."

Likely follow-up questions

  • How would you log out a user everywhere immediately with JWTs? Revoke refresh tokens, deny-list jti or bump a per-user token version checked on each request, and keep access tokens short.
  • What does SameSite do? Restricts when cookies are sent cross-site, reducing CSRF risk.
  • Can sessions work across services? Yes with a shared store, but it couples services; tokens are cleaner between services.
