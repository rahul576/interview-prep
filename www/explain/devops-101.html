Explain the structure of a GitHub Actions workflow.

CI/CD Tools · concept · levels entry, mid

In one line

A GitHub Actions workflow is a YAML file in .github/workflows/ with triggers (on), jobs that run on runners (in parallel by default, ordered with needs), steps that use actions or run commands, plus matrix builds, secrets, environments and caching.

Detailed explanation

Location and triggers: each workflow is a YAML file under .github/workflows/. The on key defines events: push and pull_request (with branch and path filters), schedule (cron), workflow_dispatch (manual, with inputs), release, workflow_call (reusable workflows) and many others.

Jobs: a workflow contains one or more jobs. Each job runs on a fresh runner selected by runs-on: GitHub-hosted (Ubuntu, Windows, macOS, larger or Arm runners) or self-hosted. Jobs run in parallel by default; needs creates dependencies, so deploy waits for build and test. Jobs can pass outputs to later jobs and use if conditions.

Steps: a job's steps run sequentially on the same runner and share its file system. A step either uses an action (uses: actions/checkout@v4, actions/setup-node), which is reusable code from the marketplace or your repo, or runs a command (run: npm test). Inputs are passed with with, environment variables with env.

Matrix: strategy.matrix runs the same job across combinations, such as Node versions or operating systems, with fail-fast and max-parallel options.

Secrets and variables: repository, environment or organisation secrets accessed as ${{ secrets.NAME }} and masked in logs; plain configuration in vars. Prefer OIDC to cloud providers over stored keys.

Environments: named targets like staging and production with protection rules (required reviewers, wait timers, branch restrictions) and environment-specific secrets, giving approvals and deployment history.

Caching and artifacts: actions/cache or the built-in caching of setup actions speeds up dependency installs; actions/upload-artifact passes build outputs between jobs.

Concurrency: concurrency groups prevent two deployments to the same environment at once.

How it works

  1. An event matches a workflow's on filters.
  2. GitHub creates jobs and queues them on matching runners.
  3. Each runner executes the job's steps in order.
  4. Jobs with needs start after dependencies succeed.
  5. Environment jobs wait for approvals.
  6. Logs, artifacts and statuses are reported on the commit or PR.

Example

name: ci
on:
  push: { branches: [main] }
  pull_request:
permissions: { contents: read }
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix: { node: [20, 22] }
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: "${{ matrix.node }}", cache: npm }
      - run: npm ci
      - run: npm test
  deploy:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production
    concurrency: production
    steps:
      - run: ./deploy.sh
        env: { API_TOKEN: "${{ secrets.DEPLOY_TOKEN }}" }

Common mistakes

  • Assuming jobs share files; they run on separate runners (use artifacts).
  • Forgetting needs, so deploy runs in parallel with tests.
  • Broad default GITHUB_TOKEN permissions.
  • No caching, making every run reinstall dependencies.

How to answer in the interview

"A workflow is a YAML file in .github/workflows. It starts with triggers under on, like push, pull_request, schedule or workflow_dispatch. It contains jobs that run on GitHub-hosted or self-hosted runners, in parallel by default, with needs to declare dependencies. Each job has steps that either use reusable actions like actions/checkout or run shell commands. A matrix runs the same job across versions or platforms. Secrets, environments with protection rules and approvals handle deployments, and caching speeds up dependency installs."

Likely follow-up questions

  • Reusable workflows vs composite actions? Reusable workflows are whole workflows with jobs called via workflow_call; composite actions bundle steps inside one job.
  • How do jobs share data? Job outputs for small values, artifacts for files.
  • How to prevent parallel deploys? A concurrency group per environment.
