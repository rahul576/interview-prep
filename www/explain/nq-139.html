What are the three main categories of design patterns?

Design Patterns · concept · levels entry

In one line

The three categories are creational (how objects are created), structural (how classes and objects are composed) and behavioural (how objects interact and divide responsibilities).

Detailed explanation

The GoF classification groups patterns by the kind of problem they solve.

Creational patterns abstract the instantiation process, so code does not hard-wire new ConcreteClass(). They control which class is created, how many instances exist, and how complex construction happens. Members: Singleton, Factory Method, Abstract Factory, Builder, Prototype.

Structural patterns describe how to assemble classes and objects into larger structures while keeping them flexible. They mostly rely on wrapping and composition. Members: Adapter (convert interfaces), Decorator (add behaviour by wrapping), Proxy (control access), Facade (simple front for a subsystem), Composite (tree of part-whole objects treated uniformly), Bridge (separate abstraction from implementation), Flyweight (share fine-grained objects to save memory).

Behavioural patterns are about algorithms and the assignment of responsibilities: who does what and how objects communicate. Members: Strategy, Observer, Template Method, Chain of Responsibility, Command, State, Visitor, Iterator, Mediator, Memento, Interpreter.

The GoF book also had a second axis: class patterns (relationships fixed via inheritance at compile time, like Template Method or class Adapter) versus object patterns (relationships via composition at runtime, like Strategy or Decorator). Most patterns are object patterns.

A quick test for categorising: if the question is "how do I get an instance?", it is creational; "how do I fit these pieces together?", structural; "how do these objects collaborate or vary behaviour?", behavioural. Decorator is structural, even though it adds behaviour, because its essence is how objects are composed (wrapping with the same interface).

How it works

  1. Look at the problem's focus: creation, composition or collaboration.
  2. Pick the category, then the pattern by intent.
  3. Check the class-vs-object scope (inheritance vs composition).
  4. Apply and name it.

Example

// Creational: Builder
HttpRequest req = HttpRequest.newBuilder(URI.create("https://api.example.com")).GET().build();

// Structural: Facade (one call hides many subsystems)
class CheckoutFacade {
    void checkout(Cart c) { inventory.reserve(c); payment.charge(c); shipping.schedule(c); }
}

// Behavioural: Strategy
list.sort(Comparator.comparing(Product::price));

Common mistakes

  • Placing Decorator or Proxy under behavioural because they "add behaviour".
  • Listing patterns without explaining what the category means.
  • Mixing in non-GoF patterns (Repository, DAO) as if they were GoF.
  • Forgetting there are 5, 7 and 11 patterns respectively.

How to answer in the interview

"Creational patterns deal with how objects are created, hiding creation logic so code doesn't depend on concrete classes: Singleton, Factory Method, Abstract Factory, Builder and Prototype. Structural patterns deal with composing classes and objects into larger structures: Adapter, Decorator, Proxy, Facade, Composite, Bridge, Flyweight. Behavioural patterns deal with how objects communicate and share responsibility: Strategy, Observer, Template Method, Chain of Responsibility, Command, State and others. I'd add that Decorator is structural, because it's about wrapping objects with the same interface."

Likely follow-up questions

  • Which category is Decorator, and why? Structural: it composes objects by wrapping them with the same interface.
  • Is Repository a GoF pattern? No, it is from enterprise patterns (Fowler) and DDD.
  • Class vs object patterns? Class patterns use inheritance; object patterns use composition at runtime.
