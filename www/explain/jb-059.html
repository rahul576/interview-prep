How would you optimize a collection holding millions of objects?

JVM & Performance · scenario · levels senior, lead

In one line

Measure the real footprint first (heap dump, JOL), then presize the collection, replace boxed values with primitive collections or arrays, make each element smaller (fewer fields, compact types, deduplicated strings), and question whether everything must be in memory at all: stream, page or offload to an external cache.

Detailed explanation

Millions of small objects are usually dominated by overhead, not data. Every object has a header (12 bytes on a typical 64-bit JVM with compressed class pointers; newer JDKs offer compact object headers that shrink it to 8 bytes) and is padded to 8-byte alignment. A HashMap<Integer, Integer> entry costs roughly a 32-byte Node, a 4-byte table slot, plus two 16-byte Integer objects: about 70 bytes to store 8 bytes of data. A List<Long> with 10 million elements uses well over 200 MB, while a long[] uses 80 MB.

1. Measure. Take a heap dump and use Eclipse MAT to see retained size per collection and per class, or use Java Object Layout (JOL) to print an object's exact layout. Knowing what dominates guides everything else.

2. Presize. new ArrayList<>(expected) or HashMap.newHashMap(expected) (Java 19+) avoids repeated growth, which copies arrays and briefly doubles memory.

3. Avoid boxing. Use int[], long[] or primitive collections from fastutil, Eclipse Collections or HPPC (Int2ObjectOpenHashMap, LongArrayList). They store raw primitives and often use open addressing, avoiding per-entry node objects.

4. Shrink elements. Remove unused fields, use int instead of long or Integer where ranges allow, enums instead of strings, LocalDate packed into an int if extreme, and deduplicate repeated strings. Consider a structure of arrays (parallel arrays of fields) instead of an array of objects for very large numeric data sets.

5. Choose the right structure. ArrayList beats LinkedList in memory and cache locality; EnumMap and BitSet are very compact; sorted arrays with binary search can replace maps for read-only data.

6. Do not hold it all. Process in batches, stream rows from the database with a fetch size, page results, or put the data in Redis or an off-heap cache (Chronicle Map) when it does not need to live in the JVM heap. Large on-heap collections also make GC slower and heap dumps huge.

How it works

  1. Heap dump or JOL to measure per-entry cost.
  2. Presize to the expected count.
  3. Replace boxed collections with primitive ones.
  4. Slim down element classes and deduplicate values.
  5. Re-measure; if still too large, stream, page or move off-heap.

Example

// Before: ~70+ bytes per entry
Map<Integer, Integer> stockBySku = new HashMap<>();

// After: primitives, open addressing, presized
Int2IntOpenHashMap stock = new Int2IntOpenHashMap(5_000_000);
stock.put(10_001, 42);

// Before: List<Long> of 10M timestamps (~250 MB); after: long[] (80 MB)
long[] timestamps = new long[10_000_000];

Common mistakes

  • Optimising without measuring, then shrinking the wrong thing.
  • LinkedList for large lists.
  • Growing collections from default capacity to millions of entries.
  • Keeping full entity graphs when only IDs are needed.

How to answer in the interview

"First I measure: a heap dump in Eclipse MAT or Java Object Layout shows the real cost per entry, which is often several times the raw data because of headers, references and boxing. Then I presize the collection to avoid resizing and copying. If values are numbers I switch from boxed collections to primitive collections like fastutil or Eclipse Collections, or plain arrays. I shrink the element objects by dropping fields, using compact types and enums, and deduplicating repeated strings. Finally I question whether it must all be in memory at once: stream or page from the database, or move it into Redis or an off-heap store."

Likely follow-up questions

  • How much memory does a HashMap entry really cost? Around 32 bytes for the node plus a table slot, plus boxed key and value objects, often 60-80 bytes in total.
  • What are compact object headers? A newer HotSpot option that reduces headers from 12 to 8 bytes, cutting memory for small objects.
  • Why does LinkedList use more memory? Each element needs a node object with two extra references.
