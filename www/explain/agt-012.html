How do you stop agents from running forever, looping or overspending?

AI Agents & AIOps · concept · levels mid, senior

In one line

Enforce hard limits outside the model: maximum steps, token and cost budgets, wall-clock timeouts, loop detection for repeated calls, plus clear completion criteria in the instructions and a graceful stop that saves state, summarises and escalates.

Detailed explanation

Models do not reliably know when to stop. They may keep exploring, retry a failing call indefinitely, or oscillate between two approaches. Because each step resends a growing context, a runaway agent burns money quickly. The rule is: the runtime enforces limits, not the model.

Every run has a maximum number of steps or tool calls, a token and cost budget tracked from the provider's usage data, and a wall-clock timeout. Limits can be per run, per user per day and per tenant, with alerts when spend spikes. Separate limits apply to sub-agents so fan-out cannot explode.

Loop detection catches the classic failure: the same tool with the same arguments several times in a row, the same error repeated, or A-B-A-B oscillation. The runtime can inject a hint ("you already called search_logs with these arguments; the result was empty, try a different approach or stop") or stop the run.

Prevention starts in the design. Clear completion criteria in the instructions tell the model what "done" means: all tests pass, a ticket exists and is linked, the report has all sections. Tool results that clearly say "no results" or "already done" remove the ambiguity that causes retries.

When a limit triggers, the agent stops gracefully: it reports what it did, what remains and why it stopped, persists its state so the run can be resumed, and escalates to a human. Silent failure or a vague "something went wrong" is not acceptable. Finally, monitor steps and cost per run: frequent limit hits usually point to poor tools or instructions rather than to limits being too strict.

How it works

  1. Configure limits per agent: steps, tokens, cost, time.
  2. Track usage on every model and tool call.
  3. Hash tool name and arguments to detect repeats.
  4. On repeat, inject a hint; on threshold, stop.
  5. On limit, summarise, save state, escalate.
  6. Dashboard limit hits and cost per task; fix root causes.

Example

class RunGuard:
    def __init__(self, max_steps=25, max_cost_usd=2.0, max_seconds=600, max_repeats=3):
        self.max_steps, self.max_cost, self.max_seconds, self.max_repeats = max_steps, max_cost_usd, max_seconds, max_repeats
        self.steps, self.cost, self.start, self.seen = 0, 0.0, time.monotonic(), Counter()

    def check(self, usage, tool_call=None):
        self.steps += 1
        self.cost += usage.cost_usd
        if tool_call:
            key = (tool_call.name, json.dumps(tool_call.args, sort_keys=True))
            self.seen[key] += 1
            if self.seen[key] >= self.max_repeats:
                raise StopRun("loop", f"Repeated {tool_call.name} {self.seen[key]} times")
        if self.steps > self.max_steps:
            raise StopRun("steps", "Step limit reached")
        if self.cost > self.max_cost:
            raise StopRun("budget", f"Cost ${self.cost:.2f} over budget")
        if time.monotonic() - self.start > self.max_seconds:
            raise StopRun("timeout", "Time limit reached")

Common mistakes

  • Trusting the model to stop or to track its own budget.
  • Limits only per run, with no per-user or per-tenant cap.
  • Hard crash on limit with no summary or saved state.
  • Setting limits once and never reviewing hit rates.
  • Ambiguous tool results that invite retries.

How to answer in the interview

"I put hard limits outside the model, because the model can't be trusted to stop itself. Each run has a maximum number of steps, a token and cost budget and a timeout, enforced by the runtime. Loop detection catches repeated identical tool calls or oscillation and either injects a hint or stops. Clear completion criteria in the instructions help the model know when it's done, like all tests passing. When a limit is reached, the agent stops gracefully: it reports what it did and what is left, saves its state and escalates. And I monitor steps and cost per run, because frequent limit hits usually mean the tools or instructions need fixing."

Likely follow-up questions

  • How do you choose the step limit for a new agent? Run evals, look at the step distribution of successful runs, and set the limit around p95 to p99 plus margin.
  • Per-user limits? Yes, daily budgets per user and tenant prevent abuse and runaway costs.
  • What about sub-agents? Each gets its own budget, counted toward the parent's total.
