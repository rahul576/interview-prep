How do you configure a Terraform backend per environment, and how do you migrate state to a new backend?

Terraform · concept · levels mid, senior

In one line

Backend blocks cannot use variables, so use partial configuration: keep only the backend type in code and pass per-environment settings with -backend-config files, each with a distinct state key; move state with terraform init -migrate-state after backing it up and stopping other runs.

Detailed explanation

Terraform initialises the backend during terraform init, before it evaluates variables, locals or anything else, so a backend block like bucket = var.state_bucket is not allowed. Copying the whole configuration per environment just to change the backend would be wasteful, so the standard solution is partial backend configuration.

The code contains an almost empty block, for example terraform { backend "s3" {} } or backend "azurerm" {}. Each environment has a small file, dev.backend.hcl, prod.backend.hcl, with the bucket or storage account, container, region and, crucially, a unique key so environments never share state. The pipeline runs terraform init -backend-config=prod.backend.hcl. Values can also be passed as -backend-config="key=value" pairs, and credentials should come from the environment (OIDC, managed identity), never from these files. Many teams also keep production state in a separate account or subscription with stricter access.

Migrating state happens when moving from local to remote, between buckets or storage accounts, or between backend types. The safe procedure: make sure no one else is running Terraform against this state (pause pipelines), take a backup with terraform state pull > backup.tfstate, change the backend configuration, then run terraform init -migrate-state. Terraform detects the change, asks for confirmation and copies the state to the new backend. Finally run terraform plan; it must show no changes. If it proposes creating everything, Terraform is reading an empty or wrong state.

How it works

  1. Define the backend type in code with no environment-specific values.
  2. Create one backend config file per environment with a unique key.
  3. terraform init -backend-config=<env>.backend.hcl in the pipeline.
  4. For migration: lock out runs, back up, update config.
  5. terraform init -migrate-state, confirm copy.
  6. terraform plan must show no changes; then re-enable pipelines.

Example

# backend.tf
terraform {
  backend "azurerm" {}
}
# prod.backend.hcl
resource_group_name  = "rg-tfstate-prod"
storage_account_name = "acmetfstateprod"
container_name       = "tfstate"
key                  = "platform/network/prod.tfstate"
use_azuread_auth     = true
terraform state pull > backup-$(date +%F).tfstate
terraform init -backend-config=prod.backend.hcl -migrate-state
terraform plan   # expect: No changes

Common mistakes

  • Using the same key for several environments.
  • Migrating while a pipeline is running.
  • Using -reconfigure when you meant to migrate, which ignores the old state.
  • Storing access keys in backend config files in Git.

How to answer in the interview

"Backend blocks are evaluated before variables, so they can't use them. I use partial configuration: the backend block only names the type, like azurerm or s3, and each environment has a small file such as prod.backend.hcl with the bucket or storage account and a distinct key, passed with terraform init -backend-config. To migrate state to a new backend, I make sure nobody is running Terraform, back up the current state with terraform state pull, change the backend configuration and run terraform init -migrate-state, which copies the state after confirmation. Then I verify with terraform plan that there are no changes."

Likely follow-up questions

  • Plan shows everything as new after migration? Wrong key, container or workspace prefix, so Terraform reads an empty state; fix config or restore backup.
  • -reconfigure versus -migrate-state? Reconfigure switches backends without copying state.
  • Workspaces instead of keys? Possible, but separate keys or directories per environment are clearer.
