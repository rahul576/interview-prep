You renamed a module call in your code and now the plan wants to destroy and recreate 40 resources. How do you fix it?

Terraform · scenario · levels mid, senior

In one line

Renaming a module call changes every resource address, so Terraform sees old resources to destroy and new ones to create; add a moved block from module.old to module.new, verify the plan shows only moves with zero destroys, and keep the block until every environment and consumer has applied.

Detailed explanation

Terraform tracks objects by resource address, not by cloud ID or name. module.network.azurerm_subnet.app is a different address from module.network_core.azurerm_subnet.app. When you rename the module call, the configuration no longer contains the old addresses and contains new ones that are not in state, so Terraform plans to destroy 40 existing resources and create 40 new ones. For a network that means downtime; for databases, data loss.

The fix is a moved block (Terraform 1.1+): moved { from = module.network to = module.network_core }. One block can move an entire module instance, including everything inside it. It also works for single resources, for adding or changing for_each keys (from = aws_instance.web to = aws_instance.web["a"]), for count to for_each conversions, and for moving resources into or out of child modules. During plan, Terraform updates addresses in state first, then compares; the plan output lists each resource as "has moved to". The goal is 0 to add, 0 to change, 0 to destroy plus the moves; if any destroy appears, something else differs and must be investigated before approving.

The older alternative is terraform state mv module.network module.network_core. It works, but it is a manual, unreviewed operation that must be repeated in every workspace and environment, and someone always forgets one.

Moved blocks are harmless once applied, so keep them until every environment using the configuration has applied. In shared modules, keep internal moved blocks for much longer, often a whole major version, because consumers upgrade at different times and each needs the move instructions.

How it works

  1. Rename the module call in code.
  2. Add moved { from = ..., to = ... }.
  3. Run plan: expect "has moved to" entries and no destroys.
  4. Merge and apply in each environment.
  5. Remove the moved block after all states are migrated.

Example

module "network_core" {
  source = "./modules/network"
  cidr   = "10.10.0.0/16"
}

moved {
  from = module.network
  to   = module.network_core
}
  # module.network.azurerm_subnet.app has moved to module.network_core.azurerm_subnet.app
  ...
Plan: 0 to add, 0 to change, 0 to destroy.

Common mistakes

  • Approving a plan that still shows destroys.
  • Using state mv in one environment and forgetting others.
  • Removing moved blocks from shared modules too early.
  • Combining the rename with other changes in the same PR, making the plan hard to read.

How to answer in the interview

"Terraform identifies resources by address, like module.network.azurerm_subnet.app. Renaming the module call to network_core changes every address inside it, so Terraform thinks the old resources should be destroyed and new ones created. The fix is a moved block from module.network to module.network_core, which moves the whole module at once. After adding it, the plan should show the resources as moved with zero destroys and zero creates, and I verify that before approving. The older alternative is terraform state mv per environment, which is manual and unreviewed. I keep the moved block until every environment has applied, and much longer in shared modules."

Likely follow-up questions

  • When can moved blocks not help? Moving between different state files or changing resource type, which needs removed plus import.
  • Can moved handle count to for_each? Yes, with one moved block per index-to-key mapping.
  • Do moved blocks change real infrastructure? No, only state addresses.
