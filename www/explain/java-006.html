Compare an abstract class with an interface in modern Java. When would you choose each?

Core Java & OOP · concept · levels entry, mid

In one line

A class can extend one abstract class but implement many interfaces; interfaces define contracts or capabilities (with default, static and private methods but no instance state), while abstract classes provide shared state, constructors and base code for closely related classes.

Detailed explanation

Since Java 8 the gap between the two has narrowed, so the question is about intent.

Interfaces can contain abstract methods, default methods (Java 8) with implementation, static methods (Java 8), private methods (Java 9) to share code between defaults, and constants (public static final). They cannot have instance fields or constructors, and all members are public except private helper methods. A class may implement any number of interfaces, which is Java's form of multiple inheritance of type and behaviour. Interfaces can be sealed (Java 17) to restrict implementations, and functional interfaces with one abstract method work with lambdas.

Abstract classes are classes that cannot be instantiated. They can have instance fields, constructors, protected and private members, final methods, and a mix of abstract and concrete methods. A class can extend only one.

When to choose an interface: to define a role or capability that unrelated classes can share (Comparable, Closeable, PaymentGateway, Repository); for anything you want to mock, inject or swap (Spring beans, ports in hexagonal architecture); and for public APIs, because a class can implement several. Default methods let you evolve such an interface without breaking implementors.

When to choose an abstract class: when closely related classes need shared state and code and an "is-a" relationship, such as a template method base class (AbstractMessageHandler handling retries and logging, subclasses implementing handle()), or when you need constructors to enforce initialisation, or non-public members.

A common combination: an interface as the contract plus an abstract AbstractXxx base class as a convenience implementation (like List and AbstractList).

How it works

  1. Define the contract as an interface (what).
  2. Optionally add default methods for common convenience behaviour.
  3. Provide an abstract base class for shared state and skeleton logic (how, partially).
  4. Concrete classes extend the base and/or implement interfaces.
  5. Clients depend on the interface type.

Example

public interface PaymentGateway {                     // contract
    PaymentResult charge(Money amount, String token);
    default boolean supportsRefunds() { return true; }
    static PaymentGateway noop() { return (a, t) -> PaymentResult.ok(); }
}

public abstract class HttpPaymentGateway implements PaymentGateway {  // shared code + state
    protected final RestClient client;
    private final RetryPolicy retry;

    protected HttpPaymentGateway(RestClient client, RetryPolicy retry) {
        this.client = client; this.retry = retry;
    }
    @Override public final PaymentResult charge(Money amount, String token) {
        return retry.execute(() -> doCharge(amount, token));   // template method
    }
    protected abstract PaymentResult doCharge(Money amount, String token);
}

public class StripeGateway extends HttpPaymentGateway implements AutoCloseable { ... }

Common mistakes

  • Saying interfaces cannot have any method bodies (outdated since Java 8).
  • Using an abstract class just to share one utility method.
  • Putting state-like logic into default methods.
  • Deep abstract class hierarchies instead of composition.

How to answer in the interview

"A class can extend only one abstract class but implement many interfaces. Since Java 8 interfaces can have default and static methods, and since Java 9 private methods, but they still can't have instance fields or constructors. An abstract class can have state, constructors, protected members and a mix of abstract and concrete methods. I use an interface to define a contract or capability that unrelated classes can share, like Comparable or a PaymentGateway, which is also easy to mock and inject. I use an abstract class when closely related classes need shared code and state, for example a template-method base class handling retries."

Likely follow-up questions

  • What happens if a class implements two interfaces that have the same default method? Compilation fails unless the class overrides the method; it can delegate with InterfaceA.super.method().
  • Can an abstract class have no abstract methods? Yes; it simply cannot be instantiated.
  • Why were default methods added? To evolve interfaces such as Collection (adding stream and forEach) without breaking existing implementations.
