What happens, at a network level, when you type a URL into the browser and press Enter?

Networking · concept · levels entry, mid

In one line

The browser resolves the name with DNS, opens a TCP connection (three-way handshake), negotiates TLS, sends an HTTP request that may pass through a CDN and load balancer to a backend, receives the response and renders the page, fetching further resources.

Detailed explanation

1. URL parsing and caches. The browser parses scheme, host, port and path, checks HSTS (forcing HTTPS) and its HTTP cache; a fresh cached response may avoid the network entirely.

2. DNS resolution. It checks the browser DNS cache, then the OS resolver (and /etc/hosts), then asks the configured recursive resolver (ISP, corporate, or public like 1.1.1.1, possibly over DNS-over-HTTPS). On a miss, the resolver queries a root server, the TLD server (for .com) and the authoritative server for the domain, caching each answer for its TTL. Modern browsers may also query HTTPS/SVCB records to learn HTTP/3 support.

3. TCP handshake. The client sends SYN, the server replies SYN-ACK, the client sends ACK, to port 443. That costs one round trip.

4. TLS handshake. With TLS 1.3, ClientHello carries key shares and SNI; the server responds with its key share, certificate chain and finishes; the browser validates the chain against trusted CAs, hostname and expiry. Session keys are derived via ECDHE. TLS 1.3 adds one round trip (zero with resumption). ALPN negotiates HTTP/2.

5. HTTP request. GET /path with headers (Host, cookies, Accept-Encoding). On the server side, a CDN edge may answer from cache; otherwise it forwards to the origin, where a load balancer picks a healthy backend, possibly via a reverse proxy, and the application talks to caches and databases.

6. Response and rendering. The server returns a status code, headers and body (often compressed). The browser parses HTML, builds the DOM, discovers CSS, JavaScript and images, fetches them (reusing connections, multiplexed over HTTP/2), builds the CSSOM, runs scripts, lays out and paints.

HTTP/3 runs over QUIC on UDP, merging transport and TLS 1.3 handshakes into one round trip and avoiding TCP head-of-line blocking.

How it works

  1. Parse URL, check HSTS and caches.
  2. DNS: browser, OS, recursive resolver, root, TLD, authoritative.
  3. TCP SYN, SYN-ACK, ACK to port 443.
  4. TLS 1.3 handshake with certificate validation and key exchange.
  5. HTTP request via CDN and load balancer to the application.
  6. Response, then parse, fetch sub-resources and render.

Example

dig +short www.example.com
curl -sv -o /dev/null https://www.example.com 2>&1 | grep -E "Connected|SSL connection|ALPN|HTTP/"
curl -s -o /dev/null -w "dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n" https://www.example.com

Common mistakes

  • Forgetting caching layers (browser, DNS, CDN).
  • Saying TLS happens before TCP for HTTP/1.1 and HTTP/2.
  • Mixing up the recursive resolver and authoritative server.
  • Ignoring that a CDN may answer without contacting the origin.

How to answer in the interview

"The browser first checks its caches and HSTS, then resolves the domain via DNS: browser and OS caches, then a recursive resolver that walks root, TLD and authoritative servers and caches the answer for the TTL. It opens a TCP connection with SYN, SYN-ACK, ACK on port 443, then does a TLS 1.3 handshake where the server presents its certificate, the browser validates it and keys are agreed. It sends an HTTP GET, which may be answered by a CDN or forwarded through a load balancer to a backend. Finally the browser parses the HTML, fetches CSS, JavaScript and images and renders the page. With HTTP/3, QUIC over UDP combines the transport and TLS handshakes."

Likely follow-up questions

  • How does HTTP/2 or HTTP/3 change this? HTTP/2 multiplexes many requests over one TCP connection; HTTP/3 uses QUIC over UDP with a combined handshake and no TCP head-of-line blocking.
  • What is SNI? The hostname sent in ClientHello so one IP can serve many certificates.
  • Where would you look if the page is slow? Browser dev tools waterfall or curl timings to split DNS, connect, TLS, time to first byte and download.
