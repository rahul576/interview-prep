How would you optimize the grouping algorithm?

DSA: Arrays & Strings · scenario · levels mid

In one line

The biggest win is algorithmic: replace pairwise comparison with hashing by a signature (quadratic → linear in n); then use a counting key (O(k) per word), build keys efficiently with char arrays/StringBuilder, pre-size the map, and for huge inputs use parallel streams or a MapReduce-style partition.

Detailed explanation

Optimise in order of impact:

1. Fix the algorithm. Pairwise comparison is O(n²·k). Grouping by a canonical key in a HashMap is O(n·k log k) or O(n·k). No micro-optimisation comes close to this gain.

2. Cheaper keys. Sorting costs O(k log k). A frequency count in an int[26] is O(k), and the serialised key has fixed size, so hashing is cheap. For short dictionary words the difference is small; for long strings it matters.

3. Reduce allocations. Avoid key += count + "#" string concatenation in a loop, which creates many temporary strings. Reuse one int[26] and one StringBuilder (setLength(0)), or encode counts directly into a char[26] and use new String(chars) (valid when counts stay below 65,536). Fewer objects mean less GC pressure.

4. Pre-size the map. If n is known, HashMap.newHashMap(n) (Java 19+) or new HashMap<>(n * 4 / 3 + 1) avoids repeated resizing and rehashing.

5. Early exits and filtering. Normalise once; skip empty or invalid words; if only groups of size > 1 are needed, filter at the end rather than building extra structures.

6. Parallelism. For millions of words on a multi-core machine, Arrays.stream(words).parallel().collect(Collectors.groupingByConcurrent(Solution::key)) spreads key computation across cores. Measure first: for small inputs the overhead outweighs the gain, and group order is not preserved.

7. Beyond one machine. For a billion words that do not fit in memory, treat it as MapReduce: map each word to (key, word), shuffle/partition by key so all anagrams go to the same reducer, then reduce into groups. Spark's groupByKey or reduceByKey, or a streaming job partitioned by key, implements this. Alternatively, an external sort by key followed by a linear scan works on a single machine with disk.

How it works

  1. Replace O(n²) comparisons with signature hashing.
  2. Switch to an O(k) counting key.
  3. Reuse buffers and pre-size the map.
  4. Parallelise with concurrent collectors when profiling shows benefit.
  5. Partition by key across machines for data beyond memory.

Example

public static Collection<List<String>> groupFast(String[] words) {
    Map<String, List<String>> map = HashMap.newHashMap(words.length);  // pre-sized
    char[] counts = new char[26];                                       // reused buffer
    for (String w : words) {
        Arrays.fill(counts, (char) 0);
        for (int i = 0, len = w.length(); i < len; i++) counts[w.charAt(i) - 'a']++;
        map.computeIfAbsent(new String(counts), k -> new ArrayList<>()).add(w);
    }
    return map.values();
}

// Multi-core for very large inputs
Map<String, List<String>> big = Arrays.stream(words).parallel()
        .collect(Collectors.groupingByConcurrent(Solution::countKey));
# Spark (PySpark) for a billion words
words.map(lambda w: ("".join(sorted(w)), w)).groupByKey().mapValues(list)

Common mistakes

  • Micro-optimising before fixing the quadratic algorithm.
  • Using parallel streams for small inputs and getting slower code.
  • String concatenation in tight loops.
  • Not measuring with a profiler or JMH benchmark.

How to answer in the interview

"The biggest gain is algorithmic: stop comparing pairs and group by a signature in a hash map, going from quadratic to linear in the number of words. Next, for long words I'd compute the key by counting into an int[26] instead of sorting, so it's O(k) per word, and build the key with a char array or StringBuilder rather than concatenation. I'd pre-size the HashMap if I know the count. For very large inputs a parallel stream with groupingByConcurrent can use several cores, and if the data doesn't fit in memory, I'd partition by key across machines, MapReduce style, for example with Spark."

Likely follow-up questions

  • How would you handle a billion words? Map to (key, word), partition by key, reduce per partition (Spark or MapReduce), or external sort by key.
  • How would you prove an optimisation helped? Benchmark with JMH and profile allocations.
  • Why reuse buffers? Fewer allocations reduce GC pressure in tight loops.
