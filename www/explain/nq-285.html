What are the key stages of a CI/CD pipeline?

DevOps & CI/CD · concept · levels mid

In one line

Key stages: trigger and checkout, build, unit and integration tests with coverage, static analysis and quality gate, security scans (SAST, dependency, secrets, image), package and publish a versioned artifact, deploy to environments with smoke and integration tests, then approval or automated gates and a progressive production rollout with monitoring and rollback.

Detailed explanation

A pipeline is a sequence of quality gates; each stage increases confidence while failing as early and cheaply as possible.

  1. Trigger and checkout on push or pull request.
  2. Build: mvn -B package or Gradle, using dependency caches.
  3. Tests: unit tests (Surefire), integration tests with Testcontainers (Failsafe), coverage via JaCoCo.
  4. Static analysis: SonarQube quality gate on new code.
  5. Security: secret scanning, SAST (CodeQL, Sonar), SCA dependency checks (Snyk, OWASP Dependency-Check, Dependabot), IaC scanning (Checkov).
  6. Package and publish: build the Docker image, scan it with Trivy or Grype, tag it with version and commit SHA, sign it, push to ECR, ACR or Nexus.
  7. Deploy to dev and test: Helm or GitOps, then smoke, API and integration tests.
  8. Staging: the same artifact, with end-to-end and performance tests.
  9. Production: approval or automated gate, then rolling, blue-green or canary rollout, health checks and automatic rollback.

Build once, promote many: the artifact tested in staging must be the exact bytes deployed to production; only configuration differs per environment.

How it works

  1. Fast checks first (compile, unit tests) for quick feedback.
  2. Parallelise independent stages such as scans and tests.
  3. Produce one immutable, versioned artifact.
  4. Promote it through environments with increasing test depth.
  5. Gate production on evidence and roll out progressively.

Example

pipeline {
  agent any
  stages {
    stage('Build & Unit') { steps { sh './mvnw -B verify' } }
    stage('Quality')      { steps { withSonarQubeEnv('sonar') { sh './mvnw sonar:sonar' } } }
    stage('Gate')         { steps { timeout(time: 10, unit: 'MINUTES') { waitForQualityGate abortPipeline: true } } }
    stage('Image')        { steps { sh 'docker build -t $REG/orders:$GIT_COMMIT . && trivy image --exit-code 1 --severity CRITICAL $REG/orders:$GIT_COMMIT' } }
    stage('Push')         { steps { sh 'docker push $REG/orders:$GIT_COMMIT' } }
    stage('Deploy dev')   { steps { sh 'helm upgrade --install orders chart -f values-dev.yaml --set image.tag=$GIT_COMMIT' } }
  }
}

Common mistakes

  • Rebuilding per environment.
  • Running slow tests before fast ones.
  • Security scans only before release.
  • No post-deployment verification.

How to answer in the interview

"A typical pipeline triggers on commit or pull request, checks out and builds with Maven, runs unit and integration tests with coverage, then SonarQube analysis with a quality gate and security scans: secrets, SAST and dependency checks. It packages a jar and Docker image, scans the image with Trivy and publishes it with a version tag. Then it deploys to dev with smoke and integration tests, promotes the same artifact to staging for end-to-end and performance tests, and after approval or an automated gate rolls out to production with canary or blue-green, monitoring and automatic rollback."

Likely follow-up questions

  • Why build once and promote? Guarantees what was tested is what runs; avoids drift.
  • How do you speed up a slow pipeline? Caching, parallel stages, test splitting, incremental builds.
  • Where do database migrations run? As a controlled deploy step, backward compatible.
