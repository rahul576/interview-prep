What does terraform init do, and when do you need to run it again?

Terraform · concept · levels entry

In one line

terraform init prepares a working directory: it configures the backend, downloads providers and writes .terraform.lock.hcl, downloads modules, and stores them in .terraform/; rerun it after changing the backend, providers or module sources, and in every fresh CI job.

Detailed explanation

Terraform configurations are not self-contained: they depend on plugins and remote code. init resolves all of that before any plan.

Backend. It reads the backend block (plus any -backend-config values), connects to the state storage such as an Azure storage container, an S3 bucket or HCP Terraform, and verifies access. If the backend changed, init asks whether to migrate existing state (-migrate-state) or start fresh (-reconfigure).

Providers. It reads required_providers, picks versions that match the constraints, or exactly the versions already recorded in the dependency lock file, downloads them and verifies their checksums. It creates or updates .terraform.lock.hcl, which you commit. To move to newer versions allowed by your constraints you run terraform init -upgrade.

Modules. It downloads modules from the registry, Git, or other sources into .terraform/modules. Local path modules are just referenced.

Everything goes into the hidden .terraform directory, which is not committed. Init never changes infrastructure and is safe to rerun. You need it the first time in a directory, in every new CI job (fresh workspace), and after changing the backend, adding or upgrading providers, or adding or changing module sources or versions; plan will tell you "Module not installed" or "Inconsistent dependency lock file" if you forgot.

How it works

  1. Parse configuration for backend, providers and modules.
  2. Initialise the backend and check or migrate state.
  3. Download modules into .terraform/modules.
  4. Resolve provider versions using constraints and the lock file.
  5. Download and verify providers into .terraform/providers.
  6. Write or update .terraform.lock.hcl.

Example

terraform init \
  -backend-config="resource_group_name=rg-tfstate" \
  -backend-config="storage_account_name=sttfstateprod" \
  -backend-config="container_name=tfstate" \
  -backend-config="key=network.tfstate"

terraform init -upgrade                  # newer providers within constraints
export TF_PLUGIN_CACHE_DIR="$HOME/.terraform.d/plugin-cache"   # faster CI

Common mistakes

  • Not committing .terraform.lock.hcl, so CI and laptops use different providers.
  • Committing the .terraform directory.
  • Using -reconfigure when you meant to migrate state, and starting with empty state.
  • Expecting init to upgrade providers without -upgrade.

How to answer in the interview

"terraform init prepares the working directory. It configures the backend so Terraform knows where state lives, downloads the providers matching required_providers or the exact versions in the lock file and writes that lock file, and downloads modules. Everything goes into the .terraform directory. I run it the first time, in every CI job, and after changing the backend, providers or module sources; for newer provider versions I use init -upgrade. It's safe to rerun and never changes infrastructure."

Likely follow-up questions

  • How do you speed up init in CI? Use a plugin cache directory, cache it between runs, or use a provider mirror.
  • Difference between -reconfigure and -migrate-state? Reconfigure ignores old state; migrate copies it to the new backend.
  • Lock file for multiple platforms? terraform providers lock -platform=... records hashes for each.
