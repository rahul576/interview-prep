Which testing frameworks have you used?

Testing · scenario · levels entry

In one line

Answer with the tools you have actually used and how: typically JUnit 5 for tests, Mockito for mocks, AssertJ for assertions, Spring Boot Test (MockMvc, slices, @SpringBootTest), Testcontainers and WireMock for integration, REST Assured for APIs, Pact or Spring Cloud Contract for contracts, and JMeter or Gatling for load.

Detailed explanation

This is an experience question. The interviewer wants to know whether you can test a real Java backend at every level, and whether you understand why each tool is used. A list of names without context sounds memorised; a structured answer with a short example per level sounds like experience.

Organise your answer by test level:

  • Unit: JUnit 5 (Jupiter) with @ParameterizedTest, @Nested, @DisplayName; Mockito for test doubles (@Mock, when, verify, ArgumentCaptor); AssertJ for fluent, readable assertions (Hamcrest is the older alternative).
  • Spring layers: Spring Boot Test: @WebMvcTest with MockMvc (or MockMvcTester), @DataJpaTest, @JsonTest, @SpringBootTest, @MockitoBean.
  • Integration with real dependencies: Testcontainers for PostgreSQL, Kafka, Redis; WireMock for third-party HTTP APIs; Awaitility for asynchronous assertions.
  • API level: REST Assured or WebTestClient for black-box API tests.
  • Between services: Pact or Spring Cloud Contract for consumer-driven contracts.
  • Non-functional: JMeter, Gatling or k6 for load tests; PIT for mutation testing.
  • Pipeline: JaCoCo coverage and SonarQube quality gates in CI (Jenkins, GitHub Actions, GitLab CI).

Be honest: only mention tools you can discuss in depth, because follow-up questions will probe them. Saying "I have read about Pact but used Spring Cloud Contract in my project" is better than bluffing. Close with a concrete result: a bug caught, a flaky suite fixed, build time reduced.

How it works

  1. Start with the levels you test at.
  2. Name the main tool for each and what you did with it.
  3. Add one concrete project example.
  4. Mention how tests run in CI and any quality gates.
  5. Be ready for deeper follow-ups on each named tool.

Example

A sample answer structure with a STAR-style example:

  • Situation: order service with PostgreSQL and Kafka; tests used H2 and missed bugs.
  • Task: make integration tests trustworthy without slowing CI.
  • Action: replaced H2 with Testcontainers PostgreSQL via @ServiceConnection, shared containers across tests, added WireMock for the payment API.
  • Result: caught two migration bugs before release; build time stayed under ten minutes.
@WebMvcTest(OrderController.class)
class OrderControllerTest {
    @Autowired MockMvc mvc;
    @MockitoBean OrderService service;

    @Test
    void validatesQuantity() throws Exception {
        mvc.perform(post("/orders").contentType(APPLICATION_JSON)
                .content("{\"sku\":\"A1\",\"quantity\":0}"))
           .andExpect(status().isBadRequest());
    }
}

Common mistakes

  • Listing every tool you have heard of.
  • Naming tools without explaining what you used them for.
  • Forgetting integration and contract tooling, implying only unit tests.
  • Claiming tools you cannot answer follow-up questions about.

How to answer in the interview

"For unit tests I use JUnit 5, including parameterised and nested tests, with Mockito for mocking dependencies and AssertJ for assertions. For Spring layers I use WebMvcTest with MockMvc for controllers, DataJpaTest for repositories and SpringBootTest for full integration tests. In my last project we ran PostgreSQL and Kafka in Testcontainers and stubbed the payment provider with WireMock, which caught migration bugs H2 had hidden. I've used REST Assured for API tests and Spring Cloud Contract between services, Gatling for load tests, and JaCoCo with SonarQube gates in the CI pipeline."

Likely follow-up questions

  • How do you decide what to test at which level? Logic in unit tests, each integration point in integration tests, critical journeys end-to-end.
  • Why AssertJ over JUnit assertions? Fluent API, better failure messages and rich collection assertions.
  • What did you load test, and what did you find? Prepare one concrete story with numbers.
