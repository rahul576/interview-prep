You inherited Terraform code written for version 0.12 with interpolation-only syntax and old patterns. How do you modernise it?

Terraform · scenario · levels mid, senior

In one line

Modernise stepwise: upgrade Terraform through 0.13, 0.14, 0.15 to 1.x with a clean plan and apply at each step, add required_providers source addresses and a lock file, remove interpolation-only syntax and deprecated features, then refactor with moved blocks so nothing is recreated.

Detailed explanation

Terraform 0.12 introduced HCL2, so the code is already in the modern language, but it usually carries habits from 0.11 and misses later features. The safe approach is many small steps, each ending with no unexpected changes in the plan.

Version upgrades. You should not jump straight from 0.12 to the latest 1.x. Version 0.13 introduced provider source addresses (hashicorp/aws) in required_providers, and the terraform 0.13upgrade command helps add them. 0.14 introduced the dependency lock file .terraform.lock.hcl and sensitive output handling. 0.15 removed many deprecated features and stabilised the state format leading to 1.0, after which upgrades within 1.x are smooth. At each step you run init -upgrade, plan and an apply so the state is written in the new format. Provider major versions (for example AWS provider 3 to 5, azurerm 2 to 4) have their own upgrade guides and should be a separate step.

Code cleanup. Replace "${var.name}" with var.name where the expression is not inside a string, remove deprecated functions like list() and map() in favour of tolist/tomap or literal syntax, replace provisioners with cloud-init or configuration management where possible, and pin provider versions with constraints.

Refactoring. Once versions are current, convert count to for_each for stable addresses, extract modules and rename resources. Since 1.1, moved blocks record these address changes in code, so the plan shows a move instead of destroy and create. Importing unmanaged resources can use import blocks (1.5+).

How it works

  1. Freeze changes, back up the state and run terraform plan to confirm a clean baseline.
  2. Upgrade to 0.13, run 0.13upgrade, init, plan, apply.
  3. Repeat for 0.14 (commit the lock file), 0.15 and then the latest 1.x.
  4. Upgrade providers one major version at a time following their upgrade guides.
  5. Clean syntax with terraform fmt and manual edits; plans must stay empty.
  6. Refactor count to for_each and into modules using moved blocks.
  7. Roll through dev, test and finally production.

Example

# before
resource "aws_instance" "web" {
  count         = 2
  ami           = "${var.ami}"
  instance_type = "${var.type}"
}

# after
resource "aws_instance" "web" {
  for_each      = toset(["a", "b"])
  ami           = var.ami
  instance_type = var.type
}

moved {
  from = aws_instance.web[0]
  to   = aws_instance.web["a"]
}
moved {
  from = aws_instance.web[1]
  to   = aws_instance.web["b"]
}

Common mistakes

  • Jumping several major Terraform versions at once and getting state or syntax errors.
  • Upgrading Terraform and providers in the same step, so you cannot tell which caused a diff.
  • Accepting plans with replacements because "it is only a refactor".
  • Forgetting other users and pipelines still pinned to the old version.

How to answer in the interview

"I modernise in small safe steps with a clean plan after each. First Terraform itself: 0.13 for provider source addresses with the upgrade command, 0.14 for the lock file, 0.15, then 1.x, applying at each step so the state format is upgraded. Then providers, one major version at a time. Then cleanup: remove interpolation-only expressions, deprecated functions and provisioners, and pin versions. Larger refactors like count to for_each or extracting modules come last, with moved blocks so nothing is recreated. The rule throughout is no unexpected changes in the plan, and I do it in lower environments first."

Likely follow-up questions

  • Which step carries the most risk? Provider major upgrades and count-to-for_each refactors, since they can trigger replacements.
  • How do you keep everyone on the same version? required_version constraints, the lock file and a pinned version in CI.
  • What replaces terraform state mv today? moved blocks, which are reviewable in code.
