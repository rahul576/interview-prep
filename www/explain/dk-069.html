Containers have intermittent DNS failures or very slow name resolution. What could be wrong?

Docker · scenario · levels senior

In one line

Container DNS goes through Docker's embedded DNS at 127.0.0.11 (on user-defined networks), which forwards to upstreams taken from the host's resolv.conf; failures usually come from an unreachable or slow upstream (often a host-local resolver like systemd-resolved), ndots/search-domain amplification, musl (Alpine) resolver quirks, conntrack races or MTU problems.

Detailed explanation

On the default bridge network a container gets a copy of the host's /etc/resolv.conf. On user-defined networks it gets nameserver 127.0.0.11, Docker's embedded resolver, which answers container and service names and forwards everything else to the host's configured upstreams. If the host points at a loopback resolver such as systemd-resolved (127.0.0.53), that address is meaningless inside the container's network namespace. Docker then uses the real upstreams or falls back to public resolvers like 8.8.8.8, which a corporate firewall may block, giving intermittent or total failures.

Slowness often comes from the resolver searching domain suffixes. With a long search list and a high ndots (Kubernetes uses 5), one lookup of api.example.com may first try several suffixed names, each timing out or returning NXDOMAIN before the real query. Alpine's musl libc behaves differently from glibc: it sends queries to all nameservers in parallel, handles search domains and TCP fallback differently, which exposes misconfigurations that Debian images hide.

At the network level, the parallel A and AAAA queries from the same socket can hit a conntrack race in the Linux kernel that drops one packet, causing 5-second timeouts. On VPNs or overlay networks a wrong MTU can drop large DNS responses.

How it works

  1. Reproduce inside the container: dig, nslookup or getent hosts with timing.
  2. Compare with the same query on the host and against a specific server (dig @10.0.0.2).
  3. Check /etc/resolv.conf in the container: nameserver, search list, options.
  4. Check the host's upstream DNS health and firewall rules.
  5. Fix: set explicit DNS servers, trim search domains, lower ndots, use fully qualified names (trailing dot) or a node-local DNS cache.

Example

docker run --rm --network appnet nicolaka/netshoot sh -c \
  'cat /etc/resolv.conf; time dig +search api.example.com; dig @10.0.0.2 api.example.com'
{ "dns": ["10.0.0.2", "10.0.0.3"], "dns-search": ["corp.example.com"] }

Placed in /etc/docker/daemon.json, this pins reachable corporate resolvers for all containers.

Common mistakes

  • Testing DNS only from the host and assuming containers behave the same.
  • Blaming the app when the real issue is 5-second timeouts from dropped UDP packets.
  • Adding many search domains, multiplying lookups per name.
  • Ignoring MTU on VPN or overlay networks.

How to answer in the interview

"First I check how the container resolves: on user-defined networks it uses Docker's embedded DNS at 127.0.0.11, which forwards to the host's upstream servers. A common trap is the host using systemd-resolved at 127.0.0.53, which containers can't reach, so Docker falls back to public DNS that the corporate network blocks. I test with dig inside the container and on the host, compare timings and look at resolv.conf. Other causes are slow upstreams, long search lists with high ndots, Alpine's musl resolver, conntrack races causing five-second timeouts and MTU issues on VPNs. The fix is usually explicit dns servers in daemon.json, fewer search domains, or a local DNS cache."

Likely follow-up questions

  • Why does Alpine behave differently? musl queries nameservers in parallel and handles search domains and TCP fallback differently from glibc.
  • What causes exact 5-second delays? A dropped query (often a conntrack race) followed by the resolver's 5-second retry timeout.
  • How do Kubernetes clusters mitigate this? NodeLocal DNSCache, lower ndots in dnsConfig, and fully qualified names.
