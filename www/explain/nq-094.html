When would you use explicit locks instead of synchronized blocks?

Concurrency · scenario · levels mid, senior

In one line

Stay with synchronized for simple critical sections; switch to explicit locks when you need tryLock/timeouts, interruptible waiting, fairness, multiple Conditions, read-write separation, or locking across methods; on Java 21-23 also to avoid virtual-thread pinning around blocking calls.

Detailed explanation

synchronized is the right default: it is short, block-structured, cannot be left locked by accident, and the JVM optimises it well. Explicit locks (ReentrantLock, ReentrantReadWriteLock, StampedLock) are a tool for specific needs:

  • Bounded waiting / deadlock avoidance: tryLock(timeout) lets a thread give up instead of waiting forever. For a money transfer that must lock two accounts, a thread that cannot get the second lock in time releases the first and retries with random backoff, breaking the hold-and-wait condition.
  • Cancellation: lockInterruptibly() lets a task waiting for a lock respond to Future.cancel(true) or shutdown. A thread blocked entering synchronized ignores interrupts.
  • Fairness: new ReentrantLock(true) serves waiters in order, useful when starvation is observed, accepting lower throughput.
  • Multiple conditions: one lock with separate Conditions such as notFull and notEmpty in a bounded buffer, so you signal only the threads that can proceed instead of notifyAll.
  • Read-write separation: many readers, one writer, via ReentrantReadWriteLock or StampedLock optimistic reads.
  • Non-block-structured locking: acquiring in one method and releasing in another, or hand-over-hand locking along a linked structure.
  • Monitoring: getQueueLength(), isLocked() for diagnostics.
  • Virtual threads: on Java 21-23, blocking (I/O, sleeps) inside synchronized pinned the virtual thread to its carrier; ReentrantLock did not. Since Java 24 (JEP 491) this is largely fixed, so it no longer needs to drive the decision on current JDKs.

Remember the cost: always unlock() in finally, and do not call lock() inside the try.

How it works

  1. Identify the requirement synchronized cannot express (timeout, interrupt, fairness, conditions, read/write).
  2. Replace the monitor with a private final lock object.
  3. Use the lock(); try { ... } finally { unlock(); } idiom.
  4. Use tryLock with timeout and backoff where deadlock is possible.
  5. Test under contention and monitor lock waits (JFR).

Example

boolean transfer(Account from, Account to, BigDecimal amount) throws InterruptedException {
    long deadline = System.nanoTime() + TimeUnit.SECONDS.toNanos(1);
    while (System.nanoTime() < deadline) {
        if (from.lock.tryLock()) {
            try {
                if (to.lock.tryLock(50, TimeUnit.MILLISECONDS)) {
                    try {
                        from.debit(amount);
                        to.credit(amount);
                        return true;
                    } finally { to.lock.unlock(); }
                }
            } finally { from.lock.unlock(); }          // release first lock if second failed
        }
        Thread.sleep(ThreadLocalRandom.current().nextLong(1, 10));   // random backoff
    }
    return false;                                     // caller reports "try again"
}

Common mistakes

  • Using explicit locks everywhere "for flexibility" and forgetting unlock().
  • tryLock retry loops without random backoff, causing livelock.
  • Fair locks by default, hurting throughput.
  • Still choosing locks for pinning reasons on Java 24+ without measuring.

How to answer in the interview

"I stay with synchronized for simple critical sections because it's shorter and can't forget to unlock. I switch to explicit locks when I need something it lacks: tryLock with a timeout so a thread can give up instead of waiting forever or deadlocking, for example when locking two accounts in a transfer; lockInterruptibly so a cancelled task stops waiting; a fair lock when I see starvation; several Conditions like notFull and notEmpty in a bounded buffer; read-write separation for read-heavy data; or locking and unlocking in different methods. On Java 21 to 23 ReentrantLock also avoided pinning virtual threads, though Java 24 largely fixed that."

Likely follow-up questions

  • Can you show how tryLock can prevent a deadlock in a money transfer? Lock the first account, tryLock the second with a timeout; on failure release both and retry with random backoff (or simply order locks by account id).
  • Why not just order the locks? Ordering is simpler and also works; tryLock helps when a global order is hard to define or you need a time limit.
  • What is lock striping? Using several locks for different parts of the data, as ConcurrentHashMap does per bin, to reduce contention.
