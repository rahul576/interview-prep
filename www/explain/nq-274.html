How do you mock external dependencies during unit testing?

Testing · scenario · levels mid

In one line

Design classes to receive external dependencies through the constructor as interfaces, replace them in unit tests with Mockito mocks stubbed for success, empty and failure cases, verify important calls with captors, inject a fixed Clock for time, use @MockitoBean only inside Spring tests, and test the real HTTP or database layer with WireMock or Testcontainers.

Detailed explanation

Mocking is easy when the design allows it. If a service creates its own RestTemplate, calls LocalDateTime.now() or uses static helpers, a test cannot replace them. So the first step is dependency injection: the service receives PaymentClient, OrderRepository, Clock and perhaps an IdGenerator through its constructor. Ideally these are your own interfaces (ports), with adapters that wrap third-party SDKs.

In the unit test:

  • Create mocks with @Mock and the service with new or @InjectMocks.
  • Stub every relevant outcome: a successful response, an empty result, a business error (card declined), a technical failure (timeout, IOException). Each branch of your code deserves a test.
  • Assert the result first: return value, thrown exception, changed state.
  • Verify only interactions that are part of the behaviour, such as "the payment was charged once with 40.00", using ArgumentCaptor to check the request. Use never() to prove something did not happen after an error.
  • Time and randomness: inject Clock.fixed(...) and a controllable id or random source so tests are deterministic.

In Spring slice tests such as @WebMvcTest, collaborators are beans; replace them with @MockitoBean (Spring Framework 6.2, the successor of @MockBean).

Mocks are for unit tests. To test the adapter itself (the HTTP client's serialisation, headers, timeouts, retries, or a repository's SQL), use WireMock to stand in for the remote API at the HTTP level, and Testcontainers for databases and brokers. Mocking an HTTP library or JDBC directly gives false confidence.

How it works

  1. Extract external calls behind interfaces; inject via constructor.
  2. In tests, mock those interfaces.
  3. Stub success, edge and failure responses per test.
  4. Act, assert outcome, verify key calls and arguments.
  5. Cover adapters separately with WireMock or Testcontainers.

Example

class RefundServiceTest {
    PaymentClient payments = mock(PaymentClient.class);
    RefundRepository refunds = mock(RefundRepository.class);
    Clock clock = Clock.fixed(Instant.parse("2026-03-01T09:00:00Z"), ZoneOffset.UTC);
    RefundService service = new RefundService(payments, refunds, clock);

    @Test
    void refundsWithinThirtyDays() {
        when(payments.refund(any())).thenReturn(new RefundResult("r-1", OK));

        service.refund(order("2026-02-10T10:00:00Z", "40.00"));

        ArgumentCaptor<RefundRequest> req = ArgumentCaptor.forClass(RefundRequest.class);
        verify(payments).refund(req.capture());
        assertThat(req.getValue().amount()).isEqualByComparingTo("40.00");
    }

    @Test
    void recordsFailureWhenProviderTimesOut() {
        when(payments.refund(any())).thenThrow(new PaymentTimeoutException());

        assertThatThrownBy(() -> service.refund(order("2026-02-10T10:00:00Z", "40.00")))
            .isInstanceOf(RefundFailedException.class);
        verify(refunds).save(argThat(r -> r.status() == Status.FAILED));
    }
}

Common mistakes

  • Hard-coded new or static calls that cannot be replaced.
  • Only stubbing the happy path.
  • Mocking the HTTP library itself instead of using WireMock.
  • Calling LocalDateTime.now() directly, making date logic untestable.

How to answer in the interview

"I design classes so external dependencies come in through the constructor as interfaces: the payment client, the repository, even the Clock. In a unit test I create Mockito mocks and stub what each should return for that scenario: success, empty results, exceptions like a timeout, so every branch runs. Then I assert the result and verify the important interactions, for example that the payment client was called once with the right amount, using an ArgumentCaptor. Time is a fixed Clock. In Spring slice tests I use MockitoBean. For the HTTP or database layer itself I use WireMock or Testcontainers instead of mocks."

Likely follow-up questions

  • Risk of over-mocking? Tests mirror implementation, break on refactoring and miss real integration bugs.
  • How do you mock static methods? Mockito.mockStatic in a try-with-resources, but prefer refactoring to injection.
  • WireMock vs Mockito for HTTP clients? WireMock tests the real HTTP behaviour; Mockito only the caller's logic.
