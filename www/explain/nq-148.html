What is the Proxy pattern?

Design Patterns · concept · levels mid

In one line

A Proxy is a surrogate that implements the same interface as a real object and controls access to it (lazy loading, security, remote calls, caching, logging); Spring's @Transactional, @Cacheable and @Async all work through JDK dynamic or CGLIB proxies.

Detailed explanation

The client thinks it is talking to the real object, but it holds a proxy that can act before and after delegating, or decide not to delegate at all.

Common kinds:

  • Virtual proxy: delays creating or loading an expensive object until it is actually used. Hibernate returns proxies for lazy @ManyToOne associations and getReference(); the database is queried only when a property is accessed.
  • Protection proxy: checks permissions before forwarding, like Spring Security's method security with @PreAuthorize.
  • Remote proxy: a local object representing something in another process: RMI stubs, gRPC stubs, Spring Cloud OpenFeign clients.
  • Caching / logging / metrics proxies: add cross-cutting behaviour, like @Cacheable or Micrometer @Timed.

How Spring does it: during startup, bean post-processors detect annotations or aspects and replace your bean with a proxy. If the bean implements an interface and proxying is interface-based, a JDK dynamic proxy (java.lang.reflect.Proxy) is created; otherwise CGLIB generates a subclass (Spring Boot defaults to CGLIB/class-based proxies). The proxy's interceptor chain starts a transaction, calls your method, then commits or rolls back.

Consequences you must know:

  • Self-invocation bypasses the proxy: calling this.otherTransactionalMethod() inside the same bean goes straight to the target, so no new transaction, cache or async behaviour.
  • CGLIB cannot proxy final classes or methods, and proxied methods should be public (Spring 6 also supports protected/package-visible for class-based proxies, but public is the safe rule).
  • Hibernate proxies outside an open session cause LazyInitializationException.

Proxy versus Decorator: both wrap with the same interface; a proxy's intent is controlling access and often manages the subject's lifecycle, while a decorator adds features and is stacked by the client.

How it works

  1. Client holds a reference typed as the interface (or class).
  2. The reference actually points to a proxy.
  3. The proxy runs pre-logic (start tx, check auth, check cache).
  4. It delegates to the real object (or not).
  5. It runs post-logic (commit/rollback, store in cache, log).

Example

// Hand-written JDK dynamic proxy for timing
@SuppressWarnings("unchecked")
static <T> T timed(T target, Class<T> iface) {
    return (T) Proxy.newProxyInstance(iface.getClassLoader(), new Class<?>[]{iface},
        (proxy, method, args) -> {
            long t = System.nanoTime();
            try { return method.invoke(target, args); }
            finally { System.out.printf("%s took %d µs%n", method.getName(), (System.nanoTime() - t) / 1000); }
        });
}

@Service
class OrderService {
    @Transactional public void place(Order o) { ... }
    public void placeAll(List<Order> os) { os.forEach(this::place); } // self-invocation: no proxy, no tx per order
}

Common mistakes

  • Expecting annotations to work on self-invoked, private or final methods.
  • Comparing proxy classes with getClass() (Hibernate proxies are subclasses).
  • Accessing lazy proxies after the transaction closes.
  • Calling a decorator a proxy without explaining intent.

How to answer in the interview

"A proxy implements the same interface as the real object and controls access to it, adding behaviour before or after delegating. A virtual proxy delays loading, like Hibernate's lazy entity proxies; a protection proxy checks permissions; a remote proxy represents an object elsewhere, like a Feign client; and caching or logging proxies add cross-cutting concerns. Spring relies on this heavily: @Transactional, @Cacheable and @Async work because the container injects a JDK dynamic proxy or a CGLIB subclass instead of my bean. That's also why calling a @Transactional method from the same class doesn't start a transaction."

Likely follow-up questions

  • Why does self-invocation of @Transactional not work? The call uses this, the raw target, so it never passes through the proxy's interceptor.
  • JDK proxy vs CGLIB? JDK proxies need interfaces; CGLIB subclasses the class and cannot handle final classes or methods.
  • How do you fix self-invocation? Move the method to another bean, inject the bean into itself lazily, or use AspectJ weaving.
