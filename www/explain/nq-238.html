What is the CAP theorem?

Databases & SQL · concept · levels mid

In one line

The CAP theorem says a distributed data store cannot guarantee Consistency, Availability and Partition tolerance all at once; since partitions are unavoidable, the real choice is whether to stay consistent (CP) or available (AP) during a partition, and PACELC adds the latency-versus-consistency trade-off the rest of the time.

Detailed explanation

Eric Brewer stated the conjecture in 2000, and Seth Gilbert and Nancy Lynch proved it in 2002. The definitions are strict:

  • Consistency: linearizability, every read returns the most recent write, as if there were one copy.
  • Availability: every request to a non-failing node gets a non-error response.
  • Partition tolerance: the system keeps working when the network loses or delays messages between nodes.

The popular "pick two of three" is misleading. In any system spread over a network, partitions (switch failures, cloud zone issues, long GC pauses that look like partitions) will happen, so P is mandatory. When they do, a node that cannot reach its peers must either refuse or delay requests to avoid inconsistency (CP) or answer with local, possibly stale data and reconcile later (AP).

CP examples: ZooKeeper, etcd and Consul (Raft/ZAB consensus; the minority side stops serving writes), HBase, and MongoDB with majority write/read concerns (a minority primary steps down). AP examples: Cassandra and Riak, and DynamoDB with eventually consistent reads; they accept writes on both sides and resolve conflicts with last-write-wins, vector clocks or CRDTs. Many products are tunable, so the label depends on configuration.

CAP ignores the normal case, so PACELC (Daniel Abadi) says: if Partitioned, choose A or C; Else choose Latency or Consistency. Waiting for a quorum or synchronous replica adds latency even when nothing is broken.

How it works

  1. Data is replicated on several nodes.
  2. A partition splits nodes into groups.
  3. CP: only the side with a quorum or the leader continues; the other returns errors or times out.
  4. AP: all sides continue; divergent versions are merged once the network heals.
  5. Without partitions, the system still balances latency against consistency.

Example

3-node cluster, network splits {A,B} | {C}

CP (etcd):      {A,B} has quorum -> serves reads/writes
                {C}             -> rejects writes (unavailable)

AP (Cassandra, CL=ONE):
                both sides accept writes for key k
                after healing -> last-write-wins by timestamp, repair syncs replicas

Common mistakes

  • Saying a distributed system can choose CA.
  • Confusing CAP consistency with ACID consistency.
  • Treating CAP as describing normal operation instead of failure behaviour.
  • Labelling products permanently when consistency is tunable per request.

How to answer in the interview

"CAP, from Eric Brewer, says a distributed store can't simultaneously guarantee consistency, meaning every read sees the latest write, availability, meaning every non-failing node responds, and partition tolerance, meaning it keeps working when the network splits. Partitions will happen, so the real decision is what to give up during one: a CP system like ZooKeeper, etcd or HBase refuses some requests to stay consistent, while an AP system like Cassandra or DynamoDB with eventual reads keeps answering and reconciles later. PACELC extends it: even without partitions you trade latency for consistency. I choose per use case, consistency for money, availability for things like feeds."

Likely follow-up questions

  • Where is a single-primary relational database? Effectively CP for writes: if the primary is unreachable, writes fail; async replica reads may be stale.
  • What is PACELC? If partition, availability vs consistency; else latency vs consistency.
  • How do AP systems converge? Read repair, anti-entropy repair, last-write-wins or CRDTs.
