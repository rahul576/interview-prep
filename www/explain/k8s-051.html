A node running pod-0 of a PostgreSQL StatefulSet goes NotReady. Kubernetes does not start pod-0 elsewhere. Why, and what do you do?

Kubernetes · scenario · levels senior, lead

In one line

A StatefulSet guarantees at most one pod per identity; when the node is unreachable, Kubernetes cannot know whether pod-0 is still running and writing, so it will not create a second one (avoiding split-brain) until you confirm the node is dead and force delete the pod or apply the out-of-service taint.

Detailed explanation

A Deployment treats pods as interchangeable, so a replacement can start while the old one is still in doubt. A StatefulSet promises stable identity: postgres-0 has a fixed name, DNS entry and PVC. The controller only creates a new postgres-0 once the old pod object is fully deleted, and a pod on an unreachable node is only fully deleted when its kubelet confirms the containers stopped.

When the node goes NotReady, the control plane sees silence. It cannot tell a powered-off node from a network partition where Postgres is still running and accepting writes. If it started postgres-0 elsewhere and attached the same volume (or a different one), two primaries could diverge or corrupt data. So after the eviction timeout the pod is marked for deletion and shows Terminating or Unknown, and it stays there. A ReadWriteOnce volume also remains attached to the old node.

A human or automation must fence the node: confirm in the cloud console or IPMI that it is powered off, or shut it down. Then either force delete the pod, or apply the taint node.kubernetes.io/out-of-service=nodeshutdown:NoExecute (non-graceful node shutdown, GA since 1.28). The taint makes Kubernetes force-delete pods on that node and force-detach volumes, so the StatefulSet can recreate pod-0 on a healthy node and reattach the PVC.

How it works

  1. Node stops reporting; pod-0 becomes Terminating/Unknown after the toleration period.
  2. StatefulSet controller waits; volume stays attached to the dead node.
  3. Operator confirms the node is truly off (fencing).
  4. Apply the out-of-service taint, or force delete the pod.
  5. Volume detaches; pod-0 is recreated on another node with the same PVC.
  6. Remove the taint once the node is recovered or deleted.

Example

kubectl get pod postgres-0 -o wide        # Terminating on node-7
aws ec2 describe-instances --instance-ids i-0abc --query 'Reservations[].Instances[].State.Name'
# "stopped" -> safe to proceed
kubectl taint nodes node-7 node.kubernetes.io/out-of-service=nodeshutdown:NoExecute
kubectl get pod postgres-0 -w             # recreated on node-3

Common mistakes

  • Force deleting before confirming the node is off.
  • Assuming Kubernetes will "just fail over" a database like a Deployment.
  • Forgetting the volume is still attached, so the new pod hangs in ContainerCreating.
  • Leaving the out-of-service taint on after recovery.

How to answer in the interview

"A StatefulSet guarantees at most one pod per identity, so there must never be two pod-0s writing the same data. When the node goes NotReady, Kubernetes can't tell if it's dead or partitioned with Postgres still running. Starting another pod-0 could cause split-brain, so it waits with the pod stuck Terminating. I'd confirm the node is really down in the cloud console, then apply the out-of-service taint or force delete the pod, which lets the volume detach and pod-0 start elsewhere. For real HA I'd use a database operator with replicas rather than rely on one pod moving."

Likely follow-up questions

  • How does CloudNativePG differ? It runs replicas and promotes a standby on primary failure, fencing the old primary, rather than moving one pod.
  • Why not just use a Deployment? No stable identity or per-pod volumes, and two pods could share data.
  • What is fencing? Guaranteeing the old instance cannot write, for example by powering it off.
