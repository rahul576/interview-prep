What are Spring Boot starter dependencies?

Spring Boot · concept · levels entry

In one line

A starter is a curated dependency descriptor for one capability (web, data-jpa, security, actuator, test) whose versions are managed by the Spring Boot BOM/parent, and adding it puts the classes on the classpath that trigger the matching auto-configuration.

Detailed explanation

Before Boot, adding a capability such as a REST API meant choosing Spring MVC, a JSON library, a validator and a servlet container, and finding versions that worked together. A starter packages that decision. It contains almost no code; it is a POM that depends on a tested set of libraries.

Common examples: spring-boot-starter-web brings Spring MVC, Jackson and embedded Tomcat (validation is now a separate spring-boot-starter-validation); spring-boot-starter-data-jpa brings Spring Data JPA, Hibernate and HikariCP; spring-boot-starter-security, spring-boot-starter-actuator, spring-boot-starter-webflux (Reactor Netty) and spring-boot-starter-test, which bundles JUnit Jupiter, Mockito, AssertJ, Hamcrest, JSONassert and Spring Test.

You do not write versions for these dependencies. The spring-boot-starter-parent or the imported spring-boot-dependencies BOM pins hundreds of library versions that the Boot team has tested together, which avoids classpath conflicts. You can still override a single version through a property such as <jackson-bom.version> when you need a security fix.

Starters and auto-configuration work as a pair: the starter puts classes on the classpath, and @ConditionalOnClass in the auto-configuration notices them and creates beans. Official starters are named spring-boot-starter-*; third-party ones should follow the pattern acme-spring-boot-starter.

How it works

  1. Declare the Boot parent or import the BOM.
  2. Add starters without versions.
  3. Maven or Gradle resolves the curated transitive dependencies.
  4. At startup, auto-configuration detects the classes and configures beans.
  5. Exclude or swap transitive pieces (for example the server) if needed.

Example

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>
  <exclusions>
    <exclusion>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-tomcat</artifactId>
    </exclusion>
  </exclusions>
</dependency>
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-jetty</artifactId>
</dependency>
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-test</artifactId>
  <scope>test</scope>
</dependency>

Common mistakes

  • Hard-coding versions for libraries already managed by the BOM.
  • Adding starters "just in case", which triggers unwanted auto-configuration (for example a DataSource that fails to start).
  • Naming a custom starter spring-boot-starter-acme, a namespace reserved for official ones.
  • Forgetting that validation is no longer inside the web starter.

How to answer in the interview

"A starter is a dependency that bundles everything needed for one capability, with versions tested together. starter-web gives Spring MVC, Jackson and embedded Tomcat; starter-data-jpa gives Spring Data JPA, Hibernate and HikariCP; starter-test gives JUnit 5, Mockito and AssertJ. I don't specify versions because the Boot parent or BOM manages them, which avoids conflicts. Adding a starter also puts classes on the classpath that trigger the matching auto-configuration, so the beans appear automatically."

Likely follow-up questions

  • Replace Tomcat with Jetty? Exclude spring-boot-starter-tomcat and add spring-boot-starter-jetty.
  • Use the BOM without the parent? Import spring-boot-dependencies in dependencyManagement with scope import.
  • What goes into a custom starter? An autoconfigure module plus a starter POM that depends on it and the libraries.
