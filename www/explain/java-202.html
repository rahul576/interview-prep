What is autoboxing and unboxing, and what pitfalls does it cause?

Core Java & OOP · concept · levels entry

In one line

Autoboxing converts a primitive like int into its wrapper Integer automatically, unboxing does the reverse; the pitfalls are NullPointerException on unboxing null, == comparing references, and allocation cost in loops and collections.

Detailed explanation

Since Java 5, the compiler inserts conversions for you: Integer x = 5; becomes Integer.valueOf(5) and int y = x; becomes x.intValue(). This lets primitives work with generics and collections, which only hold objects.

The convenience hides three classic problems.

Null unboxing. A wrapper can be null; a primitive cannot. int count = map.get("missing"); compiles but throws NullPointerException at runtime. Ternaries are a sneaky source: Integer r = flag ? obj.getCount() : 0; unboxes getCount() because the other branch is a primitive.

Reference comparison. == on two Integer objects compares references. Integer.valueOf caches values from -128 to 127 (the upper bound is configurable with -XX:AutoBoxCacheMax), so Integer a = 127, b = 127; a == b is true, but with 128 it is usually false. Always use equals or compare unboxed values.

Performance. Each boxing outside the cache can allocate an object. A List<Integer> of a million numbers holds a million objects plus references, several times the memory of an int[]. Summing with a Long accumulator in a loop allocates on every iteration. Use primitive types, primitive arrays, IntStream/LongStream, or primitive-specialised collections in hot paths.

There is also overload confusion: list.remove(1) on a List<Integer> removes the element at index 1, not the value 1; use list.remove(Integer.valueOf(1)).

How it works

  1. Compiler sees a primitive where an object is required and inserts Wrapper.valueOf(...).
  2. valueOf returns a cached instance for small values, otherwise a new object.
  3. Where a primitive is needed, the compiler inserts xxxValue().
  4. If the reference is null, the xxxValue() call throws NPE.

Example

Map<String, Integer> stock = new HashMap<>();
int qty = stock.get("SKU-1");          // NPE: unboxing null
int safe = stock.getOrDefault("SKU-1", 0);

Integer a = 1000, b = 1000;
System.out.println(a == b);            // false (different objects)
System.out.println(a.equals(b));       // true

Long sum = 0L;                         // boxes on every +=
for (long i = 0; i < 1_000_000; i++) sum += i;   // use long instead

Common mistakes

  • Comparing wrappers with == and relying on the cache.
  • Using wrapper types for counters and accumulators.
  • Forgetting that JSON or DB values mapped to Integer can be null.
  • Mixed-type ternaries that unbox unexpectedly.

How to answer in the interview

"Autoboxing is the compiler converting a primitive to its wrapper, like int to Integer via Integer.valueOf, and unboxing is the reverse through intValue. The main pitfalls: unboxing a null wrapper throws NullPointerException, for example a missing map value used in arithmetic; == on wrappers compares references and only seems to work for -128 to 127 because of the Integer cache; and boxing in tight loops or large collections creates lots of objects and GC pressure. So I use equals for wrappers, getOrDefault for maps, and primitives or primitive streams in hot code."

Likely follow-up questions

  • What does Integer.valueOf do differently from new Integer? It returns cached instances for small values; the constructor always allocates and is deprecated for removal.
  • Which wrappers cache values? Byte, Short, Integer, Long and Character (0-127), and Boolean.
  • How do you avoid boxing in streams? Use mapToInt, IntStream and sum().
