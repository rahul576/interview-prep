Design a RAG-based assistant that answers employee questions from 10 million internal documents.

AI & ML System Design · design · levels mid, senior, lead

In one line

An enterprise RAG assistant has an ingestion pipeline (connect, parse, chunk, embed, index with metadata and ACLs) and a query pipeline (hybrid retrieval, re-ranking, permission filtering, grounded generation with citations), plus evaluation and incremental re-indexing.

Detailed explanation

Ingestion: connectors for SharePoint, Confluence, Google Drive, file shares and ticket systems. Parsing is underrated: PDFs with tables, slides, scanned documents (OCR) need proper extraction or answers will be wrong. Chunking splits text into 300–800 token pieces with overlap, ideally by structure (headings, sections), keeping metadata: title, URL, section path, updated date and access control lists. Each chunk is embedded and indexed in a vector store that also supports keyword search (Azure AI Search, OpenSearch, Elasticsearch, pgvector + full-text, Vespa). At 10M documents, expect 100M+ chunks: plan sharding, quantised vectors and incremental updates via change events.

Query: optionally rewrite the question (conversation context, acronyms). Hybrid retrieval: vector similarity for meaning + BM25 for exact terms (error codes, product names), combined with reciprocal rank fusion. A cross-encoder reranker reorders the top ~50 to the best 5–10. Security trimming: filter by the user's groups at query time, so the LLM never sees documents the user can't access. The LLM is instructed to answer only from the provided context and to cite sources; if the context doesn't answer, it says so.

Quality: a golden evaluation set measures retrieval recall@k and answer faithfulness on every change; user feedback and traces feed improvements.

How it works

  1. Source change → event → parse → chunk → embed → upsert (delete stale chunks).
  2. Question → rewrite → hybrid search with ACL filter → rerank → prompt with top chunks.
  3. LLM answer with citations → UI shows sources.
  4. Log trace; collect feedback; offline eval nightly.

Common mistakes

  • Pure vector search (misses exact identifiers).
  • Applying permissions after generation (data leak).
  • Bad PDF parsing and naive fixed-size chunking.
  • No evaluation set, so changes are judged by vibes.

How to answer in the interview

"Ingestion connects to sources, parses documents properly, chunks them by structure with metadata and ACLs, embeds and indexes them, and re-indexes incrementally on change events. At query time I use hybrid vector-plus-keyword retrieval, filtered by the user's permissions, then a reranker selects the best chunks. The model answers only from that context with citations. An evaluation set tracks retrieval recall and faithfulness on every change."

Likely follow-up questions

  • Answers spread across many docs? Multi-query retrieval, larger context, map-reduce summarisation, or agentic retrieval.
  • Stale content? Prefer recent docs via metadata boosts; delete removed docs promptly.
  • Cost control? Cache embeddings, smaller models for rewriting/reranking.
