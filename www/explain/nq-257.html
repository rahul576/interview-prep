How would you join the Customer and Orders tables?

Databases & SQL · scenario · levels entry

In one line

Join on the foreign key: FROM customer c JOIN orders o ON o.customer_id = c.customer_id, using aliases for readability, an INNER JOIN when you only need customers with orders and a LEFT JOIN when every customer must appear, with an index on orders.customer_id.

Detailed explanation

The relationship is one-to-many: one customer can have many orders, and each order belongs to exactly one customer. That relationship is stored as orders.customer_id, a foreign key referencing customer.customer_id, the primary key. The join condition simply follows that relationship.

Choosing the join type depends on the question being asked:

  • INNER JOIN: only customers who have at least one order, and only orders with a valid customer. Typical for revenue reports and order listings.
  • LEFT JOIN from customer: every customer appears; customers without orders show NULL order columns. Needed for "orders per customer including zero" or "customers who never ordered" (WHERE o.order_id IS NULL).
  • RIGHT or FULL joins are rarely needed here; with a proper foreign key, orders without customers should not exist.

Readability: short aliases (c, o) and explicit JOIN ... ON syntax are clearer than the old comma join with conditions in WHERE, and they make it harder to forget a condition.

Result shape: the join produces one row per order, so a customer with five orders appears five times. Aggregate (COUNT, SUM) with GROUP BY if you want one row per customer.

Performance: the primary key is indexed automatically; add an index on orders.customer_id (PostgreSQL does not create it for foreign keys automatically; InnoDB does). That lets the database look up a customer's orders quickly with a nested loop, or the optimizer may choose a hash join for big reports.

How it works

  1. The optimizer chooses which table to read first.
  2. For each row, it finds matching rows in the other table, using the index or a hash table.
  3. Matching pairs produce output rows.
  4. For LEFT JOIN, customers without matches are output with NULLs.
  5. Filters, grouping and ordering follow.

Example

-- Orders with customer details
SELECT c.customer_id, c.name, o.order_id, o.order_date, o.amount
FROM customer c
JOIN orders o ON o.customer_id = c.customer_id;

-- Every customer with an order count, including zero
SELECT c.customer_id, c.name, COUNT(o.order_id) AS order_count
FROM customer c
LEFT JOIN orders o ON o.customer_id = c.customer_id
GROUP BY c.customer_id, c.name;

CREATE INDEX idx_orders_customer_id ON orders (customer_id);

Common mistakes

  • Forgetting the ON condition, creating a cartesian product (every customer paired with every order).
  • Joining on name instead of the key.
  • Using COUNT(*) with a LEFT JOIN, which counts customers with no orders as 1.
  • Putting order filters in WHERE after a LEFT JOIN, turning it into an inner join.

How to answer in the interview

"Orders has a foreign key, customer id, that references the primary key of Customer, a one-to-many relationship. So I'd write FROM customer c JOIN orders o ON o.customer_id equals c.customer_id, with aliases for readability. An inner join returns only customers who have orders, which is what a revenue report usually needs; if I need every customer, including those without orders, I'd use a LEFT JOIN from customer, so order columns are NULL for them. I'd make sure orders.customer_id is indexed so the join is efficient."

Likely follow-up questions

  • What if you forget the ON condition? You get a cartesian product: customers times orders rows.
  • How to list customers who never ordered? LEFT JOIN and WHERE o.order_id IS NULL, or NOT EXISTS.
  • Why one row per order rather than per customer? A join multiplies rows by matches; aggregate to collapse them.
