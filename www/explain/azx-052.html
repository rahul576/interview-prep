How do you secure Azure Pipelines against misuse, such as a malicious pull request or a compromised pipeline?

Azure DevOps & Pipelines · concept · levels mid, senior, lead

In one line

Treat pipelines as production infrastructure: require explicit pipeline permissions on protected resources, limit job authorization scope and token permissions, give fork PRs no secrets and require approval to run, enforce branch control and required templates on production resources, restrict inline scripts, pin tasks, audit, and run untrusted builds on isolated agents.

Detailed explanation

A pipeline that can deploy to production effectively is production access. Attack paths include a malicious PR that modifies the YAML to print secrets, a compromised developer account editing a pipeline, a malicious marketplace task or template, and a persistent foothold on a shared agent.

Protected resources (service connections, agent pools, variable groups, secure files, environments, repositories) should not be open to all pipelines. Each must be explicitly authorised per pipeline, so a new or rogue pipeline can't silently use the production service connection.

Job access tokens: the System.AccessToken identity should be scoped with "Limit job authorization scope to current project" (and to referenced repositories), and the build service accounts should have only needed permissions. Settings like "Protect access to repositories in YAML pipelines" reduce lateral movement.

Pull requests from forks: never make secrets available to fork builds, and require a maintainer comment (/azp run) or approval before running builds from external contributors. Remember a PR can change the pipeline YAML itself, so PR builds must never have production credentials.

Production gates: on production service connections and environments, add branch control (only main or release/*, with branch protection required) and required template checks, so only pipelines extending the approved, reviewed template can use them. That template can block inline scripts in deployment stages.

Supply chain and audit: pin task major versions and template refs, restrict which marketplace extensions are installed, disable "settable at queue time" variables that could inject commands, and stream audit logs to the SIEM. Run untrusted work on stateless, isolated agents with no network path to production; keep production deployment agents separate.

How it works

  1. Turn off "open access" on all protected resources; authorise per pipeline.
  2. Limit job authorization scope and repo access.
  3. Configure fork PR settings: no secrets, require approval.
  4. Branch control and required templates on prod service connections.
  5. Separate agent pools by trust level.
  6. Audit streaming and periodic permission reviews.

Example

Service connection sc-payments-prod
  Pipeline permissions: payments-deploy only
  Checks: Branch control (refs/heads/main, require branch protection)
          Required template: secure-deploy.yml@templates (ref refs/tags/v4)
          Approval: payments-release-managers
Project settings: Limit job authorization scope = On; Protect repos in YAML = On
GitHub fork builds: secrets = Off; require team member comment before build

Common mistakes

  • "Grant access permission to all pipelines" on production service connections.
  • Same self-hosted agents for PR builds and production deploys.
  • Assuming code review of app code covers pipeline YAML changes.
  • Allowing queue-time variables to override script inputs.

How to answer in the interview

"A pipeline with production credentials is production access, so I lock it down. Service connections, agent pools, variable groups and environments require explicit permission per pipeline. Job authorization scope is limited to the current project. Fork PRs never get secrets and need a maintainer's approval to run. Production service connections have branch control so only main can deploy, and a required template check so only pipelines built on the approved template can use them, which can also ban inline scripts. Tasks and templates are pinned, audit logs go to the SIEM, and untrusted builds run on isolated agents with no path to production."

Likely follow-up questions

  • How could a developer exfiltrate a secret? Edit YAML to send it encoded to an external URL; required templates and branch control stop that for prod.
  • Why separate agent pools? A compromised PR build could persist on a shared agent.
  • Who reviews pipeline YAML? CODEOWNERS or required reviewers on pipeline folders.
