How should you implement equals and hashCode for JPA entities?

Spring Data & JPA · concept · levels mid, senior

In one line

Entity equals/hashCode must stay stable across entity states: a generated id is null before persist, so use an immutable business key, or compare by id with a constant hashCode, or assign a UUID at construction, and avoid Lombok @Data which touches lazy associations.

Detailed explanation

Java collections such as HashSet and HashMap assume an object's hashCode does not change while it is inside them. Entities break that assumption easily.

Default Object.equals (identity) works within one persistence context, because Hibernate guarantees one instance per row there. But comparing a detached entity from one transaction with a managed one from another gives false, and sets mixing them get duplicates.

Id-based with id in hashCode is the trap: a new entity has id == null; you add it to a Set (for example order.getLines().add(line) before saving), then persist assigns the id, the hashCode changes and the set can no longer find the element; contains and remove fail.

Working options:

  1. Natural/business key: an immutable, unique attribute that exists before persist, such as ISBN, email, or SKU. Mark it @NaturalId in Hibernate. Clean, but many entities don't have one, and it must truly never change.
  2. Id-based equals with constant hashCode: equals returns true only if both ids are non-null and equal (with a class check that handles Hibernate proxies), and hashCode returns a constant such as getClass().hashCode(). All instances of a type share a bucket, which is acceptable for the small collections typical in entity graphs.
  3. Application-assigned UUID (ideally time-ordered UUIDv7 for index locality), set in the constructor or field initialiser, so the identifier exists from the start and both equals and hashCode can use it.

Avoid Lombok @Data and @EqualsAndHashCode on entities. Generated methods include all fields, including lazy collections and associations, so calling equals, hashCode or toString can trigger extra queries, LazyInitializationException on detached entities, or StackOverflowError with bidirectional relations. Mutable fields in hashCode also break sets. Use @Getter/@Setter and write equals/hashCode by hand, excluding associations from toString.

Also use instanceof or Hibernate.getClass() rather than getClass() ==, because lazy proxies are subclasses.

How it works

  1. Decide the identity rule: natural key, generated id, or assigned UUID.
  2. Ensure the hashCode never changes over the entity's lifetime.
  3. Handle proxies in the type check.
  4. Exclude associations from equals, hashCode and toString.
  5. Test equality across transient, managed and detached states.

Example

@Entity
public class OrderLine {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)
    private Long id;

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof OrderLine other)) return false;
        return id != null && id.equals(other.getId());   // getter works on proxies
    }

    @Override
    public int hashCode() {
        return getClass().hashCode();                     // constant across states
    }
}

@Entity
public class Book {
    @Id @GeneratedValue Long id;
    @NaturalId @Column(nullable = false, unique = true, updatable = false)
    private String isbn;

    @Override public boolean equals(Object o) { return o instanceof Book b && isbn.equals(b.isbn); }
    @Override public int hashCode() { return isbn.hashCode(); }
}

Common mistakes

  • Using the generated id in hashCode.
  • Lombok @Data on entities.
  • Using mutable fields such as name or status in equals.
  • getClass() != o.getClass() failing with Hibernate proxies.

How to answer in the interview

"The difficulty is that a generated id is null before persist, so an id-based hashCode changes when the entity is saved and breaks any HashSet that already contains it. I either use an immutable business key such as an ISBN, or compare by id in equals while returning a constant hashCode, which stays stable across states, or assign a UUID in the constructor. I avoid Lombok @Data on entities because generated equals and toString touch lazy collections and relations, causing extra queries, LazyInitializationException or infinite recursion."

Likely follow-up questions

  • Why can all-fields equals cause LazyInitializationException? It touches lazy associations on detached entities.
  • Is a constant hashCode slow? Only for huge hashed collections of one entity type, which are rare.
  • Why handle proxies? Lazy proxies are subclasses with uninitialised fields; use getters and instanceof.
