A Service returns connection refused and kubectl get endpoints shows no endpoints. What do you check?

Kubernetes · scenario · levels entry, mid, senior

In one line

No endpoints means the Service selects no ready pods: check the selector against pod labels, readiness, and the namespace; if endpoints exist but connections still fail, check targetPort and that the app listens on 0.0.0.0; port-forward to a pod separates app from wiring.

Detailed explanation

A Service is a stable virtual IP plus a label selector. The EndpointSlice controller continuously lists pods that match the selector in the same namespace and are Ready, and publishes their IPs and ports. kube-proxy (or the eBPF dataplane) programs rules from those. With no ready endpoints there is nowhere to send traffic; depending on the dataplane the client sees connection refused or a timeout.

The most common cause is a selector/label mismatch: a typo (app: chekout), a label changed in a new chart version, or the Service selecting on an extra label like version: v2 that only some pods have. Remember the selector must match all its labels. Next is readiness: pods failing the readiness probe are listed as not ready and excluded, which is by design. Third, the pods are in another namespace; selectors never cross namespaces.

If endpoints do exist but connections fail, the wiring is wrong further along: targetPort does not match the container's listening port (or a named port that does not exist), or the app listens on 127.0.0.1 so it accepts connections only from inside the pod. A NetworkPolicy blocking the client is another option, though that usually gives timeouts. kubectl port-forward pod/... goes straight to the pod, bypassing the Service, so if it works the app is fine and the Service is the problem.

How it works

  1. kubectl get svc <svc> -o wide to see the selector.
  2. kubectl get pods -l <selector> --show-labels in the same namespace.
  3. kubectl get endpointslices -l kubernetes.io/service-name=<svc> for ready status.
  4. Describe non-ready pods to see probe failures.
  5. Compare targetPort with the container port and bind address.
  6. Test with port-forward and a curl from a debug pod.

Example

kubectl -n shop get svc checkout -o jsonpath='{.spec.selector}{"\n"}'
#  {"app":"checkout","tier":"backend"}
kubectl -n shop get pods -l app=checkout --show-labels
#  checkout-7d..  app=checkout,tier=api      <- tier mismatch
kubectl -n shop get endpointslices -l kubernetes.io/service-name=checkout
kubectl -n shop port-forward pod/checkout-7d9f 8080:8080 &
curl -s localhost:8080/healthz

Common mistakes

  • Editing labels on pods instead of the Deployment template.
  • Forgetting that unready pods are deliberately removed.
  • Using port where targetPort was meant.
  • Apps binding to localhost inside the container.

How to answer in the interview

"No endpoints means the Service has no ready pods selected. First I compare the Service selector with the pod labels, because a typo or a label changed in a new release is the most common cause, and every selector label must match. Then readiness: pods failing their readiness probe are excluded. I confirm the pods are in the same namespace. If endpoints exist but connections still fail, I check that targetPort matches the port the app listens on and that it binds to 0.0.0.0. Port-forwarding directly to a pod tells me whether it's the app or the Service wiring."

Likely follow-up questions

  • Works from one namespace but not another? A NetworkPolicy, or the client uses the short name which resolves in its own namespace.
  • Endpoints vs EndpointSlices? EndpointSlices are the scalable replacement; the old Endpoints API is deprecated.
  • What is a headless Service? clusterIP: None; DNS returns pod IPs directly.
