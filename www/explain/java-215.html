What are the pitfalls of Arrays.asList and List.subList?

Collections · concept · levels entry, mid

In one line

Arrays.asList returns a fixed-size list backed by the array (add/remove throw UnsupportedOperationException, and a primitive array becomes one element), and subList is a view of its parent that breaks after structural changes to the parent; copy with new ArrayList or List.copyOf when you need independence.

Detailed explanation

Arrays.asList(array) does not copy anything. It returns a private Arrays.ArrayList that wraps the original array. set(i, x) writes straight into the array and changes to the array show in the list, but the size is fixed, so add, remove and clear throw UnsupportedOperationException. That surprises people who use it as a quick way to "create a list" and later try to add to it.

Generics cause a second trap. Arrays.asList takes T..., and generics cannot be primitives, so passing an int[] makes T equal to int[] and you get a List<int[]> with one element, the whole array. Use Arrays.stream(ints).boxed().toList() or an Integer[] instead.

list.subList(from, to) also returns a view, not a copy. Changes through the sublist (including clear(), which is a neat way to delete a range) affect the parent. But if the parent is structurally modified afterwards (add or remove not done through the sublist), any later use of the sublist throws ConcurrentModificationException. And because the view references the parent, keeping a small sublist of a huge list alive keeps the whole list in memory, a subtle leak.

The safe pattern is to copy whenever the result must live independently: new ArrayList<>(Arrays.asList(...)), List.of(...), List.copyOf(list.subList(0, 10)).

How it works

  1. Arrays.asList(arr) stores a reference to arr; size is arr.length.
  2. set writes to arr[i]; add/remove use the AbstractList default, which throws.
  3. subList stores parent reference, offset, size and the parent's modCount.
  4. Each sublist operation checks that the parent's modCount has not changed.

Example

String[] arr = {"a", "b", "c"};
List<String> fixed = Arrays.asList(arr);
fixed.set(0, "z");           // arr[0] is now "z"
fixed.add("d");              // UnsupportedOperationException

int[] nums = {1, 2, 3};
Arrays.asList(nums).size();  // 1 !

List<Integer> big = new ArrayList<>(List.of(1, 2, 3, 4, 5));
List<Integer> head = big.subList(0, 2);
big.add(6);
head.size();                 // ConcurrentModificationException

big.subList(1, 3).clear();   // idiomatic range delete
List<Integer> safe = List.copyOf(big.subList(0, 2));

Common mistakes

  • Returning Arrays.asList from a method whose callers will add elements.
  • Passing a primitive array and getting a single-element list.
  • Storing a subList long-term, causing CME or a memory leak.
  • Assuming subList is a copy.

How to answer in the interview

"Arrays.asList gives a fixed-size list backed by the array: set writes through to the array, but add and remove throw UnsupportedOperationException. And if you pass an int array you get a list with one element, the array itself. subList is a view of the parent, not a copy, so changes are shared, and if the parent is structurally changed afterwards the sublist throws ConcurrentModificationException; it also pins the whole parent in memory. When I need an independent list I copy it with new ArrayList or List.copyOf."

Likely follow-up questions

  • How do you remove while iterating safely? Iterator.remove() or removeIf.
  • Difference between Arrays.asList and List.of? List.of is fully immutable, rejects nulls and is not backed by an array.
  • How do you delete a range from an ArrayList? list.subList(from, to).clear().
