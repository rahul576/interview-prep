What is Docker used for?

Docker · concept · levels entry

In one line

Docker packages an application and its dependencies into an image and runs it as an isolated container that shares the host kernel. That gives consistent environments from laptop to production, fast, lightweight startup compared with VMs, and a standard unit for CI/CD and orchestration.

Detailed explanation

Before containers, deploying meant installing the right JDK, libraries and OS packages on each server and hoping they matched the developer's machine. Docker solves this by making the image the deployable artefact. An image is a read-only, layered filesystem containing the app, runtime, libraries and default configuration, built from a Dockerfile and stored in a registry (Docker Hub, ECR, ACR, GHCR).

A container is a running instance of an image. It is just a normal Linux process with isolation provided by the kernel:

  • Namespaces give it its own view of processes (PID), network, mounts, hostname and users.
  • cgroups limit and account for CPU, memory and IO.
  • A writable layer sits on top of the image layers (union filesystem).

Because containers share the host kernel instead of booting a full guest OS like a virtual machine, they start in milliseconds to seconds, use far less memory, and you can run many per host. The trade-off is weaker isolation than a hypervisor, and a Linux container needs a Linux kernel. Docker Desktop on macOS and Windows runs a small Linux VM for this.

Typical uses:

  • running services and their dependencies locally (docker compose up)
  • reproducible CI builds and tests
  • immutable deployments: the same image tag goes to test and production
  • the unit that Kubernetes, ECS or Cloud Run schedule and scale

Modern images follow the OCI standard, so images built by Docker also run on containerd, CRI-O or Podman.

How it works

  1. Write a Dockerfile describing the base image, files and start command.
  2. docker build creates image layers, cached and reused between builds.
  3. docker push uploads the image to a registry.
  4. docker run (or Kubernetes) pulls it and starts a container with namespaces and cgroups.
  5. Configuration comes from environment variables or mounted files. Data lives in volumes, not the container layer.

Example

docker build -t orders-service:1.4.0 .
docker run -d --name orders -p 8080:8080 \
  -e SPRING_PROFILES_ACTIVE=dev --memory=512m orders-service:1.4.0
docker ps
docker logs -f orders
docker exec -it orders sh

Common mistakes

  • Saying containers are "lightweight VMs" without explaining kernel sharing.
  • Storing data inside the container filesystem, where it is lost when the container is removed.
  • Running as root and using huge, unscanned base images.
  • Using the latest tag in production, so deployments are not reproducible.

How to answer in the interview

"Docker packages an application with its runtime, libraries and configuration into an image, and runs it as an isolated container. Containers share the host kernel but get their own processes, filesystem and network through namespaces, with cgroups limiting resources. So they're much lighter and faster to start than VMs. The big win is consistency: the same image runs identically on my laptop, in CI and in production. We use it to run dependencies locally, to make builds reproducible, and as the deployment unit for Kubernetes."

Likely follow-up questions

  • Image versus container? An image is the immutable template. A container is a running instance of it with a writable layer.
  • How do you persist data? Volumes or bind mounts, or external managed databases.
  • What is a multi-stage build? It builds in one stage and copies only the artefact into a small runtime image.
