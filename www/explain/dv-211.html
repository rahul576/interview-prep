What are AWS regions and availability zones, and why do they matter?

Cloud (AWS) · concept · levels entry

In one line

A region is a separate geographic area (such as ap-south-1, Mumbai) containing several availability zones, each one or more isolated data centres with independent power and networking; you spread workloads across AZs for high availability and use multiple regions for disaster recovery, latency or compliance.

Detailed explanation

AWS is built from regions that are deliberately independent of each other: a problem in eu-west-1 should not affect ap-south-1. Most services are regional: an EC2 instance, an RDS database or an S3 bucket lives in one region, and data does not leave it unless you replicate it.

Each region contains multiple availability zones (new regions launch with at least three). An AZ is one or more discrete data centres with separate power, cooling and networking, physically far enough apart that a fire, flood or power failure usually hits only one, yet close enough for low-latency, high-bandwidth links (typically single-digit milliseconds). That makes synchronous replication between AZs practical.

This is why the standard high-availability pattern is multi-AZ: subnets in two or three AZs, an Auto Scaling group spread across them, a load balancer in front, and databases such as RDS Multi-AZ or Aurora replicating across zones. If one AZ fails, the others carry the load.

Choosing a region depends on latency to users, data residency and regulatory rules (for example keeping Indian customer data in India), price (which varies by region), and service availability, since new services and instance types do not launch everywhere at once. Multi-region setups protect against a whole-region outage and serve global users with low latency, but they add cost and data-consistency complexity, so they are driven by RTO/RPO requirements.

How it works

  1. Pick a primary region by latency, compliance, cost and services.
  2. Create subnets in at least two or three AZs.
  3. Run stateless compute in all of them behind a load balancer.
  4. Use Multi-AZ databases and cross-AZ replication.
  5. For DR, replicate backups or data to a second region and plan failover with Route 53.

Example

aws ec2 describe-availability-zones --region ap-south-1 \
  --query "AvailabilityZones[].{Name:ZoneName,Id:ZoneId}" --output table

Note that AZ names like ap-south-1a map to different physical zones in different accounts; the AZ ID (for example aps1-az1) is consistent, which matters when coordinating across accounts.

Common mistakes

  • Running everything in one AZ and calling it "in the cloud, so highly available".
  • Confusing multi-AZ (high availability) with multi-region (disaster recovery).
  • Assuming every service or instance type exists in every region.

How to answer in the interview

"A region is a separate geographic area like Mumbai or Frankfurt, and each has several availability zones. An AZ is one or more physically separate data centres with their own power and networking, connected to the others by fast, low-latency links. Failures usually stay within one zone, so for high availability I run subnets, instances and databases across two or three AZs behind a load balancer. I choose the region by user latency, data residency rules, cost and which services are available, and use a second region only when the business needs disaster recovery against a full region outage."

Likely follow-up questions

  • Which services are global? IAM, Route 53, CloudFront, Organizations and WAF for CloudFront.
  • What is an AZ ID? A stable identifier of the physical zone, unlike account-specific AZ names.
  • What is a Local Zone? An extension of a region into a city for single-digit millisecond latency.
