A server has high load average but low CPU usage. What could cause this and how do you investigate?

Linux · scenario · levels mid, senior

In one line

On Linux the load average counts runnable and uninterruptible (D state) processes, so high load with idle CPU usually means processes are blocked on I/O: slow disks, saturated network storage or a hung NFS mount; confirm with top's wa, iostat, vmstat, iotop and ps state D.

Detailed explanation

Many people read load average as "CPU usage", but on Linux it is the average number of tasks that are either running or waiting for a CPU (R) or in uninterruptible sleep (D). D-state tasks usually wait on disk or network storage I/O and cannot be interrupted, even by SIGKILL. So a load of 20 on an 8-core server with CPUs 90% idle tells you lots of tasks are stuck waiting, not computing.

Investigation follows the I/O path. In top, the wa (iowait) value shows the share of time CPUs were idle while I/O was outstanding. vmstat 1 shows r (runnable) and b (blocked) columns; a high b with low r confirms I/O blocking, and si/so show swapping. iostat -x 1 shows per-device %util, r_await/w_await latency and queue size; a cloud disk at its IOPS or throughput limit shows high await. iotop or pidstat -d 1 identifies which processes do the I/O. ps -eo pid,stat,wchan:30,cmd | awk '$2 ~ /D/' lists D-state processes and the kernel function they wait in, often pointing to NFS (nfs_), a filesystem or a block device.

Typical causes: a hung NFS or network mount after the server became unreachable, a failing disk (check dmesg for I/O errors and SMART), a cloud volume throttled at its provisioned IOPS, heavy swapping due to memory pressure, or an application doing excessive synchronous writes or logging. Fixes: faster or provisioned storage, reducing I/O, more memory for page cache, or repairing or remounting the hung mount.

How it works

  1. Compare load average with core count (uptime, nproc).
  2. Check CPU breakdown: low us/sy, high wa.
  3. vmstat 1: many blocked (b) processes?
  4. iostat -x: which device has high util and await?
  5. ps for D-state processes and their wait channel.
  6. Fix the storage, mount, memory or application cause.

Example

uptime            # load average: 21.4, 19.8, 15.2
nproc             # 8
vmstat 1 5        # r=1 b=18 wa=65
iostat -x 1 3     # nvme1n1 %util 99.8 w_await 180ms
ps -eo pid,stat,wchan:30,cmd | awk '$2 ~ /D/'
dmesg -T | grep -iE "nfs|i/o error|timeout"

Common mistakes

  • Assuming high load means a CPU shortage and adding cores.
  • Trying to kill D-state processes, which does not work.
  • Ignoring cloud volume IOPS limits.
  • Missing swap activity as the source of I/O.

How to answer in the interview

"On Linux the load average counts not only runnable processes but also those in uninterruptible sleep, D state, which usually means waiting for disk or network storage. So high load with idle CPU points to I/O. I check the wa value in top, vmstat for blocked processes and swapping, iostat -x for device utilisation and latency, and iotop for which processes do I/O. ps with the state column shows which processes are stuck in D, often on an NFS mount or a failing disk. The fix may be faster storage, less I/O, more memory for cache, or repairing a hung mount."

Likely follow-up questions

  • How does swapping show up in these tools? Non-zero si/so in vmstat, swap used in free, and high I/O on the swap device.
  • Can you kill a D-state process? Not until the I/O completes or fails; fix the underlying storage.
  • What is PSI? Pressure Stall Information in /proc/pressure shows time stalled on CPU, memory and I/O.
