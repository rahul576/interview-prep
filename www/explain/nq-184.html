How can common utility libraries be shared across microservices while allowing service-specific functionality?

Spring Boot · design · levels senior, lead

In one line

Share cross-cutting code as a small, versioned internal library or custom Spring Boot starter published to an artifact repository, built with conditional, overridable auto-configuration and clear extension points (interfaces, customizer beans, properties), keeping domain logic out and following semantic versioning.

Detailed explanation

Every service needs the same plumbing: structured logging and correlation ids, a standard error response format, security filters and token validation, HTTP client configuration with timeouts and retries, metrics tags, tracing. Copying this into each service leads to drift; a shared library solves it, but done badly it couples services so tightly that they must deploy together, a distributed monolith.

The best shape is a custom starter: an acme-autoconfigure module with @AutoConfiguration classes plus an acme-spring-boot-starter POM, published to Nexus, Artifactory or GitHub Packages. Features switch on and off with properties, and every bean is annotated with @ConditionalOnMissingBean, so a service can replace any default simply by defining its own bean.

Service-specific behaviour comes through extension points: interfaces the service implements (for example a TenantResolver), customizer beans such as Boot's RestClientCustomizer or the library's own ErrorResponseCustomizer, and typed @ConfigurationProperties with sensible defaults and metadata for IDE completion.

Governance matters as much as code. Keep the library small and cross-cutting only; no shared entities or business rules. Use semantic versioning, keep minor releases backward compatible, deprecate before removing, publish release notes, and let each service upgrade at its own pace. Minimise transitive dependencies and align them with the Spring Boot BOM to avoid version clashes. Tools like Renovate or Dependabot help services stay current.

How it works

  1. Identify truly cross-cutting concerns shared by most services.
  2. Implement them in an autoconfigure module with conditions and properties.
  3. Expose extension interfaces and customizers.
  4. Publish a versioned starter to the artifact repository via CI.
  5. Services add the starter, override what they need, and upgrade independently.
  6. Test the library with ApplicationContextRunner and a sample app.

Example

@AutoConfiguration
@EnableConfigurationProperties(AcmeWebProps.class)
public class AcmeWebAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean
    CorrelationIdFilter correlationIdFilter(AcmeWebProps p) {
        return new CorrelationIdFilter(p.getHeaderName());
    }

    @Bean
    @ConditionalOnMissingBean
    ProblemDetailsExceptionHandler errorHandler(ObjectProvider<ErrorResponseCustomizer> customizers) {
        return new ProblemDetailsExceptionHandler(customizers.orderedStream().toList());
    }
}
acme:
  web:
    header-name: X-Correlation-Id

Common mistakes

  • Putting domain models or business logic in the shared library.
  • Breaking changes in minor versions, forcing synchronised upgrades.
  • Heavy transitive dependencies that conflict with services.
  • Beans without @ConditionalOnMissingBean, so services cannot override them.
  • A "common-utils" dumping ground with no ownership.

How to answer in the interview

"I'd build a small, versioned internal library, ideally a custom Spring Boot starter published to Artifactory, only for cross-cutting concerns like logging and correlation ids, error format, security filters, HTTP client setup and metrics. It uses auto-configuration with conditions, so features switch on by property and OnMissingBean lets a service replace any default. For service-specific behaviour I expose interfaces, customizer beans and ConfigurationProperties. I keep domain logic out to avoid a distributed monolith, use semantic versioning with backward-compatible changes, and let each service upgrade on its own schedule."

Likely follow-up questions

  • Risks of a shared library? Coupling, forced upgrades, dependency conflicts and a blast radius for bugs.
  • Library vs sidecar/platform? Sidecars or a service mesh handle some concerns language-independently.
  • How do you roll out a fix everywhere? Patch release plus automated dependency update PRs.
