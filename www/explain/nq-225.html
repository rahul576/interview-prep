What is Eureka, and how does it support service discovery?

Microservices · concept · levels mid

In one line

Eureka is Netflix's service registry, integrated through Spring Cloud Netflix: services register on startup and send heartbeats every 30 seconds, clients cache the registry and load-balance with @LoadBalanced/lb://, and its AP design with self-preservation favours availability over perfectly accurate data.

Detailed explanation

Eureka has two parts. The Eureka server is a Spring Boot application annotated with @EnableEurekaServer. For high availability you run several servers that replicate registrations peer to peer; there is no leader or consensus, which is deliberate.

The Eureka client, included via spring-cloud-starter-netflix-eureka-client, makes each microservice register itself on startup with its spring.application.name, host, port, status and metadata (zone, version). It then renews its lease with a heartbeat every 30 seconds by default. If the server receives no renewal for 90 seconds (the lease expiration), an eviction task removes the instance. On graceful shutdown the client deregisters immediately.

Clients also fetch the registry (delta updates every 30 seconds by default) and cache it locally. Calls go through Spring Cloud LoadBalancer (Ribbon was removed years ago): a RestClient, RestTemplate or WebClient builder marked @LoadBalanced, Spring Cloud Gateway lb://order-service routes, or OpenFeign clients resolve the service name to an instance, round robin by default. Because clients use their cache, calls continue working even if all Eureka servers are briefly down; the trade-off is that new or dead instances are noticed with a delay of up to a minute or two, so callers need retries and circuit breakers.

Eureka is an AP system in CAP terms. Its self-preservation mode protects against network problems: if the server suddenly receives far fewer renewals than expected (below a threshold, 85 percent by default), it assumes the problem is the network, not that most services died, and stops evicting instances. It may serve some stale entries, which is better than wiping out the registry and making every service undiscoverable.

On Kubernetes, Services and DNS usually replace Eureka; it remains useful on VMs and hybrid setups.

How it works

  1. Eureka servers start and replicate with peers.
  2. Service starts, registers name and address.
  3. Heartbeat every 30 s; eviction after 90 s without renewal.
  4. Clients fetch and cache the registry, refreshing every 30 s.
  5. LoadBalancer picks an instance for http://order-service.
  6. Renewals drop sharply → self-preservation stops evictions.

Example

@SpringBootApplication
@EnableEurekaServer
public class RegistryApplication { public static void main(String[] a) { SpringApplication.run(RegistryApplication.class, a); } }
# order-service application.yml
spring:
  application:
    name: order-service
eureka:
  client:
    service-url:
      defaultZone: http://eureka-1:8761/eureka/,http://eureka-2:8761/eureka/
  instance:
    prefer-ip-address: true
@Bean @LoadBalanced
RestClient.Builder lbRestClientBuilder() { return RestClient.builder(); }

// usage: builder.baseUrl("http://payment-service").build() -> resolved via Eureka

Common mistakes

  • Running a single Eureka server in production.
  • Expecting instant removal of dead instances (it can take minutes).
  • Disabling self-preservation in production to "fix" stale entries.
  • Adding Eureka to Kubernetes without need.

How to answer in the interview

"Eureka is a service registry from Netflix, integrated through Spring Cloud Netflix. You run a few Eureka servers, Spring Boot apps with @EnableEurekaServer that replicate with each other. Each microservice with the Eureka client registers on startup with its name, host and port and sends a heartbeat every thirty seconds; instances that stop renewing are evicted after about ninety seconds. Clients cache the registry, so a @LoadBalanced client can call http://order-service and Spring Cloud LoadBalancer picks an instance. Eureka favours availability: in self-preservation mode it stops evicting when renewals drop sharply, accepting stale entries rather than emptying the registry."

Likely follow-up questions

  • What is self-preservation and why does it exist? When renewals drop below a threshold, Eureka assumes a network issue and stops evicting, to avoid deregistering healthy services.
  • What replaced Ribbon? Spring Cloud LoadBalancer.
  • How do callers cope with stale entries? Retries to another instance and circuit breakers.
