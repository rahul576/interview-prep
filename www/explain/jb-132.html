What JVM parameters would you configure for a production application?

JVM & Performance · concept · levels senior, lead

In one line

In production I set heap sizing (-Xms/-Xmx, or MaxRAMPercentage in containers), choose the collector and pause goal, enable unified GC logging, add heap dump on OOM plus ExitOnOutOfMemoryError, consider Metaspace and thread stack limits, a continuous JFR recording, and fix encoding and time zone.

Detailed explanation

Memory. On VMs, set -Xms equal to -Xmx to avoid resizing and get predictable behaviour. In containers, the JVM is container-aware (default since JDK 10/8u191) and by default uses only 25% of the limit for heap, which wastes memory. Use -XX:MaxRAMPercentage=70 to 75 (and optionally InitialRAMPercentage), leaving the rest for Metaspace, thread stacks, code cache, direct buffers and GC structures. Heap equal to the container limit leads to OOMKilled pods.

Collector. Be explicit even if it is the default: -XX:+UseG1GC with -XX:MaxGCPauseMillis=100 to 200 for typical services, or -XX:+UseZGC for strict latency or large heaps. Note that a JVM that sees fewer than 2 CPUs and under about 1.8 GB of memory selects Serial GC automatically, which surprises people in small pods.

GC logging. -Xlog:gc*:file=/logs/gc.log:time,uptime,level,tags:filecount=5,filesize=20m gives rotating logs with negligible overhead; essential for post-incident analysis.

OOM handling. -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps (a persistent volume with enough space) and -XX:+ExitOnOutOfMemoryError, so a broken instance exits and the orchestrator restarts it rather than limping on.

Other limits. -XX:MaxMetaspaceSize to make class loader leaks fail clearly; -Xss (for example 512k) if you have many platform threads; -XX:MaxDirectMemorySize for Netty-heavy services; -XX:NativeMemoryTracking=summary when investigating native usage.

Observability. A continuous JFR recording, -XX:StartFlightRecording=maxage=12h,maxsize=500m,dumponexit=true,filename=/logs/, lets you dump the last hours after an incident with roughly 1% overhead.

Environment. -Duser.timezone=UTC and -Dfile.encoding=UTF-8 (UTF-8 is the default since JDK 18) avoid environment-dependent behaviour. -XX:ActiveProcessorCount can help when CPU limits mislead thread-pool sizing.

Put flags in JAVA_TOOL_OPTIONS or the image entrypoint, keep them in version control, and change them only with measurements.

How it works

  1. Decide memory budget: container limit, heap percentage, native headroom.
  2. Choose the collector and pause target from latency goals.
  3. Enable GC logs and JFR for evidence.
  4. Configure OOM dump and exit behaviour.
  5. Cap Metaspace, direct memory and stacks as needed.
  6. Load-test and refine.

Example

JAVA_TOOL_OPTIONS="\
 -XX:MaxRAMPercentage=72 -XX:InitialRAMPercentage=72 \
 -XX:+UseG1GC -XX:MaxGCPauseMillis=150 \
 -Xlog:gc*:file=/logs/gc.log:time,uptime:filecount=5,filesize=20m \
 -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps -XX:+ExitOnOutOfMemoryError \
 -XX:MaxMetaspaceSize=384m -Xss512k \
 -XX:StartFlightRecording=maxage=12h,maxsize=500m,dumponexit=true,filename=/logs/ \
 -Duser.timezone=UTC -Dfile.encoding=UTF-8"
jcmd <pid> VM.flags -all | grep -E 'MaxHeapSize|UseG1GC|MaxRAMPercentage'  # verify

Common mistakes

  • Leaving the default 25% heap in containers, or using 100% of the limit.
  • Not knowing which GC the JVM actually selected.
  • No GC logs, so incidents cannot be analysed.
  • Copying dozens of obsolete flags (CMS, PermGen) from old guides.

How to answer in the interview

"For memory I size the heap explicitly: Xms equal to Xmx on VMs, or in containers MaxRAMPercentage around 70 to 75 percent so the JVM respects the limit and leaves room for native memory. I choose the collector deliberately, G1 with a MaxGCPauseMillis goal, or ZGC for strict latency. I enable unified GC logging to rotating files. I add HeapDumpOnOutOfMemoryError with a path on a persistent volume plus ExitOnOutOfMemoryError, so the orchestrator restarts a broken instance. I may cap Metaspace and thread stack size, run a continuous JFR recording, and fix the encoding and time zone. Then I verify the effective flags with jcmd and load-test."

Likely follow-up questions

  • Why should a JVM in a container usually not use 100 percent of the memory limit as heap? Metaspace, thread stacks, code cache, direct buffers and GC structures need native memory too; exceeding the limit gets the pod killed.
  • What happens on a 1-CPU, 1 GB pod by default? The JVM picks Serial GC; set G1 explicitly if needed.
  • Why ExitOnOutOfMemoryError? After an OOM, application state may be corrupt; restarting is safer.
