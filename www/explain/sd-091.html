Your application must comply with GDPR and keep EU customer data in the EU. How does this change your design?

Architecture Trade-offs · scenario · levels senior, lead

In one line

GDPR data residency means EU personal data is stored and processed in EU regions: partition users by home region, route requests there, keep every copy (logs, backups, analytics, vendors) in-region or anonymised, and build erasure, minimisation and audit into the design.

Detailed explanation

GDPR itself does not strictly forbid transfers outside the EU (it allows them under adequacy decisions or Standard Contractual Clauses), but many customers and contracts require data residency, and keeping data in the EU is the simplest way to stay compliant. The design consequence is a regional cell architecture: each user or tenant gets a home region at sign-up, and their personal data lives only in that region's stack.

A thin global layer holds only non-personal data: routing tables keyed by pseudonymous IDs, product catalogue, feature flags. A global router (DNS, edge or API gateway) looks up the home region and forwards the request. Cross-region features, such as a global admin dashboard, work on aggregated or pseudonymised data.

The hard part is leaks through secondary copies. Personal data turns up in application logs, distributed traces, error trackers, CDN caches, search indexes, data warehouses, backups and third-party SaaS. Each must be either region-pinned or fed anonymised/pseudonymised data, and every sub-processor must be checked for where it processes data.

GDPR also brings duties that are architectural: the right to erasure and access across every store, data minimisation, purpose limitation and consent records, encryption with region-specific keys, least-privilege access and audit logs to support 72-hour breach notification.

How it works

  1. At sign-up, record the user's home region (country, contract) in a global directory keyed by an opaque ID.
  2. The edge router resolves the home region and sends requests to that regional stack (app, DB, cache, queues, search).
  3. Logs, traces and analytics pipelines run per region; anything sent globally is scrubbed of personal fields.
  4. Backups and DR replicas stay inside EU regions (e.g. Frankfurt to Ireland, not to the US).
  5. A data map lists every store with personal data; an erasure workflow fans out deletes to all of them, and crypto-shredding (deleting the per-user key) covers backups.
  6. Access is audited, region-scoped and just-in-time.

Example

# Region routing config (global, no personal data)
regions:
  eu: { api: api.eu.example.com, kms_key: arn:aws:kms:eu-central-1:...:key/eu-pii }
  us: { api: api.us.example.com, kms_key: arn:aws:kms:us-east-1:...:key/us-pii }
user_directory:          # opaque id -> home region
  u_8f3a91: eu
logging:
  eu: { sink: loki-eu, redact: [email, phone, name, ip] }
backups:
  eu: { primary: eu-central-1, replica: eu-west-1 }

Common mistakes

  • Pinning the database but shipping raw logs or traces to a US-hosted observability tool.
  • Forgetting backups, search indexes and data-warehouse copies when implementing erasure.
  • Using a single global KMS key or admin role that can read every region.
  • Treating pseudonymised data as anonymous (it is still personal data under GDPR).

How to answer in the interview

"I'd give every customer a home region and run a regional stack holding their personal data, with a thin global routing layer that only knows an opaque ID and the region. Then I'd hunt down secondary copies: logs, traces, backups, analytics and vendors either stay in the EU or receive scrubbed data. I'd keep a data map so erasure requests reach every store, using crypto-shredding for backups, and add region-specific encryption keys, least-privilege access with audit logs, and data minimisation so we collect less in the first place."

Likely follow-up questions

  • How does a support engineer in India debug an EU issue? Through an in-region tool with masked data, just-in-time approved access, and full audit, or escalate to EU staff.
  • What about users who travel or move? Route by home region, not current location; support an explicit region migration.
  • How do you handle erasure in immutable backups? Per-user encryption keys deleted on request (crypto-shredding), plus backup expiry.
