Consumers keep rebalancing and throughput collapses. How do you debug it?

Kafka · scenario · levels mid, senior

In one line

Rebalance storms usually come from slow processing exceeding max.poll.interval.ms, not crashes; fix it by reducing max.poll.records or offloading work, tuning session timeouts, using static membership and the cooperative sticky assignor or the new KIP-848 consumer protocol.

Detailed explanation

A consumer has two liveness checks. A background thread sends heartbeats; if none arrives within session.timeout.ms (45 s by default in recent versions), the coordinator assumes the consumer died. Separately, the application must call poll() again within max.poll.interval.ms (default 5 minutes). If a batch of 500 records takes longer than that to process, the client proactively leaves the group even though heartbeats are fine. Its partitions are reassigned, it rejoins, triggers another rebalance, and the cycle repeats. With the classic eager protocol, every rebalance revokes all partitions from all members, so the whole group stops: throughput collapses.

Debugging starts with evidence: consumer logs show messages such as "consumer poll timeout has expired" or "member ... has left the group", and the coordinator logs record the reason for each rebalance. Correlate rebalance timestamps with deployments, GC pauses, autoscaler events and slow downstream calls.

Fixes target the cause. Lower max.poll.records so each poll does less work, raise max.poll.interval.ms if processing is legitimately slow, or move heavy work to a worker pool while pausing partitions. For rolling restarts in Kubernetes, static membership (group.instance.id) lets a pod return with the same identity within the session timeout without any rebalance. The CooperativeStickyAssignor does incremental rebalances, moving only partitions that must move. Kafka 4.0 made the new consumer group protocol (KIP-848) generally available: the broker computes assignments and reconciles them incrementally, which removes the group-wide synchronisation barrier.

How it works

  1. Check logs and metrics for rebalance reasons and frequency.
  2. Measure processing time per batch against max.poll.interval.ms.
  3. Tune max.poll.records, timeouts, or offload work with pause/resume.
  4. Add group.instance.id for stable pods.
  5. Switch to cooperative sticky or group.protocol=consumer.

Example

max.poll.records=100
max.poll.interval.ms=600000
session.timeout.ms=45000
group.instance.id=${POD_NAME}
partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor
# Kafka 4.x clients and brokers:
# group.protocol=consumer

Common mistakes

  • Raising session.timeout.ms when the real problem is poll interval.
  • Doing synchronous HTTP calls per record on the poll thread.
  • Autoscaling consumers on CPU, causing constant membership churn.
  • Using static membership with a very long session timeout, delaying real failure detection.

How to answer in the interview

"Most rebalance storms I have seen were caused by slow processing, not crashes. If the gap between poll calls exceeds max.poll.interval.ms, the consumer leaves the group even though heartbeats continue, and the eager protocol then stops everyone. I check the logs for the rebalance reason, measure batch processing time, then reduce max.poll.records or move slow work off the poll thread. For deployments I add static membership, use the cooperative sticky assignor, and on Kafka 4 I would consider the new broker-side consumer protocol from KIP-848."

Likely follow-up questions

  • How do you monitor rebalance frequency? Consumer metrics such as rebalance-rate-per-hour and join/sync time, plus alerts.
  • Heartbeat vs poll interval? Heartbeat detects dead processes; poll interval detects stuck processing.
  • Does static membership hide failures? Only up to session.timeout.ms, after which partitions move.
