How do you back up and restore etcd, and what does a restore mean for the cluster?

Kubernetes · concept · levels mid, senior, lead

In one line

Back up etcd with etcdctl snapshot save (endpoints plus client cert, key and CA) on a schedule, store snapshots encrypted and off-cluster, and restore with etcdutl snapshot restore into a new data directory on every member; a restore sends the whole cluster back in time, so controllers reconcile and real-world resources may not match. Managed services back up etcd for you; use Velero/GitOps for workloads.

Detailed explanation

etcd contains every object, including all Secrets, so a snapshot is both your disaster recovery and a highly sensitive file.

Backup: on a self-managed cluster (kubeadm, bare metal), run etcdctl snapshot save against one healthy member using the client TLS certificate. Schedule it (hourly is common, more often for busy clusters) via a CronJob or systemd timer on control plane nodes, verify each snapshot (etcdutl snapshot status), encrypt it, and copy it to object storage in another account or region with retention.

Restore is disruptive and all-or-nothing:

  1. Stop the API servers (move their static pod manifests) so nothing writes.
  2. Stop etcd on all members.
  3. On each member, run etcdutl snapshot restore (older docs use etcdctl snapshot restore) into a new data directory, with that member's --name, --initial-cluster and --initial-advertise-peer-urls, creating a fresh cluster identity.
  4. Point etcd at the new directory, start the members, then the API servers, and restart kubelets and controllers if they misbehave.

What it means: the cluster state jumps back to the snapshot time. Objects created afterwards vanish, deleted ones reappear, and Deployments revert. The real world does not rewind: cloud load balancers and volumes created after the snapshot may be orphaned, and deleted ones get recreated by controllers.

That is why, especially on managed Kubernetes (EKS, AKS, GKE back up etcd themselves and don't expose it), teams treat clusters as rebuildable: GitOps recreates manifests and Velero backs up namespaced objects and persistent volume data.

How it works

  1. Scheduled snapshot with TLS credentials.
  2. Integrity check, encryption, off-cluster copy.
  3. Disaster: stop API servers and etcd.
  4. Restore snapshot into new data dirs on all members.
  5. Start etcd, then API servers; check health and reconcile drift.

Example

ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  snapshot save /backup/etcd-$(date +%F-%H%M).db
etcdutl snapshot status /backup/etcd-2026-11-21-0100.db -w table

etcdutl snapshot restore /backup/etcd-2026-11-21-0100.db \
  --data-dir /var/lib/etcd-restore --name cp-1 \
  --initial-cluster cp-1=https://10.0.0.11:2380,cp-2=https://10.0.0.12:2380,cp-3=https://10.0.0.13:2380 \
  --initial-advertise-peer-urls https://10.0.0.11:2380

Common mistakes

  • Unencrypted snapshots in a shared bucket (they contain every Secret).
  • Restoring into the old data directory or only one member.
  • Never rehearsing a restore.
  • Relying on etcd snapshots for application data in volumes.

How to answer in the interview

"On a self-managed cluster I take etcd snapshots with etcdctl snapshot save, using the client certificate, key and CA, on a schedule, verify them, encrypt them and copy them off the cluster, because they contain every secret. To restore, I stop the API servers, restore the snapshot into a new data directory on each member with the right cluster settings, and start etcd and then the API servers. The whole cluster goes back in time, so newer objects disappear and cloud resources may not match, and controllers reconcile. On managed services the provider handles etcd, and I use GitOps and Velero for workloads and volumes."

Likely follow-up questions

  • Why is an etcd restore a last resort? It rewinds everything and creates drift; rebuilding from GitOps is more predictable.
  • What does Velero back up? API objects via the API server and volume data via snapshots or file-level backup.
  • How often to snapshot? Based on RPO; hourly is common, plus before upgrades.
