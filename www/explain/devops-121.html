What does Docker Compose do, and when would you use it?

Docker · concept · levels entry, mid

In one line

Docker Compose defines a multi-container application in one YAML file (services, networks, volumes, environment) and runs it with docker compose up; it is ideal for local development and CI integration tests, uses depends_on with health checks for startup order, but is not a multi-host production orchestrator.

Detailed explanation

Running an app plus Postgres, Redis and Kafka by hand means long docker run commands with networks, volumes and environment variables. Compose captures all of it declaratively in compose.yaml (the old top-level version: key is obsolete in Compose v2, which is invoked as docker compose).

Each service specifies an image or a build context, ports, environment or env_file, volumes, command, resource limits and healthcheck. Compose creates a project network automatically, so services reach each other by service name (db:5432). Named volumes persist data across down/up (unless you pass -v). Profiles let you start optional services (for example monitoring tools) only when asked, and override files (compose.override.yaml) adjust settings per developer or CI.

Startup order: plain depends_on only waits until the dependency container has started, not until it is ready. To wait for readiness, give the dependency a healthcheck and use condition: service_healthy. Applications should still retry connections, because dependencies can restart later.

Typical uses:

  • Local development: one command gives every developer the same stack; bind mounts enable hot reload, and docker compose watch can sync or rebuild on file changes.
  • Integration and end-to-end tests in CI: spin up dependencies, run tests, tear down (Testcontainers is an alternative from inside test code).
  • Small single-host deployments, demos and internal tools.

It is not built for multi-host scheduling, self-healing across nodes, rolling updates or autoscaling. That is the job of Kubernetes, ECS or Nomad.

How it works

  1. docker compose up -d reads the file and creates network and volumes.
  2. Builds or pulls images.
  3. Starts services in dependency order, waiting for health where configured.
  4. logs, ps, exec manage the stack; down removes containers and network.

Example

services:
  api:
    build: .
    ports: ["8080:8080"]
    environment:
      DB_URL: postgres://app:app@db:5432/shop
      REDIS_HOST: redis
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_started
  db:
    image: postgres:17
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app
      POSTGRES_DB: shop
    volumes: [pgdata:/var/lib/postgresql/data]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d shop"]
      interval: 5s
      retries: 10
  redis:
    image: redis:7-alpine
volumes:
  pgdata:

Common mistakes

  • Assuming depends_on means "database is ready".
  • Publishing every service's port to the host when only the API needs it.
  • Committing real secrets in the compose file.
  • Using Compose as a production cluster orchestrator.

How to answer in the interview

"Compose defines a multi-container application in one YAML file: services with their image or build context, ports, environment, networks and volumes, and starts it all with docker compose up. Services find each other by name on the project network. For startup order I use depends_on with a healthcheck and the service_healthy condition, because plain depends_on only waits for the container to start. I use it for local development, say the app plus Postgres, Redis and Kafka, and for integration tests in CI. For production across multiple hosts I'd use Kubernetes or ECS."

Likely follow-up questions

  • Wait until the DB is ready? Healthcheck plus condition: service_healthy, and retries in the app.
  • Different settings per environment? Override files, profiles and .env interpolation.
  • Compose vs Kubernetes? Single host and simple vs multi-host scheduling, self-healing and scaling.
