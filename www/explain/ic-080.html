Your company has years of manually created cloud infrastructure. How do you bring it under IaC?

Infrastructure as Code · scenario · levels lead

In one line

Inventory what exists, prioritise by risk and change frequency, import resources with import blocks and generated config, iterate until the plan shows no changes, freeze or restrict manual changes meanwhile, and only then refactor into modules and standards step by step.

Detailed explanation

Brownfield adoption is mostly about not breaking anything. The resources already serve production; the first goal is to describe them exactly as they are, so Terraform takes over without changing them. Improvement comes afterwards.

Inventory and prioritise. Use AWS Resource Explorer, AWS Config, Azure Resource Graph or GCP Cloud Asset Inventory to list resources by account, region and type, and group them into components (network, IAM, data stores, compute per application). Start where IaC gives most value: things that change often or are critical, such as networking, IAM, DNS and production databases. Soon-to-be-retired or truly static resources may never be worth importing.

Import. Since Terraform 1.5, import blocks declare to (address) and id (cloud ID) in code, so imports are reviewed and planned like any change, and for_each on import blocks (1.7+) handles many resources. terraform plan -generate-config-out=generated.tf drafts the resource configuration from the real objects. Tools such as aztfexport for Azure, Former2 for AWS or Terraformer can generate code at larger scale. Generated code is verbose; clean it into readable configuration.

Iterate to a clean plan. Plan, adjust configuration, repeat until the plan reports no changes. That proves the code matches reality. Any remaining difference is decided explicitly, never applied by accident.

Freeze. During migration, manual changes to the affected area are frozen or go through a tracked request, otherwise code and reality diverge again.

Then improve. Once resources are managed, refactor into standard modules using moved blocks, then fix deviations (tags, encryption, naming) as separate, reviewed changes.

How it works

  1. Inventory and group resources; choose the first component.
  2. Write import blocks; generate draft config.
  3. Plan; tidy code; repeat until no changes.
  4. Apply (imports only); enable pipelines and drift detection.
  5. Restrict console write access for that component.
  6. Refactor and remediate in later, separate PRs.

Example

import {
  for_each = toset(["sg-0a1b2c3d", "sg-0e5f6a7b"])
  to       = aws_security_group.legacy[each.key]
  id       = each.key
}
terraform plan -generate-config-out=generated.tf
terraform plan     # repeat until: No changes. Your infrastructure matches the configuration.
terraform apply    # performs only the imports

Common mistakes

  • Fixing misconfigurations during the initial import, so the first apply changes production.
  • Importing everything at once into one huge state.
  • Allowing console changes while code is being written.
  • Keeping raw generated code forever instead of refactoring.

How to answer in the interview

"I start with an inventory from Resource Explorer or Config, group resources into components and prioritise things that change often or are critical, like networking, IAM and production databases. For each area I write import blocks and use plan with generate-config-out as a starting point, then iterate until the plan shows no changes, which proves the code matches reality without touching it. During the migration manual changes are frozen or tightly controlled. Only after resources are safely managed do I refactor into standard modules with moved blocks and fix deviations, one reviewed change at a time."

Likely follow-up questions

  • Why avoid fixing misconfigurations during import? It mixes adoption with change, so the first apply could break production.
  • What about resources Terraform's provider can't import? Leave them documented, or manage via another tool or provider.
  • How do you prove nothing changed? A clean plan before the import-only apply.
