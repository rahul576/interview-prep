How would you design an inventory management system with concurrent updates?

System Design · design · levels senior, lead

In one line

Prevent overselling with an atomic conditional update (... WHERE quantity >= :n), or optimistic locking with retry / pessimistic locks for short contended transactions, hold stock with expiring reservations, publish changes via outbox events to idempotent consumers, and handle hot SKUs with Redis counters, queues and sharding.

Detailed explanation

Inventory has many writers (orders, returns, warehouse receipts, manual adjustments) touching the same rows. The core invariant is available stock never goes below zero.

Atomic conditional update: the database does the check and decrement in one statement: UPDATE stock SET quantity = quantity - :n WHERE sku = :sku AND warehouse = :w AND quantity >= :n. If zero rows are updated, the item is out of stock. It is simple, fast and correct under any concurrency, because the row lock is held only for the statement.

Optimistic locking: read the row with a version, compute, then UPDATE ... WHERE version = :v. JPA's @Version throws OptimisticLockException on conflict; retry a few times. Good when conflicts are rare and the logic is complex.

Pessimistic locking: SELECT ... FOR UPDATE locks the row for the transaction. Useful for short, highly contended operations that need several reads, but holding locks during remote calls kills throughput and risks deadlocks (lock rows in a consistent order).

Reservations: at checkout, move units from available to reserved with an expiry; payment success confirms (commits) the reservation, failure or timeout releases it via a scheduled job. Track on-hand, reserved and available separately.

Events and idempotency: stock changes emit events via the transactional outbox to Kafka for search, analytics and other channels. Consumers are idempotent (dedupe by event ID or order ID).

Hot items: a flash sale concentrates writes on one row. Use Redis atomic counters (DECRBY with a Lua check) as a fast gate, then persist asynchronously and reconcile; queue requests per SKU for serial processing; or split stock into several sub-rows (buckets) and pick one randomly. Shard by SKU and warehouse.

How it works

  1. Checkout -> reserve(orderId, sku, n) atomically; insert reservation with expiry.
  2. Payment success -> confirm: decrement on-hand, delete reservation.
  3. Payment failure/expiry -> release: return units to available.
  4. Every change writes an outbox event in the same transaction.
  5. Consumers update read models idempotently.
  6. Nightly reconciliation compares counters with physical counts.

Example

@Entity
class StockItem {
    @Id String sku;
    int available;
    int reserved;
    @Version long version;          // optimistic locking alternative
}

@Modifying
@Query(value = """
    UPDATE stock_item SET available = available - :n, reserved = reserved + :n
    WHERE sku = :sku AND available >= :n""", nativeQuery = true)
int tryReserve(String sku, int n);

// Redis gate for a flash sale (Lua keeps check-and-decrement atomic)
String LUA = "local q = tonumber(redis.call('GET', KEYS[1]) or '0') " +
             "if q >= tonumber(ARGV[1]) then return redis.call('DECRBY', KEYS[1], ARGV[1]) else return -1 end";

Common mistakes

  • Reading stock in Java, checking, then writing (race condition).
  • Holding SELECT FOR UPDATE locks while calling the payment gateway.
  • Reservations without expiry, locking stock forever.
  • Treating Redis as the source of truth with no reconciliation.
  • Non-idempotent event consumers double-counting.

How to answer in the interview

"The key requirement is never overselling while many orders hit the same stock. The simplest robust approach is an atomic conditional update, decrementing only where quantity is at least n, and treating zero updated rows as out of stock. Alternatives are optimistic locking with a version and retry, or SELECT FOR UPDATE for short contended transactions. Checkout creates a reservation with expiry, released by a job if payment doesn't complete. Changes go out through an outbox to idempotent consumers. For flash sales I'd use Redis atomic counters or a queue per SKU, and shard by SKU and warehouse."

Likely follow-up questions

  • Reconciling Redis with the DB? Redis is a gate; the DB is the record. Periodic jobs compare and correct, and orders are confirmed only after the DB write.
  • Multiple warehouses? Reserve per warehouse and choose by availability and distance.
  • Backorders? Allow negative available only for flagged SKUs with explicit customer messaging.
