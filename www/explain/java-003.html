What is the contract between equals and hashCode, and what goes wrong if you break it?

Core Java & OOP · concept · levels entry, mid

In one line

If a.equals(b) is true, then a.hashCode() == b.hashCode() must be true; unequal objects may share a hash code. Hash-based collections rely on this, so overriding equals without hashCode breaks HashMap and HashSet lookups.

Detailed explanation

Object.equals defaults to identity (==), and Object.hashCode is typically derived from identity. When you give a class value semantics by overriding equals (two Money objects with the same amount and currency are equal), you must override hashCode consistently.

The contract from Object's Javadoc:

  • equals must be reflexive (a.equals(a)), symmetric, transitive, consistent (same answer while the fields used do not change) and return false for null.
  • hashCode must be consistent during an execution while the fields used in equals do not change.
  • Equal objects must have equal hash codes. The reverse is not required: different objects can collide, though good hash functions minimise collisions for performance.

Why it matters: HashMap, HashSet and ConcurrentHashMap first use hashCode() to pick a bucket, then use equals() to find the exact key within it. If two equal objects have different hash codes, they land in different buckets: map.get(equalKey) returns null, set.contains returns false, and a HashSet can contain "duplicates". If hashCode is constant (always 42), it is legal but every entry collides, turning O(1) lookups into a long chain or a tree (Java 8 treeifies large buckets).

Mutable keys are a related trap: if fields used in hashCode change after insertion, the entry sits in the wrong bucket and becomes unreachable.

Best practice: base both methods on the same, ideally immutable fields; generate them with Objects.equals/Objects.hash, the IDE, or use records (Java 16), which generate correct equals, hashCode and toString from their components. Be careful with inheritance: mixing subclass fields into equals usually breaks symmetry; prefer final classes or getClass() checks. JPA entities need special care because ids change at persist time.

How it works

  1. map.put(key, v) calls key.hashCode(), spreads it and picks a bucket.
  2. Within the bucket, it compares existing keys with equals().
  3. map.get(other) repeats: other.hashCode() selects the bucket, equals finds the key.
  4. Different hash codes for equal keys mean a different bucket, so the lookup misses.
  5. Collisions are resolved by equals, so correctness holds, only speed suffers.

Example

final class Email {
    private final String value;
    Email(String value) { this.value = value.toLowerCase(); }

    @Override public boolean equals(Object o) {
        return o instanceof Email e && value.equals(e.value);
    }
    // Omit this and the set below has size 2 and contains() returns false
    @Override public int hashCode() { return value.hashCode(); }
}

Set<Email> set = new HashSet<>();
set.add(new Email("A@shop.com"));
set.add(new Email("a@shop.com"));
System.out.println(set.size());                               // 1
System.out.println(set.contains(new Email("a@SHOP.com")));    // true

record Sku(String code, int version) {}                       // equals/hashCode generated

Common mistakes

  • Overriding equals(Email other) (an overload) instead of equals(Object).
  • Overriding equals but not hashCode.
  • Using mutable fields in hashCode for objects used as keys.
  • Including fields in hashCode that are not in equals.
  • Breaking symmetry with subclass comparisons.

How to answer in the interview

"If two objects are equal according to equals, they must return the same hashCode. The reverse isn't required: unequal objects can share a hash code, which is just a collision. HashMap and HashSet use hashCode to pick the bucket and then equals to find the exact key. If I override equals but not hashCode, two equal objects can land in different buckets, so lookups fail and a HashSet can hold duplicates. So I always override both together, based on the same, ideally immutable fields, keep equals reflexive, symmetric, transitive and consistent, and in modern Java I often just use a record."

Likely follow-up questions

  • What happens if you use a mutable field in hashCode and change it after putting the object in a HashMap? The entry stays in the old bucket, so get and remove with that object fail and the entry is effectively lost (a memory leak).
  • Is a constant hashCode legal? Yes, but every key collides and performance degrades badly.
  • Why use instanceof vs getClass() in equals? instanceof allows subclasses but can break symmetry; getClass() is strict; for final classes either is fine.
