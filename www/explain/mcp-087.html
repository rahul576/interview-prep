A host connects to ten MCP servers at once. What problems appear, and how do you handle them?

MCP Servers · scenario · levels mid, senior

In one line

Ten servers cause context bloat from tool definitions, worse tool selection among similar tools, name collisions, a larger attack surface with cross-server injection, and operational overhead (startup, memory, failures); handle it by enabling servers per task or agent profile, tool search or deferred loading, a curated reviewed set, isolating sensitive and external servers, and health monitoring.

Detailed explanation

Each server might contribute ten to fifty tools. With ten servers, the model may see a few hundred tool definitions on every turn.

Context bloat. All those definitions are sent with every model request, costing tokens, money and latency, and crowding out space for the actual task. Some setups spend tens of thousands of tokens on tool definitions before the user has typed anything.

Selection quality. More tools means more chances to pick the wrong one, especially when several are similar: three different search tools from the wiki, ticketing and code servers. Name collisions need namespacing (for example jira__search vs confluence__search), which hosts typically do by prefixing the server name.

Security. The attack surface grows with every server. Worse, servers are not isolated at the model level: a poisoned description or injected result from one server can influence calls to another, for example making the model read data via the database server and send it via an external web or email server. Combining many servers easily assembles the lethal trifecta.

Operations. Local servers each start a process, adding startup time and memory; any of them can crash, hang during initialisation or fail authentication, degrading the whole session.

Handling it:

  • Agent profiles: enable only the servers and tools relevant to a task (coding, support, analytics).
  • Tool search / deferred loading: the model sees a search tool and loads definitions on demand, which many hosts now support.
  • Curate: a reviewed set of servers; disable unused tools.
  • Isolate sensitive and external servers into different sessions.
  • Monitor server health and timeouts; fail gracefully when one server is down.

How it works

  1. Inventory tools per server and measure tokens spent on definitions.
  2. Group servers into task profiles.
  3. Enable deferred loading for large or rarely used servers.
  4. Namespace tools and fix ambiguous names or descriptions.
  5. Separate sessions that would combine private data, untrusted content and external communication.

Example

profiles:
  coding:
    servers: [github, filesystem, ci-logs]
  support:
    servers: [crm, tickets, kb-search]
  research:
    servers: [web-fetch, kb-search]      # no private data servers here
defaults:
  tool_loading: deferred                 # tool search instead of all definitions
  namespace_tools: true
  server_start_timeout_s: 10

Common mistakes

  • Enabling every installed server globally.
  • Ignoring the token cost of definitions.
  • Assuming servers are isolated from each other at the model level.
  • One hung server blocking the whole host at startup.

How to answer in the interview

"With ten servers the first problem is context bloat: all tool definitions go to the model every turn, costing tokens and latency. Selection quality drops because the model chooses among many tools, some similar, like several search tools, and name collisions need namespacing. Security gets harder: the attack surface grows, and a poisoned description or injected result from one server can influence calls to another, like sending database data to an external server. Operationally, local servers add startup time, memory and more failure points. I enable only the servers and tools relevant to each task or agent profile, use tool search or deferred loading, keep a curated set, isolate sensitive and external servers into different sessions, and monitor health."

Likely follow-up questions

  • Design agent profiles? By task and data sensitivity, with the minimum servers each needs.
  • How does tool search work? The model searches a catalogue and only relevant definitions are loaded.
  • Name collisions? Host prefixes tools with the server name.
