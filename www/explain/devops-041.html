How do you secure the software supply chain in a CI/CD pipeline?

DevSecOps · concept · levels senior, lead

In one line

Secure the supply chain in layers: SAST, SCA and image scanning on every change, secret scanning and short-lived OIDC credentials, SBOMs, signing (cosign) and SLSA provenance verified at admission, and hardened pipelines: ephemeral least-privilege runners, SHA-pinned actions and protected branches.

Detailed explanation

Supply chain attacks target everything between a developer's keyboard and production: dependencies (typosquatting, hijacked maintainers), build systems (SolarWinds-style tampering), CI credentials and third-party actions (the 2025 tj-actions/changed-files compromise leaked secrets from thousands of workflows). Defence therefore covers what goes in, how it is built and what is allowed to run.

What goes in: SAST (Semgrep, CodeQL, SonarQube) on pull requests; SCA (Dependabot, Renovate, Snyk, Trivy) for vulnerable or malicious dependencies, with lockfiles and an internal proxy registry so builds pull through a controlled point; secret scanning (Gitleaks, GitHub push protection) to stop credentials being committed; DAST against staging for runtime issues; image scanning that blocks critical, fixable CVEs.

How it is built: builds run on ephemeral runners that are destroyed after each job, with least-privilege tokens (permissions: set explicitly), cloud access via OIDC short-lived credentials instead of stored keys, secrets from Vault or a secrets manager, and third-party actions pinned to a full commit SHA. Branch protection requires reviews and passing checks, and CODEOWNERS protect pipeline files.

What is allowed to run: the pipeline generates an SBOM (Syft, CycloneDX/SPDX), signs the image with cosign (often keyless via Sigstore) and publishes SLSA provenance attestations. In the cluster, an admission policy (Kyverno, Sigstore policy-controller) only admits images that are signed by our pipeline identity and come from trusted registries, referenced by digest.

How it works

  1. PR → SAST, SCA, secret scan, IaC scan; review required.
  2. Merge → build on ephemeral runner with OIDC credentials.
  3. Scan image → generate SBOM → sign and attest provenance → push by digest.
  4. Deploy → admission controller verifies signature, provenance and registry.
  5. Runtime → continuous re-scanning of SBOMs against new CVEs.

Example

permissions:
  contents: read
  id-token: write          # OIDC for cloud + keyless signing
steps:
  - uses: actions/checkout@08eba0b27e820071cde6df949e0beb9ba4906955  # pinned SHA
  - run: trivy fs --exit-code 1 --severity CRITICAL --scanners vuln,secret,misconfig .
  - run: docker build -t $IMAGE .
  - run: syft $IMAGE -o cyclonedx-json > sbom.json
  - run: |
      docker push $IMAGE
      cosign sign --yes $IMAGE@$DIGEST
      cosign attest --yes --type cyclonedx --predicate sbom.json $IMAGE@$DIGEST

Common mistakes

  • Actions referenced by mutable tags like @v4 or @main.
  • Long-lived cloud keys stored as CI secrets.
  • Signing images but never verifying signatures at deploy time.
  • Scanners in "report only" mode that nobody reads.

How to answer in the interview

"I secure it in layers. On every pull request: SAST, dependency scanning, secret scanning and IaC checks, plus required reviews. Builds run on ephemeral, least-privilege runners, get cloud access via OIDC rather than stored keys, and pin third-party actions to commit SHAs. The pipeline scans the image, generates an SBOM, signs it with cosign and records SLSA provenance. In the cluster an admission policy only allows signed images from our registries, deployed by digest. SBOMs are kept so new CVEs can be traced to running services quickly."

Likely follow-up questions

  • A popular dependency is compromised? Use SBOMs to find usage, pin to a safe version, rotate exposed secrets, rebuild and redeploy.
  • Why pin to SHA? Tags are mutable and can be repointed to malicious code.
  • What does SLSA add over signing? Verifiable claims about how and from what source the artifact was built.
