What are provider-defined functions in Terraform?

Terraform · concept · levels mid, senior

In one line

Provider-defined functions (Terraform 1.8+) let providers ship their own functions, called as provider::<name>::<function>(...), for things like parsing ARNs or Azure resource IDs, extending the language without changing Terraform core and versioned with the provider.

Detailed explanation

Terraform's built-in functions (lookup, cidrsubnet, jsonencode, regex and so on) are general purpose and only change with Terraform releases. Real configurations often need domain-specific logic: extracting the account ID from an IAM role ARN, getting the resource group from an Azure resource ID, or normalising a value the same way the cloud API does. Before 1.8 people wrote fragile regex or split expressions that break when formats differ slightly, for example ARNs in China or GovCloud partitions, or nested Azure child resource IDs.

With provider-defined functions, a provider implements functions in Go alongside its resources, and you call them with a namespaced syntax: provider::aws::arn_parse(var.role_arn) returns an object with partition, service, region, account ID and resource; provider::azurerm::parse_resource_id(id) returns subscription, resource group, provider namespace and name. Terraform itself ships a few through the built-in terraform provider, such as provider::terraform::encode_tfvars. Utility providers exist mostly to offer functions.

Key properties: the provider must be declared in required_providers of the module that calls the function (the local name is used in the call); the function is versioned and pinned with the provider through version constraints and .terraform.lock.hcl, so behaviour is reproducible; and functions are pure: they compute locally during plan, without calling cloud APIs or needing credentials.

How it works

  1. Add the provider to required_providers (version 1.8+ of Terraform required).
  2. Check the provider documentation's "Functions" section.
  3. Call provider::<local-name>::<function>(args) anywhere expressions are allowed.
  4. Terraform starts the provider plugin and asks it to evaluate the function during plan.
  5. The result is used like any other value.

Example

terraform {
  required_version = ">= 1.8"
  required_providers {
    aws     = { source = "hashicorp/aws", version = "~> 6.0" }
    azurerm = { source = "hashicorp/azurerm", version = "~> 4.0" }
  }
}

locals {
  role       = provider::aws::arn_parse(var.role_arn)
  account_id = local.role.account_id

  vnet = provider::azurerm::parse_resource_id(var.vnet_id)
  rg   = local.vnet.resource_group_name
}

Common mistakes

  • Calling a function from a provider not declared in that module's required_providers.
  • Using a function name that exists only in a newer provider version than the one pinned.
  • Expecting functions to look up live data; they are pure.
  • Continuing to maintain complex regexes when a provider function exists.

How to answer in the interview

"Before Terraform 1.8 we only had built-in functions like lookup, cidrsubnet or jsonencode, so domain-specific logic ended up as fragile regexes. Provider-defined functions let providers ship their own functions, which I call as provider::aws::arn_parse(var.role_arn) or provider::azurerm::parse_resource_id(id). Typical uses are parsing or building ARNs and Azure resource IDs, or encoding special formats. They extend the language without changing Terraform core, are versioned and locked with the provider, so behaviour is reproducible, and they're pure functions evaluated during plan without calling cloud APIs."

Likely follow-up questions

  • Why is regex parsing fragile? Formats vary by partition, resource type and nesting; the provider knows the exact grammar.
  • Can you write your own functions? Yes, by writing a provider with the plugin framework, not in HCL.
  • Do functions work in modules? Yes, if the module declares the provider in required_providers.
