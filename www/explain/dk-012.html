What is the difference between ARG and ENV in a Dockerfile?

Docker · concept · levels entry

In one line

ARG is a build-time variable set with --build-arg, available only during the build (and not persisted in the container environment); ENV sets an environment variable stored in the image and present at runtime, overridable with -e; neither should carry secrets, because both are visible in image metadata or history.

Detailed explanation

ARG NAME[=default] declares a variable for the build. You pass values with docker build --build-arg APP_VERSION=1.4.2 .. Typical uses: choosing a base image tag, a tool version to download, a build profile, or labels like commit SHA. Key rules:

  • An ARG before FROM can be used in FROM lines (ARG NODE_VERSION=22 then FROM node:${NODE_VERSION}-slim). To use it again after FROM, re-declare ARG NODE_VERSION without a value inside that stage.
  • ARGs are scoped per stage in multi-stage builds.
  • They are not set in the running container's environment.
  • Predefined ARGs exist, such as HTTP_PROXY and, with BuildKit, TARGETPLATFORM, TARGETARCH and BUILDPLATFORM.

ENV NAME=value sets a variable that applies to later build steps and is saved in the image config, so every container from that image has it. Use it for runtime defaults: PORT, JAVA_OPTS, PATH additions, TZ, NODE_ENV=production. Runtime overrides with -e or --env-file, and Kubernetes env, take precedence.

Combining them when a build-time value is also needed at runtime:

ARG APP_VERSION
ENV APP_VERSION=${APP_VERSION}

Secrets: values used in RUN with ARGs can be seen in docker history and the build's provenance metadata; ENV values are visible to anyone who can docker inspect the image. Use BuildKit secret mounts (RUN --mount=type=secret,id=npm_token … with docker build --secret id=npm_token,env=NPM_TOKEN) at build time and runtime secrets (files, Vault, Kubernetes Secrets) at run time.

How it works

  1. Builder resolves ARG values from --build-arg or defaults.
  2. ARG and ENV are substituted into later instructions.
  3. ENV is written into the image config; ARG is not.
  4. At docker run, image ENV + runtime -e form the container environment.

Example

ARG NODE_VERSION=22
FROM node:${NODE_VERSION}-bookworm-slim
ARG APP_VERSION=dev
ARG GIT_SHA
LABEL org.opencontainers.image.revision=${GIT_SHA}
ENV NODE_ENV=production \
    APP_VERSION=${APP_VERSION}
WORKDIR /app
COPY package*.json ./
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci
COPY . .
CMD ["node", "server.js"]
docker build --build-arg APP_VERSION=1.4.2 --build-arg GIT_SHA=$(git rev-parse HEAD) \
  --secret id=npmrc,src=$HOME/.npmrc -t web:1.4.2 .
docker run --rm -e NODE_ENV=staging web:1.4.2 node -e 'console.log(process.env.NODE_ENV, process.env.APP_VERSION)'

Common mistakes

  • Passing tokens with --build-arg and assuming they disappear.
  • Expecting an ARG to be available in the running container.
  • Declaring ARG before FROM and wondering why it is empty inside the stage.
  • Baking environment-specific values like database hosts into ENV.

How to answer in the interview

"ARG is a build-time variable: it exists only while the image is built and I set it with docker build --build-arg, for example to pick a base image tag or a version to download. ENV sets an environment variable that's stored in the image and present in every container, so the app can read it at runtime, and it can be overridden with -e. When I need a build value at runtime I do ARG APP_VERSION then ENV APP_VERSION=$APP_VERSION. Neither is for secrets: build args show up in image history and metadata, so I use BuildKit secret mounts during builds and mounted secrets at runtime."

Likely follow-up questions

  • Can an ARG be used before FROM? Yes, for the FROM line; re-declare it inside the stage to use it later.
  • Does ENV carry into later stages? Only into stages built FROM that stage.
  • Precedence of ENV vs -e? Runtime -e wins.
