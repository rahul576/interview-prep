You want Terraform to create the storage account that will hold its own remote state. How do you solve this chicken-and-egg problem?

Terraform · scenario · levels mid, senior

In one line

Use a small bootstrap configuration that creates the state storage with local state, then add the backend and run terraform init -migrate-state to move its own state there; or create the backend outside Terraform (script, CLI, management account), and in all cases protect the state store heavily and document the one-time bootstrap.

Detailed explanation

A remote backend must exist before terraform init can use it, but you want the storage account or S3 bucket itself to be managed as code with proper settings. That is the chicken-and-egg problem.

Option 1: bootstrap with local state, then migrate. A dedicated bootstrap/ configuration creates the state storage: an S3 bucket (versioning, encryption, public access block, bucket policy, optionally Object Lock), or an Azure resource group, storage account and container (blob versioning, soft delete, private endpoint, RBAC, CanNotDelete lock). It runs once with local state, since no backend exists yet. Then you add a backend block pointing to the new storage, with its own key such as bootstrap/terraform.tfstate, and run terraform init -migrate-state. Terraform copies the local state into the bucket, and from then on the bootstrap is managed like any other configuration, including changes through pull requests.

Option 2: create the backend outside Terraform. A script with the AWS or Azure CLI, a CloudFormation stack, or an account-vending process creates the storage, often in a separate management or "tooling" account/subscription. This avoids the circular dependency entirely; you can later import the resources into Terraform if you want them in code.

Either way, the state store is the most sensitive part of the setup: it holds the map of all infrastructure and often secrets. Protect it with versioning or soft delete, encryption, private network access, very restricted write permissions (pipelines only), deletion locks and access logging. Document the bootstrap as a rare, one-time runbook, including how to recover.

How it works

  1. Write bootstrap/ configuration for the state storage.
  2. terraform init && terraform apply with local state.
  3. Add backend block (key = "bootstrap/terraform.tfstate").
  4. terraform init -migrate-state; confirm copy.
  5. Delete local state; verify terraform plan shows no changes.
  6. Other configurations use the new backend with their own keys.

Example

# bootstrap/main.tf
resource "aws_s3_bucket" "state" {
  bucket = "acme-tfstate-prod"
  lifecycle { prevent_destroy = true }
}

resource "aws_s3_bucket_versioning" "state" {
  bucket = aws_s3_bucket.state.id
  versioning_configuration { status = "Enabled" }
}

resource "aws_s3_bucket_public_access_block" "state" {
  bucket                  = aws_s3_bucket.state.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

# added after the first apply:
terraform {
  backend "s3" {
    bucket       = "acme-tfstate-prod"
    key          = "bootstrap/terraform.tfstate"
    region       = "eu-west-1"
    use_lockfile = true
  }
}
terraform init -migrate-state

Common mistakes

  • Leaving the bootstrap state on a laptop forever.
  • No versioning, so a corrupted state cannot be recovered.
  • Broad write access to the state bucket.

How to answer in the interview

"I use a small bootstrap configuration that creates the state storage, like a storage account with a container or an S3 bucket, with versioning, encryption and access policies. It first runs with local state because the backend doesn't exist yet. Once the storage exists, I add the backend block and run terraform init -migrate-state, so even the bootstrap state lives remotely under its own key. Some teams instead create the backend with a script or in a separate management account, which avoids the circular dependency. Either way the state store gets strong protection: deletion locks, versioning or soft delete, private access and very restricted permissions, and the bootstrap is documented as a one-time process."

Likely follow-up questions

  • Recovering if the state storage were deleted? Recover the account or bucket if possible, restore state from backups or replicas, otherwise re-import resources.
  • Should the bootstrap use the same bucket? Commonly yes, under its own key, or a separate management account.
  • How do you protect state from ransomware? Versioning with Object Lock or immutability, separate account, cross-region copies.
