What IAM best practices do you follow in AWS?

Cloud (AWS) · concept · levels mid, senior

In one line

I follow least privilege, use roles with temporary credentials instead of access keys, put humans behind SSO with MFA (IAM Identity Center), lock away the root user, add SCP guardrails, and audit continuously with CloudTrail and IAM Access Analyzer.

Detailed explanation

Most AWS breaches start with a leaked long-lived access key or an over-broad policy, so IAM hygiene is about two things: who can get credentials and how much those credentials can do.

Least privilege means policies scoped to the specific actions and resource ARNs needed, with conditions where useful (aws:SourceVpc, tags, aws:PrincipalOrgID). I start reasonably narrow and use IAM Access Analyzer to generate policies from CloudTrail activity and to flag unused access (roles, keys and permissions not used in months) and resources shared outside the organisation.

Humans sign in through IAM Identity Center connected to the corporate IdP, with MFA and permission sets per account, so there are no IAM users with passwords. Workloads use roles: EC2 instance profiles, ECS task roles, EKS IRSA or Pod Identity, Lambda execution roles, and CI pipelines federated via OIDC. Credentials are temporary and rotate automatically.

The root user gets a hardware or passkey MFA, no access keys, and is only used for the handful of tasks that require it;. SCPs set the outer boundary that even admins cannot cross, such as denying CloudTrail deletion or unapproved regions. Permission boundaries let teams create roles without escalating privilege. Finally, CloudTrail logs every API call to a central log archive account, and separate accounts per environment limit the blast radius.

How it works

  1. Organisation with separate accounts per environment/workload.
  2. Identity Center + IdP + MFA for people; no IAM users for humans.
  3. Roles and OIDC for workloads and CI; no static keys.
  4. Narrow policies, refined with Access Analyzer findings.
  5. SCPs and permission boundaries as guardrails.
  6. Organisation-wide CloudTrail, alerts on root login and policy changes, periodic access reviews.

Example

GitHub Actions deploying without stored keys: the role trusts GitHub's OIDC provider, restricted to one repository and branch.

{
  "Effect": "Allow",
  "Principal": { "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com" },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": {
      "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
      "token.actions.githubusercontent.com:sub": "repo:acme/shop-api:ref:refs/heads/main"
    }
  }
}

The workflow sets permissions: id-token: write and uses aws-actions/configure-aws-credentials with role-to-assume.

Common mistakes

  • "Action": "" and "Resource": "" "temporarily", which become permanent.
  • Long-lived access keys in CI variables or laptops.
  • OIDC trust policies without a sub condition, letting any repository assume the role.

How to answer in the interview

"I start with least privilege: specific actions and resources, refined over time with IAM Access Analyzer's policy generation and unused-access findings. People never get IAM users; they sign in through IAM Identity Center with MFA and permission sets. Workloads and pipelines use roles with temporary credentials, such as task roles, IRSA or Pod Identity, and OIDC from GitHub Actions, so there are no long-lived keys. The root user is locked down with strong MFA and no keys. SCPs in AWS Organizations provide guardrails, CloudTrail logs everything centrally, and separate accounts per environment limit blast radius."

Likely follow-up questions

  • How would GitHub Actions deploy without keys? OIDC federation to a role whose trust policy pins repository and branch.
  • SCP vs permission boundary? SCPs limit whole accounts; boundaries cap what a specific role or user can ever be granted.
  • How do you detect a leaked key? GuardDuty findings, CloudTrail anomalies, secret scanning; then deactivate, rotate and review activity.
