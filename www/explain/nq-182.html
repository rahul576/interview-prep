What are @ConditionalOnProperty, @ConditionalOnClass, and @ConditionalOnMissingBean?

Spring Boot · concept · levels mid

In one line

@ConditionalOnProperty registers a bean based on a property value (havingValue, matchIfMissing), @ConditionalOnClass only when a class is on the classpath, and @ConditionalOnMissingBean only when no bean of that type exists yet, giving defaults that user configuration can override.

Detailed explanation

These three conditions answer three different questions, and auto-configurations typically combine them.

@ConditionalOnProperty asks "is this feature switched on?". It checks one or more properties under an optional prefix. With havingValue the property must equal that value; without it, any value except false matches. matchIfMissing = true makes the bean active when the property is absent, which is useful for features that are on by default. It is ideal for feature flags and environment-specific beans, for example payments.mock.enabled=true in a test environment.

@ConditionalOnClass asks "is the library available?". A shared library can offer Redis support only when the application added the Lettuce driver. Use the name attribute with a fully qualified string when the class might be missing, because referencing a missing class literal on a @Bean method can fail; on a configuration class Boot reads the annotation from bytecode metadata safely.

@ConditionalOnMissingBean asks "has someone already provided this?". It lets a library or auto-configuration register a default that backs off when the application defines its own bean of that type (or name). Because it depends on what is registered at evaluation time, it belongs in auto-configuration, which runs after user configuration.

Together they express: "if the library is present, and the feature is enabled, and the user hasn't defined their own, create the default bean".

How it works

  1. Boot evaluates class conditions first, as they are cheap and can be checked before loading classes.
  2. Property conditions read the Environment (YAML, env vars, command line).
  3. Bean conditions inspect the bean factory for existing definitions.
  4. All conditions on a definition must match for it to be registered.
  5. Results appear in the conditions report.

Example

@AutoConfiguration
@ConditionalOnClass(name = "io.lettuce.core.RedisClient")
public class RateLimiterAutoConfiguration {

    @Bean
    @ConditionalOnProperty(prefix = "ratelimit", name = "enabled",
                           havingValue = "true", matchIfMissing = true)
    @ConditionalOnMissingBean(RateLimiter.class)
    RateLimiter redisRateLimiter(RedisConnectionFactory cf) {
        return new RedisRateLimiter(cf);
    }
}
ratelimit:
  enabled: false   # turns the default off in this service

Common mistakes

  • Forgetting matchIfMissing and wondering why the bean never appears.
  • Expecting havingValue = "true" to match TRUE written differently, or yes.
  • Using @ConditionalOnMissingBean in application configuration with unpredictable order.
  • Referencing a class literal in @ConditionalOnClass on a bean method when that class may be absent.

How to answer in the interview

"OnProperty registers a bean only when a property has a given value, with havingValue and matchIfMissing; I use it for feature flags. OnClass registers it only when a class is on the classpath, so a library can support Redis only if the Redis driver is present. OnMissingBean registers a default only if the application hasn't defined its own bean, so user configuration wins. Auto-configurations usually combine all three: library present, feature enabled, and no user-defined bean."

Likely follow-up questions

  • Why put OnMissingBean in auto-configuration? Auto-configuration runs after user config, so the check sees the user's beans.
  • Match on type or name? Both are supported: value/type or name.
  • Multiple properties? name = {"a", "b"} requires all to match.
