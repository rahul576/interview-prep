Deployments to the whole cluster suddenly fail with errors calling an admission webhook. What happened and how do you prevent it?

Kubernetes · scenario · levels mid, senior

In one line

The API server must call a validating or mutating admission webhook and the call fails; with failurePolicy: Fail every matching request is rejected, usually because the webhook backend is down, unreachable, or has an expired or mismatched TLS certificate; prevent it with HA, short timeouts, namespace exclusions and certificate automation.

Detailed explanation

Admission webhooks are configured cluster-wide in ValidatingWebhookConfiguration and MutatingWebhookConfiguration objects. For every matching create or update, the API server makes an HTTPS call to the webhook's Service. If the call fails or times out, failurePolicy decides: Ignore admits the request, Fail rejects it. Policy engines (Kyverno, Gatekeeper), service meshes and cert-manager install such webhooks, often matching all pods in all namespaces, so a single broken webhook can block every deployment in the cluster.

The error message names the webhook, which tells you where to look. Common causes: the webhook pods are crashing, were evicted or scaled to zero; the Service has no endpoints; a NetworkPolicy or firewall blocks the control plane from reaching the pods (common on managed clusters where the control plane is outside the node network and needs a specific port allowed); the serving certificate expired or the caBundle in the configuration no longer matches; or the webhook is so slow that timeoutSeconds is exceeded.

A nasty variant is a deadlock: the webhook's own pods are covered by the webhook, so when they die, their replacements cannot be admitted because the webhook is down. That is why the webhook's namespace and kube-system should be excluded with a namespaceSelector.

How it works

  1. Read the error: it includes the webhook name and the failure (connection refused, x509, timeout).
  2. kubectl get validatingwebhookconfigurations,mutatingwebhookconfigurations to find it.
  3. Check backend pods, Service endpoints, logs and network policies.
  4. Check certificate expiry and the caBundle.
  5. Short-term relief: temporarily set failurePolicy: Ignore or delete the configuration if non-critical.
  6. Fix and restore; then harden.

Example

apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingWebhookConfiguration
metadata:
  name: policy-webhook
  annotations: { cert-manager.io/inject-ca-from: policy/policy-webhook-cert }
webhooks:
  - name: validate.policy.example.com
    failurePolicy: Fail
    timeoutSeconds: 5
    sideEffects: None
    admissionReviewVersions: ["v1"]
    clientConfig:
      service: { name: policy-webhook, namespace: policy, path: /validate }
    namespaceSelector:
      matchExpressions:
        - key: kubernetes.io/metadata.name
          operator: NotIn
          values: ["kube-system", "policy"]
    rules:
      - { apiGroups: ["apps"], apiVersions: ["v1"], operations: ["CREATE", "UPDATE"], resources: ["deployments"] }

Common mistakes

  • Webhook running as a single replica with no PDB.
  • Not excluding its own namespace, causing deadlock.
  • Default 10-second timeouts making every API write slow.
  • Manual certificates that silently expire.
  • No alerts on apiserver_admission_webhook_rejection_count or webhook latency.

How to answer in the interview

"That error means the API server has to call a webhook before admitting objects, the call fails, and with failurePolicy Fail everything matching is rejected. I find the webhook from the error and the webhook configurations, then check its pods, Service endpoints and network policies between the control plane and pods, and its certificate, since an expired cert or stale CA bundle is common. For immediate relief I can set failurePolicy to Ignore temporarily if the policy isn't critical. To prevent it: multiple replicas with a PDB, short timeouts, a namespaceSelector excluding kube-system and the webhook's own namespace, cert-manager for certificates, and alerts on webhook errors and latency."

Likely follow-up questions

  • Why can it deadlock? If the webhook covers its own namespace, its replacement pods cannot be admitted while it is down.
  • When is Fail correct? For security-critical policy where admitting unchecked objects is worse than an outage.
  • What are ValidatingAdmissionPolicies? In-process CEL rules (GA in 1.30) that avoid webhook network calls entirely.
