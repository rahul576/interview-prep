A hospital wants an assistant that reads patient summaries through MCP. How do you design access?

MCP Servers · design · levels lead

In one line

The clinician signs in with hospital identity and MFA, the MCP server acts on behalf of that clinician so the EHR's existing access rules decide which patients they can see, tools are read-only and return the minimum necessary data, every access is audited (HIPAA-style), data stays in approved environments with no external servers in the session, and break-the-glass access is justified and reviewed.

Detailed explanation

Clinical data is among the most sensitive data there is, and hospitals already have mature access rules: clinicians see patients they have a care relationship with, role-based access distinguishes nurses, physicians and administrators, and every access is logged. The assistant must inherit those rules, not invent new ones. The model must never be the component deciding who may see what.

Identity and delegation. The clinician authenticates to the assistant with the hospital IdP and MFA. The MCP server receives a token for that clinician and calls the EHR API (for example a FHIR API) on their behalf, using delegated authorization such as SMART on FHIR scopes. The EHR enforces care-relationship and role checks. If the clinician could not open the chart in the EHR, the assistant cannot either.

Minimum necessary. Tools are read-only and task-shaped: get_patient_summary returns active problems, current medications, allergies and recent results, not the entire record with psychotherapy notes and billing. Sensitive categories (mental health, HIV status, substance use, genetic data) follow stricter rules.

Audit. Every access is logged with clinician, patient, purpose, tool and time, reviewed by privacy monitoring for unusual patterns, as HIPAA and similar regulations require.

Environment. The model and host run in an approved environment under appropriate agreements (for example a BAA in the US), with data residency respected. No external or unvetted servers in the same session, so patient data cannot be copied out.

Break-the-glass. Emergency access to a patient without a care relationship, if offered, requires an explicit justification, is time-limited and triggers review, exactly as in the EHR.

How it works

  1. Clinician signs in with SSO + MFA; host gets a token for the clinical MCP server.
  2. Server exchanges it for a delegated EHR token with read scopes.
  3. Clinician asks about a patient; server calls the EHR as that clinician.
  4. EHR returns data only if access rules allow; server trims to the minimum needed.
  5. Server writes an audit event; result goes to the model in the approved environment.

Example

Tool: get_patient_summary(patient_id)
Scopes: user/Condition.read user/MedicationRequest.read user/AllergyIntolerance.read user/Observation.read
Returns: active conditions, current meds, allergies, last 5 lab results (with dates)
Excludes: behavioural health notes, full history, billing
Audit: {clinician, patient, tool, purpose:"treatment", ts}
Denied example: "You do not have an active care relationship with this patient.
                 Use the EHR break-the-glass workflow if this is an emergency."

Common mistakes

  • A service account that can read all patients, with access checks in the prompt.
  • Returning full records "for better answers".
  • Allowing web search or external tools in clinical sessions.
  • Logging full clinical content in application logs.

How to answer in the interview

"The server has to enforce the same rules as the clinical systems. The clinician signs in with the hospital IdP and MFA, and the MCP server acts on behalf of that clinician, so they only see patients they have a care relationship with, enforced by the EHR API, not by the model. Tools are read-only and return the minimum necessary data, like active conditions and medications, rather than the full record. Every access is audited with user, patient, purpose and timestamp, as HIPAA requires, and monitored for unusual access. The model and data stay in approved environments with the right agreements, with no external servers in the same session. Break-the-glass access requires justification and triggers review."

Likely follow-up questions

  • Patient the clinician is not treating? The EHR denies it; the tool returns a clear message pointing to break-the-glass.
  • Write access later? Draft notes for clinician sign-off only, never autonomous writes.
  • Model hallucination risk? Show sources with dates and keep the clinician responsible for decisions.
