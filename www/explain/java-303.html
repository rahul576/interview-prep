How does Spring handle circular dependencies, and how should you fix them?

Spring Framework · concept · levels mid, senior

In one line

A constructor-injection cycle (A needs B, B needs A) cannot be resolved and fails at startup; field and setter cycles used to be patched with early references, but Spring Boot 2.6+ prohibits circular references by default. @Lazy or setter injection only hide it; the real fix is redesign: extract a third component, invert a dependency, or use events.

Detailed explanation

To create A, Spring needs B; to create B, it needs A. With constructor injection neither can be constructed first, so Spring throws BeanCurrentlyInCreationException and Boot prints a diagram of the cycle ("The dependencies of some of the beans in the application context form a cycle").

With field or setter injection, Spring historically resolved singleton cycles using a three-level cache of early bean references: it instantiates A, exposes an early reference, injects that into B, then finishes A. This works but means B may see A before it is fully initialised, and with proxies it can produce subtle bugs (B holding the raw A, not the transactional proxy). Since Spring Boot 2.6, spring.main.allow-circular-references defaults to false, so such cycles fail too. You can switch it back on, but that is a temporary migration aid.

Workarounds:

  • @Lazy on one injection point injects a proxy that resolves the real bean on first use. It breaks the cycle at startup but keeps the coupling.
  • Setter injection with the flag re-enabled.
  • ObjectProvider<B> to resolve lazily.

The proper fix is design, because a cycle means two classes depend on each other's details, so neither can be understood, tested or changed alone:

  1. Extract the shared logic into a third bean C that both depend on.
  2. Merge the classes if they are really one responsibility.
  3. Invert the dependency with an interface owned by the lower layer.
  4. Decouple with events: A publishes an OrderPlaced event; B listens instead of A calling B and B calling A.
  5. Check layering: services should not call controllers, repositories should not call services.

How it works

  1. Spring starts creating A and marks it "in creation".
  2. Resolving A's dependency triggers creation of B.
  3. B requires A, which is still in creation.
  4. Constructor injection: exception. Field injection with circular refs allowed: early reference injected.
  5. Boot's failure analyser prints the cycle for you to fix.

Example

// Cycle: OrderService -> CustomerService -> OrderService
@Service class OrderService {
    OrderService(CustomerService customers) { ... }
    void place(Order o) { ...; customers.updateLoyalty(o.customerId()); }
}
@Service class CustomerService {
    CustomerService(OrderService orders) { ... }   // only needed for order count
}

// Fix: extract the shared query into a third bean and use an event for loyalty
@Component class OrderStats {
    OrderStats(OrderRepository repo) { ... }
    long countFor(long customerId) { ... }
}
@Service class CustomerService {
    CustomerService(OrderStats stats) { ... }
    @EventListener void on(OrderPlaced e) { updateLoyalty(e.customerId()); }
}
@Service class OrderService {
    OrderService(ApplicationEventPublisher events) { ... }
    void place(Order o) { ...; events.publishEvent(new OrderPlaced(o.customerId())); }
}

Common mistakes

  • Setting allow-circular-references=true permanently.
  • Sprinkling @Lazy to silence startup errors.
  • Switching to field injection specifically so cycles "work".
  • Ignoring cycles between packages or modules, which cause the same tangle at a larger scale.

How to answer in the interview

"With constructor injection, if A needs B and B needs A, Spring can't construct either, so startup fails with BeanCurrentlyInCreationException. Field and setter cycles used to be resolved with early references, but since Spring Boot 2.6 circular references are prohibited by default. Workarounds like @Lazy or setter injection hide the problem. A cycle usually means responsibilities are mixed, so I fix the design: extract the shared logic into a third component, invert one dependency behind an interface, or decouple with application events so one side just publishes and the other listens."

Likely follow-up questions

  • Why is a circular dependency a design smell rather than just a Spring problem? The classes cannot be understood, tested or reused independently; it would be tangled without Spring too.
  • How do you detect cycles early? Constructor injection, ArchUnit or Spring Modulith tests for package cycles.
  • Can prototype beans have cycles? No, Spring cannot resolve prototype cycles at all.
