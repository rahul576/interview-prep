How do you version datasets for machine learning?

MLOps · concept · levels mid, senior

In one line

Version data so every training run references an immutable snapshot: DVC stores pointers in Git to data in object storage, Delta Lake and Apache Iceberg provide time travel on tables, lakeFS adds Git-like branches and commits for data lakes, managed platforms offer dataset versions, and large data never goes into Git.

Detailed explanation

Training data changes all the time: new records arrive, labels are corrected, upstream pipelines are fixed, and schemas evolve. If a run simply reads "the customers table", you cannot later reproduce it, explain its behaviour or compare it fairly.

DVC (Data Version Control) works alongside Git. Large files or directories are hashed and stored in a remote such as S3, Azure Blob or GCS, while Git stores small .dvc metafiles with the hashes. Checking out a commit and running dvc pull restores the matching data, so one commit identifies code and data.

Lakehouse table formats version tables natively. Delta Lake and Apache Iceberg record every commit as a new table version or snapshot and support time travel queries, so a run records version 412 or a timestamp and can re-read exactly that state. Old versions are kept only until retention and vacuum settings delete their files, so training snapshots you must keep need longer retention or a tag.

lakeFS adds Git-like branches, commits and merges over an object-store data lake. This enables CI for data: test a pipeline change on a branch, merge only if it passes.

Managed platforms such as Azure ML data assets also offer dataset versioning. Whatever the tool, never commit large data into Git, make snapshots immutable, and record the version in experiment tracking and the model registry.

How it works

  1. Choose a versioning mechanism matching your data storage.
  2. Create a version or snapshot when preparing training data.
  3. Training reads that specific version only.
  4. The run logs the version ID with its metrics.
  5. Retention policies keep versions referenced by production models.

Example

dvc init
dvc add data/train.parquet            # creates data/train.parquet.dvc
git add data/train.parquet.dvc .gitignore && git commit -m "Training data 2026-11-01"
dvc push                              # uploads data to the S3 remote
-- Delta Lake time travel: read exactly the version used by the run
SELECT * FROM ml.churn_features VERSION AS OF 412;
-- Iceberg: SELECT * FROM ml.churn_features FOR VERSION AS OF 8744120338461295512;

Common mistakes

  • Training from live tables without recording a version.
  • Committing datasets directly into Git.
  • Vacuuming Delta tables and deleting versions production models depend on.
  • Versioning raw data but not the processed training set.

How to answer in the interview

"Training data changes constantly, so a model is only reproducible if the run references a specific, immutable version of its data. DVC stores small metadata files in Git that point to data in object storage, so a commit identifies both code and data. Lakehouse formats like Delta Lake and Iceberg keep table history with time travel, so the run records the table version it read. lakeFS adds Git-like branches and commits on a data lake, which also lets us test pipeline changes in isolation. Managed platforms have dataset versions too. Whatever the tool, the run logs the exact version, and large data never goes into Git."

Likely follow-up questions

  • How do you handle GDPR deletion requests with versioned data? Delete from current data, purge old versions or snapshots within the legal deadline, and retrain affected models if required.
  • DVC or Delta Lake? DVC for file-based datasets alongside code; Delta or Iceberg for large tabular data in a lakehouse.
  • What retention do you need? At least as long as any production model trained on that version may need audit or reproduction.
