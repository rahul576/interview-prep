How can REST APIs and microservices be secured?

Security · concept · levels mid

In one line

Secure APIs with defence in depth: TLS everywhere, OAuth 2 / OIDC with short-lived JWTs validated by each service, authorization at gateway and service level including object-level checks, a gateway for rate limiting and request limits, input validation, secrets management and mTLS between services.

Detailed explanation

Microservices widen the attack surface: many endpoints, internal traffic and many teams. No single control is enough, so security is layered.

Transport: TLS 1.2+ on all external traffic and, inside the cluster, mTLS (often via a service mesh) so services prove their identity and internal traffic cannot be sniffed. Authentication: users sign in through an identity provider using OpenID Connect; APIs accept access tokens and validate signature, issuer, audience and expiry as an OAuth 2 resource server. Service-to-service calls use client credentials tokens or token exchange, never shared static keys.

Authorization: coarse checks at the API gateway (route requires scope orders.write), and again inside each service because the gateway can be bypassed internally. The OWASP API Security Top 10 (2023) puts Broken Object Level Authorization (BOLA) first, so services must check that the caller owns or may access each specific object, and also restrict which properties may be read or written (mass assignment).

Gateway concerns: rate limiting and quotas against abuse, request size limits, schema validation, CORS for browser clients, and a WAF at the edge. Input and output: Bean Validation on DTOs, parameterised queries, generic error messages without stack traces. Secrets: a vault or cloud secret manager, rotation, workload identity. Monitoring: log authentication failures, access denials and unusual patterns, with alerting, and keep an inventory of all APIs, including old versions.

How it works

  1. Client gets a token from the identity provider (authorization code with PKCE).
  2. Request hits the edge: WAF, TLS termination, gateway validates the token and rate-limits.
  3. Gateway applies coarse route-level scope checks and forwards the token.
  4. Service validates the token again and applies method and object-level authorization.
  5. Internal calls use mTLS plus a service token; all security events are logged.

Example

# Spring Cloud Gateway route with rate limiting (Redis)
spring:
  cloud:
    gateway:
      server:
        webflux:
          routes:
            - id: orders
              uri: lb://orders-service
              predicates:
                - Path=/api/orders/**
              filters:
                - name: RequestRateLimiter
                  args:
                    redis-rate-limiter.replenishRate: 20
                    redis-rate-limiter.burstCapacity: 40
                - name: RequestSize
                  args:
                    maxSize: 1MB

Common mistakes

  • Trusting every request that comes from inside the network.
  • Checking authorization only at the gateway.
  • Returning whole entities so clients see or can set internal fields.
  • Forgotten old API versions still deployed without protection.
  • No rate limiting on login and expensive endpoints.

How to answer in the interview

"I use defence in depth. All traffic is encrypted with TLS, and inside the cluster mTLS through a service mesh. Users authenticate with OpenID Connect, and APIs accept short-lived JWT access tokens that Spring Security validates as a resource server: signature, issuer, audience and expiry. Authorization happens at the gateway for coarse scopes and again in each service with @PreAuthorize and object-level ownership checks, because BOLA is the top API risk. The gateway also does rate limiting and request size limits. I validate input, use parameterised queries, return generic errors, keep secrets in a vault, and use client credentials or token exchange plus mTLS between services, with security events logged and monitored."

Likely follow-up questions

  • How do you protect against BOLA? Check ownership on every object access, scope queries by the caller, use non-guessable ids as an extra.
  • Where do you rate-limit? At the gateway per client or user, with stricter limits on login and costly endpoints.
  • API keys or OAuth? API keys identify a client but are static; OAuth tokens are short-lived and scoped.
