Changing the VM size of an AKS node pool forces replacement of the pool. How do you make the change without downtime?

Terraform · scenario · levels mid, senior

In one line

Because changing the VM size of an AKS node pool has traditionally forced replacement, the zero-downtime approach is to add a new pool with the new size, cordon and drain the old nodes while PodDisruptionBudgets keep apps available, then remove the old pool from code.

Detailed explanation

In the azurerm provider, vm_size on azurerm_kubernetes_cluster_node_pool (and on the default node pool) has historically been a ForceNew attribute: Terraform plans to destroy the pool and create a new one. Destroying a pool deletes all its nodes at once, so every pod on it is evicted simultaneously, ignoring the gradual rescheduling you want.

The blue/green node pool pattern avoids this. You add a second pool resource with the new VM size and the same labels, taints and node selectors, so workloads can land on it. After applying, you cordon the old nodes so nothing new is scheduled there, then drain them one by one. Drain respects PodDisruptionBudgets, so a deployment with minAvailable keeps serving while pods move. The new pool must have enough capacity, or autoscaling headroom, for all moved pods.

When the old pool is empty, remove it from the code and apply. For the system node pool, AKS requires at least one system-mode pool at all times, so create the new system pool first, then remove the old one. For the cluster's default node pool, newer azurerm versions offer temporary_name_for_rotation, which lets the provider rotate the default pool through a temporary pool automatically.

AKS has also been adding support for resizing node pools in place via surge-based upgrades, so check the current AKS documentation and provider version before choosing the manual pattern.

How it works

  1. Add a new node pool resource with the new vm_size, same labels and taints.
  2. terraform apply and wait until the new nodes are Ready.
  3. kubectl cordon all old-pool nodes.
  4. kubectl drain them gradually; PDBs throttle evictions.
  5. Verify workloads are healthy on the new pool.
  6. Remove the old pool from Terraform and apply.

Example

resource "azurerm_kubernetes_cluster_node_pool" "apps_v2" {
  name                  = "appsv2"
  kubernetes_cluster_id = azurerm_kubernetes_cluster.main.id
  vm_size               = "Standard_D8s_v5"
  auto_scaling_enabled  = true
  min_count             = 3
  max_count             = 10
  node_labels           = { workload = "apps" }
}
kubectl cordon -l agentpool=apps
for n in $(kubectl get nodes -l agentpool=apps -o name); do
  kubectl drain "$n" --ignore-daemonsets --delete-emptydir-data --timeout=10m
done

Common mistakes

  • Applying a plan that says "must be replaced" on a node pool in production.
  • Forgetting labels or taints on the new pool, so pods stay Pending.
  • Workloads without PDBs or with a single replica, which go down during drain.
  • Not checking quota for the new VM family before creating the pool.

How to answer in the interview

"Changing the VM size of a node pool has typically forced Terraform to destroy and recreate it, evicting every pod at once. Instead I add a new pool with the new size and the same labels and taints, apply, then cordon the old nodes and drain them gradually, so PodDisruptionBudgets keep applications available while pods move. Once the old pool is empty I remove it from the code. For system pools I make sure one system pool always exists, and for the default pool I'd use temporary_name_for_rotation. I'd also check whether the current AKS version supports resizing through a surge upgrade first."

Likely follow-up questions

  • How do you rename a node pool in code without destroying it? Change the Terraform address with a moved block; the AKS pool name itself is immutable.
  • What if pods do not reschedule? Check requests vs new node capacity, taints and affinity, and PDBs that are too strict.
  • What about quota? Request vCPU quota for the new VM family before the change.
