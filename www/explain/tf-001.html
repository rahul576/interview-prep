How do import blocks work in Terraform, and why are they better than the terraform import command?

Terraform · concept · levels mid, senior

In one line

An import block (Terraform 1.5+) declares in code which existing object (id) maps to which resource address (to), so importing becomes part of a reviewed plan and apply, with optional config generation and for_each support, unlike the CLI command that changes state immediately.

Detailed explanation

Most teams adopt Terraform with infrastructure that already exists: resources created by hand, by scripts or by another tool. To manage them, Terraform must record them in state under a resource address. The old way, terraform import aws_s3_bucket.logs my-logs-bucket, writes to state immediately, from whoever runs it, with no plan, no review and no record in Git. In a team with several environments that is error-prone: someone imports into the wrong workspace, or forgets the other environments.

An import block turns this into normal, declarative configuration. You write import { to = aws_s3_bucket.logs id = "my-logs-bucket" } next to the resource block. On terraform plan, Terraform reads the real object and shows "will be imported", together with any differences between the real object and your configuration. The change is reviewed in a pull request and applied by the pipeline like any other.

If you do not have configuration yet, terraform plan -generate-config-out=generated.tf writes a starting configuration from the real object's attributes. It is a draft: you clean it up, remove computed or default values, and replace hard-coded IDs with references. Since Terraform 1.7, import blocks support for_each, so you can import many similar objects from a map. The id can also be an expression, for example built from variables per environment, and newer versions let providers that support resource identity use an identity object instead of a string id.

How it works

  1. Find the provider's import ID format in the resource documentation.
  2. Add an import block (and the resource block, or generate it).
  3. Run terraform plan; check "import" and that no unintended update or replace appears.
  4. Adjust configuration until the plan shows only the import.
  5. Merge and apply through the pipeline in each environment.
  6. Remove import blocks later as cleanup.

Example

locals {
  buckets = { logs = "acme-prod-logs", assets = "acme-prod-assets" }
}

import {
  for_each = local.buckets
  to       = aws_s3_bucket.this[each.key]
  id       = each.value
}

resource "aws_s3_bucket" "this" {
  for_each = local.buckets
  bucket   = each.value
}
terraform plan -generate-config-out=generated.tf   # when no resource block exists yet

Common mistakes

  • Committing generated configuration without cleaning it up.
  • Applying when the plan shows an update or replacement along with the import.
  • Using the CLI import in one environment and forgetting the others.

How to answer in the interview

"Since Terraform 1.5 I can declare an import block with to, the resource address, and id, the cloud identifier. The import then happens during plan and apply, so it's reviewed in a pull request, visible in the plan and run by the same pipeline as every other change. If I don't have configuration yet, plan -generate-config-out writes a starting point that I clean up. Since 1.7 import blocks support for_each, so I can import a whole map of resources at once. The old terraform import command changes state immediately from someone's laptop, with no review, which is risky in a team."

Likely follow-up questions

  • What do you check in generated configuration? Remove computed and default attributes, replace IDs with references, add variables and check no secrets are hard-coded.
  • Can you import into a module? Yes, to = module.network.aws_vpc.main, but import blocks must be in the root module.
  • How do you import at scale? for_each imports, or Terraform 1.14's terraform query to discover resources and generate config.
