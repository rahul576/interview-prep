What is the Backend-for-Frontend (BFF) pattern, and when do you use API composition?

Microservices · concept · levels senior, lead

In one line

A Backend-for-Frontend (BFF) is a dedicated thin backend per client type that tailors and aggregates data for that UI, and API composition is the technique of calling several services and joining results in memory to answer one query; both risk duplicated logic and an extra hop.

Detailed explanation

A general-purpose API rarely suits every client. A mobile app on a slow network wants one compact call per screen; a web dashboard wants richer data; a partner API wants stability. Forcing all of them through one API leads to over-fetching, chatty clients and an API that changes for everyone whenever one UI changes.

The BFF pattern (popularised by SoundCloud and Sam Newman) gives each frontend its own backend, usually owned by the frontend team. The BFF calls downstream services, aggregates and reshapes data into exactly what the screen needs, and can apply client-specific concerns such as pagination styles or versioning for old app releases. It is also a good place for security in single-page apps: the BFF performs the OAuth2 login as a confidential client, keeps access and refresh tokens server-side, and gives the browser only an HTTP-only, SameSite session cookie (the "token handler" approach recommended by current OAuth browser guidance), so tokens are not exposed to JavaScript.

API composition is how a BFF, gateway or composer service implements queries that span services in a database-per-service architecture: call the order service, customer service and shipping service (ideally in parallel), then join the results in memory. It is simple and always fresh, but latency equals the slowest call, availability depends on all of them, and large joins in memory are inefficient. For heavy or frequent cross-service queries, a CQRS read model built from events is better.

The risks: logic duplicated across BFFs, business rules creeping in, and an extra network hop. Keep BFFs thin: composition and presentation only, with domain rules in the services. Shared concerns go to the gateway.

How it works

  1. Mobile app calls GET /mobile/home.
  2. BFF validates the session, picks the user's token.
  3. BFF calls profile, orders and recommendations in parallel with timeouts.
  4. Missing optional parts degrade to defaults.
  5. BFF maps results to a compact DTO and returns one response.

Example

@GetMapping("/mobile/home")
public Mono<HomeScreen> home(@AuthenticationPrincipal Jwt jwt) {
    String userId = jwt.getSubject();
    Mono<Profile> profile = profileClient.get(userId);
    Mono<List<OrderSummary>> orders = orderClient.recent(userId, 3);
    Mono<List<Product>> recs = recClient.forUser(userId)
            .timeout(Duration.ofMillis(300))
            .onErrorReturn(List.of());                 // optional part degrades
    return Mono.zip(profile, orders, recs)
               .map(t -> new HomeScreen(t.getT1().firstName(), t.getT2(), t.getT3()));
}

Common mistakes

  • Putting business rules in the BFF.
  • Calling services sequentially instead of in parallel.
  • One BFF per screen, creating service sprawl.
  • No timeouts or fallbacks for optional data.

How to answer in the interview

"The BFF pattern gives each client type, like web and mobile, its own thin backend, usually owned by the frontend team, which aggregates and reshapes data so the client gets exactly what a screen needs in one call. For browser apps it is also where I handle OAuth, keeping tokens server-side and giving the browser only a secure cookie. API composition is the technique of calling several services, ideally in parallel, and joining results in memory to answer a query when data is spread across services. Risks are duplicated logic and an extra hop, so BFFs stay thin, and for heavy cross-service queries I build a CQRS read model instead."

Likely follow-up questions

  • When would you prefer GraphQL over several BFFs? Many clients with varied data needs and a team able to manage schema and query-cost controls.
  • API composition vs CQRS read model? Composition is fresh but slow and fragile at scale; read models are fast but eventually consistent.
  • How is a BFF different from an API gateway? The gateway handles generic edge concerns; a BFF contains client-specific composition.
