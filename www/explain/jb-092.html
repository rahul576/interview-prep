How would you troubleshoot an application that frequently logs NullPointerException errors?

Troubleshooting · scenario · levels senior, lead

In one line

Aggregate and group the NPEs by stack trace to find the top sources, use helpful NullPointerException messages (JDK 14+) to see exactly what was null, trace the null to its origin (input, external response, database, config, wiring), reproduce it in a test and fix the root cause, then prevent recurrence with boundary validation, Optional, non-null contracts and static analysis such as NullAway.

Detailed explanation

Frequent NPEs are usually a few bugs repeated thousands of times, not thousands of bugs. Fix them in order of impact.

Aggregate: in Kibana, Grafana Loki, Sentry or an APM, group errors by exception type plus top stack frame (error tracking tools fingerprint this automatically), count occurrences and affected users, and check when each started (often with a release). Pick the top two or three.

Read the message: since JEP 358 (JDK 14, on by default from JDK 15), NPE messages say precisely what failed, for example Cannot invoke "Address.getCity()" because the return value of "Customer.getAddress()" is null. That removes the guesswork about which reference in a chained call was null. Make sure logging keeps the full stack trace and cause chain.

Trace to the origin: the line that throws is rarely where the bug is. Ask where the null came from:

  • a request with a missing optional field that the code treats as mandatory;
  • an external API that sometimes omits a field or returns 204;
  • a nullable database column or a legacy row with missing data;
  • Map.get or a repository method returning null for a missing key;
  • a missing configuration property bound to null;
  • a dependency not injected (field injection in a class created with new, or a Mockito @InjectMocks gap in tests);
  • concurrency: a field read before initialisation.

Reproduce and fix: write a unit test with the problematic input that throws the NPE, then fix the root cause: validate and reject at the boundary (return 400), model optionality explicitly, supply defaults, or fix the data. Do not scatter if (x != null) checks or catch the NPE; that hides the bug and produces wrong results silently.

Prevent: Bean Validation (@NotNull, @Valid) on DTOs; Optional as a return type for "may be absent"; constructor injection with required dependencies; Objects.requireNonNull for fail-fast contracts; JSpecify @Nullable/@NullMarked annotations (adopted by Spring Framework 7) checked by NullAway or Error Prone at compile time; Kotlin or records with validation for new code.

How it works

  1. Group NPEs by fingerprint; rank by frequency and impact.
  2. Read the helpful NPE message and stack trace.
  3. Trace the null value back to its source.
  4. Reproduce with a failing unit test.
  5. Fix at the origin; return meaningful errors for bad input.
  6. Add validation, nullness annotations and static analysis.

Example

  the return value of "com.shop.Address.getCountryCode()" is null
    at com.shop.tax.TaxService.rateFor(TaxService.java:42)
    at com.shop.checkout.CheckoutService.total(CheckoutService.java:88)

// Root cause: partner requests may omit countryCode. Validate at the boundary.
public record AddressDto(@NotBlank String street,
                         @NotBlank @Size(min = 2, max = 2) String countryCode) { }

@PostMapping("/checkout")
public ResponseEntity<?> checkout(@Valid @RequestBody CheckoutRequest req) { ... }

// Regression test
@Test
void rejectsAddressWithoutCountry() throws Exception {
    mvc.perform(post("/checkout").contentType(APPLICATION_JSON).content(withoutCountry()))
       .andExpect(status().isBadRequest());
}

Common mistakes

  • Catching NullPointerException or wrapping everything in null checks, hiding the real bug.
  • Fixing the line that throws rather than where the null originates.
  • Returning null from methods instead of Optional or empty collections.
  • Losing stack traces by logging only e.getMessage().

How to answer in the interview

"First I aggregate the logs and group the NPEs by stack trace and frequency, so I fix the few top sources rather than chasing every occurrence, and check whether they started with a release. On modern JDKs helpful NPE messages tell me exactly which variable or method result was null. Then I trace that null to its origin: a missing request field, an unexpected external response, a nullable column, a missing config value or a dependency that wasn't injected. I reproduce it in a unit test and fix the root cause instead of adding null checks everywhere. To prevent it, I validate input at the boundary, use Optional for absent results, rely on constructor injection and run static analysis like NullAway."

Likely follow-up questions

  • Why is catching NPE the wrong fix? It hides a programming error and lets the system continue with invalid state.
  • When should you use Optional? As a return type for possibly absent values, not for fields or parameters.
  • What are helpful NPE messages? JEP 358 messages naming the null expression, default since JDK 15.
