Search latency in your Elasticsearch cluster has doubled. How do you troubleshoot it?

Elasticsearch · scenario · levels senior, lead

In one line

Work top-down: check node health (heap/GC, CPU, disk I/O, search thread pool queues and rejections, hot nodes), then find the slow queries with slow logs and the profile API. Look for expensive patterns (leading wildcards, regex, scripts, deep or high-cardinality aggregations, too many shards), and for indexing and merges competing with search. Then fix the queries, shards and capacity.

Detailed explanation

"Latency doubled" has three broad causes: the cluster got weaker (resources), the queries got heavier, or the load changed. Correlate the timeline with deployments, traffic, data growth and index changes first.

1. Resource level (_nodes/stats, _cat/nodes, _cat/thread_pool/search?v, monitoring):

  • JVM heap and GC: heap above 75–85% and long old-GC pauses stall searches. Typical causes are fielddata, huge aggregations or too many shards.
  • CPU and disk I/O: saturated disks (merges, or cold data on slow disks) and CPU throttling in containers.
  • Search thread pool: a growing queue and rejected counts mean the node can't keep up.
  • Hot spots: one node much busier than the others because of uneven shard distribution, custom routing to a hot tenant, or a node with fewer resources.
  • GET _nodes/hot_threads shows what the CPU is actually doing.

2. Query level:

  • Enable search slow logs (index.search.slowlog.threshold.query.warn: 2s) to capture the slow requests.
  • Run the profile API ("profile": true) on a slow query to see time per shard, per query component and per aggregation.
  • Typical culprits: leading wildcards (*phone), regexp, scripts in queries or sorts, deep pagination, terms aggregations with huge size on high-cardinality fields, nested or has_child joins, and conditions in must that should be filter.

3. Data and indexing level:

  • Too many shards per query (searching logs-* across 2,000 shards), or shards grown far too large.
  • Heavy bulk indexing, frequent refreshes and segment merges compete for the same CPU and disk.
  • Lost cache efficiency (frequent refreshes invalidate caches, and now in filters prevents caching; use rounded now/m).

Fixes: move exact conditions into filter, replace leading wildcards with wildcard-type fields or n-grams, precompute fields at index time instead of using scripts, use search_after, raise refresh_interval (30 s) during bulk loads, right-size and rebalance shards, use dedicated hot nodes or replicas for read capacity, and isolate heavy tenants.

How it works

  1. Confirm the symptom: p50/p95/p99, which indices, since when, and what changed.
  2. Check node stats: heap, GC, CPU, disk, thread pool rejections, hot threads.
  3. Use slow logs to find the offending queries, then profile them.
  4. Check the shard count and sizes per query, and the indexing and merge load.
  5. Apply targeted fixes and verify with before and after metrics.
  6. Add guardrails: query timeouts, search.max_buckets, tenant limits, and alerts.

Example

GET _cat/thread_pool/search?v&h=node_name,active,queue,rejected
GET _nodes/stats/jvm,indices?filter_path=**.heap_used_percent,**.query_cache
GET _nodes/hot_threads
PUT /products/_settings
{ "index.search.slowlog.threshold.query.warn": "2s",
  "index.search.slowlog.threshold.fetch.warn": "1s" }
GET /products/_search
{ "profile": true, "query": { "wildcard": { "name": "*phone*" } } }
PUT /logs-bulk/_settings { "index.refresh_interval": "30s" }

Common mistakes

  • Adding nodes before identifying the expensive query.
  • Ignoring thread pool rejections and GC logs.
  • Leaving bulk reindex jobs running at peak hours.
  • Fixing averages while p99 stays bad (always look at the percentiles).

How to answer in the interview

"I'd first check what changed: deployments, traffic, data growth. Then node metrics: heap usage and GC pauses, CPU, disk I/O, and the search thread pool queue and rejections, to see if one node is a hot spot. Next I'd enable search slow logs to find the slow queries and run the profile API on them. The usual culprits are leading wildcards, regex, scripts, deep pagination, big aggregations on high-cardinality fields, too many shards per query, or heavy indexing and merges competing with search. Fixes are rewriting queries with filters and keyword fields, right-sizing shards, increasing the refresh interval during bulk loads, and adding replicas or nodes where capacity is genuinely short."

Likely follow-up questions

  • Isolating a noisy tenant with huge aggregations? Dedicated index or nodes (allocation filtering), per-tenant rate limits, search.max_buckets and timeouts.
  • Why does now hurt caching? It changes every millisecond. Round it (now/m) so filters are cacheable.
  • Replicas or more shards for read throughput? Replicas add read capacity. More shards add per-query overhead.
