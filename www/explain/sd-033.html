Design a distributed key-value store like DynamoDB or Cassandra.

Classic Design Problems · design · levels senior, lead

In one line

A Dynamo-style key-value store uses consistent hashing to partition, replicates to N nodes, offers tunable quorums (R + W > N), resolves conflicts with LWW or vector clocks, detects failures via gossip, and heals with hinted handoff, read repair and Merkle-tree anti-entropy.

Detailed explanation

Goals: get(key)/put(key, value) with high availability, horizontal scale and no single point of failure. Each piece solves one problem:

  • Partitioning: consistent hashing with virtual nodes, so nodes can join/leave with minimal data movement.
  • Replication: each key lives on N nodes (e.g. 3) in different racks/zones.
  • Consistency: with W write acks and R read replies, R + W > N guarantees overlap with the latest write. Lower values favour latency/availability.
  • Conflicts: concurrent writes during partitions. LWW with timestamps is simple but can drop writes; vector clocks detect concurrency and return siblings for the app (or a CRDT) to merge.
  • Membership/failure detection: gossip spreads node state without a central coordinator.
  • Healing: hinted handoff stores writes for a down node on a neighbour; read repair fixes stale replicas on read; anti-entropy compares Merkle trees to sync ranges cheaply.
  • Storage engine: commit log + memtable + SSTables (LSM tree), Bloom filters to skip files.

How it works

  1. Client (or coordinator) hashes key → finds N replicas on the ring.
  2. Write sent to all N; success after W acks (hints stored for unreachable nodes).
  3. Read from R replicas; return newest; repair stale ones.
  4. Background anti-entropy reconciles divergent ranges.

Example

N=3, W=2, R=2: survives one replica down for both reads and writes while still guaranteeing overlap. N=3, W=1, R=1: fastest, but reads may be stale.

Common mistakes

  • Assuming LWW is safe with unsynchronised clocks.
  • R + W ≤ N and expecting strong consistency.
  • Forgetting tombstones for deletes (and their garbage collection grace period).

How to answer in the interview

"Keys are spread with consistent hashing and replicated to three nodes across zones. Writes and reads use tunable quorums, so with R and W of two out of three, reads see the latest write and one node can be down. Conflicts are handled with vector clocks or last-writer-wins depending on the data. Gossip handles membership; hinted handoff, read repair and Merkle-tree anti-entropy keep replicas converging. Each node stores data in an LSM tree."

Likely follow-up questions

  • Range queries? Use an order-preserving partitioner or range partitioning (with hot-spot risk).
  • Why Merkle trees? Compare hashes top-down to find differing ranges without shipping all data.
  • Sloppy quorum? Count acks from fallback nodes during failures, improving availability.
