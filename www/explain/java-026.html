What is the difference between @Component, @Service, @Repository and @Controller?

Spring Framework · concept · levels entry, mid

In one line

All four are stereotype annotations detected by component scanning; @Service, @Repository and @Controller are specialisations of @Component. @Repository adds persistence exception translation, @Controller handles web requests (and @RestController adds @ResponseBody), and @Service marks business logic.

Detailed explanation

@Component is the generic marker: "this class is a Spring-managed bean". The others are meta-annotated with @Component, so component scanning finds them all, and they all create ordinary beans. The differences are partly semantic (they document the layer) and partly behavioural.

@Repository marks the data-access layer. Spring's PersistenceExceptionTranslationPostProcessor wraps such beans in a proxy that converts technology-specific exceptions (JDBC SQLException, Hibernate or JPA exceptions) into Spring's DataAccessException hierarchy, for example DuplicateKeyException or DataIntegrityViolationException. Callers can handle errors without depending on the database vendor. Spring Data repository interfaces get this translation automatically, even without the annotation.

@Controller marks a Spring MVC controller: RequestMappingHandlerMapping registers its @RequestMapping methods. By default return values are view names rendered by a template engine. @RestController = @Controller + @ResponseBody, so return values are serialised to JSON by message converters.

@Service has no extra behaviour in the framework today. It signals the service layer that holds business logic and orchestration, which improves readability, helps architecture tests (for example ArchUnit rules), and is the natural place for @Transactional boundaries and other aspects.

Use @Component for beans that do not fit a layer: mappers, schedulers, adapters, validators.

How it works

  1. @ComponentScan (included in @SpringBootApplication) searches the base package.
  2. Classes annotated with @Component or any meta-annotated stereotype become bean definitions.
  3. Post-processors add layer-specific behaviour: exception translation for @Repository, handler registration for @Controller.
  4. Beans are injected into each other by type.

Example

@RestController
@RequestMapping("/customers")
class CustomerController {
    private final CustomerService service;
    CustomerController(CustomerService service) { this.service = service; }
    @PostMapping CustomerDto create(@Valid @RequestBody NewCustomer c) { return service.register(c); }
}

@Service
class CustomerService {
    private final CustomerDao dao;
    CustomerService(CustomerDao dao) { this.dao = dao; }

    @Transactional
    public CustomerDto register(NewCustomer c) {
        try { return dao.insert(c); }
        catch (DuplicateKeyException e) { throw new EmailAlreadyUsedException(c.email()); }
    }
}

@Repository
class CustomerDao {
    private final JdbcTemplate jdbc;
    CustomerDao(JdbcTemplate jdbc) { this.jdbc = jdbc; }
    CustomerDto insert(NewCustomer c) { /* SQL insert */ return null; }
}

Common mistakes

  • Saying they are completely identical: @Repository and @Controller do behave differently.
  • Putting business logic in controllers or repositories.
  • Using @Controller for an API and forgetting @ResponseBody.
  • Placing @Transactional on controllers instead of services.

How to answer in the interview

"All four are stereotypes, and @Service, @Repository and @Controller are themselves annotated with @Component, so component scanning registers all of them as beans. The differences: @Repository marks data access and enables exception translation, turning SQL or JPA exceptions into Spring's DataAccessException hierarchy. @Controller marks a Spring MVC controller whose methods handle HTTP requests, normally returning views, and @RestController adds @ResponseBody so results become JSON. @Service has no extra behaviour but marks the business layer, which is where I put @Transactional. Plain @Component is for anything else, like mappers or adapters."

Likely follow-up questions

  • Where do you usually put @Transactional, and why? On service methods, since a business operation defines the unit of work.
  • Can you create your own stereotype? Yes, annotate a custom annotation with @Component.
  • Is @Repository needed on Spring Data interfaces? No, they are detected and translated automatically.
