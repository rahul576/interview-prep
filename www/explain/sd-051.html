Which caching strategy would you use for a product catalogue versus a user’s shopping cart, and why?

Scalability & Reliability · scenario · levels entry, mid, senior

In one line

Pick the caching strategy by read/write ratio and staleness tolerance: the product catalogue suits cache-aside with TTL plus a CDN; the shopping cart suits Redis as the durable primary store (or write-through), with prices re-validated at checkout.

Detailed explanation

The main strategies:

  • Cache-aside (lazy loading): app reads cache; on miss, reads DB and fills cache. Writes go to DB and delete the key. Simple, resilient (cache down = slower, not broken), but the first read after a change is a miss.
  • Read-through: the cache library loads from the DB itself; same idea, cleaner code.
  • Write-through: writes go to cache and DB synchronously; reads are always warm, writes are slower.
  • Write-back (write-behind): write to cache, flush to DB later; fastest writes, risk of losing data if the cache dies.

Catalogue: millions of reads, few updates, a few minutes of staleness is fine (except price/stock at checkout). Cache-aside with TTL + invalidation on product update events, plus CDN for pages and images.

Cart: per-user, written frequently, must not lose items, read mostly by its owner. Many shops keep active carts in Redis with AOF persistence and replicas as the system of record, and persist to the DB at checkout or on a schedule. Alternatively write-through to the DB. Write-back is risky unless the cache is durable.

How it works

  1. GET /product/42 → Redis → miss → DB → SET product:42 … EX 600.
  2. Product updated → event → DEL product:42 (+ CDN purge).
  3. POST /cart/items → Redis hash cart:{user} (persisted) → TTL 30 days.
  4. Checkout → read cart → fetch live prices/stock from source → order.

Example

def get_product(pid):
    data = redis.get(f"product:{pid}")
    if data: return json.loads(data)
    p = db.fetch_product(pid)
    redis.set(f"product:{pid}", json.dumps(p), ex=600 + random.randint(0, 60))
    return p

Common mistakes

  • Caching prices and charging the cached price.
  • Write-back with a non-persistent cache.
  • No TTL jitter (mass expiry).

How to answer in the interview

"For the catalogue I'd use cache-aside with a TTL and event-driven invalidation, plus a CDN, since it's read-heavy and tolerates slight staleness. The cart is per-user and write-heavy, so I'd store it in Redis with persistence and replication as its primary store, or write-through to the database. At checkout, price and stock are always re-read from the source of truth."

Likely follow-up questions

  • Why delete instead of update on write? Avoids races writing stale values.
  • Guest carts? Key by anonymous session ID, merge on login.
  • Read-through vs cache-aside? Same pattern; who owns the loading code.
