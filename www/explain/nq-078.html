How do threads communicate with one another in Java?

Concurrency · concept · levels mid

In one line

Threads in one JVM communicate through shared memory, so the real question is coordinating it safely: synchronized with wait/notify, Lock with Condition, and preferably higher-level tools such as BlockingQueue, Future/CompletableFuture, CountDownLatch, Semaphore, and volatile flags.

Detailed explanation

Unlike processes, threads share the heap, so "sending a message" just means one thread writes to an object another thread reads. Two things must be handled: visibility (the reader must see the write, which requires a happens-before edge) and coordination (the reader must know when data is ready, without busy-waiting).

Low level: a shared object guarded by synchronized, with wait() to sleep until a condition changes and notify()/notifyAll() to wake waiters. The explicit-lock equivalent is Lock with Condition.await()/signal(), which allows several conditions per lock (for example notFull and notEmpty). These are powerful but error-prone: you must wait in a loop, hold the lock and avoid missed signals.

High level (preferred):

  • BlockingQueue (ArrayBlockingQueue, LinkedBlockingQueue): the standard producer-consumer hand-off. put blocks when full, take blocks when empty, and it gives correct visibility of the passed objects.
  • Future / CompletableFuture: pass a single result from a task to whoever waits or registers a callback.
  • CountDownLatch: one or more threads wait until N events have happened.
  • CyclicBarrier / Phaser: a group of threads wait for each other at a rendezvous point.
  • Semaphore: limit how many threads use a resource.
  • Exchanger: two threads swap objects.
  • volatile boolean: a simple flag, such as a stop signal, written by one thread and read by others.

Concurrent collections like ConcurrentHashMap also give safe sharing. Choosing these tools avoids most visibility and missed-signal bugs.

How it works

  1. Decide what is communicated: a stream of items, one result, a signal, or a count of events.
  2. Pick the matching tool: queue, future, latch/barrier, flag.
  3. The producer writes or signals (put, complete, countDown, stopped = true).
  4. The tool establishes happens-before, so the consumer sees everything written before.
  5. The consumer is woken or polls (take, join, await, reading the flag).

Example

BlockingQueue<Order> queue = new ArrayBlockingQueue<>(100);
AtomicBoolean running = new AtomicBoolean(true);  // shared stop flag (or a volatile field)

Thread producer = new Thread(() -> {
    for (Order o : incomingOrders()) {
        try { queue.put(o); }                     // blocks when full
        catch (InterruptedException e) { Thread.currentThread().interrupt(); return; }
    }
});

Thread consumer = new Thread(() -> {
    while (running.get() || !queue.isEmpty()) {
        try {
            Order o = queue.poll(500, TimeUnit.MILLISECONDS);   // waits when empty
            if (o != null) process(o);
        } catch (InterruptedException e) { Thread.currentThread().interrupt(); return; }
    }
});
producer.start(); consumer.start();

Common mistakes

  • Sharing a plain boolean flag without volatile, so the loop never sees it change.
  • Busy-waiting with while (!ready) {} instead of blocking.
  • Calling wait with if instead of while.
  • Using an unbounded queue so a fast producer exhausts memory.

How to answer in the interview

"Threads in one JVM communicate through shared memory, so the question is how to do it safely. The low-level way is a shared object guarded by synchronized, with wait and notifyAll so one thread can wait until another changes a condition, or Lock with Condition await and signal. In practice I prefer higher-level tools: a BlockingQueue for producer-consumer hand-off, where put blocks when full and take blocks when empty; Future or CompletableFuture to pass a result; CountDownLatch, CyclicBarrier, Semaphore or Exchanger for coordination; and a volatile boolean for a simple stop flag. These handle visibility and ordering correctly."

Likely follow-up questions

  • Why should wait() always be called in a loop? Because of spurious wakeups and because another thread may change the condition before the woken thread reacquires the lock.
  • What is the advantage of BlockingQueue over wait/notify? It encapsulates locking, conditions and visibility correctly, so there is far less room for bugs.
  • How do you stop a consumer thread cleanly? Interrupt it, use a volatile flag, or send a "poison pill" item through the queue.
