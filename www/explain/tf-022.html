How do you safely use the random provider for names and passwords in Terraform?

Terraform · concept · levels mid, senior

In one line

The random provider (random_id, random_string, random_pet, random_password) generates values once and stores them in state, so they are stable across runs; keepers force a new value when inputs change; random passwords are still in state, so prefer ephemeral random_password with write-only arguments or a vault.

Detailed explanation

Terraform needs deterministic plans, so a function like uuid() that changes every run would cause permanent diffs. The random provider solves this by modelling randomness as resources: on create, the value is generated and persisted in state, and later plans reuse it. It only changes if the resource is replaced.

Typical uses are unique names for globally unique resources: S3 buckets, Azure storage accounts (3-24 lowercase letters and digits), Key Vaults or DNS labels. random_id with byte_length = 4 gives a short hex suffix; random_string lets you control character sets (upper = false, special = false) to match naming rules; random_pet produces readable names like quick-otter. Random values are also used for spreading resources across zones with random_shuffle or for one-off tokens.

keepers is a map of arbitrary values; if any value changes, the random resource is replaced and a new value generated. For example, tie a suffix to the resource group name, the AMI ID or an environment name, so renaming the environment produces a fresh, consistent name. Remember that replacing the random resource will usually replace every resource whose name uses it, so keepers should only contain values that justify that.

For passwords, random_password marks result sensitive, but the value is stored in plain text in state. Anyone with state access sees the database password. With Terraform 1.10+ I prefer ephemeral "random_password" passed to write-only arguments (password_wo) and stored in a secret manager, or let the cloud manage the secret (for example RDS manage_master_user_password with Secrets Manager).

How it works

  1. First apply: provider generates the value; it is saved in state.
  2. Subsequent plans read it from state; no change.
  3. If a keeper changes, Terraform plans replacement and a new value.
  4. Dependent resources referencing it get updated or replaced.

Example

resource "random_string" "suffix" {
  length  = 6
  upper   = false
  special = false
  keepers = {
    resource_group = azurerm_resource_group.main.name
  }
}

resource "azurerm_storage_account" "logs" {
  name                     = "acmelogs${random_string.suffix.result}"
  resource_group_name      = azurerm_resource_group.main.name
  location                 = azurerm_resource_group.main.location
  account_tier             = "Standard"
  account_replication_type = "ZRS"
}

ephemeral "random_password" "db" {
  length = 32
}

Common mistakes

  • Using uuid() or timestamp() in names, causing perpetual changes.
  • Putting frequently changing values in keepers, replacing resources unexpectedly.
  • Assuming random_password is secure because it is "sensitive".
  • Character sets that violate the target resource's naming rules.

How to answer in the interview

"The random provider has resources like random_id, random_string, random_pet and random_password. Their values are generated once and stored in state, so they stay stable across runs, which is what makes them usable for names, like a unique suffix for storage accounts or S3 buckets. The keepers argument holds values that force a new random value when they change, such as tying a suffix to the resource group name. For passwords, random_password is marked sensitive but still stored in plain text in state, so with Terraform 1.10 or later I use an ephemeral random_password with write-only arguments, or let a vault or the cloud manage the secret."

Likely follow-up questions

  • What happens to dependents when a keeper changes? The random value changes, so resources using it are updated or, for names, usually replaced.
  • Why not uuid()? It changes on every plan.
  • How do you import an existing name? Use the real name directly or import the random resource with its known value.
