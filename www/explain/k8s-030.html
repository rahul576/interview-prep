How have service account tokens changed, and how do pods get cloud permissions with workload identity?

Kubernetes · concept · levels mid, senior

In one line

Service accounts moved from long-lived token Secrets to bound, projected tokens from the TokenRequest API: audience-bound, pod-bound, expiring and auto-rotated by the kubelet. The same signed tokens enable workload identity: cloud IAM trusts the cluster's OIDC issuer and exchanges tokens for short-lived cloud credentials (IRSA / EKS Pod Identity, Azure Workload Identity, GKE Workload Identity).

Detailed explanation

Originally, every ServiceAccount got a Secret containing a JWT that never expired and wasn't tied to any pod. Anyone who copied it, from a pod, a backup or a log, had that identity forever.

Modern clusters use bound service account tokens:

  • The kubelet requests a token through the TokenRequest API and mounts it via a projected volume at /var/run/secrets/kubernetes.io/serviceaccount/token.
  • The token has an audience (who may accept it), an expiry (about an hour by default for the API audience, refreshed by the kubelet before expiry) and is bound to the pod: deleting the pod invalidates it.
  • Since 1.24, token Secrets are no longer auto-created, and unused legacy ones are later cleaned up; long-lived tokens must be created explicitly, which should be rare.
  • Set automountServiceAccountToken: false on pods or ServiceAccounts that don't call the Kubernetes API, reducing what an attacker gets from a compromised container.

Workload identity reuses these tokens for the cloud. The cluster's service account issuer publishes an OIDC discovery document and public keys. You configure cloud IAM to trust that issuer for a specific subject, system:serviceaccount:<namespace>:<name>, and audience. The pod gets a projected token with that audience; the cloud SDK exchanges it (for example AWS STS AssumeRoleWithWebIdentity, Microsoft Entra federated credentials, GCP STS) for short-lived cloud credentials. Implementations: IRSA and EKS Pod Identity on AWS (Pod Identity uses an agent and associations instead of per-cluster OIDC trust), Microsoft Entra Workload ID on AKS, Workload Identity Federation for GKE. No cloud keys are stored in Secrets, and access is scoped per service account.

How it works

  1. Pod uses ServiceAccount orders annotated or associated with a cloud role.
  2. Kubelet requests a projected token with the cloud audience.
  3. SDK reads the token file and calls the cloud token service.
  4. Cloud validates signature via the OIDC keys and checks the subject.
  5. Short-lived credentials returned; kubelet refreshes the token before expiry.

Example

apiVersion: v1
kind: ServiceAccount
metadata:
  name: orders
  namespace: shop
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789012:role/shop-orders   # IRSA
automountServiceAccountToken: false
---
# In the pod spec, mount only what is needed
spec:
  serviceAccountName: orders
  automountServiceAccountToken: true
"Condition": { "StringEquals": {
  "oidc.eks.eu-west-1.amazonaws.com/id/EXAMPLE:sub": "system:serviceaccount:shop:orders",
  "oidc.eks.eu-west-1.amazonaws.com/id/EXAMPLE:aud": "sts.amazonaws.com" } }

Common mistakes

  • Trust policies matching any service account in the cluster (wildcard subject).
  • Creating legacy long-lived token Secrets for CI out of habit.
  • Mounting tokens into every pod by default.
  • Storing cloud access keys in Secrets when workload identity is available.

How to answer in the interview

"Service accounts used to get a long-lived token in a Secret that never expired. Since 1.24 pods get bound, projected tokens from the TokenRequest API: audience-bound, tied to the pod, expiring and auto-rotated by the kubelet, and legacy token secrets aren't created automatically. Pods that don't call the API set automountServiceAccountToken false. Workload identity uses those tokens: the cluster publishes an OIDC issuer, cloud IAM trusts tokens for a specific namespace and service account and exchanges them for short-lived credentials, with IRSA or EKS Pod Identity, Azure Workload Identity or GKE Workload Identity. No cloud keys live in the cluster."

Likely follow-up questions

  • Why scope to one namespace and service account? Otherwise any pod in the cluster could assume the role.
  • IRSA vs EKS Pod Identity? Pod Identity avoids per-cluster OIDC trust setup and simplifies role reuse across clusters.
  • Can tokens be used outside the cluster? Yes, which is why short expiry and audience binding matter.
