How do you test asynchronous Kafka consumers?

Testing · scenario · levels mid, senior

In one line

Test the handler logic as a plain unit, then run integration tests against Testcontainers Kafka (or @EmbeddedKafka): produce a message, wait with Awaitility rather than Thread.sleep, and assert side effects (database rows, outbound events, dead-letter records), including retries, poison messages and duplicates.

Detailed explanation

A Kafka consumer is asynchronous: the test thread publishes a message and the listener runs later on another thread. Tests must therefore separate logic from infrastructure and wait for outcomes properly.

Unit level: keep the @KafkaListener method thin and delegate to a handler such as OrderEventHandler.handle(OrderCreated event). Unit test that method directly with constructed events and mocked repositories. This covers business rules, validation and idempotency checks in milliseconds.

Integration level: start a real broker with Testcontainers Kafka (closest to production) or Spring Kafka's @EmbeddedKafka (in-JVM, faster but less realistic). Start the Spring context so the real listener container, deserialisers, error handler and transaction settings are used. Publish with KafkaTemplate, then wait with Awaitility: await().atMost(Duration.ofSeconds(10)).untilAsserted(...) polls until the assertion passes or times out. Thread.sleep either waits too long (slow suite) or too little (flaky tests).

What to assert: effects, not internals. Rows saved in the database (Testcontainers PostgreSQL), events published to an output topic (read with a test consumer), records on the dead-letter topic (DLT), metrics or calls to WireMock-stubbed services.

Failure paths: a downstream timeout triggers retries (DefaultErrorHandler with backoff or @RetryableTopic), then the DLT; a poison message that cannot be deserialised goes straight to the DLT via ErrorHandlingDeserializer without blocking the partition; a duplicate delivery (at-least-once semantics) must not create a second row. Also test ordering if keys guarantee it.

How it works

  1. Unit test the handler with plain objects.
  2. Start Kafka (and DB) containers; configure Spring via @ServiceConnection.
  3. Send a message with a unique key to the input topic.
  4. Await the side effect with a timeout.
  5. Repeat for error cases: bad payload, downstream failure, duplicate.
  6. Use unique ids or topics per test to avoid interference.

Example

@SpringBootTest
@Testcontainers
class OrderCreatedListenerIT {
    @Container @ServiceConnection
    static KafkaContainer kafka = new KafkaContainer("apache/kafka-native:3.8.0");
    @Container @ServiceConnection
    static PostgreSQLContainer<?> pg = new PostgreSQLContainer<>("postgres:16");

    @Autowired KafkaTemplate<String, String> template;
    @Autowired ShipmentRepository shipments;

    @Test
    void createsShipmentOnceEvenIfDeliveredTwice() {
        String event = """
            {"orderId":"o-42","customerId":7}""";
        template.send("order-created", "o-42", event);
        template.send("order-created", "o-42", event);        // duplicate

        await().atMost(Duration.ofSeconds(10)).untilAsserted(() ->
            assertThat(shipments.findByOrderId("o-42")).hasSize(1));
    }

    @Test
    void poisonMessageGoesToDlt() {
        template.send("order-created", "bad", "not-json");
        await().atMost(Duration.ofSeconds(10)).untilAsserted(() ->
            assertThat(readRecords("order-created-dlt")).anyMatch(r -> r.key().equals("bad")));
    }
}

Common mistakes

  • Using Thread.sleep to wait for the consumer.
  • Putting all logic in the listener method so it cannot be unit tested.
  • Asserting on "message was received" instead of the business effect.
  • Shared topics and ids across tests, causing interference and order dependence.

How to answer in the interview

"I test at two levels. The listener just delegates to a handler, so the business logic is unit tested directly with event objects and no Kafka. For integration I run Kafka in Testcontainers, start the Spring context so the real deserialisers and error handlers are used, publish with KafkaTemplate and wait for the effect with Awaitility, never Thread.sleep, which is slow and flaky. I assert side effects: rows in the database, events on output topics, records on the dead-letter topic. And I test failure paths explicitly: retries when a downstream call fails, poison messages going to the DLT and duplicates being ignored."

Likely follow-up questions

  • Why is Thread.sleep bad? It is a fixed guess: too long slows the suite, too short makes it flaky.
  • EmbeddedKafka or Testcontainers? Embedded is faster; Testcontainers matches the real broker version and configuration.
  • How to test idempotency? Send the same message twice and assert one effect.
