How would you reduce compute costs for a large EKS or EC2 estate?

Cloud (AWS) · design · levels senior

In one line

Cut compute cost by rightsizing from utilisation data (Compute Optimizer, request-vs-usage in Kubernetes), moving to Graviton, running fault-tolerant work on Spot, covering the steady baseline with Savings Plans, and using Karpenter consolidation, bin-packing and schedules to scale idle capacity to zero.

Detailed explanation

Measure first. Cost Explorer and the Cost and Usage Report show where spend is; Compute Optimizer recommends instance types and sizes from CloudWatch metrics (enable memory metrics for better results); in Kubernetes, compare pod requests with actual usage using tools like Kubecost, the Vertical Pod Autoscaler in recommend mode, or Container Insights. Over-requested pods force more nodes than needed, so rightsizing requests is usually the biggest win.

Graviton ARM instances typically offer around 20 percent better price-performance and lower energy use. Most interpreted and JVM workloads move easily; build multi-architecture images in CI.

Spot instances offer large discounts, often 60 to 90 percent, for workloads that tolerate interruption: CI runners, batch, data processing, and stateless web services with enough replicas. Use many instance types and AZs, price-capacity-optimised allocation, handle the two-minute interruption notice, and keep a stable On-Demand baseline for critical pods.

Commitments: Compute Savings Plans cover EC2, Fargate and Lambda flexibly across families and regions; EC2 Instance Savings Plans and Reserved Instances give deeper discounts with less flexibility. Commit to the stable baseline only, after rightsizing, and track coverage and utilisation.

Kubernetes efficiency: Karpenter chooses the cheapest instance types that fit pending pods, mixes Spot and On-Demand, and consolidates under-used nodes. Use the Horizontal Pod Autoscaler or KEDA to scale replicas, and scale non-production to zero at night and weekends. Also clean up idle resources: unattached EBS volumes, old snapshots, idle load balancers, and move gp2 to gp3.

How it works

  1. Build visibility per team, cluster and namespace.
  2. Rightsize instances and pod requests.
  3. Migrate suitable workloads to Graviton.
  4. Move fault-tolerant workloads to diversified Spot.
  5. Buy Savings Plans for the remaining steady baseline.
  6. Automate consolidation, scheduling and waste cleanup; review monthly.

Example

apiVersion: karpenter.sh/v1
kind: NodePool
metadata: {name: general}
spec:
  template:
    spec:
      requirements:
        - {key: kubernetes.io/arch, operator: In, values: ["arm64", "amd64"]}
        - {key: karpenter.sh/capacity-type, operator: In, values: ["spot", "on-demand"]}
        - {key: karpenter.k8s.aws/instance-category, operator: In, values: ["c", "m", "r"]}
      nodeClassRef: {group: karpenter.k8s.aws, kind: EC2NodeClass, name: default}
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 1m
  limits: {cpu: "2000"}

Common mistakes

  • Buying Savings Plans before rightsizing, locking in waste.
  • Spot with a single instance type, causing mass interruptions.
  • Ignoring pod requests and only looking at node utilisation.
  • One-off clean-ups with no ongoing ownership.

How to answer in the interview

"I start with data: Compute Optimizer and Kubernetes request versus usage show over-provisioning, so rightsizing instances and pod requests is the first win. Then Graviton, usually around 20 percent better price-performance once images are multi-arch. Fault-tolerant and stateless workloads like CI runners, batch and replicated web services run on diversified Spot, saving 60 to 90 percent. The steady baseline is covered with Compute Savings Plans. In EKS, Karpenter bin-packs and consolidates nodes onto the cheapest fitting capacity, and non-production scales down outside working hours."

Likely follow-up questions

  • How make workloads safe for Spot? Multiple replicas, PodDisruptionBudgets, graceful shutdown, checkpointing and diversified instance types.
  • Savings Plans or RIs? Compute Savings Plans for flexibility; RIs mainly for RDS, ElastiCache and other non-EC2 services.
  • How do you keep savings from eroding? Unit cost dashboards, budgets and regular reviews with owners.
