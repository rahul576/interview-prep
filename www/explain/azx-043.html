How do you manage variables and secrets in Azure Pipelines?

Azure DevOps & Pipelines · concept · levels entry, mid, senior

In one line

Keep plain config in YAML or variable templates, shared values in variable groups (protected resources), mark secrets as secret (masked, not given to fork PRs, mapped explicitly via env), link variable groups to Key Vault or use the AzureKeyVault task, and ideally avoid secrets with workload identity federation and managed identities.

Detailed explanation

Levels of variables:

  • YAML variables and variable templates in Git: non-secret, versioned, reviewed values such as buildConfiguration or resource names.
  • Pipeline variables set in the UI: useful for values that change per run or that users may override at queue time (mark "settable at queue time" carefully).
  • Variable groups in the Library: shared across pipelines; they are protected resources, so you can control which pipelines use them and add approvals and checks.

Secret variables behave differently on purpose:

  • They are masked in logs (***).
  • They are not available to builds of pull requests from forks (unless explicitly allowed, which you shouldn't).
  • They are not mapped into environment variables automatically; a script must receive them via env: mapping. That makes the use explicit and avoids accidental exposure to every tool.
  • In YAML, they can't be defined inline; they come from the UI, variable groups or Key Vault.

Key Vault integration: link a variable group to an Azure Key Vault, selecting secrets; they are fetched at runtime using the service connection, so rotation happens in the vault, not in Azure DevOps. Alternatively the AzureKeyVault@2 task pulls secrets on demand into a job.

Best option: no secrets. Service connections with workload identity federation (OIDC) let pipelines get Entra tokens without stored client secrets, and deployed apps use managed identities. Remaining secrets (third-party API keys) stay in Key Vault with least-privilege access for the pipeline identity.

How it works

  1. Non-secret config → YAML/variable templates.
  2. Shared environment values → variable groups with pipeline permissions.
  3. Secrets → Key Vault, linked variable group or AzureKeyVault task.
  4. Scripts receive secrets via env mapping only.
  5. Azure auth → workload identity federation service connection.

Example

variables:
- template: vars/prod.yml           # non-secret values from Git
- group: kv-orders-prod             # linked to Azure Key Vault
steps:
- task: AzureCLI@2
  inputs:
    azureSubscription: sc-orders-prod-oidc     # workload identity federation
    scriptType: bash
    scriptLocation: inlineScript
    inlineScript: ./deploy.sh
  env:
    PAYMENT_API_KEY: $(PaymentApiKey)          # explicit secret mapping

Common mistakes

  • Putting secrets in YAML or variable templates in Git.
  • Making secret variables settable at queue time.
  • Giving every pipeline access to all variable groups.
  • Echoing secrets in scripts for debugging.

How to answer in the interview

"Non-secret values live in YAML or variable templates in Git, so they're versioned. Shared values go into variable groups, which are protected resources with permissions and checks. Secrets are marked secret: they're masked, not given to fork pull requests, and a script only gets them if I map them explicitly through env. Better, I link variable groups to Key Vault so secrets are rotated in the vault. Best of all, I avoid secrets: service connections use workload identity federation, and apps use managed identities."

Likely follow-up questions

  • Why can masking fail? Transformed values (base64, split, URL-encoded) aren't recognised.
  • How does a script create a secret variable? ##vso[task.setvariable variable=x;issecret=true]value.
  • Key Vault-linked group permissions? The service connection needs Get/List or Key Vault Secrets User.
