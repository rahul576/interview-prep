How would you define an infrastructure as code strategy and governance model for an enterprise?

Infrastructure as Code · design · levels lead

In one line

Standardise on one main IaC toolset with a version policy, have a platform team own golden modules and pipeline templates, make pipelines with policy as code the only route to production, require ownership, tags and budgets per stack, and drive adoption through enablement and inner source rather than gates alone.

Detailed explanation

An enterprise without an IaC strategy typically has three tools, five pipeline styles, modules copied between teams and a lot of console changes. The strategy has to make the right way the easy way while keeping enough control for security, audit and cost.

Toolset. Pick a primary tool, often Terraform or OpenTofu, because of provider coverage and hiring, with a supported-versions policy (for example current and previous minor) and an approved exceptions list, such as AWS CDK for a team with strong TypeScript skills on an AWS-only product. Every exception costs duplicated modules, policies and expertise, so it must be justified.

Golden paths. A platform team owns golden modules (network, cluster, database, service) and pipeline templates that encode security, networking, tagging and cost standards. They are versioned, tested and published in a private registry, with documentation and examples. Teams compose them in their own live repositories.

Guardrails. Every production change goes through a pipeline: plan, review, policy as code (Sentinel, OPA, Checkov), approval for high-risk changes, and audit logs. Humans have read-only console access; emergencies use break-glass roles with a rule to codify within days. Drift detection keeps this honest.

Accountability. Every stack has an owning team in a catalogue, mandatory tags and a budget, so cost and incidents are attributable.

Enablement. Governance that is only gates gets bypassed. Documentation, training paths, office hours, a champions network and an inner-source model, where application teams contribute improvements to shared modules through reviewed pull requests, make adoption voluntary and fast.

How it works

  1. Assess current tools, maturity and pain points.
  2. Publish standards: tool, versions, repo layout, state, naming, tagging.
  3. Build golden modules and pipeline templates with the first pilot teams.
  4. Enforce policy in pipelines; restrict manual production changes.
  5. Roll out by business unit with training and migration support.

Example

IaC standard v2 (excerpt)
- Tool: OpenTofu 1.x (current + previous minor); CDK allowed by exception (ADR-014)
- State: one backend per account, encrypted, versioned, locked
- Modules: from registry.acme.internal only, pinned versions
- Production: changes only via pipeline; break-glass changes codified within 3 days
- Every stack: owner, cost-centre, data-classification tags; monthly budget alert

Common mistakes

  • Mandating a tool without providing modules, templates and help.
  • Central approval of every change, creating a bottleneck.
  • Allowing permanent manual console access "for speed".
  • No metrics, so nobody knows whether the strategy works.

How to answer in the interview

"I'd standardise on one main toolset, say Terraform or OpenTofu with a clear version policy, and allow exceptions like CDK only with a documented reason. A platform team owns golden modules and pipeline templates that encode our security, networking, tagging and cost standards, published in a private registry. Every production change goes through a pipeline with plan review, policy as code and audit logging, and manual console changes are limited to break-glass. Every stack has an owner, tags and a budget. And I'd lean on enablement: docs, training, office hours and inner source so teams contribute to the shared modules."

Likely follow-up questions

  • How do you measure whether it works? IaC coverage, lead time for infrastructure changes, change failure rate, drift and module adoption.
  • How do you handle teams on a different tool? Support them during a migration window, or approve the exception with clear ownership.
  • Who owns the standards? The platform team with a cross-team forum and ADRs.
