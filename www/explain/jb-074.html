What is the difference between orElse() and orElseGet()?

Java 8+ Features · concept · levels mid, senior

In one line

orElse(value) always evaluates its argument eagerly, even when the Optional has a value, while orElseGet(supplier) calls the Supplier lazily, only when empty; it matters for expensive or side-effecting defaults, and orElseThrow is best when absence is an error.

Detailed explanation

This is ordinary Java argument evaluation, not anything special about Optional. In opt.orElse(createDefaultUser()), Java must compute the argument before calling the method, so createDefaultUser() runs every time, then the result is thrown away if the Optional was present. With opt.orElseGet(this::createDefaultUser), you pass a Supplier; orElseGet only invokes get() if the Optional is empty.

For constants or already-computed values, orElse("unknown") or orElse(Collections.emptyList()) is fine and slightly more readable; there's no real cost.

It matters when the default is expensive (a database query, remote call, heavy object construction) or has side effects (inserting a row, sending an event, incrementing a metric, logging). A classic production bug: userRepo.findByEmail(email).orElse(userRepo.save(new User(email))) creates a duplicate user every time, even for existing users, sometimes surfacing as a unique-constraint violation.

When absence is a failure, use orElseThrow() (Java 10, a clearer alias for get()), or orElseThrow(() -> new UserNotFoundException(id)) with a lazily created specific exception. Java 9 also added or(supplier) to provide an alternative Optional lazily, and ifPresentOrElse for actions.

How it works

  1. orElse(T other): other is computed by the caller, then returned if empty.
  2. orElseGet(Supplier<? extends T>): returns the value, or supplier.get() if empty.
  3. orElseThrow(Supplier<? extends X>): returns the value, or throws the supplied exception.
  4. or(Supplier<Optional<T>>): returns this Optional, or the supplied one if empty.

Example

User findOrCreate(String email) {
    // BUG: save() runs even when the user exists
    // return repo.findByEmail(email).orElse(repo.save(new User(email)));

    return repo.findByEmail(email)
        .orElseGet(() -> repo.save(new User(email)));   // runs only when absent
}

String name = Optional.ofNullable(customer.nickname()).orElse("Guest");   // constant: fine

Order order = orderRepo.findById(id)
    .orElseThrow(() -> new OrderNotFoundException(id));

Optional<Price> price = cache.get(sku).or(() -> pricingService.lookup(sku)); // Java 9

Common mistakes

  • orElse(expensiveOrSideEffectingCall()).
  • orElseGet(() -> null) and then hitting NPE later; prefer explicit handling.
  • Calling get() instead of orElseThrow().
  • Over-using orElseGet for trivial constants, hurting readability.

How to answer in the interview

"orElse takes a value, so its argument is always evaluated eagerly, even when the Optional contains a value. orElseGet takes a Supplier that's called only when the Optional is empty. With a constant default there's no difference. It matters when the default is expensive or has side effects: orElse(createDefaultUser()) would run the method, maybe insert a database row or make a remote call, on every invocation even when a user was found. So I use orElseGet there. When absence is an error, orElseThrow with a specific exception is clearer."

Likely follow-up questions

  • Why is Optional.get() discouraged? It throws NoSuchElementException without intent; orElseThrow() reads as deliberate.
  • What does Optional.or do? Lazily supplies an alternative Optional (Java 9).
  • Is orElseGet always better? No, for constants orElse is simpler.
