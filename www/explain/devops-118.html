How do PodDisruptionBudgets affect node maintenance and upgrades?

Kubernetes · concept · levels mid, senior

In one line

A PodDisruptionBudget (PDB) limits how many pods of an application may be taken down by voluntary disruptions at once, using minAvailable or maxUnavailable; kubectl drain and autoscalers use the Eviction API, which refuses evictions that would break the budget, so a misconfigured PDB can block upgrades, and PDBs do nothing for involuntary failures.

Detailed explanation

Kubernetes separates voluntary disruptions (drains, autoscaler scale-down, manual evictions) from involuntary ones (hardware failure, kernel panic, node-pressure eviction). PDBs only govern the first kind.

A PDB selects pods by label and states either minAvailable (at least N or N% must stay healthy) or maxUnavailable (at most N or N% may be down). When kubectl drain runs, it does not delete pods directly; it calls the Eviction API for each pod. The API server checks the PDB: if evicting the pod would drop healthy pods below the budget, it returns 429 Too Many Requests and drain keeps retrying until the controller has brought up a replacement elsewhere. That is what makes rolling node upgrades safe: nodes go one at a time, and an application never loses more replicas than it can tolerate.

The danger is a budget that can never be satisfied: minAvailable equal to the replica count, maxUnavailable: 0, or a single-replica Deployment with minAvailable: 1. Drains then hang forever, managed node upgrades time out or are forced, and autoscalers cannot remove nodes. Another trap is pods that are already unhealthy: by default they still count against the budget, which the unhealthyPodEvictionPolicy: AlwaysAllow setting addresses by letting broken pods be evicted.

How it works

  1. Platform team starts a node pool upgrade; each node is cordoned.
  2. Drain calls the Eviction API for every pod on the node.
  3. API server compares current healthy pods with the PDB.
  4. If allowed, the pod is evicted and the ReplicaSet creates a replacement on another node.
  5. If not allowed, drain retries until replacements are Ready.
  6. Node is empty and is replaced; the process moves to the next node.

Example

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: orders-pdb }
spec:
  maxUnavailable: 1
  unhealthyPodEvictionPolicy: AlwaysAllow
  selector:
    matchLabels: { app: orders }
# PDBs that currently allow zero disruptions will block the next drain
kubectl get pdb -A -o custom-columns=NS:.metadata.namespace,NAME:.metadata.name,ALLOWED:.status.disruptionsAllowed | awk '$3==0'

Common mistakes

  • minAvailable: 100% or maxUnavailable: 0 on production apps.
  • A PDB on a single-replica workload, which can never be drained.
  • Selectors that match no pods or pods of several apps.
  • Believing a PDB protects against node crashes.

How to answer in the interview

"A PDB limits voluntary disruptions for a set of pods with minAvailable or maxUnavailable. Drain and autoscalers use the Eviction API, which refuses an eviction that would violate the budget, so upgrades proceed only as fast as the application can tolerate. The flip side is that a PDB requiring all replicas, or one on a single-replica app, blocks drains forever and stalls upgrades. I usually set maxUnavailable to one or a percentage, run at least two replicas, and check for PDBs with zero allowed disruptions before every upgrade. PDBs don't help with node failures; for that you need replicas spread across nodes and zones."

Likely follow-up questions

  • How do you find PDBs that will block the upgrade? List PDBs where status.disruptionsAllowed is 0, and check for single-replica targets.
  • Does deleting a pod respect PDBs? No, kubectl delete pod bypasses the Eviction API.
  • minAvailable or maxUnavailable? maxUnavailable scales naturally with HPA-driven replica counts.
