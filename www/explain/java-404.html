What is the difference between a clustered and a non-clustered index, and what is a covering index?

Databases & SQL · concept · levels mid, senior

In one line

A clustered index stores the table rows themselves in key order (so only one exists), a non-clustered (secondary) index is a separate structure that points to the rows, and a covering index contains every column a query needs so it can be answered from the index alone.

Detailed explanation

In MySQL InnoDB the table is a B+tree clustered on the primary key: leaf pages hold the full rows. If you do not define a primary key, InnoDB uses the first unique not-null index or a hidden row id. Every secondary index stores the indexed columns plus the primary key value, so a lookup by secondary index finds the PK and then traverses the clustered index again (a "bookmark" lookup). SQL Server lets you choose any clustered index, defaulting to the primary key.

PostgreSQL is different: rows live in an unordered heap, and every index, including the primary key, is secondary and points to a physical tuple location (TID). CLUSTER reorders the heap once but the order is not maintained. Oracle uses heap tables by default and index-organised tables optionally.

Because secondary lookups cost extra I/O, a covering index helps: if the index contains all filtered, sorted and selected columns, the engine performs an index-only scan. You build one either with a composite index or with non-key INCLUDE columns (PostgreSQL 11+, SQL Server). In Postgres, index-only scans also depend on the visibility map being up to date, so vacuuming matters.

This is also why InnoDB primary keys should be small and sequential: every secondary index carries a copy of the PK, and random keys like UUIDv4 cause page splits and fragmentation. Sequential or time-ordered keys (auto-increment, UUIDv7) append to the end of the tree.

How it works

  1. The query planner chooses an index based on predicates and statistics.
  2. It walks the B-tree from root to leaf for the key range.
  3. With a clustered index (InnoDB PK), the leaf already holds the row.
  4. With a secondary index, it fetches the row via PK (InnoDB) or TID (Postgres).
  5. With a covering index, step 4 is skipped entirely.

Example

-- Query
SELECT status, total FROM orders WHERE customer_id = 42 ORDER BY created_at DESC;

-- PostgreSQL covering index
CREATE INDEX idx_orders_cust ON orders (customer_id, created_at DESC)
  INCLUDE (status, total);

-- MySQL: composite index that covers the query
CREATE INDEX idx_orders_cust ON orders (customer_id, created_at, status, total);
-- EXPLAIN shows "Using index" (MySQL) or "Index Only Scan" (Postgres)

Common mistakes

  • Saying PostgreSQL has a clustered primary key like InnoDB.
  • Using random UUIDv4 primary keys in InnoDB on large, write-heavy tables.
  • Building wide covering indexes for every query, which slows writes.
  • Forgetting SELECT * defeats a covering index.

How to answer in the interview

"A clustered index is the table itself stored in index order, so there's only one. InnoDB clusters every table by its primary key, while PostgreSQL stores rows in a heap and all its indexes are secondary. A non-clustered index is a separate B-tree holding the key and a pointer, which in InnoDB is the primary key, so using it can mean an extra lookup. A covering index includes all the columns the query needs, through a composite key or INCLUDE columns, so the database can do an index-only scan. That's also why I keep InnoDB primary keys small and sequential: every secondary index repeats them and random keys fragment the tree."

Likely follow-up questions

  • Why small, sequential InnoDB PKs? Every secondary index stores the PK, and sequential inserts avoid page splits.
  • What is a bookmark/key lookup? Fetching the full row after finding it in a secondary index.
  • Why might Postgres not use an index-only scan? The visibility map is stale, so it must still check the heap.
