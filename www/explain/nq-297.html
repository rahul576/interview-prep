How do you push an application image or artifact to a registry?

DevOps & CI/CD · scenario · levels mid

In one line

Build the image with docker build, Jib or Buildpacks, tag it uniquely (version and commit SHA) instead of relying on latest, authenticate with CI-stored or cloud credentials (docker login, aws ecr get-login-password, az acr login), docker push to the registry, publish jars with mvn deploy, and add scanning, signing and immutable tags.

Detailed explanation

Building: a multi-stage Dockerfile, or for Spring Boot without a Dockerfile, Jib (builds and pushes directly from Maven or Gradle, no Docker daemon) or Cloud Native Buildpacks via spring-boot:build-image.

Tagging: use tags like orders-service:1.4.2 and orders-service:3f9c2ab (commit SHA). Unique tags make deployments reproducible and rollbacks precise. latest is mutable: two nodes can pull different images, and you cannot tell what is running. For full certainty, deploy by digest (@sha256:...).

Authentication: never hard-code passwords. Use CI secrets or, better, short-lived cloud credentials via OIDC federation (for example GitHub Actions assuming an AWS IAM role):

  • Amazon ECR: aws ecr get-login-password | docker login --username AWS --password-stdin <account>.dkr.ecr.<region>.amazonaws.com
  • Azure ACR: az acr login --name myregistry
  • Docker Hub, GHCR, Nexus or Artifactory: docker login with a token.

Jars: mvn deploy publishes to Nexus or Artifactory using distributionManagement in the POM and server credentials in settings.xml; release repositories should reject redeploying the same version.

Good practice: scan with Trivy before or after pushing (and use registry scanning such as ECR enhanced scanning), sign with cosign, attach an SBOM, enable tag immutability so a version can never be overwritten, and set lifecycle policies to clean up old images.

How it works

  1. Build the image from the verified artifact.
  2. Tag with version and commit SHA.
  3. Obtain short-lived registry credentials.
  4. Scan the image; fail on critical issues.
  5. Push and record the digest.
  6. Sign and attach SBOM; deploy by tag or digest.

Example

IMAGE=123456789012.dkr.ecr.eu-west-1.amazonaws.com/orders-service
TAG=1.4.2-$(git rev-parse --short HEAD)

docker build -t $IMAGE:$TAG .
aws ecr get-login-password --region eu-west-1 | \
  docker login --username AWS --password-stdin ${IMAGE%%/*}
trivy image --exit-code 1 --severity CRITICAL $IMAGE:$TAG
docker push $IMAGE:$TAG
cosign sign --yes $IMAGE:$TAG

Jib alternative: ./mvnw compile jib:build -Dimage=$IMAGE:$TAG.

Common mistakes

  • Deploying latest.
  • Long-lived registry passwords in pipeline files.
  • Mutable tags allowing silent overwrites.
  • Scanning nothing, or scanning only once at build time.

How to answer in the interview

"The pipeline builds the image with docker build, or Jib or Buildpacks for Spring Boot, and tags it uniquely, for example with the version and commit SHA, never relying on latest. It authenticates using credentials from the CI secret store or OIDC: aws ecr get-login-password for ECR or az acr login for Azure, then docker push. Jars go to Nexus or Artifactory with mvn deploy. I also scan the image with Trivy, sign it with cosign and enable immutable tags so a version can't be overwritten."

Likely follow-up questions

  • Why is deploying latest risky? It is mutable, not reproducible and makes rollback ambiguous.
  • Tag vs digest? Tags are names that can move; digests identify exact content.
  • What is OIDC for CI? The CI job exchanges an identity token for short-lived cloud credentials, no stored secrets.
