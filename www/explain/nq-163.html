What happens to newly created objects in the young generation?

JVM & Performance · concept · levels entry

In one line

A new object is normally allocated in Eden by a cheap pointer bump in the thread's TLAB; most objects become unreachable almost immediately and their memory is reclaimed for free at the next minor GC, while survivors are copied to a survivor space and aged, and long-lived ones are promoted to the old generation; very large objects may go straight to old or humongous regions.

Detailed explanation

Allocation. When code runs new Invoice(), the JVM needs memory for the object header and fields. Each thread owns a thread-local allocation buffer (TLAB) inside Eden, so the JVM simply advances the thread's "top" pointer by the object size and initialises the memory. No lock, very few instructions: often cheaper than malloc in C. If the TLAB is full, the thread gets a new TLAB from Eden; if Eden is full, a minor GC runs.

Short lives. Most objects in a web service live for the duration of a single request or less: request and response DTOs, temporary strings, collections built and discarded, iterators, boxed numbers, lambdas. By the time the next minor GC runs, they are no longer referenced from any GC root.

Minor GC. The collector traces only live objects in the young generation, copying them into a survivor space. Dead objects are never visited: Eden is just reset to empty. So the cost of garbage is almost zero; the cost is proportional to what survives. That is why "allocate freely, but do not retain" is generally good Java advice.

Aging and promotion. Each survival increments an object's age. Objects that survive enough cycles (the tenuring threshold, up to 15) are copied to the old generation, assumed to be long-lived (cache entries, sessions, pooled objects). If the survivor space is too small, objects may be promoted early.

Large objects. An allocation too big for a TLAB is done directly in Eden outside the TLAB; in G1, objects of at least half a region are humongous and are placed directly in dedicated old-generation regions. Some collectors also allocate very large arrays directly in the old generation.

Optimisation. For hot code, escape analysis may remove the allocation entirely if the object does not escape the method.

How it works

  1. new bumps the pointer in the thread's TLAB in Eden.
  2. Object is used, then usually becomes unreachable.
  3. Eden fills: minor GC copies only live objects to a survivor space.
  4. Survivors age; old enough ones are promoted.
  5. Huge objects skip Eden (humongous regions in G1).

Example

@GetMapping("/invoices/{id}")
InvoiceDto get(@PathVariable long id) {
    Invoice inv = repo.findById(id).orElseThrow();   // entity: short-lived
    String label = "INV-" + inv.number();            // temporary string
    return new InvoiceDto(inv.id(), label, inv.total()); // dies after response is written
}

private final Map<Long, Customer> cache = new ConcurrentHashMap<>(); // long-lived: promoted
byte[] report = new byte[64 * 1024 * 1024];  // with 32 MB G1 regions: humongous

Common mistakes

  • Thinking every allocation is expensive and pooling small objects (usually slower).
  • Believing dead objects are freed one by one.
  • Ignoring humongous allocations of big buffers.
  • Assuming objects are promoted after exactly one GC.

How to answer in the interview

"A new object is normally allocated in Eden, very cheaply, by bumping a pointer in the current thread's thread-local allocation buffer. Most objects, like temporary strings, DTOs and iterators, become unreachable almost immediately. When Eden fills up, a minor GC runs: unreachable objects aren't copied, so their memory is reclaimed for free, while reachable ones are copied into a survivor space and their age increases. Objects that survive enough collections are promoted to the old generation. Very large objects can be allocated directly in the old generation, or in humongous regions with G1. That's why short-lived allocation is cheap in Java, while retaining objects is what costs."

Likely follow-up questions

  • Why is allocating many short-lived objects relatively cheap in Java? Allocation is a pointer bump, and copying collectors never visit dead objects.
  • Is object pooling a good idea? Generally not for small objects; pooled objects become long-lived and cost more GC work. Pool only expensive resources such as connections.
  • What triggers a minor GC? An allocation that cannot fit in Eden.
