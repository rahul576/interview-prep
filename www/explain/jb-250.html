How do you handle duplicate messages in Kafka consumers?

Kafka · design · levels mid, senior

In one line

With at-least-once delivery duplicates are normal, so make consumers idempotent: record each event id under a unique constraint in the same transaction as the business change, or design operations to be naturally idempotent (upserts, set-not-increment, version checks).

Detailed explanation

Duplicates are not a bug in Kafka; they are the price of not losing data. A consumer can process a record and crash before committing its offset, a rebalance can hand a partition to another consumer mid-batch, a producer can resend a message after a timeout (without idempotence), or an upstream service can publish the same business event twice. In all cases the consumer sees the record again.

The robust pattern is the idempotent consumer. Every event carries a stable, unique event id (a UUID set by the producer, or a business key such as paymentId). The consumer keeps a processed_events table with a primary key or unique constraint on that id and inserts into it in the same local database transaction as the business update. If the event was already handled, the insert fails (or ON CONFLICT DO NOTHING affects zero rows) and the consumer skips the work but still commits the offset. Because both writes share one transaction, there is no window where the change is applied but the id is not recorded.

Even better is natural idempotency: "set order status to PAID" can run twice safely, "add 10 to balance" cannot. Use upserts, absolute values instead of deltas, and optimistic version checks (apply event version 7 only if the stored version is 6). For external side effects like sending emails or calling a payment API, pass an idempotency key to the downstream system.

Kafka's exactly-once semantics (idempotent producer plus transactions) only cover Kafka-to-Kafka read-process-write flows. A database write or HTTP call inside your listener is outside that transaction, so you still need idempotency.

How it works

  1. Producer attaches eventId in the payload or a header.
  2. Consumer begins a DB transaction.
  3. Insert eventId into processed_events; if it already exists, skip.
  4. Apply the business change in the same transaction; commit.
  5. Commit the Kafka offset afterwards.
  6. A scheduled job purges ids older than the replay window.

Example

@KafkaListener(topics = "payments", groupId = "orders")
@Transactional
public void onPaymentCompleted(PaymentCompleted evt) {
    int inserted = jdbc.update("""
        INSERT INTO processed_events(event_id, processed_at)
        VALUES (?, now()) ON CONFLICT (event_id) DO NOTHING""", evt.eventId());
    if (inserted == 0) return;                 // duplicate, already handled
    orderRepository.markPaid(evt.orderId());   // natural idempotency too
}

Common mistakes

  • Recording the id in a separate transaction from the business change.
  • Using the Kafka offset as the dedup key; republished events get new offsets.
  • Believing enable.idempotence removes consumer-side duplicates.
  • Never purging the processed-id table.

How to answer in the interview

"I assume duplicates will happen, because with at-least-once delivery a consumer can process a record and crash before committing. So my consumers are idempotent. Each event has a unique id, and in the same database transaction as the business change I insert that id into a table with a unique constraint; if it already exists, I skip the work. Where I can, I make operations naturally idempotent, setting a status instead of incrementing, using upserts or version checks. Kafka's exactly-once only covers Kafka-to-Kafka flows, so it does not replace this for database writes."

Likely follow-up questions

  • How long do you keep processed ids? Longer than the maximum redelivery or replay window, often days, then purge or partition the table.
  • What about non-transactional side effects like emails? Use an idempotency key with the provider or an outbox.
  • Why not dedupe in Redis? Possible, but without a shared transaction you risk gaps between the check and the write.
