How do you design for idempotency in distributed systems?

SD Fundamentals · concept · levels entry, mid, senior

In one line

Because retries are unavoidable, design operations so repeating them has the same effect as doing them once, using idempotency keys, naturally idempotent operations, consumer deduplication and unique constraints.

Detailed explanation

A client sends "charge ₹500" and the connection times out. Did the charge happen? The client can't know, so it retries. Without idempotency, the customer may be charged twice. The same happens with message brokers: most deliver at least once, so consumers will see duplicates.

Some operations are naturally idempotent: PUT /users/42 {full state}, DELETE /items/7, SET balance_reserved = true. Others, like "create order" or "add ₹500", are not and need an idempotency key: a unique ID the client generates per logical operation and sends with every retry.

How it works

  1. Client generates Idempotency-Key: 7f3c… (UUID) per operation and reuses it on retries.
  2. Server, in one transaction: insert the key (unique), perform the operation, store the response with the key.
  3. If the key already exists: return the stored response (or 409 if still in progress).
  4. Expire keys after a window (e.g. 24 hours to a few days).
  5. Consumers store processed message IDs (or use upserts) to skip duplicates.

Example

CREATE TABLE idempotency_keys (
  key TEXT PRIMARY KEY, request_hash TEXT, response JSONB, created_at TIMESTAMPTZ
);
-- in the same transaction as creating the payment:
INSERT INTO idempotency_keys(key, request_hash) VALUES ($1, $2);  -- fails on duplicate

Also check that a reused key comes with the same request body (store a hash), otherwise reject.

Common mistakes

  • Storing the key after the operation in a separate transaction (crash in between = duplicate).
  • Server-generated keys (the client must own them, or retries create new keys).
  • Retrying non-idempotent operations automatically in HTTP clients or gateways.
  • Not deduplicating in message consumers.

How to answer in the interview

"Retries are guaranteed in distributed systems, so every write API must be safe to repeat. For naturally idempotent operations like PUT that's free. For creates and payments, the client sends an idempotency key; the server stores it with the result in the same transaction and returns the stored result on a retry, like Stripe does. Consumers deduplicate by message ID, and a unique constraint on the business key is the final safety net."

Likely follow-up questions

  • How long do you keep keys? Longer than the maximum retry window; often 24 hours to 7 days.
  • What if two retries arrive concurrently? The unique insert lets one win; the other waits or gets 409.
  • Is POST ever idempotent? Not by default; with an idempotency key it can be.
