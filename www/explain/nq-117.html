What are the time complexities of adding, reading, and removing elements in ArrayList and LinkedList?

Collections · concept · levels mid

In one line

ArrayList: get O(1), add at end amortised O(1), add/remove at index O(n); LinkedList: get O(n), add/remove at the ends O(1), at an index O(n) to find + O(1) to unlink; contains is O(n) for both.

Detailed explanation

ArrayList

  • get(i) / set(i, e): O(1), direct array access.
  • add(e) at the end: amortised O(1). Usually it writes into spare capacity; occasionally the array is full and grow() allocates a new array about 1.5× larger and copies everything, an O(n) step. Because growth is geometric, the total cost over n adds is O(n).
  • add(i, e) / remove(i): O(n - i) shifting via System.arraycopy; worst case O(n) at the front, O(1) at the end.
  • remove(Object) / contains / indexOf: O(n) linear search (plus shifting for remove).

LinkedList

  • get(i) / set(i, e): O(n); it walks from whichever end is nearer, so at most n/2 steps.
  • addFirst, addLast, removeFirst, removeLast, peek: O(1).
  • add(i, e) / remove(i): O(n) to reach the node, then O(1) to relink.
  • With a ListIterator already positioned, add and remove are truly O(1).
  • contains / remove(Object): O(n).

Big-O hides constants: ArrayList's O(n) shift is a fast memory move, while LinkedList's O(n) walk is a chain of cache misses. In benchmarks ArrayList usually wins except for heavy iterator-based edits in long lists. To avoid repeated resizing, presize with new ArrayList<>(n) or call ensureCapacity(n) before a bulk load; addAll grows once.

How it works

  1. ArrayList append: check capacity, maybe grow and copy, store.
  2. ArrayList middle insert: shift right, store.
  3. LinkedList end operations: update first/last and neighbour links.
  4. LinkedList index operation: traverse, then relink.

Example

List<Integer> a = new ArrayList<>(1_000_000);  // no resizing during load
for (int i = 0; i < 1_000_000; i++) a.add(i);  // O(1) each
a.add(0, -1);                                   // O(n) shift

LinkedList<Integer> l = new LinkedList<>(a);
l.addFirst(-2);                                 // O(1)
l.get(500_000);                                 // O(n) walk

ListIterator<Integer> it = l.listIterator();
while (it.hasNext()) if (it.next() % 2 == 0) it.remove(); // O(1) per removal

Common mistakes

  • Claiming ArrayList append is always O(1) without "amortised".
  • Saying LinkedList remove(i) is O(1).
  • Forgetting that ArrayList removal at the end is O(1).
  • Not presizing before bulk loads.

How to answer in the interview

"For ArrayList, get is O(1); add at the end is amortised O(1), occasionally O(n) when the array grows by about one and a half times and is copied; adding or removing at an index is O(n) because of shifting; and remove by value is O(n) for the search. For LinkedList, get is O(n) since it walks from the nearer end; operations at the head and tail are O(1); adding or removing at an index is O(n) to find plus O(1) to relink, and only O(1) if an iterator is already there. contains is O(n) for both."

Likely follow-up questions

  • How do you avoid repeated resizing? Presize with the constructor or ensureCapacity.
  • Why "amortised"? Rare O(n) copies are spread over many cheap appends.
  • Which is faster to iterate? ArrayList, due to cache locality.
