Your organisation is considering moving from Azure DevOps to GitHub. What would you evaluate and how would you migrate?

Azure DevOps & Pipelines · scenario · levels mid, senior, lead

In one line

Evaluate the drivers (Copilot and AI, Actions ecosystem, Advanced Security, consolidation) against cost and risk; repos migrate easily with GitHub Enterprise Importer, pipelines need conversion to Actions (helped by Actions Importer), Boards can stay integrated or move to Issues/Projects, and identity, permissions and service connections must be mapped, migrating in phased waves after a pilot.

Detailed explanation

Why move? GitHub is where Microsoft invests most in developer experience: Copilot (including coding agent features), GitHub Actions and its marketplace, Advanced Security, Codespaces and a larger community. Consolidating on one platform can simplify tooling. Against that: migration effort, retraining, licence changes, and losing some Azure DevOps strengths. Azure DevOps remains supported, so this is a business decision, not a forced move.

What to evaluate:

  • Repos: GitHub Enterprise Importer (GEI) moves Azure Repos with history, PRs and some metadata. Branch policies become rulesets / branch protection.
  • Pipelines: the hardest part. GitHub Actions Importer converts much of classic and YAML pipelines, but templates become reusable workflows or composite actions, service connections become OIDC federated credentials per repo/environment, environments with checks become GitHub environments with protection rules (required reviewers, wait timers, deployment branches, custom protection rules), variable groups become org/repo/environment variables and secrets, and agent pools become runners (GitHub-hosted, larger runners with private networking, or self-hosted / ARC on Kubernetes).
  • Boards: Azure Boards integrates with GitHub (AB# links), so many companies keep it. Moving to Issues and Projects suits teams with simpler planning.
  • Artifacts: Azure Artifacts feeds vs GitHub Packages; both can coexist.
  • Identity and governance: Enterprise Managed Users with Entra ID, team sync, audit log streaming, compliance requirements, data residency (GitHub Enterprise Cloud with data residency).
  • Missing equivalents: Test Plans, some check types (Azure Monitor gates), deployment history per environment in the same form, delivery plans.

Approach: inventory, choose target patterns, build reusable workflows first, pilot with two or three representative teams, then waves, with both platforms in parallel and Azure DevOps made read-only per migrated project.

How it works

  1. Assess drivers, costs, inventory (repos, pipelines, boards, artifacts).
  2. Design target: org structure, EMU, rulesets, runners, OIDC.
  3. Build reusable workflows and starter templates.
  4. Pilot migrate a few teams; gather feedback.
  5. Migrate in waves with GEI and Actions Importer.
  6. Decommission or archive Azure DevOps projects.

Example

gh extension install github/gh-ado2gh
gh ado2gh migrate-repo --ado-org contoso --ado-team-project Shop --ado-repo orders \
  --github-org contoso-eng --github-repo orders
gh actions-importer audit azure-devops --output-dir audit/
gh actions-importer migrate azure-devops pipeline --pipeline-id 42 \
  --target-url https://github.com/contoso-eng/orders --output-dir out/

Common mistakes

  • Migrating repos first and leaving pipelines pointing at old locations.
  • Treating Actions Importer output as finished, without redesign.
  • Ignoring identity and permission mapping until the end.
  • Big-bang migration of every team at once.

How to answer in the interview

"I'd start with the drivers, like Copilot and AI features, the Actions ecosystem, Advanced Security and consolidation, weighed against cost and risk. Repos move easily with full history using GitHub Enterprise Importer. Pipelines are the real work: Actions Importer automates much of the conversion, but templates become reusable workflows, service connections become OIDC federated credentials, environments and checks become GitHub environments with protection rules, and agent pools become runners. Boards can stay in Azure Boards with integration, or move to Issues and Projects. I'd plan identity with Entra ID, run a pilot, then migrate in waves with both systems in parallel."

Likely follow-up questions

  • Features with no direct equivalent? Azure Test Plans, some check types like Azure Monitor gates, delivery plans.
  • Keep Azure Boards? Yes, it integrates with GitHub via AB# links.
  • Private network runners? Larger runners with Azure private networking or self-hosted ARC.
