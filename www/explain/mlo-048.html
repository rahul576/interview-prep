How do you take a model from a data scientist notebook to production code?

MLOps · concept · levels mid, senior

In one line

Move from notebook to production by extracting code into a tested package with separate steps (data loading, features, training, evaluation), replacing hard-coded values with configuration, adding tests and code review, wiring steps into a pipeline with tracking and registry, and working collaboratively from shared templates rather than via a handoff.

Detailed explanation

Notebooks are excellent for exploration but poor production artefacts: hidden state from cells run out of order, hard-coded paths and credentials, global variables, no tests, copy-pasted code, and results that only reproduce on one laptop.

Extract into a package. Move logic into a Python package with modules and functions: data.py for loading, features.py for feature engineering, train.py, evaluate.py. Each step has clear inputs and outputs so it can run as a pipeline stage and be cached or retried.

Configuration. Hard-coded values—paths, dates, hyperparameters, thresholds—become config files (YAML, Hydra) or pipeline parameters. Data access goes through approved connectors and identities, never embedded credentials.

Quality. Unit tests for feature functions and edge cases, data validation, a small end-to-end smoke test, linting and type checks, and code review. Dependencies are pinned.

Pipeline and tracking. Steps are wired into the orchestrator with experiment tracking and registry integration, so training runs in CI and on the platform, not on a laptop, and every model is traceable to code and data.

Culture. The worst pattern is "throw the notebook over the wall" to engineers who rewrite it, introducing skew and resentment. Better: data scientists start from a project template that already has the structure, tests and pipeline; engineers pair with them, and notebooks remain for exploration, calling package functions. Tools like nbdev or Jupytext help keep notebooks reviewable.

How it works

  1. Restart the kernel and run the notebook top to bottom to confirm it works.
  2. Identify steps and extract functions into package modules.
  3. Move constants to config; replace local paths with data connectors.
  4. Add unit tests and a smoke test; set up CI.
  5. Define pipeline steps calling the package; log to tracking.
  6. Review together; keep exploration notebooks importing the package.

Example

churn-model/
  src/churn/data.py        load_training_data(cfg)
  src/churn/features.py    build_features(df) -> DataFrame
  src/churn/train.py       train(df, params) -> model
  src/churn/evaluate.py    evaluate(model, df) -> metrics
  conf/train.yaml          dates, params, thresholds
  tests/test_features.py
  pipeline.py              Kubeflow/Azure ML pipeline using the steps
  notebooks/explore.ipynb  imports churn.features for analysis
# conf/train.yaml
data: {table: features.customers, start: 2025-01-01, end: 2026-09-30}
params: {max_depth: 6, learning_rate: 0.05, n_estimators: 600}
gate: {min_auc: 0.80}

Common mistakes

  • Converting the notebook to a script with all its global state.
  • Engineers rewriting logic from scratch and introducing skew.
  • Credentials in notebook cells.
  • No tests because "it worked in the notebook".

How to answer in the interview

"Notebooks are great for exploration but have hidden state, hard-coded paths and no tests. I extract the logic into a package with separate data, feature, training and evaluation steps, move hard-coded values into configuration, and add unit tests, data validation and code review. The steps are wired into a pipeline with tracking and registry, so it runs in CI and on the platform. Culturally, it works far better as collaboration from the start with a shared project template than as a handoff over the wall."

Likely follow-up questions

  • Which parts of the notebook workflow should data scientists keep? Exploration, visualisation and quick experiments, importing package code.
  • How do you review notebooks? Jupytext pairing or nbdime diffs, and clearing outputs.
  • Who owns the production code? Shared ownership, with data scientists contributing via review.
