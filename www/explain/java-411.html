What are the advantages and disadvantages of microservices compared with a monolith?

Microservices · concept · levels entry, mid

In one line

Microservices give independent deployment and scaling, team autonomy and fault isolation, but cost distributed-system complexity, eventual consistency, harder testing and much more operations; a monolith is simpler, and a modular monolith is often the best starting point.

Detailed explanation

Advantages. Each service can be deployed independently, so a team ships its change without coordinating a big-bang release. Services scale independently: run twenty instances of search and two of admin. Clear service boundaries give team autonomy and ownership ("you build it, you run it"), matching Conway's law for large organisations. Fault isolation means a bug in recommendations need not take down checkout, if timeouts and circuit breakers are in place. Teams can choose technology that fits, and smaller codebases are easier to understand and upgrade.

Disadvantages. You now run a distributed system: network calls are slower and can fail, so you need timeouts, retries, circuit breakers and idempotency. Data consistency is harder: each service owns its database, so no cross-service joins or ACID transactions; you use events, sagas and eventual consistency. Testing across services needs contract tests and environments; debugging needs distributed tracing and centralised logs. The operational overhead grows: many pipelines, containers, Kubernetes, monitoring, service discovery, secrets, versioning. Badly drawn boundaries produce a distributed monolith: all the costs, none of the independence.

A monolith is a single deployable unit: easy to develop, test and run, with simple transactions and refactoring. It is the right choice for small teams, new products with unclear domains, and modest scale. Its problems appear with size: slow builds, coupled releases, one team blocking another. A modular monolith keeps one deployable but enforces strong internal module boundaries (packages, Spring Modulith, ArchUnit tests, no shared tables between modules). It delivers most maintainability benefits cheaply and allows modules to be extracted into services later when there is a real need.

How it works

  1. Start with a modular monolith around business domains.
  2. Enforce module boundaries with tooling.
  3. Measure pain: release contention, scaling hot spots, team size.
  4. Extract the module with the clearest boundary and strongest need.
  5. Add platform capabilities (CI/CD, tracing, discovery) before extracting many services.

Example

// Spring Modulith: verify module boundaries in a test
class ModularityTests {
    @Test
    void verifyModules() {
        ApplicationModules.of(ShopApplication.class).verify(); // fails on illegal cross-module access
    }
}
// Modules: com.shop.orders, com.shop.billing, com.shop.catalog
// billing reacts to orders via published application events, not by calling internals

Common mistakes

  • Choosing microservices for a three-person team "for scalability".
  • Splitting by technical layer instead of business capability.
  • Sharing a database between services.
  • Extracting services before having CI/CD, monitoring and tracing.

How to answer in the interview

"Microservices give independent deployment and scaling, clear team ownership, better fault isolation and some technology freedom, which matters for large systems and many teams. The costs are significant: network latency and failures, eventual consistency instead of simple transactions, harder testing and debugging, and much more operational work. A monolith is simpler and often the right start. My preferred middle ground is a modular monolith with strict module boundaries, for example with Spring Modulith, so we can extract services later when a module has a real need for independent scaling or release cadence."

Likely follow-up questions

  • What signals mean it is time to split? Teams blocking each other's releases, parts with very different scaling needs, long builds, clear stable boundaries.
  • What is a distributed monolith? Services that must be deployed together because of tight coupling or a shared database.
  • How do you extract a service safely? Strangler fig: route a slice of traffic to the new service, migrate data, retire the old code.
