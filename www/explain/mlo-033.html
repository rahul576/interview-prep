Latency of a prediction API increased significantly after a new model release. How do you investigate and fix it?

MLOps · scenario · levels mid, senior

In one line

Compare old and new versions directly: profile the request path with traces (preprocessing, feature lookups, inference, postprocessing), check for a larger model or heavier architecture and resource saturation, roll back first if the SLO is breached, then optimise with quantisation, ONNX Runtime/TensorRT, distillation, batching, caching and autoscaling, and add latency as a promotion gate.

Detailed explanation

Because latency changed with a release, the release is the prime suspect, and the investigation is a diff.

Profile the request path. Distributed tracing (OpenTelemetry spans around preprocessing, feature store calls, model inference and postprocessing) shows where the extra time goes. Compare p50 and p99 per span between versions.

Model cost. The new model may simply be bigger: more trees or deeper trees in a gradient boosting model, more layers or parameters in a neural network, longer input sequences, an ensemble instead of a single model, or a heavier tokeniser. Per-request compute grows accordingly, and on CPU, thread settings (intra-op threads) may now cause contention.

New preprocessing or features. An added feature might require an extra feature store lookup or a synchronous call to another service; an expensive regex or text normalisation step can dominate.

Resource saturation. CPU throttling from container limits, memory pressure causing swapping or garbage-collection pauses, GPU utilisation or GPU memory limits, and fewer requests per replica, which autoscaling hasn't adjusted for.

If the SLO is breached, roll back first, then optimise offline. Options: quantisation (INT8), conversion to ONNX Runtime or TensorRT, distillation into a smaller model, dynamic batching on GPUs, caching frequent predictions or features, parallelising feature lookups, more replicas and better autoscaling. To prevent recurrence, include latency and cost under load in model selection and the promotion gate.

How it works

  1. Confirm the regression with metrics per version (canary split if possible).
  2. Trace spans to find which stage grew.
  3. Compare model size, FLOPs and input lengths.
  4. Check CPU throttling, memory, GC and GPU metrics.
  5. Roll back if SLO breached; optimise and load-test the fix.
  6. Add a latency gate to promotion.

Example

Trace comparison (p99, ms)        v11     v12
  preprocessing                     4       5
  feature_store lookups             9      31   <- 3 new sequential lookups
  inference                        12      19   <- 800 -> 2,000 trees
  total                            28      58   (SLO 40)
Fix: rollback; batch feature lookups into one multi-get; prune trees to 1,000;
     export to ONNX Runtime -> v12.1 p99 = 33 ms

Common mistakes

  • Optimising in production while users suffer instead of rolling back.
  • Assuming the model is the cause without tracing feature lookups.
  • Benchmarking on a laptop instead of production-like hardware.
  • No latency criteria in model selection.

How to answer in the interview

"Since it started with a release, I'd diff old and new. Tracing shows where time goes: preprocessing, feature lookups, inference or postprocessing. Often the new model is just bigger, or new features added lookups. I'd check CPU throttling, memory, GC and GPU utilisation too. If the SLO is breached I roll back first. Then I optimise: quantisation, ONNX Runtime or TensorRT, distillation, batching, caching and parallel feature lookups, plus autoscaling. Finally I add latency under load as an explicit gate so a slower model can't be promoted unnoticed."

Likely follow-up questions

  • How do you include latency in model selection? Report latency and cost per candidate and set a hard p99 limit in the gate.
  • Why does p99 grow more than p50? Queuing, GC pauses and contention hit the tail first.
  • CPU or GPU for this model? Depends on size and batchability; benchmark both.
