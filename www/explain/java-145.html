Which design patterns do you use most in backend code? Explain Strategy, Factory, Builder and Observer.

Design Patterns · concept · levels mid, senior

In one line

Strategy swaps interchangeable algorithms behind an interface, Factory hides object creation, Builder constructs complex objects readably, and Observer lets components react to events without tight coupling; all four appear constantly in Spring backends.

Detailed explanation

Strategy (behavioural): define an interface for an algorithm and several implementations. The caller chooses one at runtime. In a payment service, PaymentStrategy has CardPayment, UpiPayment and WalletPayment. In Spring, every implementation is a bean, and you inject Map<String, PaymentStrategy> (keyed by bean name) or List<PaymentStrategy> and pick by a supports() method. This replaces long if/else or switch chains and satisfies open/closed.

Factory (creational): encapsulates which concrete class gets created. A NotificationSenderFactory.forChannel(channel) returns an email, SMS or push sender, so callers depend only on the NotificationSender interface. JDK static factories like List.of and Optional.of, and Spring's BeanFactory/FactoryBean, follow the idea.

Builder (creational): builds objects with many optional fields through named, chained calls and a final build(), which can validate and return an immutable object. Examples: HttpRequest.newBuilder(), UriComponentsBuilder, WebClient.builder(), Lombok @Builder, and test-data builders.

Observer (behavioural): a subject notifies registered listeners when something happens. In Spring, ApplicationEventPublisher.publishEvent(new OrderPlaced(...)) triggers @EventListener methods for email, inventory and analytics; @TransactionalEventListener can run them after commit, and @Async makes them asynchronous. At system scale the same idea becomes publish/subscribe with Kafka or another broker.

How it works

  1. Spot a variation point (algorithm, creation choice, complex construction, side effects).
  2. Introduce the interface or builder at that point.
  3. Let Spring wire implementations (beans, maps, event listeners).
  4. Keep callers dependent only on the abstraction.

Example

public interface PaymentStrategy { String method(); PaymentResult pay(Order o); }

@Service
class PaymentService {
    private final Map<String, PaymentStrategy> byMethod;
    PaymentService(List<PaymentStrategy> strategies) {
        byMethod = strategies.stream()
            .collect(Collectors.toMap(PaymentStrategy::method, s -> s));
    }
    PaymentResult pay(Order o) {
        return Optional.ofNullable(byMethod.get(o.paymentMethod()))
            .orElseThrow(() -> new IllegalArgumentException("Unsupported"))
            .pay(o);
    }
}

@Component
class OrderEmailListener {
    @TransactionalEventListener   // Observer: runs after commit
    void on(OrderPlaced e) { /* send email */ }
}

Common mistakes

  • Adding patterns where there is only one implementation.
  • Confusing Strategy with State (State changes itself; Strategy is chosen by the client).
  • Synchronous event listeners doing slow work inside the main transaction.
  • Builders on JPA entities that bypass invariants or default values.

How to answer in the interview

"The ones I use most are Strategy, Factory, Builder and Observer. Strategy puts interchangeable algorithms behind an interface; for payments each method is a PaymentStrategy bean and I inject them as a map, so adding a method is one class instead of another switch case. Factory hides which concrete class is created, so callers depend on interfaces. Builder makes objects with many optional fields readable and lets me validate in build, like HttpRequest or Lombok builders. Observer decouples side effects: Spring's ApplicationEventPublisher and EventListener, and at system level Kafka pub/sub."

Likely follow-up questions

  • Which pattern does JdbcTemplate use? Template Method with callbacks: it fixes connection, statement and exception handling, and you supply the SQL and row mapping.
  • How do you make events asynchronous? @Async on the listener with @EnableAsync, or publish to a message broker.
  • Factory vs Builder? Factory decides which object; Builder decides how a complex object is assembled.
