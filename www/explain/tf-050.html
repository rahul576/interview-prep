How do you design a Terraform pipeline in Azure DevOps or GitHub Actions with plan on pull request and approval before apply?

Terraform · concept · levels mid, senior

In one line

On every PR run fmt, validate, lint, security scan and plan with a read-only OIDC identity and post the plan to the PR; after merge, re-plan, save the plan artifact, wait for environment approval and apply that exact plan with a separate privileged identity, with concurrency control per state.

Detailed explanation

The goal is that every infrastructure change is reviewed as code and as a plan, applied by automation, and promoted safely.

PR stage. The pipeline detects which stacks changed and runs terraform fmt -check, validate, tflint, a security scanner and plan for each affected environment. Authentication uses OIDC workload identity federation (GitHub OIDC to Azure or AWS, or Azure DevOps service connections with workload identity), so there are no stored secrets. The plan identity is read-only plus state read and lock access. The plan summary is posted as a PR comment, and policy checks (OPA/Conftest or Sentinel) can fail the check and block merge.

Apply stage. After merge to main, the pipeline plans again against the latest state, because other changes may have landed, and stores the binary plan as an artifact. A protected environment gates the next job: a GitHub environment with required reviewers or an Azure DevOps environment with approvals and checks. The apply job uses a separate identity with write rights, only available to that environment, and runs terraform apply tfplan. Applying a saved plan guarantees that what was approved is exactly what runs; if state changed meanwhile, Terraform rejects the stale plan.

Concurrency. Use a concurrency group per state in GitHub Actions or an exclusive lock check in Azure DevOps, so runs queue instead of racing on the state lock. Promote through environments in order: dev, test, then prod.

How it works

  1. PR opened: detect changed stacks; run checks and plan with read-only identity.
  2. Post plan summary and policy results to the PR; reviewers approve code and plan.
  3. Merge: plan again, save tfplan as an artifact.
  4. Environment approval gate for each stage.
  5. Apply the saved plan with the privileged identity.
  6. Repeat for the next environment.

Example

jobs:
  apply-prod:
    runs-on: ubuntu-latest
    environment: production          # required reviewers
    concurrency: tfstate-prod-network
    permissions:
      id-token: write
      contents: read
    steps:
      - uses: actions/checkout@v4
      - uses: azure/login@v2
        with:
          client-id: ${{ vars.APPLY_CLIENT_ID }}
          tenant-id: ${{ vars.TENANT_ID }}
          subscription-id: ${{ vars.SUBSCRIPTION_ID }}
      - uses: actions/download-artifact@v4
        with: { name: tfplan-prod }
      - run: terraform init && terraform apply tfplan

Common mistakes

  • One all-powerful identity for both plan and apply.
  • Applying a fresh plan nobody reviewed instead of the saved one.
  • No concurrency control, causing lock errors or racing applies.
  • Long-lived client secrets instead of OIDC.
  • Posting full plans with sensitive values into PR comments.

How to answer in the interview

"On every pull request I run fmt, validate, tflint, a security scanner and plan for each affected environment, using a read-only identity via OIDC, and post the plan to the PR so reviewers see the real impact; policies can block the merge. After merge, the pipeline plans again, saves the plan as an artifact and waits on a protected environment approval. Apply uses that saved plan with a separate, more privileged identity. Concurrency is serialised per state, and environments are promoted dev, test, prod."

Likely follow-up questions

  • Why apply-before-merge like Atlantis? Main then only contains code that applied successfully.
  • What if the saved plan is stale? Terraform refuses it; re-plan and re-approve.
  • How do you handle plan secrets? Mark values sensitive and post summaries, not raw output.
