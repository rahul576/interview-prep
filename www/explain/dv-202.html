Explain the basic Terraform workflow and its main commands.

Infrastructure as Code · concept · levels entry

In one line

Write HCL with providers, resources, variables and outputs; terraform init downloads providers/modules and configures the backend; fmt and validate check the code; plan shows exactly what will be created, changed or destroyed; apply executes it; destroy removes everything; and the state file tracks what Terraform manages.

Detailed explanation

A Terraform project is a directory of .tf files. A terraform block sets the required Terraform and provider versions and the backend (where state is stored). A provider block configures, for example, aws with a region. resource blocks describe infrastructure objects; variable blocks are inputs, output blocks are results, and data blocks read existing information.

The core workflow:

  • terraform init: run first and whenever providers, modules or backend change. It downloads providers into .terraform/, writes or verifies .terraform.lock.hcl (exact provider versions and checksums) and connects to the backend.
  • terraform fmt formats code to the standard style; terraform validate checks syntax, types and references without contacting the cloud.
  • terraform plan reads the configuration, refreshes the state against the real infrastructure and shows the execution plan: + create, ~ update in place, -/+ replace, - destroy, with a summary like "Plan: 3 to add, 1 to change, 0 to destroy". This is what reviewers look at. Save it with -out=tfplan.
  • terraform apply executes a plan (asking for confirmation unless a saved plan is given) and updates the state.
  • terraform destroy removes everything in the configuration; use carefully.

Other useful commands: terraform output, terraform state list, terraform show, terraform providers, terraform console.

The state file records which real resources belong to which blocks. For teams it must be in a remote backend with locking (S3, Azure Storage, GCS, HCP Terraform). In CI, the pipeline should apply the exact saved plan that was reviewed, so nothing changes between review and apply.

How it works

  1. Write/modify .tf files.
  2. init → fmt → validate.
  3. plan -out=tfplan → review in a PR.
  4. apply tfplan → state updated in backend.
  5. Repeat; destroy only for disposable environments.

Example

terraform {
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.0" }
  }
  backend "s3" {
    bucket = "acme-tfstate"
    key    = "dev/app.tfstate"
    region = "eu-west-1"
    use_lockfile = true
  }
}
provider "aws" { region = "eu-west-1" }

resource "aws_s3_bucket" "assets" { bucket = "acme-dev-assets" }
output "bucket_arn" { value = aws_s3_bucket.assets.arn }
terraform init
terraform fmt -check && terraform validate
terraform plan -out=tfplan
terraform apply tfplan

Common mistakes

  • Running apply without reading the plan.
  • Forgetting to re-run init after adding a provider or module.
  • Not committing .terraform.lock.hcl (but committing the .terraform/ directory).
  • Local state for shared infrastructure.

How to answer in the interview

"I write configuration in HCL: a provider block like aws or azurerm, resource blocks for things like a VPC or bucket, and variables and outputs. terraform init downloads the providers and modules, writes the lock file and configures the backend where state lives. fmt and validate format and check the code. plan compares the configuration with the state and real infrastructure and shows exactly what will be created, changed, replaced or destroyed, which is what reviewers look at. apply executes that plan, ideally the saved one from review, and destroy removes everything. Terraform tracks what it manages in the state file, which for teams is stored remotely with locking."

Likely follow-up questions

  • Why apply exactly the reviewed plan? Infrastructure or code can change between plan and apply; a saved plan guarantees what was approved runs (and fails if state changed).
  • What does -/+ mean? The resource must be destroyed and recreated, usually because an immutable argument changed.
  • What is the lock file for? It pins exact provider versions and checksums for reproducible runs.
