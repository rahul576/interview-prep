What is agentic RAG, and how does it differ from a fixed retrieval pipeline?

LLMOps & RAG · concept · levels mid, senior

In one line

Agentic RAG turns retrieval into tools the model calls when it decides to, choosing which source, how to phrase queries and whether results suffice, iterating before answering; a fixed pipeline retrieves once from one index every time. Agentic is better for complex questions but costs more latency, tokens and predictability, so it needs step limits and tool-use evaluation.

Detailed explanation

A classic pipeline is deterministic: rewrite query, search, rerank, stuff top-k chunks into the prompt, generate. It is fast, cheap and easy to evaluate, but it always retrieves (even for "thanks!"), always from the same place, and gets one shot. If the first query misses, the answer is wrong.

In agentic RAG, the model receives tools such as search_kb, search_tickets, get_order(id) or read_document(id) with good descriptions. It reasons about the question, calls one or more tools, reads the results, and decides to refine the query, try another source, or answer. This handles multi-part questions ("is my order covered by the new returns policy?" needs order data plus the policy), ambiguous queries that benefit from reformulation, and questions where no retrieval is needed.

The trade-offs: several model round trips add seconds and tokens; behaviour varies between runs; and new failure modes appear, including loops, repeated searches, wrong tool choice, and indirect prompt injection via retrieved content. You must therefore cap steps and tokens, log every tool call, and evaluate trajectories (did it call the right tools with sensible arguments?) as well as final answers.

How it works

  1. Define tools with clear names, descriptions and argument schemas.
  2. Model receives question and tools; decides on a tool call or answers directly.
  3. Application executes the tool with the user's permissions; returns results.
  4. Model judges sufficiency; refines or calls another tool.
  5. Stop at a final answer or at the step/token limit, with a fallback.
  6. Trace each step for debugging and evaluation.

Example

tools = [search_kb, search_tickets, get_order]
for step in range(MAX_STEPS):          # e.g. 5
    resp = llm.chat(messages, tools=tools)
    if not resp.tool_calls:
        return resp.text
    for call in resp.tool_calls:
        result = run_tool(call, user=current_user)   # permission-checked
        messages.append(tool_result(call.id, result))
return "I couldn't find a confident answer; escalating to support."

Common mistakes

  • No step or budget limit, leading to loops.
  • Vague tool descriptions, so the model picks the wrong source.
  • Evaluating only final answers, not tool use.
  • Going agentic when 90% of questions are simple lookups.

How to answer in the interview

"A fixed pipeline retrieves once from one index and generates. Agentic RAG exposes retrieval as tools, so the model decides whether to search, which source, how to phrase the query, and whether to search again before answering. That handles multi-part questions, like combining policy documents with live order data, much better. The price is latency, token cost and less predictable behaviour, so I cap steps, write precise tool descriptions, trace everything and evaluate tool choices as well as answers. For simple Q&A I'd keep the fixed pipeline, or route only complex questions to the agent."

Likely follow-up questions

  • Support assistant: which approach? Fixed pipeline for FAQs; agentic for account-specific questions needing live data.
  • How evaluate trajectories? Expected tool sequences, judge-scored steps, step count and cost per task.
  • Security risk? Retrieved content can inject instructions; tools run with user permissions and least privilege.
