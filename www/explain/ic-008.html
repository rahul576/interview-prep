Which tools help keep Terraform code clean and correct before planning?

Infrastructure as Code · concept · levels entry

In one line

Run terraform fmt (style), terraform validate (syntax, types, references), tflint (provider-aware linting) and security scanners like Checkov or Trivy (misconfigurations) in pre-commit hooks and CI before terraform plan.

Detailed explanation

Cheap, fast checks catch most problems before anyone looks at a plan, so reviewers can focus on design.

terraform fmt rewrites .tf files into the canonical style (indentation, alignment of =). In CI, terraform fmt -check -recursive fails the build when files are not formatted, which removes style debates from code review.

terraform validate checks that the configuration is syntactically valid and internally consistent: correct argument names, types, references to existing variables and resources. It needs terraform init (it can use -backend=false) to load provider schemas, but it does not call cloud APIs or read state.

tflint goes further with pluggable rule sets for AWS, Azure and Google. It catches errors validate cannot know about, such as an invalid instance type or region, deprecated syntax, unused declarations and missing version constraints, and can enforce naming conventions.

Security and compliance scanners look for risky configuration: unencrypted buckets or disks, public S3 access, security groups open to 0.0.0.0/0 on SSH, missing logging. Checkov and Trivy are the common choices; tfsec has been merged into Trivy, which is now the recommended path for tfsec users. Cost tools like Infracost are often added to the same pipeline.

How it works

  1. Developer commits; pre-commit runs fmt, validate and tflint locally.
  2. The pull request pipeline repeats them, so nothing depends on local setup.
  3. A security scanner runs and fails on high-severity findings.
  4. Only then terraform plan runs and its output is posted for review.
  5. Accepted risks are suppressed explicitly with a justification.

Example

# .pre-commit-config.yaml
repos:
  - repo: https://github.com/antonbabenko/pre-commit-terraform
    rev: v1.96.1
    hooks:
      - id: terraform_fmt
      - id: terraform_validate
      - id: terraform_tflint
      - id: terraform_trivy
terraform fmt -check -recursive
terraform init -backend=false && terraform validate
tflint --init && tflint --recursive
checkov -d . --quiet
resource "aws_s3_bucket" "public_site" {
  #checkov:skip=CKV_AWS_18:Access logging not required for static marketing site
  bucket = "example-site"
}

Common mistakes

  • Running checks only locally, so they are skipped by anyone without hooks.
  • Thinking validate catches wrong instance types or permissions; it does not.
  • Blanket-disabling scanner rules instead of inline, justified suppressions.
  • Scanning only code and never the plan for computed values.

How to answer in the interview

"I layer the checks. terraform fmt, with -check in CI, keeps formatting consistent. terraform validate checks syntax, types and references without touching the cloud. tflint adds provider-aware rules, like invalid instance types, deprecated arguments, unused variables and naming conventions. Then a security scanner such as Checkov or Trivy flags things like unencrypted buckets or SSH open to the world. All of them run as pre-commit hooks and again in the pull request pipeline before plan, so reviewers spend their time on real design questions."

Likely follow-up questions

  • How would you suppress a scanner finding that is an accepted risk? An inline skip comment with the rule ID and a reason, or a reviewed baseline/config file.
  • Does validate need credentials? No, only provider schemas from init.
  • Code scanning vs plan scanning? Plan scanning sees computed values and module results.
