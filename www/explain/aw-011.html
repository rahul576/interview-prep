What is Amazon CloudFront, and when do you use it?

Cloud (AWS) · concept · levels entry

In one line

CloudFront is AWS's CDN: it caches content at edge locations worldwide so users get responses from nearby with lower latency, while origins (S3, ALB, any HTTP server) receive far less load; it also provides HTTPS, WAF and Shield integration, per-path cache behaviours, TTLs and invalidations.

Detailed explanation

Without a CDN, a user in Sydney fetching images from a server in Ireland pays a long round trip for every request, and the origin serves every byte. CloudFront places copies of content in hundreds of edge locations plus regional edge caches. The first request for an object at an edge is a cache miss and goes to the origin; later requests are cache hits served locally. Even uncached dynamic requests benefit because they travel over AWS's backbone with persistent, optimised connections.

A distribution has one or more origins: an S3 bucket (kept private using Origin Access Control), an Application Load Balancer, API Gateway, a VPC origin for private resources, or any custom HTTP server. Cache behaviours match path patterns such as /static/ or /api/ and set the origin, allowed methods, protocol policy, and a cache policy that defines TTLs and which headers, cookies and query strings form the cache key. An origin request policy controls what is forwarded without fragmenting the cache. Good cache keys maximise the hit ratio.

Security features: free TLS certificates from ACM (in us-east-1), HTTP to HTTPS redirect, AWS WAF rules against injection and bots, Shield Standard DDoS protection included, signed URLs or cookies for private content, and geo-restriction. CloudFront Functions and Lambda@Edge run code at the edge for redirects, header rewrites or auth checks.

When content changes, either use versioned file names (app.3f9c2.js) with long TTLs, which is best practice, or create an invalidation to remove paths from caches.

How it works

  1. DNS points cdn.example.com (alias) at the distribution.
  2. The user hits the nearest edge location.
  3. The edge checks its cache using the cache key.
  4. Hit: respond immediately. Miss: fetch from the regional cache or origin, store, respond.
  5. Objects expire per TTL or are invalidated.

Example

# After deploying a new index.html (assets use hashed names)
aws cloudfront create-invalidation \
  --distribution-id E1ABCDEF2GHIJ --paths "/index.html"

Setup for a single-page app: private S3 bucket with OAC as the default origin, /api/* behaviour to an ALB with caching disabled and all headers forwarded, hashed static assets cached for a year, index.html cached for 60 seconds, WAF attached.

Common mistakes

  • Leaving the S3 bucket public so users bypass CloudFront.
  • Forwarding all headers and cookies, which destroys the hit ratio.
  • Relying on frequent wildcard invalidations instead of versioned assets.
  • Requesting the ACM certificate in the wrong region.

How to answer in the interview

"CloudFront is the AWS CDN. It caches content at edge locations around the world, so users get static assets, images, video and even some API responses from nearby, with lower latency, and the origin, S3, a load balancer or any HTTP server, gets far fewer requests. It terminates HTTPS with free ACM certificates, integrates with WAF and Shield, and lets me define cache behaviours per path with their own TTLs and origins. For deployments I use versioned file names so caches never serve stale assets, and an invalidation for entry files like index.html."

Likely follow-up questions

  • How do you stop users bypassing CloudFront to S3? Keep the bucket private and allow only the distribution via Origin Access Control.
  • What affects cache hit ratio? The cache key: minimise headers, cookies and query strings included.
  • CloudFront Functions vs Lambda@Edge? Functions are lightweight and cheap for simple header or URL logic; Lambda@Edge handles heavier logic and network calls.
