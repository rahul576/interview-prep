When would you use Kafka Streams or Kafka Connect?

Kafka · concept · levels senior, lead

In one line

Kafka Streams is a Java library embedded in your application for stateful stream processing (joins, windowed aggregations, local state stores), whereas Kafka Connect is a separate framework of source and sink connectors for moving data between Kafka and external systems without custom code.

Detailed explanation

Kafka Streams is not a cluster you deploy; it is a dependency in a normal service. You write a topology with the DSL (KStream, KTable, GlobalKTable) or the Processor API. It supports filters and maps, stream-table joins (enrich orders with customer data), windowed aggregations (tumbling, hopping, sliding, session windows) and stateful operations backed by local RocksDB state stores. Each store is replicated to a compacted changelog topic, so a failed instance's state can be rebuilt elsewhere; standby replicas keep warm copies to speed this up. Scaling means running more instances of the app; tasks map to input partitions. With processing.guarantee=exactly_once_v2, reads, state updates and writes are transactional.

Kafka Connect runs as its own worker cluster (or managed service) with a REST API. You configure connectors in JSON rather than writing code. Source connectors pull data into Kafka: Debezium for change data capture from PostgreSQL, MySQL, SQL Server or MongoDB, JDBC source, file or MQTT sources. Sink connectors push data out: Elasticsearch/OpenSearch, S3, JDBC databases, Snowflake, BigQuery. Connect handles offsets, scaling with tasks, retries, converters (Avro, JSON, Protobuf) and lightweight Single Message Transforms, plus error tolerance with dead letter queues.

The rule of thumb: Connect moves data, Streams applies business logic. A common pipeline uses Debezium to capture database changes, a Streams app to enrich and aggregate them, and a sink connector to load results into Elasticsearch. For heavier, cross-language or SQL-based processing, Apache Flink is the main alternative.

How it works

  1. Debezium source reads the database WAL into db.orders.
  2. Streams app joins db.orders with a customers KTable.
  3. It aggregates revenue per 5-minute window into a state store.
  4. Results are written to orders-enriched and revenue-5m.
  5. Elasticsearch sink connector indexes orders-enriched.

Example

StreamsBuilder b = new StreamsBuilder();
KTable<String, Customer> customers = b.table("customers");
b.<String, Order>stream("db.orders")
 .selectKey((k, o) -> o.customerId())
 .join(customers, (o, c) -> new EnrichedOrder(o, c))
 .to("orders-enriched");

Common mistakes

  • Writing custom consumers to copy data into Elasticsearch instead of using a sink connector.
  • Putting complex business logic into Single Message Transforms.
  • Forgetting co-partitioning requirements for Streams joins.
  • Ignoring state restore time when scaling Streams apps.

How to answer in the interview

"Kafka Streams is a Java library I embed in my own service to process streams: filtering, joining streams with tables, windowed aggregations, with local RocksDB state backed by compacted changelog topics and exactly-once support. It scales by running more instances. Kafka Connect is a separate framework for integration without code: source connectors like Debezium bring data in, sink connectors push it to Elasticsearch, S3 or databases. I use Connect for moving data and Streams for business logic."

Likely follow-up questions

  • How does Streams recover state? Restores the store from its changelog topic, faster with standby replicas.
  • Streams vs Flink? Flink is a separate cluster with richer event-time and SQL features; Streams is simpler to embed.
  • How do you scale Connect? Increase tasks.max and add workers in distributed mode.
