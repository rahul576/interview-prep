How do you configure MCP servers in hosts such as Claude Desktop, VS Code or Cursor?

MCP Servers · concept · levels entry, mid, senior

In one line

Hosts use JSON configuration listing servers: command, args and env for local stdio servers, a URL (with host-managed OAuth sign-in) for remote ones, at workspace or user level; avoid plain-text secrets by using input prompts, secret stores, env references or OAuth, and manage allowed servers with organisation policies.

Detailed explanation

Local stdio servers. Each entry names a server and gives the command, args and optional env. Typical commands are npx -y <package>, uvx <package>, uv run with a script path, docker run -i --rm <image>, or an absolute path to a binary.

Where configs live:

  • Claude Desktop: claude_desktop_config.json (edited via Settings → Developer) with an mcpServers object; desktop extensions offer one-click installs.
  • VS Code: an mcp.json file, either in the workspace (.vscode/mcp.json, shareable with the team via Git) or in user settings, with a servers object and an inputs section.
  • Cursor: .cursor/mcp.json in a project or ~/.cursor/mcp.json globally.
  • Claude Code: claude mcp add commands, with local, project (.mcp.json) and user scopes.

Remote servers are configured with a URL (and transport type where needed). When the server requires authorization, the host runs the OAuth flow: discovers the authorization server, opens the browser for sign-in and stores tokens securely. No token is pasted into a file.

Secrets. The classic mistake is putting API keys in plain text in these files, which then get committed to Git or synced. Better options: VS Code-style inputs that prompt once and store values in the OS keychain; referencing environment variables or a secret manager; or preferring remote servers with OAuth.

Governance. Config files that launch commands are effectively code: a malicious .vscode/mcp.json in a cloned repository could run arbitrary programs, which is why hosts ask for trust/confirmation before starting workspace servers. Organisations can manage allowed servers centrally through enterprise policies, private registries and allowlists, and should review MCP config changes in pull requests.

How it works

  1. Choose scope: workspace (shared) or user (personal).
  2. Add a server entry: command/args/env, or URL.
  3. Reference secrets via inputs, env or OAuth, never literals.
  4. Restart or reload the host; approve the server.
  5. Check the host's MCP logs or server list for status.

Example

// .vscode/mcp.json (workspace, committed)
{
  "inputs": [
    { "id": "jira-token", "type": "promptString", "description": "Jira API token", "password": true }
  ],
  "servers": {
    "jira": {
      "command": "npx", "args": ["-y", "example-jira-mcp@2.4.1"],
      "env": { "JIRA_URL": "https://jira.example.com", "JIRA_TOKEN": "${input:jira-token}" }
    },
    "docs": { "type": "http", "url": "https://mcp.docs.example.com/mcp" }
  }
}

Common mistakes

  • Plain-text API keys committed with workspace configs.
  • Unpinned npx packages pulling new versions automatically.
  • Relative paths that depend on the host's working directory.
  • Blindly trusting MCP configs in cloned repositories.

How to answer in the interview

"Hosts use a JSON config listing servers by name. Local stdio servers have a command, args and optional env, for example npx with a package or uv run with a script path. Claude Desktop uses claude_desktop_config.json, VS Code uses mcp.json either in the workspace, so the team shares it, or in user settings. Remote servers just get a URL, and the host handles OAuth sign-in, so no token is pasted. The common mistake is plain-text API keys in these files that end up in Git; better are input prompts stored securely, environment references or OAuth. Organisations can also manage allowed servers centrally with policies."

Likely follow-up questions

  • Why review MCP configs in PRs? They launch programs and grant access, so they are code with security impact.
  • Pin versions? Yes; pinned packages or image digests prevent surprise updates.
  • Workspace versus user config? Workspace for team-shared, non-secret setup; user for personal tools and credentials.
