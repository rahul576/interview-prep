What is the difference between method overloading and method overriding?

Core Java & OOP · concept · levels entry, mid

In one line

Overloading is several methods with the same name but different parameter lists, chosen by the compiler (compile-time); overriding is a subclass redefining an inherited method with the same signature, chosen by the JVM at runtime based on the actual object.

Detailed explanation

Overloading happens within one class (or across a class and its superclass): print(int), print(String), print(String, int). Parameter lists must differ in number, type or order; the return type alone does not count. The compiler selects the most specific applicable method based on the static (declared) types of the arguments, in phases: exact match and widening first, then boxing/unboxing, then varargs. That is compile-time (static) polymorphism. Because it uses static types, Object o = "hi"; print(o) calls print(Object) even though o holds a String. Ambiguous overloads cause compile errors, and overloading with boxing (remove(int) vs remove(Object) on List<Integer>) is a well-known trap.

Overriding happens between a superclass (or interface) and a subclass. The subclass provides a method with the same name and parameter types. At runtime the JVM uses dynamic dispatch (virtual method tables) to call the implementation of the actual object's class, not the reference type: this is runtime polymorphism. Rules:

  • Return type may be the same or a covariant subtype (Animal create() overridden by Dog create()).
  • Access cannot be more restrictive (a public method cannot become protected).
  • It cannot throw new or broader checked exceptions (it may throw fewer, narrower or unchecked ones).
  • final methods cannot be overridden; static methods are hidden, not overridden; private methods are not inherited, so a same-named method is a new method.
  • Call the parent version with super.method().

Always use @Override: the compiler then errors if you are not actually overriding, catching mistakes like equals(Order o) (an overload) instead of equals(Object o).

How it works

  1. Compiler sees obj.method(args).
  2. It picks the method signature using the declared type of obj and argument types (overload resolution).
  3. Bytecode records that signature (invokevirtual/invokeinterface).
  4. At runtime the JVM looks up the actual class of obj and finds its override of that signature.
  5. That implementation runs.

Example

class PriceCalculator {
    BigDecimal price(Product p)            { return p.basePrice(); }          // overloads
    BigDecimal price(Product p, int qty)   { return price(p).multiply(BigDecimal.valueOf(qty)); }
}

class Notification {
    protected Object payload() throws IOException { return "text"; }
    public void send() { System.out.println("generic"); }
}

class EmailNotification extends Notification {
    @Override public String payload() { return "<html/>"; }  // covariant return, wider access, no exception
    @Override public void send() { System.out.println("email"); }
}

Notification n = new EmailNotification();
n.send();                         // "email": runtime dispatch on actual object

class Printer {
    void print(Object o) { System.out.println("object"); }
    void print(String s) { System.out.println("string"); }
}
Object o = "hi";
new Printer().print(o);           // "object": overload chosen by static type

Common mistakes

  • Thinking a different return type alone is an overload.
  • Writing equals(MyType) and believing it overrides equals(Object).
  • Expecting overloads to be chosen by the runtime type of arguments.
  • Omitting @Override.

How to answer in the interview

"Overloading means several methods with the same name but different parameter lists, usually in the same class, and the compiler picks one at compile time based on the declared argument types. Overriding means a subclass provides its own implementation of an inherited method with the same signature, and the JVM picks the implementation at runtime based on the actual object. When overriding, the return type can be covariant, the access modifier can't be weaker, and I can't throw broader checked exceptions. I always add @Override so the compiler catches mistakes like accidentally overloading equals."

Likely follow-up questions

  • Can you override a static or private method? No; a static method with the same signature hides the parent's, and private methods are not inherited, so a same-named method is unrelated.
  • Can you overload main? Yes, but the JVM only calls the standard entry-point signature.
  • What is double dispatch? Choosing behaviour by the runtime types of two objects, typically with the visitor pattern, because Java overload resolution is static.
