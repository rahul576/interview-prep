What is the smallest set of things you must pin to make a training run reproducible?

MLOps · concept · levels mid, senior, lead

In one line

Pin the code commit, an immutable data snapshot, the feature transformation code and config, exact dependencies including CUDA and the framework (ideally an image digest), hyperparameters and seeds, and the hardware class; even then GPU nondeterminism means aiming for statistically equivalent results.

Detailed explanation

Code: the Git commit of the training code and of any feature pipeline code, with no uncommitted changes. A dirty working tree is a common reason runs cannot be reproduced.

Data: an immutable snapshot, not a live table that keeps changing. Use a Delta or Iceberg table version, a DVC hash, a dated Parquet export or a dataset version in your platform, and record the exact query, filters and date range. The train/validation/test split must be reproducible too: store the split or its seed and logic.

Features: the transformation code and configuration (window sizes, encodings, vocabularies, scaling parameters). Features are often computed by a separate pipeline, so pinning only the training script is not enough.

Environment: exact versions of Python packages (a lock file), the ML framework (PyTorch, TensorFlow, XGBoost), CUDA and cuDNN and drivers. The most reliable way is to run training in a container referenced by image digest, not a tag.

Configuration and randomness: hyperparameters and random seeds for every library (Python, NumPy, the framework, data loader workers).

Hardware: where numerics matter, the GPU type and count. Different GPUs, numbers of workers or batch partitioning change floating-point summation order.

Even with all this, GPU training is often not bit-for-bit reproducible: some kernels use non-deterministic atomic operations, and distributed training adds ordering differences. Frameworks offer deterministic modes (in PyTorch, torch.use_deterministic_algorithms(True) plus cuDNN settings), but they can be slower and some operations are unsupported. The practical goal is statistically equivalent results within a tolerance, which suffices for debugging and most audits.

How it works

  1. Commit all code; record the SHA.
  2. Snapshot data and record its version and split.
  3. Build a container image; record its digest.
  4. Log hyperparameters and set seeds everywhere.
  5. Record hardware type and count.
  6. Re-run and compare metrics within tolerance.

Example

import os, random, numpy as np, torch
SEED = 42
random.seed(SEED); np.random.seed(SEED); torch.manual_seed(SEED)
torch.cuda.manual_seed_all(SEED)
os.environ["CUBLAS_WORKSPACE_CONFIG"] = ":4096:8"
torch.use_deterministic_algorithms(True)     # slower; only when needed
torch.backends.cudnn.benchmark = False
run_manifest:
  code_commit: 9f2c41e
  data: s3://ml-data/churn/snapshot=2026-11-01 (delta version 412)
  image: registry.example.com/train@sha256:5b1e...
  params: { lr: 0.001, epochs: 30, batch: 256 }
  seed: 42
  hardware: 1x NVIDIA L4

Common mistakes

  • Training on a live table that changes underneath.
  • Pinning Python packages but not CUDA or drivers.
  • Using image tags like latest instead of digests.
  • Promising bit-for-bit reproducibility on GPUs without deterministic settings.

How to answer in the interview

"I pin the code commit of the training and feature code, an immutable data snapshot rather than a changing table, and the feature transformation code and configuration. Dependencies must be exact, including the framework, CUDA and cuDNN, ideally by using the same container image digest. Hyperparameters and random seeds are logged and fixed, and where numerics matter, the GPU type too. Even then, GPU training is often not bit-for-bit reproducible because of nondeterministic kernels and parallelism, and deterministic modes are slower, so in practice I aim for statistically equivalent results within tolerance."

Likely follow-up questions

  • When is bit-for-bit reproducibility worth its cost? In regulated audits, debugging subtle regressions or research comparisons where tiny differences matter.
  • How do you prove equivalence? Re-run several seeds and compare metric distributions within a tolerance.
  • Why does batch size or worker count matter? It changes the order of floating-point operations and gradient updates.
