What is the difference between EBS, instance store and EFS?

Cloud (AWS) · concept · levels entry

In one line

EBS is persistent network block storage attached to one instance in one AZ, instance store is ephemeral, physically attached disk that is very fast but loses data on stop, and EFS is a shared, managed NFS file system that many instances across AZs mount at once.

Detailed explanation

EBS (Elastic Block Store) volumes behave like virtual hard disks. They live in one Availability Zone and attach to an instance in that AZ, usually one at a time (io1/io2 support Multi-Attach for clustered applications). Data persists independently of the instance: you can stop, start or replace the instance and reattach the volume. Snapshots are incremental, point-in-time backups stored in S3-backed storage; they can be copied across regions and used to create volumes in another AZ. EBS is the standard choice for boot volumes and databases on EC2.

Instance store is NVMe or SSD storage physically attached to the host on certain instance types (for example the d variants like m6id or storage-optimised i4i). It delivers very high IOPS and low latency at no extra cost, but it is ephemeral: data is lost when the instance stops, hibernates, terminates or the underlying host fails (it survives a reboot). It suits caches, buffers, scratch space and replicated data stores such as Cassandra or Kafka that already keep copies elsewhere.

EFS (Elastic File System) is a managed NFSv4 file system. Thousands of EC2 instances, ECS or EKS containers and Lambda functions in multiple AZs can mount it simultaneously, and it grows and shrinks automatically. It is ideal for shared content: uploads, CMS media, home directories or shared configuration. Latency is higher than EBS and price per GB is higher too, mitigated by lifecycle tiers (Infrequent Access, Archive). It works with Linux; Windows workloads use FSx for Windows File Server.

How it works

  1. EBS: create a volume in an AZ, attach, format, mount; snapshot for backup.
  2. Instance store: choose an instance type that includes it; format at boot.
  3. EFS: create a file system with mount targets in each AZ, mount via NFS or the EFS mount helper.
  4. Pick by sharing need, durability and performance.

Example

# EBS: attach and mount a data volume
aws ec2 attach-volume --volume-id vol-0abc --instance-id i-0123 --device /dev/sdf
sudo mkfs -t xfs /dev/nvme1n1 && sudo mount /dev/nvme1n1 /data

# EFS: mount shared uploads on every web server
sudo mount -t efs -o tls fs-0a1b2c3d:/ /var/www/uploads

A PostgreSQL server on EC2 uses EBS gp3/io2; the web tier shares user uploads via EFS; a build server uses instance store for temporary compile output.

Common mistakes

  • Storing important data on instance store.
  • Expecting an EBS volume to attach to an instance in another AZ.
  • Using EFS for a latency-sensitive database.
  • No snapshot schedule for EBS.

How to answer in the interview

"EBS is network block storage, like a virtual disk, attached to one instance in one AZ; data persists independently of the instance and I back it up with snapshots. Instance store is physically attached to the host, extremely fast but ephemeral, so data is lost if the instance stops or the host fails, which is fine for caches and scratch data. EFS is a managed NFS file system that many instances, containers or Lambdas across AZs can mount at once, good for shared files, with higher latency and cost than EBS. For a database on EC2 I'd use EBS; for shared uploads, EFS or ideally S3."

Likely follow-up questions

  • Database vs shared uploads? Database on EBS; shared uploads on EFS, or better S3.
  • How do you move an EBS volume to another AZ? Snapshot it and create a new volume from the snapshot in the target AZ.
  • Does instance store survive a reboot? Yes, but not a stop, terminate or host failure.
