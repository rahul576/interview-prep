Messages keep ending up in the Azure Service Bus dead-letter queue. How do you investigate and handle them?

Azure · scenario · levels mid, senior

In one line

Service Bus dead-letters a message when it exceeds MaxDeliveryCount, its TTL expires (with dead-lettering on expiration enabled) or a consumer explicitly dead-letters it; investigate by reading DeadLetterReason and DeadLetterErrorDescription, fix the root cause (poison data, bug, dependency), resubmit through a controlled, idempotent replay, and alert on the DLQ count.

Detailed explanation

Every queue and subscription has a dead-letter subqueue (<queue>/$deadletterqueue). Messages go there for clear reasons:

  • MaxDeliveryCountExceeded: in peek-lock mode the consumer abandoned the message, threw an exception, or let the lock expire, so it was redelivered until the count (default 10) was reached.
  • TTLExpiredException: the message's time to live passed and dead-lettering on message expiration is enabled.
  • Explicit dead-letter: the consumer called DeadLetterMessageAsync with a reason, for example a schema validation failure.
  • Filter evaluation errors on subscriptions, or header size limits.

Investigation means looking at the data, not guessing. Peek DLQ messages with Service Bus Explorer in the portal or a script, group by reason and error description, and correlate with Application Insights traces from the consumer using the message ID or correlation ID. Typical causes: a poison message (malformed payload, unexpected nulls), a bug in a new release, a schema change by the producer, a downstream dependency failing (all messages fail), or processing slower than the lock duration so locks expire.

After fixing the cause, resubmit: read from the DLQ, optionally repair, send to the main queue, then complete the DLQ copy. Consumers must be idempotent, because some messages may have been partly processed. Never resubmit poison messages blindly in a loop.

Prevention: retry with backoff inside the handler for transient errors, explicit dead-lettering with clear reasons for permanent errors, renewing locks for long processing, and alerts on the DeadletteredMessages metric.

How it works

  1. Alert fires on dead-letter count > 0 (or a rising trend).
  2. Peek messages; group by DeadLetterReason and description.
  3. Correlate with consumer logs and recent deployments.
  4. Fix code, data contract or dependency.
  5. Replay with a tool, at a controlled rate, to an idempotent consumer.
  6. Track remaining unprocessable messages for manual handling.

Example

var receiver = client.CreateReceiver("orders", new ServiceBusReceiverOptions {
    SubQueue = SubQueue.DeadLetter });
var sender = client.CreateSender("orders");
foreach (var msg in await receiver.ReceiveMessagesAsync(50)) {
    Console.WriteLine($"{msg.MessageId} {msg.DeadLetterReason} {msg.DeadLetterErrorDescription}");
    if (IsFixable(msg)) {
        await sender.SendMessageAsync(new ServiceBusMessage(msg));   // copy body and properties
        await receiver.CompleteMessageAsync(msg);
    }
}

Common mistakes

  • Nobody monitors the DLQ, so messages sit there for weeks.
  • Catching exceptions and completing the message, silently losing data.
  • Resubmitting everything to a non-idempotent consumer.
  • Lock duration shorter than processing time.

How to answer in the interview

"A message is dead-lettered when it exceeds the max delivery count, when its TTL expires with dead-lettering on expiry enabled, or when the consumer dead-letters it explicitly. I peek the DLQ with Service Bus Explorer or a script and group by DeadLetterReason and the error description, then correlate with consumer logs and recent releases. Usually it's a poison message, a bug, a schema change or a failing dependency. After the fix I replay messages in a controlled way to an idempotent consumer, and I alert on the dead-letter count so we notice in minutes, not days."

Likely follow-up questions

  • Sessions and ordering? A failed message blocks its session; dead-lettering breaks order, so the consumer may need to park the whole session.
  • Abandon vs dead-letter? Abandon for transient errors (retry), dead-letter for permanent ones.
  • Scheduled retries? Re-send with ScheduledEnqueueTime for delayed retry.
