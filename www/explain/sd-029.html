Design a file sync and storage service like Dropbox or OneDrive.

Classic Design Problems · design · levels mid, senior, lead

In one line

File sync splits files into content-hashed chunks, uploads only new or changed chunks (delta sync + dedup), stores chunks in object storage and file versions in a metadata service, and notifies other devices to pull changes, keeping conflicted copies on concurrent edits.

Detailed explanation

Re-uploading a 2 GB file because one paragraph changed is wasteful. Chunking (fixed-size, or content-defined chunking so an insert doesn't shift every later chunk) lets the client compute hashes and upload only unknown chunks. The same hash across users or versions means the chunk is stored once (deduplication).

The metadata service is the brain: a sharded relational DB with namespaces, file paths, versions, permissions and, per version, the ordered list of chunk hashes. Committing a version is a transaction, so a file never points to missing chunks.

Other devices learn about changes through a notification service (long polling or WebSockets with a per-user cursor), fetch the changed metadata and download only missing chunks. If two devices change the same file from the same base version, the second commit conflicts; rather than lose data, the server keeps both and creates a "conflicted copy".

How it works

  1. Client watcher detects change → chunk + hash.
  2. POST /commit {path, base_version, chunk_hashes} → server replies with missing hashes.
  3. Upload missing chunks (pre-signed URLs) → commit version.
  4. Notification → other devices GET /changes?cursor=… → download missing chunks → rebuild file.
  5. Conflict: base version is stale → create conflicted copy.

Example

file v7 = [h1, h2, h3, h4]
edit middle → v8 = [h1, h2', h3, h4]  → upload only h2'

Common mistakes

  • Uploading whole files on each change.
  • Fixed-size chunking only (an insert at the start invalidates all chunks).
  • Silent last-writer-wins on conflicts.
  • Notification service holding the data instead of just signalling.

How to answer in the interview

"The client splits files into content-hashed chunks and asks the server which hashes it lacks, so only changed chunks upload, with dedup for free. Chunks live in object storage; a sharded metadata DB stores versions as ordered chunk lists, committed transactionally. Other devices get notified, fetch metadata and pull missing chunks. Concurrent edits from the same base create a conflicted copy, never silent loss."

Likely follow-up questions

  • First sync of 50 GB? Parallel chunk uploads, resumable, prioritise small files, LAN sync between devices.
  • Why content-defined chunking? Boundaries depend on content, so inserts only change nearby chunks.
  • Sharing folders? Namespaces with ACLs in metadata; chunks shared by hash.
