What is the difference between SAST, DAST and SCA?

DevSecOps · concept · levels entry

In one line

SAST analyses source code without running it, DAST attacks the running application from outside, and SCA checks open-source dependencies for known CVEs and licence issues; they find different problems and run at different pipeline stages.

Detailed explanation

SAST (static application security testing) is white-box: it parses code and follows data flow from inputs (sources) to dangerous functions (sinks), spotting SQL injection, XSS, path traversal, weak crypto or hard-coded secrets. It runs early, on every PR, and points to the exact line. Downsides: false positives, language-specific, and it cannot see runtime configuration. Tools: Semgrep, CodeQL, SonarQube, Checkmarx.

DAST (dynamic application security testing) is black-box: it crawls and attacks a deployed app over HTTP like an attacker, testing for injection, broken authentication, missing security headers, misconfigured TLS, exposed admin pages and server misconfigurations. It is language-agnostic and finds real runtime issues, but needs a running environment, takes longer, and gives less precise code locations. Tools: OWASP ZAP, Burp Suite, Nuclei. It typically runs against staging, as a baseline scan per deployment and a fuller scan nightly.

SCA (software composition analysis) inventories third-party libraries, including transitive ones, and matches them against vulnerability databases (NVD, GitHub Advisory, OSV), plus licence checks (for example GPL in proprietary code). Since most of a modern application is open-source code, SCA often finds the most impactful issues. It should run on PRs and continuously, because a new CVE can affect a version that was clean yesterday. Tools: Snyk, Dependabot, OWASP Dependency-Check, Trivy, Mend.

IAST (instrumented testing during test runs) and container/IaC scanning complement these.

How it works

  1. Commit/PR → SAST and SCA (fast, precise).
  2. Build → image scan (OS packages + libraries).
  3. Deploy to staging → DAST baseline scan.
  4. Nightly → full DAST, re-run SCA against new advisories.
  5. Findings triaged by severity and exploitability.

Example

semgrep scan --config p/java --error                 # SAST
dependency-check.sh --project shop --scan . --failOnCVSS 7   # SCA
docker run -t ghcr.io/zaproxy/zaproxy:stable zap-baseline.py \
  -t https://staging.shop.example.com -r zap-report.html     # DAST

Common mistakes

  • Thinking SAST will catch vulnerable libraries (that is SCA).
  • Running DAST against production without permission or rate limits.
  • Running SCA only at build time, missing new CVEs.
  • Treating every finding as equally urgent.

How to answer in the interview

"SAST analyses source code without running it, finding things like SQL injection or hard-coded passwords, with tools like Semgrep, CodeQL or SonarQube on every pull request. DAST attacks the running application from outside, for example OWASP ZAP against staging, and finds runtime and configuration issues. SCA checks open-source dependencies for known CVEs and licence problems, using Snyk, Dependabot or Dependency-Check, and must run continuously because new CVEs appear for old versions. They complement each other; for something like Log4Shell, SCA is what flags the vulnerable library version."

Likely follow-up questions

  • Which would catch vulnerable Log4j? SCA (and image scanning); DAST might detect exploitability.
  • How to reduce SAST false positives? Tune rule sets, custom rules, triage and suppress with reasons.
  • What is IAST? Agent-based analysis inside the app during functional tests.
