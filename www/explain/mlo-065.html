How do you implement shadow deployment for a new model?

MLOps · design · levels mid, senior

In one line

In shadow deployment the new model receives a mirrored copy of live requests asynchronously, its predictions are logged but never returned, and you compare it with the production model on agreement, distributions, latency and later labels, with no side effects.

Detailed explanation

Shadow mode answers the question "how would this model behave on real traffic?" without exposing users to it. Offline tests use historical data; shadow mode uses today's traffic, with real feature values, real latency and real load.

Mirroring options: serving platforms often support it natively (Azure ML mirrored traffic, SageMaker shadow tests, KServe or Seldon mirroring), a service mesh like Istio can mirror HTTP requests, or the application can publish each request to a queue or stream that a shadow consumer reads. The key property is that mirroring is fire-and-forget: shadow latency, errors or crashes can't slow or fail the user request.

Both predictions are logged with the same request ID, model versions, feature vector and timestamp. Comparison then covers score distributions, agreement rate and, more importantly, where the models disagree (which segments), latency percentiles and resource usage under real load, and finally actual accuracy once ground-truth labels arrive.

Safeguards: the shadow path must have no side effects (no emails, no writes to decision tables, no payments), and must not overload shared dependencies like the feature store or databases; sample a percentage if needed, and give it its own capacity and rate limits.

The limitation: shadow mode can't measure how users or downstream systems react to different decisions, so a canary or A/B test is still needed for impact.

How it works

  1. Deploy the challenger alongside the champion with its own scaling.
  2. Mirror a percentage of traffic (start at 10 percent, grow to 100).
  3. Log both outputs with request IDs to the same table.
  4. Build a comparison dashboard: agreement, distributions, latency, errors.
  5. Join with labels when they arrive and compare metrics per segment.
  6. If good, move to a canary; otherwise iterate.

Example

apiVersion: networking.istio.io/v1
kind: VirtualService
metadata: { name: scoring }
spec:
  hosts: [scoring]
  http:
  - route:
    - destination: { host: scoring-v1 }
      weight: 100
    mirror: { host: scoring-v2 }
    mirrorPercentage: { value: 25.0 }

Common mistakes

  • Shadow model writing decisions or triggering notifications.
  • Calling the shadow synchronously and adding its latency to users.
  • Forgetting the extra load on the feature store.
  • Comparing only overall agreement, not the segments where models differ.

How to answer in the interview

"I deploy the new model next to the current one and mirror a share of live requests to it asynchronously, using the platform's mirroring, a service mesh or a queue, so its latency or failures never touch users. Only the current model's answer is returned. Both predictions are logged with the request ID, and I compare distributions, agreement, disagreement by segment, latency and resource use, and accuracy once labels arrive. I make sure the shadow has no side effects and doesn't overload the feature store. Because it can't show how users react, I follow it with a canary."

Likely follow-up questions

  • Why is a canary still needed? Shadow can't show the effect of new decisions on users or downstream systems.
  • How long do you shadow? Long enough to cover traffic cycles (often one to two weeks) and gather labels.
  • What if the shadow is slower? Fine in shadow, but it's a signal to optimise before it goes live.
