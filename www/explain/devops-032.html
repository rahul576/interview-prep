How do you structure Terraform for multiple environments, and how do you handle drift?

Infrastructure as Code · concept · levels mid, senior

In one line

Build small reusable modules, compose them in thin root configurations per environment with separate state (directory per environment, or workspaces only for near-identical ones), differentiate with tfvars, pin provider and module versions with the lock file, and handle drift by running scheduled terraform plan in CI, then reverting or codifying changes and adopting unmanaged resources with import blocks.

Detailed explanation

Structure: reusable modules (VPC, EKS cluster, a standard service with its IAM and alarms) live in a modules repo or registry with semantic versions. Each environment has a root configuration that calls these modules with environment-specific values. A common layout is live/dev/network, live/prod/network, each with its own backend key, so a mistake in dev can never touch prod and plans stay fast. Workspaces reuse one configuration with several states; they suit truly identical environments or ephemeral ones, but give weaker isolation (same code version, same backend credentials, easy to apply to the wrong workspace). Environment differences come from .tfvars files or module inputs.

Versioning: pin providers in required_providers with constraints like ~> 5.0 and commit .terraform.lock.hcl so everyone and CI use identical provider builds. Reference modules by tag (?ref=v2.3.0 or registry version). Promote module upgrades dev → staging → prod.

Drift is any difference between real infrastructure and code, typically from console changes during an incident. Detect it with a scheduled CI job running terraform plan -detailed-exitcode (exit code 2 means changes) or -refresh-only, alerting on differences; HCP Terraform and some tools offer built-in drift detection. Then decide: revert by applying the code, or codify the change into the code if it was intentional.

Unmanaged resources created manually are adopted with import blocks (Terraform 1.5+), which are reviewed in plan like any change; terraform plan -generate-config-out can draft their configuration. Terragrunt helps keep backends and inputs DRY across many roots, and Atlantis or similar tools give PR-driven plan and apply.

How it works

  1. Modules: versioned, small, documented inputs/outputs.
  2. Roots: one per environment/component with its own state.
  3. CI: plan on PR, apply on merge, per root.
  4. Nightly drift job: plan all roots, alert on changes.
  5. Fix drift by apply or code change; import strays.

Example

modules/  vpc/  eks/  service/
live/
  dev/   network/  eks/  apps/
  prod/  network/  eks/  apps/
# live/prod/network/main.tf
module "vpc" {
  source     = "git::https://github.com/acme/tf-modules.git//vpc?ref=v2.3.0"
  cidr_block = var.cidr_block
  azs        = ["eu-west-1a", "eu-west-1b", "eu-west-1c"]
}

import {
  to = aws_s3_bucket.legacy_reports
  id = "acme-legacy-reports"
}
terraform plan -detailed-exitcode -lock=false || [ $? -eq 2 ] && echo "DRIFT DETECTED"

Common mistakes

  • One state for all environments, so a typo can destroy prod.
  • Unpinned providers, so a new major version breaks plans.
  • Copy-pasting resources per environment instead of using modules.
  • Ignoring drift reports until an apply unexpectedly reverts an emergency fix.

How to answer in the interview

"I write reusable, versioned modules, say for a VPC, an EKS cluster or a standard service, and compose them in thin root configurations, usually a directory per environment with its own state, so dev can never affect prod. Workspaces are fine for near-identical environments but isolate less. Differences come from tfvars. I pin provider and module versions and commit the lock file. For drift, a scheduled CI job runs terraform plan against every root and alerts on differences; then we either apply to revert the manual change or update the code if it was intentional. Existing unmanaged resources are adopted with import blocks, and tools like Terragrunt or Atlantis help with orchestration and PR-based applies."

Likely follow-up questions

  • How do you rename a resource without destroying it? A moved block (or terraform state mv).
  • Directories vs workspaces? Directories give separate code, credentials and state; workspaces share code and backend.
  • How do you stop drift happening? Restrict console write access, use break-glass roles, and alert on changes outside the pipeline.
