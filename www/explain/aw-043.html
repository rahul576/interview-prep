How do IAM roles for EC2 and STS AssumeRole work?

Cloud (AWS) · concept · levels mid

In one line

An EC2 instance gets a role through an instance profile; the SDK fetches temporary credentials from the instance metadata service (IMDSv2), which come from STS, and in general sts:AssumeRole issues short-lived credentials to any principal allowed by the role's trust policy.

Detailed explanation

An IAM role has two kinds of policy. The trust policy (assume-role policy) says who may assume it: the ec2.amazonaws.com service, Lambda, a user or role in another account, or a federated SAML/OIDC identity provider. Permission policies say what the role can do once assumed.

On EC2, the role is wrapped in an instance profile attached to the instance. The EC2 service assumes the role and publishes the credentials on the metadata endpoint at 169.254.169.254. With IMDSv2, which you should enforce, clients first obtain a session token with a PUT request, protecting against SSRF attacks that could otherwise read credentials. The AWS SDKs and CLI walk the default credential provider chain, find the instance credentials automatically and refresh them before expiry. No access keys are ever stored on disk or in code.

STS AssumeRole is the general mechanism. A caller with permission for sts:AssumeRole on the role ARN calls it and receives an access key ID, secret access key and session token, valid from 15 minutes up to the role's maximum session duration (1 to 12 hours; role chaining limits it to 1 hour). Optional session policies can narrow permissions, session tags pass attributes for ABAC, an ExternalId protects third-party access, and source identity records who the human was. Related calls are AssumeRoleWithWebIdentity (used by IRSA and GitHub Actions OIDC) and AssumeRoleWithSAML. Every assumption is logged in CloudTrail.

How it works

  1. Create a role whose trust policy allows ec2.amazonaws.com.
  2. Attach permission policies, for example read access to one bucket.
  3. Attach the instance profile to the instance at launch or later.
  4. The SDK requests an IMDSv2 token, then reads the role credentials.
  5. Calls are signed with the temporary credentials, which rotate automatically.
  6. For another account, the app calls AssumeRole on a role there and uses those credentials.

Example

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {"Service": "ec2.amazonaws.com"},
    "Action": "sts:AssumeRole"
  }]
}
# On the instance (IMDSv2)
TOKEN=$(curl -sX PUT http://169.254.169.254/latest/api/token \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 300")
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/iam/security-credentials/

# Cross-account
aws sts assume-role --role-arn arn:aws:iam::444455556666:role/reports-reader \
  --role-session-name app-on-ec2

Common mistakes

  • Copying access keys onto servers instead of using instance profiles.
  • Leaving IMDSv1 enabled, exposing credentials to SSRF.
  • Confusing the trust policy (who) with permission policies (what).
  • Caching credentials manually and using them after they expire.

How to answer in the interview

"On EC2 I attach a role through an instance profile. The SDK automatically fetches temporary credentials from the metadata service, ideally IMDSv2 only, and refreshes them, so no keys live on the server. Underneath is STS: AssumeRole returns an access key, secret and session token that expire after minutes to hours. The role's trust policy defines who may assume it, the EC2 service, another account or a federated identity, and its permission policies define what it can do. Everything is visible in CloudTrail."

Likely follow-up questions

  • How would an app on EC2 access a bucket in another account? Assume a role in that account, or use a bucket policy granting the instance role, plus KMS permissions if encrypted.
  • Why IMDSv2? The session token requirement blocks most SSRF credential theft.
  • What is role chaining? Assuming a role with role credentials; sessions are capped at one hour.
