What is ZGC, and which garbage collectors are designed for low-latency applications?

JVM & Performance · concept · levels senior, lead

In one line

ZGC is the JVM's scalable, concurrent compacting garbage collector that keeps pauses typically below a millisecond regardless of heap size; together with Shenandoah it is the low-latency choice, trading some throughput and CPU for predictable latency.

Detailed explanation

Classic collectors such as Parallel GC stop all application threads to mark and compact the heap, so pause time grows with heap size. G1, the default collector, splits the heap into regions and aims for a pause target (-XX:MaxGCPauseMillis, 200 ms by default), but it still evacuates objects during stop-the-world pauses, so large or busy heaps can see tens of milliseconds.

ZGC moves almost all work, including marking, relocation (compaction) and reference fixing, into phases that run concurrently with the application. It does this with coloured pointers (metadata bits stored in 64-bit object references) and load barriers: whenever the application loads a reference, a small barrier checks the colour and, if the object has moved, heals the reference on the fly. The remaining pauses only scan thread stacks and roots, so they stay in the sub-millisecond range from a few gigabytes up to multi-terabyte heaps. ZGC became production-ready in JDK 15; Generational ZGC arrived in JDK 21 (enabled with -XX:+ZGenerational), became the default ZGC mode in JDK 23, and the non-generational mode was removed in JDK 24, so on current LTS releases (JDK 25) -XX:+UseZGC alone gives you generational ZGC.

Shenandoah, developed by Red Hat and shipped in OpenJDK builds, reaches similar goals with concurrent evacuation using load-reference barriers and forwarding pointers; recent JDKs also add a generational mode. The price for both is lower peak throughput, extra CPU used by concurrent GC threads, and the need for heap headroom: if allocation outpaces concurrent collection you get allocation stalls.

How it works

  1. A short pause marks roots (thread stacks, globals).
  2. Concurrent marking walks the object graph while the application runs.
  3. A short pause finishes marking.
  4. ZGC selects regions with mostly garbage (the relocation set).
  5. Objects are relocated concurrently; load barriers redirect any stale reference the application touches.
  6. In generational mode, the young generation is collected frequently and cheaply, the old generation rarely.

Example

# JDK 21: generational must be switched on explicitly
java -XX:+UseZGC -XX:+ZGenerational -Xmx16g -Xlog:gc:file=gc.log -jar pricing.jar

# JDK 23+: generational is the only/default mode
java -XX:+UseZGC -Xmx16g -XX:SoftMaxHeapSize=12g -jar pricing.jar

# Shenandoah
java -XX:+UseShenandoahGC -Xmx16g -jar pricing.jar

A trading API with a 64 GB in-memory order book saw G1 pauses of 80-150 ms at p99.9; after switching to ZGC pauses dropped below 1 ms, at the cost of roughly 10 percent more CPU.

Common mistakes

  • Switching to ZGC without measuring: if p99 latency is dominated by I/O or locks, GC is not the problem.
  • Running ZGC with no heap headroom, causing allocation stalls.
  • Still passing -XX:+ZGenerational on JDK 24+ where it is obsolete.
  • Expecting lower CPU usage; concurrent collectors usually use more.

How to answer in the interview

"ZGC is a concurrent, compacting, region-based collector. Using coloured pointers and load barriers, it marks and relocates objects while the application keeps running, so pauses stay below a millisecond whether the heap is 4 GB or 4 TB. Since JDK 21 it is generational, and from JDK 23 that is the default, so -XX:+UseZGC is enough. Shenandoah is the other low-latency option. Both cost some throughput, CPU and memory headroom, so I would choose them for latency-sensitive services with large heaps, after confirming with GC logs that G1 pauses really hurt our tail latency."

Likely follow-up questions

  • What would you check before moving from G1 to ZGC? GC logs for pause times versus p99 latency, allocation rate, CPU headroom and heap occupancy.
  • What is an allocation stall? The application allocates faster than ZGC frees memory, so threads wait; add heap or reduce allocation.
  • Does ZGC need tuning? Mainly -Xmx and optionally SoftMaxHeapSize; it is designed to be largely self-tuning.
