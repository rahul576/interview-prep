A VM in a spoke VNet suddenly cannot reach the internet after a network change. How do you troubleshoot it?

Azure · scenario · levels entry, mid, senior

In one line

Use Network Watcher: IP flow verify for NSG decisions, next hop and effective routes (often a new 0.0.0.0/0 UDR to the hub firewall), effective security rules, then the firewall rules and logs, DNS settings, Connection troubleshoot, and finally compare with the Activity Log / IaC change.

Detailed explanation

"Cannot reach the internet" after a network change usually has one of four causes: routing, NSG rules, firewall policy, or DNS. Work through them in the order packets travel.

Routing: check effective routes on the VM's NIC. A new route table associated with the subnet might send 0.0.0.0/0 to the Azure Firewall private IP (forced tunnelling), or to an NVA that is down, or to None (drop). Next hop in Network Watcher shows exactly where a packet to, say, 8.8.8.8 goes. Also remember default outbound access is being retired for new VNets, so a subnet with no NAT gateway, public IP or firewall may have no egress at all.

NSGs: IP flow verify tests a specific 5-tuple and reports the rule that allowed or denied it. Effective security rules show the merged NSGs from subnet and NIC, including new deny rules or rules referencing service tags.

Firewall: if traffic now goes through Azure Firewall, it needs network or application rules (FQDNs such as *.ubuntu.com) to allow it. Firewall logs (AZFWNetworkRule, AZFWApplicationRule tables) show denied flows. Asymmetric routing (traffic in through one path, out through another) also breaks connections.

DNS: if the VNet's DNS servers were changed to custom servers or a DNS Private Resolver, names may fail to resolve, which looks like no internet. Test with nslookup vs curl https://1.1.1.1.

Connection troubleshoot tests end to end from the VM, and VNet flow logs with traffic analytics show allowed and denied flows. Finally, the Activity Log or Git history of the IaC shows what changed.

How it works

  1. Reproduce from the VM: DNS lookup vs connection by IP.
  2. Next hop and effective routes.
  3. IP flow verify and effective security rules.
  4. Firewall rule match and logs.
  5. DNS server configuration on the VNet/NIC.
  6. Review the change and roll back or fix.

Example

az network watcher show-next-hop -g rg-spoke --vm vm-app-01 \
  --source-ip 10.2.1.4 --dest-ip 8.8.8.8
az network nic show-effective-route-table -g rg-spoke -n vm-app-01-nic -o table
az network watcher test-ip-flow -g rg-spoke --vm vm-app-01 --direction Outbound \
  --protocol TCP --local 10.2.1.4:50000 --remote 13.107.42.14:443
AZFWApplicationRule | where SourceIp == "10.2.1.4" and Action == "Deny" | take 20

Common mistakes

  • Checking only NSGs and ignoring routes.
  • Testing with ping (ICMP is often blocked anyway).
  • Forgetting DNS when "the internet is down".
  • Fixing in the portal while IaC reverts it.

How to answer in the interview

"I'd use Network Watcher. Next hop and the NIC's effective routes show where internet traffic goes; after a change it's often a new route table sending 0.0.0.0/0 to the hub firewall. IP flow verify and effective security rules tell me whether an NSG blocks the flow and which rule. If traffic goes through the firewall, I check its rules and logs for denies. I also test DNS, because a custom DNS change looks like no internet. Connection troubleshoot confirms end to end, and the Activity Log or IaC commits show exactly what changed."

Likely follow-up questions

  • Prevent one route table change breaking many VNets? IaC with PR review and what-if, staged rollout, Virtual Network Manager, and policy.
  • What are VNet flow logs? The successor to NSG flow logs, recording flows at VNet level.
  • Asymmetric routing? Return traffic bypasses the firewall, so stateful inspection drops it.
