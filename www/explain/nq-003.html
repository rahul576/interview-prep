What Java 17 and Java 21 features have you used or explored?

Modern Java (11-21) · concept · levels mid, senior

In one line

From Java 17 I use records, switch expressions, instanceof pattern matching, text blocks and sealed interfaces; from Java 21, virtual threads, pattern matching for switch with record patterns and sequenced collections, each with a concrete use.

Detailed explanation

This question tests real usage, so tie every feature to a place in your code.

Records replace Lombok-style DTOs for request/response bodies, Kafka event payloads, query projections and composite map keys. They are immutable and generate equals, hashCode and toString. Jackson and Spring Data projections support them.

Switch expressions with arrows return a value and never fall through, which makes mapping enums to values short and safe. Pattern matching for instanceof removes casts: if (ex instanceof HttpClientErrorException e && e.getStatusCode().is4xxClientError()).

Text blocks keep SQL in repository methods and JSON fixtures in tests readable.

Sealed interfaces model a closed set of outcomes, such as PaymentResult permitting Approved, Declined and Pending. With Java 21 pattern matching for switch and record patterns, a switch over that type is checked for exhaustiveness, so adding a new outcome makes incomplete code fail to compile.

Virtual threads: in Spring Boot 3.2+ setting spring.threads.virtual.enabled=true runs Tomcat request handling and @Async tasks on virtual threads, so blocking JDBC and HTTP calls scale without tuning a large thread pool. I still limit concurrency towards the database with the connection pool size.

Sequenced collections give getFirst(), getLast() and reversed() on lists, deques and linked sets, replacing list.get(list.size() - 1).

Mention where you would not use something: records are not JPA entities, and virtual threads do not help CPU-bound work.

How it works

  1. Pick 4-5 features you really used.
  2. For each, state where: DTOs, error handling, tests, domain model, concurrency.
  3. Mention a benefit (less boilerplate, compile-time safety, throughput).
  4. Add a limitation you are aware of.

Example

sealed interface PaymentResult permits Approved, Declined, Pending {}
record Approved(String txId) implements PaymentResult {}
record Declined(String reason) implements PaymentResult {}
record Pending(Duration retryAfter) implements PaymentResult {}

String message(PaymentResult r) {
    return switch (r) {
        case Approved(var tx) -> "Paid, ref " + tx;
        case Declined(var why) -> "Declined: " + why;
        case Pending p -> "Retry in " + p.retryAfter().toSeconds() + "s";
    };
}
spring.threads.virtual.enabled=true

Common mistakes

  • Listing features without any project context.
  • Using records as JPA entities.
  • Claiming virtual threads make everything faster.
  • Forgetting that the database pool still limits concurrency with virtual threads.

How to answer in the interview

"On Java 17 I use records for all DTOs and Kafka event payloads, switch expressions for enum mappings, instanceof pattern matching in exception handling, and text blocks for SQL and JSON test fixtures. I model payment outcomes as a sealed interface with record implementations, and with Java 21 I switch over it using record patterns, so the compiler tells me if I miss a case. We also enabled virtual threads in two Spring Boot services that mostly wait on HTTP and database calls, which removed our thread-pool tuning; we kept the Hikari pool as the real limit. And I use getFirst and getLast from sequenced collections."

Likely follow-up questions

  • Where would you avoid virtual threads? CPU-bound work, code with long synchronized blocks on older JDKs, and heavy ThreadLocal caching.
  • Why do records suit DTOs? Immutable, concise, value-based equality.
  • What does exhaustiveness give you? Compile errors instead of runtime bugs when a new subtype appears.
