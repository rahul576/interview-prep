How do you upgrade a Terraform provider major version safely?

Infrastructure as Code · scenario · levels mid

In one line

Read the upgrade guide and changelog, fix deprecation warnings on the old version, upgrade in a branch with init -upgrade, run plan in every environment looking for unexpected changes and replacements, ensure state backups, and roll out dev first, prod last.

Detailed explanation

A major provider release, such as AWS 5 to 6 or AzureRM 3 to 4, can remove resources, rename or retype arguments, change defaults and alter how attributes are stored. Upgrading carelessly can produce plans that modify or replace hundreds of resources.

1. Research. Read the provider's upgrade guide (major providers publish one per major version) and the changelog for breaking changes affecting resources you use. Check open issues for the new version; waiting for the first patch release is often wise.

2. Clean up on the old version. Many breaking changes are announced as deprecation warnings first. Fix them while still on the old version, where both old and new syntax usually work, so the upgrade diff is small.

3. Upgrade in a branch. Raise the constraint in required_providers (e.g. ~> 5.80 to ~> 6.0), run terraform init -upgrade, and review the lock file diff. Upgrade shared modules first if they constrain the version.

4. Plan everywhere. Run terraform plan for every environment and state using the code. The goal is an empty plan or only explained changes. Watch especially for replacements caused by changed defaults or new force-new behaviour, and for mass changes caused by attribute format differences.

5. Protect state. Providers may upgrade the state schema on the first apply, after which older provider versions cannot read it. Ensure the backend is versioned or take a backup (terraform state pull > backup.tfstate) before applying.

6. Roll out gradually. Merge and apply to dev, observe, then staging, then production. Keep the change separate from feature work so any diff is attributable to the upgrade.

How it works

  1. Read upgrade guide; list affected resources.
  2. Resolve deprecations on the current version.
  3. Bump constraint, init -upgrade, update lock file.
  4. Plan each environment; fix code until plans are clean.
  5. Backup state, apply dev → staging → prod.

Example

terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"   # was ~> 5.80
    }
  }
}
git switch -c chore/aws-provider-6
terraform init -upgrade
git diff .terraform.lock.hcl
for env in dev staging prod; do
  terraform -chdir=envs/$env init -upgrade -input=false
  terraform -chdir=envs/$env plan -input=false -out=$env.tfplan | tee $env.plan.txt
done
terraform -chdir=envs/prod state pull > prod-backup-$(date +%F).tfstate

Common mistakes

  • Bundling a provider major upgrade with feature changes.
  • Planning only in dev and assuming prod is the same.
  • Skipping several majors at once.
  • No state backup before the schema upgrade.

How to answer in the interview

"I start with the provider's upgrade guide and changelog to find breaking changes like removed resources, renamed arguments or changed defaults. While still on the old version I fix deprecation warnings, since most breaking changes are announced that way first. Then in a branch I bump the constraint, run init -upgrade, and run plan for every environment that uses the code, checking for unexpected changes, especially replacements caused by changed defaults. Providers may upgrade the state schema on apply, so I make sure state is versioned or backed up. Then I roll out dev first and production last, with the lock file change reviewed."

Likely follow-up questions

  • Why might a provider upgrade suddenly show changes to hundreds of resources? Changed defaults, renamed or restructured attributes, or different normalisation; resolve them in code or with explicit values before applying.
  • How do you roll back? Revert the constraint and lock file; restore the state version if the schema was upgraded.
  • How do you keep up regularly? Renovate/Dependabot PRs for minor versions so majors are smaller steps.
