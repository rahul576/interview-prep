How does HashMap work internally?

Collections · concept · levels mid, senior

In one line

A HashMap is an array of buckets: the key's hashCode is spread and masked to pick a bucket, collisions are chained and compared with equals, long chains are treeified into red-black trees, and the table doubles when size exceeds capacity × 0.75.

Detailed explanation

Internally the map holds a Node<K,V>[] table. Each node stores the hash, key, value and a next pointer. On put, HashMap computes h = key.hashCode() and then spreads it with h ^ (h >>> 16), so the high bits influence the index too. The bucket index is (n - 1) & hash, which works as a fast modulo because the capacity n is always a power of two.

If the bucket is empty, a new node is placed there. If not, it is a collision: HashMap walks the chain, compares hashes first and then equals, and either replaces the value of a matching key or appends a new node. Since Java 8, when a single bucket grows beyond 8 entries (TREEIFY_THRESHOLD) and the table has at least 64 buckets, the list becomes a red-black tree, so the worst case drops from O(n) to O(log n). If the table is smaller than 64, it resizes instead. Trees turn back into lists when they shrink to 6.

When size > capacity × loadFactor (16 × 0.75 = 12 by default), the table resizes to double. Because the capacity is a power of two, each entry either stays at index i or moves to i + oldCapacity, depending on one extra hash bit, so redistribution is cheap. HashMap allows one null key (hash 0, bucket 0) and null values, and it is not thread safe.

How it works

  1. Compute and spread the key's hash.
  2. Index = (capacity - 1) & hash.
  3. Empty bucket: insert node. Otherwise compare hash and equals along the chain or tree.
  4. Matching key: replace value; otherwise append.
  5. Bucket over 8 and table at least 64: treeify.
  6. Size over threshold: double the table and split buckets.

Example

Map<String, Integer> stock = new HashMap<>(256); // rounded to power of two
stock.put("SKU-1", 10);
stock.merge("SKU-1", 5, Integer::sum);          // 15
// expected 1000 entries? new HashMap<>(1000 / 0.75 + 1) or
Map<String, Integer> big = HashMap.newHashMap(1000); // Java 19+

Common mistakes

  • Using mutable objects as keys and changing them after insertion.
  • Overriding equals without hashCode, so lookups fail.
  • Saying collisions "always" use trees; treeification needs 8+ entries and 64+ buckets.
  • Sharing a HashMap between threads.

How to answer in the interview

"HashMap is an array of buckets. On put it takes the key's hashCode, XORs in the high bits, and masks with capacity minus one to get the bucket, which is why capacity is a power of two. Collisions are stored as a linked list and matched with equals; since Java 8 a bucket with more than eight entries, in a table of at least 64, becomes a red-black tree, so worst-case lookups are logarithmic. When size passes capacity times 0.75 it doubles and redistributes entries. It allows one null key and is not thread safe."

Likely follow-up questions

  • Why a power-of-two capacity? The index becomes a cheap bitwise AND and resizing splits buckets cleanly.
  • Why load factor 0.75? A good trade-off between memory use and collision probability.
  • What happens with a constant hashCode? Everything collides; performance degrades to tree or list lookups.
