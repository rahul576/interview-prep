Which composable patterns are common in agentic systems, such as chaining, routing and orchestrator-workers?

AI Agents & AIOps · concept · levels mid, senior

In one line

Common building blocks are prompt chaining, routing, parallelisation (sectioning and voting), orchestrator-workers and evaluator-optimizer, plus the autonomous agent loop; the advice is to start simple and add complexity only when evaluations show a gain.

Detailed explanation

Anthropic's "Building effective agents" guidance describes these patterns as composable pieces; most production systems are combinations of them.

Prompt chaining splits a task into sequential steps, each working on the previous output, with programmatic gates in between. Example: write an outline, check it covers required sections, then write the document. It trades latency for accuracy because each call has an easier job.

Routing classifies the input and sends it to a specialised prompt, tool set or model. Refund requests, technical questions and complaints get different handling; simple queries go to a small fast model and hard ones to a stronger model, saving cost.

Parallelisation runs calls concurrently. Sectioning splits independent subtasks, such as one call answering and another screening for policy violations. Voting runs the same task several times and aggregates, for example three reviewers checking code for vulnerabilities, improving confidence.

Orchestrator-workers has a lead model that decomposes a task dynamically, because the subtasks are not known in advance, delegates them to worker calls or sub-agents, and synthesises the results. Coding agents changing several files and research systems searching many sources use it.

Evaluator-optimizer pairs a generator with an evaluator that critiques against clear criteria, iterating until it passes or a round limit is reached. It works when good feedback is articulable, such as literary translation or code that must satisfy a checklist.

Beyond these sits the fully autonomous agent. Each step up adds cost, latency and failure modes, so the right choice is the simplest pattern that passes your evals.

How it works

  1. Define the task and success criteria; build a small evaluation set.
  2. Try a single well-designed call with retrieval and examples.
  3. If needed, add chaining with checks, or routing for distinct input types.
  4. Add parallelisation for independent subtasks or confidence.
  5. Use orchestrator-workers when subtasks are dynamic.
  6. Add evaluator-optimizer loops where clear criteria exist; measure each change.

Example

# Routing + evaluator-optimizer for support replies
route = llm_small("Classify as billing | technical | other", ticket)
handler = {"billing": billing_prompt, "technical": tech_prompt}.get(route, general_prompt)

draft = llm(handler, ticket)
for _ in range(3):                       # bounded loop
    review = llm(evaluator_prompt, draft)  # returns {"pass": bool, "feedback": str}
    if review["pass"]:
        break
    draft = llm(handler + "\nRevise using feedback:\n" + review["feedback"], ticket)

Common mistakes

  • Jumping straight to multi-agent orchestration.
  • Evaluator loops without a round limit or clear criteria.
  • Chaining without validation gates, so early errors propagate.
  • Not measuring whether the extra pattern improves results.

How to answer in the interview

"There are a handful of building blocks. Prompt chaining breaks a task into sequential steps with checks in between. Routing classifies an input and sends it to a specialised prompt or a cheaper or stronger model. Parallelisation either splits independent subtasks or runs the same task several times and votes. Orchestrator-workers has a lead model that decomposes the task dynamically and delegates to workers, typical for coding and research. Evaluator-optimizer has one call generate and another critique until criteria are met. I always start with the simplest option, often one good call, and add a pattern only when evaluations show it helps."

Likely follow-up questions

  • Translating legal documents with high quality needs? Chaining (translate, then terminology check) plus evaluator-optimizer with a glossary, and human review.
  • Orchestrator-workers vs parallelisation? Parallel subtasks are predefined; an orchestrator decides them at runtime.
  • When is voting worth it? When errors are costly and a single call is unreliable, like security review.
