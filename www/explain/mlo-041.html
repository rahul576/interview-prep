How do you build and optimise container images for ML training and inference?

MLOps · concept · levels mid, senior

In one line

Build ML images on CUDA or framework base images matching node drivers, use separate training and slim multi-stage inference images, pin dependencies with lock files, order layers for caching, keep model weights out of the image where possible, and scan and sign images.

Detailed explanation

ML images are often 10 to 20 GB, slow to pull and fragile, which hurts cold starts, CI time and reliability.

Base images. For GPU workloads, start from an official CUDA image (nvidia/cuda:*-runtime) or a framework image such as PyTorch or NVIDIA NGC containers. The CUDA version inside must be compatible with the node's driver and with how the framework was built; mismatches give "no kernel image" or driver errors at runtime. Use runtime rather than devel variants for inference.

Separate images. Training images contain compilers, CUDA dev tools, notebooks and profilers. Inference images should be slim, built with multi-stage builds that compile wheels in a builder stage and copy only what serving needs.

Pinning. All packages pinned with lock files (uv.lock, poetry.lock, requirements.txt with hashes), and base images referenced by digest, so builds are reproducible and a silent upgrade can't change predictions.

Layer ordering. System packages first, then Python dependencies, then application code, so code changes rebuild only the last thin layer. Use BuildKit cache mounts for pip.

Model weights. Baking a multi-gigabyte model into the image couples model and code versions and bloats every pull. Usually load weights at startup from the registry or object storage, or from a node-level cache or pre-pulled volume (KServe's model cache or modelcar/OCI artefacts help). Baking in is reasonable for small models or air-gapped sites.

Security. Scan with Trivy or Grype, run as non-root, generate an SBOM and sign with cosign.

How it works

  1. Choose base image by CUDA and driver compatibility.
  2. Builder stage installs pinned dependencies into a venv.
  3. Runtime stage copies the venv and code only.
  4. Model weights fetched at startup or mounted from cache.
  5. CI scans, generates SBOM, signs and pushes by digest.

Example

FROM nvidia/cuda:12.4.1-cudnn-runtime-ubuntu22.04 AS base
RUN apt-get update && apt-get install -y --no-install-recommends python3.11 python3.11-venv \
 && rm -rf /var/lib/apt/lists/*

FROM base AS builder
RUN python3.11 -m venv /opt/venv
COPY requirements.lock .
RUN --mount=type=cache,target=/root/.cache/pip /opt/venv/bin/pip install --require-hashes -r requirements.lock

FROM base
COPY --from=builder /opt/venv /opt/venv
COPY app/ /app/
USER 1000
ENV PATH=/opt/venv/bin:$PATH MODEL_URI=s3://models/ranker/v7
CMD ["python3.11", "/app/serve.py"]

Common mistakes

  • Using devel CUDA images for inference.
  • Unpinned pip install torch producing different builds.
  • Copying code before installing dependencies, breaking the cache.
  • Baking huge weights into every image version.

How to answer in the interview

"ML images get huge and fragile, so I start from an official CUDA or framework base image whose CUDA version matches the node drivers. Training and inference get separate images; inference uses a multi-stage build so only the runtime and venv ship. Dependencies are pinned with lock files and base images by digest. Layers go from least to most frequently changing so caching works. Large weights stay out of the image and load at startup from the registry or a node cache. Images are scanned, run as non-root and signed."

Likely follow-up questions

  • Bake the model in or load at startup? Baked is simpler and immutable but large and coupled; loading keeps images small and versions independent but adds startup time.
  • How do you speed up cold starts? Pre-pulled images, node-level model caches and smaller images.
  • How do you check driver compatibility? Follow NVIDIA's compatibility matrix and test on target nodes.
