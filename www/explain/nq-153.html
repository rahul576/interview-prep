What is the State pattern?

Design Patterns · concept · levels mid

In one line

State lets an object change its behaviour when its internal state changes: each state is a class implementing a common interface, the context delegates to its current state, and states handle transitions, replacing big switch statements on a status field.

Detailed explanation

Consider an Order with statuses NEW, PAID, SHIPPED, DELIVERED and CANCELLED, and operations pay(), ship(), cancel(). The naive version puts a switch (status) in every method. As statuses and rules grow ("cancel allowed until shipped, refund if paid"), those switches multiply, rules for one state are scattered across many methods, and invalid transitions slip through.

The State pattern restructures this:

  • State interface: OrderState with pay(ctx), ship(ctx), cancel(ctx).
  • Concrete states: NewState, PaidState, ShippedState, CancelledState. Each defines what every operation means in that state, including throwing for invalid transitions (ShippedState.cancel() throws).
  • Context: Order holds a reference to its current state and delegates. A state can call ctx.setState(new PaidState()) to transition.

All rules for "paid" now live in one class, adding a state means adding a class, and invalid transitions are explicit. It looks like the object changed its class.

Persistence in practice: with JPA you store the status as an enum column and map it to a state object, or use an enum with abstract methods (each constant overrides behaviour), which is a compact Java form of the pattern. For complex workflows with guards, actions, events and persistence, Spring State Machine or a workflow engine (Camunda, Temporal) is an alternative.

State vs Strategy: same structure, different intent. In Strategy the client picks an algorithm and strategies don't know each other; in State the object itself moves between states, and states often know their successors.

How it works

  1. Define the state interface with all state-dependent operations.
  2. Implement one class (or enum constant) per state.
  3. Context holds the current state and delegates calls.
  4. States perform transitions by setting the context's next state.
  5. Invalid operations throw or no-op explicitly.

Example

public enum OrderStatus {
    NEW {
        OrderStatus pay()    { return PAID; }
        OrderStatus cancel() { return CANCELLED; }
    },
    PAID {
        OrderStatus ship()   { return SHIPPED; }
        OrderStatus cancel() { return CANCELLED; }   // trigger refund elsewhere
    },
    SHIPPED {
        OrderStatus deliver() { return DELIVERED; }
    },
    DELIVERED, CANCELLED;

    OrderStatus pay()     { throw illegal("pay"); }
    OrderStatus ship()    { throw illegal("ship"); }
    OrderStatus deliver() { throw illegal("deliver"); }
    OrderStatus cancel()  { throw illegal("cancel"); }
    IllegalStateException illegal(String op) { return new IllegalStateException(op + " not allowed in " + this); }
}

@Entity
class Order {
    @Enumerated(EnumType.STRING) private OrderStatus status = OrderStatus.NEW;
    void pay()    { status = status.pay(); }
    void ship()   { status = status.ship(); }
    void cancel() { status = status.cancel(); }
}

Common mistakes

  • Keeping switch statements alongside state classes.
  • Letting transitions happen from outside, bypassing state rules.
  • Using State for two trivial statuses.
  • Storing state objects with mutable shared fields (states should usually be stateless).

How to answer in the interview

"State lets an object change its behaviour when its internal state changes, as if it changed class. Each state is a class implementing a common interface, and the context delegates to its current state, which can also move it to the next state. Instead of a switch on order status in every method, I'd have NewOrder, PaidOrder, ShippedOrder and CancelledOrder, each defining what pay, ship and cancel do, including rejecting invalid transitions. In Java an enum with overridden methods is a compact way to do it, and for complex workflows Spring State Machine is an option."

Likely follow-up questions

  • State vs Strategy? Same structure; Strategy is chosen by the client, State changes itself based on internal transitions.
  • How do you persist it? Store the status enum and map it back to behaviour on load.
  • How do you handle concurrent transitions? Optimistic locking with @Version so two updates cannot both apply.
