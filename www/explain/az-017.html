What are branch policies in Azure Repos and why do they matter?

Azure DevOps & Pipelines · concept · levels entry, mid

In one line

Branch policies protect important branches such as main by requiring pull requests, minimum reviewers and code owners, build validation, linked work items, resolved comments and allowed merge strategies, enforcing quality and compliance consistently rather than relying on discipline.

Detailed explanation

In Azure Repos, once any branch policy is enabled on a branch, direct pushes are blocked and every change must go through a pull request that satisfies the policies. This is the main control for code quality, security and auditability in Azure DevOps.

The main policies are:

  • Require a minimum number of reviewers, with options to block self-approval, reset votes when new changes are pushed, and require a re-approval on the latest iteration.
  • Automatically included reviewers: required reviewers or groups for specific paths, for example the security team for /auth/ or the platform team for /infra/, acting like code owners.
  • Build validation: a CI pipeline must succeed for the PR's merge result before completion, with options for build expiry so stale results do not count.
  • Status checks: external services such as security scanners or SonarQube post a required status.
  • Check for linked work items: traceability between code and requirements, important for audits.
  • Check for comment resolution: all review threads must be resolved.
  • Limit merge types: for example allow only squash merge to keep a linear, readable history, or only rebase.

Policies can be set per branch or by pattern (for example release/*), and at project or organisation level for consistency across repositories. Bypass permissions ("bypass policies when completing pull requests" or "when pushing") should be granted to a minimal group and audited.

Why they matter: they ensure every change is reviewed and tested, provide an audit trail for compliance frameworks such as SOC 2 or ISO 27001, prevent accidental pushes, and turn team conventions into automated guardrails.

How it works

  1. Enable policies on main and release branch patterns.
  2. Developer pushes a feature branch and opens a PR.
  3. Required reviewers are added automatically by path.
  4. Build validation and status checks run on the merge result.
  5. Reviewers approve; comments are resolved; work item linked.
  6. PR completes with the allowed merge type.

Example

az repos policy approver-count create --repository-id <repo-id> --branch main \
  --minimum-approver-count 2 --creator-vote-counts false \
  --reset-on-source-push true --allow-downvotes false --blocking true --enabled true
az repos policy build create --repository-id <repo-id> --branch main \
  --build-definition-id 42 --display-name "CI" --queue-on-source-update-only true \
  --manual-queue-only false --valid-duration 720 --blocking true --enabled true
az repos policy merge-strategy create --repository-id <repo-id> --branch main \
  --allow-squash true --allow-no-fast-forward false --blocking true --enabled true

Common mistakes

  • Allowing creators to approve their own PRs.
  • Not resetting votes when new commits are pushed.
  • Giving bypass permissions to large groups.
  • Build validation that is slow or flaky, so people seek bypasses.
  • Applying policies to main but not to release branches.

How to answer in the interview

"Branch policies protect important branches like main. Once enabled, changes must go through pull requests rather than direct pushes. I typically require at least two reviewers with votes reset on new pushes, automatically included reviewers for sensitive paths like infrastructure or authentication, build validation so the CI pipeline must pass on the merge result, linked work items for traceability, and all comments resolved. I also limit merge types, for example squash only, to keep history clean. Bypass permissions go to a very small, audited group. This enforces quality and compliance consistently instead of relying on team discipline."

Likely follow-up questions

  • How would you allow an emergency hotfix while keeping the policies? Fast-track review by on-call approvers, not bypass; if bypass is used, it is audited and reviewed afterwards.
  • How is this different from GitHub branch protection? Similar concepts: rulesets, required reviews, status checks and CODEOWNERS.
  • How do you enforce policies across many repos? Cross-repo policies at project level and branch patterns.
