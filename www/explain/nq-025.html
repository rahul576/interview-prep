What are the commonly used built-in functional interfaces in Java?

Java 8+ Features · concept · levels entry

In one line

The core built-ins in java.util.function are Function<T,R> (transform), Predicate<T> (test), Consumer<T> (act), Supplier<T> (provide), their two-argument forms (BiFunction, BiPredicate, BiConsumer), UnaryOperator/BinaryOperator, and primitive specialisations like IntPredicate and ToIntFunction.

Detailed explanation

The package contains about 43 interfaces, but they all derive from four basic shapes:

  • Function<T, R>, R apply(T): transformation, used by Stream.map, Map.computeIfAbsent, Comparator.comparing. Composes with andThen and compose; Function.identity() returns its input.
  • Predicate<T>, boolean test(T): condition, used by filter, removeIf, anyMatch. Combines with and, or, negate, and Predicate.not (Java 11).
  • Consumer<T>, void accept(T): side effect, used by forEach, ifPresent, peek. Chains with andThen.
  • Supplier<T>, T get(): lazy value or factory, used by orElseGet, Stream.generate, ThreadLocal.withInitial, Collectors.toCollection.

Two-argument versions: BiFunction<T,U,R> (used by Map.replaceAll, merge, compute), BiPredicate<T,U>, BiConsumer<T,U> (used by Map.forEach). There's no BiSupplier, since a supplier takes no input.

Same-type operators: UnaryOperator<T> extends Function<T,T> (used by List.replaceAll, Stream.iterate); BinaryOperator<T> extends BiFunction<T,T,T> (used by reduce, Map.merge, with minBy/maxBy helpers).

Primitive specialisations avoid boxing overhead for int, long and double: IntPredicate, IntFunction<R>, ToIntFunction<T>, IntUnaryOperator, IntBinaryOperator, IntSupplier, IntConsumer, ObjIntConsumer, IntToLongFunction, BooleanSupplier, and so on. mapToInt takes a ToIntFunction.

Older interfaces like Runnable (no input, no output), Callable<V> (no input, returns a value, may throw) and Comparator<T> are also functional and widely used with lambdas.

How it works

  1. Pick the shape by inputs and output: 1→1 Function, 1→boolean Predicate, 1→void Consumer, 0→1 Supplier.
  2. Use Bi* for two inputs, *Operator when types match.
  3. Use a primitive specialisation for numeric hot paths.
  4. Compose with default methods (andThen, and, negate).

Example

Function<Order, BigDecimal> total = Order::total;
Predicate<Order> paid = Order::isPaid;
Consumer<Order> audit = o -> log.info("order {}", o.id());
Supplier<List<Order>> fresh = ArrayList::new;

BiFunction<BigDecimal, Integer, BigDecimal> times = (p, q) -> p.multiply(BigDecimal.valueOf(q));
UnaryOperator<String> trim = String::trim;
BinaryOperator<Integer> add = Integer::sum;

ToIntFunction<Item> qty = Item::qty;
IntPredicate positive = n -> n > 0;
int units = items.stream().mapToInt(qty).filter(positive).sum();

orders.stream().filter(paid.and(Predicate.not(Order::isGift))).forEach(audit);
prices.replaceAll((sku, p) -> p.multiply(new BigDecimal("1.05")));    // BiFunction on a Map

Common mistakes

  • Writing custom interfaces where a built-in fits.
  • Using Function<Integer,Integer> in hot loops instead of IntUnaryOperator.
  • Confusing Consumer (no result) with Function.
  • Not knowing there are no built-in three-argument interfaces.

How to answer in the interview

"java.util.function has about forty interfaces built on four shapes. Function takes a T and returns an R, used in map. Predicate returns a boolean, used in filter. Consumer accepts a value and returns nothing, used in forEach. Supplier takes nothing and returns a value, used for lazy creation like orElseGet. The two-argument versions are BiFunction, BiPredicate and BiConsumer, and UnaryOperator and BinaryOperator are functions where input and output types match, used in replaceAll and reduce. Primitive versions like IntPredicate and ToIntFunction avoid boxing. Runnable, Callable and Comparator are functional too."

Likely follow-up questions

  • Why do primitive specialisations exist? Generics can't use primitives, so they avoid boxing costs and allocation.
  • Which interface does Map.forEach take? BiConsumer<K,V>.
  • What's the difference between Supplier and Callable? Callable can throw checked exceptions; Supplier can't.
