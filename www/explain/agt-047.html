Design an LLM-based SRE agent that investigates alerts before a human is paged.

AI Agents & AIOps · design · levels senior, lead

In one line

An SRE agent is triggered by an alert, gathers context from the service catalog, investigates with read-only tools (metrics, logs, traces, Kubernetes, deploys) guided by runbooks and past incidents, posts an evidence-backed summary before or as the human is paged, and remediates only through approved actions with approval.

Detailed explanation

The value of such an agent is that the on-call engineer starts with context instead of a blank page at 3 a.m. The design has to make it useful, fast and safe.

Trigger and context: the alert webhook starts an investigation with alert labels, the affected service, and catalog data: owner, dependencies, SLOs, dashboards and recent deployments. Tools: the agent has read-only tools to query metrics (PromQL/KQL), search logs, fetch traces, describe Kubernetes resources and events, list recent changes and feature flags. Knowledge: it retrieves runbook sections and similar past incidents through RAG. Time budget: it must finish an initial pass in a few minutes; for high-severity alerts the human is paged immediately and the agent's findings arrive in parallel, so the agent never delays response.

Output: a summary in the incident channel: impact, timeline, evidence with links, ranked hypotheses and suggested next steps. Remediation: only actions defined in runbooks, such as restarting a pod or rolling back a deployment, initially requiring human approval. Measurement: responders rate accuracy; track time to diagnosis and false conclusions. Humans remain accountable.

How it works

  1. Alert fires; orchestrator starts an agent run with alert and catalog context.
  2. Agent plans checks from the runbook and alert type.
  3. Executes read-only tool calls within step, time and cost budgets.
  4. Retrieves similar incidents and compares symptoms.
  5. Posts a structured summary with evidence links to Slack/Teams and the ticket.
  6. Offers approved remediation buttons; humans approve and the action is logged.
  7. Feedback is collected after the incident.

Example

agent: sre-investigator
trigger: alertmanager webhook (severity in [page, ticket])
limits: { max_steps: 25, max_duration: 4m, max_cost_usd: 1.50 }
tools:
  - prometheus.query        # read-only
  - loki.search             # read-only, PII redaction on results
  - k8s.describe / k8s.events   # RBAC: get, list, watch only
  - deploys.recent
actions_requiring_approval:
  - argo.rollback
  - k8s.rollout_restart (max 1 deployment)
output: incident channel + ticket comment

Common mistakes

  • Making the page wait for the agent.
  • Giving the agent write credentials "for convenience".
  • Free-text output without evidence links.
  • No evaluation of accuracy, so trust is based on anecdotes.

How to answer in the interview

"When an alert fires, the agent gets the alert plus catalog context: owner, dependencies, SLOs and recent deploys. It investigates with read-only tools for metrics, logs, traces, Kubernetes and change history, guided by the runbook and similar past incidents, all within strict time and cost limits. Within minutes it posts a summary with timeline, evidence links and ranked hypotheses to the incident channel. Remediation is limited to runbook actions like a rollback, with human approval at first. I measure accuracy and time saved, and humans stay accountable."

Likely follow-up questions

  • Actions without approval later? Reversible, low-risk ones with a proven record, like scaling out.
  • Handling prompt injection from logs? Treat tool output as data; no write tools; policy checks.
  • How to evaluate? Replay past incidents and compare against known root causes.
