What are embeddings-based semantic search and keyword search, and when does each fail?

AI/ML & GenAI · concept · levels mid, senior

In one line

Keyword search matches the exact words of a query using an inverted index and ranking such as BM25; semantic search matches meaning by comparing embedding vectors. Keyword search fails on synonyms and paraphrases, semantic search fails on exact identifiers and rare terms, so production systems usually use hybrid search.

Detailed explanation

Keyword (lexical) search, as in Elasticsearch, OpenSearch, Solr or PostgreSQL full-text search, tokenises documents into terms and builds an inverted index mapping each term to the documents that contain it. BM25 scores documents by term frequency (with saturation), inverse document frequency (rare words count more) and document length. It is fast, cheap, explainable ("these words matched") and very precise for exact strings. Its weakness is the vocabulary mismatch problem: "how do I get my money back" does not match a page titled "Refund policy" unless you maintain synonym lists and stemming rules.

Semantic (dense) search uses an embedding model to turn queries and documents (usually chunks) into vectors, stores them in a vector index (pgvector, OpenSearch k-NN, Pinecone, Qdrant and others) and returns the nearest neighbours by cosine similarity, typically through approximate algorithms such as HNSW. It handles paraphrases, synonyms, conversational questions and even cross-language queries. Its weaknesses are the mirror image: error codes like ORA-00942, SKUs, invoice numbers, people's names, version numbers and new jargon the model never saw are blurred together, because embeddings capture general meaning rather than exact tokens. It is also harder to explain why a result ranked first, and quality depends on the embedding model and chunking.

Hybrid search runs both retrievers and merges the result lists, commonly with Reciprocal Rank Fusion (RRF) or a weighted score, and often adds a cross-encoder reranker on the top 50-100 candidates. This gets the recall of semantic search and the precision of keyword search.

How it works

  1. Index each document twice: as terms in an inverted index and as embedding vectors.
  2. At query time, run a BM25 query and a k-NN vector query in parallel.
  3. Merge the two ranked lists with RRF or weighted scores.
  4. Optionally rerank the top candidates with a cross-encoder model.
  5. Measure with a labelled set of real queries (recall@k, nDCG, MRR) and tune.

Example

POST /docs/_search
{
  "retriever": {
    "rrf": {
      "retrievers": [
        { "standard": { "query": { "match": { "body": "ORA-00942 table not found" } } } },
        { "knn": { "field": "body_vector", "query_vector_builder": {
            "text_embedding": { "model_id": "my-embedder", "model_text": "ORA-00942 table not found" } },
            "k": 20, "num_candidates": 100 } }
      ]
    }
  }
}

The keyword side nails the exact error code; the vector side finds a troubleshooting page that says "relation does not exist".

Common mistakes

  • Replacing keyword search entirely with vectors and losing exact-match queries.
  • Judging quality on a handful of demo queries instead of real user logs.
  • Ignoring metadata filters (tenant, language, date) in the vector query.
  • Re-embedding with a new model without re-indexing everything.

How to answer in the interview

"Keyword search uses an inverted index with BM25, so it is fast, explainable and precise for exact words, but it misses synonyms and paraphrases, like 'get my money back' versus 'refund policy'. Semantic search embeds queries and documents as vectors and finds similar meaning, which fixes that, but it is weak on exact identifiers such as error codes, SKUs or names. So in production I'd use hybrid search: run both, merge with reciprocal rank fusion and rerank the top results. And I'd tune the balance using a labelled set of real queries and metrics like recall at k."

Likely follow-up questions

  • How would you tune the balance? Build an evaluation set from real queries and adjust fusion weights or RRF constants against recall@k and nDCG.
  • What is a reranker? A cross-encoder that scores query and document together; slower but more accurate, so it is applied only to the top candidates.
  • How do you detect queries that need exact match? Heuristics such as patterns for codes or IDs, or simply let hybrid fusion handle it.
