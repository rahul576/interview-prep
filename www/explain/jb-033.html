How does the Compact Strings feature work in modern Java?

Core Java & OOP · concept · levels senior, lead

In one line

Compact Strings (JEP 254, Java 9) changed String's backing storage from char[] to byte[] plus a coder flag: LATIN1 strings use one byte per character, others use UTF-16 (two bytes), often nearly halving string memory with no API change.

Detailed explanation

Strings are typically the largest consumer of heap in Java applications: JSON keys, ids, log messages, HTTP headers, cache keys. Up to Java 8, String wrapped a char[], and every char is 16 bits. Measurements across many applications showed that most strings contain only Latin-1 characters (code points 0-255), so half of the bytes in those arrays were zeros.

Java 9 introduced Compact Strings:

  • The value field became a byte[].
  • A new coder field records the encoding: LATIN1 (0) or UTF16 (1).
  • When a string is created, the JDK checks whether every character fits in Latin-1. If yes, it stores one byte per char; if any char needs more, the whole string is stored as UTF-16.
  • All String methods branch on the coder, using specialised implementations (StringLatin1, StringUTF16), and many are intrinsified by the JIT with vectorised code.

Effects: heap used by strings is often reduced by up to half, which means less GC work and better CPU cache utilisation. Concatenation (JEP 280) and StringBuilder are coder-aware too. Code that uses the String API sees no difference; charAt and length still work in UTF-16 code units.

Trade-offs: mixed-coder operations, like concatenating a Latin-1 and a UTF-16 string, require inflation; workloads dominated by non-Latin text (for example Hindi, Chinese, emoji) gain nothing and have a small branching overhead. The feature can be disabled with -XX:-CompactStrings, which forces UTF-16 everywhere, but that is rarely beneficial.

Related features: G1 string deduplication removes duplicate backing arrays, and the string pool deduplicates literals; Compact Strings reduces the size of each array.

How it works

  1. A new String's characters are scanned during construction.
  2. If all are less than or equal to 0xFF, they are compressed into a byte array with coder LATIN1.
  3. Otherwise a UTF-16 byte array (two bytes per char) is stored with coder UTF16.
  4. Methods dispatch on the coder.
  5. Operations mixing coders inflate to UTF-16 as needed.

Example

# Inspect string footprint in a heap histogram
jcmd <pid> GC.class_histogram | grep -E "java.lang.String|\[B"

# Detailed analysis: heap dump, then open in Eclipse MAT or VisualVM
jcmd <pid> GC.heap_dump /tmp/app.hprof

# Compare with compact strings disabled (for experiments only)
java -XX:-CompactStrings -jar app.jar
String ascii = "order-12345";        // LATIN1: 11 bytes of payload
String hindi = "ऑर्डर";               // UTF16: 2 bytes per char

Common mistakes

  • Thinking Compact Strings changed char to 8 bits or broke Unicode.
  • Confusing it with string interning or deduplication.
  • Assuming it was a Java 8 feature (Java 6 had an unrelated, removed UseCompressedStrings).
  • Disabling it without measurement.

How to answer in the interview

"Before Java 9 a String stored characters in a char array, two bytes each. Most strings in real apps, like ids, JSON keys and English text, are Latin-1, so half of that memory was zeros. Compact Strings, JEP 254 in Java 9, changed the backing field to a byte array plus a coder flag: if every character fits Latin-1 it uses one byte per character, otherwise UTF-16 with two. That often cuts string heap nearly in half and improves cache behaviour and GC. It's completely transparent to application code, and can be switched off with -XX:-CompactStrings, though I've never needed to."

Likely follow-up questions

  • How would you measure how much heap your application uses for strings? Class histogram via jcmd, or a heap dump analysed in MAT/JFR.
  • Does it affect charAt? No, semantics are unchanged.
  • Who benefits least? Applications dominated by non-Latin-1 text.
