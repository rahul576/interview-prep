A latency-sensitive service shows high p99 latency even though average CPU usage is low. What could be wrong?

Kubernetes · scenario · levels senior, lead

In one line

The classic cause is CPU throttling: CPU limits are enforced by the CFS quota per 100 ms period, so a multi-threaded burst uses the quota early and the container is paused until the next period, adding tens of milliseconds to some requests while average usage looks low.

Detailed explanation

A CPU limit of 1 core becomes a CFS quota of 100 ms of CPU time per 100 ms period (cgroup cpu.max). Average usage is calculated over seconds or minutes, but enforcement happens every 100 ms. A service with 8 busy threads can consume 100 ms of CPU in about 12.5 ms of wall time, after which all its threads are stopped for the remaining 87.5 ms. A request that arrived in that window waits, so p99 explodes while the dashboard shows 30 percent average CPU.

The evidence is in cAdvisor metrics: container_cpu_cfs_throttled_periods_total divided by container_cpu_cfs_periods_total. If a large share (say over 10-20 percent) of periods are throttled for a latency-sensitive service, the limit is the problem. The fix is to raise or remove the CPU limit while keeping an accurate CPU request. Requests drive scheduling and, through CPU weights, fair sharing under contention, so removing the limit still protects neighbours. Some teams keep limits but set them well above requests; the static CPU manager policy with Guaranteed pods gives exclusive cores for the most sensitive workloads.

Other causes of high p99 with low average CPU: garbage collection pauses, runtimes that size thread pools from the node's CPU count instead of the container limit (old JVMs, Go before container-aware GOMAXPROCS), noisy neighbours sharing disk or memory bandwidth, conntrack or connection pool exhaustion, and DNS timeouts.

How it works

  1. Compare p99 latency with throttling ratio over the same window.
  2. Check thread counts and runtime CPU detection.
  3. If throttled, raise or remove the CPU limit, keep the request realistic.
  4. Re-measure p99 and throttling.
  5. Rule out GC pauses (GC logs), node contention and connection limits.

Example

sum by (pod) (rate(container_cpu_cfs_throttled_periods_total{namespace="checkout", container="api"}[5m]))
/
sum by (pod) (rate(container_cpu_cfs_periods_total{namespace="checkout", container="api"}[5m]))
resources:
  requests: { cpu: "1", memory: 1Gi }
  limits: { memory: 1Gi }      # no CPU limit; request still guarantees share

Common mistakes

  • Judging CPU health by averages only.
  • Setting CPU limit equal to a low request for every service by policy.
  • Ignoring that runtimes see the node's CPU count.
  • Removing limits without accurate requests, causing contention.

How to answer in the interview

"My first suspect is CPU throttling. A CPU limit is enforced as a CFS quota per 100 millisecond period. A multi-threaded service can burn its whole quota in the first few milliseconds of a burst and is then paused until the next period, so some requests wait tens of milliseconds while average CPU looks low. I check the ratio of throttled periods to total periods, and if it's high I raise or remove the CPU limit while keeping an accurate request, which still guarantees fair sharing. I'd also rule out GC pauses, thread pools sized to the node CPU count, noisy neighbours and connection exhaustion."

Likely follow-up questions

  • Arguments for and against CPU limits? For: predictability, multi-tenant fairness, cost caps. Against: throttling latency and wasted idle CPU; requests already give fair share.
  • Does memory work the same way? No; exceeding a memory limit gets the container OOMKilled, not throttled.
  • What does a Guaranteed pod give you? Highest QoS and, with the static CPU manager, exclusive cores.
