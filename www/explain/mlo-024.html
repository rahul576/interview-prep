Which tools do you use to orchestrate ML pipelines, and how do you choose between them?

MLOps · concept · levels mid, senior

In one line

Kubeflow Pipelines for Kubernetes-native, containerised ML workflows with caching and lineage; Airflow for general scheduling of data and batch ML; Argo Workflows, Prefect and Dagster as alternatives; managed pipelines in SageMaker, Azure ML and Vertex AI. Choose by team skills, existing platform, caching, GPU scheduling and lineage needs.

Detailed explanation

Kubeflow Pipelines (KFP) runs each step as a container on Kubernetes. Pipelines are written in Python with the KFP SDK, compiled to a spec, and executed with step caching, artefact tracking and lineage. Steps can request GPUs, so it suits teams already running ML on Kubernetes. Vertex AI Pipelines runs the same KFP format as a managed service.

Apache Airflow is the most widely used general orchestrator for data pipelines, strong for scheduled ETL, dependencies across many systems and batch training. It is less ML-specific: no built-in artefact lineage, and heavy compute is usually delegated (to Kubernetes pods, Spark or a cloud ML job) rather than run on workers.

Argo Workflows is a lightweight Kubernetes-native workflow engine (Kubeflow Pipelines has used it as its backend). Prefect is a Python-first orchestrator with dynamic flows. Dagster models pipelines as data assets with strong lineage, typing and testing.

Managed pipelines—SageMaker Pipelines, Azure ML pipelines, Vertex AI Pipelines—remove infrastructure work and integrate tightly with each platform's registry, compute and endpoints, at the cost of portability.

A common hybrid: Airflow, already used by the data team, schedules the end-to-end flow and triggers a Kubeflow or cloud ML pipeline for the GPU training part.

How it works

  1. List needs: schedules, event triggers, GPUs, caching, lineage, multi-system dependencies.
  2. Check existing platforms and team skills.
  3. Prototype one real pipeline in the top two candidates.
  4. Evaluate operations: upgrades, scaling, monitoring, access control.
  5. Standardise templates for teams.

Example

from kfp import dsl

@dsl.component(base_image="python:3.11")
def validate(data: str) -> str: ...

@dsl.component(base_image="ghcr.io/acme/train:1.4")
def train(data: str) -> str: ...

@dsl.pipeline(name="churn-training")
def pipeline(data: str):
    v = validate(data=data)
    t = train(data=v.output).set_accelerator_type("nvidia.com/gpu").set_accelerator_limit(1)

Common mistakes

  • Running heavy training inside Airflow workers.
  • Picking Kubeflow without the Kubernetes skills to operate it.
  • A different orchestrator per team.
  • Ignoring caching, so every rerun recomputes all steps.

How to answer in the interview

"Kubeflow Pipelines is my choice when ML already runs on Kubernetes: every step is a container, with caching, artefact tracking and lineage. Airflow is the standard general scheduler, great for ETL and batch training, though less ML-aware, so heavy work runs elsewhere. Argo, Prefect and Dagster are good alternatives; Dagster is strong on data-asset lineage. Managed pipelines in SageMaker, Azure ML or Vertex remove operations. I choose by team skills, existing platform and needs like caching, GPUs and lineage, and often Airflow triggers Kubeflow for training."

Likely follow-up questions

  • Why run training in Kubeflow but schedule from Airflow? Airflow handles cross-system data dependencies; Kubeflow handles containerised GPU steps and ML lineage.
  • What is step caching? Reusing a step's output when inputs and code are unchanged.
  • How do you test pipelines? Unit-test components, run on sample data in CI.
