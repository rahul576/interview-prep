After a release, memory usage of a Java service keeps growing until pods restart every few hours. What do you do?

Troubleshooting · scenario · levels senior, lead

In one line

Mitigate first by rolling back (which also confirms the release is the cause), then separate heap growth from native growth with GC metrics and Native Memory Tracking, compare heap dumps over time in Eclipse MAT, diff the release for unbounded caches, listeners, ThreadLocals or library upgrades, and add memory alerts and soak tests.

Detailed explanation

Pods restarting every few hours with steadily rising memory is a classic leak, and the timing points to the release. Restarts are themselves a symptom: each one drops in-flight requests and cold-starts caches.

Mitigation: roll back. If memory becomes flat again, the release is confirmed as the cause and you can investigate calmly on a canary or staging. If rollback is impossible, temporarily raise limits or schedule controlled restarts while investigating.

Heap or native? Look at old-generation heap used after GC (or "live data set"). If the floor after each GC keeps rising, objects are being retained: a heap leak, which eventually yields OutOfMemoryError: Java heap space or GC thrashing. If heap after GC is flat but container RSS keeps rising, the leak is outside the heap: enable NMT and compare summary.diff snapshots to see whether threads, Metaspace (class loader leak, dynamic proxy generation), direct buffers or "Internal/Other" grow. Growth invisible to NMT suggests malloc fragmentation or a native library leak.

Heap leak analysis: take two or three heap dumps some time apart (jcmd <pid> GC.heap_dump, preferably on a canary pod since dumps pause the JVM and contain sensitive data), and open them in Eclipse MAT. Use the leak suspects report, the dominator tree and path to GC roots to see which objects retain the most memory and who holds them. Comparing histograms between dumps shows which classes keep growing. -XX:+HeapDumpOnOutOfMemoryError captures one automatically.

Typical culprits in a release diff: a HashMap used as a cache without eviction (use Caffeine with size and TTL), listeners or callbacks registered per request and never removed, ThreadLocal values not cleared on pooled threads, high-cardinality metric tags (Micrometer creating a meter per user id), unclosed streams or result sets, and library upgrades that changed defaults (an HTTP client connection pool, a driver statement cache).

Prevent recurrence: alert on heap-after-GC trend and RSS approaching the limit, and run a soak test of several hours in the pipeline for releases.

How it works

  1. Roll back; confirm memory stabilises.
  2. Check heap after GC vs RSS to classify the leak.
  3. Heap: dumps over time → MAT dominator tree and GC root paths.
  4. Native: NMT baseline and diffs; check threads, Metaspace, direct memory.
  5. Diff the release for caches, listeners, ThreadLocals, meters, upgrades.
  6. Fix, verify with a soak test, add alerts.

Example

# On a canary pod: two heap dumps 30 minutes apart
jcmd 1 GC.heap_dump /tmp/heap-1.hprof
sleep 1800
jcmd 1 GC.heap_dump /tmp/heap-2.hprof

# Quick class histogram comparison without full dumps
jcmd 1 GC.class_histogram | head -15
MAT dominator tree (heap-2):
  com.shop.pricing.PriceService  1.4 GB retained
    └─ java.util.HashMap "priceCache"   12,480,000 entries
Cause: cache added in release 4.12 with no eviction; key includes request timestamp
// Fix: bounded cache
Cache<String, Price> priceCache = Caffeine.newBuilder()
    .maximumSize(50_000).expireAfterWrite(Duration.ofMinutes(10)).build();

Common mistakes

  • Simply raising memory limits, which only delays the restarts.
  • Taking a single heap dump; growth needs comparison over time.
  • Assuming every leak is in the heap and ignoring RSS and NMT.
  • Dumping heaps on busy production pods without considering pauses and sensitive data.

How to answer in the interview

"Because it started with a release, I first roll back, which stops the restarts and confirms the cause. Then I check whether it's heap or native: if old-gen usage after GC keeps rising, it's a heap leak; if RSS grows while the heap is flat, I use Native Memory Tracking diffs. For a heap leak I take two heap dumps some time apart on a canary and compare them in Eclipse MAT, using the dominator tree and paths to GC roots. Then I diff the release for unbounded caches, listeners, ThreadLocals, high-cardinality metrics or library upgrades. After the fix I add memory-trend alerts and a soak test in the pipeline."

Likely follow-up questions

  • When would you suspect a library upgrade? When the dominant objects are library classes, or the diff has no relevant code but dependency versions changed.
  • Why heap after GC rather than heap used? Heap used is sawtooth; the floor after GC shows retained live data.
  • What is a class loader leak? Old class loaders retained by references, so Metaspace grows on redeploys or dynamic class generation.
