What does docker system df show, and why does Docker use so much disk space?

Docker · concept · levels entry

In one line

docker system df shows disk used by images, containers, local volumes and build cache and how much is reclaimable; disks fill because of old and dangling images, stopped containers, build cache and unbounded container logs, so use prune commands and log rotation.

Detailed explanation

Docker keeps everything until told otherwise, and on a busy build or application host the data directory (/var/lib/docker) grows steadily. docker system df gives a summary per category with a RECLAIMABLE column, the space used by items nothing currently references. docker system df -v lists individual images, containers, volumes and cache entries.

The usual growth sources are: every rebuild leaves the previous image as a dangling image (<none>:<none>) or as an unused old tag; stopped containers keep their writable layers; BuildKit's build cache grows with each build and branch; unused volumes remain after containers are removed (especially anonymous ones); and container logs with the default json-file driver have no size limit, so a chatty application can write tens of gigabytes. Note that logs are not shown by system df; they live under /var/lib/docker/containers/<id>/.

Cleaning is done with prune commands. docker image prune removes dangling images and -a all unused ones; docker container prune, docker builder prune and docker volume prune target the others; docker system prune combines several. Filters such as --filter until=168h keep recent items. For logs, configure max-size and max-file in daemon.json (applies to new containers) or use the local driver, which rotates by default.

How it works

  1. Images, layers, containers and cache are stored under /var/lib/docker.
  2. Docker tracks which items are referenced by containers or tags.
  3. system df sums sizes and calculates unreferenced space.
  4. Prune commands delete unreferenced items matching filters.
  5. Log rotation caps per-container log files.

Example

docker system df
docker builder prune --filter until=168h -f
docker image prune -a --filter until=168h -f
docker container prune -f
du -sh /var/lib/docker/containers/*/*-json.log | sort -h | tail
{ "log-driver": "json-file", "log-opts": { "max-size": "20m", "max-file": "5" } }

Common mistakes

  • Running docker volume prune or system prune --volumes on a production host and deleting database data.
  • Forgetting log rotation, the most common cause of full disks.
  • Pruning only when the disk is already full instead of scheduling it.
  • Expecting daemon.json log options to apply to already running containers.

How to answer in the interview

"docker system df summarises disk usage by images, containers, volumes and build cache and shows what's reclaimable; -v gives per-item details. Docker fills disks because every rebuild leaves old and dangling layers, stopped containers keep their writable layers, the BuildKit cache grows with each build, and json-file logs have no size limit by default. I schedule targeted prunes with an until filter, like builder prune and image prune for anything older than a week, and configure max-size and max-file log rotation in daemon.json. On production I never prune volumes automatically."

Likely follow-up questions

  • What would you never clean on production? Volumes, because they hold persistent data.
  • What is a dangling image? An untagged image left after a rebuild replaced its tag.
  • Where are container logs stored? Under /var/lib/docker/containers/<id>/ with json-file.
