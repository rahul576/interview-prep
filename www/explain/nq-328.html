How do you use Jira to track stories, tasks, and blockers?

Agile & Scrum · scenario · levels entry

In one line

In Jira I organise work as epics, stories, tasks/sub-tasks and bugs on a sprint board whose columns mirror our workflow, make blockers visible with flags, a Blocked status and "is blocked by" links, link commits and pull requests by issue key, and use burndown, velocity and dashboards for planning.

Detailed explanation

Jira is only useful if it reflects reality, so the first habit is discipline: every piece of work has an issue, and I move my issues as soon as their state changes.

The issue hierarchy gives structure. An epic represents a larger feature or initiative spanning several sprints. Stories are user-facing slices with a description, acceptance criteria and a story point estimate. Tasks cover technical work, sub-tasks break a story down for the people working on it, and bugs track defects with steps to reproduce, expected and actual behaviour. In newer Jira Cloud projects the epic link has been replaced by the general parent field, but the idea is the same.

The board maps to the workflow, for example To Do, In Progress, Code Review, QA, Done, often with WIP limits on columns. Swimlanes by epic or assignee help in stand-up. Blockers must be impossible to miss: I add the flag (which highlights the card), or move it to a Blocked status, write a comment saying exactly what is needed and from whom, and create an "is blocked by" link to the blocking issue, which may live in another team's project.

Development integration with GitHub, GitLab or Bitbucket means a branch, commit or PR that contains the issue key, such as PAY-142, shows up in the issue's development panel, and smart commits or automation rules can transition issues when a PR merges. For reporting, the sprint burndown shows progress within a sprint, the velocity chart supports planning, and dashboards with JQL filters give stakeholders a live view.

How it works

  1. Product owner creates epics; the team refines them into stories with acceptance criteria and estimates.
  2. Sprint planning moves stories into the sprint; developers add sub-tasks.
  3. Branches and commits include the issue key, so development status is linked automatically.
  4. Issues move across board columns as work progresses; WIP limits expose bottlenecks.
  5. Blockers are flagged, linked and raised in stand-up.
  6. Burndown, velocity and JQL dashboards are reviewed in planning and sprint reviews.

Example

-- JQL: all blocked or flagged work in the current sprint
project = PAY AND sprint in openSprints()
  AND (status = Blocked OR Flagged is not EMPTY)
ORDER BY priority DESC

-- JQL: issues in my project blocked by another team's issues
project = PAY AND issueLinkType = "is blocked by"
git checkout -b feature/PAY-142-refund-endpoint
git commit -m "PAY-142 add refund endpoint with idempotency key"

Common mistakes

  • Updating the board only before the sprint review, so it never reflects reality.
  • Stories without acceptance criteria, which leads to arguments about "done".
  • Blockers mentioned verbally but never flagged or linked, so nobody can see dependencies.
  • Overly complex workflows with ten statuses that nobody follows.
  • Using velocity to compare teams or individuals.

How to answer in the interview

"We use epics for larger features, broken down into stories with acceptance criteria and story points, plus tasks, sub-tasks and bugs. Our sprint board has columns like To Do, In Progress, Code Review, QA and Done, and I keep my own items updated so the board is always accurate. When something is blocked I flag it or move it to Blocked, write a comment saying exactly what I need and from whom, and add an 'is blocked by' link to the other team's issue, and I raise it in the stand-up. Branches and commits include the issue key, so Jira shows the PRs and build status. In planning and reviews we look at the burndown, velocity and a JQL dashboard of blocked items."

Likely follow-up questions

  • How do you track a dependency on another team in Jira? Create or find the issue in their project, link it with "is blocked by", and follow up in a shared dependency dashboard or sync.
  • Sub-task or separate story? Sub-tasks for steps of one deliverable; a separate story if it delivers value on its own.
  • What does the burndown tell you? Whether the sprint scope is on track and whether scope was added mid-sprint.
