What are conditional beans in Spring Boot?

Spring Boot · concept · levels mid

In one line

Conditional beans are registered only when a condition holds at startup: the core is @Conditional(MyCondition.class), and Spring Boot adds @ConditionalOnProperty, @ConditionalOnClass, @ConditionalOnBean/OnMissingBean, @ConditionalOnWebApplication, @ConditionalOnExpression and more, used by auto-configuration and for feature toggles.

Detailed explanation

Sometimes a bean should exist only in certain situations: a real SMS sender in production but a logging stub elsewhere, a Redis cache only when Redis is on the classpath, a feature only when a flag is set. Instead of if statements around object creation, Spring lets you attach a condition to the bean definition, evaluated while the context is being built.

The core mechanism, from Spring Framework 4, is @Conditional with a class implementing Condition.matches(ConditionContext, AnnotatedTypeMetadata). The context gives access to the Environment, bean factory, class loader and resource loader. @Profile itself is implemented as a condition.

Spring Boot adds ready-made conditions: @ConditionalOnProperty (value of a property, with havingValue and matchIfMissing), @ConditionalOnClass/OnMissingClass (classpath), @ConditionalOnBean/OnMissingBean (other beans in the context), @ConditionalOnWebApplication/OnNotWebApplication, @ConditionalOnExpression (SpEL), @ConditionalOnResource, @ConditionalOnJava, @ConditionalOnCloudPlatform and @ConditionalOnThreading (platform vs virtual threads). Conditions can be placed on @Configuration classes or individual @Bean methods, and several conditions combine with AND.

Auto-configuration is built entirely from these. Bean-based conditions depend on what has been registered so far, which is why they are reliable in auto-configuration (processed last, with explicit ordering) but fragile in normal application configuration.

How it works

  1. The container parses configuration classes and bean definitions.
  2. For each conditional definition it evaluates the condition(s).
  3. Matching definitions are registered; others are skipped.
  4. Skipped and matched conditions are recorded in the conditions report.
  5. The context refreshes with only the registered beans.

Example

public interface SmsSender { void send(String to, String text); }

@Configuration
class SmsConfig {
    @Bean
    @ConditionalOnProperty(name = "sms.provider", havingValue = "twilio")
    SmsSender twilioSender(TwilioProps p) { return new TwilioSmsSender(p); }

    @Bean
    @ConditionalOnMissingBean(SmsSender.class)
    SmsSender loggingSender() { return (to, text) -> log.info("SMS to {}: {}", to, text); }
}

class OnLinuxCondition implements Condition {
    public boolean matches(ConditionContext ctx, AnnotatedTypeMetadata md) {
        return ctx.getEnvironment().getProperty("os.name", "").contains("Linux");
    }
}

Common mistakes

  • Relying on @ConditionalOnBean in user configuration where registration order is not guaranteed.
  • Using conditions for business logic that should be runtime decisions.
  • Not testing both the enabled and disabled paths.
  • Overusing @ConditionalOnExpression when a property condition is clearer.

How to answer in the interview

"Conditional beans are bean definitions registered only when a condition holds at startup. The core is @Conditional with a Condition class that inspects the environment. Spring Boot adds convenient ones: OnProperty, OnClass and OnMissingClass, OnBean and OnMissingBean, OnWebApplication, OnExpression, and @Profile is also a condition. Auto-configuration is built from them. I use them for feature toggles, choosing implementations per environment, like a real SMS sender in production and a logging stub elsewhere, and for overridable defaults in shared libraries."

Likely follow-up questions

  • Why is @ConditionalOnBean ordering-sensitive? It only sees beans already registered when it is evaluated.
  • Profile vs property condition? Profiles group environment settings; properties give finer, per-feature switches.
  • How to test? ApplicationContextRunner with withPropertyValues and run(ctx -> assertThat(ctx).hasSingleBean(...)).
