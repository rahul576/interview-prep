How would you extract the year from an order date?

Databases & SQL · concept · levels entry

In one line

Use EXTRACT(YEAR FROM order_date) (SQL standard, PostgreSQL, Oracle, MySQL) or YEAR(order_date) (MySQL, SQL Server); in WHERE clauses prefer a date range so an index on the column can still be used.

Detailed explanation

Every major database can pull the year out of a date, but the syntax differs:

  • Standard SQL / PostgreSQL / Oracle / MySQL: EXTRACT(YEAR FROM o.order_date).
  • MySQL and SQL Server: YEAR(o.order_date); SQL Server also has DATEPART(year, o.order_date).
  • PostgreSQL: DATE_PART('year', o.order_date) or date_trunc('year', ...) which returns a timestamp at the start of the year.
  • Oracle: TO_CHAR(o.order_date, 'YYYY') returns text, not a number, so sorting and comparisons behave like strings.
  • SQLite: strftime('%Y', order_date), also text.

In the SELECT list and GROUP BY this is perfectly fine, because the database has to read every row anyway. The performance issue appears in filtering. WHERE YEAR(order_date) = 2024 applies a function to the column, so a normal B-tree index on order_date cannot be used for a range seek; the query is not sargable and tends to scan. Rewrite it as a half-open range: order_date >= DATE '2024-01-01' AND order_date < DATE '2025-01-01'. The half-open form also works correctly for TIMESTAMP columns, where BETWEEN ... '2024-12-31' would miss times later on 31 December. Alternatively, some databases support an index on the expression (function-based or generated column).

Also consider time zones: if order_date is a UTC timestamp, the "year" of an order placed at 23:30 on 31 December in India may differ, so convert before extracting if the business year is local.

How it works

  1. The function reads the date value of each row.
  2. It returns the year component (integer for EXTRACT/YEAR, string for TO_CHAR/strftime).
  3. The result can be aliased (AS order_year) and grouped on.
  4. For filtering, the optimiser can only use the index if the column is compared directly.

Example

-- Grouping: function is fine
SELECT EXTRACT(YEAR FROM order_date) AS order_year, SUM(amount)
FROM orders
GROUP BY EXTRACT(YEAR FROM order_date);

-- Filtering: use a sargable range
SELECT * FROM orders
WHERE order_date >= DATE '2024-01-01'
  AND order_date <  DATE '2025-01-01';

Common mistakes

  • Using WHERE YEAR(order_date) = 2024 on a large indexed table.
  • Using BETWEEN '2024-01-01' AND '2024-12-31' on timestamps and losing the last day.
  • Treating TO_CHAR output as a number.
  • Ignoring time zone conversion for business years.

How to answer in the interview

"In standard SQL, PostgreSQL and Oracle I'd write EXTRACT(YEAR FROM order_date); MySQL and SQL Server also give me YEAR(order_date). In the SELECT and GROUP BY that's fine. But I avoid it in WHERE, because wrapping the column in a function usually stops the database using the index on order_date. To filter one year I'd write order_date >= 1 January 2024 and order_date < 1 January 2025, which is index-friendly and also correct for timestamps."

Likely follow-up questions

  • Why is WHERE YEAR(order_date) = 2024 slow? The function hides the column from the index, forcing a scan of every row.
  • What does sargable mean? A predicate the engine can answer with an index seek, typically a bare column compared to a constant.
  • How else can you index it? A function-based index or an indexed generated column on the year.
