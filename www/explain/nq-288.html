How does Maven build an application and resolve dependencies?

Build Tools · concept · levels entry

In one line

Maven reads the pom.xml (coordinates, dependencies, plugins), runs the lifecycle phases in order with plugin goals, and resolves dependencies from the local repository ~/.m2 or remote repositories (Maven Central, Nexus), including transitive ones, choosing versions by nearest wins unless dependencyManagement/BOMs pin them.

Detailed explanation

The POM. Every Maven project has a pom.xml that declares its coordinates — groupId, artifactId, version — plus packaging, dependencies, plugins and, often, a parent POM such as spring-boot-starter-parent that supplies defaults.

Building. Maven's default lifecycle is an ordered list of phases: validate, compile, test, package, verify, install, deploy. When you run mvn package, Maven runs every phase up to package. Each phase executes the plugin goals bound to it: maven-compiler-plugin compiles, maven-surefire-plugin runs unit tests, maven-jar-plugin or spring-boot-maven-plugin builds the artifact. install copies the artifact to the local repository; deploy uploads it to a remote one.

Resolving dependencies. For each dependency, Maven first checks the local repository at ~/.m2/repository. If it is missing, it downloads the JAR and its POM from configured remote repositories — Maven Central by default, often a corporate Nexus or Artifactory mirror configured in settings.xml. Each dependency's POM declares its own dependencies, so Maven builds the full transitive dependency tree.

Conflicts. If two paths request different versions of the same artifact, Maven uses nearest definition wins (shallowest in the tree; first declared on ties). You take control by declaring versions in <dependencyManagement> or importing a BOM like Spring Boot's, so all modules use consistent, tested versions.

Scopes — compile, provided, runtime, test — determine on which classpaths a dependency appears and whether it is packaged.

How it works

  1. Parse pom.xml, apply parent POM and profiles.
  2. Resolve the dependency tree from ~/.m2 or remote repositories.
  3. Mediate version conflicts with nearest-wins and dependencyManagement.
  4. Run lifecycle phases up to the requested one.
  5. Each phase runs bound plugin goals.
  6. Output artifact in target/, optionally installed or deployed.

Example

<project>
  <groupId>com.example</groupId>
  <artifactId>orders</artifactId>
  <version>1.0.0</version>
  <parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>3.3.4</version>
  </parent>
  <dependencies>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-web</artifactId>
    </dependency>
  </dependencies>
</project>
./mvnw package
./mvnw dependency:tree

Common mistakes

  • Thinking mvn test skips compile (earlier phases always run).
  • Hard-coding versions in every module instead of dependencyManagement.
  • Deleting ~/.m2 to "fix" problems instead of diagnosing them.
  • Forgetting that transitive dependencies can change when a direct one is upgraded.

How to answer in the interview

"Maven reads the pom.xml, which defines the coordinates — groupId, artifactId and version — the dependencies and plugins. Running a phase like mvn package executes all earlier phases in order: validate, compile, test, package, and later verify, install and deploy, each running plugin goals such as compiler, surefire and jar. For dependencies Maven looks in the local repository in ~/.m2, otherwise downloads from Maven Central or a corporate Nexus, including transitive dependencies. Conflicts resolve by nearest wins, and I control versions with dependencyManagement or a BOM like Spring Boot's. Scopes decide where a dependency is available."

Likely follow-up questions

  • How would you find and fix a version conflict? mvn dependency:tree -Dverbose, then pin via dependencyManagement or exclude.
  • What is settings.xml for? Mirrors, credentials and profiles for repositories, per user or CI.
  • What are SNAPSHOT versions? Mutable development versions that Maven re-checks for updates.
