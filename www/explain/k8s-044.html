How do you ensure only trusted, signed images run in your clusters?

Kubernetes · concept · levels mid, senior, lead

In one line

Sign images in CI (cosign keyless via Sigstore, or Notation), attach SBOM and provenance attestations, and enforce them with an admission policy (Kyverno, Sigstore policy-controller, Gatekeeper with Ratify) that verifies signer identity, allows only approved registries and requires digests rather than mutable tags.

Detailed explanation

A trusted image pipeline answers: who built this image, from which source, and was it changed since? Signing binds an image digest to an identity. With cosign keyless signing, the CI job gets an OIDC token (for example from GitHub Actions), Fulcio issues a short-lived certificate for that workflow identity, the signature is stored in the registry next to the image and recorded in the Rekor transparency log. There is no long-lived private key to leak, and verifiers check "signed by workflow X in repo Y". Notation (Notary Project) is the alternative common with Azure and enterprise PKI.

CI also attaches attestations: an SBOM (SPDX or CycloneDX) and SLSA provenance describing the build. Signing happens after build, tests and vulnerability scanning, so a signature means the image passed the pipeline.

Enforcement happens at admission. A policy engine intercepts pod creation, resolves the image to its digest, verifies the signature against the expected issuer and subject, optionally verifies attestations (for example, provenance from your builder, no critical CVEs at scan time), and rejects images from unapproved registries. Referencing by digest matters because a tag can be moved to a different image after verification. Policies roll out in audit mode first, then enforce, with a documented break-glass exception.

How it works

  1. CI builds, tests and scans the image, then pushes it and records the digest.
  2. cosign sign keylessly with the CI OIDC identity; signature logged in Rekor.
  3. cosign attest SBOM and provenance.
  4. Deployment manifests reference image@sha256:....
  5. Admission policy verifies signature, identity and attestations; restricts registries.
  6. Start in audit, monitor violations, then enforce.

Example

cosign sign --yes registry.example.com/shop/api@sha256:3f1c...
cosign attest --yes --type spdxjson --predicate sbom.spdx.json registry.example.com/shop/api@sha256:3f1c...
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: { name: verify-signed-images }
spec:
  validationFailureAction: Enforce
  webhookTimeoutSeconds: 15
  rules:
    - name: cosign-keyless
      match: { any: [{ resources: { kinds: [Pod] } }] }
      verifyImages:
        - imageReferences: ["registry.example.com/*"]
          mutateDigest: true
          attestors:
            - entries:
                - keyless:
                    issuer: https://token.actions.githubusercontent.com
                    subject: "https://github.com/example/shop/.github/workflows/release.yml@refs/heads/main"

Common mistakes

  • Verifying "any valid signature" instead of a specific identity.
  • Signing tags rather than digests.
  • Enforcing immediately and blocking system images.
  • Treating a signature as proof the image has no vulnerabilities.

How to answer in the interview

"I sign every image in CI after it's built and scanned, using cosign keyless signing so the signature is tied to the pipeline's OIDC identity and logged in Rekor, with no long-lived keys. CI also attaches an SBOM and SLSA provenance. In the cluster, Kyverno or the Sigstore policy-controller verifies the signature and expected signer identity at admission and rejects unapproved registries. Manifests use digests, so what we verified is exactly what runs. I roll policies out in audit mode first and keep a break-glass process."

Likely follow-up questions

  • What does a signature prove? Who signed which digest; not that the code is secure or bug-free.
  • Why digests? Tags are mutable; a digest is content-addressed.
  • How do you handle third-party images? Mirror into your registry, scan and re-sign, or verify the vendor's signatures.
