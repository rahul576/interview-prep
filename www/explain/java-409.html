How do you implement a distributed lock with Redis, and what are the caveats?

Caching · concept · levels senior, lead

In one line

Acquire with SET key token NX PX ttl, release with a Lua script that deletes only if the value is still your token, and remember the lock can expire while you still work, so for strict correctness use fencing tokens or a consensus store like etcd or ZooKeeper.

Detailed explanation

A distributed lock lets only one instance run a critical section, such as a scheduled job or processing one order. The minimal correct Redis recipe:

  • Acquire: SET lock:order:42 <random-token> NX PX 30000. NX sets only if the key does not exist; PX gives a TTL so the lock disappears if the holder crashes. Both happen atomically in one command (do not use separate SETNX and EXPIRE).
  • Release: a Lua script compares the value with your token and deletes it only if they match. A plain DEL might delete a lock that already expired and was taken by someone else.

The fundamental caveat is timing. If the holder pauses longer than the TTL, the lock expires, another process acquires it, and now two processes act at once. Renewal ("watchdog", as in Redisson, which extends the TTL while the holder is alive) reduces but does not eliminate the risk, because the paused process cannot know it lost the lock. Replication adds another: Redis replication is asynchronous, so a failover can lose a freshly acquired lock.

For correctness-critical cases, use fencing tokens: the lock service issues a monotonically increasing number with each grant, and the protected resource (database, storage) rejects writes carrying an older token. etcd revisions and ZooKeeper zxids provide this naturally.

How it works

  1. Generate a unique token (UUID) per attempt.
  2. SET ... NX PX to acquire; retry with backoff or give up.
  3. Do the work, keeping it shorter than the TTL or renewing the TTL.
  4. Release with compare-and-delete in Lua.
  5. For strict safety, pass a fencing token to the resource, which rejects stale tokens.

Example

String token = UUID.randomUUID().toString();
Boolean ok = redis.opsForValue()
    .setIfAbsent("lock:job:nightly", token, Duration.ofSeconds(30));   // SET NX PX
if (Boolean.TRUE.equals(ok)) {
    try { runJob(); }
    finally {
        redis.execute(new DefaultRedisScript<>(
            "if redis.call('get', KEYS[1]) == ARGV[1] then " +
            "  return redis.call('del', KEYS[1]) else return 0 end", Long.class),
            List.of("lock:job:nightly"), token);
    }
}
// Redisson alternative: RLock lock = redisson.getLock("lock:job"); lock.lock();  // watchdog renewal

Common mistakes

  • SETNX then EXPIRE as two commands: a crash in between leaves a lock forever.
  • Releasing with plain DEL without checking the token.
  • Assuming the lock guarantees mutual exclusion under GC pauses or failover.

How to answer in the interview

"I'd acquire with SET key, a unique token, NX and PX, so it's set only if absent and expires if I crash. To release, I run a Lua script that deletes the key only if it still holds my token, so I never remove someone else's lock. The big caveat is that a lock with a TTL can expire while I'm still working, for example during a long GC pause, and async replication can lose a lock on failover, so two holders are possible. For efficiency, such as avoiding duplicate cron runs, that's fine, and Redisson gives me a tested lock with watchdog renewal. For correctness I'd add fencing tokens checked by the resource, or use etcd, ZooKeeper or a database constraint."

Likely follow-up questions

  • What is a fencing token, and who checks it? An increasing number issued with each lock grant; the protected resource rejects requests with an older number.
  • What is Redlock? Acquiring the lock on a majority of independent Redis nodes; it still relies on timing assumptions.
  • Alternative without Redis? SELECT ... FOR UPDATE, PostgreSQL advisory locks, or ShedLock for scheduled jobs.
