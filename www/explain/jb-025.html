What is the output of String s1 = "Java"; String s2 = new String("Java"); System.out.println(s1 == s2)?

Core Java & OOP · concept · levels entry, mid

In one line

It prints false: s1 refers to the pooled literal, new String("Java") creates a distinct heap object, and == compares references, not content; s1.equals(s2) would be true.

Detailed explanation

Walk through what the JVM does line by line.

String s1 = "Java"; uses a string literal. The literal is resolved through the string pool: the JVM either finds an existing "Java" instance in the pool or creates and registers one. s1 now holds a reference to that pooled object.

String s2 = new String("Java"); evaluates the literal "Java" first (the same pooled object), then the new operator always allocates a fresh String object on the heap, initialised with the same content. In modern JDKs the new object may even share the internal byte array with the literal, but it is still a different object with a different identity. s2 refers to that new object. (So this line involves up to two objects: the pooled literal, which may already exist, and the new one.)

s1 == s2 compares the two references. They point to different objects, so the result is false.

Variations interviewers like:

  • s1.equals(s2) is true: String.equals compares characters.
  • s1 == s2.intern() is true: intern() returns the pooled instance, which is exactly what s1 points to.
  • String s3 = "Java"; s1 == s3 is true: both literals share the pooled instance.
  • s1 == "Ja" + "va" is true: constant expressions are folded at compile time.
  • With a non-final variable, String p = "Ja"; s1 == p + "va" is false: runtime concatenation creates a new object.

The practical lesson: == on strings tests identity, which depends on how the strings were created. It can pass in a unit test with literals and fail in production with strings read from a request or database. Always use equals (or equalsIgnoreCase, or Objects.equals for null safety). There is almost never a reason to write new String("...").

How it works

  1. Literal "Java" is resolved via the pool; s1 gets the pooled reference.
  2. new String("Java") allocates a new object with the same content.
  3. s2 gets the new object's reference.
  4. == compares the two references: different, so false.

Example

String s1 = "Java";
String s2 = new String("Java");

System.out.println(s1 == s2);            // false
System.out.println(s1.equals(s2));       // true
System.out.println(s1 == s2.intern());   // true
System.out.println(s1 == "Ja" + "va");   // true  (compile-time constant)
System.out.println(System.identityHashCode(s1) == System.identityHashCode(s2)); // false

Common mistakes

  • Answering "true because the content is the same".
  • Thinking new String puts the object into the pool.
  • Relying on == because tests with literals pass.
  • Calling s1.equals(s2) where s1 may be null; use "Java".equals(x) or Objects.equals.

How to answer in the interview

"It prints false. s1 points to the literal "Java" in the string pool. new String always creates a new, distinct object on the heap with the same content, so s2 is a different object. The == operator compares references, not content, and the references differ. s1.equals(s2) would be true because equals compares the characters. If I used s2.intern(), or compared two literals, == would print true, because both would point to the pooled instance. The lesson for production code is to always compare strings with equals."

Likely follow-up questions

  • What does s1 == s2.intern() print, and why? True, because intern returns the pooled instance s1 already refers to.
  • How many objects does new String("Java") create? One new object, plus the pooled literal if it didn't exist yet.
  • What does "Ja" + "va" == "Java" print? True, because it's folded at compile time.
