How do Terraform and Ansible work together?

Infrastructure as Code · concept · levels mid

In one line

Terraform provisions and tracks infrastructure, Ansible configures what runs on it; connect them through dynamic inventory or Terraform outputs in separate pipeline stages, avoid provisioners, or bake images with Packer + Ansible for immutable infrastructure.

Detailed explanation

The tools have different models. Terraform is declarative with a state file: it knows which VPCs, instances, databases and DNS records it created, computes a plan of differences and handles dependencies and deletion. Ansible is procedural-but-idempotent and stateless: it connects to hosts and makes packages, files, users and services match the playbook, and it is also good at operational tasks such as rolling restarts. Using Terraform for software configuration or Ansible for cloud lifecycle works poorly; together they cover the stack.

The clean integration is a pipeline with separate stages. Terraform applies first and tags resources (role=web, env=prod). Ansible then discovers hosts through a dynamic inventory plugin (amazon.aws.aws_ec2, azure.azcollection.azure_rm) that groups instances by those tags, or reads terraform output -json. Red Hat also publishes a cloud.terraform collection whose inventory plugin can read Terraform state. Each stage can be retried on its own, and failures are easy to understand.

Provisioners (local-exec calling ansible-playbook) seem convenient but are discouraged: Terraform cannot track what Ansible did, a failed playbook taints the resource so the next apply recreates the server, and re-running configuration requires hacks with triggers.

For immutable infrastructure the split moves earlier: Packer runs Ansible to bake a golden image, Terraform deploys the image to an auto scaling group, and nobody configures running production servers. Ansible may still handle day-2 tasks that do not fit images.

How it works

  1. Terraform creates network, instances and load balancer, tagging each instance.
  2. Pipeline stores Terraform outputs (for example bastion address, DB endpoint).
  3. Ansible dynamic inventory groups hosts by tags.
  4. Ansible playbook configures hosts, using outputs as variables.
  5. Alternatively, Packer + Ansible bake the image and Terraform only rolls it out.

Example

# inventory/aws_ec2.yml
plugin: amazon.aws.aws_ec2
regions: [eu-west-1]
filters:
  tag:env: prod
keyed_groups:
  - key: tags.role
    prefix: role
terraform apply -auto-approve tfplan
terraform output -json > tf_outputs.json
ansible-playbook -i inventory/aws_ec2.yml site.yml -e @tf_outputs.json

Common mistakes

  • Calling Ansible from local-exec and losing control of retries and failures.
  • Hard-coding IP addresses from Terraform into a static inventory.
  • Letting both tools manage the same thing (for example security groups).
  • Configuring long-lived servers in place when images would avoid drift.

How to answer in the interview

"I use each for what it's good at. Terraform provisions the infrastructure and keeps state: network, instances, databases, DNS. Ansible configures the servers and handles operational tasks. In the pipeline, Terraform runs first and tags instances; Ansible then finds them with a dynamic inventory plugin and can read Terraform outputs as variables. I avoid calling Ansible from Terraform provisioners because failures taint resources and re-runs are messy. Where possible I go immutable: Packer runs Ansible to bake images, and Terraform only rolls those images out."

Likely follow-up questions

  • Why are Terraform provisioners a last resort? Their effects are not in state, they are not idempotent, and failures taint resources.
  • Where do secrets come from? A vault or cloud secrets manager, read by Ansible at runtime, not Terraform outputs in plain text.
  • What about cloud-init? Good for minimal bootstrap, such as registering with a config system, not full configuration.
