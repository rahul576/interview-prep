What is continuous batching, and why does it matter for LLM serving?

LLMOps & RAG · concept · levels mid, senior

In one line

Continuous batching (in-flight or iteration-level batching) reschedules the batch at every decode step, so finished sequences are immediately replaced by new ones; requests of different lengths no longer block each other, giving much higher GPU utilisation and throughput in engines like vLLM, TGI, TensorRT-LLM and SGLang.

Detailed explanation

Because decode is memory-bound, batching is essential: one read of the weights serves every sequence in the batch. The question is how to form batches when requests arrive at random times and produce very different output lengths.

Static batching (request-level) collects N requests, runs them together and returns when all are done. Problems: a 20-token answer waits for a 2,000-token answer in the same batch; slots of finished sequences sit idle, wasting compute; and new requests wait in a queue until the whole batch completes, so latency includes other people's long answers.

Continuous batching, introduced by the Orca paper and popularised by vLLM, makes scheduling decisions at every iteration. After each decode step, the scheduler removes sequences that hit a stop token or max length and admits waiting requests into the free capacity, constrained by available KV cache blocks and a token budget. A new request's prefill runs, then it joins the decode batch mid-flight. Modern engines use chunked prefill to mix prompt chunks and decode tokens in the same step, so a huge prompt does not freeze ongoing streams.

The effect is that the GPU always works on as many sequences as memory allows, queueing delay drops, and throughput commonly improves several times. It is the main reason a dedicated serving engine beats a simple loop around model.generate().

It introduces new trade-offs. Larger batches make each decode step slightly slower, raising inter-token latency for everyone, and long prefills can still cause spikes. Engines expose knobs such as maximum number of sequences, maximum batched tokens and scheduling policies (priority, fairness) to balance throughput against latency SLOs.

How it works

  1. Requests enter a waiting queue.
  2. Each step, the scheduler checks free KV blocks and token budget.
  3. It admits new requests (prefill, possibly chunked) alongside running decodes.
  4. One forward pass advances every running sequence by a token.
  5. Finished sequences leave; their memory is freed for the next step.

Example

vllm serve Qwen/Qwen2.5-7B-Instruct \
  --max-num-seqs 256 \
  --max-num-batched-tokens 8192 \
  --enable-chunked-prefill
# Metrics: vllm:num_requests_running, vllm:num_requests_waiting, vllm:gpu_cache_usage_perc

Common mistakes

  • Benchmarking with one request at a time and missing batching benefits.
  • Setting max sequences so high that inter-token latency breaks SLOs.
  • Confusing continuous batching with dynamic batching for classic ML models.
  • Ignoring that long prompts still affect others without chunked prefill.

How to answer in the interview

"With static batching, requests are grouped and run until every one finishes, so short answers wait for the longest, finished slots sit idle and new requests wait for the next batch. Continuous batching schedules at every decode step: when a sequence finishes, a waiting request takes its place after its prefill. Requests of very different lengths stop blocking each other, the GPU stays busy and throughput rises several times while queueing drops. vLLM, TGI, TensorRT-LLM and SGLang all do it, which is why I would never serve with a naive generate loop."

Likely follow-up questions

  • New problems for latency-sensitive traffic? Bigger batches slow each step and prefills cause spikes; use priorities, chunked prefill or separate pools.
  • What limits batch size? KV cache memory and max batched tokens.
  • Is it the same as dynamic batching? No, dynamic batching groups whole requests; continuous works per token step.
