When would you fine-tune a model in Foundry instead of using RAG or prompt engineering?

Azure AI & Foundry · concept · levels mid, senior

In one line

Use prompt engineering first (cheapest), RAG when the model needs changing or citable knowledge, and fine-tuning to teach behaviour: style, strict formats or narrow tasks, often letting a smaller model match a larger one; it requires quality training data, evaluation, retraining and hosting cost.

Detailed explanation

These techniques solve different problems, so the question is what is actually missing.

Prompt engineering: clear instructions, examples (few-shot), output schemas, structured outputs and step-by-step guidance. It is fast to iterate, needs no data pipeline and solves a surprising share of problems. Always start here and measure with an evaluation set.

RAG (retrieval-augmented generation): when the model lacks knowledge, such as internal policies, product data or recent documents, retrieval injects the relevant facts into each prompt. Updating knowledge means updating the index, not the model, and answers can cite sources, which matters for trust and compliance. It handles frequently changing facts and per-user permissions.

Fine-tuning changes model weights with your examples. In Foundry this includes supervised fine-tuning (SFT) on example conversations, preference optimisation (DPO) from preferred versus rejected answers, and reinforcement fine-tuning with graders on supported reasoning models. It is the right tool to teach behaviour:

  • a consistent tone or style,
  • a strict output format the model keeps breaking,
  • domain-specific classification or extraction,
  • a narrow task where a small model fine-tuned on outputs of a large one (distillation) matches quality at lower cost and latency.

Costs: you need hundreds to thousands of high-quality examples, training cost, an evaluation pipeline, hosting cost for fine-tuned deployments, and retraining when base models are retired. Fine-tuning is poor for facts: knowledge is baked in at training time, cannot be cited, is hard to remove and goes stale.

Often the best answer is a combination: RAG for knowledge plus a fine-tuned model for format and tone.

How it works

  1. Define success metrics and an evaluation set.
  2. Iterate on prompts; measure.
  3. Add RAG if failures are about missing knowledge.
  4. Consider fine-tuning if failures are about behaviour or cost.
  5. Prepare training data, train, evaluate against the baseline.
  6. Deploy, monitor and plan retraining.

Example

{"messages": [

  {"role": "user", "content": "My invoice shows VAT twice for March."},
  {"role": "assistant", "content": "{\"category\": \"billing\", \"priority\": \"medium\"}"}
]}
# training.jsonl with ~1,000 lines like the above; fine-tune a small model,
# then compare it with the large base model on the same evaluation set

Common mistakes

  • Fine-tuning to inject product facts that change monthly.
  • Skipping prompt engineering and evaluation baselines.
  • Training on a few dozen messy examples.
  • Forgetting hosting cost and retraining when base models retire.

How to answer in the interview

"I go in order of effort. Prompt engineering first, because instructions, examples and output schemas fix many problems cheaply. RAG when the model needs knowledge it doesn't have, especially changing or citable knowledge, because I update the index instead of the model. Fine-tuning, supervised, preference or reinforcement, is for behaviour: style, strict formats or a narrow task, and it can let a smaller, cheaper model match a large one. It needs quality training data, evaluation, retraining when base models change, and hosting costs."

Likely follow-up questions

  • Why not fine-tune facts? They go stale, can't be cited and are hard to update or remove.
  • How much data? Hundreds to a few thousand high-quality examples, depending on the task.
  • How do you know it worked? Compare with the baseline on the same evaluation set.
