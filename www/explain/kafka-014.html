How do you secure a Kafka cluster?

Kafka · concept · levels senior, lead

In one line

Secure Kafka with TLS encryption in transit, authentication via SASL (SCRAM, OAUTHBEARER) or mTLS, least-privilege ACLs per principal, private networking and quotas, plus audit logging and credential rotation.

Detailed explanation

Out of the box, Kafka listeners are PLAINTEXT: anyone who can reach port 9092 can read and write every topic. Security is layered.

Encryption: configure SSL/TLS listeners for client-to-broker traffic and for inter-broker and controller traffic, using certificates from an internal CA. Encryption at rest is handled by disk or cloud volume encryption.

Authentication: SASL_SSL listeners with SCRAM-SHA-512 (username and salted password stored in cluster metadata), OAUTHBEARER with tokens from an identity provider such as Keycloak, Okta or Entra ID, or Kerberos (GSSAPI) in enterprises. Alternatively mutual TLS, where the client certificate's distinguished name becomes the principal. Avoid SASL/PLAIN unless backed by an external callback and TLS.

Authorization: enable an authorizer (StandardAuthorizer in KRaft) with allow.everyone.if.no.acl.found=false. Grant each service principal only what it needs: Write and Describe on its output topics, Read on its input topics plus Read on its consumer group, IdempotentWrite or transactional ID permissions where needed. Prefixed ACLs (orders.) simplify team ownership.

Network and resilience: brokers live in private subnets, reachable through private endpoints or VPC peering, never on the public internet. Quotas (produce and fetch bytes per second, request rate) stop one client from starving others.

Operations: rotate SCRAM credentials and certificates automatically, keep secrets in a vault, enable authorizer audit logs, and manage ACLs as code (Terraform, Strimzi KafkaUser, Confluent RBAC). Managed services add integrations such as MSK IAM authentication.

How it works

  1. Client connects to a SASL_SSL listener over TLS.
  2. Broker authenticates the client and derives a principal.
  3. Each request is checked against ACLs for that principal.
  4. Quotas throttle the principal if it exceeds limits.
  5. Decisions are logged for audit.

Example

listeners=SASL_SSL://:9094,CONTROLLER://:9093
sasl.enabled.mechanisms=SCRAM-SHA-512
authorizer.class.name=org.apache.kafka.metadata.authorizer.StandardAuthorizer
allow.everyone.if.no.acl.found=false
kafka-acls.sh --bootstrap-server b1:9094 --command-config admin.properties \
  --add --allow-principal User:analytics-svc \
  --operation Read --topic orders --group analytics-svc

Common mistakes

  • Leaving a PLAINTEXT listener open "for internal use".
  • One shared superuser credential for all services.
  • Forgetting consumer group ACLs, then granting wildcard access to fix errors.
  • Certificates that expire with no rotation alerting.

How to answer in the interview

"I encrypt everything in transit with TLS, including broker-to-broker traffic. Clients authenticate with SASL, either SCRAM or OAUTHBEARER against our identity provider, or with mutual TLS. Authorization uses ACLs with deny by default, so each service principal can only read or write its own topics and consumer groups. Brokers sit in private networks, quotas protect against noisy clients, credentials and certificates rotate automatically, and ACLs are managed as code and audited. On MSK I would use IAM authentication."

Likely follow-up questions

  • Give a new team read access to one topic? Create a principal, add Read on the topic and its group, via a reviewed ACL change.
  • SCRAM vs mTLS? SCRAM is easier to rotate; mTLS avoids passwords but needs PKI.
  • Encrypt data at rest? Volume encryption, or client-side encryption for sensitive fields.
