How do Jenkins pipelines work? Explain the Jenkinsfile, stages, agents and credentials.

DevOps & CI/CD · concept · levels entry, mid

In one line

A Jenkinsfile defines the pipeline as code in source control, written as declarative or scripted Groovy, divided into stages of steps, run on agents (not the controller), with secrets from the credentials store via withCredentials, shared logic in shared libraries, and multibranch pipelines building every branch and PR.

Detailed explanation

Pipeline as code: the Jenkinsfile lives in the application repository, so pipeline changes are versioned and reviewed like code, and each branch can evolve its pipeline with the code it builds.

Declarative vs scripted: declarative syntax uses a structured pipeline { } block with agent, stages, steps, environment, when, post and options. It is easier to read, validate and lint, and is the recommended default. Scripted pipelines use full Groovy in node { } blocks, which is more flexible but harder to maintain; inside declarative you can still use a script { } block for small pieces of logic.

Stages and steps: stages (Build, Test, Scan, Deploy) structure the pipeline and appear in the UI; steps are the actual actions, such as sh, bat, junit, archiveArtifacts or plugin-provided steps. parallel runs stages concurrently, and post blocks handle always, success and failure actions like notifications.

Agents: the agent directive says where work runs. The controller should only orchestrate; running builds on it is a security risk, because build code could read Jenkins secrets and configuration. Work runs on agents: static nodes, Docker containers or ephemeral Kubernetes pods created per build with the Kubernetes plugin, giving clean, isolated environments.

Credentials: secrets live in the Jenkins credentials store (or an external store such as Vault). withCredentials or credentials() in environment inject them into a block, and Jenkins masks them in logs.

Shared libraries hold reusable Groovy steps (for example standardBuild()) in a separate repo, versioned and loaded with @Library. Multibranch pipelines and organisation folders discover branches and pull requests automatically and build each one.

How it works

  1. Developer pushes; a webhook triggers the multibranch job.
  2. Jenkins reads the Jenkinsfile from that branch.
  3. The controller schedules stages on matching agents.
  4. Steps run; credentials are injected only where needed.
  5. Results, test reports and artifacts are recorded; post sends notifications.

Example

@Library('platform-lib@v2') _
pipeline {
  agent { kubernetes { yamlFile 'ci/pod.yaml' } }
  options { timeout(time: 30, unit: 'MINUTES') }
  stages {
    stage('Build') { steps { sh './mvnw -B package' } }
    stage('Test')  { steps { sh './mvnw -B verify' }
                     post { always { junit 'target/surefire-reports/*.xml' } } }
    stage('Push') {
      when { branch 'main' }
      steps {
        withCredentials([usernamePassword(credentialsId: 'registry',
                         usernameVariable: 'U', passwordVariable: 'P')]) {
          sh 'echo "$P" | docker login -u "$U" --password-stdin registry.example.com'
          sh 'docker push registry.example.com/app:${GIT_COMMIT}'
        }
      }
    }
  }
  post { failure { slackSend channel: '#builds', message: "Failed: ${env.JOB_NAME}" } }
}

Common mistakes

  • Running builds on the controller (executors > 0).
  • Hard-coding secrets or echoing them in scripts.
  • Huge scripted pipelines copied across repos instead of shared libraries.
  • Outdated plugins with known vulnerabilities.

How to answer in the interview

"A Jenkinsfile defines the pipeline as code in the repo, so it's versioned and reviewed. It can be declarative, the structured pipeline block I prefer, or scripted Groovy. It's split into stages like build, test and deploy, each with steps such as sh. The agent directive decides where it runs: the controller only orchestrates, and agents, often ephemeral Kubernetes pods, do the work. Secrets come from the credentials store through withCredentials and are masked. Shared libraries hold common logic, and multibranch pipelines build every branch and PR."

Likely follow-up questions

  • Risks of building on the controller? Build code can access Jenkins home, secrets and configuration, compromising everything.
  • How to make agents scalable? Kubernetes plugin with ephemeral pod agents.
  • How to manage Jenkins config? Configuration as Code (JCasC) and pinned plugin versions.
