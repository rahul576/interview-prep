You have a large REST API with 120 endpoints. How do you design an MCP server for it?

MCP Servers · design · levels mid, senior, lead

In one line

Don't map 120 endpoints to 120 tools: design a small, curated set of task-oriented tools around real workflows, each orchestrating several API calls, read-only first with few, explicit, approved writes, hiding pagination and internal ids, returning compact results, and iterating with evaluations on real tasks.

Detailed explanation

Auto-generating one tool per OpenAPI operation is tempting but produces a poor server:

  • Tool selection degrades. Models choose worse among dozens of similar tools (getCustomer, getCustomerById, searchCustomers, listCustomerAccounts).
  • Context cost. Every definition is sent on every request; 120 tools can consume tens of thousands of tokens before the user says anything.
  • Low-level chaining. Raw endpoints force the model to look up ids, paginate, join data and handle REST conventions, multiplying calls and failure points.
  • Risk. Write endpoints exposed by default (DELETE, PATCH) become one injected instruction away from misuse.

Instead, start from user and agent tasks. Interview stakeholders and look at support tickets or common questions: "find a customer", "summarise their open orders", "check shipment status", "create a return", "explain an invoice". Design one tool per task that combines API calls internally: get_customer_overview(email) might call the customer, accounts and orders endpoints and return a concise summary.

Read-only tools first, giving value safely. Writes are few, explicit (create_return(order_no, reason)), correctly annotated, idempotent and subject to host approval. Tools accept natural identifiers (email, order number), hide pagination and internal ids, and return only relevant fields with totals. They run with the calling user's permissions.

Then evaluate: write realistic tasks, run an agent against the server, and inspect transcripts. Where it picks the wrong tool, passes bad arguments or needs too many calls, adjust names, descriptions and boundaries. Expect a handful to a couple of dozen tools, not 120.

How it works

  1. Collect top tasks and questions from users and logs.
  2. Group endpoints behind task-level tools; define inputs with natural ids.
  3. Implement read-only tools; shape compact outputs.
  4. Add a few write tools with idempotency, annotations and approvals.
  5. Build an evaluation set; run, read transcripts, iterate.
  6. Monitor real usage and add tools only when tasks demand them.

Example

Instead of:  GET /customers, GET /customers/{id}, GET /customers/{id}/accounts,
             GET /accounts/{id}/orders?page=, GET /orders/{id}/shipments, ...

Expose:
  find_customer(email_or_phone)            -> id-free summary, top 3 matches
  get_customer_overview(email)             -> profile + open orders + balance (1 call, 4 APIs)
  get_order_status(order_no)               -> status, carrier, ETA, last event
  search_invoices(email, month)            -> compact list with totals
  create_return(order_no, reason, idempotency_key)   [destructive=false, needs approval]

Common mistakes

  • Generating tools straight from OpenAPI and shipping.
  • Exposing internal UUIDs the model must copy between calls.
  • Returning raw paginated payloads.
  • Including all write operations "for completeness".
  • No evaluation with a real model.

How to answer in the interview

"I wouldn't generate 120 tools. Models choose poorly among many similar tools, every definition costs context on every request, and raw endpoints force the model to chain calls and juggle ids and pagination. I'd start from the real tasks, like find a customer, summarise open orders, check shipment status or create a return, and design a small set of tools around them, each combining several API calls. Read-only tools first; a few explicit write tools with approval and idempotency. Tools take natural identifiers, hide pagination and return compact results. Then I'd evaluate with real tasks, read where the model fails, and iterate on names, descriptions and boundaries."

Likely follow-up questions

  • When is a generic call_api tool acceptable? For trusted power users in a sandbox, read-only, with an allowlist of endpoints.
  • How do you discover the right tasks? Support tickets, chat logs, stakeholder interviews and agent transcripts.
  • What about rarely used endpoints? Leave them out, or behind a separate server enabled only when needed.
