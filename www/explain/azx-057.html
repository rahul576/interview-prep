What is Microsoft Release Flow, and how does it compare with trunk-based development and GitFlow?

Azure DevOps & Pipelines · concept · levels mid, senior

In one line

Release Flow (Microsoft's model for Azure DevOps): short-lived topic branches merged to main via PRs, a release branch cut per sprint and never merged back, with fixes made in main first and cherry-picked to the release; trunk-based deploys from main continuously with feature flags; GitFlow uses a long-lived develop branch and more merging.

Detailed explanation

Release Flow is described by Microsoft for the Azure DevOps service itself:

  • Developers create topic branches (users/alex/fix-login, feature/x), keep them short-lived, and merge into main through pull requests with branch policies (build validation, reviewers). Main is always the latest integrated code.
  • At the end of each sprint, a release branch (releases/M180) is cut from main and deployed through rings (internal users, small region, then all).
  • Release branches are never merged back to main; when the next release branch is created, the old one is effectively retired.
  • Hotfixes: the fix is made and merged into main first, then cherry-picked to the active release branch. This "upstream first" rule means a fix can never be forgotten in the next release, which is a classic GitFlow problem.

Trunk-based development goes further: teams integrate into main at least daily and deploy from main continuously, often many times a day. Unfinished work is hidden behind feature flags; there are no long-lived release branches (optionally short release branches for stabilisation). It requires strong automated testing, fast pipelines and mature monitoring.

GitFlow has main (released), a long-lived develop, feature branches off develop, release branches merged into both main and develop, and hotfix branches off main merged back to both. It suits products with explicit versions and several supported releases (installed software, libraries), but creates more merging, delayed integration and merge conflicts, and is generally a poor fit for continuously deployed web services.

How it works

  1. Topic branch from main → PR → merge to main.
  2. Sprint end: git branch releases/M180 main.
  3. Release branch deployed through rings.
  4. Bug: fix in main via PR, cherry-pick to releases/M180.
  5. Next sprint: new release branch; old one retired.

Example

git switch -c users/priya/fix-timeout main
# ... PR into main, merged as commit 9f3e2a1
git switch releases/M180
git cherry-pick -x 9f3e2a1      # hotfix after upstream-first
git push origin releases/M180   # pipeline deploys hotfix through rings

Common mistakes

  • Fixing only in the release branch and forgetting main.
  • Calling long-lived feature branches "trunk-based".
  • Using GitFlow for a SaaS deployed daily.
  • Trunk-based without feature flags or good tests.

How to answer in the interview

"Release Flow is the model Microsoft uses for Azure DevOps. Developers work in short-lived topic branches merged into main by PR, so main always has the latest integrated code. Each sprint, a release branch is cut from main and deployed through rings, and it's never merged back. Fixes go to main first and are cherry-picked into the release branch, so they're never lost. Trunk-based development goes further, deploying from main continuously with feature flags hiding unfinished work. GitFlow adds a long-lived develop branch plus release and hotfix branches merged both ways, which suits versioned products but means more merging."

Likely follow-up questions

  • When is trunk-based risky? Weak tests, no feature flags, slow pipelines, or heavily regulated release approvals.
  • Why upstream first? Prevents regressions in the next release.
  • Cherry-pick tooling? Azure Repos can cherry-pick a completed PR into another branch from the UI.
