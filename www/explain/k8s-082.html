A compromised container was detected in a production pod. What do you do?

Kubernetes · scenario · levels senior, lead

In one line

Follow the incident process: contain without destroying evidence (deny-all NetworkPolicy, remove from Service, cordon the node), capture forensics, rotate every credential the pod could reach, find the entry point with runtime detection and audit logs, then rebuild from a clean, patched image and harden.

Detailed explanation

The instinct to delete the pod is wrong: it destroys the evidence you need to learn how the attacker got in and what they touched, and the controller simply recreates the same vulnerable pod. Involve the security team and incident commander early; legal or compliance may need to be informed if data could be exposed.

Containment: apply a NetworkPolicy selecting the pod (via a quarantine label) that denies all ingress and egress, so it can no longer exfiltrate or move laterally. Changing its labels so the Service and ReplicaSet no longer select it removes it from traffic and makes the controller start a replacement (ideally from a fixed image). Cordon the node so nothing new lands there, since a container escape may have compromised the node itself.

Evidence: kubectl get pod -o yaml, container logs, process list and open connections (kubectl debug with an ephemeral container or on the node with crictl), the container filesystem diff, a node disk snapshot and possibly memory capture, plus Kubernetes audit logs, cloud logs and runtime alerts. Record timestamps.

Assume breach of everything reachable: the pod's ServiceAccount token, its cloud workload identity permissions, mounted Secrets, environment variables, database credentials, API keys. Rotate them and review what they accessed in cloud and database audit logs.

Root cause: runtime detection (Falco, Tetragon, cloud threat detection such as GuardDuty or Defender for Containers) shows suspicious behaviour like a shell spawned in the container or unexpected outbound connections. Common entry points: a known vulnerable dependency, an exposed admin endpoint, leaked credentials, or a poisoned image.

Recovery and hardening: rebuild from a patched image, redeploy, drain and replace the node, then tighten securityContext, NetworkPolicies, RBAC and image policies, and hold a post-incident review.

How it works

  1. Declare incident; involve security.
  2. Quarantine label: deny-all NetworkPolicy, out of Service selection.
  3. Cordon node; capture pod, node and log evidence.
  4. Rotate credentials and review their use.
  5. Identify entry point; patch and rebuild.
  6. Replace node; delete pod after forensics.
  7. Harden and run a post-incident review.

Example

kubectl -n shop label pod api-6c9f quarantine=true app- --overwrite   # leaves Service/ReplicaSet
kubectl apply -f - <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: quarantine, namespace: shop }
spec:
  podSelector: { matchLabels: { quarantine: "true" } }
  policyTypes: [Ingress, Egress]
EOF
kubectl cordon node-14
kubectl -n shop logs api-6c9f --all-containers > evidence/api-6c9f.log

Common mistakes

  • Deleting the pod immediately.
  • Forgetting to rotate cloud identity and database credentials.
  • Restoring the same vulnerable image.
  • Leaving the node in service after a possible escape.

How to answer in the interview

"I'd follow the incident process and bring in security early. First contain without destroying evidence: a deny-all NetworkPolicy on the pod, relabel it out of its Service, and cordon the node, rather than deleting it. Then capture evidence: logs, processes, filesystem diff, a node disk snapshot and audit logs. I'd assume everything the pod could reach is exposed and rotate its service account token, cloud identity permissions, database passwords and mounted secrets. Falco alerts and audit logs help find the entry point, often a vulnerable image or exposed endpoint. Then rebuild from a patched image, replace the node, harden and write a post-incident review."

Likely follow-up questions

  • Controls that limit blast radius? Non-root, read-only filesystems, dropped capabilities, default-deny network policies, minimal RBAC, short-lived workload identity, signed images.
  • Why cordon the node? A container escape may have compromised the node.
  • Why keep the pod? Forensics need its state.
