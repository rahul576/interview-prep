How do you version and evolve the tools of an MCP server without breaking agents that use it?

MCP Servers · concept · levels mid, senior

In one line

Treat tool names, descriptions and schemas as a contract: prefer additive changes (new optional parameters, new tools, extra output fields), deprecate before removing or renaming, notify clients with list_changed, and run evaluations before releasing description changes, exposing the server version in server info.

Detailed explanation

An MCP server's tools are consumed by hosts (which may have allowlists or approvals per tool name), saved workflows and prompts that reference tools, agents' code that parses structured output, and models whose behaviour depends on every word of the description. Changes can break any of these, often silently.

Additive, backward-compatible changes are safe:

  • new optional parameters with sensible defaults;
  • new tools;
  • extra fields in structuredContent (if consumers ignore unknown fields);
  • clarifying descriptions, after evaluation.

Breaking changes include renaming or removing a tool, making a parameter required, changing a parameter's type or meaning, removing output fields, or changing semantics (e.g. amounts now in paise instead of rupees). Handle them like API versioning:

  1. Add the new tool (e.g. search_orders_v2 or a better name) alongside the old one.
  2. Mark the old one deprecated in its description ("Deprecated: use search_orders instead"), so models prefer the replacement, and log its usage.
  3. Remove it after a deprecation period once usage drops.

When the tool set changes at runtime, send notifications/tools/list_changed so connected clients refresh.

Because descriptions are effectively prompts, run the evaluation suite before releasing any change to names, descriptions or schemas, and compare tool-selection accuracy with the previous version. Expose the server version in serverInfo and logs so problems can be correlated with releases. Some hosts re-request approval when a tool's definition changes, which is a protection against "rug pull" attacks where a server changes behaviour after being approved, so changes should be deliberate and communicated in release notes.

How it works

  1. Classify each change as additive or breaking.
  2. Additive: release after contract review and evals.
  3. Breaking: add new tool, deprecate old, monitor usage, remove later.
  4. Send list_changed; bump server version (semver).
  5. Publish release notes for host administrators.

Example

[
  { "name": "search_orders",
    "description": "Search a customer's orders by email, status and date range. Returns up to 25.",
    "inputSchema": { "type": "object",
      "properties": { "email": {"type":"string"}, "status": {"type":"string","enum":["open","shipped","all"],"default":"open"},
                      "from": {"type":"string","format":"date"} },
      "required": ["email"] } },
  { "name": "find_orders",
    "description": "DEPRECATED: use search_orders instead. Kept until 2027-01-31.",
    "inputSchema": { "type": "object", "properties": { "email": {"type":"string"} }, "required": ["email"] } }
]

Common mistakes

  • Renaming tools for aesthetics and breaking allowlists.
  • Tweaking descriptions without evaluation.
  • Making an optional parameter required in a minor release.
  • Removing deprecated tools without checking usage.

How to answer in the interview

"Tool names, descriptions and schemas are a contract: hosts may allowlist tool names, workflows reference them, and even small description changes alter model behaviour. So I evolve them like APIs. Additive changes are preferred: new optional parameters with defaults, new tools, extra output fields. Renaming, removing or making a parameter required is breaking, so I keep the old tool for a deprecation period, mark it deprecated in its description pointing to the replacement, and remove it once usage drops. Clients get a list_changed notification. Every change goes through the evaluation suite first, and the server version is visible in server info."

Likely follow-up questions

  • Why might a host require re-approval on description change? To prevent rug-pull attacks where an approved tool silently changes behaviour.
  • Version in tool names? Only for real breaking changes; prefer stable names.
  • How to track usage of deprecated tools? Per-tool metrics and logs with client identity.
