What are Linux namespaces and cgroups, and how do containers use them?

Linux · concept · levels mid, senior

In one line

Namespaces isolate what a process can see (PIDs, network, mounts, hostname, IPC, users), cgroups limit and account what it can use (CPU, memory, I/O, PIDs), and a container is just a process with both applied, plus a root filesystem.

Detailed explanation

There is no "container" object in the Linux kernel. Runtimes such as runc (used by containerd and Docker) combine several kernel features to make an ordinary process look like a separate machine.

Namespaces give a process its own view of a resource. The pid namespace gives it its own process tree, so the app is PID 1. net gives it its own interfaces, IPs, routes and ports. mnt gives it its own mount table, so the image becomes its root filesystem. uts separates hostname, ipc separates shared memory and message queues, user maps container UIDs to different host UIDs (root inside, unprivileged outside), and cgroup and time namespaces exist too. In Kubernetes, containers in one pod share the net namespace, which is why they reach each other on localhost.

Control groups organise processes into a hierarchy and apply limits and accounting: CPU weight and quota, memory maximum, block I/O and the number of PIDs. cgroups v2 uses a single unified hierarchy with consistent interfaces (memory.max, cpu.max) and is now the default on current distributions; recent Kubernetes versions treat v1 as deprecated.

The effects show up in production. Exceeding memory.max triggers the OOM killer inside that cgroup, giving exit code 137 / OOMKilled. A CPU quota (cpu.max, from Kubernetes CPU limits) causes CFS throttling when the quota is used within a period, adding latency. Namespaces are isolation, not a strong security boundary, so seccomp, capabilities, AppArmor or SELinux, and user namespaces add defence.

How it works

  1. The runtime creates new namespaces for the process.
  2. It mounts the image layers as the root filesystem.
  3. It creates a cgroup and writes limits (memory.max, cpu.max).
  4. It starts the process inside the namespaces and cgroup.
  5. The kernel enforces limits: OOM kill or throttling.

Example

# Inspect a running container's namespaces and cgroup from the host
PID=$(docker inspect -f '{{.State.Pid}}' web)
ls -l /proc/$PID/ns
cat /proc/$PID/cgroup                     # 0::/system.slice/docker-<id>.scope
CG=/sys/fs/cgroup$(cut -d: -f3 /proc/$PID/cgroup)
cat $CG/memory.max $CG/cpu.max            # e.g. 536870912 and "50000 100000"
cat $CG/cpu.stat | grep throttled
sudo nsenter -t $PID -n ip addr           # run a host tool in its network namespace

Common mistakes

  • Thinking containers are lightweight VMs with their own kernel.
  • Treating namespaces alone as a strong security boundary.
  • Confusing memory limits (OOM kill) with CPU limits (throttling).
  • Running privileged containers that disable most isolation.

How to answer in the interview

"Namespaces isolate what a process can see: pid gives it its own process tree, net its own network stack, mnt its own filesystem view, plus uts for hostname, ipc, and user namespaces for UID mapping. cgroups limit and account the resources a group of processes can use, like CPU, memory, I/O and PIDs, and cgroups v2 with its unified hierarchy is now standard. A container is simply a process with its own namespaces and cgroup limits, plus an image as its root filesystem. Exceeding the memory limit triggers the OOM killer, and exceeding the CPU quota causes throttling."

Likely follow-up questions

  • How would you see a container's cgroup limits from the host? Read /proc/<pid>/cgroup and the matching files under /sys/fs/cgroup, such as memory.max and cpu.max.
  • What do containers in a pod share? The network and IPC namespaces, optionally the PID namespace.
  • What does gVisor or Kata add? A stronger boundary with a user-space or VM kernel.
