What happens when an exception occurs inside a transactional method?

Spring Boot · concept · levels senior, lead

In one line

By default Spring rolls back on unchecked exceptions and Errors and commits on checked exceptions; change it with rollbackFor/noRollbackFor, remember the exception must escape through the proxy, and watch for rollback-only marking in nested REQUIRED calls.

Detailed explanation

The transactional proxy decides commit or rollback by looking at how the method ended. If a RuntimeException or Error escapes, the default rule says rollback. If a checked exception escapes, the default rule says commit, which surprises many developers. The reasoning, inherited from EJB, is that checked exceptions often represent expected business outcomes that the caller can handle, while unchecked exceptions represent unexpected failures.

You override the rules with rollbackFor = Exception.class (or specific exception types) and noRollbackFor for exceptions that should not undo the work. Many teams standardise on rollbackFor = Exception.class or use only unchecked business exceptions.

The proxy only sees exceptions that propagate out of the method. If you catch and swallow an exception inside the method, Spring sees a normal return and commits whatever was already written, which can leave partial data. If you must catch it, either rethrow or call TransactionAspectSupport.currentTransactionStatus().setRollbackOnly().

The subtle case is nested REQUIRED calls. When an inner transactional method (a different bean, through its proxy) throws a runtime exception, its interceptor marks the shared transaction as rollback-only. Even if the outer method catches the exception and continues, the final commit attempt fails with UnexpectedRollbackException, because the transaction can no longer be committed.

How it works

  1. The method throws; the exception reaches the TransactionInterceptor.
  2. The interceptor checks rollback rules (rollbackFor, noRollbackFor, defaults).
  3. Matching rule: rollback (or mark rollback-only if this is a participating, not the outermost, transaction).
  4. Non-matching rule: commit and rethrow the exception to the caller.
  5. On the outermost commit, a rollback-only flag turns the commit into a rollback plus UnexpectedRollbackException.

Example

@Transactional(rollbackFor = Exception.class)
public void importFile(Path file) throws IOException {
    batchRepo.save(new Batch(file));
    parser.parse(file);          // IOException now rolls back too
}

@Transactional
public void placeOrder(Order o) {
    orderRepo.save(o);
    try {
        loyaltyService.addPoints(o);   // REQUIRED, throws RuntimeException
    } catch (RuntimeException e) {
        log.warn("points failed", e);  // still rollback-only -> UnexpectedRollbackException
    }
}

Common mistakes

  • Assuming checked exceptions roll back.
  • Catching and logging exceptions inside the transactional method, causing partial commits.
  • Catching an inner REQUIRED exception and being surprised by UnexpectedRollbackException.
  • Throwing from a self-invoked method and expecting its own rollback rules to apply.

How to answer in the interview

"By default Spring rolls back on RuntimeException and Error, but commits on checked exceptions, which I change with rollbackFor when needed. The exception has to escape the method through the proxy; if I catch and swallow it, Spring sees a normal return and commits. A tricky case is nested REQUIRED calls: if an inner transactional method throws, the shared transaction is marked rollback-only, so even if the outer method catches the exception, the commit fails with UnexpectedRollbackException. If the inner work should be independent, I make it REQUIRES_NEW."

Likely follow-up questions

  • Why no rollback on checked exceptions? EJB convention: checked exceptions are treated as recoverable business outcomes.
  • How to roll back without throwing? Call setRollbackOnly() on the current TransactionStatus.
  • How do you avoid UnexpectedRollbackException? Don't swallow inner failures, or use REQUIRES_NEW/noRollbackFor for optional steps.
