Does map() modify existing objects or create transformed values?

Java 8+ Features · concept · levels entry, mid

In one line

map produces new values and never changes the source collection, but if the mapper function calls setters on the elements and returns the same reference, it mutates the shared objects; keep mappers pure and prefer immutable objects or records.

Detailed explanation

A stream does not own its data; it reads from a source such as a list. map passes each element to your function and sends whatever the function returns downstream. The source list itself is never modified: it still has the same size and holds the same references after the pipeline runs.

Whether the objects referenced by the list change is a separate question, and it depends entirely on your function. Java passes references by value, so the mapper receives the same object the list holds. If the function builds a new object, for example p -> new Product(p.name(), p.price() * 0.85), the originals are untouched and you get a new list of discounted products. If instead it does p -> { p.setPrice(p.getPrice() * 0.85); return p; }, the result list contains the same objects, now mutated. Anyone else holding the original list, including a cache, sees the discounted prices too.

That kind of hidden side effect breaks the expectations of the stream API. The java.util.stream documentation asks for behavioural parameters to be non-interfering and preferably stateless and side-effect free. In a parallel stream, mutating shared objects can cause races if the same object appears twice or is shared with other threads. It also makes code harder to test and reason about.

The clean approach is functional: treat map as "compute a new value from the old one". Java records make this natural because they have no setters, and "wither" style methods (withPrice(...)) return copies. If you truly need to update objects in place, a plain loop or list.forEach(...) makes the intent explicit.

How it works

  1. The source list holds references to Product objects.
  2. map passes each reference to the mapper.
  3. A pure mapper creates and returns a new object; the original is unchanged.
  4. A mutating mapper changes the original object and returns the same reference.
  5. The collected list contains whatever references the mapper returned.

Example

record Product(String name, double price) {
    Product withPrice(double p) { return new Product(name, p); }
}

List<Product> catalogue = List.of(new Product("Lamp", 100), new Product("Desk", 400));

List<Product> sale = catalogue.stream()
    .map(p -> p.withPrice(p.price() * 0.85))   // new objects
    .toList();
// catalogue still has 100 and 400; sale has 85 and 340

// Mutating version with a mutable class (avoid):
List<MutableProduct> changed = mutableList.stream()
    .map(p -> { p.setPrice(p.getPrice() * 0.85); return p; })
    .toList();
// mutableList now also shows discounted prices

Common mistakes

  • Claiming "streams are immutable so nothing can change"; the objects can still be mutated.
  • Calling setters inside map and reusing the original list elsewhere.
  • Mutating objects in parallel streams without thinking about thread safety.
  • Using peek to modify elements.

How to answer in the interview

"map is designed to produce new values. Each element is passed to the function and whatever it returns flows downstream; the source collection is never changed. But Java passes references, so whether the original objects change depends on the function. If it creates a new object, like a record with a discounted price, the originals are untouched. If it calls a setter and returns the same reference, it mutates the shared objects, which is a side effect that surprises other callers and can race in a parallel stream. So I keep mappers pure, prefer records and immutable objects, and if I really need in-place updates I use a normal loop to make that explicit."

Likely follow-up questions

  • Why are side effects in map especially dangerous with parallel streams? Several threads may touch shared objects concurrently without synchronisation, giving races and non-deterministic results.
  • Does stream() copy the collection? No; it reads the source lazily, which is why modifying the source during the pipeline is interference.
  • How do records help? Their fields are final, so mappers must return new instances.
