A query on a 500 million row orders table takes 40 seconds. How would you investigate and fix it?

Data & Storage Design · scenario · levels entry, mid, senior

In one line

Start with EXPLAIN ANALYZE to see why the query is slow (usually a full scan or bad plan), then fix it with the right index (composite column order, covering), query rewrites, fresh statistics and, at this size, partitioning and archiving.

Detailed explanation

A 40-second query on 500M rows almost always reads far more rows than it returns. The execution plan tells you where time goes: sequential scans, nested loops over millions of rows, huge sorts spilling to disk.

B-tree indexes keep keys sorted, so equality and range lookups touch a few pages instead of the whole table. For composite indexes, column order matters (leftmost prefix rule): an index on (customer_id, created_at) serves WHERE customer_id = ? AND created_at > ? but not WHERE created_at > ? alone. A covering index (INCLUDE columns) lets the database answer from the index alone.

Indexes can be ignored when you wrap the column in a function (WHERE date(created_at) = …), compare mismatched types, use leading wildcards (LIKE '%abc'), or when statistics are stale.

How it works

  1. Capture the exact query and parameters (slow query log, pg_stat_statements).
  2. EXPLAIN (ANALYZE, BUFFERS) and read: scan types, row estimates vs actual, sort/hash spills.
  3. Add or fix an index matching filter + sort columns; create it concurrently on a live table.
  4. Rewrite the query (avoid functions on columns, select only needed columns, keyset pagination instead of OFFSET).
  5. ANALYZE to refresh statistics.
  6. Long term: partition by date and archive old rows.

Example

EXPLAIN ANALYZE SELECT id, total FROM orders
WHERE customer_id = 42 AND created_at >= now() - interval '90 days'
ORDER BY created_at DESC LIMIT 50;
-- Seq Scan on orders (rows=500M) ... 40s
CREATE INDEX CONCURRENTLY idx_orders_cust_created
  ON orders (customer_id, created_at DESC) INCLUDE (total);
-- Index Only Scan ... 3 ms

Common mistakes

  • Adding an index for every column (each slows every write).
  • Wrong column order in a composite index.
  • Creating an index without CONCURRENTLY and locking writes for minutes.
  • Using OFFSET 100000 pagination on huge tables.

How to answer in the interview

"I'd reproduce the query and run EXPLAIN ANALYZE. Most likely it's scanning the whole table. I'd add a composite index on the filter and sort columns, here customer and created date, maybe covering the selected columns, and build it concurrently. I'd also check for functions on indexed columns and stale statistics. For a 500-million-row table I'd partition by month and archive old data so it stays fast."

Likely follow-up questions

  • Why might the DB ignore an index? Low selectivity, functions on columns, type mismatch, stale stats.
  • Keyset vs OFFSET pagination? Keyset uses WHERE created_at < last_seen, constant cost.
  • Cost of indexes? Slower writes, more storage and memory.
