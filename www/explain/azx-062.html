How do you deploy to AKS from Azure Pipelines, and how does the KubernetesManifest task support canary deployments?

Azure DevOps & Pipelines · concept · levels mid, senior

In one line

Deploy to AKS from a deployment job that targets an environment with a Kubernetes resource, using the KubernetesManifest task to bake (Helm/Kustomize), substitute image tags and apply manifests; its canary strategy creates a canary and a same-sized baseline workload, which you later promote or reject.

Detailed explanation

The cleanest setup starts with an Azure DevOps environment that contains a Kubernetes resource pointing at the target cluster and namespace. The resource is backed by a service connection, ideally an Azure Resource Manager connection using workload identity federation, so no secrets are stored. Because the pipeline uses a deployment job that targets this environment, every run is recorded in the environment's deployment history, and approvals and checks configured on the environment apply automatically.

The KubernetesManifest@1 task has several actions. bake renders Helm charts, Kustomize overlays or Compose files into plain manifests; deploy applies them, replaces image references with the exact tag built earlier in the pipeline (the containers input) and waits for rollout status, failing the job if pods never become ready. createSecret, scale, patch and delete cover other operations.

With strategy: canary, the task does not touch the stable workload. It creates a <name>-canary deployment running the new image and a <name>-baseline deployment running the current image, both with the same small replica count. Comparing canary against baseline is fair: both are new pods, with the same warm-up, age and traffic share, whereas long-running production pods may differ in cache state or memory. Traffic is split either by pod ratio (trafficSplitMethod pod) or via a Service Mesh Interface TrafficSplit (smi). After analysis, the promote action rolls the new version out to the stable workload and removes the extra ones; reject deletes canary and baseline.

Many teams now prefer GitOps with Argo CD or Flux: the pipeline only updates an image tag in Git, and the in-cluster agent pulls the change. Progressive delivery then moves to tools such as Argo Rollouts or Flagger.

How it works

  1. Build and push the image to ACR, tagged with the build ID or commit SHA.
  2. A deployment job targets environment: aks-prod.shop, so approvals and history apply.
  3. bake renders the Helm chart; deploy with strategy: canary and percentage: 20 creates canary and baseline.
  4. A manual validation or automated check compares error rate and latency of canary vs baseline.
  5. On success promote updates the stable deployment; on failure reject removes the canary.

Example

jobs:
- deployment: DeployCanary
  environment: aks-prod.shop
  strategy:
    canary:
      increments: [20]
      deploy:
        steps:
        - task: KubernetesManifest@1
          inputs:
            action: deploy
            strategy: canary
            percentage: $(strategy.increment)
            manifests: k8s/deployment.yaml
            containers: myacr.azurecr.io/shop:$(Build.BuildId)
      on:
        success:
          steps:
          - task: KubernetesManifest@1
            inputs: { action: promote, strategy: canary, manifests: k8s/deployment.yaml }
        failure:
          steps:
          - task: KubernetesManifest@1
            inputs: { action: reject, strategy: canary, manifests: k8s/deployment.yaml }

Common mistakes

  • Using a plain job instead of a deployment job, losing environment history and approvals.
  • Comparing the canary with old production pods instead of the baseline.
  • Using :latest tags, so you cannot prove which image was deployed.
  • Promoting automatically without any real metric analysis in between.

How to answer in the interview

"I create an environment with a Kubernetes resource for the target namespace, backed by a workload identity service connection, and deploy from a deployment job so approvals and history apply. The KubernetesManifest task bakes the Helm chart, injects the image tag we just built and waits for rollout. For canaries it creates a canary and an equally sized baseline running the current version, so the comparison is fair. After checking metrics, I run promote or reject. For larger estates I'd often switch to GitOps with Argo CD and Argo Rollouts."

Likely follow-up questions

  • Why a baseline instead of existing production pods? Same age, size and warm-up, so differences come from the code, not the pods.
  • How is traffic split? By replica ratio behind the same Service, or by an SMI TrafficSplit with a service mesh.
  • What replaces this in GitOps? Argo Rollouts or Flagger performing analysis inside the cluster.
