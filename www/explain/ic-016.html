What are Ansible ad-hoc commands, and when would you use them?

Configuration Management · concept · levels entry

In one line

An ad-hoc command runs one Ansible module against hosts from the command line (ansible <pattern> -m <module> -a <args>); ideal for quick checks and one-off fixes, while anything repeatable belongs in a playbook.

Detailed explanation

The ansible command (as opposed to ansible-playbook) executes a single module against a host pattern from the inventory. The pattern can be a group (web), a host, all, or combinations such as web:&prod (intersection) or web:!canary (exclusion). -m selects the module, -a passes arguments, -i chooses the inventory, --become escalates privileges and -f sets the number of parallel forks. If you omit -m, Ansible uses the command module.

Typical uses: checking connectivity with ping (an Ansible module that verifies SSH login and Python, not ICMP), gathering facts with setup, checking disk space or uptime across a fleet, restarting a service during an incident, or copying one file. Because modules are still used, many ad-hoc commands are idempotent: service state=restarted always restarts, but package state=present installs only if missing.

The limits are about process, not technology. Ad-hoc commands leave no record in version control, are not peer-reviewed and are easy to mistype against the wrong group. During an incident they are perfect; for anything that should happen again, on new servers or in other environments, write a playbook. A good habit is to run with --check first where the module supports it, and to limit scope with --limit.

How it works

  1. Ansible reads the inventory and resolves the host pattern.
  2. It connects to each host over SSH (in parallel, 5 forks by default).
  3. It copies and runs the module with the arguments.
  4. Each host returns JSON; Ansible prints SUCCESS/CHANGED/FAILED per host.

Example

# Connectivity and Python check
ansible all -i inventory/prod -m ansible.builtin.ping

# Free disk space on all web servers
ansible web -i inventory/prod -m ansible.builtin.command -a "df -h /"

# Restart PostgreSQL with sudo on db hosts, 10 at a time
ansible db -i inventory/prod -m ansible.builtin.service \
  -a "name=postgresql state=restarted" --become -f 10

# Only production web servers, excluding canaries
ansible 'web:&prod:!canary' -m ansible.builtin.setup -a "filter=ansible_distribution*"

Common mistakes

  • Running destructive ad-hoc commands against all by accident.
  • Using shell when command or a dedicated module is enough.
  • Repeating the same ad-hoc fix weekly instead of writing a playbook.
  • Thinking the ping module sends ICMP pings.

How to answer in the interview

"An ad-hoc command runs a single Ansible module against a set of hosts straight from the command line, without a playbook. For example, ansible all -m ping checks SSH and Python on every host, ansible web -a 'df -h' checks disk space, and ansible db -m service -a 'name=postgresql state=restarted' --become restarts a service with sudo. The host pattern picks groups from the inventory. They're great for quick checks, gathering information or one-off fixes during an incident. But anything that should be repeatable or reviewed goes into a playbook in Git."

Likely follow-up questions

  • How would you check free disk space on all web servers with one command? ansible web -m command -a "df -h".
  • What's the difference between command and shell? shell runs through /bin/sh, allowing pipes and redirects; command doesn't, so it's safer.
  • How do you limit to a few hosts? --limit host1,host2 or a narrower pattern.
