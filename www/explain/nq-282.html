How do you test API integrations across multiple services?

Testing · scenario · levels mid

In one line

Combine consumer-driven contract tests (Pact or Spring Cloud Contract) to catch breaking API changes before deployment, integration tests with WireMock stubs derived from contracts or OpenAPI, schema compatibility checks for events, and a small end-to-end suite for critical journeys with controlled test data, correlation ids and tracing.

Detailed explanation

Multi-service testing must answer two questions: does each service work correctly with its dependencies' real interfaces, and does the whole journey work once deployed? Relying only on end-to-end tests answers both slowly and unreliably, so the work is split into layers.

Contract tests: the consumer (order service) writes tests against a Pact mock describing the requests it sends and the response fields it relies on. The resulting contract is published to a Pact Broker. The provider (inventory service) verifies all consumer contracts in its own CI against its real code, using provider states to set up data. can-i-deploy blocks a deployment that would break a consumer. Spring Cloud Contract works similarly but contracts are typically written on the provider side, producing generated tests and WireMock stubs consumers download.

Integration tests per service: each service tests its HTTP clients against WireMock stubs that come from those contracts or the provider's OpenAPI spec, so stubs stay realistic, and uses Testcontainers for its own data stores.

Events and schemas: for Kafka, contracts are message pacts or schemas in a schema registry (Avro, Protobuf, JSON Schema) with backward compatibility enforced, so producers cannot remove a field consumers need. OpenAPI diff tools can also flag breaking REST changes in pull requests.

End-to-end tests: a handful of critical journeys (register, place order, pay, ship) run across deployed services in a test environment. They need controlled test data (seeded accounts, synthetic customers, cleanup), correlation ids propagated through every call, and distributed tracing so a failure can be traced to the service and span that broke instead of debugging blind.

How it works

  1. Consumer tests generate contracts; publish to the broker.
  2. Provider CI verifies contracts; deployment gated by can-i-deploy.
  3. Services use contract-derived stubs in integration tests.
  4. Schema registry enforces event compatibility.
  5. After deployment, E2E journeys run with seeded data.
  6. Failures investigated via correlation ids and traces.

Example

# Spring Cloud Contract (provider side): contracts/shouldReturnStock.yml
request:
  method: GET
  url: /stock/SKU-1
response:
  status: 200
  headers:
    Content-Type: application/json
  body:
    sku: SKU-1
    available: 5
# Pact: gate deployment on verified contracts
pact-broker can-i-deploy --pacticipant order-service --version "$GIT_SHA" --to-environment production

Common mistakes

  • Only end-to-end tests, slow and flaky with unclear failures.
  • Hand-written stubs that drift from the provider.
  • Contracts published but not used to gate deployments.
  • E2E tests sharing mutable data and breaking each other.

How to answer in the interview

"I use layers. Consumer-driven contract tests with Pact or Spring Cloud Contract let each consumer publish the requests and responses it relies on, and the provider build verifies them, so breaking changes are caught before deployment. Within each service, integration tests use WireMock stubs generated from contracts or the OpenAPI spec, so they match reality. Event schemas are checked for backward compatibility in a schema registry. Then a small suite of end-to-end tests covers critical journeys like placing and paying for an order across deployed services, with controlled test data and correlation ids so failures can be traced through logs and distributed tracing."

Likely follow-up questions

  • Why contract tests over E2E alone? Faster, isolated, pinpoint which interface broke and run on every commit.
  • What are provider states? Named setups the provider prepares before verifying an interaction.
  • How do you manage E2E test data? Seeded synthetic accounts, unique ids per run and automated cleanup.
