How do you design checkpointing so long training jobs survive failures and spot interruptions?

MLOps · concept · levels mid, senior

In one line

A good checkpoint contains everything needed to resume exactly (weights, optimiser, scheduler, RNG and data position), is written to durable shared storage, is resumed automatically, uses sharded/async writes for large models, and is triggered on spot interruption notices.

Detailed explanation

Long jobs will fail: hardware faults, node preemption, out-of-memory spikes, network blips. On spot or preemptible capacity, interruptions are routine. Without proper checkpoints you lose days of compute.

Contents: model weights alone are not enough. Resuming needs the optimiser state (Adam moments), learning rate scheduler and step count, gradient scaler state for FP16, RNG states (Python, NumPy, torch, CUDA), and the data position: epoch, step and sampler or data loader state, so you don't repeat or skip data. Without the data position, a resumed run sees the beginning of the epoch again, biasing training.

Storage: write to object storage or a shared file system, never only to local disk that disappears with the node. Write to a temporary name and atomically rename or write a "complete" marker, so a crash mid-write doesn't leave a corrupt "latest" checkpoint.

Automatic resume: on start, the script looks for the latest valid checkpoint and continues. Combined with an orchestrator that restarts failed jobs (Kubernetes Job backoff, TorchElastic, managed training job retries), recovery needs no human.

Frequency: balance lost work against overhead; a rule of thumb is to checkpoint every 15-60 minutes, more often on spot. For large models, sharded checkpoints (each rank writes its shard, for example PyTorch Distributed Checkpoint) and asynchronous checkpointing (copy to CPU, write in background) keep pauses short.

Interruption notices: spot instances give a short warning (two minutes on AWS, about 30 seconds on Azure and GCP), so a signal handler triggers a final checkpoint if it can finish in time. Retention keeps the last few plus milestones.

How it works

  1. At start, find the newest checkpoint with a completion marker.
  2. Load model, optimiser, scheduler, scaler, RNG and sampler state.
  3. Every N steps or minutes, save asynchronously and in shards.
  4. Upload to object storage; write the marker last.
  5. On SIGTERM or an interruption notice, save a final checkpoint.
  6. Prune old checkpoints with a retention policy.

Example

def save(step):
    state = {"model": model.state_dict(), "optim": opt.state_dict(),
             "sched": sched.state_dict(), "scaler": scaler.state_dict(),
             "step": step, "sampler": sampler.state_dict(),
             "rng": {"torch": torch.get_rng_state(), "cuda": torch.cuda.get_rng_state_all()}}
    tmp = f"{CKPT}/step-{step}.tmp"; torch.save(state, tmp)
    os.replace(tmp, f"{CKPT}/step-{step}.pt")
signal.signal(signal.SIGTERM, lambda *_: (save(global_step), sys.exit(0)))

Common mistakes

  • Saving only weights, so the resumed run has a fresh optimiser and wrong learning rate.
  • Checkpoints on local ephemeral disk.
  • No atomic write, so the latest checkpoint is corrupted.
  • Never testing resume until a real failure.

How to answer in the interview

"A checkpoint must let you continue exactly, so it includes weights, optimiser, scheduler, scaler, RNG states and the data loader position, not just the model. I write it to object storage or a shared file system with an atomic rename. The script resumes automatically from the latest valid checkpoint, so a restart after a crash or spot reclaim needs nobody. Frequency balances lost work against overhead, and for large models I use sharded, asynchronous checkpoints. On spot I catch the interruption notice to save a final checkpoint, and old ones are pruned."

Likely follow-up questions

  • Why include the data loader position? Otherwise the resumed job repeats or skips data, changing the training distribution and breaking reproducibility.
  • How do you test it? Kill the job deliberately in CI or staging and check the loss curve continues smoothly.
  • How often should you checkpoint? Based on failure rate and checkpoint cost; more often on spot capacity.
