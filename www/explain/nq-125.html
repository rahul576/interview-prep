What are concurrent collections in Java? Give examples.

Collections · concept · levels mid

In one line

Concurrent collections in java.util.concurrent are designed for many threads with high throughput: ConcurrentHashMap, ConcurrentSkipListMap/Set, ConcurrentLinkedQueue/Deque, CopyOnWriteArrayList/Set and the BlockingQueue family; they use fine-grained or lock-free techniques and weakly consistent iterators, unlike synchronized wrappers.

Detailed explanation

The older approach, Vector, Hashtable and Collections.synchronizedList/Map, puts one lock around every method. It is correct for single calls but serialises all threads, still requires manual locking for iteration and compound actions, and throws ConcurrentModificationException if you forget.

The concurrent collections take different approaches depending on the access pattern:

  • ConcurrentHashMap: CAS for empty bins and per-bin locks, lock-free reads, and atomic operations (putIfAbsent, computeIfAbsent, merge). ConcurrentHashMap.newKeySet() gives a concurrent Set.
  • ConcurrentSkipListMap / ConcurrentSkipListSet: lock-free skip lists, sorted and navigable, O(log n). The concurrent equivalents of TreeMap and TreeSet.
  • ConcurrentLinkedQueue / ConcurrentLinkedDeque: lock-free non-blocking queues based on CAS (Michael-Scott algorithm for the queue). Note size() is O(n).
  • CopyOnWriteArrayList / CopyOnWriteArraySet: every write copies the whole array; readers and iterators work on an immutable snapshot without locking. Perfect for read-mostly lists such as event listeners, terrible for frequent writes.
  • BlockingQueue: ArrayBlockingQueue, LinkedBlockingQueue, PriorityBlockingQueue, DelayQueue, SynchronousQueue, LinkedTransferQueue, plus LinkedBlockingDeque. They add waiting put/take for producer-consumer and back-pressure.

All of them have weakly consistent (or snapshot) iterators that never throw ConcurrentModificationException. A thread-safe collection does not make your sequence of calls atomic, so you still use the provided atomic methods for check-then-act logic.

How it works

  1. Identify the shape: map, sorted map, queue, read-mostly list.
  2. Pick the matching concurrent implementation.
  3. Use atomic compound methods instead of separate calls.
  4. Iterate freely; accept weakly consistent views.

Example

ConcurrentMap<String, Integer> counts = new ConcurrentHashMap<>();
counts.merge(word, 1, Integer::sum);

NavigableMap<Instant, Trade> trades = new ConcurrentSkipListMap<>();
trades.headMap(Instant.now().minusSeconds(60)).clear();   // drop old trades

List<Listener> listeners = new CopyOnWriteArrayList<>();
listeners.forEach(l -> l.onEvent(evt));

BlockingQueue<Job> jobs = new LinkedBlockingQueue<>(10_000);
jobs.put(job);

Common mistakes

  • CopyOnWriteArrayList for write-heavy data.
  • Calling size() on ConcurrentLinkedQueue in a hot loop.
  • Assuming individual thread-safe calls compose atomically.
  • Using synchronized wrappers in new code.

How to answer in the interview

"Concurrent collections in java.util.concurrent are built for many threads with high throughput, unlike the synchronized wrappers that lock the whole collection. ConcurrentHashMap gives fine-grained locking and atomic methods like computeIfAbsent; ConcurrentSkipListMap and Set are sorted and concurrent; ConcurrentLinkedQueue and Deque are lock-free; CopyOnWriteArrayList copies on each write and is ideal for read-mostly lists like listeners; and the BlockingQueue implementations support producer-consumer. Their iterators are weakly consistent and never throw ConcurrentModificationException."

Likely follow-up questions

  • Why is CopyOnWriteArrayList bad for writes? Each write copies the entire array: O(n) time and garbage.
  • Concurrent TreeMap? ConcurrentSkipListMap.
  • Concurrent Set? ConcurrentHashMap.newKeySet().
