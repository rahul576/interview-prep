How do you measure test quality beyond code coverage?

Testing · concept · levels senior, lead

In one line

Coverage shows which lines ran, not whether behaviour was verified; measure test quality with mutation testing (PIT), escaped defects, flakiness, suite speed and review of tests in pull requests.

Detailed explanation

Line or branch coverage from JaCoCo is a useful negative signal: uncovered code is definitely untested. But high coverage proves little. A test that calls a method and asserts nothing yields 100% coverage. Teams that turn coverage into a target get tests written for the number.

Mutation testing measures whether tests would catch bugs. PIT (pitest) creates many small changes ("mutants") to the bytecode: flipping > to >=, negating conditions, replacing return values with null or zero, removing method calls. It runs the tests against each mutant. If a test fails, the mutant is killed; if all pass, it survived, revealing an untested behaviour. The mutation score (killed ÷ total) is a far better indicator of test strength. Surviving mutants also point to the exact line where an assertion is missing. Because it is CPU-heavy, run it incrementally on changed code in pull requests (PIT's history files and Git integration help) and fully on a nightly build.

Outcome metrics matter most: escaped defects (bugs found in production or by QA after merge), especially which test level should have caught them; change failure rate from DORA metrics.

Health metrics: flaky test rate, because flaky tests train people to ignore red builds; suite duration, since slow suites are run less often; the ratio of unit to integration tests.

Human review: tests are reviewed like production code: clear names, meaningful assertions, one behaviour per test, no logic copied from the implementation.

How it works

  1. Collect coverage with JaCoCo to find untested areas.
  2. Run PIT on critical modules; inspect surviving mutants.
  3. Add missing assertions or cases until important mutants are killed.
  4. Track escaped defects and add a test at the right level for each.
  5. Monitor and quarantine flaky tests; fix them quickly.
  6. Review test code in every pull request.

Example

<plugin>
  <groupId>org.pitest</groupId>
  <artifactId>pitest-maven</artifactId>
  <configuration>
    <targetClasses><param>com.shop.pricing.*</param></targetClasses>
    <mutationThreshold>75</mutationThreshold>
    <withHistory>true</withHistory>
  </configuration>
  <dependencies>
    <dependency>
      <groupId>org.pitest</groupId>
      <artifactId>pitest-junit5-plugin</artifactId>
    </dependency>
  </dependencies>
</plugin>
>> Line 42: changed conditional boundary  -> SURVIVED

Common mistakes

  • Treating an 80% coverage gate as proof of quality.
  • Running full mutation testing on every commit and making CI unbearably slow.
  • Ignoring flaky tests or retrying them silently.
  • Not linking production bugs back to missing tests.

How to answer in the interview

"Coverage only tells me which lines were executed; a test with no assertions can reach 100%. So I treat it as a hint about gaps, not a quality measure. For test strength I use mutation testing with PIT: it injects small bugs like flipped conditions and checks that a test fails; surviving mutants show exactly where assertions are missing. I run it on changed code in pull requests and fully at night. I also track escaped defects, flaky test rate and suite speed, because slow or flaky suites get ignored, and I review tests in pull requests as carefully as production code."

Likely follow-up questions

  • How to introduce PIT in a large codebase? Start with critical modules, run incrementally on changed classes, set thresholds gradually.
  • What is an equivalent mutant? A mutation that does not change behaviour, so no test can kill it.
  • How do you handle flaky tests? Quarantine with an owner and deadline, find the root cause (timing, shared state, order).
