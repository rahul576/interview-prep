How does the JVM locate and load a class?

JVM & Performance · concept · levels mid, senior

In one line

On a class's first active use, the requesting loader delegates up the hierarchy, the responsible loader finds com/acme/Order.class on its path and defines it, then the JVM links and initialises it; failures surface as ClassNotFoundException or NoClassDefFoundError.

Detailed explanation

The JVM loads classes lazily. Loading is triggered by active use: new, invoking a static method, reading or writing a non-constant static field, initialising a subclass, Class.forName, reflection or MethodHandle lookups. Merely declaring a variable of a type does not load it immediately.

The loader of the calling class handles the request and uses parent delegation. The loader that is responsible converts the binary name into a resource path (com.acme.Order becomes com/acme/Order.class) and searches its sources. For the Application loader that is the module path (modules are located by package) and the classpath, in order of entries: directories and JARs. It reads the bytes and calls defineClass, creating the Class object and storing metadata in Metaspace. Superclasses and interfaces are loaded as part of this.

Linking then verifies the bytecode, prepares static fields with default values, and resolves symbolic references, usually lazily when first executed. Initialisation runs <clinit>, the static initialisers and static field assignments in source order, once, under a lock so other threads wait.

Two errors are commonly confused. ClassNotFoundException is a checked exception thrown when code loads a class by name (Class.forName, loadClass) and it cannot be found. NoClassDefFoundError is an Error thrown when a class that was present at compile time is missing at runtime, or when its static initialiser previously failed (the first failure shows as ExceptionInInitializerError).

How it works

  1. First active use triggers loading.
  2. Delegation: Application → Platform → Bootstrap.
  3. The responsible loader finds .class bytes and calls defineClass.
  4. Verify, prepare, resolve.
  5. Run static initialisers (initialisation).
  6. On failure: ClassNotFoundException, NoClassDefFoundError, ExceptionInInitializerError or UnsupportedClassVersionError.

Example

class Config {
    static final Map<String,String> VALUES = load();   // runs at initialisation
    static { System.out.println("Config initialised"); }
}

Class<?> c = Class.forName("com.acme.Config", false, loader); // loaded, not initialised
String v = Config.VALUES.get("url");                          // triggers initialisation
java -Xlog:class+load=info -cp app.jar:libs/* com.acme.Main | grep acme
# [0.412s][info][class,load] com.acme.Order source: file:/opt/app/app.jar

Common mistakes

  • Thinking classes load at startup or on import.
  • Treating the two errors as the same thing.
  • Ignoring the earlier ExceptionInInitializerError that explains a later NoClassDefFoundError.
  • Not checking for duplicate or conflicting JAR versions with -Xlog:class+load.

How to answer in the interview

"Loading happens lazily on first active use, like new, a static method call or reflection. The calling class's loader delegates up to Bootstrap; the loader that can handle it turns the name into a path such as com/acme/Order.class, searches its JARs and directories, and defines a Class object in Metaspace. The JVM then links it, verifying bytecode, preparing statics and resolving references, and initialises it by running static initialisers. If loading by name fails I get ClassNotFoundException; if a class present at compile time is missing at runtime, or its static init failed, I get NoClassDefFoundError."

Likely follow-up questions

  • ClassNotFoundException vs NoClassDefFoundError? Name-based lookup failure versus a compile-time class missing at runtime or failed initialisation.
  • How do you see which JAR a class came from? -Xlog:class+load or Order.class.getProtectionDomain().getCodeSource().
  • Does referencing a static final constant trigger loading? Compile-time constants are inlined, so no.
