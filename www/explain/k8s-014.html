What are ResourceQuota and LimitRange, and how do they work together?

Kubernetes · concept · levels entry, mid

In one line

A ResourceQuota caps the total a namespace may consume (CPU and memory requests/limits, object counts, storage); a LimitRange sets per-container or per-pod defaults and min/max. They work together because once a quota covers CPU or memory, pods without those values are rejected, and LimitRange defaults fill them in.

Detailed explanation

In a shared cluster, one team's runaway deployment or forgotten load test can claim every node. These two objects provide fairness at different levels.

ResourceQuota is an aggregate limit evaluated at admission time. It can cap:

  • compute: requests.cpu, requests.memory, limits.cpu, limits.memory, plus extended resources such as requests.nvidia.com/gpu;
  • object counts: pods, services, services.loadbalancers, secrets, configmaps, persistentvolumeclaims, or count/deployments.apps;
  • storage: requests.storage in total or per StorageClass (gold.storageclass.storage.k8s.io/requests.storage).

Quotas can also be scoped, for example by PriorityClass or to BestEffort pods. kubectl describe quota shows used versus hard values.

LimitRange works at the level of individual containers, pods or PVCs in a namespace: defaultRequest and default (default limit) are injected into containers that don't specify them; min and max reject outliers; maxLimitRequestRatio stops tiny requests with huge limits.

The interaction matters: when a quota includes requests.cpu, the API server must know every new pod's CPU request to account for it, so a pod without one is rejected with forbidden: failed quota: must specify requests.cpu. A LimitRange with defaults makes that seamless. Another subtlety: quota rejections hit the pod creation by the ReplicaSet controller, not your kubectl apply of the Deployment, so the Deployment is accepted but stays short of replicas, with the error visible only in ReplicaSet events.

How it works

  1. Platform team creates namespace with ResourceQuota and LimitRange.
  2. Developer applies a Deployment; it is accepted.
  3. ReplicaSet creates pods; LimitRange admission fills defaults and checks min/max.
  4. Quota admission adds the pod's requests to usage; rejects if over the hard limit.
  5. Deleted pods release quota.

Example

apiVersion: v1
kind: ResourceQuota
metadata: { name: team-quota, namespace: search }
spec:
  hard:
    requests.cpu: "20"
    requests.memory: 64Gi
    limits.memory: 96Gi
    pods: "100"
    services.loadbalancers: "1"
---
apiVersion: v1
kind: LimitRange
metadata: { name: defaults, namespace: search }
spec:
  limits:
  - type: Container
    defaultRequest: { cpu: 100m, memory: 128Mi }
    default: { memory: 512Mi }
    max: { cpu: "4", memory: 8Gi }
kubectl describe quota team-quota -n search
kubectl describe rs -n search | grep -i "exceeded quota"

Common mistakes

  • Adding a compute quota without a LimitRange, breaking every deployment missing requests.
  • Looking for quota errors on the Deployment instead of the ReplicaSet events.
  • Defaults so high that the quota fills with few pods.
  • Quota on limits only, while scheduling uses requests.

How to answer in the interview

"A ResourceQuota caps the total a namespace can use: sums of CPU and memory requests and limits, object counts like pods or LoadBalancer Services, and storage per StorageClass. A LimitRange works per container: it injects default requests and limits and enforces min and max. They go together because once a quota covers CPU or memory, every pod must declare those values or it's rejected, and LimitRange defaults prevent that. In multi-tenant clusters that gives fairness and stops one team consuming every node."

Likely follow-up questions

  • Deployment stuck at 3 of 10 replicas with no pod errors? Check ReplicaSet events for quota rejections and kubectl describe quota.
  • Does quota affect running pods? No, only new admissions; lowering it doesn't evict anything.
  • Quota for GPUs? Use requests.nvidia.com/gpu in the hard list.
