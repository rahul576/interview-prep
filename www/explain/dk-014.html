What is the difference between a bind mount and a named volume?

Docker · concept · levels entry

In one line

A bind mount maps a specific host path into the container (great for local development and config files, but tied to the host's layout and permissions); a named volume is storage managed by Docker, independent of host paths, portable and best for persistent data like databases; tmpfs keeps temporary data in memory.

Detailed explanation

Data written to a container's writable layer disappears with the container, so anything that matters lives in a mount.

Bind mounts (-v /host/path:/container/path or --mount type=bind,src=…,dst=…):

  • Expose an existing host file or directory directly; changes on either side are visible immediately.
  • Perfect for live code reload (mount ./src into a dev container), mounting a single config file (nginx.conf:ro), or sharing build output.
  • Downsides: depend on the host's directory structure (not portable across machines), inherit host ownership and permissions (often UID mismatches with non-root containers), and can expose sensitive host paths. Mounting /var/run/docker.sock gives root-equivalent control of the host.
  • -v silently creates a missing host directory; --mount errors instead, which is safer.

Named volumes (-v pgdata:/var/lib/postgresql/data, docker volume create pgdata):

  • Docker manages the storage (under /var/lib/docker/volumes by default, or a volume driver such as NFS or cloud storage).
  • Independent of the host's layout, easy to list, inspect, back up and migrate; better performance on Desktop.
  • A new, empty volume is pre-populated with the image's content at that path on first use.
  • The right choice for databases and persistent application data.

tmpfs (--tmpfs /tmp or --mount type=tmpfs) lives in memory only, never touches disk and vanishes when the container stops; useful for scratch files, sockets or sensitive temporary data, and with read-only root filesystems.

Data in bind mounts and volumes survives container removal.

How it works

  1. Mount declared at docker run or in Compose.
  2. Runtime mounts host path / volume / tmpfs into the container's mount namespace.
  3. App reads and writes there; data outlives the container (except tmpfs).
  4. Volumes are managed with docker volume commands.

Example

# Dev: live-reload source, read-only config
docker run -d -v "$(pwd)/src:/app/src" -v "$(pwd)/nginx.conf:/etc/nginx/nginx.conf:ro" web-dev
# Prod-like: named volume for database data, tmpfs for scratch
docker run -d --name db -v pgdata:/var/lib/postgresql/data --tmpfs /tmp:size=64m \
  -e POSTGRES_PASSWORD=secret postgres:17
# Back up a named volume
docker run --rm -v pgdata:/data:ro -v "$(pwd)":/backup alpine \
  tar czf /backup/pgdata-$(date +%F).tgz -C /data .

Common mistakes

  • Bind-mounting database data on Docker Desktop and suffering slow I/O.
  • Permission errors from UID mismatches with bind mounts.
  • Mounting the Docker socket into untrusted containers.

How to answer in the interview

"A bind mount maps a specific host path into the container, like -v $(pwd)/src:/app/src, so changes are visible immediately on both sides. It's ideal for local development with live reload or mounting a config file, but it depends on the host's directory layout and permissions. A named volume, like -v pgdata:/var/lib/postgresql/data, is storage managed by Docker, independent of the host layout, easy to back up and the right choice for persistent data like databases. Both survive container removal. A tmpfs mount keeps temporary data in memory only."

Likely follow-up questions

  • How to back up a named volume? Run a temporary container mounting it and tar the contents to a bind-mounted folder.
  • Where are volumes stored? By default under /var/lib/docker/volumes/<name>/_data, or via a volume driver.
  • Why is mounting docker.sock dangerous? It grants full control of the Docker daemon, effectively root on the host.
