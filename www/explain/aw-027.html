What is the difference between vertical and horizontal scaling in AWS?

Cloud (AWS) · concept · levels entry

In one line

Vertical scaling (scale up) means a bigger instance type: simple, but it has a ceiling, usually needs a restart and remains a single point of failure; horizontal scaling (scale out) means more instances behind a load balancer: near-unlimited and highly available, but the app must be stateless, with Auto Scaling groups automating it.

Detailed explanation

Vertical scaling changes the instance size, for example from m7g.large (2 vCPU, 8 GiB) to m7g.2xlarge (8 vCPU, 32 GiB). It needs no code changes and suits workloads that are hard to distribute, such as a single relational database primary or legacy applications. Its downsides: an EC2 instance must be stopped to change type (EBS-backed), so there is downtime unless you fail over; the largest instance types are a hard limit; cost grows steeply; and one big server is still one failure domain.

Horizontal scaling adds instances and distributes requests with an Elastic Load Balancer. Capacity grows almost linearly, instances can span multiple Availability Zones for resilience, and you can scale back in when traffic falls, paying only for what you need. The requirement is that any instance can serve any request, so the application must be stateless: user sessions go to ElastiCache or DynamoDB (or signed tokens), uploads go to S3, and shared state lives in databases rather than local disk.

Auto Scaling groups automate horizontal scaling: target tracking policies (keep average CPU at 50% or requests per target at 1,000), step policies, scheduled actions for known peaks and predictive scaling from historical patterns. Health checks replace failed instances automatically. Containers on ECS/EKS and serverless services apply the same scale-out principle.

In practice you combine them: right-size instance types vertically, then scale horizontally. Databases scale reads horizontally with read replicas, and writes vertically or through sharding or services like Aurora and DynamoDB.

How it works

  1. Monitor utilisation and latency.
  2. Vertical: stop, change instance type, start (or fail over to a resized replica).
  3. Horizontal: launch template plus Auto Scaling group across AZs.
  4. ALB distributes traffic; health checks remove bad instances.
  5. Scaling policies add or remove instances automatically.

Example

# Vertical
aws ec2 stop-instances --instance-ids i-0123
aws ec2 modify-instance-attribute --instance-id i-0123 --instance-type '{"Value":"m7g.2xlarge"}'
aws ec2 start-instances --instance-ids i-0123

# Horizontal: target tracking on an ASG
aws autoscaling put-scaling-policy --auto-scaling-group-name web-asg \
  --policy-name cpu50 --policy-type TargetTrackingScaling \
  --target-tracking-configuration '{"PredefinedMetricSpecification":
    {"PredefinedMetricType":"ASGAverageCPUUtilization"},"TargetValue":50}'

Common mistakes

  • Scaling out an app that stores sessions in memory, causing random logouts.
  • Only scaling up until hitting the largest instance.
  • Scale-in policies that are too aggressive, causing flapping.
  • Ignoring the database, which becomes the bottleneck.

How to answer in the interview

"Vertical scaling, scaling up, means moving to a bigger instance type. It's simple and needs no code changes, but there's a ceiling, it usually needs a stop and start, and one big server is still a single point of failure. Horizontal scaling, scaling out, means adding instances behind a load balancer. It grows almost without limit and gives better availability across AZs, but the app has to be stateless, with sessions in ElastiCache or DynamoDB and files in S3. Auto Scaling groups automate it with target tracking policies. In practice I right-size vertically and scale out horizontally."

Likely follow-up questions

  • How do you scale a relational database at its limit? Read replicas, caching, a bigger instance, then Aurora, partitioning or sharding.
  • What is target tracking? A policy that adjusts capacity to keep a metric at a target value.
  • Why use multiple AZs? Survive an AZ failure and spread load.
