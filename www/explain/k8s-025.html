You need to upgrade a production cluster two minor versions. How do you plan and run it?

Kubernetes · scenario · levels mid, senior, lead

In one line

Upgrade one minor version at a time (1.33 → 1.34 → 1.35), control plane first, then nodes, respecting version skew rules; beforehand, check removed APIs (pluto, kubent, apiserver_requested_deprecated_apis), add-on compatibility (CNI, CoreDNS, ingress/gateway, operators), rehearse in staging, and roll nodes with surge or blue-green pools that respect PDBs.

Detailed explanation

Kubernetes does not support skipping minor versions on the control plane, because storage migrations and API changes are designed for adjacent versions. A two-version jump is therefore two full upgrade cycles, each with its own checks.

Preparation is most of the work:

  • Release notes and deprecation guide for both target versions: removed APIs, changed defaults, feature gates graduating or being removed.
  • Removed API usage: scan Git manifests and Helm charts with pluto or kubent, and check live calls with the API server metric apiserver_requested_deprecated_apis and audit logs, which also catch operators and scripts.
  • Add-ons: each has a supported Kubernetes range: CNI, CoreDNS, CSI drivers, gateway controllers, cert-manager, mesh, Karpenter or Cluster Autoscaler, and every operator.
  • Version skew policy: API servers in an HA control plane may differ by at most one minor version; kubelets must not be newer than the API server and may be up to three minors older; kubectl within one minor.
  • Rehearsal in a staging cluster with the same add-ons and representative workloads, plus a backup (etcd snapshot or managed equivalent, Velero).

Execution per hop: upgrade the control plane (managed: one click or Terraform change; kubeadm: kubeadm upgrade apply on the first node, then others), then add-ons as required, then node pools. For nodes, either surge upgrades (add new-version nodes, drain old ones) or a blue-green node pool: create a new pool, cordon the old one, drain gradually, watch error rates and latency. PDBs limit disruption, so check beforehand that none allows zero disruptions.

Rollback: control plane downgrades are generally not supported, so the safety net is preparation, staging and the ability to keep old node pools until validation passes.

How it works

  1. Inventory: versions, add-ons, deprecated API usage.
  2. Fix manifests and charts; upgrade incompatible add-ons.
  3. Rehearse both hops in staging.
  4. Back up; upgrade control plane to N+1.
  5. Upgrade add-ons, then node pools with PDB-aware draining.
  6. Validate; repeat for N+2.

Example

pluto detect-helm -o wide --target-versions k8s=v1.35.0
pluto detect-files -d ./manifests --target-versions k8s=v1.35.0
kubectl get --raw /metrics | grep apiserver_requested_deprecated_apis
kubectl get pdb -A -o json | jq -r '.items[] | select(.status.disruptionsAllowed==0) | .metadata.namespace+"/"+.metadata.name'
# kubeadm control plane
kubeadm upgrade plan
kubeadm upgrade apply v1.34.2

Common mistakes

  • Trying to jump two minors at once.
  • Upgrading the cluster before the autoscaler, CNI or operators support it.
  • Fixing live objects but not the Helm charts and Git sources.
  • Blocking PDBs discovered halfway through the node rollout.

How to answer in the interview

"Kubernetes upgrades go one minor version at a time, so 1.33 to 1.35 is two full upgrades: control plane first, then add-ons, then nodes, within the skew policy where kubelets are never newer than the API server. Beforehand I read the release notes, find removed APIs with pluto or kubent and the deprecated-APIs metric, and check every add-on's compatibility: CNI, CoreDNS, gateway controllers, cert-manager, autoscaler and operators. I rehearse in staging, take a backup, then roll nodes with surge or a blue-green pool, respecting PDBs and watching error rates. Control plane rollback isn't really possible, so validation happens before production."

Likely follow-up questions

  • Helm release fails after upgrade due to a removed API? Use the helm mapkubeapis plugin to rewrite the stored release, then fix the chart.
  • Blue-green node pool vs in-place? Blue-green allows instant fallback to the old pool while it exists.
  • How long between hops? Long enough to validate, usually days, not minutes.
