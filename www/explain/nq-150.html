What is the Strategy pattern, and how can it support different payment methods?

Design Patterns · scenario · levels mid

In one line

Strategy puts a family of interchangeable algorithms behind a common interface so the context can choose one at runtime; for payments, CardPayment, UpiPayment and PayPalPayment implement PaymentStrategy, replacing an if/else chain and following open/closed.

Detailed explanation

A payment service without Strategy tends to look like if (method == CARD) {...} else if (method == UPI) {...} else if ..., with validation, gateway calls and error handling for every method mixed in one class. Each new method edits that class and risks breaking the others.

With Strategy:

  • Strategy interface: PaymentStrategy with pay(Order) and, often, supports(PaymentMethod) or method().
  • Concrete strategies: each class owns everything specific to its method: card tokenisation and 3-D Secure, UPI collect requests, PayPal redirects.
  • Context: PaymentService selects the strategy based on the customer's choice and calls pay; it contains no method-specific logic.

Spring wiring: make each strategy a @Component. Spring can inject a Map<String, PaymentStrategy> keyed by bean name, or a List<PaymentStrategy> that you index into an EnumMap by method() at startup, which also lets you fail fast if two strategies claim the same method or one is missing.

Benefits: adding wallet payments means adding one class; each strategy is unit-testable in isolation; feature flags or A/B tests can swap strategies; and the context class stays small. For tiny algorithms, a strategy can just be a lambda (Comparator is the JDK's classic Strategy).

Strategy vs State: structurally similar, but in Strategy the client chooses the algorithm and strategies are usually independent; in State, the object's internal state chooses the behaviour and states trigger transitions to each other.

How it works

  1. Define PaymentStrategy with method() and pay(Order).
  2. Implement one class per payment method.
  3. Register all strategies (Spring bean discovery).
  4. Context builds a lookup map at startup.
  5. On request, look up by method and call pay; unknown methods fail clearly.

Example

public enum PaymentMethod { CARD, UPI, PAYPAL }

public interface PaymentStrategy {
    PaymentMethod method();
    PaymentResult pay(Order order);
}

@Component class CardPayment implements PaymentStrategy {
    public PaymentMethod method() { return PaymentMethod.CARD; }
    public PaymentResult pay(Order o) { /* tokenise, 3DS, charge */ return PaymentResult.ok(); }
}
@Component class UpiPayment implements PaymentStrategy {
    public PaymentMethod method() { return PaymentMethod.UPI; }
    public PaymentResult pay(Order o) { /* UPI collect request */ return PaymentResult.pending(); }
}

@Service
public class PaymentService {
    private final Map<PaymentMethod, PaymentStrategy> strategies = new EnumMap<>(PaymentMethod.class);
    public PaymentService(List<PaymentStrategy> all) {
        all.forEach(s -> { if (strategies.put(s.method(), s) != null) throw new IllegalStateException("Duplicate " + s.method()); });
    }
    public PaymentResult pay(Order o) {
        var s = strategies.get(o.paymentMethod());
        if (s == null) throw new UnsupportedPaymentMethodException(o.paymentMethod());
        return s.pay(o);
    }
}

Common mistakes

  • Moving the if/else into a factory instead of removing it.
  • Strategies sharing mutable state (singleton beans must be stateless).
  • Keying the map by bean name strings that silently break on renames.
  • Creating a strategy hierarchy for something that never varies.

How to answer in the interview

"Strategy defines a family of algorithms, puts each behind a common interface and makes them interchangeable at runtime. For payments I'd have a PaymentStrategy interface with CardPayment, UpiPayment and PayPalPayment, each owning its validation and gateway calls. PaymentService, the context, picks the strategy from the customer's choice and calls pay, with no growing if/else. In Spring each strategy is a bean; I inject the list and build an EnumMap keyed by payment method, failing fast on duplicates. Adding wallet payments is one new class, and each strategy is easy to unit test."

Likely follow-up questions

  • How does Strategy differ from State? The client picks a strategy; in State the object's current state determines behaviour and drives transitions.
  • How would you test it? Unit test each strategy alone, and test the context with mock strategies.
  • Can a lambda be a strategy? Yes, for single-method interfaces like Comparator or Function.
