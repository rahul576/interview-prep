What is the difference between a message queue and an event stream, and when do you use each?

Distributed Systems · concept · levels entry, mid, senior

In one line

A message queue distributes work items to competing consumers and deletes them after acknowledgement; an event stream is a durable, replayable log read independently by many consumer groups. Use queues for tasks, streams for events and replay.

Detailed explanation

Queues (RabbitMQ, SQS, Azure Service Bus, ActiveMQ): a message goes to one consumer; per-message ack, visibility timeout (redelivered if not acked), dead-letter queue after N failures, priorities, delayed messages, routing (RabbitMQ exchanges). Ideal for jobs: send email, resize image, process payment refund.

Streams (Kafka, Kinesis, Event Hubs, Pulsar, Redis Streams): messages appended to partitioned logs and kept for a retention period; each consumer group tracks its own offset. Multiple services read the same events (billing, analytics, search indexing) without the producer knowing. Ordering per partition key, replay from any offset, very high throughput.

Error handling differs: in a stream, a consumer processes a partition in order, so a failing message blocks the partition unless you move it to a retry topic / DLQ topic and continue.

How it works

  • Queue: producer → queue → consumer A or B → ack → deleted; failures → DLQ.
  • Stream: producer → topic partitions → consumer group billing (offset 120) and analytics (offset 98) independently; data retained 7 days.

Example

OrderPlaced → Kafka topic "orders" → billing, search-indexer, analytics, loyalty (4 groups)
"generate-invoice-pdf" tasks → SQS queue → 20 competing workers → DLQ after 5 attempts

Common mistakes

  • Using a queue when several services need the same event (copy explosion).
  • Using Kafka for simple task distribution with heavy per-message retry logic.
  • Blocking a partition on a poison message.

How to answer in the interview

"A queue hands each task to one worker and removes it after ack, with visibility timeouts and dead-letter queues, so it's ideal for background jobs. A stream is a durable log where many consumer groups independently read and replay the same events, with ordering per key, so it's ideal for domain events and data pipelines. Many systems use both: Kafka for events and SQS or RabbitMQ for task work."

Likely follow-up questions

  • Poison message in Kafka? Catch, publish to retry/DLQ topic with metadata, commit offset, continue.
  • FIFO guarantees in SQS? FIFO queues with message group IDs.
  • Competing consumers on a stream? Consumer group members split partitions.
