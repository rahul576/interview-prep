Explain the JPA entity lifecycle states and the persistence context.

Spring Data & JPA · concept · levels entry, mid

In one line

JPA entities move through transient (new), managed, detached and removed states; the persistence context is a per-transaction first-level cache and unit of work that guarantees identity and uses dirty checking to flush changes, while persist makes a new entity managed and merge copies a detached entity's state into a managed one.

Detailed explanation

Transient / new: an object created with new Order() is plain Java. JPA doesn't know about it; it has no row in the database (and usually no id).

Managed: after persist(), or when loaded through find(), a query or a lazy association, the entity is managed, meaning it lives in the persistence context. The persistence context is a map from (entity type, id) to instance, scoped by default to the transaction in Spring. It guarantees identity: loading the same id twice in one transaction returns the same instance without a second query. It also acts as a unit of work: Hibernate keeps a snapshot of each managed entity's loaded state and, at flush (before commit, before queries that might be affected, or on explicit flush()), performs dirty checking, comparing current fields with the snapshot and issuing UPDATEs for changed ones. That is why you don't need to call save() for a managed entity you modified.

Detached: when the persistence context closes (transaction ends) or you call detach()/clear(), entities become detached. They still hold data and an id, but changes are no longer tracked and lazy associations can't be loaded.

Removed: remove() marks a managed entity for deletion; the DELETE executes at flush.

persist vs merge: persist(entity) makes a new instance managed (the same object). merge(detached) finds or loads the managed instance with that id, copies the detached state onto it and returns the managed copy; the argument stays detached. Spring Data's save() calls persist if the entity is new (null id or version) and merge otherwise, which is why assigning ids manually can trigger an extra SELECT.

How it works

  1. new Order() → transient.
  2. em.persist(order) or repo.save(order) → managed; INSERT at flush (or immediately with IDENTITY ids).
  3. Modify fields of managed entity → dirty checking → UPDATE at flush.
  4. Transaction commits → context closes → detached.
  5. em.merge(detached) → managed copy; em.remove(managed) → removed → DELETE at flush.

Example

@Transactional
public void renameCustomer(long id, String name) {
    Customer c = em.find(Customer.class, id);   // managed, SELECT
    Customer same = em.find(Customer.class, id);// same instance, no SELECT
    c.setName(name);                            // no save() needed
}                                               // flush: UPDATE customer set name=? ...

@Transactional
public Customer update(Customer detachedFromClient) {
    Customer managed = em.merge(detachedFromClient);   // copies state
    return managed;                                    // use the returned instance
}

Common mistakes

  • Calling save() on already-managed entities, believing it is required.
  • Continuing to modify the argument passed to merge() instead of its return value.
  • Loading 100,000 entities into one persistence context, exhausting memory and slowing flushes.
  • Expecting changes to detached entities to be saved automatically.

How to answer in the interview

"A new entity created with new is transient. After persist, or when loaded, it is managed: it lives in the persistence context, a first-level cache keyed by id within the transaction, which guarantees one instance per row. Hibernate does dirty checking on managed entities and flushes changed fields as SQL at commit, so I don't need to call save. When the context closes the entity becomes detached; merge copies its state back into a managed instance and returns it. remove marks it removed, and it's deleted on flush."

Likely follow-up questions

  • Why does saving 100,000 entities in a loop cause memory problems? All stay managed with snapshots; flush and clear in batches.
  • When does flush happen? Before commit, before conflicting queries (AUTO), or on flush().
  • persist on an entity with an id? Detached entity passed to persist throws an exception.
