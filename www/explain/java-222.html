How does the ForkJoinPool work, and what is work stealing?

Concurrency · concept · levels mid, senior

In one line

ForkJoinPool runs divide-and-conquer tasks (RecursiveTask/RecursiveAction) that fork subtasks and join results; each worker has its own deque, and idle workers steal tasks from the opposite end of other workers' deques. The common pool backs parallel streams and CompletableFuture async methods, so blocking tasks there starve the JVM.

Detailed explanation

Fork/Join targets recursive, CPU-bound problems: split a big task into halves until pieces are small enough, compute them directly, and combine the results, like parallel merge sort or summing a huge array.

A RecursiveTask<V> (returns a value) or RecursiveAction (no value) implements compute(). Inside, it checks a threshold; if the work is small, it computes sequentially; otherwise it creates subtasks, calls fork() on one (pushing it to the current worker's deque), computes the other directly, and calls join() to get the forked result. A worker waiting in join runs other pending tasks meanwhile.

Work stealing. Each worker thread owns a double-ended queue. It pushes and pops its own tasks at one end (LIFO, good cache locality, and the newest tasks are the smallest). When a worker runs out of work, it becomes a thief and takes tasks from the other end of a random victim's deque (FIFO), which are usually the largest pending pieces, so a single steal brings lots of work. Owners and thieves mostly touch different ends, so contention is low and all cores stay busy without a central queue.

Common pool. ForkJoinPool.commonPool() is a JVM-wide static pool with parallelism of available processors minus one by default. It is used by parallel streams and by CompletableFuture.*Async methods without an executor. Because it is shared and small, blocking I/O or long locks in it starve every other user: one slow HTTP call in supplyAsync can stall parallel streams elsewhere. Use a dedicated executor (or virtual threads) for blocking work, or wrap unavoidable blocking in ForkJoinPool.managedBlock (ManagedBlocker) so the pool can compensate with extra threads.

How it works

  1. Submit root task to the pool.
  2. compute() splits until below threshold.
  3. fork() pushes a subtask on the worker's deque.
  4. Idle workers steal from the far end of other deques.
  5. join() waits (helping with other tasks) and combines results.

Example

class SumTask extends RecursiveTask<Long> {
    private static final int THRESHOLD = 10_000;
    private final long[] a; private final int lo, hi;
    SumTask(long[] a, int lo, int hi) { this.a = a; this.lo = lo; this.hi = hi; }

    @Override protected Long compute() {
        if (hi - lo <= THRESHOLD) {
            long s = 0; for (int i = lo; i < hi; i++) s += a[i]; return s;
        }
        int mid = (lo + hi) >>> 1;
        SumTask left = new SumTask(a, lo, mid);
        left.fork();                                   // run asynchronously
        long right = new SumTask(a, mid, hi).compute(); // compute in this thread
        return right + left.join();
    }
}
long total = ForkJoinPool.commonPool().invoke(new SumTask(data, 0, data.length));

Common mistakes

  • Blocking I/O in the common pool via parallel streams or supplyAsync.
  • Thresholds too small, so task overhead dominates.
  • Calling join() before fork()ing the other half, losing parallelism.

How to answer in the interview

"ForkJoinPool is designed for divide and conquer: a RecursiveTask splits work into subtasks with fork and combines results with join. Each worker thread has its own deque; it works LIFO on its own end, and idle workers steal from the other end of other workers' deques, which keeps all cores busy with little contention. The common pool is shared by parallel streams and CompletableFuture async methods by default, sized to cores minus one, so blocking tasks in it can starve the whole application. For blocking work I use a separate executor or a ManagedBlocker."

Likely follow-up questions

  • Why can a parallel stream in a web request hurt throughput? Every request competes for the same small common pool and the request threads already provide parallelism.
  • RecursiveTask vs RecursiveAction? One returns a result, the other doesn't.
  • Can you run a parallel stream in a custom pool? Submitting it from a custom ForkJoinPool works in practice but is an implementation detail.
