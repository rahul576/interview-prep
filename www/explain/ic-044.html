How do you manage multiple regions or accounts in one Terraform configuration?

Infrastructure as Code · concept · levels mid

In one line

Declare the provider several times with aliases (one per region or account, using assume_role for other accounts), select them with provider = aws.alias, pass them to modules via the providers map with configuration_aliases, and keep blast radius small with separate states per account.

Detailed explanation

A provider block configures how Terraform talks to an API: region, credentials, default tags. A configuration can contain multiple configurations of the same provider by giving extra ones an alias. The block without an alias is the default, used by every resource that doesn't say otherwise.

Multiple regions: a common case is CloudFront, which only accepts ACM certificates from us-east-1, while the rest of the stack lives in eu-west-1. Add provider "aws" { alias = "us_east_1" region = "us-east-1" } and set provider = aws.us_east_1 on the certificate. Similar needs arise for disaster-recovery replicas, cross-region S3 replication or global services.

Multiple accounts: each aliased provider uses an assume_role block with a role ARN in the target account, starting from the pipeline's base credentials (ideally OIDC). Typical uses: creating a DNS delegation in a central networking account, a VPC peering accepter, or log destinations in a security account.

Modules do not inherit aliased providers automatically. The caller passes them explicitly: providers = { aws = aws, aws.dns = aws.network_account }. Inside the module, required_providers declares configuration_aliases = [aws.dns] so Terraform knows the module expects that additional configuration.

While this works, managing many accounts from one state concentrates risk: one apply can affect many accounts, plans get slow, and the pipeline needs permissions everywhere. The usual pattern is one state and pipeline per account/environment, with cross-account providers used only for genuinely cross-cutting resources like DNS delegations or peering. Account vending and baselines at scale often use tools such as AWS Control Tower/Account Factory for Terraform or a loop of pipelines.

How it works

  1. Define default and aliased provider configurations.
  2. Each aliased provider authenticates (assume_role for other accounts).
  3. Resources pick a provider with the provider meta-argument.
  4. Modules receive providers through the providers map.
  5. Terraform routes each API call through the selected configuration.

Example

provider "aws" {
  region = "eu-west-1"
}

provider "aws" {
  alias  = "us_east_1"
  region = "us-east-1"
}

provider "aws" {
  alias  = "network"
  region = "eu-west-1"
  assume_role {
    role_arn = "arn:aws:iam::444455556666:role/terraform-dns"
  }
}

resource "aws_acm_certificate" "cdn" {
  provider          = aws.us_east_1
  domain_name       = "www.example.com"
  validation_method = "DNS"
}

module "app_dns" {
  source    = "./modules/app-dns"
  providers = {
    aws     = aws
    aws.dns = aws.network
  }
}
# modules/app-dns/versions.tf
terraform {
  required_providers {
    aws = {
      source                = "hashicorp/aws"
      configuration_aliases = [aws.dns]
    }
  }
}

Common mistakes

  • Forgetting provider = on a resource, so it silently goes to the default region.
  • Configuring providers inside reusable modules instead of passing them.
  • Managing dozens of accounts in one state.
  • Removing an aliased provider while resources in state still use it (destroy them first).

How to answer in the interview

"I declare the provider several times with aliases, for example the default AWS provider in eu-west-1 and one aliased us_east_1, which I need for ACM certificates used by CloudFront. For other accounts, each aliased provider has an assume_role block with a role in that account. Resources choose with provider = aws.us_east_1, and modules get them explicitly through the providers map, declaring configuration_aliases inside the module. It works, but many accounts in one state means a big blast radius and slow plans, so usually each account or environment gets its own state and pipeline."

Likely follow-up questions

  • Why must the ACM certificate for CloudFront be in us-east-1? CloudFront is a global service whose control plane reads certificates only from us-east-1.
  • Can you loop providers with for_each? Recent OpenTofu supports for_each on providers; in Terraform you declare each alias explicitly.
  • How do you remove an aliased provider safely? Destroy or move its resources first, then delete the block.
