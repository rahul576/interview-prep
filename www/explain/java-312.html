Explain JPA relationship mapping: owning side, mappedBy, cascade and orphanRemoval.

Spring Data & JPA · concept · levels mid, senior

In one line

In a bidirectional relationship the owning side holds the foreign key (usually @ManyToOne) and is the only side JPA writes; the inverse side uses mappedBy; cascade propagates operations like persist/remove from parent to children; orphanRemoval deletes children removed from the collection; keep both sides in sync with helper methods.

Detailed explanation

Owning side. Relational databases have one foreign key per relationship, but objects can reference each other in both directions. JPA resolves this by declaring one side the owner: the side whose table contains the foreign key column, normally the @ManyToOne (order_line.order_id). Only changes to the owning side's field are written to the database. If you add a line to order.getLines() but don't set line.setOrder(order), nothing is persisted for the relationship.

mappedBy. The inverse side (@OneToMany(mappedBy = "order")) points to the owning field and is ignored for writes. Without mappedBy, a @OneToMany becomes a unidirectional association with a join table, or with @JoinColumn extra UPDATE statements, usually not what you want. For @OneToOne and @ManyToMany you also choose the owner explicitly.

Cascade. cascade = CascadeType.PERSIST, MERGE, REMOVE, REFRESH, DETACH or ALL propagates entity operations from parent to children, so persisting an order persists its lines. It suits composition, where children have no life of their own (order and order lines, invoice and items). It is wrong for shared or independent entities: cascading REMOVE from OrderLine to Product, or from Order to Customer, would delete data used elsewhere.

orphanRemoval. With orphanRemoval = true, a child removed from the parent's collection (or replaced in a one-to-one) is deleted at flush. Cascade REMOVE deletes children when the parent is removed; orphanRemoval also deletes them when they are detached from the parent.

Sync helpers. Because the in-memory object graph must stay consistent within the persistence context, write addLine/removeLine methods that update both sides, and don't expose the raw mutable collection.

How it works

  1. Owning side @ManyToOne @JoinColumn(name = "order_id") defines the FK.
  2. Inverse side @OneToMany(mappedBy = "order") mirrors it.
  3. Helper methods set both sides.
  4. On flush, Hibernate writes the FK from the owning side.
  5. Cascade and orphanRemoval decide child INSERTs and DELETEs.

Example

@Entity
class Order {
    @Id @GeneratedValue Long id;

    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<OrderLine> lines = new ArrayList<>();

    public void addLine(OrderLine line) { lines.add(line); line.setOrder(this); }
    public void removeLine(OrderLine line) { lines.remove(line); line.setOrder(null); }
}

@Entity
class OrderLine {
    @Id @GeneratedValue Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "order_id")
    private Order order;                     // owning side

    @ManyToOne(fetch = FetchType.LAZY)       // no cascade: products are shared
    private Product product;
}

Common mistakes

  • Setting only the inverse side and wondering why the FK is null.
  • CascadeType.ALL on @ManyToOne, deleting shared parents.
  • Forgetting mappedBy, creating an unintended join table.
  • Replacing the collection instance with orphanRemoval (Hibernate error); modify it instead.

How to answer in the interview

"In a bidirectional relationship, the owning side is the entity whose table holds the foreign key, usually the ManyToOne side, and only changes there are persisted. The inverse side declares mappedBy pointing to the owning field. Cascade propagates operations like persist and remove from parent to children, which suits true composition like an order and its lines, but not shared entities. orphanRemoval deletes a child when it's removed from the parent's collection. I keep both sides in sync with helper methods like addLine and removeLine."

Likely follow-up questions

  • Why is CascadeType.ALL on @ManyToOne a bug? Removing a child would delete the shared parent.
  • orphanRemoval vs cascade REMOVE? orphanRemoval also deletes children removed from the collection.
  • Unidirectional @OneToMany? Creates a join table or extra updates; prefer bidirectional or @ManyToOne only.
