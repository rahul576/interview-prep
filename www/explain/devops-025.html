What is the difference between a ConfigMap and a Secret, and how do you manage secrets securely?

Kubernetes · concept · levels mid

In one line

ConfigMaps hold non-sensitive configuration; Secrets hold sensitive data but are only base64-encoded by default, so secure them with etcd encryption at rest (KMS), tight RBAC, mounting as files rather than env vars, keeping them out of Git, and preferably an external secret manager synced by External Secrets Operator or the Secrets Store CSI driver (or Sealed Secrets for GitOps).

Detailed explanation

Both objects inject configuration into pods as environment variables or mounted files, and both are stored in etcd. The difference is intent and handling: Secrets are treated a little more carefully, but base64 is encoding, not encryption. Anyone with get on Secrets in a namespace, anyone who can create pods there (they can mount the secret), and anyone with etcd or backup access can read them.

Hardening Secrets in the cluster.

  • Encryption at rest for Secrets in etcd, ideally with a KMS provider (envelope encryption with a cloud KMS key). Managed services offer this as a setting.
  • RBAC: very few subjects get get/list/watch on Secrets; list reveals all values.
  • Mount as files rather than environment variables: env vars leak via crash dumps, /proc, child processes and debug output, and they do not update when the Secret changes. Mounted volumes (without subPath) are refreshed by the kubelet.

Keep the source of truth outside. Store secrets in HashiCorp Vault, AWS Secrets Manager, Azure Key Vault or GCP Secret Manager. The External Secrets Operator syncs them into Kubernetes Secrets on an interval; the Secrets Store CSI driver mounts them directly into pods. Pods authenticate with workload identity (IRSA or EKS Pod Identity, Azure Workload Identity, GKE Workload Identity), so there are no static cloud keys. When secrets must live in Git for GitOps, Sealed Secrets or SOPS encrypt them so only the cluster (or KMS) can decrypt.

How it works

  1. Secret stored in AWS Secrets Manager, rotated there.
  2. ExternalSecret resource references it; ESO uses a workload identity role to read it.
  3. ESO creates and refreshes a Kubernetes Secret.
  4. Pod mounts the Secret as a file; app reloads on change.
  5. etcd encryption and RBAC protect the in-cluster copy.

Example

apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata: { name: db-credentials, namespace: shop }
spec:
  refreshInterval: 1h
  secretStoreRef: { name: aws-secrets, kind: ClusterSecretStore }
  target: { name: db-credentials }
  data:
    - secretKey: password
      remoteRef: { key: prod/shop/db, property: password }

Common mistakes

  • Committing base64 Secret manifests to Git, believing they are encrypted.
  • Granting list secrets widely.
  • Using env vars and expecting rotated values to appear.

How to answer in the interview

"A ConfigMap holds non-sensitive configuration like URLs or feature settings. A Secret is meant for passwords and tokens, but by default it's only base64 encoded, so anyone who can read it via the API, create pods in the namespace or access etcd can decode it. So I enable encryption at rest with a KMS provider, restrict RBAC tightly, mount secrets as files instead of env vars, and keep them out of Git. I prefer an external manager like Vault or AWS Secrets Manager, synced with the External Secrets Operator or mounted with the CSI driver using workload identity, or Sealed Secrets when they must live in Git."

Likely follow-up questions

  • How do you rotate a DB password without downtime? Two valid credentials during rotation, update the secret, let mounted files refresh or roll the pods, then revoke the old one.
  • Why not env vars? They don't update and leak more easily.
  • Who can read a Secret without RBAC on Secrets? Anyone who can create a pod that mounts it in that namespace.
