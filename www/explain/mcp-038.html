How do you avoid tool name collisions and confusion when a host connects to many MCP servers?

MCP Servers · concept · levels mid, senior

In one line

Different servers can expose the same tool names (search, create_issue), so hosts namespace tools by server (e.g. github__create_issue), server authors pick specific, descriptive names naming their system, and teams limit which servers and tools are enabled per task, using tool filtering and tool search to reduce confusion.

Detailed explanation

Tool names are only unique within one server. A host connected to GitHub, Jira and Linear servers may see three tools called create_issue and several called search. The protocol does not prevent this.

Host namespacing. Hosts resolve collisions by prefixing tool names with the server name (or a configured alias) when presenting them to the model, such as github__create_issue and jira__create_issue, and routing calls back to the right client. Exact formats differ per host, and some providers restrict tool-name characters and length, so long server names may be shortened. Teams should choose short, clear server aliases in configuration.

Server-author responsibility. Even with prefixes, ambiguous names and descriptions hurt. Prefer specific names (search_jira_issues, create_jira_issue) and descriptions that state which system they act on and when to use them versus similar tools ("Use for Jira tickets in the PAY and OPS projects; for GitHub issues use the GitHub server").

Too many similar tools. Unique names do not solve semantic confusion: with five search tools across servers, the model may pick the wrong one, or call several. Mitigations:

  • Limit enabled servers per agent or task: a release-notes agent needs GitHub and Jira, not Slack and the database.
  • Tool filtering in host configuration: enable only the tools a role needs (many hosts allow per-server tool allow/deny lists).
  • Tool search / deferred loading: keep most tool definitions out of context and let the model search for relevant ones on demand.
  • Separate agents or profiles for different jobs.

A further security angle: a malicious server could deliberately register a tool named like a trusted one (tool shadowing) to intercept calls, so hosts should show the server of origin and policies should allowlist servers.

How it works

  1. Host collects tool lists from all clients.
  2. Applies per-server filters and allowlists.
  3. Prefixes names with server aliases; maps them back on calls.
  4. Optionally defers loading and exposes a tool search capability.
  5. Shows the server of origin in approval prompts.

Example

{
  "servers": {
    "gh":   { "url": "https://mcp.github.example/mcp", "tools": { "allow": ["search_issues", "create_issue", "get_pull_request"] } },
    "jira": { "url": "https://mcp.jira.example/mcp",   "tools": { "allow": ["search_jira_issues", "create_jira_issue"] } }
  }
}

Model sees gh__create_issue and jira__create_jira_issue. (Filter syntax illustrative; varies by host.)

Common mistakes

  • Generic tool names like search or run in servers.
  • Enabling every available server for every agent.
  • Descriptions that don't say which system the tool touches.
  • Ignoring tool shadowing from untrusted servers.

How to answer in the interview

"Two servers can both expose search or create_issue, say GitHub and Jira, and the protocol doesn't prevent it. Hosts handle it by namespacing tools by server, typically prefixing the server name, so github__create_issue and jira__create_issue are distinct. As a server author I choose specific names and descriptions that say which system they act on, like search_jira_issues. But even unique names don't stop the model picking the wrong one among many similar tools, so I limit which servers and tools are enabled per agent or task, use tool filtering in the host config, and rely on tool search or deferred loading so only relevant tools are in context."

Likely follow-up questions

  • Default servers for an internal coding agent? Source control, issue tracker, docs search and CI, read-only by default; others opt-in per task.
  • What is tool shadowing? A server registering confusingly similar tools to hijack calls meant for a trusted server.
  • Do prefixes cost tokens? Slightly; clarity is worth it.
