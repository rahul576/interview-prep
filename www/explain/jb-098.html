What is the difference between synchronized methods and synchronized blocks?

Concurrency · concept · levels mid, senior

In one line

A synchronized method locks this (or the Class object for static methods) for the whole method; a synchronized block locks an object you choose for only the statements inside, which keeps critical sections small and lets you use a private lock.

Detailed explanation

Both use the same mechanism, the object's intrinsic monitor, and give the same atomicity, reentrancy and visibility guarantees. The difference is scope and which lock.

public synchronized void add() is equivalent to wrapping the whole body in synchronized (this) { ... }. A static synchronized method is equivalent to synchronized (MyClass.class). Note that instance and static synchronized methods use different locks, so they do not exclude each other.

A synchronized block lets you choose the scope: do validation, logging, computation or I/O outside, and lock only the few lines that touch shared state. Shorter critical sections mean less contention and better throughput.

It also lets you choose the lock object. Locking on this exposes your lock publicly: any outside code holding a reference can do synchronized (yourObject) and block you or create a deadlock. A private final Object lock = new Object() is invisible to outsiders. You can also use separate locks for independent state (lock striping), for example one for a cache and one for statistics, so they do not block each other.

Synchronized methods are still fine for small classes where the whole method is the critical section; they are more readable. One subtle point: the synchronized method modifier is not part of the method's contract and is not inherited by overrides.

How it works

  1. Method form: the JVM marks the method with ACC_SYNCHRONIZED and acquires the monitor of this/Class on entry.
  2. Block form: the compiler emits monitorenter/monitorexit around the block, on the given object.
  3. Other threads on the same monitor wait as BLOCKED.
  4. The monitor is released on normal exit and on exceptions.
  5. Release publishes writes to the next thread that acquires the same monitor.

Example

public class Inventory {
    private final Object stockLock = new Object();   // private: outsiders cannot use it
    private final Map<String, Integer> stock = new HashMap<>();

    // Whole method locked on 'this'
    public synchronized int total() {
        return stock.values().stream().mapToInt(Integer::intValue).sum();
    }

    public void reserve(String sku, int qty) {
        validate(sku, qty);                  // outside the lock
        int remaining;
        synchronized (stockLock) {           // only the shared-state update
            remaining = stock.merge(sku, -qty, Integer::sum);
        }
        auditClient.send(sku, remaining);    // slow I/O outside the lock
    }
}

(In real code total() and reserve() must use the same lock if they guard the same map.)

Common mistakes

  • Guarding the same data with this in one place and a private lock in another.
  • Synchronising on a String literal or boxed Integer, which may be shared JVM-wide.
  • Synchronising on a field that gets reassigned, so threads lock different objects.
  • Doing I/O inside the critical section.

How to answer in the interview

"A synchronized instance method locks on this for the whole method, and a static synchronized method locks on the Class object. A synchronized block locks on an object I choose and only for the statements inside. I usually prefer blocks: I keep the critical section small, doing slow work like I/O outside the lock, and I can use a private final lock object so outside code cannot lock the same object and interfere or deadlock with me. I can also use separate locks for independent state. The visibility and atomicity guarantees are otherwise the same."

Likely follow-up questions

  • What can go wrong if you synchronize on a String literal or a boxed Integer? Literals are interned and small Integers cached, so unrelated code may share the same lock, causing contention or deadlocks.
  • Do a static and an instance synchronized method block each other? No; they use different monitors.
  • Is synchronized inherited by overriding methods? No; the override must declare it again if needed.
