Should Terraform deploy application code, such as Lambda or Function App packages, or only the infrastructure?

Terraform · concept · levels mid, senior

In one line

Usually Terraform should manage the infrastructure and its configuration (function app, plan, identity, networking, settings) while the application pipeline deploys the code, because the two have different change rates, owners and release mechanics.

Detailed explanation

Application code changes many times a day and needs fast deployments with slots, canaries, traffic shifting and quick rollbacks. Infrastructure changes rarely and needs careful plans and reviews. When Terraform deploys the zip or container image too, every code release becomes an infrastructure run: slower, gated by the same approvals, and the plan mixes a harmless code change with a risky network change, making review harder.

There is also an ownership problem. The platform or infrastructure team may own the Terraform repository, while product teams own the code. Coupling them forces product teams to wait for infrastructure pipelines, or gives them write access to infrastructure they should not touch.

The common pattern is: Terraform creates the Lambda function or Function App with a placeholder package or initial image, and uses lifecycle { ignore_changes = [...] } on the attribute that holds the code or image version. The app pipeline then publishes new versions with az functionapp deployment, aws lambda update-function-code, a container image tag, or a tool like the Serverless Framework or SAM. Terraform no longer sees those updates as drift.

There are sensible exceptions: small, infrastructure-like functions — a log forwarder, a custom resource handler, a scheduled tagging job — that change rarely and belong to the platform team can live with the Terraform code, packaged with the archive_file data source.

How it works

  1. Terraform creates the compute resource, identity, networking, app settings and monitoring.
  2. It deploys a placeholder package or bootstrap image so the resource is valid.
  3. ignore_changes tells Terraform not to manage the code or image version attribute.
  4. The app pipeline builds, tests and deploys code, using slots or aliases for safe rollout.
  5. Configuration the code depends on is added by Terraform first, with backward-compatible defaults.
  6. The app release then starts using the new setting.

Example

resource "aws_lambda_function" "api" {
  function_name = "orders-api"
  role          = aws_iam_role.lambda.arn
  runtime       = "python3.12"
  handler       = "app.handler"
  filename      = "${path.module}/placeholder.zip"

  lifecycle {
    ignore_changes = [filename, source_code_hash, s3_key, image_uri]
  }
}
# app pipeline
aws lambda update-function-code --function-name orders-api --zip-file fileb://build.zip --publish

Common mistakes

  • Putting the build artifact hash in Terraform, so every commit triggers an infrastructure apply.
  • Forgetting ignore_changes, so the next infrastructure apply rolls the code back to the placeholder.
  • Letting app pipelines also change infrastructure settings by CLI, causing drift.
  • Deploying code that needs a setting before Terraform has created it.

How to answer in the interview

"In most teams I let Terraform manage the infrastructure and its configuration — the function app, plan, identity, networking and app settings — and the application pipeline deploy the code. Code changes many times a day and needs slots, canaries and fast rollbacks; infrastructure changes rarely and needs careful plans. Coupling them makes releases slow and plans noisy. So Terraform creates the function with a placeholder package and uses ignore_changes on the code or image attribute, and the app pipeline publishes versions. The exception is small, infrastructure-like functions such as a log forwarder, which can live with the Terraform code."

Likely follow-up questions

  • How do you handle a config change the new code depends on? Apply the infrastructure change first, backward compatible, then release code; remove old settings later (expand and contract).
  • What about container-based apps? Same pattern: Terraform owns the service, the pipeline sets the image tag; ignore the image attribute.
  • When would you still let Terraform deploy code? Rarely-changing platform-owned functions packaged with archive_file.
