On a kubeadm cluster, kubectl suddenly fails with certificate errors one year after installation. What is wrong and how do you fix it?

Kubernetes · scenario · levels mid, senior

In one line

kubeadm issues control plane certificates valid for one year (the CA for ten); if the cluster was never upgraded they expire, so check with kubeadm certs check-expiration, renew with kubeadm certs renew all on every control plane node, restart the static pods and update kubeconfig.

Detailed explanation

kubeadm creates a cluster CA (10 years by default) and leaf certificates for the API server, API server to kubelet and etcd clients, front-proxy, etcd server and peer, and the client certificates embedded in admin.conf, controller-manager.conf and scheduler.conf. These leaf certificates default to one year. Every kubeadm upgrade apply renews them automatically, which is why clusters upgraded regularly never see this problem. A cluster left alone for a year hits it all at once.

Symptoms: kubectl fails with x509: certificate has expired or is not yet valid, the controller manager and scheduler cannot talk to the API server, and nothing reconciles. Running workloads usually keep running because containers do not need the control plane, but nothing new can be scheduled, scaled or healed.

Renewal is done per control plane node with kubeadm certs renew all, which reuses the existing CA. The control plane components run as static pods and only read certificates at start-up, so they must be restarted; the simple way is moving their manifests out of /etc/kubernetes/manifests for about 20 seconds and back. Then copy the new admin.conf to your kubeconfig. Kubelet client certificates normally rotate automatically via rotateCertificates, but check /var/lib/kubelet/pki if a node also went NotReady. Newer kubeadm configuration (v1beta4) also allows setting certificate validity periods.

How it works

  1. Confirm: kubeadm certs check-expiration on a control plane node.
  2. Back up /etc/kubernetes/pki and the kubeconfig files.
  3. Run kubeadm certs renew all on each control plane node.
  4. Restart API server, controller manager, scheduler and etcd static pods.
  5. Copy /etc/kubernetes/admin.conf to ~/.kube/config; redistribute admin credentials.
  6. Verify kubelet certificates and node status; add expiry monitoring.

Example

sudo kubeadm certs check-expiration
sudo cp -r /etc/kubernetes/pki /root/pki-backup-$(date +%F)
sudo kubeadm certs renew all
sudo mkdir -p /tmp/manifests && sudo mv /etc/kubernetes/manifests/*.yaml /tmp/manifests/
sleep 20 && sudo mv /tmp/manifests/*.yaml /etc/kubernetes/manifests/
sudo cp /etc/kubernetes/admin.conf ~/.kube/config
kubectl get nodes

Common mistakes

  • Renewing on only one control plane node in an HA cluster.
  • Forgetting to restart static pods, so old certificates stay loaded.
  • Regenerating the CA, which breaks every kubelet and kubeconfig.
  • Keeping an old kubeconfig copy that still holds the expired client certificate.

How to answer in the interview

"kubeadm issues the control plane certificates, including the API server, etcd client and admin kubeconfig certs, for one year, while the CA lasts ten. If the cluster was never upgraded they expire and kubectl, the controller manager and scheduler fail with x509 expired errors. I confirm with kubeadm certs check-expiration, back up the pki directory, run kubeadm certs renew all on every control plane node, restart the static pods by moving their manifests out and back, and copy the new admin.conf. Kubelet certs normally rotate themselves. To prevent it, upgrade at least yearly, which renews certs, and alert thirty days before expiry."

Likely follow-up questions

  • How to detect expiry across many clusters? Export certificate expiry as metrics (for example an x509 certificate exporter or API server client certificate metrics) and alert centrally.
  • Do workloads stop? Usually not immediately, but nothing new is scheduled or healed.
  • What if the CA expires? That requires a full CA rotation, a much bigger planned operation.
