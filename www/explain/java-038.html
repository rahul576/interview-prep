Explain the circuit breaker pattern and how you would configure it.

Microservices · concept · levels senior, lead

In one line

A circuit breaker wraps calls to a dependency and moves between closed, open and half-open states based on the failure or slow-call rate over a sliding window, failing fast with a fallback while the dependency recovers; in Spring I configure it with Resilience4j alongside timeouts, retries and bulkheads.

Detailed explanation

When a dependency is down or very slow, continuing to call it wastes threads, adds latency to every request and hammers a service that is trying to recover. A circuit breaker, like an electrical one, trips to stop the damage.

In the closed state calls pass through and outcomes are recorded in a sliding window, count-based (last N calls) or time-based (last N seconds). Once at least minimumNumberOfCalls are recorded and the failure rate (exceptions you count as failures) or slow-call rate (calls longer than slowCallDurationThreshold) exceeds its threshold, the breaker goes open. In the open state calls are rejected immediately with CallNotPermittedException, and the code returns a fallback: cached data, a default, a degraded response or a clear error. After waitDurationInOpenState it goes half-open and allows a small number of trial calls; if they succeed it closes, otherwise it re-opens.

Resilience4j is the standard library for Spring Boot (Hystrix has been in maintenance mode since 2018 and is gone from Spring Cloud). Spring Cloud CircuitBreaker offers an abstraction over it. A breaker alone is not enough: combine it with a TimeLimiter/timeout (otherwise slow calls never count as failures), a small retry with backoff for transient errors, and a bulkhead to cap concurrent calls. In Resilience4j's Spring annotations the default aspect order applies Retry outermost, then CircuitBreaker, RateLimiter, TimeLimiter and Bulkhead, so each retry attempt is recorded by the breaker and retries stop when it is open.

How it works

  1. Closed: call, record success/failure/slow in the window.
  2. Threshold crossed (e.g. 50 percent of last 20 calls): open.
  3. Open: reject instantly, return fallback, for 30 s.
  4. Half-open: allow 5 trial calls.
  5. Trials succeed: closed; fail: open again.
  6. Metrics and state transitions exported via Micrometer for alerts.

Example

resilience4j:
  circuitbreaker:
    instances:
      inventory:
        slidingWindowType: COUNT_BASED
        slidingWindowSize: 20
        minimumNumberOfCalls: 10
        failureRateThreshold: 50
        slowCallDurationThreshold: 2s
        slowCallRateThreshold: 60
        waitDurationInOpenState: 30s
        permittedNumberOfCallsInHalfOpenState: 5
        ignoreExceptions: [com.acme.NotFoundException]
  timelimiter:
    instances:
      inventory: { timeoutDuration: 2s }
@CircuitBreaker(name = "inventory", fallbackMethod = "unknownStock")
public Stock stock(String sku) { return inventoryClient.get(sku); }

Stock unknownStock(String sku, Throwable t) { return Stock.unknown(sku); }

Common mistakes

  • Counting business errors like 404 or validation failures as failures.
  • No timeout, so slow calls tie up threads before the breaker reacts.
  • Fallbacks that call another fragile service.
  • Window too small, so the breaker flaps on a few errors.
  • Retrying aggressively in front of an open breaker without backoff.

How to answer in the interview

"A circuit breaker sits around calls to a dependency. While closed, calls pass and it records the failure and slow-call rate over a sliding window. When that crosses a threshold it opens and fails fast, returning a fallback such as cached data, which protects our threads and gives the dependency room to recover. After a wait it goes half-open and lets a few trial calls through to decide whether to close again. In Spring Boot I use Resilience4j and configure failure-rate threshold, window size, minimum calls, slow-call threshold, wait duration and half-open permits, and I always combine it with a timeout, a limited retry with backoff and a bulkhead."

Likely follow-up questions

  • Why can retries without backoff make an outage worse? They multiply load on a struggling service exactly when it needs less.
  • Count-based vs time-based window? Last N calls versus calls in the last N seconds; time-based suits variable traffic.
  • Where should the breaker live: client or server? Client side, per dependency, often also at the gateway or mesh.
