Can we force garbage collection using System.gc()?

JVM & Performance · concept · levels mid, senior

In one line

No: System.gc() is only a request; the specification does not guarantee a collection. In HotSpot it usually triggers a full stop-the-world GC, which is why it should not be called in production code; it can be disabled with -XX:+DisableExplicitGC or made concurrent with -XX:+ExplicitGCInvokesConcurrent.

Detailed explanation

The Javadoc says System.gc() "suggests that the Java Virtual Machine expend effort toward recycling unused objects". The JVM is free to ignore it. Runtime.getRuntime().gc() is the same thing.

In practice, HotSpot does honour the call by default, and with G1 or Parallel GC it performs a full GC: all application threads stop while the whole heap is collected and compacted. On a multi-gigabyte heap that can be hundreds of milliseconds or seconds. This is exactly why calling it in application code is bad practice:

  • It adds long pauses at unpredictable moments, often under load.
  • It rarely helps: the collector already runs when memory is needed and knows better when to do so.
  • It defeats GC ergonomics, since collections are tuned around allocation patterns.
  • If you feel you need it to "free memory", you probably have a leak or an undersized heap to fix.

JVM options.

  • -XX:+DisableExplicitGC turns calls into no-ops. Common in production, but be careful: the JDK's NIO code calls System.gc() when direct memory is exhausted to free unreachable DirectByteBuffers; disabling it can turn that into OutOfMemoryError: Direct buffer memory.
  • -XX:+ExplicitGCInvokesConcurrent makes G1 start a concurrent cycle instead of a full GC, often the safer choice. ZGC treats explicit GC as a concurrent cycle by default.

Who calls it? Old RMI distributed GC (periodically, controlled by sun.rmi.dgc.server.gcInterval), NIO direct-buffer reservation, some libraries and monitoring tools, and test or benchmark code. Legitimate uses are rare: benchmarks between iterations (JMH handles this), or tools measuring heap after collection.

Detection. GC logs show the cause, for example Pause Full (System.gc()). JFR records jdk.GarbageCollection events with the cause, and the stack trace of the caller can be found via a JFR or async-profiler recording, or by searching dependencies.

How it works

  1. Code calls System.gc().
  2. With DisableExplicitGC, the call returns immediately.
  3. With ExplicitGCInvokesConcurrent, G1 starts a concurrent cycle.
  4. Otherwise HotSpot runs a stop-the-world full GC.
  5. The GC log records the cause as System.gc().

Example

// Anti-pattern in a batch processor
for (Batch b : batches) {
    process(b);
    System.gc();          // full GC after every batch: slower, not safer
}
# Detect explicit GCs in logs
grep "System.gc()" gc.log
# [3456.2s] GC(88) Pause Full (System.gc()) 1800M->420M(4096M) 1320.4ms

# Production options
java -XX:+UseG1GC -XX:+ExplicitGCInvokesConcurrent -jar app.jar

Common mistakes

  • Calling System.gc() to "fix" memory leaks.
  • Disabling explicit GC without considering direct buffers.
  • Assuming the call is ignored; in HotSpot it usually is not.
  • Calling it in tight loops or request handlers.

How to answer in the interview

"No, System.gc is only a request; the specification doesn't guarantee that a collection runs. In HotSpot it usually does trigger a full stop-the-world GC, which is exactly why calling it in production code is bad: long pauses, and it rarely helps because the collector already runs when it's needed. It can be disabled with DisableExplicitGC, or with G1 turned into a concurrent cycle with ExplicitGCInvokesConcurrent, which I prefer because NIO relies on it to free direct buffers. If I think I need it, I probably have a memory problem to fix. I'd detect unexpected calls by looking for System.gc as the cause in GC logs or JFR."

Likely follow-up questions

  • Why do some libraries call System.gc() and how would you detect it? RMI's distributed GC and NIO direct-buffer cleanup; detect via System.gc() causes in GC logs or JFR.
  • Does finalize() run after System.gc()? Not guaranteed; finalisation is deprecated anyway.
  • What is Runtime.gc()? The same request; System.gc() delegates to it.
