Pods are Pending but the cluster autoscaler does not add nodes. How do you troubleshoot it?

Kubernetes · scenario · levels mid, senior

In one line

Read the pod events and the autoscaler's logs or cluster-autoscaler-status ConfigMap; typical reasons are requests larger than any node type, node groups at max size or hitting cloud quota/capacity, selectors, taints or affinity that no node group matches, and zonal volumes in a zone the group cannot launch in.

Detailed explanation

The cluster autoscaler does not look at CPU usage. It reacts to unschedulable pods: for each node group it simulates "if I added a node from this group's template, would the pending pod fit?" If no group passes the simulation, it does nothing and logs why (for example pod didn't trigger scale-up: 3 max node group size reached or didn't match node selector). So the job is to find which constraint fails the simulation.

Too big: a pod requests 64 GiB while the largest instance in any group has 32 GiB, or requests slightly more than a node's allocatable (capacity minus system and kubelet reservations and DaemonSet overhead). Limits on the group: max size reached, cloud vCPU quota, or the provider has no capacity for that instance type in that zone; check the autoscaler events and the cloud activity log. Constraints no template satisfies: nodeSelector or affinity on a label the group does not carry, a GPU request on a non-GPU group, missing tolerations for tainted groups, topology spread that requires a zone where no group exists. Volumes: a pod bound to an existing zonal PV in zone C can only run in zone C; a node group spanning zones A and B, or an autoscaler unaware of the zone balance, cannot help.

With Karpenter, there are no node groups: it reads pod requirements and picks instance types from NodePool constraints. Check the NodePool requirements, limits, the EC2NodeClass and Karpenter's events and logs for messages such as incompatible requirements.

How it works

  1. kubectl describe pod: FailedScheduling message.
  2. Read kubectl -n kube-system get cm cluster-autoscaler-status -o yaml and autoscaler logs.
  3. Compare pod requests with node allocatable of each group.
  4. Check group max sizes, cloud quotas and capacity errors.
  5. Match selectors, affinity, tolerations and zones with group templates.
  6. Fix the node group, NodePool or pod spec; confirm scale-up.

Example

kubectl describe pod ml-batch-4 | grep -A2 FailedScheduling
#  0/12 nodes are available: 12 Insufficient nvidia.com/gpu.
kubectl -n kube-system logs deploy/cluster-autoscaler | grep ml-batch-4
#  pod didn't trigger scale-up: 2 node(s) didn't match Pod's node affinity/selector, 1 max node group size reached
kubectl get nodepools -o yaml | grep -A10 requirements   # Karpenter

Common mistakes

  • Expecting the autoscaler to react to high CPU rather than Pending pods.
  • Forgetting DaemonSet overhead when sizing requests.
  • Scale-from-zero groups whose templates lack the labels or taints the pod needs.
  • Ignoring cloud quota errors in the provider console.

How to answer in the interview

"The pod events show why the scheduler couldn't place it, and the autoscaler logs or its status ConfigMap say why it chose not to scale, like no node group fitting. The common reasons: the pod requests more than any node type's allocatable; the node group is at max size or the cloud account hit a quota or capacity limit; a nodeSelector, affinity, GPU request or toleration matches no group template; or it needs a zonal volume in a zone where the group can't launch. I fix the group or the pod spec, and with Karpenter I check NodePool requirements, limits and events."

Likely follow-up questions

  • How does Karpenter pick instances? It filters instance types by pod and NodePool requirements, then picks the cheapest that fits the batch of pending pods (with spot price and capacity considered).
  • What is allocatable? Node capacity minus kube and system reservations and eviction thresholds.
  • Why balance zones? Zonal volumes and spread constraints need capacity in specific zones.
