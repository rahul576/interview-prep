A popular cache key expires and thousands of requests hit the database at once. How do you prevent this cache stampede?

Scalability & Reliability · scenario · levels entry, mid, senior

In one line

A cache stampede (thundering herd) happens when a hot key expires and many requests rebuild it at once; prevent it with request coalescing/locks, stale-while-revalidate, probabilistic early refresh, TTL jitter and pre-warming.

Detailed explanation

Suppose the home page data takes 300 ms to compute and gets 5,000 requests/s. When it expires, in those 300 ms about 1,500 requests miss and all hit the database with the same expensive query. The database slows, more requests pile up, and an outage follows.

Remedies:

  • Single flight / coalescing: only one request per key recomputes; others wait for its result (in-process) or briefly serve stale data. Across instances, use a short Redis lock (SET lock:key NX PX 5000).
  • Stale-while-revalidate: store a soft expiry and a hard expiry. After soft expiry, serve the old value and trigger one background refresh.
  • Probabilistic early expiration (XFetch): each request recomputes early with a probability that increases near expiry, spreading refreshes.
  • Jitter: randomise TTLs so keys written together don't expire together.
  • Pre-warm / scheduled refresh for known hot keys.

How it works

  1. Read key → value + soft_expiry.
  2. If fresh → return.
  3. If stale but present → return stale; try SET lock NX; winner refreshes asynchronously.
  4. If absent → winner rebuilds; others wait briefly then retry or return a fallback.

Example

val, soft_exp = cache.get_with_meta(key)
if val and time.time() < soft_exp:
    return val
if redis.set(f"lock:{key}", 1, nx=True, px=5000):
    refresh_async(key)            # recompute, set new value + soft_exp
if val:
    return val                    # serve stale while refreshing
return wait_for_value(key, timeout=0.5) or fallback()

Common mistakes

  • Identical TTLs for keys loaded at startup.
  • Locks without expiry (a crashed refresher blocks forever).
  • Making every waiter hit the DB after the lock holder fails.

How to answer in the interview

"That's a cache stampede. I'd make sure only one request rebuilds the key, using request coalescing in-process and a short distributed lock across instances, while everyone else keeps getting the stale value: stale-while-revalidate. I'd add jitter to TTLs, and for known hot keys refresh them proactively before they expire, so they never actually go missing under load."

Likely follow-up questions

  • Detect hot keys? Redis --hotkeys, client-side sampling, per-key metrics.
  • What if the DB is down? Serve stale longer; circuit breaker.
  • CDN equivalent? stale-while-revalidate and request collapsing at the edge.
