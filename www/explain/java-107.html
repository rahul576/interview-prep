What is the Java Memory Model, and what does happens-before mean?

Core Java & OOP · concept · levels mid, senior

In one line

The Java Memory Model (JMM) defines when writes by one thread are guaranteed visible to another and which reorderings are allowed; happens-before is its core rule: if A happens-before B, B sees A's effects. Without a happens-before edge you have a data race.

Detailed explanation

Compilers, the JIT and CPUs aggressively optimise: they keep values in registers, reorder independent instructions, and CPUs buffer stores and cache data per core. Within a single thread this is invisible (as-if-serial semantics), but across threads it means a write may be seen late, never, or in a different order than written. The JMM (JSR-133, Java 5) is the contract between programmers and the JVM about what is allowed.

Happens-before is a partial order on actions. If action A happens-before B, then A's effects (and everything before A in its thread) are visible to B, and they appear ordered. The main sources of happens-before edges:

  • Program order: within one thread, each action happens-before later ones.
  • Monitor lock: an unlock of a monitor happens-before every subsequent lock of the same monitor (synchronized, and equivalently Lock.unlock/lock).
  • Volatile: a write to a volatile field happens-before every subsequent read of that field.
  • Thread start: thread.start() happens-before any action in the started thread.
  • Thread termination: all actions in a thread happen-before another thread returns from join() on it.
  • Final fields: values written in a constructor to final fields are visible to all threads after construction, provided this did not escape.
  • Transitivity: if A hb B and B hb C, then A hb C. java.util.concurrent classes document their own edges (e.g. putting into a ConcurrentHashMap or BlockingQueue happens-before retrieval).

If two threads access the same variable, at least one writes, and there is no happens-before between them, the program has a data race. Results can include stale values (a stop flag never seen), reordering (a flag seen as true before the data it guards), and seeing partially constructed objects (classic broken double-checked locking). Correctly synchronised programs are guaranteed to behave as if sequentially consistent.

How it works

  1. Thread A writes data, then performs a "release" action (unlock, volatile write, start, completing a future).
  2. The JVM emits memory barriers to prevent reordering past that action.
  3. Thread B performs the matching "acquire" (lock, volatile read, join, get).
  4. By transitivity, all of A's earlier writes are visible to B.
  5. Without the pair, no visibility or ordering guarantee exists.

Example

class Publisher {
    private Config config;                 // plain field
    private volatile boolean ready;        // publication flag

    void writer() {                        // thread A
        config = loadConfig();             // 1
        ready = true;                      // 2: volatile write (release)
    }

    void reader() {                        // thread B
        if (ready) {                       // 3: volatile read (acquire)
            use(config);                   // 4: guaranteed to see config from 1
        }
    }
}
// Without volatile on 'ready', B could see ready == true but config == null,
// or loop forever never seeing ready become true.

Thread t = new Thread(() -> result = compute());
t.start();
t.join();                                  // join: result is visible here
System.out.println(result);

Common mistakes

  • Assuming writes are immediately visible to other threads.
  • Synchronising writers but not readers.
  • Using different locks and assuming they create happens-before with each other.
  • Double-checked locking without volatile.
  • Thinking volatile also gives atomicity for compound actions.

How to answer in the interview

"The Java Memory Model defines when a write by one thread is guaranteed to be visible to another, and which reorderings the compiler and CPU may do. The key concept is happens-before: if action A happens-before B, then B sees A's effects. Edges come from releasing and acquiring the same lock, writing and then reading a volatile field, Thread start and join, final-field initialisation, and the concurrency utilities, and they're transitive. Without such an edge I have a data race, and threads can see stale values, reordered writes or partially constructed objects. So I make sure shared data is published through one of these mechanisms."

Likely follow-up questions

  • Why is safe publication of objects important, and how do you achieve it? Without it another thread may see a reference before the object's fields are initialised; publish via final fields, volatile, a lock, a concurrent collection or static initialisation.
  • What is sequential consistency for data-race-free programs? The JMM guarantee that correctly synchronised programs behave as if all actions happened in some single interleaved order.
  • Does synchronized on different objects create happens-before? No; the edge only exists between unlock and lock of the same monitor.
