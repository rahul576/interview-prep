How do you build and maintain a golden evaluation dataset?

MLOps · concept · levels mid, senior

In one line

A golden evaluation dataset is a representative, expertly labelled, versioned and never-trained-on benchmark, enriched with edge cases and past failures, refreshed periodically, and used as a promotion gate for every model, prompt or retrieval change.

Detailed explanation

Without a stable benchmark, teams can't say whether a change is better or just different. The golden set is that yardstick.

Representative: sample from recent production traffic so its distribution resembles reality, then deliberately stratify to ensure enough examples of important segments (regions, languages, customer types, rare but costly classes). Report metrics per slice, not just overall.

High-quality labels: use domain experts, written labelling guidelines, two independent labellers per item and adjudication on disagreements. Measure inter-annotator agreement (for example Cohen's kappa). Label noise in the benchmark makes comparisons meaningless, since a one-point improvement is lost in noise.

Edge cases and regressions: add tricky inputs and examples from past production incidents, effectively regression tests so old failures can't silently return. Keep these as a tagged subset so they don't distort the representative metrics.

Versioned and isolated: store immutably with a version (v2026.10), document its composition, and never use it for training or hyperparameter tuning. Access controls or hashing checks can detect leakage into training data.

Refresh: production drifts, so periodically add new samples and retire obsolete ones, releasing a new version while keeping old versions to compare historical trends.

Gate: every candidate model, and for LLM systems every prompt, model or retrieval change, runs against it in CI, with thresholds on overall and slice metrics.

How it works

  1. Sample recent traffic, stratified by key segments.
  2. Label with guidelines, double annotation and adjudication.
  3. Add curated edge cases and incident examples as tagged slices.
  4. Freeze, version and document it (datasheet).
  5. Run it in CI as a promotion gate with per-slice thresholds.
  6. Refresh on a schedule (say quarterly) as a new version.

Example

golden_set: claims-classifier
version: 2026.10
size: 4200
composition:
  random_recent: 3000         # sampled Aug-Sep 2026
  rare_classes: 600           # stratified boost
  incidents: 350              # tagged "regression"
  adversarial: 250
labels: { annotators_per_item: 2, adjudicated: true, kappa: 0.86 }
gates: { macro_f1: ">=0.88", slice_min_f1: ">=0.80", regression_subset_acc: ">=0.97" }
used_for_training: false

Common mistakes

  • Using the golden set for tuning, slowly overfitting to it.
  • Never refreshing it, so it measures last year's traffic.
  • Cheap, noisy labels.
  • Only reporting the aggregate score.

How to answer in the interview

"A golden dataset is the trusted benchmark for every model change. I sample it from recent production traffic and deliberately cover important segments and rare classes. Labels are done by experts with guidelines, double annotation and adjudication. I add edge cases and examples from past incidents as a regression subset. It's versioned, immutable and never used for training or tuning. Because production evolves, I refresh it periodically as a new version, keeping old ones for trend comparison. Every candidate model, and for LLM systems every prompt or retrieval change, must pass it as a gate."

Likely follow-up questions

  • How do you prevent overfitting to it? Limit how often teams can see detailed results, keep a hidden holdout, and rotate in fresh samples.
  • How big should it be? Large enough that confidence intervals per important slice are narrower than the improvements you care about.
  • Who owns it? A named owner, often with domain experts, with a change process.
