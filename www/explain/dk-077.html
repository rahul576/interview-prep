How would you migrate a legacy application running on VMs to containers?

Docker · design · levels lead

In one line

Migrate a VM application to containers by first assessing its dependencies, state and OS assumptions, then making it container-friendly (config from env/files, logs to stdout, state moved out to databases, Redis or object storage, health endpoints), containerising incrementally starting with stateless parts, testing for parity, and cutting over gradually with a rollback plan.

Detailed explanation

A "lift and shift" that copies a VM into a giant container usually brings all the VM's problems plus new ones. Legacy apps often assume things containers break: a fixed hostname or IP, files written to the install directory, sticky sessions stored in memory, local cron jobs, log files rotated by logrotate, configuration edited by hand on the server, or licences tied to a MAC address.

Assessment comes first: inventory runtime versions and OS packages, inbound and outbound connections, where state lives (local disk, sessions, caches), how it is configured, how it logs, and its startup and shutdown behaviour. This also identifies poor candidates: apps needing kernel modules, special hardware, GUI desktops, or vendor software that isn't supported in containers.

Refactoring for containers follows the twelve-factor ideas: configuration from environment variables or mounted files, logs to stdout, sessions moved to Redis or a database, uploads to object storage, cron jobs turned into scheduled jobs (Kubernetes CronJobs), graceful handling of SIGTERM, and health/readiness endpoints.

Delivery: build the image in CI, run the same functional and performance tests against the container as against the VM, and watch memory behaviour under limits (old JVMs especially). Deploy side by side, shift traffic gradually through the load balancer (or by feature), compare error rates and latency, and keep the VMs ready for rollback until confidence is high.

How it works

  1. Assess: dependencies, state, config, logging, network, licensing.
  2. Externalise config, logs and state; add health checks and SIGTERM handling.
  3. Write a multi-stage Dockerfile; pin versions; run as non-root.
  4. Containerise stateless components first; leave the database on its current platform initially.
  5. Parity and load test; then canary traffic (5% → 25% → 100%).
  6. Decommission VMs after a stable period; document runbooks.

Example

FROM eclipse-temurin:8-jre
RUN useradd -r -u 10001 app
COPY --chown=app build/legacy-app.war /opt/app/app.war
ENV JAVA_OPTS="-XX:MaxRAMPercentage=75"
USER app
EXPOSE 8080
HEALTHCHECK CMD curl -fs http://localhost:8080/health || exit 1
ENTRYPOINT ["sh", "-c", "exec java $JAVA_OPTS -jar /opt/app/app.war"]

Sessions moved to Redis and uploads to S3 made this container stateless, so it could run three replicas behind the existing load balancer alongside the old VMs during cut-over.

Common mistakes

  • Treating the container like a VM: SSH, systemd and multiple services inside.
  • Leaving sessions or uploads on local disk, then scaling out.
  • Skipping performance tests; container memory limits change JVM behaviour.
  • Big-bang cut-over without a rollback path.

How to answer in the interview

"I'd start with an assessment: runtime and OS dependencies, where the app keeps state, how it's configured and logs, and assumptions like fixed hostnames or cron jobs. Then I'd make it container-friendly: config from environment or mounted files, logs to stdout, sessions and uploads moved to Redis, a database or object storage, health endpoints and proper SIGTERM handling. I'd containerise incrementally, starting with stateless components and leaving the database where it is at first. The same functional and load tests run against the container as against the VM. Then I'd run both side by side, shift traffic gradually, compare metrics, and keep the VMs as a rollback until we're confident."

Likely follow-up questions

  • Poor candidates for containers? Apps needing special kernel modules or hardware, GUI desktops, or vendor-unsupported licensed software.
  • Why do old JVMs misbehave? Pre-8u191 JVMs ignore cgroup limits and size heaps from host memory.
  • Should the database move too? Usually later, or to a managed service; it carries the most risk.
