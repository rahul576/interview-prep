How does Cassandra differ from a relational database?

Databases & SQL · concept · levels mid

In one line

Cassandra is a distributed, masterless wide-column database: data is partitioned by a hash of the partition key and replicated across a peer-to-peer ring, modelled query-first with denormalised tables, offering tunable consistency and very high write throughput but no joins, foreign keys or full ACID transactions.

Detailed explanation

Architecture: a relational database typically has one primary that accepts writes, with replicas for reads. Cassandra has no master: every node is equal, any node can coordinate a request, and data is spread around a token ring using consistent hashing of the partition key. Each partition is stored on several replicas (the replication factor), placed across racks and data centres. Adding nodes scales capacity roughly linearly, and losing nodes or even a data centre does not stop the cluster.

Data modelling: in SQL you normalise first and write any query later. In Cassandra you start from the queries. Each table has a primary key made of a partition key (decides which nodes hold the data; queries must provide it) and clustering columns (sort rows within a partition, enabling range queries such as "latest 50 events for this device"). If you need the same data by another key, you create another table and write to both, accepting duplication. There are no joins and no foreign keys, WHERE clauses are restricted to key columns (unless you use ALLOW FILTERING or secondary indexes, both to be used sparingly), and aggregations are limited.

Consistency: chosen per request (ONE, QUORUM, LOCAL_QUORUM, ALL). Lightweight transactions (IF NOT EXISTS, compare-and-set) use Paxos for single-partition conditional updates, but there are no multi-row ACID transactions in the relational sense.

Storage: writes go to a commit log and an in-memory memtable, which is flushed to immutable SSTables and later merged by compaction. Writes are sequential, which is why they are so fast.

How it works

  1. Client sends a CQL request to any node (the coordinator).
  2. The coordinator hashes the partition key to find replicas.
  3. It forwards the request and waits for as many replicas as the consistency level requires.
  4. Each replica appends to its commit log and memtable.
  5. Memtables flush to SSTables; compaction merges them.

Example

CREATE TABLE iot.readings_by_device (
  device_id  text,
  day        date,
  ts         timestamp,
  temp       double,
  PRIMARY KEY ((device_id, day), ts)
) WITH CLUSTERING ORDER BY (ts DESC);

SELECT ts, temp FROM iot.readings_by_device
WHERE device_id = 'sensor-17' AND day = '2026-11-21' LIMIT 50;

Common mistakes

  • Designing normalised tables and expecting joins.
  • Using ALLOW FILTERING in production queries.
  • Choosing partition keys that create huge or hot partitions.
  • Delete-heavy patterns that build up tombstones.

How to answer in the interview

"Cassandra is a distributed wide-column database. Unlike a relational database with a primary server, it's masterless: every node is equal in a ring, data is partitioned by a hash of the partition key and replicated, so it scales linearly and survives node and data-centre failures. Modelling is query-first: I design a table per query, with a partition key that decides where data lives and clustering columns that sort it, duplicating data instead of joining. There are no joins, foreign keys or arbitrary WHERE clauses, and only lightweight transactions, but consistency is tunable per query and writes are very fast thanks to the log-structured storage."

Likely follow-up questions

  • What makes a good partition key? High cardinality, even load, included in every query, and bounded partition size.
  • What are tombstones? Markers for deleted data; too many slow reads until compaction removes them.
  • When is Cassandra a bad fit? Ad hoc queries, complex joins, or multi-row transactional workloads.
