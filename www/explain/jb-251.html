How would you implement retry mechanisms and dead-letter topics?

Kafka · design · levels senior, lead

In one line

Classify errors as transient or permanent, retry transient ones in place with backoff or via non-blocking retry topics, and after the last attempt send the record to a dead-letter topic (DLT) with error metadata that you monitor and replay.

Detailed explanation

Not every failure deserves a retry. Transient errors (downstream timeout, 503, deadlock, broker hiccup) often succeed later. Permanent errors (deserialisation failure, schema mismatch, validation error, a null field that will always be null) will fail forever; such a poison message must not block the partition. So the first step is a clear list of retryable and non-retryable exceptions.

In Spring Kafka, the DefaultErrorHandler performs blocking retries: it re-seeks the partition and redelivers the failed record with a BackOff (fixed or exponential). Order is preserved because nothing else from that partition is processed, but the partition stalls, and long waits risk exceeding max.poll.interval.ms, so keep these short (a few seconds). Wrap deserialisers in ErrorHandlingDeserializer so bad bytes become a handled error rather than an endless loop.

For longer delays use non-blocking retries: @RetryableTopic (or RetryTopicConfiguration) creates topics such as orders-retry-0, orders-retry-1 with increasing delays; a failed record is republished to the next retry topic and the main partition moves on. The trade-off is that ordering is lost for that key: later events may be processed before the retried one.

After max attempts, the DeadLetterPublishingRecoverer publishes to a DLT (orders-dlt with @RetryableTopic, orders.DLT by default for the recoverer), adding headers with the exception class, message, stack trace, original topic, partition, offset and timestamp. Operations must alert on DLT traffic, provide a tool to inspect and replay after the bug or data is fixed, and consumers must be idempotent because replays and retries produce duplicates.

How it works

  1. Listener throws an exception.
  2. Error handler checks if it is retryable.
  3. Blocking: retry in place N times with backoff. Non-blocking: publish to the next retry topic with a delay.
  4. After the final attempt, publish to the DLT with error headers and commit the original offset.
  5. Alert on DLT; investigate, fix, replay to the main topic.

Example

@RetryableTopic(
    attempts = "4",
    backoff = @Backoff(delay = 60_000, multiplier = 10.0),   // 1m, 10m, 100m
    exclude = { ValidationException.class, DeserializationException.class },
    dltTopicSuffix = "-dlt")
@KafkaListener(topics = "orders", groupId = "fulfilment")
public void onOrder(OrderPlaced evt) { fulfilmentService.handle(evt); }

@DltHandler
public void onDlt(OrderPlaced evt, @Header(KafkaHeaders.EXCEPTION_MESSAGE) String error) {
    log.error("Order {} dead-lettered: {}", evt.orderId(), error);
    metrics.counter("orders.dlt").increment();
}

Common mistakes

  • Retrying permanent errors, so a poison message loops forever.
  • Long blocking backoffs that trigger rebalances.
  • A DLT nobody watches.
  • Replaying DLT records into non-idempotent consumers.

How to answer in the interview

"I first separate transient errors from permanent ones like deserialisation or validation failures. Transient errors get a few blocking retries with exponential backoff through Spring Kafka's DefaultErrorHandler, which keeps ordering but briefly stalls the partition. For longer outages I use non-blocking retry topics with @RetryableTopic, accepting that ordering for that key is lost. After the final attempt the record goes to a dead-letter topic with headers for the exception and the original topic, partition and offset. I alert on DLT volume and have a replay tool, and because retries and replays cause duplicates, the consumers are idempotent."

Likely follow-up questions

  • When do retry topics break ordering? When later events for the same entity are processed while an earlier one waits in a retry topic, for example "OrderCancelled" before "OrderCreated".
  • How do you replay a DLT? A small consumer or admin tool republishes fixed records to the main topic, ideally preserving the key.
  • How do you handle deserialisation errors? ErrorHandlingDeserializer delegates and routes the bad record to the DLT without retries.
