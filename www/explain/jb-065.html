What is the Stream API?

Java 8+ Features · concept · levels entry, mid

In one line

The Stream API (Java 8) processes data declaratively as a pipeline: a source, zero or more lazy intermediate operations (filter, map, sorted) and one terminal operation (collect, count); streams don't store data, don't modify the source, can be consumed once, and can run in parallel.

Detailed explanation

Traditional loops describe how to iterate: indexes, temporary lists, accumulator variables. Streams describe what you want, which produces shorter, more readable and less error-prone code, and lets the library choose how to execute it.

Sources include collection.stream(), Arrays.stream, Stream.of, IntStream.range, Files.lines, BufferedReader.lines, Pattern.splitAsStream, Stream.iterate and Stream.generate. Intermediate operations return a new stream and are lazy; terminal operations trigger execution. Elements flow one at a time through the whole pipeline, so filter and map are fused into a single pass and short-circuiting operations (findFirst, limit, anyMatch) can stop early.

Key properties: a stream is not a data structure; it does not modify its source (operations produce new results); it is single-use (reusing it throws IllegalStateException); and it should use non-interfering, stateless lambdas. Primitive streams (IntStream, LongStream, DoubleStream) avoid boxing and add sum, average and summaryStatistics. Collectors provide rich terminal results: toList, toMap, groupingBy, joining, partitioningBy. Java 16 added Stream.toList(), and Java 9 added takeWhile, dropWhile and ofNullable.

parallelStream() runs on the ForkJoinPool common pool; it is beneficial only for large CPU-bound workloads.

How it works

  1. Create a stream from a source.
  2. Chain intermediate stages; each wraps the previous one.
  3. Invoke a terminal operation; the pipeline is built and evaluated.
  4. Elements are pulled through the stages one by one.
  5. The terminal operation returns a result and the stream is consumed.

Example

BigDecimal paidTotal = orders.stream()
    .filter(Order::isPaid)
    .map(Order::total)
    .reduce(BigDecimal.ZERO, BigDecimal::add);

Map<String, Long> ordersPerCity = orders.stream()
    .collect(Collectors.groupingBy(o -> o.address().city(), Collectors.counting()));

String csv = customers.stream()
    .map(Customer::name)
    .sorted()
    .collect(Collectors.joining(", "));

try (Stream<String> lines = Files.lines(Path.of("orders.csv"))) {   // close file streams
    long errors = lines.filter(l -> l.contains("ERROR")).count();
}

Common mistakes

  • Reusing a stream after a terminal operation.
  • Modifying the source collection inside the pipeline.
  • Forgetting to close I/O-backed streams like Files.lines.
  • Using streams with complex side effects where a loop is clearer.

How to answer in the interview

"The Stream API, added in Java 8, lets me process data declaratively as a pipeline instead of writing loops. A stream comes from a source like a collection, array or Files.lines, has zero or more intermediate operations like filter, map and sorted, and ends with one terminal operation like collect, count or forEach. Streams don't store data or modify the source; they're lazy, so nothing runs until the terminal operation, and each stream can be consumed only once. For example, filter paid orders, map to totals and reduce with BigDecimal add. A stream can also run in parallel."

Likely follow-up questions

  • Why can a stream only be consumed once? It may wrap a one-shot source like an iterator or I/O and holds pipeline state.
  • Stream versus Collection? A collection stores data; a stream computes over it on demand.
  • When should you close a stream? When it wraps I/O resources, using try-with-resources.
