How do you install and manage packages on Linux?

Linux · concept · levels entry, mid

In one line

Distributions install software with package managers such as apt (Debian/Ubuntu) and dnf (RHEL family), from GPG-signed repositories; you install, update, search and remove packages, pin versions for reproducibility and apply security patches regularly, ideally by rebuilding images.

Detailed explanation

A package manager installs software together with its dependencies, tracks which files belong to which package, and upgrades or removes them cleanly. On Debian and Ubuntu the high-level tool is apt (on top of dpkg and .deb files); on RHEL, Rocky, AlmaLinux, Fedora and Amazon Linux 2023 it is dnf (on top of rpm), with yum now mostly an alias for dnf. Alpine uses apk, SUSE uses zypper.

Packages come from repositories configured in /etc/apt/sources.list.d/ or /etc/yum.repos.d/. Repositories and packages are signed with GPG keys, and the package manager verifies signatures, so a tampered mirror is rejected. When adding a third-party repository, install its key scoped to that repo (apt's signed-by=), not as a globally trusted key.

Everyday operations: apt update refreshes the package index (it does not upgrade anything), apt install nginx, apt upgrade, apt remove or purge, apt search, apt show; on RHEL dnf install, dnf upgrade, dnf remove, dnf search, dnf info, plus dnf history to see and undo transactions.

Reproducibility: in Dockerfiles and server builds, pin versions (nginx=1.24.0-2ubuntu7) or pin the base image digest, so a rebuild next month gives the same result; use apt-mark hold or dnf versionlock to prevent unwanted upgrades. Clean caches in the same Docker layer to keep images small.

Patching: security updates must be applied promptly. For long-lived servers, unattended-upgrades or dnf-automatic install security fixes, with a planned reboot process for kernel updates. For immutable infrastructure and containers, the better pattern is to rebuild images with patched packages in the pipeline, scan them, and redeploy, so every environment runs a known, tested artefact.

How it works

  1. Repository metadata is downloaded and its signature verified.
  2. The package manager resolves dependencies.
  3. Packages are downloaded, verified and installed.
  4. The local database records installed files and versions.
  5. Updates repeat the process for newer versions.

Example

# Debian/Ubuntu
sudo apt update && sudo apt install -y nginx
apt-cache policy nginx
sudo apt-mark hold nginx
# RHEL family
sudo dnf install -y nginx
sudo dnf upgrade --security
dnf history
FROM ubuntu:24.04
RUN apt-get update \
 && apt-get install -y --no-install-recommends curl ca-certificates \
 && rm -rf /var/lib/apt/lists/*

Common mistakes

  • Running apt install without apt update in a fresh container and getting stale or missing packages.
  • Adding third-party repos with a globally trusted key.
  • Never patching long-running servers.
  • Leaving package caches in Docker image layers.

How to answer in the interview

"Distributions use package managers that install software and its dependencies from repositories. On Debian and Ubuntu that is apt, so apt update refreshes the index and apt install nginx installs it; on Red Hat, Rocky and Amazon Linux it is dnf, with yum as the older name. Repositories sign packages with GPG keys so tampering is detected. I search, upgrade and remove packages, and for reproducible images I pin versions or base image digests. In production, security patches must be applied regularly, with unattended upgrades on servers, or better, by rebuilding and redeploying patched images through the pipeline."

Likely follow-up questions

  • Why prefer rebuilding an image over patching running servers? Every environment gets the same tested artefact, no drift, and rollback is just the previous image.
  • What does apt update do versus apt upgrade? update refreshes the index; upgrade installs newer versions.
  • How do you see which package owns a file? dpkg -S /path or rpm -qf /path.
