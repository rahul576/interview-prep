Why is deep pagination slow in Elasticsearch, and what should you use instead?

Elasticsearch · concept · levels mid, senior

In one line

With from + size, every shard must collect from + size hits, and the coordinator sorts shards × (from + size) entries, so cost grows with depth. That's why index.max_result_window defaults to 10,000. Use search_after with a sort plus a tie-breaker and a point in time (PIT) for deep or infinite pagination and exports. Scroll is legacy and no longer recommended for deep pagination.

Detailed explanation

Elasticsearch searches are distributed. For page 1,000 with size 20 (from = 19,980), each of, say, 10 shards must find its top 20,000 results, ship them (sort values and ids) to the coordinating node, and the coordinator sorts 200,000 entries to return just 20. Memory and CPU grow linearly with depth on every shard, and with the number of shards. Deep pages become slow and can destabilise the cluster, which is why requests beyond from + size > 10,000 are rejected by default (index.max_result_window). Raising the limit just moves the problem.

search_after (the recommended approach).

  • Sort by a field plus a unique tie-breaker, so the order is total: [{"price": "asc"}, {"_shard_doc": "asc"}] with PIT, or a unique id field.
  • Each response returns sort values for the last hit. The next request passes them as search_after, so each shard only needs the next size documents after that key. The cost is constant per page.
  • Combine it with a point in time (POST /index/_pit?keep_alive=1m). A PIT freezes a consistent view of the index, so documents inserted or deleted between pages don't cause duplicates or skipped results. Pass the PIT id (and refresh it) with each request.
  • The limitation: no random jumping to page 500. It is next-page only, which fits infinite scroll and exports.

Scroll API. Keeps a search context open and walks through all results. It is still usable for one-off bulk exports or reindex-style jobs, but Elastic now recommends PIT plus search_after instead, even for exports. Scroll contexts hold resources and aren't meant for user-facing pagination.

UX design: most users never go past a few pages. Cap page numbers (show "first 50 pages"), and encourage refining filters. Use a search_after cursor for infinite scroll and composite aggregations for paging through buckets.

How it works

  1. Open a PIT: POST /products/_pit?keep_alive=2m returns its id.
  2. First page: query plus sort with a tie-breaker, size: 20, and the PIT.
  3. Read the sort array of the last hit.
  4. Next page: the same query with search_after: <last sort> and the latest PIT id.
  5. Repeat. When finished, DELETE /_pit.

Example

POST /products/_pit?keep_alive=2m

GET /_search
{
  "size": 20,
  "query": { "match": { "name": "running shoes" } },
  "pit":   { "id": "46ToAwMDaWR…", "keep_alive": "2m" },
  "sort":  [ { "_score": "desc" }, { "_shard_doc": "asc" } ],
  "search_after": [ 7.42, 18402 ]
}

Common mistakes

  • Raising max_result_window to 1,000,000.
  • search_after without a unique tie-breaker, which skips or duplicates documents with equal sort values.
  • Using scroll for user-facing pagination and leaking contexts.
  • Not closing PITs or scrolls.

How to answer in the interview

"With from and size, every shard has to collect from plus size top documents and the coordinating node merges them all, so cost grows with the page depth and the shard count. That's why index.max_result_window defaults to 10,000. For deep pagination or infinite scroll I use search_after: sort by the relevant field plus a unique tie-breaker, and pass the last hit's sort values to get the next page, at constant cost. I pair it with a point in time so the view stays consistent between pages. For bulk exports PIT with search_after also works, and scroll is now legacy and not meant for users paging."

Likely follow-up questions

  • Infinite scroll on product search? A search_after cursor token returned to the client, plus a PIT, with page jumping disabled.
  • Why a tie-breaker? Equal sort values make the order ambiguous, which skips or repeats documents.
  • Showing "page 37 of 120"? Allow it only within the window, or show approximate counts (track_total_hits up to 10k).
