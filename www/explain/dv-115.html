A pod is in Pending, OOMKilled or ImagePullBackOff state. What does each mean and how do you fix it?

Kubernetes · scenario · levels mid, senior

In one line

Pending means the pod cannot be scheduled (resources, selectors, taints, unbound PVC); ImagePullBackOff means the kubelet cannot pull the image (wrong name/tag or registry auth); OOMKilled (exit code 137) means a container exceeded its memory limit. kubectl describe pod events tell you which cause applies.

Detailed explanation

Pending: the pod exists but the scheduler found no suitable node. Events say things like 0/6 nodes are available: 3 Insufficient cpu, 3 node(s) had untolerated taint. Causes: requests larger than any node's free allocatable capacity (requests count, not real usage), a nodeSelector or affinity matching no node, taints without tolerations, topology spread rules, a ResourceQuota, or a PVC that cannot bind (no StorageClass, zone mismatch). Fix by right-sizing requests, letting the autoscaler add nodes, or correcting constraints.

ImagePullBackOff / ErrImagePull: the kubelet tried to pull and failed, then backs off exponentially. Events show the registry error: not found (typo, missing tag, wrong architecture), unauthorized (private registry without an imagePullSecret, or node IAM role lacking ECR/ACR pull rights), or rate limiting (Docker Hub anonymous limits). Fix the reference, add credentials, or mirror images to your own registry.

OOMKilled: the kernel's OOM killer terminated the container because it hit its memory limit; lastState.terminated.reason: OOMKilled, exit code 137 (128 + SIGKILL). Repeated kills lead to CrashLoopBackOff. Check real usage with kubectl top or Prometheus: a leak grows steadily, an undersized limit fails at peak. For JVMs, set heap relative to the container (-XX:MaxRAMPercentage=75) so heap plus metaspace, threads and buffers fit. Raise the limit only if the workload truly needs it.

How it works

  1. kubectl get pod shows status.
  2. kubectl describe pod → read Events and Last State.
  3. Pending → compare requests with node allocatable; check selectors, taints, PVCs.
  4. ImagePullBackOff → verify image, tag, architecture and pull credentials.
  5. OOMKilled → compare memory usage with limits; fix leak or tune limits.

Example

kubectl describe pod orders-5f6c-xyz | sed -n '/Events/,$p'
# Warning FailedScheduling  0/5 nodes are available: 5 Insufficient memory.
kubectl get pod orders-5f6c-xyz -o jsonpath='{.status.containerStatuses[0].lastState.terminated}'
# {"exitCode":137,"reason":"OOMKilled",...}
kubectl create secret docker-registry regcred --docker-server=registry.example.com \

Common mistakes

  • Setting huge requests "to be safe", leaving pods Pending.
  • Using the latest tag and wondering which image is running.
  • Raising memory limits forever instead of finding the leak.
  • JVM heap equal to the container limit.

How to answer in the interview

"I start with kubectl describe pod and read the events. Pending means the scheduler can't place it: insufficient CPU or memory requests, a selector or affinity nothing matches, an untolerated taint or an unbound PVC, so I fix requests, add nodes or correct the constraints. ImagePullBackOff means the kubelet can't pull the image, typically a wrong name or tag, or missing registry credentials. OOMKilled, exit code 137, means the container exceeded its memory limit; I check real usage, look for leaks or JVM heap settings, and only then raise the limit."

Likely follow-up questions

  • Why size JVM heap relative to the limit? The limit covers heap plus non-heap memory; a heap equal to the limit guarantees OOM kills.
  • What is CrashLoopBackOff? The container keeps exiting and the kubelet delays restarts exponentially.
  • Can a pod be evicted instead of OOMKilled? Yes, node-pressure eviction when the node runs low.
