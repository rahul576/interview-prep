Design a distributed job scheduler that runs millions of scheduled tasks reliably.

System Design · design · levels lead

In one line

A distributed job scheduler keeps jobs in a persistent store indexed by next run time, partitions due-job scanning across nodes, claims jobs with leases to avoid double execution, hands work to workers via a queue, requires idempotent jobs with retries, and monitors lag and missed runs.

Detailed explanation

Millions of scheduled tasks (reminders, billing runs, report generation) cannot live in in-memory timers on one server: a restart loses them and one node cannot keep up. The design separates scheduling (deciding what is due) from execution (doing it).

Job store: a table such as jobs(id, tenant, schedule, next_run_at, status, lease_owner, lease_until, attempts) with an index on next_run_at. For recurring jobs, the schedule is a cron expression plus a time zone; after each run the next fire time is computed.

Partitioning: scheduler nodes do not all scan the whole table. Jobs are hashed into N shards; each node owns a set of shards (assigned via a coordinator, Kubernetes leader election, or Kafka consumer group rebalancing). This scales horizontally and avoids contention.

Claiming with leases: a node atomically claims due jobs: UPDATE ... SET lease_owner = me, lease_until = now() + 60s WHERE id = ? AND (lease_until IS NULL OR lease_until < now()), or uses SELECT ... FOR UPDATE SKIP LOCKED in PostgreSQL. If the node dies, the lease expires and another node picks the job up. Use fencing tokens (an incrementing lease version) so a slow former owner cannot overwrite results.

Execution: claimed jobs are pushed to a queue (Kafka, SQS) consumed by worker pools, which allows independent scaling and priorities. Delivery is at-least-once, so jobs must be idempotent, with retries, exponential backoff and a dead-letter queue. Existing tools include Quartz (clustered JDBC mode), db-scheduler, JobRunr, and workflow engines like Temporal.

How it works

  1. Client registers a job with schedule and time zone; next_run_at computed and stored.
  2. Each scheduler node polls its shards every second for next_run_at <= now().
  3. It claims jobs with a lease and publishes them to the execution queue.
  4. Worker executes idempotently, reports success or failure.
  5. Scheduler computes the next run, clears the lease, or schedules a retry.
  6. Metrics: scheduling lag, missed runs, failures; alerts on thresholds.

Example

-- PostgreSQL: claim up to 500 due jobs for shard 7 without blocking other nodes
WITH due AS (
  SELECT id FROM jobs
  WHERE shard = 7 AND next_run_at <= now() AND status = 'SCHEDULED'
  ORDER BY next_run_at
  LIMIT 500
  FOR UPDATE SKIP LOCKED
)
UPDATE jobs j
SET status = 'CLAIMED', lease_owner = 'node-3', lease_until = now() + interval '60 seconds',
    lease_version = lease_version + 1
FROM due WHERE j.id = due.id
RETURNING j.id, j.payload, j.lease_version;

Common mistakes

  • In-memory @Scheduled timers on every instance, causing duplicates.
  • Locks without expiry, so a crashed node blocks jobs forever.
  • Assuming exactly-once execution.
  • Storing cron times in UTC and breaking local-time schedules at DST changes.
  • No visibility into missed or late runs.

How to answer in the interview

"Jobs live in a persistent store with the next run time indexed. Scheduler nodes each own shards of the job space, so they don't compete, and claim due jobs with a lease: an atomic conditional update or SKIP LOCKED with an expiry, so if a node dies another takes over. Claimed jobs go onto a queue for worker pools. Delivery is at-least-once, so jobs are idempotent with retries, backoff and a DLQ. I'd monitor scheduling lag and missed runs, and use fencing tokens so a stale node can't commit."

Likely follow-up questions

  • Cron in different time zones? Store the zone ID with the schedule and compute next run with ZonedDateTime; define DST gap/overlap behaviour.
  • What about missed runs after an outage? A per-job misfire policy: run once, run all, or skip.
  • Quartz or a custom system? Quartz/db-scheduler for moderate scale; custom or Temporal for millions with complex workflows.
