What is AWS Lambda and serverless, and what are its limits?

Cloud (AWS) · concept · levels mid, senior

In one line

Lambda runs your code as functions triggered by events, with no servers to manage, automatic scaling and pay-per-request-and-duration billing; its limits include a 15-minute timeout, up to about 10 GB memory, package size limits, concurrency quotas and cold starts, so it suits event-driven, spiky and glue workloads.

Detailed explanation

Serverless means you do not provision or patch servers, capacity scales automatically, and you pay only while code runs. With Lambda you deploy a zip or container image, choose memory (CPU scales proportionally), and AWS runs an execution environment when an event arrives.

Triggers come in three styles: synchronous (API Gateway or function URLs for HTTP APIs, ALB), asynchronous (S3 uploads, EventBridge rules and schedules, SNS) with built-in retries and dead-letter destinations, and poll-based event source mappings (SQS, Kinesis, DynamoDB Streams, Kafka) where Lambda pulls batches.

Scaling: each concurrent request needs its own environment, so Lambda scales out by creating more of them, bounded by the account's regional concurrency quota (1,000 by default, raisable) and per-function reserved concurrency. Downstream systems like relational databases can be overwhelmed, which is why RDS Proxy or queues are used.

Limits to know: maximum 15 minutes per invocation; memory 128 MB to 10,240 MB; /tmp up to 10 GB; deployment packages of 50 MB zipped for direct upload and 250 MB unzipped (container images up to 10 GB); payload size limits for synchronous calls. Cold starts happen when a new environment initialises runtime and code, adding from tens of milliseconds to seconds, worst for JVM and large packages. Mitigations: SnapStart (Java, also Python and .NET), provisioned concurrency, smaller packages and lighter frameworks.

How it works

  1. Event arrives → Lambda finds a warm environment or creates one (cold start: download code, start runtime, run init code).
  2. Handler runs with the event and context.
  3. Environment stays warm for reuse for a while, keeping connections and caches from init.
  4. Results return synchronously or go to destinations/DLQ on failure.

Example

import json, boto3
s3 = boto3.client("s3")          # created once per environment, reused

def handler(event, context):
    for rec in event["Records"]:  # S3 put notification
        bucket = rec["s3"]["bucket"]["name"]
        key = rec["s3"]["object"]["key"]
        head = s3.head_object(Bucket=bucket, Key=key)
        print(json.dumps({"key": key, "size": head["ContentLength"]}))
    return {"status": "ok"}

Common mistakes

  • Initialising SDK clients and DB connections inside the handler on every call.
  • Unbounded concurrency hammering a relational database.
  • Non-idempotent handlers despite at-least-once async and SQS delivery.
  • Using Lambda for long-running or constantly busy services where containers are cheaper.

How to answer in the interview

"Lambda runs functions without servers to manage: I deploy code or a container image, AWS runs it when an event arrives, and I pay per request and execution time. Typical triggers are API Gateway, S3, SQS, DynamoDB Streams and EventBridge. It scales by running more concurrent environments, within account concurrency limits. The limits matter: 15 minutes per invocation, around 10 GB of memory, package size limits and cold starts, which hurt JVM apps unless I use SnapStart or provisioned concurrency. I use it for event-driven, spiky and glue workloads, and containers for long-running services."

Likely follow-up questions

  • Reduce Java cold starts? SnapStart, provisioned concurrency, smaller dependencies, more memory.
  • Protect a database from Lambda scaling? Reserved concurrency, RDS Proxy or an SQS buffer.
  • How are failures handled for async events? Retries, then on-failure destinations or a DLQ.
