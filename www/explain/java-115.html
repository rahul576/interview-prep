How do you size and configure a ThreadPoolExecutor? What happens when the queue is full?

Concurrency · concept · levels mid, senior

In one line

A ThreadPoolExecutor runs tasks on core threads, queues further tasks, creates threads up to max pool size only when the queue is full, and then applies a rejection policy; use a bounded queue, size CPU-bound pools near core count and I/O-bound pools by wait/compute ratio (or use virtual threads).

Detailed explanation

The key parameters are corePoolSize, maximumPoolSize, keepAliveTime, the workQueue, a ThreadFactory and a RejectedExecutionHandler. The submission algorithm is often misunderstood:

  1. If fewer than core threads are running, start a new thread for the task.
  2. Otherwise try to enqueue the task.
  3. If the queue is full, start a new thread, up to max.
  4. If max threads are busy and the queue is full, reject.

So with an unbounded queue step 2 always succeeds and the pool never grows beyond core; max is meaningless. With a SynchronousQueue (no capacity), tasks go directly to new threads up to max. Threads above core die after keepAliveTime idle; allowCoreThreadTimeOut(true) applies that to core threads too.

Always bound the queue so overload becomes visible instead of a silent memory leak and huge latency. Rejection policies:

  • AbortPolicy (default): throws RejectedExecutionException; the caller can return 503 or retry.
  • CallerRunsPolicy: the submitting thread runs the task itself, which slows the producer: natural back-pressure.
  • DiscardPolicy / DiscardOldestPolicy: silently drop the new or oldest task; only for loss-tolerant work like metrics.
  • Custom handlers: log, record a metric, push to a fallback.

Sizing. For CPU-bound tasks, about Ncores (or +1) threads; more just adds context switching. For I/O-bound tasks, Brian Goetz's formula: threads ≈ Ncores × (1 + wait time / compute time), e.g. 8 cores, 90 ms waiting per 10 ms computing → ~80 threads. Validate with load tests and also respect downstream limits such as DB pool size. On Java 21+, blocking I/O work is often better on virtual threads with a Semaphore. Name your threads and expose metrics (active count, queue size, rejections).

How it works

  1. Task arrives → core thread if under core size.
  2. Else enqueue.
  3. Queue full → extra thread up to max.
  4. All full → rejection handler.
  5. Idle extra threads time out.

Example

int cores = Runtime.getRuntime().availableProcessors();
ThreadPoolExecutor ioPool = new ThreadPoolExecutor(
        cores * 4,                          // core
        cores * 8,                          // max, used only when queue full
        60, TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(1_000),    // bounded
        Thread.ofPlatform().name("io-", 0).factory(),
        new ThreadPoolExecutor.CallerRunsPolicy());

meter.gauge("pool.queue", ioPool, p -> p.getQueue().size());

Common mistakes

  • Unbounded queue plus a large max, expecting the pool to scale.
  • Using Executors.newFixedThreadPool / newCachedThreadPool in services.
  • CallerRunsPolicy on an event-loop or request thread that must not block.
  • Sizing far beyond downstream connection limits.

How to answer in the interview

"A ThreadPoolExecutor keeps core threads alive, queues tasks when they're busy, and only creates threads up to the maximum when the queue is full. I always use a bounded queue so memory can't grow without limit. When both the queue and max threads are exhausted, the rejection policy applies: AbortPolicy throws, CallerRunsPolicy runs the task on the caller thread, which gives natural back-pressure, and the discard policies drop work. For CPU-bound tasks I size around the number of cores; for I/O-bound tasks larger, based on wait time versus compute time, or I use virtual threads."

Likely follow-up questions

  • Why can a pool with an unbounded queue never exceed core size? New threads beyond core are created only when the queue rejects an offer, which never happens.
  • How do you monitor a pool? Active count, queue size, completed tasks and rejections exported as metrics.
  • How do you shut it down? shutdown, awaitTermination, then shutdownNow.
