What is the difference between TCP and UDP? Give examples of where each is used.

Networking · concept · levels entry

In one line

TCP is connection-oriented and reliable (handshake, ordering, retransmission, flow and congestion control); UDP is connectionless, best-effort and low-overhead. TCP carries HTTP/1.1-2, SSH and databases; UDP carries DNS queries, voice, video, gaming and QUIC (HTTP/3).

Detailed explanation

TCP starts with a three-way handshake (SYN, SYN-ACK, ACK). It numbers every byte with sequence numbers; the receiver sends acknowledgements, and missing segments are retransmitted, so the application gets a complete, in-order byte stream. Flow control (the receive window) stops a fast sender overwhelming a slow receiver, and congestion control (CUBIC, BBR) backs off when the network is congested. The connection ends with FIN or RST. The cost is latency: a round trip before data, and head-of-line blocking, where one lost segment delays everything behind it.

UDP just sends independent datagrams with source and destination ports and a checksum. No handshake, no acknowledgements, no ordering, no retransmission, no congestion control. Packets can be lost, duplicated or reordered. The header is 8 bytes versus TCP's 20 or more.

Why choose UDP? When timeliness beats completeness (a late voice packet is useless, so retransmitting it is pointless), when requests are tiny (a DNS query fits in one packet), when you need multicast/broadcast, or when the application implements its own reliability. QUIC, the transport under HTTP/3, runs on UDP and implements reliability, encryption and per-stream ordering in user space, avoiding TCP's head-of-line blocking across streams and enabling faster connection setup.

Examples: TCP for HTTP/1.1 and HTTP/2, HTTPS, SSH (22), SMTP, PostgreSQL (5432), MySQL, Kafka. UDP for DNS (53), NTP (123), DHCP, SNMP, syslog (traditionally), VoIP/RTP, video conferencing (WebRTC), online games, WireGuard VPN, and QUIC.

How it works

  1. TCP: SYN, SYN-ACK, ACK establishes state on both ends.
  2. Data flows with sequence numbers; receiver ACKs.
  3. Lost segments are detected (timeouts or duplicate ACKs) and resent.
  4. Windows control the sending rate.
  5. UDP: the application sends a datagram; it arrives or it doesn't.
  6. UDP applications add their own timeouts and retries if needed.

Example

nc -vz db.internal 5432            # TCP connect test
nc -vzu ntp.internal 123           # UDP "test" - no handshake, so success is not proof
dig @1.1.1.1 example.com           # DNS over UDP
dig +tcp @1.1.1.1 example.com      # same query forced over TCP
ss -tuln                           # listening TCP and UDP sockets

Common mistakes

  • Saying UDP is "unreliable so never used for important things"; DNS and QUIC rely on it.
  • Thinking a UDP port test with nc proves the service works.
  • Forgetting that firewalls must allow UDP separately.
  • Saying HTTP always uses TCP; HTTP/3 uses QUIC over UDP.

How to answer in the interview

"TCP is connection-oriented: it sets up a connection with a three-way handshake, and with sequence numbers, acknowledgements and retransmission it delivers a complete, ordered byte stream, plus flow and congestion control. That reliability costs latency. UDP is connectionless: it sends datagrams with no guarantee of delivery or order, but with minimal overhead. I'd use TCP for HTTP, SSH and databases, and UDP where speed matters more or the app handles reliability itself, like DNS, voice, video, gaming and QUIC, which underpins HTTP/3."

Likely follow-up questions

  • Why does DNS switch to TCP? For responses too large for UDP (truncated flag set, common with DNSSEC), and for zone transfers.
  • What is head-of-line blocking? One lost TCP segment stalls all later data; QUIC avoids it across streams.
  • How do you troubleshoot UDP? tcpdump on both ends, since there's no handshake to confirm reachability.
