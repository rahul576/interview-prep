How do null values, conditional expressions, try and can help write flexible Terraform modules?

Terraform · concept · levels entry, mid, senior

In one line

null means "omit this argument" so the provider default applies, conditionals (cond ? a : b) choose values or toggle resources, try returns the first expression that does not error, and can tests validity, mostly in validation; use them for flexible modules but keep expressions readable.

Detailed explanation

null as omission. When an argument is set to null, Terraform behaves as if it was not written at all. A module can therefore declare optional inputs with default = null and pass them straight to a resource: if the caller does not set it, the provider default applies, and you do not need two versions of the resource block. Combined with optional() object attributes (with defaults, since Terraform 1.3), this makes rich, typed inputs comfortable.

Conditional expressions. condition ? true_value : false_value picks between values, for example a premium SKU only in production. The classic toggle is count = var.enabled ? 1 : 0, or for_each = var.enabled ? toset(["this"]) : toset([]). Both branches must have compatible types.

try. try(expr1, expr2, ...) evaluates expressions in order and returns the first one that does not produce an error. It is ideal for deeply optional input, such as try(var.settings.backup.retention_days, 7), where any level might be missing. It only catches dynamic errors like missing attributes or invalid indexes, not syntax errors.

can. can(expr) returns true if the expression evaluates without error. It shines in variable validation: can(cidrhost(var.cidr, 0)) checks a valid CIDR, can(regex(...)) checks a naming pattern.

The caution: these tools make it easy to write clever one-liners that hide bugs. try in particular can swallow typos and silently return the default. Prefer typed inputs with optional() defaults, and name intermediate locals.

How it works

  1. Declare inputs with types, optional() attributes and null defaults.
  2. Pass optional values directly; null means provider default.
  3. Use conditionals for environment-dependent values and toggles.
  4. Use try for safe access to optional nested data.
  5. Use can inside validation blocks to reject bad input early.

Example

variable "cidr" {
  type = string
  validation {
    condition     = can(cidrhost(var.cidr, 0))
    error_message = "cidr must be a valid IPv4 CIDR block."
  }
}

variable "settings" {
  type    = any
  default = {}
}

resource "azurerm_postgresql_flexible_server" "db" {
  # ...
  sku_name              = var.environment == "prod" ? "GP_Standard_D4ds_v5" : "B_Standard_B1ms"
  backup_retention_days = try(var.settings.backup.retention_days, 7)
  zone                  = var.zone   # default = null -> provider decides
}

Common mistakes

  • Using try to hide typos in attribute names.
  • Conditionals with mismatched types between branches.
  • type = any everywhere instead of typed objects with optional().
  • Nested ternaries that nobody can review.

How to answer in the interview

"Setting an argument to null means omit it, so the provider default applies; modules can expose optional inputs with default null and pass them straight through. Conditionals pick values, like a bigger SKU in prod, or toggle resources with count equals enabled ? 1 : 0. try returns the first expression that doesn't error, which is handy for optional nested settings with a default, and can returns true or false, which I use in validation blocks, for example checking a CIDR with cidrhost. I use them for flexibility but keep expressions readable with named locals."

Likely follow-up questions

  • How do you reference a count = 0 or 1 resource? one(resource.x[*].id) or try(resource.x[0].id, null).
  • try versus optional()? optional() with defaults is typed and explicit; prefer it for module inputs.
  • Can validation reference other variables? Yes, since Terraform 1.9.
