How should MCP tool error messages be written so an agent can recover?

MCP Servers · concept · levels mid, senior

In one line

Return tool failures as results with isError: true, never crashes; explain what went wrong in plain language, how to fix it or which tool to use next, whether it is retryable or permanent, and include the needed identifiers but no stack traces, internals or secrets.

Detailed explanation

Agents recover from errors surprisingly well, if the error tells them what to do. Tool errors are part of the model's context, so they are effectively instructions for the next step.

Use isError, not exceptions. Unhandled exceptions may become JSON-RPC protocol errors that never reach the model, or crash a stdio server. Catch failures and return a result with isError: true and a text explanation.

Plain language plus a fix. Compare "ValidationError at line 42" with:

  • "start_date must be YYYY-MM-DD; you sent '20/11/2026'."
  • "No customer found for asha@example.com. Use search_customers with part of the name."
  • "This project has 1,200 open issues; add a status or assignee filter."

The second set gives the model a clear next action: fix an argument, call another tool, or narrow the query.

Retryable versus permanent. Distinguish transient problems ("Upstream billing API is temporarily unavailable; retry in about 30 seconds") from permanent ones ("Permission denied: your role cannot view salary data"). For permanent errors, say explicitly that retrying will not help and that the agent should tell the user, ideally with what they can do (request access from a named team). Some servers include a structured retryable flag and retry_after_seconds in structured content.

Include what the model needs, exclude what it doesn't. Include relevant identifiers and values (order number, valid enum values). Exclude stack traces, internal hostnames, SQL, file paths, tokens or secrets: they waste tokens, rarely help, and leak internals that could be exfiltrated via prompt injection. Log full details server-side with a correlation id and include only that id in the message.

Well-written errors make agents dramatically more reliable without changing the model.

How it works

  1. Catch exceptions at the tool boundary.
  2. Map them to categories: invalid input, not found, conflict, permission, rate limit, upstream outage.
  3. Write a message: what, why, how to fix, retryable or not.
  4. Log details with a correlation id.
  5. Return isError: true with the message (and optional structured fields).

Example

def tool_error(msg: str, retryable: bool = False, retry_after: int | None = None, ref: str = ""):
    return CallToolResult(isError=True,
        content=[TextContent(type="text", text=f"{msg} (ref {ref})")],
        structuredContent={"retryable": retryable, "retry_after_seconds": retry_after})

try:
    invoice = billing.get(invoice_no)
except NotFound:
    return tool_error(f"Invoice {invoice_no} not found. Invoice numbers look like INV-2026-00123; "
                      "use search_invoices with the customer email.")
except Forbidden:
    return tool_error("Permission denied: your role cannot view invoices for this region. "
                      "Do not retry; tell the user to request access from Finance Ops.")
except UpstreamUnavailable:
    ref = log_exception()
    return tool_error("Billing system temporarily unavailable.", retryable=True, retry_after=30, ref=ref)

Common mistakes

  • Raw stack traces or SQL in error text.
  • Generic "Something went wrong".
  • Not distinguishing retryable from permanent, causing retry loops.
  • Throwing exceptions that become protocol errors invisible to the model.

How to answer in the interview

"Execution errors should come back as a result with isError set, never as a crash, so the model sees them. The message explains in plain language what went wrong and how to fix it: the date must be YYYY-MM-DD, no customer for that email so use search_customers, or too many results so add a status filter. It distinguishes retryable errors, like a temporary outage with a suggested wait, from permanent ones like permission denied, where the agent should stop and tell the user. It includes the identifiers the model needs but no stack traces, hostnames, SQL or secrets. Good errors make agents much more reliable without changing the model."

Likely follow-up questions

  • Permission denied so the agent explains correctly? State the missing permission, say not to retry, and tell the user how to get access.
  • Should errors be structured? Text for the model, plus structured fields like retryable for client code.
  • How do you find bad errors? Review agent transcripts where tasks failed after an error.
