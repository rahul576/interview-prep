What is the purpose of an embedded Tomcat server?

Spring Boot · concept · levels entry

In one line

An embedded server runs Tomcat (or Jetty, Undertow, Netty) inside the application process as a library, so the service is a single executable jar started with java -jar, carrying its own server version and configuration, which is ideal for containers and microservices.

Detailed explanation

Traditionally you installed Tomcat or an application server on a machine and deployed several WAR files into it. The server's version, configuration and lifecycle were managed separately from the applications, and applications sharing one server could conflict over libraries, memory and restarts.

With Spring Boot, Tomcat is just a dependency. When the application starts, Boot's ServletWebServerFactory creates and starts the server programmatically, registers the DispatcherServlet and filters, and listens on server.port. The result is a self-contained process: the jar includes the server, the app and its libraries, so "it works on my machine" really means the same runtime in every environment.

This fits modern deployment. A Docker image just needs a JRE and the jar (or layered jar). Each microservice can choose its own server version and tuning, scale horizontally by running more instances, and restart independently. Configuration is done through properties: server.port, server.tomcat.threads.max, server.tomcat.max-connections, server.ssl.*, server.compression.enabled, HTTP/2 and graceful shutdown. With spring.threads.virtual.enabled=true (Java 21+), Tomcat handles requests on virtual threads.

You can swap servers by changing starters: Jetty or Undertow for servlet apps, while WebFlux uses Reactor Netty by default. A WAR deployment to an external server is still possible when an organisation mandates a shared application server.

How it works

  1. The web starter adds embedded Tomcat to the classpath.
  2. Auto-configuration creates a TomcatServletWebServerFactory.
  3. During context refresh, the factory starts Tomcat and registers servlets and filters.
  4. Tomcat listens on server.port and serves requests with its thread pool (or virtual threads).
  5. On shutdown, Boot stops the server, gracefully if configured.

Example

server:
  port: 8080
  shutdown: graceful
  compression:
    enabled: true
  tomcat:
    threads:
      max: 200
    max-connections: 8192
    connection-timeout: 5s
FROM eclipse-temurin:21-jre
COPY target/orders.jar /app/orders.jar
ENTRYPOINT ["java", "-jar", "/app/orders.jar"]

Common mistakes

  • Tuning threads.max very high instead of fixing slow downstream calls.
  • Running several apps in one JVM out of habit from WAR days.
  • Using shell wrappers that swallow SIGTERM, breaking graceful shutdown.
  • Thinking WebFlux runs on Tomcat by default.

How to answer in the interview

"With an embedded server, Tomcat is a library inside my application, started by Spring Boot, rather than a separate server I deploy WARs into. The whole service is one executable jar with its own server version and configuration through properties like server.port and server.tomcat.threads.max. That makes each microservice self-contained, easy to put in a Docker image and scale horizontally, and avoids conflicts between applications sharing a server. I can swap to Jetty or Undertow by changing starters, and WebFlux uses Netty."

Likely follow-up questions

  • When would you still deploy a WAR? When the organisation runs a managed shared application server or a platform requires it.
  • How do you enable HTTPS? server.ssl.* properties or SSL bundles, or terminate TLS at an ingress.
  • How many threads does Tomcat use? Default max 200 platform threads, unless virtual threads are enabled.
