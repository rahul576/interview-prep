How do you build Docker images efficiently in a CI pipeline?

Docker · concept · levels mid

In one line

Build with BuildKit/buildx and a remote layer cache (--cache-from/--cache-to to a registry or the GitHub Actions cache), tag with the commit SHA, scan and sign, push once and promote, and avoid privileged Docker-in-Docker by using rootless builders such as BuildKit rootless, kaniko or buildah.

Detailed explanation

CI runners are usually ephemeral: each job starts with an empty Docker cache, so without help every build downloads base images and reinstalls all dependencies. BuildKit, via docker buildx build, can export its cache to an external location and import it on the next run. --cache-to type=registry,ref=...:buildcache,mode=max stores all intermediate layers in a registry, and type=gha uses GitHub Actions' cache service. Combined with a Dockerfile that installs dependencies before copying source, typical builds reuse most layers.

Each build is tagged with an immutable identifier, typically the commit SHA, plus semantic version tags for releases. In the same pipeline the image is scanned (Trivy, Grype, Docker Scout) with a policy that fails on critical issues, an SBOM and provenance attestation are generated, and the image is signed with cosign (Sigstore), often keyless through OIDC. It is pushed once, and the same digest is promoted from dev to staging to production, never rebuilt per environment, so what was tested is what runs.

Where builds happen matters for security. Mounting the host's /var/run/docker.sock into CI jobs gives every job root on the build node and lets jobs see each other's containers. Docker-in-Docker needs --privileged, which disables most isolation. On Kubernetes-based runners, prefer rootless BuildKit, kaniko (Google archived the original project in 2025; maintained forks exist) or buildah, or a dedicated remote BuildKit service. Multi-platform images can be built with --platform using QEMU or native ARM runners.

How it works

  1. Checkout and set up buildx.
  2. Authenticate to the registry with short-lived credentials (OIDC).
  3. Build with cache import/export, tag with the SHA.
  4. Scan, generate SBOM and provenance, sign.
  5. Push; deploy jobs reference the digest and promote it.

Example

# GitHub Actions
- uses: docker/setup-buildx-action@v3
- uses: docker/login-action@v3
  with: { registry: ghcr.io, username: ${{ github.actor }}, password: ${{ secrets.GITHUB_TOKEN }} }
- uses: docker/build-push-action@v6
  id: build
  with:
    push: true
    tags: ghcr.io/acme/orders:${{ github.sha }}
    cache-from: type=gha
    cache-to: type=gha,mode=max
    provenance: true
    sbom: true
- run: trivy image --exit-code 1 --severity CRITICAL ghcr.io/acme/orders:${{ github.sha }}
- run: cosign sign --yes ghcr.io/acme/orders@${{ steps.build.outputs.digest }}

Common mistakes

  • No cache export, making every CI build cold.
  • Rebuilding separately for each environment.
  • Mounting the host Docker socket into untrusted jobs.
  • Tagging only latest.

How to answer in the interview

"Runners usually start empty, so I use BuildKit through docker buildx with a remote cache, cache-from and cache-to pointing at the registry or the GitHub Actions cache, and a Dockerfile ordered so dependency layers rarely change. Each build is tagged with the commit SHA, scanned with Trivy, signed with cosign and pushed once, and the same digest is promoted through environments instead of rebuilding. On Kubernetes runners I avoid privileged Docker-in-Docker or mounting the host socket, and use rootless builders like BuildKit rootless, kaniko or buildah."

Likely follow-up questions

  • Risk of mounting the host Docker socket? Any job gets root on the node and can access other jobs' containers.
  • mode=max vs min cache? max exports all intermediate layers, min only final image layers.
  • How to build ARM images on x86? buildx with QEMU emulation or native ARM runners.
