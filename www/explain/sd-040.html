Design a distributed cache cluster like Redis Cluster or Memcached at large scale.

Classic Design Problems · design · levels senior, lead

In one line

A distributed cache partitions keys (hash slots or consistent hashing), routes via smart clients or a proxy, uses replicas with failover, bounds memory with eviction (LRU/LFU) and TTLs, mitigates hot keys with local caches or key splitting, and is never the source of truth.

Detailed explanation

Redis Cluster divides keys into 16,384 hash slots (CRC16(key) mod 16384) assigned to primaries; resharding moves slots. Memcached keeps nodes independent and relies on client-side consistent hashing. Clients either know the topology (smart clients follow MOVED redirects) or talk to a proxy (Envoy, Twemproxy) that hides it.

Each primary has replicas; on failure a replica is promoted. Replication is asynchronous, so a few writes may be lost: acceptable for a cache.

Memory is finite: TTLs on every key plus an eviction policy (allkeys-lru, allkeys-lfu). Hot keys overload one shard; mitigate with a short-TTL in-process cache, or key replication (store hot:key#1..#10, read a random one). Big keys (huge hashes/lists) block the single-threaded server; split them.

How it works

  1. App computes key → slot → node (or proxy does).
  2. Cache-aside read: hit → return; miss → DB → set with TTL.
  3. Writes → DB → delete cache key.
  4. Monitoring: hit ratio, evictions, memory, latency, hot keys (--hotkeys).

Example

CLUSTER KEYSLOT user:{42}:profile   # hash tags {42} keep related keys in one slot
SET user:{42}:profile "<json>" EX 3600

Common mistakes

  • No TTLs (memory fills with stale data).
  • Treating cache data as durable.
  • Multi-key operations across slots (use hash tags).
  • Cold cache after failover causing a DB stampede.

How to answer in the interview

"I'd run a Redis Cluster: keys map to hash slots spread across primaries with replicas and automatic failover; clients route by slot. Every key has a TTL and LFU eviction bounds memory. For hot keys I add a tiny in-process cache or replicate the key under several names. The database stays the source of truth, so the app must tolerate misses and node loss, with stampede protection."

Likely follow-up questions

  • Warm a new cluster? Replay recent read keys, or dual-read from old cluster during migration.
  • Hash tags? {…} part decides the slot so related keys co-locate.
  • LRU vs LFU? LFU better keeps consistently popular keys.
