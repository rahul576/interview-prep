What are the key design decisions when creating a production AKS cluster?

Azure Kubernetes (AKS) · concept · levels mid, senior

In one line

Decide networking (Azure CNI Overlay as default), node pool layout (system versus user pools across availability zones, autoscaling), identity (Entra ID integration, workload identity), API server access (private cluster or authorised IPs), and the upgrade and observability strategy, because several of these are hard to change later.

Detailed explanation

Networking is the most important early decision because it is hard to change. Azure CNI Overlay gives pods IPs from a private overlay CIDR, so the VNet only needs IPs for nodes, avoiding IP exhaustion; it is the recommended default. Classic Azure CNI (flat) gives pods VNet IPs, useful when other systems must reach pods directly, but consumes many addresses. Kubenet is legacy and on a retirement path. Azure CNI powered by Cilium adds eBPF-based networking and network policy. Also plan service CIDR, DNS, egress (NAT gateway or user-defined routing through a firewall) and ingress.

Node pools: a system node pool runs critical add-ons such as CoreDNS and metrics-server, tainted so application pods stay off; user node pools run workloads, possibly with different VM sizes, spot instances or GPUs. Spread pools across availability zones and enable the cluster autoscaler (or node auto-provisioning). Use the Standard tier for an uptime SLA on the API server.

Identity and access: enable Microsoft Entra ID integration with Azure RBAC for Kubernetes or Kubernetes RBAC mapped to Entra groups; disable local accounts. Pods use Entra Workload ID to access Azure resources without secrets. Grant AKS pull access to ACR through the kubelet identity.

Security: a private cluster or authorised IP ranges for the API server, Azure Policy for AKS (Gatekeeper) to enforce pod security, Defender for Containers, network policies, and image scanning.

Operations: choose an auto-upgrade channel (patch or stable) and a node OS upgrade channel, with planned maintenance windows, PodDisruptionBudgets and surge settings. Enable Container Insights, Managed Prometheus and Managed Grafana. Define everything as IaC.

How it works

  1. Plan VNet, subnets and pod/service CIDRs; choose CNI Overlay.
  2. Create the cluster (Standard tier) with Entra integration and local accounts disabled.
  3. Add a system pool and zone-spread user pools with autoscaling.
  4. Enable OIDC issuer and workload identity; attach ACR.
  5. Restrict API server access; enable Azure Policy and Defender.
  6. Configure upgrade channels, maintenance windows and monitoring.

Example

az aks create -g rg-aks-prod -n aks-prod --tier standard \
  --network-plugin azure --network-plugin-mode overlay --pod-cidr 192.168.0.0/16 \
  --vnet-subnet-id <nodes-subnet-id> --zones 1 2 3 \
  --nodepool-name system --node-count 3 --node-vm-size Standard_D4ds_v5 \
  --enable-aad --enable-azure-rbac --disable-local-accounts \
  --enable-oidc-issuer --enable-workload-identity \
  --enable-private-cluster --attach-acr acrprod \
  --auto-upgrade-channel stable --node-os-upgrade-channel NodeImage \
  --enable-azure-monitor-metrics
az aks nodepool add -g rg-aks-prod --cluster-name aks-prod -n apps \
  --mode User --zones 1 2 3 --enable-cluster-autoscaler --min-count 3 --max-count 15

Common mistakes

  • Flat Azure CNI in a small subnet, exhausting IP addresses.
  • Running application pods on the system node pool.
  • Public API server with no IP restrictions.
  • Never upgrading until the version falls out of support.
  • Storing Azure credentials as Kubernetes secrets instead of workload identity.

How to answer in the interview

"Networking first: Azure CNI Overlay is the recommended default because pods get IPs from an overlay range without exhausting the VNet, while classic Azure CNI gives pods VNet IPs; kubenet is legacy. I separate a system node pool for critical add-ons from user pools for workloads, spread across availability zones with the cluster autoscaler. Identity uses Entra ID integration with local accounts disabled, and workload identity for pods. For security I prefer a private cluster or authorised IP ranges, Azure Policy and ACR integration. Finally I plan upgrades with auto-upgrade channels, maintenance windows and PodDisruptionBudgets, and enable Container Insights and Managed Prometheus, all defined as IaC."

Likely follow-up questions

  • How do you upgrade an AKS cluster with minimal disruption? Control plane first, then node pools with max surge, PDBs and maintenance windows; or blue-green node pools.
  • How do you control egress? User-defined routing through Azure Firewall or a NAT gateway.
  • Why Standard tier? Financially backed API server SLA and higher scale limits.
