How do database indexes work, and what are their trade-offs?

Databases & SQL · concept · levels entry, mid

In one line

An index is a separate, usually B-tree, structure keeping column values sorted with pointers to rows, so lookups, range scans, joins and ORDER BY avoid full table scans; the cost is slower writes, extra storage and memory, composite indexes follow the leftmost-prefix rule, and you verify with EXPLAIN.

Detailed explanation

Without an index, WHERE email = ? forces the database to read every row: O(n). A B-tree (B+tree) index stores keys in sorted order in a shallow, wide tree; with hundreds of keys per page, even a billion rows need only 4-5 page reads, O(log n). Leaf entries point to the row (a heap TID in PostgreSQL) or, in MySQL InnoDB, secondary indexes store the primary key, and the table itself is a clustered index ordered by the primary key.

Because keys are sorted, B-trees also serve range queries (BETWEEN, >), prefix LIKE ('abc%'), ORDER BY and MIN/MAX without sorting, and speed up joins on foreign keys. Other index types exist: hash, GIN (full text, JSONB, arrays), GiST/BRIN in PostgreSQL, partial and expression indexes.

Trade-offs:

  • Every INSERT, UPDATE of an indexed column, and DELETE must also maintain each index: write amplification.
  • Indexes consume disk and buffer-cache memory.
  • Too many indexes slow writes and confuse the planner; unused indexes are pure cost.

Composite indexes (customer_id, created_at) are sorted by the first column, then the second. They serve WHERE customer_id = ?, WHERE customer_id = ? AND created_at > ?, and ORDER BY created_at within a customer, but not WHERE created_at > ? alone (leftmost prefix). Put equality columns first, then range or sort columns.

Why an index isn't used: low selectivity (a status with 3 values: a scan may be cheaper), a function or cast on the column (WHERE LOWER(email) = ? unless you create an expression index), leading-wildcard LIKE, implicit type conversion, OR conditions, or stale statistics.

A covering index includes all columns a query needs, enabling an index-only scan (INCLUDE in PostgreSQL/SQL Server). Always confirm with EXPLAIN / EXPLAIN ANALYZE.

How it works

  1. The database builds the B-tree from the column values.
  2. A query predicate is matched against available indexes by the planner using statistics.
  3. The engine descends the tree to the first matching key.
  4. It scans leaf entries in order for ranges.
  5. It fetches rows from the table, unless the index covers the query.
  6. On writes, the engine updates every affected index.

Example

CREATE INDEX idx_orders_customer_created
    ON orders (customer_id, created_at DESC) INCLUDE (status, total);

EXPLAIN ANALYZE
SELECT status, total FROM orders
WHERE customer_id = 42 AND created_at > now() - interval '30 days'
ORDER BY created_at DESC;
-- Index Only Scan using idx_orders_customer_created on orders ...

-- Not usable for this: leftmost column missing
EXPLAIN SELECT * FROM orders WHERE created_at > now() - interval '1 day';

-- Function on column: needs an expression index
CREATE INDEX idx_users_email_lower ON users (LOWER(email));

Common mistakes

  • Indexing every column "to be safe".
  • Wrong column order in composite indexes.
  • Wrapping indexed columns in functions or casting them.
  • Not indexing foreign keys used in joins and cascades.
  • Trusting assumptions instead of EXPLAIN ANALYZE on realistic data.

How to answer in the interview

"An index is a separate structure, usually a B-tree, that keeps column values sorted with pointers to the rows, so the database finds rows in logarithmic time instead of scanning the whole table; it also helps ORDER BY, ranges and joins. The trade-off is that every insert, update and delete must maintain the index, so writes slow down, and indexes take storage and memory. For composite indexes order matters: they serve queries on the leftmost prefix, so I put equality columns first, then range or sort columns. Functions on indexed columns or low selectivity often prevent index use, so I always check the plan with EXPLAIN ANALYZE."

Likely follow-up questions

  • What is a covering index? One containing all columns a query needs, allowing an index-only scan.
  • Clustered vs non-clustered? Clustered stores rows in index order (InnoDB primary key); non-clustered points to rows.
  • Why might the planner ignore an index? Low selectivity, stale statistics or non-sargable predicates.
