What are the common causes of slow Java applications?

JVM & Performance · concept · levels mid, senior

In one line

Most slow Java applications are slowed by I/O, not Java: slow or excessive database queries (missing indexes, N+1), remote calls made sequentially or without timeouts, then GC pressure and leaks, lock contention and exhausted pools, and finally inefficient code (algorithms, serialisation, logging) and cold JIT after startup.

Detailed explanation

Database. The most common culprit. Queries without suitable indexes do full scans; ORMs generate N+1 selects when lazy associations are accessed in a loop; endpoints fetch whole entities or thousands of rows when they need a few fields; missing pagination; long transactions holding locks. The fix starts with query logs, EXPLAIN plans and Hibernate statistics.

Remote calls. Calling three downstream services one after another adds their latencies; calling them without timeouts means one slow dependency ties up threads until the pool is exhausted and everything queues. Use timeouts, parallel calls (CompletableFuture, virtual threads), caching and circuit breakers.

Memory and GC. High allocation rates cause frequent young GCs; leaks or an undersized heap cause frequent full GCs with long pauses. Containers with the default 25% heap or a heap close to the limit are common sources.

Concurrency. synchronized methods on hot paths, a single shared lock, or contended data structures serialise threads. Pools that are too small (HikariCP connections, HTTP client connections, Tomcat threads) make requests wait. With virtual threads, pinning in older JDKs could also limit throughput when blocking inside synchronized (much improved in JDK 24).

Inefficient code. Wrong data structures (List.contains in a loop, giving O(n²)), heavy JSON or XML serialisation of large graphs, excessive or synchronous logging, regexes compiled per call, exceptions used for control flow, and creating expensive objects (ObjectMapper) per request.

Startup and warm-up. Right after deployment, code is interpreted and the JIT is compiling, so latency is high for the first minutes.

Environment. CPU throttling from container limits, noisy neighbours, DNS or TLS handshakes without connection reuse.

How it works

  1. Measure: latency percentiles per endpoint, APM traces, metrics.
  2. Use distributed tracing to see where time goes (DB, HTTP, code).
  3. Check database: slow query log, plans, query counts per request.
  4. Check pools, GC logs, thread dumps for contention.
  5. Profile CPU and allocations for code-level hotspots.
  6. Fix the biggest contributor first and re-measure.

Example

// N+1: one query for orders, then one per order for its customer
List<Order> orders = orderRepo.findByStatus(OPEN);
orders.forEach(o -> dto(o, o.getCustomer().getName()));   // lazy load each time

// Fix: fetch join or entity graph
@Query("select o from Order o join fetch o.customer where o.status = :s")
List<Order> findWithCustomer(@Param("s") Status s);
# Timeouts and pool sizing (Spring Boot)
spring.datasource.hikari.maximum-pool-size: 20
spring.datasource.hikari.connection-timeout: 2000

Common mistakes

  • Guessing instead of tracing where time is spent.
  • Blaming GC or Java when the database is the bottleneck.
  • Raising thread pool sizes when the downstream resource is saturated.
  • Testing with tiny data sets that hide N+1 and missing indexes.

How to answer in the interview

"In my experience most slowness comes from I/O rather than Java itself. The most common cause is the database: slow queries, missing indexes, N+1 selects from the ORM and fetching too much data. Next are remote calls made sequentially or without timeouts, so one slow dependency exhausts threads. Then memory: high allocation rates cause GC pressure, and leaks lead to frequent full GCs. Then concurrency: lock contention, synchronized hot paths and connection or thread pools that are too small. Finally inefficient code, like wrong data structures, heavy serialisation, excessive logging or regexes compiled in loops, plus cold JIT right after startup. I always start with tracing and metrics to find which one it is."

Likely follow-up questions

  • How would you tell whether a slowdown is caused by GC or by the database? Correlate latency with GC pause metrics and logs versus DB query times in traces; thread dumps show threads waiting on sockets for DB issues.
  • How do you detect N+1? Hibernate statistics, SQL logging per request, or APM traces with many identical queries.
  • How do you size a connection pool? From measured concurrency and DB capacity, usually small; more connections can make the database slower.
