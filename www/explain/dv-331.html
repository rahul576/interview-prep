A web application is down. What are your first troubleshooting steps?

Troubleshooting · scenario · levels entry

In one line

Confirm scope and impact and what changed, check monitoring and recent deployments, work down the stack (load balancer, processes, ports, resources, database), read the logs, and restore service first — rollback or restart — while communicating, then find the root cause.

Detailed explanation

When an application is down, a structured approach beats random guessing. The first questions are about scope and impact: is it down for everyone or some users, one region or all, since what time, and what changed recently? Most outages follow a deployment, configuration change, certificate expiry or infrastructure change, so the deployment history is often the fastest clue.

Next, monitoring: dashboards and alerts show error rates (for example a jump in HTTP 5xx), latency, traffic and resource usage, and when exactly the problem started. Synthetic checks or uptime monitors confirm what users see.

Then work down the stack, from the outside in:

  • DNS and certificate: does the name resolve, has the TLS certificate expired?
  • Load balancer or ingress: are backends healthy, are health checks failing?
  • Application: are the processes or pods running, restarting, or crash-looping? Is the port listening?
  • Server resources: CPU, memory, disk full (a very common cause), file descriptors.
  • Dependencies: can the app reach its database, cache and external APIs?

Logs — application, web server and system — around the start time usually show the actual error.

The priority is restoring service: roll back the last deployment, restart a stuck component, fail over or scale up. While doing so, keep people informed with short status updates. Change one thing at a time so you know what fixed it. After recovery, find and fix the root cause and write a short postmortem.

How it works

  1. Confirm impact, start time and recent changes.
  2. Check dashboards, alerts and deployment history.
  3. Test from outside: DNS, TLS, load balancer health.
  4. Check processes, ports, resources and dependencies.
  5. Read logs around the start time.
  6. Restore with rollback, restart or failover; communicate.
  7. Root cause and postmortem afterwards.

Example

curl -I https://shop.example.com            # 502 Bad Gateway
systemctl status shop-api                   # failed: exit code 1
journalctl -u shop-api --since "10 min ago" | tail -20
df -h                                       # /var 100% used
ss -tlnp | grep 8080

In this example, the disk filled with logs, the service crashed on startup, and freeing space plus fixing log rotation restored it.

Common mistakes

  • Jumping to a fix before understanding scope and recent changes.
  • Changing several things at once.
  • Forgetting to communicate status to the team and users.
  • Stopping after the restart without finding the root cause.

How to answer in the interview

"First I confirm the scope: is it down for everyone, since when, and what changed recently, because most outages follow a deployment or config change. I check dashboards for error rates, latency and resources, and the deployment history. Then I work down the stack: is DNS and the certificate fine, is the load balancer healthy, are the processes or pods running and listening, is the server out of CPU, memory or disk, can the app reach its database. I read the logs around the start time. My priority is restoring service, for example rolling back the last deployment, while keeping people informed, and then I find the root cause."

Likely follow-up questions

  • Why avoid several changes at once? You can't tell which one fixed it, and you may introduce new problems.
  • What if there was no recent change? Look at expiring certificates, full disks, traffic spikes and dependency outages.
  • How do you communicate? Short regular updates in an incident channel or status page: impact, actions, next update time.
