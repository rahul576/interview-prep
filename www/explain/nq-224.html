What is service discovery?

Microservices · concept · levels mid

In one line

Service discovery lets clients find the current, healthy instances of a service by name instead of hard-coded addresses, using a service registry with registration and heartbeats, in either client-side (Eureka, Consul + client load balancer) or server-side (load balancer, Kubernetes Service and DNS) form.

Detailed explanation

In a microservice platform, instances are dynamic: autoscaling adds and removes them, deployments replace them, failed ones restart on other hosts with new IP addresses. A configuration file listing 10.0.3.17:8080 would be wrong within minutes. Service discovery provides an up-to-date mapping from a logical service name (orders) to the network locations of its healthy instances.

The central piece is a service registry. Instances are registered when they start, either by themselves (self-registration, such as the Eureka or Consul client in a Spring Boot app) or by the platform (third-party registration, as in Kubernetes). They prove they are alive with heartbeats or health checks; instances that stop responding are removed, and instances shutting down gracefully deregister.

There are two lookup styles:

  • Client-side discovery: the calling service queries the registry (and caches the result), then picks an instance itself using a client-side load balancer. In Spring Cloud that is Eureka or Consul plus Spring Cloud LoadBalancer, used via @LoadBalanced clients or lb:// URIs. Clients can make smart choices (zone affinity), but every language needs a client library.
  • Server-side discovery: the client calls a stable address, and a load balancer or the platform resolves and routes. In Kubernetes, a Service gets a stable virtual IP and DNS name (orders.shop.svc.cluster.local, or just orders in the same namespace). The control plane keeps its EndpointSlices updated with pods that pass readiness probes, and kube-proxy or a service mesh routes traffic. Cloud load balancers with target groups work similarly.

On Kubernetes, server-side discovery is built in and language-neutral, so Eureka is usually unnecessary there. Eureka and Consul remain useful on VMs, in hybrid environments or across clusters.

How it works

  1. Instance starts and becomes ready.
  2. It is registered with name, address and health.
  3. Heartbeats or probes keep the entry current.
  4. Client resolves the service name (registry lookup or DNS).
  5. A load balancer (client or server side) picks a healthy instance.
  6. Dead or terminating instances are removed.

Example

# Kubernetes: server-side discovery
apiVersion: v1
kind: Service
metadata: { name: orders, namespace: shop }
spec:
  selector: { app: orders }
  ports: [ { port: 80, targetPort: 8080 } ]
// Caller simply uses the DNS name
RestClient orders = RestClient.builder().baseUrl("http://orders").build();

// Client-side alternative with Spring Cloud LoadBalancer + Eureka/Consul
@Bean @LoadBalanced
RestClient.Builder lbBuilder() { return RestClient.builder(); }
// lbBuilder.baseUrl("http://order-service") -> instance chosen by the client

Common mistakes

  • Hard-coding IPs or hostnames per environment.
  • Running Eureka on Kubernetes without a reason.
  • Missing readiness probes, so traffic reaches pods that are not ready.
  • Ignoring client-side cache staleness after instances die.

How to answer in the interview

"Instances start, stop and move all the time, so hard-coded addresses do not work. Service discovery lets a client find the current healthy instances of a service by name. Instances register in a service registry with their address and keep sending heartbeats, and dead ones are removed. With client-side discovery, the client queries a registry such as Eureka or Consul and load-balances itself with Spring Cloud LoadBalancer. With server-side discovery, the client calls a stable address and the platform routes: in Kubernetes, a Service with a DNS name like http://orders does this, so Eureka is usually unnecessary there."

Likely follow-up questions

  • Why is Eureka often not needed on Kubernetes? Services, DNS and readiness-based endpoints already provide registration, discovery and load balancing.
  • What happens if the registry is down? Clients use cached instance lists; new registrations wait.
  • How does a headless Service differ? It has no virtual IP; DNS returns pod IPs directly, used by StatefulSets or client-side balancing.
