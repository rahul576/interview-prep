Why is HashMap not thread-safe? Explain a real-world problem caused by concurrent modifications.

Collections · scenario · levels senior, lead

In one line

HashMap has no synchronisation, so concurrent puts cause lost updates, wrong size and corrupted state during resize; in Java 7 a concurrent resize could even form a cycle and spin a later get at 100% CPU. A classic case is a HashMap cache in a singleton Spring bean; fix it with ConcurrentHashMap or immutable maps swapped atomically.

Detailed explanation

HashMap's put is a sequence of plain reads and writes: compute the index, read the bucket head, walk the chain, link a new node, increment size, maybe resize. None of these steps are atomic and there are no memory barriers. If two threads put into the same empty bucket at the same moment, both see null and both write the head; one node is silently overwritten, a lost update. size++ can also lose increments, so size() lies.

Resizing is the most dangerous moment. One thread allocates a new table and moves nodes while another writes to the old table or reads a half-built new one; entries can disappear or be duplicated. In Java 7 and earlier, resize transferred each chain by head insertion, which reversed its order. Two threads resizing concurrently could link node A → B and B → A, creating a circular list. Any later get on that bucket looped forever, and servers went to 100% CPU with threads stuck in HashMap.get in the thread dump. Java 8 preserves order during resize, so the infinite loop is gone, but data loss remains.

There is also a visibility problem: without happens-before, readers may never see other threads' entries.

A real-world example: a Spring @Service (a singleton) holds private Map<String, Rate> cache = new HashMap<>() and lazily fills it per request. Under load, rates go missing, are recomputed repeatedly, or on an old JVM requests hang and CPU pegs.

How it works

  1. Thread A and B compute the same bucket index.
  2. Both read head = null.
  3. A writes node X; B writes node Y over it; X is lost.
  4. Size threshold crossed; both start resizing.
  5. Interleaved transfers corrupt links (cycle in Java 7, lost entries in Java 8+).

Example

@Service
class RateService {
    // BUG: shared mutable HashMap in a singleton
    // private final Map<String, Rate> cache = new HashMap<>();

    private final ConcurrentMap<String, Rate> cache = new ConcurrentHashMap<>();

    Rate rate(String ccy) {
        return cache.computeIfAbsent(ccy, this::loadRate); // atomic per key
    }
}

// Read-mostly config: build a new immutable map, publish via volatile
private volatile Map<String, String> config = Map.of();
void reload() { config = Map.copyOf(loadFromDb()); }

Common mistakes

  • Assuming "only reads after startup" when lazy filling still writes.
  • Fixing with synchronizedMap and then iterating without the lock.
  • Using containsKey then put on a ConcurrentHashMap.

How to answer in the interview

"HashMap has no synchronisation, so two threads putting at once can both read the same bucket and one entry overwrites the other, size goes wrong, and a resize while another thread writes can lose entries or expose a half-built table. In Java 7 a concurrent resize could even link a bucket into a cycle, so a later get looped forever at 100 percent CPU. A classic real case is a HashMap used as a lazy cache in a singleton Spring bean: under load lookups hang or recompute. I fix it with ConcurrentHashMap and computeIfAbsent, or with immutable maps that are rebuilt and swapped atomically through a volatile reference."

Likely follow-up questions

  • Why is synchronizedMap often worse? One global lock serialises all access, and compound operations and iteration still need manual locking.
  • How would you spot it in production? Thread dumps with many threads RUNNABLE in HashMap.get/put, or inconsistent cache metrics.
  • Is a HashMap safe if only read after construction? Yes, if safely published (final field or volatile) and never modified.
