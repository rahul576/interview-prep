How does Spring AOP work through proxy objects?

Spring Framework · concept · levels mid

In one line

Spring AOP wraps a matching bean in a proxy during creation (an auto-proxy BeanPostProcessor); callers receive the proxy, which runs the advice chain and then delegates to the target, so only calls through the proxy are intercepted, and self-invocation, private and final methods bypass it.

Detailed explanation

When the container creates a bean, an auto-proxy creator such as AnnotationAwareAspectJAutoProxyCreator (a BeanPostProcessor) checks, in postProcessAfterInitialization, whether any advisor applies to it: your @Aspect pointcuts, @Transactional, @Cacheable, @Async, method security. If so, it does not publish the bean itself. It creates a proxy that either implements the same interfaces (JDK dynamic proxy) or subclasses the class (CGLIB, Spring Boot's default), holds a reference to the real target, and registers that proxy in the container. Every other bean that injects it receives the proxy.

When a caller invokes a method, the proxy builds a chain of interceptors (MethodInterceptors) for that method: for example security check, then transaction interceptor, then your logging advice. Each interceptor does its "before" work and calls proceed(), the last one invokes the real method on the target, and control unwinds back through the chain for "after" work such as commit or logging the result.

The consequences follow directly from the design:

  • Self-invocation: inside the target, this.otherMethod() is a plain Java call on the target object, not the proxy, so advice on otherMethod does not run.
  • Private methods cannot be overridden or delegated, so they are never intercepted. Final methods, and with CGLIB final classes, cannot be overridden either.
  • Static methods and objects created with new are not proxied.
  • Code in @PostConstruct runs before the proxy exists.

How it works

  1. Bean is instantiated and initialised.
  2. Auto-proxy creator finds applicable advisors.
  3. It creates a JDK or CGLIB proxy around the target.
  4. The proxy is registered and injected everywhere.
  5. Method call: proxy runs interceptor chain, then calls the target, then unwinds.

Example

@Service
public class ReportService {
    @Cacheable("reports")
    public Report load(long id) { return expensiveQuery(id); }

    public List<Report> loadAll(List<Long> ids) {
        return ids.stream().map(this::load).toList();   // self-invocation: no caching!
    }
}

// Fix: move load() to another bean, or call through the proxy
@Service
class ReportFacade {
    private final ReportService reports;               // proxy
    ReportFacade(ReportService reports) { this.reports = reports; }
    List<Report> loadAll(List<Long> ids) { return ids.stream().map(reports::load).toList(); }
}

Common mistakes

  • Expecting this.method() to trigger advice.
  • Annotating private or final methods.
  • Comparing getClass() of a bean with its declared class (CGLIB proxies are subclasses).
  • Thinking advice runs for objects created with new.

How to answer in the interview

"When a bean matches a pointcut, an auto-proxy BeanPostProcessor wraps it in a proxy that implements the same interfaces or subclasses the class, and that proxy is what other beans receive. When a caller invokes a method, the proxy runs the chain of applicable advice, like opening a transaction or logging, then calls the real method on the target, and runs the after-advice on the way back. So only calls coming through the proxy are intercepted: self-invocation with this bypasses advice, and private and final methods can't be advised."

Likely follow-up questions

  • Work around self-invocation? Split into another bean, inject a self proxy with @Lazy, use AopContext.currentProxy() with exposeProxy, or AspectJ weaving.
  • How to tell if a bean is proxied? AopUtils.isAopProxy(bean).
  • Order of multiple advisors? By @Order/Ordered; lower values run first (outermost).
