Your service crashes with OutOfMemoryError every few days. How do you find the memory leak?

JVM & Performance · scenario · levels senior, lead

In one line

Confirm it is a leak (old-gen usage after GC keeps rising), capture a heap dump (HeapDumpOnOutOfMemoryError or jcmd GC.heap_dump), analyse it in Eclipse MAT with the dominator tree and paths to GC roots, then fix typical causes: static or unbounded collections and caches, ThreadLocals, listeners, unclosed resources.

Detailed explanation

Leak or under-sizing? A healthy service shows a sawtooth: memory rises, a collection drops it back to a stable baseline. A leak shows the baseline after each GC creeping upward over hours or days until OOM. If the baseline is flat but peaks hit the limit, the heap is too small for the workload, not leaking. Micrometer metrics such as jvm.memory.used for the old-gen pool, or GC logs, show this trend. Also read the OOM message: "Java heap space" is a heap issue; "Metaspace", "Direct buffer memory" or "unable to create native thread" point elsewhere, and a Kubernetes OOMKilled without a Java error is usually native memory or container sizing.

Capture evidence. Add -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps (on a persistent volume), so the next crash leaves an .hprof. Better, take a dump before the crash while usage is high: jcmd <pid> GC.heap_dump /dumps/heap.hprof. A dump triggers a full GC and pauses the process for seconds, so take it from an instance removed from the load balancer if possible. Two dumps hours apart make growth obvious. A quick jcmd <pid> GC.class_histogram comparison between two points is a cheap first look.

Analyse. Open the dump in Eclipse MAT. The Leak Suspects report often points directly at the problem. The dominator tree sorts objects by retained size, the memory that would be freed if that object were gone. From a suspicious object, use Path to GC Roots (excluding weak references) to see the chain keeping it alive, for example a static field in a class holding a HashMap with millions of entries.

Typical causes. Static maps used as caches without eviction; caches keyed by unbounded values (session ids, request URLs); ThreadLocal values never removed in pooled threads; listeners or callbacks registered and never unregistered; unclosed streams, connections or ResultSets; queues growing because consumers fall behind; large in-memory result sets.

After the fix. Replace hand-made caches with Caffeine (size and time bounds), add try-with-resources, and set alerts on old-gen usage after GC and GC time.

How it works

  1. Plot old-gen usage after GC over days to confirm a leak.
  2. Enable heap dump on OOM and take manual dumps at high usage.
  3. Compare class histograms between two times.
  4. Open the dump in MAT: leak suspects, dominator tree, retained sizes.
  5. Follow paths to GC roots to find the owning reference.
  6. Fix, deploy, and verify the post-GC baseline stays flat.

Example

java -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps \
     -XX:+ExitOnOutOfMemoryError -jar orders.jar

jcmd 4211 GC.class_histogram | head -20
jcmd 4211 GC.heap_dump /dumps/orders-$(date +%s).hprof
// Typical culprit found via MAT: static unbounded cache
private static final Map<String, CustomerView> CACHE = new HashMap<>();
// Fix
private static final Cache<String, CustomerView> CACHE = Caffeine.newBuilder()
    .maximumSize(50_000).expireAfterWrite(Duration.ofMinutes(10)).build();

Common mistakes

  • Increasing -Xmx and calling it fixed; it only delays the crash.
  • Writing dumps to ephemeral container storage that disappears on restart.
  • Looking only at shallow size instead of retained size.
  • Ignoring ThreadLocals in thread pools.

How to answer in the interview

"First I confirm it's a leak: in the metrics, heap usage after full GC keeps growing over days, rather than the heap being simply too small. I enable HeapDumpOnOutOfMemoryError with a HeapDumpPath on a persistent volume, or take a dump with jcmd GC.heap_dump while usage is high. Then I open it in Eclipse MAT, check the leak suspects report and the dominator tree by retained size, and follow the path to GC roots to see who keeps the objects alive. The usual causes are static maps or caches without eviction, ThreadLocals not removed in thread pools, listeners never unregistered and unclosed resources. I fix it, often with a bounded Caffeine cache, and add an alert on old-gen usage after GC."

Likely follow-up questions

  • How would you distinguish a heap leak from a native memory or Metaspace leak? Check the OOM message and pool metrics; for native, use Native Memory Tracking (-XX:NativeMemoryTracking=summary, jcmd VM.native_memory) and compare process RSS to heap.
  • What is retained size? Memory freed if that object became unreachable, including everything only it references.
  • Is a heap dump safe in production? It pauses the JVM and can contain personal data, so take it carefully and protect the file.
