Offline and online features for the same metric disagree, and production performance lags offline results. What do you check?

MLOps · scenario · levels senior, lead

In one line

This is training-serving skew: check definitional differences (windows, time zones, null handling, rounding), data timing such as late-arriving events seen offline but not online, then measure it by logging online feature vectors at inference time and comparing with offline values for the same entity and timestamp, looking at the distribution of differences.

Detailed explanation

When offline metrics look great but production lags, and the "same" feature differs between paths, the model is effectively being served different inputs from those it learned on.

Definitional differences are the most common cause, especially when the offline feature is SQL in the warehouse and the online one is Java or Flink code written by another team: a 30-day window inclusive versus exclusive of today, UTC versus local time and daylight saving, how nulls become zeros or defaults, rounding, deduplication of events, currency conversion rates, or case and whitespace handling of categories.

Data timing: offline pipelines run later and see late-arriving events (delayed mobile uploads, batch files from partners), so offline features are more complete than what the online system knew at prediction time. Training on the complete version is a form of leakage. Stale online features due to pipeline lag have the same effect.

The strongest approach is measurement, not inspection. Log the exact feature vector used online at inference, recompute the offline feature for the same entity and as-of timestamp, and compute per-feature differences: mismatch rate, mean absolute difference and distribution. That quickly shows which features diverge, how often and by how much, and whether retraining or evaluating with the online values explains the performance gap.

The long-term fix is a single feature definition executed for both paths (a feature store or shared transformation code), training on logged online features where possible, and continuous skew monitoring.

How it works

  1. Enable logging of online feature vectors with entity ID and timestamp.
  2. Recompute offline features as of those timestamps.
  3. Join and compute per-feature mismatch statistics.
  4. Rank features by mismatch times importance.
  5. Inspect code for the top offenders: windows, time zones, nulls, late data.
  6. Fix definitions, unify code and add a skew monitor.

Example

skew = online_log.merge(offline_recomputed, on=["customer_id", "ts"], suffixes=("_on", "_off"))
for f in FEATURES:
    diff = (skew[f + "_on"] - skew[f + "_off"]).abs()
    print(f, "mismatch_rate=%.1f%%" % (100 * (diff > 1e-6).mean()), "p95_diff=%.2f" % diff.quantile(0.95))
# txn_count_30d   mismatch_rate=38.0%  p95_diff=4.00   <- window boundary / late events
# avg_amount_7d   mismatch_rate=0.4%   p95_diff=0.00

Common mistakes

  • Comparing a few examples by eye instead of measuring distributions.
  • Recomputing "online" values offline instead of logging what was actually served.
  • Two teams implementing the same feature in two languages.
  • Ignoring late-arriving data in training sets.

How to answer in the interview

"That's classic training-serving skew. I'd look for definitional differences: window boundaries, time zones, null and default handling, rounding and deduplication. Then timing: offline pipelines see late events that the online system didn't have. But mostly I'd measure: log the exact online feature vectors at inference time, compute offline values for the same entity and timestamp, and look at the distribution of differences per feature. That shows which features diverge and whether it explains the gap. Long term, one feature definition for both paths and continuous skew monitoring."

Likely follow-up questions

  • How would you prevent this class of bug for new features? Shared definitions via a feature store, skew tests in CI and monitoring.
  • Should you train on logged online features? Often yes, because they reflect what serving actually sees.
  • What if online is more correct than offline? Then fix the offline definition and retrain.
