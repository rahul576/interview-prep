What are the main types of class loaders?

JVM & Performance · concept · levels mid

In one line

The JVM has three built-in loaders, Bootstrap, Platform (formerly Extension) and Application/System, and frameworks add custom loaders by extending ClassLoader, such as Tomcat's per-web-app loader and Spring Boot's fat-jar loader.

Detailed explanation

The Bootstrap class loader is built into the JVM, implemented in native code. It loads the core runtime, in the module system the java.base module and other boot modules, including java.lang.Object, String and java.util. Because it is not a Java object, getClassLoader() returns null for these classes.

The Platform class loader (Java 9+) loads the remaining Java SE and JDK modules that are not in the boot layer, for example java.sql or java.net.http. Before Java 9 its role was played by the Extension class loader, which loaded JARs from jre/lib/ext; that mechanism was removed with the module system.

The Application (System) class loader loads your code and third-party libraries from the classpath (-cp) and the module path. ClassLoader.getSystemClassLoader() returns it, and it is the default context class loader for the main thread.

Custom class loaders extend ClassLoader (or URLClassLoader) and normally override findClass, keeping parent delegation. Typical examples: Tomcat's WebappClassLoader, one per web application, which loads from WEB-INF/classes and WEB-INF/lib and isolates applications; Spring Boot's launcher class loader (LaunchedURLClassLoader, renamed in Boot 3.2 as the loader was rewritten), which reads JARs nested inside the executable fat jar; and loaders used by OSGi, IDEs, Gradle and hot-reload tools.

How it works

  1. The JVM starts with the Bootstrap loader and loads java.base.
  2. The Platform loader is created with Bootstrap as parent.
  3. The Application loader is created with Platform as parent and given the classpath.
  4. main class is loaded by the Application loader.
  5. Frameworks create child loaders for plugins, web apps or nested JARs.

Example

System.out.println(String.class.getClassLoader());          // null (bootstrap)
System.out.println(java.sql.Driver.class.getClassLoader());  // jdk.internal.loader.ClassLoaders$PlatformClassLoader
System.out.println(MyService.class.getClassLoader());        // ...ClassLoaders$AppClassLoader

class EncryptedClassLoader extends ClassLoader {
    EncryptedClassLoader(ClassLoader parent) { super(parent); }
    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        byte[] bytes = decrypt(readBytes(name.replace('.', '/') + ".class.enc"));
        return defineClass(name, bytes, 0, bytes.length);
    }
}

Common mistakes

  • Saying the Extension loader still exists in modern Java.
  • Overriding loadClass instead of findClass and accidentally breaking delegation.
  • Ignoring the thread context class loader, which frameworks like JDBC ServiceLoader and JNDI use.
  • Assuming a fat jar works with plain URLClassLoader; nested JARs need Spring Boot's loader.

How to answer in the interview

"There are three built-in loaders. Bootstrap, native code, loads core modules like java.base, so String.class.getClassLoader() is null. The Platform loader, which replaced the Extension loader in Java 9, loads other JDK modules such as java.sql. The Application or System loader loads my classes and dependencies from the classpath and module path. Frameworks add custom loaders by extending ClassLoader and overriding findClass: Tomcat has one per web application for isolation, and Spring Boot has its own loader to read nested JARs inside the fat jar."

Likely follow-up questions

  • Why does String.class.getClassLoader() return null? It is loaded by the native Bootstrap loader, which has no Java object.
  • What is the context class loader? A per-thread loader that frameworks use to load application classes from library code.
  • Why override findClass rather than loadClass? loadClass implements delegation; findClass is the hook for your own lookup.
