How do you package and configure applications for different environments in Kubernetes?

Kubernetes · concept · levels mid, senior

In one line

Build one immutable image and promote it through every environment; put everything that differs into configuration (ConfigMaps, Secrets synced from a vault, env vars or files), generate per-environment manifests with Kustomize overlays or Helm values files, and deploy from Git via GitOps with reviews.

Detailed explanation

If each environment gets its own build, production runs something that was never tested. The rule from the twelve-factor app applies: the same artefact, identified by tag and ideally digest, moves from dev to staging to prod; only configuration changes.

Configuration has layers:

  • ConfigMaps for non-secret settings (feature flags, URLs, log levels), mounted as files or injected as env vars.
  • Secrets for credentials, ideally not written by hand but synced from Vault, AWS Secrets Manager or Azure Key Vault by the External Secrets Operator or mounted by the Secrets Store CSI driver.
  • Manifest differences such as replica counts, resource requests, HPA limits, ingress hostnames, node selectors.

To avoid copying YAML, use Kustomize (a base plus small overlays that patch differences, built into kubectl) or Helm (templated charts plus values-staging.yaml, values-prod.yaml). Kustomize suits in-house apps; Helm suits distributable packages and complex logic. Both can be combined: Argo CD renders a Helm chart and applies Kustomize patches.

Everything lives in Git. Changing production means a pull request on the prod overlay, reviewed and merged, then Argo CD or Flux syncs it. Image promotion is a commit changing the tag in the next environment, so every environment is versioned and reproducible.

How it works

  1. CI builds and scans the image once, pushes orders:1.8.2 (plus digest).
  2. CI updates the dev overlay with the new tag; Argo CD deploys it.
  3. Tests pass → PR promotes the same tag to staging, then prod.
  4. Each overlay supplies its ConfigMap values, replicas and hosts.
  5. Secrets come from the vault via External Secrets, never from Git in plain text.
  6. Rollback = revert the commit.

Example

# overlays/prod/kustomization.yaml
resources: [../../base]
namespace: orders-prod
images:
- { name: orders, newName: registry.example.com/orders, newTag: "1.8.2" }
replicas:
- { name: orders, count: 6 }
configMapGenerator:
- name: orders-config
  behavior: merge
  literals: [LOG_LEVEL=info, PAYMENTS_URL=https://payments.prod.internal]
patches:
- path: resources-prod.yaml

Common mistakes

  • Rebuilding images per environment or baking config into the image.
  • Plain Secrets committed to Git.
  • Huge copy-pasted manifests per environment that drift.
  • Using latest instead of immutable tags or digests.

How to answer in the interview

"I build the image once and promote exactly that image through every environment, so what we tested is what runs. Everything that differs is configuration: ConfigMaps for settings and Secrets synced from a vault with External Secrets, injected as env vars or files. To avoid duplicated YAML I use Kustomize with a base and per-environment overlays, or Helm with a values file per environment, for replicas, resources, ingress hosts and feature flags. All of it is in Git, changed through pull requests and deployed by Argo CD or Flux, so promotion and rollback are just commits."

Likely follow-up questions

  • How do pods pick up a changed ConfigMap? Env vars need a restart; use a config hash annotation or Kustomize's hashed generator names to trigger a rollout.
  • Helm or Kustomize? Kustomize for small differences; Helm for packaging and third-party software.
  • How do you promote between environments? A commit or automated PR changing the image tag in the next overlay.
