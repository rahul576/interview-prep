Design a platform that serves a large language model to thousands of concurrent users with low latency.

AI & ML System Design · design · levels senior, lead

In one line

LLM serving at scale uses GPU inference servers (vLLM, TensorRT-LLM) with continuous batching, careful KV-cache management (PagedAttention, prefix caching), token streaming, a gateway with token-based quotas, autoscaling on queue depth/tokens, and cost levers like quantisation, speculative decoding and model routing.

Detailed explanation

Generating text is memory-bandwidth bound: each new token requires reading the model weights. Processing one request at a time leaves the GPU mostly idle, so batching many sequences together multiplies throughput. Continuous (in-flight) batching adds new requests and removes finished ones at each decoding step rather than waiting for a full batch, which is the main reason vLLM-style servers deliver several times higher throughput.

The KV cache stores attention keys/values for every token of every active sequence; it limits how many concurrent requests fit in GPU memory. PagedAttention allocates it in pages (like virtual memory) to avoid fragmentation; prefix caching reuses the KV cache for shared system prompts.

Latency metrics: time to first token (TTFT) (prefill cost, grows with prompt length) and inter-token latency / tokens per second. Users perceive streaming as fast, so stream tokens via SSE.

Scaling: large models need tensor parallelism across GPUs on one node; replicas behind a router that's load-aware (queue length, KV utilisation). GPU nodes and model loading take minutes, so keep warm capacity and autoscale on queue depth or tokens/s, not CPU.

How it works

  1. Gateway: auth, per-tenant token quotas, routing by model.
  2. Router: pick least-loaded replica (or one with matching prefix cache).
  3. Inference server: prefill → decode loop with continuous batching → stream tokens.
  4. Metrics: TTFT, tokens/s, queue time, GPU utilisation, KV-cache usage.

Example

vllm serve meta-llama/Llama-3.1-8B-Instruct \
  --tensor-parallel-size 1 --max-num-seqs 256 \
  --enable-prefix-caching --gpu-memory-utilization 0.90

Common mistakes

  • Autoscaling on CPU.
  • Static batching with fixed batch sizes.
  • Ignoring prompt length (long prompts dominate TTFT and memory).
  • No per-tenant limits, so one batch job starves interactive users.

How to answer in the interview

"I'd run models on GPU nodes with an inference server like vLLM, using continuous batching and paged KV-cache management to maximise utilisation, with prefix caching for shared system prompts. Responses stream over SSE, so time to first token is the key latency metric. A gateway enforces token quotas and routes to the least-loaded replica; autoscaling uses queue depth or tokens per second with warm spare capacity. For cost, quantisation, speculative decoding and routing simple requests to smaller models."

Likely follow-up questions

  • Dashboard metrics? TTFT p50/p95, tokens/s, queue time, GPU and KV utilisation, error rate, cost per 1k tokens.
  • Separate interactive vs batch? Priority queues or separate pools.
  • Prefill/decode disaggregation? Run prefill and decode on different GPU pools for efficiency.
