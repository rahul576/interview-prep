Where does the language model sit in the MCP architecture, and what does an MCP server know about it?

MCP Servers · concept · levels entry, mid

In one line

The model lives in or behind the host application, which decides what enters the model's context; the host creates one client per server with a 1:1 connection, and the server knows nothing about the model, it just answers protocol requests.

Detailed explanation

MCP defines three roles. The host is the AI application the user interacts with: Claude Desktop, Claude Code, VS Code with Copilot, Cursor, or a custom agent. The host either runs the model locally or calls a model API, and it owns the conversation: it decides which tool definitions, resources, user messages and tool results go into the model's context, and it enforces user consent and policies.

For each MCP server it connects to, the host creates a client, a protocol component that maintains a one-to-one connection with that server, handles capability negotiation and routes messages. A host connected to GitHub, Jira and a database server has three clients.

The server exposes capabilities: tools, resources and prompts. When the model decides to call a tool, the host takes the model's tool-use output, asks the relevant client to send tools/call to that server, receives the result and feeds it back into the model's context for the next step.

Crucially, the server does not know which model is used, or whether a model is involved at all. It never sees the conversation unless the host sends parts of it as arguments. It just lists tools, executes calls and serves resources. This separation is what lets one server work with any model and any host, the "USB-C for AI" idea, and it places responsibility clearly: the host handles model interaction, consent and context; the server handles its domain logic and its own authorisation.

How it works

  1. The user configures servers in the host; the host starts one client per server.
  2. Each client connects and discovers the server's tools, resources and prompts.
  3. The host includes selected tool definitions in the model request.
  4. The model emits a tool call; the host checks policy and, if needed, asks the user for approval.
  5. The client sends tools/call; the server executes and returns a result.
  6. The host adds the result to the context and calls the model again.

Example

User ──> Host (e.g. IDE agent) ──> Model API
           |  client A ──1:1──> GitHub MCP server
           |  client B ──1:1──> Postgres MCP server
           |  client C ──1:1──> Internal tickets MCP server

Model: "call query_db(sql=...)"  -> host approves -> client B -> server B
Server B returns rows -> host appends to context -> model continues

Common mistakes

  • Believing the MCP server calls the LLM or "contains the AI".
  • Assuming the server sees the whole conversation.
  • Putting model-specific prompt tricks into server logic instead of clear tool descriptions.
  • Expecting the server to ask the user for approval; that is the host's job.

How to answer in the interview

"The model sits with the host, the AI application like Claude Desktop, an IDE or a custom agent. The host runs or calls the model and decides what goes into its context: user messages, tool definitions and tool results. For each server, the host creates a client with a one-to-one connection. When the model wants a tool, the host checks policy, the client sends tools/call to the right server, and the result is fed back to the model. The server knows nothing about which model is used, or whether there's a model at all; it just answers protocol requests. That separation is why one server works with any model and any host."

Likely follow-up questions

  • Who asks the user before a tool runs? The host; the server can only hint with annotations.
  • Can a server use a model itself? Yes, by calling a model API on its own side; earlier revisions also offered sampling through the client.
  • Why one client per server? Isolation: each connection has its own capabilities, auth and security boundary.
