Which tools are used for LLM observability, and what do they capture?

LLMOps & RAG · concept · levels mid, senior

In one line

LLM observability tools such as Langfuse, LangSmith, Arize Phoenix, Helicone and W&B Weave capture traces with nested spans for model calls, retrieval and tools, plus prompt versions, tokens, cost, feedback, datasets and evaluations; OpenTelemetry GenAI semantic conventions make instrumentation portable to APM vendors like Datadog, Azure Monitor and Grafana.

Detailed explanation

General APM shows that a call to an LLM endpoint took 3 seconds. LLM observability shows what was sent and returned and why the answer was what it was.

Dedicated tools:

  • Langfuse: open source and self-hostable, tracing, prompt management, datasets, evaluations, cost tracking.
  • LangSmith: from LangChain, deep integration with LangChain/LangGraph but usable without them; tracing, datasets, evaluations, annotation queues.
  • Arize Phoenix: open source, OpenTelemetry/OpenInference-based tracing and evaluation, strong for RAG analysis.
  • Helicone: proxy-based logging, so you get request logs, cost and caching by changing the base URL.
  • Weights & Biases Weave: tracing and evaluation in the W&B ecosystem.

What they capture: a trace per user request containing nested spans: LLM generations (model, parameters, prompt messages, completion, token usage, cost, latency, time to first token), retrieval (query, returned documents and scores), tool calls (arguments, results, errors) and custom application steps. Traces link to prompt versions, sessions/users, and feedback scores. Interesting traces can be added to datasets and used to run evaluations comparing versions.

Standards: the OpenTelemetry GenAI semantic conventions define attribute names like gen_ai.request.model, gen_ai.usage.input_tokens and gen_ai.usage.output_tokens, so instrumentation libraries (OpenLLMetry, OpenInference, vendor SDKs) emit portable telemetry. The conventions are still marked as in development, so attribute names can change between versions. Datadog LLM Observability, Azure Application Insights, Grafana, New Relic and others ingest LLM traces.

Typical setup: instrument once with OTel-compatible libraries, send full traces to an LLM-focused tool for debugging and evaluation, and export key metrics (latency, errors, cost, quality scores) to the main monitoring stack for alerting.

How it works

  1. Add SDK or OTel instrumentation around model, retrieval and tool calls.
  2. Propagate trace context through the request.
  3. Attach metadata: user/session, prompt version, feature.
  4. Record feedback against trace IDs.
  5. Build datasets from traces; run evals.
  6. Export aggregates to dashboards and alerts.

Example

from langfuse import observe

@observe()
def retrieve(query: str):
    return search(query, top_k=5)

@observe()
def answer(question: str):
    docs = retrieve(question)
    return llm_call(question, docs)   # LLM call traced via integration or OTel

Common mistakes

  • Logging full prompts with personal data without redaction or retention limits.
  • Tracing only the LLM call, not retrieval and tools.
  • Choosing a tool tied to one framework when you may switch.
  • No link between traces and prompt versions.

How to answer in the interview

"Dedicated tools include Langfuse, which is open source and self-hostable, LangSmith, Arize Phoenix, Helicone and W&B Weave. They capture a trace per request with nested spans for model calls, including prompts, outputs, parameters, tokens and cost, retrieval with the returned documents, and tool calls. They link traces to prompt versions and feedback, and let you turn traces into datasets for evaluation. OpenTelemetry's GenAI semantic conventions make instrumentation vendor-neutral, and Datadog, Azure Monitor and Grafana now ingest LLM traces. I instrument with OTel-compatible libraries, use one LLM-focused tool for debugging and evals, and export key metrics to the main stack."

Likely follow-up questions

  • Privacy controls for stored prompts? Redaction, masking, role-based access, short retention, regional storage.
  • Self-host or SaaS? Self-host when data can't leave your environment.
  • Overhead? Async export, batching and sampling of full payloads.
