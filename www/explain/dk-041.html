How do you manage different Compose configurations for development, CI and production?

Docker · concept · levels mid

In one line

Keep shared settings in compose.yaml, development tweaks in the automatically merged compose.override.yaml, other environments in extra files passed with multiple -f, optional services behind profiles, and values in a .env file with variable interpolation; real production usually moves to an orchestrator.

Detailed explanation

Different environments need the same services with different details: developers want source code mounted and debuggers exposed, CI wants a clean build with test dependencies, and a small production host wants pinned images, restart policies and resource limits. Copying whole files leads to drift, so Compose supports layering.

By default docker compose reads compose.yaml and, if present, compose.override.yaml, merging the override on top. This makes the override file a natural home for development-only settings: bind-mounting the source, enabling hot reload, publishing debug ports, using a target: dev build stage. For other environments you pass files explicitly, for example docker compose -f compose.yaml -f compose.ci.yaml up; later files override earlier ones (scalars replaced, lists like ports merged, maps merged by key). The include top-level key and extends let you reuse fragments across projects.

Profiles mark optional services: a mail catcher, pgAdmin or a load generator gets profiles: [tools] and starts only with --profile tools or COMPOSE_PROFILES=tools. Variable interpolation (${IMAGE_TAG:?required} or ${PORT:-8080}) takes values from the shell environment or the project .env file, which is different from a service's env_file, which injects variables into the container. docker compose config shows the final merged result and is the best debugging tool.

For production, Compose is fine on a single simple host, but anything needing multi-host scheduling, rolling updates or autoscaling usually moves to Kubernetes, ECS or another managed container service.

How it works

  1. Compose loads compose.yaml.
  2. It merges compose.override.yaml or the -f files in order.
  3. It interpolates ${VAR} from the shell and .env.
  4. It filters services by active profiles.
  5. It applies the resulting model to Docker.

Example

# compose.yaml
services:
  api:
    image: registry.local/api:${IMAGE_TAG:-dev}
    env_file: .env.api
  mailpit:
    image: axllent/mailpit
    profiles: [tools]
# compose.override.yaml (dev, merged automatically)
services:
  api:
    build: { context: ., target: dev }
    volumes: ["./src:/app/src"]
    ports: ["8080:8080", "5005:5005"]
docker compose up -d                                   # base + override
docker compose -f compose.yaml -f compose.ci.yaml up --abort-on-container-exit
docker compose --profile tools up -d
docker compose -f compose.yaml -f compose.prod.yaml config

Common mistakes

  • Committing .env files with real secrets.
  • Accidentally applying the dev override in production because it is merged automatically.
  • Confusing project .env (interpolation) with env_file (container environment).
  • Duplicating whole files per environment.

How to answer in the interview

"The base compose.yaml holds everything common. Compose automatically merges compose.override.yaml, which I use for development settings like bind-mounting the source, debug ports and hot reload. For CI or production I pass several files with -f, and later files override earlier ones. Profiles mark optional services like a mail catcher that start only with --profile. Image tags and ports come from a .env file through variable interpolation, and docker compose config shows the merged result. For real production most teams use Compose only on simple single hosts and move to Kubernetes or a managed container service."

Likely follow-up questions

  • env_file vs project .env? env_file sets container variables; .env feeds interpolation in the Compose file.
  • How do you avoid the dev override in production? Always pass explicit -f files there.
  • How do you require a variable? ${VAR:?error message}.
