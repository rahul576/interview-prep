What is the difference between ReentrantLock and synchronized?

Concurrency · concept · levels mid

In one line

Both give mutual exclusion, visibility and reentrancy; synchronized is a simple keyword whose lock is released automatically, while ReentrantLock adds tryLock, timeouts, interruptible locking, fairness and multiple Conditions but must be unlocked in finally. Before Java 24, ReentrantLock also avoided virtual-thread pinning.

Detailed explanation

Common ground. Both ensure only one thread holds the lock at a time, both create happens-before edges so writes inside are visible to the next holder, and both are reentrant: the holding thread can lock again and must release the same number of times.

synchronized is part of the language. It is concise, block-structured and impossible to forget to release: the lock is freed when the block exits normally or with an exception. The JVM optimises it heavily (lock coarsening, elision via escape analysis). Coordination uses wait/notify on one wait set per object. Its limits: a thread waiting to enter cannot be interrupted, cannot time out, and cannot try without blocking; there is no fairness option; and it cannot be acquired in one method and released in another.

ReentrantLock is a library class (java.util.concurrent.locks) providing:

  • tryLock() (immediate) and tryLock(timeout, unit), so a thread can give up, which helps avoid deadlocks;
  • lockInterruptibly(), so a waiting thread responds to cancellation;
  • fairness: new ReentrantLock(true) grants the lock to the longest waiter, at a throughput cost;
  • multiple Condition objects (newCondition()), for example notFull and notEmpty;
  • introspection: isLocked, isHeldByCurrentThread, getQueueLength;
  • non-block-structured locking (lock in one method, unlock in another, e.g. hand-over-hand).

The cost is verbosity and risk: you must unlock() in a finally block.

Virtual threads. In Java 21-23, blocking inside synchronized pinned a virtual thread to its carrier, so ReentrantLock was recommended around blocking calls. JEP 491 in Java 24 reworked monitors so synchronized no longer pins in typical cases. On current JDKs the choice is again mainly about features.

How it works

  1. lock.lock() acquires or queues the thread (an AQS-based queue).
  2. Reentry increments a hold count.
  3. Work in a try block.
  4. unlock() in finally decrements the count; at zero, the next waiter is unparked.
  5. tryLock(timeout) returns false if the lock is not obtained in time.

Example

private final ReentrantLock lock = new ReentrantLock();

public boolean updateIfFree(Runnable update) throws InterruptedException {
    if (!lock.tryLock(100, TimeUnit.MILLISECONDS)) {
        return false;                               // give up instead of waiting forever
    }
    try {
        update.run();
        return true;
    } finally {
        lock.unlock();                              // mandatory
    }
}

// Equivalent simple case with synchronized
public synchronized void update(Runnable update) { update.run(); }

Common mistakes

  • Calling lock() inside the try block, so unlock() runs even if locking failed.
  • Forgetting unlock() on some code path.
  • Choosing ReentrantLock by default when synchronized would be simpler.
  • Turning on fairness without measuring the throughput cost.

How to answer in the interview

"Both give mutual exclusion and memory visibility, and both are reentrant. synchronized is a keyword: simple, the lock is released automatically even on exceptions, and the JVM optimises it well. ReentrantLock is a class with more control: tryLock without blocking or with a timeout, lockInterruptibly so a waiting thread can be cancelled, an optional fairness policy, several Condition objects and methods to inspect the lock. The cost is that I must unlock in finally myself. On Java 21 to 23 it also avoided pinning virtual threads, but Java 24 fixed that for synchronized, so now I choose mostly by features."

Likely follow-up questions

  • When does tryLock help avoid deadlocks? When a thread needs several locks: if it cannot get the second within a timeout, it releases the first and retries with backoff, breaking hold-and-wait.
  • Which is faster? Similar in modern JVMs; synchronized is often as fast or faster for uncontended locks.
  • What is AQS? AbstractQueuedSynchronizer, the framework behind ReentrantLock, Semaphore and CountDownLatch.
