How does Kubernetes support application scalability?

Kubernetes · concept · levels mid

In one line

Kubernetes scales apps by running more replicas behind a Service, automatically with the HorizontalPodAutoscaler (CPU, memory, custom metrics) or KEDA (event-driven, scale to zero), adjusts sizing with the VPA, and adds nodes with the Cluster Autoscaler or Karpenter; this only works for stateless apps with accurate requests and readiness probes.

Detailed explanation

Horizontal scaling at the pod level. A Deployment declares replicas, and a Service load-balances across all ready pods, so capacity grows by adding pods. You can do it manually (kubectl scale, or changing replicas in Git with GitOps), but production systems use the HorizontalPodAutoscaler (HPA). HPA autoscaling/v2 reads metrics every 15 seconds or so and computes desired = ceil(current * currentMetric / target). Metrics can be CPU or memory utilisation relative to requests (from metrics-server), custom metrics such as requests per second via Prometheus Adapter, or external metrics such as queue length. Behaviour policies control scale-up speed and scale-down stabilisation to avoid flapping.

Event-driven scaling. KEDA adds scalers for Kafka lag, RabbitMQ, SQS, Azure Service Bus, cron schedules and many more, drives an HPA under the hood, and can scale to zero when idle.

Vertical scaling. The Vertical Pod Autoscaler recommends or applies CPU and memory requests based on observed usage. Do not let VPA and HPA both act on the same CPU metric. Kubernetes 1.33+ also supports in-place pod resize, which reduces restarts for vertical changes.

Node scaling. When new pods are Pending because nodes are full, the Cluster Autoscaler grows node groups, and removes underused nodes. Karpenter (AWS, and Azure via node auto-provisioning) provisions right-sized nodes directly and consolidates them.

Preconditions. Apps must be stateless (sessions in Redis or tokens), start fast, expose readiness probes so traffic only reaches warm pods, handle SIGTERM gracefully, and have accurate resource requests, since both the HPA percentage and the scheduler depend on them. PodDisruptionBudgets keep availability during scale-down.

How it works

  1. Load rises; metric exceeds HPA target.
  2. HPA raises replica count on the Deployment.
  3. New pods are scheduled; if no room, they stay Pending.
  4. Cluster Autoscaler or Karpenter adds nodes; pods start.
  5. Readiness passes; Service sends traffic; later, scale-down removes pods and nodes.

Example

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: orders }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: orders }
  minReplicas: 3
  maxReplicas: 30
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 65 } }
  behavior:
    scaleDown: { stabilizationWindowSeconds: 300 }

Common mistakes

  • No resource requests, so CPU utilisation targets are meaningless.
  • Scaling stateful apps that keep sessions in memory.
  • Max replicas higher than the database connection pool can handle.
  • Scaling consumers beyond the number of Kafka partitions.

How to answer in the interview

"Apps run as Deployments with several replicas behind a Service, so scaling out means adding pods. The HorizontalPodAutoscaler does it automatically on CPU, memory or custom metrics like requests per second, and KEDA scales on event sources like Kafka lag, even down to zero. The VPA tunes resource requests. When pods cannot fit, the Cluster Autoscaler or Karpenter adds nodes and removes idle ones. All of this assumes stateless apps, fast startup, readiness probes and accurate resource requests."

Likely follow-up questions

  • Why do requests matter? HPA utilisation is a percentage of requests, and the scheduler packs nodes by requests.
  • HPA and VPA together? Not on the same CPU/memory metric; use VPA in recommendation mode or HPA on custom metrics.
  • What limits scaling? Downstream databases, partitions, licences and node quotas.
