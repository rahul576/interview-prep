An AKS upgrade failed halfway and the cluster shows a Failed provisioning state. How do you recover?

Azure Kubernetes (AKS) · scenario · levels mid, senior

In one line

A Failed provisioning state means the last operation didn't finish, not that the cluster is down; read the error details and activity log, fix the cause (often PDBs blocking drain, quota or subnet IPs), then re-run the upgrade or reconcile with az aks update, and check that all node pools end on consistent versions.

Detailed explanation

The provisioningState of an AKS cluster or node pool reflects the result of the most recent ARM operation. When an upgrade fails partway, the control plane may already be on the new version and some nodes upgraded, while others are still on the old one. Workloads usually keep running, so the first step is to stay calm and confirm impact with kubectl get nodes and application health checks.

Diagnose with the activity log, the error message in az aks show or the portal, and kubectl get events. Common causes:

  • PodDisruptionBudget blocks eviction: a PDB with minAvailable equal to replicas, or one replica with maxUnavailable: 0, means the node can never drain, so the drain times out (PodDrainFailure).
  • Quota: surge nodes need extra vCPUs in the regional or family quota.
  • Subnet IP exhaustion: surge nodes (and pods with flat or pod-subnet CNI) need free addresses.
  • Policies or locks: an Azure Policy deny or a resource lock on the node resource group.
  • Custom networking issues: a firewall or UDR blocking nodes from downloading images or reaching the API server.
  • Occasionally a transient platform issue.

Fix and resume: temporarily relax the strict PDB or scale the deployment up, request quota, lower max-surge, free IPs or remove the blocking lock. Then re-run the same upgrade on the cluster or node pool; it resumes from where it stopped. If nothing needs to change, az aks update without parameters reconciles the cluster to its goal state.

Afterwards, confirm the control plane and every node pool have the expected currentOrchestratorVersion and node image, and document a prevention action.

How it works

  1. Check cluster and node pool provisioning state and error messages.
  2. Inspect activity log, events and PDBs.
  3. Fix the root cause.
  4. Re-run the upgrade or reconcile.
  5. Verify versions and workload health; write a short postmortem.

Example

az aks show -g rg-apps -n aks-prod --query "{state:provisioningState, version:currentKubernetesVersion}"
az aks nodepool list -g rg-apps --cluster-name aks-prod \
  --query "[].{name:name, state:provisioningState, version:currentOrchestratorVersion}" -o table
kubectl get pdb -A          # look for ALLOWED DISRUPTIONS = 0

az aks nodepool upgrade -g rg-apps --cluster-name aks-prod -n user1 \
  --kubernetes-version 1.33.2 --max-surge 10%
az aks update -g rg-apps -n aks-prod   # reconcile with no changes

Common mistakes

  • Deleting and recreating node pools in a panic.
  • Removing PDBs permanently instead of fixing their values.
  • Retrying repeatedly without reading the error.
  • Forgetting to check that all node pools finished, not just the control plane.

How to answer in the interview

"Failed provisioning means the last operation didn't finish; workloads usually still run. I check the activity log and error details. Typical causes are PDBs that don't allow evictions so drains time out, missing vCPU quota or subnet IPs for surge nodes, policies or locks, or a transient issue. I fix the cause, for example relaxing a PDB or requesting quota, and re-run the upgrade, which resumes, or run az aks update with no changes to reconcile. Then I verify that the control plane and all node pools are on consistent versions."

Likely follow-up questions

  • How to prevent PDB blocks? At least two replicas, maxUnavailable: 1, and PDB checks in CI or policy.
  • Is the cluster still supported while failed? Yes, but resolve it quickly; later operations may be blocked.
  • When open a support case? When the error points to the platform or reconcile keeps failing.
