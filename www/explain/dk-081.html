You discover that an image in your registry was compromised with malware. How do you respond?

Docker · scenario · levels lead

In one line

Respond like a security incident: contain (block the digest, pause pipelines, isolate workloads), scope (find every place it runs and every image built from it via inventories and SBOMs), rotate secrets it could reach, investigate the entry point (upstream, CI, registry credentials, dependency), rebuild from trusted sources, enforce signing and provenance, and run a blameless postmortem.

Detailed explanation

A compromised image is a supply chain incident: it may already run in many clusters and may have been used as a base for other images. Speed matters, but so does preserving evidence.

Containment: block the malicious digest (not just the tag) in the registry and in admission policies so it cannot be pulled or deployed again. Freeze pipelines that could rebuild on top of it. For running workloads, isolate them with network policies (deny egress to stop exfiltration and command-and-control), then replace them with a known-good version. Keep a copy of the image and node forensics before deleting everything.

Scope: use registry pull logs, cluster inventories (which pods run which digest) and SBOMs/provenance to find every environment running it and every downstream image that used it as a base. Check what those workloads had access to.

Credentials: treat every secret, token, service account and cloud role those workloads could reach as leaked and rotate it. Look for lateral movement in cloud audit logs.

Root cause: was it an upstream base image or public dependency, a compromised CI runner or pipeline, stolen registry push credentials, or an insider? Registry audit logs (who pushed, from where) and build provenance (SLSA attestations) answer this.

Recovery and prevention: rebuild clean images from verified sources, enforce signature verification at admission, restrict push rights to CI identities with short-lived credentials, pin dependencies, scan continuously, and document in a blameless postmortem.

How it works

  1. Declare an incident; assign roles (lead, comms, forensics).
  2. Block digest; quarantine repository; pause pipelines.
  3. Inventory running instances and derived images; isolate and replace.
  4. Rotate exposed credentials; hunt for persistence and lateral movement.
  5. Determine entry point from audit logs and provenance.
  6. Rebuild, enforce signing, close the gap, postmortem.

Example

# Find every pod running the bad digest
kubectl get pods -A -o json | jq -r '.items[] | select(.status.containerStatuses[]?.imageID
  | contains("sha256:badd1g3st")) | "\(.metadata.namespace)/\(.metadata.name)"'
# Verify signatures and provenance of replacement images
cosign verify --certificate-identity-regexp 'https://github.com/acme/.+' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  registry.example.com/orders@sha256:5e7a...

Common mistakes

  • Deleting the tag but leaving the digest pullable.
  • Destroying all evidence before understanding the entry point.
  • Forgetting downstream images built on the compromised base.
  • Rotating only the obvious secret and missing service account tokens and cloud roles.

How to answer in the interview

"I'd treat it as a security incident. First containment: block the compromised digest in the registry and admission policies, pause pipelines that might build on it, and isolate running workloads with network policies before replacing them, keeping copies for forensics. Then scope: using image inventories and SBOMs I find every cluster running it and every image that used it as a base. Every secret those workloads could reach is treated as leaked and rotated. Then I investigate how it got in, using registry audit logs and build provenance: upstream image, CI compromise, stolen credentials or a dependency. Finally we rebuild from trusted sources, enforce signature verification at deploy time and run a blameless postmortem."

Likely follow-up questions

  • How would signing have helped? Admission control would reject images not signed by the CI identity, stopping images pushed with stolen credentials.
  • What is build provenance? A signed attestation of source, builder and steps (SLSA), proving how an image was produced.
  • Who do you notify? Security, affected service owners, and depending on data exposure, legal and customers.
