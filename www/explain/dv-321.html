What is an internal developer platform, and what is a golden path?

Platform Engineering · concept · levels mid, senior

In one line

An internal developer platform (IDP) is a self-service layer built by a platform team so developers can create, deploy and run services without being infrastructure experts; a golden path (paved road) is the recommended, well-supported way to do a common task, with CI/CD, infrastructure, observability and security built in.

Detailed explanation

Modern delivery asks a lot of product developers: containers, Kubernetes manifests, Terraform, pipelines, secrets, observability, security scanning and compliance. Expecting every team to master all of that creates high cognitive load, inconsistency and slow delivery. An IDP packages these capabilities behind self-service interfaces: a portal such as Backstage or Port, a CLI, a Git repository with templates, or APIs. Underneath it integrates existing tools (CI/CD, Argo CD, Terraform, cloud accounts, secret stores, monitoring) rather than replacing them.

A golden path is an opinionated, end-to-end route for a common job, such as "create a new Spring Boot REST service" or "add a PostgreSQL database". Choosing it gives you a repository from a template with a working pipeline, Kubernetes manifests or Helm chart, dashboards, SLO alerts, security scanning and documentation, all following company standards. The platform team keeps it up to date, so improvements reach everyone.

Two principles matter. The platform is treated as a product: it has users, a roadmap, documentation, feedback loops and adoption metrics. And golden paths are optional but attractive: teams can leave the path when they have good reasons, but then they own the extra work. If the path is mandated and worse than alternatives, teams route around it.

How it works

  1. Identify the most common developer journeys and pain points.
  2. Build a thin platform layer integrating existing tools.
  3. Create templates for the top journey, with standards built in.
  4. Expose them via a portal, CLI or Git workflow.
  5. Collect feedback and measure adoption and lead time.
  6. Expand to more journeys (databases, queues, environments).

Example

# Developer uses the golden path via a CLI wrapper around the platform API
platform new service --template springboot-rest --name invoice-api --team billing
# Result: repo created, pipeline green, namespace and Argo CD app created,
# Grafana dashboard and SLO alerts provisioned, entry added to the catalog.

Common mistakes

  • Building a big platform before talking to developers.
  • Mandating the golden path instead of making it the easiest option.
  • Templates that are copied once and never updated.
  • Hiding everything so developers cannot debug when things go wrong.

How to answer in the interview

"An internal developer platform is a self-service layer built by a platform team so product developers can create, deploy and run services without being experts in Kubernetes, cloud networking or CI tooling. A golden path, or paved road, is the recommended and supported way to do a common task, for example creating a new Spring Boot service from a template that already includes the repository, pipeline, Kubernetes manifests, dashboards, alerts and security scanning. The goal is to reduce cognitive load and lead time while keeping standards consistent. The platform is run as a product with feedback and adoption metrics, and golden paths are optional but attractive, not mandated."

Likely follow-up questions

  • How do you measure if it helps? Time to first deploy, DORA metrics, adoption rate and developer satisfaction.
  • IDP versus portal? The portal is the interface; the platform is the integrated capabilities behind it.
  • What if a team leaves the golden path? Allowed, but they own the extra maintenance and must still meet guardrails.
