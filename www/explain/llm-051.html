How do you manage and version prompts in a production LLM application?

LLMOps & RAG · concept · levels mid, senior

In one line

Treat prompts as code: templates in version control separated from logic, optionally a prompt registry with versions and labels (staging, production), evaluation gates in CI, the prompt version recorded in every trace, gradual rollout with rollback, and prompt, model and retrieval settings versioned together.

Detailed explanation

A prompt is part of the program: changing one sentence can change behaviour across thousands of cases. Yet teams often edit prompts in a dashboard or a string constant with no review, no tests and no record of what ran when.

Version control. Store prompts as template files (Jinja, Mustache, or the framework's format) with named variables, separate from business logic, reviewed in pull requests like any other change. Keep the system prompt, few-shot examples and output schema together.

Registry (optional). Tools like Langfuse prompt management, MLflow's prompt registry, LangSmith's prompt hub or cloud equivalents store immutable versions with labels. Product experts can iterate in a UI, while production code fetches the prompt by label or explicit version and caches it. Labels give quick promotion and rollback without redeploying.

Evaluation gates. Every prompt change runs the evaluation suite in CI and must not regress key metrics.

Traceability. Each request logs prompt name and version, so you can compare quality by version and find exactly which requests a bad version affected.

Rollout. Ship changes behind a feature flag or traffic split (for example 5%, 25%, 100%), watch quality signals, and roll back by switching the label or flag.

Config bundle. Prompt, model and version, temperature, tool definitions and retrieval settings interact, so version them together as one release configuration.

How it works

  1. Edit template in a branch; open a PR.
  2. CI runs evals against baseline; reviewers inspect diffs of outputs.
  3. Merge -> new version registered with "staging" label.
  4. Promote to "production" for a traffic share via flag.
  5. Monitor; promote fully or roll back.

Example

# prompts/support-answer/v14.yaml
name: support-answer
version: 14
model: claude-sonnet-4-5
temperature: 0.2
retrieval: { top_k: 6, reranker: true }
system: |
  You are the support assistant for {{product}}.
  Answer only from the sources. Cite as [S1]. If unsure, say so.
variables: [product, sources, question]

Common mistakes

  • Editing prompts directly in production without tests or history.
  • Prompts scattered as string literals across code.
  • Not logging which version produced which output.
  • Changing model and prompt in separate, unsynchronised processes.

How to answer in the interview

"I treat prompts as code: templates with clear variables in version control, separated from business logic, reviewed in pull requests. Some teams add a prompt registry like Langfuse or MLflow with versions and labels such as staging and production, so experts can iterate while production references an explicit version. Every change runs the evaluation suite in CI, each request records its prompt version in the trace, and rollouts are gradual behind a flag with fast rollback. Prompt, model version and retrieval settings are versioned together as one configuration, because they interact."

Likely follow-up questions

  • Why never edit directly in production? No review, no eval, no rollback point, no traceability.
  • Registry outage? Cache prompts locally and fall back to a bundled version.
  • A/B testing prompts? Traffic split by user, compare online metrics and judge scores.
