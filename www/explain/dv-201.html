What is Infrastructure as Code, and what are its benefits?

Infrastructure as Code · concept · levels entry

In one line

Infrastructure as Code (IaC) means defining servers, networks, databases and permissions in code files instead of clicking in a console, usually declaratively (describe the end state, the tool works out the steps); because it lives in version control, changes are reviewed, versioned and reversible, and environments become repeatable and consistent with less drift.

Detailed explanation

Creating infrastructure by hand works for one server, but it doesn't scale: nobody remembers exactly which settings were chosen, test and production differ in small ways, and rebuilding after a disaster takes days. IaC treats infrastructure like software.

Declarative vs imperative:

  • Declarative tools (Terraform/OpenTofu, CloudFormation, Bicep, Kubernetes manifests) describe the desired end state: "there should be a VPC with three subnets and this bucket". The tool compares desired and actual state and decides what to create, change or delete. Running it again changes nothing if everything matches (idempotent).
  • Imperative approaches (shell scripts with the AWS CLI, some SDK scripts) list the steps: "create a VPC, then create a subnet". They are flexible but must handle every case themselves: what if the subnet already exists?

Benefits:

  • Version control and review: every change is a commit and a pull request with history, blame and approvals. Rollback means reverting to a previous version.
  • Repeatability and consistency: the same code builds dev, staging and prod with only parameters differing, eliminating "it works in test".
  • Speed and self-service: a new environment is minutes, not tickets and weeks.
  • Disaster recovery: recreate infrastructure in another region from code.
  • Less drift and better security: fewer manual console changes, and policy checks (no public buckets) can run automatically.
  • Documentation: the code shows exactly what exists.

Common tools: Terraform and OpenTofu (multi-cloud, HCL), AWS CloudFormation and CDK, Azure Bicep/ARM, Pulumi (general-purpose languages), and Crossplane (Kubernetes-based). Configuration management tools like Ansible configure software on servers and complement provisioning tools.

How it works

  1. Write infrastructure definitions in files.
  2. Commit to Git and open a pull request.
  3. CI validates and shows a preview (plan) of changes.
  4. Reviewers approve; the pipeline applies the change.
  5. The tool records what it manages and keeps reality matching the code.

Example

resource "aws_s3_bucket" "reports" {
  bucket = "acme-reports-${var.env}"
  tags   = { env = var.env, owner = "data-team" }
}
terraform plan -var env=dev     # preview
terraform apply -var env=dev    # create it; same code with env=prod builds production

Common mistakes

  • Using IaC but still making manual console changes.
  • Copy-pasting code for each environment instead of parameterising.
  • Storing secrets in IaC files.
  • Treating IaC as "scripts" without review or testing.

How to answer in the interview

"Infrastructure as Code means defining servers, networks, databases and permissions in code files instead of creating them by hand in a cloud console. Most tools are declarative: I describe the desired end state and the tool works out what to create or change, whereas imperative scripts list the steps themselves. Because the code lives in Git, every change is reviewed in a pull request, has history and can be rolled back. Environments become repeatable and consistent, we can recreate them after a disaster, and manual drift is reduced. Common tools are Terraform and OpenTofu for multiple clouds, CloudFormation, Azure Bicep and Pulumi."

Likely follow-up questions

  • What happens if someone changes a resource manually? That's drift; the next plan shows it and apply reverts it unless the code is updated.
  • IaC vs configuration management? IaC provisions infrastructure; config management configures software on it, though they overlap.
  • How do you keep secrets out? Reference them from a secret manager and mark variables sensitive.
