Why should microservices own their databases?

Microservices · concept · levels mid, senior

In one line

Database per service keeps services loosely coupled and independently deployable: each owns its schema, others access data only through its API or events, enabling independent scaling and technology choice, at the cost of no cross-service joins or ACID transactions.

Detailed explanation

A database schema is an interface. If the order, billing and reporting services all read and write the same tables, that schema becomes a shared, undocumented contract. Renaming a column or splitting a table requires coordinating releases across teams, which destroys the main benefit of microservices: independent deployment. A shared database also couples runtime behaviour: one service's heavy report or lock contention slows everyone, and a migration can take all services down together. Ownership becomes unclear, and business rules are bypassed when another service writes directly to "your" table.

With database per service, each service owns its data, either a separate database server, a separate database or at least a private schema with access control. Other services interact only through its API or the events it publishes. Benefits:

  • Encapsulation: the owner enforces invariants and can refactor its schema freely.
  • Independent deployment: schema migrations ship with the service.
  • Independent scaling and tuning: a read-heavy catalogue can use replicas or caching without affecting payments.
  • Polyglot persistence: PostgreSQL for orders, a document store for product content, Redis for sessions, Elasticsearch/OpenSearch for search.
  • Fault isolation: a database problem hurts one service.

The costs are real. You lose joins across services, so cross-service queries use API composition, CQRS read models or a data warehouse. You lose ACID transactions across services, so multi-service workflows use sagas, the outbox pattern and eventual consistency. Data is duplicated in read copies, and operating many databases needs automation or managed services. A pragmatic first step when splitting a monolith is a shared server with separate schemas and credentials per service, enforcing ownership even before physical separation.

How it works

  1. Assign each table or entity to exactly one service.
  2. Give each service its own schema/database and credentials.
  3. Expose data through APIs and events, never direct table access.
  4. Use sagas for multi-service writes, read models for multi-service queries.
  5. Migrations run in each service's pipeline.

Example

# order-service: own database and credentials
spring:
  datasource:
    url: jdbc:postgresql://orders-db:5432/orders
    username: order_svc
  flyway:
    locations: classpath:db/migration      # migrations versioned with the service
-- Shared server, enforced isolation
CREATE SCHEMA billing AUTHORIZATION billing_svc;
REVOKE ALL ON SCHEMA billing FROM order_svc;   -- order service cannot touch billing tables

Common mistakes

  • "Temporary" read access to another service's tables.
  • One database per service but services still sharing tables through views.
  • Splitting databases without a plan for cross-service queries.
  • Manually operating dozens of databases without automation.

How to answer in the interview

"If services share a database, they are coupled through the schema: one team cannot change a table without coordinating with every team reading it, and one service's heavy queries slow everyone. That kills independent deployment. With a database per service, each service owns its data and others use only its API or events, so the schema can evolve freely, the database scales independently and teams can pick the right technology. The price is no cross-service joins or ACID transactions, so I use sagas and the outbox for workflows, and API composition or read models for queries."

Likely follow-up questions

  • How would you build a report needing data from five services? Stream their events into a reporting read model or data warehouse rather than querying live.
  • Is a separate schema on one server enough? It is a good start if credentials enforce isolation; separate servers add fault and scale isolation.
  • How do you keep referential integrity? Through events, sagas and validating via the owner's API at write time.
