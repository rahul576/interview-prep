What is terraform_data, and how does it replace null_resource?

Terraform · concept · levels mid, senior

In one line

terraform_data is a built-in resource (Terraform 1.4+) that replaces null_resource without needing the null provider; its input/output hold a value in the graph, triggers_replace forces replacement (re-running provisioners), and it works with replace_triggered_by.

Detailed explanation

null_resource from the hashicorp/null provider has long been used as a container for provisioners and as a way to trigger actions when something changes, via its triggers map. Its downsides: an extra provider to install and pin, and triggers only accepts a map of strings.

terraform_data is part of Terraform itself (the built-in terraform.io/builtin/terraform provider), so no provider download is required. It has two arguments. input accepts any value; Terraform stores it and exposes it as the output attribute, which changes in the same plan as the input. That is useful for keeping a plain value in the dependency graph, for example so that something can depend on it or be replaced when it changes. triggers_replace accepts any value; when it changes, the terraform_data resource is replaced.

Replacement matters because creation-time provisioners run only when a resource is created. Attaching a local-exec provisioner to terraform_data with triggers_replace = var.app_version means the script, for example a database migration, cache warm-up or registration call, runs again whenever the version changes.

The second pattern is lifecycle { replace_triggered_by = [...] }. This argument only accepts references to managed resources or their attributes, not variables or locals. To replace a resource when a plain value changes, put the value in terraform_data.input and reference terraform_data.x in replace_triggered_by. Moving from null_resource is straightforward, and Terraform 1.9+ supports moved from null_resource to terraform_data.

Provisioners remain a last resort: they are not modelled in the plan, are hard to make idempotent and depend on the machine running Terraform.

How it works

  1. Define terraform_data with input and/or triggers_replace.
  2. On first apply it is created; provisioners run.
  3. If triggers_replace changes, it is replaced; provisioners run again.
  4. If input changes, output updates in place.
  5. Other resources can use replace_triggered_by = [terraform_data.x].

Example

resource "terraform_data" "db_migration" {
  triggers_replace = var.app_version

  provisioner "local-exec" {
    command = "./scripts/migrate.sh ${var.app_version}"
  }

  depends_on = [aws_db_instance.main]
}

resource "terraform_data" "ami_version" {
  input = var.ami_release
}

resource "aws_instance" "worker" {
  ami           = data.aws_ami.worker.id
  instance_type = "t3.large"
  lifecycle {
    replace_triggered_by = [terraform_data.ami_version]
  }
}

Common mistakes

  • Keeping null_resource and the null provider in new code.
  • Expecting input changes to re-run provisioners; use triggers_replace.
  • Putting variables directly in replace_triggered_by.
  • Using provisioners for work that belongs in CI/CD or configuration management.

How to answer in the interview

"terraform_data is a built-in resource added in Terraform 1.4 that does the job of null_resource without the separate null provider. Its input argument is stored and exposed as output, which is handy to hold a value in the dependency graph, and triggers_replace forces the resource to be replaced when its value changes. Replacing it re-runs attached provisioners, for example a local-exec that runs a migration when the version changes. It also pairs with lifecycle replace_triggered_by, so another resource can be replaced when a plain value changes, which resources can't reference directly. Provisioners are still a last resort, but terraform_data is the modern way to anchor them."

Likely follow-up questions

  • Why are provisioners a last resort? Not shown in plans, not idempotent, depend on the runner, and failures taint resources.
  • How do you migrate from null_resource? Replace it and use a moved block (1.9+), or accept one replacement.
  • Alternative to local-exec migrations? Run migrations in the deployment pipeline or as a Kubernetes Job.
