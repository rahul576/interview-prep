How do you let engineers query monitoring data in natural language while keeping results trustworthy?

AI Agents & AIOps · concept · levels mid, senior

In one line

An LLM translates questions into PromQL, KQL or SQL using schema, metric names and example queries as context; trust comes from showing the generated query, validating it with cost and time limits, running read-only with the user's permissions, and evaluating accuracy on known questions.

Detailed explanation

Many engineers can read a dashboard but cannot write a histogram quantile in PromQL or a KQL join. Natural language querying lowers that barrier: "what was checkout p95 latency yesterday compared with last week?" becomes a query and a chart.

Accuracy depends on context. Without knowing the real metric names, label conventions and table schemas, models invent plausible names like checkout_latency_seconds that do not exist. The assistant should provide the relevant schema and a few example queries, retrieved dynamically for the service in question, and ideally verify metric names exist through a metadata API before execution.

Trust comes from transparency and controls. The assistant always shows the generated query next to the answer, so engineers can check it and learn the language. Queries are validated before running: syntax checks, maximum time range, step size and result limits, so a vague question does not scan a month of logs. Execution uses read-only access under the user's own permissions, so nobody sees data they could not query directly. Finally, an evaluation set of questions with known-correct queries measures translation accuracy whenever the prompt, model or schema changes. Subtle errors, such as averaging percentiles or using the wrong rate window, are the main danger, so the answer should state assumptions.

How it works

  1. Detect the service and data source from the question.
  2. Retrieve schema, metric names, label values and example queries.
  3. Generate the query and verify identifiers exist.
  4. Validate: syntax, time range, cost estimate.
  5. Execute read-only with user credentials.
  6. Return result, chart, the query and stated assumptions.

Example

# "checkout p95 latency yesterday vs last week" (generated, shown to user)
histogram_quantile(0.95,
  sum by (le) (rate(http_request_duration_seconds_bucket{service="checkout"}[5m])))
# compared with the same expression using: offset 7d

Assumption shown to the user: "p95 computed from server-side histograms, 5-minute rate window, all endpoints."

Common mistakes

  • Hiding the query, so wrong answers look authoritative.
  • No schema context, leading to invented metric names.
  • A shared service account with access to everything.
  • No limits, so a question triggers an expensive full scan.

How to answer in the interview

"The LLM translates the question into PromQL, KQL or SQL, but it only works well with context: the real metric and table names, labels and some example queries, retrieved for the relevant service. To keep it trustworthy I always show the generated query with the result, validate it before running with time-range and cost limits, and execute read-only with the user's own permissions. I keep an evaluation set of known questions and correct queries and rerun it whenever the model or prompt changes."

Likely follow-up questions

  • Subtly wrong queries? Percentiles, rates, joins and time zones are common traps.
  • Ambiguous questions? Ask a clarifying question or state assumptions.
  • Can it build dashboards? Yes, as drafts reviewed before saving.
