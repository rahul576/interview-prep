What is the difference between ordered and unordered collections?

Collections · concept · levels entry

In one line

An ordered collection has a predictable iteration order (by index or insertion/access order); a sorted collection is ordered by comparison; an unordered collection like HashSet/HashMap makes no guarantee, and code must never depend on it. Java 21 formalised ordered collections as SequencedCollection.

Detailed explanation

It helps to separate three ideas:

Ordered (sequenced): elements come out in a well-defined order determined by how they were added. List implementations keep elements at indexes, usually in insertion order. LinkedHashSet and LinkedHashMap keep insertion order, and LinkedHashMap can be configured for access order. ArrayDeque keeps the order of its two ends.

Sorted: a special kind of ordered collection where the order is computed by comparing elements, not by when they arrived. TreeSet, TreeMap, ConcurrentSkipListSet/Map always iterate in ascending order of the natural ordering or a Comparator. PriorityQueue is partially ordered: only the head (what poll returns) is guaranteed to be the smallest; its iterator is not sorted.

Unordered: HashSet, HashMap and ConcurrentHashMap make no promise about iteration order. In practice the order depends on hash codes and table capacity, so it can change when the collection resizes, when the JDK changes its hashing, or between runs for Set.of/Map.of, which deliberately randomise iteration order per JVM instance. Code and tests that rely on it are fragile.

Java 21 (JEP 431) introduced SequencedCollection, SequencedSet and SequencedMap, giving ordered collections uniform methods: getFirst, getLast, addFirst, addLast, removeFirst, removeLast and reversed(). List, Deque, LinkedHashSet, SortedSet, LinkedHashMap and SortedMap implement them; HashSet and HashMap don't, which documents that they are unordered.

How it works

  1. List: order = index positions.
  2. LinkedHash*: order = doubly linked list through entries.
  3. Tree*: order = in-order traversal of a red-black tree.
  4. Hash*: order = bucket array scan, which depends on hashes and capacity.

Example

Map<String, Integer> hash = new HashMap<>();
Map<String, Integer> linked = new LinkedHashMap<>();
Map<String, Integer> tree = new TreeMap<>();
for (String k : List.of("banana", "apple", "cherry")) {
    hash.put(k, 1); linked.put(k, 1); tree.put(k, 1);
}
hash.keySet();    // unspecified order
linked.keySet();  // [banana, apple, cherry]
tree.keySet();    // [apple, banana, cherry]

List<String> names = List.of("a", "b", "c");
names.getLast();       // "c"  (Java 21)
names.reversed();      // [c, b, a]

Common mistakes

  • Assertions on the string output of a HashMap.
  • Thinking PriorityQueue iterates in sorted order.
  • Assuming Set.of preserves the order of its arguments.
  • Confusing "ordered" with "sorted".

How to answer in the interview

"An ordered collection has a predictable iteration order: lists keep elements by index in insertion order, and LinkedHashSet and LinkedHashMap keep insertion or access order. A sorted collection is a special ordered one where the order comes from comparing elements, like TreeSet and TreeMap. An unordered collection, such as HashSet or HashMap, makes no guarantee, and the order may change on resize or between Java versions, so code must not depend on it. Java 21 formalised this with SequencedCollection and SequencedMap, adding getFirst, getLast and reversed."

Likely follow-up questions

  • Why should tests not depend on HashMap order? It is unspecified and can change with capacity, JDK version or randomisation.
  • Which collections implement SequencedMap? LinkedHashMap, TreeMap and other SortedMaps.
  • Is PriorityQueue sorted? Only the head is guaranteed.
