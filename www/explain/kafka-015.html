How do you guarantee per-customer ordering while still processing millions of events in parallel?

Kafka · design · levels senior, lead

In one line

Key every event by customer ID so each customer's events go to one partition in order, while many partitions and consumers process different customers in parallel; watch for hot keys, and use key-level parallelism (such as the Confluent Parallel Consumer) to go beyond one thread per partition.

Detailed explanation

Kafka orders records only within a partition, and the default partitioner sends the same key to the same partition. Using customerId as the key therefore gives exactly the guarantee we need: all events for customer 42 are in one partition, in the order they were produced, and are consumed by one consumer in that order. Different customers spread across, say, 200 partitions, so 200 consumers can work concurrently. Throughput scales with partitions, while ordering stays per customer.

Ordering can still break in a few places. On the producer side, retries with multiple in-flight requests could reorder batches; the idempotent producer (default since 3.0) preserves order with up to 5 in-flight requests. On the consumer side, handing records to a thread pool without keying the pool breaks order. Non-blocking retry topics also break order for the affected key. And adding partitions remaps keys.

Hot keys are the main scaling risk: one enterprise customer generating 30 percent of traffic overloads one partition and one consumer. Options include giving large tenants their own topic, or using sub-keys (customerId plus accountId) when ordering is only needed per account, not per customer.

Within a partition, a single consumer thread is often the bottleneck when each event calls a slow service. The Confluent Parallel Consumer (open source) processes records concurrently with KEY ordering, so different keys from the same partition run in parallel while each key stays sequential, and it tracks offsets safely. You can build the same with a pool of single-threaded executors selected by hash(key) % n.

How it works

  1. Producer sends with key customerId; partition = hash(key) % 200.
  2. Consumer group with up to 200 members, one owner per partition.
  3. Inside each consumer, dispatch by key to ordered lanes.
  4. Commit offsets only below the lowest unfinished record.
  5. Monitor per-partition lag to spot hot keys.

Example

var options = ParallelConsumerOptions.<String, Event>builder()
    .ordering(ParallelConsumerOptions.ProcessingOrder.KEY)
    .maxConcurrency(64)
    .consumer(kafkaConsumer)
    .build();
ParallelStreamProcessor<String, Event> p = ParallelStreamProcessor.createEosStreamProcessor(options);
p.subscribe(List.of("customer-events"));
p.poll(ctx -> handle(ctx.getSingleConsumerRecord()));

Common mistakes

  • Producing with null or random keys, then expecting per-customer order.
  • Unkeyed thread pools inside the consumer.
  • Increasing partitions on a live keyed topic without a migration plan.
  • Ignoring a single hot customer that dominates one partition.

How to answer in the interview

"I use the customer ID as the message key, so all of a customer's events hash to the same partition and are processed in order, while different customers are spread across many partitions and consumers in parallel. I size partitions for the throughput I need and keep the idempotent producer on so retries do not reorder. I watch per-partition lag for hot keys, and split huge tenants if strict ordering is only needed at a finer grain. To go beyond one thread per partition, the parallel consumer processes different keys concurrently while keeping per-key order."

Likely follow-up questions

  • What breaks ordering despite keys? Non-idempotent retries with many in-flight requests, async handlers, retry topics, repartitioning.
  • Why max.in.flight 5 with idempotence? The broker tracks sequence numbers for up to five batches, preserving order.
  • Global ordering? Only with one partition, which removes parallelism.
