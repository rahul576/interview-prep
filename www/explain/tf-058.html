How would you write a custom Terraform provider, and when is it justified?

Terraform · concept · levels senior, lead

In one line

A custom provider is justified when an internal API or platform has no provider and teams need to manage it as code; you write it in Go with the Terraform Plugin Framework, define schemas and CRUD plus import per resource, make Read detect drift and handle not found, and ship it with acceptance tests and signed releases to a registry.

Detailed explanation

Before writing one, check alternatives: an existing community provider, the generic REST API provider, or calling the API from your platform's own tooling. A provider is a long-term product with maintenance, versioning and support. It pays off when many teams manage objects in an internal system (an IPAM, a developer portal, a feature-flag service) and you want the full Terraform workflow: plans, drift detection, reviews and state.

Providers are Go binaries that Terraform runs as plugins over gRPC. New providers should use the Terraform Plugin Framework, which replaced SDKv2 as the recommended library; HashiCorp's scaffolding repository gives a starting point.

For each resource you implement:

  • Schema: attributes, their types, Required, Optional, Computed, Sensitive, plus plan modifiers such as RequiresReplace for force-new and UseStateForUnknown for stable computed IDs, and validators.
  • Create, Read, Update, Delete and ImportState.

Read is the most important function. It must fetch the real object and write the actual values into state, so Terraform can show drift. If the API returns 404, Read must remove the resource from state rather than error, so the next plan proposes a re-create. Values must be normalised consistently, otherwise users get perpetual diffs or "inconsistent result after apply" errors.

You can also add data sources and provider functions. Quality comes from acceptance tests with terraform-plugin-testing that create, update, import and destroy real objects, generated docs (tfplugindocs), and releases built with GoReleaser and GPG-signed for the public or a private registry.

How it works

  1. Confirm no existing provider or generic option fits.
  2. Scaffold with the Plugin Framework; define the provider configuration.
  3. For each resource, define the schema and plan modifiers.
  4. Implement CRUD and import against the API client.
  5. Make Read handle drift and not-found correctly.
  6. Write acceptance tests, generate docs, sign and publish.

Example

func (r *dnsRecordResource) Read(ctx context.Context, req resource.ReadRequest, resp *resource.ReadResponse) {
    var state dnsRecordModel
    resp.Diagnostics.Append(req.State.Get(ctx, &state)...)

    rec, err := r.client.GetRecord(ctx, state.ID.ValueString())
    if errors.Is(err, api.ErrNotFound) {
        resp.State.RemoveResource(ctx) // deleted outside Terraform
        return
    }
    if err != nil {
        resp.Diagnostics.AddError("read failed", err.Error())
        return
    }
    state.Value = types.StringValue(rec.Value) // reflect real value: drift shows in plan
    resp.Diagnostics.Append(resp.State.Set(ctx, &state)...)
}

Common mistakes

  • Read returning the configured value instead of the real one, hiding drift.
  • Erroring on 404 instead of removing from state.
  • Missing RequiresReplace where the API cannot update a field.
  • No import support, so existing objects cannot be adopted.
  • Breaking schema changes without a major version.

How to answer in the interview

"I'd only write a provider when we have an internal API that teams need to manage as code and nothing existing fits, including the generic REST provider. I'd use Go with the Terraform Plugin Framework, which succeeded SDKv2. For each resource I define the schema, required, optional, computed, and which fields force replacement, and implement create, read, update, delete and import. Read is critical: it fetches the real object so drift shows up, and removes the resource from state on not found. Then acceptance tests against real objects, generated docs and signed releases to a registry."

Likely follow-up questions

  • What makes a provider behave badly? Perpetual diffs, unhandled 404s, missing import and inconsistent values after apply.
  • Plugin Framework or SDKv2? Framework for new work; SDKv2 is maintained for existing providers.
  • Private distribution? A private registry or a network mirror.
