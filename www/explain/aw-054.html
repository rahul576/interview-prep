What problem does RDS Proxy solve?

Cloud (AWS) · concept · levels mid

In one line

RDS Proxy is a managed connection pooler in front of RDS and Aurora that multiplexes many short-lived client connections, especially from Lambda, over a warm pool of database connections, speeds up failover, and adds IAM authentication with credentials from Secrets Manager; session state can cause pinning.

Detailed explanation

Every database connection consumes memory and CPU on the server, and engines have a max_connections limit. Creating connections is also expensive (TLS handshake, authentication, backend process creation in PostgreSQL). Serverless and highly scaled applications break this model: a traffic spike can start hundreds of Lambda execution environments, each opening its own connection, quickly exhausting the limit and adding connection churn that slows the database.

RDS Proxy sits between the application and the database. Clients connect to the proxy endpoint, and the proxy keeps a pool of database connections, sized by a percentage of max_connections. It multiplexes clients by lending a database connection per transaction and returning it afterwards, so thousands of client connections can share a few dozen backend connections. Excess requests queue briefly instead of failing.

On failover, the proxy keeps client connections open and reconnects to the new writer, bypassing DNS propagation, which AWS says can cut failover time by up to two thirds for Aurora and RDS. It supports IAM database authentication from clients, so Lambda uses its role instead of passwords, and fetches database credentials from Secrets Manager. It runs in your VPC across multiple AZs and can provide read-only endpoints for replicas.

Pinning happens when a session uses state that cannot be shared, such as temporary tables, session variables via SET, prepared statements in some cases, advisory locks or user-defined variables; that client then holds a dedicated connection, reducing efficiency. Monitor DatabaseConnectionsCurrentlySessionPinned and avoid such features or use initialization queries.

How it works

  1. Lambda opens a connection to the proxy endpoint with an IAM auth token.
  2. Proxy authenticates the client and gets DB credentials from Secrets Manager.
  3. For each transaction, it borrows a pooled database connection.
  4. After commit, the connection returns to the pool.
  5. On failover, the proxy redirects to the new primary while clients stay connected.

Example

aws rds create-db-proxy --db-proxy-name orders-proxy --engine-family POSTGRESQL \
  --auth '[{"AuthScheme":"SECRETS","SecretArn":"arn:aws:secretsmanager:eu-west-1:111122223333:secret:orders-db","IAMAuth":"REQUIRED"}]' \
  --role-arn arn:aws:iam::111122223333:role/rds-proxy-secrets \
  --vpc-subnet-ids subnet-a subnet-b --require-tls
aws rds register-db-proxy-targets --db-proxy-name orders-proxy \
  --db-cluster-identifiers orders
token = rds.generate_db_auth_token(DBHostname=PROXY, Port=5432, DBUsername="app")
conn = psycopg.connect(host=PROXY, user="app", password=token, sslmode="require")

Common mistakes

  • Relying only on in-function pooling and assuming Lambda scale will not exhaust connections.
  • Heavy use of session state, causing pinning and no real pooling.
  • Forgetting the proxy needs a role that can read the secret.
  • Expecting the proxy to fix slow queries rather than connection pressure.

How to answer in the interview

"Databases have limited connections and each costs memory. Lambda and other highly scaled apps open many short-lived connections, which can exhaust max_connections and overload the database with churn. RDS Proxy is a managed pooler: it keeps a warm pool of database connections and multiplexes many client connections over them per transaction. It also shortens failover by keeping client connections open while it reconnects to the new primary, and supports IAM auth with credentials in Secrets Manager. Session features like temporary tables cause pinning, which reduces pooling."

Likely follow-up questions

  • Why is pooling inside Lambda not enough? Each execution environment has its own pool; concurrency multiplies connections.
  • Does RDS Proxy cost extra? Yes, billed per vCPU or ACU of the target database.
  • What alternatives exist? PgBouncer on EC2 or ECS, or the Aurora Data API for HTTP-based access.
