How does transaction management work in Spring?

Spring Framework · concept · levels mid

In one line

Spring provides a uniform PlatformTransactionManager abstraction (JDBC, JPA, JTA, Kafka, reactive) used declaratively with @Transactional through an AOP proxy or programmatically with TransactionTemplate; the transaction's connection is bound to the thread, and attributes control propagation, isolation, timeout, readOnly and rollback rules.

Detailed explanation

Every data access technology has its own transaction API: JDBC Connection.commit(), JPA EntityTransaction, JTA UserTransaction. Spring hides them behind PlatformTransactionManager (and ReactiveTransactionManager for R2DBC and reactive Mongo). Implementations include DataSourceTransactionManager/JdbcTransactionManager, JpaTransactionManager (the Spring Boot default with JPA), JtaTransactionManager for distributed XA transactions, and KafkaTransactionManager. Your code stays the same whichever one is configured.

Declarative transactions are the usual approach. Annotate a service method (or class) with @Transactional. The bean's AOP proxy intercepts the call and asks the transaction manager to begin a transaction according to the attributes. The manager obtains a connection or EntityManager and binds it to the current thread via TransactionSynchronizationManager, so every repository, JdbcTemplate and EntityManager used in that call shares it. On normal return the proxy commits; if a RuntimeException or Error escapes it rolls back (checked exceptions commit unless rollbackFor says otherwise).

Attributes: propagation (REQUIRED joins or creates, REQUIRES_NEW suspends and starts a new one, plus SUPPORTS, MANDATORY, NESTED and others), isolation (READ_COMMITTED, REPEATABLE_READ, SERIALIZABLE, or database default), timeout, readOnly (a hint: with Hibernate it sets flush mode to manual and skips dirty checking snapshots, and the JDBC connection may be marked read-only, which some drivers and routing data sources use), and rollbackFor/noRollbackFor.

Programmatic transactions with TransactionTemplate (or the transaction manager directly) suit cases where you need a transaction around just part of a method, or dynamic decisions. TransactionalEventListener and TransactionSynchronization let you run code after commit, such as sending a message only when data is safely stored.

How it works

  1. Spring Boot auto-configures the appropriate transaction manager.
  2. @EnableTransactionManagement (automatic in Boot) registers the interceptor.
  3. The proxy reads attributes and calls getTransaction().
  4. Resources are bound to the thread; repositories participate.
  5. Commit or rollback, after-commit callbacks, resources unbound.

Example

@Service
class TransferService {
    private final TransactionTemplate tx;
    TransferService(PlatformTransactionManager tm) {
        this.tx = new TransactionTemplate(tm);
        this.tx.setIsolationLevel(TransactionDefinition.ISOLATION_REPEATABLE_READ);
    }

    @Transactional(timeout = 5, rollbackFor = InsufficientFundsException.class)
    public void transfer(long from, long to, BigDecimal amount) throws InsufficientFundsException {
        accounts.debit(from, amount);
        accounts.credit(to, amount);
    }

    public void importBatch(List<Row> rows) {
        rows.forEach(r -> tx.executeWithoutResult(status -> repo.save(map(r)))); // one tx per row
    }
}

Common mistakes

  • Self-invocation, so no transaction starts.
  • Assuming checked exceptions roll back.
  • Holding a transaction open during remote HTTP calls.
  • Believing readOnly prevents writes in every database.

How to answer in the interview

"Spring offers a consistent abstraction, PlatformTransactionManager, with implementations for JDBC, JPA, JTA and Kafka. Usually I use declarative transactions: @Transactional on a service method. The AOP proxy asks the manager to begin a transaction, binding the connection or EntityManager to the thread so all repositories share it. On normal return it commits; on a runtime exception it rolls back. Attributes control propagation, isolation, timeout, readOnly and rollback rules. When I need finer control, I use TransactionTemplate."

Likely follow-up questions

  • What does readOnly do with JPA? Hibernate uses manual flush and skips dirty checking; it's an optimisation hint.
  • Send a message only after commit? @TransactionalEventListener(phase = AFTER_COMMIT) or an outbox.
  • Distributed transactions? JTA/XA is possible but heavy; prefer sagas and the outbox pattern.
