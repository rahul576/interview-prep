The plan in CI differs from the plan a developer gets locally for the same commit. What could cause that?

Terraform · scenario · levels mid, senior

In one line

Different plans for the same commit come from different Terraform or provider versions, inputs (tfvars, TF_VAR_ variables, backend config), credentials and target account, the local working copy, or time-dependent data and drift between runs; compare them and treat CI as the only trusted plan.

Detailed explanation

A plan is a function of code, inputs, versions, identity and the real world at that moment. If any of these differ, the plan differs.

Versions. If .terraform.lock.hcl is not committed, or a developer ran init -upgrade, local providers may be newer than CI's, with changed defaults or diff logic. A different Terraform CLI version can also change behaviour.

Inputs. CI may pass -var-file=prod.tfvars, TF_VAR_ environment variables or -backend-config values that the developer does not. Conversely, the developer may have a terraform.tfvars or *.auto.tfvars that is git-ignored but loaded automatically.

Credentials and target. The developer might be logged into a different subscription or account, or a different region. Older AzureRM versions silently used the CLI's default subscription; AzureRM 4 requires it explicitly, which helps. Different permissions can also make data sources return different results.

Working copy. Uncommitted changes, a different branch, or stale modules in .terraform/modules after the module source changed without re-init.

Time and reality. Data sources such as "latest AMI" or "latest image version", functions like timestamp(), and real drift that happened between the two runs.

To diagnose, compare the headers: terraform version, the lock file, backend settings, identity (az account show, aws sts get-caller-identity) and inputs. To prevent, commit the lock file, pin the CLI version, keep inputs in committed files, and let only CI plans gate merges and applies.

How it works

  1. Compare Terraform and provider versions on both sides.
  2. Compare var files, TF_VAR_ variables and backend config.
  3. Compare identity, subscription, account and region.
  4. Check the working copy: git status, re-run init.
  5. Look for time-dependent data sources and recent drift.
  6. Standardise: lock file, pinned CLI, containerised runner.

Example

terraform version
git status --short && git rev-parse HEAD
env | grep '^TF_VAR_'
ls *.auto.tfvars terraform.tfvars 2>/dev/null
az account show --query "{sub:id,name:name}"   # or: aws sts get-caller-identity
terraform init -reconfigure -upgrade=false

Common mistakes

  • Not committing the lock file.
  • Hidden auto-loaded tfvars on a laptop.
  • Using timestamp() or unpinned "latest" lookups in arguments.
  • Trusting a local plan for production decisions.

How to answer in the interview

"Several things can differ. Versions: without a committed lock file or with a different Terraform binary, providers behave differently. Inputs: CI might pass different tfvars, TF_VAR variables or backend config, and locally there may be an auto.tfvars that isn't in Git. Credentials: the developer may be in a different subscription or account. The local copy may have uncommitted changes or stale modules. And time-dependent data sources or real drift between runs. I compare versions, inputs and identity, and make CI the only place plans are trusted."

Likely follow-up questions

  • How do you make plans reproducible? Lock file, pinned CLI, a container image for runs and committed inputs.
  • What about latest-image data sources? Pin image versions explicitly and update via PRs.
  • Can you detect the identity in the plan? Output or log the caller identity at the start of the job.
