A plan contains 3,000 lines of changes and reviewers cannot meaningfully read it. What do you do?

Terraform · scenario · levels mid, senior

In one line

A 3,000-line plan is a warning sign of a change or state that is too big or of noise; remove perpetual diffs, summarise with terraform show -json (counts per action and type), highlight destroys and replacements, let policy checks catch dangerous patterns, and split the change into smaller PRs.

Detailed explanation

Reviewers cannot meaningfully read thousands of lines. When they try, they skim, and a single database replacement hides between hundreds of tag updates. The goal is to make the risky parts impossible to miss and the overall change small enough to reason about.

Find the cause. Big plans come from: many unrelated changes batched into one PR; a state that is too large, so every change touches a lot; a module or provider upgrade causing changes everywhere; or noise, such as perpetual diffs (API normalisation, ordering of lists, timestamps) and accumulated drift. Fix noise first: correct the code that causes perpetual diffs, reconcile drift in a separate PR, and use ignore_changes only where another system legitimately owns the attribute.

Make it reviewable. Export the plan as JSON with terraform show -json and generate a summary posted to the PR: counts of create, update, replace and destroy per resource type, then an explicit list of every destroy and replacement with the reason Terraform gives. Reviewers read the summary first and dig into details only where needed. Tools such as tf-summarize, Atlantis or HCP Terraform's structured run output help.

Automate the dangerous checks. Policy as code (OPA/Conftest or Sentinel) fails the plan if it deletes protected resource types, opens public access or changes IAM in forbidden ways, so humans are not the only safety net.

Split. Break the change into smaller, focused PRs: mechanical refactors with moved blocks first (which should show no changes), then behavioural changes per component or environment. If the state itself is huge, plan to split the state by ownership and lifecycle.

How it works

  1. Identify the source: batching, noise, upgrade or oversized state.
  2. Remove perpetual diffs and reconcile drift separately.
  3. Generate a JSON-based summary on the PR.
  4. Highlight destroys and replacements explicitly.
  5. Enforce policy checks on the plan.
  6. Split into smaller PRs and, if needed, smaller states.

Example

terraform show -json tfplan > plan.json
jq -r '.resource_changes[]
  | select(.change.actions != ["no-op"])
  | "\(.change.actions | join("/"))\t\(.type)"' plan.json \
  | sort | uniq -c | sort -rn
#  412 update        azurerm_monitor_diagnostic_setting
#    3 create        azurerm_subnet
#    1 delete/create azurerm_postgresql_flexible_server   <- review this

jq -r '.resource_changes[] | select(.change.actions | index("delete")) | .address' plan.json

Common mistakes

  • Approving because "most of it is tags".
  • Combining refactors and behaviour changes in one PR.
  • Ignoring perpetual diffs until nobody reads plans.
  • Relying only on humans to spot destroys.

How to answer in the interview

"A plan that size is a warning sign: the change is too big, the state is too large, or there's noise like perpetual diffs hiding real changes. First I remove noise by fixing perpetual diffs and drift. Then I make the plan reviewable: export it with terraform show -json and post a summary to the PR with counts of creates, updates and destroys per resource type, and a highlighted list of every destroy and replacement. Policy checks catch dangerous patterns automatically. Most importantly, I split the change into smaller PRs and, if the state is huge, plan to split it."

Likely follow-up questions

  • What always needs human attention? Destroys, replacements, IAM and network exposure changes.
  • How do you verify a refactor PR? The plan must show only moves and no changes.
  • Can you limit apply scope? -target exists for emergencies, not as a routine workflow.
