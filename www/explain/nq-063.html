How would you use Comparator.comparing() to sort objects by a particular field?

Coding Exercises · concept · levels entry

In one line

Comparator.comparing(keyExtractor) builds a comparator that compares objects by an extracted key's natural order, e.g. comparing(Product::getPrice); use comparingInt/Long/Double to avoid boxing, a second argument for a custom key comparator, and chain thenComparing and reversed.

Detailed explanation

Before Java 8 you wrote anonymous Comparator classes with manual compare logic. Comparator.comparing replaces that with a declarative style: you say which field to compare, and the factory builds the comparator.

Basic form. Comparator.comparing(Function<T, U> keyExtractor) requires U to be Comparable. For each pair, it extracts the keys and calls compareTo. Comparator.comparing(Product::getName) sorts by name.

Primitive specialisations. comparingInt(ToIntFunction), comparingLong and comparingDouble work directly with primitive keys using Integer.compare, Long.compare and Double.compare. comparing(Product::getPrice) would box each double into a Double before comparing; comparingDouble(Product::getPrice) avoids that, which is slightly faster and clearer.

Custom key comparator. The two-argument overload comparing(keyExtractor, keyComparator) compares keys with your comparator: comparing(Product::getName, String.CASE_INSENSITIVE_ORDER), or comparing(Product::getPrice, Comparator.reverseOrder()) for descending price only.

Chaining. thenComparing(...) adds tie-breakers (with the same overloads, including thenComparingInt and so on). reversed() reverses the entire comparator built so far — a common source of bugs. In comparing(Product::getCategory).thenComparing(Product::getPrice).reversed(), both category and price are reversed. To reverse only price, use thenComparing(Product::getPrice, Comparator.reverseOrder()).

Nulls. If keys can be null, wrap the key comparator: comparing(Product::getName, Comparator.nullsLast(Comparator.naturalOrder())).

The resulting comparator can be passed to sorted, List.sort, max, min, Collectors.maxBy, TreeMap and TreeSet constructors, and stored in a constant for reuse.

How it works

  1. Provide a key extractor, usually a method reference.
  2. The factory returns a Comparator comparing extracted keys.
  3. Optional key comparator customises key comparison.
  4. thenComparing adds secondary keys; reversed flips everything so far.
  5. Use it anywhere a Comparator is accepted.

Example

Comparator<Product> byPrice = Comparator.comparingDouble(Product::getPrice);
Comparator<Product> byNameCi = Comparator.comparing(Product::getName, String.CASE_INSENSITIVE_ORDER);

// category asc, then price desc
Comparator<Product> catThenPriceDesc = Comparator
        .comparing(Product::getCategory)
        .thenComparing(Product::getPrice, Comparator.reverseOrder());

products.stream().sorted(byPrice).toList();
products.sort(catThenPriceDesc);
Optional<Product> cheapest = products.stream().min(byPrice);
TreeSet<Product> set = new TreeSet<>(byNameCi);

// pitfall: reverses category AND price
Comparator<Product> oops = Comparator.comparing(Product::getCategory)
        .thenComparing(Product::getPrice).reversed();

Common mistakes

  • Using comparing with primitive getters and boxing unnecessarily.
  • Putting .reversed() at the end and reversing all keys.
  • Type inference failures with lambdas in chains; method references or explicit types fix them.
  • Forgetting null handling for optional fields.

How to answer in the interview

"Comparator.comparing takes a key extractor and builds a comparator that compares those keys by natural order, like Comparator.comparing(Product::getPrice). For primitive keys I use comparingInt, comparingLong or comparingDouble to avoid boxing. A second argument supplies a comparator for the key, such as String.CASE_INSENSITIVE_ORDER. Comparators chain: comparing category, thenComparing price with reverseOrder, and reversed() flips the whole order so far. I pass the result to sorted, list.sort, max, min or a TreeMap."

Likely follow-up questions

  • Why can reversed() behave unexpectedly in a chain? It reverses everything built before it, not just the last key.
  • Why does comparing(p -> p.getName()).reversed() sometimes not compile? Type inference loses the type; use a method reference or Comparator.<Product, String>comparing.
  • Why not subtract prices? Double.compare handles NaN and precision; subtraction can overflow for ints.
