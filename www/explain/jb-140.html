What is the difference between WHERE and HAVING?

Databases & SQL · concept · levels entry, mid

In one line

WHERE filters individual rows before grouping and cannot use aggregates, while HAVING filters groups after GROUP BY and can use aggregates such as COUNT, SUM or AVG.

Detailed explanation

SQL is written in one order but evaluated logically in another: FROM / JOIN, WHERE, GROUP BY, HAVING, SELECT, DISTINCT, ORDER BY, LIMIT. This explains the difference.

WHERE runs on the raw rows produced by FROM and joins. At that point no groups exist yet, so WHERE SUM(amount) > 1000 is an error. WHERE conditions on plain columns can use indexes and reduce the number of rows that the more expensive grouping step must process.

HAVING runs after GROUP BY has collapsed rows into groups, so it sees one row per group and can test aggregate values: customers with more than five orders, departments whose average salary exceeds a threshold, duplicate emails (HAVING COUNT(*) > 1). HAVING can technically also test grouping columns, but a condition that does not need an aggregate should be in WHERE: the result is the same, while WHERE filters earlier. Many optimizers push such predicates down automatically, but writing them in WHERE is clearer and portable.

Because SELECT is evaluated after HAVING, standard SQL does not let HAVING reference a SELECT alias; PostgreSQL rejects it, while MySQL allows it as an extension. Repeat the expression for portability. Also note that window functions are evaluated after HAVING, so you cannot filter them in either clause; use a subquery or CTE.

How it works

  1. FROM and JOIN build the row set.
  2. WHERE keeps rows matching row-level conditions.
  3. GROUP BY forms groups.
  4. Aggregates are computed per group.
  5. HAVING keeps groups matching aggregate conditions.
  6. SELECT projects columns, then ORDER BY and LIMIT apply.

Example

SELECT customer_id,
       COUNT(*)    AS paid_orders,
       SUM(amount) AS total
FROM orders
WHERE status = 'PAID'                   -- row filter, can use an index
  AND created_at >= DATE '2026-01-01'
GROUP BY customer_id
HAVING SUM(amount) > 1000               -- group filter on an aggregate
ORDER BY total DESC;

-- Find duplicate emails
SELECT email, COUNT(*) FROM users GROUP BY email HAVING COUNT(*) > 1;

Common mistakes

  • Putting row conditions such as status = 'PAID' in HAVING.
  • Trying to use an aggregate in WHERE.
  • Relying on SELECT aliases in HAVING, which is not portable.
  • Using HAVING without GROUP BY unintentionally, which treats the whole table as one group.

How to answer in the interview

"WHERE filters rows before grouping, so it can't use aggregates; HAVING filters groups after GROUP BY, so it can use COUNT, SUM or AVG. The logical order is FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY. For example, to find customers who spent more than a thousand on paid orders, I filter status equals PAID in WHERE, group by customer, and put SUM of amount greater than a thousand in HAVING. Any condition that doesn't need an aggregate belongs in WHERE, because it reduces rows early and can use an index."

Likely follow-up questions

  • Logical evaluation order? FROM, JOIN, WHERE, GROUP BY, HAVING, SELECT, DISTINCT, ORDER BY, LIMIT.
  • Can HAVING exist without GROUP BY? Yes; the whole result becomes one group.
  • How to filter on a window function? Compute it in a subquery or CTE and filter in the outer query.
