Why are transactions needed when multiple database operations must succeed or fail together?

Spring Framework · scenario · levels entry

In one line

Transactions give atomicity: several related operations either all succeed or all roll back, so a failure never leaves partial, inconsistent data (a debit without its credit); they also provide consistency, isolation and durability (ACID).

Detailed explanation

Many business operations are made of multiple database writes that only make sense together. In a money transfer, you debit account A and credit account B. If the application crashes, the network drops, or the second update hits a constraint after the first one succeeded, money has disappeared. In an order, you insert the order, insert its lines and reduce stock; half of that leaves orders without lines or stock reduced for orders that don't exist.

A transaction groups these writes into one unit with ACID guarantees:

  • Atomicity: all or nothing. If anything fails before commit, the database undoes every change in the transaction.
  • Consistency: constraints (foreign keys, unique keys, checks) hold at commit, so the database moves from one valid state to another.
  • Isolation: concurrent transactions don't see each other's intermediate states and don't interfere, to a degree set by the isolation level (read committed, repeatable read, serializable).
  • Durability: once committed, the change survives crashes, thanks to the write-ahead log.

In Spring you mark the service method that represents the business operation with @Transactional. All repository calls inside share one connection and commit together at the end; a runtime exception rolls everything back.

Transactions have limits: they only cover one database. A call to an external API, an email or a Kafka message inside the method cannot be rolled back with it. For those, call the external system after commit, use the outbox pattern, idempotency keys, or a saga with compensating actions. Also keep transactions short, because they hold locks and connections.

How it works

  1. Begin transaction.
  2. Execute each write; the database records changes in its log and holds locks.
  3. If all succeed, commit: changes become durable and visible.
  4. If any fails, roll back: all changes are undone.
  5. Locks are released; the connection returns to the pool.

Example

@Service
public class TransferService {
    @Transactional
    public void transfer(long fromId, long toId, BigDecimal amount) {
        Account from = accounts.findByIdForUpdate(fromId);
        Account to = accounts.findByIdForUpdate(toId);
        from.debit(amount);          // throws InsufficientFunds (runtime) -> rollback
        to.credit(amount);
    }                                // commit: both changes or neither
}
BEGIN;
UPDATE account SET balance = balance - 100 WHERE id = 1;
UPDATE account SET balance = balance + 100 WHERE id = 2;
COMMIT;   -- or ROLLBACK on any error

Common mistakes

  • Running related writes without a transaction (auto-commit per statement).
  • Calling external APIs inside the transaction and assuming they roll back too.
  • Long transactions that hold locks while waiting for users or networks.
  • Catching exceptions and committing partial work.

How to answer in the interview

"Because a business operation often consists of several writes that only make sense together. In a money transfer I debit one account and credit another; if the second update fails after the first succeeded, money disappears. A transaction gives atomicity, both commit or both roll back, so the database never shows a half-done operation. It also gives consistency, isolation from concurrent users and durability once committed. In Spring I put @Transactional on the service method, for example one that saves an order, its lines and reduces stock. External calls aren't covered, so I handle them after commit or with an outbox."

Likely follow-up questions

  • External API call inside the transaction? It can't be rolled back; call it after commit, use an outbox or a saga.
  • What is an isolation level? How much concurrent transactions can see of each other; trades consistency for concurrency.
  • Multiple databases? XA/JTA or, more commonly, sagas with compensation.
