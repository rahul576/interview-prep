How do you test Ansible roles with Molecule?

Configuration Management · concept · levels mid

In one line

Molecule tests Ansible roles by creating disposable instances (containers or VMs), converging the role, running an idempotence check, verifying the result with Ansible asserts or Testinfra, and destroying everything, typically in CI on every pull request.

Detailed explanation

Roles are code shared across teams, and like any code they regress: a variable rename, a new OS version, a task that is not idempotent. Molecule gives roles a repeatable test harness. A scenario (molecule/default/) describes the platforms to test on, the driver that creates them (Docker or Podman containers, or VMs/cloud instances via plugins), the playbook that applies the role (converge.yml) and how results are checked (verify.yml).

molecule test runs the full sequence: dependency (install collections/roles), destroy any leftovers, syntax check, create, prepare, converge, idempotence, side effect, verify, and destroy. During development you use the individual steps: molecule converge repeatedly, molecule login to look inside, molecule verify, and molecule destroy at the end.

The idempotence step is the most valuable: it applies the role a second time and fails if any task reports changed. A role that always changes something will restart services on every run and hide real drift. Verification asserts outcomes, not tasks: "nginx is listening on port 80 and serves the health page", written as Ansible tasks (the default verifier in current Molecule) or Python Testinfra tests.

Containers are fast but lack a real init system and kernel features; roles that manage systemd units, sysctl or firewalls often need privileged systemd-enabled images or VMs. In recent Molecule versions linting is no longer part of the sequence, so ansible-lint runs as a separate CI step. A CI matrix (for example Ubuntu 24.04 and Rocky 9) catches distro differences.

How it works

  1. molecule init scenario creates molecule.yml, converge.yml and verify.yml.
  2. The driver creates the platform instances.
  3. Converge applies the role; failures stop the run.
  4. Idempotence reruns converge and fails on any changed task.
  5. Verify runs assertions; destroy cleans up.
  6. CI runs ansible-lint and molecule test per platform on every PR.

Example

# molecule/default/molecule.yml
driver:
  name: podman
platforms:
  - name: ubuntu2404
    image: docker.io/geerlingguy/docker-ubuntu2404-ansible
    command: /lib/systemd/systemd
    privileged: true
verifier:
  name: ansible
# molecule/default/verify.yml
- hosts: all
  tasks:
    - ansible.builtin.uri:
        url: http://localhost/health
        status_code: 200

Common mistakes

  • Testing only "the playbook ran" instead of verifying real behaviour.
  • Skipping the idempotence step or masking it with changed_when: false everywhere.
  • Using plain containers for roles that need systemd, then fighting false failures.
  • Testing one OS while the role claims to support five.

How to answer in the interview

"I use Molecule. A scenario defines the platforms, usually Podman or Docker containers, or VMs when the role needs systemd or kernel features. molecule test creates the instances, converges the role, runs it a second time as an idempotence check, which fails if anything reports changed, then verifies the outcome with Ansible assertions or Testinfra, for example that nginx answers on port 80, and destroys everything. In CI I run ansible-lint plus a Molecule matrix across the supported distros on every pull request, so shared roles don't regress."

Likely follow-up questions

  • Why is the idempotence step valuable? It proves reruns are safe and that "changed" really means something changed.
  • Testinfra or Ansible verifier? Ansible verifier needs no extra language; Testinfra gives richer Python assertions.
  • How do you test roles needing cloud APIs? Use a cloud or delegated driver against a sandbox account, or mock at the boundary.
