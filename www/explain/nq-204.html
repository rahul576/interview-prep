What are RESTful web services, and what are the key principles of REST APIs?

REST & API Design · concept · levels entry

In one line

RESTful web services expose resources identified by URIs that clients manipulate through representations (usually JSON) with standard HTTP methods; the key principles are client-server, statelessness, cacheability, a uniform interface, a layered system and optionally HATEOAS, with correct status codes.

Detailed explanation

REST, Representational State Transfer, is an architectural style described by Roy Fielding in his 2000 dissertation. A RESTful web service applies it over HTTP: instead of calling remote procedures like getCustomerOrders(), clients work with resources such as customers and orders.

Key principles (constraints):

  • Resources and URIs: each resource has a stable identifier, e.g. /customers/7/orders/42.
  • Representations: clients never touch the resource directly; they exchange representations of its state, typically JSON, sometimes XML, chosen via content negotiation.
  • Uniform interface: standard HTTP methods with defined semantics (GET read, POST create, PUT replace, PATCH partial update, DELETE remove), status codes (200, 201, 400, 404, 409, 500...) and media types. Messages are self-descriptive.
  • Client-server separation: front end and back end evolve independently.
  • Statelessness: every request carries all information needed, including authentication such as a bearer token; the server keeps no session. Any server instance can handle any request, so scaling out behind a load balancer is easy and failures do not lose sessions.
  • Cacheability: responses declare if and how long they can be cached (Cache-Control, ETag), cutting latency and load.
  • Layered system: load balancers, gateways, caches and CDNs can sit between client and server transparently.
  • HATEOAS (hypermedia as the engine of application state): responses include links to related resources and possible next actions, so clients discover the API dynamically. Most real APIs skip it.
  • Code on demand is an optional constraint.

Compared with SOAP web services (XML envelopes, WSDL contracts, often a single endpoint), REST is lighter, uses HTTP natively and is the default for web and mobile APIs. In Java, Spring MVC (@RestController) or JAX-RS (Jakarta REST) implement RESTful services.

How it works

  1. Client sends an HTTP request to a resource URI with a method.
  2. Request includes headers (Accept, Authorization) and optional body.
  3. Server processes it statelessly.
  4. Server returns a representation, status code and caching headers.

Example

GET /api/customers/7/orders?status=PAID
Accept: application/json
Authorization: Bearer eyJhbGci...

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: private, max-age=60

[{ "id": 42, "status": "PAID", "total": 1499.00,
   "links": { "self": "/api/orders/42" } }]
@RestController
@RequestMapping("/api/customers/{customerId}/orders")
class CustomerOrdersController {
    @GetMapping
    List<OrderDto> list(@PathVariable long customerId, @RequestParam Optional<OrderStatus> status) {
        return service.find(customerId, status);
    }
}

Common mistakes

  • Verbs in URIs (/getOrders) instead of resources.
  • Storing user state in server sessions.
  • Returning 200 for every outcome.
  • Calling it REST while tunnelling everything through POST.

How to answer in the interview

"REST, representational state transfer, is an architectural style described by Roy Fielding. A RESTful service exposes resources like orders or customers, each identified by a URI, and clients manipulate them through representations, usually JSON, using standard HTTP methods. The key constraints are client-server separation; statelessness, so each request carries everything needed, like the token, and the server keeps no session; cacheable responses with proper headers; a uniform interface with standard methods, status codes and media types; a layered system so gateways and proxies can sit in between; and optionally HATEOAS links to related actions."

Likely follow-up questions

  • Why does statelessness help scaling? Any instance can serve any request, so you scale horizontally without sticky sessions.
  • REST vs SOAP? REST is lightweight and uses HTTP semantics; SOAP uses XML envelopes and WSDL with WS-* standards.
  • What is HATEOAS? Responses contain links that tell clients which actions are possible next.
