What limits do you hit when a Kubernetes cluster grows very large, and how do you handle them?

Kubernetes · concept · levels senior, lead

In one line

Upstream tests about 5,000 nodes, 150,000 pods and 110 pods per node, but you usually hit etcd size and object count, API server load from LIST/WATCH, IP and pods-per-node limits, kube-proxy and DNS scale first; tune those, and often prefer several smaller clusters managed as a fleet.

Detailed explanation

The official large-cluster guidance lists roughly 5,000 nodes, 150,000 total pods, 300,000 total containers and 110 pods per node; managed services publish their own limits. These are not hard walls but tested envelopes, and the practical limits arrive earlier depending on workload shape.

etcd: it holds every object. The default storage quota is 2 GB and the commonly recommended maximum is 8 GB; beyond that, compaction, defragmentation, snapshots and leader elections get slow. Large ConfigMaps or Secrets, huge numbers of CRD instances (some operators create one object per tiny thing), and high event volume fill it. Write rate and disk latency matter as much as size.

API server: the biggest load comes from clients doing frequent full LIST calls instead of informers with watches, especially across all namespaces. Every node's kubelet and every DaemonSet pod watching resources multiplies load. API Priority and Fairness protects critical traffic, but fixing chatty clients is the real cure. Recent releases improved this with consistent reads from the watch cache and streaming lists.

Networking and nodes: pod IPs per subnet or node, kube-proxy iptables rule counts (with tens of thousands of Services, iptables updates become slow; nftables mode or eBPF dataplanes scale better), CoreDNS query load, and load balancer target limits. Scheduler throughput matters for very large batch bursts.

Handling it: right-size the control plane (managed tiers), keep etcd healthy (defrag, fast disks, event TTL, lean objects, consider a separate etcd for events on self-managed clusters), fix chatty controllers, use APF, and choose a scalable dataplane. Often the better architectural answer is many smaller clusters (per region, environment or tenant group) managed as a fleet with GitOps and centralised policy and observability, which also limits blast radius and makes upgrades less risky.

How it works

  1. Monitor etcd size, latency and object counts by resource.
  2. Monitor API request rates by client and verb; find heavy LISTs.
  3. Track IP usage, pods per node and Service counts.
  4. Tune: event TTL, object sizes, informers, APF, dataplane mode.
  5. Scale control plane tier or etcd hardware.
  6. Split into multiple clusters when limits or blast radius demand it.

Example

# biggest object types in the API server's storage
kubectl get --raw /metrics | grep apiserver_storage_objects | sort -k2 -n | tail
# promql: who is doing LISTs
# topk(10, sum by (resource, client) (rate(apiserver_request_total{verb="LIST"}[5m])))
etcdctl endpoint status --write-out=table

Common mistakes

  • Treating the documented limits as targets.
  • Operators that create millions of small CRs.
  • Cluster-wide LISTs from scripts on a schedule.
  • One giant cluster where every upgrade is high risk.

How to answer in the interview

"Upstream tests up to about 5,000 nodes, 150,000 pods and 110 pods per node, and managed services publish their own limits, but you usually hit other problems first. etcd has a recommended maximum around 8 GB, so many objects, large ConfigMaps, events and CRDs slow it down. The API server suffers from clients doing full LISTs instead of watches. Networking adds limits on IPs, kube-proxy rules and DNS. I tune event retention and object sizes, fix chatty clients, use API Priority and Fairness and size the control plane. Often the better answer is several smaller clusters managed as a fleet, which also limits blast radius."

Likely follow-up questions

  • Downsides of many small clusters? More control planes to upgrade and pay for, fleet tooling, cross-cluster networking and duplicated add-ons.
  • Why is iptables mode a limit? Rule updates are linear and slow with many Services; nftables or eBPF scale better.
  • How do you find chatty clients? API server metrics and audit logs grouped by user agent and verb.
