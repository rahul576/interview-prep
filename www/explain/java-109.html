How do Comparable and Comparator differ? How do you sort a list of employees by salary then name?

Core Java & OOP · concept · levels entry, mid

In one line

Comparable is implemented by the class itself and defines its single natural ordering via compareTo; Comparator is a separate object defining any number of external orderings via compare, and is composed with Comparator.comparing(...).thenComparing(...).

Detailed explanation

Comparable<T> lives in java.lang and has one method, int compareTo(T other). A class that implements it says "this is how instances of me are naturally ordered": String alphabetically, Integer numerically, LocalDate chronologically. Sorted collections such as TreeSet and TreeMap, and Collections.sort(list) without arguments, use it.

Comparator<T> lives in java.util and has int compare(T a, T b). It is used when the class has no natural order, when you cannot modify the class, or when you need several different orders (by salary, by name, by joining date). Since Java 8, Comparator has rich factory and combinator methods: comparing, comparingInt, thenComparing, reversed, nullsFirst and nullsLast, which make multi-key sorting readable and safe.

Both return a negative number, zero or a positive number. An important rule is consistency with equals: if compareTo returns 0, ideally equals returns true. Sorted sets and maps treat a comparison result of 0 as "the same key", so an inconsistent ordering silently drops or overwrites elements. Also avoid the old a - b trick for ints, because subtraction can overflow; use Integer.compare.

How it works

  1. Decide whether there is one obvious natural order; if yes, implement Comparable.
  2. For other orders, build a Comparator, ideally with key extractors.
  3. Chain secondary keys with thenComparing to break ties.
  4. Use reversed() for descending, applied to the right part of the chain.
  5. Pass the comparator to list.sort, stream.sorted, TreeMap or PriorityQueue.

Example

record Employee(String name, BigDecimal salary) implements Comparable<Employee> {
    public int compareTo(Employee o) { return name.compareTo(o.name); } // natural order: by name
}

// Salary descending, then name ascending
employees.sort(
    Comparator.comparing(Employee::salary, Comparator.reverseOrder())
              .thenComparing(Employee::name));

Common mistakes

  • Writing return this.age - other.age; which overflows for large values.
  • Calling .reversed() at the end of a chain and unintentionally reversing every key.
  • Ordering inconsistent with equals used in a TreeSet, causing lost elements.
  • Not handling null keys; use Comparator.nullsLast(...).

How to answer in the interview

"Comparable is implemented by the class itself and defines its natural ordering through compareTo, like String or LocalDate. Comparator is external, so I can define many orderings without touching the class. For employees by salary then name I write list.sort with Comparator.comparing on salary, then thenComparing on name, and use reverseOrder on the salary key if I want highest first. I avoid subtraction-based compare methods because of overflow, and I keep the ordering consistent with equals, because a TreeSet treats compare equals zero as a duplicate."

Likely follow-up questions

  • What happens if compareTo returns 0 for two unequal objects in a TreeSet? The second one is treated as a duplicate and not added.
  • Is Collections.sort stable? Yes, list sorting uses a stable TimSort for objects.
  • How do you sort with nulls? Wrap with Comparator.nullsFirst or nullsLast.
