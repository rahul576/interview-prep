How do you manage secrets in Ansible with an external vault?

Configuration Management · concept · levels mid

In one line

Keep secrets out of the repository and fetch them at runtime with lookup plugins for HashiCorp Vault (community.hashi_vault), AWS Secrets Manager or Azure Key Vault, authenticating with short-lived machine identity, and mark secret-handling tasks no_log: true.

Detailed explanation

Ansible Vault encrypts files in the repository with a shared password. It works, but the password must be distributed, rotation means re-encrypting and committing, anyone with the password can read all historical secrets in Git, and there is no audit of who read what. A central secrets manager fixes those problems: one place to rotate, fine-grained policies, and an audit log of every read.

Lookups at runtime. A lookup plugin runs on the control node when the variable is evaluated:

  • community.hashi_vault.vault_kv2_get (or the hashi_vault lookup) for Vault KV, plus modules for dynamic database credentials.
  • amazon.aws.secretsmanager_secret and amazon.aws.ssm_parameter for AWS.
  • azure.azcollection.azure_keyvault_secret for Azure Key Vault.

Authentication without a shared secret. The control node or CI runner proves its identity: Vault AppRole, JWT/OIDC tokens issued by GitHub Actions or GitLab CI, Vault's AWS or Azure auth methods, or simply the runner's IAM role / managed identity for the cloud secret stores. Tokens are short-lived and policies grant only the paths that playbook needs. In AWX/AAP, credential plugins can resolve secrets from these stores and inject them into jobs.

Keeping secrets out of output. Lookups return plain values that Ansible happily prints in verbose mode, in diff output, in error messages and in AAP job logs. no_log: true on tasks that use them (and on set_fact or register holding them) prevents this. Use diff: false for templated files containing secrets.

How it works

  1. CI job obtains an OIDC token and logs in to Vault with the JWT auth method.
  2. Vault policy grants read on kv/data/app/prod/* only.
  3. Playbook variables use lookups; values resolve when templates render.
  4. Tasks templating secrets use no_log and diff: false.
  5. Rotation happens in Vault; the next run picks up the new value.

Example

vars:
  db_password: >-
    {{ lookup('community.hashi_vault.vault_kv2_get', 'app/prod/db',
       engine_mount_point='kv', url='https://vault.example.com',
       auth_method='jwt', role_id='ansible-prod', jwt=lookup('env', 'CI_JOB_JWT')).secret.password }}
tasks:
  - name: Render app config
    ansible.builtin.template:
      src: app.conf.j2
      dest: /etc/app/app.conf
      mode: "0600"
    no_log: true
    diff: false

Common mistakes

  • Forgetting no_log on register or set_fact, leaking secrets on failure.
  • A long-lived Vault root or admin token stored in CI variables.
  • Broad policies that let every playbook read every secret.
  • Fetching a secret once per host in a loop, hammering the vault, instead of once per play.

How to answer in the interview

"Instead of encrypted files in Git, I fetch secrets at runtime with lookup plugins: community.hashi_vault for Vault, the amazon.aws lookups for Secrets Manager, or the Azure Key Vault lookup. The runner authenticates with machine identity, for example a JWT from the CI system or its IAM role, so there's no shared vault password, tokens are short-lived and policies are scoped per application and environment. Rotation is central and every read is audited. Any task that touches a secret gets no_log, and templates get diff false, so values never appear in logs."

Likely follow-up questions

  • Why is no_log important even with an external vault? The vault protects storage; Ansible still prints resolved values in logs, diffs and errors.
  • Is Ansible Vault still useful? For bootstrapping or small setups, ideally with its password itself coming from a secrets manager.
  • How do dynamic secrets help? Vault issues per-run database credentials that expire automatically.
