Inference spend tripled last quarter while request volume stayed flat. Where do you look?

MLOps · scenario · levels senior, lead

In one line

With flat volume, cost per request rose: check instance sizing and over-provisioned endpoints, autoscaling floors and idle replicas, batching and GPU utilisation, model size changes, forgotten dev endpoints and notebooks, and retraining frequency; then apply quantisation, distillation, caching, consolidation or batch scoring within the accuracy budget.

Detailed explanation

Inference spend equals capacity provisioned times price, not requests served. If requests are flat but spend tripled, someone added capacity or efficiency fell.

Instance sizing. Endpoints moved to bigger or GPU instances "for the launch", or each new model got its own dedicated endpoint, often over-provisioned. Autoscaling floors: minimum replicas raised for a peak event and never lowered, so many replicas idle all night and at weekends.

Batching and utilisation. A GPU server running one request at a time, without dynamic batching, may use 10 to 20 percent of the GPU. GPU utilisation and memory metrics (DCGM) per endpoint reveal this.

Model size. A new, larger model, such as a transformer replacing gradient boosting, or an LLM, may need GPUs or several replicas for the same traffic.

Forgotten resources. Development and test endpoints, idle notebooks with GPUs, experiment clusters and old model versions left running. Cost allocation by tags (team, model, environment) finds these quickly. Retraining frequency or evaluation jobs may also have grown if pipelines run more often than needed.

Then options, weighed against the accuracy budget: right-size instances, lower floors and use schedules, enable batching, quantise or distil models, cache repeated predictions, consolidate small models on shared multi-model endpoints, switch suitable use cases to batch scoring, or use serverless/scale-to-zero for rarely used models.

How it works

  1. Break down spend by endpoint, model, team and environment using tags.
  2. Compare provisioned capacity and utilisation over the quarter.
  3. Identify idle replicas, high floors and oversized instances.
  4. Check GPU utilisation and batching configuration.
  5. Find orphaned dev/test resources.
  6. Apply fixes, measure cost per 1,000 predictions, set budgets and alerts.

Common mistakes

  • Looking at request counts instead of provisioned capacity.
  • No tagging, so cost can't be attributed.
  • One dedicated GPU endpoint per small model.
  • Optimising the model before removing idle resources.

How to answer in the interview

"If volume is flat, cost per request went up, so I look at capacity and efficiency. Did endpoints move to bigger or GPU instances, did autoscaling floors go up for a launch and stay up, is the GPU running without dynamic batching at low utilisation, did a larger model ship? I also look for forgotten dev endpoints and idle notebooks via cost tags. Then I fix the waste first and weigh quantisation, distillation, caching, consolidating models on shared endpoints, or moving to batch scoring against accuracy."

Likely follow-up questions

  • How do you attribute inference cost to models and teams? Mandatory tags, per-endpoint cost reports and shared-endpoint allocation by request share.
  • What KPI would you track? Cost per 1,000 predictions and GPU utilisation per endpoint.
  • How do you prevent orphaned endpoints? TTLs on non-prod resources and IaC-only creation.
