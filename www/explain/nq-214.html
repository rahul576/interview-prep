How does API Gateway-based authentication and authorization work?

Security · design · levels mid, senior

In one line

The API gateway is the single entry point that validates tokens centrally against the identity provider, rejects bad ones with 401, applies coarse-grained authorization per route (403), and forwards the token downstream, while each service still enforces fine-grained rules in a zero-trust model.

Detailed explanation

Without a gateway every service exposed to the internet would need its own TLS, token validation, rate limiting and CORS. A gateway such as Spring Cloud Gateway, Kong, Envoy-based gateways, AWS API Gateway or Azure API Management centralises these cross-cutting concerns at the edge.

For authentication the gateway acts as an OAuth 2 resource server (or, in a BFF setup, as an OAuth client that holds tokens for a browser session). It knows the identity provider's issuer and JWKS keys and, on each request, verifies the token signature, iss, aud, exp and nbf. Invalid, missing or expired tokens get 401 immediately, so junk traffic never reaches the services. For opaque tokens it calls the introspection endpoint, usually with caching.

Then it applies coarse-grained authorization by route: /admin/ needs role ADMIN, POST /orders/ needs scope orders.write; otherwise 403. Valid requests are forwarded with the original token (token relay), sometimes exchanged for a narrower internal token, or with trusted identity headers that the gateway sets after stripping any client-supplied copies.

Services must not trust the gateway blindly. Internal traffic can bypass it, misconfigured routes happen, and the gateway does not know business data. So services validate the token again (cheap with cached keys) and enforce fine-grained rules such as "this customer owns order 123". The gateway also adds rate limiting, request size limits, correlation ids and audit logging.

How it works

  1. Client gets an access token from the identity provider.
  2. Gateway receives the request, validates token signature and claims; 401 on failure.
  3. Gateway checks route policy (scopes, roles); 403 on failure.
  4. Rate limiting and logging apply; the token is relayed downstream.
  5. Service revalidates the token and enforces object-level rules.

Example

@Bean
SecurityWebFilterChain gateway(ServerHttpSecurity http) {
    return http
        .authorizeExchange(e -> e
            .pathMatchers("/actuator/health").permitAll()
            .pathMatchers("/api/admin/**").hasRole("ADMIN")
            .pathMatchers(HttpMethod.POST, "/api/orders/**").hasAuthority("SCOPE_orders.write")
            .anyExchange().authenticated())
        .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))
        .build();
}
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://login.example.com/realms/shop

Common mistakes

  • Services accepting unauthenticated internal calls because "the gateway checked".
  • Forwarding identity headers without removing ones the client sent.
  • Putting business authorization logic in gateway configuration.
  • Not caching JWKS or introspection results, adding latency.

How to answer in the interview

"All external traffic goes through the gateway, for example Spring Cloud Gateway or Azure API Management. It's integrated with the identity provider, so for every request it validates the access token's signature with the JWKS keys plus issuer, audience and expiry, and returns 401 for anything invalid. Then it applies coarse route rules, such as orders.write scope for POST on orders, returning 403 otherwise. Valid requests are forwarded with the token relayed. But I don't trust the gateway blindly: each service validates the token again and enforces fine-grained, data-level checks like ownership. The gateway also handles rate limiting and audit logging."

Likely follow-up questions

  • Why should services not trust the gateway blindly? Internal bypass, misconfiguration and zero trust; the gateway lacks data-level context.
  • Token relay vs identity headers? Relay keeps a verifiable token; headers are simpler but must be protected by mTLS and stripping.
  • What is token exchange? RFC 8693: swap a user token for one scoped to a downstream service.
