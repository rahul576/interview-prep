A pod has been stuck in Terminating for an hour. How do you troubleshoot it?

Kubernetes · scenario · levels mid, senior

In one line

A pod stuck Terminating is waiting on something: a finalizer, an unreachable node whose kubelet cannot confirm shutdown, a hanging volume unmount or detach, or a long grace period with a process ignoring SIGTERM; find which, and force delete only after understanding it.

Detailed explanation

Deleting a pod sets a deletionTimestamp; the object disappears only when the kubelet reports that containers stopped and all finalizers are removed. So "Terminating for an hour" means one of those steps is not completing.

Finalizers on pods are less common than on other objects, but some controllers add them (for example, custom protection or job tracking finalizers in older versions). If the controller that should remove the finalizer is broken or uninstalled, deletion waits forever. If the node is NotReady or gone, nobody can confirm the containers stopped, so the API server keeps the pod in Terminating until the node returns or the Node object is deleted.

On a healthy node, check kubelet logs: unmounting a volume may hang (a dead NFS server, a stuck CSI driver, a busy device), and the kubelet will not finish termination until volumes are torn down. Occasionally the container runtime itself is hung. Finally, the application may ignore SIGTERM while terminationGracePeriodSeconds is set very high, so the kubelet patiently waits before sending SIGKILL.

kubectl delete pod --grace-period=0 --force removes the object from the API immediately, but it does not guarantee the containers stopped. For a StatefulSet pod on a partitioned node, that can mean two copies running at once.

How it works

  1. kubectl get pod -o yaml: deletionTimestamp, grace period, finalizers, node.
  2. Check the node status; NotReady means the kubelet cannot report.
  3. On a ready node, read kubelet logs for unmount/CSI errors and check crictl ps.
  4. Check whether the app handles SIGTERM and what grace period is set.
  5. Fix the controller, storage or node problem.
  6. Force delete or remove a finalizer only when you know the consequence.

Example

kubectl get pod worker-5 -o jsonpath='{.metadata.deletionTimestamp} {.metadata.finalizers} {.spec.nodeName}{"\n"}'
kubectl get node node-12
journalctl -u kubelet | grep -i -E 'unmount|worker-5' | tail
# finalizer from a removed controller:
kubectl patch pod worker-5 --type=json -p='[{"op":"remove","path":"/metadata/finalizers"}]'
# last resort:
kubectl delete pod worker-5 --grace-period=0 --force

Common mistakes

  • Force deleting by reflex, leaving a process running on the node.
  • Removing finalizers without cleaning up what they protect.
  • Ignoring hung NFS mounts that will affect the next pod too.
  • Huge grace periods with apps that never exit cleanly.

How to answer in the interview

"I start with the pod YAML: deletion timestamp, grace period, finalizers and node. A finalizer whose controller is broken blocks deletion forever. If the node is NotReady, the kubelet can't confirm containers stopped, so the pod stays Terminating until the node returns or is removed. On a healthy node I check kubelet logs for a volume unmount or CSI detach that's hanging, and whether the app ignores SIGTERM with a long grace period. Only after I understand the cause do I force delete, because for stateful pods that can leave two copies running."

Likely follow-up questions

  • Why is force-deleting on a partitioned node risky? The containers may still run and write, while a replacement starts elsewhere.
  • What does force delete actually do? Removes the API object without waiting for kubelet confirmation.
  • How should apps handle SIGTERM? Stop accepting work, finish in-flight work, exit within the grace period.
