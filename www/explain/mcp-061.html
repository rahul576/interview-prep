What is the confused deputy problem in MCP, and how do you prevent it?

MCP Servers · concept · levels senior, lead

In one line

A confused deputy is a privileged component tricked into using its own authority for someone who should not have it; in MCP it appears with shared service accounts and with proxy servers using a static client ID; prevent it with per-user authorization and consent, checking caller identity against the token subject, and short-lived, narrowly scoped tokens.

Detailed explanation

The term comes from classic security: a compiler with write access to a billing file was tricked by a user into overwriting it. The compiler was the deputy, it had the authority, and it was confused about whose behalf it acted on.

In MCP the most common form is a server that calls downstream systems with its own broad credentials, such as a service account that can read every repository or every customer record. If the server does not check what the calling user is allowed to see, then any user, or a prompt-injected agent acting for that user, can reach data they were never entitled to. The server's authority substitutes for the user's.

The MCP specification also describes an OAuth proxy variant. Some MCP servers act as proxies to a third-party API and use a single static client ID registered with that third party's authorization server. Because the third party remembers consent for that client ID, an attacker can craft an authorization request (for example via a malicious dynamically registered client and a crafted redirect URI) that reuses a victim's existing consent and obtain an authorization code without the victim knowingly approving. The specification therefore requires such proxies to obtain explicit user consent per client before forwarding to the third party.

Prevention: authorize per user, acting on behalf of the authenticated user with their own permissions (delegated tokens) rather than a shared identity; obtain consent per client; validate that the token subject matches the user the server thinks it is serving; validate redirect URIs exactly; and use short-lived, narrowly scoped tokens so mistakes have limited reach.

How it works

  1. Request arrives with a token for user U.
  2. Server extracts U from the validated token, never from tool arguments.
  3. Server obtains a downstream token for U (on-behalf-of) or applies U's entitlements before using a service credential.
  4. Downstream query is scoped to U's data.
  5. For third-party OAuth proxying, the server shows its own consent screen per client before redirecting.

Example

def get_customer(args, ctx):
    user = ctx.token.subject                 # from validated token
    cid = args["customer_id"]
    if not entitlements.can_view(user, cid): # per-user check
        return tool_error("You are not assigned to this customer.")
    return crm.get(cid, token=ctx.downstream_token)  # delegated, on behalf of user

Common mistakes

  • One service account with access to everything, no per-user filtering.
  • Taking user or tenant IDs from tool arguments the model fills in.
  • Proxy servers skipping their own consent step because the upstream IdP "already consented".
  • Loose redirect URI matching.

How to answer in the interview

"A confused deputy is a privileged component tricked into using its authority on behalf of someone who shouldn't have it. In MCP it shows up when a server uses its own broad credentials, like a shared service account that can see all repos or customers, to serve any user, so a user or a prompt-injected agent reaches data they were never allowed to see. The spec also describes a variant with MCP proxy servers that use a static client ID with a third-party authorization server, where an attacker can get authorization codes without proper consent. I prevent it by authorizing per user with delegated permissions, requiring consent per client, checking the caller matches the token subject, and using short-lived, narrowly scoped tokens."

Likely follow-up questions

  • Support assistant seeing only current customer? Bind the session to the customer from a trusted source and filter every query by it.
  • Why not trust IDs in arguments? The model, or an injection, can change them.
  • Where does row-level security help? It enforces the per-user filter in the database even if code forgets.
