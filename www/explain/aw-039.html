Explain Route 53 routing policies.

Cloud (AWS) · concept · levels mid

In one line

Route 53 routing policies decide which record answers a DNS query: simple, weighted, latency-based, failover, geolocation, geoproximity, multivalue answer and IP-based, most of them combinable with health checks.

Detailed explanation

Simple routing returns one record set; if it has several values, all are returned and the client picks one. There is no health checking. Weighted routing returns records in proportion to their weight, such as 90 and 10, which supports gradual migrations and canary releases; a weight of 0 takes a record out of rotation.

Latency-based routing answers with the record in the AWS Region that has the lowest measured network latency for the resolver's location, so users reach the fastest region. Failover routing has a primary and a secondary: while the primary's health check passes, it is returned; when it fails, Route 53 returns the secondary, for example a standby region or a static S3 maintenance site.

Geolocation routes by the user's continent, country or US state, useful for legal requirements and localised content; always define a default record or unmatched users get no answer. Geoproximity (through traffic flow) routes by physical distance with a bias that expands or shrinks a region's catchment. Multivalue answer returns up to eight healthy records chosen at random, a simple client-side load-balancing approach. IP-based routing maps the client's CIDR ranges to specific endpoints, useful for ISP-specific optimisation.

Policies can be nested with alias records, for example latency between regions and weighted within each region. Alias records to ALBs, CloudFront or S3 are free to query and can evaluate target health.

How it works

  1. A resolver asks Route 53 for app.example.com.
  2. Route 53 finds all records with that name and type and their policy.
  3. It filters out records whose health checks are failing.
  4. It applies the policy: weight, latency, location, or primary/secondary.
  5. It returns the answer with its TTL; resolvers cache it for that long.

Example

Failover pair with a health check on the primary region:

Common mistakes

  • Using geolocation without a default record.
  • Expecting DNS failover to be instant despite long TTLs and client caching.
  • Health-checking a shallow endpoint that stays green while the app is broken.
  • Treating multivalue answer as a replacement for a real load balancer.

How to answer in the interview

"Simple returns a record with no health checks. Weighted splits traffic, say 90/10, for migrations and canaries. Latency-based sends users to the region with the lowest latency. Failover returns the primary while its health check passes and a secondary otherwise, like a standby region or maintenance page. Geolocation routes by country or continent for compliance and localisation, geoproximity by distance with a bias, multivalue returns several healthy IPs, and IP-based maps client ranges. I often nest them with alias records, for example latency across regions and weighted inside a region."

Likely follow-up questions

  • Why does DNS failover not take effect instantly for all users? Resolvers and clients cache answers for the TTL, some longer, and health checks need several failures first.
  • What is the difference between geolocation and latency routing? Geolocation follows where users are; latency follows measured network speed.
  • Why prefer alias records? They are free to query, work at the zone apex and track target health.
