How do you use assertions such as assertTrue() and assertFalse()?

Testing · concept · levels entry

In one line

assertTrue(condition) passes when the boolean is true and assertFalse(condition) when it is false; both accept an optional failure message or lazy Supplier, but because a failure only says "expected true", prefer more specific assertions (assertEquals, AssertJ) when you are comparing values.

Detailed explanation

assertTrue and assertFalse live in org.junit.jupiter.api.Assertions and are usually imported statically. They are the natural choice when the code under test returns a boolean or exposes a boolean predicate: isValid(), isEmpty(), hasPermission(), canWithdraw(amount).

assertTrue(boolean condition)
assertTrue(boolean condition, String message)
assertTrue(boolean condition, Supplier<String> messageSupplier)
assertTrue(BooleanSupplier condition, ...)

The same overloads exist for assertFalse. If the condition does not hold, they throw AssertionFailedError, failing the test.

Failure messages: without a message, the report says only expected: <true> but was: <false>, which gives no clue about what was being checked. Add a message describing the expectation. A Supplier<String> (lambda) is evaluated only when the assertion fails, so expensive message building (string concatenation, toString() of large objects) costs nothing on success. Note that in JUnit 5 the message is the last argument, unlike JUnit 4 where it came first.

When not to use them: assertTrue(list.size() == 3) or assertTrue(a.equals(b)) hides the actual values. When it fails you learn nothing about what the size was. Use assertEquals(3, list.size()) (reports expected 3 but was 5) or AssertJ: assertThat(list).hasSize(3) reports the actual elements; assertThat(user.isActive()).as("user %s active", id).isTrue() adds context. Similarly prefer assertNull, assertThrows or assertInstanceOf (JUnit 5.8+) for those checks. Rule of thumb: the more specific the assertion, the better the failure message.

How it works

  1. Evaluate the condition (or call the BooleanSupplier).
  2. If it matches the expected boolean, continue.
  3. Otherwise build the message (lazy supplier only now).
  4. Throw AssertionFailedError; JUnit marks the test failed.
  5. Use assertAll to report several boolean checks together.

Example

import static org.junit.jupiter.api.Assertions.*;
import static org.assertj.core.api.Assertions.assertThat;

class OrderValidatorTest {

    private final OrderValidator validator = new OrderValidator();

    @Test
    void acceptsCompleteOrder() {
        Order order = validOrder();
        assertTrue(validator.isValid(order),
                   () -> "expected valid order but errors were " + validator.errors(order));
    }

    @Test
    void rejectsOrderWithoutItems() {
        assertFalse(validator.isValid(orderWithoutItems()), "order without items must be invalid");
    }

    @Test
    void cartHasThreeItems() {
        Cart cart = cartWithThreeItems();
        // weak: assertTrue(cart.items().size() == 3);
        assertEquals(3, cart.items().size());               // better
        assertThat(cart.items()).extracting(Item::sku)       // best for collections
                                .containsExactly("A1", "B2", "C3");
    }
}

Common mistakes

  • assertTrue(x == 5) instead of assertEquals(5, x), losing the actual value.
  • Putting the message first as in JUnit 4.
  • Building costly messages eagerly instead of using a supplier.
  • Using assertTrue(!condition) instead of assertFalse(condition).

How to answer in the interview

"assertTrue passes when the condition is true and assertFalse when it's false, for example assertTrue(validator.isValid(order)) or assertFalse(cart.isEmpty()). Both take an optional message as the last argument, or a Supplier so the message is only built if the assertion fails. I use them for genuinely boolean results. When I'm comparing values I prefer specific assertions like assertEquals(3, items.size()) or AssertJ's assertThat(items).hasSize(3), because a failed assertTrue only says expected true but was false, while the specific ones show the actual value."

Likely follow-up questions

  • Why is assertEquals argument order important? The message labels the first argument as expected; swapping them misleads.
  • What is the Supplier overload for? Lazy messages, built only on failure.
  • How do you check several conditions at once? assertAll or AssertJ soft assertions.
