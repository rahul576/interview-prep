What is the difference between Statement, PreparedStatement, and CallableStatement?

Databases & SQL · concept · levels mid, senior

In one line

Statement runs static SQL text (dangerous with concatenated input), PreparedStatement uses a precompiled SQL template with bind parameters (prevents SQL injection, reuses plans, supports batching), and CallableStatement calls stored procedures with IN, OUT and INOUT parameters.

Detailed explanation

Statement sends a complete SQL string. If you build it with user input, such as "... WHERE name = '" + name + "'", an input like ' OR '1'='1 changes the query's meaning: SQL injection. Every distinct string is also parsed and planned again, and you must handle quoting and date formats yourself. It is acceptable only for fixed DDL or admin scripts.

PreparedStatement sends the SQL with ? placeholders, and values are bound separately with typed setters (setLong, setString, setTimestamp). The database treats bound values strictly as data, never as SQL, which prevents injection. Benefits:

  • Plan and parse reuse: the server can cache the prepared statement; drivers also cache them (for example PostgreSQL's prepareThreshold, MySQL's cachePrepStmts).
  • Correct type handling and escaping.
  • Batching with addBatch() / executeBatch(), dramatically faster for bulk inserts (MySQL needs rewriteBatchedStatements=true for the best effect).

CallableStatement extends PreparedStatement for stored procedures and functions using {call proc(?, ?)} escape syntax, registering OUT parameters with registerOutParameter and reading them after execution. It also handles procedures returning result sets or cursors.

A limitation: placeholders bind values only. Table names, column names and ORDER BY direction cannot be parameters, so if they come from users, validate them against a whitelist.

How it works

  1. The application prepares SQL with placeholders.
  2. The driver sends it for parsing (server-side or client-side preparation).
  3. Values are bound with typed setters.
  4. Execution uses the parsed or cached statement.
  5. For batches, many parameter sets are sent in one round trip.
  6. CallableStatement additionally maps OUT parameters back.

Example

// Vulnerable
Statement st = con.createStatement();
st.executeQuery("SELECT * FROM users WHERE email = '" + email + "'");

// Safe
try (PreparedStatement ps = con.prepareStatement(
        "SELECT id, name FROM users WHERE email = ?")) {
    ps.setString(1, email);
    try (ResultSet rs = ps.executeQuery()) { /* ... */ }
}

// Batch insert
try (PreparedStatement ps = con.prepareStatement(
        "INSERT INTO event(type, payload) VALUES (?, ?)")) {
    for (Event e : events) { ps.setString(1, e.type()); ps.setString(2, e.json()); ps.addBatch(); }
    ps.executeBatch();
}

// Stored procedure
try (CallableStatement cs = con.prepareCall("{call calc_bonus(?, ?)}")) {
    cs.setLong(1, empId);
    cs.registerOutParameter(2, Types.NUMERIC);
    cs.execute();
    BigDecimal bonus = cs.getBigDecimal(2);
}

Common mistakes

  • Concatenating values into a PreparedStatement's SQL, which keeps the injection risk.
  • Trying to bind a table or column name as a parameter.
  • Running thousands of single inserts instead of a batch.
  • Thinking an ORM makes injection impossible; native or string-built JPQL can still be vulnerable.

How to answer in the interview

"Statement executes a raw SQL string, so concatenating user input exposes you to SQL injection and each string is parsed again. PreparedStatement uses placeholders with typed bind parameters, so values are never interpreted as SQL. That prevents injection, allows the plan to be reused, handles types properly and supports efficient batching with addBatch. CallableStatement extends it to call stored procedures, with OUT and INOUT parameters. In practice I always use PreparedStatement, directly or through JdbcTemplate or JPA, and for dynamic column names I whitelist allowed values because they can't be parameters."

Likely follow-up questions

  • Can a parameter be a table or column name? No; only values. Whitelist identifiers instead.
  • How do you speed up batch inserts in MySQL? Set rewriteBatchedStatements=true and use moderate batch sizes.
  • Is JPA immune to SQL injection? Only when you use parameters; concatenated JPQL or native queries are still vulnerable.
