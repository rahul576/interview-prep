You deleted a namespace and it has been stuck in Terminating. What causes this and how do you fix it?

Kubernetes · scenario · levels mid, senior

In one line

A namespace only disappears after the namespace controller deletes everything inside it; it gets stuck when objects have finalizers whose controller is gone or an unavailable aggregated APIService breaks discovery. Read the namespace status conditions and fix the cause rather than blindly stripping the namespace's finalizer.

Detailed explanation

Deleting a namespace sets it to Terminating with the kubernetes finalizer in spec.finalizers. The namespace controller then discovers every namespaced resource type the API server knows about, lists them in that namespace, and deletes them. Only when all are gone does it remove its finalizer and the namespace vanishes.

Two things commonly break this. First, objects with finalizers that never get removed: custom resources whose operator was uninstalled first (so nobody processes the finalizer), a Service of type LoadBalancer whose cloud controller cannot delete the cloud LB, or PVCs held by kubernetes.io/pvc-protection while a pod still uses them. Second, discovery failures: if an aggregated API such as v1beta1.metrics.k8s.io points to a service that is down, the controller cannot list all resource types, so it refuses to finish, because it cannot prove the namespace is empty.

The namespace status.conditions explain exactly which: NamespaceDeletionDiscoveryFailure, NamespaceContentRemaining, or NamespaceFinalizersRemaining, with the resource types and finalizer names.

You can force it by calling the finalize subresource with an empty finalizer list, but that only removes the namespace object: leftover objects may remain in etcd, and external resources such as cloud load balancers, DNS records or buckets created by operators can leak and keep costing money.

How it works

  1. kubectl get ns <ns> -o yaml and read status.conditions.
  2. If discovery failure: kubectl get apiservices and fix or remove the broken one.
  3. If content remains: list remaining objects and their finalizers.
  4. Reinstall or repair the owning controller so it can clean up properly.
  5. If the controller is gone for good, clean up external resources, then remove that object's finalizer.
  6. The namespace controller finishes on its own.

Example

kubectl get ns team-x -o jsonpath='{range .status.conditions[*]}{.type}: {.message}{"\n"}{end}'
kubectl get apiservices | grep False
kubectl api-resources --verbs=list --namespaced -o name \
  | xargs -n1 kubectl get -n team-x --ignore-not-found --show-kind -o name
kubectl -n team-x patch kafkatopic orders --type=merge -p '{"metadata":{"finalizers":[]}}'

Common mistakes

  • Uninstalling an operator before deleting its custom resources.
  • Calling the finalize API immediately and leaking cloud resources.
  • Ignoring a broken metrics-server APIService that affects the whole cluster.
  • Recreating a namespace with the same name while the old one is stuck.

How to answer in the interview

"Deleting a namespace makes the controller delete everything inside first. It gets stuck when some objects can't be deleted, usually custom resources with finalizers whose operator was uninstalled, or a LoadBalancer Service whose cloud cleanup fails. Another classic cause is an unavailable aggregated API like a broken metrics-server APIService, which stops discovery. The namespace status conditions tell me which. I fix the cause, repair the controller or remove a specific orphaned finalizer after cleaning up its external resource. Forcing the namespace finalizer away works but can leak resources."

Likely follow-up questions

  • What order to remove an operator? Delete its custom resources first, wait for cleanup, then uninstall the operator and CRDs.
  • Why does an APIService block deletion? The controller cannot enumerate all types, so it cannot prove the namespace is empty.
  • How do you prevent it? Uninstall runbooks, monitor APIService availability, and GitOps ordering.
