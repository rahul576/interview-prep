Explain JVM architecture.

JVM & Performance · concept · levels entry, mid

In one line

The JVM has three main parts: the class loader subsystem (load, link, initialise), the runtime data areas (shared heap and method area/Metaspace; per-thread stack, PC register, native method stack), and the execution engine (interpreter, JIT compiler, garbage collector), connected to native code via the JNI and native method libraries.

Detailed explanation

Class loader subsystem. Loads .class files on demand using the bootstrap, platform and application class loaders with parent-first delegation. Linking verifies bytecode for safety, prepares static fields with default values and resolves symbolic references. Initialisation runs static initialisers on first active use.

Runtime data areas.

  • Heap (shared): all objects and arrays; managed by the GC; typically generational or region-based.
  • Method area (shared): class-level data such as class structures, method bytecode, field and method info and the runtime constant pool. In HotSpot it is implemented as Metaspace in native memory since Java 8 (previously PermGen). Static variable values are stored with the class mirror on the heap in modern HotSpot.
  • JVM stack (per thread): one frame per method call, with local variables, operand stack and return data.
  • PC register (per thread): address of the current bytecode instruction.
  • Native method stack (per thread): for native (C/C++) calls.
  • HotSpot also has the code cache for compiled code, plus direct buffers and GC structures off-heap.

Execution engine. The interpreter runs bytecode immediately. Profiling identifies hot methods, and the JIT compiler (C1, then C2 in tiered mode) compiles them into optimised native code with inlining and escape analysis. The garbage collector (G1 by default; also ZGC, Parallel, Serial, Shenandoah in some builds) reclaims unreachable objects.

Native interface. The Java Native Interface (JNI) lets Java call native libraries and vice versa; the JDK itself uses it for file, network and OS access. The newer Foreign Function & Memory API (final in Java 22) is the modern, safer alternative for calling native code and managing off-heap memory.

Knowing this architecture explains common production issues: StackOverflowError (stack), OutOfMemoryError variants (heap, Metaspace, native), warm-up (JIT) and pauses (GC).

How it works

  1. java -jar app.jar starts the JVM and creates the runtime areas.
  2. Class loaders load and link the main class and its dependencies.
  3. The interpreter executes main on the main thread's stack.
  4. Hot methods are compiled by the JIT into the code cache.
  5. Objects are allocated on the heap; the GC reclaims garbage.
  6. Native calls go through JNI or the FFM API.

Example

             +------------------- JVM -------------------+
.class --->  | Class Loader: bootstrap > platform > app   |
             |   load -> link (verify, prepare, resolve)  |
             |   -> initialise                            |
             |-------------------------------------------|
             | Shared: Heap | Method area (Metaspace)    |
             | Per thread: Stack | PC | Native stack     |
             |-------------------------------------------|
             | Execution engine: Interpreter, JIT, GC     |
             +------------------|------------------------+
                                JNI / FFM -> native libs
jcmd <pid> VM.native_memory summary   # heap, class, thread, code, GC areas

Common mistakes

  • Saying Metaspace is part of the heap.
  • Forgetting the PC register and native stack.
  • Describing the extension class loader as current.
  • Treating the JIT and GC as outside the JVM.

How to answer in the interview

"The JVM has three main parts. The class loader subsystem loads class files, links them, which includes bytecode verification, preparation and resolution, and initialises them. The runtime data areas hold memory: the heap shared by all threads for objects, the method area, implemented as Metaspace, for class metadata, and per-thread areas: the Java stack with a frame per method call, the program counter register and the native method stack. The execution engine runs bytecode with the interpreter, compiles hot methods with the JIT and reclaims memory with the garbage collector. Finally, JNI, and now the Foreign Function and Memory API, let Java call native libraries."

Likely follow-up questions

  • Which of these memory areas are shared between threads? Heap and method area/Metaspace (and the code cache); stacks, PC registers and native stacks are per thread.
  • What is the runtime constant pool? A per-class table of literals and symbolic references used during resolution.
  • Why is JNI considered risky? Native code can crash the JVM and bypasses memory safety.
