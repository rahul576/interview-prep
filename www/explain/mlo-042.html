How does KServe autoscaling work, and what are the trade-offs of scaling to zero?

MLOps · concept · levels mid, senior

In one line

In serverless mode, KServe uses Knative to autoscale on concurrency or requests per second and can scale to zero, saving money (especially on GPUs) at the cost of cold starts (scheduling, image pull, model load); raw deployment mode uses HPA or KEDA; keep minReplicas above zero for latency-sensitive models.

Detailed explanation

CPU utilisation is a poor scaling signal for inference: a GPU model can be saturated with low CPU, and request queues are what users feel. In serverless mode, KServe deploys the predictor as a Knative Service. Knative's autoscaler (KPA) watches in-flight requests per pod (concurrency) or RPS and adds replicas when the target is exceeded. Requests queue briefly in the activator or queue-proxy while new pods start.

Scale to zero: after a period with no traffic, Knative removes all pods; the activator holds the first new request and triggers scale-up. For dozens of rarely used models, especially on GPUs, this saves a lot of money.

The trade-off is the cold start: a pod must be scheduled—maybe a new GPU node must be provisioned by the cluster autoscaler or Karpenter, taking minutes—the image pulled (often gigabytes), the model downloaded from storage and loaded into memory or GPU, and the runtime warmed up. Small CPU models may start in seconds; large models can take minutes, so the first users wait or time out.

Raw deployment mode (now the default in recent KServe releases for many setups) uses ordinary Deployments with HPA, or KEDA for custom metrics like queue depth or Prometheus request rates. It is simpler, avoids Knative and suits steady traffic, but scale to zero needs KEDA.

Mitigations for cold starts: minReplicas ≥ 1 for user-facing models, model caching on nodes (local PVs or KServe's model cache), smaller images, pre-pulled images, warm GPU node pools and scale-down delays.

How it works

  1. Choose serverless or raw deployment mode per model.
  2. Set scaling metric and target (for example concurrency 4 per pod).
  3. Set minReplicas and maxReplicas; scale-down delay.
  4. For scale to zero, measure and accept cold-start time.
  5. Reduce cold start with caches, slimmer images and warm nodes.
  6. Monitor queueing, cold-start counts and cost.

Example

apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
metadata:
  name: doc-classifier
  annotations:
    serving.kserve.io/deploymentMode: Serverless
    autoscaling.knative.dev/scale-down-delay: "10m"
spec:
  predictor:
    minReplicas: 0          # internal, low-traffic model
    maxReplicas: 4
    scaleMetric: concurrency
    scaleTarget: 4
    model:
      modelFormat: {name: huggingface}
      storageUri: s3://models/doc-classifier/v3
      resources: {limits: {nvidia.com/gpu: 1}}

Common mistakes

  • Scale to zero on a user-facing, latency-critical model.
  • Scaling GPU inference on CPU utilisation.
  • Ignoring node provisioning time in cold-start estimates.
  • Client timeouts shorter than the cold start.

How to answer in the interview

"In serverless mode KServe runs on Knative, which autoscales on concurrent requests or RPS per replica, which matches inference load far better than CPU. It can scale to zero for idle models, saving a lot, especially on GPUs. The cost is cold starts: scheduling, maybe a new GPU node, pulling a large image and loading the model, which can take minutes. Raw deployment mode uses HPA or KEDA and is simpler for steady traffic. I keep minReplicas above zero for latency-sensitive models and use scale to zero for internal or rarely used ones."

Likely follow-up questions

  • How does model caching on nodes help? It skips downloading weights, often the largest part of cold start.
  • What target concurrency would you set? From load tests: the concurrency where latency stays within SLO.
  • KEDA vs HPA? KEDA scales on external metrics like queue depth and supports scale to zero.
