As a backend developer, how do you decide between classic ML, an LLM or plain rules for a problem?

AI/ML & GenAI · concept · levels mid, senior

In one line

Start simple: rules for clear, stable logic experts can write down; classic ML for structured, labelled, high-volume prediction; LLMs for unstructured text and flexible language tasks; decide on accuracy, latency, cost per prediction and explainability, measured against a baseline, and combine approaches where useful.

Detailed explanation

Backend developers increasingly get asked to "add AI", but the right answer is often not an LLM. The decision comes down to the nature of the problem and its operating constraints.

Rules or plain code fit when logic is explicit and stable: discount eligibility, validation, routing by country, compliance thresholds. They are deterministic, microsecond-fast, free per call, easy to test and audit, and changes are code reviews. They break down when there are too many interacting conditions or the patterns are fuzzy.

Classic machine learning, such as logistic regression or gradient boosting, fits prediction on structured, tabular data with historical labels and high volume: churn, fraud scoring, credit risk, demand forecasting, ETA prediction. It runs in milliseconds on CPUs at negligible cost, is usually more accurate than an LLM on numeric tabular data, produces calibrated scores, and can be explained with coefficients or SHAP. It needs labelled data, feature pipelines and monitoring for drift.

LLMs fit tasks involving unstructured language: summarising, extracting fields from emails or contracts, classifying free-text tickets when few labels exist, answering questions over documents (RAG), drafting content, or flexible conversational interfaces. They need little or no training data and adapt by changing the prompt, but they cost more per call, add latency (hundreds of milliseconds to seconds), are non-deterministic, can hallucinate and need evaluation and guardrails.

Practical approach: estimate volume × cost per prediction, latency budget, accuracy required and explainability or regulatory needs, then build the simplest viable baseline and measure. Hybrids are common: an LLM extracts structured features from free text that a gradient boosting model scores; rules act as guardrails around ML outputs; a cheap classifier routes only hard cases to an LLM.

How it works

  1. Define the decision, inputs, volume, latency and accuracy needs.
  2. Ask whether experts can write the logic as rules; if yes, start there.
  3. If data is structured with labels, try classic ML against a baseline.
  4. If inputs are unstructured language with few labels, prototype with an LLM.
  5. Evaluate on the same test set, compare cost and latency, and combine where it helps.

Example

Ticket triage for 2 million tickets/month:
- Rules: "contains 'chargeback' -> Payments queue"  (fast, explainable guardrail)
- LLM: extract {product, intent, urgency} from free text for new categories
- Classic ML: gradient boosting on extracted fields + customer tier + history
  -> predicts escalation risk in 5 ms at near-zero cost

Common mistakes

  • Using an LLM for numeric tabular prediction.
  • Ignoring cost at production volume when prototyping.
  • Skipping a simple baseline, so you can't prove the model adds value.
  • Using ML where regulations require deterministic, auditable rules.

How to answer in the interview

"I start with the simplest thing that works. If experts can write the logic down and it's stable, like eligibility rules, I use code: cheap, fast and auditable. If it's prediction on structured data with labelled history at high volume, like churn or fraud, classic ML such as gradient boosting is usually more accurate and far cheaper than an LLM. LLMs shine with unstructured text: extraction, summarisation, free-text classification with few labels, or Q&A over documents. I weigh latency, cost at volume and explainability, compare against a baseline and often combine them."

Likely follow-up questions

  • Where would an LLM be the wrong choice despite being easy to try? High-volume numeric scoring like fraud, where latency, cost and explainability favour gradient boosting.
  • How do you justify ML over rules? Show measurable lift against the rule baseline on held-out data.
  • How do rules and ML work together? Rules as hard constraints and guardrails, ML for ranking or scoring within them.
