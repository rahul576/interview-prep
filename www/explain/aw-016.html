What are S3 presigned URLs, and when would you use them?

Cloud (AWS) · concept · levels entry

In one line

A presigned URL is a temporary, signed link to one S3 object and one operation (GET or PUT), created with the signer's credentials and expiring after a set time; it keeps the bucket private while letting browsers and apps upload or download directly, offloading traffic from your servers.

Detailed explanation

Typical problem: users must upload profile photos or 2 GB videos, or download private invoices. Streaming those bytes through your API servers wastes bandwidth and CPU and hits request size and timeout limits. Making the bucket public is unacceptable.

A presigned URL solves both. Your backend, after authenticating the user and deciding what they may do, calls the SDK to sign a request for a specific bucket, key and HTTP method with an expiry. The URL includes the signature (Signature Version 4) and query parameters such as X-Amz-Expires. Anyone holding it can perform exactly that operation until it expires; no AWS credentials are needed on the client. S3 validates the signature and also checks that the signer still has permission, so if the signing role loses access, the URL stops working. URLs signed with temporary credentials also stop when those credentials expire, which can be shorter than the requested expiry; the maximum is 7 days with SigV4.

For uploads, a presigned PUT or a presigned POST is used; POST policies allow conditions such as a maximum content length and content type prefix, which is useful for browser forms. Multipart uploads can presign each part for very large files.

Security practice: keep expiry short (minutes), generate a server-chosen key (for example uploads/{userId}/{uuid}.jpg) instead of trusting client file names, restrict content type and size, and validate after upload: an S3 event triggers a Lambda that checks the file type, scans for malware, creates thumbnails, and only then marks it available. Because the URL is a bearer token, treat it as sensitive and avoid logging it.

How it works

  1. Client asks your API for an upload URL.
  2. API authenticates the user and picks the object key.
  3. API signs a PUT for that key with a 5-minute expiry.
  4. Client uploads directly to S3 with the URL.
  5. S3 event triggers validation and processing.
  6. Downloads work the same way with a presigned GET.

Example

import boto3, uuid
s3 = boto3.client("s3")

def create_upload_url(user_id):
    key = f"uploads/{user_id}/{uuid.uuid4()}.jpg"
    url = s3.generate_presigned_url(
        "put_object",
        Params={"Bucket": "acme-user-media", "Key": key, "ContentType": "image/jpeg"},
        ExpiresIn=300,
    )
    return {"url": url, "key": key}
# Browser or CLI then uploads directly
curl -X PUT -H "Content-Type: image/jpeg" --upload-file photo.jpg "$URL"

Common mistakes

  • Long expiries such as 7 days for sensitive files.
  • Letting clients choose arbitrary keys and overwrite others' files.
  • No post-upload validation or malware scanning.
  • Missing CORS configuration for browser uploads.

How to answer in the interview

"A presigned URL is a temporary link to one S3 object for one operation, signed with the credentials of whoever generated it, and it expires. The bucket stays private. I use them for direct browser or mobile uploads and for private downloads, so large files don't stream through my servers. My backend checks the user is allowed, picks the key itself, signs with a short expiry and a content type, and an S3 event triggers a Lambda to validate or scan the file afterwards. If the signer loses permissions, the URL stops working."

Likely follow-up questions

  • What if the signing role loses permissions before expiry? Requests fail, because S3 checks the signer's current permissions.
  • Presigned PUT vs POST? POST supports policy conditions like size limits and is suited to HTML forms.
  • Alternative for private downloads at scale? CloudFront signed URLs or cookies.
