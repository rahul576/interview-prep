What is the difference between docker buildx and the classic docker build?

Docker · concept · levels mid

In one line

Today docker build already uses BuildKit; docker buildx is the extended CLI for it, adding multi-platform builds (--platform), builder instances with drivers (docker-container, kubernetes, remote), advanced cache import/export, extra output types and buildx bake for many images.

Detailed explanation

Historically, docker build used the legacy builder, which executed Dockerfile steps sequentially and had a simple local cache. BuildKit replaced it with a concurrent, graph-based engine that skips unused stages, supports cache and secret mounts, and is the default builder since Docker Engine 23. On current Docker, docker build is effectively an alias for docker buildx build using the default builder.

buildx exposes BuildKit's full feature set. The headline is multi-platform builds: --platform linux/amd64,linux/arm64 builds both variants in one command and pushes a multi-architecture image index, so the same tag works on x86 servers and ARM (Graviton, Apple silicon). Platforms are built via QEMU emulation, cross-compilation in the Dockerfile using BUILDPLATFORM/TARGETPLATFORM, or native nodes combined into one builder.

buildx manages builder instances with different drivers. The default docker driver uses the daemon's built-in BuildKit and the local image store. The docker-container driver runs BuildKit in its own container, enabling multi-platform output and all cache exporters. The kubernetes driver runs builder pods in a cluster, and remote connects to an existing BuildKit daemon, including services such as Docker Build Cloud.

It supports cache export and import (type=registry, local, gha, s3, azblob), outputs other than images (--output type=local,dest=out to extract build artifacts, type=tar, type=oci), and attestations such as SBOM and provenance. docker buildx bake reads an HCL, JSON or Compose file defining many targets, variables and groups and builds them in parallel, which is convenient for monorepos.

How it works

  1. docker buildx create defines a builder with a driver.
  2. The build request goes to that builder's BuildKit.
  3. BuildKit solves the build graph, in parallel where possible.
  4. For each platform it builds or cross-compiles.
  5. Results are exported as an image index, tarball or files, plus cache.

Example

docker buildx create --name multi --driver docker-container --use
docker buildx build --platform linux/amd64,linux/arm64 \
  --cache-from type=registry,ref=ghcr.io/acme/api:cache \
  --cache-to type=registry,ref=ghcr.io/acme/api:cache,mode=max \
  -t ghcr.io/acme/api:1.4.0 --push .
docker buildx imagetools inspect ghcr.io/acme/api:1.4.0
# docker-bake.hcl
group "default" { targets = ["api", "worker"] }
target "api"    { context = "./api"    tags = ["ghcr.io/acme/api:1.4.0"] }
target "worker" { context = "./worker" tags = ["ghcr.io/acme/worker:1.4.0"] }

Common mistakes

  • Thinking buildx is a separate builder from BuildKit.
  • Expecting multi-platform images to load into the classic local image store with --load.
  • Emulating heavy compiles with QEMU instead of cross-compiling or using native runners.
  • Forgetting --push or an output type, so the result stays only in the builder cache.

How to answer in the interview

"The classic docker build used the legacy builder; today docker build uses BuildKit by default, and buildx is the extended CLI to it. buildx adds multi-platform builds, like --platform linux/amd64,linux/arm64 producing a multi-architecture image in one command, and lets me create builder instances with drivers such as docker-container, Kubernetes or remote builders. It supports advanced cache import and export to registries or CI caches, other output types, and attestations. docker buildx bake builds many images in parallel from one HCL, JSON or Compose file."

Likely follow-up questions

  • How do you build ARM images on x86 CI? QEMU via docker/setup-qemu-action, cross-compilation, or native ARM runners.
  • What are BUILDPLATFORM and TARGETPLATFORM? Build args for cross-compiling from the build host to the target.
  • Why use the docker-container driver? It supports multi-platform builds and every cache exporter.
