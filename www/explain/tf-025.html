How do you scan Terraform code for security and compliance problems before it is applied?

Terraform · concept · levels mid, senior

In one line

Run static scanners such as Checkov, Trivy (which absorbed tfsec) or KICS on HCL in pre-commit and CI, also scan the plan JSON for evaluated values, enforce organisation rules with policy as code (OPA/Conftest or Sentinel) as a gate before apply, and document every suppression.

Detailed explanation

Misconfiguration, not zero-day exploits, causes most cloud incidents: public buckets, SSH open to the internet, unencrypted databases, wildcard IAM policies, disabled logging. Infrastructure as code lets you catch these before they exist, which is far cheaper than finding them later with a cloud security posture tool.

Static scanners parse Terraform code and apply hundreds of built-in rules mapped to frameworks such as CIS Benchmarks, NIST or PCI DSS. Checkov (Prisma Cloud) is widely used and supports graph-based checks across resources. Trivy (Aqua) now includes the former tfsec engine, so one tool scans containers, IaC and dependencies. KICS (Checkmarx) is another option. They run in seconds and output SARIF for GitHub or GitLab security dashboards.

Scanning HCL has a blind spot: values coming from variables, modules or expressions may not be resolvable statically. So for important checks I also scan the plan: terraform show -json tfplan > plan.json contains fully evaluated values, and both Checkov and policy engines can evaluate it.

Organisation-specific rules (allowed regions, mandatory tags, approved instance sizes, no public IPs in production) are written as policy as code: OPA Rego with Conftest, or Sentinel / OPA in HCP Terraform policy sets, with advisory, soft-mandatory or hard-mandatory enforcement. Cloud-side guardrails (AWS SCPs, Azure Policy) remain the last line of defence for anything that bypasses Terraform.

To keep developers engaged, scanners run in pre-commit hooks for fast feedback, a curated rule set avoids noise, and suppressions are inline comments with a reason and ticket, reviewed like code.

How it works

  1. Developer runs pre-commit: terraform fmt, TFLint, Checkov or Trivy.
  2. PR pipeline runs the same scanners and uploads SARIF.
  3. Pipeline creates the plan and exports JSON.
  4. Conftest or Sentinel evaluates organisation policies on the plan.
  5. High-severity failures block merge or apply; suppressions require review.

Example

checkov -d . --framework terraform --quiet --output sarif > checkov.sarif
trivy config --severity HIGH,CRITICAL .
terraform plan -out=tfplan && terraform show -json tfplan > plan.json
conftest test plan.json --policy policy/
package main
deny contains msg if {
  r := input.resource_changes[_]
  r.type == "aws_s3_bucket"
  not r.change.after.tags.owner
  msg := sprintf("%s must have an owner tag", [r.address])
}

Common mistakes

  • Enabling every rule and drowning developers in noise.
  • Only scanning HCL, missing values from variables and modules.
  • Suppressions without explanation.
  • Running scans only nightly instead of on every PR.

How to answer in the interview

"I run static scanners like Checkov, Trivy, which absorbed tfsec, or KICS on every pull request. They have hundreds of rules for things like public buckets, security groups open on SSH, missing encryption, disabled logging or overly broad IAM, mapped to frameworks like CIS. Because HCL scanning misses values computed from variables, I also scan the plan JSON from terraform show -json. Organisation-specific rules like allowed regions or mandatory tags go into policy as code with OPA Conftest or Sentinel as a gate before apply. Developers get the same checks in pre-commit hooks, and every suppression needs a documented reason."

Likely follow-up questions

  • Keeping scanner noise low? Curated rule set, severity thresholds, baselines for legacy code and fast feedback in pre-commit.
  • Static scan or plan scan? Both; static is fast, plan scanning sees real values.
  • What if someone bypasses Terraform? Cloud-level guardrails such as SCPs and Azure Policy plus CSPM monitoring.
