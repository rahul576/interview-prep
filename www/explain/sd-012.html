What is the difference between stateful and stateless services, and how do you handle state at scale?

SD Fundamentals · concept · levels entry, mid, senior

In one line

Stateless services keep nothing between requests, so any instance can serve anyone and scaling is trivial; stateful services need routing by key, replication and rebalancing, so isolate them and keep everything else stateless.

Detailed explanation

State is anything a service must remember: sessions, open connections, in-memory caches, game worlds, stream-processing windows. If it lives in an instance's memory, the next request must reach that instance, and losing the instance loses the state.

Making services stateless means moving state out: sessions to Redis or signed JWTs, files to object storage, data to databases. Then instances can be killed, replaced or autoscaled freely.

Some components are stateful by nature. WebSocket gateways hold millions of connections; stream processors (Flink, Kafka Streams) hold windows and aggregates; actor systems hold entity state. For these you need: consistent routing (hash by user or entity ID), replication or checkpointing (Flink checkpoints, Kafka changelog topics), and rebalancing when nodes join or leave.

How it works

  1. Default: stateless pods behind a load balancer.
  2. Externalise state to Redis, databases, object storage.
  3. For stateful parts, partition by key and route consistently.
  4. Persist state (checkpoints, changelogs, replicas) so a crash can recover.
  5. On scaling events, move partitions and restore state before serving.

Example

A chat gateway: each WebSocket server holds connections. A registry (Redis) maps userId → gatewayId. Messages for a user are routed to the right gateway through pub/sub. If a gateway dies, clients reconnect to another one and re-register; undelivered messages come from the durable message store.

Common mistakes

  • In-memory sessions plus sticky sessions as a "scaling strategy".
  • Local caches without accepting they're per-instance and inconsistent.
  • Running stateful systems without testing failover and rebalancing.

How to answer in the interview

"I keep application services stateless: sessions in Redis or tokens, files in object storage, so I can autoscale freely. Where state is unavoidable, like WebSocket gateways or stream processors, I partition by key, route consistently and make state recoverable through replication or checkpoints. That keeps the hard parts small and isolated."

Likely follow-up questions

  • How do you scale to millions of WebSocket connections? Many gateway nodes, connection registry, pub/sub fan-out, graceful reconnects.
  • JWT vs server sessions? JWTs are stateless but hard to revoke; sessions are revocable but need a store.
  • What does a StatefulSet give you? Stable names and per-pod volumes.
