How would you design an LRU cache with O(1) get and put?

DSA: Lists, Stacks & Queues · concept · levels mid

In one line

Combine a hash map (key to node, for O(1) lookup) with a doubly linked list ordered by recency. Move a node to the front on every access, insert new keys at the front, and evict from the tail when over capacity. All operations are O(1). In Java, LinkedHashMap with access order and removeEldestEntry does this out of the box.

Detailed explanation

An LRU (Least Recently Used) cache keeps at most capacity entries. When full, it evicts the entry that hasn't been accessed for the longest time. We need three operations in O(1):

  • find a key, which a hash map gives us
  • mark it most recently used, which means moving it to the front of an ordering
  • find and remove the least recently used, the back of that ordering

An array or singly linked list can't move or remove an arbitrary element in O(1). A doubly linked list can, if we already have a reference to the node, and that is exactly what the map stores. So map: key -> Node(key, value, prev, next).

Sentinel head and tail (dummy nodes) remove all null checks when inserting at the front or unlinking. The node stores its key, so that when we evict the tail we can also remove it from the map.

  • get(key): look up the node. If absent, return -1. Otherwise unlink it, insert it after the head, and return the value.
  • put(key, value): if present, update the value and move it to the front. Otherwise create a node, insert it at the front and add it to the map. If size > capacity, remove tail.prev from both the list and the map.

Java shortcut: new LinkedHashMap<>(cap, 0.75f, true) (the third argument is accessOrder), overriding removeEldestEntry to return size() > cap. This is great in production code, but interviewers usually want the manual version too.

Thread safety: wrap the operations in a lock (simple, but contention-heavy), or use a proven library such as Caffeine (Window TinyLFU, concurrent, with better hit rates than pure LRU). Redis offers allkeys-lru eviction (approximated by sampling).

How it works

  1. Create head <-> tail sentinels and an empty map.
  2. get: map lookup, then remove(node), then addFirst(node).
  3. put an existing key: update and move to the front.
  4. put a new key: addFirst and map.put. If over capacity, lru = tail.prev, remove(lru), map.remove(lru.key).

Example

class LRUCache {
    private static class Node { int key, val; Node prev, next; Node(int k, int v) { key = k; val = v; } }
    private final Map<Integer, Node> map = new HashMap<>();
    private final Node head = new Node(0, 0), tail = new Node(0, 0);
    private final int cap;
    LRUCache(int cap) { this.cap = cap; head.next = tail; tail.prev = head; }

    public int get(int key) {
        Node n = map.get(key);
        if (n == null) return -1;
        unlink(n); addFirst(n);
        return n.val;
    }
    public void put(int key, int val) {
        Node n = map.get(key);
        if (n != null) { n.val = val; unlink(n); addFirst(n); return; }
        n = new Node(key, val); map.put(key, n); addFirst(n);
        if (map.size() > cap) { Node lru = tail.prev; unlink(lru); map.remove(lru.key); }
    }
    private void unlink(Node n) { n.prev.next = n.next; n.next.prev = n.prev; }
    private void addFirst(Node n) { n.next = head.next; n.prev = head; head.next.prev = n; head.next = n; }
}

Common mistakes

  • Using a singly linked list or a queue, which makes removal O(n).
  • Not storing the key in the node, so you can't remove the evicted entry from the map.
  • Forgetting to move the node to the front on get, or on put of an existing key.
  • Using LinkedHashMap without accessOrder = true, which gives insertion order (FIFO), not LRU.

How to answer in the interview

"I'd combine a hash map with a doubly linked list. The map gives O(1) lookup from key to node, and the list keeps nodes in recency order, with sentinel head and tail nodes to avoid edge cases. On get, I find the node, move it to the front and return the value. On put, I update or insert at the front, and if we exceed capacity I evict the node before the tail and remove its key from the map. Everything is O(1). In Java, LinkedHashMap with access order and removeEldestEntry gives the same behaviour, and for concurrent production use I'd reach for Caffeine."

Likely follow-up questions

  • Thread-safe without a global lock? Segment by key hash (striped locks), or use Caffeine's buffered, lock-amortised design.
  • LFU instead? Use a map plus frequency buckets (frequency to a doubly linked list) with a tracked min frequency. O(1).
  • TTL expiry? Store an expiry time per node. Evict lazily on access plus a periodic sweep or timer wheel.
