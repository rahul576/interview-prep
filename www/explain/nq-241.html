How does Cassandra distribute data across nodes?

Databases & SQL · concept · levels mid, senior

In one line

Cassandra uses consistent hashing: the partitioner (Murmur3 by default) hashes the partition key to a token on a ring, nodes own token ranges (via virtual nodes), the partition is stored on the owning node plus further replicas per the replication strategy, and any node can act as coordinator.

Detailed explanation

Every row's partition key is hashed by the Murmur3Partitioner into a 64-bit token, from -2^63 to 2^63-1. The token space is treated as a ring. Each node owns one or more ranges of tokens; the first replica of a partition goes to the node owning its token range, and additional replicas are chosen by walking the ring.

Virtual nodes (vnodes): instead of one large range per node, each node owns many small ranges (num_tokens, which defaults to 16 in Cassandra 4.0+ with a token allocation algorithm, previously 256). This spreads data more evenly, lets a new node take small slices from many existing nodes, and spreads the streaming work during bootstrap and rebuilds.

Replication is configured per keyspace:

  • SimpleStrategy: next N nodes on the ring; only for single data centre tests.
  • NetworkTopologyStrategy: set a replication factor per data centre (for example {'dc1': 3, 'dc2': 3}) and place replicas on different racks using the snitch's topology information, so a rack or availability zone failure does not take all replicas.

Coordinator: the client driver (token-aware) usually sends a request straight to a replica, but any node can receive it, hash the key, find replicas and forward the request.

A poor partition key causes hot partitions (one key gets most traffic, such as today's date) or wide partitions (unbounded rows per key). Cassandra cannot split a single partition across nodes, so bucketing (for example (device_id, day)) is the fix.

How it works

  1. Client sends a request with the partition key.
  2. Murmur3 hashes the key to a token.
  3. The token's range identifies the primary replica.
  4. The replication strategy chooses the other replicas, rack- and DC-aware.
  5. The coordinator contacts the replicas and applies the consistency level.
  6. When nodes join or leave, only the affected token ranges are streamed.

Example

CREATE KEYSPACE shop WITH replication = {
  'class': 'NetworkTopologyStrategy', 'eu-west': 3, 'ap-south': 3 };

-- See where a key lives
SELECT token(customer_id) FROM shop.orders_by_customer WHERE customer_id = 42;
nodetool getendpoints shop orders_by_customer 42   # replicas for this key
nodetool status                                    # ownership per node

Common mistakes

  • Using SimpleStrategy in multi-DC production.
  • Partition keys with low cardinality or time-based hotspots.
  • Expecting range queries across partition keys (tokens are hashed, so order is lost).
  • Changing replication factor without running repair afterwards.

How to answer in the interview

"Cassandra uses consistent hashing. The partitioner, Murmur3 by default, hashes each partition key into a token, and the token space is a ring divided among nodes. With virtual nodes each physical node owns many small ranges, which balances data and makes adding nodes smoother. A partition is stored on the node owning its token and replicated to further nodes according to the keyspace's replication factor; NetworkTopologyStrategy places replicas on different racks and data centres. Any node can coordinate a request and forward it to the replicas. A bad partition key, such as a date, creates hot or oversized partitions, so I bucket keys to spread load."

Likely follow-up questions

  • What happens when you add a node? It takes ownership of some token ranges and streams that data; run nodetool cleanup on others afterwards.
  • What is a snitch? It tells Cassandra the rack and DC of each node for replica placement and routing.
  • Why can't you range-scan by partition key? Keys are hashed, so adjacent keys are spread across the ring.
