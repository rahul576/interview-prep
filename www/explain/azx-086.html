What is Microsoft Foundry, and how does it relate to Azure OpenAI?

Azure AI & Foundry · concept · levels entry, mid

In one line

Microsoft Foundry (formerly Azure AI Studio, then Azure AI Foundry) is Azure's platform for building generative AI apps and agents: a Foundry resource with projects organises models, agents, data connections, evaluations and access, and Azure OpenAI models are deployed and used through it alongside models from other providers.

Detailed explanation

Azure's AI tooling went through several names. Azure AI Studio became Azure AI Foundry, and it is now simply Microsoft Foundry. The idea stayed the same: one place, one portal and one SDK for the full lifecycle of AI applications, from picking a model to monitoring it in production.

Structure: you create a Foundry resource (an Azure AI Services resource) that holds model deployments, networking, keys or identity settings and quotas. Inside it, projects give a team or application an isolated workspace: its agents, files, connections to data sources (AI Search, Storage, SharePoint, Fabric), evaluations, traces and role-based access. Older hub-based projects still exist, but the resource-and-project model is the current recommendation.

Model catalog: Foundry offers models from OpenAI (GPT series, reasoning models, embeddings, image and audio models), plus Meta Llama, Mistral, DeepSeek, xAI, Cohere and Microsoft's own Phi models, among many others. Some are sold directly by Azure, others through partner offerings, and they are deployed as managed endpoints with deployment types like Standard, Global or Provisioned.

Relation to Azure OpenAI: Azure OpenAI is still a service, and existing Azure OpenAI resources and endpoints keep working. In Foundry, the same OpenAI models are deployed and called through the Foundry resource, with the same data privacy commitments, and you get the extra platform features on top.

Platform features: the Foundry Agent Service for building agents with tools, evaluations for quality and safety, tracing with OpenTelemetry, content safety filters, prompt management and responsible AI tooling, available both in the portal and the SDKs.

How it works

  1. Create a Foundry resource in a region with the models you need.
  2. Create projects per team or application, and assign RBAC.
  3. Deploy models from the catalog with a chosen deployment type.
  4. Connect data sources and build apps or agents with the SDK.
  5. Evaluate, trace and monitor from the project.

Example

az cognitiveservices account create -g rg-ai -n foundry-contoso -l swedencentral \
  --kind AIServices --sku S0 --custom-domain foundry-contoso --allow-project-management

az cognitiveservices account deployment create -g rg-ai -n foundry-contoso \
  --deployment-name gpt-chat --model-name gpt-4.1-mini --model-format OpenAI \
  --model-version "2025-04-14" --sku-name GlobalStandard --sku-capacity 100

Common mistakes

  • Treating Foundry and Azure OpenAI as competing services rather than layers.
  • One shared project for all teams, mixing data access and costs.
  • Assuming every catalog model has the same data residency and terms.
  • Ignoring the rename and searching outdated documentation.

How to answer in the interview

"Microsoft Foundry is Azure's platform for building generative AI apps and agents. It evolved from Azure AI Studio and Azure AI Foundry. You create a Foundry resource with projects that organise models, agents, data connections, evaluations and access per team. The model catalog includes OpenAI models and models from Meta, Mistral, DeepSeek and Microsoft's Phi. Azure OpenAI still exists, and its models are deployed and used through Foundry. On top you get the Agent Service, evaluations, tracing and content safety in one portal and SDK."

Likely follow-up questions

  • How to organise projects for several teams? One project per product or team, shared Foundry resource per environment, RBAC per project.
  • Do existing Azure OpenAI apps break? No, endpoints keep working; migration is optional.
  • Are partner models governed the same? Check each model's terms, region and deployment options.
