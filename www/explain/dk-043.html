How do you analyse and reduce the size of a Docker image?

Docker · concept · levels mid

In one line

Analyse with docker history and dive to find large layers, then shrink with a smaller base image, multi-stage builds, install-and-clean in the same RUN, --no-install-recommends, a .dockerignore, and copying only the built artifact.

Detailed explanation

Image size affects pull time, cold-start and autoscaling speed, registry storage and egress costs, and the number of packages a scanner reports. Before optimising, measure. docker history <image> lists each layer with its size and the instruction that created it, which quickly shows whether the base image, the dependency install or a stray COPY . . is responsible. dive is an interactive tool that browses each layer's files and calculates an efficiency score and wasted space, such as files added in one layer and deleted or overwritten in another.

The main techniques follow from how layers work. Because every instruction creates an immutable layer, files deleted in a later layer still exist in an earlier one, so package installation and cleanup must be in the same RUN: apt-get install --no-install-recommends ... && rm -rf /var/lib/apt/lists/*, pip install --no-cache-dir, npm cache clean. Multi-stage builds are the biggest win: compile in a full SDK image and copy only the JAR, binary or dist/ folder into a slim, distroless or scratch runtime image, so compilers, headers and test dependencies never ship. Choose a smaller base (slim, distroless, Alpine where compatible). A .dockerignore excludes .git, node_modules, build outputs and local secrets from the context, which also speeds builds and prevents accidental leaks.

Finally, look at the application itself: production-only dependencies, a jlink custom Java runtime, or stripping debug symbols from Go binaries (-ldflags="-s -w").

How it works

  1. Measure with docker images, docker history and dive.
  2. Identify the largest layers and wasted files.
  3. Move build tooling into a builder stage.
  4. Combine install and cleanup into single RUN steps.
  5. Exclude context files with .dockerignore.
  6. Re-measure and add a size check in CI.

Example

docker history --no-trunc --format "{{.Size}}\t{{.CreatedBy}}" api:1.4 | sort -h | tail
dive api:1.4
FROM golang:1.23 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -ldflags="-s -w" -o /out/app ./cmd/app

FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/app /app
ENTRYPOINT ["/app"]

Common mistakes

  • RUN rm in a separate layer and expecting the image to shrink.
  • COPY . . without .dockerignore, shipping .git and node_modules.
  • Shipping the full SDK image to production.
  • Squashing everything into one layer and losing cache reuse.

How to answer in the interview

"First I measure: docker history shows each layer's size and the instruction behind it, and dive lets me browse layers and highlights wasted space. Then I reduce: a slimmer base like slim or distroless, and a multi-stage build so compilers and build tools never reach the final image. Installation and cleanup go in the same RUN, with no-install-recommends and removing the apt lists, because files deleted in a later layer still exist in earlier ones. A .dockerignore keeps junk out of the context, and I copy only the built artifact."

Likely follow-up questions

  • Why does a smaller image matter? Faster pulls and scaling, lower costs, fewer CVEs.
  • Is fewer layers always better? No, well-ordered layers improve caching and reuse.
  • How do you prevent regressions? Fail CI when the image exceeds a size budget.
