How would you build an internal developer portal with Backstage?

Platform Engineering · design · levels senior, lead

In one line

Backstage, the CNCF open-source developer portal from Spotify, provides a software catalog with ownership, software templates (scaffolder) for golden paths, TechDocs for docs-as-code and plugins for CI/CD, Kubernetes, monitoring and cost; success depends on starting small and driving adoption.

Detailed explanation

Backstage is a framework, not a finished product: you build and run your own portal (a React frontend and Node.js backend with PostgreSQL), or buy a managed or commercial distribution such as Spotify Portal or Roadie. That means it needs a dedicated team with TypeScript skills.

The software catalog is the foundation. Each repository has a catalog-info.yaml describing entities: Components (services, websites, libraries), APIs, Resources (databases, buckets), Systems, Domains, Groups and Users, with owner, lifecycle and dependencies. Groups and users are ingested from the identity provider. The catalog answers "who owns this, what does it depend on, where are its docs and dashboards?".

Software templates (the scaffolder) implement golden paths: a developer fills in a form, and actions create the repository from a skeleton, register it in the catalog, open pull requests to the GitOps repo, create pipelines and cloud resources. TechDocs renders Markdown from each repo (MkDocs-based) into the portal, so docs live next to code. Plugins add tabs to each entity: CI runs (GitHub Actions, GitLab), Kubernetes status, Argo CD, Grafana dashboards, PagerDuty on-call, cost data, security findings.

Many rollouts fail because teams install it, register nothing useful and expect adoption. Treat it as a product: start with a narrow, valuable slice and measure.

How it works

  1. Deploy Backstage with SSO, PostgreSQL and the new backend system, via GitOps.
  2. Ingest users and groups; auto-discover catalog-info.yaml files across the Git organisation.
  3. Ship one high-value template, for example "new Spring Boot service".
  4. Add TechDocs and two or three plugins teams ask for most.
  5. Measure: catalog coverage, template usage, time to first production deploy.
  6. Iterate based on feedback; deprecate old paths gradually.

Example

apiVersion: backstage.io/v1alpha1
kind: Component
metadata:
  name: payments-api
  annotations:
    backstage.io/techdocs-ref: dir:.
    github.com/project-slug: acme/payments-api
    backstage.io/kubernetes-id: payments-api
spec:
  type: service
  lifecycle: production
  owner: group:payments-team
  system: checkout
  providesApis: [payments-api-v1]
  dependsOn: [resource:payments-db]

Common mistakes

  • Big-bang launch with dozens of plugins and no content.
  • No ownership data, so the catalog is untrusted.
  • Underestimating the engineering effort of maintaining Backstage upgrades.
  • Templates that create a repo but leave pipelines and infra manual.
  • Not measuring adoption.

How to answer in the interview

"Backstage has three core features. The software catalog registers every service, API and resource with its owning team and dependencies, from catalog-info files in each repo. Software templates implement golden paths: a developer fills a form and gets a repo with CI/CD, observability, security scanning and deployment config already wired. TechDocs renders documentation stored with the code. Plugins bring CI runs, Kubernetes status, dashboards, on-call and cost into one page per service. Since Backstage is a framework that needs real engineering, I'd start small, with the catalog and one high-value template, gather feedback, and measure catalog coverage and time to first deployment."

Likely follow-up questions

  • Why do Backstage rollouts fail? Empty or stale catalog, no product ownership, too much customisation; fix with automation and a narrow first use case.
  • Build or buy? Self-host if you have a TypeScript team; otherwise a managed offering.
  • How do you keep the catalog accurate? Generate entries from templates and auto-discovery, and validate in CI.
