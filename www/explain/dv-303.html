How do you implement least privilege for people, pipelines and workloads?

DevSecOps · concept · levels entry, mid

In one line

Least privilege means every person, pipeline and workload gets only the permissions it needs, for only as long as it needs them: role/group-based access, no shared accounts, MFA and just-in-time elevation for humans, short-lived federated credentials for pipelines and workloads, plus audit logs and regular access reviews.

Detailed explanation

Least privilege limits the blast radius: when an account, token or pod is compromised (and eventually one will be), the attacker gets only a narrow slice of access.

People: access is granted to groups or roles mapped from the identity provider, never ad hoc to individuals, so joiners, movers and leavers are handled by changing group membership. No shared accounts, so every action is attributable. MFA everywhere, ideally phishing-resistant. Day-to-day roles are read-only or limited; production admin rights are just-in-time: requested, approved and granted for a few hours via Azure PIM, AWS IAM Identity Center with temporary elevation tooling, or Teleport, then expire automatically. Break-glass accounts exist for emergencies, sealed and alerted.

Pipelines: each pipeline, and ideally each environment, gets its own identity with a narrowly scoped role: the staging deploy job cannot touch production. Pipelines authenticate via OIDC federation to the cloud, receiving tokens valid for minutes rather than stored keys. CI tokens themselves are minimal (permissions: contents: read), and production deploys require protected branches and environment approvals.

Workloads: use workload identity: AWS IAM roles for EC2, ECS task roles, EKS Pod Identity/IRSA, Azure managed identities, GCP workload identity. Each service gets its own identity scoped to specific resources, such as one queue or one bucket prefix. In Kubernetes, service accounts get minimal RBAC, and automounting tokens is disabled where not needed.

Verification: audit logs (CloudTrail, Entra sign-in logs), tools that find unused permissions (IAM Access Analyzer, last-accessed data), and quarterly access reviews.

How it works

  1. Define roles by job function and environment.
  2. Map IdP groups to roles; enforce MFA.
  3. Provide JIT elevation for privileged access with approval and expiry.
  4. Federate pipelines and workloads; remove static keys.
  5. Monitor usage; trim unused permissions; review regularly.

Example

# Kubernetes: a service account that can only read one ConfigMap
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { name: read-app-config, namespace: orders }
rules:
- apiGroups: [""]
  resources: ["configmaps"]
  resourceNames: ["orders-config"]
  verbs: ["get", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { name: orders-read-config, namespace: orders }
subjects: [{ kind: ServiceAccount, name: orders-api, namespace: orders }]
roleRef: { kind: Role, name: read-app-config, apiGroup: rbac.authorization.k8s.io }

Common mistakes

  • Permanent admin rights "because on-call needs them".
  • One CI service principal that can deploy everywhere.
  • Wildcard policies that are never revisited.
  • Removing users from the IdP but not from local accounts in tools.

How to answer in the interview

"Least privilege means every identity gets only the permissions it needs, for only as long as it needs them. For people, access comes through IdP groups and roles, no shared accounts, mandatory MFA, and just-in-time elevation for production admin, like Azure PIM or temporary AWS roles. Pipelines get their own scoped role per environment via OIDC federation with short-lived tokens. Workloads use workload or managed identities scoped to the exact resources they touch. Everything is logged, and I use tools like IAM Access Analyzer plus regular access reviews to remove permissions nobody uses."

Likely follow-up questions

  • Find over-privileged IAM roles? Access Analyzer unused-access findings and last-accessed data; generate policies from CloudTrail.
  • What is break-glass? An emergency account with strong controls and alerting on every use.
  • RBAC vs ABAC? Roles vs attribute/tag-based conditions; ABAC scales better with many resources.
