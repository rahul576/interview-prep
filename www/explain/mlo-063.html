How would you structure the repository for an ML project that goes to production?

MLOps · concept · levels mid, senior

In one line

Structure an ML repo like a software product: an installable src package holds production logic, notebooks only explore, and separate folders hold pipelines, configs, tests, infrastructure and deployment manifests, with pinned dependencies, Dockerfiles and CI.

Detailed explanation

The goal is that anyone can clone the repo, run tests, reproduce training and deploy, without reverse-engineering notebooks. The most important rule is that core logic lives in a package (src/<project>), with modules for data loading, feature engineering, training, evaluation and inference. That code is imported by notebooks, pipeline steps and the serving app alike, so the same feature function runs in training and serving, which reduces training-serving skew.

Notebooks are for exploration and reports. They import from the package and are not part of the production path; tools like nbstripout keep outputs out of Git. Pipelines contain thin step definitions for the orchestrator (Kubeflow, Airflow, SageMaker or Azure ML), calling package functions. Configs hold environment settings and hyperparameters in YAML (often with Hydra or similar), so the same code runs in dev, staging and prod.

Tests cover unit tests for feature functions, data validation (schema and expectations), a smoke training run on a tiny sample, and a test of the serving interface and model signature. Infrastructure as code (Terraform, Bicep) and deployment manifests (Helm values, KServe InferenceService, endpoint YAML) sit in their own folders. Dependencies are pinned with a lock file (uv.lock, poetry.lock), and Dockerfiles build training and serving images. CI runs linting, type checks, tests, image builds and pipeline compilation on every pull request.

How it works

  1. Start from a cookiecutter-style template so every project looks the same.
  2. Put reusable logic in src/, install it in editable mode.
  3. Keep pipelines and serving code as thin wrappers over the package.
  4. Parameterise everything via configs/, never hard-coded paths.
  5. Pin dependencies and build images in CI.
  6. Run tests and pipeline validation on each PR; deploy from main through CD.

Example

churn-model/
  src/churn/{data.py,features.py,train.py,evaluate.py,predict.py}
  notebooks/01-eda.ipynb
  pipelines/training_pipeline.py
  configs/{base.yaml,dev.yaml,prod.yaml}
  tests/{test_features.py,test_data_contract.py,test_train_smoke.py,test_api.py}
  serving/app.py
  docker/{train.Dockerfile,serve.Dockerfile}
  deploy/{helm/values-prod.yaml,kserve/inferenceservice.yaml}
  infra/terraform/
  .github/workflows/ci.yml
  pyproject.toml  uv.lock  README.md

Common mistakes

  • Production logic copy-pasted from notebooks into several places.
  • Unpinned dependencies, so a rebuild months later behaves differently.
  • Committing data or model binaries to Git instead of object storage or DVC.
  • No smoke test, so a broken training script is discovered only in the nightly run.

How to answer in the interview

"I use one template for every project. Production logic lives in an installable package under src, with data, features, train, evaluate and predict modules. Notebooks are for exploration and import from that package. Pipeline definitions and the serving app are thin wrappers. Configs hold environment settings and hyperparameters. Tests cover features, data validation, a smoke training run and the API. Infra and deployment manifests have their own folders, dependencies are locked, Dockerfiles build the training and serving images, and CI runs everything on each PR."

Likely follow-up questions

  • Serving code in the same repo as training? Usually yes, to share feature code and keep versions aligned; split only when teams or release cycles really differ.
  • Monorepo or one repo per model? Monorepo with shared libraries suits a platform team; per-model repos suit independent teams.
  • Where do data and models live? In object storage with versioning, referenced by the registry or DVC, not in Git.
