Design a secure multi-tier VPC for a web application across availability zones.

Cloud (AWS) · design · levels senior

In one line

Build a VPC with public, private application and isolated data subnets in each of three AZs, put only the ALB and NAT gateways in public subnets, give each AZ its own NAT gateway, keep AWS traffic private with VPC endpoints, chain security groups by reference, and add WAF, flow logs and Session Manager instead of SSH.

Detailed explanation

Start with a non-overlapping CIDR, allocated from central IPAM, large enough to grow, such as a /16 or /20 per environment. Create three tiers per AZ across three AZs. Public subnets have a route to the internet gateway and host only the internet-facing ALB and NAT gateways. Private application subnets host EC2, ECS or EKS workloads, routing outbound traffic through the NAT gateway in the same AZ, so one AZ failure does not break egress elsewhere. Isolated data subnets have no internet route at all and host RDS, Aurora and ElastiCache in subnet groups spanning AZs.

VPC endpoints cut NAT cost and keep traffic private: free gateway endpoints for S3 and DynamoDB, and interface endpoints (PrivateLink) for ECR, CloudWatch Logs, STS, Secrets Manager, SSM and KMS, with endpoint policies restricting which resources can be reached.

Security groups are the main control and reference each other rather than CIDRs: the ALB allows 443 from the internet (or CloudFront prefix list), the app SG allows the app port only from the ALB SG, and the database SG allows 5432 only from the app SG. NACLs stay mostly default, used for coarse subnet-level blocks. AWS WAF with managed rule groups and rate limiting protects the ALB, and CloudFront plus Shield add DDoS resilience. VPC flow logs go to S3 or CloudWatch, Route 53 Resolver DNS Firewall can block malicious domains, and Network Firewall can inspect egress when required.

Administration uses Systems Manager Session Manager, so no bastion hosts, SSH keys or inbound port 22. Data is encrypted with KMS and TLS end to end.

How it works

  1. User hits CloudFront or the ALB over HTTPS; WAF filters requests.
  2. ALB forwards to app targets in private subnets across AZs.
  3. App calls the database in isolated subnets via SG references.
  4. App reaches AWS APIs through VPC endpoints, internet via same-AZ NAT.
  5. Flow logs, ALB logs and CloudTrail feed central logging.

Example

module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  name    = "shop-prod"
  cidr    = "10.20.0.0/16"
  azs     = ["eu-west-1a", "eu-west-1b", "eu-west-1c"]
  public_subnets   = ["10.20.0.0/24", "10.20.1.0/24", "10.20.2.0/24"]
  private_subnets  = ["10.20.16.0/20", "10.20.32.0/20", "10.20.48.0/20"]
  database_subnets = ["10.20.64.0/24", "10.20.65.0/24", "10.20.66.0/24"]
  create_database_internet_gateway_route = false
  enable_nat_gateway     = true
  one_nat_gateway_per_az = true
  enable_flow_log        = true
}

resource "aws_security_group_rule" "db_from_app" {
  type                     = "ingress"
  from_port                = 5432
  to_port                  = 5432
  protocol                 = "tcp"
  security_group_id        = aws_security_group.db.id
  source_security_group_id = aws_security_group.app.id
}

Common mistakes

  • A single NAT gateway for all AZs, a hidden single point of failure.
  • Tiny subnets that run out of IPs once EKS or Lambda ENIs arrive.
  • CIDR-based SG rules like 10.0.0.0/8 instead of SG references.
  • Bastion hosts with SSH open to the world.

How to answer in the interview

"I use a non-overlapping CIDR and three subnet tiers in each of three AZs: public subnets only for the ALB and NAT gateways, private app subnets for workloads, and isolated data subnets with no internet route for RDS and ElastiCache. Each AZ has its own NAT gateway, and gateway and interface endpoints keep S3, ECR and Secrets Manager traffic private and cheaper. Security groups reference each other: ALB allows 443, app only from the ALB, database only from the app. WAF protects the ALB, flow logs are on, and admins use Session Manager, never SSH."

Likely follow-up questions

  • How size CIDRs so the VPC can grow? Use a large block from IPAM, big private subnets, and leave unallocated space for new tiers.
  • Why one NAT per AZ? AZ resilience and avoiding cross-AZ data charges.
  • Where would you inspect egress? AWS Network Firewall in a central inspection VPC via Transit Gateway.
