What is the transactional outbox pattern, and why is dual-write a problem?

Microservices · concept · levels mid, senior

In one line

A dual write (save to the database, then publish to the broker) can leave the two inconsistent when one step fails; the transactional outbox writes the event to an outbox table in the same local transaction, and a relay (polling or CDC with Debezium) publishes it at least once to idempotent consumers.

Detailed explanation

Consider orderRepository.save(order); kafkaTemplate.send("orders", event);. If the database commit succeeds and the publish fails, or the process crashes in between, the order exists but no one hears about it. If you publish first and the commit then fails, consumers react to an order that does not exist. Wrapping both in @Transactional does not help, because the database and Kafka are separate resources, and XA two-phase commit is not a practical option with Kafka. This is the dual-write problem.

The transactional outbox turns two writes into one. In the same local ACID transaction as the business change, the service inserts a row into an outbox table with the event id, aggregate type and id, event type, payload and timestamp. Either both commit or neither does. A separate message relay then publishes outbox rows to the broker:

  • Polling publisher: a scheduled job reads unpublished rows in order, publishes them, and marks them sent or deletes them. Simple, but adds latency and DB load; use SELECT ... FOR UPDATE SKIP LOCKED if several instances poll.
  • Change data capture (CDC): Debezium reads the database's transaction log (Postgres WAL, MySQL binlog) and streams inserts into the outbox to Kafka. Its outbox event router routes by aggregate type and uses the aggregate id as the key. Low latency, no polling load.

The relay may crash after publishing but before marking the row, so delivery is at least once: consumers must be idempotent, deduplicating on the event id. Ordering per aggregate is preserved by publishing with the aggregate id as key.

How it works

  1. Begin transaction.
  2. Update business tables.
  3. Insert event into outbox.
  4. Commit: both or neither.
  5. Relay reads new outbox rows (poll or WAL).
  6. Publish to Kafka keyed by aggregate id; mark or delete the row.
  7. Consumers dedupe by event id.

Example

CREATE TABLE outbox (
  id            UUID PRIMARY KEY,
  aggregatetype VARCHAR(64)  NOT NULL,
  aggregateid   VARCHAR(64)  NOT NULL,
  type          VARCHAR(128) NOT NULL,
  payload       JSONB        NOT NULL,
  created_at    TIMESTAMPTZ  NOT NULL DEFAULT now()
);
@Transactional
public void cancel(UUID orderId) {
    Order o = orders.findById(orderId).orElseThrow();
    o.cancel();
    outbox.save(new OutboxRow(UUID.randomUUID(), "Order", orderId.toString(),
                              "OrderCancelled", toJson(new OrderCancelled(orderId))));
}

Common mistakes

  • Believing @Transactional covers the Kafka send.
  • Forgetting idempotent consumers, assuming the outbox gives exactly-once.
  • Letting the outbox table grow forever.
  • Using random keys, losing per-aggregate ordering.

How to answer in the interview

"A dual write is when a service writes to its database and separately publishes to Kafka. If one succeeds and the other fails, or the service crashes in between, the database and the event stream disagree, and a normal transaction cannot span both. The outbox pattern fixes it by inserting the event into an outbox table in the same local transaction as the business change. A relay then publishes those rows, either by polling or with CDC using Debezium reading the write-ahead log. The relay can publish twice, so delivery is at least once and consumers deduplicate on the event id."

Likely follow-up questions

  • How do you keep outbox events ordered per aggregate? Publish with the aggregate id as key and relay in commit order (CDC does this naturally).
  • Polling vs CDC? Polling is simpler; CDC has lower latency and load but needs Debezium and Kafka Connect.
  • What is the inbox pattern? The consumer-side counterpart: store received message ids to deduplicate.
