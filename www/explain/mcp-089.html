Walk through rolling out MCP in a regulated bank, from the first server to production.

MCP Servers · design · levels lead

In one line

In a regulated bank, involve risk, compliance, security and model risk management from day one, start with a low-risk read-only pilot, build enterprise identity, per-user authorization, audit logging, approved models and hosts within data residency rules and an internal registry, put every server through threat modelling, red teaming and evaluations, and expand gradually, adding write actions only with strong controls.

Detailed explanation

Banks operate under heavy scrutiny: operational resilience rules, outsourcing and third-party risk requirements, data protection, model risk management (for example SR 11-7-style frameworks), and in the EU regulations such as DORA and the AI Act. An MCP rollout that surprises compliance will be stopped, so they must be partners from the start, agreeing a framework for AI tool use, risk classification and the evidence each stage needs.

Pilot. The first server should be low-risk and read-only: searching internal policies, engineering documentation or the IT knowledge base, used by a small group. The aim is to establish patterns, not deliver maximum value.

Foundations before scale:

  • Integration with the bank's IdP, ideally enterprise-managed authorization, so the IdP controls which apps and users reach which servers.
  • Per-user authorization: the server acts on behalf of the user, so access matches existing entitlements.
  • A gateway with audit logging retained per regulation, plus DLP.
  • Approved models and hosts meeting data residency and outsourcing rules, with contracts in place.
  • An internal registry of vetted servers and versions.

Per-server assurance. Each new server goes through threat modelling (lethal trifecta, confused deputy, injection paths), security review, red teaming for prompt injection, and evaluations of task quality and tool selection. Results are documented for audit.

Gradual expansion. More data sources first, then write actions with strong controls: human approval, monetary and scope limits, four-eyes checks for high-impact operations, and segregation of duties. Continuous monitoring and periodic recertification keep it under control.

How it works

  1. Governance charter with risk, compliance, security, legal and model risk.
  2. Pilot: read-only policy search for 50 users; measure and document.
  3. Platform: IdP integration, gateway, audit, registry, approved model endpoints.
  4. Per-server lifecycle: request, threat model, review, red team, eval, approve, monitor.
  5. Expand data access; introduce writes with approvals and limits.
  6. Quarterly reviews and annual recertification.

Common mistakes

  • Engaging compliance after building the system.
  • Starting with customer-facing or payment actions.
  • Shared service accounts that bypass entitlements.
  • No documented evidence of testing for auditors.

How to answer in the interview

"I'd involve risk, compliance, security and model risk management from the start and agree a framework for AI tool use. The first server would be a low-risk, read-only pilot, like searching internal policies, for a small group, to establish patterns. Foundations come before scaling: the bank's IdP with enterprise-managed authorization, per-user authorization matching existing entitlements, a gateway with audit logging retained per regulation, approved models and hosts that meet data residency and outsourcing rules, and an internal registry. Each new server goes through threat modelling, security review, red teaming for prompt injection and evaluations. Then gradual expansion: more data, then write actions with human approval, limits and four-eyes checks, with continuous monitoring."

Likely follow-up questions

  • Use cases to refuse? Autonomous credit decisions or payments without human approval, due to accountability and regulation.
  • How evidence controls? Documented threat models, eval results, red-team reports and audit logs.
  • Third-party servers? Treated as outsourcing, with vendor due diligence.
