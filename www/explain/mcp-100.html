How do you design MCP tools that ask the user for confirmation or extra input in the stateless protocol?

MCP Servers · concept · levels mid, senior

In one line

In the stateless revision, servers no longer send requests to clients mid-call; a tool that needs confirmation or extra data returns an input-required result, the client collects answers through its elicitation UI and retries the call with them (multi round-trip requests), so the tool must be idempotent, validate answers and avoid side effects before it has everything.

Detailed explanation

In the handshake-based revisions, a server handling tools/call could send an elicitation/create request back to the client and wait on the open connection for the user's answer. That required a long-lived session and meant the same server instance had to hold the waiting call, which complicates horizontal scaling and load balancing.

The stateless 2026-07-28 revision removes server-to-client requests. Instead, when a tool cannot proceed, it finishes the current request with a result saying input is required, describing what it needs: a form schema (for example target environment and a confirm flag) or a URL for sensitive flows such as OAuth or payments, which must not pass through the client. The client shows the form or link to the user, then sends the original tool call again with the answers attached. This pattern is called multi round-trip requests.

Because the server may be a different instance on the retry and keeps no session, the design rules change. The tool must be safe to re-execute up to the point where it asked; it must do no side effects before it has all required input; it must re-validate the answers server-side (they come from the client and could be tampered with or stale); and, where state must carry over, it should return an opaque, signed or server-stored continuation token rather than relying on memory. Destructive actions should require explicit confirmation values, not just any retry.

How it works

  1. Client calls deploy with partial arguments.
  2. Server validates; missing environment and confirmation, so it returns input-required with a schema.
  3. Client renders the elicitation form; user picks "staging" and confirms.
  4. Client retries the same tool call with the original arguments plus the answers.
  5. Server re-validates permissions and answers, then executes once, using an idempotency key.

Example

// First response
{ "inputRequired": {
    "message": "Confirm deployment target",
    "requestedSchema": { "type": "object",
      "properties": { "environment": { "enum": ["staging", "production"] },
                      "confirm": { "type": "boolean" } },
      "required": ["environment", "confirm"] } } }

// Retried call
{ "name": "deploy", "arguments": { "service": "billing", "version": "2.3.1" },
  "inputResponses": { "environment": "staging", "confirm": true } }

Field names are illustrative; follow the exact shape in the current specification and SDK.

Common mistakes

  • Performing part of the action before asking, so the retry duplicates it.
  • Trusting the answers without re-checking permissions and values.
  • Keeping pending state in instance memory, which breaks behind a load balancer.
  • Collecting secrets through form elicitation instead of a URL flow.

How to answer in the interview

"In the stateless revision the server can't pause a tool call and send an elicitation request to the client. Instead the tool returns an input-required result describing what it needs, like a schema with environment and a confirm flag, or a URL for sensitive flows. The client collects the answers in its elicitation UI and retries the original call with them attached; that's multi round-trip requests. So I design tools to do nothing with side effects until they have all inputs, to be idempotent on retry, and to re-validate answers server-side, with any needed state in a signed token rather than memory."

Likely follow-up questions

  • How does this simplify horizontal scaling? Any instance can handle the retry because no session or waiting call lives on one server.
  • How do you prevent double execution? Idempotency keys and checking whether the operation already completed.
  • When use URL mode instead of a form? For credentials, OAuth consent or payments, which must not pass through the client.
