Design a video streaming platform like YouTube.

Classic Design Problems · design · levels mid, senior, lead

In one line

A YouTube-like platform: resumable uploads to object storage → a parallel transcoding pipeline → adaptive bitrate streaming (HLS/DASH) via CDN, with metadata, search, views and recommendations handled separately and asynchronously.

Detailed explanation

Two flows with very different needs. Upload/processing is write-heavy, compute-heavy and can take minutes. Playback is extremely read-heavy and latency-sensitive: it must start fast and never stall.

Raw uploads are huge, so clients upload in chunks directly to object storage. A transcoding pipeline splits the video into segments, transcodes each in parallel into several resolutions and codecs (H.264, VP9, AV1), creates thumbnails and manifests. Workers scale with queue depth, often on spot instances.

For playback, adaptive bitrate streaming cuts video into 2–6 second segments listed in a manifest (.m3u8 for HLS, .mpd for DASH). The player measures bandwidth and picks the quality per segment, so it degrades gracefully instead of buffering. Segments are perfect for CDN caching. Popular videos are served almost entirely from edges; the long tail goes back to origin.

How it works

  1. POST /videos → metadata row, pre-signed multipart URLs.
  2. Upload complete → event → split into chunks → transcode jobs on a queue (DAG of tasks).
  3. Outputs: segments per rendition + manifest + thumbnails → object storage; status READY.
  4. Watch page: metadata from DB/cache, manifest + segments from CDN.
  5. View events → Kafka → aggregated counts, watch history, recommendation features.

Common mistakes

  • Serving video from app servers.
  • Transcoding a whole file sequentially on one machine.
  • Updating view counts synchronously on each view in the main DB.
  • Storing every rendition for every video forever (cost); use tiers and on-demand renditions for cold content.

How to answer in the interview

"Uploads go directly to object storage with resumable multipart uploads. A queue-driven pipeline splits the video and transcodes chunks in parallel into multiple bitrates, producing HLS/DASH segments and manifests. Playback is adaptive bitrate through a CDN, so quality adjusts to bandwidth. Metadata lives in a sharded DB with a search index, and views and likes flow through Kafka for asynchronous aggregation and recommendations."

Likely follow-up questions

  • How do you reduce cost for unpopular videos? Fewer renditions, colder storage tiers, transcode on demand.
  • How do you count views at scale? Events to Kafka, aggregate in streams, approximate counts shown live.
  • Live streaming differences? Ingest via RTMP/SRT, low-latency HLS, real-time transcoding.
