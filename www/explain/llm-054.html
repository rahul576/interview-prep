How do you red team an LLM application before launch?

LLMOps & RAG · concept · levels mid, senior

In one line

Red teaming starts from an application-specific threat model, combines manual adversarial testing by diverse testers with automated attack tools such as PyRIT, garak and promptfoo, covers injection, data leakage, harmful content and tool misuse, prioritises and fixes findings, adds them to regression suites, and is repeated when models, prompts, tools or data change.

Detailed explanation

Generic safety testing by the model provider does not cover your risks: your data, your tools, your users and your business commitments.

Threat model first. What would be harmful here? Leaking another customer's data, giving dangerous medical or financial advice, making unauthorised commitments ("yes, you'll get a full refund"), misusing tools (sending emails, changing records), producing offensive or brand-damaging content, revealing confidential configuration. Who might attack: curious users, fraudsters, competitors, malicious content authors?

Manual testing. A mixed group: security engineers, domain experts who know what a harmful answer looks like, and people from different backgrounds and languages, since attacks and harms vary by culture and language. They try jailbreaks, multi-turn manipulation, indirect prompt injection through uploaded documents, web pages, emails and tool results, data exfiltration (for example via markdown image URLs), and agent tool abuse.

Automated testing. Microsoft PyRIT orchestrates multi-turn attacks and scoring; NVIDIA garak probes models with many attack families; promptfoo has red-team plugins generating adversarial cases for your app. These generate large volumes of variations, which humans can't.

Triage and fix. Rate findings by impact and likelihood. Prefer design fixes (remove a tool's write access, enforce permissions in code) over prompt patches, add guardrails where design can't help, and add every finding to the regression suite.

Repeat on significant changes: new model, new tool, new data source, new market.

How it works

  1. Define scope, harms, attacker profiles and success criteria.
  2. Manual sessions with diverse testers; record transcripts.
  3. Automated scans with PyRIT/garak/promptfoo.
  4. Triage by severity; decide launch blockers.
  5. Fix by design, guardrails or scope reduction.
  6. Add to regression suite; retest; repeat on changes.

Example

# promptfoo red team config (simplified)
redteam:
  purpose: "Bank support assistant; can read balances and create support tickets"
  plugins:
    - pii
    - excessive-agency
    - hijacking
    - prompt-extraction
    - indirect-prompt-injection
  strategies:
    - jailbreak
    - prompt-injection

Common mistakes

  • Testing only single-turn, English, obvious jailbreaks.
  • Ignoring indirect injection through documents and tools.
  • Fixing findings with prompt wording only.
  • One red team exercise before launch, never again.

How to answer in the interview

"I start with a threat model for this specific app: what harm could it do, like leaking customer data, making unauthorised commitments or misusing tools, and who would attack it. Then manual testing by a diverse group, security engineers and domain experts, trying jailbreaks, indirect injection through documents and tool results, data exfiltration and tool abuse. Automated tools like PyRIT, garak and promptfoo generate thousands of variations. Findings are prioritised by impact, fixed by design changes, guardrails or tool restrictions, and added to the regression suite. I repeat it whenever the model, tools or data sources change."

Likely follow-up questions

  • Finding that delays launch? Cross-user data leakage or unauthorised actions via tools.
  • Who should red team? Mix of internal security, domain experts, and external specialists for high-risk apps.
  • Measuring success? Attack success rate per category, trending down across releases.
