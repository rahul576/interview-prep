Explain the lifecycle of a Spring bean.

Spring Boot · concept · levels entry, mid

In one line

A bean is instantiated, gets its dependencies injected, has Aware callbacks called, passes through BeanPostProcessor before-init hooks, runs @PostConstruct / afterPropertiesSet / init-method, passes after-init hooks (where AOP proxies are created), is used, and on shutdown gets @PreDestroy / destroy callbacks (singletons only).

Detailed explanation

Understanding the lifecycle explains many "why doesn't this work" questions, for example why a dependency is null in a constructor-time call, or why @Transactional does nothing.

Before any bean is created, BeanFactoryPostProcessors can modify bean definitions (for example resolving ${...} placeholders). Then for each bean:

  1. Instantiation: the constructor runs, with constructor arguments already resolved.
  2. Population: field and setter injection, @Value values.
  3. Aware interfaces: BeanNameAware, BeanFactoryAware, ApplicationContextAware and others receive container references.
  4. postProcessBeforeInitialization of every BeanPostProcessor. @PostConstruct is actually invoked by one of these, CommonAnnotationBeanPostProcessor.
  5. Initialisation: @PostConstruct, then InitializingBean.afterPropertiesSet(), then a custom initMethod. This is where you validate configuration or open resources, because all dependencies are now set.
  6. postProcessAfterInitialization: here AOP auto-proxy creators wrap the bean in a proxy for @Transactional, @Async, @Cacheable or security. Other beans receive the proxy, not the raw object.
  7. The bean is ready. Once all singletons are created, SmartInitializingSingleton and the ContextRefreshedEvent / ApplicationReadyEvent follow, which is a better place for work that needs the whole context.
  8. Destruction on context close: @PreDestroy, DisposableBean.destroy(), custom destroyMethod. Only for singletons (and scoped beans when their scope ends); prototype beans are not destroyed by the container.

How it works

  1. Context refresh loads definitions and runs BeanFactoryPostProcessors.
  2. Each singleton is created, injected and initialised in dependency order.
  3. Post-processors may replace the bean with a proxy.
  4. Lifecycle beans (SmartLifecycle) start, such as message listeners and the web server.
  5. On shutdown, lifecycle beans stop and destruction callbacks run in reverse order.

Example

@Component
class PriceFeed implements InitializingBean, DisposableBean {
    private final FeedClient client;
    private Connection conn;

    PriceFeed(FeedClient client) { this.client = client; }          // 1. instantiate + inject

    @PostConstruct void init()   { log.info("PostConstruct"); }      // 5a
    @Override public void afterPropertiesSet() { conn = client.connect(); } // 5b
    @PreDestroy void close()     { log.info("PreDestroy"); }         // 8a
    @Override public void destroy() { conn.close(); }                // 8b
}

@Component
class TimingPostProcessor implements BeanPostProcessor {
    @Override
    public Object postProcessAfterInitialization(Object bean, String name) {
        return bean;   // could return a proxy wrapping the bean
    }
}

Common mistakes

  • Using injected fields inside the constructor with field injection (they are still null).
  • Expecting @Transactional on a @PostConstruct method to start a transaction: the proxy does not exist yet for self calls.
  • Heavy work like cache warming in @PostConstruct, slowing startup; use ApplicationReadyEvent.
  • Expecting @PreDestroy on prototypes.

How to answer in the interview

"The container first instantiates the bean, then injects its dependencies. Aware interfaces like ApplicationContextAware are called, then the BeanPostProcessors' before-initialisation hooks, then initialisation callbacks: @PostConstruct, afterPropertiesSet, or a custom init method. Then the after-initialisation hooks run, and that's where AOP proxies are created for @Transactional, @Async or caching, so other beans get the proxy. The bean is then ready. On shutdown, @PreDestroy and destroy methods run for singletons; prototype beans aren't destroyed by the container."

Likely follow-up questions

  • Why might @Transactional not work on a bean created with new? It is not a Spring bean, so no post-processor wraps it in a proxy.
  • BeanPostProcessor vs BeanFactoryPostProcessor? The first changes bean instances; the second changes bean definitions before creation.
  • Where to run startup logic needing all beans? ApplicationReadyEvent listener or ApplicationRunner.
