What are user-defined routes in Azure, and how do you force traffic through a firewall?

Azure · concept · levels mid, senior

In one line

Azure adds system routes automatically; route tables with user-defined routes (UDRs) override them per subnet. To force traffic through a firewall, give spoke subnets a 0.0.0.0/0 route with next hop "virtual appliance" = firewall private IP, add routes for other spokes and on-premises, and avoid asymmetric routing and unwanted BGP propagation.

Detailed explanation

Every subnet has system routes: the VNet address space is routed locally, peered VNets are reachable, 0.0.0.0/0 goes to the Internet, and some reserved ranges go nowhere. Gateways add BGP-learned routes from on-premises via VPN or ExpressRoute.

A route table is a resource with user-defined routes, associated with one or more subnets. Each route has an address prefix and a next hop type: VirtualAppliance (with an IP), VirtualNetworkGateway, VnetLocal, Internet or None (drop). Azure picks the route with the longest prefix match; for identical prefixes, UDRs beat BGP routes, which beat system routes.

Forcing traffic through Azure Firewall in hub-and-spoke:

  • On each spoke workload subnet: 0.0.0.0/0 → VirtualAppliance → <firewall private IP>. This sends internet-bound traffic, and with no more specific route also traffic to other spokes, to the firewall. Since a peered hub VNet's own range is still more specific, add explicit routes if hub-bound traffic should be inspected too.
  • On the GatewaySubnet: routes for spoke prefixes pointing to the firewall, so traffic from on-premises is inspected on the way in.
  • Set "propagate gateway routes" = false on spoke route tables, so on-premises routes learned via BGP do not bypass the firewall.

Pitfalls:

  • Asymmetric routing: traffic goes out through the firewall but returns by a different path (for example directly via a public IP or a gateway); the stateful firewall sees only half the flow and drops it. Make sure both directions use the firewall, and avoid instance-level public IPs behind forced routes.
  • Do not route the firewall's own subnet back to itself. AzureFirewallSubnet needs direct internet access for its own outbound traffic and management; a 0.0.0.0/0 UDR pointing elsewhere breaks it unless using forced tunnelling with a management subnet.
  • PaaS services and private endpoints may need specific routes or network policies enabled.

Verify with Network Watcher: effective routes on a NIC and next hop.

How it works

  1. Deploy Azure Firewall in the hub and note its private IP.
  2. Create a route table with 0.0.0.0/0 to the firewall IP.
  3. Disable gateway route propagation on it.
  4. Associate it with spoke workload subnets.
  5. Add GatewaySubnet routes for spoke prefixes via the firewall.
  6. Verify effective routes and firewall logs.

Example

az network route-table create -g rg-spoke-app -n rt-spoke-app \
  --disable-bgp-route-propagation true
az network route-table route create -g rg-spoke-app --route-table-name rt-spoke-app \
  -n default-via-fw --address-prefix 0.0.0.0/0 \
  --next-hop-type VirtualAppliance --next-hop-ip-address 10.0.1.4
az network vnet subnet update -g rg-spoke-app --vnet-name vnet-spoke-app \
  -n snet-app --route-table rt-spoke-app
az network nic show-effective-route-table -g rg-spoke-app -n nic-app-vm01 -o table

Common mistakes

  • Forgetting to disable BGP propagation, so on-premises traffic bypasses the firewall.
  • Asymmetric routes through different appliances or public IPs.
  • A 0.0.0.0/0 UDR on AzureFirewallSubnet pointing at the firewall or another NVA.
  • Not adding routes on the GatewaySubnet for inbound inspection.
  • Assuming peering alone routes spoke-to-spoke traffic (it is not transitive).

How to answer in the interview

"Azure creates system routes automatically, so VNet subnets, peered VNets and the internet are reachable without configuration. To change that, I create a route table with user-defined routes and associate it with subnets; the longest prefix wins, and for equal prefixes UDRs beat BGP and system routes. To force traffic through Azure Firewall, each spoke subnet gets 0.0.0.0/0 with next hop virtual appliance and the firewall's private IP, plus GatewaySubnet routes so traffic from on-premises is inspected too. I disable gateway route propagation so BGP routes do not bypass the firewall, and watch for asymmetric routing, which a stateful firewall drops. I always verify with Network Watcher effective routes."

Likely follow-up questions

  • Why not put a 0.0.0.0/0 route on AzureFirewallSubnet itself? The firewall needs direct internet for its traffic and management; it would break or loop.
  • How do you route spoke-to-spoke traffic? Via the hub firewall with UDRs, since peering is not transitive.
  • What does next hop type None do? Drops the traffic, useful for blackholing ranges.
