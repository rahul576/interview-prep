How would you decide whether to move right or down to minimize the total cost?

DSA: Algorithms & DP · concept · levels mid

In one line

Don't choose right or down greedily by the next cell's value; decide using the accumulated optimal cost from DP, which relies on optimal substructure, then backtrack from the end to recover the path.

Detailed explanation

A tempting approach is: at each step, move to whichever neighbour (right or down) is cheaper. That is a greedy strategy, and it fails because a cheap next cell can lead into an expensive region later. The local best is not the global best. Greedy only works when a problem has the greedy-choice property, which the grid path problem does not.

The correct way to "decide" is to delay the decision until you know the full consequences. DP computes, for each cell, the minimum total cost to reach it. The problem has optimal substructure: the best path to (i, j) must pass through the best path to either (i-1, j) or (i, j-1). So at each cell the right decision is "come from whichever predecessor has the smaller accumulated cost", not whichever neighbour has the smaller raw value.

Once the table is filled, the actual sequence of moves is recovered by backtracking from the bottom-right: at each cell, step to the top or left neighbour with the smaller dp value until you reach the start, then reverse the list. Alternatively, store a parent/direction matrix while filling, which avoids recomputing comparisons and handles ties consistently.

How it works

  1. Fill dp with accumulated minimum costs (top/left recurrence).
  2. Start at (m-1, n-1) and add it to the path.
  3. If on the first row, move left; if on the first column, move up.
  4. Otherwise move to whichever of top/left has the smaller dp value.
  5. Stop at (0, 0), reverse the path, and derive the R/D moves.

Example

Greedy failure grid:

1  1  100
5  100 100
1  1   1

Greedy from the start goes right (1 < 5), then right again, and is forced through 100s: total ≥ 203. DP finds 1 → 5 → 1 → 1 → 1 = 9 by going down first.

List<int[]> path = new ArrayList<>();
int i = m - 1, j = n - 1;
while (i > 0 || j > 0) {
    path.add(new int[]{i, j});
    if (i == 0) j--;
    else if (j == 0) i--;
    else if (dp[i - 1][j] <= dp[i][j - 1]) i--;
    else j--;
}
path.add(new int[]{0, 0});
Collections.reverse(path);

Common mistakes

  • Using the neighbour's raw cost instead of the accumulated dp value.
  • Backtracking with a 1D rolling array, which has discarded the needed rows.
  • Forgetting to reverse the reconstructed path.
  • Not handling first-row and first-column boundaries during backtracking.

How to answer in the interview

"I wouldn't decide greedily by looking at the next cell, because a cheap neighbour can lead into an expensive area; I can show a small grid where greedy gives over 200 and the optimum is 9. Instead I rely on optimal substructure: the best path to a cell comes through the best path to its top or left neighbour. So I fill a DP table of accumulated costs first, and then reconstruct the path backwards from the bottom-right, each time stepping to the neighbour with the smaller accumulated cost, and reverse it at the end. If I need the path I keep the full table or a parent matrix."

Likely follow-up questions

  • Can you give a grid where greedy fails? Yes, a cheap first step that leads into a column of large values.
  • How do you handle ties? Pick either consistently; both give an optimal path.
  • Why not backtrack with the O(n) version? Previous rows are overwritten, so store directions or keep the full table.
