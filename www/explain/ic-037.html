How do you design a good reusable Terraform module?

Infrastructure as Code · design · levels mid

In one line

A good module has a single responsibility, a small typed, validated, documented interface with secure defaults, useful outputs, no provider configuration or hard-coded regions, semantic versioned releases, examples and automated tests.

Detailed explanation

Modules are Terraform's unit of reuse, and a badly designed one spreads problems to every consumer.

Scope. A module should do one thing that makes sense on its own: "an S3 bucket with our security baseline", "a VPC with standard subnets", "an ECS service with load balancer, logs and alarms". Thin wrappers around a single resource that add nothing are not worth the indirection; giant modules that build half the platform are hard to change and slow to plan.

Interface. Inputs have explicit types (objects with optional() attributes and defaults), descriptions, validation blocks and secure defaults: encryption on, public access off, logging on. Required inputs are only the ones the caller truly must decide. Outputs expose what callers need, IDs, ARNs, names, endpoints, and nothing internal. Hide complexity, but allow escape hatches like extra tags or policy statements.

Portability. The module declares required_providers with loose minimum versions but does not configure providers, regions, accounts or backends; the root module passes providers in, so the same module works in any account and region. No hard-coded names that would collide when used twice: use a name input or prefix.

Lifecycle. Release with semantic version tags in Git or a private registry (HCP Terraform, Artifactory, GitLab). Consumers pin version = "~> 2.3" or a Git ref. A CHANGELOG documents breaking changes, and moved blocks keep refactors non-destructive for consumers.

Docs and tests. A README generated by terraform-docs, runnable examples/ directories, and automated tests: terraform test with mocks for logic, plus Terratest or terraform test apply runs in a sandbox for important shared modules, run in CI with fmt, validate, tflint and security scans.

How it works

  1. Define the purpose and the minimal interface.
  2. Implement with typed inputs, validation and secure defaults.
  3. Add outputs, README, examples.
  4. Test in CI; tag a semantic version.
  5. Consumers pin versions and upgrade via PRs.

Example

variable "name" {
  type        = string
  description = "Bucket name prefix"
  validation {
    condition     = can(regex("^[a-z0-9-]{3,40}$", var.name))
    error_message = "Use 3-40 lowercase letters, digits or hyphens."
  }
}

variable "lifecycle_rules" {
  type = list(object({
    days          = number
    storage_class = optional(string, "STANDARD_IA")
  }))
  default = []
}

output "bucket_arn" { value = aws_s3_bucket.this.arn }
module "logs_bucket" {
  source  = "app.terraform.io/acme/s3-bucket/aws"
  version = "~> 2.3"
  name    = "orders-logs"
}
modules/s3-bucket/
  main.tf variables.tf outputs.tf versions.tf README.md CHANGELOG.md
  examples/basic/  tests/basic.tftest.hcl

Common mistakes

  • Provider blocks inside modules.
  • Exposing every resource argument as a variable ("pass-through" modules).
  • Unpinned source references to main.
  • Breaking changes in minor versions.

How to answer in the interview

"A good module does one thing well, like an S3 bucket with our security defaults or a complete ECS service, behind a small, well-typed interface. Inputs have types, descriptions, secure defaults and validation; outputs expose what callers need, like IDs and ARNs. It never configures providers or hard-codes regions or accounts, so callers stay in control. It's released with semantic version tags in Git or a private registry so consumers pin versions, with a changelog for breaking changes. And it ships with a terraform-docs README, runnable examples and automated tests with terraform test or Terratest."

Likely follow-up questions

  • When does creating a module add more complexity than value? When it wraps one resource without adding defaults or logic, or is used only once.
  • How do you handle breaking changes? Major version bump, changelog, moved blocks, migration guide.
  • Module in the same repo or separate? Separate repos/registry for widely shared modules; local paths for internal structure.
