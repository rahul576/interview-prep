How do you design an immutable class in Java?

Core Java & OOP · concept · levels entry, mid, senior

In one line

Make the class final, all fields private final, provide no setters, initialise everything in the constructor, make defensive copies of mutable inputs and outputs (List.copyOf), and do not let this escape; records give most of this for free.

Detailed explanation

An immutable object cannot change state after construction. That makes it inherently thread-safe (no synchronisation needed, thanks to final-field publication guarantees), safe to share and cache, safe as a HashMap key (its hash never changes), and easy to reason about. String, Integer, BigDecimal, LocalDate and List.of(...) are immutable.

The rules:

  1. Declare the class final (or make constructors private with static factories) so a subclass cannot add mutable state or override methods to behave mutably.
  2. Make all fields private final: assigned once, in the constructor.
  3. No setters or other mutators. "Modifying" methods return a new instance (withEmail(...), like LocalDate.plusDays).
  4. Defensive copies on the way in: if the constructor receives a mutable object (a List, Date, array), copy it; otherwise the caller keeps a reference and can change your internals. List.copyOf and Map.copyOf produce unmodifiable copies (and reject nulls).
  5. Defensive copies or unmodifiable views on the way out: never return the internal array or mutable collection. If the field already holds an unmodifiable copy, returning it directly is fine.
  6. Do not let this escape during construction (no registering listeners or starting threads in the constructor), so other threads never see a half-built object.
  7. Prefer immutable field types (LocalDate rather than java.util.Date).

Records (Java 16) are implicitly final with private final fields, canonical constructor, accessors, equals, hashCode and toString. But they are only shallowly immutable: a List component can still be mutated by whoever holds it, so use a compact constructor to copy it. The elements themselves must also be immutable for deep immutability.

How it works

  1. The constructor validates arguments and copies mutable ones.
  2. Fields are assigned once and never changed.
  3. Accessors return immutable values or copies.
  4. "Change" operations construct and return a new object.
  5. final fields guarantee other threads see the fully initialised values after construction.

Example

public final class Order {
    private final String id;
    private final List<LineItem> items;       // LineItem should itself be immutable
    private final Instant createdAt;

    public Order(String id, List<LineItem> items, Instant createdAt) {
        this.id = Objects.requireNonNull(id);
        this.items = List.copyOf(items);       // defensive, unmodifiable copy
        this.createdAt = createdAt;            // Instant is immutable
    }

    public List<LineItem> items() { return items; }   // already unmodifiable
    public Order withItem(LineItem item) {            // "modification" -> new object
        var copy = new ArrayList<>(items);
        copy.add(item);
        return new Order(id, copy, createdAt);
    }
}

public record Customer(String name, List<String> emails) {
    public Customer {                         // compact constructor
        emails = List.copyOf(emails);         // record is now immutable for this component
    }
}

Common mistakes

  • Making fields final but exposing a mutable List via the getter.
  • Storing the caller's list without copying.
  • Forgetting to make the class final.
  • Assuming a record with a List component is deeply immutable.
  • Using Collections.unmodifiableList(items) on the caller's list: it is a view, so the caller can still change it.

How to answer in the interview

"I make the class final so it can't be subclassed, make all fields private final, provide no setters, and initialise everything in the constructor. For mutable fields such as lists or dates I make defensive copies on the way in and return copies or unmodifiable views on the way out, for example with List.copyOf, and methods that 'change' something return a new instance. Immutable objects are thread-safe and make good map keys. In modern Java records give most of this for free, but I still add a compact constructor with defensive copies for mutable components."

Likely follow-up questions

  • Is a record with a List component truly immutable? Not by default; the list can be mutated by anyone holding it, so copy it with List.copyOf in a compact constructor, and its elements must be immutable too.
  • Why do final fields matter for thread safety? The JMM guarantees that a properly constructed object's final fields are visible to all threads without synchronisation.
  • What is the cost of immutability? More object allocation for changes, usually cheap with modern GCs; builders help for complex objects.
