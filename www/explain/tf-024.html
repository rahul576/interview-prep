How do you authenticate Terraform in CI to AWS or Azure without static credentials?

Terraform · concept · levels mid, senior, lead

In one line

Use OIDC federation: the CI platform issues a signed token per job, AWS assumes an IAM role or Azure uses workload identity federation, giving short-lived credentials; restrict the trust policy to repo, branch or environment, use separate plan and apply roles, or HCP Terraform dynamic provider credentials.

Detailed explanation

Long-lived secrets in CI, such as AWS access keys or Azure service principal client secrets, are a top cause of cloud breaches: they leak through logs, forks, compromised runners or old variables, and they rarely get rotated. OpenID Connect (OIDC) federation removes them.

GitHub Actions, GitLab CI, Azure DevOps, Bitbucket and others act as identity providers. For each job they mint a short-lived, signed JWT containing claims about the job: repository, branch or ref, environment, workflow, pipeline ID. On AWS, you register the CI issuer as an IAM OIDC identity provider and create a role whose trust policy allows sts:AssumeRoleWithWebIdentity when claims match. The job exchanges its token for temporary credentials valid for about an hour. On Azure, you add a federated identity credential to an app registration or user-assigned managed identity with the issuer and subject; the azurerm provider uses use_oidc = true (or ARM_USE_OIDC). On GCP, the equivalent is Workload Identity Federation.

The security lives in the conditions. The sub claim should be narrow: repo:acme/infra:environment:production rather than repo:acme/*, and always check aud. Use separate roles: a read-only plan role that pull request jobs can assume (still careful, since PRs can run modified code), and a privileged apply role that only the protected main branch or a protected environment with required reviewers can assume. Scope permissions per account and environment.

HCP Terraform dynamic provider credentials do the same for workspaces: HCP Terraform is the OIDC issuer and tokens carry organisation, project, workspace and run phase claims, so plan and apply can map to different roles.

How it works

  1. Create the OIDC trust (IAM OIDC provider or federated credential).
  2. Create plan and apply roles with narrow trust conditions.
  3. CI job requests an ID token (id-token: write in GitHub Actions).
  4. Provider or action exchanges it for temporary cloud credentials.
  5. Terraform runs; credentials expire automatically.

Example

{
  "Effect": "Allow",
  "Principal": { "Federated": "arn:aws:iam::111122223333:oidc-provider/token.actions.githubusercontent.com" },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": {
      "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
      "token.actions.githubusercontent.com:sub": "repo:acme/infra:environment:production"
    }
  }
}
permissions: { id-token: write, contents: read }
steps:
  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::111122223333:role/tf-apply-prod
      aws-region: eu-west-1

Common mistakes

  • Wildcard sub conditions allowing any repo or branch.
  • One admin role for both plan and apply.
  • Letting PRs from forks assume roles.
  • Keeping old static keys "as backup".

How to answer in the interview

"Instead of storing access keys or a client secret in CI, I use OIDC federation. GitHub Actions, GitLab or Azure Pipelines issue a signed token per job; AWS trusts that issuer and lets the job assume a role, and Azure uses a federated credential on a managed identity or app registration. Credentials are short-lived, so nothing permanent can leak. The trust policy is narrow: only a specific repository and the main branch or a protected environment can assume the production role. I use a read-only role for plans on pull requests and a privileged apply role only after approval. HCP Terraform offers the same through dynamic provider credentials."

Likely follow-up questions

  • Which claims in the AWS trust policy? aud = sts.amazonaws.com and a specific sub such as repo plus environment.
  • Is a read-only plan role safe? Mostly, but it can read state and data, so limit scope and avoid forks.
  • How long do credentials last? Typically one hour, configurable per role session.
