How do default methods support backward compatibility?

Java 8+ Features · concept · levels mid

In one line

Adding an abstract method to a published interface breaks every implementation; a default method ships the new method with an implementation, so existing classes still compile and run and simply inherit it. That's how Java 8 added stream(), forEach, removeIf and List.sort to the collections framework.

Detailed explanation

Before Java 8, interfaces were frozen once published. If the JDK had added Stream<E> stream() as an abstract method to Collection, every collection class ever written, in Guava, Apache Commons, Hibernate, Eclipse Collections and countless in-house codebases, would have stopped compiling until it implemented the method, and already-compiled classes would throw AbstractMethodError when it was called. That is unacceptable for a platform that prizes backward compatibility.

Default methods solve this. The new method comes with a body, written in terms of methods the interface already has. Collection.stream() is implemented via spliterator(), which itself got a default based on iterator(). Iterable.forEach loops using iterator(). Collection.removeIf uses the iterator's remove. List.sort copies to an array, sorts and writes back via a ListIterator. Existing implementations inherit these and keep working, both at source level (they still compile) and binary level (old class files still link). Implementations that can do better override them, as ArrayList does for sort, forEach and removeIf.

You can use the same technique for your own APIs, such as a shared library interface used by many teams: add a default method, release, and let implementers override later.

Default methods can still break things occasionally: if an existing implementation already has a method with the same signature but a different contract or return type, or if a class implements two interfaces that now provide conflicting defaults, compilation fails or behaviour changes. They also can't access state, so the default must be expressible through existing abstract methods.

How it works

  1. A library adds a new method to an interface with the default keyword and a body.
  2. Old implementation classes don't declare it, yet still compile.
  3. At runtime, calls resolve to the default body via normal virtual dispatch.
  4. Implementations that override it get their own version.

Example

// Version 1 of a shared library
public interface PaymentGateway {
    Receipt charge(Order order);
}

// Version 2: new capability without breaking existing gateways
public interface PaymentGateway {
    Receipt charge(Order order);

    default List<Receipt> chargeAll(List<Order> orders) {   // works for every old implementation
        return orders.stream().map(this::charge).toList();
    }
    default boolean supportsRefunds() { return false; }
}

// An existing implementation compiles unchanged:
class LegacyGateway implements PaymentGateway {
    public Receipt charge(Order o) { /* ... */ return new Receipt(o.id()); }
}

// A newer one optimises with a batch API:
class ModernGateway implements PaymentGateway {
    public Receipt charge(Order o) { /* ... */ return new Receipt(o.id()); }
    @Override public List<Receipt> chargeAll(List<Order> orders) { return api.batchCharge(orders); }
}

Common mistakes

  • Saying default methods exist to allow multiple inheritance (a side effect, not the goal).
  • Ignoring that new defaults can clash with existing method signatures.
  • Writing defaults that rely on assumptions implementers may violate (e.g. thread safety).
  • Forgetting the binary compatibility aspect.

How to answer in the interview

"If you add an abstract method to a published interface, every implementing class, including third-party ones, stops compiling until it implements it. Default methods solve that: the new method comes with an implementation, so existing classes keep compiling and working and just inherit it, while new ones can override it with something better. That's how Java 8 added stream, forEach, removeIf and spliterator to Collection and Iterable, and sort to List, without breaking existing collection classes. I use the same technique when evolving my own shared APIs."

Likely follow-up questions

  • Can default methods break anything? Yes, a signature clash with an existing method or conflicting defaults from two interfaces.
  • How is Collection.stream implemented by default? Via StreamSupport.stream(spliterator(), false).
  • Why does ArrayList override forEach? For efficiency and fail-fast modification checks over its array.
