What is unit testing, and why is it important?

Testing · concept · levels entry, mid

In one line

A unit test checks one small unit of code, usually a class or method, in isolation with dependencies replaced by mocks or fakes; it is fast and automated, so it runs on every build, catches regressions, enables safe refactoring and documents behaviour.

Detailed explanation

The "unit" is the smallest piece of behaviour worth testing on its own: a pricing rule, a validator, a mapper, a service method. Isolation means the test does not touch databases, networks, file systems, clocks or other services. Those collaborators are replaced with test doubles: Mockito mocks, stubs or simple in-memory fakes. That makes unit tests fast (milliseconds), deterministic and able to run anywhere.

Why they matter:

  • Fast feedback: thousands run in seconds on a laptop and in CI, so a mistake is found minutes after it is made, when it is cheapest to fix.
  • Regression safety: once behaviour is pinned down, later changes that break it fail the build.
  • Refactoring confidence: you can restructure code knowing behaviour is preserved.
  • Documentation: a test named rejectsOrderWhenStockIsInsufficient tells the next developer what the code is supposed to do, including edge cases.
  • Design pressure: code that is hard to unit test usually has hidden dependencies or too many responsibilities.

A good unit test follows Arrange-Act-Assert (Given-When-Then), checks one behaviour, has a descriptive name, covers normal, boundary and error cases, and asserts on observable behaviour rather than private implementation details, so it fails only for a real reason. Unit tests sit at the base of the test pyramid; they cannot catch wiring, SQL or configuration problems, which integration tests cover.

In Java the standard toolset is JUnit 5, Mockito and AssertJ, run by Maven Surefire or Gradle.

How it works

  1. Arrange: create the object under test and its doubles; set up input data.
  2. Act: call the method once.
  3. Assert: check the result, state or important interactions.
  4. Repeat for edge cases with parameterised tests.
  5. Run locally and in CI on every commit.

Example

class ShippingFeeCalculatorTest {

    private final ShippingFeeCalculator calc = new ShippingFeeCalculator();

    @Test
    void freeShippingFromFiftyEuros() {
        // arrange
        var cart = new Cart(new BigDecimal("50.00"));
        // act
        BigDecimal fee = calc.feeFor(cart);
        // assert
        assertThat(fee).isEqualByComparingTo("0");
    }

    @ParameterizedTest
    @CsvSource({"0.01, 4.99", "49.99, 4.99"})
    void standardFeeBelowThreshold(String total, String expected) {
        assertThat(calc.feeFor(new Cart(new BigDecimal(total))))
            .isEqualByComparingTo(expected);
    }

    @Test
    void rejectsNegativeTotals() {
        assertThatThrownBy(() -> calc.feeFor(new Cart(new BigDecimal("-1"))))
            .isInstanceOf(IllegalArgumentException.class);
    }
}

Common mistakes

  • Tests that hit a real database or network and are therefore slow and flaky.
  • Testing private methods or internal call order instead of behaviour.
  • Several unrelated assertions and behaviours in one test.
  • Only testing the happy path, ignoring boundaries and errors.

How to answer in the interview

"A unit test checks one small piece of code, usually a class or a method, in isolation: its dependencies like repositories or HTTP clients are replaced with mocks or fakes. Because they don't touch infrastructure, they run in milliseconds, so thousands run on every build and give feedback almost immediately. They catch regressions, let me refactor safely and document expected behaviour, including edge cases. I write them arrange-act-assert, one behaviour per test with a descriptive name, testing behaviour rather than implementation, using JUnit 5, Mockito and AssertJ."

Likely follow-up questions

  • What makes a unit test brittle? Coupling to implementation details such as call order, private methods or exact log messages.
  • Should unit tests use Spring? Usually not; construct the class with new and pass doubles.
  • How much should be unit tested? Business logic thoroughly; thin glue code is better covered by integration tests.
