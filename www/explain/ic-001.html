What are providers and resources in Terraform?

Infrastructure as Code · concept · levels entry

In one line

A provider is a plugin that knows how to talk to one API (AWS, Azure, Google Cloud, Kubernetes, GitHub) and translate Terraform resources into API calls; a resource block describes one infrastructure object identified by its type and local name, and other blocks reference its attributes as type.name.attribute, which also defines dependency order.

Detailed explanation

Terraform's core knows nothing about clouds. All knowledge of specific platforms lives in providers, separate binaries that Terraform downloads during terraform init from the Terraform Registry (or the OpenTofu registry, or a private mirror). Each provider defines resource types (like aws_s3_bucket, azurerm_resource_group, kubernetes_namespace) and data sources, and implements create, read, update and delete calls for them.

You declare which providers and versions you need in required_providers, with a source address (hashicorp/aws) and a version constraint (~> 5.0). The exact chosen versions are recorded in .terraform.lock.hcl. A provider block configures it: region, subscription, endpoint, and authentication, preferably from the environment (AWS profiles or roles, Azure CLI or managed identity, OIDC in CI) rather than hard-coded keys. You can define several configurations of the same provider with an alias, for example two AWS regions, and choose one per resource with provider = aws.us.

A resource block has the form resource "<TYPE>" "<NAME>" { ... }. The type (prefix = provider name) says what kind of object; the local name is only for referencing within the module. Arguments configure it (bucket name, tags, instance size). After creation, Terraform knows attributes such as id and arn. Referencing aws_s3_bucket.logs.arn in another resource does two things: it passes the value, and it creates an implicit dependency, so Terraform builds its dependency graph and creates the bucket first. depends_on handles the rare hidden dependencies. Meta-arguments like count, for_each, lifecycle and provider work on any resource.

How it works

  1. Declare providers and versions in required_providers.
  2. terraform init downloads them and writes the lock file.
  3. Configure each provider (region, credentials, aliases).
  4. Declare resources; references build the dependency graph.
  5. On plan/apply, Terraform calls the provider to read and change real objects in graph order.

Example

terraform {
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.0" }
  }
}

provider "aws" { region = "eu-west-1" }
provider "aws" {
  alias  = "us"
  region = "us-east-1"
}

resource "aws_s3_bucket" "logs" {
  bucket = "acme-logs-eu"
  tags   = { team = "platform" }
}

resource "aws_s3_bucket" "logs_us" {
  provider = aws.us
  bucket   = "acme-logs-us"
}

resource "aws_cloudtrail" "main" {
  name           = "main"
  s3_bucket_name = aws_s3_bucket.logs.id   # reference = implicit dependency
}

Common mistakes

  • Hard-coding access keys in the provider block.
  • No version constraints, so a new major provider version breaks the code.
  • Changing a resource's local name and accidentally destroying and recreating it (use moved).
  • Adding depends_on everywhere instead of relying on references.

How to answer in the interview

"A provider is a plugin that knows how to talk to a particular API, like aws, azurerm, google, kubernetes or github, and turns Terraform resources into API calls. I declare it in required_providers with a pinned version, terraform init downloads it from the registry, and the provider block sets things like the region and authentication, ideally from roles or OIDC rather than keys. A resource block describes one infrastructure object, for example resource \"aws_s3_bucket\" \"logs\" with arguments like the name and tags. The type plus local name identify it, and other resources reference its attributes as aws_s3_bucket.logs.arn, which also tells Terraform the order in which to create things."

Likely follow-up questions

  • Two AWS regions in one configuration? Two provider blocks, one with an alias, and provider = aws.alias on resources or modules.
  • Explicit vs implicit dependencies? References create implicit ones; depends_on adds explicit ones for hidden relationships.
  • Where are providers stored? Downloaded to .terraform/providers, optionally cached via a plugin cache or mirror.
