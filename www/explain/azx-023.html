How do Azure Backup and Azure Site Recovery differ, and how do you use them together?

Azure · concept · levels mid, senior

In one line

Azure Backup keeps point-in-time copies for restore after deletion, corruption or ransomware; Azure Site Recovery (ASR) continuously replicates VMs to another region or zone for failover; use both, because replication gives a low RTO but faithfully copies corruption, while backups with soft delete and immutability protect the data itself.

Detailed explanation

Azure Backup works with backup policies (schedule plus retention, for example daily for 30 days, weekly for 12 weeks, monthly for 7 years) and stores recovery points in a Recovery Services vault or a Backup vault depending on the workload. Supported sources include Azure VMs, managed disks, Azure Files, SQL Server and SAP HANA in VMs, Azure Blobs, Azure Database for PostgreSQL, and AKS. VM backups take snapshots (kept locally for fast instant restore) and transfer them to the vault, with options for LRS, ZRS or GRS storage and Cross Region Restore. Restores can be whole VMs, disks or individual files.

Against ransomware and malicious admins, vaults provide soft delete (deleted backups recoverable for at least 14 days, and enhanced soft delete that can be made always-on), immutable vaults (once locked, recovery points cannot be deleted before expiry or retention reduced), and multi-user authorization (MUA) using a Resource Guard in another tenant or subscription, so a single compromised admin cannot disable protection.

Site Recovery replicates VM disks continuously to a target region or zone, producing crash-consistent recovery points every few minutes and optional app-consistent points. Recovery plans order failover of multi-tier apps and run scripts or runbooks. You can run a test failover into an isolated VNet without affecting production, then a planned or unplanned failover, commit, re-protect and fail back.

The key insight: if ransomware encrypts the primary, ASR replicates the encrypted disks within minutes. You need backups with history to go back days. Conversely, restoring hundreds of VMs from backup during a regional outage takes far longer than ASR failover.

How it works

  1. Classify workloads by RPO/RTO.
  2. Backup: create vaults, policies and enable protection (enforce with Azure Policy).
  3. Lock down vaults: immutability, enhanced soft delete, MUA.
  4. ASR: enable replication for tier-1 VMs; build recovery plans.
  5. Run test failovers and restore drills on a schedule.
  6. Monitor jobs and alerts with Backup center / Business Continuity Center.

Example

az backup protection enable-for-vm -g rg-erp --vault-name rsv-erp-weu \
  --vm vm-erp-app01 --policy-name daily-30d-monthly-12m
az backup vault update -g rg-erp -n rsv-erp-weu --immutability-state Locked

Common mistakes

  • Treating ASR as a backup.
  • Backups in the same region with GRS disabled and no cross-region restore.
  • Never testing restores or failovers.
  • Leaving vaults deletable by the same admins who run production.

How to answer in the interview

"Azure Backup takes scheduled point-in-time copies of VMs, disks, files, databases, blobs and AKS according to policies, stored in vaults protected by soft delete, immutability and multi-user authorisation, so I can restore after deletion, corruption or ransomware. Site Recovery continuously replicates VMs to another region so I can fail over a whole application with a recovery plan in minutes. I use both: ASR for low RTO during a disaster, backups because replication would happily copy encrypted or corrupted data. And we run test failovers and restore drills regularly."

Likely follow-up questions

  • Why is replication not enough against ransomware? It replicates encrypted data quickly; you need older, immutable restore points.
  • What is a test failover? A failover into an isolated network that doesn't touch production replication.
  • PaaS DR? Use native features: SQL failover groups, GZRS storage, Cosmos DB multi-region.
