What are sequential and parallel streams?

Java 8+ Features · concept · levels entry

In one line

A sequential stream processes elements one after another in the calling thread; a parallel stream (created with parallelStream() or .parallel()) splits the source with a Spliterator and processes chunks concurrently on the common ForkJoinPool, then combines the partial results.

Detailed explanation

By default every stream is sequential. Elements are processed in encounter order (for ordered sources such as lists), in the thread that called the terminal operation. This is predictable, has no threading overhead and is the right default for most code.

A parallel stream uses the same API but a different execution strategy. The source's Spliterator splits the data into chunks, each chunk is processed by a task in ForkJoinPool.commonPool(), and the calling thread joins in as a worker too. Partial results, such as partial sums or partial lists, are merged at the end using the reduction's combiner or the collector's combiner. On a machine with 8 cores, CPU-heavy work on a large ArrayList can run several times faster.

The results are the same as sequential execution only if your operations follow the rules: lambdas must be stateless, non-interfering (do not modify the source) and reductions must be associative. Side effects such as forEach happen in no particular order, and printing from a parallel stream shows interleaved output. Ordered operations like findFirst, limit and forEachOrdered still work but cost extra coordination; unordered() or findAny can be cheaper when order does not matter.

Calling .parallel() or .sequential() sets a flag on the whole pipeline; the last call wins. You cannot make only one stage parallel. Use isParallel() to check.

Parallel is not automatically faster: splitting, scheduling and merging have overhead, so for small collections or cheap operations sequential is usually better. Always measure.

How it works

  1. parallelStream() or .parallel() marks the pipeline as parallel.
  2. At the terminal operation the source is split recursively via trySplit().
  3. Each chunk runs the full pipeline as a fork/join task.
  4. Worker threads of the common pool plus the caller execute the tasks.
  5. Partial results are combined up the task tree into the final result.

Example

List<Integer> numbers = IntStream.rangeClosed(1, 10_000_000).boxed().toList();

long seq = numbers.stream()
    .mapToLong(n -> n * 2L)
    .sum();

long par = numbers.parallelStream()
    .mapToLong(n -> n * 2L)
    .sum();                  // same result: sum is associative

numbers.parallelStream()
    .limit(5)
    .forEach(n -> System.out.println(Thread.currentThread().getName() + " " + n));
// order and thread names vary, e.g. ForkJoinPool.commonPool-worker-3

Common mistakes

  • Assuming .parallel() always speeds things up.
  • Printing or adding to an ArrayList inside a parallel forEach.
  • Thinking .sequential() later in the chain affects only later stages.
  • Using parallel streams for blocking I/O calls.

How to answer in the interview

"By default streams are sequential: elements are processed one by one in the calling thread, in encounter order. A parallel stream, created with parallelStream or parallel, splits the source with a Spliterator, processes the chunks concurrently on the common ForkJoinPool plus the calling thread, and then combines the partial results. The API is the same, and the result is the same if my operations are stateless, non-interfering and associative, but the order of side effects like forEach is not guaranteed. The parallel or sequential flag applies to the whole pipeline and the last call wins. I only use parallel for large, CPU-bound work and I measure first."

Likely follow-up questions

  • How many threads does a parallel stream use by default? The common pool has parallelism of available processors minus one, plus the calling thread.
  • Can you change that? Via the system property java.util.concurrent.ForkJoinPool.common.parallelism, or by running inside a custom ForkJoinPool.
  • Is findFirst slower in parallel? It must respect encounter order; findAny is cheaper.
