What do you need to consider when streaming LLM responses through gateways and backend services?

LLMOps & RAG · concept · levels mid, senior

In one line

Stream tokens with server-sent events or chunked responses, and make the path stream-safe: disable proxy buffering, allow long-lived connections and timeouts, handle errors after a 200 status, apply moderation to partial output, capture token usage at the end, and use non-blocking I/O in relays.

Detailed explanation

Streaming makes a 15-second answer feel fast because the first words appear in under a second. Most LLM APIs use Server-Sent Events (SSE): an HTTP response with Content-Type: text/event-stream carrying data: lines per chunk. Every hop between the model and the browser must cooperate.

Buffering. NGINX, ingress controllers, API gateways, CDNs and some frameworks buffer responses or compress them, so the client receives everything at the end. Disable buffering for streaming routes (proxy_buffering off, X-Accel-Buffering: no), avoid gzip on event streams, and flush after each event.

Timeouts and connections. A stream can last minutes. Load balancer idle timeouts (often 60 s by default), gateway request timeouts and serverless limits must allow that, and the server should send periodic keep-alive comments during long tool calls or reasoning phases. Each open stream holds a connection, so capacity planning counts concurrent streams, not requests per second.

Errors mid-stream. The HTTP status is 200 as soon as streaming starts. Rate limits, model errors or upstream disconnects then arrive as error events or simply a closed connection. Clients must detect incomplete responses (no final [DONE] or stop reason), show a sensible state, and retry carefully without duplicating text already shown, typically by regenerating the whole message.

Safety. Moderation and guardrails must operate on partial outputs; providers filter chunks and may cut a stream. Your own PII or policy filters need a buffer-and-check window.

Metering. Token usage arrives at the end of the stream (with OpenAI you request it via stream_options.include_usage). If the client disconnects, you still want usage recorded, so the backend should finish reading or estimate. Cancellation should propagate upstream to stop generation and save cost.

Backend relays should use non-blocking I/O, such as Spring WebFlux with Flux<ServerSentEvent> or Node streams, so thousands of concurrent streams do not pin thousands of threads.

How it works

  1. Browser opens an SSE or fetch stream to the backend.
  2. Backend calls the LLM with stream: true.
  3. Each chunk is forwarded and flushed immediately.
  4. Errors become error events; client handles them.
  5. Final event carries usage; backend logs cost and closes.

Example

@GetMapping(value = "/chat/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
Flux<ServerSentEvent<String>> stream(@RequestParam String q) {
  return llmClient.streamChat(q)                         // Flux<String> of deltas
      .map(d -> ServerSentEvent.builder(d).event("delta").build())
      .concatWith(Flux.just(ServerSentEvent.builder("").event("done").build()))
      .onErrorResume(e -> Flux.just(ServerSentEvent.builder(e.getMessage()).event("error").build()));
}
location /chat/stream { proxy_pass http://backend; proxy_buffering off; proxy_read_timeout 600s; }

Common mistakes

  • Gateways buffering the whole response, killing the benefit.
  • 60-second idle timeouts cutting long answers.
  • Treating HTTP 200 as success without checking the final event.
  • Not cancelling upstream generation when the user leaves.

How to answer in the interview

"Streaming improves perceived latency, usually via server-sent events. The infrastructure must not break it: I disable buffering on proxies, gateways and ingress for those routes, and raise idle and request timeouts so connections can live for minutes, with keep-alives. Error handling changes because the stream starts with 200, so clients handle error events and incomplete responses and retry without duplicating text. Moderation has to work on partial output, token usage arrives at the end so metering must handle interrupted streams, and relays should use non-blocking I/O such as WebFlux."

Likely follow-up questions

  • SSE vs WebSockets? SSE is simpler, one-way over HTTP; WebSockets suit bidirectional sessions.
  • How to cancel generation? Abort the client request and propagate cancellation to the upstream call.
  • Streaming with tool calls? Stream argument deltas, then execute tools and resume streaming.
