What are hybrid search and reranking, and why do they improve RAG quality?

LLMOps & RAG · concept · levels mid, senior

In one line

Hybrid search combines BM25 keyword search (exact terms, codes, names) with vector search (meaning, paraphrases), merging results with reciprocal rank fusion; reranking then rescores a larger candidate set with a cross-encoder that reads query and passage together, keeping the best few, for big quality gains at some latency and cost.

Detailed explanation

Why two retrievers. Dense vector search shines when wording differs: "how do I get my money back" finds "refund policy". It is weak on exact tokens: error codes like ORA-12154, SKUs, version numbers, acronyms, people's names and rare jargon, which embeddings blur. BM25 keyword search is the opposite: excellent for exact matches and rare terms, blind to synonyms. Real queries mix both kinds, so using both improves recall substantially.

Fusion. Scores from BM25 and cosine similarity are on different scales, so reciprocal rank fusion (RRF) combines ranks instead: each document scores the sum of 1 / (k + rank) across retrievers (k typically 60). Documents ranked well by either rise; documents found by both rise most. Alternatives are weighted score combination after normalisation. Elasticsearch, OpenSearch, Azure AI Search, Weaviate, Qdrant, Pinecone, Milvus and others support hybrid queries natively; with pgvector you can combine it with PostgreSQL full-text search.

Reranking. Embedding models are bi-encoders: query and document are embedded separately, which is fast but loses fine-grained interaction. A cross-encoder reranker takes the query and a passage together and outputs a relevance score, judging subtle relevance far more accurately. It is too slow to run over the whole corpus, so it is a second stage: retrieve 50 to 100 hybrid candidates, rerank them, keep the top 3 to 10 for the prompt. Options include Cohere Rerank, Voyage rerankers, Jina, open models like BGE reranker and other cross-encoders.

Trade-offs. Reranking adds tens to a few hundred milliseconds and per-query cost; candidate count is the main lever. The gains, fewer irrelevant chunks in the prompt and better answers with fewer tokens, usually justify it. Measure with recall at k and answer quality.

How it works

  1. Run BM25 and vector search in parallel (top 50 each), with the same filters.
  2. Fuse with RRF into one candidate list.
  3. Cross-encoder scores each (query, passage) pair.
  4. Sort by reranker score; keep top k above a threshold.
  5. Send selected chunks to the LLM.

Example

def rrf(result_lists, k=60):
    scores = {}
    for results in result_lists:
        for rank, doc_id in enumerate(results, start=1):
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)

cands = rrf([bm25.search(q, 50), vectors.search(embed(q), 50)])[:60]
scored = reranker.score(q, [docs[c].text for c in cands])
top = [c for c, s in sorted(zip(cands, scored), key=lambda x: -x[1])[:6]]

Common mistakes

  • Pure vector search for a corpus full of identifiers.
  • Adding raw BM25 and cosine scores without normalisation.
  • Reranking only the top 5, which cannot recover missed documents.
  • Ignoring reranker latency in the overall budget.

How to answer in the interview

"Vector search finds passages with similar meaning even when words differ, but it is weak with exact terms like product codes, error messages and names. BM25 keyword search is the opposite. Hybrid search runs both and merges them, usually with reciprocal rank fusion, so documents ranked well by either rise; most search engines and vector databases support it natively. Reranking adds a second stage: retrieve maybe 50 candidates, score each with a cross-encoder that reads the query and passage together, which is much more accurate than comparing separate embeddings, and keep the top few. Both give big quality gains for some extra latency and cost."

Likely follow-up questions

  • How many to rerank? Enough to reach high recall, often 30 to 100; tune on a test set against latency.
  • Why RRF? Rank-based, no score calibration needed, robust.
  • Reranker threshold? Drop low-scoring chunks to avoid distracting context.
