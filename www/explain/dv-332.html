A deployment through the CI/CD pipeline failed. How do you find the cause?

Troubleshooting · scenario · levels entry, mid

In one line

Read the failing step's log from the first real error, classify the failure (build, test, scan or deploy), compare with the last successful run (code, dependencies, runner image, secrets), reproduce or re-run once to detect flakiness, and for deploy failures check permissions, quotas and target events.

Detailed explanation

Pipeline failures often produce long logs where the last lines are just consequences, like "process exited with code 1". The useful information is the first error, so I search upward for error, FAILED or the first stack trace.

Classifying the failure narrows the search:

  • Build: compilation errors, missing dependencies, a dependency registry being down, or a changed base image.
  • Tests: a real regression or a flaky test.
  • Security or quality gates: a new CVE found by the image scanner, coverage or lint thresholds.
  • Deployment: authentication to the cloud, insufficient permissions, quota limits, the target rejecting the change, or a failed health check after rollout.

Compare with the last successful run. What changed: the commit diff, dependency versions (an unpinned version can change without any commit), the base image, the pipeline definition, the runner image or agent, and secrets or credentials — an expired token or service principal secret is a very common cause.

Reproduce. Run the same command locally or in the same container image. If a re-run passes without changes, the test is flaky: record it, quarantine it if needed, and fix it rather than relying on retries, which hide real problems.

Deploy failures need the target's view: Kubernetes events and kubectl rollout status, cloud activity logs for denied operations, or Terraform error output.

How it works

  1. Open the failing step and find the first real error.
  2. Classify the failure type.
  3. Diff against the last green run: code, dependencies, images, pipeline, secrets.
  4. Reproduce locally or re-run once to check for flakiness.
  5. For deploys, inspect target events, permissions and quotas.
  6. Fix, and add a guard (pinning, alerting on expiry) to prevent recurrence.

Example

Step: deploy
ERROR: AADSTS7000222: The provided client secret keys for app '...' are expired.
git diff last-green..HEAD -- package.json pipeline.yml
docker run --rm -v "$PWD":/src -w /src node:22 npm ci && npm test   # reproduce build locally
kubectl rollout status deploy/api -n prod
kubectl get events -n prod --sort-by=.lastTimestamp | tail

Here the fix was moving the pipeline to OIDC federation so there is no secret to expire.

Common mistakes

  • Reading only the last line of the log.
  • Re-running until green and ignoring flaky tests.
  • Not checking whether credentials or certificates expired.
  • Unpinned dependencies and runner images that change silently.

How to answer in the interview

"I open the failing step and read from the first real error, not the last line, since later errors are often consequences. Then I classify it: build error, failing tests, a security gate, or the deployment itself. I compare with the last successful run — code changes, dependency versions, base and runner images, pipeline definition and secrets — because an expired credential or an unpinned dependency is a common cause. I try to reproduce locally or re-run once to detect flaky tests, which need fixing rather than retries. For deploy failures I check permissions, quotas and the target, like Kubernetes events and rollout status."

Likely follow-up questions

  • How do you deal with flaky tests? Track them, quarantine with an owner and deadline, and fix the root cause such as timing or shared state.
  • How do you make builds reproducible? Lock files, pinned image digests and versioned runner images.
  • How do you avoid expired-secret failures? OIDC federation, or alerts before credential expiry.
