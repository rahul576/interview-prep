Tell me how you would run a post-incident review after a model caused wrong decisions in production.

MLOps · scenario · levels senior, lead

In one line

Run it as a blameless post-incident review: build a timeline, quantify impact, find multiple root causes across data, model, pipeline and process, assign owned action items, and share lessons across ML teams.

Detailed explanation

Model incidents are often quieter than outages: nothing crashes, but decisions are wrong for days, such as a credit model rejecting good applicants or a fraud model letting fraud through. That makes the review even more important, because detection was probably slow.

Blameless means we assume people acted reasonably with the information and tools they had, and we ask how the system allowed the failure. Without that, people hide details and the real causes stay hidden.

The timeline covers when the faulty behaviour began (often earlier than detection), when and how it was detected (monitoring, a customer, a business report), who was involved, and each mitigation step such as rollback or switching to a rules fallback. Gaps between start and detection are a key finding.

Impact is quantified: number of predictions and decisions affected, which customers or segments, financial loss, regulatory exposure and whether affected customers must be contacted or decisions re-run.

Root causes and contributing factors are usually several: an upstream data change without a data contract, missing input validation, an evaluation set lacking the affected segment, no alert on prediction distribution, an unclear rollback path. Each becomes an action item with an owner, deadline and tracking.

How it works

  1. Stabilise first: roll back or fall back, then schedule the review within a few days.
  2. Collect data: logs, model versions, dashboards, chat history.
  3. Write the timeline and measure impact together with the business.
  4. Run a facilitated session using "5 whys" or a contributing-factors approach.
  5. Agree action items: tests, monitors, gates, runbooks; track them to closure.
  6. Publish the write-up and present it to other ML teams.

Example

STAR-style summary of a real review I might describe:

  • Situation: A pricing model under-priced a product category for four days after a supplier feed switched currency from EUR to cents.
  • Task: I facilitated the review.
  • Action: Timeline showed detection came from finance, not monitoring. Root causes: no unit check on the feed, no data contract, no alert on price-output shifts per category, evaluation set lacked that category.
  • Result: Actions: schema and range checks on the feed, a data contract with the supplier team, per-category output drift alerts, a one-click rollback runbook. A similar issue two months later was caught in 20 minutes.

Common mistakes

  • Stopping at "the data was wrong" without asking why nothing caught it.
  • Naming individuals as the cause.
  • Action items with no owners or dates.
  • Not measuring business impact, so priorities are unclear.

How to answer in the interview

"First I'd make sure we've mitigated, then run a blameless review. We'd build a timeline from when the problem started, not just when we noticed, and how it was detected. We'd quantify impact with the business: how many decisions, which customers, what cost or regulatory exposure. Then we'd look for several contributing causes across data, model, pipeline and process, like missing validation or a missing evaluation slice. Each becomes an owned action item with a deadline, and I'd share the write-up with other ML teams because the same gaps usually exist elsewhere."

Likely follow-up questions

  • Which ML-specific questions go in the template? Which model and data versions were live, did inputs drift, which segments were affected, did evaluation cover them, how fast could we roll back?
  • Do affected decisions need re-running? Often yes, especially in regulated domains; lineage and prediction logs make that possible.
  • How do you ensure actions get done? Track them in the backlog and review status at the next ops review.
