What is an AWS load balancer and an Auto Scaling group?

Cloud (AWS) · concept · levels entry, mid

In one line

Elastic Load Balancing spreads traffic across healthy targets: the ALB works at layer 7 (HTTP routing, TLS), the NLB at layer 4 (TCP/UDP, static IPs, extreme throughput); an Auto Scaling group keeps a desired number of instances from a launch template across AZs, replaces unhealthy ones and scales with policies like target tracking.

Detailed explanation

An Application Load Balancer understands HTTP and HTTPS. It terminates TLS (certificates from ACM), routes by host, path, header or query (for example /api/* to one target group, admin.example.com to another), supports WebSockets, HTTP/2 and gRPC, and integrates with WAF and Cognito/OIDC authentication. A Network Load Balancer forwards TCP, UDP and TLS at layer 4 with very low latency, millions of requests per second, static or Elastic IPs per AZ and source IP preservation, which suits non-HTTP protocols or clients that need fixed IPs. (A Gateway Load Balancer exists for inline security appliances.)

Load balancers forward to target groups: EC2 instances, IPs (containers) or Lambda functions. Each target group has a health check (for example GET /health expecting 200); only healthy targets receive traffic, and deregistration delay lets in-flight requests finish during scale-in or deployments.

An Auto Scaling group (ASG) uses a launch template (AMI, instance type, security groups, IAM profile, user data) and keeps desired capacity between min and max, spread across the AZs of its subnets. If an instance fails EC2 or ELB health checks, the ASG terminates and replaces it. Scaling policies adjust desired capacity: target tracking ("keep average CPU at 60%" or "1,000 requests per target") is the simplest and most common; step scaling, scheduled and predictive scaling cover other needs.

How it works

  1. Client → DNS name of the ALB → listener on 443.
  2. Listener rules pick a target group.
  3. ALB sends requests to healthy targets in any AZ.
  4. CloudWatch metric crosses the target → ASG changes desired capacity.
  5. New instances launch from the template, pass health checks after the grace period and join the target group.

Example

resource "aws_autoscaling_group" "web" {
  min_size                  = 2
  max_size                  = 12
  vpc_zone_identifier       = var.private_subnet_ids
  target_group_arns         = [aws_lb_target_group.web.arn]
  health_check_type         = "ELB"
  health_check_grace_period = 120
  launch_template {
    id      = aws_launch_template.web.id
    version = "$Latest"
  }
}

resource "aws_autoscaling_policy" "cpu60" {
  name                   = "cpu-60"
  autoscaling_group_name = aws_autoscaling_group.web.name
  policy_type            = "TargetTrackingScaling"
  target_tracking_configuration {
    predefined_metric_specification { predefined_metric_type = "ASGAverageCPUUtilization" }
    target_value = 60
  }
}

Common mistakes

  • A health check grace period shorter than application start-up, causing a replacement loop.
  • Health checks that call the database, so a DB blip marks every instance unhealthy.
  • Min size of 1 or subnets in only one AZ.
  • Using an NLB when you need path-based routing, or an ALB when clients need static IPs.

How to answer in the interview

"Elastic Load Balancing spreads traffic over healthy targets. The ALB is layer 7: it terminates TLS and routes by host or path, which is ideal for web apps and microservices. The NLB is layer 4 for TCP and UDP, with very high throughput and static IPs. Both send traffic to target groups and only to targets passing health checks. An Auto Scaling group keeps a desired number of instances from a launch template, spread across AZs, replaces unhealthy ones and scales with policies, usually target tracking on CPU or requests per target. I set health check grace periods to match startup time."

Likely follow-up questions

  • Why are instances replaced right after launch? Health checks fail before the app is ready; fix grace period, health path or startup.
  • What is connection draining? Deregistration delay so in-flight requests finish.
  • Scale on CPU or requests? Requests per target or latency often reflect user load better for web tiers.
