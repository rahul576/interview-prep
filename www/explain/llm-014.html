What does an LLM gateway do, and how does model routing work?

LLMOps & RAG · concept · levels mid, senior

In one line

An LLM gateway exposes one consistent (often OpenAI-compatible) API in front of many providers and deployments, handling auth, per-team quotas and budgets, retries and fallbacks, logging and cost tracking, and guardrails, and routes each request to a model by task, complexity, cost or latency; examples are LiteLLM, Azure API Management, Kong, Portkey and cloud gateways.

Detailed explanation

Without a gateway, each application embeds provider SDKs and keys, implements its own retries, and nobody can answer "how much did team X spend last month?". A gateway centralises these cross-cutting concerns.

Access control. Apps authenticate with internal identities or virtual keys; real provider keys live only in the gateway's secret store. The gateway enforces rate limits in tokens per minute, quotas and budgets per team or app, and model allow-lists.

Reliability. It load-balances across deployments (several Azure OpenAI regions, Bedrock regions, self-hosted vLLM replicas), retries transient failures with backoff, and falls back on 429 or 5xx to another region, deployment or provider.

Observability and cost. It records model, tokens in and out, cached tokens, latency, errors and cost per request, tagged with team and feature, and exports traces (OpenTelemetry). Prompt and response logging is configurable per data classification.

Guardrails. PII redaction, prompt-injection and content filters, and response caching can run centrally.

Model routing chooses which model serves a request:

  • Explicit: the app requests a logical alias like fast-small or reasoning, mapped centrally to concrete models so upgrades need no app change.
  • Rule-based: by task type, tenant, data sensitivity (sensitive data to self-hosted only) or prompt length.
  • Learned/complexity-based: a small classifier or heuristic estimates difficulty and sends easy queries to a cheap model and hard ones to a frontier model, sometimes with cascading (try cheap first, escalate if confidence or validation fails).
  • Cost/latency policies: cheapest model meeting a latency target.

Products: LiteLLM (open source proxy), Portkey, Kong AI Gateway, Azure API Management AI gateway policies, Envoy AI Gateway.

How it works

  1. App calls POST /v1/chat/completions with a virtual key and model alias.
  2. Gateway authenticates, checks quota and budget.
  3. Router selects a concrete model and deployment.
  4. Call is made with retries and fallbacks.
  5. Usage, cost and latency are logged and attributed.

Example

# LiteLLM proxy config (simplified)
model_list:
  - model_name: chat-default
    litellm_params: { model: azure/gpt-4o-eu, api_base: os.environ/AZ_EU_BASE, api_key: os.environ/AZ_EU_KEY }
  - model_name: chat-default
    litellm_params: { model: bedrock/anthropic.claude-sonnet, aws_region_name: eu-central-1 }
  - model_name: fast-small
    litellm_params: { model: openai/llama-8b, api_base: http://vllm.internal/v1 }
router_settings: { routing_strategy: latency-based-routing, num_retries: 2 }
litellm_settings: { fallbacks: [ { chat-default: [ fast-small ] } ] }

Model identifiers are illustrative; use the exact ones your providers expose.

Common mistakes

  • Gateway as a single point of failure without redundancy.
  • Logging full prompts with sensitive data by default.
  • Falling back to a model with different behaviour without evaluating it.
  • Counting requests instead of tokens for limits.

How to answer in the interview

"An LLM gateway sits between apps and model providers and exposes one consistent API. Apps authenticate with internal keys, and the gateway enforces per-team token quotas, budgets and rate limits. It retries and falls back across regions or providers on 429s and 5xx, load-balances deployments, and centralises logging of usage, cost and latency, plus guardrails like PII redaction. Routing sends each request to a suitable model, by alias, task, data sensitivity or estimated complexity, so easy requests go to a cheap model and hard ones to a frontier model. LiteLLM, Portkey, Kong and Azure API Management are examples."

Likely follow-up questions

  • Risks of auto-routing to cheaper models? Silent quality drops; need evals, monitoring and escalation.
  • Where to cache responses? Gateway semantic or exact caches, carefully, for idempotent queries.
  • Gateway latency overhead? A few milliseconds, negligible against generation time.
