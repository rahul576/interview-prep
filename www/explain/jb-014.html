What happens when a variable, method, or class is declared final?

Core Java & OOP · concept · levels mid, senior

In one line

A final variable can be assigned only once (but a final reference's object can still be mutated), a final method cannot be overridden, and a final class cannot be subclassed; final fields also get safe-publication guarantees.

Detailed explanation

Final variables. A final local, parameter or field must be assigned exactly once. Final instance fields must be assigned by the end of every constructor (a blank final), and static final fields by the end of class initialisation. The compiler enforces this with definite-assignment rules. For primitives and immutable types this makes the value constant. For references, it only pins the reference: final List<String> names = new ArrayList<>(); names.add("x"); is fine, names = ... is not. To get immutability you also need immutable objects (List.of, List.copyOf, records with immutable components). static final primitives and Strings initialised with constant expressions become compile-time constants that are inlined into calling classes, so changing them requires recompiling dependants.

Effectively final. Lambdas, anonymous and local classes can only capture local variables that are final or effectively final (never reassigned). They capture a copy of the value, so allowing reassignment would make the copy and the variable diverge and create data races.

Final methods cannot be overridden. Use them to lock down behaviour such as a template method's skeleton or security checks. Private and static methods are implicitly not overridable anyway.

Final classes cannot be extended. String, the wrapper classes, LocalDate and all records are final. This protects immutability and security: nobody can create a malicious String subclass that changes after validation. Java 17 sealed classes offer a middle ground: extension only by listed subclasses.

Memory model. The JMM guarantees that once a constructor finishes, other threads that see the object reference also see the correct values of its final fields, without synchronisation, provided this didn't escape during construction. This is why immutable objects with final fields are inherently thread-safe.

How it works

  1. The compiler checks every final variable is assigned exactly once.
  2. Overriding a final method or extending a final class is a compile error.
  3. Constant expressions are folded and inlined.
  4. The JIT inserts a memory barrier at constructor end for final fields.

Example

public final class Customer {                       // cannot be extended
    private final String id;                        // blank final, set in constructor
    private final List<String> tags;

    public Customer(String id, List<String> tags) {
        this.id = id;
        this.tags = List.copyOf(tags);              // final + immutable copy
    }
}

final List<String> list = new ArrayList<>();
list.add("ok");                                     // allowed: mutating object
// list = new ArrayList<>();                        // compile error

int count = 0;
// Runnable r = () -> count++;                      // compile error: not effectively final

Common mistakes

  • Equating final with immutable.
  • Changing a public static final constant without recompiling dependent modules.
  • Leaking this from a constructor, losing the final-field guarantee.
  • Making classes final when a framework needs to proxy them (e.g. Spring CGLIB, Hibernate lazy proxies).

How to answer in the interview

"A final variable can be assigned only once, at declaration or for fields in the constructor. For references that only fixes the reference: a final list can still be modified, so final isn't the same as immutable. A final method can't be overridden, which protects critical behaviour, and a final class can't be extended, which is why String, the wrappers and records are final. Final fields also get safe-publication guarantees under the Java Memory Model, which is what makes immutable objects thread-safe, and lambdas can only capture final or effectively final locals."

Likely follow-up questions

  • Why are lambdas restricted to effectively final local variables? They capture a copy; allowing changes would cause confusing divergence and races.
  • Can a final field be changed via reflection? Instance finals sometimes yes, but it's unreliable; static finals and record fields no.
  • What is a sealed class? A class that restricts which classes may extend it.
