A failed apply left a resource marked as tainted. What does that mean and what are your options?

Terraform · scenario · levels mid, senior

In one line

Tainted means a resource was created but a later step of its creation failed, so Terraform plans to replace it; inspect the real resource first, use terraform untaint if it is healthy, and use terraform apply -replace=ADDRESS when you deliberately want a rebuild.

Detailed explanation

When the create API call succeeds but something afterwards fails, such as a provisioner, a provider wait for "ready" status that times out, or a post-create configuration step, Terraform records the object in state but marks it tainted. It cannot be sure the object is correct, so the safe default on the next plan is replacement: destroy and create again, shown as -/+ with "is tainted, so must be replaced".

That default is often right, but not always. Replacing a freshly created web server is harmless; replacing a database that took 40 minutes to provision, or one that already received data, is not. So before accepting the plan, check the real resource: portal or CLI status, logs, whether the provisioner or timeout was transient. If it is healthy, terraform untaint <address> removes the mark and Terraform keeps the object; the next plan should then show only remaining normal differences.

Historically you could also run terraform taint to force replacement. That command is deprecated (since 0.15.2) because it changes state immediately, outside of a plan, so a teammate's apply could replace the resource without anyone reviewing it. The modern approach is terraform plan/apply -replace=address, which includes the replacement in a normal plan for review and does not modify state until apply. In HCP Terraform you can trigger the same through a run with replace addresses.

How it works

  1. Create succeeds, a post-create step fails; Terraform saves the object as tainted.
  2. Next plan proposes replacement of the tainted resource.
  3. Inspect the real object and the original error.
  4. Healthy: terraform untaint ADDRESS, then re-plan.
  5. Broken: let Terraform replace it, or fix the cause first.
  6. Future forced rebuilds: use -replace in the plan.

Example

terraform plan
#  azurerm_linux_virtual_machine.app is tainted, so must be replaced
# -/+ resource "azurerm_linux_virtual_machine" "app" { ... }

az vm get-instance-view -g rg-app -n vm-app-01 --query "instanceView.statuses[].code"

# Healthy: keep it
terraform untaint azurerm_linux_virtual_machine.app

# Deliberate rebuild, reviewed in the plan
terraform apply -replace="azurerm_linux_virtual_machine.app"

Common mistakes

  • Accepting replacement of a stateful resource without checking it.
  • Using terraform taint in shared environments instead of -replace.
  • Untainting a resource that is actually half-configured.
  • Not fixing the root cause, such as a too-short timeout or a fragile provisioner.

How to answer in the interview

"A resource is tainted when creation started but a later step failed, like a provisioner or a timeout, so Terraform isn't sure it's good and plans to replace it. Before accepting that, I check the real resource. If it's healthy and the failure was transient, I run terraform untaint so we don't rebuild something expensive like a database. If it's broken, I let Terraform replace it. And when I want to force a rebuild deliberately, I use apply with -replace, because unlike the deprecated taint command it shows the replacement in a reviewed plan."

Likely follow-up questions

  • Why is -replace safer than taint? It does not change state until a reviewed apply; taint changes state immediately for everyone.
  • Can you replace a module instance? Yes, with the full address, such as module.app.azurerm_linux_virtual_machine.this[0].
  • How do you avoid taints from provisioners? Move configuration into images or cloud-init.
