How do you configure different database connections for development and production?

Spring Boot · scenario · levels mid, senior

In one line

Use Spring profiles: shared settings in application.yml, environment-specific datasource settings in application-dev.yml and application-prod.yml, activate with SPRING_PROFILES_ACTIVE, inject credentials from environment variables or a secret manager via placeholders, tune the Hikari pool per environment, run Flyway/Liquibase everywhere, and use Docker Compose or Testcontainers locally.

Detailed explanation

The goal is one build artefact that runs unchanged in every environment, with only configuration differing (a twelve-factor principle).

Profiles: application.yml contains what is common: JPA settings, Flyway location, open-in-view: false. application-dev.yml points spring.datasource.url to a local PostgreSQL with a small pool and verbose SQL logging. application-prod.yml points to the production host (or better, a placeholder filled by the platform), with a larger, tuned HikariCP pool, connection and validation timeouts, and no SQL logging. The active profile is selected at deploy time with spring.profiles.active, usually the SPRING_PROFILES_ACTIVE environment variable in the Kubernetes Deployment or container definition, never hard-coded in the jar.

Credentials: production usernames and passwords are never committed. Use placeholders like ${DB_PASSWORD}, filled from environment variables injected from Kubernetes Secrets, Vault (Spring Cloud Vault, possibly with dynamic credentials), Azure Key Vault or AWS Secrets Manager. Even better, use cloud IAM authentication so no static password exists.

Local development: Spring Boot 3.1+ can start a database from compose.yaml automatically with spring-boot-docker-compose, or use Testcontainers with @ServiceConnection for tests and TestApplication for local runs, so devs need no shared dev database. Using the same database engine as production avoids surprises from H2 differences.

Schema: Flyway or Liquibase apply the same versioned migrations in each environment; ddl-auto stays validate or none outside throwaway setups.

Safety: avoid defaults that point to production; make prod settings require explicit environment variables so startup fails if missing, and use separate credentials and network access per environment.

How it works

  1. Build one jar or image.
  2. Deploy with SPRING_PROFILES_ACTIVE=prod and secret-backed env vars.
  3. Boot loads application.yml, then the profile file, then env vars.
  4. HikariCP connects using the resolved URL and credentials.
  5. Flyway migrates the schema before the app accepts traffic.

Example

# application.yml
spring:
  jpa:
    open-in-view: false
    hibernate.ddl-auto: validate
  flyway:
    locations: classpath:db/migration
---
# application-dev.yml
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/shop
    username: shop
    password: shop
    hikari.maximum-pool-size: 5
logging.level.org.hibernate.SQL: debug
---
# application-prod.yml
spring:
  datasource:
    url: ${DB_URL}
    username: ${DB_USERNAME}
    password: ${DB_PASSWORD}
    hikari:
      maximum-pool-size: 30
      connection-timeout: 3000
      max-lifetime: 1700000
# Kubernetes Deployment excerpt
env:
  - name: SPRING_PROFILES_ACTIVE
    value: prod
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef: { name: shop-db, key: password }

Common mistakes

  • Production passwords in application-prod.yml in Git.
  • A default profile that silently connects to production.
  • Using H2 locally while production is PostgreSQL, hiding SQL differences.
  • ddl-auto: update in production.
  • Building a separate artefact per environment.

How to answer in the interview

"I use Spring profiles. Common settings stay in application.yml, application-dev.yml points the datasource at a local PostgreSQL started with Docker Compose or Testcontainers, and application-prod.yml points at the production database with a larger Hikari pool and stricter timeouts. The active profile is chosen at deploy time with the SPRING_PROFILES_ACTIVE environment variable in Kubernetes, so the same image runs everywhere. Production credentials are never committed: they come from Kubernetes secrets, Vault or a cloud key vault via placeholders like DB_PASSWORD. Schema changes are applied by Flyway or Liquibase in every environment."

Likely follow-up questions

  • How do you avoid accidentally running the dev profile in production? No prod-capable defaults, required env vars that fail fast, network separation, and checking the active profile at startup.
  • How to use two databases in one app? Define two DataSource beans with @ConfigurationProperties prefixes and mark one @Primary.
  • How do you test against a real database? Testcontainers with @ServiceConnection.
