What is a reverse proxy, and how would you configure NGINX in front of an application?

Networking · concept · levels mid, senior

In one line

A reverse proxy sits in front of backends, accepting client requests and forwarding them; with NGINX you define an upstream for load balancing, a server block that terminates TLS, proxy_pass to the upstream, set forwarding headers, and tune timeouts, body limits, compression, caching and rate limiting.

Detailed explanation

Clients only see the proxy; backends stay private. Benefits: TLS termination in one place, load balancing and health handling, routing by host or path, caching and compression, rate limiting and request size limits, security headers, and a single place for access logs.

Key NGINX pieces:

  • upstream app { ... } lists backend servers, with algorithms (least_conn, ip_hash), passive health (max_fails, fail_timeout) and keepalive connection pooling to backends.
  • A server block on port 80 that redirects to HTTPS, and on 443 with ssl_certificate, ssl_certificate_key and modern ssl_protocols TLSv1.2 TLSv1.3.
  • location / with proxy_pass http://app;.
  • Headers: by default NGINX sends the upstream name as Host and the proxy's IP as the source, so set Host $host, X-Real-IP $remote_addr, X-Forwarded-For $proxy_add_x_forwarded_for and X-Forwarded-Proto $scheme. The app must trust these only from the proxy.
  • Timeouts: proxy_connect_timeout, proxy_read_timeout (raise for slow endpoints, otherwise 504), proxy_send_timeout.
  • Body size: client_max_body_size (default 1 MB, so uploads fail with 413).
  • WebSockets: proxy_http_version 1.1 plus Upgrade and Connection headers.
  • Compression and caching: gzip on for text types; proxy_cache for cacheable responses; long cache headers for static assets.
  • Rate limiting: limit_req_zone and limit_req per client IP.

Validate with nginx -t and reload gracefully with nginx -s reload (or systemctl reload nginx) so existing connections aren't dropped.

How it works

  1. Client connects to NGINX on 443; TLS is terminated.
  2. NGINX matches server_name and location.
  3. It applies limits, then forwards to an upstream server with added headers.
  4. The response is optionally compressed or cached and returned.
  5. Failed upstreams are temporarily skipped.

Example

limit_req_zone $binary_remote_addr zone=api:10m rate=20r/s;
upstream app { least_conn; server 10.0.1.10:8080 max_fails=3 fail_timeout=10s; server 10.0.1.11:8080; keepalive 32; }
server { listen 80; server_name app.example.com; return 301 https://$host$request_uri; }
server {
    listen 443 ssl; http2 on; server_name app.example.com;
    ssl_certificate /etc/ssl/app/fullchain.pem; ssl_certificate_key /etc/ssl/app/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    client_max_body_size 20m; gzip on; gzip_types text/css application/json application/javascript;
    location / {
        limit_req zone=api burst=40 nodelay;
        proxy_pass http://app; proxy_http_version 1.1; proxy_set_header Connection "";
        proxy_set_header Host $host; proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 60s;
    }
}

Common mistakes

  • Missing forwarding headers, so the app logs only the proxy IP and builds http:// redirect URLs.
  • Default client_max_body_size, breaking uploads.
  • Restarting instead of reloading NGINX.
  • Trusting X-Forwarded-For from any client.

How to answer in the interview

"A reverse proxy accepts client requests in front of the backends and forwards them, hiding the servers. In NGINX I define an upstream block with the app instances, and a server block on 443 that terminates TLS and does proxy_pass to the upstream, with a port-80 block redirecting to HTTPS. I set Host, X-Forwarded-For and X-Forwarded-Proto so the app knows the real client and scheme. I tune timeouts and body size, enable gzip, cache static content and add rate limiting. I test with nginx -t and reload gracefully."

Likely follow-up questions

  • Why does the app see every request from the proxy IP? It's the TCP peer; the app must read X-Forwarded-For or X-Real-IP from trusted proxies.
  • What causes a 502 or 504 from NGINX? 502: upstream refused or returned an invalid response; 504: upstream too slow for proxy_read_timeout.
  • How do you proxy WebSockets? HTTP/1.1 with Upgrade and Connection headers.
