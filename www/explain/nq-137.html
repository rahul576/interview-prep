How do these relationships affect dependency management?

Core Java & OOP · concept · levels mid, senior

In one line

Stronger relationships mean tighter coupling: keep composition parts internal, inject associated and aggregated collaborators as interfaces, prefer unidirectional links, avoid cycles, and remember inheritance is the tightest dependency of all.

Detailed explanation

Every relationship is a dependency: if A references B, changes to B can force changes to A, and A can't be tested or deployed without B. The type of relationship tells you how to manage that dependency.

Composition parts are implementation details of their owner. They are usually small value objects or internal entities (an OrderLine inside Order). Create them inside the owner, keep them private or package-private, and don't expose them in the public API. Nobody else depends on them, so you can refactor them freely.

Associations and aggregations point to collaborators with their own lifecycle: repositories, gateways, other services, shared entities. These should be passed in, ideally through constructor injection, and typed as interfaces. That is the dependency inversion principle: high-level policy depends on abstractions, and details implement them. Spring wires this for you, and tests substitute fakes or mocks. Avoid new-ing collaborators or using static lookups.

Direction and cycles. Bidirectional associations double the coupling: both classes must change together and keep each other consistent. At the code level they cause infinite recursion in JSON serialisation, toString, equals. At the service level, A -> B -> A causes Spring circular-reference failures (disallowed by default since Spring Boot 2.6) and indicates muddled responsibilities. At the module level, cycles prevent independent builds and deployment. Prefer one direction, and break cycles by extracting a third component, introducing an interface owned by the lower layer, or communicating through domain events.

Inheritance is the strongest coupling: the subclass depends on the parent's internals, and changes ripple downwards. Another reason to favour composition.

Tools help keep this healthy: ArchUnit tests for layer and cycle rules, Spring Modulith for module boundaries, and the module system or Gradle modules for hard boundaries.

How it works

  1. Classify each reference as composition, aggregation/association, or inheritance.
  2. Composition: construct internally, hide.
  3. Collaborators: depend on interfaces, inject via constructors.
  4. Choose one navigation direction; add the reverse only when justified.
  5. Detect and break cycles with extraction, interfaces or events; enforce with architecture tests.

Example

@Service
class OrderService {
    private final OrderRepository orders;            // association: injected interface
    private final PaymentGateway payments;           // association: injected interface
    private final ApplicationEventPublisher events;

    OrderService(OrderRepository orders, PaymentGateway payments, ApplicationEventPublisher events) {
        this.orders = orders; this.payments = payments; this.events = events;
    }

    void place(Cart cart) {
        Order order = Order.from(cart);              // composition: lines created internally
        payments.charge(order.total());
        orders.save(order);
        events.publishEvent(new OrderPlaced(order.id())); // InventoryService listens; no cycle
    }
}
@ArchTest
static final ArchRule noCycles =
    slices().matching("com.shop.(*)..").should().beFreeOfCycles();

Common mistakes

  • Creating collaborators with new inside services, blocking tests and substitution.
  • Bidirectional entity links everywhere "just in case".
  • Fixing circular beans with @Lazy or field injection instead of redesigning.
  • Exposing composition internals in public APIs and DTOs.

How to answer in the interview

"The stronger the relationship, the tighter the coupling. Composition parts are internal details owned by the class, so I create them inside and keep them hidden. Associations and aggregations point to collaborators with their own lifecycle, so I pass them in through constructor injection and type them as interfaces, which is how Spring works and keeps things testable. Bidirectional associations and cycles between classes or modules make change harder and cause issues like infinite JSON serialisation or circular bean errors, so I prefer one direction and break cycles with an extracted component or events. Inheritance is the tightest dependency of all."

Likely follow-up questions

  • How would you break a circular dependency between two services? Extract the shared logic into a third service, invert with an interface, or use events.
  • Why constructor injection? Required dependencies are explicit, fields can be final, and tests are easy.
  • How do you enforce boundaries? ArchUnit tests, Spring Modulith or separate build modules.
