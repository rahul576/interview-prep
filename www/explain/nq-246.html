What is database denormalization, and when would you use it?

Databases & SQL · concept · levels mid

In one line

Denormalization deliberately adds redundant or precomputed data to make reads faster by avoiding expensive joins and aggregations, used for read-heavy, reporting and large-scale workloads, at the cost of more storage, more complex writes and possible inconsistency.

Detailed explanation

A normalised schema is the right starting point for transactional data, but some queries become too slow or too costly at scale: a dashboard that joins six tables and aggregates millions of rows on every page load, or a product listing that needs data from many tables. Denormalisation trades write-time effort for read-time speed.

Common techniques:

  • Copying columns: store customer_name on orders for listing pages, or product name and price on each order line, which also preserves the historical value.
  • Precomputed aggregates: order_count or lifetime_value on customer, a total on orders.
  • Summary tables and materialised views: daily sales per store refreshed by a job (REFRESH MATERIALIZED VIEW CONCURRENTLY in PostgreSQL).
  • Star schemas in data warehouses: fact tables with wide, denormalised dimension tables.
  • Read models (CQRS) and search indexes in Elasticsearch/OpenSearch built from events.
  • In NoSQL, denormalisation is the default: one Cassandra table per query, embedded documents in MongoDB, single-table design in DynamoDB.

Costs: every copy must be updated when the source changes, writes become slower and more complex, storage grows, and bugs or failures lead to inconsistent copies. You therefore need a clear source of truth and a sync mechanism: update both in the same transaction, database triggers, domain events or CDC (Debezium) to update read models, or periodic batch rebuilds. Decide how stale each copy may be.

How it works

  1. Start normalised and measure the slow query.
  2. Try indexes and query rewrites first.
  3. Identify the redundant data or aggregate that removes the expensive work.
  4. Choose the sync mechanism and acceptable staleness.
  5. Implement and backfill.
  6. Monitor drift, for example with reconciliation jobs.

Example

-- Precomputed counter kept in the same transaction
BEGIN;
INSERT INTO orders(id, customer_id, total) VALUES (991, 42, 49.00);
UPDATE customer SET order_count = order_count + 1, lifetime_value = lifetime_value + 49.00
WHERE id = 42;
COMMIT;

-- Summary for dashboards
CREATE MATERIALIZED VIEW daily_sales AS
SELECT store_id, date_trunc('day', created_at) AS day, SUM(total) AS revenue
FROM orders GROUP BY store_id, day;
CREATE UNIQUE INDEX ON daily_sales(store_id, day);
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_sales;

Common mistakes

  • Denormalising before measuring a real performance problem.
  • No owner or mechanism to keep copies in sync.
  • Counter columns updated under heavy concurrency, creating row-lock hotspots.
  • Forgetting to backfill existing rows when adding redundant columns.

How to answer in the interview

"Denormalisation deliberately adds redundant or precomputed data to speed up reads, after a normalised design has proven too slow. Examples are storing product name and price on order lines, an order count on customers, materialised views or summary tables for dashboards, star schemas in a warehouse, and query-shaped tables in Cassandra or embedded documents in MongoDB. I use it for read-heavy workloads and reporting where joins at scale are too expensive. The cost is more storage, more complex writes and the risk of copies drifting, so I define the source of truth and keep copies in sync with transactions, events or CDC, or batch rebuilds."

Likely follow-up questions

  • How to keep denormalised data in sync? Same transaction, triggers, events/CDC to update read models, or scheduled rebuilds with reconciliation.
  • Materialised view vs summary table? A materialised view is managed by the database and refreshed on demand; a summary table is maintained by your code.
  • Why is denormalisation normal in NoSQL? Joins are unavailable or expensive, so data is shaped around queries.
