How would you secure a shared build infrastructure that builds untrusted pull request code?

Docker · design · levels lead

In one line

Treat untrusted PR builds as hostile code: run each job on an ephemeral, isolated runner (ideally a microVM or separate VM), never give it privileged containers or the host Docker socket, build images with rootless BuildKit, give no secrets to untrusted PRs, keep trusted pipelines separate, restrict network egress and audit everything.

Detailed explanation

A pull request, especially from a fork, can change the build script, the Dockerfile and the tests. Anything the build can reach, the attacker can reach: secrets in environment variables, cloud credentials from the instance metadata service, the runner's filesystem, other jobs on the same host, and the internal network. Shared, long-lived runners are the worst case, because one malicious job can persist a backdoor that affects later, trusted builds.

Isolation: use ephemeral runners that are created for one job and destroyed afterwards. Containers alone are a weak boundary for hostile code, so for untrusted work use VM-level isolation: one VM per job, or microVMs such as Firecracker, or sandboxed runtimes like gVisor or Kata. Never mount /var/run/docker.sock or run --privileged (both equal host root). Build images with rootless BuildKit or similar daemonless builders inside the sandbox.

Secrets and trust tiers: untrusted PR builds get no secrets, no push rights to production registries and no deploy credentials. On GitHub Actions, pull_request from forks runs without secrets by default; avoid pull_request_target workflows that check out PR code, because they run with secrets. Trusted pipelines (publishing, deploying) run only on protected branches after review, on separate runner pools.

Network and audit: block the cloud metadata endpoint, limit egress to package mirrors and the cache registry, set short job timeouts, and log commands, network flows and runner lifecycle for investigation.

How it works

  1. PR opened → job scheduled on the "untrusted" ephemeral runner pool.
  2. Runner is a fresh microVM/VM with no credentials and restricted egress.
  3. Build and test with rootless BuildKit; artifacts kept only for the PR.
  4. Runner destroyed after the job.
  5. After review and merge, the trusted pipeline rebuilds from the protected branch with credentials and pushes/deploys.

Example

# GitHub Actions: untrusted PR tests, no secrets, read-only token
on: pull_request
permissions:
  contents: read
jobs:
  test:
    runs-on: [self-hosted, ephemeral, untrusted]
    timeout-minutes: 30
    steps:
      - uses: actions/checkout@v4
        with: { persist-credentials: false }
      - run: docker buildx build --target test .

Common mistakes

  • Shared, persistent self-hosted runners for public repositories.
  • pull_request_target workflows that build the PR's code with secrets available.
  • Docker-in-Docker with --privileged or socket mounts on shared hosts.
  • Leaving the cloud metadata service reachable from build jobs.

How to answer in the interview

"I assume PR code is malicious, because it can change the build itself. Every job runs on an ephemeral runner that's destroyed afterwards, so nothing persists between builds, and for untrusted code I want VM-level isolation, a VM or Firecracker microVM per job, not just a container. Builds never get privileged mode or the Docker socket; images are built with rootless BuildKit. Untrusted PRs get no secrets and can't push to real registries; only reviewed code on protected branches runs in a separate trusted pipeline with credentials. I also block the metadata endpoint, restrict egress to package mirrors, and log everything."

Likely follow-up questions

  • How do forked PRs run tests safely? In the untrusted tier with no secrets; integration tests needing credentials run after a maintainer approves or after merge.
  • Why is the Docker socket so dangerous? It allows starting privileged containers that mount the host filesystem.
  • Why VMs instead of containers? Containers share the host kernel; a kernel exploit escapes, a VM boundary is much harder.
