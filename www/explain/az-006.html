How do you manage secrets and certificates in Azure?

Azure · concept · levels mid

In one line

Store secrets, keys and certificates in Azure Key Vault, access them via managed identity with Key Vault RBAC, enable purge protection, private access and logging, automate rotation with expiry alerts, and consume them through App Service references, the AKS Secrets Store CSI driver or pipeline integration.

Detailed explanation

Azure Key Vault manages three object types: secrets (passwords, connection strings), keys (cryptographic keys, software- or HSM-protected), and certificates (with lifecycle management and auto-renewal from supported CAs). For stricter requirements there is Managed HSM, a single-tenant FIPS 140-3 Level 3 validated HSM pool.

Organise vaults by application and environment (for example kv-orders-prod), which limits blast radius and keeps permissions simple. Use the Azure RBAC permission model rather than legacy access policies, with roles like Key Vault Secrets User for applications and Key Vault Secrets Officer for administrators, assigned to managed identities so there is no bootstrap secret.

Protect the vault itself. Soft delete is always on, so deleted objects can be recovered during the retention period; purge protection prevents anyone from permanently deleting them early, which matters for keys used for encryption. Restrict networking with a private endpoint and disable public access, send diagnostic logs to Log Analytics to audit access, and enable Microsoft Defender for Key Vault for anomaly detection.

Rotation: set expiry dates; Key Vault emits Event Grid events such as SecretNearExpiry, which can trigger a Function that generates a new credential. Applications should fetch the latest version rather than a pinned one. Certificates from integrated CAs can renew automatically.

Integration: App Service and Functions support Key Vault references in app settings; AKS uses the Secrets Store CSI driver with the Key Vault provider and workload identity; Azure Pipelines can link variable groups to a vault or use the AzureKeyVault task.

How it works

  1. Create a vault per app and environment with RBAC authorisation and purge protection.
  2. Add a private endpoint; disable public network access.
  3. Grant the app's managed identity Key Vault Secrets User.
  4. Store secrets with expiry dates; configure diagnostic logs.
  5. Subscribe to near-expiry events and automate rotation.
  6. Reference secrets from App Service, AKS or pipelines.

Example

az keyvault create -n kv-orders-prod -g rg-orders-prod \
  --enable-rbac-authorization true --enable-purge-protection true \
  --public-network-access Disabled
az keyvault secret set --vault-name kv-orders-prod -n db-password \
  --value "$NEW_PASSWORD" --expires 2027-03-01T00:00:00Z

App Service setting using a Key Vault reference:

DB_PASSWORD=@Microsoft.KeyVault(SecretUri=https://kv-orders-prod.vault.azure.net/secrets/db-password/)

Common mistakes

  • One shared vault for every app and environment.
  • Using legacy access policies granting broad "get/list all" permissions.
  • Disabling or never enabling purge protection for encryption keys.
  • Pinning secret versions, so rotation needs a redeploy.
  • Copying secrets into pipeline variables in plain text.

How to answer in the interview

"I store secrets, keys and certificates in Azure Key Vault, usually one vault per application and environment. Applications access it with managed identities and Key Vault RBAC roles like Secrets User, so there are no secrets in code. Soft delete is always on, and I enable purge protection, private endpoint access with public access disabled, and diagnostic logging. I set expiry dates and use Event Grid near-expiry events to trigger automated rotation, and certificates auto-renew where possible. For consumption, App Service uses Key Vault references, AKS uses the Secrets Store CSI driver with workload identity, and pipelines use variable groups linked to Key Vault."

Likely follow-up questions

  • How would you rotate a database password without downtime? Use two credentials: create and store the new one, let apps pick it up, then revoke the old one.
  • Key Vault or App Configuration? Key Vault for secrets; App Configuration for non-secret settings and feature flags, referencing Key Vault.
  • When would you use Managed HSM? For single-tenant HSM requirements and strict compliance.
