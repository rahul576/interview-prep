What makes a good ChatOps assistant for DevOps teams in Slack or Teams?

AI Agents & AIOps · concept · levels mid, senior

In one line

A good ChatOps assistant answers operational questions (on-call, deployments, service status, runbooks), runs safe actions through existing automation, enforces per-user authentication and permissions, asks for in-channel confirmation of impactful actions, works visibly in shared channels, and keeps audit logs and rate limits.

Detailed explanation

Teams already coordinate incidents and releases in Slack or Microsoft Teams, so bringing information and actions there saves context switching. The assistant should answer questions by querying real systems: "who is on call for payments?" from PagerDuty or Opsgenie, "what went to production today?" from CI/CD, "is checkout healthy?" from monitoring and status pages, "where is the runbook for this alert?" from the service catalog.

For actions, it must call existing automation such as pipelines, Argo CD, runbook automation or incident tools, rather than having its own shell access. That way the same guardrails, approvals and logs apply as when a human clicks the button. Each request is tied to the chat user's identity, mapped to the identity provider, and checked against that user's permissions; the bot should never be a way to gain more rights. Impactful actions, like a production rollback, show exactly what will happen and require explicit confirmation, sometimes from a second person.

Running in shared channels gives transparency: the team sees questions and actions, which also spreads knowledge. Audit logs record who asked what and what ran, and rate limits stop a mistaken command from being repeated rapidly. With an LLM interface, text pasted into the channel from logs or tickets is untrusted and must not trigger actions without a confirmed user command.

How it works

  1. User asks a question or command in a channel.
  2. Bot resolves the user identity via SSO mapping.
  3. Intent is parsed into a specific tool call.
  4. Permission check against the user's roles and target environment.
  5. For impactful actions: preview, confirmation button, optional second approver.
  6. Execute via existing automation; post result and audit entry.

Example

@opsbot roll back checkout in prod
opsbot: Rollback plan for checkout (prod)
  current: v4.12.0 (deployed 10:14 by pipeline #5521)
  target:  v4.11.3
  method:  Argo CD sync to previous revision, canary 10% → 100%
  You (priya) have role deployer-prod. [Confirm] [Cancel]
priya: [Confirm]
opsbot: Rollback started — run #8812, tracking in #inc-3301

Common mistakes

  • One bot service account with admin rights used for all users.
  • Executing actions from free text without confirmation.
  • Bot actions in private DMs, invisible to the team.
  • Building a parallel automation path that bypasses pipeline controls.

How to answer in the interview

"It answers the questions people ask during work, like who's on call, what was deployed today, and where the runbook is, by querying the real systems. For actions it calls our existing automation, so the same guardrails apply. Every request is tied to the user's identity and permissions, and impactful actions show a preview and need explicit confirmation in the channel. Working in shared channels keeps everything visible, and all actions are audited and rate-limited. I'd also make sure content pasted into the channel can't trigger actions by itself."

Likely follow-up questions

  • Pasted untrusted instructions? Only explicit user commands trigger actions; tool output is data.
  • Read or write first? Start read-only, then add a few safe actions.
  • Approvals? Two-person rule for production-impacting actions.
