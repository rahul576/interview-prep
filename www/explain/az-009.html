Compare Azure Service Bus, Event Hubs and Event Grid.

Azure · concept · levels mid, senior

In one line

Use Service Bus for reliable business messages and commands (queues, topics, sessions, dead-lettering, transactions), Event Hubs for high-throughput event streaming (partitions, retention, Kafka endpoint), and Event Grid for push-based reactive notifications of state changes.

Detailed explanation

The three services solve different problems, and the key distinction is message versus event. A message carries an intent or valuable data that the sender expects someone to process ("charge this order"). An event is a notification that something happened ("blob created"); the publisher does not care who reacts, and a stream is a continuous flow of events like telemetry.

Azure Service Bus is an enterprise message broker. Queues give point-to-point delivery with competing consumers; topics and subscriptions give publish-subscribe with filters. Features include peek-lock with explicit completion, dead-letter queues for poison messages, sessions for FIFO ordering per session key (for example per customer), duplicate detection, scheduled messages, and transactions across operations. The Premium tier adds dedicated capacity, VNet integration and large messages.

Azure Event Hubs is a streaming platform for millions of events per second. Data is written to partitions, retained for a configurable period (hours to days, longer on higher tiers), and read independently by multiple consumer groups, each tracking its own offset/checkpoint and able to replay. It has a Kafka-compatible endpoint, so Kafka clients work without code changes, and Capture writes events to Blob Storage or Data Lake. Typical uses are telemetry, logs, clickstreams and IoT.

Azure Event Grid is an event routing service with a push model. Azure services (Storage, Resource Manager, Key Vault and more) and custom topics publish events, and subscriptions with filters deliver them to handlers such as Functions, webhooks, Service Bus or Event Hubs, with retries and dead-lettering. It supports the CloudEvents schema, and Event Grid namespaces add MQTT and pull delivery.

How it works

  1. Identify the semantics: command/transaction, stream, or notification.
  2. Commands needing guaranteed processing and ordering: Service Bus.
  3. High-volume streams needing replay and many readers: Event Hubs.
  4. Reacting to resource or application state changes: Event Grid.
  5. Combine them, for example Event Grid pushing into a Service Bus queue for durable processing.

Example

Processing Service Bus messages with sessions and dead-lettering (Python):

from azure.servicebus import ServiceBusClient
with ServiceBusClient(ns_fqdn, credential) as client:
    with client.get_queue_receiver("orders", session_id="customer-42") as rx:
        for msg in rx:
            try:
                process(msg)
                rx.complete_message(msg)
            except ValidationError as e:
                rx.dead_letter_message(msg, reason="invalid", error_description=str(e))

Common mistakes

  • Using Event Grid for business transactions that need ordering and transactions.
  • Using Service Bus for massive telemetry streams.
  • Choosing too few Event Hubs partitions for future throughput.
  • Not handling dead-letter queues.
  • Assuming exactly-once delivery; all three are at-least-once, so consumers must be idempotent.

How to answer in the interview

"Service Bus is enterprise messaging for commands and business transactions: queues and topics with subscriptions, sessions for ordering, dead-letter queues, duplicate detection and transactions. Event Hubs is a high-throughput streaming platform with partitions, retention and replay, used for telemetry and logs, and it exposes a Kafka-compatible endpoint. Event Grid pushes discrete events, like a blob being created, to handlers such as Functions or webhooks, which is ideal for serverless reactions. I choose based on semantics: valuable commands to Service Bus, streams to Event Hubs, and state-change notifications to Event Grid, and I design consumers to be idempotent because delivery is at-least-once."

Likely follow-up questions

  • An order must be processed exactly once in sequence per customer. Which service? Service Bus with sessions keyed by customer, duplicate detection and idempotent handlers.
  • How do you scale Event Hubs consumers? One consumer per partition per consumer group; more partitions for more parallelism.
  • When would you pick Kafka on Event Hubs over Confluent? When you want a managed Azure-native service and do not need full Kafka ecosystem features.
