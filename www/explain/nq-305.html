How can you check application logs in a containerized environment?

Docker · scenario · levels entry

In one line

Containers should log to stdout/stderr. Read them with docker logs or kubectl logs (-f, --previous, -c, -l), use kubectl describe and events to understand crashes, and in production rely on centralised logging (Fluent Bit to ELK/OpenSearch, Loki, CloudWatch, Azure Monitor) with structured JSON logs and correlation ids.

Detailed explanation

The container convention (also a Twelve-Factor App rule) is that applications write logs to standard output and standard error, not to files inside the container. The container runtime captures those streams, and on Kubernetes nodes they are stored under /var/log/containers, which is what kubectl logs reads.

For a quick look:

  • Docker: docker logs -f --tail 200 orders, or docker compose logs -f orders.
  • Kubernetes: kubectl logs <pod>. Add -f to follow, -c <container> for multi-container pods (sidecars, init containers), --previous to see the crashed previous instance, -l app=orders for all pods with a label, and --since=15m to limit the time range.

When a pod keeps restarting, logs may be empty or cut off, so check kubectl describe pod for the last state and reason: OOMKilled, exit code 137, failed liveness probes, or image pull errors. Also check kubectl get events --sort-by=.lastTimestamp.

Pods are ephemeral. When a pod is deleted or a node is replaced, its local logs are gone, and searching 30 replicas one by one is impractical. So production uses centralised logging. A node-level agent (a DaemonSet such as Fluent Bit, Fluentd, Vector or the OpenTelemetry Collector) tails container logs, adds Kubernetes metadata (namespace, pod, labels) and ships them to Elasticsearch/OpenSearch with Kibana, Loki with Grafana, CloudWatch Logs or Azure Monitor/Log Analytics. There you can search across all pods and set alerts.

To make search useful, emit structured JSON logs with level, service, and trace id/correlation id, so one request can be followed across services.

How it works

  1. The app logs JSON to stdout.
  2. The runtime writes it to node log files, rotated by the kubelet.
  3. The Fluent Bit DaemonSet tails the files and enriches them with pod metadata.
  4. Logs are shipped to the backend and indexed by time, service and labels.
  5. Engineers query by service, trace id or error, and alerts trigger on error spikes.

Example

kubectl logs -f deploy/orders --since=10m
kubectl logs orders-7d9c-abcde -c app --previous      # crashed instance
kubectl logs -l app=orders --all-containers --prefix --tail=100
kubectl describe pod orders-7d9c-abcde | grep -A5 "Last State"
kubectl get events -n shop --sort-by=.lastTimestamp
{namespace="shop", app="orders"} | json | level="ERROR" | traceId="4bf92f35"

Common mistakes

  • Writing logs to files inside the container, where they are invisible to kubectl logs and lost on restart.
  • Forgetting --previous when debugging CrashLoopBackOff.
  • Unstructured multi-line logs (stack traces) that the shipper splits into separate entries.
  • Logging secrets or personal data.

How to answer in the interview

"Containers should log to stdout and stderr. For one container I'd use docker logs -f. On Kubernetes I'd use kubectl logs with -f to follow, -c for a specific container, --previous for a crashed instance, and -l to select all pods of an app. If a pod keeps restarting, kubectl describe and the events tell me whether it's OOMKilled or a probe failure. Pods are ephemeral, so in production we rely on centralised logging: Fluent Bit ships logs to Elasticsearch, Loki or CloudWatch, and we search there. Structured JSON logs with trace ids make that search effective."

Likely follow-up questions

  • Logs of a container that keeps crashing? kubectl logs --previous, plus describe for the exit reason.
  • Sidecar or DaemonSet for log shipping? A DaemonSet is the default. Sidecars are for apps that can only write files.
  • Logs versus traces versus metrics? Logs record events, metrics give aggregated numbers, traces follow a request across services.
