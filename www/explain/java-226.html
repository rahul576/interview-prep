How do you make a class thread-safe? Describe the main strategies.

Concurrency · concept · levels mid, senior

In one line

Make a class thread-safe by, in order of preference, not sharing state (confinement), not mutating it (immutability), or coordinating access (locks, atomics, concurrent collections), plus safe publication and documented guarantees.

Detailed explanation

A class is thread-safe if it behaves correctly when used from multiple threads without callers adding their own synchronisation. All thread-safety bugs come from shared mutable state, so the strategies attack either "shared" or "mutable" first, and only coordinate access when both are unavoidable.

Immutability is the strongest tool: final fields, no setters, defensive copies of mutable inputs. Immutable objects can be shared freely. Thread confinement means data is only ever touched by one thread: local variables, request-scoped objects, ThreadLocal, or an actor or single-thread executor that owns the state.

When state must be shared and mutable, protect every invariant with the same lock. Compound actions such as check-then-act or read-modify-write must be atomic as a whole, not just each call. Keep critical sections short and never call alien methods while holding a lock. For single variables, atomic classes (AtomicLong, LongAdder) use CAS without locks; for collections use ConcurrentHashMap, CopyOnWriteArrayList or BlockingQueue, and use their atomic methods (computeIfAbsent, merge).

Finally, safe publication: another thread must see a fully constructed object. That happens through final fields, a volatile reference, a lock, a concurrent collection or static initialisation. Do not let this escape from the constructor. And document the policy, for example "thread-safe; guarded by lock" or "not thread-safe", so maintainers do not break it.

How it works

  1. Identify the state and its invariants (which fields must change together).
  2. Remove sharing where you can: confine to a thread or request.
  3. Remove mutation where you can: make the object or its value types immutable.
  4. For what remains, pick one guard per invariant: a lock, an atomic or a concurrent collection.
  5. Make compound actions atomic and publish objects safely.
  6. Document the guarantee and test under concurrency (stress tests, jcstress for low-level code).

Example

/** Thread-safe. All mutable state guarded by 'lock'. */
public final class RateCounter {
    private final Object lock = new Object();
    private long windowStart;   // guarded by lock
    private int count;          // guarded by lock

    public boolean tryAcquire(int limit, long nowMillis) {
        synchronized (lock) {                // compound action is atomic
            if (nowMillis - windowStart >= 1000) {
                windowStart = nowMillis;
                count = 0;
            }
            if (count >= limit) return false;
            count++;
            return true;
        }
    }
}

// Simpler alternative for independent counters
private final ConcurrentHashMap<String, LongAdder> hits = new ConcurrentHashMap<>();
void hit(String key) { hits.computeIfAbsent(key, k -> new LongAdder()).increment(); }

Common mistakes

  • Using a thread-safe collection but doing check-then-act across two calls.
  • Guarding a field with different locks in different methods.
  • Leaking this from a constructor (starting a thread or registering a listener).
  • Returning internal mutable collections, so callers modify state without the lock.
  • Making everything synchronized, which hurts throughput and risks deadlocks.

How to answer in the interview

"My first choice is to avoid shared mutable state: make objects immutable, or confine data to one thread, like local or request-scoped variables. When state really is shared, I protect each invariant with one lock and make compound actions like check-then-act atomic, keeping critical sections small, or I use atomic variables and concurrent collections such as ConcurrentHashMap with their atomic methods. I make sure objects are safely published, through final fields, volatile or a concurrent container, and I document the class's thread-safety guarantee so nobody breaks it later."

Likely follow-up questions

  • Is a class with only final fields always thread-safe? No; if a final field refers to a mutable object such as an ArrayList that is modified, the class is not thread-safe.
  • What is safe publication? Making a fully constructed object visible to other threads through a happens-before edge, such as volatile, final fields or a lock.
  • When would you use LongAdder over AtomicLong? For heavily contended counters that are written often and read rarely.
