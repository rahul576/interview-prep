How do you scale Prometheus for many clusters and long-term retention?

Observability & SRE · concept · levels mid, senior

In one line

A single Prometheus hits limits on memory, local retention, HA and global view, so run Prometheus or an agent per cluster and remote write to a horizontally scalable backend (Grafana Mimir, Thanos, Cortex, VictoriaMetrics) storing data in object storage, with a global query view, HA deduplication and strict cardinality control.

Detailed explanation

Limits of one Prometheus: it's a single process with a local TSDB. Memory grows with active series (a few kilobytes per series), so a few million series need a big machine. Local disk retention makes months or years of data expensive and fragile. There's no built-in HA: the usual answer is two identical replicas, which produces duplicate data. And each cluster's Prometheus sees only its own targets, so there's no global view across clusters or regions.

Scaling patterns:

  • Remote write from each cluster's Prometheus or Prometheus in agent mode (or Grafana Alloy / OpenTelemetry Collector) to a central backend. Agent mode only scrapes and forwards, with a small write-ahead log.
  • Grafana Mimir and Cortex: horizontally scalable, multi-tenant, microservice architectures (distributors, ingesters, store-gateways, queriers, compactors) storing blocks in S3, GCS or Azure Blob; Mimir is the actively developed successor to Cortex.
  • Thanos: a sidecar next to each Prometheus uploads TSDB blocks to object storage and serves recent data; the querier fans out across sidecars and store gateways for a global view with deduplication of HA replicas; the compactor downsamples old data; Thanos Receive supports remote write.
  • VictoriaMetrics: single-node or cluster version, resource-efficient, compatible with PromQL (MetricsQL).
  • Federation (a parent scraping /federate from children) only suits small sets of aggregated series, not full data.
  • Managed options: Amazon Managed Service for Prometheus, Azure Monitor managed Prometheus, Google Managed Prometheus, Grafana Cloud.

Cardinality control is the biggest operational issue: enforce label conventions, avoid unbounded labels, drop unused metrics with metric_relabel_configs or write_relabel_configs, aggregate with recording rules before shipping, and set per-tenant limits on series and ingestion rate in the backend. Use downsampling for long retention, and tier retention (raw 30 days, 5-minute resolution for a year).

How it works

  1. Each cluster runs Prometheus (HA pair) or an agent with external labels (cluster, replica).
  2. Metrics are filtered and remote-written to the central backend.
  3. The backend ingests, replicates and writes blocks to object storage.
  4. Compactors merge and downsample blocks.
  5. Queriers serve a global PromQL view to Grafana, deduplicating replicas.
  6. Limits and dashboards track series per tenant.

Example

global:
  external_labels: { cluster: prod-eu-1, replica: "0" }
remote_write:
  - url: https://mimir.internal/api/v1/push
    headers: { X-Scope-OrgID: platform }
    write_relabel_configs:
      - source_labels: [__name__]
        regex: "go_gc_.*|apiserver_request_duration_seconds_bucket"
        action: drop

Common mistakes

  • Using federation to copy all data centrally.
  • Scaling up one huge Prometheus instead of distributing.
  • No external labels, so data from clusters collides.
  • Ignoring cardinality until the backend falls over.

How to answer in the interview

"A single Prometheus is limited by memory, local retention, and has no built-in HA or global view. For many clusters I run Prometheus or an agent in each cluster with external labels and remote write to a scalable backend like Grafana Mimir, Thanos, Cortex or VictoriaMetrics. These store data in object storage like S3 for cheap long retention, downsample old data and give a global query view, deduplicating HA pairs. The biggest operational issue is cardinality, so I control labels, drop unused metrics before shipping and set per-tenant limits."

Likely follow-up questions

  • How do you find which metrics cause a cardinality explosion? The TSDB status page or topk(10, count by (__name__)({__name__=~".+"})), Mimir's cardinality API, and checking labels with many values.
  • Thanos sidecar versus remote write? Sidecar uploads blocks and keeps local querying; remote write streams samples to a central system.
  • What is agent mode? Prometheus that only scrapes and remote-writes, without local querying or long storage.
