What is the difference between unit testing and integration testing?

Testing · concept · levels entry

In one line

A unit test checks one unit in isolation with mocked dependencies and finds logic bugs quickly; an integration test checks several components together with real collaborators (Spring context, database, broker, HTTP) and finds wiring, configuration and contract bugs, at the cost of speed.

Detailed explanation

The two differ along four dimensions.

Scope: a unit test targets one class or function, for example DiscountCalculator. An integration test spans a chain, such as controller → service → repository → PostgreSQL, or producer → Kafka → consumer.

Dependencies: in unit tests, collaborators are replaced by mocks or stubs, so you control every input and the test never leaves the JVM. In integration tests they are real: the Spring application context with its configuration and proxies, a real database in Testcontainers, a real broker, or at least a real HTTP stack talking to WireMock.

Speed and quantity: unit tests run in milliseconds and you have hundreds or thousands. Integration tests take seconds, need Docker and setup, and you have fewer, focused on each integration point.

What they catch: unit tests catch wrong calculations, missing branches and bad edge-case handling, and pinpoint the failing line. Integration tests catch problems that only exist when pieces meet: incorrect SQL or JPA mappings, missing indexes or constraints, transaction boundaries (e.g. @Transactional not applied on a self-invocation), Jackson serialisation, validation and security configuration, bean wiring and property binding, message formats. A mock cannot reveal these, because the mock behaves exactly as you assumed.

A healthy suite follows the test pyramid: many unit tests at the base, fewer integration tests in the middle, and very few end-to-end tests on top. The anti-pattern is the ice-cream cone, where most testing is manual or end-to-end, which is slow and flaky.

How it works

  1. Unit: construct the class with mocks → call method → assert.
  2. Integration: start Spring and real dependencies → call the entry point → assert response and side effects.
  3. CI runs unit tests first (fast fail), then integration tests.
  4. Bugs found later are added as tests at the cheapest level that catches them.

Example

// Unit test: repository mocked, logic only
@Test
void appliesLoyaltyDiscount() {
    when(customers.findById(7L)).thenReturn(Optional.of(goldCustomer()));
    assertThat(pricing.priceFor(7L, new BigDecimal("100"))).isEqualByComparingTo("90");
}

// Integration test: real context + real PostgreSQL
@SpringBootTest @Testcontainers
class PricingIT {
    @Container @ServiceConnection
    static PostgreSQLContainer<?> pg = new PostgreSQLContainer<>("postgres:16");
    @Autowired PricingService pricing;
    @Autowired CustomerRepository customers;

    @Test
    void appliesDiscountFromStoredTier() {
        Long id = customers.save(new Customer("Ravi", Tier.GOLD)).getId();
        assertThat(pricing.priceFor(id, new BigDecimal("100"))).isEqualByComparingTo("90");
    }
}

Common mistakes

  • Calling @SpringBootTest tests "unit tests".
  • Trying to verify SQL correctness with mocked repositories.
  • Writing only integration tests, making feedback slow.
  • Writing only unit tests and discovering wiring errors in production.

How to answer in the interview

"A unit test checks one class in isolation with its dependencies mocked. It's very fast, pinpoints broken logic, and we write lots of them. An integration test checks components working together with real collaborators, like the Spring context, the database, a message broker or the HTTP layer. It's slower and needs more setup, but it finds things unit tests can't, such as wrong SQL, misconfigured beans, JSON mapping or transaction boundaries. I balance them with the test pyramid: many unit tests, fewer integration tests and only a few end-to-end tests."

Likely follow-up questions

  • What is the test pyramid? Many unit, fewer integration, very few end-to-end tests; the ice-cream cone is its inversion.
  • Is @DataJpaTest an integration test? Yes, a slice integration test with a real persistence layer.
  • Which level for a bug in a JPQL query? Integration, against the real database.
