How does leader election work in a distributed system, and what can go wrong?

Distributed Systems · concept · levels senior, lead

In one line

Leader election picks one coordinator using a consensus system (ZooKeeper, etcd, Raft) with leases and heartbeats and a quorum; the main danger is split brain, prevented with fencing tokens that let resources reject stale leaders.

Detailed explanation

Many tasks need exactly one actor: a scheduler firing jobs, a partition owner, the primary database. Rolling your own election with timestamps or "whoever writes first" fails under network partitions and pauses.

Consensus systems provide linearizable primitives: an ephemeral node in ZooKeeper or a lease in etcd, owned by a session kept alive by heartbeats. If the leader stops heartbeating, the lease expires and another candidate acquires it. Because the consensus cluster requires a majority, a node on the minority side of a partition can't become leader.

Split brain: the old leader may not know it lost leadership, for example after a 30 s GC pause, and may still act. Fencing tokens fix this: each leadership term gets a monotonically increasing number (etcd revision, ZooKeeper zxid); every write to shared resources includes it, and the resource rejects tokens lower than the highest seen.

How it works

  1. Candidates try to create/acquire the lease key.
  2. Winner becomes leader; gets term/token.
  3. Leader renews the lease periodically (e.g. TTL 15 s, renew every 5 s).
  4. Followers watch the key; on deletion/expiry, contend again.
  5. Leader includes the token in all side-effecting operations.

Example

// etcd concurrency package
s, _ := concurrency.NewSession(cli, concurrency.WithTTL(15))
e := concurrency.NewElection(s, "/scheduler/leader")
e.Campaign(ctx, hostname)        // blocks until elected
// leadership revision usable as fencing token: e.Rev()

In Kubernetes, the coordination.k8s.io/Lease API offers the same for pods.

Common mistakes

  • Assuming the leader always knows it's the leader.
  • Lease TTLs shorter than realistic GC/network pauses.
  • Using an even-sized consensus cluster.

How to answer in the interview

"I'd use an existing consensus system like etcd, ZooKeeper or Kubernetes Leases rather than build it. A node acquires a lease and renews it with heartbeats; if it disappears, the lease expires and another takes over. Quorum prevents a minority partition from electing a leader. Because an old leader can still be alive after a pause, every write carries a fencing token from the leadership term, and resources reject older tokens."

Likely follow-up questions

  • Kubernetes pods? client-go leaderelection with a Lease object.
  • Why odd cluster sizes? Majority tolerance: 3 tolerates 1, 5 tolerates 2.
  • What if etcd is down? No new leaders; current one should step down when it can't renew.
