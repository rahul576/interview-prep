How can sorting the characters of a string help identify anagrams?

DSA: Arrays & Strings · concept · levels entry

In one line

Sorting the characters produces a canonical signature: every arrangement of the same letters sorts to the same string ("listen", "silent", "enlist" → "eilnst"), so two words are anagrams if and only if their sorted forms are equal, at O(k log k) per word.

Detailed explanation

An anagram relationship ignores order. Sorting removes order by forcing the characters into one fixed sequence. Two strings with the same characters in the same counts must therefore produce the identical sorted string, and two strings that differ in any count must produce different sorted strings. That gives an "if and only if" test, which is exactly what you need for both checking and grouping.

This turns a fuzzy comparison ("do these contain the same letters?") into a simple equality check on strings, or a hash lookup when grouping: put each word into a map under its sorted form, and all anagrams land in the same bucket automatically. This is the standard "group anagrams" solution.

Cost: for a word of length k, sorting is O(k log k) (Java uses a dual-pivot quicksort for primitive arrays), plus O(k) to copy and build the string. For typical words (k ≤ 20) this is effectively constant. For very long strings, or when processing millions of words, a counting signature built in O(k) is faster.

Signatures without sorting:

  • A frequency array converted to a string, like "1#0#0#1#...".
  • A List<Integer> of counts (has value-based equals/hashCode).
  • A product of distinct primes per letter (elegant but overflows for long words, needing BigInteger).

Any of these work as long as two words get the same signature exactly when they are anagrams.

Remember to normalise before sorting (lowercase, strip spaces) if the problem treats those as irrelevant, otherwise "Tea" and "eat" sort differently because uppercase letters have smaller char codes.

How it works

  1. Copy the string to a char[].
  2. Sort the array.
  3. Build a string from it: the signature.
  4. Compare signatures for equality, or use them as map keys.

Example

static String signature(String w) {
    char[] c = w.toLowerCase().toCharArray();
    Arrays.sort(c);
    return new String(c);
}

signature("listen");  // "eilnst"
signature("Silent");  // "eilnst"
signature("enlist");  // "eilnst"
signature("tinsel");  // "eilnst"
signature("listed");  // "deilst"  -> not an anagram

boolean anagram = signature("listen").equals(signature("silent")); // true

Common mistakes

  • Forgetting to lowercase first, so "Tea" ≠ "eat".
  • Claiming sorting is O(k) per word.
  • Using the sorted char[] directly as a key instead of converting to String.
  • Choosing sorting for extremely long strings where counting is clearly better.

How to answer in the interview

"Sorting puts the characters into a fixed order, so every arrangement of the same letters gives exactly the same result: listen, silent and enlist all become eilnst. That sorted string is a canonical signature. Two words are anagrams if and only if their signatures are equal, so comparing becomes a simple string equality and grouping becomes a hash map lookup. The cost is O(k log k) per word of length k, which is fine for normal words; for very long ones I'd use a character-count signature in O(k)."

Likely follow-up questions

  • Can you build a signature without sorting? Yes, a frequency-count string or list in O(k).
  • Why is equality of sorted strings "if and only if"? Sorting maps each multiset of characters to exactly one sequence.
  • What about case? Normalise to lowercase before sorting.
