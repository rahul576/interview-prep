Card authorisations must be approved or declined within 100 milliseconds. Architect the risk-scoring path, including what happens when it is slow.

AI & ML System Design · design · levels senior, lead

In one line

Real-time fraud scoring sits synchronously in the authorisation path: fetch low-latency features (profile, device, streaming aggregates) from an online store, combine a rules engine with an ML model, decide approve / decline / step-up, apply a conservative fallback when slow, log everything, and retrain from delayed chargeback labels.

Detailed explanation

Card networks give the issuer or merchant only ~100 ms for the whole decision, so every component has a tight budget (e.g. features 15 ms, model 10 ms).

Features fall into three groups:

  • Static/profile: account age, usual countries, typical spend, merchant risk.
  • Device/session: fingerprint, IP reputation, emulator detection.
  • Velocity aggregates: transactions in the last 10 min/1 h/24 h, distinct merchants, distance and time from the last transaction ("impossible travel"). Computed continuously by Flink/Kafka Streams and written to an online store (Redis, Aerospike, DynamoDB).

Rules encode explicit policies and fast-moving patterns (block a compromised BIN range now). Models (gradient-boosted trees for speed, sometimes graph features for fraud rings) produce a risk score. A decision layer maps score + amount + context to approve, decline or step-up (3-D Secure, OTP).

Fallback: if features or model time out, apply simple rules (approve low amounts, step-up high ones) rather than failing payments.

Labels arrive late (chargebacks can take weeks), so training uses matured windows, plus faster proxy labels (customer reports). New models run in shadow mode before taking decisions.

How it works

  1. Auth request → fraud API (deadline 80 ms).
  2. Parallel feature fetches → rules → model → decision.
  3. Response + decision log (features snapshot) → Kafka.
  4. Outcomes (chargebacks, confirmations) joined later → training data.

Example

txn: ₹48,000, new device, IP country ≠ card country, 6 txns in 10 min
rules: velocity_high → +0.3     model score: 0.82
decision: STEP_UP (OTP) because amount > ₹10k and score in [0.6, 0.9)

Common mistakes

  • Computing aggregates at request time with DB queries.
  • Training on labels that haven't matured.
  • No fallback → payment outages when the scorer is slow.
  • Not logging the exact features used at decision time.

How to answer in the interview

"The fraud service is called synchronously with a hard deadline. It fetches profile, device and velocity features, with velocity aggregates precomputed by a streaming job into an online store, runs rules plus a fast gradient-boosted model, and returns approve, decline or step-up. If it's slow, a conservative fallback applies. Every decision is logged with its features, chargeback labels arrive later for retraining, and new models start in shadow mode."

Likely follow-up questions

  • Delayed labels? Matured training windows, proxy labels, semi-supervised methods.
  • Fraud rings? Graph features linking devices, cards, addresses.
  • False positives cost? Tune thresholds by expected loss vs customer friction.
