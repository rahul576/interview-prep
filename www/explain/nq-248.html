What is database indexing, and how does it improve query performance?

Databases & SQL · concept · levels entry

In one line

An index is an extra data structure, usually a B-tree, that keeps column values sorted with pointers to rows, so the database can find rows in logarithmic time instead of a full table scan, speeding up WHERE, JOIN, ORDER BY and GROUP BY at the cost of storage and slower writes.

Detailed explanation

Without an index, finding WHERE email = 'asha@example.com' in a 50-million-row table means reading every row. A B-tree (B+tree) index stores the email values in sorted order in a balanced tree of pages. The engine walks from the root to a leaf in a handful of page reads, then follows the pointer to the row. That is O(log n) instead of O(n), like using a book's index instead of reading every page.

Because the entries are sorted, the same index also helps range queries (created_at BETWEEN ...), ORDER BY (rows come out already sorted, avoiding a sort), GROUP BY, MIN/MAX, and joins on foreign keys, where the inner table is probed by index for each outer row.

Types you should know:

  • Primary/clustered: in InnoDB the table itself is ordered by the primary key; PostgreSQL stores rows in a heap with all indexes secondary.
  • Secondary (non-clustered): separate structure pointing to rows.
  • Unique: also enforces uniqueness.
  • Composite: several columns, following the leftmost prefix rule.
  • Covering: includes all columns a query needs, enabling an index-only scan.

Indexes are not free: each insert, update and delete must maintain them, and they use disk and memory. The optimizer decides whether to use an index based on statistics; if a query returns a large share of the table, a sequential scan may be cheaper. Verify with EXPLAIN.

How it works

  1. CREATE INDEX builds a sorted tree of (key, row pointer) entries.
  2. A query with a matching predicate lets the planner consider an index scan.
  3. The engine descends the tree to the first matching key.
  4. It scans leaf entries in order for ranges.
  5. It fetches rows by pointer, unless the index covers the query.
  6. Writes update the tree, splitting pages as needed.

Example

CREATE INDEX idx_users_email ON users(email);
EXPLAIN ANALYZE SELECT id, name FROM users WHERE email = 'asha@example.com';
-- Index Scan using idx_users_email ... actual time=0.03 ms   (was Seq Scan, 2,400 ms)

CREATE INDEX idx_orders_customer ON orders(customer_id);           -- speeds up joins
CREATE INDEX idx_active_users ON users(last_login) WHERE active;   -- partial index
CREATE INDEX idx_users_lower_email ON users (lower(email));        -- expression index

Common mistakes

  • Indexing every column "just in case".
  • Applying functions to indexed columns in queries (WHERE lower(email) = ...) without an expression index.
  • Assuming an index is used without checking the plan.

How to answer in the interview

"An index is an extra data structure, usually a B-tree, that keeps the values of one or more columns sorted with pointers to the rows. Like a book index, it lets the database find matching rows in logarithmic time instead of scanning the whole table, which matters hugely for large tables. It speeds up WHERE filters, joins on foreign keys, ORDER BY and GROUP BY, and unique indexes enforce uniqueness. Composite indexes follow the leftmost prefix rule, and covering indexes include all needed columns so the table isn't read. Indexes cost storage and slow down writes, so I add them for real query patterns and verify usage with EXPLAIN."

Likely follow-up questions

  • Why might the database ignore your index? Low selectivity, a function or type cast on the column, stale statistics, or the leading column missing from the predicate.
  • B-tree vs hash index? Hash supports only equality; B-tree supports ranges and ordering too.
  • What is a partial index? An index over only rows matching a condition, smaller and faster.
