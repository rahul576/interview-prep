What are class loaders in Java?

JVM & Performance · concept · levels mid

In one line

A class loader is a JVM object that finds a class's bytecode and turns it into a Class object at runtime; loading is followed by linking (verify, prepare, resolve) and initialisation, and a class's identity is its name plus its defining loader.

Detailed explanation

Java does not link a whole program up front. Classes are loaded lazily, the first time they are actively used. A ClassLoader locates the bytes, from a directory, a JAR, a module image, the network or bytes generated in memory by frameworks such as Hibernate or Mockito, and calls defineClass to create the Class object, whose metadata lives in Metaspace.

After loading comes linking. Verification checks the bytecode is well formed and type-safe, so malformed or malicious code cannot corrupt the JVM. Preparation allocates static fields and sets them to default values (0, null, false). Resolution turns symbolic references to other classes, methods and fields into direct references, often lazily. Finally initialisation runs the static initialisers and static field assignments, exactly once, in a thread-safe way.

Loaders form a hierarchy (Bootstrap, Platform, Application, plus custom ones) and use parent delegation: ask the parent first, load yourself only if the parent cannot. The crucial design point is that a class is identified by its fully qualified name and its defining loader. Two com.acme.Plugin classes loaded by different loaders are different types, and casting one to the other throws ClassCastException. Application servers (one loader per web app), OSGi, IDE plugin systems and hot-reload tools such as Spring Boot DevTools rely on this to isolate library versions and to unload and reload code by discarding a loader.

How it works

  1. Code triggers first use of a class (new, static call, reflection).
  2. The requesting loader delegates to its parent chain.
  3. The loader that can see the class reads its bytes and defines it.
  4. Linking: verify, prepare statics, resolve references.
  5. Initialisation runs static {} blocks.
  6. The class stays loaded until its loader becomes unreachable and is garbage collected.

Example

public class PluginHost {
    public static void main(String[] args) throws Exception {
        URL jar = Path.of("plugins/report-plugin.jar").toUri().toURL();
        try (URLClassLoader loader = new URLClassLoader(new URL[]{jar},
                PluginHost.class.getClassLoader())) {
            Class<?> cls = loader.loadClass("com.acme.ReportPlugin");
            Runnable plugin = (Runnable) cls.getDeclaredConstructor().newInstance();
            plugin.run();
            System.out.println(cls.getClassLoader());   // the URLClassLoader
            System.out.println(String.class.getClassLoader()); // null = bootstrap
        }
    }
}

Closing the loader and dropping references lets the plugin classes be unloaded, enabling reload.

Common mistakes

  • Thinking all classes are loaded at JVM start.
  • Confusing loading with initialisation: Class.forName(name, false, loader) loads without initialising.
  • Leaking a class loader (for example via a static ThreadLocal or JDBC driver registration), causing Metaspace leaks on redeploys.
  • Being surprised by ClassCastException between "identical" classes from different loaders.

How to answer in the interview

"A class loader finds the bytecode for a class and defines a Class object in the JVM, lazily on first use. After loading the JVM links the class, verifying the bytecode, preparing static fields with defaults and resolving references, and then initialises it by running static initialisers. Loaders form a hierarchy with parent delegation. The important detail is that a class's identity is its name plus its loader, which is how Tomcat, OSGi or plugin systems isolate different library versions and reload applications."

Likely follow-up questions

  • How can two classes with the same name differ in one JVM? They were defined by different class loaders.
  • What causes a Metaspace leak on redeploy? Something outside the app keeps a reference to the old web-app class loader.
  • When is a class unloaded? When its loader and all its classes and instances are unreachable and GC collects them.
