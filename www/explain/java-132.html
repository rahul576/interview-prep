What is the difference between optimistic and pessimistic locking in JPA?

Spring Data & JPA · concept · levels mid, senior

In one line

Optimistic locking assumes conflicts are rare and detects them at update time with a @Version column, throwing OptimisticLockException so you retry or report; pessimistic locking takes database row locks up front (SELECT ... FOR UPDATE) so others wait; choose by contention level.

Detailed explanation

Both prevent lost updates, where two users read the same row, both change it and the second write silently overwrites the first.

Optimistic locking adds a version attribute (@Version on an integer or timestamp). Every UPDATE includes the old version in the WHERE clause and increments it: update product set price=?, version=8 where id=? and version=7. If another transaction already changed the row, the version no longer matches, zero rows are updated and Hibernate throws OptimisticLockException (Spring translates it to ObjectOptimisticLockingFailureException). No locks are held while users think, so it scales well. It also works across requests: send the version to the client (for example as an ETag) and check it on the next update. The cost is handling conflicts: retry automatically for idempotent operations, or return 409 Conflict and let the user reload.

Pessimistic locking asks the database for a lock when reading: @Lock(LockModeType.PESSIMISTIC_WRITE) generates SELECT ... FOR UPDATE, so other transactions trying to lock or update that row wait until commit. PESSIMISTIC_READ takes a shared lock where supported. It guarantees no conflict at the cost of blocking, potential deadlocks and reduced throughput; always set a lock timeout (jakarta.persistence.lock.timeout) and keep transactions short. Lock rows in a consistent order to avoid deadlocks. SKIP LOCKED is useful for job-queue patterns.

Choosing: optimistic for typical web apps where conflicts are rare and transactions span user think-time; pessimistic for short, high-contention operations where retries would be frequent, such as decrementing inventory for a flash sale, seat booking or account balances. Atomic SQL (update stock set qty = qty - 1 where id=? and qty > 0) is sometimes simpler than either.

How it works

  1. Optimistic: read row with version 7.
  2. Update with where version = 7, set version 8.
  3. Zero rows affected → exception → retry or 409.
  4. Pessimistic: SELECT ... FOR UPDATE locks the row.
  5. Other lockers wait until commit or timeout.

Example

@Entity
class Product {
    @Id Long id;
    BigDecimal price;
    @Version long version;
}

interface SeatRepository extends JpaRepository<Seat, Long> {
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "3000"))
    @Query("select s from Seat s where s.id = :id")
    Seat lockById(@Param("id") long id);
}

@Retryable(retryFor = ObjectOptimisticLockingFailureException.class, maxAttempts = 3)
@Transactional
public void changePrice(long id, BigDecimal p) { repo.findById(id).orElseThrow().setPrice(p); }

Common mistakes

  • Setting the version manually or not exposing it to clients for long edits.
  • Retrying the whole transaction in the same persistence context (retry must start a new transaction).
  • Pessimistic locks without timeouts, or held during remote calls.
  • Using pessimistic locking everywhere "to be safe".

How to answer in the interview

"Optimistic locking assumes conflicts are rare. I add a Version column; every update includes where version equals the old value and increments it. If someone else changed the row first, zero rows update and an OptimisticLockException is thrown, so I retry or return a conflict. Pessimistic locking takes a row lock up front with select for update, so others wait. I use optimistic for typical web apps and pessimistic for short, high-contention operations like decrementing inventory, always with a lock timeout."

Likely follow-up questions

  • OptimisticLockException in a REST API? Return 409 or 412 with ETag/If-Match, or retry idempotent operations.
  • What does SKIP LOCKED do? Skips locked rows, useful for worker queues.
  • Deadlock prevention? Lock in consistent order, keep transactions short, use timeouts.
