What is the Gateway API, and why are teams moving to it from Ingress now?

Kubernetes · concept · levels entry, mid, senior

In one line

The Gateway API is the role-oriented successor to Ingress: GatewayClass (provider), Gateway (platform team: listeners, TLS, allowed namespaces) and HTTPRoute/GRPCRoute (app teams), with built-in header matching, traffic weights, redirects and mirroring; adoption accelerated after the community ingress-nginx controller was retired in March 2026.

Detailed explanation

Ingress was deliberately minimal: host and path rules plus TLS. Everything else (rewrites, canary weights, header routing, timeouts, auth) was added through controller-specific annotations, so Ingress YAML was tied to one controller, and one object mixed concerns of the platform team (certificates, load balancer) and app teams (routes).

The Gateway API, developed by Kubernetes SIG Network with its core HTTP features stable since v1.0, splits responsibility:

  • GatewayClass: cluster-scoped, defines which controller implements gateways (for example Envoy Gateway, Istio, Cilium, Traefik, NGINX Gateway Fabric, cloud implementations).
  • Gateway: owned by the platform team; defines listeners (ports, protocols, hostnames), TLS certificates and which namespaces may attach routes.
  • Routes: HTTPRoute and GRPCRoute, plus TLS and TCP routes in some implementations, created by app teams in their own namespaces and attached to a Gateway with parentRefs. Cross-namespace references to backends require an explicit ReferenceGrant.

Features that needed annotations are now in the spec: matching on headers, methods and query parameters, weighted backendRefs for canaries, redirects, URL rewrites, header modification and request mirroring. That makes configurations more portable across implementations, and conformance tests show which features each supports.

The migration pressure in 2026 is practical: the ingress-nginx project was retired with best-effort maintenance ending in March 2026, so clusters relying on it no longer receive security fixes and must change controllers anyway. Many teams choose to move to Gateway API at the same time, using tools such as ingress2gateway to translate existing Ingresses.

How it works

  1. Provider installs a controller and GatewayClass.
  2. Platform team creates a Gateway with HTTPS listener and certificate.
  3. Gateway allows routes from labelled namespaces.
  4. App team creates an HTTPRoute with matches and weighted backends.
  5. Controller programmes the data plane; route status shows acceptance.

Example

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: orders, namespace: shop }
spec:
  parentRefs: [ { name: public, namespace: infra } ]
  hostnames: [ api.example.com ]
  rules:
  - matches: [ { path: { type: PathPrefix, value: /orders } } ]
    backendRefs:
    - { name: orders-v1, port: 80, weight: 90 }
    - { name: orders-v2, port: 80, weight: 10 }

Common mistakes

  • Assuming every implementation supports every extended feature; check conformance.
  • Forgetting ReferenceGrant for cross-namespace backends.
  • Not reading route status conditions when a route "does nothing".
  • Big-bang migration of all Ingresses at once.

How to answer in the interview

"The Gateway API is the successor to Ingress. It's role-oriented: the provider supplies a GatewayClass, the platform team owns Gateways with listeners, certificates and allowed namespaces, and app teams attach HTTPRoutes from their namespaces. Features that needed vendor annotations in Ingress, like header matching, weighted traffic splitting, redirects and mirroring, are part of the spec, so it's more portable. The move accelerated because the community ingress-nginx controller was retired in March 2026, so teams had to switch controllers anyway, and Gateway API is the natural target."

Likely follow-up questions

  • How would you migrate 200 Ingresses? Translate with ingress2gateway, run the new gateway in parallel on a new IP, shift DNS per host, compare metrics.
  • Does Gateway API cover service mesh traffic? Yes, the GAMMA initiative attaches routes to Services for east-west traffic.
  • What is ReferenceGrant? Permission from a target namespace allowing routes in another namespace to reference its Services or Secrets.
