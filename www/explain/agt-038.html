Your agent needs write access to a production database. How do you design this safely?

AI Agents & AIOps · design · levels senior, lead

In one line

Never give a generic execute-SQL write tool; expose specific operations as tools with parameterised queries, a least-privilege database role, validation and business rules in code, approval and row limits for bulk or destructive changes, transactions, audit columns and reversible changes, and staging tests with realistic data.

Detailed explanation

A free-form SQL tool with write access means a single hallucinated or injected statement, an UPDATE without WHERE, a DELETE on the wrong table, a DROP, could damage data at scale in milliseconds. And because agents read untrusted content, an attacker might steer the model toward exactly such a query. So the principle is: the model chooses intents; code performs writes.

Specific tools: write operations are exposed as narrow, task-shaped tools such as update_customer_address(customer_id, address) or cancel_order(order_id, reason), implemented in application code with parameterised queries or the existing service layer. Better still, call the existing business API that humans use, so all domain rules, events and side effects are applied consistently.

Validation and business rules: each tool validates inputs (formats, ranges, existence) and enforces rules, such as only cancelling orders that are not yet shipped, or only changing addresses for the customer the agent is serving.

Least privilege: the database role used by the tools has only the required privileges, for example UPDATE on specific columns of specific tables, no DDL, no access to unrelated schemas. Row-level security can restrict tenants.

Limits and approvals: bulk or destructive operations require human approval and hard limits on rows affected per call; the tool checks the expected count before committing and aborts if it differs.

Safety nets: changes run in transactions; audit columns or tables record which agent run, on behalf of which user, changed what and when; deletes are soft deletes; old values are kept for reversal. Point-in-time recovery backups remain the last line of defence.

Testing: everything is tested in staging with realistic data, including adversarial and edge cases, before production.

How it works

  1. List required write operations; design one tool per operation.
  2. Implement with parameterised queries or existing service APIs.
  3. Validate inputs and enforce business rules in the tool.
  4. Use a least-privilege role; no DDL; row-level security if multi-tenant.
  5. Enforce row limits and approvals for bulk or destructive actions.
  6. Wrap in transactions; write audit records; prefer soft deletes; test in staging.

Example

def cancel_order(order_id: int, reason: str, ctx) -> dict:
    with db.transaction() as tx:
        order = tx.fetch_one(
            "SELECT id, status, customer_id FROM orders WHERE id = %s FOR UPDATE", (order_id,))
        if order is None:
            return {"ok": False, "error": f"Order {order_id} not found"}
        if order.customer_id != ctx.customer_id:
            return {"ok": False, "error": "Order belongs to a different customer"}
        if order.status in ("shipped", "delivered"):
            return {"ok": False, "error": f"Cannot cancel: order is {order.status}. Offer a return instead."}
        rows = tx.execute(
            "UPDATE orders SET status = 'cancelled', cancelled_reason = %s, "
            "updated_by = %s, updated_at = now() WHERE id = %s AND status = %s",
            (reason, f"agent:{ctx.run_id}:on_behalf_of:{ctx.user_id}", order_id, order.status))
        if rows != 1:
            raise RuntimeError("Unexpected row count; rolling back")
    return {"ok": True, "order_id": order_id, "status": "cancelled"}
CREATE ROLE agent_orders_writer NOLOGIN;
GRANT SELECT ON orders TO agent_orders_writer;
GRANT UPDATE (status, cancelled_reason, updated_by, updated_at) ON orders TO agent_orders_writer;

Common mistakes

  • A generic run_sql tool with a privileged account.
  • Bypassing the application layer and its business rules.
  • Hard deletes without audit or backup.
  • No row-count checks on updates.
  • Testing only on tiny, clean datasets.

How to answer in the interview

"I avoid giving the agent a generic execute-SQL tool with write access, because one hallucinated or injected query, like an UPDATE without a WHERE, could damage data at scale. Instead, writes are specific tools like update_customer_address or cancel_order, implemented in code with parameterised queries or the existing service API. Each tool validates inputs and enforces business rules, like only cancelling unshipped orders. The database role is least privilege, only the needed tables and columns, no DDL. Bulk or destructive operations need approval and have row limits. Changes run in transactions with audit columns recording which agent run and user made them, and deletes are soft. Everything is tested in staging with realistic data."

Likely follow-up questions

  • Ad-hoc read queries for analysts? Read-only role on a replica or warehouse, row limits, query timeouts, curated views and masked sensitive columns.
  • Why use existing service APIs? They apply domain rules, events and side effects consistently.
  • How do you reverse an agent change? Use audit records of old values or soft-delete flags, plus point-in-time recovery as a fallback.
