An expensive multi-GPU training job shows only 30 percent GPU utilisation. How do you find the bottleneck?

MLOps · scenario · levels mid, senior

In one line

Low GPU utilisation means the GPUs are waiting; profile the loop to see whether the gap is data loading (CPU preprocessing, slow storage), communication between GPUs or nodes, or synchronisation points such as small batches, logging and evaluation.

Detailed explanation

Don't guess: use the PyTorch Profiler (with TensorBoard or the trace viewer) or NVIDIA Nsight Systems to see a timeline of CPU work, CUDA kernels, data loader waits and NCCL collectives. Also look at simple signals: nvidia-smi dmon utilisation, CPU usage per core, disk and network throughput, and step-time breakdown.

Data loading is the most common culprit. Image decoding and augmentation are CPU-heavy; many small files on network storage cause high latency; a single loader worker can't keep eight GPUs fed. Fixes: increase num_workers, use pin_memory and prefetch_factor, keep workers persistent, move augmentation to the GPU (NVIDIA DALI or torchvision v2 on GPU), cache data on local NVMe, and use sharded sequential formats like WebDataset, Parquet or TFRecord instead of millions of small files.

Communication overhead shows up as long NCCL all-reduce or all-gather kernels. Causes are slow interconnects (no NVLink, no InfiniBand or EFA between nodes), small batches so communication dominates, or no overlap of communication with backward computation. Fixes: better networking, larger per-GPU batch or gradient accumulation, DDP bucket tuning, and checking NCCL is actually using the fast fabric.

Synchronisation points: calling .item() or printing every step forces CPU-GPU sync; frequent checkpointing or evaluation blocks training; tiny kernels with Python overhead underuse the GPU, which torch.compile or CUDA graphs can help.

How it works

  1. Measure step time and utilisation per GPU; check CPU and I/O.
  2. Run a short profile of 20-50 steps.
  3. Test with synthetic data in memory: if utilisation jumps, the input pipeline is the bottleneck.
  4. Test on one GPU versus many: if scaling is poor, look at communication.
  5. Apply fixes one at a time and re-measure throughput (samples per second).
  6. Keep a throughput benchmark in CI for future regressions.

Example

from torch.profiler import profile, schedule, ProfilerActivity, tensorboard_trace_handler
loader = DataLoader(ds, batch_size=64, num_workers=16, pin_memory=True,
                    persistent_workers=True, prefetch_factor=4)
with profile(activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA],
             schedule=schedule(wait=5, warmup=5, active=20),on_trace_ready=tensorboard_trace_handler("./prof")) as p:
    for step, batch in enumerate(loader):
        train_step(batch); p.step()
        if step > 40: break

Common mistakes

  • Adding GPUs when the input pipeline is the bottleneck.
  • Reading millions of small files from network storage.
  • Logging scalars with .item() every step.
  • Ignoring that nodes communicate over standard TCP networking instead of the fast fabric.

How to answer in the interview

"Thirty percent means the GPUs are waiting, so I'd profile with the PyTorch profiler or Nsight Systems rather than guess. A quick test is feeding synthetic data from memory: if utilisation jumps, it's the input pipeline. Then I'd add loader workers, pinned memory and prefetching, move augmentation to the GPU, cache data locally and use sharded formats like WebDataset or Parquet. If scaling across GPUs is the issue, I'd look at NCCL time and the interconnect, increase per-GPU batch or overlap communication. I'd also remove sync points like per-step logging and blocking evaluation."

Likely follow-up questions

  • How does storage affect throughput? Object storage and network file systems have high per-file latency; sharded files, local NVMe caching or high-throughput file systems such as FSx for Lustre help a lot.
  • How do you confirm NCCL uses the fast network? Set NCCL_DEBUG=INFO and check the selected transport.
  • What throughput metric do you track? Samples or tokens per second per GPU, and model FLOPs utilisation.
