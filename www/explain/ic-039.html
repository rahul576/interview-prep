What is Terragrunt, and what problems does it solve?

Infrastructure as Code · concept · levels mid

In one line

Terragrunt is a thin wrapper around Terraform and OpenTofu that keeps backend, provider and module configuration DRY across many environments, models dependencies between stacks, and runs many stacks in order, at the cost of another tool to learn.

Detailed explanation

With plain Terraform, a typical estate has directories like prod/eu-west-1/network, prod/eu-west-1/app, dev/..., each containing nearly identical backend blocks, provider blocks and a module call. Backend blocks cannot use variables, so every directory hard-codes its bucket and key, and copy-paste errors such as two stacks sharing a state key are easy to make.

Terragrunt addresses this with HCL files of its own:

  • A root configuration (in current versions conventionally root.hcl; older setups used a root terragrunt.hcl) defines remote_state once, with the state key derived from the folder path via path_relative_to_include(), and generate blocks that write backend.tf and provider.tf into each stack.
  • Each leaf terragrunt.hcl includes the root, sets terraform { source = "git::...//modules/app?ref=v1.4.0" } and passes inputs. Environment folders therefore contain only what differs: module version and inputs.
  • dependency blocks read outputs from other stacks (with mock_outputs for planning before the dependency exists), and Terragrunt orders execution accordingly.
  • Running across many stacks: historically terragrunt run-all plan; newer releases use terragrunt run --all plan. It plans or applies every stack under a directory in dependency order, in parallel where possible.
  • Hooks, read_terragrunt_config for shared variables per environment or region, and newer stacks features for generating units.

The trade-offs: another binary to install, version and debug; error messages pass through two layers; run --all apply across production is powerful but has a large blast radius; and newer Terraform/OpenTofu features (better module patterns, -chdir, HCP Terraform workspaces and Stacks, OpenTofu early variable evaluation in backends) cover part of the original motivation. Teams adopt Terragrunt mainly when they have many accounts, regions and environments with the same structure.

How it works

  1. Terragrunt reads the leaf terragrunt.hcl and its includes.
  2. It downloads the module source into a cache directory.
  3. It generates backend and provider files.
  4. It resolves dependencies and injects inputs as variables.
  5. It runs the Terraform/OpenTofu command, across many units if requested.

Example

# root.hcl
remote_state {
  backend = "s3"
  generate = { path = "backend.tf", if_exists = "overwrite" }
  config = {
    bucket       = "acme-tfstate-${local.account}"
    key          = "${path_relative_to_include()}/terraform.tfstate"
    region       = "eu-west-1"
    encrypt      = true
    use_lockfile = true
  }
}
# prod/eu-west-1/app/terragrunt.hcl
include "root" { path = find_in_parent_folders("root.hcl") }

terraform {
  source = "git::https://git.acme.local/infra-modules.git//app?ref=v1.4.0"
}

dependency "network" {
  config_path = "../network"
  mock_outputs = { private_subnet_ids = ["subnet-mock"] }
}

inputs = {
  instance_count = 4
  subnet_ids     = dependency.network.outputs.private_subnet_ids
}
cd prod/eu-west-1 && terragrunt run --all plan

Common mistakes

  • Using run --all apply on production without reviewing each plan.
  • Leaf files that pin different module refs by accident.
  • Forgetting mock outputs, breaking plans for new environments.
  • Adopting Terragrunt for a small estate where plain Terraform is enough.

How to answer in the interview

"Terragrunt is a thin wrapper around Terraform and OpenTofu. With many environments, plain Terraform repeats backend config, provider blocks and module calls in every directory. Terragrunt keeps that DRY: a root file generates backend and provider config for every stack, deriving the state key from the folder path, and each environment folder only declares the module version and its inputs. Dependency blocks pass outputs between stacks, and run-all, now run --all, plans or applies many stacks in dependency order. The trade-off is another tool to learn and debug, and newer Terraform features cover some of these needs."

Likely follow-up questions

  • How does Terragrunt keep module versions consistent? Version refs centralised in shared HCL (e.g. per-environment env.hcl) read by every leaf, promoted from dev to prod.
  • Does Terragrunt work with OpenTofu? Yes, it supports both.
  • What are mock_outputs for? Planning a stack before its dependency has been applied.
