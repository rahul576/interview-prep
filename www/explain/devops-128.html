How does HashiCorp Vault work, and what are dynamic secrets?

DevSecOps · concept · levels mid, senior

In one line

HashiCorp Vault centralises secrets: clients log in via auth methods (Kubernetes, OIDC, AWS IAM), policies grant path access, and secrets engines store static secrets or generate dynamic secrets, short-lived credentials created on demand with a lease that is revoked automatically; it starts sealed, is ideally auto-unsealed with a KMS, and audit-logs every request.

Detailed explanation

Vault replaces secrets scattered across config files and CI variables with one API. Every client first authenticates using a method that fits its identity: a Kubernetes service account token, an AWS IAM role, OIDC for humans, AppRole for legacy apps. Vault returns a token with attached policies, written in HCL, that allow specific capabilities (read, create, update) on specific paths.

Secrets engines handle the data: KV v2 for versioned static secrets, database for dynamic DB credentials, AWS/Azure/GCP for dynamic cloud credentials, PKI for issuing short-lived certificates.

Dynamic secrets are the key idea. Instead of one shared database password living for years, Vault connects to the database with an admin account and, when an app asks, creates a unique user with a defined role and a lease of, say, one hour. The app renews the lease while running; when it expires or is revoked, Vault drops the user. Leaks become short-lived and each credential is traceable to one client.

Kubernetes delivery: the Vault Agent Injector adds a sidecar that logs in and renders secrets to a shared volume; the Secrets Store CSI provider mounts them as files; the Vault Secrets Operator syncs them into Kubernetes Secrets.

Operations: Vault encrypts storage with a key that is itself protected; on start it is sealed and must be unsealed with Shamir key shares or, better, auto-unseal via AWS KMS, Azure Key Vault or an HSM. Run it highly available with integrated Raft storage, and enable audit devices.

How it works

  1. Pod starts → agent authenticates with its service account JWT.
  2. Vault verifies it with the Kubernetes API and maps it to a role and policies.
  3. Agent requests database/creds/orders-app.
  4. Vault creates a DB user with a lease and returns credentials.
  5. Agent renders them to a file, renews the lease, and re-renders on rotation.
  6. Pod deleted → lease expires → user dropped.

Example

vault secrets enable database
vault write database/config/orders plugin_name=postgresql-database-plugin \
  connection_url="postgresql://{{username}}:{{password}}@db:5432/orders" \
  allowed_roles=orders-app username=vault password=...
vault write database/roles/orders-app db_name=orders default_ttl=1h max_ttl=24h \
  creation_statements="CREATE ROLE \"{{name}}\" LOGIN PASSWORD '{{password}}' VALID UNTIL '{{expiration}}'; GRANT SELECT, INSERT ON ALL TABLES IN SCHEMA public TO \"{{name}}\";"
vault read database/creds/orders-app

Common mistakes

  • Using a root token in applications.
  • Apps that read a dynamic secret once and never handle renewal or rotation.
  • A single Vault node with manual unseal and no backups of Raft snapshots.

How to answer in the interview

"Vault centralises secrets. Clients authenticate through auth methods such as Kubernetes service accounts, OIDC or cloud IAM, and policies decide which paths they can use. Besides static KV secrets, it generates dynamic secrets: for example a unique database user per app instance with a one-hour lease, revoked automatically when the lease ends, so leaked credentials quickly become useless and are traceable. In Kubernetes I deliver secrets with the agent injector, CSI provider or Vault Secrets Operator. Vault starts sealed, so I use KMS auto-unseal and a Raft HA cluster, and audit logging records every access."

Likely follow-up questions

  • What if Vault is unavailable? HA cluster across AZs, cached secrets in agents, leases long enough to ride out short outages.
  • Static vs dynamic secrets? Static are stored and rotated; dynamic are generated per request and expire.
  • How does Kubernetes auth work? Vault validates the pod's service account token via TokenReview and maps it to a role.
