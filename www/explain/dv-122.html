What are the typical stages of a CI/CD pipeline?

DevOps & CI/CD · concept · levels entry

In one line

A typical CI/CD pipeline is triggered by a commit or pull request, then builds and unit-tests, runs static analysis and security scans, packages and publishes one versioned artifact, deploys to test or staging for integration tests, and finally deploys to production, automatically or after approval, with a safe rollout strategy.

Detailed explanation

Continuous integration (CI) means every change is merged frequently and automatically verified. Continuous delivery means every verified change is releasable at any time, with a manual decision to deploy; continuous deployment goes further and deploys every passing change to production automatically.

The stages are ordered from fast and cheap to slow and expensive, so most problems are caught in minutes. The trigger is a push, a pull request, a tag or a schedule. Build compiles the code and runs unit tests, usually in seconds to a few minutes. Quality and security checks follow: linting, static analysis (for example SonarQube), SCA dependency scanning, secret scanning and sometimes SAST. Many of these run in parallel.

If they pass, the pipeline packages an artifact, typically a container image tagged with the commit SHA, scans it, ideally signs it and produces an SBOM, then publishes it to a registry. The same artifact is deployed to a test or staging environment, where integration, end-to-end, contract or smoke tests run. Production deployment uses a rolling, blue-green or canary strategy, with health checks and automatic rollback if error rates rise. Post-deploy smoke tests and monitoring close the loop.

How it works

  1. Trigger on push or pull request; check out code.
  2. Build and run unit tests.
  3. Lint, static analysis, dependency and secret scans (in parallel).
  4. Build, scan, sign and push the image tagged with the SHA.
  5. Deploy to staging; run integration and smoke tests.
  6. Approval gate (continuous delivery) or automatic promotion (continuous deployment).
  7. Canary or rolling deploy to production with automatic rollback.

Example

# GitHub Actions outline
on: [push, pull_request]
jobs:
  build-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: ./gradlew build test
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: ./gradlew dependencyCheckAnalyze
  publish:
    needs: [build-test, scan]
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t $REGISTRY/orders:${{ github.sha }} . && docker push $REGISTRY/orders:${{ github.sha }}
  deploy-staging:
    needs: publish
    environment: staging
    runs-on: ubuntu-latest
    steps:
      - run: ./deploy.sh staging ${{ github.sha }} && ./smoke-test.sh staging
  deploy-prod:
    needs: deploy-staging
    environment: production   # requires reviewer approval
    runs-on: ubuntu-latest
    steps:
      - run: ./deploy.sh prod ${{ github.sha }}

Common mistakes

  • Rebuilding the artifact for each environment.
  • Running slow end-to-end tests before fast unit tests.
  • No rollback plan or post-deploy verification.
  • Security scans that only warn and are ignored.

How to answer in the interview

"A pipeline is triggered automatically on each commit or pull request. It builds the code and runs unit tests first because they're fast, then static analysis, dependency and secret scanning, often in parallel. If everything passes, it packages one artifact, usually a container image tagged with the commit SHA, scans it and pushes it to a registry. That same artifact is deployed to staging for integration and smoke tests. Finally it goes to production, automatically for continuous deployment or after an approval for continuous delivery, using a rolling or canary strategy with automatic rollback if health checks fail."

Likely follow-up questions

  • Which stages run in parallel? Linting, unit tests, static analysis and dependency scans are independent and parallelise well.
  • Delivery vs deployment? Delivery keeps every change releasable with a manual go; deployment releases automatically.
  • How do you verify a production deploy? Smoke tests, health checks and comparing error rate and latency against the previous version.
