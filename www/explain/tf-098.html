An engineer accidentally committed a cloud access key in a tfvars file to a Git repository. What do you do?

Terraform · scenario · levels mid, senior, lead

In one line

Treat the key as compromised immediately: revoke and rotate it first, check audit logs for misuse, then clean the history knowing that does not make it safe, and prevent recurrence with OIDC instead of static keys, a secret store and secret scanning with push protection.

Detailed explanation

Automated scanners watch public repositories and find leaked cloud keys within minutes; internal repositories are also cloned to laptops, CI caches and forks. So the right mindset is not "can we hide it?" but "assume an attacker has it".

Contain. The first action, before discussing anything else, is to deactivate and delete the key in IAM or rotate the Entra client secret, and issue a replacement to whatever legitimately used it. Every minute counts.

Investigate. Search the audit logs — AWS CloudTrail, the Azure activity log and Entra sign-in logs, GCP audit logs — for use of that credential since it was committed: unfamiliar IPs, new regions, created users or keys, launched instances (crypto-mining is common), or data access. Check the billing anomaly reports. If anything looks suspicious, escalate to the security team and follow the incident process, because the attacker may have created persistence.

Clean up. Remove the file and rewrite history with git filter-repo or BFG, force-push and ask collaborators to re-clone; for GitHub, contact support to purge cached views if needed. But this is hygiene, not remediation — clones and forks may still contain the key.

Prevent. Remove the need for static keys: Terraform pipelines authenticate with OIDC federation (GitHub Actions, GitLab, Azure DevOps workload identity), locally engineers use SSO-based short-lived credentials. Secrets live in Vault, Key Vault or Secrets Manager. *.tfvars containing secrets are in .gitignore. Secret scanning with push protection and gitleaks pre-commit hooks block such commits before they reach the server. A blameless postmortem captures the gaps.

How it works

  1. Revoke and rotate the key immediately.
  2. Update legitimate consumers with new credentials or move them to OIDC.
  3. Review audit logs and billing for misuse; escalate if found.
  4. Remove the secret from the repository and rewrite history.
  5. Add push protection, pre-commit scanning and .gitignore rules.
  6. Run a blameless postmortem.

Example

aws iam update-access-key --user-name ci-user --access-key-id AKIA... --status Inactive
aws iam delete-access-key --user-name ci-user --access-key-id AKIA...
aws cloudtrail lookup-events --lookup-attributes AttributeKey=AccessKeyId,AttributeValue=AKIA... --max-results 50

git filter-repo --path envs/prod.tfvars --invert-paths
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.18.4
    hooks:
      - id: gitleaks

Common mistakes

  • Deleting the commit first and rotating later, or not at all.
  • Assuming a private repository makes the leak harmless.
  • Not checking logs, so an attacker's persistence goes unnoticed.
  • Replacing the key with another static key in the same place.

How to answer in the interview

"I treat the key as compromised from the moment it was pushed, because scanners find keys within minutes. First I revoke and rotate it and update whatever used it legitimately. Then I check CloudTrail or the Azure activity log for any use from unexpected places and escalate to security if there's misuse. I remove the file and clean history with git filter-repo, but that doesn't make the key safe, since clones and forks exist. To prevent recurrence, Terraform authenticates with OIDC instead of static keys, secrets live in a secret store, tfvars with secrets are gitignored, and secret scanning with push protection or gitleaks hooks blocks such commits."

Likely follow-up questions

  • Why is deleting the commit not enough? The key has already been copied to clones, forks, caches and possibly attackers.
  • What should the replacement look like? Short-lived credentials via OIDC or SSO, not a new long-lived key.
  • Who do you inform? Security team, key owner and affected service owners, following the incident process.
