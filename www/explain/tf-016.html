When is terraform plan -target acceptable, and why is it dangerous as a habit?

Terraform · concept · levels mid, senior

In one line

-target restricts plan or apply to specific addresses and their dependencies; it is acceptable for exceptional recovery or a chicken-and-egg situation, but as a habit it leaves the configuration partially applied, hides other changes and drift, and signals that the state should be split.

Detailed explanation

Terraform is designed around one idea: the plan reconciles the entire configuration with reality. -target=aws_instance.web breaks that model on purpose. Terraform includes the target and everything it depends on, ignores the rest, and prints a warning that the result may be incomplete and that -target is not for routine use.

There are legitimate cases. Recovery after a failed or interrupted apply, where you need to fix one resource before the rest can plan. Provider bugs where one resource must be replaced alone. Bootstrapping dependencies, the classic being creating a Kubernetes cluster first so a Kubernetes or Helm provider that needs the cluster endpoint can be configured in a second full apply. And occasionally an emergency fix during an incident, followed by a full plan.

As a routine habit it is dangerous. The state no longer matches the code as a whole: some changes are applied, others are pending, and the next full plan contains surprises, possibly destructive ones, that nobody connects to the original change. It hides drift and other people's pending changes, because you never see the full plan. It breaks the guarantee that what is in Git is what is deployed, and makes reviews meaningless when the plan reviewers see differs from what someone applied. Dependent resources that should have updated (for example a security group referencing a changed CIDR) stay stale.

If engineers regularly need -target because full plans are slow, risky or blocked by unrelated failures, the real problem is a state that is too large or coupled. Split it into smaller root modules by layer or ownership, with clear interfaces.

How it works

  1. Terraform builds the full graph.
  2. It prunes to the targets and their dependencies (not dependents).
  3. Only those nodes are planned and applied.
  4. A warning reminds you the result is partial.
  5. A follow-up full plan is needed to converge.

Example

# Acceptable: bootstrap cluster, then converge everything
terraform apply -target=module.aks
terraform apply            # full plan, reviewed, should now succeed

# Detect in CI: fail jobs that pass -target for production
if grep -q -- "-target" <<< "$TF_CLI_ARGS $TF_CLI_ARGS_plan $TF_CLI_ARGS_apply"; then
  echo "-target is not allowed in production pipelines"; exit 1
fi

Common mistakes

  • Using -target to skip "unrelated" failing resources.
  • Not running a full plan afterwards.
  • Using it to apply only "my part" of a shared state.
  • Hiding it in wrapper scripts so reviewers never notice.

How to answer in the interview

"-target restricts plan or apply to specific resources and what they depend on. It's acceptable in exceptional situations: recovering from a failed apply, working around a provider bug, or a chicken-and-egg problem like creating a cluster before configuring a provider that needs its endpoint, always followed by a full plan. As a habit it's dangerous: the configuration ends up partially applied, so state and code drift apart and the next full plan brings surprises, and it hides other pending changes and drift. Terraform itself warns it's not for routine use. If people need it regularly, the configuration is too big or coupled and should be split into smaller states."

Likely follow-up questions

  • How do you detect -target in production CI? Pipelines control the command line; reject extra args, and alert on applies not run by the pipeline identity.
  • Does -target include dependents? No, only the targets and their dependencies.
  • Better solution for providers needing cluster endpoints? Separate states or Stacks with deferred changes.
