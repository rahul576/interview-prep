What is the heap, and how is it different from the stack?

JVM & Performance · concept · levels entry

In one line

The heap is one large area shared by all threads where every object and array is allocated and the GC reclaims memory; the stack is per thread, holding a frame per method call with locals, primitives and references, freed automatically on return; the heap fails with OutOfMemoryError, the stack with StackOverflowError.

Detailed explanation

Heap. Created when the JVM starts, sized with -Xms (initial) and -Xmx (maximum). Every new places an object here, along with all its fields, including primitive fields. Because it is shared, any thread with a reference can access an object, so mutable shared objects need synchronisation. Memory is reclaimed by the garbage collector once objects are unreachable. Allocation is fast (pointer bump in a thread-local buffer), but collection costs CPU and pauses. When live objects exceed the maximum: OutOfMemoryError: Java heap space.

Stack. Each thread has its own stack, typically around 512 KB to 1 MB for platform threads (-Xss). Calling a method pushes a frame with the method's parameters, local variables (primitives stored directly, objects as references), an operand stack and return information. When the method returns, the frame is popped, so memory is reclaimed instantly with no GC. Access is very fast and thread-confined: no other thread can see your local variables. Infinite or very deep recursion exceeds the stack: StackOverflowError.

Example. In Order o = new Order() inside a method, the variable o (a reference) is in the current frame on the stack, while the Order object with its fields is on the heap. If you pass o to another method, the reference is copied into the new frame; both point to the same heap object.

Nuances. The JIT's escape analysis can avoid heap allocation for objects that never leave a method (scalar replacement), but you cannot control that. Virtual threads have small stacks that grow and are stored on the heap when the thread is parked.

How it works

  1. Thread starts; the JVM creates its stack.
  2. Method call: a frame with locals is pushed.
  3. new allocates the object on the heap; the frame keeps a reference.
  4. Method returns: the frame is popped immediately.
  5. Unreferenced heap objects are reclaimed by the GC later.

Example

public class Demo {
    static int sum(int a, int b) {     // a, b, result: stack frame
        int result = a + b;
        return result;
    }
    public static void main(String[] args) {
        Order o = new Order("A-1", 3); // o on stack; Order object on heap
        int total = sum(2, 3);         // new frame pushed, popped on return
        recurse(0);                    // eventually StackOverflowError
    }
    static void recurse(int n) { recurse(n + 1); }
}
java -Xms512m -Xmx512m -Xss1m Demo

Common mistakes

  • "Primitives are always on the stack" (fields of objects are on the heap).
  • "Objects are passed by reference" (references are passed by value).
  • Fixing recursion bugs by increasing -Xss.
  • Thinking local variables make the referenced objects thread-safe.

How to answer in the interview

"The heap is one large memory area shared by all threads, where every object and array is allocated with new. It's managed by the garbage collector, sized with Xms and Xmx, and when it's full you get OutOfMemoryError: Java heap space. The stack is per thread: each method call pushes a frame with its local variables, primitives and references to heap objects, and the frame is popped automatically when the method returns, so no GC is involved. Stacks are small, set with Xss, very fast and thread-confined, and deep recursion gives StackOverflowError. For example in Order o = new Order(), the reference o is on the stack and the Order object is on the heap."

Likely follow-up questions

  • Can objects ever be allocated on the stack? Not by the programmer; the JIT may eliminate allocations via escape analysis and scalar replacement.
  • Why are local variables thread-safe? Each thread has its own stack, so no other thread can access them.
  • What determines how deep recursion can go? Stack size and frame size of each call.
