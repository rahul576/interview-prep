What is auto-configuration in Spring Boot?

Spring Boot · concept · levels mid

In one line

Auto-configuration is a set of ordinary @Configuration classes that Spring Boot applies automatically, loaded from META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports and guarded by conditions such as @ConditionalOnClass, @ConditionalOnProperty and @ConditionalOnMissingBean, so they back off when you define your own beans.

Detailed explanation

@SpringBootApplication combines @SpringBootConfiguration, @ComponentScan and @EnableAutoConfiguration. The last one imports every auto-configuration class listed in the AutoConfiguration.imports file of each jar on the classpath. Before Spring Boot 2.7 these were listed under the EnableAutoConfiguration key in META-INF/spring.factories; since Boot 3.0 only the imports file is supported for auto-configurations. Classes are annotated with @AutoConfiguration, which also supports before and after ordering.

Each auto-configuration is a normal configuration class, but guarded by conditions evaluated at startup. DataSourceAutoConfiguration uses @ConditionalOnClass so it applies only when DataSource and embedded database types are present; feature flags use @ConditionalOnProperty; and nearly every bean method uses @ConditionalOnMissingBean, so if your application defines its own DataSource or ObjectMapper, Boot's default steps aside. Auto-configurations are processed after user configuration, which is what makes the back-off reliable.

Settings come from type-safe @ConfigurationProperties classes bound to application.yml (for example spring.datasource.*), so most customisation needs only properties. When something surprises you, the conditions evaluation report (--debug, or the Actuator conditions endpoint) lists positive and negative matches with the reason for each. You can switch auto-configurations off with exclude on @SpringBootApplication or spring.autoconfigure.exclude.

How it works

  1. @EnableAutoConfiguration triggers an ImportSelector that reads all AutoConfiguration.imports files.
  2. Candidate classes are filtered early by cheap class conditions and sorted by before/after order.
  3. User configuration and component-scanned beans are registered first.
  4. Each auto-configuration's conditions are evaluated; matching ones register beans.
  5. @ConditionalOnMissingBean skips beans the user already defined.
  6. Properties bind to @ConfigurationProperties classes to customise the beans.

Example

@AutoConfiguration
@ConditionalOnClass(AuditClient.class)
@EnableConfigurationProperties(AuditProperties.class)
public class AuditAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean
    @ConditionalOnProperty(prefix = "acme.audit", name = "enabled", matchIfMissing = true)
    AuditClient auditClient(AuditProperties props) {
        return new AuditClient(props.getUrl());
    }
}
# src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
com.acme.audit.AuditAutoConfiguration

Common mistakes

  • Still registering auto-configurations in spring.factories with Boot 3.
  • Picking up an auto-configuration through component scanning instead of the imports file, which breaks ordering and back-off.
  • Using @ConditionalOnBean in user configuration, where ordering is not guaranteed.
  • Guessing instead of reading the conditions report.

How to answer in the interview

"@SpringBootApplication includes @EnableAutoConfiguration, which imports all classes listed in the AutoConfiguration.imports file of every jar; older versions used spring.factories. Each one is an ordinary configuration class guarded by conditions: OnClass, so DataSource configuration only applies when a driver is present; OnProperty for feature flags; and OnMissingBean, so if I define my own bean Boot backs off. They are customised through ConfigurationProperties bound to application.yml. I check decisions with --debug or the conditions endpoint and exclude ones I don't want."

Likely follow-up questions

  • How do you write your own? An @AutoConfiguration class with conditions, listed in the imports file, packaged as a starter.
  • Why do user beans win? User configuration is processed before auto-configuration, and @ConditionalOnMissingBean checks for them.
  • How to test it? ApplicationContextRunner with different classpaths and properties.
