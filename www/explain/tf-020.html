What happens internally when you run terraform plan?

Terraform · concept · levels mid, senior

In one line

terraform plan loads configuration, modules and providers, takes the state lock, refreshes resources from cloud APIs, builds and walks a dependency graph evaluating expressions and data sources, asks providers to plan each change (create, update, replace, destroy), running in parallel (default 10), and prints or saves the plan.

Detailed explanation

Understanding the internals explains slow plans, odd diffs and errors. Terraform is a graph engine plus provider plugins that talk to APIs over gRPC.

First, loading: Terraform parses all .tf files in the root module and installed child modules (from .terraform/modules), checks required_version, and starts provider plugins at the versions recorded in .terraform.lock.hcl. It loads the state from the backend and acquires the lock.

Then it builds the dependency graph: nodes are resources, data sources, variables, locals, outputs, modules and providers; edges come from references and depends_on. The graph is walked in dependency order. For each managed resource in state, Terraform calls the provider's ReadResource to refresh the current object from the API, which is how drift is detected. Data sources are read when their arguments are known; otherwise they are deferred to apply.

For every resource, Terraform compares the desired configuration with the refreshed state and calls the provider's PlanResourceChange. The provider decides the action: no-op, create, update in place, or replace when an argument marked ForceNew changed (shown as "forces replacement"), and it fills in values that will only be known after apply. Resources in state but not in configuration are planned for destroy, unless a removed block says otherwise; moved and import blocks are applied to the plan as well. Checks and conditions are evaluated.

The walk runs with up to 10 concurrent operations by default, controlled by -parallelism. Finally Terraform renders the summary ("Plan: 2 to add, 1 to change, 0 to destroy"), optionally writes a plan file with -out, and releases the lock.

How it works

  1. Parse configuration and modules; start provider plugins; load state; lock.
  2. Build the dependency graph.
  3. Refresh managed resources via provider read calls.
  4. Evaluate expressions and read data sources in graph order.
  5. Provider plans each resource change; compute replace and unknown values.
  6. Output summary, optionally save plan; unlock.

Example

terraform plan -out=tfplan -parallelism=10
TF_LOG=DEBUG terraform plan 2> plan-debug.log   # shows provider gRPC calls
terraform graph -type=plan | dot -Tsvg > graph.svg

Common mistakes

  • Thinking plan only reads files and does not call cloud APIs.
  • Ignoring "forces replacement" markers.
  • Raising parallelism without considering API rate limits.
  • Huge states where refresh dominates plan time.

How to answer in the interview

"Terraform first loads the configuration, modules and provider plugins and acquires the state lock. It then refreshes: for every resource in state it asks the provider to read the current object from the API, so drift is detected. Next it builds a dependency graph of resources, data sources, variables and outputs and walks it, evaluating expressions and reading data sources. For each resource it compares desired configuration with refreshed state and asks the provider to plan the change: create, update in place, replace or destroy, filling in values known after apply. The walk runs in parallel, ten by default via -parallelism. Finally it prints the summary and optionally saves the plan."

Likely follow-up questions

  • Why can refresh be slow and what can you do? Hundreds of API reads; split state, avoid huge data sources, use -refresh=false only carefully.
  • What decides replace versus update? The provider schema: ForceNew arguments require replacement.
  • Where do unknown values come from? Provider-computed attributes not available until the object exists.
