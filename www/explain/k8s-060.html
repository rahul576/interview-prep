A Java pod is OOMKilled although the JVM heap is set well below the container memory limit. Why?

Kubernetes · scenario · levels mid, senior, lead

In one line

The memory limit applies to the whole process, not just the heap: metaspace, thread stacks, code cache, GC structures, direct buffers and native libraries add up, so the cgroup OOM killer ends it (exit code 137); measure with Native Memory Tracking, size heap with MaxRAMPercentage and leave headroom.

Detailed explanation

-Xmx limits only the Java heap. A JVM also uses metaspace for class metadata (large with frameworks like Spring), a stack per thread (often 512 KB to 1 MB reserved each, so 400 threads add hundreds of MB), the JIT code cache, GC data structures (G1 regions and remembered sets), direct ByteBuffers used by Netty, gRPC and NIO, memory-mapped files, and allocations by native libraries (compression, TLS, JNI). glibc malloc arenas can also inflate resident memory with many threads.

The kernel accounts all of this, plus page cache for written files, against the container's cgroup memory limit. When the cgroup hits the limit and cannot reclaim, the kernel OOM killer terminates the process. Kubernetes reports OOMKilled with exit code 137 (128 + SIGKILL). The JVM never sees an OutOfMemoryError, which is why the heap "looked fine".

Modern JVMs (Java 10+, backported to 8u191) are container-aware: they read the cgroup limit. Instead of a fixed -Xmx, use -XX:MaxRAMPercentage around 70-75 percent of the limit, which scales automatically when the limit changes and leaves room for non-heap. Cap -XX:MaxDirectMemorySize and -XX:MaxMetaspaceSize where appropriate, and reduce oversized thread pools. Native Memory Tracking (-XX:NativeMemoryTracking=summary plus jcmd <pid> VM.native_memory summary) shows exactly where memory goes, and container metrics like container_memory_working_set_bytes show what the kernel sees.

How it works

  1. Confirm OOMKilled and exit code 137 in kubectl describe pod.
  2. Compare working set over time with the limit.
  3. Enable NMT and break down heap vs non-heap.
  4. Set MaxRAMPercentage, cap direct memory, fix thread counts.
  5. Set the memory request equal or close to the limit, with headroom above real peak.
  6. Watch for steady growth that suggests a native leak.

Example

containers:
  - name: orders
    image: registry.example.com/orders:3.2
    env:
      - name: JAVA_TOOL_OPTIONS
        value: >-
          -XX:MaxRAMPercentage=70 -XX:MaxDirectMemorySize=256m
          -XX:NativeMemoryTracking=summary
    resources:
      requests: { memory: 3Gi, cpu: "1" }
      limits: { memory: 3Gi }
kubectl exec orders-6f9 -- jcmd 1 VM.native_memory summary | head -30

Common mistakes

  • Setting -Xmx equal to the container limit.
  • Ignoring thread count and direct buffers.
  • Raising the limit repeatedly without measuring.
  • Running Java versions that are not container-aware.

How to answer in the interview

"The cgroup limit applies to the whole JVM process, not just the heap. Besides the heap there's metaspace, a stack per thread, code cache, GC structures, direct buffers from Netty or NIO and native libraries. A 2 GB heap with hundreds of threads can need 3 GB, so the kernel OOM killer ends it with exit code 137 and the JVM never throws OutOfMemoryError. I'd measure with Native Memory Tracking and container working-set metrics, size the heap with MaxRAMPercentage around 70 percent, cap direct memory, trim thread pools and leave headroom in the limit."

Likely follow-up questions

  • Leak or undersized limit? A leak keeps growing over time regardless of load; an undersized limit plateaus just above the limit under normal load.
  • Why exit code 137? 128 plus signal 9, SIGKILL.
  • Does page cache count? It is charged to the cgroup but is reclaimable; working set excludes inactive file cache.
