How does MCP handle long-running operations, progress and cancellation?

MCP Servers · concept · levels mid, senior

In one line

MCP handles long operations with progress notifications tied to a progress token, cancellation notifications referencing the request id, and Tasks, durable handles the client polls for status and results (experimental in 2025-11-25, an official extension in 2026-07-28), backed by sensible client timeouts.

Detailed explanation

Progress. A client that wants updates includes a progressToken in the request's _meta. The server then sends notifications/progress messages carrying the token, a progress value, an optional total and an optional human-readable message ("Indexed 4,000 of 10,000 files"). Progress values must increase. Hosts display them, and receiving progress can reset the client's timeout, though clients should still enforce a maximum overall timeout.

Cancellation. Either side can cancel an in-flight request with notifications/cancelled, giving the requestId and an optional reason. The receiver should stop the work if possible, free resources and not send a response. Cancellation can race with completion, so both sides must tolerate a response arriving after a cancel, or a cancel for an unknown request.

Tasks. Progress and cancellation still assume the original request stays open. For work taking many minutes, such as a data export, a large migration or a test-suite run, connections drop, laptops sleep, and load balancers time out. The Tasks feature, introduced as experimental in 2025-11-25, lets a request be task-augmented: the server immediately returns a durable task handle (id, status, poll interval), the work continues server-side, and the client later polls for status and fetches the result with task methods (get, result, list and cancel), even from a new connection. Tasks have statuses like working, input required, completed, failed and cancelled, plus a time-to-live after which results are discarded. Per this question's reference material, 2026-07-28 moved Tasks out of the core into an official extension, negotiated through capabilities.

Timeouts remain essential: clients set per-request timeouts, and long work should become a task rather than a long-held request.

How it works

  1. Client sends request with _meta.progressToken (or as a task).
  2. Server emits progress notifications while working.
  3. User aborts → client sends notifications/cancelled; server stops.
  4. For long jobs, server returns a task handle; client polls task status at the suggested interval.
  5. On completion, client fetches the result; on expiry, the result is gone.

Example

{"jsonrpc":"2.0","id":9,"method":"tools/call","params":{
  "name":"export_report","arguments":{"month":"2026-10"},
  "_meta":{"progressToken":"exp-9"}}}

{"jsonrpc":"2.0","method":"notifications/progress",
 "params":{"progressToken":"exp-9","progress":35,"total":100,"message":"Aggregating orders"}}

{"jsonrpc":"2.0","method":"notifications/cancelled",
 "params":{"requestId":9,"reason":"User cancelled"}}

Common mistakes

  • Holding a 20-minute request open over HTTP instead of using a task.
  • Ignoring cancellation, so cancelled work keeps consuming resources.
  • Sending progress values that go backwards.
  • No absolute timeout on the client, so a hung server blocks forever.

How to answer in the interview

"For operations that take a while, the client includes a progress token and the server sends progress notifications with that token, current progress, total and a message, which the host can display and which can reset timeouts. Either side can cancel an in-flight request with a cancellation notification; the receiver should stop and not respond. For really long work, like a twenty-minute export, Tasks let the server return a durable handle immediately; the client polls for status and fetches the result later, surviving connection drops. Tasks were experimental in 2025-11-25 and became an official extension in 2026-07-28. Clients still enforce timeouts."

Likely follow-up questions

  • Why a task handle over a long stream? Survives disconnects, restarts and load balancer timeouts, and allows polling from anywhere.
  • Who can cancel a task? The requestor, via the task cancel method, subject to authorisation.
  • How long are results kept? For the task's time-to-live, then discarded.
