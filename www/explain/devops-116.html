What happens when etcd is overloaded or loses quorum, and how do you protect it?

Kubernetes · concept · levels senior, lead

In one line

etcd holds all cluster state and uses Raft, so it needs a quorum (majority); when overloaded the API slows and times out, and when quorum is lost writes fail and the control plane stops, although running pods keep running. Protect it with odd member counts, fast disks, compaction and defragmentation, object limits and regular snapshots.

Detailed explanation

Every Kubernetes object, from Deployments to Secrets to Leases, lives in etcd, and the API server is its only client. etcd replicates a log with Raft: a write is committed only when a majority of members have persisted it with fsync. That makes etcd very sensitive to disk latency; slow disks mean slow commits, missed heartbeats and leader elections.

Overload shows up as high API latency, etcdserver: request timed out, frequent leader changes and lagging controllers. Causes include slow or shared disks, huge object counts (Events, large Secrets), unpaginated LIST calls from bad controllers, and a database near its space quota (default 2 GB), after which a NOSPACE alarm blocks writes.

Losing quorum (two of three members down) means no leader. Nothing can be created, scheduled or updated. But the data plane keeps working: kubelets keep containers running and kube-proxy keeps its rules; nothing self-heals until quorum returns.

How it works

  1. Run 3 or 5 members across failure domains; 3 tolerates 1 failure, 5 tolerates 2.
  2. Put etcd on dedicated, low-latency SSDs; watch etcd_disk_wal_fsync_duration_seconds (p99 under ~10 ms) and etcd_disk_backend_commit_duration_seconds.
  3. Let the API server compact history and run etcdctl defrag member by member to reclaim space.
  4. Limit object growth: short Event TTL, ResourceQuotas on object counts, paginated LISTs.
  5. Take scheduled etcdctl snapshot save backups, encrypted and stored off-cluster, and test restores.
  6. On managed services (EKS, AKS, GKE) the provider does most of this; you still watch API latency and object counts.

Example

ETCDCTL_API=3 etcdctl --endpoints=https://10.0.0.11:2379 \
  --cacert=ca.crt --cert=etcd.crt --key=etcd.key \
  endpoint status --write-out=table      # DB size, leader, raft term
etcdctl alarm list                       # NOSPACE?
etcdctl defrag --endpoints=https://10.0.0.11:2379

Common mistakes

  • Running etcd on network disks shared with noisy workloads.
  • Even member counts, or spreading members across high-latency regions.
  • Defragmenting all members at once, which pauses them together.
  • Never testing that a snapshot can be restored.

How to answer in the interview

"etcd stores all cluster state and needs a Raft majority to commit writes. If it's overloaded, usually from slow disks or too many objects, the API server becomes slow and starts timing out. If it loses quorum, writes fail completely, so nothing can be scheduled or changed, but existing pods keep running. I protect it with three or five members on fast SSDs, monitoring fsync latency and database size, compaction and rolling defrags, limits on object counts, and regular, tested snapshots. On managed Kubernetes most of that is the provider's job."

Likely follow-up questions

  • Why is two members worse than one? Quorum of two is two, so either failure stops the cluster: twice the failure probability with no extra tolerance.
  • What does the NOSPACE alarm do? Blocks writes until you compact, defrag and disarm the alarm.
  • Why not span etcd across regions? Every commit pays cross-region round trips, hurting the whole control plane.
