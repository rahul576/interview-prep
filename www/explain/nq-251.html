What is database sharding?

Databases & SQL · concept · levels mid

In one line

Sharding is horizontal partitioning across separate database servers: each shard holds a subset of rows chosen by a shard key (range, hash or directory), so storage and write throughput scale beyond one machine, at the cost of cross-shard queries, transactions, rebalancing and hotspots.

Detailed explanation

Vertical scaling and read replicas eventually stop helping when writes or total data exceed one primary. Sharding splits the data so each server handles only part of it. Every shard is a full database with its own CPU, memory, disk and usually its own replicas.

Placement strategies:

  • Range-based: customer ids 1 to 10 million on shard 1, and so on, or A to M and N to Z. Simple and good for range scans, but new or popular ranges become hot.
  • Hash-based: hash(customer_id) mod N, or better consistent hashing with many virtual shards, gives an even spread but loses efficient range queries across keys.
  • Directory-based: a lookup service maps each key or tenant to a shard. Most flexible (move a big tenant to its own shard) but the directory must be fast and highly available.

Routing happens in the application (a sharding library), in a proxy layer (Vitess for MySQL, Citus coordinator for PostgreSQL, Apache ShardingSphere), or inside the database: MongoDB, Cassandra, DynamoDB, CockroachDB and YugabyteDB shard natively.

Challenges:

  • Cross-shard queries need scatter-gather and merging; joins across shards are expensive.
  • Cross-shard transactions need two-phase commit or sagas.
  • Global uniqueness and IDs: use UUIDs or Snowflake-style ids rather than per-shard sequences.
  • Rebalancing when adding shards; plan for many logical shards per physical node.
  • Hotspots from skewed keys, such as a very large tenant.

A good shard key is present in most queries, has high cardinality, distributes load evenly and does not change.

How it works

  1. Choose a shard key from access patterns.
  2. Map keys to logical shards (hash or directory), and logical shards to physical servers.
  3. The router computes the shard for each request.
  4. Single-shard queries go to one server; others are scattered and merged.
  5. When capacity runs out, move logical shards to new servers.

Example

// Simple application-level routing by hashed customer id
int LOGICAL_SHARDS = 256;
int logical = Math.floorMod(Long.hashCode(customerId), LOGICAL_SHARDS);
DataSource ds = shardMap.physicalFor(logical);    // e.g. 0-63 -> db1, 64-127 -> db2 ...
try (Connection c = ds.getConnection()) { /* query for this customer */ }
// MongoDB native sharding
sh.shardCollection("shop.orders", { customerId: "hashed" })

Common mistakes

  • Sharding by a monotonically increasing key or timestamp, so all writes hit one shard.
  • Using hash mod N with N = physical servers, forcing most data to move when N changes.
  • Sharding too early, before tuning, caching and replicas.
  • Choosing a key absent from most queries.

How to answer in the interview

"Sharding is horizontal partitioning across separate database servers: each shard holds a subset of rows, for example by a hash of customer id, which lets me scale storage and write throughput beyond one machine. A shard key decides placement, using range, hash or a directory service, and the application or a routing layer sends each query to the right shard. The hard parts are cross-shard queries and transactions, rebalancing when adding shards, and hotspots from skewed keys, so I'd choose a key that most queries use and that spreads load evenly. MongoDB, Cassandra and DynamoDB shard natively, while Vitess and Citus add it to MySQL and PostgreSQL."

Likely follow-up questions

  • What makes a bad shard key? Low cardinality, skewed values, monotonically increasing values, or a key queries rarely include.
  • How do you rebalance? Move logical shards or use consistent hashing so only a fraction of keys move.
  • How do you generate unique ids across shards? UUIDv7 or Snowflake-style ids including a time component and node id.
