When should an agent plan work as an explicit task graph, and how does that help?

AI Agents & AIOps · concept · levels senior, lead

In one line

Use an explicit task graph for large goals: tasks with dependencies, executed by a deterministic engine that runs independent tasks in parallel, tracks progress and resumption per task, replans when assumptions change, and stays inspectable for review and audit.

Detailed explanation

A free-running agent loop works for short tasks, but on large ones, such as migrating 40 services to a new logging library, it tends to lose track of what is done, repeat work or skip steps, and a crash means starting again. Planning as an explicit task graph, a directed acyclic graph (DAG) of tasks, addresses these problems.

The planner, usually the model, breaks the goal into tasks with clear inputs, outputs and dependencies: analyse each service, update its dependency, adjust configuration, run its tests, then run integration tests after all updates. A deterministic execution engine, not the model, runs the graph: tasks without unmet dependencies run in parallel, possibly by sub-agents; dependent tasks wait. Each task has its own status and stored result, so progress is visible, failures are isolated, and execution can resume where it stopped. Workflow engines like Temporal, LangGraph or a simple job table can provide this.

When a task fails or its results invalidate assumptions, for example a service turns out to use a different framework, the planner replans only the affected subgraph rather than starting over. The graph is inspectable: humans can review and approve the plan before execution, see progress during it, and keep it as an audit record. For small tasks the structure is overkill; it pays off when there are many steps, parallelism or long durations.

How it works

  1. Model creates the plan as structured data (tasks, dependencies, done criteria).
  2. Plan validated (acyclic, tools available) and optionally approved.
  3. Engine schedules ready tasks; workers execute them.
  4. Results and statuses persisted per task.
  5. On failure or new information, planner revises affected tasks.
  6. Final verification task checks overall success.

Example

{
  "goal": "Migrate services to logging lib v3",
  "tasks": [
    {"id": "analyse-orders",  "deps": [], "done": "report of logging usage"},
    {"id": "analyse-billing", "deps": [], "done": "report of logging usage"},
    {"id": "update-orders",   "deps": ["analyse-orders"],  "done": "PR with passing unit tests"},
    {"id": "update-billing",  "deps": ["analyse-billing"], "done": "PR with passing unit tests"},
    {"id": "integration",     "deps": ["update-orders", "update-billing"], "done": "e2e suite green"}
  ]
}

If analyse-billing finds a different framework, only update-billing is replanned.

Common mistakes

  • Letting the model also act as the scheduler, tracking state in its context.
  • Plans with vague tasks and no definition of done.
  • Replanning the whole graph on every failure.
  • Using task graphs for small, simple tasks.

How to answer in the interview

"For larger goals I let the agent produce an explicit task graph: tasks with inputs, outputs and dependencies. A deterministic engine, not the model, runs it, so independent tasks run in parallel, dependent ones wait, and each task has its own status, which makes progress visible and lets us resume after failures. When a task fails or reveals something new, only the affected part is replanned. Humans can review and approve the plan up front and it doubles as an audit trail. For small tasks it's overkill."

Likely follow-up questions

  • Plan going stale? Re-validate assumptions at checkpoints; replan on drift.
  • Which engine? Temporal, LangGraph or an existing workflow system.
  • Parallelism limits? Cap concurrency to respect rate limits and shared resources.
