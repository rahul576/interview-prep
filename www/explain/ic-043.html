How do you enforce policies on Terraform changes with policy as code?

Infrastructure as Code · concept · levels mid

In one line

Policy as code turns rules (encryption, tags, regions, instance types, no open SSH) into automated checks: static scanners (Checkov, Trivy) on code and plan-based policies (OPA/Conftest, Sentinel) on terraform show -json, with advisory and mandatory enforcement levels.

Detailed explanation

Wiki pages listing rules like "all buckets must be encrypted" are ignored under time pressure. Policy as code makes those rules executable and runs them on every change.

Static scanning analyses Terraform source without running it. Checkov and Trivy (which absorbed tfsec) ship hundreds of built-in checks mapped to CIS and other benchmarks: unencrypted storage, public buckets, security groups open to 0.0.0.0/0 on port 22, missing logging, IAM wildcards. They're fast and good for developer feedback in pre-commit. Their limit: they see code, not computed values, and can miss what modules or variables produce.

Plan-based checks evaluate the JSON plan: terraform plan -out=tfplan && terraform show -json tfplan > plan.json. The JSON contains the resolved values after variables, modules, defaults and functions, plus the actions (create, update, delete) for each resource. OPA with Conftest uses Rego policies; HCP Terraform supports Sentinel and OPA natively, and cloud platforms add their own guardrails (AWS SCPs and Config rules, Azure Policy) as a last line of defence at the API.

Typical rules: required tags (owner, cost-center), allowed regions, allowed instance families, encryption on storage, no public IPs on databases, no deletes of protected resource types, cost thresholds.

Enforcement levels make rollout practical. Advisory policies warn but don't block; mandatory policies fail the run (Sentinel also has soft-mandatory, which an authorised person can override). New rules start advisory, teams fix violations, then the rule becomes mandatory. Exceptions are explicit, reviewed and time-limited, for example inline skip comments with justification or exception lists in the policy data.

How it works

  1. Write policies in a repo, versioned and tested.
  2. PR pipeline runs static scanners on code.
  3. Pipeline creates a plan and converts it to JSON.
  4. Policy engine evaluates the JSON; results posted to the PR.
  5. Mandatory failures block merge or apply.

Example

package main

deny contains msg if {
  rc := input.resource_changes[_]
  rc.type == "aws_s3_bucket"
  "create" in rc.change.actions
  not rc.change.after.tags.owner
  msg := sprintf("%s must have an owner tag", [rc.address])
}

deny contains msg if {
  rc := input.resource_changes[_]
  rc.type == "aws_instance"
  not startswith(rc.change.after.instance_type, "t3.")
  not startswith(rc.change.after.instance_type, "m7i.")
  msg := sprintf("%s uses a non-approved instance type", [rc.address])
}
terraform plan -out=tfplan && terraform show -json tfplan > plan.json
conftest test plan.json --policy policy/
checkov -d . --framework terraform

Common mistakes

  • Only scanning code, missing values computed by modules.
  • Making every rule blocking on day one, so teams disable the checks.
  • Policies without tests, which break unexpectedly.
  • Unlimited, undocumented exceptions.

How to answer in the interview

"Policy as code turns rules like every bucket encrypted, every resource has an owner tag, only approved regions and instance types, and no SSH open to the world into automated checks. Static scanners like Checkov or Trivy analyse the Terraform code with hundreds of built-in rules. Plan-based tools evaluate terraform show -json, which includes computed values: OPA with Conftest using Rego, or Sentinel in HCP Terraform. They run on every PR, and policies are either advisory, warning only, or mandatory, blocking the merge, so new rules start soft and become hard once teams comply."

Likely follow-up questions

  • Why is checking the plan JSON more reliable than checking code text? It contains resolved values from variables and modules and the actual actions.
  • How do you test policies? Rego unit tests with opa test and sample plan fixtures.
  • What is the last line of defence? Cloud-native guardrails like SCPs or Azure Policy that apply to every tool.
