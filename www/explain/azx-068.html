Compare Azure CNI Overlay, Azure CNI with pod subnet, Azure CNI powered by Cilium and kubenet on AKS.

Azure Kubernetes (AKS) · concept · levels mid, senior

In one line

Azure CNI Overlay gives pods IPs from a private range outside the VNet (saving address space), Azure CNI with pod subnet gives pods real VNet IPs (directly reachable), Cilium replaces the dataplane with eBPF, and kubenet is legacy, retiring on 31 March 2028.

Detailed explanation

The main question is: must pods be directly reachable from the network, and how much IP space do you have?

Azure CNI Overlay: nodes get IPs from the VNet subnet, but pods get IPs from a separate pod CIDR (for example 10.244.0.0/16) that is not part of the VNet. Traffic between pods is routed by Azure without consuming VNet addresses, and traffic leaving the cluster is SNATed to the node IP. This scales to large clusters with small subnets and is the recommended default. The downside: external systems cannot reach pods directly; they go through a load balancer, ingress or gateway.

Azure CNI with pod subnet (dynamic IP allocation) or the older flat Azure CNI: pods receive real VNet IPs, either from a dedicated pod subnet or the node subnet. Other VNets, on-premises systems and firewalls see actual pod IPs, which some legacy integrations require. It consumes much more address space and needs careful subnet planning.

Azure CNI powered by Cilium is a dataplane choice combined with overlay or pod subnet IPAM. It uses eBPF instead of iptables for routing and network policy, giving better performance at scale, and with Advanced Container Networking Services adds flow observability and FQDN-based policies.

kubenet used a separate pod range with user-defined routes, limited to 400 nodes and lacking some features. It is being retired on 31 March 2028, and clusters should migrate to Azure CNI Overlay, which AKS supports as an in-place upgrade.

How it works

  1. Decide IP strategy: overlay unless pods need direct reachability.
  2. Size the node subnet (nodes plus surge) and pick a pod CIDR that does not overlap with any network.
  3. Choose the dataplane: Cilium for eBPF and network policy.
  4. Create the cluster with matching flags.
  5. Expose services through load balancers or gateways.

Example

az aks create -g rg-net -n aks-prod \
  --network-plugin azure --network-plugin-mode overlay \
  --pod-cidr 10.244.0.0/16 --network-dataplane cilium \
  --vnet-subnet-id $NODE_SUBNET_ID

# Migrate a kubenet cluster to overlay
az aks update -g rg-net -n aks-old --network-plugin azure --network-plugin-mode overlay

Common mistakes

  • Choosing a pod CIDR that overlaps with on-premises or peered ranges.
  • Sizing the subnet for nodes only, forgetting upgrade surge.
  • Using flat CNI by default and running out of IPs.
  • Leaving kubenet clusters until the retirement deadline.

How to answer in the interview

"Overlay gives nodes VNet IPs but pods IPs from a private CIDR outside the VNet, so it saves address space and scales well; outbound pod traffic is translated to the node IP. Pod subnet mode gives pods real VNet IPs so other systems can reach them directly, but uses a lot more IP space. Cilium is the eBPF dataplane, combined with either mode, giving efficient network policy and observability. kubenet retires in March 2028, so I'd migrate those clusters to overlay. My default is overlay with Cilium, unless pods must be directly addressable."

Likely follow-up questions

  • What changes for on-premises callers with overlay? They must use an internal load balancer or gateway, not pod IPs.
  • Can you change from overlay to pod subnet later? Not easily; plan at creation.
  • Why eBPF? Avoids large iptables rule sets, improving performance and visibility.
