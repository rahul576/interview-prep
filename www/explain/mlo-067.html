What are data contracts, and why do ML teams need them?

MLOps · concept · levels mid, senior

In one line

A data contract is an explicit, versioned agreement between data producers and consumers covering schema, semantics, quality, freshness and ownership, enforced automatically in CI and pipelines so producer changes can't silently break features and models.

Detailed explanation

ML models depend not just on a column existing but on what it means: its unit, its allowed values, how nulls are represented, and when it arrives. Producers, such as an application team emitting events or owning an operational database, usually don't know which models use their data. A rename, a change from euros to cents, or filling nulls with zero may pass every technical check, yet the model now receives nonsense and keeps producing confident predictions. This is the silent failure that data contracts target.

A contract typically defines:

  • Schema: fields, types, required or optional, keys.
  • Semantics: descriptions, units, enumerations, valid ranges.
  • Quality expectations: null rates, uniqueness, distribution bounds.
  • Service levels: freshness, delivery time, completeness.
  • Ownership and change process: who owns it, how changes are versioned and announced, deprecation periods.

Contracts are written as code (YAML following a spec such as the Open Data Contract Standard, Protobuf or Avro schemas in a schema registry, or dbt model contracts) and enforced automatically: the producer's CI fails a breaking change, the schema registry rejects incompatible schemas, and consumer pipelines validate data on arrival with tools such as Great Expectations or Soda, quarantining bad batches.

Changes follow semantic versioning: additive changes are minor; removals or meaning changes are major and need a new version and notice, with old and new published in parallel during migration.

How it works

  1. Identify critical datasets feeding production models.
  2. Agree contract content with producer and consumer teams.
  3. Store the contract in Git next to the producer code.
  4. Add compatibility checks in producer CI and schema registry.
  5. Validate on ingestion; alert owners and quarantine on violations.
  6. Manage breaking changes through new versions and deprecation windows.

Example

dataset: payments.transactions
version: 2.1.0
owner: team-payments
fields:
  - { name: transaction_id, type: string, required: true, unique: true }
  - { name: amount, type: decimal(12,2), unit: EUR, min: 0 }
  - { name: status, type: string, enum: [authorised, captured, refunded] }
  - { name: created_at, type: timestamp, timezone: UTC }
quality: { amount_null_rate_max: 0.001 }
sla: { freshness: 15m }
breaking_change_notice: 30d

Common mistakes

  • Writing contracts as wiki pages that nobody enforces.
  • Covering only schema, not units and meaning.
  • Imposing contracts on producers without explaining the value or helping with tooling.
  • Trying to contract every table at once instead of starting with critical ones.

How to answer in the interview

"A data contract is an agreement between the team producing data and the teams consuming it. It defines the schema, the meaning of fields including units and allowed values, quality expectations, freshness and who owns changes. ML teams need it because models break silently: a unit change or nulls filled with zero won't crash a pipeline but will ruin predictions. I'd keep contracts as code, check compatibility in the producer's CI and schema registry, validate data on arrival, and handle breaking changes with new versions and advance notice."

Likely follow-up questions

  • How do you get producer buy-in? Start with a few critical datasets, show past incidents, provide tooling and templates so it's cheap.
  • Contract versus schema registry? A registry enforces structure; a contract adds semantics, quality, SLAs and ownership.
  • What happens on a violation? Block in CI if possible; otherwise quarantine the batch and alert the owner.
