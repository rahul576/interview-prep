How does HashSet work internally, and what is the difference between HashSet, LinkedHashSet and TreeSet?

Collections · concept · levels entry

In one line

HashSet is a HashMap with dummy values, so uniqueness depends on hashCode and equals; LinkedHashSet adds insertion order, and TreeSet is a TreeMap (red-black tree) that keeps elements sorted with O(log n) operations, deciding duplicates by compareTo.

Detailed explanation

A HashSet contains a private HashMap<E, Object>. Every element is stored as a key and the value is a shared constant called PRESENT. add(e) is simply map.put(e, PRESENT) == null, so it returns false if the key was already there. That means all HashSet behaviour, average O(1) add/contains/remove, buckets, load factor 0.75, resizing and treeified buckets, comes from HashMap, and correctness depends on hashCode and equals being implemented consistently.

LinkedHashSet extends HashSet but is backed by a LinkedHashMap, which threads a linked list through the entries. Iteration follows insertion order, with almost the same performance and slightly more memory.

TreeSet is backed by a TreeMap, a red-black tree. Elements are ordered by their natural Comparable order or by a Comparator. Operations are O(log n) and iteration is sorted. Crucially, TreeSet uses compareTo/compare, not equals, to decide whether two elements are duplicates: if compare returns 0, the second element is rejected even if equals says they differ.

Nulls: HashSet and LinkedHashSet allow one null. TreeSet with natural ordering throws NullPointerException, because it must compare the element; a null-tolerant Comparator can allow it.

How it works

  1. HashSet.add(e) → map.put(e, PRESENT).
  2. HashMap spreads e.hashCode(), finds the bucket, checks with equals.
  3. LinkedHashSet additionally links the new entry at the tail.
  4. TreeSet.add(e) → TreeMap.put(e, PRESENT), walking down by comparison and rebalancing.

Example

record Email(String value) {}            // records implement equals/hashCode
Set<Email> seen = new HashSet<>();
seen.add(new Email("a@x.com"));
seen.add(new Email("a@x.com"));          // false, duplicate

Set<String> ordered = new LinkedHashSet<>(List.of("b", "a", "b"));
// [b, a]

Set<String> ci = new TreeSet<>(String.CASE_INSENSITIVE_ORDER);
ci.add("Java"); ci.add("JAVA");           // second rejected, compare == 0

Common mistakes

  • Custom classes without equals/hashCode, so "duplicates" are stored.
  • Mutating an element after adding it, making it unfindable.
  • Comparators inconsistent with equals in TreeSet.
  • Expecting HashSet to keep any order.

How to answer in the interview

"HashSet is literally a HashMap where the elements are keys and the value is a dummy PRESENT object, so uniqueness depends on hashCode and equals and operations are constant time on average. LinkedHashSet is backed by a LinkedHashMap and keeps insertion order. TreeSet is backed by a TreeMap, a red-black tree, so it is always sorted with log n operations, and duplicates are decided by compareTo rather than equals. HashSet allows one null; TreeSet with natural ordering throws on null."

Likely follow-up questions

  • What if you modify an object after adding it? Its hash changes, so contains and remove can miss it and duplicates can appear.
  • Which set for sorted range queries? TreeSet, using subSet, floor and ceiling.
  • Thread-safe sorted set? ConcurrentSkipListSet.
