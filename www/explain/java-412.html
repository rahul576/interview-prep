What are the twelve-factor app principles most relevant to Java microservices?

Microservices · concept · levels mid, senior

In one line

For Java microservices the most relevant twelve-factor principles are config in the environment, stateless processes, backing services as attached resources, disposability (fast start, graceful shutdown), logs as event streams and dev/prod parity, all of which map naturally onto Spring Boot and Kubernetes.

Detailed explanation

The twelve-factor methodology, written by Heroku engineers, describes how to build apps that run well on cloud platforms. Several factors matter most in day-to-day Java work.

Config (III). Anything that differs between environments, URLs, credentials, feature flags, lives outside the code and the artifact. The same image is promoted from test to production. Spring Boot's externalised configuration reads environment variables (SPRING_DATASOURCE_URL), ConfigMaps and mounted secrets; secrets belong in a vault, not in application.yml.

Processes (VI). Run stateless processes; anything that must survive goes to a backing service. No HTTP session state in memory, no files on local disk; use Redis or the database. That enables horizontal scaling and safe restarts.

Backing services (IV). Databases, caches, brokers and SMTP servers are attached resources addressed by configuration, so swapping a local Postgres for a managed one is a config change.

Disposability (IX). Instances can be started or killed at any moment, so start fast and shut down gracefully: finish in-flight requests, stop consuming messages, close pools. Spring Boot supports server.shutdown=graceful; Kubernetes sends SIGTERM and waits for the grace period. Fast startup helps autoscaling; options include class data sharing (CDS/AOT caching), Spring AOT and GraalVM native images.

Logs (XI). Write logs as an event stream to stdout, ideally structured JSON (Spring Boot 3.4 added built-in structured logging), and let the platform collect and ship them. No log files or rotation in the app.

Dev/prod parity (X). Keep environments similar: same database engine, same broker. Testcontainers makes running real Postgres or Kafka in tests easy.

Also relevant: one codebase per app (I), explicit dependencies via Maven/Gradle (II), build-release-run separation (V), port binding with an embedded server (VII), and admin processes as one-off jobs (XII).

How it works

  1. Build one immutable image per commit.
  2. Inject environment-specific config at deploy time.
  3. Keep state in backing services.
  4. Handle SIGTERM: stop accepting work, drain, exit.
  5. Log to stdout; platform ships logs.
  6. Test against the same backing service types as production.

Example

# application.yml - no environment-specific values baked in
spring:
  datasource:
    url: ${DB_URL}
    username: ${DB_USER}
    password: ${DB_PASSWORD}
  lifecycle:
    timeout-per-shutdown-phase: 20s
server:
  shutdown: graceful
logging:
  structured:
    format:
      console: ecs
# Kubernetes deployment excerpt
env:
  - name: DB_URL
    valueFrom: { configMapKeyRef: { name: orders-config, key: db-url } }
  - name: DB_PASSWORD
    valueFrom: { secretKeyRef: { name: orders-db, key: password } }
terminationGracePeriodSeconds: 30

Common mistakes

  • Separate builds per environment, or profiles with hard-coded production URLs.
  • Storing sessions or uploads on local disk.
  • Writing log files inside containers.
  • Ignoring SIGTERM, so deployments drop requests.

How to answer in the interview

"The factors I care most about are: config in the environment, so the same image runs everywhere and secrets come from a vault; stateless processes, with sessions and files in backing services so I can scale and restart freely; backing services as attached resources switched by configuration; disposability, meaning fast startup and graceful shutdown when Kubernetes sends SIGTERM; logs as event streams to stdout, preferably structured JSON; and dev/prod parity, which I get with Testcontainers. Spring Boot and Kubernetes support all of these out of the box."

Likely follow-up questions

  • Which factor is most violated in legacy Java apps? Config and statelessness: environment-specific WARs and in-memory HTTP sessions.
  • How do you make shutdown graceful for Kafka consumers? Stop the listener container, finish the batch, commit offsets, then exit.
  • Is twelve-factor enough for cloud-native? It is a baseline; add observability, health probes and security.
