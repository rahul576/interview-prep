What is the difference between authentication and authorization, and how do OAuth 2 and OpenID Connect relate?

Security · concept · levels entry, mid

In one line

Authentication proves who you are; authorization decides what you may do. OAuth 2 is a framework for delegated authorization using access tokens, and OpenID Connect is an identity layer on top that adds the ID token for authentication.

Detailed explanation

Authentication comes first: the system verifies identity with something you know, have or are, such as a password, a passkey, an authenticator app or SSO. Authorization then checks the authenticated principal's roles, scopes or permissions against the resource. In HTTP terms, a failed authentication is 401 Unauthorized and an authenticated user without rights gets 403 Forbidden.

OAuth 2 solves a different problem: letting a client application call an API (the resource server) on behalf of a resource owner without sharing the user's password. The authorization server issues an access token with scopes such as orders.read. Common grants today are authorization code with PKCE for web, single-page and mobile apps, and client credentials for service-to-service calls. The implicit and password grants are deprecated, and OAuth 2.1 drops them. An access token tells the API what the client is allowed to do; it was never meant to tell the client who the user is.

OpenID Connect (OIDC) fills that gap. When the client requests the openid scope, the authorization server (now an OpenID Provider) also returns an ID token, a signed JWT with identity claims (sub, name, email, auth_time) intended for the client, plus a standard UserInfo endpoint and discovery document. So in practice: OIDC handles login, OAuth 2 access tokens handle API authorization.

How it works

  1. User clicks login; the app redirects to the provider with response_type=code, scopes openid profile orders.read and a PKCE challenge.
  2. The user authenticates at the provider (password, MFA, passkey) and consents.
  3. The app receives an authorization code and exchanges it, with the PKCE verifier, for tokens.
  4. The ID token tells the app who logged in; the access token is sent to APIs.
  5. The API validates the access token and applies authorization rules on scopes and roles.

Example

spring:
  security:
    oauth2:
      client:
        registration:
          shop:
            provider: keycloak
            client-id: web-app
            client-secret: ${CLIENT_SECRET}
            authorization-grant-type: authorization_code
            scope: openid,profile,orders.read
        provider:
          keycloak:
            issuer-uri: https://login.example.com/realms/shop

Common mistakes

  • Using an OAuth access token as proof of login in the client.
  • Sending the ID token to APIs as a bearer token.
  • Still using the implicit flow in single-page apps.
  • Treating authentication as enough and skipping object-level authorization.

How to answer in the interview

"Authentication answers who you are, authorization answers what you can do, and authentication always comes first. OAuth 2 is a delegated authorization framework: a client gets an access token from an authorization server to call an API with certain scopes, using authorization code with PKCE for user-facing apps or client credentials between services. OAuth by itself does not define login. OpenID Connect adds that on top: with the openid scope you also get an ID token, a signed JWT describing the user, for the client. So I use OIDC to sign users in and OAuth access tokens to authorise API calls."

Likely follow-up questions

  • Why PKCE instead of implicit for SPAs? Implicit returns tokens in the URL fragment, exposed to history and leaks; PKCE binds the code to the client that started the flow.
  • What is a refresh token? A long-lived credential used to get new access tokens without re-login, ideally rotated.
  • What is SAML? An older XML-based SSO standard, still common in enterprises, comparable in role to OIDC.
