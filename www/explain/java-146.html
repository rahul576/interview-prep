What is hexagonal architecture (ports and adapters), and how does it compare with layered architecture?

Design Patterns · concept · levels senior, lead

In one line

Hexagonal architecture (ports and adapters) puts a framework-free domain at the centre; the domain defines ports (interfaces) and adapters (REST, JPA, Kafka) implement them, whereas classic layered architecture stacks controller → service → repository and often lets business logic depend on infrastructure.

Detailed explanation

In a typical layered Spring app, controllers call services, services call JPA repositories, and entities double as domain objects. It is simple and familiar, but dependencies point downwards to the database: business rules import JPA annotations, Spring Data interfaces and framework exceptions, so testing logic needs a database or heavy mocking, and swapping infrastructure touches the core.

Hexagonal architecture, introduced by Alistair Cockburn, inverts this. The application core (domain model plus use cases) has no dependency on Spring, JPA or Kafka. It defines:

  • Inbound (driving) ports: use-case interfaces such as PlaceOrderUseCase, called by the outside world.
  • Outbound (driven) ports: interfaces the core needs, such as OrderRepository or PaymentPort.

Adapters sit outside: a REST controller or Kafka consumer is an inbound adapter calling a use case; a JPA repository implementation or HTTP client is an outbound adapter implementing a port. All dependencies point inwards, the dependency inversion principle at architecture level. Clean Architecture and Onion Architecture express the same idea.

Benefits: the core is unit-testable with plain in-memory fakes, infrastructure can be swapped (JPA to JDBC, REST to gRPC), and business logic stays readable. Costs: more interfaces, separate domain and persistence models with mapping code, and more modules. For a small CRUD service, layered is often the better choice; hexagonal pays off for rich domains with long lifetimes.

How it works

  1. Model the domain and use cases in a module with no framework imports.
  2. Define inbound ports (use cases) and outbound ports (repositories, gateways).
  3. Implement adapters for web, messaging, persistence and external APIs.
  4. Wire adapters to ports in a configuration module (Spring).
  5. Enforce dependency rules with modules or ArchUnit tests.

Example

// core (no Spring/JPA imports)
public interface OrderRepository { void save(Order o); Optional<Order> byId(OrderId id); }
public class PlaceOrderService implements PlaceOrderUseCase {
    private final OrderRepository repo;
    public PlaceOrderService(OrderRepository repo) { this.repo = repo; }
    public OrderId place(PlaceOrderCommand cmd) { Order o = Order.create(cmd); repo.save(o); return o.id(); }
}

// adapter
@Repository
class JpaOrderRepositoryAdapter implements OrderRepository {
    private final SpringDataOrderRepo jpa;   // JPA entity + mapper live here
    /* map domain <-> entity */
}

// ArchUnit rule
noClasses().that().resideInAPackage("..core..")

Comparison

LayeredHexagonal
Dependency directionDown to DBInwards to domain
Domain testsOften need DB/mocksPlain unit tests
BoilerplateLowHigher (ports, mappers)
Best forCRUD, small servicesComplex, long-lived domains

Common mistakes

  • Creating ports and adapters for a trivial CRUD service.
  • Leaking JPA entities into the core anyway.
  • One giant "port" interface mirroring the database.
  • No automated checks, so boundaries erode over time.

How to answer in the interview

"In layered architecture, controller calls service calls repository, and the business logic usually ends up depending on JPA and Spring. Hexagonal, or ports and adapters, puts the domain at the centre with no framework dependencies. The domain defines ports, interfaces for what it offers and what it needs, and adapters implement them: a REST controller, a JPA adapter, a Kafka adapter. Dependencies point inwards, so the core is easy to unit test and infrastructure is swappable. The cost is more interfaces and mapping code, so I use it for complex domains, not simple CRUD, and enforce boundaries with ArchUnit or Maven modules."

Likely follow-up questions

  • How do you enforce boundaries? Separate Maven/Gradle modules and ArchUnit tests that fail on forbidden dependencies.
  • Should JPA entities be domain objects? In strict hexagonal, no; you map between them, accepting some duplication.
  • How does it relate to Clean Architecture? Same dependency rule, with more named rings (entities, use cases, interface adapters).
