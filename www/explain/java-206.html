What is reflection in Java, and where is it used?

Core Java & OOP · concept · levels mid, senior

In one line

Reflection (java.lang.reflect) lets code inspect and invoke classes, constructors, methods, fields and annotations at runtime; frameworks such as Spring, Hibernate, Jackson and JUnit depend on it, at a cost in performance, type safety and encapsulation.

Detailed explanation

With reflection you start from a Class<?> object (obj.getClass(), Foo.class or Class.forName("...")) and ask for its Method, Field, Constructor and annotation objects. You can then create instances, call methods and read or write fields, even private ones, by name decided at runtime.

That is exactly what frameworks need, because they work with classes they have never seen at compile time:

  • Spring scans for @Component, finds @Autowired constructors and creates proxies.
  • Hibernate/JPA reads @Entity mappings and sets fields when loading rows.
  • Jackson maps JSON properties to fields, getters and record components.
  • JUnit finds @Test methods and invokes them.

The costs:

  • Performance. Reflective calls were historically slower; since JDK 18 (JEP 416) core reflection is reimplemented on method handles, and the JIT does well with cached Method objects, but lookups are still expensive, so cache them.
  • No compile-time safety. Typos in names become runtime errors and refactoring tools miss them.
  • Broken encapsulation. setAccessible(true) bypasses private. Since JDK 16/17 strong encapsulation, deep reflection into JDK internals fails unless the package is opened (--add-opens), and module authors must opens packages to frameworks.
  • Ahead-of-time compilation. GraalVM native images need reflection metadata because they analyse reachable code at build time.

Alternatives: MethodHandles / VarHandles for fast dynamic access, annotation processors that generate code at compile time (MapStruct, Dagger, Micronaut), and bytecode generation (ByteBuddy).

How it works

  1. Obtain a Class object.
  2. Look up members with getDeclaredMethod, getDeclaredFields, getAnnotation.
  3. Optionally call setAccessible(true) (subject to module rules).
  4. Invoke with method.invoke(target, args) or field.set(target, value).
  5. Handle checked exceptions such as InvocationTargetException (wraps the real exception).

Example

// Mini test runner
for (Method m : CalculatorTest.class.getDeclaredMethods()) {
    if (m.isAnnotationPresent(Test.class)) {
        Object instance = CalculatorTest.class.getDeclaredConstructor().newInstance();
        try {
            m.invoke(instance);
            System.out.println("PASS " + m.getName());
        } catch (InvocationTargetException e) {
            System.out.println("FAIL " + m.getName() + ": " + e.getCause());
        }
    }
}

Common mistakes

  • Using reflection in business code where an interface or lambda would do.
  • Not caching Method/Field lookups in hot paths.
  • Reporting InvocationTargetException instead of its cause.
  • Being surprised by InaccessibleObjectException after a JDK upgrade.

How to answer in the interview

"Reflection lets code inspect classes, methods, fields and annotations at runtime and invoke or modify them dynamically. Frameworks live on it: Spring for dependency injection and annotation scanning, Hibernate and Jackson for mapping fields, JUnit for discovering tests. The costs are slower lookups, no compile-time safety, and breaking encapsulation with setAccessible, which the module system now restricts. In application code I avoid it; when performance or native images matter, I prefer method handles or compile-time code generation like MapStruct or Micronaut."

Likely follow-up questions

  • Why does reflection make GraalVM native images harder? The build-time analysis can't see dynamically accessed members, so they must be declared in metadata.
  • What are MethodHandles? Typed, JIT-friendly references to methods and fields from java.lang.invoke.
  • What does --add-opens do? Opens a module's package for deep reflection at runtime.
