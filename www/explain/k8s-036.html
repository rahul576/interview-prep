How do you choose between namespaces, virtual clusters and separate clusters for multi-tenancy?

Kubernetes · design · levels mid, senior, lead

In one line

Namespaces give soft multi-tenancy (RBAC, quotas, NetworkPolicies, Pod Security) on a shared control plane and nodes; virtual clusters such as vcluster give each tenant its own API server inside a host namespace; separate clusters give hard isolation for untrusted tenants, compliance or different lifecycles, at the highest cost and operational overhead.

Detailed explanation

Multi-tenancy is a spectrum of isolation versus cost.

Namespaces per tenant: each team gets one or more namespaces with RoleBindings, ResourceQuota and LimitRange, default-deny NetworkPolicies, Pod Security Admission at restricted, and policy engines for extra rules. Benefits: cheap, efficient bin-packing, one platform to upgrade. Limits:

  • Cluster-scoped resources are shared: tenants can't install their own CRDs, webhooks, ClusterRoles or operators without affecting others, and CRD version conflicts appear.
  • Shared kernel and nodes: a container escape or kernel exploit crosses tenants. Mitigate with dedicated node pools (taints, node affinity), sandboxed runtimes (gVisor, Kata) and strict Pod Security.

Suitable for trusted internal teams.

Virtual clusters (vcluster and similar): each tenant gets a lightweight control plane (API server, backing store, syncer) running as pods in a host namespace. Tenants see a full cluster: they can install CRDs, operators, Helm charts with cluster roles, and choose some versions, while the syncer maps their pods onto the host's nodes. Good for dev, test and CI environments. Isolation of the data plane is still the host's, so node-level controls still matter.

Separate clusters: strongest isolation of control plane, network and nodes; required for untrusted or external customers, strict compliance scopes such as PCI-DSS, different regions or data residency, or very different upgrade cadences. Cost: control plane fees, idle capacity, duplicated add-ons, and fleet operations. That requires fleet tooling: cluster API or Terraform modules, GitOps (Argo CD ApplicationSets, Flux) for consistent add-ons, central policy and observability.

How it works

  1. Classify tenants: trust level, compliance, need for cluster-scoped resources.
  2. Trusted, standard workloads → namespaces with guard rails.
  3. Need own CRDs or admin, moderate trust → virtual clusters.
  4. Untrusted or regulated → dedicated clusters.
  5. Standardise provisioning and add-ons via GitOps across all models.

Example

vcluster create team-a --namespace vc-team-a
vcluster connect team-a --namespace vc-team-a
kubectl get crds        # tenant's own API, separate from the host

Common mistakes

  • Using namespaces to isolate hostile tenants.
  • Letting every team install cluster-wide CRDs in a shared cluster.
  • One cluster per team without fleet automation.
  • Assuming a virtual cluster isolates nodes and kernels.

How to answer in the interview

"Namespaces give soft multi-tenancy: RBAC, quotas, LimitRanges, NetworkPolicies and Pod Security per team, sharing the control plane and nodes. That's cheap and fine for trusted internal teams, but tenants can't own cluster-scoped resources like CRDs, and a kernel escape crosses boundaries unless I add dedicated node pools or sandboxed runtimes. Virtual clusters like vcluster give each tenant its own API server inside a host namespace, so they can install CRDs and operators while sharing nodes. Separate clusters give hard isolation for untrusted tenants, PCI-style compliance or different upgrade cycles, but cost more and need fleet tooling and GitOps."

Likely follow-up questions

  • Signals to move a team to its own cluster? Compliance scope, untrusted code, conflicting CRDs, noisy-neighbour incidents, special hardware or upgrade needs.
  • How do you stop noisy tenants overloading the API? API Priority and Fairness plus quotas.
  • What is a sandboxed runtime? gVisor or Kata via RuntimeClass, adding a kernel boundary.
