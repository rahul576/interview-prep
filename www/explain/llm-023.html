What is disaggregated serving, separating prefill and decode, and why is it gaining attention?

LLMOps & RAG · concept · levels senior, lead

In one line

Disaggregated serving runs compute-bound prefill and memory-bound decode on separate GPU pools, transferring the KV cache between them, so long prefills no longer stall decodes and each pool scales independently, improving latency consistency and goodput; it powers frameworks like llm-d, NVIDIA Dynamo, and vLLM/SGLang disaggregation.

Detailed explanation

Prefill and decode have opposite profiles. Prefill processes thousands of prompt tokens at once: compute-bound, bursty, and it determines TTFT. Decode generates one token per step for many sequences: memory-bandwidth-bound, steady, and it determines inter-token latency. On a shared GPU, a big prefill arriving mid-stream occupies the GPU for that step, so every ongoing decode stalls, causing latency spikes. Chunked prefill reduces but does not eliminate this interference, and you cannot pick one batch size, parallelism layout or GPU type that is optimal for both phases.

Disaggregation splits them. A request goes first to a prefill worker, which computes the prompt's KV cache and the first token. The KV cache is transferred to a decode worker over a high-bandwidth interconnect (NVLink, InfiniBand or RoCE using RDMA, via libraries such as NIXL), and the decode worker continues generation. Benefits:

  • No prefill-decode interference, so ITL is stable and TTFT more predictable.
  • Each pool uses its own parallelism and batching settings, possibly different hardware.
  • Pools scale independently: RAG workloads with long prompts need more prefill capacity; chat with long answers needs more decode capacity.
  • Better goodput under SLOs at large scale.

It fits into a broader architecture: KV-cache-aware routing in an inference gateway (prefer the worker that already holds a request's prefix), tiered KV caching across GPU, CPU and storage, and global scheduling. Open-source frameworks include llm-d (Kubernetes-native, built on vLLM and the Gateway API Inference Extension), NVIDIA Dynamo, and disaggregated prefill support in vLLM and SGLang.

The cost is complexity: more components, KV transfer bandwidth requirements, failure handling between stages and tuning of the prefill-to-decode ratio. For a few GPUs or short prompts, a well-tuned single pool with chunked prefill is usually better; disaggregation pays off at large scale with long prompts and strict SLOs.

How it works

  1. Gateway receives a request; picks a prefill worker (prefix-aware).
  2. Prefill computes KV cache and first token.
  3. KV blocks transfer to a decode worker via RDMA.
  4. Decode worker streams remaining tokens.
  5. Autoscalers scale prefill and decode pools on their own metrics.

Example

Cluster: 16 x H100
Prefill pool: 4 GPUs, TP=4, large token budget per step
Decode pool: 12 GPUs, 3 replicas TP=4, large max-num-seqs
Router: KV-aware; KV transfer over InfiniBand (NIXL)
Workload: RAG, 8K-token prompts, 300-token answers → prefill-heavy; rebalance ratio from metrics

Common mistakes

  • Adopting disaggregation for a small cluster where it only adds overhead.
  • Underestimating KV transfer bandwidth needs.
  • Fixed prefill:decode ratios that ignore workload shifts.
  • Ignoring failure modes between stages.

How to answer in the interview

"Prefill is compute-bound and bursty, while decode is memory-bound and steady. On the same GPUs a long prefill can stall everyone's decoding and cause latency spikes, and no single configuration suits both. Disaggregated serving runs them on separate GPU pools: a prefill worker computes the KV cache, transfers it over fast networking to a decode worker, which generates the tokens. Each pool scales and is tuned independently, which improves latency consistency and goodput. With KV-aware inference gateways, this is the direction of llm-d, NVIDIA Dynamo and vLLM and SGLang. It adds complexity, so it pays off mainly at large scale."

Likely follow-up questions

  • Why high-bandwidth networking? KV caches are gigabytes for long prompts; slow transfer erases the TTFT gain.
  • How choose the pool ratio? From prompt and output length distributions and per-pool queue metrics.
  • Alternative at small scale? Chunked prefill and priority scheduling on a single pool.
