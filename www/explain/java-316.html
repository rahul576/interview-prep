What is open-session-in-view, and why is it often disabled?

Spring Data & JPA · concept · levels senior, lead

In one line

Open-session-in-view (OSIV) keeps the persistence context open for the whole web request, so lazy loading in controllers and JSON serialisation "just works"; it's enabled by default in Spring Boot (with a warning) but often disabled because it holds database connections longer and hides N+1 lazy loads outside the service layer.

Detailed explanation

With OSIV, Spring registers OpenEntityManagerInViewInterceptor for Spring MVC. When a request starts, it opens an EntityManager and binds it to the thread; the service's @Transactional method uses that same EntityManager, and after the transaction commits the persistence context stays open until the view is rendered or the response is serialised. So accessing order.getCustomer().getName() in a controller, a Thymeleaf template or Jackson doesn't throw LazyInitializationException; Hibernate silently runs another query.

Spring Boot sets spring.jpa.open-in-view=true by default for backwards compatibility and logs a warning at startup ("spring.jpa.open-in-view is enabled by default...") precisely because it is controversial.

The problems:

  • Connection holding. Once lazy loading has used a connection, it can stay associated with the request until it completes, including slow serialisation, template rendering or calls to other services. Under load, the connection pool is exhausted much sooner.
  • Hidden queries. Lazy loads happen in the web layer, outside transactions (in auto-commit mode), often in loops, producing N+1 queries that nobody sees in the service code and that tests of the service miss.
  • Blurred boundaries. The service layer no longer defines what data a use case needs, and entities leak into the API, coupling JSON to the entity model.

Disabling it with spring.jpa.open-in-view=false makes the transaction the boundary of data access. After disabling, LazyInitializationExceptions will reveal every place that relied on it. Fix each by fetching what the use case needs inside the service: JOIN FETCH, @EntityGraph, batch fetching, or better, returning DTO projections instead of entities.

How it works

  1. Request arrives; OSIV interceptor opens and binds an EntityManager.
  2. Service transaction uses it and commits.
  3. Controller/serialiser touches lazy associations; extra queries run.
  4. Response written; interceptor closes the EntityManager.
  5. With OSIV off, step 1 doesn't happen and step 3 throws instead.

Example

spring:
  jpa:
    open-in-view: false
// Before: controller relies on OSIV
@GetMapping("/orders/{id}")
Order get(@PathVariable long id) { return service.find(id); }   // Jackson lazy-loads lines, customer

// After: service returns a fully prepared DTO
@Transactional(readOnly = true)
public OrderDto find(long id) {
    Order o = repo.findDetailedById(id).orElseThrow();   // @EntityGraph({"customer", "lines"})
    return OrderDto.from(o);
}

Common mistakes

  • Leaving OSIV on and serialising entities directly.
  • Replacing OSIV with enable_lazy_load_no_trans, which is worse.
  • Switching associations to EAGER to silence exceptions.
  • Disabling OSIV without integration tests that exercise the endpoints.

How to answer in the interview

"Open session in view keeps the persistence context open for the whole web request, until the response is rendered, so lazy loading in controllers or during JSON serialisation works silently. Spring Boot enables it by default and logs a warning. The problems are that database connections are held longer than needed, and lazy loads happen outside the service layer, creating hidden N+1 queries. I disable it with spring.jpa.open-in-view=false and fetch what each use case needs explicitly with fetch joins, entity graphs or DTO projections."

Likely follow-up questions

  • Errors after disabling it? LazyInitializationException where the web layer touched lazy data; fix with explicit fetching or DTOs.
  • Is OSIV ever acceptable? Small, low-traffic apps with server-side templates, accepting the trade-off.
  • Does it apply to WebFlux? No, it's a Spring MVC interceptor.
