What is the Istio-based service mesh add-on for AKS, and how are its upgrades handled?

Azure Kubernetes (AKS) · concept · levels senior, lead

In one line

The Istio-based service mesh add-on gives AKS a Microsoft-managed, supported Istio control plane for mTLS, traffic management and telemetry; workloads join via a revision label on namespaces, minor upgrades are canary upgrades between revisions that you complete or roll back, and patch upgrades are automatic.

Detailed explanation

Running upstream Istio yourself means installing it, tuning it, and above all upgrading it safely every few months. The add-on moves that responsibility to Microsoft: AKS installs istiod in aks-istio-system, keeps it patched and supports a defined set of revisions (named like asm-1-26) for each Kubernetes version.

Capabilities: automatic mutual TLS between workloads (with PeerAuthentication set to STRICT), traffic management with VirtualService and DestinationRule (retries, timeouts, weighted canaries, fault injection, circuit breaking), ingress and egress gateways (managed external or internal ingress gateways can be enabled), and telemetry that integrates with Managed Prometheus and Grafana.

Joining the mesh: you label a namespace with istio.io/rev=asm-1-26 (not the generic istio-injection=enabled), and new pods get an Envoy sidecar injected for that revision.

Upgrades:

  • Patch versions of the current revision are rolled out automatically by AKS; sidecars pick up the patched proxy on the next pod restart.
  • Minor upgrades are canary upgrades: az aks mesh upgrade start deploys a second control plane revision side by side. You relabel namespaces to the new revision and restart workloads gradually, because sidecars are injected only when a pod is created. When everything is healthy you run upgrade complete to remove the old revision, or upgrade rollback to return.

Because supported mesh revisions depend on the AKS Kubernetes version, mesh and cluster upgrades must be planned together; an old revision can block a Kubernetes upgrade or fall out of support.

How it works

  1. az aks mesh get-revisions to see available revisions.
  2. Enable the mesh with a chosen revision.
  3. Label namespaces with istio.io/rev and restart deployments.
  4. For a minor upgrade: start canary, relabel, roll restart, verify, complete.
  5. Monitor proxy versions and control plane health.

Example

az aks mesh enable -g rg-apps -n aks-prod --revision asm-1-25
kubectl label namespace orders istio.io/rev=asm-1-25
kubectl rollout restart deployment -n orders

# Minor upgrade
az aks mesh get-upgrades -g rg-apps -n aks-prod
az aks mesh upgrade start -g rg-apps -n aks-prod --revision asm-1-26
kubectl label namespace orders istio.io/rev=asm-1-26 --overwrite
kubectl rollout restart deployment -n orders
az aks mesh upgrade complete -g rg-apps -n aks-prod   # or: upgrade rollback

Common mistakes

  • Using istio-injection=enabled instead of the revision label.
  • Relabelling namespaces but forgetting to restart pods, leaving old sidecars.
  • Customising istiod in unsupported ways that the add-on overwrites.
  • Ignoring the compatibility table and blocking cluster upgrades.

How to answer in the interview

"The add-on installs a Microsoft-managed Istio control plane, so I get mTLS, traffic management like retries, timeouts and canary splitting, and telemetry without operating Istio myself. Namespaces join by labelling them with the specific revision. Patch upgrades are automatic. Minor upgrades are canary upgrades: a second control plane revision runs alongside, I relabel namespaces and restart workloads gradually so sidecars move to the new revision, then complete or roll back. Supported revisions depend on the Kubernetes version, so I plan mesh and cluster upgrades together."

Likely follow-up questions

  • Why restart workloads? Sidecars are injected at pod creation, so only new pods get the new proxy.
  • Does it support ambient mode? Check current add-on support; the add-on has focused on sidecar mode.
  • How do you enforce mTLS? A mesh-wide PeerAuthentication with mode STRICT.
