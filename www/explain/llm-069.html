How would you integrate an LLM into a Spring Boot backend with Spring AI?

LLMOps & RAG · concept · levels mid, senior

In one line

Spring AI gives Spring Boot a portable ChatClient over providers (OpenAI, Anthropic, Azure OpenAI, Bedrock, Vertex AI, Ollama and more) configured via starters and properties, with prompt templates, structured output into Java records, tool calling via annotated methods, advisors for memory, RAG and logging, a VectorStore abstraction (pgvector, Redis, Elasticsearch, Qdrant and others), Micrometer observability and MCP support.

Detailed explanation

Spring AI reached general availability with version 1.0 in 2025 and follows familiar Spring conventions: auto-configuration, application.yml properties and dependency injection.

ChatClient. A fluent API built from an auto-configured ChatClient.Builder. You set default system prompts, add user messages with template variables, call the model, and get either text, a streaming Flux, or a mapped entity. Switching providers is mostly a matter of changing the starter dependency and properties, as long as you avoid provider-specific options.

Structured output. .entity(MyRecord.class) instructs the model with a schema derived from the class and converts the response into a Java record, list or map.

Tool calling. Methods annotated with @Tool (and @ToolParam for argument descriptions) become tools with generated JSON schemas. The model requests a call, Spring AI invokes the method and returns the result. Existing services thus become tools, but you must enforce authorisation inside them.

Advisors. Interceptors around calls, similar to aspects: MessageChatMemoryAdvisor adds conversation memory from a ChatMemory repository; QuestionAnswerAdvisor or the modular RAG advisor queries a VectorStore and adds retrieved documents to the prompt; logging and safety advisors handle cross-cutting concerns.

VectorStore and ingestion. A common interface for pgvector, Redis, Elasticsearch, OpenSearch, Azure AI Search, Qdrant, Milvus, MongoDB Atlas and others, with document readers (PDF, Tika, JSON) and splitters (TokenTextSplitter) for ETL pipelines, and metadata filter expressions.

Observability. Micrometer metrics and traces for model calls, token usage, tool calls and vector store operations, exportable to Prometheus, OpenTelemetry and APM tools.

MCP. Client and server starters let the app consume tools from MCP servers or expose its own tools via MCP.

How it works

  1. Add the provider starter and vector store starter; configure properties.
  2. Inject ChatClient.Builder; set default system prompt and advisors.
  3. Define @Tool methods for business operations.
  4. Ingest documents into the VectorStore with readers and splitters.
  5. Call chatClient.prompt()...call().entity(...) in services.
  6. Observe via Micrometer.

Example

record TicketSummary(String category, String priority, String summary) {}

@Service
class SupportAssistant {
    private final ChatClient chat;

    SupportAssistant(ChatClient.Builder builder, VectorStore store, ChatMemory memory) {
        this.chat = builder
            .defaultSystem("You are a support assistant. Answer only from provided context.")
            .defaultAdvisors(MessageChatMemoryAdvisor.builder(memory).build(),
                             QuestionAnswerAdvisor.builder(store).build())
            .build();
    }

    TicketSummary summarise(String ticketText) {
        return chat.prompt()
            .user(u -> u.text("Summarise this ticket: {t}").param("t", ticketText))
            .call()
            .entity(TicketSummary.class);
    }
}

@Component
class OrderTools {
    @Tool(description = "Get order status by order ID for the current customer")
    String orderStatus(@ToolParam(description = "Order ID") String orderId) { /* check access */ return "SHIPPED"; }
}

Common mistakes

  • Exposing powerful service methods as tools without authorisation checks.
  • Letting provider-specific options leak throughout the codebase.
  • No timeouts or retries configured for model calls.
  • Ignoring token usage metrics.

How to answer in the interview

"Spring AI gives a portable, Spring-style API over providers like OpenAI, Anthropic, Azure OpenAI, Bedrock, Vertex and Ollama, configured through starters and properties. The ChatClient builds prompts with templates and can map responses straight into Java records. Annotated methods become tools the model can call. Advisors add cross-cutting behaviour like chat memory, RAG over a VectorStore, and logging. The VectorStore abstraction supports pgvector, Redis, Elasticsearch, Qdrant and others, with document readers and splitters for ingestion. Micrometer gives metrics and traces including tokens, and there's MCP client and server support."

Likely follow-up questions

  • Keep providers switchable? Use portable options, wrap provider-specific features behind your own interface.
  • Streaming to the UI? .stream().content() returns a Flux<String> for SSE.
  • Testing? Mock ChatModel, plus evaluation tests with real models.
