How do you get reliable structured output, such as JSON, from an LLM?

LLMOps & RAG · concept · levels mid, senior

In one line

For reliable JSON, use structured output / strict JSON-schema modes that apply constrained decoding, or tool calling for typed arguments; define schemas with Pydantic (or similar), keep them simple, still validate and retry, and remember a schema guarantees format, not correctness.

Detailed explanation

Asking "reply in JSON" in the prompt works most of the time, which is not good enough when a parser in production fails on the 1-in-200 response with a trailing comment or missing brace.

Constrained decoding solves the format problem. You pass a JSON Schema; at each decoding step the engine computes which tokens can legally come next given the schema and masks all others, so the model cannot produce invalid JSON or missing required fields. Hosted APIs expose this as structured outputs or strict schema modes (OpenAI response_format with json_schema and strict, Gemini response schemas, and comparable features in other providers' APIs; check current docs for each). Self-hosted engines such as vLLM and SGLang implement it with grammar engines like XGrammar, Outlines or llguidance, supporting JSON Schema, regexes and context-free grammars.

Tool calling is a related route: you describe functions with parameter schemas, and the model returns a tool call with typed arguments, which many providers can also enforce strictly.

In application code, define the schema as types, for example Pydantic models in Python or records with Jackson and JSON Schema generators in Java. Libraries like Instructor or Spring AI's output converters generate the schema and parse into objects. Still validate: when a provider lacks strict mode, or for semantic rules the schema cannot express, catch validation errors and retry with the error message in the prompt, with a retry limit.

Design schemas for the model: few nesting levels, clear field descriptions, enums for categories, nullable fields for "unknown" instead of forcing invented values, and field order that lets reasoning come before the conclusion if needed. Format guarantees are not truth guarantees: a perfectly valid object can contain the wrong date or a hallucinated amount, so business validation, cross-checks and evaluation remain necessary.

How it works

  1. Define a typed model and generate JSON Schema.
  2. Send it as a strict response format or tool schema.
  3. Engine masks invalid tokens during decoding.
  4. Parse into typed objects; run business validation.
  5. On failure, retry with error feedback or route to review.

Example

from pydantic import BaseModel, Field
from typing import Literal, Optional

class Invoice(BaseModel):
    vendor: str
    total: float = Field(description="Grand total including tax")
    currency: Literal["EUR", "USD", "INR", "GBP"]
    due_date: Optional[str] = Field(None, description="ISO date or null if absent")

resp = client.chat.completions.parse(            # OpenAI-style structured parse
    model=MODEL, messages=[{"role": "user", "content": invoice_text}],
    response_format=Invoice)
invoice = resp.choices[0].message.parsed
assert invoice.total >= 0

Common mistakes

  • Relying on prompt instructions alone for machine-read output.
  • Deeply nested, huge schemas that confuse the model.
  • Required fields with no "unknown" option, forcing hallucination.
  • Treating schema-valid output as correct output.

How to answer in the interview

"The most reliable approach is the structured output feature of modern APIs and engines: I pass a JSON schema and constrained decoding masks any token that would break it, so the result always parses. vLLM and SGLang do the same with grammar engines like XGrammar. Tool calling is another way to get typed arguments. In code I define the schema with Pydantic or similar, often via Instructor, and still validate, retrying with the error if a provider lacks strict mode. I keep schemas simple with descriptions and enums, because a schema guarantees format, not correctness, so business validation still matters."

Likely follow-up questions

  • Why can forcing JSON reduce quality? It constrains reasoning; let the model reason first in a field or separate step.
  • Streaming structured output? Partial JSON parsing libraries emit fields as they complete.
  • Grammar overhead? Small with modern engines, larger for complex grammars.
