How would you handle millions of database records efficiently in a Java backend application?

Databases & SQL · design · levels senior, lead

In one line

Never load everything into memory: read with keyset pagination or streaming cursors, select only needed columns through projections and indexes, write with JDBC batching and chunked commits, avoid ORM overhead for bulk work, and run large jobs in the background with tools such as Spring Batch.

Detailed explanation

Millions of rows break naive code in predictable ways: findAll() causes OutOfMemoryError; Hibernate's persistence context grows until GC thrashes; OFFSET 900000 reads and discards 900,000 rows; one huge transaction holds locks, bloats undo/WAL and causes replication lag; and row-by-row inserts take hours because of round trips.

Reading:

  • Keyset (seek) pagination: WHERE id > :lastId ORDER BY id LIMIT 1000. Each page uses the index and costs the same, unlike offset pagination.
  • Streaming with a server-side cursor and fetch size: JdbcTemplate with setFetchSize, JPA Stream<T> with a fetch-size hint. In PostgreSQL the fetch size only works with auto-commit off; in MySQL you need useCursorFetch=true or streaming mode.
  • Projections: select DTOs with only required columns, not full entities with lazy associations.
  • Make sure filters and sort keys are indexed.

Writing:

  • JDBC batching (hibernate.jdbc.batch_size of 500 to 1000, order_inserts), and avoid IDENTITY ID generation in Hibernate because it disables insert batching; use sequences.
  • Commit per chunk so transactions stay short and failures restart from the last chunk.
  • With JPA, flush() and clear() the EntityManager every chunk, or use StatelessSession or plain JdbcTemplate.batchUpdate.
  • For massive loads use database-native tools: PostgreSQL COPY, MySQL LOAD DATA, or INSERT ... SELECT set-based SQL inside the database.

Architecture: run heavy work asynchronously, outside HTTP requests, using Spring Batch (chunk-oriented, restartable, partitioned steps), queues or schedulers; partition big tables; and monitor progress and DB load.

How it works

  1. Choose set-based SQL if the work can be done in the database.
  2. Otherwise read in chunks by keyset or stream with a fetch size.
  3. Process each chunk in memory with bounded size.
  4. Write chunk results in a batch and commit.
  5. Record progress (last processed key) for restartability.
  6. Parallelise by key ranges or partitions, watching DB capacity.

Example

// Keyset-paginated processing with batched writes
long lastId = 0;
List<OrderRow> page;
do {
    page = jdbc.query(
        "SELECT id, customer_id, total FROM orders WHERE id > ? ORDER BY id LIMIT 1000",
        (rs, i) -> new OrderRow(rs.getLong(1), rs.getLong(2), rs.getBigDecimal(3)), lastId);
    if (page.isEmpty()) break;
    tx.executeWithoutResult(s -> jdbc.batchUpdate(
        "INSERT INTO order_summary(order_id, customer_id, total) VALUES (?, ?, ?)",
        page, 1000, (ps, r) -> { ps.setLong(1, r.id()); ps.setLong(2, r.customerId()); ps.setBigDecimal(3, r.total()); }));
    lastId = page.get(page.size() - 1).id();
} while (true);

Common mistakes

  • repository.findAll() on a huge table.
  • Offset pagination for deep pages or batch jobs.
  • One transaction for the whole job.
  • Hibernate IDENTITY keys silently disabling batch inserts.
  • Massive parallelism that overwhelms the database.

How to answer in the interview

"My first rule is never to load millions of rows into memory. If the work can be expressed in SQL, I let the database do it set-based. Otherwise I read in chunks with keyset pagination on an indexed column, or stream with a cursor and a fetch size, selecting only needed columns through projections. For writes I use JDBC batching with batches of several hundred to a thousand and commit per chunk to keep transactions short. With JPA I flush and clear the persistence context per chunk, or use JdbcTemplate or a StatelessSession instead. Large jobs run in the background, usually with Spring Batch, so they are restartable, can be partitioned, and are monitored."

Likely follow-up questions

  • Why does offset pagination slow down on later pages? The database must read and discard all skipped rows.
  • Why does Hibernate IDENTITY disable batching? It must execute each insert immediately to get the generated id.
  • How does Spring Batch help? Chunk processing, transactions per chunk, restart from failure, skip/retry and partitioning.
