Explain OneToOne, OneToMany, ManyToOne, and ManyToMany relationships.

Spring Data & JPA · concept · levels mid, senior

In one line

JPA models associations as @OneToOne, @OneToMany/@ManyToOne and @ManyToMany; the side holding the foreign key is the owning side, the other uses mappedBy, and in practice you make every association LAZY and cascade only where a true parent-child lifecycle exists.

Detailed explanation

Relational databases have only foreign keys and join tables; JPA associations are the object view of them.

@OneToOne links one entity to exactly one other, for example User and UserProfile. It is usually a unique foreign key (profile.user_id) or a shared primary key with @MapsId, which is the most efficient form because the child row uses the parent's id.

@ManyToOne and @OneToMany are the two ends of the same relationship: one Order has many OrderItems. The foreign key order_id lives in the order_item table, so @ManyToOne on OrderItem is the owning side: Hibernate writes the column from it. @OneToMany(mappedBy = "order") on Order is the inverse side: it is only a convenient navigation and changes to it alone are not persisted. A unidirectional @OneToMany without mappedBy makes Hibernate use a join table or extra UPDATE statements, so it is usually avoided.

@ManyToMany, such as Student and Course, uses a join table. As soon as the link needs attributes (enrolment date, grade), model the join as its own entity, Enrolment, with two @ManyToOne relations. Use a Set rather than a List for many-to-many, because Hibernate deletes and reinserts all rows of a "bag" on change.

Fetch defaults: to-one associations are EAGER by default and to-many are LAZY. Eager to-one associations cause hidden extra queries and N+1 problems, so set fetch = LAZY everywhere and fetch what each use case needs with JOIN FETCH or entity graphs. Cascade (PERSIST, REMOVE, ALL) and orphanRemoval suit aggregates where the child cannot live without the parent, never many-to-many.

How it works

  1. Decide which table holds the foreign key; that entity's field is the owning side.
  2. Annotate it with @ManyToOne(fetch = LAZY) and @JoinColumn.
  3. Optionally add the inverse @OneToMany(mappedBy = ...) for navigation.
  4. Keep both sides in sync with helper methods like addItem().
  5. Apply cascade and orphanRemoval only for parent-owned children.
  6. Load associations explicitly per query to avoid N+1.

Example

@Entity
public class Order {
    @Id @GeneratedValue private Long id;

    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<OrderItem> items = new ArrayList<>();

    public void addItem(OrderItem item) {   // keep both sides consistent
        items.add(item);
        item.setOrder(this);
    }
}

@Entity
public class OrderItem {
    @Id @GeneratedValue private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "order_id")
    private Order order;                    // owning side
}

Common mistakes

  • Updating only the inverse side (order.getItems().add(item)) and finding order_id is null in the database.
  • Leaving @ManyToOne eager and triggering a query per row.
  • Using CascadeType.REMOVE on @ManyToMany, deleting shared rows.
  • Including associations in equals, hashCode or toString, causing recursion or lazy loading.

How to answer in the interview

"OneToOne links exactly one entity to another, usually through a unique foreign key or a shared primary key with MapsId. OneToMany and ManyToOne are two views of the same foreign key: the key sits on the many side, so ManyToOne is the owning side that Hibernate writes, and OneToMany with mappedBy is the inverse side used for navigation. ManyToMany uses a join table, but once the link has its own data I model it as an entity with two ManyToOne relations. To-one associations are eager by default, so I make everything lazy, fetch per use case, keep both sides in sync with helper methods and use cascade only for true parent-child aggregates."

Likely follow-up questions

  • Why is updating only one side risky? Only the owning side is persisted, and the in-memory graph becomes inconsistent within the same transaction.
  • What does orphanRemoval do? Deletes a child row when it is removed from the parent's collection.
  • Why prefer Set for ManyToMany? Lists are treated as bags, so Hibernate deletes and reinserts all join rows on change.
