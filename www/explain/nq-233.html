How would you prevent inconsistent states during distributed transactions?

Microservices · design · levels senior, lead

In one line

Avoid 2PC and distributed locks; instead keep invariants inside one service where possible, and use sagas with compensations, outbox/CDC for reliable events, idempotency keys, explicit intermediate states with timeouts, and reconciliation and monitoring.

Detailed explanation

The best distributed transaction is the one you do not need. Start with service boundaries: if an invariant must always hold (an order's lines and total), keep that data in one service and one local ACID transaction. Splitting tightly coupled data across services creates the problem in the first place.

When a business process truly spans services, use a saga: a sequence of local transactions, each publishing an event or replying to an orchestrator, with a compensating action for each step (refund for charge, release for reservation). Model the saga as an explicit state machine with intermediate states such as PENDING_PAYMENT or AWAITING_STOCK. Users and support can see these states, and every step has a timeout, so a step that never answers leads to compensation instead of an order stuck forever. Order steps so that the hardest-to-undo action (shipping, sending money out) happens last; this is the idea of a pivot transaction.

Messages must be reliable (transactional outbox or CDC) and handlers idempotent, because retries and redeliveries are guaranteed to happen. Use idempotency keys for external APIs and a processed-message table for consumers. Sagas lack isolation, so other transactions may see intermediate states; counter that with semantic locks (a PENDING flag that blocks conflicting actions), commutative updates or rereading values before committing.

Finally, accept that something will still go wrong. Add correlation ids, dashboards of sagas per state and age, alerts on stuck ones, and reconciliation jobs that compare systems (for example, payments versus orders) and repair or escalate differences.

How it works

  1. Design boundaries so most invariants are local.
  2. For cross-service flows, define saga steps, compensations and the pivot step.
  3. Persist saga state; publish commands/events via outbox.
  4. Make every handler idempotent; dedupe by message id.
  5. Add timeouts per step, triggering compensation.
  6. Monitor states and run periodic reconciliation.

Example

Order saga (orchestrated)
PENDING -> reserve stock -> STOCK_RESERVED
        -> charge payment -> PAID          (pivot)
        -> create shipment -> CONFIRMED
Failure at charge -> release stock -> CANCELLED
No reply in 30 s  -> treat as failure -> compensate

Common mistakes

  • Using 2PC across microservices and coupling availability.
  • Compensations that are not idempotent.
  • No timeouts, so sagas hang in PENDING.
  • Ignoring lack of isolation between concurrent sagas.

How to answer in the interview

"First I try not to need distributed transactions by drawing boundaries so each invariant lives in one service. Where a process spans services, I use a saga: local transactions with compensations, modelled as a state machine with explicit states like PENDING_PAYMENT and timeouts on every step. Events go out through an outbox, all handlers are idempotent with idempotency keys or a processed-messages table, and irreversible steps come last. Then I add observability: correlation ids, dashboards of stuck sagas and reconciliation jobs that detect and repair mismatches. I accept eventual consistency instead of 2PC or distributed locks."

Likely follow-up questions

  • How would you design idempotency for a payment API? Client-supplied idempotency key stored with the result under a unique constraint; repeats return the stored response.
  • What if a compensation fails? Retry it with backoff; after limits, park it and alert for manual handling.
  • Orchestration or choreography? Orchestration for long, branching flows; choreography for short ones.
