How would you implement distributed tracing using OpenTelemetry?

Observability · design · levels senior, lead

In one line

Instrument services with the OpenTelemetry Java agent or Micrometer Tracing with the OTel bridge, propagate context with W3C traceparent over HTTP and Kafka headers, export spans via OTLP to an OpenTelemetry Collector, store them in Jaeger, Tempo or an APM, choose a sampling strategy, and correlate traces with logs and metrics.

Detailed explanation

Model: a trace is one request's journey; it consists of spans (operations) with a trace id, span id, parent id, timings, status and attributes following OpenTelemetry semantic conventions. A resource describes the emitting service (service.name, version, environment).

Instrumentation options for Java:

  • OpenTelemetry Java agent: attach with -javaagent; it bytecode-instruments Spring MVC and WebFlux, servlet containers, RestTemplate, RestClient, WebClient, JDBC, Kafka, gRPC, Redis and more without code changes. Configured with OTEL_* environment variables. Fastest way to cover a fleet.
  • Micrometer Tracing (Spring Boot 3): Spring's Observation API creates spans and metrics together; the micrometer-tracing-bridge-otel and an OTLP exporter send them out. More native to Spring configuration.
  • Manual spans for business steps via @WithSpan, the OTel Tracer API or @Observed, adding attributes such as order id (low-cardinality guidance applies to metrics, not span attributes).

Propagation: W3C traceparent/tracestate headers between services, Kafka record headers for messaging, and context propagation across threads for executors and reactive code.

Pipeline: services export via OTLP (gRPC 4317 or HTTP 4318) to an OpenTelemetry Collector, deployed as an agent per node or a gateway. The Collector batches, adds Kubernetes metadata, scrubs sensitive attributes, applies tail sampling and fans out to backends: Jaeger, Grafana Tempo, Zipkin, or vendors like Datadog, Honeycomb or New Relic, avoiding lock-in at the code level.

Sampling: head-based (decide at the root, e.g. parent-based 10%) is cheap but random; tail-based decides after the trace completes so you keep all errors and slow traces, at the cost of Collector memory. Correlation: put trace ids into logs via the MDC and use exemplars on latency histograms to jump from a metric spike to a trace.

How it works

  1. Add the agent or Micrometer Tracing dependencies to each service.
  2. Set service.name, environment and exporter endpoint.
  3. Context propagates via HTTP and Kafka headers automatically.
  4. Spans go via OTLP to the Collector.
  5. Collector samples, enriches and forwards to the backend.
  6. Dashboards link metrics → traces → logs by trace id.

Example

# OpenTelemetry Collector (excerpt)
receivers:
  otlp:
    protocols: { grpc: {}, http: {} }
processors:
  batch: {}
  tail_sampling:
    policies:
      - { name: errors, type: status_code, status_code: { status_codes: [ERROR] } }
      - { name: slow,   type: latency,     latency: { threshold_ms: 1000 } }
      - { name: sample, type: probabilistic, probabilistic: { sampling_percentage: 10 } }
exporters:
  otlp/tempo: { endpoint: tempo:4317, tls: { insecure: true } }
service:
  pipelines:
    traces: { receivers: [otlp], processors: [tail_sampling, batch], exporters: [otlp/tempo] }
@WithSpan("reserve-stock")
public void reserve(@SpanAttribute("order.id") String orderId) { ... }

Common mistakes

  • Exporting directly from every service to a vendor, losing central control of sampling and scrubbing.
  • Sampling 100% everywhere and getting a huge bill.
  • Losing context in thread pools, async code or custom messaging.
  • Traces not linked to logs, so engineers still grep.

How to answer in the interview

"A trace is made of spans linked by a trace id, and context is propagated between services with the W3C traceparent header, including Kafka message headers. In Java I either attach the OpenTelemetry agent, which auto-instruments Spring, HTTP clients, JDBC and Kafka without code changes, or use Spring Boot's Micrometer Tracing with the OTel bridge, plus custom spans for key business steps. Services export over OTLP to an OpenTelemetry Collector, which batches, scrubs and samples, then forwards to Tempo, Jaeger or a vendor. I use tail sampling to keep all errors and slow traces, and put the trace id in every log line so logs, metrics and traces connect."

Likely follow-up questions

  • Head vs tail sampling? Head decides at the start and is cheap; tail decides after completion, keeping interesting traces but needing Collector state.
  • Agent or Micrometer Tracing? Agent for zero-code broad coverage; Micrometer for Spring-native configuration and combined metrics.
  • Why a Collector? Vendor-neutral routing, central sampling, enrichment and data scrubbing.
