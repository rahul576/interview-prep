Explain volatile, synchronized and atomic classes. When is volatile not enough?

Concurrency · concept · levels mid, senior

In one line

volatile guarantees visibility and ordering (a happens-before edge) but not atomicity; synchronized gives mutual exclusion plus visibility; atomic classes use CAS for lock-free single-variable updates. volatile is not enough for compound actions like count++ or check-then-act.

Detailed explanation

Under the Java Memory Model, threads may keep values in registers or caches and the compiler and CPU may reorder instructions. Without a happens-before relationship, one thread may never see another's write.

volatile fixes visibility for one field: a write to a volatile variable happens-before every subsequent read of it, and writes before the volatile write become visible to a thread that reads it (safe publication). It also prevents reordering across the access. It does not provide mutual exclusion. count++ on a volatile int is still three steps, read, add, write, so two threads can read 5, both write 6 and lose an update. Check-then-act (if (!started) { started = true; init(); }) has the same race.

synchronized acquires the object's monitor lock. Only one thread executes the block at a time, and releasing the monitor happens-before the next acquisition, so you get atomicity and visibility for everything inside. It is reentrant and, when uncontended, cheap. It can block, and before Java 24 it could pin virtual threads.

Atomic classes (AtomicInteger, AtomicLong, AtomicReference, AtomicBoolean) wrap a volatile value and update it with compare-and-swap: read the current value, compute the new one, and CAS it in; if another thread changed it, retry. That makes incrementAndGet, compareAndSet and updateAndGet atomic without locks. Under heavy write contention CAS retries pile up, so LongAdder spreads increments across cells and sums on read. Atomics cover one variable; invariants spanning several variables still need a lock.

Use volatile for simple flags and safely publishing immutable objects; atomics for counters and single-reference swaps; locks for multi-variable invariants.

How it works

  1. volatile write: flush with a release barrier; volatile read: acquire barrier.
  2. synchronized: monitorenter, critical section, monitorexit (release).
  3. CAS: hardware instruction (for example lock cmpxchg on x86) that writes only if the value is unchanged.
  4. Retry loop on CAS failure.

Example

class Worker implements Runnable {
    private volatile boolean running = true;          // volatile is enough
    public void stop() { running = false; }
    public void run() { while (running) doWork(); }
}

class Counter {
    private volatile int broken;      // broken++ loses updates
    private final AtomicInteger ok = new AtomicInteger();
    private final LongAdder hot = new LongAdder();     // heavy contention
    void inc() { broken++; ok.incrementAndGet(); hot.increment(); }
}

class Account {                       // two fields, one invariant -> lock
    private long balance, version;
    synchronized void deposit(long amt) { balance += amt; version++; }
}

Common mistakes

  • Using volatile for counters.
  • Thinking synchronized only matters for writes; reads need it too for visibility.
  • Using several atomics for one multi-field invariant.
  • Double-checked locking without volatile.

How to answer in the interview

"volatile guarantees visibility: a write to a volatile field happens-before subsequent reads, so threads don't see stale values, and it prevents certain reorderings. But it gives no mutual exclusion, so count++ on a volatile is not atomic and can lose updates. synchronized takes the monitor lock, giving both mutual exclusion and visibility. Atomic classes like AtomicInteger use compare-and-swap to update a single variable atomically without locks, and LongAdder is better under heavy contention. I use volatile for simple flags like a shutdown signal, atomics for counters, and locks when several variables must change together."

Likely follow-up questions

  • Why is double-checked locking broken without volatile? Reordering can publish the reference before the constructor finishes, so another thread sees a half-built object.
  • What is the ABA problem? A CAS succeeds although the value changed and changed back; use AtomicStampedReference.
  • Is volatile long/double write atomic? Yes; non-volatile 64-bit writes may tear on some JVMs.
