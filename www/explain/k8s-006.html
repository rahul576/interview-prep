What is a headless Service, and why do StatefulSets use one?

Kubernetes · concept · levels entry, mid

In one line

A headless Service has clusterIP: None: no virtual IP and no kube-proxy load balancing, so DNS returns the pod IPs directly; with a StatefulSet it gives each pod a stable DNS name such as db-0.db.prod.svc.cluster.local, used for peer discovery and for clients that must reach a specific instance.

Detailed explanation

A normal ClusterIP Service hides pods behind one virtual IP and spreads connections randomly across them. That is perfect for stateless replicas but wrong for clustered stateful systems, where members are not interchangeable: one is the primary, each holds different shards, and peers must address each other individually.

With clusterIP: None, the Service still has a selector and EndpointSlices, but CoreDNS behaves differently: a lookup for db.prod.svc.cluster.local returns A/AAAA records for every ready pod, and SRV records for named ports. The client decides which to connect to.

A StatefulSet references a headless Service in spec.serviceName. Its pods have stable ordinal names (db-0, db-1, db-2), and DNS publishes a record for each: db-0.db.prod.svc.cluster.local. When db-1 is rescheduled to another node it gets a new IP, but the name stays the same and DNS is updated, and it reattaches to the same PersistentVolumeClaim (data-db-1). This stable network identity plus stable storage is what Kafka brokers, ZooKeeper ensembles, Elasticsearch nodes, Cassandra seeds and MongoDB or PostgreSQL replica sets rely on: configuration can list peers by name, and clients can target the leader or a specific shard.

Teams often add a second, normal ClusterIP Service for clients that just need any ready replica, for example read traffic. By default only ready pods are published; publishNotReadyAddresses: true publishes all pods, which some clusters need so members can discover each other while bootstrapping before they are ready.

How it works

  1. Create a headless Service selecting the database pods.
  2. StatefulSet sets serviceName to it.
  3. Pods db-0..2 are created in order, each with its own PVC.
  4. CoreDNS serves per-pod records and a list of all ready pod IPs.
  5. Members join the cluster using peer names; clients connect to the chosen member.

Example

apiVersion: v1
kind: Service
metadata: { name: db, namespace: prod }
spec:
  clusterIP: None
  selector: { app: db }
  ports: [ { name: pg, port: 5432 } ]
---
apiVersion: apps/v1
kind: StatefulSet
metadata: { name: db, namespace: prod }
spec:
  serviceName: db
  replicas: 3
  selector: { matchLabels: { app: db } }
  template:
    metadata: { labels: { app: db } }
    spec:
      containers: [ { name: pg, image: postgres:17 } ]
kubectl run -it dns --rm --image=busybox:1.36 -- nslookup db-0.db.prod.svc.cluster.local

Common mistakes

  • Forgetting to create the Service named in serviceName, so per-pod DNS never appears.
  • Expecting load balancing from a headless Service.
  • Clients caching resolved IPs forever after a pod moves.
  • Using a StatefulSet when a Deployment would do.

How to answer in the interview

"A headless Service has clusterIP None, so there's no virtual IP and no load balancing; DNS returns the pod IPs directly. With a StatefulSet it also gives every pod a stable DNS name like db-0.db.prod.svc.cluster.local, which survives rescheduling even though the IP changes. Clustered systems such as Kafka, ZooKeeper or a database replica set use those names for peer discovery, and clients can reach a specific member, like the primary. I usually add a normal ClusterIP Service alongside it for clients that just want any ready replica."

Likely follow-up questions

  • What does publishNotReadyAddresses do? Publishes DNS records for pods that aren't ready, for bootstrapping peer discovery.
  • Can a Deployment use a headless Service? Yes, for client-side load balancing like gRPC, but pods get no stable names.
  • What are SRV records used for? Discovering ports by name along with hosts.
