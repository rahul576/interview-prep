What makes a good MCP tool, beyond simply working?

MCP Servers · concept · levels mid, senior

In one line

A good MCP tool is designed around a user task rather than a raw endpoint, with a clear name and description, a strict minimal schema, concise output that respects the context window, actionable errors, and safe defaults (read-only first, explicit side effects).

Detailed explanation

A tool that "works" when called correctly is the minimum. The real consumer is a model choosing among many tools with limited context, so tool quality is about how reliably an agent can use it.

Task-oriented design. find_customer_orders(email) beats exposing GET /customers?q=, GET /customers/{id}/accounts and GET /accounts/{id}/orders, which forces the model to chain three calls and juggle internal ids. Combine steps server-side.

Clear name and description. Say what it does, when to use it, what it does not do, and how it relates to other tools ("use search_customers first if you only have a name").

Strict, minimal input schema. Few parameters, enums for fixed choices, formats (date, email), sensible defaults and bounds. Validate everything server-side; the model will sometimes send nonsense.

Concise, relevant output. Every token returned lands in the model context. Return the fields that matter, paginate, summarise large results, and include totals so the model knows if there is more. Provide structuredContent with an outputSchema when code will consume it.

Actionable errors. Return execution errors with isError: true and a message the model can act on: "date must be YYYY-MM-DD", "customer not found; try search_customers".

Safe by default. Prefer read-only tools; make side effects explicit, scoped and idempotent (idempotency keys), annotate them correctly, and use the caller's permissions.

How it works

  1. List real user tasks and the questions agents must answer.
  2. Design one tool per task, hiding internal ids and pagination.
  3. Write description and schema; add enums and bounds.
  4. Shape outputs to essential fields; add pagination and totals.
  5. Write errors with recovery hints.
  6. Evaluate with a model on realistic tasks and iterate.

Example

@mcp.tool()
def find_customer_orders(email: str, status: Literal["open", "shipped", "all"] = "open",
                         limit: int = 10) -> dict:
    """Find a customer's recent orders by email. Use for order status questions.
    Returns at most `limit` (1-25) orders, newest first, with total count."""
    customer = crm.by_email(email)
    if not customer:
        raise ToolError(f"No customer with email {email}. Ask the user to confirm the email.")
    orders = shop.orders(customer.id, status=status, limit=min(limit, 25))
    return {"total": orders.total,
            "orders": [{"order_no": o.number, "status": o.status, "eta": o.eta} for o in orders]}

Common mistakes

  • Auto-generating one tool per REST endpoint.
  • Returning full API payloads with dozens of irrelevant fields.
  • Errors like "500 Internal Server Error" or stack traces.
  • Write tools without idempotency or confirmation.
  • Never testing with an actual model.

How to answer in the interview

"Beyond working, a good tool is designed around a task the agent actually needs, like find_customer_orders, instead of mirroring endpoints and forcing the model to chain calls. Its name and description say what it does and when to use it. The input schema is strict and minimal, with enums and validation. Output is concise, because every token goes into the context, with pagination or summaries for large results. Errors are actionable so the model can recover. And it's safe by default: read-only where possible, side effects explicit, scoped and idempotent. Then I test it with a real model, not just unit tests."

Likely follow-up questions

  • How do you test model usage? Evaluation tasks run by an agent, checking tool choice, arguments and task success.
  • How many tools per server? As few as cover the tasks, often under a dozen or two.
  • Should tools return prose or JSON? Short readable text for the model, plus structuredContent for programmatic use.
