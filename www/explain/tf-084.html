During an incident an engineer changed a production resource manually in the portal. How do you reconcile Terraform afterwards?

Terraform · scenario · levels mid, senior

In one line

Record the manual change in the incident timeline, run a plan to see the drift, then decide: keep it by updating the code in a PR until the plan is clean, or revert with a planned apply; make sure nobody applies in between and silently undoes the fix, and use a break-glass process that tracks such changes.

Detailed explanation

During an incident, speed matters more than process: scaling up a database tier, opening a firewall rule temporarily or changing an app setting in the portal can be the right call. The risk comes afterwards. The code still describes the old state, so the next routine apply, perhaps an unrelated change by another engineer, will quietly revert the fix and can restart the incident.

Record it. The person making the change notes in the incident channel and timeline exactly what was changed, where and why. A break-glass process with elevated just-in-time access makes such changes visible, and automatically creates a follow-up ticket for reconciliation.

See the drift. After stabilisation, run a plan (or refresh-only plan) for the affected state. It shows precisely how reality differs from code, which sometimes reveals more changes than people remember.

Decide per change, with the owning team:

  • Keep: the change is right, for example the database really needs the larger tier. Update the code in a PR, so the plan for that resource becomes clean. That is codifying the fix.
  • Revert: the change was a temporary workaround, for example a widened firewall rule. Schedule a normal reviewed apply to restore the codified state, after confirming the root cause is fixed.

Protect the window. Until reconciled, consider pausing applies to that state, or flag the drift in the pipeline so reviewers see "this plan would revert incident change X".

How it works

  1. Make the emergency change via break-glass; log it in the timeline.
  2. After stabilisation, run a plan for the affected state.
  3. Review the drift with the owning team.
  4. Keep: update code in a PR until the plan is clean.
  5. Revert: planned apply restoring the codified state.
  6. Close the follow-up ticket; update runbooks if needed.

Example

terraform plan -refresh-only
#  ~ azurerm_postgresql_flexible_server.main
#      ~ sku_name = "GP_Standard_D2ds_v5" -> "GP_Standard_D8ds_v5"   (changed in portal during INC-4211)
# Keep the change: codify it
resource "azurerm_postgresql_flexible_server" "main" {
  # ...
  sku_name = "GP_Standard_D8ds_v5"   # INC-4211: scaled up, confirmed needed
}

Common mistakes

  • No record of the change, so nobody knows why drift exists.
  • A routine apply reverting the fix days later.
  • Leaving temporary security relaxations in place forever.

How to answer in the interview

"Manual changes during incidents can be the right call, but they must be reconciled quickly. The change should be in the incident timeline. Afterwards I run a plan for the affected state to see the drift. Then we decide: if the change should stay, like a larger database tier, we update the code in a PR so the plan becomes clean; if it was temporary, a normal apply restores the codified state at a planned time. The key is that nobody runs an apply in between that silently reverts the fix. A break-glass process makes these changes visible and creates the follow-up task."

Likely follow-up questions

  • How does drift detection help? It catches unrecorded changes and keeps reminding until reconciled.
  • Should incident fixes go through Terraform? If the pipeline is fast and healthy, yes; otherwise break-glass.
  • How do you prevent accidental reverts? Plan review that flags known drift, or a temporary apply freeze.
