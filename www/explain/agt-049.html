How can machine learning predict the risk of a deployment or change?

AI Agents & AIOps · concept · levels mid, senior

In one line

Change risk prediction trains a model on features of past changes (size, files, config or migrations, coverage, criticality, author familiarity, timing) labelled by whether they caused incidents, rollbacks or hotfixes, and uses the risk score to adapt reviews and rollout, not to block changes blindly.

Detailed explanation

Most production incidents follow a change, but most changes are harmless. Treating them all the same means either slowing everything down with heavy approvals or letting risky changes through unnoticed. A risk model lets the process scale controls to the risk.

Features describe the change: lines and files changed, number of services touched, whether it modifies configuration, database schemas, infrastructure or dependency versions, test coverage of the changed code, the service's criticality tier, recent incident history of the touched files, the author's familiarity with that code, review depth and timing such as Friday evening or holiday freezes. Labels come from linking past changes to incidents, rollbacks and hotfixes, which requires disciplined incident records.

A model, often gradient-boosted trees or logistic regression for explainability, outputs a risk score. Low-risk changes flow through normal automation; high-risk ones get an extra reviewer, a slower canary, deployment during staffed hours or additional tests. Because models are imperfect and labels are noisy, the score guides decisions and explains its reasons, rather than blocking changes. Consistently linking incidents to changes creates the feedback loop that keeps the model accurate.

How it works

  1. Collect change metadata from Git, CI/CD and the change system.
  2. Link incidents and rollbacks to the changes that caused them.
  3. Train and validate a model on historical data, time-split.
  4. Score each new pull request or deployment and show top risk factors.
  5. Map score bands to rollout policies.
  6. Retrain regularly; monitor precision and recall.

Example

change_risk_policy:
  low:    { score_below: 0.2, rollout: standard, approvals: 1 }
  medium: { score_below: 0.6, rollout: canary_10_percent_30min, approvals: 1 }
  high:   { rollout: canary_1_percent_then_manual, approvals: 2,
            window: business_hours, extra: [integration_tests, db_owner_review] }
# PR #4410 score 0.71: touches 3 services, includes DB migration,
# payments tier-1, author first change in module, Friday 17:40

Common mistakes

  • Training on poorly linked incident data, producing a meaningless model.
  • Using the score to block deploys with no explanation.
  • Features that are proxies for blaming individuals.
  • Ignoring that risk-based slowdowns change future labels (feedback effects).

How to answer in the interview

"The model learns from history which kinds of changes cause incidents. Features include size, number of services and files, whether it touches config, migrations or dependencies, test coverage, service criticality, author familiarity and timing. Labels come from linking past changes to incidents, rollbacks and hotfixes. Each new change gets a risk score, and we adapt the process: low risk flows through automation, high risk gets extra review, a slower canary or a staffed deployment window. It guides rather than blocks, and accurate incident-to-change linking keeps it useful."

Likely follow-up questions

  • Data problems? Unlinked incidents, inconsistent labels, few positive examples.
  • Explainability? Show top contributing factors so engineers trust the score.
  • Evaluation? Precision at the high-risk band and incidents caught in that band.
