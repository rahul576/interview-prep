What are the four pillars of object-oriented programming, and how does Java support each of them?

Core Java & OOP · concept · levels entry, mid

In one line

The four pillars are encapsulation (private state behind methods), inheritance (extends for reuse and specialisation), polymorphism (overriding with dynamic dispatch, plus overloading) and abstraction (abstract classes and interfaces as contracts).

Detailed explanation

Encapsulation bundles data with the behaviour that operates on it and hides internal state. In Java you make fields private and expose meaningful operations (account.withdraw(amount)) rather than raw setters, so the class can enforce its invariants (a balance never goes negative) and change its internals without breaking callers. Access modifiers (private, package-private, protected, public) and, since Java 9, modules control visibility.

Inheritance lets a subclass reuse and specialise a superclass with extends; Java allows single class inheritance but multiple interface implementation. Subclasses inherit fields and methods and can override behaviour. It models "is-a" relationships, but deep hierarchies are fragile, so modern design prefers composition over inheritance and uses final or sealed classes (Java 17) to control extension.

Polymorphism means one reference type, many behaviours. Runtime polymorphism comes from method overriding and dynamic dispatch: PaymentMethod p = new CardPayment(); p.pay() calls CardPayment.pay() based on the actual object, decided at runtime. Compile-time polymorphism is method overloading: same name, different parameter lists, resolved by the compiler. Generics add parametric polymorphism.

Abstraction exposes what an object does, not how. Interfaces define contracts (PaymentGateway, Comparable), and abstract classes provide partial implementations. Callers depend on the abstraction, so implementations can be swapped, mocked in tests or injected by Spring. This is the basis of the dependency inversion principle.

The pillars work together: abstraction defines the contract, encapsulation protects each implementation, inheritance or interface implementation creates the variants, and polymorphism lets client code treat them uniformly.

How it works

  1. Define an abstraction: an interface or abstract class describing behaviour.
  2. Implement it in concrete classes that encapsulate their own state.
  3. Reuse shared code via inheritance from an abstract base where it fits.
  4. Client code holds references of the abstract type.
  5. At runtime, the JVM dispatches each call to the actual object's override.

Example

public interface Notifier {                         // abstraction
    void send(String to, String message);
}

public abstract class BaseNotifier implements Notifier {  // inheritance base
    private int sentCount;                          // encapsulated state
    public final void send(String to, String message) {
        deliver(to, format(message));
        sentCount++;
    }
    protected String format(String m) { return "[Shop] " + m; }
    protected abstract void deliver(String to, String text);
    public int sentCount() { return sentCount; }
}

public class EmailNotifier extends BaseNotifier {
    @Override protected void deliver(String to, String text) { /* SMTP */ }
}
public class SmsNotifier extends BaseNotifier {
    @Override protected void deliver(String to, String text) { /* SMS API */ }
    @Override protected String format(String m) { return m.substring(0, Math.min(160, m.length())); } // override
}

List<Notifier> channels = List.of(new EmailNotifier(), new SmsNotifier());
channels.forEach(n -> n.send("user-42", "Your order shipped"));   // polymorphism

Common mistakes

  • Equating encapsulation with "getters and setters for every field".
  • Using inheritance for code reuse where composition fits better.
  • Calling overloading "runtime polymorphism".
  • Confusing abstraction (hiding complexity) with encapsulation (hiding state).

How to answer in the interview

"Encapsulation hides internal state behind private fields and exposes meaningful methods, so the class protects its invariants. Inheritance lets a subclass reuse and specialise another class with extends; Java allows one superclass but many interfaces, and I prefer composition when it's not a true is-a relationship. Polymorphism lets one reference call different implementations: at runtime through overriding and dynamic dispatch, and at compile time through overloading. Abstraction exposes only essential behaviour via interfaces and abstract classes, so callers depend on contracts. For example, a Notifier interface with email and SMS implementations lets the order service send notifications without knowing the channel."

Likely follow-up questions

  • Can you give a concrete example of runtime polymorphism from a project you worked on? For example, a PaymentGateway interface with Stripe and PayPal implementations chosen by Spring at runtime, with the checkout code calling gateway.charge().
  • Why prefer composition over inheritance? It avoids fragile base classes and tight coupling and lets you change behaviour at runtime.
  • What are sealed classes? Java 17 classes or interfaces that restrict which classes may extend or implement them.
