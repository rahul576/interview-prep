When would you use a time series database, a search engine or a data warehouse instead of the main database?

Data & Storage Design · concept · levels entry, mid, senior

In one line

Keep the transactional DB as the source of truth and add specialised stores for specialised workloads: time-series DBs for metrics, search engines for full-text, warehouses/lakehouses for analytics, fed via CDC or events.

Detailed explanation

OLTP databases are optimised for many small, indexed reads and writes with transactions. They struggle with:

  • Huge timestamped streams (metrics, IoT): time-series DBs (Prometheus, InfluxDB, TimescaleDB) compress points heavily and support downsampling and window queries.
  • Text search: Elasticsearch/OpenSearch provide inverted indexes, relevance scoring (BM25), typo tolerance, synonyms and facets.
  • Analytics over billions of rows: warehouses (Snowflake, BigQuery, Redshift, Databricks) use columnar storage, so SUM(amount) GROUP BY region reads only two columns, compressed, in parallel.

Running these on the main DB hurts the OLTP workload and is slow. But each extra store adds operations, cost and sync lag, so add one only for a real need.

How it works

  1. Primary DB handles transactions.
  2. CDC (Debezium) or domain events stream changes out.
  3. Consumers index into search, load into the warehouse, or write metrics.
  4. Derived stores are rebuildable from the source and tolerate slight staleness.

Example

An e-commerce site: PostgreSQL for orders; Debezium → Kafka → Elasticsearch for product search; Kafka → S3/Iceberg → Snowflake for BI; Prometheus for service metrics.

Common mistakes

  • Running heavy reports on the production primary.
  • Treating Elasticsearch as the source of truth.
  • Dual writes from the app to DB and search index.
  • Adding a new database for every feature.

How to answer in the interview

"The relational DB stays the source of truth for transactions. For search I'd add Elasticsearch, for metrics a time-series DB, and for analytics a warehouse with columnar storage. All are fed from the primary via CDC or events, never by dual writes, and they're rebuildable. I'd only add each one when the workload justifies the operational cost."

Likely follow-up questions

  • How do you keep the search index in sync? CDC to Kafka to an indexer; periodic full reindex via alias swap.
  • Why is columnar faster for analytics? Reads only needed columns, better compression, vectorised execution.
  • OLTP vs OLAP? Many small transactions vs few large scans and aggregations.
