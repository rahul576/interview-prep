What is the Builder pattern?

Design Patterns · concept · levels mid, senior

In one line

Builder is a creational pattern that constructs a complex object step by step through a fluent API ending in build(), avoiding telescoping constructors and enabling validation and immutability.

Detailed explanation

Imagine an Order with a required customer id and ten optional fields: currency, coupon, express delivery, gift message, notes and so on. Two bad options exist without a builder:

  • Telescoping constructors: many overloaded constructors, or one with ten parameters where new Order(42, null, "INR", true, false, null, ...) is unreadable and two booleans or two Strings can be swapped without a compiler error.
  • JavaBeans setters: readable, but the object is mutable and may be observed in an inconsistent, half-built state.

A builder solves both. It is usually a static nested class holding the same fields; each method sets one value and returns this, so calls chain with named steps. build() checks invariants (required fields, valid combinations such as "express requires an address") and then calls a private constructor that copies the values into final fields, producing an immutable, thread-safe object.

Java examples: StringBuilder (a related, mutable accumulator), HttpRequest.newBuilder(), HttpClient.newBuilder(), Stream.builder(), Locale.Builder, Spring's UriComponentsBuilder, ResponseEntity.ok()..., and Lombok @Builder, which generates the boilerplate. Records are immutable but have only a canonical constructor, so for records with many fields a hand-written or Lombok builder (Lombok supports @Builder on records) still helps.

Builders are also excellent for test data (anOrder().withStatus(PAID).build()).

How it works

  1. Create a static nested Builder with fields mirroring the target class.
  2. Provide fluent setter-like methods returning this.
  3. Put required parameters in the builder's constructor or validate them in build().
  4. build() validates and calls the private constructor.
  5. The target class has final fields and no setters.

Example

public final class Order {
    private final long customerId; private final String currency; private final boolean express;
    private Order(Builder b) { customerId = b.customerId; currency = b.currency; express = b.express; }
    public static Builder builder() { return new Builder(); }

    public static final class Builder {
        private Long customerId; private String currency = "INR"; private boolean express;
        public Builder customerId(long id) { this.customerId = id; return this; }
        public Builder currency(String c)  { this.currency = c; return this; }
        public Builder express(boolean e)  { this.express = e; return this; }
        public Order build() {
            if (customerId == null) throw new IllegalStateException("customerId required");
            return new Order(this);
        }
    }
}
Order o = Order.builder().customerId(42).currency("INR").express(true).build();

Common mistakes

  • Using a builder for a class with two fields.
  • Not validating in build(), so invalid objects still get created.
  • Lombok @Builder on JPA entities: it needs an all-args constructor, conflicts with the no-args constructor JPA requires, and ignores field initialisers unless you use @Builder.Default.
  • Reusing one builder instance across threads.

How to answer in the interview

"Builder is a creational pattern for constructing complex objects step by step. It solves the telescoping-constructor problem, where many optional parameters lead to lots of constructors or one with ten arguments that are easy to mix up. With a builder I write Order.builder().customerId(42).currency("INR").express(true).build(); every value is named, optional ones can be skipped, and build validates the combination. Because the object is created in one step, its fields can be final, so it's immutable. JDK examples are HttpRequest.newBuilder and StringBuilder, and Lombok @Builder generates it."

Likely follow-up questions

  • Downsides of Lombok @Builder on JPA entities? Conflicts with the required no-args constructor, loses default values without @Builder.Default, and lets code bypass domain invariants.
  • Builder vs static factory? Factories suit a few parameters; builders suit many optional ones.
  • How does a builder support immutability? All values are collected first, then assigned once to final fields in the constructor.
