How would you create beans conditionally for different microservices?

Spring Boot · scenario · levels mid, senior

In one line

Make behaviour configuration-driven: guard optional beans with @ConditionalOnProperty, handle environments with profiles, activate technology-specific beans with @ConditionalOnClass, package shared ones as auto-configuration with @ConditionalOnMissingBean defaults, supply properties via externalised config, and test with ApplicationContextRunner.

Detailed explanation

In a microservice estate, many services share code but need different beans: the order service publishes audit events, the catalogue service doesn't; one service uses Kafka, another RabbitMQ; production uses a real payment client, staging a sandbox. The goal is one codebase or library, many configurations, without if (serviceName.equals(...)) branches.

Per-service switches use @ConditionalOnProperty, for example audit.publisher.enabled=true only in the order service. Environment differences (dev, staging, prod) use profiles or profile-specific property files. Technology choices use @ConditionalOnClass, so the Kafka-based publisher activates only in services that have the Kafka client on their classpath, and a RabbitMQ variant activates elsewhere.

If these beans live in a shared library, I package them as auto-configuration listed in AutoConfiguration.imports, with @ConditionalOnMissingBean defaults so any service can override a bean by defining its own. Configuration is bound with @ConfigurationProperties so each option is documented and validated.

The property values themselves come from each service's application.yml, a config server, Kubernetes ConfigMaps and environment variables, or a secrets manager. Finally, I test each combination with ApplicationContextRunner, which starts a lightweight context with chosen properties and classpath, asserting which beans exist.

How it works

  1. Identify beans that vary by service, environment or technology.
  2. Choose the condition type: property, profile, class or missing bean.
  3. Bind settings to a @ConfigurationProperties class with defaults.
  4. Package shared beans as auto-configuration in a starter.
  5. Set properties per service via YAML, config server or env vars.
  6. Write context-runner tests for enabled and disabled cases.

Example

@AutoConfiguration
@EnableConfigurationProperties(AuditProps.class)
public class AuditAutoConfiguration {

    @Bean
    @ConditionalOnClass(name = "org.springframework.kafka.core.KafkaTemplate")
    @ConditionalOnProperty(prefix = "audit.publisher", name = "enabled", havingValue = "true")
    @ConditionalOnMissingBean(AuditPublisher.class)
    AuditPublisher kafkaAuditPublisher(KafkaTemplate<String, AuditEvent> t, AuditProps p) {
        return new KafkaAuditPublisher(t, p.getTopic());
    }
}

class AuditAutoConfigurationTest {
    ApplicationContextRunner runner = new ApplicationContextRunner()
        .withConfiguration(AutoConfigurations.of(AuditAutoConfiguration.class))
        .withBean(KafkaTemplate.class, () -> mock(KafkaTemplate.class));

    @Test void disabledByDefault() {
        runner.run(ctx -> assertThat(ctx).doesNotHaveBean(AuditPublisher.class));
    }
    @Test void enabledByProperty() {
        runner.withPropertyValues("audit.publisher.enabled=true")
              .run(ctx -> assertThat(ctx).hasSingleBean(AuditPublisher.class));
    }
}

Common mistakes

  • Branching on service names in code instead of configuration.
  • Overusing profiles for feature flags, leading to profile explosion.
  • Shared libraries that create beans unconditionally, forcing every service to exclude them.
  • Testing only the default configuration.

How to answer in the interview

"I keep the behaviour switchable through configuration rather than code branches. Beans only some services need are guarded by OnProperty, for example audit.publisher.enabled in the order service only. Environment differences use profiles, and technology-specific beans use OnClass, so the Kafka publisher activates only where Kafka is on the classpath. In a shared library I package them as auto-configuration with OnMissingBean defaults so a service can override them. Properties come from application.yml, a config server or Kubernetes env vars, and I test both enabled and disabled cases with ApplicationContextRunner."

Likely follow-up questions

  • How do you test conditional configuration? ApplicationContextRunner with properties, beans and FilteredClassLoader.
  • Profiles or properties? Profiles for environments, properties for individual features.
  • Runtime toggles? Use a feature-flag service; conditions are evaluated only at startup.
