What is AWS Step Functions, and when would you use it?

Cloud (AWS) · concept · levels mid

In one line

Step Functions is serverless workflow orchestration using state machines written in Amazon States Language, with Task, Choice, Parallel, Map, Wait and callback states, built-in retries and catch, full execution history, and Standard (long-running, exactly-once) or Express (high-volume, short) workflows.

Detailed explanation

Instead of chaining Lambda functions that call each other, you describe the process as a state machine in JSON (Amazon States Language) or in Workflow Studio. Task states call Lambda or, through SDK integrations, almost any AWS API directly (DynamoDB, SQS, ECS, Glue, Bedrock and many more), so a lot of glue code disappears. Choice branches, Parallel runs branches concurrently, Map iterates over a list, and Distributed Map processes millions of S3 objects with high concurrency. Wait pauses for a duration or timestamp. The .waitForTaskToken pattern pauses until an external system, for example a human approval, calls SendTaskSuccess.

Each Task can declare Retry rules with error types, interval, backoff rate, jitter and max attempts, and Catch rules that route errors to fallback or compensation states. Every execution keeps a visual, step-by-step history with inputs and outputs, which makes debugging much easier than reading logs from many functions. Data is passed between states as JSON, and newer JSONata support simplifies transformations.

Standard workflows run up to one year, have exactly-once step execution, and are billed per state transition, suited to business processes. Express workflows run up to five minutes with at-least-once semantics (asynchronous) or synchronous invocation, billed by duration, suited to high-volume event processing.

Use it for sagas with compensation, order and payment flows, ETL and ML pipelines, human approval steps, and fan-out batch jobs. Avoid it for ultra-low-latency request paths or trivial single-step tasks.

How it works

  1. Define the state machine with states and transitions.
  2. Start an execution with JSON input (API, EventBridge, API Gateway).
  3. Each state runs, transforms its input and passes output on.
  4. Errors trigger Retry, then Catch routes to recovery or compensation.
  5. The execution ends in Succeed or Fail with full history.

Example

Saga step with retry and compensation:

{
  "StartAt": "ReserveInventory",
  "States": {
    "ReserveInventory": {
      "Type": "Task",
      "Resource": "arn:aws:states:::lambda:invoke",
      "Parameters": {"FunctionName": "reserve-inventory", "Payload.$": "$"},
      "Retry": [{"ErrorEquals": ["States.TaskFailed"], "IntervalSeconds": 2,
                 "BackoffRate": 2, "MaxAttempts": 3}],
      "Next": "ChargePayment"
    },
    "ChargePayment": {
      "Type": "Task",
      "Resource": "arn:aws:states:::lambda:invoke",
      "Parameters": {"FunctionName": "charge-payment", "Payload.$": "$"},
      "Catch": [{"ErrorEquals": ["States.ALL"], "Next": "ReleaseInventory"}],
      "End": true
    },
    "ReleaseInventory": {
      "Type": "Task",
      "Resource": "arn:aws:states:::lambda:invoke",
      "Parameters": {"FunctionName": "release-inventory", "Payload.$": "$"},
      "Next": "OrderFailed"
    },
    "OrderFailed": {"Type": "Fail"}
  }
}

Common mistakes

  • Using Express workflows for non-idempotent steps that must run exactly once.
  • Passing large payloads between states (256 KB limit); store data in S3.
  • Wrapping every AWS call in Lambda when a direct SDK integration exists.
  • No retries with backoff for transient throttling errors.

How to answer in the interview

"Step Functions orchestrates multi-step workflows as state machines. Task states call Lambda or two hundred plus AWS services directly; Choice branches, Parallel runs steps concurrently, Map iterates, Wait pauses, and task tokens wait for callbacks like human approvals. Retries with backoff and Catch blocks are declared per step, and every execution has a visual history. Standard workflows run up to a year with exactly-once steps; Express is cheaper and faster for high-volume, short flows. I use it for order sagas, ETL pipelines and approval flows."

Likely follow-up questions

  • How implement a saga with compensation? Each step has a Catch that runs compensating tasks in reverse order, then fails the execution.
  • Standard or Express for an API backend? Synchronous Express for short request-response flows.
  • How do you wait for a human? Use .waitForTaskToken and have the approval app call SendTaskSuccess.
