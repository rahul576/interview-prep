When would you use the azapi provider instead of azurerm for Azure resources?

Terraform · concept · levels mid, senior

In one line

azurerm is the curated, typed provider and the default choice; azapi talks directly to Azure Resource Manager REST APIs with an explicit resource type and API version, giving day-zero support for new or preview features and the ability to patch azurerm-managed resources, at the cost of less validation.

Detailed explanation

azurerm has hand-written resources such as azurerm_kubernetes_cluster with typed arguments, validation, sensible defaults, import support and documentation. It covers the large majority of Azure services and is easier to read and review. Its limitation is lag: a new Azure feature or preview API appears in azurerm only when someone implements and releases it, which can take weeks or months.

azapi is a thin layer over ARM. An azapi_resource declares a type with API version, such as Microsoft.Storage/storageAccounts@2023-05-01, a parent ID, a name and a body that matches the ARM schema. In azapi 2.x the body is a native HCL object rather than a JSON string, and the provider can validate it against embedded ARM schemas. Anything ARM supports, including preview API versions, is available immediately. azapi_update_resource patches specific properties on a resource that azurerm creates, filling one missing setting without taking over the whole resource. There are also data sources and azapi_resource_action for POST operations.

Trade-offs: fewer friendly abstractions, you own API version management, defaults and some validation are weaker, and preview APIs can change. My rule is azurerm by default, azapi for gaps, documented with a comment, and migrate to azurerm when the feature lands there, typically with a removed block (destroy false) for the azapi resource and an import block for the azurerm resource, so nothing is recreated.

How it works

  1. Check azurerm for the resource or property; use it if available.
  2. If missing, find the ARM resource type, API version and schema.
  3. Write azapi_resource or azapi_update_resource with the body.
  4. Export needed response values with response_export_values.
  5. Track the gap; when azurerm supports it, migrate via removed plus import.

Example

resource "azapi_update_resource" "aks_preview_setting" {
  type        = "Microsoft.ContainerService/managedClusters@2024-05-01"
  resource_id = azurerm_kubernetes_cluster.main.id

  body = {
    properties = {
      # property not yet exposed by azurerm (illustrative)
      someNewFeature = { enabled = true }
    }
  }
}

Common mistakes

  • Using azapi for everything and losing readability and validation.
  • Managing the same property with both azurerm and azapi_update_resource, causing a tug of war.
  • Pinning old preview API versions forever.
  • Never migrating back when azurerm adds support.

How to answer in the interview

"azurerm is the main provider with typed, validated resources, so it's my default. Its limitation is that new or preview Azure features arrive only when implemented. azapi talks straight to the ARM REST API: you give the resource type with an API version and a body matching the ARM schema, so you get day-zero support, and azapi_update_resource can patch a property on an azurerm-managed resource. The trade-off is less validation and managing API versions yourself. I use azapi for gaps and migrate to azurerm when support lands."

Likely follow-up questions

  • How do you migrate later without recreating? Removed block with destroy = false for azapi, import block into azurerm.
  • Is azapi supported by Microsoft? Yes, it is maintained by Microsoft alongside azurerm.
  • How do you read outputs? response_export_values and the output attribute.
