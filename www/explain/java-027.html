What are common pitfalls with @Transactional in Spring?

Spring Data & JPA · concept · levels mid, senior

In one line

The main @Transactional pitfalls are proxy-based behaviour (self-invocation, private methods, non-Spring objects), no rollback on checked exceptions, misunderstood propagation and rollback-only marking, long transactions around remote calls, and forgetting isolation/readOnly settings.

Detailed explanation

Proxy limits. @Transactional is implemented by an AOP proxy, so only calls that go through the proxy are transactional. Calling a transactional method from another method of the same class (self-invocation) bypasses it and no transaction starts. Objects created with new are not proxied. Historically only public methods were supported; since Spring 6.0, protected and package-private methods also work with class-based (CGLIB) proxies, but private methods never do, and final methods can't be intercepted by CGLIB.

Rollback rules. By default rollback happens on RuntimeException and Error only. A checked exception escaping the method commits. Use rollbackFor = Exception.class where needed. Swallowing exceptions inside the method also commits partial work.

Propagation surprises. REQUIRED joins the existing transaction, so an inner failure marks the shared transaction rollback-only; catching that exception in the outer method then leads to UnexpectedRollbackException at commit. REQUIRES_NEW suspends the outer transaction and runs separately, which is right for an audit log that must persist even if the main work fails, but it takes a second connection and can exhaust the pool.

Transaction scope. Long transactions that include HTTP calls, file processing or message publishing hold connections and row locks, hurting throughput and causing timeouts; external calls are not rolled back anyway. Keep transactions short and do remote work before or after, or use an outbox.

Settings and environment. Set readOnly = true for queries (Hibernate skips dirty checking) and choose isolation consciously. Transactions don't follow work onto other threads (@Async, parallel streams). Calling a transactional method from @PostConstruct runs before proxies exist. Using jakarta.transaction.Transactional vs Spring's annotation changes available attributes. With multiple data sources, the wrong transaction manager may be used.

How it works

  1. Check the call path: does it go through the proxy?
  2. Check visibility and finality of the method.
  3. Check which exceptions trigger rollback.
  4. Check propagation of nested calls.
  5. Check what the transaction encloses (remote calls, threads, duration).

Example

@Service
class OrderService {
    @Transactional
    public void placeOrder(Order o) {
        orderRepo.save(o);
        paymentClient.charge(o);          // remote call inside tx: holds connection, not rolled back
        notify(o);                        // self-invocation: its @Transactional is ignored
    }
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    void notify(Order o) { ... }
}

@Service
class AuditService {                      // separate bean: REQUIRES_NEW really applies
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void record(String event) { auditRepo.save(new AuditEntry(event)); }
}

Common mistakes

  • Self-invocation and private methods.
  • Relying on checked-exception rollback.
  • Swallowing exceptions or catching inner failures (UnexpectedRollbackException).
  • Remote calls and long processing inside transactions.
  • Overusing REQUIRES_NEW and exhausting the pool.

How to answer in the interview

"Transactional is proxy-based, so self-invocation bypasses it and private methods never work; since Spring 6, protected and package-private methods work with class-based proxies. By default it rolls back only on RuntimeException and Error, so checked exceptions commit unless I set rollbackFor. Propagation matters: REQUIRED joins the transaction, so catching an inner failure gives UnexpectedRollbackException, while REQUIRES_NEW runs independently, which I use for audit logs. I also avoid long transactions holding connections during remote calls, use readOnly for queries and choose isolation deliberately."

Likely follow-up questions

  • Audit entry that survives rollback? A separate bean method with REQUIRES_NEW.
  • Detect missing transactions? Log TransactionSynchronizationManager.isActualTransactionActive() or enable transaction debug logging.
  • Where to call remote services? Outside the transaction, or after commit via events or an outbox.
