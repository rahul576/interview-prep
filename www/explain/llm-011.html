What is prompt caching or prefix caching, and how do you design prompts to benefit from it?

LLMOps & RAG · concept · levels mid, senior

In one line

Prompt (prefix) caching reuses the computed KV cache for an identical prompt prefix, skipping that prefill work to cut latency and cost; design prompts with stable content first (system prompt, tools, documents) and variable content last, and keep traffic steady because caches expire after minutes.

Detailed explanation

Most production prompts repeat a large identical beginning: a long system prompt, tool definitions, few-shot examples, a policy document, or the earlier turns of a conversation. Recomputing that prefill for every call wastes GPU time and makes time to first token grow with prompt length.

With prefix caching, the server keeps the KV blocks for previously seen prefixes. When a new request starts with exactly the same tokens, the engine reuses those blocks and only prefills the new suffix. Self-hosted engines do this automatically: vLLM's automatic prefix caching hashes KV blocks, and SGLang's RadixAttention keeps a radix tree of prefixes. Hosted APIs offer it too, with pricing incentives: Anthropic uses explicit cache_control breakpoints, charges a premium on cache writes and a large discount (around 90 percent) on cache reads; OpenAI caches automatically for prompts above about 1,024 tokens with discounted cached input; Google Gemini offers implicit caching plus explicit context caches. Prices change; check current docs.

Matching is exact and prefix-based: a single changed token invalidates everything after it. Prompt design therefore matters:

  • Put stable content first, in a fixed order: instructions, tool schemas, reference documents, examples.
  • Then conversation history, which grows by appending, so each turn reuses the previous turn's prefix.
  • Put variable content last: the latest user question, retrieved chunks that differ per request, timestamps, user names.
  • Keep serialisation deterministic (stable JSON key order, same tool list order).

Caches are evicted after a period of inactivity (often about 5 minutes on APIs, with options for longer TTLs on some) or under memory pressure, so steady traffic benefits most. On self-hosted clusters, prefix-aware routing sends similar requests to the replica that holds the cache.

How it works

  1. Request arrives; engine hashes prompt blocks.
  2. Longest matching cached prefix is found.
  3. Cached KV blocks are reused; only the suffix is prefilled.
  4. New blocks are cached for future requests.
  5. Inactive entries expire or are evicted (LRU).

Example

resp = client.messages.create(
    model=MODEL,
    max_tokens=800,
    system=[{"type": "text", "text": LONG_POLICY_AND_INSTRUCTIONS,
             "cache_control": {"type": "ephemeral"}}],
    tools=TOOLS,                      # stable order
    messages=history + [{"role": "user", "content": question}],
)
print(resp.usage.cache_read_input_tokens, resp.usage.cache_creation_input_tokens)

Common mistakes

  • Putting the current date or request ID at the top of the system prompt.
  • Reordering tools or JSON keys between requests.
  • Inserting per-request retrieved context before the stable instructions.
  • Assuming caching works for prompts shorter than the provider's minimum.

How to answer in the interview

"Many requests share a long identical beginning, like the system prompt, tool definitions or a document. Prefix caching stores the KV cache for that prefix and reuses it, skipping that prefill, which cuts time to first token and cost; APIs from Anthropic, OpenAI and Google discount cached tokens heavily, and vLLM and SGLang do it automatically. To benefit, I put stable content first in a fixed order, then conversation history, and variable parts like the user's question or a timestamp at the end, because one changed token breaks the cache from that point. Caches expire after minutes, so steady traffic benefits most."

Likely follow-up questions

  • Verify cache hits in production? Log cached-token fields from API usage or engine prefix-hit metrics.
  • Does caching change output? No, the KV values are the same computation.
  • Multi-replica self-hosting? Use prefix-aware routing so requests reach the replica with the cache.
