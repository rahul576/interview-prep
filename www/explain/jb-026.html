What does the intern() method do?

Core Java & OOP · concept · levels mid, senior

In one line

intern() returns the canonical pooled instance of a string: if an equal string is already in the pool it returns that one, otherwise it adds this string and returns it, so equal interned strings are the same object.

Detailed explanation

The JVM keeps a global string table (the string pool). Literals go there automatically. intern() lets you put runtime-created strings there too. After String a = x.intern(); String b = y.intern();, if x.equals(y) then a == b.

Why you might use it:

  • Memory deduplication: if you parse millions of records with a small set of repeated values (country codes, currency codes, status values, XML tag names), each parsed value is a fresh String. Interning collapses them to one instance per distinct value, which can save significant heap.
  • Fast identity comparison: interned strings can be compared with ==, which some parsers and compilers use for symbol tables. In ordinary application code this is a micro-optimisation not worth the risk.

Costs and caveats:

  • The pool is a native hash table; each intern() call computes a hash and does a lookup, which is not free and was historically contended.
  • The table has a fixed number of buckets (-XX:StringTableSize, default 65536 in modern JDKs); with millions of entries, chains grow. -XX:+PrintStringTableStatistics shows its state.
  • Interning unbounded or high-cardinality values (user ids, request ids) bloats the table and costs more than it saves. Pooled strings can be GC'd since Java 7, but cleanup adds work.
  • Since Java 7 the pool is in the heap, not PermGen, so the old "PermGen OOM from intern" problem is gone.

Alternatives:

  • G1 string deduplication (-XX:+UseStringDeduplication, also supported by other collectors in recent JDKs) shares the backing byte arrays of equal long-lived strings automatically, with no code change; the String objects stay distinct.
  • A local canonicalising map (ConcurrentHashMap<String,String> with computeIfAbsent) or Guava's Interners, scoped and bounded to your use case.
  • Enums for truly fixed value sets.

How it works

  1. s.intern() computes the hash of s.
  2. Looks up the JVM string table.
  3. If an equal string exists, returns that reference.
  4. Otherwise inserts s (or a reference to it) and returns it.
  5. Unreferenced entries are removed during GC.

Example

String fromInput = new String("IN");          // e.g. parsed from CSV
String pooled = fromInput.intern();
System.out.println(pooled == "IN");           // true
System.out.println(fromInput == "IN");        // false

// Dedup low-cardinality field while parsing
record Row(String country, BigDecimal amount) {}
Row parse(String[] cols) {
    return new Row(cols[0].intern(), new BigDecimal(cols[1]));
}
java -XX:+UseG1GC -XX:+UseStringDeduplication -jar app.jar   # automatic alternative

Common mistakes

  • Interning every string, including unique ones.
  • Using == after interning in only some code paths.
  • Assuming interned strings are never collected.
  • Using intern as a lock object, which can be shared across unrelated code.

How to answer in the interview

"intern returns the canonical instance of a string from the string pool. If the pool already has an equal string, it returns that; otherwise it adds this one and returns it. After interning, equal strings share one object, so == works and memory is saved when the same values repeat a lot, like country codes parsed from a large file. But the pool is a hash table, so each call has a cost, and interning high-cardinality values just bloats it. For general duplicate strings I'd rather enable G1 string deduplication, which needs no code changes."

Likely follow-up questions

  • When could interning strings actually hurt performance? With many unique values: table growth, long chains, extra GC work and lookup overhead.
  • Where is the pool stored? In the heap since Java 7.
  • What's the difference from string deduplication? Dedup shares byte arrays; intern shares the String object.
