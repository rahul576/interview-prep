What is GitOps, and what are its principles?

GitOps & Helm · concept · levels entry

In one line

GitOps operates infrastructure and applications with Git as the single source of truth for declarative desired state; an agent in the cluster (Argo CD, Flux) pulls and continuously reconciles it, every change goes through a pull request (review, audit, git revert rollback), and drift is detected and self-healed.

Detailed explanation

The OpenGitOps project (CNCF) defines four principles:

  1. Declarative: the whole system's desired state is described declaratively, for example Kubernetes manifests, Helm values or Kustomize overlays, rather than scripts of steps.
  2. Versioned and immutable: that desired state is stored in a system like Git, which keeps complete history.
  3. Pulled automatically: software agents pull the desired state from the source, rather than a pipeline pushing into the cluster.
  4. Continuously reconciled: agents keep observing the actual state and correct any difference.

In practice, a team keeps a config repository (or a folder in the app repo). An agent like Argo CD or Flux runs inside the cluster, watches the repo and applies changes. A deployment is simply a commit: CI builds a new image and updates the image tag in Git, or opens a PR that someone approves.

The benefits follow from Git: review through pull requests, a complete audit trail (who changed what and when), and rollback with git revert. Because the agent reconciles continuously, if someone runs kubectl edit in production the application shows as OutOfSync (drift), and with self-heal the agent restores what Git says. Rebuilding a cluster after a disaster becomes "point a new cluster at the repo".

Security improves too: CI no longer needs admin credentials for the cluster; the agent pulls from inside. GitOps does need extra solutions for secrets (never plain in Git) and for imperative tasks like migrations.

How it works

  1. Desired state lives in Git as YAML/Helm/Kustomize.
  2. Change proposed as a PR; reviewed and merged.
  3. Agent detects the new commit (polling or webhook).
  4. Agent renders and applies the manifests, compares with live state.
  5. Agent keeps reconciling, reporting sync and health status.

Example

# Flux: watch a repo and apply a path every minute
apiVersion: source.toolkit.fluxcd.io/v1
kind: GitRepository
metadata: { name: platform, namespace: flux-system }
spec:
  url: https://github.com/acme/deploy-config
  ref: { branch: main }
  interval: 1m
---
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata: { name: shop-prod, namespace: flux-system }
spec:
  sourceRef: { kind: GitRepository, name: platform }
  path: ./clusters/prod/shop
  prune: true
  interval: 5m

Common mistakes

  • Calling any pipeline that uses Git "GitOps" while it still pushes with kubectl.
  • Committing plain Kubernetes Secrets.
  • Allowing manual changes in production, which self-heal then reverts confusingly.
  • One huge repo with no structure or ownership.

How to answer in the interview

"GitOps means Git is the single source of truth for the desired state of our infrastructure and applications. Everything is declarative, Kubernetes manifests, Helm values or Kustomize overlays, in a repository. An agent inside the cluster, such as Argo CD or Flux, continuously pulls that repo and reconciles the cluster to match it, instead of a pipeline pushing changes. Every change is a pull request, so it's reviewed and audited, and rollback is a git revert. The agent also detects drift when someone changes the cluster by hand and can self-heal back to what Git says. As a bonus, CI doesn't need admin access to the cluster."

Likely follow-up questions

  • Why is pull more secure? Cluster credentials stay inside; CI only writes to Git.
  • How do you handle secrets? External Secrets Operator, Sealed Secrets or SOPS.
  • Argo CD vs Flux? Argo CD has a rich UI and app-centric model; Flux is a set of composable controllers, CLI/CRD-driven.
