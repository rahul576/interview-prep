How does MCP support images, audio and embedded resources in tool results and prompts?

MCP Servers · concept · levels mid, senior

In one line

MCP content is a list of typed content blocks: besides text there are image and audio blocks with base64 data and a MIME type, embedded resources with inline contents, and resource links that reference content by URI; the host decides how to pass them to the model, so mind size and token cost.

Detailed explanation

Tool results and prompt messages in MCP are not just strings. They carry an array of content blocks, which lets a server return exactly what it produced. A browser automation server can return a screenshot as an image block, a charting tool can return a rendered PNG, and a speech tool can return an audio block. Each such block contains base64-encoded data and a mimeType, such as image/png or audio/wav.

Two block types deal with resources. An embedded resource (type: "resource") includes a resource object with its uri and its contents inline, either text or base64 blob, for example a generated report file. A resource link (type: "resource_link") only references a URI with a name and MIME type, so the client can read it later via resources/read if needed. Links are better for large files, because nothing is pushed into context unless it is required.

The host decides what the model actually sees. A multimodal model can receive the image directly; a text-only model may get a placeholder or description; some hosts show images to the user but do not forward them. Blocks can also carry annotations such as the intended audience (user or assistant) and priority.

Images and audio are expensive in tokens and payload size, so servers should resize, crop or compress, and return text when text is enough.

How it works

  1. The model calls a tool, for example take_screenshot.
  2. The server captures the image, downsizes it and base64-encodes it.
  3. It returns a result with an image block and perhaps a short text block describing the page.
  4. For large artefacts it returns a resource_link instead of inline bytes.
  5. The host converts blocks into the model API's format, or omits what the model cannot handle.

Example

{
  "content": [
    { "type": "text", "text": "Checkout page after clicking Pay: error banner visible." },
    { "type": "image", "mimeType": "image/png", "data": "iVBORw0KGgoAAAANS..." },
    {
      "type": "resource_link",
      "uri": "file:///reports/run-42/trace.zip",
      "name": "Playwright trace",
      "mimeType": "application/zip"
    }
  ],
  "isError": false
}

Common mistakes

  • Returning full-resolution screenshots on every step, blowing up context and cost.
  • Inlining multi-megabyte files instead of using resource links.
  • Assuming every host forwards images to the model.
  • Omitting or mislabelling the MIME type.

How to answer in the interview

"MCP results are lists of typed content blocks. Besides text, a tool result or prompt message can contain image and audio blocks, each with base64 data and a MIME type, for example a screenshot from a browser tool or a rendered chart. Embedded resource blocks include a resource with its URI and contents inline, and resource links just reference a URI so the client can fetch it if it needs it. The host decides how this reaches the model: a multimodal model sees the image, a text-only one might just get a description. Because images and audio are large and token-heavy, I resize and compress them and use resource links for big files."

Likely follow-up questions

  • When is a screenshot better than text? For layout, visual bugs, charts or canvas UIs where the DOM text misses the problem.
  • What are annotations for? Hints like audience and priority, telling the host who the content is for.
  • Can prompts contain images? Yes, prompt messages use the same content block types.
