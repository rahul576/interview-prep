An application in a container cannot reach the internet or another service. How do you troubleshoot?

Docker · scenario · levels mid

In one line

Test layer by layer from inside the container (or a netshoot debug container on the same network): which network it is on, DNS (/etc/resolv.conf, nslookup), TCP connectivity (curl, nc), whether the target listens on 0.0.0.0 and the container port, then host firewall, iptables and proxy settings.

Detailed explanation

Network problems are solved fastest by testing from the same network namespace as the failing application, because what works on the host proves little. If the app image has no tools, start a throwaway nicolaka/netshoot container with --network container:<app> (sharing the app's exact namespace) or on the same Docker network.

First, topology: docker inspect and docker network inspect show which networks each container is attached to. Containers on different user-defined networks cannot talk unless one is connected to both, and on the default bridge names do not resolve. Second, DNS: nslookup db or getent hosts db should return the peer's IP via Docker's embedded DNS at 127.0.0.11; for external names check /etc/resolv.conf and whether corporate DNS is reachable. Third, connectivity: nc -zv db 5432 or curl -v http://api:8080/health distinguishes "connection refused" (reachable, nothing listening) from "timeout" (filtered or wrong route).

The most common bug is a service that listens on 127.0.0.1 inside its own container, so it accepts only connections from itself; it must bind to 0.0.0.0. The second is using the published host port or localhost instead of the service name and container port. For internet access, check the host's IP forwarding, iptables/nftables rules and firewalls (ufw, firewalld), whether the network was created with --internal, MTU issues on VPNs or overlays, and corporate proxy variables (HTTP_PROXY, HTTPS_PROXY, NO_PROXY), which must also be set in the container or daemon.

How it works

  1. Identify networks of client and target containers.
  2. Resolve the target name from the client namespace.
  3. Test TCP to IP and port; note refused vs timeout.
  4. Verify the target's listen address and port (ss -lntp).
  5. For egress, check host forwarding, firewall, proxy, DNS and MTU.

Example

docker network inspect appnet -f '{{range .Containers}}{{.Name}} {{.IPv4Address}}{{"\n"}}{{end}}'
docker run --rm -it --network container:api nicolaka/netshoot
# inside netshoot:
cat /etc/resolv.conf
nslookup db
nc -zv db 5432
curl -sv https://api.github.com -o /dev/null
docker exec db ss -lntp          # is it on 0.0.0.0:5432 or 127.0.0.1:5432?
sysctl net.ipv4.ip_forward       # on the host

Common mistakes

  • Testing from the host and concluding the network is fine.
  • Using localhost to reach another container.
  • Apps bound to 127.0.0.1 inside the container.
  • Forgetting NO_PROXY for internal names when a proxy is configured.

How to answer in the interview

"I test step by step from inside the container, or from a netshoot debug container on the same network. docker network inspect shows whether both are on the same network, because containers on different user-defined networks can't talk. Then DNS: does nslookup of the service name or external host work, and what's in resolv.conf. Then connectivity with nc or curl to the IP and port, where refused versus timeout tells me a lot. A classic bug is a service listening on localhost inside its container, so it must bind to 0.0.0.0. For internet access I check host firewall and iptables, proxy variables, and that clients use the container port, not the published one."

Likely follow-up questions

  • Why doesn't localhost in a container reach the host? The container has its own network namespace; use host.docker.internal or the bridge gateway.
  • Refused vs timeout? Refused means reachable but nothing listening; timeout suggests firewall or routing.
  • What is an internal network? A Docker network created with --internal that has no external connectivity.
