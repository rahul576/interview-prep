How do optional object attributes with defaults improve module interfaces?

Terraform · concept · levels mid, senior

In one line

Declaring a variable as an object({...}) with optional(type, default) attributes lets callers pass only what they need, fills in defaults inside the type, and gives type validation that catches typos, producing a cleaner module interface than many variables or type = any.

Detailed explanation

Modules often need rich settings: a database with size, backups, retention and maintenance window; a map of node pools each with VM size, min and max count and labels. Before optional attributes became stable in Terraform 1.3, module authors had two poor choices. Either dozens of separate variables (db_size, db_backup_enabled, db_retention_days...), which cannot be grouped per item in a map, or type = any plus lookup(var.settings, "retention_days", 7) calls everywhere, which accepts anything, including typos, without errors.

With optional object attributes, the type itself documents the interface. optional(bool, true) means the attribute may be omitted, and if it is, Terraform inserts true before the module sees the value. Without a default, an omitted optional attribute becomes null. Defaults apply at every nesting level, including inside map(object(...)) and list(object(...)), which is perfect for collections like node pools, subnets or per-environment settings where each item only overrides what differs.

Because the type is declared, Terraform performs type conversion and validation at plan time: an unknown attribute such as retension_days is rejected with a clear error instead of being silently ignored, and a string where a number is expected fails early. Combined with validation blocks, you can add business rules such as "retention must be between 1 and 35 days". Documentation generators like terraform-docs render the full structure, so consumers see the interface at a glance.

How it works

  1. Define a variable with type = object({...}) or map(object({...})).
  2. Wrap non-mandatory attributes in optional(type, default).
  3. Caller passes a partial object.
  4. Terraform converts it to the full type, inserting defaults.
  5. Validation blocks check business rules.
  6. Module code uses attributes directly without lookup.

Example

variable "node_pools" {
  type = map(object({
    vm_size   = string
    min_count = optional(number, 1)
    max_count = optional(number, 3)
    labels    = optional(map(string), {})
    spot      = optional(bool, false)
  }))
  validation {
    condition     = alltrue([for p in var.node_pools : p.min_count <= p.max_count])
    error_message = "min_count must not exceed max_count."
  }
}

# Caller
node_pools = {
  system = { vm_size = "Standard_D4s_v5" }
  batch  = { vm_size = "Standard_D8s_v5", max_count = 10, spot = true }
}

Common mistakes

  • Using type = any for structured settings.
  • Giving defaults outside the type with merge, duplicating logic.
  • Making huge single objects that are hard to read and document.
  • Forgetting that an optional attribute without a default is null in module code.

How to answer in the interview

"I declare the variable as an object type and wrap optional attributes in optional(), where the second argument is the default, for example backups = optional(bool, true). Terraform fills in the defaults when the caller leaves attributes out, so callers pass only what they want to change. It works nested too, so a map of node pools can have per-pool defaults. Because the type is declared, Terraform rejects unknown attribute names and wrong types at plan time, catching typos that type = any would silently accept. It replaces dozens of separate variables or lookup calls with a clean, documented interface, and I add validation blocks for business rules."

Likely follow-up questions

  • Downsides of very large object variables? Hard to read, long error messages, and every change touches one big interface; split by concern.
  • What is the default for an optional attribute without a default? null.
  • Since which version? Optional attributes with defaults are stable since Terraform 1.3.
