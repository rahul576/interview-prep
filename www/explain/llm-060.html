How do you build a fine-tuning pipeline for an LLM in production?

LLMOps & RAG · concept · levels mid, senior

In one line

A production fine-tuning pipeline collects and curates high-quality examples (deduplicated, PII removed), formats them with the model's chat template, trains as tracked experiments with versioned data and hyperparameters, evaluates against the base model and production on held-out and general sets, registers and rolls out models or adapters, and retrains when data accumulates or the base model changes.

Detailed explanation

Data is the product. Sources: production logs where users accepted outputs, expert-written answers, and corrected model outputs (human edits are gold). Curate for correctness, consistency of style and format, and coverage of real input variety, including edge cases and examples of correct refusals. Deduplicate, balance categories, and remove personal data and secrets, since fine-tuned models can memorise and regurgitate training data. A few hundred to a few thousand clean examples often beat tens of thousands of noisy ones.

Formatting. Use exactly the target model's chat template (roles, special tokens) and the same system prompt you will use at inference. Split into training, validation and a held-out test set that never influences tuning.

Training. Managed fine-tuning APIs (OpenAI, Azure AI Foundry, Vertex AI, Bedrock) or frameworks such as Hugging Face TRL, Axolotl or Unsloth, usually with LoRA. Every run is an experiment tracked in MLflow or W&B: data version (DVC, dataset hashes), base model version, hyperparameters, metrics and artefacts.

Evaluation. Compare the candidate with the base model (with a good prompt) and the current production setup on the held-out set, plus general capability and safety checks to catch forgetting or weakened refusals. Fine-tuning must beat good prompting to be worth maintaining.

Release. Register the model or adapter with lineage, deploy through the normal path (canary, monitoring, rollback). Schedule retraining when enough new data accumulates, drift appears, or the base model is upgraded or retired.

How it works

  1. Collect -> curate -> redact -> dedupe -> version dataset.
  2. Format with chat template; split train/val/test.
  3. Train (LoRA) with tracked config.
  4. Evaluate: task metrics, base comparison, general and safety sets.
  5. Register; canary deploy; monitor.
  6. Trigger retraining on data growth, drift or base model change.

Example

# axolotl-style config (simplified)
base_model: Qwen/Qwen2.5-7B-Instruct
adapter: lora
lora_r: 16
lora_alpha: 32
datasets:
  - path: s3://ml-data/ticket-summaries/v2026-11-01.jsonl
    type: chat_template
val_set_size: 0.05
num_epochs: 3
learning_rate: 0.0002
output_dir: ./out/ticket-summary-lora-v7

Common mistakes

  • Training on unreviewed logs, including bad outputs.
  • PII in training data.
  • Comparing only against the base model without a good prompt.
  • No lineage: unknown which data produced which model.

How to answer in the interview

"The pipeline starts with data: examples from production logs, expert answers and corrected outputs, curated for quality and coverage, deduplicated and stripped of personal data and secrets. They're formatted with the target model's chat template and split into train and held-out sets. Training runs as tracked experiments with data version, base model and hyperparameters recorded, using managed APIs or TRL, Axolotl or Unsloth. I evaluate against the base model with a good prompt and the current production setup, plus general and safety checks. Approved adapters are registered and deployed through a canary, and the pipeline reruns when data grows or the base model changes."

Likely follow-up questions

  • No production logs yet? Expert-written examples, synthetic data from a strong model reviewed by experts.
  • How many examples? Often hundreds to low thousands for narrow tasks; measure learning curves.
  • When stop fine-tuning? When prompting or RAG achieves similar quality at lower maintenance.
