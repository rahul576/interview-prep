Can you give real-world examples of association, aggregation, and composition?

Core Java & OOP · concept · levels entry

In one line

Association: doctor-patient, teacher-student, customer-bank; aggregation: team-players, department-employees, playlist-songs; composition: house-rooms, order-order lines, invoice-line items, human-heart.

Detailed explanation

Good examples make the lifecycle difference obvious, so pick ones where the answer to "does the part survive without the whole?" is clear.

Association (independent objects that interact)

  • Doctor and patient: a doctor treats many patients, a patient sees many doctors; neither owns the other.
  • Customer and bank: a customer can have accounts at several banks; the bank exists without any particular customer.
  • Driver and car (in a ride-hailing app): a driver uses a car for a trip; both exist independently.

Aggregation (whole groups independent parts)

  • Playlist and songs: deleting a playlist leaves the songs in the library; one song is in many playlists.
  • Team and players: players transfer; disbanding the team doesn't delete the people.
  • Department and employees: reorganising a department reassigns employees.
  • Shopping cart and products: removing the cart doesn't remove products from the catalogue.

Composition (whole owns parts exclusively)

  • House and rooms: rooms don't exist apart from a house.
  • Order and order lines: a line belongs to one order and is deleted with it.
  • Invoice and line items: same, and legally the invoice should be immutable once issued.
  • Human and heart (biological model): the heart is part of exactly one body.
  • Document and paragraphs in an editor.

In software, the question is about the domain model, so the same pair can change category. A cart line (sku and quantity inside a cart) is composition, while the product it refers to is an association or aggregation. A car and its engine is composition for a car buyer but aggregation for a workshop that swaps engines.

Practical impact: compositions get cascade persist and delete (or embeddables), aggregations and associations get no cascade delete, and only composition parts are created inside the owner.

How it works

  1. For each pair, ask whether one merely uses the other (association).
  2. If it is whole-part, ask whether parts can exist alone or be shared (aggregation).
  3. If parts are exclusively owned and die with the whole, it is composition.
  4. Map the decision to code construction and persistence cascades.

Example

class Doctor    { List<Appointment> appointments; }            // association via appointments
class Playlist  { List<Song> songs; void add(Song s) { songs.add(s); } }   // aggregation
class Invoice   {                                               // composition
    private final List<LineItem> items = new ArrayList<>();
    void addItem(String desc, BigDecimal amount) { items.add(new LineItem(desc, amount)); }
}
@OneToMany(mappedBy = "invoice", cascade = CascadeType.ALL, orphanRemoval = true)
private List<LineItem> items;          // cascade: composition

@ManyToMany
private Set<Song> songs;               // no cascade: aggregation

Common mistakes

  • Picking ambiguous examples and being unable to defend them.
  • Claiming "car-engine is always composition" without context.
  • Cascading removal on playlist-songs.
  • Forgetting association examples carry many-to-many multiplicity.

How to answer in the interview

"Association: a doctor and a patient, or a customer and a bank: they interact, but each exists on its own. Aggregation: a playlist and its songs: deleting the playlist doesn't delete the songs and one song can be in many playlists; or a team and its players. Composition: a house and its rooms, which don't exist without the house; in software, an Order and its OrderLines or an Invoice and its line items, which are deleted with it and never belong to another. I'd cascade only the composition ones in JPA."

Likely follow-up questions

  • Which of these would you cascade in JPA? Only compositions like order lines and invoice items.
  • Is a cart and its items composition? The cart lines are; the products they reference are not.
  • Can the classification change? Yes, depending on the domain's lifecycle rules.
