Design an MCP server that lets an IT helpdesk assistant work with ServiceNow incidents.

MCP Servers · design · levels senior, lead

In one line

Model the tools on helpdesk tasks (search, get, comment, work note, create, assign, resolve, KB search), call ServiceNow on behalf of the signed-in agent so roles and ACLs apply, auto-approve reads and confirm writes, make create_incident idempotent, treat ticket text as untrusted, and return compact results.

Detailed explanation

Tool design. Tools follow what helpdesk staff actually do, not the ServiceNow Table API:

  • search_incidents(caller, status, assignment_group, priority, opened_after) returning number, short description, state, priority and age.
  • get_incident(number) returning a compact summary with the last few work notes and comments, not the full record with dozens of fields.
  • add_comment (customer-visible) and add_work_note (internal), kept separate so the model cannot confuse audiences.
  • create_incident(caller, category, short_description, description, impact, urgency, idempotency_key).
  • assign_incident and resolve_incident(number, resolution_code, resolution_notes).
  • search_knowledge(query), with articles also exposed as resources.

Identity. Staff authenticate with OAuth via the corporate IdP; the server calls ServiceNow on their behalf with a delegated token, so ServiceNow roles and ACLs decide what each person can see and change. No shared admin integration user.

Approvals. Reads are auto-approved. Writes require confirmation showing the exact change: the comment text, the new priority, the resolution code. Resolving or lowering priority deserves particular care.

Reliability. create_incident uses an idempotency key (stored with a correlation field) so retries on flaky networks do not create duplicates.

Untrusted content. Ticket descriptions and comments are written by end users, and anyone can email the service desk, so they may contain prompt injection. The server returns them clearly delimited as user-supplied text, and the assistant has no external communication tools without approval. Comments to customers go through confirmation.

Personal data. Tickets often include names, phone numbers or screenshots; return only needed fields and redact in logs.

How it works

  1. Agent asks: "What's open for the Pune office VPN issue?"
  2. search_incidents runs as that agent; ServiceNow ACLs filter results.
  3. Model summarises; suggests a KB article via search_knowledge.
  4. Agent asks to add a work note and resolve; host shows both changes for confirmation.
  5. Server executes, logs the action with user and incident number.

Common mistakes

  • A single generic run_query tool against the Table API.
  • One integration user with admin rights for everyone.
  • Returning every field of the incident record.
  • Letting the assistant post customer-visible comments without confirmation.

How to answer in the interview

"The tools follow helpdesk tasks: search_incidents with filters like caller, status, assignment group and time range; get_incident returning a compact summary with recent work notes; separate add_comment and add_work_note; create_incident; and assign or resolve with a resolution code, plus a knowledge base search tool and resources. Staff authenticate with OAuth and the server calls ServiceNow on their behalf, so roles and ACLs apply. Reads are auto-approved; writes, especially resolving or changing priority, need confirmation showing the exact change. create_incident takes an idempotency key. Ticket text is written by end users, so it's untrusted and may contain injection; it's clearly marked, and the assistant can't communicate externally without approval."

Likely follow-up questions

  • Incidents with personal data? Minimal fields, redaction in logs, respect ServiceNow data policies.
  • Why separate comment and work note? Different audiences; mixing them can leak internal notes to customers.
  • Bulk operations? Avoid or require explicit approval with a preview list.
