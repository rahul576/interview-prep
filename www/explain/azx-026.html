What is Azure Container Apps, and when would you choose it over AKS?

Azure · concept · levels mid, senior

In one line

Azure Container Apps is a serverless container platform built on Kubernetes, KEDA, Dapr and Envoy with the cluster hidden: you get event-driven scaling including scale to zero, revisions with traffic splitting, built-in ingress, Dapr, jobs and serverless GPUs; choose AKS when you need the full Kubernetes API, CRDs/operators or deep platform control.

Detailed explanation

Container Apps run inside an environment, a secure boundary with its own VNet (optionally your own) and Log Analytics, where apps can talk to each other. Environments offer a Consumption profile (pay per vCPU-second and GiB-second, scale to zero) and dedicated workload profiles for specific VM sizes, more memory or GPUs.

Scaling uses KEDA under the hood: HTTP concurrency, TCP, CPU/memory, or any KEDA scaler such as Service Bus queue length, Event Hubs, Kafka or a cron schedule, with min and max replicas. Idle apps can scale to zero, which keeps costs low for spiky or internal workloads.

Every change to the template creates a revision. In multiple revision mode, you split traffic by weight between revisions or use labels, enabling blue-green and canary releases. Ingress (Envoy-based) gives HTTPS with managed certificates, custom domains, internal-only or external exposure, and session affinity.

Extras: Dapr sidecars for service invocation, pub/sub and state; managed identities and Key Vault references; jobs for manual, scheduled or event-driven batch tasks; serverless GPUs for AI inference; and dynamic sessions for sandboxed code execution.

AKS gives you the whole Kubernetes API: custom operators and CRDs, Helm charts relying on cluster resources, DaemonSets, a service mesh of your choice, node-level customisation, Windows nodes, strict multi-tenancy designs or a platform for many teams. The cost is operating the cluster: upgrades, node pools, networking and add-ons. Many teams start on Container Apps and move to AKS only when they hit these needs.

How it works

  1. Create an environment (Consumption or workload profiles, VNet, logs).
  2. Deploy a container app with image, CPU/memory, secrets and identity.
  3. Define scale rules (HTTP or KEDA scaler) with min/max replicas.
  4. Configure ingress (external or internal).
  5. Deploy new revisions; shift traffic gradually.
  6. Use jobs for batch and scheduled work.

Example

az containerapp create -n orders-worker -g rg-orders --environment cae-prod \
  --image acrprod.azurecr.io/orders-worker:1.4.2 --registry-identity system \
  --min-replicas 0 --max-replicas 30 \
  --scale-rule-name sb-queue --scale-rule-type azure-servicebus \
  --scale-rule-metadata queueName=orders namespace=sb-prod messageCount=20 \
  --scale-rule-identity system

Common mistakes

  • Choosing AKS for a few simple APIs and drowning in cluster operations.
  • Assuming you can kubectl into Container Apps.
  • Scale to zero on latency-sensitive endpoints without min replicas.
  • Single revision mode when you need canary releases.

How to answer in the interview

"Container Apps is serverless containers on top of Kubernetes, KEDA, Dapr and Envoy, but Azure runs the cluster. I deploy images with scaling rules on HTTP, CPU or KEDA scalers like Service Bus queue length, including scale to zero. Revisions let me split traffic for canary or blue-green, and it has built-in ingress, Dapr, managed identity, VNet integration, jobs and even serverless GPUs. I'd pick it for microservices and APIs when the team doesn't need the Kubernetes API. If we need operators, CRDs, a specific service mesh or a shared multi-team platform, I'd choose AKS."

Likely follow-up questions

  • What would push a team to AKS later? Need for CRDs/operators, DaemonSets, custom networking or node control.
  • Cold start when scaled to zero? Set min replicas to 1 for latency-sensitive apps.
  • How do you deploy from CI? az containerapp update or the Container Apps GitHub/Azure DevOps tasks with OIDC.
