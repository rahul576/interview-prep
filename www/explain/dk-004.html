How do you pass configuration to a container with environment variables?

Docker · concept · levels entry

In one line

Pass configuration with -e KEY=value, --env-file for many variables, ENV in the Dockerfile for defaults, and the Compose environment/env_file keys, so one image runs in every environment (twelve-factor); keep secrets out of env vars where possible, because they show up in docker inspect.

Detailed explanation

Building a separate image per environment is fragile: you want build once, deploy many, with the differences injected at run time. Environment variables are the simplest mechanism and the twelve-factor app recommendation for config.

Ways to set them:

  • docker run -e SPRING_PROFILES_ACTIVE=prod -e DB_HOST=db myapp sets values directly. -e DB_HOST without a value copies it from your shell.
  • --env-file app.env reads KEY=value lines from a file, handy for dozens of variables; keep that file out of git if it contains anything sensitive.
  • ENV in the Dockerfile sets defaults baked into the image (for example ENV PORT=8080 TZ=UTC).
  • In Compose, the environment: map or env_file:; Compose also reads a .env file for variable substitution inside the YAML itself, which is a different feature.
  • In Kubernetes: env, envFrom with ConfigMaps and Secrets.

Precedence: run-time values win. -e overrides --env-file entries and ENV defaults from the image.

Secrets: environment variables are convenient but leaky. They appear in docker inspect, in /proc/<pid>/environ, are inherited by child processes and can end up in crash dumps, debug pages or logs. For passwords and keys prefer secrets mounted as files (Docker/Swarm secrets, Compose secrets:, Kubernetes Secrets as volumes, or Vault/CSI), and support the *_FILE convention, for example POSTGRES_PASSWORD_FILE=/run/secrets/db_password, which official images like Postgres and MySQL already do.

How it works

  1. Image defines defaults with ENV.
  2. Runtime adds or overrides via --env-file then -e.
  3. The process reads variables at startup (System.getenv, process.env, os.environ).
  4. Changes require restarting the container; env vars are not reloaded live.

Example

cat > staging.env <<'EOF'
SPRING_PROFILES_ACTIVE=staging
DB_HOST=db.staging.internal
LOG_LEVEL=info
EOF
docker run -d --env-file staging.env -e LOG_LEVEL=debug myapp:2.1   # -e wins
docker exec <id> printenv LOG_LEVEL                                 # debug
services:
  db:
    image: postgres:17
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets: [db_password]
secrets:
  db_password:
    file: ./secrets/db_password.txt

Common mistakes

  • Baking environment-specific values or secrets into the image with ENV.
  • Committing .env files with real credentials.
  • Expecting a changed variable to apply without recreating the container.
  • Logging the full environment at startup.

How to answer in the interview

"The simplest way is -e on docker run, like -e SPRING_PROFILES_ACTIVE=prod. With many variables I use --env-file. The Dockerfile's ENV sets defaults that run-time values override, and in Compose I use the environment or env_file keys. That keeps one image deployable to every environment, following twelve-factor. For secrets I'm careful: environment variables are visible through docker inspect and to child processes, so for passwords I prefer Docker or Kubernetes secrets mounted as files, using the _FILE convention that many images support."

Likely follow-up questions

  • Precedence between ENV and -e? -e at run time overrides the image's ENV.
  • Compose .env vs env_file? .env substitutes values in the YAML; env_file passes variables into the container.
  • Why files for secrets? Not visible in inspect output or process environment, and can be rotated.
