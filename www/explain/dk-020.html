Explain the Docker client-server architecture.

Docker · concept · levels entry

In one line

Docker uses a client-server model: the docker CLI sends REST API calls to the daemon dockerd over a Unix socket or TCP, and dockerd manages images, containers, networks and volumes, delegating execution to containerd and runc.

Detailed explanation

When you type docker run nginx, the CLI does almost nothing itself. It is a client that converts the command into HTTP requests to the Docker Engine API. By default it connects to the Unix socket /var/run/docker.sock; with DOCKER_HOST, -H or Docker contexts it can talk to a remote daemon over SSH or TCP protected with mutual TLS.

The daemon, dockerd, does the real work. It builds images (through BuildKit), stores image layers, pulls and pushes them from registries such as Docker Hub, ECR or GHCR, creates networks and volumes, and manages container configuration. For running containers it delegates to containerd, a separate daemon that manages container lifecycle and image content. containerd starts a shim per container and calls runc, the low-level OCI runtime that creates the process with namespaces and cgroups. The shim keeps the container alive even if dockerd or containerd restarts (with live-restore enabled).

This split explains several practical facts. Because the daemon runs as root and does whatever the API asks, anyone who can reach the socket can start a privileged container and control the host, so socket access equals root. Docker Desktop on macOS and Windows runs dockerd inside a small Linux VM, while the CLI runs natively and forwards to it. And because images follow OCI standards, other runtimes can run them.

How it works

  1. CLI parses docker run and calls the API (POST /containers/create, then /start).
  2. dockerd pulls the image from a registry if it is missing.
  3. dockerd prepares networking, volumes and the container config.
  4. containerd creates the container and starts a shim.
  5. runc sets up namespaces and cgroups and executes the process, then exits.
  6. The CLI attaches to logs or returns the container ID.

Example

# Talk to the API directly over the socket
curl --unix-socket /var/run/docker.sock http://localhost/v1.45/containers/json

# Manage a remote host over SSH with a context
docker context create prod --docker "host=ssh://deploy@prod-01"
docker --context prod ps

Common mistakes

  • Exposing the daemon on TCP port 2375 without TLS.
  • Thinking the CLI runs containers itself, or that containers die when the CLI exits.
  • Mounting docker.sock into containers without understanding it grants root.
  • Confusing Docker Desktop's VM with the host on Linux.

How to answer in the interview

"Docker is client-server. The docker CLI is just a client that sends REST API requests to the daemon, dockerd, usually through the Unix socket /var/run/docker.sock, or over SSH or TLS-protected TCP for remote hosts. The daemon builds and stores images, pulls and pushes from registries, and manages networks, volumes and containers. For execution it delegates to containerd, which uses a shim and runc to create the process with namespaces and cgroups. On Mac and Windows, Docker Desktop runs the daemon inside a small Linux VM. Since the daemon is root, access to its socket is effectively root on the host."

Likely follow-up questions

  • Why is access to docker.sock equivalent to root? You can start a privileged container that mounts the host's root filesystem.
  • What are Docker contexts? Named endpoints to switch the CLI between local and remote daemons.
  • What is live-restore? A daemon option that keeps containers running while dockerd restarts.
