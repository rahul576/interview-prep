How do you set the timezone, locale and CA certificates correctly in a container image?

Docker · concept · levels mid

In one line

Containers usually default to UTC, which is right for servers; when needed set TZ and install tzdata, install ca-certificates (adding any corporate root CA to the OS store and the JVM truststore), and set LANG/LC_ALL to a UTF-8 locale such as C.UTF-8.

Detailed explanation

Minimal images remove a lot of "system" data that full operating systems include, and three gaps cause classic production bugs.

Timezone: most images have no /etc/localtime configured and run in UTC. For servers that is the best practice: store timestamps in UTC, log in UTC (ideally ISO 8601 with offset), and convert to the user's timezone in the application or UI. If a process really needs a local zone, such as a legacy batch job scheduled at local midnight, set TZ=Asia/Kolkata (or similar) and make sure the tzdata package exists, because slim and Alpine images often lack it and silently fall back to UTC. Java and Go can carry their own tz data, but keeping tzdata in the image is safest. Do not bind-mount the host's /etc/localtime as a habit; it couples the container to the host.

CA certificates: any outgoing HTTPS connection needs trusted root certificates. Slim images may lack ca-certificates, giving errors like "unable to get local issuer certificate". In companies with a TLS-inspecting proxy, the proxy re-signs traffic with a corporate root CA, so calls work on laptops (where IT installed the CA) but fail inside containers. Add the CA with update-ca-certificates (Debian/Alpine) or update-ca-trust (RHEL), and for Java import it into the JVM truststore with keytool, since Java may use its own cacerts. Python's requests uses certifi unless pointed to the system store via REQUESTS_CA_BUNDLE.

Locale: without a locale, tools may default to POSIX/ASCII, breaking non-ASCII filenames and text processing. Set LANG=C.UTF-8 and LC_ALL=C.UTF-8, available in most Debian-based images without extra packages.

How it works

  1. Base image provides minimal or no tz, CA and locale data.
  2. Dockerfile installs tzdata and ca-certificates as needed.
  3. Corporate CA is copied in and the trust store regenerated.
  4. Environment sets TZ and LANG/LC_ALL.
  5. Runtimes read these at start-up.

Example

FROM eclipse-temurin:21-jre-jammy
ENV TZ=UTC LANG=C.UTF-8 LC_ALL=C.UTF-8
RUN apt-get update && apt-get install -y --no-install-recommends tzdata ca-certificates \
 && rm -rf /var/lib/apt/lists/*
COPY corp-root-ca.crt /usr/local/share/ca-certificates/corp-root-ca.crt
RUN update-ca-certificates && \
    keytool -importcert -noprompt -cacerts -storepass changeit \
            -alias corp-root -file /usr/local/share/ca-certificates/corp-root-ca.crt

Common mistakes

  • Running servers in local time and getting DST bugs.
  • Setting TZ without tzdata installed.
  • Disabling TLS verification instead of adding the corporate CA.
  • Adding the CA to the OS store but not to the JVM truststore.

How to answer in the interview

"Most images default to UTC, and for servers that's what I want: store and log times in UTC and convert in the application or UI. If a timezone is really needed I set TZ, for example Asia/Kolkata, and make sure tzdata is installed, because slim images often lack it. For HTTPS the image needs ca-certificates; behind a TLS-inspecting corporate proxy I add the corporate root CA to the system store and, for Java, to the JVM truststore. For text handling I set LANG and LC_ALL to a UTF-8 locale like C.UTF-8 to avoid encoding bugs."

Likely follow-up questions

  • Why might HTTPS fail only in the container? Missing CA bundle or the corporate proxy CA is not trusted inside the image.
  • Why prefer UTC? No DST jumps, consistent logs and easy correlation across regions.
  • How do you verify the timezone? docker exec app date and check the app's reported zone.
