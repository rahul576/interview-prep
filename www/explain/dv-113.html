What are namespaces in Kubernetes, and how do you use them?

Kubernetes · concept · levels entry

In one line

A namespace is a virtual partition of one cluster that groups resources per team, app or environment; names must be unique within a namespace, and it is the boundary for RBAC, ResourceQuotas, LimitRanges and NetworkPolicies, but it gives no node or kernel isolation.

Detailed explanation

Without namespaces, every team's Deployments, Services and Secrets would share one flat list, with name clashes and no clean way to grant access. Namespaces scope most objects: two teams can each have a Service called api in payments-prod and search-prod. DNS also follows namespaces: a Service is reachable as api.payments-prod.svc.cluster.local.

They are mainly a policy boundary:

  • RBAC: a RoleBinding grants a team edit only in its namespaces.
  • ResourceQuota: caps total CPU, memory, storage and object counts.
  • LimitRange: sets default and maximum requests and limits per container.
  • NetworkPolicy: default deny inside a namespace, explicit allows between namespaces.
  • Pod Security Admission: labels set baseline or restricted per namespace.

Every cluster starts with default (where things land if you forget -n), kube-system (control plane add-ons such as CoreDNS and CNI agents), kube-public and kube-node-lease (node heartbeats). Some objects are cluster-scoped and not in any namespace: Nodes, PersistentVolumes, StorageClasses, ClusterRoles, CRDs and Namespaces themselves.

Namespaces are soft isolation: pods from all namespaces share nodes and the kernel, and cluster-scoped resources are shared. Untrusted tenants need separate node pools, sandboxed runtimes, virtual clusters or separate clusters.

How it works

  1. Create the namespace with labels (team, environment, pod-security level).
  2. Bind team groups to roles in that namespace.
  3. Add ResourceQuota and LimitRange.
  4. Add default-deny NetworkPolicies and needed allows.
  5. Deploy workloads with -n or metadata.namespace.

Example

apiVersion: v1
kind: Namespace
metadata:
  name: payments-prod
  labels:
    team: payments
    pod-security.kubernetes.io/enforce: restricted
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { name: payments-edit, namespace: payments-prod }
roleRef: { apiGroup: rbac.authorization.k8s.io, kind: ClusterRole, name: edit }
subjects:
- { kind: Group, name: payments-devs, apiGroup: rbac.authorization.k8s.io }

Common mistakes

  • Deploying everything into default.
  • Treating namespaces as a security boundary against hostile tenants.
  • Deleting a namespace without realising it deletes everything in it.
  • Expecting kubectl get pods to show all namespaces (use -A).

How to answer in the interview

"A namespace is a virtual partition of a cluster. We use them to group resources by team or environment, like payments-dev and payments-prod, and names only need to be unique inside a namespace. More importantly they're the boundary for policy: RBAC bindings give a team rights in its namespaces, ResourceQuotas and LimitRanges cap resource use, and NetworkPolicies and Pod Security labels apply per namespace. System components run in kube-system. Namespaces don't isolate nodes or the kernel, so for untrusted tenants I'd use separate node pools or clusters."

Likely follow-up questions

  • Which resources aren't namespaced? Nodes, PVs, StorageClasses, ClusterRoles, CRDs, Namespaces; check with kubectl api-resources --namespaced=false.
  • Why can a namespace be stuck Terminating? Finalizers on remaining objects or an unavailable API service.
  • Can a pod use a Secret from another namespace? No, Secrets are referenced within the pod's namespace.
