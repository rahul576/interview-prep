How do you structure Ansible for many environments and keep it safe?

Configuration Management · concept · levels mid, senior

In one line

Use a separate inventory per environment with group_vars/host_vars, put logic in roles and shared versioned collections, encrypt secrets with Ansible Vault (or look them up from HashiCorp Vault), always run --check --diff before production, roll out in serial batches with failure thresholds, and test roles with Molecule and ansible-lint in CI.

Detailed explanation

Layout: the same playbooks run everywhere; only data differs. Keep inventories/dev, inventories/staging and inventories/prod, each with its own hosts.yml (or a dynamic inventory plugin filtered by tags such as env=prod) plus group_vars and host_vars. Roles hold tasks, templates and defaults that environments override. Shared roles live in collections with version pins in requirements.yml, so updating a role is a reviewed change.

Secrets: encrypt sensitive vars with Ansible Vault (ansible-vault encrypt_string), using a different vault ID/password per environment, so dev users can't decrypt prod. Even better, fetch at runtime from HashiCorp Vault or a cloud secret manager via lookup plugins, and use no_log: true on tasks handling secrets.

Safety for production:

  • Dry runs: --check --diff shows exactly which files and packages would change.
  • Rolling updates: serial: "20%" and max_fail_percentage stop the play before every host is broken; combine with taking hosts out of the load balancer in pre_tasks and back in post_tasks.
  • Limit scope: --limit and tags for targeted runs.
  • Guardrails against running on prod by accident: separate credentials and SSH keys for prod, a confirmation assertion, or only allowing prod runs from CI or AWX/Ansible Automation Platform with RBAC and audit logs.

Quality: ansible-lint catches bad practices (raw shell, missing names, deprecated syntax). Molecule spins up containers or VMs, applies the role, checks idempotence (a second run must report no changes) and runs verification tests.

How it works

  1. Developer changes a role or vars in a PR.
  2. CI runs ansible-lint and Molecule (converge, idempotence, verify).
  3. Merge → run against dev, then staging.
  4. Prod run from CI/AWX: --check --diff reviewed, then real run with serial.
  5. Logs and recap stored for audit.

Example

inventories/
  prod/hosts.yml
  prod/group_vars/web.yml
  prod/group_vars/vault.yml      # encrypted
roles/nginx/  roles/app/
site.yml
- hosts: web
  serial: "20%"
  max_fail_percentage: 10
  pre_tasks:
    - name: Refuse prod runs outside CI
      ansible.builtin.assert:
        that: lookup('env', 'CI') == 'true' or env != 'prod'
  roles: [ nginx, app ]
ansible-playbook -i inventories/prod site.yml --vault-id prod@prompt --check --diff

Common mistakes

  • One inventory with all environments mixed together.
  • The same Vault password for every environment.
  • Running against all hosts at once with no serial.
  • Roles that are never tested for idempotence.

How to answer in the interview

"I keep a separate inventory per environment, with variables in group_vars and host_vars, so the same playbooks run everywhere with different values. Logic lives in roles, and shared roles come from versioned collections. Secrets are encrypted with Ansible Vault, using different vault IDs per environment, or pulled from HashiCorp Vault at runtime. Before production I run with check mode and diff, then roll out in serial batches with a max failure percentage, so a bad change stops after a few hosts. Production runs only happen from CI or AWX with separate credentials, and roles are tested with Molecule, including an idempotence check, and ansible-lint in CI."

Likely follow-up questions

  • How do you avoid accidentally running against production? Separate inventories and credentials, runs only via CI/AWX, and assertion guards.
  • Does check mode always work? Not for every task; commands and dependent tasks may be skipped or misleading, so modules need check-mode support.
  • What is AWX? The open-source upstream of Ansible Automation Platform, adding a UI, RBAC, scheduling and audit.
