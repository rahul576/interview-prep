Which JDK command-line tools do you use to diagnose a running JVM?

JVM & Performance · concept · levels mid, senior

In one line

jps lists JVMs, jcmd is the Swiss-army knife (thread dumps, heap dumps, histograms, flags, native memory, JFR), jstack prints thread dumps, jmap dumps heaps, jstat shows live GC statistics, and JFR plus JDK Mission Control give low-overhead production profiling.

Detailed explanation

jps -l shows Java process ids and main classes or jars, the starting point for every other tool.

jcmd is the recommended modern tool because it covers almost everything through one interface: jcmd <pid> help lists commands. Useful ones: Thread.print (thread dump, with -l for lock info), GC.heap_dump <file>, GC.class_histogram (objects by class, quick leak hint), GC.heap_info, VM.flags and VM.system_properties (the effective configuration), VM.native_memory summary (requires -XX:NativeMemoryTracking=summary at startup), Compiler.codecache, JFR.start, JFR.dump, JFR.stop, and Thread.dump_to_file which can write JSON and includes virtual threads (Java 21).

jstack <pid> prints all thread stacks and detects Java-level deadlocks. It is good for stuck requests, lock contention and matching hot native threads (nid) from top -H.

jmap: jmap -dump:live,format=b,file=heap.hprof <pid> for a heap dump, jmap -histo:live for a histogram. Note live forces a full GC first.

jstat -gcutil <pid> 1000 prints utilisation of survivor, eden, old and Metaspace every second, plus counts and total time of young and full GCs. It is perfect for spotting a filling old generation or GC storms live.

JFR (Java Flight Recorder) is built into the JDK (free since JDK 11), records CPU samples, allocation samples, GC, locks, I/O, exceptions and JVM events with roughly 1-2% overhead, so it can run continuously in production. JDK Mission Control analyses the .jfr files; jfr print and jfr summary work on the command line.

Containers. Tools must run as the same user and see the same process; in Kubernetes use kubectl exec if the image includes a JDK, or kubectl debug with an ephemeral container sharing the process namespace. Slim JRE images may lack these tools, so plan for it.

How it works

  1. jps to get the pid.
  2. jstat for a live view of GC health.
  3. jcmd Thread.print or jstack for hangs and CPU hotspots.
  4. jcmd GC.class_histogram then GC.heap_dump for memory issues.
  5. jcmd JFR.start for a profile; analyse in Mission Control.

Example

jps -l
# 4211 orders-service.jar

jstat -gcutil 4211 1000 5
#  S0  S1     E     O     M   YGC  YGCT  FGC  FGCT
#  0.0 42.1  63.5  71.2  94.8 1520 12.3    2  1.10

jcmd 4211 Thread.print -l > threads.txt
jcmd 4211 GC.class_histogram | head -15
jcmd 4211 GC.heap_dump /tmp/orders.hprof
jcmd 4211 VM.flags
jcmd 4211 JFR.start name=prof duration=120s filename=/tmp/prof.jfr settings=profile
jfr summary /tmp/prof.jfr

Common mistakes

  • Running tools as a different OS user than the JVM and getting attach errors.
  • Taking heap dumps on a live, overloaded instance without considering the pause.
  • Forgetting to enable Native Memory Tracking before needing it.
  • Shipping images without any diagnostic tooling.

How to answer in the interview

"jps lists the running JVMs and their process ids. jcmd is my Swiss-army knife: thread dumps, heap dumps, class histograms, effective VM flags, native memory tracking and starting or dumping Java Flight Recorder. jstack prints thread dumps for deadlocks and contention, jmap creates heap dumps and histograms, and jstat shows live GC statistics such as utilisation of each generation and GC counts. JFR records low-overhead profiling data that's safe in production, and I analyse it in JDK Mission Control. In Kubernetes I run them via kubectl exec or an ephemeral debug container that shares the process namespace, then copy the files out."

Likely follow-up questions

  • How do you take a heap dump from a JVM running in a Kubernetes pod? kubectl exec (or kubectl debug) then jcmd <pid> GC.heap_dump /tmp/h.hprof, and kubectl cp it out; make sure disk space is enough.
  • How do you find a deadlock? A thread dump; jstack and jcmd print "Found one Java-level deadlock" with the threads involved.
  • What overhead does JFR have? Typically about 1% with default settings, a bit more with the profile settings.
