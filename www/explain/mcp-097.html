How do you handle authentication for MCP servers that call third-party SaaS APIs on behalf of users?

MCP Servers · concept · levels mid, senior

In one line

The server plays two OAuth roles: a resource server that validates tokens issued for itself, and an OAuth client to the SaaS API, where each user consents separately; it stores per-user third-party tokens encrypted, refreshes them, and never passes the MCP token through to the SaaS API.

Detailed explanation

Towards MCP clients, the server is an OAuth 2.1 resource server. Clients get an access token from the authorization server associated with the MCP server, and the server validates the token's signature, expiry and audience, which must be the MCP server itself. That token proves who the user is to the MCP server; it means nothing to Salesforce or Jira.

Towards the SaaS provider, the server is a separate OAuth client, registered with that provider. The first time a user calls a tool that needs, say, Jira, and no Jira token exists for them, the server returns a message asking the user to authorise, typically via a URL-mode elicitation or a link. The user signs in at the SaaS provider and grants the requested scopes; the provider redirects to the server's callback with a code, which the server exchanges for an access token and refresh token.

Those tokens are stored per user, encrypted at rest (for example with a KMS-managed key), keyed by the stable user identity from the MCP token. Every downstream call uses that user's own SaaS token, so the SaaS permissions and audit trail apply naturally. The server refreshes tokens before expiry and handles failures: if refresh fails or the user has revoked access, it deletes the stored token and asks the user to reconnect. Token passthrough, forwarding the MCP token to a downstream API, is explicitly forbidden by the MCP specification because it breaks audience validation and creates confused-deputy risks.

How it works

  1. Client calls a tool with an MCP access token; server validates it and resolves the user ID.
  2. Server looks up the stored SaaS token for that user.
  3. If none exists, it returns an authorisation link or URL elicitation with state bound to the user.
  4. User consents at the SaaS provider; callback exchanges the code for tokens (with PKCE).
  5. Tokens are encrypted and stored; the tool call is retried and uses the user's SaaS token.
  6. On 401 or refresh failure, tokens are removed and the user is asked to reconnect.

Example

async def jira_call(mcp_user_id: str, path: str):
    tok = await token_store.get(mcp_user_id, provider="jira")   # decrypted
    if tok is None:
        raise NeedsAuthorization(auth_url=build_jira_auth_url(state=sign(mcp_user_id)))
    if tok.expires_soon():
        tok = await refresh(tok)          # store rotated refresh token
    resp = await http.get(JIRA + path, headers={"Authorization": f"Bearer {tok.access}"})
    if resp.status == 401:
        await token_store.delete(mcp_user_id, "jira")
        raise NeedsAuthorization(auth_url=build_jira_auth_url(state=sign(mcp_user_id)))
    return resp.json()

Common mistakes

  • Forwarding the MCP client's token to the SaaS API.
  • Using one shared admin service account, which bypasses per-user permissions.
  • Storing refresh tokens in plain text or logs.
  • Not binding the OAuth state to the user, enabling account-mixing attacks.
  • Ignoring refresh token rotation and revocation.

How to answer in the interview

"The server has two OAuth roles. To MCP clients it's a resource server: it validates tokens issued for it, including the audience. To the SaaS API it's an OAuth client: when a user first needs Jira, the server sends them a consent link, often through URL elicitation, and exchanges the code for tokens. I store those tokens per user, encrypted, linked to the user ID from the MCP token, and refresh them as needed. Every downstream call uses that user's own token so SaaS permissions apply, and the MCP token is never passed through, which the spec forbids."

Likely follow-up questions

  • What if the user revokes access in the SaaS app? The next call gets 401 or refresh fails; delete the token and prompt reconnection.
  • Why not a service account? It ignores per-user permissions and audit; use it only for genuinely system-level tasks.
  • Where do you store tokens? An encrypted store or secrets vault, keyed by user, with access restricted to the server.
