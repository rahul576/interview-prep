How do you handle database schema migrations in a Java application?

Spring Data & JPA · concept · levels mid, senior

In one line

Manage schema changes with Flyway or Liquibase: versioned migration scripts in source control, applied automatically and recorded in a history table, never ddl-auto=update in production, and backward-compatible expand-and-contract steps for zero-downtime deployments.

Detailed explanation

The database schema is part of the application, so it must be versioned, reviewed and reproducible just like code. Flyway and Liquibase both keep a history table (flyway_schema_history, DATABASECHANGELOG) recording which migrations were applied, with checksums, so every environment, from a developer laptop to production, arrives at the same schema in the same order.

Flyway uses plain SQL files named V1__create_orders.sql, V2__add_status.sql (plus repeatable R__ scripts and Java migrations). Liquibase uses changelogs (YAML, XML, JSON or SQL) with changesets, offering database-independent change types, preconditions and rollback definitions. Spring Boot runs either automatically at startup when it is on the classpath; many teams instead run migrations as a separate pipeline step or Kubernetes Job so multiple instances don't race and app permissions can be minimal.

Never use spring.jpa.hibernate.ddl-auto=update (or create) in production. It cannot rename or drop safely, produces unreviewed DDL and leaves no history. Use validate or none and let Hibernate only check the mapping.

Zero downtime means old and new application versions run at the same time during a rolling deploy, so every migration must be backward compatible. The expand and contract (parallel change) pattern:

  1. Expand: add the new column or table, nullable or with a default.
  2. Deploy code that writes both old and new.
  3. Backfill existing rows in batches.
  4. Switch reads to the new structure.
  5. Contract: in a later release, stop writing the old column and drop it.

Large tables need care: avoid long locks (in PostgreSQL use CREATE INDEX CONCURRENTLY, add columns without volatile defaults), batch backfills, and use online schema change tools such as gh-ost or pt-online-schema-change for MySQL.

How it works

  1. Developer adds a new migration file next to the code change.
  2. CI runs migrations on a fresh database (Testcontainers) and runs tests.
  3. Deploy: migration step applies pending versions and records them.
  4. New app version starts, compatible with the old schema state too.
  5. Later release contracts the old structure.

Example

-- V12__add_customer_email.sql  (expand)
ALTER TABLE customer ADD COLUMN email_address VARCHAR(255);

-- V13__backfill_email.sql
UPDATE customer SET email_address = email WHERE email_address IS NULL;

-- V20__drop_old_email.sql   (contract, a later release)
ALTER TABLE customer DROP COLUMN email;
spring:
  jpa:
    hibernate:
      ddl-auto: validate
  flyway:
    locations: classpath:db/migration

Common mistakes

  • Editing an already-applied migration (checksum failures, divergent environments).
  • Renaming or dropping columns in the same release as the code change.
  • Huge single-transaction backfills locking tables.
  • Using ddl-auto=update outside local development.

How to answer in the interview

"I use Flyway or Liquibase with versioned migration scripts in source control, applied automatically at startup or as a pipeline step, so every environment has the same schema history. I never use Hibernate ddl-auto update in production; I set it to validate. For zero-downtime deployments, changes must be backward compatible with expand and contract: add the new column, deploy code that writes both, backfill, switch reads, and only in a later release drop the old column. Large table changes run as batched or online migrations."

Likely follow-up questions

  • Rename a column without downtime? Add new column, dual-write, backfill, switch reads, drop old later.
  • Rollback a migration? Prefer roll-forward fixes; Liquibase supports rollback definitions.
  • Run at startup or in the pipeline? Pipeline or Job for control and permissions; startup is fine for small services.
