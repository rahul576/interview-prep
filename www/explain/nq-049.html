How can you ensure thread safety when using parallel streams?

Java 8+ Features · concept · levels mid, senior

In one line

Make parallel streams thread-safe by design: keep lambdas stateless and side-effect free, do not modify the source, build results with collect, reduce and Collectors that merge per-thread containers, use concurrent collectors when order does not matter, and atomics or LongAdder only as a last resort.

Detailed explanation

The stream API's own contract gives the recipe. Behavioural parameters (the lambdas) should be:

  • Non-interfering: they must not modify the source collection while the pipeline runs.
  • Stateless: their result must not depend on state that changes during execution, such as a shared Set used to track "seen" items.
  • Side-effect free where possible: no writes to external variables or collections.

If you follow these rules, the stream does the coordination for you. Mutable reduction with collect gives each worker its own container (a list, a map, a StringBuilder) and then combines them with the collector's combiner. reduce needs an identity value (such as 0 for addition) and an associative accumulator and combiner, because partial results may be grouped in any way: (a + b) + c must equal a + (b + c). Primitive operations like sum, count, max and summaryStatistics are already safe.

When encounter order does not matter and you are grouping a large data set, Collectors.groupingByConcurrent and toConcurrentMap write into one shared ConcurrentHashMap, which avoids the cost of merging many partial maps. They are unordered by nature.

If you really need a shared counter, for example for metrics, use LongAdder (low contention, stripes the count internally) or AtomicLong. These are correct, but they add contention, so prefer computing the value as part of the pipeline.

Immutability makes everything simpler: records and immutable value objects can be read safely by any number of threads. Finally, remember that context stored in ThreadLocal (logging MDC, security context, transactions) is not available on worker threads.

How it works

  1. Write pure lambdas that only use their input.
  2. Never add, remove or set elements on the source during processing.
  3. Produce results through collectors or reductions.
  4. Supply a correct identity and an associative combiner for reduce.
  5. Use concurrent collectors for large unordered groupings.
  6. Use LongAdder only for unavoidable shared counters.

Example

// Safe aggregation
Map<String, Long> countsByCity = customers.parallelStream()
    .collect(Collectors.groupingByConcurrent(Customer::city, Collectors.counting()));

// Correct three-argument reduce: identity, accumulator, combiner
long totalChars = lines.parallelStream()
    .reduce(0L, (acc, line) -> acc + line.length(), Long::sum);

// Unavoidable shared metric
LongAdder invalid = new LongAdder();
List<Record> valid = records.parallelStream()
    .filter(r -> { boolean ok = r.isValid(); if (!ok) invalid.increment(); return ok; })
    .toList();

// Stateful lambda (avoid): result depends on thread timing
Set<String> seen = new HashSet<>();
items.parallelStream().filter(i -> seen.add(i.key())); // use distinct() instead

Common mistakes

  • A non-associative reduction such as subtraction or average-of-averages.
  • An identity that is not neutral, for example reduce(10, Integer::sum), which adds 10 per chunk.
  • Using a shared HashSet for de-duplication instead of distinct().
  • Expecting ordered output from groupingByConcurrent.

How to answer in the interview

"I write the pipeline so it does not need synchronisation. Lambdas are stateless and pure, they do not read or write shared mutable variables, and they never modify the source while it is processed. Results come from terminal operations designed for parallelism: collect with Collectors, toList, sum, or reduce with a true identity and an associative accumulator and combiner. When order does not matter, groupingByConcurrent or toConcurrentMap use a ConcurrentHashMap. If I really need a shared counter I use LongAdder, accepting some contention. Immutable objects and records make all of this easier, and I remember that ThreadLocal context does not propagate to the workers."

Likely follow-up questions

  • Why must the reduce operation be associative? Chunks are reduced separately and combined in arbitrary groupings, so only associative operations give the same answer.
  • LongAdder vs AtomicLong? LongAdder spreads updates across cells, so it scales better under high write contention.
  • What does non-interference mean? The source must not be modified during the stream's execution.
