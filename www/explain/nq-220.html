How do microservices communicate with one another?

Microservices · concept · levels entry, mid

In one line

Microservices communicate synchronously through REST/HTTP or gRPC and asynchronously through events or messages on brokers such as Kafka, RabbitMQ or SQS, using service discovery and load balancing, resilience patterns and explicit contracts (OpenAPI, schemas).

Detailed explanation

Synchronous request-response. The caller sends a request and waits for a response.

  • REST over HTTP with JSON is the most common choice: simple, human-readable, supported everywhere and described with OpenAPI. Typical for queries and public APIs.
  • gRPC uses Protocol Buffers over HTTP/2: compact binary messages, generated type-safe clients, streaming and built-in deadlines. Popular for high-volume internal calls.

Clients find instances by name through service discovery: Kubernetes Services and DNS, or registries like Eureka or Consul with client-side load balancing.

Asynchronous messaging. A service publishes a message and continues; others consume it later.

  • Events announce facts: OrderPlaced. Many services can react: payment, inventory, email, analytics. The producer does not know or wait for them.
  • Commands ask one service to do something: SendInvoice, often via a work queue.

Brokers include Kafka (retained, replayable event streams), RabbitMQ (flexible routing, task queues) and cloud services such as Amazon SQS/SNS, Azure Service Bus or Google Pub/Sub. Messaging decouples services in time and availability, buffers spikes and suits workflows and notifications, but requires idempotent consumers and handling of eventual consistency.

What both need. Synchronous calls need timeouts, retries with backoff for idempotent operations and circuit breakers, for example with Resilience4j, so one slow service does not take down others. Messaging needs dead-letter queues, reliable publishing (the outbox pattern) and idempotency. Both need clear contracts: OpenAPI or .proto files for APIs, schemas (Avro, Protobuf, JSON Schema) in a schema registry for events, plus versioning and contract tests. Finally, trace context and auth tokens must be propagated so requests can be followed and secured across services.

How it works

  1. Order service receives "place order".
  2. It calls inventory synchronously (REST) to check stock, with a timeout and breaker.
  3. It saves the order and publishes OrderPlaced to Kafka (via outbox).
  4. Payment and notification services consume the event independently.
  5. Payment publishes PaymentCompleted; order service updates status.

Example

// Synchronous REST call with Spring's RestClient
Stock stock = restClient.get()
        .uri("http://inventory-service/stock/{sku}", sku)
        .retrieve()
        .body(Stock.class);

// Asynchronous event with Spring Kafka
kafkaTemplate.send("orders.events", order.id(), new OrderPlaced(order.id(), order.total()));

@KafkaListener(topics = "orders.events", groupId = "notification")
void onOrderPlaced(OrderPlaced e) { emailService.sendConfirmation(e.orderId()); }

Common mistakes

  • Making everything synchronous, creating long fragile call chains.
  • Making everything asynchronous, even queries.
  • No timeouts on HTTP clients.
  • Unversioned event payloads.

How to answer in the interview

"There are two styles. Synchronous request-response, where the caller waits: REST over HTTP with JSON, common for queries, or gRPC with Protocol Buffers for fast internal calls; instances are found through service discovery or Kubernetes DNS with load balancing. And asynchronous messaging, where a service publishes events or commands to Kafka, RabbitMQ or SQS and others consume them later, which decouples services and suits workflows and notifications like OrderPlaced. Synchronous calls need timeouts, retries and circuit breakers, for example with Resilience4j, and both styles need clear contracts: OpenAPI for REST and schemas in a registry for events."

Likely follow-up questions

  • How do you choose between REST and Kafka? REST when you need an answer now; an event when others just need to react.
  • Why gRPC internally? Efficient binary encoding, typed contracts, streaming and deadlines.
  • What is a dead-letter queue? Where messages go after repeated processing failures, for inspection and replay.
