Can sealed classes be applied to interfaces?

Modern Java (11-21) · concept · levels mid, senior

In one line

Yes: a sealed interface with permits restricts its implementations, typically records (implicitly final), which is the idiomatic way to model algebraic data types like Result and handle them with exhaustive pattern-matching switch.

Detailed explanation

Sealing works the same way for interfaces as for classes. sealed interface PaymentResult permits Approved, Declined, Pending means only those three types may implement it (or extend it, if one is itself an interface). Each permitted type must be final, sealed or non-sealed; records satisfy this automatically because they are final, and enums can also implement sealed interfaces.

Interfaces are actually the more common choice, because records cannot extend classes but can implement interfaces. Together they form a sum type (one of several alternatives), where each alternative carries its own data: Approved holds a transaction id, Declined a reason, Pending a retry time. Typical uses:

  • Result types: Success<T> / Failure instead of exceptions for expected outcomes.
  • Commands and events in a domain: OrderEvent permitting Created, Paid, Shipped, Cancelled.
  • API responses or parsed expression trees.

With Java 21 pattern matching for switch and record patterns, you can deconstruct the alternatives directly, add guards with when, and the compiler verifies the switch covers every permitted type, without a default.

Compared with an enum: an enum is a fixed set of instances that share the same fields; a sealed interface is a fixed set of types, each with its own shape and any number of instances. Compared with the visitor pattern, sealed types plus switch give the same safety with far less code.

How it works

  1. Declare sealed interface X permits A, B, C.
  2. Implement with records (final) or final/sealed/non-sealed classes.
  3. Switch on X with type or record patterns.
  4. Compiler enforces exhaustiveness.

Example

public sealed interface PaymentResult permits Approved, Declined, Pending {}
public record Approved(String txId, BigDecimal amount) implements PaymentResult {}
public record Declined(String code) implements PaymentResult {}
public record Pending(Duration retryAfter) implements PaymentResult {}

ResponseEntity<?> toResponse(PaymentResult r) {
    return switch (r) {
        case Approved(var tx, var amt) -> ResponseEntity.ok(Map.of("tx", tx));
        case Declined(var code) when code.equals("FRAUD") -> ResponseEntity.status(403).build();
        case Declined d -> ResponseEntity.unprocessableEntity().body(d.code());
        case Pending p -> ResponseEntity.accepted().build();
    };
}

Common mistakes

  • Adding default, losing the compile-time check.
  • Using a sealed hierarchy where a simple enum would do.
  • Mixing up the order of guarded and unguarded cases (a dominated case is a compile error).
  • Forgetting implementations must be in the same package or module.

How to answer in the interview

"Yes. An interface can be sealed exactly like a class: sealed interface PaymentResult permits Approved, Declined, Pending. The implementations are usually records, which fit perfectly because they're implicitly final, and each alternative carries its own data. That's how I model closed sets of outcomes, like a Result type or domain events. With Java 21 pattern matching for switch I can deconstruct each record, add guards with when, and the compiler checks that every case is handled without a default. Compared with an enum, each alternative can have different fields."

Likely follow-up questions

  • How does a sealed interface compare with an enum? Enum is fixed instances with shared shape; sealed interface is fixed types with different data.
  • Can an enum implement a sealed interface? Yes, enums are implicitly final or sealed.
  • What is a guard? A when condition on a case label that must also be true.
