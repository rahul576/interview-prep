What is the .terraform.lock.hcl file, and should it be committed?

Infrastructure as Code · concept · levels entry

In one line

.terraform.lock.hcl is the dependency lock file: terraform init records the exact provider versions and checksums selected, and it should be committed so every run uses the same, verified providers.

Detailed explanation

Version constraints in required_providers, such as ~> 5.40, allow a range. Without a lock, terraform init would pick the newest matching version, so two runs a week apart might use different providers with different behaviour or bugs. The lock file solves this. On first init, Terraform writes, for each provider, the selected version, the constraints it satisfied and a list of hashes. Later inits reuse exactly that version and verify the downloaded package against the hashes, which also protects against tampered or corrupted plugins.

The lock file belongs in version control alongside the code, exactly like package-lock.json. Upgrades then become deliberate: run terraform init -upgrade, which picks the newest versions allowed by the constraints and rewrites the lock file, then review that diff and the resulting plan in a pull request. Note the lock file covers providers only; module versions are controlled by the version argument or Git ref in each module call.

Hashes are platform specific for the h1: form. When installing from the public registry, Terraform also records zh: hashes the registry publishes for all platforms, but with mirrors, caches or private registries a lock created on a Mac may only contain hashes valid for macOS, and init on Linux CI fails with a checksum mismatch. terraform providers lock -platform=... pre-populates hashes for every platform the team uses.

How it works

  1. terraform init resolves provider constraints.
  2. It writes version, constraints and hashes into .terraform.lock.hcl.
  3. Subsequent inits install exactly the locked version and verify hashes.
  4. terraform init -upgrade deliberately moves to newer allowed versions.
  5. terraform providers lock adds hashes for additional platforms.

Example

provider "registry.terraform.io/hashicorp/aws" {
  version     = "5.82.2"
  constraints = "~> 5.40"
  hashes = [
    "h1:abc...",
    "zh:0123...",
  ]
}
terraform providers lock \
  -platform=linux_amd64 -platform=darwin_arm64 -platform=windows_amd64
terraform init -upgrade   # deliberate upgrade, review the diff

Common mistakes

  • Adding the lock file to .gitignore.
  • Running init -upgrade casually in CI, defeating the lock.
  • Lock files with hashes for only one platform when using mirrors.
  • Confusing the lock file with the .terraform/ directory, which should not be committed.

How to answer in the interview

"The .terraform.lock.hcl file is Terraform's dependency lock file. terraform init records the exact provider version it chose within my constraints plus checksums of the packages. I always commit it, so developers and CI use exactly the same provider versions and Terraform verifies the downloaded plugins haven't been tampered with. Without it, two runs could silently pick up different providers. Upgrades are deliberate: terraform init -upgrade, review the lock file diff and the plan in a PR. Because developers on macOS and CI on Linux need different packages, I use terraform providers lock with several platforms so hashes exist for all of them."

Likely follow-up questions

  • What happens in CI if the lock only has macOS hashes? init can fail with a checksum mismatch for the Linux package; add platforms with terraform providers lock.
  • Does it lock module versions? No, only providers.
  • Should .terraform/ be committed? No, it is a local cache.
