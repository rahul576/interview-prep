How do you share build outputs and packages in Azure DevOps: pipeline artifacts versus Azure Artifacts?

Azure DevOps & Pipelines · concept · levels mid, senior

In one line

Pipeline artifacts carry build outputs between stages and pipelines (build once, deploy the same artifact everywhere); Azure Artifacts hosts package feeds (NuGet, npm, Maven/Gradle, Python, Cargo, universal) with upstream sources that cache public registries and views for promotion; container images go to ACR.

Detailed explanation

Pipeline artifacts are files produced by a run: a zipped web app, compiled binaries, Helm charts, Bicep files, test reports. You publish them with publish: / PublishPipelineArtifact@1 and download them in later stages with download: / DownloadPipelineArtifact@2, or from another pipeline declared as a resource. Deployment jobs download artifacts automatically. They are tied to the run and its retention. The key principle is build once, deploy many: the exact binary tested in staging is the one promoted to production, rather than rebuilding per environment, which could pull different dependencies. (Build artifacts via PublishBuildArtifacts are the older, slower mechanism.)

Azure Artifacts is a package management service for reusable libraries shared across teams and repos. Feeds (organisation- or project-scoped) host NuGet, npm, Maven, Gradle, Python (pip/twine), Cargo and Universal Packages. Pipelines authenticate with the build identity using NuGetAuthenticate, npmAuthenticate or PipAuthenticate tasks.

Upstream sources let one feed proxy public registries such as nuget.org, npmjs, Maven Central and PyPI. The first time a package is requested, it is saved into the feed, so builds keep working if the public registry is down or the package is unpublished, and you have one place to audit. Combined with internal packages, upstreams help against dependency confusion: once a package name exists internally in the feed, versions of that name from the upstream are blocked by default, so an attacker publishing a higher version of your internal package name on the public registry isn't pulled.

Views (@local, @prerelease, @release) let you promote a package after validation; consumers point at @release to get only approved versions. Retention policies clean up old versions.

Container images are not stored in Azure Artifacts; they go to Azure Container Registry.

How it works

  1. Build stage compiles and publishes a pipeline artifact.
  2. Later stages download the same artifact and deploy.
  3. Library pipelines pack and push packages to a feed.
  4. Consumers restore through the feed, which proxies public upstreams.
  5. Validated packages are promoted to the @release view.

Example

- stage: Build
  jobs:
  - job: build
    steps:
    - task: NuGetAuthenticate@1
    - script: dotnet publish src/Web -c Release -o $(Build.ArtifactStagingDirectory)/web
    - publish: $(Build.ArtifactStagingDirectory)/web
      artifact: web
- stage: Prod
  jobs:
  - deployment: deploy
    environment: shop-prod
    strategy:
      runOnce:
        deploy:
          steps:
          - download: current
            artifact: web

Common mistakes

  • Rebuilding for each environment.
  • Pushing Docker images to Azure Artifacts instead of ACR.
  • Builds pulling directly from public registries, bypassing the feed.
  • Promoting packages by republishing instead of views.

How to answer in the interview

"Pipeline artifacts are the outputs of a run, published in the build stage and downloaded by later stages or pipelines, so we build once and deploy the same artifact everywhere. Azure Artifacts is package management: feeds host NuGet, npm, Maven, Python and universal packages for sharing libraries. Upstream sources proxy and cache public registries like npmjs and nuget.org, so we have one audited source that survives outages and helps against dependency confusion. Views like prerelease and release let us promote packages after validation. Container images go to Azure Container Registry."

Likely follow-up questions

  • Upstreams vs dependency confusion? Internal package names take precedence; public versions of the same name are blocked by default.
  • Artifact retention? Follows run retention; retain runs that reached production.
  • Universal Packages? Arbitrary files with versioning, like tools or datasets.
