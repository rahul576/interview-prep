What is synchronization, and why is it needed?

Concurrency · concept · levels mid, senior

In one line

Synchronisation coordinates threads that access shared mutable state, giving atomicity (no interleaving inside a critical section) and visibility (changes are seen by other threads via happens-before), which prevents race conditions.

Detailed explanation

Threads share the heap, so two threads can touch the same object at the same time. Without coordination you get two kinds of bugs.

Atomicity problems: count++ looks like one operation but is three steps: read, add, write. If two threads read 5 at the same moment, both write 6 and one update is lost. The same happens with check-then-act logic such as "if not present, insert". Synchronisation makes such a critical section run as one indivisible unit relative to other threads using the same lock.

Visibility problems: CPUs cache values and the JIT reorders and hoists reads, so without a rule one thread may never see another's write. The Java Memory Model defines happens-before edges; one of them is that releasing a monitor happens-before every later acquisition of the same monitor. So everything a thread wrote before leaving a synchronized block is visible to the next thread entering a block on that same lock.

Java's built-in mechanism is the intrinsic lock (monitor) that every object has, used by the synchronized keyword on methods or blocks. It is reentrant: the owning thread can enter again. java.util.concurrent adds explicit Locks, ReadWriteLock, atomic classes based on CAS, and concurrent collections that handle synchronisation internally.

Synchronisation has a cost: threads wait for each other (contention), throughput drops, and taking multiple locks in different orders risks deadlock. So keep critical sections small and prefer immutability or confinement when possible.

How it works

  1. Thread A reaches synchronized (lock) and acquires the monitor.
  2. Other threads trying to enter on the same lock become BLOCKED.
  3. A performs the compound action (read, modify, write).
  4. A exits the block, releasing the monitor and publishing its writes.
  5. Thread B acquires the monitor and sees A's latest values.

Example

class Counter {
    private int count;                         // shared mutable state

    void unsafeIncrement() { count++; }        // read-add-write: lost updates

    synchronized void safeIncrement() { count++; }  // atomic and visible

    synchronized int get() { return count; }   // reads need the lock too
}

// 2 threads x 100_000 increments:
// unsafeIncrement -> often less than 200000
// safeIncrement   -> always 200000
// Lock-free alternative: AtomicInteger.incrementAndGet()

Common mistakes

  • Synchronising the writer but not the reader, so readers may see stale values.
  • Using different lock objects for the same data.
  • Holding a lock during slow I/O, causing contention.
  • Assuming volatile makes count++ safe; it gives visibility only.
  • Synchronising everything "to be safe", hurting throughput and risking deadlocks.

How to answer in the interview

"Synchronisation coordinates multiple threads accessing shared mutable state. Without it you get race conditions: count++ is really read, add and write, so two threads can read the same value and one update is lost. It gives two guarantees: atomicity, so a critical section runs as one unit, and visibility, because under the Java Memory Model releasing a lock happens-before the next acquisition of the same lock. In Java, synchronized uses each object's intrinsic lock, and java.util.concurrent adds explicit locks, atomics and concurrent collections. I keep critical sections small because too much locking hurts throughput and can cause deadlocks."

Likely follow-up questions

  • Is synchronization needed if only one thread writes and others read? Atomicity is not an issue for a single variable, but visibility is; use volatile or a lock, and for multi-field updates still use a lock.
  • What is a monitor? The intrinsic lock plus wait set associated with every Java object.
  • What is reentrancy? A thread holding a lock can acquire it again without deadlocking itself.
