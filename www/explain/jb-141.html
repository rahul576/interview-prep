What is the difference between DELETE, TRUNCATE, and DROP?

Databases & SQL · concept · levels mid, senior

In one line

DELETE is DML that removes selected rows (with WHERE), logged row by row, firing triggers and rollbackable; TRUNCATE quickly removes all rows by deallocating storage and usually resets identity; DROP removes the table itself, including structure, indexes and constraints.

Detailed explanation

DELETE removes the rows that match an optional WHERE. Each row is locked, logged (undo and redo/WAL), checked against foreign keys and passed to row-level triggers. It runs inside a transaction and can be rolled back. In PostgreSQL deleted rows become dead tuples reclaimed later by VACUUM; in InnoDB space is reused but the file does not shrink. Deleting millions of rows in one statement creates huge transactions, long locks, replication lag and bloat.

TRUNCATE removes all rows by deallocating data pages or creating a fresh empty file, which makes it nearly instantaneous regardless of size. It does not fire row-level DELETE triggers, typically resets auto-increment/identity counters (MySQL always; PostgreSQL with RESTART IDENTITY), and takes an exclusive table lock. It refuses to run when other tables reference it through foreign keys (PostgreSQL offers CASCADE). It is classed as DDL in most databases: in MySQL and Oracle it causes an implicit commit and cannot be rolled back, while PostgreSQL and SQL Server allow it inside a transaction and can roll it back.

DROP TABLE removes the table definition plus its data, indexes, constraints, triggers and privileges. Dependent objects such as views or foreign keys from other tables block it unless you use CASCADE. Oracle may keep it in the recycle bin (FLASHBACK TABLE), but generally you need a backup to recover.

How it works

  1. DELETE: find rows, lock, write undo/WAL, apply FK actions and triggers, mark rows deleted.
  2. TRUNCATE: take an exclusive lock, swap or deallocate the storage, reset counters.
  3. DROP: remove catalogue entries and storage for the table and its dependants.
  4. Transactional behaviour depends on the engine for TRUNCATE and DROP.

Example

DELETE FROM audit_log WHERE created_at < DATE '2025-01-01';   -- selective, slow, rollbackable
TRUNCATE TABLE staging_import;                                -- empty it fast
TRUNCATE TABLE staging_import RESTART IDENTITY;               -- PostgreSQL
DROP TABLE IF EXISTS tmp_migration;                           -- gone

-- Deleting 50 million old rows safely: small batches
DELETE FROM audit_log
WHERE id IN (SELECT id FROM audit_log
             WHERE created_at < DATE '2025-01-01' LIMIT 10000);
-- repeat until 0 rows, pausing between batches

Common mistakes

  • Saying TRUNCATE can never be rolled back; it depends on the database.
  • Running one giant DELETE on a busy production table.
  • Expecting DELETE to reclaim disk space immediately.
  • Using TRUNCATE where audit triggers must run.

How to answer in the interview

"DELETE is DML: it removes rows matching a WHERE clause, logs each row, fires triggers, respects foreign keys and can be rolled back, but it's slow on large tables. TRUNCATE removes all rows at once by deallocating pages, so it's very fast, usually resets the identity counter and doesn't fire row triggers. It's treated as DDL, so in MySQL and Oracle it commits implicitly and can't be rolled back, while PostgreSQL allows it in a transaction. DROP removes the table itself, including structure, indexes and constraints. For deleting tens of millions of old rows in production, I'd delete in small batches, or better, partition by date and drop old partitions."

Likely follow-up questions

  • How to delete 50 million old rows from a busy table? Small batches by key range with pauses, off-peak, or drop date partitions.
  • Why doesn't DELETE shrink the file? Space is marked reusable; VACUUM FULL or OPTIMIZE TABLE is needed to shrink.
  • Can you TRUNCATE a table referenced by a foreign key? Not normally; PostgreSQL needs CASCADE, MySQL needs FK checks disabled.
