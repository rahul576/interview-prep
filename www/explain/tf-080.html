How do you document Terraform modules so other teams can use them correctly?

Terraform · concept · levels entry, mid, senior

In one line

Every module needs a README with purpose, usage example and design decisions, generated input/output reference via terraform-docs, meaningful descriptions on every variable and output, a tested examples directory, and a changelog with upgrade notes.

Detailed explanation

A module is a product for other teams. If they cannot understand what it does and how to use it in five minutes, they will copy-paste raw resources instead or misuse it. Good documentation has a hand-written part and a generated part.

Hand-written README sections. What the module is for and what it creates; important design decisions and defaults, such as "public network access is always disabled", "diagnostics go to the central workspace", "uses private endpoints only"; what it deliberately does not do; prerequisites (existing subnets, permissions); and a short usage example showing the common case.

Generated reference. Tables of inputs with types, defaults and whether required, outputs, required providers and versions are generated by terraform-docs directly from the code, usually inserted between markers in the README by a pre-commit hook or CI job that fails if the README is out of date. That only works if every variable and output has a meaningful description, and variables have precise types and validation blocks that explain constraints; enforce this with tflint rules such as terraform_documented_variables and terraform_documented_outputs.

Examples. An examples/ directory with complete, minimal and advanced configurations. CI runs terraform validate, terraform test or a real apply in a sandbox against them, so examples cannot silently rot. They double as integration tests.

Changelog. A CHANGELOG.md per version, following semantic versioning, with clear upgrade notes for breaking changes, such as renamed inputs or required moved blocks. Release notes in the registry or Git tags point to it.

How it works

  1. Write descriptions, types and validation on every variable and output.
  2. Write the README narrative and usage example.
  3. Configure terraform-docs to inject the reference section.
  4. Add pre-commit or CI checks for docs freshness and tflint rules.
  5. Maintain tested examples.
  6. Update the changelog with each release.

Example

variable "sku_name" {
  description = "Key Vault SKU. Use 'premium' only when HSM-backed keys are required."
  type        = string
  default     = "standard"
  validation {
    condition     = contains(["standard", "premium"], var.sku_name)
    error_message = "sku_name must be 'standard' or 'premium'."
  }
}
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/terraform-docs/terraform-docs
    rev: v0.19.0
    hooks:
      - id: terraform-docs-go
        args: ["markdown", "table", "--output-file", "README.md", "."]

Common mistakes

  • Hand-written input tables that drift from the code.
  • Descriptions like "the name" that add nothing.
  • Examples never executed, broken after the first refactor.
  • Breaking changes released without upgrade notes.

How to answer in the interview

"Every module has a README explaining its purpose, what it creates, key design decisions like security defaults, and a short usage example. The reference part, inputs, outputs and providers, is generated by terraform-docs in a pre-commit hook or CI, so it never goes stale, which requires meaningful descriptions on every variable and output; I enforce that with tflint. An examples directory has working configurations that CI tests with terraform test or a sandbox apply. And a changelog per version with upgrade notes for breaking changes like required moved blocks."

Likely follow-up questions

  • How do you keep examples from going stale? Run them in CI on every module change.
  • Where should docs live? In the module repository, rendered by the private registry.
  • What about architecture diagrams? Include one for pattern modules with several resources.
