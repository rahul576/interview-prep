Summarise the MCP authorization specification for remote servers.

MCP Servers · concept · levels senior, lead

In one line

For HTTP transports, MCP authorization is OAuth 2.1: the MCP server is a resource server, it answers unauthenticated calls with 401 and WWW-Authenticate pointing to Protected Resource Metadata (RFC 9728), the client discovers the authorization server, uses authorization code with PKCE and the resource parameter (RFC 8707), sends the token in the Authorization header, and the server validates audience, scopes and expiry.

Detailed explanation

The authorization specification applies to remote servers (Streamable HTTP); stdio servers get credentials from their environment instead. Its key design choice is separation of roles. The MCP server is an OAuth resource server that only validates tokens. A separate authorization server, usually the company's identity provider such as Entra ID, Okta or Auth0, authenticates users and issues tokens. Early drafts had the MCP server act as its own authorization server; that was dropped because it forced every server to implement identity.

Discovery is automatic. A client calling without a valid token gets HTTP 401 with a WWW-Authenticate header containing a resource_metadata URL. That Protected Resource Metadata document (RFC 9728) lists the authorization servers and supported scopes. The client then fetches the authorization server's metadata (RFC 8414 or OpenID Connect discovery) to find its endpoints.

The client identifies itself (via a Client ID Metadata Document, pre-registration, or dynamic registration) and runs the authorization code flow with PKCE, which is mandatory. It includes the resource parameter (RFC 8707) with the MCP server's canonical URI, so the issued token's audience is that specific server.

Every request carries Authorization: Bearer <token>, never a query string. The server validates signature, issuer, audience, scopes and expiry on every request, returns 401 for invalid tokens and 403 with insufficient_scope when more scopes are needed.

How it works

  1. Client sends an MCP request without a token.
  2. Server: 401 + WWW-Authenticate: Bearer resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource".
  3. Client reads the metadata, finds the authorization server and its endpoints.
  4. Client runs authorization code + PKCE with resource=https://mcp.example.com/mcp; user signs in and consents.
  5. Client retries with the bearer token; refreshes it when it expires.
  6. Server validates the token on every request.

Example

HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource", scope="tickets:read"

GET /.well-known/oauth-protected-resource
{
  "resource": "https://mcp.example.com/mcp",
  "authorization_servers": ["https://login.example.com"],
  "scopes_supported": ["tickets:read", "tickets:write"]
}

Common mistakes

  • Accepting any valid token from the identity provider without checking the audience.
  • Putting tokens in URLs, where they end up in logs and proxies.
  • Skipping PKCE because "it's a confidential client".
  • Implementing your own login inside the MCP server instead of delegating to the IdP.

How to answer in the interview

"For HTTP transports, MCP authorization is based on OAuth 2.1. The MCP server is a resource server, and a separate authorization server, usually the company IdP, issues tokens. When a client calls without a valid token, the server returns 401 with a WWW-Authenticate header pointing to its Protected Resource Metadata, RFC 9728, which tells the client which authorization servers and scopes to use. The client runs the authorization code flow with PKCE and includes the RFC 8707 resource parameter so the token is bound to that server as its audience. Tokens go in the Authorization header, never in query strings, and the server validates signature, issuer, audience, scopes and expiry on every request."

Likely follow-up questions

  • Why is audience binding important? It stops a token issued for one server being replayed against another.
  • What does stdio use? Credentials from the environment; the OAuth spec does not apply.
  • What happens on insufficient scope? 403 with insufficient_scope, triggering step-up authorization.
