How does an API Gateway validate user roles and scopes?

Security · concept · levels mid, senior

In one line

After validating the token, the gateway reads its claims (scope/scp, roles, groups, provider-specific claims), maps them to authorities, compares them with the route's policy, returns 403 if they are insufficient, and uses introspection for opaque tokens.

Detailed explanation

Scopes and roles mean different things. A scope describes what the client application has been allowed to do on the user's behalf (orders.read), granted through consent or client configuration. A role or group describes what the user is (ADMIN, SUPPORT). Many policies check both: the app must hold orders.delete and the user must be ADMIN.

Where these sit depends on the provider: standard OAuth uses a space-separated scope claim (Entra ID uses scp for delegated scopes and roles for app roles), Keycloak puts realm roles in realm_access.roles and client roles in resource_access.<client>.roles, Okta and Cognito often use groups. So the gateway needs a claim-to-authority mapping. In Spring Security, scopes become SCOPE_orders.write by default, and a custom converter turns role claims into ROLE_ADMIN authorities.

Each route then has a policy: method plus path mapped to required authorities. The gateway checks them in order and returns 403 Forbidden when they are missing (401 stays reserved for invalid or missing tokens). Managed gateways do the same declaratively: AWS API Gateway JWT authorizers with authorization scopes per route, Azure API Management's validate-jwt policy with required-claims, Kong's OIDC or JWT plugins.

For opaque tokens the gateway cannot read claims, so it calls the authorization server's introspection endpoint (RFC 7662), which returns active, scope and other data; results are cached briefly. Keep scopes least privilege and specific, and remember the token reflects permissions at issue time, so short lifetimes limit stale roles.

How it works

  1. Validate signature, issuer, audience and expiry (or introspect an opaque token).
  2. Extract scopes and role claims.
  3. Map them to authorities with a converter.
  4. Match the request against route rules in order.
  5. Allow and forward, or return 403 and log the denial.

Example

@Bean
SecurityWebFilterChain gateway(ServerHttpSecurity http) {
    return http.authorizeExchange(e -> e
            .pathMatchers(HttpMethod.DELETE, "/api/orders/**")
                .access((auth, ctx) -> auth.map(a -> new AuthorizationDecision(
                    has(a, "SCOPE_orders.delete") && has(a, "ROLE_ADMIN"))))
            .pathMatchers(HttpMethod.GET, "/api/orders/**").hasAuthority("SCOPE_orders.read")
            .anyExchange().authenticated())
        .oauth2ResourceServer(o -> o.jwt(j -> j.jwtAuthenticationConverter(keycloakRoles())))
        .build();
}

// Converter: realm_access.roles -> ROLE_*, plus default SCOPE_* authorities
Converter<Jwt, Mono<AbstractAuthenticationToken>> keycloakRoles() {
    return jwt -> {
        Collection<GrantedAuthority> auths = new ArrayList<>(new JwtGrantedAuthoritiesConverter().convert(jwt));
        Map<String, Object> realm = jwt.getClaimAsMap("realm_access");
        if (realm != null) ((List<String>) realm.get("roles"))
            .forEach(r -> auths.add(new SimpleGrantedAuthority("ROLE_" + r.toUpperCase())));
        return Mono.just(new JwtAuthenticationToken(jwt, auths));
    };
}

Common mistakes

  • Treating scopes and roles as interchangeable.
  • Broad scopes like api.all that defeat least privilege.
  • Returning 401 when the token is valid but lacks a scope.
  • Assuming roles in a long-lived token are always current.

How to answer in the interview

"Once the token's signature and expiry are validated, the gateway reads its claims: scopes from scope or scp, and roles or groups from provider-specific claims like Keycloak's realm_access.roles. A converter maps those into authorities, for example SCOPE_orders.write and ROLE_ADMIN. Each route has a policy, such as DELETE on orders needing the orders.delete scope and the admin role, and the gateway returns 403 if the token doesn't satisfy it. For opaque tokens it calls the introspection endpoint instead, with caching. I keep scopes narrow, and services still check data-level permissions."

Likely follow-up questions

  • Scope vs role? Scope limits what the client may do for the user; role describes the user's permissions.
  • Why not put every permission in the token? Tokens grow and go stale; fetch fine-grained permissions in the service or a policy engine.
  • What is OPA? Open Policy Agent, a policy engine the gateway or service can query for decisions.
