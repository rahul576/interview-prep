Are records immutable, and can you define accessor, getter, or setter methods in them?

Modern Java (11-21) · concept · levels entry, mid

In one line

Records are shallowly immutable: their fields are final, so setters are impossible, but referenced objects (like a list) can still change unless you make a defensive copy such as List.copyOf; accessors are generated as name() and can be overridden.

Detailed explanation

Immutability. Every record component becomes a private final field, assigned once in the canonical constructor. You cannot reassign it later, and you cannot write a method that does this.name = ...; it will not compile. That is why there are no setters.

But "final" only fixes the reference. If a component is List<String> items and the caller passes an ArrayList, they can still call items.add(...) on their copy, and anyone calling record.items().add(...) can modify it too. To make the record truly immutable, copy mutable inputs in the compact constructor: items = List.copyOf(items);. List.copyOf returns an unmodifiable list and also rejects nulls. For arrays, clone in the constructor and in the accessor. Dates such as LocalDate and BigDecimal are already immutable.

Accessors. The compiler generates a public method per component, named exactly like it: name(), not getName(). You may declare it explicitly to override it, as long as it has the same signature and returns the same type, for example to return a defensive copy. You may also add any other methods, including a getName() style method for a framework that needs JavaBean getters, though most modern libraries (Jackson, Spring) understand record accessors.

"Setters" the immutable way. Instead of changing a record, return a new one: a wither method like withEmail(String email) that calls the constructor with one value replaced. A Java language preview of derived record creation (with expressions) has been proposed, but wither methods are the standard approach today.

How it works

  1. Constructor assigns final fields once.
  2. Compact constructor can replace mutable inputs with copies.
  3. Accessors return fields; override to return copies if needed.
  4. Changes create new instances via wither methods.

Example

public record Customer(String name, String email, List<String> tags) {
    public Customer {
        tags = List.copyOf(tags);            // defensive, unmodifiable
    }
    public Customer withEmail(String newEmail) {
        return new Customer(name, newEmail, tags);
    }
    public String getName() { return name; } // allowed, extra method
}

var c = new Customer("Asha", "a@x.com", new ArrayList<>(List.of("vip")));
c.tags().add("new");   // UnsupportedOperationException
var c2 = c.withEmail("asha@x.com");

Common mistakes

  • Believing records are deeply immutable by default.
  • Writing this.tags = List.copyOf(tags) in the compact constructor (assign the parameter instead).
  • Overriding an accessor with a different return type.
  • Exposing internal arrays directly.

How to answer in the interview

"Records are shallowly immutable. Fields are final, so you can't reassign them and setters can't exist. But if a component is mutable, like an ArrayList, its contents can still change, so I make a defensive copy in the compact constructor with List.copyOf. Accessors are generated and named after the components, so name() not getName(), and I can override one explicitly, say to return a copy, or add other methods. To 'change' a record I write a wither method like withEmail that returns a new instance with one value replaced."

Likely follow-up questions

  • How would you implement a "wither" method on a record? A method returning new Record(...) with all components copied except the changed one.
  • What does List.copyOf do differently from Collections.unmodifiableList? It copies, so later changes to the original don't show through.
  • Can records have setters via Lombok? No; fields are final.
