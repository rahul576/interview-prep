What is Apache Kafka and what are its core building blocks?

Kafka · concept · levels entry, mid

In one line

Apache Kafka is a distributed event streaming platform built on a partitioned, replicated, append-only commit log. Producers write records to topics, which are split into partitions (ordered logs) stored on brokers and replicated for fault tolerance. Consumers (in consumer groups) read at their own pace using offsets, and data is retained by time or size, not deleted on consumption, so it can be replayed.

Detailed explanation

Core building blocks:

  • Topic: a named stream of records, such as orders.
  • Partition: a topic is split into N partitions. Each is an ordered, immutable, append-only log, where every record gets a sequential offset. Partitions are the unit of parallelism and ordering. Order is guaranteed only within a partition. Records with the same key go to the same partition (by hash of the key), so all events for order-42 stay ordered.
  • Broker: a Kafka server storing partitions on disk. A cluster has many brokers.
  • Replication: each partition has a leader and follower replicas on other brokers (replication factor 3 is common). Producers and consumers talk to the leader (consumers can fetch from followers when configured). Followers that are caught up form the ISR (in-sync replicas). With acks=all and min.insync.replicas=2, an acknowledged write survives a broker failure.
  • Producer: batches, compresses and sends records, and chooses the partition. Idempotent producers (the default in modern clients) prevent duplicates on retry.
  • Consumer and consumer group: consumers in the same group share the partitions. Each partition is read by one consumer in the group, so parallelism is capped at the partition count. Different groups each get all the data independently. Consumers commit their offsets (stored in the internal __consumer_offsets topic).
  • Metadata / controller: modern Kafka uses KRaft (Raft-based controllers built into Kafka). ZooKeeper mode was removed in Kafka 4.0.

Retention, not deletion on read. Unlike traditional queues, reading doesn't remove messages. Records stay until the retention time or size is exceeded (for example 7 days), or forever with log compaction (keeping the latest value per key). So new consumers can replay history, failed consumers can rewind offsets, and many independent systems (search indexing, analytics, notifications) can consume the same stream.

Its performance comes from sequential disk I/O, the OS page cache, batching and zero-copy transfer. That gives very high throughput (millions of messages per second per cluster) with low latency.

The ecosystem includes Kafka Connect (source and sink connectors, like Debezium for CDC), Kafka Streams (stream processing) and Schema Registry (Avro, Protobuf or JSON Schema contracts, provided by Confluent and others).

How it works

  1. A producer sends key=order-42 to topic orders. hash(key) % partitions gives partition 3.
  2. The leader of partition 3 appends it at offset 1057 and followers replicate it. With acks=all, the producer is acknowledged once the ISR has it.
  3. Consumer group billing reads partition 3 from its committed offset, processes, and commits 1058.
  4. Group analytics reads the same records independently.
  5. A broker fails, a follower in the ISR becomes leader, and clients reconnect.
  6. Old segments are deleted after the retention period.

Example

kafka-topics.sh --bootstrap-server localhost:9092 --create \
  --topic orders --partitions 6 --replication-factor 3 \
  --config retention.ms=604800000 --config min.insync.replicas=2

kafka-console-producer.sh --bootstrap-server localhost:9092 --topic orders \
  --property parse.key=true --property key.separator=:
> order-42:{"status":"CREATED"}

kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic orders \
  --group billing --from-beginning
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group billing

Common mistakes

  • Expecting global ordering across partitions.
  • More consumers in a group than partitions (the extra ones sit idle).
  • acks=1 or min.insync.replicas=1 for critical data.
  • Treating Kafka as a queue that deletes messages after reading.
  • Too few partitions at the start, since adding partitions later changes key-to-partition mapping.

How to answer in the interview

"Kafka is a distributed event streaming platform built around a partitioned, replicated, append-only commit log. Producers write records to topics, which are split into partitions. Each partition is an ordered log stored on brokers and replicated to other brokers, with a leader and in-sync replicas for fault tolerance. Records with the same key land in the same partition, which gives per-key ordering. Consumers in a consumer group share partitions and track their position with offsets. Unlike a traditional queue, messages aren't deleted when consumed. They're kept according to retention by time or size, so many consumer groups can read the same data and replay it. Modern Kafka uses KRaft instead of ZooKeeper."

Likely follow-up questions

  • Kafka versus RabbitMQ? Kafka is a durable, replayable log with partition-based scaling. RabbitMQ is a broker with flexible routing and per-message acks, where messages are removed once acknowledged.
  • How is ordering guaranteed? Only within a partition. Use a consistent key and an idempotent producer.
  • What is log compaction? Retaining the latest record per key, useful for changelogs and state topics.
