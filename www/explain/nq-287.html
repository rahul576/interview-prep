What happens after you commit and push code to GitHub?

DevOps & CI/CD · scenario · levels entry

In one line

Pushing to a feature branch and opening a pull request triggers CI via webhook or GitHub Actions (build, tests, scans); results become status checks that, with code review, gate the merge under branch protection; merging to main builds a versioned artifact/image, deploys to dev with smoke tests, and the same image is promoted through higher environments with approvals.

Detailed explanation

  1. Push: git push sends commits to GitHub on a feature branch (direct pushes to main are blocked by branch protection or rulesets).
  2. Pull request: you open a PR. GitHub emits an event; GitHub Actions workflows start directly, or a webhook notifies Jenkins or another CI server.
  3. CI checks: checkout, compile, unit and integration tests, SonarQube analysis, dependency and secret scanning. Each job reports a status check on the PR.
  4. Review: required reviewers (possibly via CODEOWNERS) approve. The merge button is enabled only when required checks pass and approvals exist. Some teams use a merge queue to test the PR combined with the latest main.
  5. Merge to main: a new pipeline builds the release artifact: versioned jar and Docker image tagged with the commit SHA, scanned and pushed to the registry.
  6. Deploy to dev: automatically via Helm, or by updating a GitOps repo that Argo CD syncs; smoke tests verify health.
  7. Promotion: the same image moves to QA, staging and production with approvals or automated gates, followed by monitoring.

How it works

  1. Branch push and PR open.
  2. Event triggers CI and status checks.
  3. Review plus checks gate merge.
  4. Merge builds and publishes the artifact.
  5. Auto-deploy to dev, then gated promotion.

Example

git switch -c feature/ORD-142-refund-endpoint
git commit -am "Add refund endpoint"
git push -u origin feature/ORD-142-refund-endpoint
gh pr create --fill --base main
gh pr checks --watch     # build, tests, sonar, codeql must be green

Common mistakes

  • Saying "it goes to production" without describing gates.
  • Forgetting branch protection and required checks.
  • Rebuilding a different image for production.
  • Not knowing what triggers the pipeline.

How to answer in the interview

"I push to a feature branch and open a pull request. GitHub triggers the CI pipeline, either GitHub Actions directly or a webhook to Jenkins, which builds the code, runs unit and integration tests, SonarQube and security scans. The results show as status checks, and branch protection requires them to pass plus a reviewer's approval before merging. After merge into main, the pipeline builds a versioned jar and Docker image, pushes it to the registry and deploys it automatically to dev with smoke tests. Then the same image is promoted to QA, staging and production with approvals and monitoring."

Likely follow-up questions

  • How do you prevent broken code reaching main? Branch protection, required checks, reviews, merge queue.
  • What is a merge queue? It tests each PR on top of the latest main before merging.
  • What if a webhook fails? Check delivery logs in GitHub and the CI endpoint.
