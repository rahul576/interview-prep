How do hashCode() and equals() work together in hash-based collections?

Collections · concept · levels mid

In one line

In hash-based collections hashCode selects the bucket and equals confirms the exact match; the contract is that equal objects must have equal hash codes (unequal ones may collide), and breaking it causes duplicates and failed lookups, so keys should be immutable.

Detailed explanation

A HashMap or HashSet cannot compare a key with every entry; that would be O(n). Instead it uses hashCode() to jump straight to one bucket, and only then calls equals() on the few entries in that bucket. Since different objects can produce the same hash, a collision, equals is what actually decides identity.

The contract from Object:

  • If a.equals(b) is true, then a.hashCode() == b.hashCode() must hold.
  • If two objects are unequal, their hash codes may still be equal, though a good hash makes that rare.
  • hashCode must be consistent: it must return the same value while the fields used by equals don't change.
  • equals must be reflexive, symmetric, transitive, consistent, and x.equals(null) must be false.

Breaking it has concrete effects. Override equals without hashCode, and two equal objects get different identity hashes, land in different buckets and are never compared: a set keeps duplicates, and map.get(equalKey) returns null. A legal but terrible hashCode returning a constant puts every entry in one bucket; it still works but degrades to a list or, since Java 8, a tree, making lookups slow.

Mutable keys are dangerous: if a field used in hashCode changes after insertion, the entry remains in the old bucket while lookups go to the new one, so it becomes unreachable (a memory leak too). Prefer immutable keys: String, boxed numbers, enums, records with immutable fields.

How it works

  1. put(k, v): hash = spread(k.hashCode()), index = hash & (n - 1).
  2. Scan bucket: same hash and (== or equals) means same key.
  3. get(k): same hash and bucket, same equals check.
  4. Mismatch between equals and hashCode breaks step 2 or 3.

Example

final class Point {
    private final int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }
    @Override public boolean equals(Object o) {
        return o instanceof Point p && p.x == x && p.y == y;
    }
    @Override public int hashCode() { return Objects.hash(x, y); }
}

Map<Point, String> m = new HashMap<>();
m.put(new Point(1, 2), "A");
m.get(new Point(1, 2));            // "A" - works because both are consistent

record PointR(int x, int y) {}     // the same, generated for you

Common mistakes

  • Overriding equals only.
  • Including fields in hashCode that equals ignores (or vice versa).
  • Using mutable objects, such as JPA entities with generated ids, as keys.
  • Assuming equal hash codes imply equal objects.

How to answer in the interview

"Hash-based collections use hashCode first to pick a bucket quickly, and then equals to find the exact entry, because different objects can share a hash code. The contract is that if a equals b, their hash codes must be equal, while unequal objects may collide. If I override equals without hashCode, equal objects land in different buckets, so a set keeps duplicates and map.get returns null. A constant hashCode still works but kills performance. And keys should be immutable, since changing a field used in hashCode after insertion makes the entry unreachable."

Likely follow-up questions

  • Why should HashMap keys be immutable? A changed hash leaves the entry in the wrong bucket, so it can't be found or removed.
  • Is a constant hashCode legal? Yes, but every operation degrades badly.
  • How do records help? They generate consistent equals and hashCode from all components.
