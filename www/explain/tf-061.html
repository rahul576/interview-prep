What changed in the AzureRM provider version 4, and what should you watch out for when upgrading?

Terraform · concept · levels mid, senior

In one line

AzureRM 4.0 made subscription_id mandatory, replaced skip_provider_registration with resource_provider_registrations, removed many properties and resources deprecated in 3.x, changed some defaults, and added provider functions; upgrade by reading the upgrade guide and getting clean plans in lower environments first.

Detailed explanation

AzureRM 4.0 (released in 2024) was a major version, so breaking changes were expected.

Explicit subscription. In 3.x, if you did not set a subscription, the provider used the Azure CLI's current default, so a developer who had switched az account set to another subscription could apply to the wrong place. In 4.x, subscription_id must be set in the provider block or through ARM_SUBSCRIPTION_ID. That is a valuable safety change and a common first error after upgrading.

Resource provider registration. The provider used to register a long list of Azure resource providers automatically, which fails in locked-down subscriptions where the identity lacks registration rights. The skip_provider_registration flag was replaced by resource_provider_registrations, which accepts sets such as core, extended, all, none or legacy, plus resource_providers_to_register for extra ones.

Removals and renames. Properties and resources deprecated during 3.x were removed. Many boolean properties were renamed to a consistent ..._enabled style, for example enable_auto_scaling becoming auto_scaling_enabled in AKS node pools, and some legacy resources were dropped in favour of newer ones. Some default values changed, which can show up as plan diffs.

Provider functions. 4.x added provider-defined functions (Terraform 1.8+), such as provider::azurerm::parse_resource_id and normalise_resource_id.

The upgrade approach: first get to the latest 3.x and eliminate every deprecation warning, read the official 4.0 upgrade guide, bump the constraint, plan in dev, fix code until plans are clean, then promote.

How it works

  1. Upgrade to latest 3.x; fix all deprecation warnings.
  2. Read the 4.0 upgrade guide for resources you use.
  3. Bump the constraint to ~> 4.x; set subscription_id.
  4. Choose resource_provider_registrations for your permissions.
  5. Run plans in lower environments; fix renames and defaults.
  6. Promote once plans show no unexpected changes.

Example

terraform {
  required_providers {
    azurerm = {
      source  = "hashicorp/azurerm"
      version = "~> 4.10"
    }
  }
}

provider "azurerm" {
  features {}
  subscription_id                 = var.subscription_id
  resource_provider_registrations = "none"   # identity cannot register providers
}

output "vnet_rg" {
  value = provider::azurerm::parse_resource_id(azurerm_virtual_network.main.id)["resource_group_name"]
}

Common mistakes

  • Jumping from an old 3.x straight to 4.x without fixing deprecations.
  • Accepting unexpected replacements caused by renamed properties.
  • Not setting subscription_id in CI and failing every pipeline.
  • Upgrading provider and Terraform version in the same change.

How to answer in the interview

"AzureRM 4 brought breaking changes. The provider now requires subscription_id explicitly, via the provider block or ARM_SUBSCRIPTION_ID, instead of silently using the CLI default, which prevents applying to the wrong subscription. Resource provider registration changed: skip_provider_registration became resource_provider_registrations, where you choose a set like core or none, important in locked-down subscriptions. Many deprecated properties were removed or renamed and some defaults changed. It also added provider functions such as parsing resource IDs. I fix deprecation warnings on the latest 3.x first, read the upgrade guide and get clean plans in lower environments."

Likely follow-up questions

  • Why is an explicit subscription good? It removes dependence on whichever CLI context a person happens to have.
  • How do you find breaking usages early? Deprecation warnings in 3.x plans.
  • Do provider functions need a newer Terraform? Yes, Terraform 1.8 or later.
