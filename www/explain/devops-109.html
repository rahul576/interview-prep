When does Helm make things worse than plain manifests or Kustomize?

GitOps & Helm · concept · levels mid, senior

In one line

Helm shines for packaging and distributing reusable charts (especially third-party software) with releases and rollback, but makes things worse when internal charts are over-templated into unreadable logic; for your own services with small environment differences, Kustomize overlays on plain YAML are often clearer, and whatever you use, render and diff the output in CI.

Detailed explanation

Helm combines three things: a template engine (Go templates plus Sprig functions), a package format (charts with versions and dependencies, published to chart repositories or OCI registries) and release management (revisions stored in the cluster, helm rollback). For installing ingress controllers, cert-manager, Prometheus or databases, this is excellent: the vendor maintains the chart and you only set values.

The problems start with internal charts that try to be generic. Every field becomes a value, then a conditional, then a helper in _helpers.tpl. You end up with {{- if and .Values.ingress.enabled (not .Values.global.disableIngress) }}, whitespace-sensitive nindent calls and values files nobody fully understands. Reviewers can't tell what YAML will be produced; a typo silently renders an empty field; and YAML-generating-YAML has no type checking. Charts become a second programming language with poor tooling. Helm's release state can also confuse things when combined with GitOps tools that render charts themselves.

Kustomize takes the opposite approach: no templates, just plain, valid YAML bases plus overlays that patch them per environment (replicas, image tag, resources). It is built into kubectl and easy to read. Its limits: complex parameterisation and distributing reusable packages to others.

Good practice either way: keep charts simple and opinionated, use a shared library chart for common patterns, and in CI run helm template or helm diff upgrade (or Argo CD's diff) so reviewers see the rendered manifests, plus helm lint and schema validation.

How it works

  1. Third-party software → upstream Helm chart with a small values file.
  2. Own services → Kustomize base + overlays, or one simple shared chart.
  3. CI renders final manifests and validates them (kubeconform, policies).
  4. The PR shows the rendered diff; reviewers approve the real output.
  5. GitOps applies the rendered result.

Example

# overlays/prod/kustomization.yaml
resources: [ ../../base ]
images:
  - name: orders
    newName: registry.example.com/orders
    newTag: "1.4.2"
patches:
  - target: { kind: Deployment, name: orders }
    patch: |-
      - op: replace
        path: /spec/replicas
        value: 6
helm template orders ./chart -f values-prod.yaml | kubeconform -strict -
helm diff upgrade orders ./chart -f values-prod.yaml -n orders

Common mistakes

  • Exposing every Kubernetes field as a value "for flexibility".
  • Reviewing values.yaml changes without seeing rendered output.
  • Copy-pasting charts per service instead of a library chart.
  • Forgetting that Helm and Kustomize can be combined (Kustomize can inflate Helm charts).

How to answer in the interview

"Helm is great for packaging and distributing reusable software, especially third-party things like ingress controllers or Prometheus, where you just set values and get versioning and rollback. It gets worse when our own charts are over-templated: every field a value, nested conditionals and helpers, until nobody can tell what will be deployed. For our own services with a few environment differences, Kustomize overlays patching plain YAML are usually clearer. Whichever I use, CI renders the manifests with helm template or helm diff and validates them, so reviewers approve the actual YAML, not just a values change."

Likely follow-up questions

  • How do you test a Helm chart? helm lint, schema validation with values.schema.json, helm template + kubeconform, helm-unittest, and helm test in a test cluster.
  • What is a library chart? A chart of reusable templates that other charts include, not installable itself.
  • Can Kustomize use Helm charts? Yes, via the helmCharts field with --enable-helm.
