How do you build LLM applications that work well for users in many languages, such as English and Indian languages?

LLMOps & RAG · concept · levels mid, senior

In one line

Build multilingual LLM apps by evaluating quality per language with native speakers, using multilingual embeddings for retrieval, handling code-mixing and transliteration (e.g. Hinglish), budgeting for higher token counts in non-Latin scripts, testing safety per language, and using translation pipelines only as a fallback.

Detailed explanation

Model quality is not uniform across languages. Frontier models are strong in English and major European languages, reasonably good in Hindi, Bengali, Tamil or Telugu, and weaker in lower-resource languages. Results on English evals simply do not carry over, so every supported language needs its own evaluation set built or reviewed by native speakers, covering realistic queries and domain vocabulary.

Retrieval needs multilingual embedding models that map semantically similar text in different languages close together, so a question in Hindi can find an English policy document. Alternatives are per-language indexes, or translating documents at ingestion. Keyword search (BM25) needs language-appropriate tokenisation, which matters for hybrid search.

Indian users frequently code-mix: "mera order kab aayega?" is Hindi in Latin script mixed with English. Prompts, tests and intent classifiers must cover transliteration and mixing, and the assistant should reply in the user's language and script unless asked otherwise. A system instruction like "respond in the language the user writes in" plus tests helps.

Tokenisers split many non-Latin scripts into far more tokens than English for the same meaning, so cost, latency and context usage rise; chunk sizes and budgets must be measured per language. Safety filters and guardrails are often trained mostly on English, so harmful content may slip through in other languages and need additional language-specific classifiers. Finally, a translate-to-English-and-back pipeline can rescue weak languages but loses nuance, names and tone, and adds latency and cost.

How it works

  1. Detect the user's language and script per message (allow mixing).
  2. Retrieve with multilingual embeddings or language-specific indexes.
  3. Generate with an instruction to answer in the user's language; keep product names unchanged.
  4. Run language-aware safety and PII checks on input and output.
  5. Track quality, token usage and escalations per language; route weak languages to translation or a stronger model.

Example

lang = detect_language(msg)            # e.g. "hi-Latn" for Hinglish
docs = retriever.search(msg, k=8, embedder="multilingual-e5")   # cross-lingual
answer = llm.generate(
    system="Answer in the same language and script as the user. Keep product names in English.",
    context=docs, user=msg)
assert safety.check(answer, lang=lang).ok
metrics.record(lang=lang, tokens=answer.usage.total, rating=None)

Common mistakes

  • Testing only in English and assuming other languages work.
  • Using an English-only embedding model, so non-English queries retrieve nothing useful.
  • Replying in Devanagari to a user who wrote Hinglish in Latin script.
  • Ignoring higher token costs when budgeting.
  • Assuming English-trained safety filters protect all languages.

How to answer in the interview

"Quality varies a lot by language, so I evaluate each language separately with native speakers and realistic test sets. For retrieval I use multilingual embeddings so a Hindi question can find an English document. Indian users often code-mix, like Hinglish in Latin script, so prompts and tests cover transliteration, and the assistant replies in the user's language and script. I budget for higher token counts in many non-Latin scripts, test safety filters per language and add language-specific classifiers where they're weak. Translating to English and back is a fallback for weak languages, but it loses nuance and adds latency."

Likely follow-up questions

  • Which metrics per language? Satisfaction, resolution or escalation rate, retrieval hit rate, tokens per conversation and safety flag rate.
  • Translate documents at ingestion or query time? Ingestion is cheaper at query time and easier to review; query-time translation is more flexible.
  • How do you build eval sets cheaply? Sample real queries, have native speakers label them, and augment carefully.
