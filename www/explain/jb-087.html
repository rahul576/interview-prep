How do you create custom exceptions?

Exceptions · concept · levels mid, senior

In one line

Create a class that extends Exception (checked) or RuntimeException (unchecked), give it a meaningful name, constructors taking a message and cause (calling super(message, cause)), optional context fields, and map it centrally to responses.

Detailed explanation

Custom exceptions make failures self-describing and actionable. A caller can catch InsufficientBalanceException and show a specific message, and a global handler can map it to HTTP 422 with a stable error code. A generic RuntimeException("error") allows neither.

Checked or unchecked? Extend Exception when callers can and should recover and you want the compiler to force them to think about it (rare in modern application code, more common in libraries for I/O-like conditions). Extend RuntimeException for business rule violations and technical failures in services: it keeps signatures clean, works naturally with lambdas and streams, and Spring's @Transactional rolls back by default only on unchecked exceptions (and Errors), which matches most business failures.

Design guidelines:

  • Name it after the problem, ending in Exception: OrderNotFoundException, PaymentDeclinedException.
  • Provide constructors for (message), (message, cause) and maybe (cause). Always pass the cause when wrapping so the stack trace chain survives.
  • Add context fields that handlers need: an error code enum, the order id, the retryable flag. Never include passwords, tokens or full card numbers.
  • Build a small hierarchy: a base DomainException with subclasses, so handlers can catch broadly or specifically.
  • Don't create one class per error message. Reuse JDK exceptions where they fit: IllegalArgumentException, IllegalStateException, UnsupportedOperationException.
  • For very frequent, expected exceptions, you can skip stack trace capture via the protected 4-argument constructor with writableStackTrace=false, but only when measured.

In Spring, a @RestControllerAdvice maps each type to a status and a consistent body, for example RFC 9457 ProblemDetail.

How it works

  1. Define the exception class with constructors and fields.
  2. Throw it where the rule is violated or when wrapping a lower-level failure.
  3. Let it propagate through service layers.
  4. A central handler catches it, logs at the right level and maps it to a response or message outcome.

Example

public class InsufficientBalanceException extends RuntimeException {
    private final String accountId;
    private final BigDecimal shortfall;

    public InsufficientBalanceException(String accountId, BigDecimal shortfall) {
        super("Insufficient balance in account " + accountId);
        this.accountId = accountId;
        this.shortfall = shortfall;
    }
    public String accountId() { return accountId; }
    public BigDecimal shortfall() { return shortfall; }
}

@RestControllerAdvice
class ErrorHandler {
    @ExceptionHandler(InsufficientBalanceException.class)
    ProblemDetail handle(InsufficientBalanceException e) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.UNPROCESSABLE_ENTITY, e.getMessage());
        pd.setProperty("code", "INSUFFICIENT_BALANCE");
        return pd;
    }
}

Common mistakes

  • Wrapping without passing the cause.
  • Extending Exception everywhere, forcing throws clauses through every layer.
  • Putting sensitive data in messages that reach logs or clients.
  • Exploding into dozens of nearly identical classes.

How to answer in the interview

"I create a class extending Exception for a checked exception or RuntimeException for unchecked; in Spring services most business exceptions are unchecked so they don't pollute every signature, and @Transactional rolls back on them by default. I give it a meaningful name like InsufficientBalanceException, constructors accepting a message and a cause that call super(message, cause), and context fields like an error code or account id, never sensitive data. Then a @RestControllerAdvice maps each custom exception to the right HTTP status and a consistent error body, such as ProblemDetail."

Likely follow-up questions

  • When would you choose a checked custom exception over an unchecked one? When the caller can realistically recover and must be forced to handle it, e.g. in a library API.
  • Does @Transactional roll back on checked exceptions? Not by default; use rollbackFor.
  • Should exceptions be serialisable? Throwable is Serializable; keep fields serialisable or transient.
