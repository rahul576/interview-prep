What are the different stages of the Spring bean lifecycle?

Spring Framework · concept · levels mid

In one line

A singleton bean goes through definition loading (BeanFactoryPostProcessors) → instantiation → dependency injection → Aware callbacks → BeanPostProcessor before-init → init callbacks (@PostConstruct, afterPropertiesSet, initMethod) → BeanPostProcessor after-init (proxies) → in use → destruction (@PreDestroy, destroy(), destroyMethod).

Detailed explanation

Knowing the lifecycle explains a lot of Spring behaviour: why @Transactional doesn't apply inside @PostConstruct, why property placeholders are resolved before beans exist, and where to put startup or cleanup code.

It begins before any bean exists. The container reads bean definitions from component scanning and configuration classes. BeanFactoryPostProcessors can then modify those definitions; ConfigurationClassPostProcessor parses @Configuration classes and PropertySourcesPlaceholderConfigurer resolves ${...} placeholders.

For each singleton, Spring instantiates the bean through its constructor (constructor injection happens here), then populates remaining dependencies via setters or fields. Next, Aware callbacks give the bean container objects: BeanNameAware, BeanClassLoaderAware, BeanFactoryAware, then ApplicationContextAware and EnvironmentAware (the latter invoked by a post-processor).

Then BeanPostProcessor.postProcessBeforeInitialization runs for every bean; CommonAnnotationBeanPostProcessor uses this step to call @PostConstruct. After that come InitializingBean.afterPropertiesSet() and a custom init method (@Bean(initMethod = ...)). Finally postProcessAfterInitialization runs, and this is where auto-proxy creators wrap the bean in AOP proxies for @Transactional, @Async, @Cacheable and security. The proxy, not the raw object, is what other beans get.

The bean is now ready and in use. After all singletons are created, SmartInitializingSingleton callbacks run, then SmartLifecycle beans start and ContextRefreshedEvent/ApplicationReadyEvent fire. On shutdown, beans are destroyed in reverse dependency order: @PreDestroy, DisposableBean.destroy(), then a custom destroy method (Boot infers close/shutdown methods for @Beans).

How it works

  1. Load bean definitions; run BeanFactoryPostProcessors.
  2. Instantiate via constructor.
  3. Populate properties and fields.
  4. Call Aware interfaces.
  5. Before-init post-processing, then @PostConstruct, afterPropertiesSet, init method.
  6. After-init post-processing creates proxies; bean is in use.
  7. On context close: @PreDestroy, destroy(), destroy method.

Example

@Component
class CacheWarmer implements BeanNameAware, InitializingBean, DisposableBean {
    CacheWarmer(ProductRepository repo) { log("1 constructor"); }
    public void setBeanName(String n)   { log("2 aware: " + n); }
    @PostConstruct void postConstruct() { log("3 @PostConstruct"); }
    public void afterPropertiesSet()    { log("4 afterPropertiesSet"); }
    @PreDestroy void preDestroy()       { log("5 @PreDestroy"); }
    public void destroy()               { log("6 destroy"); }
}

Common mistakes

  • Expecting @Transactional to work inside @PostConstruct (the proxy doesn't exist yet and the call is a self-invocation).
  • Doing long-running work in init callbacks, slowing or blocking startup.
  • Assuming prototypes get destroy callbacks.
  • Confusing BeanFactoryPostProcessor (definitions) with BeanPostProcessor (instances).

How to answer in the interview

"First the container loads bean definitions, which BeanFactoryPostProcessors can modify, for example resolving placeholders. Then for each singleton it instantiates the bean, injects dependencies, calls Aware interfaces like BeanNameAware and ApplicationContextAware, runs BeanPostProcessor before-initialisation, then @PostConstruct, afterPropertiesSet and any custom init method, and then after-initialisation, where AOP proxies for @Transactional are created. The bean is then in use. On shutdown it calls @PreDestroy, DisposableBean.destroy and the custom destroy method."

Likely follow-up questions

  • When are @Transactional proxies created? In postProcessAfterInitialization.
  • Where to run code after the app is fully started? ApplicationReadyEvent listener or ApplicationRunner.
  • Order of init callbacks? @PostConstruct, then afterPropertiesSet, then initMethod.
