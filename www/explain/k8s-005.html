What happens step by step when a pod is deleted, and how do you shut an application down gracefully?

Kubernetes · concept · levels entry, mid, senior

In one line

On deletion the pod is marked Terminating; in parallel it is removed from EndpointSlices and the kubelet runs the preStop hook, then sends SIGTERM; after terminationGracePeriodSeconds (default 30 s, counted from the start) remaining processes get SIGKILL. A graceful app stops taking new work, finishes in-flight work and exits.

Detailed explanation

Whether the deletion comes from kubectl delete, a rollout, a scale-down or a drain, the sequence is the same. The API server sets deletionTimestamp and the grace period on the pod. From there, two independent chains run at the same time:

  • Network chain: the EndpointSlice controller removes the pod from the Service's endpoints; kube-proxy on every node, ingress controllers, service mesh proxies and cloud load balancers then stop routing to it. Each picks up the change on its own schedule, often within a second, sometimes several.
  • Kubelet chain: the kubelet on the node sees the deletion, runs each container's preStop hook (exec command, HTTP call or the built-in sleep action), then sends SIGTERM to the container's main process (PID 1). The grace period clock started at deletion and includes the preStop time. When it expires, the runtime sends SIGKILL.

Because the chains are not coordinated, an app that exits immediately on SIGTERM can still receive new requests for a moment, causing errors. Hence the common pattern of a short preStop sleep (5-10 s) so the network catches up before the app begins shutting down.

The app's job on SIGTERM: stop accepting new connections or consuming new messages, let in-flight HTTP requests finish, commit or nack queue messages, close database pools, flush logs and metrics, and exit with code 0. PID 1 must actually receive the signal: shell-form ENTRYPOINT runs /bin/sh -c, which doesn't forward SIGTERM, so use exec form or a tiny init such as tini.

How it works

  1. Delete request → deletionTimestamp set, pod shows Terminating.
  2. Pod removed from EndpointSlices; proxies and LBs update asynchronously.
  3. Kubelet runs preStop hooks.
  4. Kubelet sends SIGTERM to PID 1 of each container.
  5. App drains and exits; otherwise SIGKILL at the end of the grace period.
  6. Pod object removed from the API.

Example

spec:
  terminationGracePeriodSeconds: 60
  containers:
  - name: api
    image: registry.example.com/api:3.2
    command: ["/app/server"]            # exec form, receives SIGTERM directly
    lifecycle:
      preStop:
        sleep: { seconds: 10 }
sig := make(chan os.Signal, 1)
signal.Notify(sig, syscall.SIGTERM)
<-sig
ctx, cancel := context.WithTimeout(context.Background(), 40*time.Second)
defer cancel()
srv.Shutdown(ctx) // stop listening, wait for in-flight requests

Common mistakes

  • Shell-form entrypoints that swallow SIGTERM, so every shutdown waits for SIGKILL.
  • preStop plus drain time longer than the grace period.
  • Exiting instantly on SIGTERM while traffic is still routed.
  • Queue workers that drop messages instead of finishing or returning them.

How to answer in the interview

"When a pod is deleted, the API server marks it Terminating, and two things happen in parallel: it's removed from the Service EndpointSlices, which proxies and load balancers pick up asynchronously, and the kubelet runs the preStop hook and then sends SIGTERM to PID 1. The app has terminationGracePeriodSeconds, 30 by default and including preStop, before SIGKILL. A graceful app fails readiness, stops new work, finishes in-flight requests or messages, closes connections and flushes logs. Because endpoint removal is asynchronous, I add a short preStop sleep so new requests stop arriving before the app stops listening."

Likely follow-up questions

  • Why does a shell-form ENTRYPOINT break SIGTERM handling? sh -c is PID 1 and doesn't forward signals to the child.
  • How long should the grace period be? Longer than preStop plus the longest normal request or message processing time.
  • What about long-running batch work? Checkpoint progress, or make work resumable and idempotent.
