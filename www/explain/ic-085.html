How do you detect configuration drift on servers, not just in cloud resources?

Configuration Management · concept · levels senior

In one line

Detect server drift with scheduled Ansible --check --diff runs, agents that enforce desired state (Puppet, Chef, SSM State Manager), compliance scans (InSpec, OpenSCAP against CIS), file integrity monitoring, and fleet services such as AWS Config with SSM Inventory or Azure Machine Configuration; the strongest defence is immutable servers.

Detailed explanation

Cloud drift is visible to Terraform; drift inside servers is not. During an incident someone edits sshd_config, installs a debugging package, changes a sysctl or adds a cron job. Weeks later the server behaves differently from its siblings, the next playbook run overwrites the fix, or an auditor finds a weakened setting.

Check-mode runs. Running the normal playbooks on a schedule with --check --diff reports every task that would change and shows the file differences, without modifying anything. Results go to a dashboard or ticket. Tasks must support check mode properly (for example command tasks need check_mode handling or changed_when).

Enforcing agents. Puppet and Chef agents, and SSM State Manager associations, re-apply desired state periodically and report what they corrected, which both fixes and records drift. Enforcement is great for baselines but can silently revert emergency changes, so reports must be watched.

Compliance scanning. InSpec profiles or OpenSCAP check servers against CIS benchmarks or internal baselines: SSH settings, password policies, open ports, installed packages.

File integrity monitoring. AIDE, Wazuh or OSSEC hash critical files and alert on change; Linux auditd watches files and records who changed them.

Fleet services. AWS Systems Manager Inventory and AWS Config track installed software and settings; Azure Machine Configuration (formerly Azure Policy guest configuration) audits or enforces OS settings through policy.

Immutable servers, replaced rather than modified, with SSH access restricted or removed (SSM Session Manager with logging instead), remove most drift at its source.

How it works

  1. Nightly AAP job runs site.yml --check --diff against all hosts.
  2. Hosts with changes are reported with diffs to the owning team.
  3. auditd and FIM alert in real time on critical files.
  4. Weekly InSpec CIS scan feeds compliance dashboards.
  5. Drifted hosts are reconciled or replaced.

Example

ansible-playbook site.yml --check --diff --limit prod 2>&1 | tee drift-$(date +%F).log
# /etc/audit/rules.d/sshd.rules: record who writes sshd_config
-w /etc/ssh/sshd_config -p wa -k sshd_config_change

Common mistakes

  • Playbooks that fail or lie in check mode, making reports useless.
  • Enforcing agents reverting incident fixes without anyone noticing.
  • Alerts that go to a shared inbox nobody reads.
  • Allowing unrestricted SSH and sudo, then wondering why servers drift.

How to answer in the interview

"Servers drift too: someone edits a config file, installs a package or changes a kernel setting during an incident. I'd run the playbooks on a schedule in check and diff mode, which reports every difference without changing anything. Agent-based tools like Puppet, Chef or SSM State Manager go further and enforce desired state periodically. Compliance scanners like InSpec or OpenSCAP check against CIS benchmarks, and file integrity monitoring plus auditd alert on changes to critical files and show who made them. AWS Config with SSM Inventory or Azure Machine Configuration give fleet-wide reports. The strongest defence is immutable servers."

Likely follow-up questions

  • How would you alert on someone editing sshd_config by hand? An auditd watch or FIM rule shipped to the SIEM with an alert.
  • Enforce or report? Enforce for security baselines, report for application settings that may need human judgement.
  • How do you reduce manual changes? Session Manager instead of SSH, least-privilege sudo and immutable images.
