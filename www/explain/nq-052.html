What is the difference between orElse(), orElseGet(), and orElseThrow()?

Java 8+ Features · concept · levels entry, mid

In one line

All three return the value when present; when empty, orElse(other) returns a default that is always evaluated eagerly, orElseGet(supplier) computes a default lazily only if empty, and orElseThrow throws NoSuchElementException or your own exception.

Detailed explanation

The difference comes from how Java evaluates arguments. In opt.orElse(createDefaultUser()), Java must evaluate createDefaultUser() before calling orElse, because it is a normal method argument. So the default is computed every time, even when the Optional holds a value and the default is thrown away. For a constant like "Unknown" or Collections.emptyList() that costs nothing. For a database query, a remote call, a heavy object construction or anything with side effects (saving a record, incrementing a counter, sending an email), it wastes work or causes real bugs.

orElseGet(Supplier<? extends T>) takes a lambda, and the lambda is invoked only when the Optional is empty. That makes it the right choice for expensive or side-effecting defaults. The cost is a tiny lambda object, usually negligible.

orElseThrow() with no arguments (Java 10) throws NoSuchElementException("No value present"). It is the preferred replacement for get(), because the name states the intent. orElseThrow(Supplier<? extends X>) throws an exception you build, typically a domain exception such as UserNotFoundException, which a Spring @ControllerAdvice maps to a 404. The supplier is lazy too, so the exception and its message are only built when needed.

Related options: or(Supplier<Optional<T>>) (Java 9) to try another source but stay in Optional, and ifPresentOrElse when you want actions rather than a value.

How it works

  1. Optional has a value: all three return it (but orElse's argument was already computed).
  2. Optional is empty and orElse: return the precomputed default.
  3. Optional is empty and orElseGet: call the supplier now and return its result.
  4. Optional is empty and orElseThrow: build and throw the exception.

Example

// Bug: a default user is INSERTED even when the user exists
User u = userRepo.findByEmail(email)
    .orElse(userRepo.save(new User(email)));   // save() always runs

// Fix: lazy default
User u2 = userRepo.findByEmail(email)
    .orElseGet(() -> userRepo.save(new User(email)));

// Cheap constant: orElse is fine
String name = nickname.orElse("Guest");

// Service layer: domain exception mapped to 404
public Order getOrder(long id) {
    return orderRepo.findById(id)
        .orElseThrow(() -> new OrderNotFoundException(id));
}

// No-arg form instead of get()
Config cfg = loadConfig().orElseThrow();

Common mistakes

  • orElse(repository.load()) or orElse(save(...)) running on every call.
  • orElse(null) used to turn Optional back into nulls everywhere.
  • Using get() instead of orElseThrow().
  • Throwing generic RuntimeException instead of a meaningful domain exception.

How to answer in the interview

"All three return the contained value when it is present and differ only when it is empty. orElse takes the default as a normal argument, so Java evaluates it before the call, even when the Optional has a value; orElse of a repository call or object creation always runs that code. orElseGet takes a Supplier and calls it only when empty, so I use it for expensive or side-effecting defaults. orElseThrow without arguments throws NoSuchElementException and is the clean replacement for get; with a supplier it throws my own exception, like UserNotFoundException, which my exception handler maps to a 404."

Likely follow-up questions

  • Can you show a bug caused by using orElse with a method call? findByEmail(e).orElse(repo.save(new User(e))) inserts a new user even when one exists.
  • Is orElseGet always better? For constants orElse is simpler and equally fast.
  • When to use or()? To fall back to another Optional-returning source, such as cache then database.
