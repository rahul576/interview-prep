Someone accidentally deleted a production namespace. How do you recover, and how do you prevent it from happening again?

Kubernetes · scenario · levels senior, lead

In one line

Contain and communicate, then recreate objects from GitOps or a Velero backup, recover persistent data depending on reclaimPolicy and snapshots, restore secrets and external resources, use audit logs to learn what happened, and prevent repeats with least-privilege RBAC, an admission policy blocking deletion of protected namespaces and restore drills.

Detailed explanation

Deleting a namespace deletes everything in it: Deployments, Services, ConfigMaps, Secrets, PVCs and, through cascading deletion, their pods. Whether the data survives depends on the PersistentVolumes: dynamically provisioned volumes default to reclaimPolicy: Delete, so the cloud disks are deleted too, while Retain leaves them as Released PVs that can be rebound.

Recovery order matters. First declare an incident, freeze further changes and tell stakeholders. Then restore configuration: with GitOps (Argo CD, Flux) the namespace and its objects are recreated by a sync within minutes, which is one of the biggest benefits of GitOps. Without it, restore from a Velero backup, which stores object manifests and optionally volume snapshots. Then restore data: rebind retained PVs to new PVCs (clear the PV's claimRef), restore from volume snapshots, or restore databases from their own backups with point-in-time recovery. Secrets that only existed in the cluster are a common gap; if they came from Vault or a cloud secret manager via External Secrets, they are recreated automatically. External resources created by controllers, such as load balancers, DNS records and certificates, are reprovisioned but may get new addresses.

Afterwards, audit logs show which identity issued the delete and from where, which leads to a blameless review: why was this possible? Prevention: humans get read-only access to production with just-in-time elevation; a Kyverno or ValidatingAdmissionPolicy rule blocks DELETE on namespaces labelled protected=true except from a break-glass group; critical storage classes use Retain; backups are tested in regular restore drills.

How it works

  1. Declare the incident and stop further changes.
  2. Recreate objects: GitOps sync or velero restore.
  3. Recover data: retained PVs, snapshots or database backups.
  4. Restore secrets, certificates and external dependencies.
  5. Verify the application end to end.
  6. Audit log review, then prevention controls and drills.

Example

velero restore create --from-backup daily-20261120 --include-namespaces payments
kubectl get pv | grep Released          # retained disks
kubectl patch pv pvc-8a1f --type=json -p='[{"op":"remove","path":"/spec/claimRef"}]'
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata: { name: protect-namespaces }
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
      - { apiGroups: [""], apiVersions: ["v1"], operations: ["DELETE"], resources: ["namespaces"] }
  validations:
    - expression: "!(has(oldObject.metadata.labels) && oldObject.metadata.labels['protected'] == 'true')"
      message: "Protected namespace; use the break-glass process."

(A ValidatingAdmissionPolicyBinding activates the policy.)

Common mistakes

  • Assuming PV data survives with the default Delete policy.
  • Backups never restored in practice.
  • Secrets only in the cluster, not in a vault.
  • Blaming a person instead of fixing the access model.

How to answer in the interview

"First I declare an incident and freeze changes. Objects come back from the source of truth: with GitOps, Argo CD recreates the namespace in minutes; otherwise I restore from Velero. Data is the hard part: with reclaimPolicy Retain the disks still exist and I rebind them; with Delete I need snapshots or database backups. Secrets not in a vault and external resources like DNS must be restored too. Then audit logs show who did it and how. Prevention is least-privilege RBAC, an admission policy blocking deletion of protected namespaces, Retain on critical storage, and regular restore drills."

Likely follow-up questions

  • How do you test Velero backups? Scheduled restores into a scratch cluster with automated checks on data and app health.
  • Why can't you just undo? Kubernetes has no recycle bin; deleted objects are gone from etcd.
  • Can RBAC deny deletes? RBAC only grants, so remove the delete verb; admission policies add explicit denial.
