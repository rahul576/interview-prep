A PersistentVolumeClaim stays Pending and the pod using it cannot start. How do you troubleshoot it?

Kubernetes · scenario · levels entry, mid, senior

In one line

kubectl describe pvc shows the provisioner events; common causes are a missing or wrong StorageClass (or no default), an unsupported access mode, WaitForFirstConsumer waiting for a pod that itself cannot be scheduled, zone mismatches, CSI driver errors and quota limits.

Detailed explanation

A PVC is Pending until it is bound to a PersistentVolume. With dynamic provisioning, the external provisioner sidecar of a CSI driver watches PVCs for its StorageClass, creates a disk in the cloud and a PV for it. If nothing happens, either no provisioner is responsible or it is failing.

StorageClass problems: storageClassName points to a class that does not exist, or the PVC omits the class and there is no default StorageClass, so nobody provisions. Access mode: asking for ReadWriteMany on a block disk driver (EBS, Azure Disk, Persistent Disk) cannot be satisfied; you need a file-based driver like EFS, Azure Files or Filestore. Driver health: if CSI controller pods crash or lack cloud permissions, provisioning fails; their logs say why.

WaitForFirstConsumer is a binding mode where provisioning is delayed until a pod using the claim is scheduled, so the disk is created in the right zone. Here Pending is normal until then, and the real problem is often that the pod is unschedulable for another reason.

Zones: block disks are zonal. A pre-existing PV or an Immediate-bound disk in zone A cannot attach to a pod that can only run in zone B. Capacity: cloud disk quotas, per-node attach limits, or for static provisioning a PV whose size, access mode, class or labels do not match the claim.

How it works

  1. kubectl describe pvc and read events.
  2. Check kubectl get storageclass for the name and a default.
  3. Check access mode compatibility with the driver.
  4. If WaitForFirstConsumer, describe the pod to see why it is not scheduled.
  5. Check CSI controller logs and cloud permissions or quota.
  6. For static PVs, compare size, class, access mode, selector and zone.

Example

kubectl describe pvc data-postgres-0 | tail -5
#  Normal  WaitForFirstConsumer  waiting for first consumer to be created before binding
kubectl get storageclass
kubectl describe pod postgres-0 | grep -A3 Events
kubectl -n kube-system logs deploy/ebs-csi-controller -c csi-provisioner | tail
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: gp3
  annotations: { storageclass.kubernetes.io/is-default-class: "true" }
provisioner: ebs.csi.aws.com
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
parameters: { type: gp3 }

Common mistakes

  • Treating WaitForFirstConsumer Pending as the bug.
  • Requesting ReadWriteMany from a block storage class.
  • Using Immediate binding in multi-zone clusters.
  • Not checking CSI driver IAM permissions after cluster changes.

How to answer in the interview

"I describe the PVC first, since the provisioner events usually say what's wrong. Common causes are a storage class name that doesn't exist or no default class, an access mode like ReadWriteMany the driver doesn't support, or failing CSI driver pods. If the class uses WaitForFirstConsumer, Pending is normal until a pod is scheduled, so the real issue is often that the pod can't be scheduled. Zone mismatches are frequent with zonal disks. Finally I check cloud quotas and, for static PVs, whether size, class and labels match."

Likely follow-up questions

  • Why does WaitForFirstConsumer help in multi-zone clusters? The disk is created in the zone where the pod is scheduled, avoiding mismatches.
  • How do you resize a PVC? Increase the request if the class allows expansion.
  • What is reclaimPolicy? Whether the disk is deleted or retained when the PVC is deleted.
