What is speculative decoding, and when does it help?

LLMOps & RAG · concept · levels senior, lead

In one line

Speculative decoding lets a cheap draft (small model, n-gram lookup, or Medusa/EAGLE heads) propose several tokens that the large model verifies in one forward pass; with rejection sampling the output distribution is identical to the large model's, giving 2 to 3 times faster decode when acceptance is high, mostly at low batch sizes.

Detailed explanation

Decode is memory-bound: each step loads all weights to produce one token per sequence, leaving compute idle. Verifying several tokens in a single pass costs almost the same as generating one, because the weights are loaded once and the extra tokens use spare compute, much like a small prefill. Speculative decoding exploits that.

A draft proposes k tokens (for example 4). Options: a smaller model from the same family (Llama 1B drafting for Llama 70B, sharing the tokenizer); n-gram / prompt lookup, which copies continuations from the prompt and is great for summarisation, code edits and RAG where output repeats input; Medusa heads, extra prediction heads trained on the target; and EAGLE (EAGLE-2/3), lightweight draft heads that use the target's hidden states and achieve high acceptance rates.

The target model runs one forward pass over the prompt plus the k drafted tokens, getting its own probabilities at every position. Tokens are accepted left to right: under greedy decoding, while they match the target's argmax; under sampling, via a rejection sampling rule that accepts token x with probability min(1, p_target/p_draft) and, on rejection, resamples from a corrected distribution. This is mathematically guaranteed to produce the same distribution as the target alone, so quality does not change.

Speed-up depends on the acceptance rate and draft cost. Predictable text (code, JSON, extraction, templated replies) accepts many tokens; creative high-temperature text accepts fewer. Under heavy batching, the GPU is already compute-saturated, so verifying extra tokens is no longer free and gains shrink or vanish; the draft also consumes memory and compute. It is most valuable for latency-sensitive, low-to-moderate concurrency deployments.

How it works

  1. Draft generates k candidate tokens cheaply.
  2. Target scores prompt plus k candidates in one pass.
  3. Accept tokens until the first rejection (rejection sampling).
  4. Add the target's correction or bonus token.
  5. Repeat; monitor acceptance rate and tune k.

Example

vllm serve meta-llama/Llama-3.1-70B-Instruct --tensor-parallel-size 4 \
  --speculative-config '{"method":"ngram","num_speculative_tokens":4,"prompt_lookup_max":4}'
# or a draft model / EAGLE head:
#  --speculative-config '{"model":"<eagle-or-draft-model>","num_speculative_tokens":3}'

Common mistakes

  • Believing speculative decoding lowers quality; with correct verification it does not.
  • Using a draft with a different tokenizer.
  • Enabling it on a fully batched throughput deployment and seeing slowdowns.
  • Not monitoring acceptance rate.

How to answer in the interview

"Decode is slow because the big model makes one token per pass while mostly waiting on memory. Speculative decoding has a cheap draft, a small model, n-gram lookup or EAGLE-style heads, propose several tokens, and the big model verifies all of them in one forward pass, which costs about the same as one token. Tokens are accepted up to the first disagreement using rejection sampling, which keeps the output distribution exactly the same as the big model. When the draft is often right, you get two to three times faster decode, especially for code and structured output at low batch sizes. Under heavy batching the benefit shrinks."

Likely follow-up questions

  • Why less help when fully batched? Compute is already used; verification is no longer free.
  • What decides speed-up? Acceptance rate, draft cost and number of speculative tokens.
  • Best draft for RAG? Prompt lookup, since answers often copy from context.
