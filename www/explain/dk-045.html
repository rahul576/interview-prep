How do you run Java applications well in containers?

Docker · concept · levels mid

In one line

Modern JVMs are container-aware, so size the heap with -XX:MaxRAMPercentage (about 70-75%) to leave room for native memory, use a JRE or jlink runtime and layered jars, handle SIGTERM for graceful shutdown, and improve start-up with CDS/AppCDS, CRaC or GraalVM native image.

Detailed explanation

Older JVMs read the host's memory and CPU count, so a container with a 1 GB limit on a 64 GB host might default to a 16 GB heap and get OOM-killed. Since Java 10 (backported to 8u191) the JVM reads cgroup limits (cgroup v2 support arrived in later updates such as JDK 15 and 11.0.16), so defaults now follow the container. The default heap is only 25% of the limit, though, which wastes memory; instead set -XX:MaxRAMPercentage=70 to 75. Avoid making the heap equal to the limit: the JVM also uses metaspace, thread stacks, code cache, GC structures and direct buffers, and the container is killed when the whole process exceeds the limit. CPU limits also affect GC thread counts and availableProcessors(); very low CPU limits slow GC and start-up.

For the image, use a JRE base (eclipse-temurin:21-jre) or build a minimal runtime with jlink containing only the modules you need. Spring Boot layered jars (java -Djarmode=tools ... extract --layers) split dependencies, Spring Boot loader, snapshot dependencies and application classes into separate Docker layers, so a code change only rebuilds a few hundred kilobytes. Run as non-root.

The JVM must be PID 1 (exec form) so it receives SIGTERM, and the framework must drain gracefully, for example server.shutdown=graceful in Spring Boot. For faster start-up, important for autoscaling and serverless, use Class Data Sharing / AppCDS archives, CRaC checkpoint and restore where supported, or GraalVM native images, which start in milliseconds but need build-time configuration for reflection.

How it works

  1. Container starts with a memory limit (e.g. 1 GiB).
  2. The JVM reads the cgroup limit and applies MaxRAMPercentage to the heap.
  3. Remaining memory covers metaspace, threads and native buffers.
  4. On SIGTERM, shutdown hooks drain requests and close resources.
  5. Metrics show heap and native memory against the limit.

Example

FROM eclipse-temurin:21-jdk AS build
WORKDIR /src
COPY . .
RUN ./mvnw -q package -DskipTests && \
    java -Djarmode=tools -jar target/app.jar extract --layers --launcher --destination /layers

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /layers/dependencies/ ./
COPY --from=build /layers/spring-boot-loader/ ./
COPY --from=build /layers/snapshot-dependencies/ ./
COPY --from=build /layers/application/ ./
USER 10001
ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75 -XX:+ExitOnOutOfMemoryError"
ENTRYPOINT ["java", "org.springframework.boot.loader.launch.JarLauncher"]

Common mistakes

  • -Xmx equal to the container limit.
  • Old JDK 8 builds that ignore cgroups.
  • Fat jars as a single layer, so every build re-pushes all dependencies.
  • Shell-form start commands that block SIGTERM.

How to answer in the interview

"Modern JVMs since Java 10 and recent Java 8 updates read the cgroup limits instead of host values. I size the heap relative to the limit with MaxRAMPercentage, around 70 to 75 percent, leaving headroom for metaspace, threads and native memory so the container isn't OOM killed. The image uses a JRE or a jlink runtime, and Spring Boot layered jars put dependencies in a separate layer that rarely changes. The JVM runs as PID 1 and handles SIGTERM with graceful shutdown. For faster startup I'd look at CDS, CRaC or GraalVM native images, especially for autoscaling."

Likely follow-up questions

  • Why OOM-killed with heap below Xmx? Native memory (threads, metaspace, direct buffers) pushes the process over the limit.
  • How do you inspect native memory? -XX:NativeMemoryTracking=summary and jcmd VM.native_memory.
  • Native image trade-offs? Fast start, lower memory, but longer builds and reflection configuration.
