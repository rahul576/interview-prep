How does LLM inference work, and why is the decode phase usually memory-bound?

LLMOps & RAG · concept · levels mid, senior

In one line

LLM inference has a compute-bound prefill that processes the whole prompt in parallel and sets time to first token, followed by a memory-bound decode that generates one token per forward pass, each pass reading all weights and the KV cache from GPU memory.

Detailed explanation

Serving a request happens in two phases with very different hardware profiles.

Prefill. All prompt tokens are known, so the model processes them in parallel as large matrix-matrix multiplications. For each token and layer it computes attention keys and values and stores them in the KV cache. This keeps the GPU's tensor cores busy: prefill is compute-bound, and its duration (plus queueing) is the time to first token (TTFT).

Decode. Output is autoregressive: token n+1 depends on token n, so the model runs one forward pass per new token. Each pass processes a single token per sequence, which is a matrix-vector multiplication. Yet it must still stream every weight (around 140 GB for a 70B model in BF16) plus that sequence's KV cache from HBM into the compute units. The arithmetic intensity, the FLOPs per byte loaded, is tiny, so the GPU waits on memory bandwidth rather than compute. A rough upper bound for a single stream is bandwidth divided by model size: an H100 with about 3.35 TB/s serving a 14 GB 7B model cannot exceed roughly 240 tokens per second for one sequence, whatever its TFLOPS.

That is why a 500-token answer needs 500 sequential passes, and why serving one request at a time wastes most of the GPU. Batching fixes it: the weights are read once per step and reused for every sequence in the batch, turning matrix-vector into matrix-matrix work. Throughput rises almost linearly until compute or KV cache memory becomes the limit, which is why engines use continuous batching.

How it works

  1. Tokenise the prompt.
  2. Prefill: run all prompt tokens in parallel, fill the KV cache, emit the first token.
  3. Decode step: feed the last token, attend to cached keys and values, sample the next token.
  4. Append its keys and values to the cache.
  5. Repeat until a stop token or max tokens; stream tokens as they are produced.

Example

Model: 8B params, BF16 → ~16 GB weights; GPU bandwidth ~3.3 TB/s
Single-stream decode ceiling ≈ 3300 / 16 ≈ 200 tokens/s (real: lower)
Batch of 32: weights read once per step → ~32x tokens per step, close to the same step time
Prompt 4,000 tokens → prefill ~ tens to hundreds of ms (compute-bound) → TTFT

Common mistakes

  • Assuming more TFLOPS always means faster generation.
  • Measuring only total latency and ignoring TTFT versus per-token speed.
  • Serving with batch size 1 and concluding GPUs are too expensive.
  • Forgetting that long prompts make TTFT grow.

How to answer in the interview

"Inference has two phases. Prefill processes the whole prompt in parallel, computing keys and values for every token; it is compute-heavy, efficient on GPUs, and it determines time to first token. Then decode generates one token at a time, and each step needs a full forward pass that reads all the weights and the KV cache from GPU memory but does very little maths per byte. So decode is limited by memory bandwidth, not compute. That is why serving engines batch many requests together: one read of the weights then produces a token for every sequence in the batch."

Likely follow-up questions

  • How does batching change cost per token? Weight reads are shared, so cost per token falls sharply until compute or memory limits.
  • What is chunked prefill? Splitting long prefills into pieces interleaved with decode steps to avoid stalls.
  • Why does quantisation speed up decode? Fewer bytes per weight means less memory traffic per step.
