What is the difference between singleton and prototype scopes?

Spring Framework · concept · levels mid

In one line

A singleton has one shared instance whose full lifecycle, including destruction, Spring manages; a prototype gets a new instance per lookup or injection, and Spring does not call its destroy callbacks; a prototype injected into a singleton is created only once, so use ObjectProvider, @Lookup or a scoped proxy for fresh instances.

Detailed explanation

Singleton beans are created once per context (eagerly at startup by default), cached, shared by every consumer, and destroyed when the context closes, so @PreDestroy and DisposableBean.destroy() run. They suit stateless services, repositories, clients and configuration.

Prototype beans are created every time they are requested from the container: each getBean() call, each ObjectProvider.getObject(), and each injection point in a new consumer. Spring instantiates them, injects dependencies and runs initialisation callbacks such as @PostConstruct, then hands them over and forgets them. It does not track them, so destroy callbacks are never called; the client is responsible for releasing resources such as files or connections. Prototypes are created lazily, on demand.

The common trap: when a singleton has a prototype dependency, injection happens once, when the singleton is created. The singleton keeps that single prototype instance for its whole life, which defeats the purpose and may introduce shared mutable state. Ways to obtain a fresh instance on each use:

  • inject ObjectProvider<MyPrototype> and call getObject() (the modern, recommended option);
  • declare an abstract or stub @Lookup method that Spring overrides with CGLIB;
  • use a scoped proxy (proxyMode = TARGET_CLASS), though for prototypes this creates a new target on every method call, which is rarely what you want;
  • jakarta.inject.Provider<T>.

Prototype use cases are objects with per-use state: builders, stateful parsers, command objects, or non-thread-safe third-party objects.

How it works

  1. Singleton: created at refresh, cached, returned for every request.
  2. Prototype: new object created and initialised for every request.
  3. Singleton depending on prototype: one prototype created at singleton construction.
  4. ObjectProvider/@Lookup: asks the container at call time, creating a new prototype each time.
  5. Shutdown: singletons destroyed; prototypes left to the garbage collector.

Example

@Component
@Scope("prototype")
class CsvParser {                     // not thread-safe, holds state
    private final List<String> errors = new ArrayList<>();
}

@Service
class ImportService {
    private final ObjectProvider<CsvParser> parsers;
    ImportService(ObjectProvider<CsvParser> parsers) { this.parsers = parsers; }

    Result importFile(Path p) {
        CsvParser parser = parsers.getObject();   // new instance per import
        return parser.parse(p);
    }
}

@Component
abstract class LegacyImporter {
    @Lookup
    protected abstract CsvParser newParser();      // overridden by Spring
}

Common mistakes

  • Expecting a prototype field in a singleton to change between calls.
  • Opening resources in a prototype and never closing them.
  • Using prototype scope as a cure for thread-safety issues in services.
  • Using a scoped proxy for prototypes, creating a new instance on every method call.

How to answer in the interview

"A singleton has one instance per context, created at startup and shared, and Spring manages its whole lifecycle including destruction. A prototype gets a new instance each time it's requested; Spring creates and initialises it, but then hands it over and never calls destroy methods, so the client cleans up. The common trap is injecting a prototype into a singleton: it's created only once at injection time. To get a fresh one each time I inject ObjectProvider and call getObject, or use a Lookup method."

Likely follow-up questions

  • A use case for prototype? Stateful, non-thread-safe helpers like parsers or builders.
  • Why no destroy callbacks? The container doesn't keep references to prototypes.
  • ObjectProvider vs Provider? Same idea; ObjectProvider adds getIfAvailable, orderedStream and more.
