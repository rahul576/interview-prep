What is dependency injection and inversion of control in Spring? Which injection style do you prefer?

Spring Framework · concept · levels entry, mid

In one line

With inversion of control, objects do not create their dependencies; the Spring IoC container (ApplicationContext) creates beans, manages their lifecycle and injects dependencies. I prefer constructor injection because it makes dependencies explicit, final and testable.

Detailed explanation

Without IoC, a class does new SmtpMailSender() itself and is tied to that implementation forever. Inversion of control reverses this: control over creating and wiring objects moves to a container. Dependency injection is the technique: the container hands a class what it needs, typically as interfaces, so the class depends on abstractions and implementations can be swapped (a fake in tests, a different provider in production).

In Spring, the ApplicationContext reads bean definitions from @Component and its stereotypes (@Service, @Repository, @Controller) found by component scanning, and from @Bean methods in @Configuration classes. It resolves dependencies by type (with @Qualifier or @Primary for ambiguity), creates singletons at startup and wires them together.

Spring supports three injection styles. Constructor injection: dependencies as constructor parameters; since Spring 4.3 a single constructor needs no @Autowired. Setter injection: for optional dependencies that can change. Field injection: @Autowired on a field, which is short but hides dependencies, prevents final fields, and needs reflection or a Spring context to test.

I prefer constructor injection: the object is never half-initialised, fields can be final and therefore safely shared between threads, a constructor with eight parameters visibly signals too many responsibilities, and unit tests just call new OrderService(mockRepo, mockMail). It also makes circular dependencies fail fast at startup instead of being silently patched. With Lombok, @RequiredArgsConstructor removes the boilerplate.

How it works

  1. Spring scans packages and reads configuration classes into bean definitions.
  2. It sorts beans by their dependencies.
  3. It instantiates each bean, passing resolved dependencies to the constructor.
  4. Post-processors apply extras like @Value, proxies for @Transactional.
  5. The fully wired beans are available; the context closes them on shutdown.

Example

public interface Notifier { void send(String to, String msg); }

@Component
class EmailNotifier implements Notifier { public void send(String to, String msg) { /* SMTP */ } }

@Service
class OrderService {
    private final OrderRepository repo;
    private final Notifier notifier;

    OrderService(OrderRepository repo, Notifier notifier) {   // no @Autowired needed
        this.repo = repo;
        this.notifier = notifier;
    }
}

// Unit test without Spring
OrderService service = new OrderService(mock(OrderRepository.class), mock(Notifier.class));

Common mistakes

  • Field injection everywhere, making classes hard to test.
  • Calling new on a Spring-managed class, so nothing is injected or proxied.
  • Depending on concrete classes instead of interfaces where alternatives exist.
  • Huge constructors instead of splitting the class.

How to answer in the interview

"Inversion of control means my classes don't create their dependencies; the Spring container, the ApplicationContext, creates the beans, manages their lifecycle and injects what they need. Beans come from @Component and its stereotypes via component scanning, or @Bean methods in configuration classes. Spring supports constructor, setter and field injection. I prefer constructor injection: dependencies are explicit, fields can be final, the object is never half-built, and unit tests just pass mocks into the constructor. The overall benefit is loose coupling and testability, because classes depend on interfaces."

Likely follow-up questions

  • How does Spring resolve a circular dependency? With constructor injection it can't and fails; Boot 2.6+ forbids cycles by default. It signals a design problem.
  • What if two beans implement the interface? Use @Primary, @Qualifier, or inject a List.
  • IoC vs DI? IoC is the principle; DI is one way to implement it (service locator is another).
