How do Ansible variables work, and where can they be defined?

Configuration Management · concept · levels entry

In one line

Ansible variables can live in the inventory, group_vars/host_vars, play vars/vars_files, role defaults and vars, facts, registered results and extra vars (-e), which have the highest precedence; you use them with Jinja2 {{ var }}.

Detailed explanation

Ansible merges variables from many sources, each with a place in a long precedence order (over 20 levels). The ones that matter in practice, roughly from lowest to highest:

  • Role defaults (roles/x/defaults/main.yml): the lowest precedence, explicitly designed to be overridden.
  • Inventory variables, and the group_vars and host_vars directories next to the inventory or playbook: group_vars/all, then specific groups, then host_vars for one host. This is the usual home for environment- and group-specific values.
  • Facts gathered from hosts, such as ansible_facts['distribution'].
  • Play vars, vars_files and vars_prompt.
  • Role vars (roles/x/vars/main.yml): high precedence, meant for internal constants.
  • Registered variables (register:) and set_fact.
  • Task and block vars, include_vars, role parameters.
  • Extra vars (-e / --extra-vars): always win.

Variables are referenced with Jinja2 syntax: "{{ app_port }}", with filters like {{ users | length }} or {{ timeout | default(30) }}. When a YAML value starts with {{, it must be quoted.

Because the precedence list is long, teams keep a simple convention: configurable values with defaults go into role defaults, environment overrides go into group_vars, host exceptions into host_vars, and -e is reserved for one-off runs or pipeline parameters. ansible-inventory --host web1 --vars or the debug module show what a host actually gets.

How it works

  1. Ansible loads inventory, group_vars and host_vars.
  2. It gathers facts at play start.
  3. It loads play and role variables.
  4. During execution, register and set_fact add host variables.
  5. For each lookup, the highest-precedence definition wins.

Example

inventory/prod/
  hosts.ini
  group_vars/all.yml       # ntp_server: ntp.acme.local
  group_vars/web.yml       # app_port: 8080
  host_vars/web03.yml      # app_port: 9090
roles/app/defaults/main.yml  # app_port: 80, app_workers: 4
- name: Configure app
  hosts: web
  tasks:
    - name: Show resolved port
      ansible.builtin.debug:
        msg: "{{ inventory_hostname }} listens on {{ app_port }} with {{ app_workers }} workers"
    - name: Check service
      ansible.builtin.command: systemctl is-active app
      register: app_state
      changed_when: false
ansible-playbook site.yml -i inventory/prod -e "app_workers=8"

Common mistakes

  • Putting overridable settings in role vars, so group_vars cannot override them.
  • Unquoted {{ var }} at the start of a YAML value.
  • Defining the same variable in many places and losing track of which wins.
  • Overusing -e so runs are not reproducible.

How to answer in the interview

"Variables can come from many places: the inventory and the group_vars and host_vars directories, which is where I keep environment and group specific values; play vars and vars_files; role defaults, which are meant to be overridden, and role vars for internal constants; and extra vars with -e, which always have the highest precedence. Ansible also gathers facts, and tasks can save results with register. I reference them with Jinja2, like {{ app_port }}. Since the precedence rules are long, I keep a convention: defaults in roles, overrides in group_vars, exceptions in host_vars, and -e only for pipeline parameters."

Likely follow-up questions

  • Why prefer role defaults over role vars for configurable values? Defaults have the lowest precedence, so inventory can override them; role vars override inventory.
  • How do you see a host's resolved variables? ansible-inventory --host <host> or debug: var=hostvars[inventory_hostname].
  • What is hostvars? A dictionary to read another host's variables and facts.
