How does Ansible work? Explain inventory, playbooks, modules and idempotency.

Configuration Management · concept · levels entry

In one line

Ansible is agentless: from a control node it connects over SSH (or WinRM) to hosts listed in an inventory, runs playbooks (YAML plays mapping host groups to tasks), and each task calls a module (apt, copy, template, service) that is idempotent: it checks current state and only changes what differs, so a second run reports no changes.

Detailed explanation

Agentless architecture: you install Ansible only on a control node (a laptop, CI runner or AWX). Managed nodes need SSH access and Python; no daemon runs there. For each task, Ansible copies a small module program to the host, executes it, reads its JSON result and removes it. Windows hosts are managed over WinRM or SSH with PowerShell modules.

Inventory lists hosts and groups, statically in INI or YAML, or dynamically from cloud APIs (an AWS EC2 or Azure plugin that groups hosts by tags). Groups like webservers and databases can have variables in group_vars, and individual hosts in host_vars.

A playbook is a YAML file with one or more plays. Each play says which hosts to target (hosts: webservers), whether to use privilege escalation (become: true) and which tasks to run in order. Tasks can use variables, loops, conditionals (when) and notify handlers, which run once at the end when something changed, for example restarting Nginx after its config changes.

Modules do the actual work: apt/dnf/package install software, copy places files, template renders Jinja2 templates with variables, service/systemd manage services, user manages accounts, and thousands more in collections.

Idempotency is the core concept: modules describe desired state ("nginx present", "service started") rather than actions. The module checks first and acts only if needed, reporting changed or ok. So you can run a playbook repeatedly and safely; the second run shows changed=0. Raw shell and command tasks break this unless guarded. Roles package tasks, templates, handlers and defaults for reuse.

How it works

  1. Control node reads inventory, variables and the playbook.
  2. Connects to target hosts over SSH in parallel (default 5 forks).
  3. Gathers facts (OS, IPs) unless disabled.
  4. Runs each task's module on every host, in order.
  5. Runs notified handlers; prints a recap (ok, changed, failed).

Example

# inventory.ini
[webservers]
web1.example.com
web2.example.com
[databases]
db1.example.com
# site.yml
- hosts: webservers
  become: true
  tasks:
    - name: Install nginx
      ansible.builtin.apt: { name: nginx, state: present, update_cache: true }
    - name: Deploy site config
      ansible.builtin.template: { src: site.conf.j2, dest: /etc/nginx/conf.d/site.conf }
      notify: Restart nginx
  handlers:
    - name: Restart nginx
      ansible.builtin.service: { name: nginx, state: restarted }
ansible-playbook -i inventory.ini site.yml
ansible webservers -i inventory.ini -m ping

Common mistakes

  • Using shell for everything and losing idempotency.
  • Restarting services in tasks instead of handlers.
  • Hard-coding passwords in playbooks instead of Ansible Vault.
  • Forgetting become: true and getting permission errors.

How to answer in the interview

"Ansible is an agentless configuration management tool: it connects to servers over SSH, or WinRM for Windows, so nothing needs installing on them except Python. The inventory lists hosts and groups, like webservers and databases, with variables per group. A playbook is YAML with plays that map groups to tasks, and each task calls a module, apt to install packages, copy or template for files, service to manage services. Modules are idempotent: they check the current state and only change what differs, so running a playbook twice gives the same result and the second run reports no changes. Handlers restart services only when something changed, and roles organise reusable tasks."

Likely follow-up questions

  • How do you keep passwords out of playbooks? Ansible Vault encryption, or lookups from HashiCorp Vault or a cloud secret manager.
  • What are facts? Host information gathered at play start (OS, memory, IPs) usable as variables.
  • Ad-hoc commands? One-off module runs like ansible all -m ping without a playbook.
