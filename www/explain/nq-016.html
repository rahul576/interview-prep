How are virtual threads created, scheduled, and managed by the JVM and operating system?

Modern Java (11-21) · concept · levels senior, lead

In one line

Virtual threads are created with Thread.ofVirtual(), Thread.startVirtualThread() or Executors.newVirtualThreadPerTaskExecutor(); the JVM (not the OS) schedules them on a work-stealing ForkJoinPool of carrier threads, storing each one's stack as a continuation on the heap that is mounted and unmounted.

Detailed explanation

Creation. A virtual thread is a java.lang.Thread, created through the builder API: Thread.ofVirtual().name("worker-", 0).start(task), Thread.ofVirtual().unstarted(task), or a factory Thread.ofVirtual().factory() for frameworks. Thread.startVirtualThread(task) is a shortcut, and Executors.newVirtualThreadPerTaskExecutor() creates one per submitted task. Creating one allocates a small heap object; no system call is made.

Scheduling. The OS only knows about carrier threads, ordinary platform threads in a dedicated ForkJoinPool running in FIFO mode with work stealing. Its parallelism defaults to the number of available processors (tunable via jdk.virtualThreadScheduler.parallelism and maxPoolSize). The JVM decides which virtual thread runs on which carrier. Scheduling is cooperative at blocking points, not time-sliced: a virtual thread runs until it blocks or finishes.

Mount/unmount. Internally a virtual thread is a continuation: a piece of code plus its stack that can be suspended and resumed. When it runs, it is mounted: its frames are copied onto the carrier's stack. When it reaches a blocking operation the JDK has adapted (socket reads/writes via NIO, Thread.sleep, LockSupport.park used by java.util.concurrent locks and queues, and, since Java 24, synchronized/Object.wait), the JDK registers interest (e.g. with the OS poller for sockets), yields the continuation, and its frames are moved to heap stack chunks. The carrier is free immediately. When the socket becomes readable, the poller unparks the virtual thread, which is submitted back to the scheduler and remounted, possibly on a different carrier.

Some operations cannot unmount: blocking file I/O on most platforms and native/JNI calls. For file I/O the JDK compensates by temporarily adding a carrier to the pool. These are cases of pinning or capture.

How it works

  1. Thread.ofVirtual().start(task) creates the continuation and submits it.
  2. A carrier picks it up and mounts it.
  3. At a blocking call the continuation yields; frames go to heap.
  4. Event completion unparks it; it is resubmitted.
  5. Another carrier mounts and resumes it.
  6. On completion, it becomes garbage.

Example

Thread t1 = Thread.ofVirtual().name("vt-", 0).start(() -> fetch("a"));
Thread t2 = Thread.startVirtualThread(() -> fetch("b"));
ThreadFactory f = Thread.ofVirtual().name("job-", 0).factory();

try (ExecutorService ex = Executors.newVirtualThreadPerTaskExecutor()) {
    ex.submit(() -> System.out.println(Thread.currentThread()));
}
// prints e.g. VirtualThread[#31]/runnable@ForkJoinPool-1-worker-1
java -Djdk.virtualThreadScheduler.parallelism=8 -jar app.jar

Common mistakes

  • Believing the OS schedules virtual threads.
  • Assuming time slicing; a CPU loop can monopolise a carrier.
  • Expecting file I/O or JNI calls to unmount.
  • Setting priority or daemon status (virtual threads are always daemon; priority is ignored).

How to answer in the interview

"I create them with Thread.ofVirtual().start, Thread.startVirtualThread, or more commonly Executors.newVirtualThreadPerTaskExecutor. The OS knows nothing about them; it only schedules the carrier platform threads. The JVM has its own scheduler, a work-stealing ForkJoinPool with by default one carrier per core. Each virtual thread is a continuation: when it runs it's mounted on a carrier; when it blocks on something like socket I/O, sleep or a j.u.c. lock, its frames are saved to the heap and it's unmounted, freeing the carrier. When the I/O is ready it's rescheduled, possibly on another carrier. File I/O and native calls can't unmount, so the JDK compensates or the carrier is pinned."

Likely follow-up questions

  • What happens to a virtual thread blocked in a file read? It pins its carrier; the JDK may temporarily add a carrier to keep parallelism.
  • Is scheduling preemptive? No, it switches at blocking points only.
  • Can you supply a custom scheduler? Not via a public API in current releases.
