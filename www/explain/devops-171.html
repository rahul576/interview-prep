How do you design CloudWatch monitoring and alarms for an AWS workload?

Cloud (AWS) · concept · levels mid, senior

In one line

Combine metrics (AWS and custom/EMF), logs with retention and Logs Insights, alarms on user-facing symptoms routed via SNS to on-call, composite alarms and anomaly detection to cut noise, plus dashboards and X-Ray/OpenTelemetry tracing.

Detailed explanation

Good monitoring answers "are users hurting?" first and "why?" second. So I alarm on symptoms and use everything else for diagnosis.

Metrics: AWS services publish metrics automatically (ALB HTTPCode_Target_5XX_Count, TargetResponseTime, SQS ApproximateAgeOfOldestMessage, RDS CPU and connections). Application and business signals (orders per minute, payment failures) are published as custom metrics, most efficiently via the embedded metric format, structured log lines that CloudWatch turns into metrics. I watch for high-cardinality dimensions, which get expensive.

Logs: structured JSON logs to log groups, with retention set (the default is never expire), searched with Logs Insights. Metric filters can turn log patterns into metrics.

Alarms: on SLO-style signals: 5xx error rate as a metric-math percentage, p99 latency, queue age, failed health checks. Alarms fire to SNS topics that fan out to PagerDuty/Opsgenie for paging or to chat for warnings. I set evaluation periods ("3 of 5 datapoints") and missing-data handling deliberately. Composite alarms combine conditions, for example page only if error rate AND latency are high, or suppress child alarms during deployments. Anomaly detection builds a band from historical patterns, useful for traffic with daily cycles where a static threshold fails.

Dashboards per service show the golden signals, and tracing with X-Ray or the AWS Distro for OpenTelemetry shows where latency comes from across services. Application Signals and Synthetics canaries add service-level and outside-in views.

How it works

  1. Define SLIs per service: availability, latency, freshness.
  2. Instrument: built-in metrics + EMF custom metrics + structured logs + traces.
  3. Create alarms on SLIs; use percentiles and metric math.
  4. Route via SNS: critical → pager, warning → chat.
  5. Composite alarms and anomaly bands to reduce noise.
  6. Review alerts after incidents; delete ones nobody acts on.

Example

aws cloudwatch put-metric-alarm --alarm-name api-p99-latency \
  --namespace AWS/ApplicationELB --metric-name TargetResponseTime \
  --dimensions Name=LoadBalancer,Value=app/prod-api/50dc6c495c0c9188 \
  --extended-statistic p99 --period 60 --evaluation-periods 5 \
  --datapoints-to-alarm 3 --threshold 1.5 \
  --comparison-operator GreaterThanThreshold \
  --treat-missing-data notBreaching \
  --alarm-actions arn:aws:sns:ap-south-1:123456789012:oncall-critical

Common mistakes

  • Alarming on averages, which hide the slow tail.
  • Paging on causes like CPU at 80% instead of user impact.
  • Log groups with infinite retention and no cost review.
  • No runbook link in the alarm description.

How to answer in the interview

"I start from SLIs: error rate, latency percentiles and things like queue age. AWS metrics cover the infrastructure, and I add custom application and business metrics through the embedded metric format. Logs are structured, have retention set and are queried with Logs Insights. Alarms on those SLIs go to SNS, which routes critical ones to PagerDuty and warnings to chat. Composite alarms reduce noise by combining conditions, anomaly detection handles daily traffic patterns, and dashboards plus X-Ray or OpenTelemetry tracing help diagnose. Every page should be actionable and have a runbook."

Likely follow-up questions

  • Why p99 rather than average? Averages hide the slow minority; p99 shows what the unluckiest users experience.
  • How do you reduce alert fatigue? Symptom-based alerts, composite alarms, regular pruning.
  • CloudWatch or Prometheus/Grafana? CloudWatch for AWS-native; Amazon Managed Prometheus and Grafana for Kubernetes-heavy, multi-cloud setups.
