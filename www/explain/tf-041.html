A replacement of a resource with create_before_destroy fails because the name already exists. Why, and how do you solve it?

Terraform · scenario · levels mid, senior

In one line

With create_before_destroy the new object is created while the old one still exists, so unique cloud names collide; fix it with name_prefix or a random suffix tied to replacement triggers, or accept a scheduled destroy-then-create with downtime.

Detailed explanation

By default Terraform replaces a resource by destroying first, then creating, which causes a gap. lifecycle { create_before_destroy = true } reverses the order to avoid downtime: create the replacement, repoint dependents, then delete the old one. That only works if two copies can exist at the same time. Many cloud resources require unique names in their scope: AWS launch templates, IAM roles, security groups in a VPC, target groups, ACM-linked listeners, Azure storage accounts (globally unique), Key Vaults and App Service plans. The second create fails with "already exists".

The standard fix is to make each generation's name unique. Several AWS resources support name_prefix, where the provider generates a unique suffix. Otherwise you add a random_id or random_pet with keepers set to the attributes that force replacement, so the suffix changes exactly when a new object is needed. When neither is possible, for example a storage account whose name is referenced by external systems, you accept destroy-then-create and schedule a maintenance window, or create a new resource side by side and migrate data deliberately.

Also remember that create_before_destroy propagates through dependencies: if A has it and B depends on A, Terraform must also handle B in create-before-destroy order, because the old A cannot be destroyed before its dependents are moved. Terraform applies this implicitly, which can surprise you with replacements in an unexpected order or with name collisions on resources you did not mark.

How it works

  1. A change forces replacement; Terraform plans +/- (create then destroy).
  2. It calls create with the same name; the API rejects the duplicate.
  3. Switch to name_prefix or a suffix from random_id with matching keepers.
  4. Now the new object gets a new name, dependents are updated, the old object is deleted.
  5. For resources that cannot rename, schedule a destroy-then-create.

Example

resource "random_id" "sg" {
  byte_length = 3
  keepers = {
    vpc_id = var.vpc_id   # replacement trigger for the security group
  }
}

resource "aws_security_group" "web" {
  name   = "web-${random_id.sg.hex}"
  vpc_id = var.vpc_id
  lifecycle { create_before_destroy = true }
}

resource "aws_launch_template" "web" {
  name_prefix   = "web-"
  image_id      = var.ami_id
  instance_type = "t3.medium"
  lifecycle { create_before_destroy = true }
}

Common mistakes

  • Adding create_before_destroy without checking whether names are unique.
  • Using timestamp() in names, which forces replacement on every plan.
  • Keepers that do not match the real replacement triggers, so the suffix never changes.
  • Forgetting quotas: two copies may exceed limits, such as public IPs.

How to answer in the interview

"With create_before_destroy, Terraform creates the new object before deleting the old one, so for a moment both exist. Many cloud resources need unique names, so the create fails because the name is taken. I make names unique per generation: name_prefix where the provider supports it, or a random_id suffix with keepers tied to the attributes that force replacement. If the name can't change, I accept destroy-then-create in a maintenance window. I also remember that create_before_destroy propagates to dependent resources, which affects their ordering too."

Likely follow-up questions

  • Which resources needed it for zero downtime? Launch templates with ASGs, TLS certificates on listeners, security groups attached to instances.
  • Why not always use it? Name collisions, quotas and unusual replacement ordering.
  • How do you see the order? The plan marks it +/- instead of -/+.
