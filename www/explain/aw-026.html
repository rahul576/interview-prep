What is a golden AMI, and why use one?

Cloud (AWS) · concept · levels entry

In one line

A golden AMI is a pre-baked machine image with the OS, latest patches, hardening, agents and runtime already installed, giving fast, consistent launches; it is built automatically with Packer or EC2 Image Builder, tested, versioned and rebuilt regularly, and rolled out by replacing instances (immutable infrastructure).

Detailed explanation

If every instance installs software at boot through user data, launches are slow (minutes of package downloads), depend on external repositories being up, and can produce different results if a package version changes between launches. During an Auto Scaling event that is exactly when you cannot afford delay or surprises.

A golden AMI moves that work to build time. A pipeline starts from a trusted base image (for example the latest Amazon Linux 2023 AMI), applies OS updates, CIS-style hardening, installs the SSM agent, CloudWatch agent, security and EDR agents, the language runtime, and sometimes the application itself. It runs tests (services start, ports closed, compliance checks with Inspector), then creates the AMI, versions it and shares it with the accounts that need it, often through AWS Organizations. Launch templates reference the new AMI ID, frequently via an SSM parameter like /golden/amazon-linux/latest.

Tools: HashiCorp Packer defines builds as code and works across clouds; EC2 Image Builder is the managed AWS service with recipes, components, test stages, schedules and distribution settings. Rebuild on a schedule (weekly or monthly) and when critical CVEs appear.

This enables immutable infrastructure: instead of patching running servers with SSH or configuration tools, you roll out new instances from the new AMI and terminate old ones, so every server matches a known, tested image and drift disappears. Containers apply the same idea at the image level.

How it works

  1. Start from a trusted base AMI.
  2. Patch, harden and install agents and runtime.
  3. Run validation tests and vulnerability scans.
  4. Create, tag and version the AMI; share to accounts.
  5. Update the launch template or SSM parameter.
  6. Roll instances with an Auto Scaling instance refresh; deprecate old AMIs.

Example

# Packer template (HCL2), simplified
source "amazon-ebs" "base" {
  region        = "eu-west-1"
  instance_type = "t3.small"
  source_ami_filter {
    filters     = { name = "al2023-ami-*-x86_64" }
    owners      = ["amazon"]
    most_recent = true
  }
  ssh_username = "ec2-user"
  ami_name     = "golden-al2023-{{timestamp}}"
}

build {
  sources = ["source.amazon-ebs.base"]
  provisioner "shell" {
    inline = [
      "sudo dnf -y update",
      "sudo dnf -y install amazon-cloudwatch-agent java-21-amazon-corretto",
      "sudo systemctl enable amazon-ssm-agent"
    ]
  }
}

Common mistakes

  • Building AMIs manually from a hand-configured instance.
  • Never rebuilding, so "golden" images are months out of date.
  • Baking secrets or environment-specific config into the image.
  • No tests before distribution.

How to answer in the interview

"A golden AMI is a pre-baked image with the patched OS, security hardening, monitoring and logging agents and often the runtime already installed. Instances from it start fast and identically, which matters for Auto Scaling. I'd build them automatically with Packer or EC2 Image Builder, run tests and scans, version them and share them to the accounts that use them, and rebuild regularly, say weekly, and for critical CVEs. Deployment is then immutable: rather than patching running servers, we roll new instances from the new AMI, for example with an Auto Scaling instance refresh."

Likely follow-up questions

  • How do you roll a new AMI to an ASG without downtime? Update the launch template and run an instance refresh with a minimum healthy percentage.
  • Packer vs Image Builder? Packer is multi-cloud and code-first; Image Builder is managed with built-in scheduling, testing and distribution.
  • What goes in user data then? Only small, instance-specific settings.
