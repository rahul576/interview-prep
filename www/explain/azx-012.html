What is Azure Bastion, and how do you give engineers secure access to VMs without public IPs?

Azure · concept · levels mid, senior

In one line

Azure Bastion is a managed jump service inside your VNet that gives RDP/SSH over TLS (port 443) from the portal or native client, so VMs need no public IP; combine it with Entra ID login, VM login RBAC roles, PIM and optionally just-in-time (JIT) access for least-privilege, audited admin access.

Detailed explanation

Exposing port 3389 or 22 on a public IP is one of the most common ways VMs get compromised: bots scan for open management ports within minutes. Bastion removes that attack surface. You deploy it into a dedicated subnet named AzureBastionSubnet (usually in the hub VNet), and engineers connect through the Azure portal over HTTPS, or with the native client using az network bastion ssh/rdp (Standard or Premium SKU). Bastion then talks to the VM's private IP, so the VM's NSG only needs to allow management traffic from the Bastion subnet.

Identity is the second layer. With the Microsoft Entra ID login extension on Windows and Linux VMs, engineers sign in with their corporate account and MFA and Conditional Access apply, instead of shared local passwords or SSH keys. Authorisation uses the Virtual Machine Administrator Login and Virtual Machine User Login roles. Those roles should be eligible through Privileged Identity Management rather than permanent, so access is activated for a few hours with a justification.

Defender for Cloud JIT VM access is an alternative or complement: management ports stay closed in the NSG and are opened for a requesting IP and time window only. The Bastion Premium SKU adds session recording and private-only deployment, and Bastion diagnostic logs record who connected to which VM.

How it works

  1. Create AzureBastionSubnet (/26 or larger) in the hub and deploy Bastion (Standard or Premium if you need the native client).
  2. Remove public IPs from VMs; NSGs allow 22/3389 only from the Bastion subnet.
  3. Enable the Entra ID login extension on VMs.
  4. Assign VM login roles as PIM-eligible to engineer groups.
  5. Engineers activate the role, then connect via portal or native client.
  6. Send Bastion logs to Log Analytics; enable session recording where required.

Example

# Activate the PIM role first, then connect with Entra ID auth through Bastion
az network bastion ssh \
  --name bas-hub-weu --resource-group rg-hub \
  --target-resource-id /subscriptions/<sub>/resourceGroups/rg-app/providers/Microsoft.Compute/virtualMachines/vm-app-01 \
  --auth-type AAD

Common mistakes

  • Keeping public IPs "just in case" after deploying Bastion.
  • Picking the Developer or Basic SKU and then finding that native client, shareable links or session recording are not available.
  • Permanent VM Administrator Login assignments for the whole team.
  • Shared local admin passwords instead of Entra ID login.
  • No logging, so nobody can tell who connected during an incident.

How to answer in the interview

"I'd deploy Azure Bastion in the hub VNet and remove every public IP from the VMs, so RDP and SSH are only reachable via Bastion over TLS. Engineers sign in with Entra ID and MFA using the VM login extension, and the Virtual Machine Administrator or User Login roles are eligible in PIM, so access is just-in-time and time-limited. Where a direct connection is still needed, Defender for Cloud just-in-time access opens the port only for one IP and a short window. Bastion logs and, on Premium, session recording give us an audit trail."

Likely follow-up questions

  • How do you reach a VM in a spoke from a hub Bastion? Bastion (Basic SKU and above) works across peered VNets, so peer hub and spoke and allow the Bastion subnet in the spoke NSGs.
  • Bastion vs JIT? Bastion removes public exposure entirely; JIT still opens a port temporarily on a public IP.
  • How do you connect from a local SSH client or for SCP? Use the native client via az network bastion ssh or tunnel.
