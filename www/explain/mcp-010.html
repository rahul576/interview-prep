When should data be exposed as an MCP resource instead of a tool?

MCP Servers · concept · levels mid, senior

In one line

Use a resource for read-only context the user or application selects (addressable by a stable URI, cacheable, subscribable); use a tool when the model must decide to fetch something with its own parameters, and always for anything with side effects; consider host support, sometimes offering both.

Detailed explanation

The decision follows MCP's control model. Resources are application-controlled: the host or the user chooses to include them. Tools are model-controlled: the model decides during reasoning to call them.

Resources fit data that is naturally a "document": a README, a database schema, a project configuration, a runbook, a dashboard snapshot, a specific ticket. They have a stable URI, benefit from caching, and can use subscriptions so the host refreshes when they change. A person would plausibly attach them to a conversation.

Tools fit when the model needs to look something up on demand with parameters it chooses: search_orders(customer, from, to), get_metrics(service, window). Search is the classic example: the query is not known in advance, the result set depends on arguments, and the model needs to iterate. Tools are also the only correct choice for actions that change state: creating tickets, updating records, sending messages. Resources must never have side effects.

A useful rule of thumb: "If a human would attach it, make it a resource; if the agent would look it up or act, make it a tool."

In practice, host support matters. Many hosts expose tools to the model automatically but require the user to attach resources manually, and some hosts barely surface resources at all. So a server author may offer both: a resource for the schema (for hosts with good resource UX and for caching) and a describe_table tool so agents can fetch it themselves. Tool results can also return resource links, combining both ideas.

How it works

  1. Ask who should trigger access: user/app or model.
  2. Ask whether it has side effects; if yes, it must be a tool.
  3. Ask whether it is addressable by a stable URI and cacheable: favour a resource.
  4. Check target hosts' support for resources versus tools.
  5. If needed, provide both, with the tool returning resource links.

Example

Data warehouse server
  resource  warehouse://schema/sales           (user attaches; cached; subscribe on changes)
  tool      describe_table(table)              (agent fetches schema itself when needed)
  tool      run_metric(metric, from, to)       (parameters chosen by the model)
  tool      schedule_report(metric, email)     (side effect -> tool, requires approval)

Common mistakes

  • Making search a resource, so the model cannot query it.
  • Exposing mutations as resources or prompts.
  • Making every static document a tool, inflating the tool list.
  • Ignoring that the target host may not surface resources to the model.

How to answer in the interview

"Resources fit read-only context that the app or user chooses deliberately, like a document, a schema or a config, especially when it has a stable URI and benefits from caching or change subscriptions. Tools fit when the model itself must decide to fetch something with parameters, like searching orders for a date range, and they're the only right choice for side effects. My rule of thumb: if a human would attach it, it's a resource; if the agent would look it up or act, it's a tool. I also check host support, because some hosts surface tools much better, so I sometimes offer both."

Likely follow-up questions

  • Why is search usually a tool? Its parameters are chosen by the model at runtime and results vary per query.
  • Can a tool return a resource? Yes, embedded or as a resource link.
  • Are resources safer? Fewer action risks, but content can still carry prompt injection or sensitive data.
