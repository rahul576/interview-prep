Compare plan-and-execute agents with ReAct-style agents.

AI Agents & AIOps · concept · levels mid, senior

In one line

A plan-and-execute agent writes an explicit plan first and then executes the steps, while a ReAct agent decides one step at a time from the latest observation; plans are inspectable, approvable, cheaper and safer against injection but can go stale, so production systems often use a hybrid with replanning.

Detailed explanation

In plan-and-execute, a planner call turns the goal into a list of steps, possibly with dependencies, for example a small DAG. An executor then works through them, sometimes with a cheaper model or deterministic code per step, and a final call synthesises the result. Because the expensive reasoning happens once, cost and latency can be lower, and independent steps can run in parallel.

Plans have operational advantages. They are inspectable: a human can review and approve the plan before anything happens, which is valuable for infrastructure or financial actions. Progress is measurable: three of seven steps done. And they help security: if the set of allowed actions is fixed before the agent reads untrusted data such as emails or web pages, injected instructions in that data cannot add new actions. This is the idea behind design patterns like plan-then-execute and Google DeepMind's CaMeL, which separate a privileged planner from quarantined data processing.

The weakness is that plans go stale. A file is missing, an API returns an unexpected error, or a search reveals the real problem lies elsewhere. A rigid executor either fails or blindly continues. ReAct adapts naturally because it re-decides after each observation, but it can wander, repeat work, and is harder to audit or approve ahead of time.

The practical answer is a hybrid: create an initial plan, execute step by step, and replan when observations diverge from expectations, keeping the plan as a visible to-do list. Many coding agents do exactly this with a task list they update as they go.

How it works

  1. Planner produces steps with expected outcomes, optionally shown for approval.
  2. Executor runs each step with tools, recording results.
  3. After each step, compare result with the expectation.
  4. If it diverges, call the planner again with the new facts.
  5. When all steps complete, synthesise and verify the final result.

Example

{
  "goal": "Rotate the expiring TLS certificate for api.example.com",
  "plan": [
    {"id": 1, "action": "get_cert_expiry", "args": {"host": "api.example.com"}},
    {"id": 2, "action": "request_cert", "args": {"domain": "api.example.com"}, "needs_approval": false},
    {"id": 3, "action": "update_secret", "args": {"ns": "prod", "name": "api-tls"}, "needs_approval": true},
    {"id": 4, "action": "verify_tls", "args": {"host": "api.example.com"}, "depends_on": [3]}
  ],
  "replan_if": "any step fails or returns unexpected state"
}

Common mistakes

  • Executing a plan rigidly after a step fails.
  • Replanning on every step, which becomes ReAct with extra cost.
  • Plans too vague to verify ("investigate the issue").
  • Letting untrusted data rewrite the plan without checks.

How to answer in the interview

"Plan-and-execute first asks the model for an explicit plan, then executes the steps, often with cheaper models or code. ReAct decides one step at a time from the latest observation. Plans can be inspected and approved by a human before anything happens, they make progress measurable and they save cost because the heavy reasoning happens once. They also help security: if the actions are fixed before reading untrusted data, injected instructions can't add new actions. But plans go stale when something unexpected happens, while ReAct adapts naturally and can also wander. In practice I use a hybrid: an initial plan, executed step by step, with replanning when observations diverge."

Likely follow-up questions

  • How would you show the plan to users? A short checklist of human-readable steps with risky steps highlighted, details expandable.
  • When is pure ReAct better? Exploratory tasks like debugging where the next step depends entirely on the last finding.
  • How do you detect that replanning is needed? Compare each step's result against its expected outcome or a success check.
