Which trigger types do Azure Pipelines support, and how do you avoid unnecessary pipeline runs in a monorepo?

Azure DevOps & Pipelines · concept · levels mid, senior

In one line

Azure Pipelines supports CI triggers (branches/tags, with batch), PR triggers (via build validation branch policies for Azure Repos, pr: for GitHub), scheduled cron triggers, and resource triggers (pipelines, repositories, containers); in a monorepo, path filters on triggers and policies prevent building everything on every change.

Detailed explanation

CI trigger (trigger:) runs on pushes to included branches or tags. batch: true means that if pushes arrive while a run is in progress, the next run includes all of them, instead of one run per push. trigger: none disables CI.

PR validation: for Azure Repos, YAML pr: is ignored; you configure a build validation policy on the target branch, which can be required or optional, have an expiry, and its own path filter. For GitHub (and Bitbucket) repos, the YAML pr: trigger is used, with branch and path filters. Fork PR settings control whether secrets are available (they should not be).

Scheduled triggers use cron in UTC: cron: "0 2 * * *" for nightly scans or long tests, with always: false to skip if nothing changed since the last scheduled run.

Resource triggers:

  • resources.pipelines with trigger: starts a pipeline when another completes (for example a deploy pipeline after a build), with branch and stage filters.
  • resources.repositories triggers on changes in another repository (Azure Repos).
  • resources.containers triggers on new images in ACR.

Monorepos need path filters. Each service pipeline includes its folder and the shared libraries it depends on, and excludes docs:

  • Too broad: every commit builds all 30 services, wasting agents and slowing feedback.
  • Too narrow: a change in a shared library doesn't rebuild dependent services, so broken code reaches main unnoticed.

Some teams add a small "affected projects" script (based on the dependency graph, like Nx or Bazel) to decide what to build.

How it works

  1. Push or PR event arrives.
  2. Branch filters decide whether the pipeline is a candidate.
  3. Path filters compare changed files with includes/excludes.
  4. Batching merges rapid pushes into one run.
  5. Completion of a pipeline can trigger downstream pipelines.

Example

trigger:
  batch: true
  branches: { include: [main, release/*] }
  paths:
    include: [services/orders, libs/common]
    exclude: [services/orders/docs]
schedules:
- cron: "0 2 * * 1-5"
  displayName: nightly security scan
  branches: { include: [main] }
  always: false
resources:
  pipelines:
  - pipeline: ordersBuild
    source: orders-ci
    trigger: { branches: { include: [main] } }

Common mistakes

  • Expecting pr: in YAML to work for Azure Repos.
  • Path filters that miss shared libraries.
  • Forgetting that cron schedules are in UTC.
  • CI and PR triggers both running duplicate builds for every PR update.

How to answer in the interview

"CI triggers run on pushes to selected branches or tags, and batch combines rapid pushes into one run. For Azure Repos, PR validation is configured through a build validation branch policy; for GitHub, the pr trigger in YAML. Scheduled triggers use cron, for example nightly scans, and can skip if nothing changed. Pipeline resource triggers chain pipelines, and repository and container resources react to other repos or new images. In a monorepo, path filters are essential: each service pipeline includes its folder and shared libraries and excludes docs, so one change doesn't build everything."

Likely follow-up questions

  • Path filters too narrow? Shared code changes don't trigger dependants, so breakages slip through.
  • Cron time zone? UTC.
  • Skip CI for a commit? Include [skip ci] in the commit message.
