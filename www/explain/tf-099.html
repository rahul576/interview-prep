How do you design Terraform variables and tfvars files for several environments without duplicating code?

Terraform · concept · levels mid, senior

In one line

Use one root configuration with a tfvars file and backend config per environment, sensible defaults so each tfvars only overrides real differences, validation rules to catch mistakes, and let the pipeline select the files so the same code version is promoted everywhere.

Detailed explanation

Copying the whole configuration into dev/, test/ and prod/ folders guarantees drift: a fix lands in one environment and is forgotten in the others. The better pattern keeps one root module and puts environment differences in data.

Each environment gets env/dev.tfvars, env/test.tfvars, env/prod.tfvars and a matching backend configuration file (env/dev.backend.hcl) passed with terraform init -backend-config=..., so each environment has separate state, often in separate storage accounts or buckets with separate permissions.

Variables are declared with types, descriptions and defaults that represent the common case. A tfvars file then contains only what genuinely differs: VM or database sizes, replica counts, CIDR ranges, feature flags, alert thresholds. A reviewer can see the entire difference between test and prod in two short files.

For small variations, a locals map keyed by environment is possible, but it hides differences in code and forces an environment variable everywhere; explicit tfvars are usually clearer. Validation blocks catch invalid input at plan time: allowed regions, CIDR format with can(cidrhost(...)), minimum replica counts for prod.

The pipeline chooses the tfvars and backend config based on the target environment, so no one types variables by hand, and the same commit flows dev → test → prod. When environments differ structurally — prod has extra regions or DR components — a separate root module per environment composing shared modules can be better than many feature flags.

How it works

  1. Write one root module using shared modules.
  2. Declare typed variables with defaults and validation.
  3. Create per-environment tfvars containing only differences.
  4. Create per-environment backend config files.
  5. The pipeline runs init, plan and apply with the right files.
  6. Promote the same commit through environments.

Example

variable "app_replicas" {
  type    = number
  default = 2
  validation {
    condition     = var.app_replicas >= 1 && var.app_replicas <= 20
    error_message = "app_replicas must be between 1 and 20."
  }
}

variable "vnet_cidr" {
  type = string
  validation {
    condition     = can(cidrhost(var.vnet_cidr, 0))
    error_message = "vnet_cidr must be a valid CIDR."
  }
}
# env/prod.tfvars: app_replicas = 6, vnet_cidr = "10.30.0.0/16", sku = "P2v3"
terraform init -backend-config=env/prod.backend.hcl
terraform plan -var-file=env/prod.tfvars -out=prod.plan

Comparison

ApproachProsCons
One root + tfvarsNo duplication, easy diffsStructural differences need flags
Folder per env, shared modulesExplicit, flexibleSome wiring duplicated
Copied code per envSimple at firstDrift and forgotten fixes

Common mistakes

  • Copy-pasting full configurations per environment.
  • Defaults that are only right for prod, so dev becomes expensive.
  • Forgetting a separate backend, so environments share one state.
  • Relying on people to pass -var flags by hand.

How to answer in the interview

"I use one root configuration with a tfvars file per environment, plus a matching backend config file so each environment has its own state. Variables have sensible defaults for the common case, and each tfvars file only overrides real differences like sizes, replica counts, CIDRs and feature flags, so the difference between environments is visible in one small file. Validation rules catch mistakes like invalid regions or bad CIDRs. The pipeline selects the files per environment, nobody types variables by hand, and the same code version is promoted through every environment."

Likely follow-up questions

  • When are separate root modules per environment better? When environments differ structurally, such as extra regions or DR in prod.
  • What about workspaces? CLI workspaces share one backend and permissions; separate backends give stronger isolation.
  • How do you keep secrets out of tfvars? Read them from a secret store via data sources or pipeline variables.
