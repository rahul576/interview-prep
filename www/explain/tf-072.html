How do you manage SaaS tools such as GitHub, Datadog or Cloudflare with Terraform, and why?

Terraform · concept · levels mid, senior

In one line

Terraform has providers for most SaaS platforms, so GitHub repos and branch protection, Datadog or Grafana monitors, Cloudflare DNS and WAF, PagerDuty and Entra ID groups can be managed with the same review, audit, consistency and recovery benefits, using scoped API tokens and watching rate limits and UI drift.

Detailed explanation

Infrastructure today includes many SaaS control planes. Configuring them by clicking creates the same problems as clicking in a cloud portal: no review, no history, inconsistency and no way to rebuild after a mistake. Terraform's provider model is generic, so vendors and the community publish providers for GitHub, GitLab, Datadog, Grafana, New Relic, Cloudflare, PagerDuty, Okta, Entra ID (azuread), Snowflake and many more.

Typical uses:

  • GitHub: repositories, teams, memberships, branch protection or rulesets, Actions secrets and variables, environments.
  • Observability: Datadog or Grafana monitors, dashboards and SLOs defined next to the service they watch.
  • Edge: Cloudflare DNS records, WAF rules, page rules, zero-trust settings.
  • Incident response: PagerDuty services, schedules and escalation policies.
  • Identity: Entra ID groups and app registrations.

Benefits mirror cloud IaC: pull-request review for risky changes like removing branch protection, an audit trail in Git, consistency across hundreds of repositories or monitors using modules and for_each, and recovery if someone deletes a monitor or DNS record.

Operational concerns: providers need API tokens, which should be least-privilege, stored in a secret store, and short-lived where possible (for example GitHub App credentials instead of a personal token). Large estates hit API rate limits, so split states and tune parallelism. People will still click in the UI, which shows up as drift; decide which settings are code-owned and communicate it, sometimes restricting UI permissions.

How it works

  1. Choose the provider and create a scoped token or app credential.
  2. Import existing objects with import blocks.
  3. Model repeated objects as modules with for_each.
  4. Review changes through PRs and plans.
  5. Detect drift with scheduled plans.

Example

provider "github" {
  owner = "acme"
  app_auth {}   # GitHub App credentials from environment variables
}

resource "github_repository" "svc" {
  for_each   = var.services
  name       = each.key
  visibility = "private"
  auto_init  = true
}

resource "github_branch_protection" "main" {
  for_each       = github_repository.svc
  repository_id  = each.value.node_id
  pattern        = "main"
  required_pull_request_reviews { required_approving_review_count = 1 }
}

Common mistakes

  • Using a personal admin token for automation.
  • One huge state for thousands of SaaS objects, hitting rate limits.
  • Managing objects that users legitimately change daily, causing constant drift.
  • Forgetting to import existing configuration before applying.

How to answer in the interview

"Terraform providers exist for most SaaS platforms, so we can use the same workflow as for cloud. Common examples: GitHub repositories, teams and branch protection, Datadog or Grafana monitors and dashboards, Cloudflare DNS and WAF rules, PagerDuty schedules and Entra ID groups. The benefits are the same: review through PRs, an audit trail, consistency across hundreds of objects and recovery if something is deleted. Providers need scoped, securely stored, ideally short-lived tokens. I watch API rate limits and UI changes, which show up as drift."

Likely follow-up questions

  • Which settings would you not manage? Things users change daily, like personal dashboards or on-call overrides.
  • How do you handle rate limits? Smaller states, lower parallelism, provider retry settings.
  • GitHub App or PAT? GitHub App: scoped, auditable, not tied to a person.
