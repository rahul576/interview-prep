What are the main advantages and disadvantages of Spring Boot?

Spring Boot · concept · levels entry, mid

In one line

Spring Boot's advantages are fast setup, auto-configuration, starters, embedded server, Actuator and a huge ecosystem; its disadvantages are hidden "magic", harder debugging, and a larger footprint and slower startup, mitigated with the conditions report, exclusions, lazy init, AOT/native images and CRaC.

Detailed explanation

Advantages. Spring Initializr creates a working project in a minute. Auto-configuration and starters remove boilerplate and version conflicts because the Boot BOM manages compatible versions. An embedded server and single executable jar make deployment and container images trivial. Externalised configuration and profiles let the same artifact run everywhere. Actuator and Micrometer give health, metrics and tracing out of the box. The ecosystem is enormous: Spring Data, Security, Cloud, Kafka, Batch, Integration, AI, plus excellent documentation, community answers and testing support such as test slices and Testcontainers integration.

Disadvantages. The convenience hides a lot. When an unexpected bean appears, a DataSource is missing or two beans conflict, you must understand conditions and ordering to debug it. Starters pull in many transitive dependencies, which increases jar size, memory and startup time (several seconds for a large app), a problem for serverless and fast scale-out. Boot is opinionated; going against its conventions can be harder than with plain Spring. Upgrades across major versions (javax to jakarta in Boot 3) take effort.

Mitigations. Use --debug or the conditions endpoint, exclude unneeded auto-configurations, remove unused starters, consider spring.main.lazy-initialization for development, enable virtual threads for blocking I/O, and for fast startup use GraalVM native images via Spring AOT, CRaC checkpoints or class data sharing (CDS/AOT cache on newer JDKs).

How it works

  1. Weigh the advantages against the deployment target (long-running service vs short-lived function).
  2. Measure startup and memory with Actuator startup endpoint and JVM metrics.
  3. Trim dependencies and auto-configurations.
  4. Apply lazy init, CDS or native compilation where startup matters.
  5. Keep the conditions report handy when debugging.

Example

# Show why beans were or were not created
java -jar app.jar --debug | grep -A3 "DataSourceAutoConfiguration"

# Build a native image with the Boot plugin
./mvnw -Pnative native:compile
./target/app      # starts in tens of milliseconds

Common mistakes

  • Listing only advantages; interviewers want balanced trade-offs.
  • Blaming Boot for slowness without measuring startup.
  • Using native images without considering reflection hints and longer build times.
  • Copying starters into every service whether used or not.

How to answer in the interview

"The big advantages are speed of development: Initializr, auto-configuration and starters remove boilerplate and version conflicts, the embedded server makes deployment a single jar, and Actuator gives production monitoring. The ecosystem is huge. The downsides are that auto-configuration hides what's happening, so debugging an unexpected bean needs the conditions report, and the footprint and startup time are larger. I mitigate with the --debug report, excluding unused auto-configs, trimming starters, and for fast startup using native images or CRaC."

Likely follow-up questions

  • How to reduce startup time? Trim dependencies, lazy init, CDS/AOT cache, native image or CRaC.
  • Downside of lazy initialisation? Errors surface at first use instead of startup, and first requests are slower.
  • Native image trade-offs? Fast startup and low memory, but longer builds, reflection limits and lower peak throughput in some cases.
