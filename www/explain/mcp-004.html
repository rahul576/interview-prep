What does an MCP tool definition contain?

MCP Servers · concept · levels entry, mid, senior

In one line

An MCP tool definition (returned by tools/list) has a unique name, optional title, a description the model reads to decide when to use it, an inputSchema (JSON Schema), an optional outputSchema for structured results, and optional annotations such as readOnlyHint and destructiveHint.

Detailed explanation

The tool definition is the contract between the server, the host and the model, and the model sees nothing else when deciding whether to use the tool.

  • name: a unique identifier used in tools/call, e.g. search_orders. Keep it short, specific and stable; hosts may reference it in allowlists.
  • title: an optional human-readable display name for UIs, e.g. "Search orders".
  • description: the most important field for model behaviour. It should say what the tool does, when to use it (and when not), what it returns and important constraints, such as "dates are in UTC" or "returns at most 50 results".
  • inputSchema: a JSON Schema object describing arguments: types, required fields, enums for fixed choices, formats, ranges and per-property descriptions. Hosts and servers validate arguments against it, and the model uses it to fill parameters.
  • outputSchema (since the 2025-06-18 revision): declares the shape of structuredContent in results, so clients can validate and programmatically use outputs.
  • annotations: behavioural hints: readOnlyHint, destructiveHint, idempotentHint, openWorldHint, plus an annotation title. Hosts may use them for approval UX, but they are untrusted unless the server is trusted.
  • Newer revisions also allow icons and a _meta field for extra metadata.

A vague description ("handles orders") leads to the model calling the wrong tool, calling it with guessed arguments, or not calling it at all.

How it works

  1. Client sends tools/list (paginated with cursors if needed).
  2. Server returns tool definitions.
  3. Host converts them into the model provider's tool format and includes them in the request.
  4. Model emits a call with arguments matching inputSchema.
  5. Server validates arguments, executes and returns content (and structuredContent if outputSchema exists).

Example

{
  "name": "search_orders",
  "title": "Search orders",
  "description": "Find a customer's orders by email and optional status. Use before get_order_details. Returns at most 20 orders, newest first.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "email":  { "type": "string", "format": "email", "description": "Customer email" },
      "status": { "type": "string", "enum": ["open", "shipped", "cancelled"] },
      "limit":  { "type": "integer", "minimum": 1, "maximum": 20, "default": 10 }
    },
    "required": ["email"]
  },
  "outputSchema": {
    "type": "object",
    "properties": { "orders": { "type": "array", "items": { "type": "object" } }, "total": { "type": "integer" } },
    "required": ["orders", "total"]
  },
  "annotations": { "readOnlyHint": true, "openWorldHint": false }
}

Common mistakes

  • One-word descriptions that do not say when to use the tool.
  • Loose schemas ("type": "object" with no properties) so the model guesses.
  • Free-text parameters where an enum would remove ambiguity.
  • Renaming tools casually, breaking host allowlists and workflows.

How to answer in the interview

"A tool definition from tools/list has a unique name used in tools/call, an optional human-readable title, and a description, which is critical because the model reads it to decide when and how to use the tool. The inputSchema is JSON Schema for the arguments: types, required fields, enums, per-field descriptions, which hosts use to validate and the model uses to fill parameters. Optionally there's an outputSchema for structured results, and annotations like readOnlyHint, destructiveHint, idempotentHint and openWorldHint, which hosts can use as hints for approval decisions."

Likely follow-up questions

  • Why can a vague description cause misuse? The model has nothing else to judge purpose, scope or constraints, so it guesses.
  • Who validates arguments? The server must; hosts may also validate before sending.
  • Are annotations enforced? No, they are hints and must be treated as untrusted from untrusted servers.
