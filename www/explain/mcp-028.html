How would you build an MCP server with Java and Spring AI?

MCP Servers · concept · levels mid, senior

In one line

Use Spring AI's MCP server starters (built on the official Java SDK), annotate bean methods with @Tool or the newer @McpTool, let Spring AI generate schemas from parameters and descriptions, choose a transport (stdio, Streamable HTTP on Spring MVC or WebFlux) and reuse Spring Security, services and observability.

Detailed explanation

For a Java backend team, the big advantage is that an MCP server becomes just another Spring Boot application.

Starters. Spring AI provides Boot starters on top of the MCP Java SDK: a standard starter for stdio, and WebMVC or WebFlux starters for HTTP-based transports, including Streamable HTTP (and stateless variants). Auto-configuration creates the MCP server, registers transports and wires capabilities.

Tools. Annotate methods on Spring beans with @Tool(description = "...") and parameters with @ToolParam(description = "..."), then expose them via a ToolCallbackProvider (e.g. MethodToolCallbackProvider). Newer Spring AI versions add MCP-specific annotations such as @McpTool, @McpResource, @McpPrompt and @McpComplete, which are picked up automatically. Spring AI generates the JSON Schema from method parameter types (records and POJOs included), so the model sees accurate argument definitions.

Configuration properties (spring.ai.mcp.server.*) set server name, version, protocol/transport type and which capabilities to advertise.

Reuse. Tools call existing services, repositories and clients, with transactions and validation as usual. Spring Security protects the HTTP endpoint as an OAuth 2 resource server, validating JWTs for issuer, audience and scopes; method security (@PreAuthorize) and passing the authenticated principal into services keep data access scoped to the calling user. Micrometer and OpenTelemetry give metrics and traces per tool call. Packaging and deployment follow the normal pipeline: container image, Kubernetes, health probes, config and secrets management.

How it works

  1. Add the Spring AI BOM and the MCP server starter for your transport.
  2. Write @Service beans with annotated tool methods.
  3. Register tools (provider bean or MCP annotations scanning).
  4. Configure server properties and Spring Security resource server.
  5. Test with the Inspector; deploy like any Boot app.

Example

@Service
public class OrderTools {
  private final OrderService orders;
  public OrderTools(OrderService orders) { this.orders = orders; }

  @Tool(description = "Get status and ETA of an order by order number, e.g. ORD-1042. Read-only.")
  public OrderStatus getOrderStatus(@ToolParam(description = "Order number") String orderNo) {
    var user = SecurityContextHolder.getContext().getAuthentication();
    return orders.statusFor(orderNo, user);   // enforces the caller's access
  }
}

@Bean
ToolCallbackProvider orderToolProvider(OrderTools tools) {
  return MethodToolCallbackProvider.builder().toolObjects(tools).build();
}
spring:
  ai.mcp.server: { name: order-mcp, version: 1.0.0, protocol: STREAMABLE }
  security.oauth2.resourceserver.jwt.issuer-uri: https://login.example.com/realms/corp

Common mistakes

  • Tools that call repositories with a technical account, ignoring the user's permissions.
  • Returning full JPA entities with lazy-loaded graphs as tool output.
  • Missing parameter descriptions, so schemas are bare.
  • Leaving the HTTP endpoint unauthenticated in non-production environments.

How to answer in the interview

"Spring AI provides MCP server starters built on the official Java SDK. I pick the starter for the transport, stdio, or Streamable HTTP on Spring MVC or WebFlux, and annotate bean methods with @Tool or the newer @McpTool annotations, with descriptions for the method and parameters. Spring AI generates the JSON schema from the parameters and registers the tools. The real win is reuse: tools call existing services, Spring Security protects the endpoint as an OAuth 2 resource server, Micrometer and OpenTelemetry give metrics and traces, and it deploys like any Boot app to Kubernetes. Properties control name, version and capabilities."

Likely follow-up questions

  • Preventing over-exposure of data? Propagate the authenticated user into services and enforce row-level access there, returning DTOs with only needed fields.
  • Stdio for a Java server? Fine for local tools, but startup time and logging to stdout need care.
  • How to observe tool calls? Micrometer timers and traces per tool, with user and outcome tags.
