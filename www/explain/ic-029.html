What are common YAML pitfalls in infrastructure code such as Ansible, Kubernetes or pipelines?

Infrastructure as Code · concept · levels entry

In one line

YAML pitfalls: indentation with spaces only, implicit typing (yes/no/on/off become booleans, 1.10 becomes 1.1, NO becomes false, leading zeros), unquoted colons and special characters, and confusion between | (literal) and > (folded) multi-line strings; catch them with yamllint and schemas.

Detailed explanation

YAML is everywhere in infrastructure, and it has traps.

Indentation defines structure and must use spaces, never tabs. A key indented one level too far or too little becomes a child of the wrong parent, and often the file is still valid YAML, so the error is silent: an env: list ends up under the wrong container, or a task option becomes a module argument.

Implicit typing. Unquoted scalars are interpreted. Under YAML 1.1 rules, still used by many parsers including PyYAML (Ansible) and parts of the Go ecosystem, yes, no, on, off, y, n can become booleans. That's the Norway problem: the country code NO becomes false. Numbers are coerced too: version: 1.10 becomes the float 1.1, 010 may be read as octal 8, 1e3 becomes 1000. YAML 1.2 fixed most of this, but you cannot rely on which spec a tool implements, so quote strings that look like something else: versions, codes, IDs with leading zeros, and Kubernetes values like env vars and annotation values, which must be strings.

Special characters. A colon followed by a space inside a value (msg: Error: failed) breaks parsing. Values starting with *, &, !, {, [, %, @ or a backtick, and Jinja expressions starting with {{, must be quoted. # after a space starts a comment.

Multi-line strings. | keeps newlines exactly (scripts, certificates); > folds lines into spaces (long descriptions). Chomping indicators |- and |+ control the trailing newline.

Tooling. yamllint, editor schemas (Kubernetes, GitHub Actions, Compose via the YAML language server), ansible-lint, kubeconform and actionlint catch most mistakes before they reach a cluster.

How it works

  1. The parser reads indentation to build maps and lists.
  2. Each unquoted scalar is matched against type rules.
  3. Quoted scalars stay strings.
  4. Block scalars (|, >) collect multi-line text.
  5. The tool then validates the resulting structure (or doesn't).

Example

country: NO          # false under YAML 1.1
country: "NO"        # string
python_version: 3.10 # float 3.1
python_version: "3.10"
msg: "Error: disk full"
env:
  - name: FEATURE_ENABLED
    value: "true"    # Kubernetes env values must be strings
script: |
  set -e
  ./build.sh
description: >
  This long text is folded
  into a single line.
yamllint -s .

Common mistakes

  • Tabs or mixed indentation copied from editors.
  • Unquoted versions in CI matrices (3.10 → 3.1).
  • Unquoted Jinja expressions in Ansible.
  • Using > for scripts, which joins commands onto one line.

How to answer in the interview

"YAML is whitespace sensitive: spaces only, and a wrong indent silently moves a key to another level. Unquoted values get typed automatically, so yes, no, on and off can become booleans, 1.10 becomes the float 1.1, leading zeros become numbers, and a country code NO becomes false, the Norway problem. So I quote versions, codes and anything ambiguous. Strings with a colon and space or starting with special characters like *, { or Jinja braces need quotes. For multi-line text, | keeps newlines and > folds them. yamllint and editor schemas for Kubernetes or GitHub Actions catch most of it early."

Likely follow-up questions

  • What is the Norway problem? Under YAML 1.1, unquoted NO is parsed as boolean false.
  • Why does Kubernetes reject value: true in env? EnvVar value must be a string.
  • How do anchors and aliases help? &name and *name reuse blocks, though many tools discourage complex use.
