What is your disaster recovery strategy for Kubernetes clusters and the applications on them?

Kubernetes · design · levels senior, lead

In one line

Set RPO and RTO per application, rebuild clusters from IaC and GitOps rather than restoring them, back up stateful data separately with the best native tool (PITR, snapshots, cross-region copies), use Velero for anything not in Git, make secrets, DNS and certificates recoverable, and run timed restore drills.

Detailed explanation

DR starts with business requirements. RPO is how much data you may lose; RTO is how long you may be down. A stateless API might accept an RTO of an hour and no RPO concern, while a payments ledger needs RPO near zero. These numbers decide cost and design.

The guiding principle is clusters are cattle. If the cluster itself is defined in Terraform/OpenTofu, Bicep or Crossplane and every workload in Git (Argo CD or Flux), recovery means creating a new cluster and pointing GitOps at it, which is reproducible and testable. Restoring etcd snapshots is mostly for self-managed control planes and brings back whatever state, good or bad, existed at backup time, including stale node objects.

Data needs its own protection. Use the strongest tool for each store: managed database backups with point-in-time recovery and cross-region replicas, native tools such as CloudNativePG's backups to object storage, CSI volume snapshots for other PVs, object storage replication for buckets. Copies must live in another region and ideally another account, protected against deletion (immutability or object lock) because ransomware and mistakes target backups too.

Velero backs up Kubernetes objects and volume data for anything not covered by Git: manually created resources, CRD instances created by operators, or legacy apps. Secrets should come from a replicated vault or cloud secret manager via External Secrets; cluster-only secrets are a classic DR gap. Also plan for DNS, TLS certificates and their issuers, container registries and identity (SSO, workload identity) in the recovery region.

Drills turn the plan into evidence: rebuild in another region on a schedule, time it against the RTO, and fix what breaks.

How it works

  1. Classify apps by RPO/RTO and dependencies.
  2. Cluster from IaC; workloads from GitOps.
  3. Data: PITR, snapshots, cross-region and cross-account copies.
  4. Velero for objects and volumes outside Git.
  5. Secrets in a replicated vault; DNS, certs and registry available in DR region.
  6. Runbooks with order of recovery.
  7. Regular timed restore drills with follow-up actions.

Example

velero schedule create nightly --schedule "0 1 * * *" \
  --include-namespaces payments,orders --snapshot-move-data --ttl 720h
# DR drill: new cluster in secondary region
terraform -chdir=infra/clusters/dr apply
argocd cluster add dr-weu && argocd app sync -l env=prod
velero restore create --from-backup nightly-20261120010000 --include-namespaces payments

Common mistakes

  • Backups in the same account and region as production.
  • Never testing restores.
  • Secrets only in the cluster.
  • Ignoring dependencies such as DNS, identity and registries.
  • One RPO/RTO for everything.

How to answer in the interview

"I start by agreeing RPO and RTO per application, because a stateless API and a payments database need different answers. Clusters are cattle: I rebuild the cluster from infrastructure as code and redeploy workloads from GitOps, which is cleaner than restoring etcd. Stateful data is backed up separately with the best tool for it: database PITR or replication, volume snapshots, copied cross-region and cross-account. Velero covers objects not in Git. Secrets live in a replicated vault, and DNS, certificates and identity must work in the DR region. Regular timed drills prove we meet the RTO."

Likely follow-up questions

  • What usually breaks in a DR drill? Forgotten secrets, hard-coded endpoints, DNS TTLs, missing quota or IAM in the DR region, and undocumented manual steps.
  • When do you restore etcd? Self-managed clusters where state cannot be rebuilt from Git.
  • How do you protect backups from ransomware? Separate account, immutable storage and limited delete permissions.
