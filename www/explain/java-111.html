Compare HashMap, LinkedHashMap and TreeMap. When do you use each?

Collections · concept · levels entry, mid

In one line

HashMap gives average O(1) with no order, LinkedHashMap adds insertion or access order (handy for LRU caches), and TreeMap is a red-black tree with sorted keys, O(log n) operations and NavigableMap range queries.

Detailed explanation

HashMap is the default choice: fast hashing, no ordering promise, and the iteration order may change after a resize. Use it when you only need lookup by key.

LinkedHashMap extends HashMap and threads a doubly linked list through all entries. By default the list follows insertion order, which gives predictable iteration, for example when building JSON with a stable field order. With the constructor flag accessOrder = true, each get or put moves the entry to the end, so the head is the least recently used entry. Overriding removeEldestEntry lets you evict automatically, which makes a simple LRU cache. The cost is slightly more memory per entry.

TreeMap stores entries in a red-black tree ordered by the keys' Comparable implementation or a supplied Comparator. Operations are O(log n), slower than hashing, but iteration is always sorted and it implements NavigableMap: floorKey, ceilingKey, firstEntry, headMap, tailMap and subMap. That suits time-based lookups ("which price was valid at 10:15?"), leaderboards and range reports. Keys must be comparable and, with natural ordering, cannot be null.

Since Java 21, LinkedHashMap and TreeMap also implement SequencedMap, adding firstEntry, lastEntry, pollFirstEntry and reversed().

How it works

  1. HashMap: hash → bucket → equals.
  2. LinkedHashMap: same lookup, plus before/after links maintained on insert, access and removal.
  3. TreeMap: compare from the root down left or right, then rebalance with rotations and recolouring.
  4. Navigation methods walk the tree to the nearest key.

Example

class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int max;
    LruCache(int max) { super(16, 0.75f, true); this.max = max; }
    @Override protected boolean removeEldestEntry(Map.Entry<K, V> e) {
        return size() > max;
    }
}

TreeMap<LocalTime, BigDecimal> prices = new TreeMap<>();
BigDecimal at1015 = prices.floorEntry(LocalTime.of(10, 15)).getValue();

Common mistakes

  • Relying on HashMap iteration order in tests or output.
  • Using TreeMap just to get "some order" when insertion order is what you need.
  • Building a production cache from LinkedHashMap without thread safety or TTL; use Caffeine.
  • Inconsistent compareTo and equals in TreeMap keys.

How to answer in the interview

"HashMap is my default: average constant time, no order. LinkedHashMap keeps a linked list through entries, so it preserves insertion order, or access order if configured, and with removeEldestEntry it becomes a simple LRU cache. TreeMap is a red-black tree, so keys are always sorted and operations are log n, and as a NavigableMap it supports floorKey, ceilingKey and range views, which I use for time windows or leaderboards. I pick the others only when ordering really matters."

Likely follow-up questions

  • How would you build an LRU cache? LinkedHashMap with accessOrder true and removeEldestEntry, or Caffeine in production.
  • Is LinkedHashMap thread safe? No; wrap it or use a concurrent cache.
  • What does subMap return? A live view of the key range, backed by the original map.
