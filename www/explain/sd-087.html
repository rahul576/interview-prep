A startup asks whether to begin with microservices or a monolith for a new product. What do you advise?

Architecture Trade-offs · scenario · levels senior, lead

In one line

For most startups, start with a modular monolith: fastest for product discovery, avoids microservices' operational and distributed complexity, matches a small team size; keep clear module boundaries so services can be extracted later, with exceptions for genuinely different scaling or isolation needs.

Detailed explanation

Microservices solve an organisational problem (many teams deploying independently) and some scaling problems, at a large cost: network calls instead of function calls, distributed transactions, eventual consistency, service discovery, versioned APIs, many pipelines, observability across services, and on-call for each. A team of 5–10 pays these costs daily without the benefits.

Early on, the main risk is building the wrong product. A monolith lets you refactor across the whole codebase in one commit, run everything locally, and deploy once.

The modular part matters: organise by business domain (orders, billing, catalogue), with explicit internal interfaces, no reaching into other modules' tables, and dependency rules enforced (ArchUnit, Spring Modulith, packages). This keeps the monolith from becoming a "big ball of mud" and makes later extraction straightforward.

Conway's law: architecture mirrors communication structure. When you have several teams stepping on each other, extract services along module boundaries. Exceptions from day one: components with very different scaling or runtime needs (video transcoding, ML inference), or strict isolation for security/compliance (payment card data).

How it works

  1. One deployable, domain modules with clear APIs.
  2. One database, but schema/tables owned per module.
  3. Async events between modules where useful (in-process first).
  4. Extract a module when: independent scaling, team ownership, release cadence or fault isolation demands it.

Example

app/
  orders/   (api, domain, persistence) → publishes OrderPlaced
  billing/  (listens to OrderPlaced)
  catalog/
rule: modules may call each other only via api packages; no cross-module table access

Common mistakes

  • Microservices first "because Netflix does it".
  • A monolith without boundaries (hard to ever split).
  • Splitting by technical layer instead of business domain.
  • Shared database across extracted services.

How to answer in the interview

"For a startup I'd start with a modular monolith. Speed of change matters most while finding product fit, and microservices bring operational and distributed-systems costs a small team can't afford. I'd enforce domain boundaries inside the codebase so modules can be extracted later when teams grow or scaling needs differ, and I'd only split from day one for something like video processing or PCI-scoped payments."

Likely follow-up questions

  • When to extract the first service? Different scaling, team contention, release cadence conflicts, isolation needs.
  • How to extract? Strangler pattern; route calls via an interface, then over the network.
  • Shared database risk? Coupling and hidden dependencies; give each service its own schema.
