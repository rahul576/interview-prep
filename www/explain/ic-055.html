What are AWX, Ansible Tower and Ansible Automation Platform?

Configuration Management · concept · levels mid

In one line

AWX is the open-source upstream, and Red Hat Ansible Automation Platform (AAP) is the supported product whose automation controller (formerly Ansible Tower) provides a web UI and REST API for running Ansible centrally with job templates, credentials, RBAC, schedules, workflows, audit logs and container-based execution environments.

Detailed explanation

Running Ansible from engineers' laptops does not scale: everyone has different versions, secrets sit on laptops, nobody knows who ran what, and other teams cannot safely trigger automation. A controller solves this by making Ansible a shared service.

Key objects:

  • Projects sync playbooks from Git at a branch or tag.
  • Inventories are static or dynamic (AWS, Azure, VMware, ServiceNow CMDB sources).
  • Credentials (SSH keys, cloud keys, vault passwords) are stored encrypted and injected at runtime; users can use a credential without ever seeing it.
  • Job templates combine project + playbook + inventory + credentials + extra vars, optionally with a survey that asks for input.
  • Workflows chain templates with success/failure branches and approval nodes.

On top come RBAC (who may view, edit or execute each object), schedules, notifications (Slack, email, webhooks) and a complete job history. The REST API lets ServiceNow, CI pipelines or chat bots launch jobs.

Jobs run inside execution environments: container images, built with ansible-builder, containing ansible-core, collections and Python dependencies, so every run uses the same tested toolchain. In AAP the work can be spread across execution nodes via the automation mesh. AAP also bundles Event-Driven Ansible, private automation hub and, in recent releases, a unified platform UI.

How it works

  1. Admin connects a Git project and an inventory source.
  2. Credentials are added once by a privileged team.
  3. A job template defines what to run and on which hosts.
  4. RBAC grants a group execute permission on that template only.
  5. A user, schedule or API call launches the job in an execution environment.
  6. Output, who ran it and with which variables are logged.

Example

# Trigger a job template from a pipeline or ticketing tool via the API
curl -s -X POST -H "Authorization: Bearer $AAP_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"extra_vars": {"service": "nginx", "target": "web03"}}' \
  https://aap.example.com/api/controller/v2/job_templates/42/launch/

Common mistakes

  • Giving broad admin roles instead of execute-only on specific templates.
  • Free-text surveys passed straight into shell commands.
  • Running AWX in production without considering that it has no vendor support.
  • Not pinning project branches, so untested code runs in production.

How to answer in the interview

"AWX is the open source upstream; Ansible Automation Platform is Red Hat's supported product, and its automation controller is what used to be called Tower. It turns Ansible into a central service with a UI and REST API. Playbooks come from Git, inventories can be dynamic, credentials are stored encrypted and injected so users never see them, and job templates with surveys let other teams or ServiceNow run automation. RBAC, schedules, workflows and an audit log make it safe to share, and jobs run in container execution environments so the toolchain is consistent."

Likely follow-up questions

  • How would you let support restart services without SSH access? A job template with a restricted survey choice list and execute-only RBAC for the support group.
  • What is an execution environment? A container image with ansible-core, collections and dependencies, built with ansible-builder.
  • AWX or AAP? AWX for labs or teams accepting self-support; AAP when you need support, certified content and lifecycle guarantees.
