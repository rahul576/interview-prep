Should you set CPU limits on Kubernetes containers? Give the arguments on both sides.

Kubernetes · concept · levels senior, lead

In one line

CPU is compressible: requests already guarantee a proportional share via CFS weights, while limits add a hard CFS quota that throttles even when the node is idle; so many teams omit CPU limits for latency-sensitive services, but limits still make sense for predictability, runaway protection, Guaranteed QoS / exclusive cores and multi-tenant chargeback. Memory limits should always be set.

Detailed explanation

When a node's CPU is contended, the kernel shares it in proportion to cpu weight, which the kubelet derives from requests. A container requesting 1 CPU on a busy node still gets roughly 1 CPU's worth; when the node is quiet it can use idle cycles. That is already fair and efficient.

A limit converts to a CFS quota (cpu.max) per 100 ms period. Once the container uses its quota, it is stopped until the next period, even if every other core is idle. Multi-threaded apps and runtimes with GC threads burst and get throttled, which shows up as p99 latency spikes and slower start-up (JVM warm-up, for example). This is the main argument against CPU limits.

Arguments for limits:

  • Predictability: performance in production matches what was load-tested, instead of varying with how busy neighbours are.
  • Runaway protection: a spinning process cannot consume all idle CPU, which matters when requests are inaccurate.
  • Guaranteed QoS: requests equal to limits for CPU and memory; with the static CPU manager policy and integer CPUs, the pod gets exclusive cores, ideal for latency-critical or NUMA-sensitive work.
  • Multi-tenancy and cost: in shared clusters or chargeback models, limits cap what a tenant can consume; some policies (LimitRanges, compliance) require them.

Memory is different: it is incompressible. A container cannot be "slowed down" when memory runs out; something gets OOM-killed or evicted. Memory limits (usually equal to or near the request) keep failures contained to the offending container.

A balanced default: accurate CPU requests everywhere, no CPU limit (or a generous one, for example 2-4 times the request) for latency-sensitive services, Guaranteed pods with exclusive CPUs for the most critical workloads, memory limits always.

How it works

  1. Kubelet maps requests to cgroup CPU weight.
  2. Under contention, CPU is shared by weight.
  3. A limit sets a quota per 100 ms period; exceeding it throttles.
  4. Requests equal to limits gives Guaranteed QoS.
  5. Static CPU manager pins integer-CPU Guaranteed pods to exclusive cores.

Example

# latency-sensitive API: no CPU limit, memory limit set
resources:
  requests: { cpu: 500m, memory: 512Mi }
  limits:   { memory: 512Mi }
---
# critical, pinned workload: Guaranteed with integer CPUs
resources:
  requests: { cpu: "2", memory: 4Gi }
  limits:   { cpu: "2", memory: 4Gi }

Common mistakes

  • Blanket policies forcing CPU limit equal to a small request.
  • Removing limits while requests are guesses.
  • Treating memory like CPU and leaving it unlimited.
  • Deciding without throttling metrics.

How to answer in the interview

"CPU is compressible, so requests already guarantee each container a proportional share through CFS weights when the node is busy. A CPU limit adds a hard quota, so the container is throttled even when the node is idle, which often hurts tail latency. That's why I usually set accurate requests and leave CPU limits off for latency-sensitive services. On the other side, limits give predictable performance, protect against runaway processes, are needed for Guaranteed QoS and exclusive cores with the static CPU manager, and may be required for multi-tenant chargeback. Memory is incompressible, so memory limits are always set."

Likely follow-up questions

  • How do you decide for one service? Compare throttled-period ratio and p99 latency with and without the limit under load tests.
  • What QoS class without CPU limits? Burstable.
  • Does removing limits hurt neighbours? Not if their requests are accurate, since weights protect them.
