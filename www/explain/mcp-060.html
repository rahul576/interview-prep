What is the lethal trifecta for AI agents, and how does it apply to MCP setups?

MCP Servers · concept · levels senior, lead

In one line

The lethal trifecta (Simon Willison) is an agent with access to private data, exposure to untrusted content and the ability to communicate externally; together they allow data exfiltration via prompt injection, so remove at least one leg per agent or session, or put human approval on the outbound channel.

Detailed explanation

Prompt injection on its own is a nuisance; prompt injection plus the right capabilities is a data breach. The trifecta names the three capabilities that, combined, make an agent exploitable:

  1. Private data: email, files, databases, internal documents, CRM records.
  2. Untrusted content: web pages, inbound email, public issues, user-submitted tickets, any text an attacker can influence.
  3. External communication: sending email, HTTP requests, creating public comments or PRs, writing to shared docs, even rendering an image whose URL encodes data.

When one agent has all three, the attack is simple: the attacker plants instructions in content the agent will read; the agent reads private data and sends it out. No system prompt reliably prevents it, because the model cannot be guaranteed to ignore instructions.

MCP makes the trifecta easy to assemble by accident. Each server looks harmless alone: a mail server, a browser server, a file server. Users add them to one host and suddenly one session holds all three legs. Some single servers already contain all three, for example a mail server that can read inbound mail, search the mailbox and send.

The defence is architectural: for each agent or session, remove at least one leg. A research agent that browses the web gets no private data. An internal-data agent gets no external channel. Where all three are genuinely needed, put human approval in front of the outbound channel and restrict destinations to an allowlist.

How it works

  1. Map each enabled server and tool to the three legs.
  2. Identify sessions or agent profiles where all three coexist.
  3. Remove a leg: drop a tool, split the agent, or sandbox outbound access.
  4. If you cannot, gate outbound actions with approval showing the full payload and destination.
  5. Block covert channels such as auto-loaded images and arbitrary URL fetches.

An email-triage assistant: keep read and search, replace send_email with create_draft so a human sends it. The external leg is gone.

Common mistakes

  • Assessing servers one by one instead of per session.
  • Forgetting covert channels such as markdown image URLs or link unfurling.
  • Assuming internal content is trusted; tickets and comments are often written by outsiders.
  • Approval prompts that hide the recipient or payload.

How to answer in the interview

"The lethal trifecta, a term popularised by Simon Willison, is three capabilities that together make an agent exploitable: access to private data, exposure to untrusted content like web pages or inbound emails, and the ability to communicate externally, like sending email, making HTTP requests or even rendering an image URL. With all three in one agent, an attacker can plant instructions in content that make the agent read private data and send it out, and no prompt reliably prevents that. With MCP it happens easily because users combine servers freely. The defence is architectural: remove at least one leg for each agent or session, or put human approval in front of the outbound channel."

Likely follow-up questions

  • Which leg for an email-triage assistant? External sending: drafts only, a human presses send; it loses full automation.
  • Is a web fetch tool external communication? Yes, the URL itself can carry data out.
  • What about read-only agents? Without an outbound channel the risk drops sharply, though answers can still be manipulated.
