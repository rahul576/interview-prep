How do you publish test results and code coverage in Azure Pipelines and enforce quality gates?

Azure DevOps & Pipelines · concept · levels entry, mid, senior

In one line

Publish results with PublishTestResults (JUnit, VSTest/TRX, NUnit, xUnit) and coverage with PublishCodeCoverageResults (Cobertura or JaCoCo), fail the build on test failures, add a SonarQube/SonarCloud quality gate focused on new code, and enforce it through branch policies (build validation and status checks).

Detailed explanation

Test results: test runners write standard report files: JUnit XML (Java, JavaScript, Python), TRX (VSTest/.NET), NUnit or xUnit formats. PublishTestResults@2 uploads them, giving the run a Tests tab with pass/fail counts, failure messages and stack traces, history per test, and flaky test detection. With failTaskOnFailedTests: true and the test task itself failing, the build fails on test failures. The DotNetCoreCLI test command publishes results automatically.

Code coverage: tools like Coverlet (.NET), JaCoCo (Java), Istanbul/nyc (JS) or coverage.py produce reports. PublishCodeCoverageResults@2 uploads Cobertura or JaCoCo output (v2 supports more formats) and shows a Code Coverage tab. For Azure Repos PRs, diff coverage can show coverage on changed lines and post a status, configured with an azurepipelines-coverage.yml file.

Quality gates: SonarQube (self-hosted) or SonarQube Cloud (formerly SonarCloud) analyses code for bugs, vulnerabilities, security hotspots, code smells, duplication and coverage. The pipeline uses Prepare, Analyze and Publish tasks; the quality gate result is reported back to the pipeline and as a PR decoration/status. The recommended "Sonar way" gate focuses on new code: no new issues, coverage on new code at least 80 percent, low duplication. That lets legacy codebases improve gradually instead of failing forever.

Enforcement: in Azure Repos, a build validation branch policy runs the pipeline on each PR; a status check policy requires the Sonar or coverage status to be green. PRs can't merge when tests fail or the gate is red.

How it works

  1. Tests run and write JUnit/TRX files.
  2. PublishTestResults uploads; failures fail the build.
  3. Coverage report published as Cobertura/JaCoCo.
  4. Sonar analysis evaluates the quality gate on new code.
  5. Branch policy requires build and status checks to pass.

Example

steps:
- task: SonarQubePrepare@7
  inputs: { SonarQube: sc-sonar, scannerMode: dotnet, projectKey: orders }
- script: dotnet test --logger trx --collect:"XPlat Code Coverage"
- task: PublishTestResults@2
  inputs: { testResultsFormat: VSTest, testResultsFiles: '**/*.trx', failTaskOnFailedTests: true }
- task: PublishCodeCoverageResults@2
  inputs: { summaryFileLocation: '**/coverage.cobertura.xml' }
- task: SonarQubeAnalyze@7
- task: SonarQubePublish@7
  inputs: { pollingTimeoutSec: '300' }

Common mistakes

  • Publishing results with condition: succeeded(), so failing runs show no results (use succeededOrFailed()).
  • Global coverage thresholds that legacy code can never meet.
  • Chasing coverage percentage with assertion-free tests.
  • Quality gate reported but not required by policy.

How to answer in the interview

"Test runners write JUnit or TRX files, and PublishTestResults uploads them so each run has a Tests tab with failures, history and flaky test detection; failed tests fail the build. Coverage from Coverlet, JaCoCo or similar is published as Cobertura or JaCoCo, including diff coverage on PRs. For broader gates I add SonarQube or SonarQube Cloud, whose quality gate checks new code for bugs, vulnerabilities, duplication and coverage. Branch policies with build validation and status checks then block a PR if tests fail or the gate is red. Gates focus on new code, so teams improve gradually."

Likely follow-up questions

  • Why is coverage alone weak? It shows lines executed, not that behaviour is asserted; mutation testing shows test strength.
  • Flaky tests? Detect, quarantine, fix; don't just rerun.
  • Publish results on failure? Use condition: succeededOrFailed().
