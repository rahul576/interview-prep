What is ThreadLocal, and what are its risks in thread pools and with virtual threads?

Concurrency · concept · levels senior, lead

In one line

ThreadLocal gives each thread its own value, used for request context, MDC and non-thread-safe helpers; in thread pools forgotten values leak memory and leak data between requests unless you call remove() in finally, with virtual threads per-thread copies multiply, and ScopedValue (final in Java 25) is the modern, immutable alternative.

Detailed explanation

A ThreadLocal<T> is a key into a map stored on each Thread object (threadLocals). get() looks up the current thread's entry, initialising it via withInitial if needed; set() and remove() change only the current thread's copy. Frameworks use it heavily: Spring's SecurityContextHolder and transaction synchronisation, the logging MDC (correlation ids in log lines), Hibernate sessions, and per-thread instances of non-thread-safe objects such as SimpleDateFormat.

Risks in thread pools. Pool threads live for the lifetime of the application. A value set during request A remains when the same thread serves request B. That causes:

  • Data leakage: request B sees A's user id or tenant, a security bug.
  • Memory leaks: large objects stay referenced. In application servers, a ThreadLocal value whose class comes from a web app's classloader pins the entire classloader after redeploy. ThreadLocalMap keys are weak, but values are strong.

The rule: set in try, remove() in finally, or use framework filters/interceptors that do it.

Async boundaries. ThreadLocal values don't follow work to other threads. With CompletableFuture or @Async, the MDC is empty unless you copy it, e.g. a Spring TaskDecorator or Micrometer context propagation. InheritableThreadLocal copies only at thread creation, which is wrong for pools.

Virtual threads. They support ThreadLocal, but with a million virtual threads, each holding its own copy of an expensive cached object, memory explodes, and the "cache an object per thread" trick no longer saves anything because threads aren't reused.

ScopedValue (JEP 506, final in Java 25) binds an immutable value for the dynamic scope of a call: ScopedValue.where(USER, u).run(() -> ...). It is automatically unbound when the scope exits, can't be mutated, is cheap to read, and is inherited by subtasks of structured concurrency.

How it works

  1. set(v): store (threadLocal → v) in the current thread's map.
  2. get(): read the current thread's entry.
  3. remove(): delete the entry.
  4. Without remove, the entry lives as long as the thread.

Example

private static final ThreadLocal<String> TENANT = new ThreadLocal<>();

void handle(Request req) {
    TENANT.set(req.tenant());
    MDC.put("traceId", req.traceId());
    try {
        service.process(req);
    } finally {
        TENANT.remove();          // prevents leaks between pooled requests
        MDC.clear();
    }
}

// Java 25+: ScopedValue
private static final ScopedValue<String> TENANT_SV = ScopedValue.newInstance();
ScopedValue.where(TENANT_SV, req.tenant()).run(() -> service.process(req));
// inside: TENANT_SV.get()

Common mistakes

  • Setting without removing in pooled threads.
  • Expecting ThreadLocal values in @Async or CompletableFuture callbacks.
  • Using InheritableThreadLocal with pools.
  • Caching heavyweight objects per virtual thread.

How to answer in the interview

"ThreadLocal gives each thread its own copy of a value, used for request context like the security context, the logging MDC, or non-thread-safe objects. The risk is that pool threads live a long time, so if I don't call remove in a finally block, values leak memory and stale data from one request can show up in the next, which can even be a security issue. Values also don't propagate to async threads automatically. With millions of virtual threads, heavy ThreadLocal use costs a lot of memory. ScopedValue, final since Java 25, is the immutable, scope-bounded alternative for passing context."

Likely follow-up questions

  • How does MDC reach async threads? Copy it with a TaskDecorator or context-propagation library when submitting the task.
  • Why are ThreadLocalMap keys weak? So an unreachable ThreadLocal can be collected; the value still leaks until cleanup or remove.
  • ScopedValue vs ThreadLocal? Immutable, bounded lifetime, cheaper, inherited by structured subtasks.
