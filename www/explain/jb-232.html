What is the difference between eventual consistency and strong consistency?

Microservices · concept · levels senior, lead

In one line

Strong consistency means every read sees the latest committed write, as if there were one copy; eventual consistency means replicas or services converge over time and reads may be stale meanwhile; CAP/PACELC explain the trade-off with availability and latency.

Detailed explanation

With strong consistency (in its strictest form, linearizability), once a write is acknowledged, every subsequent read anywhere returns it. A single relational database transaction gives you this; distributed systems achieve it with consensus (Raft in etcd, Spanner, CockroachDB) or synchronous replication with quorum reads, at the cost of latency and coordination.

With eventual consistency, updates propagate asynchronously: to database replicas, caches, search indexes or other microservices via events. For a while different readers can see different values, but if writes stop, all copies converge. In microservices this is the default between services, because each owns its own database and they communicate through events.

The CAP theorem says that during a network partition, a distributed system must choose between consistency (refuse or delay some requests) and availability (answer, possibly with stale data). PACELC adds the everyday case: Else, without a partition, you still trade latency for consistency, because confirming with remote replicas takes time. Many databases let you tune this per operation, for example Cassandra consistency levels or MongoDB read and write concerns. There are useful levels in between: read-your-writes, monotonic reads, causal consistency.

Choosing per use case: money movements, inventory reservation, unique usernames, seat booking need strong guarantees on the critical step, typically one owning service with a local ACID transaction. Feeds, like counts, recommendations, search indexes, analytics, notification status are fine with eventual consistency. Living with eventual consistency requires idempotent consumers, ordering by key, versioning to reject stale updates, compensations, and honest UX: show "Processing", update optimistically for the user who made the change, and avoid reading their own change from a lagging replica.

How it works

  1. Write commits to the primary or owning service.
  2. Strong: replicas confirm (quorum/consensus) before ack, or reads go to the primary.
  3. Eventual: ack immediately; replicate via log or events.
  4. Consumers apply updates idempotently; staleness window is seconds.
  5. UX and code handle the window (status, read-your-writes routing).

Example

// Strong: reserve stock in the owning service's ACID transaction
@Transactional
public void reserve(String sku, int qty) {
    int updated = jdbc.update(
        "UPDATE stock SET available = available - ? WHERE sku = ? AND available >= ?",
        qty, sku, qty);
    if (updated == 0) throw new OutOfStock(sku);
}

// Eventual: search index updated from events, may lag a few seconds
@KafkaListener(topics = "products.events", groupId = "search-indexer")
public void index(ProductUpdated e) { searchClient.upsert(e.id(), e.toDocument()); }

Common mistakes

  • Saying "eventually consistent" without stating the expected delay or handling it.
  • Requiring strong consistency everywhere and killing availability.
  • Reading from replicas right after a write and showing users stale data.
  • Misquoting CAP as "pick any two" without partitions in mind.

How to answer in the interview

"With strong consistency every read returns the latest committed write, as if there were one copy; a single database transaction gives that. With eventual consistency, updates propagate asynchronously to replicas or other services, so reads can be stale for a while, but all copies converge when writes stop. CAP says that during a partition you choose consistency or availability, and PACELC adds that even without one you trade latency for consistency. I keep strong consistency for things like payments and stock reservation inside one service, and accept eventual consistency for feeds, search and analytics, handling it with idempotent consumers, versioning and clear UI states."

Likely follow-up questions

  • How do you give read-your-writes in an eventually consistent system? Route the writer's reads to the primary for a short time, or return the updated state from the write itself.
  • What is linearizability? The strongest single-object consistency: operations appear instantaneous in real-time order.
  • How do you measure staleness? Consumer lag and replication lag metrics.
