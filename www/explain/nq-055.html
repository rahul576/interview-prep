How would you apply a 15% discount to products satisfying a specified condition?

Coding Exercises · scenario · levels mid

In one line

Multiply the price by 0.85 for products matching a condition: either filter then map to new objects (only discounted products), map with a conditional (whole list, discount where it applies), or forEach with setters if mutating existing objects is required; use BigDecimal for money.

Detailed explanation

The first step is to clarify the requirement, because there are three reasonable interpretations.

1. Return only the discounted products. filter(condition) selects the products, and map creates a new product with 85% of the price: p -> p.withPrice(p.price() * 0.85). The result list contains only discounted items.

2. Return the full list with discounts applied where the condition holds. Keep all products and decide per element inside map: condition.test(p) ? p.withPrice(p.price() * 0.85) : p. Untouched products are passed through as they are. This keeps objects immutable and the original list unchanged — usually the cleanest choice.

3. Update existing mutable objects in place. If products are, say, JPA entities that will be saved, the requirement is a side effect, so filter(condition).forEach(p -> p.setPrice(p.getPrice() * 0.85)) is appropriate. Everyone holding references to those objects sees the new price.

The condition should be a named Predicate<Product>, such as category equals "Electronics" or stock above 100, so it can be tested and reused.

Money. double is binary floating point; 19.99 * 0.85 is not exactly representable, and sums accumulate rounding errors. Production code uses BigDecimal with an explicit scale and rounding mode: price.multiply(new BigDecimal("0.85")).setScale(2, RoundingMode.HALF_UP), or integer minor units (cents/paise). Also extract 0.85 into a named constant like DISCOUNT_FACTOR, or compute 1 - discountRate.

How it works

  1. Define the condition as a Predicate.
  2. Choose the output: discounted subset, full list, or in-place update.
  3. Use filter + map, map with a conditional, or filter + forEach.
  4. Compute the new price with BigDecimal and rounding in real code.
  5. Collect or persist the result.

Example

record Product(String name, String category, BigDecimal price, int stock) {
    Product withPrice(BigDecimal p) { return new Product(name, category, p, stock); }
}

static final BigDecimal FACTOR = new BigDecimal("0.85");
Predicate<Product> isElectronics = p -> p.category().equals("Electronics");

UnaryOperator<Product> discount =
    p -> p.withPrice(p.price().multiply(FACTOR).setScale(2, RoundingMode.HALF_UP));

// 1. only discounted products
List<Product> onlyDiscounted = products.stream()
    .filter(isElectronics).map(discount).toList();

// 2. full list, discount where condition holds
List<Product> all = products.stream()
    .map(p -> isElectronics.test(p) ? discount.apply(p) : p).toList();

// 3. mutable entities, update in place
entities.stream().filter(e -> e.getCategory().equals("Electronics"))
    .forEach(e -> e.setPrice(e.getPrice().multiply(FACTOR).setScale(2, RoundingMode.HALF_UP)));

Common mistakes

  • Using double for prices in production code.
  • Mutating objects inside map and returning the same instance.
  • Writing price * 15 / 100 (the discount amount) instead of price * 0.85.
  • Not clarifying whether undiscounted products should remain in the result.

How to answer in the interview

"First I'd clarify whether I need only the discounted products or the whole list. For only discounted ones: filter by the condition, then map to a new product with price times 0.85. For the full list, I use a conditional inside map, returning a discounted copy when the condition holds and the original otherwise, which keeps everything immutable. If the requirement is to update existing mutable objects, like entities, I'd filter and then use forEach with setPrice. In production I'd use BigDecimal with an explicit rounding mode, because double gives rounding errors with money."

Likely follow-up questions

  • Why is double poor for prices? Binary floating point cannot represent most decimal fractions exactly, causing rounding errors.
  • Which RoundingMode? Usually HALF_UP or HALF_EVEN (banker's rounding), as the business specifies.
  • How do you test it? Assert exact BigDecimal results for matching and non-matching products.
