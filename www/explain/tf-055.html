What are the serial and lineage fields in Terraform state, and why do they matter?

Terraform · concept · levels mid, senior

In one line

Serial is a counter incremented on every state write; lineage is a unique ID assigned when a state is first created; Terraform and backends use them to refuse overwriting state with an older copy or an unrelated state, which matters most during state push and recovery.

Detailed explanation

A Terraform state file is JSON with a few header fields: version (format), terraform_version, serial, lineage and then the resources and outputs.

Lineage is a UUID generated when the state is created, for example on the first apply in a new backend key. It stays the same for the whole life of that state, across thousands of applies. It identifies "this particular state history".

Serial starts at 1 and increments every time Terraform writes a new version of the state. It orders versions within the same lineage.

Together they are safety checks. When Terraform writes state, for instance with terraform state push, it compares the incoming file with the current one. A different lineage means you are about to replace this configuration's state with a state from a completely different configuration or a re-created one, so Terraform refuses. A lower serial with the same lineage means you are about to overwrite newer state with an older copy, losing record of resources created in between, so it refuses as well.

These checks matter during recovery. If a state got corrupted and you restore a previous version from blob versioning or S3 versions, its serial is lower than the current one, so a push is rejected. You either bump the serial in a copy or use -force, but only after being completely sure it is the right file, because pushing the wrong state makes Terraform think real resources do not exist (it would try to create duplicates) or exist when they do not.

How it works

  1. First write: Terraform generates lineage and sets serial 1.
  2. Each apply or state command increments the serial.
  3. On push, Terraform compares lineage and serial with the remote state.
  4. Mismatched lineage or lower serial is rejected.
  5. -force bypasses the checks, intentionally and rarely.

Example

terraform state pull | jq '{serial, lineage, terraform_version}'
# { "serial": 412, "lineage": "6f1c2b9e-...", "terraform_version": "1.14.0" }

# Recovering an older version (serial 405): push is refused
terraform state push restored.tfstate
# Error: refused, because the pushed serial (405) is older than the current one (412)

# Only after verification:
terraform state push -force restored.tfstate
terraform plan   # confirm it matches reality

Common mistakes

  • Editing state JSON by hand and breaking the structure or checksums.
  • Using -force as a reflex when a push is rejected.
  • Copying a state file between environments and wondering why lineage differs.
  • Not running a plan immediately after a recovery push.

How to answer in the interview

"Every state has a serial, which increments on each write, and a lineage, a unique ID created with the state that never changes. Terraform uses them as safety checks: when pushing state, it refuses a lower serial or a different lineage, because that would overwrite newer state with an old copy or with an unrelated state. It matters in recovery, for example restoring a previous version after corruption: I may need to bump the serial or use -force, but only after verifying it's the right file, and I always run a plan afterwards."

Likely follow-up questions

  • Why avoid editing state JSON by hand? It is easy to break and bypasses all safety; use state commands, moved, import and removed blocks.
  • Where do previous versions come from? Backend versioning, such as blob versioning or S3 object versions.
  • Does HCP Terraform keep versions? Yes, every state version is stored and can be restored.
