What are BeanFactoryPostProcessor and BeanPostProcessor?

Spring Framework · concept · levels mid, senior

In one line

A BeanFactoryPostProcessor modifies bean definitions (metadata) before any bean is instantiated, for example PropertySourcesPlaceholderConfigurer; a BeanPostProcessor modifies or replaces bean instances around initialisation, for example AOP proxy creation and @Autowired processing.

Detailed explanation

Both are extension points of the container, but they work at different moments and on different things.

A BeanFactoryPostProcessor (BFPP) runs once, after all bean definitions are loaded and before any regular bean is created. It receives the ConfigurableListableBeanFactory and can read and change definitions: change a scope, set property values, mark beans lazy, or resolve placeholders. Examples: PropertySourcesPlaceholderConfigurer replaces ${...} placeholders with values from the Environment; ConfigurationClassPostProcessor parses @Configuration, @ComponentScan, @Import and @Bean. Its sub-interface BeanDefinitionRegistryPostProcessor can even register new definitions, which is how configuration classes and Spring Data repositories add beans.

A BeanPostProcessor (BPP) runs for every bean instance that is created, with two hooks: postProcessBeforeInitialization and postProcessAfterInitialization. It can modify the object or return a different object, typically a proxy. Examples: AutowiredAnnotationBeanPostProcessor processes @Autowired and @Value injection; CommonAnnotationBeanPostProcessor handles @PostConstruct, @PreDestroy and @Resource; AnnotationAwareAspectJAutoProxyCreator and related auto-proxy creators wrap beans for @Transactional, @Async, @Cacheable and aspects; ConfigurationPropertiesBindingPostProcessor binds @ConfigurationProperties.

Because BFPPs must exist before other beans, a @Bean method returning one should be static. Otherwise Spring must instantiate the enclosing configuration class early, which then misses BeanPostProcessor processing (such as @Autowired and @Value), and Spring logs a warning. Similarly, beans that a BPP depends on are created early and are not eligible for all post-processing.

How it works

  1. Load bean definitions.
  2. Instantiate and run BeanDefinitionRegistryPostProcessors, then BeanFactoryPostProcessors.
  3. Register BeanPostProcessors (instantiated early, ordered by PriorityOrdered/Ordered).
  4. Create regular beans; each passes through all BPP before/after hooks.
  5. BPPs may return proxies, which become the published beans.

Example

@Configuration
class InfraConfig {
    @Bean
    static BeanFactoryPostProcessor lazyReports() {      // static!
        return bf -> {
            for (String name : bf.getBeanNamesForType(ReportJob.class)) {
                bf.getBeanDefinition(name).setLazyInit(true);
            }
        };
    }
}

@Component
class TimingBeanPostProcessor implements BeanPostProcessor {
    public Object postProcessAfterInitialization(Object bean, String name) {
        if (bean.getClass().isAnnotationPresent(Timed.class)) {
            ProxyFactory pf = new ProxyFactory(bean);
            pf.addAdvice((MethodInterceptor) inv -> {
                long t = System.nanoTime();
                try { return inv.proceed(); }
                finally { log.info("{} took {} µs", name, (System.nanoTime() - t) / 1000); }
            });
            return pf.getProxy();
        }
        return bean;
    }
}

Common mistakes

  • Non-static @Bean methods for BFPPs.
  • Calling getBean() inside a BFPP, which instantiates beans too early.
  • Forgetting to return the bean from a BPP (returning null).
  • Heavy logic in BPPs that runs for every bean and slows startup.

How to answer in the interview

"Both are container extension points but act at different times. A BeanFactoryPostProcessor runs after definitions are loaded and before any bean is created, so it changes metadata: scope, property values or new definitions. PropertySourcesPlaceholderConfigurer and ConfigurationClassPostProcessor are examples. A BeanPostProcessor runs for each bean instance around initialisation, and it can return a different object, which is how Spring wraps beans in proxies for AOP, transactions and async. AutowiredAnnotationBeanPostProcessor and CommonAnnotationBeanPostProcessor handle @Autowired and @PostConstruct."

Likely follow-up questions

  • Why static @Bean for a BFPP? So the enclosing configuration isn't created too early and skips post-processing.
  • What is BeanDefinitionRegistryPostProcessor? A BFPP that can register new bean definitions.
  • How are BPPs ordered? PriorityOrdered, then Ordered, then the rest.
