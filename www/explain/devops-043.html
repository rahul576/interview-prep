How would you design a disaster recovery strategy for a critical service that must survive a full region outage?

Reliability & DR · design · levels senior, lead

In one line

Start from business-agreed RPO and RTO, choose a strategy (backup-restore, pilot light, warm standby, active-active) that meets them at acceptable cost, implement cross-region data replication, automated traffic failover via DNS or global load balancing, infrastructure as code for the second region, and prove it with regular DR drills.

Detailed explanation

RPO (recovery point objective) is how much data you can afford to lose (minutes of transactions); RTO (recovery time objective) is how long you can be down. They come from the business impact of the service and drive cost by orders of magnitude, so agree them first and per service, not one number for everything.

Strategies (from cheapest to most resilient):

  • Backup and restore: backups copied to another region; rebuild everything on disaster. RPO hours, RTO hours to a day.
  • Pilot light: data continuously replicated; minimal core infrastructure in the DR region, app tier off or tiny. RTO tens of minutes to hours.
  • Warm standby: a scaled-down but fully working copy running in the second region, ready to scale up. RTO minutes.
  • Active-active (multi-site): both regions serve production traffic; failure means routing everything to the survivor. Near-zero RTO, RPO depends on replication, highest cost and complexity.

Data is the hard part. Options: Aurora Global Database (storage-level replication, typically sub-second lag, managed failover), DynamoDB global tables (multi-active, last-writer-wins), Cosmos DB multi-region, cross-region read replicas, S3 Cross-Region Replication (with Replication Time Control for SLA), and backup copies in another region and ideally another account (protects against ransomware and account compromise). Asynchronous replication means RPO is non-zero; active-active needs conflict handling, idempotency and careful design for global uniqueness.

Traffic failover: Route 53 health checks with failover or latency routing, Azure Front Door, Cloudflare or AWS Global Accelerator. Keep DNS TTLs low and test that clients honour them.

Everything else: the DR region is built from the same Terraform/IaC and pipelines; secrets, certificates, container images, quotas and IAM must exist there too. Watch hidden regional dependencies: single-region SaaS, a control plane, an auth provider, or a CI system in the failed region.

Prove it: runbooks, automated failover where safe, regular DR drills and game days (including failing back), measuring actual RPO and RTO.

How it works

  1. Classify services and agree RPO/RTO with the business.
  2. Choose a strategy per tier.
  3. Replicate data cross-region; copy backups to an isolated account.
  4. Deploy the DR stack from IaC; keep artefacts and secrets replicated.
  5. Configure health-checked failover routing.
  6. Drill quarterly; fix gaps found.

Example

resource "aws_route53_record" "api_primary" {
  zone_id = var.zone_id
  name    = "api.example.com"
  type    = "A"
  set_identifier  = "primary-eu-west-1"
  failover_routing_policy { type = "PRIMARY" }
  health_check_id = aws_route53_health_check.api_euw1.id
  alias { name = module.alb_euw1.dns_name, zone_id = module.alb_euw1.zone_id, evaluate_target_health = true }
}

Common mistakes

  • Never testing failover, or never testing failback.
  • Backups in the same account and region as production.
  • Forgetting non-obvious dependencies (identity, CI, DNS, secrets).
  • Choosing active-active without solving data conflicts.

How to answer in the interview

"I start with the business: agree RPO and RTO, because they drive cost. Then I pick a strategy: backup and restore is cheapest with hours of RTO, pilot light keeps data replicated with minimal compute, warm standby runs a smaller ready copy, and active-active serves from both regions with near-zero RTO at the highest cost. Data needs cross-region replication, like Aurora Global Database, DynamoDB global tables or S3 replication, plus isolated backups. Traffic fails over with Route 53 health checks or a global load balancer. The second region is built from the same Terraform, and we run regular DR drills, because an untested plan isn't a plan."

Likely follow-up questions

  • Hardest problems in active-active? Write conflicts and consistency, global uniqueness, data residency, split-brain, and doubling operational complexity.
  • How do you protect against ransomware? Immutable, cross-account backups with object lock.
  • How often should you drill? At least quarterly for critical services, plus after major architecture changes.
