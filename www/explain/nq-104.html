How would you handle strings of different lengths?

DSA: Arrays & Strings · concept · levels entry

In one line

Strings of different lengths can never be anagrams, so a length check is a cheap early exit when comparing a pair; in the grouping solution they automatically get different keys, but remember that normalisation (removing spaces, punctuation, case) can change lengths, so normalise first.

Detailed explanation

An anagram uses exactly the same characters the same number of times, so the total character count must be equal. If a.length() != b.length(), you can return false immediately in O(1), skipping sorting or counting entirely. In real datasets many pairs differ in length, so this check removes a lot of work.

In the grouping solution, nothing special is needed. The key, whether sorted characters or a count signature, encodes the length implicitly: a sorted string of length 5 can never equal one of length 6, and counts summing to 5 differ from counts summing to 6. Words of different lengths therefore fall into different groups naturally. Adding an explicit length check there would be redundant.

The subtle case is normalisation. Phrase anagrams such as "dormitory" (9 characters) and "dirty room" (10 characters including the space) only match after removing the space. Similarly "Eleven plus two" and "Twelve plus one". If you check length on the raw strings, you would wrongly return false. The correct order is:

  1. normalise (lowercase, strip whitespace and punctuation per the rules);
  2. then compare lengths;
  3. then compare characters.

Unicode caveat: String.length() counts UTF-16 code units, not user-perceived characters. "é" may be one code unit (precomposed) or two (e + combining accent). If inputs can contain such text, apply java.text.Normalizer.normalize(s, Form.NFC) first so equivalent strings have equal lengths and characters.

Bucketing by length first is possible (map length → words, then group inside each bucket), but with hashing by signature it adds no asymptotic benefit; it might help in a brute-force pairwise approach or for distributing work.

How it works

  1. Normalise both strings according to the problem rules.
  2. Compare lengths; if different, return false.
  3. Otherwise compare via sorting or counting.
  4. In grouping, rely on the key to separate lengths.

Example

static String normalise(String s) {
    String n = java.text.Normalizer.normalize(s, java.text.Normalizer.Form.NFC);
    return n.toLowerCase(Locale.ROOT).replaceAll("[^\\p{L}\\p{N}]", "");   // keep letters/digits
}

static boolean isAnagram(String a, String b) {
    String x = normalise(a), y = normalise(b);
    if (x.length() != y.length()) return false;      // early exit AFTER normalising
    char[] p = x.toCharArray(), q = y.toCharArray();
    Arrays.sort(p); Arrays.sort(q);
    return Arrays.equals(p, q);
}

isAnagram("Dormitory", "dirty room");   // true  (9 vs 10 raw, 9 vs 9 normalised)
isAnagram("abc", "abcd");               // false (length)

Common mistakes

  • Checking length before removing spaces.
  • Adding redundant length checks in the grouping loop.
  • Assuming length() equals the number of visible characters.
  • Forgetting null or empty input handling.

How to answer in the interview

"Two strings of different lengths can never be anagrams, so when I compare a pair I check length first and return false straight away; it's a cheap early exit. In the grouping solution nothing special is needed, because words of different lengths produce different signatures and naturally land in different groups. The only subtlety is normalisation: if spaces or punctuation should be ignored, I remove them before the length check, because 'dormitory' and 'dirty room' only match after dropping the space."

Likely follow-up questions

  • Could you bucket by length first? Yes, but with signature hashing it adds nothing asymptotically.
  • What about Unicode? Normalise to NFC and consider code points rather than chars.
  • Should empty strings be anagrams of each other? By definition yes; confirm with the interviewer.
