How do you autoscale on custom or external metrics with the HPA, and how do you prevent flapping?

Kubernetes · concept · levels mid, senior

In one line

The autoscaling/v2 HPA scales on Resource, Pods, Object and External metrics; custom and external metrics come through an adapter such as Prometheus Adapter or KEDA. Scale on a business signal (RPS per pod, queue depth), and prevent flapping with the behavior field: stabilization windows and rate policies.

Detailed explanation

CPU utilisation is a poor signal for many services: an IO-bound API can be overloaded with low CPU, and a queue consumer's backlog says far more than its CPU. The HPA's v2 API supports four metric types:

  • Resource: CPU or memory per pod, as Utilization (percent of requests, so requests must be set) or AverageValue. ContainerResource targets one container, ignoring sidecars.
  • Pods: a per-pod custom metric averaged across pods, such as http_requests_per_second.
  • Object: a metric describing another object, such as requests on an Ingress.
  • External: a metric from outside the cluster, such as SQS queue length or Kafka lag.

The HPA reads Resource metrics from metrics-server (metrics.k8s.io) and custom/external metrics from APIs implemented by an adapter: Prometheus Adapter maps PromQL to custom.metrics.k8s.io, cloud adapters expose provider metrics, and KEDA serves external.metrics.k8s.io and manages HPAs itself. With several metrics, the HPA computes a desired replica count for each and uses the highest.

The basic formula is desired = ceil(current × currentValue / targetValue), within a 10% tolerance. Noisy metrics cause flapping: scaling up and down repeatedly, churning pods and caches. The behavior field controls this:

  • stabilizationWindowSeconds: for scale-down (default 300 s), the HPA uses the highest recommendation in the window, so brief dips don't remove pods; scale-up defaults to 0 s.
  • policies: limits like "add at most 100% or 4 pods per 60 s" and "remove at most 10% per minute", with selectPolicy Max, Min or Disabled.

Fast scale-up and slow scale-down is the usual shape.

How it works

  1. Adapter exposes the metric through the metrics API.
  2. HPA controller polls every 15 seconds by default.
  3. Computes desired replicas per metric; takes the maximum.
  4. Applies stabilisation and policies.
  5. Updates the target's scale subresource; the Deployment adjusts pods.

Example

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: api }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: api }
  minReplicas: 3
  maxReplicas: 50
  metrics:
  - type: Pods
    pods:
      metric: { name: http_requests_per_second }
      target: { type: AverageValue, averageValue: "100" }
  behavior:
    scaleUp:
      policies: [ { type: Percent, value: 100, periodSeconds: 60 } ]
    scaleDown:
      stabilizationWindowSeconds: 300
      policies: [ { type: Percent, value: 10, periodSeconds: 60 } ]

Common mistakes

  • Utilization targets with no CPU requests set (metric shows unknown).
  • Keeping replicas in the Deployment manifest so CI fights the HPA.
  • Scaling on a metric that doesn't fall when pods are added.
  • No scale-down stabilisation for spiky traffic.

How to answer in the interview

"The autoscaling/v2 HPA supports resource metrics like CPU, pods metrics averaged per pod, object metrics from another resource, and external metrics such as queue length. Custom and external metrics come through an adapter like Prometheus Adapter or KEDA. For IO-bound services I scale on requests per second per pod or queue depth rather than CPU. To prevent flapping I use the behavior field: a scale-down stabilisation window of a few minutes, policies capping how fast pods are added or removed, and faster scale-up than scale-down. Utilization targets need requests on every container."

Likely follow-up questions

  • Why does an HPA show unknown? Missing metrics-server or adapter, wrong metric name, no requests, or pods not ready yet.
  • Multiple metrics? The HPA takes the highest desired replica count.
  • Can the HPA scale to zero? Not by default; KEDA handles zero.
