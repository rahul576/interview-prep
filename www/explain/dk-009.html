What is the purpose of a .dockerignore file?

Docker · concept · levels entry

In one line

A .dockerignore excludes files from the build context sent to the builder, using .gitignore-like patterns, which makes builds faster, images smaller, prevents secrets and local junk from being copied by COPY . ., and avoids needless cache invalidation.

Detailed explanation

docker build . sends the build context, the directory you point at, to the builder (BuildKit). Without a .dockerignore, that means everything: the .git history, node_modules, target/ or build/ output, test reports, IDE folders, local .env files and perhaps SSH keys or credentials someone left in the project. BuildKit transfers files more efficiently than the old builder, but it still has to read and hash what instructions reference.

The file lives in the root of the context (or as <Dockerfile-name>.dockerignore next to a specific Dockerfile) and contains patterns:

  • node_modules, **/*.log, build/, .git
  • *.md with !README.md to re-include an exception
  • Comments start with #.

The syntax is close to .gitignore but uses Go's filepath matching with ** support; one notable difference is that patterns are relative to the context root.

Benefits:

  1. Speed: less data to transfer and hash, especially in remote builders and CI.
  2. Smaller, cleaner images: a broad COPY . . copies only what you intend.
  3. Security: secrets and .git (which may contain history with removed credentials, internal URLs and author emails) never enter a layer, where anyone with the image could extract them.
  4. Better caching: the cache key for a COPY depends on the content of the copied files. If .git or logs change on every commit and are not ignored, COPY . . and every following layer rebuild unnecessarily.
  5. Correctness: local node_modules built for macOS do not overwrite dependencies installed for Linux inside the image.

Some teams invert the approach: ignore everything () and whitelist only what is needed (!src, !package.json), which is safest.

How it works

  1. Builder reads .dockerignore before receiving the context.
  2. Matching paths are excluded from the context.
  3. COPY/ADD can only see files that remain.
  4. Cache checksums are computed only over included files.

Example

# .dockerignore
.git
.github
node_modules
dist
coverage
*.log
.env
.env.*
!.env.example
.idea
.vscode
Dockerfile*
docker-compose*.yml

Whitelist style:

*
!package.json
!package-lock.json
!src/
!tsconfig.json

Common mistakes

  • No .dockerignore, so .env with production credentials ends up in the image.
  • Ignoring files the build needs (e.g. a lockfile) and getting confusing failures.
  • Putting .dockerignore next to the Dockerfile when the context is a different directory.
  • Relying on .gitignore, which Docker does not read.

How to answer in the interview

"When I run docker build, the whole build context is sent to the builder. A .dockerignore lists patterns, similar to .gitignore, for files to exclude, like .git, node_modules, build output, local .env files and IDE settings. That makes builds faster because less data is transferred, keeps images smaller, stops secrets and local junk being copied in by a broad COPY . instruction, and avoids cache invalidation, because changes to ignored files no longer change the COPY layer. For sensitive projects I use a whitelist: ignore everything and include only what the build needs."

Likely follow-up questions

  • What could go wrong if .git is in a production image? Leaked history, removed secrets, internal info and a bigger image.
  • Does Docker read .gitignore? No, only .dockerignore.
  • Different ignore rules per Dockerfile? Use Dockerfile.name.dockerignore next to it (BuildKit).
