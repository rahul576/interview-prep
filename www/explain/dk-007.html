What is the difference between docker stop and docker kill?

Docker · concept · levels entry

In one line

docker stop shuts down gracefully: it sends SIGTERM (or the image's STOPSIGNAL), waits a grace period (10 s by default, -t to change), then sends SIGKILL; docker kill sends SIGKILL immediately (or any signal chosen with --signal).

Detailed explanation

A clean shutdown matters: a web server should stop accepting new connections, finish in-flight requests, a worker should finish or requeue its current job, and a database should flush to disk. SIGTERM is the polite request that lets the application do that; SIGKILL cannot be caught or ignored, so the process dies instantly with no cleanup.

docker stop name sends SIGTERM (or whatever STOPSIGNAL the Dockerfile defines, e.g. SIGQUIT for nginx's graceful shutdown) to the main process. It then waits up to the timeout: 10 seconds by default, configurable per command with -t 30 or per container with --stop-timeout. If the process is still alive, Docker sends SIGKILL. The container ends in the exited state with exit code 0 or 143 (128 + 15) if the app exited on SIGTERM, or 137 (128 + 9) if it had to be killed.

docker kill name sends SIGKILL by default, immediately. With --signal you can send others: docker kill --signal=SIGHUP web asks many daemons (nginx, HAProxy) to reload configuration without stopping, and SIGUSR1 may trigger log reopen or diagnostics depending on the app.

The common real-world problem: PID 1 ignores SIGTERM. Causes include shell-form CMD/ENTRYPOINT (sh is PID 1 and does not forward signals), entrypoint scripts without exec, or apps that do not install a handler (PID 1 gets no default signal behaviour from the kernel). Symptom: every docker stop takes exactly the timeout and ends with exit code 137. Fix with exec form, exec "$@", --init (tini), and a SIGTERM handler. Kubernetes behaves the same way with terminationGracePeriodSeconds (30 s default).

How it works

  1. docker stop → STOPSIGNAL (default SIGTERM) to PID 1.
  2. App drains and exits → container exited.
  3. Timeout reached → SIGKILL → exit code 137.
  4. docker kill → chosen signal immediately (default SIGKILL).

Example

docker stop -t 30 api            # allow 30 s for graceful shutdown
docker kill api                  # immediate SIGKILL
docker kill --signal=SIGHUP proxy  # reload config, keep running
docker inspect -f '{{.State.ExitCode}}' api
// Node.js: handle SIGTERM for graceful shutdown
process.on('SIGTERM', () => {
  server.close(() => process.exit(0));   // stop accepting, finish in-flight requests
  setTimeout(() => process.exit(1), 25000).unref();
});

Common mistakes

  • Using docker kill habitually and corrupting data or dropping requests.
  • Shell-form commands so SIGTERM never reaches the app.
  • Grace periods shorter than the app's real drain time.
  • Assuming SIGHUP stops a container; for many apps it means reload.

How to answer in the interview

"docker stop asks for a graceful shutdown: it sends SIGTERM to the main process, waits a grace period, 10 seconds by default and configurable with -t, and only then sends SIGKILL. That gives the app time to finish requests, close connections and flush data. docker kill sends SIGKILL immediately, so there's no cleanup, though with --signal I can send something else, like SIGHUP to reload config. I normally use stop and make sure the app actually handles SIGTERM; if every stop takes exactly 10 seconds and exits with 137, PID 1 is ignoring the signal, usually due to shell-form commands."

Likely follow-up questions

  • Why does stop take exactly 10 seconds? SIGTERM is ignored, so Docker waits for the timeout and SIGKILLs.
  • What do exit codes 137 and 143 mean? Killed by SIGKILL (137) vs terminated by SIGTERM (143).
  • What is STOPSIGNAL? A Dockerfile instruction that changes the signal docker stop sends.
