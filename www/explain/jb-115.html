How would you diagnose thread starvation in a production application?

Concurrency · scenario · levels senior, lead

In one line

Thread starvation shows as rising latency and queued work with low CPU; diagnose it with several thread dumps taken seconds apart plus pool metrics, looking for pool threads all BLOCKED/WAITING on the same resource, then fix the cause (blocking calls in small pools, nested waits, long locks).

Detailed explanation

Symptoms come first. Response times and timeouts climb, request or task queues grow, but CPU stays low: the work is not slow to compute, threads are stuck waiting. Health checks may fail because even they cannot get a thread. Garbage collection and the database may look fine.

Thread dumps are the main tool. Take three to five dumps 5-10 seconds apart with jcmd <pid> Thread.print or jstack <pid> (or the Spring Boot Actuator threaddump endpoint), so you can tell stuck threads from merely busy ones. Group threads by pool name (http-nio-8080-exec-, ForkJoinPool.commonPool-worker-, task-*) and by stack. If all 200 Tomcat threads sit in HikariPool.getConnection, the connection pool is the bottleneck. If all common-pool workers are WAITING in CompletableFuture.join, tasks are waiting on other tasks queued in the same pool: pool-induced deadlock. If many threads are BLOCKED on one monitor, find the holder's stack. Tools like fastThread or IntelliJ's dump analyser help group them. For virtual threads use jcmd <pid> Thread.dump_to_file -format=json.

Metrics confirm and quantify: with Micrometer, executor.active, executor.queued, executor.pool.size and rejected counts, Tomcat busy threads, and Hikari hikaricp.connections.pending. A pool permanently at max active with a growing queue is starved. JFR (Java Flight Recorder) shows thread park and monitor-blocked events with durations.

Common causes: blocking I/O on a small pool (or the common pool), nested submit-and-wait in the same bounded pool, long-held locks with slow calls inside, missing timeouts on HTTP or DB calls, unfair locks letting some threads always win, and one slow tenant consuming all threads. Fixes: timeouts everywhere, separate pools per workload (bulkheads), right-size pools against connection pools, avoid blocking inside async pools, move blocking work to dedicated executors or virtual threads.

How it works

  1. Notice symptoms: latency up, queues up, CPU low.
  2. Take several thread dumps a few seconds apart.
  3. Group by pool and identical stacks; find what they all wait on.
  4. Correlate with executor, Tomcat and connection-pool metrics and JFR.
  5. Identify root cause (resource, lock, nested wait, missing timeout).
  6. Fix and add alerts on pool saturation and queue depth.

Example

"http-nio-8080-exec-187" #212 daemon prio=5 WAITING (parking)
   at jdk.internal.misc.Unsafe.park
   at java.util.concurrent.locks.LockSupport.parkNanos
   at com.zaxxer.hikari.pool.HikariPool.getConnection(HikariPool.java:181)
   at com.example.OrderRepository.findOpen(OrderRepository.java:42)
-- 200 of 200 exec threads show this stack in all 4 dumps
-- hikaricp.connections.active = 10/10, pending = 190
for i in 1 2 3 4; do jcmd $(pgrep -f app.jar) Thread.print > dump_$i.txt; sleep 5; done
grep -h -A3 '"http-nio' dump_*.txt | grep 'at ' | sort | uniq -c | sort -rn | head

Common mistakes

  • Taking a single thread dump and drawing conclusions.
  • Simply increasing thread count, which just moves the queue to the connection pool.
  • Running blocking calls in ForkJoinPool.commonPool() via parallel streams or default supplyAsync.
  • No timeouts on outbound calls, so threads wait indefinitely.

How to answer in the interview

"Starvation shows up as rising latency and timeouts while CPU stays low, because work is queued but threads can't make progress. I take several thread dumps a few seconds apart with jcmd Thread.print and compare them. If all threads of one pool, say Tomcat or the ForkJoin common pool, are blocked or waiting on the same lock, socket read, connection pool or future, that's the bottleneck. I confirm with Micrometer metrics like active threads, queue size and rejections, and Hikari pending connections. Typical causes are blocking I/O in small pools, tasks waiting on other tasks in the same pool, long-held locks and missing timeouts, so fixes are separate pools, timeouts and proper sizing."

Likely follow-up questions

  • Why is calling join() on a CompletableFuture inside the common pool risky? The worker blocks waiting for a task that may be queued behind it in the same small pool, starving or deadlocking the pool.
  • What is a bulkhead? Isolating workloads in separate pools so one slow dependency cannot consume all threads.
  • How do you find the lock holder? Thread dumps show "waiting to lock <0x...>" and the thread with "locked <0x...>" for the same address.
