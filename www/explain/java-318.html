How does Spring Security work internally, and how do you secure methods?

Security · concept · levels mid, senior

In one line

Spring Security is a chain of servlet filters wired in through DelegatingFilterProxy and FilterChainProxy; authentication filters hand credentials to an AuthenticationManager/AuthenticationProvider, the result is stored in the SecurityContext, and AuthorizationFilter plus method security (@PreAuthorize) enforce access.

Detailed explanation

The servlet container knows nothing about Spring beans, so Spring registers a DelegatingFilterProxy that forwards to a bean called FilterChainProxy. That holds one or more SecurityFilterChain beans, each matching a set of requests, and each chain is an ordered list of filters: CSRF, CORS, logout, authentication filters (form login, HTTP Basic, BearerTokenAuthenticationFilter), exception translation and finally the AuthorizationFilter.

An authentication filter extracts credentials and creates an unauthenticated Authentication object. It passes this to the AuthenticationManager, usually a ProviderManager that iterates over AuthenticationProviders: DaoAuthenticationProvider loads the user through a UserDetailsService and checks the password with a PasswordEncoder, while JwtAuthenticationProvider uses a JwtDecoder. On success the authenticated principal with its GrantedAuthorities goes into the SecurityContext, held per request by SecurityContextHolder (thread-local by default) and, for session apps, saved through a SecurityContextRepository.

ExceptionTranslationFilter turns AuthenticationException into a 401 or login redirect and AccessDeniedException into 403. The AuthorizationFilter applies URL rules from authorizeHttpRequests with request matchers. For finer control, @EnableMethodSecurity activates AOP-based checks: @PreAuthorize and @PostAuthorize with SpEL expressions on service methods, which can check roles and ownership. Because it is proxy-based, self-invocation is not checked.

How it works

  1. Request enters DelegatingFilterProxy, then FilterChainProxy selects the matching SecurityFilterChain.
  2. An authentication filter builds an Authentication and calls the AuthenticationManager.
  3. A provider verifies it; the result is stored in the SecurityContext.
  4. AuthorizationFilter checks URL rules; failures go to ExceptionTranslationFilter.
  5. The controller calls a service; a method-security proxy evaluates @PreAuthorize.
  6. The context is cleared at the end of the request.

Example

@Configuration
@EnableMethodSecurity
class SecurityConfig {
    @Bean
    SecurityFilterChain api(HttpSecurity http) throws Exception {
        http.securityMatcher("/api/**")
            .authorizeHttpRequests(a -> a
                .requestMatchers("/api/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated())
            .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()));
        return http.build();
    }
}

@Service
class OrderService {
    @PreAuthorize("hasRole('ADMIN') or @orderSecurity.isOwner(#orderId, authentication.name)")
    public OrderDto get(long orderId) { ... }
}

Common mistakes

  • Relying only on URL rules and forgetting object-level checks.
  • Expecting @PreAuthorize to work on a private method or a call from the same class.
  • Assuming the SecurityContext is available in @Async threads without propagation.
  • Ordering request matchers so that a broad permitAll shadows a stricter rule.

How to answer in the interview

"Spring Security plugs into the servlet container as a filter, DelegatingFilterProxy, which delegates to FilterChainProxy and the SecurityFilterChain beans I configure. Authentication filters, say for JWT bearer tokens or form login, extract credentials and call the AuthenticationManager, whose providers check them, for example through a UserDetailsService and PasswordEncoder or a JwtDecoder. The authenticated principal goes into the SecurityContext. Then the AuthorizationFilter checks URL rules from authorizeHttpRequests, and ExceptionTranslationFilter turns failures into 401 or 403. For fine-grained rules I enable method security and put @PreAuthorize on service methods, including ownership checks."

Likely follow-up questions

  • How would you check that a user can only access their own orders? @PreAuthorize calling a bean method, or filter queries by the current user's id.
  • Can you have several filter chains? Yes, with securityMatcher and @Order, for example API versus web UI.
  • How is the context passed to async threads? DelegatingSecurityContextExecutor or a context-propagating task decorator.
