An API endpoint is slow only for some users. How do you investigate?

Troubleshooting · scenario · levels mid, senior

In one line

When only some users are slow, find what they have in common (data volume, tenant, region, plan, client version, feature flag), pull traces for their slow requests, and look for data-dependent causes such as unbounded queries, N+1 that scales with data, missing indexes for skewed data or cold caches; then reproduce with similar test data and fix with pagination, indexes or query changes.

Detailed explanation

If the code path is the same for everyone, the difference must be in the inputs or the environment of those users. The first job is segmentation.

Find the common factor: break latency down by attributes available in traces and logs: customer or tenant id, account age, number of orders or items, region or data centre, mobile app version, feature flags or A/B experiment, user role or permissions, language. Often the slow users are the power users: a business customer with 40,000 orders while most have twenty. Make sure useful attributes are on spans (but not as metric labels, which would explode cardinality).

Trace the slow requests: search the tracing backend for requests from affected users above a latency threshold and compare their span breakdown with a fast request. Typical findings:

  • Unbounded queries: findAllByCustomerId returns every order, then Java filters or maps them; memory and serialisation time grow with data.
  • N+1 queries whose count grows with the size of the user's collections.
  • Index and plan issues: a query fine for typical users scans many rows for a large tenant, or the planner picks a bad plan due to data skew or stale statistics; check EXPLAIN ANALYZE with that user's parameters.
  • Caching: rarely active users always hit a cold cache; a cache key that includes something user-specific; a cache entry too large to store.
  • Routing and region: users routed to a far region or a slow replica; replication lag; a different CDN edge.
  • Features: a flag enabling a new, slower code path for a cohort; permissions logic evaluating many roles.

Reproduce with a test account seeded with a similar data profile (anonymised copies of a large tenant), then fix: pagination or keyset pagination, limits on result sizes, indexes matching the access path, fetch plans or DTO projections, pre-computed aggregates, and cache warming for large accounts.

How it works

  1. Segment latency by user attributes to find the common factor.
  2. Retrieve traces of slow requests from affected users.
  3. Compare span breakdowns with fast requests.
  4. Run the slow query's plan with the affected user's parameters.
  5. Reproduce with similar data in a test environment.
  6. Fix, then monitor latency for that segment specifically.

Example

-- Typical user: 0.3 ms. Big tenant: 1.8 s
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE customer_id = 9001 ORDER BY created_at DESC;
--  Seq Scan on orders  (rows=41,250)  Sort Method: external merge  Disk: 52MB

CREATE INDEX CONCURRENTLY idx_orders_customer_created
    ON orders (customer_id, created_at DESC);
// Bounded, paginated access instead of loading everything
@Query("select new com.shop.OrderRow(o.id, o.total, o.createdAt) from Order o " +
       "where o.customer.id = :cid order by o.createdAt desc")
Slice<OrderRow> recentOrders(@Param("cid") Long customerId, Pageable page);

Common mistakes

  • Looking only at overall averages, where a slow minority disappears.
  • Testing with tiny datasets that never reveal data-dependent slowness.
  • Endpoints without any limit on result size.
  • Adding high-cardinality user ids as metric tags instead of span attributes.

How to answer in the interview

"When only some users are affected, I look for what they have in common: lots of data, a specific tenant or plan, a region, a client version or a feature flag. Then I pull traces of slow requests from those users and compare them with fast ones to see which span is slow. Very often it's data-dependent: an unbounded query returning thousands of rows, N+1 queries that scale with the user's data, or a query whose plan is bad for that data distribution. Caching can differ too, like a cold cache for rare users. I reproduce with a test account with a similar data profile and fix it with pagination, indexes or query changes."

Likely follow-up questions

  • How do you prevent unbounded result sets? Mandatory pagination with maximum page sizes, Slice or keyset pagination, and code review rules.
  • Why can one tenant get a bad query plan? Data skew; generic plans or statistics fit typical values, not outliers.
  • How do you test with realistic data? Anonymised production-shaped datasets or generators that create large tenants.
