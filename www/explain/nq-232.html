What happens if a database transaction succeeds but event publishing fails?

Microservices · scenario · levels senior, lead

In one line

That is the dual-write problem: the data is committed but other services are never notified, leaving the system inconsistent; the fix is the transactional outbox or CDC, backed by reconciliation jobs.

Detailed explanation

Imagine the order service commits an order and then calls kafkaTemplate.send(OrderCreated). The broker is unreachable, the send times out, or Kubernetes kills the pod a millisecond after commit. The order exists in the database, but payment never charges, inventory never reserves and the customer sees "pending" forever. Nothing throws an error that anybody sees, so the inconsistency is silent and is usually discovered by a customer complaint.

In-memory retries help only while the process is alive; a crash or redeploy loses them. Rolling back is impossible because the transaction is already committed. So the event has to be stored durably together with the data:

  • Transactional outbox: insert an outbox row in the same transaction; a relay publishes it later with retries.
  • Change data capture: Debezium reads the database log and publishes changes, so anything committed is eventually published.
  • Event sourcing: the event is the record; there is no separate state to get out of sync.
  • Listen to yourself: publish the event first and have the service update its own database from the event, accepting that its own read is eventually consistent.

On top of any of these, a reconciliation job is a safety net: find orders that have been PENDING longer than expected, republish their event or alert someone. Monitoring the age of unpublished outbox rows catches relay problems early.

How it works

  1. Business change and event are written atomically (outbox) or captured from the log (CDC).
  2. Relay publishes asynchronously, retrying until acknowledged.
  3. Consumers process idempotently, since retries cause duplicates.
  4. Explicit states (PENDING, CONFIRMED) plus timeouts show stuck flows.
  5. Reconciliation job republishes or escalates stuck records.

Example

// Risky: dual write
@Transactional
public void place(Order o) {
    repo.save(o);
    kafka.send("orders", o.id(), new OrderCreated(o)); // may be lost
}

// Safe: outbox
@Transactional
public void placeSafely(Order o) {
    repo.save(o);
    outbox.save(OutboxEvent.of("OrderCreated", o));
}

Common mistakes

  • Relying on in-memory retry loops.
  • Catching the send exception and only logging it.
  • Assuming @Transactional covers Kafka.
  • No monitoring for records stuck in intermediate states.

How to answer in the interview

"That's the classic dual-write problem. The order is committed but the event never reaches Kafka, perhaps because the broker was down or the pod crashed just after commit. Downstream services never react, so no payment and no stock reservation, and the order stays pending; the worst part is that it's silent. In-memory retries die with the process, so the real fix is a transactional outbox or CDC with Debezium, which stores the event atomically with the data and publishes it reliably later. I'd also add a reconciliation job that finds stuck orders and republishes or alerts, and make consumers idempotent because the retries will create duplicates."

Likely follow-up questions

  • And what if the event is published but the transaction rolls back? Consumers act on an order that doesn't exist; the outbox prevents this because the event only exists after commit.
  • Why not 2PC? Poor support in brokers, blocking behaviour and coupling to coordinator availability.
  • How would you detect the problem in production? Metrics on orders stuck in PENDING and outbox lag alerts.
