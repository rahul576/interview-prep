What is database replication? Explain primary-replica architecture.

Databases & SQL · concept · levels senior, lead

In one line

Replication keeps copies of data on several servers; in a primary-replica setup the primary takes all writes and streams its change log (WAL/binlog) to replicas that serve reads and can be promoted on failover, with synchronous vs asynchronous replication trading safety against latency and causing replication lag.

Detailed explanation

The primary records every change in its log: the WAL in PostgreSQL, the binlog in MySQL, redo logs in Oracle (Data Guard). Replicas receive that stream and replay it, ending up with the same data. PostgreSQL streaming replication is physical (byte-level); logical replication and MySQL row-based binlog replication ship row changes, which also enables replicating subsets or across versions.

Benefits:

  • Read scaling: send reports, searches and read-heavy endpoints to replicas.
  • High availability: if the primary fails, a replica is promoted, by tools such as Patroni, Orchestrator, or managed services (RDS Multi-AZ, Aurora, Cloud SQL).
  • Backups and analytics can run on a replica without loading the primary.

Asynchronous replication (the common default) commits on the primary immediately; replicas lag by milliseconds to seconds under load. It is fast, but if the primary dies, recently committed transactions not yet shipped can be lost. Synchronous replication makes the commit wait until at least one replica confirms (PostgreSQL synchronous_commit with synchronous_standby_names, MySQL semi-synchronous replication), protecting data at the cost of write latency and the risk of stalls if replicas are unavailable.

Lag creates the read-your-writes problem: a user saves a profile, the next request reads from a replica, and the old value appears. Solutions include reading from the primary for a short time after a write, routing the session's reads to the primary, or waiting for the replica to reach a given log position. Replication is not a backup: an accidental DELETE replicates instantly.

How it works

  1. Client writes go to the primary, which writes the WAL/binlog.
  2. Replicas connect and stream the log continuously.
  3. Replicas apply changes and serve read-only queries.
  4. The app routes reads to replicas and writes to the primary.
  5. Health checks detect primary failure; the most up-to-date replica is promoted.
  6. Clients reconnect via DNS, a virtual IP or a proxy.

Example

// Spring Boot: route read-only transactions to a replica
public class RoutingDataSource extends AbstractRoutingDataSource {
    @Override protected Object determineCurrentLookupKey() {
        return TransactionSynchronizationManager.isCurrentTransactionReadOnly()
               ? "replica" : "primary";
    }
}
// Wrap it in LazyConnectionDataSourceProxy so the read-only flag is known
// before a connection is taken.

@Transactional(readOnly = true)
public List<Order> history(long customerId) { return repo.findByCustomerId(customerId); }
-- PostgreSQL: check lag on the primary
SELECT client_addr, state, replay_lag FROM pg_stat_replication;

Common mistakes

  • Treating replicas as backups.
  • Ignoring lag and showing users stale data straight after they save.
  • Running heavy long queries on a hot-standby replica that conflict with replay.
  • Failing over without fencing the old primary, causing split brain.

How to answer in the interview

"Replication keeps copies of data on multiple servers. In primary-replica, one primary handles all writes and streams its change log, the WAL in Postgres or binlog in MySQL, to replicas that apply it and serve reads. That scales reads and gives high availability, since a replica can be promoted on failover. Asynchronous replication is fast but has lag, and you can lose the last few transactions on failure; synchronous waits for a replica, which is safer but slower. In the application I route read-only transactions to replicas, but for read-your-writes cases, like right after a user updates something, I read from the primary."

Likely follow-up questions

  • How to route reads to replicas in Spring Boot? AbstractRoutingDataSource keyed on read-only transactions, with LazyConnectionDataSourceProxy.
  • What is split brain? Two nodes both acting as primary after a failover; prevented by fencing and consensus-based failover.
  • Is replication a backup? No; deletes and corruption replicate too. You still need point-in-time recovery backups.
