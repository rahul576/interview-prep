What is garbage collection, and why is it needed?

JVM & Performance · concept · levels entry

In one line

Garbage collection is the JVM automatically reclaiming memory of unreachable objects: starting from GC roots (stack variables, static fields, active threads) it marks reachable objects and reclaims the rest by sweeping, copying or compacting; it prevents dangling pointers, double frees and most leaks, at the cost of some CPU and pauses.

Detailed explanation

The problem it solves. Programs allocate memory continuously. In languages with manual memory management (C, C++ without smart pointers), the programmer must call free. Freeing too early causes dangling pointers and crashes or security holes; freeing twice corrupts memory; forgetting to free leaks it. These bugs are hard to find and responsible for many security vulnerabilities. Java removes them: you cannot free memory yourself, and the JVM guarantees an object is reclaimed only when no code can reach it any more.

How reachability works. The collector starts from GC roots: local variables and parameters in all thread stacks, static fields of loaded classes, live threads, JNI references and JVM internals. It follows every reference, marking reachable objects. Anything unmarked is garbage, including unreachable cycles of objects that point to each other.

Reclaiming memory. Three basic techniques, combined differently by each collector:

  • Mark-sweep: free unmarked objects in place; fast, but leaves fragmentation.
  • Copying: move live objects to a fresh area; ideal for the young generation where few survive.
  • Mark-compact: slide live objects together to eliminate fragmentation; used for old generations.

Generations and concurrency. Because most objects die young, collectors use generations to focus effort. Modern collectors (G1, ZGC, Shenandoah) do much of their work concurrently with the application, keeping stop-the-world pauses short: G1 targets around 200 ms or lower by configuration, ZGC usually stays under a millisecond.

Costs. GC uses CPU, adds pauses, and needs spare memory headroom to work efficiently. These are tuned through heap size, collector choice and, most effectively, by reducing allocation.

Logical leaks still exist. GC frees unreachable objects only. Objects that are unused but still referenced, for example in a static map, an unbounded cache, a listener list or a ThreadLocal, stay in memory forever, eventually causing OutOfMemoryError.

How it works

  1. Allocation pressure triggers a collection.
  2. The collector identifies GC roots.
  3. It marks every object reachable from the roots.
  4. Unmarked objects are reclaimed by sweeping, copying or compaction.
  5. The application continues with freed memory.

Example

void handle(Request r) {
    Report rep = new Report(r);   // reachable via local variable
    send(rep);
}                                 // after return, rep unreachable -> garbage

// Logical leak: reachable forever through a static field
static final Map<String, Session> SESSIONS = new HashMap<>();
void login(User u) { SESSIONS.put(UUID.randomUUID().toString(), new Session(u)); } // never removed
java -Xlog:gc -jar app.jar   # watch collections happen

Common mistakes

  • Saying Java cannot have memory leaks.
  • Believing setting references to null everywhere is necessary.
  • Thinking GC uses reference counting and cannot handle cycles.
  • Relying on System.gc() or finalize().

How to answer in the interview

"Garbage collection is the JVM automatically freeing memory used by objects that are no longer reachable. Starting from GC roots, such as local variables on thread stacks, static fields and active threads, the collector marks every object it can reach; anything not marked is garbage, and its memory is reclaimed by sweeping, copying or compacting. It's needed because programs allocate continuously, and manual freeing, as in C, causes dangling pointers, double frees and leaks. GC makes Java memory-safe and productive at the cost of CPU and pauses, which modern collectors keep short. You can still have logical leaks when unused objects stay referenced, for example in a static map."

Likely follow-up questions

  • How can a Java application still leak memory? By keeping references to unused objects in static collections, caches without eviction, listeners or ThreadLocals.
  • Can circular references prevent collection? No; tracing collectors reclaim unreachable cycles.
  • What is a stop-the-world pause? A phase where all application threads are halted so the collector can work safely.
