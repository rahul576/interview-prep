What causes a deadlock, and how do you prevent and diagnose one in production?

Concurrency · concept · levels senior, lead

In one line

A deadlock needs all four Coffman conditions, mutual exclusion, hold and wait, no preemption, circular wait; prevent it mainly with a global lock ordering, short critical sections and tryLock with timeout, and diagnose it with thread dumps (jstack, jcmd Thread.print) or ThreadMXBean.findDeadlockedThreads.

Detailed explanation

A deadlock occurs when a set of threads each hold a resource and wait for one held by another, so none can proceed. Coffman's four conditions must all hold:

  1. Mutual exclusion: a lock can be held by one thread.
  2. Hold and wait: a thread holds one lock while requesting another.
  3. No preemption: locks can't be forcibly taken away.
  4. Circular wait: A waits for B's lock while B waits for A's.

Break any one and deadlock is impossible. Circular wait is the practical target. The classic example is a money transfer that locks from then to: transfer(A, B) and transfer(B, A) running together lock in opposite orders. A global lock ordering, for example always locking the account with the lower id first, removes the cycle.

Other prevention techniques: keep critical sections small; don't call external or overridable code (listeners, callbacks, remote calls) while holding a lock, because you can't know which locks it takes; prefer higher-level concurrency (ConcurrentHashMap, queues, immutability) over nested locks. With ReentrantLock, tryLock(timeout) breaks hold-and-wait: if the second lock isn't available, release the first, back off with jitter and retry. Deadlocks also happen with database row locks and with pool tasks waiting on other tasks queued in the same full pool (thread-starvation deadlock).

Diagnosis. Symptoms are requests that hang with low CPU. Take a thread dump with jcmd <pid> Thread.print or jstack <pid>. The JVM detects monitor and java.util.concurrent lock cycles and prints "Found one Java-level deadlock" with each thread, the lock it holds and the lock it waits for. Programmatically, ThreadMXBean.findDeadlockedThreads() can feed a health check.

How it works

  1. Thread A locks L1, Thread B locks L2.
  2. A requests L2 (held by B) and blocks.
  3. B requests L1 (held by A) and blocks: cycle.
  4. Fix: both acquire L1 before L2, so one waits without holding L2.

Example

void transfer(Account from, Account to, long amount) {
    Account first  = from.id() < to.id() ? from : to;   // global ordering
    Account second = first == from ? to : from;
    synchronized (first) {
        synchronized (second) {
            from.debit(amount);
            to.credit(amount);
        }
    }
}
jcmd 4242 Thread.print | grep -A 20 "Found one Java-level deadlock"

Common mistakes

  • Calling callbacks or remote services while holding a lock.
  • Lock ordering by hashCode without a tie-breaker.
  • Using tryLock without releasing the first lock on failure.

How to answer in the interview

"A deadlock needs four conditions: mutual exclusion, hold and wait, no preemption and circular wait, for example thread A holds lock 1 and wants lock 2 while B holds lock 2 and wants lock 1. The most practical prevention is a global lock ordering, so every thread acquires locks in the same order, plus small critical sections and never calling external code while holding a lock. With ReentrantLock I can use tryLock with a timeout and back off. To diagnose, I take a thread dump with jcmd Thread.print or jstack; the JVM reports 'Found one Java-level deadlock' and shows who holds and waits for what. ThreadMXBean.findDeadlockedThreads can detect it for monitoring."

Likely follow-up questions

  • Livelock vs deadlock? In a livelock threads keep running and reacting to each other but make no progress; add randomised back-off.
  • What is starvation? A thread never gets the resource because others always win; fairness can help.
  • Can virtual threads deadlock? Yes, deadlock is a logic problem independent of thread type.
