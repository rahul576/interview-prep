How do you configure a Kubernetes Job for reliability: retries, parallelism, failure handling and cleanup?

Kubernetes · concept · levels entry, mid, senior

In one line

A reliable Job sets completions and parallelism (optionally Indexed mode), limits retries with backoffLimit (or backoffLimitPerIndex), caps runtime with activeDeadlineSeconds, classifies failures with a podFailurePolicy, cleans up with ttlSecondsAfterFinished, and does idempotent work because pods can run more than once.

Detailed explanation

A Job runs pods until a target number of them succeed. completions is how many successful pods are needed; parallelism is how many run at once. With completionMode: Indexed, each pod gets a stable index (JOB_COMPLETION_INDEX env var) from 0 to completions-1, ideal for sharded work: pod 7 processes shard 7. Without completions, a Job is a work queue: pods pull items until the queue is empty.

Retries: failed pods are recreated with exponential backoff (10 s, 20 s, 40 s… capped at six minutes). backoffLimit (default 6) is the number of failures before the whole Job fails. For indexed Jobs, backoffLimitPerIndex retries each index independently so one bad shard doesn't fail all the others. restartPolicy in the template must be Never or OnFailure; with OnFailure, the kubelet restarts containers in place, and with Never, new pods are created, keeping failed pods for debugging.

Time limits: activeDeadlineSeconds terminates the Job and its pods once exceeded, regardless of retries, so a hung job can't run forever.

podFailurePolicy distinguishes failure types by container exit code or pod condition:

  • FailJob on an exit code that means a permanent error (bad config, invalid input), avoiding pointless retries.
  • Ignore failures caused by disruption (DisruptionTarget condition, for example preemption or node drain) so they don't consume backoffLimit.
  • Count for normal failures.

Cleanup: ttlSecondsAfterFinished lets the TTL controller delete the finished Job and its pods after a delay, avoiding thousands of leftover objects.

Idempotency: a pod can be retried, and in rare cases two pods can run for the same index (for example when a node becomes unreachable), so work must tolerate reruns: upserts, checkpoints, or output written atomically by key.

How it works

  1. Job controller creates up to parallelism pods.
  2. Each success counts towards completions (or marks its index done).
  3. Failures are matched against podFailurePolicy rules.
  4. Counted failures are retried with backoff until backoffLimit.
  5. Deadline exceeded or limit hit → Job Failed; else Complete.
  6. TTL controller deletes the Job later.

Example

apiVersion: batch/v1
kind: Job
metadata: { name: reindex }
spec:
  completions: 50
  parallelism: 10
  completionMode: Indexed
  backoffLimitPerIndex: 3
  activeDeadlineSeconds: 7200
  ttlSecondsAfterFinished: 86400
  podFailurePolicy:
    rules:
    - action: FailJob
      onExitCodes: { containerName: worker, operator: In, values: [42] }
    - action: Ignore
      onPodConditions: [ { type: DisruptionTarget } ]
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: worker
        image: registry.example.com/reindex:1.3
        args: ["--shard=$(JOB_COMPLETION_INDEX)", "--shards=50"]

Common mistakes

  • No activeDeadlineSeconds, so a hung Job runs for days.
  • Retrying permanent errors six times.
  • Non-idempotent work that double-charges or duplicates on rerun.
  • Finished Jobs never cleaned up, cluttering the API.

How to answer in the interview

"A Job runs pods until a number of completions succeed, with parallelism controlling concurrency, and Indexed mode gives each pod a shard index. backoffLimit caps retries, which use exponential backoff, and activeDeadlineSeconds caps total runtime. A podFailurePolicy lets me fail fast on exit codes that mean a permanent error, and ignore failures caused by disruption like node drains so they don't burn the retry budget. ttlSecondsAfterFinished cleans up finished Jobs. Because pods can be retried or even run twice, the work must be idempotent."

Likely follow-up questions

  • One million items with 50 workers? Indexed Job with 50 or more shards, or a queue with 50 parallel consumers; checkpoint progress.
  • OnFailure vs Never? OnFailure restarts in place; Never creates new pods and keeps failed ones for logs.
  • What is a successPolicy? Lets an indexed Job succeed when specific indexes or a count succeed, for leader-worker patterns.
