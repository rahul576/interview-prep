Kubernetes nodes are going NotReady. How do you troubleshoot it?

Troubleshooting · scenario · levels mid, senior

In one line

Use kubectl describe node to read conditions and events, check pressure conditions (memory, disk, PID), then the kubelet and containerd on the node, CNI and API server connectivity, and the cloud instance health; usually cordon, drain and replace the node first, then investigate.

Detailed explanation

A node becomes NotReady when the control plane stops receiving healthy status from its kubelet. The node controller marks the Ready condition Unknown if heartbeats stop, or False if the kubelet reports a problem.

Conditions and events. kubectl describe node shows MemoryPressure, DiskPressure, PIDPressure and NetworkUnavailable, plus the reason and last heartbeat time. DiskPressure is common: images, container logs and emptyDir volumes fill the root or image filesystem. MemoryPressure often comes from pods without memory limits or system daemons. PIDPressure comes from fork bombs or thread leaks.

Kubelet and runtime. If the status says "Kubelet stopped posting node status", log in via SSH, the cloud serial console, or kubectl debug node/<name> if it is still reachable. Check systemctl status kubelet containerd and read journalctl -u kubelet. Typical findings: the kubelet crashed, the container runtime hangs, expired kubelet certificates, or the node is out of memory so system processes are killed.

Network. A broken CNI plugin (for example the Cilium or Calico agent failing) sets NetworkUnavailable or the runtime network not ready; lost connectivity to the API server (security group, route or DNS change) stops heartbeats entirely.

Cloud level. Instance status checks, host maintenance events, spot instance reclamation, or the VM being stopped.

For production, the fastest safe action is usually to cordon and drain (or let it be evicted) and have the node replaced by the autoscaler or node pool, then investigate with logs. If many nodes go NotReady at once, suspect something shared: a network change, a CNI upgrade or a control-plane problem.

How it works

  1. kubectl get nodes and describe node for conditions and events.
  2. Check pressure conditions and resource usage.
  3. On the node, check kubelet and containerd status and logs.
  4. Check CNI pods on that node and API server connectivity.
  5. Check cloud instance health and events.
  6. Cordon, drain, replace; then root cause.

Example

kubectl describe node aks-apps-123 | sed -n '/Conditions/,/Addresses/p'
kubectl get pods -n kube-system -o wide --field-selector spec.nodeName=aks-apps-123
kubectl debug node/aks-apps-123 -it --image=busybox -- chroot /host sh
  systemctl status kubelet containerd
  journalctl -u kubelet --since "30 min ago" | tail -50
  df -h /var/lib/containerd
kubectl cordon aks-apps-123 && kubectl drain aks-apps-123 --ignore-daemonsets --delete-emptydir-data

Common mistakes

  • Debugging one node when many are affected by a shared cause.
  • Leaving a NotReady node in service instead of draining it.
  • Pods without memory limits or ephemeral storage limits causing pressure.
  • Ignoring log rotation and image garbage collection settings.

How to answer in the interview

"I start with kubectl get nodes and describe node to see conditions and events. If memory, disk or PID pressure is true, the node is short of resources, often a full disk from images and logs, or pods without memory limits. If the kubelet stopped posting status, I check on the node itself whether kubelet and containerd are running and read journalctl for kubelet. CNI failures or lost connectivity to the API server also cause NotReady, and at cloud level I check instance health and events. Usually the fastest safe action is to cordon and drain the node and let the autoscaler replace it, then investigate."

Likely follow-up questions

  • What happens to pods on a node that stays NotReady? After the default 300-second toleration for not-ready/unreachable taints, they are evicted and recreated elsewhere.
  • Why do StatefulSet pods take longer to move? Kubernetes will not create a replacement until it is sure the old pod is gone, to avoid two writers.
  • How do you prevent DiskPressure? Log rotation, image GC thresholds, ephemeral-storage limits and larger OS disks.
