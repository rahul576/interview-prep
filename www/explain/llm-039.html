Users report that the RAG assistant often retrieves irrelevant chunks. How do you debug and fix it?

LLMOps & RAG · scenario · levels mid, senior

In one line

Debug with evidence: collect failing queries, inspect retrieved chunks versus the expected document, then fix the actual cause, which is usually parsing or chunking, an embedding model mismatch, missing hybrid search or reranking, missing metadata filters or query rewriting, and lock it in with a retrieval test set measuring recall.

Detailed explanation

"Retrieval is bad" is a symptom with many causes, and guessing (switching vector databases, tweaking top-k) wastes weeks. Start by building a list of failing queries from feedback, logs and support tickets, and for each one note which document should have been found. Then look at what was retrieved and at the chunk of the expected document.

Typical findings:

  • Parsing: scrambled text from multi-column PDFs, repeated headers and footers dominating chunks, tables broken apart.
  • Chunking: chunks too small to carry meaning ("See section 4.2."), too large and mixing topics, or missing context such as the document title and heading.
  • Embeddings: a general English model on domain jargon, product codes or other languages; query and document embedded inconsistently (some models expect query/document prefixes).
  • Lexical misses: pure vector search ignores exact terms like ERR-4021 or SKU numbers; hybrid search (BM25 plus vectors, fused with reciprocal rank fusion) fixes this.
  • Noisy ranking: the right chunk is at position 15; a cross-encoder reranker over the top 50 lifts it.
  • Missing filters: the answer depends on region, product or version, so add metadata filters or let a query-understanding step extract them.
  • Conversational follow-ups: "and for Germany?" must be rewritten into a standalone query using chat history.

How it works

  1. Gather 50-200 failing and typical queries with expected documents.
  2. Measure baseline recall@k and MRR.
  3. Classify failures by cause.
  4. Change one thing at a time; re-measure.
  5. Add the set to CI so regressions are caught.

Example

def recall_at_k(testset, k=5):
    hits = 0
    for q in testset:                     # {"query": ..., "expected_doc": ...}
        docs = [c.doc_id for c in search(q["query"], top_k=k)]
        hits += q["expected_doc"] in docs
    return hits / len(testset)

print("vector only", recall_at_k(ts))    # e.g. 0.62
print("hybrid+rerank", recall_at_k(ts))  # e.g. 0.84

Common mistakes

  • Tuning the prompt when the context is already wrong.
  • Changing several components at once, so you cannot tell what helped.
  • No ground-truth set, only anecdotes.
  • Never reading the actual chunks.

How to answer in the interview

"I start from evidence: collect failing queries, note which document should have come back, and inspect what was retrieved. The causes are usually visible quickly: broken parsing, bad chunk boundaries, an embedding model that doesn't understand our jargon or language, pure vector search missing exact codes, noisy ranking, missing metadata filters, or follow-up questions that weren't rewritten. Then I fix with hybrid search, a reranker, better chunking, filters or query rewriting, one change at a time, measured against a retrieval test set using recall at k. That test set then runs in CI."

Likely follow-up questions

  • Preventing regressions as documents grow? Retrieval tests in CI and on each re-index; monitor score distributions.
  • Choosing an embedding model? Benchmark candidates on your own query set, not only public leaderboards.
  • Reranker cost? Limit candidates to about 20-50; use a small cross-encoder.
