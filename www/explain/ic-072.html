How would you offer self-service infrastructure to development teams safely?

Infrastructure as Code · design · levels senior

In one line

A platform team offers curated modules or templates with secure defaults through a self-service interface (Backstage templates, AWS Service Catalog, or a documented PR workflow), protected by policy-as-code guardrails, with owner, tags and budget on every request and maintained, versioned modules that teams upgrade with automation.

Detailed explanation

Developers want infrastructure in minutes, not after a ticket queue; security and finance want consistency and control. Self-service resolves the tension by moving control from manual approval to code: the safe way becomes the easy way.

Curated building blocks. The platform team publishes a small catalogue of high-level modules matching real needs, such as "service with Postgres, queue and dashboards", "static website", "bucket for internal data". Each encodes encryption, private networking, backups, logging, alarms and tagging, and exposes few inputs (size, name, environment). Fewer, opinionated options are better than wrapping every argument.

Interface. Options, from simple to elaborate:

  • A PR-based workflow: copy an example, fill in inputs, open a pull request; the normal pipeline plans and applies.
  • Backstage software templates that ask a few questions and generate that pull request automatically, also registering the component and owner in the catalogue.
  • AWS Service Catalog, HCP Terraform no-code modules or Crossplane compositions exposing resources as APIs.

Generating pull requests keeps review, plan visibility and audit history.

Guardrails, not gates. Policy as code (OPA, Sentinel, Checkov) blocks public buckets, unencrypted storage, oversized instances in dev or missing tags. Anything inside the rules merges without platform involvement; exceptions go through a documented process.

Ownership and cost. Every request records an owning team, tags and a budget, so there are no orphan resources and showback works. Lifecycle: the platform team versions modules, publishes changelogs, and Renovate-style automation opens upgrade PRs in consumer repositories.

How it works

  1. Developer picks "Service with Postgres" in Backstage and enters name, team, size.
  2. Template opens a PR in the team's live repo with a pinned module call.
  3. Pipeline runs plan, policy and cost checks; team lead approves.
  4. Merge applies; outputs (endpoints, secret names) are published to the catalogue.
  5. Later module releases arrive as automated upgrade PRs.

Example

# Backstage template (excerpt)
parameters:
  - title: Service database
    properties:
      name: { type: string, pattern: "^[a-z][a-z0-9-]{2,20}$" }
      size: { type: string, enum: [small, medium, large] }
      owner: { type: string, ui:field: OwnerPicker }
steps:
  - id: pr
    action: publish:github:pull-request
    input:
      repoUrl: github.com?owner=acme&repo=infra-live
      title: "Add database ${{ parameters.name }}"

Common mistakes

  • Self-service that bypasses review and the pipeline entirely.
  • Modules so flexible they are just thin wrappers.
  • No owner, so nobody decommissions resources.
  • Platform team approving every request manually.

How to answer in the interview

"The platform team maintains a small catalogue of curated modules, like a service with database and dashboards or a static website, each with secure defaults built in. Developers request them through a Backstage template or Service Catalog that generates a pull request with the module call, or just a documented PR workflow, so everything still goes through review and the normal pipeline. Policy as code guardrails catch anything outside the rules, so the platform team isn't approving each request. Every request has an owner, tags and a budget, and module upgrades arrive as automated PRs."

Likely follow-up questions

  • How do you avoid the platform team becoming a bottleneck? Guardrails instead of approvals, good docs, and inner-source contributions to modules.
  • What if a team needs something not in the catalogue? Raw resources under the same policies, and a path to promote common patterns into modules.
  • How do you measure success? Time to provision, self-service share and policy violations.
