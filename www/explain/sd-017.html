How does database replication work, and what are the trade-offs of each approach?

Data & Storage Design · concept · levels entry, mid, senior

In one line

Replication copies data to multiple nodes: leader-follower (simple, read scaling), multi-leader (multi-region writes, conflicts) or leaderless (quorums). The key trade-off is synchronous vs asynchronous: durability versus latency.

Detailed explanation

Leader-follower: the leader takes all writes and streams its log (WAL/binlog) to followers. Followers serve reads and can be promoted. With asynchronous replication, writes are fast but followers lag, so replica reads can be stale, and a failover can lose the last few writes. Synchronous (or semi-sync, one follower confirms) prevents loss but adds latency and can block if the follower is slow.

Multi-leader: each region has a leader; writes are local and fast, but two regions can update the same row concurrently, so you need conflict resolution (last-writer-wins, merge functions, CRDTs).

Leaderless (Dynamo-style): client writes to W of N replicas and reads from R; with R + W > N, reads overlap the latest write. Repair happens via read repair and anti-entropy.

How it works

  1. Leader appends change to its log.
  2. Followers pull/receive and apply it.
  3. Sync mode: commit waits for follower ack; async: commit returns immediately.
  4. Failure detection triggers promotion of the most up-to-date follower.
  5. Clients/proxies are redirected to the new leader.

Example

PostgreSQL in the cloud: primary in zone A, a synchronous standby in zone B (no data loss on zone failure), plus two asynchronous read replicas for reporting. After a user updates their profile, their reads go to the primary for a few seconds to guarantee read-your-writes.

Common mistakes

  • Reading from async replicas for data the user just wrote.
  • Assuming failover is instant and lossless with async replication.
  • Multi-leader without a conflict strategy.
  • Split brain: two leaders after a partition (needs fencing/quorum).

How to answer in the interview

"I'd use leader-follower: one synchronous standby in another zone so committed data survives a zone loss, plus async replicas for read scaling. Because async replicas lag, users get read-your-writes by reading from the primary right after their own writes. Multi-region writes would need multi-leader or a leaderless store, which brings conflict resolution I'd only accept where the data tolerates it."

Likely follow-up questions

  • How do you detect replication lag? Monitor replica LSN/seconds-behind; route away from lagging replicas.
  • What is split brain? Two nodes accepting writes as leader; prevented with quorum and fencing.
  • What's semi-synchronous? Wait for at least one follower ack, not all.
