How should an MCP tool handle large results, such as 50,000 log lines or rows?

MCP Servers · concept · levels mid, senior

In one line

Never dump huge results into the model context: give tools filter parameters, paginate with limit and cursor (reporting the total), summarise or aggregate server-side, and when the full data is needed, store it as a resource and return a resource link with a short summary.

Detailed explanation

Returning 50,000 log lines or rows to the model is harmful in every way. It wastes tokens and money, can exceed the context window or host limits, pushes useful context out, slows responses, and the model reasons worse over a wall of data than over a focused answer. Large raw output can also carry prompt-injection payloads and sensitive data into the context.

Good tools return small, useful outputs by default:

Filtering parameters let the model narrow the search: time range, severity, service, status, customer, a search term. Encourage their use in the description ("always provide a time range").

Pagination: limit (with a sensible default and hard maximum) and an opaque cursor; the result includes how many items exist in total and a next_cursor, so the model knows whether to refine or page.

Server-side summarisation and aggregation: rather than raw rows, return counts by type, top N, percentiles or time buckets, plus a few representative examples. "2,412 errors: 1,800 timeouts (mostly payment-gateway), 612 HTTP 5xx; 3 sample lines below" is far more useful than the lines themselves.

Resource links for full data: when the user genuinely needs everything, an export or a full log, the tool writes the result to storage, exposes it as a resource (e.g. exports://query/8f2c.csv) and returns a resource link plus summary. The host or user can fetch or download it separately without it entering the model's context.

Finally, tell the model about truncation explicitly ("showing 50 of 2,412; refine with severity or use next_cursor"), otherwise it may assume it saw everything.

How it works

  1. Validate filters; enforce a time range or limit.
  2. Query with the limit pushed down to the data source.
  3. Aggregate and pick representative samples.
  4. If full data is requested, write it to storage and register a resource.
  5. Return summary, samples, total, truncation note, next_cursor and/or resource link.

Example

@mcp.tool()
def search_logs(service: str, start: datetime, end: datetime,
                level: Literal["error", "warn", "info"] = "error",
                query: str | None = None, limit: int = 50, cursor: str | None = None) -> dict:
    """Search logs for one service in a time range (max 24 h). Returns counts and up to `limit` lines."""
    limit = min(limit, 200)
    res = logs.search(service, start, end, level, query, limit, cursor)
    out = {"total": res.total,
           "by_message": res.top_messages(10),
           "lines": [l.short() for l in res.lines],
           "next_cursor": res.next_cursor,
           "note": f"Showing {len(res.lines)} of {res.total}. Narrow with `query` or page with next_cursor."}
    if res.total > 5000:
        uri = exports.save(res.stream_all(), fmt="ndjson")
        out["full_export"] = uri          # also returned as a resource_link block
    return out

Common mistakes

  • No default limit, so one call returns megabytes.
  • Silent truncation that makes the model think it saw everything.
  • Returning raw JSON with every field instead of short lines.
  • Paging through 50,000 rows into context instead of aggregating.

How to answer in the interview

"I never dump huge results into the context: it wastes tokens, pushes out useful context, slows everything and the model handles a focused answer better. Tools take filters like time range, severity and a search term so the model can narrow down, and paginate with limit and cursor, reporting the total. Where possible they aggregate server-side, counts by error type plus a few examples, instead of raw rows. When the full data is really needed, the tool stores it as a resource and returns a resource link with a summary, so the user can fetch it separately. And results always say clearly when they're truncated."

Likely follow-up questions

  • How do you tell the model results were truncated? An explicit note with shown versus total, and how to refine or page.
  • What sizes are reasonable? A few thousand tokens per result at most; measure in evals.
  • Can the model analyse the full data? Via code execution in a sandbox that reads the resource, returning only conclusions.
