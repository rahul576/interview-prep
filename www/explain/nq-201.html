How does a transaction commit or roll back?

Spring Framework · concept · levels mid

In one line

The transactional proxy commits on normal return (JPA flushes first), rolls back when an unchecked exception or Error escapes, commits on checked exceptions unless rollbackFor, commits if you swallow the exception unless you call setRollbackOnly(), and throws UnexpectedRollbackException if an inner participant marked the transaction rollback-only.

Detailed explanation

The decision is made by the TransactionInterceptor when the method finishes, based only on what it can see: did the method return, or did an exception come out?

Commit path. If the method returns normally, the interceptor calls commit() on the transaction manager. With JPA, Hibernate first flushes the persistence context: it runs dirty checking and sends pending INSERT, UPDATE and DELETE statements to the database. Constraint violations can therefore appear at commit, after your method's last line. Then the database COMMIT makes the changes durable and visible to others, and after-commit callbacks run.

Rollback path. If a RuntimeException or Error escapes, the interceptor calls rollback(); the database discards all changes from this transaction and the persistence context is cleared. A checked exception escaping commits by default, unless it matches rollbackFor.

Swallowed exceptions. If you catch an exception inside the transactional method and don't rethrow, the proxy sees a normal return and commits, potentially saving half of the work. If you need to handle the error but still roll back, call TransactionAspectSupport.currentTransactionStatus().setRollbackOnly() (or status.setRollbackOnly() inside a TransactionTemplate).

Rollback-only and UnexpectedRollbackException. With REQUIRED propagation, an inner transactional method in another bean participates in the outer transaction. If it throws a runtime exception, its interceptor cannot roll back the shared physical transaction alone, so it marks it rollback-only. If the outer method catches the exception and returns normally, the outer commit finds the flag, rolls back instead, and throws UnexpectedRollbackException to tell the caller the commit didn't happen.

How it works

  1. Method completes or throws.
  2. Normal return: flush, then commit; check for rollback-only flag first.
  3. Exception: evaluate rollback rules.
  4. Outermost transaction: physical rollback; participant: mark rollback-only.
  5. Rethrow the original exception to the caller.

Example

@Transactional
public void register(User u) {
    userRepo.save(u);
    try {
        mailService.sendWelcome(u);           // @Transactional REQUIRED, throws
    } catch (MailException e) {
        log.warn("mail failed");              // outer commit -> UnexpectedRollbackException
    }
}

@Transactional
public void importPrices(List<Price> prices) {
    try {
        prices.forEach(priceRepo::save);
        validator.check(prices);
    } catch (ValidationException e) {
        TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
        report.add(e);                        // handled, but nothing is committed
    }
}

Common mistakes

  • Swallowing exceptions and committing partial data.
  • Catching an inner REQUIRED failure and being surprised by UnexpectedRollbackException.
  • Assuming the database is updated as each save() runs (writes happen at flush).
  • Not expecting constraint errors at commit time.

How to answer in the interview

"The proxy wraps the call. If the method returns normally it commits; with JPA, Hibernate flushes pending changes as SQL first, then the database commit makes them durable. If an unchecked exception or Error escapes, it rolls back; a checked exception commits unless rollbackFor includes it. If I catch and swallow an exception, the proxy never sees it and commits, unless I call setRollbackOnly. And if an inner REQUIRED method marked the transaction rollback-only, the outer commit fails with UnexpectedRollbackException."

Likely follow-up questions

  • What causes UnexpectedRollbackException? A participant marked the shared transaction rollback-only but the outer method tried to commit.
  • Force a flush earlier? saveAndFlush() or entityManager.flush() to detect errors inside the method.
  • Make the inner failure harmless? Use REQUIRES_NEW or noRollbackFor for that exception.
