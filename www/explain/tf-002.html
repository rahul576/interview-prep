What does the removed block do, and when would you use it instead of terraform state rm?

Terraform · concept · levels mid, senior

In one line

A removed block (Terraform 1.7+) declaratively tells Terraform to stop managing a resource or module; with lifecycle { destroy = false } the real object is kept and only forgotten from state, and the change is planned and reviewed, unlike the manual terraform state rm.

Detailed explanation

Sometimes you need Terraform to forget a resource without destroying it: handing a database over to another team's configuration, splitting a monolithic state, moving a resource to a different tool, or leaving a legacy object in place while the code is deleted. If you simply delete the resource block, Terraform plans to destroy the object, which can be a disaster.

Before 1.7 the only option was terraform state rm <address>. That works, but it is an imperative, manual operation: someone runs it against one state, there is no plan to review and no record in Git, and if the configuration is used by several workspaces or environments, each one needs the same command run by hand. Forget one, and the next pipeline run there destroys the resource.

The removed block makes this declarative. You delete the resource block and add removed { from = aws_db_instance.legacy lifecycle { destroy = false } }. The plan shows the resource "will no longer be managed by Terraform", reviewers see it in the pull request, and the pipeline applies the same change consistently to every environment. With destroy = true the block would destroy the object instead, which documents intentional destruction. The from address can be a whole module, and it refers to a resource, not a specific instance key. Since 1.9, removed blocks can also contain destroy-time provisioners.

Together with import and moved blocks, removed completes the set of declarative state operations, so routine state manipulation rarely needs CLI commands.

How it works

  1. Delete the resource or module block from configuration.
  2. Add a removed block with from and destroy = false.
  3. Plan: confirm "will no longer be managed" and no destroy.
  4. Merge and apply in every environment.
  5. If another configuration should take over, add an import block there.
  6. Remove the removed block once all states are updated.

Example

# The shared database moves to the platform team's configuration
removed {
  from = module.legacy_db

  lifecycle {
    destroy = false
  }
}
# In the platform team's configuration
import {
  to = aws_db_instance.shared
  id = "orders-prod"
}

Common mistakes

  • Deleting the resource block without a removed block, and destroying production.
  • Forgetting destroy = false.
  • Not importing into the new owner's state, leaving the object unmanaged.
  • Using state rm in one workspace and forgetting others.

How to answer in the interview

"The removed block, added in Terraform 1.7, lets me stop managing a resource or module without touching state by hand. I delete the resource from configuration and add a removed block with from set to its address and lifecycle destroy = false, so the real object stays and is only forgotten from state. The plan shows 'will no longer be managed', it's reviewed in the pull request and applied the same way in every environment. terraform state rm does the same but manually, against one state, with no record. I use removed when handing resources to another state or team, then add an import block on the other side."

Likely follow-up questions

  • How do you move a resource between state files without destroying it? Removed with destroy = false in the source, import block in the target.
  • What do moved blocks do? Rename an address within the same state.
  • Can removed target one instance of a for_each? No, from refers to the whole resource or module.
