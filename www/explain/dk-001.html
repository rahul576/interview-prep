What states can a Docker container be in during its lifecycle?

Docker · concept · levels entry

In one line

A container moves through created → running ⇄ paused → exited (stopped) → removed, with restarting (and rarely dead) as extra states; docker run = create + start, stop/start/restart move between states, and an exited container keeps its filesystem and logs until docker rm.

Detailed explanation

Created: docker create pulls the image if needed, sets up the writable layer, networking config and mounts, but does not start the process. Useful when you want to copy files in first (docker cp) or start it later. docker run does create and start in one step.

Running: the container's main process (PID 1) is executing. The container lives exactly as long as that process: when it exits, the container exits, even if other processes were started with exec.

Paused: docker pause freezes all processes using the cgroup freezer; they keep their memory but get no CPU. docker unpause resumes. Rarely used outside snapshots or debugging.

Exited (stopped): the main process finished on its own, crashed, or was stopped with docker stop (SIGTERM, then SIGKILL after the timeout) or docker kill. The container still exists: its writable layer, configuration, exit code and logs remain, so you can inspect it, copy files out, or docker start it again with the same configuration and data.

Restarting: a restart policy is bringing it back after it exited. Removing and dead are transient or error states (dead means removal failed).

Removed: docker rm deletes the container and its writable layer for good; docker run --rm removes it automatically on exit. Named volumes survive.

docker ps lists running containers; docker ps -a lists all, with status such as Exited (137) 2 minutes ago.

How it works

  1. docker create → created.
  2. docker start → running.
  3. docker pause / unpause → paused / running.
  4. Process exits or docker stop → exited (exit code recorded).
  5. docker start → running again; docker rm → gone.

Example

docker create --name web nginx:1.27       # created
docker start web                          # running
docker pause web && docker unpause web    # paused, then running
docker stop web                           # exited (0)
docker ps -a --filter name=web --format '{{.Names}} {{.Status}}'
docker inspect -f '{{.State.Status}} exit={{.State.ExitCode}} oom={{.State.OOMKilled}}' web
docker logs web                           # logs still available
docker start web                          # back to running, same writable layer
docker rm -f web                          # removed

Common mistakes

  • Thinking a stopped container has lost its data (it has not until it is removed).
  • Accumulating hundreds of exited containers by never using --rm or pruning.
  • Expecting a container to keep running after its main process exits.
  • Confusing pause (frozen) with stop (process terminated).

How to answer in the interview

"A container starts as created, for example with docker create, which prepares its filesystem and config without starting it; docker run creates and starts in one step. While its main process runs it's running, and docker pause freezes it. When the main process ends, or I run docker stop, it becomes exited and keeps its writable layer, logs and exit code, so docker start can bring it back. Only docker rm deletes it. docker ps shows running containers and docker ps -a shows everything, including exit codes, which is the first clue when something crashed."

Likely follow-up questions

  • Where do you see why a container exited? docker ps -a exit code, docker logs, docker inspect State (OOMKilled, Error).
  • Why does my container exit immediately? The main process finished, e.g. a service started in the background or a command that just completes.
  • What does --rm do? Removes the container automatically when it exits.
