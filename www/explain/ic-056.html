How do you perform rolling updates with Ansible?

Configuration Management · concept · levels mid

In one line

Use serial to update hosts in batches, take each host out of the load balancer with delegate_to, update it, health-check it before putting it back, stop with max_fail_percentage, and use run_once for once-per-rollout steps like migrations.

Detailed explanation

By default Ansible runs each task on all hosts in parallel (limited by forks), which for an application deployment means every server restarts at roughly the same time. serial changes the play so that all tasks run on one batch before the next batch starts. It accepts a number, a percentage or a list, for example [1, "25%", "100%"], giving a natural canary: one host first, then a quarter, then the rest.

Inside each batch the pattern is drain, update, verify, restore. pre_tasks remove the host from the load balancer. Because that API call must run on the load balancer or the control node rather than on the web server, the task uses delegate_to. The update runs, then post_tasks wait for the application: wait_for on the port and uri with until/retries against a health endpoint. Only a healthy host goes back into the pool.

Failure handling is crucial. max_fail_percentage aborts the play when more than the given share of a batch fails, so the remaining hosts stay on the old, working version. any_errors_fatal: true is stricter: any failure stops everything. run_once (often with delegate_to) runs a task a single time, for example a backward-compatible database migration in the first batch. Connection draining time should match the longest request, and application changes must tolerate old and new versions running side by side.

How it works

  1. Play has serial: [1, "25%", "100%"] and max_fail_percentage: 0.
  2. Pre-task: disable host in the load balancer (delegated), wait for connections to drain.
  3. Tasks: deploy the new version and restart the service.
  4. Post-task: wait for port and health endpoint to pass.
  5. Post-task: re-enable the host in the load balancer.
  6. Next batch starts; a failure stops the rollout.

Example

- hosts: web
  serial: [1, "25%", "100%"]
  max_fail_percentage: 0
  pre_tasks:
    - name: Drain from HAProxy
      community.general.haproxy:
        state: disabled
        host: "{{ inventory_hostname }}"
        backend: app
        drain: true
      delegate_to: "{{ item }}"
      loop: "{{ groups['lb'] }}"
  roles:
    - app_deploy
  post_tasks:
    - name: Wait for health
      ansible.builtin.uri:
        url: "http://{{ inventory_hostname }}:8080/health"
      register: h
      until: h.status == 200
      retries: 20
      delay: 5
      delegate_to: localhost
    - name: Back into pool
      community.general.haproxy:
        state: enabled
        host: "{{ inventory_hostname }}"
        backend: app
      delegate_to: "{{ item }}"
      loop: "{{ groups['lb'] }}"

Common mistakes

  • Forgetting delegate_to, so the LB call runs on the web host.
  • Health checks that only test the port, not the application.
  • No failure threshold, so a broken release rolls through the whole fleet.
  • run_once tasks that are not backward compatible with hosts still on the old version.

How to answer in the interview

"I use serial so the play runs in batches, often a list like one host, then 25 percent, then the rest, which gives me a canary for free. For each batch, pre-tasks drain the host from the load balancer using delegate_to so the call runs on the LB or control node, then the role deploys, and post-tasks wait for the health endpoint with uri and retries before re-enabling the host. max_fail_percentage stops the rollout if a batch fails, leaving the rest on the old version, and one-off steps like migrations use run_once."

Likely follow-up questions

  • How would you canary on one host first? serial: [1, ...] or a separate play with --limit canary and a pause or approval.
  • serial vs throttle? serial batches the whole play; throttle limits concurrency of a single task.
  • What about forks? It caps parallel connections overall; serial defines batch membership.
