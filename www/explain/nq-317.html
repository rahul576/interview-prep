How do SQS visibility timeouts and message delays affect processing?

Cloud (AWS) · concept · levels mid

In one line

The visibility timeout hides a message after it is received; if not deleted in time it reappears: too short causes duplicate parallel processing, too long delays retries; for Lambda set it to about six times the function timeout and extend it with ChangeMessageVisibility for long work. Message delays (delay queues or DelaySeconds, up to 15 minutes) postpone first delivery, useful for backoff and deferred checks.

Detailed explanation

Visibility timeout (default 30 seconds, up to 12 hours) starts when a consumer receives a message. During it, other consumers cannot see the message. Outcomes:

  • Consumer deletes it in time: done.
  • Consumer fails or crashes: after the timeout, the message reappears and is retried; ApproximateReceiveCount increases and the DLQ policy may apply.
  • Processing takes longer than the timeout: the message reappears while still being processed, and a second consumer processes it in parallel, causing duplicates.

So set it above the realistic maximum processing time. For Lambda, AWS recommends at least six times the function timeout, to cover retries when invocations are throttled. For long or variable work, consumers send a heartbeat with ChangeMessageVisibility to extend it. You can also set it to a short value on purpose in a failure handler to retry sooner, or longer for backoff.

Delays affect messages before first delivery:

  • Delay queue: a queue-level DelaySeconds applying to all new messages.
  • Per-message timers: DelaySeconds on SendMessage for standard queues (FIFO supports only queue-level delay).
  • Maximum 15 minutes.

Uses: deferring work ("check payment status in 5 minutes"), smoothing bursts, and exponential backoff by re-sending a failed message with an increasing delay and an attempt counter attribute. Longer schedules need EventBridge Scheduler or Step Functions.

How it works

  1. Message sent, optionally with a delay.
  2. After the delay, it becomes available.
  3. Consumer receives it; visibility timeout starts.
  4. Delete on success, or extend visibility while working.
  5. If the timeout expires, it reappears for retry.
  6. Exceeding maxReceiveCount sends it to the DLQ.

Example

// Backoff on failure: re-send with growing delay, then delete the original
int attempt = Integer.parseInt(attrs.getOrDefault("attempt", "0")) + 1;
int delay = Math.min(900, (int) Math.pow(2, attempt) * 10);   // 20s, 40s, 80s ... cap 15 min
sqs.sendMessage(b -> b.queueUrl(url).messageBody(body).delaySeconds(delay)
    .messageAttributes(Map.of("attempt", MessageAttributeValue.builder()
        .dataType("Number").stringValue(String.valueOf(attempt)).build())));
sqs.deleteMessage(b -> b.queueUrl(url).receiptHandle(receiptHandle));

Common mistakes

  • Default 30-second timeout for multi-minute processing.
  • Very long timeouts making failed messages wait hours.
  • Per-message delays on FIFO queues (not supported).
  • Unlimited re-send loops without an attempt cap.

How to answer in the interview

"The visibility timeout is how long a message stays hidden after a consumer receives it. If the consumer deletes it in time, it's gone; otherwise it reappears and may be processed again. If it's shorter than processing time, messages are processed twice in parallel; if it's very long, failed messages wait a long time before retry. For Lambda, AWS recommends about six times the function timeout, and long-running consumers can extend it with ChangeMessageVisibility. Delays, via a delay queue or DelaySeconds up to fifteen minutes, hide a new message before first delivery, which is useful for backoff or checking a status later."

Likely follow-up questions

  • Exponential backoff with SQS? Re-send with increasing DelaySeconds and an attempt counter, or change visibility on failure.
  • Delays longer than 15 minutes? EventBridge Scheduler or Step Functions wait states.
  • What is ApproximateReceiveCount? How many times a message has been received; drives DLQ redrive.
