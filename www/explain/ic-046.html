How do you validate inputs and assumptions in Terraform?

Infrastructure as Code · concept · levels mid

In one line

Use strong types (objects with optional attributes), variable validation blocks with clear error_message, preconditions/postconditions on resources, data sources and outputs, and check blocks for non-blocking assertions, so failures happen early and clearly.

Detailed explanation

Without validation, a typo in an input surfaces as an obscure provider error halfway through an apply, or worse, succeeds and creates the wrong thing. Terraform offers several layers.

Types. type = string is the minimum; for complex inputs use object({...}) with optional(attr, default) (Terraform 1.3+). Terraform rejects inputs with the wrong shape or type at plan time and the type documents the interface.

Variable validation. A validation block has a condition and an error_message. Examples: contains(["dev", "test", "prod"], var.environment), can(cidrhost(var.vpc_cidr, 0)) to ensure a valid CIDR, regex checks on names, numeric ranges. Since Terraform 1.9, conditions can reference other variables and objects, not just the variable itself, which enables cross-field checks.

Preconditions and postconditions live in a lifecycle block of resources and data sources, or in outputs. A precondition checks assumptions before Terraform plans or changes the object: the selected AMI must be arm64, the subnet must belong to the expected VPC, the instance type must be allowed in this environment. A postcondition checks the result: the certificate status is ISSUED, the looked-up VPC has DNS support enabled. When they fail, Terraform stops with your message, and the failure is attributed to the right object.

Check blocks (1.5+) express continuous assertions about the infrastructure as a whole, optionally with a scoped data source such as an HTTP request to a health endpoint. They run on every plan and apply but only produce warnings, never block, so they suit health and compliance signals, and HCP Terraform uses them for continuous validation.

The goal across all of them is to fail early with a clear message that tells the caller what to fix.

How it works

  1. Type conversion and checking of inputs.
  2. Variable validation conditions evaluated.
  3. Preconditions evaluated before planning each resource (or at apply if values are unknown).
  4. Postconditions evaluated after a resource is planned or applied.
  5. Check blocks evaluated at the end, producing warnings.

Example

variable "environment" {
  type = string
  validation {
    condition     = contains(["dev", "test", "prod"], var.environment)
    error_message = "environment must be dev, test or prod."
  }
}

variable "vpc_cidr" {
  type = string
  validation {
    condition     = can(cidrhost(var.vpc_cidr, 0))
    error_message = "vpc_cidr must be a valid CIDR block, e.g. 10.0.0.0/16."
  }
}

resource "aws_instance" "app" {
  ami           = data.aws_ami.app.id
  instance_type = var.instance_type
  lifecycle {
    precondition {
      condition     = data.aws_ami.app.architecture == "arm64"
      error_message = "The AMI must be arm64 for Graviton instances."
    }
  }
}

check "health" {
  data "http" "app" { url = "https://${aws_lb.app.dns_name}/health" }
  assert {
    condition     = data.http.app.status_code == 200
    error_message = "Application health endpoint is not returning 200."
  }
}

Common mistakes

  • type = any everywhere, losing all checking.
  • Vague error messages such as "invalid value".
  • Using check blocks expecting them to block applies.
  • Validating in the provider error instead of the module interface.

How to answer in the interview

"Strong types come first: object types with optional attributes and defaults document the interface and reject wrong shapes. Then validation blocks on variables, with a condition and error message, for example that environment is dev, test or prod, or that a CIDR is valid using can(cidrhost(...)). Preconditions and postconditions in a resource or output check assumptions at plan or apply time, like that the AMI has the right architecture or that a certificate was issued. Check blocks add assertions that run on every plan but only warn, like a health endpoint responding. All of these fail early with a clear message instead of an obscure API error."

Likely follow-up questions

  • What is the difference between a validation block and a precondition? Validation checks an input variable (at the module boundary); preconditions check assumptions about a specific resource, data source or output, possibly using other objects.
  • Do check blocks stop an apply? No, failures are warnings.
  • When are preconditions with unknown values evaluated? Deferred to apply when values become known.
