What is the difference between extending Thread and implementing Runnable?

Concurrency · concept · levels entry

In one line

Extending Thread uses up Java's single inheritance and ties the task to the thread; implementing Runnable separates the task from its execution, so it can run in any thread, pool or virtual thread, and the class stays free to extend something else. Prefer Runnable.

Detailed explanation

Java classes can extend only one superclass. If ReportJob extends Thread, it cannot also extend BaseJob. Implementing an interface has no such cost: ReportJob extends BaseJob implements Runnable is fine.

More important is separation of concerns. A Thread is an execution mechanism: it has a name, priority, state, daemon flag and a lifecycle that can be started only once. A Runnable is just a unit of work. When the work is a Runnable, the how is decided elsewhere: the same object can be passed to new Thread(r), submitted to an ExecutorService thread pool, scheduled with a ScheduledExecutorService, wrapped in CompletableFuture.runAsync, or run on a virtual thread. A Thread subclass can technically be passed to an executor (because Thread implements Runnable), but you would be creating a heavyweight object that is never started as a thread, which is confusing.

This is composition over inheritance: you do not inherit dozens of Thread methods you do not need, you just supply behaviour. Runnable is also a functional interface, so a lambda or method reference (this::sync) is enough, which reads better and makes testing easy: call run() directly in a unit test.

Sharing is easier too: one Runnable instance can be given to several threads, all working on the same state (which then needs synchronisation), whereas each Thread subclass instance is its own thread.

Extend Thread only when you genuinely customise thread behaviour itself, which is rare; even custom naming or daemon status is better done via a ThreadFactory or Thread.Builder.

How it works

  1. Extending: class Job extends Thread { public void run() {...} }, then new Job().start().
  2. Implementing: class Job implements Runnable { public void run() {...} }.
  3. Execute anywhere: new Thread(job).start(), pool.execute(job), Thread.startVirtualThread(job).
  4. Thread.run() by default calls the target Runnable's run().
  5. Thread properties (name, daemon) are configured on the Thread or factory, not the task.

Example

// Extending Thread: task and mechanism are fused
class EmailSenderThread extends Thread {
    @Override public void run() { sendPendingEmails(); }
}
new EmailSenderThread().start();

// Implementing Runnable: task is independent
class EmailSender extends AuditedJob implements Runnable {   // can still extend
    @Override public void run() { sendPendingEmails(); }
}
Runnable job = new EmailSender();
new Thread(job, "email-1").start();
scheduler.scheduleAtFixedRate(job, 0, 1, TimeUnit.MINUTES);
Thread.startVirtualThread(job);

Common mistakes

  • Extending Thread just to give it a name.
  • Passing a Thread subclass to an executor and expecting its thread settings to apply.
  • Calling run() on the Runnable expecting a new thread.
  • Sharing one Runnable across threads without synchronising its fields.

How to answer in the interview

"Extending Thread ties my task to the thread mechanism and uses up my only superclass, because Java has single inheritance. Implementing Runnable keeps the task separate from how it runs: the same Runnable can go to a new Thread, an ExecutorService, a scheduled executor or a virtual thread, and my class can still extend another class. It follows composition over inheritance, and as a functional interface it works with lambdas. So I prefer Runnable, and only extend Thread if I really need to customise thread behaviour itself."

Likely follow-up questions

  • Is Thread itself a Runnable? Yes, Thread implements Runnable; its run() calls the target Runnable if one was given.
  • How do you name threads without extending Thread? Use a ThreadFactory or Thread.ofPlatform().name("worker-", 0).
  • When would you use Callable instead? When the task must return a value or throw checked exceptions.
