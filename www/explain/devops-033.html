What is Ansible, and what makes a good playbook?

Configuration Management · concept · levels entry, mid

In one line

Ansible is an agentless automation and configuration management tool that connects over SSH (or WinRM), uses an inventory of hosts, and runs YAML playbooks of tasks built from idempotent modules; a good playbook uses proper modules instead of raw shell, is organised in roles, uses handlers and variables, keeps secrets in Ansible Vault, and is tested with check mode and Molecule.

Detailed explanation

Ansible needs nothing on the managed nodes except SSH access and Python (Windows uses WinRM or SSH with PowerShell). The control node reads an inventory (static INI/YAML or dynamic from AWS, Azure, VMware) that groups hosts, for example web and db. A playbook contains plays, each mapping a host group to a list of tasks. Each task calls a module (ansible.builtin.package, template, service, user, lineinfile, community.mysql.mysql_user), which Ansible copies to the host, runs and removes, returning JSON with changed or ok.

The defining quality of a good playbook is idempotency: running it once configures the host, running it again changes nothing and reports changed=0. Modules achieve this by checking current state first ("is nginx installed? is the file content identical?"). Raw shell or command tasks are not idempotent by default, so use them only when no module exists, with creates, removes or changed_when guards.

Good structure:

  • Roles (roles/nginx/{tasks,handlers,templates,defaults,vars}) for reusable units, shared via collections and Galaxy.
  • Variables in group_vars/host_vars, with sensible defaults in the role.
  • Handlers that restart services only when a config task reports a change.
  • Templates (Jinja2) for config files.
  • Secrets encrypted with Ansible Vault or looked up from HashiCorp Vault.
  • Testing: ansible-lint, --check --diff dry runs, and Molecule to test roles in containers or VMs.

Terraform typically provisions infrastructure (VMs, networks), while Ansible configures what runs on it.

How it works

  1. Control node reads inventory and variables.
  2. For each play, connects to hosts in parallel (forks).
  3. Runs each task's module on every host, collecting results.
  4. Notified handlers run at the end of the play.
  5. A recap shows ok/changed/failed per host.

Example

- name: Configure web servers
  hosts: web
  become: true
  tasks:
    - name: Install nginx
      ansible.builtin.package: { name: nginx, state: present }
    - name: Deploy nginx config
      ansible.builtin.template: { src: nginx.conf.j2, dest: /etc/nginx/nginx.conf, mode: "0644" }
      notify: Reload nginx
    - name: Ensure nginx is running
      ansible.builtin.service: { name: nginx, state: started, enabled: true }
  handlers:
    - name: Reload nginx
      ansible.builtin.service: { name: nginx, state: reloaded }
ansible-playbook -i inventories/prod site.yml --check --diff --limit web

Common mistakes

  • Using shell: apt-get install -y nginx instead of the package module.
  • Restarting services unconditionally on every run instead of using handlers.
  • Plain-text passwords in group_vars.
  • Huge single playbooks with no roles.

How to answer in the interview

"Ansible is agentless: it connects over SSH, or WinRM for Windows, and runs modules on the hosts, so only Python is needed on them. The inventory lists hosts in groups, and playbooks are YAML plays mapping those groups to tasks. A good playbook uses idempotent modules like package, template and service rather than raw shell, so a second run changes nothing. It's organised in roles with defaults and variables, uses handlers to restart services only when config changes, keeps secrets in Ansible Vault, and is tested with ansible-lint, check mode and Molecule. I'd use Terraform to provision infrastructure and Ansible to configure what runs on it."

Likely follow-up questions

  • Make a shell task idempotent? Use creates/removes, or register output and set changed_when.
  • Push vs pull? Ansible pushes by default; ansible-pull lets nodes pull playbooks from Git.
  • How do you speed up large runs? More forks, SSH pipelining, fact caching, and strategy: free where safe.
