What is the purpose of thenApply() and thenApplyAsync()?

Concurrency · concept · levels mid

In one line

Both transform the previous result with a Function and return a new CompletableFuture; thenApply runs the function in the thread that completed the previous stage (or the caller if already complete), while thenApplyAsync submits it to an executor: the common pool or one you pass.

Detailed explanation

thenApply(fn) is the map operation of CompletableFuture. The question is which thread runs fn.

For thenApply there are two cases. If the source future is not yet complete when you register the stage, fn will run in the thread that completes the source, for example the pool thread that ran supplyAsync, or an HTTP client's I/O thread. If the source is already complete, fn runs immediately in the calling thread, inside the thenApply call. So you do not control the thread, but you avoid a hand-off, which is efficient for cheap work.

thenApplyAsync(fn) always submits fn as a new task to the default async executor, which is ForkJoinPool.commonPool() (unless the common pool's parallelism is below two, in which case a new thread is used per task). thenApplyAsync(fn, executor) uses your executor. This costs a queue hand-off and possibly a context switch, but guarantees the function does not run on the completing thread.

When to use which:

  • thenApply: cheap, non-blocking transformations: mapping an entity to a DTO, extracting a field, simple arithmetic.
  • thenApplyAsync with your own executor: heavy CPU work or blocking calls, or when the completing thread must not be held up. Example: an async HTTP client or Netty event loop completes the future; running a slow transformation there would stall all other connections on that event loop. Also useful to move work out of a caller thread that must return quickly.

The same pattern applies to every stage: thenAccept/thenAcceptAsync, thenCompose/thenComposeAsync, thenCombine/thenCombineAsync, whenComplete/whenCompleteAsync.

How it works

  1. supplyAsync(task, pool) runs on a pool thread.
  2. thenApply(fn) registered before completion: fn runs on that same pool thread right after task.
  3. thenApply(fn) registered after completion: fn runs immediately on the caller thread.
  4. thenApplyAsync(fn): fn is submitted to the common pool.
  5. thenApplyAsync(fn, exec): fn is submitted to exec.

Example

ExecutorService io = Executors.newFixedThreadPool(8, Thread.ofPlatform().name("io-", 0).factory());
ExecutorService cpu = Executors.newFixedThreadPool(4, Thread.ofPlatform().name("cpu-", 0).factory());

CompletableFuture.supplyAsync(() -> downloadImage(url), io)       // io-N
    .thenApply(bytes -> bytes.length)                               // cheap: same io-N thread
    .thenApplyAsync(len -> log("size " + len), cpu);                // runs on cpu-N

CompletableFuture<byte[]> raw = httpClient.sendAsync(req, ofByteArray())
        .thenApply(HttpResponse::body);                             // cheap, client thread OK
CompletableFuture<Thumbnail> thumb =
        raw.thenApplyAsync(ImageUtil::resize, cpu);                 // heavy: own executor

Common mistakes

  • Using thenApplyAsync everywhere, adding hand-offs for trivial work.
  • Running blocking calls in thenApply on an event-loop thread.
  • Using thenApplyAsync without an executor for blocking work, clogging the common pool.
  • Assuming thenApply always runs on a background thread.

How to answer in the interview

"Both apply a Function to the previous stage's result and return a new CompletableFuture with the transformed value. thenApply runs the function synchronously, in the thread that completed the previous stage, or in the calling thread if the future is already complete. thenApplyAsync submits the function as a new task to the common ForkJoinPool or to an executor I pass. I use thenApply for cheap transformations such as mapping to a DTO, and thenApplyAsync with my own executor when the work is heavy or blocking, or when I must not run it on the completing thread, such as an I/O event loop."

Likely follow-up questions

  • What is the downside of making every stage async? Each stage becomes a separate task with queueing and context-switch overhead, and thread-local context is lost more often.
  • Which executor does thenApplyAsync use by default? The ForkJoinPool common pool, or a new thread per task if its parallelism is below two.
  • Does the same apply to thenCompose? Yes; every stage method has a synchronous and an Async variant with the same rules.
