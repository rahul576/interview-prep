How do Azure Machine Learning workspaces, compute and managed online endpoints work for MLOps?

MLOps · concept · levels mid, senior

In one line

An Azure Machine Learning workspace is the hub that holds runs, models, data assets and environments; training runs as jobs on compute clusters or serverless compute, and models are served from managed online endpoints whose deployments share traffic for blue-green and canary releases.

Detailed explanation

The workspace is the top-level resource for a team or project. It tracks jobs and experiments, stores registered models, data assets (versioned pointers to files or tables in storage), environments (a Docker image plus a Conda or pip spec) and components (reusable pipeline steps). It links to a storage account, Key Vault, Container Registry and Application Insights. Azure ML uses MLflow natively: the workspace exposes an MLflow tracking URI, so mlflow.log_metric and mlflow.log_model work without extra servers.

Training runs on compute clusters that autoscale between a minimum (often zero) and a maximum number of nodes, or on serverless compute, where you only pick a VM size and Azure manages the cluster. Jobs are defined in YAML (CLI v2) or the Python SDK v2, and multi-step workflows are pipelines built from components.

Registries sit outside workspaces and share models, environments and components across workspaces and regions, which is how a model trained in a dev workspace reaches a prod workspace without retraining.

For real-time serving, a managed online endpoint is a stable URL with authentication; underneath it you create one or more deployments (for example blue and green), each with its own model version, environment, instance type and scaling. The endpoint traffic allocation splits live requests between deployments, and mirrored traffic copies a percentage of requests to a deployment whose responses are discarded, which is a built-in shadow test. Batch endpoints cover offline scoring. Access uses managed identities, RBAC and private endpoints / managed virtual networks.

How it works

  1. Create the workspace with IaC (Bicep or Terraform), including private networking and a managed identity.
  2. Register data assets and environments; define training as a pipeline job on a cluster or serverless compute.
  3. Log metrics and the model with MLflow; register the model version (in the workspace or a shared registry).
  4. Create a managed online endpoint and a green deployment with the new model, alongside the existing blue.
  5. Mirror some traffic to green, then shift 10 percent live, watch metrics in Azure Monitor, then go to 100 percent.
  6. Delete the old deployment once stable.

Example

az ml online-deployment create -f green.yml --endpoint-name churn-ep
az ml online-endpoint update -n churn-ep --mirror-traffic "green=10"
az ml online-endpoint update -n churn-ep --mirror-traffic "green=0" --traffic "blue=90 green=10"
az ml online-endpoint update -n churn-ep --traffic "blue=0 green=100"
az ml online-deployment delete -n blue --endpoint-name churn-ep --yes

Common mistakes

  • Hard-coding storage keys instead of using managed identities and Key Vault.
  • Leaving compute clusters with a minimum node count above zero, paying for idle GPUs.
  • Retraining separately in prod instead of promoting the same model through a registry.
  • Forgetting that mirrored traffic still costs compute and can hit downstream dependencies.

How to answer in the interview

"In Azure ML the workspace is the central place for jobs, models, data assets and environments, and it tracks everything with MLflow. I run training as pipeline jobs on autoscaling clusters or serverless compute, defined in YAML so they live in Git. For serving I use a managed online endpoint with two deployments, blue and green. I first mirror a slice of traffic to green, then shift ten percent live, watch latency and error metrics, and move to a hundred percent. Models move from dev to prod through a shared registry, and access is via managed identities and private endpoints."

Likely follow-up questions

  • How would you promote a model from dev to prod? Register it in a shared Azure ML registry from dev and deploy that exact version in the prod workspace through a gated pipeline.
  • Managed online endpoint versus AKS? Managed endpoints remove cluster operations; Kubernetes online endpoints suit teams that already run AKS or need on-prem/Arc.
  • How do you roll back? Move traffic back to the previous deployment, which is instant as long as you keep it running.
