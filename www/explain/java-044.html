How would you lead the migration of a large Java monolith to microservices?

Architecture · design · levels lead

In one line

Lead the migration by clarifying the why, finding bounded contexts with DDD, extracting incrementally with the strangler fig pattern, solving data ownership (database per service, CDC/events during transition), building the platform first (CI/CD, observability, tracing), and measuring outcomes.

Detailed explanation

A migration of this size is a multi-year organisational change, not just a refactor. First, agree the goal: faster independent deployments, team autonomy, independent scaling, or reducing risk in a fragile area. If the real pain is slow builds or tangled code, a modular monolith (enforced module boundaries, e.g. with Spring Modulith or ArchUnit) may deliver most of the benefit at a fraction of the cost.

Use domain-driven design to map bounded contexts (catalogue, ordering, billing, notifications) with domain experts, and look at change coupling in git history. Pick a first candidate with clear boundaries, few dependencies and real business value, often an edge capability like notifications or search, not the core order flow.

The strangler fig pattern puts a routing layer (API gateway or reverse proxy) in front of the monolith. New functionality is built in the service, traffic for that capability is shifted gradually (often with feature flags or canaries), and the old code is deleted. Branch by abstraction helps inside the monolith.

Data ownership is the hardest part: each service must own its data. During transition, sync with change data capture (Debezium) or domain events using the outbox pattern, and replace cross-module joins with APIs or read models. Without this you get a distributed monolith.

Invest in the platform before scaling out: CI/CD per service, containers, centralised logging, metrics, distributed tracing (OpenTelemetry), service templates. Align teams to services (Conway's law).

How it works

  1. Define goals and metrics: lead time, deployment frequency, incident rate.
  2. Map bounded contexts and dependencies; choose the first slice.
  3. Build the paved road: pipeline, observability, service template.
  4. Put a gateway in front of the monolith.
  5. Extract the service, sync data via CDC/events, shift traffic gradually.
  6. Delete the old code path; repeat with the next context.
  7. Review metrics quarterly and stop when remaining benefit is low.

Example

# Spring Cloud Gateway: strangler routing during migration
spring:
  cloud:
    gateway:
      routes:
        - id: notifications-new
          uri: lb://notification-service
          predicates: [ Path=/api/notifications/** ]
        - id: monolith-fallback
          uri: http://legacy-monolith:8080
          predicates: [ Path=/** ]
          order: 1000

Common mistakes

  • A big-bang rewrite that freezes features for a year.
  • Splitting services but sharing one database.
  • Extracting the most entangled core domain first.
  • Starting without tracing, centralised logs or automated deployments.
  • Making services too small (nano-services) with chatty synchronous calls.

How to answer in the interview

"I'd start with why, because microservices add operational cost, and a modular monolith may be enough. Then I'd use DDD to identify bounded contexts and pick a first service with clear boundaries and business value. I'd use the strangler fig pattern: a gateway in front, build the new service, shift traffic gradually, delete the old code. Each service owns its data, synced via CDC or outbox events during transition. Before scaling out I'd build the platform: CI/CD, observability and tracing. It's incremental, one service at a time, measured with lead time and incident rate, with teams aligned to services."

Likely follow-up questions

  • What would you avoid extracting first? The core, highly coupled domain with shared tables, such as orders or pricing.
  • How do you handle transactions across services? Sagas with compensations and idempotent consumers.
  • How do you know when to stop? When the remaining monolith no longer blocks teams or goals.
