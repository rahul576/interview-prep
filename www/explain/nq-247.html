How does normalization reduce data duplication?

Databases & SQL · concept · levels entry

In one line

Normalization reduces duplication by storing each fact once, in the table where it belongs, and letting other tables refer to it by key, so changes happen in one place and update, insert and delete anomalies disappear.

Detailed explanation

Duplication arises when a table mixes several entities. Picture an orders table that also holds the customer's name, email and address on every order. A customer with 200 orders has their email stored 200 times.

Normalization asks, for each column, "what does this fact actually describe?" The email describes the customer, not the order, so it moves into a customers table and is stored once. The orders table keeps only customer_id, a foreign key pointing to that row. Whenever you need the email for an order, you join on the key.

Repeating groups are handled the same way. Columns like phone1, phone2, phone3, or a comma-separated list of products, become rows in a child table (customer_phone, order_item), so there is no fixed limit and no empty columns.

Benefits:

  • One update: changing the email touches a single row.
  • No contradictions: there is no way for two orders to show different addresses for the same customer.
  • Independent existence: you can add a customer before any orders, and deleting an order does not lose the customer.
  • Less storage, and integrity enforced by keys and constraints.

What is not duplication: a value that has a different meaning, such as the price at the time of sale on an order line, or the shipping address used for a specific order, which must stay unchanged even if the customer moves. Those belong on the order.

How it works

  1. Spot columns that repeat the same value across many rows.
  2. Identify the entity that value really belongs to.
  3. Create (or reuse) a table for that entity with a primary key.
  4. Replace the repeated columns with a foreign key.
  5. Turn repeating groups into child rows.
  6. Join on keys when reading.

Example

-- Before: customer data copied into every order
-- orders(id, customer_name, customer_email, customer_city, total)

CREATE TABLE customers (
  id BIGINT PRIMARY KEY, name TEXT, email TEXT UNIQUE, city TEXT);
CREATE TABLE orders (
  id BIGINT PRIMARY KEY,
  customer_id BIGINT NOT NULL REFERENCES customers(id),
  total NUMERIC(10,2));

-- Email change: one row, instead of 200
UPDATE customers SET email = 'asha@new.example' WHERE id = 42;

SELECT o.id, c.name, c.email FROM orders o JOIN customers c ON c.id = o.customer_id;

Common mistakes

  • Treating historical values (price, shipping address used) as duplication.
  • Keeping "convenience copies" with no plan to update them.
  • Joining or relating tables by name instead of a stable key.
  • Thinking normalization is only about saving disk space; the main goal is correctness.

How to answer in the interview

"Normalization moves each fact into the table where it naturally belongs and stores it once; other tables refer to it with foreign keys instead of copying it. For example, instead of repeating a customer's name, email and address on every order row, I keep them once in a customers table and orders hold only customer id. Repeating groups like several phone numbers become rows in a separate table. As a result, changing an email is one update in one row, different orders can't show different addresses for the same customer, and I can store a customer before they ever order."

Likely follow-up questions

  • What problems arise if customer details are copied into orders? Update anomalies, inconsistent data, wasted space, and losing customers when orders are deleted.
  • Is storing the shipping address on the order duplication? No; it records where that order was sent.
  • What is the cost of normalization? More joins, which indexes on foreign keys keep fast.
