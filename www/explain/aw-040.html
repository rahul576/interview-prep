How do you serve a private S3 bucket through CloudFront securely, and how does caching work?

Cloud (AWS) · concept · levels mid

In one line

Keep the S3 bucket private with Block Public Access, let only your distribution read it through Origin Access Control (OAC) and a bucket policy scoped to that distribution, serve HTTPS with an ACM certificate in us-east-1, and control caching with cache behaviours, cache policies and TTLs.

Detailed explanation

The secure setup has three pieces. First, Block Public Access stays on and there is no public bucket policy, so S3 URLs cannot be used directly. Second, the distribution uses Origin Access Control, the successor to the legacy origin access identity (OAI); CloudFront signs origin requests with SigV4, and OAC also works with SSE-KMS encrypted objects (the KMS key policy must allow the CloudFront service principal). Third, the bucket policy allows s3:GetObject to the cloudfront.amazonaws.com service principal only when AWS:SourceArn equals your distribution's ARN, so no other distribution can read it.

For a custom domain, the certificate must be in ACM in us-east-1, the viewer protocol policy should redirect to HTTPS, and a response headers policy can add HSTS and other security headers. For content only some users may see, use signed URLs or signed cookies with a trusted key group, and geo restrictions or AWS WAF if needed.

Caching is controlled per cache behaviour, matched on path patterns like /assets/*. The behaviour's cache policy defines the cache key (which headers, cookies and query strings are included) and min, default and max TTLs, while the origin request policy sends extra values to the origin without making them part of the key. The smaller the cache key, the higher the hit ratio. Origin Cache-Control headers are respected within those TTL bounds.

For deployments, build tools emit content-hashed file names like app.3f9c1a.js that can be cached for a year as immutable, while index.html gets a short TTL or no-cache, or is invalidated after each release.

How it works

  1. A viewer requests https://www.example.com/assets/app.3f9c1a.js.
  2. The nearest edge location checks its cache using the cache key.
  3. On a hit it returns the object; on a miss it asks a regional edge cache, then the origin.
  4. CloudFront signs the S3 request with OAC; S3 checks the bucket policy's SourceArn.
  5. The object is cached according to Cache-Control and the policy's TTLs.

Example

{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "AllowCloudFrontOAC",
    "Effect": "Allow",
    "Principal": {"Service": "cloudfront.amazonaws.com"},
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::my-site-bucket/*",
    "Condition": {"StringEquals": {
      "AWS:SourceArn": "arn:aws:cloudfront::111122223333:distribution/E2ABCDEF123"}}
  }]
}
aws s3 sync dist/ s3://my-site-bucket/ --exclude index.html \
  --cache-control "public,max-age=31536000,immutable"
aws s3 cp dist/index.html s3://my-site-bucket/ --cache-control "no-cache"

Common mistakes

  • Using the S3 website endpoint, which cannot use OAC, and making the bucket public.
  • Requesting the ACM certificate in the application's region instead of us-east-1.
  • Forwarding all headers and cookies, which destroys the cache hit ratio.
  • Relying on invalidations for every file instead of hashed names.

How to answer in the interview

"The bucket stays private with Block Public Access. CloudFront reads it through Origin Access Control, and the bucket policy allows s3:GetObject only to the CloudFront service principal with a SourceArn condition for my distribution, so nobody can bypass the CDN. The custom domain uses an ACM certificate in us-east-1 and HTTPS redirect. Caching is defined per behaviour with a cache policy, which sets the TTLs and the cache key; I keep the key minimal for a good hit ratio. Hashed assets are cached for a year, index.html is no-cache or invalidated, and private files use signed URLs or cookies."

Likely follow-up questions

  • Why should index.html have a short TTL while JS bundles can have a long one? index.html points to the current hashed bundles; if it is stale, users load old code, while a hashed file never changes.
  • OAI versus OAC? OAC supports SSE-KMS, all regions and more methods; OAI is legacy.
  • How do you serve an SPA's client-side routes? Map 403/404 errors to /index.html with a 200, or use a CloudFront Function.
