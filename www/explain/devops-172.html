A container works on your laptop but fails in production. How do you investigate?

Docker · scenario · levels mid, senior

In one line

Systematically compare the two environments: start with logs and exit codes, then check configuration and secrets, the exact image (tag, digest, architecture), user and filesystem permissions (non-root, read-only), network/DNS and dependencies, and resource limits and probes.

Detailed explanation

"It works on my machine" with containers usually means the image is the same but the environment is not, or the image is not actually the same. The fastest way through is to stop guessing and list the differences.

1. Evidence first. docker logs / kubectl logs --previous, the exit code (1 = app error, 137 = SIGKILL, often OOMKilled, 139 = segfault, exec format error = wrong architecture), and events (kubectl describe pod: image pull errors, failed probes, scheduling).

2. Configuration. Environment variables, mounted config files, secrets and feature flags that exist locally (.env, a bind-mounted config) but not in production, or have different values. A missing variable often produces a confusing stack trace.

3. The image itself. Is production running the same digest? A floating tag like latest may point elsewhere. Was it built on an Apple silicon Mac as arm64 and scheduled onto amd64 nodes? Local builds can also include files that .dockerignore or the CI build context excludes.

4. Security context. Production often enforces runAsNonRoot, a read-only root filesystem, dropped capabilities and seccomp profiles. An app writing to /app/logs or /tmp without a writable volume, binding to port 80 as non-root, or relying on root-owned files fails with permission errors.

5. Network and dependencies. DNS names, service discovery, TLS certificates and CAs, proxies, network policies and firewall rules differ. localhost in production means the container itself, not your laptop's database.

6. Resources and timing. Memory limits kill JVMs or Node apps that use more than locally; CPU limits slow startup so liveness probes fail before the app is ready, causing restart loops.

How it works

  1. Collect logs, exit code, events.
  2. Confirm image digest and architecture.
  3. Diff environment, config and secrets.
  4. Check user, filesystem and capabilities.
  5. Test connectivity from inside the container.
  6. Check limits, probes and recent changes; reproduce locally with production settings.

Example

kubectl get pod api-7d9 -o jsonpath='{.status.containerStatuses[0].lastState}'
kubectl logs api-7d9 --previous
kubectl get pod api-7d9 -o jsonpath='{.status.containerStatuses[0].imageID}'
docker buildx imagetools inspect ghcr.io/acme/api:1.4.0   # which platforms exist?
kubectl exec api-7d9 -- env | sort
kubectl debug -it api-7d9 --image=nicolaka/netshoot --target=api -- nslookup db.prod.svc
# reproduce locally with production-like constraints
docker run --rm --read-only --user 10001 --memory 512m --platform linux/amd64 \
  --env-file prod-like.env ghcr.io/acme/api:1.4.0

Common mistakes

  • Redeploying repeatedly hoping it works, without reading logs.
  • Ignoring exit code 137 and debugging application code.
  • Building images locally and pushing them instead of using CI.

How to answer in the interview

"I compare what actually differs. First the evidence: logs, the exit code, and events, because 137 points to an OOM kill and exec format error to the wrong architecture. Then configuration: environment variables, config files and secrets that exist locally but not in production. Then the image: is it the same digest, and was it built as arm64 on a Mac but run on amd64 nodes? Production often runs as non-root with a read-only filesystem, so writes fail. I check DNS and connectivity from inside the pod, and finally resource limits and probes. To prevent it, images come only from CI and local runs use production-like settings."

Likely follow-up questions

  • Make local closer to production? CI-built images, Compose with the same user and read-only settings, same env var names, limits.
  • Image has no shell? kubectl debug with an ephemeral container.
  • Exit code 137? SIGKILL, usually OOM; check OOMKilled in status.
