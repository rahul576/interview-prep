How do you implement retries correctly in distributed systems?

Microservices · concept · levels mid, senior

In one line

Retry only transient errors, with exponential backoff and jitter, a small attempt limit and an overall deadline, in one layer under a retry budget and circuit breaker, and only for idempotent operations or with idempotency keys.

Detailed explanation

Retries turn short glitches into successes, but done badly they cause outages. Four rules matter.

Retry the right errors. Transient failures, connection resets, timeouts, 503 Service Unavailable, 429 Too Many Requests (honouring Retry-After), deadlocks, are worth retrying. Permanent ones, 400, 401, 404, validation errors, will fail again and should not be retried.

Wait properly. Immediate retries hit a struggling service at the worst moment. Use exponential backoff (100 ms, 200 ms, 400 ms...) capped at a maximum, plus jitter (randomising each wait) so thousands of clients that failed together do not retry in lockstep and create synchronised waves.

Bound the cost. Limit attempts (typically 2-3) and respect an overall deadline: if the caller's budget is 2 s, there is no point starting a third attempt at 1.9 s. Propagate deadlines downstream where possible, for example gRPC deadlines.

Avoid amplification. If the gateway, service A and service B each retry three times, one failing request to C becomes up to 3 × 3 × 3 = 27 calls, a retry storm that keeps C down. Retry in one layer, usually closest to the failure or at the edge, use retry budgets (retries may only be, say, 10 percent of requests; Envoy and gRPC support this) and put a circuit breaker in front so retries stop when the dependency is clearly down.

Idempotency. A timeout does not mean the operation failed; it may have succeeded. Retrying GET or PUT is safe; retrying POST /payments can charge twice. Make operations idempotent or send an idempotency key that the server uses to deduplicate.

How it works

  1. Call fails; classify the error.
  2. Not retryable: fail immediately.
  3. Retryable and attempts and deadline remain: wait backoff × jitter.
  4. Check circuit breaker and retry budget.
  5. Retry with the same idempotency key.
  6. Give up: return an error or fallback; record metrics.

Example

resilience4j:
  retry:
    instances:
      payments:
        maxAttempts: 3
        waitDuration: 200ms
        enableExponentialBackoff: true
        exponentialBackoffMultiplier: 2
        enableRandomizedWait: true
        randomizedWaitFactor: 0.5
        retryExceptions: [java.io.IOException, java.util.concurrent.TimeoutException]
        ignoreExceptions: [com.acme.ValidationException]
@Retry(name = "payments")
@CircuitBreaker(name = "payments")
public Receipt charge(ChargeRequest req) {
    return restClient.post().uri("/charges")
        .header("Idempotency-Key", req.requestId())   // server dedupes
        .body(req).retrieve().body(Receipt.class);
}

Common mistakes

  • Retrying non-idempotent POSTs without keys.
  • Retries at every layer.
  • No deadline, so requests hang for a minute.
  • Retrying 4xx errors.
  • Not logging or measuring retries, hiding a degrading dependency.

How to answer in the interview

"I only retry transient errors like timeouts, connection resets or 503s, never validation errors. Each retry waits with exponential backoff plus jitter so clients do not retry in sync. I cap attempts at two or three and respect an overall deadline. To avoid retry storms I retry in one layer only, use retry budgets and put a circuit breaker in front, because three layers retrying three times turn one failure into 27 requests. And I only retry idempotent operations, or I send an idempotency key so the server can deduplicate a payment that actually succeeded."

Likely follow-up questions

  • How do three layers of retries become 27 requests? Each layer multiplies attempts: 3 × 3 × 3.
  • Why jitter? It desynchronises clients so their retries do not arrive as a single spike.
  • How does an idempotency key work? The server stores the key with the result and returns the stored result for repeats.
