What is node-pressure eviction, and how does it differ from API-initiated eviction?

Kubernetes · concept · levels mid, senior, lead

In one line

Node-pressure eviction is the kubelet killing pods when the node runs low on memory, disk, inodes or PIDs, using soft and hard eviction thresholds and ranking victims by usage above requests and priority; it ignores PodDisruptionBudgets. API-initiated eviction (drain, autoscaler, upgrades) goes through the Eviction API, which respects PDBs.

Detailed explanation

Node-pressure eviction protects the node itself. The kubelet monitors signals such as memory.available, nodefs.available, nodefs.inodesFree, imagefs.available and pid.available. When a signal crosses a threshold:

  • Hard threshold (default for memory is around memory.available<100Mi): evict immediately, with no graceful termination period.
  • Soft threshold: must be exceeded for evictionSoftGracePeriod; pods then get up to evictionMaxPodGracePeriod to terminate.

The node also gets a condition (MemoryPressure, DiskPressure, PIDPressure) and a taint so new pods aren't scheduled there.

For disk pressure the kubelet first reclaims node resources: garbage-collect dead containers and unused images. If that isn't enough, it evicts pods.

Victim selection for memory: first pods whose usage exceeds their requests, ordered by priority and then by how far above requests they are. Consequently BestEffort pods (no requests) and Burstable pods far above requests go first; Guaranteed pods (requests = limits) and pods within requests go last. Evicted pods show Status: Failed, Reason: Evicted; their controllers create replacements elsewhere. Because the node must protect itself, PDBs are not consulted.

If memory spikes faster than the kubelet's polling, the kernel OOM killer acts first, killing a process inside a container: that shows as OOMKilled (exit code 137), not Evicted. The kubelet sets oom_score_adj so BestEffort processes are preferred victims.

API-initiated eviction is a request to the Eviction API (pods/eviction subresource) made by kubectl drain, Cluster Autoscaler, Karpenter or managed upgrades. The API server checks PDBs and can refuse with 429, and the pod is terminated gracefully with its normal grace period.

Protecting nodes: set system-reserved and kube-reserved so the OS and kubelet keep memory, set realistic requests, and avoid BestEffort for anything important.

How it works

  1. Kubelet samples node signals periodically.
  2. Threshold crossed → node condition and taint set.
  3. Reclaim images and dead containers (disk).
  4. Rank pods by usage over requests and priority.
  5. Evict pods until the signal recovers.

Example

# KubeletConfiguration excerpt
evictionHard:
  memory.available: "200Mi"
  nodefs.available: "10%"
  pid.available: "5%"
evictionSoft:
  memory.available: "500Mi"
evictionSoftGracePeriod:
  memory.available: "1m"
systemReserved: { cpu: 500m, memory: 1Gi }
kubeReserved:   { cpu: 500m, memory: 1Gi }
kubectl get pods -A --field-selector=status.phase=Failed | grep Evicted
kubectl describe node node-3 | grep -A5 Conditions

Common mistakes

  • Believing PDBs protect against node-pressure evictions.
  • Running important workloads as BestEffort.
  • No system or kube reserved, so the kubelet itself gets starved.
  • Confusing Evicted with OOMKilled.

How to answer in the interview

"Node-pressure eviction is done by the kubelet when the node runs low on memory, disk, inodes or PIDs. Soft thresholds have a grace period, hard thresholds evict immediately. It picks pods whose usage exceeds their requests first, then by priority, so BestEffort pods and pods far over their requests go first and Guaranteed pods last. It ignores PDBs because the node is protecting itself. API-initiated eviction from drain, autoscalers or upgrades goes through the Eviction API, which respects PDBs. If the kernel OOM killer acts first, the container is OOMKilled rather than evicted."

Likely follow-up questions

  • How do you size system-reserved and kube-reserved? Measure kubelet, runtime and OS usage under load; providers publish formulas by node size.
  • Why do evicted pods linger? Failed pod objects stay until garbage-collected; clean them up.
  • What does PIDPressure mean? Too many processes, often a fork bomb; set pod PID limits.
