What happens when a consumer takes longer to process a message than the configured poll interval?

Kafka · scenario · levels senior, lead

In one line

If processing outlasts max.poll.interval.ms (5 min default), the consumer is evicted from the group, a rebalance gives its partitions to others, its offset commit fails and the records are processed again; repeated, this becomes a rebalance storm with no progress.

Detailed explanation

Kafka uses two liveness checks. A background thread sends heartbeats, judged against session.timeout.ms (45 s default), which detects crashed processes. Separately, the consumer must call poll() again within max.poll.interval.ms, which detects a process that is alive but stuck or too slow. If the gap between polls exceeds the limit, the client proactively leaves the group.

The consequences chain together. The coordinator triggers a rebalance and assigns the slow consumer's partitions to other members, which start from the last committed offset. When the slow consumer finally finishes its batch and tries to commit, it gets a CommitFailedException (or Spring Kafka logs that the commit failed because the group rebalanced), so its work is not recorded and another consumer reprocesses the same records: duplicates, and possibly concurrent processing of the same records for a while. If the cause is structural, for example every batch of 500 records takes six minutes, every member keeps being evicted, the group keeps rebalancing, lag grows and nothing ever commits: a rebalance storm.

Fixes, in order of preference:

  • Reduce the work per poll with a smaller max.poll.records (default 500).
  • Make processing faster: batch database writes, add timeouts on downstream calls, remove slow synchronous work.
  • Increase max.poll.interval.ms for genuinely long jobs, knowing that it also delays detection of stuck consumers.
  • Hand records to a worker pool and pause() the partitions while you keep calling poll(), then resume() and commit when done.
  • Move heavy, long-running work to a job system, with Kafka only triggering it.

How it works

  1. Consumer polls 500 records.
  2. Processing takes longer than max.poll.interval.ms.
  3. Client leaves the group; coordinator rebalances.
  4. Partitions go to another consumer, which restarts from the committed offset.
  5. Slow consumer's commit fails; records are processed twice.
  6. If every batch is slow, steps 1-5 repeat forever.

Example

# Symptom in logs:
# "consumer poll timeout has expired... the poll loop is spending too much time processing messages"
max.poll.records=50
max.poll.interval.ms=600000
session.timeout.ms=45000
// Pause/resume pattern with the plain consumer
ConsumerRecords<String, Order> recs = consumer.poll(Duration.ofMillis(200));
if (!recs.isEmpty()) {
    consumer.pause(consumer.assignment());
    Future<?> job = workers.submit(() -> processAll(recs));
    while (!job.isDone()) consumer.poll(Duration.ofMillis(200)); // keeps membership, returns nothing
    consumer.commitSync();
    consumer.resume(consumer.assignment());
}

Common mistakes

  • Only raising session.timeout.ms, which does not help.
  • Setting max.poll.interval.ms to hours, hiding real hangs.
  • Calling downstream services with no timeouts inside the listener.
  • Processing asynchronously but still committing immediately, losing messages.

How to answer in the interview

"Kafka expects the consumer to call poll again within max.poll.interval.ms, five minutes by default. If a batch takes longer, the consumer is considered stuck and leaves the group, a rebalance hands its partitions to others, and they restart from the last committed offset. When the slow consumer tries to commit it gets a CommitFailedException, so those records are processed twice. If every batch is slow, the group rebalances endlessly and makes no progress. I fix it by lowering max.poll.records, speeding up processing, raising the interval only when justified, or processing on a worker pool while pausing the partitions and continuing to poll."

Likely follow-up questions

  • How is max.poll.interval.ms different from session.timeout.ms? One checks poll-loop progress, the other heartbeats from a background thread.
  • How do you detect this in production? Rebalance rate, commit failures, growing lag and the poll-timeout log warning.
  • Does static membership help? It reduces rebalances on restarts, but not evictions caused by slow processing.
