How do you keep a RAG index in sync with changing source documents?

LLMOps & RAG · concept · levels mid, senior

In one line

Keep a RAG index fresh with incremental indexing driven by change detection (change feeds, webhooks, timestamps or content hashes), stable chunk IDs derived from the document ID so a document's chunks can be replaced together, explicit deletion handling, version and date metadata, freshness monitoring and periodic full rebuilds.

Detailed explanation

Re-embedding the whole corpus on every change is slow and expensive, and nightly full rebuilds leave the assistant a day out of date. Incremental indexing processes only what changed.

Change detection comes in three flavours, best first: push (webhooks, event streams), pull deltas (Microsoft Graph delta queries for SharePoint/OneDrive, Confluence's "modified since" search, database CDC) and scan and compare (list documents, compare modification time and a content hash with what the index stored). Hashing also avoids re-embedding documents whose timestamp changed but content did not.

Stable IDs make replacement simple: chunk IDs like docId#0003 mean "delete all chunks with doc_id = X, then insert the new ones", so a shorter new version does not leave orphan chunks behind.

Deletions are the most forgotten part. If withdrawn policies stay in the index, the assistant keeps quoting them confidently. Delta APIs report deletions; for scan-based sources you compare the full ID list periodically (a tombstone sweep). Permission changes are a related kind of update and must be synced too.

Metadata such as version, effective date, status (draft, current, superseded) and last-modified lets retrieval filter or boost current content and lets answers show dates.

How it works

  1. Connector fetches changes (delta token, webhook or scan).
  2. For each changed document: compute hash; skip if unchanged.
  3. Parse, chunk and embed; upsert chunks with doc_id, version and dates.
  4. Delete old chunks of that document not in the new set.
  5. Process deletions and permission changes.
  6. Record source-change and index time; alert on lag; rebuild fully on a schedule or after embedding/chunking changes.

Example

for change in source.delta(since=state.token):
    if change.deleted:
        index.delete(filter={"doc_id": change.id})
        continue
    doc = source.fetch(change.id)
    h = sha256(doc.content)
    if h == store.hash(change.id):
        continue
    chunks = chunk(parse(doc))
    index.delete(filter={"doc_id": doc.id})
    index.upsert([{"id": f"{doc.id}#{i:04d}", "vector": embed(c), "doc_id": doc.id,
                   "version": doc.version, "modified": doc.modified} for i, c in enumerate(chunks)])
    store.save_hash(doc.id, h)
state.token = source.latest_token()

Common mistakes

  • Ignoring deletions, so retired documents live on forever.
  • Random chunk IDs, which make replacing a document's chunks unreliable.
  • Not monitoring sync failures; a broken connector silently freezes the index.
  • Changing the embedding model or chunker without a full rebuild.

How to answer in the interview

"I'd index incrementally. Where the source has a change feed or delta API, like SharePoint delta queries, I use it; otherwise I compare timestamps and content hashes on a schedule. Chunk IDs derive from the document ID, so I can delete and replace all chunks of a changed document atomically. Deletions and permission changes are processed explicitly, because stale or withdrawn content is the most damaging failure. Each chunk carries version and date metadata so retrieval can prefer current versions. I monitor index lag per source and run a periodic full rebuild to correct drift."

Likely follow-up questions

  • Document changing every few minutes? Debounce updates, index at most every N minutes, or fetch it live via a tool.
  • How do you detect drift? Compare source and index document counts and hashes periodically.
  • Blue-green index? Build a new index for full rebuilds and switch an alias when validated.
