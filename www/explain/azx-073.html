How do you monitor AKS clusters with Azure-native tools?

Azure Kubernetes (AKS) · concept · levels mid, senior

In one line

Use Azure Monitor managed service for Prometheus for metrics, Azure Managed Grafana for dashboards, Container Insights for container logs and events in Log Analytics, diagnostic settings for control plane logs, plus recommended alert rules, while controlling log volume to keep costs down.

Detailed explanation

Azure's native stack covers the three signals you need for AKS.

Metrics: Managed Prometheus runs collector agents in the cluster that scrape node, kubelet, cAdvisor and kube-state-metrics data, plus application metrics via standard ServiceMonitor/PodMonitor resources or annotations. Data goes to an Azure Monitor workspace with long retention; you query it with PromQL and no longer run Prometheus servers or worry about storage.

Dashboards: Azure Managed Grafana connects to the workspace with Entra ID and ships prebuilt Kubernetes dashboards (cluster, namespace, node, pod).

Logs: Container Insights collects container stdout/stderr, Kubernetes events and inventory into a Log Analytics workspace (table ContainerLogV2, KubeEvents, KubePodInventory), queried with KQL.

Control plane: AKS hides the master nodes, so you enable diagnostic settings to send categories like kube-apiserver, kube-audit or kube-audit-admin, kube-controller-manager, kube-scheduler, cluster-autoscaler and guard (Entra auth) to Log Analytics. Audit logs answer "who deleted my deployment?".

Alerts: enable the recommended Prometheus alert rules (node not ready, pod restarts, OOM, CPU throttling, PV filling up) and add SLO-based alerts on application metrics. Route through action groups to on-call tools.

Cost: log ingestion is often the biggest monitoring cost. Use the cost-optimised collection presets, exclude noisy namespaces, collect kube-audit-admin instead of full kube-audit, use the Basic or auxiliary log plans for verbose tables, and set retention deliberately.

How it works

  1. Create an Azure Monitor workspace, a Log Analytics workspace and Managed Grafana.
  2. Enable Prometheus metrics and Container Insights on the cluster.
  3. Add diagnostic settings for control plane categories.
  4. Import dashboards and enable recommended alerts.
  5. Tune collection settings and review ingestion monthly.

Example

az aks update -g rg-apps -n aks-prod --enable-azure-monitor-metrics \
  --azure-monitor-workspace-resource-id $AMW_ID --grafana-resource-id $GRAFANA_ID
az aks enable-addons -g rg-apps -n aks-prod -a monitoring --workspace-resource-id $LAW_ID

Common mistakes

  • Collecting every log line from every namespace and getting a huge bill.
  • Not enabling control plane logs until after an incident.
  • Alerting on CPU percentage alone instead of user-facing symptoms.
  • Running self-managed Prometheus without long-term storage or HA.

How to answer in the interview

"For metrics I use Azure Monitor managed Prometheus, which scrapes cluster and application metrics into an Azure Monitor workspace, with Managed Grafana dashboards on top. Container Insights sends container logs, events and inventory to Log Analytics for KQL queries. Control plane logs like the API server and audit logs are enabled through diagnostic settings. I turn on the recommended alert rules and add SLO-based application alerts. And I watch log volume, filtering namespaces and using cheaper log plans, because ingestion costs add up quickly."

Likely follow-up questions

  • Which log shows a deleted deployment? kube-audit or kube-audit-admin, which record delete verbs and the user.
  • Can you use OpenTelemetry? Yes, send app traces to Application Insights via the Azure Monitor exporter.
  • How do you reduce cost? Presets, namespace filters, Basic logs and shorter retention.
