How do KMS key policies, envelope encryption and key rotation work in detail?

Cloud (AWS) · concept · levels senior

In one line

A key policy is the primary access control for each KMS key, ideally separating key administrators from key users; envelope encryption encrypts data locally with a data key that is itself encrypted by the KMS key; automatic rotation adds new key material while keeping old material for decryption; and grants, encryption context and CloudTrail refine and audit access.

Detailed explanation

Key policies: every KMS key has exactly one key policy. Unlike most resources, IAM policies alone cannot grant access unless the key policy includes the statement that enables IAM policies for the account (the default key policy does). Good policies separate administrators (kms:Create, Put, Enable, ScheduleKeyDeletion, but not Encrypt or Decrypt) from users (Encrypt, Decrypt, ReEncrypt, GenerateDataKey*, DescribeKey). Condition keys like kms:ViaService restrict use to a service such as S3 in one region, and kms:CallerAccount or principal conditions limit cross-account use.

Envelope encryption: KMS encrypts at most 4 KB directly, and sending large data to KMS would be slow. So clients call GenerateDataKey, receiving a plaintext data key and the same key encrypted under the KMS key. The plaintext key encrypts the data locally with AES-256-GCM and is then wiped from memory; the encrypted data key is stored alongside the ciphertext. To decrypt, the client sends the encrypted data key to KMS Decrypt, which checks permissions and returns the plaintext key. The KMS key never leaves the HSMs. S3, EBS, RDS and the AWS Encryption SDK all use this pattern, and S3 Bucket Keys reduce KMS calls.

Rotation: for symmetric customer managed keys, automatic rotation creates new key material yearly by default, or on a custom period from 90 days to 7 years, with on-demand rotation also available. The key ID and ARN stay the same; new encryptions use new material and old material is kept forever to decrypt existing data, so nothing needs re-encrypting. AWS managed keys rotate yearly automatically. Imported key material and asymmetric keys need manual rotation via aliases.

Grants give temporary, programmatic permissions (used by EBS and RDS). Encryption context is non-secret key-value data bound to the ciphertext as additional authenticated data; decryption fails if it differs, and it appears in CloudTrail and can be required in policy conditions. CloudTrail logs every KMS API call.

How it works

  1. App calls GenerateDataKey with the key ID and encryption context.
  2. KMS checks the key policy and IAM, returns plaintext and encrypted data key.
  3. App encrypts data locally and discards the plaintext key.
  4. App stores ciphertext and encrypted data key together.
  5. For reading, app calls Decrypt with the encrypted key and same context.
  6. Rotation adds new material; old ciphertexts still decrypt.

Example

{
  "Sid": "KeyUsers",
  "Effect": "Allow",
  "Principal": {"AWS": "arn:aws:iam::111122223333:role/orders-api"},
  "Action": ["kms:Encrypt", "kms:Decrypt", "kms:GenerateDataKey*", "kms:DescribeKey"],
  "Resource": "*",
  "Condition": {"StringEquals": {
    "kms:ViaService": "s3.eu-west-1.amazonaws.com",
    "kms:EncryptionContext:aws:s3:arn": "arn:aws:s3:::orders-data"}}
}
aws kms enable-key-rotation --key-id $KEY --rotation-period-in-days 180
aws kms generate-data-key --key-id alias/orders --key-spec AES_256 \
  --encryption-context tenant=acme

Common mistakes

  • Removing the account root statement and locking everyone out of the key.
  • Giving administrators decrypt rights by default.
  • Thinking rotation re-encrypts existing data or changes the key ARN.
  • Scheduling deletion of a key still protecting data.

How to answer in the interview

"Every KMS key has a key policy, the primary control; IAM policies only work if the key policy delegates to the account. I separate key administrators, who manage but cannot use the key, from key users who encrypt and decrypt. KMS only encrypts 4 KB directly, so services use envelope encryption: GenerateDataKey returns a plaintext data key used locally and discarded, plus an encrypted copy stored next to the data. Automatic rotation creates new material yearly or on a custom period and keeps old material for decryption. Grants give temporary access, encryption context binds ciphertext to metadata, and CloudTrail logs every use."

Likely follow-up questions

  • What happens if a customer managed key is deleted? All data encrypted under it becomes unrecoverable; deletion has a 7 to 30 day waiting period to cancel.
  • How share encrypted data cross-account? Customer managed key with key policy allowing the other account, plus their IAM permissions.
  • What is a multi-Region key? Related keys with the same material in several regions, for decrypting replicated data locally.
