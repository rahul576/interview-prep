How does Docker isolate containers from each other and from the host?

Docker · concept · levels senior

In one line

Containers are ordinary processes isolated by namespaces (pid, net, mnt, uts, ipc, user, cgroup), limited by cgroups, hardened with dropped capabilities, a seccomp syscall filter and AppArmor/SELinux profiles, but they share the host kernel, so isolation is weaker than VMs.

Detailed explanation

There is no "container" object in the Linux kernel. A container is a process tree that the runtime wraps in several kernel features, each addressing a different risk.

Namespaces control what a process can see. The PID namespace gives the container its own process tree with its main process as PID 1. The network namespace gives it its own interfaces, routes and ports. The mount namespace gives it its own filesystem view, rooted in the image. UTS isolates the hostname, IPC isolates shared memory and message queues, the cgroup namespace hides the host's cgroup tree, and the optional user namespace maps container UIDs to unprivileged host UIDs.

Control groups control what a process can use: CPU, memory, block I/O and the number of processes, preventing one container from starving the host or fork-bombing it.

Several layers restrict what a process can do. Linux capabilities split root's powers; Docker keeps only a small default set and drops dangerous ones like SYS_ADMIN, SYS_MODULE and SYS_TIME, so root in a container cannot load kernel modules or change the clock. A default seccomp profile blocks dozens of risky system calls (such as kexec_load, mount without privileges, keyctl). AppArmor (Ubuntu, Debian) or SELinux (RHEL, Fedora) apply mandatory access control to files and resources. no-new-privileges and read-only root filesystems add more.

All containers still run on the same kernel. A kernel vulnerability or a misconfiguration (privileged mode, host mounts, socket access) can allow an escape. For untrusted or multi-tenant workloads, add sandboxed runtimes such as gVisor or Kata Containers, or microVMs like Firecracker.

How it works

  1. Runtime creates new namespaces for the process.
  2. It places the process in a cgroup with limits.
  3. It pivots root to the image filesystem.
  4. It drops capabilities and applies seccomp and LSM profiles.
  5. It executes the container's command inside this sandbox.

Example

docker run --rm alpine sh -c 'echo $$; hostname; ip addr | grep inet'  # PID 1, own hostname, own IPs
docker run --rm alpine grep Cap /proc/self/status                     # reduced capability set
docker inspect -f '{{.HostConfig.SecurityOpt}}' app
lsns -p $(docker inspect -f '{{.State.Pid}}' app)                     # namespaces on the host

Common mistakes

  • Treating containers as a strong security boundary for untrusted code.
  • Using --privileged, which disables most of these layers.
  • Running as root without user namespaces.
  • Disabling seccomp or AppArmor to "fix" a failing app.

How to answer in the interview

"Containers are ordinary Linux processes with several isolation layers. Namespaces give each container its own view of process IDs, network, mounts, hostname, IPC and optionally user IDs. cgroups limit CPU, memory, I/O and process counts. Docker drops most capabilities, so even root in a container can't load kernel modules or change the clock; a default seccomp profile blocks dangerous syscalls, and AppArmor or SELinux restrict file access. But all containers share the host kernel, so a kernel bug can allow an escape, which is why containers are weaker isolation than VMs, and for untrusted code I'd add gVisor or Kata."

Likely follow-up questions

  • What does --privileged turn off? Capability dropping, seccomp, AppArmor/SELinux confinement and device restrictions.
  • How do user namespaces help? Container root maps to an unprivileged host UID.
  • When use gVisor or Kata? Multi-tenant or untrusted workloads.
