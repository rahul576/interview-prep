What are code quality metrics, and how do you use them without slowing the team down?

Artifacts & Code Quality · concept · levels entry, mid

In one line

Code quality metrics (coverage, bugs, vulnerabilities, code smells, duplication, complexity) help when used as fast feedback on new code, with automatic linters and formatters, PR-level results and sensible gates, not as vanity targets like 100% coverage.

Detailed explanation

Metrics are signals, not goals. Used well, they catch problems early and keep a code base changeable; used badly, they become bureaucracy that developers game or bypass.

Common metrics:

  • Test coverage (line/branch): how much code tests execute. Useful to find untested risky areas; it says nothing about assertion quality.
  • Bugs and vulnerabilities from static analysis, plus security hotspots to review.
  • Code smells: maintainability issues like long methods, deep nesting, dead code.
  • Duplication: copy-pasted blocks that drift apart.
  • Cyclomatic and cognitive complexity: how hard a function is to test and understand.
  • Technical debt ratio as an estimate of remediation effort.

Not slowing the team down comes from four practices. First, gate new code only ("Clean as You Code"): a PR must meet the bar for the lines it touches, so legacy debt does not block every change, while the code base improves with each change. Second, automate style: formatters (Prettier, Black, gofmt, Spotless) and linters (ESLint, Ruff, Checkstyle) run in pre-commit hooks and CI, so style is never discussed in reviews. Third, fast feedback in the PR: results as inline comments within minutes, plus IDE plugins (SonarQube for IDE) so issues are fixed before pushing. Fourth, sensible thresholds: around 80% coverage on new code, zero new critical issues; avoid 100% coverage targets, which lead to tests of getters and assertion-free tests.

How it works

  1. Developer gets IDE and pre-commit feedback.
  2. CI runs formatter check, linters, tests with coverage, static analysis.
  3. Quality gate evaluates the new code in the PR.
  4. Results posted inline; gate is a required check.
  5. Team reviews trends periodically, not individual numbers.

Example

# .pre-commit-config.yaml
repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.6.9
    hooks:
      - id: ruff
        args: [--fix]
      - id: ruff-format

Scenario: a legacy service has 18% coverage and fails every overall gate. The team switches the gate to new code, requires 80% coverage on changed lines and adds characterisation tests before refactoring hot spots. Six months later, the most-changed modules are well covered without a "testing freeze".

Common mistakes

  • 100% coverage mandates that produce meaningless tests.
  • Gates on the whole code base that make every PR red.
  • Arguing about formatting in code review instead of automating it.
  • Using metrics to rank individual developers.

How to answer in the interview

"The usual metrics are coverage, bugs and vulnerabilities from static analysis, code smells, duplication and complexity, typically from SonarQube. The key to not slowing people down is applying quality gates only to new code, so each pull request meets the bar for what it changes and the code base improves over time. Formatters and linters run in pre-commit and CI, so style never comes up in reviews, and results appear inline in the PR within minutes. I avoid vanity targets like 100% coverage; meaningful tests on risky code matter more than the number."

Likely follow-up questions

  • Legacy code base failing every gate? Gate new code, baseline existing issues, improve hot spots opportunistically.
  • Is coverage a good metric? Necessary but not sufficient; mutation testing shows test strength.
  • Who sets thresholds? The team, agreed and revisited, not imposed per individual.
