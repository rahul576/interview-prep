What are Azure Verified Modules, and should you use them or write your own modules?

Terraform · concept · levels mid, senior

In one line

Azure Verified Modules (AVM) are Microsoft-owned, officially supported modules for Terraform and Bicep: resource modules per resource type and pattern modules for architectures, with consistent interfaces and Well-Architected defaults; adopt them, usually wrapped thinly for company standards and version-pinned.

Detailed explanation

Before AVM, Azure had several overlapping module efforts with different quality. AVM is Microsoft's single initiative with a published specification, ownership by named Microsoft teams, testing requirements and a support statement.

Module types:

  • Resource modules (avm-res-...), one per Azure resource type, such as Key Vault or AKS. Besides the core resource they share standard interfaces: diagnostic_settings, private_endpoints, role_assignments, lock, managed_identities, customer_managed_key and tags. Once you know one module, you know how to enable private endpoints on all of them.
  • Pattern modules (avm-ptn-...) combine resources into architectures, such as hub networking or the Azure landing zone.
  • Utility modules (avm-utl-...) provide helpers like region information.

Benefits: secure defaults aligned with the Well-Architected Framework, ongoing maintenance as providers change, semantic versioning, and speed. Writing and maintaining a high-quality Key Vault module with private endpoints and diagnostics yourself takes real effort.

Caveats: some modules are young and change their interfaces between minor versions (many are still 0.x), they expose many options, and they encode Microsoft's defaults, not your company's naming, tagging or allowed SKUs. A common approach is a thin internal wrapper that calls the AVM module, fixes company decisions (naming, mandatory tags, diagnostics to the central workspace, allowed SKUs) and exposes a small interface. Pin versions and upgrade through reviewed PRs like any dependency.

How it works

  1. Search the AVM index for the resource or pattern.
  2. Review the module's inputs, defaults, maturity and issues.
  3. Create a thin internal wrapper with company standards.
  4. Pin the AVM version; publish the wrapper to the private registry.
  5. Upgrade AVM versions via automated PRs and plan review.

Example

module "key_vault" {
  source  = "Azure/avm-res-keyvault-vault/azurerm"
  version = "~> 0.10"   # pin; check the registry for the current release

  name                = "kv-orders-prod-weu"
  location            = "westeurope"
  resource_group_name = azurerm_resource_group.orders.name
  tenant_id           = data.azurerm_client_config.current.tenant_id

  public_network_access_enabled = false
  private_endpoints = {
    pe1 = { subnet_resource_id = var.pe_subnet_id }
  }
  diagnostic_settings = {
    central = { workspace_resource_id = var.log_analytics_id }
  }
  tags = local.common_tags
}

Common mistakes

  • Using AVM modules with floating versions.
  • Building heavy wrappers that re-expose every AVM variable.
  • Assuming AVM defaults satisfy company policy without checking.
  • Writing custom modules that duplicate AVM without a reason.

How to answer in the interview

"Azure Verified Modules is Microsoft's initiative for officially supported Terraform and Bicep modules. Resource modules cover one resource type with consistent interfaces for diagnostics, private endpoints, role assignments, locks and tags; pattern modules combine them into architectures like hub networking or landing zones. They follow Well-Architected defaults and are maintained as providers change, which saves a lot of work. I usually adopt them, wrapped in thin internal modules that enforce our naming, tags and allowed SKUs, and pin their versions."

Likely follow-up questions

  • When would you write your own? No AVM exists, it is immature, or your requirements conflict with its design.
  • How do you handle breaking changes in 0.x versions? Pin tightly and read changelogs per upgrade.
  • Bicep or Terraform AVM? Same concepts; choose by your IaC standard.
