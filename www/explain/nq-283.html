What is CI/CD?

DevOps & CI/CD · concept · levels entry

In one line

CI/CD automates the path from commit to production: Continuous Integration merges small changes often with an automated build and tests, and Continuous Delivery/Deployment automatically packages and deploys every passing change, so releases are fast, small, repeatable and safe.

Detailed explanation

Without CI/CD, teams merge large branches late, discover conflicts and bugs during "integration week", and deploy manually with long checklists, so releases are rare and risky.

Continuous Integration: developers integrate into the main branch frequently, at least daily, using short-lived branches and pull requests. Every change triggers a pipeline that compiles, runs unit tests, static analysis and security scans. A broken build is fixed immediately, so main is always healthy and feedback arrives in minutes.

Continuous Delivery: every change that passes CI produces a versioned artifact (jar, container image) that is automatically deployed to test and staging environments and is always releasable. Production release is a business decision, often an approval click.

Continuous Deployment: removes that manual step; every passing change goes to production automatically, which requires strong tests, monitoring and safe rollout strategies.

Common tools: Jenkins, GitHub Actions, GitLab CI, Azure DevOps Pipelines, plus Argo CD for GitOps deployments. Benefits: fast feedback, fewer integration problems, smaller and safer releases, repeatability and an audit trail. Health is measured with the DORA metrics: deployment frequency, lead time for changes, change failure rate and time to restore service.

How it works

  1. Developer pushes a branch and opens a pull request.
  2. Pipeline builds, tests and scans the change.
  3. After review, the change merges into main.
  4. Pipeline builds the artifact once and stores it in a registry.
  5. Artifact is deployed to dev, test and staging with automated tests.
  6. Production deploy happens by approval or automatically, with monitoring and rollback.

Example

name: ci
on: [push, pull_request]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { distribution: temurin, java-version: '21', cache: maven }
      - run: ./mvnw -B verify

Common mistakes

  • Calling a scheduled nightly build "CI".
  • Long-lived feature branches that defeat integration.
  • Rebuilding the artifact per environment.
  • Ignoring red builds or flaky tests.

How to answer in the interview

"CI/CD automates how code gets from a commit to production. Continuous Integration means merging small changes into main frequently, with every change triggering an automated build and tests, so problems show up in minutes. Continuous Delivery means each passing change is packaged and deployed automatically to test environments and is always ready for production, usually with an approval. Continuous Deployment goes further and releases automatically. I've used Jenkins and GitHub Actions. The benefits are fast feedback, smaller, safer releases and repeatability, which you can track with DORA metrics."

Likely follow-up questions

  • What metrics show a healthy CI/CD process? DORA metrics plus build duration and flaky test rate.
  • What is trunk-based development? Integrating into main frequently with short-lived branches and feature flags.
  • What is GitOps? Desired state in Git, reconciled to the cluster by a tool like Argo CD.
