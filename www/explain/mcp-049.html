What responsibilities belong to the MCP host rather than the server?

MCP Servers · concept · levels mid, senior

In one line

The host owns the user experience and most of the safety: it manages a client per server, keeps servers isolated, aggregates tools, decides what enters the model context, obtains user consent and approvals, enforces organisational policy, handles errors and timeouts, and shows the user what is happening.

Detailed explanation

MCP has three roles. The host is the application the user interacts with, such as a desktop chat app, an IDE or an agent runtime. Inside it, a client maintains a one-to-one connection with each server. Because the host is the only component that sees the user, the model and all servers at once, the specification places most consent and safety responsibilities there.

Connection management: the host creates clients, handles initialisation, capability negotiation, reconnection and shutdown, and keeps servers isolated: one server does not see another's tools, results or the full conversation.

Context control: the host aggregates tools from all servers, handles name collisions, and decides which tools, resources and prompts are visible for a task. It decides what goes into the model context, which is a security decision as well as a cost one.

Consent and approvals: before a tool with side effects runs, the host should show what will happen and ask the user, and it should make it clear which server is asking when a server requests sampling or elicitation.

Policy and reliability: the host enforces allowed-server lists and organisational settings, applies timeouts and retries, and surfaces errors clearly.

The server is still responsible for its own authorization, input validation and safe tool behaviour. A server cannot assume the host is well behaved, because any client can connect to it.

How it works

  1. Host reads configuration and policy, starts or connects to approved servers.
  2. Each client negotiates capabilities and lists tools, resources and prompts.
  3. Host filters and namespaces tools and sends the relevant ones to the model.
  4. Model requests a tool call; host checks policy, asks for approval if needed, routes it to the right client.
  5. Host applies timeouts, shows progress and the result, and logs the action.

Example

User: "Email the Q3 summary to the finance team."
Host:  model wants  mail.send_email
       server: corp-mail (approved)   side effect: yes
       to: finance@corp.example
       subject: Q3 summary
       body: [shown in full]
       [Approve] [Edit] [Deny]

Common mistakes

  • Assuming the server enforces user consent; the protocol leaves that to the host.
  • Sending every tool from every server to the model on every turn.
  • Truncating tool descriptions in the UI so users cannot see what the model sees.
  • Relying on the host for server-side authorization.

How to answer in the interview

"The host is the application the user talks to, so it carries most of the safety and experience responsibility. It creates and manages one client connection per server, handles their lifecycle and keeps servers isolated from each other. It aggregates the tools and decides what enters the model context for a task. It handles consent: showing what a tool will do and asking for approval before side effects, and making clear which server is asking for input. It applies organisational policy like allowed servers, handles errors, timeouts and retries, and keeps the user informed. The server, though, is still responsible for its own authorization and safe tool behaviour, because it can't trust that every host is well behaved."

Likely follow-up questions

  • Why can a server not rely on the host? Any client, including a malicious script, can call it directly.
  • Who handles sampling consent? The host, which can show and edit the request before it reaches the model.
  • How does the host avoid name collisions? By prefixing tools with the server name.
