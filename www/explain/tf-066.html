How do you publish values from Terraform for applications and other teams to consume?

Terraform · concept · levels mid, senior

In one line

Use outputs for humans and the calling pipeline, but publish values for applications and other teams to a dedicated store (SSM Parameter Store, Azure App Configuration, Key Vault for secrets) that consumers read with data sources or at runtime, instead of terraform_remote_state, which couples them to your state and exposes all of it.

Detailed explanation

Outputs are the natural interface of a configuration: the pipeline can read terraform output -json and pass values to the next step, and humans can see endpoints after an apply. Within one team, that is often enough.

Across teams and applications, outputs read via terraform_remote_state cause problems. The consumer needs read access to the whole state file, which contains every attribute of every resource, including secrets such as generated passwords and keys. Consumers also become coupled to your backend location and output names; if you split or move your state, their code breaks. And applications at runtime should not depend on Terraform at all.

A better contract is to publish values explicitly. Terraform writes non-secret values like endpoints, resource IDs, queue names and subnet IDs into AWS SSM Parameter Store, Azure App Configuration or a well-named set of Key Vault entries, with a clear hierarchy such as /prod/orders/db-endpoint. Secrets go only into a secret store (Key Vault, Secrets Manager), ideally generated so they never pass through humans. Consumers then use data sources (aws_ssm_parameter, azurerm_app_configuration_key) in their own Terraform, and applications read them at runtime with their workload identity, with permissions scoped to exactly the keys they need.

For Kubernetes workloads, values flow into ConfigMaps via GitOps, and secrets via the External Secrets Operator or the Secrets Store CSI driver reading Key Vault, so no secret is ever committed.

How it works

  1. Decide the contract: which values are shared, names and owners.
  2. Terraform writes them to the parameter store or secret store.
  3. Grant consumers read access to specific paths only.
  4. Other configurations read via data sources.
  5. Applications read at runtime with workload identity.
  6. Keep outputs for the pipeline and human visibility.

Example

# Producer (database team)
resource "aws_ssm_parameter" "db_endpoint" {
  name  = "/prod/orders/db-endpoint"
  type  = "String"
  value = aws_db_instance.orders.address
}

# Consumer (application team, separate state)
data "aws_ssm_parameter" "db_endpoint" {
  name = "/prod/orders/db-endpoint"
}

resource "aws_ecs_task_definition" "api" {
  # ... uses data.aws_ssm_parameter.db_endpoint.value in the container environment
}

Common mistakes

  • Granting every team read access to production state for remote_state.
  • Publishing secrets as plain parameters or outputs.
  • No naming convention, so parameters become an unstructured dump.
  • Breaking consumers by renaming parameters without a deprecation period.

How to answer in the interview

"Outputs are the basic mechanism and work well for humans and the pipeline that ran Terraform. For applications and other teams I publish values to a dedicated store instead: endpoints and IDs into SSM Parameter Store or App Configuration with clear names like /prod/orders/db-endpoint, and secrets only into Key Vault or Secrets Manager. Other configurations read them with data sources and apps read them at runtime with workload identity. That avoids coupling to my state structure and avoids giving read access to the whole state, which contains secrets."

Likely follow-up questions

  • Why is remote_state access risky? It exposes the entire state, including secrets and full infrastructure details.
  • How do you version the contract? Treat names as an API; add new keys before removing old ones.
  • What about HCP Terraform? tfe_outputs reads only outputs, which is safer than full state access.
