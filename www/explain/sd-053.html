How do you keep a cache consistent with the database when data changes?

Scalability & Reliability · concept · levels entry, mid, senior

In one line

Keep cache and DB consistent by writing the DB then deleting the cache key, guarding against races with delayed double delete, versions or leases, using CDC-driven invalidation for reliability, TTLs as a safety net, and bypassing the cache for critical reads.

Detailed explanation

Perfect consistency between two systems without a shared transaction is impossible; the goal is bounded staleness.

Why delete rather than update? Two writers updating cache values can apply them in the wrong order, leaving an old value indefinitely. Deleting means the next read loads the current DB value.

The classic race with delete: Reader R misses, reads old value V1 from DB… Writer W updates DB to V2 and deletes the key… R then writes V1 into the cache. Now stale until TTL. Mitigations:

  • Delayed double delete: delete again ~1 s after the write.
  • Versioned values: store a version; only set if newer (Lua compare-and-set).
  • Leases (Facebook's Memcache paper): a miss returns a lease token; only the token holder can fill, and a delete invalidates outstanding leases.

CDC-driven invalidation: a consumer reads the DB change log (Debezium) and deletes affected keys. It catches every committed change, even if the app crashed after writing the DB.

How it works

  1. Write: UPDATE db → commit → DEL cache:key (and/or CDC consumer deletes).
  2. Read: cache-aside with TTL (e.g. 5–15 min) as the upper bound on staleness.
  3. Critical reads (balance, stock at checkout): go to the DB.

Example

Debezium (orders table) → Kafka → invalidator → DEL order:{id}, DEL customer:{cid}:orders

Common mistakes

  • Updating the cache before committing the DB transaction.
  • No TTL at all.
  • Invalidating only one of several cached representations of the same data.

How to answer in the interview

"I write the database first, then delete the cache entry, so the next read loads fresh data. Because there's still a race where a slow reader re-populates an old value, I'd add a delayed second delete or versioned writes, and ideally drive invalidation from CDC so every committed change triggers it. TTLs bound how long anything stale can live, and for critical reads like balances I skip the cache."

Likely follow-up questions

  • Write-through instead? Still racy across writers; deletion is simpler.
  • Multiple cached views of one entity? Track dependencies or use tag-based invalidation.
  • Multi-region caches? Invalidate via replicated events in each region.
