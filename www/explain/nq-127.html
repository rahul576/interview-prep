How does locking work in ConcurrentHashMap?

Collections · concept · levels senior, lead

In one line

Up to Java 7, ConcurrentHashMap used lock striping with segments (16 by default, each a ReentrantLock); since Java 8 the lock granularity is a single bin: CAS for empty bins, synchronized on the head node otherwise, non-blocking reads, and compute functions run while holding the bin lock, so keep them short.

Detailed explanation

Java 7 and earlier. The map was divided into Segment objects, each a small hash table extending ReentrantLock. The constructor's concurrencyLevel (default 16) set the number of segments. A write hashed the key to a segment, locked it and modified its table, so at most 16 writers could proceed in parallel. Reads were mostly lock-free using volatile fields, and only retried under the lock in rare cases. Operations like size() first tried summing segment counts without locking and, if counts changed, locked all segments.

Java 8 and later. Segments were removed (the class still exists only for serialisation compatibility; concurrencyLevel is now just a sizing hint). The table is a single array of bins:

  • Empty bin: insert with a CAS; no lock at all.
  • Occupied bin: synchronized on the first node of the bin. Each bin is its own lock, so the number of possible concurrent writers grows with the table. JVM intrinsic locks are cheap when uncontended, which is the common case.
  • Reads: volatile reads, never locked.
  • Resize: bins are transferred one at a time under their own head lock, with helper threads.

The important practical consequence: compute, computeIfAbsent, computeIfPresent and merge execute your function while the bin lock is held. Readers carry on unaffected, but other writers to that bin block until the function returns. If the function is slow (a remote call, a DB query), it creates contention. If it modifies the same map (for example recursive computeIfAbsent for memoisation), it can deadlock, livelock, or throw IllegalStateException("Recursive update").

How it works

  1. Writer hashes key to bin.
  2. Bin null → casTabAt; success ends the write.
  3. Bin non-null → synchronized (head); re-check head unchanged; update.
  4. Compute functions run inside step 3.
  5. Readers bypass locks entirely.

Example

ConcurrentHashMap<String, Profile> cache = new ConcurrentHashMap<>();

// Risky: slow remote call holds the bin lock
cache.computeIfAbsent(id, k -> remoteClient.fetchProfile(k));

// Better for expensive loads: cache futures, do the work outside the lock
ConcurrentHashMap<String, CompletableFuture<Profile>> futures = new ConcurrentHashMap<>();
CompletableFuture<Profile> f = futures.computeIfAbsent(id,
        k -> CompletableFuture.supplyAsync(() -> remoteClient.fetchProfile(k), ioPool));

// Never: modifying the same map inside compute
// cache.computeIfAbsent(a, k -> cache.computeIfAbsent(b, ...)); // recursive update

Common mistakes

  • Saying Java 8+ still uses segments.
  • Remote I/O inside computeIfAbsent.
  • Recursive modification of the same map inside compute.
  • Thinking synchronized means slow; uncontended locks are cheap.

How to answer in the interview

"Up to Java 7 it used lock striping: the map was split into segments, sixteen by default, each a small hash table with its own ReentrantLock, so up to sixteen writers could work at once. From Java 8 segments were removed and the lock granularity is a single bin: inserting into an empty bin is a lock-free CAS, otherwise the writer synchronises on the bin's first node, and readers never lock. Because compute, computeIfAbsent and merge run my function while holding the bin lock, I keep those functions short and never update other entries of the same map inside them."

Likely follow-up questions

  • Risk of a remote call inside computeIfAbsent? It holds the bin lock for the duration, blocking other writers and risking timeouts piling up; cache a future or use Caffeine.
  • What is concurrencyLevel now? Only an initial sizing hint.
  • Why synchronized instead of ReentrantLock? Lower memory per bin and cheap uncontended locking.
