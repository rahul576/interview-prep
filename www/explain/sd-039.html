Design live comments for a live streaming event with millions of viewers.

Classic Design Problems · design · levels entry, mid, senior

In one line

Live comments use persistent connections to gateway servers, publish each moderated comment to a pub/sub channel per live video, let gateways subscribe and fan out locally, sample/throttle for huge streams, and store comments asynchronously for replay.

Detailed explanation

A live stream can have millions of viewers and thousands of comments per second. Sending every comment to every viewer from one server is impossible; the fan-out must be distributed.

Viewers connect via WebSockets or SSE to a fleet of stateless-ish gateway servers (each holding, say, 100k connections). When a viewer joins video V, their gateway subscribes to channel V (Redis pub/sub, NATS, Kafka-backed fan-out, or a custom service). A posted comment goes to the comment service, which runs moderation and spam checks, then publishes to channel V. Each subscribed gateway receives it once and pushes it to its local viewers.

Humans can't read 5,000 comments/s, so for huge streams the system samples: each viewer receives a subset, prioritising friends, verified users, top-reacted comments and their own comments.

How it works

  1. Viewer → gateway (WS); gateway subscribes to live:V if first local viewer.
  2. Comment → comment service → moderation → publish live:V → async write to DB.
  3. Gateways → local connections (with per-connection rate limit/sampling).
  4. Gateway crash: clients reconnect (with jittered backoff) to other gateways, re-subscribe, fetch last N comments.

Example

Viewer A ──WS──▶ gateway-17 ─┐            ┌─▶ gateway-17 ──▶ 80,000 local viewers
Viewer B ──WS──▶ gateway-42 ─┤ subscribe  │
                              └─ live:V ◀─┤ publish (once)
POST comment ─▶ comment-svc ─▶ moderation ┘─▶ gateway-42 ──▶ 95,000 local viewers

Common mistakes

  • Writing to the DB synchronously before broadcasting.
  • All gateways subscribing to all channels.
  • Thundering-herd reconnects after a gateway failure (use jitter).
  • No sampling for celebrity streams.

How to answer in the interview

"Viewers hold WebSocket connections to gateway servers. Each gateway subscribes to the pub/sub channel of the videos its viewers are watching. A new comment is moderated, published once to that channel, and each gateway fans it out locally, so the work is spread across the fleet. For massive streams we sample what each viewer sees, and comments are stored asynchronously for replay."

Likely follow-up questions

  • Gateway crash with 100k viewers? Jittered reconnects, load balancer spreads them, clients fetch recent comments.
  • Ordering? Approximate order is fine; sequence per channel if needed.
  • Reactions/hearts? Aggregate counts per second instead of individual messages.
