Which metrics do you use to measure LLM serving performance?

LLMOps & RAG · concept · levels mid, senior

In one line

Measure time to first token (TTFT), time per output token / inter-token latency, end-to-end latency percentiles, throughput in tokens and requests per second, and above all goodput, the throughput achieved while meeting latency SLOs, using realistic prompt and output lengths.

Detailed explanation

Users experience two things in a streamed answer: how long before anything appears, and how smoothly it flows. TTFT covers network, queueing and prefill; it grows with prompt length and load, and it dominates perceived responsiveness in chat. Many teams target well under a second for interactive use.

Time per output token (TPOT) or inter-token latency (ITL) measures streaming speed during decode. Roughly 20 to 50 ms per token (20 to 50 tokens per second) reads as fluent, faster than people read. ITL rises as batch size grows, and spikes when long prefills interrupt decoding.

End-to-end latency is roughly TTFT plus output tokens times TPOT. It matters for non-streaming uses: agents chaining several calls, APIs returning JSON, batch pipelines. Always report p50, p95 and p99, because LLM latency distributions are wide: output lengths vary hugely, and averages hide the long tail that users complain about.

Capacity metrics: output tokens per second per GPU (and total tokens per second), requests per second, and derived cost per million tokens. Engine health metrics such as running and waiting requests, KV cache utilisation and preemptions explain why latency changes.

The combined metric is goodput: requests per second (or tokens per second) that meet the SLOs, for example TTFT under 1 s and TPOT under 50 ms at p95. Raising batch size increases raw throughput but eventually breaks latency targets, so peak throughput is misleading. You pick the operating point where goodput is maximised.

Benchmarks must replay realistic distributions of input and output lengths, concurrency and arrival patterns, ideally sampled from production logs, since a 200-token-prompt benchmark says little about a RAG app with 6,000-token prompts.

How it works

  1. Define SLOs per use case (TTFT, TPOT, E2E at p95).
  2. Build a load profile from real traffic.
  3. Sweep concurrency or request rate with a benchmark tool.
  4. Record latency percentiles, throughput and engine metrics.
  5. Choose the highest load that still meets SLOs (goodput) and alert on drift.

Example

vllm bench serve --backend vllm --model meta-llama/Llama-3.1-8B-Instruct \
  --dataset-name random --random-input-len 3000 --random-output-len 300 \
  --request-rate 8 --num-prompts 500 --percentile-metrics ttft,tpot,itl,e2el

Common mistakes

  • Reporting averages instead of percentiles.
  • Benchmarking with short synthetic prompts.
  • Optimising raw throughput and breaking latency.
  • Measuring client side without separating queueing from prefill.

How to answer in the interview

"Users notice how fast the answer starts and how fast it streams, so I track time to first token, which is queueing plus prefill, and time per output token, where 20 to 50 milliseconds feels fluent. For APIs and agents I watch end-to-end latency at p50, p95 and p99. On the capacity side I measure output tokens and requests per second per GPU, which drive cost. The key metric is goodput, the throughput while still meeting latency SLOs, because bigger batches raise throughput but eventually break latency. And I always benchmark with realistic prompt and output lengths."

Likely follow-up questions

  • Why can averages hide problems? Output lengths and queueing vary widely; p99 users wait far longer.
  • What drives TTFT up? Long prompts, queueing, cache misses and prefill contention.
  • How do you lower cost per token? Higher batch within SLO, quantisation, caching, smaller models.
