A Java service shows 100 percent CPU in production. How do you find the cause?

JVM & Performance · scenario · levels mid, senior

In one line

First rule out GC as the CPU consumer; then find the hot threads with top -H, convert their ids to hex and match the nid in several thread dumps (jstack/jcmd), or better, record a flame graph with async-profiler or JFR; usual culprits are infinite loops, regex backtracking, spin waits, serialization and hot-path logging.

Detailed explanation

Is it GC? If the heap is nearly full, the collector runs constantly and burns CPU without freeing much. jstat -gcutil <pid> 1000 showing old generation near 100% with rising full GC counts, or GC logs with back-to-back collections, means this is a memory problem (leak or undersized heap), not code; follow the leak investigation path. GC threads also appear in top -H with names like GC Thread#0 or G1 Conc#0.

Which threads? top -H -p <pid> lists native threads by CPU usage. Take the hot thread id (decimal), convert it with printf '%x', and search the thread dump for nid=0x.... Take three to five dumps a few seconds apart: a thread showing the same stack frames in every dump at 100% CPU is a loop or a pathological regex. JIT compiler threads (C2 CompilerThread) at high CPU right after startup are normal warm-up.

Profiling is better. A sampling profiler shows where CPU goes across all threads, with low overhead and no safepoint bias. async-profiler (asprof -e cpu -d 30 -f cpu.html <pid>) produces an interactive flame graph: the widest frames are where time is spent. JFR (jcmd <pid> JFR.start duration=60s filename=cpu.jfr) records execution samples you open in JDK Mission Control. Both are safe in production for short recordings.

Common causes. Infinite or very long loops (bad termination condition, HashMap corruption in old JDKs from concurrent modification), catastrophic regex backtracking on unexpected input, busy-wait or spin loops, retry loops without backoff, heavy JSON or XML serialisation, expensive logging (string building, stack traces), cryptography or compression in hot paths, and excessive JIT deoptimisation cycles.

Kubernetes specifics. CPU limits cause throttling, which looks like slowness rather than 100% on the host; check container_cpu_cfs_throttled_seconds_total.

How it works

  1. Check GC activity with jstat, GC logs or metrics.
  2. top -H -p <pid> to find hot thread ids.
  3. Convert ids to hex; match nid in thread dumps taken a few seconds apart.
  4. Record a CPU flame graph with async-profiler or JFR.
  5. Identify the method, reproduce, fix and verify with a benchmark.

Example

top -H -p 4211                # thread 4250 at 99% CPU
printf '%x\n' 4250            # 109a
for i in 1 2 3; do jcmd 4211 Thread.print > dump$i.txt; sleep 5; done
grep -A 15 'nid=0x109a' dump*.txt
# "http-nio-8080-exec-7" ... nid=0x109a runnable
#   at java.util.regex.Pattern$Loop.match(...)
#   at com.acme.validation.EmailValidator.isValid(...)

asprof -e cpu -d 30 -f /tmp/cpu.html 4211   # flame graph

Common mistakes

  • Restarting the pod immediately and losing all evidence.
  • Taking a single thread dump and drawing conclusions.
  • Forgetting that the cause may be GC, not application code.
  • Ignoring container CPU throttling.

How to answer in the interview

"First I check whether it's GC: if jstat or the GC logs show constant collections with the old generation full, it's memory pressure, not code. Otherwise I find the busy threads with top -H on the process, convert the thread id to hex and take a few thread dumps with jcmd or jstack a few seconds apart, matching the nid, to see which stack keeps appearing. Better still, I record a short CPU profile with async-profiler or JFR and read the flame graph, which is safe in production. Common causes are an infinite loop, catastrophic regex backtracking, a spin wait, heavy serialization or logging in a hot path."

Likely follow-up questions

  • How would you do this safely inside a Kubernetes pod without a shell? Use kubectl debug with an ephemeral container sharing the process namespace, or trigger JFR via jcmd from it, then kubectl cp the files.
  • What is safepoint bias? Profilers sampling only at safepoints misattribute time; async-profiler and JFR avoid it.
  • How do you prevent regex backtracking? Avoid nested quantifiers, use possessive quantifiers or atomic groups, limit input length.
