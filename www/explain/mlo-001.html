What is MLOps, and how is it different from DevOps?

MLOps · concept · levels entry, mid

In one line

MLOps applies DevOps practices (automation, version control, CI/CD, testing, monitoring) to machine learning systems, adding what ML uniquely needs: versioned data and models, experiment tracking, training pipelines, and monitoring for drift with retraining, across data scientists, ML engineers and operations.

Detailed explanation

A traditional application's behaviour is defined by its code. An ML system's behaviour is defined by code, data and the trained model, and that changes almost everything about how you build and run it.

Versioning must cover all three. To reproduce or audit a model you need the training code commit, the exact data snapshot, the feature logic, the hyperparameters and the environment. Git alone cannot hold large datasets or model binaries, so MLOps adds data versioning and a model registry.

Development is experimental. Data scientists run dozens or hundreds of experiments with different features, algorithms and hyperparameters, so experiment tracking of parameters, metrics and artefacts becomes part of the workflow. Pipelines include data validation, training and evaluation, not just build and deploy, and "tests" include checking model quality against a baseline, not only unit tests. CI/CD may deliver a training pipeline that then produces models, rather than the deployable directly.

Models degrade silently. Even with no code change, accuracy drops when real-world data drifts away from the training data: customer behaviour changes, a new product launches, an upstream field changes meaning. So monitoring covers data quality, feature and prediction distributions and, when labels arrive, actual model performance, and retraining becomes a routine operation, sometimes automated (continuous training).

Finally, MLOps is a collaboration model: data scientists, data engineers, ML engineers and platform or SRE teams share pipelines, tooling and ownership, so a model moves from notebook to production without a hand-over wall.

How it works

  1. Version code, data and configuration together.
  2. Track every experiment run and its artefacts.
  3. Automate a pipeline: validate data, train, evaluate, register.
  4. Deploy models through CI/CD with gradual rollout.
  5. Monitor data, predictions and outcomes in production.
  6. Retrain and redeploy when drift or decay is detected.

Example

# Simplified ML pipeline stages in CI
stages: [validate-data, train, evaluate, register, deploy-canary]
evaluate:
  script:
    - python evaluate.py --candidate $RUN_ID --baseline production
    - python check_thresholds.py --min-auc 0.86 --max-regression 0.01

Common mistakes

  • Treating a model file as a normal binary with no lineage.
  • Monitoring only latency and errors, not prediction quality.
  • Manual hand-over from notebooks to engineers.
  • Assuming a deployed model stays accurate forever.

How to answer in the interview

"MLOps applies DevOps practices like automation, version control, CI/CD, testing and monitoring to machine learning. The difference is that an ML system depends on code, data and a trained model. So we version data and models, not just code, and must be able to reproduce a training run. Development is experimental, so experiment tracking is part of the workflow, and pipelines include training and evaluation. Most importantly, a model can silently degrade without any code change because real-world data drifts, so monitoring covers data and prediction quality and retraining is routine. It also connects data scientists, ML engineers and operations."

Likely follow-up questions

  • Which DevOps practices transfer directly, and which need rethinking? Version control, CI/CD, IaC and observability transfer; testing, versioning and monitoring must expand to data and model quality.
  • What is continuous training? Automatically retraining models on new data via a pipeline.
  • Who owns a model in production? A named team, usually with shared on-call between ML and platform engineers.
