Why is token passthrough forbidden in MCP, and what should a server do instead?

MCP Servers · concept · levels senior, lead

In one line

Token passthrough, forwarding a client's token to downstream APIs or accepting tokens not issued for the server, is forbidden because it bypasses the server's controls, breaks audit and enables confused deputy attacks; the server must only accept tokens whose audience is itself and get a separate downstream token via token exchange / on-behalf-of or its own credentials.

Detailed explanation

Passthrough looks attractive: the client already has a GitHub or Microsoft Graph token, so why not just send it to the MCP server and let the server forward it? The MCP specification prohibits this, for several reasons.

First, audience. A token is a statement that a specific resource may be accessed. If the MCP server accepts a token issued for Graph, or accepts any token without checking its audience, then any token stolen or obtained for another purpose can be replayed at the MCP server, and vice versa. The server must validate that the token was issued for it.

Second, bypassed controls. The MCP server is supposed to apply its own policies: rate limits, input validation, tool-level authorization and auditing. If it merely relays the client's downstream token, the downstream API sees the client directly and the server's controls become optional.

Third, accountability. Downstream logs show the user's token used by an unknown party; nobody can tell that an MCP server and an AI agent were involved, which complicates incident investigation.

Fourth, confused deputy: a token meant for one context is used in another with privileges the user never intended.

The correct pattern is two tokens. The client authenticates to the MCP server with a token whose audience is the MCP server. The server then obtains a separate token for each downstream API, either via OAuth 2.0 Token Exchange (RFC 8693) or the Entra ID on-behalf-of flow, which preserves the user's identity, or via its own service credentials combined with explicit authorization checks.

How it works

  1. Client gets token A with aud = https://mcp.example.com.
  2. Server validates token A: signature, issuer, audience, scopes, expiry.
  3. Server exchanges token A at the IdP for token B with aud = graph and only the scopes it needs.
  4. Server calls the downstream API with token B; logs record both the user and the MCP server.
  5. Token B is cached per user and never returned to the client or model.

Example

POST /oauth2/v2.0/token
grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer
&client_id=mcp-server-app
&client_secret=...
&assertion=<token A>
&scope=https://graph.microsoft.com/Mail.Read
&requested_token_use=on_behalf_of

The returned token B represents the user, delegated through the MCP server's app identity.

Common mistakes

  • Checking only the signature and issuer, not the audience.
  • Asking users to paste downstream API tokens into the MCP client config.
  • Returning downstream tokens in tool results or error messages.
  • Using one shared service account for every user, which creates a different confused deputy problem.

How to answer in the interview

"Token passthrough is when an MCP server accepts a token issued for another service, like GitHub or Graph, and just forwards it, or accepts tokens without checking they were meant for it. The spec forbids it: the server must only accept tokens whose audience is itself. Passthrough bypasses the server's own controls like rate limiting, validation and auditing, it breaks accountability because downstream logs can't see the MCP server was involved, and it enables confused deputy attacks. Instead the server validates its own token and obtains a separate token for downstream calls, through OAuth token exchange or the on-behalf-of flow so the user's identity is preserved, or uses its own credentials with explicit authorization checks."

Likely follow-up questions

  • How does on-behalf-of keep identity? The new token still names the user but is issued to the server's app with limited scopes.
  • What if the downstream API has no OAuth? Use a server-held credential in a vault plus per-user authorization in the server.
  • Where are downstream tokens stored? Server-side, encrypted, keyed by user, never exposed to the model.
