Explain Linux file permissions and what chmod 755 means.

Linux · concept · levels entry

In one line

Each file has read (4), write (2) and execute (1) bits for owner, group and others; chmod 755 gives the owner rwx and everyone else r-x, while chown changes ownership and setuid, setgid and the sticky bit add special behaviour.

Detailed explanation

Linux permissions are evaluated against three classes: the file's owner (user), its group, and others. Each class has three bits. On a file, read lets you view contents, write lets you modify them, and execute lets you run it as a program. On a directory, read lets you list names, write lets you create, delete and rename entries, and execute lets you enter it (cd) and access files inside by name.

Numeric mode adds the values per class: r=4, w=2, x=1. So 755 is owner 7 (4+2+1, rwx), group 5 (4+1, r-x), others 5 (r-x): typical for scripts, binaries and directories. 644 is owner rw-, group and others r--: typical for normal files. 600 keeps a file private, as required for SSH private keys. ls -l shows the symbolic form, for example -rwxr-xr-x. New files get default permissions filtered by the umask (commonly 022, giving 644 files and 755 directories).

chown user:group file changes the owner and group; chgrp only the group. A fourth leading digit holds special bits: setuid (4) runs an executable with the file owner's privileges, as passwd does; setgid (2) runs with the group's privileges, and on a directory makes new files inherit its group, handy for shared team folders; the sticky bit (1) on a directory such as /tmp (mode 1777) means only a file's owner can delete or rename it.

How it works

  1. The kernel checks if you are the owner, then group member, then other.
  2. It applies only the matching class's bits.
  3. Numeric modes sum 4, 2, 1 per class.
  4. umask removes bits from defaults for new files.
  5. Special bits change execution identity or directory behaviour.

Example

chmod 755 deploy.sh        # -rwxr-xr-x
chmod 644 config.yaml      # -rw-r--r--
chmod 600 ~/.ssh/id_ed25519
chmod u+x,g-w script.sh    # symbolic form
chown app:app /var/lib/app
chmod 2775 /srv/shared     # setgid: new files inherit group
ls -ld /tmp                # drwxrwxrwt  (sticky bit)

Common mistakes

  • Using chmod 777 to "fix" permission errors.
  • Forgetting that directories need execute to be entered.
  • Leaving setuid on custom scripts or binaries.
  • Changing permissions recursively with -R and making every file executable.

How to answer in the interview

"Every file has three permission sets, for the owner, the group and others, each with read, write and execute, worth four, two and one. So 755 gives the owner read, write and execute and everyone else read and execute, typical for scripts and directories, while 644 is typical for files. On a directory, execute means you can enter it. chown changes the owner and group. There are special bits too: setuid and setgid run a program with the owner's or group's privileges, setgid on a directory makes files inherit its group, and the sticky bit on /tmp means only owners can delete their own files."

Likely follow-up questions

  • Why is chmod 777 dangerous on a web server? Any user or compromised process can modify files, for example to plant a web shell.
  • What are ACLs? setfacl/getfacl give per-user or per-group rights beyond the three classes.
  • What does umask 027 produce? Files 640 and directories 750.
