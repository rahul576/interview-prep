One team's batch job makes other services on the same nodes slow. How do you handle noisy neighbours in Kubernetes?

Kubernetes · scenario · levels mid, senior, lead

In one line

Confirm the contention with node metrics, then make requests reflect real usage, isolate batch on its own tainted node pool, give batch a lower PriorityClass, cap teams with ResourceQuotas, and remember that disk IO, network and memory bandwidth are not isolated by requests and limits.

Detailed explanation

Kubernetes isolation is mainly about CPU and memory via cgroups, and scheduling is based on requests. If a batch job requests 0.5 CPU but uses 6, the scheduler places it next to latency-sensitive services as if it were small. Without CPU limits it will use all idle CPU, which is fine until the service needs it: CPU shares (weights from requests) protect the service proportionally, but only if its own requests are realistic. Memory overuse is worse: the node comes under pressure and the kubelet may evict pods.

The first step is data: node CPU saturation, run queue, memory pressure (PSI metrics), disk IO wait and network throughput while the batch runs, plus the service's latency. Then fix the declarations: realistic requests and appropriate limits for the batch pods, so the scheduler sees them as large.

The cleaner solution is isolation: a dedicated node pool for batch with a taint such as workload=batch:NoSchedule, batch pods carrying the toleration and a node affinity, so batch and services never share a node. A PriorityClass with lower priority for batch lets the scheduler preempt batch pods when services need room. ResourceQuotas and LimitRanges per namespace stop one team from consuming the whole cluster and enforce default requests.

Shared resources still leak: disk IO on the node's disk, network bandwidth, memory bandwidth and CPU caches, and the kernel's conntrack table. IO-heavy jobs (ETL, compaction) genuinely need separate nodes or volumes with their own IOPS.

How it works

  1. Correlate service latency with node resource metrics during batch runs.
  2. Compare batch requests with actual usage; fix them.
  3. Create a tainted batch node pool; add tolerations and affinity to batch jobs.
  4. Assign a low PriorityClass to batch.
  5. Apply ResourceQuotas and LimitRanges per team namespace.
  6. Move IO-heavy work to separate nodes or storage.

Example

apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata: { name: batch-low }
value: 1000
preemptionPolicy: Never
description: "Batch jobs; may be preempted by services"
---
apiVersion: batch/v1
kind: Job
metadata: { name: nightly-etl, namespace: data }
spec:
  template:
    spec:
      priorityClassName: batch-low
      tolerations: [{ key: workload, value: batch, effect: NoSchedule }]
      nodeSelector: { pool: batch }
      containers:
        - name: etl
          image: registry.example.com/etl:7
          resources:
            requests: { cpu: "4", memory: 8Gi }
            limits: { memory: 8Gi }
      restartPolicy: OnFailure

Common mistakes

  • Tiny requests on heavy batch pods.
  • Taints without node affinity (pods may still land elsewhere).
  • Expecting CPU limits to isolate disk IO.
  • Arguing with the other team without data.

How to answer in the interview

"First I'd confirm the contention with node metrics during the batch run: CPU saturation, memory pressure, disk IO and network. If batch pods have low requests but use much more, the scheduler packs them next to services, so I'd set realistic requests and limits. The cleaner fix is isolation: a tainted node pool just for batch, a lower PriorityClass so batch can be preempted, and ResourceQuotas per team. I'd also point out that Kubernetes doesn't isolate disk IO, network or memory bandwidth, so IO-heavy jobs really need their own nodes."

Likely follow-up questions

  • How to show impact with data? Overlay service p99 latency with batch job schedule and node IO wait on one dashboard.
  • Why preemptionPolicy: Never? Batch waits for room rather than evicting others, while still being preemptible.
  • What are PSI metrics? Pressure stall information showing time tasks wait on CPU, memory or IO.
