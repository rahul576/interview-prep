What are locals in Terraform, and when do you use them?

Infrastructure as Code · concept · levels entry

In one line

Locals are named values computed inside a module (local.name) from variables, resources and functions; they remove repetition and name complex expressions, but unlike variables they cannot be set by callers.

Detailed explanation

A locals block defines one or more named expressions, referenced as local.<name>. They are evaluated inside the module, so they can combine input variables, resource attributes, data sources and functions. Think of variables as a module's parameters and locals as its internal helper variables.

Typical uses are a name prefix like "${var.project}-${var.environment}" used by every resource, a common tags map merged into each resource's tags, derived maps that reshape an input list into a map keyed by name so for_each can iterate it, and environment-dependent settings such as instance sizes chosen with a conditional or a lookup table. Giving a long expression a meaningful name makes the configuration easier to read and review, and changing the value in one place updates every use.

Locals should not be overused. If a value is something a caller might reasonably want to change, it belongs in a variable with a sensible default, not hidden in a local. Very long chains of locals referencing other locals also make debugging harder; terraform console helps inspect what a local evaluates to. Locals cannot be referenced across modules: to expose one, return it through an output.

How it works

  1. Declare values in one or more locals {} blocks in any .tf file of the module.
  2. Terraform evaluates them lazily as part of the dependency graph.
  3. Reference them as local.name (singular local, plural locals block).
  4. A local depending on a resource attribute may be "known after apply".
  5. Expose a local outside the module only via an output.

Example

locals {
  name_prefix = "${var.project}-${var.environment}"
  common_tags = {
    Project     = var.project
    Environment = var.environment
    ManagedBy   = "terraform"
  }
  services_by_name = { for s in var.services : s.name => s }
}

resource "aws_s3_bucket" "logs" {
  bucket = "${local.name_prefix}-logs"
  tags   = merge(local.common_tags, { Purpose = "logs" })
}

resource "aws_ecs_service" "svc" {
  for_each = local.services_by_name
  name     = "${local.name_prefix}-${each.key}"
  # ...
}

Common mistakes

  • Hiding values in locals that callers need to override.
  • Writing locals.name instead of local.name.
  • Building deep chains of locals that are hard to follow.
  • Repeating the same tag map in every resource instead of one local (or provider default_tags).

How to answer in the interview

"Locals are named values computed inside a module, defined in a locals block and referenced as local.something. They can be built from variables, resources and functions, but unlike input variables nobody outside the module can set them. I use them to avoid repeating expressions, for example a name prefix of project and environment, a common tags map I merge into every resource, or a map derived from a list so for_each can iterate over it. They make the code more readable by naming complex expressions. The line I draw is: if a caller might need to change it, it's a variable, not a local."

Likely follow-up questions

  • When would you choose a variable instead of a local? When the value is configuration that differs per caller or environment.
  • Can a local reference a resource? Yes; it then becomes known only after that resource is created if the attribute is computed.
  • Locals or provider default_tags for tagging? default_tags for universal tags, locals for module-specific ones.
