You must bring 500 manually created cloud resources under Terraform management quickly. What is your approach?

Terraform · scenario · levels senior, lead

In one line

Start with an inventory grouped by ownership and lifecycle, generate code with terraform query, -generate-config-out or tools like aztfexport, refactor the generated code into modules, and only apply when the plan shows imports and no changes, working in batches with separate states.

Detailed explanation

Writing 500 resource blocks and import commands by hand is slow and error-prone. Modern Terraform gives you two big helpers. Import blocks (Terraform 1.5+) combined with terraform plan -generate-config-out=generated.tf write HCL for resources you name by ID, and import blocks support for_each since 1.7. Terraform 1.14 adds list resources in .tfquery.hcl files and the terraform query command, which asks the provider to discover existing resources by filters and can generate both configuration and import blocks, for providers that implement list resources. For Azure, aztfexport can export a resource group or a query result into code and state; similar community tools exist for other clouds.

Inventory comes first because it decides the state boundaries. Group resources by owner, application, environment and lifecycle: networking separate from application resources, production separate from test. Each group becomes its own state and becomes a batch.

Generated code is a starting point, not the result. It is verbose, hard-codes IDs and contains read-only or default-valued attributes. Refactor it: replace literal IDs with references, extract repeated patterns into modules and for_each, add variables and tags. The golden rule is that the plan must show only imports, with zero creates, updates or destroys. Any diff means the code does not yet describe reality and applying would change production.

How it works

  1. Inventory via cloud resource graph or CLI exports; tag or group by owner and environment.
  2. Pick a low-risk batch and a target state.
  3. Generate import blocks and configuration (query, generate-config-out or aztfexport).
  4. Refactor into modules, variables and references; remove read-only attributes.
  5. Plan until it shows only imports; apply; confirm a clean follow-up plan.
  6. Lock down manual changes for imported resources; move to the next batch.

Example

# imports.tf - bulk import with for_each (Terraform 1.7+)
locals {
  storage_accounts = {
    logs   = "/subscriptions/.../resourceGroups/rg-shared/providers/Microsoft.Storage/storageAccounts/stlogsprod"
    backup = "/subscriptions/.../resourceGroups/rg-shared/providers/Microsoft.Storage/storageAccounts/stbackupprod"
  }
}

import {
  for_each = local.storage_accounts
  to       = azurerm_storage_account.this[each.key]
  id       = each.value
}
terraform plan -generate-config-out=generated.tf   # draft HCL for resources without code

Common mistakes

  • Importing everything into one giant state.
  • Applying generated code as-is, with hard-coded values and noise.
  • Accepting "update in-place" diffs during import.
  • Not freezing manual changes, so resources drift while you import.
  • Forgetting child resources like role assignments, diagnostic settings and DNS records.

How to answer in the interview

"I begin with an inventory and group resources by owner, application, environment and lifecycle, which defines future state boundaries. Then I use tooling instead of hand-writing: terraform query with list resources in 1.14, import blocks with for_each and generate-config-out, or aztfexport on Azure. Generated code is verbose, so I refactor it into modules, variables and references. The rule is that the plan must show only imports and no changes before I apply. I work in batches, low-risk first, each in its own state, and lock down manual changes once a batch is managed."

Likely follow-up questions

  • How do you stop new unmanaged resources? Restrict portal write access, require pipelines, and add policies that deny untagged resources.
  • Does generate-config-out work for every resource? It depends on provider support and often needs cleanup.
  • How do you prove completeness? Compare inventory against state with a tag such as managed-by=terraform.
