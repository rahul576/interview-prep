Pipeline jobs wait a long time in the queue before an agent picks them up. How do you investigate?

Azure DevOps & Pipelines · scenario · levels mid, senior

In one line

Check pool capacity and parallel job limits, agent state (offline/busy) and demands vs capabilities, autoscaling settings (max agents, scale speed, standby agents) for VMSS or Managed DevOps Pools, stuck long-running jobs, and whether it is really queueing or an exclusive lock / approval wait.

Detailed explanation

Parallel jobs: an organisation can only run as many concurrent jobs as it has parallel jobs: separately for Microsoft-hosted and self-hosted agents. If 10 jobs are running and you have 10 parallel jobs, the 11th waits regardless of idle agents. Organization settings → Parallel jobs shows usage and the queue.

Agent availability: in the pool, check how many agents are online, offline, or busy. Offline agents may have crashed, lost network, or been deprovisioned. A job's demands (for example Agent.OS -equals Linux, docker, a specific tool) must match agent capabilities; if only two agents have Docker, Docker jobs queue behind each other even when other agents are idle.

Autoscaling: for VMSS agents, check max agent count, the number of standby agents and the time to provision a VM (image size, extension install). For Managed DevOps Pools, check maximum agents, standby agent schedules (none overnight means the first morning jobs wait for cold starts) and subnet IP capacity for VNet-injected pools. Quota limits for the VM family can also block scale-out.

Stuck jobs: hung test runs, waiting prompts or deadlocks can hold agents for hours. Set job timeoutInMinutes and cancelTimeoutInMinutes, and find long-running jobs in the pool's job list.

Not really queueing: a stage waiting for an environment check shows as waiting: exclusive lock (another run is deploying), pending approval, business hours check, or Azure Monitor gate. The run's view shows "Waiting for checks", not "Waiting for an agent".

Data: pool analytics (queue time, concurrency) and the run timeline tell you which cause applies.

How it works

  1. Open the waiting run: agent wait or check wait?
  2. Check parallel job usage at org level.
  3. Check pool agents: online/busy/offline, capabilities.
  4. Check scaling settings, standby, quota, subnet IPs.
  5. Find long-running jobs; add timeouts.
  6. Adjust capacity, demands or schedules; monitor queue time.

Example

jobs:
- job: test
  timeoutInMinutes: 30          # prevent hung jobs from holding agents
  pool:
    name: mdp-linux
    demands: [ docker ]
az pipelines pool list -o table
az pipelines agent list --pool-id 12 --include-capabilities -o table \
  --query "[].{name:name,status:status,enabled:enabled}"

Common mistakes

  • Adding agents without buying parallel jobs.
  • Overly specific demands that match one agent.
  • No standby agents during peak morning hours.
  • Default 60-minute (or unlimited on self-hosted) job timeouts for hung tests.

How to answer in the interview

"First I check the pool: how many agents are online, busy or offline, and whether we've hit our parallel job limit, because Microsoft-hosted and self-hosted parallelism are both capped by licensing. Then demands: if the job needs a capability few agents have, it waits for those. For scale set agents or Managed DevOps Pools I check the max agent count, scale-up speed and standby agents, since cold starts add minutes. Hung jobs without timeouts can hold agents for hours. And sometimes it's not queueing at all but an exclusive lock or pending approval. Pool analytics and the run timeline tell me which."

Likely follow-up questions

  • How many parallel jobs to buy? Look at peak concurrent demand and queue time in analytics; target acceptable p90 wait.
  • Standby cost vs speed? Schedule standby for working hours only.
  • Why do VNet-injected pools stall? Subnet IP exhaustion or VM quota.
