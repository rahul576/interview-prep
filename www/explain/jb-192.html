What is the difference between persist(), merge(), save(), and update()?

Spring Data & JPA · concept · levels mid, senior

In one line

persist() makes a new transient entity managed; merge() copies the state of a detached or new object onto a managed instance and returns that instance; save() and update() are legacy Hibernate Session methods (deprecated in Hibernate 6); Spring Data's repository.save() calls persist or merge depending on isNew.

Detailed explanation

An entity can be transient (new, unknown to Hibernate), managed (in the persistence context, changes tracked), detached (was managed, context closed) or removed.

persist(entity) is the JPA method for new objects. The same instance becomes managed, the id is generated (immediately for IDENTITY, from the pool for SEQUENCE) and the INSERT happens at flush. It returns void. Passing a detached entity throws an exception because JPA treats it as an attempt to insert an existing row.

merge(entity) is for detached objects, for example a DTO-like entity rebuilt from a request. Hibernate loads the managed instance with the same id (a SELECT if it is not already in the context), copies all state from your object onto it and returns the managed copy. The object you passed stays detached, so further changes to it are ignored. If no row exists, merge inserts a new one.

save() and update() come from the native Hibernate Session. save inserted a transient entity and returned the generated id; update reattached a detached instance so it became managed again; saveOrUpdate chose between them. They were deprecated in Hibernate 6 in favour of persist, merge and remove, so new code should not use them.

Spring Data save() in SimpleJpaRepository checks entityInformation.isNew(entity): by default an entity is new if its id is null (or a version field is null). New entities go to persist, others to merge. With manually assigned ids the entity never looks new, so save calls merge, which first issues a SELECT to find the existing row.

How it works

  1. Transient object + persist → becomes managed, INSERT at flush.
  2. Detached object + merge → SELECT managed copy, copy state, UPDATE at flush, return copy.
  3. Managed entity → just change fields; dirty checking writes the UPDATE, no save call needed.
  4. Spring Data save → isNew ? persist : merge, returning the managed entity.

Example

@Transactional
public Order rename(OrderDto dto) {
    Order detached = new Order(dto.id(), dto.name());   // not managed
    Order managed = entityManager.merge(detached);      // SELECT + copy
    managed.setNote("renamed");                          // tracked
    detached.setNote("ignored");                         // NOT tracked
    return managed;
}

// Assigned ids: avoid the extra SELECT by implementing Persistable
@Entity
public class Country implements Persistable<String> {
    @Id private String code;
    @Transient private boolean isNew = true;
    public boolean isNew() { return isNew; }
    @PostLoad @PostPersist void markNotNew() { isNew = false; }
    public String getId() { return code; }
}

Common mistakes

  • Ignoring merge's return value and continuing to modify the detached object.
  • Calling save() on an already managed entity inside a transaction, which is unnecessary.
  • Using assigned ids with Spring Data and paying an extra SELECT per insert.
  • Calling persist on a detached entity and getting a "detached entity passed to persist" error.

How to answer in the interview

"persist takes a new transient entity and makes that same instance managed; the insert happens at flush. merge is for detached state: Hibernate loads the managed instance, copies my object's state onto it and returns the managed copy, so I must use the returned value. save and update are the old Hibernate Session methods, now deprecated, which inserted and reattached respectively. Spring Data's save is a wrapper: if the entity is new, meaning a null id or version, it calls persist, otherwise merge. That's why assigned ids cause an extra SELECT, which I avoid by implementing Persistable or using a version field."

Likely follow-up questions

  • Why the extra SELECT with assigned ids? The entity is not considered new, so merge must check whether the row exists.
  • Do you need save() for managed entities? No, dirty checking flushes changes automatically at commit.
  • What does saveAndFlush add? It forces an immediate flush, useful to surface constraint violations early.
