What is a webhook, and how does it trigger a pipeline?

DevOps & CI/CD · concept · levels entry

In one line

A webhook is an HTTP callback: when an event occurs (push, pull request), the git provider sends an HTTP POST with a JSON payload to a URL registered by the CI server, which matches the repository and branch and starts the job; it is faster than polling and should be verified with a shared secret (HMAC signature).

Detailed explanation

Rather than the CI server asking the repository every minute "anything new?" (polling, which is slow and wasteful), the repository tells the CI server immediately when something happens.

Setup: in GitHub, GitLab or Bitbucket you register a webhook URL, for example https://jenkins.example.com/github-webhook/, select events (push, pull request, tag) and set a secret. Plugins such as the Jenkins GitHub or GitLab plugin expose that endpoint.

Event flow: a developer pushes a commit. The provider sends a POST with headers such as X-GitHub-Event: push and X-Hub-Signature-256, plus a JSON body containing repository, ref, commits and author. The CI server verifies the signature by computing an HMAC-SHA256 of the body with the shared secret, then finds jobs configured for that repo and branch (multibranch jobs scan for the new branch or PR) and queues a build.

Hosted CI such as GitHub Actions works on the same event model internally; you just declare on: push.

Reliability: providers show delivery logs with response codes and allow redelivery. The CI endpoint must be reachable from the provider (firewall rules, or a relay for private networks) and should respond quickly, processing asynchronously.

How it works

  1. Register the webhook URL, events and secret in the repository settings.
  2. An event occurs in the repository.
  3. Provider POSTs a signed JSON payload.
  4. CI verifies the signature and parses the payload.
  5. CI matches the job and queues a build for that commit.
  6. Build status is reported back to the commit or PR.

Example

import hmac, hashlib

def verify(secret: bytes, body: bytes, header: str) -> bool:
    expected = "sha256=" + hmac.new(secret, body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, header)

Header received: X-Hub-Signature-256: sha256=3f1a...; reject the request if verify returns false.

Common mistakes

  • No secret, so anyone can trigger builds.
  • CI endpoint not reachable from the internet or blocked by a firewall.
  • Slow synchronous processing causing provider timeouts.
  • Wrong events selected, so PRs never trigger.

How to answer in the interview

"A webhook is an HTTP callback: when an event happens in one system, it sends an HTTP POST with a JSON payload to a URL another system registered. For CI/CD, I configure a webhook in GitHub pointing to Jenkins. When someone pushes or opens a pull request, GitHub immediately posts the event with repository, branch and commit, and Jenkins matches it to the right job and starts the pipeline. That's faster and cheaper than polling. I secure it with a shared secret so Jenkins can verify the HMAC signature."

Likely follow-up questions

  • Pushes stopped triggering builds, what do you check? Delivery logs and response codes, URL, secret, firewall, CI plugin logs and job branch configuration.
  • Webhook vs polling? Push-based and immediate versus periodic and wasteful.
  • Can webhooks be replayed? Providers allow redelivery; idempotent handling helps.
