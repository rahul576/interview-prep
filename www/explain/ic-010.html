How do you protect important resources from being destroyed by Terraform?

Infrastructure as Code · concept · levels entry

In one line

Use lifecycle prevent_destroy, but back it with cloud-level deletion protection, backups/versioning, separate state for critical resources, careful plan review and policy checks that block destructive plans.

Detailed explanation

lifecycle { prevent_destroy = true } makes Terraform reject any plan that would destroy the resource, including replacements caused by an argument that forces a new resource. It is valuable for production databases, KMS keys and buckets with data. But it has a big weakness: it lives in the resource block. If someone deletes the block, or removes the whole module, the protection disappears with it, and the plan simply shows a destroy. It also does not protect against changes made outside Terraform.

So I add defence in depth at the cloud layer, which works no matter which tool calls the API: deletion_protection on RDS and Aurora, load balancers and DynamoDB tables; termination protection for EC2 instances and CloudFormation stacks; S3 versioning, MFA delete or Object Lock; KMS key deletion windows; Azure resource locks; and backups in a separate account. These make a mistaken destroy fail at the API.

Organisationally, critical and rarely changing resources, such as the core network or databases, often live in a separate state with stricter permissions, so an application team's routine apply cannot touch them. Every plan is reviewed for destroy and replace actions, and policy as code (OPA/Conftest on terraform show -json, or Sentinel in HCP Terraform) can fail the pipeline automatically when a plan deletes protected resource types without explicit approval.

How it works

  1. Mark critical resources with prevent_destroy.
  2. Enable provider-side deletion protection arguments.
  3. Keep backups and versioning independent of Terraform.
  4. Isolate critical resources in their own state and pipeline.
  5. Policy checks parse the plan JSON and block delete actions on protected types.

Example

resource "aws_db_instance" "prod" {
  identifier          = "orders-prod"
  deletion_protection = true
  skip_final_snapshot = false
  backup_retention_period = 14
  lifecycle {
    prevent_destroy = true
  }
}
package terraform
deny[msg] {
  rc := input.resource_changes[_]
  rc.type == "aws_db_instance"
  rc.change.actions[_] == "delete"
  msg := sprintf("Deleting database %s requires approval", [rc.address])
}

Common mistakes

  • Relying only on prevent_destroy, which vanishes with the block.
  • Skimming the plan summary and missing a -/+ replacement.
  • skip_final_snapshot = true on production databases.
  • Keeping backups in the same account the pipeline can delete from.

How to answer in the interview

"Inside Terraform I use lifecycle prevent_destroy, so any plan that would destroy, say, the production database fails. But that protection is lost if someone deletes the resource block, so I always add cloud-level protection too: deletion_protection on RDS and load balancers, termination protection, S3 versioning or Object Lock, and backups in a separate account. Critical, rarely changed resources live in their own state with tighter access. And every plan is reviewed for destroys and replacements, with a policy check in CI that blocks deletes of protected resource types unless explicitly approved."

Likely follow-up questions

  • Why is prevent_destroy alone not enough? It's removed with the block and doesn't stop out-of-band deletions.
  • How do you stop managing a resource without deleting it? A removed block with destroy = false, or terraform state rm.
  • How do you catch replacements? Look for "forces replacement" and -/+ in the plan; policy on delete actions.
