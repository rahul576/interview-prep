What is the difference between BeanFactory and ApplicationContext?

Spring Framework · concept · levels entry, mid

In one line

BeanFactory is the basic IoC container interface that creates and wires beans lazily on request; ApplicationContext extends it and adds eager singleton creation (fail fast), automatic registration of post-processors, events, i18n (MessageSource), resource loading and the Environment with profiles and properties.

Detailed explanation

BeanFactory is the root interface of Spring's container: getBean, containsBean, isSingleton and so on. The typical implementation, DefaultListableBeanFactory, holds bean definitions and creates a bean the first time someone asks for it. By itself it is minimal: you must register BeanPostProcessors and BeanFactoryPostProcessors manually, so @Autowired, @PostConstruct, ${...} placeholders, @Transactional proxies and other annotation features do not work unless you wire those processors in.

ApplicationContext is a sub-interface that wraps a bean factory and adds application-level services:

  • Eager pre-instantiation of singletons during refresh(). A missing dependency, a typo in a property or a failing constructor surfaces at startup, not on the first user request.
  • Automatic detection of BeanPostProcessors and BeanFactoryPostProcessors, which makes annotation-driven configuration, AOP, @Value and @ConfigurationProperties work.
  • ApplicationEventPublisher: publishing and listening to events, including lifecycle events like ContextRefreshedEvent.
  • MessageSource for internationalised messages.
  • ResourceLoader for classpath:, file: and URL resources.
  • Environment with profiles and property sources.
  • Hierarchies (parent/child contexts) and lifecycle management (SmartLifecycle, graceful shutdown).

Implementations include AnnotationConfigApplicationContext, and in Spring Boot AnnotationConfigServletWebServerApplicationContext (servlet web) or the reactive variant, created by SpringApplication.run.

In practice you always use an ApplicationContext. Plain BeanFactory is relevant for framework internals or extremely constrained environments. You can still make individual beans lazy with @Lazy, or globally with spring.main.lazy-initialization, when startup time matters more than fail-fast.

How it works

  1. SpringApplication.run creates the appropriate ApplicationContext.
  2. Bean definitions are loaded into the internal BeanFactory.
  3. BeanFactoryPostProcessors run (placeholders, configuration class parsing).
  4. BeanPostProcessors are registered.
  5. All non-lazy singletons are instantiated and initialised.
  6. The context publishes refresh events and starts lifecycle beans.

Example

// Plain BeanFactory: lazy, no automatic post-processors
DefaultListableBeanFactory factory = new DefaultListableBeanFactory();
new XmlBeanDefinitionReader(factory).loadBeanDefinitions("beans.xml");
OrderService s = factory.getBean(OrderService.class);   // created only now

// ApplicationContext: eager singletons, annotations, events, environment
try (var ctx = new AnnotationConfigApplicationContext(AppConfig.class)) {
    ctx.getEnvironment().getActiveProfiles();
    ctx.publishEvent(new CacheWarmupRequested());
    String msg = ctx.getMessage("greeting", null, Locale.GERMAN);
}

Common mistakes

  • Saying ApplicationContext is a completely separate container rather than an extension.
  • Claiming BeanFactory is "better for performance" in normal applications.
  • Calling ctx.getBean throughout business code instead of using injection.

How to answer in the interview

"BeanFactory is the basic Spring IoC container interface: it holds bean definitions, creates beans and injects dependencies, and it creates them lazily when first requested. ApplicationContext extends BeanFactory and is what applications actually use. It pre-instantiates singletons at startup, so configuration errors fail fast, and it automatically registers BeanPostProcessors and BeanFactoryPostProcessors, which @Autowired, AOP proxies and @Transactional rely on. It also adds application events, internationalisation through MessageSource, resource loading and the Environment with profiles and properties. Spring Boot creates an ApplicationContext for me."

Likely follow-up questions

  • When might you still mark a bean as @Lazy in an ApplicationContext? Rarely used, expensive beans, or to break startup ordering issues; it delays errors to first use.
  • Can you have several contexts? Yes, parent-child hierarchies, e.g. in older Spring MVC setups or tests.
  • How do you access the context in a bean? Inject ApplicationContext or implement ApplicationContextAware, sparingly.
