Which MCP servers are commonly used in DevOps work, and what do they enable?

MCP Servers · concept · levels mid, senior

In one line

The most common DevOps MCP servers are the GitHub MCP server, cloud servers such as the Azure MCP Server and AWS MCP servers, the HashiCorp Terraform MCP server, and Kubernetes and observability servers; they let agents read repos, pipelines, infrastructure and telemetry, ideally in read-only mode with scoped credentials.

Detailed explanation

DevOps work is mostly about stitching context together: a failing pipeline, the commit that triggered it, the Terraform module it deploys, and the metrics after the rollout. MCP servers give an agent a standard way to reach each of those systems, so one assistant can investigate across them instead of a human copying logs between browser tabs.

The GitHub MCP server (maintained by GitHub, available as a remote server or locally) exposes repositories, issues, pull requests, code search and GitHub Actions runs and logs, which makes "why did this workflow fail?" a one-prompt investigation. Cloud vendors publish their own servers: the Azure MCP Server covers many Azure services and can wrap Azure CLI operations, while AWS publishes a family of MCP servers for documentation, pricing and cost, infrastructure as code and individual services. The Terraform MCP server gives the model current provider and module documentation from the registry, which reduces hallucinated arguments, and can read HCP Terraform workspace data.

For operations, Kubernetes MCP servers let an agent list pods, describe resources and read events and logs, and observability servers from vendors such as Grafana and Datadog let it query metrics, logs and traces. The value is speed in incident investigation and routine tasks, but the risk is real: these servers often hold powerful credentials. That is why read-only modes, toolset filtering and per-environment scoped credentials matter, with production changes still flowing through normal pipelines and approvals.

How it works

  1. The host (IDE, CLI agent or chat app) is configured with each server, local over stdio or remote over HTTP.
  2. Each server authenticates to its backend: OAuth for remote servers, or a scoped token or cloud login for local ones.
  3. The host lists the tools and passes their definitions to the model.
  4. During a task the model calls tools across servers, for example GitHub for the failing run, then Kubernetes for pod events, then Grafana for error rates.
  5. Write actions (opening a PR, restarting a deployment) require approval, or are disabled outright in production.

Example

{
  "mcpServers": {
    "github": {
      "type": "http",
      "url": "https://api.githubcopilot.com/mcp/",
      "headers": { "X-MCP-Readonly": "true" }
    },
    "terraform": {
      "command": "docker",
      "args": ["run", "-i", "--rm", "hashicorp/terraform-mcp-server"]
    }
  }
}

A typical prompt: "The deploy workflow on main failed twice today. Find the failing step, the commit, and whether the pods in staging are crash-looping."

Common mistakes

  • Connecting servers to production with an admin token "just to try it".
  • Enabling every toolset, so the model sees hundreds of tools and picks badly.
  • Letting the agent apply infrastructure changes directly instead of opening a pull request.
  • Forgetting that logs and issue comments returned by these servers are untrusted content that can carry prompt injection.

How to answer in the interview

"The ones I see most are the GitHub MCP server for repos, PRs and Actions runs, the cloud providers' servers like the Azure MCP Server and the AWS MCP servers, HashiCorp's Terraform MCP server for up-to-date provider and module docs and workspace data, and Kubernetes plus observability servers from vendors like Grafana or Datadog. Together they make incident investigation much faster, because one agent can go from a failing workflow to the commit, the cluster events and the metrics. The way I run them is read-only wherever the server supports it, with credentials scoped per environment, and any change to production still goes through a pull request and the normal pipeline with approvals."

Likely follow-up questions

  • Which would you allow against production? Read-only Kubernetes and observability access for investigation; no write tools.
  • Why is the Terraform server useful even without cloud access? It grounds generated HCL in current provider documentation.
  • How do you limit what the GitHub server can do? Read-only mode, selected toolsets and a fine-grained token limited to specific repos.
