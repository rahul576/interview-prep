How would you run AI training and inference workloads on Kubernetes?

Kubernetes · design · levels mid, senior, lead

In one line

Run training as queued batch work on separate, autoscaled GPU pools (with Kueue, gang scheduling, spot plus checkpointing) and inference as long-running services (KServe, vLLM, Triton) with cached model weights and autoscaling on concurrency or queue depth, not CPU.

Detailed explanation

Training and inference have opposite shapes. Training is batch: large, long jobs that need many GPUs at the same time and can be paused and resumed. Inference is latency-sensitive serving that must scale with traffic. Putting them on separate node pools prevents a big training job from starving production inference and lets each pool use the right instance types and purchasing model.

For training, GPUs are scarce and shared between teams, so a queue is needed. Kueue adds ClusterQueues and LocalQueues with quotas, borrowing and fair sharing, and admits a job only when its whole resource set is available. That gives gang scheduling behaviour: a 16-worker PyTorch job starts all-or-nothing, instead of 10 workers holding GPUs idle while waiting for 6 more. Jobs run as Kubeflow Trainer jobs, JobSet or Ray clusters. Spot capacity cuts cost a lot, provided the job checkpoints to object storage and can resume.

For inference, KServe or plain Deployments run engines such as vLLM, SGLang or Triton. The biggest operational issue is cold start: images and weights can be tens of gigabytes, so weights are cached on node-local NVMe, a shared read-only volume, or pre-pulled images, and models are kept warm. GPU-bound pods show low CPU, so autoscaling uses in-flight requests, queue depth, KV-cache utilisation or tokens per second via KEDA or custom metrics. Node pools scale with Karpenter or the cluster autoscaler, and DCGM exporter metrics show GPU utilisation for rightsizing.

How it works

  1. Create tainted GPU node pools: training (spot allowed) and inference (on-demand base).
  2. Install the GPU Operator and Kueue; define queues and team quotas.
  3. Submit training as JobSet/PyTorch jobs to a LocalQueue; Kueue admits whole gangs.
  4. Checkpoint regularly so preempted spot jobs resume.
  5. Serve models with KServe or vLLM Deployments; cache weights locally.
  6. Autoscale on concurrency or queue depth; scale nodes with Karpenter.
  7. Monitor GPU utilisation, latency and cost per team.

Example

apiVersion: batch/v1
kind: Job
metadata:
  name: finetune-llm
  labels:
    kueue.x-k8s.io/queue-name: ml-team-a
spec:
  parallelism: 4
  completions: 4
  suspend: true          # Kueue unsuspends when quota for all 4 is available
  template:
    spec:
      tolerations: [{ key: nvidia.com/gpu, operator: Exists, effect: NoSchedule }]
      containers:
        - name: train
          image: registry.example.com/train:2.1
          resources: { limits: { nvidia.com/gpu: 8 } }
      restartPolicy: Never

Common mistakes

  • Autoscaling inference on CPU utilisation.
  • Pulling a 70 GB model from object storage on every pod start.
  • Running training on spot without checkpoints.
  • No quotas, so one team monopolises all GPUs.

How to answer in the interview

"I'd separate training and inference onto different tainted GPU pools. Training is batch, so I use Kueue for queues, quotas and fair sharing, and its all-or-nothing admission gives gang scheduling, so a distributed job never holds half the GPUs idle. Training can use spot with checkpointing. Inference runs on KServe or vLLM deployments, with weights cached on local NVMe or a shared volume, because pulling tens of gigabytes per start is slow. I autoscale inference on concurrency or queue depth, not CPU, scale nodes with Karpenter, and watch DCGM metrics to rightsize."

Likely follow-up questions

  • How do you handle a 70 GB model cold start? Node-local cache or pre-pulled image, streaming loaders, and keeping minimum warm replicas.
  • Why not CPU-based HPA? GPU-bound inference shows low CPU even when saturated.
  • How do you share small GPUs for inference? MIG slices or DRA claims for small models.
