How do you design a multi-tenant SaaS backend?

Architecture · design · levels lead

In one line

A multi-tenant SaaS backend chooses an isolation model (shared schema, schema per tenant, database per tenant), propagates tenant context from the token on every request and message, enforces tenant filtering centrally (Hibernate filters, PostgreSQL RLS), controls noisy neighbours with quotas, and tracks per-tenant observability and cost.

Detailed explanation

Isolation models trade cost against isolation:

  • Shared schema with a tenant_id column: cheapest, easiest migrations, scales to thousands of small tenants; risk is a missed filter leaking data.
  • Schema per tenant: stronger logical separation, per-tenant backup/restore, but migrations run N times and connection pools grow.
  • Database per tenant: strongest isolation, per-tenant encryption keys, residency and performance; costly, often a premium or enterprise tier.

Many products use a hybrid: pooled for small tenants, siloed for large or regulated ones, with a tenant catalogue recording each tenant's placement.

Tenant context must come from a trusted source: the authenticated JWT claim (or subdomain verified against the token), never a free-form header. It is set in a request-scoped context, propagated to async jobs and Kafka message headers, and included in logs and traces.

Enforcement must be central, not left to every developer remembering a WHERE. Options: Hibernate 6 @TenantId or filters, Spring's AbstractRoutingDataSource for schema/database routing, and PostgreSQL row-level security policies using a session variable, which protects even raw SQL. Add automated tests that attempt cross-tenant access. Caches, search indexes and object storage keys must include the tenant ID too.

Noisy neighbours: per-tenant rate limits, quotas, job concurrency limits, and moving heavy tenants to dedicated resources. Per-tenant metrics and cost attribution support pricing and capacity decisions.

How it works

  1. Request arrives with a JWT containing tenant_id.
  2. A filter sets TenantContext and MDC for logging.
  3. Data layer routes to the right DB/schema or sets app.tenant_id for RLS.
  4. Queries are automatically filtered; caches use tenant:{id}:... keys.
  5. Messages carry tenant ID headers; consumers restore context.
  6. Rate limiter and quotas apply per tenant; metrics tagged by tenant.

Example

ALTER TABLE invoices ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON invoices
  USING (tenant_id = current_setting('app.tenant_id')::uuid);
@Component
class TenantConnectionPreparer {
    @Transactional
    void apply(JdbcTemplate jdbc) {
        jdbc.queryForObject("select set_config('app.tenant_id', ?, true)", String.class,
                            TenantContext.current().toString());   // true = local to this transaction
    }
}

Common mistakes

  • Taking tenant ID from a client-controlled header.
  • Relying on developers to add WHERE tenant_id = ? manually.
  • Forgetting tenant scoping in caches, search and file storage.
  • Losing tenant context in async threads and consumers.
  • One giant tenant degrading everyone with no quotas.

How to answer in the interview

"First I'd choose the isolation model: shared schema with a tenant ID for most tenants because it's cheapest, and schema or database per tenant for large or regulated customers as a premium tier, tracked in a tenant catalogue. The tenant comes from the authenticated token and is propagated to every request, async job and message. Filtering is enforced centrally with Hibernate tenant support or PostgreSQL row-level security, not by each developer. I'd add per-tenant rate limits and quotas for noisy neighbours, and tag metrics and cost by tenant."

Likely follow-up questions

  • Migrating a big tenant to its own DB? Copy data, sync changes via CDC, switch the catalogue entry during a short write freeze, verify.
  • Schema migrations with 500 schemas? Automated, idempotent Flyway runs per schema with progress tracking and backward-compatible changes.
  • Tenant-specific customisation? Configuration and feature flags, not forked code.
