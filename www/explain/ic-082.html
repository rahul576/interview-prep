How do you plan disaster recovery for the infrastructure-as-code platform itself?

Infrastructure as Code · design · levels lead

In one line

Make sure you can change infrastructure during a disaster: versioned, cross-region replicated state (and locks), reachable repositories, registries and provider binaries, a break-glass procedure to run IaC without normal CI, tested rebuilds from code in another region, and an assessment of SaaS dependencies such as GitHub or HCP Terraform.

Detailed explanation

The IaC platform is itself critical infrastructure. During a regional outage you need to deploy into another region, scale up, or change DNS. If the state bucket, CI runners, Git hosting or module registry are in the failed region or provider, you cannot do that at the very moment you need to.

State. State buckets are versioned and replicated to another region (S3 Cross-Region Replication, GRS storage on Azure), with object lock or deletion protection. Lock mechanisms (DynamoDB tables, lock files) must also work in the recovery region.

Code and dependencies. Git repositories are mirrored or backed up (to a second provider or object storage). The private module registry and provider binaries are mirrored (provider_installation with a network or filesystem mirror), so init works even if public registries or the internal registry are down.

Execution. If normal pipelines are unavailable, a break-glass procedure describes how to run Terraform from a hardened workstation or an alternate runner, with credentials stored securely (sealed, in a separate vault or account) and use alerting the security team.

Tested rebuild. The real proof is a DR exercise: rebuild an environment from code in another region. This reveals hard-coded regions, AMI IDs, KMS keys, certificates, quotas and secrets that exist only in the primary region, and circular dependencies such as DNS or identity hosted in the failed region.

Risk assessment. Dependencies on SaaS (GitHub, GitLab.com, HCP Terraform, the CI provider) are listed with their SLAs and fallback options.

How it works

  1. Map the IaC platform's components and where each runs.
  2. Replicate state and locks; mirror repos, modules and providers.
  3. Write and secure the break-glass runbook and credentials.
  4. Parameterise code for region; remove hard-coded IDs.
  5. Run regular DR drills rebuilding an environment from code; fix findings.

Example

# CLI config on the break-glass runner: install providers from a local mirror
provider_installation {
  filesystem_mirror {
    path    = "/opt/terraform/providers"
    include = ["registry.terraform.io/*/*"]
  }
  direct {
    exclude = ["registry.terraform.io/*/*"]
  }
}

Common mistakes

  • State replicated, but the lock table or KMS key only in one region.
  • No way to run Terraform when the CI SaaS is down.
  • Never testing a rebuild, so hard-coded region values surface during the real disaster.
  • Break-glass credentials nobody can find or that have expired.

How to answer in the interview

"If the region hosting state or our CI fails, we might be unable to change infrastructure exactly when we need to recover. So state buckets are versioned and replicated cross-region, with the locking working there too. Repositories, the module registry and provider binaries are mirrored so init works anywhere. There's a break-glass procedure, with securely stored credentials, to run Terraform from a hardened workstation or alternate runner. Most importantly, we regularly rebuild an environment from code in another region, and SaaS dependencies like GitHub or HCP Terraform are part of the risk assessment."

Likely follow-up questions

  • What breaks first when rebuilding from code? Hard-coded regions, AMI IDs, KMS keys, quotas and secrets that exist only in the primary region.
  • Where do break-glass credentials live? A separate, audited vault or sealed storage, tested periodically.
  • Do replicated state files stay consistent? Mostly; replication is asynchronous, so verify the latest version before applying.
