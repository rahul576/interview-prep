Design a distributed message queue like Kafka.

Classic Design Problems · design · levels senior, lead

In one line

A Kafka-like queue stores each topic as partitioned, replicated, append-only logs; ordering is per partition, consumers in a group split partitions and track offsets, and throughput comes from sequential I/O, batching, page cache and zero-copy.

Detailed explanation

The log abstraction is the key insight. Appending to a file sequentially is extremely fast even on spinning disks, and readers simply remember a position (offset). Messages aren't deleted when consumed; they're kept for a retention period, so many independent consumer groups can read the same data and replay it.

Partitions give parallelism: a topic with 50 partitions spreads across brokers, and up to 50 consumers in a group can process in parallel. The producer chooses the partition by key, so all events for order-42 land in one partition, preserving their order.

Replication: each partition has a leader and followers; the in-sync replica (ISR) set are followers caught up with the leader. With acks=all and min.insync.replicas=2, an acknowledged message survives a broker loss. A controller (KRaft/Raft in modern Kafka) handles leader election.

How it works

  1. Producer batches + compresses messages, sends to partition leader.
  2. Leader appends to its log segment; followers fetch and append.
  3. Ack after ISR replicated (acks=all).
  4. Consumers poll from offsets; commit offsets after processing.
  5. Old segments deleted by time/size, or compacted to keep the last value per key.

Example

acks=all
enable.idempotence=true
min.insync.replicas=2
replication.factor=3

Common mistakes

  • Too few partitions (limits consumer parallelism; increasing later reshuffles keys).
  • Committing offsets before processing (data loss) or never (reprocessing storms).
  • acks=1 for critical data.
  • Expecting global ordering across partitions.

How to answer in the interview

"Each topic is split into partitions, each an append-only log replicated across brokers with a leader and in-sync followers. Producers key messages so per-entity order is preserved. Consumer groups divide partitions and commit offsets, which enables replay. It's fast because of sequential disk writes, batching, compression, the OS page cache and zero-copy transfers. Retention is time- or size-based, with log compaction for keyed state."

Likely follow-up questions

  • Exactly-once? Idempotent producer + transactions + read-process-write with offsets in the transaction.
  • How many partitions? Based on target throughput per consumer and future growth.
  • What is log compaction? Keep only the latest record per key.
