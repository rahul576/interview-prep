How do you run tasks concurrently in Java? Explain Runnable, Callable, ExecutorService and Future.

Concurrency · concept · levels entry, mid

In one line

Runnable is a task with no result and no checked exceptions, Callable returns a value and can throw; you submit them to an ExecutorService (a managed thread pool), get a Future to wait, time out or cancel, use CompletableFuture for composition, and always shut the executor down.

Detailed explanation

Creating new Thread(...) per task is expensive for platform threads and gives no control over concurrency, queueing or lifecycle. The Executor framework separates what to run from how it runs.

Runnable has void run(). It can't return a value or throw checked exceptions. Callable<V> has V call() throws Exception, so it suits tasks that compute results or call APIs that throw.

ExecutorService manages a pool of worker threads and a task queue. execute(Runnable) fires and forgets; submit(Runnable | Callable) returns a Future; invokeAll and invokeAny handle groups. The Executors factory methods are convenient, but newFixedThreadPool and newSingleThreadExecutor use an unbounded queue and newCachedThreadPool can create unbounded threads. For server code I build a ThreadPoolExecutor explicitly with a bounded queue, a named thread factory and a rejection policy. Since Java 21, Executors.newVirtualThreadPerTaskExecutor() starts a virtual thread per task, ideal for blocking I/O.

A Future<V> represents a pending result. get() blocks until done and wraps task failures in ExecutionException; get(timeout, unit) throws TimeoutException; cancel(true) interrupts the running task; isDone() polls. Java 19 added resultNow() and state(). Future can't be chained, so for non-blocking pipelines use CompletableFuture (supplyAsync, thenApply, thenCombine, exceptionally).

Shutdown matters: pool threads are non-daemon by default and keep the JVM alive. Call shutdown(), then awaitTermination, then shutdownNow() if needed. Since Java 19, ExecutorService is AutoCloseable, so try-with-resources calls close(), which shuts down and waits.

How it works

  1. Create the executor (pool size, queue, policy).
  2. submit tasks; they are queued and run by worker threads.
  3. Collect results through Futures with timeouts.
  4. Handle ExecutionException and InterruptedException.
  5. Shut down and await termination.

Example

try (ExecutorService pool = Executors.newVirtualThreadPerTaskExecutor()) { // Java 21
    Future<User> user = pool.submit(() -> userClient.find(id));          // Callable
    Future<List<Order>> orders = pool.submit(() -> orderClient.byUser(id));
    return new Dashboard(user.get(2, SECONDS), orders.get(2, SECONDS));
} // close(): shutdown + wait

ThreadPoolExecutor cpuPool = new ThreadPoolExecutor(
        8, 8, 0, SECONDS, new ArrayBlockingQueue<>(500),
        Thread.ofPlatform().name("cpu-", 0).factory(),
        new ThreadPoolExecutor.CallerRunsPolicy());

Common mistakes

  • Calling get() without a timeout on a request thread.
  • Ignoring exceptions from execute'd tasks (they go to the uncaught handler) or never calling get on submitted ones (silently lost).
  • Never shutting the executor down.
  • Using unbounded Executors factories in production services.

How to answer in the interview

"Runnable is a task with no result that can't throw checked exceptions, while Callable returns a value and can throw. Instead of raw threads I submit tasks to an ExecutorService backed by a pool, usually a ThreadPoolExecutor with a bounded queue so size and rejection policy are explicit, or a virtual-thread-per-task executor for blocking I/O on Java 21. submit returns a Future, whose get blocks until the result is ready and supports timeouts and cancel. For non-blocking composition I use CompletableFuture. And I always shut the executor down, or use try-with-resources since Java 19."

Likely follow-up questions

  • What goes wrong with newFixedThreadPool under load? The unbounded LinkedBlockingQueue grows until memory runs out and latency explodes.
  • execute vs submit for exceptions? execute surfaces them to the uncaught exception handler; submit stores them in the Future.
  • What does cancel(true) do? Interrupts the thread running the task; it only stops if the task honours interruption.
