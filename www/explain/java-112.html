What are immutable collections in modern Java, and how do List.of and Collections.unmodifiableList differ?

Collections · concept · levels entry, mid, senior

In one line

List.of / Set.of / Map.of (Java 9+) create truly immutable collections that reject nulls, whereas Collections.unmodifiableList is only a read-only view over a list that can still change underneath.

Detailed explanation

Collections.unmodifiableList(list) returns a wrapper whose mutator methods throw UnsupportedOperationException. But the wrapper delegates reads to the original list. If any code still holds a reference to that original and modifies it, the changes are visible through the "unmodifiable" view. So it protects against modification through the view, not against modification of the data.

The Java 9 factory methods List.of, Set.of and Map.of (and Map.ofEntries) build compact, unmodifiable collections that own their data. Nothing can change them. They also reject null elements, keys and values with a NullPointerException, and Set.of / Map.of throw IllegalArgumentException on duplicate elements or keys at creation time. Their iteration order for sets and maps is deliberately unspecified and randomised per JVM run.

Java 10 added List.copyOf, Set.copyOf and Map.copyOf, which create an immutable copy (and return the same instance if the input is already such a collection). Collectors.toUnmodifiableList() and, since Java 16, Stream.toList() produce unmodifiable lists; note Stream.toList() allows null elements while List.of does not.

Remember that immutability is shallow: an immutable list of mutable objects still lets callers change the objects.

How it works

  1. List.of(a, b) creates a specialised immutable implementation storing the elements.
  2. All mutators (add, set, remove, sort) throw UnsupportedOperationException.
  3. unmodifiableList stores a reference to the backing list and forwards reads.
  4. copyOf copies the elements into a new immutable collection.

Example

List<String> backing = new ArrayList<>(List.of("a", "b"));
List<String> view = Collections.unmodifiableList(backing);
backing.add("c");
System.out.println(view);           // [a, b, c] -> view changed!

List<String> snapshot = List.copyOf(backing);
backing.add("d");
System.out.println(snapshot);       // [a, b, c]

Set.of("x", "x");                   // IllegalArgumentException: duplicate
List.of("a", null);                 // NullPointerException

Common mistakes

  • Returning unmodifiableList(internalList) and assuming callers see a fixed snapshot.
  • Calling List.of with possibly null values from a database.
  • Expecting Set.of or Map.of to keep insertion order.
  • Forgetting immutability is shallow.

How to answer in the interview

"List.of, Set.of and Map.of from Java 9 create genuinely immutable collections: any change throws UnsupportedOperationException, and they reject nulls and, for sets and maps, duplicates. Collections.unmodifiableList is only a read-only wrapper, so if someone changes the backing list the view changes too. When I need an independent immutable snapshot I use List.copyOf, and Stream.toList also returns an unmodifiable list. I return immutable collections from APIs and use them for constants to avoid accidental mutation."

Likely follow-up questions

  • Why might Set.of throw at creation? It rejects duplicate elements and nulls.
  • Is Arrays.asList immutable? No, it is fixed-size but set works and writes through.
  • Defensive copies in constructors? Use List.copyOf(param) to store a safe snapshot.
