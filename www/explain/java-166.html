What are best practices for exception handling in a large Java codebase?

Exceptions · concept · levels mid, senior

In one line

In a large codebase, never swallow exceptions, catch specific types, preserve the cause when wrapping, handle and log once at the right boundary, use try-with-resources, and keep exceptions for exceptional situations, not control flow.

Detailed explanation

Exception handling becomes a cross-team concern in big systems: inconsistent handling produces missing stack traces, duplicate log noise and incidents that nobody can diagnose. A few principles cover most of it.

Do not swallow. An empty catch hides bugs. If you genuinely can ignore an exception, write a comment explaining why. Catch specifically. Catching Exception or Throwable also catches programming errors and InterruptedException, which you then mishandle. Catch what you can actually handle. Preserve the cause. When translating a low-level exception (SQLException) into a domain one, pass it as the cause: new OrderPersistenceException("...", e). Losing the cause loses the root of the stack trace.

Handle at the right layer and log once. Most code should let exceptions propagate. Handle them at boundaries: a Spring @RestControllerAdvice, a message listener's error handler, a scheduled job wrapper. Logging and rethrowing at every layer produces the same stack trace five times. Translate at boundaries: map domain exceptions to HTTP status codes and a stable error body (for example RFC 9457 Problem Details, which Spring supports via ProblemDetail).

Also: restore the interrupt flag when catching InterruptedException, use try-with-resources for anything AutoCloseable, include useful context (ids, not secrets) in messages, and do not use exceptions for normal flow such as "user not found during a search", because they are slow and obscure intent; return Optional instead.

How it works

  1. Low-level code throws or lets exceptions propagate without logging.
  2. Service code wraps infrastructure exceptions into meaningful domain or technical exceptions with the cause.
  3. A central boundary handler catches, logs once with context and correlation id, and maps to a response.
  4. Metrics count exceptions by type so alerts fire on unexpected ones.
  5. Resources are closed by try-with-resources, keeping suppressed exceptions.

Example

public Order load(long id) {
    try {
        return repository.findById(id).orElseThrow(() -> new OrderNotFoundException(id));
    } catch (DataAccessException e) {
        throw new OrderStoreUnavailableException("Failed to load order " + id, e); // keep cause
    }
}

@RestControllerAdvice
class ApiErrors {
    @ExceptionHandler(OrderNotFoundException.class)
    ProblemDetail notFound(OrderNotFoundException e) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, e.getMessage());
    }
}

Common mistakes

  • catch (Exception e) { e.printStackTrace(); } in production code.
  • Log-and-rethrow at every layer, producing duplicate logs.
  • throw new MyException(e.getMessage()), which discards the original stack trace.
  • Catching InterruptedException and not restoring the interrupt status.
  • Exposing stack traces or internal messages in API responses.

How to answer in the interview

"My rules are: never swallow exceptions, catch only specific types I can handle, and when I wrap a low-level exception into a domain one I always pass the cause. Most code just propagates; handling and logging happen once at boundaries like a controller advice or a listener error handler, which maps exceptions to proper status codes and a consistent error body. I use try-with-resources for cleanup, restore the interrupt flag, and I don't use exceptions for normal control flow. Finally, I add metrics per exception type so we notice new failures."

Likely follow-up questions

  • When would you create a custom exception class? When callers need to react to a specific condition or you need to map it to a specific response.
  • Checked or unchecked for business errors? Usually unchecked in Spring services, documented in Javadoc.
  • How do you correlate logs? Put a trace or correlation id in the MDC and include it in the error response.
