How do you speed up Ansible runs on many hosts?

Configuration Management · concept · levels mid

In one line

Raise forks (default 5), enable SSH pipelining and ControlPersist, disable, subset or cache facts, use the free strategy and async for long tasks, pass lists to modules instead of loops, and profile with the profile_tasks callback.

Detailed explanation

Parallelism. Ansible processes hosts in batches of forks, default 5. On a fleet of 500 servers, raising forks to 50 or 100 (-f 50 or forks = 50 in ansible.cfg) is usually the biggest single win, limited by control-node CPU and memory. serial still controls rolling batches where you need them.

Connection overhead. Each task normally involves several SSH operations: create a temp dir, copy the module, execute, clean up. Pipelining (pipelining = True) sends the module over the existing SSH session's stdin, cutting operations per task significantly; it requires that requiretty is not enforced in sudoers (the default on modern distros). ControlPersist (on by default in Ansible's SSH options, 60 s) keeps the master connection open for reuse; increasing it helps longer playbooks.

Facts. Gathering facts on every host each run is expensive. Use gather_facts: false when not needed, gather_subset for just what you use, and fact caching (jsonfile, Redis) with gathering = smart.

Execution strategy. The default linear strategy waits for all hosts in the batch to finish a task before the next. The free strategy lets each host run through the play as fast as it can. For long operations, async with poll: 0 starts tasks in the background, and async_status collects results later.

Task design. Modules like package, apt and dnf accept a list: one transaction instead of one per package. Avoid unnecessary shell tasks; use copy/template efficiently; synchronize (rsync) for large file trees. Use run_once or delegate_to for tasks that only need one execution.

Measure. Enable callbacks_enabled = ansible.posix.profile_tasks, ansible.posix.timer to see the slowest tasks and total time, then optimise the real bottleneck.

How it works

  1. Increase forks to parallelise hosts.
  2. Reduce SSH round-trips with pipelining and persistent connections.
  3. Avoid repeated fact gathering.
  4. Let hosts progress independently where safe.
  5. Profile and fix the slowest tasks.

Example

# ansible.cfg
[defaults]
forks = 50
gathering = smart
fact_caching = jsonfile
fact_caching_connection = ~/.ansible/facts
fact_caching_timeout = 86400
callbacks_enabled = ansible.posix.profile_tasks, ansible.posix.timer

[ssh_connection]
pipelining = True
ssh_args = -o ControlMaster=auto -o ControlPersist=300s
- hosts: web
  strategy: free
  gather_facts: true
  gather_subset: ["!all", "min", "network"]
  tasks:
    - name: Install packages in one transaction
      ansible.builtin.package:
        name: [nginx, jq, curl, htop]
        state: present

    - name: Long backup in background
      ansible.builtin.command: /usr/local/bin/backup.sh
      async: 3600
      poll: 0

Common mistakes

  • Leaving forks at 5 for hundreds of hosts.
  • Using the free strategy for ordered rolling deployments.
  • Gathering full facts for plays that never use them.
  • Optimising blindly without profiling.

How to answer in the interview

"By default Ansible handles five hosts at a time, so raising forks, say to 50, is often the biggest win. SSH settings come next: pipelining cuts the SSH operations per task and ControlPersist reuses connections. Fact gathering is slow, so I disable it when not needed, gather a subset or cache facts. The free strategy lets fast hosts carry on without waiting for slow ones, and async runs long tasks in the background. Inside tasks I pass lists to modules like package instead of looping. And the profile_tasks callback tells me which tasks actually take the time."

Likely follow-up questions

  • When is the free strategy a bad idea? When order across hosts matters: rolling deployments, cluster operations, tasks depending on other hosts.
  • Why can pipelining fail? sudoers with requiretty.
  • What limits forks? Control-node CPU, memory and file descriptors, and target-side SSH limits.
