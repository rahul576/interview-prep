Design a CI/CD pipeline for a containerised microservice, from commit to production.

DevOps & CI/CD · design · levels mid, senior

In one line

A good pipeline for a containerised microservice runs build, unit tests, static analysis and security scans on every PR, then builds, scans, tags (commit SHA) and pushes an immutable image, promotes the same image through dev, staging and production with smoke tests, approvals or canary analysis, ideally via GitOps, with a clear rollback.

Detailed explanation

Pull request stage (fast feedback, under ~10 minutes): checkout, compile, unit tests, linting, static analysis (SonarQube or similar), SAST (for example CodeQL or Semgrep), dependency scanning (SCA), secret scanning and, if infrastructure is in the repo, IaC scanning. Branch protection requires all checks and a code review before merge.

Main branch build: build the Docker image with a multi-stage Dockerfile, scan it (Trivy or Grype) and fail on critical vulnerabilities, generate an SBOM, sign the image (Cosign/Sigstore) and tag it with the commit SHA (plus a semantic version if needed). Push to a registry such as ECR, ACR or GHCR. Never use latest.

Promotion: the same immutable image moves through environments; it is never rebuilt. In dev it deploys automatically. In staging, integration, contract, smoke and performance tests run against real dependencies. Production uses a manual approval (continuous delivery) or automated canary analysis (continuous deployment) with metrics such as error rate and latency.

Deployment mechanism: I prefer GitOps. The pipeline updates the image tag in a Helm values or Kustomize file in a config repository (often by pull request for production), and Argo CD or Flux syncs the cluster. Benefits: Git is the audit trail, the cluster pulls changes so CI needs no cluster credentials, and drift is corrected automatically. Argo Rollouts can perform canary steps with analysis.

Rollback: revert the config commit or use Argo CD rollback to the previous revision; database migrations must be backward compatible (expand and contract) so rollback is safe. Notifications go to the team chat; deployments are tracked with DORA metrics.

How it works

  1. PR: build, test, lint, SAST, SCA, secret scan; review.
  2. Merge: build image, scan, SBOM, sign, push :sha.
  3. Update dev config repo; Argo CD syncs.
  4. Promote to staging; run integration and smoke tests.
  5. Approval or canary to production via config repo PR.
  6. Monitor; rollback by reverting the commit.

Example

build-image:
  needs: test
  runs-on: ubuntu-latest
  permissions: { id-token: write, contents: read }
  steps:
    - uses: actions/checkout@v4
    - run: docker build -t $REGISTRY/orders:${{ github.sha }} .
    - uses: aquasecurity/trivy-action@0.28.0   # pin to a SHA in real pipelines
      with: { image-ref: "${{ env.REGISTRY }}/orders:${{ github.sha }}", severity: CRITICAL, exit-code: "1" }
    - run: docker push $REGISTRY/orders:${{ github.sha }}
    - run: |
        git clone https://github.com/acme/deploy-config && cd deploy-config
        yq -i '.image.tag = "${{ github.sha }}"' apps/orders/values-dev.yaml
        git commit -am "orders: ${{ github.sha }} to dev" && git push

Common mistakes

  • Rebuilding the image per environment.
  • Using latest tags.
  • Security scans that only warn and never fail.
  • Rollback plans that ignore database migrations.

How to answer in the interview

"On every PR I run build, unit tests, linting, static analysis, SAST, dependency and secret scanning. After merge I build the image, scan it with Trivy, generate an SBOM, sign it, tag it with the commit SHA and push it to the registry. The same immutable image is promoted through dev, staging with integration and smoke tests, and production with an approval or automated canary analysis. I prefer GitOps: the pipeline updates the image tag in a config repo and Argo CD syncs it. Rollback is reverting that commit, with backward-compatible database migrations."

Likely follow-up questions

  • Keep pipeline under ten minutes? Caching, parallel jobs, test splitting, incremental builds and moving slow tests later.
  • Why GitOps? Audit trail in Git, no cluster credentials in CI, drift correction.
  • How to handle secrets? OIDC to the cloud and external secret stores, never in the image.
