What are ephemeral resources and write-only arguments in Terraform, and what problem do they solve?

Terraform · concept · levels senior, lead

In one line

Ephemeral resources (Terraform 1.10+) produce values that exist only during a run and are never written to plan or state; write-only arguments (1.11+, usually named *_wo) are sent to the provider but not stored; together they keep secrets out of state.

Detailed explanation

Terraform state is a JSON document that records every attribute of every managed object. Historically any secret Terraform touched ended up there in plain text: a random_password result, a database master password, a value read from Secrets Manager or Key Vault through a data source, a generated private key. The sensitive flag only hides values in CLI output. As a result, teams had to protect state like a secret store, and anyone with state read access effectively had production credentials.

Ephemeral resources are a new block type, ephemeral "type" "name" {}. Terraform opens them during a run, uses their values, and closes them; nothing is persisted. Examples include ephemeral "random_password", ephemeral "aws_secretsmanager_secret_version", ephemeral "azurerm_key_vault_secret" and Vault secrets. Their values can only be used in places that are also not persisted: provider configuration, other ephemeral contexts, ephemeral variables and outputs (ephemeral = true), and write-only arguments.

Write-only arguments are resource arguments that accept a value, pass it to the provider's API, and are always stored as null in state and plan. Providers add them for secret fields, such as password_wo on aws_db_instance or similar fields on other database and secret resources. Because Terraform never stores the value, it cannot detect a change by comparison, so these arguments come with a companion version argument (for example password_wo_version); incrementing it tells Terraform to send the new value.

Both features depend on provider support, so check the provider documentation for which resources offer them.

How it works

  1. An ephemeral resource generates or fetches the secret at run time.
  2. The value flows into a write-only argument on a managed resource.
  3. The provider sends it to the cloud API.
  4. Plan and state show the argument as null or hidden; nothing is persisted.
  5. To rotate, change the secret source and bump the version argument.

Example

ephemeral "random_password" "db" {
  length  = 32
  special = true
}

resource "aws_secretsmanager_secret_version" "db" {
  secret_id                = aws_secretsmanager_secret.db.id
  secret_string_wo         = ephemeral.random_password.db.result
  secret_string_wo_version = 1
}

resource "aws_db_instance" "main" {
  identifier          = "orders"
  engine              = "postgres"
  instance_class      = "db.t4g.medium"
  allocated_storage   = 50
  username            = "app_admin"
  password_wo         = ephemeral.random_password.db.result
  password_wo_version = 1
}

Common mistakes

  • Believing sensitive = true keeps values out of state.
  • Using a normal data source to read secrets, which stores them in state.
  • Forgetting to bump the version argument, so a new password is never applied.
  • Assuming every provider resource already supports write-only arguments.

How to answer in the interview

"Historically any secret Terraform handled, like a generated database password or a value read from a vault, was stored in plain text in plan files and state. Ephemeral resources, added in 1.10, exist only during a run: I can generate an ephemeral random password or read a secret from Secrets Manager or Key Vault, use it, and it's never persisted. Write-only arguments, added in 1.11, are arguments usually ending in _wo, like password_wo on a database, that are sent to the provider but not stored, with a version argument to trigger updates. Together I can create a database with a password that never lands in state, provided the provider supports it."

Likely follow-up questions

  • How do you rotate a write-only password? Generate or store a new value and increment the _wo_version argument.
  • Where can ephemeral values be used? Provider blocks, ephemeral variables/outputs, write-only arguments, other ephemeral resources.
  • Does state still need protection? Yes, it still contains IDs, topology and other sensitive data.
