Explain Spring bean scopes. What happens when you inject a prototype bean into a singleton?

Spring Framework · concept · levels mid

In one line

Singleton (default) means one instance per container, prototype a new instance per lookup, plus web scopes request, session, application and websocket. A prototype injected into a singleton is created only once, so use ObjectProvider, @Lookup or a scoped proxy to get fresh instances.

Detailed explanation

A bean scope controls how many instances the container creates and how long they live.

  • singleton: one shared instance per ApplicationContext, created at startup by default. This is right for stateless services, repositories and controllers. Note it is per container, not a JVM-wide singleton like the GoF pattern.
  • prototype: a new instance every time the bean is requested from the container (via injection or getBean). Spring creates and initialises it but does not manage destruction, so @PreDestroy is not called.
  • request: one instance per HTTP request; session: per HTTP session; application: per ServletContext; websocket: per WebSocket session. These need a web-aware context.

The classic trap: injection happens once, when the singleton is created. If a singleton ReportService has a prototype ReportBuilder injected into a field, that one builder is reused for every call, and if it holds state, concurrent requests interfere. The scope declaration does not help because the singleton never asks the container again.

Fixes:

  1. Inject ObjectProvider<ReportBuilder> (or ObjectFactory, or JSR-330 Provider) and call getObject() each time you need one. This is the most explicit option.
  2. Use @Lookup on an abstract or stub method that Spring overrides with CGLIB to return a new bean.
  3. Declare the bean with proxyMode = ScopedProxyMode.TARGET_CLASS, so the singleton holds a proxy that fetches the real target per call. This is how request- and session-scoped beans are injected into singletons; for prototypes it means a new instance per method call, which may surprise you.

How it works

  1. The container reads the scope on each bean definition.
  2. Singletons are created at startup and cached.
  3. Prototypes are created on every request to the container, never cached.
  4. Web scopes are stored in request or session attributes.
  5. Scoped proxies or providers defer the lookup to call time.

Example

@Component
@Scope(ConfigurableBeanFactory.SCOPE_PROTOTYPE)
class ReportBuilder {
    private final List<String> lines = new ArrayList<>();
    void add(String l) { lines.add(l); }
    String build() { return String.join("\n", lines); }
}

@Service
class ReportService {
    private final ObjectProvider<ReportBuilder> builders;
    ReportService(ObjectProvider<ReportBuilder> builders) { this.builders = builders; }

    String monthly() {
        ReportBuilder b = builders.getObject();   // fresh instance each call
        b.add("Revenue ...");
        return b.build();
    }
}

@Component
@RequestScope   // request scope with a TARGET_CLASS proxy by default
class RequestContext { String tenantId; }

Common mistakes

  • Expecting a prototype field in a singleton to be new per call.
  • Holding mutable request data in singleton fields.
  • Expecting @PreDestroy on prototypes.
  • Using session scope in a horizontally scaled app without shared sessions.

How to answer in the interview

"Singleton is the default: one instance per application context. Prototype gives a new instance every time the bean is requested from the container, and there are web scopes: request, session, application and websocket. If you inject a prototype into a singleton, injection only happens once when the singleton is created, so the singleton keeps the same prototype instance forever, which defeats the purpose and can cause thread-safety bugs if it's stateful. To get a fresh instance each time I inject an ObjectProvider and call getObject, or use a @Lookup method, or a scoped proxy, which is also how request-scoped beans are injected into singletons."

Likely follow-up questions

  • Are singleton beans thread safe by default? No; Spring does not synchronise them, so keep them stateless or use thread-safe structures.
  • Who destroys prototype beans? Nobody; the caller must release resources.
  • What does @RequestScope do? A shortcut for request scope with a class-based proxy.
