How do you insert or update a million rows efficiently with JPA?

Spring Data & JPA · scenario · levels mid, senior

In one line

For a million rows, enable JDBC batching (hibernate.jdbc.batch_size, ordered inserts/updates), flush and clear every batch, use SEQUENCE ids with a pooled optimiser (IDENTITY disables insert batching), split into chunked transactions (Spring Batch), and for the largest loads bypass JPA with JdbcTemplate batch updates, bulk SQL or COPY.

Detailed explanation

Calling save() a million times in one transaction with default settings is slow for three reasons: each INSERT is a separate round trip, every entity stays in the persistence context with a snapshot (memory grows and each flush dirty-checks more), and one giant transaction holds locks, bloats undo/WAL and can't restart midway.

JDBC batching. Set hibernate.jdbc.batch_size to around 30-100 so Hibernate groups statements into JDBC batches. Add hibernate.order_inserts=true and order_updates=true so statements for the same table are grouped, otherwise interleaved entity types break batches. For MySQL add rewriteBatchedStatements=true to the JDBC URL; PostgreSQL's reWriteBatchedInserts=true similarly helps.

Flush and clear. Every batch-size entities, call entityManager.flush() then clear() so the persistence context stays small and memory stays constant. A StatelessSession is an alternative with no persistence context at all.

Id generation. With GenerationType.IDENTITY the id is only known after the INSERT executes, and Hibernate needs it immediately to manage the entity, so it executes each insert at once and disables insert batching. Use SEQUENCE with an allocationSize (for example 50) and the pooled optimiser, which fetches blocks of ids with one sequence call. Assigned UUIDs also work.

Chunked transactions. Commit every few thousand rows rather than once, so failures don't roll back hours of work and locks are short. Spring Batch gives chunk-oriented processing with reader, processor and writer, restartability, skip and retry policies.

Bypass JPA for bulk. If you don't need entity behaviour, JdbcTemplate.batchUpdate with prepared statements is much faster; a set-based UPDATE ... WHERE or INSERT ... SELECT runs entirely in the database; and PostgreSQL COPY (via CopyManager) or MySQL LOAD DATA loads millions of rows in seconds. Consider dropping or deferring secondary indexes for one-off huge loads.

How it works

  1. Configure batching, ordering and sequence-based ids.
  2. Read input in a streaming fashion (cursor or file reader).
  3. Persist entities; every N, flush and clear.
  4. Commit per chunk; record progress for restart.
  5. For pure data loads, use JDBC batch, bulk SQL or COPY.

Example

spring:
  jpa:
    properties:
      hibernate:
        jdbc.batch_size: 50
        order_inserts: true
        order_updates: true
  datasource:
    url: jdbc:postgresql://db/app?reWriteBatchedInserts=true
@Entity
class Reading {
    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "reading_seq")
    @SequenceGenerator(name = "reading_seq", sequenceName = "reading_seq", allocationSize = 50)
    Long id;
}

@Transactional
public void importChunk(List<ReadingDto> chunk) {
    for (int i = 0; i < chunk.size(); i++) {
        em.persist(map(chunk.get(i)));
        if ((i + 1) % 50 == 0) { em.flush(); em.clear(); }
    }
}

// Fastest path without entities
jdbc.batchUpdate("insert into reading(id, sensor, value) values (nextval('reading_seq'), ?, ?)",
    rows, 1000, (ps, r) -> { ps.setString(1, r.sensor()); ps.setDouble(2, r.value()); });

Common mistakes

  • IDENTITY ids with batching expectations.
  • Never clearing the persistence context, causing OutOfMemoryError.
  • One transaction for the whole million rows.
  • Loading all input into memory before processing.
  • Using saveAll() on a huge list and assuming it batches by itself.

How to answer in the interview

"I enable JDBC batching with hibernate.jdbc.batch_size around 50 plus ordered inserts and updates. Entities pile up in the persistence context, so every batch I flush and clear to keep memory constant. IDENTITY id generation disables insert batching, so I use sequences with a pooled optimiser. Work is split into chunked transactions, for example with Spring Batch, so failures can restart. For very large loads I bypass JPA with JdbcTemplate batch updates, set-based SQL, or the database COPY command, which is much faster."

Likely follow-up questions

  • Why does IDENTITY prevent batching? The id is generated by the INSERT, so Hibernate must execute each insert immediately.
  • StatelessSession? No persistence context, no dirty checking or cascades; good for bulk.
  • Updating a million rows? Prefer one set-based UPDATE in batches by key range.
