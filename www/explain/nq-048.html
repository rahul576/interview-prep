How can shared mutable state cause problems in parallel streams?

Java 8+ Features · scenario · levels mid, senior

In one line

In a parallel stream several threads run your lambdas at the same time, so writing to a shared variable or non-thread-safe collection causes race conditions: lost updates, wrong counts, missing or null elements and even exceptions; the fix is to not share state and let collect, reduce or sum build the result.

Detailed explanation

Sequential code like orders.forEach(o -> result.add(o.id())) works because one thread does everything. Add .parallel() and the same lambda runs on several common-pool workers concurrently, all touching the same ArrayList.

ArrayList.add is not atomic: it reads size, possibly grows the internal array, writes the element and increments size. Two threads can read the same size and overwrite each other's slot (a lost update), leave null gaps, or one thread can write into the old array while another is copying it during a resize, which throws ArrayIndexOutOfBoundsException. A HashMap modified concurrently can lose entries or corrupt its bins. A counter like int[] count = {0}; ... count[0]++ is a read-modify-write and loses increments too.

The nastiest property is that these bugs are non-deterministic. With small test data the stream may not even split, so tests pass; under production volume, on more cores, results quietly differ from run to run. Nothing crashes; totals are just wrong.

Wrapping with Collections.synchronizedList or using AtomicInteger makes the code correct but serialises the threads on a lock or a contended variable, often making the parallel stream slower than a sequential one. It also does not fix ordering: elements arrive in nondeterministic order.

The idiomatic fix is to use mutable reduction. Collectors such as toList(), groupingBy, toMap and summingLong, and operations like reduce, sum and count, give each thread its own container and merge them with a combiner at the end. No synchronisation is needed and encounter order is preserved where required.

How it works

  1. The source is split into chunks for different worker threads.
  2. Each thread runs your lambda on its chunk.
  3. If the lambda writes to one shared object, the threads' writes interleave without coordination.
  4. Interleaved read-modify-write steps overwrite each other.
  5. With collect, each thread fills a private container, and containers are merged safely.

Example

// Broken: races on a shared ArrayList and counter
List<String> ids = new ArrayList<>();
int[] paid = {0};
orders.parallelStream().forEach(o -> {
    ids.add(o.id());                    // lost elements, nulls or AIOOBE
    if (o.isPaid()) paid[0]++;          // lost increments
});

// Correct: let the stream build the results
List<String> ids2 = orders.parallelStream().map(Order::id).toList();
long paid2 = orders.parallelStream().filter(Order::isPaid).count();

Map<String, Long> byStatus = orders.parallelStream()
    .collect(Collectors.groupingBy(Order::status, Collectors.counting()));

Common mistakes

  • Assuming code is safe because tests with small lists pass.
  • "Fixing" races with synchronized blocks that remove all parallelism.
  • Modifying the source collection inside the pipeline (interference).
  • Using a lambda that captures and mutates a field of the enclosing class.

How to answer in the interview

"In a parallel stream multiple threads run the lambdas at once. If they write to the same external variable or collection, like adding to an ArrayList declared outside or incrementing a counter, the updates race. Some are lost, the list can contain nulls or fewer elements, or it throws ArrayIndexOutOfBoundsException during an internal resize, and results change from run to run. It often passes tests and fails under load. Synchronising fixes correctness but kills the speed-up. The right fix is not to share state: use collect, toList, groupingBy, reduce or sum, which give every thread its own container and merge them safely."

Likely follow-up questions

  • Is using Collections.synchronizedList a good fix? It is correct but serialises all threads and loses order, so it usually defeats the purpose; use a collector.
  • Why do lambdas require effectively final variables? To prevent unsafe mutation of captured locals; arrays and objects bypass this, which is why the bug still happens.
  • Is ConcurrentHashMap acceptable? It is thread-safe, and groupingByConcurrent uses it, but order is lost and contention remains on hot keys.
