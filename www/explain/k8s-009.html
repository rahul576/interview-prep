What is a CNI plugin, and how do Calico, Cilium and Flannel differ?

Kubernetes · concept · levels entry, mid, senior

In one line

A CNI plugin implements the Container Network Interface: it gives each pod an interface and IP address and routes so every pod reaches every pod without NAT. Flannel is a simple overlay without NetworkPolicy, Calico offers BGP or overlay routing and strong policy, Cilium uses eBPF with L7 policy and observability, and cloud CNIs give pods VPC IPs.

Detailed explanation

The Kubernetes network model requires that every pod gets its own IP and can reach every other pod without NAT, but Kubernetes does not implement this itself. When the kubelet (via the container runtime) creates a pod sandbox, it calls the configured CNI plugin binary with ADD; the plugin creates a veth pair or similar interface, allocates an IP via IPAM, and programmes routes. DEL cleans up when the pod is removed.

How the major options differ:

  • Flannel: allocates a subnet per node and connects nodes with a VXLAN overlay (encapsulating pod packets in UDP). Easy to run, but it does not enforce NetworkPolicy; it is often paired with Calico for that (the "Canal" combination) or used in small or lab clusters.
  • Calico: can route pod traffic natively with BGP (no encapsulation, good performance, routable pod IPs) or use VXLAN/IP-in-IP where the network does not allow BGP. It is widely used for NetworkPolicy plus its own global and deny policies, and offers an eBPF dataplane option.
  • Cilium: an eBPF dataplane that can replace kube-proxy, enforce identity-based policy at L3/L4 and L7 (HTTP method and path, Kafka topics, DNS names), provide Hubble flow visibility, transparent encryption (WireGuard or IPsec) and service mesh features.
  • Cloud CNIs: AWS VPC CNI, Azure CNI and GKE's dataplane assign pods real VPC addresses, so they integrate directly with security groups and load balancers, at the cost of consuming subnet IPs.

How it works

  1. Pod scheduled; runtime creates the sandbox network namespace.
  2. Runtime calls CNI ADD with the configuration in /etc/cni/net.d.
  3. Plugin creates the interface and allocates an IP.
  4. Plugin installs routes or overlay tunnels between nodes.
  5. Policy agent (Calico/Cilium) enforces NetworkPolicies.
  6. On pod deletion, CNI DEL releases the IP.

Example

ls /etc/cni/net.d/          # which CNI is configured on this node
kubectl get pods -n kube-system -o wide | grep -E 'calico|cilium|flannel|aws-node'
cilium connectivity test    # end-to-end checks with Cilium

Common mistakes

  • Writing NetworkPolicies on Flannel and assuming they are enforced.
  • Running out of VPC IPs with cloud CNIs on small subnets.
  • Pod CIDR overlapping with corporate or VPC ranges.
  • MTU not reduced for overlay encapsulation.

How to answer in the interview

"CNI is the plugin contract the runtime calls when a pod is created: the plugin creates the interface, allocates an IP and sets up routes, so every pod can reach every other pod without NAT. Flannel is the simplest, a VXLAN overlay that doesn't enforce NetworkPolicy. Calico can route natively with BGP or use an overlay and is strong on NetworkPolicy. Cilium uses eBPF, can replace kube-proxy, supports L7-aware policy and gives Hubble flow visibility. Cloud CNIs like AWS VPC CNI give pods real VPC addresses."

Likely follow-up questions

  • Why do pods on different nodes fail with a wrong MTU? Encapsulation adds header bytes; large packets get dropped or fragmented, so small requests work and big ones hang.
  • Can you change CNI on a live cluster? Possible but disruptive; usually migrate node pools or rebuild.
  • What is IPAM? IP address management: how the plugin allocates pod IPs per node or subnet.
