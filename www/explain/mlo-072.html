How do you manage storage and retention of model artefacts, datasets and checkpoints?

MLOps · concept · levels mid, senior

In one line

Apply retention by category: keep production models with lineage as long as decisions must be explained, keep recent versions for rollback, expire unregistered runs and intermediate checkpoints, use lifecycle tiers for cost, and store production artefacts immutably with access control and audit.

Detailed explanation

ML platforms accumulate huge volumes: experiment runs with artefacts, checkpoints every hour of every training job, dataset snapshots and model versions. Without policy, storage bills grow forever, and important artefacts are still hard to find.

I classify artefacts:

  • Production models (current and past): the model binary, evaluation reports, model card, environment, code commit and references to the exact training data snapshot. Keep them as long as decisions made with them may need explaining, which regulation may set at several years (for example credit or medical decisions, or EU AI Act record-keeping for high-risk systems).
  • Recent registered versions: keep the last few for rollback.
  • Unregistered experiment runs: short retention, such as 90 days, unless tagged.
  • Intermediate checkpoints: delete after the job finishes, except the final and any tagged "keep".
  • Datasets: versioned snapshots (Delta/Iceberg time travel, lakeFS, DVC) retained while referenced by a retained model; raw personal data also follows data protection rules.

Implementation uses object storage lifecycle rules to move older objects to cool or archive tiers and expire them, plus registry-aware cleanup jobs. Production artefacts sit in buckets with versioning, object lock / immutability, least-privilege access and audit logs. Deleting anything still referenced by a registered model is blocked by the cleanup logic.

How it works

  1. Tag artefacts at creation with type, project, stage and retention class.
  2. Define policies per class with legal and data protection teams.
  3. Configure lifecycle rules per prefix or tag.
  4. Run a reference-aware cleanup job against the registry.
  5. Lock production artefacts; log all access.
  6. Report storage per team for cost awareness.

Common mistakes

  • Keeping everything forever, or deleting the training data a production model depends on.
  • Storing data references as mutable paths ("latest") rather than snapshot versions.
  • Archiving models needed for fast rollback in a slow-retrieval tier.
  • No legal input on retention, so obligations are missed.

How to answer in the interview

"I set different retention per artefact type. Models that are or were in production are kept with their evaluation reports and references to the exact training data snapshot for as long as decisions may need explaining, which regulation can set at years. Recent versions stay hot for rollback. Unregistered runs and intermediate checkpoints expire after a short period unless tagged. Lifecycle rules move old data to cheaper tiers. Production artefacts are immutable, access-controlled and audited, and cleanup is blocked for anything a registered model still references."

Likely follow-up questions

  • How do you reconcile deletion requests with long model retention? Delete or pseudonymise personal data in source and snapshots where required, document the impact, and retrain on the next cycle; legal decides whether the trained model must change.
  • Why snapshot references? A path like "latest" changes; a version ID reproduces the exact data.
  • How do you control cost per team? Tags plus cost reports and quotas.
