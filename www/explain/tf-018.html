How do you mark values sensitive in Terraform, and what does that protect and not protect?

Terraform · concept · levels entry, mid, senior

In one line

Mark variables and outputs with sensitive = true (many provider attributes already are); Terraform redacts them in plan and CLI output and propagates sensitivity through expressions, but values are still stored in state and plan files, and nonsensitive() should only be used when a value is truly safe.

Detailed explanation

Terraform output ends up in many places: CI logs, pull request comments, chat notifications. Without protection, a database password passed as a variable would be printed in the plan. Sensitive values prevent that.

You can set sensitive = true on input variables and outputs, and providers mark schema attributes such as password or private_key as sensitive. In plans and apply output they appear as (sensitive value). Sensitivity propagates: a local built with string interpolation from a sensitive variable is also sensitive, so "postgres://admin:${var.db_password}@host" is hidden too. If a root module output contains a sensitive value without being declared sensitive, Terraform raises an error, forcing you to be explicit. terraform output name hides it, while terraform output -raw name or -json show it, for scripts.

What it does not protect: sensitive values are stored in plain text in state and in saved plan files. Anyone who can read the state bucket, run terraform state pull or terraform console, or download the plan artifact can see them. So state and plans still need encryption at rest, strict access control and versioning. To keep secrets out of state entirely, use ephemeral resources, ephemeral variables and write-only arguments (Terraform 1.10/1.11+), or let the application read secrets directly from a vault.

nonsensitive() removes the marking. Use it only when the derived value genuinely reveals nothing, such as a hash, a boolean "is set", or a list length; otherwise you leak the secret into logs. There is also sensitive() to mark a value explicitly.

How it works

  1. A value is marked sensitive by variable, output or provider schema.
  2. Expressions using it inherit the mark.
  3. CLI rendering redacts marked values.
  4. State and plan files store real values.
  5. nonsensitive() drops the mark deliberately.

Example

variable "db_password" {
  type      = string
  sensitive = true
}

locals {
  conn = "postgres://app:${var.db_password}@${aws_db_instance.main.address}/orders"  # sensitive too
}

output "connection_string" {
  value     = local.conn
  sensitive = true
}

output "password_is_set" {
  value = nonsensitive(length(var.db_password) > 0)   # safe: reveals nothing
}

Common mistakes

  • Believing sensitive values are encrypted or excluded from state.
  • Using nonsensitive() just to silence an error.
  • Printing secrets with terraform output -json in CI logs.
  • Giving broad read access to state storage.

How to answer in the interview

"I mark variables and outputs with sensitive = true, and many provider attributes like passwords are sensitive by default. Terraform then shows (sensitive value) in plan and apply output, and sensitivity propagates through expressions, so anything derived from a secret is hidden too. That protects against secrets leaking into CI logs and PR comments. It doesn't encrypt anything: values are still in state and saved plans, so those need encryption and access control, or I avoid storing them using ephemeral resources and write-only arguments. I use nonsensitive() only for genuinely safe derived values like a hash or a length."

Likely follow-up questions

  • Why might a sensitive value make for_each fail? Sensitive values cannot be used as instance keys, because keys are shown in addresses.
  • Does terraform output -json show sensitive values? Yes, it prints them in plain text.
  • How do you keep secrets out of state entirely? Ephemeral resources, write-only arguments or runtime secret retrieval.
