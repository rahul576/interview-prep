How do you achieve zero-downtime rolling updates in Kubernetes?

Kubernetes · concept · levels mid, senior

In one line

Combine a RollingUpdate strategy with maxSurge and maxUnavailable: 0, readiness probes that gate traffic, graceful shutdown (handle SIGTERM, a short preStop delay, enough terminationGracePeriodSeconds), PodDisruptionBudgets for voluntary disruptions, and backward-compatible application and schema changes.

Detailed explanation

A rolling update replaces pods gradually, but "gradually" is not the same as "without errors". Requests fail at two moments: when new pods receive traffic before they are ready, and when old pods are killed while still receiving or processing requests. Each needs its own fix.

Pace and capacity. maxSurge sets how many extra pods may exist above the desired count; maxUnavailable sets how many may be missing. With maxUnavailable: 0 and maxSurge: 25% (or 1), capacity never drops: a new pod must become ready before an old one is removed. minReadySeconds adds a soak period before a pod counts as available.

Coming in. A readiness probe that reflects real readiness (warm caches, connections established) keeps new pods out of the Service endpoints until they can serve. Without it, a pod is "ready" as soon as the process starts.

Going out. On termination, two things happen in parallel: the pod is removed from EndpointSlices, and the kubelet sends SIGTERM to the container. Load balancers, ingress controllers and kube-proxy on every node take a moment to notice the endpoint removal, so for a few seconds new requests may still arrive. Hence:

  • A preStop hook that sleeps 5-15 seconds before SIGTERM, giving the rest of the system time to stop routing.
  • The application handles SIGTERM: stop accepting new connections, finish in-flight requests, close connections, then exit.
  • terminationGracePeriodSeconds (default 30) longer than preStop plus the longest request; after it, SIGKILL.

Other disruptions. PodDisruptionBudgets limit how many pods node drains, upgrades and autoscaler consolidation may evict at once.

Compatibility. During the rollout old and new versions serve simultaneously, so APIs, message formats and database schemas must work for both (expand-and-contract migrations).

How it works

  1. New ReplicaSet creates a surge pod.
  2. It passes readiness and joins endpoints.
  3. An old pod is selected; removed from endpoints and preStop starts.
  4. After the sleep, SIGTERM; app drains and exits.
  5. Repeat until all pods are new; PDB protects against concurrent drains.

Example

spec:
  strategy:
    type: RollingUpdate
    rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }
  minReadySeconds: 10
  template:
    spec:
      terminationGracePeriodSeconds: 45
      containers:
        - name: api
          readinessProbe:
            httpGet: { path: /ready, port: 8080 }
          lifecycle:
            preStop:
              sleep: { seconds: 10 }   # or exec: ["sleep","10"] on older clusters
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: api }
spec:
  maxUnavailable: 1
  selector: { matchLabels: { app: api } }

Common mistakes

  • No readiness probe, so traffic hits starting pods.
  • Apps that exit immediately on SIGTERM, or a shell entrypoint that never forwards it.
  • Grace period shorter than preStop plus request time.
  • Breaking schema changes deployed together with the code.

How to answer in the interview

"I use the rolling update strategy with maxSurge and maxUnavailable set to zero so capacity never drops, and readiness probes so new pods only get traffic when they're actually ready. On the way out, the pod is removed from endpoints and gets SIGTERM at the same time, so I add a short preStop sleep to let load balancers catch up, the app drains in-flight requests on SIGTERM, and terminationGracePeriodSeconds is long enough. PodDisruptionBudgets protect against node drains. And changes must be backward compatible, including the database schema, because both versions run at once."

Likely follow-up questions

  • Roll back if readiness passes but error rates rise? kubectl rollout undo, or better, Argo Rollouts or Flagger canaries with metric analysis that abort automatically.
  • Why does the shell entrypoint matter? sh -c as PID 1 may not forward SIGTERM; use exec form or a tini-style init.
  • What does minReadySeconds add? A pod must stay ready that long before it counts as available.
