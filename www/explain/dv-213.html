What is Amazon S3, and what is it used for?

Cloud (AWS) · concept · levels entry

In one line

Amazon S3 is object storage: objects (data + metadata) stored in buckets under keys, designed for eleven nines of durability and virtually unlimited scale, used for backups, static assets, uploads, logs, data lakes and Terraform state, secured with Block Public Access, encryption and IAM/bucket policies.

Detailed explanation

S3 is not a filesystem or a block device. You PUT and GET whole objects over HTTPS by key, such as invoices/2026/11/inv-123.pdf. The "folders" are just key prefixes. Objects can be up to 5 TB (with multipart upload for large files), and since 2020 S3 offers strong read-after-write consistency, so a read after a successful write returns the new data.

S3 is designed for 99.999999999% durability by storing data redundantly across multiple AZs, and it scales with no capacity planning; you pay for storage, requests and data transfer out. That makes it the default for:

  • Backups and database exports, often with versioning and Object Lock.
  • Static websites and assets served through CloudFront.
  • User uploads, typically via presigned URLs straight from the browser.
  • Logs from ALB, CloudTrail and VPC Flow Logs.
  • Data lakes, queried in place with Athena, Glue or Spark.
  • Terraform state with versioning and locking.

Security: new buckets have Block Public Access on and ACLs disabled by default; keep it on unless a bucket is deliberately public, and even then prefer CloudFront with Origin Access Control. All new objects are encrypted at rest (SSE-S3 by default, SSE-KMS for key control). Access is granted through IAM policies on roles and bucket policies, ideally least-privilege to specific prefixes.

Data management: versioning keeps older versions so deletes and overwrites are recoverable; lifecycle rules move objects to cheaper storage classes and expire old data; replication copies to another region or account.

How it works

  1. Create a bucket in a region (globally unique name).
  2. Upload objects by key; metadata and tags travel with them.
  3. Requests are authorised by IAM, bucket policy and Block Public Access.
  4. Lifecycle, replication and event notifications (to Lambda, SQS, EventBridge) run automatically.

Example

Giving an application access to one bucket only, via its IAM role:

{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Action": ["s3:ListBucket"],
      "Resource": "arn:aws:s3:::acme-invoices" },
    { "Effect": "Allow", "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::acme-invoices/*" }
  ]
}
aws s3 cp report.pdf s3://acme-invoices/2026/11/report.pdf
aws s3 presign s3://acme-invoices/2026/11/report.pdf --expires-in 900

Common mistakes

  • Making a bucket public to share a few files instead of presigned URLs.
  • Storing access keys in the app instead of using an IAM role.
  • Treating S3 like a filesystem (renames are copy + delete; no appends).
  • No lifecycle rules, so logs and old versions grow forever.

How to answer in the interview

"S3 is object storage: objects with metadata stored in buckets and addressed by key. It's designed for eleven nines of durability and scales without capacity planning, so we use it for backups, static assets behind CloudFront, user uploads, logs, data lakes and Terraform state. For security I keep Block Public Access on, rely on default encryption or KMS, and grant access through IAM roles and bucket policies scoped to the bucket or prefix. Versioning protects against accidental deletion, and lifecycle rules move old data to cheaper classes or delete it."

Likely follow-up questions

  • Access to one bucket only? IAM role policy scoped to that bucket ARN and bucket/*.
  • Let users upload directly? Presigned PUT URLs or POST policies.
  • Durability vs availability? Durability is not losing data; availability is being able to reach it right now.
