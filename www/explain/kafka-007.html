How do consumers commit offsets, and what goes wrong with auto-commit?

Kafka · concept · levels entry, mid

In one line

A committed offset is the next record to read; auto-commit commits on a timer regardless of processing, risking loss or duplicates on crash, so critical consumers disable it and commit manually after processing with commitSync/commitAsync.

Detailed explanation

Consumers store their position in the internal __consumer_offsets topic, keyed by group, topic and partition. By convention the committed value is the offset of the next record to consume, so after processing offset 41 you commit 42. When a consumer restarts or a partition moves in a rebalance, the new owner resumes from the committed offset.

With enable.auto.commit=true (the plain Java client default), the client commits the offsets returned by the previous poll() every auto.commit.interval.ms (5 s by default), as part of later poll calls. This is simple and fine when you process records synchronously inside the poll loop and duplicates are acceptable. Problems appear when processing is asynchronous or slow. If you hand records to another thread and the timer commits before they are done, a crash loses those records. If the consumer crashes after processing but before the next commit, the new owner reprocesses them, producing duplicates. Either way you get at-most-once or at-least-once by accident rather than by design.

For control, set enable.auto.commit=false and commit after processing. commitSync blocks and retries until success, so it is safe but adds latency; commitAsync does not block or retry, so it is used in the loop with a final commitSync on shutdown and in the rebalance listener's onPartitionsRevoked. The result is at-least-once, so handlers should also be idempotent. Note that Spring Kafka disables client auto-commit by default and commits per batch (AckMode.BATCH) on its own.

How it works

  1. poll() returns records from the current position.
  2. Process records (and write results).
  3. Commit offset of last processed record plus one.
  4. On rebalance revoke, commit synchronously.
  5. On restart, resume from committed offset.

Example

props.put("enable.auto.commit", "false");
try {
  while (running) {
    var records = consumer.poll(Duration.ofMillis(500));
    for (var r : records) handle(r);          // idempotent handler
    consumer.commitAsync();
  }
} finally {
  consumer.commitSync();
  consumer.close();
}

Common mistakes

  • Auto-commit with asynchronous processing threads.
  • Committing the processed offset instead of offset plus one.
  • Committing per record synchronously, killing throughput.
  • Not committing on partition revocation.

How to answer in the interview

"The committed offset is the next message the group will read, stored in the consumer offsets topic. Auto-commit commits periodically, every five seconds by default, whether or not my processing has finished, so a crash can lose messages that were committed but not processed, or duplicate those processed but not committed. When correctness matters I turn it off and commit after processing, using commitAsync in the loop and commitSync on shutdown and rebalance, and I make handlers idempotent because that gives at-least-once."

Likely follow-up questions

  • Spring Kafka AckMode? BATCH by default; RECORD, MANUAL and MANUAL_IMMEDIATE give finer control.
  • Why not commit every record? Commit cost; batch commits are enough with idempotency.
  • Where are offsets stored? The compacted __consumer_offsets topic.
