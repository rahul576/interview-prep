What is the difference between unit, integration, and end-to-end testing?

Testing · concept · levels mid, senior

In one line

Unit tests check one class in isolation with mocks (fast, many), integration tests check several components with real infrastructure such as a database or broker (slower, fewer), and end-to-end tests exercise the whole deployed system like a user (most confidence, slowest, fewest), arranged as a test pyramid.

Detailed explanation

The three levels trade speed and precision against realism.

Unit tests isolate one class or function. Dependencies are mocked, so the test runs in milliseconds and a failure points at a specific piece of logic. They are ideal for business rules, validation, calculations and edge cases. Their blind spot is everything between components: a mocked repository cannot tell you the SQL is wrong.

Integration tests combine real parts. Examples: a Spring Data repository against PostgreSQL in Testcontainers, a REST controller through the full Spring context with serialisation, validation and security filters, a @KafkaListener consuming from a real broker, or a client against a WireMock server. They find wiring, mapping, SQL, transaction and configuration bugs. They take seconds and need Docker or more setup.

End-to-end tests run against the deployed system through its UI (Playwright, Selenium) or public API (REST Assured): register, add to cart, pay, receive confirmation. They prove the system works as users experience it, including networking and configuration, but they are slow, need shared environments and data, fail for reasons unrelated to the change, and make diagnosis hard.

The test pyramid (Mike Cohn) recommends a broad base of unit tests, a middle layer of integration tests and a thin top of E2E tests for critical journeys. The anti-pattern is the ice-cream cone: mostly manual and E2E tests, few unit tests, giving slow, flaky feedback. In microservices, contract tests sit between integration and E2E and replace much of the E2E layer.

How it works

  1. Developers write unit tests for each behaviour as they code.
  2. Integration tests cover each adapter: database, messaging, HTTP clients, controllers.
  3. Contract tests verify interfaces between services.
  4. A few E2E tests run critical journeys after deployment to staging.
  5. CI runs unit tests first, then integration, then E2E, failing fast.

Example

// Unit: service with mocked repository
when(repo.findById(1L)).thenReturn(Optional.of(order));
assertThat(service.total(1L)).isEqualByComparingTo("40.00");

// Integration: real PostgreSQL via Testcontainers
@DataJpaTest @Testcontainers
class OrderRepositoryIT {
    @Container @ServiceConnection
    static PostgreSQLContainer<?> pg = new PostgreSQLContainer<>("postgres:16");
}

// End-to-end: deployed API with REST Assured
given().baseUri(stagingUrl).body(newOrderJson).contentType(JSON)
.when().post("/orders")
.then().statusCode(201).body("status", equalTo("CONFIRMED"));

Common mistakes

  • Calling a test with the full Spring context a "unit test".
  • Testing all logic through slow E2E tests (ice-cream cone).
  • Using H2 instead of the real database in integration tests.
  • No E2E checks at all, missing deployment and configuration errors.

How to answer in the interview

"A unit test checks one class in isolation with dependencies mocked, so it's fast and precise and we have many. An integration test checks components working together with real infrastructure, like a repository against PostgreSQL in Testcontainers or a controller through the full Spring context, catching wiring, SQL and serialisation issues that mocks hide, at the cost of speed. An end-to-end test runs a real user journey against the deployed system; it gives the most confidence but is slow and often flaky. So I follow the pyramid: many unit tests, fewer integration tests, contract tests between services, and only a few E2E tests for critical flows."

Likely follow-up questions

  • Where do contract tests fit? Between integration and E2E, verifying service interfaces without a full environment.
  • What is the ice-cream cone? An inverted pyramid dominated by manual and E2E tests.
  • Is a @WebMvcTest a unit or integration test? A slice integration test: it uses the real MVC framework but mocks services.
