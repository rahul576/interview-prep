How do you design tools that agents can use reliably?

AI Agents & AIOps · concept · levels mid, senior

In one line

Treat tools as the agent-computer interface: give them clear names and model-oriented descriptions, few strictly typed parameters, design them around tasks rather than raw APIs, return concise relevant results, provide actionable errors and safe defaults, and test and iterate with the real model.

Detailed explanation

An agent can only be as good as its tools. The model knows a tool only through its name, description and parameter schema, so these deserve as much care as a user interface. A good description explains what the tool does, when to use it and when not to, what it returns, and important constraints, written as you would brief a new colleague.

Parameters should be few, with strict types, enums, formats and examples in the JSON Schema. Use identifiers the model naturally has, such as an email address or order number, rather than internal UUIDs it must discover through other calls. Many providers support strict schema modes that guarantee arguments match the schema.

Tools should match tasks, not database tables or REST endpoints. One find_orders(customer_email, from_date, status) is better than list_customers, get_customer, list_orders that the model must chain correctly, because each extra step costs tokens and adds failure risk. Equally, avoid giant do-everything tools with dozens of options.

Results consume context, so they should be concise and relevant: select fields, paginate, summarise, and return human-readable names alongside IDs. Errors should be actionable: "date must be YYYY-MM-DD, got 03/04/2026" lets the model self-correct, while "400 Bad Request" leads to loops. Destructive tools get safe defaults such as dry_run=true and confirmation requirements enforced in code.

Finally, test with the actual model on realistic tasks, read the traces, look for misuse or confusion, and iterate on names, descriptions and boundaries. Standards like MCP make well-designed tools reusable across agents.

How it works

  1. List the tasks the agent must accomplish; design one tool per meaningful task.
  2. Write names and descriptions for the model, including when not to use it.
  3. Define strict schemas with enums, formats and examples.
  4. Return compact, structured results with pagination and clear empty states.
  5. Return actionable errors; default destructive tools to dry run.
  6. Evaluate tool selection and argument accuracy from traces; iterate.

Example

{
  "name": "find_orders",
  "description": "Search a customer's orders. Use when the user asks about order status, delivery or refunds. Returns at most 20 orders, newest first. Do not use for invoices; use get_invoice instead.",
  "input_schema": {
    "type": "object",
    "properties": {
      "customer_email": {"type": "string", "format": "email"},
      "status": {"type": "string", "enum": ["any", "open", "shipped", "delivered", "cancelled"], "default": "any"},
      "from_date": {"type": "string", "description": "ISO date, e.g. 2026-03-01"}
    },
    "required": ["customer_email"]
  }
}

Error returned to the model: {"ok": false, "error": "from_date must be ISO YYYY-MM-DD, got '03/04/26'. Example: 2026-04-03"}.

Common mistakes

  • Exposing raw internal APIs one-to-one as tools.
  • Vague descriptions like "gets data".
  • Returning huge JSON payloads that flood the context.
  • Generic error messages that give no hint how to fix the call.
  • Never looking at traces to see how the model actually uses the tools.

How to answer in the interview

"Tools are the interface between the model and the world, so I design them like a UI for the model. Each has a clear name and a description that says what it does, when to use it, what it returns and its constraints. Parameters are few and strictly typed, with enums, formats and examples, using identifiers the model naturally has. Tools match tasks, so one tool that finds orders by customer and date beats three low-level calls. Results are concise, with pagination, because they consume context. Errors tell the model how to fix the call, and destructive tools default to dry run. Then I test with the real model, read the traces and iterate."

Likely follow-up questions

  • The agent keeps passing the wrong date format? Specify the format and an example in the schema, accept and normalise common formats in code, and return an actionable error.
  • How many tools is too many? It depends on the model, but dozens of overlapping tools degrade selection; scope per agent or use tool search.
  • Where does MCP fit? It standardises exposing tools to any compatible agent client.
