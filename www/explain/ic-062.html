How do you estimate and control infrastructure cost in IaC workflows?

Infrastructure as Code · concept · levels mid

In one line

Make cost visible before money is spent: run Infracost (or similar) on the plan to post the monthly cost difference on each pull request, enforce policies on thresholds and instance types, build cost-conscious defaults into modules, apply tags via default_tags for allocation, and compare estimates with the real bill.

Detailed explanation

Cloud cost is mostly decided when infrastructure is designed, yet teams usually see it a month later on the invoice. Infrastructure as code gives a natural checkpoint: every change becomes a plan, and a plan can be priced.

Estimation in review. Infracost parses the Terraform plan (or HCL), maps resources to public price lists and posts a pull-request comment such as "+$420/month: NAT gateway $33 + data processing, db.r6g.xlarge Multi-AZ $380". The reviewer sees cost next to the code. Usage-based charges (data transfer, Lambda invocations, S3 requests) cannot be known from code, so you supply a usage file with realistic assumptions or treat those numbers as ranges.

Guardrails. The cost JSON can be checked with policy as code (OPA/Conftest, Sentinel or the tool's own guardrails): require approval when a change adds more than, say, $500/month, block GPU or very large instance families outside approved accounts, or require lifecycle rules on buckets.

Defaults in modules. Most savings come from good defaults: gp3 instead of gp2 volumes, Graviton/ARM instance types where supported, single NAT gateway in non-production, S3 lifecycle and log retention policies, autoscaling minimums of one in dev, and schedules that stop dev resources at night.

Allocation and feedback. default_tags on the provider (and labels on GCP) puts team, env, service and cost-centre on everything, enabling showback in Cost Explorer or FinOps tools. Budgets and anomaly alerts catch what estimates miss, and comparing estimate to actual improves the usage assumptions.

How it works

  1. Pipeline runs terraform plan -out and terraform show -json.
  2. Infracost computes the cost of base and PR branches and the difference.
  3. A comment is posted on the PR; policy checks evaluate the JSON.
  4. Large increases require FinOps or lead approval.
  5. After deploy, tagged spend is tracked against budgets.

Example

terraform plan -out tfplan && terraform show -json tfplan > plan.json
infracost breakdown --path plan.json --format json --out-file cost.json
infracost comment github --path cost.json --repo org/infra \
  --pull-request "$PR_NUMBER" --github-token "$GITHUB_TOKEN" --behavior update

Common mistakes

  • Treating the estimate as exact while ignoring usage-based costs.
  • Policies so strict that teams bypass the pipeline.
  • No tags, so the bill cannot be attributed to teams.
  • Optimising only at creation and never reviewing running resources.

How to answer in the interview

"I put cost into the pull request. Infracost reads the Terraform plan and comments the monthly difference, for example that this change adds 420 dollars because of a NAT gateway and a bigger database, so it's discussed in review rather than discovered on the bill. Policies flag changes above a threshold or expensive instance types without approval. Shared modules have cost-conscious defaults like gp3, Graviton and lifecycle rules, and provider default_tags make every resource attributable to a team. Then budgets and anomaly alerts, and comparing estimates with actual spend, close the loop."

Likely follow-up questions

  • Why might the estimate differ from the real bill? Usage-based charges, discounts like Savings Plans, data transfer and resources created outside Terraform.
  • How do you handle usage-based services? A usage file with assumptions, and budgets plus alerts as a backstop.
  • Who approves cost increases? The owning team lead or FinOps above a threshold, enforced by the policy check.
