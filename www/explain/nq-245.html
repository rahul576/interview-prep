What is database normalization?

Databases & SQL · concept · levels entry

In one line

Normalization is structuring relational tables so each fact is stored once, removing redundancy and insert, update and delete anomalies, by following normal forms: 1NF (atomic values), 2NF (no partial dependency), 3NF (no transitive dependency) and the stricter BCNF.

Detailed explanation

The core idea is functional dependency: if knowing column A determines column B, then B should live in a table whose key is A. When this rule is broken, the same fact appears in many rows and anomalies follow:

  • Update anomaly: the customer's city appears in every order; changing it in some rows and not others leaves contradictions.
  • Insert anomaly: you cannot store a new customer until they place an order.
  • Delete anomaly: deleting a customer's only order also deletes the customer's details.

The normal forms:

  • 1NF: each column holds atomic values, no repeating groups like phone1, phone2, phone3 or comma-separated lists, and each row is identifiable by a key.
  • 2NF: in 1NF, and every non-key column depends on the whole primary key. In enrolment(student_id, course_id, course_name), course_name depends only on course_id, so it moves to a course table. This matters only with composite keys.
  • 3NF: in 2NF, and no non-key column depends on another non-key column (transitive dependency). In orders(id, customer_id, customer_city), city depends on customer_id, not on the order, so it belongs in customer.
  • BCNF: every determinant must be a candidate key, closing a few edge cases 3NF allows.
  • Higher forms (4NF, 5NF) deal with multi-valued and join dependencies and are rarely discussed in interviews.

The result is consistent data that is updated in one place, smaller rows and clearer constraints, at the cost of more joins. OLTP systems usually aim for 3NF or BCNF; reporting systems often denormalise deliberately.

How it works

  1. List all attributes and determine functional dependencies.
  2. Choose a key for each entity.
  3. Remove repeating groups into separate tables (1NF).
  4. Move columns that depend on part of a composite key (2NF).
  5. Move columns that depend on non-key columns (3NF).
  6. Link tables with foreign keys and verify queries still work efficiently.

Example

Before (unnormalised):
order_id | customer | customer_city | products
1001     | Asha     | Pune          | Lamp, Bulb

After (3NF):
customer(customer_id PK, name, city)
orders(order_id PK, customer_id FK, order_date)
product(product_id PK, name, price)
order_item(order_id FK, product_id FK, qty, unit_price, PK(order_id, product_id))

Common mistakes

  • Thinking 2NF matters for tables with a single-column key.
  • Treating price on an order line as redundant; it records price at time of sale.
  • Normalising lookup data so far that every query needs many joins.
  • Memorising forms without being able to give an anomaly example.

How to answer in the interview

"Normalisation structures relational tables to remove redundant data and avoid insert, update and delete anomalies. You split data into related tables linked by keys. First normal form means atomic values and no repeating groups. Second normal form means every non-key column depends on the whole primary key, not just part of a composite key. Third normal form means no transitive dependencies, so customer city belongs in the customer table, not every order. BCNF is a stricter 3NF. The result is that each fact is updated in one place, at the cost of more joins."

Likely follow-up questions

  • Example of an update anomaly? Changing a customer's city in only some of their order rows.
  • What is a transitive dependency? A non-key column determined by another non-key column.
  • Do you always normalise to 3NF? For OLTP yes, then denormalise selectively for proven read needs.
