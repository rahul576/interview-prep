How do you secure a Kubernetes cluster?

Kubernetes · concept · levels senior, lead

In one line

Secure a cluster in layers: RBAC least privilege with SSO, dedicated service accounts and workload identity, default-deny NetworkPolicies, Pod Security Standards (restricted) and hardened securityContext, admission control (Kyverno/Gatekeeper) with image scanning and signing, plus patching, private API endpoints, secret encryption, audit logs and runtime detection.

Detailed explanation

Identity and access. Humans authenticate through SSO/OIDC to the cloud or API server; no shared admin kubeconfigs. RBAC uses namespaced Roles and RoleBindings for teams, with ClusterRoles bound only where needed; avoid cluster-admin, wildcard verbs and access to secrets, pods/exec or escalate/bind. Each workload gets its own service account, with automountServiceAccountToken: false when it does not call the API. Cloud access uses workload identity (IRSA or EKS Pod Identity, Azure Workload Identity, GKE Workload Identity) rather than static keys.

Network. NetworkPolicies (enforced by the CNI) start with default-deny ingress, and ideally egress, per namespace, then allow only required flows, such as frontend to API and API to database. Block access to the cloud metadata endpoint from pods that do not need it. A service mesh can add mTLS and identity-based authorisation.

Workload hardening. Pod Security Admission at the restricted level enforces: run as non-root, no privileged containers, no host namespaces or hostPath, dropped capabilities, allowPrivilegeEscalation: false, a seccomp profile. Add a read-only root filesystem and resource limits.

Supply chain and admission. CI scans images (Trivy, Grype) and signs them (Sigstore cosign); Kyverno or OPA Gatekeeper admission policies block unsigned images, latest tags, untrusted registries and non-compliant manifests.

Platform. Keep Kubernetes and nodes patched; restrict the API endpoint (private or IP-allow-listed); enable encryption at rest for Secrets with KMS; turn on audit logging; run runtime detection such as Falco for suspicious behaviour (shells in containers, unexpected network connections). Benchmarks like CIS and tools like kube-bench check the baseline.

How it works

  1. SSO + RBAC for people; service accounts + workload identity for apps.
  2. Namespaces per team with default-deny NetworkPolicies.
  3. PSA restricted labels on namespaces.
  4. Admission policies verify images and manifests.
  5. Audit logs and Falco alerts feed the SIEM.

Example

apiVersion: v1
kind: Namespace
metadata:
  name: shop
  labels:
    pod-security.kubernetes.io/enforce: restricted
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny, namespace: shop }
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]

Common mistakes

  • Everyone using cluster-admin.
  • Static cloud keys in Secrets instead of workload identity.
  • NetworkPolicies defined but the CNI does not enforce them.
  • Default service account tokens mounted in every pod.

How to answer in the interview

"I layer it. RBAC with least privilege: namespaced roles, SSO for humans, no shared admin credentials. Each workload has its own service account, token automount off when not needed, and cloud access through workload identity like IRSA instead of static keys. Network policies default-deny and allow only required flows. Pod Security Standards at restricted enforce non-root, no privileged containers and dropped capabilities, plus a read-only root filesystem. Kyverno or Gatekeeper block non-compliant manifests and unsigned images, which are scanned in CI. And I keep the cluster patched, restrict the API endpoint, encrypt secrets, enable audit logs and run Falco."

Likely follow-up questions

  • How would you limit the blast radius of a compromised pod? Restricted pod security, minimal service account permissions, default-deny network policies and narrow workload identity.
  • Why is pods/exec sensitive? It gives a shell into containers and their secrets.
  • How do you verify image signatures? Admission policy checking cosign signatures against trusted keys or identities.
