Which SLOs would you define for an AI agent in production?

AI Agents & AIOps · concept · levels mid, senior

In one line

Agent SLOs combine availability of the agent and its tools, latency (first response, completion), task success rate, cost per task, escalation and human intervention rate, and near-zero safety violations, tracked per agent version with breaches triggering investigation or rollback.

Detailed explanation

Classic SLOs measure whether a service responds and how fast. An agent can respond quickly with HTTP 200 and still fail the task, so its SLOs must include quality and safety.

Availability: the agent service accepts and completes requests without errors, and its critical tools are reachable, for example 99.9% of requests accepted. Latency: for interactive agents, time to first token or first response under a few seconds; for background agents, task completion within a target such as 95% of tickets triaged within 10 minutes.

Task success rate: the core quality SLO. Measure it with automated verification where tasks are checkable (tests pass, record correctly updated), or through sampled human review, LLM-as-judge evaluations calibrated against humans, and user feedback. Example: at least 90% of tickets correctly categorised in weekly samples.

Cost per task: median and p95 tokens or money per task within budget, because cost regressions from longer loops or a pricier model are a real failure mode. Escalation and intervention rate: how often humans must step in; it should fall over time, but not because escalation was suppressed. Safety: very low tolerance objectives, such as zero unauthorised actions and near-zero policy violations, with any breach investigated.

SLOs are tracked per agent version (prompt, model, tools), so a regression after a release is visible and can trigger rollback, just like any service.

How it works

  1. Define SLIs and targets with product owners.
  2. Instrument traces with version, outcome, cost, escalation and safety events.
  3. Sample tasks for quality review where outcomes are not auto-checkable.
  4. Build dashboards and error-budget alerts per version.
  5. Breach: investigate, roll back, or pause autonomy.

Example

agent: ticket-triage
version_label: true
slos:
  availability:      { sli: accepted_and_completed / total, target: 99.9%, window: 28d }
  latency:           { sli: p95_completion_time, target: "< 10m" }
  task_success:      { sli: sampled_correct_category, target: ">= 90%", sample: 200/week }
  cost_per_task:     { sli: p95_cost_usd, target: "< 0.08" }
  human_intervention:{ sli: escalated / total, target: "< 15%" }
  safety:            { sli: unauthorised_actions, target: 0 }

Common mistakes

  • Only uptime and latency SLOs for an agent.
  • Quality measured once at launch instead of continuously.
  • Not tagging metrics by version, so regressions cannot be traced.
  • Rewarding low escalation rates, encouraging the agent to never escalate.

How to answer in the interview

"I'd combine classic and quality SLOs. Availability of the agent and its critical tools, latency to first response and to completion, and task success rate, measured with automated checks where possible and sampled human review otherwise. Cost per task within budget, because cost regressions are real. Escalation and human intervention rate, which should fall over time without hiding problems. And safety objectives with near-zero tolerance, like no unauthorised actions. I track everything per agent version, so breaches trigger investigation or rollback like any service."

Likely follow-up questions

  • Outcomes known days later? Use leading proxies now and backfill with delayed labels.
  • Error budgets for quality? Yes; budget burn can block risky releases.
  • Per-tenant SLOs? Useful when task types differ by customer.
