How do you secure access to an Azure Storage account?

Azure · concept · levels mid, senior

In one line

Prefer Entra ID with data-plane RBAC and managed identities, disable shared key authorisation, use user delegation SAS for temporary access, lock the network with private endpoints and no public access, and enable encryption, soft delete, versioning and logging.

Detailed explanation

Storage accounts support several authorisation methods, and the account key is the most dangerous: it grants full control over all data, it does not identify who used it, and rotating it breaks every client using it. Security best practice is therefore identity-based access.

Entra ID and RBAC: applications use managed identities and people use their Entra accounts, with data-plane roles such as Storage Blob Data Reader, Storage Blob Data Contributor or Storage Queue Data Message Processor, scoped to the account or, better, a single container. Note that control-plane roles like Contributor do not by themselves grant data access with Entra auth.

Disable shared key: setting allowSharedKeyAccess to false blocks account-key and account-SAS requests. Before doing so, find remaining key users, for example in resource logs (StorageBlobLogs shows the AuthenticationType) or the Transactions metric split by authentication type.

SAS tokens: when an external client needs temporary access, use a user delegation SAS, signed with Entra credentials, scoped to a container or blob, with minimal permissions, HTTPS only and a short expiry (maximum seven days). Stored access policies allow revocation for service SAS.

Network: add private endpoints and set public network access to Disabled, or restrict to selected VNets and IPs, allowing trusted Azure services where needed. Disable anonymous blob access and require TLS 1.2 or higher.

Data protection: encryption at rest is always on with Microsoft-managed keys; use customer-managed keys in Key Vault for compliance. Enable soft delete for blobs and containers, versioning, point-in-time restore, and immutability policies for regulated or ransomware-resilient data. Send diagnostic logs to Log Analytics and enable Defender for Storage for malware scanning and threat detection.

How it works

  1. Assign managed identities and data-plane roles at container scope.
  2. Identify and migrate clients still using keys or account SAS.
  3. Disable shared key authorisation and anonymous access.
  4. Add private endpoints; disable public network access.
  5. Enable soft delete, versioning, logging and Defender.
  6. Enforce all of this through Azure Policy.

Example

az role assignment create --assignee <app-identity-id> \
  --role "Storage Blob Data Contributor" \
  --scope /subscriptions/<sub>/resourceGroups/rg-docs/providers/Microsoft.Storage/storageAccounts/stdocs/blobServices/default/containers/invoices
az storage account update -n stdocs -g rg-docs \
  --allow-shared-key-access false --allow-blob-public-access false \
  --public-network-access Disabled --min-tls-version TLS1_2
az storage blob generate-sas --account-name stdocs -c invoices -n inv-981.pdf \
  --permissions r --expiry 2026-11-22T12:00Z --auth-mode login --as-user --https-only
StorageBlobLogs
| where TimeGenerated > ago(7d) and AuthenticationType in ("AccountKey", "SAS")
| summarize count() by CallerIpAddress, UserAgentHeader, AuthenticationType

Common mistakes

  • Account keys in application configuration.
  • Long-lived account SAS tokens shared by email.
  • Contributor role assumed to grant data access.
  • Private endpoint added but public access left enabled.
  • Disabling shared key without checking dependencies (some tools still need it).

How to answer in the interview

"I prefer identity-based access: applications use managed identities and people use Entra ID, with data-plane roles like Storage Blob Data Reader or Contributor scoped to the container. Account keys give full control and are hard to rotate, so I disable shared key authorisation once nothing depends on it, after checking the resource logs for key usage. For temporary client access I use a short-lived user delegation SAS signed with Entra credentials. On the network side I use private endpoints and disable public network access, and block anonymous access. Data is encrypted at rest, optionally with customer-managed keys, and I enable soft delete, versioning, logging and Defender for Storage, all enforced with Azure Policy."

Likely follow-up questions

  • How would you find which applications still use account keys? Query StorageBlobLogs for AuthenticationType AccountKey or split the Transactions metric by authentication.
  • What if a SAS token leaks? Revoke via stored access policy, rotate keys for key-signed SAS, or revoke user delegation keys.
  • When use customer-managed keys? For compliance requirements needing key control and revocation.
