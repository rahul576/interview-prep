A widely used Terraform module needs a breaking change. How do you roll it out across 100 consumers?

Infrastructure as Code · scenario · levels senior

In one line

Ship it as a new major version with a migration guide, keep the old major supported for a deprecation period, add moved blocks and compatibility shims so upgrades don't recreate resources, open automated upgrade PRs with plans (Renovate), start with early adopters, and track adoption to end of life.

Detailed explanation

A breaking change in a popular module is a migration project, not a release. If 100 stacks must upgrade at once, someone will get a destroy-and-create plan on a production database. The goal is that upgrades are safe, visible and paced by consumers.

Versioning. Under semantic versioning, breaking changes (removed inputs, renamed outputs, new required variables, resources that move) require a major version. The changelog and migration guide list each breaking change with before/after code. Consumers pin versions (~> 4.0), so nobody is upgraded by surprise.

Making the upgrade cheap.

  • moved blocks inside the module map old resource addresses to new ones, so a refactor from count to for_each or into a submodule does not recreate resources.
  • Compatibility inputs: keep old variable names for one major version, map them to the new ones and emit a deprecation warning (for example with a check block or validation message).

Support window. The previous major gets security and critical fixes for a published period, such as six months, so teams can schedule the work.

Rollout. Renovate (or a script using the registry and code search) opens an upgrade PR in each consumer repository; the pipeline runs a plan, so owners see the exact impact, ideally "0 to destroy". Start with a few friendly teams, fix surprises in a minor release, then broaden. A dashboard from code search or registry download data shows who is still on v3, and the platform team helps stragglers before end of life.

How it works

  1. Design change; write migration guide and moved blocks.
  2. Release v4.0.0; keep v3.x on a maintenance branch.
  3. Early adopters upgrade; fixes ship as v4.0.x.
  4. Renovate opens PRs to all consumers with plans attached.
  5. Track adoption; announce v3 end of life; help the last teams.

Example

# Inside module v4: resources moved from count to for_each and into a submodule
moved {
  from = aws_subnet.private[0]
  to   = module.subnets.aws_subnet.private["eu-west-1a"]
}

variable "subnet_cidrs" {            # deprecated in v4, removed in v5
  type    = list(string)
  default = null
}
{ "packageRules": [ { "matchDatasources": ["terraform-module"], "matchUpdateTypes": ["major"], "labels": ["breaking-module-upgrade"] } ] }

Common mistakes

  • Breaking changes in a minor version.
  • Consumers referencing ?ref=main, so everyone breaks at once.
  • No moved blocks, causing replacement of stateful resources.
  • Dropping the old version without knowing who still uses it.

How to answer in the interview

"I release it as a new major version with a clear changelog and migration guide, and keep the previous major supported with fixes for a defined period so nobody has to rush. Inside the module I add moved blocks so consumers don't get destroy-and-create plans, and where possible keep old inputs working with deprecation warnings. Renovate opens upgrade PRs in every consumer repo with a plan attached, so owners see the exact impact. I start with a few friendly teams, fix surprises, then track adoption on a dashboard and help the remaining teams before the old version reaches end of life."

Likely follow-up questions

  • How would you detect which repos use the old version? Code search for the module source and version constraints, or registry download data.
  • Can moved blocks span modules? Yes within one state: a module can move resources into its own child modules.
  • What if a change truly requires replacement? Document a manual migration path and provide tooling or office hours.
