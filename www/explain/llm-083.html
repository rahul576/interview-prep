How do you roll out a new LLM feature or model change gradually and safely?

LLMOps & RAG · concept · levels mid, senior

In one line

Ship LLM changes behind feature flags that select a versioned model/prompt configuration, widen exposure in stages (internal → beta → 5% → 25% → 100%), watch quality, safety, latency and cost guardrails against a control cohort, and keep a kill switch and one-click rollback.

Detailed explanation

LLM changes are riskier than ordinary code changes because their behaviour is probabilistic. A new model or reworded prompt can improve average quality while breaking a niche use case, raising refusals or doubling token usage. Offline evaluations catch a lot, but real traffic always contains surprises, so exposure must grow gradually.

The key idea is to decouple deployment from release. The code that can call the new model is deployed to production, but a feature flag (LaunchDarkly, Unleash, OpenFeature, or an in-house config service) decides who gets it. For model or prompt changes, the flag does not toggle code paths; it selects a configuration version: model id, prompt template version, temperature, tool set, retrieval settings. Rollback is then just pointing the flag back to the previous version, with no redeploy.

Audiences widen in rings. Internal users go first because they expect rough edges and give detailed feedback. A beta group of friendly customers follows. Then a percentage rollout, sticky per user so people do not flip between behaviours. At each stage you compare the treatment cohort with the control through A/B testing: thumbs up/down, retries, regenerations, escalations to humans, task completion, plus safety signals (moderation hits, guardrail blocks), p95 latency and cost per request. A kill switch disables the feature instantly and falls back to the previous behaviour or a non-AI path.

How it works

  1. Version the full configuration (model, prompt, params, tools) and run offline evals in CI.
  2. Deploy code dark; the flag defaults to the current version.
  3. Enable for internal users, then a beta segment; review traces and feedback.
  4. Ramp 5% → 25% → 50% → 100%, holding each step long enough for meaningful data.
  5. Define automatic guardrails: if a metric crosses its threshold, the flag reverts.
  6. Prepare release notes and brief support, because users notice changed AI behaviour.

Example

flag: support-assistant-config
variations:
  control:   { model: model-a-2026-03, prompt: support-v14, temperature: 0.2 }
  candidate: { model: model-b-2026-09, prompt: support-v15, temperature: 0.2 }
rules:
  - segment: employees        -> candidate
  - segment: beta-customers   -> candidate
  - rollout: { candidate: 5, control: 95, bucketBy: userId }
guardrails:
  - metric: escalation_rate      max_relative_increase: 10%
  - metric: moderation_flag_rate max_absolute: 0.2%
  - metric: cost_per_request     max_relative_increase: 30%
killSwitch: serve control

Common mistakes

  • Shipping a new model by redeploying, so rollback takes a full release cycle.
  • Judging the rollout on "looks fine" rather than comparing against a control cohort.
  • Bucketing per request instead of per user, giving inconsistent experiences.
  • Watching only quality and forgetting cost and latency, which can explode with a new model.
  • Not telling support, who then get surprised by tickets about "the bot changed".

How to answer in the interview

"I treat an LLM change like a risky release and decouple deploy from release with feature flags. The flag selects a versioned configuration: model, prompt and parameters, so rollback is just switching the flag back. I start with internal users, then a beta group, then ramp by percentage, sticky per user. At every stage I compare against the control cohort on quality signals like ratings, retries and escalations, safety signals like moderation hits, plus latency and cost per request. I define guardrail metrics that automatically revert the flag, and keep a kill switch that falls back to the old behaviour. And I brief support, because users do notice when AI behaviour changes."

Likely follow-up questions

  • Which metric would you use as an automatic stop guardrail? A safety metric such as moderation or policy-violation rate, plus escalation rate, because they are fast and unambiguous.
  • How long per ramp step? Until you have statistically meaningful volume, often days.
  • What about shadow testing? Run the candidate on mirrored traffic without showing users, and compare outputs with an LLM judge before ramping.
