Design a ride-hailing service like Uber.

Classic Design Problems · design · levels mid, senior, lead

In one line

Ride-hailing combines high-frequency driver location updates in an in-memory geospatial index, a matching service that finds and offers nearby drivers with strongly consistent assignment, a trip state machine, and real-time updates over WebSockets/push.

Detailed explanation

With ~1M active drivers each sending a location every 4 seconds, that's ~250,000 writes/s, mostly overwriting the previous position. A relational DB is the wrong tool; an in-memory structure partitioned by city/region is right (Redis GEO, or custom services on geohash/H3 cells, as Uber does).

Finding nearby drivers means looking up the rider's cell and neighbouring cells, then ranking candidates by ETA (road network, not straight-line distance), rating, vehicle type. Assignment is the consistency-critical step: a driver must never get two trips, so use a conditional update or short lock on the driver's state (AVAILABLE → OFFERED).

Trips are a state machine persisted durably: requested → driver assigned → arriving → in progress → completed → paid. Pricing (including surge), ETA, maps, payments and notifications are separate services.

How it works

  1. Driver app → location service (via gateway) every few seconds → geo index (latest position) + Kafka (history, analytics).
  2. Rider requests → matching service queries geo index for nearby available drivers.
  3. Offer to best driver with timeout; on accept, atomically set driver busy and trip assigned.
  4. Both apps subscribe to trip updates via WebSocket; driver location relayed to rider.
  5. Trip end → pricing → payment → receipts.

Example

SET driver:123 state AVAILABLE -> OFFERED  IF state == AVAILABLE   (compare-and-set)
GEOSEARCH drivers:blr FROMLONLAT 77.59 12.97 BYRADIUS 3 km ASC COUNT 20

Common mistakes

  • Storing every location update in a relational DB.
  • Matching by straight-line distance only.
  • Non-atomic assignment leading to double booking.
  • One global geo index instead of partitioning by region.

How to answer in the interview

"Drivers stream locations into an in-memory geospatial index partitioned by city, with history going to Kafka. Matching looks up nearby cells, ranks drivers by ETA, and offers the trip; assignment is a compare-and-set on driver state so a driver can't be double booked. Trips are a persisted state machine, both apps get live updates over WebSockets, and pricing, ETA and payments are separate services."

Likely follow-up questions

  • Demand spike after a concert? Surge pricing, batching requests, widening search radius, pre-positioning drivers.
  • Why H3 hexagons? Uniform neighbour distances and easy multi-resolution aggregation.
  • What if the driver's app disconnects mid-trip? Trip state is server-side; resume on reconnect, buffer GPS on device.
