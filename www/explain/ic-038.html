How do you share values between separate Terraform configurations?

Infrastructure as Code · concept · levels mid

In one line

Share values between stacks with terraform_remote_state (simple but needs read access to the whole state and couples tightly), data sources that look up resources by tags/names, or a parameter store (SSM, Consul) acting as an explicit contract.

Detailed explanation

Large estates are split into several states: network, shared platform, data stores, applications. Consumers need values from producers, such as VPC and subnet IDs, a cluster name or a DNS zone ID.

terraform_remote_state reads the outputs of another state from its backend. It's simple and exact. The drawbacks: the consumer needs read access to the entire state file, which may contain secrets, not just the outputs; it couples the consumer to the producer's backend location and output names; and refactoring the producer can break consumers silently.

Data sources query the cloud directly: data "aws_vpc" "shared" { tags = { network = "shared" } }, aws_subnets filtered by tags, aws_route53_zone by name. The consumer depends on real infrastructure and tag conventions, not on another team's Terraform layout, and needs only read API permissions. They require consistent tagging and fail if the lookup finds zero or several matches.

Parameter stores make the contract explicit: the producer writes values to SSM Parameter Store paths like /platform/network/prod/vpc_id, Consul KV, Azure App Configuration or similar, and consumers read them with data sources. Access can be granted per path, values are usable by non-Terraform tools as well, and the paths form a documented API between teams.

The general principle is loose coupling with narrow permissions: consumers should depend on a small, stable interface, not on the producer's internals. In HCP Terraform, workspaces can share outputs with selected workspaces, and the tfe_outputs data source reads outputs without full state access. Terragrunt dependency blocks are another option in Terragrunt setups.

How it works

  1. Producer creates resources and exposes values (outputs, tags or parameters).
  2. Consumer reads them during plan via a data source.
  3. Values feed consumer resources like any other attribute.
  4. Changes in the producer propagate on the consumer's next plan.

Example

# Option 1: remote state
data "terraform_remote_state" "network" {
  backend = "s3"
  config = {
    bucket = "acme-tfstate-prod"
    key    = "network/terraform.tfstate"
    region = "eu-west-1"
  }
}
# subnet_ids = data.terraform_remote_state.network.outputs.private_subnet_ids

# Option 2: tag lookup
data "aws_vpc" "shared" {
  tags = { network = "shared", env = "prod" }
}

# Option 3: parameter store contract (producer)
resource "aws_ssm_parameter" "vpc_id" {
  name  = "/platform/network/prod/vpc_id"
  type  = "String"
  value = aws_vpc.main.id
}
# consumer
data "aws_ssm_parameter" "vpc_id" {
  name = "/platform/network/prod/vpc_id"
}

Common mistakes

  • Granting every app pipeline read access to the network state with its secrets.
  • Tag lookups without unique tags, matching several resources.
  • Renaming outputs without coordinating with consumers.
  • Circular dependencies between stacks.

How to answer in the interview

"When the estate is split into network, platform and app states, they need values from each other, like subnet IDs. terraform_remote_state reads another state's outputs directly; it's simple, but the consumer needs read access to that whole state, which can contain secrets, and it couples them tightly. Alternatives are data sources looking resources up by tags or names, like the VPC tagged network=shared, or having the producer publish values to SSM Parameter Store or Consul as an explicit contract. Those keep stacks loosely coupled and permissions narrow."

Likely follow-up questions

  • What happens to consumers if the producer renames an output? Their next plan fails with an unsupported attribute error; treat outputs as an API and deprecate gradually.
  • How do you avoid exposing secrets via remote state? Use parameter stores or tfe_outputs, and keep secrets out of shared outputs.
  • Does reading another state create ordering? Only at plan time; there's no automatic cross-stack apply ordering.
