How does class loading work in the JVM? Explain the delegation model.

JVM & Performance · concept · levels mid, senior

In one line

Class loading has three phases, loading, linking (verify, prepare, resolve) and initialisation, performed by a hierarchy of bootstrap, platform and application class loaders that use parent-first delegation, so core classes cannot be replaced; problems show up as ClassNotFoundException, NoClassDefFoundError and jar version conflicts.

Detailed explanation

Loading. When a class is first needed, a class loader finds its bytes (from a jar, the module image, the network, or generated in memory) and creates a Class object plus its metadata in Metaspace. A class is identified by its name plus its defining loader, so the same class name loaded by two loaders gives two distinct, incompatible types.

Linking. Verification checks the bytecode is structurally valid and type-safe. Preparation allocates static fields and sets them to default values (0, null, false). Resolution turns symbolic references in the constant pool into direct references; HotSpot does this lazily on first use.

Initialisation. Runs static initialisers and static field assignments (<clinit>), exactly once, thread-safely, triggered on first active use: creating an instance, calling a static method, accessing a non-constant static field, or reflection. This guarantee is why the holder-class idiom gives lazy, thread-safe singletons.

Loader hierarchy (Java 9+). The bootstrap loader (native, shown as null) loads core modules like java.base. The platform class loader loads other Java SE and JDK modules (it replaced the old extension loader). The application (system) class loader loads your classpath and module path. Frameworks add their own loaders.

Parent delegation. A loader first delegates to its parent; only if the parent cannot find the class does it search itself. This keeps a single version of java.lang.String, prevents spoofing core classes and avoids duplicates.

Typical problems. ClassNotFoundException is a checked exception from explicit loading (Class.forName, loadClass) when the class is not found. NoClassDefFoundError is an error when a class present at compile time is missing at runtime, or when its static initialiser previously failed (after an ExceptionInInitializerError). Version conflicts (two versions of Jackson or Guava) give NoSuchMethodError or ClassCastException such as "X cannot be cast to X" across loaders.

How it works

  1. Code references class A for the first time.
  2. The application loader delegates to platform, which delegates to bootstrap.
  3. Parents cannot find it; the application loader reads A.class from the classpath.
  4. The JVM verifies and prepares A, resolving references lazily.
  5. On first active use, A's static initialiser runs once.

Example

System.out.println(String.class.getClassLoader());        // null (bootstrap)
System.out.println(java.sql.Driver.class.getClassLoader()); // platform loader
System.out.println(MyService.class.getClassLoader());     // app loader

class Config {
    static final Map<String,String> VALUES = load(); // fails -> ExceptionInInitializerError,
}                                                     // later uses -> NoClassDefFoundError
java -Xlog:class+load=info -jar app.jar | grep Jackson   # which jar a class came from
mvn dependency:tree -Dincludes=com.fasterxml.jackson.core # find version conflicts

Common mistakes

  • Thinking verification and static initialisation happen at load time together.
  • Confusing ClassNotFoundException with NoClassDefFoundError.
  • Naming the Java 8 extension loader for modern JDKs.
  • Ignoring the root ExceptionInInitializerError behind a NoClassDefFoundError.

How to answer in the interview

"Class loading has three phases: loading the bytecode, linking, which verifies it, prepares static fields with default values and resolves symbolic references, and initialisation, which runs static initialisers once on first active use. There's a hierarchy of loaders: bootstrap for core classes, the platform loader for other JDK modules, and the application loader for the classpath. They use parent delegation: a loader asks its parent first, so core classes cannot be replaced and there is one copy of them. Typical problems are ClassNotFoundException when explicit loading by name fails, NoClassDefFoundError when a class was there at compile time but is missing at runtime or its static initialiser failed, and version conflicts between jars that cause NoSuchMethodError."

Likely follow-up questions

  • How do application servers or plugins break the parent-first rule, and why? Web containers use child-first loaders so each application can ship its own library versions; core java.* classes still go to the parent.
  • What is the thread context class loader? A per-thread loader that frameworks like JDBC's ServiceLoader use to find classes in application code.
  • Can two classes with the same name coexist? Yes, if loaded by different loaders; they are different types.
