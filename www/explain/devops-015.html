What is the difference between a Docker image and a container?

Docker · concept · levels entry

In one line

An image is a read-only, layered template (built from a Dockerfile, stored in a registry), while a container is a running instance of that image with a thin writable layer, its own namespaces and cgroup limits.

Detailed explanation

Think of the image as a class and the container as an object, or the image as a recipe and the container as the dish.

An image packages the application, its runtime, libraries and filesystem plus metadata (default command, environment, exposed ports, user). It is built from a Dockerfile; each filesystem-changing instruction (RUN, COPY, ADD) creates a layer, a content-addressed diff. Layers are shared between images and cached, so pulling a new version only downloads changed layers. Images are identified by digest (sha256:…, immutable) and labelled with tags (myapp:1.4.2, mutable), and stored in registries like Docker Hub, Amazon ECR, GHCR or Harbor. Images follow the OCI image spec, so they work with Docker, containerd, Podman and Kubernetes.

A container is created from an image. The runtime stacks the image's read-only layers using a union filesystem (overlayfs) and adds a writable container layer on top; writes use copy-on-write. It then starts the configured process inside Linux namespaces (its own PID tree, network stack, mount table, hostname) and cgroups that limit CPU and memory. Many containers can run from one image simultaneously, each with its own writable layer.

When a container is removed, its writable layer is deleted. Anything that must survive goes into volumes or external storage, which is why containers are treated as immutable and disposable: to change software you build a new image and replace the container, rather than patching a running one.

How it works

  1. docker build executes the Dockerfile, producing layers and an image config.
  2. docker push uploads layers and manifest to a registry.
  3. docker run pulls missing layers, creates the writable layer, sets up namespaces and cgroups, starts the process.
  4. docker rm deletes the container and its writable layer; the image remains.

Example

docker build -t shop-api:1.4.2 .
docker image ls shop-api
docker image history shop-api:1.4.2        # see layers
docker run -d --name api1 -p 8080:8080 shop-api:1.4.2
docker run -d --name api2 -p 8081:8080 shop-api:1.4.2   # same image, second container
docker diff api1                            # changes in api1's writable layer
docker rm -f api1                           # its writable layer is gone

Common mistakes

  • Making changes inside a running container and expecting them to persist.
  • Deploying mutable tags like latest instead of versions or digests.
  • Saying an image "contains an OS kernel" (it contains userland only).
  • Storing database data in the writable layer.

How to answer in the interview

"An image is a read-only template with the application, its dependencies and filesystem, built from a Dockerfile as a stack of cached layers and stored in a registry with tags and immutable digests. A container is a running instance of an image: Docker adds a thin writable layer and runs the process in isolated namespaces with cgroup limits. I can run many containers from one image. Changes in a container are lost when it's removed unless they're in a volume, which is why we treat containers as disposable and rebuild images to change anything."

Likely follow-up questions

  • Why treat containers as immutable? Reproducibility, easy rollback, no configuration drift.
  • Tag vs digest? Tags can move; digests identify exact content.
  • What is a dangling image? An untagged image left behind by a rebuild.
