How do you implement a blue-green deployment on Kubernetes without a service mesh?

Kubernetes · design · levels mid, senior

In one line

Run two Deployments (blue and green) distinguished by a version label, test green through a preview Service, then switch the production Service selector to green for a near-instant cutover; rollback is switching back while blue still runs. Costs are double capacity and backward-compatible database changes; Argo Rollouts automates it.

Detailed explanation

Blue-green keeps the old and new versions fully running side by side, so the cutover is a routing change rather than a gradual replacement. Without a mesh, the routing switch is the Service selector: a Service with selector: {app: shop, version: blue} sends traffic to blue pods; patching it to version: green makes the EndpointSlice controller swap the endpoints within seconds.

Before switching, green is deployed at full size and tested through a preview Service (and maybe a separate ingress host like preview.shop.example.com) with smoke tests, synthetic transactions or internal users. Because blue is untouched, rollback is the same patch in reverse and takes seconds. After a soak period with healthy metrics, blue is scaled down (or kept at zero replicas as the next deploy target).

Trade-offs: you need double capacity during the switch, which the cluster autoscaler can provide temporarily. Both versions must work with the same database schema, so migrations follow the expand and contract pattern: add new columns or tables first in a compatible way, switch code, remove old structures in a later release. Background workers and queue consumers in both colours may process the same messages, so they need care. Cutover is all-at-once, so it is less gradual than a canary.

Connections: changing the selector affects new connections. Existing keep-alive connections, gRPC streams or WebSockets may stay on blue pods until they close, which is another reason to keep blue running for a while and to use connection draining.

Argo Rollouts implements this as a BlueGreen strategy: it manages active and preview Services, can run AnalysisTemplates against Prometheus before promotion, supports auto-promotion and scales down the old version after a delay.

How it works

  1. Blue Deployment serves; Service selects version: blue.
  2. Deploy green Deployment with version: green.
  3. Preview Service selects green; run tests.
  4. Patch the production Service selector to green.
  5. Monitor; rollback by patching back if needed.
  6. Scale down blue after soak.

Example

kubectl apply -f shop-green-deployment.yaml          # labels: app=shop, version=green
kubectl rollout status deploy/shop-green
curl -fsS https://preview.shop.example.com/healthz && ./smoke-tests.sh preview
kubectl patch svc shop -p '{"spec":{"selector":{"app":"shop","version":"green"}}}'
# rollback
kubectl patch svc shop -p '{"spec":{"selector":{"app":"shop","version":"blue"}}}'
# Argo Rollouts equivalent
strategy:
  blueGreen:
    activeService: shop
    previewService: shop-preview
    autoPromotionEnabled: false
    scaleDownDelaySeconds: 600

Common mistakes

  • Incompatible schema migrations that break blue during rollback.
  • Scaling blue down immediately, removing the fast rollback.
  • Forgetting long-lived connections stay on blue.
  • Not testing green at production size.

How to answer in the interview

"I run two Deployments, blue with the current version and green with the new one, distinguished by a version label. The production Service selects blue. I deploy green alongside and test it through a preview Service. When it's good, I patch the production Service selector to green, which moves new traffic almost instantly, and rollback is just switching back while blue still runs. After a soak, blue scales down. The costs are double capacity during the switch and backward-compatible database changes using expand and contract. Argo Rollouts automates this with preview services and automated analysis."

Likely follow-up questions

  • Long-lived connections when you flip? They stay on blue until closed; keep blue up and drain or set max connection age.
  • Blue-green vs canary? Blue-green switches all at once with instant rollback; canary shifts gradually and limits blast radius.
  • What about queue consumers? Pause blue consumers at cutover or make processing idempotent.
