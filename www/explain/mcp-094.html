How do you keep the cost and token usage of MCP-heavy agents under control?

MCP Servers · concept · levels mid, senior

In one line

Tokens in MCP-heavy agents come from tool definitions on every turn, tool results that accumulate in context, and the number of steps; control them by loading tools on demand, returning compact results, setting step and token budgets, using prompt caching, and measuring tokens per tool and task.

Detailed explanation

Every model call sends the full conversation: system prompt, all tool definitions and every earlier message, including tool results. A host connected to ten servers with a hundred tools may send tens of thousands of tokens of definitions before the user has typed anything. A single tool that returns a 20,000-token JSON blob does not cost 20,000 tokens once; it costs that on every later step because it stays in the context, and it also degrades the model's focus.

So start by measuring: tokens per task, per step, per tool definition and per tool result. Usually one of three things dominates. Definitions are cut by enabling only the servers relevant to a task, filtering tools per agent role, writing concise descriptions and using tool search or deferred loading so the model sees only a small index until it needs a tool. Results are cut at the source: filtered fields, summaries instead of raw dumps, pagination, and resource links to large content rather than inline payloads. Hosts can also trim or summarise old tool results (context editing or compaction).

Steps are reduced by better tool design (one get_order_summary instead of five calls), and capped by step limits and per-run token budgets, so a confused agent stops instead of looping. Finally, prompt caching of stable prefixes such as instructions and tool definitions cuts both cost and latency, as long as the prefix stays byte-identical between calls.

How it works

  1. Instrument the host to log input/output tokens per step and attribute them to definitions and to each tool's results.
  2. Scope servers and tools per task or agent; defer rarely used tools behind tool search.
  3. Redesign heavy tools to return filtered, paginated, compact output or resource links.
  4. Trim or summarise stale tool results in long sessions.
  5. Enable prompt caching; keep tool order and instructions stable.
  6. Enforce max steps and token budgets; alert on outliers.

Example

agent: incident-triage
servers: [observability, tickets]      # not all 12 company servers
tool_loading: on_demand                # tool search for the rest
limits:
  max_steps: 15
  max_tokens_per_run: 150000
context:
  trim_tool_results_older_than_steps: 5
tool_defaults:
  max_result_tokens: 2000              # larger output returned as a resource link

Common mistakes

  • Connecting every server to every agent "just in case".
  • Tools returning raw API responses with hundreds of unused fields.
  • Optimising prompts without measuring where tokens actually go.
  • Breaking the prompt cache by reordering tools or injecting timestamps into the prefix.
  • No step limit, so retries loop until the budget is gone.

How to answer in the interview

"I look at three sources of tokens: tool definitions sent every turn, tool results that stay in the context, and the number of steps. First I measure tokens per task and per tool to find what dominates. Then I scope servers per task and load tools on demand, make tools return compact, paginated output or resource links, and trim old results. I cap runs with step limits and token budgets, and use prompt caching for stable prefixes like instructions and tool definitions. That usually cuts cost substantially without hurting quality."

Likely follow-up questions

  • Why does result size cost on every later step? The whole context is resent on each model call, so a big result is paid for repeatedly until it is trimmed.
  • Does fewer tools hurt capability? Not if loading is on demand; fewer visible tools often improves tool selection.
  • How do you set a budget? From measured p95 token usage per task type plus headroom, with alerts when exceeded.
