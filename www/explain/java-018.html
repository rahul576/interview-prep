How do you compose asynchronous work with CompletableFuture, and what pitfalls do you watch for?

Concurrency · concept · levels senior, lead

In one line

Use thenApply to transform a result and thenCompose to chain a call that itself returns a future (flatMap); combine with thenCombine/allOf, handle errors with exceptionally/handle/whenComplete, run blocking I/O on a dedicated executor instead of the common pool, and add timeouts with orTimeout/completeOnTimeout.

Detailed explanation

CompletableFuture<T> is both a Future and a CompletionStage: you attach callbacks that run when the value is ready, building a non-blocking pipeline.

Transforming vs chaining. thenApply(fn) maps T → U (like map). thenCompose(fn) takes T → CompletableFuture<U> and flattens it (like flatMap); using thenApply there would give a nested CompletableFuture<CompletableFuture<U>>. thenAccept and thenRun consume without producing.

Combining. a.thenCombine(b, (x, y) -> ...) runs when both independent futures finish. allOf(f1, f2, f3) returns CompletableFuture<Void> that completes when all do; then join each (they are done, so no blocking). anyOf completes with the first result.

Errors. An exception skips subsequent stages until a handler. exceptionally(ex -> fallback) recovers; handle((v, ex) -> ...) sees both outcomes and returns a new value; whenComplete observes for logging without changing the result. Exceptions arrive wrapped in CompletionException, so unwrap getCause(). Java 12 added exceptionallyCompose for async fallbacks.

Threads. Methods without Async run on whichever thread completes the previous stage (or the caller if already complete). The *Async variants without an executor use ForkJoinPool.commonPool(), sized to cores minus one and shared JVM-wide with parallel streams. Blocking JDBC or HTTP calls there starve everything else, so pass a dedicated executor, today often Executors.newVirtualThreadPerTaskExecutor().

Timeouts and cancellation. Java 9 added orTimeout(d, unit) (fails with TimeoutException) and completeOnTimeout(value, d, unit) (fallback). Note that cancel(true) does not interrupt the underlying task. Avoid join()/get() on request threads in reactive code; return the future instead.

How it works

  1. Start stages with supplyAsync(supplier, executor).
  2. Chain with thenApply/thenCompose.
  3. Fan out and join with thenCombine/allOf.
  4. Attach timeouts and error handlers.
  5. Return or join at the boundary.

Example

ExecutorService io = Executors.newVirtualThreadPerTaskExecutor();

CompletableFuture<User> user = CompletableFuture
        .supplyAsync(() -> userClient.find(id), io);
CompletableFuture<List<Order>> orders = user
        .thenCompose(u -> CompletableFuture.supplyAsync(() -> orderClient.byUser(u.id()), io));
CompletableFuture<Prefs> prefs = CompletableFuture
        .supplyAsync(() -> prefsClient.get(id), io)
        .completeOnTimeout(Prefs.DEFAULT, 300, MILLISECONDS);

CompletableFuture<Dashboard> dash = orders
        .thenCombine(prefs, (o, p) -> new Dashboard(user.join(), o, p))
        .orTimeout(2, SECONDS)
        .exceptionally(ex -> Dashboard.degraded(ex.getCause()));

Common mistakes

  • Using thenApply with a function returning a future (nested futures).
  • Blocking I/O on the common pool.
  • Swallowing exceptions by never attaching a handler or joining.
  • Expecting cancel(true) to stop the running work.

How to answer in the interview

"thenApply transforms a result, while thenCompose flattens a function that itself returns a CompletableFuture, like flatMap. For independent calls I use thenCombine for two futures or allOf for many and then join the completed results. For errors I use exceptionally for a fallback, or handle and whenComplete to see both result and exception. The big pitfall is that async methods default to the ForkJoinPool common pool, so for blocking I/O I pass a dedicated executor. I add timeouts with orTimeout or completeOnTimeout, and avoid calling join on request threads."

Likely follow-up questions

  • With virtual threads, still CompletableFuture? Often simple blocking code on virtual threads is clearer; CompletableFuture still helps for fan-out composition and existing async APIs, and structured concurrency is the emerging alternative.
  • Why are exceptions wrapped? Stages wrap failures in CompletionException; unwrap the cause.
  • Which thread runs thenApply? The thread that completed the previous stage, or the caller if already done.
