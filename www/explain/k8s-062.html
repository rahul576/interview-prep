Users get 502 Bad Gateway from the ingress during every deployment. How do you fix it?

Kubernetes · scenario · levels mid, senior

In one line

It is the termination race: the pod receives SIGTERM at the same time its endpoint is removed, but the ingress or load balancer learns of the change later and keeps sending requests; fix it with a preStop sleep, graceful SIGTERM handling, proper readiness probes and keep-alive timeouts where the app outlives the proxy.

Detailed explanation

When a pod is deleted, two things happen in parallel, not in sequence. The kubelet runs the preStop hook and then sends SIGTERM to the container. Meanwhile the EndpointSlice controller marks the endpoint as terminating, and every consumer (kube-proxy on each node, the ingress controller, a cloud load balancer's target group, a service mesh) must notice and update its routing. That propagation takes from hundreds of milliseconds to several seconds, longer for cloud load balancers. If the app exits immediately on SIGTERM, requests still being routed to it get connection refused, which the proxy reports as 502.

The fix is to keep serving until everyone has stopped sending. A preStop hook that sleeps 5-15 seconds delays SIGTERM, giving routing time to converge (since Kubernetes 1.30 there is a native sleep action, so no shell is needed in the image). Then the app should handle SIGTERM gracefully: stop accepting new connections, finish in-flight requests, close keep-alive connections, and exit. terminationGracePeriodSeconds must exceed the preStop sleep plus drain time. For cloud load balancers, configure deregistration delay or connection draining to match.

On the new pod side, a correct readiness probe ensures traffic is sent only once the app can actually serve, not when the process just started. A third, separate cause is keep-alive mismatch: if the app's idle timeout is shorter than the proxy's, the app closes an idle connection just as the proxy reuses it, and that request fails with 502. The app's idle timeout should be longer than the proxy's.

How it works

  1. Pod deletion starts preStop and endpoint removal together.
  2. preStop sleep keeps the pod serving while proxies update.
  3. SIGTERM arrives; the app stops accepting, drains and exits.
  4. Grace period covers sleep plus drain, then SIGKILL if needed.
  5. New pods only receive traffic after readiness passes.
  6. Keep-alive timeouts: app idle timeout longer than proxy's.

Example

spec:
  terminationGracePeriodSeconds: 45
  containers:
    - name: web
      image: registry.example.com/web:5.1
      lifecycle:
        preStop:
          sleep: { seconds: 10 }
      readinessProbe:
        httpGet: { path: /ready, port: 8080 }
        periodSeconds: 5
        failureThreshold: 2

Common mistakes

  • Relying on readiness failure during shutdown to remove the pod (endpoint removal already started).
  • Shell-based preStop sleep in distroless images with no shell.
  • Grace period shorter than preStop plus drain.
  • App idle timeout shorter than the ingress keep-alive.

How to answer in the interview

"502s on every rollout are almost always the termination race. When an old pod is deleted, SIGTERM and endpoint removal happen at the same time, and the ingress controller or cloud load balancer only learns about it a bit later, so it keeps sending requests to a pod that already stopped. I add a preStop sleep of a few seconds, make the app handle SIGTERM by draining in-flight requests, and set the grace period long enough. New pods need a real readiness probe. I also check keep-alive timeouts, because if the app closes idle connections before the proxy does, the proxy reuses a dead connection and returns 502."

Likely follow-up questions

  • How do you verify the fix? Run a load test (k6, vegeta) during a rollout and assert zero 5xx.
  • Why not just make readiness fail on SIGTERM? Endpoint removal is already in progress; the issue is propagation delay, not detection.
  • Does a service mesh help? It can retry idempotent requests, but graceful shutdown is still needed.
