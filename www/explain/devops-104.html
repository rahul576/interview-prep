Explain the structure of a GitLab CI pipeline.

CI/CD Tools · concept · levels entry, mid

In one line

A GitLab CI pipeline is defined in .gitlab-ci.yml at the root of the repository: stages run in order, jobs inside a stage run in parallel on runners, and rules, needs, artifacts, cache and environments control when jobs run, what they share and where they deploy.

Detailed explanation

Every push, merge request, tag or schedule can create a pipeline. Stages (for example build, test, deploy) define the default order: all jobs in one stage finish before the next starts. Jobs are the units of work: a script, an optional image, and settings such as rules and artifacts. Jobs in the same stage run in parallel.

Jobs run on GitLab Runner, self-hosted or GitLab-hosted. Each runner uses an executor: docker (a fresh container per job), kubernetes (a pod per job) or shell. Tags route jobs to specific runners, such as GPU or ARM machines.

needs turns the pipeline into a DAG: a job starts as soon as the jobs it needs finish, regardless of stage. rules (replacing only/except) decide whether a job is added: only on the default branch, for merge requests, when paths change, or when: manual.

Artifacts are job outputs passed reliably to later jobs and downloadable; cache is a best-effort speed-up for dependencies like node_modules, reused between pipelines. Environments record deployments and, with protected environments and manual jobs, provide approvals. include, extends and CI/CD components keep configuration reusable.

How it works

  1. A trigger creates a pipeline; GitLab evaluates rules to decide which jobs exist.
  2. A runner with matching tags picks up each queued job.
  3. The executor starts a clean container, fetches the repo, restores cache and artifacts.
  4. The script runs; exit code 0 means success.
  5. Artifacts and cache are uploaded; dependent jobs start.
  6. Deploy jobs record an environment and may wait for approval.

Example

stages: [build, test, deploy]

default:
  image: node:22

build:
  stage: build
  script: [npm ci, npm run build]
  cache:
    key: { files: [package-lock.json] }
    paths: [node_modules/]
  artifacts:
    paths: [dist/]
    expire_in: 1 week

unit-tests:
  stage: test
  needs: [build]
  script: [npm test]

deploy-prod:
  stage: deploy
  needs: [build, unit-tests]
  script: [./deploy.sh dist/]
  environment: { name: production, url: https://app.example.com }
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
      when: manual

Common mistakes

  • Using cache to pass build outputs between jobs; that is what artifacts are for.
  • Mixing rules with only/except in the same job.
  • Strict stages everywhere when needs would save minutes.
  • Copy-pasting YAML into every repo instead of include or components.

How to answer in the interview

"The pipeline lives in .gitlab-ci.yml. Stages like build, test and deploy run in order, and jobs in a stage run in parallel on GitLab runners, usually with the Docker or Kubernetes executor. rules control when jobs run, for example deploy only from main, and needs builds a DAG so jobs start as soon as their dependencies finish. Artifacts pass build outputs between jobs, cache speeds up installs, and environments track deployments with a protected manual job for production. Shared logic comes in through include or CI/CD components."

Likely follow-up questions

  • What is the difference between cache and artifacts? Artifacts reliably pass outputs between jobs; cache is an optional speed-up for dependencies.
  • What is a parent-child pipeline? A job triggers a separate pipeline from another YAML file, useful for monorepos or generated configs.
  • How do you protect production deployments? Protected branches and environments, required approvers, and protected, masked variables.
