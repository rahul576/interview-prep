Users get 502 and 504 errors from an Application Load Balancer. How do you investigate?

Cloud (AWS) · scenario · levels senior

In one line

502 Bad Gateway means the ALB got an invalid or no response from the target (crash, connection reset, malformed response, TLS or protocol mismatch, often a keep-alive shorter than the ALB idle timeout), while 504 Gateway Timeout means the target did not respond in time; investigate with ALB access logs, CloudWatch target metrics and application logs.

Detailed explanation

First check whether the errors come from the ALB or the app. HTTPCode_ELB_5XX_Count (split into ELB 502, 503 and 504) means the load balancer generated the error, while HTTPCode_Target_5XX_Count means your application returned it. A 503 from the ALB usually means no healthy targets in the group.

502 causes: the target closed or reset the connection (process crash, OOM kill, restart), returned a malformed HTTP response or headers too large, the target group protocol mismatches the app (HTTPS target group to an HTTP port, or vice versa), a TLS handshake failed, or a Lambda target returned an invalid response format. The classic intermittent cause: the app server's keep-alive timeout is shorter than the ALB idle timeout (default 60 seconds), so the server closes an idle connection exactly as the ALB reuses it. Fix by setting the server keep-alive longer, for example 65 seconds in Node.js or Gunicorn. During deployments, 502s appear when targets are killed before deregistration finishes or without graceful shutdown.

504 causes: the target accepted the connection but did not send a response within the idle timeout, usually due to a slow database or downstream API, thread or connection pool exhaustion, or long-running requests that should be asynchronous. It can also happen when security groups or NACLs block traffic so the connection never completes.

ALB access logs (to S3, query with Athena) show per request: target IP, request_processing_time, target_processing_time, response_processing_time, ELB and target status codes and error_reason. A target time of -1 means the target did not respond. CloudWatch TargetResponseTime, HealthyHostCount, TargetConnectionErrorCount and per-AZ views narrow it to a target, AZ or time window, then correlate with app logs and traces.

How it works

  1. Split ELB versus target 5xx in CloudWatch.
  2. Query access logs for failing requests, targets and timings.
  3. 502: check crashes, restarts, keep-alive, protocol and TLS settings.
  4. 504: check downstream latency, thread pools and timeouts.
  5. Check health checks, healthy host count and capacity.
  6. Fix and confirm metrics return to baseline.

Example

SELECT target_ip, elb_status_code, target_status_code,
       target_processing_time, error_reason, count(*) AS n
FROM alb_logs
WHERE day = '2026/11/20' AND elb_status_code IN (502, 504)
GROUP BY 1,2,3,4,5 ORDER BY n DESC LIMIT 20;
// Node.js: keep-alive longer than ALB idle timeout (60s)
const server = app.listen(8080);
server.keepAliveTimeout = 65000;
server.headersTimeout = 66000;

Common mistakes

  • Raising the ALB idle timeout to hide slow requests instead of fixing them.
  • Ignoring the difference between ELB-generated and target-generated 5xx.
  • No graceful shutdown, so deployments produce 502 bursts.
  • Health checks too lenient, keeping broken targets in rotation.

How to answer in the interview

"First I separate the codes. A 502 means the ALB got an invalid or no response: the app crashed, reset the connection, returned something malformed, or there is a protocol mismatch. A classic cause is the app keep-alive being shorter than the ALB idle timeout, so the server closes connections the ALB reuses; I set the server keep-alive longer. A 504 means the target did not respond within the idle timeout, usually a slow database or downstream API or exhausted threads. ALB access logs give per-request target and timings, and CloudWatch target response time, healthy hosts and target 5xx narrow it down."

Likely follow-up questions

  • Why would 502s appear only during deployments? Targets stop before draining completes or without graceful shutdown; align deregistration delay and SIGTERM handling.
  • What does a 503 from the ALB mean? No healthy registered targets in the group.
  • Should you increase the idle timeout? Only for legitimate long requests; otherwise make them asynchronous.
