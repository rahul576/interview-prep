An application gets AccessDenied when reading from S3. How do you find the cause?

Cloud (AWS) · scenario · levels senior

In one line

Confirm the actual calling principal (sts get-caller-identity, CloudTrail), then check each layer: the identity policy for the exact action and object ARN, the bucket policy for explicit denies and conditions, the KMS key policy for encrypted objects, and SCPs, RCPs, permission boundaries, VPC endpoint policies and object ownership.

Detailed explanation

Who is calling? Applications often run with a different role than you think: the node role instead of the pod's IRSA role, a missing environment variable falling back to another profile, or a stale credential. Run aws sts get-caller-identity from the same context, or find the CloudTrail event (data events must be enabled for S3 object-level calls) to see the principal and error.

Identity policy: it must allow the exact action on the correct resource. s3:GetObject applies to arn:aws:s3:::bucket/* (objects), while s3:ListBucket applies to arn:aws:s3:::bucket (the bucket). Without ListBucket, a missing object returns 403 instead of 404, which misleads debugging. Check prefixes and conditions too.

Bucket policy: look for explicit denies with conditions such as aws:SecureTransport, aws:SourceVpce (only via a specific endpoint), aws:PrincipalOrgID or IP ranges. A deny for requests not through a VPC endpoint blocks developers' laptops. Block Public Access does not affect authenticated access, but access points may have their own policies.

KMS: for SSE-KMS objects, the caller needs kms:Decrypt allowed by the key policy (and the identity policy if the key policy delegates to IAM). Cross-account it must be a customer managed key, because AWS managed keys cannot be shared. This is one of the most common hidden causes.

Other layers: SCPs and RCPs from Organizations, permission boundaries, session policies, VPC endpoint policies on the S3 gateway endpoint, and for cross-account uploads Object Ownership: with ACLs enabled, objects uploaded by another account may be owned by the uploader; setting BucketOwnerEnforced solves this. Modern AccessDenied messages often say which policy type denied the request and whether the deny was explicit, and the IAM policy simulator helps confirm.

How it works

  1. Reproduce the call and capture the full error message.
  2. Confirm the principal via get-caller-identity or CloudTrail.
  3. Check identity policy action and resource ARN.
  4. Check bucket policy, access point and endpoint policy.
  5. Check KMS key policy if encrypted.
  6. Check SCPs, boundaries and object ownership; test with the simulator.

Example

aws sts get-caller-identity
aws s3api head-object --bucket reports-prod --key 2026/11/summary.csv
# An error occurred (403) ... User: arn:aws:sts::111122223333:assumed-role/app-node/i-0abc
#   is not authorized to perform: kms:Decrypt on resource: arn:aws:kms:... because
#   no resource-based policy allows the kms:Decrypt action
aws s3api get-object-attributes --bucket reports-prod --key 2026/11/summary.csv \
  --object-attributes ObjectParts 2>/dev/null
aws iam simulate-principal-policy --policy-source-arn arn:aws:iam::111122223333:role/app \
  --action-names s3:GetObject --resource-arns arn:aws:s3:::reports-prod/2026/11/summary.csv

Common mistakes

  • Granting s3:GetObject on the bucket ARN instead of bucket/*.
  • Forgetting kms:Decrypt for SSE-KMS objects.
  • Debugging the role you expect rather than the one actually used.
  • Missing VPC endpoint conditions in the bucket policy.

How to answer in the interview

"First I confirm which identity is really calling, with get-caller-identity or the CloudTrail event, because apps often run with a different role than expected. Then I go layer by layer. The identity policy must allow s3:GetObject on the object ARN, bucket/*, not just the bucket. The bucket policy may have an explicit deny or conditions like a required VPC endpoint, TLS or org ID. If objects use a customer managed KMS key, the role needs kms:Decrypt in the key policy, a very common cause. Finally SCPs, boundaries, endpoint policies and object ownership for cross-account uploads. The error message often names the policy type."

Likely follow-up questions

  • Why does s3:ListBucket need a different ARN than GetObject? ListBucket acts on the bucket resource; GetObject acts on object resources.
  • Why do I get 403 for an object that does not exist? Without ListBucket permission, S3 hides existence by returning 403.
  • How fix cross-account object ownership? Set Object Ownership to BucketOwnerEnforced, disabling ACLs.
