Your Spring Boot service is OOMKilled in Kubernetes, but heap usage looks fine. What is going on?

Troubleshooting · scenario · levels senior, lead

In one line

The container limit covers the whole JVM process, not just the heap: Metaspace, thread stacks, direct buffers, code cache, GC structures and native libraries add up, so a heap sized too close to the limit (high MaxRAMPercentage or Xmx near the limit) gets the pod OOMKilled; diagnose with Native Memory Tracking and RSS, and leave headroom.

Detailed explanation

Kubernetes enforces resources.limits.memory via cgroups. When the process's resident memory (RSS plus page cache it owns) exceeds the limit, the kernel's OOM killer terminates it: exit code 137, reason OOMKilled. The JVM never throws OutOfMemoryError, there is no heap dump, and heap dashboards look fine because the heap is only part of the footprint.

JVM memory beyond the heap:

  • Metaspace: class metadata; large for Spring apps with many classes, proxies and dynamic generation.
  • Thread stacks: default up to 1 MB reserved per platform thread (-Xss); 400 threads can commit hundreds of MB. Virtual threads keep stacks on the heap and are much cheaper.
  • Direct (off-heap) buffers: NIO, Netty (WebFlux, gRPC, Lettuce, Kafka clients) use ByteBuffer.allocateDirect; default max is roughly the heap size unless -XX:MaxDirectMemorySize is set.
  • Code cache for JIT-compiled code, GC data structures (G1 remembered sets, card tables), symbol tables, and native libraries (compression, crypto, JNI).
  • glibc malloc arenas: multiple per-thread arenas fragment and retain memory; many threads can make RSS creep.

Sizing: the JVM is container-aware and sizes the heap from the limit. -XX:MaxRAMPercentage=75 is a common start; 90% or -Xmx equal to the limit almost guarantees OOMKills. Set requests equal to limits for memory to avoid surprises, cap direct memory and thread pools, and measure the real non-heap footprint.

Diagnosis: enable Native Memory Tracking (-XX:NativeMemoryTracking=summary), take a baseline with jcmd <pid> VM.native_memory baseline, then summary.diff later to see which category grows. Compare with container RSS (container_memory_working_set_bytes). If NMT totals stay flat while RSS grows, suspect native allocation outside the JVM's tracking: malloc fragmentation (try MALLOC_ARENA_MAX=2 or jemalloc) or a native library leak.

How it works

  1. Pod limit = 1 GiB; heap max set to 90% = ~920 MiB.
  2. Metaspace 150 MiB + threads 200 MiB + direct buffers 100 MiB + code cache 50 MiB.
  3. Total exceeds 1 GiB while the heap itself is half full.
  4. Kernel OOM killer terminates the process (exit 137).
  5. Fix: reduce heap share, cap non-heap areas, or raise the limit.

Example

resources:
  requests: { memory: "1536Mi", cpu: "1" }
  limits:   { memory: "1536Mi" }
env:
  - name: JAVA_TOOL_OPTIONS
    value: >-
      -XX:MaxRAMPercentage=70
      -XX:MaxDirectMemorySize=128m
      -XX:ReservedCodeCacheSize=128m
      -Xss512k
      -XX:NativeMemoryTracking=summary
  - name: MALLOC_ARENA_MAX
    value: "2"
jcmd 1 VM.native_memory baseline
# ...a few hours later
jcmd 1 VM.native_memory summary.diff
#  Thread (reserved=412MB +180MB, committed=412MB +180MB)  <- thread count growing

Common mistakes

  • Setting -Xmx equal to the container limit.
  • Watching only heap metrics and not container working set.
  • Unbounded thread pools creating hundreds of platform threads.
  • Assuming an OOMKill means a heap leak and analysing heap dumps that show nothing.

How to answer in the interview

"The container limit applies to the whole process, not just the heap. Besides the heap, the JVM uses Metaspace, thread stacks, around a megabyte per platform thread, direct buffers for Netty and NIO, the code cache, GC structures and native libraries. If the heap is sized too close to the limit, say Xmx equal to it or MaxRAMPercentage at 90, the total exceeds it and the kernel kills the container with exit code 137, so there's no OutOfMemoryError. I diagnose with Native Memory Tracking diffs compared to RSS, set MaxRAMPercentage around 70 to 75, cap direct memory and threads, and check malloc fragmentation with MALLOC_ARENA_MAX or jemalloc."

Likely follow-up questions

  • How to size requests and limits? Measure total RSS under peak load, add headroom, set memory request equal to limit.
  • OOMKilled vs OutOfMemoryError? The kernel kills the process for exceeding the cgroup limit; OOME is the JVM failing to allocate within its heap or another pool.
  • Do virtual threads help? Yes for stack memory, since their stacks live on the heap and grow as needed.
