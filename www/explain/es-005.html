How do you keep Elasticsearch in sync with your primary database?

Elasticsearch · design · levels mid, senior

In one line

Keep the database as the source of truth and treat Elasticsearch as a derived read model. Avoid dual writes, and stream changes with CDC (Debezium into Kafka) or a transactional outbox. Index them as idempotent upserts with external versions, and handle changes and recovery with a full reindex behind an alias swap.

Detailed explanation

The tempting approach, "write to the database, then write to Elasticsearch in the same request", is a dual write. If the second write fails, times out, or the process crashes in between, the two stores silently diverge. Retrying in the request makes latency and failure handling worse, and concurrent updates can arrive at Elasticsearch out of order.

Reliable patterns:

  • Change data capture. Debezium reads the database's transaction log (PostgreSQL WAL, MySQL binlog), publishes row changes to Kafka, and a consumer or Kafka Connect Elasticsearch sink indexes them. Every committed change is captured, with no app changes, and in commit order per key.
  • Transactional outbox. The application writes the business row and an outbox event in the same DB transaction. A relay (or CDC on the outbox table) publishes it. This gives you meaningful domain events and lets you build denormalised search documents (product + brand + stock).
  • Periodic batch sync (updated_at > last_run) is simple, but misses hard deletes and has lag.

Idempotency and ordering. Consumers get at-least-once delivery, so use the entity id as the document _id (upserts overwrite rather than duplicate). Use external versioning (version_type=external with the DB row version or the log sequence number), so Elasticsearch rejects an older event arriving after a newer one. Partition Kafka by entity id to preserve per-entity order.

Deletes. CDC emits delete events or tombstones, and the consumer issues a DELETE. Soft deletes in the DB become a filtered field or a delete in the index.

Reindexing (mapping change, new analyzer, corruption): build products_v2 from a DB snapshot or by replaying the topic, catch up with live events, then atomically switch the alias products from v1 to v2. There is no downtime, and rollback means switching back.

Monitor consumer lag and run periodic reconciliation (counts or checksums per partition).

How it works

  1. The app writes PostgreSQL (plus the outbox row) in one transaction.
  2. Debezium streams changes to the Kafka topic db.products, keyed by product id.
  3. The indexer consumes, enriches, and runs a bulk upsert with an external version.
  4. Delete events become document deletes.
  5. Searches go through the alias products.
  6. Reindex: create the new index, backfill, catch up, swap the alias, drop the old index.

Example

PUT /products_v2/_doc/42?version=1718&version_type=external
{ "name": "Trail Running Shoe", "brand": "Acme", "price": 89.0, "inStock": true }

POST /_aliases
{ "actions": [
    { "remove": { "index": "products_v1", "alias": "products" } },
    { "add":    { "index": "products_v2", "alias": "products" } } ] }

Common mistakes

  • Dual writes from the application without any reconciliation.
  • Using Elasticsearch auto-generated ids, so retries create duplicates.
  • Ignoring event ordering, so an old update overwrites a new one.
  • Forgetting deletes.
  • Pointing clients at a concrete index name instead of an alias.

How to answer in the interview

"The database stays the source of truth, and Elasticsearch is a derived read model. Instead of dual writes from the application, which silently diverge on failures, I stream changes with change data capture, Debezium into Kafka, or publish domain events through a transactional outbox. A consumer or Kafka Connect sink indexes them. Writes are idempotent upserts keyed by the entity id with external versioning, so out-of-order events can't overwrite newer data, and deletes come through as delete events. For mapping changes or recovery I reindex into a new index and switch an alias atomically, with no downtime."

Likely follow-up questions

  • Handling deletes? CDC delete events or tombstones lead to DELETE by id. Soft deletes become a filter field.
  • Joining data from several tables? Denormalise in the consumer (a Kafka Streams join) or build documents from outbox events.
  • How stale can search be? Pipeline lag plus the refresh interval, typically seconds. Monitor consumer lag.
