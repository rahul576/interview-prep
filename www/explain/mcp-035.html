How do you test an MCP server properly?

MCP Servers · concept · levels mid, senior

In one line

Test an MCP server at several levels: unit tests for tool logic, protocol tests with an in-memory SDK client, contract tests on tool names, descriptions and schemas, manual Inspector checks, model-in-the-loop evaluations on realistic tasks, and security tests for authorisation, injection and rate limits.

Detailed explanation

An MCP server has three audiences: code that calls it, the protocol, and a model that must understand it. Each needs its own tests.

Unit tests. Tool logic is plain code. Test it independently of MCP with mocked downstream APIs: correct results, validation, edge cases, error messages.

Protocol-level tests. Use the SDK's client connected to the server in memory (linked transports) or over stdio. Call tools/list, tools/call, resources/read, prompts/get and assert: tools are registered; schemas reject invalid inputs; execution failures come back as isError results with helpful text rather than protocol errors; structured output matches the declared outputSchema; pagination and notifications behave.

Contract / snapshot tests. Snapshot the tool list (names, descriptions, schemas, annotations). Any change fails the test until reviewed, because renames break host allowlists and description changes silently alter model behaviour.

Manual exploration with the Inspector for quick checks and debugging.

Evaluations with a real model. The true consumer is an LLM, so build a set of realistic tasks ("Which of Asha's orders are delayed?") with expected outcomes, run an agent with the server connected, and measure tool selection accuracy, argument correctness, number of calls, task success and token usage. Run them in CI on changes to descriptions or schemas and compare against a baseline, ideally across the models your hosts use.

Security tests. Authorisation (user A cannot access B's data or handles), unauthenticated requests rejected, Origin validation, injection-style inputs (SQL, path traversal, shell metacharacters, prompt-injection strings in returned data), oversized inputs and rate limiting.

How it works

  1. Unit tests run on every commit.
  2. In-memory protocol tests in the same suite.
  3. Contract snapshots reviewed on change.
  4. Evaluation suite runs on PRs touching tools, nightly otherwise.
  5. Security tests in CI plus periodic penetration testing for remote servers.

Example

import pytest
from mcp.shared.memory import create_connected_server_and_client_session as connect
from server import mcp

@pytest.mark.anyio
async def test_get_order_errors_are_tool_errors():
    async with connect(mcp._mcp_server) as client:
        tools = await client.list_tools()
        assert "get_order" in [t.name for t in tools.tools]
        res = await client.call_tool("get_order", {"order_no": "ORD-404"})
        assert res.isError
        assert "search_orders" in res.content[0].text      # actionable hint

def test_tool_contract(snapshot):
    assert snapshot == [t.model_dump() for t in mcp.list_tools_sync()]

Common mistakes

  • Only manual Inspector testing.
  • Never testing with a model, so descriptions are unvalidated.
  • No snapshot of the tool contract, allowing accidental renames.
  • Ignoring authorisation tests because "the host handles security".

How to answer in the interview

"I test at several levels. Tool logic gets ordinary unit tests with mocked APIs, independent of MCP. Protocol tests use the SDK client connected in memory to check tools are registered, schemas validate inputs, failures come back as isError results and structured output matches the schema. Contract tests snapshot names, descriptions and schemas, because even description changes alter model behaviour. The Inspector is for manual exploration. Since the real consumer is a model, I run evaluations: realistic tasks executed by an agent, measuring tool choice, arguments and task completion. And security tests cover authorisation, injection-style inputs and rate limits."

Likely follow-up questions

  • Detect a description change that hurt tool choice? Compare eval tool-selection accuracy against the baseline in CI.
  • How many eval tasks? Start with 20 to 50 realistic ones, growing from production failures.
  • Which models to evaluate with? The ones your target hosts actually use.
