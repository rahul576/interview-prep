How do you choose between Terraform, Pulumi, AWS CDK and Crossplane for an organisation?

Infrastructure as Code · design · levels lead

In one line

Choose by people and context: Terraform/OpenTofu for the widest provider ecosystem, multi-cloud and ops-friendly declarative HCL; Pulumi or AWS CDK for developer-heavy teams wanting general-purpose languages (CDK is AWS-only on CloudFormation); Crossplane for platform teams building Kubernetes-native self-service APIs with continuous reconciliation; weigh ecosystem, hiring, support, licensing and the cost of running two tools.

Detailed explanation

All four describe infrastructure as code, but they differ in language, state model and who they suit.

Terraform / OpenTofu. Declarative HCL, a provider for almost every cloud and SaaS product (DNS, monitoring, identity, Git hosting), state files in a backend you control, and the largest pool of experienced engineers and modules. It is the default for multi-cloud or mixed estates and for operations-heavy teams. Licensing matters: Terraform is under the BSL, OpenTofu under the MPL.

Pulumi. Real languages (TypeScript, Python, Go, C#, Java) with loops, types, packages and unit tests; it can use Terraform providers through bridging, so coverage is broad. State lives in Pulumi Cloud or a self-managed backend. It suits developer-centric teams who want infrastructure in the same language as their application, but expressive code can become hard to review if abstractions grow.

AWS CDK. TypeScript or Python constructs synthesised to CloudFormation, which holds the state and performs deployments with rollback. Excellent high-level constructs for AWS, no state backend to manage, but AWS-only and bound to CloudFormation's speed and limits.

Crossplane. Runs inside Kubernetes as controllers; cloud resources are Kubernetes objects that are continuously reconciled. Compositions let a platform team publish its own APIs (for example a PostgresInstance claim) consumed with kubectl or GitOps. Powerful for internal platforms, but requires Kubernetes expertise, and debugging controllers differs from reading a plan.

The cost of two tools is real: duplicated modules, policies, pipelines, training and on-call knowledge.

How it works

  1. List requirements: clouds and SaaS, team skills, compliance, self-service.
  2. Shortlist and build the same reference stack in each.
  3. Evaluate review experience, testing, drift handling, speed and support.
  4. Consider hiring market, licensing and existing investment.
  5. Decide a default plus allowed exceptions; document in an ADR.

Common mistakes

  • Choosing by feature list instead of team skills and ecosystem.
  • Letting every team pick its own tool.
  • Building deep custom abstractions that only one engineer understands.

How to answer in the interview

"It depends more on people and context than features. Terraform or OpenTofu has the biggest ecosystem, providers for every cloud and SaaS tool and lots of experienced engineers, so it's my default for multi-cloud or mixed estates. Pulumi and CDK use general-purpose languages, which suits developer-heavy teams wanting loops, types and tests; CDK is AWS-only and uses CloudFormation for state. Crossplane runs in Kubernetes and continuously reconciles, which fits platform teams building Kubernetes-style self-service APIs. I'd also weigh licensing, support, existing investment and the real cost of running two tools."

Likely follow-up questions

  • What does standardising on two tools cost? Duplicate modules, policies, pipelines, training and support.
  • When is Crossplane clearly better? When the platform is Kubernetes-centric and you want self-service APIs with continuous reconciliation.
  • Can Pulumi use Terraform providers? Yes, many Pulumi providers are bridged from Terraform providers.
