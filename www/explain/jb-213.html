How would you secure a public REST API?

REST & API Design · design · levels senior, lead

In one line

Secure a public API with HTTPS/TLS (plus HSTS), OAuth 2.0/OIDC with properly validated JWTs (or API keys / mTLS for partners), authorization per endpoint and per object to stop BOLA, input validation, rate limiting at a gateway/WAF, narrow CORS, safe errors, and audit logging and monitoring, guided by the OWASP API Security Top 10.

Detailed explanation

Transport. TLS 1.2+ (prefer 1.3) everywhere, HTTP redirected or refused, HSTS for browser clients. Never put secrets or tokens in URLs, where they end up in logs.

Authentication. Delegate to an identity provider using OAuth 2.0 and OpenID Connect. Clients obtain access tokens (authorization code with PKCE for apps, client credentials for machine-to-machine). The API acts as a resource server and validates every JWT: signature against the IdP's JWKS, issuer, audience, expiry and not-before, and allowed algorithms (reject none). Keep access tokens short-lived. For partners, API keys (hashed in storage, rotatable) identify the caller, ideally combined with OAuth or mTLS for strong authentication.

Authorization. Check scopes or roles per endpoint (orders:read), and, crucially, object-level authorization: user A must not read /orders/123 belonging to user B by changing the id. This Broken Object Level Authorization (BOLA) is the number one issue in the OWASP API Security Top 10. Also guard property-level access (no mass assignment of role or price from request bodies; use DTOs) and function-level access to admin endpoints.

Input and resource protection. Validate all inputs (Bean Validation, allow-lists), limit payload and page sizes, use parameterised queries, and protect against unrestricted resource consumption with rate limiting and quotas per client at an API gateway (Kong, Apigee, AWS API Gateway, Spring Cloud Gateway) and a WAF for common attacks and bot traffic.

Browser clients. Configure CORS narrowly (explicit origins, not * with credentials) and set security headers (Content-Security-Policy where relevant, X-Content-Type-Options: nosniff).

Errors, logging, operations. Return generic errors without stack traces; log security events (failed auth, authorization denials) with correlation ids, but never log tokens or personal data. Monitor for anomalies, keep an API inventory so old versions do not stay exposed, scan dependencies, and run security tests (DAST, penetration tests).

How it works

  1. Gateway terminates TLS, applies WAF rules and rate limits.
  2. Service validates the JWT (signature, iss, aud, exp).
  3. Endpoint checks scopes/roles.
  4. Business layer checks ownership of the object.
  5. Input validated; response filtered via DTOs.
  6. Security events logged and monitored.

Example

@Bean
SecurityFilterChain api(HttpSecurity http) throws Exception {
    return http
        .csrf(csrf -> csrf.disable())                       // stateless bearer-token API
        .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .authorizeHttpRequests(a -> a
            .requestMatchers(HttpMethod.GET, "/api/orders/**").hasAuthority("SCOPE_orders:read")
            .requestMatchers("/api/admin/**").hasRole("ADMIN")
            .anyRequest().authenticated())
        .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))
        .build();
}

@GetMapping("/api/orders/{id}")
OrderDto get(@PathVariable long id, @AuthenticationPrincipal Jwt jwt) {
    return repo.findByIdAndCustomerId(id, jwt.getSubject())   // object-level check
               .map(OrderDto::from)
               .orElseThrow(NotFoundException::new);           // 404, don't reveal existence
}
spring.security.oauth2.resourceserver.jwt:
  issuer-uri: https://login.shop.com/realms/shop
  audiences: orders-api

Common mistakes

  • Checking only that the token is valid, not that the user owns the object.
  • Not validating audience, so tokens for other APIs are accepted.
  • CORS * with credentials.
  • Exposing entities directly (mass assignment, data leaks).
  • No rate limiting on login or expensive endpoints.

How to answer in the interview

"I start with HTTPS everywhere and HSTS. For authentication I use OAuth 2.0 and OpenID Connect through an identity provider, and the API validates every JWT properly: signature via JWKS, issuer, audience and expiry; partners can use API keys or mTLS. Authorization is enforced per endpoint with scopes or roles and at object level, so a user can only access their own orders, which prevents BOLA, the top OWASP API risk. I validate all input, use DTOs to avoid mass assignment, limit payload sizes, and add rate limiting at the gateway and a WAF. CORS is narrow, errors never expose stack traces, and I keep audit logs and monitoring for abuse."

Likely follow-up questions

  • What is broken object level authorization, and how would you test for it? Accessing another user's object by changing an id; test with two users' tokens swapping ids, automated in integration tests.
  • JWT or opaque tokens? JWTs validate locally; opaque tokens need introspection but are easier to revoke.
  • Why disable CSRF here? Stateless bearer tokens aren't sent automatically by browsers, unlike cookies.
