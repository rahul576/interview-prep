How do you make a Spring Boot application start faster and use less memory?

Spring Boot · concept · levels mid, senior

In one line

Measure first (actuator startup endpoint), then trim starters and auto-configuration, use lazy initialisation selectively, avoid heavy startup work, use AppCDS / AOT cache or CRaC, and for the biggest gains compile to a GraalVM native image; reduce memory with heap and thread tuning and virtual threads.

Detailed explanation

Startup time matters for autoscaling, serverless, fast deployments and developer feedback; memory determines how many pods fit on a node and therefore cost.

Measure: register a BufferingApplicationStartup and read /actuator/startup, which lists startup steps with durations, or use JFR and the startup log. Often a few beans dominate: Hibernate scanning many entities, Flyway migrations, connecting to slow external systems, or cache warm-up.

Reduce work: remove unused starters, since each brings auto-configurations and classpath scanning; exclude auto-configurations you do not need; narrow component scanning; move heavy work like cache warming to ApplicationReadyEvent or a background task; consider spring.main.lazy-initialization=true for rarely used beans, but note that errors then appear on first request and the first call is slower. Running database migrations as a separate job also helps.

JVM-level startup acceleration:

  • Class Data Sharing (AppCDS): archive parsed and verified classes. Spring Boot 3.3+ supports extracting the jar and creating a CDS archive with a training run (-XX:ArchiveClassesAtExit, then -XX:SharedArchiveFile), often cutting startup by a third or more. JDK 24+ adds the AOT cache from Project Leyden (-XX:AOTCache), which goes further, and combining it with Spring AOT helps more.
  • CRaC (Coordinated Restore at Checkpoint): snapshot a warmed-up JVM and restore in milliseconds; needs a CRaC-enabled JDK and Linux, and care with open connections and secrets.
  • GraalVM native image: Spring AOT plus native compilation gives startup in tens of milliseconds and much lower RSS, at the cost of long builds, no JIT peak optimisations for long runs (PGO helps), and limits on reflection and dynamic proxies that need hints.

Memory: set heap explicitly or with -XX:MaxRAMPercentage, size thread pools sensibly or use virtual threads instead of hundreds of platform threads with their stacks, lower Tomcat max threads, choose a suitable GC (Serial for tiny containers, G1 by default), and check metaspace and direct memory with NMT.

How it works

  1. Enable startup tracking and record a baseline.
  2. Remove or defer the slowest beans and unused auto-configuration.
  3. Add a CDS or AOT cache archive in the Docker build.
  4. Evaluate native image or CRaC if startup is critical.
  5. Tune heap, threads and GC; load-test to confirm.

Example

public static void main(String[] args) {
    SpringApplication app = new SpringApplication(App.class);
    app.setApplicationStartup(new BufferingApplicationStartup(2048));   // for /actuator/startup
    app.run(args);
}
# AppCDS with Spring Boot 3.3+
java -Djarmode=tools -jar app.jar extract --destination app
java -XX:ArchiveClassesAtExit=app.jsa -Dspring.context.exit=onRefresh -jar app/app.jar
java -XX:SharedArchiveFile=app.jsa -XX:MaxRAMPercentage=75 -jar app/app.jar

# Native image with Maven
./mvnw -Pnative native:compile

Common mistakes

  • Optimising without measuring.
  • Global lazy initialisation hiding configuration errors until production traffic.
  • Assuming native images are always faster at peak throughput.
  • Container memory limits without matching heap settings, causing OOM kills.

How to answer in the interview

"First I measure with the actuator startup endpoint or startup logs to see which beans are slow. Then I remove unused starters and auto-configuration, consider lazy initialisation for rarely used beans, and move heavy work like cache warming out of startup. Class Data Sharing, which Boot 3.3 supports directly, or the newer JDK AOT cache noticeably cut startup, and CRaC can restore from a checkpoint. For the biggest gains, GraalVM native image starts in milliseconds with much less memory, at the cost of build time and reflection limits. For memory I set heap relative to the container, right-size thread pools and use virtual threads instead of large pools."

Likely follow-up questions

  • What features become harder when you compile to a native image? Reflection, dynamic proxies, runtime classpath scanning and some libraries; they need hints and testing.
  • Does lazy init reduce memory? Somewhat, for beans never used, but its main effect is startup time.
  • When is CRaC risky? When checkpoints contain secrets or open connections that must be re-established.
