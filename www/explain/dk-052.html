What is Docker Swarm, and how does it compare with Kubernetes?

Docker · concept · levels mid

In one line

Docker Swarm is the orchestration mode built into Docker Engine: managers and workers run services as replicated tasks with overlay networks, a routing mesh and docker stack deploy from Compose-style files; Kubernetes is more complex but far more extensible and is the industry standard.

Detailed explanation

With docker swarm init and docker swarm join, a group of Docker hosts becomes a cluster. Manager nodes keep cluster state in a built-in Raft store (run 3 or 5 for fault tolerance) and schedule work; worker nodes run it. You declare a service with an image and a number of replicas, and Swarm creates tasks (containers) across nodes, restarts failed ones, reschedules them when a node dies and performs rolling updates with configurable parallelism, delay and automatic rollback. Overlay networks connect services across hosts with built-in DNS and virtual-IP load balancing, and the routing mesh lets any node accept traffic on a published port and forward it to a healthy task. Swarm also has encrypted secrets and configs, and docker stack deploy -c compose.yaml deploys a whole application from a Compose file with a deploy section.

The appeal is simplicity: no separate control plane to install, a CLI developers already know, mutual TLS between nodes by default, and few moving parts.

Kubernetes has a steeper learning curve but offers much more: a rich API with custom resources and operators, Helm and GitOps tooling, horizontal and cluster autoscaling, sophisticated scheduling (affinity, taints, topology spread), network policies, admission control, service meshes, and managed offerings on every cloud (EKS, AKS, GKE). That ecosystem made it the default. Swarm is still maintained by Mirantis and Docker, but its ecosystem is small. It suits small teams with modest needs on a few hosts, edge deployments, or labs.

How it works

  1. Initialise managers; join workers with a token.
  2. Declare services and stacks; managers store desired state in Raft.
  3. The scheduler assigns tasks to nodes.
  4. Agents run containers and report status.
  5. The reconciliation loop restarts or reschedules failed tasks.

Example

docker swarm init --advertise-addr 10.0.0.10
docker swarm join-token worker
docker stack deploy -c compose.yaml shop
docker service ls
docker service update --image registry.local/api:1.5 --update-parallelism 1 shop_api
services:
  api:
    image: registry.local/api:1.4
    deploy:
      replicas: 3
      update_config: { parallelism: 1, failure_action: rollback }

Common mistakes

  • Running a single manager in production.
  • Choosing Kubernetes for one small app with no team to run it.
  • Assuming Compose features like build work in stack deploy.
  • Thinking Swarm is the same as the old standalone "Docker Swarm" product.

How to answer in the interview

"Docker Swarm is the orchestration mode built into Docker Engine. You join hosts into a swarm with managers and workers and declare services with replicas; Swarm schedules tasks, restarts failed ones, does rolling updates, load balances through the routing mesh and connects services with overlay networks, and docker stack deploy uses Compose-style files. It's very simple to run. Kubernetes is more complex but far more capable and extensible, with operators, Helm, autoscaling, policies and managed services on every cloud, so it's the industry standard. Swarm still fits small teams with simple needs on a few hosts."

Likely follow-up questions

  • When would you choose Swarm today? Small team, few hosts, simple apps, no Kubernetes skills or budget.
  • How many managers? Odd numbers, 3 or 5, for Raft quorum.
  • Alternatives for simple setups? Managed services like ECS, Cloud Run or Azure Container Apps.
