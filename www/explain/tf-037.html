Azure Policy automatically adds tags to resources, and now every Terraform plan shows tag changes. How do you handle it?

Terraform · scenario · levels mid, senior

In one line

Azure Policy with a modify effect adds tags outside Terraform, so every plan tries to remove them; the best fix is to define the same tags in Terraform so policy has nothing to do, and otherwise ignore those tag keys, after agreeing who owns which tags.

Detailed explanation

Terraform considers the tags map in code to be the complete desired set. When Azure Policy (modify or append-style effects), AWS automation or a tag-inheritance rule adds CostCenter or Owner after creation, the real resource has more tags than the code. The plan shows them being removed, an apply removes them, and the policy remediation adds them back. That loop creates noise in every plan and hides real changes.

The strongest fix is to make Terraform the source of the same tags. Put the organisation's mandatory tags in a common locals map, merge it into every resource, or on AWS use provider-level default_tags so every resource gets them automatically. Then policy finds nothing to change and acts only as a safety net for resources created outside Terraform.

When some tags are genuinely owned by the platform team (for example a tag stamped by a governance process), tell Terraform to leave them alone. Terraform supports ignoring individual map keys, such as ignore_changes = [tags["CostCenter"]], which is better than ignoring all tags. On AWS the provider also has an ignore_tags block with keys and key_prefixes, which applies across every resource. Many teams also prefer a deny or audit policy over modify: deny fails the apply with a clear message, so the code gets fixed at the source instead of being silently patched.

How it works

  1. Look at the plan to identify which keys keep reappearing.
  2. Find the policy assignment that adds them and its effect.
  3. Agree ownership: application tags in code, governance tags either in code or explicitly platform-owned.
  4. Add mandatory tags to a shared locals map or default_tags.
  5. For platform-owned keys, add per-key ignore_changes or provider ignore_tags.
  6. Confirm the plan is clean and the policy shows resources as compliant.

Example

locals {
  common_tags = {
    CostCenter  = var.cost_center
    Environment = var.environment
    Owner       = "team-orders"
  }
}

resource "azurerm_storage_account" "data" {
  name                     = "stordersprod01"
  resource_group_name      = azurerm_resource_group.main.name
  location                 = "westeurope"
  account_tier             = "Standard"
  account_replication_type = "ZRS"
  tags                     = merge(local.common_tags, { Purpose = "exports" })

  lifecycle {
    ignore_changes = [tags["PolicyStamp"]]   # set by platform policy only
  }
}

Common mistakes

  • Ignoring the whole tags attribute, so application teams can no longer manage their own tags.
  • Letting policy and Terraform fight forever and training reviewers to skim noisy plans.
  • Using different spellings or casing for the same key in code and policy.

How to answer in the interview

"The policy adds tags after creation, Terraform thinks they should not exist and removes them, then policy adds them again, so every plan is noisy. My first fix is to define those mandatory tags in Terraform itself, through a common tags local or AWS default_tags, so policy finds nothing to change and becomes a safety net. If a tag really belongs to the platform team, I ignore just that key with ignore_changes on tags with the key name, not all tags. Most importantly, I agree with the platform team which tags are owned by whom, and often prefer a deny policy so problems are fixed in code."

Likely follow-up questions

  • Why is deny sometimes better than modify? It fails fast and forces the fix in code instead of creating hidden drift.
  • What about resource group tag inheritance? Same issue; either set the tags in code or ignore the inherited keys.
  • Does default_tags show in plans? Yes, as tags_all, which includes provider default tags.
