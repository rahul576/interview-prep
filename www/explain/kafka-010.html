How would you size and operate a production Kafka cluster?

Kafka · design · levels senior, lead

In one line

Size from peak throughput, message size, replication factor and retention to get disk, network and broker count; plan partitions from consumer parallelism; spread RF 3 across AZs with min ISR 2; monitor URP, offline partitions, latency and lag; and consider managed services.

Detailed explanation

Start with the numbers. Suppose peak ingest is 100 MB/s, replication factor 3 and 7-day retention. Each byte is written three times, so cluster disk writes are 300 MB/s, and storage is 100 MB/s x 604,800 s x 3, about 181 TB, plus 30 to 40 percent headroom for growth and rebalancing. Network outbound includes replication (200 MB/s) plus every consumer group reading the data. Divide by what one broker can comfortably handle (keep disks and NICs under about 60 to 70 percent at peak) to get a broker count, then make sure the cluster still copes with one broker or one AZ down.

Partitions come from target parallelism: if one consumer handles 5 MB/s, 100 MB/s needs at least 20 partitions; round up for future growth, and keep total partitions per broker within tested limits. Use rack awareness (broker.rack set to the AZ) so the three replicas land in different zones, with min.insync.replicas=2 and acks=all.

Operations: alert on under-replicated partitions, offline partitions, active controller count, ISR shrink and expand rates, produce and fetch request latency (p99), request handler idle ratio, disk usage and consumer lag. Use quotas per client to stop noisy neighbours, Cruise Control for partition rebalancing, and automated rolling upgrades. Tiered storage (KIP-405, production-ready in 3.9) offloads older segments to object storage, which shrinks local disk needs. Managed options such as Amazon MSK, Confluent Cloud, Aiven or Azure Event Hubs (Kafka-compatible API) often cost less than the engineering time of self-running.

How it works

  1. Gather peak MB/s, message size, retention, consumer groups, RPO/RTO.
  2. Compute disk, network and broker count with headroom and N-1 tolerance.
  3. Choose partitions per topic from parallelism targets.
  4. Deploy across 3 AZs with rack awareness and KRaft controllers.
  5. Monitor, set quotas, rebalance and load test regularly.

Example

Ingest 100 MB/s, RF 3, 7 days
Disk  = 100 MB/s * 604800 s * 3 ≈ 181 TB (+35% → ~245 TB)
Brokers: 12 x 24 TB usable, 4 per AZ; each ~25 MB/s in, 50 MB/s replication out
Topic orders: 48 partitions, RF 3, min.insync.replicas=2

Common mistakes

  • Sizing for average instead of peak traffic.
  • Forgetting replication and consumer fan-out in network math.
  • No capacity to absorb a lost AZ.
  • Running self-managed Kafka without people to operate it.

How to answer in the interview

"I start from peak write throughput, message size, replication factor and retention to work out disk and network per broker, then add headroom and make sure we survive losing a broker or a zone. Partition counts come from the consumer parallelism we need. Replication factor three spread across availability zones with rack awareness and min ISR two. I monitor under-replicated and offline partitions, request latency, disk and consumer lag, and use quotas for noisy clients. Often a managed service like MSK or Confluent Cloud is cheaper overall."

Likely follow-up questions

  • What does tiered storage change? Local disk sized for hot data only; long retention lives in object storage.
  • How many partitions per broker? Stay within tested limits; KRaft raises them, but recovery time still grows.
  • How do you rebalance load? Cruise Control or reassignment tools with throttles.
