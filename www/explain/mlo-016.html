What do you monitor for a model in production?

MLOps · concept · levels mid, senior, lead

In one line

Monitor in layers: service health (latency, errors, throughput), input data quality, feature drift, prediction drift, model performance once labels arrive, business metrics, and feature freshness and pipeline lag, all sliced by important segments.

Detailed explanation

A model service can be up and fast while giving useless answers, so ordinary APM is only the first layer.

Service health: latency percentiles (p50, p95, p99), error rates, throughput, CPU, memory and GPU use, queue lengths. Data quality: missing values, schema changes, out-of-range values and default rates; a broken upstream pipeline often appears as a sudden jump in nulls or default values. Feature drift compares current input distributions with the training or a reference window (PSI, KS tests, divergences). Prediction drift compares the distribution of outputs, such as the share of high fraud scores or the predicted class mix, with a reference period; it is a fast, label-free signal.

Model performance—accuracy, precision, recall, calibration, ranking metrics—can be measured only when ground truth arrives, which may take minutes (clicks) or weeks (chargebacks). Until then you rely on proxies. Business metrics—conversion, fraud losses, manual review workload—show real impact. Freshness and lag of features and pipelines catch stale online features, which silently degrade predictions.

Everything should be segmented (region, device, customer type), because problems often hit one segment while global averages look fine. Tools include Prometheus and Grafana for service metrics, and Evidently, WhyLabs, Arize or cloud model monitors for data and model metrics.

How it works

  1. Instrument the endpoint with standard service metrics and traces.
  2. Log inputs, features, predictions and model version per request.
  3. Compute data-quality and drift statistics on a schedule against a reference.
  4. Join predictions with labels when they arrive and compute performance.
  5. Track business KPIs alongside model metrics.
  6. Alert on thresholds with owners and runbooks.

Example

Dashboard: fraud-model-v14
- Service: p99 latency 42 ms, error rate 0.02 %, RPS 1,800
- Data quality: device_id null rate 0.4 % (baseline 0.3 %)
- Feature drift (PSI): amount 0.04, merchant_category 0.21  <- investigate
- Prediction drift: share score > 0.9 = 1.8 % (baseline 1.1 %)
- Performance (labels to 45 days ago): precision 0.62, recall 0.71
- Business: fraud loss / 1k txns, manual reviews per day

Common mistakes

  • Monitoring only CPU and latency.
  • No logging of inference-time features, so drift and skew can't be analysed.
  • Only global metrics, missing segment failures.
  • Alerting on every tiny statistical drift until people ignore alerts.

How to answer in the interview

"I monitor several layers. Service health first: latency percentiles, errors and throughput. Then data quality, like nulls and default rates, because broken upstream pipelines show up there. Feature drift and prediction drift give early, label-free signals. When labels arrive I measure real performance such as precision, recall and calibration, and I track business metrics like fraud losses. I also watch feature freshness and pipeline lag, and slice everything by key segments since problems often hit one group while averages look fine."

Likely follow-up questions

  • Labels arrive after 45 days—what do you watch on day one? Data quality, prediction drift, decision rates, latency and early proxies like analyst feedback.
  • What is calibration monitoring? Checking predicted probabilities match observed frequencies.
  • Who owns model alerts? The model's owning team, with platform alerts routed to the platform team.
