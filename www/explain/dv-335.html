After a release, error rates rise slowly over several hours. How do you investigate?

Troubleshooting · scenario · levels senior, lead

In one line

Correlate the timing with the release and other changes; a slow rise over hours suggests accumulation — memory, connection or thread leaks, growing queues, filling disks — so compare old and new versions (ideally a canary), check dependencies, and roll back to protect users and confirm the hypothesis.

Detailed explanation

The shape of the graph is a clue. An error rate that jumps the minute a release goes out points to a functional bug, bad config or an incompatible dependency. A rate that climbs slowly for hours suggests something that accumulates with time or traffic:

  • A memory leak: heap after garbage collection grows, GC pauses lengthen, latency rises, and eventually pods are OOMKilled and restart, causing errors during restarts.
  • Connection or thread leaks: a code path that does not return connections to the pool; requests start waiting and timing out once the pool is exhausted.
  • Growing queues or backlogs: a consumer slower than before, so lag grows until timeouts hit.
  • Disk filling with logs or temp files, or a cache that grows without eviction.
  • Dependency effects: a new query without an index gets slower as a table grows, or a lower cache hit rate gradually overloads the database.

First I correlate: release time, config or feature flag changes, traffic patterns (is this just the daily peak?) and dependency incidents. Then I compare versions side by side. If there was a canary, I compare canary and baseline on heap after GC, open connections, thread count, restarts, p99 latency and error types. Without a canary, I compare the same hours on the previous day.

If evidence points to the release, I roll back: it protects users and also tests the hypothesis — if errors stop climbing after rollback, the release is confirmed as the cause. Then, before fixing forward, I take heap dumps, thread dumps or traces from the new version in a test environment to find the actual leak.

How it works

  1. Overlay release markers on error and latency graphs.
  2. Rule out traffic peaks and dependency incidents.
  3. Check accumulation metrics: heap after GC, connections, threads, queue lag, disk.
  4. Compare canary vs baseline, or today vs yesterday.
  5. Roll back and watch whether the trend stops.
  6. Analyse dumps or profiles and fix forward with a test.

Example

# heap used after GC trend per version
max by (version) (jvm_memory_used_bytes{area="heap"})
# pool exhaustion
max by (pod) (hikaricp_connections_pending)
# restarts
increase(kube_pod_container_status_restarts_total{container="orders"}[1h])
jcmd 1 GC.heap_dump /tmp/orders.hprof    # analyse with Eclipse MAT

Common mistakes

  • Assuming the release is innocent because the first hour looked fine.
  • Restarting pods regularly to hide a leak.
  • Fixing forward under pressure without confirming the cause.
  • Canaries that only compare error rates, not resource trends.

How to answer in the interview

"First I correlate the timing with the release and anything else that changed, like config, traffic or a dependency. A slow rise over hours rather than a jump suggests accumulation: a memory leak causing GC pressure and OOM restarts, connection or thread leaks exhausting pools, growing queues, or a disk filling with logs. I compare old and new versions, ideally canary versus baseline, on heap after GC, open connections, restarts and latency percentiles, and check database load and cache hit rate. If evidence points to the release, I roll back to protect users and confirm the hypothesis, then analyse heap dumps or traces before fixing forward."

Likely follow-up questions

  • Which metrics would you add to the canary? Heap after GC, pool usage, thread count, restarts and p99 latency, analysed over a longer window.
  • Why does a canary sometimes miss this? It runs too briefly or at too low traffic for accumulation to show.
  • How do you find a connection leak? Pool leak detection logs with stack traces, or checking code paths that skip close on exceptions.
