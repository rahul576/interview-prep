What is the difference between a private endpoint and a Private Link service?

Azure · concept · levels mid, senior, lead

In one line

A private endpoint is the consumer side: a NIC with a private IP in your VNet that maps to one specific resource; a Private Link service is the provider side: your own service behind a Standard Load Balancer, published so consumers in other VNets or tenants can create private endpoints to it, with approval, and no peering or IP overlap concerns.

Detailed explanation

Both are part of Azure Private Link. When you create a private endpoint for a storage account, Azure places a NIC in your subnet with an IP such as 10.1.2.5, and a private DNS zone (for example privatelink.blob.core.windows.net) makes the public name resolve to that IP. Traffic stays on the Microsoft backbone, and you can disable public network access on the resource. Importantly, the endpoint maps to one resource, not the whole service, which protects against data exfiltration to other storage accounts.

A Private Link service lets you be the provider. You put your application behind a Standard internal Load Balancer and create a Private Link service on its frontend. Consumers anywhere, in other subscriptions or other Entra tenants, create a private endpoint pointing at your service's alias or resource ID. The provider sees a connection request and can approve or reject it, or auto-approve listed subscriptions. Traffic is NAT'd on the provider side into a NAT IP from your subnet, which is why overlapping address spaces don't matter: consumers only see their own private endpoint IP.

Compared with VNet peering, Private Link exposes a single service, is unidirectional (only consumer to provider), and needs no routing coordination. SaaS vendors such as Snowflake or Databricks and internal platform teams use it to offer services to many networks.

How it works

  1. Provider: deploy the service behind a Standard internal Load Balancer.
  2. Provider: create a Private Link service on that LB frontend, choose NAT IPs and visibility.
  3. Consumer: create a private endpoint referencing the alias or resource ID.
  4. Provider approves the pending connection.
  5. Consumer creates DNS records pointing the service name to the endpoint IP.
  6. Consumer traffic flows endpoint → backbone → NAT → load balancer → backend.

Example

# Provider side
az network private-link-service create -g rg-platform -n pls-orders-api \
  --vnet-name vnet-platform --subnet snet-pls \
  --lb-name lb-orders-internal --lb-frontend-ip-configs fe-orders

# Consumer side (another subscription or tenant)
az network private-endpoint create -g rg-spoke-a -n pe-orders-api \
  --vnet-name vnet-spoke-a --subnet snet-pe \
  --private-connection-resource-id <pls-resource-id> \
  --connection-name orders --manual-request true

Common mistakes

  • Forgetting private DNS, so the name still resolves to the public IP.
  • Using a Basic Load Balancer (Private Link service needs Standard).
  • Thinking a private endpoint gives access to the whole PaaS service.
  • Not restricting visibility or auto-approval for a Private Link service.

How to answer in the interview

"A private endpoint is the consumer side: a private IP in my VNet that connects to one specific resource, like a single storage account or SQL server, with private DNS so the normal hostname resolves privately. A Private Link service is the provider side: I put my own service behind a Standard Load Balancer and publish it, and consumers in other VNets, subscriptions or tenants create private endpoints to it, which I approve. Because the provider NATs traffic, overlapping IP ranges don't matter, and only that one service is exposed, unlike peering."

Likely follow-up questions

  • How do you offer an API to 50 spokes with overlapping ranges? One Private Link service; each spoke creates its own private endpoint.
  • How does the backend see the client IP? Through the TCP Proxy Protocol v2 option, which carries the source and link ID.
  • Who manages DNS at scale? Central private DNS zones in the hub, often automated with Azure Policy.
