What do consistency, availability, and partition tolerance mean?

Databases & SQL · concept · levels mid

In one line

In CAP, consistency means linearizability (every read sees the latest completed write), availability means every request to a healthy node gets a non-error response, and partition tolerance means the system keeps operating when messages between nodes are lost; this consistency is not the C in ACID.

Detailed explanation

Consistency (C) in CAP is a property of replicated data. The system behaves as if there were a single copy: once a write completes, every subsequent read, from any client and any node, returns that value or a newer one. This is linearizability, the strongest single-object consistency model. Weaker models include sequential consistency, causal consistency, read-your-writes and eventual consistency (replicas converge if writes stop). By contrast, ACID consistency means a transaction preserves database invariants and constraints; it is about valid data, not about replicas agreeing.

Availability (A) has a strict meaning: every request received by a non-failing node must eventually produce a non-error response. Returning "service unavailable" or timing out counts as unavailable, while returning stale data counts as available. Note this is different from the operational "99.99% uptime" notion of availability, which a CP system can also achieve most of the time.

Partition tolerance (P) means the system continues to function despite an arbitrary number of messages being dropped or delayed between nodes, for example when a data centre link fails and the cluster splits into groups that cannot talk. From the inside, a partition is indistinguishable from a very slow or crashed node, which is why timeouts drive the decision.

Putting them together: during a partition a node either waits/rejects (giving up A to keep C) or answers from local state (giving up C to keep A).

How it works

  1. A client writes x = 2 to node A.
  2. Node A tries to replicate to node B, but the link is down.
  3. A client reads x from node B.
  4. CP behaviour: B rejects or blocks the read because it cannot confirm the latest value.
  5. AP behaviour: B returns x = 1 (stale) and catches up after the partition heals.

Example

Linearizable (C):   write x=2 completes at 10:00:00.000
                    read x anywhere after that -> 2 (never 1)

Eventual:           read from replica at 10:00:00.050 -> 1 (stale)
                    read again at 10:00:01           -> 2 (converged)

Availability check: node up but returns HTTP 503 "no quorum" -> NOT available in CAP terms

Common mistakes

  • Using "consistency" for both CAP and ACID without distinguishing.
  • Believing a CP system is "down" all the time; it only rejects requests on the minority side during partitions.
  • Thinking that returning an error is acceptable for availability.
  • Treating partition tolerance as optional for a multi-node system.

How to answer in the interview

"In CAP, consistency means linearizability: every client sees the same data, and every read returns the most recent completed write no matter which node answers. That's different from ACID consistency, which is about constraints. Availability means every request to a non-failing node gets a non-error response in reasonable time, even if the data might be stale. Partition tolerance means the system keeps operating when the network drops or delays messages between nodes, splitting the cluster. During a partition you must choose: reject requests to stay consistent, or answer with possibly stale data to stay available."

Likely follow-up questions

  • Can a single-node database be CA? Trivially, because there is no network between replicas to partition; but it is not distributed and a crash makes it unavailable.
  • What is eventual consistency? If no new writes arrive, all replicas eventually return the same value.
  • Is a stale answer "available"? Yes, in CAP terms any non-error response counts.
