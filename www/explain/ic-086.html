How do you manage Terraform in GitOps style for platform infrastructure?

Infrastructure as Code · concept · levels senior

In one line

GitOps for Terraform means Git is the source of truth and automation makes reality match: typically PR-driven workflows (Atlantis, HCP Terraform VCS-driven runs) that plan on every PR and apply on merge, or Kubernetes-native controllers (Crossplane, the Flux tofu-controller) that continuously reconcile, with trade-offs between automatic drift correction and explicit, reviewed applies.

Detailed explanation

GitOps principles: desired state is declared in Git, changes happen through pull requests, an automated agent applies them, and the system is continuously compared with Git. Applying this to Terraform gives two main styles.

PR-driven (most common). Atlantis (self-hosted) or HCP Terraform VCS-driven workspaces (and platforms such as Spacelift or env0) react to pull requests: they run plan for each affected project, post the plan as a PR comment, enforce policy checks and approvals, and run apply either on a command (atlantis apply) or after merge. The PR history becomes the audit log; nobody needs local credentials. Locking per project prevents two PRs from planning against the same state concurrently.

Controller-driven (Kubernetes-native). Crossplane represents cloud resources as Kubernetes objects; providers continuously reconcile them, and Argo CD or Flux sync those objects from Git. The tofu-controller for Flux runs Terraform/OpenTofu configurations as Kubernetes custom resources on an interval, with options for auto-apply or manual approval of plans. Drift is corrected automatically, the same way Argo CD corrects manual changes to Deployments.

Trade-offs. Continuous reconciliation keeps reality honest, but it can revert an emergency fix made during an incident, and a destructive change merged to Git gets applied without a human reading a plan at apply time. Explicit applies are slower but make destructive changes visible. Many teams use continuous reconciliation for low-risk, high-churn resources and PR-driven explicit applies for foundations such as networking and data stores, with drift detection rather than correction there.

How it works

  1. Engineer opens a PR changing live/prod/network.
  2. Atlantis detects the project, runs plan, posts it, runs policy checks.
  3. Reviewer approves; atlantis apply or merge triggers apply.
  4. Atlantis comments the result; PR merges (or is already merged).
  5. Scheduled plans or controllers detect later drift.

Example

# atlantis.yaml
version: 3
projects:
  - name: prod-network
    dir: live/prod/eu-west-1/network
    autoplan:
      when_modified: ["*.tf", "../../../../modules/network/**/*.tf"]
    apply_requirements: [approved, mergeable]

Common mistakes

  • Auto-applying foundational infrastructure without plan review.
  • Mixing PR-driven applies with manual applies from laptops.
  • Continuous reconciliation fighting an incident responder.
  • No per-project locking, causing stale plans.

How to answer in the interview

"GitOps means Git is the source of truth and automation makes reality match it. For Terraform the common approach is pull-request driven: Atlantis or HCP Terraform VCS-driven workspaces plan every PR, post the plan for review and apply after approval or merge, so every change is reviewed and audited in Git. A more Kubernetes-native approach uses controllers, Crossplane or the tofu-controller for Flux, that continuously reconcile infrastructure defined as Kubernetes objects and correct drift automatically. The trade-off is that continuous reconciliation can revert emergency fixes and makes destructive changes less visible than an explicit, reviewed apply."

Likely follow-up questions

  • What risks does automatic drift correction introduce? Reverting legitimate emergency changes and applying destructive changes without a human reading the plan.
  • Apply before or after merge? Apply-before-merge keeps main reflecting reality; apply-after-merge keeps main as intent; choose one consistently.
  • How do you secure Atlantis? Restrict who can comment apply, require approvals, and scope its cloud roles per project.
