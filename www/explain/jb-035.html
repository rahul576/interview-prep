How can excessive string creation contribute to memory pressure in a backend application?

JVM & Performance · scenario · levels senior, lead

In one line

Excessive string creation raises the allocation rate, which means more frequent young GCs, extra CPU and latency spikes; duplicate long-lived strings also fill the old generation; fix it with parameterised logging, StringBuilder in loops, fewer needless toString calls, streaming JSON, enums or deduplication, and confirm with an allocation profiler.

Detailed explanation

Strings are immutable, so every concatenation, substring, split, format, toUpperCase or toString creates new objects: a String plus its backing byte[]. In a busy backend these add up quickly: a request handler that builds log messages, converts IDs, serialises a JSON response and parses headers can allocate hundreds of kilobytes per request. At 2,000 requests per second that is hundreds of megabytes per second.

Short-lived strings die young, which is cheap per object, but a high allocation rate fills Eden faster, so minor GCs run more often. Each is a stop-the-world pause (short with G1, but frequent), and GC threads compete with request threads for CPU. Under load, this shows up as higher p99 latency and CPU usage.

Long-lived duplicate strings are a different problem. Large caches, parsed configuration or in-memory lookup tables often contain the same values (country codes, status names, currency codes) millions of times. These survive into the old generation, inflate the heap and increase the risk of long mixed or full collections.

Common sources:

  • log.debug("User " + user + " loaded " + order) builds the string even when debug is disabled.
  • toString() on large objects for logs or exceptions.
  • String-based JSON building, or reading whole payloads into one String before parsing.
  • String.format and regex split in hot loops.
  • Using String keys built by concatenation (userId + ":" + date) for maps and caches.

Fixes. Use parameterised logging (log.debug("User {} loaded {}", id, orderId)) or lambda suppliers so nothing is built when the level is off. Use StringBuilder for loops (single expressions are already optimised by javac). Stream JSON with Jackson directly to the output stream. Replace repeated values with enums or canonical constants, use String.intern() sparingly for bounded sets, or enable string deduplication (-XX:+UseStringDeduplication, available for G1 and, since JDK 18, other collectors), which shares backing arrays of equal long-lived strings. Since Java 9, compact strings already store Latin-1 text with one byte per character.

How it works

  1. Each string operation allocates a new String and byte[] in Eden.
  2. High volume fills Eden quickly; minor GCs become frequent.
  3. GC threads use CPU; pauses accumulate into latency.
  4. Long-lived duplicates get promoted, bloating the old generation.
  5. Profiling identifies allocation sites; code fixes reduce bytes per request.

Example

// Before: allocates even when DEBUG is off
log.debug("Processing order " + order.getId() + " for " + customer.toString());

// After
log.debug("Processing order {} for {}", order.getId(), customer.getId());

// Before: concatenation in a loop creates a new String each iteration
String csv = "";
for (Item i : items) csv += i.sku() + ",";

// After
StringBuilder sb = new StringBuilder(items.size() * 12);
for (Item i : items) sb.append(i.sku()).append(',');
java -XX:+UseG1GC -XX:+UseStringDeduplication -Xlog:stringdedup*=debug -jar app.jar
asprof -e alloc -d 30 -f alloc.html <pid>   # allocation flame graph

Common mistakes

  • Assuming disabled log levels cost nothing with string concatenation.
  • Interning unbounded, user-supplied strings.
  • Optimising single-line + expressions that the compiler already handles.
  • Tuning GC flags instead of reducing allocation.

How to answer in the interview

"Every request can create thousands of temporary strings: concatenation in log statements even when the level is off, JSON serialisation, toString calls, splitting and formatting. That raises the allocation rate, so young GCs run more often, costing CPU and adding latency spikes. Separately, duplicate long-lived strings, like status values in a big cache, survive into the old generation and increase heap use and full GC risk. I fix it with parameterised logging, StringBuilder in loops, avoiding needless toString, streaming JSON, enums or deduplication for repeated values, and I confirm the hot spots with an allocation profiler like JFR or async-profiler before and after."

Likely follow-up questions

  • How would you find which code path allocates the most strings? JFR allocation samples or async-profiler in alloc mode, read as a flame graph.
  • What are compact strings? Since Java 9, strings with only Latin-1 characters use one byte per character.
  • Is intern() a good idea? Only for small, bounded sets; string deduplication or enums are safer.
