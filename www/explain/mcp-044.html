How do you add observability to an MCP server running in production?

MCP Servers · concept · levels mid, senior

In one line

Treat an MCP server like a production API with tool-level telemetry: structured logs per tool call, metrics for rate, errors and latency per tool, distributed tracing with context propagated through request metadata, careful redaction, and dashboards and alerts per tool and per client.

Detailed explanation

An MCP server is called by models, not humans, which changes what you need to observe. A slow or failing tool does not produce a support ticket; the agent just retries, picks a worse tool or gives up. So observability has to answer three questions: is the server healthy, are individual tools behaving, and are models using the tools as intended?

Structured logs are the base layer. Each tool call should log the authenticated user, the client application, the tool name, duration, outcome, and whether a failure was a protocol error (JSON-RPC error such as invalid params) or a tool execution error (a result with isError: true). Arguments should be logged selectively: they can contain personal data or secrets that the model copied from context, so redact or hash them by default.

Metrics give call rate, error rate and latency percentiles per tool, plus downstream dependency latency, exported through OpenTelemetry or Prometheus. Distributed tracing is where agent systems benefit most: W3C trace context can be carried in the request's _meta field or HTTP headers, so one trace spans the agent loop, the model call that chose the tool, the MCP request and the downstream API calls. That shows whether the slowness was the model, the server or the database.

Usage data is also product feedback: tools that are never chosen, or chosen and then followed by immediate errors, usually have unclear names, descriptions or schemas.

How it works

  1. Wrap every tool handler in middleware that starts a span and records start time, user, client and tool.
  2. Extract incoming trace context from _meta or headers and make the span its child.
  3. Record outcome, error class and duration; increment counters and histograms labelled by tool and client.
  4. Log a structured event with redacted arguments and a result size, not the full result.
  5. Build dashboards per tool and per client, and alert on error-rate spikes and p95 latency.

Example

from opentelemetry import trace, metrics
tracer = trace.get_tracer("orders-mcp")
calls = metrics.get_meter("orders-mcp").create_histogram("mcp.tool.duration", unit="ms")

def instrumented(tool_name, handler):
    def wrapper(args, ctx):
        with tracer.start_as_current_span(f"tool {tool_name}", context=ctx.trace_context) as span:
            span.set_attribute("mcp.tool", tool_name)
            span.set_attribute("enduser.id", ctx.user_id)
            start = time.monotonic()
            result = handler(args, ctx)
            outcome = "tool_error" if result.is_error else "ok"
            calls.record((time.monotonic() - start) * 1000,
                         {"tool": tool_name, "client": ctx.client_name, "outcome": outcome})
            log.info("tool_call", tool=tool_name, user=ctx.user_id,
                     args=redact(args), outcome=outcome)
            return result
    return wrapper

Common mistakes

  • Logging full arguments and results, leaking customer data or tokens into log storage.
  • Only measuring HTTP status codes; tool errors come back as successful responses with isError.
  • No per-client labels, so you cannot tell which host or agent is causing a spike.
  • Metrics with unbounded label values such as raw arguments, which explode cardinality.

How to answer in the interview

"I instrument it like any production API, but at the level of tools. Every tool call gets a structured log with user, client, tool, duration and outcome, and I distinguish protocol errors from tool execution errors. Arguments are logged selectively with redaction because models copy sensitive data into them. Metrics cover call rate, error rate and latency per tool and per downstream dependency, through OpenTelemetry. Tracing is the most valuable part: I propagate trace context through request metadata so one trace covers the agent, the model call, the MCP request and the downstream calls. Dashboards and alerts are per tool and per client, and I also watch usage, because a tool the models never pick usually has a bad description."

Likely follow-up questions

  • Which metric reveals a confusing tool description? Low selection rate, or high rate of invalid-argument errors right after selection.
  • Where does trace context travel? In HTTP headers for remote servers or the _meta field of the request.
  • How do you alert without noise? SLO-based alerts on error budget burn per critical tool.
