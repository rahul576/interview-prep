What is the difference between Docker and Podman?

Docker · concept · levels mid

In one line

Podman is a daemonless, rootless-by-default container engine with a Docker-compatible CLI, a native pods concept, strong systemd (Quadlet) and Kubernetes YAML integration, using the same OCI images and Buildah for builds.

Detailed explanation

Docker uses a client-server design: the CLI talks to a long-running dockerd daemon, traditionally running as root, which owns all containers. Podman, developed by Red Hat and the containers community, has no central daemon. Each podman command directly creates containers through the OCI runtime (crun by default on most distributions, or runc), and a tiny conmon process monitors each container. There is no single privileged service that every container depends on or that an attacker can target through a socket.

Podman is rootless by default: an ordinary user runs containers inside a user namespace, so root in the container maps to that user's UID range on the host. Rootless networking uses pasta (default in Podman 5) or slirp4netns. Root mode is still available when needed.

The CLI is largely compatible with Docker (podman run, build, ps, push), so many people alias docker=podman or install the podman-docker package. Podman can also expose a Docker-compatible REST API socket, letting tools like docker compose or Testcontainers talk to it, and podman compose wraps Compose providers. On macOS and Windows, podman machine runs a Linux VM, similar to Docker Desktop.

Distinctive features: pods, groups of containers sharing network and IPC namespaces exactly like Kubernetes pods; podman kube generate and podman kube play to export and run Kubernetes YAML; and Quadlet files that turn containers into systemd services, ideal for servers and edge devices. Images are standard OCI, so images move freely between the two. Podman builds images with Buildah under the hood.

How it works

  1. podman run resolves and pulls the OCI image into user storage.
  2. It sets up a user namespace and rootless network.
  3. It launches conmon, which calls crun/runc to start the container.
  4. The CLI exits; conmon keeps monitoring the container.
  5. systemd (via Quadlet) can supervise the container as a service.

Example

podman run -d --name web -p 8080:80 docker.io/library/nginx:1.27
podman pod create --name app -p 8080:8080
podman run -d --pod app registry.local/api:1.4
podman kube generate app > app.yaml
systemctl --user enable --now podman.socket   # Docker-compatible API for tools
# ~/.config/containers/systemd/web.container (Quadlet)
[Container]
Image=docker.io/library/nginx:1.27
PublishPort=8080:80
[Install]
WantedBy=default.target

Common mistakes

  • Assuming 100% CLI parity; some flags and Compose features differ.
  • Forgetting short image names need registries configured (docker.io/...).
  • Rootless limits: ports below 1024, cgroup delegation for resource limits.
  • CI scripts that rely on /var/run/docker.sock existing.

How to answer in the interview

"Podman is an alternative engine from Red Hat. The biggest difference is that it's daemonless: each podman command runs containers directly through conmon and crun or runc, instead of talking to a long-running root daemon, so there's no single privileged point of failure. It's rootless by default and integrates with systemd through Quadlet. The CLI is compatible with Docker, so many people alias docker to podman, and it can expose a Docker-compatible socket. It also has pods like Kubernetes and can generate or play Kubernetes YAML. Both use OCI images, and Podman uses Buildah for builds."

Likely follow-up questions

  • What might break replacing Docker with Podman in CI? Socket-dependent tools, Compose edge cases, short image names, rootless port and volume permissions.
  • What is Quadlet? Declarative systemd unit files for Podman containers.
  • Can Podman run Docker Compose files? Yes, through its compatible API socket or podman compose.
