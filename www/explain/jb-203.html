How would you implement pagination and sorting in a REST API?

REST & API Design · design · levels mid, senior

In one line

Expose query parameters like ?page=0&size=20&sort=createdAt,desc, bind them to Spring Data Pageable, return items plus metadata (page, size, total or hasNext, links), cap page size, whitelist sort fields with a unique tie-breaker, index the sort columns, and use keyset/cursor pagination for large data.

Detailed explanation

Any endpoint returning a collection must be paginated; otherwise one request can load millions of rows and take down the service.

Request. Standard query parameters: page (zero-based in Spring), size, and sort=field,direction, repeatable for multiple fields. Filters are separate parameters: ?status=PAID&from=2026-11-01.

Spring implementation. A controller method parameter of type Pageable is resolved automatically by Spring Data Web support. @PageableDefault sets defaults, and spring.data.web.pageable.max-page-size caps the size (default max 2000; set it lower, such as 100). The repository method Page<Order> findByStatus(Status s, Pageable p) produces ORDER BY ... LIMIT ... OFFSET ... plus a count query. If you do not need totals, return Slice<T>, which fetches size+1 rows to know whether there is a next page and skips the count.

Response. Return the items with metadata: page, size, totalElements/totalPages (if cheap) or hasNext, and ideally next/prev links. Do not serialise Spring's PageImpl directly: its JSON structure is not a stable contract (Spring Data 3.3+ warns about it and offers @EnableSpringDataWebSupport(pageSerializationMode = VIA_DTO) or PagedModel). Map to your own DTO.

Sorting safety. Clients should only sort on whitelisted, indexed fields. Arbitrary sort properties can cause slow full scans or errors; validate them and map API names to entity properties. Always append a unique tie-breaker (id) so the order is deterministic; otherwise rows with equal createdAt may appear on two pages or none.

Large or fast-changing data. Offset becomes slow on deep pages and unstable under inserts, so use keyset (cursor) pagination: WHERE (created_at, id) < (:c, :id), supported in Spring Data via ScrollPosition and Window. Index the sort columns, for example (status, created_at DESC, id DESC) to match filter plus sort.

How it works

  1. Client sends page, size, sort and filters.
  2. Spring builds a Pageable; size is capped, sort validated.
  3. Repository runs a limited, ordered query (and count if needed).
  4. Response DTO includes items and metadata/links.
  5. For big data, return a cursor instead of page numbers.

Example

private static final Set<String> SORTABLE = Set.of("createdAt", "total", "id");

@GetMapping("/orders")
PageResponse<OrderDto> list(@RequestParam(required = false) OrderStatus status,
                            @PageableDefault(size = 20, sort = "createdAt", direction = Sort.Direction.DESC) Pageable pageable) {
    pageable.getSort().forEach(o -> {
        if (!SORTABLE.contains(o.getProperty())) throw new BadRequestException("Cannot sort by " + o.getProperty());
    });
    Pageable stable = PageRequest.of(pageable.getPageNumber(), Math.min(pageable.getPageSize(), 100),
                                     pageable.getSort().and(Sort.by("id").descending()));
    Page<OrderDto> page = repo.findByStatus(status, stable).map(OrderDto::from);
    return PageResponse.of(page);
}

record PageResponse<T>(List<T> items, int page, int size, long totalElements, boolean hasNext) {
    static <T> PageResponse<T> of(Page<T> p) {
        return new PageResponse<>(p.getContent(), p.getNumber(), p.getSize(), p.getTotalElements(), p.hasNext());
    }
}
spring.data.web.pageable.max-page-size=100

Common mistakes

  • No maximum page size.
  • Sorting on any client-supplied field.
  • No tie-breaker, causing duplicates across pages.
  • Expensive COUNT on huge tables for every request.
  • Serialising PageImpl directly as the API contract.

How to answer in the interview

"I expose query parameters like page, size and sort, for example sort=createdAt,desc. In Spring the controller takes a Pageable, which Spring Data turns into LIMIT, OFFSET and ORDER BY. The response contains the items plus metadata, such as page, size and total or just a hasNext flag, and next and previous links, using my own DTO rather than Spring's Page JSON. I cap the page size, whitelist sortable fields so nobody sorts on unindexed columns, and always add id as a tie-breaker so ordering is stable. For large or fast-changing data I switch to keyset pagination with a cursor and make sure the sort columns are indexed."

Likely follow-up questions

  • Why can a total count be expensive, and how would you avoid it? COUNT(*) scans many rows; use Slice/hasNext, cached or approximate counts.
  • Page vs Slice? Page runs a count query; Slice only checks for a next page.
  • How do you index for filter plus sort? A composite index matching filter columns then sort columns.
