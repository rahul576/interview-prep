What is thread safety?

Concurrency · concept · levels entry

In one line

Code is thread-safe if it behaves correctly when used by multiple threads at the same time, whatever the scheduling, without callers adding extra synchronisation: no lost updates, no stale reads, no broken invariants.

Detailed explanation

Thread safety is about correctness under concurrency. The definition from "Java Concurrency in Practice": a class is thread-safe if it behaves correctly when accessed from multiple threads, regardless of scheduling or interleaving, and with no additional synchronisation or coordination by the calling code.

All problems come from shared mutable state. Three kinds of failure appear:

  • Race conditions: the result depends on timing. count++ (read, add, write) can lose updates; check-then-act (if (!map.containsKey(k)) map.put(k, v)) can insert twice.
  • Visibility problems: without a happens-before relationship, one thread may never see another thread's write, for example a loop waiting on a non-volatile flag forever.
  • Broken invariants: two related fields, such as min and max, are updated separately and another thread sees an inconsistent pair. Unsafe collections can even corrupt their internal structure.

There are three families of solution:

  1. Do not share: thread confinement, such as local variables, request-scoped objects or ThreadLocal.
  2. Do not mutate: immutable objects (String, records with immutable components, List.of).
  3. Coordinate: synchronized, Locks, atomic classes (AtomicInteger, LongAdder) and concurrent collections (ConcurrentHashMap, CopyOnWriteArrayList, BlockingQueue).

Classic examples: StringBuilder is not thread-safe, StringBuffer is; HashMap is not, ConcurrentHashMap is; ArrayList is not, CopyOnWriteArrayList is. Note that a thread-safe class does not make compound operations across several calls safe automatically. And thread safety is a contract worth documenting, because callers need to know it.

How it works

  1. Find the state that is shared between threads and mutable.
  2. Eliminate sharing or mutation where possible.
  3. For the rest, ensure each compound action is atomic.
  4. Ensure visibility via a happens-before edge (lock, volatile, concurrent collection).
  5. Verify with concurrent tests and code review; document the guarantee.

Example

// Not thread-safe: lost updates, HashMap may corrupt under concurrent writes
class UnsafeStats {
    private final Map<String, Integer> hits = new HashMap<>();
    void hit(String page) { hits.put(page, hits.getOrDefault(page, 0) + 1); }
}

// Thread-safe: atomic per-key update in a concurrent map
class SafeStats {
    private final ConcurrentHashMap<String, LongAdder> hits = new ConcurrentHashMap<>();
    void hit(String page) { hits.computeIfAbsent(page, p -> new LongAdder()).increment(); }
    long get(String page) {
        LongAdder a = hits.get(page);
        return a == null ? 0 : a.sum();
    }
}

Common mistakes

  • Assuming that using a thread-safe collection makes multi-step logic safe.
  • Sharing SimpleDateFormat across threads.
  • Making a class thread-safe with locks when confinement would avoid the need.
  • Assuming read-only access needs no thought: it does if anyone else writes.

How to answer in the interview

"Code is thread-safe when it behaves correctly however the threads are scheduled, without callers adding their own coordination: invariants hold, no updates are lost and every thread sees up-to-date values. The problems come from shared mutable state: race conditions like count++ losing updates, visibility issues where a thread never sees another's write, and broken invariants. I get thread safety by not sharing, with thread confinement and local variables, by not mutating, with immutable objects, or by coordinating with synchronized, locks, atomics and concurrent collections. For example HashMap and StringBuilder aren't thread-safe, while ConcurrentHashMap and StringBuffer are."

Likely follow-up questions

  • Is an immutable object automatically thread safe? Yes, if it is truly immutable (all fields final, no mutable internals escape) and properly constructed without this escaping.
  • Are local variables thread-safe? Yes, each thread has its own stack, though objects they reference may still be shared.
  • Is ConcurrentHashMap enough for check-then-act? Only if you use its atomic methods like putIfAbsent, computeIfAbsent or merge.
