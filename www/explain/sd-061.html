How do you implement a distributed lock safely?

Distributed Systems · concept · levels senior, lead

In one line

A safe distributed lock needs expiry, owner tokens, and, for correctness, fencing tokens checked by the protected resource; Redis SET NX PX suits efficiency locks, etcd/ZooKeeper suit correctness locks, and often conditional writes remove the need for locks entirely.

Detailed explanation

Two kinds of locks:

  • Efficiency locks: prevent duplicate work (two workers generating the same report). If the lock occasionally fails, you waste some CPU. Redis is fine.
  • Correctness locks: two holders would corrupt data (double charge, overwrite). Here you need stronger guarantees.

Why expiry? A holder may crash; without a TTL the lock is held forever. But expiry creates the core problem: a holder can pause (GC, VM migration, network delay) longer than the TTL. The lock expires, someone else acquires it, then the first holder wakes up and writes, believing it still owns the lock.

Fencing tokens solve this: the lock service returns a monotonically increasing number with each grant; the storage layer accepts writes only with a token ≥ the highest it has seen. etcd revisions and ZooKeeper zxids provide such numbers; plain Redis doesn't, which is the core of the Redlock debate.

How it works

  1. Acquire: SET lock:job42 <uuid> NX PX 30000 (or etcd lease + key).
  2. Do work; extend the TTL if needed (watchdog).
  3. Write to resource with fencing token; resource checks it.
  4. Release only if value == my uuid (Lua script).

Example

-- safe release
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
else return 0 end
-- lock-free alternative: conditional write
UPDATE jobs SET owner='w7', version=version+1 WHERE id=42 AND version=5;

Common mistakes

  • DEL without checking ownership (releasing someone else's lock).
  • No TTL, or TTL shorter than the work.
  • Assuming Redis locks are safe for correctness under pauses.
  • Locks where a unique constraint or compare-and-set would do.

How to answer in the interview

"First I ask whether I need a lock at all: idempotency, unique constraints or compare-and-set often solve it. For efficiency locks I use Redis SET NX with a TTL and a random owner value, releasing only my own lock. For correctness, I use etcd or ZooKeeper and pass a fencing token to the protected resource, which rejects writes from stale holders, because any lock with expiry can be outlived by a paused process."

Likely follow-up questions

  • Why is Redlock controversial? It relies on timing assumptions and lacks fencing tokens.
  • Lock renewal? Watchdog threads extending TTL (Redisson).
  • Database advisory locks? pg_advisory_lock for single-DB coordination.
