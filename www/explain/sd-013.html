Design the API layer for a public platform used by web, mobile and partner clients. How do you choose between REST, gRPC and GraphQL?

SD Fundamentals · design · levels mid, senior

In one line

Use REST for public and partner APIs, gRPC for internal service-to-service calls, and GraphQL for client apps that aggregate many resources, all behind an API gateway with clear versioning rules.

Detailed explanation

REST over HTTPS with JSON is universal: every language and tool understands it, it maps well to resources, and HTTP caching (ETags, Cache-Control) works through CDNs. That makes it the safe default for external consumers.

gRPC uses Protobuf over HTTP/2: compact binary messages, strict typed contracts with code generation, streaming and lower latency. It's excellent internally but harder for browsers and partners.

GraphQL exposes a typed schema; clients ask for exactly the fields they need in one round trip, which suits mobile screens composed from many resources. The costs: HTTP caching is harder, and a single query can be very expensive, so you need depth/complexity limits and persisted queries.

An API gateway (Kong, Apigee, AWS API Gateway, Azure APIM) handles auth, rate limiting, routing and logging. A backend for frontend (BFF) can tailor APIs per client.

How it works

  1. Public API: REST, OpenAPI spec, OAuth 2.0, versioned (/v1) or header-versioned.
  2. Internal: gRPC with Protobuf contracts in a shared repo; backward-compatible field changes.
  3. Clients: GraphQL or BFF aggregating internal services.
  4. Gateway: authentication, quotas, request IDs, observability.

Example

service OrderService {
  rpc GetOrder (GetOrderRequest) returns (Order);
  rpc StreamOrderUpdates (OrderId) returns (stream OrderEvent);
}

Common mistakes

  • Exposing gRPC to third parties who can't easily consume it.
  • GraphQL without query cost limits.
  • Breaking changes without versioning or deprecation windows.
  • Chatty APIs that need ten calls per screen.

How to answer in the interview

"I'd choose by audience. Partners get REST with OpenAPI and OAuth, because it's universal and cacheable. Internally, services talk gRPC for typed contracts and performance. The mobile and web apps get a BFF or GraphQL layer so each screen loads in one call. A gateway in front handles auth and rate limits, and we only make additive changes to stay backward compatible."

Likely follow-up questions

  • How do you protect GraphQL? Depth and complexity limits, persisted queries, per-client rate limits.
  • How do you version gRPC? Add fields, never reuse field numbers, new package for breaking changes.
  • What is a BFF? A backend tailored to one client type that aggregates downstream APIs.
