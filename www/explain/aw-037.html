How do ALB listener rules, target groups and target types work?

Cloud (AWS) · concept · levels mid

In one line

An ALB listener accepts connections on a port and protocol, its ordered rules match on host, path, headers, method, query string or source IP, and the matching action forwards to a target group of instances, IPs or a Lambda function, optionally weighted across several groups.

Detailed explanation

The Application Load Balancer works at layer 7. A listener is a process bound to a port, typically HTTP on 80 and HTTPS on 443. An HTTPS listener terminates TLS using a certificate from ACM (several certificates can be attached and chosen by SNI) and a security policy that fixes the allowed TLS versions and ciphers.

Each listener has a default action plus rules evaluated in priority order, lowest number first. Conditions include host-header, path-pattern, http-header, http-request-method, query-string and source-ip, and one rule may combine several. Actions are forward, redirect (the classic HTTP to HTTPS redirect), fixed-response (for example a 503 maintenance page), and authenticate-oidc or authenticate-cognito before forwarding.

A target group holds targets of exactly one target type: instance (EC2 instance IDs, traffic goes to the primary interface), ip (any private IP, which is what ECS awsvpc tasks and EKS pods use through the AWS Load Balancer Controller, and also on-premises servers over Direct Connect), or lambda (one function, the request turned into a JSON event). Each group has its own health check path, port, thresholds and success codes.

A forward action can list several target groups with weights, which is the building block for canary and blue/green releases. Target group attributes add stickiness (load-balancer cookie or application cookie), slow start (ramping new targets up over a period), the deregistration delay (connection draining, 300 seconds by default) and the routing algorithm (round robin, least outstanding requests or weighted random).

How it works

  1. A client connects to the ALB DNS name; the HTTPS listener on 443 terminates TLS.
  2. Rules are checked in priority order until one matches; otherwise the default action runs.
  3. The forward action picks a target group, by weight if several are listed.
  4. Within the group, the algorithm chooses a healthy target, honouring stickiness if enabled.
  5. Health checks continuously mark targets healthy or unhealthy.
  6. On deregistration, in-flight requests get the deregistration delay to finish.

Example

Routing two hostnames through one ALB, with a 10 percent canary for the API:

aws elbv2 create-rule --listener-arn $LISTENER --priority 10 \
  --conditions Field=host-header,Values=api.example.com \
  --actions '[{"Type":"forward","ForwardConfig":{"TargetGroups":[
     {"TargetGroupArn":"'$API_BLUE'","Weight":90},
     {"TargetGroupArn":"'$API_GREEN'","Weight":10}]}}]'

aws elbv2 create-rule --listener-arn $LISTENER --priority 20 \
  --conditions Field=host-header,Values=app.example.com \
  --actions Type=forward,TargetGroupArn=$APP_TG

Common mistakes

  • Leaving a broad path rule at a lower priority number so it shadows more specific rules.
  • Pointing the health check at a page that needs a database, so one slow dependency marks every target unhealthy.
  • Using the instance target type for Fargate tasks, which require the ip type.
  • Setting a long deregistration delay for short requests, which slows every deployment.

How to answer in the interview

"An ALB has listeners, say HTTPS on 443 with an ACM certificate, and each listener has prioritised rules. A rule matches on host, path, headers, method, query string or source IP and then forwards, redirects, returns a fixed response or authenticates. Forwarding goes to a target group, which has one target type: instances, IPs, which is what ECS and EKS use, or a Lambda function, each with its own health check. Because a forward action can weight several target groups, I use that for canaries and blue/green. On the target group I tune stickiness, slow start and the deregistration delay."

Likely follow-up questions

  • How would you route api.example.com and app.example.com through one ALB? Two host-header rules on the same HTTPS listener, a SAN or wildcard certificate, each forwarding to its own target group.
  • What is the difference between ALB stickiness types? Duration-based uses an ALB-generated cookie; application-based follows a cookie your app sets.
  • Why least outstanding requests? It helps when request costs vary a lot, avoiding piling work on a busy target.
