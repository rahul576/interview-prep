Is exactly-once message delivery possible, and how do real systems achieve exactly-once processing?

Distributed Systems · concept · levels senior, lead

In one line

Exactly-once delivery is impossible over unreliable networks; systems achieve exactly-once effect with at-least-once delivery + deduplication/idempotent consumers, Kafka's idempotent producers and transactions, and atomic commits of results with offsets.

Detailed explanation

The Two Generals problem in practice: a sender gets no ack. Was the message lost, or was the ack lost? It must choose: resend (risk duplicate → at-least-once) or not (risk loss → at-most-once). No protocol avoids both on its own.

So "exactly-once" in products really means: the observable effect of processing happens once.

Techniques:

  • Idempotent processing: upserts keyed by event ID, INSERT … ON CONFLICT DO NOTHING, setting state rather than incrementing.
  • Deduplication store: remember processed message IDs (with TTL) in the same DB transaction as the effect (inbox pattern).
  • Kafka idempotent producer: broker deduplicates producer retries using producer ID + sequence numbers.
  • Kafka transactions: consume → produce output + commit consumer offsets atomically; downstream consumers with read_committed see only committed results.
  • External sinks: store output and source offsets in one DB transaction, or use two-phase-commit sinks (Flink).

How it works

  1. Consumer reads message (id=m17).
  2. BEGIN; INSERT INTO processed(id) VALUES ('m17') (unique) → if conflict, skip.
  3. Apply effect; COMMIT.
  4. Commit offset (if crash before this, redelivery is deduplicated in step 2).

Example

props.put("enable.idempotence", "true");
props.put("transactional.id", "payments-processor-1");
producer.initTransactions();
producer.beginTransaction();
producer.send(outputRecord);
producer.sendOffsetsToTransaction(offsets, consumer.groupMetadata());
producer.commitTransaction();

Common mistakes

  • Believing a broker setting alone gives end-to-end exactly-once with external side effects.
  • Dedup store in a different transaction from the effect.
  • Side effects like emails that can't be deduplicated by the receiver.

How to answer in the interview

"Exactly-once delivery isn't achievable over a network, so I design for at-least-once delivery and make processing idempotent. Consumers record processed message IDs in the same transaction as their effect, or use naturally idempotent writes. Within Kafka, idempotent producers plus transactions make read-process-write exactly-once, and for external databases I commit results and offsets together."

Likely follow-up questions

  • Exactly-once email sending? Record "sent" with message ID before/after via provider idempotency key; accept rare duplicates or use provider dedup.
  • At-most-once use cases? Metrics where loss is acceptable but duplicates aren't.
  • What's the inbox pattern? Consumer-side dedup table in the same transaction.
