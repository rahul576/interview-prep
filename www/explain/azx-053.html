A production secret appeared in clear text in a pipeline log. What do you do and how do you prevent it?

Azure DevOps & Pipelines · scenario · levels mid, senior

In one line

Rotate the secret immediately, delete or restrict the logs, find why masking failed (transformed/encoded/partial value, unmarked source, system.debug or set -x), then prevent recurrence: never echo secrets, mark generated values as secret, and reduce secrets via workload identity federation and Key Vault.

Detailed explanation

Contain first. Once a secret has been in a log, assume it is compromised: anyone with read access to the pipeline, log exports or integrations may have it. Rotate it immediately (and the dependent configuration), then check usage logs of the target system (sign-ins, API access) for misuse since the run.

Limit exposure: delete the pipeline run (or retention lease) to remove its logs, check who had view permission on the pipeline, and whether logs were forwarded elsewhere (SIEM, chat notifications, artifacts).

Root cause. Azure Pipelines masking replaces the exact string of known secret variables. It fails when:

  • The value was transformed: base64 encoded, URL encoded, JSON-escaped, split across lines, or only part of it printed.
  • The value came from a source not marked as secret: a normal variable, a tool's output, a file printed with cat, an ARM deployment output, or a secret fetched by a script.
  • Debug logging (system.debug: true) or set -x in bash / Set-PSDebug -Trace in PowerShell echoed commands with expanded values.
  • A tool printed its own config or verbose HTTP headers (--debug, -v).

Prevention:

  • Never echo secrets; pass them via env mapping, not command-line arguments.
  • Any value a script generates or retrieves that is sensitive must be registered with ##vso[task.setvariable variable=x;issecret=true] (or ##vso[task.setsecret]value) so it's masked.
  • Avoid set -x and debug flags in steps handling secrets; restrict who can enable system.debug.
  • Mark deployment outputs as secure (@secure() in Bicep).
  • Prefer workload identity federation and managed identities, and Key Vault references, so pipelines handle fewer long-lived secrets. Secret scanning on logs can catch leaks early.

How it works

  1. Rotate the credential; review its access logs.
  2. Delete the run/logs; review who had access.
  3. Reproduce how it leaked from the step output.
  4. Fix the script/template; add masking for generated values.
  5. Replace the secret with federation or managed identity where possible.
  6. Write a short post-incident note and template guard.

Example

# Register a generated value as secret so later output is masked
TOKEN=$(az account get-access-token --query accessToken -o tsv)
echo "##vso[task.setvariable variable=apiToken;issecret=true]$TOKEN"
# Bad: set -x; curl -H "Authorization: Bearer $TOKEN" ...
# Bad: echo $SECRET | base64      (encoded value is not masked)

Common mistakes

  • Deleting the log but not rotating the secret.
  • Rotating without checking whether it was already used.
  • Blaming masking rather than fixing the script.
  • Leaving system.debug settable at queue time by anyone.

How to answer in the interview

"First I treat the secret as compromised: rotate it immediately and check whether it was used. Then I delete the run's logs and check who could view them. Next I find how it bypassed masking: masking only hides the exact value, so a base64 or URL-encoded version, a partial print, a value from a source not marked secret, system.debug or set -x will leak it. To prevent it, scripts never echo secrets, any generated sensitive value is registered with issecret=true, debug tracing is avoided in those steps, and we move to workload identity federation and Key Vault so the pipeline handles fewer secrets."

Likely follow-up questions

  • Register a generated value as secret? ##vso[task.setvariable ...;issecret=true] or ##vso[task.setsecret].
  • Why env mapping instead of arguments? Arguments can show in process lists and command echoes.
  • Detect leaks automatically? Scan logs or use secret scanning and alerts on log exports.
