How do you define build stages and deployment steps in a pipeline?

DevOps & CI/CD · scenario · levels mid

In one line

Define ordered stages (build, test, analyse, package, publish, deploy), each with steps running commands (mvn, docker build/push, helm), add conditions (when on branch), parallel stages and approvals (input or environment protection), keep environment-specific config and credentials outside the code, and use post actions for reports, notifications and rollback.

Detailed explanation

A good pipeline reads like the team's release process. Typical stages for a Spring Boot service:

  • Build: ./mvnw -B clean package -DskipTests to fail fast on compile errors.
  • Test: unit and integration tests, possibly in parallel stages.
  • Quality: SonarQube scan and waitForQualityGate.
  • Package: docker build tagged with version and commit SHA.
  • Publish: docker push using credentials from the CI store.
  • Deploy: per environment, helm upgrade --install with that environment's values file, or a commit to a GitOps repository that Argo CD syncs.

Conditions: when { branch 'main' } limits deployment to main; PR builds stop after publish or even after tests.

Approvals: input steps in Jenkins, or environment protection rules with required reviewers in GitHub Actions and GitLab, gate staging or production.

Configuration and secrets: environment differences live in values files, Spring profiles or a config server; credentials are bound per stage from Jenkins credentials, GitHub secrets, Vault or cloud secret managers, never in the repo.

Post actions: publish JUnit and coverage reports, notify Slack or Teams, and on deployment failure run helm rollback or rely on the rollout tool's automatic rollback.

How it works

  1. Map the release process to stages.
  2. Implement each stage with tool commands.
  3. Add parallelism for independent work.
  4. Add conditions and approvals per environment.
  5. Bind credentials and environment config per stage.
  6. Add post actions for reporting and recovery.

Example

pipeline {
  agent any
  environment { IMAGE = "registry.example.com/orders:${env.GIT_COMMIT.take(8)}" }
  stages {
    stage('Build')   { steps { sh './mvnw -B clean package -DskipTests' } }
    stage('Test')    { parallel {
        stage('Unit') { steps { sh './mvnw -B test' } }
        stage('IT')   { steps { sh './mvnw -B verify -Pit' } } } }
    stage('Image')   { steps { sh 'docker build -t $IMAGE .' } }
    stage('Push')    { steps { withCredentials([usernamePassword(credentialsId: 'reg', usernameVariable: 'U', passwordVariable: 'P')]) {
        sh 'echo $P | docker login registry.example.com -u $U --password-stdin && docker push $IMAGE' } } }
    stage('Deploy dev')  { when { branch 'main' } steps { sh 'helm upgrade --install orders chart -f values-dev.yaml --set image.tag=${IMAGE##*:}' } }
    stage('Approve prod'){ when { branch 'main' } steps { input message: 'Deploy to production?' } }
    stage('Deploy prod') { when { branch 'main' } steps { sh 'helm upgrade --install orders chart -f values-prod.yaml --set image.tag=${IMAGE##*:} --atomic' } }
  }
  post { always { junit '**/target/*-reports/*.xml' } }
}

Common mistakes

  • Deploying from feature branches by accident.
  • Holding an executor while waiting on input for hours.
  • Environment config baked into the image.
  • No rollback path.

How to answer in the interview

"I define ordered stages, each with steps. Build runs Maven, Test runs unit and integration tests in parallel, Quality runs Sonar and waits for the gate, Package builds the Docker image tagged with the commit SHA, Publish pushes it with stored credentials, and Deploy stages per environment run helm upgrade with that environment's values, or update a GitOps repo. When conditions restrict deployments to main, an input step or environment protection adds approval for production, and post sections publish reports, notify the team and trigger rollback on failure."

Likely follow-up questions

  • Minimal Jenkinsfile for Spring Boot? Checkout, ./mvnw verify, junit in post; add image and deploy later.
  • Why --atomic in Helm? Rolls back automatically if the upgrade fails.
  • Avoid holding an agent during approval? Use agent none at the top level and run input outside agent blocks.
