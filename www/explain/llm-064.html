Answer quality dropped after a prompt change that looked harmless. How do you handle it and prevent it next time?

LLMOps & RAG · scenario · levels mid, senior

In one line

Roll back to the previous prompt version, compare both versions on the evaluation set and affected traces to find which cases regressed and why, fix against those failures, add them to the regression suite, and prevent recurrence with PR review, CI evaluation gates, gradual rollout and per-request prompt version tracing.

Detailed explanation

Mitigate first. If prompts are versioned and referenced by label or config, rollback is a one-line change. Because each trace records the prompt version, you can also see exactly which requests and users were affected and for how long.

Diagnose. Run old and new versions side by side on the evaluation set and on a sample of real affected traces. Look at diffs, not just aggregate scores. Typical mechanisms for "harmless" changes:

  • An added sentence ("be thorough") makes answers longer and buries the key fact.
  • Reordering instructions changes priority, so the grounding rule loses to a style rule.
  • A new example (few-shot) is copied too literally, or biases edge cases.
  • Rewording a format instruction changes JSON field names or breaks a parser.
  • A new caveat makes the model refuse or hedge more.
  • Moving content changes prompt caching and latency, a non-quality regression.

Fix. Design the new change against the observed failures, then re-run the full suite.

Prevent. Why did existing tests not catch it? Often the eval set lacked the affected segment, or there was no gate at all. So:

  • Add the failing cases to the regression suite.
  • Treat prompt changes like code: pull request review with sample output diffs.
  • CI evaluation gates with thresholds per metric and per segment that block merges.
  • Gradual rollout behind a flag (5% then 25% then 100%) with quality monitoring, so issues surface on a small share of traffic.
  • Version and trace every prompt in production.

How it works

  1. Roll back via label or flag.
  2. Identify affected traces by prompt version.
  3. Pairwise compare versions on evals and traces.
  4. Categorise regressions; fix prompt.
  5. Extend eval set; re-run; gated merge.
  6. Canary rollout with monitoring.

Example

# compare two prompt versions on the eval set with promptfoo
npx promptfoo eval -c evals/support.yaml \
  --prompts prompts/support_v13.txt prompts/support_v14.txt \
  --output results/v13_vs_v14.html

Common mistakes

  • Editing prompts directly in production.
  • Judging a prompt change by trying three questions manually.
  • Only an average score, hiding segment regressions.
  • Not adding the regression cases to the suite.

How to answer in the interview

"First I roll back to the previous version, which is quick when prompts are versioned and traced per request, and the traces show exactly which requests were affected. Then I compare both versions on the evaluation set and on real affected traces to see which cases regressed and why; small wording changes can make answers more verbose, shift instruction priority or reduce use of retrieved context. I fix against those failures and add them to the regression suite. To prevent it, prompt changes go through PR review, automated evals in CI that block regressions, and gradual rollout with quality monitoring."

Likely follow-up questions

  • Why didn't evals catch it? Missing segment coverage, too few cases, or no gating; fix the dataset.
  • Who may change prompts? Anyone via PR; production promotion via the release process.
  • Detect in production quickly? Online eval and feedback dashboards split by prompt version.
