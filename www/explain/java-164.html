What is test-driven development, and what are its benefits and limits?

Testing · concept · levels entry, mid

In one line

Test-driven development repeats a short red-green-refactor cycle: write a small failing test, write the simplest code to pass it, then refactor with the tests green; it improves design and gives a regression safety net, but adds overhead for exploratory and UI-heavy work.

Detailed explanation

TDD, popularised by Kent Beck, is a design technique as much as a testing technique. Writing the test first forces you to decide how the code will be called, what it returns and how it fails before you write it. Code written this way tends to have small units, clear interfaces and injected dependencies, because hard-to-test code is painful to write a test for first.

The cycle is deliberately small, often a few minutes:

  • Red: write one test for the next tiny behaviour and watch it fail. Seeing it fail proves the test can detect the missing behaviour.
  • Green: write the minimum code to pass, even if it is naive.
  • Refactor: clean up duplication and naming in both code and tests while everything stays green.

Benefits: high, meaningful coverage as a by-product; a regression safety net that makes refactoring safe; tests that document behaviour; fewer debugging sessions because failures are found seconds after they are introduced. It is especially effective for business rules, parsers, calculations and bug fixes: first reproduce the bug in a failing test, then fix it, so it cannot return.

Limits: for exploratory prototypes and spikes the design is not known yet, so tests would be rewritten constantly; UI layout and visual work are hard to specify as tests; some integration-heavy code is better driven by an outside-in acceptance test. Dogmatic TDD can produce many tiny tests coupled to implementation. TDD also does not replace integration, exploratory or performance testing.

How it works

  1. Pick the next small behaviour from the requirement.
  2. Write a test expressing it; run it and see it fail (red).
  3. Implement the simplest code that passes (green).
  4. Refactor code and tests; keep the suite green.
  5. Repeat, growing behaviour in small steps; commit often.

Example

// RED: written first
@Test
void ordersOver100GetTenPercentDiscount() {
    var calc = new DiscountCalculator();
    assertThat(calc.discountFor(new BigDecimal("150.00")))
        .isEqualByComparingTo("15.00");
}

@Test
void ordersOf100OrLessGetNoDiscount() {
    assertThat(new DiscountCalculator().discountFor(new BigDecimal("100.00")))
        .isEqualByComparingTo("0");
}

// GREEN: simplest implementation, then refactor
class DiscountCalculator {
    private static final BigDecimal THRESHOLD = new BigDecimal("100");
    BigDecimal discountFor(BigDecimal total) {
        return total.compareTo(THRESHOLD) > 0
            ? total.multiply(new BigDecimal("0.10")).setScale(2, RoundingMode.HALF_UP)
            : BigDecimal.ZERO;
    }
}

Common mistakes

  • Writing big tests covering many behaviours at once, losing the fast feedback loop.
  • Skipping the refactor step, so code stays naive and messy.
  • Never seeing the test fail, so it may not test anything.
  • Applying TDD to throwaway spikes and then keeping the spike code.

How to answer in the interview

"TDD is a red-green-refactor loop: I write a small failing test for the next behaviour, write the simplest code to make it pass, then refactor while the tests stay green. Writing the test first makes me design the API from the caller's side, so I get smaller units with injected dependencies, and I end up with a regression suite that lets me refactor confidently. It's less useful for exploratory prototypes or UI layout, and it costs time if applied dogmatically. I use it most for business logic and for bug fixes, where I always reproduce the bug in a failing test first."

Likely follow-up questions

  • How do you test code not designed for testing? Add characterisation tests around it, then introduce seams such as injected dependencies before changing it.
  • Does TDD mean 100% coverage? Coverage is high as a side effect, but the goal is behaviour, not a number.
  • Inside-out vs outside-in TDD? Inside-out starts from domain units; outside-in starts from an acceptance test and mocks downward.
