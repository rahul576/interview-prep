What are the four golden signals and the RED and USE methods?

Observability & SRE · concept · levels mid, senior

In one line

The four golden signals are latency, traffic, errors and saturation; the RED method (rate, errors, duration) applies them to request-driven services, and the USE method (utilisation, saturation, errors) to resources such as CPU, disks and pools.

Detailed explanation

These frameworks exist so that every team monitors a small, consistent set of metrics instead of hundreds of random graphs.

The golden signals come from Google's Site Reliability Engineering book. Latency is how long requests take; measure successful and failed requests separately, because a fast error is still an error. Traffic is demand, such as requests per second or messages per second. Errors is the rate of failed requests, including explicit failures (HTTP 5xx) and wrong answers (a 200 with bad content, or responses slower than a promised limit). Saturation is how full the most constrained resource is, ideally with a leading indicator that warns before it is 100%.

The RED method, coined by Tom Wilkie, is a simplified version for microservices: Rate, Errors, Duration. It fits every HTTP or gRPC service and makes dashboards uniform. The USE method, from Brendan Gregg, is for resources: for every CPU, disk, network interface, connection pool or queue, check Utilisation (percent busy), Saturation (queued work that cannot be served) and Errors. RED tells you users are hurting; USE helps explain which resource is the bottleneck.

Two practical rules follow. Latency should be shown as percentiles such as p95 and p99, since averages hide the slow requests users notice. And alerts should fire on user-facing symptoms (errors and latency against the SLO), while USE metrics mainly support diagnosis.

How it works

  1. Instrument every service with a request counter and a latency histogram labelled by route and status.
  2. Derive rate, error ratio and percentiles from them (RED).
  3. Collect resource metrics from node-exporter, cAdvisor and runtime exporters (USE).
  4. Put RED at the top of each dashboard, USE below.
  5. Alert on RED versus SLOs; use USE for capacity tickets.

Example

# Rate
sum(rate(http_requests_total{service="orders"}[5m]))
# Errors (ratio)
sum(rate(http_requests_total{service="orders",code=~"5.."}[5m]))
  / sum(rate(http_requests_total{service="orders"}[5m]))
# Duration p99
histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket{service="orders"}[5m])))

Common mistakes

  • Using average latency.
  • Mixing error latency into success latency, making things look faster.
  • Treating CPU utilisation as the only saturation metric.
  • Alerting on every USE metric, creating noise.

How to answer in the interview

"The four golden signals from the Google SRE book are latency, traffic, errors and saturation. RED is the service version: rate, errors and duration, which I'd put on top of every microservice dashboard. USE is for resources like CPU, disks and connection pools: utilisation, saturation and errors, which helps find the bottleneck. I always show latency as p95 and p99 percentiles, because averages hide slow users, and I alert on user-facing symptoms like error rate and latency against the SLO, keeping resource metrics mostly for diagnosis and capacity planning."

Likely follow-up questions

  • Good saturation metric for a Java service? Thread pool and connection pool usage, queue length, and GC pause time or heap after GC.
  • Why histograms instead of summaries in Prometheus? Histograms can be aggregated across instances.
  • Is traffic an alerting signal? Mostly not, but a sudden drop to zero is a useful symptom alert.
