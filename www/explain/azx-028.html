Compare Azure Functions hosting plans: Consumption, Flex Consumption, Premium and Dedicated.

Azure · concept · levels mid, senior

In one line

Consumption is pay-per-execution with scale to zero but cold starts and limited networking; Flex Consumption keeps serverless billing but adds VNet integration, always-ready instances, configurable memory and fast scaling and is Microsoft's recommended plan for new serverless apps; Premium (Elastic Premium) gives pre-warmed instances; Dedicated runs on an App Service plan.

Detailed explanation

Consumption (classic): you pay per execution and GB-second, with a monthly free grant, and the app scales to zero. The downsides are cold starts after idle periods, a default 5-minute and maximum 10-minute execution timeout, limited instance memory (1.5 GB), and no VNet integration. Microsoft has stopped adding features to the Linux Consumption plan and announced its retirement, steering Linux users to Flex.

Flex Consumption: the newer Linux-based serverless plan. It still scales to zero and bills per use, but adds VNet integration (outbound to private endpoints), always-ready instances you can set per function group to avoid cold starts (billed at a lower baseline rate), instance memory sizes (for example 2 GB or 4 GB), per-function scaling and much higher scale-out limits, plus longer execution times. For most new event-driven or HTTP apps it is the default choice.

Premium (Elastic Premium, EP1-EP3): you pay for running instances (at least one always on), with pre-warmed instances so scale-out doesn't hit cold starts, VNet integration, larger instances, longer (effectively unbounded for non-HTTP triggers) execution, and Windows support. Good for steady, latency-sensitive workloads that need Windows or features Flex lacks.

Dedicated (App Service plan): functions run on VMs you already pay for, scaling with plan rules. Useful when you have spare capacity, need predictable cost, or need App Service Environment isolation. Containerised functions can also run on Azure Container Apps.

Choose by latency tolerance (cold starts), networking (private resources), execution duration, OS, and cost profile (spiky vs steady).

How it works

  1. Spiky, tolerant, no VNet → Consumption or Flex.
  2. Needs VNet or low-latency serverless → Flex with always-ready instances.
  3. Steady load, Windows, specific features → Premium.
  4. Existing App Service capacity or ASE → Dedicated.
  5. Load test cold start and scale-out before committing.

Example

az functionapp create -g rg-orders -n func-orders --storage-account stfuncorders \
  --flexconsumption-location westeurope --runtime dotnet-isolated --runtime-version 8.0 \
  --instance-memory 2048
az functionapp scale config always-ready set -g rg-orders -n func-orders \
  --settings http=2

Common mistakes

  • Choosing Premium "for VNet" when Flex now covers it more cheaply.
  • Long-running work in Consumption that hits the timeout.
  • Ignoring the 230-second HTTP response limit on any plan.
  • Forgetting Always On in a Dedicated plan.

How to answer in the interview

"Consumption is pay per execution and scales to zero, great for sporadic work but with cold starts, short timeouts and no VNet. Flex Consumption is the newer serverless plan Microsoft recommends: still per-use billing and scale to zero, but with VNet integration, always-ready instances to avoid cold starts, choosable memory and fast scaling. Premium keeps pre-warmed instances and bills per instance, suiting steady latency-sensitive or Windows workloads. Dedicated runs on an existing App Service plan for predictable cost. I choose by latency, networking, run duration and cost."

Likely follow-up questions

  • Reduce cold starts? Always-ready or pre-warmed instances, smaller packages, avoid heavy startup work.
  • Long-running HTTP work? Return 202 and use Durable Functions or a queue.
  • Flex on Windows? Flex is Linux-only; Windows needs Premium or Dedicated.
