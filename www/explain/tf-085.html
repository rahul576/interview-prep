How would you implement subscription or account vending with Terraform for new application teams?

Terraform · design · levels senior, lead

In one line

Teams request a subscription or account through a pull request or portal with parameters; a vending module creates it in the right management group or OU, applies a baseline (network spoke, policies, budgets, logging, security), sets up identity (groups, role assignments), creates a pipeline identity with OIDC and a state backend, with one state per vended subscription.

Detailed explanation

Subscription vending (account vending on AWS) turns "please give us an environment" from a ticket that takes weeks into a reviewed, automated process that produces consistent, governed landing zones.

Request. A team opens a PR in a vending repository adding a small file, or a portal form generates it: team, application, environment, cost centre, network size, region, owners.

Create and place. On Azure, the module creates the subscription via the billing scope (with azurerm_subscription or Microsoft's lz-vending module) and moves it into the right management group, so Azure Policy assignments and guardrails apply from minute one. On AWS, an account is created with Organizations or Control Tower Account Factory for Terraform (AFT) and placed in the correct OU, inheriting SCPs.

Baseline. A network spoke peered to the hub with a CIDR from IPAM, routes through the firewall and DNS links; budgets and cost alerts; diagnostic settings or CloudTrail and Config sending logs centrally; Defender for Cloud or Security Hub enabled; mandatory tags.

Identity. Entra ID or IAM Identity Center groups for the team with role assignments, such as Reader for everyone and Contributor via just-in-time elevation. A pipeline identity (user-assigned managed identity or IAM role) with OIDC federated credentials for the team's repository and environments, so their pipelines have no secrets. A state backend (container or bucket prefix) for the team's own Terraform.

State per subscription. Each vended subscription has its own state so changing one team's subscription cannot affect others and plans stay small.

Day two. Baseline changes roll out as new module versions in waves across vended subscriptions.

How it works

  1. Team submits request file via PR; platform reviews.
  2. Pipeline creates a new state and runs the vending module.
  3. Subscription or account is created and placed in the hierarchy.
  4. Baseline: network, policies, budgets, logging, security.
  5. Identity: team groups, role assignments, OIDC pipeline identity, state backend.
  6. Outputs (IDs, CIDR, identity client ID) returned to the team.

Example

# vending/requests/orders-prod.tf  (one state per request)
module "lz_orders_prod" {
  source  = "Azure/lz-vending/azurerm"
  version = "~> 4.1"   # pin; illustrative

  subscription_alias_enabled = true
  subscription_billing_scope = var.billing_scope
  subscription_display_name  = "orders-prod"
  subscription_alias_name    = "orders-prod"
  subscription_workload      = "Production"
  subscription_management_group_id = "corp-prod"
  subscription_management_group_association_enabled = true

  # virtual network and role assignment inputs omitted for brevity
}

Common mistakes

  • One state containing every vended subscription.
  • Giving teams Owner, letting them remove guardrails.
  • Manual steps after vending (networking tickets) that defeat automation.
  • No plan for rolling baseline changes across hundreds of subscriptions.

How to answer in the interview

"A team requests a subscription or account through a PR to a vending repo or a portal that generates one, with team, environment, cost centre and network size. The vending module creates the subscription in the right management group, or the account in the right OU, so policies apply immediately. Then a baseline: a network spoke peered to the hub with a CIDR from IPAM, budgets, central logging and Defender or Security Hub. It creates team groups and role assignments, a pipeline identity with OIDC federation and a state backend for the team's own Terraform. Each vended subscription has its own state."

Likely follow-up questions

  • How do you change the baseline later? Release a new module version and roll it out in waves across subscription states.
  • What does AWS offer natively? Control Tower Account Factory for Terraform.
