When would you choose Azure Virtual WAN instead of a self-managed hub-and-spoke network?

Azure · design · levels senior, lead

In one line

Choose Azure Virtual WAN when you need Microsoft-managed hubs with automatic any-to-any transit across many branches, SD-WAN, VPN users, ExpressRoute and regions; choose a self-managed hub-and-spoke when you need fine-grained control over routing and custom NVAs, or have a small, single-region footprint.

Detailed explanation

In a classic hub-and-spoke, you build the hub VNet yourself: VPN and ExpressRoute gateways, Azure Firewall or an NVA, user-defined routes (UDRs) in every spoke, and peering. Spoke-to-spoke traffic needs routes through the firewall, and multi-region designs need you to connect hubs and maintain route tables. That gives full control but a lot of operational work as the network grows.

Virtual WAN turns the hub into a managed virtual hub with a built-in router. VNet connections, site-to-site VPN, point-to-site VPN and ExpressRoute gateways are attached to the hub, and routes are propagated automatically. In the Standard SKU, hubs in different regions are connected over the Microsoft backbone, giving any-to-any transit between branches, VNets and users. SD-WAN partners can connect branches automatically. With a secured hub (Azure Firewall inside the hub, managed by Firewall Manager) and routing intent, you declare that private and/or internet traffic goes through the firewall, instead of hand-writing route tables. Supported third-party NVAs and SaaS security can also be deployed into the hub.

The trade-off: the hub is a managed black box. You cannot put arbitrary VMs in it, some routing scenarios are constrained, and cost has a per-hub and per-connection component. For a handful of VNets in one region, classic hub-and-spoke (or Azure Virtual Network Manager to automate peering and connectivity) is often simpler and cheaper.

How it works

  1. Create a Virtual WAN (Standard) and a virtual hub per region.
  2. Connect spoke VNets to the hub.
  3. Add VPN, P2S and ExpressRoute gateways to hubs; connect branches or SD-WAN devices.
  4. Deploy Azure Firewall in the hub (secured hub) and enable routing intent.
  5. Hubs interconnect automatically; routes propagate to all connections.
  6. Monitor with Network Insights and firewall logs.

Example

A retailer has 300 stores on an SD-WAN, 2,000 remote staff on VPN, ExpressRoute from two data centres and workloads in West Europe and North Europe. With Virtual WAN, each region gets a secured hub; the SD-WAN controller registers stores automatically, and routing intent forces all private and internet traffic through Azure Firewall:

resource ri 'Microsoft.Network/virtualHubs/routingIntent@2023-09-01' = {
  parent: hubWeu
  name: 'ri-weu'
  properties: {
    routingPolicies: [
      { name: 'PrivateTraffic',  destinations: [ 'PrivateTraffic' ],  nextHop: firewall.id }
      { name: 'InternetTraffic', destinations: [ 'Internet' ],        nextHop: firewall.id }
    ]
  }
}

A start-up with three VNets in one region would instead peer them to a simple hub with Azure Firewall and a couple of UDRs.

Common mistakes

  • Picking Virtual WAN for two VNets in one region.
  • Not checking that your chosen NVA vendor is supported in the hub.
  • Forgetting that custom route tables and routing intent interact and need design.
  • Underestimating per-hub and data processing costs.

How to answer in the interview

"Virtual WAN gives me Microsoft-managed hubs where routing and gateways are run for me. I'd choose it for an organisation with many branches over SD-WAN or VPN, remote users, ExpressRoute and several regions, because it provides any-to-any transit automatically and hub-to-hub connectivity. Secured hubs with routing intent send traffic through Azure Firewall by policy. If we only have a few VNets in one region, or need custom NVAs and detailed route control, I'd stay with a self-managed hub-and-spoke, possibly automated with Virtual Network Manager."

Likely follow-up questions

  • What limitations would you check? Supported NVAs, routing intent constraints, hub capacity, regional availability and cost.
  • Can you migrate later? Yes, but re-pointing spokes and gateways is a planned project with downtime windows.
  • Basic vs Standard? Basic supports only site-to-site VPN; Standard gives full transit.
