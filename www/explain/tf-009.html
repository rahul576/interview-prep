When do you need depends_on in Terraform, and what are its drawbacks?

Terraform · concept · levels entry, mid, senior

In one line

Terraform infers dependencies from references; depends_on is only for hidden dependencies not visible in arguments, and it should be used sparingly because it is coarse, and on modules and data sources it makes values unknown until apply, producing noisy, conservative plans.

Detailed explanation

Terraform builds a dependency graph from expressions. If a subnet sets vpc_id = aws_vpc.main.id, the subnet depends on the VPC, so it is created after and destroyed before it. This implicit dependency covers the vast majority of cases and is precise: it links exactly the objects involved.

Sometimes a real dependency exists but no attribute expresses it. The classic example is IAM: a Lambda function or ECS service references a role ARN, but its permissions come from a separate aws_iam_role_policy_attachment. Terraform may create the function before the policy is attached, and the first invocation or startup fails with access denied. Other examples are an application that needs a database firewall rule or private endpoint to exist, or a VM that must wait for a NAT gateway before its bootstrap script downloads packages. Here depends_on = [aws_iam_role_policy_attachment.lambda_logs] tells Terraform about the hidden ordering.

The drawbacks are real. depends_on is coarse: on a module, every resource and data source in the module depends on everything in the list, which serialises work and can widen what gets replaced. On data sources, or data sources inside a module with depends_on, Terraform must defer reading until apply whenever the dependency has pending changes, so their results are "known after apply". Anything derived from them becomes unknown too, which can show unnecessary updates or replacements and perpetual diffs in plans. It also hides intent: a future reader does not know why it is there.

So prefer expressing the dependency through data: pass an attribute (for example output the policy attachment ID or a combined value) into the dependent resource or module. When depends_on is truly needed, put it on the narrowest resource and add a comment.

How it works

  1. Terraform parses references and builds the graph.
  2. depends_on adds explicit edges to the listed objects.
  3. During plan, data sources with dependencies on pending changes are deferred to apply.
  4. Apply follows the graph order, parallelising independent nodes.

Example

resource "aws_iam_role_policy_attachment" "logs" {
  role       = aws_iam_role.lambda.name
  policy_arn = "arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole"
}

resource "aws_lambda_function" "api" {
  function_name = "orders-api"
  role          = aws_iam_role.lambda.arn
  handler       = "app.handler"
  runtime       = "python3.12"
  filename      = "build/app.zip"

  # The role ARN is referenced, but the attached policy is not.
  depends_on = [aws_iam_role_policy_attachment.logs]
}

Common mistakes

  • Adding depends_on everywhere "to be safe".
  • Putting depends_on on whole modules.
  • Using it on data sources and then wondering why plans always show changes.
  • No comment explaining the hidden dependency.

How to answer in the interview

"Terraform normally builds the dependency graph from references: if a subnet uses the VPC ID, it waits for the VPC. I only need depends_on for hidden dependencies that aren't visible in arguments, like a Lambda that references its role but needs the policy attachment to exist before it runs. The drawbacks are that it's coarse: on a module it makes everything inside depend on everything listed, and on data sources it delays reading them to apply time, so values become unknown and plans show unnecessary changes or replacements. So I use it sparingly, on the narrowest resource, prefer passing an attribute that expresses the dependency, and add a comment."

Likely follow-up questions

  • Why might depends_on on a module cause perpetual diffs? Data sources inside are deferred to apply whenever dependencies change, making derived values unknown.
  • Does depends_on affect destroy order? Yes, dependents are destroyed first.
  • Alternative to depends_on for modules? Pass an output from the dependency as an input the module actually uses.
