How do HCP Terraform workspaces, variable sets and run triggers work compared with the open source CLI?

Terraform · concept · levels mid, senior

In one line

An HCP Terraform workspace holds the state, variables, credentials, settings and run history for one configuration and environment, runs execute remotely through VCS-, CLI- or API-driven workflows, variable sets share variables across workspaces, and run triggers chain workspaces when an upstream one applies.

Detailed explanation

In the open source CLI, a workspace is just an extra named state in the same backend (terraform workspace new dev). Everything else, variables, credentials, history, approvals, lives in your CI system. In HCP Terraform (formerly Terraform Cloud) and Terraform Enterprise, a workspace is a first-class object: it stores state versions, Terraform and environment variables (with sensitive flags), the Terraform version, execution mode, team permissions, notifications and every run with its plan and apply logs.

Runs are started in three ways. VCS-driven: the workspace is linked to a repository; pull requests create speculative plans shown as checks, merges to the tracked branch queue a run. CLI-driven: developers run terraform plan locally with the cloud block, and the plan executes remotely while output streams back. API-driven: other pipelines upload a configuration version and create runs through the API.

Variable sets define variables or cloud credentials once and apply them to the whole organisation, selected projects or specific workspaces. Run triggers connect workspaces: when the network workspace applies successfully, dependent workspaces like aks-cluster automatically queue a plan, so changes flow downstream.

On top come policy checks with Sentinel or OPA, approval steps, dynamic provider credentials via OIDC, health assessments for drift detection, private registry, audit logs and team RBAC.

How it works

  1. Create a project and workspaces per configuration and environment.
  2. Connect VCS or use the cloud block for CLI-driven runs.
  3. Attach variable sets for shared credentials and settings.
  4. A run plans remotely, then policy checks evaluate the plan.
  5. Approval (or auto-apply) triggers apply; state is versioned.
  6. Run triggers queue plans in downstream workspaces.

Example

terraform {
  cloud {
    organization = "acme"
    workspaces {
      name    = "orders-prod"
      project = "orders"
    }
  }
}
terraform login
terraform plan    # executes remotely, output streams locally

Common mistakes

  • Treating HCP workspaces like CLI workspaces and putting all environments in one configuration with no separation of access.
  • Duplicating credentials per workspace instead of variable sets or dynamic credentials.
  • Forgetting that remote runs cannot reach private endpoints without agents.

How to answer in the interview

"In HCP Terraform a workspace is much more than a CLI workspace: it holds state, variables, credentials, settings and the full run history for one configuration and environment. Runs execute remotely: VCS-driven from pull requests and merges, CLI-driven where my local plan streams from a remote run, or API-driven from other pipelines. Variable sets share variables or credentials across workspaces or projects, and run triggers chain workspaces, so when the network applies, the cluster workspace plans automatically. Policies, approvals, permissions, drift detection and audit come built in."

Likely follow-up questions

  • When are self-hosted agents required? When runs must reach private networks or on-premises systems.
  • What are speculative plans? Plan-only runs for PRs that can never be applied.
  • How are credentials best handled? Dynamic provider credentials with OIDC, no static secrets.
