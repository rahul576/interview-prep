Your LLM bill tripled overnight without a matching traffic increase. How do you investigate?

LLMOps & RAG · scenario · levels mid, senior

In one line

Break down cost by application, model, feature and API key, then check tokens per request over time; common causes are agent loops or retry storms, prompt or context growth and prompt-cache misses, a switch to a pricier model or reasoning mode, batch work on real-time APIs, or abuse and leaked keys; fix it and add budgets, per-key limits and alerts.

Detailed explanation

If traffic did not change, cost per request did, or the number of model calls per user action did. Find where before guessing why.

Break down. Use the gateway's usage data or the provider's usage and cost reports, grouped by project, API key, model, and if available feature tag. Usually one line item jumped.

Check tokens and calls. Compare input tokens, output tokens, cached tokens and calls per request before and after the jump.

Typical causes:

  • Agent loops or retry storms. An agent failing to finish a task keeps calling tools and the model; or an upstream outage triggers retries without limits, multiplying calls.
  • Prompt changes. A new instruction block, more retrieved chunks, full conversation history instead of a summary, or large tool results pasted back into the context.
  • Prompt cache misses. Someone moved a timestamp, user ID or other variable content to the beginning of the prompt, so the cached prefix no longer matches and every token is billed at full price.
  • Model routing changes. Config now sends traffic to a frontier model, or a reasoning mode was enabled, generating many billed reasoning tokens.
  • Batch jobs. An offline job accidentally runs on the real-time API, or reprocesses the full dataset every night because a checkpoint broke.
  • Abuse. A leaked API key in a public repository or front-end bundle, or bots scraping a public chatbot.

Fix and prevent. Fix the cause (roll back prompt, rotate keys, fix loop limits), then add daily and hourly budget alerts, per-key and per-user quotas, max steps and tokens per task for agents, and dashboards of cost per request and calls per user action.

How it works

  1. Group cost by key, model, feature, hour.
  2. Identify the jump's start time; correlate with deployments.
  3. Compare tokens and calls per request before/after.
  4. Check cache hit rate, model mix, reasoning token counts.
  5. Check for anomalous callers (new IPs, unusual hours).
  6. Fix; add alerts and limits.

Example

SELECT date_trunc('hour', ts) AS hour, feature, model,
       count(*) AS calls,
       avg(input_tokens) AS avg_in, avg(cached_tokens) AS avg_cached,
       avg(output_tokens) AS avg_out, sum(cost_usd) AS cost
FROM llm_usage
WHERE ts > now() - interval '3 days'
GROUP BY 1, 2, 3
ORDER BY cost DESC
LIMIT 20;

Common mistakes

  • No per-feature attribution, so the bill is one number.
  • Agents without step or token limits.
  • API keys embedded in mobile or web clients.
  • Only monthly budget alerts.

How to answer in the interview

"I'd break the cost down by application, model, feature and API key through the gateway or provider reports, which normally points to one source, then compare tokens and calls per request before and after. Typical causes are an agent loop or retry storm, a prompt change that added context or broke prompt caching by putting variable content first, a config change to a pricier model or reasoning mode, a batch job running on the real-time API, or abuse through a leaked key. I'd fix the cause, rotate keys if needed, and add hourly budget alerts, per-key quotas and step limits so it's caught within hours."

Likely follow-up questions

  • Alert catching it in an hour? Hourly cost or tokens-per-request anomaly alert per feature.
  • Preventing key leaks? Keys only server-side, secret scanning, short-lived credentials via the gateway.
  • Agent budgets? Max steps, max tokens and wall time per task.
