Estimate how many GPUs you need to serve an internal assistant for 2,000 daily users on a self-hosted 70B model.

LLMOps & RAG · scenario · levels senior, lead

In one line

Work it out from assumptions: convert 2,000 daily users into peak concurrent requests, estimate input and output tokens per request, note a 70B model needs about 140 GB in BF16 (two 80 GB GPUs with tensor parallelism, or fewer with quantisation, plus KV cache room), benchmark one replica under latency SLOs, then divide peak load by replica capacity and add headroom and redundancy, validated with load tests.

Detailed explanation

Interviewers care about the method and stated assumptions more than the final number.

Users to load. 2,000 daily users; assume 30% active in the busiest hour (600 users), each sending about 10 requests that hour: 6,000 requests per peak hour, about 1.7 requests/second. Bursts within the hour might be 2-3x, so plan for about 4-5 requests/second.

Tokens. Assume 3,000 input tokens (system prompt, RAG context, history) and 400 output tokens per request. At 1.7 req/s that is about 5,000 input tokens/s (prefill) and 700 output tokens/s (decode); at burst roughly 15,000 and 2,000.

Memory. 70B parameters x 2 bytes (BF16) is about 140 GB of weights. Two 80 GB GPUs (H100/A100 80GB) with tensor parallelism give 160 GB total, leaving little for KV cache, which limits concurrency, so many deployments use 4 GPUs per replica in BF16, or FP8 (about 70 GB, supported on Hopper-class GPUs) on 2 GPUs, or 4-bit AWQ/GPTQ (about 35-40 GB) on a single 80 GB GPU, if evaluations show acceptable quality. KV cache per token for a Llama-70B-class model with grouped-query attention is roughly 0.3 MB in 16-bit, so 32 concurrent sequences of 4,000 tokens need around 40 GB.

Benchmark. Run vLLM on one replica with realistic prompts and a load generator, increasing concurrency until TTFT (for example p95 under 2 s) or inter-token latency (for example under 50 ms per token) SLOs break. Suppose an FP8 replica on 2 GPUs sustains about 2 requests/s within SLOs.

Count. Peak 1.7 req/s, burst about 4-5 req/s, divided by 2 req/s per replica: about 3 replicas for bursts, plus one for redundancy and maintenance: 4 replicas, around 8 GPUs in this scenario. With 4-bit on single GPUs, perhaps 4-5 GPUs; in BF16 on 4-GPU replicas, more. Then load test with real traffic patterns and adjust.

How it works

  1. Users -> peak requests per second (with burst factor).
  2. Requests -> input/output tokens per second.
  3. Model precision -> GPU memory per replica including KV cache.
  4. Benchmark replica throughput under SLOs.
  5. Replicas = burst load / capacity, plus N+1 redundancy.
  6. Validate with load tests; monitor and revise.

Example

Peak hour: 2,000 x 30% x 10 = 6,000 req/h = 1.7 req/s (burst ~4.5 req/s)
Tokens/s:  input 3,000 x 1.7 = 5,100 ; output 400 x 1.7 = 680
Weights:   70B x 2 B = 140 GB (BF16) | ~70 GB (FP8) | ~38 GB (4-bit)
Replica:   FP8 on 2 x 80 GB GPUs, benchmarked ~2 req/s at p95 TTFT < 2 s
Replicas:  ceil(4.5 / 2) = 3, +1 redundancy = 4 replicas = 8 GPUs

Common mistakes

  • Dividing daily requests by 86,400 instead of planning for peak.
  • Forgetting KV cache memory and only counting weights.
  • Assuming quantisation is free without evaluating quality.
  • No redundancy for failures or upgrades.

How to answer in the interview

"I'd state assumptions and work through it. 2,000 daily users, maybe 30 percent active in the peak hour with ten requests each, is 6,000 requests an hour, under two per second, with bursts maybe to four or five. With 3,000 input and 400 output tokens, that's around 5,000 prefill and 700 decode tokens per second at peak. A 70B model is about 140 GB in BF16, so it needs multiple 80 GB GPUs with tensor parallelism, or FP8 or 4-bit quantisation if quality holds, plus KV cache room. Then I'd benchmark one vLLM replica against TTFT and per-token SLOs, divide burst load by its capacity, add a redundant replica, and validate with load tests. Here that's maybe four replicas, around eight GPUs."

Likely follow-up questions

  • Agent with five calls per request? Roughly 5x requests and growing context per call; recompute, consider smaller models for sub-steps.
  • Longer contexts? Prefill and KV cache grow, reducing concurrency per replica.
  • Cheaper option? Smaller model or MoE model for most traffic, 70B only for hard cases.
