Your remote MCP server works with one replica but fails intermittently behind a load balancer with several replicas. Diagnose it.

MCP Servers · scenario · levels mid, senior

In one line

Intermittent failures that vanish with one replica mean state is held in memory on one instance: an Mcp-Session-Id (or SSE stream, handle, task ID) created on replica A is sent to replica B, which does not know it; short term use sticky sessions, properly fix it with external state and the stateless protocol revision.

Detailed explanation

The symptom pattern is the diagnosis. Works with one replica, fails sometimes with several, and failure rate grows with replica count: requests are landing on instances that lack state they depend on.

With handshake-based protocol revisions (such as 2025-06-18 and 2025-11-25 Streamable HTTP), the client sends initialize, and the server may return an Mcp-Session-Id header. Many SDK defaults keep the session object, negotiated capabilities, subscriptions and open SSE streams in process memory. The client then sends every later request with that session ID. The load balancer, knowing nothing about MCP sessions, round-robins request two to replica B. Replica B has never heard of the session and returns an error such as 404 / session not found, or a resumed SSE stream breaks. With three replicas, roughly two out of three follow-up requests miss.

The same bug appears with handles, pagination cursors, task IDs for long-running operations, or caches of downstream OAuth tokens stored in local memory.

Short-term fix: sticky sessions at the load balancer keyed on the Mcp-Session-Id header (or a cookie). This reduces failures but breaks on scale-in, restarts and deployments, when a replica disappears with its sessions.

Real fix: move all state to an external store such as Redis or a database, so any replica can load it, and adopt the stateless 2026-07-28 revision, where requests carry what they need and no session is required. Then plain load balancing works.

How it works

  1. Reproduce: run 3 replicas locally behind a round-robin proxy; run an integration test that initialises and calls several tools.
  2. Check logs for session-not-found or unknown task errors correlated with replica IDs.
  3. Confirm by enabling sticky routing; failures should drop.
  4. Refactor: session, task and handle stores backed by Redis.
  5. Upgrade SDK and transport to the stateless revision; remove stickiness.

Example

POST /mcp  initialize              -> replica A   (Mcp-Session-Id: 7f3e...)
POST /mcp  tools/call search       -> replica B   404 Session not found
POST /mcp  tools/call search       -> replica A   200 OK
# before: sessions = {}            # per-process memory
# after:
sessions = RedisSessionStore(url=REDIS_URL, ttl_seconds=3600)
tasks = RedisTaskStore(url=REDIS_URL)

Common mistakes

  • Adding retries, which hides the problem and multiplies load.
  • Sticky sessions as the permanent solution.
  • Testing only with one replica in staging.
  • Forgetting that in-memory task IDs are lost on every deployment.

How to answer in the interview

"Failures that disappear with one replica almost always mean in-memory state. With handshake-based revisions, the server assigns an Mcp-Session-Id at initialization and keeps session data, capabilities, subscriptions or open SSE streams, in that replica's memory. When the load balancer sends the next request with that ID to a different replica, the session is unknown, so it fails with session not found or the stream breaks. Handles or task IDs in local memory cause the same thing. Short term, sticky sessions on the session header reduce it, though they fail on scaling and restarts. The real fix is external state in something like Redis, and moving to the stateless 2026-07-28 revision."

Likely follow-up questions

  • Test before production? Integration tests against multiple replicas behind a round-robin proxy, plus chaos tests killing replicas.
  • Why do sticky sessions fail? A removed replica takes its sessions with it.
  • What state is legitimate? Durable tasks, idempotency keys and tokens, all stored externally.
