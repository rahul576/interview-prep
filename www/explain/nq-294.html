What is a Jenkins pipeline script written in Groovy?

DevOps & CI/CD · concept · levels mid

In one line

Jenkinsfiles use a Groovy-based DSL in two flavours: scripted pipelines (node { stage { } }, full Groovy flexibility) and declarative pipelines (pipeline { agent; stages { } }, a validated structure), with script { } blocks and shared libraries for custom logic, all running in a Groovy sandbox with script approval.

Detailed explanation

Scripted pipeline: the original style. It is essentially Groovy code executed by the pipeline engine: you can use variables, loops, conditionals, try/catch and functions anywhere. Very powerful for unusual flows, but large scripted pipelines become hard to read, test and maintain, and errors appear only at runtime.

Declarative pipeline: introduced later and now recommended for most teams. It enforces a fixed structure (pipeline, agent, stages, steps, post, when, options, parameters) that Jenkins validates before running, gives better Blue Ocean and stage views, and supports features like when conditions and restart from a stage. When logic is needed, a script { } block allows Groovy inside a step.

Shared libraries: reusable code stored in a separate Git repository with a standard layout:

  • vars/ global steps, e.g. vars/mavenBuild.groovy with a call() method, used as mavenBuild().
  • src/ Groovy classes in packages.
  • resources/ non-Groovy files such as templates.

Loaded with @Library('ci-lib@v2') _, they let 50 repositories share one tested pipeline definition.

CPS and serialisation: pipeline code is transformed so builds can survive controller restarts; some Groovy features (certain closures, non-serialisable objects) behave differently, and @NonCPS marks helper methods that run normally.

Security: untrusted pipeline code runs in the Groovy sandbox; calls to methods not on the allow-list need administrator script approval. Trusted global libraries run outside the sandbox, so access to them must be controlled.

How it works

  1. Jenkins reads the Jenkinsfile from SCM.
  2. Declarative syntax is validated; scripted code is compiled.
  3. Shared libraries are loaded at the requested version.
  4. The CPS engine executes steps, checkpointing state.
  5. Sandbox checks every method call against the allow-list.

Example

// Scripted
node('maven') {
  stage('Build') { sh './mvnw -B package' }
  if (env.BRANCH_NAME == 'main') { stage('Deploy') { sh './deploy.sh dev' } }
}

// Declarative using a shared library step
@Library('ci-lib@v2') _
pipeline {
  agent any
  stages {
    stage('Build') { steps { mavenBuild(goals: 'verify') } }
    stage('Tag')   { steps { script { env.VERSION = readMavenPom().version } } }
  }
}

Common mistakes

  • Putting large Groovy programs in script {} blocks instead of a library.
  • Approving dangerous scripts just to make a build pass.
  • Unversioned shared libraries (@master) breaking all pipelines at once.

How to answer in the interview

"Jenkinsfiles are written in a Groovy-based DSL with two flavours. Scripted pipelines, starting with node and stage blocks, are plain Groovy with loops, conditions and functions, very flexible but harder to maintain. Declarative pipelines, starting with pipeline, agent and stages, have a fixed structure that Jenkins validates, and you use script blocks when you need Groovy logic. Reusable logic goes into shared libraries under vars and src, versioned and loaded with @Library. For security, Groovy runs in a sandbox and non-approved methods need admin script approval."

Likely follow-up questions

  • Share pipeline code across 50 repos? A versioned shared library with a standard pipeline step each repo calls.
  • What is @NonCPS? Marks a method to run outside the CPS transformation.
  • How do you test shared libraries? JenkinsPipelineUnit tests and a sandbox Jenkins.
