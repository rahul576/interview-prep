You must upgrade the Terraform version used by 200 workspaces. How do you plan it?

Terraform · scenario · levels senior, lead

In one line

Treat it as a fleet rollout: inventory versions and constraints, read the release notes for every version in between, pilot on non-production workspaces, let automation open PRs that bump required_version and the runner image and run plans, require clean plans, and roll out in waves with rollback available.

Detailed explanation

Terraform 1.x comes with compatibility promises: configurations and state written for an earlier 1.x version keep working on later 1.x versions. That makes upgrades much safer than in the 0.x era, but not risk-free. New versions can add stricter validation that turns sloppy code into errors, deprecate features, change behaviour in edge cases, and require newer provider protocol versions. Also, once a workspace is applied with a newer Terraform, its state is written by that version, and older binaries may refuse to work with it, so rollback must be planned.

Inventory first. For 200 workspaces you need data: the current Terraform version per workspace (from HCP Terraform settings, pipeline images or terraform_version in state), each required_version constraint, and the pipeline or runner image. Group them by version and owning team.

Read release notes for every minor version between current and target, noting upgrade notes and deprecations. Then pilot on a handful of representative non-production workspaces, including the most complex ones, with full plan and apply.

Automate the change. A script or Renovate opens a PR per workspace that updates required_version and the runner image or workspace setting, and CI runs a plan. The merge rule: the plan must be clean, meaning no changes, or only changes explained by the release notes.

Waves: non-production first, then production in groups, with a pause between. Keep the old version available in images until everything has moved. A version manager (tfenv, tenv, mise) keeps laptops aligned.

How it works

  1. Inventory versions, constraints, images and owners.
  2. Read release and upgrade notes for all intermediate versions.
  3. Pilot on representative non-production workspaces.
  4. Automation opens PRs per workspace and runs plans.
  5. Merge only clean plans; non-production first, production in waves.
  6. Retire the old version once all workspaces have moved.

Example

terraform {
  required_version = "~> 1.14.0"   # was ~> 1.9.0
}
# .terraform-version used by tenv / tfenv on developer machines
echo "1.14.0" > .terraform-version

# Inventory from state files in a bucket (illustrative)
for f in $(aws s3 ls s3://tfstate-prod --recursive | awk '{print $4}'); do
  aws s3 cp "s3://tfstate-prod/$f" - | jq -r --arg f "$f" '"\($f) \(.terraform_version)"'
done

Common mistakes

  • Big-bang upgrading all workspaces at once.
  • Mixing a Terraform upgrade with provider upgrades in the same PR.
  • Upgrading a developer's local binary first and writing state with a newer version than CI.
  • Ignoring warnings in pilot plans.

How to answer in the interview

"I start with an inventory: which Terraform version each workspace uses, its required_version constraint and its pipeline image. Terraform 1.x has strong compatibility promises, but I still read the release notes for every version in between for deprecations and new validation errors. Then I pilot on representative non-production workspaces. Automation opens PRs that bump required_version and the image per workspace and runs a plan, and the rule is the plan must be clean. Rollout goes in waves, non-production first, then production groups, with old versions available for rollback and a version manager for developer machines."

Likely follow-up questions

  • Why not share state between versions during rollout? A newer version may write state that older binaries refuse to read.
  • How do you handle HCP Terraform workspaces? Update the workspace Terraform version setting via the API or the tfe provider.
  • Do providers need upgrading too? Separately, in their own PRs, to isolate changes.
