How does the Azure Key Vault provider for the Secrets Store CSI driver work on AKS?

Azure Kubernetes (AKS) · concept · levels mid, senior

In one line

The Key Vault secrets provider add-on installs the Secrets Store CSI driver and Azure provider; a SecretProviderClass says which secrets to fetch with which workload identity, pods mount them as files at start, and optionally they are synced to Kubernetes Secrets and rotated by polling.

Detailed explanation

Storing secrets in Git or creating Kubernetes Secrets by hand spreads sensitive values and makes rotation hard. With the CSI driver, Key Vault stays the source of truth.

Enabling the add-on deploys two DaemonSets on every node: the generic Secrets Store CSI driver and the Azure Key Vault provider. In each namespace you create a SecretProviderClass with provider: azure, the vault name, tenant ID, the client ID of a workload identity and a list of objects (secrets, keys or certificates, optionally with versions).

A pod references the class in a CSI volume. When the kubelet mounts the volume, the driver calls the provider, which authenticates to Entra ID using the pod's federated service account token and fetches the values. They are written to a tmpfs mount inside the container, for example /mnt/secrets/db-password. If fetching fails, the pod does not start, which surfaces misconfiguration immediately.

Sync to Kubernetes Secrets via secretObjects is optional and useful for environment variables or ingress TLS certificates, but the synced Secret only exists while at least one pod mounts the volume, and it lives in etcd (encrypted at rest, but readable to anyone with Secret read access).

Rotation: with --enable-secret-rotation, the driver polls Key Vault (default every two minutes) and updates mounted files and synced Secrets. Applications must re-read files or be restarted (for example with Reloader); environment variables never change in a running process.

How it works

  1. Enable the add-on with rotation.
  2. Create a user-assigned identity, federate it with the service account, grant Key Vault Secrets User.
  3. Create the SecretProviderClass in the namespace.
  4. Mount the CSI volume in the pod spec.
  5. The driver fetches and mounts secrets at pod start and refreshes them when rotation is enabled.

Example

apiVersion: secrets-store.csi.x-k8s.io/v1
kind: SecretProviderClass
metadata: { name: orders-kv, namespace: orders }
spec:
  provider: azure
  parameters:
    clientID: "<workload-identity-client-id>"
    keyvaultName: kv-orders-prod
    tenantId: "<tenant-id>"
    objects: |
      array:
        - |
          objectName: db-password
          objectType: secret
---
# in the pod spec (serviceAccountName must be the federated account)
volumes:
- name: secrets
  csi:
    driver: secrets-store.csi.k8s.io
    readOnly: true
    volumeAttributes: { secretProviderClass: orders-kv }

Common mistakes

  • Expecting environment variables from synced Secrets to update on rotation.
  • Granting the kubelet identity Key Vault access instead of a per-app workload identity.
  • Forgetting that a synced Secret disappears when no pod mounts the volume.
  • Using Key Vault access policies inconsistently instead of Azure RBAC.

How to answer in the interview

"The add-on installs the Secrets Store CSI driver and Azure provider as DaemonSets. In each namespace I define a SecretProviderClass naming the vault, the secrets and the workload identity to use. Pods mount it as a CSI volume, so at start the driver fetches values from Key Vault and writes them as files, and nothing is stored in Git. Optionally it syncs into Kubernetes Secrets for env vars or TLS. With rotation enabled it polls Key Vault and updates files, but the app has to reload them."

Likely follow-up questions

  • Compared with External Secrets Operator? ESO syncs into Kubernetes Secrets from many backends without mounting; CSI avoids etcd copies.
  • How do apps pick up rotated secrets? Watch files, reload periodically, or restart via Reloader.
  • Which identity is used? A per-application workload identity, not the node identity.
