What are MCP tool annotations, and can a client trust them?

MCP Servers · concept · levels mid, senior

In one line

Tool annotations are optional behaviour hints, readOnlyHint, destructiveHint, idempotentHint and openWorldHint, that hosts use for approval and UI decisions; clients must treat them as untrusted unless the server is trusted, so real security comes from host policy.

Detailed explanation

Annotations were introduced in the 2025-03-26 revision to describe how a tool behaves without changing what it does:

  • readOnlyHint: the tool does not modify its environment. Default false.
  • destructiveHint: if not read-only, the tool may perform destructive updates (deleting, overwriting) rather than only additive ones. Default true.
  • idempotentHint: calling repeatedly with the same arguments has no additional effect. Default false.
  • openWorldHint: the tool interacts with an open set of external entities (e.g. web search, sending emails) rather than a closed domain like a local database. Default true.
  • An annotation title for display.

Note the conservative defaults: a tool with no annotations is assumed to be potentially destructive, non-idempotent and open-world.

Hosts use these hints for user experience: auto-approving read-only tools, showing a strong confirmation for destructive ones, or grouping tools in the UI. That is genuinely useful because it reduces approval fatigue.

However, the specification is explicit that clients must consider annotations untrusted unless they come from a trusted server. A malicious or compromised server can label delete_all_files as readOnlyHint: true. Even an honest server can be wrong after a code change. Therefore security decisions rely on host policy: allowlists per server and per tool, user approval for anything with side effects, sandboxing, and least-privilege credentials on the server side so that even a misbehaving tool cannot do much damage. Annotations become one additional signal inside that policy, trusted only for servers your organisation has vetted.

How it works

  1. Server includes annotations in each tool definition.
  2. Host receives definitions via tools/list.
  3. Host looks up its policy for this server: trusted or not.
  4. For trusted servers, hints may drive auto-approval of read-only tools.
  5. For untrusted servers, every side-effecting or unknown tool requires explicit approval regardless of hints.

Example

{
  "name": "delete_branch",
  "description": "Delete a Git branch in the given repository.",
  "inputSchema": { "type": "object",
    "properties": { "repo": {"type": "string"}, "branch": {"type": "string"} },
    "required": ["repo", "branch"] },
  "annotations": { "title": "Delete branch", "readOnlyHint": false,
                   "destructiveHint": true, "idempotentHint": true, "openWorldHint": false }
}
# host policy (illustrative)
servers:
  internal-git: { trusted: true,  auto_approve: readOnlyHint }
  community-x:  { trusted: false, auto_approve: none, allowed_tools: [search, read_file] }

Common mistakes

  • Auto-approving any tool that claims to be read-only.
  • Omitting annotations on genuinely safe tools, causing approval fatigue.
  • Setting destructiveHint: false on tools that overwrite data.
  • Treating annotations as access control instead of hints.

How to answer in the interview

"Annotations are optional hints: readOnlyHint says the tool doesn't modify anything, destructiveHint that it may delete or overwrite, idempotentHint that repeating it has no extra effect, and openWorldHint that it talks to external entities like the web. Hosts use them for UX, like auto-approving read-only tools and confirming destructive ones. But the spec says clients must treat them as untrusted unless the server is trusted, because a malicious server can simply lie. So real security comes from host policy: per-server and per-tool allowlists, approval for side effects, and least-privilege credentials. Annotations are just an extra signal."

Likely follow-up questions

  • Which tools may be auto-approved? Read-only tools from vetted internal servers, with scoped credentials and audit logging.
  • What are the defaults? Not read-only, destructive, non-idempotent, open-world: conservative.
  • Can annotations change? Yes, so hosts may re-check or re-approve when definitions change.
