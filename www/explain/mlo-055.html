How do you monitor ML data and training pipelines, beyond whether jobs succeeded?

MLOps · concept · levels mid, senior

In one line

Monitor outcomes, not just job status: freshness SLAs per dataset, row counts and volume anomalies, data quality results over time, duration and resource trends, and lineage (for example OpenLineage) to know which models are affected, with alerts routed to owners with context.

Detailed explanation

A green job can still produce bad data: it ran on an empty input, processed yesterday's file again, or wrote half the rows. Monitoring has to answer "is the data right and on time?".

Freshness. Each important dataset and feature table has an SLA, such as "updated by 06:00 IST", and an alert fires when it is late, whether or not any job failed. Stale features silently degrade online predictions.

Volume. Row counts, partition sizes and distinct key counts compared with history (same weekday, recent average) catch silently missing data, such as a source that sent half its records, or duplicated loads.

Quality over time. Results of validation checks—null rates, range violations, distribution shifts—are stored and charted, so slow degradation is visible, not just pass or fail.

Performance trends. Pipeline duration, queue time and resource usage trends reveal growing data or inefficient code before they cause a missed deadline or a cost spike.

Lineage. Tools emitting OpenLineage events (Airflow, Spark, dbt integrations, with backends like Marquez or data catalogues) connect datasets to downstream features, training pipelines and models. When something fails, you know which models, dashboards and decisions are affected, and which upstream change caused it.

Alerting. Alerts go to the owning team with context: dataset, check that failed, last good run, downstream impact and runbook link—not to one noisy generic channel. Severity reflects impact, so critical feature tables page while minor reports create tickets. Data observability tools (Monte Carlo, Soda, Elementary for dbt) bundle much of this.

How it works

  1. Register datasets with owners, SLAs and criticality.
  2. Emit run metadata and lineage from every pipeline.
  3. Compute freshness, volume and quality metrics per run.
  4. Compare with historical baselines; detect anomalies.
  5. Route alerts to owners with downstream impact.
  6. Review incidents and tune thresholds.

Example

datasets:
  features.customer_spend_daily:
    owner: team-payments-data
    freshness_sla: "06:00 Asia/Kolkata"
    volume: {min_rows_vs_7d_avg: 0.8, max_rows_vs_7d_avg: 1.3}
    quality: [not_null(customer_id), null_rate(spend_30d) < 0.02]
    criticality: high          # feeds fraud-model, credit-model
    alert: {channel: "#payments-data-oncall", page_if: criticality == high}

Common mistakes

  • Alerting only on job failure.
  • No freshness SLAs, so stale data goes unnoticed.
  • Alerts without owners or downstream context.
  • No lineage, so impact analysis takes hours.

How to answer in the interview

"A job that succeeds can still produce bad data, so I monitor outcomes. Each important dataset has a freshness SLA. Row counts and partition sizes are compared with history to catch silently missing data. Data quality results are tracked over time, not just pass or fail. Duration and resource trends warn before deadlines are missed. Lineage, for example with OpenLineage, tells us which features and models depend on a failing dataset. Alerts go to the owning team with that context rather than to one generic channel."

Likely follow-up questions

  • How do you prioritise when many datasets fail at once? Use lineage to find the common upstream root and rank by downstream criticality.
  • What is data observability? Monitoring freshness, volume, schema, quality and lineage of data.
  • Who owns a dataset alert? The producing team, with consumers notified.
