What trade-offs exist between consistency, availability, and latency in distributed databases?

Databases & SQL · concept · levels senior, lead

In one line

Strong consistency needs replicas to coordinate before answering, which costs latency and, when replicas are unreachable, availability; weaker consistency answers locally with low latency and high availability but risks stale or conflicting reads, so you tune it per operation, for example with quorums where R + W > N.

Detailed explanation

Every replicated system decides how many replicas must agree before a read or write completes.

Strong consistency (linearizability): a write is acknowledged only after a leader and a majority have it, using consensus protocols such as Raft or Paxos, or a single leader with synchronous replicas. Reads either go to the leader or must confirm they are current. Cost: at least one extra network round trip per operation. Within a region that is about a millisecond; across regions it can be 50 to 200 ms or more. And if a quorum cannot be reached, requests fail: availability drops.

Weaker models: eventual consistency answers from the nearest replica immediately and propagates writes asynchronously; reads can be stale, and concurrent writes on different replicas can conflict and need resolution (last-write-wins, vector clocks, CRDTs). Intermediate models such as read-your-writes, monotonic reads, causal consistency and bounded staleness (offered, for example, by Azure Cosmos DB) give useful guarantees more cheaply.

Quorums: with N replicas, a write waits for W acknowledgements and a read queries R replicas. If R + W > N, read and write sets overlap, so a read sees the latest acknowledged write. N=3, W=2, R=2 tolerates one failure. W=1, R=1 is fastest but eventual. Tuning W and R moves cost between reads and writes.

Choose per operation: account balances, inventory reservation, unique usernames and payments need strong consistency. Like counts, view counters, social feeds, recommendations and analytics tolerate staleness.

How it works

  1. Define each operation's tolerance for stale data and conflicts.
  2. For strict operations, use a leader or quorum with synchronous acknowledgement.
  3. For relaxed ones, read local replicas and replicate asynchronously.
  4. Use session guarantees (read-your-writes) where users notice staleness.
  5. Keep strongly consistent data in one region where possible to avoid cross-region consensus.
  6. Measure p99 latency and failure behaviour under partitions.

Example

N = 3 replicas
Strong:    W=2, R=2 -> R+W=4 > 3, sees latest write, survives 1 down, ~2 RTT
Read-fast: W=3, R=1 -> reads cheap, writes fail if any replica is down
Eventual:  W=1, R=1 -> lowest latency, stale reads possible

DynamoDB:  GetItem(ConsistentRead=true)  -> strongly consistent, costs 2x read units
           GetItem(ConsistentRead=false) -> eventually consistent (default)
Cassandra: LOCAL_QUORUM writes + LOCAL_QUORUM reads

Common mistakes

  • Using one consistency level for every operation.
  • Putting synchronous cross-region consensus on hot paths without measuring latency.
  • Assuming eventual consistency means "consistent within milliseconds" always.

How to answer in the interview

"Stronger consistency requires replicas to coordinate before answering, waiting for a quorum or a leader using protocols like Raft or Paxos, which adds round trips, so latency grows, especially across regions, and if replicas are unreachable the system must refuse requests, lowering availability. Weaker models like eventual consistency answer from the nearest replica, giving low latency and high availability but stale or conflicting reads. Many systems let me tune it: with N replicas, choosing R and W so R plus W exceeds N gives reads that see the latest write. I choose per operation: balances and inventory need strong consistency; likes, feeds and analytics can be eventual."

Likely follow-up questions

  • How does DynamoDB let you choose? ConsistentRead=true for strongly consistent reads within a region, at double the read cost.
  • What is read-your-writes? A client always sees its own previous writes, even if others may see stale data.
  • How does Spanner stay consistent globally? Paxos replication plus TrueTime-based commit timestamps, accepting higher write latency.
