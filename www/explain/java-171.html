What is a race condition? Give an example and explain how to fix it.

Concurrency · concept · levels entry, mid

In one line

A race condition is a bug where the result depends on the timing or interleaving of threads accessing shared mutable state, such as count++ (lost update) or check-then-act; fix it with synchronisation/locks, atomic classes, atomic operations of concurrent collections, or better, immutability and thread confinement.

Detailed explanation

Code that looks like one step is often several. count++ compiles to read, add, write. If threads A and B both read 41, both compute 42 and both write 42, one increment is lost: a lost update. With enough threads and iterations, a counter that should reach 1,000,000 ends at some random lower number. This is a read-modify-write race.

The second classic shape is check-then-act: if (!map.containsKey(k)) map.put(k, create());. Between the check and the act another thread can insert, so two objects get created and one overwrites the other. Lazy initialisation (if (instance == null) instance = new X()) and "check balance then withdraw" are the same pattern. Even a thread-safe collection doesn't help if the sequence of calls isn't atomic.

Race conditions are related to, but distinct from, data races (unsynchronised conflicting accesses under the Java Memory Model), which also cause visibility problems such as a thread never seeing a flag change.

Fixes, from most to least preferred:

  • Avoid shared mutable state: immutable objects, records, List.copyOf; thread confinement (state local to one thread or request); message passing via queues.
  • Atomic operations: AtomicInteger.incrementAndGet, LongAdder for hot counters, ConcurrentHashMap.computeIfAbsent/merge, putIfAbsent.
  • Locks: synchronized or ReentrantLock around the whole critical section, using the same lock everywhere the state is accessed.
  • At the database level: transactions, optimistic locking (@Version), or conditional updates (UPDATE ... WHERE balance >= ?).

Races are timing dependent, so they pass unit tests and appear under production load.

How it works

  1. Two threads read the same shared value.
  2. Each computes a new value from its stale read.
  3. Both write; the later write wins.
  4. A fix makes read-compute-write indivisible, or removes sharing.

Example

class Stats {
    private int unsafe;                               // lost updates
    private final AtomicInteger safe = new AtomicInteger();
    private final ConcurrentMap<String, Session> sessions = new ConcurrentHashMap<>();

    void hit() { unsafe++; safe.incrementAndGet(); }

    Session session(String id) {
        // race: if (!sessions.containsKey(id)) sessions.put(id, new Session(id));
        return sessions.computeIfAbsent(id, Session::new);   // atomic
    }
}

// Demonstration: usually prints less than 2_000_000 for 'unsafe'

Common mistakes

  • Making only the write synchronised, not the read.
  • Using different locks for the same data.
  • Believing volatile fixes count++.
  • Testing once on a laptop and declaring it safe.

How to answer in the interview

"A race condition happens when the result depends on the timing or interleaving of threads accessing shared state. The classic example is count++ from two threads: it reads, increments and writes, so both can read the same value and one update is lost. Another is check-then-act, like if not containsKey then put. Fixes include synchronized blocks or locks around the critical section, atomic classes like AtomicInteger, atomic operations of concurrent collections like computeIfAbsent, and best of all avoiding shared mutable state through immutability or thread confinement."

Likely follow-up questions

  • How do you test for race conditions? Stress tests with many threads and a start latch, jcstress for low-level cases, and code review of shared state.
  • Race condition vs data race? A race condition is a logic timing bug; a data race is unsynchronised conflicting memory access under the JMM.
  • Is a race possible with one CPU core? Yes, preemption can interleave threads anywhere.
