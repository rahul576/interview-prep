Explain resource requests and limits in Kubernetes, and the pod QoS classes.

Kubernetes · concept · levels mid, senior

In one line

Requests are what the scheduler reserves for a container; limits cap usage, with CPU throttled and memory over the limit OOMKilled; together they set the QoS class, Guaranteed, Burstable or BestEffort, which affects eviction order; right-size from real metrics and combine with autoscaling.

Detailed explanation

Requests. The scheduler places a pod only on a node whose allocatable capacity minus the sum of existing requests can fit the pod's requests. Requests are therefore about placement and guaranteed share, not actual usage. CPU requests also translate into CPU weight, so under contention a container gets CPU proportional to its request. The HPA's utilisation percentages are relative to requests, so wrong requests break autoscaling too.

Limits. CPU is compressible: above its limit, the kernel's CFS quota throttles the container, causing latency spikes even when the node has idle CPU. Memory is incompressible: above its limit, the kernel OOM-kills the container (exit code 137, reason OOMKilled).

QoS classes are derived automatically:

  • Guaranteed: every container has CPU and memory requests equal to limits.
  • Burstable: at least one container has a request or limit, but not Guaranteed.
  • BestEffort: no requests or limits at all.

When a node runs short of memory, the kubelet evicts pods whose usage exceeds their requests first, also considering priority; in practice BestEffort pods go first and Guaranteed pods last. QoS also sets the kernel OOM score.

Practical policy. Many teams set memory request = limit (predictable, no surprise OOMs from overcommit) and set CPU requests but no or generous CPU limits to avoid throttling, while LimitRanges and ResourceQuotas provide namespace defaults and caps. Right-size from metrics (p95 usage over weeks) using VPA in recommendation mode or tools like Goldilocks; recent Kubernetes versions also support resizing pod resources in place.

How it works

  1. Scheduler sums requests per node and picks one with room.
  2. Kubelet configures cgroups: CPU weight from requests, CPU quota and memory limit from limits.
  3. Over the CPU limit → throttled; over the memory limit → OOMKilled.
  4. Node memory pressure → kubelet evicts pods, BestEffort first.
  5. Metrics feed VPA recommendations and HPA scaling.

Example

resources:
  requests:
    cpu: "500m"
    memory: "1Gi"
  limits:
    memory: "1Gi"          # equal to request: no overcommit for memory
    # no CPU limit: avoid throttling, rely on requests for fair share
kubectl top pod -n shop --containers
kubectl get pod api-7d9f -o jsonpath='{.status.qosClass}'

Common mistakes

  • No requests, so the scheduler overpacks nodes.
  • Tight CPU limits on latency-sensitive services.
  • Requests copied from limits far above real usage, wasting capacity.
  • JVM heap sized close to the memory limit.

How to answer in the interview

"Requests are what the container is guaranteed; the scheduler uses them to place pods, and the HPA calculates utilisation against them. Limits cap usage: over the CPU limit you're throttled, over the memory limit you're OOMKilled. The QoS class follows: Guaranteed when requests equal limits for all containers, Burstable when some are set, BestEffort when none; under memory pressure BestEffort pods are evicted first and Guaranteed last. I usually set memory request equal to limit and avoid tight CPU limits to prevent throttling, and I right-size from real usage with VPA recommendations, combined with the HPA."

Likely follow-up questions

  • Why can a JVM get OOMKilled with a heap smaller than the limit? Off-heap memory: metaspace, thread stacks, direct buffers, code cache and GC overhead; size heap with MaxRAMPercentage.
  • How do you spot CPU throttling? container_cpu_cfs_throttled_periods_total relative to total periods.
  • What do LimitRanges do? Set default and maximum requests/limits per namespace.
