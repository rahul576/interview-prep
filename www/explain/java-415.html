How do you handle data that several microservices need, without sharing a database?

Microservices · concept · levels senior, lead

In one line

Each piece of data has one owning service as the source of truth; other services either query its API at runtime or keep a local read copy updated by events, accepting eventual consistency, and nobody reads another service's tables.

Detailed explanation

With a database per service, sharing tables is off-limits: it would couple schemas, deployments and performance, and bypass the owner's business rules. Yet services constantly need others' data: orders need customer names, shipping needs addresses, search needs product details.

The first step is clear ownership. The customer service owns customer data; everyone else holds at most a copy. Then there are two main options.

Query the owner via its API at runtime (REST or gRPC). It is simple and always fresh, suitable when the data changes often or must be exact, such as current stock or credit limit. The costs are runtime coupling (if the customer service is down, the caller degrades), added latency and load on the owner, and N+1 call patterns. Mitigate with batch endpoints, caching with short TTLs, timeouts and circuit breakers.

Replicate via events (event-carried state transfer). The owner publishes CustomerCreated/CustomerUpdated, or a compacted topic with the latest state per key, and consumers keep a local read copy containing only the fields they need. Reads are fast and resilient to the owner being down, and queries can join locally. The cost is eventual consistency (a name change appears seconds later), storage duplication, the need for idempotent, ordered updates, and a backfill strategy for new consumers.

Other techniques: copy a snapshot of data at the time of the business event (the order stores the shipping address as it was, which is often the correct business semantics anyway), API composition for queries, and CQRS read models or a data platform for reporting. The choice depends on how fresh the data must be, how often it is read, and how much coupling you can tolerate.

How it works

  1. Define the owner of each data entity.
  2. Owner exposes an API and publishes change events with the entity id as key.
  3. Consumer chooses runtime query or local copy per use case.
  4. Local copy: idempotent upsert, keep last version per id.
  5. New consumer backfills from a compacted topic or bulk export, then follows events.

Example

// Order service keeps a minimal local copy of customers
@KafkaListener(topics = "customers.state", groupId = "orders-customer-cache")
public void onCustomer(CustomerState evt) {
    jdbc.update("""
        INSERT INTO customer_view(id, name, tier, version) VALUES (?,?,?,?)
        ON CONFLICT (id) DO UPDATE SET name = EXCLUDED.name, tier = EXCLUDED.tier,
            version = EXCLUDED.version
        WHERE customer_view.version < EXCLUDED.version""",
        evt.id(), evt.name(), evt.tier(), evt.version());
}

Common mistakes

  • "Temporarily" reading another service's database.
  • Copying whole entities with sensitive data everywhere.
  • No version checks, so out-of-order events overwrite newer data.
  • Forgetting how a new service gets historical data.

How to answer in the interview

"Every piece of data has one owning service, and no one else reads its tables, because a shared database couples schemas and releases. Other services either call the owner's API at runtime, which is simple and fresh but couples availability and adds latency, or they keep a local read copy of just the fields they need, updated from events like CustomerUpdated, which is fast and resilient but eventually consistent. Sometimes the right answer is to snapshot data into the business record, like the address on an order. I choose based on how fresh the data must be and how much coupling we can accept."

Likely follow-up questions

  • How do you backfill a new read copy? Consume a compacted state topic from the beginning, or bulk-load an export, then follow live events.
  • How do you handle out-of-order updates? Key by entity id for partition ordering and apply only higher versions.
  • What about reports across services? Stream events into a warehouse or a dedicated reporting read model.
