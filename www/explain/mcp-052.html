How does authentication differ between stdio and HTTP MCP servers?

MCP Servers · concept · levels mid, senior

In one line

A stdio server is a local subprocess running with the user's OS permissions, getting downstream credentials from environment variables or local credential stores; an HTTP server is a network service that follows the OAuth-based authorization spec and authenticates every request with bearer tokens.

Detailed explanation

The transport decides the trust model. With stdio, the host launches the server as a child process and talks over standard input and output. There is no network endpoint, so nothing to authenticate at the MCP level: the only party that can talk to the server is the process that started it. The MCP authorization specification explicitly does not apply. The server acts with whatever the OS user can do: read files, run commands, use network access.

Downstream credentials for a stdio server typically come from environment variables in the host config (for example GITHUB_PERSONAL_ACCESS_TOKEN) or from existing local logins like the Azure CLI, AWS profiles or kubeconfig. That is convenient, but it often means a powerful personal token sits in a JSON file that may get copied into a repo or shared in a chat. Good practice is least-privilege tokens (fine-grained, repo-limited, read-only where possible), secrets referenced from the OS keychain or a secret manager rather than pasted, and separate tokens per server.

HTTP servers are reachable over a network, so they must authenticate every request. They follow the OAuth 2.1-based spec: bearer tokens issued by an authorization server, validated for audience and scopes. Because the server knows who each user is, it can enforce per-user permissions, revoke access centrally and produce audit logs. For enterprises this is far easier to govern than hundreds of laptops each holding personal tokens.

How it works

  1. stdio: host reads config, spawns server with env vars, pipes JSON-RPC over stdin/stdout.
  2. stdio server uses the env token or local CLI login to call downstream APIs.
  3. HTTP: client connects to a URL; server responds 401 if no token.
  4. Client completes the OAuth flow; each request carries a bearer token.
  5. HTTP server validates the token and maps it to the user's downstream permissions.

Example

{
  "mcpServers": {
    "github-local": {
      "command": "github-mcp-server",
      "args": ["stdio", "--read-only"],
      "env": { "GITHUB_PERSONAL_ACCESS_TOKEN": "${env:GH_FINEGRAINED_RO}" }
    },
    "github-remote": {
      "type": "http",
      "url": "https://api.githubcopilot.com/mcp/"
    }
  }
}

The local entry runs with a fine-grained read-only token referenced from the environment; the remote entry triggers an OAuth sign-in instead.

Common mistakes

  • Assuming a local server is "safe" because it has no network endpoint; it has all your OS permissions.
  • Committing config files with tokens in the env block.
  • Running a local server bound to an HTTP port on 0.0.0.0 without authentication.
  • Using one classic all-scope token for every server.

How to answer in the interview

"A stdio server runs locally as a subprocess of the host, so it acts with the OS permissions of whoever launched it. There's no network endpoint, and the MCP authorization spec doesn't apply. Its downstream credentials usually come from environment variables in the host config or local logins like the cloud CLI. That's convenient but often means a powerful personal token, so I use fine-grained, least-privilege tokens and keep them out of shared config files. HTTP servers are network services, so they follow the OAuth-based spec: every request carries a bearer token the server validates, and the server can enforce per-user permissions and central revocation, which is why enterprises usually prefer remote servers."

Likely follow-up questions

  • Why do enterprises prefer remote servers? Central control, per-user auth, revocation and audit instead of tokens on laptops.
  • Local server on localhost HTTP? It still needs auth and Origin checks, or other local software and websites could reach it.
  • Where should local secrets live? OS keychain or a secret manager, injected at launch.
