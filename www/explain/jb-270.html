How would you securely manage passwords, API keys, and database credentials?

Security · design · levels senior, lead

In one line

Keep secrets out of code, Git and images, store them in a secret manager (Vault, AWS Secrets Manager, Azure Key Vault), inject them at runtime, prefer managed or workload identity and short-lived dynamic credentials, rotate them, and hash user passwords rather than storing them.

Detailed explanation

Three different things are often mixed up. Application secrets (database passwords, API keys, signing keys) must be readable by the service. User passwords must never be readable and are hashed with bcrypt or Argon2id. Configuration (URLs, timeouts) is not secret at all and can live in Git.

For application secrets the rule is: never in source code, never in application.yml committed to Git, never baked into Docker images or CI logs. Run secret scanning (gitleaks, GitHub secret scanning, trufflehog) on every push, because a leaked key stays in Git history. Store secrets in a secret manager with access policies, versioning and audit logs. Applications read them at runtime: via Spring Cloud Vault or Spring Cloud AWS/Azure config integration, mounted files from the Secrets Store CSI Driver or External Secrets Operator in Kubernetes, or environment variables as the simplest option (note that env vars can leak in crash dumps and /actuator/env).

Better still is having no static secret: with managed identity (Azure), IAM roles for service accounts / EKS Pod Identity (AWS) or GKE Workload Identity, the pod authenticates to cloud services with short-lived tokens. For databases, Vault dynamic secrets create a unique user per service with a TTL, and AWS RDS or Azure SQL support IAM or Entra ID token authentication.

Rotation must be routine and automated. Least privilege applies per service. And secrets must never be logged; mask them and lock down Actuator's env and configprops endpoints.

How it works

  1. Classify: secret, user credential, or plain configuration.
  2. Store secrets in the manager with per-service access policies.
  3. The workload authenticates with its identity and fetches secrets at startup or via a mounted file.
  4. Rotate automatically; the app reloads or reconnects.
  5. Scan repositories and images; audit access to secrets.

Example

# application.yml: no secret values, only references
spring:
  datasource:
    url: jdbc:postgresql://orders-db:5432/orders
    username: ${DB_USERNAME}
    password: ${DB_PASSWORD}
  config:
    import: optional:vault://
  cloud:
    vault:
      uri: https://vault.internal:8200
      authentication: KUBERNETES
      kubernetes:
        role: orders-service
gitleaks detect --source . --redact

Common mistakes

  • Removing a committed secret in a new commit without rotating it.
  • One shared database admin password for all services.
  • Exposing /actuator/env publicly.
  • Encrypting user passwords instead of hashing them.
  • Secrets printed in CI logs or exception messages.

How to answer in the interview

"Secrets never go into source code, committed config or Docker images, and I run secret scanning like gitleaks in CI. They live in a secret manager such as Vault, AWS Secrets Manager or Azure Key Vault, and are injected at runtime through Spring Cloud Vault, mounted files or environment variables. Where possible there is no static credential at all: the service uses managed or workload identity, and Vault issues short-lived dynamic database credentials. Everything is rotated, least privilege per service, and never logged. User passwords are a separate case: they are hashed with bcrypt or Argon2, not stored or encrypted."

Likely follow-up questions

  • How would you rotate a database password without downtime? Dual credentials: create the new one, roll out, then revoke the old; or dynamic per-pod credentials with TTL.
  • Are Kubernetes Secrets secure? Only base64-encoded by default; enable etcd encryption, RBAC, or sync from an external manager.
  • What if a key leaks? Revoke and rotate immediately, investigate usage in audit logs, then clean history.
