What is an API gateway, and what is service discovery?

Microservices · concept · levels mid, senior

In one line

An API gateway is the single entry point that routes client requests and handles cross-cutting concerns (auth, rate limiting, TLS), while service discovery lets services find each other's current instances by name, either client-side (Eureka, Consul) or server-side (Kubernetes Services and DNS).

Detailed explanation

API gateway. External clients should not know how the backend is split into services or where they run. A gateway such as Spring Cloud Gateway, Kong, NGINX/Envoy-based gateways, AWS API Gateway or Azure API Management exposes one public surface and routes by path, host or header (/api/orders/ → order service). It centralises cross-cutting concerns: TLS termination, authentication and token validation (for example verifying JWTs from an OAuth2 provider), rate limiting and quotas, CORS, request size limits, response caching, logging and correlation ids, and canary or blue-green routing. It can also do light request aggregation, though heavy aggregation belongs in a BFF. It must be highly available and must not contain business logic**, or it becomes a coupling bottleneck that every team must change.

Service discovery. Instances start, stop, scale and move, so addresses cannot be hard-coded. A service registry holds the current healthy instances of each service. With client-side discovery, instances register (self-registration with heartbeats) in Eureka or Consul, and the calling client fetches the list and load-balances itself, for example with Spring Cloud LoadBalancer and lb://order-service. With server-side discovery, the client calls a stable name and the platform resolves and balances it. On Kubernetes, a Service gets a DNS name (orders.shop.svc.cluster.local), and kube-proxy or a service mesh routes to ready pods, registered automatically when readiness probes pass. This is the common choice today, so Eureka is mainly used outside Kubernetes.

How it works

  1. Client calls https://api.shop.com/api/orders/42.
  2. Gateway terminates TLS, validates the JWT, applies rate limits.
  3. Gateway matches the route and resolves order-service.
  4. Discovery returns healthy instances (registry or Kubernetes DNS).
  5. Request is load-balanced to an instance; response flows back.

Example

spring:
  cloud:
    gateway:
      server:
        webflux:
          routes:
            - id: orders
              uri: lb://order-service        # resolved via discovery
              predicates: [ Path=/api/orders/** ]
              filters:
                - StripPrefix=1
                - name: RequestRateLimiter
                  args: { redis-rate-limiter.replenishRate: 50, redis-rate-limiter.burstCapacity: 100 }

(Recent Spring Cloud Gateway versions use the spring.cloud.gateway.server.webflux prefix; older ones use spring.cloud.gateway.routes.) On Kubernetes the uri could simply be http://order-service:8080.

Common mistakes

  • Putting business rules or orchestration in the gateway.
  • A single gateway instance (single point of failure).
  • Running Eureka inside Kubernetes when Services already provide discovery.
  • Trusting the gateway alone for security; services should still verify tokens.

How to answer in the interview

"An API gateway, like Spring Cloud Gateway or Kong, is the single entry point for clients. It routes requests to the right service and handles cross-cutting concerns such as TLS termination, authentication, rate limiting, CORS and logging, so services do not duplicate them, but it should contain no business logic. Service discovery lets services find each other without hard-coded addresses. With client-side discovery, instances register in Eureka or Consul and clients look them up and load-balance. With server-side discovery the platform does it, as with Kubernetes Services and DNS, which is what I mostly use today."

Likely follow-up questions

  • Why is business logic in the gateway an anti-pattern? It couples all teams to one component and creates a deployment bottleneck.
  • How does Kubernetes know a pod is ready to receive traffic? Readiness probes control whether the pod is in the Service endpoints.
  • Gateway vs service mesh? Gateway handles north-south traffic at the edge; a mesh handles east-west traffic between services.
