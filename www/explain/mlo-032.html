Your model accuracy dropped from 95 percent to 70 percent. Walk me through your investigation.

MLOps · scenario · levels mid, senior

In one line

A drop from 95 to 70 percent is usually a pipeline or measurement problem, not gradual drift: confirm the measurement (labels, metric pipeline, sample), check data quality and pipeline failures, line up recent deployments and code changes, then look at data drift and concept drift, and mitigate by rollback, pipeline fix and backfill, or retraining.

Detailed explanation

Gradual drift erodes a few points over weeks. A 25-point fall usually has a sharp cause, so I work from the most likely and cheapest checks outward and build a timeline.

Confirm the measurement. Are labels correct and complete, or are recent labels still immature (for example, only fraud cases are labelled so far)? Did the metric pipeline change—a join, a filter, a new definition of "positive"? Is the evaluation sample representative, or did a new segment enter it? Many "accuracy drops" are reporting bugs.

Data quality and pipeline failures. Schema changes, missing partitions, a key feature flooded with nulls or default values, a unit or encoding change upstream, a stale feature store. I compare feature statistics before and after the drop.

Recent changes. A new model version, a preprocessing change, a library upgrade (tokeniser, scikit-learn version), a configuration or threshold change. Plotting deployments on the same timeline as the metric often reveals the cause immediately.

Drift. If the data is clean and nothing changed in our systems, look for data drift in important features and segments, and concept drift—a policy change, a new fraud pattern, a competitor launch, a pandemic-like event.

Mitigation follows the cause: roll back the model or code; fix the pipeline and backfill features; or retrain on recent data and validate before redeploying. Meanwhile, consider a fallback for high-impact decisions.

How it works

  1. Verify labels, metric code and evaluation sample.
  2. Pinpoint when the drop started; overlay deployments and data changes.
  3. Check feature null rates, ranges and distributions around that time.
  4. Break the metric down by segment to localise the problem.
  5. Test hypotheses: score the same data with the previous model.
  6. Mitigate, then add monitoring that would have caught it earlier.

Example

Timeline
  Mon 09:00  accuracy 95 %
  Mon 14:10  deploy: preprocessing v3.2 (new text normaliser)
  Tue 09:00  accuracy 71 %
Check: old model + old preprocessing on Tuesday data -> 94 %
       old model + new preprocessing -> 70 %
Cause: normaliser lower-cases product codes used as a key feature.
Fix: roll back preprocessing, add golden-input test to CI.

Common mistakes

  • Retraining immediately before understanding the cause.
  • Trusting the metric without checking label completeness.
  • Looking only at averages instead of segments.
  • No deployment markers on dashboards.

How to answer in the interview

"A drop that big is usually a pipeline issue, not slow drift. I'd first confirm the measurement: are labels correct and complete, did the metric code change, is the sample representative. Next data quality: schema changes, missing partitions, nulls or defaults in a key feature, unit changes. Then recent changes to the model, preprocessing or dependencies, lined up against when the drop started. If all that's clean, I'd look for data and concept drift by segment. Mitigation depends on cause: rollback, pipeline fix and backfill, or retrain and validate."

Likely follow-up questions

  • Which single dashboard would have shortened this? Feature null and default rates plus prediction distribution, with deployment markers.
  • How do you isolate model vs data? Score the same data with old and new versions.
  • What if labels are delayed? Use prediction drift and proxies until labels mature.
