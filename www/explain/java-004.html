Why is String immutable in Java, and when would you use StringBuilder instead?

Core Java & OOP · concept · levels entry

In one line

String is immutable: once created, its value never changes and every "modification" creates a new object. This enables the string pool, thread safety, security and a cached hash code; use StringBuilder when building strings through repeated concatenation, especially in loops.

Detailed explanation

A String's content is stored in a private final array (since Java 9, a byte[] with a coder flag, called compact strings, so Latin-1 text uses one byte per character). There are no methods that modify it; concat, replace, toUpperCase and substring all return new strings. The class is also final, so no subclass can add mutability.

Why immutable?

  • String pool / interning: string literals are stored once in the pool (on the heap since Java 7) and shared. "OK" in a hundred classes is one object. This sharing is only safe because nobody can change it. intern() adds a runtime string to the pool.
  • Thread safety: immutable objects can be shared between threads without synchronisation.
  • Security and integrity: strings carry file paths, URLs, class names, SQL and credentials-related data. If a string could change after validation (time-of-check to time-of-use), an attacker or bug could alter a path after the security check. Class loading relies on class names not changing.
  • Cached hash code: hashCode() is computed once and cached, making strings fast HashMap keys, and keys that never change their hash.

When to use StringBuilder: each + on strings in a loop creates a new string and copies all previous characters, which is O(n²) for n appends and generates garbage. StringBuilder is a mutable, resizable buffer; appends are amortised O(1), and toString() produces the final immutable string. For a single expression like "Hello " + name + "!", the compiler already optimises (since Java 9 via invokedynamic/StringConcatFactory), so + is fine there. StringBuffer is the older synchronised version; it is rarely needed because builders are almost always local to one thread. Also consider String.join, StringJoiner, Collectors.joining, text blocks and formatted().

How it works

  1. String s = "shop"; refers to a pooled literal.
  2. s = s + "ping"; creates a new String; the old one is unchanged.
  3. new String("shop") creates a separate heap object, not the pooled one.
  4. StringBuilder keeps a growable array and appends in place.
  5. toString() copies the buffer into a new immutable String.

Example

String a = "java";
String b = "java";
String c = new String("java");
System.out.println(a == b);          // true: same pooled literal
System.out.println(a == c);          // false: different object
System.out.println(a.equals(c));     // true: same content

String upper = a.toUpperCase();      // a is still "java"

// Loop concatenation: use StringBuilder
StringBuilder csv = new StringBuilder();
for (Order o : orders) {
    csv.append(o.id()).append(',').append(o.total()).append('\n');
}
String report = csv.toString();

String names = customers.stream().map(Customer::name).collect(Collectors.joining(", "));

Common mistakes

  • Using += in a large loop.
  • Comparing strings with == instead of equals.
  • Using StringBuffer "for safety" in single-threaded code.
  • Thinking s.toUpperCase() changes s.

How to answer in the interview

"A String is immutable: once created its value can't change, and every modification creates a new object. That enables the string pool, where literals are interned and shared, saving memory. It also makes strings thread-safe without synchronisation, helps security because values like file paths or class names can't be altered after validation, and lets the hash code be cached, which makes strings fast HashMap keys. When I build a string in a loop or with many concatenations I use StringBuilder, which is mutable and avoids creating many temporary objects; StringBuffer is the older synchronised variant I rarely need."

Likely follow-up questions

  • How many objects are created by: String s = new String("hello")? Up to two: the pooled literal "hello" (if not already in the pool, created when the class is loaded) and a new String object on the heap.
  • Is "a" + "b" + c compiled efficiently? Yes; compile-time constants are folded, and since Java 9 concatenation uses invokedynamic, so single expressions are fine.
  • Why should passwords use char[] instead of String? A char[] can be wiped after use, while an immutable String lingers in memory until GC.
