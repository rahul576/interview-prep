Design an immutable infrastructure pipeline using Packer, Terraform and auto scaling groups.

Infrastructure as Code · design · levels senior

In one line

Packer bakes versioned, tested images (with Ansible), publishes them and records the latest approved version; Terraform puts that image into the launch template; an instance refresh replaces instances in batches with health checks and automatic rollback; rollback means pointing back to the previous image.

Detailed explanation

In an immutable model servers are never patched or reconfigured in place. Every change, from an OS patch to an application release, produces a new image, and instances are replaced. This removes configuration drift, makes every server identical and makes rollback a matter of using the previous image.

Build. A pipeline (scheduled weekly for patches, or triggered by a base image or application release) runs Packer. Packer launches a temporary instance from the latest approved base image (for example the newest Ubuntu or Amazon Linux AMI found with a filter), runs Ansible for hardening (CIS settings), agents and application dependencies, and then runs tests such as Goss or InSpec on the instance before creating the image. Images are tagged with version, git SHA and base image, and vulnerability-scanned.

Publish. The image is shared with or copied to target accounts and regions (encrypted with the right KMS keys), and the approved version is written to a registry: an SSM parameter, HCP Packer channel or similar. Dev gets new images first; promotion to prod updates the prod pointer.

Deploy. Terraform reads the pointer, updates the launch template image_id, and the auto scaling group starts an instance refresh: instances are replaced in batches while keeping a minimum healthy percentage, waiting for load balancer health checks and warm-up, with checkpoints and auto rollback if the refresh fails.

State must live outside instances: databases, S3, EFS, caches; logs shipped centrally; configuration and secrets fetched at boot.

How it works

  1. Packer build → Ansible provisioning → Goss tests → image web-2026.11.21-abc123.
  2. Image shared; SSM parameter /images/web/dev updated.
  3. Terraform apply updates launch template; ASG instance refresh begins.
  4. Batches replaced; health checks gate progress; failure rolls back.
  5. Promotion copies the version to /images/web/prod and repeats.

Example

data "aws_ssm_parameter" "web_ami" { name = "/images/web/prod" }

resource "aws_launch_template" "web" {
  image_id      = data.aws_ssm_parameter.web_ami.value
  instance_type = "m7g.large"
}

resource "aws_autoscaling_group" "web" {
  launch_template {
    id      = aws_launch_template.web.id
    version = aws_launch_template.web.latest_version
  }
  instance_refresh {
    strategy = "Rolling"
    preferences {
      min_healthy_percentage = 90
      instance_warmup        = 120
      auto_rollback          = true
    }
  }
}

Common mistakes

  • Images without tests, so broken images reach production.
  • most_recent = true in production, deploying unreviewed images.
  • State or logs left on instance disks.
  • Never cleaning up old images and snapshots (cost), or deleting the one you need for rollback.

How to answer in the interview

"A pipeline runs Packer, which starts from the latest approved base image, applies hardening and dependencies with Ansible, runs Goss or InSpec tests and produces a versioned image, which is shared to target accounts and recorded as the approved version in a parameter store. Terraform reads that parameter and updates the launch template, and an instance refresh replaces instances in batches with a minimum healthy percentage, health checks and automatic rollback. Servers are never patched in place, state lives in managed services, and rolling back means pointing the launch template at the previous image."

Likely follow-up questions

  • How do you handle state that lives on instances? Move it to managed data stores, shared file systems or object storage; ship logs.
  • How fast can you ship an urgent patch? Trigger the build, skip the soak only with approval, refresh fleets in waves.
  • Why not most_recent data sources? Deploys are no longer explicit or reviewable.
