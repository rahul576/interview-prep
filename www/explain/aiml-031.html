What is a mixture-of-experts model, and why do many frontier models use it?

AI/ML & GenAI · concept · levels senior, lead

In one line

A mixture-of-experts (MoE) model replaces some layers (usually feed-forward) with many expert sub-networks and a router that sends each token to only a few, so total capacity is huge but compute per token stays small, at the price of high memory, load balancing and serving complexity.

Detailed explanation

In a dense transformer every parameter is used for every token. In an MoE layer, there are, say, 64 or 128 parallel experts (feed-forward networks), and a small gating network (router) scores them for each token and selects the top-k, often one or two, sometimes more fine-grained experts plus a shared one. The token is processed only by those experts and their outputs are combined using the router weights. Attention layers usually stay dense.

The result is sparse activation: a model may have hundreds of billions of total parameters but only a fraction, for example tens of billions, active per token. Because the compute (FLOPs) per token is like a much smaller dense model, MoE gives better quality for the same training and inference compute, which is why many frontier and open models use it; published examples include Mixtral, DeepSeek-V3 and Qwen MoE variants, and several closed models are widely reported to use it too.

The trade-offs are significant. Memory: every expert must be loaded because any token might route to any expert, so serving needs as much GPU memory as a dense model of the total size. Load balancing: routers can collapse onto a few favourite experts, so training adds auxiliary balancing losses or bias-based balancing and capacity limits, and dropped or overflowing tokens hurt quality. Distributed serving: experts are spread over GPUs (expert parallelism), requiring all-to-all communication every MoE layer, which demands fast interconnects and makes small-batch latency harder. Fine-tuning can be less stable, and quantisation and batching strategies differ from dense models.

How it works

  1. Each token's hidden vector enters the MoE layer.
  2. The router computes a score per expert and picks the top-k.
  3. The token is dispatched to those experts (possibly on other GPUs).
  4. Experts process it; outputs are weighted by router probabilities and summed.
  5. Results return to the token's position; balancing losses keep usage even across experts.

Example

import torch, torch.nn.functional as F

def moe_layer(x, router, experts, k=2):
    logits = router(x)                        # [tokens, n_experts]
    weights, idx = logits.topk(k, dim=-1)
    weights = F.softmax(weights, dim=-1)
    out = torch.zeros_like(x)
    for slot in range(k):
        for e in idx[:, slot].unique():
            mask = idx[:, slot] == e
            out[mask] += weights[mask, slot, None] * experts[e](x[mask])
    return out

Common mistakes

  • Assuming MoE needs less GPU memory because it uses less compute.
  • Thinking each expert is a human-interpretable topic specialist; specialisation is mostly at token or pattern level.
  • Comparing an MoE's total parameters directly with a dense model's.
  • Ignoring interconnect bandwidth when planning MoE serving.

How to answer in the interview

"MoE swaps the feed-forward layers for many expert networks plus a router that picks a few experts per token. So a model can have hundreds of billions of parameters but only use a small slice for each token, giving much more capacity at roughly the compute of a smaller dense model; Mixtral, DeepSeek and Qwen MoE models use this. The catch is that all experts must sit in memory, the router needs balancing so experts aren't overloaded or idle, and distributing experts across GPUs adds all-to-all communication and serving complexity."

Likely follow-up questions

  • Why lots of memory despite little compute per token? Any token may route to any expert, so all weights must be resident.
  • What is expert parallelism? Placing different experts on different GPUs and routing tokens between them.
  • What happens with poor load balancing? Overloaded experts drop or delay tokens and idle experts waste capacity.
