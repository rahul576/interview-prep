How does the Spring Cache abstraction work, and what are its pitfalls?

Spring Boot · concept · levels mid, senior

In one line

Enable caching with @EnableCaching and annotate methods: @Cacheable returns a cached result or calls and stores it, @CachePut always calls and updates, @CacheEvict removes entries; the provider is pluggable (Caffeine, Redis). Pitfalls: proxy-based (no self-invocation), key design, TTL configured on the provider, mutable objects and nulls, and stale data.

Detailed explanation

The cache abstraction separates caching logic from business code. Spring creates a proxy around beans with cache annotations; on a call, the interceptor computes a key, consults the CacheManager and either returns the cached value or invokes the method.

  • @Cacheable("products"): look up the key; on a hit skip the method; on a miss call it and store the result. condition and unless (for example unless = "#result == null") control what is cached. sync = true lets only one thread compute a missing value per key, reducing stampedes.
  • @CachePut: always run the method and put the result, used after updates.
  • @CacheEvict: remove one key or allEntries = true; beforeInvocation controls timing.
  • @Caching combines several; @CacheConfig sets class-level defaults.

Providers: Spring Boot auto-configures one based on the classpath: Caffeine for fast local in-JVM caching with size and time limits; Redis for a distributed cache shared by all instances, which survives restarts and keeps instances consistent; others via JCache. A simple ConcurrentHashMap cache is the fallback and has no eviction.

Pitfalls:

  • Self-invocation bypasses the proxy, just like @Transactional.
  • Default key: built from all parameters with SimpleKeyGenerator; no-arg methods share one key, and two different methods using the same cache name with the same arguments collide. Define keys explicitly with SpEL, such as key = "#id".
  • TTL and size are not part of the annotations; configure them per cache on the provider (spring.cache.redis.time-to-live, Caffeine spec, or RedisCacheManagerBuilderCustomizer).
  • Mutable objects: with a local cache, callers receive the same instance and can modify the cached value. Cache immutable DTOs or records.
  • Nulls may or may not be cached depending on the provider.
  • Serialisation for Redis: configure JSON serialisation and versioning.
  • Staleness and multi-instance: local caches on different pods diverge after an eviction on one pod.

How it works

  1. @EnableCaching registers the cache interceptor and proxies.
  2. A call computes the key from SpEL or parameters.
  3. The cache manager returns the named cache from the provider.
  4. Hit: return cached value. Miss: invoke, store, return.
  5. Put and evict operations update entries after writes.

Example

@Service
@CacheConfig(cacheNames = "products")
class ProductService {
    @Cacheable(key = "#id", unless = "#result == null")
    public ProductDto get(long id) { return mapper.toDto(repo.findById(id).orElse(null)); }

    @CachePut(key = "#result.id()")
    public ProductDto update(long id, UpdateProduct cmd) { ... }

    @Caching(evict = { @CacheEvict(key = "#id"), @CacheEvict(cacheNames = "productLists", allEntries = true) })
    public void delete(long id) { repo.deleteById(id); }
}
spring:
  cache:
    type: redis
    cache-names: products,productLists
    redis:
      time-to-live: 10m

Common mistakes

  • Caching inside the same class and wondering why nothing is cached.
  • No TTL, so stale data lives forever.
  • Caching JPA entities with lazy associations.
  • Local cache on several pods with no invalidation strategy.

How to answer in the interview

"I enable caching and annotate service methods: @Cacheable returns the cached value for a key or calls the method and stores the result, @CachePut always calls and updates the entry, and @CacheEvict removes entries after writes. The provider is pluggable: Caffeine for local caching, Redis for a shared distributed cache. The pitfalls: it's proxy-based, so self-invocation isn't cached; the default key is all method arguments, so I define keys explicitly; TTL and size must be configured on the provider; and caching mutable objects or nulls gives surprising results, so I cache immutable DTOs. With several instances I prefer Redis or a clear invalidation strategy."

Likely follow-up questions

  • How would you cache a list of products but evict a single product when it changes? Separate caches: evict the product key and clear or version the list cache.
  • How do you avoid a stampede? sync = true, TTL jitter, or refresh-ahead with Caffeine.
  • How do you monitor it? Micrometer cache metrics: hits, misses, evictions.
