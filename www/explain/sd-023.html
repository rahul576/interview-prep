How do you design a data model for a NoSQL database like DynamoDB or Cassandra?

Data & Storage Design · concept · levels mid, senior

In one line

In DynamoDB or Cassandra you design tables from queries: choose a high-cardinality partition key, a sort/clustering key for ranges, denormalise per access pattern, and avoid hot partitions.

Detailed explanation

These stores scale by spreading partitions across nodes. Queries are fast only when they hit one partition (or a small number) using the key. There are no joins, and secondary indexes are limited or expensive. So instead of normalising entities and querying freely, you list every access pattern first and shape data to serve each one directly.

The partition key spreads data and load; it must have many distinct values with even traffic. The sort key (DynamoDB) or clustering key (Cassandra) orders items inside a partition, enabling queries like "latest 20 orders for customer X". Duplicating data across tables (or items) is normal: you trade storage for fast reads.

How it works

  1. Write down access patterns: "get orders of a customer by date", "get order by ID", "list items of an order".
  2. Design keys: PK = CUSTOMER#123, SK = ORDER#2026-11-20#987.
  3. Add GSIs (DynamoDB) or extra tables (Cassandra) for other patterns.
  4. Check partition size limits and traffic per key.
  5. Write to all denormalised copies (batch, or via streams).

Example

CREATE TABLE orders_by_customer (
  customer_id uuid,
  order_date timestamp,
  order_id uuid,
  total decimal,
  PRIMARY KEY ((customer_id), order_date, order_id)
) WITH CLUSTERING ORDER BY (order_date DESC);

DynamoDB single-table: PK=CUSTOMER#123, SK=PROFILE and PK=CUSTOMER#123, SK=ORDER#2026-11-20#987 in the same table.

Common mistakes

  • Low-cardinality partition keys (status, country) → hot partitions.
  • Unbounded partitions (all events of a device forever); add time buckets.
  • Using ALLOW FILTERING / scans in production.
  • Designing tables before knowing the queries.

How to answer in the interview

"I start from the access patterns, not the entities. The partition key must spread load evenly, like customer ID, and the sort key supports range queries, like order date. I denormalise and duplicate data per query, using a table per query in Cassandra or single-table design with GSIs in DynamoDB. I bucket large partitions by time to keep them bounded."

Likely follow-up questions

  • New query after launch? Add a GSI or a new table and backfill from the source or a stream.
  • How do you avoid hot partitions? High-cardinality keys, write sharding with suffixes, adaptive capacity.
  • Transactions? DynamoDB has limited transactions; Cassandra has lightweight transactions (Paxos), costly.
