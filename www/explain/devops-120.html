How do you build multi-architecture images and speed up Docker builds with BuildKit?

Docker · concept · levels mid, senior

In one line

BuildKit, the default Docker builder, speeds builds with parallel stages, skipping unused stages, cache mounts and secret mounts; docker buildx uses it to build multi-platform images (amd64/arm64) via QEMU emulation, native builders or cross-compilation, pushing a manifest list/OCI index, with registry or GitHub Actions cache for ephemeral CI runners.

Detailed explanation

BuildKit (default since Docker Engine 23) turns the Dockerfile into a dependency graph. Independent stages build in parallel, stages the target does not need are skipped, and caching is more precise than the legacy builder. Dockerfile features it enables:

  • RUN --mount=type=cache,target=/root/.m2 keeps package manager caches between builds without putting them in layers.
  • RUN --mount=type=secret,id=npmrc exposes a secret for one step only; it never lands in a layer or history.
  • RUN --mount=type=ssh forwards an SSH agent for private git dependencies.
  • COPY --link creates layers that do not need rebuilding when earlier layers change.

Multi-architecture images: Graviton servers, Apple silicon laptops and Raspberry Pis are arm64, most CI and many servers are amd64. docker buildx build --platform linux/amd64,linux/arm64 builds one image per platform and pushes a manifest list (OCI image index) under a single tag; when a node pulls myapp:1.4, the registry serves the variant for its architecture. Three ways to build the foreign platform:

  • QEMU emulation (binfmt): easy, but CPU-heavy steps such as compiling can be 5-20x slower.
  • Native builders: a buildx builder with nodes on both architectures, or separate jobs on amd64 and arm64 runners (GitHub offers arm64 hosted runners), merged into one manifest with docker buildx imagetools create.
  • Cross-compilation: run the build stage on $BUILDPLATFORM and compile for $TARGETARCH (easy in Go, Rust, .NET), so no emulation is needed.

CI caching: runners are ephemeral, so local cache disappears. Export and import it with --cache-to / --cache-from, using type=registry (a cache image in your registry), type=gha (GitHub Actions cache) or type=s3. mode=max caches intermediate stages too.

How it works

  1. Create a buildx builder (docker-container driver for multi-platform).
  2. BuildKit resolves the graph, pulling cache metadata.
  3. Builds each platform (emulated, native or cross-compiled).
  4. Pushes per-platform images and the index; exports cache.

Example

# syntax=docker/dockerfile:1
FROM --platform=$BUILDPLATFORM golang:1.23 AS build
ARG TARGETOS TARGETARCH
WORKDIR /src
COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod go mod download
COPY . .
RUN --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH go build -o /out/api ./cmd/api
FROM gcr.io/distroless/static-debian12
COPY --from=build /out/api /api
ENTRYPOINT ["/api"]
docker buildx create --use --name multi
docker buildx build --platform linux/amd64,linux/arm64 \
  -t ghcr.io/acme/api:1.4.0 --push \
  --cache-from type=registry,ref=ghcr.io/acme/api:buildcache \
  --cache-to type=registry,ref=ghcr.io/acme/api:buildcache,mode=max .

Common mistakes

  • Compiling heavy code under QEMU and accepting 40-minute builds.
  • Pushing separate -arm64 tags instead of one manifest list.
  • No cache export in CI, so every build starts cold.
  • Native dependencies (glibc vs musl, binary downloads) hard-coded for amd64.

How to answer in the interview

"BuildKit is the modern builder: it runs independent stages in parallel, skips unused ones, and supports cache mounts so package caches survive between builds and secret mounts so credentials never land in layers. With docker buildx I build multi-platform images, for example amd64 and arm64 for Graviton and Apple silicon, and push a manifest list so each node pulls the right variant. Emulation through QEMU works but is slow for compilation, so I prefer native arm64 runners or cross-compiling with BUILDPLATFORM and TARGETARCH. In CI I use registry or GitHub Actions cache with cache-from and cache-to, since runners are ephemeral."

Likely follow-up questions

  • Why is QEMU slow? Every instruction is emulated in software; use native builders or cross-compilation.
  • How do you check an image's platforms? docker buildx imagetools inspect image:tag.
  • mode=min vs mode=max? Min caches only final layers; max also caches intermediate stages.
