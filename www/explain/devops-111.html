When do you use a StatefulSet, a DaemonSet, a Job or a CronJob?

Kubernetes · concept · levels mid, senior

In one line

StatefulSet for stateful apps needing stable identity, ordered rollout and a persistent volume per pod; DaemonSet for one pod per (selected) node such as agents; Job for run-to-completion tasks with retries; CronJob to create Jobs on a schedule.

Detailed explanation

A Deployment treats pods as interchangeable cattle. Other workloads need different guarantees, and Kubernetes has a controller for each.

StatefulSet. Pods get stable, ordinal names (kafka-0, kafka-1), stable DNS through a headless Service (kafka-0.kafka.data.svc), and their own PersistentVolumeClaim from volumeClaimTemplates that follows the pod when it is rescheduled. By default pods start and stop in order (podManagementPolicy: OrderedReady), and rolling updates proceed from the highest ordinal down, with partition allowing staged rollouts. Used for databases, Kafka, ZooKeeper, Elasticsearch and anything with replication roles. For production databases, an operator (CloudNativePG, Strimzi) usually manages the StatefulSet plus failover and backups.

DaemonSet. Ensures one pod on every node, or every node matching a nodeSelector/affinity, and automatically adds pods to new nodes. Used for log collectors (Fluent Bit), monitoring agents (node-exporter), CNI and CSI node plugins, security agents. They usually need tolerations to run on tainted nodes too.

Job. Runs pods until a number of successful completions, with backoffLimit for retries, parallelism for concurrent pods, activeDeadlineSeconds as a timeout and ttlSecondsAfterFinished for cleanup. Indexed Jobs give each pod a completion index for sharded work. Used for migrations, batch processing and one-off tasks.

CronJob. Creates Jobs on a cron schedule, with a timeZone, concurrencyPolicy (Allow, Forbid, Replace), startingDeadlineSeconds for missed runs and history limits. Used for backups, reports and cleanups. Jobs must be idempotent, because a run can occasionally happen twice or be skipped.

How it works

  1. StatefulSet creates db-0, waits for ready, then db-1, each with PVC data-db-N.
  2. DaemonSet controller places one pod per eligible node, including new nodes.
  3. Job controller creates pods until completions succeed or backoffLimit is hit.
  4. CronJob controller creates a Job at each schedule time per its concurrency policy.

Example

apiVersion: batch/v1
kind: CronJob
metadata: { name: nightly-backup }
spec:
  schedule: "0 2 * * *"
  timeZone: "Europe/London"
  concurrencyPolicy: Forbid
  jobTemplate:
    spec:
      backoffLimit: 2
      ttlSecondsAfterFinished: 86400
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: backup
              image: ghcr.io/acme/pg-backup:2.3

Common mistakes

  • Running a database as a Deployment with a shared volume.
  • Non-idempotent CronJobs with concurrencyPolicy: Allow.
  • DaemonSets without resource requests, starving nodes.
  • Jobs without TTL, leaving thousands of finished pods.

How to answer in the interview

"A StatefulSet is for stateful apps like databases or Kafka: each pod gets a stable name and DNS entry, ordered startup and its own persistent volume claim that follows it. A DaemonSet runs one pod per node, or per selected node, for agents such as log collectors, monitoring exporters or CNI plugins, and adds pods to new nodes automatically. A Job runs pods to completion with retries, for things like a database migration. A CronJob creates Jobs on a schedule, like a nightly backup, with settings for concurrency, missed runs and history, and those jobs should be idempotent."

Likely follow-up questions

  • What happens to a StatefulSet's volumes when you scale down? PVCs are kept by default so data survives scale-up again; persistentVolumeClaimRetentionPolicy can delete them.
  • Why use an operator instead of a plain StatefulSet for databases? Failover, backups and upgrades need domain logic.
  • Can a DaemonSet run on control-plane nodes? Yes, with tolerations for their taints.
