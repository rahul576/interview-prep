What are design patterns, and why are they useful?

Design Patterns · concept · levels entry, mid

In one line

Design patterns are reusable, proven solutions to recurring design problems, described as templates rather than finished code; the GoF groups them into creational, structural and behavioural patterns, and they give teams a shared vocabulary, though overusing them leads to over-engineering.

Detailed explanation

A pattern names a problem that keeps coming back, describes a solution structure, and lists its trade-offs. It is not a library you import; you adapt the idea to your code. The idea came from architect Christopher Alexander and was brought to software by the "Gang of Four" (Gamma, Helm, Johnson, Vlissides) in their 1994 book, which catalogues 23 patterns:

  • Creational: how objects are created (Singleton, Factory Method, Abstract Factory, Builder, Prototype).
  • Structural: how classes and objects are composed (Adapter, Decorator, Proxy, Facade, Composite, Bridge, Flyweight).
  • Behavioural: how objects collaborate and share responsibility (Strategy, Observer, Template Method, Chain of Responsibility, Command, State, Visitor, Iterator, Mediator, Memento, Interpreter).

Why they help:

  • They capture experience: you reuse a design others have already debugged.
  • They support flexibility and maintainability, typically by programming to interfaces and favouring composition.
  • They provide vocabulary: "wrap the vendor SDK in an adapter" or "use a strategy per tax rule" communicates a full design in a sentence, which speeds up design reviews.
  • They help you read frameworks. Spring uses Proxy for @Transactional, Template Method in JdbcTemplate, Factory in BeanFactory, Observer in application events, Front Controller in DispatcherServlet.

Caveats: patterns add indirection. Applying them before a need exists (an AbstractFactoryFactory for one implementation) makes code harder to read. Modern Java features such as lambdas, records, sealed types and pattern matching make some patterns (Strategy, Command, Visitor) much lighter. Beyond GoF there are enterprise and architectural patterns: Repository, Unit of Work, CQRS, Saga, Circuit Breaker.

How it works

  1. Recognise a recurring problem (varying algorithm, incompatible interface, complex construction).
  2. Recall the pattern that addresses it and its trade-offs.
  3. Adapt the structure to your context and language features.
  4. Name it in code and docs so others recognise it.

Example

// Strategy with a lambda: the pattern without ceremony
Comparator<Employee> bySalary = Comparator.comparing(Employee::salary);
employees.sort(bySalary.reversed());

// Adapter: our interface, vendor SDK inside
class TwilioSmsAdapter implements SmsSender {
    public void send(String to, String msg) { twilio.messages().create(to, msg); }
}

Common mistakes

  • Treating patterns as goals rather than tools.
  • Memorising UML without being able to give a real use case.
  • Applying heavyweight class-based versions where a lambda suffices.
  • Forgetting that frameworks already implement many patterns for you.

How to answer in the interview

"Design patterns are reusable, proven solutions to common design problems, more a template than finished code. The Gang of Four grouped 23 of them into creational, like Singleton, Factory and Builder; structural, like Adapter, Decorator and Proxy; and behavioural, like Strategy, Observer and Template Method. They're useful because they capture experience, make code more flexible, and give the team a shared vocabulary. Spring itself is full of them: proxies for transactions, Template Method in JdbcTemplate. But I don't apply them speculatively, because that leads to over-engineering."

Likely follow-up questions

  • Example where a pattern made code worse? A factory plus abstract classes for a single implementation, adding layers with no variation.
  • Are patterns language-specific? The ideas are general, but language features change how heavy the implementation is.
  • What are anti-patterns? Common but harmful solutions, such as God Object or Singleton abuse.
