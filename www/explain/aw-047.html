Explain SQS standard vs FIFO queues, visibility timeout and dead-letter queues.

Cloud (AWS) · concept · levels mid

In one line

Standard SQS queues give near-unlimited throughput with at-least-once delivery and best-effort order, FIFO queues give ordering per message group and exactly-once processing via deduplication; the visibility timeout hides a message while it is processed, and a dead-letter queue catches messages that fail maxReceiveCount times.

Detailed explanation

A standard queue scales to virtually any rate. Because messages are stored redundantly across servers, a message can occasionally be delivered more than once or out of order, so consumers must be idempotent, for example by recording processed message or business IDs.

A FIFO queue (name ends in .fifo) delivers messages in order within a MessageGroupId and removes duplicates within a five-minute deduplication window, using a MessageDeduplicationId or content-based hashing. Different groups are processed in parallel, so the group ID is your unit of ordering, such as one per customer or order. Throughput is lower: 300 API calls per second per action, 3,000 messages per second with batching, and much more in high-throughput mode.

SQS never pushes; consumers call ReceiveMessage. A received message becomes invisible for the visibility timeout (default 30 seconds, maximum 12 hours). If the consumer calls DeleteMessage it is gone; if it crashes or the timeout passes, the message reappears and its receive count increases. Long tasks can extend the timeout with ChangeMessageVisibility. For Lambda event sources, set the queue's timeout to about six times the function timeout.

A redrive policy moves a message to a dead-letter queue after maxReceiveCount receives, so poison messages do not loop forever. Alarm on DLQ depth and use DLQ redrive to move messages back after a fix. Long polling (WaitTimeSeconds up to 20) cuts empty responses and cost. Other limits: 256 KB message size (larger payloads go to S3) and retention up to 14 days.

How it works

  1. Producer sends a message (with group ID for FIFO).
  2. Consumer long-polls and receives up to 10 messages.
  3. Messages become invisible for the visibility timeout.
  4. Success: consumer deletes them.
  5. Failure or timeout: messages reappear; receive count grows.
  6. After maxReceiveCount, the redrive policy moves them to the DLQ.

Example

aws sqs create-queue --queue-name orders-dlq
aws sqs create-queue --queue-name orders --attributes '{
  "VisibilityTimeout":"180",
  "ReceiveMessageWaitTimeSeconds":"20",
  "RedrivePolicy":"{\"deadLetterTargetArn\":\"arn:aws:sqs:eu-west-1:111122223333:orders-dlq\",\"maxReceiveCount\":\"5\"}"
}'
for msg in sqs.receive_message(QueueUrl=url, MaxNumberOfMessages=10,
                               WaitTimeSeconds=20).get("Messages", []):
    order = json.loads(msg["Body"])
    if not already_processed(order["id"]):   # idempotency
        process(order)
    sqs.delete_message(QueueUrl=url, ReceiptHandle=msg["ReceiptHandle"])

Common mistakes

  • Visibility timeout shorter than processing time, causing duplicate work.
  • No DLQ, so a poison message retries until retention expires.
  • Assuming FIFO removes the need for idempotency in downstream side effects.
  • Using one FIFO message group for everything, serialising all processing.

How to answer in the interview

"Standard queues have nearly unlimited throughput with at-least-once delivery and best-effort order, so duplicates and reordering can happen. FIFO queues guarantee order within a message group and exactly-once processing through deduplication, at lower throughput. When a consumer receives a message, it is hidden for the visibility timeout; if the consumer deletes it, it is gone, otherwise it comes back, so the timeout must exceed processing time. After maxReceiveCount failures, the redrive policy sends it to a dead-letter queue. I always make consumers idempotent and use long polling."

Likely follow-up questions

  • What if processing takes longer than the visibility timeout? The message reappears and another consumer processes it too; extend visibility or raise the timeout.
  • How do you replay DLQ messages? Fix the bug, then use DLQ redrive to move them back to the source queue.
  • How do you send messages larger than 256 KB? Store the payload in S3 and send a pointer (extended client pattern).
