How can an enum be used to implement a Singleton?

Design Patterns · concept · levels mid

In one line

Declare an enum with a single constant (INSTANCE): the JVM creates it exactly once with thread-safe initialisation, and enums are safe against reflection and serialization attacks, which is why Effective Java recommends it.

Detailed explanation

An enum is a class whose instances are fixed at compile time. With one constant you get a singleton for free:

  • One instance, thread-safe: enum constants are public static final fields created during class initialisation, which the JVM performs once under a lock.
  • Reflection-proof: Constructor.newInstance throws IllegalArgumentException: Cannot reflectively create enum objects, so the usual setAccessible(true) trick fails.
  • Serialization-proof: Java serialises enums by name only and deserialises by looking up the existing constant with valueOf, so no duplicate appears and no readResolve() is needed.
  • Concise: no private constructor boilerplate or locking code.

You add fields and methods like any class, and an enum can implement interfaces, which helps testability: code depends on the interface and a test can supply a fake.

Limitations:

  • An enum cannot extend another class (it already extends java.lang.Enum).
  • It is created when the enum class initialises, not on a separate lazy trigger; usually fine because that happens on first use.
  • It still represents global state, with the same testing and coupling issues as any singleton, and its mutable fields still need thread-safe handling.
  • It cannot be subclassed or have per-test instances; constructors can't take runtime parameters.
  • Frameworks that need proxies or no-args constructors (some DI or JPA features) do not work with enums.

How it works

  1. Declare enum X { INSTANCE; } with fields and methods.
  2. First access triggers class initialisation, creating INSTANCE.
  3. All callers share X.INSTANCE.
  4. Reflection and deserialisation are handled specially by the JVM.

Example

public interface IdGenerator { long next(); }

public enum SequenceGenerator implements IdGenerator {
    INSTANCE;

    private final AtomicLong counter = new AtomicLong();

    @Override
    public long next() { return counter.incrementAndGet(); }
}

long id = SequenceGenerator.INSTANCE.next();

// Reflection attempt fails:
// SequenceGenerator.class.getDeclaredConstructors()[0].newInstance(...)
//   -> IllegalArgumentException: Cannot reflectively create enum objects

Common mistakes

  • Assuming the enum makes its mutable state thread-safe (use atomics or synchronisation).
  • Putting heavy work (I/O, network) in the enum constructor, which can fail class initialisation with ExceptionInInitializerError.
  • Using enum singletons for things that need configuration or swapping in tests.
  • Forgetting it cannot extend a base class.

How to answer in the interview

"I'd declare an enum with one constant, INSTANCE, and put the methods on it, then call ConfigService.INSTANCE.get(key). The JVM guarantees enum constants are created exactly once during thread-safe class initialisation. Enums can't be instantiated through reflection, and serialization returns the same constant, so the usual ways to break a singleton don't work. Joshua Bloch recommends it in Effective Java. The limitations are that it can't extend another class, it isn't separately lazy, and it's still global state that's hard to swap in tests, so I'd have it implement an interface."

Likely follow-up questions

  • When is an enum singleton inappropriate? When it needs to extend a class, take runtime configuration, be lazily loaded independently, or be managed and mocked by a DI container.
  • How does serialization treat enums? Only the name is written; deserialisation returns the existing constant.
  • Is its state thread-safe? Creation is; mutable fields are not automatically.
