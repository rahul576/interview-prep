How do you handle secrets in Terraform safely?

Infrastructure as Code · concept · levels mid

In one line

Never put secrets in .tf or committed tfvars; read them from a secret manager, or better let the service generate and store them (e.g. RDS manage_master_user_password); since state still holds what Terraform sees, encrypt and restrict the backend, and use ephemeral resources / write-only arguments in newer versions.

Detailed explanation

Secrets reach Terraform in several ways, from worst to best:

  1. Hard-coded in .tf or committed .tfvars: leaked to everyone with repo access, forever. Never.
  2. Sensitive variables from the CI secret store (TF_VAR_db_password, marked sensitive = true). Keeps them out of Git and logs, but the value still lands in state and in the saved plan file.
  3. Data sources reading from HashiCorp Vault, AWS Secrets Manager, Azure Key Vault or GCP Secret Manager at plan time. Centralised and rotatable, but the value read is still stored in state.
  4. Let the platform manage it: for example manage_master_user_password = true on aws_db_instance or Aurora makes RDS generate the password and store it in Secrets Manager; Terraform never sees it, and applications fetch it at runtime. Similar patterns exist for Azure managed identities and workload identity, which avoid secrets altogether.
  5. Ephemeral values (Terraform 1.10+): ephemeral resources such as ephemeral "aws_secretsmanager_secret_version" and ephemeral variables/outputs exist only during a run and are never persisted to state or plan. Write-only arguments (1.11+), like password_wo with a password_wo_version on supported resources, send a value to the provider without storing it. OpenTofu offers related features and also client-side state encryption.

Because many resources still return secrets as attributes (generated keys, random_password, connection strings), assume state is sensitive: use an encrypted backend with a customer-managed key, versioning, access only for the pipeline role and a few admins, audit logs, and never local state on laptops. sensitive = true only redacts CLI output; it does not encrypt state. Also protect saved plan files, which contain the same data, and avoid TF_LOG output in shared logs.

How it works

  1. Secret lives in a manager or is generated by the service.
  2. Terraform references it via data source, ephemeral resource or managed flag.
  3. Resources receive it at apply; write-only/ephemeral values are not stored.
  4. Anything stored in state is protected by backend encryption and IAM.
  5. Rotation happens in the secret manager, not in code.

Example

resource "aws_db_instance" "orders" {
  identifier                  = "orders"
  engine                      = "postgres"
  instance_class              = "db.t4g.medium"
  username                    = "app_admin"
  manage_master_user_password = true    # RDS + Secrets Manager own the password
}

# Terraform 1.10+/1.11+: value never written to state
ephemeral "aws_secretsmanager_secret_version" "api" {
  secret_id = "prod/payment-api-key"
}

variable "db_password" {
  type      = string
  sensitive = true   # supplied via TF_VAR_db_password from CI
}

Common mistakes

  • Thinking sensitive = true keeps values out of state.
  • Plan files with secrets uploaded as public CI artifacts.
  • Broad read access to state buckets.
  • Using random_password and forgetting it is stored in state.

How to answer in the interview

"Secrets never go into .tf files or committed tfvars. At minimum they come in as sensitive variables from the CI secret store; better, Terraform reads them from Vault, Secrets Manager or Key Vault through data sources; best, the service generates and stores them itself, like RDS manage_master_user_password, so Terraform never sees them. Since whatever Terraform reads or generates ends up in state, the backend must be encrypted, versioned and readable only by the pipeline and a few admins. Newer Terraform versions add ephemeral resources and write-only arguments so secrets don't have to be persisted at all."

Likely follow-up questions

  • Why does marking a variable sensitive not protect it in the state? It only redacts display; state stores the raw value for future comparisons.
  • How do you rotate a database password managed this way? Secrets Manager rotation; apps read it at runtime, no Terraform change.
  • Are saved plans sensitive? Yes, they contain the same values as state.
