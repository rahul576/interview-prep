How do you configure and use the AWS CLI with multiple accounts?

Cloud (AWS) · concept · levels entry

In one line

The AWS CLI reads ~/.aws/config and ~/.aws/credentials; for multiple accounts you define named profiles and select them with --profile or AWS_PROFILE, preferably using IAM Identity Center with aws sso login for short-lived credentials, assuming roles with role_arn and source_profile, and checking with aws sts get-caller-identity.

Detailed explanation

aws configure writes a default profile with region, output format and, if you supply them, access keys. That works for one account, but real organisations have many accounts: dev, staging, production, security, shared services. Long-lived access keys for each one on a laptop are a security risk.

Named profiles solve the switching problem. Each [profile name] section in ~/.aws/config describes how to get credentials for one account and role. You select a profile per command with --profile prod or for the whole shell with export AWS_PROFILE=prod. SDKs and tools such as Terraform honour the same files and variables.

The recommended source of credentials is IAM Identity Center (formerly AWS SSO). aws configure sso creates an [sso-session] block with the start URL and region, and profiles referencing it with an sso_account_id and sso_role_name. aws sso login --sso-session acme opens the browser for your corporate login and MFA, then caches short-lived tokens; every profile using that session works until the token expires. No access keys are stored.

Profiles can also assume roles: role_arn plus source_profile (or credential_source on EC2) makes the CLI call STS AssumeRole automatically, optionally requiring mfa_serial. This is common for cross-account access.

Safety habits: always run aws sts get-caller-identity before destructive commands, show the active profile in your shell prompt, give production profiles read-only roles by default, and never put keys in scripts. Precedence matters: command-line options override environment variables (AWS_ACCESS_KEY_ID etc.), which override profile settings, so stale environment variables can silently target the wrong account.

How it works

  1. aws configure sso to create the SSO session and profiles.
  2. aws sso login to get cached short-lived tokens.
  3. Choose a profile with --profile or AWS_PROFILE.
  4. The CLI exchanges the token for role credentials.
  5. Verify with aws sts get-caller-identity.

Example

# ~/.aws/config
[sso-session acme]
sso_start_url = https://acme.awsapps.com/start
sso_region = eu-west-1
sso_registration_scopes = sso:account:access

[profile dev]
sso_session = acme
sso_account_id = 111111111111
sso_role_name = Developer
region = eu-west-1

[profile prod-readonly]
sso_session = acme
sso_account_id = 222222222222
sso_role_name = ReadOnly
region = eu-west-1

[profile prod-deploy]
role_arn = arn:aws:iam::222222222222:role/Deployer
source_profile = prod-readonly
aws sso login --sso-session acme
export AWS_PROFILE=dev
aws sts get-caller-identity
aws s3 ls --profile prod-readonly

Common mistakes

  • Long-lived admin access keys in ~/.aws/credentials.
  • Leftover AWS_ACCESS_KEY_ID variables overriding the chosen profile.
  • Not checking the identity before destructive commands.
  • Using the default profile for production.

How to answer in the interview

"The CLI reads ~/.aws/config and ~/.aws/credentials. With several accounts I define named profiles, one per account and role, and pick them with --profile or AWS_PROFILE. The setup I recommend is IAM Identity Center: aws configure sso creates an SSO session, aws sso login opens the browser and caches short-lived credentials, so there are no access keys on my laptop. Profiles can also assume roles in other accounts with role_arn and source_profile. Before anything destructive I run aws sts get-caller-identity to confirm which account and role I'm using."

Likely follow-up questions

  • How do you avoid running commands in production by mistake? Read-only default role for prod, profile shown in the prompt, identity check, separate deploy role.
  • What is the credential precedence? Command-line options, then environment variables, then profile files, then container or instance roles.
  • How does CI authenticate? OIDC federation to an IAM role, not stored keys.
