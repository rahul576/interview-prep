When should you not build an agent?

AI Agents & AIOps · concept · levels mid, senior

In one line

Do not build an agent when the steps are known, when one LLM call or a workflow suffices, when errors are costly and unverifiable, when latency or cost budgets are tight, when success cannot be evaluated, or when traditional code, rules or classic ML solve it better.

Detailed explanation

Agents are the most flexible option, but also the most expensive, slow and unpredictable. Every additional model-driven step adds latency, token cost and a chance of error, and those errors compound: at 95 percent reliability per step, a 20-step run succeeds only about 36 percent of the time.

Known, fixed steps are the clearest signal. Extracting fields from an invoice, validating them and posting them to an API is a workflow with one or two model calls; letting a model choose the order adds nothing but risk. Often a single well-designed call with good retrieval and examples is enough, for example answering from a knowledge base.

Costly, unverifiable errors are another. If the agent's actions affect money, health, legal status or production systems, and there is no way to verify or review them before they take effect, autonomy adds risk without enough benefit. Agents shine where outcomes are verifiable, like code with tests.

Tight latency or cost budgets matter too: an interactive feature that must respond in 500 ms cannot run a multi-step loop, and a high-volume process at fractions of a cent per item cannot afford one.

If there is no way to evaluate success, you cannot improve, compare models or trust the agent. Build the evaluation first.

Finally, many problems are better solved without LLMs at all: deterministic code for calculations and validations, rules engines for policies, classic ML for fraud scoring or forecasting, where they are cheaper, faster, explainable and auditable.

How it works

  1. Describe the task's steps; if you can write them down, start with a workflow.
  2. Try a single call or a simple chain first and measure.
  3. Assess error cost, reversibility and whether outcomes are verifiable.
  4. Check latency and cost per task against budgets.
  5. Ensure you can evaluate success; if not, build evals first.
  6. Choose an agent only if the gain is proven over simpler baselines.

Example

Request: "Build an agent that processes expense reports."

Analysis:
- Steps known: extract -> validate policy -> route for approval -> post to ERP
- Policy rules (limits, receipts) are deterministic -> rules engine
- Unstructured part: reading receipts -> one LLM extraction call with schema
- Errors affect money; approval already human

Decision: workflow with one LLM extraction step + rules engine.
Agentic step only for "explain why this report was rejected" chat.

Common mistakes

  • Using "agent" as a buzzword requirement rather than a design choice.
  • No baseline comparison against a simpler approach.
  • Letting an LLM perform calculations or policy decisions that code should do.
  • Ignoring compounding error rates in long chains.

How to answer in the interview

"Agents are the most flexible but also the most expensive, slow and unpredictable option, so I avoid them when something simpler works. If the steps are known and fixed, like extracting invoice fields and posting them to an API, a workflow with one or two model calls is cheaper and easier to test. Often a single good call with retrieval is enough. If mistakes are costly and can't be verified before they matter, autonomy adds risk. If latency or cost budgets are tight, a multi-step loop won't fit. If there is no way to evaluate success, we can't trust or improve it. And many problems are still best solved with plain code, rules or classic ML. I use agents for open-ended tasks with verifiable outcomes, like coding with tests."

Likely follow-up questions

  • A stakeholder wants everything to be an agent? Show cost, latency and reliability of a simple baseline versus an agent on real examples, and frame it as choosing the right tool.
  • Signs a workflow should become an agent? Many branches and exceptions you keep hard-coding, with verifiable outcomes.
  • What is compounding error? Per-step failure probabilities multiply across steps, so long runs fail more often.
