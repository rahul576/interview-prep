A backfill changes historical feature values. How do you handle it without breaking reproducibility?

MLOps · scenario · levels senior, lead

In one line

Never overwrite historical feature values in place: write a new version or snapshot (Delta Lake or Iceberg versions), store features effective-dated with both event time and the time they became known, keep old training runs pointing at their snapshots, and record the backfill in an audit trail with an impact assessment.

Detailed explanation

Backfills happen for good reasons: a bug fix in feature logic, a new definition, late data. But if the backfill overwrites history, two things break. First, reproducibility: a model trained in March can no longer be retrained or explained with the data it actually saw. Second, correctness: corrected values were not available at prediction time, so training on them creates leakage—the model learns from cleaner data than it will ever get in production.

So backfills write a new version. Table formats like Delta Lake, Apache Iceberg and Apache Hudi support versioned tables and time travel, so old versions remain queryable by version number or timestamp. Alternatively, write to a new table or path with a version suffix.

Features are best stored bitemporally: the event or effective time the value applies to, and the knowledge time (ingestion or as-of time) when it became known. Point-in-time correct training sets then use values "as known at prediction time", while analysis can use corrected values. Feature stores with point-in-time joins (Feast, Databricks, SageMaker, Vertex) rely on these timestamps.

Existing training runs record which snapshot they used, so they remain reproducible. The backfill itself is documented: why, what changed, which version, which downstream models consume the feature (from lineage), and an impact assessment—compare model performance on old versus corrected features and decide whether to retrain.

How it works

  1. Write backfilled values to a new table version or path; keep the old one.
  2. Record effective time and knowledge time for each value.
  3. Update the feature registry with the new version and change notes.
  4. Use lineage to notify owners of affected models.
  5. Evaluate models on corrected data; retrain if beneficial.
  6. Expire old versions only after dependent models are retired.

Example

-- Delta Lake: backfill writes a new version; old training runs used version 41
SELECT * FROM features.customer_spend VERSION AS OF 41;     -- reproduce March model
SELECT * FROM features.customer_spend VERSION AS OF 42;     -- corrected values

-- point-in-time join using knowledge time
SELECT l.app_id, f.spend_30d
FROM labels l JOIN features.customer_spend_history f
  ON f.customer_id = l.customer_id
 AND f.known_at <= l.prediction_ts
QUALIFY ROW_NUMBER() OVER (PARTITION BY l.app_id ORDER BY f.known_at DESC) = 1;

Common mistakes

  • INSERT OVERWRITE on historical partitions without versioning.
  • Training on corrected values that weren't known at prediction time.
  • Vacuuming old table versions still used by production models.
  • Backfilling silently without telling model owners.

How to answer in the interview

"I never overwrite history in place. The backfill writes a new table version, using Delta or Iceberg time travel, while the old version stays available. Features are effective-dated with both the time a value applies to and when it became known, so training sets use values as known at prediction time and avoid leakage from corrections. Existing models keep pointing to their snapshot, so they stay reproducible. The backfill is logged with reason and scope, lineage tells us which models use the feature, and we assess impact and retrain if it helps."

Likely follow-up questions

  • How do you notify model owners? Feature registry change events and lineage-driven notifications to subscribed owners.
  • How long keep old versions? At least as long as any model trained on them is in production or under audit.
  • Is backfilled data ever right for training? Yes, if production now computes features the corrected way at serving time.
