Design a calendar and meeting scheduling service like Google Calendar.

Classic Design Problems · design · levels entry, mid, senior

In one line

A calendar service stores events with attendees, named time zones and RRULE recurrence, expands recurring events at query time with stored exceptions, answers free/busy queries, handles invitations and RSVPs, fires reminders from a scheduler, and syncs clients with CalDAV or sync tokens plus push.

Detailed explanation

The data model is the heart of the problem. An event has organiser, attendees, start/end, location, visibility and optionally a recurrence rule in iCalendar (RFC 5545) form, e.g. FREQ=WEEKLY;BYDAY=TU;UNTIL=20270630. Storing every instance of "every weekday forever" is impossible, so we store the rule and expand instances at query time for the requested range. When a single occurrence is moved or cancelled, we store an exception (a recurrence ID override or EXDATE).

Time zones must be stored as IANA names (Asia/Kolkata, Europe/London), not fixed offsets, because a 9:00 weekly meeting in London must stay at 9:00 local after daylight saving changes. All-day events are dates, not timestamps.

Free/busy is computed from attendees' expanded events, returning only busy blocks for privacy, possibly across organisations. Invitations: the organiser's event is the master; attendees get linked copies, RSVPs update the master and notify the organiser. Data is partitioned by calendar or user ID.

Reminders need a reliable scheduler: index the next trigger time per event instance, poll due reminders, send notifications. Sync uses CalDAV (for third-party clients) or an API with sync tokens for incremental changes and push notifications (webhooks, APNs/FCM) so clients refresh promptly.

How it works

  1. Create event -> store master with RRULE; write attendee copies; enqueue invitation emails.
  2. Read calendar for a week -> load events overlapping the range, expand rules, apply exceptions, convert to viewer's zone.
  3. Find a slot -> fetch free/busy for all attendees, merge busy intervals, find gaps within working hours.
  4. RSVP -> update attendee status on master, notify organiser.
  5. Scheduler computes next reminder time and fires it; recalculated on change.
  6. Clients pull deltas using sync tokens after a push notification.

Example

BEGIN:VEVENT
UID:standup-team-a@example.com
DTSTART;TZID=Europe/London:20261124T093000
DURATION:PT15M
RRULE:FREQ=WEEKLY;BYDAY=MO,TU,WE,TH,FR;UNTIL=20270630T000000Z
EXDATE;TZID=Europe/London:20261225T093000
ATTENDEE;PARTSTAT=ACCEPTED:mailto:priya@example.com
ATTENDEE;PARTSTAT=NEEDS-ACTION:mailto:arjun@example.com
END:VEVENT

Common mistakes

  • Storing UTC offsets instead of IANA time zones.
  • Materialising every recurring instance forever.
  • Forgetting exceptions when expanding rules.
  • Leaking event titles in free/busy responses.
  • Running reminders off a cron that misses or duplicates triggers.

How to answer in the interview

"Events store organiser, attendees, start and end with named time zones, and an optional RRULE. I don't materialise every recurrence; I expand rules for the requested range at query time and store exceptions for moved or cancelled instances. Free/busy merges attendees' expanded busy blocks, showing only busy time for privacy. Invitations create attendee copies and RSVPs update the organiser's master event. A scheduler indexes upcoming reminders and fires them reliably, and clients sync through CalDAV or sync tokens with push notifications."

Likely follow-up questions

  • Common free slot for 12 people in 4 zones? Fetch busy intervals in UTC, merge and sort them, sweep for gaps intersecting everyone's working hours.
  • Editing "this and following" events? Split the series: end the old rule and create a new one.
  • Very large recurring meetings? Store attendees once on the master and fan out notifications asynchronously.
