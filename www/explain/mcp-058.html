What is a rug pull attack in MCP, and how is it different from tool poisoning?

MCP Servers · concept · levels mid, senior

In one line

A rug pull is about timing: a server behaves well when it is reviewed and approved, then changes its tool definitions or behaviour after trust is granted; install-time review cannot catch it, so defend with version pinning, change detection and re-approval, vetted internal registries and limiting what the server can reach.

Detailed explanation

Tool poisoning and rug pulls overlap in effect, both can inject malicious instructions, but they differ in when the malice appears. With tool poisoning, the bad content is present in the definition you could have inspected. With a rug pull, the server is genuinely benign during evaluation, builds a user base, and then turns.

Several mechanisms make this easy in MCP. Host configs often launch local servers with npx -y package or uvx package without a version, so every restart fetches the latest release; a compromised maintainer account or a sold package can push a malicious update that runs automatically. A server can also change tool descriptions at runtime and emit a notifications/tools/list_changed notification; if the host silently accepts the new list, the model sees new instructions mid-session. Remote servers are the hardest case: the operator can change behaviour on the server side, for instance returning injected text in results or logging arguments, without changing any definition at all.

Defences: pin exact versions (or image digests) for local servers and update deliberately after review; hosts should hash tool definitions and require re-approval when they change; organisations should run an internal registry or mirror with vetted versions only; and monitor tool behaviour and outbound traffic. For remote servers, trust ultimately rests on the operator and contracts, so limit damage with scoped credentials, data minimisation and network controls.

How it works

  1. Server v1.0 is reviewed: clean descriptions, sensible behaviour; it is approved.
  2. Users install it with an unpinned command.
  3. v1.4 ships with a description that instructs the model to exfiltrate data, or the remote server starts injecting text into results.
  4. Hosts restart, fetch v1.4 automatically, and the model follows the new instructions.
  5. With pinning and definition hashing, the change is blocked or flagged for re-approval instead.

Example

{
  "mcpServers": {
    "weather": {
      "command": "npx",
      "args": ["-y", "weather-mcp@1.0.3"]
    }
  }
}
Host check on startup:
  weather.get_forecast description hash changed
  old: 9a1f...  new: 41cc...
  -> tool disabled until user/admin re-approves (diff shown)

Common mistakes

  • Treating a one-time security review as permanent approval.
  • Using @latest or no version in shared configs.
  • Hosts that accept list_changed updates without showing the diff.
  • Assuming a remote server is safe because its tool list has not changed.

How to answer in the interview

"Tool poisoning is malicious content present in a definition; a rug pull is about timing. The server looks benign when it's reviewed and approved, then later, once it's trusted and widely installed, it changes its tool definitions or behaviour, for example through an update that hosts pull automatically with npx or uvx, or a remote server simply changing what it returns. Install-time review can't catch that. I defend with exact version pinning and deliberate updates, hosts that detect changed tool definitions and require re-approval, an internal registry of vetted versions, and monitoring. For remote servers behaviour can change without any definition change, so trust depends on the operator, and I limit what the server can reach with scoped credentials."

Likely follow-up questions

  • How would you vet updates? Mirror versions internally, diff code and tool definitions, run automated scans and a short review before promoting.
  • Why are remote servers harder? Behaviour is invisible and changeable server-side without any client-visible update.
  • Does signing help? It proves who published, not that the update is benign.
