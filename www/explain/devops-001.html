What is the difference between continuous integration, continuous delivery and continuous deployment?

DevOps & CI/CD · concept · levels entry, mid

In one line

Continuous integration merges small changes often with automated build and tests; continuous delivery keeps every passing change deployable, with release to production as a manual business decision; continuous deployment automatically deploys every passing change to production.

Detailed explanation

These three practices build on each other.

Continuous integration (CI): developers integrate small changes into the main branch frequently, at least daily. Every push or pull request triggers an automated build and tests (unit tests, linting, often integration tests). If something breaks, the team knows within minutes and fixing the build is top priority. The goal is to avoid "integration hell", where long-lived branches are merged weeks later with painful conflicts and hidden bugs.

Continuous delivery (CD): extends CI so that every change that passes the pipeline produces a releasable artifact and is automatically deployed to test or staging environments. The software is always in a deployable state. Releasing to production is a business decision, often a manual approval, which suits regulated environments or products with planned release dates.

Continuous deployment: removes the manual gate. Every change that passes all automated stages goes to production automatically, often many times a day. This requires very strong automated tests, monitoring and automatic rollback, progressive delivery like canaries, and feature flags to hide incomplete features, because there is no human checkpoint.

All three depend on fast feedback, a reliable test suite and a DevOps culture where development and operations share responsibility for running software. Teams practising them typically show better DORA metrics: higher deployment frequency, shorter lead time, lower change failure rate and faster recovery.

How it works

  1. Developer pushes a small change; CI builds and tests it.
  2. On merge, an immutable artifact (for example a container image) is created.
  3. The artifact is deployed automatically to dev and staging; more tests run.
  4. Continuous delivery: a person approves the production release.
  5. Continuous deployment: production deploy happens automatically, guarded by canary analysis.
  6. Monitoring feeds back into the next change.

Example

on: { push: { branches: [main] }, pull_request: {} }
jobs:
  ci:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: ./gradlew build test
  deploy-staging:
    needs: ci
    if: github.ref == 'refs/heads/main'
    environment: staging
    runs-on: ubuntu-latest
    steps: [{ run: ./deploy.sh staging }]
  deploy-prod:
    needs: deploy-staging
    environment: production   # required reviewers = delivery; none = deployment
    runs-on: ubuntu-latest
    steps: [{ run: ./deploy.sh production }]

Common mistakes

  • Calling a nightly build "CI" while people work on branches for weeks.
  • Treating continuous delivery and deployment as the same thing.
  • Enabling continuous deployment with a weak, flaky test suite.
  • Ignoring monitoring and rollback.

How to answer in the interview

"Continuous integration means merging small changes into main frequently, with every change triggering an automated build and tests, so problems surface in minutes. Continuous delivery extends that so every passing change is always deployable and deployed to staging, and going to production is a business decision, often an approval. Continuous deployment removes that gate: every change that passes all stages goes to production automatically. All three rely on fast feedback, good automated tests and a DevOps culture; continuous deployment also needs strong monitoring, canaries and feature flags."

Likely follow-up questions

  • What must be true before continuous deployment? Reliable, fast tests, good monitoring, automatic rollback and feature flags.
  • Can regulated companies do continuous deployment? Sometimes, with automated controls and audit trails replacing manual gates.
  • How do you measure success? DORA metrics.
