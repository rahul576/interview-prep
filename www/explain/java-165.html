What makes logging good in a Java backend?

Observability · concept · levels mid, senior

In one line

Good logs are structured (JSON), use correct levels, carry a correlation or trace id via the MDC, contain no sensitive data, are written with SLF4J parameterised messages, and are emitted once per error with enough context to act on.

Detailed explanation

Logs are for the person debugging an incident at 3 a.m. They should answer what happened, to which entity, in which request, and why.

Structure: emit one JSON object per event with stable fields: timestamp, level, service, version, logger, thread, message, trace id, span id and business keys such as orderId or tenantId. Searching orderId:123 AND level:ERROR in Kibana or Loki is then trivial. Spring Boot 3.4+ supports ECS, Logstash and GELF JSON formats natively; otherwise use the Logstash Logback encoder.

Levels: ERROR for failures that need attention, WARN for unexpected but handled situations (retry succeeded, fallback used), INFO for significant business and lifecycle events (order placed, service started), DEBUG/TRACE for diagnostics, off in production but switchable at runtime via the Actuator loggers endpoint.

Context: a filter or Micrometer Tracing puts the trace id into the MDC so every line of a request carries it across services. Remember the MDC is thread-local, so context must be propagated to async executors.

Safety: never log passwords, tokens, card numbers or unnecessary personal data; mask fields and avoid logging whole request bodies. This is a GDPR and security issue, not only hygiene.

Performance and code: SLF4J placeholders (log.info("Order {} paid", id)) avoid string building when the level is off; pass the exception as the last argument so the stack trace is kept; use async appenders so slow disks or networks do not block request threads. Log an exception once, where it is handled, not at every layer it passes through.

How it works

  1. Request enters → filter sets trace id and user/tenant in the MDC.
  2. Code logs events with SLF4J and key-value context.
  3. Logback encoder writes JSON to stdout via an async appender.
  4. The platform (Fluent Bit, OTel Collector) ships logs to ELK or Loki.
  5. Queries and alerts use fields, correlated with traces by trace id.

Example

private static final Logger log = LoggerFactory.getLogger(PaymentService.class);

public void pay(Order order) {
    log.atInfo().setMessage("Payment started")
       .addKeyValue("orderId", order.id())
       .addKeyValue("amount", order.total())
       .log();
    try {
        gateway.charge(order);
    } catch (GatewayException e) {
        // logged once here, where it is handled; card number never logged
        log.error("Payment failed for order {}", order.id(), e);
        throw new PaymentFailedException(order.id(), e);
    }
}

Common mistakes

  • String concatenation in log calls, building strings that are never printed.
  • Logging and rethrowing at every layer, producing five copies of one stack trace.
  • log.error(e.getMessage()), losing the stack trace.
  • Logging tokens or full request bodies containing personal data.

How to answer in the interview

"Good logging means structured JSON logs with consistent fields, so they can be searched and aggregated. I use levels deliberately: error for things needing action, warn for handled surprises, info for key business events, debug off in production. Every line carries the trace id from the MDC, so I can follow a request across services. I never log secrets or personal data and mask anything sensitive. In code I use SLF4J placeholders, pass the exception as the last argument, use async appenders, and log each exception once at the place it's handled rather than at every layer."

Likely follow-up questions

  • How do you avoid logging the same exception five times? Log only where the exception is handled or translated at the boundary; intermediate layers just rethrow or wrap.
  • How do you keep the MDC in async code? Use a TaskDecorator or context propagation from Micrometer.
  • How do you control log cost? Sensible levels, sampling of noisy logs, retention tiers and dropping debug in production.
