What is an Elastic IP address, and when should you use one?

Cloud (AWS) · concept · levels entry

In one line

An Elastic IP is a static public IPv4 address allocated to your account until released, which you can remap between instances or network interfaces; since AWS charges for all public IPv4 addresses, use them sparingly and prefer load balancers and DNS, keeping Elastic IPs for NAT gateways and partner allow-lists.

Detailed explanation

A normal auto-assigned public IP on an EC2 instance is taken from Amazon's pool and changes when the instance is stopped and started (not on reboot). For something that must keep the same address, you allocate an Elastic IP (EIP). It belongs to your account in one region and stays yours until you release it. You associate it with an instance or an elastic network interface, and can reassociate it with another instance in seconds, which was the classic way to fail over a single-server service. You can also bring your own IP range (BYOIP).

Since February 2024, AWS charges an hourly fee for every public IPv4 address, whether attached or idle, including EIPs and auto-assigned public IPs. That makes hoarding EIPs or giving every instance a public IP wasteful, and it encourages IPv6 and private networking.

For most applications, individual IPs should not matter. Put instances in private subnets behind an Application or Network Load Balancer and use a DNS name (Route 53 alias). Instances can then be replaced and scaled without anyone noticing. Failover is handled by health checks, not by moving an IP.

Elastic IPs remain the right tool when a fixed public address is genuinely needed: a NAT gateway requires one; a partner or customer must allow-list your outbound IP, so all private instances egress through NAT gateways with known EIPs; a Network Load Balancer can use one EIP per AZ for clients that require fixed inbound IPs; and some legacy software is licensed or configured by IP. AWS Global Accelerator offers static anycast IPs for global applications.

How it works

  1. Allocate an Elastic IP in a region.
  2. Associate it with an instance, ENI, NAT gateway or NLB.
  3. Traffic to the IP routes to the associated resource.
  4. Reassociate for failover or replacement.
  5. Release it when no longer needed to stop charges.

Example

aws ec2 allocate-address --domain vpc
# { "AllocationId": "eipalloc-0abc", "PublicIp": "203.0.113.25" }
aws ec2 associate-address --allocation-id eipalloc-0abc --instance-id i-0123

# Find unassociated EIPs that still cost money
aws ec2 describe-addresses --query "Addresses[?AssociationId==null].PublicIp"

A bank partner only accepts webhook calls from known IPs: the private application servers egress through two NAT gateways, and the two EIPs are given to the partner.

Common mistakes

  • Using EIPs instead of a load balancer for scaling and failover.
  • Leaving unattached EIPs allocated.
  • Giving every instance a public IP unnecessarily.
  • Hard-coding IPs in clients instead of DNS names.

How to answer in the interview

"An Elastic IP is a static public IPv4 address that belongs to my account until I release it. I can associate it with an instance or network interface and remap it quickly. A normal public IP changes when an instance stops and starts; an Elastic IP doesn't. AWS charges for every public IPv4 address, so I avoid hoarding them. For most apps I'd use a load balancer and DNS names so individual IPs don't matter. Elastic IPs are still right for NAT gateways and when a partner needs to allow-list a fixed outbound IP."

Likely follow-up questions

  • One fixed outbound IP for private instances? Route them through a NAT gateway with an Elastic IP.
  • Fixed inbound IPs for a load-balanced service? NLB with EIPs per AZ, or Global Accelerator.
  • Does an EIP survive instance stop? Yes, the association remains.
