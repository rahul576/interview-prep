How do you package a trained model for deployment, and why are pickle files risky?

MLOps · concept · levels mid, senior

In one line

A deployable model is the weights plus preprocessing, input/output schema and pinned dependencies, usually packaged in a framework-native, ONNX or MLflow format inside a container image; pickle is risky because loading a pickle can execute arbitrary code, so prefer safetensors or ONNX, trusted signed sources and artefact scanning.

Detailed explanation

Weights alone are not a model you can deploy. The serving system also needs the preprocessing (tokeniser, encoders, scalers, vocabularies), the signature describing expected inputs and outputs, and the exact runtime dependencies. If preprocessing lives in a separate script that the serving team re-implements, you get training-serving skew. Bundling it, for example in a scikit-learn Pipeline or an MLflow pyfunc model, keeps them together.

Common formats: framework-native files (PyTorch state dicts, TensorFlow SavedModel), pickle/joblib for scikit-learn, ONNX for a portable, framework-independent graph that runs fast in ONNX Runtime, and the MLflow Models format, which wraps a model with its flavour, signature and environment (conda or pip requirements). The package is then built into a container image with pinned versions and a serving layer (FastAPI, KServe runtime, Triton), so the same artefact runs identically in staging and production.

Pickle is not a data format but a small program for Python's unpickler; a crafted file can call os.system during pickle.load. A malicious model from a public hub, or a file swapped in a compromised bucket, can therefore take over the serving host or a data scientist's laptop. joblib and older torch.load behaviour inherit this risk (recent PyTorch defaults to weights_only=True, which helps but does not remove all risk). safetensors stores only tensors, with no code execution, and ONNX stores a graph. Controls: load only from a trusted registry, verify hashes and signatures, scan artefacts (tools such as ModelScan or hub-side scanners), and run serving with least privilege.

How it works

  1. Train and bundle preprocessing with the model (pipeline or custom wrapper).
  2. Save in a safe, appropriate format and record the input/output signature.
  3. Generate a lock file of exact dependencies.
  4. Build a container image with the serving layer; scan and sign it.
  5. Register model and image in the registry with hashes.
  6. Serving loads only signed artefacts from the registry.

Example

from safetensors.torch import save_file, load_file
import mlflow

save_file(model.state_dict(), "model.safetensors")       # tensors only, no code
state = load_file("model.safetensors")                    # safe to load

# MLflow bundles model, signature and environment
mlflow.sklearn.log_model(pipeline, "model",
                         signature=mlflow.models.infer_signature(X_sample, pipeline.predict(X_sample)))

Common mistakes

  • Shipping weights without the exact tokeniser or scaler used in training.
  • Unpinned dependencies, so a new library version changes predictions.
  • Calling pickle.load on files downloaded from the internet.
  • Treating model files as data rather than as executable supply-chain artefacts.

How to answer in the interview

"A deployable model is more than weights: it needs its preprocessing, an input and output signature and pinned dependencies. I package it in a framework-native, ONNX or MLflow format and build a container image with a serving layer, so it runs the same everywhere. Pickle is dangerous because unpickling can execute arbitrary code, so a malicious file from a hub or a tampered bucket can compromise the host. I prefer safetensors or ONNX for weights, load only from a trusted registry, verify hashes or signatures and scan artefacts in CI."

Likely follow-up questions

  • Why is a model hub download a supply chain risk? Files can contain executable payloads or backdoored weights, and names can be typosquatted.
  • Is ONNX always better? It is portable and fast, but not every custom operation converts cleanly, so validate outputs after conversion.
  • Should preprocessing live in the model? Yes where possible, so training and serving cannot diverge.
