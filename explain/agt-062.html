How would you use an AI agent to diagnose and fix failing CI pipelines?

AI Agents & AIOps · scenario · levels mid, senior

In one line

A CI agent reads failing job logs and recent changes, classifies the failure (code, flaky test, infrastructure, dependency), proposes a fix as a comment or pull request, re-runs flaky jobs within limits, runs sandboxed with limited credentials, and humans review every fix.

Detailed explanation

Developers lose a lot of time on red pipelines: scrolling through thousands of log lines, guessing whether the failure is theirs or the runner's, and re-running jobs hoping they pass. An agent can do the first pass.

It gathers context: the failing job log (trimmed to the failing step and error region), the diff of the commit or pull request, recent changes to the pipeline definition, lockfiles and base images, and the history of the failing test. It then classifies: a genuine failure caused by the change (compile error, assertion failure in touched code), a known flaky test (fails intermittently across unrelated commits), an infrastructure problem (runner out of disk, network timeout, registry rate limit) or a dependency issue (new upstream version broke the build).

For code failures, it explains the cause in a PR comment and can open a fix commit or pull request with tests passing. For flaky tests or transient infrastructure errors it may re-run the job, but with a limit, and records the flake so it is tracked and fixed rather than hidden. Security matters: logs and code can contain untrusted content (a PR from a fork can include prompt injection), so the agent runs in a sandbox with no production secrets and minimal repository permissions. Humans review any fix before merge.

How it works

  1. Pipeline fails; webhook starts the agent with job ID and PR context.
  2. Fetch the failing step's log, diff and test history.
  3. Classify the failure with evidence.
  4. Code issue: reproduce in sandbox, write fix, run tests, open PR or suggestion.
  5. Flake or infra: re-run once or twice, log to flake tracker, notify owners.
  6. Post a summary comment; humans decide.

Example

# GitHub Actions: trigger the agent when CI fails
on:
  workflow_run:
    workflows: ["ci"]
    types: [completed]
jobs:
  diagnose:
    if: github.event.workflow_run.conclusion == 'failure'
    runs-on: ubuntu-latest
    permissions: { contents: read, pull-requests: write, actions: read }
    steps:
      - run: ci-agent diagnose --run-id ${{ github.event.workflow_run.id }} --max-reruns 1
ci-agent: Classified as DEPENDENCY. jackson-databind 2.18 → 2.19 via lockfile refresh;
UserMapperTest fails on changed null handling (log line 1842). Proposed PR #612 pins 2.18.2.

Common mistakes

  • Auto-retrying until green, hiding real flakiness.
  • Giving the agent deploy or production secrets.
  • Feeding the whole multi-megabyte log to the model.
  • Letting the agent push directly to main.

How to answer in the interview

"The agent reads the failing job log, the PR diff and recent pipeline and dependency changes, and classifies the failure: a real code problem, a known flaky test, an infrastructure issue or a broken dependency. For code issues it explains the cause and can propose a fix as a PR with passing tests. For flakes or transient infra errors it may re-run, with a strict limit, and records the flake so it gets fixed. It runs in a sandbox with limited credentials and no production secrets, since logs and code are untrusted, and humans review every fix."

Likely follow-up questions

  • Agent modifying pipeline definitions? Risky: could weaken checks or exfiltrate secrets; require code-owner review.
  • Fork PRs? No secrets; read-only analysis only.
  • Measure value? Time to green and accepted fixes.
