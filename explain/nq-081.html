What is dirty writing, and how can concurrent access cause inconsistent results?

Concurrency · concept · levels mid

In one line

A dirty write is when one thread or transaction overwrites data that another has written but not yet finished or committed, so updates are lost or the data ends up as an inconsistent mix; prevent it with locks, synchronisation, transaction isolation or optimistic locking.

Detailed explanation

The term comes from database theory: a dirty write (phenomenon P0 in the ANSI isolation discussion) happens when transaction T2 overwrites a value written by T1 before T1 commits or rolls back. If T1 then rolls back, should it restore its old value and wipe T2's change? The outcome becomes undefined. Every real database isolation level, even Read Uncommitted, prevents dirty writes with row write locks held until commit. The closely related, and much more common, problem is the lost update: two transactions both read a row, both compute a new value, and the second write silently overwrites the first.

The same pattern appears in memory in Java. If two threads update several fields of a shared object without synchronisation, writes interleave. Thread A sets balance = 900 and is about to set lastUpdated, while thread B sets balance = 1100 and lastUpdated. The final object can show B's balance with A's timestamp, or a balance that ignores one of the operations entirely. Readers may also see a half-updated object. The cause is the same: concurrent read-modify-write without coordination.

Prevention in Java: guard the whole compound update with one lock (synchronized or ReentrantLock), replace the object atomically (an immutable value in an AtomicReference updated with updateAndGet), or confine the state to one thread.

Prevention in databases: rely on transactions and appropriate isolation; use pessimistic locking (SELECT ... FOR UPDATE); use atomic conditional updates (UPDATE account SET balance = balance - 100 WHERE id = ? AND balance >= 100); or use optimistic locking with a version column, as JPA's @Version does: the update includes WHERE version = ?, and if no row matches, an OptimisticLockException is thrown and the application retries or reports a conflict.

How it works

  1. Two actors read the same state.
  2. Each computes a change based on what it read.
  3. Both write, without coordination; the later write overwrites the earlier.
  4. Result: lost update or a mix of both writes.
  5. With a lock or version check, the second writer either waits or is rejected and retries.

Example

@Entity
class Account {
    @Id Long id;
    BigDecimal balance;
    @Version long version;          // optimistic locking
}

@Transactional
void withdraw(long id, BigDecimal amount) {
    Account a = repo.findById(id).orElseThrow();
    a.setBalance(a.getBalance().subtract(amount));
    // Hibernate issues: UPDATE account SET balance=?, version=version+1
    //                   WHERE id=? AND version=?
    // 0 rows updated -> OptimisticLockException -> retry or 409 Conflict
}
-- Atomic alternative without read-modify-write in the app
UPDATE account SET balance = balance - 100 WHERE id = 42 AND balance >= 100;

Common mistakes

  • Assuming @Transactional alone prevents lost updates at Read Committed.
  • Updating related fields under different locks or no lock.
  • Catching OptimisticLockException and ignoring it.
  • Doing read-modify-write in application code when an atomic SQL update would do.

How to answer in the interview

"A dirty write is when one thread or transaction overwrites data another has written but not yet finished or committed, so one change silently wins, or the data ends up as a mix of both. In Java, two threads updating fields of the same account object without synchronisation can leave one thread's balance with the other's timestamp. In databases the common form is the lost update, where two transactions read, modify and write the same row. The cure is coordination: synchronized or locks around compound updates in memory, and in databases row locks, the right isolation level, atomic conditional updates or optimistic locking with a version column, like JPA's @Version."

Likely follow-up questions

  • How does JPA optimistic locking detect a conflicting write? It adds WHERE version = ? to the update and increments the version; if zero rows are updated, someone else changed the row first.
  • Optimistic or pessimistic locking? Optimistic for low contention and user think time; pessimistic for hot rows with frequent conflicts.
  • What is a dirty read? Reading another transaction's uncommitted data, allowed only at Read Uncommitted.
