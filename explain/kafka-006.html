What does exactly-once in Kafka really guarantee, and where does it stop?

Kafka · concept · levels senior, lead

In one line

Kafka exactly-once semantics (EOS) combines the idempotent producer and transactions so a consume-transform-produce loop writes outputs and input offsets atomically for read_committed consumers; it stops at Kafka's boundary, so external side effects need outbox or idempotent writes.

Detailed explanation

There are three building blocks. The idempotent producer gets a producer ID (PID) and attaches a sequence number per partition to each batch; the broker discards duplicates caused by retries. This gives exactly-once writes per partition per producer session.

Transactions extend this across partitions. A producer configured with a stable transactional.id calls beginTransaction, sends records to several topics, adds the consumer's offsets with sendOffsetsToTransaction, then commitTransaction. A transaction coordinator writes commit or abort markers. The transactional.id also enables zombie fencing: when a restarted instance initialises with the same ID, the epoch increases and the old instance's writes are rejected.

Consumers must set isolation.level=read_committed to skip aborted records and records from open transactions. Kafka Streams packages all of this with processing.guarantee=exactly_once_v2.

The boundary matters. If your consumer charges a card, sends an email or updates PostgreSQL, that action is not part of the Kafka transaction. A crash after the external call but before the commit leads to reprocessing and a second charge. For those cases, make the external effect idempotent (unique event ID as a key, INSERT ... ON CONFLICT DO NOTHING, payment API idempotency keys), or use the transactional outbox pattern to write the database change and the event together. EOS also does not protect against data loss from poor durability settings: you still need acks=all and min ISR.

How it works

  1. Producer initTransactions() registers transactional.id and fences zombies.
  2. Consumer polls input records.
  3. beginTransaction(), process, send outputs.
  4. sendOffsetsToTransaction(offsets, groupMetadata).
  5. commitTransaction(); on error, abortTransaction() and reprocess.

Example

producer.initTransactions();
while (true) {
  var records = consumer.poll(Duration.ofMillis(500));
  producer.beginTransaction();
  for (var r : records) producer.send(new ProducerRecord<>("enriched", r.key(), enrich(r.value())));
  producer.sendOffsetsToTransaction(offsets(records), consumer.groupMetadata());
  producer.commitTransaction();
}

Common mistakes

  • Believing EOS covers database writes or HTTP calls inside the consumer.
  • Forgetting read_committed on downstream consumers.
  • Using a random transactional.id per start, which disables fencing.
  • Relying on EOS while running acks=1.

How to answer in the interview

"Exactly-once in Kafka has two parts. The idempotent producer uses a producer ID and sequence numbers so the broker drops retried duplicates. Transactions with a transactional.id let a consume-transform-produce app commit its output records and its input offsets atomically, and read_committed consumers only see committed data; Kafka Streams wraps this as exactly_once_v2. But it stops at Kafka: if my consumer writes to a database or calls a payment API, I need idempotent writes keyed by an event ID or the outbox pattern."

Likely follow-up questions

  • Write landed on one replica that died? EOS does not help; durability comes from acks=all and min ISR.
  • What is zombie fencing? Epoch bump on the transactional.id rejects writes from an old instance.
  • Cost of transactions? Extra latency per commit; batch more records per transaction.
