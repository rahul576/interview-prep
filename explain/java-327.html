Explain the Maven build lifecycle and dependency scopes.

Build Tools · concept · levels entry

In one line

Maven's default lifecycle runs ordered phases — validate, compile, test, package, verify, install, deploy — where running a phase runs all earlier ones and plugins bind goals to phases; dependency scopes (compile, provided, runtime, test, plus system and import) control which classpaths a dependency is on.

Detailed explanation

Maven has three built-in lifecycles: clean, default (the build) and site. The default lifecycle is a fixed sequence of phases. The key ones are:

  • validate – check the project is correct.
  • compile – compile main sources.
  • test – run unit tests (Surefire).
  • package – create the JAR or WAR in target/.
  • verify – run integration tests and checks (Failsafe, quality gates).
  • install – copy the artifact into the local repository (~/.m2/repository) so other local projects can use it.
  • deploy – publish the artifact to a remote repository such as Nexus or Artifactory.

Phases themselves do nothing; plugin goals bound to them do the work. The packaging type (jar, war, pom) defines default bindings, for example compiler:compile to compile and surefire:test to test. Running mvn package executes every phase up to and including package.

Dependency scopes decide where a dependency is visible and whether it is transitive:

  • compile (default): needed to compile and run, on all classpaths, transitive.
  • provided: needed to compile, but supplied at runtime by the environment, such as the Servlet API in Tomcat or Lombok at compile time; not packaged.
  • runtime: not needed to compile, but needed to run, such as a JDBC driver.
  • test: only for compiling and running tests, like JUnit and Mockito.
  • system (discouraged) points to a local file; import is used in dependencyManagement to import a BOM.

How it works

  1. Maven reads pom.xml and resolves dependencies.
  2. You run a phase, e.g. mvn verify.
  3. Maven executes all earlier phases in order.
  4. Each phase runs its bound plugin goals.
  5. install and deploy publish to local and remote repositories.

Example

<dependencies>
  <dependency>
    <groupId>org.postgresql</groupId>
    <artifactId>postgresql</artifactId>
    <scope>runtime</scope>
  </dependency>
  <dependency>
    <groupId>jakarta.servlet</groupId>
    <artifactId>jakarta.servlet-api</artifactId>
    <scope>provided</scope>
  </dependency>
  <dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <scope>test</scope>
  </dependency>
</dependencies>
mvn clean package      # compile, test, build jar
mvn install            # also copy into ~/.m2
mvn deploy             # also publish to Nexus

Common mistakes

  • Putting JUnit in compile scope, shipping it in production.
  • Using compile scope for the Servlet API in a WAR, causing classloader conflicts.
  • Running mvn install in CI when mvn verify is enough.
  • Thinking phases run independently of earlier ones.

How to answer in the interview

"Maven's default lifecycle runs phases in order: validate, compile, test, package, verify, install and deploy. Running a phase runs all earlier ones, and plugins bind goals to phases, like Surefire for tests. Scopes control the classpath: compile is the default and available everywhere; provided is needed to compile but supplied at runtime by the container, like the Servlet API; runtime is needed only to run, like a JDBC driver; and test is only for tests. install puts the artifact in the local repository, and deploy publishes it to a remote repository like Nexus."

Likely follow-up questions

  • mvn package vs mvn install? package builds the artifact in target; install also copies it to the local repository for other projects.
  • What does clean do? A separate lifecycle that deletes the target directory.
  • What is the import scope? Imports a BOM's dependencyManagement into yours.
