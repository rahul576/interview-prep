The Terraform state file was corrupted or lost. How do you recover?

Infrastructure as Code · scenario · levels senior

In one line

Stop all applies first, then restore the last good version from backend versioning and confirm with a plan showing no unexpected changes; with no backup, rebuild state by importing existing resources (import blocks, generated config) until the plan is clean; prevent it with a versioned, encrypted, locked backend and restricted access.

Detailed explanation

A missing or corrupted state is dangerous mainly because of what Terraform does next: with an empty state it believes nothing exists and will try to create everything again, failing on name conflicts or, worse, creating duplicates. With a corrupted or old state it may plan to delete or replace resources. So the first action is containment, not repair.

Contain. Pause pipelines for that stack, tell the team, and keep the lock held or revoke apply permissions.

Restore from versions. S3 with versioning, Azure Blob with versioning or soft delete, GCS object versioning and HCP Terraform state history all keep previous versions. Find the last good one (by timestamp and the serial/lineage fields), restore it, and run terraform plan. The plan should be empty, or show only changes applied after that version, which you then reconcile. With the older S3 backend setup using DynamoDB locking, a stored checksum (digest) may need updating after a manual restore; newer Terraform versions can lock with an S3 lock file instead of DynamoDB.

Rebuild if there is no backup. Create a fresh state and adopt resources with import blocks. terraform plan -generate-config-out=generated.tf can draft configuration for imported resources, and an inventory from the cloud (resource explorer, tags, tools like Terraformer) gives the list of IDs. Iterate until the plan shows no changes.

Prevent. Versioned, encrypted backend with locking, MFA delete or object lock where appropriate, cross-region replication, write access only for pipeline roles, and no manual state push.

How it works

  1. Freeze applies; copy current state for analysis.
  2. List object versions and identify the last good serial.
  3. Restore it; run terraform plan.
  4. If no backup: import resources in batches with import blocks.
  5. Clean plan, then re-enable pipelines.

Example

aws s3api list-object-versions --bucket acme-tfstate \
  --prefix prod/network/terraform.tfstate --query 'Versions[].[VersionId,LastModified]'
aws s3api get-object --bucket acme-tfstate --key prod/network/terraform.tfstate \
  --version-id "3HL4kqtJlcpXroDTDmJ" restored.tfstate
terraform state push restored.tfstate   # deliberate, one-off, lock held
terraform plan
import {
  to = aws_vpc.main
  id = "vpc-0a1b2c3d4e5f"
}

Common mistakes

  • Running apply on an empty state "to see what happens".
  • Restoring a version without checking it with a plan.
  • Importing and "fixing" configuration in the same step, causing unplanned changes.

How to answer in the interview

"First I stop every pipeline for that stack, because an apply against an empty or broken state could try to recreate or delete everything. If the backend has versioning, I find the last good version, restore it and run a plan, which should show no changes or only ones I can explain. Without a backup I rebuild the state by importing existing resources with import blocks, using generate-config-out and a cloud inventory, iterating until the plan is clean. Then prevention: versioned, encrypted backend with locking, restricted write access, and no manual state pushes."

Likely follow-up questions

  • How could you generate import blocks for hundreds of resources? Script them from a cloud inventory by tags or resource IDs, then use generated config as a starting point.
  • What are serial and lineage? Serial increments per write; lineage identifies one state history and prevents mixing states.
  • What if the state is fine but the lock is stuck? Confirm no run is active, then terraform force-unlock with the lock ID.
