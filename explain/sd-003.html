Your service has outgrown a single server. How do you decide between scaling up and scaling out, for the app tier and for the database?

SD Fundamentals · scenario · levels entry, mid

In one line

Scale up (a bigger machine) first when it is cheap and simple; scale out (more machines) when you hit limits, need availability, or the workload is easy to split. Stateless app tiers scale out easily; databases usually scale up first.

Detailed explanation

Vertical scaling adds CPU, memory or faster disks to one server. It needs no code change, keeps transactions and joins simple, and is often surprisingly far-reaching: a modern database server with 64+ cores and hundreds of GB of RAM handles a lot. But it has a ceiling, cost grows non-linearly, and the machine remains a single point of failure.

Horizontal scaling adds instances behind a load balancer. For stateless services this is easy: move sessions to Redis or tokens, and autoscale. For stateful data it is harder: you need read replicas for reads and partitioning (sharding) for writes, which introduces cross-shard queries and consistency issues.

How it works

  1. Measure: CPU, memory, I/O, connections, latency percentiles.
  2. App tier: make it stateless, put it behind a load balancer, autoscale on CPU or requests.
  3. Database: optimise queries and indexes → add cache → read replicas → scale up the primary → shard when writes or size require it.
  4. Keep redundancy in every tier so one machine failing isn't an outage.

Example

An API at 2,000 requests/s with one 8-core VM at 85% CPU: run four smaller instances behind a load balancer with autoscaling. Its PostgreSQL primary at 70% CPU from reads: add Redis caching and two read replicas before considering sharding.

Common mistakes

  • Sharding a database that a bigger instance plus caching would handle for years.
  • Scaling out an app that keeps sessions in memory, then fighting sticky sessions.
  • Ignoring that more app instances means more database connections.

How to answer in the interview

"For the application tier I'd scale out: make it stateless, put it behind a load balancer and autoscale. For the database I'd first optimise and cache, add read replicas, and scale the primary up, because sharding adds a lot of complexity. I'd shard only when write volume or data size truly needs it, choosing a key that matches the access pattern."

Likely follow-up questions

  • What makes a service stateless? No per-user data in memory between requests; state lives in shared stores.
  • When must you shard? When write throughput or dataset size exceeds a single primary.
  • What breaks when you add many app instances? Database connection limits; use pooling or a proxy like PgBouncer.
