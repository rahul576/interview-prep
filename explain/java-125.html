How do you manage configuration and profiles in Spring Boot?

Spring Boot · concept · levels entry, mid

In one line

Put defaults in application.yml, override per environment with profile-specific files activated by spring.profiles.active, bind settings into validated @ConfigurationProperties classes, inject environment values through Boot's externalised configuration precedence, and keep secrets out of files.

Detailed explanation

Spring Boot merges configuration from many property sources into the Environment. The usual layout: application.yml holds shared defaults; application-dev.yml, application-prod.yml hold profile-specific overrides. A profile is activated with spring.profiles.active=prod, typically via the SPRING_PROFILES_ACTIVE environment variable. Profile groups (spring.profiles.group.prod=postgres,metrics) bundle profiles, and spring.config.activate.on-profile lets one YAML file contain several profile documents.

Precedence matters: later, more specific sources win. From low to high, roughly: defaults, application.yml in the jar, profile-specific files, files outside the jar (./config/), OS environment variables, Java system properties, and command-line arguments. Environment variables use relaxed binding, so SPRING_DATASOURCE_URL sets spring.datasource.url. That is how containers and Kubernetes ConfigMaps inject values without rebuilding the image. spring.config.import can pull in extra files, a config tree (mounted Kubernetes secrets) or Config Server.

For your own settings, prefer @ConfigurationProperties over scattered @Value. It gives a type-safe, immutable (records work) object, relaxed binding, IDE metadata, and validation with @Validated so the app fails at startup on bad values.

Secrets do not belong in committed files. They come from Vault, a cloud secret manager or Kubernetes Secrets, via environment variables, config trees or Spring Cloud integrations. Spring Cloud Config Server can centralise non-secret configuration for many services, backed by Git.

How it works

  1. Boot loads property sources in a defined order.
  2. Active profiles add their specific files.
  3. Higher-precedence sources override lower ones key by key.
  4. @ConfigurationProperties beans are bound and validated.
  5. Beans receive the bound objects through injection.

Example

# application.yml
orders:
  payment:
    base-url: http://localhost:8089
    timeout: 2s
    max-retries: 2
---
spring:
  config:
    activate:
      on-profile: prod
orders:
  payment:
    base-url: https://payments.internal
@ConfigurationProperties("orders.payment")
@Validated
public record PaymentProperties(@NotNull URI baseUrl, Duration timeout, @Min(0) int maxRetries) {}

@SpringBootApplication
@ConfigurationPropertiesScan
class App { }
SPRING_PROFILES_ACTIVE=prod ORDERS_PAYMENT_TIMEOUT=3s java -jar orders.jar

Common mistakes

  • Passwords in application-prod.yml committed to Git.
  • Dozens of @Value annotations with no validation.
  • Profile-specific logic sprinkled through code with @Profile instead of configuration.
  • Not knowing which source won; check /actuator/env (secured) or the startup log.

How to answer in the interview

"Shared defaults live in application.yml, with profile-specific files such as application-prod.yml activated through spring.profiles.active, usually set as an environment variable. I bind related settings into @ConfigurationProperties classes, often records, with @Validated, so config is type-safe and the app fails fast on bad values instead of using scattered @Value. Boot externalises configuration with a defined precedence, so environment variables and command-line arguments override the files; that's how Kubernetes ConfigMaps inject values. Secrets never go in config files; they come from Vault, a cloud secret manager or Kubernetes secrets, and Config Server can centralise the rest."

Likely follow-up questions

  • How would you reload configuration without restarting? Spring Cloud @RefreshScope with /actuator/refresh or Spring Cloud Kubernetes reload, or simply a rolling restart.
  • What is relaxed binding? orders.payment.base-url, ORDERS_PAYMENT_BASEURL and baseUrl all map to the same property.
  • @Profile on beans? Fine for swapping implementations, but keep it rare.
