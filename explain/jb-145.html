What is an execution plan, and how do you use it to optimize slow queries?

Databases & SQL · scenario · levels mid, senior

In one line

An execution plan is the optimizer's step-by-step strategy for running a query (access paths, join order, join algorithms, sorts, estimated rows); you read it with EXPLAIN / EXPLAIN ANALYZE, find the expensive or mis-estimated step, fix it, and verify the new plan.

Detailed explanation

SQL says what you want; the cost-based optimizer decides how. It uses statistics (row counts, value distributions, distinct values, correlations) to estimate the cost of alternatives: sequential scan vs index scan vs index-only scan, nested loop vs hash join vs merge join, the join order, and whether to sort or read pre-sorted index data.

EXPLAIN shows the chosen plan with estimates. EXPLAIN ANALYZE (PostgreSQL, MySQL 8.0.18+) actually executes the query and adds actual rows, loops and time per node; in PostgreSQL add BUFFERS to see I/O. Be careful running it on UPDATE or DELETE: wrap it in a transaction and roll back. Oracle uses EXPLAIN PLAN and DBMS_XPLAN.DISPLAY_CURSOR, and SQL Server has actual execution plans.

What to look for:

  • Seq Scan / full table scan on a large table where few rows are needed.
  • Estimated vs actual rows differing by orders of magnitude: stale statistics, correlated columns, or skewed data. This often causes a nested loop that runs millions of times.
  • Expensive Sort nodes or sorts spilling to disk ("external merge"), or hashes exceeding work_mem.
  • Rows Removed by Filter being huge: an index exists but doesn't match the predicate well.
  • Plans that read the table repeatedly through correlated subqueries.

How it works

  1. Capture the real query and representative parameters.
  2. Run EXPLAIN (ANALYZE, BUFFERS) and read it bottom-up, inner nodes first.
  3. Find the node with the most time and check row estimates.
  4. Form a hypothesis: missing index, non-sargable predicate, stale stats, bad join order.
  5. Apply one change: index, rewrite, ANALYZE, extended statistics, query restructuring.
  6. Re-run and compare time, rows and buffers; monitor in production.

Example

EXPLAIN (ANALYZE, BUFFERS)
SELECT c.name, SUM(o.total)
FROM orders o JOIN customer c ON c.id = o.customer_id
WHERE o.created_at >= '2026-11-01'
GROUP BY c.name;

-- Seq Scan on orders (cost=... rows=1200) (actual rows=4,800,000) -> estimates off
--   Filter: created_at >= '2026-11-01'  Rows Removed by Filter: 40,000,000
ANALYZE orders;
CREATE INDEX CONCURRENTLY idx_orders_created ON orders (created_at) INCLUDE (customer_id, total);
-- Re-run: Index Only Scan + Hash Join, 9.8 s -> 310 ms

Common mistakes

  • Reading only total cost numbers, which are unitless estimates, not milliseconds.
  • Testing on a tiny dev database where plans differ completely.
  • Running EXPLAIN ANALYZE on a destructive statement without rollback.
  • Forcing hints instead of fixing statistics or indexes.

How to answer in the interview

"An execution plan shows how the optimizer will run a query: which indexes or scans it uses, the join order and algorithms like nested loop or hash join, sorts, and estimated row counts. I get it with EXPLAIN, and preferably EXPLAIN ANALYZE with buffers, which runs the query and shows actual rows and time per step. I look for full scans on large tables, expensive sorts, nested loops over many rows, and big gaps between estimated and actual rows, which usually mean stale statistics. Then I add or adjust an index, rewrite the query or run ANALYZE, and re-check the plan and timing to confirm the improvement."

Likely follow-up questions

  • Estimated rows far lower than actual? Stale or insufficient statistics or correlated columns; the optimizer may choose a nested loop wrongly.
  • Why would the optimizer choose a seq scan despite an index? The query returns a large fraction of rows, so a sequential read is cheaper.
  • How do you find slow queries in the first place? Slow query log, pg_stat_statements, APM traces.
