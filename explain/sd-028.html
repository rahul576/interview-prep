Design a collaborative document editor like Google Docs.

Classic Design Problems · design · levels senior, lead

In one line

Collaborative editing sends small operations over WebSockets, applies them locally first, and resolves concurrent edits with operational transformation (OT) or CRDTs, with a per-document session server, an operation log plus snapshots, and ephemeral presence.

Detailed explanation

If two users type at the same time, positions shift: Alice inserts at 5 while Bob deletes at 3. Naively applying both gives different documents on each screen. OT transforms an incoming operation against those already applied (Bob's delete shifts Alice's insert to 4). It needs a central server to define the order, which is how Google Docs works.

CRDTs (Yjs, Automerge) give each character a unique, ordered identity so replicas merge in any order and still converge. They naturally support offline and peer-to-peer editing, at the cost of metadata overhead (mitigated by modern implementations).

Either way, the client applies edits optimistically for instant feedback. A session server per document (selected by consistent hashing on doc ID) orders operations, broadcasts them and appends them to a durable operation log; periodic snapshots make loading fast and power version history.

How it works

  1. Open doc → load latest snapshot + ops since → connect WebSocket to doc's session server.
  2. Local edit → apply locally → send op with base revision.
  3. Server transforms (OT) or merges (CRDT), assigns revision, persists, broadcasts.
  4. Clients apply remote ops (transforming against pending local ops).
  5. Cursors/presence broadcast but not stored long-term.

Example

Doc: "abc"   Alice: insert("X", 3) → "abcX"   Bob: delete(0) → "bc"
Server orders Bob first; transforms Alice's insert to position 2 → "bcX" on both clients

Common mistakes

  • Last-writer-wins on the whole document.
  • Storing every keystroke forever without snapshots.
  • Multiple servers handling the same document without coordination.

How to answer in the interview

"Each client applies edits locally and sends operations over a WebSocket to the session server that owns the document. Concurrent edits are reconciled with OT, the Google Docs approach, or a CRDT like Yjs if offline editing matters. The server persists an operation log with periodic snapshots for fast loading and version history, while cursors and presence are ephemeral broadcasts."

Likely follow-up questions

  • OT or CRDT for a new product? CRDT (Yjs) if offline/peer features matter; OT if you have a central server and want proven simplicity.
  • How do you scale to many docs? Shard documents across session servers by doc ID.
  • How do you handle comments and suggestions? Anchored to stable positions/IDs in the model.
