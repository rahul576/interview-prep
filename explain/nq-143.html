Why is volatile used in double-checked locking?

Design Patterns · concept · levels mid, senior

In one line

volatile is needed because instance = new Singleton() is not atomic and may be reordered, so another thread could see a non-null reference to a half-initialised object; volatile's happens-before guarantee (Java 5+ memory model) prevents that.

Detailed explanation

Creating an object conceptually takes three steps: allocate memory, run the constructor to initialise fields, and assign the reference to the variable. The Java Memory Model allows the compiler, JIT and CPU to reorder operations as long as a single thread cannot tell the difference. So the reference may be published (step 3) before the constructor's field writes (step 2) are visible to other cores.

In double-checked locking, the first null check runs outside the synchronized block. Thread A, inside the lock, is constructing the singleton. Thread B performs the unlocked check, sees a non-null instance, skips synchronisation, and calls a method that reads fields still at default values (null, 0). Thread B never entered the lock, so the lock's memory guarantees do not apply to it. The result is rare, timing-dependent, hardware-dependent bugs.

Declaring the field volatile fixes it. Under the revised memory model from JSR-133 (Java 5), a write to a volatile variable happens-before every subsequent read of that variable. Everything thread A did before the volatile write, including all constructor writes, is visible to any thread that later reads the reference. Volatile also guarantees visibility: no thread keeps reading a stale cached null. Note that volatile does not make compound actions atomic; mutual exclusion still comes from the synchronized block.

The holder idiom avoids all this: the JVM initialises the nested class under its own lock and the JLS guarantees that any thread seeing the class initialised also sees its static fields fully written, so no volatile is needed. Fields declared final also get special safe-publication semantics after construction.

How it works

  1. Thread A acquires the lock and starts new Singleton().
  2. Without volatile, the reference may become visible before constructor writes.
  3. Thread B reads non-null on the unlocked path and uses a partial object.
  4. With volatile, the write of the reference is ordered after construction and visible with all prior writes.
  5. Thread B either sees null (and takes the lock) or a fully built object.

Example

private static volatile Singleton instance;   // remove volatile = broken DCL

public static Singleton getInstance() {
    if (instance == null) {
        synchronized (Singleton.class) {
            if (instance == null) instance = new Singleton();
        }
    }
    return instance;
}

// Holder idiom: no volatile needed
private static class Holder { static final Singleton INSTANCE = new Singleton(); }

Common mistakes

  • Thinking synchronized alone covers the unlocked first read.
  • Believing volatile makes count++ atomic.
  • Claiming the bug "never happens on x86", so it is safe; the JIT can still reorder.
  • Forgetting that pre-Java 5, DCL was broken even with volatile.

How to answer in the interview

"instance = new Singleton() isn't atomic: it allocates memory, runs the constructor and assigns the reference, and the compiler or CPU may reorder them so the reference is visible before the constructor finishes. A second thread doing the unlocked first check could then see a non-null instance and use a half-initialised object. Declaring the field volatile, under the Java 5 memory model, prevents that reordering and creates a happens-before relationship, so any thread reading the field sees a fully constructed object. The holder idiom avoids the issue entirely, because class initialisation is already synchronised."

Likely follow-up questions

  • Why does the holder idiom not need volatile? JVM class initialisation is locked and guarantees visibility of static initialisers.
  • Does volatile make operations atomic? Only single reads and writes; not read-modify-write sequences.
  • What is happens-before? A JMM rule guaranteeing that one action's effects are visible to and ordered before another.
