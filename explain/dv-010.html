How do you use cron to schedule jobs, and what are common pitfalls?

Scripting · concept · levels entry, mid

In one line

cron runs commands on a schedule defined by five time fields (minute, hour, day of month, month, day of week) edited with crontab -e; the classic pitfalls are its minimal environment, lost output, unnoticed failures, overlapping runs (use flock) and time zones, with systemd timers or Kubernetes CronJobs as modern alternatives.

Detailed explanation

The cron daemon checks schedules every minute. Each user has a crontab edited with crontab -e (listed with crontab -l); system jobs live in /etc/crontab and /etc/cron.d/, which have an extra user field. A line has five fields followed by the command: minute hour day-of-month month day-of-week. means every value, /15 every 15 units, 1-5 a range and 1,15 a list. So 0 2 * * runs at 02:00 daily, /10 * * * every ten minutes, and 30 6 * 1-5 at 06:30 on weekdays.

Pitfalls: cron runs with a minimal environment: a short PATH, no .bashrc, often /bin/sh instead of Bash. Scripts that work interactively fail with "command not found", so use full paths, set PATH and SHELL at the top of the crontab, or load an env file. Output is mailed to the user if a mail agent exists, otherwise effectively lost, so redirect stdout and stderr to a log. Failures go unnoticed unless you monitor: use a dead man's switch (the job pings a monitoring URL such as Healthchecks.io on success) or alert on missing runs. A job that runs longer than its interval overlaps the next run, causing duplicate work or corruption; wrap it with flock -n to skip if one is already running. Beware DST transitions in the server's time zone.

Alternatives: systemd timers give journal logging, dependencies, Persistent=true to catch up missed runs. In Kubernetes use a CronJob with concurrencyPolicy: Forbid.

How it works

  1. The daemon wakes every minute and reads crontabs.
  2. Matching entries are started with a minimal environment.
  3. Output is mailed or redirected to logs.
  4. flock prevents concurrent runs of the same job.
  5. Monitoring checks that each run succeeded.

Example

crontab -e
SHELL=/bin/bash
PATH=/usr/local/bin:/usr/bin:/bin
# nightly backup at 02:00, no overlap, logged, monitored
0 2 * * * /usr/bin/flock -n /tmp/backup.lock /opt/scripts/backup.sh >> /var/log/backup.log 2>&1 && curl -fsS -m 10 https://hc.example.com/ping/backup >/dev/null
# systemd alternative: a transient timer with catch-up of missed runs
sudo systemd-run --unit=backup --on-calendar="*-*-* 02:00:00" \
  --timer-property=Persistent=true /opt/scripts/backup.sh
systemctl list-timers backup.timer

Common mistakes

  • Relying on PATH and variables from your interactive shell.
  • No output redirection, so errors vanish.
  • No overlap protection for long jobs.
  • Scheduling in the DST transition window.
  • Forgetting to escape % in commands.

How to answer in the interview

"cron runs commands on a schedule. I edit a user's schedule with crontab -e, and each line has five fields, minute, hour, day of month, month and day of week, then the command, so 0 2 * * * runs every day at 2 a.m. The pitfalls: cron has a minimal environment, so I use full paths and set PATH; output is lost unless I redirect it to a log; failures go unnoticed unless I monitor them, for example with a heartbeat ping; and long jobs can overlap, which flock prevents. On modern systems systemd timers give better logging and catch-up, and in Kubernetes I'd use a CronJob."

Likely follow-up questions

  • How would you get alerted when a nightly job fails? A dead man's switch ping on success, alerting if no ping arrives, plus logging non-zero exits.
  • How do you test a cron job? Run it with env -i and the cron PATH to mimic the environment.
  • What does Persistent=true do in a timer? Runs a missed job at next boot if the machine was off.
