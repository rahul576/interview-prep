An App Service app becomes slow with high CPU at peak times. How do you diagnose and fix it?

Azure · scenario · levels mid, senior

In one line

Diagnose with Diagnose and solve problems and Application Insights (which requests and dependencies slowed), check whether the App Service plan is shared, find hot code with the Profiler or a CPU trace, then scale out with autoscale (or up) short term and fix the code (caching, async I/O, efficient queries) long term, confirmed by load testing.

Detailed explanation

First establish what "slow" means: high CPU on instances, or slow dependencies, or thread starvation. Diagnose and solve problems shows CPU and memory per instance, HTTP queue length, restarts and known issues like high CPU or SNAT exhaustion. Application Insights Performance view shows which operations got slow at peak and whether time is spent in the app or in dependencies such as SQL.

Plan sharing is a common hidden cause: all apps and slots on one App Service plan run on the same instances, so a noisy batch app or a staging slot under load steals CPU from production. Also check whether one instance is hot (uneven load, ARR affinity cookies keeping users sticky).

To find hot code, use the Application Insights Profiler (traces sampled at high CPU), or collect a CPU profile via Kudu / diagnostics tools (dotnet-trace for .NET, profilers for Node, Java Flight Recorder). Typical culprits: large JSON serialisation, inefficient regular expressions, synchronous blocking on async code (.Result) causing thread pool starvation, N+1 database queries in loops, compression or image processing on the request path, or excessive logging.

Short term: scale out with autoscale rules on CPU percentage or HTTP queue length (or automatic scaling on Premium plans), or scale up to a Premium v3/v4 tier with faster CPUs. Long term: fix the code: caching (Azure Cache for Redis or in-memory), async I/O, query optimisation and indexes, moving heavy work to background queues. Validate with Azure Load Testing against a realistic peak profile.

How it works

  1. Confirm symptom: CPU vs dependency latency vs thread starvation.
  2. Check plan composition and per-instance load.
  3. Profile during peak to find hot paths.
  4. Mitigate: autoscale out, isolate noisy apps to their own plan.
  5. Fix code and queries; add caching.
  6. Load test and set alerts on CPU and response time.

Example

az monitor autoscale create -g rg-web --resource asp-shop-prod \
  --resource-type Microsoft.Web/serverfarms --name as-shop --min-count 3 --max-count 10 --count 3
az monitor autoscale rule create -g rg-web --autoscale-name as-shop \
  --condition "CpuPercentage > 70 avg 5m" --scale out 2
az monitor autoscale rule create -g rg-web --autoscale-name as-shop \
  --condition "CpuPercentage < 35 avg 10m" --scale in 1

Common mistakes

  • Scaling out endlessly when the bottleneck is the database.
  • Running production and heavy staging/test apps on one plan.
  • No scale-in rule, or rules that flap.
  • Profiling outside the peak, missing the real hotspot.

How to answer in the interview

"I'd start with Diagnose and solve problems and Application Insights to see which requests got slow and whether time is in our code or in dependencies. I'd check if the plan is shared with other apps or slots competing for CPU. Then I'd profile at peak with the Application Insights Profiler or a CPU trace, which typically shows serialisation, sync-over-async blocking or chatty queries. Short term I scale out with autoscale on CPU or HTTP queue length, or scale up. Long term I fix the code with caching, async I/O and better queries, and confirm with a load test."

Likely follow-up questions

  • Why doesn't scaling out help with a DB bottleneck? More instances just send more concurrent queries to the same constrained database.
  • Thread pool starvation signs? Low CPU, rising latency, growing request queue.
  • Autoscale flapping? Use wider thresholds and longer windows for scale in.
