Explain how TLS works and how you manage certificates in production.

Networking · concept · levels mid, senior

In one line

In TLS the server proves its identity with a certificate chain to a trusted CA, both sides run an (EC)DHE key exchange to derive symmetric session keys, TLS 1.3 does this in one round trip, mTLS adds client certificates, and production certificates are automated (ACME, cert-manager, cloud managers) with expiry monitoring.

Detailed explanation

Handshake (TLS 1.3):

  1. ClientHello: supported versions, cipher suites, a key share for ECDHE (for example X25519, or a hybrid post-quantum group such as X25519MLKEM768 now offered by modern browsers), and SNI with the hostname.
  2. ServerHello: the server picks parameters, sends its key share; from here everything is encrypted. It sends its certificate and chain, a CertificateVerify signature proving it holds the private key, and Finished.
  3. The client validates the chain up to a trusted root, the hostname against the SAN, the validity dates, and possibly revocation. It sends Finished and data flows, encrypted with AEAD ciphers such as AES-GCM or ChaCha20-Poly1305.

Because keys come from ephemeral Diffie-Hellman, TLS 1.3 always provides forward secrecy: stealing the server's private key later doesn't decrypt past traffic. TLS 1.3 removed RSA key exchange, CBC modes and other weak options, and supports resumption and optional 0-RTT (replay-sensitive). TLS 1.2 is still acceptable when configured well; TLS 1.0/1.1 are deprecated.

Certificate chain: leaf certificate signed by an intermediate CA, signed by a root CA in the trust store. Servers must send the intermediates; a missing intermediate is a common cause of failures on some clients.

mTLS: the server also requests a client certificate and validates it, so both sides authenticate. Common for service-to-service traffic, usually automated by a service mesh (Istio, Linkerd) with short-lived certificates.

Certificate management in production: use ACME with Let's Encrypt or another CA; in Kubernetes, cert-manager issues and renews certificates into Secrets; in the cloud, AWS Certificate Manager, Azure Key Vault or Google Certificate Manager renew automatically for their load balancers. Certificate lifetimes are shrinking (the CA/Browser Forum has approved a phased reduction towards 47 days by 2029), so manual renewal is no longer viable. Monitor expiry with alerts (for example Prometheus blackbox exporter probe_ssl_earliest_cert_expiry), keep an inventory, and store private keys in secret managers or HSMs.

How it works

  1. Client connects and sends ClientHello with SNI and key share.
  2. Server returns key share, certificate chain and signature.
  3. Client validates chain, hostname and dates.
  4. Both derive session keys; encrypted data flows.
  5. Automation renews certificates well before expiry.
  6. Monitoring alerts on anything expiring soon.

Example

apiVersion: cert-manager.io/v1
kind: Certificate
metadata: { name: shop-tls, namespace: web }
spec:
  secretName: shop-tls
  dnsNames: [shop.example.com, www.shop.example.com]
  issuerRef: { name: letsencrypt-prod, kind: ClusterIssuer }
---
# alert: certificates expiring within 21 days
# expr: (probe_ssl_earliest_cert_expiry - time()) / 86400 < 21

Common mistakes

  • Manual renewals tracked in a spreadsheet.
  • Not serving the intermediate certificate.
  • Disabling certificate verification in clients "temporarily".
  • Monitoring only public endpoints, not internal and mTLS certificates.

How to answer in the interview

"In the handshake the client sends supported options and a key share; the server answers with its key share, its certificate chain and a signature proving it owns the key. The client validates the chain to a trusted CA, the hostname and expiry, and both sides derive symmetric session keys with ECDHE, which gives forward secrecy. TLS 1.3 does this in one round trip and removes weak ciphers. mTLS adds client certificates so both sides authenticate, usually via a service mesh. In production I automate everything with ACME and cert-manager or the cloud certificate manager, and alert on expiry, because expired certificates are a classic outage."

Likely follow-up questions

  • How do you find certificates expiring in 30 days? Blackbox exporter or a scanner across endpoints, cert-manager status, and cloud certificate inventories, alerting below 30 days.
  • What is forward secrecy? Session keys come from ephemeral keys, so a later key compromise can't decrypt past sessions.
  • What is SNI for? Lets one IP host many certificates by sending the hostname in ClientHello.
