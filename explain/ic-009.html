How does Terraform decide the order in which resources are created?

Infrastructure as Code · concept · levels entry

In one line

Terraform builds a dependency graph from references between resources (implicit dependencies) plus any depends_on; it creates dependencies first, runs independent resources in parallel (10 by default), and destroys in reverse order.

Detailed explanation

Terraform does not execute files top to bottom; file order is irrelevant. Instead it builds a directed acyclic graph of every resource, data source, module, variable and output. Whenever an expression references another object, for example vpc_id = aws_vpc.main.id, that creates an implicit dependency: the subnet cannot be created until the VPC exists and its ID is known. This is the normal and preferred way to express ordering, because the dependency is visible in the code and exact.

Resources with no path between them are independent and Terraform works on them concurrently. The default concurrency is 10 operations, controlled with -parallelism=n; lowering it helps when an API rate-limits you.

Sometimes a dependency is real but invisible to Terraform, for example an EC2 instance whose startup script needs an IAM role policy attached, but the instance only references the instance profile, not the policy attachment. For such cases depends_on adds an explicit dependency. Use it sparingly: it is coarse, and when used on a module or data source it can make Terraform defer reading data until apply, producing more "known after apply" values and noisier plans.

On destroy, Terraform walks the graph in reverse: the subnet is deleted before the VPC. For replacements, the default order is destroy then create, unless create_before_destroy is set. If you create a cycle (A references B and B references A), Terraform reports a cycle error.

How it works

  1. Parse all configuration files into objects.
  2. Add edges for every reference and every depends_on.
  3. Check for cycles.
  4. Walk the graph, starting objects whose dependencies are complete, up to the parallelism limit.
  5. For destroy, walk the reversed graph.

Example

resource "aws_vpc" "main" { cidr_block = "10.0.0.0/16" }

resource "aws_subnet" "app" {
  vpc_id     = aws_vpc.main.id          # implicit dependency
  cidr_block = "10.0.1.0/24"
}

resource "aws_instance" "app" {
  subnet_id            = aws_subnet.app.id
  iam_instance_profile = aws_iam_instance_profile.app.name
  depends_on           = [aws_iam_role_policy_attachment.app_s3]  # hidden dependency
}
terraform graph | dot -Tsvg > graph.svg
terraform apply -parallelism=5

Common mistakes

  • Assuming file or block order controls creation order.
  • Adding depends_on everywhere "to be safe", slowing and bloating plans.
  • Hard-coding IDs instead of references, losing the implicit dependency.
  • Creating cycles between security groups that reference each other inline (use separate rule resources).

How to answer in the interview

"Terraform builds a dependency graph. Any time one resource references another's attribute, like a subnet using aws_vpc.main.id, that's an implicit dependency, so the VPC is created first. Resources with no dependency between them are created in parallel, ten at a time by default via -parallelism. When there's a real dependency Terraform can't see, such as an instance needing a policy attached before it boots, I add depends_on, but sparingly because it makes plans more conservative. On destroy it walks the graph in reverse, and terraform graph can visualise it."

Likely follow-up questions

  • Why use depends_on sparingly? It's coarse, hides intent and can defer data reads, causing more unknown values and replacements.
  • How do you fix a cycle? Break it with separate resources, e.g. standalone security group rules.
  • Does Terraform retry failed resources? No automatic graph retry; providers retry some API errors internally.
