Should you run production databases on Kubernetes? How do you decide?

Kubernetes · design · levels senior, lead

In one line

Default to a managed database service for lower operational risk; run databases on Kubernetes when portability, on-prem, many small databases or cost justify it, using a mature operator (CloudNativePG, Percona, Strimzi for Kafka) with stable storage, anti-affinity, PDBs, tested backups and failover, and a team with database operations skills.

Detailed explanation

The question is less "can Kubernetes run databases?" (it can) and more "who carries the operational load?" A managed service (Amazon RDS or Aurora, Azure Database for PostgreSQL Flexible Server, Cloud SQL, AlloyDB) handles provisioning, patching, automated backups with point-in-time recovery, replication, failover and monitoring, with an SLA. For most product teams in the cloud, that is the lower-risk and often cheaper choice once engineering time is counted.

Kubernetes has become a solid place for databases thanks to operators, which encode DBA runbooks as controllers. CloudNativePG manages PostgreSQL clusters with streaming replication, automated failover with fencing, continuous WAL archiving and backups to object storage, PITR, rolling minor upgrades and declarative major upgrades. Similar operators exist for MySQL (Percona, Oracle MySQL Operator, Vitess), MongoDB, Redis and Strimzi for Kafka.

Good reasons to run on Kubernetes: portability across clouds and on-prem; on-premises or edge with no managed option; many small databases for dev, test or per-tenant setups created on demand; cost at scale; or features or extensions a managed service does not offer.

Requirements if you do: fast stable storage (SSD, appropriate IOPS, Retain reclaim policy, volume expansion), pod anti-affinity and topology spread across zones, PDBs so drains do not take out the primary and replicas together, dedicated nodes to avoid noisy neighbours, monitoring of replication lag and disk, backups to another region with restore tests, and documented failover drills. And critically, a team with database operations skills, since the operator automates actions but does not replace understanding.

How it works

  1. Assess requirements: RPO/RTO, scale, compliance, team skills, cost.
  2. If managed fits, use it and integrate via workload identity and private endpoints.
  3. If on Kubernetes, choose a mature operator.
  4. Provision storage classes, dedicated nodes, anti-affinity and PDBs.
  5. Configure backups to object storage and PITR.
  6. Test failover, node loss, restores and upgrades regularly.

Example

apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata: { name: orders-db }
spec:
  instances: 3
  storage: { size: 200Gi, storageClass: premium-ssd-retain }
  affinity:
    enablePodAntiAffinity: true
    topologyKey: topology.kubernetes.io/zone
  backup:
    barmanObjectStore:
      destinationPath: s3://pg-backups-eu/orders
      s3Credentials: { inheritFromIAMRole: true }
    retentionPolicy: "30d"

(Newer CloudNativePG versions move object-store backups to the Barman Cloud plugin; check the version you run.)

Common mistakes

  • Running a single-replica StatefulSet with no operator and calling it HA.
  • Never testing restores.
  • Ignoring storage performance and zone placement.
  • Choosing Kubernetes for "consistency" without DBA skills.

How to answer in the interview

"It depends on the team and requirements. Managed services like RDS, Azure Database for PostgreSQL or Cloud SQL handle backups, patching, replication and failover, so for most product teams in the cloud they're the lower-risk choice. Running on Kubernetes is practical now with mature operators like CloudNativePG or Strimzi, which automate replication, failover, backups to object storage and upgrades. I'd choose it for portability, on-prem, many small databases or cost at scale. Then I'd require fast stable storage, zone anti-affinity, PDBs, dedicated nodes, monitoring, tested restores and failover drills, and people with database operations skills."

Likely follow-up questions

  • Failure scenarios to test? Primary node loss, zone loss, network partition, full disk, failed backup restore, major version upgrade.
  • How does CloudNativePG avoid split-brain? It fences the old primary before promoting a replica.
  • Why Retain reclaim policy? Accidental PVC deletion does not destroy the data disk.
