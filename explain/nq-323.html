What experience do you have with OpenShift and Cloud Platform Foundation?

Kubernetes · scenario · levels mid

In one line

Answer honestly from real experience: OpenShift is Red Hat's enterprise Kubernetes distribution (Projects, Routes, Security Context Constraints, BuildConfigs/S2I, oc, OperatorHub), while Cloud Foundry (sold as Pivotal, then VMware Tanzu, sometimes called "Cloud Platform Foundation") is a PaaS where cf push plus buildpacks deploy your app and you bind marketplace services.

Detailed explanation

Interviewers ask this in enterprises, banks and telecoms that run these platforms. They want to know whether you can deploy and troubleshoot there, and they value honesty about depth more than buzzwords.

OpenShift (OpenShift Container Platform on-prem, or managed as ROSA on AWS and ARO on Azure) is certified Kubernetes with opinionated additions:

  • Projects wrap namespaces with extra annotations and self-service.
  • Routes expose services externally through the built-in HAProxy router (Ingress and Gateway API also work).
  • Security Context Constraints (SCCs): by default the restricted-v2 SCC runs containers with a random, non-root UID in the namespace range and drops capabilities. Images that write to root-owned directories or bind port 80 fail until fixed.
  • BuildConfigs and Source-to-Image (S2I) build images inside the cluster; ImageStreams track image tags; an integrated registry.
  • A strong web console, the oc CLI (kubectl-compatible plus extras), OperatorHub and OpenShift GitOps and Pipelines (Argo CD and Tekton).

Cloud Foundry is a higher-level PaaS. You run cf push with a JAR; buildpacks detect Java, add a JRE and produce a droplet; Diego schedules app instances; the router gives a URL. You bind services from a marketplace (databases, RabbitMQ), with credentials injected via VCAP_SERVICES. It is very productive for twelve-factor web apps but less flexible than Kubernetes for custom networking, sidecars or stateful workloads, and many organisations are migrating from it to Kubernetes.

How it works

  1. State what you used, for how long and in what role.
  2. Describe the deployment flow you ran (Helm, templates, S2I, cf push).
  3. Mention a concrete platform-specific problem you solved.
  4. Contrast with plain Kubernetes to show understanding.
  5. Be clear where your knowledge is theoretical.

Example

A typical OpenShift fix for an image that assumed root:

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY target/app.jar app.jar
RUN chgrp -R 0 /app && chmod -R g=u /app   # arbitrary UID, group 0
USER 1001
EXPOSE 8080
ENTRYPOINT ["java","-jar","app.jar"]
oc new-project orders-dev
oc apply -f k8s/ && oc expose service orders   # creates a Route
cf push orders -p target/app.jar -m 1G -i 2 && cf bind-service orders orders-db

Common mistakes

  • Claiming deep OpenShift experience after only using kubectl on a vanilla cluster.
  • Not knowing why containers fail under the restricted SCC.
  • Confusing Cloud Foundry with a cloud provider.
  • Granting anyuid SCC to every workload instead of fixing images.

How to answer in the interview

"I have used OpenShift for about two years, deploying Spring Boot services with Helm charts and OpenShift Routes. The biggest adjustment was Security Context Constraints: containers run as a random non-root user, so we fixed images to use group-zero permissions and port 8080 instead of asking for anyuid. I used the oc CLI, the console for debugging and OpenShift GitOps for deployments. With Cloud Foundry, which some people call Cloud Platform Foundation, my experience is lighter: I deployed apps with cf push and buildpacks and bound marketplace databases. It is simpler but less flexible than Kubernetes."

Likely follow-up questions

  • What changes to run on OpenShift? Non-root, arbitrary UID, writable dirs owned by group 0, ports above 1024.
  • Route vs Ingress? Routes are OpenShift's native object with TLS termination modes; Ingress is converted to Routes.
  • Why migrate from Cloud Foundry? Flexibility, ecosystem, cost and vendor licensing changes.
