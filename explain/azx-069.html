How do you manage AKS upgrades: auto-upgrade channels, node OS upgrades and maintenance windows?

Azure Kubernetes (AKS) · concept · levels mid, senior

In one line

AKS separates Kubernetes version upgrades (cluster auto-upgrade channel: patch, stable, rapid, node-image) from node OS updates (node OS upgrade channel: NodeImage, SecurityPatch, Unmanaged), and you control timing with planned maintenance windows, safety with max surge and PDBs, and lifecycle with the supported version window or LTS.

Detailed explanation

Cluster auto-upgrade channel controls the Kubernetes version:

  • none: you upgrade manually.
  • patch: latest patch of your current minor version.
  • stable: latest patch of minor version N-1 (one behind the newest), a sensible default for production.
  • rapid: latest supported minor version.
  • node-image: only updates node images (now better handled by the node OS channel).

Node OS upgrade channel controls OS security updates on nodes:

  • NodeImage: AKS rolls out new node images (typically weekly) by reimaging nodes.
  • SecurityPatch: applies security patches with less disruption, reimaging only when needed.
  • Unmanaged: the OS applies updates itself (for example unattended-upgrades on Ubuntu).
  • None: no automatic updates.

Planned maintenance uses separate configurations: aksManagedAutoUpgradeSchedule for version upgrades and aksManagedNodeOSUpgradeSchedule for node OS updates, such as Saturday 22:00 for eight hours.

During a node upgrade AKS cordons and drains nodes; max surge (for example 33%) adds temporary nodes so pods have somewhere to go, and PodDisruptionBudgets keep enough replicas available. A PDB that allows zero disruptions will block the drain.

AKS supports roughly the three latest minor versions (N-2). Long-term support (Premium tier) extends a selected version for two years from release, for teams that cannot upgrade frequently. Upgrade non-production first, and check deprecated APIs before every minor upgrade.

How it works

  1. Set the auto-upgrade and node OS channels.
  2. Define maintenance windows for each.
  3. Configure max surge per node pool and sensible PDBs.
  4. Upgrade dev and test clusters a week or more earlier than production.
  5. Check deprecated APIs and release notes before minor upgrades.
  6. Monitor upgrade events and node versions afterwards.

Example

az aks update -g rg-apps -n aks-prod \
  --auto-upgrade-channel stable --node-os-upgrade-channel NodeImage

az aks maintenanceconfiguration add -g rg-apps --cluster-name aks-prod \
  --name aksManagedAutoUpgradeSchedule --schedule-type Weekly \
  --day-of-week Saturday --interval-weeks 1 --start-time 22:00 --duration 8

az aks nodepool update -g rg-apps --cluster-name aks-prod -n user1 --max-surge 33%

Common mistakes

  • Leaving channels at none and falling out of support.
  • PDBs with maxUnavailable: 0 that block every drain.
  • Upgrading production and non-production in the same window.
  • Ignoring deprecated API removals before a minor upgrade.

How to answer in the interview

"AKS separates Kubernetes version upgrades from node OS updates. The auto-upgrade channel decides how the version moves: patch, stable, which tracks N-1, rapid, or node-image. The node OS channel handles security updates, with NodeImage reimaging weekly or SecurityPatch for less disruption. Planned maintenance windows control when each runs. During node upgrades max surge adds extra nodes and PDBs protect availability. AKS supports about the three latest minors, and LTS on the Premium tier gives two years. Non-production upgrades first so we catch problems early."

Likely follow-up questions

  • Why upgrade non-production earlier? To catch API removals and behaviour changes before they hit production.
  • How do you find deprecated APIs? AKS upgrade insights, kubent or Pluto scans in CI.
  • What if surge needs more IPs than the subnet has? Lower surge or enlarge the subnet before upgrading.
