Compare the bridge, host, none and macvlan network drivers.

Docker · concept · levels mid

In one line

bridge (default) gives containers private IPs behind NAT with published ports; host shares the host network stack with no isolation; none gives only loopback; macvlan gives each container its own MAC/IP on the LAN; overlay spans multiple hosts.

Detailed explanation

Docker network drivers trade isolation against directness.

bridge creates a Linux bridge (docker0 for the default network, a new one for each user-defined network). Containers get IPs on a private subnet, reach the outside world through NAT (masquerading) and are reachable from outside only through published ports (-p 8080:80), implemented with iptables or nftables rules and docker-proxy. User-defined bridges add DNS by container name and better isolation between applications. It is the right choice for almost everything on a single host.

host removes network isolation: the container uses the host's interfaces directly. There is no NAT and no port mapping, so throughput and latency are slightly better and applications that need many dynamic ports or multicast work easily. The costs are port conflicts between containers and the host, and the container can see and bind to all host interfaces. On Docker Desktop host networking behaves differently because the "host" is a VM.

none gives only a loopback interface, useful for batch jobs that must not touch the network, or for security-sensitive processing.

macvlan (and ipvlan) attach the container directly to the physical network with its own MAC and IP address from the LAN, so it looks like a separate device. This suits legacy applications or network appliances that expect a real LAN address. It needs network support (promiscuous mode, enough addresses), and by default the host cannot talk to its own macvlan containers.

overlay uses VXLAN to connect containers on different hosts, used by Swarm; Kubernetes uses CNI plugins instead.

How it works

  1. bridge: veth pair connects container to a bridge; NAT for egress, DNAT for published ports.
  2. host: container joins the host network namespace.
  3. none: container network namespace with only lo.
  4. macvlan: sub-interface of a physical NIC with its own MAC.
  5. overlay: VXLAN tunnels between hosts with a distributed key-value store.

Example

docker network create appnet                                # bridge
docker run -d --network host prom/node-exporter             # host
docker run --rm --network none alpine ip addr               # none
docker network create -d macvlan --subnet 192.168.1.0/24 \
  --gateway 192.168.1.1 -o parent=eth0 lan
docker run -d --network lan --ip 192.168.1.50 legacy-app    # macvlan

Common mistakes

  • Using host networking to avoid learning port mapping.
  • Using the default bridge and expecting name resolution.
  • Expecting the host to reach its macvlan containers without extra setup.
  • Assuming -p publishing is blocked by host firewalls like ufw (Docker's rules often bypass them).

How to answer in the interview

"Bridge is the default: containers get private IPs on a virtual bridge, use NAT to go out and are reachable only through published ports, and user-defined bridges add DNS by name. Host removes network isolation so the container uses the host stack directly, with no port mapping and slightly better performance but port conflicts and less security. None gives only loopback for jobs that mustn't use the network. Macvlan gives each container its own MAC and IP on the physical LAN, useful for legacy apps that expect to be a real device. Overlay spans several hosts for Swarm."

Likely follow-up questions

  • When is host networking justified? Node-level monitoring agents, very high packet rates, multicast or many dynamic ports.
  • Why can published ports bypass ufw? Docker inserts its own iptables rules before ufw's chains.
  • macvlan vs ipvlan? ipvlan shares the parent MAC, helpful where switches limit MAC addresses.
