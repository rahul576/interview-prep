How do engineers and pipelines access a private AKS cluster API server?

Azure Kubernetes (AKS) · concept · levels mid, senior

In one line

A private AKS cluster has no public API endpoint, so pipelines use self-hosted agents or Managed DevOps Pools in the network, engineers use VPN/ExpressRoute or Bastion to a jump box, emergencies can use az aks command invoke, and access is still authenticated with Entra ID and Azure RBAC.

Detailed explanation

In a private cluster the API server is reached through a private endpoint in the cluster's VNet (or, with API server VNet integration, through an internal load balancer in a delegated subnet). A private DNS zone such as privatelink.<region>.azmk8s.io resolves the API server name to the private IP. From the internet, kubectl simply cannot connect, which removes a large attack surface.

Access patterns:

  • Pipelines: run on self-hosted agents (VMs, VM Scale Set agents or Managed DevOps Pools injected into a VNet) or GitHub self-hosted runners in the hub or a peered spoke. Microsoft-hosted agents cannot reach the private endpoint.
  • Engineers: connect from the corporate network via VPN or ExpressRoute, or through Azure Bastion to a jump box in a peered VNet that has kubectl and kubelogin installed.
  • Emergencies and occasional tasks: az aks command invoke runs kubectl or helm commands in a temporary pod inside the cluster through the Azure control plane, with no network line of sight needed. It is slower and limited, but handy for break-fix.
  • GitOps: Flux or Argo CD runs inside the cluster and pulls from Git, so pipelines often do not need API access at all.

DNS is the most common source of trouble: peered VNets, hub DNS servers and on-premises resolvers must all resolve the private zone, typically with a virtual network link on the zone and Azure DNS Private Resolver with conditional forwarding.

Whatever the network path, every request is still authenticated with Entra ID, authorised with Azure RBAC, and local accounts should be disabled.

How it works

  1. Create the cluster with --enable-private-cluster (optionally a custom private DNS zone).
  2. Link the private DNS zone to hub and agent VNets; configure forwarding for on-premises.
  3. Deploy agents or runners in a VNet with line of sight.
  4. Give engineers VPN or Bastion access to a jump box.
  5. Use command invoke for emergencies.

Example

az aks create -g rg-apps -n aks-private --enable-private-cluster \
  --enable-aad --enable-azure-rbac --disable-local-accounts

# Run kubectl without network access to the API server
az aks command invoke -g rg-apps -n aks-private \
  --command "kubectl get pods -n orders"

# Check resolution from an agent
nslookup aks-private-dns-12345.privatelink.westeurope.azmk8s.io

Common mistakes

  • Forgetting to link the private DNS zone to peered or hub VNets.
  • Expecting Microsoft-hosted agents to reach the cluster.
  • Using shared admin credentials on the jump box instead of personal Entra logins.
  • Making the cluster private but leaving local accounts enabled.

How to answer in the interview

"A private cluster exposes the API server only on a private IP with a private DNS zone, so kubectl from the internet doesn't work. Pipelines run on self-hosted agents or Managed DevOps Pools inside the VNet or a peered network. Engineers use VPN or ExpressRoute, or Bastion to a jump box. For emergencies, az aks command invoke runs kubectl through the Azure control plane without network access. API server VNet integration is another model. In all cases access is still Entra ID and Azure RBAC."

Likely follow-up questions

  • Common DNS issues? Zone not linked to the peered VNet, or custom DNS servers not forwarding to Azure DNS.
  • Does GitOps help? Yes, the in-cluster agent pulls changes, so CI needs no API access.
  • Limits of command invoke? Slower, limited file upload, not suitable for routine automation.
