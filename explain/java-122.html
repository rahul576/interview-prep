How does the java.time API improve on Date and Calendar?

Java 8+ Features · concept · levels entry, mid

In one line

The java.time API (Java 8, JSR-310) replaces mutable, error-prone Date/Calendar with immutable, thread-safe types with clear meanings: LocalDate, LocalDateTime, Instant, ZonedDateTime, plus Duration, Period and a thread-safe DateTimeFormatter.

Detailed explanation

The legacy classes had well-known problems. java.util.Date is mutable, so passing it around invites bugs; its name is misleading since it actually represents an instant; months in Calendar are zero-based; time zone handling is confusing; and SimpleDateFormat is not thread-safe, a classic source of corrupted dates when shared as a static field.

java.time, designed by the author of Joda-Time, fixes these. All core classes are immutable: date.plusDays(1) returns a new object. Each type has one meaning. LocalDate is a calendar date (birthday), LocalTime a time of day, LocalDateTime a date-time without zone (useful for "store opens at 09:00"), Instant a point on the UTC timeline (machine timestamps), ZonedDateTime a date-time with a ZoneId that understands daylight-saving rules, and OffsetDateTime a date-time with a fixed offset, common in APIs and databases. Duration measures time-based amounts (seconds, nanos), Period date-based amounts (years, months, days). DateTimeFormatter is immutable and thread-safe, with ISO constants built in.

In backends the usual rule is: store Instant / UTC timestamps, convert to the user's zone only at the edges for display. For testability, inject a java.time.Clock instead of calling Instant.now() directly.

How it works

  1. Get current time via Instant.now(clock) or LocalDate.now(clock).
  2. Do arithmetic with plus, minus, with, each returning a new instance.
  3. Attach a zone with instant.atZone(ZoneId.of("Asia/Kolkata")).
  4. Measure differences with Duration.between or Period.between.
  5. Format/parse with a shared DateTimeFormatter constant.
  6. Interoperate with old APIs via Date.from(instant) and date.toInstant().

Example

private static final DateTimeFormatter UI = DateTimeFormatter.ofPattern("dd MMM yyyy, HH:mm");

class OrderService {
    private final Clock clock;
    OrderService(Clock clock) { this.clock = clock; }

    Order place(Cart cart) {
        Instant createdAt = Instant.now(clock);                // store in UTC
        LocalDate deliveryBy = LocalDate.now(clock).plusDays(3);
        return new Order(cart, createdAt, deliveryBy);
    }
    String display(Order o, ZoneId userZone) {
        return UI.format(o.createdAt().atZone(userZone));
    }
}
// test: new OrderService(Clock.fixed(Instant.parse("2026-01-01T10:00:00Z"), ZoneOffset.UTC));

Common mistakes

  • Using LocalDateTime for event timestamps, losing the zone.
  • Calling Instant.now() directly, making tests time-dependent.
  • Assuming a day is always 24 hours across DST changes.
  • Sharing a static SimpleDateFormat in legacy code.

How to answer in the interview

"java.time replaced the mutable and confusing Date and Calendar. Its classes are immutable and thread-safe and each has a clear meaning: LocalDate for a date, LocalDateTime without a zone, Instant for a UTC point on the timeline, and ZonedDateTime with a ZoneId when time zones and daylight saving matter. Duration and Period represent amounts of time, and DateTimeFormatter is thread-safe unlike SimpleDateFormat. In backends I store Instant or UTC timestamps, convert to the user's zone only for display, and inject a Clock so time-dependent code is testable."

Likely follow-up questions

  • How would you inject a Clock for testing? Pass a Clock into the constructor and use Clock.fixed or a mutable test clock in tests.
  • Duration versus Period? Duration is time-based (seconds), Period is date-based (years, months, days).
  • What JDBC type maps to Instant? Usually TIMESTAMP WITH TIME ZONE via OffsetDateTime/Instant in JDBC 4.2+ drivers.
