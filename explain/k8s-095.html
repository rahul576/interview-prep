kubectl apply fails on a large CRD with metadata.annotations Too long. Why, and how do you fix it?

Kubernetes · scenario · levels mid, senior

In one line

Client-side kubectl apply stores the whole object in the last-applied-configuration annotation, and annotations are capped at 256 KB in total, so big CRDs overflow it; use server-side apply (or create/replace) instead.

Detailed explanation

Classic client-side apply performs a three-way merge between your manifest, the live object and the configuration you applied last time. To remember the last one, kubectl writes the full object as JSON into the annotation kubectl.kubernetes.io/last-applied-configuration. The API server limits the combined size of all annotations on an object to 256 KB (262,144 bytes).

CustomResourceDefinitions with long OpenAPI v3 schemas, such as the Prometheus Operator's prometheuses or alertmanagers CRDs, or many CRDs from Crossplane providers, are larger than that. The object itself is within the etcd size limit, but the duplicate copy in the annotation is not, so you get metadata.annotations: Too long: must have at most 262144 bytes.

Server-side apply solves it properly: kubectl apply --server-side sends the manifest to the API server, which performs the merge and records field ownership in managedFields instead of storing a full copy. It also gives clear conflict detection between managers. Alternatives are kubectl create for the first install and kubectl replace for updates. In Argo CD, set the ServerSideApply=true sync option on those resources (or Replace=true); Helm installs CRDs from its crds/ directory without the annotation but does not upgrade them, which is why many teams manage CRDs separately.

How it works

  1. Client-side apply serialises the manifest into the last-applied annotation.
  2. The API server validates total annotation size and rejects anything over 256 KB.
  3. With server-side apply, the server merges and tracks owners in managedFields.
  4. No full-copy annotation is written, so size is no longer an issue.
  5. Use --force-conflicts once when migrating fields previously owned by client-side apply.

Example

kubectl apply -f prometheus-operator-crds/
# The CustomResourceDefinition "prometheuses.monitoring.coreos.com" is invalid:
#   metadata.annotations: Too long: must have at most 262144 bytes
kubectl apply --server-side --force-conflicts -f prometheus-operator-crds/
# Argo CD Application
spec:
  syncPolicy:
    syncOptions:
      - ServerSideApply=true

Common mistakes

  • Stripping the schema from the CRD to make it fit, which removes validation.
  • Using kubectl replace on objects other tools also modify, overwriting their changes.
  • Forgetting that Helm does not upgrade CRDs from crds/ on helm upgrade.
  • Deploying the operator before its CRDs exist.

How to answer in the interview

"Client-side apply keeps the whole object as JSON in the last-applied-configuration annotation for its three-way merge, and all annotations on an object are limited to 256 kilobytes. Large CRDs with big OpenAPI schemas, like the Prometheus operator ones, exceed that, so apply fails with Too long. The clean fix is server-side apply, which tracks field ownership in managedFields instead of that annotation. Otherwise create for the first install and replace for updates. In Argo CD I enable the ServerSideApply sync option, and I usually manage CRDs as their own application so they update before the operator."

Likely follow-up questions

  • Why manage CRDs separately from the operator? CRDs are cluster-wide, must exist and be upgraded before the operator, and deleting them deletes all custom resources.
  • What are managedFields? Per-field records of which manager set which value, used for conflict detection.
  • Can you switch a resource from client-side to server-side apply? Yes; kubectl migrates ownership, sometimes needing --force-conflicts.
