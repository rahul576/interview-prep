Design the serving architecture for a recommendation system on a high-traffic website.

MLOps · design · levels senior, lead

In one line

High-traffic recommendations use a two-stage pipeline: fast candidate generation (ANN search over embeddings plus other sources) narrows millions of items to hundreds, then a ranking model with real-time features scores them, followed by business rules, with caching and impression/click logging around it.

Detailed explanation

Scoring every item for every request with a heavy model is impossible at millions of items and thousands of requests per second, so the work is split.

Candidate generation must be cheap and high-recall. A two-tower model produces user and item embeddings; item embeddings are indexed in a vector index (FAISS, ScaNN, a vector database or OpenSearch k-NN) and approximate nearest neighbour (ANN) search returns a few hundred similar items in milliseconds. Other sources add candidates: trending items, recently viewed, co-purchase lists, new items.

Ranking is precise but more expensive: gradient-boosted trees or a deep model scores each candidate using rich features, including real-time features from an online feature store (items clicked this session, cart contents, time of day). The latency budget is typically tens of milliseconds for the whole call, so features are fetched in batch and models are optimised (ONNX, GPUs or batching).

Re-ranking and business rules then remove out-of-stock or already purchased items, enforce diversity, apply promotions and legal constraints.

Caching and precomputation keep costs down: for anonymous users and popular pages, results are precomputed in batch and cached; personalised results are computed online with a fallback to cached popular lists if a dependency is slow.

Logging every impression, click and purchase with the model version and position creates training data and powers A/B tests. Because the model only learns from what it showed, you need exploration (a small share of random or new items) and position-bias correction to avoid feedback loops.

How it works

  1. Request arrives with user ID and context.
  2. Candidate generators (ANN, trending, history) return about 500 items.
  3. Feature store returns user, item and real-time features.
  4. Ranker scores candidates; top N kept.
  5. Business rules filter and diversify; response returned within the SLO.
  6. Impressions and clicks are streamed to the log for training and experiments.

Example

def recommend(user_id, ctx, k=20):
    u = feature_store.get_user(user_id)            # embedding + realtime features
    cands = set(ann.search(u.embedding, top_k=400)) | trending(ctx.region, 50) | recent(user_id, 50)
    feats = feature_store.get_items(cands, user=u)
    scores = ranker.predict(feats)                 # e.g. LightGBM / ONNX
    ranked = apply_rules(sorted(zip(cands, scores), key=lambda x: -x[1]), user=u)
    log_impressions(user_id, ranked[:k], model_version=ranker.version)
    return ranked[:k]

Common mistakes

  • One heavy model over the whole catalogue: too slow and too expensive.
  • No fallback, so a feature store hiccup returns empty pages.
  • Logging clicks without impressions or positions, which makes training data biased.
  • No exploration, so popular items dominate forever.

How to answer in the interview

"I'd use two stages. Candidate generation uses approximate nearest neighbour search over user and item embeddings, plus trending and history sources, to get a few hundred items in milliseconds. A ranking model then scores them using real-time features from an online feature store within a tight latency budget. Business rules filter out-of-stock or purchased items and add diversity. Anonymous and popular cases are precomputed and cached, with a fallback list. Every impression and click is logged with the model version for training and A/B tests, and I add exploration to avoid feedback loops."

Likely follow-up questions

  • How do you avoid only recommending popular items? Exploration traffic, popularity-debiased training, diversity constraints and boosts for new items.
  • How do you handle new users (cold start)? Popular and contextual lists, onboarding preferences, then quickly use session signals.
  • How do you update embeddings? Retrain periodically, rebuild the index offline and swap atomically.
