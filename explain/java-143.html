Explain the SOLID principles with examples.

Design Patterns · concept · levels entry, mid

In one line

SOLID is five object-oriented design principles: Single responsibility, Open/closed, Liskov substitution, Interface segregation and Dependency inversion, all aimed at code that is easy to change, test and extend.

Detailed explanation

The principles were collected by Robert C. Martin and named SOLID by Michael Feathers. They are guidelines for managing dependencies and change, not rules to apply mechanically.

  • S – Single Responsibility Principle: a class should have one reason to change, meaning it serves one actor or concern. An InvoiceService that calculates totals, renders PDFs and sends emails changes whenever finance, design or the mail provider changes; split it into InvoiceCalculator, InvoicePdfRenderer and InvoiceMailer.
  • O – Open/Closed Principle: modules should be open for extension, closed for modification. Adding a new payment type should mean adding a new PaymentStrategy class, not editing a growing switch.
  • L – Liskov Substitution Principle: a subtype must be usable wherever its base type is expected without breaking the caller's expectations: it may not strengthen preconditions, weaken postconditions or throw unexpected exceptions. The classic violation is Square extends Rectangle: setting width on a square also changes height, so code that sets width 5 and height 4 and expects area 20 breaks.
  • I – Interface Segregation Principle: clients should not depend on methods they do not use. Prefer small role interfaces (Readable, Writable) over a fat Repository with twenty methods that every fake must implement.
  • D – Dependency Inversion Principle: high-level policy should depend on abstractions, and details should implement them. OrderService depends on a PaymentGateway interface; StripeGateway implements it. Spring's dependency injection wires the concrete class at runtime, making the service easy to test with a mock.

How it works

  1. Identify reasons for change and split classes along them (SRP).
  2. Put variation points behind interfaces so new behaviour is added, not edited (OCP).
  3. Check that subclasses honour the parent's contract (LSP).
  4. Shape interfaces around what each client needs (ISP).
  5. Depend on interfaces and inject implementations (DIP).

Example

interface PaymentGateway { PaymentResult charge(Money amount, String token); }

@Service
class OrderService {                      // high-level policy (DIP)
    private final PaymentGateway gateway; // abstraction
    OrderService(PaymentGateway gateway) { this.gateway = gateway; }
    void checkout(Order o) { gateway.charge(o.total(), o.paymentToken()); }
}

@Component class StripeGateway implements PaymentGateway { /* detail */ }
@Component class UpiGateway    implements PaymentGateway { /* new type, no edits (OCP) */ }

Common mistakes

  • Treating SRP as "one method per class" and creating hundreds of tiny classes.
  • Adding interfaces for everything "for OCP" when nothing varies.
  • Confusing dependency inversion with dependency injection (DI is one way to achieve DIP).
  • Overriding methods to throw UnsupportedOperationException, a typical LSP violation.

How to answer in the interview

"SOLID is five principles for maintainable OO code. Single responsibility: one reason to change, so a report class shouldn't also send emails. Open/closed: extend by adding code, for example a new payment strategy class, instead of editing a switch. Liskov: a subclass must work wherever the parent is expected; Square extending Rectangle is the classic violation. Interface segregation: small focused interfaces rather than fat ones. Dependency inversion: high-level code depends on abstractions; in Spring I inject interfaces through constructors, which also makes unit testing with mocks easy. I apply them pragmatically, where change actually happens."

Likely follow-up questions

  • Give a Liskov violation. Square extends Rectangle, or an immutable list subclass that throws on add.
  • Is DI the same as DIP? No; DIP is the principle, DI is a technique that helps achieve it.
  • Can SOLID be overdone? Yes; too many abstractions add indirection without benefit (YAGNI).
