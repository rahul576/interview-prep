Do you need a feature store? Explain when it helps and when it is overhead.

MLOps · concept · levels mid, senior, lead

In one line

A feature store manages feature definitions with an offline store for training and an online store for low-latency serving, solving training-serving parity, reuse across teams and point-in-time correct joins; without real-time needs or cross-team reuse, it is mostly overhead.

Detailed explanation

A feature store has three parts: a registry of feature definitions (name, entity, source, transformation, owner, freshness), an offline store holding historical feature values, usually in a warehouse or lakehouse, for building training sets, and an online store, a low-latency key-value database such as Redis or DynamoDB, holding the latest values for real-time inference. Materialisation jobs or streaming pipelines keep both in sync.

It solves real problems. Training-serving parity: the same definition produces features for training and serving, avoiding subtle bugs where the online service computes "transactions in the last 7 days" differently from the training SQL. Reuse and governance: features such as customer lifetime value or 30-day spend are defined once, documented, owned and shared across teams and models, rather than re-implemented five times. Point-in-time correctness: when building a training set, the store joins each label with feature values as they were at the prediction time, preventing data leakage from future information, which is easy to get wrong in hand-written SQL.

But it is significant infrastructure: two storage systems, materialisation pipelines, freshness monitoring, access control and another platform to upgrade. If you only do batch scoring, have a handful of models owned by one team, and do not need millisecond lookups, a well-organised feature pipeline writing versioned tables, with shared transformation code, gives most of the benefit. Adopt a feature store when real-time serving, many models or several teams make parity and reuse painful.

Options include Feast (open source), Tecton, Databricks Feature Engineering, SageMaker Feature Store and Vertex AI Feature Store.

How it works

  1. Define features and entities in the registry.
  2. Materialise values into offline and online stores.
  3. Training retrieves point-in-time correct historical features.
  4. Serving fetches the latest values by entity key.
  5. Monitor freshness and consistency between stores.

Example

from feast import FeatureStore
store = FeatureStore(repo_path=".")

# training: point-in-time correct join against labelled events
training_df = store.get_historical_features(
    entity_df=labels_df,       # customer_id, event_timestamp, label
    features=["customer_stats:spend_30d", "customer_stats:txn_count_7d"],
).to_df()

# serving: latest values with low latency
online = store.get_online_features(
    features=["customer_stats:spend_30d", "customer_stats:txn_count_7d"],
    entity_rows=[{"customer_id": 1842}],
).to_dict()

Common mistakes

  • Adopting a feature store for one batch model.
  • Treating it as a magic fix while transformations remain duplicated outside it.
  • Ignoring feature freshness monitoring in the online store.
  • Building training sets with naive joins that leak future data.

How to answer in the interview

"A feature store manages feature definitions and serves them two ways: an offline store with history for training sets and an online store for low-latency lookups during real-time inference. It solves training-serving parity, because one definition feeds both, and reuse, because features are defined once and shared with ownership. It also gives point-in-time correct joins, preventing leakage. But it's significant infrastructure, so with batch scoring only, a few models and one team, a well-organised feature pipeline writing tables is enough. Examples are Feast, Tecton and the Databricks, SageMaker and Vertex feature stores."

Likely follow-up questions

  • How would you migrate existing pipelines gradually? Register the most-reused, real-time features first, keep pipelines writing to the offline store, then add online materialisation per model.
  • What is a point-in-time join? Joining each label with the latest feature values known before its timestamp.
  • What if online and offline values diverge? Monitor by sampling online values and comparing them with offline recomputation.
