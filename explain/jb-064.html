What is the purpose of the @FunctionalInterface annotation?

Java 8+ Features · concept · levels entry, mid

In one line

@FunctionalInterface declares that an interface is intended to have exactly one abstract method, and makes the compiler reject it if that contract is broken; it is optional, since any single-abstract-method interface works with lambdas.

Detailed explanation

The annotation (in java.lang) serves two purposes. First, documentation: readers and API users immediately see the interface is meant as a lambda target. Second, and more important, compile-time enforcement. If a colleague later adds a second abstract method, or removes the only one, compilation fails at the interface itself with a clear error ("Multiple non-overriding abstract methods found"). Without the annotation the interface would compile fine, but every lambda using it would break somewhere else, possibly in another module or a client's code.

The annotation is not required: the compiler treats any interface with a single abstract method as functional. Many pre-Java-8 interfaces such as Runnable, Callable and Comparator were simply annotated retroactively.

What still counts as functional:

  • Any number of default methods (they have bodies).
  • Any number of static methods.
  • Private methods (Java 9+).
  • Abstract methods that redeclare public methods of Object, such as boolean equals(Object) or String toString(), because every implementation inherits them from Object anyway. That's why Comparator, which declares equals, is still functional.

An interface can also extend another interface and remain functional if the total set of abstract methods is still one (or if it overrides inherited ones to resolve to one signature). The annotation is only allowed on interfaces, not on classes, enums or annotation types.

How it works

  1. The compiler collects all abstract methods, including inherited ones.
  2. It removes those matching public Object methods.
  3. If exactly one remains, the interface is functional.
  4. With the annotation present, any other count is a compile error.

Example

@FunctionalInterface
public interface DiscountPolicy {
    BigDecimal apply(Order order);                 // the single abstract method

    default DiscountPolicy capAt(BigDecimal max) {  // default: allowed
        return o -> apply(o).min(max);
    }
    static DiscountPolicy none() {                 // static: allowed
        return o -> BigDecimal.ZERO;
    }
    boolean equals(Object other);                  // Object method: doesn't count
    // BigDecimal applyTwice(Order o);             // would cause a compile error
}

DiscountPolicy festive = o -> o.total().multiply(new BigDecimal("0.10"));

Common mistakes

  • Believing lambdas require the annotation.
  • Thinking default or static methods break the functional contract.
  • Forgetting the annotation on your own interfaces, losing the safety net.
  • Annotating an interface that inherits two unrelated abstract methods.

How to answer in the interview

"@FunctionalInterface documents that an interface is meant to have exactly one abstract method, so it can be a lambda or method reference target. Its real value is enforcement: if someone adds a second abstract method, compilation fails right there instead of silently breaking every lambda using it. It's optional; any single-abstract-method interface works without it. The interface may still have default, static and private methods, and abstract methods that redeclare Object's public methods, like equals, don't count. Runnable, Comparator and Function are examples."

Likely follow-up questions

  • Why does Comparator count as functional although it declares equals? equals is a public Object method, so it is excluded from the count.
  • Can a functional interface extend another? Yes, if it still ends up with one abstract method.
  • Can you put it on an abstract class? No, only on interfaces.
