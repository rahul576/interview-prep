What is Kubernetes used for?

Kubernetes · concept · levels entry

In one line

Kubernetes is a container orchestration platform: you declare desired state, and it schedules, scales, heals, load-balances and updates containers across a cluster, while managing configuration and secrets.

Detailed explanation

Running one container on one server is easy; running hundreds of services with several replicas each across dozens of machines is not. You need to decide where each container runs, restart it when it crashes, move it when a machine fails, route traffic to healthy copies, and roll out new versions without downtime. Kubernetes automates all of this.

The core idea is declarative desired state. You submit objects, usually YAML, to the API server: "a Deployment named orders with 3 replicas of image orders:1.4, each requesting 500m CPU and 512Mi memory". Controllers run reconciliation loops that constantly compare actual state with desired state and act on differences. If a pod crashes, the kubelet restarts it; if a node dies, the ReplicaSet controller creates replacement pods and the scheduler places them on nodes with free capacity.

Key capabilities:

  • Scheduling based on resource requests, affinity and taints.
  • Self-healing with restarts, rescheduling and liveness/readiness probes.
  • Scaling manually or with the HorizontalPodAutoscaler, and node autoscaling.
  • Service discovery and load balancing: a Service gives a stable DNS name and virtual IP over changing pods; Ingress or Gateway API handles external HTTP.
  • Rolling updates and rollbacks for Deployments.
  • ConfigMaps and Secrets injected as environment variables or files.
  • Storage through PersistentVolumes, and batch work through Jobs and CronJobs.

It runs on-premises or as managed services such as EKS, AKS and GKE, so teams get one consistent platform for microservices.

How it works

  1. Developer applies a Deployment manifest with kubectl apply or GitOps.
  2. API server stores it in etcd.
  3. Controllers create a ReplicaSet and pods.
  4. Scheduler assigns pods to nodes; kubelets start containers.
  5. Service routes traffic to ready pods; controllers keep reconciling.

Example

apiVersion: apps/v1
kind: Deployment
metadata: { name: orders }
spec:
  replicas: 3
  selector: { matchLabels: { app: orders } }
  template:
    metadata: { labels: { app: orders } }
    spec:
      containers:
        - name: orders
          image: registry.example.com/orders:1.4
          resources: { requests: { cpu: 500m, memory: 512Mi } }
          readinessProbe: { httpGet: { path: /actuator/health/readiness, port: 8080 } }
---
apiVersion: v1
kind: Service
metadata: { name: orders }
spec: { selector: { app: orders }, ports: [ { port: 80, targetPort: 8080 } ] }

Common mistakes

  • Calling Kubernetes "just Docker on many servers" and missing reconciliation.
  • Running stateful databases on it without understanding storage.
  • No resource requests or probes, so scheduling and healing misbehave.
  • Storing secrets in plain ConfigMaps.

How to answer in the interview

"Kubernetes orchestrates containers across a cluster of machines. I declare the desired state, for example three replicas of an image with certain resources, and controllers continuously reconcile reality with it. It schedules pods onto nodes with capacity, restarts crashed containers, replaces pods when a node dies, scales with the HorizontalPodAutoscaler, gives services stable DNS names with load balancing, does rolling updates and rollbacks, and injects config and secrets. It turns a fleet of servers into one platform for running microservices."

Likely follow-up questions

  • Control plane components? API server, etcd, scheduler, controller manager, and cloud controller manager.
  • Pod vs container? A pod is one or more containers sharing network and storage, the smallest schedulable unit.
  • Deployment vs StatefulSet? StatefulSets give stable identities and per-pod storage.
