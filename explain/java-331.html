How do you use virtual threads in a Spring Boot application, and what should you check first?

Spring Boot · concept · levels mid, senior

In one line

On Spring Boot 3.2+ and Java 21+, set spring.threads.virtual.enabled=true so Tomcat requests, @Async, scheduling and more run on virtual threads; first check pinning (synchronized blocks before Java 24), ThreadLocal-heavy code, and downstream limits like connection pools, then load test.

Detailed explanation

Virtual threads (Project Loom, final in Java 21) are lightweight threads scheduled by the JVM onto a small pool of carrier platform threads. When a virtual thread blocks on I/O, it is unmounted and the carrier runs another one. You keep simple blocking code but can have hundreds of thousands of concurrent tasks, which removes the main reason for reactive programming in many I/O-bound services.

In Spring Boot 3.2+ the single property spring.threads.virtual.enabled=true (with Java 21+) switches embedded Tomcat and Jetty request handling to virtual threads, makes the auto-configured applicationTaskExecutor used by @Async and Spring MVC async a SimpleAsyncTaskExecutor with virtual threads, and applies to @Scheduled and various message listener containers. Since Boot 3.2 you can also add spring.main.keep-alive=true, because virtual threads are daemon threads and an app with only scheduled tasks might otherwise exit.

Check before enabling:

  • Pinning: on Java 21-23, a virtual thread blocking inside a synchronized block or native call pins its carrier, so a few such calls can starve the carriers. JEP 491 in Java 24 removes pinning for synchronized; on older JDKs look for it with -Djdk.tracePinnedThreads (removed later) or JFR jdk.VirtualThreadPinned events, and upgrade drivers that use ReentrantLock instead.
  • Downstream limits: virtual threads remove the thread bottleneck, not the database one. A Hikari pool of 20 connections still allows 20 concurrent queries; thousands of requests will queue for connections and time out. Similar for rate-limited APIs. Use semaphores to bound concurrency explicitly.
  • ThreadLocal usage: millions of threads each with large ThreadLocal caches waste memory; object pools relying on thread reuse no longer help. Scoped values are the modern alternative.
  • CPU-bound work gains nothing.
  • Observability: thread dumps look different, and thread-per-request metrics change.

Then load test and compare throughput, p99 latency, pool wait times and memory with the old setup.

How it works

  1. Requests arrive; Tomcat starts a new virtual thread per request.
  2. Blocking I/O (JDBC, HTTP) parks the virtual thread and frees the carrier.
  3. When I/O completes, the thread is scheduled again on any carrier.
  4. Concurrency is then limited by real resources: pools, CPU, downstream services.

Example

spring:
  threads:
    virtual:
      enabled: true
  main:
    keep-alive: true
  datasource:
    hikari:
      maximum-pool-size: 30
      connection-timeout: 2000   # fail fast instead of queuing forever
# Java 21-23: record pinning events during a load test
java -XX:StartFlightRecording=filename=pin.jfr,settings=profile -jar app.jar
jfr print --events jdk.VirtualThreadPinned pin.jfr

Common mistakes

  • Expecting more throughput when the database pool is the bottleneck.
  • Pooling virtual threads in a fixed-size executor, defeating the point.
  • Ignoring pinning on Java 21 with old JDBC drivers.
  • Enabling it for CPU-heavy services.

How to answer in the interview

"From Spring Boot 3.2 on Java 21 I set spring.threads.virtual.enabled to true, and Tomcat request handling, @Async tasks, scheduling and several listeners run on virtual threads. Before enabling it I check three things: pinning, where synchronized blocks in our code or libraries pin the carrier during blocking calls, which Java 24 largely fixes; heavy ThreadLocal usage; and downstream limits, because connection pools and rate limits still bound real concurrency, so thousands of virtual threads may just queue on a database pool of twenty. Then I load test and compare throughput, latency and pool wait times."

Likely follow-up questions

  • Would virtual threads help a CPU-heavy image processing service? No; throughput is bound by cores, so use a sized platform thread pool.
  • Do virtual threads replace WebFlux? For most I/O-bound services yes; reactive still helps for streaming and backpressure.
  • Should you pool virtual threads? No, create one per task and limit concurrency with semaphores.
