Which data structures would you use to solve the grouped-anagrams problem efficiently?

DSA: Arrays & Strings · concept · levels mid

In one line

A HashMap from signature to an ArrayList of words gives average O(1) insertion and lookup, so grouping is a single pass; build each signature with a sorted char[] or an int[26] counter, and avoid pairwise comparison, which is quadratic.

Detailed explanation

The problem reduces to "bucket items by a computed key", which is exactly what hash maps are for.

HashMap<String, List<String>>. Hashing the signature and finding its bucket is average O(1) (plus O(k) to hash a key of length k). With one insertion per word, the grouping step is linear in the number of words. Since Java 8, heavily colliding buckets turn into balanced trees, so even worst-case lookups degrade to O(log n) rather than O(n).

ArrayList for each group. Appending is amortised O(1), it keeps words in input order, and converting map.values() into the result is cheap. A LinkedList offers no advantage here and uses more memory.

char[] or int[26] for the signature.

  • char[] + Arrays.sort → new String(chars): O(k log k), works for any characters.
  • int[26] frequency counts → serialised string: O(k), only for lowercase a–z (or int[128] for ASCII, HashMap for Unicode).

Why not compare pairs? A naive solution takes each word and compares it with every other word to find its anagrams, needing about n²/2 comparisons and a "visited" set to avoid duplicates. For 100,000 words that is around five billion comparisons; the hash approach does 100,000 key computations.

Alternatives and when to use them:

  • LinkedHashMap: same complexity, preserves first-seen group order.
  • TreeMap: sorted by key, but each operation is O(log g) with string comparisons, slower than hashing; use only if sorted output is required.
  • Pre-sizing: new HashMap<>(expectedGroups * 4 / 3 + 1) avoids rehashing for large inputs (Java 19+ offers HashMap.newHashMap(n)).
  • Trie keyed by sorted letters is possible but adds complexity with no benefit here.

How it works

  1. For each word, build the signature with char[] sort or int[26] counts.
  2. Hash the signature and find the bucket in the HashMap.
  3. Create or fetch the ArrayList for that key.
  4. Append the word.
  5. Return the collection of lists.

Example

public List<List<String>> group(String[] words) {
    Map<String, List<String>> map = HashMap.newHashMap(words.length);   // Java 19+
    int[] counts = new int[26];
    StringBuilder sb = new StringBuilder();
    for (String w : words) {
        Arrays.fill(counts, 0);
        for (int i = 0; i < w.length(); i++) counts[w.charAt(i) - 'a']++;
        sb.setLength(0);
        for (int n : counts) sb.append(n).append('#');
        map.computeIfAbsent(sb.toString(), k -> new ArrayList<>()).add(w);
    }
    return new ArrayList<>(map.values());
}

Common mistakes

  • Using a TreeMap without needing sorted keys.
  • Using arrays as keys.
  • Choosing LinkedList for groups.
  • Allocating a new int[26] and StringBuilder per word in hot loops when reuse is easy.

How to answer in the interview

"A HashMap from signature to an ArrayList of words, which gives average constant-time insertion and lookup per word, so the whole grouping is one pass. To build each signature I'd use a char array that I sort, or an int array of 26 counts for lowercase letters. The result is just the map's values. That avoids comparing every pair of words, which is quadratic. If order matters, LinkedHashMap keeps first-seen order; a TreeMap would sort groups by key but costs a log factor."

Likely follow-up questions

  • Why is a TreeMap slower here? Each operation is O(log g) with string comparisons instead of one hash computation.
  • What is the worst case of HashMap? O(log n) per bucket in Java 8+ because of treeified bins.
  • Why pre-size the map? To avoid repeated resizing and rehashing.
