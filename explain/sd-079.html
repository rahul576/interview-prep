Design an ML platform for training, deploying and monitoring models across many teams.

AI & ML System Design · design · levels senior, lead

In one line

An ML platform gives teams a paved road: data/feature pipelines and a feature store, scalable GPU training with scheduling, experiment tracking and a model registry, deployment for batch and online inference with canaries/shadowing, monitoring for drift and performance, and reproducibility, lineage and governance.

Detailed explanation

Without a platform, every team builds its own notebooks-to-production path, with inconsistent quality, duplicated infrastructure and models nobody can reproduce.

Data & features: orchestrated pipelines (Airflow, Dagster) produce features into a feature store with offline (training) and online (serving) stores, sharing definitions to avoid skew. Data versioning (Delta/Iceberg time travel, DVC) enables reproducibility.

Training: Kubernetes + Kubeflow/Ray, or managed (Azure ML, SageMaker, Vertex AI). GPU scheduling with quotas per team, queueing, spot instances with checkpointing, distributed training for large models.

Tracking & registry: MLflow (or W&B) records parameters, metrics, code commit and data snapshot per run. The model registry holds versions with stages (staging/production), approvals and model cards.

Deployment: batch scoring jobs; online endpoints (KServe, Seldon, Triton, managed endpoints) with autoscaling; canary or shadow deployments compare new vs current model on real traffic.

Monitoring: service metrics plus data drift (input distributions change), prediction drift, and performance once labels arrive; alerts can trigger retraining pipelines.

Governance: lineage from data to model to deployment, access control, audit, fairness/bias checks where required.

How it works

  1. Feature pipeline → feature store.
  2. Training job (CI-triggered or scheduled) → tracked run → registered model.
  3. Approval → deploy to staging → shadow/canary → production.
  4. Monitoring → drift alert → retrain → repeat.

Common mistakes

  • Feature logic duplicated in training notebooks and serving code.
  • No data versioning (can't reproduce a model).
  • Monitoring only latency, not model quality.
  • GPUs allocated per team statically and idle.

How to answer in the interview

"I'd provide a paved road: feature pipelines into a feature store with online and offline views; GPU training on Kubernetes or a managed service with quotas and spot capacity; MLflow for experiment tracking and a model registry with approvals; deployment to batch jobs or autoscaled endpoints with canary or shadow releases; and monitoring for drift and real performance that can trigger retraining. Lineage and access control cover governance."

Likely follow-up questions

  • Detect training/serving skew? Log online features and compare with offline values.
  • Shadow deployment? New model gets real traffic but its outputs aren't used.
  • GPU cost? Shared pools, spot with checkpointing, right-sized instances.
