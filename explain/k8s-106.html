Several pods across your worker nodes show very high CPU usage and latency is rising. How do you investigate and mitigate it?

Kubernetes · scenario · levels mid, senior

In one line

Identify the hot pods and nodes, separate real load from CPU limit throttling, correlate with traffic, releases or noisy neighbours, profile the code, and mitigate by scaling, rolling back and right-sizing requests and limits, with LimitRanges and quotas for governance.

Detailed explanation

Start with scope: kubectl top pods -A --sort-by=cpu and kubectl top nodes show current usage, and Prometheus/Grafana history shows when it started, which is often the strongest clue.

Next, distinguish two very different situations. If a container's CPU usage is flat at its limit, the kernel's CFS quota is throttling it: within each 100 ms period it uses its quota and then waits, which adds latency even while the node has idle CPU. Metrics container_cpu_cfs_throttled_periods_total and container_cpu_cfs_periods_total show the throttled share. The fix is a higher limit or removing the CPU limit and relying on requests. If instead the node is saturated, pods compete for real CPU, and the fix is more capacity or better placement.

Then correlate: a traffic increase, a new deployment that introduced an inefficient query or loop, a batch job or a noisy neighbour on the same node, garbage collection churn, or a retry storm where clients hammer a slow service. Profile the application to find hot paths: async-profiler or JFR for Java, pprof for Go, py-spy for Python.

Mitigation: scale horizontally with more replicas or an HPA, with node autoscaling behind it; roll back a bad release; right-size requests so the scheduler spreads load properly and limits do not throttle. LimitRanges set defaults and ResourceQuotas cap namespaces; they improve governance but do not make a busy app faster.

How it works

  1. Find affected pods and nodes with kubectl top and metrics history.
  2. Check throttling metrics versus node saturation.
  3. Correlate with traffic, deployments and co-located workloads.
  4. Profile the application for hot code paths.
  5. Mitigate: scale, roll back, adjust requests and limits.
  6. Prevent: HPA, alerts on throttling, load testing.

Common mistakes

  • Adding nodes when the real problem is a low CPU limit causing throttling.
  • Scaling out a retry storm, which multiplies the load.
  • Ignoring the timeline and missing that a release started it.
  • Expecting quotas and LimitRanges to fix performance.

How to answer in the interview

"First I find which pods and nodes are affected with kubectl top and look at the history in Grafana to see when it started. Then I separate real load from throttling: if usage sits at the limit, CFS throttling raises latency even when the node is idle, so the fix is a higher limit or none. I correlate with traffic, a new release, batch jobs or noisy neighbours, and profile the app, for example with async-profiler for Java. To mitigate I scale out with an HPA and node capacity, roll back a bad release and right-size requests and limits. LimitRanges and quotas help governance, not performance."

Likely follow-up questions

  • How do you tell throttling from a busy node? High throttled-period ratio with idle node CPU means throttling; node CPU near 100% means saturation.
  • Should you set CPU limits at all? Many teams set requests only for latency-sensitive services and use limits for multi-tenant fairness.
  • What is CPU steal? Time the hypervisor gave to other VMs, visible in top's st column.
