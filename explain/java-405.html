Your application logs database deadlock errors. How do you analyse and fix them?

Databases & SQL · scenario · levels mid, senior

In one line

A deadlock is two or more transactions each waiting for a lock the other holds; the database kills one as the victim, so you read the deadlock report, find the inconsistent lock order or over-broad locking, fix it, and make the application retry the victim.

Detailed explanation

Deadlocks are normal in busy OLTP systems, but frequent ones signal a design problem. Both InnoDB and PostgreSQL detect a cycle in the wait-for graph and abort one transaction: MySQL raises error 1213 (ER_LOCK_DEADLOCK), PostgreSQL raises SQLSTATE 40P01, and Spring translates them into exceptions such as CannotAcquireLockException or DeadlockLoserDataAccessException.

The first step is evidence. In MySQL, SHOW ENGINE INNODB STATUS shows the latest deadlock, with both transactions, the statements, the index and the locks held and waited for; innodb_print_all_deadlocks=ON writes every deadlock to the error log. PostgreSQL logs the deadlock with both queries (with log_lock_waits helping to see long waits too).

Typical causes:

  • Different lock order: one transfer updates account A then B, another B then A.
  • Missing indexes: an UPDATE ... WHERE email = ? without an index scans and locks many rows (and in InnoDB, gap/next-key locks under Repeatable Read), widening collisions.
  • Long transactions that hold locks while doing remote calls or user think-time.
  • Lock upgrades: read with a shared lock, then try to write.
  • Foreign key checks and unique-index inserts that take extra locks.

How it works

  1. Collect deadlock reports and correlate them with application logs and endpoints.
  2. Identify the two statements and the rows or index ranges involved.
  3. Enforce a consistent lock order (for example, always lock the lower account id first).
  4. Add indexes so statements lock only the rows they need.
  5. Keep transactions short; move HTTP or messaging calls outside them.
  6. Consider optimistic locking (@Version) or Read Committed to reduce gap locks.
  7. Add a bounded retry with backoff for the victim.

Example

@Transactional
public void transfer(long a, long b, BigDecimal amt) {
    long first = Math.min(a, b), second = Math.max(a, b);
    Account x = repo.findByIdForUpdate(first);   // SELECT ... FOR UPDATE
    Account y = repo.findByIdForUpdate(second);  // same order in every transaction
    // debit/credit ...
}

// Retry the deadlock victim (spring-retry)
@Retryable(retryFor = CannotAcquireLockException.class,
           maxAttempts = 3, backoff = @Backoff(delay = 50, multiplier = 2))
public void transferWithRetry(long a, long b, BigDecimal amt) { tx.transfer(a, b, amt); }

Common mistakes

  • Retrying inside the same transaction instead of starting a new one.
  • Raising the lock wait timeout, which does not prevent deadlocks.
  • Ignoring them because "the database resolves it" while users see errors.
  • Retrying non-idempotent work that includes external side effects.

How to answer in the interview

"A deadlock means two transactions wait on each other's locks, and the database aborts one as the victim. I'd start with evidence: SHOW ENGINE INNODB STATUS or innodb_print_all_deadlocks in MySQL, or the PostgreSQL logs, to see the exact statements and rows. The usual cause is acquiring locks in different orders, like A then B versus B then A, so I enforce a consistent order. I'd also add indexes so updates don't scan and lock extra rows, keep transactions short with no remote calls inside, and use optimistic locking where it fits. Because deadlocks can still occur, the application retries the victim transaction a few times with backoff."

Likely follow-up questions

  • Why can a missing index increase deadlocks? The statement scans and locks many rows or gaps instead of one, so more transactions collide.
  • Deadlock vs lock wait timeout? A deadlock is a cycle detected immediately; a timeout is a long wait with no cycle.
  • Where should the retry live? Around the whole transaction boundary, outside @Transactional.
