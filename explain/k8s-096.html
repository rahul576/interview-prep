A developer asks for their container to run as root because the app writes to /var/lib and binds port 80. How do you respond?

Kubernetes · scenario · levels entry, mid

In one line

I say no to root but solve the real needs: listen on a high port and let the Service map port 80, mount a writable volume for the data directory with fsGroup or correct ownership, and keep a documented exception process for truly privileged cases.

Detailed explanation

Running as root inside a container is not the same as root on the host, but it increases the blast radius of any vulnerability: combined with a kernel or runtime escape, a misconfigured hostPath, or excess capabilities, root in the container can become root on the node. That is why the restricted Pod Security Standard requires runAsNonRoot, allowPrivilegeEscalation: false, dropping all capabilities and a RuntimeDefault seccomp profile, and our admission policy would reject the pod anyway.

The developer's two needs are easy to meet without root. Port 80 matters only to clients; inside Kubernetes the app can listen on 8080 and the Service exposes port: 80 with targetPort: 8080. Ingress or the load balancer handles 80 and 443 externally. If a port below 1024 is truly needed, adding only NET_BIND_SERVICE is far narrower than root.

For writing to /var/lib/app, mount a volume at that path: an emptyDir for scratch data or a PersistentVolumeClaim for real data, and set fsGroup so the volume is group-writable by the app user. Alternatively create the directory and chown it to a non-root user in the Dockerfile. Keeping the root filesystem read-only is then also possible. Anything that genuinely needs privileges goes through a security review and a documented exception, scoped to one namespace.

How it works

  1. Explain the risk and the policy that will block root.
  2. Change the app to listen on 8080; map 80 in the Service.
  3. Add a non-root USER in the Dockerfile.
  4. Mount an emptyDir or PVC at the data path with fsGroup.
  5. Apply a restricted securityContext and test.
  6. Route remaining privileged needs to the exception process.

Example

spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    fsGroup: 10001
    seccompProfile: { type: RuntimeDefault }
  containers:
    - name: app
      image: registry.example.com/app:1.4.2
      ports: [{ containerPort: 8080 }]
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities: { drop: ["ALL"] }
      volumeMounts: [{ name: data, mountPath: /var/lib/app }]
  volumes:
    - name: data
      persistentVolumeClaim: { claimName: app-data }
---
apiVersion: v1
kind: Service
metadata: { name: app }
spec:
  selector: { app: app }
  ports: [{ port: 80, targetPort: 8080 }]

Common mistakes

  • Granting root "just this once" without an expiry or review.
  • Using privileged: true when one capability would do.
  • Writing data into the container filesystem, where it is lost on restart.
  • Forgetting that some volume types ignore fsGroup, leading to permission errors.

How to answer in the interview

"I would explain that root in a container raises the impact of any vulnerability, especially combined with an escape, and our restricted pod security policy would block it anyway, then help with the real needs. The app does not need port 80: it listens on 8080 and the Service exposes 80 with targetPort 8080. For writing data, I mount an emptyDir or a PersistentVolume at that directory and use fsGroup or set ownership in the Dockerfile for a non-root user. Most apps work in minutes. If something truly needs privileges, it goes through a documented exception with security review."

Likely follow-up questions

  • What would make you accept a privileged exception? Node-level agents like CNI or storage drivers, isolated in their own namespace, reviewed and monitored.
  • What does fsGroup do? Sets the group owner of mounted volumes and adds that group to the container's processes.
  • Are user namespaces relevant? Yes; they map container root to an unprivileged host user, reducing the risk further.
