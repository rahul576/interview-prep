What is tokenisation, and why does it matter for cost, limits and multilingual applications?

LLMOps & RAG · concept · levels entry, mid, senior

In one line

Tokenisation splits text into subword tokens (learned with algorithms like BPE), and everything in LLM APIs is counted in tokens: pricing, context windows, output limits and rate limits; English averages about four characters or three quarters of a word per token, while many other languages, code and JSON need more, and each model has its own tokenizer.

Detailed explanation

A model's vocabulary is a fixed set of tokens, typically tens of thousands to a few hundred thousand entries. A tokenizer converts text into token IDs. Most modern LLMs use byte pair encoding (BPE) or related methods (SentencePiece unigram, WordPiece): starting from bytes or characters, the most frequent adjacent pairs are merged repeatedly during tokenizer training. Common words become single tokens ("the", " interview"), while rare words, names, typos, IDs and technical strings split into several pieces ("Kubernetes" might be "Kub" + "ernetes"). Byte-level BPE guarantees any text can be encoded.

Why it matters for cost and limits. Providers price per million input and output tokens, context windows and max_tokens are in tokens, and rate limits are often tokens per minute. Estimating tokens is part of capacity and cost planning, and output tokens usually cost several times more than input.

Multilingual impact. Tokenizers are trained on data dominated by English and a few major languages. Hindi, Tamil, Telugu, Bengali, Arabic, Thai and many others often need noticeably more tokens for the same meaning, sometimes two to several times more, depending on tokenizer. That means higher cost, more context used, lower effective throughput and sometimes slower responses. Newer tokenizers with larger vocabularies have reduced the gap, but you should measure with the actual model.

Other effects. Code, JSON keys and whitespace tokenise inefficiently; verbose tool results are expensive. Numbers may split oddly, which partly explains arithmetic errors. Because models see tokens rather than letters, tasks like counting letters ("how many r's in strawberry") or reversing strings are harder than they look.

Each model family has its own tokenizer, so the same text yields different counts for different providers; compare prices per task, not per token.

How it works

  1. Text -> normalisation -> pre-tokenisation (split on spaces/punctuation, or bytes).
  2. BPE merges map pieces to vocabulary tokens.
  3. Tokens -> IDs -> embeddings in the model.
  4. API counts input and output tokens for billing and limits.
  5. Output token IDs are decoded back into text.

Example

import tiktoken
enc = tiktoken.get_encoding("o200k_base")   # tokenizer used by recent OpenAI models

for text in ["Where is my order?", "मेरा ऑर्डर कहाँ है?", '{"order_id": "A-77812"}']:
    print(len(text), "chars ->", len(enc.encode(text)), "tokens")

Common mistakes

  • Estimating cost from word counts.
  • Assuming the same token count across providers.
  • Budgeting multilingual products with English token averages.
  • Sending bulky JSON when compact text would do.

How to answer in the interview

"Models read tokens, not characters or words: subword pieces produced by a tokenizer, usually learned with byte pair encoding. Common words are one token, rare words and IDs split into several. Everything in the API is counted in tokens: price per million input and output tokens, context window, max output and tokens-per-minute rate limits. In English a token is about four characters, but many languages like Hindi, Tamil or Arabic need more tokens for the same meaning, so they cost more and use more context, and code and JSON tokenise differently. Each model has its own tokenizer, so counts differ. It also explains oddities like struggling to count letters."

Likely follow-up questions

  • Estimate multilingual cost? Tokenise a representative sample per language with the target model's tokenizer.
  • Why letter counting fails? The model sees multi-letter tokens, not individual characters.
  • Reduce tokens? Compact formats, shorter prompts, trimmed tool outputs.
