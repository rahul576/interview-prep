An analytics agent calls list_tables and describe_table before every query, adding seconds of latency. How do you fix it?

MCP Servers · scenario · levels mid, senior

In one line

Schemas rarely change, so stop rediscovering them: put ttlMs caching hints on list_tables and describe_table, expose the schema as a resource loaded once, put key table hints in the query tool description, return correct columns in errors, cache metadata server-side, and tell the agent to reuse known schema.

Detailed explanation

The agent is behaving rationally: it has no reliable signal that the schema it saw two questions ago is still valid, so it re-checks before every query. Each discovery call costs a tool round trip plus a model round trip, which together often add one to three seconds per call. Several complementary fixes remove most of that.

Protocol caching hints. Newer MCP revisions let servers attach caching hints, such as a ttlMs, to results. Marking list_tables and describe_table results as valid for, say, an hour lets supporting clients reuse them instead of calling again. Where supported, a scope hint can mark them as shareable or private.

Schema as a resource. Expose schema://analytics/main as a resource. Hosts can load it into context at the start of a session, so the model already knows the tables before the first question.

Smarter descriptions. The run_query tool description can name the key tables and their purpose ("orders: one row per order; order_items: line items; customers: …") and state that schema information does not need refreshing within a session.

Error-driven discovery. When a query references an unknown table or column, the error returns the correct columns or closest matches: "Column customer_name not found in orders; available: order_id, customer_id, …". The agent only looks up schema when it actually needs it.

Server-side caching. Cache information_schema queries in the server, invalidated on migrations, so even repeated calls take milliseconds.

Agent instructions. The system prompt can say: reuse schema already in context; describe a table only if it is unknown or a query fails.

How it works

  1. Session starts; host loads the schema resource (or the first list_tables result is cached by ttlMs).
  2. User asks a question; model writes SQL directly using known tables.
  3. Query runs; on schema error, the server returns corrected column lists.
  4. Repeated describe_table calls hit the server cache.
  5. Migration event invalidates the server cache and bumps the schema resource.

Example

{
  "content": [{ "type": "text", "text": "tables: orders(order_id, customer_id, created_at, total, status), order_items(...), customers(...)" }],
  "structuredContent": { "tables": ["orders", "order_items", "customers"] },
  "_meta": { "cache": { "ttlMs": 3600000 } }
}
run_query description:
"Run a read-only SQL query on the analytics warehouse. Main tables: orders, order_items,
customers, products. Schema is stable during a session; only call describe_table for
tables you have not seen."

The exact field names for caching hints depend on the protocol revision your SDK implements; check it before relying on them.

Common mistakes

  • Caching so long that a migration leaves the agent writing invalid SQL.
  • Dumping the entire warehouse schema (thousands of tables) into context.
  • Generic errors like "query failed" that force rediscovery.
  • Fixing only the prompt, which works inconsistently.

How to answer in the interview

"Schemas rarely change, but the agent doesn't know its view is still valid, so it rediscovers every time. I'd combine fixes. On the protocol side, list_tables and describe_table results carry caching hints with a ttlMs of maybe an hour, so supporting clients skip repeat calls. Exposing the schema as a resource lets the host load it once at session start. The query tool description names the key tables and says schema doesn't need refreshing within a session, and when a query hits an unknown column the error returns the right columns, so the agent only looks up schema when needed. On the server, metadata queries are cached. Finally, agent instructions tell it to reuse known schema."

Likely follow-up questions

  • Risk of aggressive caching? Stale schema after migrations; invalidate on deploy and keep TTLs moderate.
  • Huge warehouses? Expose a curated subset or a schema search tool, not everything.
  • Semantic layer? Even better: expose metrics and dimensions instead of raw tables.
