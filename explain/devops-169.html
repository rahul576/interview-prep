Users get intermittent DNS resolution failures inside a Kubernetes cluster. How do you troubleshoot?

Troubleshooting · scenario · levels mid, senior

In one line

Reproduce from a debug pod with dig/nslookup, check CoreDNS pods, logs and metrics, and look for the classic causes: ndots:5 and search domains multiplying queries, conntrack races on UDP causing 5-second timeouts, overloaded CoreDNS, and network policies blocking port 53; fix with scaling CoreDNS, NodeLocal DNSCache, lower ndots or FQDNs.

Detailed explanation

Intermittent DNS failures are hard because most lookups work. Start by reproducing: run a debug pod (for example nicolaka/netshoot) in the affected namespace and node, and loop dig against a service name (orders.shop.svc.cluster.local) and an external domain, recording failures and latency. Then check CoreDNS: are all replicas Running, restarting or OOMKilled; do logs show SERVFAIL, upstream timeouts or i/o timeout; and do metrics such as coredns_dns_request_duration_seconds and coredns_forward_responses_total show saturation?

ndots and search domains. Pods get options ndots:5 and several search domains in /etc/resolv.conf. A name with fewer than five dots, like api.stripe.com, is first tried with every search suffix — api.stripe.com.shop.svc.cluster.local, ...svc.cluster.local, ...cluster.local, plus cloud domains — each for A and AAAA. One lookup becomes eight to ten queries, multiplying CoreDNS load.

Conntrack races. glibc sends A and AAAA queries in parallel from the same UDP socket. A known Linux conntrack race can drop one of them under DNAT to the CoreDNS service IP, so the resolver waits for its 5-second timeout and retries. This produces the signature "sometimes exactly five seconds".

Fixes: scale CoreDNS (more replicas, or the cluster-proportional autoscaler) and give it adequate resources; deploy NodeLocal DNSCache, which runs a cache on every node, avoids conntrack for pod-to-cache traffic and uses TCP upstream; lower ndots via dnsConfig or use FQDNs with a trailing dot for external names; use single-request-reopen for glibc images; and verify NetworkPolicies allow egress to kube-dns on UDP and TCP 53.

How it works

  1. Reproduce with dig loops from a debug pod on the affected node.
  2. Check CoreDNS replicas, restarts, logs and latency metrics.
  3. Inspect /etc/resolv.conf in the app pod for ndots and search list.
  4. Look for 5-second latency patterns pointing to conntrack drops.
  5. Check node conntrack table usage and NetworkPolicies.
  6. Apply fixes: scale, NodeLocal DNSCache, ndots, FQDNs.

Example

kubectl run dnstest --rm -it --image=nicolaka/netshoot -- bash
for i in $(seq 1 200); do dig +short +tries=1 +time=2 api.stripe.com >/dev/null || echo fail; done
cat /etc/resolv.conf   # search shop.svc.cluster.local svc.cluster.local cluster.local; options ndots:5
kubectl -n kube-system logs -l k8s-app=kube-dns --tail=100
spec:
  dnsConfig:
    options:
      - name: ndots
        value: "2"

Common mistakes

  • Testing once from a laptop and concluding DNS is fine.
  • Restarting CoreDNS without understanding the load source.
  • Lowering ndots globally without testing short internal names.
  • NetworkPolicies allowing UDP 53 but not TCP 53.

How to answer in the interview

"I start a debug pod and loop dig or nslookup against service names and external domains to reproduce, then look at CoreDNS pods, logs and metrics for errors, latency and saturation. A common cause is ndots 5 with long search lists, so each external lookup turns into several extra queries and multiplies load. Another is the conntrack race with parallel UDP A and AAAA queries, which causes intermittent exactly-five-second timeouts. Fixes include scaling CoreDNS, deploying NodeLocal DNSCache, lowering ndots or using FQDNs with a trailing dot, and checking network policies allow port 53."

Likely follow-up questions

  • Why does curl sometimes take exactly five seconds? A dropped UDP DNS packet; the resolver waits its 5-second timeout and retries.
  • What does NodeLocal DNSCache change? Pods query a local cache on the node, avoiding conntrack and reducing CoreDNS load.
  • Why does a trailing dot help? It marks the name fully qualified, skipping search domain expansion.
