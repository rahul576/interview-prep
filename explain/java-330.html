How do you containerise a Spring Boot application well?

Build Tools · concept · levels mid, senior

In one line

Use layered images (Spring Boot layered jars via jarmode tools/layertools, Buildpacks or Jib) so dependencies cache separately from code, a small JRE or distroless base running as non-root, container-aware JVM memory (MaxRAMPercentage), graceful shutdown and liveness/readiness probes.

Detailed explanation

Layering. A Spring Boot fat jar contains your code plus 50–150 MB of dependencies. Copying it as a single layer means every code change produces a new large layer to build, push and pull. Spring Boot's layered jars split the content into layers such as dependencies, spring-boot-loader, snapshot-dependencies and application. In a multi-stage Dockerfile you extract them (java -Djarmode=tools -jar app.jar extract --layers --launcher on Boot 3.3+, or the older layertools extract) and COPY each as its own layer; only the small application layer changes per commit.

No-Dockerfile options. mvn spring-boot:build-image (or bootBuildImage) uses Cloud Native Buildpacks to produce an optimised, layered image with a memory calculator and regularly patched base. Jib builds layered images directly from Maven/Gradle without a Docker daemon.

Base image and user. Use a JRE, not a JDK, from a maintained distribution (Eclipse Temurin, distroless Java, or a jlink-built runtime), pin it by tag or digest, scan it, and run as a non-root user.

JVM memory. Modern JVMs are container-aware and read cgroup limits, but the default heap is only 25% of the container limit. Set -XX:MaxRAMPercentage=75 (leaving room for metaspace, threads and native memory) and set the container memory limit accordingly.

Lifecycle. Enable server.shutdown=graceful so in-flight requests finish when Kubernetes sends SIGTERM, use the exec form of ENTRYPOINT so the JVM receives signals, and expose Actuator liveness and readiness probes (/actuator/health/liveness, /readiness), with a startup probe for slow starts.

How it works

  1. Build the layered jar in a build stage.
  2. Extract layers.
  3. Copy layers in order of change frequency onto a JRE base.
  4. Run as non-root with container-aware JVM flags.
  5. Configure graceful shutdown and health probes in Kubernetes.

Example

FROM eclipse-temurin:21-jdk AS build
WORKDIR /src
COPY . .
RUN ./mvnw -q package -DskipTests && \
    java -Djarmode=tools -jar target/app.jar extract --layers --launcher --destination /layers

FROM eclipse-temurin:21-jre
RUN useradd -r -u 1001 app
USER 1001
WORKDIR /app
COPY --from=build /layers/dependencies/ ./
COPY --from=build /layers/spring-boot-loader/ ./
COPY --from=build /layers/snapshot-dependencies/ ./
COPY --from=build /layers/application/ ./
ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75"
ENTRYPOINT ["java", "org.springframework.boot.loader.launch.JarLauncher"]
# application.yml
server.shutdown: graceful
management.endpoint.health.probes.enabled: true

Common mistakes

  • Copying a single fat jar, so every build pushes the whole image.
  • Using a full JDK base image and running as root.
  • Setting -Xmx equal to the container limit, causing OOMKills.
  • Shell-form ENTRYPOINT, so SIGTERM never reaches the JVM.

How to answer in the interview

"Spring Boot supports layered jars, so dependencies, which rarely change, go into separate image layers from application code, making rebuilds and pushes fast. I either write a multi-stage Dockerfile that extracts the layers, or use Buildpacks with spring-boot:build-image, or Jib, which build optimised images without a Dockerfile. The image uses a small JRE or distroless base and runs as non-root. The JVM is container-aware, and I tune MaxRAMPercentage rather than a fixed Xmx. And I enable graceful shutdown and expose Actuator liveness and readiness probes."

Likely follow-up questions

  • Why is copying a single fat jar inefficient? Any code change invalidates the whole large layer, so caching does not help.
  • What about startup time? Class Data Sharing, Spring AOT, or GraalVM native images for fast start.
  • Why not liveness check the database? A database outage would restart all pods without fixing anything; put it in readiness only if needed.
