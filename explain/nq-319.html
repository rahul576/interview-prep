How would you avoid repeatedly polling a database for a downstream callback?

Cloud (AWS) · design · levels senior, lead

In one line

Replace "keep asking the database" with "the change announces itself": the callback handler publishes an event or message, or change data capture emits it, and the waiting process reacts. Workflows wait on a task token and browsers get a push (WebSocket/SSE). Any polling that has to stay uses backoff, limits and indexes.

Detailed explanation

A typical case: we call a payment provider or a partner API, and the result comes back later on a webhook callback. The naive design has workers or the UI query SELECT status FROM payments WHERE id = ? every two seconds. At scale that means thousands of wasted queries per second, extra load on the primary, and latency set by the polling interval.

The cure is to turn the state change into a signal:

  • Publish from the callback handler. After updating the row, the handler publishes PaymentCompleted to SNS, SQS, EventBridge or Kafka. Use the transactional outbox so the DB update and the event cannot drift apart.
  • Change data capture. DynamoDB Streams trigger a Lambda, Debezium tails the PostgreSQL WAL or MySQL binlog into Kafka, or PostgreSQL LISTEN/NOTIFY works for small, single-database setups.
  • Workflow wait states. In AWS Step Functions, a task using .waitForTaskToken pauses the execution (up to a year) at no compute cost. The callback calls SendTaskSuccess with the token, and the workflow resumes.
  • Push to clients. Use WebSocket (API Gateway WebSocket, AppSync), server-sent events, or a webhook to the client system.

If polling cannot be removed, for example with a partner who offers no callback, make it cheap. Use exponential backoff with jitter and a maximum wait. Run an indexed query on status, or read from a cache. A delayed message (SQS DelaySeconds, a scheduler) can trigger the next check, so no thread sits in a loop.

How it works

  1. The client submits a request. The service stores it as PENDING and returns an id.
  2. The external system later calls our webhook. The handler verifies the signature and updates the row.
  3. In the same transaction, an outbox row is written. A relay (or CDC) publishes StatusChanged.
  4. Consumers react: the Step Functions task token is completed, the next business step starts, or a notification service pushes to the browser via WebSocket.
  5. A timeout path (Step Functions heartbeat/timeout or a scheduled check) handles callbacks that never arrive.

Example

# Webhook handler resumes a Step Functions execution instead of anyone polling
def on_payment_callback(event):
    body = verify_signature(event)
    order = db.update_status(body["orderId"], body["status"])   # commit
    sfn.send_task_success(
        taskToken=order.task_token,
        output=json.dumps({"status": body["status"]}))

Common mistakes

  • Tight polling loops in many workers, all hitting the primary database.
  • Publishing the event outside the transaction, so it gets lost or arrives before the commit.
  • No timeout handling for callbacks that never come.
  • Using LISTEN/NOTIFY as a durable queue. Notifications are lost if no listener is connected.

How to answer in the interview

"I'd make the state change push a signal instead of having anyone poll. The callback handler updates the record and, through an outbox, publishes an event to SNS, EventBridge or Kafka. Or I'd use CDC, such as DynamoDB Streams or Debezium. A long-running process can wait on a Step Functions task token that the callback completes, and the browser gets the update over WebSocket or SSE. If some polling has to remain, I'd add exponential backoff, a time limit and an indexed query, and I'd always have a timeout path for callbacks that never arrive."

Likely follow-up questions

  • What is a Step Functions task token? It is a unique token passed to a waiting task. An external system calls SendTaskSuccess or SendTaskFailure with it to resume the workflow.
  • Webhook security? Verify HMAC signatures, check timestamps for replay protection, and make the handler idempotent.
  • CDC versus outbox? CDC captures every committed change with no app code. An outbox gives you explicit, well-shaped domain events.
