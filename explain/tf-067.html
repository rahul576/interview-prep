terraform plan shows that resources you never touched will be destroyed. How do you investigate before anyone applies?

Terraform · scenario · levels mid, senior

In one line

Never apply a plan with unexpected destroys: first check you are on the right workspace, backend key and variable file, then inspect git history for removed code or bad merges, changed for_each/count keys, and module or provider version changes, then fix with restored code, moved blocks or corrected inputs.

Detailed explanation

An unexpected destroy is one of the most dangerous moments in Terraform work. The plan is telling you that the configuration no longer contains objects the state knows about, or that their addresses changed. Investigate systematically, from the cheapest explanation to the hardest.

Wrong target. The most common cause: the wrong workspace, backend key or tfvars file. Prod variables against the dev state (or the reverse) make Terraform want to replace or delete large parts of the environment. Check the backend configuration printed by init, terraform workspace show and the var files in the command.

Code removed. Someone deleted a resource or module block, intentionally without realising the consequence, or through a bad merge or rebase. git log -p and the branch diff against main reveal it.

Address changes. A renamed resource label, a changed for_each key (for example renaming a map key from web to frontend), or an item removed from the middle of a count list all change addresses. Terraform sees "old address destroyed, new address created".

Version changes. A module version bump may have renamed internal resources or switched from count to for_each; a provider upgrade may introduce force-new attributes. The module changelog should mention required moved blocks.

Once found: restore the code, add moved blocks for renames, correct the inputs, or, if the removal is intentional but the object must survive, use a removed block with destroy = false. Re-plan until only intended changes remain.

How it works

  1. Stop: no apply, notify reviewers.
  2. Verify workspace, backend key, var files and credentials.
  3. Diff the branch and recent merges for deleted blocks.
  4. Compare addresses: look for key or index changes.
  5. Check module and provider version changes.
  6. Fix and re-plan until destroys are gone or intentional.

Example

terraform workspace show
grep -A5 'backend' .terraform/terraform.tfstate | head
git diff origin/main...HEAD --stat
git log -p -S 'azurerm_storage_account' -- '*.tf'
terraform show -json tfplan | jq -r '.resource_changes[] | select(.change.actions|index("delete")) | .address'
moved {
  from = module.app.azurerm_linux_web_app.this["web"]
  to   = module.app.azurerm_linux_web_app.this["frontend"]
}

Common mistakes

  • Assuming the plan is wrong and applying anyway.
  • Fixing symptoms with state rm instead of finding the cause.
  • Running local plans with leftover .terraform pointing at another backend.
  • Upgrading modules without reading their changelog.

How to answer in the interview

"I never approve unexpected destroys. First I check we're pointing at the right state: workspace, backend key and variable file, because prod variables against a dev state produce exactly this. Then git history and the branch diff: someone may have removed a resource or module, maybe through a bad merge. Then key changes: a renamed for_each key or an item removed from a count list destroys and recreates. A module or provider upgrade can also rename resources. Once I know the cause I restore the code, add moved blocks or fix inputs, and re-plan until only intended changes remain."

Likely follow-up questions

  • How can CI flag destroys automatically? Parse the JSON plan and require extra approval or fail on deletes of protected types.
  • What protects critical resources? prevent_destroy, cloud deletion locks and policy checks.
  • Why prefer for_each keys? Stable names instead of positions.
