How does JWT-based authentication work in a Spring Boot microservice?

Security · concept · levels mid, senior

In one line

The client gets a signed JWT access token from an identity provider and sends it as a Bearer token; Spring Security, configured as an OAuth 2 resource server, verifies the signature via JWKS and checks exp, iss and aud on every request, so the service stays stateless.

Detailed explanation

A JWT (JSON Web Token) has three base64url parts: a header (algorithm such as RS256 or ES256, and a key id kid), a payload of claims (sub, iss, aud, exp, iat, scope, roles) and a signature. The signature proves the token was issued by the trusted authorization server and not altered. It does not hide the content: the payload is only encoded, so personal or secret data must not go in it.

In a typical microservice setup the user signs in through OAuth 2 / OpenID Connect at an identity provider (Keycloak, Okta, Entra ID, Auth0). The client receives an access token and calls APIs with Authorization: Bearer <token>. Each Spring Boot service is a resource server: the BearerTokenAuthenticationFilter in the SecurityFilterChain extracts the token, a JwtDecoder fetches and caches the provider's public keys from the JWKS endpoint, verifies the signature, and validates expiry, not-before, issuer and audience. Then it builds a JwtAuthenticationToken with authorities (by default SCOPE_ + each scope) and stores it in the SecurityContext.

Because everything needed is in the token, there is no server session and any instance can handle any request, which suits horizontal scaling. The trade-off is revocation: a valid token works until it expires. So access tokens are short lived (5 to 15 minutes) and clients use refresh tokens, which the authorization server can revoke and rotate.

How it works

  1. Client authenticates at the identity provider (authorization code with PKCE) and receives access and refresh tokens.
  2. Client sends the access token as a Bearer header.
  3. Resource server filter extracts it and looks up the signing key by kid in the cached JWKS.
  4. It verifies the signature and validates exp, nbf, iss and aud.
  5. Claims are mapped to authorities and placed in the SecurityContext; authorization rules run.
  6. When the token expires, the client uses the refresh token to get a new one.

Example

spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://login.example.com/realms/shop
          audiences: orders-api
@Bean
SecurityFilterChain api(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(a -> a
            .requestMatchers("/actuator/health/**").permitAll()
            .requestMatchers(HttpMethod.POST, "/orders/**").hasAuthority("SCOPE_orders.write")
            .anyRequest().authenticated())
        .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))
        .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS));
    return http.build();
}

Common mistakes

  • Not validating the audience, so a token for another API is accepted.
  • Accepting alg: none or using a shared HS256 secret across many services.
  • Long-lived access tokens with no refresh strategy.
  • Putting personal or sensitive data in the payload.
  • Storing tokens in localStorage in browser apps, exposing them to XSS.

How to answer in the interview

"The user logs in at an identity provider using OAuth 2 and OpenID Connect and the client gets a JWT access token. A JWT has a header, a payload of claims like subject, scopes, issuer, audience and expiry, and a signature. The client sends it as a Bearer token. In Spring Boot I configure the service as an OAuth 2 resource server with the issuer URI; the filter chain verifies the signature using the provider's JWKS public keys and checks expiry, issuer and audience, then puts the principal and authorities into the SecurityContext. Nothing is stored server side, so it is stateless. I keep access tokens short lived with refresh tokens, and never put secrets in the payload because it is only encoded."

Likely follow-up questions

  • How would you revoke a JWT before it expires? Short expiry plus refresh-token revocation; for urgent cases a deny-list of jti values in Redis, or opaque tokens with introspection.
  • How are signing keys rotated? The provider publishes new keys in JWKS with a new kid; Spring refreshes its cached key set.
  • What about service-to-service calls? Client credentials tokens or token exchange, often plus mTLS.
