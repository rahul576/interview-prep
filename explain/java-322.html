How does HTTP caching work for APIs? Explain ETag and Cache-Control.

REST & API Design · concept · levels mid, senior

In one line

Cache-Control tells browsers, proxies and CDNs whether and how long to cache (max-age, private, no-store, no-cache); an ETag identifies a resource version, enabling conditional requests: If-None-Match → 304 Not Modified for reads and If-Match → 412 Precondition Failed for safe updates.

Detailed explanation

HTTP caching saves bandwidth, latency and server load, and works for APIs as well as web pages.

Cache-Control (RFC 9111) directives on the response:

  • max-age=60: the response is fresh for 60 seconds; caches can serve it without asking the server. s-maxage applies only to shared caches (CDN, proxies).
  • public allows shared caches to store it; private allows only the user's browser, needed for user-specific data.
  • no-cache: may store, but must revalidate with the server before each use.
  • no-store: never store, for sensitive data like account details or tokens.
  • stale-while-revalidate lets caches serve a slightly stale copy while fetching a new one.

ETag is an opaque validator for the current representation, such as a hash of the body ("5d8c72a5") or a version number. Strong ETags mean byte-identical; weak ones (W/"...") mean semantically equivalent. Last-Modified is an older, date-based validator.

Conditional GET (revalidation). The client stores the ETag and later sends If-None-Match: "5d8c72a5". If unchanged, the server replies 304 Not Modified with no body; the client reuses its copy. Bandwidth is saved; whether server work is saved depends on how the ETag is computed.

Conditional update (optimistic concurrency). A client sends PUT or PATCH with If-Match: "v7". If the resource is still at version 7, the update proceeds; if someone else changed it, the server returns 412 Precondition Failed, preventing lost updates. Some APIs require If-Match and return 428 Precondition Required if it is missing. Mapping the ETag to a JPA @Version column is a neat implementation.

CDNs and proxies honour these headers, so public catalogue data with public, max-age=300 can be served from the edge. Use Vary (e.g. Vary: Accept-Encoding) when the response depends on request headers. Never cache authenticated responses in shared caches unless marked appropriately.

How it works

  1. Server returns body + ETag + Cache-Control.
  2. Within max-age, cache serves it directly.
  3. After expiry, cache revalidates with If-None-Match.
  4. Server answers 304 (reuse) or 200 (new body + new ETag).
  5. Updates send If-Match; mismatch gives 412.

Example

GET /products/42
HTTP/1.1 200 OK
Cache-Control: public, max-age=300
ETag: "v17"

GET /products/42
If-None-Match: "v17"
HTTP/1.1 304 Not Modified

PUT /products/42
If-Match: "v16"
HTTP/1.1 412 Precondition Failed
@GetMapping("/products/{id}")
ResponseEntity<ProductDto> get(@PathVariable long id) {
    Product p = repo.findById(id).orElseThrow();
    return ResponseEntity.ok()
        .eTag("\"" + p.getVersion() + "\"")
        .cacheControl(CacheControl.maxAge(Duration.ofMinutes(5)).cachePublic())
        .body(ProductDto.from(p));
}

Common mistakes

  • Marking user-specific responses public.
  • Confusing no-cache (revalidate) with no-store (never store).
  • Computing ETags by rendering the full body every time on expensive endpoints.
  • Ignoring If-Match, allowing lost updates.

How to answer in the interview

"Cache-Control tells clients and proxies how to cache: max-age sets freshness, public or private decides whether shared caches like CDNs may store it, no-cache forces revalidation and no-store forbids storing sensitive data. An ETag identifies the current version of a resource, for example a hash or the entity version. Clients send If-None-Match with the ETag, and if nothing changed the server returns 304 Not Modified with no body. For updates, If-Match gives optimistic concurrency: the update only succeeds if the version still matches, otherwise 412 Precondition Failed. Public responses can then be served straight from a CDN."

Likely follow-up questions

  • How would you generate ETags efficiently in Spring? Use the entity's @Version or updated timestamp; ShallowEtagHeaderFilter hashes the body but still does the work.
  • What is a weak ETag? Indicates semantic equivalence, not byte equality.
  • How do you invalidate a CDN cache? Purge by URL or tag, or use short max-age with versioned URLs.
