Apply fails with Provider produced inconsistent final plan or inconsistent result after apply. What does it mean, and what do you do?

Terraform · scenario · levels mid, senior

In one line

Both errors mean the provider broke Terraform's contract: a value at apply differed from what the plan promised, or the result after apply did not match the configuration; it is almost always a provider bug, often due to unknown values or API normalisation, so re-run, check known issues and upgrade, work around it, and report it.

Detailed explanation

Terraform's core relies on a promise: during plan, the provider says what each attribute will become (a concrete value or "unknown"). During apply, it re-plans with now-known values and then creates or updates the object. Terraform checks two things.

"Provider produced inconsistent final plan": when re-planning at apply time, a value differs from the original plan. Typically an attribute that was known in the plan changed because some upstream value that was unknown is now known, and the provider did not mark it unknown correctly.

"Provider produced inconsistent result after apply": after the API call, the value the provider returns differs from the planned value. Common causes: the API normalises input (lower-cases a name, reorders a list, adds a trailing dot to DNS names, expands a short JSON policy), or applies a default the provider schema did not declare as computed.

In both cases Terraform stops and refuses to record misleading state, because silently accepting the value would break the guarantee that applies do what plans show. The resource may actually exist; often state still records it, and the error message says the issue should be reported to the provider developers.

Practical response: re-run plan and apply, which often succeeds because the values are now known and stored. Check the provider's changelog and GitHub issues for the resource; upgrade if a fix exists. Otherwise work around: set the value explicitly in the normalised form the API returns, avoid passing unknown values into that argument, or split the apply. Then report with a minimal reproduction and TF_LOG=DEBUG logs.

How it works

  1. Plan records predicted values; apply re-plans with known values.
  2. Terraform compares the final plan with the original, then the result with the plan.
  3. Mismatch: Terraform raises the error and stops.
  4. Re-run; check state and the real resource.
  5. Search issues, upgrade or apply a workaround.
  6. Report the bug with a reproduction.

Example

Error: Provider produced inconsistent result after apply

When applying changes to aws_iam_policy.app, provider "registry.terraform.io/hashicorp/aws"
produced an unexpected new value: .policy: was "{...}", but now "{...}".

This is a bug in the provider, which should be reported in the provider's own issue tracker.
# Workaround: give the API the normalised form it returns
policy = jsonencode(local.policy_document)   # instead of a hand-written JSON string

Common mistakes

  • Editing state to "fix" the value.
  • Assuming your own code is wrong and rewriting large parts.
  • Not checking whether the resource was actually created before retrying.
  • Ignoring the error because the second apply worked, so it returns in every new environment.

How to answer in the interview

"These errors mean the provider broke Terraform's contract: at apply time a value differed from what the plan promised, or after apply the provider returned something different from the configuration. Terraform stops rather than record incorrect state. They're almost always provider bugs, often from values unknown during plan, or the API normalising values like casing or list order. I re-run plan and apply, which often works, check the changelog and issues and upgrade if fixed, otherwise work around it by setting the value explicitly, and report it with a minimal reproduction."

Likely follow-up questions

  • Why refuse to save state? Saving would make state disagree with the reviewed plan, breaking trust in plans.
  • How do you collect evidence? TF_LOG=DEBUG with sensitive data removed, plus versions and a minimal config.
  • Are these ever user errors? Rarely; sometimes configuration feeds values the API rewrites.
