What are the Proxy, Decorator and Adapter patterns, and where does Spring use them?

Design Patterns · concept · levels mid, senior

In one line

A Proxy stands in for an object to control access (transactions, security, lazy loading), a Decorator wraps an object with the same interface to add behaviour, and an Adapter converts one interface into another; Spring uses proxies for AOP and @Transactional, and HandlerAdapter in MVC.

Detailed explanation

All three are structural patterns and all three wrap another object, so they look alike in code. The difference is intent.

Proxy implements the same interface as the real subject and controls how and when it is reached. Spring AOP creates a JDK dynamic proxy (for interfaces) or a CGLIB subclass around beans with @Transactional, @Cacheable, @Async or @PreAuthorize; the proxy opens a transaction, checks the cache or verifies permissions, then delegates. Hibernate returns lazy-loading proxies for associations, and Feign or gRPC stubs are remote proxies. Because the proxy is outside your object, a method calling another method on this skips the proxy, the famous self-invocation problem.

Decorator also keeps the same interface but its purpose is to stack extra behaviour dynamically, composing as many layers as needed. Java I/O is the textbook case: new BufferedReader(new InputStreamReader(new FileInputStream(f))). Spring examples include BeanPostProcessor-wrapped beans, ContentCachingRequestWrapper, and decorating a RestTemplate/WebClient with logging or retry. It is a flexible alternative to subclassing for each combination.

Adapter changes the interface. Spring MVC's DispatcherServlet does not know whether a handler is an @RequestMapping method, an HttpRequestHandler or a functional endpoint; a HandlerAdapter for each type makes them callable uniformly. InputStreamReader adapts bytes to characters; your own code adapts a vendor SDK to your PaymentGateway interface.

How it works

  1. Proxy: client → proxy (same interface) → checks/setup → real object.
  2. Decorator: client → decorator A → decorator B → core object, each adding behaviour.
  3. Adapter: client → target interface → adapter → adaptee's different API.
  4. In Spring, a post-processor replaces your bean with a proxy at startup.

Example

@Service
public class TransferService {
    @Transactional
    public void transfer(long from, long to, BigDecimal amt) { /* proxy wraps this in a tx */ }

    public void batch() {
        transfer(1, 2, BigDecimal.TEN); // self-invocation: bypasses proxy, no new tx!
    }
}

// Decorator
InputStream in = new BufferedInputStream(new GZIPInputStream(new FileInputStream("data.gz")));

// Adapter
class LegacySmsAdapter implements SmsSender {
    private final LegacySmsClient client;
    LegacySmsAdapter(LegacySmsClient c) { this.client = c; }
    public void send(String to, String text) { client.sendMessage(new LegacyMsg(to, text)); }
}

Common mistakes

  • Expecting @Transactional to work on self-invoked or private methods.
  • Calling a decorator an adapter because both wrap an object.
  • Deep decorator chains that are hard to debug.
  • Lazy-loading proxies accessed after the session closes (LazyInitializationException).

How to answer in the interview

"All three wrap an object but with different intent. A proxy has the same interface and controls access, adding things like transactions, security or lazy loading. Spring AOP wraps beans with JDK or CGLIB proxies for @Transactional and @Cacheable, and Hibernate uses proxies for lazy associations. A decorator also keeps the interface but stacks behaviour, like BufferedInputStream around FileInputStream. An adapter converts one interface into another; Spring MVC's HandlerAdapter lets DispatcherServlet call different handler types. I'd also mention self-invocation bypassing Spring proxies."

Likely follow-up questions

  • How is a decorator different from inheritance? It adds behaviour at runtime by composition and can combine layers freely, without a subclass per combination.
  • JDK proxy vs CGLIB? JDK proxies need an interface; CGLIB subclasses the class, so final classes and methods cannot be proxied.
  • How do you fix self-invocation? Move the method to another bean, inject the proxy (self-injection), or use AspectJ weaving.
