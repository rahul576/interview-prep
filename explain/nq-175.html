Why do you use Spring Boot, and what does it add on top of the Spring Framework?

Spring Boot · concept · levels entry

In one line

Spring Boot is an opinionated layer on Spring Framework that adds auto-configuration, starter dependencies, an embedded server with a runnable jar, externalised configuration and production features (Actuator), so you get a production-ready service quickly while still being able to override every default.

Detailed explanation

Spring Framework gives the core building blocks: the IoC container and dependency injection, Spring MVC and WebFlux, data access, transactions, AOP and more. But a plain Spring application needed a lot of setup: XML or Java configuration for every infrastructure bean, a separately installed servlet container, WAR packaging and manual alignment of dozens of library versions.

Spring Boot removes that work without replacing Spring. Auto-configuration creates sensible beans based on what is on the classpath and in your properties: add a JDBC driver and Spring Data JPA and you get a DataSource, HikariCP pool, EntityManagerFactory and transaction manager. Starters such as spring-boot-starter-web bring a curated set of dependencies whose versions are managed by the Boot BOM, so they are known to work together. An embedded Tomcat, Jetty or Undertow (or Netty for WebFlux) lets you package everything as one executable jar started with java -jar, which fits containers perfectly.

Externalised configuration (application.yml, profiles, environment variables, config trees) means the same artifact runs in every environment. Actuator with Micrometer adds health checks, metrics, info and diagnostics. Boot also provides testing support (@SpringBootTest, test slices), DevTools, Docker Compose and Testcontainers integration, and support for GraalVM native images.

The key idea is convention over configuration with escape hatches: every auto-configured bean backs off when you define your own.

How it works

  1. Spring Initializr generates a project with the Boot parent/BOM and chosen starters.
  2. @SpringBootApplication enables component scanning, configuration and auto-configuration.
  3. SpringApplication.run creates the context, loads properties and evaluates auto-configuration conditions.
  4. The embedded server starts on server.port.
  5. Actuator endpoints expose health and metrics for operations.

Example

@SpringBootApplication
public class CatalogueApplication {
    public static void main(String[] args) {
        SpringApplication.run(CatalogueApplication.class, args);
    }
}
./mvnw package
java -jar target/catalogue-1.0.jar --spring.profiles.active=prod --debug

Common mistakes

  • Saying Spring Boot replaces Spring Framework; it builds on it.
  • Treating auto-configuration as magic and never checking the conditions report.
  • Overriding managed dependency versions without need, causing conflicts.
  • Exposing all Actuator endpoints publicly.

How to answer in the interview

"Spring Framework gives DI, MVC, data access and transactions, but on its own you configure a lot. Spring Boot sits on top and removes that work. Auto-configuration creates beans based on the classpath and properties, starters bring compatible dependency sets, the embedded server lets me run the service as a single jar, externalised configuration and profiles suit containers, and Actuator gives health and metrics. So I get to a production-ready service much faster, and I can still override any default by defining my own bean or property."

Likely follow-up questions

  • How do you see which auto-configurations applied? Run with --debug or use the Actuator conditions endpoint.
  • How do you disable one? @SpringBootApplication(exclude = ...) or spring.autoconfigure.exclude.
  • Can Boot build a WAR? Yes, extend SpringBootServletInitializer and mark the server dependency as provided.
