How do you make a Java microservice observable in production?

Observability · concept · levels senior, lead

In one line

Make a service observable with the three signals: structured logs carrying a trace id, metrics via Micrometer exported to Prometheus, and distributed traces with OpenTelemetry, plus Actuator health probes, and SLO-based dashboards and alerts on top.

Detailed explanation

Observability means you can answer new questions about production behaviour without shipping new code. For a Java microservice that rests on three signals that must be correlated.

Logs: JSON, one event per line, with consistent fields (timestamp, level, service, version, trace id, span id, business keys like orderId). Spring Boot 3.4+ has built-in structured logging (logging.structured.format.console=ecs or logstash); Micrometer Tracing puts the trace id in the MDC automatically. Logs are shipped to ELK, Loki or a vendor.

Metrics: Micrometer is the facade; Actuator exposes /actuator/prometheus. Track RED per endpoint (rate, errors, duration as histograms for p95/p99), JVM (heap after GC, GC pauses, threads), resource pools (Hikari, executors), dependencies and Kafka consumer lag, plus business metrics like orders placed. Watch cardinality: never use user ids as tags.

Traces: OpenTelemetry (Java agent or Micrometer Tracing with the OTel bridge) creates spans for HTTP, JDBC and Kafka and propagates context via the W3C traceparent header, exported via OTLP to a Collector and on to Jaeger, Tempo or an APM. Sampling keeps cost under control.

Health: Actuator liveness and readiness groups back Kubernetes probes; readiness reflects whether the instance can serve, liveness only whether it is stuck.

Finally, define SLOs (for example 99.9% of requests under 300 ms) and alert on symptoms with burn-rate alerts, while causes like CPU go on dashboards.

How it works

  1. Add Actuator, Micrometer Prometheus registry and Micrometer Tracing / OTel.
  2. Configure JSON logging with trace and span ids.
  3. Instrument custom business metrics and spans for key steps.
  4. Export to Prometheus, an OTel Collector and a log store.
  5. Build Grafana dashboards per service (RED, JVM, dependencies).
  6. Define SLOs and burn-rate alerts with runbooks.

Example

management:
  endpoints.web.exposure.include: health,info,prometheus
  endpoint.health.probes.enabled: true
  metrics.distribution.percentiles-histogram.http.server.requests: true
  tracing.sampling.probability: 0.1
  otlp.tracing.endpoint: http://otel-collector:4318/v1/traces
logging:
  structured.format.console: ecs
Counter.builder("orders.placed").tag("channel", "web").register(registry).increment();

Common mistakes

  • Logs without trace ids, so signals cannot be correlated.
  • High-cardinality metric tags (user id, full URL) exploding storage.
  • Liveness probes that check the database, causing restart storms.
  • Alerting on every CPU spike instead of user-facing symptoms.

How to answer in the interview

"I cover logs, metrics and traces and make sure they're correlated. Logs are structured JSON with the trace id from the MDC, shipped centrally. Metrics come from Micrometer through Actuator to Prometheus: request rate, errors and latency percentiles, JVM and pool metrics, Kafka lag and business metrics, keeping tag cardinality low. Tracing uses OpenTelemetry, propagating context over HTTP and Kafka and exporting through a Collector to Tempo or Jaeger. Actuator liveness and readiness back the Kubernetes probes. On top I define SLOs and alert on symptoms like error rate and latency burn rate, keeping causes on dashboards."

Likely follow-up questions

  • What would you alert on? SLO burn rate for errors and latency, saturation that predicts outages; everything else goes on dashboards.
  • How do you connect a metric spike to a trace? Exemplars attach trace ids to histogram buckets.
  • Liveness vs readiness? Readiness removes the pod from traffic; liveness restarts it, so it must not depend on external systems.
