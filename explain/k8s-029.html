How do you manage secrets in Kubernetes beyond plain Secret objects?

Kubernetes · concept · levels mid, senior, lead

In one line

Kubernetes Secrets are only base64-encoded, so enable encryption at rest with a KMS provider, lock down RBAC, keep the source of truth in a vault (Vault, AWS Secrets Manager, Azure Key Vault) synced by the External Secrets Operator or mounted by the Secrets Store CSI driver, use Sealed Secrets or SOPS for GitOps, and design for rotation.

Detailed explanation

A Secret object is stored in etcd and readable by anyone with get on Secrets in that namespace; base64 is an encoding, not encryption. Hardening happens in layers.

Cluster level:

  • Encryption at rest: an EncryptionConfiguration with a KMS v2 provider, so etcd stores ciphertext; managed services offer customer-managed keys.
  • RBAC: few subjects get get/list on Secrets (list reveals contents), and anyone who can create pods can mount the namespace's Secrets.

Source of truth outside the cluster: a dedicated secrets manager provides access policies, versioning, audit and rotation.

  • External Secrets Operator (ESO): an ExternalSecret maps vault entries to a Kubernetes Secret and refreshes it on an interval, so rotated values flow in. Apps consume normal Secrets.
  • Secrets Store CSI Driver with a provider (Vault, AWS, Azure, GCP): mounts secrets as files at pod start directly from the provider, optionally syncing to a Secret object if needed; it can avoid storing them in etcd at all.
  • Vault Agent or Vault's Secrets Operator for dynamic secrets such as short-lived database credentials.

GitOps: never commit plain Secrets. Sealed Secrets encrypts with a cluster key so only the controller can decrypt; SOPS encrypts values with KMS or age keys, decrypted by Flux or Argo CD plugins. Many teams prefer committing only ExternalSecret references.

Consumption: prefer mounted files over env vars: env vars leak into crash dumps, debug endpoints and child processes, and don't update. Apps should re-read files or be restarted on rotation.

How it works

  1. Secret stored in a vault with access policy.
  2. Pod's service account authenticates to the vault via workload identity.
  3. ESO syncs it into a Secret, or the CSI driver mounts it.
  4. etcd copy, if any, is KMS-encrypted.
  5. Rotation in the vault → refreshed Secret → app reloads or restarts.

Example

apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata: { name: db-credentials, namespace: shop }
spec:
  refreshInterval: 1h
  secretStoreRef: { kind: ClusterSecretStore, name: aws-secrets-manager }
  target: { name: db-credentials }
  data:
  - secretKey: password
    remoteRef: { key: prod/shop/db, property: password }

Common mistakes

  • Believing base64 is protection.
  • Plain Secrets in Git, even private repos.
  • Broad list secrets permissions for CI or monitoring tools.
  • Rotation that requires a code change or manual redeploy everywhere.

How to answer in the interview

"A Secret is only base64-encoded, so first I enable encryption at rest with a KMS provider and restrict RBAC, remembering that anyone who can create pods in a namespace can read its secrets. The source of truth lives in a vault such as HashiCorp Vault, AWS Secrets Manager or Azure Key Vault. External Secrets Operator syncs values into Kubernetes Secrets and refreshes them on rotation, or the Secrets Store CSI driver mounts them as files directly from the provider. For GitOps I use Sealed Secrets or SOPS, and I prefer files over env vars because env vars leak into logs and dumps."

Likely follow-up questions

  • How does a pod authenticate to the vault without a stored credential? Its projected service account token via workload identity or Vault's Kubernetes auth.
  • ESO or CSI driver? ESO for normal Secret consumption; CSI to avoid etcd copies and fetch at pod start.
  • How do you rotate without downtime? Support two valid credentials during overlap, then retire the old one.
