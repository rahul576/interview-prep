What must you consider when designing an active-active multi-region application on AWS?

Cloud (AWS) · design · levels senior

In one line

Active-active multi-region needs global routing (Route 53 latency/failover or Global Accelerator), a data replication and conflict strategy (DynamoDB global tables, home-region partitioning, Aurora Global with one writer), stateless, independent regions, idempotency and eventual consistency, region-by-region deployments and a budget for roughly double the infrastructure.

Detailed explanation

Routing: Route 53 latency-based records with health checks send users to the nearest healthy region, but failover depends on DNS caching. AWS Global Accelerator gives two static anycast IPs, routes over the AWS backbone, and shifts traffic within seconds when endpoint health fails. CloudFront in front adds origin failover for cacheable content. Route 53 Application Recovery Controller adds controlled, manual-override switching.

Data is the hard part. If both regions accept writes to the same items, you need conflict resolution. DynamoDB global tables replicate asynchronously with last-writer-wins, and now also offer multi-region strong consistency for some setups at higher latency. Alternatively, give each user or tenant a home region (cell or partition-based routing), so writes for one entity happen in one place and other regions serve reads or take over on failure. Aurora Global Database has one writer region (with write forwarding from secondaries), so it is active-active for reads but failover for writes. Aurora DSQL offers active-active distributed SQL. S3 cross-region replication, ElastiCache Global Datastore and Secrets Manager replication cover other state.

Independence: each region must run on its own, with its own copies of dependencies, queues and caches, and no synchronous cross-region calls on the request path, because that couples their availability and adds latency. Sessions must be stateless (tokens) or replicated.

Operations: design for idempotent writes (requests may be retried in another region), accept and surface eventual consistency, deploy one region at a time with bake time, keep identical IaC, run game days that fail a whole region, and watch quotas. Cost roughly doubles, plus cross-region data transfer.

How it works

  1. Users resolve to the nearest region through Global Accelerator or Route 53.
  2. Each region serves reads and writes from local data stores.
  3. Data replicates asynchronously to the other region.
  4. Conflicts resolve via last-writer-wins or home-region ownership.
  5. On regional failure, health checks remove it and the other region absorbs traffic.

Example

aws dynamodb update-table --table-name carts \
  --replica-updates '[{"Create":{"RegionName":"us-east-1"}}]'

aws globalaccelerator create-endpoint-group --listener-arn $LISTENER \
  --endpoint-group-region eu-west-1 \
  --endpoint-configurations EndpointId=$ALB_EU,Weight=100 \
  --health-check-path /health --traffic-dial-percentage 100

Common mistakes

  • Synchronous calls to the other region on the hot path.
  • Ignoring write conflicts until customers see lost updates.
  • Deploying to both regions simultaneously, so one bug takes down both.
  • Never testing full region evacuation under load and capacity limits.

How to answer in the interview

"First, routing: Route 53 latency-based records with health checks or Global Accelerator with anycast IPs and fast failover. The hard part is data: if both regions write, I need conflict handling, like DynamoDB global tables with last-writer-wins, or a home region per user or tenant, because Aurora Global Database has a single writer region. Each region must be stateless and fully independent, with no synchronous cross-region calls. Writes must be idempotent and the product must tolerate eventual consistency. I deploy one region at a time, run regular region-failure game days and budget for roughly double the infrastructure."

Likely follow-up questions

  • How avoid a deployment bug taking down both regions? Sequential regional deployments with bake time, alarms and automatic rollback.
  • Why Global Accelerator over DNS? Static IPs and failover in seconds without depending on DNS caching.
  • What is a cell-based architecture? Independent copies of the stack, each serving a subset of customers, limiting blast radius.
