What is semantic caching for LLM applications, and what are its risks?

LLMOps & RAG · concept · levels mid, senior

In one line

A semantic cache stores answers keyed by the embedding of the question, so semantically similar questions reuse a previous answer, saving cost and latency; the risks are wrong matches from a loose similarity threshold, cross-user leakage of personalised answers, and stale answers without invalidation, so it fits frequent, generic questions.

Detailed explanation

An exact-match cache rarely hits for natural language: "How do I reset my password?" and "password reset steps" are different strings. A semantic cache embeds the incoming question, searches a small vector index of previous questions, and if the nearest neighbour's similarity exceeds a threshold, returns its stored answer in milliseconds without calling the LLM. Gateways such as Azure API Management (semantic caching policies) and LLM proxies or libraries (for example LiteLLM, GPTCache-style tools, Redis-based caches) offer this.

The risks are serious:

  • False hits. Embeddings capture topic more than detail. "Refund policy for Germany" and "refund policy for France" can be very similar vectors but need different answers. Negations, numbers, dates and product names are typical traps. The threshold must be tuned on real pairs, and it is safer to include extracted entities (country, product) in the cache key.
  • Personalisation and permissions. Answers that depend on user identity, permissions, account data or conversation history must never be served to another user. Scope cache keys by tenant, user or permission set, or bypass the cache for such requests.
  • Staleness. When underlying documents change, cached answers are wrong. Use TTLs and invalidate entries that cite changed documents.
  • Context. A follow-up like "and what about the premium plan?" means nothing alone; cache only standalone, rewritten questions or first turns.

How it works

  1. Normalise and (if needed) rewrite the question to standalone form.
  2. Decide if the request is cacheable (generic, no personal data, no tools).
  3. Embed; search the cache within the right scope.
  4. Similarity above threshold and entities match -> return cached answer.
  5. Otherwise call the LLM; store question, embedding, answer, cited doc IDs, TTL.
  6. Invalidate on document change; monitor hit rate and wrong-hit rate.

Example

def answer(q, user):
    if is_cacheable(q):
        key_scope = f"tenant:{user.tenant}"
        hit = cache.nearest(embed(q), scope=key_scope)
        if hit and hit.score >= 0.93 and hit.entities == extract_entities(q):
            return hit.answer
    resp = rag_answer(q, user)
    if is_cacheable(q):
        cache.put(q, embed(q), resp.text, docs=resp.cited_doc_ids, ttl=86400, scope=key_scope)
    return resp.text

Common mistakes

  • One global cache for personalised answers.
  • Picking a threshold without measuring false hits.
  • No invalidation when source documents change.
  • Caching multi-turn questions without rewriting them.

How to answer in the interview

"A semantic cache keys answers by the meaning of the question rather than the exact text, using embeddings, so 'how do I reset my password' and 'password reset steps' share one answer. That saves model calls and returns in milliseconds. The risks are significant: a loose threshold returns the wrong answer for subtly different questions, like Germany versus France; personalised or permission-dependent answers must never be shared, so I scope keys by user or tenant or bypass the cache; and entries must be invalidated when the source documents change. I use it for frequent, generic questions and measure wrong-hit rate."

Likely follow-up questions

  • Measuring wrong answers? Sample cache hits for judge or human review; compare cached vs fresh answers.
  • Typical hit rate? Highly workload-dependent; FAQ-style traffic benefits most.
  • Versus prompt caching? Prompt caching reuses computation for a shared prefix but still generates a fresh answer.
