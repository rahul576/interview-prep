How do NetworkPolicies work in Kubernetes?

Kubernetes · concept · levels mid, senior

In one line

By default all pods can reach all pods; a NetworkPolicy selects pods with a podSelector and allows specific ingress and egress by pod labels, namespaces, IP blocks and ports, and once a pod is selected everything else in that direction is denied. Start with default deny, add explicit allows, remember DNS egress, and use a CNI that enforces policies.

Detailed explanation

Kubernetes networking is flat: any pod can reach any other pod, so a compromised pod can attack everything. NetworkPolicies are the built-in way to segment traffic at L3/L4.

The semantics are additive allow-lists. A policy has a podSelector choosing the pods it applies to and policyTypes (Ingress, Egress). If no policy selects a pod, all traffic is allowed. As soon as at least one policy selects a pod for a direction, only traffic matching some rule in some policy is allowed; there are no deny rules in the core API, and policies are unioned. Rules match peers by podSelector, namespaceSelector (often on the automatic kubernetes.io/metadata.name label), combinations of both, or ipBlock CIDRs, plus ports and protocols.

A subtle point is the difference between one from entry containing both namespaceSelector and podSelector (AND: these pods in those namespaces) and two separate entries (OR). Another is that policies are stateful: allowing ingress automatically allows the reply traffic. And the API only stores intent: enforcement is done by the CNI plugin. Calico and Cilium enforce policies; plain Flannel does not, so policies are silently ignored. Calico and Cilium also offer extended policies (cluster-wide, explicit deny, FQDN or L7 rules), and the upstream AdminNetworkPolicy work aims to standardise cluster-wide admin rules.

How it works

  1. Apply a default-deny policy (ingress and egress) in each namespace.
  2. Allow DNS egress to kube-dns on UDP/TCP 53.
  3. Allow ingress to each service only from its known callers and the ingress controller.
  4. Allow egress to required databases, other services or external CIDRs.
  5. Verify with test pods and CNI flow logs (for example Cilium Hubble).

Example

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny, namespace: shop }
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-dns, namespace: shop }
spec:
  podSelector: {}
  policyTypes: [Egress]
  egress:
  - to:
    - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: kube-system } }
      podSelector: { matchLabels: { k8s-app: kube-dns } }
    ports: [ { protocol: UDP, port: 53 }, { protocol: TCP, port: 53 } ]

Common mistakes

  • Default deny egress without allowing DNS, so everything fails with resolution errors.
  • Writing policies on a CNI that does not enforce them.
  • Confusing AND and OR selectors in from entries.
  • Forgetting the ingress controller or monitoring scrapers as sources.

How to answer in the interview

"By default every pod can talk to every other pod. A NetworkPolicy selects pods and lists allowed ingress and egress by pod labels, namespaces, CIDRs and ports, and once a pod is selected, anything not allowed in that direction is denied. Policies are additive allow-lists. I start each namespace with default deny, then allow DNS to port 53, traffic from the ingress controller, and the specific service-to-service flows. They only work if the CNI enforces them, like Calico or Cilium, and I test them with probe pods and flow logs."

Likely follow-up questions

  • How do you test them? Run curl or netcat pods in source namespaces in CI, and inspect Hubble or Calico flow logs for drops.
  • Can you allow egress by domain name? Not in the core API; Cilium and Calico support FQDN policies.
  • Do policies affect host-network pods? Generally not reliably; they are not normal pod traffic.
