What extra risks appear when one remote MCP server serves many tenants, and how do you isolate them?

MCP Servers · concept · levels senior, lead

In one line

In a multi-tenant remote server the main risk is cross-tenant data leakage; derive tenant identity from the validated token, never arguments, enforce row-level or per-tenant data isolation, include the tenant in cache keys and mark results with a private cacheScope, scope handles, resource URIs and tasks to the tenant, and apply per-tenant rate limits.

Detailed explanation

A SaaS vendor running one MCP server for all its customers faces the classic multi-tenancy problems, with some MCP-specific twists.

Identity. The tenant must come from the validated access token (an issuer, audience and tenant claim), never from a tenant_id tool argument. The model fills arguments, and a prompt injection or a curious user could change them.

Data access. Every downstream query must be filtered by tenant. Application-level WHERE tenant_id = ? is necessary but fragile; one forgotten filter leaks data. Stronger options are row-level security in the database bound to the session's tenant, or separate databases or schemas per tenant for high-sensitivity customers.

Caching is a classic leak. Tool lists may differ per tenant (feature flags, plans), and resource reads and query results are tenant-specific. Cache keys must include the tenant (and user, where permissions differ). Newer protocol revisions add caching hints such as cacheScope, which lets the server mark results as private to a user or tenant rather than shareable, so intermediaries and clients do not reuse them across principals.

Handles and identifiers. Resource URIs, opaque handles, task IDs and pagination cursors must be unguessable and validated against the tenant on every use, so tenant B cannot access tenant A's task by guessing an ID.

Noisy neighbours. Per-tenant rate limits and quotas stop one customer's runaway agent from degrading everyone. Logs and traces carry tenant IDs for audit and incident response.

How it works

  1. Request arrives; gateway or server validates token, extracts tenant_id and user_id.
  2. A request context carries the tenant; tool arguments cannot override it.
  3. Database session sets the tenant for row-level security.
  4. Cache lookups use tenant:user:key and results are marked private.
  5. Handles are signed or stored with the owning tenant and checked on access.
  6. Rate limiter keys on tenant; logs include tenant.

Example

ALTER TABLE tickets ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON tickets
  USING (tenant_id = current_setting('app.tenant_id')::uuid);
async def search_tickets(args, ctx):
    async with db.session() as s:
        await s.execute("SET LOCAL app.tenant_id = :t", {"t": ctx.token.tenant_id})
        key = f"{ctx.token.tenant_id}:{ctx.token.user_id}:tickets:{hash_args(args)}"
        return await cache.get_or_load(key, lambda: s.search(args["query"]))

Common mistakes

  • tenant_id as a tool parameter.
  • Global caches keyed only by query text.
  • Sequential task or handle IDs.
  • Shared rate limits, so one tenant can exhaust capacity.

How to answer in the interview

"In a multi-tenant server the main risk is data leaking between tenants. Tenant identity must come from the validated token, never from tool arguments the model or an attacker could manipulate. Every downstream query is filtered by tenant, ideally enforced by row-level security or separate databases rather than only application code. Caches are a classic leak, so cache keys include the tenant, and the cacheScope hint marks tenant- or user-specific results as private. Handles, resource URIs and tasks are scoped and validated so nobody can access another tenant's by guessing. Per-tenant rate limits stop noisy neighbours, and logs carry tenant IDs for audit."

Likely follow-up questions

  • Test for leaks? Automated tests with two tenants trying each other's IDs, plus penetration testing.
  • Separate DB per tenant? For regulated or large customers; costlier but strongest isolation.
  • Tool list per tenant? Yes, it can differ, so cache it per tenant too.
