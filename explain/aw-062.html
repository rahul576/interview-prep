How do you publish custom metrics to CloudWatch?

Cloud (AWS) · concept · levels mid

In one line

Publish custom metrics with the CloudWatch agent (memory, disk, StatsD/collectd, Prometheus), the PutMetricData API, or the Embedded Metric Format in structured logs, organised by namespace and dimensions, while avoiding high-cardinality dimensions because each unique combination is a billed metric.

Detailed explanation

EC2's default metrics come from the hypervisor: CPU, network, disk operations on instance store, and status checks. Memory and filesystem usage are inside the guest OS, so you install the CloudWatch agent, configured via a JSON file (often stored in Parameter Store), which collects OS metrics, log files, StatsD and collectd metrics, and can scrape Prometheus endpoints for containers.

Applications can call PutMetricData directly, batching up to 1,000 values per call, with standard resolution (one minute) or high resolution (one second). It is synchronous and costs per API call, so in high-volume code it is better to aggregate locally.

The Embedded Metric Format (EMF) is ideal for Lambda and containers: the code writes a JSON log line with a _aws metadata block naming metrics, units and dimensions, and CloudWatch Logs extracts metrics asynchronously. You get metrics plus the full log event for context, with no extra API calls or latency. Powertools for AWS Lambda implements EMF in a few lines.

A metric is identified by namespace, name and dimensions (up to 30). Each unique combination of dimension values is a separate metric billed monthly, so dimensions like Service, Environment and Operation are fine but user id, request id or IP explode the count and cost. Put such values in log fields and query them with Logs Insights instead. Custom metrics support alarms, anomaly detection, metric math, dashboards, and target tracking auto scaling just like built-in metrics.

How it works

  1. Decide what to measure: business and golden signals.
  2. Choose transport: agent, PutMetricData, or EMF logs.
  3. Define a namespace and a few low-cardinality dimensions.
  4. CloudWatch stores data points and aggregates statistics and percentiles.
  5. Build alarms, dashboards and scaling policies on the metric.

Example

from aws_lambda_powertools import Metrics
from aws_lambda_powertools.metrics import MetricUnit

metrics = Metrics(namespace="Shop", service="checkout")

@metrics.log_metrics
def handler(event, context):
    metrics.add_dimension(name="Environment", value="prod")
    metrics.add_metric(name="OrdersPlaced", unit=MetricUnit.Count, value=1)
    metrics.add_metadata(key="orderId", value=event["orderId"])  # log only, not a dimension

Common mistakes

  • Using request or user IDs as dimensions and getting a huge bill.
  • Calling PutMetricData once per request in hot code paths.
  • Expecting memory metrics on EC2 without the agent.
  • Alarming on averages instead of percentiles for latency.

How to answer in the interview

"EC2 does not report memory or disk usage by default, so I install the CloudWatch agent, which also collects logs and StatsD or Prometheus metrics. Code can call PutMetricData, but in Lambda and containers I prefer the Embedded Metric Format: I write structured JSON logs and CloudWatch extracts the metrics asynchronously, with no extra calls. Metrics live in a namespace with dimensions; every unique combination is a billed metric, so I avoid high-cardinality dimensions like user ID. Then they drive alarms, dashboards and auto scaling."

Likely follow-up questions

  • Why is a request ID as a dimension a bad idea? Every request creates a new metric that is billed and useless for aggregation.
  • When use high-resolution metrics? For fast auto scaling or alarms needing sub-minute reaction.
  • How alert on p99 latency? Publish raw values or use EMF and alarm on the p99 statistic.
