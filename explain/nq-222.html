What are RestTemplate and WebClient, and when would you use each?

Microservices · concept · levels mid

In one line

RestTemplate is Spring's classic synchronous, blocking HTTP client, now in maintenance mode; WebClient is the non-blocking, reactive client from WebFlux; for new blocking code use RestClient (Spring 6.1+) or HTTP interfaces, and always configure timeouts and connection pools.

Detailed explanation

RestTemplate has existed since Spring 3. Each call such as getForObject blocks the calling thread until the response arrives. In a servlet application with thread-per-request this is simple and perfectly adequate. However, its API is template-method style with many overloads, and it has been in maintenance mode for years: no new features, only fixes. The Spring team has announced its eventual deprecation, so it should not be used for new code.

WebClient arrived with Spring WebFlux (Spring 5). It is non-blocking: calls return Mono or Flux, and I/O is handled by an event loop (Reactor Netty by default), so a few threads can handle thousands of concurrent requests. It has a fluent API, supports streaming and backpressure, and makes parallel fan-out easy (Mono.zip of several calls). It is the natural choice in reactive applications. You can call .block() in a servlet app, but then you pay for the reactive dependency without its benefits, and you must never block inside a reactive pipeline.

RestClient, introduced in Spring Framework 6.1 (Spring Boot 3.2), is the modern synchronous client: the fluent API of WebClient, built on blocking HTTP libraries (JDK HttpClient, Apache HttpClient, Jetty), without reactive types. With virtual threads (Java 21+, spring.threads.virtual.enabled=true), blocking calls become cheap, so RestClient covers most needs of servlet applications. HTTP interfaces (@HttpExchange) give declarative, Feign-like clients on top of RestClient or WebClient; OpenFeign remains common in Spring Cloud projects.

Whichever client you use: set connect and read/response timeouts (defaults can be infinite or very long), configure connection pooling, build clients from Spring Boot's auto-configured builders so observability and tracing work, and wrap calls with resilience policies.

How it works

  1. Inject the auto-configured RestClient.Builder or WebClient.Builder.
  2. Configure base URL, timeouts, default headers.
  3. Build the request fluently; execute.
  4. RestClient returns the body; WebClient returns Mono/Flux subscribed by the framework.
  5. Errors map to exceptions or reactive error signals.

Example

// RestClient: synchronous, modern
@Bean
RestClient catalogClient(RestClient.Builder b) {
    var settings = ClientHttpRequestFactorySettings.defaults()
            .withConnectTimeout(Duration.ofSeconds(1))
            .withReadTimeout(Duration.ofSeconds(2));
    return b.baseUrl("http://catalog")
            .requestFactory(ClientHttpRequestFactoryBuilder.detect().build(settings))
            .build();
}
Product p = catalogClient.get().uri("/products/{id}", id).retrieve().body(Product.class);

// WebClient: non-blocking fan-out
Mono<Product> product = webClient.get().uri("/products/{id}", id).retrieve().bodyToMono(Product.class);
Mono<Stock> stock = webClient.get().uri("/stock/{id}", id).retrieve().bodyToMono(Stock.class);
Mono<ProductPage> page = Mono.zip(product, stock, ProductPage::new)
        .timeout(Duration.ofSeconds(2));

(Exact timeout configuration classes differ between Spring Boot versions; check your version's docs.)

Common mistakes

  • No timeouts, so a hanging downstream exhausts threads.
  • Calling .block() inside a reactive pipeline.
  • Creating clients with new instead of the builders, losing tracing and metrics.
  • Pulling in WebFlux just to call one API from a blocking app.

How to answer in the interview

"RestTemplate is the classic synchronous client: each call blocks the thread until the response arrives. It works, but it is in maintenance mode. WebClient, from WebFlux, is non-blocking and reactive with a fluent API returning Mono or Flux, so it handles many concurrent calls on few threads and suits reactive apps or fan-out to several services. For new blocking code I use RestClient from Spring 6.1, often with HTTP interfaces, and with virtual threads blocking is cheap anyway. Whatever the client, I build it from the Spring Boot builder and always configure connect and read timeouts and connection pooling."

Likely follow-up questions

  • What if you forget timeouts? A slow or hung dependency holds threads indefinitely and can bring your service down.
  • Do virtual threads make WebClient unnecessary? For many servlet apps yes; reactive still helps for streaming and backpressure.
  • What is an HTTP interface? A Java interface annotated with @HttpExchange that Spring turns into a client proxy.
