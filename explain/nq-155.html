When would you use these design patterns in a project?

Design Patterns · scenario · levels mid, senior

In one line

Use a pattern when a real, recurring problem shows up, not speculatively: Strategy for runtime-selected rules, Factory for choosing implementations, Builder for complex objects, Adapter for vendors, Observer for side effects, Template Method for fixed workflows and Chain of Responsibility for pipelines, remembering that Spring already provides many.

Detailed explanation

Interviewers ask this to see judgement, not memorisation. The good answer links each pattern to a symptom in the code and admits the cost.

Symptoms and patterns from typical backend projects:

  • Growing if/else on a type (payment method, tax rule, shipping carrier) → Strategy, with Spring beans in a map. New variants are new classes.
  • Callers needing the right implementation without knowing classes → Factory or a bean registry.
  • Constructors with many optional parameters, or verbose test setup → Builder (production DTOs, request objects, test-data builders).
  • Third-party SDKs leaking into business code → Adapter behind your own interface, making vendors swappable and mockable.
  • Main transaction doing emails, analytics and notifications → Observer with Spring events (@TransactionalEventListener) or Kafka, decoupling side effects.
  • Several jobs with identical steps but different parsing → Template Method, or a composition-based variant.
  • Sequential checks that change often → Chain of Responsibility (validation, fraud, approval).
  • Order lifecycle with many status rules → State.

Already built in: Spring gives you singleton beans, Proxy (transactions, caching, security), Template classes (JdbcTemplate, RestTemplate, TransactionTemplate), Observer (events), Factory (BeanFactory, @Bean). Knowing this stops you re-implementing them.

When not to: a pattern adds classes and indirection. Follow YAGNI and the "rule of three": write the straightforward code first, and refactor toward a pattern when the second or third variation appears and the pain is real. Modern Java (lambdas, records, sealed types) often gives a lighter form.

How it works

  1. Notice a pain point: duplication, growing conditionals, coupling, hard tests.
  2. Name the forces: what varies, what stays fixed.
  3. Pick the pattern whose intent matches, checking if the framework offers it.
  4. Refactor in small steps, covered by tests.
  5. Review whether the added indirection actually paid off.

Example

A STAR-style project example:

  • Situation: our checkout service had a 300-line switch on payment method, and adding PhonePe took a week with regressions in card payments.
  • Task: make adding payment methods safe and fast.
  • Action: extracted a PaymentStrategy interface, one bean per method, an EnumMap lookup in the context, and an Adapter per gateway SDK. Side effects (receipt email, loyalty points) moved to events after commit.
  • Result: the next method (wallet) shipped in two days, each strategy had its own tests, and payment-related incidents dropped noticeably.
@Component class WalletPayment implements PaymentStrategy {
    public PaymentMethod method() { return PaymentMethod.WALLET; }
    public PaymentResult pay(Order o) { return walletGateway.debit(o.customerId(), o.total()); }
}

Common mistakes

  • Listing pattern definitions without real project contexts.
  • Introducing patterns "for the future" with one implementation.
  • Re-implementing what Spring already provides.
  • Ignoring the cost in readability and onboarding.

How to answer in the interview

"I use a pattern when a real, recurring problem appears, not speculatively. In projects I've used Strategy for payment and pricing rules chosen at runtime; a factory or bean map to pick the right notification sender; Builder for complex requests and test data; Adapter to wrap vendors behind our own interface so they're swappable and mockable; Observer through Spring events or Kafka to move emails out of the main transaction; Template Method for import jobs; and Chain of Responsibility for validation pipelines. Many come free with Spring, like proxies and JdbcTemplate. Usually I refactor toward a pattern once the second or third variation shows up."

Likely follow-up questions

  • A time a pattern made code worse? An abstract factory hierarchy for a single implementation that just added layers; we removed it.
  • How do you decide between Strategy and a simple if? Two stable branches: an if; many or growing variants: Strategy.
  • Which patterns do you avoid? Hand-written Singletons, since DI handles shared instances better.
