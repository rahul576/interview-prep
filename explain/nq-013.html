What are scoped values in Java?

Modern Java (11-21) · concept · levels senior, lead

In one line

Scoped values (java.lang.ScopedValue, preview in Java 21, final in Java 25) share an immutable value with all code called within a bounded scope, without parameters; they are a safer, cheaper alternative to ThreadLocal, especially with virtual threads and structured concurrency.

Detailed explanation

Applications often need "ambient" context, such as the current user, tenant or request id, deep in the call stack. Traditionally this is a ThreadLocal, but ThreadLocal has problems: values are mutable (any code can set them), they live as long as the thread unless someone calls remove(), causing leaks in thread pools, and InheritableThreadLocal copies values into every child thread, which is expensive with millions of virtual threads.

A ScopedValue binds a value for the dynamic extent of a method call:

  1. Declare static final ScopedValue<User> USER = ScopedValue.newInstance();
  2. Bind and run: ScopedValue.where(USER, user).run(() -> handle()); (or call to return a value).
  3. Anywhere inside handle(), read USER.get(); outside, USER.isBound() is false.

Properties:

  • Immutable for the scope: there is no set; you can only rebind a new value for a nested scope, which ends when that inner call returns.
  • Bounded lifetime: when run returns, the binding is gone, so nothing leaks into the next task on the thread.
  • Cheap inheritance: child tasks forked in a StructuredTaskScope automatically see the parent's bindings without copying.
  • Fast reads, designed for many virtual threads.

History: incubator in Java 20, preview in 21-24, finalised in Java 25 (JEP 506). On Java 21 you need --enable-preview; the API changed slightly across previews (for example orElse no longer accepts null in the final version), so prefer the final API on 25. Structured concurrency itself is still a preview in Java 25.

How it works

  1. A ScopedValue key is declared once, usually static final.
  2. where(key, value).run(op) creates a binding on the current thread.
  3. Code inside op reads it with get().
  4. Forked structured-concurrency subtasks inherit the binding.
  5. Binding disappears when op returns.

Example

public final class RequestContext {
    public static final ScopedValue<String> TENANT = ScopedValue.newInstance();
}

// in a filter / entry point
ScopedValue.where(RequestContext.TENANT, tenantId)
           .run(() -> orderService.process(request));

// deep inside
String tenant = RequestContext.TENANT.get();

// nested rebinding for a sub-call
ScopedValue.where(RequestContext.TENANT, "admin").run(this::auditAsAdmin);

Common mistakes

  • Treating it as a mutable holder.
  • Expecting bindings to be visible in threads started with a plain executor (only structured tasks inherit).
  • Using preview APIs in production without accounting for changes.
  • Calling get() outside a binding (throws NoSuchElementException).

How to answer in the interview

"Scoped values let me share an immutable value, like the current user or tenant, with everything called inside a bounded scope, without passing it through every method. I declare a static final ScopedValue, then ScopedValue.where(USER, user).run(...), and code inside reads USER.get(). Unlike ThreadLocal, the value can't be changed, it disappears when the scope ends so there's no leak, and subtasks forked in a structured task scope inherit it cheaply, which matters with millions of virtual threads. It was a preview in Java 21 and became final in Java 25."

Likely follow-up questions

  • What problems does ThreadLocal cause with virtual threads? Per-thread copies multiply memory, inheritance copying is costly, and forgotten values leak.
  • Can you change a scoped value? Only by rebinding it for a nested scope.
  • Is it available in Java 21 production code? Only with --enable-preview; it's final from Java 25.
