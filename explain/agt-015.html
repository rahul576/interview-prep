How do you implement observability for agents in production?

AI Agents & AIOps · concept · levels mid, senior

In one line

Trace every run end to end, with spans for each model call and tool call, capture inputs, outputs, decisions and token usage, aggregate metrics (success, steps, cost, latency, tool errors, escalations), link traces to user feedback and outcomes, follow OpenTelemetry GenAI conventions, and replay failed runs.

Detailed explanation

Traditional APM tells you an endpoint is slow; with agents you need to know why the agent did what it did. The core is distributed tracing: a root span per agent run, nested spans for every model call (model and version, prompt version, input and output tokens, latency, finish reason) and every tool call (name, arguments, result size, errors, latency). Sub-agents become child spans under the same trace. Where models expose them, reasoning summaries and decision points are captured, so you can reconstruct the trajectory step by step.

OpenTelemetry GenAI semantic conventions define standard attributes such as gen_ai.request.model, gen_ai.usage.input_tokens, and operation names for chat and tool execution, including agent spans. Instrumenting with them lets traces flow both to LLM-focused tools such as Langfuse, LangSmith, Arize Phoenix or cloud offerings, and to your main APM like Datadog, Grafana or Azure Monitor.

Metrics aggregate health: task success rate, steps per task, cost per task, latency distribution, tool error rates, escalation and abandonment rates, guardrail triggers and how often limits are hit. Dashboards should slice by agent version, model, tenant and task type.

Outcome linking closes the loop: thumbs up or down, whether a resolved ticket was reopened, whether a code change was merged or reverted. Those signals are often more meaningful than model metrics.

Because traces contain user data, apply redaction, access control and retention limits. Finally, failed or poorly rated runs can be inspected and replayed in a test environment and turned into evaluation cases.

How it works

  1. Generate a run ID; create the root span with user, tenant and agent version.
  2. Wrap each model and tool call in child spans with GenAI attributes.
  3. Export via OpenTelemetry to an LLM observability tool and APM.
  4. Compute metrics and alerts on success, cost, latency and errors.
  5. Attach feedback and business outcomes to the trace.
  6. Sample failing runs for review; convert them into eval cases.

Example

from opentelemetry import trace
tracer = trace.get_tracer("support-agent")

with tracer.start_as_current_span("invoke_agent support-agent") as run:
    run.set_attribute("gen_ai.operation.name", "invoke_agent")
    run.set_attribute("app.agent.version", "2026.05.2")
    with tracer.start_as_current_span("chat") as span:
        resp = client.messages.create(model=MODEL, messages=msgs, tools=tools)
        span.set_attribute("gen_ai.request.model", MODEL)
        span.set_attribute("gen_ai.usage.input_tokens", resp.usage.input_tokens)
        span.set_attribute("gen_ai.usage.output_tokens", resp.usage.output_tokens)
    with tracer.start_as_current_span("execute_tool find_orders") as span:
        span.set_attribute("gen_ai.tool.name", "find_orders")
        result = find_orders(**args)

Common mistakes

  • Logging only the final answer.
  • Storing full prompts with personal data forever.
  • No link between traces and outcomes.
  • Separate, unlinked traces for sub-agents.
  • Dashboards without version breakdowns, so regressions hide.

How to answer in the interview

"Each run is traced end to end: a root span for the task and nested spans for every model call, with model, prompt version, tokens and latency, and every tool call, with arguments, results and errors, so I can see the full trajectory. Metrics show health: success rate, steps and cost per task, latency, tool errors, escalations and limit hits. Traces are linked to user feedback and business outcomes, like whether a ticket was reopened. I instrument with OpenTelemetry GenAI conventions so data goes to tools like Langfuse or LangSmith and to our APM. Failed runs can be replayed and become evaluation cases, with redaction and retention rules for sensitive data."

Likely follow-up questions

  • Which metric warns first that a new model made things worse? Task success and escalation rate by category, plus steps per task, compared against the previous version.
  • How long do you keep traces? Short retention for full content, longer for redacted metadata and metrics.
  • Sampling? Keep all failures and a sample of successes.
