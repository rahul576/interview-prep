Explain checked versus unchecked exceptions, and how you handle resources safely.

Exceptions · concept · levels entry, mid

In one line

Checked exceptions (subclasses of Exception but not RuntimeException, e.g. IOException) must be caught or declared at compile time; unchecked exceptions (RuntimeException and Error subclasses) are not enforced. Handle resources safely with try-with-resources on AutoCloseable.

Detailed explanation

All throwables extend Throwable, which has two branches: Error (serious JVM problems such as OutOfMemoryError and StackOverflowError that applications normally should not catch) and Exception.

Checked exceptions are Exception subclasses outside RuntimeException: IOException, SQLException, InterruptedException. The compiler enforces handle or declare: either catch them in try/catch or add throws to the method signature. They represent recoverable conditions outside the program's control, such as a missing file or a network failure, where the caller is expected to react.

Unchecked exceptions extend RuntimeException: NullPointerException, IllegalArgumentException, IllegalStateException, IndexOutOfBoundsException. They usually signal programming errors or violated preconditions, and the compiler does not force handling. Modern frameworks (Spring's DataAccessException, JPA exceptions) use unchecked exceptions because checked ones clutter signatures and do not work well with lambdas and streams. Spring's @Transactional by default rolls back on unchecked exceptions and errors, not on checked ones.

Resource safety: files, sockets, JDBC connections and locks must be released even when exceptions occur. try-with-resources (Java 7) declares resources in the try header; anything implementing AutoCloseable is closed automatically in reverse order. If the body throws and close() also throws, the close exception is attached as a suppressed exception (getSuppressed()) rather than hiding the original. Since Java 9 you can use an effectively final variable in the header.

In services: catch exceptions where you can do something meaningful, translate low-level exceptions into domain exceptions (keeping the cause), never swallow them silently, and handle them centrally, for example with @RestControllerAdvice mapping to HTTP responses (Problem Details, RFC 9457).

How it works

  1. A method throws; the JVM unwinds the stack looking for a matching catch.
  2. The compiler has already checked that checked exceptions are caught or declared.
  3. try-with-resources closes resources on every exit path, in reverse order.
  4. Close failures are added as suppressed exceptions.
  5. Unhandled exceptions reach the framework's handler or the thread's uncaught handler.

Example

public List<String> readSkus(Path file) {
    try (BufferedReader in = Files.newBufferedReader(file)) {          // auto-closed
        return in.lines().map(String::trim).toList();
    } catch (NoSuchFileException e) {
        throw new ImportFileMissingException(file, e);                  // domain, unchecked
    } catch (IOException e) {
        throw new UncheckedIOException("Cannot read " + file, e);       // keep the cause
    }
}

@RestControllerAdvice
class ApiErrors {
    @ExceptionHandler(ImportFileMissingException.class)
    ProblemDetail missing(ImportFileMissingException e) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, e.getMessage());
    }
}

Common mistakes

  • Empty catch blocks or just e.printStackTrace().
  • Wrapping without passing the cause.
  • Catching Exception broadly and hiding bugs.
  • Closing resources manually in finally and losing the original exception.
  • Catching InterruptedException without restoring the interrupt flag.

How to answer in the interview

"Checked exceptions, like IOException or SQLException, are verified at compile time: the method must catch them or declare them with throws. Unchecked exceptions extend RuntimeException, like NullPointerException or IllegalArgumentException, and usually indicate programming errors, so the compiler doesn't force handling; Errors like OutOfMemoryError are also unchecked and shouldn't normally be caught. For resources I use try-with-resources, which closes anything AutoCloseable even when an exception occurs, and keeps close failures as suppressed exceptions. In services I translate low-level exceptions into meaningful domain exceptions with the cause, and handle them centrally with a ControllerAdvice."

Likely follow-up questions

  • Should you ever catch Exception or Throwable? Why or why not? Only at top-level boundaries (a request handler, a job runner) to log and respond; elsewhere it hides bugs, and catching Throwable can intercept Errors you cannot recover from.
  • What are suppressed exceptions? Exceptions thrown by close() in try-with-resources, attached to the primary exception instead of replacing it.
  • Does @Transactional roll back on checked exceptions? Not by default; configure rollbackFor if needed.
