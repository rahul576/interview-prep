How do you evaluate and monitor generative AI applications in Foundry?

Azure AI & Foundry · concept · levels mid, senior

In one line

Evaluate generative AI apps with an evaluation dataset, Foundry's built-in evaluators (quality such as groundedness and relevance, RAG, agent and safety metrics), LLM-as-judge and custom evaluators, run in CI on every prompt, retrieval or model change, and monitor production with OpenTelemetry tracing, Application Insights and continuous evaluation.

Detailed explanation

LLM outputs are non-deterministic and there is rarely one correct string, so traditional unit tests are not enough. You need measured quality over a representative set of inputs.

Dataset: start with 50-500 realistic questions or tasks, covering common intents, edge cases, multi-turn conversations, out-of-scope requests and adversarial prompts. For each, store expected answers, reference facts or criteria, and for RAG the context that should be retrieved. Grow it from real production failures.

Built-in evaluators in Foundry and the azure-ai-evaluation SDK:

  • Quality: groundedness (is the answer supported by context), relevance, coherence, fluency, similarity, F1 or BLEU-style metrics when references exist.
  • Retrieval: document retrieval and ranking quality for RAG.
  • Agents: intent resolution, task adherence, tool call accuracy.
  • Risk and safety: hateful, sexual, violent and self-harm content, protected material, indirect attack and jailbreak susceptibility, often combined with the AI red teaming agent for generated attacks.

Most quality metrics are AI-assisted: an LLM acts as a judge with a rubric, returning a score and a reason. You can write custom evaluators as code (regex, JSON schema validity, business rules) or as prompt-based judges.

CI: evaluations run when prompts, chunking, retrieval settings or model versions change. Compare runs side by side in Foundry, set thresholds (for example groundedness average ≥ 4.2, no safety defects) and fail the pipeline on regressions.

Production: tracing sends every request, tool call, token count and latency to Application Insights; continuous evaluation samples live traffic and scores it, so dashboards show quality, safety, latency and cost drift. User feedback (thumbs up/down) is linked to traces.

How it works

  1. Build and version the evaluation dataset.
  2. Choose evaluators and thresholds.
  3. Run the app over the dataset, then evaluate outputs.
  4. Gate releases in CI on the scores.
  5. Trace production and continuously evaluate a sample.
  6. Add failures back into the dataset.

Example

from azure.ai.evaluation import evaluate, GroundednessEvaluator, RelevanceEvaluator
judge = {"azure_endpoint": ENDPOINT, "azure_deployment": "gpt-4.1-judge"}

result = evaluate(
    data="eval/rag_cases.jsonl",          # query, context, response, ground_truth
    evaluators={
        "groundedness": GroundednessEvaluator(model_config=judge),
        "relevance": RelevanceEvaluator(model_config=judge),
    },
    azure_ai_project=PROJECT_ENDPOINT,     # results visible in Foundry
)
assert result["metrics"]["groundedness.groundedness"] >= 4.0, "Groundedness regression"

Common mistakes

  • Testing with five handpicked prompts.
  • Trusting an LLM judge without checking it against human labels.
  • Evaluating only quality, not safety and cost.
  • Never adding production failures to the dataset.

How to answer in the interview

"I start with an evaluation dataset of realistic and adversarial cases with expected answers or criteria. Foundry has built-in evaluators for quality like groundedness and relevance, retrieval metrics, agent metrics like task adherence and tool call accuracy, and safety evaluators. Many use an LLM as judge, and I add custom code evaluators for format or business rules. Evaluations run in CI whenever prompts, retrieval or models change, with thresholds that block regressions. In production, OpenTelemetry tracing goes to Application Insights and continuous evaluation samples live traffic, so we see drift in quality, safety, latency and cost."

Likely follow-up questions

  • How to make the judge reliable? Calibrate against human-labelled samples, use clear rubrics and a strong, pinned judge model.
  • How big should the dataset be? Big enough to cover intents and edge cases; hundreds, growing over time.
  • How to evaluate agents? Score tool selection and arguments per step, not only the final answer.
