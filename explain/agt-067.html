How do AI assistants like K8sGPT or HolmesGPT help troubleshoot Kubernetes, and how would you deploy them safely?

AI Agents & AIOps · concept · levels mid, senior

In one line

K8sGPT scans clusters with analysers and uses an LLM to explain problems and suggest fixes; HolmesGPT investigates alerts by gathering evidence from Kubernetes, metrics and logs; deploy them with read-only RBAC, anonymisation and filtering of data, and approved or self-hosted model backends.

Detailed explanation

Kubernetes failures often show up as cryptic states: CrashLoopBackOff, ImagePullBackOff, pending pods, unbound PersistentVolumeClaims, services without endpoints. Experienced engineers know where to look; others lose time.

K8sGPT (a CNCF sandbox project) runs built-in analysers for common resource types, such as pods, deployments, services, ingresses, PVCs and nodes, detects problems from status and events, and sends a compact description to an LLM that explains the issue and suggests fixes in plain language. It runs as a CLI or as a Kubernetes operator that continuously writes results as custom resources, which can feed dashboards or alerts. It supports multiple backends, including OpenAI-compatible APIs, Azure OpenAI, Amazon Bedrock and local models through Ollama, and an --anonymize option that masks resource names before sending.

HolmesGPT (open source, originally from Robusta) takes an agentic approach: given an alert or a question, it calls tools to fetch pod logs, describe resources, query Prometheus and other sources, and then writes a root cause analysis.

To deploy safely: a dedicated service account with read-only RBAC (get, list, watch), ideally excluding Secrets; minimise data sent to the model by anonymising names and filtering logs for credentials and personal data; choose an approved provider or self-hosted model for sensitive clusters; and treat findings as suggestions that engineers verify.

How it works

  1. Install CLI or operator in the cluster.
  2. Bind a read-only ClusterRole without secrets access.
  3. Configure an approved AI backend and anonymisation.
  4. Analysers or the agent collect state, events, logs and metrics.
  5. LLM explains findings; results posted to CRs, Slack or tickets.
  6. Engineers verify and apply fixes through normal processes.

Example

k8sgpt auth add --backend azureopenai --model gpt-4o --baseurl https://myco.openai.azure.com/
k8sgpt analyze --explain --anonymize --filter=Pod,Service,PersistentVolumeClaim -n payments
kind: ClusterRole
metadata: { name: ai-troubleshooter-readonly }
rules:
  - apiGroups: ["", "apps", "batch", "networking.k8s.io"]
    resources: ["pods", "pods/log", "events", "services", "endpoints",
                "deployments", "replicasets", "jobs", "ingresses", "persistentvolumeclaims", "nodes"]
    verbs: ["get", "list", "watch"]

Common mistakes

  • Running with cluster-admin "to make it work".
  • Including Secrets and ConfigMaps with credentials in what is read.
  • Sending unfiltered logs to a public model.
  • Letting it apply fixes automatically from day one.

How to answer in the interview

"K8sGPT runs analysers over cluster resources and events to find things like CrashLoopBackOff, failing probes, unbound PVCs or services without endpoints, and uses an LLM to explain them and suggest fixes, either as a CLI or an operator. HolmesGPT is more agentic: given an alert, it gathers evidence from Kubernetes, logs and metrics and writes a root cause analysis. I'd deploy them with a read-only service account that can't read secrets, anonymise and filter what goes to the model, use an approved or self-hosted backend, and treat results as suggestions."

Likely follow-up questions

  • Automatic fixes? Only via GitOps PRs or approved low-risk actions.
  • Local models? Possible via Ollama or vLLM, trading some quality for privacy.
  • Operator vs CLI? Operator for continuous scanning; CLI for ad hoc use.
