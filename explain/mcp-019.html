How do version and capability negotiation work in the stateless MCP revision?

MCP Servers · concept · levels mid, senior

In one line

In the stateless revision, every request declares its protocol version and relevant client capabilities in metadata, a discovery method lets clients check support in advance (cacheably), an unsupported-version error lists the versions the server supports, and the client retries with a mutually supported version or falls back to the handshake protocol for legacy servers.

Detailed explanation

Negotiation used to happen once, during initialize, and both sides remembered the result for the connection. Without a handshake, nothing is remembered, so negotiation information must travel with each request. Per the reference material for this question:

Per-request declaration. Each request includes, in its _meta, the protocol version it uses and the client capabilities relevant to that request, for example whether the client can satisfy input-required results through elicitation. The server can process the request completely independently, even if consecutive requests hit different replicas or a serverless function.

Discovery. A client that wants to know what a server supports before doing real work calls the discovery method, which returns the supported protocol versions, server capabilities (tools, resources, prompts, extensions) and server information. Because the answer rarely changes, it can be cached, avoiding a round trip on every conversation.

Version mismatch. If a request names a version the server does not support, the server returns an error listing the versions it does support. The client picks a mutually supported version and retries. If the server turns out to be a legacy server that does not understand the new style at all, the client can fall back to the older handshake-based protocol (initialize), so modern clients still interoperate with existing servers.

Capabilities and extensions. Capabilities still switch optional features on, including an extensions map: a feature such as Tasks or MCP Apps is only used when both sides declare the extension. The rule is unchanged from earlier revisions: use only what the other side supports.

How it works

  1. Client (optionally) calls discovery and caches result with a TTL.
  2. Client chooses the highest version both support.
  3. Every request carries that version and relevant capabilities in _meta.
  4. On an unsupported-version error, client reads the supported list and retries.
  5. If the server only speaks handshake revisions, client performs initialize instead.

Example

Client -> discovery
Server <- { supportedVersions: ["2026-07-28","2025-11-25"],
            capabilities: { tools: {}, extensions: { tasks: {} } } }

Client -> tools/call  _meta.protocolVersion = "2026-07-28"   -> OK

Old client -> tools/call _meta.protocolVersion = "2027-xx"   (unknown)
Server <- error: unsupported protocol version, supported: ["2026-07-28","2025-11-25"]
Client -> retry with "2026-07-28"

Common mistakes

  • Calling discovery before every request instead of caching.
  • Ignoring the supported-versions list and failing hard.
  • Sending capabilities the client does not actually implement.
  • Forgetting a fallback path for handshake-only servers.

How to answer in the interview

"Because there's no handshake, every request carries its protocol version and the client capabilities relevant to it in the metadata, so the server can handle each request independently on any replica. Clients that want to know support in advance call the discovery method, which returns supported versions, capabilities and server info, and they cache it. If a client sends a version the server doesn't support, the server returns an error listing the versions it does support, and the client retries with a mutual one, or falls back to the older initialize handshake for legacy servers. Capabilities, including the extensions map, still decide which optional features both sides use."

Likely follow-up questions

  • How would a 2025-11-25 client talk to a new stateless server? Through the server's support for older versions via initialize, if it keeps that path.
  • Why cache discovery? Saves latency; capabilities change rarely.
  • What if capabilities change? Subscription notifications or cache expiry trigger re-discovery.
