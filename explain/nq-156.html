What is Domain-Driven Design (DDD)?

Design Patterns · concept · levels senior, lead

In one line

Domain-Driven Design (DDD), from Eric Evans' 2003 book, builds software around the business domain with domain experts, using a ubiquitous language, bounded contexts and context maps strategically, and entities, value objects, aggregates, repositories, domain services and domain events tactically.

Detailed explanation

DDD targets systems where business complexity, not technology, is the main difficulty. Its core idea: the code should model the business the way experts think about it, and that model is refined continuously through collaboration.

Strategic design (the big picture):

  • Ubiquitous language: one shared vocabulary used by business people, in conversations, in tests and in code. If experts say "policy lapses", the code has policy.lapse(), not updateStatus(3).
  • Bounded context: a boundary within which a model and its language are consistent. "Customer" in Sales (leads, discounts) differs from "Customer" in Billing (payment terms) and Shipping (addresses). Each context owns its own model rather than one giant shared one.
  • Context map: describes relationships between contexts: customer–supplier, conformist, anticorruption layer (translating a legacy model), shared kernel, published language.
  • Subdomains: core (competitive advantage, invest most), supporting and generic (buy or use off-the-shelf).

Tactical design (inside a context):

  • Entity: identity that persists over time (Order #123).
  • Value object: defined by its values, immutable, no identity (Money, Address); Java records fit well.
  • Aggregate: a cluster of objects treated as one consistency boundary with a single aggregate root (Order with its OrderLines). Outside code references only the root, invariants are enforced inside, and a transaction should modify one aggregate; other aggregates are referenced by id and updated via events (eventual consistency).
  • Repository: collection-like persistence per aggregate root.
  • Domain service: domain logic that does not belong to one entity (pricing across products).
  • Domain event: something that happened (OrderPlaced), used to trigger other aggregates or contexts.

Microservices: bounded contexts are a strong guide for service boundaries, reducing chatty, tightly coupled services. DDD is overkill for simple CRUD apps.

How it works

  1. Work with domain experts (for example in event storming sessions) to discover events, commands and language.
  2. Identify subdomains and draw bounded contexts.
  3. Map relationships between contexts; add anticorruption layers where needed.
  4. Model each context with aggregates, entities and value objects.
  5. Enforce invariants inside aggregates; integrate via domain events.

Example

public record Money(BigDecimal amount, Currency currency) {           // value object
    public Money add(Money o) {
        if (!currency.equals(o.currency)) throw new IllegalArgumentException("Currency mismatch");
        return new Money(amount.add(o.amount), currency);
    }
}

public class Order {                                                    // aggregate root
    private final OrderId id; private final CustomerId customerId;      // other aggregate by id
    private final List<OrderLine> lines = new ArrayList<>();
    private OrderStatus status = OrderStatus.DRAFT;

    public void addLine(ProductId p, int qty, Money price) {
        if (status != OrderStatus.DRAFT) throw new IllegalStateException("Order is not editable");
        lines.add(new OrderLine(p, qty, price));                        // invariant enforced here
    }
    public OrderPlaced place() { status = OrderStatus.PLACED; return new OrderPlaced(id); } // domain event
}

public interface OrderRepository { Optional<Order> findById(OrderId id); void save(Order o); }

Common mistakes

  • Applying tactical patterns (repositories, entities) without strategic design, giving "DDD-lite" with the same big ball of mud.
  • One shared "Customer" model across the whole company.
  • Huge aggregates that lock too much and perform badly.
  • Anaemic domain models where entities are just getters and setters and all logic sits in services.

How to answer in the interview

"DDD, from Eric Evans' 2003 book, builds the software model around the business domain together with domain experts. Strategically, we develop a ubiquitous language shared by business and developers, split the domain into bounded contexts like Ordering, Billing and Shipping, each with its own consistent model, and describe their relationships in a context map. Tactically, we model with entities that have identity, immutable value objects like Money, aggregates that are consistency boundaries with a root such as Order, repositories per aggregate, domain services and domain events. Bounded contexts are also a good basis for microservice boundaries. For simple CRUD, it's overkill."

Likely follow-up questions

  • What is an aggregate, and why modify only one per transaction? A consistency boundary with a root; one per transaction keeps locks small and boundaries clear, with others updated via events.
  • Entity vs value object? Entities have identity over time; value objects are defined by values and immutable.
  • What is an anticorruption layer? A translation layer that protects your model from a legacy or external model.
