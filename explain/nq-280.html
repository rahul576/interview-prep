How do you validate success and failure scenarios in integration tests?

Testing · scenario · levels mid

In one line

For each scenario, arrange real or stubbed dependencies explicitly (Testcontainers data, WireMock responses), call the API, assert the HTTP status, body and headers, and above all assert side effects: database state, published messages, no partial writes, retry counts and consistent error formats, with isolated, repeatable test data.

Detailed explanation

An integration test is only as good as its assertions. Checking "200 OK" proves little; bugs hide in what happened behind the response.

Arrange the world per scenario. Insert the data the scenario needs in the Testcontainers database (via repositories, @Sql scripts or builders), and configure WireMock stubs for downstream systems: a normal success; a 4xx such as 404 or 409; a 5xx; a delay beyond the client timeout; a malformed body. Each test sets up exactly what it needs, which also documents the scenario.

Act through the real entry point: MockMvc or MockMvcTester for the MVC stack, WebTestClient or REST Assured against a running server, or KafkaTemplate for message-driven flows.

Assert the response: status code, body fields, headers such as Location or Retry-After, and that errors follow the agreed format (for example RFC 9457 Problem Details with type, title, status, detail), with no stack traces leaking.

Assert side effects, the most important part:

  • Success: the expected rows exist with correct values; the expected event was published to Kafka (read with a test consumer and Awaitility); downstream calls were made with the right payload (wireMock.verify(...)).
  • Failure: nothing partial was committed (transaction rolled back, or compensation executed); no event was published, or an outbox row was not created; retries happened the configured number of times; the circuit breaker or fallback engaged; invalid input was rejected before any downstream call.
  • Duplicates: repeating a request with the same idempotency key creates only one record.

Isolation: use unique ids per test, clean tables in @AfterEach or rely on rollback (careful: with a real server, the HTTP request runs in a different transaction, so test-level rollback does not apply). Reset WireMock between tests.

How it works

  1. Seed data and configure stubs for the scenario.
  2. Call the API or publish the message.
  3. Assert status, body, headers and error format.
  4. Assert DB state, events and downstream calls.
  5. For failures, assert absence of partial effects.
  6. Clean up or isolate data for the next test.

Example

@Test
void returns502AndPersistsNothingWhenInventoryFails() {
    inventory.stubFor(post("/reservations").willReturn(serverError()));

    given().port(port).contentType(JSON)
           .body("""
                 {"sku":"A1","quantity":2,"customerId":7}""")
    .when().post("/orders")
    .then().statusCode(502)
           .contentType("application/problem+json")
           .body("title", equalTo("Inventory unavailable"));

    assertThat(orderRepository.count()).isZero();                       // no partial write
    inventory.verify(3, postRequestedFor(urlEqualTo("/reservations")));  // retries
    assertThat(testConsumer.poll("order-created", Duration.ofSeconds(2))).isEmpty();
}

@Test
void createsOrderAndPublishesEvent() {
    inventory.stubFor(post("/reservations").willReturn(okJson("{\"id\":\"r-1\"}")));
    String id = createOrder("A1", 2);
    assertThat(orderRepository.findById(id)).get().extracting(Order::status).isEqualTo(CONFIRMED);
    await().atMost(Duration.ofSeconds(10)).untilAsserted(() ->
        assertThat(testConsumer.records("order-created")).anyMatch(r -> r.key().equals(id)));
}

Common mistakes

  • Asserting only the status code.
  • Not checking that failures leave no partial data.
  • Tests depending on data from other tests.
  • Assuming @Transactional on a test rolls back changes made by a real HTTP server thread.

How to answer in the interview

"For each scenario I set the world up explicitly: data in the Testcontainers database and WireMock stubs returning success, a 500, a 404 or a delay beyond the timeout. Then I call the API through MockMvc or REST Assured and assert status, body, headers and that errors follow our problem-details format. Most importantly I assert side effects: the right rows were written, or for failures that nothing partial was committed; the Kafka event was or wasn't published; retries happened the configured number of times. Each test uses its own data or cleans up, so tests are independent and repeatable."

Likely follow-up questions

  • How do you assert a Kafka event was published? A test consumer on the topic plus Awaitility, matching by key.
  • Why doesn't test rollback work with RANDOM_PORT? The request runs on a server thread in its own transaction.
  • How do you test idempotency? Send the same request with the same idempotency key twice and assert one record.
