What security requirements apply to Streamable HTTP MCP servers, including local ones?

MCP Servers · concept · levels mid, senior, lead

In one line

Streamable HTTP servers must validate the Origin header (against DNS rebinding), local servers should bind to 127.0.0.1 and require authentication even locally, remote servers need TLS, OAuth 2.1, rate limiting and input validation, and in the 2026-07-28 revision servers must reject requests whose routing headers do not match the body.

Detailed explanation

An HTTP MCP server is a web service that can trigger real actions, so it inherits all web threats plus some specific ones.

DNS rebinding. A malicious website can make its domain resolve to 127.0.0.1 after the page loads, so the victim's browser sends requests to a server running on the victim's machine while the browser believes it is talking to the attacker's origin. If a local MCP server accepts those requests, the website can call its tools. The specification therefore requires servers to validate the Origin header and reject unexpected origins.

Local binding. Local servers should bind to localhost (127.0.0.1), not 0.0.0.0, so other machines on the same café Wi-Fi or office network cannot reach them.

Authentication everywhere. Servers should implement authentication for all connections, even local ones. Any process or browser page that can reach an unauthenticated localhost port can use the server with the user's privileges.

Remote servers must use TLS, authenticate every request, normally with OAuth 2.1 bearer tokens issued for that server (audience-bound via resource indicators, validated on every call, never passed through to downstream APIs), and apply rate limiting, request size limits, timeouts, input validation and the usual OWASP controls.

Header/body consistency. Per the question's reference material, the 2026-07-28 revision has requests carry headers such as Mcp-Method and Mcp-Name mirroring the JSON-RPC body, so gateways and WAFs can route, authorise and rate-limit without parsing bodies. Servers must reject requests where headers and body disagree, otherwise an attacker could pass a harmless-looking header to a gateway policy while the body calls a dangerous tool.

How it works

  1. Terminate TLS; reject plain HTTP for remote servers.
  2. Check Origin against an allowlist; reject mismatches with 403.
  3. Validate the bearer token: signature, expiry, audience = this server, scopes.
  4. Check routing headers match the body's method and tool name.
  5. Enforce rate limits, size limits and schema validation; then dispatch.

Example

app.post("/mcp", (req, res, next) => {
  const origin = req.get("Origin");
  if (origin && !ALLOWED_ORIGINS.has(origin)) return res.status(403).end();
  const claims = verifyJwt(req.get("Authorization"), { audience: "https://mcp.example.com" });
  if (!claims) return res.status(401).set("WWW-Authenticate", 'Bearer resource_metadata="..."').end();
  const hdrMethod = req.get("Mcp-Method");
  if (hdrMethod && hdrMethod !== req.body.method) return res.status(400).end();
  next();
});
app.listen(8080, "127.0.0.1");   // local development: never 0.0.0.0

Common mistakes

  • No authentication on a "local only" server.
  • Binding to all interfaces during development and forgetting.
  • Accepting tokens issued for other services (no audience check).
  • Trusting gateway-visible headers without checking the body.
  • Skipping rate limits because "only agents call it".

How to answer in the interview

"The spec requires validating the Origin header to stop DNS rebinding, where a malicious website gets the browser to send requests to a server on my machine. Local servers should bind to 127.0.0.1, not all interfaces, and should still require authentication, because any local process or web page reaching that port could otherwise use it. Remote servers need TLS, OAuth 2.1 bearer tokens validated for audience and scope on every request, rate limiting, size limits and input validation like any web API. And in the 2026-07-28 revision, routing headers like Mcp-Method mirror the body so gateways can act on them, so servers must reject requests where headers and body don't match."

Likely follow-up questions

  • Why is unauthenticated localhost dangerous? Malicious pages (via rebinding) or local malware can invoke tools with the user's privileges.
  • What is token passthrough and why avoid it? Forwarding the client's token to downstream APIs breaks audience checks and auditing; use separate tokens.
  • Where to rate limit? At a gateway per client and per tool, plus inside the server for expensive tools.
