What is a good testing strategy for infrastructure code?

Infrastructure as Code · design · levels senior

In one line

Test infrastructure code as a pyramid: fast static checks on every commit, unit tests with terraform test and mocks, policy and security checks on plans, integration tests in sandbox accounts for shared modules, and post-deploy smoke tests plus continuous compliance.

Detailed explanation

Infrastructure tests are expensive at the top (real resources cost money and take minutes) and cheap at the bottom, so you run many cheap checks often and few expensive ones selectively, exactly like application testing.

Static checks (seconds, every commit). terraform fmt -check, terraform validate, tflint (provider-aware rules such as invalid instance types), and security scanners like Checkov or Trivy (which absorbed tfsec) catch public buckets or missing encryption before anything runs. Pre-commit hooks make them local too.

Unit tests (seconds). terraform test (Terraform 1.6+) runs .tftest.hcl files with command = plan to assert on module logic: naming, conditional resources, computed values and variable validation. Mock providers (1.7+) let tests run without cloud credentials. These cover the logic most likely to break.

Policy checks (per plan). OPA/Conftest, Sentinel or Checkov evaluate the plan JSON against organisational rules: mandatory tags, allowed regions, no deletes of protected types. They run on every PR in live repositories.

Integration tests (minutes, selective). For shared modules, tests actually apply in an isolated sandbox account, using terraform test with command = apply or Terratest in Go, then check behaviour (can a pod reach the database, does the bucket deny public access) and destroy. They run on module releases, nightly or when relevant paths change, with cleanup jobs (for example aws-nuke on sandbox accounts) for leftovers.

After deployment. Smoke tests verify endpoints, DNS and connectivity; continuous compliance (AWS Config rules, Azure Policy) keeps checking reality, including changes made outside code.

How it works

  1. Pre-commit: fmt, validate, tflint, Checkov.
  2. PR on module: terraform test unit tests with mocks.
  3. PR on live repo: plan + policy checks.
  4. Module release: integration tests in sandbox, then destroy.
  5. Post-apply: smoke tests; continuous compliance alerts.

Example

# tests/naming.tftest.hcl
mock_provider "aws" {}

variables {
  app = "pay"
  env = "prod"
}

run "bucket_name_follows_convention" {
  command = plan
  assert {
    condition     = aws_s3_bucket.this.bucket == "acme-pay-prod-logs"
    error_message = "Bucket name does not follow the naming convention."
  }
}

Common mistakes

  • Only running validate and calling it testing.
  • Integration tests on every commit, making CI slow and costly.
  • Tests that create resources in shared accounts and leak them.
  • No tests for the policies themselves.

How to answer in the interview

"I treat it as a pyramid. On every commit, fast static checks: fmt, validate, tflint and a security scanner like Checkov or Trivy. Then unit tests with terraform test, often with mock providers, checking module logic like naming, conditional resources and outputs without creating anything. Policy checks run against every plan. For shared modules, integration tests actually apply in isolated sandbox accounts, with terraform test or Terratest, verify the resources work, and destroy them. After deployments there are smoke tests, and AWS Config or Azure Policy keep checking continuously."

Likely follow-up questions

  • Why not run full integration tests on every change? They are slow and costly; run them on releases or relevant changes.
  • How do you test policies? Unit tests for Rego or Sentinel with passing and failing sample plans.
  • What do mocks miss? Real API behaviour, permissions, quotas and eventual consistency.
