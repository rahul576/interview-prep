How do you configure the Kubernetes or Helm provider in Terraform so credentials do not expire or leak?

Terraform · concept · levels mid, senior

In one line

Configure the Kubernetes and Helm providers with the cluster endpoint, CA certificate and an exec credential plugin (kubelogin for AKS, aws eks get-token for EKS) so short-lived tokens are fetched at every run, keep the providers in a separate state from cluster creation, and prefer GitOps for workloads.

Detailed explanation

The easy option — writing a kubeconfig with a client certificate or a long-lived service account token, or passing kube_admin_config attributes straight from the cluster resource — has two problems. It leaks: the credential is stored in state, in pipeline artifacts or on disk. And it expires or gets rotated, so the next run fails with an authentication error long after anyone remembers why.

The better approach is the provider's exec block. Terraform calls a credential plugin whenever it needs a token. For AKS with Entra ID integration and local accounts disabled, kubelogin get-token with --login workloadidentity or azurecli uses the pipeline's federated identity. For EKS, aws eks get-token produces a token signed with the runner's IAM role, mapped to Kubernetes permissions through EKS access entries. Tokens live minutes, are never written to state, and Kubernetes RBAC controls what the pipeline can do.

The second issue is provider configuration from unknown values. If the cluster and the Kubernetes resources share a state, the provider is configured from attributes that are unknown during the first plan, and on destroy or replacement the provider may try to talk to a cluster that is being deleted. Terraform's documentation recommends keeping them in separate root modules: one creates the cluster, the other reads it with a data source and manages in-cluster resources.

Finally, Terraform is good at bootstrapping a cluster — namespaces, an ingress controller, Argo CD or Flux — but application workloads change often and are better reconciled continuously by GitOps.

How it works

  1. Root module A creates the cluster and outputs its name.
  2. Root module B uses a data source to read the endpoint and CA certificate.
  3. The provider exec block runs kubelogin or aws eks get-token at each operation.
  4. The pipeline identity is mapped to a Kubernetes role with only the needed rights.
  5. B installs bootstrap components; GitOps manages the rest.

Example

data "azurerm_kubernetes_cluster" "main" {
  name                = "aks-prod"
  resource_group_name = "rg-aks-prod"
}

provider "kubernetes" {
  host                   = data.azurerm_kubernetes_cluster.main.kube_config[0].host
  cluster_ca_certificate = base64decode(data.azurerm_kubernetes_cluster.main.kube_config[0].cluster_ca_certificate)
  exec {
    api_version = "client.authentication.k8s.io/v1beta1"
    command     = "kubelogin"
    args        = ["get-token", "--login", "workloadidentity",
                   "--server-id", "6dae42f8-4368-4678-94ff-3960e28e3630"]
  }
}

Common mistakes

  • Using kube_admin_config credentials, which bypass Entra ID and are stored in state.
  • Writing a kubeconfig file in the pipeline and uploading it as an artifact.
  • Creating the cluster and Helm releases in the same state, then failing on destroy.
  • Managing every application manifest with Terraform instead of GitOps.

How to answer in the interview

"I avoid static kubeconfigs because long-lived certificates or tokens leak and expire. I configure the Kubernetes and Helm providers with the endpoint, the CA certificate and an exec block that runs a credential plugin each time: kubelogin for AKS using the pipeline's workload identity, or aws eks get-token for EKS. Tokens are short-lived and never stored. I keep these providers in a separate state from the cluster, because configuring a provider from a cluster created in the same run causes unknown values and destroy problems. And beyond bootstrapping, I hand workloads to GitOps."

Likely follow-up questions

  • What breaks if the cluster and Kubernetes resources share a state and you destroy? Terraform may delete the cluster first, then fail to reach it to delete in-cluster resources.
  • How is the pipeline authorised in EKS? EKS access entries or aws-auth mapping the IAM role to a Kubernetes group.
  • Why GitOps for workloads? Continuous reconciliation, faster deploys, and drift correction without a Terraform run.
