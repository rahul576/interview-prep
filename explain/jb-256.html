How would you design an event-driven architecture using Kafka and Spring Boot?

Kafka · design · levels senior, lead

In one line

Model domain events first, key them by aggregate id, publish reliably with a transactional outbox, consume with idempotent @KafkaListener services in their own groups, govern schemas in a registry, and add retries, DLTs, tracing and lag monitoring.

Detailed explanation

Events and topics. Start from the business domain, ideally with event storming: facts such as OrderPlaced, PaymentCompleted, ShipmentDispatched. Events describe what happened, in past tense, owned by the producing service. A common layout is one topic per aggregate type or bounded context (orders.events) with the aggregate id as key, so all events of an order land in one partition and stay ordered. Choose partition counts for peak consumer parallelism; set retention, or compaction for "latest state" topics.

Reliable production. Writing to the database and then calling KafkaTemplate.send is a dual write: a crash between them loses or invents events. The transactional outbox solves it: insert the event into an outbox table in the same transaction as the business change, and let a relay, such as Debezium CDC or a poller, publish it. For simpler cases, KafkaTemplate with idempotent producers and acks=all is acceptable.

Consumers. Each downstream service has its own consumer group, so it receives every event independently and scales up to the partition count. Consumers are idempotent (processed-id table or upserts), because delivery is at-least-once. Errors use Spring Kafka's DefaultErrorHandler and @RetryableTopic with a DLT.

Contracts. Use Avro, Protobuf or JSON Schema with a schema registry and a backward-compatible evolution policy: add optional fields, never remove or repurpose them. Include metadata: event id, type, version, timestamp and trace context.

Operations. Propagate trace ids in headers (Micrometer Tracing / OpenTelemetry), monitor consumer lag and DLT counts, and document topics in a catalogue.

How it works

  1. Order service saves the order and an outbox row in one transaction.
  2. Debezium reads the database log and publishes OrderPlaced keyed by orderId.
  3. Payment, inventory and notification services consume in separate groups.
  4. Each checks its processed-id table, applies its change, emits its own events.
  5. Failures go through retry topics to a DLT; dashboards show lag and errors.

Example

@Transactional
public Order placeOrder(PlaceOrder cmd) {
    Order order = orders.save(Order.from(cmd));
    outbox.save(new OutboxEvent(UUID.randomUUID(), "Order", order.getId(),
            "OrderPlaced", json(new OrderPlaced(order.getId(), order.total()))));
    return order;
}

@KafkaListener(topics = "orders.events", groupId = "inventory")
public void on(OrderPlaced evt, @Header("eventId") String eventId) {
    if (!processed.markIfNew(eventId)) return;
    inventory.reserve(evt.orderId(), evt.lines());
}

Common mistakes

  • Publishing events outside the database transaction (dual write).
  • Using events as remote commands that tightly couple services.
  • Random keys, losing per-entity ordering.
  • No schema governance, so one producer change breaks every consumer.
  • Putting entire entities with sensitive data into every event.

How to answer in the interview

"I start from the domain events, like OrderPlaced and PaymentCompleted, and design topics per aggregate, keyed by aggregate id so each order's events stay ordered. Producers use the transactional outbox, written in the same transaction as the business change and relayed by Debezium, so we never lose an event. Each consumer is a Spring Boot service with @KafkaListener in its own consumer group, scaled up to the partition count, and idempotent. Events have Avro or JSON Schema contracts in a schema registry with backward-compatible evolution. Around that I add retry topics, a DLT, trace propagation and lag monitoring."

Likely follow-up questions

  • How would a new service build its read model from existing events? Replay from the beginning with a new consumer group if retention allows, or from a compacted topic or a snapshot plus events.
  • Event notification vs event-carried state transfer? Thin events need a callback; fat events carry the data consumers need.
  • How do you version events? Backward-compatible schema changes; for breaking changes, a new event type or topic.
