How do you run Terraform safely in a CI/CD pipeline?

Infrastructure as Code · design · levels mid

In one line

Run Terraform through a pipeline: checks and plan on the pull request (posted for review), apply the saved plan after approval, OIDC short-lived credentials with least-privilege roles per environment, locking and serialised runs, and no local applies to production.

Detailed explanation

Pull request stage. Every change goes through a PR. The pipeline runs terraform fmt -check, validate, tflint and a security scanner (Checkov or Trivy), then terraform plan -out=tfplan for each affected state. The rendered plan, and often a cost diff from Infracost and policy results (OPA/Conftest, Sentinel), are posted as a PR comment. Reviewers approve code and plan.

Apply stage. After approval and merge, the pipeline applies exactly the saved plan from the reviewed run (terraform apply tfplan), or re-plans on main and requires approval of that plan. Production uses a manual approval gate, such as a GitHub Environment with required reviewers or a GitLab protected environment. Saved plan files contain sensitive data, so they are stored as short-lived, access-restricted artifacts.

Credentials. No long-lived access keys. The CI system authenticates to the cloud through OIDC federation (GitHub Actions, GitLab, Azure DevOps to AWS IAM roles, Azure federated credentials, GCP Workload Identity Federation) and gets short-lived tokens. Each environment has its own role, trust-limited to the right repository, branch and environment, so a dev pipeline or a PR from a fork cannot touch production. Plan roles can be read-only; apply roles have write access.

Concurrency. The backend's state lock prevents simultaneous writes, and pipeline concurrency groups ensure only one apply per state at a time and runs happen in order. One pipeline owns each state. Nobody applies to production from a laptop; break-glass access exists but is audited.

Afterwards. Scheduled drift-detection plans, notifications, and run history for audit. Tools such as Atlantis, HCP Terraform, Spacelift or env0 package this workflow.

How it works

  1. PR opened → checks → plan → comment with plan, cost and policy results.
  2. Review and approval.
  3. Merge → apply saved plan (with approval gate for prod).
  4. OIDC role per environment provides credentials.
  5. Lock and concurrency controls serialise applies.

Example

name: terraform-prod
on:
  push:
    branches: [main]
permissions:
  id-token: write
  contents: read
concurrency: { group: tf-prod, cancel-in-progress: false }
jobs:
  plan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::111122223333:role/tf-plan-prod
          aws-region: eu-west-1
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init -input=false && terraform plan -input=false -out=tfplan
      - uses: actions/upload-artifact@v4
        with: { name: tfplan, path: tfplan, retention-days: 1 }
  apply:
    needs: plan
    runs-on: ubuntu-latest
    environment: production        # required reviewers
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::111122223333:role/tf-apply-prod
          aws-region: eu-west-1
      - uses: hashicorp/setup-terraform@v3
      - uses: actions/download-artifact@v4
        with: { name: tfplan }
      - run: terraform init -input=false && terraform apply -input=false tfplan

Common mistakes

  • Long-lived cloud keys stored as CI secrets.
  • Re-running apply without a plan, applying something nobody reviewed.
  • One all-powerful role for every environment.
  • Parallel pipelines racing on the same state.

How to answer in the interview

"Every change goes through a pull request. The pipeline runs fmt, validate, tflint and a security scanner, then plan, and posts the plan, often with an Infracost estimate, for reviewers. After approval and merge it applies exactly the saved plan, with a manual approval gate for production, so what was reviewed is what gets applied. Credentials come from OIDC federation as short-lived tokens, with a separate least-privilege role per environment, so there are no long-lived keys and dev pipelines can't touch prod. State locking and concurrency limits prevent parallel applies, and nobody applies to production from a laptop."

Likely follow-up questions

  • What should happen if the state changed between plan and apply? Terraform rejects the stale saved plan; re-plan and re-review.
  • How do you handle PRs from forks? No cloud credentials for untrusted runs; plan only after maintainer approval.
  • Plan role vs apply role? Read-only for plan, write for apply, limiting what an unreviewed run can do.
