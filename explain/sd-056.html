What are backpressure and load shedding, and how do you apply them in a high-traffic system?

Scalability & Reliability · concept · levels senior, lead

In one line

Backpressure makes producers slow down when consumers can't keep up; load shedding rejects excess work early (429/503) so accepted requests stay fast; use bounded queues, priorities and adaptive concurrency limits.

Detailed explanation

Every system has a maximum throughput. Beyond it, a system that accepts everything just builds queues: latency rises for everyone, memory grows, timeouts fire, clients retry, and goodput (useful work completed) collapses. It's better to serve 90% of requests well than 100% badly.

Backpressure mechanisms: TCP flow control; reactive streams request(n); pull-based consumers (Kafka) that only fetch what they can process; blocking on bounded queues.

Load shedding: reject at the edge before doing work. Return 429 (client should slow down) or 503 with Retry-After. Shed low-priority traffic first: background sync, prefetch, analytics, then anonymous traffic, keeping checkout and logged-in critical paths.

Adaptive concurrency limits (Netflix concurrency-limits, Envoy adaptive concurrency) measure latency and lower the allowed in-flight requests when latency rises, like TCP congestion control (AIMD/Vegas/gradient algorithms).

How it works

  1. Each service has a max in-flight limit (static or adaptive).
  2. Over the limit → reject immediately with 503 (cheap).
  3. Queues are bounded; if full → reject or apply backpressure upstream.
  4. Priority headers decide what to shed first.
  5. Clients back off with jitter.

Example

# Envoy adaptive concurrency filter (concept)
adaptive_concurrency:
  gradient_controller_config:
    sample_aggregate_percentile: { value: 90 }
    concurrency_limit_params: { max_concurrency_limit: 1000 }

Common mistakes

  • Unbounded thread pools or queues.
  • Shedding after expensive work (DB query) instead of before.
  • Retrying shed requests immediately.
  • Treating all traffic as equal priority.

How to answer in the interview

"When load exceeds capacity, queuing just makes everything slow, so I'd bound queues and limit in-flight requests per service, ideally adaptively based on latency. Excess requests are rejected early with 429 or 503 and Retry-After so clients back off. I'd shed by priority: background and prefetch traffic first, checkout and payments last. Pull-based consumers naturally apply backpressure."

Likely follow-up questions

  • What to shed first? Non-user-facing, retries, low-value endpoints.
  • Goodput vs throughput? Successful useful work vs raw requests handled.
  • Client role? Exponential backoff with jitter, honouring Retry-After.
