What are the main features of Java, and why is Java platform-independent?

Core Java & OOP · concept · levels entry, mid

In one line

Java is an object-oriented, strongly typed, garbage-collected language with built-in multithreading, a strong security model and a rich standard library; it is platform-independent because javac produces bytecode that runs on a platform-specific JVM.

Detailed explanation

Java's main features:

  • Object-oriented: classes, interfaces, inheritance, polymorphism and encapsulation, now complemented by functional features (lambdas, streams) and data-oriented features (records, sealed types, pattern matching).
  • Strong static typing: the compiler catches many errors before runtime, and generics give type-safe collections.
  • Automatic memory management: objects are allocated on the heap and reclaimed by a garbage collector (G1 by default, with ZGC and others available), so there are no manual frees and no dangling pointers.
  • Robustness and security: no pointer arithmetic, array bounds checks, bytecode verification before execution, and exceptions for error handling.
  • Concurrency: threads and java.util.concurrent are built in, and virtual threads (Java 21) make high-concurrency I/O code simpler.
  • Huge ecosystem: the standard library plus Maven Central, Spring, Hibernate, Kafka and more.
  • Performance: the JIT compiler (C1/C2 in HotSpot) profiles running code and compiles hot paths to optimised native code.

Platform independence comes from an extra layer. javac does not compile to x86 or ARM instructions; it compiles to bytecode in .class files, an instruction set for an abstract machine. Each operating system and CPU has its own JVM implementation that loads, verifies, interprets and JIT-compiles that bytecode to native code. So the same jar runs on Windows, Linux or macOS, on Intel or Apple Silicon: "write once, run anywhere". The bytecode is portable; the JVM is not.

Portability has limits: native libraries via JNI, OS-specific paths, line endings, or a jar compiled for a newer class-file version than the installed JVM.

How it works

  1. Write .java source.
  2. javac compiles it to platform-neutral bytecode in .class files, packaged in jars.
  3. The JVM's class loader loads classes on demand.
  4. The bytecode verifier checks type safety.
  5. The interpreter runs code; the JIT compiles hot methods to native machine code.
  6. The GC manages heap memory throughout.

Example

javac Hello.java           # produces Hello.class (bytecode)
javap -c Hello             # inspect the bytecode instructions
java Hello                 # run on any OS with a compatible JVM (JRE/JDK 17+, say)
java -XX:+PrintCompilation Hello   # watch the JIT compile hot methods

Common mistakes

  • Saying Java is "interpreted only"; HotSpot JIT-compiles hot code.
  • Claiming the JVM is platform-independent.
  • Confusing JDK (tools + runtime), JRE (runtime) and JVM (execution engine).
  • Ignoring class-file version errors (UnsupportedClassVersionError) when moving jars between Java versions.

How to answer in the interview

"Java is an object-oriented, strongly typed language with automatic garbage collection, built-in multithreading, a strong security model with bytecode verification, and a huge standard library and ecosystem. It's platform-independent because javac doesn't produce machine code; it produces bytecode. Every platform has its own JVM that loads, verifies, interprets and JIT-compiles that bytecode into native code. So the same jar runs anywhere a compatible JVM exists. The bytecode is portable; the JVM itself is platform-specific."

Likely follow-up questions

  • Is the JVM itself platform-independent? No, each OS and CPU architecture has its own JVM build.
  • What is the JIT? A compiler inside the JVM that turns frequently executed bytecode into optimised native code at runtime.
  • What is GraalVM native image? Ahead-of-time compilation to a native executable, trading portability for startup time.
