Explain ACID transactions and isolation levels, and the anomalies each level prevents.

Data & Storage Design · concept · levels mid, senior

In one line

ACID makes a transaction all-or-nothing, valid, isolated and durable; isolation levels (read committed → repeatable read → serializable) trade concurrency for protection against anomalies like dirty reads, non-repeatable reads, phantoms, lost updates and write skew.

Detailed explanation

Full serializability is expensive, so databases default to weaker levels. Knowing which anomalies remain is what lets you write correct concurrent code.

  • Dirty read: reading uncommitted data. Prevented by read committed.
  • Non-repeatable read: the same row read twice gives different values. Prevented by repeatable read / snapshot isolation.
  • Phantom: a range query returns new rows the second time.
  • Lost update: two transactions read-modify-write the same row; one overwrites the other.
  • Write skew: two transactions read overlapping data and write different rows, together violating a rule (the "two doctors on call" example). Only serializable (or explicit locks) prevents it.

PostgreSQL defaults to read committed; MySQL InnoDB to repeatable read. PostgreSQL's serializable uses SSI and aborts conflicting transactions, so apps must retry.

How it works

  1. Choose the default level for the app (usually read committed).
  2. For critical invariants, use one of: atomic updates, SELECT … FOR UPDATE, optimistic version columns, or serializable with retries.
  3. Keep transactions short to reduce contention.

Example

-- Lost-update-safe stock decrement (atomic, no read-modify-write in app code)
UPDATE inventory SET qty = qty - 1
WHERE sku = 'X1' AND qty > 0;
-- 0 rows updated → out of stock

-- Optimistic locking
UPDATE account SET balance = 900, version = 8 WHERE id = 1 AND version = 7;

Common mistakes

  • Read-modify-write in application code without locks or versions.
  • Assuming "repeatable read" prevents write skew.
  • Using serializable without retry logic.
  • Long transactions holding locks during HTTP calls.

How to answer in the interview

"ACID gives atomicity, consistency, isolation and durability. Isolation is the tricky one: most databases default to read committed, which still allows lost updates and write skew. For things like stock or balances I use atomic conditional updates, row locks with SELECT FOR UPDATE, or optimistic version columns, and for complex invariants serializable isolation with retries."

Likely follow-up questions

  • How do you prevent overselling? UPDATE … SET qty = qty - n WHERE qty >= n, or row lock.
  • Pessimistic vs optimistic locking? Locks for high contention; versions for low contention.
  • What is MVCC? Multi-version concurrency control: readers see snapshots and don't block writers.
