How would you implement a callback or polling mechanism for an asynchronous downstream system?

Cloud (AWS) · design · levels senior, lead

In one line

Prefer callbacks or events from the downstream system: store the request as PENDING with a correlation ID, return 202 Accepted with a status link, and on callback authenticate, verify the signature, match the correlation ID and update state idempotently; if callbacks are impossible, poll efficiently with delayed SQS messages or Step Functions wait states, exponential backoff and a maximum timeout, then notify clients via status endpoint, webhook, WebSocket or events.

Detailed explanation

Many downstream systems (payment providers, KYC checks, document processing, partner APIs) take seconds to hours. Holding an HTTP request open for that is fragile, so the design becomes asynchronous.

Callback first:

  1. Persist the request with a correlation ID and status PENDING before calling downstream (avoiding the race where the callback arrives first).
  2. Submit to the downstream system with the correlation ID and a callback URL, or subscribe to its events.
  3. Return 202 Accepted with Location: /requests/{id} to your client.
  4. On callback: authenticate (mTLS, OAuth, or HMAC signature with timestamp to stop replay), look up by correlation ID, apply a state transition idempotently (callbacks can be repeated or out of order), respond 2xx quickly and process asynchronously via a queue.
  5. Publish a domain event and notify the client.

Polling fallback: avoid tight loops and cron jobs scanning tables. Schedule each check: send an SQS message with DelaySeconds, re-enqueue with longer delays (10 s, 30 s, 2 min, 10 min); or use Step Functions with a Wait state and a loop with retry/backoff, ideal for long durations. Respect downstream rate limits, and after a maximum time mark the request FAILED or TIMED_OUT and escalate.

Hybrid: many teams use callbacks plus a slower reconciliation poll to catch missed callbacks.

Client notification: status endpoint for polling clients, webhooks to their systems, WebSocket or Server-Sent Events for UIs, or events on a bus.

How it works

  1. Save request as PENDING with correlation ID.
  2. Call downstream with callback URL.
  3. Return 202 and status link.
  4. Callback: verify, match, update idempotently.
  5. If no callback: delayed polls with backoff until done or timeout.
  6. Notify the client and publish an event.

Example

@PostMapping("/payments/callback")
public ResponseEntity<Void> callback(@RequestHeader("X-Signature") String sig, @RequestBody String body) {
    if (!signatureVerifier.valid(body, sig)) return ResponseEntity.status(401).build();
    CallbackEvent e = mapper.readValue(body, CallbackEvent.class);
    int updated = jdbc.update(
        "UPDATE payment_request SET status = ? WHERE correlation_id = ? AND status = 'PENDING'",
        e.status(), e.correlationId());           // idempotent: only first transition applies
    if (updated == 1) events.publish(new PaymentCompleted(e.correlationId(), e.status()));
    return ResponseEntity.ok().build();
}

Common mistakes

  • Saving the record after calling downstream, so early callbacks find nothing.
  • Unauthenticated callback endpoints.
  • Non-idempotent updates on duplicate callbacks.
  • Tight polling loops with no backoff or timeout.

How to answer in the interview

"My first choice is a callback. I save the request as PENDING with a correlation ID before calling downstream, send the correlation ID and a callback URL, and return 202 Accepted with a status link to our client. When the callback arrives, I verify its signature, find the request by correlation ID and update the state idempotently, since callbacks can repeat, then publish an event or notify the client by webhook or WebSocket. If the downstream system can't call back, I poll efficiently with delayed SQS messages or a Step Functions wait loop with exponential backoff, and give up after a maximum time, marking it failed or escalating."

Likely follow-up questions

  • Callback arrives before your record is saved? Persist first; otherwise store unmatched callbacks and retry matching.
  • What if callbacks are lost? Reconciliation polling for requests pending too long.
  • How to stop replay attacks? Signed timestamps, short tolerance windows and event-ID deduplication.
