Design a real-time leaderboard for a game with millions of players.

Classic Design Problems · design · levels entry, mid, senior

In one line

Use Redis sorted sets (ZINCRBY, ZREVRANGE, ZREVRANK) for O(log N) updates, top-N and rank queries, back them with a durable store, keep one set per time window, and shard or approximate for very large boards.

Detailed explanation

A leaderboard needs two fast queries under constant updates: "top 100" and "what's my rank, and who is around me?". A SQL ORDER BY score LIMIT 100 is fine for small tables, but computing one player's rank (COUNT(*) WHERE score > mine) over millions of rows on every request is expensive.

A Redis sorted set is a skip list plus hash: each member has a score; updates, rank lookups and range queries are all O(log N). Millions of members fit comfortably in memory.

Redis isn't the source of truth: score events go to a durable database (or log) first, and the sorted set can be rebuilt. Time-windowed boards (daily, weekly, season) are separate keys with expiry. For hundreds of millions of players, you shard by region or score band, or show exact ranks only for the top and percentiles for everyone else.

How it works

  1. Game server emits ScoreEvent(player, delta, matchId) with an idempotency key.
  2. Leaderboard service persists it and runs ZINCRBY lb:global:2026-w47 delta player.
  3. Top N: ZREVRANGE lb:… 0 99 WITHSCORES.
  4. My rank: ZREVRANK lb:… player; neighbours: ZREVRANGE lb:… rank-5 rank+5.
  5. Friends board: fetch friends' scores with ZMSCORE and sort in the app.

Example

ZINCRBY lb:daily:2026-11-21 50 player:42
ZREVRANGE lb:daily:2026-11-21 0 9 WITHSCORES
ZREVRANK lb:daily:2026-11-21 player:42
EXPIRE lb:daily:2026-11-21 172800

Common mistakes

  • Treating Redis as the only copy of scores.
  • Not deduplicating score events (double points on retries).
  • One giant key for a global board with hundreds of millions of members.
  • Ties: decide a tie-breaker (e.g. encode earlier timestamp into the score).

How to answer in the interview

"I'd use Redis sorted sets: score updates with ZINCRBY, top-N with ZREVRANGE and a player's rank with ZREVRANK, all logarithmic. Score events are persisted durably first so Redis can be rebuilt. Daily and weekly boards are separate keys with TTLs. At very large scale I'd shard by region and show percentile ranks for players outside the top."

Likely follow-up questions

  • Friends-only leaderboard? Fetch friends' scores and sort, or maintain per-user small sets.
  • How to break ties? Composite score: score × 10^k + (MAX_TS − timestamp).
  • Cheating? Server-authoritative scores, anomaly detection.
