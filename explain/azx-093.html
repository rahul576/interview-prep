What is the Foundry Agent Service, and what does it handle for you?

Azure AI & Foundry · concept · levels mid, senior

In one line

The Foundry Agent Service is a managed runtime for AI agents: you define a model, instructions and tools, and it runs the model-tool loop, keeps conversation state (on the Responses API), executes built-in and custom tools, handles identity, content safety and networking, and provides tracing and evaluation.

Detailed explanation

Building an agent yourself means writing a loop: call the model, parse tool calls, execute them securely, append results, call the model again, store the conversation, handle errors, enforce limits and log everything. The Agent Service provides that loop as a managed service in a Foundry project.

Definition: an agent combines a model deployment, instructions (system prompt) and a set of tools. The current service is built on the OpenAI-compatible Responses API with conversations for state, while the earlier version used threads, messages and runs; the concepts are the same.

Tools:

  • File search over uploaded documents (managed vector store) and Azure AI Search for enterprise indexes.
  • Code interpreter, a sandbox for running Python on data and files.
  • Grounding with Bing Search for current web information.
  • OpenAPI tools that call your REST APIs from a spec, Azure Functions, and function calling executed by your own code.
  • Remote MCP servers, exposing tools via the Model Context Protocol.
  • Connected or multi-agent setups where one agent delegates to others.

What it manages: state storage, tool orchestration and retries, Entra ID identities (for example the agent's identity or on-behalf-of) for tool calls, content safety filters on inputs and outputs, and networking options to use your own storage, search and VNet (standard setup with bring-your-own resources).

Operations: tracing with OpenTelemetry shows every step: model calls, tool arguments and results, tokens and latency. Foundry evaluators measure intent resolution, task adherence, tool call accuracy and safety, which you need before giving an agent real permissions.

How it works

  1. Deploy a model in the Foundry project.
  2. Create an agent with instructions and tools.
  3. A user message starts or continues a conversation.
  4. The service calls the model, executes requested tools, loops until a final answer.
  5. Traces and evaluation results are stored for review.

Example

# Illustrative agent definition (SDK names vary by version)
name: it-helpdesk
model: gpt-4.1
instructions: |
  You help employees with IT issues. Use the knowledge base first.
  Never reset passwords without the create_ticket tool and user confirmation.
tools:
  - type: azure_ai_search        # internal KB index
    index: it-kb
  - type: openapi                 # ticketing API, Entra-authenticated
    spec: ./ticketing-openapi.json
  - type: mcp
    server_url: https://mcp.contoso.internal/devices
    require_approval: always

Common mistakes

  • Giving agents broad API permissions instead of narrow, purpose-built tools.
  • No human approval for destructive actions.
  • Skipping tracing, so failures can't be explained.
  • Testing with a few happy-path prompts instead of an evaluation set.

How to answer in the interview

"The Foundry Agent Service is a managed service for building and running agents. I define an agent with a model, instructions and tools, and the service runs the loop of calling the model, executing tools and keeping conversation state, built on the Responses API. Tools include file search, code interpreter, Bing grounding, Azure AI Search, OpenAPI functions, Azure Functions and remote MCP servers, plus multi-agent setups. It handles state, tool orchestration, Entra identities, content safety and private networking. OpenTelemetry tracing and Foundry evaluators make it operable in production."

Likely follow-up questions

  • How to restrict agent actions? Narrow tools, least-privilege identities, approval for risky calls, and policies at the API.
  • When use your own framework? For custom orchestration or on-premises hosting; Semantic Kernel or Microsoft Agent Framework can still use Foundry models.
  • How is state stored? In the service or in your own storage resources with the standard setup.
