After a deployment, the p99 latency of your Spring Boot API jumps from 100 milliseconds to 2 seconds. How do you investigate?

Troubleshooting · scenario · levels mid, senior, lead

In one line

Scope the regression with dashboards and APM, correlate it with the deployment and roll back first if users suffer, then use traces, the code and config diff, database metrics, Hikari pool waits, GC and CPU data, thread dumps and JFR profiles to find the cause, and finish with a regression guard such as a performance test and p99 alert.

Detailed explanation

A p99 jump from 100 ms to 2 s right after a deploy is a strong signal the change caused it, but confirm before assuming. The order of work matters: mitigate first, diagnose second.

Scope: is it every endpoint or one? All pods or only new ones (during a canary)? All customers or some? Did traffic change at the same time? Compare old and new versions side by side if both are running. If impact is significant, roll back (or shift the canary back): it restores service and, if latency recovers, confirms the release is responsible.

What changed: read the diff including dependency upgrades (Spring Boot, Hibernate, drivers, HTTP client), configuration (pool sizes, timeouts, log levels), JVM flags, base image and infrastructure (CPU limits, new sidecars). A changed default is a common culprit.

Where the time goes: pick slow requests in distributed tracing and look at the span breakdown. Typical findings:

  • Database: a new query without an index, N+1 queries introduced by a changed fetch type, larger result sets; check slow query logs and execution plans.
  • Connection pool: hikaricp_connections_pending > 0 and high acquisition time means threads wait for connections, often because transactions got longer or a call to a remote service now happens inside a transaction.
  • Downstream: a new remote call, missing timeout or retries amplifying latency.
  • Own code: synchronous logging, regex, serialisation of large objects, lock contention.

JVM: GC pause time and frequency (a new cache increasing allocation), CPU usage and container CPU throttling, heap pressure. Thread dumps (jcmd <pid> Thread.print, several seconds apart) show where threads block; Java Flight Recorder profiles and flame graphs (JFR, async-profiler) show hot methods, locks and allocation.

Close the loop: fix, verify on canary, then add a load or performance test in the pipeline and a p99 latency alert tied to the SLO.

How it works

  1. Confirm impact and scope on dashboards; correlate with deploy time.
  2. Roll back or halt the canary if users are affected.
  3. Review the diff, dependencies and configuration.
  4. Use traces to locate the slow span.
  5. Drill into DB, pool, downstream or JVM metrics accordingly.
  6. Capture thread dumps and JFR profiles to confirm.
  7. Fix, verify, add regression tests and alerts.

Example

# Thread dumps, three samples 5 s apart
for i in 1 2 3; do jcmd 1 Thread.print > /tmp/td-$i.txt; sleep 5; done
grep -c "HikariPool.getConnection" /tmp/td-*.txt

# 60-second Flight Recorder profile
jcmd 1 JFR.start duration=60s filename=/tmp/latency.jfr settings=profile
"http-nio-8080-exec-187" WAITING
   at com.zaxxer.hikari.pool.HikariPool.getConnection(HikariPool.java:181)
   at org.springframework.orm.jpa.JpaTransactionManager.doBegin(...)
-> 190 of 200 request threads waiting for a DB connection

Common mistakes

  • Debugging for an hour in production instead of rolling back.
  • Looking at average latency, which may barely move.
  • Ignoring dependency and configuration changes, focusing only on application code.
  • Fixing without adding a performance check, so the regression returns.

How to answer in the interview

"First I scope it on dashboards and APM: which endpoints, which instances, and does it line up exactly with the deploy? If users are badly affected I roll back first, which also confirms the cause. Then I review the diff, including dependency upgrades and config. I use traces to find the slow span: database, a downstream call or our code. For the database I check slow queries, missing indexes, N+1 and Hikari pending connections. For the JVM I look at GC pauses, CPU and throttling, and take thread dumps and a JFR profile to spot blocking or contention. After the fix I add a performance test in the pipeline and a p99 alert."

Likely follow-up questions

  • 200 threads waiting on HikariPool.getConnection? The pool is exhausted: connections held too long (slow queries, remote calls inside transactions, leaks) or the pool is too small for the concurrency.
  • Why roll back before diagnosing? It limits user impact and confirms causation; diagnosis can continue on a canary or staging.
  • How do you catch this before production? Canary analysis on p99 and a performance test stage.
