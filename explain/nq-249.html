What are the disadvantages of adding too many indexes?

Databases & SQL · concept · levels mid

In one line

Too many indexes slow every write (each must be maintained), consume disk and buffer-cache memory, can lead to worse plans and redundant choices, and add maintenance, locking and replication overhead, so index only what real queries need and drop unused or redundant indexes.

Detailed explanation

Write amplification: an INSERT into a table with ten indexes performs one heap or clustered-index write plus ten index insertions, each possibly causing page splits, plus write-ahead log records for all of them. UPDATE and DELETE are similar. In PostgreSQL, updating an indexed column prevents HOT (heap-only tuple) updates, so every index gets a new entry even for unrelated columns. Write-heavy tables like events, orders or audit logs feel this first, and the extra WAL also increases replication lag and backup size.

Storage and memory: indexes can easily exceed the table size. They compete with table data for the buffer pool / shared buffers; when hot indexes and data no longer fit in RAM, reads start hitting disk and everything slows.

Optimizer side effects: more indexes mean more plans to evaluate, and with overlapping indexes the planner may choose a less suitable one, especially if statistics are off. Redundant indexes, such as (customer_id) next to (customer_id, created_at), add cost with no benefit because the composite already serves the leading-column queries.

Operations: more indexes mean longer VACUUM, ANALYZE, rebuilds and index bloat in PostgreSQL; slower bulk loads; longer schema migrations; and in some engines more lock contention on hot index pages, for example monotonically increasing keys all inserting into the rightmost leaf.

The approach: design indexes from actual query patterns, prefer a few well-chosen composite and covering indexes over many single-column ones, and periodically review usage statistics.

How it works

  1. Each write must update all indexes on the table.
  2. Each index update writes pages and WAL/redo.
  3. Index pages occupy cache memory, evicting other data.
  4. The planner considers each index when building plans.
  5. Maintenance tasks scale with index count and size.

Example

-- PostgreSQL: indexes never scanned since stats reset
SELECT relname AS table_name, indexrelname AS index_name,
       idx_scan, pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE idx_scan = 0 AND indexrelname NOT LIKE '%_pkey'
ORDER BY pg_relation_size(indexrelid) DESC;

-- MySQL 8: sys schema
SELECT * FROM sys.schema_unused_indexes;
-- Oracle: ALTER INDEX idx_name MONITORING USAGE; then check DBA_INDEX_USAGE

-- Redundant: idx_orders_customer (customer_id) is covered by
-- idx_orders_customer_created (customer_id, created_at)
DROP INDEX CONCURRENTLY idx_orders_customer;

Common mistakes

  • Dropping an index flagged unused without checking replicas, monthly jobs or unique constraints.
  • Indexing every foreign key and filter column individually instead of designing composites.
  • Ignoring the write cost on high-ingest tables.
  • Forgetting that usage statistics reset on restart or stats reset.

How to answer in the interview

"Indexes aren't free. Every insert, update and delete must also modify each affected index, so write-heavy tables slow down and produce more I/O and log volume, which also increases replication lag. Each index takes disk space and competes for buffer cache memory, pushing out useful data. Many overlapping indexes can lead the optimizer to a worse plan, and they add maintenance like rebuilds, statistics and vacuum, plus some lock contention. So I index from actual query patterns, prefer a few well-designed composite indexes over many single-column ones, remove redundant ones, and use pg_stat_user_indexes or the sys schema to find unused indexes."

Likely follow-up questions

  • How to find unused indexes? pg_stat_user_indexes with idx_scan = 0, MySQL sys.schema_unused_indexes, Oracle index usage monitoring.
  • What is a redundant index? One whose columns are a leading prefix of another index.
  • Safe way to drop an index? Make it invisible first (MySQL/Oracle) or monitor, then DROP INDEX CONCURRENTLY.
