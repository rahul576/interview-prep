How do you run AI models on AKS with GPU node pools and KAITO?

Azure Kubernetes (AKS) · concept · levels mid, senior

In one line

Run AI models on AKS with GPU node pools (NVIDIA NC/ND sizes, drivers by AKS or the GPU operator), tainted so only GPU workloads land there and autoscaled to control cost; KAITO (Kubernetes AI Toolchain Operator) automates it: a Workspace resource provisions GPU nodes and deploys an OpenAI-compatible vLLM inference server for a preset open model, and supports fine-tuning and RAG.

Detailed explanation

GPU node pools use VM sizes like the NC A100/H100 or ND series. AKS can install NVIDIA drivers automatically, or you skip that and use the NVIDIA GPU Operator for drivers, device plugin and monitoring (DCGM exporter). Pods request GPUs with resources.limits: nvidia.com/gpu: 1. Because GPU VMs are expensive, pools are tainted (for example sku=gpu:NoSchedule) so ordinary pods cannot use them, and autoscaled, possibly to zero when idle. Capacity and quota for GPU families must be requested in advance per region.

Wiring a model server yourself means choosing a VM size that fits the model's memory, building an image with the model weights, configuring vLLM or another runtime, setting probes for long start-up times and exposing an API. KAITO, available as an AKS add-on, does this from one custom resource. A Workspace names a preset model (families such as Phi, Llama, Mistral, Qwen or DeepSeek variants) and an instance type; KAITO provisions matching GPU nodes (via node auto provisioning or its GPU provisioner), pulls the model image, and deploys an inference server using vLLM by default with an OpenAI-compatible API. It also supports fine-tuning with LoRA/QLoRA adapters (tuning workspaces that output adapters to a registry), and a RAG engine that adds retrieval in front of the model.

Self-hosting makes sense for data control, specific open models, fine-tuned variants, predictable high volume or offline/sovereign environments; managed APIs like Azure OpenAI are simpler for most teams.

How it works

  1. Enable the KAITO add-on (and OIDC issuer) on the cluster.
  2. Ensure GPU quota for the chosen VM family.
  3. Apply a Workspace with preset model and instance type.
  4. KAITO creates GPU nodes and the inference deployment and service.
  5. Call the OpenAI-compatible endpoint from apps inside the cluster or through a gateway.

Example

az aks update -g rg-ai -n aks-ai --enable-ai-toolchain-operator --enable-oidc-issuer
apiVersion: kaito.sh/v1beta1
kind: Workspace
metadata: { name: workspace-phi-4-mini }
resource:
  instanceType: Standard_NC24ads_A100_v4
  labelSelector:
    matchLabels: { apps: phi-4-mini }
inference:
  preset:
    name: phi-4-mini-instruct
kubectl run -it --rm curl --image=curlimages/curl -- \
  curl http://workspace-phi-4-mini/v1/chat/completions -H "Content-Type: application/json" \
  -d '{"model":"phi-4-mini-instruct","messages":[{"role":"user","content":"Hello"}]}'

Common mistakes

  • Leaving GPU pools untainted so ordinary pods waste them.
  • Underestimating GPU memory needed for model size and context length.
  • Short readiness probes for models that take minutes to load.
  • Forgetting GPU quota requests until launch day.

How to answer in the interview

"I add GPU node pools with NVIDIA sizes like NC or ND, with drivers from AKS or the GPU operator, taint them so only workloads requesting nvidia.com/gpu land there, and autoscale them, even to zero. KAITO, the AI toolchain operator add-on, simplifies serving open models: I create a Workspace naming a preset model, it provisions suitable GPU nodes, pulls the model and deploys a vLLM inference server with an OpenAI-compatible API. It also supports LoRA fine-tuning and a RAG engine."

Likely follow-up questions

  • Self-host vs Azure OpenAI? Self-host for open or fine-tuned models, data control or steady high volume; managed for simplicity.
  • How to share a GPU? MIG partitions or time-slicing for smaller workloads.
  • How to autoscale inference? HPA or KEDA on queue depth or request metrics, with node provisioning underneath.
