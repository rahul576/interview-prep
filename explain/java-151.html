Users report intermittent 500 errors from one microservice. How do you investigate?

Troubleshooting · scenario · levels mid, senior

In one line

Scope the errors with metrics by instance, endpoint, version and time, find the stack traces in logs via correlation ids, use traces to see whether a dependency fails or times out, check resource exhaustion (pools, timeouts, memory, GC) and one bad pod, then reproduce, fix, and add a test and an alert.

Detailed explanation

"Intermittent" means the failure depends on something that varies: an instance, traffic level, a specific input, a dependency's health or timing. The investigation is about finding that variable.

Scope with metrics: break the 5xx rate down by pod, endpoint, version, client and time. Patterns are revealing:

  • one pod out of five → a node or instance problem (bad configuration, memory pressure, full disk, a failed cache warm-up, a stale DNS entry or certificate);
  • one endpoint → a code path or a dependency only that endpoint uses;
  • correlated with traffic peaks → resource exhaustion;
  • started at a deployment or config change → the change;
  • periodic (every hour) → scheduled jobs, token or certificate refresh, batch loads.

Logs: filter for level ERROR on that service, group by exception type and message, and use the correlation or trace id from a failing request to see the full story across services. Make sure the error is logged once with the stack trace and the cause chain.

Traces: look at failed traces to see whether the 500 originates in this service or is propagated from a downstream timeout, connection refused or 503. A dependency failing occasionally without retries or a circuit breaker often looks like "our service is flaky".

Resources: intermittent 500s frequently come from exhaustion: Hikari "Connection is not available, request timed out", thread pool rejections, HTTP client connection pool limits, timeouts set too low for the dependency's p99, memory pressure and long GC pauses, file descriptor limits. Also check concurrency bugs: race conditions, non-thread-safe shared objects (e.g. SimpleDateFormat), optimistic locking failures not mapped to 409.

Reproduce: with the failing input, under load in staging, or by injecting the fault. Then fix, add a regression test, map expected errors to proper 4xx codes, and add an alert on the error rate.

How it works

  1. Break down error rate by pod, endpoint, version and time.
  2. Pull logs and stack traces for failing requests by trace id.
  3. Inspect traces for downstream failures and timeouts.
  4. Check pool saturation, GC, memory and node health.
  5. Reproduce with the identified condition.
  6. Fix, test, and alert on recurrence.

Example

# 5xx rate per pod: is it one instance?
sum by (pod) (rate(http_server_requests_seconds_count{app="orders", status=~"5.."}[5m]))

# Pool exhaustion?
max by (pod) (hikaricp_connections_pending{app="orders"})
ERROR trace.id=9f2c... o.h.e.j.s.SqlExceptionHelper :
  HikariPool-1 - Connection is not available, request timed out after 30000ms
  (total=10, active=10, idle=0, waiting=37)

Common mistakes

  • Looking only at aggregate error rate and missing that one pod is the culprit.
  • Restarting pods and declaring victory without finding the cause.
  • Swallowing the root cause in logs (log.error(e.getMessage())).
  • Returning 500 for client errors like validation or conflicts, polluting the signal.

How to answer in the interview

"First I scope it with metrics: error rate by instance, endpoint and version, and whether it lines up with traffic peaks or a deployment. Then I search the logs by trace id to get the stack traces behind the 500s, and use distributed traces to see whether a downstream dependency is failing or timing out. Intermittent errors are often resource exhaustion, so I check connection and thread pools, timeouts, memory and GC, and whether one pod is unhealthy. Once I can reproduce it, I fix it, add a regression test and an alert on the error rate so we catch it earlier next time."

Likely follow-up questions

  • Errors on one of five pods? Instance-specific: node issues, configuration drift, memory pressure, bad local state; compare it with healthy pods or drain it.
  • What if the 500 comes from a downstream service? Add timeouts, retries with backoff, circuit breaker and map it to 502/503.
  • How do you reproduce intermittent issues? Replay failing inputs, load test, or inject faults in staging.
