Design the Terraform for a production AKS cluster with workload identity, private networking and GitOps bootstrap.

Terraform · design · levels senior, lead

In one line

Use separate states for network, cluster and platform add-ons; make the cluster private or API-server-VNet-integrated with restricted access, use Entra ID with Azure RBAC and local accounts disabled, enable the OIDC issuer and workload identity with federated credentials per app, run zonal autoscaling node pools with a separate system pool, and bootstrap Flux or Argo CD for everything inside the cluster.

Detailed explanation

State layout. The network spoke (VNet, subnets, route tables to the hub firewall, private DNS links). The cluster state holds AKS, node pools, identities and role assignments. Platform add-ons (GitOps bootstrap, monitoring wiring) are separate so a broken add-on does not block cluster changes and plans stay fast.

Network and access. Either a private cluster (API server reachable only through a private endpoint) or API Server VNet Integration, which projects the API server into a delegated subnet. Access comes only from build agents in the VNet and admins via VPN or Bastion, or through authorised IP ranges if a public endpoint remains. Egress goes through the hub firewall with outbound_type = "userDefinedRouting".

Authentication. Entra ID integration with Azure RBAC for Kubernetes authorisation, admin groups instead of individuals, and local_account_disabled = true so nobody can use static cluster-admin certificates.

Workload identity. Enable oidc_issuer_enabled and workload_identity_enabled. For each application, Terraform creates a user-assigned managed identity, a federated identity credential whose subject is system:serviceaccount:<namespace>:<serviceaccount> and whose issuer is the cluster's OIDC URL, and the role assignments it needs (for example Key Vault Secrets User). Pods get Azure tokens without secrets.

Node pools. A small system pool (with only_critical_addons_enabled) for system pods, and user pools for workloads across three availability zones with autoscaling and ignore_changes on node counts.

GitOps bootstrap. Terraform installs the Flux extension with a flux_configuration pointing at the platform repo, or installs Argo CD and a root application. From then on, everything inside the cluster is managed by GitOps.

How it works

  1. Network state: spoke, subnets, routes, DNS links.
  2. Cluster state: AKS with private access, Entra ID RBAC, local accounts disabled.
  3. Enable OIDC issuer and workload identity.
  4. Node pools: system pool plus zonal autoscaling user pools.
  5. Per app: managed identity, federated credential, role assignments.
  6. Add-ons state: Flux extension and configuration pointing at Git.

Example

resource "azurerm_kubernetes_cluster" "main" {
  name                      = "aks-orders-prod"
  location                  = var.location
  resource_group_name       = var.rg_name
  dns_prefix                = "aks-orders-prod"
  private_cluster_enabled   = true
  local_account_disabled    = true
  oidc_issuer_enabled       = true
  workload_identity_enabled = true

  azure_active_directory_role_based_access_control {
    azure_rbac_enabled     = true
    admin_group_object_ids = [var.aks_admin_group_id]
  }
  default_node_pool {
    name                         = "system"
    vm_size                      = "Standard_D4s_v5"
    zones                        = ["1", "2", "3"]
    vnet_subnet_id               = var.nodes_subnet_id
    only_critical_addons_enabled = true
    auto_scaling_enabled         = true
    min_count                    = 3
    max_count                    = 5
  }
  network_profile {
    network_plugin      = "azure"
    network_plugin_mode = "overlay"
    outbound_type       = "userDefinedRouting"
  }
  identity { type = "SystemAssigned" }
}

resource "azurerm_federated_identity_credential" "orders_api" {
  name                = "orders-api"
  resource_group_name = var.rg_name
  parent_id           = azurerm_user_assigned_identity.orders_api.id
  issuer              = azurerm_kubernetes_cluster.main.oidc_issuer_url
  subject             = "system:serviceaccount:orders:orders-api"
  audience            = ["api://AzureADTokenExchange"]
}

resource "azurerm_kubernetes_cluster_extension" "flux" {
  name           = "flux"
  cluster_id     = azurerm_kubernetes_cluster.main.id
  extension_type = "microsoft.flux"
}

Common mistakes

  • Leaving local accounts enabled, bypassing Entra ID.
  • One shared identity for all workloads.
  • Deploying every application with Terraform instead of GitOps.
  • No ignore_changes on autoscaled node counts.

How to answer in the interview

"I split it into network, cluster and add-on states. The cluster is private or uses API server VNet integration, reachable only from build agents and admins. Authentication is Entra ID with Azure RBAC, local accounts disabled. I enable the OIDC issuer and workload identity, and each app gets a user-assigned identity with a federated credential bound to its namespace and service account, plus role assignments, all in Terraform. Node pools are a system pool and zonal autoscaling user pools. Finally Terraform installs the Flux extension or bootstraps Argo CD, so everything inside the cluster is GitOps."

Likely follow-up questions

  • Why stop Terraform at the GitOps bootstrap? In-cluster objects change often and are reconciled better by GitOps; Terraform plans stay small.
  • How do CI agents reach a private API server? Self-hosted agents in the VNet or az aks command invoke.
  • How are upgrades handled? Upgrade channel plus maintenance windows, or blue-green clusters for big jumps.
