How does distributed tracing work across services and Kafka messages?

Observability · concept · levels mid, senior

In one line

Each request gets a trace id; every operation is a span with its own id and a parent id; context propagation carries them across services in the W3C traceparent HTTP header and in Kafka record headers, instrumented by the OpenTelemetry agent or Micrometer Tracing, sampled and exported to Jaeger, Tempo or Zipkin.

Detailed explanation

A trace is the tree of all work done for one request. A span represents one unit of work (an HTTP server request, an outgoing call, a SQL query, a Kafka produce or consume) and records start time, duration, status, attributes (http.route, db.system, messaging.destination) and its parent span id. Together they show exactly where time was spent and where an error originated.

Propagation over HTTP: when service A calls B, the instrumented client injects traceparent: 00-<trace-id>-<parent-span-id>-<flags> (and optionally tracestate and baggage). B's server instrumentation extracts it and creates its span as a child. The flags byte carries the sampling decision so the whole trace is consistently kept or dropped.

Propagation over Kafka: the producer instrumentation writes the same context into record headers. The consumer extracts it and creates a consumer span. OpenTelemetry semantic conventions link the consumer span to the producer either as a child or through a span link, which is useful for batch consumption where one poll processes messages from many traces.

Instrumentation: the OpenTelemetry Java agent (-javaagent) auto-instruments Spring MVC, WebClient, RestClient, JDBC, Kafka clients and more. In Spring Boot 3, Micrometer Tracing with the OTel or Brave bridge instruments Spring components through the Observation API. Custom spans mark business steps.

Export and sampling: spans go via OTLP to an OpenTelemetry Collector and to a backend. Head sampling decides at the start (for example 10%); tail sampling in the Collector keeps all error or slow traces. The trace id in the MDC links logs to traces.

How it works

  1. Edge service starts a root span with a new trace id.
  2. Outgoing HTTP call injects traceparent; downstream extracts it.
  3. Kafka producer adds the context to record headers.
  4. Consumer extracts it and starts a consumer span (child or link).
  5. Each service exports finished spans via OTLP.
  6. The backend assembles spans by trace id into one timeline.

Common mistakes

  • Handing work to thread pools or @Async without propagating context, breaking the trace.
  • Custom HTTP clients or message wrappers that drop headers.
  • Sampling 100% in high-traffic production, driving up cost.
  • Not putting the trace id into logs, so traces and logs cannot be joined.

How to answer in the interview

"A trace has one trace id and is made of spans, each with its own id, a parent id, timing and attributes. Context travels between services in the W3C traceparent header, and for Kafka the producer writes it into record headers so the consumer continues the trace or links to it. I get instrumentation from the OpenTelemetry Java agent or from Micrometer Tracing in Spring Boot 3, which covers HTTP, JDBC and Kafka automatically, and I add custom spans for business steps. Spans are exported over OTLP to a Collector with head or tail sampling, then to Tempo or Jaeger, and the trace id goes in every log line."

Likely follow-up questions

  • Why do traces break with @Async? Context is thread-local; executors must be wrapped to propagate it (context propagation, TaskDecorator).
  • Child span or span link for Kafka? Links fit batches and long delays; child relations fit one-message processing.
  • What is baggage? Key-value context propagated with the trace, such as tenant id; keep it small and non-sensitive.
