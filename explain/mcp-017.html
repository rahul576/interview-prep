How does the connection lifecycle work in handshake-based MCP revisions such as 2025-11-25?

MCP Servers · concept · levels mid, senior

In one line

In handshake-based revisions, the client sends initialize (protocol version, capabilities, client info), the server replies with its chosen version and capabilities, the client sends notifications/initialized, then normal operation begins; over HTTP the server may assign an Mcp-Session-Id, and shutdown is simply closing the transport.

Detailed explanation

Up to and including 2025-11-25, every MCP connection began with an initialization phase that negotiated version and features.

1. initialize request. The client sends initialize with protocolVersion (the latest version it supports, e.g. "2025-11-25"), its capabilities (such as roots with listChanged, sampling, elicitation) and clientInfo (name, version).

2. initialize response. The server replies with the protocolVersion it will use, its capabilities (tools with listChanged, resources with subscribe and listChanged, prompts, logging, completions), serverInfo and optional instructions describing how to use the server. Version negotiation: if the server supports the requested version it must respond with the same one; otherwise it responds with another version it supports, normally its latest, and if the client does not support that, it should disconnect.

3. initialized notification. The client sends notifications/initialized. Before this, neither side should send normal requests (except pings and logging).

Operation. Each side uses only features the other advertised: a client must not call resources/subscribe if the server did not declare subscribe. Over HTTP, clients also send the MCP-Protocol-Version header on subsequent requests (from 2025-06-18).

Sessions. With Streamable HTTP, the server may return an Mcp-Session-Id header in the initialize response; the client must include it on all later requests. The server can expire it (returning 404), after which the client re-initialises. Clients can end a session with an HTTP DELETE.

Shutdown has no special message: for stdio the client closes the server's stdin and, if needed, terminates the process; for HTTP it closes connections or deletes the session.

How it works

  1. Client → initialize {version, capabilities, clientInfo}.
  2. Server → result {version, capabilities, serverInfo, instructions}.
  3. Client checks version compatibility; aborts if unsupported.
  4. Client → notifications/initialized.
  5. Requests flow, limited to negotiated capabilities; HTTP requests carry session and version headers.
  6. Close transport to shut down.

Example

{"jsonrpc":"2.0","id":1,"method":"initialize","params":{
  "protocolVersion":"2025-11-25",
  "capabilities":{"elicitation":{},"roots":{"listChanged":true}},
  "clientInfo":{"name":"my-agent","version":"1.4.0"}}}

{"jsonrpc":"2.0","id":1,"result":{
  "protocolVersion":"2025-11-25",
  "capabilities":{"tools":{"listChanged":true},"resources":{"subscribe":true}},
  "serverInfo":{"name":"tickets","version":"2.3.1"}}}

{"jsonrpc":"2.0","method":"notifications/initialized"}

Common mistakes

  • Sending requests before initialized.
  • Using features the peer did not advertise.
  • Holding session state in memory on one replica without sticky routing.
  • Not handling 404 for an expired session by re-initialising.

How to answer in the interview

"Every connection starts with initialize: the client sends the protocol version it wants, its capabilities, like elicitation or roots, and client info. The server replies with the version it will use, which is the same if it supports it, otherwise one it does support so the client can decide whether to continue, plus its capabilities, like tools with listChanged or resource subscriptions, and server info. Then the client sends an initialized notification and normal operation starts, with each side only using features the other advertised. Over HTTP the server may assign an Mcp-Session-Id that the client sends on later requests. Shutdown is just closing the transport."

Likely follow-up questions

  • Problems with sessions when scaling? Requests must reach the replica holding the session, or state must be shared; restarts lose sessions.
  • What is instructions for? Server-provided guidance the host may add to the model's context.
  • Is there a ping? Yes, ping requests check liveness.
