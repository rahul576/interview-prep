How do you sandbox local MCP servers to limit damage if one is malicious or compromised?

MCP Servers · concept · levels mid, senior

In one line

Sandbox local servers by running them in containers or lightweight VMs, mounting only the directories they need (read-only where possible), restricting network egress to required hosts, running as non-root with dropped capabilities, and passing only the credentials that server needs.

Detailed explanation

By default a local stdio server is just a process running as you. If it is malicious, compromised by a supply-chain attack, or tricked through prompt injection into running something harmful, it can read your SSH keys and cloud credentials, modify source code and send everything anywhere on the internet. Sandboxing reduces that blast radius to what the server legitimately needs.

Isolation boundary. Containers (Docker, Podman) are the usual choice; they work over stdio with docker run -i. For higher-risk servers, such as ones that execute code or browse arbitrary websites, lightweight VMs (Firecracker-style micro-VMs, or desktop sandboxes) give a stronger boundary than a shared kernel.

Filesystem. Mount only what is needed. A filesystem server gets the project directory, read-only if it only reads. Never mount the home directory, ~/.ssh, ~/.aws or the Docker socket.

Network egress. This is as important as filesystem limits. Restricting outbound traffic to the specific hosts a server needs (for example api.github.com) blocks exfiltration to arbitrary destinations, which is the end goal of most attacks. Servers that need no network should get --network none.

Privileges. Run as a non-root user, drop Linux capabilities, use a read-only root filesystem, no --privileged, and set memory and CPU limits.

Credentials. Pass only the scoped token that server needs as an environment variable, not the user's whole environment or credential files.

Some hosts and tools offer built-in sandboxing for MCP servers, which makes consistent policy across an organisation much easier than relying on every developer's docker flags.

How it works

  1. Package the server as a container image pinned by digest.
  2. Define mounts: project dir only, read-only by default.
  3. Attach the container to a network with an egress proxy allowlist, or no network.
  4. Run as non-root, drop capabilities, set resource limits.
  5. Inject one scoped secret; nothing else from the host environment.

Example

docker run -i --rm \
  --user 10001:10001 \
  --read-only --cap-drop ALL --security-opt no-new-privileges \
  --memory 512m --pids-limit 128 \
  -v "$PWD":/workspace:ro \
  --network mcp-egress-github \
  -e GITHUB_TOKEN="$GH_FINEGRAINED_RO" \
  ghcr.io/github/github-mcp-server@sha256:<digest> stdio

The mcp-egress-github network routes through a proxy that only allows api.github.com.

Common mistakes

  • Mounting $HOME so the server "can find things".
  • Default bridge networking with unrestricted internet access.
  • Mounting /var/run/docker.sock, which is root on the host.
  • Passing the full host environment with --env-file containing every secret.

How to answer in the interview

"Local servers run with the user's permissions by default, so a malicious one can read anything and contact anywhere. I sandbox them in containers, or lightweight VMs for higher-risk ones, so they only see what's mounted: a filesystem server gets just the project directory, read-only if it doesn't need to write. Network egress is restricted to the hosts the server needs, like the GitHub API, which blocks exfiltration. Containers run as non-root with dropped capabilities and no privileged mode, and each server only gets the scoped credentials it needs, not my whole environment. Where hosts offer built-in sandboxing I prefer that, because it's easier to apply consistently across an organisation."

Likely follow-up questions

  • Why is egress as important as filesystem? Reading data is harmless if it cannot leave; exfiltration needs a network path.
  • Container vs VM? VMs give a stronger boundary for servers that run untrusted code.
  • What about servers that need GUI or browser? Run the browser inside the sandbox too, with egress controls.
