What is Azure Kubernetes Fleet Manager used for?

Azure Kubernetes (AKS) · concept · levels senior, lead

In one line

Azure Kubernetes Fleet Manager manages many AKS clusters as a fleet: mainly orchestrated update runs across clusters in stages, groups and wait times (or automatic via auto-upgrade profiles), plus multi-cluster resource propagation from a hub and multi-cluster load balancing.

Detailed explanation

Once an organisation has dozens of clusters across regions and subscriptions, upgrading them safely becomes a coordination problem. Teams used to write scripts to upgrade dev first, then one production cluster, then the rest, checking health between steps. Fleet Manager makes that a managed feature.

You create a fleet resource and add clusters as members, each assigned to an update group (for example dev, canary, prod-eu, prod-us).

Update strategies define stages executed in order, each containing groups updated together, with after-stage wait times to observe health. An update run applies a Kubernetes version upgrade (full or control plane only) or a node image update following that strategy. If a member fails, the run stops, so a bad version does not spread. Auto-upgrade profiles connect a release channel (such as Stable) to a strategy, so new versions roll through the fleet automatically.

Resource propagation: with a hub cluster, you define ClusterResourcePlacement objects that select Kubernetes resources (namespaces, RBAC, configmaps, CRDs) and place them onto member clusters by name, labels or policy, including spreading across a number of clusters. This is useful for baseline configuration and multi-cluster apps.

Multi-cluster networking: layer 4 load balancing of a service across member clusters using ServiceExport and MultiClusterService resources.

Fleet Manager complements GitOps: Flux or Argo CD delivers applications, while Fleet orchestrates platform upgrades.

How it works

  1. Create a fleet (with or without a hub).
  2. Join clusters as members with update groups.
  3. Define an update strategy with stages and waits.
  4. Start an update run or configure an auto-upgrade profile.
  5. Monitor run progress; failures halt later stages.

Example

az fleet create -g rg-platform -n fleet-prod -l westeurope
az fleet member create -g rg-platform -f fleet-prod -n aks-dev \
  --member-cluster-id $DEV_ID --update-group dev
az fleet member create -g rg-platform -f fleet-prod -n aks-prod-eu1 \
  --member-cluster-id $EU1_ID --update-group canary

az fleet updatestrategy create -g rg-platform -f fleet-prod -n staged --stages stages.json
az fleet updaterun create -g rg-platform -f fleet-prod -n upgrade-1-33 \
  --upgrade-type Full --kubernetes-version 1.33.2 --update-strategy-name staged
az fleet updaterun start -g rg-platform -f fleet-prod -n upgrade-1-33

Common mistakes

  • Putting all production clusters in one stage with no wait time.
  • Skipping health checks between stages.
  • Using Fleet for app delivery that GitOps handles better.
  • Not aligning maintenance windows with update runs.

How to answer in the interview

"Fleet Manager groups many AKS clusters into one fleet. The main use is orchestrated updates: I define a strategy with stages, such as dev, a canary production cluster, then the remaining production clusters, with wait times between them, and an update run upgrades Kubernetes or node images in that order, stopping on failure. Auto-upgrade profiles can make it continuous. With a hub cluster, it also propagates resources like namespaces and RBAC to members using placement policies, and offers multi-cluster layer 4 load balancing. It replaces custom upgrade scripts."

Likely follow-up questions

  • How to combine with GitOps? Fleet for platform upgrades and baseline config, Flux or Argo CD for applications.
  • What if one cluster fails? The run stops; fix it and resume or skip the member.
  • Does every fleet need a hub? No, update orchestration works without one.
