What are check blocks in Terraform, and how do they differ from preconditions and postconditions?

Terraform · concept · levels mid, senior

In one line

A check block (Terraform 1.5+) runs assertions after plan and apply that produce warnings, not errors, and can use scoped data sources to probe real endpoints; preconditions and postconditions are hard guarantees that fail the run.

Detailed explanation

Terraform offers several ways to validate assumptions, and they differ in where they live and what happens on failure.

Variable validation checks inputs. Preconditions and postconditions live inside the lifecycle block of a resource, data source or output. A precondition checks assumptions before Terraform acts on the object, for example "the selected AMI must be x86_64"; a postcondition checks the result, for example "the created bucket must have versioning enabled". If they fail, the plan or apply fails, and with postconditions downstream resources are not touched. They are the right tool for contracts that must never be violated.

A check block is a top-level block containing one or more assert conditions with error messages. It is evaluated at the end of every plan and apply, and a failed assertion produces a warning, so it never blocks a deployment. Inside a check you can declare a scoped data source, visible only within that check, for example an http data source that calls the new website's health endpoint, or a TLS certificate data source to check expiry. If the scoped data source itself fails, that is also only a warning. This makes checks ideal for validating overall behaviour of the infrastructure, functional smoke tests and early warnings, things that should be noticed but should not stop an unrelated change.

In HCP Terraform, health assessments include continuous validation, which re-evaluates checks (and postconditions) on a schedule and reports failures, alongside drift detection.

How it works

  1. Terraform finishes planning or applying the normal graph.
  2. Scoped data sources inside checks are read.
  3. Each assert condition is evaluated.
  4. Failures print warnings with your message; the run still succeeds.
  5. Pre/postconditions are evaluated when their resource is planned or applied and fail the run if false.

Example

check "website_health" {
  data "http" "home" {
    url = "https://${aws_lb.web.dns_name}/healthz"
  }
  assert {
    condition     = data.http.home.status_code == 200
    error_message = "Health endpoint returned ${data.http.home.status_code}"
  }
}

resource "aws_instance" "app" {
  ami           = data.aws_ami.app.id
  instance_type = var.instance_type
  lifecycle {
    precondition {
      condition     = data.aws_ami.app.architecture == "x86_64"
      error_message = "The AMI must be x86_64."
    }
  }
}

Common mistakes

  • Using checks for rules that must block deployment.
  • Using postconditions for health checks of slow-starting services, which fail applies randomly.
  • Ignoring check warnings in CI output.

How to answer in the interview

"A check block, added in Terraform 1.5, contains assertions evaluated at the end of plan and apply, and a failure produces a warning, not an error, so it never blocks a deployment. Inside a check I can declare a scoped data source, like an http call to the new site's health endpoint or a certificate expiry check, and assert on it. That makes checks good for validating that the infrastructure works overall. Preconditions and postconditions live in a resource, data source or output lifecycle and are hard guarantees: if they fail, the run fails, which is right for assumptions like the AMI must be x86. HCP Terraform can run checks continuously as health assessments."

Likely follow-up questions

  • When would you deliberately choose a check? A health endpoint that may take minutes to come up; you want visibility without failing the apply.
  • Can checks reference resources? Yes, any resource or data source in the module.
  • Where would you test modules instead? terraform test with .tftest.hcl files and run blocks.
