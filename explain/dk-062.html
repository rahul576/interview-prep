What are rootless Docker and user namespace remapping?

Docker · concept · levels senior

In one line

User namespace remapping (userns-remap) maps container root to an unprivileged high host UID range, while rootless Docker runs the daemon and all containers as an ordinary user; both mean container root is not host root, at the cost of limits on low ports, some storage, networking and cgroup features.

Detailed explanation

In a default installation the daemon runs as root and UID 0 in the container is UID 0 on the host. Capabilities, seccomp and LSM profiles restrict that root, but if a process escapes through a kernel or runtime bug, it lands on the host as real root.

User namespace remapping changes the mapping. With "userns-remap": "default" in daemon.json, Docker creates a dockremap user and uses a subordinate UID range from /etc/subuid and /etc/subgid, for example 165536-231071. Container UID 0 becomes host UID 165536, UID 1000 becomes 166536, and so on. An escaped process has no privileges on host files it does not own. The daemon itself still runs as root. Downsides: it is a daemon-wide setting, image layers are stored separately per remapping, --privileged and host namespace sharing need --userns=host, and bind-mounted host files appear owned by nobody or unexpected UIDs, so permissions must be adjusted.

Rootless mode goes further: dockerd, containerd and all containers run as a normal user inside a user namespace created by RootlessKit. Networking uses slirp4netns or pasta user-space networking, which can be slower, and storage uses native overlay (on recent kernels) or fuse-overlayfs. Limitations include binding ports below 1024 (unless you lower net.ipv4.ip_unprivileged_port_start or grant a capability), resource limits needing cgroup v2 with systemd delegation, some network drivers such as macvlan or overlay being unavailable, and AppArmor or some storage drivers not working. In exchange, compromise of the daemon or a container breakout yields only that user's privileges. Kubernetes has comparable support through user namespaces for pods (hostUsers: false).

How it works

  1. Host defines subordinate UID/GID ranges for a user.
  2. The runtime creates a user namespace with that mapping.
  3. Inside, the process sees itself as UID 0.
  4. On the host, it is a high unprivileged UID.
  5. Rootless mode also runs the daemon itself inside that namespace.

Example

{ "userns-remap": "default" }
grep dockremap /etc/subuid           # dockremap:165536:65536
docker run -d --name t alpine sleep 600
ps -o user,pid,cmd -C sleep          # runs as 165536 on the host

# Rootless mode for user alice
dockerd-rootless-setuptool.sh install
systemctl --user enable --now docker
export DOCKER_HOST=unix:///run/user/$(id -u)/docker.sock

Common mistakes

  • Enabling remapping on an existing host and "losing" images (stored per remap).
  • Forgetting bind mount ownership changes.
  • Expecting rootless performance to match rootful networking.
  • Believing user namespaces make --privileged safe.

How to answer in the interview

"Normally the daemon runs as root and root in a container is UID 0 on the host too. With userns-remap in daemon.json, UID 0 in the container maps to a high unprivileged host UID range, so a process that escapes has no real privileges. Rootless mode goes further: the daemon and all containers run as an ordinary user, with user-space networking like slirp4netns or pasta. Limitations include ports below 1024, some storage and network drivers, cgroup delegation and performance. Both greatly reduce the impact of a breakout."

Likely follow-up questions

  • Why do bind-mounted files show strange owners? Host UIDs outside the mapped range appear as nobody inside, and container UIDs are offset on the host.
  • Kubernetes equivalent? User namespaces for pods with hostUsers: false.
  • How do you bind port 80 in rootless mode? Lower ip_unprivileged_port_start or use a port mapping above 1024.
