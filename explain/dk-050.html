What do common container exit codes mean?

Docker · concept · levels mid

In one line

0 = normal exit, 1 or other small codes = application error, above 128 = killed by a signal (128 + signal number): 137 SIGKILL (often OOM), 143 SIGTERM (normal stop), 139 SIGSEGV; 125/126/127 are Docker or command errors.

Detailed explanation

A container's exit code is simply the exit status of its main process, so it follows Unix conventions and immediately narrows down where to look.

0 means the process finished successfully. For a batch job that is expected; for a web service it is suspicious, because it means the server process ended on purpose, often due to backgrounding or a script that finished. 1 and other small codes (2, 3...) are chosen by the application: an unhandled exception, invalid configuration, failed connection. docker logs tells you which.

Codes above 128 mean the process was terminated by a signal, and the code is 128 plus the signal number. 137 = 128 + 9 (SIGKILL): either the kernel OOM killer after the memory limit was exceeded, a docker kill, or Docker escalating after docker stop timed out because the app ignored SIGTERM. 143 = 128 + 15 (SIGTERM): the process was asked to stop and exited because of it, the normal result of docker stop for an app without a custom handler exit code. 139 = 128 + 11 (SIGSEGV), a segmentation fault, typically in native code or because of an incompatible library (for example glibc binaries on musl). 134 is SIGABRT, for example a JVM or C++ abort.

Codes 125, 126 and 127 come from Docker or the shell before your app runs: 125 means the docker run command itself failed (bad flag, daemon error); 126 means the command cannot be executed (permission denied, missing execute bit); 127 means command not found, usually a typo, a missing binary in a slim image, or Windows line endings in a script's shebang.

How it works

  1. The main process exits or is killed.
  2. The runtime records the wait status.
  3. Docker stores State.ExitCode, State.OOMKilled and State.Error.
  4. Restart policies and orchestrators react to the code.
  5. Kubernetes shows the same code with a reason such as OOMKilled.

Example

docker ps -a --format '{{.Names}}\t{{.Status}}'
docker inspect -f 'code={{.State.ExitCode}} oom={{.State.OOMKilled}} err={{.State.Error}}' api
dmesg -T | grep -i 'killed process'        # kernel OOM messages on the host
kubectl get pod api-7d9 -o jsonpath='{.status.containerStatuses[0].lastState.terminated}'

Common mistakes

  • Assuming every 137 is an OOM kill.
  • Treating 143 as a failure in alerts.
  • Ignoring exit 0 for services that should keep running.
  • Not checking the kernel log when OOMKilled is unclear.

How to answer in the interview

"Exit code 0 means the main process finished successfully, normal for jobs but suspicious for a service. 1 or another small code is an application error, so I check docker logs. Codes above 128 mean killed by a signal, 128 plus the signal number: 137 is SIGKILL, typically the OOM killer or a kill after the stop timeout, and docker inspect shows OOMKilled; 143 is SIGTERM from a normal docker stop; 139 is a segfault. 125 means Docker itself failed to run the container, 126 the command wasn't executable and 127 the command wasn't found."

Likely follow-up questions

  • OOM kill vs docker kill, both 137? Check State.OOMKilled and the host kernel log.
  • Why might an app always exit 137 on stop? It ignores SIGTERM, so Docker sends SIGKILL after the timeout.
  • What does Kubernetes show? lastState.terminated with exit code and reason.
