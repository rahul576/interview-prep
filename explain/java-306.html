What is the difference between @RequestParam, @PathVariable, @RequestBody and @RequestHeader?

Spring Framework · concept · levels entry, mid

In one line

@PathVariable binds a URI path segment that identifies a resource, @RequestParam binds query string or form parameters (with required/defaultValue), @RequestBody deserialises the body (usually JSON via Jackson, with @Valid), and @RequestHeader reads HTTP headers.

Detailed explanation

These annotations tell Spring MVC's argument resolvers where each method parameter comes from.

@PathVariable maps a placeholder in the URI template: in /orders/{orderId}/items/{itemId} both ids are path variables. They identify which resource you mean, are required by default, and are converted to the parameter type (long, UUID, enums), with a failed conversion producing 400. Regex constraints like {id:\\d+} are possible.

@RequestParam reads ?status=OPEN&page=2 or form-encoded fields. It suits filtering, sorting, pagination and options: things that refine a collection rather than identify a resource. Use required = false, Optional<T> or defaultValue = "0". Repeated parameters bind to a List, and Map<String,String> captures all. For pagination Spring Data's Pageable resolver handles page, size, sort.

@RequestBody takes the whole body and converts it with an HttpMessageConverter selected by the Content-Type, typically Jackson for application/json, into a DTO or record. Only one body per request. Combine with @Valid (or @Validated with groups) for Bean Validation; malformed JSON gives HttpMessageNotReadableException → 400.

@RequestHeader reads a header such as Idempotency-Key, X-Correlation-Id, Accept-Language or If-Match for optimistic locking. @RequestHeader HttpHeaders gives all of them. (Authorization headers are better left to Spring Security.)

All of them support name, required and, except @RequestBody, defaultValue. Since Spring 6.1, constraint annotations directly on @RequestParam or @PathVariable (like @Min(1)) are validated by built-in method validation.

ResponseEntity is the response-side counterpart, letting you set status and headers, for example 201 with Location or 304 with an ETag.

How it works

  1. HandlerMapping matches the URI template and extracts path variables.
  2. Argument resolvers check each parameter's annotation.
  3. Values are converted with the ConversionService or a message converter.
  4. Validation runs; failures become 400 responses.
  5. The method executes with typed arguments.

Example

@RestController
@RequestMapping("/api/customers/{customerId}/orders")
class CustomerOrderController {

    @GetMapping
    Page<OrderDto> list(@PathVariable UUID customerId,
                        @RequestParam(defaultValue = "OPEN") Status status,
                        @RequestParam(required = false) LocalDate from,
                        Pageable pageable) { ... }

    @PostMapping
    ResponseEntity<OrderDto> create(@PathVariable UUID customerId,
                                    @Valid @RequestBody NewOrder body,
                                    @RequestHeader("Idempotency-Key") String idempotencyKey) {
        OrderDto created = service.create(customerId, body, idempotencyKey);
        return ResponseEntity.created(URI.create("/api/customers/" + customerId + "/orders/" + created.id()))
                             .body(created);
    }
}

Common mistakes

  • Putting filters in the path or ids in the query inconsistently.
  • Sending sensitive data like passwords in query parameters, which end up in logs.
  • Two @RequestBody parameters in one method.
  • Forgetting @Valid.

How to answer in the interview

"@PathVariable binds a segment of the URI path, like the id in /orders/{id}, and identifies the resource. @RequestParam binds query string or form parameters, typically for filtering, sorting and pagination, and supports required and default values. @RequestBody deserialises the request body, usually JSON through Jackson, into a DTO, and I combine it with @Valid. @RequestHeader reads headers such as an idempotency key or correlation id. On the way back, ResponseEntity lets me control the status and headers, like 201 with a Location header."

Likely follow-up questions

  • When would you use ResponseEntity instead of returning the object? When the status or headers vary: 201, 204, 304, Location, ETag.
  • How do you make a request parameter optional? required = false, Optional<T> or defaultValue.
  • Why not GET with a body? Semantics are undefined and many proxies drop it; use query params or POST a search.
