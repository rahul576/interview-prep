What is a container registry, and how do you tag and version images?

Docker · concept · levels entry, mid

In one line

A container registry stores and distributes images (Docker Hub, ECR, ACR, Artifact Registry, GHCR, Harbor); images are named registry/repository:tag, production should use immutable version tags (git SHA, semantic version) or digests rather than latest, and private registries add access control, scanning and retention.

Detailed explanation

A registry is to images what a package repository is to libraries. Docker Hub is the default public registry; companies use private ones such as Amazon ECR, Azure Container Registry, Google Artifact Registry, GitHub Container Registry or self-hosted Harbor and Artifactory. All speak the OCI Distribution API, so docker push/pull work the same everywhere.

A full image reference is registry/repository:tag, for example myacr.azurecr.io/orders:1.4.2. If the registry is omitted, Docker assumes docker.io, and if the tag is omitted, it assumes latest.

A tag is a mutable pointer: anyone with push rights can move 1.4.2 or latest to a different image. latest is just a default name, not "the newest", and in production it makes it impossible to know exactly what runs, causes different nodes to run different versions, and breaks reliable rollback. A digest (@sha256:...) is the hash of the image manifest and is immutable by definition.

A good scheme: CI tags every build with the git commit SHA (traceable to the code), releases also get a semantic version like 1.4.2, and release repositories enable tag immutability so tags can't be overwritten. Deployments reference the version tag, and ideally pin the digest too. Private registries add IAM/RBAC (CI can push, clusters can only pull), vulnerability scanning on push, signing, replication and lifecycle policies that delete old untagged builds.

How it works

  1. CI builds the image and tags it, for example orders:3f9c2ab and orders:1.4.2.
  2. docker login with CI credentials, then docker push.
  3. The registry stores layers and the manifest, scans it and records the digest.
  4. Deployments pull by tag or digest; nodes authenticate with pull-only credentials.
  5. Lifecycle rules clean up old builds.

Example

GIT_SHA=$(git rev-parse --short HEAD)
docker build -t myacr.azurecr.io/orders:$GIT_SHA -t myacr.azurecr.io/orders:1.4.2 .
docker push myacr.azurecr.io/orders:$GIT_SHA
docker push myacr.azurecr.io/orders:1.4.2
docker buildx imagetools inspect myacr.azurecr.io/orders:1.4.2   # shows the digest
# deploy: image: myacr.azurecr.io/orders:1.4.2@sha256:7d2e...

Common mistakes

  • Deploying latest to production.
  • Reusing a version tag for a different build.
  • Using Docker Hub directly from production nodes and hitting rate limits.
  • Giving clusters push rights to the registry.

How to answer in the interview

"A registry stores and distributes images: Docker Hub publicly, or private ones like ECR, ACR, GHCR or Harbor. An image name is registry/repository:tag, for example myacr.azurecr.io/orders:1.4.2. I never deploy latest in production, because tags are mutable pointers and latest tells you nothing about what's running or how to roll back. Instead CI tags each build with the git SHA and releases with a semantic version, release tags are immutable, and deployments can pin the digest, which is the content hash and can never change. The private registry adds access control, with CI pushing and clusters pull-only, scanning on push and retention policies."

Likely follow-up questions

  • Tag vs digest? A tag is a movable name; a digest is the immutable hash of the manifest.
  • Why include the git SHA? It links the running image to the exact commit for debugging and audits.
  • How do Kubernetes nodes authenticate to a private registry? imagePullSecrets or cloud workload identity (for example an ECR or ACR node role).
