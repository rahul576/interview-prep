Compare virtual threads with reactive programming for scalable I/O.

Concurrency · concept · levels senior, lead

In one line

Both target high-concurrency I/O without one expensive platform thread per request: virtual threads keep the simple blocking style and normal tooling, while reactive programming is non-blocking with backpressure and stream operators, at the cost of complexity.

Detailed explanation

The classic thread-per-request model breaks down because platform threads are OS threads: each costs memory for its stack and a context switch, so a few thousand is a practical limit, while most of their time is spent waiting on I/O.

Reactive programming (Project Reactor, Spring WebFlux, RxJava) solves this by never blocking: a small number of event-loop threads handle many requests, and work is expressed as Mono/Flux pipelines that resume when data arrives. It brings real strengths: backpressure (a slow consumer can signal demand), rich operators for streaming, merging, retrying and timing out, and efficient handling of long-lived streams like server-sent events. The costs are a different programming model, the need for non-blocking drivers end to end (R2DBC instead of JDBC), harder debugging, and stack traces full of operator frames.

Virtual threads (final in Java 21) solve the same problem in the runtime: millions of cheap threads scheduled by the JVM onto a few carrier threads. When a virtual thread blocks on I/O, it unmounts and the carrier runs something else. Code stays plain imperative Java with JDBC, try/catch, debuggers, profilers and readable stack traces. Since Java 24 (JEP 491), synchronized no longer pins virtual threads in most cases, removing the main early caveat.

The choice: for typical request/response services, virtual threads give most of the scalability with far less complexity. Reactive still wins for streaming, fine-grained backpressure, and teams already invested in a reactive stack.

How it works

  1. Platform thread model: one OS thread per request, blocked during I/O.
  2. Reactive: requests become event-driven pipelines on a few event-loop threads; no code may block.
  3. Virtual threads: each request gets a virtual thread; blocking calls park it and free the carrier.
  4. Limits move: the bottleneck becomes downstream resources (DB connections, APIs), not threads.
  5. Decide per service based on streaming needs, library support and team skills.

Example

// Virtual threads: plain blocking code, scales to many concurrent requests
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    Future<User> user = exec.submit(() -> userRepo.findById(id));   // JDBC
    Future<List<Order>> orders = exec.submit(() -> orderClient.list(id));
    return new Profile(user.get(), orders.get());
}

// Reactive (WebFlux): non-blocking composition
Mono<Profile> profile = Mono.zip(userRepo.findById(id), orderClient.list(id).collectList())
        .map(t -> new Profile(t.getT1(), t.getT2()));

In Spring Boot 3.2+, spring.threads.virtual.enabled=true runs request handling on virtual threads.

Common mistakes

  • Assuming virtual threads make CPU-bound code faster; they only help waiting.
  • Removing connection pool limits because "threads are free".
  • Pooling virtual threads; create one per task instead.
  • Calling blocking code inside a reactive pipeline on the event loop.

How to answer in the interview

"Both solve the same problem: lots of concurrent I/O-bound work without one expensive platform thread per request. Virtual threads keep the simple blocking style, so I keep JDBC, normal stack traces and debugging, and the JVM parks the virtual thread during I/O. Reactive with Reactor or WebFlux is non-blocking and gives backpressure and powerful stream operators, which is great for streaming, but it is harder to write and debug and needs non-blocking libraries everywhere. For new request-response services on Java 21 or later I prefer virtual threads, and I use reactive for streaming use cases or where a reactive stack already exists."

Likely follow-up questions

  • Does adopting virtual threads remove the need for connection pool limits? No; the database still has finite connections, so keep pool limits and add semaphores for other downstreams.
  • What is pinning? A virtual thread that cannot unmount from its carrier while blocked, historically inside synchronized blocks or native calls; mostly fixed for synchronized in Java 24.
  • Are virtual threads good for CPU-heavy work? No; use a bounded platform pool sized near the core count.
