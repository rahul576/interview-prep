What is CompletableFuture, and how does it support asynchronous programming?

Concurrency · concept · levels mid

In one line

CompletableFuture (Java 8) is a Future you can complete and compose: start work with supplyAsync/runAsync, chain non-blocking callbacks (thenApply, thenCompose, thenCombine, thenAccept), handle errors with exceptionally/handle/whenComplete, and coordinate with allOf/anyOf and timeouts.

Detailed explanation

A plain Future only lets you block with get(). CompletableFuture implements both Future and CompletionStage, which turns asynchronous results into a pipeline: you describe what should happen when a value arrives, and threads are not blocked waiting.

Starting work: supplyAsync(supplier) returns a value; runAsync(runnable) does not. Without an executor argument they use the ForkJoinPool.commonPool(), which is sized for CPU work and shared JVM-wide, so for blocking I/O you should pass your own executor. You can also create an incomplete future and finish it yourself with complete(value) or completeExceptionally(ex), which is handy for bridging callback-based APIs.

Composing:

  • thenApply(fn): transform the result (like map).
  • thenAccept(consumer) / thenRun: consume it, end of chain.
  • thenCompose(fn): chain another async call returning a CompletableFuture (like flatMap), avoiding nested futures.
  • thenCombine(other, bifn): merge two independent results.
  • allOf(...) / anyOf(...): wait for all or the first of many.

Each has an ...Async variant that runs the callback on an executor rather than the completing thread.

Errors propagate down the chain, skipping normal stages, until handled with exceptionally (recover), handle (always runs, sees value or exception) or whenComplete (observe, e.g. log). Timeouts came in Java 9: orTimeout fails with TimeoutException, completeOnTimeout supplies a default.

The result is that you can call several services in parallel and combine the results with very little thread usage. Note: with virtual threads (Java 21+), simple blocking code is often an easier alternative for request/response fan-out.

How it works

  1. supplyAsync submits the supplier to an executor; returns an incomplete future immediately.
  2. You register dependent stages; each returns a new future.
  3. When the supplier finishes, the future completes and triggers dependent stages.
  4. Exceptions complete the future exceptionally and propagate to handlers.
  5. At the boundary, join() or return the future to a framework that supports it (Spring MVC accepts CompletableFuture return values).

Example

ExecutorService io = Executors.newFixedThreadPool(20);

CompletableFuture<Customer> customer = CompletableFuture.supplyAsync(() -> crm.find(id), io);
CompletableFuture<BigDecimal> balance = CompletableFuture.supplyAsync(() -> ledger.balance(id), io);

CompletableFuture<Statement> statement = customer
        .thenCombine(balance, Statement::new)                    // merge independent results
        .thenCompose(s -> pdfService.renderAsync(s))             // another async call
        .orTimeout(3, TimeUnit.SECONDS)
        .exceptionally(ex -> Statement.unavailable(id, ex))      // fallback
        .whenComplete((s, ex) -> metrics.record("statement", ex == null));

return statement;          // e.g. returned from a Spring MVC controller

Common mistakes

  • Using the common pool for blocking I/O.
  • Calling get()/join() right after supplyAsync, making it synchronous.
  • Using thenApply with a function returning a future, giving CompletableFuture<CompletableFuture<T>> (use thenCompose).
  • Forgetting to handle exceptions, so failures disappear.
  • Expecting cancel(true) to interrupt the running task (it does not).

How to answer in the interview

"CompletableFuture, from Java 8, is a Future I can complete manually and, more importantly, compose. supplyAsync and runAsync start work on the common ForkJoinPool or on an executor I pass, which I always do for I/O. Instead of blocking with get, I attach callbacks: thenApply to transform, thenAccept to consume, thenCompose to chain another async call, thenCombine to merge two results, and allOf or anyOf to coordinate many. Errors flow down the chain and I handle them with exceptionally, handle or whenComplete, and Java 9 added orTimeout. This lets me call several services in parallel and combine the results without blocking threads."

Likely follow-up questions

  • Why should you pass your own executor for I/O tasks? The common pool is small (cores minus one) and shared; blocking it starves parallel streams and other async work.
  • thenApply vs thenCompose? thenApply maps a value; thenCompose flattens a function that itself returns a CompletableFuture.
  • Does cancel() stop the task? It completes the future with CancellationException but does not interrupt the underlying computation.
