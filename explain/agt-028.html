A multi-agent system costs ten times more than expected and agents seem to talk in circles. What do you do?

AI Agents & AIOps · scenario · levels senior, lead

In one line

Trace token usage per agent and message; typical causes are agents re-sending full histories, overlapping responsibilities and no stopping rules; fix with an orchestrator assigning well-specified tasks and output formats, compact summaries, acceptance criteria, limits on rounds and budgets, cheaper models for simple roles, and a single-agent baseline comparison.

Detailed explanation

Start with data, not intuition. Break down tokens and cost per agent, per message and per round from traces. The patterns are usually obvious once visible.

Context forwarding: agents pass entire conversation histories to each other instead of results. Each hop resends tens of thousands of tokens, and with several agents the total grows multiplicatively.

Overlapping responsibilities: a "researcher" and an "analyst" both search the web; a "planner" and a "coordinator" both re-plan. Agents redo each other's work or ask each other for clarification.

No stopping rules: a reviewer agent keeps requesting improvements and a writer keeps revising, because nobody defined "good enough". Free-form "group chat" designs where agents decide who speaks next are especially prone to circular discussions.

Fixes:

  • An orchestrator that assigns well-specified subtasks with scope, inputs, explicit deliverables and output schemas, and budgets.
  • Sub-agents return compact structured summaries, not transcripts.
  • Acceptance criteria for review: a checklist, after which the work is accepted.
  • Hard limits on rounds (for example, at most two review cycles) and tokens or cost per task and per agent.
  • Cheaper models for simple roles like formatting or classification; prompt caching for shared prefixes.
  • Remove agents whose role adds nothing.

Most importantly, compare against a single-agent baseline on the same evaluation tasks. Often one agent with good tools reaches similar quality at a fraction of the cost and latency. Keep the multi-agent design only for the parts where it clearly wins, such as parallel research across many independent sources.

How it works

  1. Collect traces; attribute tokens and cost to agents, messages and rounds.
  2. Identify forwarding, overlap and endless review loops.
  3. Redefine roles with explicit inputs, outputs and boundaries.
  4. Replace transcripts with structured summaries between agents.
  5. Add round limits, budgets and acceptance criteria.
  6. Benchmark against a single-agent baseline; simplify.

Example

Cost breakdown per task (before):
  writer        41%   (7 revision rounds, full history each time)
  reviewer      33%   (re-reads full transcript every round)
  researcher    18%
  coordinator    8%
Avg cost $3.80, quality score 4.1/5

After: orchestrator + researcher (summaries only) + writer;
       reviewer uses checklist, max 2 rounds
Avg cost $0.61, quality score 4.2/5
Single-agent baseline: $0.48, quality 3.9/5 -> keep slim multi-agent for research fan-out

Common mistakes

  • Adding more agents to fix quality problems.
  • Unbounded agent conversations.
  • Sharing full context "so everyone knows everything".
  • No baseline comparison.
  • Optimising prompts before measuring where tokens go.

How to answer in the interview

"I'd trace token usage per agent and per message to see where the cost goes. Usually agents pass whole histories to each other instead of results, responsibilities overlap so they redo each other's work, and there are no stopping rules, so a reviewer and writer go round in circles. I'd put an orchestrator in charge that assigns well-specified subtasks with explicit deliverables and output formats, have sub-agents return compact summaries, define acceptance criteria, and set hard limits on rounds and budgets. Simple roles can use cheaper models. And I'd compare with a single-agent baseline on the same evals; often one agent with good tools matches quality at a fraction of the cost."

Likely follow-up questions

  • Tasks that genuinely benefit from multiple agents? Broad parallel research, large codebase exploration, and security-separated reader and actor roles.
  • How do you stop review loops? A checklist-based acceptance and a maximum number of rounds, then escalate.
  • Group chat vs orchestrator? Orchestrators are more predictable and cheaper; group chat suits exploratory brainstorming at best.
