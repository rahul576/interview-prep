What is the Chain of Responsibility pattern?

Design Patterns · concept · levels mid

In one line

Chain of Responsibility passes a request along a chain of handlers, where each one processes it, stops it, or forwards it to the next, decoupling the sender from whoever handles it and making handlers easy to add, remove or reorder.

Detailed explanation

Some requests need several independent checks or processing steps, and the sender should not know which ones exist. Hard-coding them in one method creates a long, fragile procedure.

With Chain of Responsibility, each step is a handler implementing a common interface. A handler receives the request and the next handler (or a chain object). It can:

  • handle and stop, for example reject an unauthenticated request with 401;
  • handle and pass on, for example log, enrich or validate, then call next;
  • simply pass on if the request is not its concern.

There are two variants. In the classic GoF form, exactly one handler typically takes responsibility (support ticket escalation: agent, then supervisor, then manager). In the pipeline / interceptor form common in web frameworks, several handlers each do part of the work.

Examples:

  • Servlet filters (Filter.doFilter(req, res, chain) calling chain.doFilter).
  • Spring Security's SecurityFilterChain: CORS, CSRF, authentication, exception translation and authorisation filters in a defined order.
  • Spring MVC HandlerInterceptor (preHandle returning false stops the chain), Spring Cloud Gateway filters, OkHttp interceptors.
  • Business pipelines: order validation, then fraud check, then discount, then approval.
  • Logging frameworks passing events through appender/filter chains, and Java exception propagation up the call stack.

Trade-offs: flexibility and single-responsibility handlers versus order dependence (authentication must run before authorisation), the risk of a request falling off the end unhandled, and harder debugging when many handlers are involved.

How it works

  1. Define a handler interface (handle(request, chain)).
  2. Implement small handlers, each with one concern.
  3. Assemble them into an ordered chain (configuration, @Order).
  4. Sender calls the first handler.
  5. Each handler handles, stops, or forwards; define a default at the end.

Example

public interface OrderCheck {
    void check(Order order);   // throw to stop the chain
}

@Component @Order(1) class StockCheck   implements OrderCheck { public void check(Order o) { /* ... */ } }
@Component @Order(2) class FraudCheck   implements OrderCheck { public void check(Order o) { /* ... */ } }
@Component @Order(3) class CreditCheck  implements OrderCheck { public void check(Order o) { /* ... */ } }

@Service
class OrderValidator {
    private final List<OrderCheck> chain;           // Spring injects in @Order order
    OrderValidator(List<OrderCheck> chain) { this.chain = chain; }
    void validate(Order o) { chain.forEach(c -> c.check(o)); }
}

// Servlet filter style
public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain) throws IOException, ServletException {
    if (!isAuthorised(req)) { ((HttpServletResponse) res).sendError(401); return; } // stop
    chain.doFilter(req, res);                                                           // forward
}

Common mistakes

  • Forgetting to call chain.doFilter, silently dropping requests.
  • Ignoring ordering, such as authorisation before authentication.
  • Handlers with hidden dependencies on each other's side effects.
  • No fallback when nobody handles the request.

How to answer in the interview

"Chain of Responsibility passes a request along a chain of handlers. Each handler either processes it, stops it, or passes it to the next one. The sender doesn't know which handler will act, and I can add, remove or reorder handlers without touching the sender. Classic examples are servlet filters and the Spring Security filter chain, where CORS, authentication and authorisation filters each handle part of the request, and Spring MVC interceptors. In business code I use it for pipelines like stock check, fraud check and credit check, as a list of ordered Spring beans."

Likely follow-up questions

  • How would you implement a validation chain in Spring? Beans implementing a common interface with @Order, injected as a List and run in sequence.
  • How does it differ from Decorator? Decorators always delegate and add behaviour; chain handlers may stop the request.
  • How do you add a custom filter to Spring Security? Register it with http.addFilterBefore(...) or addFilterAfter(...) in the SecurityFilterChain bean.
