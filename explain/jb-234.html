How would you handle partial failures when one microservice becomes unavailable?

Microservices · scenario · levels senior, lead

In one line

Contain the failure with timeouts and circuit breakers, degrade gracefully with fallbacks or cached data, defer writes through queues or the outbox for later retry, repair half-done work with idempotent retries and compensation, and communicate clearly with good errors and alerts.

Detailed explanation

Suppose the recommendation, loyalty or even payment service becomes unavailable. The goal is that the rest of the system keeps working and nothing ends in an inconsistent state.

1. Stop the spread. Every call to the failing service has a timeout, so requests do not pile up. A circuit breaker opens once failures exceed a threshold, so callers fail fast instead of tying up threads, and a bulkhead caps how many threads that dependency can consume. Retries are limited and backed off so we do not hammer a recovering service.

2. Degrade per feature. Decide, with the product owner, what each feature does when its dependency is missing. Non-critical data uses a fallback: hide the recommendations widget, show cached prices with a notice, use default delivery estimates. Critical features may need to fail honestly, for example "payments are temporarily unavailable".

3. Defer what can wait. Writes that do not need an immediate answer are accepted and put on a queue, or recorded via the outbox, and processed when the service recovers. The user sees "order received, confirmation will follow" rather than an error. Brokers naturally buffer when a consumer service is down.

4. Repair half-finished work. If a multi-step operation failed midway (order created, payment unknown), use idempotent retries with the same idempotency key to find out or complete it, and saga compensation to undo steps if it cannot complete. Reconciliation jobs catch anything missed.

5. Communicate and observe. Return clear statuses to clients, 503 with Retry-After, or 202 Accepted with a pending status, not generic 500s. Dashboards and alerts on error rates, breaker state and queue depth notify the owning team, and runbooks describe the degradation modes.

How it works

  1. Timeout fires or breaker is open.
  2. Fallback logic chooses: cached data, default, hide feature, or queue.
  3. Deferred work stored durably for retry.
  4. Partially completed workflows are retried or compensated.
  5. Client receives a clear status; alerts fire.
  6. On recovery, queues drain and breakers close.

Example

@CircuitBreaker(name = "loyalty", fallbackMethod = "pointsLater")
public CheckoutResult applyPoints(Order order) {
    return new CheckoutResult(loyaltyClient.redeem(order.customerId(), order.points()));
}

// Degrade: complete checkout without points, settle them asynchronously
CheckoutResult pointsLater(Order order, Throwable t) {
    outbox.save(OutboxEvent.of("RedeemPointsRequested", order.id(), order));
    return CheckoutResult.pendingPoints("Points will be applied shortly");
}

Common mistakes

  • No timeouts, so one dead service freezes all callers.
  • Fallbacks that silently produce wrong business results.
  • Losing deferred work by keeping it only in memory.
  • Generic 500 errors that clients retry aggressively.

How to answer in the interview

"First I contain it: every call to that service has a timeout and goes through a circuit breaker and bulkhead, so once it is clearly down we fail fast instead of piling up threads. Then I degrade per feature: non-critical data uses fallbacks like cached data or hiding a widget, while the rest of the page works. Writes that can wait go onto a queue or the outbox and are retried when the service recovers. If a multi-step operation was half done, idempotent retries and saga compensation bring it back to a consistent state. Clients get a clear 503 or a pending status, and monitoring alerts the owning team."

Likely follow-up questions

  • Which checkout features can degrade and which must fail? Recommendations, estimates and loyalty can degrade; payment and stock reservation usually must succeed or fail clearly.
  • How do you test this? Chaos or fault-injection tests in staging, such as stopping a dependency or adding latency.
  • What is a reconciliation job? A periodic check that compares systems and fixes inconsistencies missed by real-time flows.
