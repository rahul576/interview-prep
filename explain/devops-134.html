How do you test and review infrastructure code before it reaches production?

Infrastructure as Code · concept · levels senior, lead

In one line

Treat infrastructure code like application code: every change via pull request, CI runs fmt, validate, tflint, security/policy as code (Checkov, Trivy, OPA/Conftest, Sentinel), posts the plan to the PR for review (Atlantis, HCP Terraform, pipeline), modules are tested with terraform test or Terratest in ephemeral accounts, and changes are promoted dev → staging → prod.

Detailed explanation

Infrastructure mistakes are expensive: a public bucket, an open security group or a destroyed database. Testing works in layers, from cheap and fast to slow and realistic.

Static checks: terraform fmt -check and terraform validate catch syntax and type errors. tflint catches provider-specific problems, such as invalid instance types or deprecated arguments. Security scanners like Checkov or Trivy (which absorbed tfsec) flag misconfigurations: unencrypted storage, 0.0.0.0/0 ingress, missing logging.

Policy as code: organisation rules written as code, for example "all resources must have owner and cost-centre tags", "no public S3 buckets", "only approved instance families". Tools: OPA/Conftest evaluating the JSON plan, Sentinel or OPA in HCP Terraform, and cloud-native guardrails such as AWS SCPs or Azure Policy as a last line.

Plan review: CI posts the plan output to the PR (Atlantis, HCP Terraform, Spacelift, or a pipeline). Reviewers approve the plan, not just the code: a one-line change can mean "must be replaced" for a database. Apply runs the saved, approved plan.

Tests: the native terraform test framework (Terraform 1.6+, .tftest.hcl files) can run plan-only assertions or real apply runs, with mocked providers in 1.7+. Terratest (Go) deploys real infrastructure, checks it works (HTTP endpoint responds, bucket encrypted) and destroys it. Run them in an isolated sandbox account with budgets.

Promotion: apply to dev, then staging, then production, with the same module version; production applies need approval.

How it works

  1. PR opened → fmt, validate, tflint, Checkov/Trivy.
  2. terraform plan -out → terraform show -json → policy checks.
  3. Plan posted as PR comment; reviewers approve.
  4. Module tests run on module changes in a sandbox.
  5. Merge → apply saved plan to dev → promote to staging/prod with approval.

Example

# tests/bucket.tftest.hcl
run "bucket_is_encrypted_and_private" {
  command = plan
  assert {
    condition     = aws_s3_bucket_public_access_block.this.block_public_acls == true
    error_message = "Bucket must block public ACLs"
  }
}
terraform fmt -check -recursive && terraform validate && tflint
checkov -d . --quiet
terraform plan -out=tfplan && terraform show -json tfplan > plan.json
conftest test plan.json -p policy/
terraform test

Common mistakes

  • Reviewing the code diff but not the plan.
  • Applying a fresh plan in CI instead of the reviewed one.
  • Running integration tests in a shared production account.
  • Policies so noisy that everyone adds skip annotations.

How to answer in the interview

"Every infrastructure change goes through a pull request. CI runs terraform fmt, validate and tflint, then security and policy-as-code checks with Checkov, Trivy or OPA, for things like no public storage and required tags. The plan is posted to the PR by Atlantis, HCP Terraform or our pipeline, and reviewers approve the plan, not just the code, looking especially for destroys and replacements. Modules have tests with the native terraform test framework or Terratest, which create real resources in an ephemeral sandbox account and destroy them. Then changes are applied to dev and staging first and promoted to production with approval, applying exactly the reviewed plan."

Likely follow-up questions

  • What should a reviewer look for first in a plan? Destroy and replace actions, especially on stateful resources, then IAM and network changes.
  • How do you protect critical resources? lifecycle { prevent_destroy = true }, deletion protection and policies.
  • Mocking in terraform test? mock_provider blocks allow tests without real cloud calls (1.7+).
