How do you secure the Terraform state storage itself?

Terraform · concept · levels mid, senior

In one line

State holds secrets and a full map of your infrastructure, so protect it like a secret store: encryption at rest (optionally customer-managed keys) and TLS, least-privilege access with only pipelines writing, private network access, versioning, soft delete and deletion locks, audited access logs, and fewer secrets in state via ephemeral resources and write-only arguments.

Detailed explanation

Terraform state records every attribute of every managed resource. That includes generated passwords, connection strings, access keys and private keys, plus resource IDs, IPs and topology that are valuable for an attacker. Anyone who can read production state effectively holds production secrets. Anyone who can write it can make Terraform destroy or recreate resources.

Encryption. Azure Storage and S3 encrypt at rest by default; use customer-managed keys in Key Vault or KMS where compliance requires it, and enforce TLS (secure transfer required, minimum TLS 1.2). HCP Terraform encrypts state with Vault-backed keys. OpenTofu also offers client-side state encryption.

Access control. Only pipeline identities can write production state. A small platform group gets read access for troubleshooting, ideally through just-in-time elevation. Developers do not get direct access to production state. Use data plane RBAC (Storage Blob Data Contributor on the specific container, scoped IAM on the bucket prefix) and disable shared key access on Azure storage where possible.

Network. Disable public network access; reach the storage through private endpoints or VPC endpoints, which also means runners must be inside the network.

Resilience. Enable blob versioning or S3 versioning, soft delete, and resource locks or deletion protection on the account or bucket, so corruption or accidental deletion is recoverable. Use state locking (blob leases, S3 native lockfile or DynamoDB).

Monitoring. Send access logs to the SIEM and alert on unusual reads, for example a human identity reading production state.

Reduce what is stored. Use ephemeral resources (Terraform 1.10+) and write-only arguments (1.11+) so secrets are never persisted, and prefer managed identities over keys.

How it works

  1. Dedicated storage account or bucket per environment tier.
  2. Encryption at rest with CMK if required; TLS enforced.
  3. RBAC: pipelines write, few humans read, no shared keys.
  4. Private endpoints; public access disabled.
  5. Versioning, soft delete, locks and state locking.
  6. Access logs to SIEM with alerts; minimise secrets in state.

Example

resource "azurerm_storage_account" "tfstate" {
  name                            = "sttfstateprod01"
  resource_group_name             = azurerm_resource_group.tfstate.name
  location                        = "westeurope"
  account_tier                    = "Standard"
  account_replication_type        = "ZRS"
  min_tls_version                 = "TLS1_2"
  shared_access_key_enabled       = false
  public_network_access_enabled   = false
  allow_nested_items_to_be_public = false

  blob_properties {
    versioning_enabled = true
    delete_retention_policy { days = 30 }
    container_delete_retention_policy { days = 30 }
  }
}

resource "azurerm_management_lock" "tfstate" {
  name       = "do-not-delete"
  scope      = azurerm_storage_account.tfstate.id
  lock_level = "CanNotDelete"
}
terraform {
  backend "azurerm" {
    storage_account_name = "sttfstateprod01"
    container_name       = "tfstate"
    key                  = "orders.tfstate"
    use_azuread_auth     = true
  }
}

Common mistakes

  • Granting developers Contributor on the state account "for debugging".
  • Using storage account keys in pipelines.
  • No versioning, so corruption is unrecoverable.
  • Assuming sensitive = true keeps values out of state; it does not.

How to answer in the interview

"State contains secrets and a full map of the infrastructure, so I protect it like a secret store. Encryption at rest, with customer-managed keys where required, and TLS. Least privilege: only pipeline identities can write, a small group can read, developers have no direct access to production state. Private endpoints with public access disabled. Versioning and soft delete for recovery, plus deletion locks. Access logs are audited with alerts on unusual reads. And I reduce secrets in state with ephemeral resources and write-only arguments."

Likely follow-up questions

  • Why is remote_state across teams risky? Readers get the whole state, including secrets.
  • Does sensitive hide values in state? No, only in CLI output.
  • One storage account for all environments? Separate at least production from non-production.
