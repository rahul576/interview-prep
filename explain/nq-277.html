What is the purpose of the @Test annotation?

Testing · concept · levels entry

In one line

@Test marks a method as a test case that JUnit discovers and runs; the test passes if it completes normally and fails if an assertion fails or an unexpected exception escapes; in JUnit 5 (org.junit.jupiter.api.Test) it has no expected or timeout attributes, so you use assertThrows and @Timeout/assertTimeout.

Detailed explanation

JUnit does not run arbitrary methods. During discovery, the Jupiter engine scans test classes for methods annotated with @Test (and related annotations such as @ParameterizedTest, @RepeatedTest, @TestFactory). Each one becomes a separate test in the report, with its own pass, fail or skipped status, so one failing test does not stop the others.

Execution: by default JUnit creates a new instance of the test class for every test method, runs @BeforeEach methods, the test, then @AfterEach methods. This isolation means fields set in one test do not leak into another. The outcome:

  • Pass: the method returns normally.
  • Fail: an assertion throws AssertionFailedError (or any AssertionError).
  • Error/fail: any other exception escapes; JUnit 5 reports it as a failure with the stack trace.
  • Skipped/aborted: @Disabled or a failed assumption (assumeTrue).

Rules for JUnit 5 test methods: they must not be private or static, should return void (non-void @Test methods are not run), and may take parameters only if an extension resolves them (for example TestInfo, @TempDir Path, or Mockito mocks). Neither the class nor the method needs to be public, unlike JUnit 4.

Differences from JUnit 4: JUnit 4's org.junit.Test had @Test(expected = X.class) and @Test(timeout = 1000). Jupiter's @Test has no attributes. Exceptions are checked with assertThrows, which is more precise because it targets one statement and returns the exception for message checks. Timeouts use @Timeout(1) on the method or class, or assertTimeout(Duration, executable). Importing the wrong @Test is a classic mistake that makes tests silently not run.

How it works

  1. The build or IDE asks the JUnit Platform to discover tests.
  2. Jupiter finds @Test methods in test classes.
  3. For each: new instance → @BeforeEach → test → @AfterEach.
  4. Outcome determined by normal return or thrown exception.
  5. Results reported individually.

Example

import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.Timeout;
import static org.junit.jupiter.api.Assertions.*;

class AccountTest {

    @Test
    void depositIncreasesBalance() {
        var account = new Account(100);
        account.deposit(50);
        assertEquals(150, account.balance());
    }

    @Test
    void withdrawingTooMuchThrows() {
        var account = new Account(100);
        var ex = assertThrows(InsufficientFundsException.class,
                              () -> account.withdraw(500));
        assertEquals("balance 100 < 500", ex.getMessage());
    }

    @Test
    @Timeout(1)   // seconds
    void interestCalculationIsFast() {
        new Account(100).projectInterest(30);
    }
}

Common mistakes

  • Importing org.junit.Test in a JUnit 5 project, so tests are not executed.
  • Making a test method private or static, or returning a value.
  • Writing a test with no assertion that passes whatever happens.
  • Expecting state from one test to be available in another.

How to answer in the interview

"@Test marks a method as a test case, so the JUnit engine discovers it, runs it and reports it separately. It passes if the method finishes normally and fails if an assertion fails or an unexpected exception is thrown. By default JUnit creates a new instance of the class for each test, so tests are isolated. In JUnit 5 the annotation comes from org.junit.jupiter.api, the method returns void and must not be private, and the class doesn't need to be public. Unlike JUnit 4 it has no expected or timeout attributes: I use assertThrows for exceptions and @Timeout or assertTimeout for time limits."

Likely follow-up questions

  • How do you test an exception in JUnit 5? assertThrows(Type.class, () -> call()), then assert on the returned exception.
  • Why a new instance per test? Isolation, so state does not leak between tests.
  • How do you skip a test? @Disabled or an assumption such as assumeTrue.
