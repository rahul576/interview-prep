Have you worked with GitHub Copilot, Claude, or Cursor?

AI/ML & GenAI · scenario · levels entry

In one line

Name the tools you actually used and how: GitHub Copilot for inline completion and chat in the IDE, Claude for reasoning-heavy work and agentic multi-file changes (for example via Claude Code), Cursor as an AI-first editor with codebase-aware chat and project rules; then share strengths, limitations and policy awareness.

Detailed explanation

Interviewers ask this to see practical familiarity and maturity. Structure your answer around the three interaction styles these tools offer:

  • Inline completion: suggestions as you type. Great for boilerplate, repetitive patterns and tests that mirror existing ones. GitHub Copilot in IntelliJ or VS Code is the classic example.
  • Chat: ask about selected code or the repository: explain a class, propose a refactoring, write tests, draft a regex. Copilot Chat, Cursor chat and Claude all do this.
  • Agentic editing: the tool plans a change, edits several files, runs the build and tests, and iterates. Examples include Claude Code in the terminal or IDE, Cursor's agent mode and Copilot's agent mode and coding agent. These need the most supervision and the clearest instructions.

Context is what makes them good. Tools index the repository and read instruction files such as CLAUDE.md, .github/copilot-instructions.md or Cursor rules in .cursor/rules, which describe conventions, build commands and things not to touch. Mention that you curate this context.

Observed strengths: boilerplate, tests, migrations, documentation, explaining code. Limitations: subtle concurrency or transaction bugs, invented or outdated APIs, overconfident large diffs, and drift from team conventions. So you review diffs, keep changes small and run tests.

Policy: use the enterprise or business editions your company approved, which typically offer contractual commitments not to train on your code, and follow rules on what data may be shared.

How it works

  1. List the tools honestly; do not claim ones you only read about.
  2. Map each to the interaction style you used.
  3. Describe how you gave context (open files, rules files, references).
  4. Give a concrete win and a concrete failure.
  5. Mention review practices and company policy.

Example

A small rules file that helped an agent follow team conventions:

# CLAUDE.md
- Java 21, Spring Boot 3, build with `./mvnw verify`
- Constructor injection only; no field @Autowired
- Use AssertJ in tests; test names: should_<result>_when_<condition>
- Never edit files under src/main/resources/db/migration that are already released

With this, a multi-file refactoring produced code matching our conventions and ran the right build command.

Common mistakes

  • Saying "yes" without explaining usage.
  • Treating all tools as the same thing.
  • Overclaiming agentic results without mentioning review.
  • Ignoring licensing and data privacy policy.

How to answer in the interview

"Yes. I use GitHub Copilot in IntelliJ daily for inline completions and its chat to explain code or generate tests. For reasoning-heavy work, like reviewing a design or refactoring a large class, I use Claude, and I've used Claude Code as an agent to make multi-file changes and run the test suite. I've also tried Cursor, whose codebase-aware chat and project rules are strong. What works well is boilerplate, tests and migrations; what doesn't is subtle concurrency logic or invented APIs, so I keep changes small and review every diff. We used the enterprise editions approved by the company, which don't train on our code."

Likely follow-up questions

  • How do you give these tools enough context? Instruction files in the repo, referencing specific files, and splitting tasks into small, well-described steps.
  • Which tool do you prefer and why? Depends on the task: completion for flow, agents for well-specified multi-file changes.
  • How do you review an agent's large diff? Ask for small commits, read tests first, run the build and check for unrelated changes.
