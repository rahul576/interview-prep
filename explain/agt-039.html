How do you handle a multi-step agent task that fails halfway through, after some actions already happened?

AI Agents & AIOps · concept · levels mid, senior

In one line

Record every completed step and its effects durably, then decide by error type: resume from the failed step for transient issues (safe because tools are idempotent), run compensating actions defined in code in a saga for permanent failures, or escalate to a human; always tell the user exactly what was and was not done.

Detailed explanation

Agents act across several systems, such as a CRM, a booking system and email, with no global transaction. If step four of six fails, steps one to three have already changed the world. Partial failure must be designed for, not improvised.

Durable record of effects: the runtime, not the model, records each completed step and its effects in durable state: "created ticket 4711", "reserved room 12 for 14 May", "charged card, payment ID pi_88". The model's context may be compacted or lost; the step log is the source of truth.

Transient failures (timeouts, rate limits, temporary outages): retry with backoff, or resume from the failed step after the cause is fixed. This is only safe if tools are idempotent, using idempotency keys per run and step, so a repeated "reserve room" does not create a second reservation and a repeated charge is not taken twice.

Permanent failures (business rule violation, resource unavailable, permission denied): the system runs compensating actions that semantically undo earlier steps in reverse order, such as cancelling the reservation and refunding the charge. This is the saga pattern from distributed systems. Compensations are defined in code alongside each action, because the model might improvise incorrect undo steps, skip some, or be manipulated; compensations must themselves be idempotent and retried until they succeed.

Escalation: if neither resume nor compensation is possible, for example a non-reversible email was sent, the case goes to a human with full context: what happened, current state and options.

Honest communication: in every case, the user receives a clear, factual account generated from the step log: what was done, what was undone, and what still needs attention.

How it works

  1. Before each action, record the intent; after success, record the effect and IDs.
  2. On failure, classify transient or permanent.
  3. Transient: retry or resume from the failed step using the same idempotency keys.
  4. Permanent: run compensations for completed steps in reverse order.
  5. If compensation fails or is impossible, escalate with context.
  6. Report the final state to the user from the step log.

Example

Task: "Book team offsite: room, catering, calendar invites"

Step log
1 reserve_room      OK   reservation R-551   compensate: cancel_reservation(R-551)
2 order_catering    OK   order C-930         compensate: cancel_catering(C-930)
3 send_invites      FAILED  permanent: calendar API rejects external domain

Decision: invites are the goal; partial booking without invites is not useful
-> compensate 2: cancel_catering(C-930)        OK
-> compensate 1: cancel_reservation(R-551)     OK

Message to user: "I couldn't send invites (external attendees not allowed by
calendar policy). I cancelled the room R-551 and catering C-930 so nothing is
left half-booked. Options: invite internal attendees only, or ask IT to allow
the partner domain."

Common mistakes

  • Relying on the model's memory of what it already did.
  • Retrying non-idempotent steps.
  • Letting the model invent compensating actions.
  • Leaving resources half-created silently.
  • Vague failure messages to the user.

How to answer in the interview

"Agents act on several systems without a global transaction, so I plan for partial failure. The runtime records each completed step and its effects, like 'created ticket 4711', in durable state, not just the model's context. For transient failures, the agent resumes from the failed step after a retry, which is safe because tools are idempotent. For permanent failures, the system runs compensating actions to undo earlier steps, like cancelling a reservation, following the saga pattern, with compensations defined in code rather than improvised by the model. If neither works, it escalates to a human with full context. And the user is always told exactly what was done and what wasn't."

Likely follow-up questions

  • Why define compensations in code? They must be correct, complete, idempotent and immune to injection; the model may improvise wrongly.
  • What if a compensation fails? Retry it durably with backoff, then escalate; never silently drop it.
  • Can every action be compensated? No; sent emails or payments may need follow-up actions instead, so gate them behind approval.
