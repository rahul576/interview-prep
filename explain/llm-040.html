The assistant answers with outdated information even though the documents were updated. Why, and how do you fix it?

LLMOps & RAG · scenario · levels mid, senior

In one line

Stale answers usually mean old versions or deletions still in the index, failed or lagging sync jobs, caches serving old responses, ranking that doesn't prefer current documents, or the model using training knowledge instead of context; check each in order and add freshness monitoring and dates in answers.

Detailed explanation

Work through the pipeline from source to answer.

Index contents. Search the index for the updated document. Is the new version there? Is the old one still there? If updates are inserted with new chunk IDs instead of replacing the old chunks, both versions coexist and retrieval picks whichever scores higher. Deleted documents that were never removed cause the same problem.

Sync. Check ingestion job history: failures, permission errors on the source (an expired service account secret is common), throttling, or change detection that missed edits, for example because the connector only watches one library or relies on a timestamp that is not updated on metadata-only changes.

Caches. Semantic or response caches, CDN caches on API responses, and even embedding caches keyed by document ID can keep serving content generated from old text. They need invalidation on document change events, or short TTLs.

Ranking. Old and new versions are nearly identical textually, so similarity cannot distinguish them. Store effective date, version and status (current, superseded) and filter superseded versions or boost recent ones.

Generation. If the context is correct but the answer is old, the model may be relying on prior knowledge, typical for public facts like tax rates. Stronger instructions ("answer only from the sources, prefer the most recent effective date") and groundedness checks help.

How it works

  1. Reproduce with the failing question; inspect retrieved chunks and their versions.
  2. Query the index directly for the document ID.
  3. Check connector logs and last-success time per source.
  4. Check and flush caches; add invalidation hooks.
  5. Add version/status metadata and filters.
  6. Monitor source-to-index lag; show "last updated" dates in citations.

Example

{
  "id": "travel-policy#0004",
  "doc_id": "travel-policy",
  "version": "2026-09",
  "status": "current",
  "effective_from": "2026-10-01",
  "text": "Economy class is required for flights under 6 hours..."
}

Retrieval filter: status eq 'current', so superseded versions are never candidates.

Common mistakes

  • Appending new versions instead of replacing chunks.
  • No alerting on failed sync jobs.
  • Forgetting cache invalidation when content changes.
  • Not showing document dates, so users can't spot staleness.

How to answer in the interview

"I'd check the pipeline in order. First the index: is the new version there, and are the old version and deleted documents gone, or do both coexist? Then the sync job: failures, expired credentials, missed changes. Then caches, which may still serve answers generated from old content and need invalidation. Then ranking: near-identical versions need version and effective-date metadata so we filter superseded ones. Finally the model may be answering from its own knowledge, which stricter grounding instructions address. Going forward I'd monitor freshness lag and show document dates in answers."

Likely follow-up questions

  • Superseded policies never used? Status metadata set at ingestion; filter in every query; owners mark replacements.
  • Freshness SLO? For example 95% of changes indexed within 30 minutes.
  • Cache strategy? Key by document versions used, invalidate on change events.
