How do generics work in Java, and what is type erasure? Explain wildcards and PECS.

Core Java & OOP · concept · levels mid, senior

In one line

Generics give compile-time type safety without casts; they are implemented by type erasure, so type arguments are removed at runtime. Wildcards (? extends T, ? super T) make APIs flexible, following PECS: Producer Extends, Consumer Super.

Detailed explanation

Generics (Java 5) let classes and methods be parameterised by type: List<Order>, Map<String, Customer>, <T> T first(List<T>). The compiler checks that only Orders go into a List<Order> and inserts casts automatically, so ClassCastExceptions are caught at compile time.

Type erasure: to stay compatible with pre-generics code, the compiler erases type parameters, replacing them with their bound (Object, or Number for <T extends Number>), inserting casts, and generating bridge methods where needed. At runtime List<String> and List<Integer> are both just List. Consequences:

  • No new T(), new T[], or instanceof List<String> (only instanceof List<?>).
  • No primitive type arguments (List<int>), hence boxing.
  • You cannot overload m(List<String>) and m(List<Integer>): same erasure.
  • Raw types and unchecked casts can cause heap pollution.

Workarounds: pass a Class<T> token, or "super type tokens" (as Jackson's TypeReference does). Some generic info survives in class metadata (field and method signatures, superclass declarations), which frameworks read via reflection.

Invariance and wildcards: List<Integer> is not a List<Number>, even though Integer is a Number; otherwise you could add a Double to a list of integers. Wildcards add controlled variance:

  • List<? extends Number> (upper bound, covariant): you can read elements as Number, but cannot add anything except null, because the actual list might be List<Double>.
  • List<? super Integer> (lower bound, contravariant): you can add Integers, but reading gives only Object.
  • List<?>: unknown type, read as Object.

PECS (from Effective Java): if a parameter produces values you read, use extends; if it consumes values you write, use super. Collections.copy(List<? super T> dest, List<? extends T> src) is the textbook example, and Comparator<? super T> is common in sorting APIs.

How it works

  1. You declare class Box<T> or a generic method <T>.
  2. The compiler type-checks all uses against the type arguments.
  3. Erasure replaces T with its bound and inserts casts at use sites.
  4. Wildcards relax invariance for method parameters (read with extends, write with super).
  5. At runtime, objects carry no type-argument information.

Example

static double sum(Collection<? extends Number> nums) {      // producer: extends
    double total = 0;
    for (Number n : nums) total += n.doubleValue();
    return total;
}

static void fillIds(List<? super Integer> out, int count) { // consumer: super
    for (int i = 1; i <= count; i++) out.add(i);
}

sum(List.of(1, 2, 3));            // List<Integer> OK
sum(List.of(1.5, 2.5));           // List<Double> OK

List<Number> numbers = new ArrayList<>();
fillIds(numbers, 3);              // List<Number> accepts Integers
List<Object> objects = new ArrayList<>();
fillIds(objects, 3);              // also OK

static <T> void copy(List<? super T> dest, List<? extends T> src) {
    for (T item : src) dest.add(item);
}

List<? extends Number> ro = List.of(1, 2);
// ro.add(3);                     // compile error: actual type unknown
// if (ro instanceof List<Integer>) {}   // compile error: erased at runtime

Common mistakes

  • Assuming List<Integer> is a subtype of List<Number>.
  • Using raw types (List) and getting heap pollution.
  • Putting wildcards in return types, which burdens callers.
  • Trying to create generic arrays or call new T().

How to answer in the interview

"Generics give compile-time type safety and remove casts. They're implemented with type erasure: generic type information is removed at runtime and replaced by the bounds or Object, with casts inserted, which is why I can't do new T or instanceof List<String>. Generic types are invariant, so List<Integer> isn't a List<Number>; wildcards add flexibility. A List<? extends Number> can be read as Numbers but not added to, and a List<? super Integer> can accept Integers. The rule is PECS, producer extends, consumer super, as in Collections.copy, where the source extends T and the destination is super T."

Likely follow-up questions

  • Why can you not add an Integer to a List<? extends Number>? The actual list could be a List<Double>; the compiler cannot prove the add is safe, so it forbids it.
  • How do frameworks like Jackson get generic types at runtime? Through type tokens such as TypeReference, which capture the generic superclass signature kept in class metadata.
  • What is a bounded type parameter? <T extends Comparable<? super T>>, restricting T so you can call its methods.
