What is reactive programming with Spring WebFlux, and when is it worth it?

REST & API Design · concept · levels senior, lead

In one line

Spring WebFlux is Spring's non-blocking, reactive web stack built on Project Reactor (Mono, Flux) and usually Netty, with backpressure; it pays off for very high concurrency, streaming and gateways, but you must never block, and since Java 21 virtual threads with Spring MVC are often the simpler choice.

Detailed explanation

Classic Spring MVC uses one thread per request: while a request waits for the database, its thread waits too. WebFlux instead runs on a few event-loop threads (by default about one per core on Netty). Handlers return publishers instead of values: Mono<T> for zero or one item and Flux<T> for zero to many. Work is described as a pipeline of operators (map, flatMap, zip, timeout, retryWhen), and when an I/O result arrives the next stage runs, without any thread sitting idle.

Backpressure comes from the Reactive Streams specification: subscribers request n items, so a slow consumer controls how fast a producer emits. That matters for streaming large result sets, Server-Sent Events, WebSockets and Kafka pipelines.

Where WebFlux shines:

  • API gateways and proxies (Spring Cloud Gateway is built on it).
  • Streaming responses and long-lived connections.
  • Fan-out to many slow downstream services with high concurrency.
  • End-to-end reactive stacks (R2DBC, reactive MongoDB, reactive Redis).

The costs:

  • A different programming model: composing operators, less readable stack traces, harder debugging (Reactor's checkpoint and Hooks.onOperatorDebug help) and steeper onboarding.
  • The golden rule: never block an event-loop thread. A blocking JDBC call or Thread.sleep inside a handler stalls every request on that loop. JDBC/JPA are blocking, so you need R2DBC, or must offload blocking code with subscribeOn(Schedulers.boundedElastic()).
  • Context propagation (security, MDC, tracing) uses Reactor Context rather than ThreadLocal.

With Java 21 virtual threads, Spring MVC can handle very high numbers of concurrent blocking requests with plain imperative code (spring.threads.virtual.enabled=true). For typical CRUD services on JPA, that is now usually the better trade-off; WebFlux remains valuable for streaming and backpressure-heavy scenarios.

How it works

  1. Request arrives on a Netty event loop.
  2. Handler returns a Mono/Flux pipeline.
  3. Non-blocking I/O registers callbacks; thread moves on.
  4. Results flow through operators as they arrive.
  5. Subscriber demand (backpressure) limits emission.

Example

@RestController
class PriceController {
    private final WebClient client;

    @GetMapping("/quotes/{sku}")
    Mono<Quote> quote(@PathVariable String sku) {
        Mono<Price> price = client.get().uri("/prices/{s}", sku).retrieve().bodyToMono(Price.class);
        Mono<Stock> stock = client.get().uri("/stock/{s}", sku).retrieve().bodyToMono(Stock.class);
        return Mono.zip(price, stock, Quote::new)
                   .timeout(Duration.ofSeconds(2));
    }

    @GetMapping(value = "/prices/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    Flux<Price> stream() { return priceFeed.updates(); }
}

Common mistakes

  • Calling blocking JDBC or block() inside handlers.
  • Choosing WebFlux for a simple CRUD app on JPA.
  • Losing MDC/security context by relying on ThreadLocal.
  • Forgetting nothing happens until something subscribes.

How to answer in the interview

"WebFlux is Spring's non-blocking web stack on Project Reactor, usually running on Netty with a small event loop. I return Mono for zero or one value and Flux for many and compose them with operators, and Reactor supports backpressure so slow consumers control the rate. It's worth it for very high concurrency, streaming like SSE, and gateways; Spring Cloud Gateway itself is reactive. The costs are a harder programming model and debugging, and the rule that you must never block, which rules out JDBC unless you use R2DBC or offload to boundedElastic. With Java 21 virtual threads, plain Spring MVC is now often enough for typical services."

Likely follow-up questions

  • What happens if you call a blocking JDBC query inside a WebFlux handler? It blocks an event-loop thread, stalling all requests on it and collapsing throughput.
  • Mono vs Flux? Mono emits at most one item; Flux any number.
  • How do you detect blocking calls? BlockHound in tests.
