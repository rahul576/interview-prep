How do StatefulSet updates work, and what are partitions and podManagementPolicy?

Kubernetes · concept · levels mid, senior

In one line

With RollingUpdate, a StatefulSet replaces pods one at a time in reverse ordinal order, waiting for each to be Ready; a partition limits the update to ordinals ≥ the partition (canaries), OnDelete updates only pods you delete, and podManagementPolicy chooses OrderedReady (sequential) or Parallel creation and scaling.

Detailed explanation

StatefulSets manage pods with stable identities (db-0, db-1, db-2) and their own PVCs, so updates must be careful: members are not interchangeable and often form a cluster with a leader.

RollingUpdate (default): when the pod template changes, the controller deletes and recreates pods from the highest ordinal down to 0. It waits until the updated pod is Running and Ready before moving on (and minReadySeconds if set). Each recreated pod reattaches to the same PVC and DNS name. The lowest ordinals, often the initial leader or seed, are updated last.

partition (updateStrategy.rollingUpdate.partition): only pods with ordinal ≥ partition are updated; lower ones stay on the old revision even if deleted. In a 5-replica set, partition 4 updates only db-4: a canary. Observe it, then lower the partition step by step to 0. This is the StatefulSet equivalent of a staged rollout.

OnDelete: the controller never replaces pods automatically; a pod picks up the new template only when you (or an operator) delete it. Database operators often use this to control order themselves, for example updating replicas first, then failing over and updating the old primary.

podManagementPolicy affects creation, scaling and deletion, not updates:

  • OrderedReady (default): create 0, wait for Ready, then 1…; scale down from the highest ordinal one at a time.
  • Parallel: create or delete all at once, faster for systems where members don't depend on start order (for example Cassandra with seeds configured).

Rollbacks need care: a new version may already have migrated on-disk data formats, so returning to the old image is not always safe.

How it works

  1. Template change creates a new controller revision.
  2. Controller picks the highest ordinal ≥ partition still on the old revision.
  3. Deletes it; recreates with new template, same PVC and name.
  4. Waits for Ready (and minReadySeconds).
  5. Repeats down to the partition; lowering partition continues.

Example

apiVersion: apps/v1
kind: StatefulSet
metadata: { name: kafka }
spec:
  serviceName: kafka
  replicas: 5
  podManagementPolicy: Parallel
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      partition: 4         # canary: only kafka-4 updates
  selector: { matchLabels: { app: kafka } }
  template: { ... }
kubectl rollout status sts/kafka
kubectl patch sts kafka -p '{"spec":{"updateStrategy":{"rollingUpdate":{"partition":0}}}}'

Common mistakes

  • Assuming podManagementPolicy Parallel speeds up rolling updates by itself.
  • Readiness probes that don't reflect cluster membership, so updates move on too early.
  • Forgetting a stuck partition, leaving the set half-updated.
  • Rolling back an image after an irreversible data migration.

How to answer in the interview

"With RollingUpdate a StatefulSet replaces pods one at a time in reverse ordinal order, from the highest down to zero, waiting for each to be Ready, and each pod keeps its name and volume. A partition restricts the update to ordinals at or above it, so partition 4 in a five-pod set updates only the last pod as a canary, and lowering it continues the rollout. OnDelete updates only pods you delete, which operators use for full control. podManagementPolicy is about creation and scaling: OrderedReady is sequential, Parallel starts everything at once. Rollbacks need care because data formats may have changed."

Likely follow-up questions

  • Why can a rollout get stuck? An updated pod never becomes Ready (bad config, failed migration); the controller waits and may need manual fixing even after reverting.
  • Why reverse order? Higher ordinals are typically followers; ordinal 0 is often the initial leader or seed.
  • What happens to PVCs on scale-down? Retained by default; persistentVolumeClaimRetentionPolicy can delete them.
