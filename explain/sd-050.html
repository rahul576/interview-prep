Design a hotel reservation system like Booking.com.

Classic Design Problems · design · levels senior, lead

In one line

Hotel booking models inventory per hotel, room type and date, reserves all nights atomically with constraints or optimistic locking, allows controlled overbooking, uses idempotent reservation requests, serves search from a separate read index, and shards by hotel.

Detailed explanation

You don't assign room 304 at booking time; you reserve a room type for each night. A table room_inventory(hotel_id, room_type_id, date, total, reserved) makes availability simple: a 3-night stay needs reserved < total for 3 rows.

Concurrency: two users booking the last room at the same moment. Options: a single transaction with UPDATE … SET reserved = reserved + 1 WHERE … AND reserved < total for each date (all must succeed or roll back), a CHECK (reserved <= total * overbook_ratio) constraint, or optimistic locking with a version column and retries. Contention is low per hotel, so this works well.

Overbooking: hotels often sell 105–110% knowing some guests cancel; it's just a different limit.

Idempotency: double-clicks and retries must not create two reservations; the client sends a reservation ID.

Search is far heavier than booking and spans many hotels; serve it from Elasticsearch (location, price, amenities, approximate availability) updated via CDC, then re-check availability and price in the transactional DB at booking time.

Since every booking touches one hotel, shard by hotel_id.

How it works

  1. Search → ES (cached prices/availability).
  2. Select → POST /reservations {reservationId, hotel, roomType, dates}.
  3. Transaction: update inventory rows for each date with condition; insert reservation PENDING.
  4. Payment → CONFIRMED; failure/timeout → release inventory.

Example

UPDATE room_inventory SET reserved = reserved + 1
WHERE hotel_id=$h AND room_type_id=$r AND date BETWEEN $in AND $out - 1
  AND reserved < total;
-- require updated row count = number of nights, else ROLLBACK

Common mistakes

  • Assigning specific rooms at booking time.
  • Checking availability and booking in separate transactions.
  • Treating search results as authoritative availability.
  • Forgetting partial-date failures in multi-night stays.

How to answer in the interview

"Inventory is per hotel, room type and date. Booking updates every night's row in one transaction with a condition that reserved stays within the limit, which may include an overbooking margin, so concurrent bookings can't exceed capacity. Requests carry an idempotency key. Search runs on a separate Elasticsearch index fed by CDC, and we re-validate price and availability at booking. Data is sharded by hotel since transactions never span hotels."

Likely follow-up questions

  • Price changed between search and booking? Re-quote at booking; show the change; quotes with expiry.
  • Channel managers (Booking.com + Expedia)? Sync inventory via APIs; allocate per channel or shared pool.
  • Cancellations? Release rows in a transaction; apply penalties per policy.
