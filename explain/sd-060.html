Explain how the Raft consensus algorithm works at a high level.

Distributed Systems · concept · levels senior, lead

In one line

Raft keeps a replicated log consistent: nodes are leader, follower or candidate; leaders are elected per term with randomised timeouts; the leader replicates log entries, which are committed once a majority stores them; a safety rule ensures only up-to-date nodes become leader.

Detailed explanation

Raft was designed to be understandable (unlike Paxos). It splits consensus into leader election, log replication and safety.

Election: followers expect heartbeats from the leader. If none arrives within a randomised election timeout (e.g. 150–300 ms), a follower becomes a candidate, increments the term, votes for itself and requests votes. A majority makes it leader. Randomisation makes simultaneous candidacies rare; if a split vote happens, a new term starts.

Replication: clients send commands to the leader, which appends them to its log and sends AppendEntries to followers. Once a majority has the entry, it's committed, applied to the state machine and acknowledged. Followers with gaps are repaired by the leader walking back to the last matching entry.

Safety: a voter grants its vote only if the candidate's log is at least as up-to-date (higher last term, or same term and longer). So any elected leader contains all committed entries.

How it works

  1. Leader heartbeats (empty AppendEntries) every ~50 ms.
  2. Write → leader log → replicate → majority ack → commit index advances → apply.
  3. Leader fails → timeout → election → new leader continues.
  4. Snapshots compact the log.

Example

5-node cluster: commit needs 3 acks → tolerates 2 failures
Term 7: leader A. A crashes. C times out first → term 8 → votes from C, D, E → leader C

Common mistakes

  • Even cluster sizes (no extra fault tolerance).
  • Spreading members across high-latency links without considering commit latency.
  • Thinking reads from followers are linearizable by default (need ReadIndex/lease reads).

How to answer in the interview

"Raft keeps a replicated log in sync. One leader per term accepts writes and replicates log entries to followers; an entry is committed when a majority has it. If followers stop hearing heartbeats, one times out after a randomised delay and starts an election. Voters only support candidates with logs at least as up-to-date as theirs, so a new leader has every committed entry. etcd, Consul, CockroachDB and Kafka KRaft use it."

Likely follow-up questions

  • Odd number of nodes? An even node adds cost without raising tolerated failures.
  • Linearizable reads? Go through leader with ReadIndex or lease-based reads.
  • Membership changes? Joint consensus or single-server changes.
