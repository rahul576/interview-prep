How does an Application Load Balancer health check work, and what happens to unhealthy targets?

Cloud (AWS) · concept · levels entry

In one line

An ALB sends periodic requests to a health check path on each target; after consecutive successes or failures (healthy/unhealthy thresholds, interval, timeout, expected codes) it marks targets healthy or unhealthy and stops routing to unhealthy ones; with the ELB health check type, the Auto Scaling group replaces them, and deregistration delay drains in-flight requests.

Detailed explanation

Each target group defines a health check: protocol and path (for example /actuator/health), port, interval (5 to 300 seconds, default 30), timeout, healthy threshold (consecutive successes, default 5), unhealthy threshold (consecutive failures, default 2) and success codes (default 200, configurable such as 200-299). Each ALB node checks each registered target independently.

A new target starts in initial state and receives traffic only after passing the healthy threshold. When a target fails the unhealthy threshold, it becomes unhealthy and the ALB stops sending it new requests, distributing traffic among the healthy targets. If all targets are unhealthy, the ALB fails open and sends traffic to all of them, on the theory that partial service beats none.

The load balancer only stops routing; it does not fix anything. Auto Scaling groups use EC2 status checks by default, so an instance whose app has crashed but whose OS is fine stays in service forever. Setting the ASG health check type to ELB makes it terminate and replace instances the load balancer reports unhealthy, with a grace period for startup. ECS services and EKS (via the AWS Load Balancer Controller) behave similarly with their own replacement logic.

When a target is deregistered, during scale-in or deployment, it enters draining: the deregistration delay (default 300 seconds) lets in-flight requests finish while no new ones arrive. Tune it to your longest typical request.

Design the endpoint carefully. It should be fast and cheap, reflect whether this instance can serve requests, and generally not fail because a shared downstream dependency is slow, otherwise one database hiccup marks every target unhealthy at once.

How it works

  1. Target registers; health checks start.
  2. Passes N consecutive checks: healthy, receives traffic.
  3. Fails M consecutive checks: unhealthy, no new traffic.
  4. ASG with ELB health checks replaces the instance.
  5. Deregistration drains connections before removal.

Example

aws elbv2 modify-target-group --target-group-arn arn:aws:elasticloadbalancing:...:targetgroup/orders/abc \
  --health-check-path /actuator/health/readiness --health-check-interval-seconds 10 \
  --healthy-threshold-count 3 --unhealthy-threshold-count 3 --matcher HttpCode=200
aws elbv2 modify-target-group-attributes --target-group-arn arn:...:targetgroup/orders/abc \
  --attributes Key=deregistration_delay.timeout_seconds,Value=30
aws autoscaling update-auto-scaling-group --auto-scaling-group-name orders-asg \
  --health-check-type ELB --health-check-grace-period 120
aws elbv2 describe-target-health --target-group-arn arn:...:targetgroup/orders/abc

Common mistakes

  • Health checks that call the database, failing all targets together.
  • Timeouts too short, so a traffic spike makes healthy but busy targets "unhealthy".
  • ASG still using EC2 health checks only.
  • Default 300-second deregistration delay slowing deployments.

How to answer in the interview

"The ALB periodically calls a health check path, say /actuator/health, on each target. After a configured number of consecutive successes within the timeout a target is healthy; after a number of failures it's unhealthy and stops receiving traffic, which goes to the healthy targets. If the Auto Scaling group uses the ELB health check type, it also terminates and replaces unhealthy instances, after a grace period. When targets are removed, the deregistration delay lets in-flight requests finish. I keep the health endpoint fast and focused on whether that instance can serve, not on shared dependencies."

Likely follow-up questions

  • Why can a strict health check cause an outage in a spike? Busy targets time out, get removed, overloading the rest in a cascade.
  • What if all targets are unhealthy? The ALB fails open and routes to all of them.
  • Liveness vs readiness? Readiness says "can take traffic"; liveness says "process is alive"; ALB checks should use readiness.
