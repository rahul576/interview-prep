What is Amazon ECR, and how do you use it with containers?

Cloud (AWS) · concept · levels entry

In one line

Amazon ECR is a managed private registry for Docker/OCI images (and Helm charts): you authenticate with get-login-password or the credential helper, push versioned, immutable tags, scan on push, clean up with lifecycle policies, and let ECS, EKS and Lambda pull via IAM, with replication and pull-through cache for multi-account and public images.

Detailed explanation

Running your own registry means managing storage, TLS, authentication and availability. ECR handles all of that and integrates with IAM, so pulls need no passwords.

You create one repository per image, for example orders-service. Docker authenticates with a short-lived token from aws ecr get-login-password (valid 12 hours), or more conveniently the amazon-ecr-credential-helper, which fetches tokens automatically. Images are pushed with tags such as the commit SHA or a semantic version. Enabling tag immutability prevents a tag from being overwritten, which supports build-once-promote-many.

Image scanning: basic scanning checks OS packages for CVEs on push; enhanced scanning through Amazon Inspector continuously rescans images, including language packages, as new vulnerabilities are published. Lifecycle policies delete untagged images or keep only the last N images per prefix, controlling storage cost. Images are encrypted at rest with KMS.

Consumers authenticate via IAM: an ECS task execution role, EKS node or pod role, or Lambda execution role needs ecr:GetAuthorizationToken, ecr:BatchGetImage and ecr:GetDownloadUrlForLayer. Repository policies grant pull access to other accounts. Replication copies images across regions and accounts automatically. Pull-through cache rules mirror public registries such as Docker Hub, Quay or ECR Public, avoiding rate limits and keeping copies under your control. Private clusters pull through VPC endpoints (ecr.api, ecr.dkr and the S3 gateway endpoint for layers).

How it works

  1. Create a repository with immutability and scanning enabled.
  2. CI authenticates and pushes an image tagged with the SHA.
  3. Scanning reports vulnerabilities; the pipeline can block on criticals.
  4. ECS/EKS pull using IAM roles.
  5. Lifecycle policy prunes old images.

Example

aws ecr create-repository --repository-name orders-service \
  --image-tag-mutability IMMUTABLE --image-scanning-configuration scanOnPush=true

aws ecr get-login-password --region eu-west-1 | docker login --username AWS \
  --password-stdin 123456789012.dkr.ecr.eu-west-1.amazonaws.com

docker build -t 123456789012.dkr.ecr.eu-west-1.amazonaws.com/orders-service:9f2e1ab .
docker push 123456789012.dkr.ecr.eu-west-1.amazonaws.com/orders-service:9f2e1ab

Common mistakes

  • Mutable latest tags in production.
  • No lifecycle policy, so storage grows forever.
  • Private clusters without ECR and S3 endpoints, sending pulls through NAT.
  • Ignoring scan findings.

How to answer in the interview

"ECR is AWS's managed private registry for Docker and OCI images. I create a repository per service, authenticate with get-login-password piped into docker login or the credential helper, and push images tagged with the commit SHA, with tag immutability turned on. Scanning on push, or enhanced scanning through Inspector, finds vulnerabilities, and lifecycle policies delete old or untagged images. ECS, EKS and Lambda pull with IAM roles, no passwords. Repositories can replicate across regions and accounts, and pull-through cache mirrors public registries like Docker Hub."

Likely follow-up questions

  • Share images from a central account? Repository policy allowing workload accounts, or replication into each account.
  • Why pull-through cache? Avoids Docker Hub rate limits and keeps a controlled copy.
  • How do you block vulnerable images? Fail the pipeline on critical findings and use admission policies in EKS.
