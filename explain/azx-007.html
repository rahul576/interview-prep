Compare Azure SQL Database, Azure SQL Managed Instance and SQL Server on Azure VMs.

Azure · concept · levels mid, senior

In one line

Azure SQL Database is fully managed PaaS per database or elastic pool, SQL Managed Instance offers near full SQL Server compatibility inside your VNet for lift-and-shift, and SQL Server on Azure VMs gives full OS and engine control at the cost of managing it yourself; choose the most managed option that is compatible.

Detailed explanation

Azure SQL Database is a database-scoped PaaS service. Microsoft handles patching, automated backups with point-in-time restore, built-in high availability (zone-redundant options) and scaling. Purchase models are vCore (General Purpose, Business Critical, Hyperscale for very large databases with fast scaling and many read replicas) or DTU. Serverless compute scales automatically and can auto-pause idle databases, and elastic pools share resources across many databases, ideal for SaaS with a database per tenant. It lacks instance-level features: no SQL Agent (use elastic jobs), no cross-database queries in the normal sense, no CLR, limited linked servers.

Azure SQL Managed Instance is a PaaS instance deployed into your VNet, with near 100 percent compatibility with SQL Server: SQL Agent, cross-database queries, CLR, linked servers, Service Broker and Database Mail. Backups, patching and HA are still managed. It is the usual target for migrating existing applications with minimal changes, and supports the Managed Instance link for near real-time replication from on-premises SQL Server.

SQL Server on Azure VMs is IaaS: you choose the exact version, edition and OS configuration, can install third-party software and use any feature (SSRS, SSIS, specific trace flags). The SQL IaaS Agent extension helps with automated patching and backup, but you design HA (Always On availability groups or failover cluster instances) and own the operations. It suits vendor applications with strict requirements or OS access needs.

Licensing: Azure Hybrid Benefit lets you reuse existing SQL Server licences with Software Assurance across all three, which can reduce cost significantly.

How it works

  1. Assess the source with Azure Migrate or the Azure SQL migration extension for compatibility.
  2. If no blocking features: SQL Database (single, pool, serverless or Hyperscale).
  3. If instance features needed: Managed Instance.
  4. If OS access or unsupported features needed: SQL Server on VM.
  5. Size compute and storage; apply Hybrid Benefit.
  6. Plan migration method and cut-over.

Example

# Serverless database that auto-pauses after 60 minutes idle
az sql db create -g rg-app -s sql-app-weu -n reportsdb \
  --edition GeneralPurpose --compute-model Serverless --family Gen5 \
  --min-capacity 0.5 --capacity 4 --auto-pause-delay 60 --zone-redundant true

Common mistakes

  • Picking SQL on VMs by default and inheriting all patching and HA work.
  • Choosing SQL Database for an app that relies on cross-database queries or SQL Agent.
  • Ignoring serverless auto-pause cold start for latency-sensitive apps.
  • Not using Azure Hybrid Benefit when licences exist.
  • Skipping a compatibility assessment before migration.

How to answer in the interview

"Azure SQL Database is fully managed PaaS scoped to a single database or elastic pool: patching, backups with point-in-time restore, HA and scaling are handled, and it offers serverless compute that auto-pauses and Hyperscale for very large databases. It lacks instance-level features like SQL Agent, CLR or cross-database queries. SQL Managed Instance provides near full SQL Server compatibility, including SQL Agent, cross-database queries and linked servers, inside my VNet, so it is the usual lift-and-shift target. SQL Server on VMs gives full control of OS and version for special requirements, but I manage patching and HA. I choose the most managed option that is compatible, and use Azure Hybrid Benefit to reduce licensing cost."

Likely follow-up questions

  • How would you migrate an on-premises SQL Server with minimal downtime? Managed Instance link or Database Migration Service in online mode, then a short cut-over.
  • When choose Hyperscale? Large databases, fast scaling, rapid backups and many read replicas.
  • Business Critical versus General Purpose? Business Critical uses local SSD and Always On replicas, giving lower latency and a free readable secondary.
