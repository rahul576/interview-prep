What is Docker, and why do teams use containers?

Docker · concept · levels entry

In one line

Docker is a platform to build, ship and run applications in containers: you package the app with its runtime and dependencies into an image that runs the same everywhere, and containers are lightweight, isolated processes sharing the host kernel, so they start in seconds and pack densely, making them the standard unit for CI/CD and Kubernetes.

Detailed explanation

Before containers, deploying meant installing the right runtime version, libraries and config on every server, and differences between a developer's laptop, the test server and production caused the famous "works on my machine" problem. Docker solves this by packaging everything the app needs into an image: a read-only, layered filesystem plus metadata such as the start command. The same image runs on a laptop, a CI runner or a production cluster.

A container is a running instance of an image. Technically it is an ordinary Linux process isolated with namespaces (its own view of processes, network, filesystem and hostname) and limited with cgroups (CPU and memory). Unlike a virtual machine, it does not boot its own operating system kernel; it shares the host kernel. That is why containers start in seconds or less, use megabytes instead of gigabytes of overhead, and many more can run on one machine. The trade-off is weaker isolation than a VM.

Under the hood Docker Engine uses containerd and runc, and images follow the OCI standard, so they also run on Kubernetes, Podman and cloud services.

Teams use containers for consistent environments, simple dependency management, fast, repeatable deployments and rollbacks, and as the deployable artifact for CI/CD and Kubernetes.

How it works

  1. Write a Dockerfile describing the base image, dependencies and start command.
  2. docker build creates an image.
  3. docker push stores it in a registry.
  4. Any host runs docker run (or Kubernetes schedules it) to start containers from it.
  5. To change anything, build a new image version and redeploy.

Example

FROM eclipse-temurin:21-jre
COPY target/app.jar /app/app.jar
EXPOSE 8080
CMD ["java", "-jar", "/app/app.jar"]
docker build -t orders:1.0 .
docker run -d -p 8080:8080 orders:1.0

Common mistakes

  • Saying containers are "lightweight VMs" without mentioning the shared kernel.
  • Treating containers like pets: SSH in and change them.
  • Storing data inside the container instead of volumes.
  • Thinking Docker is required to run containers; Kubernetes uses containerd directly.

How to answer in the interview

"Docker is a platform to build, ship and run applications in containers. I package the app together with its runtime, libraries and config into an image, and that image runs identically on my laptop, in CI and in production, which removes the works-on-my-machine problem. A container is just an isolated process using Linux namespaces and cgroups; it shares the host kernel instead of booting its own OS like a VM, so it starts in seconds and we can run many per host. Teams use containers for consistent environments, easy dependency management, fast and repeatable deployments and rollbacks, and as the standard unit for CI/CD and Kubernetes."

Likely follow-up questions

  • Docker Engine vs Docker Desktop vs containerd? Engine is the daemon and CLI on Linux; Desktop packages it with a VM and GUI for Mac/Windows; containerd is the lower-level runtime both use and Kubernetes uses directly.
  • Can a Linux container run on Windows? Via a Linux VM (WSL 2 in Docker Desktop), because it needs a Linux kernel.
  • Image vs container? An image is the template; a container is a running instance with a writable layer.
