How would you implement graceful shutdown in a Spring Boot application?

Spring Boot · scenario · levels senior, lead

In one line

Enable graceful shutdown (server.shutdown=graceful, default since Spring Boot 3.4) with spring.lifecycle.timeout-per-shutdown-phase, make Kubernetes stop routing traffic first (readiness, preStop, terminationGracePeriodSeconds), and drain consumers, schedulers and executors before closing resources.

Detailed explanation

Shutdown happens on every deploy, scale-in and node drain, so it must not drop requests or lose messages. When the JVM receives SIGTERM, Spring Boot closes the application context. With graceful shutdown the embedded server (Tomcat, Jetty, Undertow or Netty) stops accepting new requests and lets in-flight requests finish, up to spring.lifecycle.timeout-per-shutdown-phase (default 30 s). Requests still running when the timeout expires are cut off.

In Kubernetes, removing a pod from Service endpoints and sending SIGTERM happen in parallel, so for a few seconds load balancers and kube-proxy may still send traffic. A short preStop sleep (for example 5-10 s) delays SIGTERM until routing has caught up. During shutdown Spring Boot's readiness state changes to refusing traffic, so /actuator/health/readiness fails. terminationGracePeriodSeconds (default 30 s) must be larger than preStop plus the Spring timeout, otherwise the kubelet sends SIGKILL.

HTTP is only part of it. Kafka listener containers stop polling and commit offsets for processed records; schedulers stop launching new jobs; custom executor services are shut down and awaited; and connection pools and clients are closed in @PreDestroy methods or SmartLifecycle beans, whose phases control the stop order (consumers before the resources they use).

How it works

  1. Kubernetes marks the pod terminating; preStop hook sleeps while endpoints are removed.
  2. SIGTERM arrives; Spring starts closing the context and readiness switches to refusing traffic.
  3. The web server stops accepting connections and waits for active requests.
  4. SmartLifecycle beans stop in reverse phase order: listeners, schedulers, executors.
  5. @PreDestroy and destroy methods close pools and clients.
  6. The JVM exits before terminationGracePeriodSeconds; otherwise SIGKILL.

Example

# application.yml
server:
  shutdown: graceful
spring:
  lifecycle:
    timeout-per-shutdown-phase: 25s
  task:
    scheduling:
      shutdown:
        await-termination: true
        await-termination-period: 20s
---
# deployment.yaml (excerpt)
spec:
  terminationGracePeriodSeconds: 45
  containers:
    - name: orders
      lifecycle:
        preStop:
          exec:
            command: ["sh", "-c", "sleep 10"]
      readinessProbe:
        httpGet: { path: /actuator/health/readiness, port: 8080 }

Common mistakes

  • Grace period shorter than preStop plus Spring timeout, so pods are SIGKILLed.
  • Running the app via a shell script that doesn't forward SIGTERM to the JVM.
  • No preStop delay, so requests hit a pod that already stopped listening.
  • Forgetting custom thread pools and consumers, losing queued work.
  • Long-running requests or jobs with no idempotency or resume strategy.

How to answer in the interview

"I enable server.shutdown=graceful, which is the default in recent Boot versions, and set timeout-per-shutdown-phase, say 25 seconds. On SIGTERM the server stops accepting requests and finishes in-flight ones. In Kubernetes I add a short preStop sleep so endpoints are removed before shutdown begins, use the readiness health group for the probe, and set terminationGracePeriodSeconds longer than preStop plus the Spring timeout. Beyond HTTP, Kafka listeners stop and commit offsets, schedulers and executors are drained, and resources close in PreDestroy or SmartLifecycle beans."

Likely follow-up questions

  • Request longer than the grace period? It is aborted; the client sees a reset or error, so it should be idempotent and retryable.
  • Why preStop sleep? Endpoint removal is asynchronous; the sleep avoids routing to a closing pod.
  • How do you control stop order? SmartLifecycle phases; higher phases stop first.
