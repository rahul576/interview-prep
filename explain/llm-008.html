How do you estimate GPU memory needs for serving a model, and how does quantisation help?

LLMOps & RAG · concept · levels mid, senior, lead

In one line

GPU memory ≈ weights (parameters x bytes per parameter) + KV cache + activations and overhead; a 70B model in FP16 needs about 140 GB for weights alone, and quantisation (FP8, INT8, 4-bit AWQ/GPTQ, GGUF) shrinks that by 2 to 4 times, at a quality cost you must evaluate.

Detailed explanation

Weights. BF16/FP16 uses 2 bytes per parameter, FP8/INT8 uses 1, 4-bit about 0.5 (plus small scale overheads). So a 7–8B model needs about 14–16 GB in BF16, and a 70B model about 140 GB, which does not fit on one 80 GB H100 and needs at least two GPUs, usually with tensor parallelism. For MoE models, memory follows the total, not active, parameter count.

KV cache. This is what makes serving efficient. Per token it is 2 x layers x KV heads x head_dim x bytes; for a 70B GQA model roughly 0.3 MB per token in BF16. In practice you often want as much memory for the cache as for the weights to get good batch sizes.

Overhead. Activations, CUDA graphs, the engine's workspace and fragmentation typically take a few GB per GPU. Budget 20 to 50 percent above the weights as a minimum, then size the KV part from target concurrency and context length.

Quantisation. FP8 (on Hopper, Blackwell and recent AMD GPUs) halves weight memory with very small quality loss and also speeds up compute; INT8 (for example SmoothQuant or W8A8) is similar. 4-bit weight-only methods such as AWQ and GPTQ, or GGUF Q4/Q5 formats for llama.cpp, cut weights to about a quarter, so a 70B model fits in about 35–40 GB, on one large GPU with room for cache. The KV cache can be quantised to FP8 too. Lower precision loses more quality, especially on reasoning, maths, code and non-English text, so evaluate on your own task set, not only perplexity.

How it works

  1. Weights = params x bytes/param.
  2. KV per token = 2 x layers x KV heads x head_dim x bytes.
  3. KV total = KV per token x context length x concurrent sequences.
  4. Add 20 percent or more for activations and overhead.
  5. Pick precision and GPU count; validate with a load test and quality eval.

Example

Llama-3.1-70B, target 32 concurrent users x 8K tokens
Weights BF16: 70e9 x 2 = 140 GB      | FP8: 70 GB      | AWQ 4-bit: ~38 GB
KV (BF16, ~0.32 MB/token): 32 x 8192 x 0.32 MB ≈ 84 GB (FP8 KV ≈ 42 GB)
Overhead ~10-15 GB
BF16 total ≈ 240 GB → 4 x 80 GB (TP=4)
FP8 + FP8 KV ≈ 125 GB → 2 x 80 GB (TP=2)

Common mistakes

  • Sizing only for weights and leaving no room for KV cache.
  • Using active parameters for MoE memory estimates.
  • Assuming 4-bit quantisation is free in quality.
  • Mixing up GB and GiB and ending up a few GB short.

How to answer in the interview

"I start with weights: parameters times bytes per parameter, so a 7B model in BF16 is about 14 GB and a 70B is about 140 GB, already more than one 80 GB GPU. Then the KV cache, which grows with context length and concurrency and often needs as much memory again for good throughput, plus activations and engine overhead, so I budget 20 to 50 percent extra. Quantisation helps a lot: FP8 or INT8 halves weight memory, 4-bit AWQ, GPTQ or GGUF cuts it to a quarter, and the KV cache can be FP8 too. The cost is some quality loss, so I evaluate it on our own tasks."

Likely follow-up questions

  • 200 users with 8K prompts? Compute KV for realistic concurrent active users, not total users, then GPUs per replica and replicas.
  • Weight-only vs weight-and-activation quantisation? Weight-only saves memory; W8A8/FP8 also speeds compute.
  • Does quantisation speed decode? Yes, fewer bytes to read per step.
