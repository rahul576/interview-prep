How can Generative AI help with technical documentation?

AI/ML & GenAI · scenario · levels entry

In one line

Generative AI removes the blank page problem in documentation: it drafts READMEs, Javadoc and API docs from code, summarises changes into PR descriptions, release notes and ADR drafts, generates diagrams (Mermaid/PlantUML) and runbooks, improves clarity and consistency, and flags stale docs, but a human expert must review for accuracy.

Detailed explanation

Documentation is usually neglected because writing it is slow and boring. LLMs are strong at turning structured input (code, diffs, notes) into readable prose, which makes them ideal first-draft writers.

Useful applications:

  • From code: a README with setup, configuration properties and endpoints; Javadoc for public methods; descriptions and examples in an OpenAPI spec.
  • From changes: pull request descriptions from diffs, release notes grouped by feature and fix from merged PRs or conventional commits, and changelog entries.
  • From discussions: turning a design thread or meeting notes into an Architecture Decision Record with context, decision and consequences.
  • Diagrams as code: sequence, component or flow diagrams in Mermaid or PlantUML, which render in GitHub, GitLab and Confluence and can be versioned with the code.
  • Operations: turning incident timelines and shell history into runbooks and postmortem drafts.
  • Editing: rewriting for clarity, consistent terminology, a given audience, or translating.
  • Freshness: comparing docs with the code to flag outdated sections.

The key risk is invented behaviour: the model may describe a parameter that does not exist or a retry policy you never implemented. A person who knows the system must review, and generated docs should be grounded in the actual code, preferably generated in the pipeline from source (OpenAPI from annotations, for example).

How it works

  1. Provide the source material: code, diff, notes or logs.
  2. Specify audience, structure and format.
  3. Generate the draft (or diagram code).
  4. Review for accuracy with someone who knows the system.
  5. Commit docs alongside code so they are versioned and reviewed.
  6. Automate refresh steps in CI where possible.

Example

Prompt: "From this controller, draw a sequence diagram of the order flow in Mermaid."

  OrderController->>OrderService: create(order)

  PaymentClient-->>OrderService: authorised
  OrderService->>Kafka: OrderCreated
  OrderController-->>Client: 201 Created

Common mistakes

  • Publishing generated docs without expert review.
  • Generating docs once and never updating them.
  • Producing verbose text that hides the important points.
  • Feeding confidential designs into unapproved tools.

How to answer in the interview

"AI is great at removing the blank page. It can draft a README from the codebase, generate or improve Javadoc and OpenAPI descriptions, write PR descriptions and release notes from diffs, turn a design discussion into an ADR draft, and produce Mermaid or PlantUML diagrams that live with the code. It also helps turn incident notes into runbooks and makes existing docs clearer and more consistent. But it can invent behaviour, so someone who knows the system reviews everything, and I keep docs in the repository so they're reviewed with code changes."

Likely follow-up questions

  • How do you keep AI docs from going stale? Keep them in the repo, regenerate in CI from code where possible, and have AI flag mismatches in PR review.
  • Which docs should never be auto-generated? Security or compliance statements without careful human authorship.
  • Why diagrams as code? They are versionable, diffable and easy for AI to update.
