What is the difference between Docker volumes plugins and storage options for multi-host setups?

Docker · concept · levels senior

In one line

The default local volume driver keeps data on one host, so a container rescheduled elsewhere loses access to it; multi-host setups use volume plugins/drivers for NFS/SMB shares, cloud block storage or distributed storage, choosing between block storage (single attach, fast, good for databases) and shared file storage (many readers/writers, weaker semantics), and in Kubernetes this is standardised by CSI.

Detailed explanation

A named volume like docker volume create pgdata uses the local driver: the data sits in /var/lib/docker/volumes/pgdata/_data on that machine. That is perfect on a single host, but in Swarm or any multi-host setup, a container moved to another host gets an empty new volume there.

Docker supports volume drivers (plugins) that put the data somewhere reachable from multiple hosts. The local driver itself can mount NFS or CIFS/SMB shares through driver_opts. Plugins and vendor drivers exist for cloud block storage (EBS, Azure Disk), and for distributed storage systems like Portworx, Ceph/RBD or GlusterFS. Many older Docker plugins are now unmaintained, which is one reason the ecosystem moved to Kubernetes.

The important design choice is the storage semantics:

  • Block storage (EBS, Azure Disk, iSCSI): a raw disk attached to one host at a time (ReadWriteOnce), formatted with a local filesystem. Low latency and correct fsync, good for databases, but failover means detaching and reattaching, often within one availability zone.
  • Shared file storage (NFS, EFS, Azure Files, SMB): many hosts mount it simultaneously (ReadWriteMany). Great for shared uploads or content, but higher latency, different locking and caching behaviour, and risk for databases.

In Kubernetes, the Container Storage Interface (CSI) replaced in-tree and Docker-style plugins. You define a StorageClass, request a PersistentVolumeClaim, and the CSI driver provisions and attaches a PersistentVolume wherever the pod is scheduled, with access modes, topology and snapshots.

How it works

  1. Decide the access pattern: one writer (block) or many (file).
  2. Choose a driver: local+NFS options, a cloud or vendor plugin, or CSI in Kubernetes.
  3. Create the volume with the driver; it is mounted on whichever host runs the container.
  4. On rescheduling, the storage is detached and reattached (block) or simply mounted again (file).
  5. Handle backups and snapshots at the storage layer.

Example

# Docker Compose / Swarm: NFS-backed volume reachable from every node
volumes:
  shared-uploads:
    driver: local
    driver_opts:
      type: nfs
      o: "addr=10.0.5.20,nfsvers=4.1,rw,hard"
      device: ":/exports/uploads"
# Kubernetes equivalent via CSI
apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: pgdata }
spec:
  accessModes: [ReadWriteOnce]
  storageClassName: gp3
  resources: { requests: { storage: 100Gi } }

Common mistakes

  • Using local volumes in Swarm and losing data after rescheduling.
  • Putting databases on NFS without understanding locking and fsync.
  • Forgetting block volumes are zonal, so pods can't move to another zone.
  • Relying on abandoned third-party Docker volume plugins.

How to answer in the interview

"A normal named volume uses the local driver, so the data lives on one host, and if the container moves to another host it doesn't follow. For multi-host setups Docker has volume drivers or plugins that store data elsewhere: NFS or SMB shares, cloud block storage like EBS or Azure Disk, or distributed systems like Portworx or Ceph. Block storage attaches to one host at a time but performs well and suits databases; shared file storage can be mounted by many containers but has weaker locking and lower performance. In Kubernetes the same idea is standardised as CSI drivers with StorageClasses, PersistentVolumeClaims and PersistentVolumes."

Likely follow-up questions

  • Why is NFS often poor for databases? Higher latency, client caching and locking semantics that can lead to corruption or poor performance.
  • What does ReadWriteOnce mean? The volume can be mounted read-write by a single node at a time.
  • How do you move zonal block storage? Snapshot and restore in the target zone, or use regional disks.
