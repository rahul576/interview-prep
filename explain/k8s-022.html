What runs on a worker node, and what is the role of the container runtime interface?

Kubernetes · concept · levels entry, mid, senior

In one line

A worker node runs the kubelet (manages pods, probes, volumes, status), a container runtime such as containerd or CRI-O reached through the CRI gRPC API, plus kube-proxy (or an eBPF replacement) and the CNI plugin for networking; dockershim was removed in 1.24, but Docker-built OCI images still run.

Detailed explanation

The kubelet is the node agent. It registers the node, sends heartbeats via Lease objects, watches the API for pods bound to its node, and makes them real: pulls images, sets up volumes (with CSI node plugins), starts containers, runs liveness, readiness and startup probes, enforces resource limits via cgroups, performs node-pressure eviction, and reports pod and node status. It also runs static pods from a local manifest directory.

The kubelet does not run containers itself. It talks to a container runtime over the Container Runtime Interface (CRI), a gRPC API with two services: RuntimeService (create pod sandboxes, start and stop containers, exec, logs) and ImageService (pull, list, remove images). containerd (via its CRI plugin) and CRI-O are the common runtimes; underneath they use a low-level OCI runtime such as runc or crun, or sandboxed ones like gVisor or Kata Containers selected with a RuntimeClass.

Docker Engine never implemented CRI, so Kubernetes contained an adapter, dockershim, which was removed in 1.24. Clusters switched to containerd directly. Nothing changed for images: Docker builds standard OCI images, which any CRI runtime runs. What changed is node debugging, since there's no docker CLI on nodes.

Networking: the runtime calls the CNI plugin to give each pod an interface and IP; kube-proxy programmes Service routing (iptables, IPVS or nftables), unless an eBPF dataplane like Cilium replaces it. Node agents for logs, metrics and security usually run as DaemonSets.

How it works

  1. Scheduler binds a pod to the node.
  2. Kubelet sees it, calls CRI to create a pod sandbox.
  3. Runtime calls CNI to set up networking.
  4. Kubelet pulls images through CRI ImageService.
  5. Containers start via runc; kubelet runs probes.
  6. Kubelet reports status; kube-proxy routes Service traffic.

Example

# On a node without docker
crictl ps                       # running containers
crictl pods                     # pod sandboxes
crictl logs <container-id>
crictl inspecti registry.example.com/api:5.1
journalctl -u kubelet -f
kubectl get node node-1 -o jsonpath='{.status.nodeInfo.containerRuntimeVersion}'
# containerd://2.x

Common mistakes

  • Thinking Docker images stopped working after 1.24.
  • Mounting /var/run/docker.sock in CI pods on containerd nodes.
  • Confusing the kubelet with the container runtime.
  • Forgetting system-reserved resources for kubelet and runtime.

How to answer in the interview

"A worker node runs the kubelet, which registers the node, watches for pods assigned to it, starts and stops containers, runs probes, mounts volumes and reports status. It doesn't run containers itself: it talks to a runtime like containerd or CRI-O through the Container Runtime Interface, a gRPC API for sandboxes, containers and images. Docker Engine was supported via dockershim, removed in 1.24, but Docker-built images still work because they're OCI images. Networking comes from the CNI plugin and kube-proxy or an eBPF replacement, and agents like log shippers run as DaemonSets."

Likely follow-up questions

  • How do you debug without docker? crictl on the node, kubectl debug node/..., and kubelet logs via journalctl.
  • What is a RuntimeClass? Selects a runtime handler, such as gVisor or Kata, per pod.
  • How do you build images in CI without Docker socket? BuildKit rootless, Kaniko-style builders or Buildah.
