What is runtime polymorphism? Explain with an example.

Core Java & OOP · concept · levels mid, senior

In one line

Runtime polymorphism means the method executed is chosen at runtime from the object's actual class, not the reference type; it comes from method overriding and is implemented by dynamic method dispatch (late binding).

Detailed explanation

Polymorphism means "many forms": one reference type, many behaviours. Java has two kinds. Compile-time polymorphism is method overloading: the compiler chooses among methods with different parameter lists. Runtime polymorphism is method overriding: a subclass or implementing class provides its own version of an inherited instance method, and the JVM chooses at runtime.

The key mechanics: a variable has a static type (declared) and points to an object with a dynamic type (actual class). The compiler only checks that the method exists on the static type. At runtime, the JVM looks at the object's class and invokes the most specific override. HotSpot implements this with virtual method tables (vtables, itables for interfaces), and the JIT often removes the indirection by inlining when only one or two implementations are seen at a call site.

Why it matters: code can depend on an abstraction (Payment, List, Repository) and work with any implementation, including ones written later. This is the basis of the open/closed principle, the Strategy pattern, plugin architectures, and Spring injecting PaymentService without the caller knowing the concrete class. It replaces long if/else or switch chains on type codes.

What does not participate: static methods (hidden), private methods (not inherited), final methods (cannot be overridden), constructors and fields (field access uses the static type). Modern Java offers a complementary approach for closed hierarchies: sealed interfaces with pattern-matching switch (Java 21).

How it works

  1. Define a method in a superclass or interface.
  2. Subclasses override it with the same signature (covariant return allowed).
  3. Code holds a superclass or interface reference to a subclass object.
  4. The compiler emits invokevirtual or invokeinterface.
  5. At runtime the JVM uses the object's class to find the override and calls it.

Example

interface Payment { String pay(BigDecimal amount); }
class CardPayment implements Payment {
    public String pay(BigDecimal a) { return "Charged card " + a; }
}
class UpiPayment implements Payment {
    public String pay(BigDecimal a) { return "Collected via UPI " + a; }
}

List<Payment> payments = List.of(new CardPayment(), new UpiPayment());
for (Payment p : payments)
    System.out.println(p.pay(new BigDecimal("499")));  // each object's own version

Payment p = new UpiPayment();   // static type Payment, dynamic type UpiPayment
p.pay(BigDecimal.TEN);          // calls UpiPayment.pay

Common mistakes

  • Calling overloading "runtime polymorphism".
  • Expecting fields to be polymorphic.
  • Calling overridable methods from constructors, so the subclass runs before it is initialised.
  • Using instanceof chains instead of overriding.

How to answer in the interview

"Runtime polymorphism means the method that runs is chosen at runtime based on the actual object, not the reference type. It comes from overriding and is called dynamic dispatch or late binding. For example, Payment has a pay method and CardPayment and UpiPayment override it. If I write Payment p = new UpiPayment() and call p.pay, the UPI version runs even though the reference is Payment. The JVM resolves it through the virtual method table. This lets code depend on an interface and work with any implementation, which is the basis of the Strategy pattern and of Spring injecting interfaces."

Likely follow-up questions

  • Is method overloading an example of runtime polymorphism? No, overloads are chosen at compile time from argument types.
  • Are fields polymorphic? No, field access uses the declared type.
  • Why avoid calling overridable methods in constructors? The override can run before the subclass fields are initialised.
