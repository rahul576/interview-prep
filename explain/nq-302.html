Have you worked with Docker and Kubernetes?

Docker · scenario · levels entry

In one line

Answer concretely and honestly: describe the Dockerfiles (multi-stage, non-root), Compose for local dependencies, the Kubernetes objects you used (Deployments, Services, Ingress, ConfigMaps, Secrets, HPA, probes), Helm and the managed cluster, how you troubleshoot with kubectl, and what you owned versus the platform team.

Detailed explanation

This is an experience question. The interviewer wants to know your real level, and whether they can trust what you say. Vague answers ("yes, we used Docker and Kubernetes") score poorly. Specific details show genuine hands-on work: image size, probe configuration, a real incident.

A strong answer covers four layers:

  • Building images: multi-stage Dockerfiles (a JDK/Maven stage to build, a slim JRE or distroless stage to run), layer caching, a non-root user, .dockerignore, image scanning (Trivy) and tagging by git SHA.
  • Local development: Docker Compose to start PostgreSQL, Kafka and Redis, or Testcontainers in integration tests.
  • Kubernetes runtime: Deployments with readiness and liveness probes (for example Spring Boot Actuator /actuator/health/readiness), resource requests and limits, Services, Ingress, ConfigMaps and Secrets (often synced from a vault), and the HorizontalPodAutoscaler. Delivery happened through Helm charts or Kustomize, often via a GitOps tool like Argo CD, on EKS, AKS or GKE.
  • Operations: kubectl get/describe/logs/exec, reading events, and diagnosing CrashLoopBackOff, OOMKilled, ImagePullBackOff or failing probes.

Be honest about scope. "The platform team ran the clusters and ingress controller; I owned our service's Dockerfile, Helm chart and alerts" is a perfectly good answer for an entry or mid role. Never claim to have administered clusters if you haven't. A follow-up will expose it.

How it works

  1. Name the context: the stack, how many services, which cloud.
  2. Describe what you built: the Dockerfile and Compose.
  3. Describe the Kubernetes setup and deployment pipeline.
  4. Give one troubleshooting story.
  5. State your ownership boundary and what you are learning next.

Example

FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /app
COPY pom.xml .
RUN mvn -q dependency:go-offline
COPY src ./src
RUN mvn -q package -DskipTests

FROM eclipse-temurin:21-jre
RUN useradd -r -u 1001 app
COPY --from=build /app/target/app.jar /app/app.jar
USER 1001
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75", "-jar", "/app/app.jar"]

Debug story: pods restarted with OOMKilled. kubectl describe pod showed the 512 Mi limit, and the JVM heap was not container-aware in our old flags. Setting MaxRAMPercentage and raising the limit to 768 Mi fixed it.

Common mistakes

  • Listing buzzwords with no specifics.
  • Overclaiming cluster administration you never did.
  • Not knowing what your own probes or resource limits were.
  • Having no troubleshooting example ready.

How to answer in the interview

"Yes. I containerised our Spring Boot services with multi-stage Dockerfiles: a Maven/JDK stage to build and a slim JRE image running as a non-root user. Locally we used Docker Compose for PostgreSQL, Kafka and Redis. In production the services ran on AKS, deployed with Helm through our pipeline. I wrote the Deployments with readiness and liveness probes on Actuator, resource requests and limits, ConfigMaps, Secrets and an HPA. When things break I use kubectl describe, logs with --previous, and events. For example, I fixed an OOMKilled loop by tuning the JVM memory flags. The platform team owned the cluster itself and the ingress controller."

Likely follow-up questions

  • Hardest Kubernetes issue? For example, a readiness probe that was too strict and caused cascading restarts during a slow database start.
  • Liveness versus readiness? Readiness removes the pod from traffic. Liveness restarts the container.
  • How are secrets handled? Kubernetes Secrets synced from Key Vault or Secrets Manager via a CSI driver or External Secrets.
