What is integration testing?

Testing · concept · levels entry

In one line

Integration testing checks that several components work together with real infrastructure or framework code, for example a repository against a real database or a REST endpoint through the Spring context, using tools like @SpringBootTest, slice tests, Testcontainers, WireMock and MockMvc; such tests are slower, so there are fewer of them.

Detailed explanation

Unit tests prove each piece works alone, but most production bugs live in the seams between pieces: a JPQL query with a typo, a column mapped to the wrong type, a Jackson setting that renames a field, a missing @Transactional, a security rule blocking an endpoint, a Kafka deserialiser mismatch, a Flyway migration that fails on the real engine. Integration tests exercise those seams with real collaborators.

Typical integration tests in a Spring Boot service:

  • Persistence: repositories, custom queries and migrations against PostgreSQL in Testcontainers, often with @DataJpaTest so each test rolls back.
  • Web layer: controllers through MockMvc or a real server with @SpringBootTest(webEnvironment = RANDOM_PORT) and WebTestClient or REST Assured, verifying status codes, validation, JSON shape, error handling and security.
  • Messaging: listeners and producers against a real Kafka or RabbitMQ container.
  • External HTTP APIs: WireMock simulates the third-party service, including errors and slow responses, so the real HTTP client, serialisation, timeouts and retries are tested.
  • Full flows: an API call that writes to the database and publishes an event, asserting both.

Testcontainers is preferred over H2 because it runs the same database engine and version as production; H2's compatibility modes do not support every feature and behave differently for locking, types and SQL functions.

Integration tests take seconds rather than milliseconds and need Docker, so the test pyramid keeps them fewer than unit tests. They are still far cheaper and more reliable than full end-to-end tests across deployed services. Keep them independent: each test creates its own data or relies on rollback.

How it works

  1. Spring starts the relevant part of the context (slice or full).
  2. Testcontainers starts real dependencies; @ServiceConnection wires them in.
  3. WireMock stands in for third-party HTTP APIs.
  4. The test calls the real entry point (HTTP, message, method).
  5. Assertions check responses and side effects in DB or topics.
  6. Data is rolled back or isolated per test.

Example

@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@Testcontainers
class CustomerApiIT {

    @Container @ServiceConnection
    static PostgreSQLContainer<?> pg = new PostgreSQLContainer<>("postgres:16");

    @Autowired WebTestClient client;
    @Autowired CustomerRepository repo;

    @Test
    void createsCustomerAndStoresIt() {
        client.post().uri("/customers")
              .bodyValue(Map.of("name", "Asha", "email", "asha@example.com"))
              .exchange()
              .expectStatus().isCreated()
              .expectBody().jsonPath("$.id").isNotEmpty();

        assertThat(repo.findByEmail("asha@example.com")).isPresent();
    }

    @Test
    void rejectsInvalidEmail() {
        client.post().uri("/customers")
              .bodyValue(Map.of("name", "Asha", "email", "not-an-email"))
              .exchange()
              .expectStatus().isBadRequest();
    }
}

Common mistakes

  • Using H2 and missing production SQL behaviour.
  • Mocking so much in "integration" tests that nothing real is integrated.
  • Tests sharing data and failing depending on order.
  • Writing every scenario as an integration test, making the build slow.

How to answer in the interview

"Integration tests check that several parts work together with real infrastructure or the framework: a repository running its queries against a real PostgreSQL, a REST controller through the full Spring context with serialisation, validation and security, or a Kafka listener consuming real messages. In Spring Boot I use SpringBootTest or slices like DataJpaTest and WebMvcTest, Testcontainers for real databases and brokers, and WireMock for external APIs. They catch wiring, mapping, SQL and configuration bugs that unit tests can't, but they're slower, so following the test pyramid there are fewer of them than unit tests."

Likely follow-up questions

  • Why Testcontainers over H2? Same engine and version as production, so dialect and behaviour match.
  • How do you isolate test data? Rollback in @DataJpaTest, unique ids per test, or cleanup in @AfterEach.
  • How do you keep them fast? Shared containers and a cached Spring context.
