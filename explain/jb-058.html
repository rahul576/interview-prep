How would you choose between ArrayList, LinkedList, HashSet, and ConcurrentHashMap for a high-throughput application?

Collections · design · levels senior, lead

In one line

Choose by access pattern and concurrency: ArrayList for append-and-iterate data (cache friendly), almost never LinkedList, HashSet for O(1) membership, and ConcurrentHashMap for shared mutable state across threads, then presize and verify with JMH and profiling.

Detailed explanation

In high-throughput systems the constant factors matter as much as Big-O. Modern CPUs are fast at streaming through contiguous memory and slow at pointer chasing, and every extra object adds allocation and GC pressure.

ArrayList is the default for ordered data that is mostly appended and iterated: one compact array, O(1) index access and excellent cache locality. Presize it with the expected capacity to avoid repeated copies.

LinkedList rarely wins, even for inserts: each element is a separate node of 24 or more bytes plus the element itself, nodes are scattered across the heap, and finding a position is O(n). For queues and stacks, ArrayDeque is faster.

HashSet gives average O(1) contains, ideal for de-duplication, idempotency checks or "seen ids". Performance depends on a well-distributed hashCode and on sizing to avoid rehashing (HashSet.newHashSet(n) in Java 19+). For primitive ids at very large scale, primitive collections (Eclipse Collections, fastutil) avoid boxing.

ConcurrentHashMap is the tool when many threads read and update the same map: counters, caches, session registries. Use atomic operations like merge, compute and computeIfAbsent, and LongAdder values for hot counters. If the data is read-mostly and changes rarely, an immutable map swapped through a volatile reference is even cheaper. For thread-confined data, plain HashMap per thread or per request avoids any synchronisation.

Finally, measure: write JMH benchmarks for the hot path with realistic sizes and use a profiler such as async-profiler or JFR to confirm allocation and cache behaviour.

How it works

  1. Identify the operations: append, index, insert, membership, key lookup.
  2. Identify sharing: thread-confined, read-mostly or concurrently mutated.
  3. Pick the simplest structure that fits.
  4. Presize with expected capacity.
  5. Benchmark with JMH and profile in production-like load.

Example

List<Event> batch = new ArrayList<>(BATCH_SIZE);         // append + iterate
Set<String> seen = HashSet.newHashSet(1_000_000);         // dedup, Java 19+
if (!seen.add(event.id())) return;                        // already processed

ConcurrentMap<String, LongAdder> perTenant = new ConcurrentHashMap<>();
perTenant.computeIfAbsent(tenant, t -> new LongAdder()).increment();

@Benchmark public long iterateArrayList() { long s = 0; for (int x : arrayList) s += x; return s; }
@Benchmark public long iterateLinkedList() { long s = 0; for (int x : linkedList) s += x; return s; }

Common mistakes

  • Picking LinkedList for "frequent inserts" without measuring.
  • Locking a HashMap with synchronized around every call instead of using ConcurrentHashMap.
  • Poor hashCode implementations causing collisions.
  • Micro-benchmarking with System.nanoTime loops instead of JMH.

How to answer in the interview

"I start from the access pattern and whether data is shared between threads. For ordered data that's mostly appended and iterated, ArrayList is my default because the contiguous array is cache friendly. LinkedList almost never wins because of pointer chasing and per-node overhead; for queues I use ArrayDeque. For fast membership and de-duplication I use HashSet, which needs a well-distributed hashCode. When many threads update shared state like counters or caches, I use ConcurrentHashMap with merge or computeIfAbsent. I presize collections and confirm choices with JMH and profiling."

Likely follow-up questions

  • When would you use an immutable copy instead? For read-mostly data: rebuild and publish a new immutable map, so readers need no locks.
  • What does JMH protect against? JIT warm-up, dead-code elimination and other benchmarking pitfalls.
  • Primitive collections? They avoid boxing and save memory for large numeric data sets.
