How would you design a standard API response structure?

REST & API Design · design · levels mid, senior

In one line

Keep responses consistent across services: return the resource directly (or a data envelope with metadata for collections), let the HTTP status code carry the outcome, use one error format based on RFC 9457 Problem Details with a stable error code, field errors and trace id, and follow shared naming, date and versioning rules.

Detailed explanation

A standard structure lets client developers write one error handler and one pagination helper for all your APIs, and makes support easier.

Success responses. For single resources, return the resource itself: { "id": 42, "status": "PAID", ... }. For collections, use an envelope with metadata: { "items": [...], "page": {...} } or { "data": [...], "nextCursor": "..." }. Avoid wrapping everything in { "success": true, "data": ... }: the status code already says success or failure, and HTTP tooling (gateways, monitoring, retries) relies on it.

Errors. Use RFC 9457 Problem Details for HTTP APIs (it obsoletes RFC 7807), media type application/problem+json. Standard members:

  • type: URI identifying the error type (can link to documentation);
  • title: short human-readable summary;
  • status: HTTP status code;
  • detail: explanation for this occurrence;
  • instance: URI of the request or occurrence.

Add extension members: a stable, machine-readable code (ORDER_ALREADY_SHIPPED) clients can branch on, an errors array of field-level validation problems, and a traceId/correlation id that support can search in logs and traces. Spring 6 / Boot 3 support this with ProblemDetail and ErrorResponseException; set spring.mvc.problemdetails.enabled=true for built-in exceptions, and use a @RestControllerAdvice to map your own.

Never include stack traces, SQL or internal hostnames in errors; log them with the trace id instead.

Conventions. One naming style (camelCase JSON), ISO 8601 timestamps with time zone (2026-11-21T10:15:30Z), money as decimal strings or minor units with currency, enums as strings, consistent null handling (omit or null, but be consistent). Changes are additive to stay backward compatible; clients should ignore unknown fields. Document everything in a shared OpenAPI components file and lint it.

How it works

  1. Define a shared API guideline and OpenAPI components.
  2. Success: resource or collection envelope with metadata.
  3. Errors: global handler converts exceptions to Problem Details.
  4. Trace id added from the tracing context.
  5. CI lints specs for compliance.

Example

@RestControllerAdvice
class ApiErrors {
    @ExceptionHandler(MethodArgumentNotValidException.class)
    ProblemDetail validation(MethodArgumentNotValidException ex) {
        ProblemDetail pd = ProblemDetail.forStatus(HttpStatus.BAD_REQUEST);
        pd.setType(URI.create("https://api.shop.com/errors/validation"));
        pd.setTitle("Validation failed");
        pd.setProperty("code", "VALIDATION_ERROR");
        pd.setProperty("errors", ex.getFieldErrors().stream()
            .map(f -> Map.of("field", f.getField(), "message", f.getDefaultMessage())).toList());
        pd.setProperty("traceId", Span.current().getSpanContext().getTraceId());
        return pd;
    }
}

Common mistakes

  • 200 OK with "success": false.
  • Different error shapes per service or endpoint.
  • Only human-readable messages, no stable error code.
  • Leaking exception details.
  • Inconsistent date formats and naming.

How to answer in the interview

"I keep one structure across all services. Success responses return the resource directly, or for collections an envelope with pagination metadata, and the HTTP status carries the outcome rather than a success flag inside a 200. Errors follow RFC 9457 Problem Details, the successor of RFC 7807, which Spring supports with ProblemDetail: type, title, status and detail, plus my own fields like a stable machine-readable error code, a list of field errors for validation, and a trace id support can search in logs. Field names are camelCase, dates ISO 8601, and changes are additive so existing clients don't break."

Likely follow-up questions

  • Why is returning 200 OK with an error flag in the body a bad idea? Gateways, monitoring, caches and retry logic see success; clients must parse every body.
  • Why a separate error code when you have status? Status is coarse; the code identifies the specific business error.
  • Should you wrap single resources in a data envelope? Not necessary; keep envelopes for collections and metadata.
