What is Microsoft Entra ID, and how do managed identities work?

Azure · concept · levels entry, mid

In one line

Microsoft Entra ID (formerly Azure AD) is Microsoft's cloud identity platform; a managed identity is a service principal that Azure creates and rotates for a resource, so code obtains tokens without any secret, either system-assigned (tied to one resource) or user-assigned (standalone and reusable).

Detailed explanation

Entra ID handles authentication and authorisation for users, groups, devices and applications using standards such as OAuth 2.0, OpenID Connect and SAML. It also provides conditional access, MFA and Privileged Identity Management.

Applications are represented in two ways. An app registration is the global definition of an application. A service principal is its local instance in a tenant, and that is what you grant roles to. Traditionally, an app authenticates as its service principal with a client secret or certificate, which must be stored, protected and rotated, and leaked secrets are a frequent cause of breaches.

Managed identities remove that burden. Azure creates a service principal for a resource such as a VM, App Service, Function, Container App or AKS workload, and manages its credentials internally. The code asks the local Azure Instance Metadata Service (or an equivalent endpoint on PaaS) for an access token for a target resource such as Key Vault or Storage, and receives a short-lived token. There is nothing to store in configuration and nothing to rotate.

There are two types. A system-assigned identity is enabled on a resource and shares its lifecycle: delete the resource and the identity is deleted. A user-assigned identity is a separate Azure resource that you can attach to several resources, pre-create and grant permissions to before deployment, and keep when resources are recreated. User-assigned identities are also what AKS workload identity federates with. Either way, you grant access through RBAC role assignments on the target.

How it works

  1. Enable a system-assigned identity on the resource, or create and attach a user-assigned identity.
  2. Grant it an RBAC role on the target, such as Key Vault Secrets User.
  3. Application code uses an SDK credential, such as DefaultAzureCredential.
  4. The SDK requests a token from the local identity endpoint.
  5. Entra ID issues a short-lived token; the app calls the target service.
  6. Azure rotates the underlying credentials automatically.

Example

az identity create -g rg-app -n id-orders-api
az webapp identity assign -g rg-app -n orders-api \
  --identities /subscriptions/<sub>/resourceGroups/rg-app/providers/Microsoft.ManagedIdentity/userAssignedIdentities/id-orders-api
az role assignment create --assignee <principal-id> \
  --role "Key Vault Secrets User" --scope <key-vault-resource-id>
from azure.identity import DefaultAzureCredential
from azure.keyvault.secrets import SecretClient
client = SecretClient("https://kv-orders.vault.azure.net", DefaultAzureCredential())
db_password = client.get_secret("db-password").value

Common mistakes

  • Storing client secrets in app settings when a managed identity would work.
  • Granting the identity Contributor on the subscription instead of a narrow data role.
  • Using system-assigned identities where resources are recreated often, breaking role assignments.
  • Forgetting that user-assigned identities need explicit client ID selection when several are attached.
  • Confusing app registrations with service principals.

How to answer in the interview

"Microsoft Entra ID, formerly Azure AD, is the identity platform for users, groups and applications, based on OAuth and OpenID Connect. Applications are represented by app registrations and service principals. A managed identity is a service principal that Azure manages for a resource like a VM, App Service or AKS workload: the code requests tokens from a local endpoint, so there are no secrets in code or config and credentials rotate automatically. System-assigned identities live and die with the resource; user-assigned identities are standalone and can be shared and pre-authorised. I then grant the identity least-privilege RBAC roles, for example Key Vault Secrets User on one vault."

Likely follow-up questions

  • How does AKS workload identity map a service account to an Entra identity? A federated credential on a user-assigned identity trusts the cluster's OIDC issuer and a specific service account.
  • When would you still use a service principal with a certificate? For workloads outside Azure that cannot use federation.
  • What is DefaultAzureCredential? An SDK chain that tries environment, workload identity, managed identity and developer credentials in order.
