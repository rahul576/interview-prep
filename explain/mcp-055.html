What is step-up authorization in MCP?

MCP Servers · concept · levels senior, lead

In one line

Step-up authorization means starting with minimal scopes and requesting more only when needed: the server returns 403 with insufficient_scope and the required scopes in WWW-Authenticate, the client re-authorizes with the combined scopes and user consent, then retries.

Detailed explanation

Asking for every scope up front is bad for least privilege: the token sitting in a client can do far more than most tasks need, and users approve a long consent list without reading it. Step-up flips this. The client first obtains a token with modest scopes, for example repo:read, which covers most tools.

When the user asks for something more powerful, such as creating a release, merging a PR or approving a payment, the server checks the token's scopes and rejects the call with HTTP 403 and a WWW-Authenticate header containing error="insufficient_scope" and a scope value listing what is required. The MCP specification describes this flow and how clients should react.

The client then starts a new authorization request including the previously granted scopes plus the new ones, so it does not lose existing access. The user sees a consent screen for the additional permission, approves it, and the client retries the original call with the new token.

This has practical benefits: users become aware when the agent needs more power, the identity provider can attach stronger requirements to sensitive scopes such as fresh MFA or a shorter token lifetime, and stolen tokens from routine sessions are less damaging. Step-up complements host-level approvals: approval says "yes, do this specific action", step-up says "this client may now hold this permission".

How it works

  1. Client obtains token with orders:read.
  2. Model calls refund_order; server requires orders:refund.
  3. Server responds 403 with WWW-Authenticate: Bearer error="insufficient_scope", scope="orders:read orders:refund".
  4. Client starts authorization with both scopes; IdP may require MFA.
  5. User consents; client gets the new token and retries the call.
  6. Optionally the elevated token is short-lived and drops back afterwards.

Example

HTTP/1.1 403 Forbidden
WWW-Authenticate: Bearer error="insufficient_scope",
  scope="orders:read orders:refund",
  resource_metadata="https://mcp.shop.example/.well-known/oauth-protected-resource",
  error_description="Refunds require orders:refund"

Common mistakes

  • Requesting all scopes at first login "to avoid friction".
  • Returning 401 instead of 403, which makes clients think the token is invalid.
  • Requesting only the new scope and losing previously granted ones.
  • Treating step-up as a replacement for confirming the specific action.

How to answer in the interview

"Step-up authorization is least privilege over time. The client starts with a token that has minimal scopes, say read access, which is enough for most tools. When the user asks for something that needs more, like creating a release or approving a payment, the server rejects it with 403 and an insufficient_scope error in the WWW-Authenticate header listing the scopes required. The client starts a new authorization including the existing scopes plus the new ones, the user approves the extra consent, and the call is retried with the new token. It avoids broad permissions up front, makes users aware when the agent needs more power, and lets sensitive scopes require fresh MFA or shorter lifetimes."

Likely follow-up questions

  • How combine with host approval? Host confirms the exact action; step-up grants the permission once; both are logged.
  • 401 vs 403? 401 means no or invalid token; 403 means valid token lacking permission.
  • Can elevated scopes expire sooner? Yes, the IdP can issue short-lived tokens for sensitive scopes.
