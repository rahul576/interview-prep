How do you force Terraform to recreate a single resource?

Infrastructure as Code · concept · levels entry

In one line

Use terraform apply -replace="ADDRESS", which plans a destroy-and-recreate of just that resource and shows it in the plan for review; it replaced the older terraform taint, and create_before_destroy avoids downtime.

Detailed explanation

Sometimes a resource's configuration is correct but the real object is not: an instance that is unhealthy or was modified by hand, a VM whose user data should run again, a key, password or certificate that must be regenerated or rotated. Terraform would show no changes because nothing in the code differs, so you need to ask explicitly for replacement.

terraform plan -replace="aws_instance.web[0]" or terraform apply -replace=... tells Terraform to treat the resource as if a force-new argument changed. The plan shows the -/+ action with "will be replaced, as requested", so it can be reviewed like any other change, and nothing is altered until apply. You can pass -replace multiple times. Addresses with indexes or keys need quoting in the shell, for example -replace='aws_iam_access_key.ci["deploy"]'.

Before Terraform 0.15.2 the tool was terraform taint, which immediately wrote a mark into the state saying "recreate this on the next apply". That had two problems: it changed shared state without showing the impact, and anyone else's next apply would unexpectedly recreate the resource. Taint still exists but is deprecated in favour of -replace. Terraform also taints resources automatically when creation fails partway, which is why a failed provisioner leads to replacement next time.

Replacement follows the usual graph rules: resources that depend on the replaced one are updated if they reference changed attributes such as its ID or IP, and may themselves be replaced if those attributes force new resources. For resources serving traffic, lifecycle { create_before_destroy = true } creates the new object first, then deletes the old one, which requires that names do not collide. For declarative, repeatable triggers, replace_triggered_by replaces a resource whenever another value changes.

How it works

  1. Run plan/apply with -replace=ADDRESS.
  2. Terraform plans delete + create for that address.
  3. Dependent resources referencing changed attributes are updated or replaced.
  4. Review, then apply.
  5. State records the new object.

Example

terraform plan -replace='aws_instance.web[0]' -out=tfplan
terraform show tfplan | grep -A3 "replaced"
terraform apply tfplan

# Rotate a generated password
terraform apply -replace='random_password.db'
resource "aws_instance" "web" {
  count = 2
  # ...
  lifecycle {
    create_before_destroy = true
  }
}

Common mistakes

  • Using terraform taint on shared state without telling the team.
  • Replacing a stateful resource (database, volume) without a backup.
  • Forgetting quotes around addresses with brackets.
  • Replacing to "fix" drift that should be fixed in code.

How to answer in the interview

"I use terraform plan or apply with -replace and the resource address, for example -replace='aws_instance.web[0]'. Terraform plans to destroy and recreate just that resource even though its configuration hasn't changed, and it shows up in the plan, so it can be reviewed first. That replaced the old terraform taint command, which modified state immediately without showing the effect. Typical reasons are a broken or manually modified instance, rotating a key or certificate, or re-running user data. For things serving traffic I use create_before_destroy so the replacement comes up before the old one goes away."

Likely follow-up questions

  • What happens to resources that depend on the replaced one? They're updated if they reference changed attributes, and may be replaced if those attributes force it.
  • Why did Terraform replace a resource I didn't ask for? It was tainted after a failed create or provisioner.
  • How do you replace automatically when something else changes? replace_triggered_by in the lifecycle block.
