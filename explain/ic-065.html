What is the difference between push and pull configuration management, and how can Ansible do pull?

Configuration Management · concept · levels mid

In one line

Push means a central control node connects out to servers and applies changes (Ansible's default); pull means each node fetches and applies its own configuration on a schedule (Puppet, Chef); Ansible does pull with ansible-pull on a systemd timer or cron, or via AWS SSM State Manager.

Detailed explanation

Push gives immediate, coordinated changes: you decide when it runs, on which hosts, in which order, with rolling batches and a single place to see results. The costs are that the control node needs network access and credentials for every host, a run across thousands of hosts is limited by forks and SSH connections, and hosts that are offline or just created by an autoscaler are missed until someone runs the playbook again.

Pull inverts the direction. Each node runs an agent or timer that fetches the desired configuration and applies it locally. It scales naturally (each host does its own work), works behind NAT and firewalls because connections are outbound, and suits ephemeral and autoscaled nodes: a new instance configures itself on boot. The costs are slower and less coordinated changes: you wait for the next interval, ordering across hosts is hard, and you need reporting to know whether every node has converged.

ansible-pull clones a Git repository (-U url, -C branch) and runs a playbook (by default local.yml, or one named after the host) against localhost. With -o/--only-if-changed it runs only when the repository has new commits. A systemd timer or cron triggers it.

On AWS, Systems Manager State Manager can run the AWS-ApplyAnsiblePlaybooks document on instances selected by tag on a schedule, with compliance reporting in the console, and Run Command can trigger it immediately.

How it works

  1. Base image includes Ansible and a deploy key or token for the repo.
  2. A systemd timer or cron job runs ansible-pull every 30 minutes with a random delay.
  3. The node clones/updates the repo and applies local.yml to itself.
  4. Logs and results go to central logging or a callback plugin.
  5. Urgent changes are forced via SSM Run Command or a push run.

Example

# /etc/cron.d/ansible-pull: every 30 minutes, random delay up to 5 minutes
*/30 * * * * root sleep $((RANDOM % 300)); /usr/bin/ansible-pull \
  -U https://git.example.com/infra/config.git -C main -o \
  -i localhost, local.yml >> /var/log/ansible-pull.log 2>&1

Common mistakes

  • No random delay, so thousands of nodes hit Git at the same second.
  • No central reporting, so failures on individual nodes go unnoticed.
  • Giving every node write access or broad secrets.
  • Assuming pull mode handles urgent, ordered changes well.

How to answer in the interview

"In push mode, Ansible's default, a control node SSHes into every host and applies changes, which is immediate and coordinated but needs connectivity to everything and doesn't scale well to thousands of hosts or catch new autoscaled ones. In pull mode each node fetches and applies its own configuration periodically, like Puppet or Chef, which scales, works behind NAT and self-heals drift. Ansible does that with ansible-pull: the node clones a Git repo and runs a playbook locally from a systemd timer. On AWS, SSM State Manager can run playbooks on tagged instances on a schedule."

Likely follow-up questions

  • What are the downsides of pull for urgent changes? You wait for the interval and lack ordering; trigger immediately with Run Command or a push run.
  • How do you know all nodes converged? Central logs, callback plugins or State Manager compliance reports.
  • Where does ansible-pull get secrets? From the node's own identity, such as an instance role reading Secrets Manager.
