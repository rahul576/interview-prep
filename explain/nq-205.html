What HTTP methods are commonly used in REST APIs?

REST & API Design · concept · levels entry

In one line

The common methods are GET (read), POST (create/action), PUT (replace), PATCH (partial update) and DELETE (remove), plus HEAD (headers only) and OPTIONS (allowed methods, CORS preflight); GET, HEAD, OPTIONS are safe, and GET, HEAD, OPTIONS, PUT, DELETE are idempotent.

Detailed explanation

Each HTTP method carries agreed semantics (RFC 9110). Using them correctly lets clients, browsers, caches, gateways and retry logic behave sensibly without knowing your API.

  • GET retrieves a resource or collection (GET /orders/42, GET /orders?status=PAID). It must not change state, and responses can be cached.
  • POST creates a new resource under a collection (POST /orders), typically returning 201 Created with a Location header; it is also used for actions that are not simple CRUD, such as POST /payments/91/refunds. Not idempotent.
  • PUT replaces the resource at a known URI with the full representation sent, or creates it there if the client chooses the id. Idempotent.
  • PATCH applies a partial update, using JSON Merge Patch or JSON Patch. Not guaranteed idempotent.
  • DELETE removes the resource, usually returning 204 No Content. Idempotent.
  • HEAD is GET without the body: useful to check existence, size (Content-Length) or the ETag cheaply.
  • OPTIONS describes communication options, notably the Allow header. Browsers send it automatically as a CORS preflight before cross-origin requests with non-simple methods or headers, and the server answers with Access-Control-Allow-* headers.

Two properties matter:

  • Safe: the method is read-only from the client's point of view (GET, HEAD, OPTIONS). Crawlers and prefetchers may call safe methods freely, which is why a GET must never delete anything.
  • Idempotent: sending the request many times has the same effect on server state as sending it once (all safe methods plus PUT and DELETE). This is what makes automatic retries safe after timeouts. POST, and generally PATCH, are not idempotent; to retry them safely, APIs use idempotency keys.

TRACE and CONNECT also exist but are rarely used in APIs (TRACE is usually disabled for security).

How it works

  1. Client chooses the method matching its intent.
  2. Server applies the semantics and returns an appropriate status.
  3. Caches store responses to safe methods if allowed.
  4. Clients and proxies may retry idempotent methods.

Example

curl -I https://api.shop.com/orders/42                      # HEAD
curl -X OPTIONS https://api.shop.com/orders \
     -H "Origin: https://shop.com" \
     -H "Access-Control-Request-Method: POST"               # preflight
curl -X POST https://api.shop.com/orders -H "Content-Type: application/json" \
     -d '{"customerId":7,"items":[{"sku":"A1","qty":1}]}'

Common mistakes

  • State changes via GET links.
  • Treating PATCH as always idempotent.
  • Blocking OPTIONS at the gateway, breaking CORS.
  • Retrying POSTs automatically without idempotency keys.

How to answer in the interview

"GET retrieves a resource and must not change state. POST creates a new resource, returning 201 with a Location header, or triggers a non-idempotent action. PUT replaces a resource entirely at a known URI, PATCH applies a partial update, and DELETE removes it. HEAD is GET without the body, handy for checking existence or ETags, and OPTIONS describes allowed methods; browsers use it for CORS preflight. GET, HEAD and OPTIONS are safe; those plus PUT and DELETE are idempotent, which means retries are safe. POST and usually PATCH aren't, so I protect them with idempotency keys when retries matter."

Likely follow-up questions

  • What does idempotent mean, and why does it matter for retries? Repeating gives the same server state, so clients can retry after timeouts without side effects.
  • When does a browser send a preflight? For cross-origin requests with non-simple methods, headers or content types.
  • Safe vs idempotent? Safe means no state change; idempotent means repeated calls have the same effect.
