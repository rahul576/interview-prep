How do you run a container as a non-root user?

Docker · concept · levels mid

In one line

Create a dedicated user in the Dockerfile, set ownership with COPY --chown, switch with the USER instruction, listen on a port above 1024, and enforce it at runtime with --user or Kubernetes runAsNonRoot.

Detailed explanation

By default the process in a container runs as root (UID 0). Capabilities and seccomp limit what that root can do, but if an attacker exploits the application and then a kernel or runtime bug, root in the container may become root on the host. Running as an unprivileged user removes a whole class of escalation and limits damage to files the user owns.

In the Dockerfile you create a system user and group (adduser/useradd, or addgroup -S/adduser -S on Alpine), copy application files owned by that user with COPY --chown=app:app, and add USER app (or a numeric USER 10001:10001) before CMD. Numeric IDs are better because Kubernetes can only verify runAsNonRoot for numeric UIDs. Many images already include a user: node in Node images, nonroot in distroless images, nginx in nginxinc/nginx-unprivileged.

The application then has some constraints. Non-root processes cannot bind to ports below 1024 without the NET_BIND_SERVICE capability, so use 8080 and map it. They can only write where they have permission, so create writable directories (/tmp, /app/data) owned by the user, or use volumes. Mounted volumes and bind mounts are a frequent problem: host files owned by another UID can be unreadable, so align UIDs, use fsGroup in Kubernetes, or fix ownership.

At runtime, docker run --user 1000:1000 overrides the user, and Kubernetes enforces it through the securityContext: runAsNonRoot: true, runAsUser, allowPrivilegeEscalation: false and readOnlyRootFilesystem.

How it works

  1. Build stage compiles the application.
  2. Runtime stage creates the user and group.
  3. Files are copied with correct ownership.
  4. USER sets the default UID for CMD.
  5. The orchestrator verifies non-root at admission or start.

Example

FROM eclipse-temurin:21-jre
RUN groupadd --system --gid 10001 app && useradd --system --uid 10001 --gid app app
WORKDIR /app
COPY --chown=app:app target/app.jar app.jar
USER 10001:10001
EXPOSE 8080
CMD ["java", "-jar", "app.jar"]
securityContext:
  runAsNonRoot: true
  runAsUser: 10001
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true

Common mistakes

  • RUN chown -R on large directories in a separate layer, doubling image size.
  • Using a username in USER so Kubernetes cannot verify non-root.
  • Binding to port 80 and adding capabilities instead of using 8080.
  • Forgetting writable directories, causing permission errors at runtime.

How to answer in the interview

"By default containers run as root, which makes a breakout much more dangerous. In the Dockerfile I create a dedicated user and group with a fixed numeric UID, copy the application with COPY --chown, and switch with USER before CMD; many official images already provide one, like node or nonroot. The app then listens on a port above 1024 and writes only to directories it owns or to volumes. At runtime I can force a user with --user, and in Kubernetes I enforce runAsNonRoot, disable privilege escalation and ideally use a read-only root filesystem."

Likely follow-up questions

  • Problems with mounted volumes? UID mismatch makes files unreadable or unwritable; align UIDs or use fsGroup.
  • Why numeric UIDs? Kubernetes can verify runAsNonRoot only for numeric users.
  • How do you bind port 80 as non-root? Map host 80 to container 8080, or grant NET_BIND_SERVICE.
