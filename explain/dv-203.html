What are Terraform variables, outputs and modules?

Infrastructure as Code · concept · levels entry, mid

In one line

Variables parameterise a configuration (with types, defaults, validation, values from tfvars, env vars or CLI); outputs expose values after apply to people or other configurations; locals hold computed values reused within a module; and modules are reusable groups of resources with their own inputs and outputs, sourced from local paths, Git or the registry and pinned to versions.

Detailed explanation

Input variables make the same code work for dev and prod. Each variable block can declare a type (string, number, bool, list(string), map, object({...})), a default, a description, validation rules and sensitive = true to hide values in output. Values come, in increasing precedence, from defaults, environment variables TF_VAR_name, terraform.tfvars and *.auto.tfvars, -var-file, and -var on the command line. Variables without defaults are required.

Outputs publish values after apply, such as a load balancer DNS name, a VPC ID or a database endpoint. They are the interface of a module (the parent reads module.vpc.private_subnet_ids), usable by scripts via terraform output -json, and stored in state.

Locals are named expressions inside a module, such as a common tag map or a computed name prefix: local.name = "${var.project}-${var.env}". They reduce repetition but aren't inputs.

Modules: every directory of .tf files is a module; the one you run is the root module. A child module is called with a module block and a source: a local path (./modules/vpc), a Git URL with ?ref=v1.2.0, or the Terraform Registry (terraform-aws-modules/vpc/aws with version = "~> 5.0"). Pin versions so upgrades are deliberate. Good modules are small, focused and composable (VPC, database, service), with clear inputs, sensible defaults and documented outputs, rather than one giant module that does everything through dozens of flags.

How it works

  1. Root module declares variables and receives values from tfvars.
  2. It calls child modules, passing variables as inputs.
  3. Modules create resources and expose outputs.
  4. Root module wires outputs of one module into inputs of another.
  5. Root outputs are printed and stored in state.

Example

variable "env" {
  type = string
  validation {
    condition     = contains(["dev", "staging", "prod"], var.env)
    error_message = "env must be dev, staging or prod."
  }
}
locals { tags = { env = var.env, managed_by = "terraform" } }

module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 5.0"
  name    = "app-${var.env}"
  cidr    = "10.10.0.0/16"
  tags    = local.tags
}

output "private_subnets" { value = module.vpc.private_subnets }
# prod.tfvars
env = "prod"

Common mistakes

  • Unpinned module sources, so a new version changes infrastructure unexpectedly.
  • Giant "do everything" modules with dozens of boolean flags.
  • Putting secrets in tfvars committed to Git.
  • Using count with lists where removing an item shifts and recreates others; prefer for_each with keys.

How to answer in the interview

"Variables parameterise a configuration so the same code works for different environments. Each has a type, maybe a default and validation, and values come from tfvars files, environment variables or the command line. Outputs expose values after apply, like a load balancer DNS name, for people, scripts or other configurations, and they form a module's interface. Locals hold computed values I reuse, like a tag map. A module is a reusable group of resources with inputs and outputs, for example a VPC with subnets and routing; it can come from a local path, Git or the Terraform registry and I always pin its version. Good modules are small, focused and composable."

Likely follow-up questions

  • How do you pass an output from one state to another? terraform_remote_state, or publish to SSM/Key Vault and read with a data source.
  • count vs for_each? for_each keys instances by name, avoiding recreation when list order changes.
  • What does sensitive = true do? Hides the value in CLI output, but it is still stored in state.
