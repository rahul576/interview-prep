How does HashSet work internally?

Collections · concept · levels mid

In one line

A HashSet wraps a HashMap: elements are keys with a shared dummy value PRESENT; hashCode picks the bucket, equals detects duplicates, giving average O(1) operations, with load factor 0.75 resizing, treeified buckets, no order and one null allowed.

Detailed explanation

The JDK source is short: HashSet holds private transient HashMap<E,Object> map and a static final Object PRESENT = new Object(). add(e) returns map.put(e, PRESENT) == null, contains(e) is map.containsKey(e) and remove(e) is map.remove(e) == PRESENT. So every property of a HashSet is really a property of HashMap.

When you add an element, HashMap computes h = e.hashCode(), spreads it with h ^ (h >>> 16) and maps it to a bucket with (capacity - 1) & h. If the bucket is empty the element is stored. Otherwise each entry in the bucket is checked: same hash and equals true means the element already exists, so nothing is added and add returns false. This is why custom element types must override equals and hashCode consistently.

With a good hash distribution, add, contains and remove are average O(1). When the number of elements exceeds capacity × load factor (default 16 × 0.75), the table doubles and entries are redistributed. Since Java 8, a bucket with more than 8 colliding entries, in a table of at least 64, becomes a red-black tree, so worst-case lookups are O(log n) rather than O(n).

HashSet gives no iteration order guarantee; the order can change after resizing. It allows one null element (hash 0). It is not thread safe; use ConcurrentHashMap.newKeySet() for a concurrent set.

How it works

  1. add(e) → map.put(e, PRESENT).
  2. Spread hash, compute bucket index.
  3. Walk bucket comparing hash then equals.
  4. Found: return false. Not found: insert, size++.
  5. Size over threshold: resize; long bucket: treeify.

Example

Set<String> emails = new HashSet<>();
emails.add("a@x.com");                    // true
emails.add("a@x.com");                    // false, duplicate

Set<String> concurrent = ConcurrentHashMap.newKeySet();
Set<Long> presized = HashSet.newHashSet(10_000); // Java 19+, no rehash

Common mistakes

  • Mutating an element's fields used in hashCode after adding it.
  • Weak hashCode (for example constant), causing heavy collisions.
  • Expecting stable iteration order.
  • Using new HashSet<>(n) thinking it holds n elements without resizing (it's capacity, not expected size).

How to answer in the interview

"A HashSet is a thin wrapper around a HashMap: each element is a key, and the value is a shared dummy object called PRESENT. On add, the element's hashCode is spread and used to pick a bucket; if the bucket has entries, equals checks whether the element is already present. If so, add returns false; otherwise it's stored. That gives average constant-time add, contains and remove. When size exceeds capacity times 0.75 the table doubles, and heavily collided buckets become red-black trees. There's no order guarantee and one null is allowed."

Likely follow-up questions

  • What if you mutate an element after adding? It may sit in the wrong bucket, so contains and remove fail and duplicates can appear.
  • Concurrent HashSet? ConcurrentHashMap.newKeySet().
  • Why a dummy value rather than null? So remove can tell whether the key was present.
