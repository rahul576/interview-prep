How would you propagate correlation IDs across multiple services?

Microservices · design · levels mid, senior

In one line

Generate the id at the edge if missing, carry it in headers on every hop (the W3C traceparent, optionally X-Correlation-Id), put it in the logging MDC, propagate it through HTTP clients and Kafka headers, and let Micrometer Tracing / OpenTelemetry automate this, including async context.

Detailed explanation

When one user request touches ten services, you need a single identifier to find all related logs and spans.

Creation. The API gateway (or the first service) checks the incoming request. If it carries a traceparent or correlation header from a trusted source, it reuses it; otherwise it creates a new one. Untrusted external values can be replaced to avoid log injection.

Transport. The id travels in headers on every hop. The standard today is the W3C Trace Context traceparent header (version, 16-byte trace id, 8-byte parent span id, flags), understood by OpenTelemetry, Micrometer Tracing, service meshes and cloud APM tools. Many teams additionally send a business-friendly X-Correlation-Id or X-Request-Id, and return it to clients so support staff can search for it.

Logging. In each service, a filter (or the tracing library) extracts the id and stores it in the MDC (Mapped Diagnostic Context) of SLF4J/Logback, so every log line includes traceId and spanId. Spring Boot with Micrometer Tracing adds these to the log pattern and structured logs automatically.

Outgoing calls. HTTP clients (RestClient, RestTemplate, WebClient, Feign) add the header through interceptors, if they are built from Spring's auto-configured builders. Kafka producers write the context into record headers, and listeners restore it, when observation is enabled on KafkaTemplate and the listener container. The same applies to RabbitMQ.

Async boundaries. MDC and tracing context are thread-local, so moving work to an executor, @Async, CompletableFuture or reactive operators can lose them. Use context-propagating executors (ContextExecutorService, Spring's ContextPropagatingTaskDecorator) or Reactor's automatic context propagation (Hooks.enableAutomaticContextPropagation()).

How it works

  1. Gateway receives request; reuses or generates trace id.
  2. Service filter extracts context; MDC now holds traceId.
  3. Logs include the id; spans are exported to Tempo, Jaeger or Zipkin.
  4. Outgoing HTTP and Kafka calls inject traceparent.
  5. Downstream services continue the same trace.
  6. Search logs by trace id, or open the trace in the tracing UI.

Example

management:
  tracing:
    sampling:
      probability: 0.1
spring:
  kafka:
    template:
      observation-enabled: true
    listener:
      observation-enabled: true
logging:
  pattern:
    correlation: "[${spring.application.name:},%X{traceId:-},%X{spanId:-}] "
@Bean
RestClient inventoryClient(RestClient.Builder builder) {   // auto-configured builder => propagation
    return builder.baseUrl("http://inventory").build();
}

@Bean
ThreadPoolTaskExecutor appExecutor() {
    var ex = new ThreadPoolTaskExecutor();
    ex.setTaskDecorator(new ContextPropagatingTaskDecorator()); // keeps MDC/trace on worker threads
    return ex;
}

Common mistakes

  • Creating clients with new RestTemplate() instead of the builder, losing instrumentation.
  • Losing context at @Async or thread-pool boundaries.
  • Forgetting Kafka headers, so the trace stops at the broker.
  • Inventing custom headers when traceparent is the standard.
  • Logging the id only in some services.

How to answer in the interview

"The id is created at the edge, usually the gateway, if the request does not already have one, and it travels in headers on every hop; today that is the W3C traceparent header, sometimes with an extra X-Correlation-Id we return to clients. Each service puts it into the logging MDC so every log line carries it. Outgoing HTTP clients add it through interceptors and Kafka producers add it to record headers, so consumers continue the chain. In Spring Boot, Micrometer Tracing with OpenTelemetry does most of this automatically, and I use context-propagating executors so the id survives thread switches."

Likely follow-up questions

  • How do you keep the id when work moves to another thread? Context-propagating task decorators or executors, or Reactor's automatic context propagation.
  • Correlation id vs trace id? A trace id is the tracing standard with spans; a correlation id is a simpler log-search key.
  • Why sample traces but not logs? Traces are expensive to store; logs still include the id for every request.
