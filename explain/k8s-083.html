How do you restrict and audit kubectl exec into production pods?

Kubernetes · concept · levels mid, senior

In one line

Exec is governed by RBAC on the pods/exec subresource, separate from reading pods, so grant it via just-in-time access with approval and expiry, audit every exec, keep a monitored break-glass account, and invest in observability and kubectl debug so shell access becomes rare.

Detailed explanation

kubectl exec opens an interactive channel into a running container. Anyone with it can read secrets from the environment and filesystem, alter running code, and use the pod's ServiceAccount and cloud identity. In production that is effectively the pod's full privilege, so it should not be a standing permission.

RBAC: exec is authorised as the create verb on pods/exec (and pods/attach, pods/portforward are similar subresources). Engineers can have get, list, watch on pods and pods/log without exec. Since Kubernetes 1.30 exec uses WebSockets, and RBAC requires create on pods/exec; older clusters or configurations may also accept get, so check both when reviewing roles. Be careful with broad wildcard roles and with permissions that indirectly grant exec, such as creating pods (which can mount any Secret in the namespace) or nodes/proxy.

Just-in-time access: engineers request elevation for a reason, with approval and an automatic expiry. Implementations include Entra ID PIM for groups mapped to AKS RBAC, AWS IAM Identity Center with EKS access entries, Teleport or similar access proxies, or a workflow that creates a temporary RoleBinding and deletes it after an hour.

Auditing: the API server audit log records each exec request (user, pod, command for non-interactive execs) at Metadata or Request level. Tools such as Teleport can record entire sessions. Alert on exec in production namespaces.

Break-glass: a documented emergency account or group, credentials sealed, use triggers alerts and a review.

Reduce the need: good logs, metrics and traces; kubectl debug with ephemeral debug containers (also RBAC-controlled via pods/ephemeralcontainers); distroless images without shells.

How it works

  1. Default production roles: read pods and logs, no exec.
  2. Separate role granting pods/exec, bound only through JIT groups.
  3. Approval workflow with reason and expiry.
  4. Audit logs and session recording; alerts on exec.
  5. Break-glass account with alerting.
  6. Improve observability to remove reasons for exec.

Example

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { name: prod-exec, namespace: payments }
rules:
  - apiGroups: [""]
    resources: ["pods/exec"]
    verbs: ["create", "get"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { name: prod-exec-jit, namespace: payments }
subjects:
  - { kind: Group, name: "jit-payments-exec", apiGroup: rbac.authorization.k8s.io }   # PIM-managed group
roleRef: { kind: Role, name: prod-exec, apiGroup: rbac.authorization.k8s.io }

Common mistakes

  • Granting edit or admin cluster roles that include exec.
  • Permanent exec bindings for whole teams.
  • Audit policy level None for exec requests.
  • Ignoring that pod creation rights equal access to the namespace's secrets.

How to answer in the interview

"Exec is controlled by RBAC on the pods/exec subresource, separate from reading pods, so engineers can view pods and logs in production without a shell. When someone needs exec, they get just-in-time access through an approval workflow, like Entra PIM or Teleport, that expires after an hour. The audit log records every exec with user and pod, and some tools record the whole session; we alert on it. A break-glass account exists for emergencies with alerting. Long term, good observability and kubectl debug make shell access rare."

Likely follow-up questions

  • Why is exec risky even for well-meaning engineers? Manual changes cause drift, mistakes in production, and exposure of secrets in terminals.
  • Is kubectl debug safer? It can use limited images and is separately controlled, but it still needs strict RBAC.
  • How do you audit interactive commands? The API audit shows the session start; session recording tools capture the content.
