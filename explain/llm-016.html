Self-hosted LLM pods take ten minutes to become ready after scaling up. How do you reduce startup time?

LLMOps & RAG · scenario · levels mid, senior

In one line

First measure each phase: node provisioning, image pull, weight download, loading into GPU memory and engine warmup; then cache weights outside the image on node-local NVMe or shared volumes in safetensors, pre-pull or stream images, keep warm GPU nodes, and cache compilation artefacts.

Detailed explanation

Ten minutes is common for a naive deployment, and it makes autoscaling nearly useless. The time usually splits into:

  1. Node provisioning (2 to 5 minutes or more for a GPU VM, plus driver and device plugin setup), only if no free node exists.
  2. Image pull: CUDA-based serving images are often 8 to 20 GB.
  3. Weight download: 16 to 150 GB from Hugging Face Hub or object storage, often single-threaded.
  4. Loading weights from disk into GPU memory.
  5. Warmup: CUDA graph capture, torch.compile, kernel autotuning, KV cache profiling.

Measure with pod events and timestamps in engine logs, then attack the biggest phases.

Weights. Never bake them into the image and never download from a public hub on every start. Options: a node-local NVMe cache filled by a DaemonSet or init job; a shared high-throughput volume (FSx for Lustre, Filestore, Azure Managed Lustre, or a fast NFS); OCI image volumes or model-as-artefact approaches; or object storage with parallel, multi-connection downloads (for example the Hugging Face transfer accelerator or s5cmd). Store weights in safetensors, which supports fast, zero-copy memory mapping; engines can also use loaders that stream tensors directly to GPU.

Images. Slim images, shared base layers, pre-pull on GPU nodes (DaemonSet or node image baking), or lazy image streaming such as GKE image streaming, SOCI on AWS, or Artifact Streaming on AKS.

Nodes. Keep a buffer of warm GPU nodes, for example low-priority placeholder pods that are preempted when real pods need the node, or a minimum node count during business hours.

Warmup. Cache compiled artefacts between runs (vLLM's compile cache directory on a persistent volume), reduce captured CUDA graph sizes, or disable graph capture where latency allows.

Finally, readiness probes should pass only when the model can serve, a startupProbe should allow the real loading time, and autoscaling should start earlier.

How it works

  1. Instrument startup phases.
  2. Pre-stage weights on nodes or shared fast storage.
  3. Pre-pull or stream images.
  4. Keep warm node buffer.
  5. Cache compile artefacts; set probes; re-measure.

Example

spec:
  containers:
    - name: vllm
      image: vllm/vllm-openai:<pinned-version>
      args: ["--model", "/models/llama-3.1-70b-fp8", "--tensor-parallel-size", "4"]
      env: [ { name: VLLM_CACHE_ROOT, value: /models/.vllm-cache } ]
      volumeMounts: [ { name: models, mountPath: /models, readOnly: false } ]
      startupProbe: { httpGet: { path: /health, port: 8000 }, periodSeconds: 10, failureThreshold: 60 }
      readinessProbe: { httpGet: { path: /health, port: 8000 }, periodSeconds: 5 }
  volumes:
    - name: models
      hostPath: { path: /mnt/nvme/models, type: Directory }   # filled by a cache DaemonSet

Common mistakes

  • Baking 140 GB of weights into the container image.
  • Downloading from a public hub on every pod start (also a supply-chain risk).
  • Readiness passing before weights are loaded.
  • Scaling to zero GPUs for interactive workloads.

How to answer in the interview

"First I measure where the ten minutes go: GPU node provisioning, pulling a huge image, downloading weights, loading them into GPU memory and engine warmup like CUDA graph capture. Then I fix the biggest parts. Weights stay out of the image and are cached on node-local NVMe or a fast shared volume, in safetensors format, downloaded in parallel. Images are slimmed and pre-pulled or streamed. I keep a small buffer of warm GPU nodes so provisioning is not on the critical path, cache compile artefacts, make readiness reflect real serving ability, and scale earlier."

Likely follow-up questions

  • Cost of warm GPUs vs startup? Compare idle cost with the cost of missed SLOs; use placeholders only at peak hours.
  • Why safetensors? Memory-mappable, fast, and no arbitrary code execution like pickle.
  • What about model updates? Version weight directories and roll pods gradually.
