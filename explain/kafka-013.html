How do you manage message schemas and evolve them safely?

Kafka · concept · levels mid, senior

In one line

Use a schema registry (Confluent, Apicurio, AWS Glue) with Avro, Protobuf or JSON Schema, where messages carry a schema ID and the registry enforces a compatibility mode (backward, forward, full); safe evolution means adding optional fields with defaults, checked in CI.

Detailed explanation

Kafka itself treats messages as bytes. Without a contract, a producer that renames a field silently breaks every consumer. A schema registry stores versioned schemas per subject (by default <topic>-value). The producer's serializer registers or looks up the schema and prefixes each message with a small header containing the schema ID; the consumer's deserializer fetches that schema (cached) and decodes reliably, even if its own code was compiled against a different version.

Compatibility modes decide which changes are allowed:

  • BACKWARD (Confluent default): consumers using the new schema can read data written with the previous one. Upgrade consumers first. Deleting fields and adding fields with defaults are allowed.
  • FORWARD: consumers on the old schema can read data written with the new one. Upgrade producers first. Adding fields is allowed; deleting only optional fields with defaults.
  • FULL: both directions; only add or remove optional fields with defaults.
  • The _TRANSITIVE variants check against all previous versions, not just the last, which matters for topics with long retention or replays.

Safe changes are adding optional fields with defaults. Dangerous ones are renaming fields, changing types, removing required fields or changing Protobuf field numbers. For a breaking change, create a new topic or subject version (for example orders.v2) and dual-publish during migration.

Make it a pipeline step: run the registry's compatibility check (Maven/Gradle plugin or REST call) in CI before a producer deploys, and set auto.register.schemas=false in production so only reviewed schemas are registered.

How it works

  1. Developer changes the .avsc or .proto file.
  2. CI calls the registry compatibility endpoint; fails the build if incompatible.
  3. Pipeline registers the new version.
  4. Producer serializes with the new schema ID.
  5. Consumers resolve the writer schema by ID and project it onto their reader schema.

Example

{ "type": "record", "name": "Order", "fields": [
  { "name": "id", "type": "string" },
  { "name": "amount", "type": "long" },
  { "name": "currency", "type": "string", "default": "EUR" },
  { "name": "couponCode", "type": ["null", "string"], "default": null } ] }
curl -X POST -H "Content-Type: application/vnd.schemaregistry.v1+json" \
  --data @order-v3.json \
  http://registry:8081/compatibility/subjects/orders-value/versions/latest

Common mistakes

  • Plain JSON with no schema, discovered breaking at runtime.
  • Adding a required field without a default.
  • Auto-registering schemas from any producer in production.
  • Using non-transitive compatibility on long-retention topics.

How to answer in the interview

"I use a schema registry with Avro or Protobuf. Producers register schemas and each message carries a schema ID, so consumers can always decode it. The registry enforces a compatibility mode: backward means new consumers read old data, forward means old consumers read new data, and full means both. Safe changes are adding optional fields with defaults; renames, type changes or removing required fields break consumers, so those need a new topic version. Compatibility checks run in CI before a producer deploys."

Likely follow-up questions

  • Mode for an event used by ten teams? FULL_TRANSITIVE, so producers and consumers can upgrade independently.
  • Avro vs Protobuf? Avro has compact schema resolution; Protobuf has strong codegen and gRPC reuse.
  • Where is the schema ID stored? A magic byte plus a 4-byte ID at the start of the payload.
