Describe the Kubernetes architecture: the control plane and worker node components.

Kubernetes · concept · levels entry, mid

In one line

The control plane (API server, etcd, scheduler, controller manager, optionally the cloud controller manager) stores and reconciles desired state; each worker node runs the kubelet, kube-proxy and a container runtime (containerd, CRI-O), and everything talks through the API server.

Detailed explanation

Kubernetes is a declarative, reconciling system: you store desired state as objects, and independent components continuously work to make reality match. Understanding who does what explains almost every troubleshooting session.

Control plane.

  • kube-apiserver is the front door. Every request (kubectl, controllers, kubelets) goes through it: authentication, authorisation (RBAC), admission control (mutating and validating webhooks, Pod Security Admission), validation, then persistence. It also serves watches, so components react to changes instead of polling.
  • etcd is a consistent, Raft-replicated key-value store holding all cluster state. Only the API server talks to it. Losing etcd without a backup means losing the cluster's definition.
  • kube-scheduler watches for pods without a node, filters nodes that fit (resources, affinity, taints, volumes) and scores the rest, then binds the pod to the best node.
  • kube-controller-manager runs controllers: Deployment, ReplicaSet, Node, Job, EndpointSlice, ServiceAccount and more, each a loop comparing desired and actual state.
  • cloud-controller-manager integrates with the cloud: load balancers for Services, node lifecycle, routes.

Worker nodes.

  • kubelet watches pods assigned to its node, asks the runtime (via the CRI) to start containers, sets up volumes, runs probes and reports status.
  • Container runtime: containerd or CRI-O (Docker Engine support via dockershim was removed in 1.24); the CNI plugin gives pods their network.
  • kube-proxy programs iptables, IPVS or nftables rules for Service virtual IPs; some CNIs such as Cilium replace it with eBPF.

In managed services (EKS, AKS, GKE) the provider runs the control plane; you manage nodes and workloads.

How it works

  1. kubectl apply sends the Deployment to the API server; it is authenticated, authorised, admitted and stored in etcd.
  2. The Deployment controller creates a ReplicaSet; the ReplicaSet controller creates Pods.
  3. The scheduler binds each pending Pod to a node.
  4. The kubelet on that node pulls images and starts containers via the CRI; CNI assigns an IP.
  5. Readiness passes; the EndpointSlice controller adds the pod to its Service.
  6. Status flows back through the API server.

Example

kubectl get --raw='/readyz?verbose'          # API server health checks
kubectl get pods -n kube-system -o wide      # control-plane/addon pods (self-managed)
kubectl get events --sort-by=.lastTimestamp  # watch reconciliation happen

Common mistakes

  • Saying the scheduler starts containers (the kubelet does).
  • No etcd backups on self-managed clusters.
  • Thinking components talk to each other directly rather than via the API server.

How to answer in the interview

"The control plane has the API server, the front door that authenticates, authorises, runs admission and stores every object; etcd, the consistent key-value store with all cluster state; the scheduler, which assigns pending pods to nodes; and the controller manager, whose controllers reconcile actual state to desired state, plus a cloud controller manager for load balancers and nodes. Each worker runs the kubelet, which starts containers through the container runtime like containerd and reports status, and kube-proxy, which programs Service rules. Everything communicates through the API server using watches."

Likely follow-up questions

  • What happens step by step on kubectl apply of a Deployment? API server stores it, controllers create ReplicaSet and Pods, scheduler binds, kubelet starts containers.
  • What if etcd loses quorum? The API becomes read-unavailable for writes; running pods continue, but nothing changes.
  • Is kube-proxy required? Not with CNIs that implement Services in eBPF, such as Cilium.
