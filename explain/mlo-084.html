A stakeholder asks why the model performed so well in the notebook but is disappointing in production. How do you explain and address it?

MLOps · scenario · levels mid, senior

In one line

Offline scores only predict production if the test data resembles production and evaluation is honest; gaps come from leakage or overfitting to validation, random splits on time data, training-serving skew, drift, and metric mismatch, fixed by time-based evaluation, skew checks, aligned metrics and monitoring.

Detailed explanation

I'd explain to the stakeholder that the notebook result was an estimate based on assumptions, and that we now need to find which assumption failed. The usual suspects:

  • Data leakage: features that contain information not available at prediction time, such as a "days until cancellation" column or a status updated after the event, give unrealistically high scores.
  • Overfitting to the validation set: dozens of experiments tuned on the same split produce an optimistic number.
  • Wrong split: random splits on time-dependent data let the model learn from the future; customers appearing in both train and test inflate results.
  • Training-serving skew: features computed differently in production (different code, units, defaults for missing values), or arriving later than in the historical tables, so the model sees different inputs.
  • Drift: the world changed since the training data was collected (new products, seasonality, a policy change, a competitor).
  • Metric mismatch: a good AUC doesn't guarantee business value; the business may care about precision at a fixed review capacity, revenue or customer impact, or the threshold may be wrong.

To address it: audit features for leakage, re-evaluate with time-based splits on recent data, compare the online feature values logged in production with the offline values for the same entities, check performance per segment, align the evaluation with the business metric, and add monitoring. Then reset expectations with a realistic estimate and, ideally, an A/B test.

How it works

  1. Gather production predictions, logged features and available outcomes.
  2. Recompute offline metrics on the same production period.
  3. Compare logged online features with offline recomputed features (skew).
  4. Audit features for leakage and redo the split by time.
  5. Check drift and segment performance.
  6. Align metric and threshold with the business; agree monitoring and an A/B plan.

Example

online = load_logged_features("2026-10-01", "2026-10-31")      # what the model saw
offline = build_training_features(online.entity_ids, online.ts)   # what training would compute
diff = (online.set_index("request_id") - offline.set_index("request_id")).abs()
print(diff.mean().sort_values(ascending=False).head(10))         # largest skew first
time_split_auc = evaluate(model, data[data.ts >= "2026-09-01"])  # honest, recent holdout

Common mistakes

  • Defending the notebook number instead of investigating.
  • Retraining immediately without diagnosing the cause.
  • Explaining in jargon; stakeholders need impact and a plan.
  • Promising a new number without fixing the evaluation method.

How to answer in the interview

"I'd explain that the notebook score was only an estimate and holds only if the test data looks like production and the evaluation is honest. Then I'd check the usual causes: leakage or overfitting from tuning many times on one validation set, random splits on time data, training-serving skew where production features are computed differently or arrive later, drift since the data was collected, and a metric that doesn't match the business outcome. I'd compare logged online features with offline ones, re-evaluate on a recent time-based split, align the metric with the business goal, add monitoring and set realistic expectations going forward."

Likely follow-up questions

  • How do you present uncertain performance to non-technical stakeholders? Ranges and business terms ("between 40 and 55 extra fraud cases caught per week"), with what would change the estimate.
  • How do you prevent this next time? Time-based holdouts, feature logging, a shadow phase and pre-agreed business metrics.
  • How do you find leakage? Suspiciously important features, perfect scores, and checking each feature's availability timestamp.
