When are multi-agent systems worth it, and how do you coordinate the agents?

AI Agents & AIOps · concept · levels senior, lead

In one line

Multi-agent systems pay off for broad, parallelisable tasks, very different tool sets or security separation, using isolated contexts per sub-agent and a supervisor/orchestrator (or handoffs or shared state) to coordinate; but token costs multiply and errors compound, so use them only when evaluations beat a single agent.

Detailed explanation

A single agent with good tools is the default. Multiple agents become worth it in specific situations. Breadth and parallelism: researching 30 companies, or exploring several parts of a large codebase at once, where sub-agents can work simultaneously and the wall-clock time drops. Context isolation: each sub-agent gets a focused context with only its subtask, so it is not distracted by everything else, and returns a condensed result, keeping the orchestrator's context clean. Different specialisations: a sub-agent with SQL tools and a sub-agent with document search need different instructions. Security separation: a reader agent that processes untrusted content has no write tools, and an actor agent never sees raw untrusted text.

Coordination patterns: the most common is a supervisor or orchestrator that decomposes the goal, spawns sub-agents with clear task descriptions, boundaries, expected output formats and budgets, then merges results. Handoffs, as in the OpenAI Agents SDK, pass control of the conversation from one agent to another, for example triage to billing. Shared state or a blackboard lets agents read and write a common workspace, which needs care to avoid conflicts. Peer-to-peer protocols such as A2A connect agents from different systems.

The costs are real. Anthropic reported its multi-agent research system used roughly 15 times more tokens than a chat interaction. Latency grows when agents wait for each other, failures in one agent propagate, and debugging requires tracing across agents. Poorly specified sub-tasks cause duplicated work or agents "talking in circles". Tasks with tight interdependencies, like editing one tightly coupled module, often work worse when split.

How it works

  1. Confirm the task is parallelisable or needs isolation or separation.
  2. Orchestrator plans subtasks with explicit scope, tools, budget and output schema.
  3. Sub-agents run in parallel in fresh contexts.
  4. They return compact, structured results with sources.
  5. Orchestrator validates, merges and decides whether more work is needed.
  6. Trace all agents under one run ID; compare against a single-agent baseline.

Example

orchestrator:
  goal: "Compare data residency options of 5 cloud CRM vendors for EU customers"
  max_subagents: 5
  subagent_template:
    tools: [web_search, fetch_page]          # read-only
    budget: { max_steps: 25, max_tokens: 200000 }
    instructions: "Research ONLY vendor {vendor}. Return JSON: {regions, certifications, sub_processors, sources[]}"
  merge: "Build comparison table; flag conflicts between sources"

Common mistakes

  • Splitting tightly coupled work across agents.
  • Vague delegation like "research the topic", causing overlap.
  • Passing full transcripts between agents instead of summaries.
  • No per-agent budgets or round limits.
  • Not comparing cost and quality against one well-equipped agent.

How to answer in the interview

"Multiple agents help when a task splits into fairly independent parallel pieces, like researching many companies, when subtasks need very different tools, or when separating concerns improves security, like a reader agent without write tools. Each sub-agent gets an isolated, focused context and returns a condensed result. The usual pattern is an orchestrator that breaks the goal down and delegates with clear task descriptions, output formats and budgets, then combines results; alternatives are handoffs or shared state. The costs are real: tokens multiply, latency and coordination overhead grow, and errors compound. So I only keep a multi-agent design where evaluations show it beats a single good agent."

Likely follow-up questions

  • How would you debug a wrong answer from five agents? Follow the distributed trace from the final claim back to the sub-agent and tool result that produced it.
  • Handoff vs orchestrator? Handoff transfers control; an orchestrator stays in charge and aggregates.
  • How do sub-agents share knowledge? Through the orchestrator or a shared, structured store, not by forwarding full histories.
