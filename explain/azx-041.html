Explain stages, jobs, steps and deployment jobs in Azure Pipelines, including deployment strategies.

Azure DevOps & Pipelines · concept · levels entry, mid, senior

In one line

A YAML pipeline has stages → jobs → steps; each job runs on one agent, flow is controlled by dependsOn and conditions; a deployment job targets an environment (history, approvals, checks) and uses a strategy (runOnce, rolling, canary) with lifecycle hooks such as preDeploy, deploy, routeTraffic, postRouteTraffic, on: failure/success.

Detailed explanation

Stages are major phases (Build, Test, Prod). By default each stage depends on the previous one; dependsOn: [] makes it run in parallel, and condition expressions like and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main')) decide whether it runs.

Jobs are units of work that run on one agent (or server jobs with no agent, used for delays or invoking REST APIs). Jobs in a stage run in parallel unless they declare dependsOn. They have their own pool, workspace, timeout, variables and can use a matrix or parallel strategy for multiple configurations.

Steps run sequentially inside a job: tasks (AzureCLI@2, DotNetCoreCLI@2) or scripts (script, bash, pwsh), plus shortcuts like checkout, publish and download.

A deployment job (- deployment:) targets an environment. This gives deployment history (which run, commits and work items reached prod), applies the environment's approvals and checks, and can target Kubernetes namespace or virtual machine resources in the environment. It does not check out code automatically and downloads pipeline artifacts by default.

Strategies:

  • runOnce: run the hooks once; the most common.
  • rolling: for VM resources, update maxParallel machines (number or percentage) at a time.
  • canary: run the hooks for increments like [10, 20] and then 100 percent, typically with Kubernetes manifests creating canary workloads.

Lifecycle hooks: preDeploy (e.g. migrations, resource checks), deploy, routeTraffic, postRouteTraffic (monitor health), then on: failure (rollback) or on: success (cleanup).

How it works

  1. Pipeline compiles; stages scheduled by dependencies.
  2. Jobs within a stage dispatched to agents in parallel.
  3. Steps execute in order on each agent.
  4. Deployment job waits for environment checks.
  5. Strategy executes hooks; failure triggers on: failure.

Example

stages:
- stage: Deploy
  jobs:
  - deployment: aks
    environment: shop-prod.orders          # environment.namespace resource
    strategy:
      canary:
        increments: [10, 25]
        preDeploy:
          steps: [ script: ./check-cluster.sh ]
        deploy:
          steps:
          - task: KubernetesManifest@1
            inputs: { action: deploy, strategy: canary, percentage: $(strategy.increment), manifests: k8s/*.yaml }
        postRouteTraffic:
          steps: [ script: ./verify-slo.sh ]
        on:
          failure:
            steps:
            - task: KubernetesManifest@1
              inputs: { action: reject, manifests: k8s/*.yaml }

Common mistakes

  • Using a normal job for production deploys, losing history and checks.
  • Assuming jobs in a stage run sequentially.
  • Expecting code checkout in a deployment job.
  • Forgetting succeeded() in custom conditions, so jobs run after failures.

How to answer in the interview

"A pipeline is stages, which contain jobs, which contain steps. Each job runs on one agent and steps run in order. dependsOn and conditions control flow and parallelism. A deployment job targets an environment, so Azure DevOps records deployment history and enforces that environment's approvals and checks. Deployment jobs support strategies: runOnce, rolling for VMs in batches, and canary with increments like 10 percent then 100. Strategies expose lifecycle hooks, preDeploy, deploy, routeTraffic, postRouteTraffic, and on failure or success for rollback and cleanup."

Likely follow-up questions

  • Pass an output variable to a later stage? isOutput=true and stageDependencies.Stage.Job.outputs['step.var'].
  • Server job? An agentless job for delays, manual validation or REST calls.
  • Matrix? Runs the same job for several configurations in parallel.
