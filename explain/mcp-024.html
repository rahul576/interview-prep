Which official MCP SDKs exist, and how do you choose one?

MCP Servers · concept · levels entry, mid, senior

In one line

Official MCP SDKs exist for TypeScript, Python, C#, Go, Java, Rust, Kotlin, Swift, Ruby, PHP and more, grouped in tiers that reflect conformance and maintenance commitments (TypeScript, Python, C# and Go in tier 1); choose by team language and stack, then confirm support for the spec features and transports you need.

Detailed explanation

The MCP project maintains official SDKs under the modelcontextprotocol GitHub organisation, several co-maintained with companies such as Microsoft (C#), Google (Go), JetBrains (Kotlin) and the Spring team (Java). They implement the protocol details (message framing, capability negotiation, transports, authorization helpers) so you only write tools, resources and prompts.

SDKs are organised into tiers. Higher tiers commit to tracking new specification revisions quickly, passing conformance tests and responding to issues within defined times. Per the reference material, TypeScript, Python, C# and Go are tier 1 and typically get new features first; Java and Rust follow in tier 2; others such as Swift, Ruby, PHP and Kotlin are in further tiers. Tier assignments change over time, so check the current SDK page before committing.

Frameworks build on the SDKs. Spring AI provides MCP server and client starters on top of the Java SDK, with annotation-based tools and Spring Boot auto-configuration. The Python SDK includes the high-level FastMCP-style API with decorators. Other ecosystems (Quarkus, .NET hosting, various agent frameworks) offer integrations too.

Choosing. Start from the team's language and existing stack: a Spring Boot team uses Spring AI, a Node/TypeScript team uses the TypeScript SDK, a data team often Python. Then verify the SDK supports what you need: Streamable HTTP, authorization (resource server metadata, token validation), structured output, elicitation, Tasks or newer stateless features. Lower-tier SDKs can lag behind the latest revision.

How it works

  1. Identify team language, frameworks and deployment platform.
  2. Check the SDK tier and supported spec revision.
  3. Verify needed features: transports, auth, structured output, extensions.
  4. Prototype a tool, test with the Inspector and target hosts.
  5. Pin SDK versions and track releases.

Example

# TypeScript
npm install @modelcontextprotocol/sdk zod
# Python
uv add "mcp[cli]"
# Java with Spring AI (Maven artifactId)
#   org.springframework.ai:spring-ai-starter-mcp-server-webmvc
# C#
dotnet add package ModelContextProtocol --prerelease

Common mistakes

  • Picking a language the team does not know just for a tier.
  • Assuming every SDK supports the newest revision.
  • Unpinned SDK versions breaking builds on upgrade.
  • Writing raw JSON-RPC by hand instead of using an SDK.

How to answer in the interview

"There are official SDKs in many languages, organised in tiers that reflect how quickly they follow the spec and their conformance and maintenance commitments. TypeScript, Python, C# and Go are tier 1 and usually support new features first; Java and Rust are next, with others like Swift, Ruby, PHP and Kotlin. Frameworks build on them: Spring AI on the Java SDK with annotations, and the Python SDK's FastMCP-style decorators. I choose by team language and stack, so Spring Boot teams use Spring AI, Node teams use TypeScript, and then I check the SDK supports what I need, like Streamable HTTP, authorization and structured output, because lower tiers can lag."

Likely follow-up questions

  • Risks of a lagging SDK? Missing security fixes, auth features or interoperability with newer hosts.
  • Can you mix languages? Yes; the protocol is language-neutral, so clients and servers can differ.
  • Write your own implementation? Rarely worthwhile; conformance is hard.
