New pods take several minutes to start because the container image is 6 GB. How do you speed this up?

Kubernetes · scenario · levels mid, senior

In one line

Make the image smaller (multi-stage builds, slim or distroless bases, no bundled data or models), then make the remaining pull faster: pre-pulled or cached images, lazy loading/image streaming, and a registry close to the cluster.

Detailed explanation

A pod cannot start until the kubelet has pulled and unpacked every layer of its image. Six gigabytes means minutes of download and decompression on each new node, which hurts most exactly when you scale out under load or replace nodes.

The biggest win is usually shrinking. Multi-stage builds compile in one stage and copy only the runtime artefacts into a slim or distroless base. Remove package caches, compilers and test data, and order layers so the large, stable parts (base, dependencies) come first and are shared and cached between versions. Very often the bulk is ML models or datasets; those belong in object storage or a shared volume, downloaded at startup or mounted, so code releases do not re-ship gigabytes.

For what remains, pre-pull: bake images into the node image (AMI or custom image), or run a DaemonSet that pulls them on every node. Lazy loading lets the container start before the whole image has arrived, fetching files on demand: GKE Image streaming, SOCI on AWS, Azure Artifact Streaming, or eStargz-style snapshotters. Peer-to-peer caches such as Spegel help large clusters. Finally, use a registry in the same region, a pull-through cache, and avoid imagePullPolicy: Always with mutable tags.

How it works

  1. Measure: compare "Pulling" and "Successfully pulled ... in Xs" event times with app startup time.
  2. Inspect layers with docker history or dive to see what is large.
  3. Rebuild with multi-stage and a slim base; move models and data out.
  4. Pre-pull or bake common images into nodes.
  5. Enable image streaming or lazy loading where available.
  6. Keep the registry regional and tags immutable.

Example

FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /src
COPY pom.xml .
RUN mvn -q dependency:go-offline
COPY src ./src
RUN mvn -q package -DskipTests

FROM gcr.io/distroless/java21-debian12
COPY --from=build /src/target/app.jar /app/app.jar
ENTRYPOINT ["java","-jar","/app/app.jar"]
# models are downloaded from object storage at startup, not baked in

Common mistakes

  • Baking large models into every application image version.
  • Using latest tags with imagePullPolicy: Always, forcing pulls on every start.
  • Pulling across regions or from the public internet without a cache.
  • Optimising the app's startup when most of the time is actually the pull.

How to answer in the interview

"Pull time scales with image size, so first I shrink it: multi-stage builds, a slim or distroless base, no caches or build tools, and layers ordered so the big stable parts are cached. Usually the size comes from bundled data or models, which should live in object storage or a volume instead. For what is left, I pre-pull images with a DaemonSet or bake them into the node image, and enable lazy loading such as GKE image streaming, SOCI on AWS or Azure artifact streaming, so containers start before the full download. A registry in the same region helps a lot too."

Likely follow-up questions

  • How do you measure pull time versus app start time? Pod events show pull duration; compare with the time from container start to readiness.
  • Does lazy loading have downsides? First file accesses can be slower, and it needs supported registries and snapshotters.
  • Why distroless? Smaller image and attack surface, but harder debugging without a shell.
