Explain Pods, Deployments and Services in Kubernetes, and the main Service types.

Kubernetes · concept · levels entry, mid

In one line

A Pod is the smallest unit (one or more containers sharing network and volumes); a Deployment manages ReplicaSets for replicas, rolling updates and rollbacks; a Service gives a stable IP and DNS name that load-balances to pods chosen by a label selector, with types ClusterIP, NodePort, LoadBalancer (plus ExternalName and headless).

Detailed explanation

Pods. A pod groups containers that must run together on one node: they share a network namespace (same IP, talk via localhost) and can share volumes. Typical extras are sidecars for proxies or log shipping and init containers that run before the main container. Pods are ephemeral: if a node dies or a pod is replaced, the new pod gets a new name and IP.

Deployments. A Deployment declares a pod template and a replica count. It creates a ReplicaSet, which keeps exactly that many matching pods running. When the template changes (new image), the Deployment creates a new ReplicaSet and shifts pods gradually according to maxSurge and maxUnavailable: a rolling update. Old ReplicaSets are kept (revisionHistoryLimit) so kubectl rollout undo can roll back.

Services. Because pod IPs change, clients need a stable target. A Service selects pods by labels (app: web) and tracks the ready ones in EndpointSlices. Cluster DNS gives it a name like web.shop.svc.cluster.local.

Service types:

  • ClusterIP (default): a virtual IP reachable only inside the cluster.
  • NodePort: also opens a port (30000-32767) on every node.
  • LoadBalancer: also provisions a cloud load balancer pointing at the nodes or pods.
  • ExternalName: a DNS CNAME to an external name, no proxying.
  • Headless (clusterIP: None): no virtual IP; DNS returns pod IPs directly, used by StatefulSets and client-side load balancing.

For HTTP routing by host or path you add an Ingress or Gateway API route in front of ClusterIP Services.

How it works

  1. Deployment web with replicas: 3 and labels app: web.
  2. ReplicaSet creates three pods with those labels.
  3. Service selector app: web lists ready pod IPs in EndpointSlices.
  4. kube-proxy or eBPF rules send traffic for the Service IP to one of them.
  5. A new image triggers a rolling update via a new ReplicaSet.

Example

apiVersion: apps/v1
kind: Deployment
metadata: { name: web }
spec:
  replicas: 3
  selector: { matchLabels: { app: web } }
  template:
    metadata: { labels: { app: web } }
    spec:
      containers:
        - name: web
          image: ghcr.io/acme/web:1.4.2
          ports: [{ containerPort: 8080 }]
---
apiVersion: v1
kind: Service
metadata: { name: web }
spec:
  type: ClusterIP
  selector: { app: web }
  ports: [{ port: 80, targetPort: 8080 }]

Common mistakes

  • Selector labels on the Service not matching pod labels, so no endpoints.
  • Using NodePort or one LoadBalancer per service instead of Ingress/Gateway.
  • Creating bare pods that are not recreated after failure.

How to answer in the interview

"A pod is the smallest deployable unit: one or more containers sharing a network namespace and volumes on one node, and it's ephemeral, getting a new IP when recreated. A Deployment declares the pod template and replica count; it manages ReplicaSets to keep that many pods running and does rolling updates and rollbacks. A Service gives a stable virtual IP and DNS name and load-balances across ready pods matched by its label selector. Types are ClusterIP for internal access, NodePort which opens a port on every node, and LoadBalancer which provisions a cloud load balancer, plus ExternalName and headless Services."

Likely follow-up questions

  • When would you use a StatefulSet instead? When pods need stable identities and their own persistent volumes, such as databases.
  • What does a headless Service do? DNS returns the individual pod IPs instead of one virtual IP.
  • Service with no endpoints? Check selector labels and pod readiness.
