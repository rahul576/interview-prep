An agent tells the user it completed a task, but logs show the tool call failed. How do you prevent false success claims?

AI Agents & AIOps · scenario · levels mid, senior

In one line

Prevent false success claims with explicit structured status in tool results, a verification step that checks real state after important actions, a final report generated from recorded outcomes rather than the model's narrative, evals with deliberate failures, and evidence such as links or IDs shown to users.

Detailed explanation

Language models are trained to produce plausible continuations. After planning "create the ticket, then confirm to the user", the most likely next text is a confirmation, even when the tool call failed. Other causes: the error was buried inside a long output, the result was ambiguous (HTTP 202 accepted but not completed), or the context was compacted and the failure lost. False success is particularly damaging because users stop checking.

The fix is to make truth structural, not dependent on the model's reading.

Explicit status: every tool returns a structured result such as {"ok": false, "error": "...", "retryable": false} at the top, rather than raw text the model must interpret. Asynchronous operations return status: "pending" with a way to check.

Verification: after important actions, the system checks the actual state of the world: read back the created ticket, query the deployment status, run the tests, fetch the sent message from the outbox. This can be an explicit tool call the agent must make, or a deterministic post-condition check in code. Success may only be reported if verification passes.

Grounded reporting: the user-facing summary is generated from the recorded outcomes in the trace, for example a structured list of steps and statuses built by code, or at least the model's summary is checked by code against the tool results. A claim like "ticket created" must correspond to a successful create_ticket result with an ID.

Evals for honesty: test suites inject tool failures, timeouts and partial successes and assert that the agent reports them accurately.

Evidence: responses include links, ticket numbers or commit IDs, so users and reviewers can verify quickly.

How it works

  1. Tools return structured status with explicit success flags.
  2. After key actions, run verification against real state.
  3. Record each step's outcome in durable run state.
  4. Build the final report from recorded outcomes; check model claims.
  5. Include evidence links or IDs in the response.
  6. Run failure-injection evals regularly.

Example

def final_report(run):
    lines = []
    for step in run.steps:
        if step.kind != "action":
            continue
        verified = step.verification and step.verification.ok
        status = "done" if step.result.ok and verified else "FAILED"
        evidence = step.result.data.get("url", "") if step.result.ok else step.result.error
        lines.append(f"- {step.description}: {status} {evidence}")
    report = "\n".join(lines)
    summary = llm("Summarise for the user. Do not claim anything not in this list.", report)
    assert_claims_match(summary, run.steps)   # code check: no 'created'/'sent' without a matching ok step
    return summary + "\n\nDetails:\n" + report

Common mistakes

  • Returning raw API responses and expecting the model to interpret them.
  • Treating "request accepted" as "task completed".
  • Letting the model write the final summary from memory.
  • Never testing behaviour when tools fail.
  • No evidence in responses.

How to answer in the interview

"Models sometimes claim success because they misread an ambiguous result, the error was buried, or they just continue the expected story. I address it from several sides. Tools return explicit structured status, success true or false with an error, not raw text. After important actions a verification step checks the real state, like reading back the ticket or running the tests, and success can only be reported if that passes. The final summary is built from the recorded outcomes in the trace, or checked against them by code. Eval suites inject tool failures to test honest reporting. And responses show evidence like ticket links or commit IDs that users can check."

Likely follow-up questions

  • Design a report where a failed step can never be hidden? Generate the step list deterministically from run state and append it below any model-written summary.
  • Verification for asynchronous jobs? Poll status with a dedicated tool until done or timeout, and report pending honestly.
  • Is a judge model enough to catch false claims? It helps, but deterministic checks against tool results are stronger.
