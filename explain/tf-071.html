A change in a shared module must reach 30 environments safely. How do you roll it out?

Terraform · scenario · levels mid, senior, lead

In one line

Release the change as a new module version, never change it in place; each environment pins its version, and you upgrade in waves (sandbox and dev, test, production groups) via automated PRs such as Renovate, reviewing each plan, monitoring between waves and rolling back by re-pinning.

Detailed explanation

A shared module used by 30 environments is effectively a platform release. If consumers reference a branch like main or a floating version, one merge changes everything at once on the next apply, which is an outage multiplier. So the first principle is immutable, versioned releases: tag the module (v2.4.0) with semantic versioning and a changelog that says what changes, whether it is breaking and whether moved blocks or input changes are required.

Each environment pins a version, so an upgrade is an explicit, reviewable change per environment. Then roll out in waves: a sandbox and dev first, then test or staging, then production in small groups, for example one low-traffic region or a non-critical business unit, then the rest. Waves limit blast radius and give time to observe.

Automation makes 30 environments manageable. Renovate (which understands Terraform module versions) or a script opens one PR per environment or per wave, CI produces the plan for each, and reviewers check that plans match the expected pattern, such as "2 resources updated in place". A plan that differs, say a replacement in one environment only, is a red flag: that environment has drift or unusual inputs and gets investigated before merging.

Between waves, monitor service health, alerts and error budgets. If problems appear, pause the rollout and roll back by re-pinning the previous version, provided the change is reversible; for irreversible changes (data migrations), plan forward fixes instead.

How it works

  1. Merge the change in the module repo with tests; tag a new version.
  2. Write a changelog with upgrade notes.
  3. Automation opens version-bump PRs per environment.
  4. Wave 1: sandbox and dev; review plans, apply, monitor.
  5. Waves 2-3: test, then production groups.
  6. Pause and re-pin the old version if issues appear.

Example

module "aks" {
  source  = "app.terraform.io/acme/aks/azurerm"
  version = "2.4.0"   # bumped from 2.3.1 by Renovate in wave 2
  # ...
}
{
  "extends": ["config:recommended"],
  "packageRules": [
    { "matchManagers": ["terraform"], "matchFileNames": ["envs/dev/**"], "groupName": "wave-1" },
    { "matchManagers": ["terraform"], "matchFileNames": ["envs/prod-*/**"], "groupName": "wave-3", "minimumReleaseAge": "7 days" }
  ]
}

Common mistakes

  • Referencing modules by branch, so changes reach everything at once.
  • Approving 30 plans without comparing them to the expected pattern.
  • No changelog, so consumers cannot assess risk.
  • Rolling out to all production environments on the same day.

How to answer in the interview

"I never change a shared module in place. The change is released as a new version with a changelog, and each environment pins its version, so upgrading is explicit. Rollout goes in waves: sandbox and dev, then test, then production in small groups like one low-traffic region first. Renovate or a script opens upgrade PRs per environment so every plan is generated and reviewed, and any plan that differs from the expected pattern is a warning sign. Between waves I monitor, and if something breaks I pause and roll back by re-pinning the previous version."

Likely follow-up questions

  • What if plans differ between environments? Investigate drift or different inputs before merging that environment.
  • How do you handle breaking changes? Major version, migration guide, moved blocks, and a support window for the old version.
  • How do you test the module itself? terraform test and an example applied in a sandbox.
