A Linux server feels slow. Which commands do you use to check CPU, memory, disk and network?

Linux · concept · levels entry

In one line

Check load and CPU with uptime and top/htop, memory with free and vmstat, disk with df, du and iostat, network with ss and iftop, and logs with journalctl and dmesg, working from the overall picture down to the guilty process.

Detailed explanation

"Slow" can come from four resources, and the trick is to check each quickly rather than guess. A methodical approach such as Brendan Gregg's USE method (Utilisation, Saturation, Errors for each resource) keeps you honest.

CPU and load: uptime shows the 1, 5 and 15-minute load averages; compare them with the core count from nproc. top or htop shows per-process CPU and memory and the CPU breakdown: us and sy for real work, wa for I/O wait, st for steal on VMs. On Linux, load includes processes in uninterruptible sleep (D state), so high load with idle CPU points to I/O.

Memory: free -h shows used, available and swap; the available column matters, because Linux uses spare RAM for cache. vmstat 1 shows the run queue (r), blocked processes (b), swap in/out (si/so) and context switches. Swapping activity is a strong sign of memory pressure.

Disk: df -h for free space (and df -i for inodes), du -sh to find large directories, iostat -x 1 for per-device %util and await latency, and iotop for per-process I/O.

Network: ss -tulpn lists listening ports and owning processes, ss -s summarises connections, iftop or nload shows bandwidth. Logs: journalctl -p err --since "1 hour ago" and dmesg -T reveal OOM killer messages, disk errors or network resets.

How it works

  1. uptime and nproc: is load high relative to cores?
  2. top/htop: which process, and is time in user, system, iowait or steal?
  3. free -h, vmstat 1: memory pressure or swapping?
  4. df -h, iostat -x 1, iotop: disk full or slow?
  5. ss, iftop: connections and bandwidth.
  6. journalctl, dmesg: errors, OOM kills, hardware faults.

Example

uptime; nproc
top -o %CPU            # or htop
free -h
vmstat 1 5
df -h; df -i
iostat -x 1 3
ss -tulpn; ss -s
journalctl -p err --since "1 hour ago"
dmesg -T | grep -iE "oom|error|i/o"

Common mistakes

  • Treating the "free" memory column as available memory, ignoring cache.
  • Judging load average without knowing the number of cores.
  • Ignoring iowait and steal, and blaming the application.
  • Forgetting the logs, where the OOM killer leaves clear messages.

How to answer in the interview

"I start with uptime to compare the load average with the number of cores, then top or htop to see which processes use CPU and memory, and whether time goes to iowait or steal. free -h and vmstat 1 show memory and swapping. For disk, df -h checks space, du finds large directories and iostat -x shows utilisation and latency per device. For network, ss lists connections and listening ports and iftop shows bandwidth. Finally journalctl and dmesg tell me about OOM kills or hardware errors. That narrows it down to the resource and then the process."

Likely follow-up questions

  • Load is 16 on 8 cores but CPU is idle. What could it be? Processes stuck in D state waiting on disk or NFS; check iowait, iostat and ps for D states.
  • What is a good quick overview tool? sar for history, or atop, plus your monitoring dashboards.
  • How do you see which process uses the network? ss -p or nethogs.
