How do service discovery, API gateways and service meshes fit together in a microservices architecture?

Distributed Systems · concept · levels entry, mid, senior

In one line

Service discovery resolves service names to healthy instances; the API gateway is the north-south entry point (auth, rate limits, routing); a service mesh handles east-west traffic with sidecars adding mTLS, retries, timeouts and telemetry without code changes.

Detailed explanation

Discovery: instances register (Consul, Eureka) or the platform tracks them (Kubernetes Endpoints/EndpointSlices behind a Service's DNS name). Clients resolve names at call time; health checks remove dead instances. Client-side discovery (the client picks an instance) vs server-side (a load balancer picks).

API gateway (Kong, Apigee, AWS API Gateway, Azure API Management, Envoy Gateway): terminates TLS, validates JWT/OAuth tokens, applies rate limits and quotas, routes /orders/* to the order service, handles versioning, transforms requests, logs and meters. It's about external clients.

Service mesh (Istio, Linkerd, Consul Connect; sidecar or ambient/eBPF modes): each service's traffic passes through a proxy. Centrally configured policies give mutual TLS with workload identities, authorization (who may call whom), retries, timeouts, circuit breaking, traffic splitting for canaries, and uniform metrics/traces. It's about internal traffic.

They complement each other: gateway at the edge, mesh inside, discovery underneath.

How it works

  1. Client → DNS → gateway (auth, rate limit) → orders service name.
  2. Discovery resolves to healthy pods.
  3. Mesh sidecar (client side) → mTLS → sidecar (server side) → pod, with retries/timeouts and telemetry.

Example

apiVersion: networking.istio.io/v1
kind: VirtualService
metadata: { name: orders }
spec:
  hosts: [orders]
  http:
  - route:
    - { destination: { host: orders, subset: v1 }, weight: 90 }
    - { destination: { host: orders, subset: v2 }, weight: 10 }
    timeout: 2s
    retries: { attempts: 2, perTryTimeout: 500ms }

Common mistakes

  • Putting business logic into the gateway.
  • Adopting a mesh for 5 services (operational overhead).
  • Retries configured in both mesh and code.

How to answer in the interview

"Discovery maps names to healthy instances; in Kubernetes that's Services and DNS. The API gateway is the front door for external clients, handling TLS, authentication, rate limiting and routing. A service mesh manages service-to-service traffic through proxies, giving mTLS, authorization, retries, timeouts, canary splits and telemetry without code changes. Gateway at the edge, mesh inside."

Likely follow-up questions

  • When is a mesh not worth it? Few services, small team, no mTLS/traffic-policy needs.
  • Ambient mesh? Node-level proxies instead of sidecars, lower overhead.
  • Gateway vs ingress controller? Ingress routes HTTP; gateways add API management features.
