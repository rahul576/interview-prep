How can a queue and Lambda be combined to orchestrate asynchronous processing?

Cloud (AWS) · design · levels senior, lead

In one line

The API accepts, persists and enqueues the request to SQS, returning 202 Accepted with an id. Lambda consumers process messages in batches and hand off to the next step via queues, SNS or EventBridge, or a Step Functions state machine for complex flows. Reliability comes from DLQs, partial batch failures, idempotency and concurrency limits.

Detailed explanation

Synchronous request chains are fragile: one slow step blocks the user and failures cascade. Putting a queue between steps decouples them. The API stays fast, each step scales on its own, and a spike just becomes queue depth instead of an outage.

The typical flow: API Gateway plus a Lambda (or a container) validates the request and writes a record with status RECEIVED. It sends a message to SQS and returns 202 with a requestId the client can use to check status or receive a callback. The SQS event source mapping polls the queue and invokes the worker Lambda with batches (up to 10 for standard queues by default, more with a batching window). The worker calls downstream systems, updates the status, and publishes to the next queue or to an SNS topic / EventBridge bus for fan-out.

When the flow needs branching, parallel steps, long waits, human approval or compensation (saga), chained queues become hard to reason about. Step Functions gives an explicit state machine with built-in retries, catch blocks and visual execution history.

Reliability details matter:

  • Visibility timeout should be at least 6x the function timeout.
  • ReportBatchItemFailures retries only the failed messages.
  • A redrive policy sends poison messages to a DLQ after N receives.
  • Idempotent handlers keyed by request id are needed because delivery is at least once.
  • Maximum concurrency on the event source protects downstream databases.

How it works

  1. Client POST /orders. The API stores the order as RECEIVED, sends to orders-queue and returns 202 {id}.
  2. Lambda polls the queue and processes a batch, returning failed message ids.
  3. On success it updates the status and emits OrderValidated to EventBridge.
  4. Rules route the event to the payment and notification queues.
  5. Failures retry until maxReceiveCount, then land in the DLQ with an alarm.
  6. CloudWatch watches ApproximateNumberOfMessagesVisible, ApproximateAgeOfOldestMessage and Lambda errors and throttles.

Example

def handler(event, context):
    failures = []
    for record in event["Records"]:
        msg = json.loads(record["body"])
        try:
            if already_processed(msg["requestId"]):   # idempotency table
                continue
            process(msg)
            mark_processed(msg["requestId"])
        except Exception:
            failures.append({"itemIdentifier": record["messageId"]})
    return {"batchItemFailures": failures}

Common mistakes

  • Visibility timeout shorter than processing time, which causes duplicate processing.
  • Failing the whole batch for one bad message.
  • No DLQ, or a DLQ with no alarm.
  • Unlimited Lambda concurrency overwhelming a relational database.

How to answer in the interview

"The API validates the request, stores it as RECEIVED, puts a message on SQS and returns 202 with an id. A Lambda triggered by the queue processes batches and updates the status. It passes work on through the next queue or an EventBridge event, so each step scales and fails independently. For branching, waits or compensation I'd switch to Step Functions. For reliability I'd use DLQs with alarms, partial batch failure reporting, idempotent handlers keyed by request id, and maximum concurrency to protect downstream systems. I'd monitor queue depth and the age of the oldest message."

Likely follow-up questions

  • When to switch to Step Functions? When you need branching, long waits, human steps or sagas, or when you need clear end-to-end visibility.
  • FIFO queues with Lambda? They give ordering per message group id. Throughput scales with the number of groups.
  • How does the client get the result? It polls a status endpoint with backoff, or gets a webhook or WebSocket notification.
