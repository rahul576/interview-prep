When would you choose gRPC or GraphQL over REST?

REST & API Design · concept · levels mid, senior

In one line

Use REST as the default for public, cacheable, simple APIs; choose gRPC (HTTP/2, protobuf, generated clients, streaming) for fast internal service-to-service calls; choose GraphQL when clients need to select fields across many resources, such as complex UIs and mobile apps.

Detailed explanation

REST over HTTP/JSON is universally understood: any language, browser or curl can call it, HTTP caching and CDNs work out of the box, and tooling (OpenAPI, gateways, API management) is mature. Its downsides are verbose payloads, no enforced schema unless you use OpenAPI, and over-fetching or under-fetching: a screen may need five calls or receive fields it does not use.

gRPC uses HTTP/2 and Protocol Buffers. You define services and messages in a .proto file and generate strongly typed client and server code. Binary encoding is compact and fast, HTTP/2 multiplexes many calls over one connection, and gRPC supports unary, server-streaming, client-streaming and bidirectional streaming, plus deadlines and cancellation built in. It is ideal for internal microservice traffic, high-throughput or low-latency paths, and polyglot systems. Downsides: browsers cannot call it directly (gRPC-Web or a proxy is needed), payloads are not human-readable, HTTP caching does not apply, and some load balancers need HTTP/2 awareness. Schema evolution is safe if you follow protobuf rules: never reuse field numbers, add new optional fields.

GraphQL exposes one endpoint with a typed schema; clients send queries that specify exactly the fields and nested relations they need. That suits frontends aggregating many resources, mobile apps on slow networks, and BFF layers. Downsides: HTTP caching is harder (mostly POST to one URL; persisted queries help), N+1 resolver problems need batching with DataLoader, authorisation must be enforced per field or type, and query cost limits are needed to stop abusive queries. Spring for GraphQL provides support in Spring Boot.

Many systems mix them: REST or GraphQL at the edge, gRPC internally, and async messaging for events.

How it works

  1. REST: resources + HTTP verbs + JSON; cache with HTTP headers.
  2. gRPC: .proto contract, generated stubs, binary over HTTP/2.
  3. GraphQL: schema + resolvers; clients query only needed fields.
  4. Pick per boundary: public, internal, or UI aggregation.

Example

syntax = "proto3";
service PriceService {
  rpc GetPrice (PriceRequest) returns (PriceReply);
  rpc StreamPrices (PriceRequest) returns (stream PriceReply);
}
message PriceRequest { string sku = 1; }
message PriceReply   { string sku = 1; int64 amount_minor = 2; string currency = 3; }
query { order(id: "42") { status total customer { name } items { sku qty } } }

Common mistakes

  • Choosing GraphQL for simple CRUD with one client.
  • Exposing gRPC directly to browsers without gRPC-Web.
  • Reusing protobuf field numbers, breaking compatibility.
  • Ignoring N+1 and query depth limits in GraphQL.

How to answer in the interview

"REST is my default, especially for public APIs, because it's simple, cacheable and every client understands it. I'd pick gRPC for internal service-to-service calls where performance matters: it uses HTTP/2 and protobuf, gives generated, strongly typed clients, deadlines and bidirectional streaming. I'd pick GraphQL when frontends need flexible data, like a mobile app showing an order with customer and items in one round trip, since clients select exactly the fields they want. The trade-offs are complexity: GraphQL makes caching, per-field authorisation and N+1 resolvers harder, and gRPC isn't browser-friendly. Often it's REST or GraphQL at the edge and gRPC inside."

Likely follow-up questions

  • How do you version a gRPC API safely? Add fields with new numbers, never reuse or change types, reserve removed numbers, use a package version for breaking changes.
  • How do you solve N+1 in GraphQL? Batch resolvers with DataLoader or @BatchMapping.
  • Can gRPC go through an API gateway? Yes, with HTTP/2-aware gateways like Envoy.
