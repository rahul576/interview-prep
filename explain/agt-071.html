How do you manage identities and credentials for AI agents as non-human identities?

AI Agents & AIOps · concept · levels senior, lead

In one line

Give each agent its own identity, authenticated with short-lived credentials (workload identity federation, OAuth), use delegated permissions when acting for a user, keep an inventory with owner and lifecycle, apply least privilege with access reviews, and monitor and revoke quickly.

Detailed explanation

Agents are a fast-growing class of non-human identities, alongside service accounts and workloads. The common anti-patterns are shared API keys, a developer's personal access token baked into configuration, or one powerful service principal used by many agents. These make it impossible to tell which agent did what, to limit damage, or to revoke one agent without breaking others.

Each agent, or each agent deployment, gets its own identity in the identity provider: a managed identity, workload identity, service principal or dedicated agent identity features such as Microsoft Entra Agent ID. It authenticates with short-lived credentials through workload identity federation (for example Kubernetes service account tokens exchanged for cloud tokens) or OAuth client credentials, never long-lived secrets in environment variables.

When an agent acts on behalf of a person, it uses delegated permissions (OAuth on-behalf-of or token exchange), so it can never exceed that user's rights, and audit logs record both the user and the agent. Every agent identity has an owner, purpose and lifecycle in an inventory, so abandoned agents are decommissioned. Permissions follow least privilege and get regular access reviews. Activity is monitored for anomalies, such as unusual resources or volumes, and credentials can be revoked quickly with a kill switch.

How it works

  1. Register the agent identity with owner, purpose and expiry review date.
  2. Grant minimal roles scoped to required resources.
  3. Configure workload identity federation; no static secrets.
  4. For user-facing actions, exchange the user token for a delegated token.
  5. Log every call with agent and user identity.
  6. Review access periodically; revoke on decommission or anomaly.

Example

# Kubernetes service account federated to Azure via workload identity
apiVersion: v1
kind: ServiceAccount
metadata:
  name: invoice-agent
  namespace: agents
  annotations:
    azure.workload.identity/client-id: "<invoice-agent-app-id>"
  labels:
    owner: team-finance-platform
    purpose: invoice-triage
    review-by: "2027-03-31"

The agent receives short-lived tokens for only the Storage and Service Bus resources it needs.

Common mistakes

  • Agents running with a developer's personal token.
  • One identity shared across many agents.
  • Long-lived secrets in configuration files.
  • No owner, so orphaned agents keep access for years.

How to answer in the interview

"I treat agents as non-human identities. Each agent gets its own identity in the identity provider, like a managed or workload identity or Entra Agent ID, and authenticates with short-lived credentials through workload identity federation or OAuth, never long-lived keys. When it acts for a person it uses delegated permissions, so it can't exceed that user's rights and logs show both. Every agent identity has an owner, purpose and lifecycle in an inventory, gets least privilege and regular access reviews, and is monitored so we can revoke it quickly."

Likely follow-up questions

  • Owner after reorganisation? Transfer is part of the reorg checklist; unowned identities get disabled.
  • Agent-to-agent calls? Each agent authenticates with its own identity; propagate the user context.
  • Detecting misuse? Baseline normal activity and alert on deviations.
