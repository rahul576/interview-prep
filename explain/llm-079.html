When should you use batch APIs for LLM workloads, and how do you operate them?

LLMOps & RAG · concept · levels entry, mid, senior

In one line

Use batch APIs for work nobody is waiting on: requests are processed asynchronously (within a window such as 24 hours, often much sooner) at roughly half price, with separate quotas that protect real-time traffic; operate them by submitting request files with custom IDs, polling or being notified, matching results by ID, handling partial failures and validating outputs.

Detailed explanation

What they are. Anthropic's Message Batches API, OpenAI's Batch API, Azure OpenAI global batch deployments and Vertex AI batch prediction for Gemini all accept large sets of requests for asynchronous processing. Typical properties: a completion window of up to 24 hours, about 50% discount, and a separate, larger quota, so a nightly job can't starve interactive users. Exact limits on batch size and file size vary by provider.

Good fits: classifying or tagging an archive of tickets or documents; summarising or translating large collections; generating product descriptions or metadata in bulk; data labelling; running evaluation suites and LLM-judge scoring; backfills after a prompt or model change. Bad fits: anything a user waits for, or chains where each step depends on the previous result within minutes.

Operating them:

  1. Build the request file: JSONL or a request list, each item with a custom ID (your record key) and the full request body (model, messages, max tokens).
  2. Submit and store the batch ID with job metadata.
  3. Poll status or receive a notification/webhook; batches move through states like in progress, ended, expired, cancelled.
  4. Download results and match them to records via custom ID; order is not guaranteed.
  5. Handle partial failures: some items error (invalid request, rate or server errors) or expire; collect them and resubmit in a new batch with limited retries.
  6. Validate outputs (schema, required fields) before writing to downstream systems; write idempotently keyed by custom ID.

Orchestration. Run batches as normal data pipeline jobs (Airflow, Dagster, cloud workflows) with checkpoints, monitoring of completion time and failure rate, and cost tracking. Prompt caching can sometimes combine with batch discounts for shared prefixes.

How it works

  1. Select records not yet processed.
  2. Write JSONL with custom IDs; submit.
  3. Poll until ended.
  4. Parse results; validate; upsert by custom ID.
  5. Resubmit failures; alert if failure rate is high.
  6. Mark job complete; record cost.

Example

batch = client.messages.batches.create(requests=[
    {"custom_id": f"ticket-{t.id}",
     "params": {"model": MODEL_ID, "max_tokens": 200,
                "messages": [{"role": "user", "content": f"Classify: {t.text}"}]}}
    for t in tickets
])
# later
for r in client.messages.batches.results(batch.id):

Common mistakes

  • Running large offline jobs on real-time endpoints at full price.
  • Assuming results come back in input order.
  • Ignoring partial failures and expired items.
  • Writing unvalidated outputs into production tables.

How to answer in the interview

"Batch APIs from Anthropic, OpenAI, Azure and Google process large sets of requests asynchronously within a window like 24 hours, usually faster, at around half price, and with separate quotas so they don't eat into the rate limits of interactive traffic. I use them whenever nobody waits: classifying archives, bulk summaries, generating metadata, running evaluations. Operationally I build a file of requests with custom IDs, submit, poll or get notified, then match results by custom ID. Some items fail individually, so I resubmit those, validate outputs before writing them downstream, and orchestrate it like any other data job."

Likely follow-up questions

  • Migrating a nightly real-time job? Run both in parallel for a cycle, compare outputs and timing, then switch.
  • Deadline needs? If results are needed within an hour, batch may not guarantee it; keep a real-time fallback.
  • Idempotency? Upsert by custom ID so resubmissions don't duplicate.
