How do Spring Data JPA derived query methods and @Query work?

Spring Data & JPA · concept · levels entry, mid

In one line

Spring Data JPA derives queries from method names (findByStatusAndCreatedAtAfter), while @Query gives explicit JPQL or native SQL; methods accept Pageable and Sort, return Page, Slice or projections, and update/delete queries need @Modifying plus a transaction because they bypass the persistence context.

Detailed explanation

Derived queries. At startup Spring Data parses repository method names: a subject (find…By, count…By, exists…By, delete…By, findFirst10By), then property expressions joined with And/Or and operators such as GreaterThan, Between, Like, In, IsNull, IgnoreCase, and OrderBy…. findByStatusAndCreatedAtAfter(Status s, Instant t) becomes JPQL where status = ?1 and createdAt > ?2. Typos fail fast at startup. They're great for simple queries but get unreadable beyond two or three conditions.

@Query. For joins, fetch joins, aggregates or complex conditions, write JPQL in @Query, which works on entities and stays portable. Use nativeQuery = true when you need database-specific features such as window functions, JSON operators or hints; native queries return entities, projections or tuples. Prefer named parameters (:status with @Param). For dynamic filters, use Specifications, Querydsl or Query by Example rather than many method variants.

Paging and sorting. Add a Pageable or Sort parameter. Returning Page<T> runs an additional count query to know total elements and pages; Slice<T> only fetches one extra row to know whether a next slice exists, which is cheaper for infinite scroll. For deep pagination, consider keyset (ScrollPosition/Window in newer Spring Data) instead of offsets.

Projections. Interface projections (interface OrderSummary { Long getId(); String getCustomerName(); }), class/record DTO projections, or constructor expressions in JPQL fetch only needed columns, avoiding entity overhead and lazy-loading issues.

Modifying queries. @Query("update ...") or delete needs @Modifying and must run inside a transaction (@Transactional). These bulk statements go directly to the database and bypass the persistence context: managed entities in memory become stale, and lifecycle callbacks and cascades don't run. Use @Modifying(clearAutomatically = true, flushAutomatically = true) to flush pending changes first and clear afterwards.

How it works

  1. Repository interface is scanned at startup.
  2. Each method is parsed (derived) or its @Query validated.
  3. A proxy implementation is created.
  4. At call time, parameters bind and the query executes via EntityManager.
  5. Results map to entities, projections, Page or Slice.

Example

public interface OrderRepository extends JpaRepository<Order, Long> {

    List<Order> findByStatusAndCreatedAtAfter(Status status, Instant after);

    Slice<OrderSummary> findByCustomerIdOrderByCreatedAtDesc(long customerId, Pageable page);

    @Query("select o from Order o join fetch o.customer c where c.country = :country")
    Page<Order> findByCountry(@Param("country") String country, Pageable page);

    @Query(value = "select * from orders where tags @> cast(:tag as jsonb)", nativeQuery = true)
    List<Order> findByTag(@Param("tag") String tagJson);

    @Modifying(clearAutomatically = true, flushAutomatically = true)
    @Transactional
    @Query("update Order o set o.status = 'EXPIRED' where o.createdAt < :cutoff and o.status = 'PENDING'")
    int expireOld(@Param("cutoff") Instant cutoff);
}

Common mistakes

  • Extremely long derived method names.
  • Forgetting @Modifying or a transaction for updates.
  • Stale managed entities after bulk updates.
  • Page with fetch-joined collections, causing in-memory pagination and slow counts.

How to answer in the interview

"Spring Data generates queries from method names like findByStatusAndCreatedAtAfter, which is great for simple cases. For anything complex I use @Query with JPQL, or native SQL when I need database-specific features. Methods can take Pageable and Sort and return Page or Slice. Interface or DTO projections fetch only needed columns. Update and delete queries need @Modifying and a transaction, and because they bypass the persistence context I flush and clear around them."

Likely follow-up questions

  • Page vs Slice? Page runs a count query for totals; Slice only knows if there's a next one.
  • Dynamic search filters? Specifications, Querydsl or Query by Example.
  • Custom count query? @Query(countQuery = "...") for expensive or fetch-join queries.
