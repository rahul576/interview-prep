Each pull request should get a temporary preview environment created by Terraform and destroyed when the PR closes. How do you design this?

Terraform · scenario · levels mid, senior, lead

In one line

Give each pull request its own state (backend key or workspace), PR-number naming, a destroy on PR close plus a scheduled TTL cleanup, and keep it cheap by reusing shared base infrastructure with small sizes and caps on count and cost.

Detailed explanation

Preview environments let reviewers and testers see a change running before merge. The design challenge is isolation, speed and cost. Isolation comes from a separate state per PR, for example previews/pr-123.tfstate passed through -backend-config or a Terraform workspace named pr-123, and from including the PR number in every resource name, DNS record and namespace so previews never collide.

Speed and cost come from splitting the infrastructure. Expensive, slow things like VNets, a shared Kubernetes cluster, a database server and the ingress controller live in a long-lived base state. The preview configuration creates only thin per-PR pieces: a Kubernetes namespace, a database on the shared server, a DNS record such as pr-123.preview.example.com, secrets and the app deployment. A preview then appears in a couple of minutes rather than forty.

Lifecycle is driven by the CI system: apply when the PR opens or updates, terraform destroy when it closes or merges. Destroys fail sometimes (an API timeout, a dependency created outside Terraform), so a scheduled cleanup job compares existing previews with open PRs and TTL tags and removes leftovers, including their state files. Guardrails include a maximum number of concurrent previews, small SKUs, auto-shutdown, budget alerts and tags like preview=true and pr=123 for cost tracking.

How it works

  1. PR opened: pipeline runs init with key previews/pr-<n>.tfstate, passing pr_number.
  2. Plan and apply create namespace, database, DNS and deployment from the shared base.
  3. The pipeline comments the preview URL on the PR.
  4. PR updated: re-apply with the new image tag.
  5. PR closed: terraform destroy, then delete the state file.
  6. Nightly job removes previews whose PR is closed or whose TTL expired.

Example

# GitHub Actions (excerpt)
on:
  pull_request:
    types: [opened, synchronize, reopened, closed]
concurrency: preview-${{ github.event.number }}
jobs:
  preview:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init -backend-config="key=previews/pr-${{ github.event.number }}.tfstate"
      - if: github.event.action != 'closed'
        run: terraform apply -auto-approve -var="pr_number=${{ github.event.number }}"
      - if: github.event.action == 'closed'
        run: terraform destroy -auto-approve -var="pr_number=${{ github.event.number }}"

Common mistakes

  • Building a full stack per PR, which is slow and expensive.
  • No cleanup job, so failed destroys leave orphans billing for months.
  • Sharing one state for all previews, causing lock contention and accidental deletes.
  • Running previews from forked PRs with privileged credentials.

How to answer in the interview

"Each PR gets its own state, a backend key like previews/pr-123 or a workspace, and every name includes the PR number. To keep it fast and cheap, previews reuse a shared base: network, a shared cluster and database server, and only create a namespace, a database, DNS and the deployment. The pipeline applies on open and update and destroys on close. Because destroy can fail, a scheduled job removes previews whose PR is closed or TTL expired, using tags. I also cap the number of previews and track their cost."

Likely follow-up questions

  • How do you handle data and migrations? Seed a small anonymised dataset per preview database and run migrations in the deploy step.
  • Forked PRs? Do not run privileged previews automatically; require a maintainer label.
  • Workspaces or keys? Either works; keys keep naming explicit in CI.
