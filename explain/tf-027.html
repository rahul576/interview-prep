Every terraform plan shows the same change on an IAM policy even right after apply. What causes perpetual diffs and how do you fix them?

Terraform · scenario · levels mid, senior

In one line

A perpetual diff means what Terraform sends is not what the API returns on the next read; for IAM policies the API normalises JSON, so build policies with jsonencode or aws_iam_policy_document, fix external modifications or overlapping resources, use ignore_changes only for attributes legitimately managed elsewhere, and report provider bugs.

Detailed explanation

After apply, Terraform stores what the provider returned. On the next plan it refreshes the object and compares it with configuration. If the API stores the value in a different form than you wrote, the comparison never matches, and every plan shows the same update; applying "fixes" it and the cycle repeats. This noise is harmful: reviewers learn to ignore plans and miss real changes.

IAM policies are the classic case. AWS normalises policy JSON: it may reorder keys, strip whitespace, turn "Action": "s3:GetObject" into a list or back, or return principals in canonical ARN form. A hand-written heredoc rarely matches byte for byte. The AWS provider tries to compare policies semantically, but formatting quirks still cause diffs. Building the policy with jsonencode() or the aws_iam_policy_document data source produces consistent, normalised JSON and usually solves it.

Other common causes:

  • Case or format normalisation: lowercase names, CIDR notation, trailing dots in DNS names, time formats.
  • Defaults added by the API that you did not set, or a provider default different from the API's.
  • External systems: Azure Policy appending tags, an autoscaler changing desired_count or node counts, a Kubernetes controller adding annotations, another team's script.
  • Two resources managing the same thing: inline ingress blocks plus separate rule resources, inline bucket policy plus aws_s3_bucket_policy, or two configurations owning one object.

Fix the source where you can: write the value as the API stores it, remove overlapping management, or let only one system own an attribute. Use lifecycle { ignore_changes = [...] } for attributes legitimately managed elsewhere, narrowly, never for whole resources. If the provider is wrong, reproduce it minimally and report it with the plan output.

How it works

  1. Apply sends value A; API stores normalised A'.
  2. Refresh reads A'; Terraform compares with A from config.
  3. A' differs from A, so plan proposes an update.
  4. Fix by matching representation, removing conflicts or ignoring the attribute.

Example

data "aws_iam_policy_document" "read_logs" {
  statement {
    actions   = ["s3:GetObject", "s3:ListBucket"]
    resources = [aws_s3_bucket.logs.arn, "${aws_s3_bucket.logs.arn}/*"]
  }
}

resource "aws_iam_policy" "read_logs" {
  name   = "read-logs"
  policy = data.aws_iam_policy_document.read_logs.json
}

resource "aws_ecs_service" "api" {
  # ...
  lifecycle { ignore_changes = [desired_count] }   # owned by autoscaling
}

Common mistakes

  • Accepting perpetual diffs as normal noise.
  • ignore_changes = all to silence diffs.
  • Mixing inline rules and separate rule resources.
  • Not checking whether a newer provider version fixed the bug.

How to answer in the interview

"A perpetual diff means what Terraform sends isn't what the API returns on the next read. With IAM policies the API normalises the JSON, reordering keys, removing whitespace or converting a single action into a list, so a hand-written heredoc never matches exactly. The fix is to build the policy with jsonencode or the aws_iam_policy_document data source. Other causes are case differences, defaults the API adds, attributes changed by another system like Azure Policy tags or an autoscaler, or two resources managing the same setting. I fix the source when possible, use ignore_changes only for attributes legitimately managed elsewhere, and report genuine provider bugs."

Likely follow-up questions

  • Finding the attribute in a large plan? terraform show -json and diff before/after for that resource, or filter the plan output.
  • Why are perpetual diffs dangerous? Reviewers stop reading plans and miss real changes.
  • ignore_changes risks? Real drift on that attribute is hidden too.
