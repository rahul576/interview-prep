How do containers find and talk to each other on the same host?

Docker · concept · levels entry

In one line

Attach containers to the same user-defined bridge network; Docker's embedded DNS then resolves container and service names, and they talk directly on the container port without publishing anything.

Detailed explanation

Each Docker network is an isolated virtual switch. A user-defined bridge created with docker network create gives containers private IP addresses and, importantly, an embedded DNS server at 127.0.0.11 inside each container. That server resolves the names of other containers on the same network, their --network-alias names, and in Compose the service names. So an API container simply connects to db:5432.

Traffic between containers on the same network goes straight over the bridge to the container port. Publishing with -p 8080:80 is only needed for traffic coming from the host or outside world. Not publishing internal services like databases is a security win.

The legacy default bridge network (bridge, used when you do not specify --network) does not provide name resolution. Containers there can only use IP addresses or the deprecated --link option, which is why you should always create your own network. Containers on different user-defined networks cannot reach each other unless you connect a container to both with docker network connect, which is a useful way to segment front-end and back-end tiers.

Docker Compose creates a network called <project>_default automatically, so every service is reachable by its service name; when scaled, the name resolves to all replicas (simple DNS round robin). Container IP addresses change whenever containers are recreated, so names are the only reliable addresses. Across several hosts you need an overlay network (Swarm) or an orchestrator's service discovery.

How it works

  1. docker network create appnet creates a bridge and subnet.
  2. Containers started with --network appnet get an IP on it.
  3. Each container's /etc/resolv.conf points to the embedded DNS.
  4. Name lookups for peers are answered by Docker; others are forwarded upstream.
  5. Packets travel over the bridge directly to the target port.

Example

docker network create appnet
docker run -d --name db --network appnet -e POSTGRES_PASSWORD=secret postgres:16
docker run -d --name api --network appnet \
  -e DB_URL=jdbc:postgresql://db:5432/app -p 8080:8080 registry.local/api:1.4
docker run --rm --network appnet busybox nslookup db

Common mistakes

  • Using the default bridge and expecting names to resolve.
  • Hard-coding container IP addresses.
  • Connecting to the published host port from another container instead of the container port.
  • Publishing database ports when only the API needs them.

How to answer in the interview

"I put containers that need to talk on the same user-defined bridge network. Docker runs an embedded DNS server there, so the API can connect to db:5432 by name, using the container port directly without publishing anything to the host. The old default bridge network doesn't do name resolution, so containers there would need IPs or legacy links. Compose creates a network per project automatically, where each service is reachable by its service name. I never hard-code IPs because they change whenever a container is recreated."

Likely follow-up questions

  • Why avoid hard-coded container IPs? They change on every recreation and differ between environments.
  • How do you isolate tiers? Separate networks; only the API joins both.
  • What about multiple hosts? Overlay networks or Kubernetes services.
