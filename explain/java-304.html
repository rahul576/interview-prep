Explain the request flow through Spring MVC, from DispatcherServlet to response.

Spring Framework · concept · levels mid, senior

In one line

A request passes through servlet filters (including Spring Security) to the DispatcherServlet, which uses a HandlerMapping to find the controller method, runs interceptor preHandle, invokes it through a HandlerAdapter with argument resolvers and HttpMessageConverters, writes the return value back, routes exceptions to HandlerExceptionResolvers / @ControllerAdvice, and finishes with postHandle/afterCompletion.

Detailed explanation

Spring MVC follows the front controller pattern: one servlet, the DispatcherServlet, receives every request and delegates to pluggable strategy beans that Boot auto-configures.

Before it, the servlet container runs the filter chain: character encoding, request logging, CORS, the Spring Security FilterChainProxy and so on. Filters can reject a request before Spring MVC is involved, which is why an unauthenticated call gets a 401 without touching your controller.

Inside the dispatcher:

  1. HandlerMapping: RequestMappingHandlerMapping matches the path, HTTP method, consumes/produces, params and headers against registered @RequestMapping methods and returns a HandlerExecutionChain: the handler plus its interceptors. No match gives 404, a wrong method 405, a media type mismatch 415 or 406.
  2. HandlerInterceptor.preHandle runs for each interceptor; returning false stops processing.
  3. HandlerAdapter (RequestMappingHandlerAdapter) invokes the method. HandlerMethodArgumentResolvers supply each parameter: @PathVariable, @RequestParam, @RequestHeader, Principal, Pageable, and @RequestBody, which an HttpMessageConverter (Jackson's MappingJackson2HttpMessageConverter) deserialises from JSON. @Valid triggers validation here.
  4. Return value handlers: for @ResponseBody or ResponseEntity, content negotiation picks a converter based on Accept and serialises the result; for views, a ViewResolver renders a template.
  5. postHandle runs after the handler (for @ResponseBody the response is already committed, so it is of limited use).
  6. Exceptions at any step go to HandlerExceptionResolvers: ExceptionHandlerExceptionResolver (your @ExceptionHandler and @ControllerAdvice), ResponseStatusExceptionResolver, and DefaultHandlerExceptionResolver for Spring's own exceptions.
  7. afterCompletion always runs, even after errors, useful for cleanup and timing.

How it works

  1. Container → filters → DispatcherServlet.doDispatch.
  2. HandlerMapping finds handler + interceptors.
  3. preHandle → HandlerAdapter → argument resolution and conversion → controller method.
  4. Return value handled by a message converter (or view).
  5. Exceptions resolved by exception resolvers.
  6. afterCompletion, then the response flows back through the filters.

Example

@Component
class TimingInterceptor implements HandlerInterceptor {
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {
        req.setAttribute("start", System.nanoTime());
        return true;
    }
    public void afterCompletion(HttpServletRequest req, HttpServletResponse res, Object handler, Exception ex) {
        long ms = (System.nanoTime() - (long) req.getAttribute("start")) / 1_000_000;
        if (handler instanceof HandlerMethod hm) log.info("{} took {} ms", hm.getMethod().getName(), ms);
    }
}

@Configuration
class WebConfig implements WebMvcConfigurer {
    private final TimingInterceptor timing;
    WebConfig(TimingInterceptor timing) { this.timing = timing; }
    public void addInterceptors(InterceptorRegistry r) { r.addInterceptor(timing).addPathPatterns("/api/**"); }
}
Request -> Filters (Security, CORS) -> DispatcherServlet -> HandlerMapping
        -> preHandle -> HandlerAdapter (argument resolvers, Jackson) -> @GetMapping method
        -> return value -> Jackson -> postHandle -> afterCompletion -> Response

Common mistakes

  • Expecting interceptors to run for requests rejected by Spring Security filters.
  • Trying to modify the response body in postHandle for @ResponseBody methods.
  • Configuring a custom ObjectMapper incorrectly and replacing Boot's converters.
  • Doing authentication in an interceptor instead of in Spring Security.

How to answer in the interview

"A request first goes through the servlet filters, such as Spring Security, and then reaches the DispatcherServlet, the front controller. It asks the HandlerMapping which controller method matches the URL and HTTP method, which also returns the interceptors. Interceptors' preHandle run, then the HandlerAdapter invokes the method, using argument resolvers for path variables, request params and headers, and HttpMessageConverters like Jackson to deserialise the JSON body. The return value is serialised back by a message converter after content negotiation. Exceptions go to the exception resolvers, including my @ControllerAdvice handlers, and postHandle and afterCompletion hooks run at the end."

Likely follow-up questions

  • Where would you put request logging: a filter or an interceptor? A filter, because it sees every request, including those rejected earlier, and can wrap the body.
  • What happens if no handler matches? 404 through NoResourceFoundException in Spring 6.1+.
  • How does content negotiation work? The Accept header is matched against converters' supported media types and produces.
