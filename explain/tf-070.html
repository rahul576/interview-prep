for_each fails with an error saying the value cannot be a set of objects or contains sensitive values. How do you fix it?

Terraform · scenario · levels mid, senior

In one line

for_each accepts only a map or a set of strings, so convert a set or list of objects into a map keyed by a unique attribute; it also rejects sensitive values because keys appear in resource addresses and logs, so restructure input to keep secrets in values, not keys, or use nonsensitive on keys that are not actually secret.

Detailed explanation

Every instance created by for_each gets an address such as azuread_user.this["alice"]. Terraform needs a string key per instance, known at plan time. A list or set of objects has no natural key, so Terraform refuses with an error like "the for_each argument must be a map, or set of strings, and you have provided a value of type set of object".

The fix is a for expression that builds a map using a unique attribute: { for u in var.users : u.name => u }. Choose a stable, unique attribute (name, email, logical ID), not a list index, so additions and removals affect only that item. A plain list of strings can be converted with toset().

The second error is about sensitivity. If the collection is marked sensitive, for example it came from a sensitive = true variable, a secret data source, or was built from a sensitive value, Terraform says sensitive values cannot be used as for_each arguments. Keys become part of resource addresses, which are printed in plan output, logs, state and UI, and cannot be redacted. Allowing them would leak secrets.

Solutions: restructure the input so keys are non-secret names and secret material lives only in the values, for example a map from user name to an object containing the password. Values of a non-sensitive map can still be sensitive and remain redacted. If the keys are genuinely not secret, and the sensitivity only propagated from a wider object, wrap the keys with nonsensitive(), but only after confirming that, since it removes protection deliberately.

How it works

  1. Terraform evaluates the for_each expression.
  2. It rejects non-map, non-string-set types.
  3. It rejects values marked sensitive.
  4. Convert objects to a map keyed by a stable attribute.
  5. Separate secret values from keys, or apply nonsensitive to safe keys.

Example

variable "app_secrets" {
  type      = map(string)    # name => secret value
  sensitive = true
}

resource "azurerm_key_vault_secret" "this" {
  # keys (secret names) are not secret; values stay sensitive
  for_each     = toset(nonsensitive(keys(var.app_secrets)))
  name         = each.key
  value        = var.app_secrets[each.key]
  key_vault_id = azurerm_key_vault.kv.id
}

resource "azuread_user" "this" {
  for_each            = { for u in var.users : u.upn => u }
  user_principal_name = each.key
  display_name        = each.value.display_name
}

Common mistakes

  • Using nonsensitive on the whole map, exposing secret values.
  • Keying by list index, causing churn when lists change.
  • Using secret values such as tokens as keys.
  • Building keys from attributes unknown until apply.

How to answer in the interview

"for_each only accepts a map or a set of strings, because each instance needs a string key for its address. So a list or set of objects fails, and I convert it with a for expression keyed by a unique attribute, like name. The sensitive error happens when the collection is marked sensitive, since keys show up in addresses and logs. I restructure the input so keys are non-secret names and secrets are only in the values, or if the keys genuinely aren't secret, wrap them with nonsensitive. Secrets should never become part of resource addresses."

Likely follow-up questions

  • Why would secret keys leak even with sensitive outputs? Addresses appear in plans, logs, state and run UIs unredacted.
  • Can values be sensitive? Yes, values remain redacted when keys are not.
  • What about unknown keys? Keys must be known at plan time; derive them from inputs.
