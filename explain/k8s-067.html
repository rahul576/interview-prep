Design a multi-region, highly available deployment of a critical service on Kubernetes.

Kubernetes · design · levels lead

In one line

Run at least two multi-zone clusters in different regions behind a health-checked global load balancer, deploy identical versions via GitOps one region at a time, make an explicit data replication and consistency decision (active-passive or active-active), keep capacity headroom to absorb a lost region and prove it with failover drills.

Detailed explanation

Start from requirements: availability target, RTO and RPO, latency for users in different geographies, and data residency. Inside one region, a cluster spread across three availability zones with topologySpreadConstraints, PodDisruptionBudgets and zone-redundant storage already survives node and zone failures. A region-wide outage, a bad cloud control plane change or a cluster-level mistake needs a second cluster in another region.

Traffic: a global entry point (Azure Front Door, AWS Route 53 with health checks or Global Accelerator, a Google global external load balancer, or Cloudflare) routes users to the nearest healthy region and removes a region when its health checks fail. Health checks should test a meaningful endpoint, not just "pod alive". DNS-based failover is affected by TTLs and client caching.

Delivery: GitOps (Argo CD ApplicationSets or Flux) deploys the same manifests to all clusters; rollouts are progressive per region, so a bad release hits one region first. Clusters are built from the same IaC to avoid drift.

Data is the hard part and dictates the topology. Active-passive: one writer region with asynchronous replicas in the other, simple and consistent, but failover loses up to the replication lag (RPO above zero) and needs a promotion runbook. Active-active: both regions serve writes, requiring a globally distributed database (Spanner, Cosmos DB, CockroachDB, DynamoDB global tables) or partitioning users by home region, and conflict or consistency trade-offs. Caches, queues and object storage need their own replication.

Capacity: each region must be able to take the other's traffic, either by running with headroom (around 50 percent utilisation in two-region active-active) or by autoscaling fast enough with reserved quota.

How it works

  1. Two or more regional clusters, each across three zones, built from IaC.
  2. Global load balancer with health checks routing to healthy regions.
  3. GitOps deploys identical versions, region by region.
  4. Database replication matching the RPO; promotion runbook or multi-writer DB.
  5. Secrets, certificates and config replicated to both regions.
  6. Headroom or fast autoscaling for full failover load.
  7. Scheduled failover drills and game days.

Example

apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata: { name: orders }
spec:
  generators:
    - list:
        elements:
          - { cluster: prod-weu, url: https://weu.k8s.example.com }
          - { cluster: prod-neu, url: https://neu.k8s.example.com }
  template:
    metadata: { name: "orders-{{cluster}}" }
    spec:
      project: prod
      source: { repoURL: https://git.example.com/apps.git, path: orders/overlays/prod, targetRevision: main }
      destination: { server: "{{url}}", namespace: orders }
      syncPolicy: { automated: { prune: true, selfHeal: true } }

Common mistakes

  • Two regions sharing one database in a single region.
  • Never testing failover, so the runbook fails on the day.
  • No capacity in the surviving region.
  • Deploying to all regions simultaneously.

How to answer in the interview

"I'd run at least two clusters in different regions, each spread over three zones with topology spread and PDBs. A global load balancer with real health checks routes users to the nearest healthy region and drops a failed one automatically. GitOps deploys the same versions everywhere, one region at a time. The hard part is data: either a single writer region with replicas for active-passive, accepting some RPO, or a globally distributed database for active-active. Each region needs headroom for the other's traffic, and we run regular failover drills to prove it."

Likely follow-up questions

  • What if strong consistency is required across regions? Use a consensus-based global database and accept higher write latency, or a single writer region with synchronous replication and lower availability.
  • How do you avoid split-brain on failover? Fence the old primary and use a single, authoritative promotion decision.
  • Multi-cluster service discovery? Global LB at the edge; for internal calls, mesh multi-cluster or MCS API.
