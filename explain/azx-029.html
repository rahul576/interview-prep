What are Durable Functions, and which problems do they solve?

Azure · concept · levels mid, senior

In one line

Durable Functions lets you write stateful, long-running workflows in code: an orchestrator calls activities, its progress is checkpointed to a storage backend, and it is replayed from event history, so orchestrator code must be deterministic; it implements chaining, fan-out/fan-in, async HTTP, monitors and human interaction.

Detailed explanation

Plain functions are stateless and short. Real processes, like order fulfilment or document processing, involve several steps, parallel work, waiting for people and retries over hours or days. Building that by hand needs queues, state tables and timers. Durable Functions (built on the Durable Task Framework) gives you that as code.

Function types: orchestrator functions describe the workflow, activity functions do the actual work (I/O, calculations), entity functions hold small pieces of durable state, and client functions start and query orchestrations.

Patterns:

  • Function chaining: A then B then C, with outputs passed along.
  • Fan-out/fan-in: start many activities in parallel, await Task.WhenAll, aggregate.
  • Async HTTP APIs: the client gets 202 with status URLs while work continues.
  • Monitor: a loop with durable timers polling until a condition holds.
  • Human interaction: wait for an external event (approval) with a timeout via a durable timer.

Replay: when an activity completes, the orchestrator is unloaded; later it is re-run from the start, and completed calls return their recorded results from history instead of executing again. That is why orchestrators must be deterministic: use context.CurrentUtcDateTime instead of DateTime.Now, context.NewGuid() instead of Guid.NewGuid(), no direct I/O, random numbers or thread sleeps; put those in activities. Long-running loops use ContinueAsNew to keep history small.

Backends store history and queues: Azure Storage (default), MSSQL, and the managed Durable Task Scheduler, which offers higher throughput and a monitoring dashboard. Version orchestrations carefully, because in-flight instances replay against new code.

How it works

  1. Client function starts an orchestration instance with an ID.
  2. Orchestrator schedules activities; framework records events.
  3. Activities run on any worker; results are appended to history.
  4. Orchestrator replays, consuming results, and continues.
  5. Timers and external events resume it later.
  6. Final output stored; status queryable via HTTP API.

Example

[Function(nameof(ProcessOrder))]
public static async Task<string> ProcessOrder([OrchestrationTrigger] TaskOrchestrationContext ctx)
{
    var order = ctx.GetInput<Order>();
    await ctx.CallActivityAsync("ReserveStock", order);
    var tasks = order.Lines.Select(l => ctx.CallActivityAsync<decimal>("PriceLine", l));
    var total = (await Task.WhenAll(tasks)).Sum();               // fan-out/fan-in
    using var cts = new CancellationTokenSource();
    var approval = ctx.WaitForExternalEvent<bool>("Approved");
    var timeout = ctx.CreateTimer(ctx.CurrentUtcDateTime.AddHours(24), cts.Token);
    if (await Task.WhenAny(approval, timeout) == approval) { cts.Cancel(); return "approved"; }
    return "expired";
}

Common mistakes

  • Calling DateTime.Now, HTTP clients or databases inside the orchestrator.
  • Huge inputs/outputs bloating history.
  • Infinite loops without ContinueAsNew.
  • Deploying breaking orchestrator changes while instances are in flight.

How to answer in the interview

"Durable Functions is an extension for stateful workflows in code. An orchestrator calls activities and waits for them, while the framework checkpoints progress to a backend, so a workflow survives restarts and can run for days. It covers chaining, fan-out fan-in, async HTTP status APIs, monitors and human approval with timeouts using durable timers and external events. Because orchestrators are replayed from history to rebuild state, their code must be deterministic: no DateTime.Now, random values or I/O, only durable APIs. State lives in Azure Storage, SQL or the managed Durable Task Scheduler."

Likely follow-up questions

  • Why is DateTime.Now a bug? Each replay gets a different value, so decisions diverge from recorded history.
  • Durable Functions vs Logic Apps? Code-first for developers vs low-code designer with connectors.
  • Versioning? Side-by-side deployment, new orchestrator names, or waiting for instances to drain.
