One worker node in your cluster becomes unresponsive and must be replaced. How do you replace it without affecting application availability?

Kubernetes · scenario · levels entry, mid, senior

In one line

Replace a node safely by having replicas spread with PDBs beforehand, then cordon and drain, handle an unreachable node carefully (force-delete StatefulSet pods only when it is truly dead), delete the node object, let the node group or autoscaler provision a replacement, and verify.

Detailed explanation

Availability during a node replacement is decided before the node fails. Every important workload needs several replicas spread across nodes and zones using topology spread constraints or pod anti-affinity, and a PodDisruptionBudget so voluntary evictions never take too many replicas at once. If a service runs a single replica, no procedure will keep it up.

If the node still responds, the flow is simple. Cordon it so nothing new lands there (drain does this too), then drain with --ignore-daemonsets --delete-emptydir-data. Pods are evicted gracefully, honouring PDBs and termination grace periods, and their controllers recreate them on healthy nodes.

If the node is unresponsive, the kubelet cannot confirm anything. The node controller marks it NotReady/Unknown, applies node.kubernetes.io/unreachable taints, and after the default toleration of about five minutes pods are marked for deletion. Deployment pods are recreated elsewhere. StatefulSet pods are not, because the system cannot be sure the old copy has stopped, and two pods with the same identity could corrupt data. Only after confirming the machine is powered off or terminated do you force-delete them (or apply the out-of-service taint, which lets volumes detach and pods move).

Then delete the node object and let the managed node group, cluster autoscaler or Karpenter create a replacement rather than repairing by hand. Verify the new node is Ready and workloads are healthy.

How it works

  1. Confirm replicas, spread and PDBs are in place.
  2. kubectl cordon the node.
  3. kubectl drain to evict pods gracefully.
  4. If unreachable: wait for eviction; force-delete StatefulSet pods only after confirming the node is dead.
  5. kubectl delete node; terminate the instance; let automation replace it.
  6. Check the new node is Ready and pods are Running and Ready.

Example

kubectl cordon worker-3
kubectl drain worker-3 --ignore-daemonsets --delete-emptydir-data --timeout=10m
# node unreachable and confirmed powered off:
kubectl taint node worker-3 node.kubernetes.io/out-of-service=nodeshutdown:NoExecute
kubectl -n data delete pod db-1 --grace-period=0 --force
kubectl delete node worker-3
kubectl get nodes; kubectl get pods -A -o wide | grep -v Running

Common mistakes

  • Force-deleting StatefulSet pods while the old node might still be running.
  • Repairing nodes manually instead of replacing them through the node group.
  • Running critical services with one replica and expecting zero downtime.
  • Uncordoning a node that is being retired.

How to answer in the interview

"Availability depends on preparation: several replicas spread across nodes with topology spread or anti-affinity, and PodDisruptionBudgets. Then I cordon the node and drain it with ignore-daemonsets and delete-emptydir-data, which evicts pods gracefully, respecting PDBs, and controllers recreate them elsewhere. If the node is completely unresponsive, the control plane marks it NotReady and evicts pods after a timeout; Deployments recover, but StatefulSet pods are not recreated, so I force-delete them only after confirming the node is really off. Then I delete the node object, let the node group or Karpenter create a replacement, and verify it is Ready."

Likely follow-up questions

  • What if a PDB allows zero disruptions during the drain? Drain retries indefinitely; fix the PDB or replica count with the owner.
  • Why not recreate StatefulSet pods automatically? It could create two pods with the same identity writing to the same volume.
  • How long until pods move from a dead node? About five minutes by default, set by the unreachable toleration.
