A CronJob that sends invoices ran twice one night, and another night it did not run at all. How do you investigate and make it safe?

Kubernetes · scenario · levels mid, senior

In one line

A CronJob creates about one Job per schedule, so occasionally two or none; extra runs also come from Job retries (backoffLimit) and missed runs from controller downtime beyond startingDeadlineSeconds. Use concurrencyPolicy: Forbid, sensible deadlines and alerts, and above all make the job idempotent.

Detailed explanation

The Kubernetes documentation states that a CronJob creates a Job approximately once per scheduled time, and that it may sometimes create two Jobs or none; jobs must therefore be idempotent. The controller lives in kube-controller-manager; controller restarts, leader-election changes, clock problems or control-plane downtime can produce edge cases.

Two runs usually have one of these explanations. The Job controller retried: the pod failed or its node died halfway, so backoffLimit started a new pod that ran the whole job again, possibly after half the invoices were already sent. With concurrencyPolicy: Allow (default), a slow run overlapped the next scheduled run. Or someone triggered a manual run with kubectl create job --from=cronjob/....

No run: if the controller was down or the previous run was still active with Forbid, and the time since the schedule exceeded startingDeadlineSeconds, the run is skipped. If more than 100 schedules were missed without a deadline set, the controller stops scheduling and logs an error. Also check the timeZone field; schedules default to the controller's time zone, and DST changes can skip or repeat an hour.

Investigation: list Jobs with their creation timestamps, read CronJob events, controller-manager logs or managed cluster logs for that window, and the application's own logs.

How it works

  1. List Jobs and pods owned by the CronJob and compare timestamps.
  2. Check pod failures and Job retries for the double run.
  3. Check control-plane availability for the missed night.
  4. Set concurrencyPolicy: Forbid, startingDeadlineSeconds, timeZone.
  5. Make the work idempotent with a run record and per-invoice state.
  6. Alert on missing successful runs.

Example

apiVersion: batch/v1
kind: CronJob
metadata: { name: send-invoices }
spec:
  schedule: "30 2 * * *"
  timeZone: Europe/London
  concurrencyPolicy: Forbid
  startingDeadlineSeconds: 3600
  jobTemplate:
    spec:
      backoffLimit: 2
      template:
        spec:
          restartPolicy: Never
          containers:
            - name: invoices
              image: registry.example.com/billing:4.3
              args: ["send-invoices", "--run-date=$(date +%F)"]
INSERT INTO invoice_runs (run_date, status) VALUES ('2026-11-20', 'started')
ON CONFLICT (run_date) DO NOTHING;          -- second run detects existing record
UPDATE invoices SET sent_at = now() WHERE id = $1 AND sent_at IS NULL;  -- send only if not sent

Common mistakes

  • Assuming exactly-once scheduling.
  • Non-idempotent jobs with retries enabled.
  • No alert when a run is missing.
  • Ignoring time zones and DST.

How to answer in the interview

"The docs say a CronJob creates about one job per schedule, so it can occasionally create two or none, for example around controller restarts or control-plane downtime. A second run can also be a Job retry after the pod or node failed halfway. A missed run happens if the controller was unavailable longer than startingDeadlineSeconds. I'd check job history, events and control-plane logs. To make it safe I'd use concurrencyPolicy Forbid, a sensible deadline, a time zone and alerts on missing runs, and most importantly make the job idempotent by recording each run and each sent invoice so repeated work is skipped."

Likely follow-up questions

  • Would a workflow engine be better? For multi-step, long-running or exactly-once-style business processes, yes: Temporal or Argo Workflows give durable state, retries per step and visibility.
  • How do you alert on missed runs? Alert when the last successful completion time is older than the expected interval.
  • What does Replace do? Cancels the running Job and starts the new one.
