How do you collect metrics from containers and the Docker host?

Docker · concept · levels senior

In one line

Container metrics come from cgroups: cAdvisor (built into the kubelet in Kubernetes) exposes per-container CPU, memory (including working set), network and filesystem metrics, node_exporter adds host metrics, the Docker daemon exposes engine metrics, Prometheus scrapes them with Grafana dashboards and alerts, and applications add their own metrics via Micrometer or OpenTelemetry.

Detailed explanation

The Linux kernel accounts resource usage per cgroup, and every container has its own cgroup. cAdvisor reads these counters and publishes them in Prometheus format: container_cpu_usage_seconds_total, container_cpu_cfs_throttled_periods_total (CPU throttling against limits), container_memory_working_set_bytes, container_memory_rss, network bytes and errors, and filesystem usage. On a plain Docker host you run cAdvisor as a container; in Kubernetes it is embedded in the kubelet and scraped through /metrics/cadvisor.

Containers don't tell you everything about the host, so node_exporter adds disk space and I/O, load, memory and pressure stall information (PSI), network and filesystem metrics. The Docker daemon can expose its own engine metrics via the metrics-addr setting in daemon.json (container actions, builder and daemon health). In Kubernetes, kube-state-metrics adds object state such as restarts, desired versus available replicas and OOMKilled reasons.

Prometheus scrapes all of these; Grafana builds dashboards; Alertmanager routes alerts such as memory working set above 90% of the limit, high CPU throttling, restart loops or a disk filling up.

Infrastructure metrics only show symptoms. Application metrics (request rate, errors, latency per endpoint, queue depth, pool saturation) come from the app itself via Micrometer in Spring Boot or the OpenTelemetry SDKs. Use consistent labels such as service, version and env so you can correlate a latency jump with a new version.

How it works

  1. Kernel cgroups record CPU, memory, I/O per container.
  2. cAdvisor/kubelet export them; node_exporter exports host data.
  3. Prometheus scrapes targets every 15-30 s and stores time series.
  4. Grafana dashboards: per container, per service, per node.
  5. Alert rules fire on SLO symptoms and saturation; apps add RED/USE metrics.

Example

services:
  cadvisor:
    image: gcr.io/cadvisor/cadvisor:v0.49.1
    volumes: [ "/:/rootfs:ro", "/var/run:/var/run:ro", "/sys:/sys:ro", "/var/lib/docker/:/var/lib/docker:ro" ]
    ports: [ "8080:8080" ]
  node-exporter:
    image: prom/node-exporter
    pid: host
    volumes: [ "/:/host:ro,rslave" ]
    command: [ "--path.rootfs=/host" ]
container_memory_working_set_bytes{container!=""}
  / on(namespace,pod,container) kube_pod_container_resource_limits{resource="memory"} > 0.9

Common mistakes

  • Alerting on container_memory_usage_bytes, which includes reclaimable page cache and looks scary.
  • Ignoring CPU throttling, a common hidden cause of latency.
  • High-cardinality labels (user IDs, full URLs) that overload Prometheus.
  • Only infrastructure metrics, no application-level RED metrics.

How to answer in the interview

"Container metrics come from cgroups. cAdvisor, which is built into the kubelet on Kubernetes, exposes per-container CPU, throttling, memory including working set, network and filesystem metrics in Prometheus format. node_exporter adds host metrics like disk space and memory pressure, and the Docker daemon can expose engine metrics with metrics-addr. Prometheus scrapes them, Grafana shows dashboards, and Alertmanager fires on things like memory near the limit, throttling, restart loops or a filling disk. But infrastructure metrics aren't enough, so services expose request rate, errors and latency through Micrometer or OpenTelemetry, with consistent labels like service and version."

Likely follow-up questions

  • Which memory metric predicts an OOM kill? container_memory_working_set_bytes against the limit; that is what the kubelet uses for eviction decisions.
  • How do you spot CPU throttling? Ratio of container_cpu_cfs_throttled_periods_total to container_cpu_cfs_periods_total.
  • Pull vs push metrics? Prometheus pulls; short-lived jobs can push via Pushgateway or OTLP to a collector.
