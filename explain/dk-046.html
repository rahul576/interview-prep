What are best practices for a Node.js or Python Dockerfile?

Docker · concept · levels mid

In one line

Copy dependency manifests and lock files first for layer caching, install reproducibly with npm ci or pip install --no-cache-dir, ship production dependencies only via multi-stage builds, use a slim base and non-root user, set NODE_ENV=production or PYTHONUNBUFFERED=1, and run in exec form so signals work.

Detailed explanation

The single most important optimisation for interpreted languages is layer ordering. Dependencies change rarely while source code changes constantly, so copy only package.json and package-lock.json (or requirements.txt, poetry.lock, uv.lock) first, install, and only then COPY the source. A code change reuses the cached dependency layer and a rebuild takes seconds.

Installs must be reproducible from the lock file. For Node, npm ci installs exactly what the lock file says and fails if it is out of sync; npm ci --omit=dev skips dev dependencies. For Python, install pinned requirements with pip install --no-cache-dir (no pip cache in the layer), or use Poetry/uv to export locked requirements. Packages with native extensions need a compiler, so use a multi-stage build: build wheels or node_modules in a full image and copy them into a slim runtime. A .dockerignore must exclude local node_modules, .venv, __pycache__ and .git; laptop-built native modules may be for another OS or CPU and break the container.

Runtime settings matter. NODE_ENV=production makes many frameworks enable production optimisations. PYTHONUNBUFFERED=1 sends logs to stdout immediately instead of buffering, and PYTHONDONTWRITEBYTECODE=1 avoids writing .pyc files. Run as a non-root user (the Node image provides node). Start the process in exec form, directly (node server.js, gunicorn) rather than via npm start, which adds an extra process that may not forward signals, or use --init/tini.

How it works

  1. Copy manifest and lock file.
  2. Install dependencies in a cached layer (optionally with a BuildKit cache mount).
  3. Copy source and build assets.
  4. Copy runtime pieces into a slim final stage.
  5. Set environment, user and exec-form CMD.

Example

FROM node:22-slim AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev

FROM node:22-slim
ENV NODE_ENV=production
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY --chown=node:node . .
USER node
CMD ["node", "server.js"]
FROM python:3.12-slim
ENV PYTHONUNBUFFERED=1 PYTHONDONTWRITEBYTECODE=1
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
RUN useradd --system --uid 10001 app
USER 10001
CMD ["gunicorn", "-b", "0.0.0.0:8000", "app:app"]

Common mistakes

  • COPY . . before installing dependencies, invalidating the cache on each change.
  • npm install instead of npm ci, giving non-reproducible builds.
  • Copying local node_modules into the image.
  • CMD npm start, leaving signals unhandled.

How to answer in the interview

"For both I copy only the manifest and lock file first, install dependencies, then copy the source, so code changes reuse the cached dependency layer. Installs are reproducible from the lock file, npm ci for Node and pip install --no-cache-dir for Python, with production dependencies only, often in a multi-stage build. I use a slim base and a non-root user. Node gets NODE_ENV=production, Python PYTHONUNBUFFERED=1 so logs appear immediately, and I run the process directly in exec form or with an init so signals work, not through npm start."

Likely follow-up questions

  • Why never copy local node_modules? They may be built for another OS or architecture and break reproducibility.
  • Why avoid npm start as CMD? npm adds a process that may not forward SIGTERM.
  • How do you handle native extensions? Build them in a full stage, copy results into slim.
