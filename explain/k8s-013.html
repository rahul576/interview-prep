Compare ValidatingAdmissionPolicy, admission webhooks, Kyverno and OPA Gatekeeper for enforcing cluster policies.

Kubernetes · concept · levels mid, senior, lead

In one line

ValidatingAdmissionPolicy runs CEL rules inside the API server (GA since 1.30), simple and with no extra service; admission webhooks call an external service and can validate and mutate; Kyverno (YAML policies, mutation, generation) and OPA Gatekeeper (Rego) are webhook-based engines, carrying availability and failurePolicy risks.

Detailed explanation

Admission control is the last gate before an object is stored: after authentication and RBAC, admission can reject or modify the request. Options:

  • ValidatingAdmissionPolicy (VAP): you write a policy with CEL expressions, for example object.spec.template.spec.containers.all(c, has(c.resources.limits)), and a binding that selects which resources and namespaces it applies to and whether to Deny, Warn or Audit. It runs in-process, so there's no network hop, no extra deployment to keep alive, and it is fast. Parameters can come from a ConfigMap or CRD. Limits: validation only, and CEL is less expressive for complex lookups. A MutatingAdmissionPolicy counterpart has been added more recently and is still maturing.
  • Admission webhooks: the API server calls your HTTPS endpoint with an AdmissionReview. Mutating webhooks run first and can patch the object (inject sidecars, set defaults), then validating webhooks run. Fully flexible, but you operate a highly available service.
  • Kyverno: a webhook-based policy engine where policies are Kubernetes YAML with pattern matching; supports validate, mutate, generate (for example create default NetworkPolicies in new namespaces), image signature verification and background reports. Approachable for platform teams; recent versions also support CEL-based policies.
  • OPA Gatekeeper: uses Rego via ConstraintTemplates and Constraints; very expressive and shared with OPA policies elsewhere (Terraform, APIs), with audit of existing resources and some mutation support; steeper learning curve.

The webhook trade-off is availability: with failurePolicy: Fail, if the webhook is down, matching requests are rejected and deployments, even of the webhook itself, can stall. With Ignore, policy is silently skipped. Mitigate with multiple replicas, PDBs, short timeoutSeconds, and namespaceSelector excluding kube-system and the engine's own namespace.

How it works

  1. Request passes authentication and authorisation.
  2. Mutating admission (webhooks, mutating policies) modifies the object.
  3. Schema validation.
  4. Validating admission: VAP CEL rules and validating webhooks.
  5. Any denial returns an error; otherwise the object is persisted.

Example

apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata: { name: require-limits }
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
    - { apiGroups: [apps], apiVersions: [v1], operations: [CREATE, UPDATE], resources: [deployments] }
  validations:
  - expression: "object.spec.template.spec.containers.all(c, has(c.resources.limits) && has(c.resources.limits.memory))"
    message: "every container needs a memory limit"
---
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata: { name: require-limits }
spec:
  policyName: require-limits
  validationActions: [Deny]
  matchResources:
    namespaceSelector: { matchLabels: { env: prod } }

Common mistakes

  • Webhooks with failurePolicy: Fail and a single replica.
  • Policies that also match kube-system, blocking recovery.
  • Enforcing new policies without an audit/warn phase.
  • Using a webhook for rules that CEL could express in-process.

How to answer in the interview

"ValidatingAdmissionPolicy is built into the API server since 1.30: rules in CEL, bound to resources and namespaces, running in-process with nothing extra to operate, so it's my first choice for simple validation. Webhooks call an external service and can validate and mutate; Kyverno and Gatekeeper build on them. Kyverno uses YAML policies and can mutate and generate resources, which platform teams find easy. Gatekeeper uses Rego, more powerful but harder. The main webhook risk is availability: with failurePolicy Fail an outage blocks deployments, so I run replicas, short timeouts and exclude system namespaces."

Likely follow-up questions

  • First policies for a new prod cluster? Pod Security restricted, resource requests and limits, trusted registries, no latest tags, required owner labels.
  • How do you test policies? Kyverno CLI or gator tests in CI, then audit mode in the cluster.
  • Why order matters? Mutation runs before validation, so validators see the mutated object.
