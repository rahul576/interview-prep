How do you sandbox agents that execute code?

AI Agents & AIOps · concept · levels senior, lead

In one line

Run agent-generated code in an isolated, ephemeral sandbox per task, preferably with microVM or user-space-kernel isolation (Firecracker, gVisor) rather than plain containers, with no secrets inside, restricted network egress, CPU, memory and time limits, and explicit copying of outputs.

Detailed explanation

Code written by a model can be buggy, and after a prompt injection it can be deliberately malicious: reading credentials, scanning the internal network, mining cryptocurrency or exfiltrating data. It must never run on a host that has access to anything valuable, such as the agent server itself.

Isolation level is the first decision. Standard containers share the host kernel; a kernel vulnerability or misconfiguration (privileged mode, mounted Docker socket, host paths) can lead to escape. For untrusted code, stronger boundaries are preferred: microVMs such as Firecracker or Kata Containers give each sandbox its own kernel, and gVisor intercepts system calls in a user-space kernel. Managed sandbox services from cloud and AI providers package this.

Contents: the sandbox holds no secrets or production credentials; required files are copied in explicitly. Network: egress is blocked by default or limited to an allowlist (for example an internal package mirror), preventing exfiltration and malware downloads; no access to cloud metadata endpoints. Resources: limits on CPU, memory, disk, processes and wall-clock time stop runaway loops and fork bombs. Lifecycle: sandboxes are ephemeral, created per task and destroyed afterwards; outputs are copied out explicitly and scanned if they go anywhere important. Activity, commands and network attempts, is logged for investigation.

How it works

  1. Agent requests code execution with code and input files.
  2. Orchestrator creates a fresh sandbox from a minimal image.
  3. Inputs copied in; network policy and resource limits applied.
  4. Code runs as non-root with a timeout.
  5. Outputs collected; sandbox destroyed.
  6. Logs and outputs checked before further use.

Example

# Kubernetes: sandbox pods on gVisor with no egress
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata: { name: gvisor }
handler: runsc
---
apiVersion: v1
kind: Pod
metadata: { name: sandbox-7f3a, namespace: agent-sandboxes, labels: { role: sandbox } }
spec:
  runtimeClassName: gvisor
  automountServiceAccountToken: false
  activeDeadlineSeconds: 300
  securityContext: { runAsNonRoot: true, runAsUser: 10001 }
  containers:
    - name: run
      image: registry.internal/python-sandbox:3.12
      resources: { limits: { cpu: "1", memory: 1Gi, ephemeral-storage: 2Gi } }
      securityContext: { allowPrivilegeEscalation: false, readOnlyRootFilesystem: true }
# plus a NetworkPolicy denying all egress for role=sandbox

Common mistakes

  • Running generated code inside the agent's own container.
  • Mounting the Docker socket or using privileged containers.
  • Leaving cloud metadata endpoints reachable.
  • Reusing sandboxes across tasks or users.

How to answer in the interview

"Model-written code can be buggy or, after prompt injection, malicious, so it never runs where anything valuable is reachable. Each task gets its own sandbox, and for untrusted code I prefer microVMs like Firecracker or gVisor over plain containers, which share the host kernel. The sandbox has no secrets, network egress is blocked or allowlisted, and CPU, memory, disk and time are limited. Sandboxes are ephemeral, destroyed after the task, with outputs copied out explicitly and checked, and everything inside is logged."

Likely follow-up questions

  • Why is Docker not enough? Shared kernel; escapes and misconfigurations expose the host.
  • Needs package installs? Use an internal mirror on the egress allowlist.
  • Cold-start cost? Pre-warmed pools of microVMs.
