What are pipeline decorators in Azure DevOps, and when would you use them?

Azure DevOps & Pipelines · concept · levels senior, lead

In one line

Pipeline decorators are delivered by an organisation-installed extension and inject steps at the start or end of every job (optionally conditional), which teams cannot remove from their YAML; use them sparingly for mandatory controls like credential scanning or compliance telemetry, preferring extends templates with required template checks for most governance.

Detailed explanation

A decorator is a contribution in an Azure DevOps extension of type ms.azure-pipelines.pipeline-decorator, targeting ms.azure-pipelines-agent-job.pre-job-tasks or post-job-tasks (there are also targets around specific tasks, such as before or after checkout). The extension contains a YAML file with steps, and template expressions can make the injection conditional: only on Linux agents, only when a certain task is present, only in specific projects or repositories.

Once the extension is installed in the organisation, every job of every pipeline (YAML and classic) gets those steps. Teams see them in their logs but can't remove them in YAML. That makes decorators a strong enforcement tool for organisation-wide requirements:

  • Running a credential scanner or malware scan on the workspace.
  • Collecting SBOM or compliance evidence.
  • Reporting telemetry on which tools, tasks or images are used.
  • Enforcing a policy check such as "fail if job uses a forbidden task".

Microsoft has used decorators internally for organisation-wide security scanning.

Why sparingly: decorators run in every job, so they add time and cost everywhere; a bug in a decorator breaks all pipelines in the organisation at once; they're less visible and harder to test (developing them means publishing private extensions); and their logic is hidden from the people whose pipelines they change.

Extends templates with required template checks are usually better: they're versioned in Git, visible in the pipeline definition, testable, can be rolled out per project, and checks enforce them only where it matters (production resources). Decorators fit controls that truly must apply to every job regardless of team cooperation.

How it works

  1. Create an extension with a pipeline-decorator contribution and YAML steps.
  2. Add conditions with template expressions.
  3. Publish privately and share with the organisation.
  4. Install; steps are injected into matching jobs.
  5. Monitor duration impact and failures; version carefully.

Example

{
  "contributions": [{
    "id": "credscan-decorator",
    "type": "ms.azure-pipelines.pipeline-decorator",
    "targets": [ "ms.azure-pipelines-agent-job.post-job-tasks" ],
    "properties": { "template": "credscan.yml" }
  }]
}
# credscan.yml
steps:
- ${{ if eq(variables['Agent.OS'], 'Linux') }}:
  - script: ./tools/credscan --path $(Build.SourcesDirectory) --fail-on-findings
    displayName: '(Injected) Credential scan'

Common mistakes

  • Shipping an untested decorator update that breaks every build.
  • Heavy scans in every job, including trivial ones.
  • Using decorators for things that should be in templates.
  • No communication to teams about injected steps.

How to answer in the interview

"Pipeline decorators come from an extension installed at the organisation level and inject steps at the start or end of every job, optionally with conditions such as only Linux jobs. Teams can't remove them in their YAML, so they're good for mandatory controls like credential scanning, SBOM or compliance telemetry. I use them sparingly, because they add time to every pipeline and a bug breaks all builds at once. For most governance, I prefer extends templates with required template checks, which are versioned, visible and enforced on production resources."

Likely follow-up questions

  • Why prefer extends templates? Versioned in Git, transparent, testable, enforced where needed.
  • Can decorators target specific tasks? Yes, pre/post targets for specific tasks or checkout.
  • Testing decorators? Publish privately to a test organisation first.
