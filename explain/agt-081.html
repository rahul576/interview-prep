How do you deploy and scale agents on Kubernetes?

AI Agents & AIOps · design · levels mid, senior

In one line

Split into an API service and worker pools, decouple them with queues, keep all state in external stores, scale workers on queue depth with KEDA, run code execution in separate isolated sandbox pods, and handle graceful shutdown with checkpointing.

Detailed explanation

Agent workloads differ from typical web requests: a run may take seconds or hours, spends most time waiting on model and tool calls (I/O-bound), and must survive pod restarts. The architecture reflects that.

An API service accepts requests, authenticates users and streams responses for interactive use (SSE or WebSockets). Longer runs are placed on a queue, such as Kafka, RabbitMQ, SQS or Azure Service Bus, which buffers bursts and enables retries. Worker pools consume runs and execute the agent loop.

State lives outside pods: conversation history, checkpoints, memory and artefacts go to PostgreSQL, Redis or object storage. Any worker can then resume any run, pods can be replaced freely, and deployments do not lose work. Scaling uses KEDA on queue depth or active runs, because CPU is a poor signal for workers mostly waiting on network calls; concurrency per worker is often high with async code.

Code execution runs in separate sandbox pods or microVMs with strict NetworkPolicies, gVisor or Kata runtime classes and no service account tokens, never inside the worker. Workers handle SIGTERM gracefully: stop taking new runs, checkpoint the current step and release the message so another worker resumes; set terminationGracePeriodSeconds accordingly. Model and tool calls go through gateways with rate limits, timeouts, retries and per-tenant quotas, since provider rate limits are often the real bottleneck.

How it works

  1. Client calls API; short runs stream directly, long runs are enqueued.
  2. Worker picks a run, loads state, executes steps.
  3. Each step checkpoints to the state store.
  4. Code execution requests go to sandbox pods.
  5. KEDA scales workers by queue length.
  6. On SIGTERM, worker checkpoints and requeues.

Example

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata: { name: agent-workers }
spec:
  scaleTargetRef: { name: agent-worker }
  minReplicaCount: 2
  maxReplicaCount: 60
  triggers:
    - type: rabbitmq
      metadata:
        queueName: agent-runs
        mode: QueueLength
        value: "10"          # target runs per worker
---
# worker Deployment excerpt
terminationGracePeriodSeconds: 120

Common mistakes

  • Keeping run state in pod memory.
  • Scaling workers on CPU.
  • Executing generated code inside worker pods.
  • Ignoring model provider rate limits when scaling out.

How to answer in the interview

"I split it into an API service that accepts requests and streams responses, and worker pools that execute runs, with a queue in between to buffer bursts and allow retries. All state, conversations, checkpoints and memory, lives in external stores like Postgres, Redis or object storage, so any worker can resume a run. Workers scale on queue depth with KEDA, since CPU is a poor signal for I/O-bound agents. Code execution goes to separate isolated sandbox pods. Workers checkpoint on SIGTERM, and model and tool calls pass through gateways with rate limits and timeouts."

Likely follow-up questions

  • Deploying with runs in flight? Graceful shutdown with checkpoints; version-pinned runs finish on old workers.
  • Streaming with workers? Workers publish events to Redis or a pub/sub that the API relays.
  • Multi-tenancy? Per-tenant queues or quotas and namespaces.
