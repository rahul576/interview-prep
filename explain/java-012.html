Explain how Java Streams work: intermediate versus terminal operations, and laziness.

Java 8+ Features · concept · levels mid

In one line

A stream is a lazy pipeline over a data source: intermediate operations (filter, map, sorted) return new streams and do nothing until a terminal operation (collect, reduce, forEach) triggers a single pass; a stream can be consumed only once.

Detailed explanation

A stream does not store data; it describes a computation over a source such as a collection, array, file or generator. Intermediate operations each return a new Stream and are lazy: calling filter just records a stage. When a terminal operation runs, the pipeline is executed, typically by pulling elements one at a time through all stages (loop fusion), so no intermediate collections are created.

Laziness enables short-circuiting: findFirst, anyMatch and limit stop as soon as the answer is known, which even makes infinite streams (Stream.iterate, Stream.generate) usable. Intermediate operations are either stateless (filter, map) or stateful (sorted, distinct), the latter needing to buffer elements.

After a terminal operation the stream is consumed; reusing it throws IllegalStateException. To process again, create a new stream from the source or use a Supplier<Stream<T>>.

Parallel streams (parallelStream() or .parallel()) split the source with a Spliterator and run on the shared ForkJoinPool common pool. They help for large, CPU-bound work on splittable sources, but hurt for small data, blocking I/O, ordered stateful operations or shared mutable state.

How it works

  1. Obtain a stream from a source (list.stream()).
  2. Chain intermediate operations; each wraps the previous stage.
  3. Call a terminal operation; the pipeline is evaluated.
  4. Elements flow one by one through the stages; short-circuit ops may stop early.
  5. The result is returned and the stream is closed for reuse.

Example

List<String> names = List.of("anna", "bob", "carla", "dev");
List<String> result = names.stream()
    .filter(n -> { System.out.println("filter " + n); return n.length() > 3; })
    .map(n ->    { System.out.println("map " + n);    return n.toUpperCase(); })
    .limit(1)
    .toList();                       // Java 16+
// prints: filter anna, map anna  -> stops after one element

Common mistakes

  • Expecting side effects in peek or map to run without a terminal operation.
  • Reusing a stream after a terminal operation.
  • Using parallel streams by default without measuring.
  • Mutating shared collections inside lambdas instead of using collectors.

How to answer in the interview

"A stream is a pipeline over a source; it doesn't store data. Intermediate operations like filter, map and sorted return a new stream and are lazy, so nothing happens until a terminal operation such as collect, reduce or count runs. Then elements flow through all stages in one pass, and short-circuiting operations like findFirst or limit can stop early, which also makes infinite streams usable. A stream can be consumed only once. Parallel streams use the common ForkJoinPool; they help large CPU-bound jobs but can hurt small data sets or blocking I/O, so I measure first."

Likely follow-up questions

  • What is the difference between map and flatMap? map is one-to-one; flatMap maps each element to a stream and flattens them.
  • What is toList() versus collect(Collectors.toList())? toList() (Java 16) returns an unmodifiable list.
  • Why is sorted stateful? It must see all elements before emitting the first one.
