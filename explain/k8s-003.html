What are init containers, and when do you use them?

Kubernetes · concept · levels entry, mid

In one line

Init containers run to completion, one by one, before app containers start; each must succeed, failures are retried according to the pod's restartPolicy, and they are used to wait for dependencies, run migrations, fetch config or prepare volumes, sharing results through volumes.

Detailed explanation

Some work must happen before the application can start, and doing it inside the app image complicates the image and its start-up code. Init containers, listed under spec.initContainers, separate that work. The kubelet runs them sequentially in the listed order; container 2 starts only after container 1 exits with code 0. Only when all have succeeded do the regular containers start. While they run, the pod shows Init:0/2; failures show Init:Error or Init:CrashLoopBackOff.

If an init container fails, the kubelet retries it per restartPolicy: with Always or OnFailure it restarts with backoff; with Never the whole pod fails. Because init containers can run again after a pod restart (for example node reboot), their work must be idempotent.

Typical uses:

  • Wait for a dependency, for example loop until the database port answers.
  • Schema migrations before the app starts (with care, see below).
  • Fetch config, certificates or models into a shared emptyDir.
  • Fix volume permissions or generate config files from templates.

They can use different images with tools (curl, migration binaries, git) that you don't want in the hardened app image, and they have their own resources and security context. Their resource requests affect scheduling: the effective request is the maximum of any init container and the sum of the app containers.

A related feature is the native sidecar: an init container with restartPolicy: Always keeps running alongside the app instead of completing.

How it works

  1. Pod scheduled; volumes mounted.
  2. Init container 1 runs to completion.
  3. Init container 2 runs to completion.
  4. App containers start, reading files the init containers wrote.
  5. On failure, retries per restartPolicy; pod stays in Init state.

Example

spec:
  volumes:
  - { name: config, emptyDir: {} }
  initContainers:
  - name: wait-for-db
    image: busybox:1.36
    command: ['sh', '-c', 'until nc -z postgres 5432; do echo waiting; sleep 2; done']
  - name: render-config
    image: registry.example.com/config-tool:2.1
    args: ['--out', '/config/app.yaml']
    volumeMounts: [ { name: config, mountPath: /config } ]
  containers:
  - name: app
    image: registry.example.com/orders:1.8.2
    volumeMounts: [ { name: config, mountPath: /etc/app } ]

Common mistakes

  • Endless "wait for X" loops that block every restart during an outage.
  • Running migrations in each of 20 replicas at once.
  • Non-idempotent init work that breaks on rerun.
  • Forgetting that init containers' resources affect scheduling.

How to answer in the interview

"Init containers are defined in initContainers and run to completion, sequentially, before the app containers start; each must succeed before the next begins, and failures are retried according to the pod's restart policy, with the pod showing Init status. I use them to wait for a dependency, fetch config or certificates, fix volume permissions, and sometimes run migrations, sharing results with the main container through an emptyDir. They can use a separate image, keeping tools out of the app image. I keep them short and idempotent, because they rerun on every pod restart."

Likely follow-up questions

  • Downside of migrations in init containers with many replicas? Concurrent runs and lock contention; prefer a single pre-deploy Job or a migration lock.
  • Are probes supported on init containers? Not on regular ones; native sidecars can have probes.
  • How do you see init container logs? kubectl logs pod -c <init-name>.
