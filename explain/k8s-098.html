How do you manage a fleet of many Kubernetes clusters consistently?

Kubernetes · design · levels senior, lead

In one line

Treat clusters as standardised, replaceable units: create them from IaC or Cluster API templates, deliver add-ons with GitOps targeted by cluster labels, centralise policy, identity and observability, and roll out upgrades in rings.

Detailed explanation

With five or fifty clusters, hand-configured differences (drift) become the main source of incidents. The goal is that any cluster can be recreated from code and that a new one becomes production-ready automatically.

Creation comes from Terraform or OpenTofu modules, or Cluster API templates, so each cluster gets the same network layout, node pools, OIDC/SSO integration, logging and baseline security. Variables differ (region, size), structure does not.

Platform add-ons such as ingress or Gateway API controllers, cert-manager, External Secrets, Kyverno or Gatekeeper, and monitoring agents are delivered by GitOps. In Argo CD, an ApplicationSet with the cluster generator creates one Application per registered cluster that matches labels like env=prod or region=eu; Flux does the same with Kustomizations per cluster directory. Register a new cluster with the right labels and it receives the whole stack.

Central services: the same policies everywhere, SSO-based access with RBAC groups, and metrics and logs shipped to one place with a cluster label, so dashboards and alerts cover the fleet. Upgrades of Kubernetes versions and add-ons go through rings: sandbox, then non-production, then production waves, with automated health checks and a pause between waves. Exceptions are expressed as labelled overlays in Git, never manual changes.

How it works

  1. Define a cluster blueprint in IaC or Cluster API.
  2. Provision the cluster and register it with GitOps, adding labels.
  3. ApplicationSet or Flux targets labels and installs add-ons.
  4. Policies, identity and telemetry are applied centrally.
  5. Version bumps flow ring by ring with automated checks.

Example

apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata: { name: platform-ingress }
spec:
  generators:
    - clusters:
        selector:
          matchLabels: { env: prod }
  template:
    metadata: { name: 'ingress-{{name}}' }
    spec:
      project: platform
      source:
        repoURL: https://git.example.com/platform/addons.git
        path: ingress/overlays/prod
        targetRevision: main
      destination: { server: '{{server}}', namespace: ingress }
      syncPolicy: { automated: { prune: true, selfHeal: true } }

Common mistakes

  • "Pet" clusters with manual kubectl changes nobody can reproduce.
  • Upgrading all clusters at once instead of in rings.
  • Per-cluster copies of manifests instead of shared bases with overlays.
  • No fleet-wide view, so problems appear one cluster at a time.

How to answer in the interview

"I treat clusters as standardised, replaceable units. They are created from infrastructure as code, Terraform modules or Cluster API templates, so each has the same baseline. Add-ons like ingress, cert-manager, policy engines and monitoring are deployed by GitOps, for example an Argo CD ApplicationSet with a cluster generator targeting labels like env=prod, so a new cluster gets everything automatically. Policy, SSO and observability are central. Upgrades roll out in rings, sandbox, non-production, then production waves with automated checks. That keeps drift low and makes recreating a cluster routine."

Likely follow-up questions

  • How do you handle a cluster that needs different configuration? A label-selected overlay in Git, documented and reviewed, not a manual change.
  • How many clusters is too many? When operational cost outweighs isolation benefits; namespaces and vClusters can reduce the count.
  • How do you track versions across the fleet? Inventory dashboards fed by GitOps and cluster metadata.
