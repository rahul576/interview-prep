What is the purpose of the @FunctionalInterface annotation?

Java 8+ Features · concept · levels entry

In one line

@FunctionalInterface tells the compiler an interface is meant to have exactly one abstract method; compilation fails if that is broken, it documents intent, and it is optional since any single-abstract-method interface works with lambdas.

Detailed explanation

The annotation is an informative marker in java.lang, retained at runtime, but its practical effect is a compile-time check. If the annotated interface has zero abstract methods, or more than one (after excluding default, static, private methods and redeclared public Object methods), the compiler reports an error such as "Invalid '@FunctionalInterface' annotation; MyInterface is not a functional interface".

Why does that matter? Imagine a shared library defines interface Validator { boolean validate(Order o); } and dozens of services pass lambdas to it. If someone adds String name();, the library itself still compiles, but every client's lambda breaks, possibly discovered only at the next release of another team. With @FunctionalInterface, the mistake fails immediately, at the source, where it's cheap to fix.

It also documents intent: readers know the interface is designed as a lambda target, and API evolution should preserve that, adding only default methods.

It is optional. The JVM and compiler treat any SAM interface as functional, which is how pre-Java-8 interfaces like Runnable and Comparator work with lambdas (they were annotated in Java 8 for clarity). Adding the annotation to your own functional interfaces is good practice.

A functional interface can extend another interface, as long as the result has a single abstract method; for example, interface StringMapper extends Function<String, String> {} is functional. It can't be applied to classes, enums or abstract classes.

How it works

  1. The compiler sees the annotation on an interface.
  2. It gathers abstract methods, including inherited ones.
  3. It excludes methods matching public Object methods.
  4. If the count isn't exactly one, it emits an error.

Example

@FunctionalInterface
public interface OrderValidator {
    boolean validate(Order order);

    default OrderValidator and(OrderValidator other) {
        return o -> validate(o) && other.validate(o);
    }
    static OrderValidator nonEmpty() { return o -> !o.items().isEmpty(); }

    // String name();   // uncommenting causes: "OrderValidator is not a functional interface"
}

@FunctionalInterface
interface Upper extends UnaryOperator<String> {}   // still one abstract method: apply

OrderValidator v = OrderValidator.nonEmpty().and(o -> o.total().signum() > 0);

Common mistakes

  • Saying lambdas require the annotation.
  • Thinking the annotation changes runtime behaviour.
  • Assuming you can't add default methods to an annotated interface.
  • Annotating classes or abstract classes.

How to answer in the interview

"It's an informative annotation that tells the compiler the interface is intended to be functional. If someone adds a second abstract method or removes the only one, compilation fails, which protects all the lambdas that already use it. It also documents intent for other developers. It's optional: any interface with a single abstract method works with lambdas without it, but I always add it to my own functional interfaces as good practice. Default and static methods are still allowed."

Likely follow-up questions

  • Can a functional interface extend another interface? Yes, if the total is still one abstract method.
  • Does it affect bytecode or runtime? Only as retained metadata; behaviour is unchanged.
  • Does equals count as an abstract method? No, it redeclares an Object method.
