How do you patch and manage fleets of EC2 instances with Systems Manager?

Cloud (AWS) · concept · levels mid

In one line

Instances with the SSM Agent and an instance role become managed nodes; Patch Manager applies patch baselines in maintenance windows by patch group, Run Command runs ad-hoc commands fleet-wide without SSH, State Manager and Automation runbooks enforce configuration and multi-step operations, and Inventory and Compliance report the fleet's state.

Detailed explanation

Registration: the SSM Agent comes preinstalled on Amazon Linux, recent Ubuntu and Windows AMIs. With an instance profile containing AmazonSSMManagedInstanceCore, or account-wide via Default Host Management Configuration, the instance registers as a managed node. Private subnets need a NAT gateway or interface endpoints for ssm, ssmmessages and ec2messages. On-premises servers join through hybrid activations.

Patch Manager uses patch baselines that define which classifications and severities are approved (for example Security and Critical), an auto-approval delay such as seven days after release, and explicit approve or reject lists. Instances are grouped by patch group tag or targeted through patch policies in Quick Setup, which can apply across an organisation. Operations are Scan (report only) or Install, run by the AWS-RunPatchBaseline document, typically within maintenance windows with concurrency and error thresholds so only a fraction of instances reboot at once.

Run Command executes SSM documents such as AWS-RunShellScript across instances selected by tags or resource groups, with rate control and output sent to S3 or CloudWatch Logs, all logged in CloudTrail. Session Manager provides interactive shells without SSH keys or open ports. State Manager associations keep configuration in a desired state, for instance ensuring the CloudWatch agent is installed. Automation runbooks perform multi-step workflows like building golden AMIs, restarting services or remediating Config findings.

Inventory collects installed software, patches, network config and files; Compliance shows patch and association compliance, aggregated across accounts with Resource Data Sync to S3 and Athena.

How it works

  1. Attach the SSM instance role and confirm nodes appear as managed.
  2. Define a patch baseline with approval rules.
  3. Tag instances with Patch Group values like dev, prod-a, prod-b.
  4. Create maintenance windows per group with Install tasks and rate limits.
  5. Patch dev first, verify, then production groups on later windows.
  6. Review compliance dashboards and fix failures.

Example

aws ssm create-patch-baseline --name linux-prod --operating-system AMAZON_LINUX_2023 \
  --approval-rules 'PatchRules=[{PatchFilterGroup={PatchFilters=[
     {Key=CLASSIFICATION,Values=[Security,Bugfix]},
     {Key=SEVERITY,Values=[Critical,Important]}]},ApproveAfterDays=7}]'

aws ssm send-command --document-name AWS-RunPatchBaseline \
  --targets Key=tag:PatchGroup,Values=prod-a \
  --parameters Operation=Install,RebootOption=RebootIfNeeded \
  --max-concurrency 10% --max-errors 1

Common mistakes

  • Instances missing the role or endpoints, so they silently never register.
  • Patching all production at once with no concurrency limit.
  • No auto-approval delay, so a bad patch hits every server on release day.
  • Patching long-lived pets instead of rebuilding immutable AMIs where possible.

How to answer in the interview

"Instances with the SSM agent and an instance role become managed nodes. Patch Manager applies OS patches based on baselines that say which classifications and severities are approved and after how many days, during maintenance windows, and patch groups by tag let me patch dev before production with concurrency limits. Run Command executes ad-hoc commands across hundreds of instances by tag without SSH, State Manager keeps configuration in a desired state and Automation runbooks handle multi-step tasks like golden AMIs. Inventory and compliance reports show software and patch levels across the fleet."

Likely follow-up questions

  • How avoid patching every production instance at once? Separate patch groups and windows, max concurrency and max errors, plus Auto Scaling health checks.
  • Why Session Manager instead of SSH? No open ports or keys, IAM-controlled and fully logged.
  • How patch Auto Scaling fleets? Prefer baking a new AMI and doing an instance refresh.
