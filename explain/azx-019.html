Explain Azure Policy effects such as deny, audit, modify and deployIfNotExists, and how remediation works.

Azure · concept · levels mid, senior

In one line

Azure Policy applies an effect when a resource matches a rule: deny blocks it, audit only reports it, modify changes properties like tags during create or update, and deployIfNotExists deploys a missing related resource; changing effects use a managed identity, and remediation tasks fix existing resources.

Detailed explanation

A policy definition has an if condition on resource properties (aliases) and a then effect. Definitions are grouped into initiatives (policy set definitions), such as the Microsoft cloud security benchmark, and assigned at a scope: management group, subscription, resource group, with exclusions, parameters and exemptions (waiver or mitigated, optionally time-limited).

  • Deny evaluates during the Resource Manager request and rejects non-compliant creates and updates, for example a storage account allowing public blob access or a VM SKU not on the allowed list.
  • Audit lets the request through but marks the resource non-compliant, visible in the compliance dashboard. AuditIfNotExists checks for a related resource without deploying it.
  • Modify adds, replaces or removes properties or tags as part of the request, typically inheriting tags from the resource group or forcing a setting.
  • DeployIfNotExists (DINE) runs after a successful deployment: if a related resource (diagnostic settings, backup protection, private DNS zone group, Defender plan) is missing, it deploys an ARM template.
  • Others: append, disabled, denyAction (block deletes), and manual.

Modify and DINE need a managed identity on the assignment with roles that let it make the change. Policy only acts on new or updated resources automatically; for resources that existed before the assignment, you create a remediation task, which applies the fix at scale. Evaluation runs on changes and in a regular compliance scan, roughly every 24 hours.

How it works

  1. Write or pick a definition; group into an initiative.
  2. Assign at management group scope with parameters.
  3. New requests are evaluated: deny/modify inline, DINE after deployment.
  4. Compliance scan reports existing non-compliant resources.
  5. Create remediation tasks for modify/DINE using the assignment identity.
  6. Handle justified exceptions with exemptions.

Example

{
  "if": { "allOf": [
    { "field": "type", "equals": "Microsoft.Storage/storageAccounts" },
    { "field": "Microsoft.Storage/storageAccounts/allowBlobPublicAccess", "notEquals": false }
  ]},
  "then": { "effect": "[parameters('effect')]" }
}
az policy remediation create -n fix-diag --policy-assignment diag-to-law \
  --resource-discovery-mode ReEvaluateCompliance

Common mistakes

  • Rolling out deny without an audit phase, breaking pipelines.
  • Forgetting role assignments for the assignment's managed identity.
  • Expecting DINE to fix existing resources without remediation.
  • Exemptions with no expiry or justification.

How to answer in the interview

"Policy evaluates resource properties and applies an effect. Deny blocks non-compliant creates or updates, audit just reports them, modify changes properties inline, typically adding or inheriting tags, and deployIfNotExists deploys a related resource such as diagnostic settings if it's missing. Modify and DINE run under a managed identity on the assignment, and for resources that existed before, I run remediation tasks. I group policies into initiatives, assign them at management group level, and use exemptions for justified exceptions. New deny policies start as audit, parameterised, so we see the impact first."

Likely follow-up questions

  • Why audit before deny? To find existing violations and pipelines that would break.
  • Policy vs RBAC? RBAC controls who can act; Policy controls what configurations are allowed.
  • Policy as code? Store definitions in Git and deploy with Bicep/Terraform or EPAC.
