When would you buy provisioned throughput (PTUs) for Azure OpenAI instead of using pay-as-you-go?

Azure AI & Foundry · concept · levels senior, lead

In one line

Buy provisioned throughput (PTUs) when traffic is high and predictable (lower cost per token, especially with reservations) or when you need consistent latency; size it from real traffic with the capacity calculator, keep utilisation high, and spill peaks over to Standard deployments.

Detailed explanation

With pay-as-you-go Standard deployments you share capacity with other customers. You pay only for tokens used, but latency varies with platform load and you can be throttled at quota limits.

With provisioned throughput you reserve dedicated model capacity, measured in PTUs. Each PTU corresponds to a certain throughput that depends on the model and on the ratio of input to output tokens. You pay per PTU per hour, or much less with monthly or yearly reservations, regardless of usage.

When PTUs win:

  • Steady, high volume: if your workload uses a large number of tokens per minute most of the day, reserved PTUs become cheaper per token than pay-as-you-go.
  • Latency-sensitive user-facing apps with response time SLOs: dedicated capacity gives more consistent time to first token and generation speed.
  • Guaranteed capacity for launches or critical periods when regional pay-as-you-go capacity might be constrained.

Sizing: use the Foundry capacity calculator with real data: requests per minute at peak, average prompt and completion tokens, and caching rate. Load-test against a small provisioned deployment, because actual throughput depends on your token mix.

Utilisation is the key risk: unused PTUs are wasted money. A common design reserves PTUs for the baseline and handles peaks with spillover, where excess requests automatically go to a Standard deployment, or with API Management backend pools prioritising provisioned first. Provisioned deployments return 429 immediately when full, so the gateway can redirect quickly.

For spiky, low-volume or experimental workloads, pay-as-you-go stays better.

How it works

  1. Collect a few weeks of token metrics per application.
  2. Estimate PTUs with the calculator; validate by load test.
  3. Create the provisioned deployment, then purchase a matching reservation.
  4. Configure spillover or APIM priority routing to Standard.
  5. Monitor utilisation and adjust at reservation renewal.

Example

<!-- APIM: provisioned first, standard as overflow -->
<set-backend-service backend-id="openai-pool" />
<!-- backend pool "openai-pool":
     priority 1: ptu-swedencentral (circuit breaker on 429)
     priority 2: standard-global-1, standard-global-2 (weighted) -->
AzureMetrics
| where MetricName == "AzureOpenAIProvisionedManagedUtilizationV2"
| summarize p95 = percentile(Maximum, 95) by bin(TimeGenerated, 1h)

Common mistakes

  • Buying PTUs from a guess, without a load test.
  • Sizing for peak, leaving utilisation at 20% most of the day.
  • Hourly billing for months instead of a reservation.
  • No overflow path, so peaks become user-facing errors.

How to answer in the interview

"PTUs make sense when traffic is high and predictable, because reserved capacity becomes cheaper per token than pay-as-you-go, especially with reservations, and when latency consistency matters because the capacity is dedicated. I size them with the capacity calculator using real traffic: requests per minute, prompt and completion sizes and peaks, and validate with a load test. Utilisation must stay high, so I reserve for the baseline and spill peaks over to Standard deployments directly or via API Management. For spiky or low-volume workloads I stay on pay-as-you-go."

Likely follow-up questions

  • How do you monitor PTU usage? The provisioned utilisation metric; sustained near 100% with spillover means buy more.
  • Why do PTUs return 429 quickly? To let clients or gateways redirect instead of queueing.
  • Can reservations move between models? They apply to deployment type and scope; check terms before switching.
