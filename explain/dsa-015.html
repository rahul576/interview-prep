How do you merge K sorted lists efficiently?

DSA: Lists, Stacks & Queues · concept · levels mid

In one line

Put the head of each list into a min-heap, then repeatedly pop the smallest and push its successor. With N total nodes and k lists, that is O(N log k) time and O(k) space. Divide and conquer pairwise merging has the same complexity. It's the same idea as the k-way merge in external sorting.

Detailed explanation

Merging two sorted lists is a simple linear walk. For k lists, the naive approaches are slow:

  • Merge one by one (result with list 1, then with list 2, ...): early nodes are re-scanned in every merge, giving O(N·k).
  • Collect everything and sort: O(N log N), which ignores the fact that the input is already sorted.

Min-heap approach. At any time the next output node must be the smallest among the current heads of the k lists. A min-heap (PriorityQueue ordered by value) gives that smallest in O(log k). Pop it, append it to the result, and push its next (if any) so that list stays represented. The heap never holds more than k nodes. Each of the N nodes is pushed and popped once, at O(log k) each, so the total is O(N log k) time and O(k) extra space.

Divide and conquer. Merge lists in pairs (0+1, 2+3, ...), then merge the results in pairs, and so on. There are log k rounds, each touching all N nodes, so it is also O(N log k), with O(1) extra space iteratively (or O(log k) recursion). There is no heap overhead, and it works well when k is small.

Real world: databases and big-data systems use exactly this k-way merge in external merge sort (sort chunks that fit in memory, write sorted runs, then merge runs with a heap reading buffered blocks). It also appears in LSM-tree compaction (Cassandra, RocksDB), merging sorted log files by timestamp, and combining paginated results from shards.

How it works

  1. Create a PriorityQueue<ListNode> ordered by val.
  2. Add every non-null head.
  3. dummy -> tail. While the heap is not empty: node = poll(), tail.next = node, tail = node.
  4. If node.next != null, offer(node.next).
  5. Return dummy.next.

Example

public ListNode mergeKLists(ListNode[] lists) {
    PriorityQueue<ListNode> heap = new PriorityQueue<>(Comparator.comparingInt(n -> n.val));
    for (ListNode head : lists) if (head != null) heap.offer(head);
    ListNode dummy = new ListNode(0), tail = dummy;
    while (!heap.isEmpty()) {
        ListNode node = heap.poll();
        tail.next = node;
        tail = node;
        if (node.next != null) heap.offer(node.next);
    }
    return dummy.next;
}
// [1->4->5, 1->3->4, 2->6] -> 1->1->2->3->4->4->5->6

Comparison

ApproachTimeExtra space
Merge sequentiallyO(N·k)O(1)
Collect and sortO(N log N)O(N)
Min-heapO(N log k)O(k)
Divide and conquerO(N log k)O(1)–O(log k)

Common mistakes

  • Adding null heads to the heap, which causes a NullPointerException in the comparator.
  • Pushing all N nodes into the heap at once (O(N log N), O(N) space).
  • Comparator a.val - b.val, which can overflow. Use Integer.compare.
  • Merging sequentially and calling it efficient.

How to answer in the interview

"I'd put the head of each list into a min-heap ordered by value. Then I repeatedly pop the smallest node, append it to the result, and push that node's next if it exists. The heap never holds more than k nodes, so each operation is log k, and with N total nodes that's O(N log k) time and O(k) space. Alternatively, divide and conquer, merging lists in pairs over log k rounds, gives the same complexity without a heap. It's the same k-way merge databases use in external merge sort."

Likely follow-up questions

  • Sorted files that don't fit in memory? External merge: buffer a block from each file, use a heap of the current records, and write output in blocks.
  • Heap versus divide and conquer? Same big-O. The heap is natural for streams, pairwise merging has less overhead.
  • Ties and stability? Break ties by list index in the comparator.
