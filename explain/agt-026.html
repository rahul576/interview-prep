An infrastructure agent deleted production resources while cleaning up test environments. How do you respond and prevent a repeat?

AI Agents & AIOps · scenario · levels senior, lead

In one line

First contain and recover: stop the agent, revoke its credentials, assess damage and restore from IaC and backups; then run a blameless postmortem on root causes such as ambiguous scope, broad permissions and missing checks; prevent repeats with least privilege (no production access), dry runs and approvals for destructive actions, policy guardrails in code (tag allowlists, deletion locks) and new evaluation cases.

Detailed explanation

Incident response comes first, exactly as for a human-caused outage. Disable the agent and revoke its credentials so it cannot continue. Declare an incident, assess what was deleted using cloud activity logs (CloudTrail, Azure Activity Log) and the agent's own trace, and restore: recreate infrastructure from Terraform or Bicep, restore data from backups, point-in-time recovery or soft-deleted resources (many services support soft delete or recycle bins). Communicate with affected teams.

Then a blameless postmortem focused on the system. The agent did what the system allowed. Typical root causes:

  • The cleanup agent's credentials could reach production at all.
  • The instruction "clean up old test environments" was ambiguous: old by what measure, test by what definition?
  • Targets were chosen by name patterns like -test- that also matched production resources.
  • Nothing checked the target list before deletion, and there was no approval for bulk deletes.
  • No deletion protection on critical resources.

Prevention is mostly architectural. A cleanup agent gets least-privilege credentials scoped to test subscriptions or accounts only, so production deletion is technically impossible. Destructive actions run first as a dry run that lists exactly what will be deleted, and require human approval above a threshold, such as more than five resources. Guardrails in code, not prompts, enforce rules: only delete resources tagged env=test with an expired ttl tag, never resources tagged env=prod. Critical resources get deletion locks (Azure resource locks, AWS termination protection, Terraform prevent_destroy), and organisation policies (SCPs or Azure Policy) add a backstop. Finally, the scenario becomes an evaluation case, and the agent's change goes through review like any automation.

How it works

  1. Stop the agent; revoke credentials; declare an incident.
  2. Determine what was deleted from cloud logs and traces.
  3. Restore from IaC, backups and soft delete; verify services.
  4. Blameless postmortem: timeline, root causes, contributing factors.
  5. Implement least privilege, dry run plus approval, tag-based policy, locks.
  6. Add eval cases and monitoring; review other agents for the same risk.

Example

def delete_resources(candidates, approver=None):
    allowed, refused = [], []
    for r in candidates:
        if r.subscription not in TEST_SUBSCRIPTIONS or r.tags.get("env") != "test":
            refused.append((r.id, "not a test resource"))
        elif r.locked or r.tags.get("protected") == "true":
            refused.append((r.id, "protected"))
        elif not ttl_expired(r.tags.get("ttl")):
            refused.append((r.id, "ttl not expired"))
        else:
            allowed.append(r)
    plan = {"delete": [r.id for r in allowed], "refused": refused}
    if len(allowed) > 5 and approver is None:
        return {"ok": False, "status": "approval_required", "plan": plan}
    for r in allowed:
        cloud.delete(r.id)
    return {"ok": True, "deleted": plan["delete"], "refused": refused}

Common mistakes

  • Blaming the model and just rewording the prompt.
  • Keeping production access "for convenience".
  • Relying on name patterns instead of authoritative tags and account boundaries.
  • No dry run or approval for bulk deletions.
  • Not checking other agents and automations for the same weakness.

How to answer in the interview

"First incident response: disable the agent and revoke its credentials, find out what was deleted from cloud logs and the agent trace, and restore infrastructure from code and data from backups or soft delete. Then a blameless postmortem on the system. Usually the agent's credentials could reach production at all, the instruction was ambiguous, targets were matched by name patterns, and nothing checked the list before deletion. Prevention is architectural: the cleanup agent only gets credentials for test accounts, so production deletion is impossible; deletes run as a dry run first and need approval above a threshold; code-level guardrails only allow resources tagged env=test, and critical resources have deletion locks. And the scenario becomes an eval case."

Likely follow-up questions

  • Which control first? Removing production access, because it eliminates the failure mode regardless of model behaviour.
  • Why not just improve the prompt? Prompts are not enforcement; a different input or injection could cause the same result.
  • How do you prove recovery is possible? Regularly test restores and IaC rebuilds.
