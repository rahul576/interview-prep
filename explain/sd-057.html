Design a multi-region active-active architecture for a global application.

Scalability & Reliability · design · levels senior, lead

In one line

Active-active multi-region routes users to the nearest healthy region (GeoDNS/anycast), deploys stateless services everywhere, and handles data by home-region partitioning, conflict-tolerant replication or globally consistent databases, with capacity headroom and failover drills.

Detailed explanation

Benefits: lower latency for a global user base and survival of a full region outage. The hard part is always data.

Data strategies:

  1. Home region (partitioned writes): each user/tenant has a home region where their writes go; other regions hold read replicas. Few conflicts, easy reasoning; a region failure means failing over that region's users (with possible lag loss).
  2. Multi-leader with conflict resolution: every region accepts writes; resolve with LWW, merges or CRDTs. Good for carts, likes, presence; bad for balances.
  3. Globally consistent DBs: Spanner, CockroachDB, Cosmos DB (strong), YugabyteDB. Consensus across regions gives correctness but each write pays cross-region latency (tens to 100+ ms).

Routing: Route 53 latency/geo routing, Azure Front Door, Cloudflare/Global Accelerator anycast, with health checks to drain a failing region. Headroom: with 3 regions, each needs ~50% extra capacity to absorb a lost region. Drills: regularly fail over for real.

How it works

  1. Global LB → nearest healthy region.
  2. Region: full stateless stack + local caches + data replicas.
  3. Writes → home region (or consistent DB / CRDT store).
  4. Async replication of events, search indexes, caches per region.
  5. Region down → health checks fail → traffic shifted; promote replicas for its home users.

Example

users in India   ─▶ Front Door ─▶ ap-south  (home region for IN users: writes here)
users in Germany ─▶ Front Door ─▶ eu-west   (home region for EU users: writes here)
ap-south ⇄ async replication of read models, search indexes, events ⇄ eu-west
eu-west down → health probe fails → EU traffic to ap-south; promote EU replica there

Common mistakes

  • Assuming databases replicate magically without conflicts.
  • No spare capacity for failover.
  • Hidden single-region dependencies (auth, config, DNS).

How to answer in the interview

"Global load balancing sends users to the nearest healthy region, and stateless services run in all regions. For data I'd give each user a home region for writes with replicas elsewhere, which avoids most conflicts; conflict-tolerant data like carts could be multi-leader, and truly global strongly consistent data would use Spanner or Cosmos DB, accepting write latency. Each region keeps headroom to absorb another's traffic, and we rehearse failovers."

Likely follow-up questions

  • When is active-passive better? Strong consistency needs, simpler ops, lower budgets.
  • What about sessions? Stateless tokens valid in all regions.
  • Data residency? Home region aligned with legal region.
