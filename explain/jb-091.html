How do you distinguish between business exceptions, technical exceptions, and infrastructure failures?

Exceptions · design · levels senior, lead

In one line

Business exceptions are expected rule violations (4xx, no retry, info/warn), technical exceptions are bugs or impossible states (500, error log, alert), and infrastructure failures are environment problems such as timeouts or unavailable dependencies (often transient: retry with backoff, circuit breaker, 503); model them as separate hierarchies with separate handling.

Detailed explanation

Treating every exception the same leads to bad outcomes: retrying "insufficient balance" five times, paging on-call for a user typo, or returning 400 for a database outage. Classifying failures lets each layer react correctly.

Business exceptions express domain rules: insufficient balance, order already shipped, coupon expired, duplicate registration. They are normal, expected outcomes. Map them to 4xx (400, 404, 409, 422) with a stable error code the client can act on. Log at info or warn without full stack traces, count them as business metrics, and never retry, because the result will not change.

Technical exceptions are unexpected states caused by defects: NullPointerException, IllegalStateException, a mapping error, a violated invariant. They are not the user's fault. Return a generic 500 without internal details, log at error with the full stack trace and correlation id, and alert on rate increases. Retrying rarely helps.

Infrastructure failures come from the environment: DB connection timeouts, deadlocks, a downstream service returning 503, broker unavailable, DNS issues. They are often transient, so apply retries with exponential backoff and jitter (only for idempotent operations or with idempotency keys), circuit breakers and bulkheads (Resilience4j), timeouts, and fallbacks. Externally, return 503 or 504, possibly with Retry-After. For messaging, transient failures go to retry topics and eventually a dead-letter queue.

Implementation: a base BusinessException (with error code), a TechnicalException, and an InfrastructureException with a retryable flag, or classification via marker interfaces. Translate third-party exceptions at the adapter boundary (Spring already maps SQL errors into TransientDataAccessException vs NonTransientDataAccessException). Retry policies list retryable types explicitly.

How it works

  1. Adapters catch raw library exceptions and translate them into the right category.
  2. Domain code throws business exceptions for rule violations.
  3. Retry and circuit-breaker policies apply only to retryable infrastructure exceptions.
  4. A central handler maps each category to status, log level and response body.
  5. Metrics and alerts are configured per category.

Example

public abstract class BusinessException extends RuntimeException {
    private final String code;
    protected BusinessException(String code, String msg) { super(msg); this.code = code; }
    public String code() { return code; }
}
public class InfrastructureException extends RuntimeException {
    public InfrastructureException(String msg, Throwable cause) { super(msg, cause); }
}

Common mistakes

  • Retrying everything, including business and non-idempotent failures.
  • Logging business exceptions with full stack traces at error level, creating alert noise.
  • Leaking infrastructure details (SQL, hostnames) to clients.
  • Catching Exception in retry config.

How to answer in the interview

"I separate them by cause and reaction. Business exceptions are expected rule violations like insufficient balance; they map to 4xx with an error code, log at info or warn, and are never retried. Technical exceptions are bugs like an NPE or illegal state; they return a generic 500, log at error with the stack trace and alert. Infrastructure failures are timeouts or downstream outages; they're often transient, so retries with backoff, circuit breakers and 503 responses fit. I model them as separate hierarchies, translate library exceptions at adapters, and configure retries and alerts per category."

Likely follow-up questions

  • How would your retry logic avoid retrying business exceptions? Explicit retry and ignore lists by exception type, or a retryable flag.
  • How do you make retries safe? Idempotent operations or idempotency keys.
  • Where do failed messages go? Retry topics, then a dead-letter queue.
