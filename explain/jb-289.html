How would you identify CPU-intensive operations in a Java application?

JVM & Performance · scenario · levels mid, senior

In one line

Confirm the process is CPU-bound, find the hot threads with top -H and match their hex ids to the nid in thread dumps, then use a sampling profiler (async-profiler or JFR) to get flame graphs; check whether CPU goes to GC or JIT threads rather than application code, and verify fixes with JMH.

Detailed explanation

Is it really CPU? High latency can come from waiting (locks, I/O) rather than computation. Check process CPU in metrics (process.cpu.usage), top, and in Kubernetes whether the container is throttled by its CPU limit, which looks like slowness without 100% usage.

Which threads? top -H -p <pid> shows per-thread CPU. Thread names help (http-nio-8080-exec-12, GC Thread#3, C2 CompilerThread0). Convert the hot native thread id to hex and find nid=0x... in a dump from jcmd <pid> Thread.print. Take several dumps seconds apart; a thread stuck in the same frames each time and in state RUNNABLE is your hotspot.

GC or JIT? If GC threads dominate, the root cause is memory pressure: look at allocation rates and heap occupancy. If compiler threads dominate shortly after startup, it is normal warm-up; persistently, it might be deoptimisation loops or a full code cache.

Sampling profilers. Thread dumps are a crude, manual sample. async-profiler uses perf_events and HotSpot APIs to sample all threads, including native and JVM frames, with low overhead and produces flame graphs: the x-axis width is the share of samples, the y-axis the call stack. JFR records jdk.ExecutionSample events with similar low overhead and is built into the JDK. Both avoid safepoint bias, the distortion where older profilers could only sample at safepoints and misattributed time. Both are safe for short recordings in production.

Typical culprits. Regex backtracking, JSON or XML serialisation, hashing and encryption, compression, logging with expensive formatting, inefficient loops and data structures (nested loops over large lists), busy waiting, retry loops without backoff, and exception creation with stack traces in hot paths.

Verify. Reproduce the hot method in a JMH benchmark, optimise, compare throughput, then confirm CPU usage dropped in production.

How it works

  1. Confirm CPU saturation and rule out throttling.
  2. top -H to find hot thread ids; map to thread dumps.
  3. Distinguish GC, JIT and application threads.
  4. Record a CPU flame graph with async-profiler or JFR.
  5. Fix the widest frames; benchmark with JMH; re-check production.

Example

top -H -p 4211 -n 1 | head -15
printf '%x\n' 4302             # 10ce
jcmd 4211 Thread.print | grep -A 12 'nid=0x10ce'

asprof -e cpu -d 30 -f /tmp/cpu.html 4211
# or JFR
jcmd 4211 JFR.start duration=60s settings=profile filename=/tmp/cpu.jfr
@Benchmark
public String serialise(State s) throws Exception {
    return s.mapper.writeValueAsString(s.order);   // measure before/after
}

Common mistakes

  • Relying on one thread dump.
  • Ignoring GC and JIT threads in the analysis.
  • Using instrumenting profilers in production, distorting timings.
  • Optimising code that was not on the flame graph.

How to answer in the interview

"First I confirm the process is CPU-bound with metrics and top, and that it isn't just container throttling. To find which threads burn CPU I use top -H on the JVM process, convert the hot thread ids to hex and match them to the nid fields in a thread dump from jcmd or jstack; several dumps in a row show whether it's a tight loop. The better tool is a sampling profiler: async-profiler or JFR produce flame graphs showing exactly which methods consume CPU, with low overhead, safe in production. I also check whether CPU is going to GC or JIT compiler threads rather than application code. Typical culprits are regex, serialisation, inefficient loops and logging, and I verify fixes with JMH."

Likely follow-up questions

  • Why can a sampling profiler be misleading because of safepoint bias? Profilers that sample only at safepoints attribute time to the nearest safepoint, not the real hot code; async-profiler and JFR avoid this.
  • How do you read a flame graph? Wide frames consume the most samples; look for wide plateaus near the top.
  • What is wall-clock profiling? Sampling all threads regardless of state, useful for latency including waits.
