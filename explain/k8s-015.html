What are PriorityClasses and preemption in Kubernetes, and when do you use them?

Kubernetes · concept · levels mid, senior

In one line

A PriorityClass gives pods an integer priority; the scheduler orders the pending queue by it and, if a high-priority pod cannot fit, may preempt lower-priority pods. Critical system pods use system-cluster-critical / system-node-critical, batch work gets low priority, and preemptionPolicy: Never lets a pod jump the queue without evicting others.

Detailed explanation

Without priorities, a flood of batch jobs can fill the cluster and leave a production rollout Pending. Priorities let the scheduler make value judgements.

A PriorityClass is cluster-scoped, with a value (higher wins, user classes up to one billion), optional globalDefault, and preemptionPolicy (PreemptLowerPriority by default, or Never). Pods reference it via priorityClassName; admission resolves it to spec.priority.

Effects:

  • Scheduling order: higher-priority Pending pods are tried first.
  • Preemption: if no node fits a pod, the scheduler looks for a node where evicting lower-priority pods would make room, picks victims minimising impact, sets nominatedNodeName, and deletes the victims gracefully (honouring their termination grace period). It tries to respect PodDisruptionBudgets but will violate them if there's no other option.
  • Node-pressure eviction also considers priority after usage over requests.

Kubernetes ships system-cluster-critical and system-node-critical (values around two billion) for CoreDNS, CNI and CSI agents, kube-proxy and similar, so applications can never push them out.

A practical scheme has only a few classes: critical customer-facing services, default for normal services, low for batch, CI runners and dev workloads, which tolerate preemption and retry. Risks: everyone marks their service critical; preemption cascades, where evicted pods preempt still-lower ones; and preempted batch jobs that never get to finish. Restrict high classes with ResourceQuota scoped by priority class so only approved namespaces can use them. preemptionPolicy: Never suits important batch jobs: they queue ahead but wait for free capacity.

How it works

  1. Define PriorityClasses; set a sensible global default.
  2. Workloads set priorityClassName.
  3. Scheduler sorts pending pods by priority.
  4. If a high-priority pod doesn't fit, scheduler simulates removing lower-priority pods per node.
  5. Victims are evicted gracefully; the pod is bound once room is free.
  6. Autoscaler can add nodes for the preempted pods afterwards.

Example

apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata: { name: prod-critical }
value: 100000
description: Customer-facing production services
---
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata: { name: batch-low }
value: 1000
preemptionPolicy: Never
description: Batch and CI work; waits for capacity

Common mistakes

  • Making every workload high priority, which equals no priority.
  • No quota restricting who uses critical classes.
  • Assuming PDBs fully protect against preemption.
  • Putting application pods in system-critical classes.

How to answer in the interview

"A PriorityClass gives pods an integer priority. The scheduler orders pending pods by it, and if a high-priority pod can't fit, it can preempt lower-priority pods on a node, evicting them gracefully. Kubernetes uses system-cluster-critical and system-node-critical for components like CoreDNS and CNI agents. I keep a few classes: critical customer-facing, default, and low for batch and CI that can be retried. The risk is starvation or eviction cascades, so I restrict high classes with priority-scoped quotas and use preemptionPolicy Never for work that should queue ahead without evicting anything."

Likely follow-up questions

  • How does priority interact with PDBs? Preemption tries to respect PDBs but violates them if no other victims exist.
  • What is nominatedNodeName? The node the scheduler plans to place the preemptor on after victims leave.
  • Does preemption work across nodes? It picks victims on a single node per scheduling attempt.
