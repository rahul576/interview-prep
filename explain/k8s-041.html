How does Kubernetes schedule GPUs and other accelerators, and what does Dynamic Resource Allocation add?

Kubernetes · concept · levels mid, senior, lead

In one line

Classically, device plugins advertise accelerators as integer extended resources like nvidia.com/gpu (whole devices, no overcommit, sharing only via MIG or time-slicing); Dynamic Resource Allocation (DRA), GA in Kubernetes 1.34, adds ResourceClaims, DeviceClasses and attribute-based selection with CEL.

Detailed explanation

With the device plugin framework, a vendor DaemonSet (for NVIDIA usually deployed by the GPU Operator, which also installs drivers, the container toolkit and the DCGM exporter) registers with the kubelet and reports a count of devices. The node then advertises, say, nvidia.com/gpu: 8. Pods request them in resources.limits as integers: no fractions and no overcommit. The scheduler only sees a number, so it cannot express "a GPU with 80 GB of memory" or "two GPUs on the same NVLink" except with node labels and affinity.

Sharing is possible in two ways. Multi-Instance GPU (MIG) on supported GPUs splits a card into hardware-isolated slices that appear as separate resources such as nvidia.com/mig-1g.10gb. Time-slicing advertises one GPU as several replicas but gives no memory or fault isolation. GPU nodes are usually a dedicated pool with a taint like nvidia.com/gpu=present:NoSchedule, so only workloads that tolerate it (and request GPUs) land there.

DRA generalises this, much like PVCs did for storage. DRA drivers publish devices and their attributes (model, memory, capacity) in ResourceSlices. Admins define DeviceClasses. Workloads create a ResourceClaim or a ResourceClaimTemplate (one claim per pod) that selects devices with CEL expressions, and the scheduler allocates matching devices. Claims can be shared between containers or pods, can request several devices with constraints, and allocations are visible as API objects. This makes heterogeneous accelerator fleets far easier to schedule.

How it works

  1. Driver or device plugin runs as a DaemonSet on GPU nodes.
  2. Device plugin path: node advertises nvidia.com/gpu: N; pod requests an integer.
  3. DRA path: driver publishes ResourceSlices with device attributes.
  4. Admin creates a DeviceClass; workload creates a ResourceClaim with a CEL selector.
  5. Scheduler allocates a matching device and binds the pod to that node.
  6. Kubelet asks the driver to prepare the device and injects it into the container.

Example

apiVersion: resource.k8s.io/v1
kind: ResourceClaimTemplate
metadata: { name: big-gpu }
spec:
  spec:
    devices:
      requests:
        - name: gpu
          exactly:
            deviceClassName: gpu.nvidia.com
            selectors:
              - cel:
                  expression: device.capacity["gpu.nvidia.com"].memory.compareTo(quantity("40Gi")) >= 0
---
apiVersion: v1
kind: Pod
metadata: { name: trainer }
spec:
  resourceClaims:
    - name: gpu
      resourceClaimTemplateName: big-gpu
  containers:
    - name: app
      image: registry.example.com/trainer:1.4
      resources:
        claims: [{ name: gpu }]

Common mistakes

  • Requesting fractional GPUs with the device plugin (not allowed).
  • Using time-slicing for multi-tenant workloads that need isolation.
  • Forgetting taints, so ordinary pods fill expensive GPU nodes.
  • Assuming the scheduler understands GPU memory or topology without DRA or labels.

How to answer in the interview

"Traditionally a device plugin, usually installed by the NVIDIA GPU Operator, advertises nvidia.com/gpu as an extended resource and pods request whole GPUs as integers, with no overcommit. Sharing needs MIG for isolated slices or time-slicing without isolation, and GPU pools are tainted. DRA, GA in 1.34, is the newer model: drivers publish devices with attributes in ResourceSlices, admins define DeviceClasses, and pods use ResourceClaims with CEL selectors, for example a GPU with at least 40 GB, and claims can be shared. It's like PVCs for devices."

Likely follow-up questions

  • Why is gang scheduling important for training? Distributed jobs need all workers at once; partial placement holds GPUs idle and can deadlock; Kueue or Volcano solve this.
  • MIG vs time-slicing? MIG has hardware isolation of memory and compute; time-slicing just shares time.
  • How do you monitor GPU use? DCGM exporter metrics in Prometheus.
