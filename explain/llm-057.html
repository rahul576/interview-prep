Your provider announces that the model version you use will be retired in three months. What is your migration playbook?

LLMOps & RAG · scenario · levels mid, senior

In one line

Start immediately: inventory every use of the model (apps, batch jobs, judges), pick candidate replacements, run the evaluation suite comparing quality, format compliance, tool use, latency and cost, adapt prompts, parsers and parameters, then roll out gradually with monitoring and rollback while the old version still exists.

Detailed explanation

Model retirements are routine: providers publish deprecation schedules, and after the retirement date requests to that version fail. Three months sounds long but disappears quickly if many teams and pipelines depend on the model.

Inventory. Search code, configuration and gateway logs for the model ID. Include the easy-to-miss places: batch and ETL jobs, evaluation judges (changing the judge shifts all your metrics), fine-tuned models built on that base, and hard-coded fallbacks. Gateway usage logs grouped by model and caller are the most reliable source.

Candidates. Usually the provider's recommended successor, plus one or two alternatives (a cheaper tier, another provider) since migration effort is similar.

Evaluate. Run the full suite on each candidate. Compare per task and segment: accuracy, groundedness, output format compliance (JSON validity, field names), tool-calling behaviour, refusal rates, verbosity, latency and cost. New models often differ subtly: more verbose, different JSON habits, changed refusal thresholds, different sensitivity to prompt wording, different defaults for parameters, or a different tokenizer that changes cost.

Adapt. Tune prompts for the new model, harden parsers, adjust max tokens and temperature, then re-evaluate. Use the provider's migration notes for known behaviour changes.

Roll out. Shadow traffic (run both, compare offline), then a canary percentage through the gateway, monitoring quality signals, errors and cost, with instant rollback while the old model still exists. Pin the explicit new version, not an alias that moves, and update documentation.

How it works

  1. Week 1: inventory via code search and gateway logs; assign owners.
  2. Week 2-3: evaluate candidates; choose.
  3. Week 3-6: adapt prompts and parsers; re-evaluate.
  4. Week 6-9: shadow and canary rollout; monitor.
  5. Week 10: complete cut-over; remove old references.
  6. Buffer before deadline for surprises.

Example

# gateway routing during canary
routes:
  support-answer:
    - model: provider/model-v3-2026-08   # new, pinned
      weight: 20
    - model: provider/model-v2-2025-05   # retiring
      weight: 80
  fallback: provider/model-v2-2025-05

Common mistakes

  • Waiting until the final weeks.
  • Forgetting judge models and batch jobs.
  • Using a floating alias that changes under you again.
  • Assuming the successor is a drop-in replacement.

How to answer in the interview

"I'd start straight away. First an inventory of every app, prompt, batch job and evaluation judge using that version, from code search and gateway logs. Then I'd pick candidates, usually the recommended successor plus an alternative, and run the full evaluation suite comparing quality per task, format compliance, tool calling, latency and cost. New models behave differently, so I'd adjust prompts, parsers and parameters and re-evaluate. Rollout is gradual, shadow then canary through the gateway, with monitoring and rollback while the old model still exists. Finally I pin the new explicit version and keep the eval suite ready for next time."

Likely follow-up questions

  • No replacement matches on a critical task? Prompt tuning, a larger model for that task, fine-tuning, or negotiate extended support; escalate early.
  • Fine-tuned model on retiring base? Re-run the fine-tuning pipeline on the new base and evaluate.
  • Preventing future pain? Gateway abstraction, model registry, routine eval suite.
