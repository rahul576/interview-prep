One shard of your database is overloaded because a celebrity account gets most of the traffic. How do you handle hot keys and hot partitions?

Distributed Systems · scenario · levels entry, mid, senior

In one line

For hot keys: identify them, cache in layers (CDN, distributed and in-process), split writes across sub-keys, treat celebrities specially (fan-out on read), aggregate counters asynchronously, and choose high-cardinality partition keys or dedicated shards.

Detailed explanation

Sharding assumes load is spread evenly. One celebrity, viral post or giant tenant breaks that assumption: millions of reads or writes hit one key on one shard, while others idle.

Reads: a hot key is the easiest case. Put a short-TTL in-process cache in each app instance (even 1–5 s removes most load), keep the distributed cache, and serve public data from the CDN. Replicate the hot key across several cache nodes (key#1..#N).

Writes: e.g. likes on a viral post. Split the counter into N sub-counters (likes:post9:0..15), increment a random one, and sum on read (or periodically). Or buffer increments in a stream and apply aggregated updates every second.

Fan-out: in feeds, pushing a celebrity's post to 50M followers' timelines (fan-out on write) is too expensive; instead merge celebrity posts at read time (fan-out on read), a hybrid model.

Data placement: move very large tenants to dedicated shards; avoid partition keys with skew.

How it works

  1. Detect: per-key QPS metrics, sampling, Redis hotkeys, DynamoDB contributor insights.
  2. Reads: local cache + replicated cache keys + CDN.
  3. Writes: sharded counters / stream aggregation.
  4. Architecture: hybrid fan-out; tenant isolation.

Example

shard = random.randrange(16)
redis.incr(f"likes:{post_id}:{shard}")
total = sum(int(x or 0) for x in redis.mget([f"likes:{post_id}:{i}" for i in range(16)]))

Common mistakes

  • Adding more shards (doesn't help one key).
  • Strongly consistent real-time counters where approximate is fine.
  • Fan-out on write for accounts with millions of followers.

How to answer in the interview

"First I'd confirm which key is hot and whether it's reads or writes. For reads, I'd layer caches: CDN, Redis and a short-lived local cache in each instance, possibly replicating the key. For writes like likes, I'd split the counter into sub-keys or aggregate through a stream. In feeds, celebrities use fan-out on read. Long term, high-cardinality keys and dedicated shards for huge tenants."

Likely follow-up questions

  • A million likes per minute? Sharded counters + async aggregation, approximate display.
  • DynamoDB adaptive capacity? Helps but doesn't remove per-partition limits.
  • Hot tenant? Move to dedicated shard or cell.
