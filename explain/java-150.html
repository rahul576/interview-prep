How would you design a scalable e-commerce order service that must not oversell inventory?

System Design · design · levels senior, lead

In one line

To avoid overselling, reserve stock with an atomic conditional update (or optimistic locking), coordinate order, payment and inventory with a saga with compensations and expiring reservations, make every step idempotent, publish events via outbox + Kafka, and handle hot items with Redis pre-allocation, queuing and sharding.

Detailed explanation

Overselling happens when two buyers read "1 left" and both decrement. The fix is to make check-and-decrement one atomic operation at the source of truth: UPDATE inventory SET available = available - :qty WHERE sku = :sku AND available >= :qty; if zero rows change, the item is out of stock. Alternatively, optimistic locking with a @Version column and retry, or SELECT ... FOR UPDATE for short transactions.

The order flow spans services, so there is no single ACID transaction. A saga coordinates it: order created (PENDING) -> inventory reserved -> payment authorised -> order CONFIRMED. If payment fails, a compensating action releases the reservation and the order is CANCELLED. Reservations have an expiry (e.g. 15 minutes), so abandoned checkouts return stock automatically. Orchestrated sagas (a coordinator or a workflow engine like Temporal) are easier to reason about than pure choreography for this flow.

Every message can be delivered twice, so each step is idempotent: reservations keyed by order ID, payments by idempotency key. Events use the transactional outbox so the database change and the event are never out of sync.

Flash sales concentrate writes on one row. Options: pre-load stock into Redis and decrement atomically with DECRBY/Lua as a gatekeeper, then persist asynchronously; queue purchase requests per SKU; split stock into sub-buckets (shards) across rows; use a virtual waiting room.

How it works

  1. Client places order with an idempotency key; order saved as PENDING with outbox event.
  2. Inventory service reserves stock atomically and records reservation (order ID, expiry).
  3. Payment service authorises; emits success or failure.
  4. On success: confirm reservation (commit stock), order CONFIRMED.
  5. On failure or timeout: release reservation, order CANCELLED.
  6. Expiry job releases stale reservations.

Example

@Modifying
@Query("""
   UPDATE Inventory i SET i.available = i.available - :qty, i.reserved = i.reserved + :qty
   WHERE i.sku = :sku AND i.available >= :qty""")
int reserve(@Param("sku") String sku, @Param("qty") int qty);

@Transactional
public ReservationResult reserve(String orderId, String sku, int qty) {
    if (reservations.existsByOrderId(orderId)) return ReservationResult.ALREADY_DONE; // idempotent
    if (inventoryRepo.reserve(sku, qty) == 0) return ReservationResult.OUT_OF_STOCK;
    reservations.save(new Reservation(orderId, sku, qty, Instant.now().plus(15, MINUTES)));
    outbox.save(new OutboxEvent("StockReserved", orderId));
    return ReservationResult.RESERVED;
}

Common mistakes

  • Read-then-write stock checks in application code.
  • Distributed 2PC across services instead of a saga.
  • Reservations that never expire.
  • Publishing to Kafka outside the DB transaction (lost or phantom events).
  • Using a cache as the source of truth without reconciliation.

How to answer in the interview

"The order starts as pending and reserves stock with an atomic conditional update, so concurrent buyers can't both take the last unit; optimistic locking is the alternative. Payment and inventory are coordinated with a saga: if payment fails, a compensation releases the reservation, and reservations expire anyway. Every step is idempotent and events go through an outbox to Kafka. For flash sales I'd gate demand with Redis atomic counters pre-loaded with stock, queue requests per SKU, and shard hot stock rows."

Likely follow-up questions

  • 1,000 units, a million users? Waiting room, Redis counter as gatekeeper, async order creation, reconcile with DB.
  • Orchestration or choreography? Orchestration for multi-step flows with clear ownership and visibility.
  • Multiple warehouses? Reserve per warehouse location, choose by proximity, split shipments if needed.
