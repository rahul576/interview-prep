How does Kafka achieve high throughput and fault tolerance?

Kafka · concept · levels senior, lead

In one line

Kafka gets throughput from a sequential append-only log, the OS page cache, zero-copy transfer, batching and compression and partitioning, and fault tolerance from replication with leaders, followers and the ISR, acks=all, min.insync.replicas and KRaft controller failover.

Detailed explanation

Throughput. Each partition is an append-only log split into segment files. Writes are sequential, which disks and SSDs handle far faster than random I/O, and Kafka relies on the operating system page cache rather than a large JVM heap cache, so recent data is usually read from memory and GC stays small. When sending data to consumers, brokers use zero-copy (sendfile), moving bytes from the page cache to the network socket without copying them through user space (this does not apply when TLS encryption is enabled, since data must be encrypted in the JVM). Producers batch records per partition (batch.size, linger.ms) and compress whole batches (lz4, zstd, snappy, gzip); brokers store the compressed batch as is, and consumers fetch in large chunks. Finally, partitions spread a topic across brokers and allow as many parallel consumers per group as there are partitions.

Fault tolerance. Each partition has a replication factor, typically 3. One replica is the leader, handling reads and writes by default; followers fetch from it. Replicas that are caught up form the in-sync replica set (ISR). With acks=all the leader only acknowledges once all ISR members have the record, and min.insync.replicas=2 makes writes fail rather than be accepted by a lone replica. If a broker dies, the controller elects a new leader from the ISR, so acknowledged data is not lost; unclean.leader.election.enable=false (the default) prevents electing an out-of-date replica. Since Kafka 4.0 metadata and controller election use KRaft, a Raft-based quorum of controllers; ZooKeeper support has been removed. Replicas are spread across racks or availability zones with broker.rack.

How it works

  1. Producer batches and compresses records for a partition.
  2. Leader appends the batch sequentially to the active segment.
  3. Followers fetch and append; ISR is updated.
  4. With acks=all, the leader acks after ISR replication.
  5. Consumers fetch large chunks via zero-copy from page cache.
  6. On broker failure, the KRaft controller promotes an ISR follower to leader.

Example

# Topic
replication.factor=3
min.insync.replicas=2
# Producer
acks=all
enable.idempotence=true
compression.type=zstd
linger.ms=10
batch.size=65536
kafka-topics.sh --bootstrap-server b1:9092 --create --topic payments \
  --partitions 12 --replication-factor 3 --config min.insync.replicas=2

With RF 3 and min ISR 2, one broker can fail and writes continue; with two failures, producers get NotEnoughReplicas instead of silently losing durability.

Common mistakes

  • Using acks=all with min.insync.replicas=1, which gives little extra safety.
  • Giving brokers huge heaps instead of leaving memory for the page cache.
  • Too many partitions, increasing metadata and failover cost.
  • Saying Kafka fsyncs every message; it relies mainly on replication for durability.

How to answer in the interview

"For throughput, every partition is an append-only log written sequentially, reads are served mostly from the OS page cache, brokers use zero-copy sendfile to push data to the network, and producers batch and compress records. Partitioning spreads load across brokers and consumers. For fault tolerance, each partition is replicated, typically three times; the leader takes writes and followers in the ISR copy them. With acks=all and min.insync.replicas=2 an acknowledged write survives a broker failure, and the KRaft controller quorum elects a new leader from the ISR."

Likely follow-up questions

  • What do you trade by using acks=1? Lower latency, but writes acknowledged by a leader that dies before replication are lost.
  • What is unclean leader election? Electing an out-of-sync replica; restores availability but loses data.
  • Why did Kafka drop ZooKeeper? KRaft simplifies operations and scales metadata to far more partitions.
