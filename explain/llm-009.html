When do you use tensor parallelism or pipeline parallelism to serve a large model?

LLMOps & RAG · concept · levels senior, lead

In one line

Use tensor parallelism (TP) to split each layer across GPUs within a node over NVLink when a model does not fit or you need lower latency, and pipeline parallelism (PP) to split groups of layers into stages across nodes for very large models, accepting extra latency and bubble overhead.

Detailed explanation

Tensor parallelism shards the big weight matrices of every layer. For a feed-forward block, each of 4 GPUs holds a quarter of the columns, computes its part of the result, and the GPUs combine partial results with an all-reduce (twice per transformer layer in the common Megatron-style layout). All GPUs work on every token, so per-token compute and memory reads are divided, which reduces latency. The catch is communication on every layer for every step: it needs very high bandwidth and low latency, such as NVLink/NVSwitch inside a node (hundreds of GB/s to well over a TB/s per GPU). That is why TP is used with 2, 4 or 8 GPUs in one server, for example a 70B model with TP=4 on four H100s. TP degree must divide the number of attention heads.

Pipeline parallelism assigns consecutive layers to different GPUs: layers 1–40 on node A, 41–80 on node B. Only activations at stage boundaries travel between stages, so it tolerates slower links like InfiniBand or Ethernet between nodes. But a single token must pass through stages sequentially, so it does not reduce latency and adds hops; to keep all stages busy you need many sequences in flight (micro-batching), otherwise pipeline bubbles waste GPUs.

A common pattern for huge models is TP within a node and PP across nodes, for example TP=8, PP=2 on two 8-GPU servers. vLLM, SGLang and TensorRT-LLM expose these as simple flags. Also consider the alternative: quantisation may make the model fit with less or no splitting, and several independent replicas usually give better throughput than one heavily split replica.

How it works

  1. Compute memory need; choose minimum GPUs.
  2. Use TP up to the GPUs connected by NVLink in a node.
  3. If still too large, add PP stages across nodes.
  4. Launch with matching TP/PP settings; engine shards weights.
  5. Benchmark latency and throughput against more replicas with less parallelism.

Example

# 70B on one 4-GPU node
vllm serve meta-llama/Llama-3.1-70B-Instruct --tensor-parallel-size 4
# 405B across two 8-GPU nodes (Ray or multi-node launcher)
vllm serve meta-llama/Llama-3.1-405B-Instruct-FP8 \
  --tensor-parallel-size 8 --pipeline-parallel-size 2

Common mistakes

  • Running TP across nodes over ordinary networking.
  • Splitting a model that would fit with FP8, wasting GPUs.
  • TP degree that does not divide the attention heads.
  • Assuming one big split replica beats several smaller replicas for throughput.

How to answer in the interview

"When the model does not fit on one GPU, or I need more room for the KV cache, I split it. Tensor parallelism splits each layer's matrix multiplications across GPUs, so all GPUs work on every token and exchange partial results at every layer; that needs NVLink within a node, typically 2, 4 or 8 GPUs, and it also cuts latency. Pipeline parallelism puts groups of layers on different GPUs or nodes as stages; it needs less bandwidth and can span nodes, but adds latency and needs batching to avoid bubbles. For very large models I combine TP inside a node with PP across nodes."

Likely follow-up questions

  • Why not TP across nodes? Per-layer all-reduce over slower links dominates step time.
  • What is expert parallelism? Distributing MoE experts across GPUs with all-to-all routing.
  • Data parallelism in serving? Independent replicas behind a load balancer, the simplest scaling.
