What is the pseudo-random generator API in Java?

Modern Java (11-21) · concept · levels mid, senior

In one line

Java 17 (JEP 356) added the RandomGenerator interface in java.util.random, implemented by Random, SplittableRandom, ThreadLocalRandom and SecureRandom, plus RandomGeneratorFactory to pick algorithms such as the new LXM family; it is not for security, which still needs SecureRandom.

Detailed explanation

Before Java 17 the random classes had no common type. Code written against java.util.Random could not easily switch to SplittableRandom, and each class duplicated methods like nextInt(bound) or doubles().

JEP 356, Enhanced Pseudo-Random Number Generators, introduced:

  • RandomGenerator: a common interface with nextInt, nextLong, nextDouble, nextGaussian, bounded versions, and streams like ints(). Existing classes now implement it, so you can write methods that accept any generator.
  • Sub-interfaces for special abilities: SplittableGenerator (split into an independent generator, good for fork/join and parallel streams), JumpableGenerator and LeapableGenerator (jump far ahead in the sequence to create non-overlapping streams), and StreamableGenerator.
  • RandomGeneratorFactory: discover and create algorithms by name, for example RandomGenerator.of("L64X128MixRandom") or RandomGeneratorFactory.all() to list them with properties like period and state size.
  • New LXM algorithms (combining an LCG with an xor-based generator), such as L32X64MixRandom, L64X128MixRandom and L128X256MixRandom, plus Xoshiro and Xoroshiro variants. They are fast, have good statistical quality and are splittable. RandomGenerator.getDefault() currently returns L32X64MixRandom.

All of these are pseudo-random: deterministic from the seed and predictable. For tokens, passwords, session ids or keys use SecureRandom. For ordinary concurrent code, ThreadLocalRandom.current() avoids contention on a shared Random.

How it works

  1. Choose an algorithm by name or use getDefault().
  2. Program against RandomGenerator rather than a concrete class.
  3. For parallel work, split or jump to get independent streams per task.
  4. Use SecureRandom whenever unpredictability matters.

Example

RandomGenerator gen = RandomGenerator.of("L64X128MixRandom");
int dice = gen.nextInt(1, 7);           // 1..6

RandomGeneratorFactory.all()
    .forEach(f -> System.out.println(f.name() + " period=2^" + f.period().bitLength()));

// Parallel simulation with independent streams
var root = (RandomGenerator.SplittableGenerator)
        RandomGeneratorFactory.of("L64X128MixRandom").create(42);
double avg = root.splits(1_000)
        .parallel()
        .mapToDouble(r -> simulate(r))
        .average().orElse(0);

// Security: never the above
String token = HexFormat.of().formatHex(SecureRandom.getInstanceStrong().generateSeed(16));

Common mistakes

  • Using Random or LXM generators for security tokens.
  • Sharing one Random across many threads (contention).
  • Hard-coding an algorithm name not available on all JDKs without handling the exception.
  • Reusing the same seed in all parallel tasks.

How to answer in the interview

"Java 17, through JEP 356, unified random number generation with the RandomGenerator interface in java.util.random. Random, SplittableRandom, ThreadLocalRandom and SecureRandom all implement it, so my code can depend on the interface and swap algorithms. RandomGeneratorFactory lets me pick algorithms by name, like the new fast LXM family, L64X128MixRandom for example. There are splittable and jumpable sub-interfaces that give independent streams for parallel simulations. They're still pseudo-random and predictable, so for tokens or keys I always use SecureRandom, and in multithreaded code ThreadLocalRandom."

Likely follow-up questions

  • Why should ThreadLocalRandom be preferred over a shared Random in multithreaded code? Random uses an atomic seed that threads contend on; ThreadLocalRandom has per-thread state.
  • What does splittable mean? Creating a new, statistically independent generator from an existing one.
  • Is SecureRandom slower? Usually yes, and it may block when strong entropy is requested.
