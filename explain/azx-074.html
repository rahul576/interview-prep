How do you reduce AKS costs?

Azure Kubernetes (AKS) · concept · levels mid, senior

In one line

Reduce AKS cost by rightsizing requests so node auto provisioning or the autoscaler can shrink nodes, using spot for tolerant workloads, stopping non-production clusters, covering the baseline with reservations or savings plans, choosing efficient VM families such as Arm-based Cobalt, and making cost visible with the cost analysis add-on.

Detailed explanation

Kubernetes bills you for nodes, but the scheduler places pods by requests. If pods request 2 CPUs and use 0.2, the cluster looks full while nodes sit idle. So rightsizing requests is usually the biggest lever: compare requests with actual usage from Prometheus or Container Insights, adjust them (the Vertical Pod Autoscaler in recommendation mode helps), and let node auto provisioning consolidate onto fewer, better-fitting nodes, or let the cluster autoscaler scale down. HPA keeps replica counts tied to load.

Spot node pools offer large discounts on spare capacity, but VMs can be evicted at short notice. They fit batch jobs, CI agents and stateless services with several replicas spread across pools. AKS taints spot nodes, so only workloads with the matching toleration land there.

Non-production clusters can be stopped outside working hours with az aks stop, which deallocates nodes and the control plane, then az aks start in the morning. Reservations or an Azure savings plan cover always-on baseline capacity at a discount. Arm-based VMs like Cobalt 100 offer good price-performance for compatible (multi-arch) images.

Visibility drives behaviour: the AKS cost analysis add-on, based on OpenCost, splits cost by namespace and workload in Cost Management, so teams see their own impact. Do not forget hidden costs: log ingestion, unattached disks, public IPs, load balancers and oversized system pools.

How it works

  1. Measure requests vs usage per workload.
  2. Rightsize, enable HPA, and let NAP or autoscaler consolidate.
  3. Move tolerant workloads to spot with on-demand fallback.
  4. Schedule stop/start for dev and test.
  5. Buy reservations for the stable baseline.
  6. Show cost per namespace to teams monthly.

Example

az aks nodepool add -g rg-apps --cluster-name aks-prod -n spotpool \
  --priority Spot --eviction-policy Delete --spot-max-price -1 \
  --enable-cluster-autoscaler --min-count 0 --max-count 20

az aks update -g rg-apps -n aks-prod --enable-cost-analysis
az aks stop -g rg-dev -n aks-dev     # evening
az aks start -g rg-dev -n aks-dev    # morning

Common mistakes

  • Setting requests from guesses and never revisiting them.
  • Running stateful or single-replica services on spot.
  • Buying reservations before rightsizing.
  • Ignoring Log Analytics ingestion, which can exceed compute cost.

How to answer in the interview

"The biggest lever is rightsizing: pods often request far more than they use, so I compare requests with real usage, adjust them, and let node auto provisioning or the autoscaler shrink the cluster. Fault-tolerant workloads go on spot pools. Non-production clusters are stopped at night with az aks stop. Always-on baseline capacity is covered with reservations or savings plans, and Arm-based Cobalt VMs help for compatible workloads. The cost analysis add-on shows cost per namespace so teams own their spend, and I also tune log volume."

Likely follow-up questions

  • Risks of stopping clusters nightly? Start-up time, failed starts on capacity, missed scheduled jobs and expiring things like certificates or tokens.
  • How do you handle spot evictions? Multiple replicas, PDBs, on-demand fallback and graceful shutdown.
  • Which metric shows waste? The gap between requested and used CPU and memory per namespace.
