How do you evaluate a public module from the Terraform registry before using it in production?

Terraform · concept · levels mid, senior

In one line

Treat a public module like any third-party dependency: check the maintainer and activity, read the code and its security defaults, judge inputs, outputs and versioning discipline, assess license and supply-chain risk, then pin exact versions or mirror/fork it into your internal registry.

Detailed explanation

A registry module runs with your cloud credentials and creates resources in your production accounts. A careless or compromised module can open networks, create IAM backdoors or simply be abandoned. So evaluate before adopting.

Maintainer and health. Is it from a verified partner, the cloud vendor (for example Azure Verified Modules or the AWS-IA modules) or a well-known community project such as terraform-aws-modules? Look at release frequency, open issues and how quickly pull requests are handled, number of downloads, and whether it keeps up with provider major versions.

Read the code. Documentation can understate what a module creates. Look for hidden resources, local-exec provisioners, external data sources that run scripts, and security defaults: encryption on, public access off, logging enabled, IAM scoped to least privilege. A module whose defaults are insecure will eventually be used with those defaults.

Interface fit. Do the inputs and outputs fit your needs without hacks, such as passing raw JSON or using count tricks? Are variables typed and validated? Does it follow semantic versioning with a changelog and upgrade notes, including moved blocks for refactors?

License and supply chain. Check the license is acceptable. Registry versions point to Git tags, and tags can be moved; pin an exact version and consider verifying the commit. For critical modules, mirror or fork into your private registry, so availability and contents are under your control, and upgrades are reviewed diffs.

Wrap if needed. A thin internal wrapper can enforce naming, tagging and policy while reusing the public module.

How it works

  1. Shortlist modules; check maintainer, activity and adoption.
  2. Read the source: resources created, provisioners, defaults.
  3. Test it in a sandbox with terraform test or an example.
  4. Check license and versioning practice.
  5. Pin an exact version or mirror into the internal registry.
  6. Review every upgrade diff before bumping.

Example

module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "5.13.0"   # exact pin; upgrades via reviewed PRs (illustrative version)

  name            = "orders-prod"
  cidr            = "10.20.0.0/16"
  azs             = ["eu-west-1a", "eu-west-1b", "eu-west-1c"]
  private_subnets = ["10.20.1.0/24", "10.20.2.0/24", "10.20.3.0/24"]
  enable_flow_log = true
}
checkov -d .terraform/modules/vpc     # scan the downloaded module code

Common mistakes

  • Using floating versions or no version constraint at all.
  • Trusting the README without reading the code.
  • Adopting a module with hundreds of variables for a simple need.
  • Not reviewing upgrade diffs.

How to answer in the interview

"I treat a public module like any third-party dependency. First the maintainer: verified partner or known organisation, recent releases, how issues and PRs are handled and adoption. Then I read the code, because it may create more than documented, and check security defaults: encryption, public access, logging and IAM scope. I check whether inputs and outputs fit and whether it follows semantic versioning with changelogs. I check the license and supply-chain risk, since it runs with our credentials. In production I pin an exact version, review upgrades, and mirror or fork critical modules into our internal registry."

Likely follow-up questions

  • Red flags? Provisioners running scripts, insecure defaults, no releases in a year, no tests.
  • Why mirror? Control over availability and contents; immune to moved tags or deleted repos.
  • How do you scan modules? Run Checkov or Trivy over the module code and over plans using it.
