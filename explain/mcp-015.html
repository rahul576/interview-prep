What happened to the original HTTP+SSE transport in MCP?

MCP Servers · concept · levels mid, senior

In one line

The original HTTP+SSE transport (2024-11-05) used two endpoints, a long-lived SSE stream for server messages plus a POST endpoint for client messages; it was hard to scale and proxy, so 2025-03-26 replaced it with Streamable HTTP, where SSE survives only as an optional response format.

Detailed explanation

The first MCP specification, 2024-11-05, defined two transports: stdio and HTTP with Server-Sent Events. With HTTP+SSE, the client first opened a GET request to an SSE endpoint and kept that connection open indefinitely. The server's first event told the client the URL of a second endpoint, and the client then sent all its messages as POST requests to that URL. Responses did not come back on the POST; they arrived asynchronously on the long-lived SSE stream.

This design had practical problems:

  • Persistent connections per client, limiting scale.
  • Sticky routing: the POST and the SSE stream had to reach the same instance.
  • Proxies and load balancers often buffer or time out long-lived streams.
  • Serverless platforms fitted poorly, and dropped streams could not be resumed cleanly.

The 2025-03-26 revision replaced it with Streamable HTTP: a single endpoint where each client message is a POST, and the server decides per request whether to return a plain JSON response or to stream that request's messages over SSE. A simple server can be completely request/response, scale like any HTTP API and run on serverless platforms.

So SSE still exists, but only as a response format within Streamable HTTP, not as a standalone transport. The old transport is deprecated: new servers should implement Streamable HTTP. Clients that must talk to legacy servers can keep fallback support: the specification describes trying a POST to the URL first and, if that fails with an error like 404 or 405, falling back to a GET expecting the old SSE handshake.

How it works

  1. Old: GET /sse → stream opens → server sends endpoint event → client POSTs to /messages → responses arrive on stream.
  2. New: POST /mcp with JSON-RPC → server returns JSON or an SSE stream for that request.
  3. Compatibility: client tries Streamable HTTP; on failure, falls back to legacy SSE.
  4. Servers may host both temporarily for old clients.

Example

Legacy (2024-11-05)
  GET  /sse                 -> event: endpoint  data: /messages?sessionId=abc
  POST /messages?sessionId=abc  {"id":1,"method":"tools/list"}   -> 202 Accepted
  (response arrives later on the /sse stream)

Streamable HTTP (2025-03-26+)
  POST /mcp {"id":1,"method":"tools/list"}  -> 200 application/json {"id":1,"result":{...}}

Common mistakes

  • Building new servers with the deprecated SSE transport from old tutorials.
  • Thinking "SSE is gone" and not supporting streamed responses at all.
  • Forgetting to disable proxy buffering for SSE responses.
  • Dropping legacy support in clients before important servers have migrated.

How to answer in the interview

"The first spec, 2024-11-05, had an HTTP+SSE transport with two endpoints: the client kept a long-lived SSE stream open to receive messages and posted its own messages to a second endpoint. That meant a persistent connection per client, sticky routing, trouble with proxies and load balancers, and a poor fit for serverless. The 2025-03-26 revision replaced it with Streamable HTTP: one endpoint, each message is a POST, and the server chooses per request to reply with JSON or stream with SSE. So SSE survives only as a response format. The old transport is deprecated; new servers should use Streamable HTTP, and clients can keep a fallback for old servers."

Likely follow-up questions

  • Client compatibility strategy? Try POST first; on 4xx fall back to legacy GET/SSE; log which servers still need it.
  • Why not WebSockets? They need more infrastructure support and do not fit plain request/response or serverless well.
  • How do you migrate a server? Serve both endpoints during transition, then remove the legacy one.
