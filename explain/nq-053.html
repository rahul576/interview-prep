Given a list of product objects, how would you implement multiple filtering, transformation, sorting, and aggregation operations using streams?

Coding Exercises · scenario · levels mid, senior

In one line

Model products as an immutable record, then write one clear stream pipeline per requirement: filter for conditions, map for transformations, sorted(Comparator.comparing(...)) for ordering, and Collectors like groupingBy, summingDouble and maxBy for aggregation, leaving the source list unchanged.

Detailed explanation

This is a classic live-coding exercise. Interviewers look for clean modelling, correct use of the Stream API, readable pipelines and good communication.

Model. Start with record Product(String name, String category, double price, int stock). Records are immutable, give you accessors, equals, hashCode and toString, and make transformations naturally produce new objects. Mention that real money code would use BigDecimal.

One pipeline per question. A single 15-step chain answering everything is hard to read and debug. Separate, named results are clearer:

  • Filter: filter(p -> p.stock() < 10) keeps low-stock products.
  • Transform: map(p -> p.withPrice(p.price() * 0.85)) creates discounted copies; map(Product::name).map(String::toUpperCase) gives upper-case names.
  • Sort: sorted(Comparator.comparing(Product::name)), with thenComparing for ties.
  • Aggregate: collect(groupingBy(Product::category)) for groups, groupingBy(Product::category, summingDouble(Product::price)) for totals, max(comparingDouble(Product::price)) for the most expensive item.

Principles. Streams are lazy and do not modify their source; terminal operations like toList() or collect produce new results. Keep lambdas free of side effects, prefer method references when they read well, and handle Optional results from max and min.

Communication. Talk through each step, state assumptions (is "total price" unit prices or stock value?), and finish by running the code on a few sample products or writing a quick test.

How it works

  1. Define the record and sample data.
  2. For each requirement, write a separate pipeline.
  3. Use intermediate operations: filter, map, sorted.
  4. Finish with a terminal operation: toList, collect, max.
  5. Print or assert the results.

Example

record Product(String name, String category, double price, int stock) {
    Product withPrice(double p) { return new Product(name, category, p, stock); }
}

List<Product> products = List.of(
    new Product("Laptop", "Electronics", 1200, 5),
    new Product("Phone", "Electronics", 800, 15),
    new Product("Desk", "Furniture", 300, 8));

List<Product> lowStock = products.stream().filter(p -> p.stock() < 10).toList();

List<Product> discounted = products.stream()
    .filter(p -> p.category().equals("Electronics"))
    .map(p -> p.withPrice(p.price() * 0.85)).toList();

List<Product> byName = products.stream()
    .sorted(Comparator.comparing(Product::name)).toList();

Map<String, Double> totals = products.stream()
    .collect(Collectors.groupingBy(Product::category, Collectors.summingDouble(Product::price)));

Optional<Product> priciest = products.stream()
    .max(Comparator.comparingDouble(Product::price));

Common mistakes

  • One giant pipeline answering several questions.
  • Mutating objects inside map or adding to external lists in forEach.
  • Calling get() on the Optional from max without handling empty.
  • Using double for money without mentioning BigDecimal.

How to answer in the interview

"I'd start with an immutable model, a record Product with name, category, price and stock, and a sample list. Then I'd write one clear pipeline per requirement rather than one huge chain. Filtering uses filter with a predicate like stock below ten. Transformations use map, for example creating discounted copies or upper-case names with method references. Sorting uses sorted with Comparator.comparing. Aggregation uses collectors: groupingBy category, with summingDouble for totals, and max with comparingDouble for the most expensive product. I'd talk through each step, keep the source list unchanged, and test with a few products."

Likely follow-up questions

  • How would you test these pipelines? JUnit tests with small fixed lists and assertions on exact results, including empty lists.
  • Why records? Immutable, concise, with value semantics.
  • When would you use a loop instead? When logic has complex early exits or checked exceptions, or readability suffers.
