Why should a pipeline save the plan with -out and apply that plan file?

Terraform · concept · levels entry, mid, senior

In one line

terraform plan -out=tfplan saves the exact reviewed changes, and terraform apply tfplan applies precisely those, so the pipeline never applies something different from what was approved; Terraform refuses a stale plan, and the file must be protected because it contains sensitive values.

Detailed explanation

Without a saved plan, terraform apply runs a new plan at apply time and applies that. In a pipeline with an approval step, time passes between the plan reviewers saw and the apply: someone may merge another change, a data source may return a new AMI, an object may drift, or a module version range may resolve differently. The apply could then do something nobody reviewed, such as replacing a database. In interactive use, Terraform asks for confirmation, but in CI people use -auto-approve, which removes that protection.

A saved plan file is a binary snapshot of the proposed changes, plus the configuration, variable values and the state version it was computed from. terraform apply tfplan does not ask for approval and does not re-plan; it applies exactly that set of actions. If the state changed after the plan was created, for example because another run applied in between, Terraform reports that the saved plan is stale and refuses. That is the desired, safe outcome: you plan again and review again.

Because the plan file contains variable values and planned attribute values, including sensitive ones that are only redacted in the human-readable output, it must be treated as a secret: stored as a short-lived, access-restricted pipeline artifact, never committed or posted. The apply job must also run with the same Terraform version, providers (lock file) and working directory. A human-readable summary for the pull request comes from terraform show tfplan or terraform show -json tfplan for policy checks.

How it works

  1. CI runs terraform plan -out=tfplan.
  2. terraform show output is posted to the PR; policy tools scan the JSON.
  3. Plan file is uploaded as a protected artifact.
  4. A reviewer approves in the pipeline environment.
  5. Apply job downloads the artifact and runs terraform apply tfplan.
  6. If stale, the pipeline re-plans and requires approval again.

Example

plan:
  script:
    - terraform init -input=false
    - terraform plan -input=false -out=tfplan
    - terraform show -no-color tfplan > plan.txt
  artifacts:
    paths: [tfplan, plan.txt, .terraform.lock.hcl]
    expire_in: 1 day

apply:
  needs: [plan]
  when: manual
  environment: production
  script:
    - terraform init -input=false
    - terraform apply -input=false tfplan

Common mistakes

  • terraform apply -auto-approve after a separate plan job.
  • Publishing plan files as public artifacts.
  • Different Terraform or provider versions in plan and apply jobs.
  • Keeping approved plans for days and expecting them to apply.

How to answer in the interview

"terraform plan -out saves the exact set of changes, and terraform apply with that file applies precisely that plan without re-planning. In a pipeline it guarantees that what reviewers approved is exactly what gets applied. Without it, apply re-plans and might do something different if code, infrastructure or a data source changed meanwhile. If the state changed after the plan was saved, Terraform detects the plan is stale and refuses, which is safe. The plan file contains sensitive values, so it's a protected, short-lived artifact. The flow is plan, post the summary to the PR, manual approval, then apply the saved plan."

Likely follow-up questions

  • How long is a saved plan valid? Until state changes; in practice hours, and re-plan if approval took longer.
  • Can you inspect a plan file? terraform show tfplan or -json for tools like OPA.
  • Does HCP Terraform do this? Yes, runs plan, wait for confirmation, and apply the same plan.
