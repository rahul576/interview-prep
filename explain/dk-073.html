How do you run Docker containers securely on a production host?

Docker · concept · levels senior

In one line

Secure production Docker hosts in layers: a minimal, patched host OS checked against the CIS Docker Benchmark, a locked-down daemon (no unauthenticated TCP, rootless or userns-remap, log limits, live-restore), hardened containers (non-root, read-only, dropped capabilities, seccomp, limits), only signed and scanned images, and centralised logs plus runtime detection such as Falco.

Detailed explanation

Containers share the host kernel, so the host is part of the security boundary. Start with a minimal OS (a container-optimised distribution or a stripped-down Linux), automatic patching, SSH restricted or replaced with SSM-style access, and a regular check against the CIS Docker Benchmark using docker-bench-security.

The Docker daemon runs as root and controls everything, so access to it equals root on the host. Never expose its API over TCP without mutual TLS, restrict the docker group, and never mount /var/run/docker.sock into application containers. Rootless mode or user namespace remapping means root in a container maps to an unprivileged user on the host. Set default log rotation, live-restore so containers survive daemon restarts, and no-new-privileges as a default.

Each container runs as a non-root user, with a read-only root filesystem, --cap-drop ALL plus only what is needed, the default seccomp and AppArmor/SELinux profiles, and memory, CPU and PID limits to contain abuse and fork bombs. Never use --privileged or host namespaces for apps.

Supply chain: deploy only images from the private registry that are scanned and signed (cosign), verified before running. Detection: ship host and container logs centrally, audit Docker API calls, and run Falco to alert on suspicious behaviour like shells spawning in containers or writes to /etc.

How it works

  1. Build hosts from a hardened image; patch automatically.
  2. Configure daemon.json (userns or rootless, logs, live-restore, no-new-privileges).
  3. Run containers with a hardened default profile.
  4. Admit only signed, scanned images.
  5. Monitor with central logging, auditd and Falco; rescan regularly.

Example

{
  "userns-remap": "default",
  "live-restore": true,
  "no-new-privileges": true,
  "icc": false,
  "log-driver": "json-file",
  "log-opts": { "max-size": "50m", "max-file": "3" }
}
docker run -d --user 10001 --read-only --cap-drop ALL \
  --security-opt no-new-privileges --pids-limit 200 \
  --memory 512m --cpus 1 registry.example.com/api@sha256:3f1c...

Common mistakes

  • Exposing the daemon on port 2375 without TLS.
  • Mounting the Docker socket into CI or monitoring containers without understanding it is root access.
  • Hardening images but leaving the host unpatched.
  • No runtime monitoring, so a breach goes unnoticed.

How to answer in the interview

"I think of it in layers. The host is minimal, patched and checked against the CIS Docker benchmark with docker-bench-security. The daemon is never exposed over TCP without mutual TLS, uses rootless mode or user namespace remapping, and has log rotation and live-restore. Containers run as non-root with read-only filesystems, dropped capabilities, no-new-privileges, the default seccomp profile and resource limits, and never privileged or with the Docker socket. Only signed, scanned images from our private registry are allowed. Finally, logs are centralised and Falco watches for suspicious behaviour like a shell starting in a container."

Likely follow-up questions

  • What does the CIS Docker Benchmark check? Host config, daemon settings, file permissions, image and container runtime settings, and operations.
  • Rootless vs userns-remap? Rootless runs the whole daemon unprivileged; userns-remap keeps a root daemon but maps container root to a high UID.
  • Why is the Docker socket dangerous? Whoever can talk to it can start a privileged container mounting the host filesystem.
