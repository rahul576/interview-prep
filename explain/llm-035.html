How do you handle PDFs, tables, scanned documents and images in a RAG pipeline?

LLMOps & RAG · concept · levels mid, senior

In one line

Use layout-aware parsing that preserves reading order, headings and tables; OCR scanned pages; convert tables to Markdown or self-contained rows with headers; turn images and charts into text via vision models or use multimodal embeddings; keep headings and page numbers as metadata; and evaluate parsing quality on real samples.

Detailed explanation

Retrieval can only be as good as the text it indexes. Naive PDF extraction reads multi-column layouts across columns, mixes headers and footers into every page, and turns tables into number soup. Those errors propagate into embeddings, retrieval and finally answers.

Layout-aware parsers detect blocks, reading order, headings, lists and tables. Managed options include Azure AI Document Intelligence (layout model), Amazon Textract and Google Document AI; open-source options include Unstructured, Docling and similar libraries. Output as Markdown with heading levels preserved works well because chunkers can then split on structure.

Scanned documents need OCR first; most of the services above include it. Check confidence scores and handwriting support for forms.

Tables need special care. Small tables can stay as Markdown tables inside one chunk. Large tables are better split into rows, each repeating the column headers ("Plan: Gold; Region: EU; Price: 40 EUR"), so a single chunk is meaningful alone. Very large or numeric tables often belong in a database queried by a tool (text-to-SQL) rather than in a vector index.

Images, diagrams and charts can be captioned by a vision-capable model into searchable text, or embedded with a multimodal embedding model. Alternatively, store the page image and pass it directly to a multimodal LLM at answer time.

How it works

  1. Detect file type and whether the PDF has a text layer.
  2. OCR pages without text; run layout analysis on all.
  3. Emit structured Markdown: headings, paragraphs, tables, figure placeholders.
  4. Caption figures with a vision model; process tables into rows or Markdown.
  5. Chunk by section, attaching title, section path and page numbers.
  6. Spot-check a sample of documents and measure retrieval on them.

Example

from docling.document_converter import DocumentConverter

result = DocumentConverter().convert("policy.pdf")
md = result.document.export_to_markdown()   # headings and tables preserved
for section in split_by_headings(md):
    index_chunk(text=section.text,
                meta={"source": "policy.pdf", "section": section.path, "page": section.page})

Common mistakes

  • Using plain text extraction and never looking at the output.
  • Splitting tables across chunks without headers.
  • Dropping page numbers, which breaks citations.
  • Ignoring figures that contain the actual answer (process diagrams, charts).

How to answer in the interview

"I'd use a layout-aware parser such as Azure Document Intelligence, Textract or Docling, which keeps reading order, headings and tables, with OCR for scanned pages. Tables become Markdown or rows that repeat their headers so each chunk stands alone; huge tables go into a database behind a tool. Figures get captions from a vision model or multimodal embeddings. I keep headings and page numbers as metadata for context and citations. And I manually check parsing on a sample of real documents, because errors here poison everything downstream."

Likely follow-up questions

  • When send the page image directly? Complex visual layouts, forms or charts where parsing loses meaning and volume is low.
  • How to measure parsing quality? Compare with hand-labelled pages; track retrieval recall on table and figure questions.
  • Headers and footers? Detect repeated lines across pages and strip them.
