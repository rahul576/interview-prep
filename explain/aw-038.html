When would you choose a Network Load Balancer over an Application Load Balancer?

Cloud (AWS) · concept · levels mid

In one line

Choose a Network Load Balancer for layer 4 traffic (TCP, UDP, TLS), extreme throughput and low latency, static IPs per AZ, client source IP preservation and PrivateLink; choose an ALB when you need HTTP-aware features like path routing, WAF and built-in authentication.

Detailed explanation

An NLB forwards connections or datagrams without parsing HTTP. It is built on AWS Hyperplane, scales to millions of requests per second without pre-warming and adds very little latency. That makes it the right choice for protocols an ALB cannot handle: MQTT, game servers over UDP, SMTP, database protocols, custom TCP, or end-to-end encrypted gRPC passthrough when you do not want the load balancer to terminate TLS.

The NLB has one static IP per availability zone, and you can assign your own Elastic IPs, which matters when customers must whitelist addresses in firewalls. An ALB's IPs change over time, so it can only be referenced by DNS name. With instance targets, and with IP targets when enabled, an NLB preserves the client source IP, so the backend sees the real caller; for other cases it supports Proxy Protocol v2. An ALB instead passes the client address in X-Forwarded-For.

Exposing a service to other VPCs or accounts with AWS PrivateLink (an endpoint service) requires an NLB in front of it (Gateway Load Balancers serve the appliance case). NLBs now support security groups too, though historically they did not.

The ALB remains the better choice for web applications: host and path routing, header and query-string rules, redirects and fixed responses, AWS WAF integration, OIDC/Cognito authentication, HTTP/2 and gRPC routing, and rich HTTP metrics and access logs.

How it works

  1. Identify the protocol: anything not HTTP/HTTPS points to an NLB.
  2. Check networking needs: static IPs, source IP visibility, PrivateLink.
  3. Check scale and latency needs: sudden huge spikes favour NLB.
  4. Check application needs: routing rules, WAF, authentication favour ALB.
  5. If you need both, chain them: NLB in front with an ALB-type target group.

Example

An NLB with fixed Elastic IPs in front of an ALB, so partners get stable IPs while the app keeps ALB routing:

aws elbv2 create-load-balancer --name edge-nlb --type network \
  --subnet-mappings SubnetId=subnet-a,AllocationId=eipalloc-1 \
                    SubnetId=subnet-b,AllocationId=eipalloc-2

aws elbv2 create-target-group --name to-alb --target-type alb \
  --protocol TCP --port 443 --vpc-id vpc-123
aws elbv2 register-targets --target-group-arn $TG --targets Id=$ALB_ARN

Common mistakes

  • Using an NLB for a web app and then rebuilding routing and auth in every service.
  • Forgetting that client IP preservation changes which security group rules the targets need.
  • Assuming the ALB has fixed IPs and hard-coding them in firewalls.
  • Ignoring cross-zone load balancing, which is off by default on NLBs.

How to answer in the interview

"I reach for an NLB when the traffic is not HTTP, like MQTT, UDP game traffic or databases, when I need extreme throughput with minimal latency, when clients need static or Elastic IPs to whitelist, when the backend must see the original source IP, and when I publish a service over PrivateLink, which needs an NLB. For normal web apps I prefer an ALB because of host and path routing, WAF, authentication and HTTP metrics. If I need both, I put an NLB in front of an ALB using an ALB target group."

Likely follow-up questions

  • How would you combine an NLB in front of an ALB, and why? Use an ALB-type target group on the NLB to get static IPs or PrivateLink while keeping layer 7 routing.
  • Does an NLB terminate TLS? It can with a TLS listener and ACM certificate, or pass TLS through untouched with TCP.
  • What does cross-zone load balancing change? Traffic is spread evenly over all targets across AZs, possibly adding inter-AZ data charges.
