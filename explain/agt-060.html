An auto-remediation rule kept restarting pods of a service and turned a small issue into a full outage. How do you fix the design?

AI Agents & AIOps · scenario · levels mid, senior

In one line

The restarts removed capacity and caused a cascading failure while the real cause (for example a slow dependency) was not fixable by restart; fix the design with rate limits and maximum attempts, a circuit breaker that escalates, blast radius limits respecting PDBs, verification before repeating, and dependency checks first.

Detailed explanation

The rule mapped a symptom, failing health checks, to an action, restart. But the underlying cause was shared: perhaps a slow database or an exhausted downstream API. Restarting pods cannot fix that. Worse, each restart removed a pod from service and added startup load (JVM warm-up, cache filling, connection storms), so remaining pods received more traffic, became slower, failed their checks and were restarted as well. That is a positive feedback loop: the automation amplified the incident into a full outage.

The redesign adds guardrails at several levels. Rate limits and maximum attempts: at most N restarts per service per time window. Circuit breaker: if the same remediation has not helped after a few attempts, or if many instances fail at once, automation stops and escalates to a human. Blast radius: restart one or a few pods at a time, honouring PodDisruptionBudgets and a minimum healthy capacity threshold. Verification: after each action, check whether error rates or health improved before doing anything more.

Most importantly, add diagnosis before action: if failures are widespread across instances, the cause is usually shared, and restarts make things worse. The rule should check dependency health and recent changes first. Liveness probes should also not depend on downstream services, which is a common root of this pattern.

How it works

  1. Alert triggers remediation evaluation, not immediate action.
  2. Check scope: one pod failing or many? Dependencies healthy?
  3. If widespread or dependency unhealthy: do not restart; page.
  4. Otherwise restart one pod within rate and PDB limits.
  5. Verify improvement within a window.
  6. Repeat only on success; open the breaker after failures.

Example

remediation: restart-unhealthy-pod
preconditions:
  failing_pods_ratio: "< 0.2"          # widespread = shared cause
  dependencies_healthy: [orders-db, payments-api]
  no_recent_deploy_within: 15m
limits:
  max_concurrent: 1
  max_per_hour: 3
  respect_pdb: true
  min_available_ratio: 0.8
verify: { metric: pod_ready_and_error_rate_ok, within: 5m }
circuit_breaker: { failures: 2, open_for: 2h, on_open: page_owner }

Also move dependency checks out of liveness probes into readiness probes.

Common mistakes

  • Restarting on symptoms without checking scope.
  • Liveness probes that call the database.
  • No limit on concurrent or total restarts.
  • Not testing remediation under realistic failure conditions.

How to answer in the interview

"The rule treated a symptom with a restart, but the cause was shared, like a slow database, so restarting couldn't help. Each restart removed capacity and added startup load, so the rest failed too: a cascade. I'd add rate limits and a maximum number of attempts, a circuit breaker that stops and escalates after repeated failures or when many instances are affected, blast radius limits of one or two pods respecting PodDisruptionBudgets, and verification before repeating. And the rule checks dependencies first, because widespread failures almost always mean restarts will make it worse."

Likely follow-up questions

  • Test remediation rules? Chaos experiments in staging, dry-run mode in production.
  • Liveness vs readiness? Liveness for deadlocks only; readiness can consider dependencies.
  • Who gets paged when the breaker opens? The service owner, with automation history attached.
