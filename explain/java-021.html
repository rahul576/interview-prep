How do you choose and tune a garbage collector for a latency-sensitive service?

JVM & Performance · concept · levels senior, lead

In one line

Start from the goal (throughput or tail latency): G1 is the balanced default with a pause target, ZGC or Shenandoah give millisecond-level pauses on large heaps at some CPU cost, Parallel maximises throughput; size the heap deliberately, then measure with GC logs and JFR and often reduce allocation rather than adding flags.

Detailed explanation

Define the SLO first. "p99 under 50 ms" and "process the nightly batch fastest" lead to different collectors. GC pauses add directly to request latency, so for a latency-sensitive API the relevant numbers are pause duration distribution and how often pauses hit p99/p999.

Collectors.

  • G1 (default since Java 9): region-based, mostly concurrent marking, evacuation pauses sized to -XX:MaxGCPauseMillis (default 200 ms). Good for most services with heaps from a few GB to tens of GB. Lowering the target to around 50-100 ms is common; too low causes more frequent collections and lower throughput.
  • ZGC: concurrent marking, relocation and compaction using coloured pointers and load barriers; pauses typically well under a millisecond and independent of heap size, up to terabyte heaps. Generational ZGC arrived in Java 21 (-XX:+UseZGC -XX:+ZGenerational) and became the only mode in later releases, so on current JDKs -XX:+UseZGC is generational. Costs: more CPU for barriers and concurrent work, and it needs heap headroom.
  • Shenandoah: also concurrent compaction with low pauses, available in OpenJDK builds from Red Hat and others.
  • Parallel GC: highest throughput, long pauses; batch jobs.

Heap sizing. Set -Xms equal to -Xmx to avoid resize pauses and surprises, or in containers use -XX:MaxRAMPercentage (often 60-75%), leaving room for Metaspace, threads, direct buffers and the code cache. Concurrent collectors need headroom: if allocation outpaces concurrent collection you get allocation stalls (ZGC) or full GCs (G1).

Measure. Enable unified logging -Xlog:gc*, record with JFR and inspect in JDK Mission Control, use jstat for live views. Look at allocation rate, promotion rate, pause times, concurrent cycle frequency and humongous allocations. Load-test with realistic traffic.

Biggest win. Lower allocation in hot paths (logging, JSON, boxing, copies). Less garbage means fewer and shorter collections with any collector.

How it works

  1. Write down the latency or throughput target.
  2. Pick the collector: G1 default, ZGC for strict latency or large heaps, Parallel for batch.
  3. Size heap and container memory with headroom.
  4. Enable GC logging and JFR; run a realistic load test.
  5. Analyse pauses, allocation and promotion; change one setting at a time.
  6. Reduce allocation in the code; re-measure.

Example

# Latency-sensitive API on JDK 21+, 8 GB container
java -XX:+UseZGC \
     -XX:MaxRAMPercentage=70 \
     -Xlog:gc*,safepoint:file=/logs/gc.log:time,uptime:filecount=5,filesize=20m \
     -XX:StartFlightRecording=maxage=6h,filename=/logs/app.jfr \
     -jar api.jar

# G1 alternative with a tighter pause goal
java -XX:+UseG1GC -Xms6g -Xmx6g -XX:MaxGCPauseMillis=100 -jar api.jar

Common mistakes

  • Copying flag lists from blog posts without measuring.
  • Tuning many flags at once, so you cannot tell what helped.
  • Giving the heap the whole container limit, causing OOM kills.
  • Blaming GC for latency that is really database or lock contention.

How to answer in the interview

"First I define the goal: throughput or tail latency. G1 is the default and balances both with a pause target via MaxGCPauseMillis. For very low latency or large heaps I'd consider ZGC, generational since Java 21, or Shenandoah, which do almost all work concurrently and keep pauses around a millisecond or less, at some CPU cost. Parallel GC is for batch throughput. I size the heap with Xms equal to Xmx, or MaxRAMPercentage in containers, leaving room for native memory. Then I measure rather than guess, with GC logs, JFR and jstat, looking at allocation rate, pauses and promotion. Often the biggest win is reducing allocation in the code."

Likely follow-up questions

  • How do container memory limits interact with JVM heap settings? The JVM is container-aware; heap defaults to a percentage of the limit, and heap plus off-heap must stay below it or the pod is OOM-killed.
  • What is an allocation stall in ZGC? Threads wait because the heap filled before the concurrent cycle freed memory; give more headroom or reduce allocation.
  • When would you pick Parallel GC? For batch jobs where total runtime matters and pauses do not.
