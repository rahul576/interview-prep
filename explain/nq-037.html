What are the stages of a stream pipeline?

Java 8+ Features · concept · levels entry

In one line

A stream pipeline has three stages: a source (list.stream(), Arrays.stream, Stream.of, Files.lines), zero or more intermediate operations (filter, map, sorted) and exactly one terminal operation (collect, count, forEach); nothing runs until the terminal operation.

Detailed explanation

1. Source. Creates the stream and defines its characteristics, such as whether it is ordered, sized or sorted. Common sources: collection.stream() and parallelStream(); Arrays.stream(array); Stream.of(a, b, c); IntStream.range(0, n); Files.lines(path) and BufferedReader.lines(); String.chars(); Pattern.splitAsStream; Stream.iterate and Stream.generate (infinite); Stream.ofNullable (Java 9); map.entrySet().stream().

2. Intermediate operations. Each returns a new Stream and is lazy; calling it only adds a stage. Examples: filter, map, flatMap, mapToInt, distinct, sorted, peek, limit, skip, takeWhile, dropWhile, mapMulti. There can be any number, including zero (list.stream().count()).

3. Terminal operation. Exactly one, and it triggers execution. It produces a result (collect, toList, reduce, count, min, max, findFirst, anyMatch, toArray) or a side effect (forEach, forEachOrdered). After it, the stream is consumed and can't be reused.

When the terminal operation runs, the stages are linked into a chain and elements are pulled from the source and pushed through every stage one at a time, so no intermediate collections exist. Short-circuiting terminal or intermediate operations can stop the source early.

If you build a pipeline without a terminal operation, nothing happens at all: no filtering, no mapping, no side effects in peek. This surprises people who use peek or map for logging. Streams backed by I/O (e.g. Files.lines) should be closed with try-with-resources, which onClose handlers support.

How it works

  1. The source creates a Spliterator describing elements and characteristics.
  2. Each intermediate call wraps the previous pipeline stage.
  3. The terminal call builds a sink chain from the stages.
  4. The spliterator feeds elements into the chain until exhausted or short-circuited.
  5. The terminal operation returns its result; the stream is marked consumed.

Example

try (Stream<String> lines = Files.lines(Path.of("access.log"))) {    // 1. source
    Map<String, Long> hitsByIp = lines
        .filter(l -> l.contains(" 200 "))                             // 2. intermediate
        .map(l -> l.split(" ")[0])                                    //    intermediate
        .collect(Collectors.groupingBy(ip -> ip, Collectors.counting())); // 3. terminal
}

Stream<String> noTerminal = Stream.of("a", "b")
    .peek(s -> System.out.println("seen " + s));   // prints nothing: no terminal op

long evens = IntStream.rangeClosed(1, 100)       // source
    .filter(n -> n % 2 == 0)                      // intermediate
    .count();                                     // terminal -> 50

Common mistakes

  • Forgetting the terminal operation and wondering why nothing happens.
  • Calling two terminal operations on one stream.
  • Not closing I/O-based streams.
  • Thinking each intermediate operation loops over the whole data separately.

How to answer in the interview

"A stream pipeline has three parts. First a source that creates the stream: list.stream(), Arrays.stream, Stream.of, Files.lines or IntStream.range. Second, zero or more intermediate operations such as filter, map, flatMap, sorted, distinct and limit, each returning a new stream and being lazy. Third, exactly one terminal operation, like collect, forEach, reduce, count, findFirst or anyMatch, which triggers processing and produces a result or side effect. After that the stream is consumed and can't be reused. Without a terminal operation, nothing runs at all."

Likely follow-up questions

  • What happens if you build a pipeline without a terminal operation? Nothing executes, not even peek side effects.
  • Can a pipeline have zero intermediate operations? Yes, e.g. list.stream().count().
  • Why close Files.lines? It holds an open file handle.
