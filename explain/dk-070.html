What are the trade-offs of running stateful services such as databases in containers?

Docker · concept · levels senior

In one line

You can run databases in containers, but the container gives you packaging, not durability: data must live on persistent volumes, storage I/O and fsync performance matter, backups, upgrades, replication and failover are still your job, and resource limits must match the database config, which is why production often uses managed services or Kubernetes operators.

Detailed explanation

Containers were designed for stateless, disposable processes. A database is the opposite: its whole value is the data it keeps. Anything written to the container's writable layer disappears when the container is removed, so data must live on a volume or a PersistentVolume backed by durable storage.

Storage is the biggest trade-off. Databases call fsync constantly; local NVMe is fast, while network storage (NFS, some cloud disks) adds latency and may not honour fsync semantics correctly, risking corruption. Placement matters too: if the scheduler moves the container to another node, the storage must follow it.

Containers add no database operations for you. Backups and point-in-time recovery, major version upgrades, replication and failover, connection pooling and monitoring all still need designing. Resource limits are a classic trap: if PostgreSQL shared_buffers and work memory, or a JVM-based database heap, exceed the container memory limit, the kernel's OOM killer stops the database under load.

The sweet spot is clear. For local development, CI tests and ephemeral environments, containerised databases are perfect: fast, disposable and identical for everyone. In production, many teams choose managed services (Amazon RDS/Aurora, Azure Database for PostgreSQL, Cloud SQL), or run on Kubernetes with an operator such as CloudNativePG or the Percona and Strimzi operators that automate replication, failover and backups.

How it works

  1. Store data on a volume or PersistentVolume with a suitable StorageClass (SSD, correct fsync behaviour).
  2. Use a StatefulSet for stable identities and per-replica volumes.
  3. Set memory limits above the database's configured memory plus overhead; avoid aggressive CPU throttling.
  4. Automate backups to object storage and test restores regularly.
  5. Use replication with automated failover, usually via an operator.

Example

apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata: { name: orders-db }
spec:
  instances: 3
  storage: { size: 100Gi, storageClass: premium-ssd }
  resources:
    requests: { memory: 4Gi, cpu: "2" }
    limits: { memory: 4Gi }
  backup:
    barmanObjectStore:
      destinationPath: s3://backups/orders-db

Common mistakes

  • Keeping data in the container layer or an emptyDir.
  • Running a database on NFS without checking locking and fsync behaviour.
  • Memory limits smaller than the configured buffers.
  • Assuming "it's in Kubernetes" means it's highly available and backed up.

How to answer in the interview

"Containers are great for packaging, but they don't make a database durable or highly available. The data has to sit on persistent volumes with storage that performs well and honours fsync, and you still have to handle backups, point-in-time recovery, upgrades, replication and failover. Memory limits have to fit the database's own memory settings, or the OOM killer takes it down. I use containerised databases happily for development and CI. In production I'd prefer a managed service like RDS, or, if we run it ourselves on Kubernetes, an operator like CloudNativePG that automates replication, failover and backups."

Likely follow-up questions

  • What does an operator add over a StatefulSet? Domain knowledge: failover, replica management, backups, upgrades and config tuning as automated controllers.
  • Why is NFS risky for databases? Latency, weaker locking and fsync semantics, and risk of corruption.
  • When is self-hosting worth it? When you need versions, extensions or cost/control the managed service can't offer, and have the skills to operate it.
