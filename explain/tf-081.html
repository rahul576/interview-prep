Your hosted CI runners cannot reach private endpoints of databases and Key Vault that Terraform must configure. How do you solve it?

Terraform · scenario · levels mid, senior

In one line

Creating resources uses the public control plane, but some Terraform resources perform data plane operations (Key Vault secrets, storage containers, database users, Kubernetes objects) that require network reach to private endpoints; run Terraform on self-hosted runners or agents inside the VNet, never temporarily open public access, and separate control and data plane steps.

Detailed explanation

Azure Resource Manager and AWS control plane APIs are public endpoints authenticated by identity, so a hosted runner anywhere on the internet can create a Key Vault or a database server. But many resources call the service's own endpoint: azurerm_key_vault_secret talks to https://kv-name.vault.azure.net, storage containers and blobs use the storage account endpoint, PostgreSQL or SQL providers connect to the database to create users and grants, and the Kubernetes and Helm providers talk to the cluster API server. With private endpoints and public access disabled, those endpoints resolve to private IPs reachable only from inside the network. Hosted runners time out or get 403 Forbidden.

The proper fix is to run Terraform where the network is:

  • GitHub Actions self-hosted runners in the VNet, often autoscaled with Actions Runner Controller on Kubernetes, or GitHub-hosted runners with Azure private networking where available.
  • Azure DevOps Managed DevOps Pools with VNet injection, or VM scale set agents.
  • HCP Terraform agents deployed inside the network, which poll HCP Terraform outbound, so no inbound firewall openings are needed.

A tempting anti-pattern is a pipeline step that enables public network access or adds the runner's IP to the firewall, runs Terraform, and closes it again. It creates an exposure window and fails open if the pipeline crashes.

Architecturally, separate control plane and data plane into different states or stages. Creating the vault, network and cluster can run anywhere; only the data plane state (secrets, database roles, in-cluster resources) needs private runners.

How it works

  1. Identify resources that call data plane endpoints.
  2. Deploy runners or agents in a VNet with private DNS resolution.
  3. Give them a managed identity with only required permissions.
  4. Route data plane stages to the private runner pool.
  5. Keep control plane stages on hosted or private runners.
  6. Patch and monitor runners as production infrastructure.

Example

jobs:
  control-plane:
    runs-on: ubuntu-latest            # hosted: ARM only
    steps:
      - run: terraform -chdir=stacks/platform apply -auto-approve
  data-plane:
    needs: control-plane
    runs-on: [self-hosted, vnet-prod] # inside the VNet, private DNS
    steps:
      - run: terraform -chdir=stacks/secrets apply -auto-approve

Common mistakes

  • Opening public access during pipelines.
  • Self-hosted runners without private DNS links, so names still resolve publicly.
  • Shared, long-lived runners with broad credentials and no patching.
  • Mixing control and data plane in one large state.

How to answer in the interview

"Creating resources goes through the cloud control plane, which is reachable from anywhere, but resources like Key Vault secrets, storage containers, database users or Kubernetes objects use the data plane, and behind private endpoints that's only reachable from inside the network. The proper fix is running Terraform on runners inside the VNet: GitHub self-hosted runners, Azure DevOps Managed DevOps Pools, or HCP Terraform agents. I avoid temporarily opening public access in pipelines because that's a security gap. And I separate control plane and data plane into different states so only the data plane needs private runners."

Likely follow-up questions

  • How do you secure the runners? Ephemeral instances, hardened images, least-privilege identities, patching and network restrictions.
  • Why do agents need no inbound ports? They poll the service outbound.
  • What about DNS? Runners must use DNS linked to the private DNS zones.
