How would you design observability for a system with 200 microservices?

Scalability & Reliability · design · levels senior, lead

In one line

Observability for 200 services = metrics, structured logs and distributed traces, correlated by trace IDs, instrumented with OpenTelemetry, alerting on SLOs/symptoms, with sampling and retention to control cost.

Detailed explanation

At this scale, "which service is slow?" can't be answered by reading logs. Each signal has a role:

  • Metrics: cheap aggregates, RED (rate, errors, duration) per service/endpoint, USE (utilisation, saturation, errors) for resources. Dashboards and alerts.
  • Traces: the path of one request across services with timings per span; shows where latency comes from. Requires context propagation (W3C traceparent) through HTTP, gRPC, queues and async work.
  • Logs: detailed events, structured as JSON with trace_id, span_id, service, version, so you can jump from a trace to its logs.

OpenTelemetry standardises SDKs and auto-instrumentation in every language, and the Collector pipeline routes data to any backend (Prometheus/Mimir, Tempo/Jaeger, Loki/Elastic, or a vendor). Changing vendors doesn't touch code.

Alerting on SLO burn rates (symptoms users feel) rather than every CPU spike reduces noise. Cost control: head sampling (keep x%), tail sampling (keep all errors and slow traces), log levels, retention tiers, cardinality limits.

How it works

  1. Every service: OTel SDK + auto-instrumentation; service.name, version, env attributes.
  2. Collector agents → gateway collectors → backends.
  3. Exemplars link metrics to traces; logs carry trace IDs.
  4. Golden dashboards per service; SLOs with burn-rate alerts.

Common mistakes

  • Different formats and libraries per team.
  • No propagation through message queues (traces break).
  • Logging everything at DEBUG in production.
  • Alerts on causes rather than user impact.

How to answer in the interview

"I'd standardise on OpenTelemetry across all services, producing RED metrics, structured logs with trace IDs and distributed traces with context propagated through HTTP and queues. A collector pipeline sends them to the backends. Alerting is based on SLO burn rates, and tail-based sampling keeps all slow and failed traces while dropping most healthy ones to control cost."

Likely follow-up questions

  • Tail-based sampling? Decide after the trace completes; keep errors/slow ones.
  • High-cardinality debugging? Traces/logs or wide events, not metric labels.
  • What are exemplars? Trace IDs attached to metric samples.
