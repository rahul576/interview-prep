How would you reduce REST API response time from 5 seconds to 500 milliseconds?

REST & API Design · scenario · levels senior, lead

In one line

Measure first with distributed tracing and profiling to see where the 5 seconds go, then fix the biggest contributors: database (indexes, N+1, projections), downstream calls (parallelise, remove, timeouts), caching, smaller payloads, and moving non-essential work async, and re-measure under load.

Detailed explanation

Guessing wastes time; a 5-second endpoint is usually dominated by one or two causes.

1. Measure. Use distributed tracing (OpenTelemetry with Jaeger, Tempo, Datadog, Dynatrace) to break the request into spans: database queries, downstream HTTP calls, serialisation. Check p50/p95/p99 latency, not just averages. Enable SQL logging or Hibernate statistics to count queries. A profiler (async-profiler, JFR) shows CPU hot spots, lock contention or GC pauses. Reproduce with realistic data volumes.

2. Database (most common).

  • N+1 queries: loading 100 orders and lazily fetching lines per order makes 101 queries. Fix with fetch joins, @EntityGraph or batch fetching.
  • Missing indexes: check EXPLAIN ANALYZE for sequential scans; add composite indexes matching filters and sorts.
  • Over-fetching: use DTO projections instead of loading full entity graphs; paginate.
  • Connection pool waits: check Hikari metrics.

3. Downstream calls. Five sequential 800 ms calls are 4 seconds. Run independent ones in parallel (CompletableFuture, virtual threads, structured concurrency), remove unnecessary ones, request bulk endpoints instead of one-by-one calls, and set strict timeouts with circuit breakers so one slow dependency does not dominate.

4. Caching. Cache expensive, rarely changing data: Caffeine in-process for reference data, Redis for shared data, HTTP caching with ETags for clients. Define TTLs and invalidation.

5. Payload and work. Return only needed fields, paginate large lists, enable gzip/br compression. Move non-essential work, such as sending emails, audit logs, analytics or PDF generation, to asynchronous processing via a queue or Kafka, returning 202 Accepted where appropriate.

6. Verify and protect. Load-test (Gatling, k6, JMeter) to confirm p95 under 500 ms at expected traffic, then add latency SLO alerts and performance tests in CI to prevent regressions.

How it works

  1. Trace a slow request; identify the largest spans.
  2. Fix database issues (queries, indexes, N+1).
  3. Parallelise or eliminate downstream calls with timeouts.
  4. Cache stable data.
  5. Trim payloads and offload async work.
  6. Load-test and monitor p95/p99.

Example

// Before: sequential calls ~2.4 s
Customer c = customerClient.get(id);
List<Order> o = orderClient.recent(id);
Loyalty l = loyaltyClient.points(id);

// After: parallel on virtual threads, ~0.8 s (slowest call), with timeouts in the clients
try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {
    var fc = ex.submit(() -> customerClient.get(id));
    var fo = ex.submit(() -> orderClient.recent(id));
    var fl = ex.submit(() -> loyaltyClient.points(id));
    return new Dashboard(fc.get(), fo.get(), fl.get());
}
EXPLAIN ANALYZE SELECT * FROM orders WHERE customer_id = 42 ORDER BY created_at DESC LIMIT 20;
CREATE INDEX CONCURRENTLY ix_orders_customer_created ON orders (customer_id, created_at DESC);

Common mistakes

  • Optimising without measuring.
  • Adding a cache to hide an N+1 or missing index.
  • Looking only at averages.
  • Parallelising calls without timeouts.
  • Not re-testing under realistic load.

How to answer in the interview

"I don't guess; I measure where the five seconds go with distributed tracing, OpenTelemetry into Jaeger or Datadog, plus a profiler, broken down into database, downstream calls and CPU. Usually the database dominates, so I fix slow queries with indexes based on EXPLAIN ANALYZE, remove N+1 patterns with fetch joins or entity graphs, and use projections to fetch only needed columns. Sequential downstream calls get parallelised with CompletableFuture or virtual threads, or removed, with strict timeouts. Stable, expensive data goes into Caffeine or Redis. I reduce the payload with pagination and compression, and move emails and audit writes to async processing. Then I load-test again and add latency alerts."

Likely follow-up questions

  • How do you prevent the response time from regressing after you fix it? Latency SLO alerts, performance tests in CI, and query-count assertions in tests.
  • How do you find N+1 queries? SQL logs, Hibernate statistics, or tracing showing many identical query spans.
  • When is caching the wrong fix? When data must be fresh or the real issue is a bad query.
