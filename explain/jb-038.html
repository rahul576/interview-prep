How does ArrayList work internally?

Collections · concept · levels entry, mid

In one line

ArrayList wraps an Object[] elementData; it allocates capacity 10 on the first add, grows about 1.5× by copying, gives O(1) get/set and amortised O(1) append, shifts elements for middle inserts (O(n)), and is not thread safe with fail-fast iterators.

Detailed explanation

Internally an ArrayList has two fields that matter: Object[] elementData and int size. new ArrayList<>() points elementData at a shared empty array, so an unused list costs almost nothing. On the first add it allocates the default capacity of 10. new ArrayList<>(n) allocates exactly n up front.

When an add finds the array full, grow() computes the new capacity as roughly old + (old >> 1), about 1.5 times, and calls Arrays.copyOf. Copying is O(n), but because capacity grows geometrically the total copying cost over n appends is still O(n), so append is amortised O(1). The list never shrinks automatically; trimToSize() reduces capacity to the current size, and ensureCapacity(n) grows it in one step.

get(i) and set(i, x) do a bounds check and access the array directly: O(1). add(i, x) and remove(i) call System.arraycopy to shift the tail by one position, which is O(n) in the number of elements after i. Removing from the end is O(1). remove(Object) and contains scan linearly.

It is not synchronised. Every structural change increments modCount, which makes its iterators fail-fast. For thread safety use CopyOnWriteArrayList for read-mostly data, or external locking.

How it works

  1. add(e): if size == elementData.length, call grow().
  2. grow(): new length ≈ 1.5 × old (at least the minimum required), copy.
  3. Store elementData[size++] = e; modCount++.
  4. add(i, e): grow if needed, arraycopy elements i..size right by one, store.
  5. remove(i): arraycopy left by one, null the last slot for GC.

Example

List<Row> rows = new ArrayList<>(50_000);   // avoid ~20 resize copies
for (Row r : resultSet) rows.add(r);        // amortised O(1)

Row r = rows.get(123);                       // O(1)
rows.add(0, header);                         // O(n) shift
rows.remove(rows.size() - 1);                // O(1)

ArrayList<Row> cached = new ArrayList<>(rows);
cached.trimToSize();                         // release spare capacity

Common mistakes

  • Saying it doubles in size (that's Vector by default).
  • Saying the default capacity is allocated at construction; it is lazy.
  • Using remove(0) repeatedly as a queue (O(n) each).
  • Sharing an ArrayList across threads.

How to answer in the interview

"ArrayList is backed by an Object array called elementData. It starts empty and allocates a default capacity of 10 on the first add. When full it grows by about one and a half times, creating a new array and copying with Arrays.copyOf, so appending is amortised constant time. get and set are O(1) because they're direct array access, while inserting or removing in the middle shifts later elements with System.arraycopy, which is O(n). It isn't thread safe, and modCount makes its iterators fail fast. If I know the size, I presize it to avoid copying."

Likely follow-up questions

  • What does trimToSize do? Shrinks the backing array to the current size, useful for long-lived lists after loading.
  • Why null the slot on remove? So the removed object can be garbage collected.
  • Maximum size? Close to Integer.MAX_VALUE, limited by heap and array size limits.
