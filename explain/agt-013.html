How should agents handle errors from tools and external systems?

AI Agents & AIOps · concept · levels mid, senior

In one line

Handle tool errors deliberately: retry transient errors with backoff in tool code, return other errors to the model as actionable observations for self-correction, stop or escalate on permanent errors, use compensating actions for partial work, and never accept success without verification.

Detailed explanation

Errors are normal in agent work: APIs time out, rate limits hit, files are missing, permissions are denied. The design question is who handles which error.

Transient errors such as timeouts, HTTP 429 and 503, and connection resets should be retried inside the tool implementation with exponential backoff and jitter, respecting Retry-After. The model should not spend steps and tokens on network blips, and it has no better strategy than code.

Correctable errors are returned to the model as observations with actionable messages: "file not found: src/app.py; did you mean src/main/app.py?", "date must be ISO format YYYY-MM-DD". Good error messages turn failures into self-correction. A bare "500 Internal Server Error" causes guessing and loops.

Permanent errors, such as permission denied, resource does not exist, or business rule violated, should make the agent stop that path and report or escalate, not try endless variants. Tools can mark errors with a type such as retryable: false to make this clear, and the runtime can stop after repeated identical errors.

For multi-step tasks that fail halfway, the system needs a record of completed steps and, where needed, compensating actions, the saga pattern, defined in code rather than improvised by the model.

Finally, models sometimes report success after a failed step because they misread the output or continue the expected story. So important outcomes are verified: tests actually pass, the record exists, the deployment is healthy, and the final report is checked against recorded tool results.

How it works

  1. Tool code retries transient errors with backoff, then gives up with a clear status.
  2. Errors return structured: ok=false, type, message, hint.
  3. Model corrects arguments for fixable errors.
  4. Permanent errors trigger stop, alternative plan or escalation.
  5. Partial failures trigger compensation from durable step records.
  6. Verification confirms the final state before reporting success.

Example

def create_ticket(project: str, title: str, body: str) -> dict:
    for attempt in range(4):
        try:
            resp = jira.create(project=project, title=title, body=body, timeout=10)
            return {"ok": True, "ticket": resp.key, "url": resp.url}
        except RateLimited as e:
            time.sleep(e.retry_after or (2 ** attempt + random.random()))
        except ProjectNotFound:
            return {"ok": False, "retryable": False, "error": f"Project '{project}' does not exist.",
                    "hint": "Call list_projects to find valid project keys."}
        except PermissionDenied:
            return {"ok": False, "retryable": False, "error": "No permission to create issues in this project.",
                    "hint": "Stop and ask the user to request access."}
    return {"ok": False, "retryable": False, "error": "Jira unavailable after 4 attempts."}

Common mistakes

  • Letting the model retry network errors step by step.
  • Raw stack traces or HTTP codes as the only error information.
  • Not distinguishing permanent from transient errors.
  • No record of completed side effects when a later step fails.
  • Trusting the model's claim of success.

How to answer in the interview

"Errors are normal, so I handle them deliberately. Transient ones like timeouts and rate limits are retried with backoff inside the tool code, so the model doesn't waste steps. Other errors go back to the model as observations with actionable messages, like 'file not found, did you mean this path' or 'the API needs an ISO date', so it can self-correct. Permanent errors like permission denied should make the agent stop that path and report or escalate rather than try variants. If a multi-step task fails halfway, we need a record of what was done and compensating actions. And the agent never claims success without verification, like checking the tests pass or the record exists."

Likely follow-up questions

  • Detect success claims without work? Compare the final message against the trace with code; require evidence like IDs that are verified.
  • Should tool errors raise exceptions? Inside the runtime, convert them into structured results the model can read.
  • What is a saga? A sequence of steps where each has a compensating action used to undo it on failure.
