terraform plan fails with a Cycle error. How do you find and break the cycle?

Terraform · scenario · levels mid, senior

In one line

A Cycle error means objects depend on each other, so no valid order exists; read the addresses in the error, use terraform graph if needed, and break it, typically by replacing inline rules with separate rule resources, removing unneeded depends_on, or splitting modules.

Detailed explanation

Terraform must create, update and destroy objects in an order consistent with the dependency graph. A cycle (A depends on B, B depends on A, possibly through several hops) makes that impossible, and Terraform aborts with Error: Cycle: followed by the list of nodes involved. Those addresses are the starting point. For complex cases, terraform graph outputs the graph in DOT format; render it with Graphviz and look for the loop, or simply read the references between the listed resources.

The classic example is two security groups that reference each other in inline rules: the app group allows egress to the database group, and the database group allows ingress from the app group. Each group's definition needs the other's ID, so neither can be created first. The fix is to create the groups without inline rules and add separate rule resources, such as aws_vpc_security_group_ingress_rule and aws_vpc_security_group_egress_rule. Each rule depends on both groups, but the groups no longer depend on each other, so the order becomes: groups, then rules. The same applies to NSGs and route tables.

Other causes:

  • Module outputs feeding back into inputs of the same module, possibly through another module. Split the module, or pass a value that does not depend on the module's own resources.
  • Broad depends_on, especially on modules, which creates edges to everything inside. Remove it or narrow it.
  • create_before_destroy during replacement: it reverses destroy ordering, and if a dependency does not also use it, cycles can appear. Make the lifecycle settings consistent.

How it works

  1. Read the cycle node list in the error.
  2. Trace references between those nodes in code or with terraform graph.
  3. Identify the edge that is unnecessary or can be moved to a separate resource.
  4. Refactor; use moved blocks if addresses change.
  5. Run plan to confirm the cycle is gone and nothing is replaced unexpectedly.

Example

resource "aws_security_group" "app" { name = "app", vpc_id = var.vpc_id }
resource "aws_security_group" "db"  { name = "db",  vpc_id = var.vpc_id }

resource "aws_vpc_security_group_ingress_rule" "db_from_app" {
  security_group_id            = aws_security_group.db.id
  referenced_security_group_id = aws_security_group.app.id
  ip_protocol = "tcp"
  from_port   = 5432
  to_port     = 5432
}

resource "aws_vpc_security_group_egress_rule" "app_to_db" {
  security_group_id            = aws_security_group.app.id
  referenced_security_group_id = aws_security_group.db.id
  ip_protocol = "tcp"
  from_port   = 5432
  to_port     = 5432
}

Common mistakes

  • Mixing inline ingress blocks with separate rule resources for the same group.
  • Adding depends_on to "fix" ordering and creating new cycles.
  • Inconsistent create_before_destroy across dependent resources.
  • Huge modules that both produce and consume the same values.

How to answer in the interview

"A cycle means two or more objects depend on each other, so there's no valid order. The error lists the addresses involved, and terraform graph helps visualise it if it's not obvious. The classic case is two security groups whose inline rules reference each other. I fix it by creating the groups without inline rules and adding separate rule resources, like aws_vpc_security_group_ingress_rule, which depend on both groups but not on each other. Other causes are module outputs feeding back into inputs, broad depends_on, or inconsistent create_before_destroy during replacement; removing unneeded depends_on or splitting a module usually breaks them."

Likely follow-up questions

  • Why do inline blocks and separate resources conflict? Both manage the same rules, so each apply removes the other's rules, causing perpetual diffs.
  • Can cycles appear only on destroy? Yes, especially with create_before_destroy or provider dependencies.
  • How do you avoid cycles in module design? Clear layering: modules consume inputs and produce outputs, never both for the same data.
