How do you create a thread in Java?

Concurrency · concept · levels entry, mid

In one line

You can extend Thread, pass a Runnable (often a lambda) to new Thread(...), or, as you should in real applications, submit Runnable/Callable tasks to an ExecutorService; since Java 21 you can also create cheap virtual threads.

Detailed explanation

Extending Thread and overriding run() works but mixes the task with the execution mechanism and uses up your only superclass. Implementing Runnable separates what to do from how it runs; with Java 8 a lambda is enough: new Thread(() -> work()).start(). Callable<V> is like Runnable but returns a value and may throw checked exceptions; it is used with executors.

In production code you rarely create threads by hand. Threads are expensive platform resources, and unbounded creation can exhaust memory. An ExecutorService reuses a pool of worker threads, limits concurrency, queues extra work and returns Future objects for results and cancellation. You create one via Executors factory methods or, for full control over queue size and rejection policy, a ThreadPoolExecutor. In Spring you usually inject a TaskExecutor or use @Async.

CompletableFuture.supplyAsync(...) runs a task asynchronously on a pool and lets you chain further steps without blocking.

Virtual threads, final in Java 21, are lightweight threads managed by the JVM. Create them with Thread.ofVirtual().start(task), Thread.startVirtualThread(task) or Executors.newVirtualThreadPerTaskExecutor(). They are ideal for many blocking I/O tasks; you create one per task rather than pooling them. The builder API Thread.ofPlatform().name("worker-", 0).start(task) also helps name platform threads.

Whatever the approach, always call start(), not run(), and give threads meaningful names for thread dumps.

How it works

  1. Define the work as a Runnable (no result) or Callable (result, checked exceptions).
  2. Choose the executor: raw Thread, a thread pool, or virtual threads.
  3. Start it: thread.start() or executor.submit(task).
  4. Collect results or failures via join(), Future.get() or CompletableFuture callbacks.
  5. Shut down executors when done (or use try-with-resources on Java 19+).

Example

// 1. Extend Thread (least preferred)
class Worker extends Thread { public void run() { System.out.println("extends"); } }
new Worker().start();

// 2. Runnable as lambda
Thread t = new Thread(() -> System.out.println("runnable"), "report-thread");
t.start();

// 3. Callable with a pool
ExecutorService pool = Executors.newFixedThreadPool(4);
Future<Integer> f = pool.submit(() -> 6 * 7);
System.out.println(f.get());       // 42
pool.shutdown();

// 4. Virtual threads (Java 21+)
try (var vexec = Executors.newVirtualThreadPerTaskExecutor()) {
    vexec.submit(() -> callSlowApi());
}
Thread.ofVirtual().name("vt-1").start(() -> System.out.println("virtual"));

Common mistakes

  • Calling run() instead of start().
  • Creating a new thread per request in a server instead of using a pool or virtual threads.
  • Pooling virtual threads; they are meant to be created per task.
  • Forgetting to shut down executors, so the JVM does not exit.
  • Leaving threads unnamed, making dumps hard to read.

How to answer in the interview

"There are a few ways. I can extend Thread and override run, but that wastes my single superclass. Better is to implement Runnable, usually as a lambda, and pass it to a Thread and call start; Callable is similar but returns a result and can throw checked exceptions. In real applications I don't create threads by hand: I submit Runnable or Callable tasks to an ExecutorService, usually a ThreadPoolExecutor with a bounded queue, and get Futures back. Since Java 21 I can use virtual threads, via Thread.ofVirtual or newVirtualThreadPerTaskExecutor, which are great for blocking I/O."

Likely follow-up questions

  • Why is implementing Runnable preferred over extending Thread? It keeps the class free to extend something else and separates the task from how it is executed, so it can run in any executor.
  • What is a daemon thread? A background thread that does not keep the JVM alive; set with setDaemon(true) before start.
  • Should you pool virtual threads? No; create one per task and limit access to scarce resources with semaphores.
