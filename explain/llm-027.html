Which vector database options and index types exist, and how do you choose?

LLMOps & RAG · concept · levels mid, senior

In one line

Vector search uses approximate nearest neighbour (ANN) indexes such as HNSW (high recall, memory-hungry) and IVF (clustered, leaner), often with vector quantisation; choose between dedicated databases (Pinecone, Weaviate, Qdrant, Milvus) and vector support in existing stores (pgvector, Elasticsearch, OpenSearch, Azure AI Search) based on scale, filtering, hybrid search, multi-tenancy and operations.

Detailed explanation

Why ANN. Exact (flat) search compares the query with every vector: fine for tens of thousands, too slow for tens of millions at low latency. ANN indexes trade a little recall for orders-of-magnitude speed.

HNSW (Hierarchical Navigable Small World) builds a multi-layer graph where each vector links to near neighbours; search greedily walks from coarse upper layers to the dense bottom layer. It gives high recall and low latency and supports incremental inserts, but keeps the graph and vectors in memory, and builds slowly.

IVF (inverted file) clusters vectors with k-means into lists; a query searches only the nearest nprobe clusters. Lower memory and faster builds, some recall loss, and it needs retraining when data distribution shifts. Often combined with product quantisation (IVF-PQ).

Quantisation compresses vectors: scalar (float32 to int8, 4x smaller), product quantisation and binary (32x smaller) with rescoring of top candidates using full vectors. DiskANN-style indexes keep most data on SSD for billion-scale corpora.

Options.

  • Dedicated vector databases: Pinecone (managed, serverless), Weaviate, Qdrant, Milvus/Zilliz, offering rich filtering, hybrid search, multi-tenancy and horizontal scale.
  • Existing stores with vector support: PostgreSQL + pgvector (HNSW and IVFFlat, plus SQL joins and transactions), Elasticsearch / OpenSearch (strong BM25 plus kNN), Redis, MongoDB Atlas Vector Search, Azure AI Search, Vertex AI Vector Search, and others.

How to choose: number of vectors and growth; latency and QPS targets; metadata filtering quality (filtered HNSW can lose recall with very selective filters); built-in hybrid keyword search; multi-tenancy and access control; update rate; and above all what the team already runs well. For many applications up to several million vectors, pgvector or the existing search engine is enough and avoids a new system.

How it works

  1. Choose distance metric (cosine, dot product, L2) matching the embedding model.
  2. Build the index (HNSW or IVF) with chosen parameters.
  3. Query: ANN search with filters returns top candidates.
  4. Optionally rescore with full-precision vectors and rerank.
  5. Tune parameters against recall and latency targets.

Example

CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE chunks (id bigserial PRIMARY KEY, tenant_id int, doc_id text, body text, embedding vector(1024));
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 128);
SET hnsw.ef_search = 100;
SELECT id, body FROM chunks
WHERE tenant_id = 42
ORDER BY embedding <=> $1
LIMIT 20;

Common mistakes

  • Adding a new vector database when pgvector would do.
  • Ignoring recall loss with selective filters.
  • Never measuring recall versus exact search.
  • Mismatched distance metric for the embedding model.

How to answer in the interview

"Vector search uses approximate nearest neighbour indexes because exact search over millions of vectors is too slow. HNSW, a graph index, gives high recall and low latency but needs lots of memory and builds slowly; IVF clusters vectors and probes only nearby clusters, leaner with some recall loss; and quantisation compresses vectors. Options are dedicated databases like Pinecone, Weaviate, Qdrant and Milvus, or vector support in stores we already run like pgvector, Elasticsearch, OpenSearch or Azure AI Search. I choose by scale, filtering and hybrid search needs, multi-tenancy, latency and operations; for many teams pgvector or the existing search engine is enough."

Likely follow-up questions

  • When move off pgvector? Hundreds of millions of vectors, high QPS, or complex filtering at scale hurting latency.
  • HNSW tuning? Raise ef_search for recall, M and ef_construction for quality at memory cost.
  • Filtered search issues? Pre-filter vs post-filter trade-offs; use engines with filter-aware traversal.
