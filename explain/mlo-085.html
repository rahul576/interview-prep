What are the main components of Kubeflow, and when would you adopt it?

MLOps · concept · levels mid, senior

In one line

Kubeflow is a set of Kubernetes-native ML components: Pipelines, Notebooks, the Training Operator / Kubeflow Trainer, Katib, KServe and a Model Registry; adopt it when you already run Kubernetes, want a portable open-source platform, and have a platform team to operate it.

Detailed explanation

  • Kubeflow Pipelines (KFP): define workflows in Python with the KFP SDK v2; each step runs in a container, with caching, artefact and metadata tracking, run comparison and a UI. Pipelines compile to an intermediate YAML that can also run on Vertex AI Pipelines.
  • Kubeflow Notebooks: Jupyter, VS Code (code-server) or RStudio servers running as pods with requested CPUs, GPUs and mounted volumes, under per-user profiles and namespaces.
  • Training Operator / Kubeflow Trainer: CRDs for distributed training. The classic operator provides PyTorchJob, TFJob, MPIJob and others; Kubeflow Trainer v2 introduces a unified TrainJob with reusable training runtimes, handling worker setup, rendezvous and restarts.
  • Katib: hyperparameter tuning (random, grid, Bayesian, and more) and neural architecture search with early stopping, running trials as Kubernetes jobs.
  • KServe: model serving via the InferenceService resource, with autoscaling (including scale-to-zero with Knative), canary rollouts, standard inference protocols and increasingly LLM serving. It started in Kubeflow and is now a separate project used widely on its own.
  • Model Registry: stores model metadata, versions and artefact locations, bridging training and serving.
  • Central Dashboard and multi-tenant profiles tie components together; Spark Operator has also joined the project.

You can install the full platform (manifests or a distribution from a vendor) or adopt components individually, which many teams do: just KFP, or just KServe.

When to adopt: you already run Kubernetes well, want cloud-portable or on-premises ML, need GPU sharing with other workloads, and have a platform team to handle upgrades, authentication (Istio, Dex/OIDC) and multi-tenancy. If not, managed platforms (SageMaker, Vertex AI, Azure ML, Databricks) are usually faster and cheaper to operate.

How it works

  1. Install Kubeflow or selected components on a cluster with GPU node pools.
  2. Users get profiles (namespaces) and notebooks.
  3. Pipelines orchestrate data prep, training jobs and evaluation.
  4. Training runs as TrainJob or PyTorchJob across GPU nodes; Katib tunes hyperparameters.
  5. Models are registered and deployed as KServe InferenceServices.
  6. The platform team manages upgrades, quotas and access.

Example

from kfp import dsl, compiler
@dsl.component(base_image="python:3.11")
def train(lr: float, model: dsl.Output[dsl.Model]):
    ...
@dsl.component(base_image="python:3.11")
def evaluate(model: dsl.Input[dsl.Model]) -> float:
    ...
@dsl.pipeline(name="churn-training")
def pipeline(lr: float = 0.01):
    t = train(lr=lr).set_accelerator_type("nvidia.com/gpu").set_accelerator_limit(1)
    evaluate(model=t.outputs["model"])
compiler.Compiler().compile(pipeline, "churn.yaml")

Common mistakes

  • Installing the full platform without a team to operate and upgrade it.
  • Treating Kubeflow as a single product rather than separable components.
  • Ignoring multi-tenancy and authentication design up front.
  • Choosing it when the organisation doesn't run Kubernetes.

How to answer in the interview

"Kubeflow is a set of Kubernetes-native components for ML. Pipelines runs containerised workflows with caching and artefact tracking. Notebooks gives users Jupyter or VS Code on the cluster with GPUs. The Training Operator, now evolving into Kubeflow Trainer with TrainJob, runs distributed training. Katib does hyperparameter tuning. KServe serves models, and there's a Model Registry. You can adopt components individually. I'd choose it when the company already runs Kubernetes, wants a portable open-source platform across clouds or on-prem, and has a platform team; otherwise a managed ML platform is quicker."

Likely follow-up questions

  • Which component first? Usually Pipelines for reproducible training, or KServe if serving is the pain point.
  • Kubeflow versus a managed platform? Kubeflow gives portability and control; managed platforms reduce operational burden.
  • How do you handle multi-tenancy? Profiles map to namespaces with RBAC, resource quotas and OIDC authentication.
