What is the difference between CMD and ENTRYPOINT in a Dockerfile?

Docker · concept · levels entry, mid

In one line

ENTRYPOINT sets the executable that always runs, CMD supplies the default command or default arguments to it; docker run arguments replace CMD, while replacing ENTRYPOINT needs --entrypoint; use the exec (JSON) form so your process is PID 1 and receives signals.

Detailed explanation

Docker builds the container's command line as ENTRYPOINT + CMD:

  • Only CMD set: CMD is the whole command, and docker run image something replaces it entirely. Good for general-purpose images where users often run other commands.
  • Only ENTRYPOINT set: it always runs, and docker run arguments are appended to it.
  • Both: ENTRYPOINT is the executable, CMD the default arguments. docker run image --port 9090 keeps the entrypoint and swaps the arguments. This makes an image behave like a binary.

Exec form vs shell form. The exec form ["java", "-jar", "app.jar"] runs the program directly as PID 1. The shell form java -jar app.jar is wrapped as /bin/sh -c "java -jar app.jar", so sh becomes PID 1. Many shells do not forward SIGTERM to the child, so docker stop or a Kubernetes pod termination waits for the grace period and then SIGKILLs the app, skipping graceful shutdown: in-flight requests drop and connections are not closed. The shell form also ignores CMD arguments when used for ENTRYPOINT.

A common pattern is an entrypoint script that prepares configuration and ends with exec "$@", which replaces the shell with the real process so it inherits PID 1 and receives signals.

PID 1 is special: the kernel does not apply default signal handlers to it, and it must reap orphaned child processes. If your app spawns children, use a tiny init like tini (docker run --init) to forward signals and reap zombies.

How it works

  1. Docker reads ENTRYPOINT and CMD from the image config.
  2. docker run image args → args replace CMD.
  3. docker run --entrypoint sh image → replaces ENTRYPOINT (and clears the image CMD).
  4. Final argv is executed as PID 1 in the container.

Example

FROM eclipse-temurin:21-jre
COPY app.jar /app/app.jar
COPY docker-entrypoint.sh /usr/local/bin/
ENTRYPOINT ["docker-entrypoint.sh"]
CMD ["java", "-jar", "/app/app.jar", "--server.port=8080"]
#!/bin/sh
# docker-entrypoint.sh
set -e
[ -n "$DB_PASSWORD_FILE" ] && export DB_PASSWORD="$(cat "$DB_PASSWORD_FILE")"
exec "$@"          # hand PID 1 to the real process
docker run shop-api                                  # default CMD
docker run shop-api java -jar /app/app.jar --debug   # override CMD
docker run --entrypoint sh -it shop-api              # override ENTRYPOINT

Common mistakes

  • Shell-form ENTRYPOINT, so SIGTERM never reaches the app.
  • Entrypoint scripts that forget exec.
  • Putting configuration flags in ENTRYPOINT that users then cannot override.
  • Thinking docker run image arg overrides ENTRYPOINT.

How to answer in the interview

"ENTRYPOINT defines the executable that always runs; CMD gives the default command, or default arguments when there's an ENTRYPOINT. Arguments to docker run replace CMD, while changing the ENTRYPOINT needs the --entrypoint flag. My usual pattern is ENTRYPOINT with the binary or a small script ending in exec, and CMD with default flags. I always use the exec JSON form, so the app runs as PID 1 and receives SIGTERM directly; with the shell form, sh is PID 1 and may not forward signals, so the container gets killed instead of shutting down gracefully."

Likely follow-up questions

  • Zombie processes? Use --init/tini or a proper init as PID 1 to reap children.
  • Why does stop take 10 seconds? SIGTERM is ignored, so Docker waits and then SIGKILLs.
  • How does Kubernetes map these? command overrides ENTRYPOINT, args overrides CMD.
