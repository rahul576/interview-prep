How do you optimise a Dockerfile for image size, build speed and security?

Docker · concept · levels mid

In one line

Use multi-stage builds, a small base (slim, alpine, distroless), instruction order that maximises layer caching, a .dockerignore, combined RUN steps with cleanup and cache mounts, and for security run as non-root, pin versions or digests, keep secrets out of layers and scan in CI.

Detailed explanation

Size. A multi-stage build compiles in a full SDK image and copies only the artefact into a minimal runtime stage, so compilers, sources and caches never ship. A Java app can go from an 800 MB JDK-based image to under 200 MB with a JRE or distroless base; a Go binary can run on scratch or distroless/static. Choose bases wisely: slim Debian variants are compatible and small; alpine is tiny but uses musl libc, which can break some native libraries; distroless contains no shell or package manager. Because layers are additive, delete temporary files in the same RUN that created them; deleting in a later layer does not shrink the image.

Build speed. Docker caches each layer and reuses it until an instruction or its inputs change, then rebuilds everything after it. So order instructions from least to most frequently changing: copy the dependency manifest (package.json, pom.xml, requirements.txt), install dependencies, and only then copy source code. A .dockerignore keeps .git, node_modules, build output and .env files out of the build context, speeding uploads and avoiding needless cache invalidation. BuildKit cache mounts (RUN --mount=type=cache) keep package manager caches between builds.

Security. Add a non-root USER; pin base images to a version or digest for reproducibility (and let Renovate update them); never COPY secrets or pass them as build args, use RUN --mount=type=secret; install only needed packages (--no-install-recommends); and scan the result with Trivy or Grype, failing on critical fixable CVEs.

How it works

  1. Stage 1: SDK image, copy manifests, install deps (cached), copy source, build.
  2. Stage 2: minimal runtime image, copy only the artefact.
  3. Set non-root user, exec-form entrypoint.
  4. CI: build with BuildKit and registry cache, scan, push by digest.

Example

# syntax=docker/dockerfile:1
FROM node:22-bookworm-slim AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci
COPY . .
RUN npm run build && npm prune --omit=dev

FROM gcr.io/distroless/nodejs22-debian12
WORKDIR /app
COPY --from=build /app/node_modules ./node_modules
COPY --from=build /app/dist ./dist
USER nonroot
EXPOSE 3000
CMD ["dist/server.js"]

Common mistakes

  • COPY . . before installing dependencies, busting the cache on every code change.
  • RUN apt-get update in one layer and install in another (stale cache) or no cleanup.
  • Secrets in ARG/ENV, visible in image history.
  • Running as root and using :latest base images.

How to answer in the interview

"For size I use multi-stage builds, so the final image contains only the runtime and the artefact, on a slim or distroless base. For speed I order instructions from least to most frequently changing, copying the dependency manifest and installing dependencies before copying source, so the cache is reused, and a .dockerignore keeps the context small. I combine RUN commands and clean up in the same layer, and use BuildKit cache mounts. For security I run as a non-root user, pin base image versions or digests, use secret mounts instead of baking credentials, and scan with Trivy in CI."

Likely follow-up questions

  • Why doesn't deleting a file in a later layer reduce size? Earlier layers still contain it; the later layer only hides it.
  • Alpine downsides? musl libc compatibility and DNS quirks; slim or distroless are often safer.
  • How to debug distroless images? kubectl debug or docker debug with an ephemeral tools container.
