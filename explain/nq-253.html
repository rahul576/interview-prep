When would you use sharding in a large-scale application?

Databases & SQL · scenario · levels senior, lead

In one line

Use sharding as a last resort, when a single primary cannot handle the data size or write throughput even after query tuning, indexing, caching, read replicas, vertical scaling, archiving and partitioning, and when a natural shard key such as tenant, customer or region exists that most queries include.

Detailed explanation

Sharding permanently increases complexity: routing, cross-shard reporting, distributed transactions, rebalancing, per-shard migrations and more operational surface. So the first question is whether simpler options are exhausted:

  • Query and index tuning, removing N+1 queries.
  • Caching hot reads in Redis or a CDN.
  • Read replicas for read-heavy traffic.
  • Vertical scaling: one well-tuned PostgreSQL or MySQL primary can handle tens of terabytes and many thousands of transactions per second.
  • Archiving cold data and partitioning for retention.
  • Functional split: moving a separate domain (audit logs, events) to its own database is often enough.

Signals that sharding is warranted:

  • Write throughput exceeds a single primary even after batching and tuning, for example sustained tens of thousands of writes per second.
  • Data volume is growing towards limits where backups, restores, index builds and vacuum take too long on one node.
  • Multi-tenant SaaS with large tenants, where isolating tenants also limits blast radius and enables per-tenant placement.
  • Data residency: EU customers' data must stay in the EU, India's in India, so sharding by region is a legal requirement.

The shard key must appear in the large majority of queries and spread load evenly. I would also seriously consider databases that shard natively, such as DynamoDB, Cassandra, MongoDB, CockroachDB, YugabyteDB, Spanner, or Citus and Vitess on top of PostgreSQL and MySQL, rather than hand-rolling shard routing in application code.

How it works

  1. Measure: CPU, I/O, write rate, data growth and projected limits.
  2. Apply cheaper optimisations and re-measure.
  3. Analyse queries to choose a shard key and check its distribution.
  4. Choose technology: native distributed DB vs proxy vs application routing.
  5. Migrate incrementally: dual writes or CDC, backfill, verify, cut over shard by shard.
  6. Build cross-shard reporting through a data warehouse or lakehouse.

Example

A B2B SaaS platform with 4,000 tenants:

Problem:   single Postgres primary at 85% CPU on writes, 18 TB, restore takes 14 hours
Tried:     indexes, caching, 3 read replicas, archived old events, partitioned by month
Decision:  shard by tenant_id using Citus (hash distribution, 128 logical shards)
           tenant-scoped tables co-located; reference tables (plans, currencies) replicated
           two largest tenants moved to dedicated nodes
Reporting: CDC (Debezium) -> warehouse for cross-tenant analytics

Common mistakes

  • Sharding because "we might be big one day".
  • Picking a key most queries lack, forcing scatter-gather everywhere.
  • Ignoring how cross-shard reports, global uniqueness and schema migrations will work.
  • Building custom routing when a managed distributed database would fit.

How to answer in the interview

"Sharding is a last resort because it adds lasting complexity. First I'd optimise queries and indexes, add caching, use read replicas for reads, scale vertically, archive old data and partition large tables. Sharding becomes the right choice when data volume or write throughput really exceeds one primary, like billions of fast-growing rows or tens of thousands of writes per second, and there's a natural shard key that most queries include, such as tenant id in a multi-tenant SaaS, customer id or region, which can also satisfy data residency rules. I'd also prefer databases that shard natively, like DynamoDB, Cassandra, CockroachDB or Citus, over building sharding into the application."

Likely follow-up questions

  • How would you handle a report across all shards? Scatter-gather for small queries, otherwise stream data into a warehouse via CDC.
  • How do you migrate to shards without downtime? CDC or dual writes, backfill, verify, then cut over tenant by tenant.
  • What about a tenant too large for one shard? Give it a dedicated shard or sub-shard by a secondary key.
