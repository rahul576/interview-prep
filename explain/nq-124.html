When would you choose HashSet over TreeSet, considering performance?

Collections · scenario · levels mid

In one line

Choose HashSet when you only need uniqueness and fast membership (average O(1)), and TreeSet when you need sorted order or range/nearest queries (O(log n)); if you only need sorted output once, collect in a HashSet and sort once at the end.

Detailed explanation

The decision is about what operations you need, not about which set is "better".

HashSet suits pure membership work: de-duplicating ids from a stream of events, checking whether an email has been seen, idempotency keys, visited nodes in a graph search. Each operation is average O(1): one hash computation, one bucket lookup and usually one equals. That holds only if the elements have a well-distributed hashCode and the set is presized for large volumes to avoid repeated rehashing.

TreeSet suits work where order is part of the requirement continuously: you repeatedly need the smallest or largest element, the nearest value (floor, ceiling), or a range (subSet(from, to)), while elements keep arriving. Each operation is O(log n) comparisons plus pointer chasing through tree nodes, and each element costs a larger node object. For a million elements that's roughly 20 comparisons per operation versus one or two hash probes, so for pure lookups HashSet is typically several times faster. Comparison cost matters too: comparing long strings is slower than comparing ints.

A common optimisation: if sorted output is needed only once, collect into a HashSet (or straight into a list with distinct()) and sort once: O(n log n) total, but with a fast contiguous sort rather than n tree inserts. And for "top K" queries, a bounded PriorityQueue of size K (O(n log K)) beats keeping everything in a TreeSet.

How it works

  1. List the operations: add, contains, min/max, range, sorted iteration.
  2. Only add/contains/remove → HashSet.
  3. Continuous ordering or navigation → TreeSet.
  4. Ordering only at the end → HashSet then sort.
  5. Top K only → bounded min-heap.

Example

// Dedup then sort once
Set<String> unique = HashSet.newHashSet(events.size());
for (Event e : events) unique.add(e.userId());
List<String> sorted = new ArrayList<>(unique);
Collections.sort(sorted);

// Or with streams
List<String> sorted2 = events.stream().map(Event::userId).distinct().sorted().toList();

// Continuous nearest-value queries -> TreeSet
TreeSet<Long> slots = new TreeSet<>(availableSlots);
Long next = slots.ceiling(requestedTime);

// Top 10 scores
PriorityQueue<Integer> top = new PriorityQueue<>();
for (int s : scores) { top.offer(s); if (top.size() > 10) top.poll(); }

Common mistakes

  • Using TreeSet "just in case" sorted output is needed.
  • Ignoring hashCode quality, which can make HashSet slow.
  • Keeping all elements in a TreeSet just to get the top K.
  • Benchmarking with tiny data sets where differences vanish.

How to answer in the interview

"I choose HashSet when I only care about uniqueness and fast lookups, like de-duplicating ids or checking whether an email was already seen; it's average constant time, much faster than TreeSet's log n for large sets, provided hashCode is good. I choose TreeSet when I need sorted order all the time or navigation like floor, ceiling or subSet. If I only need sorted output once at the end, it's usually faster to collect in a HashSet and sort once, or use a stream with distinct and sorted. For top K, a bounded PriorityQueue is better still."

Likely follow-up questions

  • Top 10 highest scores efficiently? A min-heap of size 10: offer each, poll when size exceeds 10.
  • Insertion-ordered unique elements? LinkedHashSet.
  • Sorted and concurrent? ConcurrentSkipListSet.
