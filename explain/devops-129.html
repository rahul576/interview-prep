Compare OPA Gatekeeper and Kyverno for Kubernetes policy enforcement.

DevSecOps · concept · levels senior, lead

In one line

Both are admission controllers that check requests against policies; OPA Gatekeeper uses Rego in ConstraintTemplates (powerful, reusable beyond Kubernetes), while Kyverno uses Kubernetes-native YAML (and CEL) and excels at mutate, generate, verifyImages and cleanup; roll either out in audit mode before enforce.

Detailed explanation

Kubernetes RBAC controls who can create resources, but not what those resources may look like. Policy engines fill that gap: they register as validating and mutating admission webhooks, so the API server sends them each request and rejects or modifies it before it is stored. Typical policies: no privileged containers, no latest tags, required labels, resource limits, images only from approved registries.

OPA Gatekeeper builds on Open Policy Agent. A platform team writes a ConstraintTemplate containing Rego logic and parameters; users then create Constraints that apply it to specific kinds and namespaces. Rego is a general-purpose policy language, so the same skills and even policies can be reused for Terraform plans (Conftest), APIs and CI checks. Gatekeeper also has an audit controller that reports existing violations and supports mutation (Assign, AssignMetadata). The trade-off is Rego's learning curve.

Kyverno is built for Kubernetes only. Policies are YAML resources using familiar patterns, JMESPath and increasingly CEL, so they read like manifests. Beyond validation it can mutate (add default labels, set imagePullPolicy), generate resources (create a default-deny NetworkPolicy and quota in every new namespace), verify image signatures and attestations with cosign, and clean up resources. Kyverno CLI tests policies in CI.

Kubernetes itself now offers ValidatingAdmissionPolicy with CEL (GA since 1.30), which covers simple validation without a webhook; both engines integrate with or complement it.

How it works

  1. Install the engine; it registers admission webhooks.
  2. Write policies; test them in CI against sample manifests.
  3. Deploy in audit (Gatekeeper enforcementAction: dryrun/warn, Kyverno Audit).
  4. Review policy reports, fix workloads, add exceptions.
  5. Switch to enforce; monitor webhook latency and failure policy.

Example

apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: disallow-latest-tag
spec:
  validationFailureAction: Audit   # switch to Enforce after review
  rules:
  - name: require-pinned-tag
    match:
      any:
      - resources:
          kinds: ["Pod"]
    validate:
      message: "Images must use a pinned tag or digest, not :latest."
      pattern:
        spec:
          containers:
          - image: "!*:latest"

Common mistakes

  • Enforcing on day one and blocking critical system pods.
  • failurePolicy: Fail without HA, so an engine outage blocks all deployments.
  • Forgetting to exclude kube-system and the engine's own namespace.
  • Validating only Pods, so Deployments are accepted but their Pods silently fail.

How to answer in the interview

"Both are admission controllers: the API server asks them to validate requests before storing them. Gatekeeper uses Rego in ConstraintTemplates; it's powerful and reusable outside Kubernetes but has a learning curve. Kyverno policies are Kubernetes-native YAML, easier for platform teams, and it can also mutate, generate resources like default network policies for new namespaces, and verify image signatures. I'd pick Kyverno for a Kubernetes-focused team and Gatekeeper where OPA is already used elsewhere. Either way I roll policies out in audit mode first, fix violations, then enforce."

Likely follow-up questions

  • Which policies first? No privileged pods or host mounts, resource requests and limits, trusted registries, no latest, required labels.
  • What about native policies? ValidatingAdmissionPolicy with CEL for simple checks without a webhook.
  • How to handle exceptions? Kyverno PolicyExceptions or Gatekeeper excluded namespaces, documented and time-boxed.
