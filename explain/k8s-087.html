A pod cannot start because of a Multi-Attach error for its volume. What does it mean and how do you resolve it?

Kubernetes · scenario · levels mid, senior

In one line

Multi-Attach error means a ReadWriteOnce block disk is still attached to another node, and it can attach to only one; it happens when the old pod or a dead node still holds it, typically in rolling updates of single-replica Deployments or after node failure. Use Recreate or a StatefulSet, wait for detach, or fix a stuck VolumeAttachment (out-of-service taint for dead nodes).

Detailed explanation

Cloud block volumes (EBS, Azure Disk, Persistent Disk) can only be attached to one VM at a time, which Kubernetes models as ReadWriteOnce (more precisely, one node; ReadWriteOncePod restricts it to a single pod). The attach/detach controller tracks attachments through VolumeAttachment objects and the CSI driver. Before attaching a volume to a new node, it must be detached from the old one. If the new pod is scheduled to a different node while the old attachment exists, the kubelet reports Multi-Attach error for volume ... Volume is already used by pod(s) ... or already exclusively attached to one node.

Two classic causes. Rolling updates: a Deployment with one replica and a RWO PVC uses RollingUpdate by default, so it starts the new pod (maxSurge) before stopping the old one. If the new pod lands on another node, it cannot attach until the old pod terminates and the disk detaches. Depending on timing it either resolves after a delay or deadlocks when the old pod only stops once the new one is ready. Node failure: the old node is NotReady, so nobody can confirm the volume was unmounted; the controller waits (a force-detach timeout of around six minutes in many setups) before detaching, or longer for safety.

Fixes: for single-replica workloads with RWO volumes, use strategy: Recreate so the old pod stops first, or a StatefulSet, which replaces pods one at a time by identity. For dead nodes, confirm the node is off and apply the node.kubernetes.io/out-of-service taint, which force-detaches. Check kubectl get volumeattachment for the stale attachment and the cloud console for the disk's state; if a CSI driver is stuck, its controller logs explain why.

How it works

  1. kubectl describe pod: Multi-Attach event naming the volume and old pod.
  2. kubectl get volumeattachment to find which node holds it.
  3. Check the old pod and node status.
  4. Healthy node: wait for the old pod to stop and detach.
  5. Dead node: fence it and apply the out-of-service taint.
  6. Prevent: Recreate strategy or StatefulSet for RWO workloads.

Example

kubectl get volumeattachment | grep pvc-3a9c
#  csi-7f...  ebs.csi.aws.com  pvc-3a9c  ip-10-0-2-44  true
kubectl get node ip-10-0-2-44                # NotReady?
apiVersion: apps/v1
kind: Deployment
metadata: { name: grafana }
spec:
  replicas: 1
  strategy: { type: Recreate }   # old pod releases the RWO disk before the new one starts

Common mistakes

  • RollingUpdate for single-replica apps with RWO volumes.
  • Deleting VolumeAttachments while the old node may still write.
  • Expecting RWO to allow several replicas on different nodes.
  • Using RWX file shares for databases to "fix" it.

How to answer in the interview

"A Multi-Attach error means the volume, usually a ReadWriteOnce cloud disk, is still attached to another node, and block disks can attach to only one node at a time. It happens when the old pod or its node still holds the attachment: a node died and the controller is waiting before force-detaching, or a single-replica Deployment with RollingUpdate starts the new pod on another node before the old one releases the disk. I check VolumeAttachments and the old pod and node. Fixes: wait for the detach, use the out-of-service taint for dead nodes, and use Recreate or a StatefulSet for RWO workloads."

Likely follow-up questions

  • When choose ReadWriteMany? Shared content across pods (uploads, ML datasets); costs are lower performance, higher price, and locking semantics unsuitable for databases.
  • What is ReadWriteOncePod? Guarantees a single pod, not just a single node, has the volume.
  • Why not delete the VolumeAttachment? The old node may still be writing, risking corruption.
