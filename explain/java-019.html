When do virtual threads help, and what are their pitfalls?

Concurrency · concept · levels senior, lead

In one line

Virtual threads (final in Java 21) are cheap JVM-scheduled threads that unmount from carrier threads when they block, so they shine for high-concurrency blocking I/O; they don't speed up CPU-bound work, can be pinned (synchronized pinning was fixed in Java 24, native calls still pin), should not be pooled, and need Semaphores to protect scarce resources.

Detailed explanation

A platform thread maps one-to-one to an OS thread, with a large stack and expensive context switches, so servers cap pools at hundreds of threads. A virtual thread is a lightweight Thread managed by the JVM whose stack lives on the heap and grows as needed. Millions can exist. They run on a small pool of carrier threads, one per core by default.

When a virtual thread performs a blocking operation that the JDK supports (socket I/O, sleep, BlockingQueue.take, ReentrantLock, JDBC drivers using JDK sockets), it unmounts: its stack is parked on the heap and the carrier runs another virtual thread. When the I/O completes it is remounted, possibly on a different carrier. So simple thread-per-request blocking code scales like async code, as long as the workload mostly waits.

They do not make CPU-bound work faster: there are still only as many carriers as cores. For number crunching use platform thread pools or parallel streams.

Pitfalls:

  • Pinning: if a virtual thread blocks while it can't unmount, it holds its carrier. Before Java 24, blocking inside synchronized pinned; JEP 491 in Java 24 removed that for monitors. Native frames (JNI, some foreign calls) and certain class initialisation still pin. On Java 21 use ReentrantLock around blocking calls and diagnose with -Djdk.tracePinnedThreads or JFR jdk.VirtualThreadPinned events.
  • Don't pool them: they are cheap; create one per task with Executors.newVirtualThreadPerTaskExecutor().
  • Limit resources explicitly: a pool used to bound concurrency implicitly; now 10,000 virtual threads can all hit the DB. Use a Semaphore or the connection pool's limit.
  • ThreadLocal heavy objects per thread multiply memory; prefer ScopedValue (final in Java 25).

How it works

  1. Thread.ofVirtual().start(task) or a per-task executor creates a virtual thread.
  2. Scheduler mounts it on a carrier.
  3. On blocking I/O, its continuation is saved and it unmounts.
  4. Carrier runs other virtual threads.
  5. On completion it is rescheduled and remounted.

Example

Semaphore dbPermits = new Semaphore(50);           // match connection pool

try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    for (Request r : requests) {
        exec.submit(() -> {
            String profile = http.send(r.profileCall(), ofString()).body(); // unmounts
            dbPermits.acquire();
            try { return repo.save(r, profile); }
            finally { dbPermits.release(); }
        });
    }
}

Common mistakes

  • Expecting virtual threads to speed up CPU-heavy computation.
  • Putting them in a fixed-size pool.
  • Removing all concurrency limits and overwhelming databases.

How to answer in the interview

"Virtual threads are cheap JVM-managed threads, so I can run one per request even with hundreds of thousands of concurrent requests. They help most for blocking I/O: when a virtual thread blocks it unmounts from its carrier, which runs other virtual threads. They don't make CPU-bound work faster because carriers equal the number of cores. The pitfalls are pinning, where blocking inside synchronized or native code holds the carrier, mostly fixed for synchronized in Java 24; heavy ThreadLocal use; and the fact that you shouldn't pool them, but create one per task and use a Semaphore to limit access to scarce resources like database connections."

Likely follow-up questions

  • Enable in Spring Boot 3? Set spring.threads.virtual.enabled=true (Boot 3.2+, Java 21+).
  • How do you detect pinning? JFR jdk.VirtualThreadPinned events, or -Djdk.tracePinnedThreads on older JDKs.
  • Reactive vs virtual threads? Virtual threads give similar scalability with simpler blocking code; reactive still helps for streaming and back-pressure.
