How would you structure image layers for a large application to maximise cache reuse?

Docker · concept · levels senior

In one line

Order layers from least to most frequently changing: shared base image and OS packages, then the runtime, then third-party dependencies (installed from lock files), and finally application code, splitting large dependency sets further (for example Spring Boot layered jars) so most builds and deploys move only a few megabytes.

Detailed explanation

Docker caches each layer and reuses it until an instruction or its inputs change; after the first changed layer, every later layer is rebuilt. Registries and nodes work the same way: they store and transfer layers by content digest, so a node that already has a layer never downloads it again. Good layering therefore speeds up three things at once: builds, pushes and pulls.

The practical order is:

  • Base OS and system packages: ideally a shared company base image used by every service, so nodes already have it cached.
  • Language runtime: JRE, Node, Python.
  • Third-party dependencies: they change weekly at most. Copy only pom.xml, package-lock.json or requirements.txt, install, and only then copy source.
  • Application code: changes on every commit, so it goes last and should be small.

For Java, a fat jar is one big file, so any code change produces a new 100 MB layer. Spring Boot layered jars (java -Djarmode=tools ... extract --layers in Boot 3.3+, previously -Djarmode=layertools) split it into dependencies, spring-boot-loader, snapshot-dependencies and application layers. Jib does a similar split automatically. For Node or Python, separate the lock-file install from the source copy, and consider separate layers for rarely changing large assets.

How it works

  1. Start FROM a pinned, shared base image.
  2. Install OS packages in one RUN with cache cleanup.
  3. Copy dependency manifests and install dependencies.
  4. Copy and build source in a separate stage.
  5. In the runtime stage, copy layers in stable-to-volatile order.

Example

FROM eclipse-temurin:21-jdk AS build
WORKDIR /src
COPY pom.xml .
RUN --mount=type=cache,target=/root/.m2 mvn -q dependency:go-offline
COPY src ./src
RUN --mount=type=cache,target=/root/.m2 mvn -q package -DskipTests
RUN java -Djarmode=tools -jar target/app.jar extract --layers --launcher --destination /layers

FROM registry.example.com/base/java-21-jre:2026.11
WORKDIR /app
COPY --from=build /layers/dependencies/ ./
COPY --from=build /layers/spring-boot-loader/ ./
COPY --from=build /layers/snapshot-dependencies/ ./
COPY --from=build /layers/application/ ./
ENTRYPOINT ["java", "org.springframework.boot.loader.launch.JarLauncher"]

Common mistakes

  • COPY . . before installing dependencies.
  • Every team using a different base image, so nothing is shared on nodes.
  • Putting timestamps or build numbers in early layers, which breaks caching every build.
  • Copying the fat jar as one layer.

How to answer in the interview

"Layers are cached and transferred in order, and once one changes, everything after it rebuilds, so I order them from least to most frequently changing. At the bottom is a shared company base image with the OS and runtime, which every node already has. Then third-party dependencies installed from the lock file, and on top the application code. For Java I use Spring Boot layered jars or Jib so dependencies and application classes are separate layers. The result is that a typical commit changes only the top layer, a few megabytes, so CI pushes are quick and Kubernetes nodes pull only that small layer when we deploy."

Likely follow-up questions

  • How does this speed up Kubernetes deploys? Nodes already hold base and dependency layers, so they pull only the changed top layer and pods start sooner.
  • Many small layers or few big ones? Group by change frequency, not by count; layer count matters far less than reuse.
  • Does squashing help? Usually not; it destroys layer sharing.
