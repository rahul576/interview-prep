How do you validate request input in Spring Boot, including custom rules?

Spring Boot · concept · levels entry, mid

In one line

Annotate DTO fields with Bean Validation constraints (@NotNull, @NotBlank, @Size, @Email, @Pattern), trigger them with @Valid on controller parameters or @Validated for method validation, write custom constraints with ConstraintValidator (including class-level cross-field rules), use validation groups for create vs update, and return clear 400 responses.

Detailed explanation

Spring Boot uses Jakarta Bean Validation with Hibernate Validator through spring-boot-starter-validation (not included in the web starter since Boot 2.3). Constraints live on request DTOs or records: @NotBlank for strings that must contain text, @NotNull, @Size(max = 100), @Email, @Pattern, @Positive, @Past, @Future, @Min/@Max, @Digits. Nested objects and lists need @Valid on the field to cascade.

Triggering: @Valid @RequestBody CreateBooking req validates before the method body; failures raise MethodArgumentNotValidException. For simple parameters, Spring 6.1+ validates constraints such as @RequestParam @Min(1) int page automatically and raises HandlerMethodValidationException. On service classes, @Validated at class level enables method validation of parameters and return values via AOP, raising ConstraintViolationException.

Custom rules that annotations cannot express: create an annotation with @Constraint(validatedBy = ...) and implement ConstraintValidator<A, T>. Put it on a field for single-value rules (a valid IBAN or SKU format) or on the class for cross-field rules such as "end date after start date". Validators are Spring beans, so they can have dependencies, but keep database lookups light.

Groups let one DTO carry different rules for create and update: @Null(groups = Create.class) Long id, activated with @Validated(Create.class). Often separate request DTOs per operation are simpler.

Errors: a @RestControllerAdvice converts the exceptions into 400 Bad Request with a ProblemDetail listing each field and message. Messages can be externalised in ValidationMessages.properties for i18n.

Keep a clear split: syntactic validation (format, required, length) belongs on the DTO; business validation (stock available, user may book) belongs in the service layer.

How it works

  1. JSON is deserialised into the DTO.
  2. The validator evaluates field and class constraints, cascading with @Valid.
  3. Violations become a binding result and an exception.
  4. The advice maps them to a 400 response.
  5. Service-layer method validation and business checks run next.

Example

@Target(ElementType.TYPE) @Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = DateRangeValidator.class)
public @interface ValidDateRange {
    String message() default "end must be after start";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

public class DateRangeValidator implements ConstraintValidator<ValidDateRange, CreateBooking> {
    public boolean isValid(CreateBooking b, ConstraintValidatorContext ctx) {
        return b.start() == null || b.end() == null || b.end().isAfter(b.start());
    }
}

@ValidDateRange
public record CreateBooking(
    @NotBlank @Size(max = 80) String guestName,
    @Email @NotBlank String email,
    @NotNull @FutureOrPresent LocalDate start,
    @NotNull LocalDate end,
    @Valid @NotEmpty List<RoomRequest> rooms) {}

@PostMapping("/bookings")
ResponseEntity<BookingDto> create(@Valid @RequestBody CreateBooking req) { ... }

Common mistakes

  • Missing the validation starter, so annotations do nothing.
  • Forgetting @Valid on nested objects or collections.
  • Using @NotNull on strings where @NotBlank is meant.
  • Putting business rules requiring database state into DTO annotations.
  • Returning only the first error instead of all field errors.

How to answer in the interview

"I annotate DTO fields with Bean Validation constraints such as @NotBlank, @Size, @Email and @Pattern, and put @Valid on the request body parameter so validation runs before the controller method. @Validated on a service class enables method validation there too. For rules annotations can't express, like end date after start date, I write a custom constraint annotation with a ConstraintValidator, applied at class level. Validation groups can separate create and update rules, though often separate DTOs are clearer. Failures raise MethodArgumentNotValidException, and my @RestControllerAdvice turns that into a 400 ProblemDetail listing all field errors."

Likely follow-up questions

  • Where should business validation live: DTO annotations or the service layer? Format rules on the DTO; rules needing state or other services in the service layer.
  • @Valid vs @Validated? @Valid is standard and cascades; @Validated is Spring's, supports groups and enables method validation.
  • How do you validate a list in the body? Put @Valid on the elements, e.g. List<@Valid Item>.
