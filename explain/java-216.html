What are WeakHashMap, IdentityHashMap and EnumMap used for?

Collections · concept · levels mid, senior

In one line

WeakHashMap holds keys through weak references so entries vanish after the key is garbage collected, IdentityHashMap compares keys with == instead of equals, and EnumMap is a compact array indexed by ordinal for enum keys.

Detailed explanation

WeakHashMap wraps each key in a WeakReference registered with a ReferenceQueue. When nothing else strongly references the key, the GC can collect it, and the next time the map is accessed it drains the queue and removes the stale entries. It is useful for attaching metadata to objects you don't own without preventing their collection, for example extra information per class loader or per UI component. Two caveats: it uses equals, so it works badly with keys like interned strings or boxed small integers that are always strongly reachable; and if the value references its key, the entry never disappears. It is not a good general cache, because eviction depends on GC of keys, not on memory pressure or age; use Caffeine for real caches.

IdentityHashMap deliberately breaks the Map contract by using reference equality (==) and System.identityHashCode. Two distinct but equal objects are separate keys. It is used for graph traversal, deep copying and serialisation, where you must track "have I visited this exact object?" even if objects override equals. It uses open addressing (linear probing) in a single array.

EnumMap stores values in an array whose index is the key's ordinal(). There is no hashing and no collisions, so it is very fast and compact, iterates in enum declaration order, and rejects null keys. EnumSet is the matching bit-vector set.

How it works

  1. WeakHashMap: GC clears weak key → reference enqueued → expungeStaleEntries removes it on next access.
  2. IdentityHashMap: index from identityHashCode, compare with ==, probe linearly on collision.
  3. EnumMap: values[key.ordinal()] = value.

Example

enum Status { NEW, PAID, SHIPPED }
Map<Status, Duration> sla = new EnumMap<>(Status.class);
sla.put(Status.NEW, Duration.ofHours(1));
sla.put(Status.PAID, Duration.ofHours(24));

Map<Object, Boolean> visited = new IdentityHashMap<>();
void walk(Object node) {
    if (visited.put(node, true) != null) return;   // already seen this instance
    // ... visit children
}

Map<Widget, Metadata> extra = new WeakHashMap<>();  // gone when widget is GC'd

Common mistakes

  • Using WeakHashMap as an LRU or size-bounded cache.
  • Values that strongly reference their keys in a WeakHashMap.
  • Using IdentityHashMap with String keys and expecting equals semantics.
  • Using HashMap with enum keys when EnumMap is simpler and faster.

How to answer in the interview

"WeakHashMap holds keys through weak references, so once a key is no longer strongly referenced anywhere else the GC can reclaim it and the entry disappears. It's good for metadata attached to objects, but for real caches I use Caffeine. IdentityHashMap compares keys with double-equals instead of equals, which I'd use to track visited objects during graph traversal or serialisation. EnumMap is backed by an array indexed by ordinal, so it's extremely fast and compact for enum keys, for example config per order status."

Likely follow-up questions

  • Soft, weak and phantom references? Soft are cleared under memory pressure, weak at next GC once unreachable, phantom only signal post-finalisation cleanup.
  • Is WeakHashMap thread safe? No; wrap it with Collections.synchronizedMap.
  • What is EnumSet? A bit-vector-backed set for enum values.
