What are the main components of MLflow, and how do they fit into an MLOps workflow?

MLOps · concept · levels mid, senior

In one line

MLflow's main components are Tracking (parameters, metrics, artefacts), the Model Registry (versions, aliases, tags), the MLflow Models format (flavours, signature, environment), Projects for reproducible runs, and newer GenAI features (tracing, prompt management, evaluation); together they connect training, registration and deployment.

Detailed explanation

MLflow is an open source platform, also offered as a managed service in Databricks and supported in Azure ML and SageMaker.

Tracking records each run with parameters, metrics (including step-wise curves), tags and artefacts such as plots, data samples and models. Autologging captures these automatically for scikit-learn, XGBoost, PyTorch Lightning, Keras and others. Runs are grouped into experiments, and the UI compares them side by side.

The Model Registry stores registered models with numbered versions, each linked to the run that produced it. Instead of the older fixed stages (Staging, Production), current MLflow recommends aliases such as champion and challenger, plus tags and descriptions. Deployment pipelines resolve models:/fraud-model@champion.

The MLflow Models format packages a model with one or more flavours (for example sklearn, pytorch, and the generic pyfunc), a signature describing inputs and outputs, an input example and the environment (pip/conda requirements). The same artefact can be served locally (mlflow models serve), built into a container, or deployed to Databricks, SageMaker or Azure ML.

Projects describe how to run code reproducibly with an entry point and environment. MLflow 3 also adds GenAI capabilities: tracing of LLM and agent calls, prompt registry, and evaluation with LLM judges and human feedback.

How it works

  1. Training job sets the tracking URI and logs params, metrics and the model.
  2. The best run's model is registered as a new version.
  3. Evaluation compares it with the champion alias.
  4. If gates pass, CI/CD moves the champion alias to the new version.
  5. Serving loads models:/name@champion; logs record the version.

Example

import mlflow
mlflow.set_tracking_uri("https://mlflow.internal")
mlflow.autolog()

with mlflow.start_run(run_name="xgb-depth6") as run:
    model.fit(X_train, y_train)
    mlflow.log_metric("val_auc", auc)
    mlflow.sklearn.log_model(model, "model", registered_model_name="churn")

from mlflow import MlflowClient
MlflowClient().set_registered_model_alias("churn", "challenger", version=8)

Common mistakes

  • Running a local file-based tracking store that nobody else can see.
  • Registering models without signatures or input examples.
  • Still relying on deprecated stages instead of aliases.
  • Deploying from run artefacts directly, bypassing the registry.

How to answer in the interview

"MLflow has Tracking for parameters, metrics and artefacts, with autologging and run comparison; the Model Registry for versioned models with aliases like champion; and the MLflow Models format, which packages a model with flavours, a signature and its environment so it can be served locally, in a container or on Databricks, SageMaker or Azure ML. Projects make runs reproducible, and newer versions add GenAI tracing and evaluation. In a workflow, training logs to tracking, the best run is registered, and CI/CD promotes by moving aliases and deploying that version."

Likely follow-up questions

  • How would you host MLflow for many teams? Central server with a database backend and object store, SSO, per-team permissions, or managed MLflow.
  • Aliases vs stages? Aliases are flexible named pointers; stages are deprecated.
  • What does the signature enforce? Input column names and types at inference time.
