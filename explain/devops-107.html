Compare push-based and pull-based (GitOps) deployment, including security implications.

GitOps & Helm · concept · levels mid, senior

In one line

In push-based deployment the CI pipeline holds cluster credentials and runs kubectl apply/helm upgrade; in pull-based GitOps an in-cluster agent (Argo CD, Flux) pulls desired state from Git and continuously reconciles, so credentials stay inside the cluster, drift is detected and corrected, and Git history is the audit trail.

Detailed explanation

Push model: after building and testing, the pipeline authenticates to the cluster and applies manifests. It is simple and familiar, and works for any target. But the CI system becomes a high-value target: it stores kubeconfigs or cloud credentials with broad write rights to every environment it deploys to. Anyone who compromises a runner, a plugin or a pipeline definition can deploy anything. And the pipeline only acts when it runs; if someone edits the cluster by hand later, nothing notices or corrects the drift.

Pull model (GitOps): an agent running inside the cluster watches a Git repository (or OCI artifact) and makes the cluster match it. CI's job ends at building the image and committing a new image tag to the config repo (or opening a PR). The agent authenticates outbound to Git and the registry with read-only credentials; no external system needs cluster admin rights, and the cluster API does not need to be reachable from CI at all, which suits private clusters. Because the agent reconciles continuously, manual changes show as OutOfSync and can be reverted automatically with self-heal. Every change is a commit, so you get review, audit and rollback via git revert.

GitOps has costs too: two repos or more to manage, the agent itself must be secured (its RBAC is powerful), secrets need a separate solution, and sequencing imperative steps (migrations, tests after deploy) needs hooks or extra tooling.

How it works

  1. Developer merges code; CI builds, tests, scans and pushes the image.
  2. CI (or Renovate/Argo CD Image Updater) updates the image tag in the config repo.
  3. The in-cluster agent detects the new commit.
  4. It renders manifests (Helm/Kustomize), diffs with live state and applies.
  5. It keeps reconciling, reporting drift and health.

Example

# CI step: no cluster credentials, only Git write access
- name: Bump image tag in config repo
  run: |
    git clone https://github.com/acme/deploy-config && cd deploy-config
    yq -i '.image.tag = "${{ github.sha }}"' apps/orders/values-prod.yaml
    git commit -am "orders: deploy ${{ github.sha }}" && git push

Common mistakes

  • Calling it GitOps while CI still runs kubectl apply with admin credentials.
  • Giving the GitOps agent cluster-admin everywhere without restricting projects.
  • Committing plain Kubernetes Secrets to the config repo.
  • Letting people make manual cluster changes and then wondering why self-heal reverts them.

How to answer in the interview

"In a push model the CI pipeline holds cluster credentials and runs kubectl or helm, so CI becomes a powerful attack target, and once the pipeline finishes nothing stops manual drift. In a pull model, an agent such as Argo CD or Flux runs inside the cluster, watches Git and syncs the desired state. CI only needs to push an image and update a tag in a Git repo, so cluster credentials never leave the cluster, and the API server doesn't even need to be reachable from CI. The agent reconciles continuously, flags or reverts manual changes, and Git history gives us review, audit and rollback with git revert. The trade-off is that secrets and imperative steps need extra handling."

Likely follow-up questions

  • How do you handle secrets in GitOps? External Secrets Operator from a vault, or encrypted with Sealed Secrets/SOPS.
  • How does CI know the deployment succeeded? Query Argo CD/Flux status or notifications, or run post-sync hooks.
  • Is push ever better? For non-Kubernetes targets or very simple setups where a reconciler adds little.
