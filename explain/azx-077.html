How do you back up workloads on AKS, and how does Azure Backup for AKS compare with Velero?

Azure Kubernetes (AKS) · concept · levels mid, senior

In one line

Azure Backup for AKS uses a backup extension and a Backup vault to protect cluster resources and persistent volumes (disk snapshots) on a schedule, restoring to the same or another cluster, even another region; Velero is the open source, cloud-agnostic alternative; both complement GitOps and database-native backups.

Detailed explanation

Kubernetes workloads have two parts to protect: resource definitions (deployments, configmaps, secrets, PVCs, CRDs) and data in persistent volumes. Ideally definitions already live in Git, but backups also catch things created by hand, operators' generated state and secrets.

Azure Backup for AKS installs the backup extension (microsoft.dataprotection.kubernetes) in the cluster with a storage account for metadata, and uses Trusted Access so the Backup vault can talk to the cluster. A backup policy defines schedule and retention. Each backup captures selected namespaces and resources, filtered by labels if needed, plus Azure Disk snapshots of persistent volumes. Snapshots stay in an operational tier (in your subscription); the vault tier copies data into the Backup vault, which supports geo-redundant storage and cross-region restore for disaster recovery. You can restore everything or selected namespaces and resources, to the original cluster or a different one, with conflict handling options. It integrates with Backup Center, Azure Policy and RBAC.

Velero is open source, widely used and works across clouds, backing up resources to object storage (Blob) and volumes via CSI snapshots or file-level backup. It suits multi-cloud teams but you operate it yourself.

In both cases, volume snapshots are crash-consistent, not application-consistent: a database may be mid-write. So for databases I rely on native backups (point-in-time restore of Azure Database for PostgreSQL, or pg_dump and WAL archiving), use pre-backup hooks to quiesce writes, and test restores regularly.

How it works

  1. Create a Backup vault and policy.
  2. Install the backup extension and enable Trusted Access.
  3. Configure a backup instance for the cluster and namespaces.
  4. Backups run on schedule; snapshots and optional vault copies are retained.
  5. Restore to the same or a different cluster, testing quarterly.

Example

az k8s-extension create --name azure-aks-backup --extension-type microsoft.dataprotection.kubernetes \
  --scope cluster --cluster-type managedClusters --cluster-name aks-prod -g rg-apps \
  --release-train stable --configuration-settings blobContainer=aksbackup \
  storageAccount=staksbackup storageAccountResourceGroup=rg-backup storageAccountSubscriptionId=$SUB

# Velero alternative
velero backup create orders-daily --include-namespaces orders --snapshot-volumes
velero restore create --from-backup orders-daily

Common mistakes

  • Treating backups as the only recovery plan instead of GitOps plus data backups.
  • Assuming disk snapshots give consistent database backups.
  • Never testing a restore into a clean cluster.
  • Keeping backups only in the same region as the cluster.

How to answer in the interview

"Azure Backup for AKS installs a backup extension and uses a Backup vault and policy. It backs up Kubernetes resources for selected namespaces plus persistent volumes as disk snapshots, and can restore to the same or a different cluster, including another region with vaulted copies. Velero is the open source, cloud-agnostic alternative storing backups in object storage. Either way, GitOps is my main way to recreate workloads, databases use their own native backups because snapshots are only crash-consistent, and we test restores regularly."

Likely follow-up questions

  • Why are snapshots inconsistent for databases? They capture disk state mid-write without flushing or coordinating transactions.
  • What about Azure Files volumes? Protect them with Azure Files backup or Velero file-level backup.
  • How do you prove recoverability? Scheduled restore drills with measured RTO and RPO.
