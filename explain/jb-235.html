How do you prevent cascading failures across microservices?

Microservices · design · levels senior, lead

In one line

Prevent cascades at every hop with timeouts within the caller's budget (ideally deadline propagation), circuit breakers, bulkheads and limited concurrency, controlled retries (backoff, jitter, retry budgets), plus rate limiting, load shedding, autoscaling and asynchronous decoupling.

Detailed explanation

A cascading failure starts small: service D slows down. C's threads wait on D, C's pool fills, C becomes slow; B waits on C, and so on until the edge returns errors for everything, including features that never touched D. Retries make it worse by multiplying traffic just as capacity drops. Recovery is hard because restarted instances are immediately overwhelmed.

Defences, layer by layer:

Timeouts and deadlines. Each call's timeout must fit inside the caller's remaining time budget. If the edge allows 2 s, downstream calls cannot each wait 5 s. Deadline propagation (gRPC deadlines, or a header carrying the remaining budget) lets downstream services abandon work nobody is waiting for.

Circuit breakers. Stop calling a dependency with a high failure or slow-call rate, fail fast with a fallback, and probe for recovery.

Bulkheads and concurrency limits. Separate thread pools, semaphores or connection pools per dependency, so one slow dependency can only exhaust its own share. Adaptive concurrency limiters adjust limits based on observed latency.

Controlled retries. Retry only transient errors, with exponential backoff and jitter, few attempts, in one layer only, and with retry budgets (retries capped at, say, 10 percent of normal traffic) so a failure cannot multiply load.

Self-protection. Services enforce rate limits per client and load shedding: when queues or latency exceed thresholds, reject excess requests early with 503/429, prioritising critical traffic. Bounded queues prevent memory exhaustion. Autoscaling adds capacity, but it is slow, so it complements rather than replaces shedding.

Decoupling and design. Move non-urgent work to queues so slow consumers do not block users. Avoid deep synchronous call chains; cache data that can be stale. Test with chaos engineering and load tests to verify these limits.

How it works

  1. Edge sets a deadline; each hop uses a smaller timeout.
  2. Bulkheads cap concurrency per dependency.
  3. Breakers open on sustained failures and return fallbacks.
  4. Retries obey budget and backoff.
  5. Overloaded services shed load early.
  6. Autoscaling and queues absorb the remaining pressure.

Example

resilience4j:
  timelimiter.instances.pricing: { timeoutDuration: 800ms }   # edge budget 2s
  circuitbreaker.instances.pricing: { failureRateThreshold: 50, slowCallDurationThreshold: 500ms, slowCallRateThreshold: 50 }
  bulkhead.instances.pricing: { maxConcurrentCalls: 30 }
  retry.instances.pricing: { maxAttempts: 2, waitDuration: 100ms, enableRandomizedWait: true }
# Envoy/Istio retry budget idea: retries limited to 20% of active requests
retry_budget:
  budget_percent: { value: 20.0 }
  min_retry_concurrency: 3

Common mistakes

  • Downstream timeouts longer than upstream ones.
  • Retries at every layer without budgets.
  • Unbounded queues and thread pools.
  • Relying on autoscaling alone during sudden spikes.
  • Health checks that fail on dependency outages, causing restart storms.

How to answer in the interview

"A cascading failure is when one slow service makes callers wait until they run out of threads, and their callers fail in turn. I defend at every hop. Each call has a timeout shorter than the caller's budget, ideally with deadline propagation. Circuit breakers stop calls to a failing dependency. Bulkheads give each dependency its own limited pool so it cannot exhaust everything. Retries use backoff, jitter and retry budgets to avoid retry storms. Services protect themselves with rate limiting and load shedding, returning 503 early when overloaded, autoscaling adds capacity, and queues decouple non-urgent work. I verify all of it with load and chaos tests."

Likely follow-up questions

  • What is a retry storm and how do budgets help? Layers of retries multiply traffic during an outage; budgets cap retries as a fraction of normal requests.
  • What is load shedding? Rejecting excess work early and cheaply so the service can still serve what it accepts.
  • Why shouldn't liveness probes check dependencies? A dependency outage would restart all instances and deepen the failure.
