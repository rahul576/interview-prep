What is the Observer pattern?

Design Patterns · concept · levels entry, mid

In one line

Observer defines a one-to-many dependency: when a subject changes state, it notifies all registered observers through a common interface, keeping the subject loosely coupled from whoever reacts.

Detailed explanation

Without Observer, an OrderService that must send an email, update inventory and record analytics calls all three services directly. Every new reaction means editing OrderService, and it ends up depending on half the system.

With Observer, the subject keeps a list of observers that implement a shared interface (OrderListener.onOrderPlaced(event)). Observers subscribe and unsubscribe; when the event happens, the subject loops over them and calls the method. The subject knows only the interface, so new reactions are added without touching it (open/closed).

Push vs pull: the subject can push data in the notification (an event object), or just signal and let observers pull state. Event objects are the modern norm.

Where it appears:

  • GUI listeners (ActionListener), JavaBeans PropertyChangeListener. (The old java.util.Observable is deprecated since Java 9.)
  • Spring events: ApplicationEventPublisher.publishEvent(new OrderPlacedEvent(...)) and @EventListener methods. By default listeners run synchronously in the publisher's thread and transaction. @TransactionalEventListener(phase = AFTER_COMMIT) runs only once the transaction commits, and @Async moves work to another thread.
  • Reactive streams (Flow.Publisher/Subscriber, Project Reactor) add backpressure.
  • At system level: publish/subscribe with Kafka, RabbitMQ or cloud pub/sub, where observers are separate services.

Pitfalls: memory leaks from listeners never removed (the subject holds strong references); a slow or failing observer blocking or breaking the subject if notification is synchronous; unpredictable ordering; and hidden control flow that is harder to debug. In-process events are also lost on crash, so critical side effects use the transactional outbox plus a broker.

How it works

  1. Define an observer interface or event type.
  2. Observers register with the subject (or are discovered by Spring).
  3. Subject state changes; it creates an event.
  4. Subject notifies each observer in turn (or via a broker).
  5. Observers react independently; they can unsubscribe.

Example

public record OrderPlacedEvent(long orderId, String email) {}

@Service
class OrderService {
    private final ApplicationEventPublisher events;
    OrderService(ApplicationEventPublisher events) { this.events = events; }

    @Transactional
    public void place(Order o) {
        // save order...
        events.publishEvent(new OrderPlacedEvent(o.id(), o.email()));
    }
}

@Component
class OrderEmailListener {
    @Async
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void onPlaced(OrderPlacedEvent e) { /* send confirmation email */ }
}

Common mistakes

  • Sending emails in a synchronous listener inside the transaction, then rolling back.
  • Forgetting to unregister listeners.
  • Assuming listener execution order.
  • Relying on in-memory events for data that must never be lost.

How to answer in the interview

"Observer defines a one-to-many dependency: when the subject changes, every registered observer is notified automatically. Observers implement a common interface, so the subject doesn't know their concrete classes and I can add reactions without changing it. In Spring I use ApplicationEventPublisher with @EventListener: an OrderPlaced event triggers email, inventory and analytics listeners. At system level it becomes pub/sub with Kafka. I watch out for listeners that are never unregistered, and for slow synchronous observers, so I use @TransactionalEventListener after commit and @Async where appropriate."

Likely follow-up questions

  • How do you make notifications asynchronous in Spring? @EnableAsync and @Async on the listener, or publish to a message broker.
  • Observer vs pub/sub? Pub/sub adds a broker between publishers and subscribers, so they do not know each other at all.
  • How do you avoid losing events? Transactional outbox table relayed to Kafka.
