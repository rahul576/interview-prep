How do you design a system with cloud cost as a first-class requirement?

Architecture Trade-offs · concept · levels senior, lead

In one line

Make cost a requirement: estimate unit cost (per request/user), right-size and autoscale, use reserved/savings plans for the baseline and spot for flexible work, apply storage tiering and lifecycle rules, watch data transfer/egress, and enforce tagging, budgets and cost observability.

Detailed explanation

Cloud bills grow quietly. Treating cost like latency (a target with dashboards and regressions) keeps it under control.

Unit economics: cost per order, per active user, per 1,000 API calls. It shows whether growth makes the business healthier and which component dominates.

Compute: right-size from real utilisation (many instances run at 10–20% CPU); autoscale; scale to zero for low-traffic services (serverless, KEDA); use ARM/Graviton where possible; reserved instances/savings plans for steady base load; spot/preemptible for CI, batch and stateless workers that tolerate interruption.

Storage: lifecycle rules move objects to cool/archive tiers; delete old snapshots and orphaned volumes; log retention limits; compress.

Network: cross-AZ and cross-region traffic and internet egress add up; keep chatty services together, use CDNs, VPC endpoints instead of NAT gateways for cloud APIs.

Data: warehouse queries scanning whole tables; partitioning and clustering reduce scanned bytes.

Governance: mandatory tags (team, service, env), budgets with alerts, per-team showback/chargeback, cost anomaly detection, FinOps reviews.

How it works

  1. Tag everything; build per-service cost dashboards.
  2. Track unit cost per release.
  3. Monthly review of top spenders and waste reports.
  4. Commitments sized to the stable baseline.

Example

Before: 40 × m5.2xlarge at 18% CPU, NAT egress 30 TB/month, logs kept 365 days
After:  autoscaled 12–30 × m7g.xlarge, S3/ECR via VPC endpoints, logs 30 days hot + archive
Unit cost: ₹0.42 → ₹0.19 per 1,000 requests

Common mistakes

  • Optimising only compute while ignoring egress and storage.
  • Overcommitting reservations.
  • Untagged resources nobody owns.
  • Non-production environments running 24/7.

How to answer in the interview

"I'd define unit cost, like cost per thousand requests, early and track it per release. Compute is right-sized and autoscaled, with commitments for the steady baseline and spot for batch and CI. Storage gets tiering and retention rules. I watch data transfer and egress closely since they often surprise teams. Every resource is tagged by team and service, with budgets, anomaly alerts and dashboards so engineers see the cost of their designs."

Likely follow-up questions

  • Hidden cost to check first? NAT gateway/egress, idle resources, log ingestion.
  • Spot safely? Diversified instance types, interruption handling, checkpointing.
  • Dev environments? Schedules to shut down nights/weekends; ephemeral environments.
