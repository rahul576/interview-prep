What is EC2, and what are instance types, AMIs and key pairs?

Cloud (AWS) · concept · levels entry

In one line

EC2 provides virtual servers; the instance type (family + size) sets CPU, memory, network and storage, the AMI is the image the instance boots from, and key pairs (or better, SSM Session Manager) give access, with on-demand, Savings Plans/RIs and Spot as pricing options.

Detailed explanation

Instance types are named like m7g.large: the letter is the family, the number the generation, extra letters are attributes (g = Graviton ARM, i = Intel, a = AMD, d = local NVMe, n = enhanced networking) and the suffix is the size. Main families: t burstable general purpose using CPU credits, good for small, spiky workloads; m balanced; c compute-optimised; r/x memory-optimised; i storage-optimised; p/g GPUs. Graviton instances usually offer better price-performance if your software runs on ARM.

An AMI (Amazon Machine Image) contains the root volume snapshot (OS and any pre-installed software) plus launch metadata. You can use AWS or marketplace AMIs, but teams often bake their own golden AMIs with Packer or EC2 Image Builder so instances boot fast and consistently, and use user data or configuration management for the last mile.

Key pairs are SSH key pairs: AWS stores the public key and injects it into the instance; you keep the private key. Modern practice prefers Systems Manager Session Manager: no open port 22, no keys to manage, access controlled by IAM and every session logged. EC2 Instance Connect is another option for short-lived keys.

Pricing: on-demand per second with no commitment; Savings Plans or Reserved Instances for one- or three-year commitments at big discounts; Spot uses spare capacity at up to around 90% off but can be reclaimed with a two-minute warning.

How it works

  1. Choose an AMI (OS/golden image).
  2. Choose an instance type for the workload profile.
  3. Place it in a subnet with a security group and an IAM instance profile.
  4. Attach EBS volumes; add user data for bootstrap.
  5. Access via Session Manager; scale via Auto Scaling groups.

Example

aws ec2 run-instances \
  --image-id ami-0abcdef1234567890 \
  --instance-type m7g.large \
  --subnet-id subnet-0a1b2c3d \
  --security-group-ids sg-0123456789abcdef0 \
  --iam-instance-profile Name=app-ssm-profile \
  --metadata-options HttpTokens=required \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=team,Value=payments}]'

aws ssm start-session --target i-0123456789abcdef0

HttpTokens=required enforces IMDSv2, which protects instance credentials from SSRF attacks.

Common mistakes

  • Using t-family instances for constant high CPU and running out of credits.
  • Opening SSH to 0.0.0.0/0 and sharing one private key across the team.
  • Hand-configured "snowflake" servers instead of baked AMIs.
  • Running stateful, non-interruptible work on Spot without checkpointing.

How to answer in the interview

"EC2 is AWS's virtual server service. The instance type sets CPU, memory and networking: t for burstable, m for balanced, c for compute and r for memory-heavy, with Graviton variants on ARM that are usually cheaper for the same performance. The AMI is the template with the OS and optionally our software; we bake golden AMIs with Packer. Access can use a key pair for SSH, but I prefer Session Manager, so there's no port 22 and access is IAM-controlled and audited. For pricing, on-demand for flexibility, Savings Plans for steady load and Spot for interruptible work."

Likely follow-up questions

  • What suits Spot? Stateless, fault-tolerant work: CI runners, batch, rendering, stateless web tiers in mixed groups.
  • What is IMDSv2? Session-token-based metadata access that blocks simple SSRF credential theft.
  • EBS vs instance store? EBS persists independently; instance store is fast local disk lost on stop.
