A Java service is restarted repeatedly by its liveness probe during traffic peaks, causing an outage. What went wrong?

Kubernetes · scenario · levels mid, senior

In one line

The liveness probe was timing out because the JVM was slow under load or paused in GC, so the kubelet restarted healthy-but-busy pods, which shifted load to the rest and caused a cascading failure; liveness must only detect a stuck process.

Detailed explanation

A liveness probe answers one question: should the kubelet kill and restart this container? During a traffic peak, request threads are saturated or a long garbage collection pause freezes the JVM. The probe request waits behind real traffic, exceeds timeoutSeconds (default 1 second) a few times in a row, reaches failureThreshold, and the container is restarted.

Each restart removes a replica exactly when capacity is most needed, and a restarting JVM is slow to warm up. The remaining pods receive more traffic, they slow down, they fail liveness too, and the whole Deployment collapses, although nothing was actually broken. It is often worse when the liveness endpoint checks the database or downstream services: one slow dependency then restarts every pod at once.

The fix is to separate the probes by purpose. Liveness checks only that the process is not deadlocked, using a cheap endpoint (Spring Boot's /actuator/health/liveness) with generous timeoutSeconds and failureThreshold. Readiness can fail under overload, removing a pod from Service endpoints temporarily without restarting it. A startup probe protects slow JVM startup. And the root cause, too little capacity, poor autoscaling or GC tuning, still needs fixing.

How it works

  1. Peak traffic or GC pause makes responses slow.
  2. Liveness probe times out repeatedly and hits failureThreshold.
  3. Kubelet restarts the container; capacity drops.
  4. Surviving pods get more load and fail liveness in turn.
  5. Fix: cheap liveness, tolerant thresholds, readiness for overload, startup probe, more capacity.

Example

startupProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  periodSeconds: 5
  failureThreshold: 36          # up to 3 minutes to start
livenessProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  periodSeconds: 10
  timeoutSeconds: 5
  failureThreshold: 6           # ~1 minute of failures before restart
readinessProbe:
  httpGet: { path: /actuator/health/readiness, port: 8080 }
  periodSeconds: 5
  timeoutSeconds: 3

Common mistakes

  • Using the same deep health endpoint, including database checks, for liveness and readiness.
  • Keeping the 1-second default timeout for a JVM service.
  • Using initialDelaySeconds instead of a startup probe for slow starts.
  • Treating the restarts as the problem and ignoring the capacity or GC issue behind them.

How to answer in the interview

"Under peak load the service responded slowly, or long GC pauses froze it, so the liveness probe timed out and the kubelet restarted the container. Each restart removed capacity, pushing more traffic to the rest, which then failed too, so we got a cascade with nothing actually broken. Often liveness also checked the database, which makes it worse. I would make liveness a cheap check that the process is not stuck, with longer timeouts and a higher failure threshold, let readiness take overloaded pods out of rotation, add a startup probe for JVM startup, and then fix the capacity and GC problem underneath."

Likely follow-up questions

  • When is it reasonable to have no liveness probe at all? When the process exits on its own when it breaks, so the restart policy already handles it.
  • Can readiness failures cascade too? Yes, if all pods go unready together, so keep readiness thresholds sensible.
  • How do you confirm GC is the cause? GC logs or JFR showing pauses aligned with probe failures.
