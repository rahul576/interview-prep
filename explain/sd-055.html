A slow downstream dependency is making your whole service unresponsive. Which resilience patterns would you apply?

Scalability & Reliability · scenario · levels entry, mid, senior

In one line

A slow dependency usually causes thread/connection pool exhaustion; fix it with timeouts, a circuit breaker, bulkheads isolating resources per dependency, fallbacks/graceful degradation, and monitoring of dependency latency.

Detailed explanation

If a dependency normally answers in 50 ms but now takes 30 s, each request holds a thread (or connection) 600x longer. With 200 threads, the pool fills in seconds, and requests that don't even need that dependency queue up. The whole service looks dead.

  • Timeouts turn slow failures into fast ones; set them from the dependency's SLO/p99, never infinite.
  • Circuit breaker (Resilience4j, Polly, Envoy outlier detection): track failure and slow-call rates; above a threshold, open the circuit and fail immediately for a cool-down; then half-open with a few trial calls.
  • Bulkheads: separate thread pools/semaphores/connection pools per dependency, so the slow one can only consume its own compartment.
  • Fallbacks: cached data, defaults, or omit the feature.
  • Observability: per-dependency latency, error rate, pool saturation, breaker state.

How it works

  1. Request → bulkhead permit for dependency X (else fallback).
  2. Call X with timeout → breaker records result.
  3. Breaker open → skip call → fallback.
  4. Alerts on breaker open and saturation.

Example

@CircuitBreaker(name = "recs", fallbackMethod = "popularItems")
@Bulkhead(name = "recs", type = Bulkhead.Type.SEMAPHORE)
@TimeLimiter(name = "recs")
public CompletableFuture<List<Item>> recommendations(String userId) { ... }

Common mistakes

  • Default HTTP client timeouts (often infinite or minutes).
  • One shared pool for all outbound calls.
  • Fallbacks that call another slow dependency.
  • Breaker thresholds never tuned.

How to answer in the interview

"The root cause is usually that calls to the slow service hold all our threads. I'd add strict timeouts, a circuit breaker that opens on high error or slow-call rates, and bulkheads so each dependency gets its own limited pool. Non-essential features degrade to cached or default data. Then I'd monitor dependency latency and breaker state so we see it before users do."

Likely follow-up questions

  • What can degrade on an e-commerce page? Recommendations, reviews, recently viewed; not cart or payment.
  • Breaker in a mesh or in code? Mesh for uniform policy; code when you need fallbacks.
  • Semaphore vs thread-pool bulkhead? Semaphore is cheaper; thread pool isolates blocking calls.
