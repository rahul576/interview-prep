Design a thread-safe in-memory cache with TTL and a maximum size.

Low-Level Design · design · levels mid, senior

In one line

Store entries in a ConcurrentHashMap with value + expiry time, expire lazily on read plus a background sweep, bound size with an eviction policy (LRU or similar), prevent duplicate loads with computeIfAbsent, and in production use Caffeine (W-TinyLFU).

Detailed explanation

Requirements: concurrent reads and writes, entries expire after a TTL, total entries never exceed maxSize, and good performance under contention.

Storage: ConcurrentHashMap<K, Entry<V>> where Entry holds the value and expiresAtNanos (use System.nanoTime(), which is monotonic). The map gives lock-striped, highly concurrent access.

Expiry: check on read (lazy expiry): if expired, remove it with map.remove(key, entry) (conditional remove avoids deleting a fresh replacement) and treat as a miss. Entries that are never read again would leak memory, so a ScheduledExecutorService runs a periodic background cleanup.

Size bound: this is the hard part. True LRU needs access-order bookkeeping on every read: a LinkedHashMap(accessOrder=true) with removeEldestEntry is simple but needs a lock around every operation, including reads, which kills concurrency. Concurrent approximations include a ConcurrentLinkedDeque of keys or sampled eviction. Caffeine solves this elegantly by buffering reads in lock-free ring buffers and replaying them asynchronously, and uses W-TinyLFU, which combines recency and frequency for better hit rates than LRU.

Loading: computeIfAbsent ensures only one thread computes a missing value per key, preventing a cache stampede on that key; keep the loader fast because it holds a bin lock.

Interviewers want to see that you can build the basic version and know why you would choose Caffeine (or Spring's @Cacheable with a Caffeine backend) in real code.

How it works

  1. get(k): look up entry; if present and not expired, return (and record access for LRU).
  2. If expired: conditional remove, return empty or load.
  3. put(k, v): insert entry with now + ttl; if size exceeds max, evict least recently used.
  4. Scheduled task every few seconds removes expired entries.
  5. Metrics: hit rate, evictions, load time.

Example

public final class TtlLruCache<K, V> {
    private record Entry<V>(V value, long expiresAt) {}
    private final long ttlNanos; private final int maxSize;
    private final LinkedHashMap<K, Entry<V>> map;
    private final ReentrantLock lock = new ReentrantLock();

    public TtlLruCache(Duration ttl, int maxSize) {
        this.ttlNanos = ttl.toNanos(); this.maxSize = maxSize;
        this.map = new LinkedHashMap<>(16, 0.75f, true) {           // access order = LRU
            protected boolean removeEldestEntry(Map.Entry<K, Entry<V>> e) { return size() > TtlLruCache.this.maxSize; }
        };
        Executors.newSingleThreadScheduledExecutor(Thread.ofVirtual().factory())
                 .scheduleAtFixedRate(this::purgeExpired, 5, 5, TimeUnit.SECONDS);
    }

    public Optional<V> get(K key) {
        lock.lock();
        try {
            Entry<V> e = map.get(key);
            if (e == null) return Optional.empty();
            if (System.nanoTime() - e.expiresAt() >= 0) { map.remove(key); return Optional.empty(); }
            return Optional.of(e.value());
        } finally { lock.unlock(); }
    }

    public void put(K key, V value) {
        lock.lock();
        try { map.put(key, new Entry<>(value, System.nanoTime() + ttlNanos)); } finally { lock.unlock(); }
    }

    private void purgeExpired() {
        lock.lock();
        try { long now = System.nanoTime(); map.values().removeIf(e -> now - e.expiresAt() >= 0); }
        finally { lock.unlock(); }
    }
}

// Production:
Cache<String, User> users = Caffeine.newBuilder()
        .maximumSize(10_000).expireAfterWrite(Duration.ofMinutes(5)).recordStats().build();

Common mistakes

  • Using HashMap or an unsynchronised LinkedHashMap across threads.
  • Only lazy expiry, so unread entries leak.
  • Comparing nanoTime values with < instead of subtraction.
  • Slow loaders inside computeIfAbsent blocking other keys.
  • Reinventing a cache instead of using Caffeine in production.

How to answer in the interview

"I'd store entries in a ConcurrentHashMap with each entry holding the value and expiry time. Reads check expiry lazily and conditionally remove expired entries, and a scheduled task sweeps entries that are never read. For the size limit I need eviction like LRU: the simple correct version is an access-ordered LinkedHashMap guarded by a lock, accepting lower concurrency. computeIfAbsent stops multiple threads loading the same key. In production I'd just use Caffeine, which does this with lock-free read buffers and the W-TinyLFU policy for better hit rates."

Likely follow-up questions

  • Cache stampede? Single-flight loading per key, soft TTL with background refresh (refreshAfterWrite), TTL jitter.
  • LRU vs LFU? LRU favours recency; LFU favours frequency; W-TinyLFU blends both and resists scans.
  • Weak or soft references? Let the GC reclaim values, but eviction becomes unpredictable; prefer explicit size bounds.
