What is an image digest, and why pin images by digest?

Docker · concept · levels mid

In one line

A digest is the sha256 hash of an image manifest (nginx@sha256:...) and identifies one immutable image, while tags can move; pinning by digest gives reproducible builds and deployments and supply-chain safety, with Renovate or Dependabot keeping digests updated.

Detailed explanation

Images are content-addressed. Every layer and config is identified by the hash of its content, and the manifest lists them. The hash of the manifest is the image digest. For multi-architecture images there is also an image index (manifest list) with its own digest pointing to per-platform manifests. Change one byte anywhere and the digest changes, so a digest is a cryptographic guarantee of exactly which bits you get.

A tag such as nginx:1.27 or myapp:prod is just a mutable pointer. Publishers routinely move tags to rebuilt images with security fixes, and a compromised registry account or a mistake can point a tag to a different image entirely. If you deploy by tag, the image that runs can differ from the one you tested, and two nodes pulling at different times can run different code.

Pinning by digest in the Dockerfile (FROM eclipse-temurin:21-jre@sha256:...) and in deployment manifests makes builds and rollouts reproducible and defends against tag tampering. Admission controllers can require digests, and signatures (cosign) are attached to digests. You can keep the tag in the reference for readability; when both are present, the digest wins.

The downside is that you stop receiving updates automatically; a pinned base image stays vulnerable until someone bumps it. Tools like Renovate and Dependabot detect new digests for the tag and open pull requests, so updates go through CI and review.

How it works

  1. The builder produces layers and a config, each hashed.
  2. The manifest lists those hashes; its own hash is the digest.
  3. The registry stores the manifest under the digest and maps tags to it.
  4. Pulling by digest fetches exactly that manifest and verifies its hash.
  5. Update bots compare tag targets with pinned digests and open PRs.

Example

docker pull nginx:1.27
docker inspect --format '{{index .RepoDigests 0}}' nginx:1.27
docker buildx imagetools inspect nginx:1.27      # index and per-platform digests
crane digest nginx:1.27
FROM nginx:1.27@sha256:<digest>
image: ghcr.io/acme/orders:1.4.0@sha256:<digest>

Common mistakes

  • Pinning a per-platform digest instead of the index digest, breaking other architectures.
  • Pinning without an update bot, so images rot.
  • Confusing image ID (config hash, local) with the registry digest.
  • Deploying mutable tags like prod to Kubernetes.

How to answer in the interview

"A digest is the sha256 hash of an image manifest, like nginx@sha256:..., and identifies exactly one immutable image, while a tag is just a pointer the publisher can move at any time. Pinning base images in FROM and images in deployments by digest makes builds and deployments reproducible, so we run the exact bits we tested, and protects the supply chain because a retagged or compromised image can't silently change what runs. The downside is no automatic patches, so I let Renovate or Dependabot open pull requests to bump pinned digests."

Likely follow-up questions

  • How do you find a pulled image's digest? docker inspect RepoDigests or docker images --digests.
  • Image ID vs digest? Image ID hashes the local config; the digest hashes the registry manifest.
  • Tag and digest together? Allowed; the digest is authoritative.
