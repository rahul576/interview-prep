Design a URL shortening service like bit.ly. Walk me through the key components.

System Design · design · levels senior, lead

In one line

A URL shortener has a create API and a redirect API, generates unique IDs encoded in base62, stores the mapping in a horizontally scalable key-value store, serves reads from Redis and the CDN, and chooses 301 vs 302 depending on whether every click must be counted.

Detailed explanation

Start with requirements and scale. Suppose 100 million new links per month and a 100:1 read/write ratio: about 40 writes/s and 4,000 redirects/s on average, with peaks several times higher. Over 5 years that is 6 billion links, so a 7-character base62 code (62^7 ≈ 3.5 trillion) is plenty.

ID generation is the key design decision. Options: (1) a distributed counter where each app instance leases ranges of IDs (e.g. 1,000 at a time) from a coordinator like a DB sequence or ZooKeeper, then encodes them in base62; (2) a Snowflake-style 64-bit ID (timestamp + worker + sequence); (3) hashing the long URL (MD5/SHA-256 truncated), which needs collision checks and re-hashing. Sequential counters make codes guessable; if that matters, shuffle the ID with a reversible permutation or add random bits.

Storage is a simple key-value lookup: code -> {longUrl, owner, createdAt, expiresAt}. DynamoDB or Cassandra shard by code naturally; a relational DB with read replicas also works at moderate scale.

Reads dominate, so hot links are cached in Redis (LRU) and redirects can even be cached at the CDN edge. A 301 (permanent) lets browsers cache the redirect, cutting load but hiding repeat clicks; a 302/307 (temporary) sends every click to us for analytics. Analytics events go asynchronously to Kafka, never blocking the redirect.

How it works

  1. POST /api/links {longUrl} -> validate URL, check malware blocklists, rate-limit the caller.
  2. Take the next ID from the local range, base62-encode it, store the mapping.
  3. Return https://sho.rt/aZ3k9Q.
  4. GET /aZ3k9Q -> Redis -> on miss, DB -> populate cache.
  5. Respond 302 Location: <longUrl> and publish a click event to Kafka.
  6. Expired links return 404/410; a cleanup job removes them.

Example

public final class Base62 {
    private static final char[] ALPHABET =
        "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz".toCharArray();

    public static String encode(long id) {
        StringBuilder sb = new StringBuilder();
        do { sb.append(ALPHABET[(int) (id % 62)]); id /= 62; } while (id > 0);
        return sb.reverse().toString();
    }
}

@GetMapping("/{code}")
ResponseEntity<Void> redirect(@PathVariable String code) {
    String target = linkService.resolve(code);          // Redis, then DynamoDB
    clickPublisher.publishAsync(code);                   // Kafka, fire-and-forget
    return ResponseEntity.status(HttpStatus.FOUND).location(URI.create(target)).build();
}

Common mistakes

  • Hashing URLs without handling collisions.
  • Using a single auto-increment database as a global bottleneck.
  • Writing click analytics synchronously in the redirect path.
  • Choosing 301 and then wondering why click counts are low.
  • No abuse protection: phishing links and enumeration of sequential codes.

How to answer in the interview

"There are two APIs: create a short link and redirect. For IDs I'd lease ranges from a distributed counter or use a Snowflake-style generator, then base62-encode, so seven characters give about 3.5 trillion codes with no collisions. The mapping lives in DynamoDB or Cassandra sharded by code. Reads dominate, so I'd cache hot links in Redis and at the CDN. I'd use 302 when we need analytics on every click, 301 when we want browsers to cache, and send click events asynchronously via Kafka. Rate limiting, malware checks and expiry complete it."

Likely follow-up questions

  • How do two servers avoid the same code? Each leases a disjoint ID range or has a unique worker ID in Snowflake.
  • Custom aliases? Conditional insert (attribute_not_exists) so a taken alias fails atomically.
  • How do you make codes non-guessable? Permute IDs with a keyed bijection or use random 8-character codes with a uniqueness check.
