What different kinds of OutOfMemoryError exist, and what does each mean?

JVM & Performance · concept · levels mid, senior

In one line

Java heap space (objects exceed -Xmx), Metaspace (too many classes or a class loader leak), GC overhead limit exceeded (almost all time spent in GC for little gain), unable to create native thread (OS, container or memory limits on threads) and Direct buffer memory (off-heap NIO buffers exceed MaxDirectMemorySize) each point to a different memory area and a different investigation.

Detailed explanation

Java heap space. An allocation could not be satisfied even after a full GC. Causes: a leak (static maps, unbounded caches, ThreadLocals), loading huge data sets into memory, or simply an undersized heap. Diagnose with a heap dump in Eclipse MAT.

Metaspace (and its sibling Compressed class space). Class metadata exceeded MaxMetaspaceSize or the compressed class space. Typical causes are class loader leaks after repeated hot redeploys in application servers, or libraries generating classes at runtime (dynamic proxies, bytecode generation, scripting engines, lambdas compiled per call through misuse). Diagnose with jcmd VM.metaspace, jcmd VM.classloader_stats, class-loading logs and a heap dump to see what keeps loaders alive.

GC overhead limit exceeded. The JVM detected that it spent the vast majority of time (about 98%) in GC while recovering only a tiny amount of heap (about 2%). It is effectively an early warning of heap exhaustion: same causes and same diagnosis as heap space.

unable to create native thread. The OS refused to create another thread. Causes: unbounded thread creation (a new Thread or executor per request), the user's process limit (ulimit -u), a container pids limit, or not enough native memory for thread stacks. A heap dump does not help; count threads with jcmd Thread.print, check ulimit and container limits, and use bounded pools or virtual threads.

Direct buffer memory. Off-heap ByteBuffer.allocateDirect memory exceeded -XX:MaxDirectMemorySize (by default roughly the max heap size). Common with Netty, NIO servers and some database drivers, from buffer leaks (not released) or bursts. Diagnose with Native Memory Tracking, Netty's leak detector and buffer pool metrics (jvm.buffer.memory.used).

Others. Requested array size exceeds VM limit (an array larger than the JVM supports) and failures to reserve memory at startup. And a Kubernetes OOMKilled is the kernel killing the process for exceeding the container limit: no Java error at all, usually because heap plus off-heap exceeded the limit.

How it works

  1. Read the exact message after OutOfMemoryError:.
  2. Map it to the area: heap, Metaspace, threads or direct memory.
  3. Collect matching evidence: heap dump, metaspace stats, thread count or NMT.
  4. Find the cause: leak, unbounded creation, or undersized limit.
  5. Fix the code first; adjust limits only with evidence.

Example

-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps -XX:+ExitOnOutOfMemoryError
-XX:MaxMetaspaceSize=256m -XX:MaxDirectMemorySize=512m
-XX:NativeMemoryTracking=summary

jcmd <pid> VM.metaspace           # Metaspace usage by class loader type
jcmd <pid> VM.native_memory summary
jcmd <pid> Thread.print | grep -c '^"'   # number of threads
cat /sys/fs/cgroup/pids.max        # container thread/process limit

Common mistakes

  • Raising -Xmx for every kind of OOM.
  • Not noticing the message type at all.
  • Confusing a container OOM kill with a Java OOM.
  • Catching OutOfMemoryError and continuing to run in a corrupt state.

How to answer in the interview

"Java heap space means live objects exceed the maximum heap, from a leak or an undersized heap. Metaspace means too many classes are loaded, often a class loader leak from redeploys or heavy runtime class generation. GC overhead limit exceeded means the JVM spends nearly all its time collecting while freeing almost nothing, so the heap is effectively full. Unable to create new native thread means the OS or container thread limit or native memory is exhausted, usually from unbounded thread creation. Direct buffer memory means off-heap NIO buffers exceeded MaxDirectMemorySize, common with Netty. Each needs different evidence: a heap dump for the first two, metaspace stats, thread counts or native memory tracking for the rest."

Likely follow-up questions

  • Which of these would a heap dump not help you diagnose? Native thread exhaustion and most direct-memory or native leaks; use thread counts and Native Memory Tracking.
  • Should you catch OutOfMemoryError? Generally no; prefer ExitOnOutOfMemoryError so the orchestrator restarts a clean instance.
  • What is an OOMKilled pod? The kernel cgroup killer terminating the process for exceeding the memory limit.
