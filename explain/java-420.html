Design an elevator control system for a building with several elevators.

Low-Level Design · design · levels senior, lead

In one line

Model an ElevatorController, several Elevators with state and direction, Floors and Requests (hall calls vs car calls); use a dispatching strategy to assign hall calls and SCAN/LOOK within each car, the State pattern for elevator behaviour, and a single event loop for concurrency.

Detailed explanation

Clarify first: number of floors and cars, capacity, whether destination-dispatch panels exist, emergency and maintenance modes, and the optimisation goal (wait time, travel time, energy).

Requests come in two kinds: hall calls (floor + direction, pressed outside) and car calls (destination pressed inside a specific car). Hall calls must be assigned to a car by the controller; car calls belong to their car.

Elevator holds current floor, direction, state, load, and two sorted sets of stops: upStops and downStops (TreeSet). Its state (Idle, MovingUp, MovingDown, DoorsOpen, OutOfService) can be modelled with the State pattern, so behaviour such as "what to do on a new request" or "on arriving at a floor" lives in each state class instead of large switch statements.

Scheduling within a car: SCAN (elevator algorithm) travels in one direction serving stops until the end, then reverses; LOOK reverses as soon as there are no further stops in the current direction, which is more efficient and realistic.

Dispatching across cars is a Strategy: a common heuristic is a cost function, preferring a car already moving towards the floor in the same direction, then an idle car closest to the floor, penalising load and number of stops. Swappable strategies allow peak-time modes (up-peak in mornings).

Concurrency: button presses and sensor events arrive concurrently. Rather than locking each object everywhere, events go into a BlockingQueue processed by the controller's single event loop, or each elevator has its own thread-confined loop receiving commands.

How it works

  1. Hall button pressed -> HallCall(floor 7, UP) event queued.
  2. Controller computes cost per car with the dispatch strategy, assigns to the best one.
  3. Elevator adds floor 7 to upStops; state machine starts moving if idle.
  4. On each floor sensor event, the elevator checks whether to stop.
  5. At a stop: DoorsOpen, timer, then continue per LOOK.
  6. Faults move the car to OutOfService; its hall calls are reassigned.

Example

enum Direction { UP, DOWN, IDLE }
sealed interface Request permits HallCall, CarCall {}
record HallCall(int floor, Direction dir) implements Request {}
record CarCall(int elevatorId, int floor) implements Request {}

interface DispatchStrategy { Elevator choose(List<Elevator> cars, HallCall call); }

final class NearestCarStrategy implements DispatchStrategy {
    public Elevator choose(List<Elevator> cars, HallCall c) {
        return cars.stream().filter(Elevator::inService)
            .min(Comparator.comparingInt(e -> e.costTo(c))).orElseThrow();
    }
}

final class Elevator {
    private final NavigableSet<Integer> upStops = new TreeSet<>(), downStops = new TreeSet<>();
    private int floor; private Direction dir = Direction.IDLE; private ElevatorState state = new Idle();
    int costTo(HallCall c) {
        boolean onTheWay = (dir == Direction.UP && c.dir() == Direction.UP && c.floor() >= floor)
                        || (dir == Direction.DOWN && c.dir() == Direction.DOWN && c.floor() <= floor);
        return Math.abs(c.floor() - floor) + (onTheWay || dir == Direction.IDLE ? 0 : 20);
    }
    boolean inService() { return !(state instanceof OutOfService); }
    // nextStop() implements LOOK using upStops.ceiling(floor) / downStops.floor(floor)
}

Common mistakes

  • Treating hall and car calls the same way.
  • A single FIFO queue of requests (serves floors in press order, not efficiently).
  • Giant switch statements on state instead of the State pattern.
  • Locks sprinkled everywhere, risking deadlock.
  • Forgetting out-of-service and capacity handling.

How to answer in the interview

"I'd model an ElevatorController, Elevators, Floors and Requests, distinguishing hall calls with a direction from car calls with a destination. Each elevator has a state, idle, moving up, moving down, doors open, out of service, modelled with the State pattern, and sorted sets of up and down stops. A dispatching strategy assigns hall calls, for example to the car moving towards the floor in the same direction, otherwise the nearest idle car. Each car serves stops with LOOK. All button and sensor events go through a queue into an event loop, so concurrency is handled in one place."

Likely follow-up questions

  • Car goes out of service mid-trip? Stop at nearest floor, open doors, mark out of service, reassign its hall calls.
  • Morning rush? Up-peak strategy parks idle cars at the lobby.
  • Destination dispatch? Passengers enter destinations in the lobby; group same-destination riders.
