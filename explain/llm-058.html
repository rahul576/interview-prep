What techniques reduce LLM costs without hurting quality too much?

LLMOps & RAG · concept · levels mid, senior

In one line

Cut costs with model routing or cascades (cheap model first, escalate when needed), prompt caching and response/semantic caching, fewer tokens in prompts, context and outputs, batch APIs for offline work, fine-tuning or distillation of small models for narrow high-volume tasks, and always measure cost per task alongside quality.

Detailed explanation

LLM cost is roughly requests x (input tokens x input price + output tokens x output price), and price differences between model tiers are often 10-30x, so the largest lever is which model handles each request.

Routing and cascades. A router (rules, a classifier or a small LLM) sends simple requests (greetings, FAQ lookups, extraction) to a small model and complex ones to a frontier model. A cascade tries the cheap model first and escalates when validation fails (invalid JSON, low confidence, judge failure). Often 70-90% of traffic never needs the big model.

Caching. Prompt caching (offered by Anthropic, OpenAI, Google and others) discounts repeated long prefixes such as system prompts, tool definitions and shared documents; structure prompts so stable content comes first. Response or semantic caching skips the call entirely for repeated generic questions.

Fewer tokens. Concise system prompts; fewer, better retrieved chunks after reranking; summarising old conversation turns instead of resending full history; compacting tool results (return the 5 fields needed, not a 20 KB JSON blob); limiting output length and asking for concise formats. Output tokens are typically several times more expensive than input tokens.

Batch APIs. Offline tasks (classification, summarising archives, evals) via batch endpoints at around 50% discount.

Smaller specialised models. For a high-volume, narrow task, fine-tuning or distilling a small model can match a large one at a fraction of the cost, especially when self-hosted at high GPU utilisation.

Reasoning budgets. Where reasoning modes are used, cap the effort or thinking budget per task.

Measure. Track cost per completed task (per resolved ticket, per document processed) with quality metrics side by side.

How it works

  1. Attribute cost by feature, model and token type.
  2. Pick the biggest line item; apply the matching lever.
  3. Evaluate quality before and after on the eval set.
  4. Roll out; monitor cost per task and quality.
  5. Repeat for the next largest item.

Example

def answer(q):
    draft = small_model(q, max_tokens=400)
    if passes_validation(draft) and confidence(draft) > 0.8:
        return draft                      # about 80% of traffic, cheap
    return large_model(q, max_tokens=600)  # escalate the hard 20%

Common mistakes

  • Using the frontier model for every call by default.
  • Putting timestamps or user data at the start of prompts, defeating prompt caching.
  • Optimising tokens without checking quality.
  • Ignoring output token costs and reasoning tokens.

How to answer in the interview

"The biggest saving is not using the largest model for everything: a router or cascade sends simple requests to a small model and escalates only when needed. Next is caching: prompt caching for long stable prefixes and semantic caching for repeated questions. Then token reduction: shorter system prompts, fewer and better chunks, summarised history, compact tool results and output limits. Offline jobs go to batch APIs at about half price, and for high-volume narrow tasks a fine-tuned or distilled small model can be far cheaper. I measure cost per completed task together with quality, so savings never silently degrade results."

Likely follow-up questions

  • What goes to the larger model? Decided by a router trained on eval data, validation failures, or task type.
  • Self-hosting cheaper? Only at high, steady utilisation; include ops costs.
  • Budget enforcement? Gateway quotas per team and alerts on cost per request.
