What is the KV cache, and why does it limit how many concurrent requests a GPU can serve?

LLMOps & RAG · concept · levels mid, senior

In one line

The KV cache stores each previous token's attention keys and values so decode does not recompute them; it grows with sequence length, layers and batch size and shares GPU memory with the weights, so it caps concurrency; mitigations are paged allocation, FP8 KV, prefix sharing and offloading.

Detailed explanation

In self-attention, each new token's query is compared with the keys of all earlier tokens and combines their values. Without a cache, generating token 1,000 would mean recomputing keys and values for the 999 tokens before it at every layer, making generation quadratic. The KV cache keeps them in GPU memory; each decode step computes keys and values only for the new token and appends them.

The cost is memory. Per token, the cache holds 2 (K and V) x layers x KV heads x head dimension x bytes. For a Llama-3-style 70B model (80 layers, 8 KV heads thanks to grouped-query attention, head dim 128, BF16) that is about 320 KB per token. A single 32K-token conversation needs about 10 GB; 64 such conversations would need 640 GB.

On an 80 GB GPU (or a group of GPUs), the weights take a fixed chunk; what is left is the KV budget, and that budget, measured in tokens, decides how many sequences can run at once. Concurrency is therefore not "requests" but "total cached tokens": a few long-context users can consume as much cache as dozens of short chats. When the cache is full, engines queue new requests or preempt running ones (swapping or recomputing), and throughput and latency degrade.

Mitigations:

  • PagedAttention allocates the cache in small blocks on demand, avoiding fragmentation and over-reservation.
  • Quantised KV cache (FP8, sometimes INT4) roughly halves memory.
  • Prefix caching/sharing stores a common system prompt once for many requests.
  • Offloading cold blocks to CPU memory or SSD tiers (for example LMCache).
  • Architectural choices like GQA/MQA, multi-head latent attention, and sliding-window attention reduce cache size per token.

How it works

  1. Prefill writes K and V for every prompt token in every layer.
  2. Each decode step computes K and V for one new token and appends them.
  3. Attention reads the whole cache for that sequence.
  4. The scheduler admits requests only while cache blocks are free.
  5. When a sequence ends, its blocks are freed or kept for prefix reuse.

Example

vllm serve meta-llama/Llama-3.1-70B-Instruct \
  --tensor-parallel-size 4 \
  --gpu-memory-utilization 0.90 \
  --max-model-len 32768 \
  --kv-cache-dtype fp8 \
  --enable-prefix-caching
# Startup log reports the KV cache size in tokens and the max concurrency at max-model-len

Common mistakes

  • Sizing GPUs from weight size only.
  • Allowing 128K context on a deployment sized for short chats.
  • Thinking concurrency is a fixed number of requests rather than tokens.
  • Ignoring preemption metrics when latency spikes.

How to answer in the interview

"The KV cache stores the attention keys and values of all previous tokens so each decode step only computes them for the new token instead of recomputing the whole sequence. Its size grows linearly with sequence length, number of layers and KV heads, and the number of sequences in the batch, so long prompts can take gigabytes each. It shares GPU memory with the weights, so whatever is left after loading the model decides how many tokens, and therefore requests, can run concurrently. Engines mitigate it with paged allocation, FP8 KV caches, prefix sharing and CPU offload."

Likely follow-up questions

  • Why might longer prompts collapse throughput? Each request takes more cache, so fewer fit, and preemption starts.
  • What is GQA? Several query heads share one key/value head, shrinking the cache.
  • Does prefix caching save memory? Yes, shared prefix blocks are stored once and reused.
