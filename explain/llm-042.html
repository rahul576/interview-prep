Your RAG endpoint takes eight seconds per answer. How do you bring latency down?

LLMOps & RAG · scenario · levels mid, senior

In one line

Measure each stage (rewrite, embed, search, rerank, prompt build, time to first token, generation), then fix the biggest: stream output, use smaller models for auxiliary steps, send fewer, better chunks, prompt caching, parallel and cached retrieval, tuned index and reranker, and co-located, warm endpoints.

Detailed explanation

Eight seconds is an average of several stages, and without tracing you will optimise the wrong one. Instrument a request with spans (OpenTelemetry works well) and look at p50 and p95 per stage.

Usually generation dominates: time to first token (driven by prompt length, model size and provider load) plus output tokens divided by tokens per second. The second offender is extra LLM calls before retrieval, such as query rewriting, classification or HyDE, each adding a full round trip.

Fixes by stage:

  • Perceived latency: stream tokens so users see text within about a second; show sources early.
  • Pre-retrieval calls: use a small, fast model for rewriting, skip rewriting for first-turn standalone questions, or merge classification and rewriting into one call.
  • Context size: 20 chunks of 800 tokens is 16k tokens of prefill; after reranking, 5 good chunks often answer better and faster.
  • Prompt caching: put the stable system prompt and tool definitions first so the provider can cache the prefix.
  • Output length: concise answer instructions and a sensible max token limit.
  • Retrieval: run vector, keyword and other sources in parallel; cache query embeddings and results for frequent questions; tune ANN parameters (for HNSW, ef_search) for the recall/latency balance.
  • Reranking: limit to 20-50 candidates or use a smaller cross-encoder.
  • Infrastructure: same region for app, search and model; keep connections and self-hosted endpoints warm.

How it works

  1. Trace and build a per-stage latency breakdown.
  2. Fix perceived latency with streaming.
  3. Remove or shrink pre-retrieval LLM calls.
  4. Trim context and output; enable prompt caching.
  5. Parallelise and cache retrieval; tune index and reranker.
  6. Re-measure and check quality did not drop.

Example

Before (p50)                      After
rewrite (large model)   1.4 s  -> small model / skipped  0.3 s
embed + search          0.6 s  -> parallel, cached       0.3 s
rerank 100 chunks       0.9 s  -> 30 chunks              0.3 s
TTFT (16k ctx)          2.1 s  -> 5k ctx + cache         0.8 s
generation (600 tok)    3.0 s  -> 300 tok, streamed      1.5 s (first text at ~1.7 s)
total                   8.0 s  -> 3.2 s

Common mistakes

  • Optimising the vector database when generation is 70% of the time.
  • Sending every retrieved chunk "just in case".
  • Variable content at the start of the prompt, breaking prompt caching.
  • Measuring averages only, not p95.

How to answer in the interview

"I'd trace a request and measure every stage: rewrite, embedding, search, rerank, prompt build, time to first token and generation. Usually generation dominates, followed by LLM calls before retrieval. So I'd stream the answer, use a small model for query rewriting or skip it when not needed, send fewer, better chunks after reranking, put stable content first for prompt caching, and limit output length. On retrieval I'd parallelise sources, cache embeddings for frequent queries, tune index parameters and limit reranking candidates. Then I'd verify that quality held, because latency gains that hurt answers aren't gains."

Likely follow-up questions

  • Latency budget per stage? For example rewrite 300 ms, retrieval 300 ms, rerank 300 ms, TTFT under 1 s.
  • Speculative retrieval? Start retrieving with the raw query while rewriting runs in parallel.
  • Self-hosted? Continuous batching, KV cache sizing, quantisation, speculative decoding.
