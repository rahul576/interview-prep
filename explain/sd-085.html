Design the evaluation and monitoring setup for LLM features running in production.

AI & ML System Design · design · levels mid, senior

In one line

Treat prompts and models like code: offline evaluation sets (real + edge cases), scored by metrics, LLM-as-judge with rubrics and human review, run as regression tests on every change; in production track feedback, latency, cost, errors, trace every request, and monitor safety and drift with alerts.

Detailed explanation

LLM features fail quietly: a prompt tweak or model upgrade can improve one case and break ten others. Without evaluation you only find out from users.

Offline: build an evaluation set per feature: anonymised real queries, tricky edge cases, adversarial prompts (injection, jailbreaks), and past failures, with expected answers or grading criteria. Score with:

  • deterministic checks (JSON validity, contains citation, exact match),
  • retrieval metrics for RAG (recall@k, context precision),
  • LLM-as-judge with explicit rubrics (faithfulness, relevance, tone), calibrated against periodic human grading.

Run in CI for every prompt, model, retrieval or tool change; block regressions.

Online: user signals (thumbs, edits, copy, task completion, escalation to human), latency (TTFT, total), tokens and cost per request, error/refusal rates. Tracing (Langfuse, LangSmith, Arize Phoenix, OpenTelemetry GenAI conventions) records prompt, retrieved context, tool calls and output, so you can debug a bad answer end to end.

Safety & drift: sample production traffic for policy violations, hallucinations and PII leakage; watch topic/intent mix shifting; alert on spikes. New models/prompts roll out via A/B tests or shadow runs.

How it works

  1. Change PR → eval suite runs → scores compared to baseline → pass/fail.
  2. Deploy behind flag → canary/A/B.
  3. Production traces + feedback → dashboards.
  4. Weekly: sample review, add new failures to the eval set.

Example

eval: support-answer-v3
dataset: evals/support_golden.jsonl   # 400 cases
metrics:
  - faithfulness_judge >= 0.90
  - citation_present == 1.0
  - p95_latency_ms <= 4000
fail_if_regression: 2%

Common mistakes

  • Judging changes by trying five prompts manually.
  • LLM-as-judge without calibration against humans.
  • Tracing without redacting personal data.
  • Eval sets that never grow.

How to answer in the interview

"Each LLM feature gets an evaluation set of real and edge-case examples, scored automatically and with a calibrated LLM judge, and it runs as a regression gate in CI for any prompt, model or retrieval change. In production I track user feedback, latency, cost and errors, trace every request including retrieval and tool calls, and sample traffic for safety and drift with alerts. New versions roll out through A/B tests."

Likely follow-up questions

  • No production traffic yet? Synthetic queries from docs, internal dogfooding, expert-written cases.
  • Judge bias? Swap answer order, use rubrics, compare with human labels.
  • Which online metric matters most? Task success (resolution, acceptance), not thumbs alone.
