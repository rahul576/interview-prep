What does set -euo pipefail do in a Bash script, and what other practices make scripts robust?

Scripting · concept · levels entry, mid

In one line

set -e exits on errors, set -u fails on unset variables and set -o pipefail makes a pipeline fail if any part fails; combine them with quoting, ShellCheck, trap cleanup and clear logging for robust scripts.

Detailed explanation

By default Bash happily continues after a failed command, treats unset variables as empty strings and reports only the last command's status in a pipeline. All three hide failures, and hidden failures in deployment scripts are dangerous.

set -e (errexit) exits when a simple command returns non-zero. set -u (nounset) makes referencing an unset variable an error, which catches typos: with rm -rf "$BUILD_DIR/"* and a misspelt variable, -u stops the script instead of deleting from /. set -o pipefail makes a pipeline return the status of the last command that failed, so curl ... | jq . fails when curl fails, not only when jq does.

set -e has well-known exceptions: it is ignored for commands in if, while and until conditions, in &&/|| lists except the last command, and in commands negated with !; it is also disabled inside functions called from those contexts. local var=$(cmd) hides the failure because local succeeds. So -e is a safety net, not a substitute for checking important commands.

Other practices: quote variables ("$var") to avoid word splitting and globbing; lint with ShellCheck in CI; use trap ... EXIT to remove temporary files and release locks; use local in functions; mktemp for temp files; log with timestamps to stderr; make scripts idempotent; and switch to Python once logic, data structures or error handling grow complex.

How it works

  1. Start with #!/usr/bin/env bash and set -euo pipefail.
  2. Default optional variables with ${VAR:-default}.
  3. Create temp files with mktemp and clean them in trap.
  4. Quote every expansion; check important commands explicitly.
  5. Run ShellCheck in CI.

Example

#!/usr/bin/env bash
set -euo pipefail

ENVIRONMENT="${1:?usage: deploy.sh <env>}"
TMP="$(mktemp -d)"
trap 'rm -rf "$TMP"' EXIT

log() { printf '%s %s\n' "$(date -Is)" "$*" >&2; }

log "Fetching release manifest for $ENVIRONMENT"
curl -fsS "https://releases.example.com/$ENVIRONMENT.json" | jq -r '.version' > "$TMP/version"
log "Deploying version $(cat "$TMP/version")"

Common mistakes

  • Assuming set -e catches failures inside if conditions or && chains.
  • local out=$(cmd) masking the command's exit code.
  • Unquoted variables breaking on spaces.
  • Using curl without -f, so HTTP errors look like success.

How to answer in the interview

"set -e makes the script exit as soon as a command fails instead of carrying on. -u treats unset variables as errors, which catches typos before something like rm -rf runs on an empty path. pipefail makes a pipeline fail if any command in it fails, not just the last. Together they make failures loud. I also quote all variables, lint with ShellCheck, use trap to clean up temp files on exit, use local variables in functions and log clearly. I know set -e has exceptions, like in if conditions, so important commands still get explicit checks, and complex logic moves to Python."

Likely follow-up questions

  • Where does set -e not behave as expected? In if/while conditions, && and || lists, negated commands and local var=$(cmd).
  • How do you debug a script? set -x, optionally with a PS4 showing line numbers.
  • What does ${VAR:?msg} do? Exits with the message if VAR is unset or empty.
