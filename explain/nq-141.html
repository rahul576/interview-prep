What is the Singleton pattern, and how do you implement a thread-safe Singleton?

Design Patterns · concept · levels entry, mid

In one line

A Singleton guarantees exactly one instance with a global access point (private constructor + static accessor); thread-safe options are eager static final, the holder idiom, double-checked locking with volatile, or an enum, though in Spring you should prefer container-managed singleton beans.

Detailed explanation

The basic shape is a private constructor so nobody else can call new, a static field holding the instance and a static getInstance(). The naive lazy version, if (instance == null) instance = new Singleton();, is not thread-safe: two threads can both see null and create two instances.

Thread-safe implementations:

  1. Eager initialisation: private static final Singleton INSTANCE = new Singleton(); The JVM initialises a class exactly once under an internal lock, so this is safe. The instance is created when the class is first initialised (usually on first use of getInstance()), so it is "lazy enough" in many cases.
  2. Initialization-on-demand holder: a private static nested Holder class holds the instance; it is initialised only when getInstance() references it. Lazy, lock-free on reads, and guaranteed by the Java Language Specification.
  3. Double-checked locking: check, synchronise, check again, assign to a volatile field. Lazy and fast, but easy to get wrong.
  4. Enum: enum Singleton { INSTANCE; } Thread-safe and also immune to reflection and serialization creating duplicates.
  5. synchronized getInstance(): correct but every call contends for a lock.

Drawbacks: a singleton is global state. It hides dependencies (classes reach out instead of receiving collaborators), complicates unit tests (state leaks between tests, hard to mock), and becomes a concurrency hotspot if mutable. One instance is per class loader, not per JVM. In Spring applications I let the container manage singleton-scoped beans and inject them, which gives one shared instance without these problems.

How it works

  1. Private constructor blocks external instantiation.
  2. A static field holds the single instance.
  3. Initialisation is protected by class-loading guarantees, locking or enum semantics.
  4. Callers use getInstance() or Enum.INSTANCE.

Example

// Eager
public final class Clock1 {
    private static final Clock1 INSTANCE = new Clock1();
    private Clock1() {}
    public static Clock1 getInstance() { return INSTANCE; }
}

// Lazy holder
public final class Config {
    private Config() {}
    private static class Holder { static final Config INSTANCE = new Config(); }
    public static Config getInstance() { return Holder.INSTANCE; }
}

// Enum
public enum Metrics { INSTANCE; public void inc(String name) { /* ... */ } }

Common mistakes

  • Using the unsynchronised lazy check in multi-threaded code.
  • Double-checked locking without volatile.
  • Forgetting readResolve() for serializable singletons.
  • Writing singletons in Spring apps instead of using beans.

How to answer in the interview

"A Singleton ensures one instance and a global access point, with a private constructor and a static getInstance. For thread safety I'd pick eager initialisation with a static final field, which is safe because class initialisation is thread-safe, or the lazy holder idiom, where a nested class creates the instance on first access without locking. Double-checked locking with a volatile field also works, and an enum singleton additionally handles serialization and reflection. A synchronized getInstance works but locks every call. In Spring I prefer container-managed singleton beans, because hand-written singletons are global state and hard to test."

Likely follow-up questions

  • How can reflection or serialization break it? Reflection calls the private constructor; deserialisation creates a new object without readResolve. Enums prevent both.
  • Is the eager version lazy? Class initialisation happens on first active use, so it is often effectively lazy.
  • Are singletons an anti-pattern? Often when they hold mutable global state; acceptable for stateless, injected services.
