How do vulnerability and security scans fit into a deployment pipeline?

DevOps & CI/CD · concept · levels mid

In one line

Security scans are shifted left into every PR: secret scanning, SAST on code, SCA on dependencies, container image and IaC scanning at build time, DAST against a deployed test environment; builds fail on critical/high findings with an exception process, and pipelines produce an SBOM and sign images.

Detailed explanation

Finding a vulnerability in a PR costs minutes; finding it in production costs incidents. So each scan runs at the earliest stage where it makes sense:

  • Secret scanning: pre-commit hooks and server-side checks (GitHub secret scanning with push protection, Gitleaks) to stop credentials being committed.
  • SAST: analyses source code for injection, path traversal, insecure deserialisation: CodeQL, SonarQube, Semgrep.
  • SCA: checks dependencies, including transitive ones, against CVE databases: Snyk, OWASP Dependency-Check, Dependabot.
  • Container scanning: Trivy or Grype scan OS packages and libraries in the image; use minimal base images.
  • IaC scanning: Checkov, Trivy config or KICS for Terraform, Helm and Kubernetes manifests (public buckets, privileged pods).
  • DAST: OWASP ZAP probes the running API in a test environment.

Policy: fail on critical and high severity (ideally considering exploitability, such as known exploited vulnerabilities), with a documented, time-limited exception process. Produce an SBOM (CycloneDX or SPDX) for each artifact and sign images with cosign, so clusters can admit only signed images. Keep scanning registries continuously, since new CVEs appear for images already deployed.

How it works

  1. Pre-commit and PR: secrets, SAST, SCA.
  2. Build: image scan, IaC scan, SBOM generation.
  3. Publish: sign the image and attach the SBOM.
  4. Test environment: DAST.
  5. Deploy: admission policy verifies signatures.
  6. Runtime: continuous re-scanning and alerts.

Example

- name: Scan image
  uses: aquasecurity/trivy-action@master
  with:
    image-ref: ${{ env.IMAGE }}
    severity: CRITICAL,HIGH
    exit-code: '1'
    ignore-unfixed: true
- run: syft $IMAGE -o cyclonedx-json > sbom.json
- run: cosign sign --yes $IMAGE

Common mistakes

  • Scanning only before a release.
  • Failing builds on every low finding, causing alert fatigue and bypasses.
  • Ignoring transitive dependencies.
  • Exceptions with no expiry.

How to answer in the interview

"I build security into the pipeline and shift it left. On every pull request we run secret scanning, SAST with CodeQL or Sonar, and dependency scanning with Snyk or Dependabot for known CVEs. When the image is built, Trivy scans it and Checkov scans Terraform and Kubernetes manifests. After deploying to a test environment, OWASP ZAP probes the running API. The build fails on critical or high findings, with a documented, time-limited exception process, and we generate an SBOM and sign images so only signed images can run."

Likely follow-up questions

  • Critical CVE in a transitive dependency? Check reachability, upgrade the parent or pin the transitive version, or apply a time-limited exception with mitigation.
  • SAST vs DAST? SAST reads code; DAST attacks the running application.
  • What is an SBOM for? Knowing exactly which components each artifact contains, to respond to new CVEs fast.
