How does object ownership and lifecycle differ in these three relationships?

Core Java & OOP · concept · levels mid

In one line

In association nobody owns anybody and lifecycles are independent; in aggregation the whole holds but does not control the parts' lifecycle; in composition the whole exclusively owns and controls the parts' creation and destruction, which in JPA means cascade + orphanRemoval.

Detailed explanation

Ownership answers the question "who is responsible for this object's existence?"

Association: no ownership. Both objects are created and destroyed independently by other code. A customer references their relationship manager; deleting the customer doesn't delete the manager, and vice versa. Each side just keeps a reference. Removing the link only removes the reference.

Aggregation: weak ownership. The whole groups parts and may manage membership, but not existence. A department holds professors; closing the department means professors are reassigned, not deleted. A part can belong to several wholes or move between them. The aggregating object must therefore never assume it can free, mutate the identity of, or delete its parts.

Composition: exclusive ownership. The whole controls the part's full lifecycle:

  • Creation: parts are created by or through the whole (order.addLine(...)).
  • Exclusivity: a part belongs to exactly one whole and cannot be moved.
  • Destruction: deleting the whole deletes its parts; removing a part from the whole means the part ceases to exist.
  • Consistency: invariants spanning whole and parts (order total, max lines) are enforced by the whole, which is the DDD aggregate root idea.

Persistence consequences are where mistakes get expensive:

  • Composition: @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true); or @Embedded / @ElementCollection for value objects. Saving the order saves lines; removing a line from the collection deletes its row; deleting the order deletes all lines. DB foreign keys can use ON DELETE CASCADE.
  • Aggregation and association: no REMOVE cascade, often no cascade at all; deleting the whole should just remove join rows or null out foreign keys, typically with ON DELETE SET NULL or restricted deletes.

In memory, Java's GC handles destruction, but ownership still matters for who may modify the parts, thread safety, and defensive copying.

How it works

  1. Decide who creates the part.
  2. Decide whether the part can be shared or moved.
  3. Decide what happens to the part when the whole is deleted or the link is removed.
  4. Encode it: creation methods, encapsulation, cascades and FK rules.

Example

@Entity
class PurchaseOrder {                               // composition
    @Id @GeneratedValue Long id;
    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<OrderLine> lines = new ArrayList<>();
    void addLine(String sku, int qty) { lines.add(new OrderLine(this, sku, qty)); }
    void removeLine(OrderLine l)      { lines.remove(l); }   // row deleted by orphanRemoval
}

@Entity
class Department {                                  // aggregation
    @Id @GeneratedValue Long id;
    @OneToMany(mappedBy = "department")             // no cascade remove
    private Set<Professor> professors = new HashSet<>();
}

Common mistakes

  • CascadeType.ALL on @ManyToMany or on aggregations, deleting shared data.
  • Exposing composition parts so other entities hold them.
  • Forgetting orphanRemoval, leaving orphan rows.
  • Modelling each composition part as an independently managed repository entity.

How to answer in the interview

"In association nobody owns anybody: both objects are created and destroyed independently and just reference each other. In aggregation the whole holds the parts but doesn't control their life: removing a department doesn't delete its professors, who can join another department. In composition the whole exclusively owns the parts: creating an order creates its lines, deleting the order deletes them, and a line can't move to another order. This matters in persistence: in JPA I map composition with cascade ALL and orphanRemoval, while aggregations must never cascade deletes."

Likely follow-up questions

  • What could go wrong if you cascade deletes on an aggregation? Deleting the whole wipes shared parts still used elsewhere.
  • What does orphanRemoval do? Deletes a child row when it is removed from the parent's collection.
  • How does this relate to DDD aggregates? The aggregate root owns its internal entities as compositions.
