How do you check and manage disk space and mounts in Linux?

Linux · concept · levels entry, mid

In one line

Use df -h for filesystem usage, du to find large directories, df -i for inode exhaustion, lsblk, mount and /etc/fstab for disks and mounts, and clean up with logrotate, journal vacuuming, package and container image pruning.

Detailed explanation

df -h reports each mounted filesystem's size, used, available space and mount point in human-readable units; add -T to see the filesystem type. Once you know which filesystem is full, du finds where the space goes: du -xh --max-depth=1 /var | sort -h lists subdirectories by size while staying on one filesystem (-x). Drill down level by level, or use the interactive ncdu.

Space is not the only limit. Every file needs an inode, and ext4 creates a fixed number at format time. Millions of tiny files (session files, cache entries, mail queues) can exhaust them, so writes fail with "No space left on device" while df -h still shows free space. df -i reveals this. A mismatch where df shows full but du does not usually means a deleted file still held open, found with lsof +L1.

lsblk shows disks, partitions, sizes and mount points; blkid shows UUIDs and filesystem types. mount attaches a filesystem to a directory, and findmnt shows the mount tree. Mounts that must survive reboots go in /etc/fstab, referenced by UUID rather than device names like /dev/sdb1, which can change. Use nofail for non-critical disks so a missing disk does not block boot, and test with mount -a before rebooting.

Common clean-up: logrotate to rotate and compress logs, journalctl --vacuum-size=500M to shrink the systemd journal (and SystemMaxUse= to cap it), apt autoremove and apt clean or dnf clean all for old packages, and docker system prune or crictl rmi --prune for unused images. Long-term, alert on disk usage before it hits 100%.

How it works

  1. df -h and df -i identify the full filesystem.
  2. du -xh --max-depth=1 drills into the largest directories.
  3. lsof +L1 checks for deleted-but-open files.
  4. Clean up or move data; fix the source of growth.
  5. Add capacity or mounts via lsblk, mount and fstab if needed.

Example

df -hT
df -i /
sudo du -xh --max-depth=1 /var | sort -h | tail
lsblk -f
sudo journalctl --vacuum-size=500M
docker system prune -af --filter "until=168h"
# /etc/fstab
UUID=3f2a9c1e-8b7d-4e21-9a55-0c1d2e3f4a5b  /data  xfs  defaults,nofail  0  2

Common mistakes

  • Using device names instead of UUIDs in fstab.
  • Rebooting with an untested fstab entry and failing to boot.
  • Deleting active log files instead of rotating them.
  • Forgetting inodes when df shows free space.

How to answer in the interview

"df -h shows how full each mounted filesystem is, and du -sh or du with max-depth inside a directory shows which subdirectories use the space, so I drill down from the top, staying on one filesystem. A filesystem can also run out of inodes with millions of tiny files, which df -i shows. lsblk lists disks and partitions, mount attaches a filesystem, and /etc/fstab, using UUIDs, defines persistent mounts, which I test with mount -a. To clean up I rotate logs with logrotate, vacuum the journal, remove old packages and prune unused container images."

Likely follow-up questions

  • How would you safely extend a disk on a cloud VM? Snapshot, resize the volume in the cloud, then growpart and resize2fs or xfs_growfs online.
  • Why might df show full but du shows less? Deleted files held open, or files hidden under a mount point.
  • What does nofail do? Lets boot continue if that disk is missing.
