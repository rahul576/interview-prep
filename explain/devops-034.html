Explain the components of an AWS VPC and the difference between security groups and NACLs.

Cloud (AWS) · concept · levels mid

In one line

A VPC is your isolated network in a region, split into public and private subnets per AZ, wired together by route tables, an internet gateway and NAT gateways; security groups are stateful, allow-only firewalls on ENIs, while NACLs are stateless, ordered allow/deny rules on subnets.

Detailed explanation

A VPC gets one or more CIDR blocks (for example 10.20.0.0/16) and lives in one region. You carve it into subnets, and each subnet sits in exactly one availability zone, so a resilient layout has a public and a private subnet in each of two or three AZs.

What makes a subnet "public" is not a checkbox but its route table: a route 0.0.0.0/0 → igw-… to an internet gateway. A private subnet has no such route; for outbound access (patches, external APIs) it routes 0.0.0.0/0 to a NAT gateway that lives in a public subnet, ideally one per AZ so an AZ failure does not cut egress everywhere.

Security groups attach to network interfaces (EC2, RDS, Lambda in a VPC, load balancers). They contain only allow rules, are stateful (return traffic is allowed automatically), and can reference other security groups, e.g. "allow 5432 from the app SG", which is cleaner than IP ranges. Network ACLs apply to a whole subnet, are stateless, and rules are evaluated in number order, first match wins, with both allow and deny. Because they are stateless, you must also allow return traffic on ephemeral ports (1024-65535). Custom NACLs deny everything until you add rules.

How it works

  1. Create the VPC with a non-overlapping CIDR.
  2. Create public and private subnets in each AZ.
  3. Attach an internet gateway; give public subnets a route to it.
  4. Place NAT gateways in public subnets; point private route tables at them.
  5. Apply security groups per tier (ALB → app → DB) and, if needed, NACLs as a coarse subnet-level guard, for example to block a known bad CIDR.
  6. Add VPC endpoints for AWS services and enable VPC Flow Logs for troubleshooting.

Example

resource "aws_security_group_rule" "db_from_app" {
  type                     = "ingress"
  from_port                = 5432
  to_port                  = 5432
  protocol                 = "tcp"
  security_group_id        = aws_security_group.db.id
  source_security_group_id = aws_security_group.app.id
}

resource "aws_network_acl_rule" "deny_bad_range" {
  network_acl_id = aws_network_acl.public.id
  rule_number    = 90
  egress         = false
  protocol       = "-1"
  rule_action    = "deny"
  cidr_block     = "203.0.113.0/24"
}

Common mistakes

  • A single NAT gateway for all AZs, which is a hidden single point of failure and adds cross-AZ data charges.
  • Custom NACLs that forget ephemeral return ports, breaking connections mysteriously.
  • Opening security groups to 0.0.0.0/0 on SSH or database ports.

How to answer in the interview

"A VPC is an isolated network with its own CIDR, split into public and private subnets in each availability zone. Public subnets route to an internet gateway; private ones send outbound traffic through a NAT gateway, one per AZ. Route tables decide where each subnet's traffic goes, including peering, Transit Gateway and VPC endpoints. Security groups are stateful allow-only firewalls on the network interface, and I chain them by referencing other groups. NACLs are stateless, numbered allow and deny rules at the subnet boundary, so return traffic on ephemeral ports must be allowed."

Likely follow-up questions

  • How does a private instance reach S3 without the NAT gateway? A gateway VPC endpoint for S3 added to the private route table, free and private.
  • Can a security group deny traffic? No; it only allows, so explicit blocks need a NACL or a network firewall.
  • How do you debug blocked traffic? VPC Flow Logs (ACCEPT/REJECT) and Reachability Analyzer.
