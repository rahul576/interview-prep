How would you prevent SQL injection in a Java application?

Security · concept · levels senior, lead

In one line

Prevent SQL injection with parameterised queries everywhere: PreparedStatement bind variables, JPA/Spring Data named parameters, never string concatenation; whitelist dynamic identifiers like sort columns, and add least-privilege DB users, validation and static analysis as defence in depth.

Detailed explanation

SQL injection happens when user input becomes part of the SQL text and so changes the query's structure. With "... WHERE email = '" + email + "'", the input ' OR '1'='1 returns every row, and other payloads can read other tables or modify data. With a bind parameter, the database receives the SQL with placeholders and the values separately; the value can never be parsed as SQL, whatever characters it contains.

In Java that means PreparedStatement with ? placeholders in JDBC, JdbcTemplate and NamedParameterJdbcTemplate with arguments, :name parameters in JPQL and native @Query methods, the Criteria API, jOOQ or QueryDSL. Spring Data derived queries such as findByEmail are parameterised automatically. The danger is code that concatenates inside these tools, such as createQuery("... " + input) or a native query assembled with String.format.

Parameters only work for values. Table names, column names, ORDER BY fields and sort directions cannot be bound, so map them through a whitelist, for example an enum or a Map of allowed sort keys, and reject anything else. LIKE patterns should be bound too, escaping % and _ if needed.

Defence in depth limits damage if something slips through: validate input types and lengths, connect with a least-privilege database account that cannot drop tables or read other schemas, avoid detailed SQL errors in responses, run SAST tools (SpotBugs with FindSecBugs, Sonar, Semgrep, CodeQL) in CI, test with tools like sqlmap or OWASP ZAP, and optionally add a WAF.

How it works

  1. Write SQL with placeholders.
  2. The driver sends the statement and parameter values separately.
  3. The database parses and plans the statement once, treating values as data.
  4. Dynamic identifiers go through a whitelist before reaching SQL.
  5. CI scanners flag concatenated queries; reviews check native queries.

Example

// Vulnerable
String sql = "select * from users where email = '" + email + "'";

// Safe JDBC
try (PreparedStatement ps = con.prepareStatement("select * from users where email = ?")) {
    ps.setString(1, email);
    ResultSet rs = ps.executeQuery();
}

// Safe Spring Data
@Query("select u from User u where u.email = :email")
Optional<User> byEmail(@Param("email") String email);

// Whitelisted sort column
private static final Map<String, String> SORT = Map.of("name", "u.name", "created", "u.createdAt");
String column = Optional.ofNullable(SORT.get(sortParam)).orElseThrow(BadRequestException::new);

Common mistakes

  • Believing that JPA or Hibernate automatically makes concatenated JPQL safe.
  • Escaping quotes manually instead of binding.
  • Passing a user-supplied sort field straight into ORDER BY.
  • Using a database admin account for the application.

How to answer in the interview

"SQL injection happens when input is concatenated into the SQL string and changes the query. My main defence is parameterised queries everywhere: PreparedStatement with bind variables in JDBC, named parameters in JPQL and Spring Data @Query, including native queries, and never building SQL with string concatenation. Identifiers like a sort column cannot be parameters, so I map them through a whitelist. On top I validate input, use a least-privilege database user, keep SQL errors out of responses, and run static analysis in CI and security tests as defence in depth."

Likely follow-up questions

  • Is a Spring Data derived method like findByEmail safe? Yes, the value is bound as a parameter.
  • Are stored procedures safe? Only if they do not build dynamic SQL from parameters inside.
  • What is second-order injection? Stored input later used unsafely in another query; bind it there too.
