How does the A2A protocol let agents from different vendors work together?

AI Agents & AIOps · concept · levels mid, senior

In one line

A2A (Agent2Agent), started by Google and now a Linux Foundation project, lets independent agents collaborate: agents publish Agent Cards describing skills, endpoint and auth; clients send messages that create tasks; tasks move through states (working, input-required, completed, failed) with streaming updates and artifacts, over HTTP with JSON-RPC (and other bindings), while agents stay opaque.

Detailed explanation

MCP connects an agent to tools and data; A2A connects agents to other agents, possibly built on different frameworks by different vendors or companies. Google announced it in April 2025 and later donated it to the Linux Foundation, with broad industry backing.

Discovery uses the Agent Card, a JSON document typically served at a well-known URL (/.well-known/agent-card.json). It describes the agent's name, description, provider, service endpoint, skills with examples, supported input and output modes, capabilities such as streaming and push notifications, and security schemes such as OAuth 2.0, API keys or OpenID Connect. Client agents read cards to decide whom to delegate to.

Interaction centres on tasks. The client sends a message, for example via message/send or message/stream; the remote agent may answer directly or create a task with an ID. The task has a lifecycle of states including submitted, working, input-required, completed, failed, canceled and rejected. Progress arrives via Server-Sent Events streaming, or via push notifications to a webhook for long-running work. Results are returned as artifacts, composed of parts such as text, files or structured JSON data.

If the remote agent needs clarification or approval, it sets the task to input-required; the client then sends another message in the same task context.

A2A is built on familiar web standards: HTTPS, JSON-RPC 2.0, with gRPC and REST bindings added in later versions. Crucially, agents are opaque: they share capabilities and results, not their internal prompts, tools, memory or chain of reasoning, which makes cross-company collaboration feasible.

How it works

  1. Remote agent publishes an Agent Card with skills and auth requirements.
  2. Client agent discovers the card and authenticates.
  3. Client sends a message; remote agent creates a task.
  4. Remote agent works autonomously, streaming status updates.
  5. If needed, task goes to input-required; client supplies more input.
  6. Task completes with artifacts, or fails or is cancelled.

Example

{
  "name": "Travel Booking Agent",
  "description": "Searches and books business travel within company policy",
  "url": "https://agents.travelco.example/a2a",
  "version": "1.2.0",
  "capabilities": { "streaming": true, "pushNotifications": true },
  "defaultInputModes": ["text/plain", "application/json"],
  "defaultOutputModes": ["application/json"],
  "securitySchemes": { "oauth": { "type": "oauth2", "flows": { "clientCredentials": { "tokenUrl": "https://auth.travelco.example/token", "scopes": {} } } } },
  "skills": [
    { "id": "book_flight", "name": "Book flight", "description": "Find and hold flights matching policy", "examples": ["Book LHR to BLR on 12 May, economy"] }
  ]
}

Common mistakes

  • Treating A2A as a replacement for MCP rather than a complement.
  • Trusting remote agent outputs without validation.
  • Ignoring authentication and authorisation per skill.
  • No timeouts or cancellation for delegated tasks.

How to answer in the interview

"A2A, the Agent2Agent protocol, started by Google and now under the Linux Foundation, standardises how independent agents talk to each other regardless of vendor. Each agent publishes an Agent Card at a well-known URL describing its skills, endpoint, capabilities like streaming, and authentication. A client sends a message that creates a task; the remote agent works on it, and the task moves through states like working, input-required, completed or failed, with streamed updates and artifacts as results. If it needs clarification, it asks via input-required. It runs over HTTP with JSON-RPC and standard auth. Agents stay opaque, keeping internal tools and memory private, and it complements MCP, which is for tools."

Likely follow-up questions

  • Trust and contract questions with another company's agent? Authentication, data handling, liability, SLAs, auditability, and validating outputs before acting.
  • How are long tasks handled? Streaming via SSE or push notifications to a webhook.
  • Can an agent be both MCP client and A2A server? Yes, commonly: it uses MCP tools internally and exposes skills via A2A.
