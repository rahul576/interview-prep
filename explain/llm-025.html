How do you choose a chunking strategy for RAG?

LLMOps & RAG · concept · levels mid, senior

In one line

Chunking balances precision (small chunks) against context completeness (large chunks): start with a few hundred tokens with overlap, prefer structure-aware splitting (headings, sections, tables), consider semantic chunking, enrich chunks with titles, section paths and context, and evaluate with retrieval metrics.

Detailed explanation

Retrieval returns chunks, so a chunk is the unit of both matching and answering. Small chunks (one to three sentences) produce focused embeddings that match specific questions well, but often lack the surrounding context needed to answer, and the answer may span several chunks. Large chunks (several pages) carry more context but dilute the embedding (many topics averaged into one vector), match less precisely, and waste prompt tokens.

A common baseline is 300 to 800 tokens with 10 to 20 percent overlap, so sentences split at a boundary appear in both neighbours. Use the embedding model's token limit as a hard ceiling.

Better than fixed windows is structure-aware splitting: follow the document's own hierarchy, splitting by headings and sections, then paragraphs, keeping list items, code blocks and tables intact. Recursive and header-based splitters do this. Tables deserve special handling: keep header rows with each table chunk, or convert rows to text such as "Plan: Gold, Price: 40 EUR".

Semantic chunking computes embeddings of consecutive sentences and splits where similarity drops, so each chunk covers one topic; it costs more at ingestion and is not always better.

Enrichment often matters more than size. Prefix each chunk with document title, section path ("Admin Guide > Backups > Retention"), product and date, so a chunk saying "set it to 30 days" is retrievable for "backup retention". Contextual retrieval (popularised by Anthropic) goes further: an LLM writes a one-sentence summary of how the chunk fits into the document, prepended before embedding and BM25 indexing. Parent-child or small-to-big retrieval matches on small chunks but returns their larger parent section to the model.

There is no universal best. Build a test set of real questions with known source passages and compare strategies on recall at k and answer quality.

How it works

  1. Parse documents into a structural tree.
  2. Split by sections; sub-split long sections to the token budget with overlap.
  3. Keep tables, code and lists intact; repeat headers.
  4. Prepend title, section path and optional generated context.
  5. Embed, index, and evaluate recall on a test set.

Example

from langchain_text_splitters import MarkdownHeaderTextSplitter, RecursiveCharacterTextSplitter

by_header = MarkdownHeaderTextSplitter([("#", "h1"), ("##", "h2"), ("###", "h3")])
sections = by_header.split_text(markdown_doc)
splitter = RecursiveCharacterTextSplitter.from_tiktoken_encoder(chunk_size=500, chunk_overlap=75)
chunks = []
for s in splitter.split_documents(sections):
    path = " > ".join(v for k, v in s.metadata.items() if k.startswith("h"))
    s.page_content = f"{doc_title} | {path}\n{s.page_content}"
    chunks.append(s)

Common mistakes

  • Fixed character splits that cut tables and code in half.
  • Chunks with no title or section context.
  • Choosing chunk size by intuition instead of measurement.
  • Huge chunks that exceed the embedding model's input limit (silently truncated).

How to answer in the interview

"Chunking is a trade-off: small chunks match queries precisely but may lack context, large chunks carry context but dilute the embedding and waste tokens. I start around a few hundred tokens with some overlap, but prefer structure-aware splitting by headings, sections and paragraphs, keeping tables, lists and code blocks intact. Semantic chunking by topic shifts is an option. Each chunk gets metadata and context such as document title, section path and date, sometimes a generated summary of its place in the document, which is contextual retrieval. Then I compare strategies with retrieval metrics on real questions."

Likely follow-up questions

  • 200-page manual with tables? Layout-aware parsing, section-based chunks, tables as row-level chunks with headers, parent-child retrieval.
  • What is small-to-big? Retrieve small precise chunks, return the parent section.
  • Overlap trade-off? More overlap improves boundary recall but adds duplicates and cost.
