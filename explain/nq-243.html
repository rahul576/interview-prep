How does Cassandra support high availability?

Databases & SQL · concept · levels mid, senior

In one line

Cassandra achieves high availability through masterless replication across nodes, racks and data centres, tunable consistency levels such as QUORUM and LOCAL_QUORUM that tolerate replica failures, and repair mechanisms (hinted handoff, read repair, anti-entropy repair) that bring missed writes back in sync.

Detailed explanation

No single point of failure: every node is equal and any node can coordinate. Each partition has a replication factor, typically RF=3 per data centre, with NetworkTopologyStrategy placing replicas on different racks or availability zones. Multi-DC clusters replicate asynchronously between regions, so a whole region can fail while others keep serving.

Tunable consistency: per request the client chooses how many replicas must acknowledge:

  • ONE / LOCAL_ONE: fastest, tolerates two of three replicas down.
  • QUORUM: a majority across all DCs; LOCAL_QUORUM: majority in the local DC (2 of 3), tolerating one replica down per DC without cross-region latency.
  • ALL: every replica; strongest but any failure causes errors.
  • EACH_QUORUM for writes needing a quorum in every DC.

With RF=3, LOCAL_QUORUM for both reads and writes gives R + W > RF (2 + 2 > 3), so reads see the latest acknowledged write while one replica is down.

Recovering missed writes:

  • Hinted handoff: if a replica is down, the coordinator stores a hint and replays it when the replica returns (within max_hint_window, default 3 hours).
  • Read repair: during reads with consistency above ONE, if replicas disagree, the newest value (by timestamp) is returned and written back to the stale replicas.
  • Anti-entropy repair: nodetool repair (incremental or full, often run via Cassandra Reaper) compares Merkle trees and streams differences; it must run regularly, within gc_grace_seconds (default 10 days), so deleted data does not resurrect.

The client driver adds resilience with token-aware, DC-aware load balancing, speculative retries and retry policies.

How it works

  1. Client sends a write at LOCAL_QUORUM to a coordinator.
  2. Coordinator sends it to all three local replicas.
  3. Two acknowledge, so the write succeeds; the third is down.
  4. The coordinator stores a hint for the down replica.
  5. The replica returns and the hint is replayed.
  6. Scheduled repair fixes anything hints missed.

Example

// DataStax Java driver 4.x
CqlSession session = CqlSession.builder()
    .withLocalDatacenter("eu-west").build();

SimpleStatement write = SimpleStatement
    .newInstance("INSERT INTO shop.cart (user_id, sku, qty) VALUES (?, ?, ?)", 42L, "LAMP-01", 2)
    .setConsistencyLevel(DefaultConsistencyLevel.LOCAL_QUORUM);
session.execute(write);
nodetool repair -pr shop     # primary-range repair, run on each node on a schedule

Common mistakes

  • Using QUORUM instead of LOCAL_QUORUM in multi-DC clusters, adding cross-region latency.
  • Never running repair, leading to inconsistency and zombie data after deletes.
  • RF=1 in production, which gives no availability.
  • Relying only on hinted handoff for long outages beyond the hint window.

How to answer in the interview

"High availability comes from masterless replication. Each partition lives on several replicas, usually three per data centre on different racks, possibly in multiple data centres, and any node can coordinate, so there's no single point of failure. Clients choose a consistency level per request: with LOCAL_QUORUM two of three local replicas must respond, so one node can be down with no errors, and ONE tolerates even more. Missed writes are recovered through hinted handoff, where the coordinator stores hints for the down replica, through read repair, and through regular anti-entropy repair with nodetool repair, run within gc_grace_seconds."

Likely follow-up questions

  • Why do QUORUM reads plus QUORUM writes give strong consistency? Read and write sets overlap (R + W > RF), so at least one replica read has the latest write.
  • What is gc_grace_seconds? How long tombstones are kept; repair must run within it to avoid resurrected data.
  • What happens if a whole DC fails? Clients fail over to another DC using its LOCAL_QUORUM.
