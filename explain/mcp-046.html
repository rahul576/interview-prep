Design an MCP server that lets platform engineers and developers self-serve common infrastructure tasks.

MCP Servers · design · levels senior, lead

In one line

Build the server on internal developer platform APIs, not raw cloud access: read tools for catalog, status and cost, write tools that open pull requests against GitOps repos, user identity and RBAC passed through, policy checks and approvals kept in the pipeline, and a full audit trail.

Detailed explanation

The goal is self-service without bypassing governance. If you hand an agent cloud admin credentials, you get a fast path around every guardrail your platform team built. Instead, the MCP server should sit on top of the same golden paths humans use: the service catalog, approved templates and Terraform modules, and the GitOps workflow.

Read tools answer most questions: who owns a service, what is deployed where, the status of environments, recent deployments and incidents, and cost per service. These are low risk and can usually be auto-approved.

Write tools express intent rather than performing changes. "Create a new service", "add a Postgres database" or "scale staging to three replicas" produce a pull request against the infrastructure or GitOps repository using approved templates. The pipeline then runs the normal checks: plan, policy as code (OPA, Sentinel), security scans, and human review. The agent cannot do anything a developer could not have done by opening the same PR.

The server authenticates users with OAuth through the company identity provider and acts on behalf of the user, so team ownership and RBAC limit what each person can request. Every action is written to an audit trail with the user, the tool, the arguments and the PR link.

How it works

  1. Developer asks the assistant: "Give payments-api a Redis cache in staging."
  2. The host calls get_service to confirm ownership, then request_resource with type redis, environment staging.
  3. The server checks the user's team owns the service, renders the approved module and opens a PR.
  4. CI runs terraform plan, policy checks and cost estimate; results are posted to the PR.
  5. A human reviewer approves; GitOps applies. The server can report PR status back to the agent.

Example

tools:
  - name: list_services          # read, auto-approve
  - name: get_environment_status # read
  - name: get_service_costs      # read
  - name: request_resource       # write -> opens PR
    input:
      service: payments-api
      resource_type: { enum: [postgres, redis, queue, bucket] }
      environment: { enum: [dev, staging, prod] }
      size: { enum: [small, medium, large] }

The returned result includes the PR URL, the template version used and the checks that will run.

Common mistakes

  • Giving the server cloud credentials that can change infrastructure directly.
  • Free-text parameters like "terraform_code", which let the model bypass templates.
  • A shared service account, so everybody can request anything.
  • Measuring success by number of tool calls rather than time saved and failed-change rate.

How to answer in the interview

"I'd build it on our internal developer platform APIs, not on raw cloud credentials, so the agent follows the same golden paths as people. Read tools cover the service catalog, ownership, environment status, deployment history and cost. Write tools never apply changes directly: creating a service or adding a database generates a pull request from approved templates, so plans, policy checks and human approvals all still happen in the pipeline. Users authenticate with OAuth and the server acts on their behalf, so RBAC and team ownership apply, and every action is audited. Developers get a conversational interface, and governance stays intact."

Likely follow-up questions

  • How do you measure value? Lead time for common requests, ticket volume to the platform team, PR acceptance rate.
  • What about urgent production scaling? A narrow, pre-approved tool with limits, plus approval, still audited.
  • Why enums instead of free text? They constrain the model to supported options and simplify policy checks.
