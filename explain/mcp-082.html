An agent creates duplicate support tickets whenever the network is unreliable. How do you fix it?

MCP Servers · scenario · levels mid, senior

In one line

On unreliable networks a create_ticket call can succeed on the server while the response is lost, so the client or agent retries and creates a duplicate because the tool is not idempotent; fix it with an idempotency key that the server stores and checks, returning the existing ticket on repeats.

Detailed explanation

This is the classic at-least-once delivery problem, made more likely by agents. The sequence: the agent calls create_ticket; the server creates ticket #501; the response is lost to a timeout or connection reset. The client sees a failure. Either the MCP client library retries automatically, or the model sees an error and decides to call the tool again. In the stateless protocol revision, a re-issued request gets a new JSON-RPC request ID, so the server has no protocol-level way to recognise it as a repeat. Ticket #502 is created, then perhaps #503.

The tool is not idempotent: calling it twice with the same intent has two effects. The fix belongs on the server, because only the server knows whether the effect already happened.

Idempotency key. create_ticket accepts an idempotency_key. It should be stable across retries of the same logical operation: generated once by the client per operation, or derived deterministically from stable inputs such as the conversation or task ID plus a hash of the normalised title and requester. The server stores the key with the created ticket (with a TTL, say 24 hours) in a durable store. When a call arrives with a known key, the server returns the existing ticket instead of creating a new one, ideally with a flag like "deduplicated": true.

The key must not be freshly invented by the model on each attempt: a new key per retry defeats the purpose.

Also: update the tool description to say the tool is safe to retry with the same key, make timeouts sensible, and clean up existing duplicates (merge or close them, notify affected users).

How it works

  1. Client or server derives key = hash(conversation_id + requester + normalised_title).
  2. Server does an atomic "insert if absent" of the key in Redis or a unique-constrained DB column.
  3. If inserted: create the ticket, store the ticket ID against the key.
  4. If the key exists: return the stored ticket.
  5. Handle the in-progress case: if the first call is still running, wait briefly or return "in progress".

Example

@mcp.tool()
async def create_ticket(title: str, description: str, requester: str,
                        idempotency_key: str | None = None, ctx: Context = None):
    """Create a support ticket. Safe to retry: repeated calls with the same
    idempotency_key return the original ticket instead of creating a new one."""
    key = idempotency_key or sha256(f"{ctx.conversation_id}|{requester}|{normalise(title)}")
    existing = await store.get(f"idem:{key}")
    if existing:
        return {"ticket_id": existing, "deduplicated": True}
    if not await store.set(f"idem:{key}", "pending", nx=True, ex=86400):
        return tool_error("Ticket creation already in progress; check again shortly.")
    ticket = await servicedesk.create(title=title, description=description, requester=requester)
    await store.set(f"idem:{key}", ticket.id, ex=86400)
    return {"ticket_id": ticket.id, "deduplicated": False}

Common mistakes

  • Relying on the JSON-RPC request ID for deduplication.
  • Letting the model generate a random key on each attempt.
  • Check-then-insert without atomicity, so two concurrent retries both create tickets.
  • Fixing the client only; other clients still create duplicates.

How to answer in the interview

"When the network is flaky, create_ticket can succeed on the server while the response is lost. The client or agent sees a timeout and retries, and in the stateless revision the retried request has a new ID, so the server can't tell it's a repeat. Each retry creates a new ticket because the tool isn't idempotent. I'd fix it on the server: create_ticket accepts an idempotency key, either generated by the client once per logical operation or derived from stable inputs like the conversation ID and a hash of the summary, and the server stores it atomically with the ticket. A call with an existing key returns the existing ticket. I'd also clean up the duplicates and make the description say it's safe to retry with the same key."

Likely follow-up questions

  • Why not a fresh key from the model? Each retry would look like a new operation.
  • How long keep keys? Longer than any realistic retry window, often 24 hours.
  • What if two different tickets look alike? Include requester and conversation so genuine distinct requests get different keys.
