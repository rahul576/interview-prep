What happens when an exception is thrown inside a finally block?

Exceptions · concept · levels mid, senior

In one line

An exception thrown from finally replaces (masks) the exception that was propagating from try or catch, so the original cause is lost; a return in finally swallows exceptions the same way; keep finally simple or use try-with-resources, which records suppressed exceptions instead.

Detailed explanation

When the try block throws, the JVM saves that exception, runs finally, and then rethrows the saved one. But if finally itself completes abruptly, by throwing or returning, that new outcome replaces the pending one. The JLS defines it this way: the reason for abrupt completion of finally wins.

Typical scenario: a database query fails with a meaningful SQLException: deadlock detected. In finally, connection.close() throws SQLException: connection already closed, because the failed query broke the connection. The caller and the logs now see only "connection already closed". The real root cause has vanished, and the incident takes hours to diagnose.

return in finally is even worse: it silently discards the exception altogether, and the method appears to succeed. Most linters and IDEs flag "finally block does not complete normally".

How to avoid it:

  • Use try-with-resources for anything AutoCloseable. If the body throws and close() also throws, the close exception is attached to the primary one via addSuppressed, visible with getSuppressed() and in stack traces under Suppressed:.
  • Keep finally blocks trivial: unlock, reset a flag, remove MDC entries.
  • If finally must do something risky, wrap it in its own try/catch, log the cleanup failure, and optionally attach it with original.addSuppressed(cleanupEx).
  • Never return or throw from finally.

How it works

  1. Try throws exception A; the JVM stores it and jumps to finally.
  2. Finally throws exception B.
  3. A is discarded; B propagates.
  4. With try-with-resources, B from close is added to A as suppressed; A propagates.

Example

// Masking
try {
    throw new IllegalStateException("real problem");
} finally {
    throw new RuntimeException("cleanup failed");   // caller sees only this
}

// Safer manual cleanup
Connection c = ds.getConnection();
try {
    runQuery(c);
} finally {
    try { c.close(); }
    catch (SQLException closeEx) { log.warn("close failed", closeEx); }
}

// Best
try (Connection c2 = ds.getConnection()) {
    runQuery(c2);
} catch (SQLException e) {
    log.error("query failed", e);                    // close failures are in e.getSuppressed()
}

Common mistakes

  • Calling close() in finally without protecting it.
  • Returning from finally to "make sure the method returns a value".
  • Ignoring suppressed exceptions when logging only getMessage().
  • Throwing new exceptions from finally for validation.

How to answer in the interview

"The exception from finally replaces the one that was propagating from try or catch, so the original is lost and the caller only sees the new one, often just a close error. That makes debugging very hard because the root cause disappears. A return in finally swallows exceptions the same way. To avoid it I keep finally blocks simple, and wrap any risky cleanup in its own try-catch that logs the failure. Better still, I use try-with-resources: if close fails after the body has thrown, the close exception is attached to the original as a suppressed exception instead of replacing it."

Likely follow-up questions

  • How do you read suppressed exceptions from a caught exception? e.getSuppressed() returns the array; stack traces print them too.
  • What if try returns and finally throws? The exception propagates and the return value is lost.
  • Can you add suppressed exceptions manually? Yes, addSuppressed.
