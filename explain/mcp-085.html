An agent keeps acting on stale data from MCP resources. Why might this happen, and how do you fix it?

MCP Servers · scenario · levels mid, senior

In one line

Resources are typically read once into context, so in long sessions the model reasons from a stale snapshot; clients may cache beyond freshness (wrong or missing TTL hints) and many hosts ignore subscriptions; fix it by serving fast-changing data through tools, setting realistic ttlMs hints, supporting subscriptions, and timestamping data so the model knows its age.

Detailed explanation

MCP resources are designed as context: files, documents, records that a host or user attaches to the conversation. Once a resource's contents are in the context window, they stay there as text. The model has no idea that an hour later the ticket was reassigned or the stock level dropped to zero. It keeps reasoning, and acting, from the snapshot.

There are several contributing causes:

  • Snapshot in context. The resource was read at the start of a long session and never re-read.
  • Client caching. Hosts may cache resource reads or lists. If the server sends generous caching hints such as a large ttlMs, or none, the client may reuse old data longer than is safe.
  • Subscriptions not handled. The protocol lets clients subscribe to a resource and receive notifications/resources/updated, but many hosts do not implement subscriptions, or do not re-inject updated content into the conversation.

Fixes. For data that changes often, such as ticket status, inventory, prices or deployment state, expose it through a tool that fetches the current value whenever the model needs it; tools are model-initiated, so the model can re-check before acting. Keep resources for stable content: documentation, schemas, policies, closed records. Set realistic ttlMs hints per resource type and support subscriptions for hosts that use them. Include timestamps in returned data, "status: open (as of 2026-11-21 10:42 UTC)", and tool descriptions that encourage re-checking important values before write actions. Write tools can also use optimistic concurrency: require a version or ETag, so acting on stale data fails safely.

How it works

  1. Session starts; host attaches tickets://4711 as a resource.
  2. Ticket changes in the backend; the model's context still shows the old status.
  3. Model acts on old status, for example closing an already reassigned ticket.
  4. After the fix: status comes from get_ticket with a timestamp; update_ticket requires the current version.
  5. Stale updates are rejected with a clear error telling the model to re-read.

Example

{
  "content": [{
    "type": "text",
    "text": "{\"ticket\": 4711, \"status\": \"open\", \"assignee\": \"team-network\", \"version\": 17, \"as_of\": \"2026-11-21T10:42:05Z\"}"
  }]
}
update_ticket(id=4711, status="resolved", expected_version=16)
-> error: "Ticket changed since you read it (now version 17, assigned to team-db). Re-read with get_ticket before updating."

Common mistakes

  • Exposing live operational data only as resources.
  • Long TTL hints on volatile data.
  • No version check on writes.
  • Returning data without any timestamp.

How to answer in the interview

"Resources are usually read once and put into context, so in a long session the model keeps reasoning from that snapshot while the real data changes. Clients may also cache resource reads longer than they should if the server's TTL hints are generous or missing, and many hosts don't implement subscriptions, so update notifications are never acted on. For data that changes often, like ticket status or inventory, I expose it through a tool that fetches the current value whenever the model needs it. I set realistic ttlMs hints, support subscriptions for hosts that use them, and include timestamps like 'as of 10:42 UTC' so the model knows the data's age. Writes can also require a version so stale actions fail safely."

Likely follow-up questions

  • Fine as long-lived resources? Docs, schemas, policies, historical or closed records.
  • Why version checks? Optimistic concurrency turns stale-data actions into safe errors.
  • Do subscriptions solve it? Only if the host re-injects updates into the conversation.
