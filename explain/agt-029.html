An agent worked perfectly in the demo but fails often in production. What usually explains the gap?

AI Agents & AIOps · scenario · levels mid, senior

In one line

Demos use happy-path inputs, mocked or clean tools, generous permissions and short tasks; production brings messy, diverse requests, failing, slow or rate-limited APIs, different permissions, longer tasks and compounding errors; close the gap with evaluation sets from real traffic, staging tests against real tools, error handling, fewer steps and careful monitored rollout.

Detailed explanation

A demo is a sample of one, chosen to succeed. The builder knows how to phrase the request, the input is complete, and the agent has been tuned on it.

Input diversity: real users write vague, multi-part, misspelled or contradictory requests, omit key information, mix languages, paste screenshots, and ask things outside the intended scope. The long tail of edge cases dominates failures.

Real tools: demo tools are often mocks or test data. Real APIs time out, rate limit, paginate, return unexpected formats or partial data, and change without notice. Data is dirty: duplicates, nulls, legacy fields.

Permissions and environment: the demo ran with the builder's broad access; production runs with each user's or the service identity's permissions, so the agent hits access errors it was never tested against. Network policies, SSO and data residency add more differences.

Task length: real tasks are longer, so they exceed step limits or context windows, and compaction kicks in where it never did in the demo.

Compounding errors: reliability multiplies across steps. At 95 percent per step, a 20-step task succeeds only about 36 percent of the time (0.95^20). Small per-step weaknesses that were invisible in five-step demos dominate.

Closing the gap: build evaluation sets from real or realistic traffic, including failures and adversarial cases; test against real tool behaviour in staging, with fault injection for timeouts and errors; add robust error handling and verification; reduce the number of steps with higher-level tools; and launch with a limited rollout, close monitoring, quick feedback channels and a process that turns failures into new eval cases.

How it works

  1. Sample real requests (logs, tickets) to build an eval set; label outcomes.
  2. Run evals against staging with real APIs, permissions and data.
  3. Inject faults: timeouts, 429s, malformed responses.
  4. Measure per-step reliability; reduce steps where it is weak.
  5. Pilot with a small group; monitor success, escalation, cost.
  6. Turn production failures into eval cases; iterate before widening.

Example

Reliability compounds:
per-step success   5 steps   10 steps   20 steps
      99%           95%        90%        82%
      95%           77%        60%        36%
      90%           59%        35%        12%

Demo:       5 curated prompts, mocked CRM, admin token        -> 5/5 success
Production: first week, 1,200 real requests, user tokens      -> 61% success
Top causes: missing order number (22%), CRM 429s (14%), permission denied (9%)

Common mistakes

  • Treating the demo as validation.
  • Evaluating only on builder-written examples.
  • Mocked tools that never fail.
  • Testing with admin credentials.
  • Big-bang launch without monitoring or feedback loops.

How to answer in the interview

"Demos use a few carefully chosen, happy-path inputs, while production brings messy, ambiguous and diverse requests with missing information and edge cases. Demo tools are often mocks, but real APIs fail, are slow, rate limited or return unexpected formats, and real permissions differ, so the agent hits access errors it never saw. Real tasks are longer and exceed context or step limits. And reliability compounds: at 95 percent per step, a twenty-step task succeeds only about a third of the time. To close the gap I build evals from real traffic including failures, test against real tools in staging with fault injection, add error handling and verification, reduce steps with better tools, and launch to a limited group with close monitoring."

Likely follow-up questions

  • Setting expectations before launch? Share eval results by category, known limits, the pilot plan and success criteria for widening.
  • How to get realistic eval data before launch? Historical tickets, logs, shadow mode on live traffic, and synthetic variations reviewed by experts.
  • What is shadow mode? The agent processes real requests without acting, and its outputs are compared with what humans did.
