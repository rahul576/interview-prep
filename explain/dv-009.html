What are environment variables in Linux, and how do you use them in scripts?

Scripting · concept · levels entry

In one line

Environment variables are key-value settings inherited by child processes; export makes a shell variable visible to programs you start, common ones are PATH and HOME, they persist via .bashrc, .profile, /etc/environment or systemd and container definitions, and scripts should read them quoted with sensible defaults, keeping secrets in a secret store.

Detailed explanation

Every process has an environment: a list of NAME=value strings copied to its children when they start. A child cannot change its parent's environment, which is why a script that exports a variable does not affect the shell that ran it unless you source it.

In Bash, NAME=value creates a shell variable visible only to the current shell. export NAME (or export NAME=value) marks it for export, so programs you launch inherit it. NAME=value command sets it for a single command only. env or printenv lists the environment, and unset NAME removes a variable.

Common variables: PATH, the colon-separated directories searched for commands (order matters); HOME, the user's home; USER, SHELL, LANG for locale, TZ, and tool-specific ones like KUBECONFIG, AWS_PROFILE or HTTPS_PROXY.

Persistence: for one user, put exports in ~/.bashrc (interactive shells) or ~/.profile / ~/.bash_profile (login shells). /etc/environment sets simple system-wide values (no shell syntax), and /etc/profile.d/*.sh holds system-wide scripts. Services do not read your shell files: systemd units use Environment= or EnvironmentFile=, containers use ENV in the Dockerfile or env/envFrom in Kubernetes, and cron has its own minimal environment.

In scripts, read variables as "$NAME", always quoted, and use parameter expansion: ${PORT:-8080} for a default, ${DB_HOST:?must be set} to fail fast. Environment variables are the twelve-factor way to pass configuration, but secrets in them can leak through logs, /proc/<pid>/environ, crash dumps and child processes, so inject them from a secret manager at runtime and never print them.

How it works

  1. The shell keeps variables; exported ones form the environment.
  2. On fork/exec, the child receives a copy.
  3. Programs read values via getenv or os.environ.
  4. Login and shell startup files set persistent values.
  5. Services get their environment from systemd or the container runtime.

Example

export APP_ENV=staging
PORT=9090 ./server            # only for this command
echo "$PATH"
export PATH="$HOME/.local/bin:$PATH"
#!/usr/bin/env bash
set -euo pipefail
PORT="${PORT:-8080}"
DB_HOST="${DB_HOST:?DB_HOST must be set}"
echo "Starting on port $PORT, database $DB_HOST"

Common mistakes

  • Forgetting export, so the child program never sees the value.
  • Expecting .bashrc variables to reach systemd services or cron jobs.
  • Unquoted $VAR breaking on spaces.
  • Printing all variables (env) in CI logs and exposing secrets.

How to answer in the interview

"Environment variables are key-value settings a process passes to its children. In a shell, NAME=value creates a variable for the current shell, and export makes it available to programs I start. PATH lists directories searched for commands and HOME is the user's directory. To persist them I use .bashrc or .profile for a user or /etc/environment system-wide, while services get them from systemd unit files or container definitions. Scripts read them quoted, with defaults like PORT colon-dash 8080. They are the standard way to pass configuration, but secrets should come from a secret store and never be printed."

Likely follow-up questions

  • Why is printing all environment variables in CI logs risky? They often contain tokens and passwords; masking is not perfect and logs are widely readable.
  • What does source do? Runs a file in the current shell, so its exports stay.
  • Why might a command work in your shell but not in cron? Cron's PATH and environment are minimal.
