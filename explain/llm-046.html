After a deployment, retrieval quality collapsed: almost every search returns unrelated chunks. What do you suspect first?

LLMOps & RAG · scenario · levels mid, senior

In one line

Suspect an embedding mismatch first: queries embedded with a different model or version than the index, or changed dimensions, normalisation or distance metric, or the app pointing at the wrong index or namespace; roll back, then add embedding version checks and retrieval tests in CI.

Detailed explanation

A sudden, near-total collapse right after a deployment is rarely a data problem; data problems degrade gradually or affect some documents. It is a configuration problem, and the most common one is that query vectors and document vectors no longer live in the same space.

Each embedding model defines its own vector space. Vectors from model A and model B are not comparable even if they have the same dimension, so cosine similarities become essentially random and top results look unrelated. This happens when a client library update changes the default model, a deployment name in config points to a newer embedding deployment, an environment variable differs between staging and production, or someone "upgraded" the embedding model for new documents only.

Related causes:

  • Dimensions: models supporting configurable output dimensions (truncated, Matryoshka-style embeddings) set differently for queries than for the index. Many vector stores error on mismatch, but some pipelines pad or truncate silently.
  • Normalisation and metric: switching from cosine to dot product with unnormalised vectors, or changing index metric, reshuffles rankings.
  • Query/document prefixes: some models expect task-specific prefixes or input types (query vs document); dropping them degrades quality noticeably.
  • Wrong target: an empty or test index, a wrong namespace or tenant, or a filter that excludes everything except junk.

How it works

  1. Roll back the deployment to restore service.
  2. Diff configuration: embedding model, version, dimensions, endpoint, index name.
  3. Embed a known document's text and check similarity to its stored vector (should be about 1.0).
  4. Fix config or re-embed the corpus with the new model into a new index.
  5. Add guards: index metadata with model and dimension, startup check, CI retrieval test.

Example

meta = index.get_metadata()   # stored at build time
assert meta["embedding_model"] == settings.EMBED_MODEL, "embedding model mismatch"
assert meta["dimensions"] == settings.EMBED_DIM

# smoke test: a stored chunk must retrieve itself
probe = index.get("faq#0001")
v = embed(probe.text)
assert cosine(v, probe.vector) > 0.99
assert search(v, top_k=1)[0].id == "faq#0001"

Common mistakes

  • Changing embedding models without re-indexing everything.
  • Relying on library defaults for the embedding model.
  • No golden retrieval tests in the deployment pipeline.
  • Debugging chunking or prompts first and losing hours.

How to answer in the interview

"A sudden collapse right after a deploy points to configuration, and the classic cause is an embedding mismatch: queries are now embedded with a different model or version than the vectors in the index, for example because a library default or deployment name changed. Vectors from different models aren't comparable, so similarity becomes meaningless. Related causes are changed dimensions, normalisation or distance metric, or pointing at the wrong index. I'd roll back first, then store the embedding model and dimension as index metadata, check them at startup, and run a small golden retrieval test in CI and after every deployment."

Likely follow-up questions

  • Which test would have caught it? A golden-query recall test in CI and a post-deploy smoke test.
  • Upgrading embedding models safely? Build a new index in parallel, evaluate, then switch an alias.
  • Can you mix old and new vectors? No; re-embed everything.
