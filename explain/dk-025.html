How do you pull images and choose a specific version?

Docker · concept · levels entry

In one line

docker pull name:tag downloads an image; omitting the tag means latest, which is only a moving label, so pin a specific version tag or, for full immutability, a digest (name@sha256:...), and prefer official or verified images.

Detailed explanation

An image reference has the form registry/repository:tag or registry/repository@digest. If you leave out the registry, Docker uses Docker Hub; if you leave out the tag, it uses latest. Despite its name, latest is just a tag the publisher chooses to move. It may not be the newest stable release, and it will change under you, so a build that worked yesterday can break today, and two servers can run different code under the same name.

For repeatable environments you choose a specific tag. Most official images publish several granularities: postgres:16 moves with every minor release of 16, postgres:16.4 is more specific, and variants like -bookworm or -alpine fix the base OS. Even specific tags can be re-pushed, for example when the publisher rebuilds for a security fix. For complete immutability you pin the content digest, the sha256 of the manifest, which always identifies exactly the same bits. Tools like Renovate keep digests up to date.

Trust matters as much as version. Prefer Docker Official Images and Verified Publisher images, check how recently they were updated, and scan them. Images are stored in the local image cache after the first pull. Because images are made of content-addressed layers, a later pull only downloads the layers you do not already have, which is why upgrading from 16.3 to 16.4 is quick. On multi-architecture images, Docker automatically selects the variant for your platform, or you choose with --platform.

How it works

  1. The client resolves the reference to a registry, repository and tag.
  2. It fetches the manifest (or manifest list for multi-arch) for the tag.
  3. It selects the platform-specific manifest.
  4. It compares layer digests with the local cache.
  5. It downloads only missing layers, verifies their hashes and tags the image locally.

Example

docker pull postgres:16.4
docker pull --platform linux/arm64 nginx:1.27
docker images --digests postgres
docker pull postgres@sha256:<digest-from-above>
FROM eclipse-temurin:21.0.4_7-jre-jammy

Common mistakes

  • FROM node:latest in Dockerfiles, giving non-reproducible builds.
  • Pinning a digest and never updating it, so security patches never arrive.
  • Pulling random community images without checking the publisher.
  • Assuming latest locally is the same as latest in the registry; it is only what was pulled last.

How to answer in the interview

"docker pull downloads an image from a registry, for example docker pull postgres:16.4. If you omit the tag Docker uses latest, which is just a label the publisher moves, not a guarantee of the newest stable version, so builds can change unexpectedly. For repeatable environments I pin a specific version, and for full immutability the digest. I prefer official or verified publisher images and check how often they're updated. Images are cached locally, and only missing layers are downloaded, which is why pulling a new version of a familiar image is fast."

Likely follow-up questions

  • Risk of latest in FROM? Builds silently change and can break or introduce vulnerabilities.
  • How do you get the digest? docker images --digests or docker buildx imagetools inspect.
  • How do you keep pinned versions current? Renovate or Dependabot pull requests.
