How would you design a thread pool for processing 10,000 concurrent tasks?

Concurrency · design · levels senior, lead

In one line

Do not create 10,000 platform threads: classify the work (CPU- vs I/O-bound), size the pool from cores or Little's law, use a bounded queue with a rejection policy for backpressure, consider virtual threads plus a semaphore for blocking I/O, and add timeouts, metrics and graceful shutdown.

Detailed explanation

"10,000 concurrent tasks" is a load requirement, not a thread count. The right design depends on what the tasks do.

CPU-bound tasks (parsing, image resizing, calculations) cannot run faster than the number of cores. A pool of about availableProcessors() threads (perhaps +1) is optimal; more threads only add context switching. The 10,000 tasks wait in a queue and throughput is set by the CPU.

I/O-bound tasks spend most time waiting. Size with Little's law: concurrency = throughput x latency. If you need 2,000 tasks/s and each spends 100 ms, you need about 200 in flight. The rule of thumb threads = cores x (1 + wait/compute) gives the same idea. But the real cap is downstream: a database pool of 50 connections means more than 50 concurrent DB tasks just queue at Hikari. Size against the scarcest resource.

Use a ThreadPoolExecutor with a bounded queue so overload produces backpressure instead of memory exhaustion, and an explicit rejection policy: CallerRunsPolicy slows producers naturally; AbortPolicy lets you return 429/503 or retry later. If the tasks come from a message broker, consumer prefetch limits are the backpressure.

On Java 21+, blocking I/O tasks fit virtual threads: one per task, 10,000 is cheap. Concurrency control then moves from pool size to a Semaphore guarding each downstream. Keep a separate small platform pool for CPU-heavy steps.

Operational hygiene: timeouts on every external call, named threads, metrics (active, queued, rejected, task duration), error handling for every task, separate pools per workload (bulkheads), and a graceful shutdown.

How it works

  1. Classify tasks: CPU-bound, I/O-bound or mixed (split stages).
  2. Compute target concurrency: cores, or throughput x latency, capped by downstream limits.
  3. Create bounded executors per workload with named threads.
  4. Choose rejection/backpressure behaviour.
  5. For blocking I/O on Java 21+, use virtual threads and semaphores.
  6. Add timeouts, metrics, alerts and shutdown handling; load test and tune.

Example

int cores = Runtime.getRuntime().availableProcessors();

ThreadPoolExecutor cpuPool = new ThreadPoolExecutor(
        cores, cores, 0, TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(2_000),
        Thread.ofPlatform().name("cpu-", 0).factory(),
        new ThreadPoolExecutor.CallerRunsPolicy());

Semaphore dbPermits = new Semaphore(40);          // below Hikari max of 50
try (var io = Executors.newVirtualThreadPerTaskExecutor()) {
    for (Task t : tasks) {                          // 10,000 tasks
        io.submit(() -> {
            dbPermits.acquire();
            try {
                Data d = repo.load(t.id());          // blocking JDBC, with query timeout
                return cpuPool.submit(() -> transform(d)).get(5, TimeUnit.SECONDS);
            } finally { dbPermits.release(); }
        });
    }
}   // close() waits for all tasks

Common mistakes

  • One giant pool of thousands of platform threads.
  • Unbounded queues that hide overload until OutOfMemoryError.
  • Sizing threads above the connection pool, so threads just wait at the pool.
  • Pooling virtual threads instead of limiting the resource with semaphores.
  • No timeouts, so a slow dependency holds every thread.

How to answer in the interview

"I wouldn't create 10,000 platform threads. First I classify the work. For CPU-bound tasks the pool has about as many threads as cores and the rest wait in a queue. For I/O-bound tasks I size from Little's law, throughput times latency, but cap it by what downstream systems and the connection pool can take. I use a ThreadPoolExecutor with a bounded queue for backpressure and a rejection policy like CallerRunsPolicy. On Java 21 I'd run blocking I/O on virtual threads, one per task, and limit concurrency to each downstream with a semaphore. And I add timeouts, named threads, metrics on active and queued tasks, and graceful shutdown."

Likely follow-up questions

  • How would you limit concurrency to a downstream service when using virtual threads? A Semaphore per downstream (or a bounded connection pool or rate limiter), acquired around the call with a timeout.
  • What if tasks must survive a restart? Put them on a durable queue (Kafka, SQS) instead of an in-memory executor queue.
  • How do you pick the queue size? From the acceptable waiting time: queue length divided by throughput should stay below your latency budget.
