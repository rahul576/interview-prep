What is a trie, and where would you use it?

DSA: Trees & Graphs · concept · levels mid, senior

In one line

A trie (prefix tree) stores strings character by character along paths from the root. Each node has children (a map or a 26-array) and an end-of-word flag. Insert and search take O(L), where L is the word length, independent of how many words are stored, which makes tries ideal for autocomplete, prefix search, spell checking and longest-prefix routing. The cost is memory.

Detailed explanation

With a hash set you can check whether a whole word exists in O(L), but you cannot efficiently ask "which words start with inter?" without scanning everything. A trie shares common prefixes. "interview", "internet" and "interval" all walk the same i-n-t-e-r path before branching. So:

  • insert(word): walk from the root, creating missing child nodes, and mark the last node isEnd = true.
  • search(word): walk. If any child is missing, return false. At the end, return isEnd, because "inter" might only be a prefix.
  • startsWith(prefix): walk. If the path exists, the subtree under that node contains exactly the words with this prefix. Collect them with DFS.

All operations cost O(L) regardless of dictionary size N. Children storage is a trade-off. A TrieNode[26] array is fastest but wastes memory on sparse nodes. A HashMap<Character, TrieNode> is compact and supports any alphabet.

Memory is the main downside: millions of nodes with object overhead. Mitigations include compressed tries (radix/Patricia trees), which merge single-child chains into edge labels, ternary search trees, DAWG/FST (Lucene uses finite state transducers for its term dictionary and suggesters), or a sorted array with binary search for static sets.

Real uses:

  • Autocomplete / typeahead. Store popularity at nodes. Precompute top-k suggestions per node so a lookup is O(L) plus O(k).
  • Spell checkers, word games (Boggle: prune DFS when no prefix exists).
  • IP routing longest-prefix match, using binary tries over address bits.
  • Prefix-based routing in HTTP routers.

How it works

  1. The root is an empty node.
  2. To insert, for each char create or follow the child, then mark the final node as a word end. Optionally store a count or score there.
  3. To search, follow the children, failing if one is missing, and check isEnd at the end.
  4. For a prefix query, follow to the prefix node, then DFS to collect the words beneath it, or return cached top-k.
  5. To delete, unmark isEnd and prune nodes left childless.

Example

class Trie {
    private static class Node { Node[] next = new Node[26]; boolean end; }
    private final Node root = new Node();

    void insert(String w) {
        Node n = root;
        for (char c : w.toCharArray()) {
            int i = c - 'a';
            if (n.next[i] == null) n.next[i] = new Node();
            n = n.next[i];
        }
        n.end = true;
    }
    boolean search(String w)     { Node n = walk(w); return n != null && n.end; }
    boolean startsWith(String p) { return walk(p) != null; }
    private Node walk(String s) {
        Node n = root;
        for (char c : s.toCharArray()) { n = n.next[c - 'a']; if (n == null) return null; }
        return n;
    }
}

Common mistakes

  • Forgetting the end-of-word flag, so search("inter") returns true just because the path exists.
  • Saying a trie is always more memory-efficient than a hash set (usually it is the opposite).
  • Collecting all words under a short prefix at query time for autocomplete, which is slow for popular prefixes.
  • Using a 26-array when the input has uppercase letters or Unicode.

How to answer in the interview

"A trie, or prefix tree, stores strings character by character. Each node has children, a map or an array of 26, plus an end-of-word marker. Inserting or searching a word takes O(L), the word length, regardless of how many words are stored, and finding all words with a prefix is just walking to that node and exploring its subtree. I'd use it for autocomplete, prefix search, spell checking or longest-prefix IP routing. The trade-off is memory, which compressed radix tries reduce. For autocomplete at scale I'd store the top-k suggestions at each node."

Likely follow-up questions

  • Top 5 suggestions by popularity? Cache a top-k list at every node, updated on insert, or keep a heap at query time.
  • Trie versus hash set? Hash set for exact lookups. Trie when you need prefix queries or ordered traversal.
  • Word search in a grid (Boggle)? Build a trie of the dictionary and prune the DFS when the current path isn't a prefix.
