How do you manage secrets in a GitOps workflow?

GitOps & Helm · concept · levels mid, senior

In one line

Never commit plain Kubernetes Secrets (they are only base64-encoded); either keep secrets out of Git with the External Secrets Operator syncing from Vault, AWS Secrets Manager or Azure Key Vault, or store them encrypted in Git with Sealed Secrets or SOPS + KMS, authenticate with workload identity, and let the secret store handle rotation and access control.

Detailed explanation

GitOps wants everything in Git, but a Kubernetes Secret manifest only base64-encodes values, which anyone can decode. Git history is permanent and widely cloned, so a leaked secret must be considered compromised forever. Two patterns solve this.

1. Reference, don't store: External Secrets Operator (ESO). Git contains an ExternalSecret resource that says "fetch prod/orders/db-password from this store and create a Kubernetes Secret named orders-db". A SecretStore/ClusterSecretStore describes how to reach the provider. ESO polls the provider (refreshInterval), so a rotated value in Vault or Secrets Manager flows into the cluster automatically. The vault keeps access policies, audit logs and rotation. The Secrets Store CSI Driver is a file-mount alternative.

2. Encrypt in Git: Sealed Secrets or SOPS. Sealed Secrets uses a controller with a private key in the cluster; developers encrypt with kubeseal using the public key, and only that controller can decrypt the resulting SealedSecret. Simple, but secrets are tied to the cluster key, which must be backed up, and rotation means re-sealing. SOPS encrypts values in YAML files with AWS KMS, Azure Key Vault, GCP KMS, age or PGP; Flux decrypts natively, Argo CD via plugins such as KSOPS or helm-secrets.

Authentication to the store should use workload identity (IRSA or EKS Pod Identity, Azure Workload Identity, GKE Workload Identity, or Vault's Kubernetes auth) rather than static keys stored as yet another secret.

How it works

  1. Secret value lives in the vault (or encrypted in Git).
  2. Git contains only an ExternalSecret reference (or encrypted SealedSecret/SOPS file).
  3. Argo CD/Flux applies it to the cluster.
  4. ESO (or the Sealed Secrets controller/SOPS) creates the real Kubernetes Secret.
  5. Pods consume it; rotation in the vault propagates on the next refresh.

Example

apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata: { name: orders-db, namespace: orders }
spec:
  refreshInterval: 1h
  secretStoreRef: { kind: ClusterSecretStore, name: aws-secrets-manager }
  target: { name: orders-db }
  data:
    - secretKey: password
      remoteRef: { key: prod/orders/db, property: password }
kubectl create secret generic api-key --from-literal=key=s3cr3t --dry-run=client -o yaml \
  | kubeseal --format yaml > sealed-api-key.yaml   # safe to commit

Common mistakes

  • Committing base64 Secrets and thinking they are encrypted.
  • Losing the Sealed Secrets controller key, making every sealed secret undecryptable.
  • Using long-lived cloud access keys for ESO instead of workload identity.
  • Forgetting that apps need restarting or reloading to pick up rotated values.

How to answer in the interview

"Plain Kubernetes Secrets are just base64, so they never go into Git. I prefer keeping secrets out of Git entirely: the External Secrets Operator reads them from Vault, AWS Secrets Manager or Azure Key Vault and creates Kubernetes Secrets in the cluster, and Git only contains a reference saying which secret to fetch. That keeps rotation, audit and access control in the vault. The alternative is encrypted secrets in Git, either Sealed Secrets, which only the in-cluster controller can decrypt, or SOPS with a cloud KMS key. Either way, the operator authenticates with workload identity instead of static keys, and RBAC and etcd encryption protect the resulting Secrets."

Likely follow-up questions

  • Sealed Secrets vs ESO? Sealed Secrets is self-contained but harder to rotate; ESO needs a vault but gives central rotation and audit.
  • How do pods pick up rotated secrets? Mounted volumes update automatically; env vars need a restart, for example via Reloader.
  • What if a secret was already committed? Rotate it immediately; rewriting history is not enough.
