How do pagination, list change notifications and caching hints work for MCP list operations?

MCP Servers · concept · levels mid, senior

In one line

MCP list operations use cursor-based pagination (nextCursor), servers with the listChanged capability send list_changed notifications so clients re-fetch, and newer revisions add caching hints: ttlMs for freshness and cacheScope for whether a cached result may be shared across users.

Detailed explanation

Pagination. tools/list, resources/list, resources/templates/list and prompts/list are paginated with opaque cursors. A response may include nextCursor; the client passes it back as cursor to get the next page, and the absence of nextCursor means the end. The server chooses the page size, and clients must treat cursors as opaque strings, never parsing or constructing them. This keeps servers with thousands of resources from returning everything in one response.

List change notifications. A server that declares listChanged in a capability (e.g. "tools": {"listChanged": true}) sends notifications/tools/list_changed, notifications/resources/list_changed or notifications/prompts/list_changed when the set changes. Reasons include a feature flag turning on, a plugin being installed, or the user gaining or losing a permission, since servers often return different lists for different users. The notification carries no payload; the client re-fetches the list. In the stateless revision these notifications arrive over a subscription stream.

Caching hints. Fetching tools/list on every model turn adds latency, while caching forever misses changes. Per the reference material for this question, newer revisions add hints modelled on HTTP caching to list and read results: ttlMs says how many milliseconds the result can be considered fresh, and cacheScope says whether the cached result may be shared across users or must be kept private to one user.

The cacheScope part is a security issue, not just performance. A gateway or multi-tenant host that caches a private per-user tool list or resource and serves it to another user can leak tool names, data or even capabilities belonging to another tenant. Shared caches must key private results by user identity, or not cache them at all.

How it works

  1. Client calls tools/list; follows nextCursor until exhausted.
  2. Client caches the list for ttlMs, respecting cacheScope (shared vs per user).
  3. Server state changes → sends list_changed notification.
  4. Client invalidates its cache and re-fetches.
  5. Host updates tool definitions in the next model request.

Example

{"jsonrpc":"2.0","id":4,"method":"tools/list","params":{"cursor":"eyJwYWdlIjoyfQ"}}

{"jsonrpc":"2.0","id":4,"result":{
  "tools":[{"name":"search_orders","description":"...","inputSchema":{"type":"object"}}],
  "nextCursor":"eyJwYWdlIjozfQ",
  "ttlMs":300000, "cacheScope":"private"}}

{"jsonrpc":"2.0","method":"notifications/tools/list_changed"}

(Placement of caching fields illustrative; consult the published schema.)

Common mistakes

  • Ignoring nextCursor and only reading the first page.
  • Parsing or generating cursors client-side.
  • Caching per-user lists in a shared cache keyed only by server URL.
  • Re-fetching lists on every turn, adding latency for nothing.
  • Declaring listChanged but never sending notifications.

How to answer in the interview

"List operations like tools/list use cursor-based pagination: the response may include a nextCursor that the client passes back to get the next page, and cursors are opaque. Servers that declare listChanged send list_changed notifications when their tools, resources or prompts change, say after a user gains a permission, and the client re-fetches. Newer revisions add caching hints modelled on HTTP: ttlMs for how long a result stays fresh, so clients don't refetch every turn, and cacheScope for whether the cache may be shared across users or must stay private. Getting cacheScope wrong in a shared cache can leak one tenant's tools or data to another."

Likely follow-up questions

  • Why different tool lists per user? Authorisation: users only see tools and resources they are permitted to use.
  • Why opaque cursors? Servers can change pagination internals without breaking clients.
  • What if a notification is missed? TTL expiry eventually forces a refresh.
