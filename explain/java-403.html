What is database normalization, and when would you denormalize?

Databases & SQL · concept · levels entry, mid

In one line

Normalization structures tables so each fact is stored once, removing redundancy and update, insert and delete anomalies through 1NF, 2NF and 3NF; you denormalize deliberately for read performance, accepting the cost of keeping copies consistent.

Detailed explanation

When the same fact is stored in many rows, it can drift out of sync. If the customer's city is copied onto every order, changing it requires updating thousands of rows, and missing one leaves the data contradictory: an update anomaly. You also cannot record a customer until they order (insert anomaly), and deleting their last order loses the customer (delete anomaly).

The normal forms are a checklist:

  • 1NF: atomic values, no repeating groups or comma-separated lists; each row identified by a key.
  • 2NF: 1NF, and every non-key column depends on the whole composite key, not part of it. In order_item(order_id, product_id, product_name), product_name depends only on product_id, so it moves to a product table.
  • 3NF: 2NF, and no transitive dependencies: non-key columns depend only on the key. Customer city depends on customer, not on the order.
  • BCNF tightens 3NF so every determinant is a candidate key.

For OLTP systems I normalise to roughly 3NF by default. Denormalization is a deliberate optimisation once a real read problem exists: storing a computed order total, copying the price and product name onto order lines (which is also a legal record of what was sold), summary tables, materialised views, star schemas in a warehouse, search indexes, and CQRS read models. The price is more storage, more complex writes and the risk of inconsistent copies.

How it works

  1. Identify entities and their keys.
  2. Remove repeating groups into child tables (1NF).
  3. Move columns that depend on part of a composite key (2NF).
  4. Move columns that depend on other non-key columns (3NF).
  5. Measure real query performance.
  6. Denormalize specific hot paths and define how copies are kept in sync (triggers, events, batch rebuilds).

Example

-- Unnormalised: orders(id, customer_name, customer_city, product_list)
CREATE TABLE customer (id BIGINT PRIMARY KEY, name TEXT, city TEXT);
CREATE TABLE orders   (id BIGINT PRIMARY KEY,
                       customer_id BIGINT REFERENCES customer(id),
                       created_at TIMESTAMP);
CREATE TABLE order_item (order_id BIGINT REFERENCES orders(id),
                         product_id BIGINT, qty INT,
                         unit_price NUMERIC(10,2),   -- deliberate copy: price at sale time
                         PRIMARY KEY (order_id, product_id));

Common mistakes

  • Denormalising up front "for speed" without measuring.
  • Normalising so aggressively that simple screens need ten joins.
  • Treating price-at-time-of-sale as redundancy; it is actually a different fact.
  • Adding redundant columns with no mechanism to keep them consistent.

How to answer in the interview

"Normalization means storing each fact once, in the table it belongs to, so we avoid update, insert and delete anomalies. First normal form means atomic values and no repeating groups, second removes columns that depend on only part of a composite key, and third removes transitive dependencies, so non-key columns depend only on the key. I normalise transactional data to about third normal form by default. I denormalize deliberately when reads are proven slow, for example storing an order total, summary tables, materialised views or read models for search, and I always decide how those copies stay in sync."

Likely follow-up questions

  • Example of an update anomaly? Customer city copied on every order; changing it in some rows but not others.
  • How do you keep denormalised data consistent? Same-transaction updates, triggers, domain events or periodic rebuilds.
  • Is a JSON column a 1NF violation? Strictly yes if you query inside it often; it is fine for opaque or rarely filtered data.
