What is the Saga pattern?

Microservices · concept · levels mid, senior

In one line

A saga manages a business transaction across services as a sequence of local transactions, each triggering the next via events or commands, with compensating transactions undoing completed steps on failure; it is coordinated by orchestration or choreography and gives eventual consistency instead of two-phase commit.

Detailed explanation

In a microservice architecture each service owns its database, so placing an order touches several databases: orders, payments, inventory, shipping. One ACID transaction cannot span them, and distributed two-phase commit is avoided because it couples availability, holds locks across services and is poorly supported by brokers and cloud databases.

The saga pattern, first described by Garcia-Molina and Salem in 1987 for long-lived database transactions, splits the business transaction into local transactions. For an order:

  1. Order service creates the order with status PENDING.
  2. Payment service charges the card.
  3. Inventory service reserves stock.
  4. Shipping service schedules delivery.
  5. Order service marks the order CONFIRMED.

Each step commits locally and then publishes an event or sends a command that triggers the next step. If a step fails, earlier steps cannot be rolled back because they are already committed, so the saga runs compensating transactions in reverse order: release the stock, refund the payment, cancel the order. Compensation is a semantic undo, often visible to the user (a refund appears on the statement), and must be idempotent and retryable.

Sagas are coordinated in two ways. Choreography: services react to each other's events with no central controller; good for short flows. Orchestration: a central orchestrator or workflow engine (Temporal, Camunda, AWS Step Functions) sends commands and tracks state; clearer for long flows.

Sagas give eventual consistency: intermediate states such as PENDING are visible and must be acceptable to the business and UI. Because steps are not isolated, design against anomalies using semantic locks (status flags), and publish events reliably using the transactional outbox, with idempotent participants.

How it works

  1. Start: local transaction in the first service plus outbox event.
  2. Each participant consumes, performs its local transaction, emits success or failure.
  3. On success, the next step runs.
  4. On failure, compensations run for completed steps in reverse.
  5. Final state: CONFIRMED or CANCELLED.

Example

Happy path:
OrderCreated(PENDING) -> PaymentCharged -> StockReserved -> ShipmentScheduled -> OrderConfirmed

Failure at inventory:
OrderCreated(PENDING) -> PaymentCharged -> StockUnavailable
   compensate: RefundPayment -> PaymentRefunded -> CancelOrder -> OrderCancelled
@KafkaListener(topics = "inventory.events", groupId = "payment-saga")
public void onStockUnavailable(StockUnavailable e) {
    if (!processed.markIfNew(e.eventId())) return;  // idempotent
    paymentService.refund(e.orderId());              // compensating transaction
    outbox.save(OutboxEvent.of("PaymentRefunded", e.orderId()));
}

Common mistakes

  • Forgetting compensations for some steps.
  • Non-idempotent participants, causing double refunds.
  • Hiding the PENDING state from the UI and confusing users.
  • Publishing saga events with dual writes instead of an outbox.

How to answer in the interview

"A saga manages a business transaction spanning several services, each with its own database, without two-phase commit. It is a sequence of local transactions: the order service creates a pending order, payment charges the card, inventory reserves stock, shipping schedules delivery. Each step commits locally and triggers the next through an event or command. If a step fails, the saga runs compensating transactions for the steps already done, such as refunding the payment and cancelling the order. Sagas are coordinated by orchestration or choreography and give eventual consistency, so intermediate states like PENDING must be acceptable, and participants must be idempotent."

Likely follow-up questions

  • Why avoid two-phase commit? It blocks on coordinator failure, holds locks across services and couples their availability.
  • What if a compensation fails? Retry it idempotently; if it keeps failing, alert for manual intervention.
  • What is a pivot transaction? The point of no return after which the saga must complete forward.
