How do you use forecasting for capacity planning and predictive autoscaling?

AI Agents & AIOps · concept · levels mid, senior

In one line

Forecasting learns demand patterns and seasonality from history so predictive autoscaling adds capacity before peaks, with reactive autoscaling as a safety net, known events as overrides, longer forecasts for capacity and quota planning, and monitored forecast accuracy.

Detailed explanation

Reactive autoscaling waits for CPU or request rate to rise, then adds capacity. If new instances or GPU nodes take five to ten minutes to become ready, users suffer during every morning surge. Forecasting fixes this for predictable load.

Models learn from history: requests per second, CPU, queue depth or storage growth, with daily and weekly seasonality and trends. Methods range from seasonal decomposition and exponential smoothing (Holt-Winters) to Prophet-style models and ML. Predictive scaling uses short-term forecasts to scale ahead, for example at 08:45 for the 09:00 surge. AWS EC2 Auto Scaling predictive scaling and Azure VMSS predictive autoscale provide this natively; on Kubernetes, KEDA's cron scaler or a forecasting controller can raise minimum replicas ahead of time.

Predictive scaling should set a floor, while reactive scaling handles unexpected spikes on top. Known events, such as launches, sales or TV adverts, cannot be learned from history and are added as inputs or manual overrides. Longer horizons drive capacity planning: reserved instances, savings plans and quota requests, which can take days. Monitor accuracy (for example MAPE) and retrain when patterns change.

How it works

  1. Collect several weeks to months of demand metrics.
  2. Fit a model with seasonality and trend; forecast the next hours and weeks.
  3. Convert forecast demand into required capacity using per-instance throughput.
  4. Schedule minimum capacity ahead of predicted peaks, plus warm-up time.
  5. Keep reactive autoscaling for deviations above the forecast.
  6. Track forecast error and cost; retrain and adjust.

Example

# KEDA: raise the floor before the weekday surge; HPA metrics still scale above it
triggers:
  - type: cron
    metadata:
      timezone: Europe/London
      start: "45 8 * * 1-5"
      end:   "0 18 * * 1-5"
      desiredReplicas: "40"
  - type: prometheus
    metadata:
      query: sum(rate(http_requests_total{app="checkout"}[2m]))
      threshold: "200"

Using AWS, the equivalent is a predictive scaling policy in "forecast only" mode first, then "forecast and scale".

Common mistakes

  • Replacing reactive scaling entirely with forecasts.
  • Ignoring warm-up time when timing scale-out.
  • Forgetting one-off events and holidays.
  • Never checking whether forecasts overprovision every day.

How to answer in the interview

"Forecasting models learn demand patterns with daily and weekly seasonality, and predictive autoscaling uses them to add capacity before peaks, which matters when instances or GPU nodes take minutes to start. AWS and Azure offer predictive scaling natively. I always keep reactive autoscaling as a safety net for surprises, add known events like campaigns as overrides, and use longer forecasts for reservations and quota requests. I monitor forecast accuracy and start in forecast-only mode to compare predictions with reality before letting it scale."

Likely follow-up questions

  • What if it overestimates daily? You pay for idle capacity; tune or cap the forecast.
  • Which metric to forecast? A load metric proportional to capacity, like requests per second.
  • Batch workloads? Scheduled scaling or queue-based scaling usually beats forecasting.
