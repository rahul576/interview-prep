What is KEDA, and when do you use it instead of a plain HPA?

Kubernetes · concept · levels mid, senior

In one line

KEDA (Kubernetes Event-Driven Autoscaling) scales workloads on event sources via many built-in scalers (Kafka lag, queues, Prometheus, cron, databases), creates and drives an HPA under the hood, and adds scale to zero and from zero; ScaledObject scales Deployments, ScaledJob launches Jobs.

Detailed explanation

A plain HPA scales between minReplicas (at least 1) and maxReplicas, using metrics someone has exposed through a metrics API. For event-driven consumers, the right signal lives outside the cluster (how many messages are waiting) and the ideal minimum is often zero.

KEDA, a CNCF graduated project, adds:

  • Scalers for dozens of sources: Kafka consumer lag, RabbitMQ, AWS SQS, Azure Service Bus, Google Pub/Sub, Redis lists and streams, PostgreSQL or MySQL queries, Prometheus queries, cron schedules, HTTP (via an add-on) and more. Authentication is configured with TriggerAuthentication, ideally using workload identity rather than stored keys.
  • A ScaledObject that targets a Deployment, StatefulSet or custom resource with a scale subresource. KEDA's operator creates an HPA for it and serves the scaler values through the external metrics API, so the HPA does the 1-to-N scaling with all its behaviour settings.
  • Activation: KEDA itself handles 0 ↔ 1. When the trigger shows no work for the cooldown period, it scales the workload to zero; when work appears (above the activation threshold), it scales to one and hands over to the HPA.
  • A ScaledJob for long-running or bursty work: instead of scaling a Deployment, it creates Jobs in proportion to the backlog, so each pod processes messages and exits, and in-flight work isn't killed by a scale-down.

Use KEDA for queue consumers, stream processors, scheduled bursts and spiky internal workloads where CPU is a poor proxy. Trade-offs: cold start latency when scaling from zero, polling intervals adding delay, and another operator to run.

How it works

  1. Install KEDA (operator plus metrics server).
  2. Create a ScaledObject with triggers, min/max and cooldown.
  3. KEDA polls the source every pollingInterval.
  4. No work → scales to zero after cooldownPeriod.
  5. Work appears → scales to 1; HPA scales further using the external metric.

Example

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata: { name: order-consumer }
spec:
  scaleTargetRef: { name: order-consumer }
  minReplicaCount: 0
  maxReplicaCount: 40
  cooldownPeriod: 300
  triggers:
  - type: kafka
    metadata:
      bootstrapServers: kafka:9092
      consumerGroup: orders
      topic: orders
      lagThreshold: "500"

Common mistakes

  • Creating your own HPA for the same Deployment as a ScaledObject.
  • More replicas than Kafka partitions, leaving consumers idle.
  • Scale-to-zero for latency-sensitive synchronous APIs.
  • Using a Deployment for long jobs that get killed on scale-down instead of ScaledJob.

How to answer in the interview

"KEDA is Kubernetes Event-Driven Autoscaling. I define a ScaledObject pointing at a deployment with triggers from built-in scalers like Kafka lag, SQS or Service Bus queue length, Prometheus queries or cron. KEDA creates and drives an HPA for one to N replicas through the external metrics API, and handles zero to one itself, so workloads scale to zero when idle, which a plain HPA can't. For batch-style work a ScaledJob creates Jobs per backlog instead. I use it for queue consumers and event processing, where CPU is a poor signal."

Likely follow-up questions

  • Cold-start trade-off of zero? First messages wait for scheduling, image pull and start-up; keep min 1 for latency-sensitive paths.
  • Max replicas for Kafka? No more than the partition count of the topic.
  • How does KEDA authenticate? TriggerAuthentication with Secrets or workload identity.
