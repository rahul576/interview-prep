What is PagedAttention, and why did vLLM become popular for serving?

LLMOps & RAG · concept · levels mid, senior

In one line

PagedAttention stores the KV cache in fixed-size blocks mapped by a block table, like OS virtual memory pages, eliminating fragmentation and over-reservation and enabling block sharing for common prefixes; combined with continuous batching and an OpenAI-compatible API, it made vLLM the default open serving engine.

Detailed explanation

Early serving systems allocated each request one contiguous KV region sized for the maximum possible length, for example 2,048 or 4,096 tokens, because they could not know in advance how long the output would be. Most answers are far shorter, so most of that memory was reserved but unused (internal fragmentation), and variable-sized regions left unusable gaps (external fragmentation).

PagedAttention borrows the idea of paging. The KV cache is divided into small blocks, each holding keys and values for a fixed number of tokens (16 by default in vLLM). A per-sequence block table maps logical token positions to physical blocks anywhere in GPU memory. Blocks are allocated on demand as the sequence grows, so waste is limited to the last partly filled block.

Paging also enables sharing. Sequences with the same prefix, such as a shared system prompt, or several samples from one prompt in parallel sampling or beam search, point to the same physical blocks, with copy-on-write when one diverges. This underpins automatic prefix caching.

The result: many more sequences fit in the same memory, so batches are larger and throughput rises substantially, often 2 to 4 times against earlier systems in the paper's benchmarks. vLLM became popular by pairing this with continuous batching, chunked prefill, prefix caching, many quantisation formats (FP8, AWQ, GPTQ), tensor and pipeline parallelism, speculative decoding, LoRA adapters, broad model and hardware support (NVIDIA, AMD, TPU and others), and an OpenAI-compatible server that lets teams swap it in behind existing clients.

How it works

  1. New request gets an empty block table.
  2. Prefill fills as many blocks as the prompt needs.
  3. Each decode step appends to the last block, allocating a new one when full.
  4. Matching prefixes reuse existing blocks by reference count.
  5. On completion, blocks return to the free pool or stay cached.

Example

vllm serve meta-llama/Llama-3.1-8B-Instruct --enable-prefix-caching --block-size 16
curl localhost:8000/v1/chat/completions -H "Content-Type: application/json" \
  -d '{"model":"meta-llama/Llama-3.1-8B-Instruct","messages":[{"role":"user","content":"Hi"}]}'

Common mistakes

  • Thinking PagedAttention makes the model compute faster; it improves memory efficiency and therefore batching.
  • Assuming vLLM is always fastest regardless of hardware or workload.
  • Setting gpu-memory-utilization too high and hitting out-of-memory with other processes.
  • Ignoring version upgrades, since the engine changes quickly.

How to answer in the interview

"Before PagedAttention, servers reserved one contiguous KV region per request sized for the maximum length, which wasted most of the memory through fragmentation and over-reservation. vLLM's PagedAttention splits the KV cache into small fixed-size blocks, like virtual memory pages, with a block table per sequence and allocation on demand, so almost nothing is wasted and blocks can be shared copy-on-write between sequences with the same prefix. More sequences fit on the GPU, so throughput rises a lot. vLLM became the default by combining that with continuous batching, prefix caching, quantisation, parallelism, broad model support and an OpenAI-compatible API."

Likely follow-up questions

  • When choose another engine? TensorRT-LLM for maximum NVIDIA performance, SGLang for heavy prefix reuse, llama.cpp for CPU or edge.
  • What is block size trade-off? Smaller blocks waste less memory but add table overhead.
  • Does paging help long contexts? Yes, memory is used only as tokens are generated.
