How do you deploy and scale a remote MCP server in production?

MCP Servers · design · levels mid, senior, lead

In one line

Package the server as a container, run it on Kubernetes, Container Apps or serverless behind TLS and a gateway handling OAuth, rate limits and logging, keep it stateless so any replica serves any request, put handles, tasks and tokens in external state (Redis, database), autoscale on request rate, concurrency and latency, and ship with health checks, observability and gradual rollouts.

Detailed explanation

A remote MCP server is a web service with some special traits: long-running tool calls, possibly streaming responses, and clients that are models whose behaviour depends on your tool descriptions.

Packaging and platform. Build a container image and run it where your organisation runs services: Kubernetes, Azure Container Apps, Cloud Run, ECS, or serverless functions for light, short tools. Put it behind TLS and an API or MCP gateway that validates OAuth tokens, applies rate limits and logs calls.

Statelessness. Design the server so any replica can handle any request. Older protocol revisions used an initialisation handshake and an Mcp-Session-Id, tempting servers to keep session state in memory, which breaks behind load balancers. The newer stateless revision (2026-07-28) makes stateless operation the default, so an ordinary load balancer works without sticky sessions. Anything that must persist, such as handles, long-running tasks, idempotency keys and stored OAuth refresh tokens, goes into external state like Redis or a database.

Scaling. Tool calls are usually I/O-bound, waiting on downstream APIs, so CPU is a poor scaling signal. Autoscale on request rate, in-flight concurrency and latency (KEDA or HPA with custom metrics). Set timeouts per downstream and use connection pools.

Operations. Liveness and readiness probes, metrics and traces per tool, alerts, and gradual rollouts (canary or blue-green). Treat tool description changes as behaviour changes: run an evaluation set of realistic prompts before promoting a version, because a reworded description can change which tools models choose.

How it works

  1. CI builds and signs the image, runs unit tests and tool-selection evals.
  2. Deploy to a canary with a small share of traffic via the gateway.
  3. Replicas are stateless; Redis stores tasks, handles and idempotency keys.
  4. Autoscaler scales on concurrency and p95 latency.
  5. Metrics and evals look good; promote to full rollout.

Example

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata: { name: orders-mcp }
spec:
  scaleTargetRef: { name: orders-mcp }
  minReplicaCount: 2
  maxReplicaCount: 30
  triggers:
    - type: prometheus
      metadata:
        serverAddress: http://prometheus:9090
        query: sum(mcp_inflight_requests{service="orders-mcp"})
        threshold: "20"

Common mistakes

  • In-memory session or task state with multiple replicas.
  • Scaling on CPU for an I/O-bound server.
  • Deploying description changes without evaluation.
  • Validating OAuth inconsistently in each server instead of at a shared layer plus the server.

How to answer in the interview

It's stateless, which the 2026-07-28 revision makes the default, so any replica can serve any request and a normal load balancer works without sticky sessions; anything that must persist, like handles, tasks or refresh tokens, goes in Redis or a database. I autoscale on request rate, concurrency and latency rather than CPU, because tool calls mostly wait on downstream APIs. Likely follow-up questions

  • Older clients with sessions? Support the older transport at the gateway with sticky routing, or store session data externally.
  • Serverless suitable? For short tools yes; long tasks need external state and async patterns.
  • Minimum replicas? At least two across zones for availability.
