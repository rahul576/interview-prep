How do you read a Terraform plan? What do the +, -, ~ and -/+ symbols mean?

Infrastructure as Code · concept · levels entry

In one line

In a plan, + create, - destroy, ~ update in place, -/+ replace (destroy then create) and +/- replace with create_before_destroy; always look for "forces replacement", understand "known after apply", and check the summary line.

Detailed explanation

terraform plan compares configuration, state and refreshed reality and lists the actions it proposes, each prefixed with a symbol:

  • + create: a new resource will be created.
  • - destroy: an existing resource will be deleted.
  • ~ update in place: some arguments change and the provider can modify the object without recreating it.
  • -/+ replace: an argument that the API cannot change in place has changed, so Terraform destroys the old object and creates a new one. With create_before_destroy it shows +/-: new first, then delete.
  • <= read: a data source will be read during apply, because its inputs are not known yet.

For replacements Terraform annotates the responsible attribute with # forces replacement. This is the single most important line to check: replacing a database, a disk, a load balancer or a Kubernetes cluster can mean data loss or downtime, and it is often triggered by an innocent-looking change such as a subnet, name or availability zone.

(known after apply) marks values the provider computes during creation, like IDs and ARNs. Many of them are harmless, but a known-after-apply value feeding a force-new argument can cascade into more replacements. (sensitive value) hides sensitive attributes.

The final line, such as Plan: 3 to add, 1 to change, 0 to destroy., gives the scale and is a quick sanity check: a small code change should not produce "12 to destroy". Recent versions also report moved, imported and forgotten objects.

Reviewers should read the whole plan, not just the summary. In CI the plan is saved with -out=tfplan, rendered with terraform show tfplan, and terraform show -json tfplan feeds automated policy checks.

How it works

  1. Refresh real objects and compare with config and state.
  2. Decide per resource: no-op, create, update, replace, delete.
  3. Mark attributes that force replacement.
  4. Print grouped changes and a summary.
  5. Optionally save the plan for an exact apply later.

Example

  # aws_db_instance.orders must be replaced
-/+ resource "aws_db_instance" "orders" {
      ~ availability_zone = "eu-west-1a" -> "eu-west-1b" # forces replacement
      ~ id                = "orders-db" -> (known after apply)
        # (25 unchanged attributes hidden)
    }

  # aws_security_group.web will be updated in-place
  ~ resource "aws_security_group" "web" {
      ~ description = "web" -> "web tier"
    }

Plan: 1 to add, 1 to change, 1 to destroy.
terraform plan -out=tfplan
terraform show -json tfplan | jq '.resource_changes[] | select(.change.actions | index("delete")) | .address'

Common mistakes

  • Reading only the summary line.
  • Missing a -/+ on a stateful resource.
  • Running apply without a saved plan, so something different gets applied.
  • Ignoring unexpected in-place updates that indicate drift.

How to answer in the interview

"Plus means create, minus destroy, tilde update in place, and minus-slash-plus replace: destroy and recreate, or plus-slash-minus if create_before_destroy is set. For replacements the plan marks the argument that forces replacement, which is the first thing I look for, because replacing a database or load balancer can mean data loss or downtime. Known after apply values are computed by the provider. The summary line gives the scale. I read the whole plan, save it with -out, and question any unexpected destroy or replace."

Likely follow-up questions

  • Why apply a saved plan file in CI rather than running apply again? It guarantees what was reviewed is exactly what's applied; Terraform rejects it if state changed meanwhile.
  • What does <= mean? A data source read deferred to apply time.
  • How can you avoid a forced replacement? Revert the change, use ignore_changes if appropriate, or plan a migration.
