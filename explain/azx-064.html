You are responsible for 500 pipelines across 40 teams. How do you standardise and govern them without slowing teams down?

Azure DevOps & Pipelines · design · levels lead

In one line

Govern 500 pipelines with a central, versioned template library (extends templates), golden-path starters, security built into templates, required template checks on production resources and metrics, run as an inner-source platform so the compliant path is also the easiest one.

Detailed explanation

At this scale you cannot review every pipeline, and you cannot force every team into one rigid design. The goal is to make the right way the default way.

A platform team owns a template repository with extends templates for the main stacks: .NET, Java, Node, Python and containers. An extends template controls the overall structure (stages, required steps, deployment jobs) while exposing parameters and extension points (step lists) where teams add their own logic. Templates are versioned with Git tags or release branches, and consumers reference them through a repository resource with a ref, so a change does not break 500 pipelines at once.

Golden-path starters (for example a repository template or scaffolding tool that creates a new service with a ready pipeline) mean new services are compliant from day one. Security is built in: secret scanning, dependency and container scanning, SBOM generation, image signing and publishing to an approved registry.

Enforcement happens where it matters: production environments and service connections get a Required template check, so only pipelines that extend an approved template can use them. Combined with branch control checks and approvals, this gives auditors a strong guarantee without manual reviews.

Finally, measure and support. Track DORA metrics, pipeline duration, queue time and failure rate per template version to find bottlenecks. Treat templates as a product: documentation, changelog, office hours, a support channel, and pull-request contributions from product teams.

How it works

  1. Create platform/pipeline-templates with stack-specific extends templates.
  2. Tag releases (v3.2.0) and publish a changelog and migration guide.
  3. Provide starters that reference @templates at a pinned ref.
  4. Add Required template checks on prod environments and service connections.
  5. Report adoption and DORA metrics per team; deprecate old versions with dates.
  6. Accept contributions through PRs reviewed by the platform team.

Example

resources:
  repositories:
  - repository: templates
    type: git
    name: Platform/pipeline-templates
    ref: refs/tags/v3.2.0

extends:
  template: dotnet/service.yml@templates
  parameters:
    serviceName: orders-api
    runIntegrationTests: true
    extraTestSteps:
    - script: dotnet test tests/Contract

Common mistakes

  • One giant template with hundreds of parameters that nobody understands.
  • Consumers referencing main, so every template change hits production pipelines instantly.
  • Enforcing through manual reviews instead of required template checks.
  • No owner or support, so teams fork templates and drift.

How to answer in the interview

"I'd create a platform-owned, versioned library of extends templates for each main stack, providing build, test, scanning, SBOM, signing and deployment. New services start from golden-path starters so compliance is the default. Production environments and service connections get Required template checks, so only approved templates can deploy, but teams still customise through parameters and extension points. I track DORA metrics, duration and failure rates, and run it as inner source with docs, a changelog and support."

Likely follow-up questions

  • How do you roll out a breaking change? New major version, migration guide, automated PRs, a deprecation date and adoption dashboards.
  • How do you allow exceptions? Extension points first; documented, time-limited exemptions approved by security.
  • Classic release pipelines? Migrate them to YAML so they can be governed the same way.
