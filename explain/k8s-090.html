A pod shows CreateContainerConfigError. What does it usually mean and how do you fix it?

Kubernetes · scenario · levels entry, mid, senior

In one line

CreateContainerConfigError means the kubelet could not assemble the container's configuration, almost always because a referenced ConfigMap, Secret or key does not exist; kubectl describe pod shows exactly which one.

Detailed explanation

Before starting a container, the kubelet resolves everything the pod spec points to: env.valueFrom, envFrom, and projected or volume sources. If a referenced object is missing in the pod's namespace, or the object exists but the named key does not, the kubelet cannot build the config and the container sits in CreateContainerConfigError. The image is fine and the scheduler has done its job; this is purely a reference problem.

Typical causes are a Secret or ConfigMap that was never created in that namespace (objects are namespaced, so one in default does not help a pod in shop), a name typo, a key renamed in a newer config version, or an External Secrets Operator or Sealed Secrets sync that failed, so the target Secret never appeared. A related cause with the same status is a security context conflict, for example runAsNonRoot: true with an image whose user is root.

The kubelet retries automatically, so once you create the object or fix the reference the pod starts without being deleted. For genuinely optional configuration, mark the reference optional: true.

How it works

  1. kubectl get pod shows CreateContainerConfigError.
  2. kubectl describe pod events give the message, e.g. secret "db-credentials" not found.
  3. Check the object in the right namespace and list its keys.
  4. If it is synced from an external store, check the ExternalSecret status and controller logs.
  5. Create or fix the object or the reference; the kubelet retries on its own.

Example

kubectl -n shop describe pod api-7d9f | grep -A3 Events
#  Error: couldn't find key password in Secret shop/db-credentials
kubectl -n shop get secret db-credentials -o jsonpath='{.data}' | jq 'keys'
# ["pass","user"]   -> key was renamed
env:
  - name: FEATURE_FLAGS
    valueFrom:
      configMapKeyRef: { name: flags, key: all, optional: true }

Common mistakes

  • Creating the Secret in a different namespace from the pod.
  • Deleting and recreating pods repeatedly instead of reading the event message.
  • Marking required secrets optional: true just to make the error go away.
  • Deploying workloads before the secrets they depend on in the pipeline.

How to answer in the interview

"CreateContainerConfigError means the kubelet could not build the container configuration, which almost always means something the pod references does not exist. I run kubectl describe pod and the events tell me exactly what, for example secret not found or a missing key in a ConfigMap. Then I check the namespace, spelling and keys, and if the secret comes from External Secrets I check that sync. Once the object exists the kubelet retries by itself. For optional settings I use optional true, and in pipelines I make sure secrets are created before the workloads."

Likely follow-up questions

  • How would you catch this before deploying? Render manifests in CI and run policy or dry-run checks that referenced objects exist, plus GitOps sync ordering.
  • How does it differ from CreateContainerError? That one comes from the runtime, such as a bad command or mount, after the config was built.
  • Does updating a ConfigMap restart pods? No; mounted files update eventually, but env vars need a rollout.
