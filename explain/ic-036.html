How do you refactor Terraform code without destroying resources?

Infrastructure as Code · concept · levels mid

In one line

Renaming or moving resources changes their address, which Terraform reads as destroy + create; record the change with moved blocks (or the older terraform state mv), require a plan with only moves, and use import and removed blocks to adopt or forget resources.

Detailed explanation

Terraform tracks each real object by its resource address in state, such as aws_instance.web or module.app.aws_instance.this["a"]. Refactoring that changes the address, like renaming a resource, moving it into or out of a module, renaming a module call, or switching from count to for_each, looks to Terraform like one resource removed and a new one added, so the plan proposes destroying and recreating it. For a database or network, that is unacceptable.

moved blocks (Terraform 1.1+) declare the refactor in code: moved { from = aws_instance.web to = module.web.aws_instance.this }. During the next plan Terraform updates the address in state, and the plan shows "has moved to" with no destroy. Because the block lives in code, every environment and every state using that configuration migrates automatically when it next runs, and reviewers see exactly what was renamed. Shared modules should keep moved blocks for a while so consumers on older versions can upgrade safely.

The older method is terraform state mv, a CLI command that edits state directly. It works, but must be run manually against every state, outside the normal review process, which is error-prone.

Related tools: import blocks (1.5+) adopt existing resources into state declaratively, and terraform plan -generate-config-out can draft the configuration; removed blocks (1.7+) with lifecycle { destroy = false } stop managing a resource without destroying it, the declarative version of terraform state rm.

The rule after any refactor: run plan in every environment and confirm it shows only moves, no create or destroy.

How it works

  1. Change the code structure.
  2. Add moved blocks mapping old to new addresses.
  3. Plan: Terraform matches old state entries to new addresses.
  4. Apply updates state without touching infrastructure.
  5. Remove moved blocks later once all states have migrated.

Example

# Rename and move into a module
moved {
  from = aws_instance.web
  to   = module.web.aws_instance.this
}

# count -> for_each
moved {
  from = aws_iam_user.users[0]
  to   = aws_iam_user.users["alice"]
}

# Adopt an existing bucket
import {
  to = aws_s3_bucket.legacy
  id = "acme-legacy-bucket"
}

# Stop managing without deleting
removed {
  from = aws_s3_bucket.old_logs
  lifecycle { destroy = false }
}
terraform plan   # expect: "has moved to", "will be imported", 0 to destroy
terraform state mv 'aws_instance.web' 'module.web.aws_instance.this'   # older approach

Common mistakes

  • Refactoring without checking the plan in every environment.
  • Using state mv in one environment and forgetting the others.
  • Removing moved blocks from a shared module too early.
  • Deleting a resource block to "forget" it, which destroys the resource.

How to answer in the interview

"Terraform identifies resources by address, so renaming one, moving it into a module or switching count to for_each looks like delete plus create. moved blocks solve that declaratively: moved from aws_instance.web to module.web.aws_instance.this tells Terraform it's the same object at a new address, and state is updated on the next apply in every environment automatically. The older way was terraform state mv, run manually per state. After a refactor the plan must show only moves, no destroy or create. import blocks adopt existing resources, and removed blocks stop managing one without destroying it."

Likely follow-up questions

  • How would you split one large state into two without recreating anything? Add removed blocks (destroy = false) in the old config and import blocks in the new one, or use terraform state mv -state-out; verify both plans show no changes.
  • Can moved blocks cross state boundaries? No, only within one state.
  • How do you generate config for imports? terraform plan -generate-config-out=generated.tf.
