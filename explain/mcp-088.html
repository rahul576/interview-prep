Leadership wants every internal API exposed as MCP tools this quarter. How do you respond?

MCP Servers · scenario · levels senior, lead

In one line

Support the goal, change the approach: instead of auto-generating tools for every API, build foundations first (auth, gateway, audit, registry, server template), prioritise high-value, read-only use cases with task-oriented tools, measure adoption and outcomes, then scale in phases.

Detailed explanation

Leadership's underlying goal, making internal systems usable by AI agents, is sound and worth supporting. The risk is in the literal plan. "Every API as MCP tools this quarter" usually ends up as auto-generated, endpoint-shaped tools from OpenAPI specs. That fails in three ways:

  • Quality. Models perform poorly with hundreds of low-level CRUD tools: they pick the wrong ones, chain them badly and drown in large payloads. Users conclude "AI doesn't work here".
  • Security. Every write endpoint becomes an agent-callable action, often behind a shared service account. The attack surface explodes, and prompt injection can reach anything.
  • Governance. Nobody owns hundreds of servers; there is no audit, versioning or review.

A better response is a phased plan that still shows progress within the quarter.

Phase 1: foundations (first weeks). OAuth integration with the corporate IdP, an MCP gateway for routing, logging and rate limits, an approved internal registry, and a server template (SDK, auth, telemetry, tests, deployment) so teams build consistently and quickly.

Phase 2: high-value pilots. Pick three to five use cases with clear value and low risk, starting read-only: support agents looking up orders, engineers querying deployments and incidents, staff searching policies. Design task-oriented tools with good descriptions and evaluate them.

Phase 3: measure and scale. Track adoption, task success, time saved and incidents. Use the results to prioritise the next APIs and introduce write capabilities with approvals in later phases.

This reframes the quarter's deliverable as "a platform plus proven use cases" rather than "N endpoints wrapped".

How it works

  1. Agree the business outcome with leadership (time saved, self-service rate).
  2. Build the platform pieces and the template.
  3. Select pilots via a value-versus-risk matrix.
  4. Ship pilots with evals, telemetry and approvals.
  5. Report metrics monthly; expand scope based on evidence.

Common mistakes

  • Saying "no" instead of offering a better path.
  • Measuring success by number of tools exposed.
  • Starting with write access to critical systems.
  • Letting every team invent its own auth and logging.

How to answer in the interview

"I'd support the goal of making our systems usable by AI, but push back on auto-generating tools for every API in one quarter, because endpoint-shaped tools work poorly with models, create a huge attack surface and are hard to govern. I'd propose a plan. First, foundations: OAuth with our IdP, an MCP gateway for routing, logging and rate limits, an approved server registry and a template so teams build consistently. Second, prioritise by value and risk: a few high-value use cases like support agents looking up orders or engineers querying deployments, starting read-only, with task-oriented tools. Third, measure adoption, task success and incidents, and use that to scale to more APIs and write capabilities."

Likely follow-up questions

  • Metrics to convince leadership? Weekly active users, task success rate, time saved per task, incidents.
  • Who builds the servers? API-owning teams using the platform template.
  • What if leadership insists? Offer read-only coverage of more APIs, still via the gateway and templates.
