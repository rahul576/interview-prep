How would you troubleshoot frequent Full GC events?

JVM & Performance · scenario · levels senior, lead

In one line

Start with the GC logs: how often full GCs happen, how long they pause and, above all, old-generation occupancy after each GC; a rising baseline means a leak (analyse a heap dump in MAT), a stable baseline that refills fast means an undersized heap or premature promotion; also check humongous allocations, System.gc() calls and Metaspace, then fix code before tuning.

Detailed explanation

Read the evidence. Unified GC logs record the cause of each pause (G1 Compaction Pause, System.gc(), Metadata GC Threshold, G1 Humongous Allocation, "To-space exhausted"). Tools like GCeasy or JDK Mission Control summarise frequency, pause distribution, allocation and promotion rates. The single most useful number is heap used after full GC, the live set.

Pattern 1: baseline keeps climbing. Each full GC frees less, until the service dies. That is a memory leak. Take a heap dump (jcmd GC.heap_dump) at high usage, open it in Eclipse MAT, look at the dominator tree by retained size and the leak suspects report, and follow paths to GC roots. Typical owners: unbounded caches or static maps, ThreadLocal values in pooled threads, listener lists, growing queues, session stores.

Pattern 2: baseline is stable but the heap refills quickly. The live set is simply large relative to the heap, or allocation and promotion rates are so high that concurrent collection cannot keep up. Options: increase the heap (with container headroom), reduce allocation, or check premature promotion where medium-lived objects overflow survivor spaces into old regions.

Pattern 3: specific triggers.

  • Humongous allocations in G1: large arrays (big byte buffers, huge JSON strings, large collections) of half a region or more fill old regions directly and can cause evacuation failures. Fix by chunking data or raising G1HeapRegionSize.
  • Explicit System.gc(): cause shows System.gc(); find the caller, or use -XX:+ExplicitGCInvokesConcurrent.
  • Metaspace: cause Metadata GC Threshold; check class loading and loader leaks.
  • Heap dumps or jmap -histo:live run by monitoring tools also force full GCs.

Fix and verify. Bound caches (Caffeine with size and expiry), remove leaks, stream large data instead of materialising it, then tune: heap size, InitiatingHeapOccupancyPercent to start marking earlier, or switch to ZGC if pauses remain the problem. Confirm with logs that full GCs disappear.

How it works

  1. Collect GC logs and plot old-gen after GC over time.
  2. Classify: rising baseline, fast refill, or specific cause.
  3. Leak: heap dump and MAT analysis.
  4. Pressure: heap sizing, allocation reduction, promotion tuning.
  5. Specific triggers: humongous, explicit GC, Metaspace.
  6. Deploy the fix; verify full GCs stop.

Common mistakes

  • Increasing heap size without knowing whether there is a leak.
  • Looking only at pause times, not occupancy after GC.
  • Missing monitoring agents that trigger heap histograms or dumps.
  • Tuning many flags at once.

How to answer in the interview

"First I read the GC logs, or feed them to GCeasy, to see how often full GCs happen, how long they pause and, most importantly, how much old generation remains after each one. If occupancy after GC keeps rising, it's a leak: I take a heap dump and use Eclipse MAT's dominator tree and paths to GC roots, often finding an unbounded cache, a static map or a ThreadLocal. If occupancy drops but refills quickly, the heap is undersized for the allocation rate or objects are promoted too early. In G1 I also check humongous allocations, explicit System.gc calls and Metaspace. Then I fix the code, bound caches, and only then tune heap size or the collector."

Likely follow-up questions

  • What is a humongous allocation in G1, and why does it matter? An object at least half a region in size, allocated straight into old regions; frequent ones waste space and trigger marking or full GCs.
  • What does "to-space exhausted" mean? G1 had no free regions to copy survivors into, leading to evacuation failure.
  • When would you switch to ZGC? When the live set is healthy but pause times still violate latency goals.
