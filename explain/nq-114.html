How would you explain the algorithm before implementing the solution?

DSA: Algorithms & DP · scenario · levels entry

In one line

Before coding, restate the problem and clarify constraints, walk through a small example by hand, explain the brute force and why it's slow, present the DP insight, then state complexity and edge cases; only then write code and test it.

Detailed explanation

Interviewers assess communication and problem-solving, not just the final code. Jumping straight into typing risks solving the wrong problem and gives the interviewer no window into your reasoning. A structured explanation shows you can reason about requirements, compare approaches and justify trade-offs, which is what real engineering looks like.

For the minimum-cost grid path, start by restating: "Find the cheapest path from top-left to bottom-right." Then clarify: are moves only right and down? Can costs be negative? How large is the grid? Do we need the cost only, or the path too? Is the grid ever empty? These answers can change the algorithm completely (DP versus Dijkstra).

Next, mention the brute force: recursively try every path, which is exponential because the number of paths is combinatorial. Then present the key insight: each cell can only be entered from above or the left, so the best cost into a cell is its value plus the better of those two, and storing these results avoids recomputation. Walk through a 3×3 example, filling the table aloud. State O(m·n) time and the O(n) space option. List edge cases: empty grid, single row or column, very large values. Finally, code it cleanly and dry-run the example to test.

How it works

  1. Restate the problem in your own words.
  2. Ask clarifying questions about moves, costs, size and output.
  3. Describe brute force and its complexity.
  4. Explain the optimisation (DP recurrence) and walk through an example.
  5. State time/space complexity and edge cases.
  6. Code, then test with the example and an edge case.

Example

A spoken walk-through on the whiteboard:

grid        dp
1 3 1       1 4 5
1 5 1  -->  2 7 6
4 2 1       6 8 7

"First row: 1, 1+3=4, 4+1=5. First column: 1, 2, 6.
 Cell (1,1): 5 + min(4, 2) = 7. Cell (1,2): 1 + min(5, 7) = 6.
 Cell (2,1): 2 + min(7, 6) = 8. Cell (2,2): 1 + min(6, 8) = 7. Answer 7."

Common mistakes

  • Coding immediately without clarifying the allowed moves.
  • Skipping the brute force, so the interviewer can't see why DP helps.
  • Explaining for too long without checking in with the interviewer.
  • Forgetting to test the code against the example afterwards.

How to answer in the interview

"I'd start by restating the problem and asking about constraints: which moves are allowed, whether costs can be negative, the grid size, and whether they want the cost or the path. Then I'd mention the brute force of trying every path and why it's exponential. Next the insight: the best way into a cell comes from its best top or left neighbour, so I can store accumulated minimums. I'd fill a 3 by 3 example on the board, state O(m times n) time and O(n) space, and list edge cases like an empty grid or a single row. Only then would I code and dry-run it."

Likely follow-up questions

  • Why do interviewers value this explanation step? It shows reasoning and communication and catches misunderstandings before code is written.
  • What if you get stuck? Say what you're thinking, try a smaller example, and ask for a hint.
  • How do you test without running code? Dry-run the example and an edge case line by line.
