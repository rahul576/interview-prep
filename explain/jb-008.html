Can we override static, private, and final methods in Java? Why?

Core Java & OOP · concept · levels entry, mid

In one line

No: static methods are hidden, not overridden (resolved at compile time by reference type); private methods are not inherited, so a same-named subclass method is unrelated; final methods cannot be overridden at all (compile error).

Detailed explanation

Overriding means runtime polymorphism: the JVM picks the method based on the actual object's class. Only methods that are instance methods, inherited and not final take part in this dynamic dispatch.

Static methods belong to the class, not to an object, so there is no receiver to dispatch on. If a subclass declares a static method with the same signature, it hides the parent method. Which one is called depends on the compile-time (static) type of the expression: Parent p = new Child(); p.staticMethod() calls Parent.staticMethod(). Calling statics through instances is legal but misleading; IDEs warn about it. A subclass also cannot declare an instance method that overrides a static one, or vice versa; both are compile errors. @Override on a static method fails to compile.

Private methods are not visible outside their class and therefore not inherited. A subclass may declare a method with the same signature; it is a completely new method, not an override. Calls to the private method from within the parent class always invoke the parent's version, even on a child object. @Override here also fails.

Final methods are explicitly locked: declaring one with the same signature in a subclass is a compile error. This is used to protect behaviour that must not change, for example template-method algorithms or security checks. A final class (such as String) cannot be subclassed at all, so none of its methods can be overridden.

Related: constructors are never inherited or overridden, and fields are hidden, not overridden.

How it works

  1. Static calls compile to invokestatic with the class fixed at compile time.
  2. Private method calls are bound to the declaring class (historically invokespecial).
  3. Overridable instance calls compile to invokevirtual/invokeinterface, resolved through the vtable at runtime.
  4. The compiler rejects attempts to override final methods.

Example

class Parent {
    static String id()   { return "Parent.static"; }
    private String secret() { return "Parent.private"; }
    final String locked()   { return "Parent.final"; }
    String callSecret()     { return secret(); }
}
class Child extends Parent {
    static String id()   { return "Child.static"; }   // hides
    private String secret() { return "Child.private"; } // new method
    // String locked() { ... }                         // compile error
}

Parent p = new Child();
System.out.println(p.id());          // Parent.static
System.out.println(p.callSecret());  // Parent.private

Common mistakes

  • Saying static methods are overridden because the code compiles.
  • Expecting p.id() to call the child's static version.
  • Forgetting @Override, which would catch these mistakes.
  • Confusing hiding with overloading.

How to answer in the interview

"No in all three cases. Static methods belong to the class, so a subclass method with the same signature only hides the parent's; the call is resolved at compile time from the reference type, not the object. Private methods aren't inherited or visible, so a subclass method with the same name is a brand-new method, and the parent's internal calls still use its own private version. Final methods are explicitly locked, so overriding one is a compile error. Only non-static, non-private, non-final instance methods take part in dynamic dispatch."

Likely follow-up questions

  • What happens if you call a hidden static method through a subclass instance? The version for the variable's declared type runs.
  • Can you overload a static method? Yes, overloading is fine.
  • Can a private method be final? Yes, but it's redundant.
