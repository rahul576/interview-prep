Explain Cosmos DB consistency levels and partitioning.

Azure · concept · levels mid, senior

In one line

Cosmos DB offers five consistency levels (strong, bounded staleness, session, consistent prefix, eventual) trading consistency for latency and availability, with session as the default; data is distributed by a partition key that must spread storage and requests evenly, and throughput is measured in request units (RU/s).

Detailed explanation

Consistency levels, from strongest to weakest:

  • Strong: linearisable reads; always the latest committed write. Highest latency, and not available with multi-region writes.
  • Bounded staleness: reads lag by at most K versions or T time.
  • Session (default): within a client session you get read-your-writes, monotonic reads and writes; other clients may see slightly older data. The best balance for most apps.
  • Consistent prefix: reads never see out-of-order writes, but may be behind.
  • Eventual: no ordering guarantee; lowest latency and cost.

The default is set on the account, and a client can relax it per request but not strengthen it.

Partitioning: each item belongs to a logical partition defined by its partition key value; Cosmos maps logical partitions onto physical partitions, which it splits automatically as data and throughput grow. A logical partition is limited to 20 GB, and each physical partition serves a limited share of RU/s (about 10,000). A good partition key has high cardinality, distributes requests and storage evenly, and appears in the most frequent queries, so they stay single-partition. Cross-partition queries fan out and cost more RUs. Hierarchical partition keys (for example tenantId then userId) help with large tenants.

Throughput is expressed in RU/s; a 1 KB point read by id and partition key costs about 1 RU, writes and queries cost more. Choose provisioned manual, autoscale (scales between 10% and max), or serverless for spiky, low-volume workloads. Exceeding throughput returns HTTP 429, which SDKs retry.

Global distribution: add regions with one click, optional multi-region writes with conflict resolution (last writer wins or custom), and automatic failover.

How it works

  1. Pick API (NoSQL is most common) and default consistency.
  2. Choose a partition key based on access patterns.
  3. Choose throughput model: manual, autoscale or serverless.
  4. Writes route to the physical partition for the key's hash.
  5. Point reads by id plus partition key are cheapest.
  6. Add regions and configure failover or multi-region writes.

Example

Orders container with a partition key on customer:

container = db.create_container_if_not_exists(
    id="orders",
    partition_key=PartitionKey(path="/customerId"),
    offer_throughput=ThroughputProperties(auto_scale_max_throughput=4000),
)
container.upsert_item({"id": "o-981", "customerId": "c-42", "total": 59.90})
item = container.read_item(item="o-981", partition_key="c-42")   # ~1 RU point read

Common mistakes

  • Low-cardinality keys like status or country, causing hot partitions.
  • Partitioning by a timestamp so all writes hit one partition.
  • Choosing strong consistency without need, increasing latency and cost.
  • Queries without the partition key, causing expensive fan-out.
  • Ignoring 429 rates and RU cost per query.

How to answer in the interview

"Cosmos DB offers five consistency levels: strong, bounded staleness, session, consistent prefix and eventual, trading consistency for latency and availability. Session is the default and gives read-your-own-writes per client session, which suits most apps. Data is partitioned by a partition key, which must have high cardinality and even access to avoid hot partitions, and should match the most common query filter so queries hit one partition. Throughput is measured in request units per second, provisioned manually, autoscaled or serverless. It supports global distribution with automatic failover and optional multi-region writes, though strong consistency is not available with multi-region writes."

Likely follow-up questions

  • What would be a good partition key for an orders container? customerId if most queries are per customer; consider hierarchical keys for big tenants.
  • What happens when you exceed RU/s? Requests get 429 with retry-after; SDKs retry, and you scale or optimise.
  • Can you change the partition key later? Not in place; you migrate data to a new container.
