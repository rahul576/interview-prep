Which AWS database services do you know, and when would you use each?

Cloud (AWS) · concept · levels mid, senior

In one line

RDS for managed relational engines, Aurora for high-performance MySQL/PostgreSQL-compatible databases with distributed storage, DynamoDB for serverless key-value/document data at any scale with known access patterns, and ElastiCache for Redis/Valkey/Memcached caching, all with Multi-AZ, backups and encryption.

Detailed explanation

Amazon RDS runs PostgreSQL, MySQL, MariaDB, SQL Server, Oracle and Db2 as a managed service: AWS handles provisioning, patching, automated backups with point-in-time recovery and failover. Multi-AZ keeps a synchronous standby in another AZ and fails over automatically; read replicas (asynchronous) scale reads and can live in other regions. Use it when you want a standard relational database with joins, transactions and SQL.

Amazon Aurora is AWS's cloud-native engine compatible with MySQL and PostgreSQL. Storage is distributed, keeping six copies across three AZs and growing automatically; up to 15 low-lag replicas share the same storage, so failover is faster. Aurora Serverless v2 scales capacity in fine-grained steps for spiky or unpredictable loads, and Global Database replicates to other regions for DR. It costs more than plain RDS, so it pays off for demanding production workloads.

DynamoDB is a fully managed, serverless NoSQL key-value and document database with consistent single-digit millisecond latency at virtually any scale, on-demand or provisioned capacity, streams, TTL and global tables. The catch: you design tables around access patterns known in advance, using a high-cardinality partition key, sort keys and secondary indexes. Ad-hoc queries and joins are not its strength.

ElastiCache provides managed Redis OSS, Valkey or Memcached for caching, sessions, rate limiting and leaderboards, reducing database load and latency.

Others worth knowing: DocumentDB, Neptune (graph), Timestream, OpenSearch and Redshift for analytics.

How it works

  1. Start from the data model and access patterns, not the product.
  2. Relational with complex queries → RDS, or Aurora for scale and fast failover.
  3. Massive scale, simple key lookups → DynamoDB.
  4. Hot reads or sessions → ElastiCache in front.
  5. Always: private subnets, encryption, automated backups, Multi-AZ for production.

Example

aws rds create-db-instance --db-instance-identifier orders-prod \
  --engine postgres --db-instance-class db.r7g.large \
  --allocated-storage 200 --storage-type gp3 \
  --multi-az --backup-retention-period 14 --storage-encrypted \
  --master-username app --manage-master-user-password \
  --db-subnet-group-name private-db --no-publicly-accessible

A DynamoDB orders table might use PK = CUSTOMER#123, SK = ORDER#2026-11-21#987 to fetch a customer's recent orders in one query.

Common mistakes

  • Choosing DynamoDB and then needing ad-hoc relational queries.
  • Low-cardinality partition keys (such as status) creating hot partitions.
  • Confusing read replicas (scaling) with Multi-AZ standby (availability).
  • Publicly accessible databases.

How to answer in the interview

"For relational data I use RDS, managed PostgreSQL or MySQL where AWS handles patching, backups and failover; Multi-AZ keeps a standby and read replicas scale reads. Aurora is AWS's MySQL and PostgreSQL compatible engine with distributed storage across three AZs, faster failover and Serverless v2 for spiky load. DynamoDB is serverless NoSQL with millisecond latency at any scale, great when access patterns are known, but it needs careful key design. ElastiCache with Redis or Valkey is for caching and sessions. In every case: private subnets, encryption and tested backups."

Likely follow-up questions

  • How do you choose a DynamoDB partition key? High cardinality, evenly accessed, matching the main query.
  • Multi-AZ vs read replica? Standby for failover vs asynchronous copy for reads.
  • When Aurora over RDS? High throughput, many replicas, fast failover or global DR needs.
