How do public benchmarks for LLMs work, and why should you be careful interpreting them?

AI/ML & GenAI · concept · levels mid, senior

In one line

LLM benchmarks are standard test sets for knowledge, reasoning, coding, maths and agents (MMLU, GPQA, SWE-bench, HumanEval and others); they help narrow choices but suffer from contamination, saturation, setup sensitivity and selective reporting, so you must run your own evaluations on your tasks.

Detailed explanation

Benchmarks give a common yardstick. Knowledge tests such as MMLU and harder successors like MMLU-Pro cover many subjects; GPQA contains expert-written graduate-level science questions that are hard to look up. Maths benchmarks range from grade-school word problems to competition problems. Coding benchmarks include HumanEval (write a function that passes unit tests), LiveCodeBench (fresh problems collected over time) and SWE-bench, where the model must fix real GitHub issues in real repositories so the project's tests pass. Agent and tool-use benchmarks test multi-step tasks in browsers, terminals or simulated customer-service settings. Human preference leaderboards such as LMArena rank models by blind pairwise votes.

They need careful reading. Contamination: if test questions or solutions appear in web-scraped training data, scores reflect memorisation, which is why newer benchmarks use private, held-out or continually refreshed questions. Saturation: once top models score near the ceiling, differences of a point or two are within noise and say little. Setup sensitivity: prompt format, number of shots, reasoning effort, tool access, sampling and scoring scripts can shift results noticeably, so vendor numbers are not always comparable. Selective reporting: providers publish the benchmarks where they look best. Preference leaderboards can reward style and length over correctness.

Above all, a benchmark rarely matches your domain, data, languages, latency and cost constraints. I use public results to shortlist two or three models, then run an internal evaluation set built from representative and edge-case examples of our real tasks, scoring quality, latency, cost per task and failure modes, and re-run it whenever models or prompts change.

How it works

  1. A benchmark defines fixed inputs and an expected answer or automatic check.
  2. Models are run under a stated setup (prompting, shots, tools, attempts).
  3. Outputs are scored by exact match, unit tests or graders.
  4. Scores are aggregated and compared across models.
  5. Users shortlist models and validate on their own evaluation sets.

Example

# Minimal internal eval harness
results = []
for case in load_cases("evals/support_tickets.jsonl"):
    out = call_model(model_name, prompt_template.format(**case["input"]))
    results.append({
        "id": case["id"],
        "correct": grade(out, case["expected"]),
        "latency_ms": out.latency_ms,
        "cost_usd": out.cost,
    })
summarise(results)   # accuracy, p95 latency, cost per 1k tasks, failure categories

Common mistakes

  • Choosing a model purely from a leaderboard.
  • Comparing numbers from different evaluation setups.
  • Treating a one-point gap on a saturated benchmark as meaningful.
  • Never building a domain-specific evaluation set.

How to answer in the interview

"Benchmarks are standard test sets: MMLU and GPQA for knowledge and reasoning, HumanEval and LiveCodeBench for coding, SWE-bench for fixing real GitHub issues, plus agent benchmarks and preference leaderboards like LMArena. They're useful to track progress and shortlist models, but I'm careful: questions can leak into training data, many are saturated, results depend on the setup, and vendors pick what they report. Most importantly they don't reflect my tasks, so I always run our own evaluation on representative examples, measuring quality, latency and cost."

Likely follow-up questions

  • What makes SWE-bench more realistic? Real repositories, real issues and the project's own tests, requiring navigation of large codebases rather than isolated functions.
  • How do benchmark makers fight contamination? Private test sets, fresh questions after the training cutoff and canary strings.
  • How big should an internal eval set be? Start with 50-200 well-chosen cases and grow it from production failures.
