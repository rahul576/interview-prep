How does the JIT compiler optimise code, and what do warm-up and GraalVM native images change?

JVM & Performance · concept · levels senior, lead

In one line

The JVM interprets bytecode first, profiles it, and uses tiered compilation (fast C1, then optimising C2) to compile hot methods with inlining, escape analysis and speculative optimisations, which is why services need warm-up; GraalVM native image compiles ahead of time for instant startup, while CRaC and Project Leyden AOT caches cut startup without leaving the JVM.

Detailed explanation

Interpreter and profiling. At startup every method runs in the interpreter, which is slow but starts immediately. The JVM counts invocations and loop back-edges and collects profiles: which branches are taken, which concrete types appear at call sites.

Tiered compilation. When a method gets warm, C1 compiles it quickly with light optimisations and profiling code. When it becomes hot, C2 recompiles it using the gathered profile into highly optimised machine code. Hot loops can be replaced mid-execution via on-stack replacement (OSR). Compiled code lives in the code cache.

Key optimisations. Inlining copies small or hot callees into the caller, removing call overhead and enabling everything else. Escape analysis detects objects that never leave a method, enabling scalar replacement (no heap allocation) and lock elision. Also loop unrolling, range-check elimination, intrinsics for things like System.arraycopy and string operations, and speculative optimisations: if a call site has only ever seen one implementation, C2 devirtualises it. If an assumption later breaks (a new subclass is loaded, an untaken branch is hit), the code is deoptimised back to the interpreter and recompiled.

Warm-up. Until hot paths are compiled, latency is higher and CPU usage spikes from compilation. Mitigations: warm-up traffic before joining the load balancer, readiness probes that wait, or synthetic requests at startup.

GraalVM native image. Builds a standalone executable ahead of time with a closed-world analysis. Startup is milliseconds, memory footprint is much smaller, there is no warm-up. Trade-offs: long builds, reflection, proxies and resources need configuration (Spring Boot generates much of it via its AOT processing), and peak throughput may be lower than a well-warmed C2 unless profile-guided optimisation is used (available in Oracle GraalVM).

Other options. CRaC (Coordinated Restore at Checkpoint, in some OpenJDK distributions and supported by Spring) snapshots a warmed JVM and restores it in milliseconds. Project Leyden has started landing in OpenJDK: recent JDKs offer an AOT cache that stores pre-loaded and linked classes and method profiles from a training run, improving startup and warm-up while staying on the normal JVM.

How it works

  1. Method runs in the interpreter; counters and profiles accumulate.
  2. Threshold reached: C1 compiles with profiling.
  3. More invocations: C2 compiles optimised code using the profile.
  4. Assumption violated: deoptimise, interpret, recompile.
  5. Native image skips steps 1-4 by compiling everything at build time.

Example

# Watch JIT activity
java -XX:+PrintCompilation -jar app.jar | head

# JDK AOT cache (recent JDKs): training run, then production run
java -XX:AOTCacheOutput=app.aot -jar app.jar   # run representative workload, exit
java -XX:AOTCache=app.aot -jar app.jar

# Spring Boot native image (GraalVM installed)
./mvnw -Pnative native:compile
./target/orders-service     # starts in tens of milliseconds

Common mistakes

  • Benchmarking without warm-up and blaming Java for slowness.
  • Assuming native image is always faster at steady state.
  • Sending full traffic to a freshly started pod.
  • Treating deoptimisation as a bug rather than normal behaviour.

How to answer in the interview

"The JVM starts by interpreting bytecode and profiling which methods are hot. With tiered compilation, C1 compiles warm code quickly, then C2 recompiles the hottest code using the profile, applying inlining, escape analysis that can remove allocations, loop optimisations and speculative devirtualisation, with deoptimisation if an assumption breaks. That's why Java services need warm-up before peak performance. GraalVM native image compiles ahead of time into a native binary with millisecond startup and lower memory, good for serverless or scale-to-zero, at the cost of long builds and reflection configuration. CRaC snapshots and Leyden-style AOT caches are ways to cut startup while staying on the JVM."

Likely follow-up questions

  • What would make you choose a native image for a Spring Boot service? Fast scale-out, serverless or scale-to-zero, tight memory limits, and dependencies that support AOT.
  • What is deoptimisation? Discarding compiled code whose speculative assumptions no longer hold, falling back to the interpreter.
  • How do you reduce warm-up impact in Kubernetes? Readiness gates after warm-up requests, gradual traffic ramp, or AOT caches/CRaC.
