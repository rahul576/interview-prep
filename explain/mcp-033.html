How do you make MCP tools that change things safe to retry?

MCP Servers · concept · levels mid, senior, lead

In one line

Assume side-effecting tools will be called twice (timeouts, dropped connections, re-issued requests with new ids), so make them idempotent: accept an idempotency key, record each key with its result, and on a duplicate return the existing result instead of repeating the action.

Detailed explanation

A client cannot distinguish "the request failed" from "it succeeded but the response was lost". If create_ticket succeeds and the connection then drops, the retry creates two tickets, or worse, two payments.

MCP makes this more likely: per the reference material for this question, in the stateless 2026-07-28 revision response streams are not resumable, so a dropped request is simply re-issued with a new JSON-RPC id, and the server cannot use the request id to detect duplicates. Agents also retry on their own when results look ambiguous.

Read-only tools are naturally safe to repeat. Tools with side effects need idempotency:

  • Idempotency key parameter. The tool accepts a key supplied by the client or agent, or derived deterministically from the task, for example a hash of the conversation id, step and normalised inputs. Keys from the model itself are acceptable if the description asks for a unique key per intended action, but deterministic derivation is more reliable.
  • Server deduplication. Store key → {status, result, request_hash} atomically (unique constraint or SET NX) before performing the action. If the key exists and the action completed, return the stored result. If it is in progress, return a "still processing" result. If the same key arrives with different arguments, reject it.
  • Pass keys downstream where supported: payment APIs such as Stripe accept Idempotency-Key headers, and many cloud APIs accept client tokens.
  • Natural idempotency: prefer "set status to X" over "toggle", and upserts by business key.
  • Mark such tools with idempotentHint: true and tell the model not to retry blindly.

Asking the model to "remember whether it already called the tool" is not enough: the model never saw the lost response, and its context may be summarised or restarted.

How it works

  1. Tool receives arguments plus idempotency_key.
  2. Atomically insert the key with status "pending"; if it exists, return its stored outcome.
  3. Perform the action, passing the key downstream.
  4. Store the result under the key with a TTL (e.g. 24 h).
  5. Return the result; duplicates within TTL get the same answer.

Example

@mcp.tool(annotations={"idempotentHint": True, "destructiveHint": False})
def create_ticket(project: str, title: str, body: str, idempotency_key: str) -> dict:
    """Create a ticket. Use a new idempotency_key per intended ticket; reuse it when retrying."""
    req_hash = sha256(f"{project}|{title}|{body}".encode()).hexdigest()
    inserted = db.execute(
        "INSERT INTO idem(key, req_hash, status) VALUES (%s, %s, 'pending') ON CONFLICT DO NOTHING",
        (idempotency_key, req_hash)).rowcount
    if not inserted:
        row = db.get_idem(idempotency_key)
        if row.req_hash != req_hash:
            raise ToolError("idempotency_key already used with different arguments.")
        return row.result or {"status": "processing"}
    ticket = jira.create(project, title, body)
    db.complete_idem(idempotency_key, {"ticket": ticket.key, "url": ticket.url})
    return {"ticket": ticket.key, "url": ticket.url}

Common mistakes

  • Using the JSON-RPC request id as the dedup key.
  • Check-then-act without atomicity, so concurrent retries both execute.
  • Relying on the model's memory to avoid duplicates.
  • Storing keys forever, or for too short a time.

How to answer in the interview

"Networks fail and clients time out, and in the stateless revision streams aren't resumable, so a dropped request is just re-issued with a new id. A create_ticket or place_order might run twice even though the first attempt succeeded. Read-only tools are fine, but side-effecting ones must be idempotent. I add an idempotency key parameter, supplied by the client or derived deterministically from the task, and the server records each key atomically with its result. If the same key comes again, it returns the existing result instead of repeating the action. I pass the key downstream where APIs support it, like payments, and mark the tool with idempotentHint."

Likely follow-up questions

  • Why isn't the model's memory enough? It never saw the lost response, and contexts get summarised or restarted.
  • How long to keep keys? Longer than any realistic retry window, often 24 hours to a few days.
  • Same key, different arguments? Reject with a clear error.
