What is database partitioning?

Databases & SQL · concept · levels mid

In one line

Partitioning splits a large table into smaller physical partitions that still look like one table, typically within one database, using range, list or hash on a partition key, giving partition pruning, smaller indexes and cheap archiving.

Detailed explanation

A table with billions of rows becomes hard to query, index, vacuum and clean up. Partitioning divides it while the application keeps writing SELECT ... FROM orders.

Horizontal partitioning (the usual meaning) splits rows:

  • Range: by date or numeric range, for example one partition per month. Ideal for time-series and data with retention policies.
  • List: by discrete values, such as region or country.
  • Hash: by hash of a key modulo N, spreading rows evenly when there is no natural range.
  • Composite / sub-partitioning: range by month, then hash by customer.

Vertical partitioning splits columns: rarely used or large columns (a BLOB, a JSON payload) move to a separate table with the same key, keeping the main table narrow and cache-friendly.

Benefits:

  • Partition pruning: a query filtering on the partition key scans only relevant partitions.
  • Smaller per-partition indexes that fit in memory better.
  • Maintenance: DROP or DETACH an old partition instead of deleting millions of rows; vacuum, reindex and backups per partition.
  • Possibly placing old partitions on cheaper storage.

Caveats: queries that do not filter on the partition key must scan all partitions, sometimes slower than one table. In PostgreSQL, unique constraints and primary keys must include the partition key, and too many partitions (thousands) increase planning overhead. Partitioning is not sharding: it all still runs on one server's CPU, memory and disk.

How it works

  1. Choose a partition key matching the most common filter and retention rule.
  2. Create the parent table with a partitioning method.
  3. Create partitions for ranges or values, plus a default partition if needed.
  4. Inserts are routed to the right partition automatically.
  5. Queries with the key in WHERE are pruned at planning or execution time.
  6. Automate creating future partitions and dropping old ones (for example with pg_partman).

Example

CREATE TABLE orders (
  id BIGINT, customer_id BIGINT, created_at TIMESTAMPTZ NOT NULL, total NUMERIC,
  PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

CREATE TABLE orders_2026_10 PARTITION OF orders
  FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
CREATE TABLE orders_2026_11 PARTITION OF orders
  FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');

-- Only scans orders_2026_11
EXPLAIN SELECT SUM(total) FROM orders WHERE created_at >= '2026-11-01';

-- Retention: instant instead of a huge DELETE
ALTER TABLE orders DETACH PARTITION orders_2024_01;
DROP TABLE orders_2024_01;

Common mistakes

  • Partitioning by a column queries rarely filter on.
  • Creating thousands of tiny partitions.
  • Expecting partitioning to scale beyond one server.
  • Forgetting to pre-create future partitions, causing insert failures without a default partition.

How to answer in the interview

"Partitioning divides a large table into smaller physical partitions while it still appears as one table, usually within one database server. Horizontal partitioning splits rows, by range such as month, by list such as region, or by hash for an even spread; vertical partitioning moves large or rarely used columns to another table. The benefits are partition pruning, so queries filtering on the key scan only relevant partitions, smaller indexes, and easy maintenance, such as dropping an old month instead of deleting millions of rows. The key must match common query filters, otherwise every query scans all partitions."

Likely follow-up questions

  • How would you partition a 2-billion-row orders table? Range by month on created_at, possibly hash sub-partitions, with automated creation and retention.
  • What is partition pruning? The planner skipping partitions that cannot contain matching rows.
  • Does partitioning replace indexing? No; each partition still needs indexes for its queries.
