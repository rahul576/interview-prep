What is an SBOM, and why are artifact provenance and signing important?

Artifacts & Code Quality · concept · levels mid, senior

In one line

An SBOM lists every component and version in an artifact (SPDX/CycloneDX, generated with tools like Syft), provenance records where, how and from which source it was built (SLSA attestations), and signing with cosign/Sigstore proves integrity and origin; admission policies verify all of it before deploy.

Detailed explanation

Modern applications are mostly third-party code, built by automated pipelines, and pushed through registries. Each step is a place where something can be swapped or poisoned. These three practices make the artifact transparent and verifiable.

SBOM (software bill of materials): a machine-readable inventory of application dependencies (including transitive ones), OS packages in the image, versions, licences and hashes. Formats are SPDX and CycloneDX; Syft, Trivy, the Docker BuildKit SBOM attestation or language build plugins generate them in CI. The SBOM answers "do we ship the vulnerable version?" instantly and supports licence compliance and customer or regulatory requests, which are increasingly common (for example US federal procurement rules and the EU Cyber Resilience Act).

Provenance: a signed statement, usually an in-toto attestation following the SLSA provenance format, saying which source repository and commit, which build platform and workflow, and which parameters produced the artifact digest. It defends against a tampered build or someone pushing an image built on a laptop.

Signing: cosign signs the image digest; in keyless mode Sigstore issues a short-lived certificate for the CI job's OIDC identity and logs the signature in the Rekor transparency log. Verifiers check not just "signed", but "signed by our release workflow".

Enforcement: in Kubernetes, Kyverno verifyImages, Sigstore policy-controller, or Gatekeeper with external data, rejects images without a valid signature or required attestations.

Storing SBOMs where they stay useful: attach them to the image in the registry as OCI attestations (they travel with the artifact) and ingest them into Dependency-Track or a similar platform for continuous vulnerability matching.

How it works

  1. Build image from a tagged commit on a hosted runner.
  2. Generate SBOM; push image; capture digest.
  3. Sign digest; attach SBOM and provenance as attestations.
  4. Upload SBOM to Dependency-Track.
  5. Deploy: admission policy verifies signer identity and attestations.

Example

apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: { name: verify-signed-images }
spec:
  validationFailureAction: Enforce
  rules:
  - name: check-signature
    match: { any: [ { resources: { kinds: ["Pod"] } } ] }
    verifyImages:
    - imageReferences: ["ghcr.io/acme/*"]
      attestors:
      - entries:
        - keyless:
            subject: "https://github.com/acme/*/.github/workflows/release.yml@refs/heads/main"
            issuer: "https://token.actions.githubusercontent.com"

Common mistakes

  • Generating SBOMs as a checkbox and discarding them.
  • SBOMs from source only, missing OS packages in the image.
  • Signing mutable tags rather than digests.
  • Verification that accepts any valid Sigstore signature, from anyone.

How to answer in the interview

"An SBOM is an inventory of every component and version inside an artifact, including transitive dependencies and OS packages, in SPDX or CycloneDX, generated in CI with something like Syft. It lets us answer instantly whether we ship a vulnerable component. Provenance describes where and how the artifact was built, which commit and which pipeline, as a signed SLSA attestation. Signing with cosign and Sigstore proves the image came from our pipeline and wasn't altered. In Kubernetes, Kyverno or the Sigstore policy controller rejects images that aren't signed by our release workflow. I store SBOMs as registry attestations and in Dependency-Track."

Likely follow-up questions

  • Where to store SBOMs? As OCI attestations next to the image and in Dependency-Track for continuous analysis.
  • Does an SBOM prove security? No, it is an inventory; it needs vulnerability matching and action.
  • What is VEX? A statement that a listed vulnerability does or does not affect the product, reducing noise.
