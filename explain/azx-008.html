How does high availability work for Azure Database for PostgreSQL Flexible Server?

Azure · concept · levels mid, senior

In one line

Flexible Server HA runs a hot standby (in another zone or the same zone) with synchronous replication, and fails over automatically in about one to two minutes behind the same endpoint; read replicas (asynchronous, optionally cross-region) handle read scaling and DR, and backups with PITR and geo-redundant backup protect data.

Detailed explanation

Azure Database for PostgreSQL Flexible Server offers two HA modes:

  • Zone-redundant HA: the standby server runs in a different availability zone from the primary, protecting against a zone outage. This is the recommended production setting where zones exist.
  • Same-zone HA: the standby is in the same zone, with slightly lower write latency, protecting against server and storage failures but not a zone failure.

In both modes, the primary replicates its write-ahead log synchronously to the standby: a transaction is acknowledged only after it is durably written on both sides, so committed transactions are not lost on failover (RPO zero). This adds some write latency, especially across zones.

When Azure detects the primary or its zone is unhealthy, it performs an automatic failover: the standby is promoted and the same server name/DNS endpoint points to it. Failover typically takes around 60 to 120 seconds. You can also trigger a planned failover to test. After failover a new standby is created automatically. Note that HA increases cost (you pay for the standby) and the standby cannot serve reads.

Read replicas use asynchronous streaming replication, so they may lag. They offload read-heavy queries and reporting, and can be placed in another region for disaster recovery; in a regional disaster you promote a replica to a standalone server, optionally using virtual endpoints to keep connection strings stable.

Backups are automatic with point-in-time restore within the retention period (up to 35 days), and geo-redundant backup allows restoring in the paired region.

Application side: use retry logic with backoff for transient connection errors, short DNS caching, connection pooling (the built-in PgBouncer), idempotent writes, and reasonable connection timeouts so failover is barely noticed.

How it works

  1. Enable zone-redundant HA; standby provisioned in another zone.
  2. Writes commit on primary and standby synchronously.
  3. Health monitoring detects primary failure.
  4. Standby is promoted; DNS endpoint switches.
  5. Clients reconnect with retries; a new standby is built.
  6. Read replicas and geo-backups cover regional DR.

Example

az postgres flexible-server create -g rg-db -n pg-orders --location westeurope \
  --tier GeneralPurpose --sku-name Standard_D4ds_v5 --version 16 \
  --high-availability ZoneRedundant --zone 1 --standby-zone 2 \
  --geo-redundant-backup Enabled --backup-retention 35
az postgres flexible-server replica create -g rg-db-neu \
  --replica-name pg-orders-neu --source-server <pg-orders-resource-id> --location northeurope
az postgres flexible-server restart -g rg-db -n pg-orders --failover Planned   # test failover

Common mistakes

  • No retry logic, so a one-minute failover becomes user-visible errors.
  • Assuming read replicas are synchronous and fully up to date.
  • Using same-zone HA and expecting zone-failure protection.
  • Never testing failover.
  • Long-lived connections with no reconnect handling or cached IPs.

How to answer in the interview

"Flexible Server supports high availability with a hot standby. In zone-redundant mode the standby is in a different availability zone, while same-zone mode keeps it in the same zone for lower latency. Writes are replicated synchronously to the standby, so committed transactions are not lost, and if the primary or its zone fails Azure fails over automatically, usually within one to two minutes, keeping the same endpoint. Applications need retry logic and connection pooling for that brief interruption. Read replicas use asynchronous replication for read scaling and can be in another region for DR, where they can be promoted. Backups give point-in-time restore, and geo-redundant backup lets me restore in the paired region."

Likely follow-up questions

  • What do applications need so a failover is barely noticed? Retries with backoff, connection pooling, short timeouts and idempotent operations.
  • Can the HA standby serve reads? No; use read replicas for that.
  • How do you measure replica lag? The replication lag metric in Azure Monitor or pg_stat_replication.
