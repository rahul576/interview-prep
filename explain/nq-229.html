What is the Strangler Fig pattern, and how does it support incremental monolith migration?

Microservices · concept · levels mid, senior

In one line

The Strangler Fig pattern migrates a monolith incrementally: a routing layer sits in front of it, one capability at a time is rebuilt as a new service and traffic for it is switched over, until the old code can be retired.

Detailed explanation

The name comes from the strangler fig, which grows around a host tree and eventually replaces it. A big-bang rewrite freezes features for months, has to match years of hidden behaviour and usually ships late; the Strangler Fig avoids that by keeping the system in production the whole time.

First you put a facade in front of the monolith: an API gateway, reverse proxy (NGINX, Envoy) or Spring Cloud Gateway. At the start it routes everything to the monolith. Then you pick one capability with clear boundaries and real value, such as notifications, product catalogue or invoicing, build it as a new service, and change the routes for its endpoints. Everything else still goes to the monolith. Once the new service is stable, you delete the corresponding code from the monolith and repeat.

Risk is low because both systems run side by side: if the new service misbehaves you route back. You can also release gradually with a percentage of traffic, canary or feature flags, or run the new service in shadow mode and compare its responses with the monolith's before switching.

The hard part is data. The monolith usually has one shared database. The new service should own its data, so during the transition you keep both sides in sync, often with change data capture (Debezium) from the monolith tables, or by having the monolith publish events. An anti-corruption layer translates the monolith's model into the new service's clean domain model so the legacy design does not leak in.

How it works

  1. Put a gateway or proxy in front of the monolith; route 100% to it.
  2. Identify bounded contexts and choose a first, loosely coupled capability.
  3. Build the new service with its own database; sync data via CDC or events.
  4. Shadow traffic or canary a small percentage; compare results.
  5. Switch the routes fully; keep the rollback route ready.
  6. Remove the dead code and tables from the monolith; repeat.

Example

spring:
  cloud:
    gateway:
      routes:
        - id: notifications-new
          uri: http://notification-service
          predicates: [ Path=/api/notifications/** ]
        - id: legacy
          uri: http://monolith:8080
          predicates: [ Path=/** ]

Common mistakes

  • Extracting the most tangled module first (orders, billing core) instead of an easy win.
  • Sharing the monolith's database tables with the new service indefinitely.
  • Never deleting the old code, so you maintain two implementations.
  • Migrating without observability, so regressions are invisible.

How to answer in the interview

"Strangler Fig means replacing a monolith piece by piece instead of rewriting it. I put a gateway in front of the monolith, then extract one capability, say notifications, as a new service and route only its endpoints there, while everything else still hits the monolith. I can canary or shadow traffic and route back if something breaks, so risk stays low. Once it is stable I delete the old code and move to the next capability. The tricky part is data: the new service gets its own schema, kept in sync with CDC during the transition, and an anti-corruption layer keeps the legacy model out of the new design."

Likely follow-up questions

  • Which capability would you extract first, and why? A low-coupling, high-value one like notifications or catalogue, to prove the platform and deliver quick wins.
  • How do you handle writes during the transition? One side owns writes for an entity at a time; the other is synced via CDC or events.
  • How do you know a capability is fully migrated? No traffic reaches the old code paths in monitoring, then you remove them.
