What is Helm, and what are charts, values and releases?

GitOps & Helm · concept · levels entry

In one line

Helm is the package manager for Kubernetes: a chart is a package of templated manifests plus Chart.yaml metadata; values (defaults in values.yaml, overridden per environment with -f or --set) fill the templates; installing a chart creates a release whose every upgrade is a numbered revision you can roll back.

Detailed explanation

Deploying an app to Kubernetes means several manifests (Deployment, Service, Ingress, ConfigMap, HPA), and each environment needs slightly different values. Copying YAML per environment drifts quickly. Helm solves packaging and parameterisation.

A chart is a directory with:

  • Chart.yaml: name, chart version, appVersion and dependencies (for example a Redis subchart).
  • templates/: Kubernetes manifests written as Go templates, like replicas: {{ .Values.replicaCount }}, with helpers in _helpers.tpl.
  • values.yaml: the default values.
  • Optionally values.schema.json for validation and templates/tests/ for helm test.

Values are how you configure a chart per environment. You pass your own files (-f values-prod.yaml) or single overrides (--set image.tag=1.4.2); later sources override earlier ones. Typical values are replicas, image tag, resources, ingress host and feature toggles.

A release is an installed instance of a chart in a namespace with a name, for example orders in namespace shop. The same chart can be installed many times under different release names. Each helm upgrade creates a new revision; Helm stores release history as Secrets in the namespace, so helm rollback orders 3 returns to revision 3. helm history lists revisions and helm list shows releases.

Charts are shared through chart repositories (an index.yaml over HTTP) or, increasingly, OCI registries (helm push / oci:// references), the same registries that store images. Artifact Hub is the public index.

How it works

  1. helm create orders scaffolds a chart; edit templates and values.
  2. helm lint and helm template check and render it locally.
  3. helm upgrade --install orders ./orders -n shop -f values-prod.yaml installs or upgrades.
  4. Helm renders templates with values, applies manifests, records a revision.
  5. helm rollback if something goes wrong; helm uninstall removes it.

Example

# values-prod.yaml
replicaCount: 4
image:
  repository: registry.example.com/orders
  tag: "1.4.2"
resources:
  requests: { cpu: 250m, memory: 512Mi }
# templates/deployment.yaml (excerpt)
spec:
  replicas: {{ .Values.replicaCount }}
  template:
    spec:
      containers:
        - name: orders
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
helm upgrade --install orders ./orders -n shop -f values-prod.yaml --atomic --wait
helm history orders -n shop
helm rollback orders 3 -n shop
helm push orders-0.7.0.tgz oci://registry.example.com/charts

Common mistakes

  • Confusing chart version (the package) with appVersion (the app inside).
  • Long chains of --set flags instead of versioned values files.
  • Assuming helm rollback reverts database changes; it only reverts Kubernetes objects.
  • Not previewing changes before upgrade.

How to answer in the interview

"Helm is the package manager for Kubernetes. A chart packages templated Kubernetes manifests, like the deployment, service and ingress, plus a Chart.yaml with metadata and dependencies. The templates are filled in from values: the chart has defaults in values.yaml, and I override them per environment with my own values file or --set, for example replicas, image tag or resources. Installing a chart creates a release, a named instance in a namespace, and each upgrade creates a new revision, so helm rollback returns to a previous one. I mostly use helm upgrade --install with --atomic, and charts are shared via chart repositories or OCI registries."

Likely follow-up questions

  • How do you preview an upgrade? helm diff upgrade plugin, helm template, or --dry-run=server.
  • What does --atomic do? Rolls back automatically if the upgrade fails and implies --wait; Helm 4 names this flag --rollback-on-failure.
  • Where does Helm store release state? Secrets in the release namespace (Helm 3).
