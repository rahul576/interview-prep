What does Spring Boot Actuator provide, and how do you secure it?

Spring Boot · concept · levels mid, senior

In one line

Actuator adds production endpoints such as health (with liveness/readiness groups for Kubernetes), metrics and a Prometheus endpoint via Micrometer, info, loggers and more; secure it by exposing only what is needed, using a separate management port, Spring Security, and never exposing env, heapdump or similar publicly.

Detailed explanation

Adding spring-boot-starter-actuator provides operational endpoints under /actuator. Important ones:

  • health: aggregated status from indicators for the database, disk space, Redis, Kafka, mail and custom checks.
  • Health groups: liveness and readiness are enabled automatically on Kubernetes and map to /actuator/health/liveness and /actuator/health/readiness for probes.
  • metrics and prometheus: Micrometer meters (JVM, HTTP server requests, Hikari pool, custom) exposed for scraping with micrometer-registry-prometheus.
  • info: build and Git information, loggers (change log levels at runtime), threaddump, heapdump, env, configprops, beans, mappings, conditions, startup, scheduledtasks.

By default only health is exposed over HTTP (Boot 2.5+ hides others). Several endpoints are dangerous: heapdump contains every secret in memory, env and configprops show configuration (Boot 3 masks values by default, controlled with show-values), and loggers POST or shutdown change behaviour.

Securing it:

  1. Expose minimally: management.endpoints.web.exposure.include=health,info,prometheus.
  2. Separate port: management.server.port=8081, reachable only inside the cluster, not through ingress.
  3. Spring Security: a dedicated filter chain with EndpointRequest matchers, allowing health probes and requiring an ops role for the rest.
  4. Health details: show-details: when-authorized so anonymous callers see only UP/DOWN.
  5. Keep sensitive endpoints disabled in production unless required, and audit their use.

How it works

  1. Actuator auto-configures endpoints and health indicators from the classpath.
  2. Exposure settings decide which endpoints are reachable over HTTP or JMX.
  3. Kubernetes probes call the liveness and readiness groups.
  4. Prometheus scrapes the metrics endpoint.
  5. Security rules guard everything except what probes and scrapers need.

Example

management:
  server:
    port: 8081
  endpoints:
    web:
      exposure:
        include: health,info,prometheus
  endpoint:
    health:
      show-details: when-authorized
      probes:
        enabled: true
      group:
        readiness:
          include: readinessState,db,redis
@Bean
@Order(1)
SecurityFilterChain actuator(HttpSecurity http) throws Exception {
    http.securityMatcher(EndpointRequest.toAnyEndpoint())
        .authorizeHttpRequests(a -> a
            .requestMatchers(EndpointRequest.to(HealthEndpoint.class, InfoEndpoint.class)).permitAll()
            .anyRequest().hasRole("OPS"))
        .httpBasic(Customizer.withDefaults());
    return http.build();
}

Common mistakes

  • exposure.include: "*" in production behind a public ingress.
  • Including the database in the liveness probe, so a DB outage restarts all pods.
  • Leaving heapdump reachable.
  • Showing full health details to anonymous users.

How to answer in the interview

"Actuator adds production endpoints: health with indicators for the database and other dependencies, liveness and readiness groups that map to Kubernetes probes, metrics and a Prometheus endpoint through Micrometer, info, loggers to change log levels at runtime, thread dumps and more. To secure it I expose only what's needed, typically health, info and prometheus, put management on a separate port that isn't routed from the internet, protect anything else with Spring Security and an ops role, and show health details only when authorised. I never expose env or heapdump publicly because they leak secrets."

Likely follow-up questions

  • Which health indicators belong in readiness but not liveness? External dependencies like the DB or broker; liveness should only reflect the app itself.
  • How do you add a custom health check? Implement HealthIndicator and add it to a group.
  • Can you change log levels at runtime? Yes, POST to /actuator/loggers/{name}, secured.
