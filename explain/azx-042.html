How do templates work in Azure Pipelines, and how do extends templates enforce governance?

Azure DevOps & Pipelines · concept · levels mid, senior

In one line

Templates package reusable steps, jobs, stages and variables with typed parameters, are expanded at compile time using ${{ }} expressions, and usually live in a central repo referenced as a repository resource; an extends template controls the whole pipeline structure, and a required template check on production resources guarantees only compliant pipelines deploy.

Detailed explanation

Without templates, every team copies YAML and drifts. Templates fix that:

  • Step templates (a list of steps, e.g. "build and test .NET"), job templates, stage templates, and variable templates (shared values).
  • Parameters are typed: string, number, boolean, object, step, stepList, job, stage and more, with defaults and allowed values. That's safer than variables because invalid input fails at compile time.
  • Central templates are referenced via resources.repositories and pinned to a ref (a tag or branch), so a platform team can release new versions deliberately: - template: dotnet/build.yml@templates.

Compile time: before the run starts, Azure DevOps expands all templates into one final YAML. Template expressions ${{ }} (with if, each, else) can include or exclude whole sections, loop over parameter lists, and insert values. Runtime variables do not exist yet at this point.

Extends templates invert control. The team's pipeline contains only extends: template: secure-pipeline.yml@templates plus parameters (for example the build steps as a stepList). The central template defines stages and always injects mandatory steps: credential scanning, SBOM generation, dependency scanning, artifact signing. It can also inspect and reject the steps passed in, for example failing if a step is an inline script in the deploy stage, or allowing only approved task types.

Enforcement: on the production environment, service connection or agent pool, add a Required template check pointing to secure-pipeline.yml@templates at a specific ref. Any pipeline not extending it cannot use the resource, so governance does not depend on goodwill.

How it works

  1. Platform team publishes templates in a pipeline-templates repo with versions.
  2. Teams reference the repo as a resource with a pinned ref.
  3. Team pipeline extends the secure template and passes parameters.
  4. Compile time expands templates and evaluates ${{ }} logic.
  5. Required template check validates extension before using protected resources.

Example

# team pipeline
resources:
  repositories:
  - repository: templates
    type: git
    name: Platform/pipeline-templates
    ref: refs/tags/v3.2
extends:
  template: secure-pipeline.yml@templates
  parameters:
    buildSteps:
    - task: DotNetCoreCLI@2
      inputs: { command: build, arguments: '-c Release' }
# secure-pipeline.yml (excerpt)
parameters:
- name: buildSteps
  type: stepList
  default: []
stages:
- stage: Build
  jobs:
  - job: build
    steps:
    - ${{ each step in parameters.buildSteps }}:
      - ${{ each pair in step }}:
          ${{ if eq(pair.key, 'script') }}:
            'Inline scripts are not allowed': error     # fails compilation
          ${{ else }}:
            ${{ pair.key }}: ${{ pair.value }}
    - task: MicrosoftSecurityDevOps@1   # always injected scanning

Common mistakes

  • Referencing templates from a moving branch with no version pinning.
  • Using runtime variables inside ${{ if }} and wondering why they are empty.
  • Extends template that teams can bypass because no required template check exists.
  • Overly generic templates with dozens of parameters nobody understands.

How to answer in the interview

"Templates let me define reusable steps, jobs, stages and variables in a central repo, referenced as a repository resource pinned to a tag. They take typed parameters with defaults and allowed values, and they're expanded at compile time, so ${{ }} expressions can include or exclude whole sections. An extends template goes further: the team pipeline only extends a central template and passes parameters, while the template controls the structure and always injects security scanning, and can reject things like inline scripts. With a required template check on production environments and service connections, only pipelines built on that template can deploy."

Likely follow-up questions

  • Template vs macro vs runtime expressions? ${{ }} at compile time, $( ) before a task runs, $[ ] at runtime for conditions and variables.
  • Why pin template versions? So template changes don't break every pipeline at once.
  • Can teams override injected steps? Not if the extends template controls structure and the check enforces it.
