A server says the disk is full, but du does not show where the space went. What is happening?

Linux · scenario · levels mid, senior

In one line

The space is usually held by a deleted file that a process still has open, invisible to du but counted by df; find it with lsof +L1, then restart the process or truncate the file via /proc, fix log rotation, and also check inode exhaustion with df -i.

Detailed explanation

df asks the filesystem how many blocks are allocated; du walks directory entries and adds up file sizes. Normally they agree. A file's blocks are only freed when its link count reaches zero and no process holds it open. If someone runs rm on a 40 GB log while the application keeps writing to it, the directory entry disappears, so du cannot see it, but the inode and data stay allocated until the process closes the file descriptor. df keeps showing the disk as full.

lsof +L1 lists open files with a link count below one, that is deleted but open; lsof | grep '(deleted)' works too. The output shows the process, PID, file descriptor number and size. The clean fix is to restart or reload the process so it reopens its logs. If you cannot restart immediately, truncate through the proc file descriptor: : > /proc/<pid>/fd/<fd> frees the space at once.

Prevention is proper log rotation: logrotate with a postrotate signal (such as kill -USR1 or systemctl reload) so the app reopens files, or copytruncate for apps that cannot reopen (accepting that a few lines may be lost).

Other causes of "full but no files": inode exhaustion from millions of tiny files (df -i at 100% while df -h shows space), reserved blocks for root on ext4 (about 5% by default), files hidden under a mount point (written before a filesystem was mounted over the directory).

How it works

  1. df -h says full; du -shx / totals much less.
  2. lsof +L1 finds deleted-but-open files and their PIDs.
  3. Restart the process, or truncate via /proc/<pid>/fd/<n>.
  4. Check df -i for inodes.
  5. Fix logrotate so it does not recur.

Example

df -h /var
du -shx /var 2>/dev/null
sudo lsof +L1 | head
# java 2314 app 12w REG 259,1 42949672960 0 /var/log/app/app.log (deleted)
sudo sh -c ': > /proc/2314/fd/12'     # frees space immediately
df -i /var                            # inode check
# /etc/logrotate.d/app
/var/log/app/*.log {
  daily
  rotate 7
  compress
  postrotate
    systemctl reload app >/dev/null 2>&1 || true
  endscript
}

Common mistakes

  • Deleting a log with rm while the app is writing to it.
  • Rebooting the server instead of identifying the process.
  • Forgetting inodes and reserved blocks.
  • Using copytruncate where the app supports a reopen signal.

How to answer in the interview

"The classic cause is a deleted file that a process still holds open, usually a big log someone removed with rm while the app keeps writing. The space is not freed until the file handle closes, and du cannot see it because the directory entry is gone. I find it with lsof +L1, then restart or reload the process, or truncate the file through its /proc file descriptor if I cannot restart. To prevent it, I use proper log rotation that signals the app to reopen logs, or copytruncate. I also check df -i for inode exhaustion, and files hidden under mount points."

Likely follow-up questions

  • How would you find the largest directories quickly on a huge filesystem? du -xh --max-depth=1 / | sort -h, or ncdu, staying on one filesystem with -x.
  • What are reserved blocks? Space ext4 keeps for root; tune2fs -m changes it.
  • How can files hide under a mount point? Data written to the directory before mounting stays underneath; bind-mount / elsewhere to see it.
