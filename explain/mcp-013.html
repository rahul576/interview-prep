What are sampling and roots in MCP, and what is their current status?

MCP Servers · concept · levels mid, senior

In one line

Sampling lets a server request a completion from the client's model (keeping model choice, cost and approval with the host), and roots let the client tell the server which locations it may operate on; per the 2026-07-28 revision both are deprecated (with logging) but keep working for at least twelve months.

Detailed explanation

Sampling (sampling/createMessage) was a client feature from the first revision. A server that needed language-model help, say to summarise a document it fetched, could ask the host's model through the client rather than shipping its own API key. The request carries messages, a system prompt, model preferences (hints and cost/speed/intelligence priorities) and token limits. The host stays in control: it chooses the actual model, can show the request to the user for approval, can edit or reject it, and bears the cost under the user's account.

Roots (roots/list, with notifications/roots/list_changed) let the client tell the server which locations, usually filesystem directories or URIs, it should operate within, for example the folder of the currently open project. They are a coordination hint for scoping, not a security sandbox: a server could ignore them, so real enforcement still needs OS or container controls.

Both features saw limited adoption in hosts, and both require the server to send requests back to the client, which complicates the protocol and conflicts with a stateless, horizontally scaled design. According to the question's reference material, the 2026-07-28 revision marks sampling, roots and logging as deprecated. Under the new feature lifecycle, deprecated features continue to function for at least twelve months before removal, giving implementers time to migrate.

Alternatives for new designs: pass locations as explicit tool parameters (validated server-side against an allowlist), and make server-side model calls with the server's own credentials and budget when it needs model help, or return data and let the host's agent do the reasoning.

How it works

  1. (Legacy) Client advertises sampling and/or roots capabilities.
  2. Sampling: server sends sampling/createMessage; host optionally asks the user, calls its model and returns the completion.
  3. Roots: server calls roots/list; client returns URIs like file:///home/dev/project.
  4. Migration: replace sampling with server-side model calls or returning raw data; replace roots with explicit, validated parameters.

Example

# Before: server relied on sampling
summary = await ctx.session.create_message(messages=[...], max_tokens=300)

# After: explicit parameter plus server-side model call (own key, own budget)
@mcp.tool()
def summarise_repo_docs(path: str) -> str:
    """Summarise markdown docs under `path` (must be inside an allowed workspace)."""
    safe = ensure_within(path, ALLOWED_WORKSPACES)
    text = collect_markdown(safe)
    return llm_client.summarise(text, max_tokens=300)

Common mistakes

  • Treating roots as a security boundary.
  • Building new servers that depend on sampling despite its deprecation and spotty host support.
  • Assuming deprecated means "stops working now"; it continues during the deprecation window.
  • Moving model calls server-side without budgets or data-handling review.

How to answer in the interview

"Sampling lets a server ask the host's model for a completion through the client, so the server needs no API key and the host keeps control of model choice, cost and user approval. Roots let the client tell the server which locations, like the open project folder, it should work within. Both had limited host adoption and require servers to send requests back to clients, which complicates the protocol. In the 2026-07-28 revision they're deprecated, along with logging, but under the feature lifecycle they keep working for at least twelve months. For new designs I'd use explicit, validated tool parameters for locations and server-side model calls instead."

Likely follow-up questions

  • How would you redesign a server that relied on sampling? Return the raw data for the host's agent to reason over, or call a model server-side with its own budget.
  • Are roots enforced? No; enforce scoping with OS permissions, containers or server-side path checks.
  • Who paid for sampling? The host or user, through their model access.
