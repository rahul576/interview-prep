A node shows NotReady. How do you investigate, and what happens to its pods?

Kubernetes · scenario · levels mid, senior

In one line

NotReady means the node controller stopped receiving healthy status or Lease updates from the kubelet; investigate the kubelet, container runtime, network and resource pressure, and expect pods to be evicted after about 300 seconds via taint-based eviction, then cordon, drain or replace the node.

Detailed explanation

The kubelet reports node health by updating a Lease object in kube-node-lease (every 10 seconds) and the node status. If the node controller sees no update within the grace period (40 seconds by default), it sets the Ready condition to Unknown (NotReady). If the kubelet does report but says it is unhealthy, the condition is False, often with a reason such as container runtime not ready or the CNI not initialised. So NotReady can mean "kubelet cannot talk to us" or "kubelet talks but is sick".

Typical causes: the kubelet or containerd crashed or was OOM-killed; the disk is full (DiskPressure, images and logs); memory or PID exhaustion; an expired kubelet certificate; the CNI plugin is broken; or a network or security group change cut the node off from the API server. Cloud issues such as a failing VM or a hung kernel also show up this way.

Meanwhile the node gets taints node.kubernetes.io/unreachable or not-ready with effect NoExecute. Pods get a default toleration of 300 seconds for these taints, so after five minutes they are evicted and controllers recreate them elsewhere. DaemonSet pods tolerate these taints and stay. StatefulSet pods are a special case because their replacement waits until the old pod is confirmed gone. Pods on an unreachable node may actually still be running and serving traffic if only the node-to-API link is broken.

How it works

  1. kubectl describe node: conditions, last heartbeat, events, taints.
  2. Access the node (SSH, serial console, or kubectl debug node/... if the kubelet still works).
  3. systemctl status kubelet containerd, journalctl -u kubelet.
  4. Check df -h, memory, PIDs, kubelet certificate and connectivity to the API server.
  5. Fix the cause, or cordon and drain, then replace the node.
  6. Confirm workloads rescheduled and investigate why the node failed.

Example

kubectl describe node ip-10-0-3-17 | sed -n '/Conditions/,/Addresses/p'
kubectl get lease -n kube-node-lease ip-10-0-3-17 -o jsonpath='{.spec.renewTime}'

# on the node
sudo systemctl status kubelet containerd
sudo journalctl -u kubelet --since "30 min ago" | tail -50
df -h /var/lib/containerd /var/log
curl -sk https://<api-server>:6443/healthz

kubectl cordon ip-10-0-3-17
kubectl drain ip-10-0-3-17 --ignore-daemonsets --delete-emptydir-data

Common mistakes

  • Assuming pods move immediately; the default delay is five minutes.
  • Draining before checking whether it is a cluster-wide network problem.
  • Ignoring disk pressure from images and logs as a root cause.
  • Rebooting without collecting logs, so the cause recurs.

How to answer in the interview

"NotReady means the node controller hasn't had a healthy status or lease from the kubelet. I start with kubectl describe node to see conditions like DiskPressure or MemoryPressure and when it last reported. Then on the node I check the kubelet and container runtime with systemctl and journalctl, disk space, the kubelet certificate and connectivity to the API server, because network or security group changes are common. Meanwhile the node is tainted and, after the default 300 seconds, pods are evicted and recreated elsewhere if a controller owns them. If I can't fix it quickly, I cordon, drain and replace it."

Likely follow-up questions

  • Why might pods on a NotReady node still serve traffic? Only the kubelet-to-API link may be broken; containers keep running and may still get traffic.
  • How do you speed up eviction? Set lower tolerationSeconds for unreachable/not-ready on critical pods.
  • What is node auto-repair? Managed services or node problem detector with automation replace unhealthy nodes.
