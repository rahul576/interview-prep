What happens to running containers when the Docker daemon is restarted or upgraded?

Docker · concept · levels senior

In one line

By default, stopping or upgrading dockerd stops all its containers, and those with restart policies come back when it restarts; with live-restore enabled, containers keep running because each is supervised by a containerd shim, and dockerd reattaches on start. In clusters, drain the node before upgrading.

Detailed explanation

Docker is not one process. dockerd handles the API, networking and images; it delegates container lifecycle to containerd, which starts each container through runc and leaves a small containerd-shim process as its parent. The shim keeps stdio open and reports the exit code, so the container process does not depend on dockerd being alive.

Without extra configuration, when dockerd stops it shuts down its containers. When it starts again, containers with --restart always or unless-stopped (and on-failure ones in some cases) are restarted; the rest stay stopped. That is a short outage for everything on the host.

With "live-restore": true in daemon.json, dockerd leaves containers running while it is stopped, restarted or upgraded, and reconnects to them when it comes back. Limitations matter: while the daemon is down you cannot start, stop or inspect containers, published ports may not work during the gap when the userland proxy is used, logs can fill the buffer and block if the outage is long, and live-restore is not supported with Swarm mode, because Swarm manages orchestration and networking state that must stay consistent. Live restore also only supports patch-level upgrades reliably; major upgrades can require container restarts.

In a cluster (Kubernetes with containerd, ECS, Swarm), the safest pattern is: cordon and drain the node, let workloads move, upgrade the runtime, verify and uncordon, one node at a time.

How it works

  1. Enable live-restore and reload config (systemctl reload docker or SIGHUP).
  2. Upgrade or restart dockerd; containers keep running under their shims.
  3. dockerd starts, reads its state and reconnects to running containers.
  4. Without live-restore: containers stop, then restart policies decide what comes back.
  5. In clusters: drain, upgrade, verify, uncordon.

Example

echo '{ "live-restore": true }' | sudo tee /etc/docker/daemon.json
sudo systemctl reload docker
docker info --format '{{.LiveRestoreEnabled}}'   # true
ps -ef | grep containerd-shim                    # one shim per container
kubectl cordon node-7 && kubectl drain node-7 --ignore-daemonsets --delete-emptydir-data
# upgrade container runtime, reboot if needed
kubectl uncordon node-7

Common mistakes

  • Assuming restart policies mean zero downtime; there is still a gap.
  • Enabling live-restore on Swarm nodes and expecting it to work.
  • Upgrading all nodes in a cluster at once.
  • Forgetting that long daemon outages can block container logging.

How to answer in the interview

"By default, when the Docker daemon stops, its containers stop too, and when it comes back, containers with restart policies like always or unless-stopped are started again, so you get a brief outage. If you enable live-restore in daemon.json, containers keep running during the restart or upgrade, because each one is parented by a containerd shim rather than dockerd, and dockerd reattaches when it starts. It has limits: no Swarm support, mainly patch upgrades, and you can't manage containers while dockerd is down. In a cluster I wouldn't rely on it; I'd drain the node, upgrade, check and return it to service one node at a time."

Likely follow-up questions

  • Why no live-restore with Swarm? Swarm's orchestration and overlay networking state depends on the daemon and cluster coordination.
  • What is the shim's job? Keep the container running independently of dockerd, hold stdio and report exit status.
  • Does restarting containerd affect containers? Shims keep running containers alive; containerd reconnects to them on restart.
