How do you copy files between a container and the host?

Docker · concept · levels entry

In one line

docker cp copies files or directories between a container and the host in both directions, even for stopped containers; for regular data exchange use volumes or bind mounts instead.

Detailed explanation

docker cp works through the Docker API, so it needs neither a shell nor any tools inside the container. The syntax mirrors cp: docker cp <container>:<path> <host-path> copies out, and docker cp <host-path> <container>:<path> copies in. Directories are copied recursively, and - can be used to stream a tar archive through stdin or stdout. Because it reads the container's filesystem rather than running a process, it also works on a stopped or crashed container, which makes it a great way to retrieve a core dump, a log file or a generated report after a failure.

It is, however, a debugging and one-off tool. Files copied into a container land in its writable layer. They disappear as soon as the container is removed and recreated from the image, they are invisible to other replicas, and nobody can reproduce how the container got into that state. Changes made this way also drift away from version control. For data that is exchanged regularly, such as uploads, configuration, databases and logs, use named volumes or bind mounts, and for configuration use mounted config files, Docker configs or Kubernetes ConfigMaps. To change what is inside an image, change the Dockerfile and rebuild.

Some details: copied files keep the host ownership unless you use -a (archive mode) to preserve UID and GID, and files copied into a read-only filesystem fail. In Kubernetes, the equivalent is kubectl cp, which needs tar in the container.

How it works

  1. The CLI calls the archive endpoint of the Docker API.
  2. dockerd reads or writes the container's merged filesystem.
  3. Data is streamed as a tar archive between client and daemon.
  4. The CLI unpacks it at the destination.

Example

# Pull a log out of a crashed container
docker cp web:/var/log/nginx/error.log ./error.log

# Put a file in (temporary debugging only)
docker cp ./debug.conf web:/etc/nginx/conf.d/debug.conf

# Copy a whole directory and keep ownership
docker cp -a worker:/app/reports ./reports

Common mistakes

  • Hot-fixing production by copying files into a running container.
  • Expecting copied files to survive a docker compose up that recreates the container.
  • Using docker cp in scripts as the normal way to deliver configuration.
  • Forgetting that copied files may have the wrong owner for a non-root app.

How to answer in the interview

"docker cp copies files between a container and the host in either direction, for example docker cp web:/var/log/nginx/error.log . to get a log out, or docker cp config.yml web:/app/ to put something in. It works on stopped containers too, which is very useful for getting files out of a container that crashed. But it's a debugging tool: anything copied in lives in the writable layer and is lost when the container is recreated from the image. For regular data I use volumes or bind mounts, and for real changes I update the Dockerfile and rebuild."

Likely follow-up questions

  • Why not fix production by copying files in? The change is untracked, lost on recreation and not on other replicas.
  • Does docker cp need a shell in the container? No, it uses the Docker API.
  • Kubernetes equivalent? kubectl cp, which requires tar in the container.
