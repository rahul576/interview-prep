How do you secure SSH access to Linux servers?

Linux · concept · levels entry, mid

In one line

Use key-based authentication only, disable root login and passwords, keep port 22 off the internet behind a bastion, Session Manager or a zero-trust proxy, prefer short-lived SSH certificates via SSO and MFA, and audit everything, ideally needing SSH rarely at all.

Detailed explanation

SSH is one of the most attacked services on the internet, so harden both the daemon and the access model.

In /etc/ssh/sshd_config: PasswordAuthentication no and KbdInteractiveAuthentication no so only keys work; PermitRootLogin no, so people log in as themselves and use sudo, which leaves an audit trail; AllowGroups to restrict who may log in; modern key types such as Ed25519. Keep OpenSSH patched, since serious vulnerabilities do appear.

Network exposure matters more than any setting. Port 22 should not be open to 0.0.0.0/0. Access goes through a bastion host, or better through AWS Systems Manager Session Manager, Azure Bastion, GCP IAP TCP forwarding or a zero-trust access proxy (Teleport, Cloudflare Access, Tailscale), which need no inbound port, enforce identity and record sessions.

Static keys scattered across authorized_keys files are hard to rotate and revoke. For teams, an SSH certificate authority (OpenSSH CA, HashiCorp Vault, Teleport) issues short-lived certificates after SSO with MFA; servers trust the CA, not individual keys, and access expires automatically. fail2ban or similar blocks brute-force sources on anything still exposed. Logs (auth logs, auditd, session recordings) go to a central SIEM.

The best SSH is no SSH: immutable servers built from images and managed with config management or containers rarely need interactive access, so it becomes a break-glass path.

How it works

  1. Engineer authenticates to the access proxy or SSO with MFA.
  2. A short-lived certificate is issued or a session is brokered.
  3. The connection reaches the server without a public port 22.
  4. sshd accepts only key or certificate auth for allowed groups.
  5. Sessions and commands are logged centrally.

Example

# /etc/ssh/sshd_config.d/10-hardening.conf
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
AllowGroups ssh-users
TrustedUserCAKeys /etc/ssh/user_ca.pub
MaxAuthTries 3
sudo sshd -t && sudo systemctl reload ssh     # validate before reloading
aws ssm start-session --target i-0abc123def4567890

Common mistakes

  • Opening port 22 to the whole internet "temporarily".
  • Shared accounts or shared private keys.
  • Never removing keys of people who left.
  • Reloading sshd with a broken config and locking everyone out.

How to answer in the interview

"I allow only key-based authentication, disable passwords and direct root login, and people use sudo. Port 22 is not open to the internet: access goes through a bastion, or better Session Manager, Azure Bastion or a zero-trust proxy, which also record sessions. For bigger teams I prefer short-lived SSH certificates issued after SSO with MFA instead of distributing static keys, so access expires on its own. fail2ban blocks brute force on anything exposed and all access is logged centrally. Ideally servers are immutable and SSH is only a break-glass path."

Likely follow-up questions

  • How do you revoke access for an engineer who leaves? Disable their SSO account; with short-lived certificates access ends at expiry, otherwise remove keys everywhere via config management.
  • Why change the default port? It only reduces log noise; it is not real security.
  • How do you avoid locking yourself out? Test with sshd -t and keep an existing session open while testing a new one.
