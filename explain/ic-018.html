What are handlers in Ansible?

Configuration Management · concept · levels entry

In one line

Handlers are tasks that run only when notified by a task that reported changed, run once per play by default at the end, and are typically used to restart or reload a service after a configuration change.

Detailed explanation

Restarting a service on every playbook run is wasteful and causes needless downtime. Handlers solve this. A task such as template that writes nginx.conf includes notify: Reload nginx. If the template's output is identical to the file on the host, the task reports ok and nothing is notified. If the file changes, the task reports changed and the handler is queued.

Handlers are defined in a handlers: section of the play or in handlers/main.yml of a role. They are matched by name, or by a listen topic so several handlers can respond to one notification (for example listen: "restart web stack" triggering both nginx and php-fpm restarts). No matter how many tasks notify the same handler, it runs only once, and by default after all tasks in the play (or in the current section: pre_tasks, roles/tasks, post_tasks) have completed, in the order handlers are defined, not the order notified.

If a later task needs the restart to have already happened, for example a health check right after the config change, use ansible.builtin.meta: flush_handlers, which runs all pending handlers immediately.

An important edge case: if a task fails on a host after a handler was notified, by default the play stops for that host and the handler does not run, leaving a changed config without a reload. --force-handlers or force_handlers: true in the play makes notified handlers run anyway.

How it works

  1. Task runs and reports changed.
  2. Its notify queues the named handler (or listen topic).
  3. Duplicate notifications are collapsed.
  4. At the end of the section, or at flush_handlers, queued handlers run in definition order.
  5. Handlers not notified never run.

Example

- hosts: web
  become: true
  tasks:
    - name: Deploy nginx config
      ansible.builtin.template:
        src: nginx.conf.j2
        dest: /etc/nginx/nginx.conf
        validate: nginx -t -c %s
      notify: Reload nginx

    - name: Apply handlers now
      ansible.builtin.meta: flush_handlers

    - name: Health check
      ansible.builtin.uri:
        url: http://localhost/health

  handlers:
    - name: Reload nginx
      ansible.builtin.service:
        name: nginx
        state: reloaded

Common mistakes

  • Restarting services in normal tasks so they bounce every run.
  • Misspelling the handler name in notify (Ansible errors, but only when notified).
  • Expecting handlers to run in notification order.
  • Forgetting that a later failure skips pending handlers.

How to answer in the interview

"Handlers are tasks that run only when notified, and only if the notifying task actually reported changed. The classic case is a template task for nginx.conf with notify: reload nginx. The reload happens only when the config really changed, which keeps playbooks idempotent and avoids needless restarts. Even if several tasks notify it, a handler runs once, by default at the end of the play. If I need it earlier, say before a health check, I use meta: flush_handlers. And handlers can listen to a shared topic so one notify triggers several of them."

Likely follow-up questions

  • What happens to notified handlers if a later task fails? They're skipped for that host unless --force-handlers or force_handlers: true.
  • Reload or restart? Reload when the service supports it, to avoid dropping connections.
  • Can a handler notify another handler? Yes, handlers can notify other handlers.
