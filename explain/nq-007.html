What are sealed classes, and how do they restrict inheritance?

Modern Java (11-21) · concept · levels mid, senior

In one line

A sealed class or interface (standard since Java 17) lists exactly which types may extend it with permits; each permitted subclass must be final, sealed or non-sealed, giving a closed hierarchy the compiler can check for exhaustiveness.

Detailed explanation

Before Java 17 you had two choices: make a class final (no subclasses) or leave it open (anyone can extend it). Often the domain has a fixed set of variants, for example a shape is a circle, square or rectangle, or a payment is card, UPI or wallet. Sealed types express that middle ground.

public sealed class Shape permits Circle, Square, Rectangle {}

Rules:

  • Each permitted subclass must directly extend the sealed class.
  • Each must declare one of final (end of the line), sealed (with its own permits list) or non-sealed (reopened for anyone to extend).
  • Permitted subclasses must be in the same module, or the same package if you are in the unnamed module. If they are in the same source file, permits can be omitted and is inferred.

Benefits:

  • Design intent is enforced: no unexpected subclass can appear in another team's code.
  • Exhaustiveness: because the compiler knows every subtype, a switch that handles all of them needs no default branch (pattern matching for switch, Java 21). If someone adds a new permitted subtype, every switch that does not handle it fails to compile, pointing you to all the places to update. A default branch would hide that.
  • Works perfectly with records, which are implicitly final, to build algebraic data types.

Sealed types restrict who can extend, not who can use the class; visibility is still controlled by access modifiers.

How it works

  1. Mark the base sealed and list subtypes in permits.
  2. Mark each subtype final, sealed or non-sealed.
  3. Compiler rejects any other subclass.
  4. Switch over the base type is checked for completeness.

Example

public sealed interface Shape permits Circle, Square, Polygon {}
public record Circle(double r) implements Shape {}
public record Square(double side) implements Shape {}
public non-sealed class Polygon implements Shape {}   // open for extension

double area(Shape s) {
    return switch (s) {
        case Circle c -> Math.PI * c.r() * c.r();
        case Square sq -> sq.side() * sq.side();
        case Polygon p -> p.computeArea();
    };   // no default needed
}

Common mistakes

  • Forgetting to mark subclasses final, sealed or non-sealed.
  • Putting permitted classes in different packages without a named module.
  • Adding a default branch, which disables the compile-time check for new subtypes.
  • Thinking sealed controls visibility.

How to answer in the interview

"A sealed class or interface, standard since Java 17, declares exactly which types may extend it with a permits clause, for example sealed class Shape permits Circle, Square. Each permitted subclass must be final, sealed again, or non-sealed to reopen the hierarchy, and they must be in the same module or package. That gives a closed hierarchy, between final and fully open. The big benefit is exhaustiveness: a switch that covers all permitted subtypes needs no default, and when someone adds a new subtype, every incomplete switch fails to compile, so nothing gets missed."

Likely follow-up questions

  • Why is exhaustive switching useful when the domain changes? The compiler lists every place that must handle the new case.
  • What does non-sealed do? Reopens that branch of the hierarchy for unrestricted extension.
  • Sealed vs enum? Enums are fixed instances; sealed types are fixed types that can carry different data.
