An upstream change silently filled a key feature with nulls, and the model served bad predictions for three days. How do you respond and prevent it?

MLOps · scenario · levels mid, senior

In one line

Stop the damage (fallback model, rules or pause automation), assess and remediate affected decisions from prediction logs, fix the pipeline and backfill, then prevent recurrence with blocking null-rate validation, a data contract with the upstream team, prediction distribution monitoring and a blameless post-incident review.

Detailed explanation

This is an incident with two parts: the model is still harming decisions, and three days of bad decisions already happened.

Stop the damage. If the feature can't be fixed within minutes, switch to a fallback: a previous model or a variant trained without that feature, a rules-based policy, or route decisions to manual review or pause automation for high-impact actions. Communicate with stakeholders early.

Assess impact. Prediction logs, with model version and features per request, show exactly which predictions used null values over the three days. Quantify how decisions changed: approvals, declines, prices, alerts. Then remediate where possible—re-score affected applications with correct features, review declined transactions or rejected applicants, contact customers if required, and inform compliance if regulated decisions were affected.

Fix and backfill. Work with the upstream team to fix the change (or adapt our pipeline), backfill correct feature values for the affected period as a new version, and verify the online feature store is correct before switching back.

Prevent. Several layers, because one failed:

  • Data validation on key features with null-rate and distribution checks that block bad data from reaching the online store, not just warn.
  • A data contract with the upstream team covering schema, semantics, allowed nulls and a change notification process, ideally enforced in their CI.
  • Prediction distribution monitoring, which would have shown a shift within hours, plus default-value rates per feature.
  • A model that degrades gracefully, for example explicit missing-value handling.
  • A blameless post-incident review asking why detection took three days.

How it works

  1. Declare an incident; switch to fallback or pause automation.
  2. Query prediction logs for affected requests; quantify impact.
  3. Remediate decisions with business and compliance teams.
  4. Fix upstream or pipeline; backfill; verify online features.
  5. Restore the model; watch metrics closely.
  6. Add blocking checks, contract, monitoring; run the review.

Example

-- Affected decisions
SELECT decision, COUNT(*) AS n
FROM prediction_log
WHERE model = 'credit-risk' AND ts BETWEEN '2026-11-10' AND '2026-11-13'
  AND features:income_verified IS NULL
GROUP BY decision;
-- -> 4,812 declines to re-score with corrected features
check: {feature: income_verified, max_null_rate: 0.01, action: block_and_page}

Common mistakes

  • Fixing the pipeline but never remediating past decisions.
  • Validation that only warns.
  • Blaming the upstream team instead of fixing detection.
  • Switching the model back before verifying the online features.

How to answer in the interview

"First I stop the damage: switch to a fallback model that doesn't use the feature, rules, or pause automated decisions. Then I use prediction logs to find every decision made with null features over the three days and remediate, for example re-scoring applications or reviewing declines. I fix the pipeline with the upstream team and backfill. For prevention: blocking validation on null rates for key features, a data contract with change notification, and prediction distribution monitoring, which would have shown the shift within hours. And a blameless review on why detection took three days."

Likely follow-up questions

  • Why did three days pass unnoticed? No blocking checks or prediction drift alerts, and labels lagged; fix with label-free monitoring.
  • What belongs in a data contract? Schema, semantics, null rules, freshness, owners and change process.
  • How should models handle missing features? Explicit missing indicators and sensible defaults, tested in evaluation.
