What is LinkedBlockingQueue?

Collections · concept · levels mid

In one line

LinkedBlockingQueue is a FIFO BlockingQueue of linked nodes, optionally bounded (default Integer.MAX_VALUE), using two locks (putLock and takeLock) so producers and consumers can work at the same time; it is the queue behind Executors.newFixedThreadPool.

Detailed explanation

Internally the queue keeps head and last node references, a capacity and an AtomicInteger count. Enqueue links a new node after last; dequeue advances head. Ordering is strictly FIFO.

Capacity. new LinkedBlockingQueue<>() uses Integer.MAX_VALUE, which is unbounded in practice. If producers outpace consumers, the backlog grows silently until latency explodes or the JVM hits OutOfMemoryError. In production pass an explicit capacity, for example new LinkedBlockingQueue<>(10_000), so put blocks or a timed offer fails and you get back-pressure.

Two-lock design. Unlike ArrayBlockingQueue, which uses one ReentrantLock for both ends, LinkedBlockingQueue has a putLock with a notFull condition and a takeLock with a notEmpty condition. Because producers touch only the tail and consumers only the head, a put and a take can proceed in parallel; the shared AtomicInteger count coordinates them. Under mixed producer-consumer load this usually gives higher throughput. The trade-off is allocating a node per element, which adds GC pressure, while ArrayBlockingQueue preallocates its array. Operations that touch both ends, such as remove(Object) or iteration, acquire both locks.

Thread pools. Executors.newFixedThreadPool(n) and newSingleThreadExecutor() build a ThreadPoolExecutor with an unbounded LinkedBlockingQueue. That means the pool never grows beyond its core size and never rejects tasks; under sustained overload, tasks pile up in memory. For services, construct a ThreadPoolExecutor yourself with a bounded queue and a rejection policy.

How it works

  1. put(e): lock putLock; while count == capacity await notFull.
  2. Link node at tail; count.getAndIncrement().
  3. If room remains, signal another producer; unlock.
  4. If the queue was empty before, signal notEmpty (taking takeLock briefly).
  5. take() mirrors this on the head with takeLock.

Example

BlockingQueue<Runnable> work = new LinkedBlockingQueue<>(2_000);   // bounded!
ThreadPoolExecutor pool = new ThreadPoolExecutor(
        8, 8, 0L, TimeUnit.MILLISECONDS, work,
        new ThreadPoolExecutor.CallerRunsPolicy());

// What newFixedThreadPool does (unbounded):
// new ThreadPoolExecutor(n, n, 0L, MILLISECONDS, new LinkedBlockingQueue<Runnable>());

Common mistakes

  • Using the no-arg constructor in production.
  • Trusting newFixedThreadPool under unpredictable load.
  • Assuming remainingCapacity() is meaningful for an unbounded queue.
  • Ignoring InterruptedException from put/take.

How to answer in the interview

"LinkedBlockingQueue is a BlockingQueue backed by linked nodes with FIFO ordering. It's optionally bounded: without a capacity it's effectively unbounded at Integer.MAX_VALUE, which can hide a backlog until you run out of memory, so in production I pass a capacity. Internally it uses two separate locks, one for put and one for take, so a producer and a consumer can work at the same time, which usually gives more throughput than ArrayBlockingQueue's single lock, at the cost of a node allocation per element. Executors.newFixedThreadPool uses an unbounded one for its tasks."

Likely follow-up questions

  • What goes wrong with newFixedThreadPool? Its unbounded queue accepts everything, so overload becomes memory growth and huge latency instead of rejection.
  • Why can it use two locks? Producers and consumers touch different ends; an atomic count links them.
  • When choose ArrayBlockingQueue? Fixed bound, less GC, predictable memory.
