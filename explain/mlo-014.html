How do you test machine learning systems beyond accuracy on a test set?

MLOps · concept · levels mid, senior

In one line

Beyond test-set accuracy, test data (schema, ranges, nulls, distributions), code (unit tests for features), model behaviour (invariance and directional tests), slices of important segments, fairness and robustness, and infrastructure (latency, load, API contract).

Detailed explanation

A single accuracy number hides many failure modes: broken input data, a preprocessing bug, a model that fails for one customer group, or a service that is too slow. ML testing is layered like a pyramid.

Data tests check inputs on training data and incoming production data: schema, allowed ranges, null rates, uniqueness, category sets and distribution checks, using Great Expectations, Pandera, Soda or TFX Data Validation. Unit tests cover feature engineering and preprocessing code like any other code, including edge cases such as empty strings and time zones.

Behavioural tests (popularised by the CheckList approach) probe model logic. Invariance tests: changing an irrelevant attribute, such as a name in a sentence, should not change the prediction. Directional expectation tests: increasing income should not lower a credit score. Minimum functionality tests: simple, known cases must be right.

Slice-based evaluation measures metrics on segments like new customers, regions, devices or rare classes, where averages hide failures. Fairness tests compare error rates across protected groups; robustness tests add noise, typos or adversarial perturbations. Finally, infrastructure tests check serving latency, throughput, memory, and the API contract between the model service and consumers, plus golden-input smoke tests of the packaged container.

How it works

  1. Validate training and serving data with automated expectations.
  2. Unit-test feature and preprocessing functions.
  3. Run behavioural test suites against each candidate model.
  4. Evaluate overall and per slice; compare with the production model.
  5. Run fairness and robustness checks where relevant.
  6. Load-test the serving container and verify the API contract.

Example

def test_invariance_to_name(model):
    a = model.predict(["Priya was very happy with the delivery"])
    b = model.predict(["John was very happy with the delivery"])
    assert a == b

def test_directional_income(credit_model, applicant):
    low = credit_model.score({**applicant, "income": 40_000})
    high = credit_model.score({**applicant, "income": 80_000})
    assert high >= low

def test_slice_recall(eval_df, preds):
    new = eval_df["tenure_months"] < 3
    assert recall(eval_df.y[new], preds[new]) >= 0.80

Common mistakes

  • Only reporting aggregate accuracy.
  • Testing training data but not production inputs.
  • No tests for preprocessing, the most common source of bugs.
  • Never load-testing the serving path before release.

How to answer in the interview

"Accuracy on a holdout set is necessary but not sufficient. I test data with schema, range, null and distribution checks, in training and in production. Feature code gets ordinary unit tests. For the model itself I use behavioural tests: invariance, where irrelevant changes shouldn't change predictions, and directional tests, like higher income not lowering a credit score. I evaluate on important slices because averages hide failures, add fairness and robustness checks where they matter, and load-test the serving container against latency targets and the API contract."

Likely follow-up questions

  • How do you test a ranking model with no single right answer? Use ranking metrics like NDCG on judged sets, plus invariance and sanity tests on known queries.
  • Where do behavioural tests run? In the evaluation step of the training pipeline, as a promotion gate.
  • How do you choose slices? With the business: high-value, regulated, new or historically problematic segments.
