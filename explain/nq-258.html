Which columns would you use to join the tables, and why use customer_id?

Databases & SQL · concept · levels entry

In one line

Join on customer_id because it is the primary key in Customer and the foreign key in Orders: it is unique, stable, compact and indexed, whereas names are not unique, can change or contain typos, and would attribute orders to the wrong customer.

Detailed explanation

A join condition should identify exactly one parent row for each child row. customer_id does that by design:

  • Unique: as the primary key, no two customers share it, so each order maps to one customer.
  • Stable: a surrogate id never changes, even when the customer changes their name, email or address.
  • Enforced: the foreign key constraint guarantees every orders.customer_id exists in customer, so the join cannot silently lose or invent relationships.
  • Efficient: an integer (or UUID) key is small and indexed, making lookups and hash joins fast; comparing long strings is slower and subject to collation and case rules.
  • Defined by the model: the join follows the relationship the schema declares, which makes queries predictable and lets the optimizer use foreign key knowledge.

Joining on name breaks in several ways. Two customers called "Priya Sharma" would both match each other's orders, multiplying rows and inflating revenue. A customer who changes their name, or a typo like "Priya Sharmaa", would lose their history. Trailing spaces, case differences and Unicode normalisation cause further mismatches. Names are attributes for display, not identity.

The same reasoning applies to grouping: even if a report displays only the name, you should GROUP BY customer_id (plus name) so customers with identical names stay separate. And if Orders lacked a customer_id column, the right fix would be to add one, not to join on descriptive data.

How it works

  1. Customer rows each have a unique customer_id (primary key, indexed).
  2. Each order stores the customer_id of its owner (foreign key).
  3. The database verifies the reference exists on insert or update.
  4. A join on equal ids matches each order to one customer.
  5. The index on the key makes this lookup fast.

Example

-- Correct: key-based join and grouping
SELECT c.customer_id, c.name, SUM(o.amount) AS revenue
FROM customer c
JOIN orders o ON o.customer_id = c.customer_id
GROUP BY c.customer_id, c.name;

-- Wrong: name-based join merges two different "Priya Sharma" customers
SELECT c.name, SUM(o.amount)
FROM customer c
JOIN orders o ON o.customer_name = c.name
GROUP BY c.name;   -- each Priya's orders are counted for both -> inflated totals

Common mistakes

  • Joining on names, emails or other mutable attributes.
  • Grouping by name only in reports.
  • Leaving out the foreign key constraint, allowing orphan orders.
  • Storing ids with mismatched types (varchar vs bigint), preventing index use.

How to answer in the interview

"I join on customer id because it's the primary key of Customer and the foreign key in Orders, so it uniquely identifies each customer and never changes. Joining on name would be wrong: two customers can share a name, names can change or have typos, so orders could be attributed to the wrong person or lost, and totals could be inflated. Keys are also compact and indexed, so the join is efficient, and the foreign key constraint guarantees every order points to a real customer. For the same reason I group by customer id even if I only display the name."

Likely follow-up questions

  • Why group by customer_id if you only show the name? So different customers with the same name are not merged.
  • Natural key or surrogate key? Usually a surrogate id, with natural keys like email enforced by unique constraints.
  • What if the id types differ between tables? Implicit casts can prevent index use; align the column types.
