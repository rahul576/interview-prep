How do you build an evaluation dataset for an LLM application from production data?

LLMOps & RAG · concept · levels mid, senior

In one line

Build the dataset by sampling production traces stratified across topics, users, languages and difficulty (using query clustering to cover rare categories), adding failures from feedback and incidents plus adversarial cases, getting expert reference answers or rubrics (and expected documents for RAG), anonymising personal data, balancing and versioning it, and refreshing regularly.

Detailed explanation

Synthetic or developer-written test questions are cleaner and more obvious than what users really type: real queries are vague, misspelled, multilingual, multi-part and full of internal jargon. Production traces are therefore the best source.

Sampling. Random sampling over-represents the most frequent questions. Instead, embed and cluster queries, then sample from each cluster, so rare but important categories (complaints, legal questions, specific products) are included. Stratify also by user type, channel, language and difficulty (single-fact vs multi-step).

Failures. Add every case from negative feedback, escalations and incidents, plus adversarial inputs: injection attempts, out-of-scope requests, questions with no answer in the knowledge base (to test "I don't know").

Labels. Domain experts write reference answers for factual questions, or rubrics listing what a good answer must contain and must not contain for open-ended ones. For RAG, they mark which documents or passages should be retrieved, enabling retrieval metrics separately from generation. Use clear labelling guidelines and double-label a subset to check agreement.

Privacy. Remove or pseudonymise personal data; restrict dataset access; respect retention rules and consent.

Balance and versioning. Cap the share of any one category so it doesn't dominate the average; report per-segment scores. Version the dataset (v1, v2...) so results remain comparable, and keep older versions.

Refresh. Usage evolves with new products and features; add new clusters and retire obsolete cases on a schedule. Keep a held-out portion that prompt authors don't look at, to avoid overfitting prompts to the test.

How it works

  1. Export recent traces (redacted).
  2. Embed and cluster queries; sample per cluster and segment.
  3. Add failures and adversarial cases.
  4. Expert labelling: references, rubrics, expected documents.
  5. Balance, version, split dev/held-out.
  6. Refresh monthly or quarterly.

Example

  "expected_docs": ["refund-policy#0003"],

  "dataset_version": "v5"
}

Common mistakes

  • Only frequent questions; rare high-risk ones missing.
  • Unlabelled data, so scores are judge guesses.
  • Personal data left in the set.
  • Tuning prompts on the full set, overfitting to it.

How to answer in the interview

"Production data shows what users really ask, so I sample traces stratified by topic, user type, language and difficulty, using query clustering so rare but important categories are covered. I add failures from feedback, escalations and incidents plus adversarial cases. Domain experts write reference answers or rubrics, and for RAG they mark which documents should be retrieved. Personal data is removed and access controlled. The set is balanced across categories, versioned for comparability, and refreshed as usage evolves. A few hundred well-chosen cases usually catch most regressions, and I keep a held-out part to avoid overfitting prompts."

Likely follow-up questions

  • Avoid overfitting the dataset? Held-out split, rotation of cases, periodic fresh samples.
  • No production data yet? Expert-written and synthetic cases, replaced with real data after launch.
  • Label quality? Guidelines, double labelling, agreement checks.
