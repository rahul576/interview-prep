How do you run coding agents, such as Claude Code or Copilot coding agent, safely in a team?

AI Agents & AIOps · concept · levels mid, senior

In one line

Run coding agents like contributors, not admins: they work in branches or isolated workspaces and open pull requests, human review and CI stay mandatory, they run in sandboxes with limited credentials and network, permission settings control commands and file access, instruction files such as CLAUDE.md or AGENTS.md encode conventions, and you track the quality of their changes.

Detailed explanation

Coding is one of the most productive uses of agents because results are verifiable: code compiles, tests pass, linters are happy. Tools like Claude Code, GitHub Copilot coding agent, OpenAI Codex and Cursor can implement features, fix bugs and refactor across repositories. The safety model should mirror how you onboard a new developer, with extra caution because agents act fast and read untrusted content.

Workflow: the agent works on a branch or isolated worktree and opens a pull request. It never pushes to main or deploys. Branch protection, required reviews and CI checks, tests, linting, type checks, SAST, dependency and secret scanning, apply to agent PRs exactly as to human ones. The human who requested or reviews the change is accountable for merging it.

Sandboxing: agents run in containers, dev containers or cloud sessions with limited credentials: a scoped token for the repository, no production secrets, no cloud admin rights. Network access is restricted or allowlisted, because the agent reads issues, dependencies and web pages that may contain prompt injection, and an exfiltration path plus secrets is a dangerous combination.

Permissions: tools like Claude Code have permission settings that allow some commands without asking, such as running tests or the linter, and require approval for others, like installing packages, network calls, or deleting files. Organisation-wide managed settings can enforce this.

Instructions: repository files such as CLAUDE.md, AGENTS.md or .github/copilot-instructions.md describe build and test commands, conventions, architecture and boundaries, which improves quality and consistency.

Measurement: track merge and rejection rates, review comments, reverts and incidents linked to agent changes, and start with well-scoped tasks.

How it works

  1. Write repository instructions: commands, conventions, no-go areas.
  2. Configure the sandbox: scoped repo token, no prod secrets, restricted egress.
  3. Configure permissions: allowed commands, ask-first commands, denied paths.
  4. Assign a well-defined issue; agent works in a branch and opens a PR.
  5. CI and security scans run; a human reviews and merges.
  6. Track outcomes and refine instructions and permissions.

Example

{
  "permissions": {
    "allow": ["Bash(npm test:*)", "Bash(npm run lint)", "Bash(git diff:*)"],
    "ask": ["Bash(npm install:*)", "Bash(curl:*)", "WebFetch"],
    "deny": ["Read(./.env)", "Read(./secrets/**)", "Bash(git push --force:*)"]
  }
}
# CLAUDE.md
- Build: `./gradlew build`; tests: `./gradlew test`
- Java 21, Spring Boot 3; follow existing package layout under `com.acme.orders`
- Never edit `db/migrations` that are already released; add a new migration
- All PRs need tests; do not change CI workflows without asking

Common mistakes

  • Giving the agent a developer's personal token with admin rights.
  • Auto-merging agent PRs because "tests pass".
  • Unrestricted network plus secrets in the environment.
  • No repository instructions, so the agent guesses conventions.
  • Starting with vague, large tasks instead of well-scoped issues.

How to answer in the interview

"Coding agents are very productive because their work is verifiable with tests, but I treat them like a contributor. They work in a branch or isolated workspace and open a pull request; they never push to main or deploy. Human review and all CI checks, tests, linting and security scanning, stay mandatory. They run in sandboxes with limited credentials, no production secrets and restricted network, because they read untrusted content like issues and dependencies. Permission settings allow things like tests and linters but ask before installing packages or making network calls. The repo has instruction files like CLAUDE.md with commands and conventions. And we track merge rates, reverts and incidents from agent changes."

Likely follow-up questions

  • Which tasks would you assign to agents first? Well-scoped bugs with reproductions, test coverage, dependency upgrades, small refactors and documentation.
  • Who is accountable for agent code? The human who requested and approved the merge.
  • How do you handle secrets? Keep them out of the sandbox; use mocks or scoped test credentials.
