A customer disputes an automated decision made two months ago. How do you trace which model, data and features produced it?

MLOps · scenario · levels senior, lead

In one line

Tracing a disputed decision should be a lookup, not an investigation: the prediction log gives model version, inputs, output and thresholds; the registry maps the version to the training run, which pins code commit and data snapshot; because features were logged at inference time, you can reproduce and explain the decision.

Detailed explanation

Regulators and customers increasingly expect explanations for automated decisions; under GDPR, for example, people can contest significant automated decisions, and lending rules require reasons for declines. A good system makes this a few minutes' work.

The chain starts with the prediction log: request ID, timestamp, customer or application ID, model name and version, the exact feature values used, the output score, the decision threshold or rules applied, and the final decision. From the version, the model registry links to the training run, which records the code commit, the data snapshot or table version, hyperparameters, evaluation results and approvals.

Logging features at inference time is the critical link. Recomputing features two months later from tables that have since been updated, backfilled or corrected gives different values, so you could not reproduce the decision. With logged features you can load that exact model version, rerun the prediction, and generate an explanation: SHAP values or reason codes listing the main factors (for example, "high utilisation of existing credit").

If any link is missing—most often inference-time feature logging or data snapshot pinning—the honest conclusion is that the system has no real lineage, and fixing that becomes a priority.

How it works

  1. Look up the prediction by request or customer ID and date.
  2. Read model version, features, score, threshold and decision.
  3. Follow registry version to training run, commit and data snapshot.
  4. Load the exact model artefact and reproduce the score.
  5. Generate local explanations and reason codes.
  6. Document the outcome and any remediation for the customer.

Example

{
  "request_id": "a7f3-9c21",
  "ts": "2026-09-14T10:22:31Z",
  "application_id": "APP-55812",
  "model": "credit-risk", "version": 21,
  "features": {"utilisation": 0.93, "missed_payments_12m": 2, "income": 41000},
  "score": 0.71, "threshold": 0.65, "decision": "decline",
  "reason_codes": ["HIGH_UTILISATION", "RECENT_MISSED_PAYMENTS"]
}

Common mistakes

  • Logging only the score, not the feature values.
  • Recomputing features from current tables and calling it a reproduction.
  • Not pinning the training data version in the run.
  • Short log retention that ends before the dispute window closes.

How to answer in the interview

"In a well-built system this is a lookup. Each prediction is logged with request ID, timestamp, model version, the exact feature values, the score and the threshold applied. The registry maps that version to its training run, which records the code commit and data snapshot. Because features were logged at inference time, I don't recompute them from tables that have changed. I can reload that model, reproduce the score and produce SHAP-based reason codes for the customer or regulator. If inference-time feature logging is missing, that's the first gap I'd fix."

Likely follow-up questions

  • What retention would you choose for prediction logs? Aligned with legal dispute and audit periods, limited by privacy rules and storage cost.
  • How do you protect personal data in logs? Pseudonymise IDs, restrict access and encrypt.
  • What if the model is a black box? Use model-agnostic explanations like SHAP and document their limitations.
