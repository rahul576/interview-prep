Design a highly available and scalable web application on AWS.

Cloud (AWS) · design · levels senior, lead

In one line

Build it multi-AZ at every layer: CloudFront + WAF + Route 53 at the edge, an ALB in front of a stateless, auto-scaled app tier, Multi-AZ RDS/Aurora with read replicas, ElastiCache and SQS for decoupling, all in IaC with monitoring, backups and defined RPO/RTO.

Detailed explanation

High availability on AWS starts with the assumption that an instance or a whole AZ will fail. So each tier runs in at least two, preferably three, availability zones, and no state lives on individual servers.

At the edge, Route 53 resolves the domain with health checks, CloudFront caches static assets and absorbs traffic spikes close to users, and AWS WAF filters common attacks and bots; Shield Standard covers network DDoS. An Application Load Balancer spans the AZs and routes to healthy targets only.

The application tier is stateless: sessions in ElastiCache or DynamoDB, uploads in S3. It runs on ECS/Fargate, EKS or an EC2 Auto Scaling group, using target tracking on CPU or requests per target, with health checks so failed tasks are replaced automatically. Slow or bursty work (emails, image processing, exports) goes through SQS to workers that scale on queue depth, so a spike does not overload the web tier.

The data tier is usually the hardest. RDS Multi-AZ keeps a synchronous standby and fails over automatically in about a minute or two; Aurora stores six copies of data across three AZs and fails over to a replica faster. Read replicas offload reads, and ElastiCache Redis caches hot data. Backups use automated snapshots with point-in-time recovery, copied to another region or account.

Everything is defined in Terraform, deployed through a pipeline with rolling or blue/green deployments, and observed with CloudWatch metrics, logs, alarms and tracing. RPO/RTO targets drive how much DR you need.

How it works

  1. User → Route 53 → CloudFront (+WAF) → static from S3, dynamic to ALB.
  2. ALB → app tasks in three AZs, scaled by target tracking.
  3. App → ElastiCache for cache/sessions → Aurora writer for writes, replicas for reads.
  4. Async jobs → SQS → worker service.
  5. CloudWatch alarms → on-call; backups → cross-region copies.

Example

resource "aws_appautoscaling_policy" "api_cpu" {
  name               = "api-cpu-60"
  policy_type        = "TargetTrackingScaling"
  service_namespace  = "ecs"
  resource_id        = "service/prod/api"
  scalable_dimension = "ecs:service:DesiredCount"
  target_tracking_scaling_policy_configuration {
    target_value = 60
    predefined_metric_specification {
      predefined_metric_type = "ECSServiceAverageCPUUtilization"
    }
  }
}

Common mistakes

  • Multi-AZ app servers but a single-AZ database or a single NAT gateway.
  • Sticky sessions or local files that make instances non-disposable.
  • Auto scaling with a maximum too low, or minimum of one task.
  • Backups that are never restore-tested.

How to answer in the interview

"I design for AZ failure: everything spans at least three availability zones. Route 53 and CloudFront with WAF sit at the edge, then an ALB in front of a stateless app tier on ECS or EKS that auto-scales on CPU or request count. Sessions go to ElastiCache, files to S3, background work to SQS. The database is Aurora or RDS Multi-AZ with read replicas, plus point-in-time recovery and cross-region backup copies. It's all Terraform, monitored with CloudWatch alarms, and the DR level, from backup-and-restore to warm standby in another region, follows the agreed RPO and RTO."

Likely follow-up questions

  • What if it must survive a region outage? Warm standby or active-active in a second region with Aurora Global Database or DynamoDB global tables and Route 53 failover.
  • How do you deploy without downtime? Rolling or blue/green behind the ALB with health checks and connection draining.
  • Where do sessions live? ElastiCache or stateless JWTs, never on the instance.
