What are feature flags, and how do they relate to deployments?

DevOps & CI/CD · concept · levels mid, senior

In one line

A feature flag is a runtime switch that turns functionality on or off without redeploying, which separates deployment from release and enables trunk-based development, gradual rollouts, targeting and an instant kill switch, at the cost of flag debt that must be cleaned up.

Detailed explanation

Without flags, deploying code and releasing a feature are the same event: when the new version goes live, every user sees the change. With a flag, new code ships to production dark, disabled, and the release becomes a configuration change that product or engineering can make at any time, for anyone.

This enables several practices. Trunk-based development: developers merge unfinished work to main daily behind a disabled flag, avoiding long-lived branches and painful merges. Progressive delivery: enable for internal staff, then 1%, 10%, 50% and 100% of users, watching error rates and business metrics at each step. Targeting: enable for beta customers, a region or a plan. Kill switch: if something goes wrong, turn the feature off in seconds rather than rolling back a deployment. Flags also support A/B experiments and operational toggles, such as disabling a heavy recommendation call during peak load.

Flags are evaluated by an SDK in the application, using rules from a flag service such as LaunchDarkly, Unleash, Flagsmith, Azure App Configuration or AWS AppConfig; OpenFeature is a vendor-neutral standard API. SDKs cache rules locally so evaluation is fast and survives a flag service outage with safe defaults.

The cost is complexity. Every flag doubles code paths, so long-lived flags make code hard to read and test. Treat release flags as temporary: each has an owner and an expiry, and is removed once the feature is fully on. Flag changes should be audited because they change production behaviour.

How it works

  1. Wrap new behaviour in a flag check with a safe default (off).
  2. Deploy to production; nobody sees the feature.
  3. Enable for internal users and test in production.
  4. Roll out by percentage while watching metrics.
  5. Turn off instantly if metrics degrade.
  6. At 100%, delete the flag and the old code path.

Example

// OpenFeature Java SDK
Client flags = OpenFeatureAPI.getInstance().getClient();
EvaluationContext ctx = new ImmutableContext(user.getId(),
        Map.of("country", new Value(user.getCountry())));

if (flags.getBooleanValue("new-checkout-flow", false, ctx)) {
    return newCheckout.process(cart);
}
return legacyCheckout.process(cart);

Rollout plan: staff only, then 5% of UK users for a day, then 25%, 50%, 100%; delete the flag two weeks later.

Common mistakes

  • Never removing flags, leaving hundreds of dead branches.
  • Testing only the "on" path.
  • Unsafe defaults when the flag service is unreachable.
  • Using flags for secrets or long-term configuration.

How to answer in the interview

"A feature flag is a runtime switch around a piece of functionality, so we can turn it on or off without a redeploy. That separates deployment from release: code goes to production dark, then we enable it for internal users, then a growing percentage of customers, watching metrics, and if something breaks the flag is a kill switch. It's also what makes trunk-based development practical, because unfinished work can merge to main behind a disabled flag. We use a tool like LaunchDarkly or Unleash, ideally behind OpenFeature. The downside is flag debt, so every flag has an owner and gets removed once the feature is fully released."

Likely follow-up questions

  • How do you test code with many flags? Test both states of each active flag, and default-on and default-off configurations, not every combination.
  • Flags vs canary deployments? Canaries route traffic between versions; flags switch features inside one version.
  • What if the flag service is down? SDKs use cached rules or coded safe defaults.
