Why did Kubernetes remove dockershim, and what does it mean for Docker images?

Docker · concept · levels senior

In one line

Kubernetes talks to runtimes via the CRI; Docker Engine never implemented CRI, so the kubelet carried an adapter called dockershim, removed in 1.24; nodes now use containerd or CRI-O directly, Docker-built OCI images still work, but anything relying on Docker on the node (socket mounts, docker ps) broke.

Detailed explanation

Early Kubernetes was tightly coupled to Docker. To support other runtimes, it introduced the Container Runtime Interface (CRI), a gRPC API the kubelet uses to manage pods, containers and images. containerd (via its CRI plugin) and CRI-O implement CRI natively. Docker Engine did not, so Kubernetes maintained dockershim inside the kubelet, translating CRI calls into Docker API calls. The path became kubelet → dockershim → dockerd → containerd → runc, an extra hop with extra failure modes, and the Kubernetes project had to maintain Docker-specific code. Dockershim was deprecated in 1.20 and removed in 1.24 (2022).

For images, nothing changed. docker build produces standard OCI images, and containerd and CRI-O pull and run them exactly as before, because Docker itself used containerd underneath. Developers can keep using Docker locally and in CI.

What broke were things that assumed Docker was installed on the node. Workloads that mounted /var/run/docker.sock to build images (Docker-in-Docker style CI runners), to discover containers, or to read metadata stopped working. Log collectors that read /var/lib/docker/containers/*.log had to switch to /var/log/pods and the CRI log format. Monitoring agents querying the Docker API needed CRI support. Admin habits changed too: docker ps on a node became crictl ps, docker logs became crictl logs, and ctr -n k8s.io gives lower-level containerd access. Teams that truly needed Docker Engine could use cri-dockerd, an external adapter maintained by Mirantis. Managed services (EKS, AKS, GKE) moved to containerd.

How it works

  1. kubelet sends CRI requests (RunPodSandbox, CreateContainer).
  2. containerd's CRI plugin or CRI-O handles them.
  3. The runtime pulls OCI images from registries.
  4. It starts containers through runc or crun.
  5. Logs are written to /var/log/pods in CRI format.

Example

kubectl get nodes -o wide                 # CONTAINER-RUNTIME column: containerd://1.7.x
sudo crictl ps                            # list running containers
sudo crictl images
sudo crictl logs <container-id>
sudo ctr -n k8s.io containers list        # containerd native view

Common mistakes

  • Believing Docker images no longer work on Kubernetes.
  • Keeping CI jobs that mount the node's Docker socket.
  • Log agents still reading Docker's log path.
  • Confusing "Docker the build tool" with "Docker the node runtime".

How to answer in the interview

"Kubernetes talks to runtimes through the Container Runtime Interface. Docker Engine never implemented CRI, so Kubernetes maintained dockershim in the kubelet as an adapter, which added complexity and an extra hop through dockerd to containerd. It was removed in 1.24, and nodes now use containerd or CRI-O directly. Docker-built images are OCI images, so they run unchanged. What broke were things depending on Docker on the node: tools mounting docker.sock to build images or collect logs, and habits like docker ps, which is now crictl. Teams had to switch log collectors and in-cluster builds."

Likely follow-up questions

  • How do you list containers on a containerd node? crictl ps, or ctr -n k8s.io containers list.
  • How do you build images in-cluster now? BuildKit, kaniko or buildah, rootless where possible.
  • Can you still use Docker Engine? Yes, with the external cri-dockerd adapter.
