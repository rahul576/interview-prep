Design an ad click aggregation system that reports clicks per ad in near real time.

Classic Design Problems · design · levels senior, lead

In one line

Stream click events through Kafka, aggregate per ad per minute with event-time windows in Flink, deduplicate and use exactly-once sinks, handle late events with watermarks, serve from an OLAP store, and reconcile daily against raw logs for billing.

Detailed explanation

This is a classic interview problem because it mixes scale (billions of events/day), freshness (minutes) and money: advertisers are billed on these numbers, so double counting or losing clicks is unacceptable.

Event time vs processing time: a click on a phone at 10:01 may arrive at 10:07. Aggregating by arrival time puts it in the wrong minute. Stream processors use event time with watermarks (a notion of "we've probably seen everything up to 10:02") and allowed lateness to update windows when stragglers arrive.

Exactly-once in Flink combines checkpoints of state with transactional sinks; events carry a click ID for deduplication (retries from ad servers or clients). Click fraud filtering removes bots before counting.

Because streaming bugs happen, the raw events are archived to object storage, and a batch job recomputes daily totals for billing and corrects the real-time numbers (a lambda-style safety net).

How it works

  1. Ad servers log clicks → Kafka (partition by ad_id).
  2. Flink: dedup by click_id (state with TTL) → tumbling 1-min windows by event time → counts per ad.
  3. Results → ClickHouse/Druid/Pinot → dashboards and APIs.
  4. Raw → S3 → daily Spark job → reconciliation → billing.

Example

-- ClickHouse query for an advertiser dashboard
SELECT ad_id, toStartOfMinute(ts) AS minute, sum(clicks)
FROM ad_clicks_1m WHERE advertiser_id = 77 AND ts >= now() - INTERVAL 1 HOUR
GROUP BY ad_id, minute ORDER BY minute;

Common mistakes

  • Processing-time windows.
  • No deduplication.
  • Treating the streaming result as the final billing number without reconciliation.
  • Hot partitions for viral ads (pre-aggregate or salt keys).

How to answer in the interview

"Clicks land in Kafka partitioned by ad ID and are archived raw. Flink deduplicates by click ID and counts per ad per minute using event time, with watermarks for late events, writing exactly-once to an OLAP store like ClickHouse for dashboards. Since this drives billing, a daily batch job recomputes totals from raw logs and reconciles any differences, and fraud filtering runs before counting."

Likely follow-up questions

  • Detect click fraud? Rate per IP/device, impossible patterns, ML scoring, blocklists.
  • Very hot ads? Two-stage aggregation with salted keys.
  • Why OLAP store? Fast group-bys and filters over large aggregates.
