What CI/CD tools have you used?

DevOps & CI/CD · scenario · levels entry

In one line

Describe your toolchain by category (CI servers such as Jenkins, GitHub Actions, GitLab CI, Azure DevOps; build and quality tools Maven/Gradle, SonarQube; registries Nexus, Artifactory, ECR, ACR; deployment Helm, Argo CD, Kubernetes, Terraform) and, most importantly, your own role and an improvement you made.

Detailed explanation

Interviewers are less interested in a list of logos than in what you did with them. Organise the answer by pipeline stage so it sounds structured:

  • CI orchestration: Jenkins with declarative Jenkinsfiles and shared libraries, GitHub Actions workflows, GitLab CI or Azure DevOps Pipelines.
  • Build and test: Maven or Gradle, JUnit, Testcontainers, JaCoCo.
  • Quality and security: SonarQube quality gates, Snyk or OWASP Dependency-Check, Trivy for images, secret scanning.
  • Artifacts: Nexus or Artifactory for jars, ECR, ACR or Docker Hub for images.
  • Deployment: Helm charts on Kubernetes, Argo CD for GitOps, Terraform for infrastructure.
  • Observability after deployment: Prometheus, Grafana, CloudWatch or Datadog.

Then explain ownership: did you write pipelines from scratch, maintain them, or just use them? Concrete contributions sound strong: parallelised tests to cut build time from 25 to 9 minutes, introduced the Sonar gate, moved secrets into a vault, or fixed flaky deployments with readiness probes. Be honest about what a platform team handled.

How it works

  1. Walk through your pipeline stage by stage.
  2. Name the tool used at each stage.
  3. State your responsibility for each.
  4. Highlight one or two improvements with numbers.
  5. Mention migrations between tools if you did any.

Example

Sample STAR answer:

  • Situation: builds for our order service took 25 minutes, slowing reviews.
  • Task: reduce feedback time.
  • Action: in the Jenkinsfile I split unit and integration tests into parallel stages, enabled Maven dependency caching on Kubernetes agents and moved Sonar analysis to run alongside the image build.
  • Result: pipeline time dropped to 9 minutes.
stage('Tests') {
  parallel {
    stage('Unit')        { steps { sh './mvnw -B test' } }
    stage('Integration') { steps { sh './mvnw -B verify -DskipUnitTests' } }
  }
}

Common mistakes

  • Listing tools without context.
  • Claiming ownership of what a platform team built.
  • No measurable improvement.
  • Not knowing why a tool was chosen.

How to answer in the interview

"In my last project we used Jenkins with declarative Jenkinsfiles in each repo, and we moved newer services to GitHub Actions. Builds used Maven, SonarQube for quality gates, and Snyk and Trivy for dependency and image scanning. Jars went to Nexus and images to Amazon ECR. We deployed with Helm to Kubernetes, with Argo CD doing GitOps for higher environments, and Terraform for infrastructure. I wrote and maintained the pipeline stages; my biggest improvement was parallelising tests and caching dependencies, which cut build time from twenty-five to nine minutes."

Likely follow-up questions

  • Biggest improvement to a pipeline? Give the parallelisation or quality-gate story with numbers.
  • Jenkins vs GitHub Actions? Jenkins is self-hosted and highly customisable; Actions is managed and tightly integrated with GitHub.
  • Why Argo CD? Pull-based GitOps, drift detection and easy rollback.
