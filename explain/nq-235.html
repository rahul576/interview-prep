What is the difference between SQL and NoSQL databases?

Databases & SQL · concept · levels entry

In one line

SQL (relational) databases store data in tables with a fixed schema, relationships and ACID transactions queried with SQL and joins, while NoSQL databases (document, key-value, wide-column, graph) use flexible schemas, are built to scale horizontally, and often favour availability and eventual consistency.

Detailed explanation

Relational databases such as PostgreSQL, MySQL, Oracle and SQL Server model data as rows in tables with declared columns and types. Relationships are enforced with foreign keys, data is normalised, and SQL supports joins, aggregations and ad hoc queries you did not plan for. They provide strong ACID transactions. Traditionally they scale vertically (bigger machine) plus read replicas; scaling writes horizontally needs sharding or distributed SQL (Citus, CockroachDB, YugabyteDB, Spanner).

NoSQL means "not only SQL" and covers several models:

  • Document: MongoDB, Couchbase. JSON-like documents with nested data.
  • Key-value: Redis, DynamoDB. Very fast lookups by key.
  • Wide-column: Cassandra, HBase, ScyllaDB. Rows grouped by partition key, huge write throughput.
  • Graph: Neo4j, Amazon Neptune. Nodes and edges for relationship traversal.

They usually have a flexible schema (each record can differ), partition data across many nodes by design, and replicate it automatically. Many follow BASE (basically available, soft state, eventually consistent), but the line has blurred: MongoDB has multi-document ACID transactions, DynamoDB has transactions and strongly consistent reads, and Cassandra has tunable consistency. Their main constraint is that you model data around known access patterns, often duplicating data, because joins and ad hoc queries are limited.

How it works

  1. Relational: design normalised tables, constraints and indexes; queries are planned by an optimizer.
  2. NoSQL: start from queries and design keys and documents to answer them directly.
  3. Relational scale: vertical scaling, replicas, partitioning, then sharding.
  4. NoSQL scale: add nodes; data is redistributed by partition key.
  5. Choose consistency: strict ACID by default in SQL, tunable in many NoSQL stores.

Example

-- Relational: normalised and joined
SELECT o.id, c.name, SUM(i.qty * i.price)
FROM orders o JOIN customer c ON c.id = o.customer_id
JOIN order_item i ON i.order_id = o.id
GROUP BY o.id, c.name;
// MongoDB: one document answers "show order 991" in a single read
{ "_id": 991, "customer": { "id": 42, "name": "Asha" },

Common mistakes

  • Claiming NoSQL databases have no transactions at all.
  • Saying relational databases cannot scale.
  • Choosing NoSQL to skip schema design; the schema just moves into code.
  • Treating "NoSQL" as one technology.

How to answer in the interview

"Relational databases store data in tables with a defined schema, enforce relationships with foreign keys, support joins and ad hoc SQL, and give strong ACID transactions; they traditionally scale vertically with read replicas. NoSQL is a family: document stores like MongoDB, key-value stores like Redis and DynamoDB, wide-column stores like Cassandra and graph databases like Neo4j. They have flexible schemas, scale horizontally by partitioning, and often favour availability and eventual consistency, though many now support transactions. I choose relational for complex relationships and consistency, like orders and payments, and NoSQL for huge scale or simple key-based access, like sessions or event history."

Likely follow-up questions

  • A use case for each? Payments in PostgreSQL; user sessions in Redis or DynamoDB; IoT readings in Cassandra.
  • What is BASE? Basically available, soft state, eventually consistent.
  • Can you use both? Yes, polyglot persistence: each service uses the store that fits.
