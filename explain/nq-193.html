What callback interfaces are involved in the bean lifecycle?

Spring Framework · concept · levels mid

In one line

Lifecycle callbacks come as interfaces (InitializingBean.afterPropertiesSet, DisposableBean.destroy), Aware interfaces (BeanNameAware, BeanFactoryAware, ApplicationContextAware, EnvironmentAware), annotations (@PostConstruct/@PreDestroy, preferred), @Bean(initMethod, destroyMethod), plus Lifecycle/SmartLifecycle and application events.

Detailed explanation

Spring offers several ways for a bean to react to its own lifecycle, each with a purpose.

Initialisation and destruction interfaces. InitializingBean.afterPropertiesSet() runs after all properties are set; DisposableBean.destroy() runs on context shutdown. They work but couple your class to Spring, so they are mostly used inside framework code.

Aware interfaces let a bean receive container infrastructure: BeanNameAware (its bean name), BeanClassLoaderAware, BeanFactoryAware, ApplicationContextAware, EnvironmentAware, ResourceLoaderAware, ApplicationEventPublisherAware. In modern code you usually just inject Environment or ApplicationEventPublisher through the constructor instead.

Annotations @PostConstruct and @PreDestroy come from jakarta.annotation (they were javax.annotation before Jakarta EE 9). They are the preferred approach: standard, non-Spring-specific and readable.

Configuration-based: @Bean(initMethod = "start", destroyMethod = "close") is ideal for third-party classes you cannot annotate. For @Bean methods Spring also infers a public close() or shutdown() method as the destroy method.

Phased start and stop: Lifecycle and SmartLifecycle have start(), stop() and isRunning(); SmartLifecycle adds getPhase() and isAutoStartup(), so components like message listeners and schedulers start after all beans are ready and stop in a controlled order during graceful shutdown. SmartInitializingSingleton.afterSingletonsInstantiated() runs once all singletons exist.

Events: ApplicationListener or @EventListener for ContextRefreshedEvent, ApplicationStartedEvent, ApplicationReadyEvent and ContextClosedEvent; ApplicationRunner/CommandLineRunner run code after startup.

How it works

  1. Aware callbacks after dependency injection.
  2. @PostConstruct, then afterPropertiesSet(), then the custom init method.
  3. After all singletons: SmartInitializingSingleton, then SmartLifecycle start() by phase.
  4. Context refreshed and ready events; runners execute.
  5. Shutdown: SmartLifecycle stop() by phase, then @PreDestroy, destroy(), destroy method.

Example

@Configuration
class ClientConfig {
    @Bean(initMethod = "connect", destroyMethod = "disconnect")
    LegacyFtpClient ftpClient() { return new LegacyFtpClient("ftp.internal"); }
}

@Component
class OutboxPoller implements SmartLifecycle {
    private volatile boolean running;
    public void start() { running = true; executor.submit(this::poll); }
    public void stop()  { running = false; executor.shutdown(); }
    public boolean isRunning() { return running; }
    public int getPhase() { return 100; }       // starts late, stops early
}

@Component
class StartupReport {
    @EventListener(ApplicationReadyEvent.class)
    void ready() { log.info("Service ready to accept traffic"); }
}

Common mistakes

  • Implementing Spring interfaces in business classes when annotations would do.
  • Importing javax.annotation.PostConstruct on Boot 3, which is silently ignored if not on the classpath or fails to compile.
  • Starting background threads in @PostConstruct without stopping them.
  • Using ContextRefreshedEvent, which can fire multiple times with child contexts.

How to answer in the interview

"There are several forms. Interfaces: InitializingBean with afterPropertiesSet and DisposableBean with destroy. Aware interfaces give the bean container objects: BeanNameAware, BeanFactoryAware, ApplicationContextAware, EnvironmentAware. Annotations: @PostConstruct and @PreDestroy from jakarta.annotation, which I prefer because they don't couple code to Spring. For third-party classes, @Bean initMethod and destroyMethod. For start and stop phases, SmartLifecycle, and events like ApplicationReadyEvent for work after startup."

Likely follow-up questions

  • Order of init callbacks? @PostConstruct, afterPropertiesSet, then initMethod.
  • SmartLifecycle vs @PostConstruct? SmartLifecycle runs after all beans exist and supports ordered stop.
  • Where to run startup tasks? ApplicationRunner or an ApplicationReadyEvent listener.
