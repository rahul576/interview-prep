Why are tags important in AWS, and what tagging strategy would you use?

Cloud (AWS) · concept · levels entry

In one line

Tags are key-value labels on AWS resources that enable cost allocation, automation and attribute-based access control (ABAC); a good strategy defines a small mandatory set such as Environment, Application, Owner and CostCenter, applies them automatically through IaC, and enforces them with tag policies, SCPs and Config rules.

Detailed explanation

In an account with thousands of resources, names alone do not tell you who owns an instance, which product it belongs to or whether it can be deleted. Tags carry that metadata, and many AWS features consume it.

Cost allocation: once you activate cost allocation tags in the Billing console, Cost Explorer, budgets and the Cost and Usage Report can group spend by Application, Team or Environment, enabling showback or chargeback. Only tags applied after activation appear in billing data, so start early.

Automation: scripts and services select resources by tag: Instance Scheduler stops everything with Environment=dev at night, AWS Backup plans include resources tagged Backup=daily, patch groups in Systems Manager use tags, and incident tooling looks up Owner to page the right team.

Access control (ABAC): IAM conditions such as aws:ResourceTag/Team equals aws:PrincipalTag/Team let a team manage only its own resources without writing a policy per resource. This scales better than listing ARNs, but then tag changes must themselves be restricted.

A strategy keeps the mandatory set small and well defined: allowed keys, exact casing (Environment, not env and ENV), allowed values (dev, staging, prod). Apply tags automatically: Terraform default_tags in the AWS provider, CDK Tags.of(app), CloudFormation stack tags. Enforce them with AWS Organizations tag policies (standardise keys and values), SCPs that deny creating resources without required tags, and AWS Config required-tags rules plus reports for drift. Tags are case-sensitive and not secret, so never store sensitive data in them.

How it works

  1. Agree mandatory keys and allowed values.
  2. Add them as defaults in IaC modules.
  3. Activate cost allocation tags in Billing.
  4. Enforce with tag policies, SCPs and Config rules.
  5. Report and fix untagged resources regularly.

Example

provider "aws" {
  region = "eu-west-1"
  default_tags {
    tags = {
      Environment = "prod"
      Application = "orders"
      Owner       = "team-payments"
      CostCenter  = "CC-1042"
    }
  }
}
# Find resources missing an Owner tag
aws resourcegroupstaggingapi get-resources \
  --query "ResourceTagMappingList[?!(Tags[?Key=='Owner'])].ResourceARN"

Common mistakes

  • Inconsistent keys (env, Env, environment).
  • Tagging manually, so coverage decays.
  • Forgetting to activate cost allocation tags.
  • Too many mandatory tags that nobody fills correctly.
  • Storing secrets or personal data in tags.

How to answer in the interview

"Tags are key-value labels on resources. They make cost allocation possible: once activated, the bill can be broken down by team, application and environment. They drive automation, like stopping all dev instances at night or selecting resources for backup plans, and attribute-based access control, where IAM conditions let a team manage only resources carrying its tag. My strategy is a small mandatory set, Environment, Application, Owner and CostCenter, with fixed spelling and values, applied automatically through Terraform default_tags, and enforced with tag policies, SCPs and AWS Config rules."

Likely follow-up questions

  • How do you find untagged resources across many accounts? Tag policies compliance reports, AWS Config aggregators, or the Resource Groups Tagging API.
  • Why restrict who can change tags under ABAC? Otherwise users could retag resources to gain access.
  • Are tags inherited? Not generally; use IaC defaults or propagation settings where services support them.
