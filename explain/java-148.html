How do you test microservice integrations without a full end-to-end environment?

Testing · concept · levels senior, lead

In one line

Replace most end-to-end testing with consumer-driven contract tests (Pact or Spring Cloud Contract), test each service's own integrations with Testcontainers and WireMock, check event schema compatibility, and keep only a few end-to-end smoke tests after deployment.

Detailed explanation

A full end-to-end environment with twenty services is slow to build, shared by many teams, full of unrelated failures and always running the wrong versions. Tests there are flaky and feedback comes hours late. The goal is to get the same confidence from cheaper, isolated tests.

Consumer-driven contracts solve the core question: "will my change break someone who calls me?" With Pact, the consumer writes a test against a Pact mock server describing the requests it sends and the response fields it relies on. That produces a contract file published to a Pact Broker. The provider's pipeline replays each contract against the real provider (with its dependencies stubbed) and fails if any expectation is broken. can-i-deploy checks whether the versions about to be deployed are compatible. Spring Cloud Contract is provider-driven by default: the provider writes contracts in Groovy or YAML, generates provider tests and publishes WireMock stubs that consumers use.

Within each service, integration tests run against real infrastructure in Testcontainers (PostgreSQL, Kafka, Redis) and use WireMock for HTTP dependencies, including 500s, malformed bodies and timeouts, which a real environment rarely produces on demand.

Asynchronous contracts matter too: Pact supports message pacts, and Avro or Protobuf schemas in a schema registry with backward-compatibility checks stop producers breaking consumers.

A small set of end-to-end smoke tests then verifies the critical journeys in staging after deployment, checking configuration and networking rather than business logic.

How it works

  1. Consumer writes a Pact test; the contract is generated and published to the broker.
  2. Provider CI fetches contracts and verifies them against its real API.
  3. can-i-deploy gates deployment on verified compatibility.
  4. Each service runs Testcontainers and WireMock integration tests.
  5. Schemas are checked for compatibility in the registry.
  6. After deployment, a few smoke tests run the main journeys.

Example

@ExtendWith(PactConsumerTestExt.class)
@PactTestFor(providerName = "inventory-service")
class InventoryClientPactTest {

    @Pact(consumer = "order-service")
    V4Pact stockForSku(PactDslWithProvider b) {
        return b.given("SKU-1 has 5 units")
                .uponReceiving("get stock")
                .path("/stock/SKU-1").method("GET")
                .willRespondWith().status(200)
                .body(new PactDslJsonBody().stringType("sku", "SKU-1")
                                           .integerType("available", 5))
                .toPact(V4Pact.class);
    }

    @Test
    void readsStock(MockServer server) {
        var client = new InventoryClient(server.getUrl());
        assertThat(client.available("SKU-1")).isEqualTo(5);
    }
}

Common mistakes

  • Treating contracts as full functional tests of the provider rather than of the interface.
  • Consumers asserting on fields they do not use, making contracts over-strict.
  • Publishing contracts but never gating deployment on verification.
  • Keeping a large flaky end-to-end suite "just in case".

How to answer in the interview

"I rely on consumer-driven contract tests with Pact or Spring Cloud Contract. The consumer records exactly which requests it sends and which fields it needs, the contract goes to a broker, and the provider's pipeline verifies it, so breaking changes fail before deployment without any shared environment. Inside each service I run integration tests with Testcontainers for the database and Kafka, and WireMock for HTTP dependencies, including errors and timeouts. Event schemas are checked for compatibility in the registry. Then only a handful of smoke tests run against staging after deployment, because big end-to-end suites are slow and flaky."

Likely follow-up questions

  • Who owns a contract? The consumer defines its needs, but changes are negotiated; the provider must not break verified contracts without coordination.
  • Pact vs Spring Cloud Contract? Pact is consumer-driven and polyglot; SCC fits Spring providers and generates WireMock stubs.
  • What do smoke tests add? They catch deployment, configuration and networking problems that isolated tests cannot.
