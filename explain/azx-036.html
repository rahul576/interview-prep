An application gets 403 errors when reading a Key Vault secret with its managed identity. What do you check?

Azure · scenario · levels mid, senior

In one line

A 403 means authenticated but not authorised, or blocked by the network: check the right identity is used (client ID for user-assigned), the data-plane role (Key Vault Secrets User) under the RBAC model vs access policies, the vault firewall / private endpoint / DNS, and role propagation and token caching delays.

Detailed explanation

Key Vault returns 401 when no valid token was presented and 403 when the caller is known but not allowed, either by permissions or by the network firewall. The error body usually says which: ForbiddenByRbac, ForbiddenByPolicy or ForbiddenByFirewall with the client IP.

1. Identity: Is the managed identity enabled on the app (and on the right slot)? If the app has several user-assigned identities, DefaultAzureCredential may pick the wrong one or none; set ManagedIdentityClientId or AZURE_CLIENT_ID. Locally, DefaultAzureCredential may use a developer account instead, hiding the problem.

2. Permission model: A vault uses either the Azure RBAC model or legacy access policies, not both. With RBAC, the identity needs a data-plane role such as Key Vault Secrets User on the vault or the individual secret. Roles like Contributor or Owner are control-plane only and do not grant reading secret values. With access policies, the identity needs Get on secrets, and RBAC assignments are ignored.

3. Network: If the vault firewall allows only selected networks or private endpoints, the app must come through VNet integration and resolve the vault name to the private endpoint IP via the privatelink.vaultcore.azure.net zone. A missing DNS link makes the app go to the public endpoint and be rejected.

4. Timing: New role assignments can take minutes to propagate, and apps cache tokens (and sometimes failures). Restarting the app or waiting usually confirms this.

How it works

  1. Read the full error: RBAC, policy or firewall.
  2. Verify the identity's object ID used in the token.
  3. Check the vault's permission model and the identity's role or policy.
  4. Check firewall settings, private endpoint and DNS resolution from the app.
  5. Wait for propagation or restart; retest.
  6. Fix in IaC, not by hand.

Example

az keyvault show -n kv-orders-prod --query "{rbac:properties.enableRbacAuthorization, net:properties.networkAcls.defaultAction}"
az role assignment list --assignee <principal-id> --scope $(az keyvault show -n kv-orders-prod --query id -o tsv) -o table
# From the app's Kudu console / SSH:
nslookup kv-orders-prod.vault.azure.net     # should return a 10.x private IP
# Test as the identity without the app:
az login --identity --username <client-id>   # on a VM with that identity
az keyvault secret show --vault-name kv-orders-prod -n SqlPassword

Common mistakes

  • Assigning Contributor and expecting secret access.
  • Adding an access policy to an RBAC-model vault (or vice versa).
  • Ignoring the slot's separate identity.
  • Private endpoint without the DNS zone linked to the app's VNet.

How to answer in the interview

"403 means the request was authenticated but not authorised, or blocked by the vault firewall, and the error text tells you which. I check the identity first: is it enabled, and with several user-assigned identities, is the code passing the right client ID? Then permissions: with the RBAC model it needs a data-plane role like Key Vault Secrets User, Contributor isn't enough; with access policies it needs Get on secrets. Then network: if the vault only allows private endpoints, the app needs VNet integration and correct private DNS. Finally, role assignments take a few minutes to propagate and tokens are cached."

Likely follow-up questions

  • Test permissions without deploying? Use a VM or Cloud Shell with that identity, or az rest with a token for it.
  • RBAC vs access policies? RBAC is recommended: central, PIM-capable, per-secret scope.
  • 401 vs 403? 401 is no or invalid token; 403 is valid token, denied.
