What is a service mesh, and when is it worth the complexity?

Service Mesh · concept · levels senior, lead

In one line

A service mesh (Istio, Linkerd, Cilium) moves service-to-service concerns into proxies, either a sidecar per pod or ambient/node-level proxies, giving mTLS with workload identity, traffic management and uniform observability; it is worth it for many services with strong security or traffic-control needs, and rarely for a handful.

Detailed explanation

In a microservice system every team otherwise reimplements the same things: TLS between services, retries and timeouts, circuit breaking, metrics and tracing headers. A mesh puts a programmable proxy, usually Envoy (Linkerd uses its own Rust micro-proxy), in the path of every request, controlled centrally by a control plane.

What you get:

  • Security: automatic mutual TLS with short-lived certificates tied to the workload's service account (SPIFFE identities), and authorization policies such as "only checkout may call payments on POST /charge". This is the core of zero-trust networking inside the cluster.
  • Traffic management: timeouts, retries with budgets, outlier detection, weighted traffic splitting for canaries, header-based routing, mirroring and fault injection.
  • Observability: golden signals (request rate, errors, latency) per service pair and trace spans, without code changes.

The cost is real. Sidecars add memory and CPU per pod (multiplied across thousands of pods), a little latency per hop, start-up ordering issues, and an upgrade burden because every pod must be restarted to update its proxy. Istio ambient mode addresses this by splitting the mesh: a per-node ztunnel handles L4 mTLS and identity, and optional per-namespace waypoint proxies handle L7 features only where needed, so pods need no sidecar. Before adopting a mesh, ask whether simpler tools suffice: NetworkPolicies for segmentation, a gateway for edge traffic, OpenTelemetry for tracing.

How it works

  1. Install the control plane (istiod, Linkerd control plane).
  2. Enrol namespaces: sidecar injection label or ambient label.
  3. Control plane issues certificates and pushes routing and policy config to proxies.
  4. All pod traffic is transparently redirected through the proxy.
  5. Proxies enforce mTLS, policies and routing and emit telemetry.

Example

apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata: { name: default, namespace: shop }
spec:
  mtls: { mode: STRICT }
---
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata: { name: payments-allow-checkout, namespace: shop }
spec:
  selector: { matchLabels: { app: payments } }
  rules:
  - from:
    - source: { principals: ["cluster.local/ns/shop/sa/checkout"] }

Common mistakes

  • Adopting a mesh for five services because it is fashionable.
  • Retries configured both in the mesh and in application code.
  • Enabling STRICT mTLS before all clients are in the mesh.
  • No plan for proxy upgrades and control plane versioning.

How to answer in the interview

"A service mesh moves networking concerns like mTLS, retries, timeouts, traffic splitting and telemetry out of application code into proxies managed by a control plane, traditionally Envoy sidecars, or in Istio ambient mode a per-node ztunnel plus optional waypoint proxies. It's worth it when you have many services, need zero-trust mTLS with identity-based authorization, and want consistent canaries and observability across teams. For a handful of services, the extra latency, resource use and operational burden usually outweigh the benefits, and NetworkPolicies plus a gateway and OpenTelemetry are enough."

Likely follow-up questions

  • What does ambient mode solve? Sidecar resource overhead, pod restarts for proxy upgrades and start-up ordering problems.
  • Mesh mTLS vs NetworkPolicy? NetworkPolicy filters by IP and labels at L3/L4; mesh authenticates workload identity and can authorise at L7.
  • How do you roll out a mesh safely? Namespace by namespace in permissive mode, then strict.
