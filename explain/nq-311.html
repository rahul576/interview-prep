What is Amazon SQS?

Cloud (AWS) · concept · levels entry

In one line

Amazon SQS is a fully managed message queue that decouples producers and consumers and buffers load; standard queues offer very high throughput with at-least-once delivery and best-effort ordering, FIFO queues give ordering per message group and exactly-once processing with deduplication; key settings are visibility timeout, retention, delay, long polling and dead-letter queues.

Detailed explanation

Producers call SendMessage; SQS stores the message redundantly across availability zones. Consumers poll with ReceiveMessage, process, and then call DeleteMessage. There are no servers or brokers to manage; you pay per request.

Why use it: the producer does not wait for slow processing, the queue absorbs traffic spikes, consumers can scale independently, and failures in consumers do not lose work.

Queue types:

  • Standard: nearly unlimited throughput, at-least-once delivery (occasional duplicates) and best-effort ordering. Consumers must be idempotent.
  • FIFO: strict order within a message group ID, deduplication via a deduplication ID or content hash within a 5-minute window, so exactly-once processing; lower throughput than standard unless high-throughput mode is enabled.

Important settings:

  • Visibility timeout (default 30 s, max 12 h): hides a received message while it is being processed.
  • Retention: default 4 days, up to 14 days.
  • Delay (DelaySeconds, up to 15 minutes) for postponed delivery.
  • Long polling (WaitTimeSeconds up to 20 s) reduces empty responses and cost.
  • Dead-letter queue with maxReceiveCount for messages that keep failing, plus redrive back to the source queue after a fix.
  • Encryption with SSE-SQS or KMS, access via IAM and queue policies.

SQS is a queue, not a log: once deleted, a message is gone, and each message goes to one consumer. For fan-out, combine with SNS or EventBridge.

How it works

  1. Producer sends a message.
  2. Consumer long-polls and receives up to 10 messages.
  3. Messages become invisible for the visibility timeout.
  4. Successful processing deletes them.
  5. Failures reappear and are retried; after maxReceiveCount they go to the DLQ.

Example

aws sqs create-queue --queue-name orders-dlq
aws sqs create-queue --queue-name orders --attributes '{
  "VisibilityTimeout":"120", "ReceiveMessageWaitTimeSeconds":"20",
  "RedrivePolicy":"{\"deadLetterTargetArn\":\"arn:aws:sqs:eu-west-1:123456789012:orders-dlq\",\"maxReceiveCount\":\"5\"}"}'

Common mistakes

  • Non-idempotent consumers on standard queues.
  • Short polling, causing cost and empty receives.
  • No DLQ, so poison messages loop forever.
  • Expecting replay like Kafka.

How to answer in the interview

"SQS is a fully managed message queue. Producers send messages and consumers poll, process and delete them, so the two sides are decoupled and the queue buffers bursts. Standard queues give nearly unlimited throughput with at-least-once delivery and best-effort ordering, so consumers must be idempotent. FIFO queues guarantee order within a message group and exactly-once processing with deduplication, at lower throughput. The key settings are the visibility timeout, retention up to fourteen days, delays, long polling, and a dead-letter queue for messages that keep failing."

Likely follow-up questions

  • SQS or Kafka? SQS for simple managed work queues; Kafka for high-throughput event streams, replay and multiple consumer groups.
  • How to fan out to several consumers? SNS topic or EventBridge rule to multiple queues.
  • Large payloads? Store in S3 and send a reference.
