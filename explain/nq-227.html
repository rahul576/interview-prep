What is the difference between Saga orchestration and choreography?

Microservices · concept · levels senior, lead

In one line

In orchestration a central orchestrator (service or workflow engine like Temporal, Camunda, AWS Step Functions) holds saga state and sends commands; in choreography services react to each other's events with no coordinator; choreography is loosely coupled but implicit, orchestration is explicit and easier to manage but adds a central component.

Detailed explanation

Orchestration. One component owns the saga's logic as an explicit workflow. For an order it sends ChargePayment, waits for PaymentCharged, sends ReserveStock, waits, and so on. On failure or timeout, it sends compensating commands (RefundPayment, CancelOrder). Its state is persisted, so it survives crashes. Benefits: the flow is visible in one place, easy to reason about, test, monitor and change; timeouts, retries and compensations are handled consistently; participants are simpler because they only respond to commands and do not need to know about each other. Workflow engines like Temporal (code-first durable workflows), Camunda (BPMN models), AWS Step Functions, or framework support such as Axon sagas, provide persistence, retries and visual history. Drawbacks: the orchestrator knows all participants, becomes a central component to operate and scale, and there is a risk of moving too much business logic into it, making participants anaemic.

Choreography. There is no coordinator. The order service publishes OrderCreated; payment listens and publishes PaymentCompleted; inventory listens and publishes StockReserved; order listens and confirms. Compensation is also event-driven: inventory publishes StockUnavailable, payment refunds, order cancels. Benefits: loose coupling, no single point of control, easy to add a new listener (analytics) without changing others, and it is simple for two or three steps. Drawbacks: the overall flow is implicit, spread across services' code, so understanding "what happens when an order is placed" requires reading several codebases; it is harder to debug and monitor (you need distributed tracing and process dashboards); adding a step means changing multiple services; and services can develop cyclic event dependencies.

A practical rule: choreography for short, stable flows, orchestration for longer business processes with many steps, timeouts, human tasks or frequent changes. They can also be combined: an orchestrated core process that publishes domain events others choreograph around.

How it works

  1. Orchestration: orchestrator persists state → sends command → awaits reply → next command or compensation.
  2. Choreography: service commits → publishes event → interested services react → publish their own events.
  3. Both: local transactions, outbox publishing, idempotent handlers.
  4. Monitoring: orchestrator history versus tracing and correlation across events.

Example

// Orchestration with Temporal: the whole flow in one place
@WorkflowInterface
public interface OrderWorkflow { @WorkflowMethod void process(Order order); }

public class OrderWorkflowImpl implements OrderWorkflow {
    public void process(Order order) {
        Saga saga = new Saga(new Saga.Options.Builder().build());
        try {
            payments.charge(order);       saga.addCompensation(payments::refund, order);
            inventory.reserve(order);     saga.addCompensation(inventory::release, order);
            shipping.schedule(order);
            orders.confirm(order.id());
        } catch (ActivityFailure e) { saga.compensate(); orders.cancel(order.id()); }
    }
}
Choreography of the same flow:
order: OrderCreated --> payment: PaymentCompleted --> inventory: StockReserved --> order: confirm
                                                      inventory: StockUnavailable --> payment: refund --> order: cancel

Common mistakes

  • Choreographing a ten-step process nobody can follow.
  • Putting all domain logic into the orchestrator.
  • No correlation id across choreographed events.
  • Forgetting timeouts when a participant never responds.

How to answer in the interview

"In orchestration a dedicated orchestrator, a service or a workflow engine like Temporal, Camunda or Step Functions, holds the saga state and tells each participant what to do: charge payment, wait, reserve stock, and on failure send the compensating commands. The flow is explicit in one place and easy to monitor and change, but it is a central component that knows all participants. In choreography there is no coordinator; each service listens to events and reacts. It is loosely coupled and simple for a few steps, but the flow is implicit and spread across services, harder to debug, and can create cyclic dependencies. I use choreography for short flows and orchestration for longer business processes."

Likely follow-up questions

  • How would you monitor a choreographed saga? Correlation ids in all events, distributed tracing, and a process-tracking view that consumes the events.
  • Is the orchestrator a single point of failure? Workflow engines persist state and run clustered, so it can resume after failures.
  • Can you mix both? Yes: orchestrate the core process and let other services react to its events.
