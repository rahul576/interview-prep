What is HashiCorp Packer, and how does it fit with Terraform?

Infrastructure as Code · concept · levels entry

In one line

Packer builds machine images from HCL templates: sources/builders for AMIs, Azure, GCP, VMware or Docker, provisioners (shell, Ansible) to configure, producing versioned golden images that Terraform deploys, enabling immutable infrastructure.

Detailed explanation

Configuring servers after they boot is slow and fragile: package mirrors are down, versions differ between instances, and auto scaling has to wait minutes for configuration to finish. Packer moves that work earlier, into an image build.

A Packer template (HCL2, *.pkr.hcl) has:

  • packer { required_plugins }: plugins such as amazon, azure, googlecompute, vsphere, docker, installed with packer init.
  • source blocks (builders): where to build. For example amazon-ebs launches a temporary EC2 instance from a base AMI.
  • A build block: which sources to use and the provisioners that configure the machine: shell scripts, file uploads, ansible playbooks, or PowerShell for Windows. Typical steps are patching the OS, installing runtimes and agents, CIS hardening and cleanup.
  • post-processors: manifests, compression, uploading or pushing metadata.

Packer then snapshots the machine into an image, such as an AMI named web-2026-11-21-1530, and terminates the temporary instance. One template can build for several platforms in parallel.

Terraform consumes the result: an aws_launch_template or VM resource references the image, usually found with a data source filtering by name, tags and owner, or through HCP Packer channels that track approved versions. Releasing a change means building a new image and rolling instances, for example via an auto scaling group instance refresh, rather than mutating running servers.

The benefits of this immutable infrastructure approach are fast, consistent boots, images that can be scanned and tested before use, easy rollback to the previous image, and far less drift. Runtime-specific settings like secrets and environment configuration still come at boot via user data or a secret manager.

How it works

  1. packer init installs plugins.
  2. packer validate and packer build start a temporary machine from a base image.
  3. Provisioners configure it.
  4. Packer captures an image and tags it.
  5. Terraform looks up the image and rolls instances onto it.

Example

packer {
  required_plugins {
    amazon  = { source = "github.com/hashicorp/amazon", version = ">= 1.3.0" }
    ansible = { source = "github.com/hashicorp/ansible", version = ">= 1.1.0" }
  }
}

source "amazon-ebs" "web" {
  region        = "eu-west-1"
  instance_type = "t3.small"
  ssh_username  = "ubuntu"
  ami_name      = "web-${formatdate("YYYYMMDDhhmm", timestamp())}"
  source_ami_filter {
    filters = { name = "ubuntu/images/hvm-ssd-gp3/ubuntu-noble-24.04-amd64-server-*" }
    owners      = ["099720109477"]
    most_recent = true
  }
  tags = { Role = "web", Approved = "false" }
}

build {
  sources = ["source.amazon-ebs.web"]
  provisioner "shell"   { inline = ["sudo apt-get update", "sudo apt-get -y upgrade"] }
  provisioner "ansible" { playbook_file = "./ansible/web.yml" }
}
data "aws_ami" "web" {
  owners      = ["self"]
  most_recent = true
  filter {
    name   = "tag:Role"
    values = ["web"]
  }
}

Common mistakes

  • Baking secrets or environment-specific config into images.
  • most_recent = true without an approval tag, deploying untested images.
  • Never rebuilding images, so they fall behind on patches.
  • Large manual steps after boot, defeating the purpose.

How to answer in the interview

"Packer builds machine images from an HCL template. A source defines the platform, like an Amazon AMI, Azure image, VMware template or Docker image. Provisioners configure the temporary machine with shell scripts or Ansible, installing packages, hardening and adding agents, and Packer captures the result as a versioned golden image. Terraform then deploys instances or auto scaling groups from those images, usually looking up the latest approved image with a data source. Together that's immutable infrastructure: instead of configuring servers after boot, we bake new images and replace instances, which gives faster and more consistent boots."

Likely follow-up questions

  • How would you automate Packer builds and testing? A scheduled and on-change CI pipeline: validate, build, test (Goss/InSpec), scan, tag as approved, then roll out.
  • Packer vs Dockerfile? Dockerfiles build container images; Packer focuses on VM images across clouds.
  • How do you roll out a new AMI? Update the launch template and run an ASG instance refresh.
