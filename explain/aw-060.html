What is AWS Backup, and how do you design backup plans with it?

Cloud (AWS) · concept · levels mid

In one line

AWS Backup centralises backups across services like EC2, EBS, RDS, Aurora, DynamoDB, EFS, FSx and S3 using backup plans (schedules, retention, lifecycle) assigned by tags, with cross-region and cross-account copies, Vault Lock immutability, restore testing and organisation-wide backup policies.

Detailed explanation

Without AWS Backup, every service has its own snapshot settings and retention, which is hard to audit. AWS Backup provides one control plane. A backup plan contains rules: schedule (cron or frequency), backup window, retention, optional lifecycle to cold storage for supported resources, continuous backup for point-in-time recovery on RDS, Aurora and S3, and copy actions to other vaults.

Resources are attached through resource assignments, ideally by tags such as backup=gold, so anything new and correctly tagged is protected automatically. Different tiers map to different plans: gold might mean hourly continuous backups with 35 days, monthly copies kept seven years, and cross-region copies.

Recovery points live in backup vaults, each encrypted with a KMS key and protected by a vault access policy. The key resilience pattern is a copy to a separate backup account (and often another region), because an attacker or mistake in the production account then cannot delete every copy. Backup Vault Lock in compliance mode makes recovery points immutable and the retention unchangeable, even by root, after a grace period. Logically air-gapped vaults add an isolated, AWS-owned key and sharing option for recovery.

Restore testing runs scheduled restores and validates them, giving evidence that backups work. Backup Audit Manager reports on compliance with controls like minimum retention. With AWS Organizations, backup policies enforce plans across accounts from a delegated administrator.

How it works

  1. Create a vault per tier, KMS-encrypted, with Vault Lock.
  2. Define a backup plan with daily, monthly rules and copy actions.
  3. Assign resources by tag.
  4. Jobs run in the backup window and create recovery points.
  5. Copies go to a vault in the backup account and DR region.
  6. Restore tests run on schedule and report results.

Example

{
  "BackupPlanName": "gold",
  "Rules": [{
    "RuleName": "daily",
    "TargetBackupVaultName": "prod-gold",
    "ScheduleExpression": "cron(0 2 * * ? *)",
    "Lifecycle": {"DeleteAfterDays": 35},
    "CopyActions": [{
      "DestinationBackupVaultArn": "arn:aws:backup:eu-central-1:999900001111:backup-vault:central-gold",
      "Lifecycle": {"DeleteAfterDays": 35}}]
  }, {
    "RuleName": "monthly",
    "TargetBackupVaultName": "prod-gold",
    "ScheduleExpression": "cron(0 3 1 * ? *)",
    "Lifecycle": {"MoveToColdStorageAfterDays": 30, "DeleteAfterDays": 365}
  }]
}
aws backup put-backup-vault-lock-configuration --backup-vault-name central-gold \
  --min-retention-days 7 --max-retention-days 400 --changeable-for-days 3

Common mistakes

  • Keeping all backups in the production account and region.
  • Never testing restores, so failures are discovered during an incident.
  • Missing tags, leaving new databases unprotected.
  • Forgetting cross-account KMS key permissions so copies fail.

How to answer in the interview

"AWS Backup centralises backups for EC2, EBS, RDS, Aurora, DynamoDB, EFS, FSx, S3 and more. A backup plan has rules with schedules and retention, for example daily kept 35 days and monthly kept a year, with lifecycle to cold storage. I assign resources by tag, so new resources are protected automatically. Rules copy recovery points to another region and to a separate backup account to survive account compromise. Vault Lock makes them immutable, restore testing proves they work, and Organizations backup policies enforce it centrally."

Likely follow-up questions

  • Why is a backup in the same account as production not enough? Compromised credentials or a mistake can delete both data and backups.
  • How do you prove recoverability? Scheduled restore testing with validation and documented RTO results.
  • Does AWS Backup replace database PITR? It manages continuous backups for supported engines, giving PITR within the window.
