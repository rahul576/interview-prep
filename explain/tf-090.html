You create private endpoints with Terraform, but applications cannot resolve the private IP addresses. What is missing?

Terraform · scenario · levels mid, senior

In one line

A private endpoint only gives the service a private IP; clients also need a private DNS zone (for example privatelink.blob.core.windows.net) with the A record, a virtual network link to every VNet that resolves it, and forwarding from custom or on-premises DNS to Azure DNS.

Detailed explanation

Clients keep using the public name, such as mystorage.blob.core.windows.net. When private link is enabled, public DNS returns a CNAME to mystorage.privatelink.blob.core.windows.net. If the client's resolver has a private DNS zone for privatelink.blob.core.windows.net containing an A record pointing to the endpoint's private IP, the name resolves privately. Without that zone, the client gets the public IP, and if public access is disabled the connection fails.

In Terraform, the cleanest way to manage the record is the private_dns_zone_group block on azurerm_private_endpoint. It registers the A record in the given zone and removes it when the endpoint is deleted, so you do not manage azurerm_private_dns_a_record by hand.

The zone must also be linked to the virtual networks whose clients resolve through Azure-provided DNS, with azurerm_private_dns_zone_virtual_network_link. In hub-and-spoke designs, the zones usually live centrally in a connectivity subscription and are linked to the hub, with spokes using a DNS server or Azure DNS Private Resolver in the hub.

If VNets use custom DNS servers (for example domain controllers), those servers must forward the privatelink.* zones, or simply everything, to 168.63.129.16, the Azure-provided resolver, from inside a linked VNet. On-premises clients need conditional forwarders pointing to the Private Resolver's inbound endpoint. Many enterprises let Azure Policy create the DNS zone group automatically (DeployIfNotExists) so application teams cannot forget it.

How it works

  1. Create (or reference) the private DNS zone for the service subresource.
  2. Link the zone to the hub VNet and any VNet using Azure-provided DNS.
  3. Create the private endpoint with a private_dns_zone_group referencing the zone.
  4. Configure custom DNS servers to forward to 168.63.129.16, or use the Private Resolver.
  5. Add on-premises conditional forwarders to the resolver's inbound endpoint.
  6. Test with nslookup from a client and confirm the private IP.

Example

resource "azurerm_private_endpoint" "blob" {
  name                = "pe-mystorage-blob"
  location            = var.location
  resource_group_name = var.rg
  subnet_id           = var.pe_subnet_id

  private_service_connection {
    name                           = "blob"
    private_connection_resource_id = azurerm_storage_account.main.id
    subresource_names              = ["blob"]
    is_manual_connection           = false
  }

  private_dns_zone_group {
    name                 = "default"
    private_dns_zone_ids = [var.blob_private_dns_zone_id]
  }
}
nslookup mystorage.blob.core.windows.net
# expect: canonical name mystorage.privatelink.blob.core.windows.net -> 10.20.1.5

Common mistakes

  • Creating the endpoint but no DNS zone, or a zone with no VNet link.
  • Creating duplicate privatelink zones per spoke, so records end up in the wrong zone.
  • Custom DNS servers that forward to public resolvers instead of 168.63.129.16.
  • Using the wrong zone name for the subresource (blob vs dfs vs file).

How to answer in the interview

"The endpoint gives the service a private IP, but clients still resolve the public name, which needs to return that private IP. That requires a private DNS zone such as privatelink.blob.core.windows.net with an A record. In Terraform I use the private_dns_zone_group block on the endpoint, which registers and cleans up the record. The zone needs a virtual network link to the VNets that resolve it, usually the hub. If VNets use custom DNS, those servers forward to 168.63.129.16, and on-premises uses conditional forwarding to a DNS Private Resolver. Often Azure Policy creates the records centrally."

Likely follow-up questions

  • Why centralise private DNS zones in the hub? One zone per service avoids split records and makes resolution consistent for all spokes and on-premises.
  • What does 168.63.129.16 do? It is the Azure-provided virtual IP for DNS and other platform services, reachable only from inside Azure VNets.
  • How do you debug it? nslookup from the client, check for the privatelink CNAME and the private IP.
