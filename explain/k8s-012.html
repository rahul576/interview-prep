What are Pod Security Standards, and how does Pod Security Admission enforce them?

Kubernetes · concept · levels mid, senior

In one line

Pod Security Standards define three profiles, privileged, baseline and restricted; the built-in Pod Security Admission controller, which replaced PodSecurityPolicy (removed in 1.25), enforces them through namespace labels in three modes: enforce, audit and warn.

Detailed explanation

Pod specs can request dangerous powers: privileged mode, host namespaces, hostPath mounts, extra Linux capabilities, running as root. PodSecurityPolicy tried to control this but was confusing (policies chosen via RBAC, mutating defaults) and was removed in 1.25. Its replacement is deliberately simple: three fixed profiles, chosen per namespace.

  • Privileged: no restrictions; for system components such as CNI agents, CSI drivers and node exporters.
  • Baseline: blocks known privilege escalations while staying compatible with most apps: no privileged containers, no hostNetwork, hostPID, hostIPC, no hostPath volumes, no host ports, only a default set of capabilities, no unsafe sysctls.
  • Restricted: baseline plus hardening: runAsNonRoot: true, allowPrivilegeEscalation: false, capabilities.drop: [ALL] (only NET_BIND_SERVICE may be added), a seccompProfile of RuntimeDefault or Localhost, and limited volume types.

Pod Security Admission (PSA) reads labels on the namespace:

  • pod-security.kubernetes.io/enforce=<level> rejects violating pods.
  • .../audit=<level> records violations in the API audit log.
  • .../warn=<level> returns warnings to the client (kubectl shows them).

Each can be pinned with ...-version labels. Checks apply to pods and also warn on workload templates such as Deployments, so you see problems at apply time rather than when pods fail to be created.

PSA cannot express custom rules (allowed registries, required labels, resource limits) and cannot mutate. For that you add ValidatingAdmissionPolicy, Kyverno or OPA Gatekeeper.

How it works

  1. Label all namespaces warn=restricted and audit=restricted.
  2. Collect warnings and audit events; fix workloads' securityContext.
  3. Set enforce=baseline everywhere, then enforce=restricted where ready.
  4. Keep privileged only for system namespaces, documented.
  5. Cluster-wide defaults and exemptions via the AdmissionConfiguration file.

Example

kubectl label ns shop pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/warn=restricted --overwrite
kubectl label --dry-run=server --overwrite ns --all pod-security.kubernetes.io/enforce=baseline
securityContext:
  runAsNonRoot: true
  allowPrivilegeEscalation: false
  capabilities: { drop: [ALL] }
  seccompProfile: { type: RuntimeDefault }

Common mistakes

  • Switching straight to enforce and breaking deployments.
  • Labelling kube-system restricted and breaking CNI or CSI pods.
  • Expecting PSA to mutate pods into compliance.
  • Leaving namespaces without any labels (cluster default often privileged).

How to answer in the interview

"Pod Security Standards define three profiles: privileged with no restrictions, baseline that blocks known escalations like privileged containers, hostNetwork and hostPath, and restricted that also requires non-root, no privilege escalation, dropping all capabilities and a seccomp profile. Pod Security Admission is the built-in controller that replaced PodSecurityPolicy, configured with namespace labels in three modes: enforce rejects, audit logs and warn shows warnings. I roll out with warn and audit first, fix workloads, then enforce, keeping privileged only for system namespaces."

Likely follow-up questions

  • Rules PSA can't express? Use ValidatingAdmissionPolicy, Kyverno or Gatekeeper.
  • How do you find violations before enforcing? Server-side dry-run labelling shows warnings for existing pods.
  • Why did PSP get removed? Confusing authorisation model, mutation surprises and hard-to-predict policy selection.
