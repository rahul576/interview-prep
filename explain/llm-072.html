How do you test application code that calls LLMs?

LLMOps & RAG · concept · levels mid, senior

In one line

Separate deterministic logic from model quality: unit tests with a mocked model client cover prompt construction, parsing and error handling; contract tests cover structured outputs and fallbacks; integration tests use recorded responses or a small local model; an evaluation suite with real models checks quality with thresholds, never exact text matches.

Detailed explanation

Code that calls an LLM has two very different parts. Most of it is ordinary code that can and should be tested deterministically; the model's behaviour is probabilistic and needs evaluation, not assertions on strings.

Unit tests (mocked client). Replace the model client with a fake that returns scripted responses. Test that prompts are built correctly from inputs (variables filled, right context and tools included, token budget respected), that outputs are parsed and validated, and that errors are handled: timeouts, 429s, refusals, empty content, malformed JSON, unexpected tool calls, truncated output due to max tokens. Snapshot tests of rendered prompts catch accidental template changes.

Contract tests. Verify that structured outputs map to your types and that invalid outputs trigger the right behaviour (retry with error feedback, fallback, user-facing error). Also check tool schemas generated from code match expectations.

Integration tests. Exercise the whole flow (API, retrieval, model client, tool execution) cheaply and reproducibly using recorded real responses (VCR-style cassettes, WireMock stubs) or a small local model via Ollama or Testcontainers. Assertions target structure and flow, not wording.

Evaluation suite. Runs against the real model with realistic inputs, scoring outputs with deterministic checks and judges, in CI or nightly, with thresholds (for example 95% schema-valid, groundedness 0.9 or above). Outputs vary between runs and model versions, so exact-text assertions produce flaky tests and false confidence.

How it works

  1. Wrap model access behind an interface.
  2. Unit test logic with a fake implementation.
  3. Contract test schemas and invalid-output handling.
  4. Integration test with recordings or a local model.
  5. Evaluate quality with real models against thresholds.
  6. Refresh recordings when prompts or models change.

Example

@Test
void fallsBackWhenModelReturnsInvalidJson() {
    ChatModel fake = prompt -> new ChatResponse(List.of(
        new Generation(new AssistantMessage("Sure! Here is the data: {category: billing"))));
    var classifier = new TicketClassifier(ChatClient.builder(fake).build());

    Classification c = classifier.classify("I was charged twice");

    assertThat(c.category()).isEqualTo("unknown");   // graceful fallback
    assertThat(c.needsHumanReview()).isTrue();
}

Common mistakes

  • Asserting exact sentences from real model outputs.
  • Only end-to-end tests against the live API: slow, costly, flaky.
  • No tests for refusals, truncation or malformed outputs.
  • Stale recordings that no longer reflect real model behaviour.

How to answer in the interview

"I separate what's deterministic from model quality. Unit tests mock the model client and check our logic: how prompts are built, that the right context and tools are included, how outputs are parsed and validated, and how timeouts, refusals and malformed responses are handled. Contract tests make sure structured outputs map to our types and invalid ones trigger retries or fallbacks. Integration tests replay recorded responses or use a small local model to run the full flow cheaply. Quality is checked separately by an evaluation suite against the real model with thresholds. I never assert exact text from a real model, because outputs vary."

Likely follow-up questions

  • Keep recordings current? Re-record on prompt or model changes, flagged automatically in CI.
  • Testing agents? Fake tools and scripted model turns; trajectory evals with real models.
  • Cost of eval runs? Smaller subset per PR, full suite nightly.
