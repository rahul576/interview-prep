What is the difference between COPY and ADD in a Dockerfile?

Docker · concept · levels entry

In one line

Both copy files into the image, but COPY only copies from the build context (or another stage), while ADD also auto-extracts local tar archives and can fetch remote URLs (and git repos); prefer COPY for predictability, and use --chown (and --chmod) to set ownership for non-root users.

Detailed explanation

COPY src dest does exactly one thing: copy files or directories from the build context into the image. With COPY --from=build /out/app /app it copies from an earlier stage of a multi-stage build or from another image.

ADD src dest does the same plus extra magic:

  • If the source is a local tar archive (plain, gzip, bzip2 or xz), it is automatically extracted into the destination. Handy when you really want that, surprising when you just wanted to copy app.tar.gz as a file.
  • If the source is a URL, Docker downloads it. Remote archives are not extracted.
  • With BuildKit it can also add a git repository (ADD https://github.com/org/repo.git#v1.2 /src) and verify HTTP downloads with --checksum=sha256:….

Why the official best practice is "prefer COPY":

  1. Predictability: the extraction rule depends on the file type, so behaviour can change silently.
  2. Download risks: a URL's content can change or be tampered with. Without a checksum you get whatever the server returns, the layer may not be cached reliably, and you cannot clean up in the same layer (the downloaded archive stays in the image).
  3. Better alternatives: RUN curl -fsSL … -o /tmp/x.tgz && echo "<sha256> /tmp/x.tgz" | sha256sum -c - && tar -xzf /tmp/x.tgz -C /opt && rm /tmp/x.tgz verifies and cleans up in one layer, or download in a builder stage and COPY --from.

Ownership: files are copied as root by default. COPY --chown=app:app target/app.jar /app/ (and --chmod=0755) sets ownership and mode in the same step, avoiding a separate RUN chown -R, which would duplicate the files in a new layer and double the size.

How it works

  1. COPY: read files from context/stage → write to image layer.
  2. ADD local tar: detect archive → extract into dest.
  3. ADD URL: download → place file (optionally verify checksum).
  4. --chown/--chmod apply ownership and permissions as the layer is written.

Example

FROM eclipse-temurin:21-jre
RUN useradd -r -u 10001 app
# Preferred: explicit copy with ownership
COPY --chown=app:app target/app.jar /app/app.jar
# Legitimate ADD: unpack a vendored local archive
ADD vendor/agent-1.8.tar.gz /opt/agent/
# Remote download with integrity check (BuildKit)
ADD --checksum=sha256:4f3c...e9a1 https://example.com/tools/cli-2.3.tar.gz /tmp/cli.tar.gz
USER app
ENTRYPOINT ["java", "-jar", "/app/app.jar"]

Common mistakes

  • Using ADD everywhere out of habit.
  • ADD of a remote URL without --checksum, trusting whatever is downloaded.
  • RUN chown -R after COPY, doubling layer size.
  • Expecting remote archives to be extracted by ADD.

How to answer in the interview

"Both copy files into the image. COPY simply copies from the build context or another stage, which is explicit and predictable. ADD also auto-extracts local tar archives and can download from a URL or a git repo. Because of those surprises, best practice is to prefer COPY and use ADD only when I actually want a local archive extracted. For downloads I use RUN with curl and checksum verification, or a builder stage, so I can verify and clean up in the same layer; with BuildKit, ADD --checksum is acceptable. Both support --chown, like COPY --chown=app:app app.jar /app/, to set ownership for a non-root user."

Likely follow-up questions

  • Why is ADD from a URL risky? Unverified, mutable content and poor caching; use checksums.
  • Why not RUN chown afterwards? It creates a new layer with a full copy of the files.
  • Can COPY copy from another image? Yes, COPY --from=image:tag /path /dest.
