What are OAuth 2.0 and JWT, and how are they used for authentication?

Security · concept · levels mid

In one line

OAuth 2.0 is an authorization framework in which a client obtains an access token from an authorization server to call a resource server; OpenID Connect adds authentication with an ID token; a JWT is a signed token format (header, claims, signature) that APIs can validate statelessly.

Detailed explanation

OAuth 2.0 defines four roles: the resource owner (the user), the client (the app acting for the user), the authorization server (Keycloak, Okta, Entra ID, Auth0, Spring Authorization Server) and the resource server (your API). Instead of giving the app a password, the user authenticates at the authorization server, and the app receives an access token limited by scopes and lifetime.

The main grant types: authorization code with PKCE for web, single-page and mobile apps; client credentials for service-to-service with no user; refresh token to obtain new access tokens; and device code for TVs and CLIs. The implicit and password grants are deprecated and removed in OAuth 2.1.

OAuth itself does not say who the user is. OpenID Connect adds that: with the openid scope the client also gets an ID token describing the authenticated user, meant for the client, not for APIs.

A JWT (RFC 7519) is often the format of both tokens: three base64url parts, a header (alg, kid), a payload of claims (sub, iss, aud, exp, iat, scope) and a signature. The API fetches the issuer's public keys from the JWKS endpoint and verifies tokens locally, with no call per request. Access tokens may also be opaque, in which case the API calls the introspection endpoint. Because JWTs are signed but not encrypted, keep them short-lived, never put secrets in them, and rely on refresh tokens for long sessions.

How it works

  1. Client redirects the user to the authorization server with scopes and a PKCE challenge.
  2. User authenticates and consents; client receives an authorization code.
  3. Client exchanges the code plus PKCE verifier for access, refresh and (with OIDC) ID tokens.
  4. Client calls the API with Authorization: Bearer <access token>.
  5. API verifies signature and claims, then authorises on scopes and roles.
  6. When the access token expires, the client uses the refresh token.

Example

Header : {"alg":"RS256","kid":"2026-key-1","typ":"JWT"}
Payload: {"iss":"https://login.example.com/realms/shop","sub":"user-42",
          "aud":"orders-api","scope":"orders.read orders.write",
          "iat":1763700000,"exp":1763700600}
Signature: RS256(base64url(header) + "." + base64url(payload), privateKey)
# client credentials grant for a backend job
curl -s https://login.example.com/realms/shop/protocol/openid-connect/token \
  -d grant_type=client_credentials -d client_id=report-job \
  -d client_secret="$SECRET" -d scope=orders.read

Common mistakes

  • Calling OAuth an authentication protocol.
  • Using the ID token as an API access token.
  • Not checking aud, so tokens for other APIs are accepted.
  • Long-lived access tokens and sensitive data in claims.

How to answer in the interview

"OAuth 2.0 is an authorization framework. A client application obtains an access token from an authorization server, like Keycloak or Entra ID, to call APIs, the resource servers, on behalf of a user or itself. I use authorization code with PKCE for user-facing apps and client credentials between services. OAuth alone isn't authentication; OpenID Connect adds that with an ID token for the client. A JWT is the usual token format: header, claims such as sub, iss, aud, exp and scope, and a signature. APIs verify it with the issuer's public keys without calling back, so it's stateless. I keep tokens short-lived with refresh tokens and never put secrets in the payload, because it's only encoded."

Likely follow-up questions

  • How do you revoke a JWT before it expires? Short lifetimes, revoke refresh tokens, a jti deny-list, or opaque tokens with introspection.
  • Opaque vs JWT access token? Opaque needs introspection (revocable, private); JWT validates locally.
  • What is PKCE? A per-request code verifier and challenge that stops a stolen authorization code from being redeemed.
