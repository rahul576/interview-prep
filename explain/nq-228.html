How does event-driven choreography work?

Microservices · concept · levels mid

In one line

In event-driven choreography each service does its own local transaction, then publishes a domain event; other services subscribe and react with their own local work, so the business flow emerges from events instead of a central coordinator.

Detailed explanation

Choreography is one of the two ways to implement a saga (the other is orchestration). There is no service that "runs" the order process. The order service saves an order in state PENDING and publishes OrderCreated to a broker such as Kafka. The payment service consumes it, charges the card in its own database transaction and publishes PaymentCompleted or PaymentFailed. Inventory listens for PaymentCompleted, reserves stock and publishes StockReserved. The order service listens to the outcome events and moves the order to CONFIRMED or CANCELLED.

The broker decouples producers and consumers: the order service does not know who listens, services can be down for a while and catch up from the log, and a new consumer (say, a loyalty-points service) can be added without changing existing code. Failures are handled by compensation: when PaymentFailed arrives, the order service cancels the order; if stock reservation fails after payment, a StockFailed event makes payment issue a refund.

The price of this loose coupling is visibility. The flow is spread across many services, so you need correlation ids (usually the order id) on every event and distributed tracing to see where a given order is stuck. Reliability also needs discipline: events must be published with the transactional outbox, because a crash between commit and publish would silently break the chain, and consumers must be idempotent, since Kafka delivers at least once.

How it works

  1. Order service commits the order (PENDING) and an outbox row in one transaction.
  2. A relay publishes OrderCreated with key = orderId and a correlation id header.
  3. Payment consumes it, checks whether this event id was already processed, charges, and publishes PaymentCompleted or PaymentFailed via its own outbox.
  4. Inventory reacts to PaymentCompleted and publishes StockReserved or StockFailed.
  5. Order service updates its status from outcome events; failure events trigger compensations.
  6. Timeouts or a reconciliation job flag orders stuck in PENDING.

Example

@KafkaListener(topics = "orders.events")
public void on(OrderCreated e, @Header("eventId") String eventId) {
    if (processed.existsById(eventId)) return;          // idempotency
    PaymentResult r = gateway.charge(e.orderId(), e.amount());
    outbox.save(r.ok()
        ? new PaymentCompleted(e.orderId())
        : new PaymentFailed(e.orderId(), r.reason()));
    processed.save(new ProcessedEvent(eventId));        // same transaction
}

Common mistakes

  • Publishing the event outside the database transaction (dual write).
  • Non-idempotent consumers that charge twice on redelivery.
  • No correlation id, so nobody can trace a broken flow.
  • Cyclic event chains that become impossible to reason about as steps grow.

How to answer in the interview

"In choreography each service does its local transaction and publishes a domain event, and other services react to it. For an order, the order service publishes OrderCreated, payment charges and publishes PaymentCompleted or PaymentFailed, inventory reserves stock, and the order service updates the status from those outcomes. Failures trigger compensations, like cancelling the order on PaymentFailed. No service calls another directly; Kafka decouples them. To make it reliable I publish through an outbox, make every consumer idempotent and carry the order id as a correlation id for tracing. For long flows with many steps I would switch to orchestration."

Likely follow-up questions

  • What happens if the same event is delivered twice? The consumer checks a processed-event table or uses a natural idempotent update, so the second delivery is a no-op.
  • When would you prefer orchestration? When the flow has many steps, branches or timeouts and you want its state in one place.
  • How do you keep event order per order? Use the order id as the Kafka message key so all its events land on one partition.
