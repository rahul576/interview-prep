A pod is stuck in CrashLoopBackOff. How do you troubleshoot it?

Kubernetes · scenario · levels mid, senior

In one line

CrashLoopBackOff means the container keeps exiting and the kubelet waits longer between restarts; investigate with kubectl describe pod (events, last state, exit code, reason), kubectl logs --previous, then check OOMKilled/137, config, secrets and env vars, probes, image and command, and dependencies, using kubectl debug when needed.

Detailed explanation

CrashLoopBackOff is a state, not a cause. The container started, exited (for whatever reason), and with restartPolicy: Always the kubelet restarts it with exponential back-off (10 s, 20 s, 40 s… up to five minutes). The job is to find out why it exits.

Describe first. kubectl describe pod shows events (image pulls, probe failures, mounts) and the container's Last State: Terminated with a reason and exit code.

  • 137 / OOMKilled: exceeded its memory limit; check limits and actual usage.
  • 137 without OOMKilled: killed by SIGKILL, often after a failed liveness probe or a grace period expiring.
  • 1 or other application codes: the app failed; read the logs.
  • 126/127: command not executable or not found, a wrong entrypoint or missing binary.

Logs of the crashed instance. kubectl logs POD -c CONTAINER --previous shows output from the last crashed run; the current one may have just started and be empty.

Common causes.

  • Missing or wrong ConfigMap, Secret or environment variable (the app exits on startup validation).
  • A dependency unreachable: database, DNS name, credentials, network policy blocking egress.
  • Wrong command/args or image tag, architecture mismatch (exec format error for ARM vs x86).
  • A liveness probe too aggressive for start-up time.

Interactive debugging. kubectl debug can add an ephemeral container to the pod or create a copy with a different command (for example sleep) so you can inspect the filesystem, environment and network.

How it works

  1. kubectl get pod → restarts count and status.
  2. kubectl describe pod → reason, exit code, events.
  3. kubectl logs --previous → application error.
  4. Check config, secrets, probes, resources, image and command.
  5. Reproduce with kubectl debug or a copy that sleeps.
  6. Fix, redeploy, watch restarts stop.

Example

kubectl describe pod api-7d9f -n shop | sed -n '/Last State/,/Ready/p'
kubectl logs api-7d9f -n shop -c api --previous
kubectl get events -n shop --field-selector involvedObject.name=api-7d9f
kubectl debug api-7d9f -n shop -it --copy-to=api-debug --container=api -- sh

Common mistakes

  • Reading current logs instead of --previous.
  • Raising memory limits without checking for a leak or JVM settings.
  • Ignoring exit code and reason in describe.
  • Deleting the pod repeatedly, hoping it fixes itself.

How to answer in the interview

"CrashLoopBackOff means the container keeps exiting and the kubelet is backing off between restarts, so I need to find why it exits. First kubectl describe pod for events, the last state, exit code and reason: 137 with OOMKilled means it hit its memory limit, 1 is usually an application error, 127 a wrong command. Then kubectl logs with previous to see the crashed run's output. Common causes are a missing ConfigMap, Secret or env var, an unreachable dependency, a wrong command or image, or a liveness probe killing a slow starter. If needed I use kubectl debug or a copy that just sleeps to inspect interactively."

Likely follow-up questions

  • Logs empty and exit code 0? The main process finished: a script or one-shot command, or a daemon forking into the background; it needs a long-running foreground process.
  • What's ImagePullBackOff instead? The image cannot be pulled: wrong name or tag, missing registry credentials or no network.
  • How do you catch OOMs early? Monitor working-set memory against limits and alert on OOMKilled events.
