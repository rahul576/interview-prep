An internal assistant showed an employee content from an HR document they are not allowed to see. What went wrong, and what do you do?

LLMOps & RAG · scenario · levels senior, lead

In one line

This is a data protection incident: contain it, assess exposure from logs, involve security, HR and privacy for notification; the root cause is usually retrieval that didn't enforce document permissions (index built with an all-seeing service account, or stale ACLs), fixed by ACL metadata on every chunk, per-user filtering and permission sync.

Detailed explanation

Respond first. Disable the affected source or the assistant itself, preserve logs, and use query, retrieval and response logs to find which documents were exposed, to whom and since when. Involve the security team, HR (the data owner) and the data protection officer; under GDPR, a personal data breach may need to be reported to the supervisory authority within 72 hours of becoming aware, unless it is unlikely to result in a risk to individuals, and affected people may need to be informed. That decision belongs to the privacy function, not the engineering team.

Root causes. The classic one: ingestion used a service account with read access to everything, and retrieval returned chunks without checking whether the requesting user could see them. Sometimes the team relied on the system prompt ("don't reveal HR content"), which is not access control. Another cause is stale permissions: the document was restricted or the employee's group membership changed after indexing, and ACLs were never re-synced. Less often: a misconfigured filter (wrong group IDs, missing nested group expansion) or a shared cache returning another user's answer.

Fix. Store access control metadata (allowed users and groups) with every chunk at ingestion. At query time, resolve the user's identity and group memberships from the IdP and apply a security filter in the search query, before ranking, never after generation. Sync permission changes quickly, ideally from the source's change feed. Exclude highly sensitive sources (HR cases, salaries, legal) unless there is a clear need. Make response caches user-scoped.

How it works

  1. Contain: disable source/assistant; preserve evidence.
  2. Assess: logs show which chunks were returned to which users.
  3. Notify per privacy officer's decision.
  4. Fix ingestion: capture ACLs per document.
  5. Fix retrieval: filter by user and group IDs.
  6. Test with accounts of different access levels before re-enabling; audit regularly.

Example

groups = idp.get_transitive_groups(user.id)       # include nested groups
results = search_client.search(
    query,
    filter=f"allowed_principals/any(p: search.in(p, '{user.id},{','.join(groups)}'))",
    top=20,
)

Common mistakes

  • Treating it as a prompt bug rather than an access-control failure.
  • Filtering results after generation, when the content is already in the prompt.
  • Ignoring permission changes after initial indexing.
  • Indexing everything "because it might be useful".

How to answer in the interview

"First I treat it as a data breach: contain it by disabling the source or assistant, use the retrieval logs to see what was exposed to whom, and bring in security, HR and the privacy officer to decide on notification. The usual root cause is that ingestion used a service account that can read everything and retrieval didn't filter by the user's permissions, or permissions changed after indexing and were never synced. The fix is ACL metadata on every chunk, a security filter on every query using the user's identity and groups, fast permission sync, and excluding highly sensitive sources. Before re-enabling, I test with accounts at different access levels."

Likely follow-up questions

  • Sources to exclude entirely? HR case files, salaries, legal matters, security incident data, board papers.
  • How to test permissions continuously? Synthetic test users with known access, automated canary queries.
  • Why not rely on the prompt? Prompts can be bypassed; the model can't leak what it never receives.
