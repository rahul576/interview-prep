How would you safely expose kubectl or other CLI tools to an AI agent through MCP?

MCP Servers · design · levels mid, senior

In one line

Never expose a generic run_command or raw kubectl tool; build specific, validated tools (list_pods, get_pod_logs, describe_deployment) using the Kubernetes API client without shell interpolation, read-only by default under a scoped RBAC service account, with separate, approved mutating tools, audit logging, and truncated, secret-filtered output.

Detailed explanation

A tool that passes model-generated strings to a shell (run_command("kubectl " + args)) is dangerous: command injection (; rm -rf, $(curl …)) and destructive commands such as kubectl delete namespace prod become one hallucination or one prompt injection away. Logs, tickets or web pages the agent reads can contain instructions designed to trigger exactly that.

Specific tools. Expose the operations agents actually need: list_pods(namespace, label_selector), get_pod_logs(namespace, pod, container, since_minutes, tail_lines), describe_deployment(namespace, name), get_events(namespace, since_minutes). Parameters are validated (namespace allowlist, Kubernetes name regex, bounded numbers) and executed through the Kubernetes API client library, or at least subprocess with argument arrays and no shell, so nothing is interpolated.

Least privilege. The server runs with its own service account whose RBAC Role allows only get, list and watch on needed resources in permitted namespaces, and explicitly not secrets. Even if the model or server misbehaves, the cluster refuses anything more. For per-user accountability, use impersonation or user-scoped tokens where possible.

Mutating tools such as rollout_restart(namespace, deployment) or scale_deployment(namespace, deployment, replicas) are separate, annotated destructive, restricted to non-production or allowlisted namespaces and bounded values (replicas 1–10), use a separate, more privileged identity, and require human approval in the host. Production changes may go through GitOps pull requests instead.

Audit and output hygiene. Log every call with user identity, arguments, result and correlation id. Truncate logs (tail lines, time windows) and filter secrets: redact tokens, passwords and keys in log lines, and never return environment variables or Secret contents.

How it works

  1. Define a minimal tool set from real troubleshooting tasks.
  2. Validate inputs; call the Kubernetes API, never a shell.
  3. Bind a read-only Role in allowed namespaces; deny Secrets.
  4. Put write tools behind a separate identity, limits and host approval.
  5. Redact and truncate outputs; audit every call.

Example

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { name: mcp-readonly, namespace: payments-staging }
rules:
  - apiGroups: [""]
    resources: [pods, pods/log, events, services]
    verbs: [get, list, watch]
  - apiGroups: [apps]
    resources: [deployments, replicasets]
    verbs: [get, list, watch]
NAME = re.compile(r"^[a-z0-9]([-a-z0-9]*[a-z0-9])?$")

@mcp.tool(annotations={"readOnlyHint": True})
def get_pod_logs(namespace: str, pod: str, tail_lines: int = 200) -> str:
    """Last lines of a pod's logs (max 500) in an allowed namespace. Secrets are redacted."""
    if namespace not in ALLOWED_NS or not NAME.match(pod):
        raise ToolError(f"Namespace must be one of {sorted(ALLOWED_NS)} and pod a valid name.")
    text = core_v1.read_namespaced_pod_log(pod, namespace, tail_lines=min(tail_lines, 500))
    audit.log(user=current_user(), tool="get_pod_logs", ns=namespace, pod=pod)
    return redact_secrets(text)

Common mistakes

  • shell=True with model-provided strings.
  • Using a cluster-admin kubeconfig for the server.
  • Granting get on Secrets "for debugging".
  • Mutating tools without approval or namespace limits.
  • Returning entire, unredacted logs.

How to answer in the interview

"I wouldn't expose a generic run_command or kubectl tool, because command injection or a destructive command becomes one hallucination or prompt injection away. Instead I'd build specific tools like list_pods, get_pod_logs, describe_deployment and get_events, with validated parameters, calling the Kubernetes API client with no shell interpolation. They're read-only by default, and the server's service account has RBAC for only get, list and watch in permitted namespaces, no Secrets. Mutating tools like rollout_restart or scale are separate, marked destructive, limited to allowed namespaces and need human approval. Every call is audited with user identity, and logs are truncated and filtered for secrets."

Likely follow-up questions

  • Keeping secrets out of model context? No access to Secrets via RBAC, redaction of log lines, and never returning env vars.
  • Production changes? Prefer GitOps PRs generated by the agent and approved by humans.
  • Per-user identity? Kubernetes impersonation or OIDC tokens so audit logs show the real user.
