What is in-place pod resize, and how does it change vertical scaling with the VPA?

Kubernetes · concept · levels mid, senior, lead

In one line

In-place pod resize makes a running pod's CPU and memory requests and limits mutable through the resize subresource, without recreating the pod; it is GA in Kubernetes 1.35. Each container's resizePolicy says whether a change needs a restart, and the VPA can now apply recommendations in place instead of evicting pods.

Detailed explanation

Historically, resources in a pod spec were immutable. Changing them meant a new pod: the VPA evicted pods to apply recommendations, which caused restarts, cold caches and disruption for stateful or slow-starting workloads. In-place resize (KEP-1287), alpha in 1.27, beta in 1.33 and stable in 1.35, changes that.

How it works:

  • You patch the pod's resize subresource (kubectl patch --subresource resize), not the main spec. The desired values go in spec.containers[].resources; the actually applied values appear in status.containerStatuses[].resources.
  • The kubelet checks whether the node has room. If yes, it updates the container's cgroup limits through the runtime. If not right now, the resize is deferred; if it can never fit (larger than the node), it is infeasible. These states appear as pod conditions (PodResizePending, PodResizeInProgress), and the kubelet never evicts other pods to make room.
  • resizePolicy per resource: NotRequired (default) changes values live; RestartContainer restarts just that container, sensible for memory in runtimes such as the JVM or Node.js that size heaps at start-up.
  • QoS class cannot change through a resize, and decreasing memory limits is handled cautiously because the kernel cannot reclaim memory the process still uses.

For the Vertical Pod Autoscaler, this enables an in-place update mode (InPlaceOrRecreate) that tries a live resize first and falls back to eviction only when necessary. That makes vertical scaling practical for databases, caches and JVM services, and enables patterns like boosting CPU during start-up and lowering it afterwards.

How it works

  1. Patch the pod's resize subresource with new requests/limits.
  2. API server validates (no QoS change, within LimitRange and quota).
  3. Kubelet checks node allocatable.
  4. Fits → runtime updates cgroups, or restarts the container per resizePolicy.
  5. Doesn't fit → deferred or infeasible condition; retried later.
  6. Status shows the applied resources.

Example

containers:
- name: api
  image: registry.example.com/api:5.1
  resources:
    requests: { cpu: 500m, memory: 1Gi }
    limits:   { cpu: "1",  memory: 1Gi }
  resizePolicy:
  - { resourceName: cpu, restartPolicy: NotRequired }
  - { resourceName: memory, restartPolicy: RestartContainer }
kubectl patch pod api-7c9d --subresource resize --type merge \
  -p '{"spec":{"containers":[{"name":"api","resources":{"requests":{"cpu":"1"},"limits":{"cpu":"2"}}}]}}'
kubectl get pod api-7c9d -o jsonpath='{.status.containerStatuses[0].resources}'

Common mistakes

  • Patching the pod spec directly instead of the resize subresource.
  • Expecting a resize to evict neighbours to make room.
  • Resizing memory live for apps whose heap is fixed at start-up.
  • Forgetting the Deployment template still holds the old values for new pods.

How to answer in the interview

"In-place pod resize lets you change CPU and memory requests and limits of a running pod without recreating it. It's stable since 1.35 and works through the resize subresource. Each container has a resizePolicy: NotRequired changes cgroup values live, while RestartContainer restarts only that container, which suits memory for JVMs. If the node lacks capacity the resize is marked deferred or infeasible instead of evicting anything. That makes the VPA much more useful, because it can apply recommendations in place rather than evicting pods, which matters for stateful and slow-warming workloads."

Likely follow-up questions

  • Why not run VPA and a CPU-based HPA together? They react to the same signal and fight; combine VPA on memory with HPA on a custom metric.
  • Does a resize change the Deployment? No, only that pod; new pods use the template.
  • Can QoS class change? No, resizes that would change QoS are rejected.
