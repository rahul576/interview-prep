How would you investigate an API that works correctly in development but is slow in production?

Troubleshooting · scenario · levels senior, lead

In one line

The code is the same, so look for what differs: data volume and distribution (execution plans on production-sized data, missing indexes, stale statistics), real load and concurrency (pool exhaustion, GC, CPU throttling), network path and infrastructure (cross-zone latency, DNS, TLS, proxies, WAF), downstream services and configuration, located with tracing and APM.

Detailed explanation

"Works on my machine but slow in production" is almost never about the code itself. Development environments typically have a thousand rows, one user, local services and generous resources. Production has fifty million rows, five hundred concurrent requests, real network hops and tight container limits.

Data: the most common cause. A query that does a sequential scan over 1,000 rows in 1 ms takes seconds over 50 million. Run EXPLAIN (ANALYZE, BUFFERS) against production-sized data (a read replica or anonymised copy) and compare with development. Look for missing indexes, indexes not used because of functions or type mismatches, stale statistics after large data loads, data skew, N+1 queries that multiply with collection sizes, and endpoints returning unbounded results.

Tracing and APM: find which span is slow in production: database, a downstream call, application code, or time spent waiting before work even started (queueing, pool acquisition).

Network and infrastructure: the app and database may be in different availability zones; each round trip adds latency, multiplied by chatty access patterns. Check DNS resolution time (no caching, ndots search domains in Kubernetes), TLS handshakes on every call because connection pooling or keep-alive is off, service mesh sidecars, WAFs, API gateways and proxies that exist only in production.

Concurrency and resources: under real load, Hikari or HTTP client pools may be exhausted, thread pools queue, GC runs more often with production heap sizes and allocation rates, and Kubernetes CPU limits cause CFS throttling, adding tens or hundreds of milliseconds even at moderate average CPU. Check container_cpu_cfs_throttled_periods_total.

Configuration: different log levels (DEBUG logging synchronously), pool sizes, timeouts, JVM flags, feature flags, disabled caches, connection to a remote rather than local cache.

How it works

  1. Confirm where time is spent with production traces.
  2. Compare execution plans with production-like data.
  3. Check network path: zones, DNS, TLS reuse, proxies.
  4. Check saturation: pools, threads, GC, CPU throttling.
  5. Diff configuration between environments.
  6. Reproduce with production-like data and load in staging.

Example

-- Dev (2k rows): Index Scan, 0.4 ms. Prod (48M rows):
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM events WHERE lower(email) = 'asha@example.com';
-- Seq Scan on events (actual time=0.03..3120.5 rows=3) Buffers: read=612,004
-- the index is on email, not lower(email)
CREATE INDEX CONCURRENTLY idx_events_email_lower ON events (lower(email));
ANALYZE events;
# CPU throttling ratio per pod
rate(container_cpu_cfs_throttled_periods_total{pod=~"orders-.*"}[5m])
  / rate(container_cpu_cfs_periods_total{pod=~"orders-.*"}[5m])

Common mistakes

  • Profiling locally with tiny data and concluding the code is fine.
  • Ignoring the network: chatty calls across zones or without connection reuse.
  • Assuming low average CPU means no CPU problem, missing throttling.
  • Running production with DEBUG logging or development-sized pools.

How to answer in the interview

"Since the code is identical, I look for what's different. Production usually has far more data, so a query that's instant on a thousand rows does a full scan on fifty million; I compare the execution plan on production-sized data and check for missing indexes and stale statistics. I use tracing or APM to find the slow span: database, downstream service or the app. I check network latency between zones, DNS and TLS handshakes, and production-only components like a WAF or proxy. Then concurrency under real load: exhausted connection or thread pools, GC pressure, and CPU throttling from Kubernetes limits. Configuration differences like log levels and pool sizes matter too."

Likely follow-up questions

  • How to reproduce production-like data safely? Anonymised or masked snapshots, or synthetic generators matching production distributions.
  • What is CPU throttling? The CFS quota stops a container's threads for the rest of each period once its CPU limit is used up.
  • Why might a plan differ across environments? Different data volumes, statistics, configuration and parameter values.
