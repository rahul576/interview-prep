How do you use MCP servers in non-interactive settings, such as CI pipelines or scheduled agents?

MCP Servers · concept · levels mid, senior

In one line

In CI pipelines and scheduled agents no human is present to approve, so safety is designed in advance: a pre-approved allowlist of tools (mostly read-only), machine identities with short-lived scoped tokens, outputs as pull requests or reports for later review, and hard budgets, step limits and timeouts.

Detailed explanation

Interactive MCP use leans on the human in the loop: the host asks before a tool with side effects runs. Headless runs, such as a GitHub Actions job that triages failing tests or a nightly agent that reviews dependency updates, remove that safety net. Whatever the agent is allowed to call, it will be able to call without anyone watching.

So the first control is an explicit allowlist. The agent's configuration lists exactly which servers and tools it may use, and destructive tools are simply not available. Most CLI agents support allow and deny lists for tools in a non-interactive mode; anything not listed is refused rather than prompted.

The second is identity. Never reuse a person's token in a pipeline. Use a machine identity: OAuth client credentials (MCP has an extension for this), or workload identity federation, where the CI system's OIDC token is exchanged for a short-lived cloud or API token with narrow scopes.

The third is deferred human review. The agent proposes rather than acts: a pull request that fixes a flaky test, a comment summarising a failure, a report listing upgrade risks. Humans review on their own schedule.

Finally, budgets: maximum tokens or cost, maximum tool calls or turns, and an overall wall-clock timeout, so a confused agent stops instead of looping. All tool calls are logged against the pipeline run ID.

Be careful with untrusted input. A CI agent reading pull requests from forks is reading attacker-controlled text; combine that with write tools or secrets and you have a prompt injection path.

How it works

  1. Pipeline starts the agent with a fixed config: allowed servers, allowed tools, model, budgets.
  2. CI's OIDC token is exchanged for short-lived, scoped credentials.
  3. Agent runs non-interactively; disallowed tool calls are rejected.
  4. Output is a PR, comment, artefact or report, never a direct production change.
  5. Logs and traces are attached to the run; failure or budget exhaustion fails the job visibly.

Example

# .github/workflows/triage.yml (sketch)
permissions:
  contents: read
  pull-requests: write
  id-token: write
jobs:
  triage:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@v4
      - name: Run agent on failing tests
        run: |
          agent run --non-interactive \
            --allowed-tools "github.get_workflow_run,github.get_job_logs,github.create_pull_request" \
            --max-turns 30 \
            --prompt-file .ci/triage-prompt.md

Common mistakes

  • Running with a "skip all permissions" flag and a personal access token.
  • Letting a job triggered by forked PRs access secrets and write tools.
  • No turn or cost limit, so a looping agent burns budget for hours.
  • Agents pushing directly to main instead of opening a PR.

How to answer in the interview

"Without a human present, approvals have to be designed in advance. I give the agent an explicit allowlist of pre-approved tools, mostly read-only, and destructive tools simply aren't available. It authenticates with a machine identity, client credentials or workload identity federation, with narrow scopes and short-lived tokens, never someone's personal credentials. Instead of acting directly, it produces things humans review later: a pull request with a fix, a comment summarising a failure, or a report. Runs have token and cost budgets, step limits and timeouts, and every tool call is logged with the pipeline run. I'm particularly careful when the agent reads untrusted content like PRs from forks."

Likely follow-up questions

  • Risk of untrusted PR content with write tools? Prompt injection could make the agent leak secrets or push malicious changes.
  • How do approvals work overnight? Queue proposed actions for review in the morning instead of executing them.
  • Why workload identity over stored secrets? Nothing long-lived to leak, and tokens are bound to the specific job.
