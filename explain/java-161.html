SQL or NoSQL: how do you choose a database for a new service?

Databases & SQL · concept · levels mid, senior

In one line

Choose from the data model and access patterns: a relational database such as PostgreSQL is the sensible default for transactional business data, and a NoSQL store (document, key-value, wide-column, graph) is chosen when a specific scale, shape or latency need justifies it.

Detailed explanation

Relational databases give strong consistency, ACID transactions, joins, constraints and flexible ad hoc SQL. Most business domains (orders, payments, users, inventory) are relational by nature, and a single well-tuned PostgreSQL instance with read replicas handles far more load than many teams expect. It also has JSONB, full-text search and extensions, so it covers many "we need NoSQL" cases.

NoSQL is a family, not one thing:

  • Document (MongoDB): nested, varying structures read as a whole, such as a product with category-specific attributes.
  • Key-value (Redis, DynamoDB): very fast lookups by key at huge scale; sessions, carts, caches.
  • Wide-column (Cassandra, ScyllaDB): massive write volume, time series, multi-region, queried by partition key.
  • Graph (Neo4j): deep relationship traversal such as recommendations or fraud rings.

The trade-off is that many NoSQL systems scale horizontally by partitioning data and relaxing consistency (per CAP/PACELC), and they require you to design tables around known queries. Changing access patterns later is expensive. Operational factors matter too: team skills, managed offerings, cost, backup and compliance.

How it works

  1. List the entities, relationships and invariants (what must never be inconsistent).
  2. Write down the main queries, their frequency, latency targets and read/write ratio.
  3. Estimate data volume and growth, and whether a single primary can handle peak writes.
  4. Decide the consistency requirement per operation.
  5. Default to Postgres; pick a specialised store only where a requirement clearly fails.
  6. Consider polyglot persistence: Postgres as system of record plus Redis, a search index or a wide-column store for specific needs.

Example

An e-commerce platform:

Orders, payments, inventory  -> PostgreSQL (transactions, constraints, reporting)
Product search               -> OpenSearch/Elasticsearch (full-text, facets)
Sessions, carts, rate limits -> Redis (low-latency key access, TTL)
Click/event history          -> Cassandra or DynamoDB (huge write volume, query by user+time)

Common mistakes

  • Choosing NoSQL because it is "web scale" without numbers to prove it.
  • Picking MongoDB to avoid schema design, then reinventing joins in code.
  • Ignoring that NoSQL modelling needs access patterns fixed up front.
  • Running many databases a small team cannot operate.

How to answer in the interview

"I start from the data and the queries, not the technology. If the data is relational, needs transactions and will be queried in ways I can't fully predict, I default to PostgreSQL, which also gives me JSONB if some fields are flexible. I'd pick a NoSQL store for a concrete reason: a key-value store like DynamoDB or Redis for very high-throughput key lookups, Cassandra for huge write volumes like event history, a document store for nested data read as one unit, or a graph database for relationship queries. I'd also weigh consistency needs, since many NoSQL systems trade consistency for horizontal scale, and what the team can operate."

Likely follow-up questions

  • What does CAP mean in practice? During a network partition you choose between refusing requests (consistency) and serving possibly stale data (availability).
  • Can Postgres scale writes horizontally? With sharding extensions such as Citus, or distributed SQL like CockroachDB or YugabyteDB.
  • When would MongoDB be wrong? When data is highly relational and needs many cross-document transactions and joins.
