What is service registration?

Microservices · concept · levels mid, senior

In one line

Service registration is how a running instance publishes its network location and metadata to a service registry, either by self-registration (Eureka or Consul client with heartbeats) or third-party registration by the platform (Kubernetes adding ready pods to Service endpoints), and is removed again on shutdown or failed health checks.

Detailed explanation

Discovery only works if the registry knows which instances exist and are healthy. Registration is that half of the problem.

With self-registration, the instance itself talks to the registry. A Spring Boot app with the Eureka client registers on startup with its application name (spring.application.name), host, port, status and metadata such as zone or version. It then renews its lease with a heartbeat every 30 seconds; if renewals stop for the lease expiry period (90 seconds by default), the Eureka server evicts it. On graceful shutdown it deregisters explicitly, so traffic stops at once. With Consul, the agent registers the service and runs health checks (HTTP, TCP or TTL), marking it critical if they fail. Self-registration is simple but couples every service to a registry client library and language.

With third-party registration, a separate component registers instances on their behalf. In Kubernetes, you never write registry code: the control plane watches pods matching a Service's label selector, and only pods whose readiness probe passes are added to the Service's EndpointSlices. When a pod fails readiness or is terminated, it is removed. kube-proxy or a service mesh then routes traffic to the current endpoints. Other examples are Registrator for Docker, or cloud load balancers registering auto-scaled VMs in target groups.

Important details: register only when the instance can really serve traffic (after caches warm up, migrations run), deregister before shutting down so in-flight requests finish, and include metadata for zone-aware or version-aware routing.

How it works

  1. Instance starts and initialises.
  2. It becomes ready (readiness probe or health check passes).
  3. It is registered (by itself or the platform) with address and metadata.
  4. Heartbeats or periodic checks keep it registered.
  5. Failure or missed heartbeats → removed from the registry.
  6. Graceful shutdown → deregister first, then drain and exit.

Example

# Self-registration with Eureka (Spring Boot)
spring:
  application:
    name: order-service
eureka:
  client:
    service-url:
      defaultZone: http://eureka-1:8761/eureka/,http://eureka-2:8761/eureka/
  instance:
    prefer-ip-address: true
    lease-renewal-interval-in-seconds: 30
    metadata-map:
      zone: eu-west-1a
# Third-party registration in Kubernetes: readiness controls endpoint membership
readinessProbe:
  httpGet: { path: /actuator/health/readiness, port: 8080 }
  periodSeconds: 5

Common mistakes

  • Registering before the app is ready, so early requests fail.
  • No readiness probe in Kubernetes (pod receives traffic while starting).
  • Not deregistering on shutdown, leaving stale entries for up to 90 seconds.
  • Using liveness probes that check downstream dependencies, causing restart loops.

How to answer in the interview

"Service registration is how an instance makes its address and metadata known to a registry so others can discover it. With self-registration the instance does it, for example a Spring Boot app with the Eureka client registers at startup, sends heartbeats every thirty seconds and deregisters on shutdown; if heartbeats stop, it is evicted. With third-party registration the platform does it: in Kubernetes, pods that pass their readiness probe are automatically added to the Service's endpoints, so the application needs no registry client. Either way, an instance should only be registered once it can actually serve traffic."

Likely follow-up questions

  • Why is a readiness probe important for registration in Kubernetes? It decides when a pod joins and leaves the Service endpoints.
  • Readiness vs liveness? Readiness controls traffic; liveness controls restarts.
  • What happens if the registry is down? Clients use cached registry data; new instances cannot register until it recovers.
