How does Kafka guarantee ordering, and what delivery semantics can you achieve?

Kafka · concept · levels mid, senior

In one line

Kafka guarantees ordering only within a partition, so related messages share a key; delivery is at-most-once, at-least-once or exactly-once depending on when offsets are committed and whether you use idempotent producers and transactions.

Detailed explanation

A topic is split into partitions, each an append-only, ordered log. Records get increasing offsets within a partition, and consumers read them in that order. There is no global order across partitions. To keep related events ordered, such as all events of order 42, the producer sets a key; the default partitioner hashes the key so the same key always lands in the same partition (as long as the partition count does not change).

Within a consumer group, each partition is assigned to exactly one consumer, which preserves per-partition order and gives parallelism up to the number of partitions. On the producer side, retries could reorder or duplicate batches; the idempotent producer (enable.idempotence=true, the default since Kafka 3.0) uses producer ids and sequence numbers so the broker drops duplicates and keeps order, with up to five in-flight requests.

Delivery semantics come from offset handling:

  • At-most-once: commit offsets before processing; a crash loses messages.
  • At-least-once: process, then commit; a crash causes redelivery, so processing must be idempotent. This is the usual choice.
  • Exactly-once: inside Kafka, a consume-transform-produce flow uses transactions so output records and consumer offsets commit atomically, and downstream consumers use isolation.level=read_committed (Kafka Streams does this with processing.guarantee=exactly_once_v2). For external systems such as a database, you achieve "effectively once" by combining at-least-once with idempotent writes or storing offsets in the same database transaction.

For durability, producers use acks=all with min.insync.replicas=2.

How it works

  1. Producer sends a record with key orderId.
  2. Partitioner hashes the key to a partition; the leader appends it.
  3. Followers replicate; with acks=all the producer gets an ack after ISR replication.
  4. The group consumer for that partition polls records in offset order.
  5. It processes and then commits offsets (at-least-once).
  6. On crash, the new owner resumes from the last committed offset.

Example

// Producer: same key -> same partition -> ordered per order
props.put(ProducerConfig.ACKS_CONFIG, "all");
props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);
producer.send(new ProducerRecord<>("orders", order.getId(), event));

// Consumer: at-least-once
props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, false);
while (true) {
    var records = consumer.poll(Duration.ofMillis(500));
    for (var r : records) handleIdempotently(r.value());
    consumer.commitSync();
}

Common mistakes

  • Expecting topic-wide ordering.
  • Adding partitions later and breaking key-to-partition mapping.
  • Claiming exactly-once covers database writes or HTTP calls.
  • Auto-commit with asynchronous processing, causing silent message loss.

How to answer in the interview

"Kafka only guarantees order within a partition, so I key messages by the entity whose events must stay ordered, like the order id, and the same key always goes to the same partition. Within a consumer group, one consumer owns each partition. Delivery semantics depend on offset commits: commit before processing is at-most-once, after processing is at-least-once, which I use with idempotent consumers. Exactly-once is available for Kafka-to-Kafka pipelines using idempotent producers, transactions and read_committed consumers. On the producer I use acks=all and idempotence for durability and to avoid retry duplicates."

Likely follow-up questions

  • What happens during a rebalance? Partitions move between consumers; uncommitted work may be reprocessed, so commit on revoke and use cooperative rebalancing.
  • Why not one partition for global order? It limits throughput and parallelism to one consumer.
  • Does idempotent producer give exactly-once end to end? No, only no duplicates per partition from producer retries.
