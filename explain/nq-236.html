What is the difference between relational databases and MongoDB?

Databases & SQL · concept · levels entry

In one line

A relational database stores normalised rows in tables with a fixed schema and joins them at query time, while MongoDB stores BSON documents in collections that can embed related data, scale out with sharding and replica sets, and are designed around access patterns.

Detailed explanation

In a relational design, an order is spread across orders, order_items and customer tables, linked by keys and joined when read. The schema is enforced by the database, constraints guarantee integrity, and SQL lets you query in any combination.

MongoDB stores documents: JSON-like objects encoded as BSON (which adds types such as dates, decimals and ObjectId), grouped in collections. A document can contain nested objects and arrays, so an order with its line items and shipping address can be one document, fetched or updated atomically in a single operation without joins. Documents in a collection may differ in shape, although you can enforce rules with JSON Schema validation.

Key differences:

  • Modelling: embed data that is read together and bounded in size (order lines); reference data that is shared, large or grows without limit (customer, product, comments). Documents are limited to 16 MB.
  • Querying: the MongoDB query language and the aggregation pipeline ($match, $group, $lookup for left-outer-join style lookups). Joins exist but are not the main pattern.
  • Indexes: B-tree indexes including compound, multikey (on arrays), text, geospatial and TTL indexes.
  • Scaling and HA: replica sets (one primary, secondaries with automatic election) and sharding by a shard key across shards.
  • Transactions: single-document operations are always atomic; multi-document ACID transactions exist since 4.0 (4.2 for sharded clusters) but are costlier and should be the exception.

How it works

  1. Identify the application's main reads and writes.
  2. Group data read together into one document.
  3. Reference data that is shared or unbounded.
  4. Create indexes for query filters and sorts.
  5. Use write concern majority and read concern for durability and consistency needs.
  6. Shard collections by a high-cardinality key when one replica set is not enough.

Example

// Embedded order document
db.orders.insertOne({
  customerId: 42,
  status: "PAID",
  items: [{ sku: "LAMP-01", qty: 2, price: NumberDecimal("24.50") }],
  createdAt: new Date()
});
db.orders.createIndex({ customerId: 1, createdAt: -1 });

// Occasional join with $lookup
db.orders.aggregate([
  { $match: { status: "PAID" } },
  { $lookup: { from: "customers", localField: "customerId",
               foreignField: "_id", as: "customer" } }
]);

Common mistakes

  • Porting a normalised relational schema table-for-collection and doing $lookup everywhere.
  • Embedding unbounded arrays such as all comments forever.
  • Saying MongoDB has no transactions or no schema validation.
  • Storing money as floating point instead of Decimal128.

How to answer in the interview

"A relational database stores rows in tables with a fixed schema, normalises related data and joins it at query time, with ACID transactions and SQL. MongoDB stores BSON documents in collections; documents can vary in structure and embed related data, so an order with its items is one document and a typical read needs no join. It uses the Mongo query language and aggregation pipelines, with $lookup for occasional joins, and scales with replica sets for availability and sharding for horizontal scale. It supports multi-document transactions since 4.0, but the main design rule is to model documents around access patterns: embed what's read together, reference what's shared or unbounded."

Likely follow-up questions

  • Embed or reference? Embed bounded data read together; reference shared, large or growing data.
  • What is a replica set? A primary and secondaries with automatic election for failover.
  • Is a single-document update atomic? Yes, even when it changes several nested fields.
