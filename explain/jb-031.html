How does Java handle string concatenation internally?

Core Java & OOP · concept · levels mid, senior

In one line

Constant expressions are folded by javac into one literal; up to Java 8, other + expressions compiled to a StringBuilder append chain; since Java 9 (JEP 280) they compile to an invokedynamic call bootstrapped by StringConcatFactory, letting the JVM pick the best strategy at runtime.

Detailed explanation

Compile-time constants. If every operand is a compile-time constant (literals, static final constants with constant initialisers), javac computes the result itself: "a" + "b" + 1 becomes the literal "ab1" in the class file and is pooled.

Java 5 to 8. For anything else, javac rewrote a + b + c into new StringBuilder().append(a).append(b).append(c).toString(). This worked but was suboptimal: the builder started at default capacity and might resize several times, the final toString copied the buffer again, and the shape was frozen into the bytecode of every class. The JIT had special-case optimisations (-XX:+OptimizeStringConcat) that recognised the pattern, but they were fragile.

Java 9+. JEP 280, "Indify String Concatenation", changed javac to emit a single invokedynamic instruction with a recipe like "\u0001,\u0001" and the dynamic argument types. On first execution, the bootstrap method StringConcatFactory.makeConcatWithConstants builds a MethodHandle chain tailored to those types. The default strategy computes the exact final length and coder (Latin-1 or UTF-16, linked to Compact Strings) up front, allocates one byte array and fills it directly, with no intermediate builder and no extra copy. Later call executions jump straight to the linked handle.

Benefits: faster concatenation and less garbage, smaller bytecode, and future JDKs can improve the strategy without recompiling your code, since the logic lives in the runtime, not your class files. (javac still has the hidden -XDstringConcat=inline option to emit the old builder style, used for example by code that runs very early in JVM startup.)

What it does not change: each expression is still optimised in isolation. A loop with s += x still allocates a new String per iteration, so StringBuilder or joining remains the right tool there.

How it works

  1. javac folds constant operands.
  2. For dynamic operands, it emits invokedynamic makeConcatWithConstants with a recipe.
  3. First execution bootstraps a call site via StringConcatFactory.
  4. The linked MethodHandle computes length/coder, allocates once and copies operands.
  5. Subsequent executions reuse the linked call site.

Example

String greet(String name, int age) {
    return "Hi " + name + ", age " + age;
}
javac Greeter.java && javap -c -p Greeter
#   invokedynamic #7, 0  // InvokeDynamic #0:makeConcatWithConstants:(Ljava/lang/String;I)Ljava/lang/String;
# Compiled with --release 8 instead you'd see:
#   new java/lang/StringBuilder ... append ... toString

Common mistakes

  • Saying modern Java still compiles + to StringBuilder.
  • Concluding that loops are now fine because "Java 9 optimised concatenation".
  • Hand-rewriting simple + into builders for performance.
  • Ignoring that toString() of operands is still called and may be expensive.

How to answer in the interview

"Constant expressions like "a" + "b" are folded by javac into a single literal. Up to Java 8, anything else was compiled into a StringBuilder append chain plus toString. Since Java 9, JEP 280 compiles concatenation into a single invokedynamic call bootstrapped by StringConcatFactory. At runtime the JVM builds a strategy for those argument types, typically computing the exact final length and filling one byte array without intermediate copies. It's faster and the JDK can improve it without recompiling our code. It still optimises one expression at a time, so concatenating inside a loop still allocates each iteration."

Likely follow-up questions

  • Why did the JDK move string concatenation to invokedynamic? To make the strategy a runtime decision that can evolve and optimise per type without recompiling.
  • Does it help loops? No, each iteration is still a separate concatenation.
  • How can you see it? javap -c shows the invokedynamic instruction.
