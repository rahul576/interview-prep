What are event sourcing and CQRS, and when are they worth the complexity?

Distributed Systems · concept · levels senior, lead

In one line

Event sourcing stores every change as an immutable event and rebuilds state by replay; CQRS separates the write model from query-optimised read models built by projections. Use them where history and auditability matter, accepting eventual consistency, schema evolution and complexity.

Detailed explanation

In CRUD, a row holds the latest state; history is lost unless you add audit tables. In event sourcing, the event stream is the source of truth: AccountOpened, MoneyDeposited(500), MoneyWithdrawn(200). Current state is a fold over events; snapshots avoid replaying millions of events.

CQRS often pairs with it: commands go to aggregates that validate and emit events; projections subscribe and build read models such as a balance table, a search index or a monthly statement view. Each read model is tailored to its query and can be rebuilt from scratch by replaying events, which also means new views from old history.

Costs: read models lag (eventual consistency); events are forever, so schema evolution needs versioned events and upcasters; debugging requires good tooling; GDPR deletion needs crypto-shredding. Don't use it for simple CRUD.

How it works

  1. Command Withdraw(200) → load aggregate (snapshot + later events).
  2. Validate invariants → append MoneyWithdrawn with expected version (optimistic concurrency).
  3. Publish event → projections update read models.
  4. Queries hit read models.

Example

stream: account-42
v1 AccountOpened {owner: "Asha"}
v2 MoneyDeposited {amount: 500}
v3 MoneyWithdrawn {amount: 200}
→ state: balance 300 (rebuildable at any point in time)

Tools: EventStoreDB, Axon, Marten, or Kafka + a DB table as the event store.

Common mistakes

  • Using Kafka topics with short retention as the only event store.
  • Event-sourcing every service.
  • Events that mirror table columns rather than business facts.
  • Ignoring idempotency in projections.

How to answer in the interview

"Event sourcing stores state changes as an append-only event log and rebuilds state by replay, with snapshots for speed. CQRS splits writes from read models that projections build from those events. You get a full audit trail, time travel and the ability to build new views later. The price is eventual consistency, event versioning and complexity, so I'd use it for ledgers, orders or compliance-heavy domains, not plain CRUD."

Likely follow-up questions

  • Changing an event's structure? Version events; upcast old versions on read.
  • Deleting personal data? Encrypt per-user fields; delete the key (crypto-shredding).
  • Concurrency? Expected-version check on append.
