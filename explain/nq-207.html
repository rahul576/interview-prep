How should REST endpoints and resource names be designed?

REST & API Design · concept · levels entry, mid

In one line

Use plural nouns for resources (/orders, not /getOrders), ids for items, shallow hierarchies for relationships (/customers/{id}/orders), let HTTP methods express actions, use lowercase with hyphens, put filtering, sorting and paging in query parameters, model special actions as sub-resources, and add versioning and consistent errors.

Detailed explanation

Good resource naming makes an API guessable: once a developer knows /orders/{id}, they expect /customers/{id} to behave the same way.

Nouns, not verbs. The URI identifies what; the method says what to do. GET /orders, POST /orders, GET /orders/{orderId}, PATCH /orders/{orderId}, DELETE /orders/{orderId}. Avoid /getOrders, /createOrder, /deleteOrder?id=5.

Plural collections. /orders is the collection; /orders/42 is one member. Being consistently plural avoids debates about /order/42 versus /orders.

Relationships. Express ownership with sub-resources: /customers/7/orders lists that customer's orders. Keep nesting shallow (one or two levels): /orders/42/items is fine, but /customers/7/orders/42/items/3/discounts is hard to use. Once an item has a global id, address it directly: /orders/42.

Formatting. Lowercase, words separated by hyphens (/payment-methods), no file extensions, no trailing slashes. JSON field names in camelCase, consistently.

Query parameters for everything that shapes a collection rather than identifying a resource: filtering (?status=SHIPPED&from=2026-11-01), sorting (?sort=createdAt,desc), pagination (?page=2&size=20 or ?after=cursor), field selection (?fields=id,status) and search (?q=phone).

Actions that are not CRUD. Model them as resources: cancelling an order becomes POST /orders/42/cancellation (creates a cancellation, which can have a reason and timestamp), or a state change via PATCH /orders/42 {"status":"CANCELLED"} if it is simple. Some APIs use a colon-style custom method (POST /orders/42:cancel, Google's API guidelines). Pick one style and keep it consistent.

Versioning and errors. Prefix with a version (/api/v1/...) or use headers; return consistent error bodies (Problem Details) and document everything with OpenAPI.

How it works

  1. List the domain resources and their relationships.
  2. Map each to a plural collection and item URI.
  3. Assign HTTP methods for operations.
  4. Put shaping options in query parameters.
  5. Model non-CRUD actions as sub-resources.
  6. Document and lint the naming rules.

Example

GET    /api/v1/customers/7/orders?status=SHIPPED&sort=createdAt,desc&page=0&size=20
POST   /api/v1/orders
GET    /api/v1/orders/42
PATCH  /api/v1/orders/42
DELETE /api/v1/orders/42
GET    /api/v1/orders/42/items
POST   /api/v1/orders/42/cancellation      {"reason": "Customer request"}
GET    /api/v1/payment-methods

Avoid: /api/getOrders, /api/Order/42/, /api/orders/delete?id=42, /api/customer_orders

Common mistakes

  • Verbs in paths and everything via POST.
  • Mixed singular and plural or mixed case styles.
  • Deeply nested URIs.
  • Filters as path segments (/orders/status/shipped).
  • Inconsistent styles for custom actions across services.

How to answer in the interview

"I use nouns for resources, in plural, and let the HTTP method express the action: GET /orders and POST /orders, not /getOrders or /createOrder. Single items are /orders/{orderId}, and ownership is a sub-resource, /customers/{id}/orders, keeping nesting shallow. I use lowercase with hyphens, like /payment-methods. Filtering, sorting and pagination go into query parameters, for example ?status=SHIPPED&sort=createdAt,desc&page=2&size=20. Actions that don't fit CRUD become resources, like POST /orders/{id}/cancellation. And I add versioning such as /api/v1, consistent error bodies, and document it all in OpenAPI."

Likely follow-up questions

  • How would you design an endpoint for cancelling an order? POST /orders/{id}/cancellation with a reason, returning 201 or 200, and 409 if already shipped.
  • When is nesting appropriate? When the child only makes sense in the parent's context; keep it to one or two levels.
  • Hyphens or underscores? Hyphens in URIs are the common convention.
