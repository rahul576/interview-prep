How do you run distributed training, and what infrastructure does it need?

MLOps · concept · levels senior, lead

In one line

Data parallelism (PyTorch DDP) replicates the model and splits batches; for large models, FSDP or DeepSpeed ZeRO shard parameters, gradients and optimiser state, and tensor and pipeline parallelism split layers. It needs fast interconnects (NVLink, InfiniBand/RoCE) with NCCL, gang scheduling, and regular checkpointing.

Detailed explanation

In data parallelism, every GPU holds a full model copy and processes a different slice of each global batch. After the backward pass, gradients are averaged across GPUs with an all-reduce, so all replicas stay identical. PyTorch DistributedDataParallel (DDP) implements this, overlapping communication with computation.

When the model, gradients and optimiser state don't fit on one GPU, you shard. FSDP (Fully Sharded Data Parallel) and DeepSpeed ZeRO split parameters, gradients and optimiser states across GPUs and gather them just in time for each layer. Tensor parallelism splits individual matrix multiplications within a layer across GPUs (as in Megatron-LM), needing very high bandwidth, so it usually stays within a node. Pipeline parallelism places groups of layers on different GPUs as stages and streams micro-batches through them. Large LLM training combines these ("3D parallelism").

Infrastructure matters because GPUs exchange data every step. Within a node, NVLink/NVSwitch; between nodes, InfiniBand or RoCE at hundreds of gigabits per GPU, with NCCL handling collective operations. Slow networking leaves GPUs idle waiting for gradients.

On Kubernetes (Kubeflow Training Operator, Kueue, Volcano) or Slurm, jobs need gang scheduling: all workers start together or none do, avoiding deadlocked partial jobs. Failures are normal at scale, so checkpoint regularly to shared storage and support automatic restart (for example torchrun elastic launch).

How it works

  1. Choose strategy by model size: DDP if it fits, FSDP/ZeRO if not, add tensor/pipeline for very large models.
  2. Launch workers with torchrun or an operator; each gets a rank.
  3. Initialise the process group with the NCCL backend.
  4. Shard data with a distributed sampler.
  5. Train; collectives synchronise gradients or shards.
  6. Checkpoint periodically; restart from last checkpoint on failure.

Example

torchrun --nnodes=4 --nproc_per_node=8 \
  --rdzv_backend=c10d --rdzv_endpoint=$MASTER_ADDR:29500 train.py
import torch.distributed as dist
from torch.distributed.fsdp import FullyShardedDataParallel as FSDP
dist.init_process_group("nccl")
model = FSDP(model.cuda())          # shards params, grads, optimiser state
sampler = torch.utils.data.distributed.DistributedSampler(dataset)

Common mistakes

  • Adding nodes over slow Ethernet and seeing little speed-up.
  • No gang scheduling, so jobs hang with half their workers.
  • Checkpointing rarely, losing days on a node failure.
  • Ignoring data loading, leaving GPUs starved.

How to answer in the interview

"For models that fit on one GPU, I use data parallelism with PyTorch DDP: each GPU has a copy, processes part of the batch, and gradients are all-reduced every step. For larger models, FSDP or DeepSpeed ZeRO shard parameters, gradients and optimiser state, and very large models add tensor and pipeline parallelism. The infrastructure needs NVLink in the node and InfiniBand or RoCE between nodes, with NCCL for collectives. The scheduler must gang-schedule all workers, and we checkpoint frequently to shared storage so failures don't cost days."

Likely follow-up questions

  • Why do more GPUs sometimes barely help? Communication overhead, small per-GPU batches, data-loading bottlenecks or slow interconnects.
  • What does gradient accumulation do? Simulates a bigger batch with fewer GPUs by summing gradients over steps.
  • Spot instances for training? Possible with frequent checkpoints and elastic restart.
