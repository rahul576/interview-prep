A Docker host keeps running out of disk space. How do you investigate and prevent it?

Docker · scenario · levels senior

In one line

Confirm which filesystem is full, then use docker system df -v and du on /var/lib/docker to find the culprit, usually unrotated container logs, old images, build cache or data written into containers' writable layers; prevent it with log limits, scheduled pruning, volumes, a dedicated disk and alerts.

Detailed explanation

Docker keeps everything under its data root, normally /var/lib/docker: image layers and container writable layers (under overlay2), container logs (under containers/<id>/<id>-json.log), volumes and the BuildKit cache. On a busy host several of these grow without limit by default.

The most common surprise is logs. The default json-file driver has no size limit, so a chatty container can write tens of gigabytes. Next come images: a host that deploys several times a day keeps every previous version, plus dangling (untagged) images. On build machines the BuildKit cache can grow very large. Finally, an app writing data, uploads or temp files into its writable layer instead of a volume grows the overlay2 directory, and that data is hidden from a quick look at volumes.

A full disk is serious: the daemon cannot create containers or pull images, running apps fail on writes, and databases may corrupt or stop. So the fix is not just a one-off cleanup but prevention.

How it works

  1. df -h (and df -i for inodes) to confirm which mount is full.
  2. docker system df -v to split usage into images, containers, volumes and build cache.
  3. du -sh /var/lib/docker/* and du on containers/ to find large log files.
  4. docker ps -s shows the size of each container's writable layer.
  5. Clean safely: truncate or rotate huge logs, docker image prune -a --filter until=168h, docker builder prune.
  6. Prevent: configure log rotation, scheduled prunes, volumes for data, monitoring.

Example

docker system df -v
sudo du -sh /var/lib/docker/{overlay2,containers,volumes,buildkit} 2>/dev/null
sudo find /var/lib/docker/containers -name '*-json.log' -size +1G -exec ls -lh {} \;
docker image prune -a -f --filter "until=168h"
docker builder prune -f --filter "until=168h"
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "50m", "max-file": "3" }
}

Common mistakes

  • Deleting files inside /var/lib/docker by hand, which corrupts Docker's metadata.
  • Running docker system prune --volumes on a host with important volume data.
  • Setting log limits in daemon.json and forgetting they only apply to newly created containers.
  • Alerting only at 100% instead of at 80%.

How to answer in the interview

"First I check with df -h which filesystem is actually full, then docker system df -v and du under /var/lib/docker to see whether it's images, containers, volumes or build cache. The usual culprits are json-file logs with no rotation, hundreds of old images from frequent deploys, a growing BuildKit cache, or a container writing data into its writable layer, which I spot with docker ps -s. I clean up with prune commands using age filters, never by deleting files manually. For prevention, I set max-size and max-file in daemon.json, schedule pruning, move data to volumes, put Docker on its own disk and alert at around 80%."

Likely follow-up questions

  • What breaks when the disk fills? Pulls and container starts fail, apps get write errors, logging may block, and databases can crash or corrupt.
  • Why are log limits not applied to my old container? Log options are fixed at container creation; recreate the container.
  • Alternative to local logs? Ship logs with the local driver plus a collector, or to a central system such as Loki or Elasticsearch.
