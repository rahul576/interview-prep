Should you build a multi-cloud abstraction layer over AWS, Azure and GCP in your IaC?

Infrastructure as Code · design · levels lead

In one line

Usually no deep abstraction: a single "any-cloud" layer forces a lowest common denominator, hides valuable provider features and becomes a costly product to maintain; instead standardise the workflow, tooling and conventions across clouds and use provider-specific modules with consistent interfaces only where use cases truly match, driven by a real business need for portability.

Detailed explanation

The appeal is obvious: one module "database" that works on AWS, Azure and GCP, and freedom from lock-in. In practice the costs usually outweigh it.

Lowest common denominator. Aurora, Azure SQL Hyperscale and Cloud Spanner differ in features, scaling, backup and networking. A common interface can expose only what all share, so teams lose the managed features that made the cloud valuable, or the interface grows provider-specific flags until it is three modules in one file.

Maintenance. The abstraction becomes an internal product tracking three fast-moving providers, with its own bugs, documentation and on-call. Every new provider feature needs design work before teams can use it.

Portability is rarely real. Even with identical module calls, moving a workload means migrating data (data gravity), rewriting IAM (different identity models), re-doing networking, observability and compliance evidence. The module call is the easy part.

What pays off is commonality one level up:

  • The same IaC tool, pipeline templates, policy-as-code framework, state handling and review process on every cloud.
  • Shared naming, tagging and ownership conventions, and shared security baselines expressed per cloud.
  • Provider-specific modules with similar interfaces where the use case genuinely matches: a static website, a DNS record, a storage bucket with standard retention.
  • Portable layers where they naturally exist, such as Kubernetes for workloads, while accepting cloud-specific infrastructure beneath.

The decision should follow a concrete driver: regulatory exit plans, a customer requirement to run in their cloud, or M&A, and the abstraction depth should match that need.

How it works

  1. Clarify the business driver for multi-cloud.
  2. Standardise workflow, tooling, policy and conventions everywhere.
  3. Build per-cloud golden modules with aligned input names.
  4. Abstract only stable, simple, truly common use cases.
  5. Revisit as needs change; avoid speculative generality.

Example

# Same interface, separate provider-specific modules
module "site" {
  source      = "registry.acme.internal/platform/static-site/aws"   # or .../azure
  version     = "2.1.0"
  domain_name = "docs.acme.com"
  owner       = "docs-team"
}

Common mistakes

  • Building the abstraction before there is a second cloud in use.
  • Promising portability that data and IAM differences make impossible.
  • Hiding provider features teams need, pushing them to bypass the platform.
  • Underestimating the long-term maintenance cost.

How to answer in the interview

"Usually not, at least not a deep one. A module that creates a database on any cloud has to reduce each provider to the lowest common denominator, hiding the managed features that make each cloud valuable, and it becomes a large internal product to maintain as all three evolve. Real portability is rare anyway because data, IAM and networking differ. What pays off is a common workflow: the same tool, pipelines, policy as code, naming and tagging across clouds, with provider-specific modules that share an interface only where the use case is truly the same, like a static website. The depth should follow a concrete business need."

Likely follow-up questions

  • When would a thin abstraction be worth it? For simple, stable, identical use cases or when you must deploy the same product into customers' different clouds.
  • Is Kubernetes the portability layer? Partly for workloads; the infrastructure beneath stays cloud-specific.
  • How do you address lock-in concerns? Exit plans, data export strategies and open standards, not a universal module layer.
