Which storage options do you use on AKS, and what do you need to consider for each?

Azure Kubernetes (AKS) · concept · levels mid, senior

In one line

On AKS use Azure Disk CSI for ReadWriteOnce block storage (databases), Azure Files CSI for ReadWriteMany shares, the Blob CSI driver for large datasets, and ephemeral OS disks or local NVMe for scratch, remembering that disks are zonal and choosing Premium SSD v2 or Ultra for demanding databases.

Detailed explanation

Azure Disk (StorageClasses managed-csi, managed-csi-premium) attaches a managed disk to one node, so it is ReadWriteOnce: one pod writes at a time. It is the default for StatefulSets and databases. SKUs range from Standard SSD to Premium SSD, Premium SSD v2 (where IOPS and throughput are configured independently of size, often the best price-performance for databases) and Ultra Disk for extreme latency needs. The VM size also limits the number of disks and total IOPS.

Zones matter: a locally redundant disk lives in one availability zone, so a pod using it can only run on nodes in that zone. Use volumeBindingMode: WaitForFirstConsumer so the disk is created where the pod is scheduled, spread StatefulSet replicas across zones, or use ZRS disks (Premium_ZRS) that can attach in any zone of the region.

Azure Files (azurefile-csi, azurefile-csi-premium) provides ReadWriteMany shares over SMB or NFS, mountable by many pods across nodes and zones. Good for shared uploads, CMS content or legacy apps; too slow and lock-sensitive for most databases.

Blob CSI driver mounts blob containers with BlobFuse2 (with local caching) or NFS 3.0, suited to large read-mostly data such as ML models and datasets.

Ephemeral storage: ephemeral OS disks use the VM's local cache or temp disk, faster and free, and local NVMe on sizes like Lsv3 offers very high IOPS, usable directly or via Azure Container Storage. Data is lost when the node is reimaged or deleted, so use it for caches, scratch or replicated databases only.

How it works

  1. Choose by access mode: RWO (Disk), RWX (Files), object-style (Blob).
  2. Choose performance tier and redundancy (LRS vs ZRS).
  3. Create a StorageClass with the right parameters and binding mode.
  4. Reference it from PVCs or StatefulSet volumeClaimTemplates.
  5. Back up volumes and monitor IOPS and latency.

Example

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata: { name: premiumv2-db }
provisioner: disk.csi.azure.com
parameters:
  skuName: PremiumV2_LRS
  DiskIOPSReadWrite: "8000"
  DiskMBpsReadWrite: "300"
  cachingMode: None
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
reclaimPolicy: Retain

Common mistakes

  • Using Immediate binding and getting pods stuck in a different zone from their disk.
  • Running databases on Azure Files SMB.
  • Leaving reclaimPolicy: Delete on critical data.
  • Forgetting VM-level IOPS limits when buying fast disks.

How to answer in the interview

"Azure Disk is ReadWriteOnce block storage, my default for databases, with Premium SSD v2 when I need tunable IOPS and throughput. Disks are zonal, so I use WaitForFirstConsumer and zone-aware scheduling or ZRS disks. Azure Files gives ReadWriteMany SMB or NFS shares for shared content. The Blob CSI driver mounts containers for big datasets like models. Ephemeral OS disks and local NVMe are fast for scratch, but data disappears with the node."

Likely follow-up questions

  • 70 GB model read by many pods? Blob or Files premium NFS mounted read-only with local caching, or pre-load to local NVMe; avoid baking it into images.
  • Why Premium SSD v2? Independent IOPS and throughput at lower cost.
  • How to resize a disk? Edit the PVC size with volume expansion enabled.
