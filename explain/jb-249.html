What is a Kafka rebalance, and when does it happen?

Kafka · concept · levels mid, senior

In one line

A rebalance is the group coordinator reassigning partitions among consumers in a group; it happens when members join, leave, crash, exceed max.poll.interval.ms, or when subscribed partitions change, and it pauses consumption unless you use cooperative or the new consumer protocol.

Detailed explanation

In a consumer group each partition is owned by exactly one member. The group coordinator (a broker) tracks membership through heartbeats. When membership or the set of partitions changes, ownership must be redistributed: that is a rebalance.

Triggers:

  • A consumer joins: scaling out, a new pod in a rolling deploy.
  • A consumer leaves gracefully (calls close) or crashes and misses heartbeats for session.timeout.ms (45 s default).
  • A consumer stops calling poll for longer than max.poll.interval.ms (5 min default) because processing is slow; it is considered stuck and kicked out.
  • Partitions are added to a subscribed topic, or a new topic matches a pattern subscription.

With the classic eager protocol, every member revokes all partitions, the group synchronises, and a new assignment is handed out: a stop-the-world pause for the whole group. Cooperative incremental rebalancing (CooperativeStickyAssignor) only moves the partitions that need to move, so other consumers keep working. Static membership (group.instance.id) lets a restarted pod reclaim its partitions without a rebalance if it returns within the session timeout, ideal for rolling restarts. Kafka 4.0 made the new consumer group protocol (KIP-848, group.protocol=consumer) generally available, which moves assignment to the broker and makes rebalances incremental and far less disruptive.

To avoid duplicates, commit processed offsets in onPartitionsRevoked of a ConsumerRebalanceListener (Spring Kafka does this for you with its container), and clean up per-partition state.

How it works

  1. A member joins, leaves or times out; the coordinator starts a rebalance.
  2. Members revoke partitions (all for eager, only moved ones for cooperative).
  3. onPartitionsRevoked runs: commit offsets, flush state.
  4. A new assignment is computed (by the group leader or, in the new protocol, the broker).
  5. onPartitionsAssigned runs; consumers resume from committed offsets.

Example

partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor
group.instance.id=${HOSTNAME}          # static membership per pod
session.timeout.ms=45000
max.poll.interval.ms=300000
max.poll.records=200
# Kafka 4.0+ clients and brokers: group.protocol=consumer
consumer.subscribe(List.of("orders"), new ConsumerRebalanceListener() {
    public void onPartitionsRevoked(Collection<TopicPartition> parts) {
        consumer.commitSync(currentOffsets);   // don't lose progress
    }
    public void onPartitionsAssigned(Collection<TopicPartition> parts) { }
});

Common mistakes

  • Slow processing inside the poll loop, causing repeated rebalances.
  • Not committing on revoke, leading to reprocessing.
  • Ignoring rebalance metrics during deployments.
  • Running more consumers than partitions and expecting more throughput.

How to answer in the interview

"A rebalance is when the group coordinator redistributes partitions among a consumer group's members. It happens when a consumer joins, leaves or crashes and stops heartbeating, when it exceeds max.poll.interval.ms because processing is too slow, or when partitions are added. With the old eager protocol everyone stops and gives up all partitions, which pauses the whole group. I use the cooperative sticky assignor or, on Kafka 4, the new consumer protocol so only affected partitions move, static membership to survive rolling restarts, and I commit offsets in onPartitionsRevoked to avoid reprocessing."

Likely follow-up questions

  • Why do deployments cause rebalance storms? Each pod leaving and joining triggers a rebalance; static membership and cooperative assignment reduce it.
  • session.timeout.ms vs max.poll.interval.ms? Heartbeat liveness from a background thread versus progress of the poll loop.
  • Can more consumers than partitions help? No, extra consumers stay idle.
