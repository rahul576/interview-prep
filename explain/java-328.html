How do you resolve dependency conflicts in Maven or Gradle?

Build Tools · concept · levels mid, senior

In one line

Conflicts come from transitive dependencies requiring different versions; Maven picks nearest wins, Gradle picks the highest version; diagnose with mvn dependency:tree or gradle dependencyInsight, and fix with dependencyManagement/BOMs, exclusions, constraints and enforcer rules.

Detailed explanation

Your project depends on library A, which needs Jackson 2.15, and library B, which needs Jackson 2.17. Only one version can be on the classpath, so the build tool must choose.

Maven uses nearest definition wins: the version closest to your project in the dependency tree is chosen, and on equal depth the one declared first. This can select an older version than some library needs. Gradle by default uses optimistic upgrade: the highest requested version wins, and it supports rich version constraints (strictly, require, prefer, reject).

The symptoms usually appear at runtime, not at compile time: NoSuchMethodError, NoClassDefFoundError, ClassNotFoundException or AbstractMethodError, because code compiled against one version calls a method missing in the chosen one.

Diagnosis: mvn dependency:tree -Dverbose -Dincludes=com.fasterxml.jackson.core shows which paths bring which versions and which were omitted for conflict. In Gradle, ./gradlew dependencyInsight --dependency jackson-databind --configuration runtimeClasspath explains why a version was selected.

Fixes:

  • Align versions centrally in <dependencyManagement> or by importing a BOM such as spring-boot-dependencies or jackson-bom, which pins a consistent, tested set of versions.
  • Exclusions to drop an unwanted transitive dependency, for example commons-logging when using SLF4J bridges.
  • In Gradle, platforms (implementation(platform(...))), constraints and version catalogs.
  • Fail fast with the Maven Enforcer dependencyConvergence rule, or Gradle's failOnVersionConflict().

How it works

  1. A runtime error or warning suggests a conflict.
  2. Inspect the tree to find which versions are requested and by whom.
  3. Choose the compatible version, usually the newest supported.
  4. Pin it via dependencyManagement, BOM or constraints.
  5. Add exclusions where a dependency should not be present at all.
  6. Add enforcer rules so new conflicts fail the build.

Example

<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>com.fasterxml.jackson</groupId>
      <artifactId>jackson-bom</artifactId>
      <version>2.17.2</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>
mvn dependency:tree -Dverbose -Dincludes=com.fasterxml.jackson.core
./gradlew dependencyInsight --dependency jackson-databind --configuration runtimeClasspath
dependencies {
    implementation(platform("org.springframework.boot:spring-boot-dependencies:3.3.4"))
    constraints { implementation("org.yaml:snakeyaml:2.2") }
}

Common mistakes

  • Overriding a version without checking compatibility with the libraries that use it.
  • Excluding a dependency that is actually needed at runtime.
  • Overriding versions managed by the Spring Boot BOM piecemeal.
  • Ignoring "omitted for conflict" until production fails.

How to answer in the interview

"Conflicts come from transitive dependencies: two libraries pull different versions of the same artifact. Maven resolves with nearest wins, the version closest to my project in the tree, while Gradle picks the highest version. Symptoms usually appear at runtime as NoSuchMethodError or ClassNotFoundException. I inspect with mvn dependency:tree or gradle dependencyInsight, then fix by aligning versions in dependencyManagement or importing a BOM like Spring Boot's, adding exclusions, or using Gradle constraints. I also add the Maven Enforcer dependencyConvergence rule so new conflicts fail the build."

Likely follow-up questions

  • Why do Spring Boot projects rarely specify versions? The Spring Boot parent or BOM manages tested versions for Spring and many common libraries.
  • Why does a conflict fail at runtime, not compile time? Compilation uses your declared API; the library was compiled against another version.
  • What is dependency convergence? All paths resolve the same version of an artifact.
