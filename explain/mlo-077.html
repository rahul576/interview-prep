What is Ray, and how is it used for ML workloads?

MLOps · concept · levels mid, senior

In one line

Ray is an open-source framework for scaling Python across a cluster with tasks and actors, plus ML libraries: Ray Data (processing, batch inference), Ray Train (distributed training), Ray Tune (hyperparameter search) and Ray Serve (online serving), running on Kubernetes via KubeRay or managed services.

Detailed explanation

Ray's core gives three primitives: tasks (remote stateless functions, @ray.remote), actors (remote stateful classes) and objects in a distributed object store. A scheduler places work on nodes according to resource requests such as num_gpus=1, and the autoscaler adds or removes nodes. You write ordinary Python, which is the main appeal for ML engineers.

On top sit the Ray AI libraries:

  • Ray Data: distributed, streaming data loading and transformation, feeding GPUs during training and doing batch inference at scale with heterogeneous CPU and GPU stages.
  • Ray Train: distributed training for PyTorch, Hugging Face, Lightning, XGBoost and others; it sets up workers and process groups, handles checkpoints and fault tolerance (restarting failed workers).
  • Ray Tune: hyperparameter optimisation with search algorithms (random, Bayesian via Optuna) and early-stopping schedulers such as ASHA, running many trials in parallel.
  • Ray Serve: online serving with autoscaling, model composition (several models and business logic in one application), dynamic batching and fractional GPUs. It is widely used for LLM serving with vLLM.

Deployment: on a laptop for development, on Kubernetes with the KubeRay operator (RayCluster, RayJob, RayService custom resources), on VMs, or managed via Anyscale and cloud offerings that integrate Ray. Ray emphasises one framework across data prep, training, tuning and serving, rather than stitching Spark, a training operator, a tuning tool and a separate serving system.

How it works

  1. Start a Ray cluster: head node plus workers (via KubeRay).
  2. Submit a job with ray job submit or a RayJob resource.
  3. The scheduler places tasks and actors on nodes with requested CPUs or GPUs.
  4. Libraries (Data, Train, Tune) build on these primitives.
  5. The autoscaler adds nodes for pending work and removes idle ones.
  6. Ray Serve deployments run as long-lived actors behind an HTTP proxy.

Example

import ray
from ray import serve
ray.init()
ds = ray.data.read_parquet("s3://bucket/reviews/")
class Scorer:
    def __init__(self): self.model = load_model()
    def __call__(self, batch): batch["score"] = self.model(batch["text"]); return batch
ds.map_batches(Scorer, concurrency=4, num_gpus=1, batch_size=256).write_parquet("s3://bucket/scored/")

@serve.deployment(num_replicas="auto", ray_actor_options={"num_gpus": 1})
class Api:
    def __init__(self): self.model = load_model()
    async def __call__(self, req): return {"score": self.model((await req.json())["text"])}
serve.run(Api.bind())

Common mistakes

  • Using Ray for simple single-node jobs where it adds overhead.
  • Passing huge objects into many tasks instead of ray.put once.
  • Running large clusters without autoscaling limits or resource requests.
  • Treating Ray as a replacement for SQL-heavy ETL, where Spark or a warehouse fits better.

How to answer in the interview

"Ray is a distributed Python framework built on tasks and actors with a scheduler that understands CPUs and GPUs. On top are libraries: Ray Data for distributed preprocessing and batch inference, Ray Train for distributed training with fault tolerance, Ray Tune for hyperparameter searches with early stopping, and Ray Serve for serving and composing models with autoscaling, popular with vLLM for LLMs. I'd run it on Kubernetes with KubeRay or use a managed service. Its strength is one Python framework across the lifecycle."

Likely follow-up questions

  • Spark or Ray for preprocessing? Spark for large SQL-style ETL and joins on tabular data; Ray for Python-heavy, GPU-involved or ML-specific pipelines.
  • What does KubeRay provide? CRDs to run Ray clusters, jobs and services natively on Kubernetes.
  • How does Ray Tune save compute? Early-stopping schedulers like ASHA kill poor trials early.
