What is Terraform state, and how should a team manage it?

Infrastructure as Code · concept · levels entry, mid

In one line

Terraform is declarative IaC: you describe resources in HCL, providers call the cloud APIs, plan shows the diff and apply makes it; the state file maps configuration to real resource IDs and attributes, so teams must keep it in a remote, encrypted, versioned backend with locking, restrict access because it contains secrets, and review plans in pull requests.

Detailed explanation

When you write resource "aws_s3_bucket" "logs" {...}, Terraform needs to remember that this block corresponds to the real bucket acme-logs-prod with a specific ARN. That mapping, plus all known attributes and dependency information, lives in the state (terraform.tfstate, JSON). On every plan, Terraform refreshes state from the real APIs, compares it with the configuration and computes the actions: create, update in place, replace or destroy.

For a team, a local state file is dangerous: it lives on one laptop, two people can apply from different copies, and it can be lost. Git is worse: no locking and secrets in history. The solution is a remote backend:

  • S3 with versioning (to recover older states), encryption (SSE-KMS) and locking, either the classic DynamoDB table or the newer native S3 lock file (use_lockfile = true, Terraform 1.10+), which makes DynamoDB unnecessary.
  • Azure Storage (locking via blob leases), GCS, or HCP Terraform / Terraform Enterprise, which also runs plans remotely.

Locking ensures only one operation modifies state at a time. State is sensitive: database passwords, generated keys and connection strings are stored in plain text inside it, even for variables marked sensitive. So restrict who can read the bucket, encrypt it, and prefer generating secrets in a secret manager.

Workflow: changes go through pull requests; CI runs plan and posts it for review; after approval, CI applies exactly that plan. Split state by environment and component to limit blast radius.

How it works

  1. terraform init configures the backend and downloads providers.
  2. plan acquires the lock, refreshes state, diffs, shows changes.
  3. apply executes, writes updated state to the backend, releases the lock.
  4. The backend keeps versions for recovery.
  5. Other configurations can read outputs via terraform_remote_state or data sources.

Example

terraform {
  required_version = ">= 1.10"
  backend "s3" {
    bucket       = "acme-tfstate-prod"
    key          = "network/terraform.tfstate"
    region       = "eu-west-1"
    encrypt      = true
    use_lockfile = true      # native S3 locking; older setups use dynamodb_table
  }
}

Common mistakes

  • Committing terraform.tfstate to Git.
  • One giant state for everything, so every plan is slow and risky.
  • Giving all developers read access to state that contains passwords.
  • Applying from laptops instead of a controlled pipeline.
  • Hand-editing state JSON.

How to answer in the interview

"Terraform is declarative: I describe resources in HCL, providers talk to APIs like AWS, plan shows the changes and apply makes them. The state file maps each resource in the code to the real resource ID and its attributes, so Terraform knows what exists and can compute diffs. For a team, state must never be on a laptop or in Git. I use a remote backend like S3 with versioning, encryption and locking, now with the native S3 lock file instead of DynamoDB, or HCP Terraform, so two people can't apply at once. State can contain secrets, so access is restricted. All changes go through PRs where the plan is reviewed, and CI applies the approved plan."

Likely follow-up questions

  • State corrupted or resource deleted manually? Restore a previous state version from the bucket; for deleted resources, plan will recreate them, or state rm if they should go.
  • Why split state? Smaller blast radius, faster plans and clearer ownership.
  • How do you read another state's outputs? terraform_remote_state or, better, data sources or SSM parameters.
