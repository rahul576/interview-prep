Explain the differences between POST, PUT and PATCH, and what idempotency means.

REST & API Design · concept · levels entry, mid

In one line

POST creates (or triggers actions) and is not idempotent; PUT replaces the whole resource at a known URI and is idempotent; PATCH applies a partial update and is not guaranteed idempotent; idempotent means repeating a request has the same effect on server state as sending it once.

Detailed explanation

POST sends data to a collection resource, and the server decides the new resource's identity: POST /orders creates an order and returns 201 Created with a Location header pointing to /orders/123. Sending it twice creates two orders, so POST is not idempotent. POST is also used for actions that do not fit CRUD.

PUT sends the complete representation to a URI the client knows: PUT /users/42/address. The server replaces the resource with it (or creates it if allowed). Fields missing from the body are cleared or reset. Sending the same PUT ten times leaves the same state, so PUT is idempotent. Responses: 200 OK with the body, 204 No Content, or 201 if it was created.

PATCH (RFC 5789) sends only changes. Common formats are JSON Merge Patch (RFC 7396, a partial document where null deletes a field) and JSON Patch (RFC 6902, a list of operations). A merge patch setting status to SHIPPED is effectively idempotent, but a JSON Patch "add item to array" is not, which is why PATCH is not guaranteed idempotent.

Idempotency concerns the effect on server state, not the response: a second DELETE /orders/7 may return 404 instead of 204, but the order is still deleted, so DELETE is idempotent. Idempotent methods per RFC 9110 are GET, HEAD, OPTIONS, PUT and DELETE. This matters because networks fail: if a client times out, it can safely retry an idempotent request. For POST, make retries safe with an Idempotency-Key header: the server stores the key with the first result and returns the same response for repeats.

Other typical statuses: 400 invalid body, 404 resource not found, 409 conflict, 412 when an If-Match precondition fails.

How it works

  1. POST to a collection: server assigns id, returns 201 + Location.
  2. PUT to an item: full replacement, idempotent.
  3. PATCH to an item: apply partial changes in a defined format.
  4. Retries: safe for idempotent methods; POST needs an idempotency key.

Example

POST /orders
Idempotency-Key: 7f3c9a1e-...
Content-Type: application/json

{"customerId": 5, "items": [{"sku": "A1", "qty": 2}]}

HTTP/1.1 201 Created
Location: /orders/123
PATCH /orders/123
Content-Type: application/merge-patch+json

{"status": "CANCELLED"}

Common mistakes

  • Using PUT with a partial body, wiping other fields.
  • Claiming PATCH is always idempotent.
  • Thinking idempotent means "same response".
  • Retrying POST payments without an idempotency key.

How to answer in the interview

"POST usually creates a resource under a collection; the server assigns the id and returns 201 with a Location header. It's not idempotent, so sending it twice creates two resources. PUT replaces the entire resource at a known URI with what I send, and it's idempotent: repeating it leaves the same state. PATCH is a partial update, for example with JSON Merge Patch, and isn't guaranteed idempotent. Idempotent means the effect on the server is the same whether the request is sent once or many times, which makes retries safe; GET, PUT and DELETE are idempotent. For POSTs like payments I add an idempotency key header so retries don't double-charge."

Likely follow-up questions

  • How would you implement an idempotency key for a payment API? Store key plus request hash and response under a unique constraint; repeats return the stored response.
  • Is DELETE idempotent if the second call returns 404? Yes, the state is the same.
  • Can PUT create a resource? Yes, if the client chooses the URI, returning 201.
