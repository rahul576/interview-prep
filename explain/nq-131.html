What is the difference between association, aggregation, and composition?

Core Java & OOP · concept · levels entry, mid

In one line

All three are object relationships of increasing strength: association is a general "uses/knows" link with independent lifecycles; aggregation is a weak whole-part ("has-a") where parts can exist alone and be shared; composition is strong, exclusive ownership where the part's lifecycle is bound to the whole.

Detailed explanation

Association is the broadest term. Two classes are associated if one holds or uses a reference to the other. Neither owns the other, and each can be created and destroyed independently. Examples: a teacher and a student, a doctor and a patient, a customer and a bank. Associations have multiplicity (one-to-one, one-to-many, many-to-many) and direction (unidirectional or bidirectional).

Aggregation is a specialised association expressing a whole-part relationship with weak ownership. The whole groups the parts, but the parts have their own lifecycle: they can exist before the whole, outlive it and even belong to several wholes. A department aggregates professors; a playlist aggregates songs; a team aggregates players. In UML it is drawn with an empty (hollow) diamond at the whole's end.

Composition is a stronger whole-part relationship with exclusive ownership. A part belongs to exactly one whole at a time, is typically created by it, and is destroyed when the whole is destroyed. A house and its rooms, an order and its order lines, an invoice and its line items. In UML it is a filled (black) diamond.

Why it matters in practice: these concepts drive real design decisions. Composition parts are internal implementation details, created inside the owner and not shared, and in persistence they get cascade delete and orphan removal. Aggregated and associated objects are external collaborators, usually injected, and must never be deleted along with the referencing object. In domain-driven design, a composition is close to an aggregate root and its internal entities.

Note: in Java code all three look like fields holding references; the difference is in ownership semantics and lifecycle management, not syntax.

How it works

  1. Ask "does one object merely use the other?" - association.
  2. Ask "is it a whole-part relationship?" - aggregation or composition.
  3. Ask "can the part exist without, or be shared beyond, the whole?" - yes: aggregation; no: composition.
  4. Reflect the answer in construction (inject vs create), encapsulation and persistence cascades.

Example

class Teacher { private final Set<Student> students = new HashSet<>(); }   // association

class Department {                                                         // aggregation
    private final List<Professor> professors;
    Department(List<Professor> professors) { this.professors = new ArrayList<>(professors); }
}

class Order {                                                              // composition
    private final List<OrderLine> lines = new ArrayList<>();
    void addItem(String sku, int qty) { lines.add(new OrderLine(sku, qty)); } // created inside
    List<OrderLine> lines() { return List.copyOf(lines); }                  // not handed out to mutate
}

Common mistakes

  • Saying the difference is visible in Java syntax.
  • Calling everything composition because it "has a field".
  • Cascading deletes over aggregations.
  • Exposing composition parts so external code can keep or move them.

How to answer in the interview

"All three describe how objects relate. Association is the general case: one object uses or knows another and both have independent lifecycles, like a teacher and a student. Aggregation is a whole-part association with weak ownership: the parts can exist without the whole and can be shared, like a department and its professors; UML draws it with a hollow diamond. Composition is strong ownership: the part belongs to exactly one whole and dies with it, like a house and its rooms or an order and its order lines; that's a filled diamond. In code it changes whether I create parts internally or inject them, and whether deletes cascade."

Likely follow-up questions

  • How would you model composition in Java code? Create parts inside the owner, keep them private, expose copies or behaviour only.
  • Is inheritance one of these? No, it's an is-a relationship, a different category.
  • How does it map to JPA? Composition: cascade ALL plus orphanRemoval; aggregation: no cascade delete.
