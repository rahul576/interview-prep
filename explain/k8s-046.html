How do you reduce Kubernetes infrastructure costs without hurting reliability?

Kubernetes · design · levels mid, senior, lead

In one line

Most waste is over-requested resources, so rightsize requests from real usage (VPA recommendations), improve bin packing with node autoscaling and Karpenter consolidation, move tolerant work to spot, scale down non-production, and make cost visible per team with OpenCost or Kubecost, while keeping PDBs, headroom and SLO checks.

Detailed explanation

Kubernetes bills you for nodes, but the scheduler packs nodes by requests, not usage. If a service requests 2 CPU and uses 0.2, the remaining 1.8 CPU is reserved and paid for but idle. In most clusters, the gap between requested and used resources is the single largest cost, often more than half of node capacity. So the first lever is rightsizing: compare requests with real usage percentiles over a few weeks (Prometheus, VPA in recommendation mode, Goldilocks) and lower them team by team.

Lower requests only save money if nodes are then removed. Cluster autoscaler scale-down or Karpenter consolidation packs pods onto fewer, better-fitting nodes and deletes empty or underused ones. Choosing suitable instance families (including arm64, often cheaper per unit of performance) helps.

Spot or preemptible capacity costs a fraction of on-demand. It suits stateless services with several replicas spread across zones, CI runners and batch jobs, provided they handle interruption notices and graceful shutdown. Non-production clusters and namespaces can scale to zero at night and weekends. Cost allocation per namespace or team with OpenCost or Kubecost turns cost into something teams own.

Reliability guards: PodDisruptionBudgets so consolidation cannot take down all replicas, topology spread across zones, an on-demand base for critical services, some headroom for spikes (possibly low-priority placeholder pods), and checking SLO dashboards after each change.

How it works

  1. Measure: cost per namespace, requests vs p95 usage.
  2. Rightsize requests in small steps; keep memory request close to real peak.
  3. Enable consolidation or autoscaler scale-down; review instance types.
  4. Move tolerant workloads to spot with interruption handling.
  5. Schedule non-production scale-down.
  6. Protect with PDBs, spread constraints and on-demand for critical paths.
  7. Watch SLOs and roll back if latency, OOMKills or errors rise.

Example

apiVersion: karpenter.sh/v1
kind: NodePool
metadata: { name: general }
spec:
  template:
    spec:
      requirements:
        - { key: karpenter.sh/capacity-type, operator: In, values: ["spot", "on-demand"] }
        - { key: kubernetes.io/arch, operator: In, values: ["amd64", "arm64"] }
      nodeClassRef: { group: karpenter.k8s.aws, kind: EC2NodeClass, name: default }
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 5m

Common mistakes

  • Cutting memory requests below real peaks, causing OOMKills and node pressure evictions.
  • Lowering requests but never letting nodes scale down.
  • Putting singletons or stateful primaries on spot.
  • Missing PDBs, so consolidation evicts all replicas at once.

How to answer in the interview

"Most waste comes from requests far above real usage, so I start by comparing requests with actual usage and VPA recommendations and rightsize team by team. Then I make sure the savings turn into fewer nodes, with Karpenter consolidation or autoscaler scale-down and suitable instance types. Tolerant workloads move to spot, and non-production scales down out of hours. OpenCost or Kubecost shows each team its spend. To protect reliability I keep PDBs, zone spreading, on-demand for critical services, some headroom, and I check SLO dashboards after every change."

Likely follow-up questions

  • Why can lowering requests increase incidents? Pods get packed tightly, then contend for CPU or get OOMKilled and evicted under real peaks.
  • Should you use HPA and VPA together? Not on the same CPU/memory metric; VPA for recommendations, HPA for replicas.
  • Reserved instances or savings plans? Yes, for the stable on-demand baseline.
