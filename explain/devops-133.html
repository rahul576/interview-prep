A terraform apply failed halfway through. How do you recover?

Infrastructure as Code · scenario · levels mid, senior

In one line

Don't panic or delete things: Terraform writes each resource to state as soon as it is created, so a partial apply usually leaves a consistent state; read the error and fix the root cause, re-run plan to see what remains, apply again, carefully force-unlock a stale lock, and repair mismatches with import or state rm, never by hand-editing state.

Detailed explanation

Terraform applies changes in dependency order and, for each resource, updates the state after the provider reports success. If the apply fails halfway, resources that were created are already in state; resources not yet attempted are simply still pending; the one that failed may be marked tainted (created but failed later steps), so it will be replaced next time. Because Terraform is declarative, the normal recovery is to fix the cause and run it again: the next plan shows only the remaining work.

Typical causes: quotas, missing IAM permissions, invalid arguments, API rate limits, name conflicts or eventual consistency (an IAM role not yet visible). Fix the cause, then plan again.

Edge cases:

  • Stale lock: if the CI job was killed, the lock may remain. Confirm nobody else is running (check pipelines, ask the team), then terraform force-unlock <LOCK_ID>. Forcing a lock while someone is applying can corrupt state.
  • Created but not recorded: if the process crashed between creation and state write, the resource exists but Terraform doesn't know it; the next apply fails with "already exists". Adopt it with terraform import or an import block.
  • State references something gone: remove it with terraform state rm or let plan recreate it.
  • Corrupted or lost state: restore a previous version from the versioned backend bucket; Terraform also writes errored.tfstate locally if it can't save state remotely, which you push with terraform state push.

How it works

  1. Stop and read the error; don't delete resources manually.
  2. Fix root cause (quota, permission, argument).
  3. terraform plan to see remaining and replacement actions.
  4. Resolve lock or state mismatches if present.
  5. terraform apply again; verify a clean plan afterwards.
  6. Postmortem: add checks or policies to prevent recurrence.

Example

terraform plan -out=tfplan             # shows what is still missing
terraform force-unlock 6c1a7e2b-...    # only after confirming no other run is active
terraform import aws_iam_role.app app-role-prod      # resource exists but not in state
terraform state rm aws_route53_record.old            # state points to something deleted
terraform state push errored.tfstate                 # if apply couldn't upload state
terraform apply tfplan

Common mistakes

  • Deleting partially created resources in the console, causing more drift.
  • Force-unlocking while a colleague's apply is still running.
  • Editing terraform.tfstate JSON manually.
  • Running apply -auto-approve repeatedly without reading the plan.

How to answer in the interview

"First, I don't panic or start deleting things. Terraform records each resource in state as soon as it's created, so a partial apply usually leaves state consistent for what was created. I read the error and fix the root cause, maybe a quota, a missing permission or an invalid argument, then run plan to see the remaining changes and apply again. If the crashed run left the lock behind, I confirm nobody else is running and use force-unlock carefully. If a resource was created but not recorded, I bring it in with terraform import; if state references something that no longer exists, I use state rm. I never edit the state file by hand, and versioned state lets me restore if needed."

Likely follow-up questions

  • How do you prevent concurrent applies? Remote backend locking and applies only from one CI pipeline with concurrency limits.
  • What does tainted mean? The resource will be destroyed and recreated on next apply; -replace does this deliberately.
  • How do you recover a corrupted state? Restore an earlier version from the versioned bucket and reconcile with plan.
