What is the Java String Constant Pool?

Core Java & OOP · concept · levels entry, mid

In one line

The String Constant Pool (string pool) is a JVM-wide table, in the heap since Java 7, holding one shared instance per string literal; literals and compile-time constants are interned and reused, while new String creates a separate object, which is safe only because String is immutable.

Detailed explanation

Applications use the same strings over and over: "id", "status", "ACTIVE", HTTP header names. Storing a separate copy each time would waste memory, so the JVM interns string literals. When a class is loaded and its code first uses a literal, the JVM looks up the string table; if an equal string exists, the existing instance is used, otherwise the new one is added. So String a = "Java"; String b = "Java"; gives two variables pointing to the same object, and a == b is true.

Details worth knowing:

  • Compile-time constant expressions are folded and pooled too: "Ja" + "va" and final String x = "Ja"; x + "va" produce the pooled "Java". Concatenation involving non-final variables happens at runtime and creates a new, non-pooled String.
  • new String("Java") always allocates a new heap object (the literal "Java" itself is still in the pool), so "Java" == new String("Java") is false.
  • intern() returns the pooled instance for any string, adding it if absent.
  • Location: until Java 6 the pool lived in PermGen, which was small and could throw OutOfMemoryError: PermGen space. Since Java 7 it is in the main heap, and pooled strings that are no longer referenced can be garbage-collected. Its hash table size is tunable with -XX:StringTableSize.
  • Immutability is what makes sharing safe. If one piece of code could change a pooled "ACTIVE" to "DELETED", every other user of that literal would be affected.

This is different from G1 string deduplication (-XX:+UseStringDeduplication), which shares the underlying byte arrays of equal String objects without making them the same object.

How it works

  1. The class file's constant pool records each literal.
  2. On first resolution, the JVM checks the global string table.
  3. If present, it reuses the existing instance; otherwise it creates and registers one.
  4. Later uses of that literal in any class get the same reference.
  5. Unreferenced entries are cleaned up by the GC.

Example

String a = "Java";
String b = "Java";
String c = new String("Java");
String d = "Ja" + "va";           // folded at compile time
String part = "Ja";
String e = part + "va";           // built at runtime

System.out.println(a == b);           // true  (same pooled object)
System.out.println(a == c);           // false (new heap object)
System.out.println(a == d);           // true
System.out.println(a == e);           // false
System.out.println(a == e.intern());  // true

Common mistakes

  • Using == to compare strings because it "works" with literals.
  • Believing the pool is still in PermGen and never collected.
  • Interning everything, bloating the string table.
  • Confusing the class-file constant pool with the runtime string pool.

How to answer in the interview

"The string pool is a special table inside the heap, since Java 7, where the JVM keeps one shared copy of each string literal. If I write String a = "Java" and String b = "Java", both point to the same pooled object, so memory is saved. Compile-time constant expressions are pooled too. new String("Java") always creates a separate heap object outside the pool, unless I call intern on it. This sharing is only safe because String is immutable. In real code I still always compare strings with equals."

Likely follow-up questions

  • Can strings in the pool be garbage collected? Yes, since Java 7 unreferenced pooled strings are collectable.
  • Why was the pool moved out of PermGen? PermGen was small and fixed, causing OOMs.
  • What is string deduplication? A G1 feature sharing backing arrays of equal strings.
