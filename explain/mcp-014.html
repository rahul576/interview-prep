Compare the stdio and Streamable HTTP transports in MCP.

MCP Servers · concept · levels entry, mid, senior

In one line

stdio runs the server as a local subprocess exchanging newline-delimited JSON-RPC over stdin/stdout (logs on stderr), ideal for developer tools; Streamable HTTP exposes one HTTP endpoint receiving POSTs and answering with JSON or an SSE stream, for remote, shared servers that need authentication and network security.

Detailed explanation

stdio. The host launches the server as a child process (e.g. npx some-server or uv run server.py) and writes JSON-RPC messages to its stdin; the server writes responses and notifications to stdout. Each message is one line of JSON, with no embedded newlines. Because stdout is the protocol channel, anything else printed there corrupts the stream, so logs must go to stderr, which hosts typically capture into their log files. stdio is simple, fast, works offline and needs no ports. Trust follows the OS user: the server runs with the user's permissions, and credentials are usually passed via environment variables in the host config. The downsides: it only works on the same machine, each user installs and updates the server, and every user holds their own secrets.

Streamable HTTP, introduced in the 2025-03-26 revision, is for remote servers. The server exposes a single endpoint, such as https://mcp.example.com/mcp. The client sends each JSON-RPC message as an HTTP POST, with Accept: application/json, text/event-stream. The server either returns a single JSON response or opens a server-sent events (SSE) stream for that request when it needs to send progress notifications or several messages before the final response. Handshake-based revisions also allow an optional GET stream for server-initiated messages and an Mcp-Session-Id header.

Because it is network-reachable, Streamable HTTP needs TLS, authentication (normally OAuth 2.1 bearer tokens per the MCP authorization spec), Origin validation, rate limiting, request size limits and input validation, like any web API. In return it offers central deployment, one place to update and audit, per-user authorisation, and access from web and mobile hosts.

How it works

  1. stdio: host spawns process → writes line-delimited JSON to stdin → reads stdout → captures stderr.
  2. HTTP: client POSTs JSON-RPC to the endpoint with a bearer token.
  3. Server replies Content-Type: application/json or text/event-stream.
  4. With SSE, progress notifications stream first, then the final response; the stream closes.

Common mistakes

  • Printing logs or banners to stdout in a stdio server.
  • Running an HTTP server without authentication "because it's internal".
  • Binding a local HTTP server to 0.0.0.0.
  • Using the deprecated HTTP+SSE transport for new servers.

How to answer in the interview

"With stdio, the host launches the server as a local subprocess and exchanges newline-delimited JSON-RPC over stdin and stdout. It's simple and fast, trust follows the OS user, and credentials usually come from environment variables; logs must go to stderr because stdout is the protocol channel. Streamable HTTP is for remote servers: one HTTP endpoint, each message is a POST, and the server answers with plain JSON or an SSE stream when it needs to send progress or several messages. Because it's on the network it needs TLS, OAuth 2.1, rate limiting and normal web security. stdio suits developer tools; HTTP suits shared and enterprise services."

Likely follow-up questions

  • Why remote servers even for internal tools? Central updates, audit, per-user OAuth and no secrets on laptops.
  • Can a stdio server be remote? Only via a proxy or bridge that wraps it in HTTP.
  • Why SSE inside HTTP? To stream progress and multiple messages for one request without WebSockets.
