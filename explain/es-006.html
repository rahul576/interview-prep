What are aggregations in Elasticsearch? Give examples.

Elasticsearch · concept · levels mid, senior

In one line

Aggregations compute analytics over the documents matching a query. Bucket aggregations group them (terms, date_histogram, range), metric aggregations compute values (avg, sum, percentiles, cardinality), and pipeline aggregations work on other aggregations' output (derivative, moving_fn, bucket_sort). They run on keyword, numeric and date fields via doc values, and some are approximate.

Detailed explanation

Aggregations are why Elasticsearch powers dashboards (Kibana) and faceted search ("Brand: Acme (124)"). They run on the same filtered result set as the query, so a search and its facets come back in one request. Use "size": 0 when you only want the numbers.

Bucket aggregations create groups, and can nest:

  • terms: top values of a field (top 10 brands)
  • date_histogram: counts per minute, hour or day (calendar_interval or fixed_interval)
  • range / histogram: price bands
  • filters, composite (paginate through all buckets), significant_terms

Metric aggregations compute numbers, overall or inside each bucket: avg, sum, min, max, stats, value_count, percentiles (p95 latency), cardinality (distinct count), top_hits.

Pipeline aggregations take other aggregations as input: derivative (rate of change), cumulative_sum, moving_fn (moving averages), bucket_script, bucket_selector (HAVING-like filtering), bucket_sort.

Data structures: aggregations read doc values (columnar), so they work on keyword, numeric, date, IP and boolean fields. Aggregating on an analysed text field is disabled by default. Enabling fielddata loads terms into heap and is a classic memory killer. Use the .keyword sub-field instead.

Approximate by design:

  • terms over multiple shards: each shard returns its local top shard_size terms, and the coordinator merges them. A term that is moderately common on every shard but never in any local top list can be undercounted or missed (doc_count_error_upper_bound reports the bound). Raise shard_size, or use composite for exact exhaustive results.
  • cardinality uses HyperLogLog++ (exact below precision_threshold, approximate above).
  • percentiles uses TDigest (accurate at the extremes, approximate in the middle). hdr is an alternative.

How it works

  1. The query and filters select the documents on each shard.
  2. Each shard builds its buckets and metrics from doc values.
  3. Shards return partial results (the top shard_size for terms).
  4. The coordinating node reduces and merges them.
  5. Pipeline aggregations run on the merged buckets.

Example

GET /orders/_search
{
  "size": 0,
  "query": { "range": { "createdAt": { "gte": "now-7d/d" } } },
  "aggs": {
    "per_day": {
      "date_histogram": { "field": "createdAt", "calendar_interval": "day" },
      "aggs": {
        "revenue":   { "sum": { "field": "total" } },
        "p95_total": { "percentiles": { "field": "total", "percents": [95] } },
        "buyers":    { "cardinality": { "field": "customerId" } },
        "growth":    { "derivative": { "buckets_path": "revenue" } }
      }
    },
    "top_brands": { "terms": { "field": "brand.keyword", "size": 5 } }
  }
}

Common mistakes

  • Aggregating on text fields, or enabling fielddata.
  • terms aggregations with a huge size on high-cardinality fields (memory and latency). Use composite.
  • Treating cardinality or terms results as exact.
  • Forgetting size: 0 and fetching hits you don't need.

How to answer in the interview

"Aggregations compute analytics over the documents a query matches. Bucket aggregations group documents, like terms for top values or date_histogram for counts per hour. Metric aggregations compute values such as avg, sum, percentiles and cardinality, inside each bucket if nested. Pipeline aggregations work on other aggregations' output, like derivatives or moving averages. They run on keyword, numeric and date fields using doc values, not on analysed text. Some results are approximate by design: terms counts across shards, cardinality via HyperLogLog, and percentiles via TDigest."

Likely follow-up questions

  • Why are terms counts slightly wrong? Each shard returns only its local top terms, so the merge can miss counts. Raise shard_size or use composite.
  • Paging through all buckets? The composite aggregation with after_key.
  • Heavy dashboards? Transforms or rollups into summary indices, plus a sensible time range.
