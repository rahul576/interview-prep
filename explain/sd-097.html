Design a distributed file system like HDFS or Google File System.

Classic Design Problems · design · levels senior, lead

In one line

A distributed file system like HDFS/GFS splits files into large blocks (64-128 MB), keeps the namespace and block map on a metadata server (NameNode), stores 3 replicas of each block on data nodes across racks, lets clients stream data directly to data nodes, and uses heartbeats to trigger re-replication.

Detailed explanation

GFS (2003) and HDFS were designed for very large files, high sequential throughput and commodity hardware that fails constantly. They favour write-once, read-many (append) workloads such as logs and batch analytics, not low-latency random writes.

Large blocks keep metadata small (a 1 TB file is only about 8,000 blocks at 128 MB) and make reads long and sequential. The metadata server holds the directory tree, permissions and the block-to-node mapping in memory for speed, made durable with a write-ahead edit log and periodic checkpoints (fsimage). Block locations are not persisted; they are rebuilt from block reports sent by data nodes.

Data nodes store blocks as local files. Replication (default 3) uses rack awareness: e.g. one replica on the writer's rack and two on another rack, so losing a whole rack loses no data. Writes flow through a replication pipeline: client -> DN1 -> DN2 -> DN3, with acknowledgements back, so the client sends data once.

Because data never flows through the metadata server, it is not a bandwidth bottleneck; it is, however, a single point of failure and a memory limit. HDFS addresses this with HA NameNodes (active/standby sharing edits via a JournalNode quorum and ZooKeeper failover) and federation to split the namespace. Modern systems (Colossus, and object stores like S3) shard metadata across a distributed database.

How it works

  1. Client asks the NameNode to create a file; NameNode picks data nodes for the first block.
  2. Client streams the block through the DN pipeline; each DN writes and forwards.
  3. After all blocks are written, the NameNode records the file as complete.
  4. To read, the client gets block locations and reads from the closest replica, verifying checksums.
  5. DNs heartbeat every few seconds and send block reports.
  6. If a DN misses heartbeats, the NameNode schedules copies of its blocks to restore the replication factor.

Example

hdfs dfs -put clickstream-2026-11-20.log /data/raw/
hdfs fsck /data/raw/clickstream-2026-11-20.log -files -blocks -locations
# Shows each 128 MB block and the 3 data nodes (on 2 racks) holding it
hdfs dfs -setrep -w 2 /data/archive/old.log   # lower replication for cold data

Common mistakes

  • Saying the client sends data through the NameNode.
  • Ignoring the small-files problem: millions of tiny files exhaust NameNode memory.
  • Placing all three replicas on one rack.
  • Forgetting checksums to detect silent disk corruption.

How to answer in the interview

"These systems target huge files and throughput. Files are split into 128 MB blocks. A metadata server, the NameNode, keeps the namespace and block locations in memory, with an edit log and checkpoints for durability. Data nodes store blocks, each replicated three times across racks. Clients get block locations from the NameNode, then read and write directly to data nodes, with writes going through a replication pipeline. Heartbeats and block reports detect failures and trigger re-replication. The NameNode is made highly available with a standby and a shared edit log, and federation splits the namespace for scale."

Likely follow-up questions

  • Why are small files a problem? Each file and block costs NameNode memory and adds per-file overhead; combine them into sequence files or larger Parquet files.
  • How is consistency handled? Single writer per file with leases; data visible after close or hflush.
  • Erasure coding? HDFS 3 supports it for cold data, cutting storage overhead from 200% to about 50%.
