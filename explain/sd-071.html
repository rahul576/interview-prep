How do you build security into a system design from the start?

Scalability & Reliability · concept · levels senior, lead

In one line

Security by design: threat model first, then standard authN (OAuth 2.0/OIDC, MFA), authZ at every service with least privilege and object-level checks, encryption in transit and at rest, secrets in a vault, zero-trust segmentation, edge protection and audit logging.

Detailed explanation

Retrofitting security is expensive; designing it in is cheap. Threat modelling (e.g. STRIDE: spoofing, tampering, repudiation, information disclosure, denial of service, elevation of privilege) over a data-flow diagram identifies assets, trust boundaries and the controls that matter.

Authentication: never build your own password system if you can avoid it; use an identity provider (Entra ID, Okta, Auth0, Cognito, Keycloak) with OIDC, MFA, short-lived access tokens and refresh tokens. Services authenticate to each other with mTLS or workload identity, not shared API keys.

Authorization: enforce in every service, not just the gateway. RBAC for coarse roles, ABAC/policies (OPA, Cedar) for fine-grained rules, and always object-level checks (does this user own invoice 123?) to prevent IDOR, the most common API vulnerability (OWASP API #1).

Data protection: TLS 1.2+ everywhere; encryption at rest with KMS-managed keys; field-level encryption or tokenisation for card numbers and identifiers.

Secrets: Vault/Key Vault/Secrets Manager, injected at runtime, rotated, never in Git or images.

Network: zero trust (authenticate every call), segmentation and private endpoints to limit blast radius. Edge: WAF, rate limiting, input validation, DDoS protection. Detection: audit logs of security events into a SIEM.

How it works

  1. Threat model per feature/architecture change.
  2. IdP + OIDC for users; mTLS/workload identity for services.
  3. Policy checks per request; tenant ID from token, never from request body.
  4. Secrets from vault; keys in KMS.
  5. Security tests in CI (SAST, dependency scanning, DAST).

Example

@GetMapping("/invoices/{id}")
Invoice get(@PathVariable UUID id, @AuthenticationPrincipal Jwt jwt) {
  Invoice inv = repo.findById(id).orElseThrow(NotFound::new);
  if (!inv.tenantId().equals(jwt.getClaim("tenant_id"))) throw new NotFound(); // object-level check
  return inv;
}

Common mistakes

  • Authorization only at the gateway.
  • Long-lived static credentials.
  • Trusting client-supplied tenant or user IDs.
  • Logging tokens or personal data.

How to answer in the interview

"I start with a threat model to find trust boundaries. Users authenticate through an identity provider with OIDC and MFA; services use mTLS or workload identities. Every service enforces authorization, including object-level checks that the resource belongs to the caller's tenant. Data is encrypted in transit and at rest, secrets come from a vault, the network is segmented with zero-trust principles, and security events go to audit logs."

Likely follow-up questions

  • Tenant isolation in a shared DB? Tenant ID from token, row-level security, tests for IDOR.
  • JWT revocation? Short expiry + refresh tokens + deny list for emergencies.
  • Where do you validate input? At every boundary; schema validation at the gateway and service.
