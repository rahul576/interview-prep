Design a flash sale system where 1 million users try to buy 10,000 discounted items at noon.

Classic Design Problems · design · levels mid, senior

In one line

A flash sale serves static pages from a CDN, keeps stock in Redis decremented atomically (Lua), rejects early once sold out, meters users with tokens/waiting room, creates orders asynchronously from a queue, blocks bots with rate limits, and releases unpaid reservations after a timeout.

Detailed explanation

At 12:00:00, a million users click "Buy" for 10,000 items. 99% of requests must fail, quickly and cheaply. The database must see only ~10,000 order writes.

Before the sale: pre-render pages, push to CDN; load stock into Redis; scale gateways; warm caches.

At the sale: each attempt hits the gateway (rate-limited per user/device/IP) and runs a Lua script in Redis that checks the user hasn't already bought, checks stock, decrements and records the reservation atomically. Once stock hits zero, a "sold out" flag lets the edge reject immediately without touching Redis.

After a successful reservation: a message goes to a queue; order services consume at a controlled rate and create orders, take payment, etc. The user sees "you got it, complete payment within 10 minutes". Unpaid reservations expire and stock is returned (possibly for a second wave).

Recovery: Redis is persisted/replicated, and reservations are also in the queue, so the DB can be reconciled if Redis fails.

How it works

  1. CDN page with countdown (server time sync).
  2. POST /flash/buy → gateway rate-limit → Redis Lua reserve.
  3. Success → enqueue Reservation(user, sku, id) → "pending payment" page.
  4. Order workers → DB order + payment link.
  5. Timeout job → release stock in Redis + cancel order.

Example

-- KEYS[1]=stock key, KEYS[2]=buyers set; ARGV[1]=userId
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then return -1 end
local s = tonumber(redis.call('GET', KEYS[1]))
if s <= 0 then return 0 end
redis.call('DECR', KEYS[1]); redis.call('SADD', KEYS[2], ARGV[1])
return 1

Common mistakes

  • SELECT stock then UPDATE in the DB under load (race + DB overload).
  • Synchronous order creation for every attempt.
  • No per-user limit (one bot buys everything).
  • Clock skew on clients starting the sale early.

How to answer in the interview

"Pages are static on the CDN. Stock is preloaded into Redis and each purchase runs a Lua script that checks and decrements atomically, so we never oversell and rejections cost microseconds; once sold out, the gateway rejects without even calling Redis. Winners get a reservation, and orders are created asynchronously from a queue at a safe rate. Rate limits and bot checks protect fairness, and unpaid reservations are released after a timeout."

Likely follow-up questions

  • Redis fails mid-sale? Replica failover; reconcile from the reservation queue/log.
  • Fairness? Waiting room with randomised admission.
  • Multiple SKUs? Separate keys; hash tags if one script touches several.
