When and how would you cache model predictions?

MLOps · concept · levels mid, senior

In one line

Cache predictions when identical inputs repeat and inference is expensive; build the key from normalised inputs plus the model version, set the TTL by how fast the underlying data changes, precompute in batch for known entities, invalidate on deployment, and watch hit rates, permissions and privacy.

Detailed explanation

Caching pays off when the same inputs are scored repeatedly: recommendations for popular items, classification of duplicate documents, embeddings for repeated texts, risk scores for the same merchant, or identical LLM prompts. It saves compute and latency.

Cache key. Build it from normalised input features—sorted keys, consistent rounding, trimmed and lower-cased text—hashed, plus the model name and version (and feature-pipeline version). Including the version means a new model never serves old predictions; deployment naturally bypasses old entries, and you can also purge explicitly.

TTL. Match it to how quickly inputs and the world change. A credit or fraud score that depends on real-time features can only be cached for seconds, or not at all. A product category prediction or an embedding of unchanging text can be cached for days or indefinitely.

Precomputation. For a known set of entities, batch-score them and store predictions in a key-value store (Redis, DynamoDB, Bigtable). Serving becomes a lookup, with fallback to online inference for new or missing entities. This is caching taken to its limit.

Semantic caching for LLMs reuses answers for similar (not identical) prompts using embedding similarity, but needs care because near-matches can be wrong.

Operational concerns. Monitor hit rate, latency saved and staleness. Make sure cached results respect permissions: if the output depends on who asks, the user or tenant must be in the key. Personal data in cache keys or values needs encryption, TTLs and deletion handling.

How it works

  1. Confirm repetition: measure duplicate input rate in logs.
  2. Define normalisation and the key including model version.
  3. Choose TTL per use case.
  4. On request: compute key, return cached value or score and store.
  5. Invalidate or bypass on deployment.
  6. Monitor hit rate and correctness.

Example

import hashlib, json

MODEL_VERSION = "doc-classifier:7"

def cache_key(features: dict) -> str:
    norm = {k: (round(v, 4) if isinstance(v, float) else str(v).strip().lower())
            for k, v in sorted(features.items())}
    raw = MODEL_VERSION + json.dumps(norm, sort_keys=True)
    return "pred:" + hashlib.sha256(raw.encode()).hexdigest()

def predict(features):
    k = cache_key(features)
    if (hit := redis.get(k)) is not None:
        return json.loads(hit)
    out = model.predict(features)
    redis.set(k, json.dumps(out), ex=24 * 3600)
    return out

Common mistakes

  • Leaving the model version out of the key.
  • Caching predictions that depend on fast-changing real-time features.
  • Ignoring per-user permissions in shared caches.
  • Not normalising inputs, so the hit rate stays near zero.

How to answer in the interview

"Caching makes sense when identical inputs repeat and inference is expensive, like popular items, duplicate documents or embeddings. The key is built from normalised features plus the model version, so a new model never serves stale predictions. The TTL depends on how fast the underlying data changes: a real-time fraud score barely at all, a product category for days. For known entities I precompute in batch into a key-value store with online fallback. I monitor hit rates and make sure cached results respect permissions and privacy."

Likely follow-up questions

  • What goes wrong if the key ignores the model version? Old predictions are served after a deployment, hiding the new model and breaking rollbacks and audits.
  • What is semantic caching? Reusing results for similar inputs by embedding similarity, mainly for LLMs.
  • Cache or precompute? Precompute for a known, bounded entity set; cache for open-ended inputs.
