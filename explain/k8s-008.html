Compare kube-proxy modes and eBPF-based alternatives for Service routing.

Kubernetes · concept · levels mid, senior

In one line

kube-proxy programmes each node so traffic to a Service ClusterIP reaches a backend pod: iptables mode (long-time default, linear rule chains), IPVS (kernel load balancer with hash tables), and the newer nftables mode (GA in 1.33); eBPF dataplanes like Cilium replace kube-proxy entirely for better scale and observability.

Detailed explanation

A Service's ClusterIP is virtual: no interface owns it. kube-proxy watches Services and EndpointSlices and installs rules that translate (DNAT) the ClusterIP and port into a chosen pod IP.

  • iptables mode writes a chain per Service and per endpoint, choosing a backend with random probability rules. It is simple and battle-tested, but packets of new connections walk chains sequentially and updates rewrite large rule sets. With tens of thousands of Services and endpoints, rule sync can take seconds to minutes and adds CPU.
  • IPVS mode uses the kernel's IP Virtual Server with hash-table lookups, scaling better. It still relies on some iptables for helpers, and the Kubernetes project now steers new setups towards nftables rather than IPVS.
  • nftables mode uses the modern netfilter API with maps and sets, giving faster lookups and incremental updates; it graduated to stable in 1.33 and is the intended long-term successor to iptables mode, although iptables remains the default for compatibility.
  • eBPF dataplanes (Cilium, also Calico's eBPF mode) attach programs to sockets and network interfaces. With socket-level load balancing, a connect() to a ClusterIP is rewritten to a pod IP before any packet is built, avoiding per-packet NAT and conntrack. Cilium can run kube-proxy-free, handles NodePort and LoadBalancer services, and adds deep visibility through Hubble flow logs.

The choice matters mainly at scale, with high connection churn, or when you need flow-level observability.

How it works

  1. Service and EndpointSlice change in the API.
  2. kube-proxy or the eBPF agent on each node receives the update.
  3. It updates iptables chains, IPVS tables, nftables maps or eBPF maps.
  4. A client connects to the ClusterIP.
  5. The rule or program selects a backend and rewrites the destination.
  6. Return traffic is reverse-translated (or never needed translation with socket LB).

Example

# kube-proxy configuration
apiVersion: kubeproxy.config.k8s.io/v1alpha1
kind: KubeProxyConfiguration
mode: nftables
# Cilium without kube-proxy
helm install cilium cilium/cilium -n kube-system \
  --set kubeProxyReplacement=true \
  --set k8sServiceHost=10.0.0.10 --set k8sServicePort=6443
cilium status | grep KubeProxyReplacement

Common mistakes

  • Removing kube-proxy without fully enabling the replacement.
  • Not telling Cilium the API server address when kube-proxy is gone.
  • Assuming IPVS removes all iptables use.
  • Switching modes in place without cleaning old rules.

How to answer in the interview

"kube-proxy watches Services and EndpointSlices and programmes each node so ClusterIP traffic reaches a backend pod. iptables mode is the long-time default and simple, but it uses linear chains that get slow to update with thousands of services. IPVS uses kernel hash tables and scales better, and nftables, stable since 1.33, is the modern successor with faster incremental updates. eBPF dataplanes like Cilium replace kube-proxy completely, load balancing at the socket level before netfilter, with better performance and Hubble observability. It mostly matters at scale."

Likely follow-up questions

  • What breaks if you remove kube-proxy incorrectly? ClusterIP, NodePort and even API server access from pods stop working.
  • Why might traffic not follow session affinity? Affinity is per client IP and node; NAT or many nodes change the picture.
  • What is externalTrafficPolicy: Local? Keeps client source IP and avoids extra hops, routing only to local pods.
