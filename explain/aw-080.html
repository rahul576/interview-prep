How do you design private, zero-trust style access to internal applications on AWS?

Cloud (AWS) · design · levels senior

In one line

Zero trust means no implicit trust from network location: internal apps are never public, employees reach them through AWS Verified Access or another identity-aware proxy that checks SSO identity and device posture per request, services talk privately over PrivateLink and VPC endpoints with IAM SigV4 or mTLS authentication and least privilege, and everything is logged.

Detailed explanation

Traditional designs trust anyone on the VPN or inside the VPC; once inside, an attacker can move laterally. Zero trust verifies every request based on identity, device and context, grants least privilege and assumes the network is hostile.

User-to-application access: AWS Verified Access puts internal web apps (and now TCP endpoints) behind an endpoint that authenticates users via IAM Identity Center or an OIDC provider such as Okta or Entra ID, and evaluates Cedar policies using user claims like group and department plus device trust signals from providers like CrowdStrike, Jamf or JumpCloud. Each request is evaluated, apps stay in private subnets, and access logs record everything. Alternatives include ALB with OIDC authentication plus WAF, or third-party ZTNA products. Administrative access uses Session Manager rather than SSH bastions.

Service-to-service access: traffic stays off the internet with VPC endpoints, PrivateLink endpoint services for exposing APIs to other VPCs or accounts without peering, and VPC Lattice, which connects services across VPCs and accounts with auth policies using IAM SigV4 identities. Alternatively a service mesh provides mutual TLS with workload identities (for example via ACM Private CA). Each service has its own IAM role with least privilege, security groups reference each other, and network segmentation limits blast radius.

Data and monitoring: encryption in transit everywhere, short-lived credentials, central logs from Verified Access, CloudTrail, VPC flow logs and Lattice access logs, analysed by GuardDuty and a SIEM for anomalies, plus regular access reviews.

How it works

  1. User opens internal.example.com; Verified Access redirects to SSO.
  2. Identity and device claims are evaluated against Cedar policy.
  3. Allowed requests reach the app in a private subnet.
  4. The app calls backend services via Lattice or PrivateLink with SigV4 or mTLS.
  5. Each hop is authorised and logged centrally.

Example

// Verified Access Cedar policy: finance group on a managed, healthy device
permit(principal, action, resource)
when {
  context.idc.groups has "finance-group-id" &&
  context.crowdstrike.assessment.overall > 50
};
{
  "Statement": [{
    "Effect": "Allow",
    "Principal": {"AWS": "arn:aws:iam::111122223333:role/billing-service"},
    "Action": "vpc-lattice-svcs:Invoke",
    "Resource": "*",
    "Condition": {"StringEquals": {"vpc-lattice-svcs:RequestMethod": "GET"}}
  }]
}

Common mistakes

  • Treating the VPN as proof of trust and leaving internal apps without auth.
  • Allowing broad CIDR ranges between services instead of identities.
  • Ignoring device posture, so stolen credentials from any laptop work.
  • No central logging, making investigations impossible.

How to answer in the interview

"Zero trust means no implicit trust from network location, so internal apps are never public and being on the VPN is not enough. For employees I would use AWS Verified Access or another identity-aware proxy: each request is authenticated through corporate SSO and evaluated against policies that include group membership and device posture from tools like CrowdStrike or Jamf. Service-to-service traffic stays private via PrivateLink, VPC endpoints or VPC Lattice, and each call is authenticated with IAM SigV4 or mTLS, with least privilege roles. Everything is logged centrally for audit and anomaly detection."

Likely follow-up questions

  • How does this improve on a traditional VPN? Per-app, per-request decisions with device checks, no broad network access and no lateral movement.
  • PrivateLink or VPC Lattice? PrivateLink exposes one service via an NLB; Lattice is a service network with routing and IAM auth policies.
  • How handle legacy apps without SSO? Put them behind the proxy, which handles authentication, and pass identity headers.
