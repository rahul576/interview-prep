You are asked to design an ML platform for 20 data science teams. What would you build?

MLOps · design · levels senior, lead

In one line

Build the ML platform as an internal product with golden paths: self-service environments with quotas and governed data access, shared experiment tracking and model registry, pipeline templates with CI/CD, standard serving paths for online and batch, a feature store only where reuse justifies it, and governance, monitoring and cost visibility built in, measured by adoption and time to production.

Detailed explanation

Twenty teams each building their own stack means twenty ways to deploy, monitor and audit models, and nobody can support them all. A platform gives them a paved road that is easier than going off-road, while allowing escape hatches.

Self-service environments. Managed notebooks and training compute, including GPUs, with quotas and budgets per team, access to approved data through a governed catalogue (Unity Catalog, Lake Formation, Purview), secrets handled by the platform, and project spaces created from a template in minutes.

Shared services. Central experiment tracking and model registry (MLflow or the cloud equivalent) with per-team permissions and a common naming and alias convention.

Pipeline templates. A cookiecutter-style project layout on an orchestrator (Kubeflow, Airflow or the cloud ML pipelines) with data validation, training, evaluation, registration and CI/CD wired in, so a new project starts with tests and gates instead of a notebook.

Standard serving. Two or three supported paths: online endpoints with autoscaling, canary rollouts and prediction logging; batch scoring jobs; and, increasingly, an LLM gateway for foundation models. Monitoring for drift and performance comes by default.

Feature store or shared feature pipelines are added when several teams genuinely reuse features or need online serving; otherwise it is overhead.

Governance and cost. Model inventory, cards, approvals and audit trail integrated in the registry; cost per team and model visible on dashboards.

Run it like a product: user research with teams, a roadmap, documentation, office hours, and metrics such as adoption, time from idea to production and incidents.

How it works

  1. Interview teams; find common pain points and the most frequent workflows.
  2. Build the thinnest golden path end to end for one pilot team.
  3. Add self-service onboarding, quotas and data access.
  4. Expand to standard serving and monitoring.
  5. Onboard teams in waves; collect feedback.
  6. Add feature store and advanced features when demand is proven.

Example

Golden path: "new-ml-project" template
  repo: src/, tests/, pipeline.py, model_card.md, .github/workflows/ci.yml
  infra: workspace + storage + GPU quota (Terraform module, team budget alerts)
  training: Kubeflow pipeline -> MLflow tracking -> registry (team namespace)
  deploy: KServe InferenceService via Argo CD, canary 10 %, prediction logs -> lake
  monitor: Evidently drift job + Grafana dashboard + on-call routing to team

Common mistakes

  • Building every component before the first team ships a model.
  • Mandating the platform without making it easier than alternatives.
  • A feature store on day one with no reuse.
  • No cost visibility, so GPU spend surprises finance.

How to answer in the interview

"I'd treat it as an internal product with golden paths. Teams get self-service notebooks and compute with quotas and governed data access. Shared experiment tracking and a model registry with per-team permissions. Pipeline templates with validation, training, evaluation and CI/CD built in. Standard serving paths for online endpoints and batch scoring, with prediction logging and drift monitoring by default. A feature store only where reuse justifies it. Governance and cost per team are built in, and I'd measure adoption and time to production."

Likely follow-up questions

  • What would you leave out of version one? Feature store, custom UIs and rare frameworks; focus on one end-to-end path.
  • How do you drive adoption? Make the paved road faster, pilot with a friendly team, publish wins.
  • Build or buy? Mostly managed and open components glued with templates.
