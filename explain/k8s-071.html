A gRPC service has five replicas, but almost all traffic goes to one pod. Why, and how do you fix it?

Kubernetes · scenario · levels mid, senior

In one line

gRPC uses long-lived HTTP/2 connections that multiplex many requests, and a ClusterIP Service balances at L4 per connection, so each client sticks to one pod; fix it with per-request L7 balancing (mesh or Envoy-based proxy), client-side load balancing via a headless Service, or max connection age on the server.

Detailed explanation

kube-proxy (iptables, IPVS or nftables mode) and eBPF dataplanes pick a backend when a TCP connection is established, and every packet of that connection then goes to the same pod. For HTTP/1.1 with short connections this spreads load well. gRPC over HTTP/2 opens one connection per client channel and sends thousands of concurrent requests over it. If you have three client pods, at most three server pods get traffic, and when the HPA adds replicas, existing connections never move, so the new pods sit idle.

The fix is to balance requests, not connections, which requires something that understands HTTP/2.

Service mesh (Istio sidecar or waypoint, Linkerd) or an Envoy-based gateway terminates HTTP/2 and spreads individual requests across endpoints, transparently to the application. Linkerd does this out of the box; with Istio, L7 load balancing requires a sidecar or, in ambient mode, a waypoint proxy.

Client-side load balancing: point the gRPC client at a headless Service (clusterIP: None) using the dns:/// resolver, so DNS returns all pod IPs, and enable the round_robin policy. The client keeps a connection to each pod. DNS re-resolution happens on connection failure or periodically, so new pods are picked up with some delay. xDS-based proxyless gRPC is a more advanced variant.

MaxConnectionAge on the server (gRPC keepalive setting) sends GOAWAY after, say, 5 minutes, forcing clients to reconnect and reshuffle; combined with a grace period, in-flight calls finish. This is a cheap mitigation that also works with L4 balancing.

How it works

  1. Confirm per-pod request rates are skewed while connection counts are few.
  2. Choose: mesh/L7 proxy, client-side LB or connection ageing.
  3. For client-side LB, create a headless Service and configure round_robin.
  4. Set server MaxConnectionAge and grace.
  5. Verify request distribution after scaling events.

Example

apiVersion: v1
kind: Service
metadata: { name: pricing-headless }
spec:
  clusterIP: None
  selector: { app: pricing }
  ports: [{ name: grpc, port: 50051 }]
conn, err := grpc.NewClient(
    "dns:///pricing-headless.shop.svc.cluster.local:50051",
    grpc.WithDefaultServiceConfig(`{"loadBalancingConfig":[{"round_robin":{}}]}`),
    grpc.WithTransportCredentials(creds))

// server side
grpc.NewServer(grpc.KeepaliveParams(keepalive.ServerParameters{
    MaxConnectionAge: 5 * time.Minute, MaxConnectionAgeGrace: 30 * time.Second}))

Common mistakes

  • Scaling replicas and expecting load to spread.
  • Using an L4 cloud load balancer for gRPC ingress.
  • Headless Service without changing the client LB policy (pick_first is the default).
  • Very short connection ages causing reconnect storms.

How to answer in the interview

"gRPC runs over HTTP/2, which multiplexes many requests over one long-lived connection. A ClusterIP Service is balanced by kube-proxy at layer 4, per connection, so each client sticks to one pod and new replicas get nothing. I fix it by balancing per request: a mesh like Linkerd or Istio, or an Envoy-based proxy, does it transparently. Alternatively the gRPC client does round robin across pod IPs from a headless Service. Setting a max connection age on the server forces periodic reconnects, which rebalances load after scaling."

Likely follow-up questions

  • Does HTTP/1.1 keep-alive have the same problem? Partly; connections are reused but there are usually many, so skew is milder.
  • Why does the default pick_first matter? It uses one address only, even with a headless Service.
  • How does a mesh help canaries too? It can weight requests between versions.
