How do you instrument an application with Application Insights today, and what do you get from it?

Azure · concept · levels entry, mid, senior

In one line

Instrument apps today with the Azure Monitor OpenTelemetry Distro (or auto-instrumentation on App Service, Functions and AKS), configured by a connection string, sending to a workspace-based Application Insights resource; you get requests, dependencies, exceptions, logs and metrics correlated for distributed tracing, the application map, alerts and sampling for cost control.

Detailed explanation

Application Insights is the APM feature of Azure Monitor. The old classic SDKs and instrumentation keys are legacy: Microsoft ended support for instrumentation-key-based ingestion in March 2025 in favour of connection strings, and classic (non-workspace) resources have been retired. The modern approach is OpenTelemetry: Microsoft ships the Azure Monitor OpenTelemetry Distro for .NET, Java, Node.js and Python, which bundles the OpenTelemetry SDK, common instrumentations and the Azure Monitor exporter. On App Service, Functions and AKS you can also use autoinstrumentation without code changes (for supported languages).

Out of the box you get incoming requests (server spans), dependencies (HTTP, SQL, Service Bus, storage calls), exceptions, logs from the standard logging framework and metrics. Telemetry carries W3C Trace Context (traceparent), so a single request across many services and queues shares one operation ID. Application Insights stitches that into the application map (services and their dependencies with failure rates), transaction search and end-to-end transaction details, plus Live Metrics and the Failures and Performance blades.

You then add value on top: custom spans and attributes around business operations, custom metrics, availability tests (standard tests pinging endpoints from multiple regions) and alerts on failure rate, latency or dependency failures. Because data lands in Log Analytics tables such as AppRequests, you can query it with KQL. For busy services, sampling (the distro supports fixed-rate sampling, and rate-limited sampling in newer versions) keeps volume and cost manageable while keeping traces complete.

How it works

  1. Create a workspace-based Application Insights resource.
  2. Add the distro package and call its setup method, or enable autoinstrumentation.
  3. Provide APPLICATIONINSIGHTS_CONNECTION_STRING (ideally with Entra ID auth).
  4. Telemetry is exported with trace context propagated across calls.
  5. Use the application map, failures and performance views; add alerts and availability tests.
  6. Configure sampling and review ingestion cost.

Example

// Program.cs (.NET 8+)
using Azure.Monitor.OpenTelemetry.AspNetCore;

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddOpenTelemetry().UseAzureMonitor(o =>
{
    o.SamplingRatio = 0.25f;   // keep 25% of traces
});
// connection string read from APPLICATIONINSIGHTS_CONNECTION_STRING
var app = builder.Build();

Common mistakes

  • Hard-coding instrumentation keys or using the deprecated classic SDK for new apps.
  • Different sampling per service, breaking end-to-end traces.
  • No custom dimensions, so business failures are invisible.
  • Logging everything at debug level into the workspace.

How to answer in the interview

"Today I instrument with the Azure Monitor OpenTelemetry Distro, or autoinstrumentation on App Service and AKS, configured through a connection string to a workspace-based Application Insights resource. That gives me requests, dependencies, exceptions, logs and metrics automatically, correlated with W3C trace context, so I can follow one request across services in the application map and transaction view. I add custom spans for business operations, availability tests and alerts on failure rate and latency, and I configure sampling so busy services stay affordable."

Likely follow-up questions

  • How to trace a request across services and a queue? Propagate trace context in message properties; Service Bus SDKs do this with diagnostic IDs.
  • Why OpenTelemetry? Vendor-neutral APIs; you can send data elsewhere later.
  • Workspace-based benefit? One place for KQL, RBAC and retention alongside other logs.
