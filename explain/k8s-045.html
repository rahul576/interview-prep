Which securityContext settings do you apply to a typical application container, and why?

Kubernetes · concept · levels entry, mid, senior

In one line

Run as non-root with an explicit UID, set allowPrivilegeEscalation: false, readOnlyRootFilesystem: true (with emptyDir for writable paths), drop ALL capabilities, use seccompProfile: RuntimeDefault, and enforce the restricted Pod Security Standard.

Detailed explanation

A container is just a process on a shared kernel. If an attacker exploits the application, the securityContext decides how much they can do next. Each setting removes one capability an attacker would use.

runAsNonRoot: true with runAsUser/runAsGroup (for example 10001) ensures the process is not UID 0, so a container escape bug or a mounted host path is far less dangerous, and the kubelet refuses to start an image that would run as root. allowPrivilegeEscalation: false sets the no_new_privs flag, so setuid binaries like su cannot gain privileges. readOnlyRootFilesystem: true stops an attacker from dropping tools or modifying application files; apps that need scratch space get an emptyDir mounted at /tmp or a cache directory.

Linux capabilities split root's power into pieces. Container runtimes grant a default set (such as CHOWN, SETUID, NET_RAW); drop: [ALL] removes them, and you add back only what is truly needed, like NET_BIND_SERVICE for ports under 1024, which is rarely needed because a container can listen on 8080 behind a Service on 80. seccompProfile: RuntimeDefault blocks dangerous syscalls. Never use privileged: true, hostNetwork, hostPID or hostPath for normal apps.

These settings match the restricted level of Pod Security Standards. Labelling namespaces with pod-security.kubernetes.io/enforce: restricted makes Pod Security Admission reject regressions.

How it works

  1. Build images with a non-root USER and files owned correctly.
  2. Set pod-level runAsNonRoot, runAsUser, fsGroup and seccomp.
  3. Set container-level privilege escalation, read-only root and capability drops.
  4. Mount emptyDir volumes for paths the app writes.
  5. Enforce restricted via namespace labels; use warn/audit first.

Example

spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    runAsGroup: 10001
    fsGroup: 10001
    seccompProfile: { type: RuntimeDefault }
  containers:
    - name: api
      image: registry.example.com/api@sha256:3f1c...
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities: { drop: ["ALL"] }
      volumeMounts:
        - { name: tmp, mountPath: /tmp }
  volumes:
    - name: tmp
      emptyDir: { sizeLimit: 256Mi }

Common mistakes

  • Setting runAsNonRoot on an image whose user is root, causing CreateContainerConfigError.
  • Disabling read-only root instead of finding the write path.
  • Adding SYS_ADMIN "to make it work".
  • Not enforcing Pod Security, so settings drift back.

How to answer in the interview

"For a normal service I run as non-root with an explicit UID and group, set allowPrivilegeEscalation false so setuid binaries can't elevate, and make the root filesystem read-only with an emptyDir for /tmp or caches. I drop all capabilities and add back only what's needed, which is almost never anything since the app can listen on a high port. I use the RuntimeDefault seccomp profile and never privileged or host namespaces. That matches the restricted Pod Security Standard, so I enforce it per namespace to catch regressions."

Likely follow-up questions

  • App fails with readOnlyRootFilesystem? Find the write path from logs or strace, mount an emptyDir there, or configure the app to write elsewhere.
  • Pod-level vs container-level? Pod-level sets defaults; container-level overrides and holds capabilities and read-only root.
  • What about user namespaces? hostUsers: false maps container root to an unprivileged host UID for extra isolation where supported.
