One MCP server has become a bottleneck that slows every agent using it. What do you do?

MCP Servers · scenario · levels mid, senior

In one line

Measure where time goes (server CPU, downstream calls, queuing, retry loops), then apply the matching fix: scale out horizontally if stateless, cache expensive results and tool lists, optimise or batch downstream calls, rate-limit noisy agents, isolate heavy tools or split the server, and return less data.

Detailed explanation

A shared MCP server becomes a bottleneck when many agents depend on it and its latency sets the pace for all of them. Guessing at the fix wastes time; traces and metrics usually point to one dominant cause.

Diagnose. Look at per-tool latency broken into server processing and downstream time; in-flight requests and queue depth; connection pool and thread pool utilisation; CPU and memory; and callers: is the load evenly spread, or are a few agents in retry loops responsible for most of it?

Matching fixes:

  • CPU-bound or simply overloaded: if the server is stateless, scale out horizontally with autoscaling on concurrency and latency. If it holds in-memory state, making it stateless (external Redis or database) is the first step.
  • Slow downstream: add caching for expensive, slow-changing results and for tool lists; batch calls (one query for many IDs instead of N); add connection pool capacity; push work to the downstream (filter server-side, not in the MCP server).
  • Queuing on limited concurrency: raise limits where downstream capacity allows; use async I/O.
  • Noisy agents: per-client rate limits and quotas, plus clear 429 errors with retry-after so agents back off instead of hammering.
  • Mixed workloads: isolate expensive tools (report generation, large exports) into a separate deployment so they do not starve cheap, frequent ones, or split the server by domain.

Return less data. Large results slow serialisation, transfer and the next model call. Pagination, field selection and summaries help both the server and the agents.

How it works

  1. Dashboards: p95 per tool, in-flight requests, pool saturation, top callers.
  2. Identify the dominant contributor.
  3. Apply targeted fix; load test with a realistic agent traffic replay.
  4. Add autoscaling and per-client limits as standing protection.
  5. Re-measure end-to-end agent task time, not just server latency.

Example

Before: p95 get_inventory 4.8 s
  - 70% waiting on inventory DB (N+1 queries per SKU)
  - 3 agents in retry loops = 45% of traffic
Fixes:
  - batch SKU lookup: 1 query per call      -> p95 900 ms
  - 60 s cache for SKU metadata              -> p95 300 ms
  - per-client limit 30/min + Retry-After    -> traffic -40%
  - export_report moved to separate deployment

Common mistakes

  • Adding replicas when the downstream database is the bottleneck.
  • Scaling a stateful server horizontally and introducing session bugs.
  • Ignoring retry loops that multiply load.
  • One deployment for cheap lookups and heavy exports.

How to answer in the interview

"First I measure where the time goes with traces and metrics: is the server CPU-bound, waiting on slow downstream APIs, queueing because of limited concurrency or connection pools, or being hammered by a few agents in retry loops. Then the matching fix. If it's stateless, I scale out with autoscaling on concurrency and latency; if not, making it stateless comes first. I cache expensive, slow-changing results and tool lists. Downstream calls get batched, optimised or more connections. Noisy agents get per-client rate limits, and expensive tools can move to a separate deployment or the server gets split by domain. Returning less data also helps everyone."

Likely follow-up questions

  • How do retry loops make it worse? Each slow response triggers more calls, increasing load exactly when capacity is short.
  • Separate deployment or split server? Separate deployment for heavy tools; split when domains are unrelated.
  • Which metric to scale on? In-flight requests or latency, not CPU.
