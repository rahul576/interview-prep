How do you design configuration for many environments without copy-paste?

Configuration Management · design · levels senior

In one line

Run the same code everywhere and layer configuration: defaults, then environment, then region/cluster, then (rarely) host, so each layer holds only differences; keep secrets separate and referenced, and validate and diff environments regularly.

Detailed explanation

Copy-pasted environment folders look simple at first, then diverge: a fix lands in prod but not staging, a new setting is forgotten in one region, and reviewers cannot tell what is intentionally different. The goal is one codebase, small override files.

Ansible. Precedence gives a natural hierarchy: role defaults (defaults/main.yml) hold sensible values; inventory group_vars/all sets organisation-wide values; group_vars/prod and group_vars/staging hold environment differences; groups like eu_west or cluster_a hold regional values; host_vars only for genuine one-offs. Inventories per environment (inventories/prod, inventories/staging) keep hosts separate while playbooks and roles are shared.

Terraform. One root module or a set of modules is reused; each environment has a small prod.tfvars or a thin live directory calling the same pinned module with different inputs. Locals can merge maps (merge(local.defaults, var.overrides)) for structured settings.

Kubernetes. The same idea appears as Kustomize base plus overlays, or one Helm chart with per-environment values files.

Small files are reviewable. If group_vars/prod is 20 lines, a reviewer immediately sees how production differs, and a new environment is a new small file rather than a copy of everything.

Secrets stay out of these files: they are references to a vault path or secret name, resolved at runtime.

Guarding divergence. Schema validation (JSON Schema, Terraform variable validation, ansible.builtin.assert on required variables) catches typos and missing values. A scheduled job renders the effective configuration per environment (ansible-inventory --host, terraform console, helm template) and diffs them, highlighting unexpected differences like a feature flag enabled in staging but forgotten in production.

How it works

  1. Put defaults in role defaults or module variables.
  2. Add only differing values per environment.
  3. Add region or cluster layers where needed.
  4. Reference secrets by path; never inline.
  5. Validate on every PR; diff rendered configs on a schedule.

Example

inventories/
  prod/
    hosts.yml
    group_vars/
      all.yml          # env: prod, log_level: warn
      eu_west.yml      # ntp_servers, s3_region
  staging/
    hosts.yml
    group_vars/all.yml # env: staging, log_level: debug, replicas: 1
roles/app/defaults/main.yml   # replicas: 3, feature_new_checkout: false
diff <(ansible-inventory -i inventories/staging --host app1 | jq -S .) \
     <(ansible-inventory -i inventories/prod --host app1 | jq -S .)

Common mistakes

  • Copying the full configuration per environment.
  • Putting values in host_vars that belong to groups.
  • Mixing secrets into ordinary variable files.
  • Relying on hidden precedence rules nobody understands; keep layers few and documented.

How to answer in the interview

"The same code runs everywhere and configuration is layered so each layer only holds what differs. Defaults live in role defaults or module variables, then environment overrides like group_vars/prod or prod.tfvars, then region or cluster values, and host_vars only for real exceptions. Each environment file stays short, so reviewers see immediately how production differs from staging, and a new environment is a small override file. Secrets are separate, referenced from a vault. Validation on every PR and periodic diffs of the rendered configuration catch accidental divergence, like a flag set in staging but forgotten in production."

Likely follow-up questions

  • How would you spot unintended differences between staging and prod? Render effective configuration per environment and diff it regularly.
  • Where should a value used by all environments live? In defaults or group_vars/all, never duplicated per environment.
  • How many layers are too many? More than four or five; precedence becomes hard to reason about.
