How can coding standards be provided to AI tools to improve automated code reviews?

AI/ML & GenAI · scenario · levels mid

In one line

Put coding standards in versioned repository instruction files (such as CLAUDE.md, .github/copilot-instructions.md or .cursor/rules), make them concrete with good/bad examples and checklists, link ADRs, linter configs and security rules, inject them into the system prompt or retrieve them (RAG) for custom bots, and refine them from feedback.

Detailed explanation

An AI reviewer only knows generic best practice unless you tell it your team's rules. Without them it makes comments that contradict conventions or misses team-specific issues.

Where: AI tools read instruction files from the repository: CLAUDE.md for Claude Code, .github/copilot-instructions.md (plus path-specific instruction files) for GitHub Copilot, and project rules in .cursor/rules for Cursor; AGENTS.md is a widely used cross-tool convention. Keeping them in the repo means they are versioned, reviewed like code and the same for every developer and the CI bot.

What: package structure, dependency injection style, exception handling, logging rules (no personal data), transaction rules, API conventions, test naming, and forbidden patterns. Concrete beats abstract: a short good and bad snippet teaches the rule better than a paragraph. A review checklist helps the model work systematically.

Links: reference architecture decision records, Checkstyle, PMD and Sonar configs and security guidelines. Linters should still enforce what is mechanical; AI handles judgement.

Custom bots: if you built a reviewer on an LLM API, put the standards in the system prompt and use retrieval to add the relevant docs for the changed files.

Refine: when the AI makes the same wrong comment twice, update the rules, like improving an onboarding guide.

How it works

  1. Write the standards file in the repository root.
  2. Add examples, a checklist and links to ADRs and lint configs.
  3. Configure tools and bots to load it.
  4. For custom bots, retrieve relevant docs per changed file.
  5. Review AI comments and collect false positives.
  6. Update the rules file through normal PRs.

Example

## Review rules (.github/copilot-instructions.md)
- Constructor injection only.
  Bad:  @Autowired private OrderRepository repo;
  Good: private final OrderRepository repo; // via constructor
- Never log request bodies or emails (GDPR). See docs/adr/0012-logging.md
- REST errors use ProblemDetail (RFC 9457).
- Checklist: transactions, null handling, authorisation, tests for new branches.

Common mistakes

  • Standards kept only in a wiki the tools never see.
  • Long, vague rules without examples.
  • Duplicating linter rules instead of linking to them.
  • Never updating rules after repeated bad comments.

How to answer in the interview

"I put the standards where the tools can read them, versioned with the code: a CLAUDE.md, a Copilot instructions file or Cursor rules. They describe our conventions like constructor injection, error handling and logging rules, with short good and bad examples and a review checklist, and they link to our ADRs, Checkstyle and Sonar configs and security guidelines. For a custom review bot I include the rules in the system prompt and retrieve relevant docs for the changed files. When the AI makes the same wrong comment twice, we update the rules through a normal PR."

Likely follow-up questions

  • Why in the repo, not developer settings? Versioned, reviewed, consistent for everyone and for CI.
  • How long should the file be? Concise and focused; very long files dilute attention and cost tokens.
  • Different rules per module? Use path-specific or nested instruction files.
