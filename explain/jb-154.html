What causes connection pool exhaustion? How would you troubleshoot it?

Databases & SQL · scenario · levels senior, lead

In one line

Pool exhaustion means every connection is busy or leaked and threads time out waiting; causes are leaks, long transactions, slow queries, remote calls inside transactions, an undersized pool or a traffic spike, diagnosed with pool metrics, leak detection, thread dumps and database session views.

Detailed explanation

The classic symptom with HikariCP is SQLTransientConnectionException: HikariPool-1 - Connection is not available, request timed out after 30000ms, often with the database looking calm. Requests pile up, latency rises, and health checks may fail, triggering restarts that hide the cause.

Common causes:

  • Connection leaks: code borrows a connection and never closes it, typically manual JDBC without try-with-resources, or a stream/ResultSet left open.
  • Long-held connections: a @Transactional method that makes an HTTP call, sends to Kafka, or waits on a lock while holding a connection.
  • Slow queries or lock waits that keep connections busy much longer than expected.
  • Open Session in View (spring.jpa.open-in-view=true, Spring Boot's default, with a startup warning) keeping a connection for the whole web request including view rendering.
  • Undersized pool for the concurrency, or more app threads than connections with every request needing the DB.
  • Traffic spikes or retries amplifying load.
  • Nested transactions using REQUIRES_NEW, which need a second connection per thread and can deadlock a small pool.

How it works

  1. Check metrics: hikaricp.connections.active, idle, pending, usage and acquire time (via Micrometer/Actuator).
  2. If active stays at max with pending threads, find who holds connections.
  3. Enable leakDetectionThreshold to log the stack trace of connections held longer than the threshold.
  4. Take thread dumps; look for threads inside JDBC calls, HTTP clients or locks while holding a connection.
  5. Inspect pg_stat_activity (state, idle in transaction, wait events) or SHOW PROCESSLIST.
  6. Fix the code path, add timeouts, then size the pool based on measurements.

Example

spring:
  jpa:
    open-in-view: false
  datasource:
    hikari:
      maximum-pool-size: 20
      connection-timeout: 3000        # fail fast instead of 30 s
      leak-detection-threshold: 20000 # log stack trace if held > 20 s
SELECT pid, state, now() - xact_start AS tx_age, wait_event, left(query, 80)
FROM pg_stat_activity
WHERE datname = 'shop' ORDER BY tx_age DESC NULLS LAST;
-- many 'idle in transaction' rows = app holding connections without working

Common mistakes

  • Simply raising maximum-pool-size to 200, which overloads the database.
  • Leaving Open Session in View on in a busy API.
  • Calling external services inside @Transactional.
  • No statement or socket timeouts, so stuck queries hold connections forever.
  • Ignoring that N app instances times pool size must fit the database's max connections.

How to answer in the interview

"The symptom is threads timing out waiting for a connection, like Hikari's 'connection is not available, request timed out', while the database may look idle. Causes are leaks where connections aren't closed, long transactions, slow queries or lock waits, remote HTTP or Kafka calls inside a transaction, open session in view, a pool too small for the concurrency, or a traffic spike. I'd check Hikari metrics for active and pending connections, turn on leakDetectionThreshold to get stack traces, take thread dumps to see what connection-holding threads are doing, and look at pg_stat_activity for long or idle-in-transaction sessions. Then I fix the code path and size the pool from measurements, not guesses."

Likely follow-up questions

  • Why isn't a bigger pool always the fix? The database has limited cores and connections; more concurrent queries add contention and slow everything.
  • How do you size a pool? Start small (roughly cores times two on the DB side, divided across instances) and tune with load tests.
  • What does 'idle in transaction' mean? The app opened a transaction and is holding the connection without running a query.
