What is AKS Automatic, and how does it differ from AKS Standard?

Azure Kubernetes (AKS) · concept · levels mid, senior

In one line

AKS Automatic is an opinionated AKS mode where Azure chooses and operates production-ready defaults: node auto provisioning instead of node pools, built-in security, automatic upgrades and monitoring; AKS Standard gives you full control of every setting.

Detailed explanation

Running Kubernetes well requires dozens of decisions: node pool sizes, networking plugin, ingress, identity, policy, upgrade cadence and monitoring. AKS Automatic makes those decisions for you, similar in spirit to GKE Autopilot, so teams can focus on deploying applications.

Nodes: you don't create or size node pools. Node auto provisioning, the managed form of Karpenter, looks at pending pods and creates right-sized VMs, then consolidates when load drops.

Security: Entra ID authentication with Azure RBAC, local accounts disabled, workload identity for pods, image cleaner to remove vulnerable unused images, deployment safeguards enforcing best practices through Azure Policy, and protected system namespaces so users cannot break critical components.

Networking: Azure CNI Overlay powered by Cilium, with ingress handled by the managed application routing add-on; newer versions move toward a Gateway API based implementation as Ingress NGINX is retired.

Operations: automatic cluster and node image upgrades within planned maintenance windows, and Managed Prometheus, Container Insights and Managed Grafana integration enabled. Pods without resource requests get sensible defaults.

AKS Standard remains the right choice when you need custom node pools (specific GPU SKUs, Windows nodes, custom kernels), a specific CNI or ingress, privileged workloads that safeguards would block, or full control over upgrade timing. You can still adopt many Automatic features (NAP, safeguards, managed Prometheus) on Standard individually.

How it works

  1. Create the cluster with --sku automatic.
  2. Azure configures networking, identity, policy and monitoring.
  3. Deploy workloads; pending pods trigger node provisioning.
  4. Safeguards validate manifests (probes, requests, no privileged containers).
  5. Upgrades run automatically in maintenance windows.

Example

az aks create --resource-group rg-apps --name aks-auto-prod --sku automatic \
  --location westeurope
az aks get-credentials -g rg-apps -n aks-auto-prod
kubectl apply -f deployment.yaml   # safeguards may reject or warn on bad practices

Common mistakes

  • Assuming Automatic means "no Kubernetes knowledge needed"; you still write manifests, probes and requests.
  • Deploying privileged agents that safeguards will block, without checking first.
  • Choosing Standard by habit and then rebuilding the same defaults by hand.
  • Ignoring maintenance windows and being surprised by upgrades.

How to answer in the interview

"AKS Automatic is a managed mode where Azure picks and operates production defaults, a bit like GKE Autopilot. There are no node pools to manage: node auto provisioning, based on Karpenter, creates right-sized nodes. Security is built in with Entra ID, Azure RBAC, workload identity, image cleaner and deployment safeguards. Networking is Azure CNI Overlay with Cilium, ingress is managed, monitoring is on and upgrades are automatic. Standard gives full control, which I'd choose for special node types, custom networking or privileged workloads."

Likely follow-up questions

  • Why choose Standard? Windows or special GPU pools, custom CNI, privileged DaemonSets or strict upgrade control.
  • Can you change a Standard cluster into Automatic? Treat it as a new cluster and migrate workloads.
  • Is there still a control plane SLA? Yes, Automatic includes the uptime SLA of the Standard tier.
