How does HashSet handle duplicate elements?

Collections · concept · levels entry

In one line

HashSet never stores two equal elements: add finds the bucket via hashCode, compares with equals, and if a match exists it returns false and changes nothing, so custom classes must override both methods consistently.

Detailed explanation

Calling set.add(e) delegates to the internal HashMap's put(e, PRESENT). HashMap uses e.hashCode() to locate a bucket, then compares e with each entry in that bucket: first by the cached hash value (cheap), then by reference, then by equals. If an equal element is found, the existing element is kept (the original object, not the new one), the map's value is overwritten with the same dummy, and add returns false. If not, a new entry is created and add returns true. The return value is handy: if (!seen.add(id)) skipDuplicate(); checks and inserts in one step.

For JDK types like String, Integer or records this just works, because they implement value-based equals and hashCode. For your own classes, the default Object implementations compare identity: two new Customer("42") objects are different, so both are stored and the set appears to "allow duplicates".

If you override equals but not hashCode, two equal objects usually get different identity hash codes, land in different buckets and are never compared, so duplicates remain. If you override hashCode but not equals, they land in the same bucket but equals returns false, so both are kept again. Both methods must use the same fields. Using records or IDE/Lombok-generated methods avoids mistakes.

Finally, if a field used by hashCode changes after insertion, the element sits in the wrong bucket, and adding an "equal" object can create a real duplicate.

How it works

  1. Compute hashCode, select bucket.
  2. Compare stored hash, then ==, then equals.
  3. Match: keep existing element, return false.
  4. No match: insert new node, return true.

Example

class Customer {                          // no equals/hashCode
    final String id;
    Customer(String id) { this.id = id; }
}
Set<Customer> s = new HashSet<>();
s.add(new Customer("42"));
s.add(new Customer("42"));
s.size();                                 // 2 - looks like a duplicate

record CustomerR(String id) {}           // value-based equals/hashCode
Set<CustomerR> r = new HashSet<>();
r.add(new CustomerR("42"));
r.add(new CustomerR("42"));               // false
r.size();                                 // 1

Common mistakes

  • Overriding only one of equals/hashCode.
  • Using mutable fields in hashCode and changing them later.
  • Expecting the new object to replace the old one on a duplicate add.
  • Using equals(Customer other) (overload) instead of equals(Object).

How to answer in the interview

"HashSet never keeps two equal elements. When I call add, it finds the bucket with hashCode and compares with equals against what's in that bucket. If an equal element exists nothing changes and add returns false; otherwise it stores the element and returns true. So for my own classes duplicates are only detected if equals and hashCode are overridden consistently on the same fields; with the default Object versions, two objects with the same data are different and both are kept. I usually use records, which generate both correctly."

Likely follow-up questions

  • equals overridden but not hashCode? Equal objects land in different buckets, so duplicates are stored and lookups fail.
  • Does add replace the existing element? No, the original stays.
  • How do you de-duplicate a list while keeping order? new LinkedHashSet<>(list).
