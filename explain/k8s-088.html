kubectl drain hangs during a node upgrade. What is blocking it and how do you proceed?

Kubernetes · scenario · levels mid, senior

In one line

kubectl drain uses the Eviction API, which honours PodDisruptionBudgets, so a drain that hangs is almost always a PDB with zero allowed disruptions; fix the budget or the replica count rather than forcing deletion.

Detailed explanation

When you drain a node, kubectl first cordons it and then asks the API server to evict each pod. An eviction is a polite request: the API server checks every PDB that selects the pod, and if evicting it would drop the workload below minAvailable (or above maxUnavailable), it answers HTTP 429 and kubectl keeps retrying, printing "Cannot evict pod as it would violate the pod's disruption budget". From the outside this looks like a hang.

The typical culprits are a single-replica Deployment with minAvailable: 1, which can never be evicted, a PDB with maxUnavailable: 0, or a workload whose replacement pods cannot schedule (no capacity, affinity rules, zone-bound volumes), so the budget never recovers and the next eviction never becomes allowed.

Drain also stops on pods it refuses to touch by default: DaemonSet pods (need --ignore-daemonsets), pods with emptyDir data (--delete-emptydir-data) and bare pods not owned by a controller (--force, because they will not come back). These fail fast with a clear message rather than hanging.

How it works

  1. Read the drain output to see which pod it is waiting on.
  2. Run kubectl get pdb -A and look for ALLOWED DISRUPTIONS = 0.
  3. Check whether the workload's other replicas are Ready and whether new pods are Pending.
  4. Fix the cause: scale to two or more replicas, correct the PDB with the owning team, or add capacity.
  5. Re-run the drain with a --timeout so automation fails visibly instead of hanging forever.
  6. Only as a last resort use --disable-eviction, which deletes pods directly and bypasses PDBs.

Example

kubectl drain node-7 --ignore-daemonsets --delete-emptydir-data --timeout=10m
kubectl get pdb -A
# NAMESPACE  NAME        MIN AVAILABLE  ALLOWED DISRUPTIONS
# payments   ledger-pdb  1              0
kubectl -n payments get deploy ledger     # READY 1/1  -> single replica
kubectl -n payments scale deploy ledger --replicas=2

Common mistakes

  • Jumping straight to --disable-eviction or --force and causing the outage the PDB was protecting against.
  • Writing minAvailable: 100% or maxUnavailable: 0, which blocks every voluntary disruption.
  • Scaling up during the drain without checking that the new pods can actually schedule.
  • Running node upgrades with no drain timeout, so the pipeline stalls silently.

How to answer in the interview

"Drain evicts pods through the Eviction API, and that respects PodDisruptionBudgets, so when it hangs I first run kubectl get pdb across namespaces and look for zero allowed disruptions. The classic case is a single-replica Deployment with minAvailable one, or replacements that cannot schedule so the budget never recovers. I also check for DaemonSet, emptyDir and unmanaged pods, which need explicit flags. The proper fix is to scale the workload to two replicas or fix the PDB with its owners and make sure there is capacity. Disabling eviction deletes pods and ignores the budget, so I treat it as a last resort."

Likely follow-up questions

  • How do you prevent teams from creating PDBs that block every upgrade? Enforce rules with Kyverno or Gatekeeper, for example rejecting PDBs that allow zero disruptions for workloads with one replica.
  • What does Karpenter or a managed node upgrade do with a blocking PDB? It waits and retries, and some managed upgrades force-delete after a timeout, so the PDB only delays.
  • PDB minAvailable or maxUnavailable? maxUnavailable scales better with autoscaled replica counts.
