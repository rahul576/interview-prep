How does DNS-based service discovery work inside a Kubernetes cluster?

Kubernetes · concept · levels entry, mid

In one line

CoreDNS serves cluster DNS; each Service gets <service>.<namespace>.svc.cluster.local, pointing to its ClusterIP (or pod IPs if headless); search domains in /etc/resolv.conf let you use short names, but ndots:5 makes external names try every search domain first, so busy clusters use FQDNs, tuned dnsConfig and NodeLocal DNSCache.

Detailed explanation

Every cluster runs a DNS add-on, almost always CoreDNS, behind a Service usually named kube-dns in kube-system. The kubelet writes that Service's IP into each pod's /etc/resolv.conf, along with search domains and options. CoreDNS's kubernetes plugin watches Services and EndpointSlices and answers:

  • orders.shop.svc.cluster.local → ClusterIP of Service orders in namespace shop.
  • Headless Services → A records for each ready pod, plus per-pod names for StatefulSets.
  • SRV records for named ports.

A typical resolv.conf in namespace shop:

nameserver 10.96.0.10
search shop.svc.cluster.local svc.cluster.local cluster.local
options ndots:5

The search list is why orders works in the same namespace and orders.shop from another namespace.

The cost is ndots:5: any name with fewer than five dots is treated as relative and tried with each search domain before being tried as-is. So api.stripe.com produces lookups for api.stripe.com.shop.svc.cluster.local, ...svc.cluster.local, ...cluster.local (and any cloud search domains), each failing with NXDOMAIN, often for both A and AAAA, before the real query. That multiplies CoreDNS load and adds latency. Conntrack races on UDP can also drop queries, producing the classic 5-second timeouts.

Mitigations: use trailing-dot FQDNs for external names (api.stripe.com.), lower ndots to 2 via dnsConfig for pods calling many external hosts, scale CoreDNS (or use its autoscaler), enable caching, and deploy NodeLocal DNSCache, a DaemonSet caching resolver on each node that avoids conntrack and cuts latency.

How it works

  1. Pod calls orders.
  2. Resolver appends the first search domain: orders.shop.svc.cluster.local.
  3. Query goes to the node-local cache or CoreDNS.
  4. CoreDNS answers from its Service/EndpointSlice cache.
  5. External names are forwarded to upstream resolvers.

Example

spec:
  dnsConfig:
    options:
    - { name: ndots, value: "2" }
  containers:
  - name: payments
    image: registry.example.com/payments:4.0
    env:
    - { name: STRIPE_HOST, value: "api.stripe.com." }   # trailing dot = absolute name

Common mistakes

  • Hard-coding pod IPs instead of Service names.
  • Ignoring ndots overhead in services making many external calls.
  • Running two CoreDNS replicas for a large cluster.
  • Apps that cache DNS forever (old JVM defaults), missing changes.

How to answer in the interview

"Cluster DNS is served by CoreDNS, and the kubelet points every pod's resolv.conf at it. A Service resolves as service.namespace.svc.cluster.local, to its ClusterIP or to pod IPs if it's headless. Search domains let me use just orders in the same namespace or orders.shop from another. The catch is ndots 5: external names are first tried with every search domain, creating several failed lookups. In busy clusters I use FQDNs with a trailing dot, lower ndots per pod, scale CoreDNS and deploy NodeLocal DNSCache to cut latency and load."

Likely follow-up questions

  • How do you find intermittent 5-second DNS delays? CoreDNS metrics and logs, tcpdump on port 53, conntrack insert failures; NodeLocal DNSCache usually fixes it.
  • What is dnsPolicy? ClusterFirst (default), Default (node's resolver), None (custom dnsConfig).
  • How do you resolve a Service in another cluster? Multi-cluster services or external DNS, not plain cluster DNS.
