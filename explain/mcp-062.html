How do you apply least privilege to an MCP deployment?

MCP Servers · concept · levels mid, senior

In one line

Apply least privilege at every layer: expose only the tools each use case needs, separate read-only and write tool sets, use per-user, narrowly scoped downstream credentials, limit network egress, use short-lived tokens and step-up for sensitive actions, require approvals for side effects, and review permissions regularly.

Detailed explanation

Agents are unpredictable by design: they decide which tools to call, and they can be manipulated through prompt injection. Least privilege limits the blast radius when that goes wrong. It needs to be applied in layers, because each layer catches what the others miss.

Tool layer. Each agent or use case gets only the servers and tools it needs. A support assistant does not need deployment tools; a code-review bot does not need to merge. Many servers offer read-only modes or toolset filtering; where they do not, a gateway or host policy can hide tools. Splitting read-only and write-capable servers makes it easy to enable writes only where justified.

Credential layer. Servers act on behalf of the user with per-user delegated tokens and narrow scopes, rather than a powerful shared account. Sensitive operations use step-up authorization and tokens are short-lived, so stolen tokens expire quickly.

Network layer. Servers run with restricted egress: a GitHub server can reach the GitHub API and nothing else. That stops a compromised server from exfiltrating to arbitrary hosts. Local servers can be sandboxed in containers with only the needed directories mounted.

Host layer. Side-effecting tools require approval, with risk-based rules to avoid fatigue.

Process. Permissions drift as people add servers "temporarily". Regular reviews using usage logs find servers and tools that are enabled but never used, and scopes that are broader than needed.

How it works

  1. Define agent profiles by use case with an explicit list of tools.
  2. Configure servers in read-only mode by default; enable specific write tools per profile.
  3. Issue per-user delegated tokens with minimal scopes; step up for sensitive ones.
  4. Apply egress allowlists and filesystem mounts per server.
  5. Require host approval for side effects.
  6. Quarterly: compare enabled tools and scopes with actual usage; remove the unused.

Example

profiles:
  support-assistant:
    servers:
      crm:      { tools: [search_customers, get_order], mode: read }
      tickets:  { tools: [search_tickets, add_comment] }
    approvals: { add_comment: required }
  release-bot:
    servers:
      github:   { toolsets: [repos, pull_requests], read_only: false }
    egress: [api.github.com]

Common mistakes

  • Enabling all toolsets of a server because it is quicker.
  • Using the same broad token for every agent.
  • Forgetting network egress; filesystem limits alone do not stop exfiltration.
  • Never removing access once granted.

How to answer in the interview

"Least privilege applies at several layers. At the tool layer, each agent or use case only gets the servers and tools it needs, and I often separate read-only from write-capable tool sets and only enable writes where justified. At the credential layer, servers act on behalf of the user with per-user, narrowly scoped tokens rather than a shared powerful account, with step-up for sensitive operations and short-lived tokens. At the network layer, servers have restricted egress so a compromised one can only reach the systems it serves. At the host layer, approvals for side effects. And because permissions drift, I regularly review which servers and scopes are enabled against actual usage and remove what's unused."

Likely follow-up questions

  • Find enabled but unused tools? Compare the enabled tool list with gateway or server call logs over 30-90 days.
  • Read-only server enough? Often yes for investigation and Q&A use cases.
  • Who owns the review? The platform or security team, with server owners attesting.
