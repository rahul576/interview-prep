What is the difference between docker save/load and docker export/import?

Docker · concept · levels entry

In one line

docker save/load move images with all layers, tags and metadata; docker export/import move a container's flattened filesystem, losing history and configuration such as CMD, ENV and ENTRYPOINT.

Detailed explanation

The two pairs look similar because both produce tar archives, but they operate on different objects. An image is a stack of read-only layers plus a configuration (entrypoint, environment, exposed ports, user, labels). A container is a running or stopped instance with its own writable layer.

docker save writes one or more images, including every layer, their tags and the image config, into a tar file. docker load restores them exactly, with the same IDs, so they behave identically on the other machine. This is the standard way to move images to an air-gapped environment, or to cache images as artifacts.

docker export writes the merged filesystem of a container as a single flat tar, with no layer history and no image configuration. docker import turns such a tar (or any root filesystem tarball) into a new single-layer image. You lose the entrypoint, default command, environment variables and ports unless you supply them again with --change. It is occasionally useful to flatten an image or to create a base image from a root filesystem, but it is not a migration tool for normal images.

In everyday work you use a registry with docker push and pull, which transfers only missing layers and keeps tags and digests. For offline sites you can also run a private registry inside the network and mirror images into it with tools like skopeo or crane.

How it works

  1. save reads image layers and config from local storage.
  2. It writes them with a manifest into a tar archive.
  3. load unpacks the archive and registers the layers and tags.
  4. export reads a container's merged root filesystem.
  5. import creates a new image with one layer and empty config.

Example

# Move images to an offline host
docker save -o release-1.4.tar registry.local/orders:1.4.0 registry.local/web:1.4.0
gzip release-1.4.tar
# copy via approved media, then:
docker load -i release-1.4.tar.gz

# Flatten a container (metadata lost, re-added with --change)
docker export web-tmp | docker import --change 'CMD ["nginx","-g","daemon off;"]' - web:flat

Common mistakes

  • Using export/import to move an image and then wondering why it has no entrypoint.
  • Saving each image separately, duplicating shared layers in the tars.
  • Shipping tar files when a registry mirror would be simpler and verifiable.
  • Not verifying digests or signatures after transfer.

How to answer in the interview

"docker save writes images with all their layers, tags and metadata like CMD and ENV into a tar, and docker load restores them exactly. That's how I move images to an air-gapped machine without a registry. docker export takes the flattened filesystem of a container, not an image, and docker import makes that tar a new single-layer image, so history and configuration like the entrypoint and environment are lost. Normally I prefer a registry, because only missing layers are transferred and digests stay intact."

Likely follow-up questions

  • How would you deliver images to a customer data centre with no internet? docker save or skopeo copy to an archive, transfer, load into their private registry, verify digests or signatures.
  • Why save several images in one tar? Shared layers are stored only once.
  • Can import be useful? Yes, to create a base image from a root filesystem tarball.
