How do you do back-of-the-envelope capacity estimation in a design interview?

SD Fundamentals · concept · levels entry, mid

In one line

Back-of-the-envelope estimation converts users and behaviour into requests per second, storage and bandwidth, using rounded numbers, so the design is driven by scale rather than guesswork.

Detailed explanation

Estimates answer practical questions: can one database handle the writes? Does the hot data fit in memory? Do we need a CDN? You don't need precision; you need the order of magnitude. Interviewers watch whether you state assumptions clearly and then use the results.

Useful shortcuts: a day has 86,400 seconds, round to ~100,000 (10^5). 1 million requests per day ≈ 12 per second. Peak traffic is usually 2–5x the average. Remember powers of ten: KB = 10^3, MB = 10^6, GB = 10^9, TB = 10^12.

How it works

  1. Users: daily active users (DAU) and actions per user per day.
  2. QPS: actions per day ÷ 10^5 = average QPS; multiply for peak.
  3. Read/write split: often 10:1 to 100:1 for consumer apps.
  4. Storage: records per day × size × retention (× replication factor).
  5. Bandwidth: QPS × response size.
  6. Memory for cache: 20% of daily read data often serves 80% of reads.

Example

Photo app: 10M DAU, 2 uploads/user/day, 50 views/user/day
Writes: 20M/day ÷ 1e5 ≈ 200 QPS (peak ~1,000)
Reads:  500M/day ÷ 1e5 ≈ 5,000 QPS (peak ~20,000)
Metadata: 20M × 1 KB = 20 GB/day ≈ 7 TB/year
Photos: 20M × 500 KB = 10 TB/day → object storage + CDN

Conclusion: metadata fits a sharded SQL or NoSQL store; photos must go to object storage; reads need caching and a CDN.

Common mistakes

  • Spending ten minutes on exact arithmetic.
  • Forgetting peak versus average.
  • Forgetting replication and indexes in storage estimates.
  • Computing numbers and then never referring to them again.

How to answer in the interview

"Let me assume 10 million daily users. Each writes about twice and reads about fifty times a day, so roughly 200 writes and 5,000 reads per second on average, maybe 4x at peak. That's read-heavy, so caching matters. Storage is about 7 TB a year of metadata, so one database will be tight within a couple of years; I'd plan for sharding."

Likely follow-up questions

  • How much memory for a cache? Cache the hot ~20% of daily reads; compute that size.
  • How many servers? Divide peak QPS by per-server capacity (for example 1,000–5,000 simple requests/s).
  • What latency numbers matter? Memory vs SSD vs network vs cross-region, as in the table.
