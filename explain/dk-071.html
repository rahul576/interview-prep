How do you design a registry strategy for a company: retention, replication, pull-through caches and rate limits?

Docker · concept · levels senior

In one line

Use a private registry close to each cluster as the single source of images, pull-through caches for Docker Hub and other public registries (avoiding rate limits and outages), retention policies plus garbage collection, cross-region replication, and RBAC, scanning, immutable tags and signing.

Detailed explanation

A registry strategy answers four questions: where images come from, where they are stored, how long they are kept and who can do what with them.

Single source: all production workloads pull from a company registry such as Amazon ECR, Azure Container Registry, Google Artifact Registry, Artifactory or Harbor, never directly from the internet. Public images are consumed through a pull-through cache (proxy) such as ECR pull-through cache rules, Harbor proxy projects or Artifactory remote repositories. This avoids Docker Hub pull rate limits (which hit hard when many nodes share one NAT IP), speeds pulls, keeps you running during upstream outages and lets you scan third-party images. Many companies go further and promote vetted public images into a curated repository.

Retention: CI pushes an image per commit, so storage grows fast. Lifecycle rules delete untagged images and old snapshot builds after N days while keeping release tags and anything currently deployed. In self-hosted registries, deletion only removes references; garbage collection reclaims the blobs.

Replication: images are replicated to every region with clusters, for pull speed and disaster recovery, so a regional registry outage does not stop deployments elsewhere.

Security: repository-level RBAC (CI can push, clusters can only pull), scan on push, immutable tags for release repositories, cosign signatures and SBOMs, and admission policies allowing only this registry.

How it works

  1. Create repositories per team/service with naming conventions.
  2. Configure pull-through cache rules for docker.io, ghcr.io, quay.io and point nodes and builds at them.
  3. Apply lifecycle policies and schedule garbage collection.
  4. Enable replication to all cluster regions.
  5. Enforce scanning, immutability, signing and allowed-registry policies.

Example

{
  "rules": [
    { "rulePriority": 1, "description": "expire untagged",
      "selection": { "tagStatus": "untagged", "countType": "sinceImagePushed",
                     "countUnit": "days", "countNumber": 7 },
      "action": { "type": "expire" } },
    { "rulePriority": 2, "description": "keep last 50 builds",
      "selection": { "tagStatus": "tagged", "tagPrefixList": ["build-"],
                     "countType": "imageCountMoreThan", "countNumber": 50 },
      "action": { "type": "expire" } }
  ]
}

This ECR lifecycle policy expires untagged images after a week and keeps only the 50 newest CI builds, while v* release tags are untouched.

Common mistakes

  • Nodes pulling straight from Docker Hub and hitting rate limits during a scale-out.
  • Retention rules that delete an image still running in production.
  • Mutable release tags, so 1.4.2 can silently change.
  • One global registry in a single region as a hidden single point of failure.

How to answer in the interview

"I'd have a private registry, like ECR, ACR or Harbor, as the single source for production images, located close to the clusters. Public images go through a pull-through cache, which avoids Docker Hub rate limits, speeds up pulls, survives upstream outages and gives us a place to scan them. Lifecycle policies remove untagged and old CI builds while keeping releases, followed by garbage collection where needed. Images replicate to every region we run in for speed and DR. On top, CI gets push rights and clusters pull-only, every image is scanned on push, release tags are immutable and signed, and admission policies only allow our registry."

Likely follow-up questions

  • Why immutable tags? A tag must always mean the same bits, so rollbacks, audits and security scans stay valid.
  • How do you avoid deleting running images? Exclude release tags and cross-check with what clusters report as deployed.
  • Tag vs digest in deployments? Digests are immutable by definition; many teams deploy tag plus digest.
