Where should guardrails live: in Terraform validation, in CI policy checks or in cloud policies like Azure Policy and SCPs?

Terraform · concept · levels senior, lead

In one line

Guardrails belong in all three layers as defence in depth: Terraform variable validation and preconditions for fast feedback, policy as code in CI against the plan, and cloud-native policies (Azure Policy, AWS SCPs, GCP organisation policies) as the runtime backstop for every tool.

Detailed explanation

Each layer catches different mistakes at a different cost. Terraform validation — validation blocks on variables, precondition and postcondition blocks, and opinionated module design — runs inside terraform plan on the developer's laptop. It is ideal for module-level correctness: an invalid SKU, a name that breaks the naming convention, a CIDR that is too small. Feedback arrives in seconds, but it only protects code that uses your modules.

Policy as code in CI — OPA with Conftest, HashiCorp Sentinel, Checkov or similar — evaluates the plan JSON before apply. It enforces organisation rules across every Terraform change, such as allowed regions, mandatory tags, no public storage accounts or no 0.0.0.0/0 ingress. Its strength is a clear, specific message in the pull request, before anything has been created.

Cloud-native policy — Azure Policy with deny or modify effects, AWS Service Control Policies and resource control policies, GCP organisation policy constraints — is enforced by the cloud API itself. It applies to the portal, the CLI, SDKs, other IaC tools and anyone with credentials. That makes it the real backstop: Terraform and CI can be bypassed, the cloud control plane cannot.

The design principle is that the critical rules are strict at the cloud layer, while the earlier layers exist to make compliance easy and fast, so that developers rarely hit a cryptic deny error at apply time.

How it works

  1. Write a short list of guardrails and classify each: critical (security, compliance, cost) or convention.
  2. Encode module-level rules as variable validation and precondition blocks in shared modules.
  3. Run terraform show -json plan.out in CI and evaluate it with Conftest or Sentinel; fail the PR with a readable message.
  4. Enforce critical rules in Azure Policy, SCPs or organisation policies, assigned at management group or OU level.
  5. Start new cloud policies in audit mode, review the impact, then switch to deny.
  6. Keep rules consistent across layers so a change that passes CI does not fail at the cloud.

Example

variable "location" {
  type = string
  validation {
    condition     = contains(["westeurope", "northeurope"], var.location)
    error_message = "Only westeurope and northeurope are allowed."
  }
}
package terraform.tags
deny contains msg if {
  r := input.resource_changes[_]
  r.change.after.tags.owner == null
  msg := sprintf("%s is missing the 'owner' tag", [r.address])
}

Common mistakes

  • Relying only on cloud policy, so developers discover violations as failed applies.
  • Relying only on CI checks, leaving portal and CLI changes uncontrolled.
  • Switching new cloud policies straight to deny and breaking existing workloads.
  • Rules that disagree between layers, causing confusion about which is correct.

How to answer in the interview

"I use all three as defence in depth, each for what it does best. Variable validation and preconditions give instant feedback inside the plan, for example rejecting an invalid SKU or a bad name. Policy as code in CI, with Conftest or Sentinel against the plan JSON, enforces organisation rules like allowed regions, mandatory tags and no public storage on every Terraform change, with a clear message in the pull request. Cloud-native policies such as Azure Policy, SCPs or GCP organisation policies are the real backstop, because they apply to the portal, the CLI and every other tool. I keep the cloud layer strict for critical rules, and use the earlier layers to make compliance easy."

Likely follow-up questions

  • What happens to developer experience if only cloud policy exists? Violations surface late as failed applies with generic deny messages, often half-way through a run.
  • How do you roll out a new cloud policy safely? Assign it in audit mode, review non-compliant resources, fix or exempt, then switch to deny.
  • Where do exceptions live? As documented, time-limited policy exemptions, reviewed like code, not as disabled rules.
