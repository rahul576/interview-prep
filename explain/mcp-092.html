A retailer assistant must check stock and place supplier orders. One supplier offers an MCP server, another offers an A2A agent. Design the integration.

MCP Servers · design · levels lead

In one line

Hide protocol differences behind a common internal interface (check_stock, get_price, place_order) with two adapters: an MCP client calling supplier A's tools directly, and an A2A client delegating tasks to supplier B's agent and tracking their lifecycle; across both, enforce human approval and budget limits, idempotency, order tracking, and per-supplier authentication and contracts.

Detailed explanation

The retailer's assistant should reason about suppliers and orders, not about protocols. So the core of the design is a supplier abstraction: a small internal interface with operations like check_stock(sku), get_price(sku, qty) and place_order(sku, qty, delivery_by, reference). Each supplier gets an adapter that implements it. Adding a third supplier later, with a REST API, means one more adapter.

Supplier A: MCP server. The adapter is an MCP client connecting to the supplier's remote server with OAuth credentials scoped to the retailer's account. It maps check_stock to the supplier's stock tool and place_order to its order tool. Tool calls are deterministic and synchronous: our agent stays in control and gets a structured result.

Supplier B: A2A agent. The adapter discovers the agent via its agent card, authenticates per its declared security scheme, and delegates a task, for example "Order 200 units of SKU X-114, delivered to the Nagpur warehouse by Friday, reference PO-88123." The remote agent is autonomous: it may take time, stream status, or move to input-required ("Only 150 available by Friday; accept partial delivery?"). The adapter tracks the task lifecycle, surfaces questions to our agent or a human buyer, and maps the final artifact (order confirmation) back to our interface.

Cross-cutting controls:

  • Human approval for orders above a threshold and budget limits per supplier and period, enforced in our code, not in a prompt.
  • Idempotency: an MCP idempotency key or an A2A client reference such as our PO number, so retries never double-order.
  • Order tracking in our own order system, the source of truth, with status updates and audit logs.
  • Per-supplier auth, contracts and SLAs, and treating all supplier responses, especially free-text from the remote agent, as untrusted.

How it works

  1. Agent decides stock is low and calls check_stock across suppliers.
  2. It proposes an order; policy checks budget; above threshold a buyer approves.
  3. place_order routes to the adapter: MCP tool call, or A2A task creation.
  4. A2A task streams updates; clarifying questions go to the buyer if needed.
  5. Confirmation stored in our order system with the PO reference; audit event logged.

Example

class SupplierAdapter(Protocol):
    async def check_stock(self, sku: str) -> Stock: ...
    async def place_order(self, sku: str, qty: int, deliver_by: date, ref: str) -> OrderResult: ...

class McpSupplier:
    async def place_order(self, sku, qty, deliver_by, ref):
        r = await self.session.call_tool("create_order",
              {"sku": sku, "quantity": qty, "deliver_by": deliver_by.isoformat(), "idempotency_key": ref})
        return OrderResult.from_mcp(r)

class A2ASupplier:
    async def place_order(self, sku, qty, deliver_by, ref):
        task = await self.client.send_message(
            f"Order {qty} x {sku}, deliver by {deliver_by}, PO reference {ref}.",
            metadata={"po_ref": ref})
        async for update in self.client.stream(task.id):
            if update.state == "input-required":
                await self.escalate_to_buyer(task.id, update.message)
            if update.state in ("completed", "failed", "canceled"):
                return OrderResult.from_a2a(update)

Common mistakes

  • Letting the LLM talk to both protocols directly with no internal abstraction.
  • Budget and approval rules only in the prompt.
  • No client reference, so a retried A2A task creates a second order.
  • Treating the remote agent's confirmation text as authoritative without a structured artifact.

How to answer in the interview

"The orchestration shouldn't care which protocol a supplier uses, so I'd define a common internal interface, check_stock, get_price, place_order, with two adapters. For the MCP supplier, the adapter is an MCP client calling their tools directly with OAuth scoped to our account; calls are deterministic and our agent stays in control. For the A2A supplier, the adapter discovers the agent through its agent card, delegates a task like 'order 200 units of X by Friday', and tracks the lifecycle, including questions it asks back and the final artifact like an order confirmation. Across both, orders need human approval above thresholds and stay within budget, use idempotency keys or client references, and are tracked in our own order system with audit logs."

Likely follow-up questions

  • Remote agent asks a question mid-task? Answer from policy if possible, otherwise escalate to a buyer and resume the task.
  • Why our own order system? It is the source of truth regardless of supplier protocol.
  • Testing? Contract tests per adapter and a sandbox from each supplier.
