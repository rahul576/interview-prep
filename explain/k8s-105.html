Traffic is about to triple for a sale and you must scale a Deployment manually right now. How do you do it, and what should you check?

Kubernetes · scenario · levels entry

In one line

Run kubectl scale deployment --replicas for an immediate change (or update replicas in Git), but first check for an HPA or GitOps tool that will override you, enough node capacity, and whether dependencies can take the load, then watch readiness.

Detailed explanation

The imperative command kubectl scale deployment checkout --replicas=12 -n shop updates the Deployment's desired replica count; the ReplicaSet controller creates the extra pods within seconds. The declarative way is to change spec.replicas in the manifest and apply it, or, in a GitOps setup, commit the change to Git, so the cluster and the source of truth agree.

Several things can undo or defeat a manual scale. If a HorizontalPodAutoscaler targets the Deployment, it owns the replica count and will scale back based on metrics; raise the HPA's minReplicas instead. If Argo CD or Flux manages the Deployment with self-heal, a manual change is reverted within minutes unless Git is updated (or replicas are ignored in the diff). And if the manifest still says 3 replicas, the next kubectl apply from a pipeline silently scales back down.

New pods need somewhere to run. Check spare allocatable capacity on nodes; if the cluster autoscaler or Karpenter will add nodes, remember that takes minutes, so for a known sale pre-scale nodes in advance. Dependencies matter as much: four times the pods means four times the database connections, cache clients and calls to downstream services, which may hit connection limits or rate limits. Finally, watch the rollout: kubectl rollout status, Ready pods, and latency and error dashboards.

How it works

  1. Check for an HPA and GitOps ownership.
  2. Confirm node capacity or pre-scale node groups.
  3. Check database connection limits and downstream capacity.
  4. Scale: kubectl scale, HPA minReplicas, or a Git commit.
  5. Watch pods become Ready and monitor latency and errors.
  6. After the sale, scale back and record what was needed.

Example

kubectl -n shop get hpa checkout        # is an HPA in charge?
kubectl -n shop scale deploy checkout --replicas=12
# or, if an HPA exists:
kubectl -n shop patch hpa checkout -p '{"spec":{"minReplicas":12}}'
kubectl -n shop rollout status deploy/checkout
kubectl -n shop get pods -l app=checkout

Common mistakes

  • Scaling a Deployment that an HPA immediately scales back.
  • Forgetting GitOps self-heal, which reverts the change.
  • Assuming nodes appear instantly for new pods.
  • Ignoring database connection limits until the sale starts.

How to answer in the interview

"The quick way is kubectl scale deployment with the replicas flag, and the declarative way is to change replicas in the manifest, ideally in Git, so the source of truth matches. Before scaling I check whether an HPA manages it, in which case I raise minReplicas, and whether Argo CD would revert the change. I check there is node capacity or that the autoscaler can add nodes, and pre-scale nodes for a known sale because that takes minutes. I check databases and other dependencies can handle more pods. Then I watch rollout status, readiness and dashboards."

Likely follow-up questions

  • How would you prepare autoscaling so manual scaling is not needed next time? HPA on a load metric with scheduled minimum increases, for example via KEDA's cron scaler, plus load testing.
  • Does kubectl scale cause a rollout? No; it only changes the replica count, not the pod template.
  • How do you scale down safely? Gradually, with graceful shutdown and HPA stabilisation.
