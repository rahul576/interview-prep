What is the Java Platform Module System (JPMS) and do you use it?

Core Java & OOP · concept · levels mid, senior

In one line

JPMS (Java 9, Project Jigsaw) groups packages into modules declared in module-info.java with requires and exports, giving reliable configuration and strong encapsulation, plus jlink custom runtimes; most applications still run on the classpath, but everyone feels its encapsulation of JDK internals.

Detailed explanation

Before Java 9, the classpath was a flat list of jars: any public class was accessible to anyone, missing dependencies showed up only as NoClassDefFoundError at runtime, and two versions of a library could silently conflict. The JDK itself was a monolith whose internal APIs (sun.misc.Unsafe, com.sun.*) were widely abused.

JPMS introduces modules: named, self-describing units. In module-info.java a module states:

  • requires other modules it depends on (requires transitive re-exports a dependency to its consumers, requires static is compile-time only).
  • exports packages that other modules may use; everything else is strongly encapsulated, even public classes.
  • opens packages for deep reflection (needed by frameworks like Hibernate or Jackson for private fields).
  • uses / provides for the ServiceLoader mechanism.

The module system checks the graph at startup: missing modules, cycles and split packages fail fast. The JDK was itself split into about 70 modules (java.base, java.sql, ...), enabling jlink to assemble a trimmed runtime image containing only the modules your app needs, which is useful for small containers.

In practice, most enterprise applications, including typical Spring Boot fat jars, still run on the classpath in the unnamed module, because library adoption is uneven and frameworks rely on reflection. But since JDK 16/17, JDK internals are strongly encapsulated for everyone, so old libraries fail with InaccessibleObjectException unless you add --add-opens. Libraries often add an Automatic-Module-Name manifest entry to be usable from modular apps.

How it works

  1. Each module jar contains a compiled module-info.class.
  2. At startup, the JVM resolves the module graph from --module-path.
  3. Accessibility checks ensure only exported packages are reachable.
  4. Reflection into non-opened packages throws unless opened by declaration or command-line flag.
  5. Jars on the classpath form the unnamed module, which reads all modules.

Example

// module-info.java
module com.shop.orders {
    requires java.sql;
    requires transitive com.shop.common;
    exports com.shop.orders.api;               // public API
    opens com.shop.orders.model to com.fasterxml.jackson.databind; // reflection only
    provides com.shop.common.Plugin with com.shop.orders.OrdersPlugin;
}
jlink --add-modules java.base,java.sql --strip-debug --no-header-files \
      --output build/jre-min
java --add-opens java.base/java.lang=ALL-UNNAMED -jar legacy-app.jar

Common mistakes

  • Thinking exports also allows private-field reflection; that needs opens.
  • Treating --add-opens as a permanent fix rather than upgrading the library.
  • Splitting one package across two modules (not allowed).
  • Claiming JPMS replaces Maven or Gradle; it does not handle versions or downloads.

How to answer in the interview

"JPMS came in Java 9. A module declares in module-info which modules it requires and which packages it exports; anything not exported is strongly encapsulated, even public classes, and reflection needs an opens declaration. It also validates the module graph at startup and lets jlink build a small custom runtime. Honestly, most of the applications I've worked on, like Spring Boot services, still run on the classpath, because library support is uneven. Where I feel JPMS is when upgrading JDKs: strong encapsulation of internals produces illegal reflective access errors that we fix by upgrading libraries or, temporarily, with --add-opens."

Likely follow-up questions

  • What does --add-opens do and why might you need it? It opens a module's package for deep reflection, for old libraries poking JDK internals.
  • What is an automatic module? A plain jar on the module path, named from its manifest or file name, exporting everything.
  • Does JPMS manage versions? No, it ignores versions; build tools do that.
