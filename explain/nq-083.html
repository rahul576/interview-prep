How does volatile differ from synchronization?

Concurrency · concept · levels mid

In one line

volatile gives visibility and ordering only for one variable and never blocks; synchronized gives mutual exclusion (atomicity) plus visibility for a whole block by acquiring a monitor lock. Use volatile for single-writer flags and synchronized for compound actions.

Detailed explanation

Both create happens-before edges in the Java Memory Model, so both solve visibility. A volatile write happens-before subsequent volatile reads of the same variable; a monitor release happens-before subsequent acquisitions of the same monitor. The difference is what else they give and what they cost.

volatile is a field modifier. It makes each individual read and write of that field visible and prevents harmful reordering around it. It takes no lock, so a thread is never blocked and there is no deadlock risk. But each access is independent: nothing stops another thread from running between your read and your write. So count++, if (x == null) x = ..., or updating two related fields together are not safe with volatile alone.

synchronized applies to methods or blocks. Only one thread at a time can hold a given monitor, so the whole block executes as an atomic unit with respect to other blocks on the same lock. Entering the block also sees all writes made by the previous holder before it released the lock. The costs: threads may block waiting (contention), there is some overhead, and lock ordering mistakes can cause deadlocks. synchronized is also reentrant and supports wait/notify.

Practical rule: one writer, many readers, simple value: volatile. Multiple writers, compound actions, or invariants across several fields: synchronized, a Lock, or an atomic class (AtomicInteger, AtomicReference), which combines volatile visibility with lock-free compare-and-set atomicity.

How it works

  1. volatile write: the value and preceding writes are flushed and made visible; no lock.
  2. volatile read: always reads the current value; later reads cannot move before it.
  3. synchronized entry: acquire monitor (block if held), then see prior holder's writes.
  4. Execute the block exclusively.
  5. synchronized exit: release monitor, publishing writes to the next acquirer.

Example

class Service {
    private volatile boolean shutdown;           // single writer flag: volatile fine
    private int requests;                         // compound update: needs a lock
    private long totalMillis;                     // invariant with 'requests'

    void stop() { shutdown = true; }

    void record(long millis) {
        if (shutdown) return;
        synchronized (this) {                    // both fields updated atomically
            requests++;
            totalMillis += millis;
        }
    }

    synchronized double averageMillis() {
        return requests == 0 ? 0 : (double) totalMillis / requests;
    }
}

Common mistakes

  • Thinking volatile is a "lightweight synchronized" for everything.
  • Using synchronized for writes but reading without a lock or volatile.
  • Using volatile for two fields that must change together.
  • Locking on different objects and expecting mutual exclusion.

How to answer in the interview

"volatile only guarantees that reads and writes of that one variable are visible to all threads and not reordered; it never blocks and gives no atomicity for compound actions. synchronized gives mutual exclusion, so only one thread at a time runs the guarded code on the same monitor, and visibility too, because releasing the monitor publishes changes and acquiring it sees them. So a volatile boolean is fine as a stop flag, but incrementing a shared counter or updating two related fields together needs synchronized, a Lock or an atomic class. volatile is cheaper; synchronized is broader."

Likely follow-up questions

  • Can you make count++ safe with volatile alone? No; use AtomicInteger, LongAdder or a lock.
  • How do atomic classes relate? They use volatile semantics for visibility plus CAS instructions for lock-free atomic updates.
  • Does synchronized on different objects exclude each other? No; mutual exclusion only applies to the same monitor.
