How do you use virtual threads with ExecutorService?

Modern Java (11-21) · concept · levels mid, senior

In one line

Use Executors.newVirtualThreadPerTaskExecutor(), which starts a new virtual thread per task, inside try-with-resources so closing waits for all tasks; submit tasks and collect Futures, or in Spring Boot 3.2+ set spring.threads.virtual.enabled=true.

Detailed explanation

ExecutorService is still the convenient API for submitting tasks and getting results, so virtual threads plug into it directly. Executors.newVirtualThreadPerTaskExecutor() returns an executor that does not pool: each submit or execute starts a fresh virtual thread, and the thread ends when the task ends. Because virtual threads are cheap, this is exactly what you want.

Since Java 19, ExecutorService implements AutoCloseable. Its close() method calls shutdown() and waits for submitted tasks to finish. With try-with-resources you get a clean fan-out/fan-in: start many tasks, and when the block exits, all of them are done.

Typical uses: calling several suppliers in parallel, processing a batch of independent records that each do I/O, or scatter-gather calls to microservices. You can also use invokeAll for a list of callables, or pass Thread.ofVirtual().factory() to Executors.newThreadPerTaskExecutor(factory) to name threads.

Important rules:

  • Do not put virtual threads into newFixedThreadPool(n) to limit concurrency. If you need a limit (say, 20 calls to a partner API), use a Semaphore.
  • Handle errors per future: get() throws ExecutionException wrapping the task's exception. For "fail fast, cancel the rest" semantics, structured concurrency (StructuredTaskScope, still preview in Java 25) is the better tool.
  • In Spring Boot 3.2+, spring.threads.virtual.enabled=true makes embedded Tomcat/Jetty handle requests on virtual threads and configures the application task executor and scheduler for @Async and @Scheduled to use them.

How it works

  1. Open the executor in try-with-resources.
  2. Submit one task per unit of work.
  3. Each task gets a new virtual thread.
  4. Collect results from futures.
  5. Leaving the block waits for completion and shuts down.

Example

record Price(String supplier, BigDecimal amount) {}

List<Price> bestPrices(List<String> suppliers) throws Exception {
    try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
        List<Future<Price>> futures = suppliers.stream()
            .map(s -> executor.submit(() -> fetchPrice(s)))   // blocking HTTP call
            .toList();
        List<Price> result = new ArrayList<>();
        for (Future<Price> f : futures) {
            try { result.add(f.get(2, TimeUnit.SECONDS)); }
            catch (ExecutionException | TimeoutException e) { log.warn("supplier failed", e); }
        }
        return result;
    }
}
spring.threads.virtual.enabled=true

Common mistakes

  • Using a fixed pool of virtual threads to limit concurrency.
  • Forgetting try-with-resources, leaving the executor open.
  • Ignoring ExecutionException and timeouts on futures.
  • Exhausting the DB pool by submitting thousands of DB tasks at once.

How to answer in the interview

"I use Executors.newVirtualThreadPerTaskExecutor, which creates a new virtual thread for every task instead of reusing a pool. Since Java 19 ExecutorService is AutoCloseable, so I open it in try-with-resources, submit a task per supplier, collect the futures, and leaving the block waits for everything to finish. If I need to limit concurrency towards a downstream system I use a Semaphore rather than a fixed pool. In Spring Boot 3.2 and later I just set spring.threads.virtual.enabled=true, so Tomcat requests and @Async tasks run on virtual threads."

Likely follow-up questions

  • Why should you not put virtual threads in a fixed-size pool? Pooling defeats their purpose; limit resources with semaphores instead.
  • What does close() do on the executor? Shuts down and waits for all submitted tasks.
  • What is structured concurrency? A preview API that treats related subtasks as one unit with joint cancellation and error handling.
