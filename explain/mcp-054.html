How do MCP clients register with authorization servers?

MCP Servers · concept · levels senior, lead

In one line

MCP clients identify themselves to authorization servers by Client ID Metadata Documents (recommended: the client ID is an HTTPS URL serving its metadata), pre-registration by an admin, or Dynamic Client Registration (RFC 7591), which is now treated as a legacy fallback because it is hard to govern.

Detailed explanation

OAuth requires the authorization server to know which client is asking, so it can validate redirect URIs, show the user a recognisable consent screen and apply policy. MCP's problem is scale: there are many hosts and many servers, and nobody can pre-register every combination.

Client ID Metadata Documents (CIMD) became the recommended approach in the 2025-11-25 revision. The client uses an HTTPS URL, such as https://app.example.com/oauth/client.json, as its client_id. That URL serves a JSON document with the client name, logo, redirect URIs and other metadata. When the authorization server sees the URL, it fetches and validates the document. Because the identity is anchored in a domain the client controls, administrators can allowlist or block clients by URL, and no per-server registration step is needed.

Pre-registration is the classic enterprise approach. An admin registers the client in Entra ID or Okta and gives it a client ID (and perhaps a secret). It is predictable and fully controlled, but it requires manual work for every client and server pair.

Dynamic Client Registration lets a client call a registration endpoint and get a client ID on the fly. It was the original MCP mechanism, but it produces many anonymous, unverified registrations that pile up in the identity provider, and many enterprise IdPs restrict or disable it. Newer revisions keep it only as a backwards-compatible option.

How it works

  1. Client discovers the authorization server from the MCP server's Protected Resource Metadata.
  2. It checks the AS metadata for CIMD support, pre-registered credentials, or a registration endpoint.
  3. With CIMD it sends its URL as client_id in the authorization request.
  4. The AS fetches the document, verifies redirect_uri matches, applies policy.
  5. The user sees consent naming the verified client and the flow continues with PKCE.

Example

{
  "client_id": "https://desktop.example-ai.com/oauth/client-metadata.json",
  "client_name": "Example AI Desktop",
  "redirect_uris": ["http://127.0.0.1/callback", "https://desktop.example-ai.com/callback"],
  "grant_types": ["authorization_code", "refresh_token"],
  "token_endpoint_auth_method": "none",
  "logo_uri": "https://desktop.example-ai.com/logo.png"
}

Common mistakes

  • Assuming every enterprise IdP will accept dynamic registration.
  • Not validating that redirect URIs in the fetched document match the request.
  • Treating a self-asserted client name as proof of identity without the URL check.
  • Ignoring caching and SSRF risks when the authorization server fetches metadata URLs.

How to answer in the interview

"There are three options. The recommended one since the 2025-11-25 revision is Client ID Metadata Documents: the client uses an HTTPS URL as its client ID, and that URL serves a JSON document with its name and redirect URIs. The authorization server fetches and verifies it, so clients don't need to register with every server in advance, but there's still a verifiable identity that admins can allowlist or block. Pre-registration is the classic enterprise approach where an admin registers known clients in the IdP. Dynamic Client Registration lets clients register themselves; it was the original mechanism but creates lots of anonymous registrations that are hard to govern, so it's now treated as legacy."

Likely follow-up questions

  • Why is DCR hard to govern? Anyone can register; the IdP fills with unverified clients and names that can be spoofed.
  • What does the AS check in CIMD? That the document is at the client_id URL and the redirect URI is listed.
  • When choose pre-registration? Known first-party clients in a locked-down enterprise.
