Explain GET, POST, PUT, PATCH, and DELETE.

REST & API Design · concept · levels entry, mid

In one line

GET reads (safe, idempotent, cacheable); POST creates or triggers actions (not idempotent, 201 Created); PUT replaces a full resource (idempotent); PATCH partially updates it; DELETE removes it (idempotent, usually 204).

Detailed explanation

The HTTP methods give each request a well-defined meaning (RFC 9110), which lets clients, caches, proxies and retries behave correctly.

GET retrieves a resource (GET /orders/42) or collection (GET /orders?status=PAID). It is safe, meaning it must not change server state, and idempotent. Responses can be cached and requests can be retried freely. GET requests should not carry a body; parameters go in the path or query string.

POST submits data for processing. Most often it creates a resource in a collection: POST /orders with a JSON body, returning 201 Created with a Location header (/orders/43) and usually the created resource. It is also used for actions that do not map to CRUD, like POST /orders/43/cancellation. It is not idempotent: retrying may create duplicates, so critical POSTs use an Idempotency-Key header.

PUT replaces the resource at a known URI with the full representation sent. Fields omitted are cleared or reset. Repeating the same PUT gives the same state, so it is idempotent. It can also create a resource if the client chooses the URI, returning 201. Typical responses: 200 with the body or 204.

PATCH sends only the changes: PATCH /orders/43 with {"status":"SHIPPED"} as JSON Merge Patch, or a list of operations as JSON Patch. It avoids sending the full object and overwriting concurrent changes to other fields. It is not guaranteed idempotent.

DELETE removes the resource and usually returns 204 No Content. It is idempotent: after the first call the resource is gone, and a second call returns 404 (or 204), but the state is unchanged.

Also worth knowing: HEAD (GET without body) and OPTIONS (allowed methods, CORS preflight).

How it works

  1. Client picks the method that matches its intent.
  2. Server applies the semantics (read, create, replace, modify, remove).
  3. Server returns a matching status code.
  4. Safe/idempotent properties decide caching and retry behaviour.

Example

@RestController
@RequestMapping("/orders")
class OrderController {
    @GetMapping("/{id}")  OrderDto get(@PathVariable long id) { return service.get(id); }
    @PostMapping          ResponseEntity<OrderDto> create(@Valid @RequestBody NewOrder o) {
        OrderDto created = service.create(o);
        return ResponseEntity.created(URI.create("/orders/" + created.id())).body(created);
    }
    @PutMapping("/{id}")  OrderDto replace(@PathVariable long id, @Valid @RequestBody OrderDto o) { return service.replace(id, o); }
    @PatchMapping(path = "/{id}", consumes = "application/merge-patch+json")
                          OrderDto patch(@PathVariable long id, @RequestBody Map<String, Object> changes) { return service.patch(id, changes); }
    @DeleteMapping("/{id}") @ResponseStatus(HttpStatus.NO_CONTENT)
                          void delete(@PathVariable long id) { service.delete(id); }
}

Common mistakes

  • Changing state in a GET handler.
  • Using PUT with partial data and wiping fields.
  • Returning 200 instead of 201 + Location on create.
  • Retrying POST without idempotency protection.

How to answer in the interview

"GET reads a resource or collection; it's safe, so no side effects, idempotent and cacheable. POST creates a new resource under a collection, like POST /orders, and returns 201 Created with a Location header, or triggers an action; it isn't idempotent, so a retry can create a duplicate. PUT replaces the full resource at a known URI and is idempotent. PATCH sends only the changed fields, for example as JSON Merge Patch. DELETE removes the resource, usually returns 204, and is idempotent: a second call might return 404, but the state is the same."

Likely follow-up questions

  • How do you make a POST endpoint safe to retry? Idempotency key stored with the response, or a unique business constraint.
  • Can GET have a request body? Technically allowed but has no defined semantics; avoid it.
  • What are HEAD and OPTIONS for? Headers without body, and allowed methods/CORS preflight.
