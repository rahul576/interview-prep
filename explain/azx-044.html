What are environments, approvals and checks in Azure Pipelines?

Azure DevOps & Pipelines · concept · levels mid, senior

In one line

An environment is a deployment target with deployment history; environments and other protected resources (service connections, agent pools, variable groups, secure files, repos) can have approvals and checks such as branch control, business hours, required template, exclusive lock, Azure Monitor alerts and Azure Function/REST API gates that must pass before a stage runs.

Detailed explanation

An environment (for example shop-prod) is created in Azure DevOps and optionally contains resources: Kubernetes namespaces or virtual machines (agents registered to the environment). Every deployment job that targets it is recorded, so you can see which run, commits and work items reached production and when. That is valuable for audits and incident analysis.

Approvals and checks are evaluated when a stage is about to use a protected resource. The stage waits until all pass, or fails on rejection or timeout.

  • Approvals: named users or groups must approve, optionally with instructions, a minimum number of approvers, a rule that the person who triggered the run cannot approve, and a timeout.
  • Branch control: only allowed branches (e.g. refs/heads/main, refs/heads/release/*) can use the resource, and you can require branch protection.
  • Business hours: deployments only in a window.
  • Required template: the pipeline must extend an approved template.
  • Exclusive lock: only one run uses the resource at a time; others queue (or the latest wins).
  • Query Azure Monitor alerts: block if active alerts exist, for example during an incident.
  • Invoke Azure Function / REST API: custom gates, such as checking that a ServiceNow change is approved.
  • Evaluate artifact: policies on container image metadata.

Checks on service connections are particularly important: the environment is only a logical name, while the service connection holds the credentials. If checks exist only on the environment, a pipeline could use the production service connection in a normal job and bypass them.

How it works

  1. Create environments per stage (dev, test, prod).
  2. Configure approvals and checks on the prod environment.
  3. Add the same branch control and required template checks to the prod service connection.
  4. Deployment job targets the environment; stage waits for checks.
  5. Checks pass → deploy; history recorded.

Example

- stage: Prod
  dependsOn: Test
  jobs:
  - deployment: web
    environment: shop-prod        # approvals: release-managers, business hours 08-17,
                                  # branch control main, exclusive lock, Azure Monitor alerts
    strategy:
      runOnce:
        deploy:
          steps:
          - task: AzureWebApp@1
            inputs: { azureSubscription: sc-shop-prod, appName: app-shop-prod, package: '$(Pipeline.Workspace)/web/*.zip' }

Common mistakes

  • Checks only on the environment, not on the service connection.
  • Approvers rubber-stamping without information (link to what-if or change ticket).
  • Approval timeouts so short that releases fail overnight.
  • No exclusive lock, so two runs deploy simultaneously.

How to answer in the interview

"An environment represents a deployment target like production and records which runs, commits and work items were deployed there. Environments and other protected resources, such as service connections, agent pools and variable groups, can have approvals and checks that run before a stage uses them: approvals by named people, branch control so only main deploys, business hours, required templates, exclusive locks, Azure Monitor alert queries to stop deployments during incidents, and Function or REST checks for things like approved change tickets. I put the critical checks on the service connection too, because that's where the credentials are."

Likely follow-up questions

  • Why checks on service connections? They hold the credentials; environment-only checks can be bypassed.
  • Exclusive lock behaviour? Runs queue; lockBehavior: runLatest can cancel older ones.
  • Manual validation in a pipeline? The ManualValidation task in an agentless job.
