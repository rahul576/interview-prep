How do you handle read replicas and read/write splitting in a Spring application?

Spring Data & JPA · concept · levels senior, lead

In one line

Scale reads by routing read-only transactions to replicas and writes to the primary, typically with an AbstractRoutingDataSource keyed on @Transactional(readOnly = true) plus LazyConnectionDataSourceProxy, while handling replication lag (read-your-writes) or delegating routing to a proxy/reader endpoint like ProxySQL or Aurora.

Detailed explanation

Most applications read far more than they write. Database read replicas receive the primary's changes through replication (usually asynchronous) and can serve queries, offloading the primary.

Routing in Spring. Define two DataSources (primary and replica pool) and an AbstractRoutingDataSource whose determineCurrentLookupKey() returns REPLICA when TransactionSynchronizationManager.isCurrentTransactionReadOnly() is true, and PRIMARY otherwise. Mark query services with @Transactional(readOnly = true). The catch: the transaction manager normally obtains a connection at transaction begin, possibly before the read-only flag is bound to the thread. Wrapping the routing DataSource in a LazyConnectionDataSourceProxy delays fetching the physical connection until the first statement, when the flag is known. Recent Spring Framework versions (6.1.2+) also let LazyConnectionDataSourceProxy take a separate read-only target DataSource directly, which simplifies this. Alternatively, use an explicit annotation and aspect to select the route.

Replication lag. Asynchronous replicas can be milliseconds to seconds behind. A user who just updated a profile and is redirected to a page served by a replica may see old data: read-your-writes violation. Options: keep reads that follow a write within the same request or transaction on the primary; pin a user to the primary for a short window after a write (session flag or cookie); compare replication position (for example PostgreSQL LSN or MySQL GTID) before reading; or accept eventual consistency for non-critical views. Also never use replicas for reads that drive writes, such as checking stock before decrementing.

Infrastructure alternatives. A database proxy can do the routing: ProxySQL for MySQL with query rules, Pgpool-II for PostgreSQL, or cloud endpoints such as the Aurora reader endpoint (load-balanced across replicas) and the AWS JDBC wrapper's read/write splitting. These keep application code simpler but still need the same lag awareness.

Operations. Monitor replica lag, size pools per DataSource, and have a fallback to the primary when replicas are unhealthy.

How it works

  1. Request enters a readOnly = true service method.
  2. Transaction begins; read-only flag bound to the thread.
  3. First statement: lazy proxy asks the routing DataSource for a connection.
  4. Routing chooses replica (read-only) or primary.
  5. Writes and read-after-write paths use the primary.

Example

public class ReadWriteRoutingDataSource extends AbstractRoutingDataSource {
    @Override
    protected Object determineCurrentLookupKey() {
        return TransactionSynchronizationManager.isCurrentTransactionReadOnly() ? "replica" : "primary";
    }
}

@Configuration
class DataSourceConfig {
    @Bean
    @Primary
    DataSource dataSource(@Qualifier("primaryDs") DataSource primary,
                          @Qualifier("replicaDs") DataSource replica) {
        var routing = new ReadWriteRoutingDataSource();
        routing.setTargetDataSources(Map.of("primary", primary, "replica", replica));
        routing.setDefaultTargetDataSource(primary);
        routing.afterPropertiesSet();
        return new LazyConnectionDataSourceProxy(routing);
    }
}

@Service
class ProductQueries {
    @Transactional(readOnly = true)
    public Page<ProductView> search(String q, Pageable p) { return repo.search(q, p); }  // replica
}

Common mistakes

  • Forgetting the lazy connection proxy, so everything goes to the primary.
  • Reading from a replica right after a write in the same user flow.
  • Using replica reads for decisions that lead to writes.
  • No monitoring of lag or fallback when a replica falls behind.

How to answer in the interview

"Reads can scale by sending them to replicas while writes go to the primary. In Spring I use an AbstractRoutingDataSource that picks the replica when the current transaction is read-only, using @Transactional(readOnly = true), wrapped in a LazyConnectionDataSourceProxy so the connection is chosen after the flag is set. The main issue is replication lag: a user who just wrote data might read stale results, so read-your-writes flows stay on the primary for a short time. Alternatively a proxy like ProxySQL or the Aurora reader endpoint does the routing."

Likely follow-up questions

  • Detect lag hurting users? Monitor replica lag metrics, and log or compare versions/LSNs on read-after-write paths.
  • Why the lazy proxy? The connection would otherwise be fetched before the read-only flag is known.
  • Synchronous replicas? Remove lag but add write latency; often used only within a region.
