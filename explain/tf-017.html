What does terraform plan -refresh-only do, and when do you use it?

Terraform · concept · levels mid, senior

In one line

terraform plan -refresh-only reads real infrastructure and shows how state would change to match it, i.e. drift, without proposing changes to resources; apply -refresh-only accepts those updates into state after review, replacing the deprecated, unreviewed terraform refresh.

Detailed explanation

Drift means real infrastructure no longer matches what Terraform last recorded: someone resized a database during an incident, an autoscaler changed a count, a tag was added by a policy, or a resource was deleted. A normal terraform plan detects drift during refresh but immediately proposes changes to the real infrastructure to make it match the code again, which may revert a deliberate fix.

Refresh-only mode answers a different question: "what has changed outside Terraform?". terraform plan -refresh-only refreshes every resource and reports the differences as "Objects have changed outside of Terraform", without planning any create, update or destroy actions. terraform apply -refresh-only shows the same and, after your approval, writes the refreshed values into state. Real resources are never modified.

It replaced terraform refresh, which updated state silently, with no review. That was dangerous: if credentials pointed at the wrong account or region, refresh would conclude every resource was gone and drop them all from state. terraform refresh still exists as an alias for apply -refresh-only -auto-approve but is deprecated.

Typical use: someone made an intentional out-of-band change, such as increasing a database instance class during an incident. You run refresh-only to see it and accept it into state, then update the code to match; otherwise the next normal apply reverts it. If the drift was a mistake, skip refresh-only and let a normal apply restore the desired configuration. Scheduled refresh-only plans in CI, or HCP Terraform drift detection, report drift continuously.

How it works

  1. Terraform reads each resource in state via the provider.
  2. It compares refreshed values with stored state.
  3. Differences are shown as changes outside Terraform.
  4. No resource actions are planned.
  5. On apply, only state is updated.
  6. You then align code with reality, or revert with a normal apply.

Example

terraform plan -refresh-only
#   ~ resource "aws_db_instance" "orders" {
#       ~ instance_class = "db.r6g.large" -> "db.r6g.xlarge"
#     }
# This is a refresh-only plan, so Terraform will not take any actions to undo these.

terraform apply -refresh-only      # review, type yes
# then change instance_class in code to "db.r6g.xlarge" and open a PR

Common mistakes

  • Accepting refresh-only changes without reading them.
  • Forgetting to update the code afterwards, so the next apply reverts the fix.
  • Running refresh with the wrong credentials and losing resources from state.
  • Using refresh-only to "fix" a plan instead of understanding the drift.

How to answer in the interview

"terraform plan -refresh-only reads the real infrastructure and shows how the state would change to match it, without proposing any changes to the resources, so it's essentially a drift report. terraform apply -refresh-only writes those changes into state after I approve them. It replaced terraform refresh, which updated state silently and is deprecated. I use it when someone made an intentional out-of-band change, like resizing a database in an incident, to record reality in state. Afterwards I update the code to match, otherwise the next normal apply reverts it; if the drift was a mistake, a normal apply puts things back."

Likely follow-up questions

  • Risks of accepting without reading? A resource deleted by mistake or wrong credentials could drop resources from state.
  • How do you detect drift regularly? Scheduled refresh-only plans with -detailed-exitcode, or HCP Terraform drift detection.
  • What does -refresh=false do? Skips refresh entirely, the opposite trade-off.
