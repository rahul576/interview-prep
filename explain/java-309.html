What does Spring Cloud provide for microservices, and which parts are still relevant on Kubernetes?

Spring Boot · concept · levels senior, lead

In one line

Spring Cloud offers Config Server, Gateway, OpenFeign, a Circuit Breaker abstraction over Resilience4j, Eureka discovery, LoadBalancer, Stream and Bus; on Kubernetes, Services/DNS replace Eureka and ConfigMaps/Secrets often replace Config Server, while Gateway, HTTP clients and Resilience4j stay relevant.

Detailed explanation

Spring Cloud was born in the Netflix OSS era when teams ran microservices on VMs and had to build service discovery, client-side load balancing and central config themselves. Its main projects:

  • Spring Cloud Config: a Config Server serving properties from Git or Vault, with refresh via @RefreshScope and Spring Cloud Bus.
  • Spring Cloud Netflix Eureka: service registry and discovery. (Hystrix, Ribbon and Zuul are gone; replaced by Resilience4j, Spring Cloud LoadBalancer and Gateway.)
  • Spring Cloud Gateway: reactive (and now also MVC-based) API gateway with routes, predicates and filters: rate limiting, token relay, rewriting.
  • Spring Cloud OpenFeign: declarative HTTP clients (now feature-complete; Spring's own HTTP interfaces are the suggested future path).
  • Spring Cloud Circuit Breaker: abstraction with Resilience4j as the main implementation.
  • Spring Cloud LoadBalancer: client-side load balancing.
  • Spring Cloud Stream: binder-based messaging over Kafka or RabbitMQ.
  • Spring Cloud Kubernetes: discovery and config from the Kubernetes API.

On Kubernetes, the platform covers several concerns:

  • Discovery: a Kubernetes Service gives a stable DNS name and load balances across pods, so Eureka and client-side balancing are usually redundant. Running Eureka would duplicate state and health information the platform already has.
  • Configuration: ConfigMaps and Secrets mounted as files or env vars, often managed by GitOps, plus External Secrets for vaults. Config Server is still useful for shared, frequently changed config across many apps or non-Kubernetes environments.
  • Gateway and resilience: an Ingress controller or Gateway API, and a service mesh like Istio, can handle routing, retries, timeouts, mTLS and outlier detection.

Still widely used: Spring Cloud Gateway for application-aware routing, BFF and token relay; Resilience4j for in-code circuit breakers with fallbacks; declarative clients; Stream for messaging.

How it works

  1. Decide which concerns the platform owns: discovery, config, traffic, mTLS.
  2. Remove overlapping Spring Cloud components (Eureka, Ribbon-era load balancing).
  3. Keep app-level concerns in code: fallbacks, business routing, token relay.
  4. Use Spring Cloud Kubernetes or plain env/config trees for config.
  5. Avoid configuring the same retry both in the mesh and in code.

Example

# Feign or HTTP interface calls a Kubernetes Service by DNS, no Eureka
spring:
  cloud:
    openfeign:
      client:
        config:
          inventory:
            url: http://inventory.shop.svc.cluster.local:8080
            connect-timeout: 1000
            read-timeout: 2000
resilience4j:
  circuitbreaker:
    instances:
      inventory:
        failure-rate-threshold: 50
        wait-duration-in-open-state: 10s

Common mistakes

  • Running Eureka on Kubernetes out of habit.
  • Duplicate retries in mesh, gateway and client causing retry storms.
  • Mixing incompatible Spring Cloud and Boot versions; use the release train BOM.

How to answer in the interview

"Spring Cloud gives Config Server for central configuration, Spring Cloud Gateway as an API gateway, OpenFeign for declarative clients, a circuit breaker abstraction backed by Resilience4j, Eureka for discovery, LoadBalancer and Stream for messaging. On Kubernetes several parts are replaced by the platform: Services and DNS replace Eureka, ConfigMaps and Secrets often replace Config Server, and ingress or a service mesh can take over routing, retries and mTLS. What remains widely used is Gateway for application-aware routing and token relay, Feign or HTTP interfaces, Resilience4j for fallbacks, and Stream."

Likely follow-up questions

  • Would you run Eureka on Kubernetes? Usually not; it duplicates Services and adds a component to operate, unless hybrid VM and Kubernetes discovery is needed.
  • Mesh or Resilience4j? Mesh for uniform policies; Resilience4j when you need fallbacks and business-aware behaviour.
  • How to keep versions aligned? Import the spring-cloud-dependencies BOM matching the Boot version.
