Why is StringBuilder generally preferred over String concatenation in loops?

Core Java & OOP · concept · levels mid, senior

In one line

Because String is immutable, s = s + x in a loop creates a new String and copies all previous characters every iteration, giving O(n²) work and lots of garbage; StringBuilder appends into a resizable buffer in amortised O(1).

Detailed explanation

Consider building a CSV line from 10,000 values with result += value + ",";. Each iteration:

  1. Creates a new String (or builder) for the concatenation.
  2. Copies every character of the current result into it.
  3. Appends the new piece.
  4. Discards the old result.

If the final string has length L, the total characters copied is roughly L/2 per iteration on average times n iterations, which is quadratic. With 10,000 values of 10 characters that is around 500 million character copies instead of 100,000, plus tens of thousands of short-lived objects that increase GC pressure and allocation rate.

StringBuilder keeps a mutable byte array with spare capacity. append writes into the free space. When full, it grows (roughly double plus two) and copies once, so the total copying is linear: amortised constant time per append. You call toString() once at the end. Presizing (new StringBuilder(expectedLength)) removes even the growth copies.

The compiler does help, but only within a single expression. a + b + c compiles (since Java 9) to one invokedynamic call to StringConcatFactory that computes the exact length and fills one array. It cannot merge work across loop iterations, because each iteration is a separate expression whose result is assigned back to an immutable variable. Escape analysis also rarely rescues this pattern.

For joining collections, String.join, StringJoiner and Collectors.joining use a builder internally and handle separators cleanly. For readability, plain + is perfect outside loops. Prefer StringBuilder over the synchronised StringBuffer unless the buffer is really shared between threads.

How it works

  1. Builder allocates an internal array (default capacity 16).
  2. Each append copies only the new characters into free space.
  3. On overflow, it allocates a larger array and copies once.
  4. toString() creates the final immutable String.

Example

// O(n^2): new String every iteration
String slow = "";
for (int i = 0; i < 100_000; i++) slow += i + ",";

// O(n): one buffer, presized
StringBuilder sb = new StringBuilder(100_000 * 6);
for (int i = 0; i < 100_000; i++) sb.append(i).append(',');
String fast = sb.toString();

// Clearest for collections
String joined = IntStream.range(0, 100_000).mapToObj(Integer::toString)
                         .collect(Collectors.joining(","));

Common mistakes

  • Using sb.append(a + b), which creates a temporary string; append separately.
  • Replacing every + with a builder, hurting readability for no gain.
  • Sharing a StringBuilder across threads.
  • Forgetting that logging string building also costs; use parameterised logging (log.debug("x={}", x)).

How to answer in the interview

"String is immutable, so s = s + x in a loop creates a new String each iteration and copies everything built so far. Over n iterations that's quadratic work and a lot of short-lived garbage. StringBuilder keeps a mutable, resizable buffer; append writes into it in amortised constant time and only occasionally grows, and I call toString once at the end. The compiler optimises a single expression like a + b + c, but it can't remove the repeated allocation across loop iterations. Presizing the builder helps further, and for collections Collectors.joining is often the cleanest."

Likely follow-up questions

  • Why is StringBuilder preferred over StringBuffer in most code? Builders are usually thread-local, so StringBuffer's synchronisation is pure overhead.
  • Does the JIT fix loop concatenation? Generally no.
  • What's the default capacity? 16 characters, or 16 plus the initial string's length.
