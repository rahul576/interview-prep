What is the difference between start() and run()?

Concurrency · concept · levels entry, mid

In one line

start() asks the JVM to create a new thread that then calls run(); calling run() directly is just an ordinary method call on the current thread, so there is no concurrency.

Detailed explanation

Thread.run() holds the work: either your override, or it delegates to the Runnable you passed in. On its own it is just a method. Thread.start() is what makes a thread: it moves the thread from the NEW state to RUNNABLE, the JVM creates a native thread (or schedules a virtual thread) with its own call stack, and that new thread invokes run(). start() returns immediately, so the caller continues in parallel.

If you call run() directly, the code executes synchronously on the calling thread. The output looks correct, which is why this bug is easy to miss, but you lose all concurrency: a slow run() blocks the caller, Thread.currentThread().getName() inside it prints main (or whatever the caller is), and the Thread object remains in the NEW state.

A thread can be started only once. Calling start() again, even after the thread has finished, throws IllegalThreadStateException, because a terminated thread's native resources are gone and the lifecycle is one way: NEW, RUNNABLE, (BLOCKED/WAITING/TIMED_WAITING), TERMINATED. To run the work again, create a new Thread or, better, submit the Runnable again to an executor.

In modern code you rarely call either method by hand. You submit tasks to an ExecutorService, use CompletableFuture, or start virtual threads with Thread.startVirtualThread(task) or Executors.newVirtualThreadPerTaskExecutor().

How it works

  1. new Thread(task) creates a Thread object in state NEW; no OS thread exists yet.
  2. start() registers it with the JVM, which creates the underlying thread and stack.
  3. The new thread runs run(), which calls task.run().
  4. The caller continues immediately after start().
  5. When run() returns or throws, the thread is TERMINATED and cannot be restarted.

Example

Runnable task = () ->
    System.out.println("Running in " + Thread.currentThread().getName());

Thread t = new Thread(task, "worker-1");

t.run();     // prints "Running in main"   - same thread, synchronous
t.start();   // prints "Running in worker-1" - new thread, asynchronous
t.join();

t.start();   // throws IllegalThreadStateException - already started once

Common mistakes

  • Calling run() and believing the code is running in parallel.
  • Trying to restart a finished thread instead of creating a new one.
  • Overriding start() instead of run().
  • Creating raw threads in server code instead of using a managed executor.

How to answer in the interview

"start asks the JVM to create a new thread with its own call stack, and that new thread then invokes run, while the caller continues immediately. Calling run directly is just a normal method call, so the code runs on the current thread, sequentially, with no concurrency at all; if it is slow it blocks the caller. A thread can be started only once, so calling start twice throws IllegalThreadStateException. So run defines the work and start executes it asynchronously. In practice I rarely call either: I submit tasks to an ExecutorService or use virtual threads."

Likely follow-up questions

  • Why can a Thread not be restarted after it finishes? Its lifecycle is one way and the native thread is released on termination; the API forbids reuse, so create a new thread or reuse via a pool.
  • How do you get a result from a thread? Use a Callable with an ExecutorService, which returns a Future, or a CompletableFuture.
  • What state is a Thread in before start()? NEW, as reported by getState().
