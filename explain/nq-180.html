What is Spring Boot Actuator, and what information does it expose?

Spring Boot · concept · levels entry, mid

In one line

Actuator adds production-ready endpoints under /actuator: health (with liveness/readiness groups), info, metrics/prometheus, and diagnostics like env, beans, mappings, conditions, loggers, threaddump, heapdump; only health is exposed over HTTP by default, and sensitive endpoints must be secured.

Detailed explanation

Running a service in production requires answers to: is it up, is it healthy, how is it performing, and what is it doing right now? Actuator answers those through endpoints that are available over HTTP or JMX.

health aggregates HealthIndicators for the database, disk space, Redis, Kafka and more into UP/DOWN. Spring Boot defines liveness and readiness groups (/actuator/health/liveness, /actuator/health/readiness) designed for Kubernetes probes; they are enabled automatically on Kubernetes and can be enabled elsewhere with management.endpoint.health.probes.enabled. info shows build, git and custom info. metrics and prometheus expose Micrometer metrics: JVM memory and GC, HTTP request timings, HikariCP pool usage, executor and cache statistics. Observability integrates with tracing through Micrometer Tracing and OpenTelemetry.

Diagnostic endpoints include env and configprops (resolved configuration), beans, mappings (all request mappings), conditions (auto-configuration report), loggers (view and change log levels at runtime with a POST), threaddump, heapdump, scheduledtasks, caches and startup.

Security matters: env, configprops and heapdump can reveal secrets and personal data. Boot masks values by default in env and configprops, but you should expose only what you need with management.endpoints.web.exposure.include, protect them with Spring Security, and often bind them to a separate management port that is not reachable from the internet.

How it works

  1. Add spring-boot-starter-actuator.
  2. Endpoints are enabled but only health is exposed over HTTP.
  3. Choose exposure with management.endpoints.web.exposure.include.
  4. Health indicators are auto-configured for detected dependencies.
  5. Micrometer registers metrics; a registry (Prometheus, OTLP) publishes them.

Example

management:
  server:
    port: 9090
  endpoints:
    web:
      exposure:
        include: health,info,prometheus,loggers
  endpoint:
    health:
      probes:
        enabled: true
      show-details: when-authorized
curl localhost:9090/actuator/health/readiness
curl -X POST localhost:9090/actuator/loggers/com.acme \
  -H 'Content-Type: application/json' -d '{"configuredLevel":"DEBUG"}'

Common mistakes

  • exposure.include=* on a public port.
  • Putting external dependency checks into the liveness probe, causing restart storms.
  • Ignoring the metrics and using Actuator only for health.
  • Leaving heapdump reachable, exposing memory contents.

How to answer in the interview

"Actuator adds monitoring and management endpoints under /actuator. Health shows the app and its dependencies, with liveness and readiness groups for Kubernetes probes. Info shows build and git data, and metrics and prometheus expose Micrometer metrics like JVM memory, HTTP latency and connection pools. For diagnostics there are env, beans, mappings, conditions, loggers to change log levels at runtime, threaddump and heapdump. By default only health is exposed over HTTP; I expose more explicitly, secure them and often use a separate management port."

Likely follow-up questions

  • How do probes use health groups? Liveness checks the app itself; readiness can include dependencies to stop traffic without restarting.
  • How to add a custom check? Implement HealthIndicator and return Health.up() or down().
  • Custom metrics? Inject MeterRegistry and register counters, timers or gauges.
