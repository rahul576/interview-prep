How does connection pooling work, and how do you size HikariCP?

Spring Data & JPA · concept · levels mid, senior

In one line

A connection pool keeps database connections open and reuses them to avoid expensive connects; HikariCP is Spring Boot's default; size it small (start near cores × 2 + effective spindles, often 10-20), set connectionTimeout and maxLifetime, and keep pool size × instances under the database's max_connections.

Detailed explanation

Opening a database connection involves a TCP handshake, often TLS, authentication and server-side session setup: milliseconds to tens of milliseconds, plus a process or thread on the database server. A pool opens a set of connections once and lends them out: getConnection() borrows one, close() returns it. HikariCP is fast, lightweight and the default in Spring Boot.

Sizing counterintuition. More connections don't mean more throughput. The database has a limited number of CPU cores and I/O channels; beyond that, extra concurrent queries just compete, add context switching and lock contention, and latency rises. HikariCP's wiki cites the PostgreSQL-derived starting formula connections = (core_count × 2) + effective_spindle_count, which for a typical database server gives 10-20. Then tune by measurement: watch hikaricp.connections.pending (threads waiting), hikaricp.connections.acquire time and usage, and database CPU and wait events. Also remember the default maximumPoolSize is 10 and Hikari recommends a fixed-size pool (minimumIdle equal to max).

Timeouts. connectionTimeout (default 30 s) is how long a thread waits for a connection; lower it (for example 2-5 s) so requests fail fast instead of piling up. maxLifetime (default 30 min) retires connections; set it a bit shorter than any database, firewall, load balancer or proxy idle timeout so connections aren't killed underneath you. idleTimeout, keepaliveTime and leakDetectionThreshold (logs connections held too long) help too.

Fleet-wide limits. Each application instance has its own pool. Ten pods with a pool of 20 means 200 connections; with autoscaling it can exceed the database's max_connections. Budget the total, and if you have many instances or serverless functions, put a server-side pooler such as PgBouncer, RDS Proxy or ProxySQL in front.

If threads wait on getConnection, first check why connections are held: slow queries, long transactions, remote calls inside transactions, OSIV, or leaks. Increasing the pool often just moves the bottleneck into the database.

How it works

  1. At startup Hikari opens minimumIdle connections.
  2. A request borrows a connection; if none free, it waits up to connectionTimeout.
  3. Query runs; connection returned at transaction end.
  4. Connections are retired after maxLifetime and replaced.
  5. Metrics expose active, idle and pending counts.

Example

spring:
  datasource:
    hikari:
      maximum-pool-size: 16
      minimum-idle: 16
      connection-timeout: 3000      # ms
      max-lifetime: 1680000         # 28 min, below a 30 min proxy idle timeout
      keepalive-time: 300000
      leak-detection-threshold: 20000
DB: 8 cores, SSD  → start at ~ 8*2 + 1 = 17 connections in total for the busiest workload
6 pods × 16 = 96 connections  <  max_connections 200 (leave room for admin, migrations)

Common mistakes

  • Pool size 100+ "to be safe", overloading the database.
  • Ignoring the multiplier of instances and autoscaling.
  • maxLifetime longer than infrastructure idle timeouts, causing broken connections.
  • Raising the pool to hide long transactions or leaks.

How to answer in the interview

"Opening a connection is expensive, so a pool keeps connections open and reuses them; HikariCP is the Spring Boot default. Pools should be small, because the database can only do so much in parallel; a common starting point is about twice the database cores plus effective spindles, often ten to twenty, then I tune by measuring wait time. I set connectionTimeout so requests fail fast and maxLifetime below any database or proxy idle timeout. I multiply pool size by instance count to stay under max connections, and use PgBouncer if needed."

Likely follow-up questions

  • Threads waiting on getConnection; increase the pool? First find why connections are held long; only increase if the database has headroom.
  • Pool with virtual threads? The pool becomes the concurrency limit; keep it sized for the database, not the thread count.
  • Detect leaks? leakDetectionThreshold and active-connection metrics.
