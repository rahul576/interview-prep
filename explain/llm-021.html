How do you estimate and track the token cost of an LLM feature?

LLMOps & RAG · concept · levels entry, mid, senior

In one line

Token cost = input tokens x input price + output tokens x output price (output is several times dearer), counting everything sent each call (system prompt, history, retrieved context, tool results, reasoning tokens), multiplied by calls per action, actions per user and users; then track real usage from API responses and use caching and batch discounts.

Detailed explanation

Providers price per million tokens, with separate rates for input and output; output usually costs about 3 to 5 times more. Discounts exist for cached input (prompt caching) and batch APIs (often around 50 percent off for asynchronous jobs).

Counting tokens. Use the provider's tokenizer or token-counting endpoint, not word counts. As a rule of thumb, one token is about 0.75 English words (about 4 characters); many other languages, code and JSON use more tokens per word, and different model families tokenise differently.

What goes into input. Not just the user's question. Each call sends the system prompt, tool definitions (which can be thousands of tokens), conversation history (growing every turn), retrieved documents, and in agents, previous tool calls and results. In a 10-step agent loop, input grows at each step because the transcript is resent, so total input is roughly quadratic in steps unless caching or summarisation is applied. Reasoning models produce hidden or summarised thinking tokens billed as output, often exceeding the visible answer.

Estimating. Tokens per call x calls per user action x actions per user per month x users, plus a margin (10 to 30 percent) for retries, longer-than-typical inputs and growth. Compare alternatives: a smaller model, shorter prompts, caching.

Tracking. Every API response includes a usage object (input, output, cached and reasoning tokens). Record it per request with tags for feature, team, tenant and model, compute cost with a price table, and export to dashboards. Alert on cost per request drift and daily spend anomalies; a prompt change or runaway agent loop can multiply costs overnight. Set max tokens and step limits as safety nets.

How it works

  1. Sample realistic requests; count tokens per component.
  2. Apply input, cached and output prices.
  3. Multiply by call volume; add margin.
  4. In production, log usage per call with tags.
  5. Review dashboards; optimise the largest contributors.

Example

Support assistant, per answer:
  system + tools 2,500 | history 1,500 | 5 retrieved chunks 3,000 | question 100 → input 7,100
  output 400
Prices (illustrative): input $3/M, cached input $0.30/M, output $15/M
  Without cache: 7,100*3e-6 + 400*15e-6 = $0.0213 + $0.0060 = $0.0273
  With 2,500 cached: 4,600*3e-6 + 2,500*0.3e-6 + $0.0060 ≈ $0.0206
Volume: 2 answers/session * 3 sessions/user/month * 50,000 users = 300,000 answers
Monthly ≈ $6,200 (cached) to $8,200 (uncached), +20% margin

Common mistakes

  • Counting only the user's message as input.
  • Forgetting reasoning tokens and tool definitions.
  • Estimating agents as one call.
  • No per-feature attribution, so cost spikes cannot be traced.

How to answer in the interview

"Pricing is per token, with output several times dearer than input and discounts for cached and batch tokens. I count tokens with the provider tokenizer for a typical request, including everything sent each time: system prompt, tool definitions, history, retrieved documents and earlier tool results, plus reasoning tokens billed as output. Then I multiply by calls per action, actions per user and users, with a margin for retries. In production I record the usage returned in every response, tag it by feature and team, and alert when cost per request drifts."

Likely follow-up questions

  • Why do agents cost more than estimated? The growing transcript is resent each step, plus retries and reasoning tokens.
  • Cheapest optimisations? Prompt caching, trimming context, smaller models for easy steps, batch APIs.
  • Self-hosted cost per token? GPU cost per hour divided by tokens served at real utilisation.
