What is the Visitor pattern?

Design Patterns · concept · levels senior, lead

In one line

Visitor lets you add new operations to an object structure without changing its classes: each element has accept(visitor) calling visitor.visit(this), giving double dispatch; it suits stable types with growing operations, and modern Java often replaces it with sealed types and pattern-matching switch.

Detailed explanation

Java method calls are single dispatch: which override runs depends on the runtime type of the receiver, but overloads are chosen from the static type of the arguments. If you have a List<Shape> and an AreaCalculator with visit(Circle) and visit(Square), calling calc.visit(shape) with a Shape variable will not pick the right overload.

Visitor solves this with double dispatch:

  1. Each element class implements accept(Visitor v) { v.visit(this); }.
  2. Inside accept, this has the concrete static type (Circle), so the compiler selects visit(Circle).
  3. The first dispatch is on the element (virtual accept), the second on the visitor (virtual visit).

Now new operations, such as area, perimeter, JSON export or rendering, are just new Visitor implementations; the shape classes never change. That fits domains where the set of types is stable but operations keep growing: compilers and abstract syntax trees (type checking, optimisation, code generation, pretty printing), document models, and Files.walkFileTree with FileVisitor. Tools like the Java compiler's tree API and ASM bytecode library use visitors.

The trade-off is the reverse: adding a new element type forces a change to the visitor interface and every visitor. Visitors may also need access to element internals, weakening encapsulation, and the boilerplate is heavy.

Modern Java (21+): with sealed interfaces, records and pattern matching for switch, you can write switch (shape) { case Circle c -> ...; case Square s -> ...; }. The compiler checks exhaustiveness over the sealed hierarchy, so adding a new type produces compile errors where it is not handled, which is the same safety Visitor gives with far less code.

How it works

  1. Define Visitor<R> with one visit per element type.
  2. Each element implements accept(Visitor<R> v) returning v.visit(this).
  3. Write a visitor per operation.
  4. Client calls element.accept(new SomeVisitor()).
  5. Adding a new type means updating the interface and all visitors.

Example

// Classic Visitor
interface ShapeVisitor<R> { R visit(Circle c); R visit(Square s); }
interface Shape { <R> R accept(ShapeVisitor<R> v); }
record Circle(double r) implements Shape { public <R> R accept(ShapeVisitor<R> v) { return v.visit(this); } }
record Square(double side) implements Shape { public <R> R accept(ShapeVisitor<R> v) { return v.visit(this); } }

class Area implements ShapeVisitor<Double> {
    public Double visit(Circle c) { return Math.PI * c.r() * c.r(); }
    public Double visit(Square s) { return s.side() * s.side(); }
}
double a = shape.accept(new Area());

// Java 21 alternative
sealed interface Shape2 permits Circle2, Square2 {}
record Circle2(double r) implements Shape2 {}
record Square2(double side) implements Shape2 {}

static double area(Shape2 s) {
    return switch (s) {                    // exhaustive: no default needed
        case Circle2 c -> Math.PI * c.r() * c.r();
        case Square2 q -> q.side() * q.side();
    };
}

Common mistakes

  • Using Visitor when element types change frequently.
  • Believing overloading alone gives double dispatch.
  • Adding a default branch to sealed switches, losing exhaustiveness checks.
  • Overusing it for two operations that could be ordinary methods.

How to answer in the interview

"Visitor lets me add operations to a class hierarchy without modifying it. Each element has accept(visitor) that calls visitor.visit(this), and the visitor has a visit method per type. That's double dispatch: first on the element, then on the visitor, so the right overload runs. It fits when the types are stable but operations grow, like a compiler walking an AST for type checking and code generation, or Files.walkFileTree with a FileVisitor. The cost is that adding a new element type changes every visitor. In Java 21, sealed interfaces with pattern-matching switch give exhaustive type handling with much less code."

Likely follow-up questions

  • How does Java 21 reduce the need for Visitor? Sealed hierarchies plus exhaustive pattern-matching switch let the compiler check every type is handled.
  • What is double dispatch? Choosing the method by the runtime types of two objects, achieved via two virtual calls.
  • When is Visitor a bad fit? When new element types are added often.
