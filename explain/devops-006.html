Which branching strategy would you recommend for a team that deploys several times a day?

Git · concept · levels entry, mid

In one line

For several deployments a day, use trunk-based development: short-lived branches (hours to a day or two) merged into an always-deployable main through PRs with review and required CI checks, with feature flags hiding incomplete work; GitFlow is too heavy for this pace.

Detailed explanation

Frequent deployment needs small, frequent integration. The longer a branch lives, the more it diverges, the bigger and riskier the merge, and the slower the feedback.

Trunk-based development: everyone integrates into main (trunk) at least daily. Work happens on short-lived feature branches, ideally merged within a day or two, through pull requests with code review and required status checks (build, tests, security scans) enforced by branch protection. Main is always releasable, and every merge can flow to production through the CD pipeline. Small PRs are also faster and better to review.

Incomplete work: instead of keeping a feature on a branch for weeks, merge it in small pieces behind feature flags (toggles) that are off in production, or use branch by abstraction for large refactorings. This separates deploy (code in production) from release (feature visible to users), and enables gradual rollout and instant kill switches. Remove flags once a feature is fully released.

GitFlow uses develop, feature/, release/ and hotfix/* branches plus main. It suits versioned products with scheduled releases and several supported versions (desktop software, libraries, on-premises products), but creates long-lived branches, merge pain and delays, which conflict with continuous delivery.

GitHub Flow is a lightweight middle ground: branch from main, open a PR, deploy (sometimes from the branch for verification), merge. In practice it is very close to trunk-based development with PRs.

Hotfixes in trunk-based development: fix on a short branch from main, merge quickly and deploy through the normal (fast) pipeline. If you release from release branches, cherry-pick the fix there.

How it works

  1. Pull latest main; create a short branch.
  2. Make a small change behind a flag if incomplete.
  3. Open a PR; CI runs; a teammate reviews.
  4. Merge to main within a day or two.
  5. CD deploys main to production.
  6. Enable the flag gradually; remove it later.

Example

git switch -c feat/checkout-discount origin/main
# small, flagged change
git commit -am "Add discount calculation behind checkout.discount flag"
git push -u origin feat/checkout-discount
gh pr create --fill --base main
if (flags.isEnabled("checkout.discount", user)) {
    total = discountService.apply(total, user);
}

Common mistakes

  • Calling it trunk-based while branches live for weeks.
  • No required CI checks, so main breaks often.
  • Feature flags never removed, becoming technical debt.
  • Large PRs that take days to review.

How to answer in the interview

"For several deployments a day I'd recommend trunk-based development. People work on short-lived branches, ideally under a day or two, merged into main through pull requests with code review and required CI checks, and main is always deployable. Incomplete work is hidden behind feature flags rather than long-running branches, which also separates deploy from release. GitFlow, with develop, release and hotfix branches, fits versioned products with scheduled releases, but its long-lived branches slow continuous delivery. GitHub Flow is a lightweight alternative that works well for web services."

Likely follow-up questions

  • Urgent hotfix? Short branch from main, fast PR, normal pipeline; cherry-pick to a release branch if one exists.
  • How to keep main green? Required checks, merge queues and fast revert culture.
  • How to manage flags? A flag service with owners, expiry dates and cleanup tickets.
