What is Mockito, and why is it used?

Testing · concept · levels entry

In one line

Mockito is the most widely used Java mocking framework; it creates test doubles for a class's dependencies so you can test it in isolation, stub responses with when().thenReturn()/thenThrow(), verify interactions, and use @Mock, @InjectMocks, MockitoExtension, argument matchers and captors.

Detailed explanation

Imagine testing a UserService that uses a UserRepository, an EmailSender and a Clock. With real implementations the test needs a database and an SMTP server, runs slowly and cannot easily simulate "the email server times out". Mockito replaces each dependency with a mock: an object of the same type whose behaviour you script.

Why it is used:

  • Isolation: failures point at the class under test, not at a database or network issue.
  • Speed and determinism: no I/O, the same result every run.
  • Hard-to-produce situations: exceptions, timeouts, empty results, specific data, on demand.
  • Verifying side effects: check that an email was sent or a record saved, exactly once, with the right data.

Core API:

  • Create: mock(UserRepository.class) or @Mock fields with @ExtendWith(MockitoExtension.class); @InjectMocks builds the class under test with those mocks.
  • Stub: when(repo.findById(1L)).thenReturn(Optional.of(user)), thenThrow(...), thenAnswer(...); BDD style given(...).willReturn(...); for void methods doThrow(...).when(mock).method().
  • Verify: verify(emailSender).send(any()), times(1), never(), atLeastOnce().
  • Matchers: any(), eq(), anyString(), argThat(...); if one argument uses a matcher, all must.
  • Captors: ArgumentCaptor<Email> captures the actual argument for detailed assertions.

Unstubbed methods return defaults: null, 0, false, empty collections and empty Optional. Mockito 5 uses the inline mock maker by default, so final classes can be mocked.

Avoid mocking types you do not own (for example a third-party HTTP client): your mock may not behave like the real library. Wrap it in your own interface and test the wrapper with WireMock instead.

How it works

  1. MockitoExtension creates fresh mocks before each test.
  2. Stubs define answers for specific calls.
  3. The real class under test calls the mocks.
  4. Mockito records every invocation.
  5. verify checks the recorded calls; strict stubs flag unused stubs.

Example

@ExtendWith(MockitoExtension.class)
class UserServiceTest {
    @Mock UserRepository repo;
    @Mock EmailSender email;
    @InjectMocks UserService service;
    @Captor ArgumentCaptor<Email> sent;

    @Test
    void sendsWelcomeEmailOnRegistration() {
        when(repo.existsByEmail("asha@example.com")).thenReturn(false);
        when(repo.save(any())).thenAnswer(inv -> inv.getArgument(0));

        service.register("asha@example.com");

        verify(email).send(sent.capture());
        assertThat(sent.getValue().subject()).contains("Welcome");
    }

    @Test
    void rejectsDuplicateEmail() {
        when(repo.existsByEmail("asha@example.com")).thenReturn(true);
        assertThatThrownBy(() -> service.register("asha@example.com"))
            .isInstanceOf(DuplicateUserException.class);
        verify(email, never()).send(any());
    }
}

Common mistakes

  • Mixing matchers and raw values in one call.
  • Verifying every single interaction, making tests brittle.
  • Mocking simple value objects instead of creating them.
  • Forgetting MockitoExtension, so @Mock fields stay null.

How to answer in the interview

"Mockito is the most popular mocking framework in Java. It creates mock objects that stand in for a class's dependencies, like repositories, HTTP clients or other services, so I can test the class in isolation, quickly, and simulate things that are hard to produce for real, like timeouts or errors. I stub behaviour with when-thenReturn or thenThrow, and check interactions with verify, for example that an email was sent once. With JUnit 5 I use MockitoExtension, @Mock for dependencies and @InjectMocks for the class under test, plus argument matchers and ArgumentCaptor to inspect what was passed."

Likely follow-up questions

  • Why avoid mocking types you don't own? Your mock encodes assumptions about a library that may be wrong; wrap it instead.
  • What does an unstubbed mock return? Defaults: null, 0, false, empty collections or Optional.
  • How do you stub a void method to throw? doThrow(new X()).when(mock).method().
