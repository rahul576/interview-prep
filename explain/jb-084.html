Can finally execute without a catch block?

Exceptions · concept · levels mid, senior

In one line

Yes: try { } finally { } without catch is valid; finally runs, then the exception propagates to the caller; it is the standard pattern for cleanup without handling, such as unlocking, while try-with-resources is preferred for closing resources.

Detailed explanation

Java requires a try block to be followed by at least one catch or a finally. A try-finally is therefore perfectly legal, and it expresses a useful intent: "I don't know how to handle failures here, but whatever happens I must clean up".

Behaviour:

  • If the try block completes normally, finally runs and execution continues.
  • If it throws, finally runs and then the same exception continues propagating up the stack, because nothing caught it. The method's throws clause must still declare checked exceptions.
  • If it executes return, the return value is computed, finally runs, then the method returns.

The classic use is explicit locks:

lock.lock(); try { ... } finally { lock.unlock(); }

Note that lock() is called before the try. If it were inside and lock() itself failed (or was interrupted, for lockInterruptibly), finally would call unlock() on a lock the thread does not hold, throwing IllegalMonitorStateException and masking the original error.

Other uses: restoring thread-local or MDC state, resetting a flag, recording metrics or timing, decrementing a counter. All of these must happen even if the work fails, and the caller is the right place to decide what the failure means.

For closing things that implement AutoCloseable (streams, JDBC connections, HTTP responses, channels), try-with-resources is the modern replacement: it closes automatically in reverse order, handles null resources and attaches close failures as suppressed exceptions instead of losing the original. Try-with-resources itself can also have no catch blocks.

How it works

  1. Execute the try body.
  2. On normal completion, return or exception, jump to finally.
  3. Run finally.
  4. Resume the pending action: continue, return the saved value, or rethrow the saved exception.

Example

private final ReentrantLock lock = new ReentrantLock();

public void transfer(Account from, Account to, BigDecimal amt) {
    lock.lock();                       // outside try
    try {
        from.debit(amt);
        to.credit(amt);                // may throw; caller handles it
    } finally {
        lock.unlock();                 // always released
    }
}

public void handle(Request r) {
    MDC.put("requestId", r.id());
    try { process(r); }
    finally { MDC.remove("requestId"); }   // no leak to the next request on this thread
}

Common mistakes

  • Calling lock() inside the try block.
  • Using try-finally to close streams instead of try-with-resources.
  • Throwing or returning from finally, masking the original exception.
  • Forgetting checked exceptions still need declaring when there's no catch.

How to answer in the interview

"Yes. A try must be followed by at least one catch or a finally, so try with only finally is valid. If the body throws, finally runs first and then the exception propagates to the caller, since nothing caught it. That's the right pattern when cleanup must happen but this method shouldn't handle the error, for example lock.lock(), then try, work, finally unlock. I call lock before the try so we never unlock a lock we didn't get. For AutoCloseable resources like streams and JDBC connections, I use try-with-resources, which closes them automatically and keeps suppressed exceptions."

Likely follow-up questions

  • Why must lock.lock() be called before the try block and not inside it? If acquiring fails, finally would unlock a lock not held, throwing and masking the real error.
  • Does finally run if try returns? Yes, before the method returns.
  • Can try-with-resources omit catch? Yes.
