Some workloads must run only on GPU nodes, and other pods must stay off those expensive nodes. How do you control scheduling?

Kubernetes · scenario · levels mid, senior

In one line

Attract GPU workloads with nodeSelector or node affinity, repel everything else with taints, give GPU pods tolerations (which allow but do not force placement), combine both for dedicated nodes, and request nvidia.com/gpu so capacity is checked.

Detailed explanation

Two controls work in opposite directions. Attraction is set on the pod: a nodeSelector matches simple labels such as accelerator=nvidia-l4, while node affinity supports operators and two strengths. requiredDuringSchedulingIgnoredDuringExecution must be satisfied; preferredDuringSchedulingIgnoredDuringExecution is a weighted preference, useful for soft choices like a preferred zone or instance family.

Repulsion is set on the node: a taint such as nvidia.com/gpu=present:NoSchedule keeps away every pod without a matching toleration. NoSchedule blocks new pods, PreferNoSchedule is a soft version, and NoExecute also evicts running pods that do not tolerate it. Some platforms, such as GKE, add this GPU taint automatically, and the ExtendedResourceToleration admission plugin can add tolerations to pods that request GPUs.

The common misunderstanding: a toleration does not attract a pod. It only permits the pod onto a tainted node; the scheduler may still put it on a cheap general node. So dedicated nodes need both: a taint so only GPU workloads can land there, and affinity or a selector so GPU workloads land only there. The resource request nvidia.com/gpu: 1, advertised by the NVIDIA device plugin or GPU operator, makes the scheduler count GPUs, preventing two jobs being placed on one GPU.

For spreading replicas across nodes or zones use pod anti-affinity or topology spread constraints. On cloud clusters, a separate node pool or Karpenter NodePool per workload type, with its own labels and taints, keeps this manageable and lets GPU nodes scale to zero when idle.

How it works

  1. Label GPU nodes and taint them with NoSchedule.
  2. Install the NVIDIA device plugin or GPU operator.
  3. GPU pods add a toleration plus node affinity or selector.
  4. GPU pods request nvidia.com/gpu.
  5. Non-GPU pods, lacking the toleration, are kept off.
  6. Use topology spread for replicas; autoscale the GPU pool.

Example

kubectl label node gpu-1 accelerator=nvidia-l4
kubectl taint node gpu-1 nvidia.com/gpu=present:NoSchedule
spec:
  tolerations:
    - { key: nvidia.com/gpu, operator: Exists, effect: NoSchedule }
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - { key: accelerator, operator: In, values: ["nvidia-l4"] }
  containers:
    - name: trainer
      image: registry.example.com/trainer:2.3
      resources:
        limits: { nvidia.com/gpu: 1 }

Common mistakes

  • Using only a toleration and expecting pods to go to GPU nodes.
  • Using only affinity, so random pods still fill expensive GPU nodes.
  • Forgetting the GPU resource request, so jobs share or oversubscribe GPUs.
  • Using NoExecute without realising it evicts running pods.

How to answer in the interview

"There are two directions. To attract pods I label nodes and use a nodeSelector or node affinity, required for hard rules and preferred for soft ones. To keep others off I taint the GPU nodes, for example nvidia.com/gpu NoSchedule, which repels any pod without a toleration. The usual misunderstanding is that a toleration forces placement; it only allows it. So for dedicated nodes I combine a taint with affinity, and GPU pods request nvidia.com/gpu so the scheduler checks capacity. For spreading I use anti-affinity or topology spread, and a separate node pool or Karpenter NodePool makes it manageable."

Likely follow-up questions

  • NoSchedule, PreferNoSchedule and NoExecute? Hard block for new pods, soft avoidance, and block plus eviction of running pods.
  • How do you share one GPU between small workloads? Time-slicing or MIG via the NVIDIA GPU operator.
  • Why IgnoredDuringExecution? Label changes after scheduling do not evict already running pods.
