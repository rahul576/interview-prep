How do you run large-scale batch scoring efficiently?

MLOps · concept · levels mid, senior

In one line

Run batch scoring on a distributed engine (Spark with pandas UDFs, Ray Data, or managed batch endpoints), load the model once per worker, run vectorised or batched inference, partition input with checkpointing and idempotent outputs, use spot capacity off-peak, record model version and run ID on every row, and validate outputs before publishing.

Detailed explanation

Scoring tens of millions of records row by row, or by calling an online endpoint per record, is slow and expensive. Efficient batch scoring has a few rules.

Distributed processing. Spark with pandas UDFs (or mapInPandas) processes Arrow batches of rows; Ray Data streams batches to CPU or GPU actors; managed options include SageMaker Batch Transform, Azure ML batch endpoints, Vertex AI batch prediction and Databricks.

Load once per worker. Loading a 500 MB model for each record or each small task dominates runtime. Use iterator-style UDFs or long-lived actors so the model is loaded once per executor or actor and reused.

Vectorised inference. Score thousands of rows per call; on GPUs use batches sized to memory. This can be 10 to 100 times faster than per-row calls.

Partitioning and idempotency. Partition input by date or ID range so failed partitions are retried individually. Write outputs idempotently—overwrite a partition, or upsert by key—rather than append, so reruns don't duplicate. Checkpoint progress for long jobs.

Cost. Use spot or preemptible capacity (the partitioning makes retries cheap) and schedule off-peak.

Traceability and validation. Each output row records model name, version, run ID and scoring time. Before publishing, validate: row count matches input, null scores absent, score distribution close to the previous run. Then swap the published table or pointer atomically.

How it works

  1. Read input partitions from the lake or warehouse.
  2. Broadcast the model artefact path; load once per worker.
  3. Score in batches with vectorised operations.
  4. Write each partition with overwrite, adding version and run ID.
  5. Validate counts and distributions.
  6. Publish by swapping a view or table pointer; alert on failure.

Example

import pandas as pd, mlflow
from typing import Iterator

MODEL_URI = "models:/churn@champion"

def score(batches: Iterator[pd.DataFrame]) -> Iterator[pd.DataFrame]:
    model = mlflow.pyfunc.load_model(MODEL_URI)          # once per worker
    for df in batches:
        df["score"] = model.predict(df[FEATURES])
        df["model_version"] = "churn:23"
        yield df[["customer_id", "score", "model_version"]]

(spark.table("features.customers_daily").where("ds = '2026-11-20'")
      .mapInPandas(score, "customer_id string, score double, model_version string")
      .write.mode("overwrite").option("replaceWhere", "ds = '2026-11-20'")
      .saveAsTable("predictions.churn"))

Common mistakes

  • Calling an online endpoint per record for millions of rows.
  • Loading the model inside a per-row function.
  • Appending outputs so reruns create duplicates.
  • Publishing without validating counts and distributions.

How to answer in the interview

"For millions of records I use Spark with pandas UDFs, Ray Data or a managed batch endpoint. The model is loaded once per worker, not per record, and inference runs on batches with vectorised or GPU operations. Input is partitioned so failures retry per partition, and outputs overwrite partitions so reruns are idempotent. Jobs run off-peak on spot capacity. Each row carries the model version and run ID for traceability, and I validate row counts and score distributions before publishing."

Likely follow-up questions

  • How do you score a GPU-only model inside Spark? GPU executor pools with one model per GPU, or Ray Data actors on GPU nodes reading from the lake.
  • How do consumers read results safely? Through a view or table swapped only after validation.
  • How do you handle new entities between runs? Online fallback scoring or a default.
