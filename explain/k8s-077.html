Your cluster has 40 nodes, but monitoring shows average CPU usage of only 15 percent. Yet new pods cannot be scheduled. Explain and fix it.

Kubernetes · scenario · levels mid, senior

In one line

The scheduler uses requests, not actual usage: if teams request far more than they use, nodes look full while real CPU is 15 percent; compare requests with usage per workload, rightsize with VPA recommendations or Goldilocks, and also check memory requests and pods-per-node or IP limits.

Detailed explanation

For each node, the scheduler subtracts the sum of requests of pods already placed from the node's allocatable capacity. Usage is irrelevant to that calculation. So a pod requesting 2 CPU and using 0.1 still blocks 2 CPU. Multiply by hundreds of pods and a 40-node cluster can be "full" at 15 percent utilisation; new pods sit Pending with Insufficient cpu, and the cluster autoscaler adds expensive nodes.

Typical reasons for over-requesting: copy-pasted Helm defaults, requests set during a load test years ago, sidecars with generous defaults, fear of throttling (which actually comes from limits, not requests), or setting requests equal to peak rather than typical usage.

The analysis: compare kube_pod_container_resource_requests (from kube-state-metrics) with real usage (container_cpu_usage_seconds_total rate, container_memory_working_set_bytes) at p95 or p99 over a few weeks. Usually a small number of workloads hold most of the unused reservation, so start there.

Rightsizing: VPA in Off/recommendation mode or Goldilocks suggests values; teams apply them via their manifests, keeping headroom (for example p95 plus 20-30 percent for CPU, peak plus buffer for memory). With in-place pod resize now GA, VPA can apply changes with fewer restarts.

Also check the other constraints: memory requests are often the actual bottleneck even if CPU looks fine; maxPods per node (110 by default, lower on some managed CNIs) and IP addresses per node or subnet can block scheduling while CPU and memory are free; and DaemonSet overhead on every node.

How it works

  1. Check Pending reasons: Insufficient cpu, memory, or Too many pods.
  2. Compare requested vs used per namespace and workload.
  3. Prioritise the biggest gaps.
  4. Apply VPA or Goldilocks recommendations with headroom.
  5. Verify node count drops and SLOs stay healthy.
  6. Add policy: LimitRange defaults, reviews of large requests.

Example

# CPU requested minus used, by namespace (cores)
sum by (namespace) (kube_pod_container_resource_requests{resource="cpu"})
-
sum by (namespace) (rate(container_cpu_usage_seconds_total{container!=""}[30m]))
kubectl describe node ip-10-0-1-23 | sed -n '/Allocated resources/,/Events/p'
#  cpu     3800m (95%)   memory  12Gi (80%)   <- requested, not used

Common mistakes

  • Looking only at average usage dashboards.
  • Rightsizing CPU but ignoring memory.
  • Cutting requests to the average and causing contention at peak.
  • Forgetting pod count and IP limits.

How to answer in the interview

"The scheduler places pods by requests, not actual usage. If teams request far more than they use, nodes look full to the scheduler while utilisation is 15 percent, so pods stay Pending and the autoscaler adds nodes. I'd compare requests with real usage per workload in Prometheus or a cost tool; usually a few deployments reserve most of the capacity. Then I'd rightsize with VPA recommendations or Goldilocks, starting with the biggest gaps and keeping headroom. I'd also check memory requests, often the real constraint, and max pods per node or IP limits."

Likely follow-up questions

  • How to convince teams? Show their own data and cost, change in small steps with SLO monitoring and easy rollback.
  • Why not schedule by usage? Usage fluctuates; requests are the contract that guarantees resources.
  • What is allocatable? Capacity minus system and kubelet reservations.
