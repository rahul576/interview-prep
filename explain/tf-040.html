After terraform apply creates an IAM role, the next resource that uses it fails with an access denied or principal not found error. Why, and how do you fix it?

Terraform · scenario · levels mid, senior

In one line

AWS IAM and Microsoft Entra ID are eventually consistent, so a newly created role or service principal may not be visible to other services for seconds or minutes; rely on provider retries, re-run apply, add a time_sleep for persistent cases, and create identities in an earlier stage.

Detailed explanation

The create call for an IAM role or an Entra service principal returns success as soon as the identity service accepts it. Replication to other regions and to consuming services (Lambda, EKS, Azure Resource Manager role assignments, Key Vault) takes time. If Terraform immediately creates a Lambda function that assumes the role, or an azurerm_role_assignment for a just-created managed identity, the consumer may answer "The role defined for the function cannot be assumed" or "PrincipalNotFound". The identity is fine; it just has not propagated.

Providers know this. The AWS and AzureRM providers retry many of these specific errors for a period, which is why the problem is intermittent. A simple re-run of apply usually succeeds because the identity now exists everywhere. That is acceptable occasionally, but flaky pipelines erode trust, so for recurring cases you add a deliberate wait.

The time_sleep resource from the hashicorp/time provider sits between the identity and its consumer with a create_duration, for example 30 seconds. Because it only waits on create (or when its triggers change), it does not slow later runs. For Azure role assignments, setting principal_type = "ServicePrincipal" or skip_service_principal_aad_check = true avoids the lookup in Entra that fails for brand-new principals. The cleanest structural fix is to create long-lived identities in an earlier stage or state, so by the time workloads use them they have fully propagated.

How it works

  1. Terraform creates the identity; the API returns success.
  2. Terraform creates the consumer immediately because the dependency is satisfied.
  3. The consumer's service has not seen the identity yet and returns an error.
  4. The provider retries some errors; otherwise apply fails.
  5. A time_sleep or stage split gives propagation time before the consumer is created.

Example

resource "azurerm_user_assigned_identity" "app" {
  name                = "id-orders-api"
  resource_group_name = azurerm_resource_group.main.name
  location            = azurerm_resource_group.main.location
}

resource "time_sleep" "wait_for_identity" {
  depends_on      = [azurerm_user_assigned_identity.app]
  create_duration = "30s"
}

resource "azurerm_role_assignment" "kv_reader" {
  depends_on           = [time_sleep.wait_for_identity]
  scope                = azurerm_key_vault.kv.id
  role_definition_name = "Key Vault Secrets User"
  principal_id         = azurerm_user_assigned_identity.app.principal_id
  principal_type       = "ServicePrincipal"
}

Common mistakes

  • Adding sleeps everywhere instead of only where propagation actually bites.
  • Treating the error as a permissions bug and granting broader access.
  • Long sleeps that slow every create without solving the root cause.
  • Ignoring that role assignment propagation itself can take minutes before access works.

How to answer in the interview

"This is eventual consistency. IAM or Entra ID accepted the role, but it has not propagated to the service using it, so I get access denied or principal not found. Providers retry many of these errors and a re-run usually works. If it keeps happening, I add a time_sleep resource between the identity and its consumer, triggered on create, and on Azure I set principal_type on role assignments so the provider skips the directory lookup. Structurally, I prefer creating identities in an earlier stage so they are ready before workloads use them."

Likely follow-up questions

  • Why is a fixed sleep not perfect? Propagation time varies; it can still be too short, or waste time.
  • Does the sleep run on every apply? No, only on create or when its triggers change.
  • What else is eventually consistent? DNS, RBAC assignments, S3 bucket policies and some quota changes.
