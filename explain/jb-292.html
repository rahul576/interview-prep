What metrics would you monitor for a production Java application?

Observability · concept · levels mid, senior

In one line

Monitor RED metrics (rate, errors, duration percentiles) per endpoint, JVM health (heap after GC, GC pauses, threads, CPU, container memory), resource pools (DB connections, executors), dependencies and Kafka lag, and business metrics, collected with Micrometer into Prometheus and Grafana, with SLO-based alerts.

Detailed explanation

Metrics answer "is something wrong, and where?" cheaply and continuously. A useful set has layers:

Service level (RED): request rate, error rate (5xx and important 4xx separately) and duration as histograms, so you can compute p95 and p99. Averages hide the slow tail that users actually feel; one request in a hundred taking 5 s is invisible in a 120 ms average.

JVM: heap used after GC (a rising floor indicates a leak), GC pause time and frequency, allocation rate, live and daemon threads, Metaspace, CPU usage and, in Kubernetes, container memory (RSS) against the limit and CPU throttling, which explain OOMKills and latency spikes that heap graphs do not.

Saturation of pools: HikariCP active, idle and pending connections plus acquisition time; executor active threads and queue size; Tomcat busy threads; cache hit ratio. Pending connections are often the first sign of a slow database.

Dependencies: latency and errors of each downstream HTTP call, circuit breaker state (Resilience4j exports it), database query time and Kafka consumer lag per group and partition.

Business metrics: orders placed, payments failed, sign-ups. A drop in orders can reveal a broken flow before any technical metric moves.

Spring Boot Actuator plus Micrometer exports most of these automatically (http.server.requests, jvm., hikaricp., kafka.*); business metrics are custom counters and timers. Keep tag cardinality low (no user ids or raw URLs). Alerts follow SLOs: alert on error-budget burn and user-facing latency, keep causes on dashboards.

How it works

  1. Actuator exposes /actuator/prometheus with Micrometer metrics.
  2. Prometheus scrapes every pod; percentile histograms are enabled.
  3. Custom business counters and timers are added in code.
  4. Grafana dashboards group RED, JVM, pools and dependencies.
  5. SLOs and burn-rate alerts route to on-call with runbooks.

Example

# p99 latency per endpoint
histogram_quantile(0.99,
  sum by (le, uri) (rate(http_server_requests_seconds_bucket{app="orders"}[5m])))

# error ratio
sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
  / sum(rate(http_server_requests_seconds_count[5m]))

# threads waiting for DB connections
hikaricp_connections_pending{pool="HikariPool-1"} > 0
Timer.builder("payment.authorisation").tag("provider", "stripe")
     .publishPercentileHistogram().register(registry)
     .record(() -> gateway.authorise(request));

Common mistakes

  • Watching average latency instead of percentiles.
  • Monitoring heap but not container RSS and CPU throttling.
  • High-cardinality tags that overload Prometheus.
  • Alerting on every CPU spike, causing alert fatigue.

How to answer in the interview

"I start with RED per endpoint: rate, errors, and latency as p95 and p99 rather than averages. Then JVM health: heap after GC, GC pauses, threads, CPU and, in containers, memory against the limit and CPU throttling. Then pools: Hikari active and pending connections, executor queues. Then dependencies: downstream latency and errors, circuit breaker state and Kafka consumer lag. And business metrics like orders placed, which often show problems first. Spring Boot exposes them via Micrometer to Prometheus and Grafana, and I alert on SLO burn rate, not every spike."

Likely follow-up questions

  • Why are averages misleading? They hide the tail; a few very slow requests barely move the mean.
  • What does rising heap after GC mean? Live data is growing, a possible memory leak.
  • How do you track Kafka lag? Consumer group lag metrics from the client or an exporter such as Burrow or kafka-exporter.
