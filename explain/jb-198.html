What is REST architecture?

REST & API Design · concept · levels entry, mid

In one line

REST (Representational State Transfer, defined by Roy Fielding) is an architectural style where everything is a resource identified by a URI, manipulated through representations (usually JSON) using a uniform interface of HTTP methods and status codes, with stateless, cacheable, layered client-server communication and, in full form, HATEOAS.

Detailed explanation

REST is not a protocol or a standard but a set of constraints. An API that follows them gains scalability, simplicity and independent evolution of client and server.

The constraints:

  • Client-server: UI concerns are separated from data storage, so each side evolves independently.
  • Stateless: each request contains everything needed to process it, including authentication (for example a JWT bearer token). The server keeps no client session between requests, so any instance can handle any request, which makes horizontal scaling and failover easy.
  • Cacheable: responses state whether they can be cached (Cache-Control, ETag), reducing load and latency.
  • Uniform interface: resources identified by URIs (/orders/42); manipulation through representations (JSON, XML); self-descriptive messages using standard methods (GET, POST, PUT, PATCH, DELETE), status codes and media types; and hypermedia as the engine of application state (HATEOAS), where responses include links to related resources and allowed actions.
  • Layered system: clients cannot tell whether they talk to the server directly or via load balancers, gateways, caches or CDNs.
  • Code on demand (optional): servers can send executable code, like JavaScript.

In practice most "REST APIs" follow the first constraints but skip HATEOAS; Leonard Richardson's maturity model calls that level 2 (resources plus HTTP verbs), with HATEOAS as level 3. Spring HATEOAS can add links if needed.

REST fits CRUD-like resource APIs and public APIs well because it builds on HTTP semantics and infrastructure everyone already has. It is less suited to chatty internal calls needing high performance (gRPC) or clients that need flexible queries (GraphQL).

How it works

  1. Identify resources and give each a URI.
  2. Clients send HTTP requests with methods expressing intent.
  3. Server returns a representation and status code.
  4. Each request is self-contained; no server session.
  5. Caching headers and intermediaries optimise delivery.

Example

GET /api/orders/42
Authorization: Bearer eyJhbGciOi...
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: private, max-age=30
ETag: "v3"

{
  "id": 42,
  "status": "PAID",
  "total": 1499.00,
  "_links": {
    "self":   { "href": "/api/orders/42" },
    "cancel": { "href": "/api/orders/42/cancellation", "method": "POST" }
  }
}

Common mistakes

  • Calling any JSON-over-HTTP API RESTful (POST for everything with verbs in URLs).
  • Server-side sessions that break statelessness.
  • Ignoring status codes and caching.
  • Treating REST as a protocol rather than an architectural style.

How to answer in the interview

"REST, representational state transfer, is an architectural style for networked APIs, usually over HTTP. Everything is a resource identified by a URI, like /orders/42, and clients work with representations, usually JSON. It has a uniform interface: standard HTTP methods with defined meanings and standard status codes. Requests are stateless, so each one carries everything needed, including the token, which makes horizontal scaling easy. Responses declare whether they're cacheable, the system can be layered with gateways and proxies, and client and server evolve independently. Full REST also includes HATEOAS links, which few APIs implement; most are at Richardson level 2."

Likely follow-up questions

  • Is an API that only uses POST for everything RESTful? No, it ignores the uniform interface and method semantics.
  • What is the Richardson maturity model? Levels 0-3: single endpoint, resources, HTTP verbs, hypermedia.
  • Why does statelessness help scaling? Any instance can serve any request; no session affinity.
