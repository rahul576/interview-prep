A Helm upgrade failed and now every new upgrade says another operation is in progress. How do you recover?

Kubernetes · scenario · levels mid, senior

In one line

The previous operation was interrupted and left the release in pending-upgrade, pending-install or pending-rollback, so Helm refuses new operations; inspect with helm history, roll back to the last deployed revision, fix the root cause and use --rollback-on-failure (formerly --atomic) with --wait in pipelines.

Detailed explanation

Helm 3 and 4 store each release revision as a Secret in the release namespace (named like sh.helm.release.v1.<release>.v<revision>), labelled with a status. When an upgrade starts, Helm writes a new revision with status pending-upgrade; only when it finishes does it mark it deployed and the previous one superseded. If the CI job is cancelled, the runner dies or a timeout kills the process, nobody updates that status. The next helm upgrade sees a pending revision and fails with "another operation (install/upgrade/rollback) is in progress", which is a deliberate lock against two concurrent operations.

The clean recovery is helm rollback to the last revision whose status is deployed. A rollback creates a new revision with the old manifest and moves the stuck one out of the pending state. If the very first install got stuck (pending-install) there is nothing to roll back to, so helm uninstall and reinstall is usually simplest. Only if rollback itself fails should you edit or delete the stuck release Secret, after backing it up, because you are editing Helm's source of truth by hand.

Recovery is only half the job: find out why the upgrade hung. Typical causes are a pre-upgrade or post-upgrade hook Job that never completes, pods that never become ready (bad image, failing probes, missing config), PVC or quota problems, or a --timeout shorter than a realistic rollout.

How it works

  1. helm status <rel> and helm history <rel> show the pending revision and the last deployed one.
  2. Check what is actually running: kubectl get pods,jobs and events in the namespace.
  3. helm rollback <rel> <last-good-rev> --wait clears the lock with a new revision.
  4. If rollback fails, back up and fix or remove the stuck sh.helm.release.v1 Secret.
  5. Fix the root cause (hook, image, probe, timeout) and upgrade again.
  6. Make pipelines safe: --rollback-on-failure (or --atomic on Helm 3), --wait, realistic --timeout, and no parallel deploys of one release.

Example

helm history payments -n prod
# REVISION  STATUS           DESCRIPTION
# 41        deployed         Upgrade complete
# 42        pending-upgrade  Preparing upgrade

helm rollback payments 41 -n prod --wait --timeout 10m

# last resort only, after a backup
kubectl -n prod get secret -l owner=helm,name=payments,status=pending-upgrade
kubectl -n prod get secret sh.helm.release.v1.payments.v42 -o yaml > rev42-backup.yaml
kubectl -n prod delete secret sh.helm.release.v1.payments.v42

helm upgrade payments ./chart -n prod --rollback-on-failure --wait --timeout 10m

Common mistakes

  • Deleting release Secrets first instead of trying helm rollback.
  • Recovering the lock but never fixing the hook or probe that caused the hang.
  • Pipeline timeouts shorter than Helm's --timeout, so the runner is killed mid-operation.
  • Allowing two pipelines to deploy the same release concurrently.

How to answer in the interview

"That error means a previous operation was interrupted, usually a cancelled or timed-out pipeline, and Helm left the release in pending-upgrade. I'd run helm history to find the last deployed revision and roll back to it, which creates a new revision and clears the pending state. Only if that fails would I back up and fix the release Secret by hand. Then I'd find the root cause, often a hook job that never finishes or pods that never become ready. In CI I use rollback-on-failure, or atomic on Helm 3, with --wait, a realistic timeout and a lock so only one deploy runs per release."

Likely follow-up questions

  • Why is GitOps less prone to this? Argo CD or Flux reconcile continuously from Git and simply retry; there is no client process that can be killed halfway through holding a lock.
  • What if the stuck revision is the first install? Uninstall (keeping any PVCs you need) and install again.
  • How do hooks cause hangs? Helm waits for hook Jobs to complete; a failing or never-ending hook blocks the release until timeout.
