How do you run hyperparameter tuning efficiently at scale?

MLOps · concept · levels mid, senior

In one line

Prefer random search or Bayesian optimisation over grid search, add early stopping of poor trials (Hyperband, ASHA), run parallel trials with tools like Optuna, Ray Tune, Katib or managed tuning under budgets and resource limits, and track every trial in experiment tracking.

Detailed explanation

Grid search tries every combination; it scales exponentially with the number of hyperparameters and wastes trials on unimportant dimensions. Random search samples combinations and usually finds good regions faster, because only a few hyperparameters matter most. Bayesian optimisation (Gaussian processes, or TPE as in Optuna and Hyperopt) builds a model of which configurations perform well and proposes promising ones next.

The biggest saving usually comes from early stopping. Successive halving, Hyperband and ASHA (asynchronous successive halving) start many trials with small budgets (few epochs or a data subset), keep the best fraction, and give them more budget. Pruners in Optuna and schedulers in Ray Tune do this. Population Based Training goes further, mutating hyperparameters of promising trials during training.

At scale, trials run in parallel on a cluster: Ray Tune, Kubeflow Katib, Optuna with a shared database, or managed tuning in SageMaker, Azure ML (sweep jobs) and Vertex AI (Vizier). Set limits on concurrent trials, total trials, total GPU hours and per-trial timeouts; use spot capacity because trials are naturally restartable. Note that too much parallelism weakens Bayesian methods, which learn from completed trials.

Every trial is logged to experiment tracking with parameters and curves. And use domain knowledge to define a sensible search space (log scales for learning rates, realistic ranges) instead of searching blindly.

How it works

  1. Define the objective metric on a validation set and the search space.
  2. Pick a sampler (TPE or random) and a pruner (ASHA/Hyperband).
  3. Set budgets: max trials, concurrency, GPU hours.
  4. Run trials in parallel, reporting intermediate metrics.
  5. Prune poor trials early; log all to tracking.
  6. Retrain the best configuration and evaluate once on the test set.

Example

import optuna

def objective(trial):
    lr = trial.suggest_float("lr", 1e-5, 1e-2, log=True)
    depth = trial.suggest_int("depth", 3, 10)
    for epoch in range(20):
        score = train_one_epoch(lr, depth, epoch)
        trial.report(score, epoch)
        if trial.should_prune():
            raise optuna.TrialPruned()
    return score

study = optuna.create_study(direction="maximize",
          sampler=optuna.samplers.TPESampler(),
          pruner=optuna.pruners.HyperbandPruner(),
          storage="postgresql://optuna@db/optuna", study_name="churn-v9", load_if_exists=True)
study.optimize(objective, n_trials=200, timeout=4 * 3600)

Common mistakes

  • Grid search over many dimensions.
  • No early stopping, so bad trials run to completion.
  • Selecting on the test set, overfitting the evaluation.
  • Unbounded parallelism and GPU spend.

How to answer in the interview

"I avoid grid search; random search or Bayesian optimisation with TPE in Optuna finds good configurations faster. The biggest saving is early stopping with Hyperband or ASHA, which kills poor trials after a few epochs. At scale I run trials in parallel with Ray Tune, Katib or managed tuning, with limits on concurrency, total trials and GPU hours, often on spot instances. Every trial goes to experiment tracking, the search space comes from domain knowledge, and the final choice is checked once on a held-out test set."

Likely follow-up questions

  • How do you avoid overfitting the validation set? Cross-validation, a separate untouched test set and limiting search breadth.
  • Why can high parallelism hurt Bayesian search? It proposes many trials before learning from results.
  • What is Population Based Training? Evolving hyperparameters during training by copying and perturbing good trials.
