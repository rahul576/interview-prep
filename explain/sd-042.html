Design a top-K trending topics system, such as trending hashtags in the last hour.

Classic Design Problems · design · levels entry, mid, senior

In one line

Stream hashtag events through Kafka, count them in time windows per partition (exact or Count-Min Sketch), keep a min-heap of top K per partition, merge into a global top K, score by growth vs baseline, and cache the precomputed result.

Detailed explanation

"Trending" is about what's spiking now, not what's always popular. Volume alone would show #love forever, so scoring compares the current window with a baseline (e.g. same hour last week, or a moving average).

Counting: partition the stream by hashtag so each processor owns a subset and counts exactly in memory for the window, using tumbling 1-minute windows combined into a sliding 1-hour total. With extreme cardinality, a Count-Min Sketch gives approximate counts in fixed memory (it may overestimate, never underestimates). Each partition maintains a min-heap of size K of its top candidates; an aggregator merges partition heaps into the global top K. Because each hashtag lives in one partition, merging is exact for candidates.

Results are recomputed every minute per region/language and stored in a cache; reads (very frequent) are just lookups. Spam defence: count unique users rather than posts, weight by account reputation, ignore coordinated bursts.

How it works

  1. Post service → HashtagUsed(tag, user, region, ts) → Kafka (key = tag).
  2. Stream job: windowed counts per tag; compute trend score.
  3. Per-partition top-K heap → aggregator → global top K per region.
  4. Store in Redis; API returns cached list.

Example

import heapq
heap = []                      # (score, tag), size K
for tag, score in scores.items():
    if len(heap) < K: heapq.heappush(heap, (score, tag))
    elif score > heap[0][0]: heapq.heapreplace(heap, (score, tag))

Common mistakes

  • Ranking by raw volume only.
  • Global single counter (bottleneck).
  • Computing trends on read.
  • Counting posts instead of distinct users (easy to spam).

How to answer in the interview

"Hashtag events go into Kafka keyed by tag. Stream processors keep windowed counts per tag, exact or with Count-Min Sketch at huge cardinality, and compute a trend score versus a baseline. Each partition keeps a top-K heap and an aggregator merges them into a global list per region every minute, which is cached so reads are trivial. Counting distinct users and reputation weighting limits spam."

Likely follow-up questions

  • Why Count-Min Sketch? Fixed memory for high-cardinality frequency estimates.
  • Personalised trends? Combine global trends with the user's graph and interests.
  • Exact daily ranking? Batch job on archived events.
