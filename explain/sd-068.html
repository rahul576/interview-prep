You must add a column and change a heavily used table without downtime. How do you plan a zero-downtime schema migration?

Scalability & Reliability · scenario · levels mid, senior

In one line

Use expand and contract: make only backward-compatible changes first, deploy code that dual-writes, backfill in batches, switch reads (behind a flag), verify, and only then remove the old structure, using online schema-change tools to avoid long locks.

Detailed explanation

During a rolling deploy, old and new code run side by side against the same database, and a rollback brings old code back. So every schema state must work with both versions.

Dangerous operations on big tables: adding a column with a volatile default (older MySQL/Postgres rewrite the table), adding NOT NULL constraints, changing types, renaming, creating indexes without CONCURRENTLY, dropping columns still read by running code.

Expand: add new column/table (nullable); create indexes concurrently; use gh-ost / pt-online-schema-change for MySQL (copy to shadow table + replay changes + atomic swap). Migrate: deploy code writing both old and new; backfill existing rows in small batches (e.g. 5,000 rows, sleep, watch replication lag). Switch: read from new column behind a feature flag; compare results. Contract: stop writing old; later release drops it.

How it works

  1. Release N: add full_name (nullable).
  2. Release N+1: write first/last and full_name; backfill job.
  3. Release N+2: read full_name (flag), verify.
  4. Release N+3: stop writing old columns.
  5. Release N+4: drop old columns.

Example

ALTER TABLE customers ADD COLUMN full_name text;              -- instant in PG 11+
CREATE INDEX CONCURRENTLY idx_customers_full_name ON customers(full_name);
UPDATE customers SET full_name = first_name || ' ' || last_name
WHERE id BETWEEN $1 AND $2 AND full_name IS NULL;               -- batched

Common mistakes

  • Rename in one step (breaks running old code).
  • Huge single-transaction backfills (locks, replication lag, WAL explosion).
  • Dropping columns in the same release that stops using them.
  • Migrations that auto-run on app start in every pod.

How to answer in the interview

"I'd follow expand and contract. First a backward-compatible change, like adding the new column as nullable, using online tools so the table isn't locked. Then code that writes both old and new, plus a throttled batch backfill. Then switch reads behind a feature flag and verify. Only in a later release, once no running version uses it, drop the old column. Every step is reversible."

Likely follow-up questions

  • Rename a column used by five services? Add new, dual-write, migrate consumers one by one, then drop.
  • Add NOT NULL? Add as NOT VALID check constraint, validate later, then set.
  • Who runs migrations? A dedicated job/pipeline step, not every pod.
