How do you know right now which model version is serving production traffic?

MLOps · concept · levels mid, senior

In one line

Have one source of truth—a registry alias or a GitOps deployment manifest—that deployment writes and serving reads; the endpoint reports its loaded version and artefact hash at runtime, prediction logs include the version, and a check alerts when runtime and expected versions differ.

Detailed explanation

"Which model is in production?" sounds trivial but is often answered with "let me ask the data scientist". That is a red flag, because rollbacks, audits and incident response all depend on the answer.

The intended state lives in one place: a production alias in the model registry (for example champion in MLflow) or a deployment manifest in a Git repository that pins model version and image, applied by Argo CD or Flux. The deployment pipeline is the only thing that changes it.

The actual state is reported by the serving system: a metadata or version endpoint returning model name, version and artefact hash; metrics labels with the model version, so dashboards show traffic per version; and the version field in every prediction log. KServe and Triton expose model metadata via the inference protocol; custom services should add it.

A reconciliation check compares actual with intended and alerts on mismatch. It catches pods that failed to reload, a stale replica after a partial rollout, a manual hotfix or a cached old artefact. During a canary, several versions serve deliberately; the manifest then lists both with traffic weights, and dashboards split metrics per version.

How it works

  1. CD sets the registry alias or updates the GitOps manifest.
  2. Serving loads the artefact, verifies its hash and exposes version metadata.
  3. Each prediction and metric carries the model version label.
  4. A scheduled check compares runtime versions across all replicas with intended state.
  5. Mismatch raises an alert to the on-call owner.

Example

curl -s https://models.internal/v2/models/fraud-model | jq '{name, versions}'
# {"name":"fraud-model","versions":["14"]}

# Prometheus: traffic share per serving version
sum by (model_version) (rate(predictions_total{model="fraud-model"}[5m]))

Common mistakes

  • Tracking production versions on a wiki page or spreadsheet.
  • Version known only at deploy time, not reported at runtime.
  • Prediction logs without a version field.
  • Manual changes on the cluster outside the GitOps flow.

How to answer in the interview

"There should be one source of truth that deployment writes and serving reads, like a production alias in the registry or a pinned version in a GitOps manifest. On top of that the endpoint itself reports the loaded model version and artefact hash through a metadata endpoint and metric labels, and every prediction log carries the version. A check compares runtime with expected and alerts on mismatch, which catches a pod that didn't reload or a manual hotfix. If the honest answer is 'we check a wiki', that's the first thing I'd fix."

Likely follow-up questions

  • How do you handle several versions during a canary? The manifest lists both with weights; metrics and logs are split by version label.
  • Why an artefact hash as well as a version? It proves the exact bytes loaded, catching re-uploaded or corrupted artefacts.
  • Who may change the alias? Only the CD pipeline or named approvers, with audit.
