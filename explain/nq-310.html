What is Azure Kubernetes Service (AKS)?

Kubernetes · concept · levels mid

In one line

Azure Kubernetes Service (AKS) is Azure's managed Kubernetes: Azure runs the control plane, you manage node pools on VM Scale Sets, and it integrates with Entra ID, ACR, Azure CNI, Azure Monitor, Key Vault and workload identity; it is the Azure equivalent of EKS and GKE.

Detailed explanation

In AKS, Microsoft operates the control plane (API server, etcd, scheduler, controller manager), patches it and keeps it available. Pricing tiers differ: the Free tier has no financial SLA, the Standard tier adds an uptime SLA and higher scale limits, and Premium adds long-term support for Kubernetes versions. You pay mainly for the worker nodes.

Workers are organised into node pools, each backed by a Virtual Machine Scale Set. A system pool runs critical add-ons such as CoreDNS; user pools run applications and can use different VM sizes, GPU SKUs, spot instances, availability zones or Windows nodes. The cluster autoscaler scales pools, and node auto-provisioning (based on Karpenter) can pick VM sizes automatically. AKS Automatic is a more opinionated mode that manages nodes and defaults for you.

Integrations are where AKS adds value:

  • Microsoft Entra ID for cluster sign-in, with Kubernetes RBAC or Azure RBAC for authorisation.
  • Azure Container Registry attached for image pulls without secrets.
  • Networking: Azure CNI (including Azure CNI Overlay and Cilium-powered dataplane) or kubenet, private clusters, network policies; ingress through Application Gateway for Containers, the managed NGINX app routing add-on, or other controllers.
  • Azure Monitor Container Insights and managed Prometheus and Grafana for observability.
  • Key Vault Secrets Store CSI driver to mount secrets.
  • Microsoft Entra Workload ID so pods get federated tokens and access Azure resources without stored secrets.
  • Managed upgrades, auto-upgrade channels, planned maintenance windows and node image auto-patching.

How it works

  1. Create the cluster with Terraform, Bicep or az aks create.
  2. Azure provisions the control plane and a system node pool.
  3. Add user pools; attach ACR; enable OIDC issuer and workload identity.
  4. Deploy apps via Helm or GitOps (Flux extension or Argo CD).
  5. Autoscaler and upgrade channels keep it sized and patched.

Example

az aks create -g rg-prod -n aks-prod --tier standard \
  --network-plugin azure --network-plugin-mode overlay \
  --enable-oidc-issuer --enable-workload-identity \
  --enable-addons azure-keyvault-secrets-provider,monitoring \
  --attach-acr myregistry --zones 1 2 3 \
  --node-count 3 --enable-cluster-autoscaler --min-count 3 --max-count 10
az aks nodepool add -g rg-prod --cluster-name aks-prod -n apps \
  --node-vm-size Standard_D8s_v5 --enable-cluster-autoscaler --min-count 2 --max-count 20

Common mistakes

  • Running application workloads on the system pool.
  • Using the free tier for production without an SLA.
  • Storing Azure credentials in Kubernetes Secrets instead of workload identity.
  • Skipping upgrades until the version falls out of support.

How to answer in the interview

"AKS is Azure's managed Kubernetes. Azure runs the control plane, with an SLA on the Standard tier, and I manage node pools, which are VM scale sets, choosing sizes, system versus user pools and autoscaling. Its strength is integration: Entra ID for authentication and RBAC, ACR for images, Azure CNI networking in our VNets, Application Gateway or NGINX ingress, Container Insights, Key Vault through the Secrets Store CSI driver, and workload identity so pods reach Azure resources without secrets. It is the Azure counterpart to EKS and GKE."

Likely follow-up questions

  • Pod access to Key Vault securely? Workload identity with a federated credential plus the CSI driver or SDK.
  • How do upgrades work? Control plane first, then node pools with surge nodes, cordon and drain.
  • Private cluster? API server on a private endpoint, reached via VNet, VPN or a jump host.
