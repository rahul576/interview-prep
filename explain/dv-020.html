What is a pull request, and what makes a good code review?

Git · concept · levels entry

In one line

A pull request (GitLab: merge request) proposes merging a branch into another, with a diff, discussion and automated CI checks; a good review is about small focused changes, a clear description and constructive, specific feedback on correctness, readability, tests and security, enforced by branch protection.

Detailed explanation

A pull request is the team's quality gate and knowledge-sharing tool. Reviewers comment on specific lines and suggest edits, and CI runs builds, tests, linters and secret scanning as status checks. Branch protection (or rulesets) on main requires passing checks, approvals, sometimes CODEOWNERS approval, before merging.

A good pull request is small and focused on one logical change, because reviewers catch far more in 200 lines than in 2,000. It has a clear description: what, why, how it was tested, and any risk. The author reviews their own diff first.

A good review checks correctness and edge cases, design, readability, tests that cover the behaviour, and security (validation, secrets, permissions). Formatters and linters handle style so humans focus on substance. Comments are specific, kind and about the code, separating blocking issues from optional "nit:" suggestions. Reviews should be timely; a pull request waiting two days slows the whole team.

How it works

  1. Author pushes a branch and opens a pull request with a description.
  2. CI runs checks and reports status.
  3. Reviewers are assigned (often by CODEOWNERS) and comment or suggest changes.
  4. Author responds and pushes fixes; checks re-run.
  5. Required approvals and checks pass.
  6. Merge (merge commit, squash or rebase), then delete the branch.

Example

## What
Add retry with exponential backoff to the payment client.

## Why
Payment provider returns occasional 503s; ~0.4% of checkouts fail today.

## How tested
- Unit tests for backoff timing and max retries
- Ran against provider sandbox with injected 503s

## Risk
Retries only on idempotent calls; uses idempotency key header.

Sample review comment: "If charge() times out after the provider processed it, will this retry charge twice? Could we pass the idempotency key here as well?"

Common mistakes

  • Giant pull requests that nobody can review properly.
  • Rubber-stamp approvals without reading.
  • Nitpicking style a formatter should handle.
  • Harsh or personal comments.
  • Letting pull requests sit for days.

How to answer in the interview

"A pull request asks to merge a branch into main. It shows the diff, lets teammates discuss it, and triggers CI checks. A good one is small, does one thing and explains what, why and how it was tested. As a reviewer I check correctness, edge cases, readability, real test coverage and security issues like secrets. My comments are specific and constructive, with minor ones marked optional. Branch protection requires passing checks and an approval before merging."

Likely follow-up questions

  • How small should a pull request be? Ideally a few hundred lines or less, reviewable in under an hour.
  • Squash or merge commit? Squash gives a clean one-commit-per-change history; merge commits keep full branch history.
  • How do you handle disagreement in a review? Discuss with reasons and data, follow team guidelines, and talk synchronously if comments go back and forth.
