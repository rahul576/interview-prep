What is multi-LoRA serving, and when is it useful?

LLMOps & RAG · concept · levels senior, lead

In one line

Multi-LoRA serving keeps one base model in GPU memory and applies many small LoRA adapters per request, even mixed in the same batch, so dozens or hundreds of per-customer or per-task fine-tunes run on shared GPUs; supported by vLLM, SGLang, TGI, LoRAX and managed platforms.

Detailed explanation

LoRA (Low-Rank Adaptation) fine-tunes a model by freezing the original weights and learning small low-rank matrices A and B for selected layers, so the effective weight becomes W + BA. With rank 8 to 64, an adapter is typically megabytes to a few hundred megabytes, compared with tens or hundreds of gigabytes for the base model.

Deploying each fine-tune as a separate full model would mean one GPU set per variant, mostly idle. Multi-LoRA serving loads the base model once and keeps a pool of adapters in GPU memory, with more in CPU memory or disk. Each request names its adapter (often via the model field of an OpenAI-compatible API). Specialised kernels, such as Punica / S-LoRA style batched LoRA kernels, apply the correct adapter to each sequence within the same batch, so continuous batching still works across tenants. Adapters are loaded on demand and evicted LRU when GPU slots are full.

Use cases: per-customer fine-tunes in a SaaS product, per-language or per-domain variants, per-task adapters (classification, extraction, tone), and A/B testing of fine-tune versions.

Trade-offs: some throughput overhead versus the plain base model, especially with many distinct adapters in one batch or high ranks; a limit on concurrently active adapters per GPU (max_loras) and maximum rank; adapter cold-load latency on first use; and all adapters must match the exact base model version. Merging an adapter into the weights is faster for a single high-traffic variant, so very popular adapters may get dedicated merged deployments.

Operationally you need an adapter registry with versions, evaluation results and the base model they were trained on, plus gradual rollout and per-adapter metrics.

How it works

  1. Train LoRA adapters against a fixed base model version.
  2. Store them in a registry or object storage.
  3. Serving engine loads base model; adapters load on request.
  4. Batches mix requests for different adapters; kernels apply each one.
  5. Hot adapters stay in GPU memory; cold ones are evicted.

Example

vllm serve meta-llama/Llama-3.1-8B-Instruct --enable-lora \
  --max-loras 16 --max-lora-rank 64 --max-cpu-loras 128 \
  --lora-modules acme-support=/adapters/acme/v3 globex-legal=/adapters/globex/v1
curl localhost:8000/v1/chat/completions -H "Content-Type: application/json" \
  -d '{"model":"acme-support","messages":[{"role":"user","content":"Reset my router"}]}'

Common mistakes

  • Training adapters on a different base version than the one served.
  • Expecting zero overhead with hundreds of active adapters.
  • No per-adapter evaluation or rollback.
  • Using LoRA where prompt engineering or RAG would suffice.

How to answer in the interview

"LoRA fine-tuning trains small low-rank adapter matrices instead of changing all weights, so each variant is megabytes to a few hundred megabytes while the base model is many gigabytes. Multi-LoRA serving keeps one copy of the base model on the GPU and loads many adapters next to it; each request names its adapter and the engine applies the right one per sequence, even within one batch, swapping adapters between GPU and CPU memory. That makes it practical to serve one fine-tune per customer, language or task on shared GPUs. vLLM, SGLang and managed platforms support it, with some overhead per adapter."

Likely follow-up questions

  • Versioning hundreds of adapters? Registry with base-model version, eval scores, staged rollout and aliases.
  • When merge instead? For one high-traffic variant where latency matters most.
  • Limits? Max active adapters, max rank, and cold-load latency.
