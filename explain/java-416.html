What is the bulkhead pattern, and how does it differ from a circuit breaker?

Microservices · concept · levels mid, senior

In one line

A bulkhead isolates resources per dependency, with its own limited thread pool or semaphore, so one slow dependency can exhaust only its own compartment; a circuit breaker instead detects failure and stops calling the dependency for a while; they are complementary.

Detailed explanation

The name comes from ships: watertight compartments mean a hull breach floods one section, not the whole ship. In a service, the shared resource is usually the request thread pool (Tomcat's 200 threads by default) or a connection pool. Suppose your service calls a fast inventory API and a slow third-party tax API. If the tax API starts taking 30 seconds, every request that calls it holds a thread; soon all 200 threads wait on tax, and even requests that never touch tax get no thread. One dependency has taken the whole service down.

A bulkhead caps how many concurrent calls each dependency may use. A semaphore bulkhead limits concurrent calls on the caller's thread (cheap, good for most cases, including virtual threads); a thread-pool bulkhead runs calls on a dedicated, bounded pool with a queue (stronger isolation, plus asynchronous timeouts). When the compartment is full, extra calls are rejected immediately (BulkheadFullException) and can use a fallback, while the rest of the service keeps working. Bulkheads also apply at higher levels: separate connection pools per downstream, separate consumer groups, separate deployments for critical and non-critical traffic.

A circuit breaker answers a different question. It does not cap concurrency; it watches outcomes and, when the failure or slow-call rate crosses a threshold, opens and fails fast for a period before testing recovery. A breaker reacts after failures accumulate; a bulkhead limits blast radius from the first second. Together with a timeout (TimeLimiter), they form the core of resilience; Resilience4j provides all of them. Spring Framework 7 also added a basic @ConcurrencyLimit annotation for simple concurrency throttling.

How it works

  1. Assign each dependency a max concurrency (e.g. 20).
  2. Each call acquires a permit; release it on completion.
  3. If none is free within maxWaitDuration, reject and fall back.
  4. Timeouts ensure permits are released.
  5. The circuit breaker opens if failures persist, so calls fail even faster.

Example

resilience4j:
  bulkhead:
    instances:
      taxApi:
        maxConcurrentCalls: 20
        maxWaitDuration: 10ms
  thread-pool-bulkhead:
    instances:
      reportApi:
        coreThreadPoolSize: 4
        maxThreadPoolSize: 8
        queueCapacity: 20
@Bulkhead(name = "taxApi", fallbackMethod = "estimatedTax")
@CircuitBreaker(name = "taxApi")
public Tax tax(Order o) { return taxClient.calculate(o); }

Tax estimatedTax(Order o, Throwable t) { return Tax.estimate(o); }

Sizing: by Little's law, concurrency ≈ throughput × latency. At 50 requests/s and 200 ms normal latency you need about 10 permits; 20 gives headroom.

Common mistakes

  • Using one shared pool for all downstream calls.
  • Bulkheads without timeouts, so permits stay held.
  • Sizing by guesswork instead of throughput × latency.
  • Thinking a circuit breaker alone prevents thread exhaustion.

How to answer in the interview

"A bulkhead isolates resources per dependency, like a separate limited thread pool or a semaphore, so if one downstream becomes slow it can only use up its own compartment instead of every request thread, which stops a cascading failure. A circuit breaker is different: it watches failure and slow-call rates and, when they cross a threshold, stops calling the dependency for a while and fails fast. The bulkhead limits blast radius immediately, the breaker reacts to sustained failure. Resilience4j provides both plus time limiters, and I combine them, sizing bulkheads from expected throughput times latency."

Likely follow-up questions

  • How would you size a bulkhead for a slow third-party API? Throughput × p99 latency plus headroom, then load-test.
  • Semaphore or thread-pool bulkhead? Semaphore for most sync code and virtual threads; thread pool when you need async timeouts and stronger isolation.
  • Do virtual threads remove the need for bulkheads? No; they remove thread scarcity but not downstream overload or connection-pool exhaustion.
