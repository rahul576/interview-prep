What is structured logging, and why is it useful?

Observability · concept · levels mid, senior

In one line

Structured logging writes each log event as machine-readable data, typically one JSON object per line with consistent named fields (timestamp, level, service, trace id, business keys), so logs can be searched, filtered and aggregated reliably instead of parsed with fragile regexes.

Detailed explanation

A traditional log line is a sentence: 2026-01-10 10:00:01 INFO Payment of 40.00 for order 42 failed after 3 retries. Humans can read it, but tools must parse it with patterns that break whenever a developer rewords the message. Across fifty services with different formats, finding "all failed payments for customer 7 in the last hour" becomes guesswork.

A structured log line carries the same information as fields: {"@timestamp":"2026-01-10T10:00:01Z","log.level":"INFO","service.name":"payments","trace.id":"4bf9...","message":"Payment failed","orderId":"42","customerId":"7","retries":3}

Benefits:

  • Search and filter by any field in Kibana, OpenSearch, Grafana Loki or a vendor: orderId:42, level:ERROR AND service:payments.
  • Aggregate: count failures per endpoint or tenant, chart them, alert on them.
  • Correlate: the trace id links log lines to distributed traces and across services.
  • Consistency: standard schemas such as Elastic Common Schema (ECS) or OpenTelemetry semantic conventions make every service's logs look the same.

In Java: contextual fields come from the MDC (set in a servlet filter or interceptor; Micrometer Tracing adds trace and span ids automatically) or from SLF4J 2 key-value pairs (log.atInfo().addKeyValue(...)). Output is JSON via the Logstash Logback encoder or, since Spring Boot 3.4, built-in structured logging with logging.structured.format.console=ecs|logstash|gelf. In containers, write to stdout and let Fluent Bit or the OTel Collector ship logs.

Caveats: JSON is larger, so manage volume and cost (levels, sampling, retention); never include passwords, tokens or unnecessary personal data; local developers may prefer plain text, which profiles can enable.

How it works

  1. A filter puts trace id, user or tenant into the MDC.
  2. Code logs messages with key-value context.
  3. The encoder serialises event, MDC and key-values to one JSON line.
  4. A shipper forwards stdout to the log store, which indexes fields.
  5. Queries, dashboards and alerts work on fields.

Example

@Component
class TenantMdcFilter extends OncePerRequestFilter {
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res,
                                    FilterChain chain) throws IOException, ServletException {
        MDC.put("tenantId", req.getHeader("X-Tenant-Id"));
        try { chain.doFilter(req, res); } finally { MDC.remove("tenantId"); }
    }
}

Common mistakes

  • Putting all data in the message string, losing the benefit of fields.
  • Inconsistent field names (order_id, orderID, orderId) across services.
  • Not clearing the MDC, leaking values into other requests on pooled threads.
  • Logging secrets or whole request bodies.

How to answer in the interview

"Structured logging means writing each log entry as data, usually one JSON object per line with named fields, instead of free text. Every line has consistent fields such as timestamp, level, service, trace id and business keys like orderId, so in ELK or Loki I can filter all errors for one customer or count failures per endpoint without regex parsing, and jump from a log line to its trace. In Java I add context through the MDC and SLF4J key-values and output JSON with the Logstash encoder or Spring Boot 3.4's built-in ECS format. I keep field names consistent across services and never log secrets or personal data."

Likely follow-up questions

  • How do you control log volume and cost? Appropriate levels, sampling of noisy events, shorter retention for debug data, dropping fields at the shipper.
  • What is ECS? Elastic Common Schema, a standard set of field names for logs.
  • Why clear the MDC? Threads are pooled, so stale values would appear on unrelated requests.
