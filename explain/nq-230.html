What is the Outbox pattern?

Microservices · concept · levels mid, senior

In one line

The Outbox pattern writes the business change and an outbox event row in the same local database transaction, and a separate relay publishes those rows to the broker, solving the dual-write problem with at-least-once delivery.

Detailed explanation

A service often needs to update its database and notify others, for example save an order and publish OrderCreated to Kafka. The database and Kafka cannot share one transaction (XA/2PC is slow and rarely supported well), so doing both is a dual write: if the commit succeeds and the publish fails, or the pod dies in between, the systems disagree. Publishing first is no better, because the transaction may roll back after the event is out.

The outbox pattern turns the two writes into one. The service inserts the order and an outbox row (event id, aggregate type, aggregate id, event type, JSON payload, created timestamp) in one ACID transaction. Either both are committed or neither.

A message relay then moves outbox rows to the broker. Two common designs:

  • Polling publisher: a scheduled job selects unsent rows (with FOR UPDATE SKIP LOCKED so several instances can share work), publishes them and marks them sent.
  • Change data capture: Debezium reads the database's transaction log (PostgreSQL WAL, MySQL binlog) and publishes new outbox rows; its outbox event router can route by aggregate type and use the aggregate id as the key. No polling load on the table.

Because the relay can crash after publishing but before marking a row as sent, the same event may be published twice. Delivery is therefore at least once, and consumers must be idempotent, typically deduplicating by event id.

How it works

  1. Begin transaction.
  2. Insert/update business rows.
  3. Insert outbox row with a unique event id.
  4. Commit.
  5. Relay (polling or CDC) reads the row and publishes it, keyed by aggregate id.
  6. Relay marks it as published or deletes it; consumers dedupe by event id.

Example

@Transactional
public Order placeOrder(CreateOrder cmd) {
    Order order = orders.save(Order.from(cmd));
    outbox.save(new OutboxEvent(UUID.randomUUID(), "Order",
        order.getId().toString(), "OrderCreated", json(order)));
    return order;   // both rows commit together
}
SELECT * FROM outbox WHERE published_at IS NULL
ORDER BY id LIMIT 100 FOR UPDATE SKIP LOCKED;

Common mistakes

  • Calling kafkaTemplate.send() inside the @Transactional method and thinking that is atomic.
  • Letting the outbox table grow forever.
  • Consumers that are not idempotent.
  • Using a random key, which loses per-aggregate ordering.

How to answer in the interview

"The outbox pattern solves the dual-write problem. Instead of saving an order and then sending a Kafka message, which can't be done atomically, I insert the order and an outbox event row in the same local transaction, so both commit or neither does. A separate relay, either a polling job using SKIP LOCKED or Debezium reading the database log, publishes the outbox rows to Kafka and marks them as sent. Since the relay might publish a row twice after a crash, delivery is at least once and consumers must be idempotent, usually by tracking processed event ids."

Likely follow-up questions

  • How do you keep the outbox table from growing forever? Delete or archive published rows on a schedule, or with Debezium delete rows right after insert since CDC reads the log.
  • Polling or CDC? Polling is simpler; CDC gives lower latency and no table polling but needs Kafka Connect operations.
  • How is ordering preserved? Publish in insert order and use the aggregate id as the message key.
