Explain composition versus inheritance. Which one should generally be preferred?

Core Java & OOP · concept · levels mid, senior

In one line

Inheritance models an is-a relationship and reuses code by extending a parent, at the cost of tight coupling; composition models has-a, holding collaborators as fields and delegating to them; prefer composition, keeping inheritance for genuine, stable subtypes.

Detailed explanation

Inheritance lets SavingsAccount extends Account reuse fields and methods and be used wherever an Account is expected. It is simple and gives polymorphism for free. The problems appear at scale:

  • Tight coupling: the subclass depends on the parent's implementation details, not just its interface.
  • Fragile base class: a harmless-looking change in the parent (say addAll starting to call add) breaks subclasses that overrode one of them. Effective Java's InstrumentedHashSet example double-counts exactly this way.
  • Rigid hierarchies: it is fixed at compile time, Java allows only one superclass, and combinations explode (LoggingCachingRetryingClient).
  • Inherited baggage: subclasses get every public method, including ones that violate their invariants (Stack extends Vector exposes insertElementAt).

Composition means a class holds references to other objects, typically typed as interfaces, and forwards work to them. A NotificationService has a MessageSender; a CachingRepository wraps a Repository. Benefits: behaviour can be swapped or injected at runtime, each piece is small and testable with mocks, features combine freely (decorators), and only the methods you choose are exposed. The cost is some forwarding boilerplate.

The guideline from the Gang of Four and Effective Java: favour composition over inheritance. Use inheritance when the subclass really is a subtype that honours the Liskov substitution principle, the base class is designed and documented for extension (otherwise make it final), and it is stable, for example a framework's template-method base class or sealed hierarchies modelling a closed set of types.

How it works

  1. Define a small interface for the behaviour you need.
  2. Implement it in focused classes.
  3. Hold the interface as a field in the client class, injected through the constructor.
  4. Delegate calls to it, adding your own logic around.
  5. Swap or decorate implementations without changing the client.

Example

// Inheritance: coupled to HashSet internals (addAll calls add)
class CountingSet<E> extends HashSet<E> {
    int added;
    @Override public boolean add(E e) { added++; return super.add(e); }
    @Override public boolean addAll(Collection<? extends E> c) { added += c.size(); return super.addAll(c); }
} // addAll counts twice!

// Composition: depends only on the Set interface
class CountingSet2<E> {
    private final Set<E> delegate;
    private int added;
    CountingSet2(Set<E> delegate) { this.delegate = delegate; }
    boolean add(E e) { added++; return delegate.add(e); }
    boolean addAll(Collection<? extends E> c) { c.forEach(this::add); return true; }
}

Common mistakes

  • Inheriting just to reuse a utility method.
  • Deep hierarchies (BaseService > AbstractCrudService > ...).
  • Overriding methods of classes not designed for extension.
  • Treating composition as "never use inheritance"; sealed types and template methods are fine.

How to answer in the interview

"Inheritance models an is-a relationship and reuses the parent's code, but couples the subclass to the parent's implementation; that leads to the fragile base class problem, rigid hierarchies and inherited methods that may break invariants. Composition models has-a: a class holds other objects, usually through interfaces, and delegates to them. That's more flexible because behaviour can be injected and swapped, and much easier to test. So I prefer composition and use inheritance only for genuine subtypes that respect Liskov, with a base designed for extension, like a template method in a framework."

Likely follow-up questions

  • How does the Strategy pattern use composition? The context holds a strategy interface and delegates the varying algorithm to it.
  • What is the decorator pattern? Wrapping an object implementing the same interface to add behaviour.
  • When is inheritance right? True subtypes with a stable, extension-designed base.
