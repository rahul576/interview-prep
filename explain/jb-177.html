How does @Transactional work internally?

Spring Boot · concept · levels senior, lead

In one line

@Transactional works through an AOP proxy: a TransactionInterceptor asks the PlatformTransactionManager to begin, commit or roll back around the method call, and binds the connection to the current thread via TransactionSynchronizationManager, which is why self-invocation and private methods bypass it.

Detailed explanation

When Spring creates a bean whose class or methods carry @Transactional, an auto-proxy BeanPostProcessor wraps it in a proxy. If the bean implements interfaces and you use plain Spring, this can be a JDK dynamic proxy; in Spring Boot the default is a CGLIB subclass (proxyTargetClass=true). Every other bean that injects it actually receives the proxy, not the raw object.

On each call, the proxy runs the TransactionInterceptor. It looks up the method's transaction attributes (propagation, isolation, timeout, readOnly, rollback rules) and calls PlatformTransactionManager.getTransaction(). For JPA that is the JpaTransactionManager, which opens an EntityManager, gets a JDBC connection, switches off auto-commit and binds both to the current thread through the ThreadLocal-based TransactionSynchronizationManager. Repositories, JdbcTemplate and the shared EntityManager proxy look up that thread-bound resource, so every call inside the method takes part in the same transaction without passing anything around.

When the method returns, the interceptor commits (with JPA, Hibernate flushes pending changes first). If an exception escapes and matches the rollback rules (by default RuntimeException and Error), it rolls back. Then it unbinds the resources and returns the connection to the pool.

Because everything happens in the proxy, a call like this.otherMethod() inside the same class never goes through it, so no new transaction attributes apply. Private methods cannot be intercepted at all. Since Spring 6, protected and package-private methods work with class-based proxies, but public is still the safe convention.

How it works

  1. At startup, a BeanPostProcessor finds @Transactional and creates a proxy around the bean.
  2. A caller invokes the method on the proxy.
  3. TransactionInterceptor reads the attributes and calls getTransaction() on the transaction manager.
  4. The manager joins, suspends or starts a transaction according to propagation and binds the connection to the thread.
  5. The target method runs; repositories reuse the thread-bound connection.
  6. On return the interceptor commits; on a matching exception it rolls back, then unbinds the resources.

Example

@Service
public class OrderService {
    private final OrderService self;          // injected proxy of itself
    public OrderService(@Lazy OrderService self) { this.self = self; }

    public void importAll(List<Order> orders) {
        orders.forEach(self::saveOne);        // goes through the proxy
        // orders.forEach(this::saveOne);     // would bypass the proxy
    }

    @Transactional
    public void saveOne(Order o) { /* repository calls share one connection */ }
}

Common mistakes

  • Calling a @Transactional method from the same class and expecting a new transaction.
  • Putting @Transactional on private methods.
  • Starting work on another thread (@Async, parallel streams) and expecting it to join the transaction.
  • Assuming checked exceptions roll back by default.

How to answer in the interview

"Spring wraps the bean in a proxy, CGLIB by default in Spring Boot. When I call a transactional method, the TransactionInterceptor reads the attributes and asks the PlatformTransactionManager, for example JpaTransactionManager, to begin a transaction according to propagation. The connection and EntityManager are bound to the current thread through TransactionSynchronizationManager, so all repositories reuse them. After the method returns it commits, or rolls back on a runtime exception. Because it is proxy-based, self-invocation and private methods bypass it, so I move such methods to another bean or use TransactionTemplate."

Likely follow-up questions

  • How do you fix self-invocation? Move the method to a separate bean, inject the proxy of itself, or use TransactionTemplate.
  • Does it work across threads? No, the transaction is bound to the calling thread only.
  • Where are the proxies created? In postProcessAfterInitialization of an auto-proxy creator BeanPostProcessor.
