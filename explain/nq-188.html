What is the default bean scope?

Spring Framework · concept · levels entry

In one line

The default scope is singleton: one instance per ApplicationContext (not per JVM), created eagerly at startup unless @Lazy, and shared by all threads, so it must be stateless or thread-safe.

Detailed explanation

If you declare a bean without @Scope, Spring creates exactly one instance of it, caches it in the singleton registry and injects that same instance into every dependent bean and every getBean call.

It is important to distinguish this from the Gang of Four Singleton pattern. A GoF singleton enforces one instance per class loader through a private constructor and a static getInstance(). A Spring singleton is just "one per container": the class is ordinary, you can still create other instances with new in a test, and if you create two application contexts, or declare two @Bean methods returning the same type, you get two instances. This makes Spring singletons easy to test and replace.

Singletons are instantiated eagerly during context refresh. That is deliberate: missing dependencies, bad configuration or failing connections surface at startup instead of on the first user request. You can defer creation with @Lazy on a bean or globally with spring.main.lazy-initialization=true, trading fast startup for late failures.

Because one instance serves all concurrent requests, singleton beans such as services and controllers must be stateless: dependencies in final fields are fine, but per-request data like the current user, an order being processed or a temporary list must live in local variables or method parameters. If shared state is necessary, use thread-safe structures (ConcurrentHashMap, AtomicLong) or a properly scoped bean.

How it works

  1. Context refresh iterates over non-lazy singleton definitions.
  2. Each bean is created, injected and initialised once.
  3. The instance is stored in the singleton cache.
  4. Every injection and lookup returns the cached instance.
  5. On context close, destroy callbacks run once.

Example

@Service
class PriceService {                       // BUG: shared mutable state
    private BigDecimal lastTotal;          // overwritten by concurrent requests
    BigDecimal total(Cart cart) {
        lastTotal = cart.sum();
        return lastTotal.multiply(TAX);
    }
}

@Service
class SafePriceService {                   // stateless
    private final TaxRates rates;          // immutable dependency
    SafePriceService(TaxRates rates) { this.rates = rates; }
    BigDecimal total(Cart cart) {
        BigDecimal sum = cart.sum();       // local variable per call
        return sum.multiply(rates.forRegion(cart.region()));
    }
}

Common mistakes

  • Storing request or user data in fields of a @Service or controller.
  • Believing a Spring singleton is one per JVM.
  • Making everything @Lazy and discovering configuration errors in production.
  • Using synchronized on whole service methods, serialising all requests.

How to answer in the interview

"The default scope is singleton: the container creates one instance and injects it everywhere. It's one per ApplicationContext, unlike the GoF singleton which is one per class loader. Singletons are created eagerly at startup unless marked lazy, so configuration errors surface early. Since one instance serves all concurrent requests, services and controllers must be stateless, or keep only thread-safe state, never per-request data in fields."

Likely follow-up questions

  • Why is request data in a service field a bug? Concurrent requests overwrite each other's data, leaking information.
  • How to get lazy creation? @Lazy or global lazy initialisation.
  • Are singletons garbage collected? Not while the context is alive; it holds references.
