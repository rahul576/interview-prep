How do you write a good entrypoint script for a container?

Docker · concept · levels mid

In one line

A good entrypoint script does small, idempotent start-up work (render config, fix permissions, brief dependency wait, optional migrations), uses set -e to fail fast, and ends with exec "$@" so the app becomes PID 1, with CMD providing default arguments and no secrets in logs.

Detailed explanation

Some work must happen at container start rather than build time, because it depends on the runtime environment: rendering a configuration file from environment variables, creating a directory on a freshly mounted volume, adjusting permissions, translating secrets mounted as files into the format the app expects, or, in simple setups, running a migration step. An entrypoint script is the place for this.

Good scripts follow a few rules. Start with set -e (often set -eu) so that any failing command stops the container immediately instead of launching a half-configured application that fails later in confusing ways. Make every step idempotent, because containers restart: creating a directory that exists or rendering a file twice must be harmless. Keep it small, POSIX sh if the image has no bash, and fast, because it delays every start.

Crucially, the script must end with exec "$@". exec replaces the shell process with the application, so the app becomes PID 1 and receives SIGTERM directly. "$@" passes the arguments that came from CMD or from docker run, which keeps the image flexible: ENTRYPOINT ["/entrypoint.sh"] and CMD ["java","-jar","/app.jar"] run the app by default, while docker run image sh still gives a shell with the same preparation.

Never echo secrets or run with set -x when secrets are present. Waiting for dependencies should be bounded (a few seconds with a timeout); real resilience belongs in the application's retry logic, and in Kubernetes, migrations are better as a separate Job or init container.

How it works

  1. Docker runs /entrypoint.sh with CMD as arguments.
  2. The script validates required variables.
  3. It prepares config and directories idempotently.
  4. Optionally it waits briefly for a dependency.
  5. exec "$@" replaces the shell with the application.

Example

#!/bin/sh
set -eu
: "${DB_HOST:?DB_HOST is required}"

# Render config from template
envsubst < /app/config.tmpl > /app/config.yml

# Prepare volume directory (idempotent)
mkdir -p /data/uploads

# Allow a short wait for the database
i=0; until nc -z "$DB_HOST" 5432 || [ $i -ge 30 ]; do i=$((i+1)); sleep 1; done

exec "$@"
COPY --chmod=0755 entrypoint.sh /entrypoint.sh
ENTRYPOINT ["/entrypoint.sh"]
CMD ["java", "-jar", "/app.jar"]

Common mistakes

  • Forgetting exec, so the shell stays PID 1 and swallows signals.
  • Infinite "wait for DB" loops that hide real outages.
  • Printing environment variables (including secrets) for debugging.
  • Windows line endings or a missing execute bit, causing "no such file or directory".

How to answer in the interview

"An entrypoint script handles start-up work the app can't do itself, like rendering a config file from environment variables, preparing a mounted volume or briefly waiting for a dependency. It starts with set -e so any failure stops the container instead of launching a half-configured app. It must end with exec "$@" so the shell is replaced by the real process, which becomes PID 1 and gets signals, while CMD supplies the default arguments. I keep it small and idempotent because containers restart, and I never print secrets."

Likely follow-up questions

  • Why isn't waiting in the entrypoint a replacement for app retries? Dependencies can fail after start-up too.
  • Why use "$@" with quotes? It preserves each argument exactly, including spaces.
  • Where should migrations run in Kubernetes? A Job, init container or Helm hook.
