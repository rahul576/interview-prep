What is the difference between configuration management and immutable infrastructure?

Configuration Management · concept · levels entry, mid

In one line

Configuration management (Ansible, Chef, Puppet, Salt) changes running servers in place (mutable infrastructure), which risks configuration drift and snowflake servers; immutable infrastructure never modifies a running server but replaces it with a new golden image (Packer AMI) or container image, giving consistency, easy rollback and simpler debugging.

Detailed explanation

With mutable infrastructure, servers live for months or years. Config management tools converge them to a desired state, but in practice they accumulate differences: a hotfix applied by hand, a package upgraded on one host, a failed run on another. Over time each server becomes a snowflake: unique, hard to reproduce and scary to touch. Updates happen in place, so a failed upgrade can leave a server half-changed, and rollback means writing another change.

With immutable infrastructure, a server or container is never changed after deployment. To change anything, you build a new artifact: a VM image with Packer (an AMI or Azure image) or a container image, test it, and replace the old instances via an auto scaling group instance refresh, a blue-green swap or a Kubernetes rolling update. Every instance from the same image is identical, environments match, and rollback means redeploying the previous image. Debugging is easier because what runs is exactly what was tested. It also fits security: SSH can be disabled, and any unexpected change is suspicious.

It's not either/or. Config management remains useful to build images (Ansible as a Packer provisioner), for legacy or stateful servers that can't be replaced easily (databases, mainframe-adjacent systems), and for network devices. Immutable infrastructure requires good automation: image pipelines, fast provisioning, externalised state and configuration, and health-checked rollouts.

How it works

  1. Define the server in code (Packer template, Ansible role or Dockerfile).
  2. CI builds a versioned image, scans and tests it.
  3. Deploy new instances from the image behind the load balancer.
  4. Health checks pass → drain and terminate old instances.
  5. Problem → redeploy the previous image version.

Example

# Packer: bake a golden AMI, configured once at build time with Ansible
source "amazon-ebs" "web" {
  region        = "eu-west-1"
  instance_type = "t3.small"
  source_ami_filter {
    filters     = { name = "al2023-ami-*-x86_64" }
    owners      = ["amazon"]
    most_recent = true
  }
  ssh_username = "ec2-user"
  ami_name     = "web-{{timestamp}}"
}
build {
  sources = ["source.amazon-ebs.web"]
  provisioner "ansible" { playbook_file = "web.yml" }
}

Terraform then updates the launch template to the new AMI and an instance refresh replaces servers gradually.

Common mistakes

  • Calling infrastructure immutable while still SSHing in to patch.
  • Storing state on instances that are meant to be replaced.
  • Building images manually instead of in a pipeline.
  • Rebuilding images rarely, so they lag on security patches.

How to answer in the interview

"Configuration management tools like Ansible, Chef or Puppet change running servers in place. That's mutable infrastructure, and over time servers drift through manual fixes and partial runs until they become snowflakes that are hard to reproduce. With immutable infrastructure we never modify a running server: we bake a new golden image with Packer or a new container image, test it, and replace the old instances. That gives identical environments, easy rollback to the previous image and simpler debugging. Config management is still useful inside the image build, for example Ansible as a Packer provisioner, and for legacy or stateful servers we can't simply replace."

Likely follow-up questions

  • How do you patch an OS vulnerability? Rebuild the image from the patched base, test, and roll it out by replacing instances.
  • What about stateful servers? Keep data on separate volumes or managed services so instances stay replaceable.
  • Is Kubernetes immutable infrastructure? Pods and images are; nodes can be too with node image upgrades.
