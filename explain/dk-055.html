How do you run a database in Docker for local development safely?

Docker · concept · levels mid

In one line

Use the official image pinned to production's major version, a named volume for data, init scripts in /docker-entrypoint-initdb.d for seed data, credentials from an uncommitted env file, publish the port only on 127.0.0.1, and use Testcontainers for automated tests.

Detailed explanation

Running a database in a container is the easiest way to give every developer the same environment, but a few habits keep it reliable and safe.

Version: use the official image pinned to the same major version as production, for example postgres:16 or mysql:8.4. Running a newer major locally hides incompatibilities; data directories are also not compatible across Postgres majors, so upgrading needs a dump and restore.

Persistence: mount a named volume at the data directory (/var/lib/postgresql/data). Without it, data lives in the writable layer and disappears when the container is recreated. Bind mounts to the host work but can cause permission and performance problems on macOS and Windows.

Initialisation: the official Postgres, MySQL and MariaDB images run .sql, .sql.gz and *.sh files from /docker-entrypoint-initdb.d on first start only, when the data directory is empty. That is good for creating databases, roles and seed data. Real schema changes should come from migration tools like Flyway or Liquibase, the same ones used in production, so local and production schemas never drift.

Security: read credentials from an .env file that is not committed, or a secrets file. Publish the port as 127.0.0.1:5432:5432, because -p 5432:5432 listens on all interfaces, and Docker's iptables rules can bypass host firewalls, exposing a weak dev password to the network.

Tests: for automated tests, Testcontainers (Java, Go, Node, Python, .NET) starts a fresh, throwaway database per test run with a random port and cleans up afterwards, avoiding shared state and order-dependent tests.

How it works

  1. Compose starts the pinned database image.
  2. On first start, the entrypoint initialises the data volume and runs init scripts.
  3. Migrations run from the app or a migrate service.
  4. Developers connect through localhost only.
  5. Tests spin up isolated containers via Testcontainers.

Example

services:
  db:
    image: postgres:16
    env_file: .env.db                 # not committed
    ports: ["127.0.0.1:5432:5432"]
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./db/init:/docker-entrypoint-initdb.d:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER}"]
      interval: 5s
volumes:
  pgdata:
@Container
static PostgreSQLContainer<?> pg = new PostgreSQLContainer<>("postgres:16");

Common mistakes

  • Using latest and getting a new major version unexpectedly.
  • Expecting init scripts to re-run after the volume already exists.
  • Publishing the database on all interfaces with a trivial password.
  • Running docker compose down -v and losing local data unintentionally.

How to answer in the interview

"I use the official image pinned to the same major version as production, like postgres:16, with a named volume for the data directory so data survives recreation, and credentials from an env file that isn't committed. The official images run SQL or shell scripts in /docker-entrypoint-initdb.d on first start, handy for roles and seed data, but schema changes come from Flyway or Liquibase. I publish the port only on 127.0.0.1 so it isn't exposed on the network. For automated tests I use Testcontainers to start a fresh throwaway database per run."

Likely follow-up questions

  • Would you run production databases in Docker? Possible with careful storage and operations, but managed services or operators are usually safer.
  • Why don't my init scripts run? The volume already contains a data directory.
  • How do you reset local data? Remove the named volume deliberately and restart.
