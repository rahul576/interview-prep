How does Lambda scale when a queue receives many messages?

Cloud (AWS) · concept · levels mid

In one line

With an SQS trigger, the event source mapping adds pollers and concurrent invocations as the backlog grows (for standard queues, scaling by up to 300 concurrent executions per minute to about 1,250 per mapping), bounded by account concurrency (default 1,000 per region) and any reserved or maximum concurrency; FIFO scales only up to the number of active message groups; throttled messages stay in the queue, so you cap concurrency to protect downstream systems.

Detailed explanation

Scale-up: the Lambda service starts with a few pollers and monitors queue depth. As messages accumulate, it increases the number of pollers and concurrent function invocations; as the queue drains, it scales down. Since late 2023, scaling for standard queues is faster, adding up to 300 concurrent executions per minute, up to 1,250 concurrent invocations per event source mapping by default.

Limits:

  • Account concurrency quota: shared by all functions in a region, 1,000 by default (can be raised).
  • Reserved concurrency on the function: caps it (and reserves capacity).
  • Maximum concurrency on the event source mapping: caps how many concurrent invocations that queue drives (minimum 2).
  • Batch size and batching window: larger batches mean fewer invocations for the same work.

FIFO queues: ordering per message group ID means only one batch per group is in flight; concurrency is limited by the number of active groups. Design group IDs (for example per customer) to allow parallelism.

Throttling: if Lambda cannot invoke because of concurrency limits, messages are not lost: they remain or return to the queue and are retried later. But with reserved concurrency alone, repeated throttled receives increase the receive count and can push messages into the DLQ; maximum concurrency on the mapping avoids that.

Downstream protection: scaling to hundreds of instances can exhaust a relational database's connections. Cap concurrency to what the database can handle, use RDS Proxy for connection pooling and keep connections outside the handler for reuse.

How it works

  1. Messages arrive; queue depth rises.
  2. ESM adds pollers and invocations.
  3. Concurrency grows until a limit is reached.
  4. Excess messages wait in the queue.
  5. Backlog drains; ESM scales down.

Example

aws lambda update-event-source-mapping --uuid 6f1c-... \
  --scaling-config MaximumConcurrency=40 \
  --batch-size 20 --maximum-batching-window-in-seconds 2

With 40 concurrent invocations and an RDS Proxy, the database sees a bounded connection count even with 500,000 messages queued.

Common mistakes

  • Assuming Lambda scales infinitely.
  • Letting one function consume the whole account quota.
  • Using reserved concurrency alone with SQS and seeing DLQ entries.
  • Too few FIFO message groups, so no parallelism.

How to answer in the interview

"With an SQS trigger, Lambda watches the backlog and adds pollers and concurrent invocations as messages pile up, then scales down as the queue drains. For standard queues it scales up by up to about three hundred concurrent executions per minute, to roughly 1,250 per mapping, bounded by the account concurrency, a thousand per region by default, and any reserved or maximum concurrency. FIFO queues scale only up to the number of active message groups. Throttled messages just wait in the queue. Because fast scaling can overwhelm a database, I cap concurrency with maximum concurrency on the mapping and use RDS Proxy."

Likely follow-up questions

  • Stop Lambda overwhelming a relational database? Maximum concurrency on the ESM, RDS Proxy, batching.
  • How do you monitor scaling? ConcurrentExecutions, Throttles, queue age and depth.
  • Need more than default throughput? Request quota increases and consider provisioned pollers or more queues.
