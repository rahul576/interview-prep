How do you run configuration management at scale for thousands of servers?

Configuration Management · design · levels senior

In one line

At thousands of servers, shrink what configuration management must do by baking immutable images, run the rest with pull/agent-based tools (ansible-pull, SSM, Puppet) or centralised execution (AAP with execution nodes), roll changes out in batches with canaries and failure thresholds, and add reporting, compliance and drift detection.

Detailed explanation

Fleet-scale configuration management fails in predictable ways: one control node cannot hold thousands of SSH connections, a bad change reaches every server at once, nobody knows which hosts actually converged, and long-lived servers drift into snowflakes.

Do less at runtime. Most packages, agents and settings go into images, rebuilt and rolled out regularly. Runtime configuration management handles what genuinely changes on running servers: certificates, credential rotation, emergency mitigations, per-host settings, and fleets that cannot be replaced easily (bare metal, legacy VMs).

Execution model.

  • Pull or agent-based: ansible-pull on timers, AWS SSM State Manager associations, or agent tools like Puppet and Chef. Each node converges itself, so scale is not limited by a central host, and new nodes configure themselves.
  • Centralised execution: Ansible Automation Platform with many execution nodes (automation mesh), close to the hosts, using execution environments and dynamic inventories. Good for coordinated, ordered changes.

Many organisations combine both: pull for baseline enforcement, central push for orchestrated changes.

Safe rollout. Changes go to canary hosts first, then growing batches (serial, SSM rate controls with concurrency and error thresholds), with health checks between batches and automatic stop on failure. Inventories group hosts by environment, region and role so waves are meaningful.

Visibility. Every run reports results centrally (AAP job history, SSM compliance, Puppet reports) into dashboards: which hosts are compliant, failing or unreachable. Scheduled check-mode runs and compliance scans (InSpec, OpenSCAP) detect drift.

How it works

  1. Baseline baked into images; rebuilt weekly.
  2. Runtime roles applied by pull agents every 30 minutes.
  3. Orchestrated changes run from AAP execution nodes in waves.
  4. Canary → 5% → 25% → 100%, stopping on error thresholds.
  5. Results and drift reports feed a compliance dashboard.

Example

# Urgent change via SSM: 10% of tagged hosts at a time, stop at 2% errors
aws ssm send-command \
  --document-name "AWS-ApplyAnsiblePlaybooks" \
  --targets "Key=tag:role,Values=web" \
  --max-concurrency "10%" --max-errors "2%" \
  --parameters '{"SourceType":["GitHub"],"SourceInfo":["{\"owner\":\"acme\",\"repository\":\"config\",\"getOptions\":\"branch:main\"}"],"PlaybookFile":["hotfix.yml"],"InstallDependencies":["True"]}'

Common mistakes

  • Pushing to the whole fleet from one laptop.
  • No canary stage or error threshold.
  • No reporting, so silent failures accumulate.
  • Using configuration management to install everything on every boot instead of baking images.

How to answer in the interview

"First I'd reduce what configuration management has to do: bake most software and settings into immutable images, and use CM only for what really changes at runtime, like certificates, rotations and emergency fixes. For that, a single push host doesn't scale, so I'd use a pull model, such as ansible-pull, SSM State Manager or Puppet, and centralised execution through Ansible Automation Platform with execution nodes for orchestrated changes. Every change rolls out in waves starting with canaries, with failure thresholds that stop it. Results go to dashboards, and scheduled check runs and compliance scans detect drift."

Likely follow-up questions

  • How would you roll out an urgent security change within an hour? Pre-tested playbook, SSM Run Command or AAP in fast waves with error thresholds, plus a compliance query to confirm.
  • Pull or push for compliance? Pull/agents enforce continuously; push is better for ordered changes.
  • How do you handle unreachable hosts? Report them, retry, and treat persistent ones as candidates for replacement.
