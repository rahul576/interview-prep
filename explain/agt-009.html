Which agent frameworks and SDKs are common today, and how do you choose?

AI Agents & AIOps · concept · levels mid, senior

In one line

Common choices include LangGraph, Microsoft Agent Framework (successor to Semantic Kernel and AutoGen), provider SDKs like the OpenAI Agents SDK, Claude Agent SDK and Google ADK, CrewAI, and managed platforms such as Microsoft Foundry Agent Service, Amazon Bedrock AgentCore and Vertex AI Agent Engine; choose by language, control, durability, observability, MCP support, cloud and lock-in.

Detailed explanation

The ecosystem moves fast, so it is more important to understand the categories than every feature.

Graph and orchestration frameworks. LangGraph (Python and JavaScript) models an agent as a graph of nodes and edges over explicit state, with checkpointing, human-in-the-loop interrupts and streaming; it offers fine control and durability and is widely used in production. Microsoft Agent Framework unifies Semantic Kernel and AutoGen for .NET and Python, adding graph-based workflows, multi-agent orchestration patterns and tight Azure integration. CrewAI focuses on role-based "crews" of agents and flows. Others such as LlamaIndex, Pydantic AI and Mastra (TypeScript) are also common.

Provider SDKs. The OpenAI Agents SDK provides agents, tools, handoffs, guardrails and tracing. The Claude Agent SDK exposes the agent harness behind Claude Code: the loop, tools such as file and shell access, context management, permissions and MCP. Google's Agent Development Kit (ADK) supports multi-agent hierarchies and deploys to Google Cloud. They are quick to start but naturally favour their provider's models, although several support other models.

Managed platforms. Microsoft Foundry Agent Service, Amazon Bedrock AgentCore and Vertex AI Agent Engine host agents with runtime isolation, identity, memory, tool gateways and observability, reducing operational work at the price of cloud coupling.

Choosing. Consider the team's language (.NET shops lean to Microsoft Agent Framework), how much control over the loop you need, durability and state for long runs, MCP and A2A support, observability (OpenTelemetry), the cloud you are on, and lock-in. For simple cases, a small custom loop on a provider SDK is often clearer and easier to debug than a large framework.

How it works

  1. Define requirements: languages, models, run length, human approvals, scale.
  2. Shortlist one framework, one provider SDK and one managed option.
  3. Build the same small agent in each; measure developer effort and traceability.
  4. Check MCP support, OpenTelemetry tracing and checkpointing.
  5. Evaluate operations: hosting, identity, cost, upgrade cadence.
  6. Wrap model and tool calls behind your own interfaces to limit lock-in.

Example

# LangGraph: prebuilt ReAct agent with a checkpointer for durability
from langgraph.prebuilt import create_react_agent
from langgraph.checkpoint.memory import MemorySaver   # use a Postgres saver in production

agent = create_react_agent(model, tools=[search_tickets, get_runbook], checkpointer=MemorySaver())
config = {"configurable": {"thread_id": "incident-4711"}}
result = agent.invoke({"messages": [("user", "Why is checkout slow?")]}, config)

Common mistakes

  • Choosing a framework before understanding the problem.
  • Adopting heavy abstractions that hide prompts and make debugging hard.
  • Ignoring framework churn and upgrade cost.
  • Assuming a managed platform removes the need for evals and guardrails.

How to answer in the interview

"There are three groups. Frameworks like LangGraph, which models agents as stateful graphs with checkpointing and human interrupts, and Microsoft Agent Framework, which merges Semantic Kernel and AutoGen for .NET and Python; CrewAI for role-based teams. Provider SDKs like the OpenAI Agents SDK, the Claude Agent SDK and Google's ADK. And managed platforms like Foundry Agent Service, Bedrock AgentCore and Vertex AI Agent Engine that host agents with identity and memory. I choose by team language, how much control over the loop we need, durability for long runs, MCP support, observability, our cloud and lock-in risk. For simple cases, a small custom loop on a provider SDK is often enough."

Likely follow-up questions

  • When would you write your own loop? Simple, single-agent cases where transparency matters and you don't need graphs or durability.
  • How do you limit lock-in? Abstract model and tool interfaces, use MCP for tools and OpenTelemetry for traces.
  • What is checkpointing? Persisting agent state after each step so a run can resume or be inspected.
