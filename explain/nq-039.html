What is lazy evaluation, and when does a stream pipeline execute?

Java 8+ Features · concept · levels entry, mid

In one line

Streams use lazy evaluation: intermediate operations such as filter and map only describe the pipeline, and nothing runs until a terminal operation such as collect, findFirst or forEach is invoked; then elements are pulled through all stages one at a time.

Detailed explanation

When you write list.stream().filter(...).map(...), each call returns a new stream object that records the operation and links it to the previous stage. No element of the source has been read yet. This is why a stream with no terminal operation does nothing at all, and why a peek with a print statement stays silent until you add collect or count.

When the terminal operation is called, the stream builds a chain of sinks, one per stage, and pushes elements from the source through that chain. Processing is vertical, not horizontal: the first element goes through filter, then map, then into the collector, before the second element is read. In effect the stages are fused into a single pass (often called loop fusion), so there are no intermediate lists between stages.

Laziness enables short-circuiting. Operations like findFirst, anyMatch, allMatch, noneMatch and limit can stop the pull as soon as the answer is known. With filter(...).findFirst() over a million elements, processing stops at the first match. The same mechanism makes infinite streams practical: Stream.iterate(1, n -> n + 1) or Stream.generate(...) never terminate on their own, but limit(10) or takeWhile(...) ends the pull.

One exception to pure element-by-element flow is stateful intermediate operations such as sorted and distinct. sorted must see every element before it can emit the first one, so it acts as a barrier in the pipeline. Laziness still applies (nothing happens before the terminal call), but the single-pass flow is interrupted at that stage.

How it works

  1. Each intermediate call creates a new pipeline stage and returns immediately.
  2. The terminal operation triggers evaluation and builds a chain of sinks.
  3. The source's Spliterator supplies elements one by one into the first sink.
  4. Each element passes through every stage before the next element is read.
  5. Short-circuiting operations signal "cancellation requested" and the source stops.
  6. Stateful stages such as sorted buffer elements until upstream is exhausted.

Example

List<String> names = List.of("anna", "bob", "carla", "dave");

Optional<String> first = names.stream()
    .peek(n -> System.out.println("read " + n))
    .filter(n -> n.length() > 3)
    .map(String::toUpperCase)
    .findFirst();      // only now does anything print

// Output:
// read anna
// result: ANNA   ("bob", "carla", "dave" are never read)

List<Integer> squares = Stream.iterate(1, n -> n + 1)
    .map(n -> n * n)
    .limit(5)
    .toList();         // [1, 4, 9, 16, 25] from an infinite source

Common mistakes

  • Expecting side effects inside map or peek to run when no terminal operation is called.
  • Reusing a stream after its terminal operation; it throws IllegalStateException.
  • Putting sorted before limit on an infinite stream, which never finishes.
  • Assuming peek is meant for business logic; it is a debugging aid.

How to answer in the interview

"Streams are lazy. Calling filter or map just adds a stage to a pipeline and returns a new stream; nothing is processed. Execution starts only at the terminal operation. Then the elements are pulled through all the stages one at a time, so the first element goes through filter, map and into the collector before the second one is read. That fuses everything into one pass with no intermediate lists, and it allows short-circuiting: filter followed by findFirst stops at the first match. It is also why infinite streams like Stream.iterate work, as long as something like limit or takeWhile ends the pull. Stateful operations such as sorted are the exception, because they must buffer everything first."

Likely follow-up questions

  • How does laziness let you work with infinite streams? The source is only asked for elements on demand, so limit or takeWhile stops the pull after enough elements.
  • Is sorted lazy? It does not run before the terminal operation, but once running it must consume all upstream elements before emitting any.
  • What happens if you call two terminal operations on one stream? The second throws IllegalStateException; streams are single-use.
