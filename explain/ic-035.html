Explain the Terraform lifecycle meta-arguments.

Infrastructure as Code · concept · levels mid

In one line

The lifecycle block tunes resource handling: create_before_destroy (zero-downtime replacement), prevent_destroy (block deletion), ignore_changes (tolerate external changes), replace_triggered_by (force replacement on other changes), and precondition/postcondition (validate assumptions).

Detailed explanation

Every resource accepts a lifecycle block with meta-arguments that change Terraform's default behaviour.

create_before_destroy = true: by default a replacement deletes the old object first, then creates the new one, causing downtime. With this flag Terraform creates the replacement, repoints dependents, then deletes the old one. It requires that both can coexist, so unique names are needed, typically name_prefix instead of name. The behaviour propagates to dependencies.

prevent_destroy = true: any plan that would destroy the resource, including a replacement, fails with an error. Protects databases and buckets, but only as long as the block exists in code.

ignore_changes = [attr, ...]: Terraform ignores differences in those attributes after creation. Correct for values legitimately managed elsewhere: desired_count of an autoscaled ECS service, desired_capacity of an ASG, tags added by another tool, or a password rotated outside Terraform. ignore_changes = all ignores everything after creation.

replace_triggered_by = [ref, ...]: replaces this resource whenever a referenced resource or attribute changes, for example recreating instances when their launch template or a config hash (terraform_data) changes.

precondition and postcondition blocks contain a condition and an error_message. Preconditions check assumptions before the resource is planned or changed, such as that a looked-up AMI is arm64; postconditions check results afterwards, such as that a certificate is ISSUED. Both fail with clear messages instead of obscure downstream errors.

How it works

  1. Terraform computes the normal plan.
  2. ignore_changes removes diffs on listed attributes.
  3. replace_triggered_by upgrades changes in referenced objects to replacements.
  4. create_before_destroy reorders replacement steps.
  5. prevent_destroy fails plans with destroy actions; conditions are evaluated at plan or apply time.

Example

resource "aws_launch_template" "web" {
  name_prefix   = "web-"
  image_id      = data.aws_ami.web.id
  instance_type = var.instance_type

  lifecycle {
    create_before_destroy = true
    precondition {
      condition     = data.aws_ami.web.architecture == "x86_64"
      error_message = "The selected AMI must be x86_64."
    }
  }
}

resource "aws_ecs_service" "api" {
  name          = "api"
  desired_count = 2
  lifecycle {
    ignore_changes = [desired_count]   # managed by autoscaling
  }
}

resource "aws_instance" "worker" {
  # ...
  lifecycle {
    replace_triggered_by = [aws_launch_template.web.latest_version]
  }
}

Common mistakes

  • create_before_destroy with fixed names, causing "already exists" errors.
  • ignore_changes = all to silence plans, hiding real drift.
  • Relying on prevent_destroy as the only protection.
  • Using variables in lifecycle arguments (they must be static).

How to answer in the interview

"The lifecycle block changes how Terraform handles a resource. create_before_destroy builds the replacement before deleting the old one to avoid downtime, which needs unique names like name_prefix. prevent_destroy makes any plan that would destroy the resource fail. ignore_changes ignores drift in attributes legitimately managed elsewhere, like the desired count of an autoscaled service. replace_triggered_by forces replacement when another resource changes, for example instances when a launch template changes. And preconditions and postconditions validate assumptions with clear error messages."

Likely follow-up questions

  • What is the risk of ignore_changes = all? Terraform stops managing the resource after creation; code changes and drift are silently ignored.
  • Can lifecycle use variables? No, most lifecycle arguments must be literal values.
  • What is terraform_data used for? A neutral resource to hold values or trigger replace_triggered_by.
