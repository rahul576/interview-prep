What is CQRS and event sourcing? When would you use them?

Microservices · concept · levels senior, lead

In one line

CQRS separates the write model that handles commands from read models optimised for queries; event sourcing stores every change as an append-only stream of events that is the source of truth, with projections building read models; use them for complex, audit-heavy domains, not by default.

Detailed explanation

CQRS (Command Query Responsibility Segregation) recognises that writes and reads have different needs. The command side enforces business rules and invariants on a normalised model (PlaceOrder, CancelOrder). The query side serves screens and APIs from denormalised read models: a search index, a reporting table, a cache, each shaped for one use case and scaled independently. CQRS can be as simple as separate query classes on the same database, or as far as separate datastores updated asynchronously.

Event sourcing changes how state is stored. Instead of updating a row, the aggregate appends events (OrderPlaced, ItemAdded, OrderShipped) to its stream in an event store (EventStoreDB/Kurrent, Axon Server, or a Postgres table). Current state is rebuilt by replaying events, optimised with periodic snapshots. Projections subscribe to events and build read models, which is why event sourcing and CQRS fit together naturally. Concurrency is handled with optimistic locking on the stream version.

The benefits are a complete audit trail, temporal queries ("what did this account look like on 1 March?"), the ability to rebuild or add new read models by replaying history, and natural integration through events. The costs are high: eventual consistency between write and read sides, event schema versioning over years (upcasters), replay times, GDPR erasure in immutable logs (crypto-shredding), more infrastructure and a steeper learning curve. Use them where the domain genuinely benefits: ledgers, payments, bookings, compliance-heavy workflows. A simple CRUD service does not need them.

How it works

  1. Client sends a command to the command handler.
  2. Handler loads the aggregate by replaying its events (or snapshot + events).
  3. Aggregate validates and emits new events.
  4. Events are appended with an expected version (optimistic lock).
  5. Projections consume events and update read models.
  6. Queries read from the projections.

Example

public class Account {
    private BigDecimal balance = BigDecimal.ZERO;
    private final List<Object> changes = new ArrayList<>();

    public static Account rehydrate(List<Object> history) {
        Account a = new Account();
        history.forEach(a::apply);
        return a;
    }
    public void withdraw(BigDecimal amt) {
        if (balance.compareTo(amt) < 0) throw new InsufficientFunds();
        raise(new MoneyWithdrawn(amt));
    }
    private void raise(Object e) { apply(e); changes.add(e); }
    private void apply(Object e) {
        if (e instanceof MoneyDeposited d) balance = balance.add(d.amount());
        if (e instanceof MoneyWithdrawn w) balance = balance.subtract(w.amount());
    }
}
// Projection: on MoneyWithdrawn -> UPDATE account_summary SET balance = ... (read model)

Common mistakes

  • Applying CQRS/ES to every service by default.
  • Ignoring that read models lag behind writes in the UI.
  • No strategy for evolving event schemas.
  • Treating events as database change logs instead of meaningful domain facts.

How to answer in the interview

"CQRS splits the model that handles commands and enforces invariants from read models built for queries, so each can be optimised and scaled separately. Event sourcing stores every state change as an immutable event in an append-only stream; current state comes from replaying events, and projections build the read models, so the two fit together. You get a full audit trail, temporal queries and the ability to rebuild new views from history. The cost is eventual consistency, event versioning and much more complexity, so I use them for domains like ledgers or booking systems with strong audit needs, not for simple CRUD."

Likely follow-up questions

  • How do you handle event schema changes after years? Version events, add upcasters that transform old events on read, never rewrite history in place.
  • How do you delete personal data in an event store? Crypto-shredding: encrypt personal fields per user and delete the key.
  • Why snapshots? To avoid replaying thousands of events on every load.
