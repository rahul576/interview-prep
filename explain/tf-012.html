How do you version and source Terraform modules for a team?

Terraform · concept · levels entry, mid, senior

In one line

Source shared modules from a registry or Git, pin versions (version = "~> 3.2" or ?ref=v3.2.1), follow semantic versioning with a changelog, publish through a private registry and a release pipeline with tests, and let consumers upgrade deliberately, often via Renovate.

Detailed explanation

A module's source tells Terraform where to fetch it. Local paths (./modules/network) are for modules that live and change together with the calling configuration in the same repository; they are not versioned separately. Git sources (git::https://github.com/acme/tf-aws-network.git?ref=v3.2.1, or the GitHub shorthand) fetch a specific tag or commit. Registry sources (acme/network/aws from the public registry or app.terraform.io/acme/network/aws from HCP Terraform or Terraform Enterprise's private registry) support the version argument with constraints. OCI and other artifact stores are also options.

Pinning matters because a module change can modify dozens of resources across every consumer. With a registry I use constraints like ~> 3.2 (any 3.x from 3.2) or an exact version for critical stacks; with Git I pin a tag or commit, never a branch like main, which changes underneath you. Unlike providers, module versions are not recorded in the lock file, so the version in code is what controls them.

Semantic versioning communicates impact: patch for fixes, minor for backward-compatible features such as a new optional variable, major for breaking changes such as renamed variables, removed outputs or resource address changes, which should ship with moved blocks and an upgrade guide in the changelog.

Each module repository has a release pipeline: terraform fmt -check, validate, TFLint, security scanning (Checkov or Trivy), terraform test or Terratest against real or mocked providers, docs generation with terraform-docs, then tagging and publishing. Consumers get upgrade pull requests from Renovate or Dependabot and review the plan.

How it works

  1. Developer opens a PR on the module repo; CI runs lint, scan and tests.
  2. Merge triggers semantic release: version bump and changelog.
  3. Tag is pushed; the private registry picks up the new version.
  4. Renovate opens PRs in consumer repos.
  5. Consumers review the plan and upgrade environment by environment.

Example

module "network" {
  source  = "app.terraform.io/acme/network/aws"
  version = "~> 3.2"
  cidr    = "10.20.0.0/16"
}

module "dns" {
  source = "git::https://github.com/acme/tf-aws-dns.git?ref=v1.4.0"
  zone   = "prod.acme.example"
}

Common mistakes

  • Referencing ?ref=main or no ref at all.
  • Breaking changes in a minor version.
  • No tests, so consumers discover bugs in production plans.
  • Deeply nested module chains that are hard to upgrade.
  • One giant "everything" module instead of focused modules.

How to answer in the interview

"Module sources can be local paths for modules inside the same repo, Git URLs or registry addresses, either public or a private registry in HCP Terraform or another artifact store. For shared modules I always pin: version constraints like ~> 3.2 with a registry, or a tag with ?ref=v3.2.1 in Git, never a branch. Modules follow semantic versioning with a changelog, so a major version signals breaking changes, which ship with moved blocks and an upgrade guide. Each module has a release pipeline with fmt, validate, linting, security scanning and terraform test before tagging, and consumers upgrade deliberately through Renovate pull requests."

Likely follow-up questions

  • How do you migrate consumers after a breaking change? Upgrade guide, moved blocks, support the previous major for a while, and track adoption.
  • Mono-repo or repo per module? Repo per module gives independent versions; mono-repo needs path-based tags.
  • Are module versions locked in .terraform.lock.hcl? No, only providers are.
