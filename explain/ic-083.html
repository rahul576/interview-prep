How would you measure the maturity and effectiveness of infrastructure as code in an organisation?

Infrastructure as Code · design · levels lead

In one line

Combine coverage (share of resources managed by IaC), DORA-style flow metrics (lead time, deployment frequency, change failure rate, recovery time), quality metrics (drift, policy violations, security findings), adoption (golden-module and latest-version usage, self-service share) and developer-experience surveys.

Detailed explanation

Maturity is not "we use Terraform"; it is whether infrastructure changes are safe, fast and consistent. A balanced set of metrics avoids optimising one dimension (speed) at the cost of another (safety).

Coverage. Compare cloud inventories (AWS Config, Resource Graph, Cloud Asset Inventory) with resources in state, or use tags such as managed-by = terraform, to compute the share of resources managed as code, per account and team. Manual resources are risk.

Flow (DORA applied to infrastructure). Lead time from infrastructure pull request opened to applied in production; deployment frequency of infrastructure changes; change failure rate (applies causing incidents or rollbacks); time to restore after a failed change. These come from Git and CI data.

Quality and compliance. Drift incidents found by scheduled plans, policy violations blocked or excepted, open security findings from scanners and cloud posture tools, and failed applies. Trends matter more than absolute numbers.

Adoption. How many stacks use golden modules, how many are on supported module and tool versions, and how much is provisioned through self-service rather than tickets.

Experience. Short, regular developer surveys reveal friction that metrics miss: confusing modules, slow pipelines, unclear ownership. Pair them with pipeline duration and wait-for-review times.

For leadership, keep a small set of headline indicators, typically lead time and change failure rate, plus coverage, and use the detailed metrics internally to direct improvement.

How it works

  1. Define metrics and data sources (CI, Git, state, cloud inventory).
  2. Automate collection into a dashboard per team and overall.
  3. Baseline, then set targets per quarter.
  4. Review trends with teams; pick improvements.
  5. Survey developers twice a year and act on findings.

Common mistakes

  • Measuring only activity (number of PRs), not outcomes.
  • Using metrics to rank teams, which encourages gaming.
  • Ignoring developer experience until people bypass the pipeline.
  • Counting coverage by stacks rather than resources.

How to answer in the interview

"I'd combine outcome and adoption metrics. Coverage, the share of cloud resources managed by IaC, found by comparing state with cloud inventories. DORA-style flow metrics for infrastructure: lead time from pull request to production, deployment frequency, change failure rate and time to restore. Quality metrics like drift incidents, policy violations and security findings over time. Adoption of golden modules and current versions, and how much goes through self-service. And regular developer surveys, because they reveal friction the numbers miss. For leadership I'd report a few headline numbers and keep the detail for the teams."

Likely follow-up questions

  • Which single metric would you report to leadership? Lead time with change failure rate alongside, showing speed and safety together.
  • How do you measure coverage? Compare cloud inventory to state or managed-by tags.
  • How do you prevent gaming? Use metrics for improvement, not ranking, and look at several together.
