How do you make CI/CD pipelines reusable across many repositories?

CI/CD Tools · concept · levels mid, senior

In one line

Make pipelines reusable with shared, versioned, parameterised building blocks: GitHub reusable workflows and composite actions, GitLab include and CI/CD components, Jenkins shared libraries or Azure Pipelines templates, offered as a golden path owned by a platform team with changelogs and gradual upgrades.

Detailed explanation

When fifty repositories each contain a copied pipeline, they drift: some pin old tool versions, some skip security scans, and a simple change such as adding image signing means fifty pull requests. Reusable building blocks fix this by defining the logic once and letting repositories call it with parameters.

Each platform has a mechanism. GitHub Actions has reusable workflows (a whole workflow invoked with on: workflow_call, accepting inputs and secrets) and composite actions (a sequence of steps used like any action). GitLab has include (local, project, remote or template files), extends for job inheritance, and CI/CD components published in the CI/CD catalog with typed inputs. Jenkins uses shared libraries of Groovy steps loaded with @Library. Azure Pipelines uses templates with parameters and extends templates that can enforce mandatory steps.

Good blocks are parameterised (language version, image name, deploy target), versioned with semantic tags so consumers pin @v2 and upgrade deliberately, and opinionated with escape hatches. Together they form a golden path: build, test, scan, sign and deploy with security and compliance built in, so the easy way is also the right way. Teams can add custom jobs around it.

Ownership matters: a platform team maintains the templates, tests them against sample repositories, documents inputs, publishes changelogs, and rolls breaking changes out as a new major version with a migration period, often with automated update pull requests from Renovate or Dependabot.

How it works

  1. Identify common steps across repositories.
  2. Extract them into a central templates repository.
  3. Expose inputs and secrets; give safe defaults.
  4. Release with semantic version tags and changelogs.
  5. Consumers call the template, pinned to a version.
  6. Ship breaking changes as new major versions with migration guides.

Example

# acme/ci-templates/.github/workflows/build-java.yml
on:
  workflow_call:
    inputs:
      java-version: { type: string, default: "21" }
      image-name:   { type: string, required: true }
jobs:
  build:
    runs-on: ubuntu-latest
    permissions: { contents: read, id-token: write }
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { distribution: temurin, java-version: "${{ inputs.java-version }}" }
      - run: ./mvnw -B verify
      - run: docker build -t ${{ inputs.image-name }}:${{ github.sha }} .
# consumer repo: .github/workflows/ci.yml
on: [push]
jobs:
  ci:
    uses: acme/ci-templates/.github/workflows/build-java.yml@v2
    with: { image-name: orders-service }

Common mistakes

  • Referencing templates from main so every change hits all teams at once.
  • Monolithic templates with dozens of flags.
  • No tests or documentation for the templates.
  • Hard-coding secrets or environment names inside templates.

How to answer in the interview

"Copying YAML into many repos causes drift, so I build shared building blocks. In GitHub that's reusable workflows and composite actions, in GitLab include and CI/CD components, in Jenkins shared libraries, in Azure Pipelines templates. Each one is parameterised and versioned with tags, so teams pin a version and upgrade when ready. Together they form a golden path with build, test, scanning, signing and deployment built in, while teams can still add their own jobs. A platform team owns them, tests changes, publishes changelogs and ships breaking changes as new major versions with a migration window."

Likely follow-up questions

  • How do you roll out a breaking change safely? Release a new major version, migrate pilot teams first, automate update pull requests, deprecate the old one with a deadline.
  • Reusable workflow vs composite action? A reusable workflow is whole jobs with its own runners; a composite action is steps inside a job.
  • How do you enforce mandatory steps? Required workflows or rulesets in GitHub, extends templates in Azure, compliance pipelines in GitLab.
