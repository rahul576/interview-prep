What is the difference between authentication and authorization?

Security · concept · levels entry

In one line

Authentication verifies who you are; authorization decides what you are allowed to do. Authentication comes first; failures are 401 Unauthorized, while an authenticated user lacking permission gets 403 Forbidden.

Detailed explanation

Authentication (AuthN) establishes identity. The user or system presents credentials, such as a password, a passkey, a one-time code, a client certificate, or a token issued by a trusted identity provider, and the system checks them. The result is a principal: "this request comes from user 42" or "from the billing service". Multi-factor authentication strengthens this step by combining factors.

Authorization (AuthZ) happens after identity is known. It compares the principal's roles, scopes, permissions or attributes with the action and the resource: only ADMIN may delete users; a token with scope orders.read may list orders; a customer may read only their own orders. Authorization can be coarse (by URL or role) or fine-grained (by object ownership or business rules such as amount limits).

The two are easy to confuse because the HTTP status name is misleading: 401 Unauthorized actually means "not authenticated" (missing, invalid or expired credentials) and should include a WWW-Authenticate header. 403 Forbidden means "I know who you are, but you may not do this". Some APIs return 404 instead of 403 for other users' resources, to avoid revealing that they exist.

In Spring Security, authentication filters (form login, HTTP Basic, the JWT bearer filter) create an Authentication and store it in the SecurityContext. Authorization is then enforced by authorizeHttpRequests URL rules and by method security such as @PreAuthorize. In OAuth terms, OpenID Connect handles authentication, while OAuth 2 access tokens and scopes handle authorization.

How it works

  1. Request arrives with credentials (cookie, Bearer token, certificate).
  2. Authentication checks them; if missing or invalid, return 401.
  3. The principal and authorities are stored in the security context.
  4. Authorization checks rules for the URL, method and object.
  5. If allowed, the request proceeds; otherwise return 403.

Example

http.authorizeHttpRequests(a -> a
        .requestMatchers(HttpMethod.DELETE, "/users/**").hasRole("ADMIN")   // authorization
        .anyRequest().authenticated())                                     // must be authenticated
    .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()));          // authentication via JWT
GET /users/7  (no token)                 -> 401 Unauthorized
DELETE /users/7 (valid token, role USER) -> 403 Forbidden
DELETE /users/7 (valid token, ADMIN)     -> 204 No Content

Common mistakes

  • Returning 403 for a missing or expired token.
  • Assuming "logged in" means "allowed".
  • Checking authorization only in the UI.

How to answer in the interview

"Authentication answers who you are. The system verifies credentials such as a password with MFA, a certificate or a JWT issued by our identity provider. Authorization answers what you're allowed to do once your identity is known: roles, scopes or ownership, for example only admins can delete users and customers only see their own orders. Authentication always comes first. In HTTP, a missing or invalid credential is 401, and an authenticated user without permission is 403. In Spring Security the filter chain authenticates and fills the SecurityContext, and authorizeHttpRequests and @PreAuthorize enforce authorization."

Likely follow-up questions

  • Which status code for an expired token? 401 with WWW-Authenticate: Bearer error="invalid_token".
  • Is OAuth authentication or authorization? Authorization; OpenID Connect adds authentication.
  • Why return 404 instead of 403 sometimes? To avoid revealing that another user's resource exists.
