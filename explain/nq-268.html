What is unit testing?

Testing · concept · levels entry

In one line

Unit testing means testing the smallest testable unit of code, usually a method or class, in isolation, with dependencies replaced by mocks or stubs, using fast, automated, repeatable tests written Arrange-Act-Assert in tools like JUnit 5, Mockito and AssertJ.

Detailed explanation

A unit test answers one question: "does this piece of logic behave correctly for this input?" The unit is small, a single method of a pricing class or a service operation, and the test controls everything around it. Anything slow or unpredictable, such as a database, HTTP API, file system, current time or random numbers, is replaced by a test double: a stub that returns fixed data or a mock that records calls.

Because nothing external is involved, unit tests are:

  • Fast: milliseconds each, so thousands run in seconds.
  • Automated: they run with mvn test or gradle test on every build and pull request.
  • Repeatable (deterministic): same result every run, on every machine.
  • Precise: a failure points straight at the broken logic.

That makes them the base of the test pyramid. They give quick feedback while coding, catch regressions when someone changes code later, make refactoring safe and act as living documentation of how the code should behave.

A good unit test follows Arrange-Act-Assert (or Given-When-Then): set up the object and inputs, call the method once, check the outcome. It tests one behaviour, has a name that describes it (returnsZeroFeeForOrdersOverFifty), and covers normal cases, boundaries (exactly 50, zero, empty list, max value) and error cases (null input, invalid values, exceptions from dependencies). It checks observable results, not private details.

Java tools: JUnit 5 to define and run tests (@Test, @ParameterizedTest), Mockito for test doubles, AssertJ for readable assertions, and JaCoCo to see what is not covered.

How it works

  1. Choose a behaviour of the class to test.
  2. Arrange: create the object and stub its dependencies.
  3. Act: call the method.
  4. Assert: compare the result or verify interactions.
  5. Add cases for boundaries and errors.
  6. Run automatically in the build and CI.

Example

class PasswordPolicyTest {

    private final PasswordPolicy policy = new PasswordPolicy(12);

    @Test
    void acceptsLongPasswordWithDigit() {
        // arrange
        String password = "correcthorse1";
        // act
        boolean valid = policy.isValid(password);
        // assert
        assertThat(valid).isTrue();
    }

    @ParameterizedTest
    @ValueSource(strings = {"short1", "nodigitsatallhere", ""})
    void rejectsWeakPasswords(String password) {
        assertThat(policy.isValid(password)).isFalse();
    }

    @Test
    void rejectsNull() {
        assertThatThrownBy(() -> policy.isValid(null))
            .isInstanceOf(IllegalArgumentException.class);
    }
}

Common mistakes

  • Tests that call a real database or API and become slow and flaky.
  • Depending on the current time or random values without controlling them.
  • Testing only the happy path.
  • Tests that depend on each other's order or shared state.

How to answer in the interview

"Unit testing means testing the smallest piece of code, usually one method or class, in isolation. Its dependencies, like a database or an external API, are replaced with mocks or stubs, so the test is fast, automated and gives the same result every time. That's why they run on every build and give quick feedback, catch regressions and make refactoring safe. I write them arrange-act-assert, one behaviour per test, and cover normal, boundary and error cases. In Java I use JUnit 5, Mockito for mocks and AssertJ for assertions."

Likely follow-up questions

  • What makes a unit test flaky? Dependence on time, randomness, threads, network or shared state and test order.
  • Unit test vs integration test? Unit isolates one class with mocks; integration uses real components together.
  • Should you test private methods? No, test them through the public behaviour that uses them.
