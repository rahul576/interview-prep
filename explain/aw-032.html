What are CloudWatch Logs and Logs Insights, and how do you use them?

Cloud (AWS) · concept · levels entry

In one line

CloudWatch Logs stores logs in log groups (per app or function) containing log streams (per container, instance or Lambda environment), fed by Lambda, ECS, the CloudWatch agent, VPC Flow Logs and more; set retention on every group, search and aggregate with Logs Insights, and turn patterns into alarms with metric filters.

Detailed explanation

A log group holds logs sharing retention, encryption and access settings, for example /aws/lambda/orders-api or /ecs/orders-service. Inside it, log streams are sequences of events from one source. Lambda writes automatically; ECS tasks use the awslogs driver or FireLens; EC2 and on-premises servers use the CloudWatch agent; EKS uses Fluent Bit or Container Insights; VPC Flow Logs, API Gateway, Route 53 Resolver, CloudTrail and RDS can deliver too.

Retention defaults to never expire, so storage cost grows forever. Set retention per group (for example 30 days for debug logs, longer for audit logs), ideally enforced through IaC. Export or subscribe older logs to S3 for cheap long-term storage. The Infrequent Access log class lowers ingestion cost for logs you rarely query.

Logs Insights provides a query language with commands like fields, filter, stats, sort, parse and limit, across one or many log groups, charged per GB scanned. It works best with structured JSON logs, because fields are discovered automatically. Natural-language query generation and saved queries help.

Metric filters match patterns in incoming logs and publish metrics, such as a count of "level":"ERROR"; a CloudWatch alarm on that metric notifies the team. Subscription filters stream logs in real time to Lambda, Kinesis or OpenSearch. Live Tail shows logs as they arrive. Logs can be encrypted with KMS, and data protection policies can mask sensitive data such as emails or card numbers.

How it works

  1. Applications emit logs (ideally JSON) to stdout or files.
  2. Agents or integrations ship them to log groups.
  3. Retention policies expire old data.
  4. Logs Insights queries for investigation.
  5. Metric filters create metrics; alarms notify.
  6. Subscriptions stream to other systems.

Example

# Error count in 5-minute buckets
fields @timestamp, level, message
| filter level = "ERROR"
| stats count() as errors by bin(5m)

# Slowest requests in the last hour
fields @timestamp, path, durationMs
| filter ispresent(durationMs)
| sort durationMs desc
| limit 20
aws logs put-retention-policy --log-group-name /ecs/orders-service --retention-in-days 30
aws logs put-metric-filter --log-group-name /ecs/orders-service \
  --filter-name errors --filter-pattern '{ $.level = "ERROR" }' \
  --metric-transformations metricName=OrdersErrors,metricNamespace=Orders,metricValue=1

Common mistakes

  • Never setting retention.
  • Unstructured logs that are hard to query.
  • Logging secrets or personal data.
  • Huge debug logging in production inflating ingestion cost.

How to answer in the interview

"CloudWatch Logs stores logs in log groups, usually one per application or function, each with log streams per container or Lambda instance. Lambda and ECS send logs automatically, EC2 uses the CloudWatch agent, and services like VPC Flow Logs can deliver there too. I always set retention, because the default keeps logs forever. Logs Insights lets me search and aggregate, for example filtering errors and counting them in five-minute bins, which works best with JSON logs. Metric filters turn patterns into metrics so I can alarm when errors exceed a threshold."

Likely follow-up questions

  • Find the slowest requests in the last hour? Filter on the duration field, sort descending, limit 20.
  • How do you reduce log costs? Retention, sampling debug logs, Infrequent Access class, exporting to S3.
  • Metric filter vs subscription filter? Metric filters create metrics; subscriptions stream raw events elsewhere.
