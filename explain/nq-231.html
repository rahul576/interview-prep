How does the Outbox pattern maintain consistency between database updates and event publishing?

Microservices · concept · levels senior, lead

In one line

The outbox keeps database and events consistent by committing the business data and the event in one local ACID transaction, then publishing asynchronously with retries until the broker acknowledges, giving reliable eventual consistency with idempotent consumers.

Detailed explanation

The key move is turning a dual write into a single write. Because the outbox row lives in the same database as the business data, atomicity comes for free: if the transaction rolls back, there is no event; if it commits, the event is durably stored alongside the change. There is never a committed order without its OrderCreated event, or an event for an order that does not exist.

Publishing becomes a separate, retryable step after commit. The relay sends the row to Kafka and only marks it published once the broker acknowledges (with acks=all and an idempotent producer). If Kafka is down for ten minutes, events simply wait in the table; the outage delays notifications but loses nothing. This is the core difference from publishing inside the transaction method, where a broker failure either rolls back the business change or loses the event.

Two subtleties remain. First, duplicates: if the relay crashes after Kafka acknowledged but before the row was marked, the event is sent again. Consumers handle this by deduplicating on a unique event id (a processed-messages table updated in the consumer's own transaction) or by being naturally idempotent (setting status to PAID is safe twice). Second, ordering: the relay reads rows in commit order and uses the aggregate id as the partition key, so all events of one order land on one partition in sequence. Across different aggregates there is no global order, and you should not need one.

The result is eventual consistency: other services learn about the change shortly after commit, reliably, but not instantly. Business processes are designed with that lag in mind.

How it works

  1. Local transaction writes business rows and the outbox row.
  2. Commit makes both durable together.
  3. Relay reads committed rows (polling or CDC from the log).
  4. Relay publishes with key = aggregate id; retries with backoff until acked.
  5. Relay marks the row as published; a cleanup job removes old rows.
  6. Consumers dedupe by event id within their own transaction.

Example

@KafkaListener(topics = "orders")
@Transactional
public void handle(ConsumerRecord<String, String> rec) {
    String eventId = new String(rec.headers().lastHeader("id").value());
    if (inbox.insertIfAbsent(eventId) == 0) return; // duplicate, skip
    payments.startFor(rec.key());
}

Common mistakes

  • Marking the row as sent before the broker acknowledges.
  • Assuming exactly-once end to end; Kafka transactions do not cover your database.
  • Dedup table written outside the consumer's business transaction.
  • Expecting global ordering across aggregates.

How to answer in the interview

"The outbox removes the dual write. The business change and the event row are committed in one local transaction, so they're always consistent: rollback means no event, commit means the event is stored. Publishing happens afterwards and is retried until Kafka acknowledges; only then is the row marked as sent, so a broker outage just delays events. If the relay crashes after sending but before marking, the event goes out again, so consumers dedupe by event id. Using the aggregate id as the Kafka key keeps per-order ordering. Overall we get reliable eventual consistency between services."

Likely follow-up questions

  • Why is publishing to Kafka inside the @Transactional method not enough? Kafka isn't part of the database transaction: the send can succeed and the commit fail, or the commit succeed and the send fail.
  • What about Kafka transactions? They give exactly-once within Kafka, not across your database.
  • How do you monitor the outbox? Alert on the age of the oldest unpublished row.
