How do LLMOps differ from traditional MLOps?

MLOps · concept · levels mid, senior

In one line

LLMOps is MLOps adapted to applications built on foundation models: you mostly version prompts, retrieval settings, tools and model versions rather than weights, evaluation of open-ended output is harder, and safety, cost per token and provider changes become first-class concerns.

Detailed explanation

In classic MLOps the team owns the full loop: collect data, train, evaluate on a labelled test set, deploy weights, monitor drift. Many LLM applications skip training entirely and call a hosted model or serve an open-weights model, sometimes with fine-tuning or LoRA adapters. The behaviour of the system is therefore defined by a configuration bundle: system prompt and templates, the exact model identifier and version, sampling parameters, RAG settings (chunking, embedding model, index version, top-k, reranker), tool or function definitions and guardrail policies. All of these must be versioned together, because changing any one changes the output.

Evaluation is the hardest shift. Outputs are free text with many acceptable answers, so teams combine a curated evaluation set of realistic queries, rule-based checks (format, citations, banned content), LLM-as-judge scoring for relevance, groundedness and helpfulness, and human review. The judge itself must be validated against human labels. Evaluations run in CI for every prompt or config change, as regression tests.

New risks: hallucination, prompt injection (including indirect injection from retrieved documents), data leakage of PII or secrets, jailbreaks and unsafe tool actions. Mitigations include input and output filters, least-privilege tools and red-teaming.

Cost and latency are driven by tokens and GPU capacity, so caching (including prompt caching), model routing to smaller models, token budgets and streaming matter. Monitoring tracks quality signals (user feedback, judge scores on sampled traffic), safety flags, latency, tokens and cost per request. A provider can retire or update a model, so pin versions and re-run evals before switching.

How it works

  1. Store prompts, model versions and RAG config in Git as a versioned bundle.
  2. Build an evaluation set from real queries, with expected facts or rubrics.
  3. Run automated evals (rules plus LLM-as-judge) in CI on each change.
  4. Deploy behind a gateway that logs prompts, responses, tokens and cost with trace IDs.
  5. Sample production traffic for judge scoring and human review.
  6. Alert on quality, safety, latency and cost regressions; roll back the config bundle if needed.

Example

release: support-bot-2026.11.3
model: { provider: azure-openai, name: gpt-4o, version: "2024-11-20", temperature: 0.2 }
prompt: prompts/support_v14.md
retrieval: { embedder: text-embedding-3-large, index: kb-2026-11-15, chunk: 800, top_k: 6, reranker: on }
tools: [lookup_order_v3, create_ticket_v2]
eval_gate: { groundedness: ">=0.90", answer_relevance: ">=0.85", injection_suite: "pass" }

Common mistakes

  • Changing prompts in production without versioning or evals.
  • Trusting LLM-as-judge without calibrating it against humans.
  • Using a floating model alias, so the provider silently changes behaviour.
  • Ignoring indirect prompt injection from retrieved content.

How to answer in the interview

"The main difference is that we often don't train anything. We version a bundle of prompts, model version, retrieval settings and tools, and treat any change to that bundle like a code release. Evaluation is harder because outputs are open-ended, so I combine a curated eval set, rule checks, LLM-as-judge scores validated against humans, and human review, all in CI. There are new risks like hallucination and prompt injection, and cost is driven by tokens, so caching and routing to smaller models matter. Monitoring covers quality, safety, latency and cost per request."

Likely follow-up questions

  • What do you version without weights? Prompts, model ID and version, sampling parameters, retrieval and index versions, tools and guardrails.
  • How do you detect hallucinations in production? Groundedness checks against retrieved sources on sampled traffic, plus user feedback.
  • When would you fine-tune? When prompting and RAG can't reach the needed style, format or latency, and you have quality data.
