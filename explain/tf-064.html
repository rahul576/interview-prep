How do you test Terraform modules with the native terraform test framework, including mocks?

Terraform · concept · levels mid, senior

In one line

Native tests live in .tftest.hcl files with run blocks that use command = plan or apply, check results with assert blocks, avoid real infrastructure with mock_provider and override blocks (Terraform 1.7+), and verify validation rules with expect_failures.

Detailed explanation

Since Terraform 1.6, terraform test is built in, so module tests are written in HCL rather than Go (Terratest) or external tools. Test files sit in the module root or a tests/ directory.

Each file contains run blocks executed in order. A run with command = plan evaluates the configuration and checks the planned values: fast, cheap, good for logic. A run with command = apply (the default) creates real resources, then Terraform destroys everything at the end of the file in reverse order. Each run has assert blocks with a condition and an error_message, referencing outputs, resource attributes or locals, for example that a storage account has public access disabled. Variables can be set at file level or per run, and later runs can reference earlier ones, such as run.setup.resource_group_name. Helper modules can be loaded in a run to create prerequisites.

Terraform 1.7 added mocking. A mock_provider block replaces a real provider: no credentials, no API calls, computed attributes get generated fake values, and you can set defaults with mock_resource and mock_data. override_resource, override_data and override_module fix values for specific addresses, useful when logic depends on data sources. With mocks, even apply runs are pure unit tests.

expect_failures asserts that something fails, typically a variable validation or precondition: the run passes only if the listed checkable objects report errors.

How it works

  1. Create tests/name.tftest.hcl in the module.
  2. Optionally declare mock_provider blocks for unit tests.
  3. Add run blocks with command, variables and assert.
  4. Add negative tests with invalid input and expect_failures.
  5. Run terraform test locally and in CI.
  6. Use real-apply tests in a sandbox subscription for integration.

Example

# tests/storage.tftest.hcl
mock_provider "azurerm" {}

variables {
  name        = "stordersdev01"
  environment = "dev"
}

run "private_by_default" {
  command = plan
  assert {
    condition     = azurerm_storage_account.this.public_network_access_enabled == false
    error_message = "Storage must not be publicly accessible."
  }
}

run "rejects_bad_name" {
  command   = plan
  variables { name = "Invalid_Name!" }
  expect_failures = [var.name]
}

Common mistakes

  • Only writing apply tests, making CI slow and costly.
  • Only writing mocked tests, missing real provider and API behaviour.
  • Asserting on values that are unknown during plan.
  • Not testing validation rules with negative cases.

How to answer in the interview

"Since Terraform 1.6 I write tests in .tftest.hcl files. Each run block uses command plan for fast checks or apply to create real resources, which are destroyed at the end. Assert blocks check outputs or attributes, like public access being disabled. Variables can be set per file or per run, and runs can use outputs from earlier runs. Since 1.7, mock_provider and override blocks let me unit test logic without credentials or cost, and expect_failures checks that invalid inputs fail validation."

Likely follow-up questions

  • PR versus nightly tests? Mocked and plan tests on every PR; real apply tests nightly or before releases.
  • Where do tests clean up? Terraform destroys created resources at the end of each test file.
  • Terratest still useful? For complex end-to-end checks in Go, such as calling the deployed app.
