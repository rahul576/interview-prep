What are fail-fast and fail-safe iterators?

Collections · concept · levels entry, mid

In one line

Fail-fast iterators (ArrayList, HashMap) detect structural changes via modCount and throw ConcurrentModificationException; fail-safe / weakly consistent iterators (CopyOnWriteArrayList, ConcurrentHashMap) work on a snapshot or tolerate concurrent changes without throwing.

Detailed explanation

Most java.util collections keep a counter called modCount that increases on every structural modification (add, remove, resize, but not set). When you create an iterator it remembers expectedModCount. On each next() it checks the two values and throws ConcurrentModificationException if they differ. This is called fail-fast: it stops quickly instead of continuing with corrupted state.

It is important to understand that fail-fast is a best-effort bug detector, not a thread-safety mechanism. The documentation explicitly says it cannot be guaranteed in the presence of unsynchronised concurrent modification. Most of the time the exception is triggered in a single thread, by calling list.remove() inside a for-each loop.

The concurrent collections behave differently. CopyOnWriteArrayList copies the entire array on every write, so an iterator walks an immutable snapshot taken when it was created; it never sees later changes and its remove is unsupported. ConcurrentHashMap iterators are weakly consistent: they traverse the live table, never throw, and may reflect some, all or none of the changes made during iteration. The term "fail-safe" is informal; the Java docs prefer "weakly consistent" or "snapshot".

How it works

  1. Collection increments modCount on each structural change.
  2. Iterator stores expectedModCount at creation.
  3. next() compares them and throws on mismatch.
  4. Iterator.remove() updates both counters, so it is allowed.
  5. Snapshot iterators read a fixed array; weakly consistent iterators read live volatile data.

Example

List<String> names = new ArrayList<>(List.of("a", "b", "c"));
for (String n : names) {
    if (n.equals("b")) names.remove(n);   // ConcurrentModificationException
}

names.removeIf(n -> n.equals("b"));       // safe
Iterator<String> it = names.iterator();
while (it.hasNext()) if (it.next().isEmpty()) it.remove(); // safe

List<Listener> listeners = new CopyOnWriteArrayList<>();
for (Listener l : listeners) l.onEvent(e); // never throws, snapshot

Common mistakes

  • Believing fail-fast iterators make a collection thread safe.
  • Removing inside an enhanced for loop instead of using removeIf or Iterator.remove.
  • Expecting a CopyOnWriteArrayList iterator to see newly added items.
  • Using CopyOnWriteArrayList for write-heavy data.

How to answer in the interview

"Fail-fast iterators, used by ArrayList and HashMap, check a modCount on every next call and throw ConcurrentModificationException if the collection was structurally changed other than through the iterator's own remove. It is a best-effort bug detector, not thread safety. Fail-safe or weakly consistent iterators, in CopyOnWriteArrayList and ConcurrentHashMap, don't throw: CopyOnWriteArrayList iterates a snapshot and ConcurrentHashMap may or may not reflect concurrent changes. To remove while iterating I use Iterator.remove or removeIf."

Likely follow-up questions

  • When would you choose CopyOnWriteArrayList? Read-mostly, small lists such as event listeners.
  • Does set() trigger the exception? No, it is not a structural modification.
  • Can single-threaded code throw ConcurrentModificationException? Yes, it is the most common case.
