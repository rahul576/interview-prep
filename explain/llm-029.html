How do you make RAG retrieval permission-aware so users only see documents they are allowed to access?

LLMOps & RAG · concept · levels senior, lead

In one line

Enforce permissions in retrieval, never in the prompt: store ACL metadata per chunk, filter by the user's identity and groups at query time, sync permission changes from sources (or check at query time for sensitive data), isolate tenants with separate indexes or namespaces, and test with different users.

Detailed explanation

An LLM cannot keep secrets: anything placed in its context can appear in its answer, whether through a direct question, a summarisation or a prompt injection hidden in another document. The only safe rule: a user's request may only retrieve content that user is allowed to read in the source system.

At ingestion, each chunk carries access control metadata from its source: allowed user IDs, group or role IDs, sensitivity labels, tenant ID, or a document ID that maps to an ACL table. Connectors must capture inherited permissions and deny entries faithfully.

At query time, the backend derives the user's identity from the verified token (OIDC / Entra ID / Okta), resolves group memberships (cached, with expiry), and adds them as a mandatory filter in the search query, so only permitted chunks are candidates. The filter must be applied server-side by the retrieval service, not by the client, and before top-k selection (pre-filtering); filtering after retrieving the top 10 can leave nothing or leak via counts.

Freshness. Permissions change: people move teams, documents are re-shared, employees leave. A permission sync process updates chunk metadata on change events or on a schedule, and group membership caches expire quickly. For highly sensitive content, late-binding checks call the source system's permission API for the final candidates before they go into the prompt. Define and monitor an SLA, for example revocations effective within 15 minutes.

Multi-tenant products add stronger isolation: separate indexes, namespaces or collections per tenant, separate encryption keys where required, and tenant ID enforced in every query.

Verification. Automated tests with personas at different permission levels, including recently removed users and guest accounts, assert that restricted documents never appear in retrieved sets or citations.

How it works

  1. Connector ingests documents with ACLs and tenant ID.
  2. User authenticates; backend resolves user and groups.
  3. Search query includes a mandatory ACL and tenant filter.
  4. Optional late check against source for sensitive hits.
  5. Answer cites only permitted documents; access is logged.

Example

{
  "query": { "bool": {
    "must": [ { "knn": { "field": "embedding", "query_vector": [0.12, -0.03], "k": 50 } } ],
    "filter": [
      { "term":  { "tenant_id": "acme" } },
      { "terms": { "allowed_principals": ["user:u123", "group:finance", "group:all-staff"] } }
    ] } }
}

Common mistakes

  • Relying on the system prompt to hide restricted content.
  • Indexing everything with one service account and no ACLs.
  • Post-filtering after top-k retrieval.
  • Stale group caches that keep access after revocation.

How to answer in the interview

"Permissions must be enforced in retrieval, never by asking the model to hide content, because anything in the prompt can come out. At ingestion each chunk stores access metadata from its source, like allowed users and groups. At query time I take the user identity and groups from the identity provider token and apply them as a mandatory server-side filter, so only permitted chunks are candidates. A sync process updates metadata when source permissions change, and for very sensitive content I recheck against the source at query time. For multi-tenant products I separate indexes or namespaces, and I test with users at different permission levels, including recently removed ones."

Likely follow-up questions

  • How fast should revocation apply? Define an SLA, often minutes; late-binding checks for sensitive data.
  • Large group lists per user? Use group IDs and hierarchical ACL resolution, not per-user lists.
  • Can embeddings leak data? They can be partly inverted, so protect vector stores like source data.
