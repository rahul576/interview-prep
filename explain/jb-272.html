How would you implement role-based access control in Spring Security?

Security · design · levels senior, lead

In one line

Get roles or authorities into Spring Security (from a UserDetailsService or mapped from JWT claims with a JwtAuthenticationConverter), enforce them with URL rules in the SecurityFilterChain and @PreAuthorize method security, add object-level ownership checks, deny by default, and test every rule.

Detailed explanation

RBAC grants permissions to roles and roles to users. In Spring Security everything becomes a GrantedAuthority. A role is just an authority with the prefix ROLE_: hasRole("ADMIN") checks ROLE_ADMIN, while hasAuthority("orders:write") checks the exact string. A good design keeps coarse roles (ADMIN, SUPPORT, CUSTOMER) mapped to fine permissions (orders:read, orders:refund), and code checks permissions, so changing who can refund does not need a code change.

Authorities come from somewhere. In a classic app a UserDetailsService loads the user and their roles from the database. In a resource server, they come from the token: by default Spring maps scope/scp into SCOPE_xxx authorities; for custom claims such as Keycloak's realm_access.roles or Entra ID's roles, you configure a JwtAuthenticationConverter.

Enforcement happens in two layers. URL rules in authorizeHttpRequests give coarse protection, ending with anyRequest().authenticated() or denyAll() so new endpoints are not accidentally open. Method security, enabled with @EnableMethodSecurity, puts @PreAuthorize on service methods, closer to the business logic. Roles alone do not stop a customer reading another customer's order, so you also need object-level checks: a SpEL call to a bean, a PermissionEvaluator, @PostAuthorize on the returned object, or simply queries scoped to the current user. Finally write tests with @WithMockUser or jwt() request post-processors for each role, including negative cases.

How it works

  1. Define roles and permissions; store or issue them (database or identity provider).
  2. Map them to GrantedAuthority objects (UserDetailsService or JwtAuthenticationConverter).
  3. Add URL rules with deny by default.
  4. Add @PreAuthorize on service methods, including ownership checks.
  5. Test allowed and denied paths for each role.

Example

@Bean
JwtAuthenticationConverter jwtAuthConverter() {
    JwtGrantedAuthoritiesConverter roles = new JwtGrantedAuthoritiesConverter();
    roles.setAuthoritiesClaimName("roles");
    roles.setAuthorityPrefix("ROLE_");
    JwtAuthenticationConverter c = new JwtAuthenticationConverter();
    c.setJwtGrantedAuthoritiesConverter(roles);
    return c;
}

@Bean
SecurityFilterChain chain(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(a -> a
            .requestMatchers("/admin/**").hasRole("ADMIN")
            .requestMatchers(HttpMethod.GET, "/orders/**").hasAnyRole("CUSTOMER", "SUPPORT")
            .anyRequest().denyAll())
        .oauth2ResourceServer(o -> o.jwt(j -> j.jwtAuthenticationConverter(jwtAuthConverter())));
    return http.build();
}

@PreAuthorize("hasAuthority('orders:refund') or @orderAccess.isOwner(#id, authentication)")
public void refund(long id) { ... }

@Test
@WithMockUser(roles = "CUSTOMER")
void customerCannotOpenAdmin() throws Exception {
    mvc.perform(get("/admin/users")).andExpect(status().isForbidden());
}

Common mistakes

  • Writing hasRole("ROLE_ADMIN"), which looks for ROLE_ROLE_ADMIN.
  • Hard-coding role names everywhere instead of permissions.
  • Only checking in the UI or only at URL level.
  • Ending rules with permitAll() instead of deny by default.

How to answer in the interview

"First the roles must reach Spring Security as GrantedAuthorities, either from the database through a UserDetailsService or, in a resource server, from JWT claims mapped by a JwtAuthenticationConverter. Then I enforce them in two layers: URL rules in the SecurityFilterChain, like admin paths requiring ROLE_ADMIN, with deny by default at the end; and method security with @PreAuthorize on service methods, ideally checking permissions like orders:refund rather than role names. Roles are not enough for data, so I add ownership checks through a bean or PermissionEvaluator. And I test every role, including the forbidden cases, with @WithMockUser."

Likely follow-up questions

  • hasRole vs hasAuthority? hasRole adds the ROLE_ prefix; hasAuthority matches the exact string.
  • Role hierarchy? A RoleHierarchy bean lets ADMIN imply SUPPORT, and so on.
  • RBAC vs ABAC? ABAC decides on attributes (department, time, owner); RBAC on roles; many systems combine them.
