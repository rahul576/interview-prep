Design the classes for a parking lot system.

Low-Level Design · design · levels mid, senior

In one line

Model ParkingLot -> Levels -> Spots, Vehicle types and Ticket, let each spot decide canFit(vehicle) via polymorphism, use the Strategy pattern for allocation and pricing, and make spot assignment thread-safe so two cars never get the same spot.

Detailed explanation

Low-level design interviews test object modelling, SOLID principles and extensibility more than algorithms. Start by clarifying requirements: multiple levels, spot sizes (motorcycle, compact, large, EV), multiple entry/exit gates, hourly pricing, display of free spots, payment at exit.

Core entities:

  • ParkingLot (singleton per site, or just one instance) holds Levels and gates.
  • Level holds ParkingSpots and counts free spots per type.
  • ParkingSpot has an ID, SpotType, and an occupied vehicle.
  • Vehicle with VehicleType (enum or subclasses Car, Bike, Truck).
  • Ticket records ticket ID, vehicle, spot, entry time, exit time and status.
  • Payment / Receipt.

Avoid instanceof chains: each SpotType (or spot class) answers canFit(VehicleType), which follows the Open/Closed principle: adding EV spots adds a type, not edits everywhere.

Allocation is a SpotAllocationStrategy interface (nearest to entrance, lowest level first, EV preference), swappable without touching the lot. Pricing is a PricingStrategy (hourly, flat weekend rate, first 30 minutes free), composed per vehicle type.

Concurrency: several gates assign spots simultaneously. Use per-type free-spot queues (ConcurrentLinkedQueue or BlockingQueue) where polling a spot is atomic, or a lock per level, or a compare-and-set on the spot's occupied flag. Observer pattern updates display boards when spots change.

How it works

  1. Vehicle arrives at an entry gate; gate calls lot.park(vehicle).
  2. Strategy picks a candidate spot; spot is claimed atomically.
  3. A Ticket is issued with entry time.
  4. At exit, PricingStrategy calculates the fee from duration and type.
  5. Payment succeeds -> spot released back to its free queue.
  6. Observers update displays with free counts.

Example

enum VehicleType { BIKE, CAR, TRUCK }

enum SpotType {
    SMALL(Set.of(VehicleType.BIKE)), COMPACT(Set.of(VehicleType.BIKE, VehicleType.CAR)),
    LARGE(Set.of(VehicleType.CAR, VehicleType.TRUCK));
    private final Set<VehicleType> fits;
    SpotType(Set<VehicleType> fits) { this.fits = fits; }
    boolean canFit(VehicleType v) { return fits.contains(v); }
}

final class ParkingSpot {
    private final String id; private final SpotType type;
    private final AtomicReference<Vehicle> vehicle = new AtomicReference<>();
    ParkingSpot(String id, SpotType type) { this.id = id; this.type = type; }
    boolean tryOccupy(Vehicle v) { return type.canFit(v.type()) && vehicle.compareAndSet(null, v); }
    void release() { vehicle.set(null); }
}

interface SpotAllocationStrategy { Optional<ParkingSpot> allocate(List<Level> levels, Vehicle v); }
interface PricingStrategy { Money fee(Ticket t, Instant exit); }

record Ticket(String id, Vehicle vehicle, ParkingSpot spot, Instant entry) {}

Common mistakes

  • One god class ParkingLot doing allocation, pricing and payment.
  • if (vehicle instanceof Truck) scattered through the code.
  • Ignoring concurrency across multiple gates.
  • Hard-coding pricing rules.
  • Not clarifying requirements before drawing classes.

How to answer in the interview

"I'd clarify requirements first, then model ParkingLot containing Levels, each with Spots, plus Vehicle types and a Ticket recording vehicle, spot and times. Spot types decide which vehicles fit through a canFit method rather than type checks. Allocation is a strategy, say nearest to entrance, and pricing is another strategy so rules can change. Spot assignment is thread-safe, using an atomic compare-and-set on the spot or per-type concurrent queues, so two gates never assign the same spot. Display boards observe spot events."

Likely follow-up questions

  • Reservations in advance? A Reservation with time window; allocation excludes reserved spots for that window.
  • Multiple lots in a city? A service layer with lot IDs, persistence and an availability API.
  • EV charging? A spot capability plus a charging session with its own pricing.
