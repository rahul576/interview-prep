How does an AI model use MCP to access external tools or information?

AI/ML & GenAI · concept · levels senior, lead

In one line

The client discovers tools with tools/list (names, descriptions, JSON Schemas), the host gives these definitions to the model, the model emits a structured tool call, the host checks policy and approval, the client sends tools/call, and the result is fed back to the model, which may call more tools or answer; resources are loaded via resources/list and resources/read.

Detailed explanation

The model never connects to the server directly. It only produces text, including structured tool-use requests; the host turns those into MCP calls.

Discovery: after the handshake, the client sends tools/list. Each tool has a unique name, a natural-language description, an inputSchema (JSON Schema), optionally an outputSchema and annotations hinting whether it is read-only or destructive. The host converts them into the model API's tool format.

Decision: given the user request and tool definitions, the model decides whether a tool helps. The description quality matters enormously: it is the model's only guide to when and how to use the tool.

Invocation: the model returns a tool call with arguments matching the schema. The host validates, applies policy (allow-lists, approval for sensitive actions) and asks the user if needed. The client sends tools/call; the server executes and returns content (text, images, structured content) or an error flagged with isError so the model can adapt.

Loop: the host appends the result to the conversation. The model may chain calls (search, then read, then update) before giving a final answer. This loop is the basis of agents.

Resources are typically application- or user-controlled context: the client lists them and reads selected URIs into the context. Prompts are user-invoked templates.

How it works

  1. initialize handshake, then tools/list and resources/list.
  2. Host adds tool definitions to the model request.
  3. Model returns a tool call with JSON arguments.
  4. Host validates, checks policy and gets approval if required.
  5. Client sends tools/call; server executes and returns content.
  6. Host returns the result to the model; repeat until a final answer.

Example

// tools/list result (excerpt)
{ "tools": [ { "name": "get_order_status",
  "description": "Look up the current status of an order by its order ID (e.g. ORD-1234).",
  "inputSchema": { "type": "object",
    "properties": { "orderId": { "type": "string" } }, "required": ["orderId"] },
  "annotations": { "readOnlyHint": true } } ] }

// tools/call result
{ "content": [ { "type": "text", "text": "ORD-1234: SHIPPED on 2026-11-19" } ], "isError": false }

Common mistakes

  • Believing the model talks to servers itself.
  • Vague tool descriptions, causing wrong or missed calls.
  • Returning huge raw payloads that flood the context.
  • Trusting annotations from untrusted servers for security decisions.

How to answer in the interview

"At connection time the client calls tools/list, which returns each tool's name, description and JSON Schema for inputs. The host passes those definitions to the model. When the user asks something, the model decides whether a tool helps and returns a structured call with arguments. The host validates it, checks policy and, if needed, asks the user to approve, then the client sends tools/call to the server, which executes it and returns content or an error. The host feeds that back to the model, which may call more tools or answer. Resources work similarly with resources/list and resources/read to load data into context."

Likely follow-up questions

  • Why do tool descriptions matter so much? They are the model's only information about when and how to use a tool.
  • How should tool errors be returned? As results with isError, so the model can retry or explain.
  • How do you limit context usage? Expose few, focused tools and return concise results with pagination.
