Which model serving frameworks have you used or evaluated, and how do they differ?

MLOps · concept · levels mid, senior

In one line

KServe is Kubernetes-native serving with autoscaling and a standard inference protocol; NVIDIA Triton is high-performance multi-framework GPU serving; BentoML and Ray Serve are Python-first for composing models and logic; TorchServe and TF Serving are framework-specific; managed endpoints (SageMaker, Azure ML, Vertex AI) remove infrastructure work. Choose by frameworks, latency, GPU needs and platform.

Detailed explanation

KServe defines an InferenceService custom resource. It deploys a model with a chosen runtime, supports autoscaling (including scale to zero in serverless mode with Knative, or raw Deployments with HPA/KEDA), canary traffic splitting, transformers for pre- and post-processing, and the Open Inference Protocol (V2). It also has runtimes for LLMs, such as vLLM-based Hugging Face serving. It suits teams already running Kubernetes.

NVIDIA Triton Inference Server is built for throughput: it serves TensorRT, ONNX, PyTorch, TensorFlow and Python backends, with dynamic batching, concurrent model execution on one GPU, model ensembles and detailed metrics. It is often used as a runtime underneath KServe or SageMaker.

BentoML and Ray Serve are Python-first: you write the service as Python classes, compose multiple models and business logic into one graph, and scale replicas independently. Ray Serve runs on a Ray cluster and is strong for multi-model pipelines and LLM serving. TorchServe (now in limited maintenance) and TensorFlow Serving are framework-specific and simpler but narrower. Managed endpoints give autoscaling, monitoring and security integration with little operational work, at higher unit cost and with more lock-in.

For LLMs specifically, dedicated engines like vLLM, TGI or TensorRT-LLM handle continuous batching and KV-cache management and are commonly plugged into these platforms.

How it works

  1. List the frameworks and model types to serve.
  2. Define latency, throughput and GPU requirements.
  3. Check the platform: Kubernetes in-house, or a cloud ML platform.
  4. Shortlist and benchmark with real models and payloads.
  5. Evaluate operability: rollouts, metrics, autoscaling, security.
  6. Standardise on one or two golden paths for teams.

Example

apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
metadata:
  name: churn-model
spec:
  predictor:
    minReplicas: 1
    maxReplicas: 10
    model:
      modelFormat:
        name: sklearn
      storageUri: s3://models/churn/v12

Common mistakes

  • Choosing a framework from a blog post without benchmarking your own models.
  • Running GPU models without dynamic batching.
  • Letting every team pick a different serving stack.
  • Ignoring how rollouts and monitoring work in the chosen tool.

How to answer in the interview

"I've worked mostly with KServe on Kubernetes, where an InferenceService gives autoscaling, canary rollouts and a standard inference protocol over many runtimes. For heavy GPU workloads, Triton is the performance choice, with dynamic batching and multiple models per GPU, and it often runs underneath KServe. BentoML and Ray Serve are nice when the service is Python logic composing several models. Managed endpoints on SageMaker, Azure ML or Vertex remove ops work. I choose by frameworks, latency and GPU needs, and whether we already run Kubernetes, and I benchmark before standardising."

Likely follow-up questions

  • What does dynamic batching do? Groups concurrent requests into one GPU batch within a short delay, raising throughput at a small latency cost.
  • When pick managed endpoints? Small teams, standard models, strong alignment with one cloud.
  • How do you serve LLMs? An engine like vLLM with continuous batching, behind KServe, Ray Serve or a managed service.
