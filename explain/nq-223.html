What is an API Gateway, and why is it used?

Microservices · concept · levels entry, mid

In one line

An API gateway is the single entry point in front of microservices that routes client requests, can compose responses and centralises cross-cutting concerns (TLS, authentication, rate limiting, CORS, logging), hiding the internal topology; examples are Spring Cloud Gateway, Kong, NGINX, AWS API Gateway and Azure API Management.

Detailed explanation

Without a gateway, a web or mobile client would need to know the address of every service, call several of them for one screen, and each service would have to implement authentication, rate limiting and CORS itself. Moving services around or splitting one into two would break clients.

The gateway solves this by sitting at the edge:

  • Routing: /api/orders/ goes to the order service, /api/products/ to catalogue, based on path, host, headers or methods. Clients see one domain; the internal split can change freely.
  • Composition: it can aggregate a few calls into one response, though heavier client-specific aggregation belongs in a Backend-for-Frontend.
  • Security: TLS termination, validating OAuth2/JWT tokens, API keys, and passing identity downstream.
  • Traffic control: rate limiting and quotas per client, request size limits, IP allow lists, protection against abuse.
  • CORS handling, response caching, compression.
  • Observability: request logging, metrics, generating or forwarding correlation and trace ids.
  • Release techniques: canary and blue-green routing, header-based routing to test versions, API versioning (/v1, /v2).

Common products: Spring Cloud Gateway (Java, with WebFlux and WebMVC variants), Kong and Envoy-based gateways, NGINX, and managed services such as AWS API Gateway, Azure API Management and Google Apigee. On Kubernetes, ingress controllers and the Gateway API cover many of these features.

Two rules: the gateway must be highly available and scalable (several instances behind a load balancer) because everything passes through it, and it must stay free of business logic, otherwise every team depends on changing it and it becomes a new monolith. Services should still validate tokens themselves (defence in depth).

How it works

  1. Client calls https://api.shop.com/api/orders.
  2. Gateway terminates TLS and validates the JWT.
  3. Applies rate limit for the client.
  4. Matches the route; adds trace and user headers.
  5. Forwards to the order service via discovery; returns the response.

Example

spring:
  cloud:
    gateway:
      server:
        webflux:
          routes:
            - id: orders
              uri: lb://order-service
              predicates:
                - Path=/api/orders/**
              filters:
                - StripPrefix=1
                - name: RequestRateLimiter
                  args:
                    redis-rate-limiter.replenishRate: 20
                    redis-rate-limiter.burstCapacity: 40
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://login.shop.com/realms/shop

Common mistakes

  • Putting business logic or orchestration into the gateway.
  • Running a single gateway instance.
  • Relying only on the gateway for security.
  • Making the gateway team a bottleneck for every route change.

How to answer in the interview

"An API gateway is the single entry point for external clients in front of the microservices. It routes requests, like /api/orders to the order service, so clients do not need to know internal addresses or how services are split, and it can aggregate a few calls into one response. It also centralises cross-cutting concerns: TLS termination, token validation, rate limiting, CORS, logging, correlation ids and canary routing. Examples are Spring Cloud Gateway, Kong, NGINX, AWS API Gateway and Azure API Management. It must be highly available and kept free of business logic."

Likely follow-up questions

  • What is the Backend-for-Frontend pattern? A dedicated backend per client type that tailors and aggregates data for that UI.
  • Gateway vs load balancer? A load balancer distributes traffic; a gateway adds API-level routing, security and policies.
  • Gateway vs service mesh? The gateway handles edge (north-south) traffic, the mesh service-to-service (east-west) traffic.
