Pull requests are often blocked by flaky tests that fail randomly. How do you deal with them?

Azure DevOps & Pipelines · scenario · levels mid, senior

In one line

Treat flaky tests as a quality problem: detect them with test history and reruns, quarantine them with an owner, ticket and deadline, fix root causes (timing, shared state, external dependencies) and track the flaky rate, rather than adding retries everywhere.

Detailed explanation

A flaky test passes and fails on the same code. The real damage is cultural: once developers see random red builds, they click "rerun" by reflex and start ignoring genuine failures. Branch policies that require a green build then block pull requests for reasons unrelated to the change, slowing the whole team.

Detection comes first. Azure Pipelines Test Analytics shows pass rates and outcome history per test, and flaky test management can flag tests whose outcome changes without a code change, either detected by the system (for example when a rerun of a failing test passes) or marked manually. Flagged tests can be excluded from the pass percentage so they don't fail the build. A quick confirmation is to rerun the same commit several times, or loop a single test locally a few hundred times.

Quarantine is a deliberate, visible state: the test still runs and reports, but does not block merges. Each quarantined test has an owner, a work item and a deadline to fix or delete it, otherwise quarantine becomes a graveyard.

Root causes are usually: fixed sleep calls instead of waiting for a condition; shared state (static variables, a shared database, test order dependence); real external dependencies such as third-party APIs instead of mocks or Testcontainers; time, date and time-zone assumptions; random data without fixed seeds; and resource limits on agents. Sometimes the flakiness is a real race condition in the product, which is why automatic retries everywhere are dangerous: they hide bugs that will surface in production.

How it works

  1. Monitor Test Analytics and flaky-test flags; rerun the commit to confirm.
  2. Quarantine: tag or mark the test so it reports but doesn't gate the PR.
  3. Create a bug with owner and deadline; announce it in the team channel.
  4. Reproduce by looping the test, capture logs and timing.
  5. Fix the cause (condition-based waits, isolation, containers, fixed clock).
  6. Return it to the gating suite; track flaky rate per sprint.

Example

// Flaky: assumes the job finishes within 2 seconds
await Task.Delay(2000);
Assert.Equal("Done", await api.GetStatus(jobId));

// Stable: wait for a condition with a timeout
await WaitUntil(async () => await api.GetStatus(jobId) == "Done",
                timeout: TimeSpan.FromSeconds(30), poll: TimeSpan.FromMilliseconds(200));

[Trait("Category", "Quarantine")]   // excluded from the gating run: --filter "Category!=Quarantine"
public async Task Export_handles_large_file() { ... }

Common mistakes

  • Adding global retries (--retry 3) and declaring victory.
  • Quarantining tests without an owner, so they never return.
  • Deleting tests that actually caught an intermittent product bug.
  • Sharing one database between parallel test runs.

How to answer in the interview

"Flaky tests are dangerous because people stop trusting red builds. I'd use Azure Pipelines test analytics and flaky-test detection, plus reruns of the same commit, to identify them. Confirmed ones go into quarantine: they still run but don't block PRs, and each has an owner, a ticket and a deadline. Then we fix root causes: sleeps instead of condition waits, shared state, real external services instead of containers or mocks, and date or time-zone assumptions. Retries are at most a temporary bandage, because they can hide real race conditions. We track flaky rate as a team metric."

Likely follow-up questions

  • When is a flaky test a real bug? When it exposes a race, timeout or ordering issue that users could also hit under load.
  • How do you stop new flaky tests? Run new tests repeatedly in CI before merge and keep tests isolated by design.
  • Is a retry ever acceptable? For genuinely external, non-deterministic integration tests, with retries reported and counted.
