How do you version and roll out changes to an agent, such as new prompts, tools or models?

AI Agents & AIOps · concept · levels mid, senior

In one line

Version the whole agent configuration (prompts, tools, model, skills, policies) as one release, run the evaluation suite before release, roll out as a canary or percentage, let running tasks finish on their original version, compare SLOs between versions, and keep rollback fast.

Detailed explanation

An agent's behaviour emerges from many parts: the system prompt, tool definitions and their implementations, the model and its version, skills, retrieval settings, policies and limits such as maximum steps. Changing any one can change behaviour in surprising ways; a "small prompt tweak" can double tool calls, and a model upgrade can change how tools are chosen. So these parts are versioned together as one agent configuration, stored in Git, with a single version identifier recorded in every trace. Pin model versions explicitly rather than using floating aliases that can change underneath you.

Before release, the full evaluation suite runs: task success on a representative dataset, safety and policy tests, prompt injection tests, cost and step counts. Results must meet thresholds relative to the current version, not just absolute ones.

Rollout is gradual: internal users first, then a canary of a few percent of traffic or specific task types, with monitoring of success rate, steps per task, cost, escalation rate and safety signals compared side by side with the previous version. Long-running tasks that started on the old version finish on it, because switching prompts or tools mid-run can confuse the agent or break checkpoints whose state format changed. Rollback is a fast traffic switch to the previous configuration. Tool changes stay backward compatible during the transition, since both versions may call them at the same time.

How it works

  1. Change prompt, tool, model or policy in the agent config repo.
  2. CI runs evals and compares with the production version.
  3. Deploy as new version; route 5% of new runs to it.
  4. Compare metrics per version for a set period.
  5. Promote gradually or roll back by switching routing.
  6. Retire the old version after its in-flight runs finish.

Example

agent: support-agent
version: 2026.11.3
model: { provider: anthropic, name: claude-sonnet-4-5, temperature: 0.2 }
prompt: prompts/system@v41.md
tools: [orders.lookup@v3, refunds.create@v2, kb.search@v5]
skills: [refund-policy@1.4.0]
limits: { max_steps: 20, max_cost_usd: 0.40 }
rollout:
  stages: [internal, 5%, 25%, 100%]
  gates: { task_success_drop: "< 1pt", cost_increase: "< 10%", safety_violations: 0 }
  in_flight_runs: stay_on_original_version

Common mistakes

  • Changing prompts directly in production without versioning.
  • Floating model aliases that change silently.
  • Switching versions in the middle of long-running tasks.
  • Breaking tool schemas while old versions still call them.

How to answer in the interview

"I version everything that shapes behaviour, the prompt, tools, model version, skills and policies, as one agent configuration, and every trace records that version. Before release the evaluation suite has to match or beat the current version. Then I roll out gradually, internal users and a small percentage first, comparing success rate, steps, cost, escalations and safety signals between versions. Runs that started on the old version finish on it, tool changes stay backward compatible during the transition, and rollback is just switching traffic back."

Likely follow-up questions

  • Riskier: new model or new tool? Usually a new model, since it changes behaviour everywhere at once.
  • A/B vs canary? Canary for safety; A/B when comparing quality on equal traffic.
  • Prompt registries? Fine, if versions are immutable and referenced explicitly.
