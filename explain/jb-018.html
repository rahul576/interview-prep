Are Java objects always created on the heap? Explain escape analysis.

JVM & Performance · concept · levels mid, senior

In one line

Logically every object is on the heap, but the HotSpot JIT runs escape analysis on hot code and, for objects that do not escape the method or thread, can apply scalar replacement (no heap allocation at all) and lock elision; it reduces GC pressure but is an optimisation, not a guarantee.

Detailed explanation

The Java language and JVM specification describe objects as heap-allocated and garbage collected. You cannot request stack allocation. But the specification only defines observable behaviour, so the JIT may do anything that gives the same results.

Escape analysis is performed by the C2 compiler (and Graal) on hot, compiled methods, after inlining. For each allocation it determines how far the object's reference can travel:

  • No escape: the object is only used inside the compiled method, including inlined callees.
  • Argument escape: passed to a method that is not inlined, but not stored globally.
  • Global escape: returned, stored in a field or static, put into a collection, passed to another thread or to unknown code.

For non-escaping objects HotSpot uses scalar replacement: rather than allocating the object, it treats each field as a separate local variable held in registers or stack slots. The object never exists on the heap, so no allocation cost, no GC work. HotSpot does not literally allocate objects on the stack; it eliminates them. GraalVM adds partial escape analysis, which handles objects that escape only on some branches.

Lock elision: if a synchronized block locks an object no other thread can see, such as a local StringBuffer, the lock is removed.

Limits. It only applies after JIT compilation, so not during warm-up or in the interpreter. It depends on inlining: a call to a large or megamorphic method that is not inlined makes objects escape. Arrays that are large or of unknown length, objects merged from different branches into one variable (in C2), and objects stored in fields or collections are not replaced. It is on by default (-XX:+DoEscapeAnalysis). So write clear code, but never rely on it for correctness or as the main memory strategy.

How it works

  1. Method becomes hot and is compiled by C2.
  2. Callees are inlined into it where possible.
  3. Escape analysis classifies each allocation.
  4. Non-escaping objects are scalar-replaced; their fields become locals.
  5. Locks on non-escaping objects are removed.
  6. Escaping objects are allocated on the heap normally.

Example

record Point(int x, int y) {}

int distanceSquared(int x1, int y1, int x2, int y2) {
    Point a = new Point(x1, y1);          // does not escape
    Point b = new Point(x2, y2);          // does not escape
    int dx = a.x() - b.x(), dy = a.y() - b.y();
    return dx * dx + dy * dy;             // after C2: no Point objects allocated
}

Point last;
Point keep(int x, int y) {
    Point p = new Point(x, y);
    last = p;                             // global escape: heap allocation
    return p;
}

String join(String a, String b) {
    StringBuffer sb = new StringBuffer();  // synchronized methods, but local:
    return sb.append(a).append(b).toString(); // locks elided
}
# Compare allocation with and without EA in a JMH benchmark
java -XX:-DoEscapeAnalysis -jar benchmarks.jar -prof gc

Common mistakes

  • Saying "Java allocates small objects on the stack".
  • Expecting escape analysis in the interpreter or during warm-up.
  • Benchmarking without JMH, so the optimisation (or dead-code elimination) distorts results.
  • Designing APIs around assumed escape analysis.

How to answer in the interview

"From the language point of view every object is created on the heap. In practice the HotSpot C2 compiler runs escape analysis on hot code after inlining: it checks whether an object escapes the method or thread, for example by being returned, stored in a field or passed to code that isn't inlined. If it doesn't escape, the JIT can apply scalar replacement, breaking the object into its fields held in registers or stack slots, so there's no heap allocation at all. It can also elide locks on objects only one thread can see. That reduces allocation and GC pressure, but it only happens after warm-up, depends on inlining and is never guaranteed."

Likely follow-up questions

  • Which coding patterns stop escape analysis from working? Storing objects in fields or collections, returning them, passing them to non-inlined or megamorphic methods, and very large methods that defeat inlining.
  • What is partial escape analysis? Graal's variant that removes allocations on paths where the object does not escape.
  • How do you verify it happens? JMH with -prof gc showing allocated bytes per operation near zero.
