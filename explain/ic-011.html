What are Terraform workspaces, and when are they a good or bad idea?

Infrastructure as Code · concept · levels entry

In one line

CLI workspaces give one configuration several state files (terraform workspace new/select, terraform.workspace); they suit identical, short-lived copies, but separate directories/backends are safer for long-lived environments like dev and prod.

Detailed explanation

By default a configuration has one state, in the default workspace. terraform workspace new feature-x creates another, independent state in the same backend (for S3, under an env:/ prefix), and terraform workspace select switches between them. Inside the code, terraform.workspace returns the current name, often used in resource names or to look up settings.

They work well for identical, short-lived stacks: an environment per feature branch or per developer, a test copy spun up and destroyed by CI. The code is the same, only the state differs, and cleanup is terraform destroy plus workspace delete.

They are a poor fit for long-lived environments that differ. All workspaces share the same code version, backend, and usually the same credentials, so you cannot easily give prod stricter access or deploy a new code version to dev first. Differences end up as conditionals on terraform.workspace scattered through the code. Worst of all, the active workspace is invisible state on your machine, so it is easy to run apply in the wrong one. For dev, staging and prod I prefer separate root modules or directories, each with its own backend configuration, variables, credentials and pipeline, sharing logic through versioned modules.

HCP Terraform workspaces are a different concept: each has its own state, variables, permissions, run history and optionally its own VCS branch or directory, so they behave more like separate root configurations.

How it works

  1. terraform workspace new <name> creates an empty state.
  2. terraform workspace select <name> switches the active state.
  3. Plans and applies operate only on the selected workspace's state.
  4. terraform.workspace exposes the name to expressions.
  5. terraform workspace delete removes an empty workspace.

Example

terraform workspace new pr-1423
terraform apply -var-file=preview.tfvars
terraform workspace show        # pr-1423
terraform destroy && terraform workspace select default && terraform workspace delete pr-1423
resource "aws_s3_bucket" "assets" {
  bucket = "shop-assets-${terraform.workspace}"
}

Preferred layout for long-lived environments:

envs/dev/main.tf      backend: state/dev.tfstate   role: tf-dev
envs/prod/main.tf     backend: state/prod.tfstate  role: tf-prod
modules/app/          shared, versioned

Common mistakes

  • Using workspaces for dev and prod with identical credentials.
  • Forgetting which workspace is selected and applying to the wrong one.
  • Heavy terraform.workspace == "prod" ? ... : ... logic everywhere.
  • Confusing CLI workspaces with HCP Terraform workspaces.

How to answer in the interview

"CLI workspaces let a single configuration have multiple independent states. I create them with terraform workspace new, switch with select, and terraform.workspace gives the name for resource naming. They're great for identical, short-lived copies, like a preview environment per pull request. For long-lived environments like dev and prod that differ in size, settings and access, they're risky: everything shares the backend, credentials and code version, and it's easy to apply to the wrong one. For those I use separate directories or root modules, each with its own backend, role and pipeline."

Likely follow-up questions

  • How do HCP Terraform workspaces differ? Each is a full unit with its own state, variables, permissions and runs.
  • Where does S3 store workspace states? Under the env:/<workspace>/ prefix by default (workspace_key_prefix).
  • How do you avoid wrong-workspace applies? Pipelines select explicitly; show the workspace in the prompt.
