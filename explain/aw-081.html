How would you design an AWS landing zone for a growing company?

Cloud (AWS) · design · levels lead

In one line

A landing zone uses AWS Organizations with OUs (Security, Infrastructure, Workloads prod/non-prod, Sandbox), built with Control Tower or IaC such as Landing Zone Accelerator, foundational log archive, security tooling and network accounts, IAM Identity Center SSO with permission sets, guardrail SCPs, a Transit Gateway hub and automated account vending.

Detailed explanation

Multi-account is the AWS best practice: accounts are the strongest isolation boundary for security, quotas, billing and blast radius. The landing zone is the pre-configured, governed foundation they live in.

Structure: the management account only handles billing, Organizations and Control Tower, with no workloads. A Security OU holds the log archive account (immutable CloudTrail, Config and flow logs) and the security tooling account (delegated admin for GuardDuty, Security Hub, Inspector, Macie, Access Analyzer, Detective). An Infrastructure OU holds a network account with Transit Gateway, central egress and inspection, Route 53 Resolver rules and IPAM, plus shared services like CI/CD tooling and container registries. Workloads OUs split production and non-production, and a Sandbox OU gives developers experimental accounts with budgets and auto-cleanup. A Suspended OU parks closed accounts.

Build: Control Tower sets up the OUs, foundational accounts, organisation CloudTrail, Config and preventive, detective and proactive controls, and its Account Factory (or Account Factory for Terraform) vends accounts. Landing Zone Accelerator or custom Terraform/CDK pipelines add more customisation. Everything is code, versioned and reviewed.

Identity: IAM Identity Center federates with the corporate IdP (Entra ID, Okta, Google) via SAML and SCIM; groups map to permission sets like ReadOnly, Developer and Admin per account. No IAM users. Break-glass access is documented and monitored.

Guardrails and baseline: SCPs (deny region use, disabling security services, leaving the org, root actions), RCPs, tag policies and backup policies. Each vended account gets VPCs from IPAM attached to Transit Gateway, logging, security services, budgets and SSO assignments in minutes.

How it works

  1. Create the organisation and management account; enable Control Tower.
  2. Define OUs and foundational accounts.
  3. Connect IAM Identity Center to the IdP; define permission sets.
  4. Deploy network hub, IPAM and DNS in the network account.
  5. Apply SCPs and controls per OU.
  6. Vend workload accounts with the baseline through a pipeline.

Common mistakes

  • Running workloads in the management account.
  • One giant shared account for all environments.
  • Overlapping CIDRs because nobody owns IP allocation.
  • Manual account creation that drifts from the baseline.

How to answer in the interview

"I would use AWS Organizations, usually set up with Control Tower or Landing Zone Accelerator, with OUs for security, infrastructure, workloads split into prod and non-prod, and sandboxes. Foundational accounts are a management account for billing and org settings only, a log archive for CloudTrail and Config, a security tooling account as delegated admin for GuardDuty and Security Hub, and a network account with Transit Gateway, central egress and DNS. People sign in via IAM Identity Center connected to the corporate IdP with permission sets. SCPs enforce guardrails, and account vending creates new accounts with the baseline in minutes."

Likely follow-up questions

  • Why give each workload and environment its own account? Strong isolation of security, quotas and cost, and a small blast radius.
  • Control Tower or custom? Control Tower for speed and managed controls; custom IaC when you need full flexibility.
  • How handle break-glass access? A few locked-down IAM users or root with hardware MFA, alerts on every use.
