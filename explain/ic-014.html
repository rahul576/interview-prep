What does idempotency mean in infrastructure as code and configuration management?

Infrastructure as Code · concept · levels entry

In one line

Idempotency means applying the same code repeatedly yields the same end state: the first run converges the system, later runs change nothing; Terraform shows no changes, Ansible reports ok instead of changed.

Detailed explanation

Infrastructure as code and configuration management are declarative: you describe the desired state, and the tool works out what to do. Idempotency is the property that makes this safe. The first run makes whatever changes are needed; a second run finds that reality already matches the description and does nothing.

Terraform achieves it by comparing three things: the configuration, the state and the real infrastructure (via refresh). If they agree, terraform plan reports "No changes. Your infrastructure matches the configuration." A plan that is never empty, a perpetual diff, usually indicates a provider quirk, ordering differences in a list or something outside Terraform changing values.

Ansible modules are written to check the current state before acting: ansible.builtin.package with state: present only installs if the package is missing, lineinfile only adds a line if it is absent. Results are reported as ok (already correct) or changed, and a second run of a good playbook shows changed=0.

Why it matters: you can rerun safely after a failure halfway, without worrying about duplicating work; you can run configuration on a schedule to correct drift; and "changed" becomes a meaningful signal that triggers handlers such as service restarts. The usual sources of non-idempotent behaviour are raw shell commands: echo "x" >> file appends every time, useradd fails the second time, a download step runs on every run. The fix is to use proper modules or add guards like creates, changed_when and checks.

How it works

  1. Read the current state of each resource or setting.
  2. Compare it with the desired state in code.
  3. Act only on differences.
  4. Report what changed.
  5. A second run finds no differences and makes no changes.

Example

# Not idempotent: appends a line every run
- name: Add JVM option
  ansible.builtin.shell: echo "-Xmx2g" >> /etc/app/jvm.options

# Idempotent: ensures the line exists exactly once
- name: Add JVM option
  ansible.builtin.lineinfile:
    path: /etc/app/jvm.options
    line: "-Xmx2g"
ansible-playbook site.yml   # changed=3
ansible-playbook site.yml   # changed=0
terraform plan              # No changes. Your infrastructure matches the configuration.

Common mistakes

  • Using shell or command where a module exists.
  • Tasks that always report changed, triggering needless restarts.
  • Ignoring perpetual diffs in Terraform plans.
  • Treating "it ran without errors" as proof of idempotency instead of running twice.

How to answer in the interview

"Idempotency means running the same code again gives the same end state: the first run makes the needed changes, later runs change nothing because the system already matches. Terraform does it by comparing configuration, state and real infrastructure, so a second plan says no changes. Ansible modules check current state first and report ok instead of changed. That's what makes it safe to rerun after a failure halfway or on a schedule to fix drift. Raw shell commands are the usual offenders, like appending to a file every run, so I prefer modules or add guards like creates and changed_when."

Likely follow-up questions

  • How would you make an Ansible shell task idempotent? Use creates/removes, a check task with register and when, and changed_when.
  • How do you test idempotency? Run twice in CI (Molecule's idempotence step) and fail if anything changes.
  • What causes perpetual Terraform diffs? Provider normalisation issues, unordered lists, or external changes.
