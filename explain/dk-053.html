How do you handle configuration files for containers across environments?

Docker · concept · levels mid

In one line

Build one image for all environments and inject configuration at runtime: environment variables for simple settings, mounted files (bind mounts, Docker configs, Kubernetes ConfigMaps) for structured config, secrets separately, optional templating at start-up, and validation with fail-fast.

Detailed explanation

The twelve-factor principle of separating config from code is essential for containers. If you build a different image per environment, the image tested in staging is not the one deployed to production, and promotion becomes rebuilding. So the image contains the application and sensible defaults, and everything that differs, such as URLs, feature flags, log levels and credentials, is supplied when the container starts.

Environment variables suit simple key-value settings: SPRING_PROFILES_ACTIVE=prod, LOG_LEVEL=info, DB_HOST=db.prod. Most frameworks map them to configuration automatically. For larger or structured configuration, such as nginx.conf, application.yml or a JSON rules file, mount a file: a bind mount on a single host or Compose, a Docker config in Swarm, or a ConfigMap in Kubernetes mounted as a volume. Files are easier to review, can be reloaded by some apps without restart, and avoid huge environment blocks.

Secrets are handled separately because they need encryption, access control and rotation: Docker secrets in Swarm or Compose, Kubernetes Secrets (ideally encrypted at rest, or synced from Vault, AWS Secrets Manager or Azure Key Vault via the Secrets Store CSI driver or External Secrets Operator). Mount them as files with restrictive permissions rather than environment variables, which leak into docker inspect, crash dumps and child processes.

When a third-party app only reads a static file, an entrypoint can render a template with envsubst or a tool like gomplate. Finally, the application should validate configuration at start-up and fail fast with a clear message, instead of failing on the first request.

How it works

  1. Build a single image with defaults.
  2. Define per-environment values in Compose overrides, Helm values or Kustomize overlays.
  3. Inject env vars and mount config files at start.
  4. Mount secrets from a secret store.
  5. App validates config and refuses to start if invalid.

Example

# Kubernetes
apiVersion: v1
kind: ConfigMap
metadata: { name: orders-config }
data:
  application.yml: |
    orders:
      max-items: 50
---
spec:
  containers:
    - name: orders
      image: ghcr.io/acme/orders@sha256:<digest>
      env:
        - { name: SPRING_PROFILES_ACTIVE, value: prod }
      volumeMounts:
        - { name: config, mountPath: /config, readOnly: true }
        - { name: db-secret, mountPath: /run/secrets/db, readOnly: true }
  volumes:
    - name: config
      configMap: { name: orders-config }
    - name: db-secret
      secret: { secretName: orders-db, defaultMode: 0400 }

Common mistakes

  • Baking environment-specific config or secrets into the image.
  • Secrets in plain environment variables committed to Compose files.
  • No validation, so a typo only surfaces under traffic.
  • Changing ConfigMaps without rolling pods, so apps never pick up changes.

How to answer in the interview

"The rule is one image for every environment with configuration injected at runtime, so what was tested is exactly what runs in production. Simple settings come from environment variables. Larger structured config like nginx.conf or application.yml is mounted as a file: a bind mount on a single host, a Docker config in Swarm or a ConfigMap in Kubernetes. Secrets are handled separately through Docker or Kubernetes secrets or an external vault, mounted as files with restricted permissions. If a file needs env-specific values, the entrypoint renders a template with envsubst, and the app validates config at startup and fails fast."

Likely follow-up questions

  • Why never bake env config into the image? It breaks build-once-promote and can leak secrets.
  • Env vars vs files for secrets? Files are less likely to leak via inspect, logs or child processes.
  • How do apps pick up ConfigMap changes? Mounted files update eventually; env vars need a restart, often triggered by a checksum annotation.
