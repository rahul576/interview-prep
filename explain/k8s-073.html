Your EKS or AKS cluster cannot schedule new pods because the subnet ran out of IP addresses. What do you do?

Kubernetes · scenario · levels senior, lead

In one line

With EKS VPC CNI or classic Azure CNI, every pod takes a real subnet IP (plus warm IPs), so subnets run out; short term, tune warm IP settings, add secondary CIDRs / new subnets or enable prefix delegation; long term, move to an overlay (Azure CNI Overlay, Cilium overlay) and plan IP space for growth.

Detailed explanation

VPC-native CNIs give pods routable IPs from the VPC or VNet, which is great for performance and for security groups or firewall rules that see pod IPs directly. The cost is address consumption. On EKS, the VPC CNI attaches ENIs to nodes and keeps a pool of warm IPs (by default a whole spare ENI's worth) per node so pods start quickly. A /24 subnet with 251 usable addresses fills up after a handful of busy nodes. Classic Azure CNI pre-allocates maxPods IPs per node (30 by default) from the subnet at node creation, whether used or not. Symptoms: pods stuck in ContainerCreating with failed to assign an IP address, or new nodes failing to join.

Short-term on EKS: tune WARM_IP_TARGET and MINIMUM_IP_TARGET instead of WARM_ENI_TARGET to stop hoarding; enable prefix delegation, which assigns /28 prefixes per ENI slot and raises pod density, though it needs contiguous free space in the subnet; and add a secondary CIDR (for example from 100.64.0.0/10) to the VPC with custom networking (ENIConfig per zone) so pods use new subnets separate from node subnets. On AKS: add node pools in new subnets, or use Azure CNI with dynamic pod IP allocation (separate pod subnet).

Long-term: an overlay mode gives pods addresses from a private range not allocated in the VNet. Azure CNI Overlay is the recommended AKS default for most clusters; on EKS, options include Cilium in overlay mode or IPv6 clusters where address exhaustion disappears. Overlays trade away direct routability of pod IPs from outside the cluster.

Finally, IP planning belongs in cluster design: maximum nodes times pods per node, upgrade surge nodes, and future clusters in the same network.

How it works

  1. Confirm IP exhaustion from pod events and subnet free IP metrics.
  2. Reduce waste: warm IP targets or lower maxPods where appropriate.
  3. Add capacity: secondary CIDR with custom networking, new subnets or node pools.
  4. Consider prefix delegation for density.
  5. Plan migration to overlay or IPv6 for new clusters.
  6. Document an IP plan including upgrade surge.

Example

aws ec2 describe-subnets --subnet-ids subnet-0a1b --query 'Subnets[].AvailableIpAddressCount'
kubectl -n kube-system set env daemonset/aws-node WARM_IP_TARGET=5 MINIMUM_IP_TARGET=10
kubectl -n kube-system set env daemonset/aws-node ENABLE_PREFIX_DELEGATION=true

# AKS new cluster with overlay
az aks create -n prod2 -g rg-prod --network-plugin azure --network-plugin-mode overlay --pod-cidr 192.168.0.0/16

Common mistakes

  • Small /24 node subnets for production clusters.
  • Forgetting surge nodes during upgrades need IPs.
  • Enabling prefix delegation on fragmented subnets.
  • Overlapping pod CIDRs with on-premises ranges.

How to answer in the interview

"With the VPC CNI on EKS or classic Azure CNI, each pod gets a real IP from the node subnet and nodes reserve warm IPs, so busy clusters run out. Short term I'd tune warm IP targets, then add capacity: on AWS a secondary CIDR with custom networking or prefix delegation; on AKS new node pools in new subnets or a dynamic pod subnet. Long term, an overlay mode such as Azure CNI Overlay or Cilium overlay gives pods a separate range that isn't routed in the VNet, which removes the pressure. And I'd add IP capacity planning, including upgrade surge, to cluster design."

Likely follow-up questions

  • What do you lose with an overlay? Pods are not directly reachable from the VNet; traffic is SNATed to node IPs, so external firewalls see node IPs.
  • Why does upgrade surge matter? New nodes are added before old ones drain, temporarily needing extra IPs.
  • Does IPv6 solve it? Yes for address space, but all dependencies must support IPv6.
