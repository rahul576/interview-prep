Some replicas of a Deployment keep failing their health checks and restarting while others are fine. How do you find the root cause and fix it?

Kubernetes · scenario · levels mid, senior

In one line

When only some replicas fail health checks, compare failing versus healthy pods: read probe failure events and restart reasons, check previous logs, verify probe configuration, look for CPU throttling or OOMKills, and look for a common node, version or dependency.

Detailed explanation

If all replicas failed, I would suspect the code or configuration. Partial failure points to something that differs between pods, so the investigation is a comparison.

kubectl get pods -o wide shows restart counts and nodes; if failing pods cluster on one node, suspect that node (network, disk, noisy neighbour). kubectl describe pod shows events like Liveness probe failed: Get "http://10.2.3.4:8080/healthz": context deadline exceeded or HTTP probe failed with statuscode: 500, and Last State: Terminated, Reason: OOMKilled or Error, Exit Code 137. kubectl logs --previous shows what the crashed container said before dying.

Probe configuration: right path and port, timeoutSeconds not too short (default 1 second), sensible failureThreshold and periodSeconds. Slow starters like JVM services need a startup probe, otherwise liveness kills them mid-start, especially on busier nodes where startup is slower.

Resources: pods on busy nodes, or with tight CPU limits, get CFS throttling, respond slowly and fail probes; those over their memory limit are OOMKilled. Compare image tags too: during a stuck rollout, half the pods may run a new, broken version. Check configuration and dependencies: if liveness calls a slow database, pods restart for a problem that restarting cannot fix, which is why liveness should not check dependencies. If a recent rollout caused it, kubectl rollout undo is the quick escape while you investigate.

How it works

  1. List pods with nodes, restarts and image versions.
  2. Describe failing pods: probe events and last termination reason.
  3. Read current and previous logs.
  4. Verify probe settings and add a startup probe where needed.
  5. Check throttling and memory metrics per pod.
  6. Compare nodes, versions, config and dependencies; fix or roll back.

Example

kubectl get pods -l app=search -o custom-columns=NAME:.metadata.name,NODE:.spec.nodeName,RESTARTS:.status.containerStatuses[0].restartCount,IMAGE:.spec.containers[0].image
kubectl describe pod search-5f7c-xk2 | grep -E "Last State|Reason|Exit Code|probe failed"
kubectl logs search-5f7c-xk2 --previous | tail -50
kubectl rollout undo deploy/search   # if a recent rollout is the common factor

Common mistakes

  • Increasing timeouts blindly without finding why responses are slow.
  • Reading only current logs and missing the crash in --previous.
  • Liveness probes that check databases or other services.
  • Ignoring that failing pods share a node or image version.

How to answer in the interview

"Because only some replicas fail, I look for what differs. kubectl get pods -o wide shows restarts and nodes, describe shows the probe failure events and last termination reason, such as a timeout, a 500 or OOMKilled, and logs --previous shows what the crashed container said. I check the probe configuration, path, port, timeouts and thresholds, and add a startup probe for slow starters. Then resources: CPU throttling makes pods slow to answer probes and memory limits cause OOMKills. I compare node, image version, config and dependencies, and if a recent rollout is the cause I roll back first."

Likely follow-up questions

  • Why should liveness not check downstream dependencies? Restarting your pod cannot fix the database, and it restarts every replica at once.
  • What does exit code 137 mean? The process got SIGKILL, often from the OOM killer.
  • How do you spot CPU throttling? container_cpu_cfs_throttled_periods_total relative to total periods.
