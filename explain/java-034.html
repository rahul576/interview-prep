Explain the transaction isolation levels and the anomalies each one prevents.

Databases & SQL · concept · levels mid, senior

In one line

The SQL standard levels, from weakest to strongest: Read Uncommitted (allows dirty reads), Read Committed (prevents dirty reads), Repeatable Read (also prevents non-repeatable reads) and Serializable (prevents phantoms and all anomalies, as if transactions ran one by one); real databases implement them differently, mostly with MVCC.

Detailed explanation

Isolation controls what concurrent transactions can see of each other's work. Stronger isolation means fewer anomalies but more blocking, aborts and retries.

Anomalies:

  • Dirty read: reading another transaction's uncommitted change, which may roll back.
  • Non-repeatable read: reading the same row twice and getting different values because another transaction committed an update in between.
  • Phantom read: re-running a range query and getting new or missing rows because another transaction inserted or deleted matching rows.
  • Lost update: two transactions read the same value, both modify and write, and one write overwrites the other.
  • Write skew: two transactions read overlapping data and write different rows based on it, together violating a constraint (classic: two doctors both going off call).

Levels:

  • Read Uncommitted: dirty reads possible. PostgreSQL treats it as Read Committed.
  • Read Committed: each statement sees only committed data as of the statement's start. Default in PostgreSQL, Oracle and SQL Server.
  • Repeatable Read: rows you've read don't change. The standard still permits phantoms, but PostgreSQL implements it as snapshot isolation (one snapshot for the whole transaction, no phantoms, and concurrent updates of the same row abort with a serialization error). MySQL InnoDB defaults to Repeatable Read, using a consistent snapshot for plain reads and next-key (gap) locks for locking reads and writes, which prevents most phantoms.
  • Serializable: the result equals some serial order. PostgreSQL uses Serializable Snapshot Isolation (SSI), aborting conflicting transactions; others use stricter locking. Applications must retry on serialization failures (SQLSTATE 40001).

Lost updates are often handled without raising the level: optimistic locking with a version column (JPA @Version, which throws OptimisticLockException when the version changed), pessimistic locking with SELECT ... FOR UPDATE, or atomic updates (UPDATE ... SET stock = stock - 1 WHERE stock > 0).

In Spring: @Transactional(isolation = Isolation.REPEATABLE_READ); the default uses the database's default.

How it works

  1. With MVCC, each row version records the creating and deleting transaction.
  2. A transaction reads from a snapshot: per statement (Read Committed) or per transaction (Repeatable Read/Snapshot).
  3. Writers create new versions; readers aren't blocked.
  4. Write-write conflicts are resolved with row locks, and at higher levels by aborting one transaction.
  5. Serializable additionally tracks read/write dependencies (SSI) or uses range locks.

Example

-- Session A (READ COMMITTED)
BEGIN;
SELECT balance FROM account WHERE id = 1;   -- 100
-- Session B: UPDATE account SET balance = 50 WHERE id = 1; COMMIT;
SELECT balance FROM account WHERE id = 1;   -- 50  (non-repeatable read)
COMMIT;
@Entity class Account {
    @Id Long id;
    BigDecimal balance;
    @Version long version;        // optimistic locking prevents lost updates
}

@Transactional(isolation = Isolation.SERIALIZABLE)
@Retryable(retryFor = CannotAcquireLockException.class, maxAttempts = 3)
public void allocateShift(...) { ... }

Common mistakes

  • Assuming every database behaves exactly per the standard table.
  • Using Serializable without retry logic.
  • Believing Read Committed prevents lost updates.
  • Forgetting long transactions at high isolation increase contention and bloat.

How to answer in the interview

"Read uncommitted allows dirty reads. Read committed prevents them, but a row read twice can change, a non-repeatable read. Repeatable read guarantees rows I've read don't change, though by the standard new matching rows, phantoms, can still appear. Serializable behaves as if transactions ran one after another, at the cost of locking or serialization failures that must be retried. Defaults differ: PostgreSQL, Oracle and SQL Server use read committed, MySQL InnoDB uses repeatable read with MVCC snapshots and next-key locks. For lost updates I usually use optimistic locking with @Version rather than raising the isolation level."

Likely follow-up questions

  • What is a lost update, and how do optimistic locking and @Version prevent it? Two writers overwrite each other; @Version makes the second update fail because the version changed.
  • What is write skew? Two transactions write different rows based on the same read, breaking an invariant; prevented by Serializable.
  • What is MVCC? Keeping multiple row versions so readers see a snapshot without blocking writers.
