What are database sharding strategies, and what problems does sharding introduce?

Data & Storage Design · concept · levels entry, mid, senior

In one line

Sharding splits data across databases by a shard key (hash, range or directory); it scales writes and storage but makes cross-shard queries, transactions, resharding and hot keys hard.

Detailed explanation

When one primary can't handle the writes or the data size, you partition rows across several databases. The shard key decides everything: it must spread load evenly and keep data that is queried together on the same shard.

  • Hash sharding: shard = hash(user_id) % N (better: consistent hashing or many logical shards). Even load; range scans hit all shards.
  • Range sharding: by key ranges (A–F, G–M…) or time. Efficient range scans; risk of hot spots (all new writes go to the newest range).
  • Directory sharding: a lookup table maps tenant → shard. Flexible (move a big tenant to its own shard) but the directory must be highly available and cached.

How it works

  1. Pick a shard key aligned with the main access pattern (tenant_id, user_id).
  2. Create many logical shards (e.g. 1,024) mapped to fewer physical servers, so rebalancing moves logical shards.
  3. Route queries via an application library, a proxy (Vitess, Citus) or the database itself.
  4. Avoid cross-shard transactions; use sagas when unavoidable.
  5. Monitor per-shard load to catch hot keys.

Example

SaaS app: shard by tenant_id. All of a tenant's orders, users and invoices sit on one shard, so joins and transactions stay local. A global "admin report across all tenants" uses a data warehouse fed by CDC, not live cross-shard queries.

Common mistakes

  • Sharding too early.
  • Sharding by a low-cardinality key (country) or a monotonic key (timestamp).
  • No plan for resharding.
  • Ignoring celebrity tenants that outgrow a shard.

How to answer in the interview

"I'd shard by the key that matches the main access pattern, here tenant ID, so each tenant's transactions stay on one shard. I'd use many logical shards mapped to physical nodes so I can rebalance by moving logical shards. Cross-tenant analytics go to a warehouse, and very large tenants can be moved to dedicated shards via the directory."

Likely follow-up questions

  • How do you reshard with no downtime? Dual-write or CDC copy to the new layout, verify, switch reads, then writes.
  • How do you generate IDs across shards? Snowflake-style IDs or UUIDv7.
  • What about global unique constraints (email)? A separate lookup table or service keyed by the unique value.
