Pods on the same node can talk to each other, but pods on different nodes cannot. How do you troubleshoot it?

Kubernetes · scenario · levels mid, senior

In one line

Same-node traffic working means pod networking on each node is fine, so the fault is between nodes: a broken CNI agent, firewall or security group rules blocking the overlay (VXLAN, Geneve, BGP) or pod CIDR routes, or an MTU mismatch; isolate it with ping, curl and tcpdump on both nodes.

Detailed explanation

Pods on one node talk through a local bridge or eBPF path that never leaves the host. Cross-node traffic must be carried between hosts, either encapsulated in an overlay (VXLAN, Geneve, IP-in-IP) or natively routed, where the network must know which node owns each pod CIDR (cloud route tables, BGP peering or VPC-native IPs). Different CNIs, same principle.

CNI health: check the CNI DaemonSet pods (calico-node, cilium, kube-flannel) are running and ready on every node; read their logs for errors like failed BGP sessions, missing tunnel devices or IPAM failures. cilium status or calicoctl node status give quick summaries.

Firewalls: overlays need specific ports open between nodes: VXLAN typically UDP 4789 (Calico, Cilium default 8472 as in Flannel), Geneve UDP 6081, Calico IP-in-IP uses IP protocol 4, BGP TCP 179, WireGuard encryption has its own UDP ports. A new security group, NSG or on-premises firewall rule that only allows node-port traffic breaks pod-to-pod across nodes. With native routing, check the cloud route table or BGP advertisements, and source/destination checks on cloud instances.

MTU: encapsulation adds headers (about 50 bytes for VXLAN). If pod MTU equals the node MTU, large packets exceed it and are dropped, especially when ICMP "fragmentation needed" is blocked. Symptoms are strange: ping and small HTTP requests work, but TLS handshakes or large responses hang.

How it works

  1. Confirm: same-node pod-to-pod OK, cross-node fails (ping, curl by pod IP).
  2. Check CNI pods and logs on both nodes.
  3. Verify firewall/security group rules for overlay protocol and ports.
  4. With native routing, check routes and BGP sessions.
  5. Test MTU with large non-fragmenting pings.
  6. tcpdump on both nodes' interfaces to see where packets vanish.

Example

kubectl get pods -n kube-system -o wide -l k8s-app=cilium
kubectl exec -it netshoot-a -- ping -c3 10.244.2.15          # pod on other node
kubectl exec -it netshoot-a -- ping -c3 -M do -s 1400 10.244.2.15   # MTU test
# on source and destination nodes
sudo tcpdump -ni eth0 udp port 8472

Common mistakes

  • Debugging Services and DNS before raw pod-IP connectivity.
  • Firewall rules updated for nodes but not for overlay traffic.
  • Ignoring MTU because ping works.
  • Mixing CNI versions or configs across node pools.

How to answer in the interview

"If same-node traffic works but cross-node doesn't, the pod interfaces are fine and the problem is the path between nodes, the overlay tunnel or pod CIDR routing. I'd check the CNI pods are healthy on every node and read their logs. Then firewalls and security groups: overlays need ports like UDP 4789 or 8472 for VXLAN, BGP needs TCP 179, and native routing needs pod CIDR routes. MTU mismatch is a classic: ping works but large packets are dropped because of encapsulation headers, so TLS hangs. I'd test with pings of different sizes and tcpdump on both nodes to see where packets disappear."

Likely follow-up questions

  • Why do small requests work but large responses hang with bad MTU? Small packets fit; large ones exceed MTU and are dropped, often silently when ICMP is blocked.
  • Overlay vs native routing? Overlay works anywhere but adds overhead; native routing is faster but needs network integration.
  • How does Cilium help debugging? Hubble shows flows and drop reasons per packet.
