What is reserved concurrency in AWS Lambda?

Cloud (AWS) · concept · levels mid

In one line

Reserved concurrency sets aside a number of concurrent executions for one function from the regional account pool and simultaneously caps the function at that number; setting it to 0 disables the function; it is free and different from provisioned concurrency, which pre-initialises instances to avoid cold starts and costs money; for SQS triggers, maximum concurrency on the event source mapping is usually preferred.

Detailed explanation

All Lambda functions in a region share the account's concurrency quota (1,000 by default). Without controls, one busy function can consume it all and starve others, and one function can overwhelm whatever it calls.

Reserved concurrency solves both:

  • Guarantee: reserving 100 for the payments function means those 100 are always available to it; other functions cannot use them.
  • Cap: the payments function can never exceed 100 concurrent executions. Excess invocations are throttled (HTTP 429 for synchronous calls; retried for async and stream or queue sources).
  • Kill switch: reserved concurrency 0 stops all invocations immediately, useful during incidents.
  • No charge. But reserved capacity reduces the unreserved pool for other functions (AWS keeps at least 100 unreserved).

Provisioned concurrency keeps a set number of execution environments initialised and warm, eliminating cold starts for that number of concurrent requests. It is billed while configured, and is applied to a version or alias. It can be scheduled or auto-scaled with Application Auto Scaling. For Java, SnapStart is often a cheaper alternative.

With SQS: reserved concurrency limits invocations, but the event source mapping keeps polling; messages that cannot be invoked are throttled and returned, and their receive count increases, which can push them into the DLQ without ever being processed. Maximum concurrency on the ESM limits polling itself, avoiding this. You can use both, with maximum concurrency at or below reserved concurrency.

How it works

  1. Decide the safe concurrency for the function and its downstreams.
  2. Set reserved concurrency to guarantee and cap it.
  3. For SQS triggers, set maximum concurrency on the mapping.
  4. Add provisioned concurrency only for latency-sensitive paths.
  5. Monitor Throttles and ConcurrentExecutions.

Example

aws lambda put-function-concurrency --function-name payments \
  --reserved-concurrent-executions 20        # guarantee and cap at 20

aws lambda put-function-concurrency --function-name payments \
  --reserved-concurrent-executions 0         # emergency stop

aws lambda put-provisioned-concurrency-config --function-name checkout-api \
  --qualifier live --provisioned-concurrent-executions 10   # warm instances, billed

Common mistakes

  • Confusing reserved with provisioned concurrency.
  • Using reserved concurrency as the only throttle for an SQS trigger.
  • Reserving so much that other functions are starved.

How to answer in the interview

"Reserved concurrency guarantees a function a number of concurrent executions from the regional pool, so other functions can't take them, and at the same time caps it at that number. For example, reserving twenty protects a downstream database because at most twenty instances run. Setting it to zero disables the function, a handy kill switch. It's free. Provisioned concurrency is different: it keeps instances pre-initialised to avoid cold starts and costs money. For SQS triggers I prefer maximum concurrency on the event source mapping, because it limits polling instead of causing throttled retries."

Likely follow-up questions

  • Why can reserved concurrency with SQS cause DLQ messages? Throttled invocations return messages and increase their receive count until maxReceiveCount is hit.
  • When use provisioned concurrency? Latency-sensitive synchronous APIs with predictable traffic.
  • Unreserved minimum? AWS keeps at least 100 unreserved executions per account.
