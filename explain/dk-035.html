What is the difference between the shell form and exec form of CMD and ENTRYPOINT?

Docker · concept · levels mid

In one line

The exec form (CMD ["java","-jar","app.jar"]) runs the program directly as PID 1 so it receives signals; the shell form (CMD java -jar app.jar) runs via /bin/sh -c, making the shell PID 1 and blocking signals but allowing variable expansion; prefer exec form.

Detailed explanation

CMD, ENTRYPOINT and RUN accept two syntaxes. The exec form is a JSON array of the executable and its arguments. Docker calls the program directly, without a shell, so it becomes PID 1 and receives SIGTERM from docker stop. Note it must be valid JSON with double quotes; single quotes silently turn it into shell form.

The shell form is a plain string. Docker wraps it as /bin/sh -c "java -jar app.jar". The shell becomes PID 1 and, by default, does not forward signals to its child, so the application never sees SIGTERM and is killed with SIGKILL after the timeout. The image also needs a shell, which distroless and scratch images lack. Some shells exec the last command automatically, but you cannot rely on this.

The shell form's advantage is shell features: environment variable expansion ($PORT), pipes, && and globbing. The exec form does not expand variables, because no shell runs (Dockerfile-level ENV values are not substituted into exec-form arrays at run time).

ENTRYPOINT and CMD combine: with both in exec form, CMD supplies default arguments to ENTRYPOINT, and docker run image arg1 replaces CMD. If ENTRYPOINT is shell form, CMD and run arguments are ignored. The best pattern when you need variables is an exec-form ENTRYPOINT script that ends with exec "$@", so the shell is replaced by the application.

How it works

  1. Exec form: Docker calls execve("java", ["java","-jar","app.jar"]).
  2. Shell form: Docker calls execve("/bin/sh", ["sh","-c","java -jar app.jar"]).
  3. The resulting PID 1 receives signals from docker stop.
  4. With ENTRYPOINT + CMD (exec), the final argv is ENTRYPOINT + CMD.

Example

# Good
ENTRYPOINT ["/entrypoint.sh"]
CMD ["java", "-jar", "/app.jar"]
#!/bin/sh
# entrypoint.sh
set -e
# JAVA_TOOL_OPTIONS is read by the JVM itself
export JAVA_TOOL_OPTIONS="${JAVA_TOOL_OPTIONS:--XX:MaxRAMPercentage=75}"
exec "$@"
docker run myimg                 # runs /entrypoint.sh java -jar /app.jar
docker run myimg java -version   # CMD replaced

Common mistakes

  • Single quotes in the JSON array, which falls back to shell form.
  • Expecting $VAR to expand in exec form.
  • Shell-form ENTRYPOINT, which ignores CMD and run arguments.
  • Entrypoint scripts that do not exec the final command.

How to answer in the interview

"The exec form is a JSON array like CMD ["java", "-jar", "app.jar"]; Docker runs that program directly, so it's PID 1 and receives SIGTERM. The shell form is a plain string that Docker wraps in /bin/sh -c, so the shell is PID 1, doesn't forward signals, and graceful shutdown breaks; the image also needs a shell. The shell form's advantage is variable expansion and pipes. I use the exec form, and when I need variables I use an entrypoint script that ends with exec "$@" so the application replaces the shell."

Likely follow-up questions

  • How do ENTRYPOINT and CMD combine in exec form? CMD becomes the default arguments to ENTRYPOINT.
  • How do you override ENTRYPOINT? docker run --entrypoint.
  • Does RUN have the same two forms? Yes; for RUN the shell form is normal and harmless.
