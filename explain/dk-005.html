Where do container logs go, and how do you read them?

Docker · concept · levels entry

In one line

Apps in containers should log to stdout/stderr; Docker captures the streams via a logging driver (default json-file on the host), you read them with docker logs (-f, --tail, --since, -t), configure rotation (max-size, max-file) so disks don't fill, and ship logs centrally in production.

Detailed explanation

Containers are ephemeral and often read-only, so writing log files inside them is a trap: the files vanish with the container, fill the writable layer, and are invisible to tooling. The convention (twelve-factor) is to treat logs as an event stream on stdout/stderr. Official images such as nginx even symlink their log files to /dev/stdout.

Docker's daemon captures both streams and hands them to the configured logging driver:

  • json-file (default): one JSON object per line, stored under /var/lib/docker/containers/<id>/<id>-json.log. No rotation by default, so a chatty container can fill the disk.
  • local: a compact format with rotation enabled by default; recommended by Docker for single hosts.
  • journald, syslog, fluentd, gelf, awslogs, gcplogs, splunk send logs elsewhere. Since Docker 20.10, "dual logging" keeps a local cache so docker logs still works with remote drivers.

Reading logs: docker logs web prints everything; -f follows; --tail 100 shows the last lines; --since 10m or --until limit by time; -t adds timestamps. docker compose logs -f api does the same per service.

Rotation is set globally in /etc/docker/daemon.json (applies to new containers) or per container with --log-opt.

Production: a node-level agent (Fluent Bit, Vector, the OpenTelemetry Collector or Promtail/Alloy) tails container logs and ships them to Elasticsearch/OpenSearch, Loki, CloudWatch or Datadog, where they survive the container, are searchable across instances and power alerts. Log structured JSON with fields like level, request ID and trace ID.

How it works

  1. App writes to stdout/stderr.
  2. Docker daemon reads streams and passes them to the logging driver.
  3. json-file/local stores them on the host; docker logs reads from there.
  4. An agent ships them to central storage; rotation prevents disk exhaustion.

Example

docker logs -f --tail 100 --since 10m -t web
docker inspect -f '{{.HostConfig.LogConfig.Type}} {{.LogPath}}' web
docker run -d --log-driver local --log-opt max-size=20m --log-opt max-file=5 nginx:1.27
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "50m", "max-file": "3" }
}

Common mistakes

  • Logging to files inside the container.
  • No log rotation, then a full disk takes down every container on the host.
  • Unstructured multi-line logs that break parsing.
  • Logging secrets or personal data.

How to answer in the interview

"In containers, apps should write logs to stdout and stderr, not to files. Docker captures those streams and docker logs shows them; -f follows, --tail 100 shows the last lines and --since 10m limits by time. By default the json-file driver stores them as JSON on the host, which grows without limit, so I configure rotation with max-size and max-file in daemon.json or use the local driver. In production a node agent like Fluent Bit ships them to Loki, Elasticsearch or CloudWatch, so logs survive the container and can be searched across instances, ideally as structured JSON with trace IDs."

Likely follow-up questions

  • Why not log to a file in the container? Lost on removal, fills the writable layer, invisible to docker logs and agents.
  • Change logging for existing containers? Daemon changes apply to new containers only; recreate them.
  • Kubernetes? Kubelet/container runtime writes logs under /var/log/pods, rotated, and agents ship them.
