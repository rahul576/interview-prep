If you already have a well-documented REST API, why build an MCP server at all?

MCP Servers · concept · levels mid, senior

In one line

A REST API is designed for developers writing integration code; an MCP server makes the capability usable by any MCP host without custom code, with model-oriented, task-level tools, descriptions and compact results designed for models, and standard discovery, notifications and OAuth; but for a single app with one model, plain function calling may be simpler.

Detailed explanation

A well-documented REST API is a great foundation, but its audience is a human developer who reads docs, understands the domain, chains calls deliberately and handles errors in code. To use it from an AI assistant without MCP, every host or agent team must write and maintain its own integration: tool definitions, auth handling and result formatting, multiplied by every client (desktop chat apps, IDE agents, internal bots).

An MCP server makes the capability available to any MCP-compatible host, and users can add it in minutes by URL. Just as important, it is a chance to design for the model:

  • Task-oriented tools instead of mirroring dozens of CRUD endpoints. find_customer_orders(email, status) beats GET /customers?email= followed by GET /orders?customerId=.
  • Descriptions that say what the tool does, when to use it and when not to.
  • Compact results: the fields the model needs, not 200-field JSON objects.
  • Actionable errors: "No customer with that email. Try search_customers with a partial name."

MCP also brings standard behaviour across clients: tool discovery, list_changed notifications, OAuth-based authorization, structured output with output schemas, progress and pagination.

It is not always needed. If only one application uses the API with one model, defining a few function-calling tools directly against the REST API is less moving parts. And the MCP server should be a thin layer over the API, not a second implementation, to avoid drift.

How it works

  1. Identify the top user tasks agents should perform.
  2. Design a small set of task-level tools mapping onto one or more API calls.
  3. Implement the server as a thin adapter using the API's client SDK and auth.
  4. Write model-oriented descriptions, schemas and error messages.
  5. Evaluate with realistic prompts; iterate on descriptions.
  6. Keep in sync by generating clients from the OpenAPI spec and testing in CI.

Example

@mcp.tool()
async def find_customer_orders(email: str, status: Literal["open", "shipped", "returned", "any"] = "any"):
    """Find a customer's orders by email. Use for 'where is my order' questions.
    Returns up to 10 recent orders with id, date, status and total."""
    customer = await api.customers.search(email=email)
    if not customer:
        return tool_error("No customer with that email. Ask the user to confirm it.")
    orders = await api.orders.list(customer_id=customer.id, status=status, limit=10)
    return [{"id": o.id, "date": o.created, "status": o.status, "total": o.total} for o in orders]

Common mistakes

  • Auto-generating one tool per endpoint from OpenAPI and shipping it.
  • Duplicating business logic in the MCP server instead of calling the API.
  • Returning raw API payloads.
  • Building an MCP server when only one internal app will ever use it.

How to answer in the interview

"A REST API is designed for developers who read docs and write integration code. An MCP server makes the capability usable by any MCP host, Claude, ChatGPT, Copilot, IDEs, custom agents, without each one writing custom code, and users can add it in minutes. It's also a chance to design for models: task-oriented tools instead of dozens of low-level endpoints, descriptions that explain when to use each tool, compact results and actionable errors. MCP adds standard discovery, change notifications, OAuth-based auth and structured output. But it's not always needed: if one app uses the API with one model, plain function calling against the REST API is simpler."

Likely follow-up questions

  • Avoid drift? Thin adapter over the API, generated clients, contract tests in CI.
  • Why not auto-generate from OpenAPI? Endpoint-shaped tools are too many and too low-level for models.
  • Who owns the server? The API team, so changes ship together.
