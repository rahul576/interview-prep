An EC2 instance in a private subnet cannot reach the internet. How do you troubleshoot?

Cloud (AWS) · scenario · levels senior

In one line

Follow the packet path: the private subnet's route table must send 0.0.0.0/0 to a NAT gateway, the NAT gateway must sit in a public subnet routed to an internet gateway with an Elastic IP, security groups and stateless NACLs (including ephemeral ports) must allow the traffic, VPC DNS must work, and Reachability Analyzer and flow logs confirm where it breaks.

Detailed explanation

Routing: check the route table associated with the instance's subnet, not the main table by assumption. It needs 0.0.0.0/0 -> nat-xxxx (or ::/0 to an egress-only internet gateway for IPv6). The NAT gateway must be public type, in state available, placed in a public subnet whose own route table has 0.0.0.0/0 -> igw-xxxx, and have an Elastic IP. The internet gateway must be attached to the VPC. A common error is putting the NAT gateway in a private subnet.

Filtering: the instance security group allows all outbound by default, but hardened environments restrict it; check egress to 443 and 53. Network ACLs are stateless, so the private subnet's NACL must allow outbound to the destination port and inbound from the ephemeral range 1024-65535 for responses, and the public subnet's NACL must allow the NAT's traffic both ways. Firewalls like AWS Network Firewall or a proxy may also be in the path.

DNS: enableDnsSupport must be on (and enableDnsHostnames for private DNS of endpoints). Custom DHCP option sets pointing to unreachable DNS servers or Route 53 Resolver DNS Firewall rules can make names fail while IPs work.

Tools: VPC Reachability Analyzer traces the configured path from the instance to the internet gateway and names the blocking component. Flow logs on the instance ENI and NAT ENI show ACCEPT or REJECT. On the instance, curl, dig and traceroute separate DNS from connectivity. Also check the OS: local firewalls, proxy settings and missing default routes.

How it works

  1. Verify the instance's subnet route table: 0.0.0.0/0 to NAT.
  2. Verify the NAT gateway: public subnet, available, Elastic IP.
  3. Verify the public subnet route: 0.0.0.0/0 to an attached IGW.
  4. Check security group egress and both subnets' NACLs.
  5. Test DNS separately from IP connectivity.
  6. Run Reachability Analyzer and inspect flow logs.

Example

# On the instance (via Session Manager)
dig +short amazon.com             # DNS works?
curl -sv --max-time 5 https://1.1.1.1 -o /dev/null   # IP connectivity?

# From your workstation
aws ec2 describe-route-tables --filters Name=association.subnet-id,Values=subnet-priv-a \
  --query 'RouteTables[].Routes'
aws ec2 describe-nat-gateways --nat-gateway-ids nat-0abc \
  --query 'NatGateways[].{State:State,Subnet:SubnetId,IP:NatGatewayAddresses[0].PublicIp}'
aws ec2 create-network-insights-path --source i-0123 \
  --destination igw-0456 --protocol tcp --destination-port 443

Common mistakes

  • Checking the main route table instead of the subnet's explicit association.
  • NAT gateway placed in a private subnet.
  • NACLs without the inbound ephemeral port range.
  • Testing only with a hostname and blaming routing for a DNS issue.

How to answer in the interview

"I follow the path. The private subnet's route table must send 0.0.0.0/0 to a NAT gateway. The NAT gateway must be in a public subnet whose route table points to an attached internet gateway, with an Elastic IP and in available state. The security group must allow outbound traffic, and NACLs, being stateless, must allow the outbound port and inbound ephemeral ports 1024 to 65535. DNS support must be enabled. Then I test DNS and IP connectivity separately, run Reachability Analyzer and check flow logs for rejects."

Likely follow-up questions

  • How test whether it is DNS or connectivity? Resolve a name with dig and curl a known IP; if the IP works but the name fails, it is DNS.
  • Why does the NAT need to be in a public subnet? It must reach the internet gateway itself.
  • Could a VPC endpoint be involved? Yes, endpoint policies or private DNS can block access to specific AWS services.
