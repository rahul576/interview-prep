How do you design for high read traffic versus high write traffic?

SD Fundamentals · concept · levels entry, mid, senior

In one line

For read-heavy systems, cache, replicate and precompute; for write-heavy systems, partition, batch and use write-optimised storage. Start by measuring the read/write ratio.

Detailed explanation

Reads and writes scale in different ways. Reads can be copied: the same data can be served from many caches and replicas. Writes must eventually land in one authoritative place per record, so the only way to scale them is to split the data (sharding) or make each write cheaper (batching, append-only storage).

Read-heavy techniques: caching (Redis, CDN), read replicas, denormalisation so a page needs one lookup, and CQRS with read models shaped for queries. Write-heavy techniques: sharding with a key that spreads load, queues/streams like Kafka to buffer bursts, batching, and LSM-tree databases (Cassandra, ScyllaDB, RocksDB, time-series DBs) that turn random writes into sequential appends.

How it works

  1. Estimate read and write QPS separately at peak.
  2. Read path: CDN → app cache → read replica → primary, with sensible TTLs.
  3. Write path: validate → append to log/queue → write to partitioned storage.
  4. Derived views (counts, feeds, search) built asynchronously from the write stream.
  5. Re-check hot keys and hot partitions on both paths.

Example

A metrics platform ingesting 1M points/s: agents → Kafka (partitioned by series) → consumers batch 10,000 points per write → time-series DB. Dashboards read pre-aggregated 1-minute rollups from a cache. Same system, write-optimised ingest plus read-optimised query side.

Common mistakes

  • Adding read replicas to fix a write bottleneck.
  • Sharding before trying caching for a read problem.
  • Choosing a shard key like "date" that sends all writes to one shard.
  • Forgetting that every extra index slows writes.

How to answer in the interview

"First I'd ask about the read/write ratio. If it's read-heavy, like most consumer apps, I'd cache aggressively, add read replicas and precompute views. If it's write-heavy, like logging or IoT, I'd partition by a high-cardinality key, buffer through Kafka, batch writes and use an LSM-based store like Cassandra. Often a system has both, and I'd separate the write model from read models."

Likely follow-up questions

  • Why are LSM trees faster for writes? Writes go to memory and a sequential log, then are flushed and compacted in the background.
  • What's the cost? Read amplification and compaction overhead; Bloom filters help reads.
  • How do you keep read models in sync? Events or CDC from the write store.
