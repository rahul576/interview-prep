What are Spring beans?

Spring Framework · concept · levels entry

In one line

A Spring bean is an object whose creation, wiring and lifecycle are managed by the IoC container (ApplicationContext), declared with stereotype annotations or @Bean methods, injected into other beans (preferably via constructors), and singleton by default.

Detailed explanation

In plain Java you create objects with new and pass their dependencies yourself. In Spring you describe the objects and their dependencies, and the Inversion of Control (IoC) container creates them, connects them and manages their lifetime. Those managed objects are beans.

You declare beans in two main ways. Stereotype annotations, @Component, @Service, @Repository, @Controller/@RestController and @Configuration, mark classes that component scanning discovers in the packages under your main class. @Repository also enables exception translation into Spring's DataAccessException hierarchy. @Bean methods inside a @Configuration class create beans explicitly, which is the way to register third-party classes you cannot annotate, such as an ObjectMapper or a RestClient.

The container then performs dependency injection. Constructor injection is preferred: dependencies are explicit, fields can be final, the object is never half-initialised, and it is easy to unit test without Spring. With a single constructor, @Autowired is not needed. When there are several candidates of one type, @Qualifier or @Primary resolves the choice.

The container also manages scope (singleton by default, or prototype, request, session), runs lifecycle callbacks such as @PostConstruct and @PreDestroy, and may wrap a bean in a proxy to add transactions, security, caching or async behaviour. This is why objects you create with new don't get @Transactional behaviour: they are not beans.

How it works

  1. Spring reads bean definitions from scanning and @Bean methods.
  2. It instantiates each bean, resolving constructor dependencies first.
  3. It injects remaining dependencies and runs Aware callbacks.
  4. It runs initialisation callbacks and BeanPostProcessors (proxies).
  5. The bean is used by the application; on shutdown, destroy callbacks run.

Example

@Repository
interface OrderRepository extends JpaRepository<Order, Long> { }

@Service
class OrderService {
    private final OrderRepository repo;
    private final Clock clock;
    OrderService(OrderRepository repo, Clock clock) {   // constructor injection
        this.repo = repo;
        this.clock = clock;
    }
}

@Configuration
class AppConfig {
    @Bean
    Clock clock() { return Clock.systemUTC(); }   // third-party class as a bean
}

Common mistakes

  • Creating a service with new and expecting injection or proxies to work.
  • Field injection with @Autowired, which hides dependencies and hinders testing.
  • Classes outside the scanned package tree never becoming beans.
  • Storing per-request state in singleton beans.

How to answer in the interview

"A Spring bean is an object whose creation, wiring and lifecycle are managed by the IoC container, the ApplicationContext, rather than created with new in my code. I declare beans with stereotype annotations like Service, Repository and Controller, found by component scanning, or with Bean methods in Configuration classes for third-party classes. The container creates them, injects dependencies, preferably through constructors, applies the scope, singleton by default, runs lifecycle callbacks and can wrap them in proxies for transactions or caching."

Likely follow-up questions

  • Why prefer constructor injection? Immutable, explicit, testable, and fails fast on missing dependencies.
  • Two beans of the same type? Use @Primary, @Qualifier or inject a List.
  • @Component vs @Bean? @Component on your own classes; @Bean for explicit or third-party construction.
