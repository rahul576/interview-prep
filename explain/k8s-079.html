How does cert-manager automate TLS certificates in Kubernetes?

Kubernetes · concept · levels entry, mid, senior

In one line

cert-manager is a controller that turns certificates into Kubernetes resources: an Issuer/ClusterIssuer defines the CA (for example Let's Encrypt via ACME), a Certificate declares names and the target Secret, cert-manager solves HTTP-01 or DNS-01 challenges, stores the cert and renews it automatically; Ingress or Gateway annotations request certificates with no extra YAML.

Detailed explanation

Manually issued certificates expire, and expiry outages are embarrassingly common. cert-manager makes certificates declarative: you describe the certificate you want and a controller keeps reality matching.

Issuers: an Issuer is namespaced, a ClusterIssuer is cluster-wide. Types include ACME (Let's Encrypt, ZeroSSL, others), CA (a CA key stored in a Secret), Vault, self-signed (for bootstrapping a private CA), and external issuers for cloud private CAs such as AWS Private CA or Google CAS.

Certificate flow: a Certificate lists dnsNames, secretName, issuerRef and optional duration and key settings. cert-manager generates a private key, creates a CertificateRequest, and for ACME an Order and Challenges. For HTTP-01, it temporarily routes /.well-known/acme-challenge/<token> through the Ingress or Gateway so the CA can fetch it; this needs the domain to be publicly reachable on port 80. For DNS-01, it creates a _acme-challenge TXT record through a DNS provider API (Route 53, Azure DNS, Cloud DNS, Cloudflare); this is required for wildcard certificates and works for internal services. The signed certificate and key land in a kubernetes.io/tls Secret.

Renewal: by default cert-manager renews when two thirds of the lifetime has passed (for a 90-day Let's Encrypt cert, about 30 days before expiry), configurable with renewBefore. Pods using the Secret pick up changes when mounted volumes refresh; some apps need a reload.

Shortcuts: annotating an Ingress with cert-manager.io/cluster-issuer (or enabling Gateway API support for Gateways) makes cert-manager create the Certificate automatically. It also injects CA bundles into webhook configurations via its CA injector.

How it works

  1. Install cert-manager (CRDs, controller, webhook, cainjector).
  2. Create a ClusterIssuer with ACME account and solver.
  3. Create a Certificate or annotate an Ingress/Gateway.
  4. cert-manager creates CertificateRequest, Order and Challenge.
  5. CA validates; cert stored in the Secret.
  6. Renewal happens automatically before expiry.

Example

apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata: { name: letsencrypt-prod }
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: platform@example.com
    privateKeySecretRef: { name: le-account-key }
    solvers:
      - dns01:
          azureDNS: { resourceGroupName: rg-dns, subscriptionID: 0000-..., hostedZoneName: example.com, managedIdentity: { clientID: 1111-... } }
---
apiVersion: cert-manager.io/v1
kind: Certificate
metadata: { name: shop-tls, namespace: shop }
spec:
  secretName: shop-tls
  dnsNames: ["shop.example.com", "*.shop.example.com"]
  issuerRef: { name: letsencrypt-prod, kind: ClusterIssuer }

Common mistakes

  • Testing against Let's Encrypt production and hitting rate limits (use staging).
  • HTTP-01 for wildcards or private hostnames.
  • Ingress class mismatch, so the challenge route is never served.
  • Not monitoring Certificate readiness and expiry.

How to answer in the interview

"cert-manager is a controller that manages certificates as Kubernetes resources. I define an Issuer or ClusterIssuer pointing at a CA, for example Let's Encrypt via ACME, Vault or a private CA. A Certificate lists the DNS names and target Secret; cert-manager creates a key, solves the ACME challenge, HTTP-01 through the ingress or DNS-01 with a TXT record, which wildcards need, and stores the signed certificate in the Secret. It renews automatically, by default after two thirds of the lifetime. Annotating an Ingress or Gateway is enough to get a certificate, and it also injects CA bundles for webhooks."

Likely follow-up questions

  • Certificate stuck not ready? kubectl describe the Certificate, then CertificateRequest, Order and Challenge; the Challenge shows DNS or HTTP errors.
  • HTTP-01 vs DNS-01? HTTP-01 is simple but needs public port 80; DNS-01 supports wildcards and internal names.
  • How do apps get new certs? Mounted Secrets update; apps must reload or be restarted (for example with Reloader).
