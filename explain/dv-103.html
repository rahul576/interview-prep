Explain the main instructions of a Dockerfile.

Docker · concept · levels entry

In one line

A Dockerfile is the recipe for an image: FROM picks the base, RUN executes build steps, COPY/ADD bring in files, WORKDIR, ENV, ARG, EXPOSE configure it, USER sets a non-root user, and CMD/ENTRYPOINT define what runs at start; ordering instructions for layer caching keeps builds fast.

Detailed explanation

Docker executes the instructions top to bottom, and each instruction that changes the filesystem (mainly RUN, COPY, ADD) creates a layer. Understanding the main instructions:

  • FROM sets the base image, for example eclipse-temurin:21-jre or node:22-alpine. Pin a specific version, not latest. Several FROM lines create a multi-stage build.
  • RUN runs a command at build time, such as installing packages. Combine related commands and clean caches in the same RUN so they don't bloat a layer.
  • COPY copies files from the build context into the image. ADD can also extract local tar archives and fetch URLs, so prefer COPY for clarity unless you need those features.
  • WORKDIR sets the working directory for later instructions and the container.
  • ENV sets environment variables that persist into the running container; ARG defines build-time variables that do not (but never pass secrets with ARG, they show up in history).
  • EXPOSE documents the port the app listens on; it does not publish it, -p does.
  • USER switches to a non-root user for following instructions and at runtime.
  • CMD gives the default command or arguments; ENTRYPOINT defines the executable. With both, CMD supplies default arguments to ENTRYPOINT. Use the exec form (JSON array) so the app is PID 1 and receives signals.
  • Others worth knowing: HEALTHCHECK, LABEL, VOLUME.

Caching: a layer is reused until its instruction or input files change; after that, all later layers rebuild. So put rarely changing steps first: base, OS packages, dependency manifest and install, and finally source code.

How it works

  1. FROM loads the base image layers.
  2. Each RUN/COPY produces a new layer on top.
  3. Metadata instructions (ENV, EXPOSE, USER, CMD) are stored in the image config.
  4. docker run creates a writable layer and runs ENTRYPOINT + CMD.

Example

FROM node:22-alpine
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev
COPY . .
ENV NODE_ENV=production
EXPOSE 3000
USER node
CMD ["node", "server.js"]

Common mistakes

  • COPY . . before installing dependencies, breaking the cache.
  • Shell form CMD java -jar app.jar, so signals go to sh and graceful shutdown fails.
  • Running as root because there's no USER.
  • Thinking EXPOSE publishes a port.
  • Putting secrets in ENV or ARG.

How to answer in the interview

"A Dockerfile is the recipe for an image. FROM chooses the base image, like eclipse-temurin:21-jre. RUN executes commands at build time, such as installing packages, and each filesystem change becomes a layer. COPY brings files from the build context in; ADD can also extract archives, but I prefer COPY. WORKDIR sets the directory, ENV sets environment variables and EXPOSE documents the port. CMD and ENTRYPOINT define what runs at start, in exec form so the app gets signals. I always add a USER so it runs as non-root, and I copy the dependency file and install dependencies before copying the source, so code changes reuse the cached dependency layer."

Likely follow-up questions

  • Why copy dependency files before source? So the expensive install layer stays cached when only code changes.
  • ARG vs ENV? ARG exists only during build; ENV persists into the container.
  • How do you pass a secret at build time? RUN --mount=type=secret, never ARG or COPY.
