Which terraform state subcommands do you use, and when?

Infrastructure as Code · concept · levels mid

In one line

Use terraform state list / state show to inspect, state mv to change addresses (now usually moved blocks), state rm to stop managing without destroying (or removed blocks), and state pull / push only in emergencies, always with a backup and the lock held.

Detailed explanation

The state maps resource addresses in your code (aws_s3_bucket.logs, module.net.aws_vpc.this) to real objects (bucket name, VPC ID). Most of the time plan and apply maintain it for you; the terraform state subcommands exist for inspection and for the rare cases where the mapping itself must change.

Inspect. state list prints every address, optionally filtered (terraform state list module.net). state show ADDRESS prints the recorded attributes, useful to compare with the cloud console when debugging drift or finding an ID.

Change addresses. state mv renames an address or moves it into a module so Terraform does not destroy and recreate the resource after a refactor. Since Terraform 1.1, moved blocks do the same declaratively: they are in code, reviewed in the pull request, visible in the plan and work for every consumer of a module. Prefer them.

Forget a resource. state rm drops an address from state without touching the real object, for example when handing a resource to another stack or when it was deleted out of band. Since 1.7, a removed block with lifecycle { destroy = false } does this in code. Adopting is the reverse: terraform import or, better, import blocks (1.5+).

Raw access. state pull downloads the state JSON; state push overwrites remote state and can destroy history or serials, so it is a last resort.

Before any manual change: stop pipelines, take a backup (terraform state pull > backup.tfstate), ensure backend versioning, and run plan afterwards to confirm no unexpected changes.

How it works

  1. Confirm nobody else is applying; the commands take the state lock.
  2. Back up the current state.
  3. Run the change (or merge the moved/removed/import block).
  4. Run terraform plan and expect no changes for affected resources.

Example

terraform state list | grep aws_s3_bucket
terraform state show aws_s3_bucket.logs
terraform state pull > backup-$(date +%F).tfstate
terraform state mv aws_s3_bucket.logs module.logging.aws_s3_bucket.this
moved {
  from = aws_s3_bucket.logs
  to   = module.logging.aws_s3_bucket.this
}
removed {
  from = aws_iam_role.legacy
  lifecycle { destroy = false }
}

Common mistakes

  • Using state rm and then forgetting the resource still exists, costing money or leaving it unmanaged.
  • Running state mv locally while CI applies the same stack.
  • Refactoring modules without moved blocks, causing destroy-and-create plans for consumers.

How to answer in the interview

"For inspection I use state list and state show, for example to find an ID or compare attributes with what's really in the cloud. When refactoring I need addresses to change without recreating resources; state mv does that, but today I prefer moved blocks because they're reviewed in code and work for all consumers. state rm, or a removed block, makes Terraform forget a resource without destroying it, for example when moving it to another stack. state pull and push are emergency tools. Before touching state manually I stop pipelines, take a backup and verify with a clean plan."

Likely follow-up questions

  • When would you use terraform state rm? Handing a resource to another configuration, or removing an entry for something already deleted outside Terraform.
  • How do you move a resource between two states? removed (destroy false) in the old stack and an import block in the new one.
  • What protects you if it goes wrong? Backend versioning and a pulled backup copy.
