How do you do blue-green and canary deployments on AWS?

Cloud (AWS) · design · levels senior

In one line

Blue/green runs a new green environment alongside blue and switches traffic once green is healthy, keeping blue for instant rollback; a canary shifts a small share first and increases gradually; on AWS use ALB weighted target groups, Route 53 weighted records or CodeDeploy for ECS and Lambda with alarm-based rollback, and keep database changes backward compatible.

Detailed explanation

Blue/green isolates the release: green is deployed and tested (smoke tests, synthetic checks) without user traffic, then traffic moves over at once or gradually. Blue stays running for a defined period so rollback is just switching back. Canary releases send, for example, 5 or 10 percent of traffic to the new version, watch error rate and latency, then proceed. Linear shifts in equal steps over time. All of these reduce blast radius compared with in-place updates.

Mechanisms on AWS: an ALB listener rule forwarding to two weighted target groups switches traffic instantly and precisely, because the ALB controls every request. Route 53 weighted records work across load balancers or regions, but clients cache DNS for the TTL, so shifts and rollbacks are slow and imprecise. Elastic Beanstalk offers CNAME swaps. API Gateway stages support canary settings, and Lambda aliases support weighted versions.

CodeDeploy automates this for ECS (blue and green task sets behind two target groups, with a test listener) and Lambda (alias weight shifting), with predefined configurations like Canary10Percent5Minutes or Linear10PercentEvery1Minute, lifecycle hooks for validation tests, and automatic rollback when CloudWatch alarms fire. ECS also now supports native blue/green deployments in the service itself. On EKS, Argo Rollouts or Flagger provide similar progressive delivery with the AWS Load Balancer Controller.

The database is shared, so schema changes must work with both versions: the expand and contract pattern adds new columns or tables first, deploys code that writes both or reads either, migrates data, and removes old structures only after blue is gone. Also consider sessions, caches, queue message formats and feature flags.

How it works

  1. Deploy green next to blue; run tests via a test listener.
  2. Shift a canary percentage of traffic to green.
  3. Watch alarms on errors, latency and business metrics.
  4. Continue shifting, or roll back automatically on alarm.
  5. After full shift and bake time, retire blue.

Example

# appspec.yaml for ECS blue/green via CodeDeploy
version: 0.0
Resources:
  - TargetService:
      Type: AWS::ECS::Service
      Properties:
        TaskDefinition: <TASK_DEFINITION>
        LoadBalancerInfo:
          ContainerName: web
          ContainerPort: 8080
Hooks:
  - AfterAllowTestTraffic: arn:aws:lambda:eu-west-1:111122223333:function:smoke-tests
aws deploy create-deployment-group --application-name web \
  --deployment-group-name prod \
  --deployment-config-name CodeDeployDefault.ECSCanary10Percent5Minutes \
  --alarm-configuration enabled=true,alarms=[{name=web-5xx-rate},{name=web-p99-latency}] \
  --auto-rollback-configuration enabled=true,events=DEPLOYMENT_FAILURE,DEPLOYMENT_STOP_ON_ALARM \
  --service-role-arn arn:aws:iam::111122223333:role/codedeploy-ecs --ecs-services clusterName=prod,serviceName=web \
  --deployment-style deploymentType=BLUE_GREEN,deploymentOption=WITH_TRAFFIC_CONTROL \
  --blue-green-deployment-configuration file://bg.json \
  --load-balancer-info file://lb.json

Common mistakes

  • Breaking schema changes that make rollback impossible.
  • No rollback alarms, so canaries proceed regardless of errors.
  • Relying on DNS switching and expecting instant rollback.
  • Destroying blue immediately after the switch.

How to answer in the interview

"In blue/green, a new green environment runs beside blue; once it passes tests, traffic switches and blue stays ready for instant rollback. On AWS the switch can be ALB weighted target groups, Route 53 weighted records or a Beanstalk swap. A canary sends a small share first, say 10 percent, then increases. CodeDeploy automates both for ECS and Lambda with canary and linear configs, validation hooks and automatic rollback on CloudWatch alarms. Because the database is shared, schema changes must be backward compatible using expand and contract."

Likely follow-up questions

  • Why is DNS-based blue/green slower to roll back than ALB-based? Resolvers and clients cache records for the TTL, while ALB weights apply immediately.
  • What metrics gate a canary? Error rate, p99 latency and a key business metric, compared with the baseline.
  • How handle long-lived connections? Deregistration delay and graceful draining, plus client reconnect logic.
