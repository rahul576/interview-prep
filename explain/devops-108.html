How do you manage many applications and environments in Argo CD?

GitOps & Helm · concept · levels mid, senior

In one line

In Argo CD each deployable unit is an Application (source repo path/chart → destination cluster/namespace); at scale you generate them with the app-of-apps pattern or, better, ApplicationSets with generators (cluster, Git directory, list, matrix), isolate teams with AppProjects and RBAC, use automated sync with prune and self-heal, and order resources with sync waves and hooks.

Detailed explanation

An Application CRD says: render this source (plain YAML, Kustomize overlay or Helm chart with values) and keep it in sync with this destination (cluster plus namespace). Writing hundreds of Applications by hand doesn't scale.

App of apps: a root Application points to a directory containing other Application manifests, so syncing one root creates the rest. It is simple but still means writing each child.

ApplicationSet is the modern answer: a controller that templates Applications from generators:

  • Cluster generator: one Application per registered cluster matching labels (for example env=prod).
  • Git directory/file generator: one per folder like apps/*/overlays/prod or per config file.
  • List, matrix (combine services × clusters) and pull request generators (preview environments).

Adding a new service becomes "add a folder", adding a cluster becomes "register it with a label".

AppProjects are the guardrails: which source repos, destination clusters and namespaces, and which resource kinds a team may use, plus RBAC roles and sync windows (for example no prod syncs on Friday evenings). Combined with SSO groups, team A cannot deploy into team B's namespace.

Sync policy: automated syncs on every Git change; prune deletes resources removed from Git; selfHeal reverts manual drift. Sync waves (argocd.argoproj.io/sync-wave annotation) order resources, and hooks (PreSync, Sync, PostSync, SyncFail) run Jobs such as database migrations before the Deployment or smoke tests afterwards.

How it works

  1. Repo layout: apps/<service>/base plus overlays/<env>, or Helm values per env.
  2. One ApplicationSet per pattern generates Applications for every service/env/cluster.
  3. Each generated Application belongs to a team AppProject.
  4. Argo CD syncs automatically with prune and self-heal.
  5. Waves and hooks order CRDs, config, migrations and workloads.

Example

apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata: { name: payments-services, namespace: argocd }
spec:
  goTemplate: true
  generators:
    - matrix:
        generators:
          - git:
              repoURL: https://github.com/acme/deploy-config
              revision: main
              directories: [ { path: "apps/payments/*" } ]
          - clusters: { selector: { matchLabels: { env: prod } } }
  template:
    metadata: { name: "{{.path.basename}}-{{.name}}" }
    spec:
      project: payments
      source:
        repoURL: https://github.com/acme/deploy-config
        targetRevision: main
        path: "{{.path.path}}/overlays/prod"
      destination: { server: "{{.server}}", namespace: payments }
      syncPolicy: { automated: { prune: true, selfHeal: true } }

Common mistakes

  • Everyone in the default project with no restrictions.
  • One giant Application containing every service.
  • Enabling prune without understanding it deletes resources removed from Git.
  • Using hooks for long-running work without timeouts.

How to answer in the interview

"Each deployable unit is an Argo CD Application pointing to a repo path, Kustomize overlay or Helm chart and a destination cluster and namespace. To manage many I use ApplicationSets: for example a Git directory generator combined with a cluster generator creates one Application per service per production cluster automatically, so onboarding is adding a folder. AppProjects restrict which repos, clusters and namespaces each team can use, with RBAC tied to SSO groups and sync windows. Applications sync automatically with prune and self-heal, and sync waves and hooks handle ordering, like running a migration job before the deployment."

Likely follow-up questions

  • How do you promote staging to prod? A PR that copies the image tag or chart version from the staging overlay to prod, possibly automated with Kargo or a pipeline.
  • App of apps vs ApplicationSet? App of apps is manual composition; ApplicationSet generates Applications from data.
  • How do you prevent risky syncs at peak times? Sync windows on the AppProject.
