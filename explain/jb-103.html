What is the difference between wait(), notify(), and notifyAll()?

Concurrency · concept · levels mid, senior

In one line

wait(), notify() and notifyAll() are Object methods for low-level coordination on a monitor: wait() releases the lock and suspends, notify() wakes one waiting thread, notifyAll() wakes all; you must hold the monitor and should always wait in a loop.

Detailed explanation

Every object has an intrinsic lock and a wait set. These three methods let threads wait for a condition on shared state ("queue not empty") without busy-spinning.

You must call them while holding the object's monitor, that is inside synchronized (obj), otherwise you get IllegalMonitorStateException. This requirement is deliberate: checking the condition and going to sleep must be atomic with respect to the thread that changes the condition, or you could miss the notification.

wait() atomically releases the monitor and puts the thread in the WAITING state (or TIMED_WAITING with wait(millis)). When it is woken, it must reacquire the monitor before wait() returns, so it competes with other threads. notify() moves one arbitrary thread from the wait set; notifyAll() wakes them all, and they then take turns acquiring the lock. The notifier keeps the lock until it leaves its synchronized block.

Always wrap wait() in a while loop that re-checks the condition. The JVM permits spurious wakeups, and even a genuine notification may be stale: another thread may grab the lock first and consume the item. if instead of while is a classic bug.

Prefer notifyAll() when threads wait for different conditions on the same object (producers waiting for space, consumers for items); notify() might wake the wrong kind of thread and the right one never gets woken. Use notify() only when all waiters are equivalent and any one can proceed.

In modern code use higher-level tools: BlockingQueue, Condition (await/signal with separate conditions per lock), CountDownLatch, Semaphore.

How it works

  1. Consumer enters synchronized (queue) and checks while (queue.isEmpty()).
  2. It calls queue.wait(): releases the lock, joins the wait set.
  3. Producer enters synchronized (queue), adds an item, calls queue.notifyAll().
  4. Producer exits the block, releasing the lock.
  5. Consumer wakes, reacquires the lock, re-checks the condition, then takes the item.

Example

class BoundedBuffer<T> {
    private final Deque<T> items = new ArrayDeque<>();
    private final int capacity;
    BoundedBuffer(int capacity) { this.capacity = capacity; }

    public synchronized void put(T item) throws InterruptedException {
        while (items.size() == capacity) wait();     // loop, not if
        items.addLast(item);
        notifyAll();                                  // wake consumers
    }

    public synchronized T take() throws InterruptedException {
        while (items.isEmpty()) wait();
        T item = items.removeFirst();
        notifyAll();                                  // wake producers
        return item;
    }
}
// Production code: just use new ArrayBlockingQueue<>(capacity)

Common mistakes

  • Calling wait()/notify() without holding the monitor.
  • Using if instead of while around wait().
  • Using notify() when producers and consumers share one wait set, causing hangs.
  • Calling wait() on one object while synchronised on another.
  • Swallowing InterruptedException inside the wait loop.

How to answer in the interview

"They are methods on Object for low-level coordination, and you must hold the object's monitor, so call them inside synchronized on that object or you get IllegalMonitorStateException. wait releases the lock and suspends the thread until it is notified, then it reacquires the lock before continuing. notify wakes one arbitrary waiting thread; notifyAll wakes all of them, which is safer when threads wait for different conditions. I always call wait in a while loop that re-checks the condition because of spurious wakeups and competing threads. In real code I'd prefer BlockingQueue, Condition or CountDownLatch."

Likely follow-up questions

  • How would you implement a producer-consumer queue with wait and notify? A synchronized bounded buffer where put waits while full and take waits while empty, each calling notifyAll after changing state.
  • Does notify() release the lock immediately? No; the lock is released only when the notifying thread leaves the synchronized block.
  • Why is Condition better? One lock can have separate notFull and notEmpty conditions, so you signal only the right waiters.
