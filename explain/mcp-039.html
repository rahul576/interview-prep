An agent connected to many MCP servers wastes much of its context on tool definitions. How do you fix it?

MCP Servers · concept · levels mid, senior, lead

In one line

Every tool definition costs tokens on every request, so fix context bloat by designing fewer, better tools, filtering servers and tools per task, using tool search / deferred loading so tools load on demand, adopting the code execution pattern where the model writes code that calls tools, and keeping tool results compact.

Detailed explanation

A tool definition is typically a few hundred tokens, and hosts send all enabled tools with every model request. Ten servers with twenty tools each easily reach tens of thousands of tokens before the user's first message: higher cost and latency, less room for real context, and lower accuracy, because similar tools get confused. Prompt caching softens cost, not accuracy.

Fixes at several levels:

Server design. Fewer, task-oriented tools with concise descriptions; merge near-duplicates; move rarely used operations to optional servers.

Host filtering. Enable only the servers and tools an agent or task needs; use profiles or per-project configurations.

Tool search / deferred loading. Keep most tool definitions out of the initial context. The model gets a small search capability (or a short index of names) and loads full definitions of relevant tools only when needed. Anthropic has described this approach (a tool search tool with deferred tool loading) and reported large token reductions and better tool-selection accuracy in setups with many tools. Some hosts implement it natively. Trade-offs: an extra step and latency, and the risk of the model failing to find the right tool if descriptions are poor.

Code execution. Present MCP tools as a code API (e.g. TypeScript or Python modules) in a sandbox. The model writes code that calls the tools it needs, filters and joins intermediate results inside the sandbox, and returns only the final answer to the context. Anthropic has written about this approach as a way to cut both definition and intermediate-result tokens; it requires a secure sandbox with resource limits.

Compact results. Large tool outputs bloat context just as much; trim fields, paginate, summarise.

How it works

  1. Measure: tokens used by tool definitions per request.
  2. Remove or merge tools; shorten descriptions without losing clarity.
  3. Filter servers/tools per agent.
  4. Enable deferred loading with tool search for the long tail.
  5. For data-heavy workflows, use code execution in a sandbox.
  6. Re-run evals to confirm accuracy and cost improvements.

Example

Before: 12 servers, 230 tools, ~55k tokens of definitions per request
After:
  always loaded: 8 core tools (~3k tokens)
  deferred: 222 tools, discoverable via tool search by description
  code-exec sandbox: agent calls crm.search() + billing.invoices() in Python,
                     joins 5,000 rows locally, returns a 10-line summary
Result: per-request context down >90%; tool-selection accuracy up in evals

Common mistakes

  • Enabling every server "just in case".
  • Long marketing-style tool descriptions.
  • Deferred loading with poor descriptions, so search fails.
  • Code execution without a proper sandbox.
  • Fixing definitions but returning huge tool results.

How to answer in the interview

"Every tool definition is sent with every request, so ten servers with twenty tools can cost tens of thousands of tokens before the conversation starts, raising cost and latency and reducing accuracy because the model must choose among hundreds of tools. I fix it at several levels: server authors design fewer, better tools; hosts filter which servers and tools each agent gets; tool search or deferred loading keeps most tools out of context and loads them on demand, which Anthropic reports cuts token usage dramatically. For data-heavy work, the code-execution pattern lets the model write code that calls tools in a sandbox and returns only the result. And tool results must stay compact too."

Likely follow-up questions

  • Trade-offs of tool search? Extra latency and a step, and failure if the model doesn't search well or descriptions are vague.
  • Does prompt caching solve it? It reduces cost and latency but not the accuracy problem.
  • When is code execution worth it? Multi-step, data-heavy workflows with large intermediate results.
