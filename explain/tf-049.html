What is the HashiCorp Terraform MCP server, and how can it help AI assistants work with Terraform?

Terraform · concept · levels mid, senior

In one line

The Terraform MCP server is HashiCorp's Model Context Protocol server that lets AI assistants fetch current provider and module documentation from the Terraform registry and, when configured, query HCP Terraform / Terraform Enterprise workspaces and runs, reducing hallucinated arguments, with scoped permissions and changes kept behind normal approvals.

Detailed explanation

MCP is an open protocol that lets an AI client (Claude, GitHub Copilot, Cursor, VS Code agents and others) call external tools exposed by a server. HashiCorp publishes an open source terraform-mcp-server, typically run locally as a container or binary and registered in the assistant's MCP configuration.

Its first job is documentation retrieval. Instead of answering from training data, the assistant can search providers and modules in the registry and pull the actual resource docs, arguments and examples for a specific provider version. That directly addresses the most common AI failure in Terraform: arguments that do not exist or were renamed in a newer major version. It can also search modules and policy libraries, so the assistant suggests maintained building blocks instead of inventing them.

Its second job, when you provide an HCP Terraform or Terraform Enterprise token, is workspace context: listing organisations, projects and workspaces, reading run status, plans and variables, and in some setups creating runs or changing workspace settings. That turns the assistant into a helpful operator ("why did last night's run fail?") but also makes it a powerful credential holder.

So treat it like any integration: run it with a least-privilege or read-only token, keep any operation that changes infrastructure behind pipelines and human approval, and review everything the assistant generates. Used this way it makes AI-assisted Terraform noticeably more accurate.

How it works

  1. The MCP server runs locally and is registered with the AI client.
  2. The user asks for a resource; the model calls a docs tool for that provider version.
  3. The server queries the registry and returns current docs and examples.
  4. The model writes code based on that documentation.
  5. With a token, the model can read workspace and run details.
  6. Write operations stay disabled or gated by approvals.

Example

{
  "mcpServers": {
    "terraform": {
      "command": "docker",
      "args": ["run", "-i", "--rm", "hashicorp/terraform-mcp-server"]
    }
  }
}

Common mistakes

  • Giving the server an organisation-owner token.
  • Assuming docs lookups make generated code correct without review and plan.
  • Enabling write operations against production workspaces.
  • Forgetting to pin and update the server image like any dependency.

How to answer in the interview

"The Terraform MCP server is HashiCorp's implementation of the Model Context Protocol, so AI assistants like Claude, Copilot or Cursor can call tools to get Terraform information. The big win is current provider and module documentation from the registry, for the exact provider version, which cuts hallucinated or outdated arguments. With a token it can also read HCP Terraform workspaces, runs and variables. I run it with read-only or scoped credentials, keep anything that changes infrastructure behind pipelines and approvals, and still review all generated code."

Likely follow-up questions

  • Which actions would you allow? Docs and module search, reading run status; no applies or variable changes in production.
  • Does it replace code review? No, it improves input quality, not accountability.
  • Can it work without HCP Terraform? Yes, registry documentation tools need no token.
