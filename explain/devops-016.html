How are containers different from virtual machines?

Docker · concept · levels entry, mid

In one line

VMs virtualise hardware and run a full guest OS with its own kernel on a hypervisor, giving strong isolation at a cost of size and boot time; containers share the host kernel and isolate processes with namespaces and cgroups, so they are lightweight and start fast but have a weaker isolation boundary.

Detailed explanation

A virtual machine runs on a hypervisor: type 1 (bare-metal, like KVM, ESXi, Hyper-V, AWS Nitro) or type 2 (on a host OS, like VirtualBox). The hypervisor presents virtual CPUs, memory, disks and NICs; each VM boots its own kernel and full OS. Isolation is strong because an attacker must escape both guest kernel and hypervisor, but each VM carries gigabytes of OS, needs its own patching, and typically boots in tens of seconds to minutes.

A container is just a set of processes on the host, restricted by kernel features:

  • Namespaces give each container its own view of PIDs, network interfaces, mounts, hostname, IPC and users.
  • cgroups limit and account CPU, memory, I/O and process counts.
  • Capabilities, seccomp, AppArmor/SELinux reduce what the processes may ask the kernel to do.

There is no guest kernel, so images are megabytes, containers start in milliseconds to seconds, and you can run far more of them per host. The trade-off: all containers share the host kernel, so a kernel vulnerability or a misconfigured privileged container can affect the host and its neighbours.

That is why multi-tenant platforms combine both: containers inside VMs, or sandboxed runtimes such as gVisor (user-space kernel) and Kata Containers / Firecracker microVMs (a lightweight VM per container or function, used by AWS Lambda and Fargate).

Because containers share the kernel, a Linux container needs a Linux kernel. Docker Desktop on macOS and Windows runs a small Linux VM (WSL 2 or a lightweight hypervisor) behind the scenes. Windows containers need a Windows kernel.

How it works

  1. VM: hardware → hypervisor → guest kernel → OS → app.
  2. Container: hardware → host OS kernel → container runtime → isolated processes.
  3. Runtime sets up namespaces, cgroups and security profiles, then execs the process.

Example

docker run --rm alpine uname -r      # prints the HOST kernel version
docker run --rm --memory=256m --cpus=0.5 alpine sh -c 'cat /sys/fs/cgroup/memory.max'
ps -ef | grep nginx                  # container processes are visible on the host

Common mistakes

  • Saying containers are "lightweight VMs" without mentioning the shared kernel.
  • Running privileged containers and assuming they are isolated.
  • Expecting a Windows container to run on a Linux host.

How to answer in the interview

"A VM runs a full guest OS with its own kernel on a hypervisor that virtualises hardware, which gives strong isolation but costs gigabytes and slower boots. Containers share the host kernel and isolate processes with namespaces for things like PIDs, network and mounts, and cgroups for CPU and memory limits. So they're small, start in seconds or less and pack densely. The trade-off is a weaker boundary: a kernel exploit affects every container on the host. That's why multi-tenant platforms run containers inside VMs or use sandboxes like gVisor or Firecracker microVMs."

Likely follow-up questions

  • Windows container on Linux? No, it needs a Windows kernel; Linux containers on Windows work through a Linux VM.
  • What does a privileged container break? It removes most isolation, giving near-host access.
  • What are rootless containers? Running the runtime and containers without root, using user namespaces.
