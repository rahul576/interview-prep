How do you do progressive delivery (canary) on Kubernetes with automated rollback?

GitOps & Helm · concept · levels senior, lead

In one line

Use a progressive delivery controller such as Argo Rollouts or Flagger: it shifts traffic in gradual steps (for example 5 → 25 → 50 → 100%) via an ingress controller, Gateway API or service mesh, runs automated analysis against metrics (error rate, latency vs stable) at each step, and aborts and rolls back automatically when thresholds are breached.

Detailed explanation

A plain Kubernetes Deployment rolling update replaces pods gradually but has no notion of traffic percentage or health beyond readiness probes: if the new version returns 5% errors, it still rolls out to 100%. Progressive delivery adds measured exposure and automatic decisions.

Argo Rollouts replaces the Deployment with a Rollout resource that defines canary steps: set a weight, pause, run analysis, continue. Flagger wraps an existing Deployment and drives the canary through a Canary resource. Both integrate with traffic routers: NGINX or other ingress controllers, the Gateway API, AWS ALB, and service meshes like Istio or Linkerd, which split traffic by weights precisely, or by headers for internal testers. Without a router, Rollouts approximates weights by replica counts.

At each step an analysis runs: an AnalysisTemplate queries Prometheus (or Datadog, CloudWatch, New Relic) for the canary's error rate, p99 latency and maybe business KPIs, ideally compared with the stable version in the same time window. If a metric fails its condition a set number of times, the rollout aborts: traffic goes back to stable and the canary scales down, with no human involved. Success promotes it to 100%.

Practicalities: canaries need enough traffic to be statistically meaningful, metrics must be labelled by version, and changes must be backward compatible, because old and new versions run together. Database migrations follow expand/contract: add compatible schema first, deploy code, remove old columns later. Feature flags complement canaries by decoupling deploy from release.

How it works

  1. New image committed → Rollout starts canary at 5% traffic.
  2. Pause (for example 5 minutes) while analysis queries metrics.
  3. Pass → 25% → analysis → 50% → analysis → 100%.
  4. Fail → abort: traffic to stable, canary scaled down, alert sent.
  5. Promotion makes the canary the new stable.

Example

apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata: { name: orders }
spec:
  strategy:
    canary:
      canaryService: orders-canary
      stableService: orders-stable
      trafficRouting: { nginx: { stableIngress: orders } }
      analysis:
        templates: [ { templateName: error-rate } ]
        startingStep: 1
      steps:
        - setWeight: 5
        - pause: { duration: 5m }
        - setWeight: 25
        - pause: { duration: 10m }
        - setWeight: 50
        - pause: { duration: 10m }
---
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata: { name: error-rate }
spec:
  metrics:
    - name: error-rate
      interval: 1m
      failureLimit: 2
      successCondition: result[0] < 0.01
      provider:
        prometheus:
          address: http://prometheus.monitoring:9090
          query: |
            sum(rate(http_requests_total{app="orders",role="canary",code=~"5.."}[2m]))
            / sum(rate(http_requests_total{app="orders",role="canary"}[2m]))

Common mistakes

  • Analysing metrics that mix stable and canary traffic.
  • Canary steps too short or traffic too low to detect anything.
  • Non-backward-compatible schema changes deployed with the canary.
  • Relying on readiness probes as the only health signal.

How to answer in the interview

"I'd use Argo Rollouts or Flagger instead of a plain Deployment. The rollout defines gradual steps, say 5, 25, 50 and 100 percent, and the ingress controller, Gateway API or a service mesh splits traffic by weight. At each step an analysis queries Prometheus for the canary's error rate and p99 latency, compared with thresholds or the stable version. If it fails, the rollout aborts automatically and traffic returns to stable, without anyone being paged first. I make sure metrics are labelled by version, there's enough traffic for a signal, and changes are backward compatible, with database changes done via expand and contract. Combined with feature flags, this keeps the blast radius of a bad release very small."

Likely follow-up questions

  • Canary with a database migration? Expand/contract: backward-compatible schema change first, then the canary, then cleanup later.
  • Canary vs blue-green? Blue-green switches all traffic at once with instant rollback; canary exposes gradually.
  • Low-traffic services? Use longer steps, synthetic traffic, or header-based canaries for internal users.
