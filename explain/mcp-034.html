Your stdio MCP server works in the Inspector, but the host shows server disconnected or fails to start it. How do you debug it?

MCP Servers · scenario · levels entry, mid, senior

In one line

If a stdio server works in the Inspector but not in the host, suspect stdout pollution (anything non-JSON-RPC on stdout breaks the stream; log to stderr) and environment differences (PATH, working directory, missing env vars); fix with absolute paths, explicit env in the config, and read the host's MCP logs.

Detailed explanation

Cause 1: stdout pollution. With stdio, stdout is the protocol channel: every line must be a JSON-RPC message. A stray print("Server started"), a library banner, a deprecation warning, a progress bar or console.log sends non-JSON text, the host fails to parse it and disconnects ("server disconnected", "invalid JSON"). The Inspector is sometimes more tolerant or the output appears only in certain code paths, so it can work there and fail in the host. All logs must go to stderr (or MCP log notifications).

Cause 2: launch environment. The host starts the server as a subprocess with its own environment, which often differs from your terminal:

  • PATH: GUI apps on macOS don't load your shell profile, so node, npx, uv or python installed via nvm, pyenv or Homebrew may not be found ("spawn npx ENOENT").
  • Working directory: may be / or the app's folder, so relative paths to scripts, .env files or data break.
  • Environment variables: API keys exported in your shell are not inherited; they must be in the config's env block (or a secure input mechanism).
  • Versions: a different Node or Python version than in your terminal.

Debugging steps: use absolute paths for the command and files; set env explicitly; read the host's MCP logs, which capture stderr and the exact spawn error (Claude Desktop writes per-server mcp*.log files, on macOS under ~/Library/Logs/Claude/; VS Code shows output in its MCP output channel). Reproduce by running the exact command from the config in a clean shell (env -i). Make the server fail fast with a clear stderr message when configuration is missing.

How it works

  1. Open the host's MCP log for that server.
  2. Look for spawn errors (ENOENT, permission denied) or JSON parse errors.
  3. Search code and dependencies for stdout writes; redirect to stderr.
  4. Replace relative paths and bare commands with absolute ones.
  5. Add required env vars to the config; restart the host fully.

Example

{
  "mcpServers": {
    "orders": {
      "command": "/Users/asha/.local/bin/uv",
      "args": ["--directory", "/Users/asha/code/orders-mcp", "run", "server.py"],
      "env": { "ORDERS_API_URL": "https://api.internal.example", "LOG_LEVEL": "debug" }
    }
  }
}
tail -f ~/Library/Logs/Claude/mcp-server-orders.log
env -i /Users/asha/.local/bin/uv --directory /Users/asha/code/orders-mcp run server.py   # reproduce clean

Common mistakes

  • print() or console.log debugging in a stdio server.
  • Bare npx or python commands that the GUI app cannot find.
  • Relying on shell-exported API keys.
  • Editing the config without fully restarting the host.

How to answer in the interview

"The most common cause is something written to stdout that isn't a JSON-RPC message: a print, a library banner or a warning. In stdio, stdout is the protocol channel, so the host sees garbage and disconnects; all logs must go to stderr. The second cause is the environment: the host launches the server with a different PATH, working directory and environment than my terminal or the Inspector, so node or uv isn't found, relative paths break or API keys are missing. I use absolute paths in the host config, pass env vars explicitly, and read the host's MCP logs, which show stderr and the exact launch error."

Likely follow-up questions

  • How to fail fast on missing config? Validate settings at startup and exit with a clear stderr message naming the missing variable.
  • How to find hidden stdout writes? Run the server manually and pipe stdout through a JSON validator.
  • Why does it work in the Inspector? Different launch environment, or the Inspector was started from your shell.
