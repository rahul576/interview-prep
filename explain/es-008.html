How do you manage log data lifecycle and cost in Elasticsearch or OpenSearch?

Elasticsearch · concept · levels senior, lead

In one line

Use ILM (Elasticsearch) or ISM (OpenSearch) with data streams. Hot on fast disks, rollover by size or age, then warm, cold and frozen tiers on cheaper storage (frozen uses searchable snapshots in S3/object storage), then delete per retention. The biggest savings come from reducing volume: drop noisy fields and debug logs, sample, and use efficient mappings.

Detailed explanation

Log data is write-heavy, mostly queried when recent, and grows without limit. Keeping 90 days on the same SSD nodes with 1 replica is expensive. Lifecycle management automates moving indices through phases as they age:

  • Hot: active writes and frequent queries. Fast NVMe/SSD nodes. Rollover creates a new backing index when the current one reaches a size (for example 50 GB primary shard size) or age (1 day), keeping shards well sized.
  • Warm: read-only, queried less often. Cheaper nodes. Actions include forcemerge to 1 segment, shrink, and fewer replicas.
  • Cold: rarely queried. In Elasticsearch it can be backed by searchable snapshots (fully mounted), so replicas aren't needed because the snapshot in the repository provides resilience.
  • Frozen: partially mounted searchable snapshots. Data lives in S3, GCS or Azure Blob, and nodes keep only a local cache. Very cheap per TB, with slower queries.
  • Delete: remove after the retention period, which is set by business, security and legal needs (for example 30 days hot/warm, 1 year frozen for audit).

Note: searchable snapshots for cold and frozen tiers require an appropriate Elastic subscription. OpenSearch has its own equivalents (ISM, UltraWarm/cold storage on AWS OpenSearch Service, and searchable snapshots in recent OpenSearch versions).

Snapshots (SLM in Elasticsearch) to object storage double as backup and DR.

Reduce volume first. Storage you never ingest is the cheapest:

  • Drop or sample DEBUG/TRACE logs and health-check noise at the shipper (Fluent Bit, Logstash, an ingest pipeline).
  • Remove unused fields and avoid indexing fields you never search (index: false, or don't map them).
  • Use keyword instead of text+keyword multi-fields where full-text isn't needed. Consider logsdb index mode or synthetic _source in newer Elasticsearch versions to cut storage.
  • Turn high-volume repetitive logs into metrics.
  • Put different retention on different streams (audit versus app debug).

How it works

  1. Apps log JSON, and the shipper filters and enriches it.
  2. Data is written to the data stream logs-app-default, with an index template that applies the ILM policy.
  3. Rollover at 50 GB/shard or 1 day.
  4. After 3 days: warm (forcemerge, replicas 1 to 0 if a snapshot exists).
  5. After 14 days: frozen (searchable snapshot in S3).
  6. After 365 days: delete.

Example

PUT _ilm/policy/app-logs
{ "policy": { "phases": {
  "hot":    { "actions": { "rollover": { "max_primary_shard_size": "50gb", "max_age": "1d" } } },
  "warm":   { "min_age": "3d",  "actions": { "forcemerge": { "max_num_segments": 1 },
                                             "allocate": { "number_of_replicas": 1 } } },
  "frozen": { "min_age": "14d", "actions": { "searchable_snapshot": { "snapshot_repository": "s3-logs" } } },
  "delete": { "min_age": "365d", "actions": { "delete": {} } }
} } }

Common mistakes

  • One giant index, or daily indices with no lifecycle, so retention means manual deletes.
  • Keeping everything on hot SSD nodes.
  • Ingesting debug logs from production at full volume.
  • No snapshot repository, or untested restores.
  • Retention that ignores compliance (too short) or privacy (too long).

How to answer in the interview

"I'd use index lifecycle management, ILM in Elasticsearch or ISM in OpenSearch, with data streams. New data lands on a hot tier with fast disks, and rollover creates a new backing index by size or age. Older indices move to warm and cold tiers on cheaper hardware with fewer replicas, then to a frozen tier backed by searchable snapshots in object storage like S3. Finally the delete phase removes them according to the retention policy. Snapshots double as backups. But the biggest savings come from not ingesting noise: dropping debug logs and unused fields, sampling, and converting repetitive logs into metrics."

Likely follow-up questions

  • Retention period for app logs? Driven by incident investigation needs, compliance (audit or PCI) and privacy law. Often 14–30 days searchable, longer archived.
  • Searchable snapshots versus a restore? Searchable snapshots query directly from object storage. A restore copies the data back first.
  • Why forcemerge in warm? Fewer segments mean less overhead and faster searches on read-only indices.
