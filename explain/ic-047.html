How do you test Terraform code?

Infrastructure as Code · concept · levels mid

In one line

Test Terraform in layers: static checks (fmt, validate, tflint, security scans), terraform test with .tftest.hcl files using plan or apply runs and mock providers for unit tests, and Terratest or apply-mode tests in ephemeral sandbox accounts with guaranteed cleanup for integration.

Detailed explanation

Infrastructure code can fail in different ways: syntax and type errors, risky configuration, wrong logic in expressions, and infrastructure that is created but does not actually work. Each layer of testing catches a different class, at a different cost.

Static checks run in seconds on every commit: terraform fmt -check, terraform validate, tflint and a security scanner such as Checkov or Trivy. No cloud access needed.

terraform test (built in since 1.6) runs test files ending in .tftest.hcl, placed in the module or a tests/ directory. Each file has run blocks with command = plan or command = apply, optional variables, and assert blocks with a condition and error message. Plan-mode runs check the logic of a module, such as naming, tags, counts and conditional resources, quickly and without creating anything. Since 1.7, mock providers (mock_provider "aws" {}) and overrides let tests run without any credentials, generating fake computed values, which makes them true unit tests. Apply-mode runs create real resources in a test account, assert on them, and Terraform destroys them automatically at the end of the file.

Terratest is a Go library for integration tests: it runs terraform init/apply on an example, then uses Go code to check that the infrastructure actually behaves, for example an HTTP endpoint returns 200, a bucket rejects public access, an instance is reachable through the load balancer, and finally runs destroy in a defer. It is more flexible than terraform test for behavioural checks but requires Go skills.

Integration tests are slow and cost money, so they run in isolated, ephemeral accounts or subscriptions, with unique name suffixes, cleanup guaranteed even on failure (plus scheduled tools such as cloud-nuke or aws-nuke for leftovers), and they are reserved for shared modules and critical paths, often nightly or on release rather than every commit.

How it works

  1. Pre-commit/CI: static checks.
  2. PR: terraform test with plan runs and mock providers.
  3. Release or nightly: apply-mode tests or Terratest in a sandbox.
  4. Destroy and verify cleanup.
  5. Publish the module version only if all layers pass.

Example

# tests/bucket.tftest.hcl
mock_provider "aws" {}

variables {
  name = "orders-logs"
}

run "applies_security_defaults" {
  command = plan
  assert {
    condition     = aws_s3_bucket_public_access_block.this.block_public_acls == true
    error_message = "Public ACLs must be blocked."
  }
  assert {
    condition     = startswith(aws_s3_bucket.this.bucket, "orders-logs")
    error_message = "Bucket name must start with the given prefix."
  }
}
func TestWebModule(t *testing.T) {
    opts := &terraform.Options{TerraformDir: "../examples/basic"}
    defer terraform.Destroy(t, opts)
    terraform.InitAndApply(t, opts)
    url := terraform.Output(t, opts, "url")
    http_helper.HttpGetWithRetry(t, url, nil, 200, "OK", 30, 10*time.Second)
}
terraform test
terraform test -filter=tests/bucket.tftest.hcl

Common mistakes

  • Only running validate and calling it testing.
  • Integration tests in shared accounts that leak resources.
  • Asserting on computed values in plan mode that are unknown until apply.
  • Expensive integration tests for every tiny root config.

How to answer in the interview

"I test in layers. Static checks first: fmt, validate, tflint and security scanners catch syntax errors and misconfigurations in seconds. Then the built-in terraform test framework: .tftest.hcl files run plan or apply against a module and assert on outputs and attributes, and with mock providers I can test logic without creating real resources. For integration I use Terratest, which applies a module into a real sandbox account, checks it actually works, like an HTTP endpoint responding, and destroys everything. Those run in isolated, ephemeral accounts with guaranteed cleanup and are reserved for shared modules."

Likely follow-up questions

  • Which modules deserve expensive integration tests? Widely shared, security-critical or complex modules (networking, IAM baselines, clusters).
  • How do you avoid name collisions in parallel tests? Random suffixes via random_id or Terratest's UniqueId.
  • Can terraform test use real providers? Yes; apply-mode runs create and then destroy real resources.
