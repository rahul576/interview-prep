How does Spring Boot auto-configuration work?

Spring Framework · concept · levels mid, senior

In one line

@SpringBootApplication enables @EnableAutoConfiguration, which loads candidate classes listed in META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports; each is guarded by @Conditional annotations such as @ConditionalOnClass and @ConditionalOnMissingBean, so Boot configures beans only when appropriate and backs off when you define your own.

Detailed explanation

Auto-configuration is Spring Boot's way of providing sensible defaults based on the classpath, existing beans and properties. @SpringBootApplication combines @SpringBootConfiguration, @ComponentScan and @EnableAutoConfiguration. The last one imports AutoConfigurationImportSelector, which reads every AutoConfiguration.imports file on the classpath. Since Boot 3.0 this file replaced the old spring.factories entry for auto-configuration. Third-party starters contribute their own entries the same way.

Each auto-configuration class is a normal @AutoConfiguration (a configuration class) whose beans are protected by conditions:

  • @ConditionalOnClass / @ConditionalOnMissingClass: is a library present?
  • @ConditionalOnBean / @ConditionalOnMissingBean: has the user already defined one?
  • @ConditionalOnProperty: is a feature switched on?
  • @ConditionalOnWebApplication, @ConditionalOnResource and others.

So DataSourceAutoConfiguration creates a HikariCP DataSource only if a JDBC driver and Hikari are on the classpath and you have not defined a DataSource bean yourself. Auto-configurations are processed after your own configuration, which is why @ConditionalOnMissingBean lets your bean win. Ordering between them uses before/after attributes.

Starters like spring-boot-starter-web are just dependency bundles with tested versions; they bring Spring MVC, Jackson and Tomcat onto the classpath, which in turn satisfies the conditions. Settings are bound from properties into @ConfigurationProperties classes such as DataSourceProperties.

You customise by setting properties, by defining your own bean, or by excluding classes with @SpringBootApplication(exclude = ...) or spring.autoconfigure.exclude. To debug, run with --debug to print the conditions evaluation report, or use the Actuator /actuator/conditions endpoint.

How it works

  1. SpringApplication.run creates the context and processes your configuration and components.
  2. The import selector loads all auto-configuration class names from the imports files.
  3. Exclusions are removed, and classes are ordered.
  4. Conditions are evaluated; matching classes register their beans.
  5. Properties are bound into configuration-properties beans that the auto-configured beans use.

Example

@AutoConfiguration
@ConditionalOnClass(AuditClient.class)
@EnableConfigurationProperties(AuditProperties.class)
public class AuditAutoConfiguration {
    @Bean
    @ConditionalOnMissingBean
    @ConditionalOnProperty(prefix = "acme.audit", name = "enabled", matchIfMissing = true)
    AuditClient auditClient(AuditProperties props) {
        return new AuditClient(props.getUrl());
    }
}
# src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
com.acme.audit.AuditAutoConfiguration
java -jar app.jar --debug     # prints the conditions evaluation report

Common mistakes

  • Still registering auto-configurations only in spring.factories with Boot 3.
  • Component-scanning auto-configuration classes, which breaks ordering and conditions.
  • Excluding an auto-configuration when a single property would do.
  • Not knowing why a bean exists and guessing instead of reading the report.

How to answer in the interview

"@SpringBootApplication includes @EnableAutoConfiguration. Boot then loads the candidate auto-configuration classes listed in META-INF/spring AutoConfiguration.imports files, which replaced spring.factories in Boot 3. Each class is guarded by conditions like @ConditionalOnClass, @ConditionalOnMissingBean and @ConditionalOnProperty. For example a DataSource is only created if a JDBC driver is present and I haven't defined my own. Starters just bring the dependencies that trigger those conditions. I customise with properties, by defining my own bean so Boot backs off, or with exclude. When something is unclear I check the conditions report with --debug or the Actuator conditions endpoint."

Likely follow-up questions

  • How would you write your own starter? An autoconfigure module with conditional @AutoConfiguration classes and the imports file, plus a starter POM that pulls it in with dependencies.
  • Why does my bean replace Boot's? @ConditionalOnMissingBean, evaluated after user configuration.
  • How to disable one auto-configuration? exclude attribute or spring.autoconfigure.exclude.
