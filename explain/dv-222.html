How do you create and manage Azure resources: portal, Azure CLI, PowerShell and IaC?

Azure · concept · levels entry

In one line

Every Azure tool, the portal, Azure CLI, Azure PowerShell and infrastructure as code (Bicep/ARM or Terraform), talks to Azure Resource Manager (ARM); use the portal to explore, CLI or PowerShell for scripts and quick tasks, and IaC deployed from pipelines for anything repeatable in production.

Detailed explanation

Azure Resource Manager is the single control plane for Azure. Whether you click a button, run a command or deploy a template, the request goes to the ARM API, which authenticates you with Entra ID, checks RBAC and Azure Policy, and asks the resource provider (Compute, Storage, Network) to act. That is why all tools are equivalent in power and why permissions apply consistently.

Azure portal: the web UI. Excellent for learning, exploring, viewing metrics and logs, and one-off investigations. It is hard to repeat, review or audit as "code", so manual production changes should be the exception.

Azure CLI (az): a cross-platform command-line tool, great for quick tasks and shell scripts: az group create, az vm list -o table, az aks get-credentials. Output can be JSON, table or TSV, and --query uses JMESPath to filter results. Azure Cloud Shell gives you a browser-based CLI with tools preinstalled.

Azure PowerShell (Az module): the same capabilities as cmdlets (New-AzResourceGroup, Get-AzVM), natural for Windows admins and object-based pipelines.

Infrastructure as code: desired state described in files, stored in Git, reviewed through pull requests and deployed from a pipeline:

  • ARM templates: JSON, native but verbose.
  • Bicep: Microsoft's cleaner DSL that compiles to ARM, with day-zero support for new resource types, what-if previews and deployment stacks.
  • Terraform with the azurerm provider: multi-cloud, with a state file and plan/apply workflow.

IaC gives repeatability (same environment every time), review, history and the ability to detect and correct drift caused by manual portal changes.

How it works

  1. Sign in (az login / Connect-AzAccount), select a subscription.
  2. Explore in the portal; prototype with CLI.
  3. Write Bicep or Terraform for the resources.
  4. Preview changes (what-if or terraform plan) in a PR.
  5. Deploy from a pipeline using a workload identity service connection.
  6. Detect drift and fix it in code.

Example

az group create --name rg-shop-dev --location centralindia
az deployment group what-if -g rg-shop-dev --template-file main.bicep
az deployment group create -g rg-shop-dev --template-file main.bicep --parameters env=dev
param env string
resource st 'Microsoft.Storage/storageAccounts@2023-05-01' = {
  name: 'stshop${env}${uniqueString(resourceGroup().id)}'

Common mistakes

  • Building production by clicking in the portal.
  • Mixing manual changes with IaC, causing drift.
  • Running scripts with personal admin accounts from laptops.
  • Not using what-if or plan before applying.

How to answer in the interview

"Everything goes through Azure Resource Manager, so the tools are equivalent in what they can do. I use the portal for exploring and one-off investigations, and the Azure CLI or PowerShell for quick tasks and scripts, like az group create or az aks get-credentials. For anything that must be repeatable and reviewed, I use infrastructure as code, Bicep, which compiles to ARM, or Terraform, stored in Git and deployed from a pipeline with a what-if or plan step. Manual portal changes in production should be rare, because they cause drift."

Likely follow-up questions

  • How to find manual changes? what-if or terraform plan showing differences, plus the Activity Log for who changed what.
  • Bicep or Terraform? Bicep for Azure-only teams; Terraform for multi-cloud or existing Terraform skills.
  • How to prevent manual changes? Limit write roles in production, use PIM and resource locks.
