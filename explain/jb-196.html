What is the difference between JPQL, HQL, and native SQL?

Spring Data & JPA · concept · levels senior, lead

In one line

JPQL is the portable JPA query language over entities and fields, HQL is Hibernate's superset of JPQL, and native SQL targets tables and columns in the database dialect, giving access to vendor features at the cost of portability and entity awareness.

Detailed explanation

JPQL (Jakarta Persistence Query Language) looks like SQL but operates on the object model: SELECT o FROM Order o JOIN o.customer c WHERE c.id = :id. You navigate associations with paths, the provider knows the mapping, and it generates SQL for the configured dialect. Because results are entities, they enter the persistence context and dirty checking works. JPQL is portable across databases supported by the provider.

HQL is Hibernate's language and every JPQL query is valid HQL. In Hibernate 6 HQL gained much more: set operations (UNION), CTEs, window functions in some forms, LIMIT/OFFSET, many SQL functions and insert ... select. Using HQL-only features ties you to Hibernate, which is rarely a real problem in Spring Boot projects.

Native SQL is plain SQL for your database, run with createNativeQuery or @Query(nativeQuery = true). It is the right tool for vendor-specific features: PostgreSQL ON CONFLICT upserts, JSONB operators, recursive CTEs, LATERAL, full-text search, query hints, or a hand-tuned query the provider cannot express. Downsides: no portability, column names must be maintained by hand, results are not automatically entities unless mapped, and Hibernate does not know which tables a native modifying query touched, so caches and the persistence context can become stale.

Also consider the Criteria API (type-safe, for dynamic queries) and tools like jOOQ or Querydsl when many complex queries are needed.

How it works

  1. JPQL/HQL string is parsed into an abstract tree using entity metadata.
  2. Hibernate translates it into dialect-specific SQL and caches the plan.
  3. Results are hydrated as entities, DTOs (constructor expressions) or scalars.
  4. Native SQL skips translation; Hibernate only binds parameters and maps the result set.
  5. Mapping of native results uses entity classes, @SqlResultSetMapping, Spring Data interface projections or Tuple.

Example

public interface OrderRepository extends JpaRepository<Order, Long> {

    // JPQL with a DTO constructor expression
    @Query("select new com.shop.OrderSummary(o.id, o.total) " +
           "from Order o where o.customer.id = :cid")
    List<OrderSummary> summaries(@Param("cid") Long customerId);

    // Native SQL with a window function, mapped to an interface projection
    @Query(value = """
        select o.id as id, o.total as total,
               rank() over (order by o.total desc) as position
        from orders o where o.created_at > :since
        """, nativeQuery = true)
    List<RankedOrder> ranked(@Param("since") Instant since);
}

interface RankedOrder { Long getId(); BigDecimal getTotal(); Long getPosition(); }

Common mistakes

  • Writing table names in JPQL (from orders) instead of entity names.
  • Concatenating user input into native SQL instead of binding parameters (SQL injection).
  • Using native UPDATEs without @Modifying(clearAutomatically = true), leaving stale entities in the context.
  • Jumping to native SQL for things JPQL handles well, losing type safety.

How to answer in the interview

"JPQL is the JPA standard: it queries entities and their fields, navigates associations by path, and the provider translates it to SQL for each database, so it is portable and returns managed entities. HQL is Hibernate's superset; every JPQL query is valid HQL, and Hibernate 6 adds CTEs, set operations and more functions. Native SQL is written against tables in the database dialect. I default to JPQL with DTO projections and use native queries for vendor features like upserts, JSON operators or window functions, or for hand-tuned performance, mapping the result to an interface projection or a result set mapping and always binding parameters."

Likely follow-up questions

  • How do you map a native result to a DTO? Interface projections in Spring Data, @SqlResultSetMapping with @ConstructorResult, or Tuple.
  • When use the Criteria API? For dynamic filters built at runtime; Specifications in Spring Data wrap it.
  • Are native queries cached? Plans are not translated, but the query cache can store results if you declare affected tables.
