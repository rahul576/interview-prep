What is the difference between partitioning and sharding?

Databases & SQL · concept · levels mid

In one line

Both split data by a key, but partitioning divides a table into pieces inside one database instance (mainly for pruning and maintenance), while sharding places pieces on different servers (for scale-out capacity), bringing distributed-system complexity; sharding is essentially horizontal partitioning across machines.

Detailed explanation

Partitioning in the usual database sense (PostgreSQL declarative partitioning, MySQL or Oracle partitioning) splits one logical table into partitions by range, list or hash. The database manages it transparently: SQL, transactions, constraints and joins work as normal. The gains are partition pruning, smaller per-partition indexes, and easy lifecycle management, such as dropping last year's partition in milliseconds. What it does not do is add capacity: all partitions share the same server's CPU, RAM, disk and write-ahead log, so the write ceiling of one primary remains.

Sharding places each partition (shard) on an independent database server with its own resources. Total storage and write throughput grow with the number of shards. The price is that the system is now distributed:

  • Something must route each query to the right shard.
  • Cross-shard queries need scatter-gather; cross-shard joins are expensive.
  • Cross-shard transactions require two-phase commit or sagas.
  • Rebalancing data when adding shards, and handling hotspots.
  • Global constraints (unique emails), schema migrations and backups across shards.

Some products blur the line: Citus, Vitess, CockroachDB, MongoDB and Cassandra handle the routing for you, so sharding feels closer to partitioning, but the distributed trade-offs remain.

They combine well: shard by tenant or customer across servers, then partition each shard's tables by date for retention and pruning.

On ordering: partition first. It is cheap, reversible and transparent. Shard only when one primary truly cannot handle the write volume or data size after tuning, caching, replicas and vertical scaling.

How it works

  1. Partitioning: parent table + partitions on one server; planner prunes partitions by key.
  2. Sharding: shard key maps rows to servers; a router directs queries.
  3. Partitioned table: local transactions and joins as usual.
  4. Sharded system: single-shard operations are local; multi-shard ones need coordination.
  5. Combined: router picks the shard, then the shard's planner prunes partitions.

Example

-- Partitioning (one PostgreSQL server)
CREATE TABLE events (tenant_id BIGINT, ts TIMESTAMPTZ, payload JSONB)
  PARTITION BY RANGE (ts);

-- Sharding the same table across nodes with Citus, still partitioned by time on each node
SELECT create_distributed_table('events', 'tenant_id');
Router: tenant 42 -> shard 7 -> db-node-3 -> partition events_2026_11

Common mistakes

  • Using the terms interchangeably without defining them.
  • Expecting partitioning to fix a CPU-bound or write-bound primary.
  • Sharding before trying partitioning, indexing and replicas.
  • Forgetting that each shard can itself be partitioned and replicated.

How to answer in the interview

"Both split data into pieces by a key. Partitioning usually means splitting a table into partitions inside a single database instance; the database handles it transparently, and the benefits are partition pruning, smaller indexes and easy maintenance, like dropping an old month, but capacity is still one server. Sharding is horizontal partitioning across multiple servers, each with its own CPU, memory and disk, so capacity scales out, at the cost of routing, cross-shard queries and transactions, and rebalancing. I'd partition first because it's cheap and transparent, and shard only when one primary can't keep up. They're often combined: shard by tenant, partition by date within each shard."

Likely follow-up questions

  • Shard or partition first? Partition first; it is simpler and reversible. Shard when a single primary's limits are reached.
  • Is a Cassandra token range a partition or a shard? Effectively a shard: data is spread across nodes by partition key.
  • Can replicas replace sharding? Only for read scaling; all writes still go to one primary.
