How do you meet audit requirements about who deployed what to production with Azure DevOps?

Azure DevOps & Pipelines · concept · levels mid, senior

In one line

Prove who changed what, who approved it and when it reached production by combining branch policies, environment deployment history with approvals, a build-once-promote artifact chain, long enough retention policies, and audit log streaming to Log Analytics or a SIEM.

Detailed explanation

Auditors typically follow a chain: a requirement or ticket, the code change, the review, the build, the approval and the production deployment. Azure DevOps can provide every link if it is configured deliberately.

Code: branch policies on main require pull requests, a minimum number of reviewers (excluding the author), linked work items and successful builds. This proves the four-eyes principle, and the PR record shows who reviewed and approved.

Deployment: production is an environment, and deployment jobs targeting it are recorded in its deployment history, listing each run, its commits and work items. Approvals and checks on the environment record who approved and when. Because the artifact is built once and promoted, with the same image digest or package version moving from test to production, there is an immutable link between commit, artifact and deployment.

Retention: by default, runs and their logs are deleted after the project's retention period. For regulated industries you configure retention policies, retain specific production runs (manually or with a retention lease from the pipeline), or export run data, logs and approvals to long-term storage, for example for seven years.

Organisation events: the audit log covers permission changes, policy changes, service connection edits and pipeline modifications. It is only kept for a limited time in the portal (90 days), so you configure audit streaming to Azure Monitor Logs, Splunk or Event Grid for long-term retention, alerting and correlation with Azure Activity Logs.

How it works

  1. Enforce branch policies and link PRs to work items.
  2. Deploy to production only via deployment jobs targeting a protected environment.
  3. Promote immutable artifacts; record image digests in the run.
  4. Add retention leases to production runs.
  5. Stream audit logs to Log Analytics; build workbooks and alerts.
  6. Periodically produce an evidence report for auditors.

Example

- stage: Prod
  jobs:
  - deployment: Deploy
    environment: payments-prod      # approvals + history
    strategy:
      runOnce:
        deploy:
          steps:
          - script: echo "Deploying digest $(imageDigest)"
          - task: PowerShell@2       # keep this run for the audit period
            inputs:
              targetType: inline
              script: |
                $body = @{ daysValid = 2555; definitionId = $(System.DefinitionId);
                           ownerId = "User:$(Build.RequestedForId)"; protectPipeline = $false;
                           runId = $(Build.BuildId) } | ConvertTo-Json -AsArray
                Invoke-RestMethod -Method Post -ContentType 'application/json' `
                  -Uri "$(System.CollectionUri)$(System.TeamProject)/_apis/build/retention/leases?api-version=7.1" `
                  -Headers @{ Authorization = "Bearer $(System.AccessToken)" } -Body $body

Common mistakes

  • Relying on default retention and discovering old runs were deleted.
  • Rebuilding for production, breaking the commit-to-artifact link.
  • Allowing people to bypass branch policies without logging or alerting.
  • Forgetting changes made directly in the Azure portal outside pipelines.

How to answer in the interview

"Auditors want who changed what, who approved it and when it reached production. Branch policies with required reviewers prove four-eyes for code. Production is an environment, so its deployment history shows each run with commits, work items and who approved. We build once and promote the same artifact, so the chain is immutable. I configure retention so production runs and logs are kept for the required period, and I stream the organisation audit log to Log Analytics or our SIEM for long-term retention and alerts on permission or policy changes."

Likely follow-up questions

  • Which changes outside pipelines matter? Portal changes, permission grants and policy bypasses, covered by Azure Activity Log and audit streaming.
  • How do you stop portal changes? Restrict write roles in production; use PIM for break-glass access.
  • What if an approver approves their own change? Configure approvals to block the person who requested the run.
