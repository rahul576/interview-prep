Your team wants to use AI coding assistants to write Terraform. What are the benefits, risks and guardrails?

Terraform · scenario · levels mid, senior, lead

In one line

AI assistants speed up scaffolding, explanation and refactoring, but they hallucinate arguments, use outdated syntax and produce insecure defaults, so AI-written Terraform gets the same review, plan and policy gates as human code, better context (modules, standards, docs via MCP) and no direct production apply.

Detailed explanation

The benefits are real. Assistants draft modules with variables, outputs and validation in minutes, explain unfamiliar code or a confusing plan, convert between resource types or providers, write terraform test files and help with refactors such as adding moved blocks. For experienced engineers that removes boilerplate; for newer ones it is an on-demand tutor.

The risks are specific to infrastructure. Models can hallucinate arguments that do not exist or mix provider major versions, such as AzureRM 3.x property names in 4.x code. They reproduce insecure patterns common in public examples: 0.0.0.0/0 ingress, public storage, wildcard IAM actions, disabled encryption. Mistakes in infrastructure have a large blast radius, and a plausible-looking change can delete a database through a forced replacement.

So the guardrail principle is simple: AI-generated code is untrusted code from a fast junior colleague. It passes fmt, validate, tflint, a security scanner such as Checkov or Trivy, terraform test, a reviewed plan and policy as code (OPA or Sentinel), exactly like human code. Quality improves a lot with context: point the assistant at your approved internal modules, naming and tagging standards, and current provider docs, for example via HashiCorp's Terraform MCP server. Finally, assistants may run read-only commands like plan in a sandbox, but applies happen only through pipelines with approvals.

How it works

  1. Developer asks the assistant for a module or change, with repository context.
  2. Assistant looks up current provider docs (MCP) and uses internal modules.
  3. Developer reviews the diff and runs local checks.
  4. CI runs validate, lint, security scan, tests and plan.
  5. Policy checks and human review approve the plan.
  6. Pipeline applies; the assistant never holds production credentials.

Example

# Same gates for every PR, human or AI-authored
steps:
  - run: terraform fmt -check -recursive
  - run: terraform validate
  - run: tflint --recursive
  - run: checkov -d . --quiet
  - run: terraform test
  - run: terraform plan -out=tfplan && terraform show -json tfplan > plan.json
  - run: conftest test plan.json -p policy/

Common mistakes

  • Merging generated code because "it validated", without reading the plan.
  • Letting assistants run with production credentials or auto-apply.
  • No context, so the assistant reinvents modules that already exist internally.
  • Skipping security scanning for "small" generated changes.

How to answer in the interview

"AI assistants are genuinely useful for Terraform: scaffolding modules, explaining plans, refactoring and writing tests. But they hallucinate arguments, use outdated provider syntax and often produce insecure defaults like open security groups or wildcard IAM. So AI-written code gets exactly the same guardrails as human code: validate, lint, security scans, tests, a reviewed plan and policy checks. I improve quality by giving the assistant context, our approved modules and standards and current provider docs through the Terraform MCP server. And the assistant never applies to production; pipelines do."

Likely follow-up questions

  • How would you measure the benefit? Lead time per change, review rework, policy violations and incidents before and after.
  • Which actions would you allow the assistant? Read docs, run fmt/validate/plan in sandboxes, open PRs.
  • What about secrets? Never paste state or credentials into prompts.
