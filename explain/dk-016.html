What is the difference between Alpine, Debian slim and full base images?

Docker · concept · levels entry

In one line

Base images differ mainly in size, C library and package manager: Alpine is tiny and uses musl libc and apk, Debian slim is small but keeps glibc compatibility, and full images add many tools at the cost of size and attack surface.

Detailed explanation

Every image starts from a base, and that choice affects pull time, compatibility, debugging comfort and how many vulnerabilities you have to patch. Alpine Linux is only a few megabytes because it is built on musl libc and BusyBox, and it installs packages with apk. That makes images very small and fast to pull, which is attractive for simple static binaries and small tools.

The catch is that most prebuilt software on Linux is compiled against glibc. Native extensions for Python or Node.js may need to be compiled from source on Alpine (although many popular Python packages now ship musllinux wheels), which slows builds and requires a compiler in the build stage. musl also behaves differently in places: its DNS resolver has historically handled search domains and large responses differently from glibc, memory allocation performance can differ, and some JVM and locale behaviour is not identical. These surprises cost more engineering time than the few megabytes saved.

Debian slim (for example python:3.12-slim or debian:bookworm-slim) strips documentation, man pages and extra packages but keeps glibc and apt, so prebuilt wheels and binaries just work. Full images such as python:3.12 or node:22 include compilers, git, curl and many libraries, which is convenient for build stages and CI but heavy (often close to 1 GB) and full of packages that produce CVE findings. A good habit is a full or slim image to build and a slim or distroless image to run.

How it works

  1. Decide what the runtime really needs: a static binary, an interpreter, native libraries.
  2. Check the compatibility of native dependencies with musl versus glibc.
  3. Compare image size and the number of known CVEs with a scanner such as Trivy or Grype.
  4. Check how quickly the base is rebuilt when security fixes appear.
  5. Use a multi-stage build: heavy image for building, slim image for running.
  6. Pin the tag (and ideally the digest) so the base does not change unexpectedly.

Example

# Build stage: full image with compilers
FROM python:3.12 AS build
COPY requirements.txt .
RUN pip wheel --wheel-dir /wheels -r requirements.txt

# Runtime stage: glibc-compatible but small
FROM python:3.12-slim
COPY --from=build /wheels /wheels
RUN pip install --no-cache-dir /wheels/* && rm -rf /wheels
COPY app/ /app
CMD ["python", "/app/main.py"]

Common mistakes

  • Choosing Alpine for Python apps and then spending minutes compiling wheels on every build.
  • Assuming a smaller image is automatically more secure without scanning it.
  • Shipping the full image to production because it was used for building.
  • Using latest instead of a pinned version.

How to answer in the interview

"The main differences are size and the C library. Alpine is only a few megabytes and uses musl and apk, which is great for static binaries but can cause problems with native Python or Node modules and with DNS or performance differences. Debian slim is a bit bigger but keeps glibc, so prebuilt packages work, which is why I usually prefer slim for Java and Python. Full images have lots of tools, so I use them only in the build stage of a multi-stage build. I decide based on compatibility, size and how fast the base gets security patches, and I check with a scanner."

Likely follow-up questions

  • When would you choose a distroless image instead? When you want only the runtime, no shell or package manager, to minimise attack surface in production.
  • Why can DNS behave differently on Alpine? musl's resolver handles search domains and fallbacks differently from glibc.
  • How do you compare two base images objectively? Measure size, scan for CVEs and test the app's build and startup on both.
