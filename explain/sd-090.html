How do you document and communicate architecture decisions in a large engineering organisation?

Architecture Trade-offs · concept · levels lead

In one line

Use design docs/RFCs reviewed before building, Architecture Decision Records capturing context, decision, alternatives and consequences, C4-model diagrams as code, lightweight review forums/guilds for visibility, and keep docs close to code and up to date.

Detailed explanation

In a large organisation, the cost of a poor decision is high and people change teams often. Written artefacts preserve the why.

Design docs / RFCs: for significant changes, a short document: problem, goals and non-goals, requirements, proposed design, alternatives considered, trade-offs, risks, rollout and migration plan, open questions. Reviewed asynchronously by affected teams (comments), then a short meeting to resolve disagreements. Writing forces clarity and includes people across time zones.

ADRs: one decision per file, numbered, stored in the repository (docs/adr/0007-use-kafka-for-domain-events.md). Status (proposed, accepted, superseded). Years later, new engineers learn why the system looks the way it does, and when context changes, a new ADR supersedes the old one.

Diagrams: the C4 model (Context, Containers, Components, Code) gives each audience the right zoom level. Diagrams as code (Structurizr, Mermaid, PlantUML) live in Git, are versioned and reviewed like code.

Forums: an architecture review or guild focuses on guidance, shared patterns and cross-team impact, not gatekeeping; small decisions stay with teams.

How it works

  1. Template for RFCs and ADRs in a repo.
  2. Threshold: what needs an RFC (new service, new datastore, cross-team API).
  3. Time-boxed review (e.g. one week), named approvers.
  4. Docs updated as part of the definition of done.

Example

# ADR 0012: Use PostgreSQL logical replication + Debezium for CDC
Status: Accepted (2026-11-21)
Context: search index drifts due to dual writes...
Decision: capture changes from WAL via Debezium into Kafka...
Alternatives: dual writes; polling; vendor CDC
Consequences: +reliable sync; −operate Kafka Connect; WAL retention monitoring

Common mistakes

  • Huge design docs nobody reads.
  • Decisions made in meetings and never written down.
  • Architecture boards that become bottlenecks.
  • Outdated diagrams on a wiki.

How to answer in the interview

"For significant changes we write a short RFC with requirements, the proposed design, alternatives and trade-offs, reviewed asynchronously by affected teams. Individual decisions become ADRs in the repo, so the reasoning survives team changes. Diagrams follow the C4 model as code. A light architecture forum shares patterns and reviews cross-team impact without blocking teams, and docs are part of the definition of done."

Likely follow-up questions

  • Avoid review bottlenecks? Clear thresholds, time-boxes, delegate to domain architects.
  • Keep docs current? Docs in repo, PR checklist, ADR supersession.
  • What goes in an RFC? Problem, goals, design, alternatives, risks, rollout.
