Design an agent that onboards new customers by calling several backend systems. How do you make it reliable?

AI Agents & AIOps · design · levels senior, lead

In one line

Make onboarding an explicit workflow with the agent handling only the unstructured parts, validate data in code before actions, give every backend call an idempotency key, store durable state to resume after failures, use sagas with compensating actions for partial failures, and provide human escalation and audit logs, verifying the final state in each system.

Detailed explanation

Customer onboarding has fixed business steps: verify identity or KYC, create the account in the CRM, set up billing, provision the product, and send a welcome email. Letting a model decide the order of these steps adds risk without benefit. So the process is a deterministic workflow, and the agent is used where language understanding helps: reading customer emails and documents, extracting details, asking for missing information, answering questions and handling unusual cases.

Validation in code: data the agent collects, company registration number, VAT ID, billing address, contact email, plan, is validated by code against schemas and external checks before any backend call. The model proposes; validators decide.

Idempotency: each backend call is a tool with an idempotency key derived from the onboarding case ID and step, such as onb-7781:create_billing_account. If a call times out and is retried, the backend returns the existing result instead of creating a duplicate account or invoice. Where a backend lacks idempotency support, the tool first checks for an existing record.

Durable state: the workflow state, completed steps and created resource IDs is persisted after each step, using a durable execution engine like Temporal or a state machine with a database. The process resumes after crashes or deployments and can wait days for customer replies without holding resources.

Partial failure: if a later step fails permanently, a saga runs compensating actions defined in code, such as deactivating the half-created CRM account or voiding the billing account, or escalates to a human with full context and the current state.

Audit and verification: every action is recorded in an audit log, and the final status is verified by reading back from each system before the customer is told onboarding is complete.

How it works

  1. Agent reads customer input and extracts structured onboarding data.
  2. Code validates data; agent asks the customer for anything missing or invalid.
  3. Workflow executes steps in order, each with an idempotency key.
  4. State is persisted after each step; waits are durable.
  5. On permanent failure, compensate or escalate.
  6. Verify the final state in all systems; send welcome email; audit everything.

Example

STEPS = [
    ("verify_identity",   kyc.verify,          None),
    ("create_crm",        crm.create_account,  crm.deactivate_account),
    ("create_billing",    billing.create,      billing.void_account),
    ("provision_product", provisioning.create, provisioning.deprovision),
    ("send_welcome",      mailer.send_welcome, None),
]

def run_onboarding(case):
    done = case.state.completed            # persisted list of (step, result)
    for name, action, compensate in STEPS:
        if name in done:
            continue                       # resume after crash
        try:
            result = action(case.data, idempotency_key=f"{case.id}:{name}")
            case.state.record(name, result)   # durable write
        except PermanentError as e:
            for prev, res in reversed(case.state.completed_with_compensation(STEPS)):
                prev.compensate(res, idempotency_key=f"{case.id}:undo:{prev.name}")
            return escalate(case, reason=str(e))
    return verify_all_systems(case)

Common mistakes

  • Letting the agent decide the order of fixed business steps.
  • Retrying create calls without idempotency keys.
  • Keeping progress only in memory or model context.
  • Compensations improvised by the model.
  • Telling the customer "done" without verifying.

How to answer in the interview

"Onboarding has fixed business steps, identity check, CRM account, billing, provisioning, welcome email, so I make the overall process an explicit workflow and use the agent for the unstructured parts: understanding customer messages and documents, asking for missing information and handling exceptions. Collected data is validated by code before any action. Each backend call has an idempotency key derived from the onboarding case, so retries don't create duplicates. State is stored durably after each step, so the process resumes after crashes or long waits. If a later step fails permanently, a saga runs compensating actions or escalates to a human. Everything is audited, and the final state is verified in each system."

Likely follow-up questions

  • Which steps stay fully deterministic? Identity checks, account creation, billing and provisioning calls and their order.
  • Backend without idempotency support? Check-then-create using a unique external reference, inside the tool.
  • Long waits for the customer? Durable timers with reminders and timeouts, no running process.
