What are EC2 user data and instance metadata?

Cloud (AWS) · concept · levels entry

In one line

User data is a script or cloud-init config that runs once at first boot to bootstrap an instance; the instance metadata service (IMDS) at 169.254.169.254 exposes instance details and the IAM role's temporary credentials, so you should require IMDSv2 session tokens to block SSRF abuse.

Detailed explanation

User data is passed at launch, in the console, CLI, launch template or Terraform. On Linux, cloud-init executes it, by default only on the first boot: install packages, write config files, fetch secrets, join a cluster, start services. Output goes to /var/log/cloud-init-output.log. User data is limited to 16 KB and is not secret: anyone who can describe the instance or reach IMDS can read it, so never put passwords in it. Long bootstrap scripts slow scaling and fail unpredictably, so heavy installation usually moves into a golden AMI, leaving user data for small instance-specific settings.

The instance metadata service is a link-local HTTP endpoint reachable only from inside the instance. It returns the instance ID, type, AMI, AZ, region, private and public IPs, network interfaces, tags (if enabled), user data and, crucially, temporary credentials for the attached IAM role at /latest/meta-data/iam/security-credentials/<role>. AWS SDKs use this automatically, which is why apps on EC2 need no stored keys.

The danger: if an application has a server-side request forgery (SSRF) flaw, an attacker can make it fetch the metadata URL and steal the role's credentials. That is essentially what happened in the 2019 Capital One breach, via a misconfigured WAF and an over-privileged role. IMDSv2 defends against this: a client must first send a PUT request to obtain a session token and include it as a header on every request; typical SSRF primitives cannot do that, and a default hop limit of 1 stops containers from reaching it through extra network hops unless configured. Set HttpTokens=required on all instances, enforce it with account defaults, SCPs or Config rules.

How it works

  1. Launch with user data; cloud-init runs it on first boot.
  2. The app or SDK calls IMDS for metadata and credentials.
  3. IMDSv2: PUT /latest/api/token returns a token.
  4. Subsequent GET requests include X-aws-ec2-metadata-token.
  5. Credentials refresh automatically before expiry.

Example

#!/bin/bash
# user data
dnf install -y nginx amazon-cloudwatch-agent
aws s3 cp s3://acme-config/nginx.conf /etc/nginx/nginx.conf
systemctl enable --now nginx
# IMDSv2 from inside the instance
TOKEN=$(curl -sX PUT http://169.254.169.254/latest/api/token \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 300")
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/placement/region

# Enforce IMDSv2 on an existing instance
aws ec2 modify-instance-metadata-options --instance-id i-0123 \
  --http-tokens required --http-endpoint enabled

Common mistakes

  • Secrets in user data.
  • Leaving IMDSv1 enabled.
  • Expecting user data to rerun on every reboot.
  • Huge bootstrap scripts instead of baked AMIs.

How to answer in the interview

"User data is a script or cloud-init config passed at launch that runs once at first boot to bootstrap the server: install packages, fetch config, start services. For speed and reliability, most of that is better baked into a golden AMI. The metadata service at 169.254.169.254 lets software on the instance read its ID, region, network details, user data and the IAM role's temporary credentials, which is how SDKs get credentials without keys. Because an SSRF bug could expose those credentials, as in the Capital One breach, I require IMDSv2, which needs a session token obtained by a PUT request."

Likely follow-up questions

  • How did Capital One relate to metadata? SSRF through a misconfigured WAF fetched role credentials from IMDSv1, which had broad S3 access.
  • Can user data run on every boot? Yes, with cloud-init configuration such as [scripts-user, always], but it is not the default.
  • Where do you debug user data? /var/log/cloud-init-output.log.
