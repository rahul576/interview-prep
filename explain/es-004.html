Explain the difference between query context and filter context, and how relevance scoring works.

Elasticsearch · concept · levels mid, senior

In one line

Query context asks "how well does it match?" and computes a relevance score (BM25). Filter context asks "does it match, yes or no?", skips scoring and can be cached, so it is faster. A bool query combines must (scored), should (boosts or optional), filter (unscored) and must_not (exclusion, unscored).

Detailed explanation

Every clause in an Elasticsearch query runs in one of two contexts:

  • Query context: used by must, should and top-level match. Lucene computes a _score for each matching document, and results are sorted by it.
  • Filter context: used by filter, must_not, constant_score and the filters inside aggregations. A pure yes/no. No scoring work is done, and frequently used filters are stored in the node query cache as bitsets.

Rule of thumb: anything that is not about relevance (status = ACTIVE, price range, date range, tenant id, in stock) belongs in filter. Only full-text intent ("wireless headphones") goes in must or should.

bool semantics:

  • must: all must match and they contribute to the score.
  • should: optional matches that add to the score. If there is no must or filter, at least one should must match (configurable with minimum_should_match).
  • filter: must match, no score.
  • must_not: must not match, no score.

BM25 scoring (the default since Elasticsearch 5) uses three factors:

  • Term frequency (TF): more occurrences in the field means a higher score, with saturation (parameter k1, default 1.2), so the 10th occurrence adds little.
  • Inverse document frequency (IDF): rare terms across the index count more than common ones ("the" is worth little).
  • Field length normalisation (b, default 0.75): a match in a short title beats one in a long body.

Scores are computed per shard (IDF uses shard-local statistics), so tiny indices can show inconsistencies. search_type=dfs_query_then_fetch fixes that at extra cost.

Tune relevance with field boosts (title^3), multi_match, and function_score or rank_feature for freshness or popularity. Recent versions also support hybrid lexical plus vector search.

How it works

  1. Parse the bool query.
  2. Execute the filters (from cache if possible) to get the candidate set.
  3. Score the must and should clauses with BM25 over the candidates.
  4. Collect the top N by score per shard, then merge on the coordinating node.
  5. Use explain: true or the profile API to inspect scores and cost.

Example

GET /products/_search
{
  "query": {
    "bool": {
      "must":     [ { "multi_match": { "query": "wireless headphones",
                                       "fields": ["name^3", "description"] } } ],
      "should":   [ { "term": { "brand": { "value": "acme", "boost": 2 } } } ],
      "filter":   [ { "term":  { "status": "ACTIVE" } },
                    { "range": { "price": { "lte": 200 } } } ],
      "must_not": [ { "term": { "discontinued": true } } ]
    }
  }
}

Common mistakes

  • Putting exact conditions in must, which wastes CPU on scoring and skews relevance.
  • Expecting filter clauses to affect ranking.
  • Comparing scores across different queries (they are only relative within one query).
  • Confusing a should with no must (where it is required) with should alongside must (optional).

How to answer in the interview

"In query context Elasticsearch asks how well a document matches and computes a relevance score, using BM25 by default. That combines term frequency with saturation, inverse document frequency so rare terms count more, and field-length normalisation so short fields matching rank higher. In filter context it only asks yes or no. There's no scoring, and results can be cached, so it's faster. A bool query combines must clauses that score, should clauses that boost, filter clauses for exact conditions like status or date ranges, and must_not for exclusions. I put every non-relevance condition in filter."

Likely follow-up questions

  • Boost newer documents? A function_score with a gauss decay on the date, or rank_feature / distance_feature queries.
  • Why does the score differ between shards? IDF is per-shard. Use more data, or dfs_query_then_fetch.
  • How do you debug ranking? explain: true, the _explain API and the profile API.
