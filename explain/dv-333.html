An application suddenly cannot connect to its database. Walk me through your investigation.

Troubleshooting · scenario · levels mid, senior

In one line

Start from the exact error — timeout (network path), connection refused (nothing listening), authentication failed (credentials) — then check DNS, the network path and port, the database side (up, max connections, rotated password, failover) and the app's connection pool.

Detailed explanation

"Cannot connect to the database" covers very different problems, and the error message is the best map.

  • A timeout means packets are not getting a reply: a firewall, security group, NSG or NetworkPolicy dropping traffic, a routing change, or the database host being down.
  • Connection refused means the host answered but nothing listens on that port: wrong port, the database process stopped, or the app is connecting to the wrong host.
  • Authentication or authorisation errors mean the network is fine: wrong or rotated password, expired token, user locked, or TLS requirements changed.
  • "Too many connections" or pool timeouts mean the database or the app's pool is exhausted.

DNS is a frequent hidden cause. After a failover, managed databases update a DNS name to point to the new primary; apps that cache DNS forever (the JVM can, depending on settings) keep connecting to the old address. Private endpoints add private DNS zones that may be misconfigured.

Network path. From the application host or pod, nc -vz host 5432 tests reachability. Then review recent changes to security groups, firewall rules, private endpoints and Kubernetes NetworkPolicies.

Database side. Is the instance up and healthy, in maintenance or failing over? Is it at max_connections? Are there blocking locks? Was a password or certificate rotated?

Application side. A connection pool can be exhausted by leaked connections (not closed on error paths) or slow queries holding connections, giving errors even though the database is fine.

How it works

  1. Read the exact error and timestamp.
  2. Resolve the hostname from the app environment.
  3. Test the port with nc or openssl s_client.
  4. Review recent network and security changes.
  5. Check database health, connections, locks and credential changes.
  6. Check pool metrics: active, idle, waiting.

Example

kubectl exec -it deploy/orders -- sh
nslookup orders-db.postgres.database.azure.com
nc -vz orders-db.postgres.database.azure.com 5432
SELECT count(*), state FROM pg_stat_activity GROUP BY state;
SHOW max_connections;

Common mistakes

  • Restarting the app without reading the error type.
  • Forgetting DNS caching after a failover.
  • Testing connectivity from a laptop instead of from the app's network.
  • Raising max_connections to hide a connection leak.

How to answer in the interview

"The exact error tells me where to look: a timeout usually means the network path, connection refused means nothing is listening on that host and port, and an authentication error means credentials. I check DNS first — does the hostname still resolve to the right address, especially after a failover. Then I test the path from the app host or pod with nc, and review security groups, firewall rules and NetworkPolicies for recent changes. On the database side I check it's up, not at max connections, and whether a password was rotated. Finally I look at the app's connection pool, which can be exhausted by leaks or slow queries."

Likely follow-up questions

  • How do apps survive failover gracefully? Short DNS TTL caching, retries with backoff, pool validation and connecting via the cluster endpoint.
  • How do you detect connection leaks? Pool metrics and leak detection settings such as HikariCP's leakDetectionThreshold.
  • What about TLS errors? Check certificate trust, required SSL mode and CA rotation.
