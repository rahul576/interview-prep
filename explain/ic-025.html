What is a dynamic inventory in Ansible?

Configuration Management · concept · levels entry

In one line

A dynamic inventory builds the host list at runtime from a source of truth (AWS, Azure, GCP, VMware, Kubernetes, a CMDB) using inventory plugins, creating groups from tags/metadata (keyed_groups) so playbooks always target the current fleet.

Detailed explanation

A static inventory file works for a handful of long-lived servers. In the cloud, instances are created and destroyed by auto scaling, Terraform and deployments, so a hand-maintained list is stale within days: new servers are missed and old IPs time out.

A dynamic inventory asks the platform at the start of each run. Modern Ansible uses inventory plugins configured by YAML files, for example amazon.aws.aws_ec2, azure.azcollection.azure_rm, google.cloud.gcp_compute, community.vmware.vmware_vm_inventory, kubernetes.core.k8s or a CMDB such as NetBox. (Older custom scripts still work but plugins are preferred.)

The power is in grouping. With the aws_ec2 plugin, keyed_groups creates groups from tags or attributes: all instances tagged role=web land in role_web, those tagged env=prod in env_prod. groups with Jinja conditions creates groups from expressions, compose sets host variables such as ansible_host from the private IP, and filters limit which instances are included (for example only running instances in one VPC). Playbooks then target role_web:&env_prod and never need editing when the fleet changes. The plugin config can be combined with static group_vars in the same inventory directory.

Querying cloud APIs on every run can be slow, so plugins support caching with a timeout. Tagging discipline becomes essential: an untagged instance will not be configured.

How it works

  1. Ansible loads the inventory source file matching a plugin (name must end appropriately, e.g. aws_ec2.yml).
  2. The plugin authenticates and queries the API.
  3. It filters instances and creates hosts with variables.
  4. keyed_groups and groups build group membership.
  5. Results may be cached; playbooks target groups as usual.

Example

# inventory/prod.aws_ec2.yml
plugin: amazon.aws.aws_ec2
regions: [eu-west-1]
filters:
  instance-state-name: running
  tag:env: prod
keyed_groups:
  - key: tags.role
    prefix: role
  - key: tags.env
    prefix: env
compose:
  ansible_host: private_ip_address
cache: true
cache_plugin: ansible.builtin.jsonfile
cache_connection: /tmp/aws_inventory
cache_timeout: 300
ansible-inventory -i inventory/prod.aws_ec2.yml --graph
ansible-playbook -i inventory/ site.yml --limit 'role_web:&env_prod'

Common mistakes

  • Inconsistent tags, so hosts end up in no group.
  • Using public IPs when the control node is inside the VPC.
  • Wrong file suffix so the plugin isn't recognised.
  • No filters, accidentally targeting every instance in the account.

How to answer in the interview

"A static inventory goes stale in the cloud, where instances come and go. A dynamic inventory builds the host list at runtime from the source of truth using inventory plugins for AWS, Azure, GCP, VMware, Kubernetes or a CMDB. With the aws_ec2 plugin I use keyed_groups to create groups from tags, so every instance tagged role=web and env=prod lands in the right groups automatically, compose to set ansible_host to the private IP, and filters to include only running instances. Results can be cached to avoid hitting the API every run."

Likely follow-up questions

  • How would you target only production web servers? --limit 'role_web:&env_prod' or a filter on tag:env: prod.
  • How do you check what the inventory produces? ansible-inventory --graph or --list.
  • Can you mix static and dynamic sources? Yes, point -i at a directory containing both.
