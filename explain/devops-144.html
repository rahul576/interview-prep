How do you use SonarQube quality gates in a CI pipeline?

Artifacts & Code Quality · concept · levels entry, mid

In one line

The SonarQube scanner runs in CI after tests, uploads static analysis (bugs, code smells, vulnerabilities, security hotspots) plus coverage and duplication, and the pipeline waits for the quality gate, failing the build if conditions on new code are not met; results appear as PR decoration.

Detailed explanation

SonarQube (self-hosted Server or SonarQube Cloud) analyses code with language-specific rules. Findings are classified by impact on reliability (bugs), maintainability (code smells, complexity, duplication) and security (vulnerabilities, plus security hotspots that a human must review). It does not run tests itself; it imports coverage reports produced by JaCoCo, Istanbul/nyc, coverage.py and others.

A quality gate is a set of pass/fail conditions. The default "Sonar way" gate focuses on new code: no new issues above a threshold, all new security hotspots reviewed, coverage on new code at least 80% and duplication on new code at most 3%. This "Clean as You Code" approach is crucial for legacy systems: you cannot fix ten years of debt before the next release, but you can insist that every change is clean, and the overall code base improves over time. The new code period is defined relative to the previous version, a number of days or a reference branch.

In CI, the scanner runs after the build and tests, then either the pipeline polls for the result (sonar.qualitygate.wait=true, or the Jenkins waitForQualityGate step with a webhook) and fails if the gate is red. On pull requests, branch and PR analysis posts a summary and inline comments to GitHub, GitLab, Azure DevOps or Bitbucket, and the gate status can be a required check for merging.

How it works

  1. Build and run tests with coverage.
  2. Run the scanner with project key, token and coverage report paths.
  3. SonarQube computes metrics and evaluates the gate on new code.
  4. Pipeline waits for the gate result and fails on red.
  5. PR shows decoration; merge blocked until the gate passes.

Example

- run: mvn -B verify      # tests + JaCoCo report
- run: >
    mvn -B sonar:sonar
    -Dsonar.projectKey=orders-service
    -Dsonar.host.url=${{ secrets.SONAR_HOST_URL }}
    -Dsonar.token=${{ secrets.SONAR_TOKEN }}
    -Dsonar.qualitygate.wait=true
    -Dsonar.qualitygate.timeout=300

Common mistakes

  • Running the scanner without importing coverage, so coverage always shows 0%.
  • Gates on overall code that block every PR in a legacy repository.
  • Letting the gate fail but not failing the pipeline.
  • Chasing the coverage number with assertion-free tests.

How to answer in the interview

"SonarQube does static analysis for bugs, code smells, vulnerabilities and security hotspots, and imports coverage and duplication metrics from our test run. In CI the scanner runs after tests, and the pipeline waits for the quality gate result; if it fails, for example new-code coverage below 80% or a new critical vulnerability, the build fails. I apply the gate to new code, the Clean as You Code approach, so legacy debt doesn't block every change but the code base gets better with each PR. Results show up as PR decoration with inline comments, and the gate is a required check."

Likely follow-up questions

  • Why do teams game coverage, and how to prevent it? Targets become goals; review test quality, use mutation testing, focus on risky code.
  • What is a security hotspot? Security-sensitive code needing human review, not a confirmed vulnerability.
  • Where does the gate run for monorepos? One project per module or service, each with its own gate.
