What are Metaspace and PermGen?

JVM & Performance · concept · levels mid, senior

In one line

Both store class metadata: PermGen was a fixed-size part of the heap until Java 7, configured with MaxPermSize; Metaspace (Java 8+) lives in native memory and grows dynamically, so it should be capped with MaxMetaspaceSize; both can still be exhausted by class loader leaks.

Detailed explanation

Every loaded class needs metadata: its structure, field and method descriptions, method bytecode, the runtime constant pool, annotations and JIT-related data. The JVM must keep this as long as the class is loaded.

PermGen (Permanent Generation) held this data up to Java 7, as a special part of the GC-managed heap with a fixed maximum (-XX:MaxPermSize, often 64-256 MB). Applications that loaded many classes, used frameworks generating proxies, or were hot-redeployed repeatedly in Tomcat or JBoss regularly hit OutOfMemoryError: PermGen space. Sizing it was guesswork. Interned strings also lived there until Java 7 moved them to the heap.

Metaspace replaced PermGen in Java 8 (JEP 122). Class metadata now lives in native memory, allocated in chunks per class loader. Benefits: no fixed size to guess, and metadata for a class loader can be freed in bulk when that loader is collected. Related parts: Compressed Class Space (-XX:CompressedClassSpaceSize, default 1 GB of reserved address space) holds class structures when compressed class pointers are used. -XX:MetaspaceSize is not the initial size, but the high-water mark at which the first Metaspace-triggered GC happens; setting it higher avoids early full GCs at startup in big applications. Java 16 improved Metaspace's elastic memory return to the OS.

Default is unbounded. That is dangerous in containers: a leak keeps consuming native memory until the pod is OOM-killed with no Java error. Set -XX:MaxMetaspaceSize (for example 256-512 MB for a Spring Boot service, based on measured usage) so you get a clear OutOfMemoryError: Metaspace instead.

Leaks. Class metadata is freed only when its class loader becomes unreachable. Anything that holds a reference to one class, object or thread from that loader keeps the whole loader and all its classes alive: a ThreadLocal in a container thread, a JDBC driver registered in DriverManager, a static cache in a parent loader, an un-stopped thread. Libraries that generate classes per call (misused proxies, script engines, serialisation frameworks) also grow Metaspace.

How it works

  1. A class loader loads a class; metadata is allocated in Metaspace chunks.
  2. Usage grows; when it reaches MetaspaceSize, a GC tries to unload classes.
  3. The high-water mark adjusts up or down.
  4. When a class loader is collected, all its metadata is freed.
  5. If usage reaches MaxMetaspaceSize, OutOfMemoryError: Metaspace is thrown.

Example

java -XX:MetaspaceSize=128m -XX:MaxMetaspaceSize=384m -jar app.jar

jcmd <pid> VM.metaspace                 # usage by loader type
jcmd <pid> VM.classloader_stats         # classes and bytes per loader
jstat -gc <pid> 1000                     # MC/MU columns: metaspace capacity/used
java -Xlog:class+load,class+unload -jar app.jar   # are classes being unloaded?

Common mistakes

  • Saying Metaspace removed all class-related OOMs.
  • Thinking MetaspaceSize is the initial or maximum size.
  • Leaving Metaspace unbounded in containers.
  • Using -XX:MaxPermSize on Java 8+, where it is ignored with a warning.

How to answer in the interview

"Both are where the JVM stores class metadata: class structures, method bytecode and the runtime constant pool. Up to Java 7 that was PermGen, a fixed-size area of the heap set with MaxPermSize, and apps that loaded many classes or were redeployed often hit OutOfMemoryError: PermGen space. Java 8 replaced it with Metaspace in native memory, which grows dynamically and frees metadata when its class loader is collected. That removed most tuning, but it's unbounded by default, so in containers I set MaxMetaspaceSize. Metaspace can still leak when class loaders stay reachable, for example after hot redeploys, through ThreadLocals or registered drivers, or with heavy runtime class generation."

Likely follow-up questions

  • What keeps a classloader from being garbage collected? Any strong reference to one of its classes, instances or threads, for example from a ThreadLocal, static registry or running thread.
  • What does MetaspaceSize do? Sets the initial threshold that triggers a GC for class unloading.
  • Where did interned strings go? To the regular heap in Java 7.
