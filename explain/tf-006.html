What did Terraform 1.14 add with list resources, terraform query and the actions block?

Terraform · concept · levels mid, senior, lead

In one line

Terraform 1.14 added list resources in .tfquery.hcl files with the terraform query command to discover existing infrastructure and generate configuration and import blocks, and the action block for provider operations outside create/read/update/delete, such as invoking a Lambda or invalidating a CDN cache.

Detailed explanation

Two long-standing gaps in Terraform were adopting existing infrastructure at scale and running one-off operational tasks. Terraform 1.14 (released late 2025) addressed both, with features that rely on provider support, so coverage grows as providers add implementations.

List resources and terraform query. You write list blocks in files ending in .tfquery.hcl. Each block names a resource type and a provider and contains a config block with filters, for example all EC2 instances with tag team = payments, or all resource groups in a subscription. Running terraform query executes these searches against the real environment and prints the matching objects with their identities. With terraform query -generate-config-out=imported.tf, Terraform writes resource blocks plus import blocks for the results. You then review, clean up and apply them through the normal plan and pipeline. Compared with writing import blocks by hand, this makes bulk adoption of unmanaged infrastructure much more practical.

Actions. Terraform models everything as resources with a lifecycle, which is awkward for operations that are not "desired state", like invalidating a CloudFront cache after deploying files, invoking a function to seed data, or stopping an instance. The top-level action block declares such an operation with provider-specific configuration. It can be triggered from a resource's lifecycle with action_trigger (for example after create or update), or invoked explicitly from the CLI with terraform apply -invoke=action.<type>.<name>. Actions run during apply, appear in the plan, and do not store state.

How it works

  1. Write list blocks in a .tfquery.hcl file next to your configuration.
  2. Run terraform query to see matching resources.
  3. Generate configuration and import blocks, then clean them up.
  4. Plan and apply to bring resources under management.
  5. Declare action blocks and trigger them from lifecycle events or -invoke.

Example

# discover.tfquery.hcl
list "aws_instance" "payments" {
  provider = aws
  config {
    filter {
      name   = "tag:team"
      values = ["payments"]
    }
  }
}
# main.tf
action "aws_lambda_invoke" "seed" {
  config {
    function_name = aws_lambda_function.seed.function_name
    payload       = jsonencode({ env = var.env })
  }
}

resource "aws_dynamodb_table" "orders" {
  # ...
  lifecycle {
    action_trigger {
      events  = [after_create]
      actions = [action.aws_lambda_invoke.seed]
    }
  }
}
terraform query -generate-config-out=imported.tf

Common mistakes

  • Assuming every resource type supports list or actions; check provider docs.
  • Committing generated configuration without review.
  • Using actions for things that should be real managed resources.
  • Running queries with overly broad filters and importing everything at once.

How to answer in the interview

"Terraform 1.14 added two things. List resources go in new .tfquery.hcl files and describe a search, like all EC2 instances with a given tag. terraform query runs those searches against the real environment and can generate configuration plus import blocks, which makes adopting large amounts of unmanaged infrastructure much easier, still through a reviewed plan. The new action block lets providers model operations outside the CRUD lifecycle, such as invoking a Lambda, invalidating a CDN cache or restarting something, triggered from resource lifecycle events or invoked from the CLI. Both depend on provider support, so coverage grows over time."

Likely follow-up questions

  • How would you adopt a large set of unmanaged resources? Query by tag or resource group, generate config in batches per team, clean up, apply import plans incrementally.
  • Why not use local-exec for these operations? Actions are typed, provider-implemented and visible in the plan.
  • Do actions affect state? No, they run as side effects during apply.
