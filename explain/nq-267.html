How would you handle multiple orders from the same customer in the same year and return one row per customer per year?

Databases & SQL · scenario · levels mid

In one line

GROUP BY customer and year already merges multiple orders into one row with SUM(amount) and COUNT(order_id); the real trap is extra one-to-many joins that repeat orders and inflate sums, which you fix by pre-aggregating in a CTE rather than using DISTINCT.

Detailed explanation

If customer 7 placed five orders in 2024, all five rows share the key (7, 2024), so they fall into one group. SUM(o.amount) adds them and COUNT(o.order_id) reports five. The output has exactly one row per customer per year, which is the requirement.

Problems appear when the query joins more tables with a one-to-many relationship to orders, such as order_items, payments or shipments. Each order row is then repeated once per item. An order of 1,000 with three items contributes 3,000 to SUM(o.amount), and COUNT(o.order_id) says three. This is often called fan-out or a join explosion, and it produces convincing but wrong numbers.

Patching it with SUM(DISTINCT o.amount) is dangerous: two different orders of the same amount get collapsed into one. COUNT(DISTINCT o.order_id) is fine for counting, but sums need a structural fix. The clean solution is to aggregate each child table to the order grain first (one row per order) in a subquery or CTE, then join that to orders and customers and group by customer and year. Every table being joined is then at the same grain, so nothing is repeated.

Always state the grain of each intermediate result; it makes these bugs easy to spot in code review.

How it works

  1. Decide the target grain: one row per customer per year.
  2. Pre-aggregate child tables to one row per order (CTE).
  3. Join customers, orders and the pre-aggregated CTE: one row per order.
  4. GROUP BY customer and year; SUM and COUNT.
  5. Verify with a reconciliation query (grand total equals sum of orders).

Example

WITH order_totals AS (
    SELECT order_id,
           SUM(quantity * unit_price) AS items_total,
           COUNT(*)                   AS item_count
    FROM order_items
    GROUP BY order_id
)
SELECT c.customer_id, c.name,
       EXTRACT(YEAR FROM o.order_date) AS order_year,
       COUNT(o.order_id)               AS orders,
       SUM(ot.items_total)             AS revenue,
       SUM(ot.item_count)              AS items
FROM customers c
JOIN orders o        ON o.customer_id = c.customer_id
JOIN order_totals ot ON ot.order_id = o.order_id
WHERE o.status = 'COMPLETED'
GROUP BY c.customer_id, c.name, EXTRACT(YEAR FROM o.order_date)
ORDER BY c.name, order_year;

Common mistakes

  • Summing an order-level column after joining item-level rows.
  • Using SUM(DISTINCT amount) to hide duplication.
  • Grouping by full order date and getting one row per day.
  • Not reconciling totals against a simple orders-only query.

How to answer in the interview

"That's exactly what grouping does: all orders for customer 7 in 2024 land in the same group, SUM adds the amounts and COUNT of order_id shows how many orders, so I get one row per customer per year. The subtle trap is joining another one-to-many table like order_items or payments; each order is repeated per item and SUM of the order amount is inflated. In that case I pre-aggregate the child table per order in a CTE, then join and group, rather than patching it with DISTINCT."

Likely follow-up questions

  • Can you write the CTE version? Aggregate order_items by order_id in a CTE, join it to orders, then group by customer and year.
  • Why not SUM(DISTINCT)? It merges different orders with equal amounts and gives wrong totals.
  • How would you show each customer's best year? Use a window function such as RANK() OVER (PARTITION BY customer_id ORDER BY revenue DESC) over the grouped result.
