Explain DynamoDB capacity modes, secondary indexes and TTL.

Cloud (AWS) · concept · levels mid

In one line

DynamoDB offers on-demand (pay per request, instant scaling) and provisioned (RCUs/WCUs with auto scaling) capacity; tables are accessed by partition key and optional sort key, GSIs add alternative keys with eventual consistency, LSIs add an alternative sort key created with the table, and TTL deletes expired items for free.

Detailed explanation

Capacity modes: on-demand charges per read and write request and absorbs sudden spikes, ideal for new, spiky or unpredictable workloads; it is now the recommended default for most tables. Provisioned mode sets read and write capacity units (1 RCU = one strongly consistent 4 KB read per second, 1 WCU = one 1 KB write per second), optionally with auto scaling and reserved capacity, which is cheaper for steady, predictable traffic. You can switch modes, with limits on how often.

Keys: the partition key is hashed to choose a partition; the optional sort key orders items within it and enables range queries, such as PK=CUSTOMER#42, SK begins_with ORDER#2026. Good design spreads traffic evenly across many partition key values and models access patterns first, often in a single-table design.

A global secondary index has its own partition and sort keys, can be added or removed at any time, is updated asynchronously so reads are eventually consistent, and has its own throughput, which can throttle base table writes if too low. A table can have up to 20 GSIs. A local secondary index keeps the table's partition key with a different sort key, must be created with the table, supports strongly consistent reads, shares the table's capacity, and limits each item collection to 10 GB. Prefer GSIs in most cases.

TTL: you name a numeric attribute holding an epoch-seconds expiry; a background process deletes expired items, typically within a few days, without consuming write capacity. Deleted items appear in DynamoDB Streams, so you can archive them. Filter expired items in queries if exactness matters.

How it works

  1. Choose access patterns, then partition and sort keys.
  2. Pick on-demand or provisioned with auto scaling.
  3. Add GSIs for other query patterns, projecting only needed attributes.
  4. Write items with an expiresAt attribute and enable TTL.
  5. Monitor throttling and hot keys with CloudWatch Contributor Insights.

Example

aws dynamodb create-table --table-name sessions \
  --billing-mode PAY_PER_REQUEST \
  --attribute-definitions AttributeName=pk,AttributeType=S \
     AttributeName=sk,AttributeType=S AttributeName=email,AttributeType=S \
  --key-schema AttributeName=pk,KeyType=HASH AttributeName=sk,KeyType=RANGE \
  --global-secondary-indexes '[{"IndexName":"by-email",
     "KeySchema":[{"AttributeName":"email","KeyType":"HASH"}],
     "Projection":{"ProjectionType":"KEYS_ONLY"}}]'

aws dynamodb update-time-to-live --table-name sessions \
  --time-to-live-specification Enabled=true,AttributeName=expiresAt

Common mistakes

  • Low-cardinality partition keys such as status or date, creating hot partitions.
  • Using Scan instead of designing keys and indexes for queries.
  • Under-provisioned GSIs throttling writes on the base table.
  • Expecting TTL deletion at the exact expiry second.

How to answer in the interview

"DynamoDB has on-demand capacity, paying per request with instant scaling, good for unpredictable traffic, and provisioned capacity with auto scaling, cheaper for steady load. Items are found by partition key plus an optional sort key for ranges, so I design keys around access patterns. GSIs let me query by different keys, are eventually consistent, have their own capacity and can be added anytime. LSIs share the partition key with a different sort key, must be created with the table and allow strong reads. TTL deletes expired items automatically at no cost, which is ideal for sessions."

Likely follow-up questions

  • What is a hot partition and how avoid it? One key gets too much traffic; use high-cardinality keys or write sharding with suffixes.
  • Can a GSI read be strongly consistent? No, GSIs are always eventually consistent.
  • How do you do transactions? TransactWriteItems for up to 100 items atomically, at double the cost.
