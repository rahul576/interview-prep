How are Terraform variable values set, and what is the order of precedence?

Infrastructure as Code · concept · levels entry

In one line

Terraform variables get values from defaults, TF_VAR_ environment variables, terraform.tfvars, **\.auto.tfvars and the command line (-var-file, -var); later sources override earlier ones, so the command line wins*.

Detailed explanation

An input variable is declared with a variable block, which can include a type, a description, a default and validation. The value Terraform finally uses is resolved from several sources. From lowest to highest precedence they are: the default in the variable block, environment variables named TF_VAR_<name>, the terraform.tfvars file, terraform.tfvars.json, any **\.auto.tfvars or \.auto.tfvars.json files (in lexical order of filename), and finally -var and -var-file** options on the command line, processed in the order they are given. If the same variable is set in several places, the last one wins.

The files terraform.tfvars and *.auto.tfvars are loaded automatically from the working directory, which is convenient but also a trap: a forgotten auto file can silently override what you expected. For that reason many teams keep one explicit file per environment, such as dev.tfvars and prod.tfvars, and pass it deliberately with -var-file in the pipeline. In HCP Terraform, workspace variables play the same role and are injected for each run.

A variable with no default and no value is required: Terraform prompts for it interactively, or fails when run with -input=false, which is what you want in CI. Required variables are a good way to force callers to make a conscious choice, for example the environment name. Secrets should not live in tfvars files at all; they should come from a secret store or the CI secret mechanism, typically as TF_VAR_ environment variables, and the variable should be marked sensitive = true.

How it works

  1. Terraform reads the variable blocks and their defaults.
  2. It reads TF_VAR_* environment variables.
  3. It loads terraform.tfvars and terraform.tfvars.json if present.
  4. It loads *.auto.tfvars files alphabetically.
  5. It applies -var and -var-file flags in command-line order; the last assignment wins.
  6. Any required variable still unset triggers a prompt or an error.

Example

variable "instance_count" {
  type    = number
  default = 1
}
export TF_VAR_instance_count=2          # overrides default
terraform plan -var-file=prod.tfvars    # prod.tfvars sets 4 -> overrides env var
terraform plan -var-file=prod.tfvars -var="instance_count=6"   # 6 wins
terraform plan -input=false             # fails fast if a required variable is missing

Common mistakes

  • Forgetting that *.auto.tfvars files load automatically and override environment variables.
  • Committing tfvars files that contain passwords or tokens.
  • Relying on interactive prompts, which hang or fail in CI.
  • Giving every variable a default, so a missing environment setting goes unnoticed.

How to answer in the interview

"A variable can have a default in its block, and values can then be supplied from several places. In increasing order of precedence: TF_VAR environment variables, terraform.tfvars, terraform.tfvars.json, any auto.tfvars files in alphabetical order, and finally -var and -var-file on the command line in the order given, so the command line wins. In practice I keep one tfvars file per environment and pass it explicitly in the pipeline, run with -input=false so missing required values fail fast, and keep secrets out of files entirely: they come from the CI secret store or a vault as sensitive variables."

Likely follow-up questions

  • Why should tfvars files with secrets never be committed? Git history is permanent and widely readable, so the secret leaks to everyone with repo access and must be rotated.
  • How do you make a variable mandatory? Omit the default; Terraform then requires a value.
  • What is the type of a TF_VAR value? It is a string parsed according to the declared type, so complex types need HCL syntax.
