What is Terraform state locking, and how do you import existing resources?

Infrastructure as Code · concept · levels mid, senior

In one line

Team state lives in a remote backend (S3, Azure Storage, GCS, HCP Terraform), encrypted and versioned, and state locking ensures only one operation writes state at a time (S3 native lock file or legacy DynamoDB, Azure blob leases); existing resources are adopted with terraform import or import blocks (which can generate config), refactors use moved blocks or state mv, and state is never edited by hand.

Detailed explanation

Why locking: plan and apply read state, call APIs and write state back. If two engineers (or two pipelines) apply at the same time from the same state, one can overwrite the other's changes, leading to lost or corrupted state and duplicate or orphaned resources. With locking, Terraform acquires a lock before any state-modifying operation; a second run waits (-lock-timeout) or fails with the lock holder's details.

Backends: S3 historically required a DynamoDB table for locks; since Terraform 1.10 it supports native locking with a lock file in the bucket (use_lockfile = true), and the DynamoDB option is deprecated. Azure Storage uses blob leases, GCS uses lock objects, and HCP Terraform locks workspaces itself. Enable bucket versioning and encryption.

Stuck locks: if a CI job was killed, the lock remains. First confirm no run is active, then terraform force-unlock <ID>.

Importing: resources created manually or by another tool aren't in state, so Terraform would try to create duplicates. Options:

  • terraform import <address> <id>: imperative CLI command, one resource at a time, not reviewable in a PR.
  • import blocks (Terraform 1.5+): declared in code, shown in plan, applied like any change, so they're reviewable and repeatable. With terraform plan -generate-config-out=generated.tf Terraform drafts the resource configuration for you. Then tidy the code until plan shows no changes.

Refactoring: renaming a resource or moving it into a module would normally destroy and recreate it. moved blocks record the address change in code; terraform state mv does it imperatively.

How it works

  1. Configure backend with versioning, encryption and locking.
  2. Every plan/apply acquires and releases the lock.
  3. To adopt a resource: add an import block, generate config, plan, apply.
  4. To refactor: add moved blocks; plan should show moves, not destroys.
  5. Restore from bucket versions if state is damaged.

Example

import {
  to = aws_s3_bucket.legacy
  id = "acme-legacy-data"
}

moved {
  from = aws_instance.web
  to   = module.web.aws_instance.this
}
terraform plan -generate-config-out=generated.tf
terraform apply
terraform force-unlock 2f6e9c1d-...     # only after confirming no active run

Common mistakes

  • No locking, especially with several pipelines sharing state.
  • Force-unlocking a lock that belongs to a running apply.
  • Importing and then applying without reaching a clean plan, causing unwanted changes.
  • Editing state JSON by hand.

How to answer in the interview

"Team state lives in a remote backend like S3, Azure Storage or HCP Terraform, encrypted and versioned. Locking ensures only one apply runs at a time; without it two people can corrupt state or create duplicates. The S3 backend used a DynamoDB table for locks and now supports native locking with a lock file, and Azure uses blob leases. To bring manually created infrastructure under management I use import blocks, which are reviewable in the plan and can generate the configuration, then adjust the code until plan shows no changes; the older terraform import command also works. For refactoring I use moved blocks or state mv, and I never edit the state file by hand."

Likely follow-up questions

  • How do you recover a stuck lock? Verify no run is active, then terraform force-unlock with the lock ID.
  • Why prefer import blocks over the CLI command? They're in code, reviewed in plan, and can generate configuration.
  • Stop managing a resource without deleting it? A removed block with lifecycle { destroy = false }, or terraform state rm.
