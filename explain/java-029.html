What is the difference between lazy and eager fetching in JPA, and what is a LazyInitializationException?

Spring Data & JPA · concept · levels entry, mid

In one line

Lazy fetching loads an association on first access through a proxy, eager loads it immediately with the parent; JPA defaults are eager for @ManyToOne/@OneToOne and lazy for @OneToMany/@ManyToMany, and a LazyInitializationException occurs when a lazy association is accessed after the persistence context is closed.

Detailed explanation

With lazy fetching, Hibernate doesn't load the association when it loads the entity. For a single-valued association it places a proxy (a generated subclass holding only the id); for a collection, an uninitialised PersistentBag/PersistentSet. The first time you call a method on it, Hibernate runs a query using the session that loaded the entity.

With eager fetching, the association is always loaded together with the parent, either via a join or an immediate extra query. That sounds convenient, but it is static: every use case pays for it, eager associations chain (A eager to B eager to C), and with JPQL queries eager associations are often loaded with separate queries, causing N+1.

The JPA defaults are EAGER for @ManyToOne and @OneToOne and LAZY for @OneToMany and @ManyToMany. Recommended practice is to declare everything LAZY (@ManyToOne(fetch = FetchType.LAZY)) and decide the fetch plan per use case with join fetch, entity graphs or DTO projections.

A LazyInitializationException ("could not initialize proxy - no Session") happens when you touch a lazy association after the session or persistence context that loaded the entity has closed. Typical scenario: a @Transactional service returns an entity, the transaction ends, and the controller or Jackson then accesses order.getLines(). The correct fixes are to fetch what you need inside the transaction (join fetch, entity graph, Hibernate.initialize) or map to a DTO inside the service. Avoid workarounds like enabling open-session-in-view (hides the problem and holds connections), switching to EAGER, or hibernate.enable_lazy_load_no_trans (opens a new session per lazy load, a hidden N+1 anti-pattern).

How it works

  1. Service method starts a transaction and loads Order; lines is an uninitialised collection.
  2. Inside the transaction, accessing lines triggers a SELECT.
  3. The transaction commits; the persistence context closes; entities are detached.
  4. Accessing an uninitialised lazy association now throws LazyInitializationException.
  5. Fix by initialising or mapping before step 3.

Example

@Entity
class Order {
    @ManyToOne(fetch = FetchType.LAZY)        // override eager default
    private Customer customer;

    @OneToMany(mappedBy = "order")            // lazy by default
    private List<OrderLine> lines;
}

@Service
class OrderQueryService {
    @Transactional(readOnly = true)
    public OrderDto get(long id) {
        Order o = repo.findWithLinesById(id)  // @EntityGraph(attributePaths = "lines")
                      .orElseThrow();
        return OrderDto.from(o);              // mapping happens inside the transaction
    }
}

Common mistakes

  • Switching to EAGER to fix LazyInitializationException.
  • Returning entities from services and serialising them in controllers.
  • Relying on open-session-in-view.
  • Forgetting that @ManyToOne is eager unless you say otherwise.

How to answer in the interview

"With lazy fetching the association isn't loaded with the entity; Hibernate puts a proxy or uninitialised collection there and loads it on access. With eager fetching it's loaded immediately with the parent. JPA defaults are eager for ManyToOne and OneToOne and lazy for the to-many associations, but I make everything lazy and fetch explicitly per use case. LazyInitializationException happens when I access a lazy association after the persistence context is closed, for example in a controller. I fix it by fetching inside the transaction with a join fetch or entity graph, or mapping to a DTO, not by enabling open-session-in-view."

Likely follow-up questions

  • Why disable open-in-view? It holds connections for the whole request and hides lazy loading and N+1.
  • Can lazy work on @OneToOne? On the owning side yes; on the inverse side Hibernate often can't proxy it without bytecode enhancement.
  • Hibernate.initialize? Forces loading of a proxy or collection inside the session.
