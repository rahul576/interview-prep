Which resilience patterns do you apply to LLM API calls in backend services?

LLMOps & RAG · concept · levels mid, senior

In one line

Treat LLM APIs as slow, variable, rate-limited dependencies: timeouts sized to generation length (with streaming), retries with exponential backoff and jitter on 429 and 5xx honouring Retry-After, circuit breakers, fallback to another model, region or provider, bulkheads and rate limiting, and graceful degradation.

Detailed explanation

An LLM call differs from a typical REST call: latency ranges from hundreds of milliseconds to minutes depending on output length and reasoning, providers enforce tokens-per-minute quotas, and outages or capacity issues happen regularly.

Timeouts. Separate connect timeout (short, a few seconds) from overall or read timeout, sized to expected generation length plus margin, and set max_tokens so generation is bounded. For long outputs, stream and apply an idle timeout between chunks. Always respect the caller's deadline.

Retries. Retry 429 (rate limited), 5xx and overload errors (Anthropic uses 529 for overloaded), and connection resets, with exponential backoff and jitter, a small maximum (2-3 attempts), and honouring Retry-After headers. Don't retry 400-class validation errors. Many SDKs include retry logic; configure it rather than layering another retry on top. Never automatically repeat side effects triggered by a response (sending an email based on the model's output) without idempotency.

Circuit breaker. With Resilience4j, Polly or a gateway, open the circuit when failure or slow-call rates exceed a threshold, failing fast instead of piling up waiting threads.

Fallbacks. Route to another deployment, region or provider, or a smaller model, typically through an LLM gateway (LiteLLM, cloud API gateways, Azure API Management) that knows the alternatives. Test that prompts work acceptably on the fallback model.

Bulkheads and rate limiting. Limit concurrent LLM calls per feature so slow responses don't exhaust the service's thread or connection pools, and rate-limit client-side to stay within quotas and share them fairly between features.

Graceful degradation. Cached answers, a simpler non-LLM feature, a queued "we'll email you" path, or a clear message.

How it works

  1. Bulkhead permit -> rate limiter -> circuit breaker -> call with timeout.
  2. Retryable error -> backoff with jitter -> retry (max 2-3).
  3. Breaker open or retries exhausted -> fallback model/provider.
  4. Fallback fails -> degraded response.
  5. Metrics: latency, 429s, breaker state, fallback rate.

Example

@Retry(name = "llm")                       // 429/5xx, exponential backoff + jitter, max 3
@CircuitBreaker(name = "llm", fallbackMethod = "fallbackModel")
@Bulkhead(name = "llm", type = Bulkhead.Type.SEMAPHORE)   // e.g. max 50 concurrent
public String summarise(String text) {
    return primaryClient.complete(text, Duration.ofSeconds(30));
}

String fallbackModel(String text, Throwable t) {
    try { return secondaryClient.complete(text, Duration.ofSeconds(20)); }
    catch (Exception e) { return "Summary unavailable right now; please try again shortly."; }
}

Common mistakes

  • Default HTTP timeouts (often far too long or infinite).
  • Retries in the SDK, the gateway and the app simultaneously.
  • Fallback model never tested with the prompts.
  • Retrying a stream from the start and duplicating output to the user.

How to answer in the interview

"LLM calls are slow, variable and rate-limited, so I apply the usual remote-dependency patterns tuned for them. Timeouts account for generation length, with a short connect timeout, bounded max tokens and streaming for long outputs. Retries use exponential backoff with jitter on 429 and 5xx, honour Retry-After, and are limited, at one layer only. A circuit breaker stops hammering a failing provider, and a gateway falls back to another deployment, region or provider. Bulkheads cap concurrent calls so slow responses don't exhaust threads, rate limits protect quotas, and users get a graceful degraded response."

Likely follow-up questions

  • Why is retrying a stream harder? Partial output was already sent; you must resume, discard, or clearly restart.
  • Fallback quality? Evaluate prompts on the fallback model in CI.
  • Rate limits across many pods? Central gateway or distributed rate limiter.
