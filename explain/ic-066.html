How would you structure Terraform repositories for a large organisation?

Infrastructure as Code · design · levels senior

In one line

Separate reusable, versioned modules from live configuration; organise live code by account/environment, region and component, each a small root module with its own state calling pinned module versions; choose monorepo vs repo-per-team by ownership needs and use CODEOWNERS and path-based pipelines.

Detailed explanation

Large organisations fail with Terraform in two typical ways: one giant configuration with thousands of resources, slow plans and a huge blast radius, or hundreds of copy-pasted folders that drift apart. The structure that works rests on a few principles.

Modules versus live code. Modules are libraries: a VPC, an EKS cluster, a service with its database and alarms. They live in their own repositories or a modules monorepo, are tested (static checks, terraform test, integration tests), and are released with semantic version tags to a private registry. Live configuration is what is actually deployed; it contains almost no logic, just module calls with inputs and pinned versions.

Small states. Live code is split by account or subscription, region and component: prod/eu-west-1/network, prod/eu-west-1/eks, prod/eu-west-1/payments. Each directory is a root module with its own backend key. That limits blast radius, keeps plans fast and allows different permissions per component. Components share data through outputs read via terraform_remote_state or, more loosely coupled, data sources and parameter store lookups. Tools such as Terragrunt reduce backend and provider boilerplate; Terraform's newer Stacks feature and similar orchestration tools address the same problem.

Repository layout. A live monorepo gives one place to see everything, makes cross-cutting changes easy, and works well with CODEOWNERS per directory and pipelines that detect changed paths and plan only those. Repository per team gives cleaner permissions and autonomy but makes estate-wide changes harder. Many organisations use a modules repo (or several), a platform live repo and per-team live repos generated from a template.

How it works

  1. Platform team publishes terraform-aws-vpc v3.2.0 to the private registry.
  2. Live repo prod/eu-west-1/network/main.tf calls it with version pinned.
  3. PR changes only that directory; the pipeline plans only it.
  4. CODEOWNERS requires the network team's approval.
  5. Merge triggers apply with that environment's role.

Example

modules/ (separate repos, semver tags)
  terraform-aws-vpc   terraform-aws-eks   terraform-aws-service
live/
  dev/eu-west-1/{network,eks,payments}/
  prod/eu-west-1/{network,eks,payments}/
  prod/us-east-1/{network,eks}/
CODEOWNERS:  /live/*/*/network/  @org/network-team
module "vpc" {
  source  = "app.terraform.io/acme/vpc/aws"
  version = "3.2.0"
  cidr    = "10.20.0.0/16"
}

Common mistakes

  • One state per environment containing everything.
  • Modules referenced by branch instead of version tag.
  • Business logic duplicated in live directories instead of modules.
  • Deep chains of terraform_remote_state dependencies that are hard to change.

How to answer in the interview

"I separate modules from live configuration. Modules are reusable, tested and released with semantic versions to a private registry. Live configuration is organised by account, region and component, like prod/eu-west-1/network, where each directory is a small root module with its own state that just calls pinned module versions. That keeps plans fast and blast radius small. For the live code I usually prefer a monorepo with CODEOWNERS per path and pipelines that plan only changed directories, because it gives visibility and easy cross-cutting changes, though per-team repositories make sense when ownership and permissions need stronger separation."

Likely follow-up questions

  • How do you roll out a module upgrade to 40 environments safely? Automated PRs per environment, in waves from dev to prod, each with a reviewed plan.
  • How do stacks share values? Outputs via remote state or published parameters, kept to a minimum.
  • Do you need Terragrunt? Not required; it helps reduce repetition at large scale.
