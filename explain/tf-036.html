An autoscaling group or node pool keeps having its instance count reset by Terraform after the autoscaler changes it. How do you fix it?

Terraform · scenario · levels mid, senior

In one line

The autoscaler changes the instance count at runtime, Terraform sees that as drift and reverts it; fix it by giving each attribute one owner: Terraform owns min/max and scaling policy, the autoscaler owns the actual count, enforced with lifecycle { ignore_changes = [...] }.

Detailed explanation

Terraform compares three things on every plan: the configuration, the state and the real object. When an AWS Auto Scaling group, an EKS managed node group or an AKS node pool with autoscaling enabled scales from 3 to 7 nodes, the real object now says 7 while the code still says 3. Terraform treats that as drift and the plan proposes setting the count back to 3. An apply at peak time terminates four nodes: a real outage pattern, not just plan noise.

The root cause is shared ownership of a single attribute. The clean rule is that every attribute is managed by exactly one system. Terraform should manage the boundaries and behaviour: min_size, max_size, instance types, launch template, scaling policies, and for AKS min_count, max_count and auto_scaling_enabled. The autoscaler owns the current count. You still set an initial value so the first create works, then tell Terraform to stop tracking it with ignore_changes.

Note that ignore_changes only stops Terraform from proposing updates for that attribute; the value still lives in state, and a change elsewhere that forces replacement still recreates the resource. The same pattern applies to replicas managed by an HPA or tags added by policy.

How it works

  1. Identify the attribute that flips in every plan (for example desired_capacity or node_count).
  2. Decide the owner: the autoscaler owns the count; Terraform owns limits and configuration.
  3. Keep a sensible initial value in code so creation works.
  4. Add lifecycle { ignore_changes = [that_attribute] } to the resource.
  5. Run a plan and confirm the count no longer appears as a change.
  6. Document why the ignore exists with a comment, so nobody removes it later.

Example

resource "aws_autoscaling_group" "web" {
  name             = "web-prod"
  min_size         = 3
  max_size         = 20
  desired_capacity = 3          # initial value only
  # ...launch template, subnets, policies...

  lifecycle {
    # Owned by the scaling policies / cluster autoscaler at runtime
    ignore_changes = [desired_capacity]
  }
}

resource "azurerm_kubernetes_cluster_node_pool" "user" {
  name                  = "user"
  kubernetes_cluster_id = azurerm_kubernetes_cluster.main.id
  vm_size               = "Standard_D4s_v5"
  auto_scaling_enabled  = true
  min_count             = 3
  max_count             = 15
  node_count            = 3

  lifecycle {
    ignore_changes = [node_count]
  }
}

Common mistakes

  • Using ignore_changes = all, which hides every future change, including ones you meant to make.
  • Ignoring min_size or max_size too, so Terraform can no longer change the limits.
  • Forgetting the default node pool in AKS, where the path is default_node_pool[0].node_count.
  • Removing the ignore during a refactor and resetting production capacity on the next apply.

How to answer in the interview

"This is an ownership conflict. The autoscaler legitimately changes the desired count, Terraform sees it as drift, and an apply resets it, which can kill nodes during peak load. My rule is that each attribute has one owner. Terraform manages the min and max, instance types and scaling policies, and the autoscaler owns the current count. So I keep an initial value in code and add a lifecycle ignore_changes on desired_capacity, or node_count for an AKS pool with autoscaling. I add a comment explaining why, and I apply the same thinking to HPA replicas or policy-added tags."

Likely follow-up questions

  • What is the risk of overusing ignore_changes? Real drift and intended changes become invisible, so code stops describing reality.
  • Does ignore_changes prevent replacement? No, it only suppresses updates to that attribute; use prevent_destroy to guard against deletion.
  • How do you change the desired count deliberately later? Use the autoscaler or CLI, or temporarily remove the ignore in a reviewed change.
