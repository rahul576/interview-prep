What is Istio ambient mode, and how does it differ from the sidecar model?

Kubernetes · concept · levels mid, senior, lead

In one line

Ambient mode is Istio's sidecar-less data plane: a per-node ztunnel provides L4 mTLS, identity and authorization for every pod, and optional waypoint proxies (Envoy) are added only where L7 features are needed.

Detailed explanation

In the classic sidecar model, an Envoy proxy is injected into every pod. All traffic passes through it, giving mTLS, retries, timeouts, traffic splitting, header-based authorization and rich telemetry. The costs are real: every pod pays CPU and memory for its proxy, every hop crosses two proxies, upgrading Istio means restarting every workload, and sidecars complicate Jobs (the proxy keeps the pod alive) and startup ordering.

Ambient mode, generally available since Istio 1.24, splits the mesh into two layers. The secure overlay is provided by ztunnel, a lightweight Rust proxy running as a DaemonSet on each node. Traffic from pods in an ambient-enabled namespace is redirected into ztunnel, which wraps it in mTLS using the workload's SPIFFE identity (tunnelled over HBONE, HTTP CONNECT on port 15008) and enforces L4 authorization policies. Enrolling a namespace is just a label, and pods do not need to restart.

For L7 features (HTTP routing, retries, fault injection, JWT checks, path-based authorization) you deploy a waypoint proxy, an Envoy deployment per namespace or per service, defined with the Gateway API. Traffic for services that use a waypoint is routed through it. So you pay the Envoy cost only for services that need L7, and scale waypoints independently of the application.

How it works

  1. Install Istio with the ambient profile (istiod, istio-cni, ztunnel).
  2. Label a namespace istio.io/dataplane-mode=ambient; existing pods join with no restart.
  3. istio-cni redirects pod traffic to the node's ztunnel.
  4. ztunnels establish mTLS tunnels between nodes and enforce L4 AuthorizationPolicy.
  5. Where L7 is needed, create a waypoint and label the namespace or service to use it.
  6. Waypoints apply HTTP routes, retries and L7 policy before forwarding.

Example

istioctl install --set profile=ambient
kubectl label namespace shop istio.io/dataplane-mode=ambient
istioctl waypoint apply -n shop --enroll-namespace

Common mistakes

  • Assuming ztunnel does HTTP routing; it is L4 only.
  • Forgetting a waypoint and wondering why L7 policies are not enforced.
  • Thinking ambient means no Envoy at all.
  • Mixing sidecar and ambient pods without checking interoperability for your Istio version.

How to answer in the interview

"In the sidecar model every pod gets an Envoy proxy, which gives full L7 features but costs resources per pod and needs pod restarts to inject or upgrade. Ambient removes sidecars: a ztunnel on each node transparently provides mTLS identity, encryption and L4 authorization for all pods in labelled namespaces, with no restarts. When a service needs HTTP routing, retries or L7 authorization, I add a waypoint proxy just for that namespace or service. So I get zero-trust mTLS everywhere cheaply and pay for L7 only where it's needed."

Likely follow-up questions

  • Which workloads stay on sidecars? Ones needing per-pod L7 behaviour or features not yet supported in ambient, or VMs and multi-cluster setups depending on version.
  • Is ztunnel a single point of failure? It is per node, so its failure affects only that node's pods; it is run and upgraded as a DaemonSet.
  • How is identity provided? SPIFFE identities from service accounts, certificates issued by istiod.
