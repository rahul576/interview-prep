How do you keep container images up to date with security patches?

Docker · concept · levels mid

In one line

Never patch running containers; rebuild and redeploy: let Renovate/Dependabot bump base images, rebuild on a schedule, continuously rescan images in the registry for new CVEs, automatically test and redeploy, and track which image versions run where and how old they are.

Detailed explanation

Containers are immutable. Running apt-get upgrade inside a running container changes only its writable layer: the fix disappears on the next restart, other replicas stay vulnerable, and the image in the registry still contains the old packages. Patching means producing a new image and rolling it out.

Vulnerabilities enter images through the base OS packages, the language runtime and the application dependencies, and new CVEs are published every day against images that were clean when built. So patching has two triggers. First, upstream updates: Renovate or Dependabot watch FROM lines (tags and pinned digests) and dependency lock files and open pull requests when new versions appear, which then run through the normal CI tests. Second, time: a scheduled rebuild (for example weekly) rebuilds images even without code changes so they pick up refreshed base images, using --pull and a fresh cache for the package layer.

Continuous scanning catches what is already deployed. Registries (ECR enhanced scanning, ACR with Defender, Harbor with Trivy, Docker Scout) or a scheduled Trivy job rescan stored images and alert on new critical findings, ideally filtered by whether a fix is available and whether the image is actually running. The pipeline then tests and redeploys automatically, with a progressive rollout so a bad base update is caught early.

Finally, keep an inventory: which image digest runs in which cluster, from which commit, and how old it is. Alert on images older than a policy (say 30 days) and use SBOMs to answer "are we affected by this CVE?" within minutes.

How it works

  1. Bots open PRs for new base images and dependencies.
  2. CI builds, tests and scans the new image.
  3. A schedule rebuilds unchanged services regularly.
  4. Registry scanning re-evaluates stored images daily.
  5. CD deploys patched images progressively and records versions.

Example

{
  "extends": ["config:recommended", "docker:pinDigests"],
  "packageRules": [
    { "matchDatasources": ["docker"], "matchUpdateTypes": ["patch", "digest"], "automerge": true }
  ]
}
# GitHub Actions: weekly rebuild
on:
  schedule: [{ cron: "0 3 * * 1" }]
jobs:
  rebuild:
    steps:
      - run: docker buildx build --pull --no-cache-filter runtime -t ghcr.io/acme/api:${{ github.sha }} --push .
      - run: trivy image --exit-code 1 --severity CRITICAL --ignore-unfixed ghcr.io/acme/api:${{ github.sha }}

Common mistakes

  • Patching inside running containers.
  • Scanning only at build time.
  • Automerging major base image upgrades without tests.
  • No inventory, so nobody knows which services run the vulnerable version.

How to answer in the interview

"Containers are immutable, so I never apt upgrade inside a running container; I rebuild the image and redeploy. Renovate or Dependabot open PRs when a new base image version or digest is published, and a scheduled pipeline rebuilds images weekly even without code changes so they get patched OS packages. The registry or Trivy continuously rescans stored images because new CVEs appear in old images, and alerts on critical ones. The pipeline tests and redeploys automatically with a progressive rollout. I also keep an inventory of which image versions run where and alert when an image is too old."

Likely follow-up questions

  • How do you avoid breaking apps on automatic base updates? Pin majors, automerge only patch/digest updates after tests, canary deployments.
  • How do you prioritise CVEs? Severity, fix availability, exploitability, and whether the package is actually used at runtime.
  • What helps answer "are we affected"? SBOMs stored per image.
