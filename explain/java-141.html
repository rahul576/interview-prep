How do you protect a Java web application against the OWASP Top 10, such as SQL injection and XSS?

Security · concept · levels mid, senior

In one line

Defend in layers: parameterised queries against injection, contextual output encoding plus a CSP against XSS, server-side authorization on every request and object, CSRF protection and narrow CORS, patched dependencies, secrets outside code, secure headers and logging.

Detailed explanation

The OWASP Top 10 is a ranking of the most common web application risk categories. In the 2021 list, Broken Access Control is number one, followed by cryptographic failures and injection (which now includes XSS). The 2025 edition keeps broken access control first and adds more emphasis on software supply chain and misconfiguration. The practical point is that no single control covers it; you need a set of habits.

Injection: never build SQL, JPQL, LDAP or shell commands by concatenating input. Use PreparedStatement, JPA named parameters or Spring Data methods, and whitelist dynamic identifiers like sort columns. XSS: treat all data as untrusted when rendering. Thymeleaf escapes by default with th:text; avoid th:utext and innerHTML with user data, and frameworks like React escape too. Add a Content-Security-Policy to block inline scripts as a second line. Broken access control: every endpoint checks authorization on the server, including object ownership (an IDOR check), with deny by default.

CSRF: Spring Security enables CSRF tokens by default, which you keep for cookie-based sessions; stateless bearer-token APIs can disable it. Configure CORS with specific origins. Vulnerable components: use dependency scanning (OWASP Dependency-Check, Snyk, Dependabot) and patch. Cryptographic failures: TLS everywhere, passwords hashed with bcrypt or Argon2. Misconfiguration: disable verbose errors, lock down Actuator, set security headers (HSTS, X-Content-Type-Options, frame-ancestors). Logging and monitoring: record authentication failures and access denials.

How it works

  1. Validate input at the boundary with Bean Validation (types, length, format).
  2. Bind data to queries as parameters only.
  3. Encode output for the context (HTML, attribute, JavaScript, URL) and apply CSP.
  4. Authorise every request in the filter chain and every object in the service layer.
  5. Scan dependencies and code (SAST, DAST) in CI and patch regularly.
  6. Monitor security events and rate-limit login and sensitive endpoints.

Example

// SQL injection: parameter binding, not concatenation
@Query("select o from Order o where o.customer.id = :customerId and o.status = :status")
List<Order> find(@Param("customerId") long customerId, @Param("status") Status status);

// Security headers and CSP
http.headers(h -> h
        .contentSecurityPolicy(c -> c.policyDirectives("default-src 'self'; script-src 'self'; frame-ancestors 'none'"))
        .httpStrictTransportSecurity(Customizer.withDefaults()));

// Object-level check
@PreAuthorize("@orderSecurity.isOwner(#orderId, authentication)")
public OrderDto getOrder(long orderId) { ... }

Common mistakes

  • Relying on input validation alone to stop XSS instead of output encoding.
  • Hiding admin buttons in the UI but leaving the API unprotected.
  • Disabling CSRF globally in an app that uses session cookies.
  • Never updating libraries until a breach forces it.
  • Returning detailed exception messages that reveal the schema.

How to answer in the interview

"I map controls to the main risks. For injection I only use prepared statements or JPA parameters and whitelist dynamic column names. For XSS I rely on output encoding in the templates or frontend framework and add a Content Security Policy. Broken access control is the top risk, so every endpoint checks authorization on the server, including whether the user owns that object, with deny by default. Spring Security gives CSRF protection for cookie sessions, and CORS is restricted to known origins. Beyond code, I scan dependencies for CVEs in CI, keep secrets in a vault, harden headers and Actuator, and log security events."

Likely follow-up questions

  • What is an insecure direct object reference? Accessing another user's record by changing an id; prevent with ownership checks on every lookup.
  • Stored vs reflected XSS? Stored is saved and served to others; reflected comes back from the request; both are fixed by output encoding.
  • What is SSRF? The server fetches attacker-chosen URLs; restrict outbound destinations and block internal addresses.
