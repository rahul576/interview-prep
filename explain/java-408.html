What Redis data structures do you know, and what are they used for?

Caching · concept · levels mid, senior

In one line

Redis offers strings (values, counters), hashes (objects), lists and streams (queues and logs), sets and sorted sets (membership, leaderboards, rate limiters), plus bitmaps, HyperLogLog and geospatial indexes, each with atomic server-side commands.

Detailed explanation

Picking the right structure lets Redis do the work atomically instead of reading, modifying and writing from the application.

  • Strings: binary-safe values up to 512 MB. Used for cached JSON, feature flags, and atomic counters with INCR/INCRBY. Combined with EXPIRE, a counter per user per minute is a simple fixed-window rate limiter.
  • Hashes: field-value maps, ideal for objects such as a session or user profile, letting you read or update one field (HSET, HINCRBY) without rewriting the whole value. Small hashes are stored compactly.
  • Lists: ordered, push/pop from either end. LPUSH + BRPOP (or BLMOVE for reliable processing) implement simple queues; LTRIM keeps "last N" items such as recent activity.
  • Streams: append-only logs with IDs, consumer groups, acknowledgements (XACK) and pending-entry tracking, good for event processing when Kafka is overkill.
  • Sets: unique unordered members, with intersections and unions: tags, "users who liked", deduplication.
  • Sorted sets: members ordered by a score with O(log N) updates: leaderboards, priority queues, delayed jobs (score = run time), and sliding-window rate limiting (score = timestamp).
  • Bitmaps: bit operations on strings, for example one bit per user id for daily active users.
  • HyperLogLog: approximate distinct counts (about 0.81% standard error) in roughly 12 KB per key.
  • Geo: built on sorted sets; GEOADD and GEOSEARCH find nearby points.

Redis Stack and Redis 8 also add JSON documents, search, time series and probabilistic structures such as Bloom filters.

How it works

  1. Map each use case to its access pattern (lookup, ordering, uniqueness, counting).
  2. Choose the structure whose commands perform that pattern atomically.
  3. Design key names (user:42:session) and TTLs.
  4. Use pipelines or Lua/MULTI when several commands must be combined.
  5. Watch memory usage and big keys.

Example

INCR   rate:user:42:202611211030        # fixed-window counter
EXPIRE rate:user:42:202611211030 60
HSET   session:abc user 42 role admin    # object
ZADD   leaderboard 1500 "alice" 1720 "bob"
ZREVRANGE leaderboard 0 9 WITHSCORES     # top 10
PFADD  visitors:2026-11-21 u1 u2 u3      # unique count
PFCOUNT visitors:2026-11-21
XADD   orders * id 991 total 49.90        # stream
XREADGROUP GROUP billing w1 COUNT 10 STREAMS orders >

Common mistakes

  • Storing big objects as JSON strings and rewriting them for every field change.
  • Using KEYS * in production instead of SCAN.
  • Creating huge single keys (a list or set with millions of members) that block Redis.
  • Using lists as reliable queues without acknowledgement, losing messages on crash.

How to answer in the interview

"Strings hold simple values and atomic counters with INCR, often with a TTL for rate limits or cached JSON. Hashes store objects like sessions field by field. Lists work as simple queues, and Streams give a persistent log with consumer groups and acknowledgements. Sets give unique membership, and sorted sets keep members ordered by score, which is perfect for leaderboards, delayed jobs and sliding-window rate limiters. There are also bitmaps for compact flags like daily active users, HyperLogLog for approximate unique counts in about 12 KB, and geo commands for nearby searches. I pick the structure so that Redis performs the operation atomically on the server."

Likely follow-up questions

  • Sliding-window rate limiter with a sorted set? ZREMRANGEBYSCORE old entries, ZADD now, ZCARD to count, all in a Lua script or MULTI.
  • Streams vs Kafka? Streams are simpler and in-memory; Kafka is better for large retention and very high throughput.
  • Why avoid big keys? Redis is largely single-threaded per command, so operations on huge keys block other clients.
