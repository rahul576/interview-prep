How do you debug a running pod whose image has no shell or debugging tools?

Kubernetes · concept · levels entry, mid, senior

In one line

Distroless images have no shell by design, so use kubectl debug: add an ephemeral container with tools to the running pod (with --target to share the app's process namespace), make a copy of the pod with a different image or command (--copy-to), or debug the node with a privileged pod (kubectl debug node/...).

Detailed explanation

Minimal images contain only the app and its runtime, shrinking the attack surface, but kubectl exec -it pod -- sh fails with "executable file not found".

Ephemeral containers (stable since 1.25) are temporary containers added to an existing pod through the ephemeralcontainers subresource. They share the pod's network namespace and volumes (if mounted), can't have ports or probes, are never restarted, and stay in the pod spec until the pod is deleted. kubectl debug -it pod --image=busybox:1.36 --target=app adds one; --target places it in the process namespace of the app container, so ps shows the app's processes and /proc/<pid>/root exposes its filesystem, and you can inspect open files, environment and sockets. Tool images such as nicolaka/netshoot provide tcpdump, dig, curl and ss. --profile (general, netadmin, sysadmin, restricted) sets the security context, for example adding NET_ADMIN for packet capture.

Pod copies: kubectl debug pod --copy-to=debug-pod --container=app --image=... or -- sleep infinity creates a duplicate pod where you can swap the image or override the command, useful for a CrashLoopBackOff where the original container dies too fast to inspect. --share-processes enables a shared process namespace in the copy. Remember the copy may receive traffic if labels match; --same-node helps reproduce node-specific problems.

Node debugging: kubectl debug node/node-3 -it --image=ubuntu starts a pod in the host's namespaces with the node filesystem at /host; chroot /host then lets you run crictl, journalctl -u kubelet or check disk usage, without SSH.

Because ephemeral containers can read memory, secrets and traffic of production pods, restrict the pods/ephemeralcontainers and nodes/proxy related permissions via RBAC and audit their use.

How it works

  1. kubectl debug patches the pod's ephemeralcontainers subresource.
  2. Kubelet starts the tool container in the pod's namespaces.
  3. With --target, it joins the app container's PID namespace.
  4. You attach interactively and investigate.
  5. On exit the container stops but remains listed until the pod is replaced.

Example

kubectl debug -it orders-6d8f-abc --image=nicolaka/netshoot --target=orders --profile=netadmin
# inside: ps aux; ss -tnp; cat /proc/1/environ | tr '\0' '\n'; tcpdump -i eth0 port 5432

kubectl debug orders-6d8f-abc -it --copy-to=orders-debug --container=orders -- sh   # needs an image with sh
kubectl debug orders-6d8f-abc --copy-to=orders-debug --set-image=orders=registry.example.com/orders:1.8.2-debug

kubectl debug node/node-3 -it --image=ubuntu:24.04
# chroot /host; crictl ps; journalctl -u kubelet --since "10 min ago"

Common mistakes

  • Adding shells to production images "just in case".
  • Forgetting --target, so the app's processes are invisible.
  • Leaving debug pod copies running with production labels.
  • Allowing everyone to create ephemeral containers in production.

How to answer in the interview

"Distroless images have no shell by design, so kubectl exec doesn't help. I use kubectl debug to add an ephemeral container with a tools image like busybox or netshoot to the running pod without restarting it; with --target set to the app container it shares the process namespace, so I can see its processes, files and connections. If the container crashes too quickly, kubectl debug --copy-to creates a copy where I change the image or command. For node issues, kubectl debug node starts a privileged pod with the host filesystem mounted. In production, ephemeral containers are restricted by RBAC and audited."

Likely follow-up questions

  • Why audit ephemeral containers? They can read secrets, memory and traffic of production workloads.
  • Can you remove an ephemeral container? No, it stays in the spec until the pod is deleted.
  • What does --profile do? Applies a preset security context, such as netadmin for packet capture.
