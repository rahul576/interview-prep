Users complain that the assistant is slow during business-hour peaks but fine at night. What is going on?

LLMOps & RAG · scenario · levels mid, senior

In one line

Load-dependent latency points to capacity: provider rate limits (429s absorbed by retries with backoff) or busy shared capacity, request queueing on too few self-hosted replicas, slow or mis-signalled autoscaling, or saturated shared components such as vector search; fix with more quota or provisioned throughput, load balancing across deployments, scheduled pre-scaling, better scaling signals and moving batch work off-peak.

Detailed explanation

"Fine at night, slow at 10 am" means the system is close to a limit during peaks. Confirm by plotting, per hour, request rate against queue time, time to first token (TTFT), tokens per second, 429 rate, retry count and per-stage latency.

Hosted APIs. Quotas are typically expressed as requests and tokens per minute. At peak, the app hits them and receives 429 errors; the SDK retries with exponential backoff, so users never see errors, only slowness. The provider's shared capacity may also be slower at global peak times. Options: request higher quota, buy provisioned throughput (reserved capacity, for example PTUs in Azure OpenAI or provisioned throughput in Bedrock and Vertex), spread load across deployments or regions via a gateway, and use priority tiers where offered.

Self-hosted models. Requests queue when concurrent load exceeds what the replicas can batch. TTFT climbs sharply once the KV cache is full. Autoscaling often reacts too late: provisioning a GPU node and loading a large model can take many minutes. It may also scale on CPU, which says nothing about GPU load. Use metrics like queue length, running requests or KV cache utilisation (vLLM exposes these), scheduled pre-scaling before business hours, and warm spare capacity.

Shared dependencies. Vector search, rerankers, embedding services, databases and the API layer may saturate too; per-stage traces reveal which.

Mixed workloads. Batch jobs sharing the same quota or GPUs steal capacity. Move them to batch APIs, separate deployments, or night time.

How it works

  1. Hourly dashboards: RPS, 429s, retries, queue time, TTFT, per-stage latency.
  2. Identify the saturated component.
  3. Hosted: raise quota, provisioned throughput, multi-deployment routing.
  4. Self-hosted: scale on queue/KV metrics; pre-scale on schedule.
  5. Separate batch from interactive traffic.
  6. Load test at expected peak plus headroom.

Common mistakes

  • Retries hiding 429s, so nobody notices the rate limit.
  • Autoscaling GPUs on CPU utilisation.
  • Batch jobs competing with interactive traffic.
  • No load test at real peak concurrency.

How to answer in the interview

"Latency that tracks load means we're hitting a capacity limit. With a hosted API, peak traffic often hits rate limits, and the client silently retries 429s with backoff, which users experience as slowness. With self-hosted models, requests queue on too few replicas, and autoscaling is too slow because GPU nodes and model loading take minutes, or it scales on CPU. Shared pieces like vector search can saturate too. I'd check hourly metrics for queue time, TTFT, 429s and retries per stage, then add quota or provisioned throughput, balance across deployments, pre-scale before business hours, scale on queue depth, and move batch work off-peak."

Likely follow-up questions

  • Protect interactive users from batch? Separate deployments or quotas, priority queues, batch APIs.
  • Provisioned throughput worth it? When steady peak load is high enough that reserved capacity beats pay-as-you-go plus throttling.
  • Graceful degradation? Smaller model fallback at peak, shorter outputs, queue messages.
