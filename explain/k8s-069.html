How do you implement zero-trust networking inside a Kubernetes cluster?

Kubernetes · design · levels senior, lead

In one line

Zero trust means no implicit trust for in-cluster traffic: default-deny NetworkPolicies for ingress and egress, allow only required flows by labels, mTLS with workload identities via a mesh, L7 authorization policies, egress control including DNS-aware rules, and observe flows before enforcing.

Detailed explanation

By default every pod can talk to every other pod in a Kubernetes cluster. An attacker who compromises one container can scan and reach databases, internal admin APIs and the cloud metadata endpoint. Zero trust replaces "inside the network = trusted" with explicit, identity-based permission for each flow.

Layer 3/4 segmentation: in every namespace, a default-deny NetworkPolicy for both ingress and egress, then specific allow policies using pod and namespace labels (not IPs, which change constantly). Remember to allow DNS egress to CoreDNS, or everything breaks. Enforcement requires a CNI that supports policies (Calico, Cilium, cloud CNIs with a policy engine). The newer AdminNetworkPolicy API lets platform teams set cluster-wide rules that namespaces cannot override.

Identity and encryption: a service mesh (Istio, including ambient mode, or Linkerd) or Cilium's mutual authentication gives every workload a cryptographic identity, usually SPIFFE IDs derived from service accounts, and encrypts service-to-service traffic with mTLS. Set mTLS to STRICT so plaintext is rejected.

Authorization: identity-based policies allow, say, only the orders service account to call payments, and at L7 only POST /charges. This stays correct even when pods move or IPs are reused.

Egress: restrict which external destinations pods may reach, using FQDN-aware policies (Cilium, Calico Enterprise) or an egress gateway, and block the cloud metadata IP for workloads that do not need it.

Rollout: observe real traffic first with Hubble, Calico flow logs or mesh telemetry, generate policies from it, apply in audit or permissive mode, then enforce namespace by namespace.

How it works

  1. Map actual flows with flow logs or mesh telemetry.
  2. Apply default-deny ingress and egress per namespace, allowing DNS.
  3. Add allow policies by labels for each required flow.
  4. Enable mesh mTLS in permissive mode, then STRICT.
  5. Add identity-based L7 AuthorizationPolicies for sensitive services.
  6. Restrict egress to approved domains and block metadata access.

Example

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny, namespace: payments }
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
  egress:
    - to:
        - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: kube-system } }
          podSelector: { matchLabels: { k8s-app: kube-dns } }
      ports: [{ protocol: UDP, port: 53 }, { protocol: TCP, port: 53 }]
---
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata: { name: payments-allow-orders, namespace: payments }
spec:
  selector: { matchLabels: { app: payments } }
  action: ALLOW
  rules:
    - from: [{ source: { principals: ["cluster.local/ns/orders/sa/orders"] } }]
      to: [{ operation: { methods: ["POST"], paths: ["/charges"] } }]

Common mistakes

  • Default deny without allowing DNS.
  • Using IP blocks for pod-to-pod rules.
  • mTLS left in permissive mode forever.
  • Enforcing before observing, causing outages.

How to answer in the interview

"Zero trust means nothing is trusted just because it's inside the cluster. I start with default-deny ingress and egress NetworkPolicies in every namespace and allow only the required flows using labels, including DNS. On top, a mesh like Istio or Linkerd, or Cilium mutual auth, gives each workload a SPIFFE identity and strict mTLS. Authorization policies then allow, for example, only the orders service account to POST to payments. Egress is limited to approved domains. To avoid outages I observe flows with Hubble or mesh telemetry first and enforce gradually."

Likely follow-up questions

  • Why are IP rules a poor fit? Pod IPs are ephemeral and reused; labels and identities follow workloads.
  • NetworkPolicy vs mesh policy? NetworkPolicy is L3/L4 by network; mesh policy is identity-based and can be L7; use both.
  • How to protect the metadata endpoint? Deny egress to 169.254.169.254 and use workload identity.
