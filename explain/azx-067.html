What is node auto provisioning on AKS, and how does it differ from the cluster autoscaler?

Azure Kubernetes (AKS) · concept · levels mid, senior

In one line

Node auto provisioning (NAP) is managed Karpenter on AKS: it reads pending pods' requirements and creates nodes with dynamically chosen VM sizes, then consolidates underused nodes; the cluster autoscaler only scales predefined node pools between min and max counts.

Detailed explanation

With the cluster autoscaler, you design node pools in advance, for example D4s_v5 for general workloads and E8s_v5 for memory-heavy ones. When pods are pending, it adds nodes of that fixed size; when nodes are underused, it removes them. If your guess about VM size is wrong, you waste capacity or have pods that fit nowhere, and many teams end up with lots of pools.

NAP works pod-first. When pods are pending, it evaluates their resource requests, node selectors, affinity, topology spread and tolerations, and picks a VM size that fits, from a broad range of allowed SKUs. One large pending pod may get a large VM; many small pods may be bin-packed onto one node.

Constraints are expressed in Kubernetes resources:

  • NodePool (karpenter.sh): allowed VM families or sizes (karpenter.azure.com/sku-family), capacity type (spot or on-demand), zones, architecture, taints, limits on total CPU and memory, and disruption settings.
  • AKSNodeClass (karpenter.azure.com): Azure-specific settings such as the OS image family, OS disk size and other node configuration.

NAP also does consolidation: it removes empty nodes and replaces several underused nodes with fewer or cheaper ones, and handles drift, replacing nodes whose configuration no longer matches the NodePool or node image. This disruption is controlled with disruption budgets, consolidation policies and the karpenter.sh/do-not-disrupt annotation, plus PodDisruptionBudgets.

How it works

  1. Enable NAP: az aks update --node-provisioning-mode Auto.
  2. Define NodePools and AKSNodeClasses (defaults are created for you).
  3. A pod is pending; NAP computes a fitting SKU and creates a node.
  4. The node joins and the pod is scheduled.
  5. Consolidation and drift checks run continuously within disruption budgets.

Example

apiVersion: karpenter.sh/v1
kind: NodePool
metadata: { name: general }
spec:
  template:
    spec:
      nodeClassRef: { group: karpenter.azure.com, kind: AKSNodeClass, name: default }
      requirements:
      - { key: karpenter.azure.com/sku-family, operator: In, values: [D, E] }
      - { key: karpenter.sh/capacity-type, operator: In, values: [on-demand, spot] }
  limits: { cpu: "400" }
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    budgets:
    - nodes: "10%"

Common mistakes

  • Pods without resource requests, so NAP cannot size nodes correctly.
  • No limits on NodePools, allowing runaway cost.
  • Ignoring disruption settings for latency-sensitive workloads.
  • Running cluster autoscaler and NAP on the same pools.

How to answer in the interview

"Node auto provisioning is the managed Karpenter on AKS. Instead of scaling fixed pools, it looks at pending pods' requests, selectors, affinity and tolerations and creates a node with a fitting VM size from the families I allow. I describe constraints in NodePool resources, like VM families, spot or on-demand, zones and limits, and Azure-specific settings in AKSNodeClass. It consolidates underused nodes and handles drift. The cluster autoscaler only grows and shrinks predefined pools, so you have to guess sizes. NAP usually gives better utilisation and cost."

Likely follow-up questions

  • How do you protect latency-sensitive pods? PDBs, do-not-disrupt annotations, disruption budgets and consolidation only in a maintenance window.
  • How do you use spot safely? Allow spot for tolerant workloads and on-demand fallback in the NodePool.
  • What drives right sizing? Accurate resource requests on pods.
