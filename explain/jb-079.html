How would you process a large collection without creating unnecessary intermediate objects?

Java 8+ Features · scenario · levels senior, lead

In one line

Keep work in one lazy stream pipeline, use primitive streams to avoid boxing, collect directly into the final structure with downstream collectors, stream from the source in batches (files, DB cursors, pagination), and use plain loops on proven hot paths, verifying with an allocation profiler.

Detailed explanation

Unnecessary objects cost allocation time, GC pressure and cache misses. With large collections the common culprits are intermediate lists, boxed numbers, repeated transformations and loading everything into memory at once.

Single pipeline: chaining filter, map and collect in one stream fuses them into one pass with no temporary lists. The anti-pattern is list1 = filter...collect; list2 = list1.stream().map...collect; ....

Primitive streams: Stream<Long> boxes every value. mapToLong(Order::amount).sum(), IntStream.range, and collectors like summingLong keep primitives. Store data in primitive arrays where practical.

Collect once into the target shape: groupingBy(Order::customerId, summingLong(Order::amount)) produces the result directly instead of grouping into lists and summing later. Pre-size collections (new HashMap<>(expected)) when building them manually, and avoid sorted unless needed.

Don't load everything: read files with Files.lines (lazy, closed with try-with-resources), read databases with a JDBC cursor and fetch size, Spring Data Stream<T> query methods inside a read-only transaction, or keyset pagination in batches, and use projections (records with only needed columns) rather than full entities. Detach or clear the persistence context periodically in batch jobs.

Hot paths: a simple for loop over an array can beat streams in tight code; reuse buffers like StringBuilder. Measure with JMH and inspect allocations with JFR or async-profiler before optimising.

How it works

  1. Identify the data source and stream it lazily.
  2. Express all transformations in one pipeline.
  3. Use primitive specialisations for numeric work.
  4. Use downstream collectors to aggregate in one pass.
  5. Profile allocation rate; refine hot spots with loops or primitive structures.

Example

// Wasteful: three intermediate lists and boxed Longs
List<Order> paid = orders.stream().filter(Order::isPaid).collect(toList());
List<Long> amounts = paid.stream().map(Order::amount).collect(toList());
long total = amounts.stream().reduce(0L, Long::sum);

// Efficient: one pass, no boxing
long total2 = orders.stream().filter(Order::isPaid).mapToLong(Order::amount).sum();

// Sum per customer for a million orders, directly
Map<String, Long> perCustomer = orders.stream()
    .collect(Collectors.groupingBy(Order::customerId,
             HashMap::new, Collectors.summingLong(Order::amount)));

// Stream from the DB instead of loading a List (Spring Data JPA)
@QueryHints(@QueryHint(name = "org.hibernate.fetchSize", value = "500"))
@Query("select new com.shop.OrderRow(o.customerId, o.amount) from Order o")
Stream<OrderRow> streamAll();     // use inside @Transactional(readOnly = true), in try-with-resources

Common mistakes

  • Collecting to a list after every step.
  • Using Stream<Integer> arithmetic instead of IntStream.
  • Calling findAll() on millions of rows and streaming the resulting list.
  • Optimising without measuring allocation and GC behaviour.

How to answer in the interview

"I keep the work in one lazy pipeline instead of building intermediate lists, so filter, map and the final collect process each element once. For numbers I use primitive streams like mapToLong or IntStream to avoid boxing. I collect directly into the structure I need, for example groupingBy with a summing downstream collector, rather than collecting and transforming again. If the data comes from a file or database I stream it from the source, with Files.lines, a JDBC cursor with a fetch size, or pagination, instead of loading everything. On very hot paths a plain loop is fine, and I confirm with an allocation profiler like JFR."

Likely follow-up questions

  • How would you sum the amount per customer for a million orders? One pass with groupingBy(customerId, summingLong(amount)), ideally pushed to SQL GROUP BY.
  • Why are boxed streams slow? Each value is a heap object, adding allocation, GC and indirection.
  • When should aggregation happen in the database? Usually when data lives there; GROUP BY avoids transferring rows.
