Someone deleted an S3 bucket or storage account manually that Terraform manages. What happens on the next plan, and what do you do?

Terraform · scenario · levels entry, mid, senior

In one line

On the next plan, refresh finds the object missing, Terraform drops it from state and proposes to create it again; applying gives an empty bucket or account, so first assess and restore the data, investigate via audit logs, and prevent repeats with locks, deny policies, prevent_destroy and least privilege.

Detailed explanation

Terraform does not get alarmed by a deleted resource. During refresh, the provider asks the API for the bucket or storage account, receives "not found", and Terraform removes it from the in-memory state. The plan then shows it as to be created, often with dependent resources (bucket policy, versioning, lifecycle rules, event notifications, private endpoints, role assignments) also being recreated or updated. Applying would create a new, empty resource with the same name and configuration.

That is fine for infrastructure, but the data is gone. So do not apply blindly. First, assess impact and recovery options. For S3, a deleted bucket cannot be undeleted; recovery comes from cross-region replication, AWS Backup for S3 or application-level backups. Bucket names are global, so someone else could even claim the name. For Azure, a deleted storage account can sometimes be recovered for a limited period (if the name has not been reused) through the portal or support, and blob soft delete does not help once the account itself is gone. Recover first if possible, then plan: if the account comes back, Terraform will see it again and plan no create.

Then investigate who and why using CloudTrail (DeleteBucket) or the Azure Activity Log. Usually it is someone cleaning up with too much access, or another automation.

Prevention happens in layers: least privilege, so humans do not have delete rights in production; cloud-side protection such as Azure resource locks (CanNotDelete), AWS SCPs or bucket policies denying s3:DeleteBucket, S3 Object Lock for critical data; lifecycle { prevent_destroy = true } to stop Terraform itself from destroying it; and backups or replication stored separately.

How it works

  1. Refresh: provider reports resource not found.
  2. Terraform removes it from refreshed state; plan proposes create.
  3. Pause pipelines; assess data loss and restore options.
  4. Recover or restore data; then plan again.
  5. Investigate audit logs; add locks and permission changes.

Example

resource "azurerm_storage_account" "data" {
  name                     = "acmeproddata"
  resource_group_name      = azurerm_resource_group.data.name
  location                 = "westeurope"
  account_tier             = "Standard"
  account_replication_type = "GZRS"
  lifecycle { prevent_destroy = true }
}

resource "azurerm_management_lock" "data" {
  name       = "no-delete"
  scope      = azurerm_storage_account.data.id
  lock_level = "CanNotDelete"
  notes      = "Production data. Remove via change request only."
}

Common mistakes

  • Applying immediately and overwriting any chance of recovering the original.
  • Assuming prevent_destroy protects against manual deletion.
  • No backups outside the account that holds the data.
  • Blaming the person instead of fixing the access model.

How to answer in the interview

"On the next plan Terraform refreshes, the provider reports the bucket no longer exists, so Terraform drops it from state and proposes creating it again. Applying would create an empty bucket with the right settings, but the data is gone, and dependent resources may also change. So before applying I check whether the data matters and restore it from replication or backups, or recover the storage account if Azure still allows it. I find out who deleted it and why from CloudTrail or the Activity Log. To prevent it, I use resource locks or deny policies on critical resources, prevent_destroy in Terraform and least-privilege access, so nobody deletes production resources by hand."

Likely follow-up questions

  • Why is prevent_destroy not enough? It only blocks Terraform-planned destroys; it has no effect on console or CLI deletion.
  • Can Terraform tell you who deleted it? No, use cloud audit logs.
  • How do you detect this earlier? Scheduled drift detection and alerts on delete events.
