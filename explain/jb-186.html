Explain @Entity, @Table, @Id, and @GeneratedValue.

Spring Data & JPA · concept · levels mid, senior

In one line

@Entity marks a class as a persistent JPA entity, @Table customises the table it maps to, @Id marks the primary key, and @GeneratedValue chooses how keys are generated (IDENTITY, SEQUENCE, TABLE, AUTO, plus UUID since JPA 3.1); SEQUENCE is usually best because it keeps JDBC batching possible.

Detailed explanation

An entity is a class whose instances are managed by the persistence context: Hibernate tracks their state, detects changes (dirty checking) and writes them at flush. An entity needs an identifier and a no-argument constructor (public or protected) so the provider can instantiate it through reflection, and it should not be final if you want lazy proxies.

@Table is optional. Without it the table name is derived from the entity name by the naming strategy (Spring Boot turns OrderItem into order_item). Use it to set name, schema, uniqueConstraints and indexes; the last two only matter for schema generation, so in production they document intent while Flyway or Liquibase creates the real schema.

@Id marks the primary key field (field access) or getter (property access); its placement decides the access type for the whole entity. @GeneratedValue tells the provider who produces the value:

  • IDENTITY uses an auto-increment or identity column. The database creates the id during the INSERT, so Hibernate must execute the INSERT immediately on persist() to learn the id. That is why JDBC insert batching is disabled for such entities.
  • SEQUENCE asks a database sequence for values before inserting. With allocationSize (default 50) and a pooled optimiser, Hibernate fetches one sequence value per 50 ids, assigns ids in memory and can then batch the INSERTs. Preferred on PostgreSQL, Oracle and SQL Server.
  • TABLE emulates a sequence with a row in a separate table and row locks: portable but slow and contended.
  • AUTO lets the provider choose; Hibernate 6 picks SEQUENCE where supported, which surprises people migrating from Hibernate 5 on MySQL.

How it works

  1. At startup Hibernate scans @Entity classes and builds metadata from the annotations.
  2. @Table and the naming strategy decide the table and column names.
  3. On persist(), the id generator runs: SEQUENCE takes the next value from its in-memory pool, IDENTITY forces an immediate INSERT.
  4. The entity is stored in the persistence context keyed by its id.
  5. At flush, pending INSERTs are grouped into JDBC batches if ids are already known and hibernate.jdbc.batch_size is set.

Example

@Entity
@Table(name = "orders", schema = "sales",
       indexes = @Index(name = "idx_orders_customer", columnList = "customer_id"))
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "order_seq")
    @SequenceGenerator(name = "order_seq", sequenceName = "order_seq", allocationSize = 50)
    private Long id;

    @Column(name = "customer_id", nullable = false)
    private Long customerId;

    protected Order() { }          // required by JPA
}
CREATE SEQUENCE sales.order_seq INCREMENT BY 50;

Common mistakes

  • Using IDENTITY for bulk-loading entities and wondering why batch_size has no effect.
  • Setting allocationSize = 50 in Java while the database sequence increments by 1, which produces duplicate or overlapping ids.
  • Relying on @Table(indexes = ...) in production instead of migrations.
  • Making entities final or omitting the no-arg constructor, breaking proxies.

How to answer in the interview

"@Entity tells JPA that a class is persistent and managed by the persistence context; it needs an id and a no-arg constructor. @Table is optional and overrides the table name, schema, unique constraints and indexes. @Id marks the primary key, and @GeneratedValue picks the strategy. IDENTITY relies on an auto-increment column, so Hibernate has to insert immediately to get the id, which disables batch inserts. SEQUENCE fetches ids from a sequence, and with an allocation size of 50 Hibernate hands out ids in memory and batches inserts, so that is my default on PostgreSQL. TABLE is slow, and AUTO leaves the choice to the provider, which I avoid so behaviour is explicit."

Likely follow-up questions

  • Why does IDENTITY prevent batching? The id only exists after the INSERT runs, so Hibernate must execute each INSERT straight away to put the entity in the persistence context.
  • When would you use UUID keys? When ids are generated by clients or across services; prefer time-ordered UUIDs (v7) to keep B-tree indexes compact.
  • What does allocationSize do? It is how many ids Hibernate reserves per sequence call; it must match the sequence increment.
