What is the difference between shutdown() and shutdownNow() on an ExecutorService, and how do you shut down gracefully?

Concurrency · concept · levels mid, senior

In one line

shutdown() stops accepting new tasks but lets running and queued tasks finish; shutdownNow() also interrupts running tasks and returns the queued tasks that never started. A graceful shutdown combines shutdown(), awaitTermination() with a timeout, and shutdownNow() as a fallback.

Detailed explanation

An ExecutorService owns worker threads, and unless they are daemon threads they keep the JVM alive. So every executor you create needs an explicit end of life. There are two levels of stopping.

shutdown() is the polite request: the executor rejects new submissions (they hit the RejectedExecutionHandler), but every task already in the queue still runs. The call returns immediately; it does not wait. shutdownNow() is the forceful request: it drains the queue, returns those tasks as a List<Runnable> so you can log or persist them, and calls interrupt() on running workers. Interruption is cooperative: a task stuck in a loop that never checks Thread.interrupted() or never calls a blocking method that throws InterruptedException will keep running.

awaitTermination(timeout, unit) is what actually waits. It returns true if all tasks finished in time. The standard pattern is: shutdown, wait, force, wait again briefly. Since Java 19, ExecutorService is AutoCloseable, and close() does a shutdown plus wait for you, which suits try-with-resources for short-lived executors.

In frameworks, let the container manage it. Spring's ThreadPoolTaskExecutor supports setWaitForTasksToCompleteOnShutdown(true) and setAwaitTerminationSeconds(...); for your own executors call the pattern from a @PreDestroy method or a shutdown hook. In Kubernetes the pod first gets SIGTERM, the JVM runs shutdown hooks, and after terminationGracePeriodSeconds (30 s by default) it gets SIGKILL, so your timeouts must fit inside that grace period.

How it works

  1. Stop taking new work: call shutdown() (and stop consumers or schedulers feeding the pool).
  2. Wait for in-flight and queued tasks with awaitTermination(...).
  3. If the timeout expires, call shutdownNow() and record the returned unstarted tasks.
  4. Wait a few more seconds for interrupted tasks to react.
  5. If it still has not terminated, log it; the process will be killed anyway.
  6. If the current thread is interrupted while waiting, call shutdownNow() and restore the interrupt flag.

Example

void shutdownGracefully(ExecutorService pool) {
    pool.shutdown();                                   // no new tasks
    try {
        if (!pool.awaitTermination(20, TimeUnit.SECONDS)) {
            List<Runnable> dropped = pool.shutdownNow(); // interrupt + drain
            log.warn("Forced shutdown, {} tasks never started", dropped.size());
            if (!pool.awaitTermination(5, TimeUnit.SECONDS)) {
                log.error("Executor did not terminate");
            }
        }
    } catch (InterruptedException e) {
        pool.shutdownNow();
        Thread.currentThread().interrupt();
    }
}

@PreDestroy
void stop() { shutdownGracefully(reportPool); }

Common mistakes

  • Assuming shutdown() waits; it returns immediately, you need awaitTermination.
  • Never shutting executors down, so non-daemon threads keep the JVM from exiting.
  • Writing tasks that ignore interruption, so shutdownNow() cannot stop them.
  • Swallowing InterruptedException instead of restoring the interrupt flag.
  • Using timeouts longer than the Kubernetes grace period.

How to answer in the interview

"shutdown stops accepting new tasks but lets the queued and running ones finish, and it returns immediately. shutdownNow also interrupts running tasks and hands back the tasks that never started. For a graceful stop I call shutdown, then awaitTermination with a timeout; if that fails I call shutdownNow and wait a few more seconds, and if I get interrupted I restore the flag. In Spring I let the framework manage the pool with wait-for-tasks settings, or call this from PreDestroy, and I make sure the timeouts fit inside the Kubernetes grace period after SIGTERM."

Likely follow-up questions

  • What happens to queued tasks if the JVM exits without shutting down the executor? They are simply lost; nothing persists them, and non-daemon workers may even block a normal exit.
  • How do you make a task respond to shutdownNow? Check Thread.currentThread().isInterrupted() in loops and let InterruptedException end the task.
  • What does close() on an ExecutorService do? Since Java 19 it calls shutdown and waits for termination, interrupting only if the waiting thread is interrupted.
