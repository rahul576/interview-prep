How do you protect secrets and sensitive data stored in Terraform state?

Infrastructure as Code · concept · levels senior

In one line

Assume state contains secrets: use an encrypted backend (KMS at rest, TLS in transit) with versioning, strict per-environment access and access logging, and keep secrets out of state with service-managed credentials, a vault, ephemeral resources and write-only arguments; OpenTofu also offers client-side state encryption.

Detailed explanation

Terraform state stores every attribute of every resource in plain JSON, including generated passwords (random_password.result), database master passwords, private keys from tls_private_key, access keys and connection strings. Marking variables or outputs sensitive only hides them in CLI output; they are still in state. Anyone who can read the state file can read the secrets.

Protect the state.

  • Backend encrypted at rest with a customer-managed KMS key (S3 SSE-KMS, Azure Storage encryption, GCS CMEK), TLS in transit, public access blocked.
  • Versioning for recovery; remember old versions contain old secrets too.
  • Separate buckets or containers per environment; access only for that environment's pipeline role and a small break-glass group. Developers should not need production state.
  • Access logging (CloudTrail data events, storage logs) and alerts on unusual reads.
  • In HCP Terraform, state is encrypted and access is controlled per workspace; restrict who can read state.

Keep secrets out of it.

  • Let services manage credentials: for RDS, manage_master_user_password = true stores the master password in Secrets Manager instead of state.
  • Generate secrets in a vault or secrets manager and have applications read them at runtime; Terraform only references the secret's name or ARN.
  • Newer Terraform (1.10+) has ephemeral resources and values that are never persisted, and (1.11+) write-only arguments, such as a database password passed via a _wo argument with a version number to trigger updates.
  • OpenTofu supports client-side state and plan encryption, so the backend only ever sees ciphertext.

How it works

  1. Classify state as confidential data.
  2. Configure encrypted, versioned, per-environment backend with tight IAM.
  3. Replace random_password patterns with service-managed or vault-generated secrets.
  4. Use ephemeral/write-only features where providers support them.
  5. Audit access and rotate any secret that has lived in state.

Example

resource "aws_db_instance" "app" {
  identifier                  = "app-prod"
  engine                      = "postgres"
  username                    = "app_admin"
  manage_master_user_password = true   # password lives in Secrets Manager, not state
}

terraform {
  backend "s3" {
    bucket       = "acme-tfstate-prod"
    key          = "app/terraform.tfstate"
    region       = "eu-west-1"
    encrypt      = true
    kms_key_id   = "alias/tfstate-prod"
    use_lockfile = true
  }
}

Common mistakes

  • Thinking sensitive = true keeps values out of state.
  • One state bucket readable by every engineer.
  • Committing terraform.tfstate or plan files to Git, or publishing them as CI artifacts.
  • Never rotating secrets that were exposed in state.

How to answer in the interview

"I assume every state file contains secrets, because providers store generated passwords, keys and connection strings in plain JSON, and sensitive only hides them in output. So the backend is encrypted with KMS, versioned, separated per environment, readable only by that environment's pipeline role and a small break-glass group, with access logging. Beyond that I keep secrets out of state: services manage their own credentials, like RDS storing the master password in Secrets Manager, secrets are generated in a vault rather than with random_password, and newer Terraform has ephemeral resources and write-only arguments. OpenTofu can also encrypt state client-side."

Likely follow-up questions

  • Why is random_password a secret-in-state problem? Its result is stored in plain text in state.
  • Are plan files sensitive too? Yes; saved plans contain the same values and must be protected.
  • What if state leaked? Rotate every secret in it and review access logs.
