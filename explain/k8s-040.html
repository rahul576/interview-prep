How is monitoring typically set up for a Kubernetes cluster, and what is the difference between metrics-server and kube-state-metrics?

Kubernetes · concept · levels entry, mid, senior

In one line

metrics-server gives live CPU and memory usage for kubectl top and the HPA with no history, while kube-state-metrics turns object state (replicas, pod phase, restarts) into metrics; real monitoring uses Prometheus (often kube-prometheus-stack) with node-exporter, cAdvisor, Grafana and SLO-based alerts.

Detailed explanation

These two components are often confused because both have "metrics" in their name. metrics-server scrapes the kubelet's resource metrics endpoint on every node, keeps only the latest sample in memory and serves it through the aggregated metrics.k8s.io API. It exists to power kubectl top and resource-based autoscaling (HPA, VPA). It is not a monitoring system: no history, no Prometheus format, no alerting.

kube-state-metrics (KSM) watches the API server and exposes the state of objects in Prometheus format: kube_deployment_status_replicas_available, kube_pod_status_phase, kube_pod_container_status_restarts_total, job failures, PVC phases, node conditions. It does not measure resource usage; it answers "is the cluster in the state I asked for?"

A typical stack is the Prometheus Operator, usually installed via kube-prometheus-stack. It manages Prometheus and Alertmanager and discovers targets with ServiceMonitor and PodMonitor objects. node-exporter provides host metrics (CPU, disk, network, filesystem), the kubelet's cAdvisor endpoint provides per-container usage and throttling, and control plane components expose their own metrics. Grafana provides dashboards, and Thanos, Mimir or a managed Prometheus service provide long-term, multi-cluster storage. Many teams now add OpenTelemetry collectors for traces and logs.

Alerting should focus on symptoms users feel, such as SLO burn rate on error rate and latency, plus a small set of cluster-health signals: nodes NotReady, pods crash looping for a sustained time, PVCs filling up, API server errors, certificate expiry.

How it works

  1. Install metrics-server for kubectl top and HPA.
  2. Install kube-prometheus-stack: Prometheus, Alertmanager, Grafana, KSM, node-exporter.
  3. Applications expose /metrics; teams add ServiceMonitors to have them scraped.
  4. Prometheus scrapes kubelet/cAdvisor, KSM, node-exporter and apps.
  5. Remote-write to long-term storage; Grafana dashboards per service.
  6. Alertmanager routes SLO and cluster alerts to on-call.

Example

apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: checkout
  labels: { release: kube-prometheus-stack }
spec:
  selector:
    matchLabels: { app: checkout }
  endpoints:
    - port: http-metrics
      interval: 30s

Common mistakes

  • Using metrics-server as a monitoring backend.
  • Alerting on every pod restart instead of sustained crash loops or SLO impact.
  • Unbounded label cardinality (user IDs in labels) overwhelming Prometheus.
  • No long-term storage or no monitoring of the monitoring stack itself.

How to answer in the interview

"metrics-server gives the current CPU and memory of pods and nodes through the metrics API; it has no history and exists for kubectl top and the HPA. kube-state-metrics reads the API server and exposes object state, like desired versus available replicas, pod phase and restarts. For real monitoring I'd run kube-prometheus-stack with ServiceMonitors, node-exporter and cAdvisor, Grafana for dashboards and Thanos or a managed backend for retention. I alert on SLO burn rates plus key cluster signals like NotReady nodes and sustained crash loops."

Likely follow-up questions

  • Why not alert on every pod restart? Restarts are normal self-healing; alert on sustained crash loops or user impact to avoid alert fatigue.
  • What is a burn-rate alert? It fires when the error budget is being consumed faster than the SLO allows, over short and long windows.
  • How do you monitor many clusters? Remote-write to central Thanos/Mimir or a managed service, with a cluster label.
