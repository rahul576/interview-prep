MCP has three server primitives. Who controls each one, and why does that matter?

MCP Servers · concept · levels entry, mid, senior

In one line

Tools are model-controlled (the model decides to call them), resources are application-controlled context (the host or user chooses what to load), and prompts are user-controlled templates (the user explicitly picks them); who triggers each primitive determines its risk and approval needs.

Detailed explanation

MCP servers offer three primitives, and the important difference is the direction of control.

Tools are actions the server describes, such as create_ticket, query_metrics or send_email. The model decides during a conversation whether to call them and with which arguments. Because the model can act on its own initiative, and can be manipulated by prompt injection in documents or web pages it reads, tools carry the highest risk. Tools with side effects need clear annotations, host approval policies, least-privilege credentials and server-side validation.

Resources are read-only data identified by URIs, such as file:///repo/README.md, a database schema or a dashboard snapshot. The application or user decides which resources enter the context, for example the user attaches a file or the host selects relevant ones. Their risk is mainly content risk: a resource might contain injected instructions or sensitive data that should not be exposed.

Prompts are parameterised message templates that the user explicitly invokes, often shown as slash commands like /review-pr or /incident-summary. Nothing runs automatically, so the risk is lowest, though arguments still flow into the model context.

When designing a server, choose the primitive by asking who should trigger it. If the agent must fetch something on demand with parameters, or perform an action, it is a tool. If a person or the application would attach it as background, it is a resource. If it is a reusable workflow the user starts, it is a prompt.

How it works

  1. The server advertises tools, resources and/or prompts capabilities.
  2. Tools: host sends definitions to the model; the model emits calls; host approves; client calls tools/call.
  3. Resources: host lists them (resources/list), user or app selects; client calls resources/read.
  4. Prompts: host shows them in a menu; user picks one; client calls prompts/get with arguments.

Example

Server: incident-helper
  tool      get_recent_alerts(service, minutes)   -> model decides when to call
  tool      acknowledge_alert(alert_id)           -> side effect, requires approval
  resource  runbook://payments/checkout-latency    -> user attaches the runbook
  prompt    /postmortem(incident_id)               -> user starts the workflow

Common mistakes

  • Exposing a side-effecting action as a resource or prompt.
  • Making everything a tool, flooding the model's context.
  • Assuming resources are safe because they are read-only.
  • Auto-approving tools without considering prompt injection.

How to answer in the interview

"Tools are model-controlled: the model decides when to call them and with what arguments. Resources are application-controlled: read-only data with URIs that the host or user selects as context. Prompts are user-controlled templates, usually slash commands the user picks. This matters for security and design. Since the model can call tools by itself, and can be tricked by injected text, tools carry the most risk and need approvals for side effects and least privilege. Resources mainly carry content risk. So I choose the primitive based on who should trigger it."

Likely follow-up questions

  • Data that should be a resource, not a tool? A project's database schema: stable, attachable, cacheable, and the user decides to include it.
  • Why does host support matter? Some hosts expose tools to the model far better than resources or prompts.
  • Can a tool return a resource? Yes, as an embedded resource or a resource link in its result.
