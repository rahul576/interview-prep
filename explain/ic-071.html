How do you design Terraform pipelines for many AWS or Azure accounts with least privilege?

Infrastructure as Code · design · levels senior

In one line

Give each account/subscription its own deployment roles, let CI assume them through OIDC federation scoped to repository, branch or environment, separate a read-only plan role from a write apply role, keep state per account with matching backend permissions, and add approval gates and audit trails for production.

Detailed explanation

A single all-powerful CI credential that can change every account is the biggest risk in infrastructure automation: one leaked secret or malicious pull request compromises everything. The design aims for no long-lived keys and least privilege per account and stage.

Identity. The landing zone creates, in every target account (or Azure subscription), roles such as tf-plan and tf-apply. Their trust policy accepts only the CI provider's OIDC tokens, with conditions on claims: for GitHub Actions the sub claim like repo:acme/infra-live:environment:prod; for Azure, federated credentials on a managed identity or app registration.

Plan versus apply. Pull-request plans run code nobody has reviewed yet. They use the plan role: read access to resources and state, plus only what locking needs. Even read access can expose data, and providers or external data sources in a PR can run arbitrary code, so the plan role should not read secret values, and secret-heavy stacks may skip automatic PR plans from forks. Apply runs only after merge, from the protected branch or a protected environment, using the apply role with write permissions scoped to what that stack manages.

State isolation. Each account has its own state bucket or container, and only that account's roles can access it. A dev pipeline cannot read production state, which often contains secrets.

Gates and audit. Production environments require reviewer approval of the exact saved plan. CloudTrail or the Azure activity log records actions by role session name, and CI keeps the plan, approver and logs, giving end-to-end traceability.

How it works

  1. PR opened → CI requests an OIDC token → assumes tf-plan in the target account.
  2. Plan output posted for review; plan file stored as an artifact.
  3. Merge to main → job in prod environment waits for approval.
  4. Approved → assumes tf-apply (trust only for environment:prod).
  5. Applies the saved plan; logs link CI run to cloud audit events.

Example

{
  "Effect": "Allow",
  "Principal": { "Federated": "arn:aws:iam::111122223333:oidc-provider/token.actions.githubusercontent.com" },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": {
      "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
      "token.actions.githubusercontent.com:sub": "repo:acme/infra-live:environment:prod"
    }
  }
}

Common mistakes

  • One admin role trusted by every repository and branch.
  • Wildcard sub conditions such as repo:acme/*.
  • PR plans running with apply permissions.
  • A shared state bucket readable by all environments.

How to answer in the interview

"Each account has its own deployment roles created by the landing zone, and their trust policies only accept OIDC tokens from our CI, scoped to the specific repository and, for production, to the protected environment or main branch, so there are no static keys. Pull request plans use a read-only role, because that code isn't reviewed yet; applies after merge use a separate role with write access. State is per account and backend permissions match, so dev can't even read prod state. Production applies need an approval of the saved plan, and CloudTrail plus CI history give a full audit trail."

Likely follow-up questions

  • Why shouldn't PR plans have write permissions? Unreviewed code, including providers and external data sources, runs during plan.
  • Does the plan role need any write? Only for state locking, scoped to the lock object or table.
  • How do you handle cross-account resources? Provider aliases assuming roles in each account, each scoped narrowly.
