Compare Ansible with Chef and Puppet.

Configuration Management · concept · levels entry

In one line

Ansible is agentless and push-based over SSH with YAML playbooks; Puppet (declarative DSL) and Chef (Ruby) use agents that pull configuration from a server periodically, giving continuous enforcement for large fleets at the cost of more infrastructure and a steeper learning curve.

Detailed explanation

Ansible runs from a control node (a laptop, CI job, AWX or Ansible Automation Platform) and connects to targets over SSH (or WinRM for Windows). Nothing needs to be installed on targets except Python, playbooks are YAML executed in order, and it works as well for orchestration, such as rolling deployments, as for configuration. That makes it quick to adopt. Its model is push: changes happen when someone or something runs a playbook.

Puppet installs an agent on every node that, by default every 30 minutes, sends facts to a Puppet server, receives a compiled catalogue and enforces it. Configuration is written in Puppet's declarative DSL, organised into modules and classes, with Hiera for data. Puppet models resources and dependencies explicitly and is strong at continuous compliance across tens of thousands of servers.

Chef also uses an agent, chef-client (Chef Infra Client), which periodically pulls cookbooks and recipes from a Chef Infra Server and converges the node. Recipes are written in a Ruby DSL, which is powerful for developers but harder for operations teams without Ruby experience.

The pull models give continuous drift correction without anyone running anything, but require running and securing servers, certificates and agents. Market context in 2026: with immutable images, containers and Kubernetes, much configuration moved into image builds and manifests, so classic configuration management is used less overall. Ansible is the most common choice for the remaining work and for network automation; Puppet and Chef remain in large established estates. The open-source Puppet ecosystem has also seen a community fork, OpenVox, after Perforce changed how it distributes Puppet builds. SaltStack is another agent-based option with an event-driven model.

How it works

  1. Ansible: control node → SSH → run modules → done (push, on demand).
  2. Puppet: agent → server with facts → compiled catalogue → enforce → report (pull, every 30 min).
  3. Chef: chef-client → server → download cookbooks → converge → report.
  4. Continuous enforcement in Ansible requires scheduling (AWX/AAP, cron, ansible-pull).

Example

# Ansible
- hosts: web
  become: true
  tasks:
    - ansible.builtin.package: { name: nginx, state: present }
    - ansible.builtin.service: { name: nginx, state: started, enabled: true }
# Puppet
package { 'nginx': ensure => installed }
service { 'nginx': ensure => running, enable => true, require => Package['nginx'] }
# Chef
package 'nginx'
service 'nginx' do
  action [:enable, :start]
end

Common mistakes

  • Saying Ansible cannot enforce continuously; it can when scheduled.
  • Ignoring the operational cost of Puppet/Chef servers and certificates.
  • Treating these tools as replacements for immutable images.

How to answer in the interview

"Ansible is agentless and push-based: a control node connects over SSH and applies YAML playbooks, so nothing to install on targets and it's quick to learn. Puppet and Chef install agents on every server that periodically pull their configuration from a central server and enforce it, typically every 30 minutes, which continuously corrects drift across large fleets. Puppet uses a declarative DSL, Chef uses Ruby, both with a steeper learning curve and more infrastructure. Today, with immutable images and containers, config management is used less, and Ansible is the most common choice for what remains."

Likely follow-up questions

  • How can you get continuous enforcement with Ansible? Schedule playbooks in AWX/Automation Platform or CI, or use ansible-pull via cron on each host.
  • Which is better for 20,000 servers? Either works; pull agents scale naturally, Ansible needs forks, batching and execution nodes.
  • What does declarative mean here? You describe desired state, the tool decides the actions.
