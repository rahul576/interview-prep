What are IAM users, groups, roles and policies?

Cloud (AWS) · concept · levels entry

In one line

IAM users are identities with long-term credentials, groups bundle users to share permissions, roles are identities assumed to get temporary credentials, and policies are JSON documents that grant or deny actions on resources; best practice is SSO plus roles with few or no long-lived keys.

Detailed explanation

IAM (Identity and Access Management) answers two questions for every AWS API call: who is calling (authentication) and are they allowed to do this action on this resource (authorisation). By default everything is denied.

An IAM user has permanent credentials: a console password and optionally access keys for the CLI and SDKs. Because these never expire, they are the main risk when leaked from a laptop, repository or CI system.

An IAM group is a collection of users such as Developers; policies attached to the group apply to every member. Groups cannot be nested and are not identities, so you cannot sign in as one.

An IAM role has permissions but no permanent credentials. A trusted principal assumes it through STS and gets temporary credentials, typically valid for an hour. Roles are used by EC2 instances (via an instance profile), Lambda, ECS tasks, other accounts, SSO users and CI pipelines via OIDC. A trust policy says who may assume the role.

Policies are JSON documents of Effect, Action, Resource and optional Condition, either AWS managed, customer managed or inline. Resource-based policies such as bucket policies attach to resources instead.

Best practice: people use IAM Identity Center (SSO), workloads use roles, and IAM users with keys are rare exceptions.

How it works

  1. A principal authenticates (password, keys, SSO or assumed role).
  2. Each API request is signed with its credentials.
  3. IAM collects all applicable policies: identity, resource, permission boundaries, SCPs.
  4. An explicit Deny wins; otherwise an Allow is required.
  5. Temporary role credentials expire and are refreshed automatically.

Example

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "ec2.amazonaws.com" },
    "Action": "sts:AssumeRole"
  }]
}

This trust policy lets EC2 assume an orders-app role; a permission policy on the role then allows s3:GetObject on arn:aws:s3:::orders-config/*. The application on the instance uses the SDK, which picks up temporary credentials automatically; no keys live on the server.

Common mistakes

  • Creating IAM users with access keys for applications on EC2.
  • Attaching policies to individual users instead of groups or roles.
  • Granting AdministratorAccess "temporarily" and never removing it.
  • Overly broad trust policies on roles.

How to answer in the interview

"A user is an identity with long-term credentials, a password or access keys. A group is a set of users so permissions are attached once. A role has no permanent credentials; it's assumed by an EC2 instance, a Lambda, another account or an SSO user, and hands out temporary credentials. Policies are JSON documents of allowed or denied actions on resources. I'd use IAM Identity Center for people and roles for workloads, with almost no long-lived keys."

Likely follow-up questions

  • Why are roles safer than stored keys? Credentials are temporary, rotate automatically and are never stored on disk.
  • What is a trust policy? The resource policy on a role saying who may assume it.
  • What is a permission boundary? A maximum set of permissions an identity can ever have, even if other policies allow more.
