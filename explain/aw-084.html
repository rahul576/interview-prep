How do you design hybrid DNS and connectivity between on-premises and many AWS accounts?

Cloud (AWS) · design · levels lead

In one line

Connect on-premises over redundant Direct Connect with site-to-site VPN backup into a Transit Gateway in a central network account, allocate addresses with VPC IPAM, and unify DNS with Route 53 Resolver inbound and outbound endpoints, forwarding rules shared through RAM, and private hosted zones associated across VPCs.

Detailed explanation

Connectivity: two or more Direct Connect connections at different DX locations (for high resilience), connected via a Direct Connect gateway to a Transit Gateway using a transit virtual interface. A site-to-site VPN over the internet to the same Transit Gateway serves as backup, with BGP preferring DX. The Transit Gateway lives in the network account and is shared with workload accounts through AWS Resource Access Manager. TGW route tables segment traffic: production VPCs, non-production VPCs, shared services and on-premises each get route tables controlling who can reach whom, and an inspection VPC with Network Firewall can sit in the path. For very large global networks, AWS Cloud WAN offers policy-based management.

IP planning: VPC IPAM manages pools per region and environment, allocates non-overlapping CIDRs to every new VPC and tracks usage, because overlaps with on-premises ranges make routing impossible without NAT.

DNS: inside VPCs, the Route 53 Resolver (the .2 address) answers queries. Inbound endpoints are ENIs in the shared VPC that on-premises DNS servers forward to, allowing them to resolve private hosted zones like aws.example.internal and VPC endpoint names. Outbound endpoints with forwarding rules send queries for corp.example.com to on-premises DNS servers. Rules are created in the network account and shared via RAM to all accounts, then associated with their VPCs, so every workload resolves on-premises names the same way. Private hosted zones are associated with VPCs in other accounts (via authorisation), or managed with Route 53 Profiles, which bundle zones, rules and DNS Firewall settings and share them across accounts. Centralising interface endpoints with shared private hosted zones also cuts cost.

How it works

  1. On-prem router peers BGP with AWS over DX and VPN.
  2. DX gateway and VPN terminate on the Transit Gateway.
  3. Workload VPCs attach to the TGW; route tables segment traffic.
  4. On-prem DNS forwards AWS zones to Resolver inbound endpoints.
  5. VPCs resolve corp zones via shared outbound forwarding rules.
  6. IPAM guarantees unique CIDRs for new VPCs.

Example

aws route53resolver create-resolver-rule --name corp-forward \
  --rule-type FORWARD --domain-name corp.example.com \
  --resolver-endpoint-id rslvr-out-123 \
  --target-ips Ip=10.0.0.53,Port=53 Ip=10.0.1.53,Port=53

aws ram create-resource-share --name dns-rules \
  --resource-arns arn:aws:route53resolver:eu-west-1:111122223333:resolver-rule/rslvr-rr-abc \
  --principals arn:aws:organizations::111122223333:organization/o-xyz

# In each workload account
aws route53resolver associate-resolver-rule \
  --resolver-rule-id rslvr-rr-abc --vpc-id vpc-workload

Common mistakes

  • A single Direct Connect link with no backup.
  • Overlapping CIDRs discovered only when attaching a VPC.
  • Each account building its own DNS forwarding, creating inconsistent resolution.
  • Forgetting to authorise and associate private hosted zones across accounts.

How to answer in the interview

"Connectivity runs over redundant Direct Connect links, with site-to-site VPN as backup, into a Transit Gateway in a central network account that attaches all workload VPCs and controls routing between them and on-premises. Address ranges come from VPC IPAM so nothing overlaps. For DNS, Resolver inbound endpoints let on-premises servers resolve AWS private zones, and outbound endpoints with forwarding rules send corp.example.com queries on-premises. Those rules are shared to every account through RAM, and private hosted zones are associated with the VPCs that need them, so every workload resolves both worlds consistently."

Likely follow-up questions

  • Why is DNS usually the hardest part? Split-horizon zones, many accounts, conditional forwarding loops and endpoint names all need consistent resolution in both directions.
  • When choose Cloud WAN over Transit Gateway? For multi-region global networks managed through central policy.
  • How make Direct Connect highly available? Multiple connections at separate locations, plus VPN failover.
