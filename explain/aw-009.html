What is a NAT gateway, and why is it needed?

Cloud (AWS) · concept · levels entry

In one line

A NAT gateway lets instances in private subnets make outbound internet connections while blocking inbound ones; it sits in a public subnet with an Elastic IP, should be deployed one per AZ for availability, and is billed per hour and per GB, so AWS service traffic should use VPC endpoints instead.

Detailed explanation

Private-subnet instances have only private IPs, yet they often need to download patches, pull public images or call third-party APIs. The NAT gateway replaces the private source IP with its own Elastic IP, tracks the connection and returns replies to the right instance. Because it only translates connections that started inside, nobody on the internet can open a connection to the private instances.

The classic NAT gateway lives in a public subnet and is zonal: if its AZ fails, subnets routed to it lose internet access. The resilient design is one NAT gateway per AZ, each private subnet using its local gateway, which also avoids cross-AZ data charges (AWS has since added a regional availability mode; check current docs). It scales automatically and needs no patching, unlike a self-managed NAT instance.

Cost is the classic surprise: you pay an hourly charge per gateway plus a per-GB data processing charge on everything that passes through it. Pulling large container images from ECR, sending logs to CloudWatch or moving data to S3 via NAT can cost more than the workload itself. Gateway endpoints for S3 and DynamoDB are free, and interface endpoints for ECR, CloudWatch, STS and others are usually cheaper than NAT processing.

How it works

  1. Allocate an Elastic IP and create the NAT gateway in a public subnet.
  2. Route private subnets' 0.0.0.0/0 to it.
  3. An instance opens a connection; the gateway rewrites source IP and port.
  4. Replies return to the gateway and are translated back.
  5. Unsolicited inbound traffic is dropped.

Example

aws ec2 allocate-address --domain vpc
aws ec2 create-nat-gateway --subnet-id subnet-public-a \
  --allocation-id eipalloc-0abc --tag-specifications \
  'ResourceType=natgateway,Tags=[{Key=Name,Value=nat-a}]'
aws ec2 create-route --route-table-id rtb-private-a \
  --destination-cidr-block 0.0.0.0/0 --nat-gateway-id nat-0123

An EKS cluster pulled several TB of images per month from ECR through NAT; adding ECR interface endpoints and an S3 gateway endpoint cut the NAT bill by most of its value.

Common mistakes

  • One NAT gateway for all AZs (single point of failure, cross-AZ charges).
  • Sending S3, ECR and CloudWatch traffic through NAT.
  • Expecting NAT to allow inbound connections.
  • Forgetting idle NAT gateways in test VPCs still bill hourly.

How to answer in the interview

"A NAT gateway lets instances in private subnets make outbound connections, for updates or external APIs, while nobody on the internet can start connections to them. It sits in a public subnet with an Elastic IP, and the private route tables send 0.0.0.0/0 to it. It's zonal, so for high availability I create one per AZ and route each private subnet to its local gateway. It's billed per hour and per GB processed, which can get expensive, so traffic to AWS services like S3, ECR or CloudWatch should go through VPC endpoints instead."

Likely follow-up questions

  • How can NAT charges grow unexpectedly? Image pulls, log shipping or S3 transfers through NAT are charged per GB.
  • NAT gateway vs NAT instance? The gateway is managed and scales; an instance is cheaper but you patch and scale it yourself.
  • How do partners allow-list your outbound IP? Give them the NAT gateway's Elastic IPs.
