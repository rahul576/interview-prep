How does the API Priority and Fairness feature protect the Kubernetes API server?

Kubernetes · concept · levels mid, senior, lead

In one line

API Priority and Fairness (APF) divides the API server's concurrency budget into priority levels (via PriorityLevelConfigurations), classifies each request with FlowSchemas, and uses fair queuing between flows so one noisy client cannot starve others; overflow gets HTTP 429.

Detailed explanation

The API server is shared by everything: kubelets, controllers, operators, CI pipelines and humans. Before APF, the only protection was a global limit on in-flight requests (--max-requests-inflight, --max-mutating-requests-inflight). A single buggy controller doing expensive LIST calls could consume all slots, and then kubelet heartbeats or leader-election renewals were rejected, causing cascading failures. APF, stable since Kubernetes 1.29 (flowcontrol.apiserver.k8s.io/v1), replaced that behaviour; those flags now just set the total concurrency that APF shares out.

Each request is matched against FlowSchemas in order of matchingPrecedence. A FlowSchema matches on subject (user, group, ServiceAccount) and resource or verb, and assigns the request to a PriorityLevelConfiguration. It also defines the flow distinguisher, usually by user or by namespace, which identifies "who" a request belongs to.

Each priority level gets a share of total concurrency (nominalConcurrencyShares) and can borrow or lend unused seats. Built-in levels include exempt (system masters, health checks), system, leader-election, node-high, workload-high, workload-low and global-default, plus catch-all. Inside a level, requests from different flows go into queues using shuffle sharding and are served fairly, so one heavy flow mainly delays itself. Expensive requests like large LISTs cost more seats. When queues are full or wait too long, clients receive 429 Too Many Requests with Retry-After; client-go backs off automatically.

How it works

  1. Request arrives; APF matches the highest-precedence FlowSchema.
  2. FlowSchema picks the priority level and flow distinguisher.
  3. If the level has free seats, the request executes.
  4. Otherwise it is queued in a shuffle-sharded queue for its flow.
  5. Queues are served fairly; overflow returns 429.
  6. Metrics and debug endpoints show who is waiting or rejected.

Example

kubectl get flowschemas,prioritylevelconfigurations
kubectl get --raw /debug/api_priority_and_fairness/dump_priority_levels
# PromQL: who is being throttled?
# sum by (flow_schema, priority_level) (rate(apiserver_flowcontrol_rejected_requests_total[5m]))
apiVersion: flowcontrol.apiserver.k8s.io/v1
kind: FlowSchema
metadata: { name: noisy-operator }
spec:
  priorityLevelConfiguration: { name: workload-low }
  matchingPrecedence: 1000
  distinguisherMethod: { type: ByUser }
  rules:
    - subjects:
        - kind: ServiceAccount
          serviceAccount: { name: report-operator, namespace: tools }
      resourceRules:
        - { verbs: ["*"], apiGroups: ["*"], resources: ["*"], namespaces: ["*"] }

Common mistakes

  • Raising global in-flight limits instead of finding the noisy client.
  • Putting custom workloads into exempt.
  • Ignoring 429s in custom scripts that retry without backoff.
  • Writing controllers that LIST instead of using informers and watches.

How to answer in the interview

"APF replaced the old max-in-flight limits with a shared concurrency budget. Each request is classified by FlowSchemas, matching user, group, service account or verb, into a priority level. PriorityLevelConfigurations split concurrency between levels like system, leader election and workloads, so critical traffic always has seats. Inside a level, requests are grouped into flows, usually per client, and fair queuing means one misbehaving controller mainly delays itself. When a level is saturated clients get 429s. I use the rejected and wait-time metrics to find the operator or script hammering the API."

Likely follow-up questions

  • An operator lists all pods every few seconds? It loads the API server and etcd; switch to informers with watches, label selectors and resync, and isolate it in a low priority level.
  • What is shuffle sharding? Each flow is hashed to a few queues, so a heavy flow rarely shares all queues with a light one.
  • Why are LISTs expensive? They may read many objects from etcd or the watch cache and serialise large responses, so APF charges them more seats.
