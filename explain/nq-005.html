What is the difference between a record and a regular Java class?

Modern Java (11-21) · concept · levels entry, mid

In one line

A regular class gives full freedom (mutable fields, setters, inheritance), while a record is a final, restricted class whose state is exactly its components: private final fields, no extra instance fields, no superclass besides java.lang.Record, with all boilerplate generated.

Detailed explanation

The two serve different purposes. A record declares "I am a transparent carrier of these values". Because the compiler knows that, it can generate the constructor, accessors, equals, hashCode and toString, and two records with equal components are equal. A regular class makes no such promise, so you write or generate those members yourself and decide what equality means.

Concrete restrictions on records:

  • Fields are final, so no setters and no reassignment after construction.
  • No extra instance fields beyond the components; static fields are allowed.
  • Cannot extend another class (it already extends Record) and is implicitly final, so nothing can extend it.
  • Instance initialiser blocks are not allowed; use the compact constructor.

What records can still do: implement interfaces, declare static and instance methods, nested types, additional constructors delegating to the canonical one, and annotations on components.

Choose a regular class when the object has identity and changing state: JPA entities, services, builders, aggregates whose lifecycle mutates them, or anything needing inheritance. JPA entities in particular need a no-argument constructor, non-final fields for lazy-loading proxies, and identity-based equality, so records do not fit (though they are excellent for JPA projections and DTOs). Choose a record for values: DTOs, events, configuration properties, keys and results.

How it works

  1. Record: compiler derives members from the header.
  2. Equality is component-based automatically.
  3. Regular class: you control fields, constructors and equality.
  4. Regular class can be extended or extend another class.

Example

public record OrderDto(Long id, String status, BigDecimal total) {}

@Entity
public class Order {                 // regular class for JPA
    @Id @GeneratedValue private Long id;
    private String status;
    protected Order() {}             // required by JPA
    public void ship() { this.status = "SHIPPED"; }
}

// JPA projection into a record
@Query("select new com.shop.OrderDto(o.id, o.status, o.total) from Order o")
List<OrderDto> summaries();

Common mistakes

  • Using records as JPA entities.
  • Thinking records cannot have methods at all.
  • Assuming records are deeply immutable.
  • Using a regular class with Lombok for simple DTOs where a record is clearer.

How to answer in the interview

"A regular class gives me full control: mutable fields, setters, any constructor, and inheritance. A record is a restricted, final class whose state is exactly its components; the fields are private and final, I can't add other instance fields, and it can't extend another class since it extends java.lang.Record. In return the compiler generates the constructor, accessors, equals, hashCode and toString with value semantics. Records can still implement interfaces and have methods. I use records for DTOs and events, and regular classes for things with identity and changing state, like JPA entities, which need a no-arg constructor and mutable fields."

Likely follow-up questions

  • Why are records a poor fit for JPA entities? JPA needs a no-arg constructor, mutable non-final fields and proxies, which records forbid.
  • Can a record implement an interface? Yes, commonly a sealed interface.
  • Can you override equals in a record? Yes, but it must remain consistent with component semantics.
