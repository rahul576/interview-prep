An assistant with long-term memory revealed one user preference to another user. What went wrong and how do you fix it?

AI Agents & AIOps · scenario · levels mid, senior

In one line

Treat it as a privacy incident; the cause is almost always memory not scoped per user or tenant, such as a shared vector index without filters, a cache keyed without user scope or shared agent state; fix by enforcing isolation in storage and retrieval code using the authenticated identity, adding cross-user leakage tests, and giving users controls to view and delete memories.

Detailed explanation

Incident response first: contain the issue, for example by disabling memory retrieval, determine which data leaked to whom from logs and traces, and follow the organisation's privacy incident and notification process, which may involve the data protection officer and regulators under GDPR or similar laws.

Typical technical causes:

  • Memories stored in a shared vector index retrieved by similarity alone, without filtering on user or tenant ID, so a similar memory from another user ranked highly.
  • A response or semantic cache keyed only on the question text, returning another user's personalised answer.
  • A shared agent instance or session object kept state between requests, for example a singleton with conversation history.
  • The user or tenant filter was taken from model output or a request parameter rather than the authenticated session.
  • Background memory extraction jobs mixing conversations from several users.

Fix: enforce isolation in code. Every memory record carries owner user ID and tenant ID. Every read path filters on the authenticated identity from the session token, applied by the data access layer, never by the model. Ideally storage is partitioned per tenant: separate namespaces, collections or indexes, or row-level security in the database. Caches include user and tenant scope in keys, and personalised responses are not cached globally. Agent instances are stateless per request, with state loaded by session ID.

Prevention: automated cross-user leakage tests that create memories for user A and try to retrieve them as user B through every path, run in CI; periodic audits sampling retrievals. User controls let people view, correct and delete what the assistant remembers, and sensitive categories (health, finances, credentials) are not stored at all or require explicit consent.

How it works

  1. Contain: disable memory or affected path; preserve logs.
  2. Assess scope of exposure; trigger privacy incident process.
  3. Find the faulty path: index, cache, shared state or filter source.
  4. Add mandatory identity filters in the data layer; partition storage.
  5. Scope cache keys; make agent instances stateless.
  6. Add leakage tests in CI; release user memory controls.

Example

class MemoryRepository:
    """All access goes through here; identity comes from the verified session only."""
    def __init__(self, vector_store):
        self.vs = vector_store

    def search(self, session, query, k=5):
        namespace = f"tenant:{session.tenant_id}"            # per-tenant partition
        return self.vs.query(
            namespace=namespace,
            vector=embed(query),
            top_k=k,
            filter={"user_id": {"$eq": session.user_id}},    # mandatory filter
        )

def test_no_cross_user_leak(repo, make_session):
    a, b = make_session("acme", "alice"), make_session("acme", "bob")
    repo.save(a, "Alice prefers aisle seats and is vegetarian")
    assert repo.search(b, "seat preference vegetarian") == []

Common mistakes

  • Treating it as a minor bug rather than a privacy incident.
  • Relying on the model to "only use this user's memories".
  • Filters built from request parameters that callers can change.
  • Global semantic caches for personalised answers.
  • No automated tests for isolation.

How to answer in the interview

"First, this is a privacy incident: contain it, assess what leaked to whom and follow the notification process. Technically, the cause is almost always that memory wasn't properly scoped: memories in a shared vector index retrieved by similarity without a user or tenant filter, a cache keyed only on the question, or a shared agent instance keeping state. The fix is to enforce isolation in code: every memory has an owner user and tenant, every read filters on the authenticated identity from the session, never from model output, and ideally storage is partitioned per tenant. Cache keys include user scope. I'd add automated tests that try to read one user's memories as another. And users get controls to view and delete memories, with sensitive categories not stored."

Likely follow-up questions

  • What should an assistant never store as memory? Credentials, payment data, and sensitive personal categories without explicit consent.
  • Namespace per tenant or metadata filter? Namespaces give stronger isolation; filters are fine if enforced centrally and tested.
  • How do you detect leaks in production? Audit sampling of retrievals for owner mismatches and alerts on any mismatch.
