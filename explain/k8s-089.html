A Service of type LoadBalancer stays in Pending without an external IP. How do you troubleshoot it?

Kubernetes · scenario · levels mid, senior

In one line

A LoadBalancer Service gets its external IP from the cloud controller manager (or a load balancer controller), so Pending means that controller is missing, failing or misconfigured; kubectl describe service events usually name the exact cause.

Detailed explanation

Kubernetes itself does not create load balancers. For type: LoadBalancer, a controller watches the Service and calls the cloud API: the in-tree or external cloud controller manager on AKS, GKE and EKS, or the AWS Load Balancer Controller when you use its annotations or loadBalancerClass. Until that call succeeds, EXTERNAL-IP shows <pending>.

The common failures are permissions: the cluster identity cannot create load balancers or public IPs, for example on AKS when the managed identity lacks Network Contributor on a custom subnet or on the resource group of a static IP. Quotas for public IPs or load balancers are exhausted. On AWS, subnets lack the discovery tags kubernetes.io/role/elb (public) or kubernetes.io/role/internal-elb (internal), so the controller cannot choose where to place the load balancer. Annotations may be invalid, such as an internal load balancer requested in a non-existent subnet, or a static IP that does not exist in that region.

On bare-metal, kind or on-premises clusters there is no cloud controller at all, so Pending is the expected state. You need an implementation such as MetalLB, kube-vip or Cilium's LB IPAM to hand out addresses.

How it works

  1. kubectl describe svc <name> and read the events (SyncLoadBalancerFailed, EnsuringLoadBalancer).
  2. Check which controller should handle it: spec.loadBalancerClass, annotations, add-ons installed.
  3. Read that controller's logs (cloud controller manager or aws-load-balancer-controller pods).
  4. Verify identity permissions, quotas, subnet tags and the existence of referenced IPs or subnets.
  5. Fix and let the controller reconcile; no need to recreate the Service.

Example

kubectl describe svc web
# Warning SyncLoadBalancerFailed ... AuthorizationFailed: does not have authorization
#   to perform action 'Microsoft.Network/virtualNetworks/subnets/join/action'
az role assignment create --assignee <cluster-identity-id> \
  --role "Network Contributor" --scope <subnet-resource-id>

Common mistakes

  • Waiting for an IP on a local or bare-metal cluster with no load balancer implementation.
  • Looking only at the Service YAML and never at the controller events or logs.
  • Mixing annotations for the legacy cloud provider and the AWS Load Balancer Controller.
  • Forgetting subnet tags when building VPCs with Terraform.

How to answer in the interview

"The external IP is created by the cloud controller manager or a load balancer controller, so Pending means that controller could not do its job. I start with kubectl describe service, because the events usually contain the cloud error, and then the controller logs. Typical causes are missing permissions for the cluster identity, for example Network Contributor on the subnet in AKS, quotas reached, AWS subnets without the elb tags, or annotations pointing to an internal subnet or static IP that does not exist. On bare metal there is no controller, so I install MetalLB or a similar implementation."

Likely follow-up questions

  • Why prefer one shared ingress or gateway over many LoadBalancer Services? Fewer cloud load balancers, lower cost, central TLS and routing, and fewer public IPs to secure.
  • How do you keep the same IP across recreations? Reserve a static IP and reference it through the provider annotation, since spec.loadBalancerIP is deprecated.
  • What is externalTrafficPolicy Local for? It preserves client source IPs and avoids an extra hop, at the cost of uneven balancing.
