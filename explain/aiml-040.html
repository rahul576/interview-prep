Which similarity measures are used with embeddings, and how do they differ?

AI/ML & GenAI · concept · levels mid, senior

In one line

Cosine similarity compares the angle between vectors, dot product depends on direction and magnitude, and Euclidean distance measures straight-line distance; for unit-normalised vectors all three give the same ranking, so use the metric the embedding model was trained for and configure the index to match.

Detailed explanation

Embeddings place items such as sentences, products or images in a vector space where closeness means similarity. How you measure closeness matters.

Cosine similarity = (a · b) / (|a| |b|), ranging from -1 to 1. It ignores vector length and looks only at direction, which suits text embeddings where length often reflects things like text length or token frequency rather than meaning. It is the most common choice for semantic search and RAG.

Dot product = Σ aᵢbᵢ. It grows with both alignment and magnitude. Some models deliberately encode information in magnitude; in recommendation systems a popular or high-quality item might get a larger vector so it scores higher across many users. Models trained with a dot-product objective (many two-tower recommenders and some retrieval models) should be searched with dot product.

Euclidean (L2) distance = √Σ(aᵢ − bᵢ)²; smaller means more similar. It is natural for clustering methods like k-means and some image embeddings.

The relationship: if vectors are normalised to length 1, cosine similarity equals the dot product, and squared Euclidean distance = 2 − 2 × cosine, so all three produce identical rankings. Many embedding models output normalised vectors, or you can normalise them yourself. The practical rule: check the model's documentation, use the metric it was trained with, and configure the vector index (pgvector operator class, HNSW space, Pinecone metric) accordingly. A mismatch, such as L2 search on unnormalised vectors from a cosine-trained model, does not cause errors; it silently degrades retrieval quality, which you only notice through evaluation metrics like recall@k.

How it works

  1. Generate embeddings with the chosen model.
  2. Normalise them if the model expects cosine similarity.
  3. Create the vector index with the matching metric.
  4. Embed the query the same way and search for nearest neighbours.
  5. Evaluate retrieval quality (recall@k, MRR) on labelled query-document pairs.

Example

-- pgvector: cosine distance operator (<=>) with an HNSW index
CREATE INDEX ON docs USING hnsw (embedding vector_cosine_ops);
SELECT id, title, 1 - (embedding <=> :query_vec) AS cosine_sim
FROM docs ORDER BY embedding <=> :query_vec LIMIT 5;
-- <#> = negative inner product, <-> = L2 distance

Common mistakes

  • Using a different metric in the index than the model was trained for.
  • Mixing normalised and unnormalised vectors in one index.
  • Comparing embeddings from different models or model versions.
  • Treating a cosine score as an absolute probability of relevance.

How to answer in the interview

"Cosine similarity measures the angle between vectors and ignores length, which is why it's the default for text embeddings. Dot product depends on both direction and magnitude, useful when magnitude carries meaning, like popularity in recommender embeddings. Euclidean distance is straight-line distance. If vectors are unit-normalised, all three rank results identically. The rule I follow is to use the metric the embedding model was trained with and configure the vector index to match, because a mismatch silently hurts retrieval."

Likely follow-up questions

  • Why might a vector database prefer dot product? On normalised vectors it equals cosine but skips the norm division, so it is cheaper.
  • What happens if you change embedding model? You must re-embed the whole corpus; vectors from different models aren't comparable.
  • How do you choose a similarity threshold? Tune it on labelled pairs; scores aren't calibrated across models.
