How do you organise ownership and permissions when many teams contribute to Terraform repositories?

Terraform · concept · levels mid, senior, lead

In one line

Map Terraform boundaries to team boundaries (repos, directories, states), route reviews with CODEOWNERS, enforce branch protection, scope a pipeline identity per state and environment, and let a platform team own shared modules and guardrails.

Detailed explanation

When many teams share Terraform, the failure modes are blocked teams, unclear responsibility and large blast radius. The answer is clear ownership at four levels.

Code and state boundaries. Each team owns its own repositories, or directories in a monorepo, each with its own state per environment. They can change their infrastructure without coordinating with everyone. Foundation layers — landing zones, hub networking, identity, policy — and the shared module library are owned by a platform team, published with versions so teams upgrade on their own schedule.

Review routing. A CODEOWNERS file assigns owners per path. Changes under teams/payments/ need payments approval; sensitive paths like /iam/, /network/ or policies/ also require platform or security review. This puts the right expert on the change without making everyone review everything.

Branch protection. The default branch requires pull requests, a minimum number of approvals, approval from code owners, passing checks (fmt, validate, plan, policy checks) and no direct pushes. Plans are posted to the PR so reviewers see the actual impact.

Cloud permissions. Each state is applied by its own pipeline identity using OIDC, with rights only on that team's subscriptions or accounts and that environment. A mistake in one team's code physically cannot modify another team's resources. Humans get read access by default and break-glass access through PIM or similar.

This gives teams autonomy with guardrails: they move fast inside their boundary, and the platform team's policies and modules keep everything consistent.

How it works

  1. Define ownership: which team owns which repo, directory and cloud scope.
  2. Create one state per team component and environment.
  3. Add CODEOWNERS with extra reviewers for sensitive paths.
  4. Configure branch protection with required checks and code-owner review.
  5. Create OIDC-federated pipeline identities scoped per state.
  6. Publish versioned shared modules and policy-as-code from the platform team.

Example

# CODEOWNERS
/teams/payments/          @org/payments-team
/teams/search/            @org/search-team
/modules/                 @org/platform-team
**/iam/                   @org/platform-team @org/security-team
**/network/               @org/platform-team
/policies/                @org/security-team

Common mistakes

  • One giant state that every team applies, so any change can break everything.
  • A single pipeline identity with Owner on all subscriptions.
  • CODEOWNERS without branch protection, so ownership is advisory only.
  • A platform team that must approve every change and becomes a bottleneck.

How to answer in the interview

"I align Terraform boundaries with team boundaries: each team owns its repos or directories and states, while the platform team owns shared modules, policies and foundation layers like networking and identity. CODEOWNERS routes reviews, so team directories need that team's approval and sensitive paths like IAM or network also need platform or security review. Branch protection enforces PRs, required reviews and passing plan and policy checks. In the cloud each state has its own pipeline identity scoped to that team's subscriptions and environment, so a mistake can't touch another team's resources. That gives autonomy with guardrails."

Likely follow-up questions

  • How do you handle a firewall rule another team needs? They raise a PR against the owning team's code or a self-service module input; the owner approves.
  • Monorepo or many repos? Either works; what matters is clear paths, states and identities.
  • How do teams consume module updates? Versioned modules with changelogs; Renovate or Dependabot proposes upgrades.
