What is an artifact repository like Nexus or Artifactory, and why use one?

Artifacts & Code Quality · concept · levels entry, mid

In one line

Nexus and Artifactory are artifact repository managers: they store versioned build outputs (Maven, npm, PyPI, Helm, Docker), proxy and cache public registries, enforce access control and retention, and act as a supply chain control point that keeps builds working during upstream outages.

Detailed explanation

Without a repository manager, every build downloads dependencies directly from the internet and every team stores binaries in its own way. A repository manager centralises both.

Hosted (local) repositories store your own outputs: release jars, npm packages, Python wheels, Helm charts, container images and generic files. Releases are immutable: version 2.4.1 can never be overwritten, so a deployment is always traceable back to an exact build. Snapshot repositories hold work-in-progress builds that can change.

Proxy (remote) repositories cache public sources such as Maven Central, npmjs, PyPI and Docker Hub. The first request fetches from upstream; later requests come from the cache. That gives faster builds, resilience when an upstream is down or a package is deleted (remember left-pad), protection against Docker Hub pull rate limits, and a single place to scan, block or quarantine malicious or vulnerable packages (Sonatype Firewall, JFrog Xray, Curation).

Group (virtual) repositories combine hosted and proxy repos behind one URL, so developers configure one endpoint. Note: keep internal package names reserved or scoped so a public package with the same name cannot be resolved instead (dependency confusion).

Governance: per-repository permissions mapped to SSO groups, tokens for CI, audit logs, and cleanup policies to delete old snapshots and unused images so storage does not grow without limit. Artifacts can be promoted between repositories (dev → staging → release) instead of rebuilt.

How it works

  1. CI resolves dependencies through the group URL.
  2. Cache hit → served locally; miss → fetched upstream, scanned, cached.
  3. CI publishes build outputs to the hosted repo with metadata (commit, build number).
  4. Promotion moves tested artifacts to release repos.
  5. Cleanup jobs remove expired snapshots and untagged images.

Example

<!-- ~/.m2/settings.xml: route all Maven traffic through Nexus -->
<mirrors>
  <mirror>
    <id>nexus</id>
    <mirrorOf>*</mirrorOf>
    <url>https://nexus.acme.internal/repository/maven-public/</url>
  </mirror>
</mirrors>
npm config set registry https://artifactory.acme.internal/artifactory/api/npm/npm-virtual/
docker pull artifactory.acme.internal/docker-remote/library/nginx:1.27

Common mistakes

  • Allowing release versions to be overwritten.
  • No cleanup policy, so disks fill with years of snapshots.
  • Builds that still bypass the proxy and hit the internet directly.
  • Group repos that resolve public packages ahead of internal ones.

How to answer in the interview

"Nexus and Artifactory are artifact repository managers. They store our build outputs, Maven jars, npm packages, Helm charts and Docker images, with immutable versions so every release is traceable. They also proxy and cache public registries like Maven Central, npm and Docker Hub, which speeds up builds, protects us from upstream outages and rate limits, and gives us one control point to scan or block packages. Access is controlled per repository, artifacts are promoted between stages rather than rebuilt, and cleanup policies keep storage under control."

Likely follow-up questions

  • Clean up old snapshots safely? Retention by age and count, keep anything referenced by deployed releases, dry-run first.
  • What is dependency confusion? A public package with an internal name being resolved; prevent with scoped names and repo ordering rules.
  • Nexus vs a cloud registry like ECR? ECR covers containers; repository managers cover many package formats in one place.
