How should microservices communicate: synchronous or asynchronous? What are the trade-offs?

Microservices · concept · levels mid, senior

In one line

Use synchronous calls (REST, gRPC) when the caller needs an immediate answer, and asynchronous messaging (Kafka, RabbitMQ) for state changes others react to; sync is simpler but creates temporal coupling, async decouples but brings eventual consistency and duplicate handling.

Detailed explanation

Synchronous request-response is easy to reason about: call, wait, get a result or an error. It suits queries and user-facing flows that need an answer now, such as "get price" or "validate card". The cost is temporal coupling: the caller depends on the callee's availability and latency at that moment. In a chain A → B → C, latencies add up and availability multiplies (three services at 99.9 percent give about 99.7 percent). A slow dependency holds threads in every caller and can cause cascading failures.

Asynchronous messaging sends events (OrderPlaced) or commands (SendInvoice) through a broker. The producer continues immediately; consumers process when they can. This decouples availability, absorbs load spikes in the queue, enables fan-out to many consumers and natural retries. The costs: eventual consistency (other services learn about changes later), harder debugging and tracing, ordering concerns, duplicates under at-least-once delivery, schema governance and the operational load of a broker.

Most real systems mix both. I use synchronous calls for reads and for the few steps where the user must wait, and events for state changes that other services react to: inventory, notifications, analytics. For synchronous calls, resilience is mandatory: timeouts, limited retries with backoff and jitter for idempotent operations, a circuit breaker and bulkhead (Resilience4j). For messaging: idempotent consumers, dead-letter queues, the outbox pattern and tracing headers.

How it works

  1. Identify whether the caller needs the result to continue.
  2. If yes: REST/gRPC with timeout, retry, circuit breaker.
  3. If no: publish an event or command through the outbox.
  4. Consumers react asynchronously, idempotently.
  5. Long operations return 202 Accepted and a status resource or push notification.

Example

// Synchronous: checkout needs a price now
@CircuitBreaker(name = "pricing", fallbackMethod = "cachedPrice")
@Retry(name = "pricing")
public Price price(String sku) {
    return restClient.get().uri("/prices/{sku}", sku).retrieve().body(Price.class);
}

// Asynchronous: others react to the order
@Transactional
public void placeOrder(Order o) {
    orders.save(o);
    outbox.save(OutboxEvent.of("OrderPlaced", o.getId(), o));
}

Common mistakes

  • Long synchronous chains for a single user request.
  • No timeouts on HTTP clients.
  • Using async for queries that need an answer, then polling awkwardly.
  • Forgetting idempotency and DLQs on the async side.

How to answer in the interview

"Synchronous REST or gRPC is simple and right when the caller needs an immediate answer, but it creates temporal coupling: latency and outages of every downstream service hit the caller. Asynchronous messaging through Kafka or RabbitMQ decouples services and absorbs spikes, at the cost of eventual consistency, harder debugging and duplicates. I use sync calls for reads and user-facing steps, and events for state changes others react to. Sync calls always get timeouts, retries with backoff and circuit breakers with Resilience4j; async consumers are idempotent, with DLQs and the outbox pattern."

Likely follow-up questions

  • How do you trace a request across sync calls and events? W3C trace context in HTTP and message headers, via OpenTelemetry or Micrometer Tracing.
  • Is a non-blocking WebClient call asynchronous communication? No, it is still request-response with temporal coupling, just without blocking a thread.
  • How do you return results of async work to a user? 202 plus a status endpoint, WebSocket or SSE, or a notification.
