How would you do a blue-green replacement of infrastructure, such as a new cluster, using Terraform?

Terraform · design · levels senior, lead

In one line

Parameterise the stack so a green copy is created alongside blue (two module instances or two states), deploy and test on green, shift traffic gradually with weighted DNS or a global load balancer managed as a Terraform variable, roll back by shifting weights back, remove blue after a soak period, and handle stateful data separately.

Detailed explanation

Some infrastructure changes are too risky to apply in place: a Kubernetes cluster upgrade spanning several versions, a new network design, a different node OS or a new region layout. Blue-green turns a risky mutation into a controlled migration with an instant rollback path.

Parameterisation. Write the stack as a module and instantiate it per colour, for example for_each = toset(var.active_colors) producing module.cluster["blue"] and module.cluster["green"], or keep a separate state per colour (cluster-blue, cluster-green) for isolation. The green instance gets the new Kubernetes version or network design.

Deploy and verify. Applications are deployed to green and tested with synthetic traffic, smoke tests and internal users.

Traffic shifting. A layer in front of both stacks splits traffic: Route 53 weighted records, Azure Front Door or Traffic Manager with weighted origins, or a global load balancer. The weights are a Terraform variable, changed through PRs: 10 percent, 50, then 100. Each step is reviewed and observed.

Rollback is simply shifting the weights back while blue is still running, which takes effect in seconds for a load balancer and within the DNS TTL for DNS.

Decommission. After a soak period at 100 percent green, remove "blue" from the colour set and apply, which destroys the old stack.

Stateful data such as databases, storage accounts and message brokers usually lives outside the coloured stacks, in its own state, shared by both colours or migrated deliberately, because duplicating data with every cluster swap is expensive and error-prone.

How it works

  1. Shared layer: data stores and global entry point in their own state.
  2. Add green to the active colours; apply creates the new stack.
  3. Deploy apps to green; run tests.
  4. Shift weights in steps through PRs, monitoring each step.
  5. Roll back by restoring weights if metrics degrade.
  6. After soak, remove blue from the set and apply.

Example

variable "active_colors" { default = ["blue", "green"] }
variable "weights"       { default = { blue = 90, green = 10 } }

module "cluster" {
  source     = "./modules/aks-stack"
  for_each   = toset(var.active_colors)
  color      = each.key
  k8s_version = each.key == "green" ? "1.33" : "1.31"
}

resource "aws_route53_record" "api" {
  for_each       = toset(var.active_colors)
  zone_id        = var.zone_id
  name           = "api.example.com"
  type           = "CNAME"
  ttl            = 60
  set_identifier = each.key
  records        = [module.cluster[each.key].ingress_hostname]
  weighted_routing_policy { weight = var.weights[each.key] }
}

Common mistakes

  • Putting the database inside the coloured stack.
  • High DNS TTLs, so traffic shifts and rollbacks are slow.
  • Destroying blue immediately after reaching 100 percent.
  • Forgetting capacity: green must handle full load before the last step.

How to answer in the interview

"I parameterise the stack, either a module instantiated twice with keys blue and green or a state per colour, so green, with the new Kubernetes version or network design, is created next to blue. Apps are deployed to green and tested. Traffic shifts gradually with weighted DNS or a global load balancer like Front Door or Route 53, with the weights as a Terraform variable: 10, 50, then 100. If metrics degrade, I shift the weights back while blue still runs. After a soak period, blue is removed. Stateful data is shared or migrated separately."

Likely follow-up questions

  • How do you avoid DNS caching delays? Low TTLs set well in advance, or a load balancer layer instead of DNS.
  • What about in-cluster state such as PVCs? Keep state in managed services or migrate with backups.
  • Cost? Double infrastructure for the overlap; keep the window short.
