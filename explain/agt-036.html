A new model version is available. How do you decide whether to switch your production agent to it?

AI Agents & AIOps · scenario · levels mid, senior

In one line

Run the full agent evaluation suite with the new model, several times per task, compare success rate, steps, cost and latency per category, check tool-calling behaviour and output formats, re-tune prompts if needed, repeat safety and red-team tests, then roll out gradually with monitoring and fast rollback.

Detailed explanation

A new model may be better on public benchmarks but behave differently in your agent. Agents are especially sensitive because small changes in tool use, verbosity or instruction following compound over many steps.

Evaluation: run the complete scenario suite with the new model and the current one, multiple runs per task to account for variance, and compare success rate, number of steps, tokens, cost and latency per task, broken down by category. An average improvement can hide a regression in a critical category.

Tool-calling behaviour: check whether the model calls tools more or less eagerly, uses parallel calls, handles errors, respects schemas and output formats, asks for clarification appropriately, and stops at the right time. Newer models often follow instructions more literally, so prompts written to shout at older models ("ALWAYS", "CRITICAL") can cause over-triggering.

Prompt tuning: new models sometimes need adjusted prompts, different reasoning-effort settings or changed examples. Re-tune, then re-run the evals, keeping prompt versions paired with model versions.

Safety: repeat safety and red-team tests, including prompt injection in tool results, refusal behaviour and data-leakage scenarios, because robustness can change in either direction.

Decision: if quality is better, or equal at lower cost or latency, and no critical category regresses, proceed. Roll out gradually: shadow mode or a small share of traffic, a specific user group, then wider. Monitor production metrics against the old version with the same dashboards, and keep rollback to the previous pinned model version quick, ideally a configuration flag. Also note provider deprecation dates, which can force a migration timeline.

How it works

  1. Pin the candidate model version; run the eval suite several times.
  2. Compare metrics per category against the current model.
  3. Inspect traces for tool-calling and format differences.
  4. Adjust prompts and settings; re-evaluate.
  5. Run safety and injection tests.
  6. Canary rollout with monitoring; roll back or proceed.

Common mistakes

  • Switching based on public benchmarks or a few manual tries.
  • Comparing only averages.
  • Single runs per scenario.
  • Skipping safety tests.
  • Using a moving model alias so the switch happens unannounced.

How to answer in the interview

"I run the agent's full evaluation suite with the new model, several times per task, and compare it with the current one on success rate, steps, cost and latency, broken down by task category. I specifically check tool-calling behaviour: does it call tools more or less eagerly, handle errors and follow formats, and does it over- or under-follow instructions. New models sometimes need prompt adjustments, so I re-tune and re-evaluate. Safety and injection tests run again. If it's better, or equal at lower cost, I roll out gradually, starting with a share of traffic, monitor production metrics against the old version and keep rollback quick through a pinned version flag."

Likely follow-up questions

  • Better overall but worse on one critical category? Fix with prompt or tool changes, or route that category to the old model until it passes.
  • Why pin model versions? So changes are deliberate, tested releases rather than silent shifts.
  • What is shadow testing? Running the new model on live inputs without acting and comparing results.
