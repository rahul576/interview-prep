How does asynchronous messaging work using SQS?

Cloud (AWS) · concept · levels mid

In one line

The producer calls SendMessage and continues immediately; consumers poll with ReceiveMessage (long polling, batches up to 10), each received message becomes invisible for the visibility timeout, successful processing calls DeleteMessage, failures reappear and are retried, and after maxReceiveCount the redrive policy moves them to a DLQ; because delivery is at-least-once, processing must be idempotent.

Detailed explanation

Producer side: the API stores the order request and sends a message such as {"orderId":"ORD-1","type":"OrderPlaced"}; once SQS acknowledges, the request returns, for example with 202 Accepted. Batch sends (SendMessageBatch) reduce cost. Optional message attributes carry metadata like correlation IDs.

Consumer side: a Spring Boot service with Spring Cloud AWS @SqsListener, a plain SDK loop, or Lambda via an event source mapping. Consumers long-poll so empty queues cost little.

In-flight state: a received message is not deleted; it carries a receipt handle and is hidden for the visibility timeout. If processing succeeds, the consumer deletes it using the receipt handle. If the consumer crashes, throws or takes too long, the message becomes visible again and another consumer receives it. The ApproximateReceiveCount attribute increases each time.

Poison messages: a redrive policy with maxReceiveCount (say 5) moves repeatedly failing messages to a dead-letter queue where you alert, inspect and later redrive them after fixing the bug.

Idempotency: standard queues may deliver duplicates, and a consumer can process successfully but crash before deleting. So use a processed-message table, unique constraints or conditional writes keyed on a business ID.

Long jobs: extend visibility with ChangeMessageVisibility as a heartbeat.

How it works

  1. Producer sends message; returns immediately.
  2. Consumer long-polls and receives a batch.
  3. Messages hidden for the visibility timeout.
  4. Process each idempotently.
  5. Delete on success; on failure let it reappear.
  6. After max receives, the message moves to the DLQ.

Example

@SqsListener("orders")
public void onOrder(OrderPlaced event) {
    if (processedRepo.existsById(event.messageId())) return;   // idempotency
    fulfilmentService.fulfil(event.orderId());
    processedRepo.save(new Processed(event.messageId()));
}   // returns normally -> Spring Cloud AWS deletes the message; exception -> retried

Common mistakes

  • Deleting before processing, losing messages on crash.
  • Visibility timeout shorter than processing time.
  • Non-idempotent side effects such as double charging.
  • Ignoring the DLQ with no alarm.

How to answer in the interview

"The producer calls SendMessage and continues without waiting. SQS stores it redundantly. Consumers, like a Spring service with @SqsListener or a Lambda, long-poll with ReceiveMessage in batches of up to ten. A received message isn't deleted; it becomes invisible for the visibility timeout. If processing succeeds, the consumer deletes it; if it crashes or fails, the message reappears and is retried. After maxReceiveCount attempts, the redrive policy moves it to a dead-letter queue. Because a message can arrive more than once, I make processing idempotent."

Likely follow-up questions

  • Processing longer than the visibility timeout? The message reappears and is processed twice; extend visibility or raise the timeout.
  • How do you monitor? ApproximateAgeOfOldestMessage, queue depth, DLQ depth alarms.
  • Ordering? Use FIFO with message groups when order matters.
