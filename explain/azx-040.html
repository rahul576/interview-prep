Compare classic release pipelines and YAML pipelines in Azure DevOps. Why do teams move to YAML?

Azure DevOps & Pipelines · concept · levels entry, mid

In one line

Classic pipelines are configured in the UI; YAML pipelines are pipeline as code in the repository, so changes are versioned, reviewed in PRs and branched with the code, reused via templates, and use environments, approvals and checks instead of classic release gates; new Azure DevOps features target YAML, so teams migrate.

Detailed explanation

Classic build definitions and release pipelines use a visual designer: tasks, stages, pre- and post-deployment approvals and gates are clicked together. That is quick for beginners, but the configuration lives in Azure DevOps, not in Git. Changes have only a basic history, can't be reviewed in a pull request, can't differ between branches, and reusing the same logic across 100 projects means copying (task groups help only a little).

YAML pipelines live in an azure-pipelines.yml file. Benefits:

  • Versioned with the code: the pipeline that built release 1.3 is in the 1.3 commit; you can roll back pipeline changes.
  • Reviewable: pipeline changes go through pull requests and branch policies.
  • Branchable: feature branches can change build steps without affecting main.
  • Reusable: templates (steps, jobs, stages, variables) and extends templates standardise pipelines across teams and enforce governance with required template checks.
  • Multi-stage: build, test and deploy in one definition, with deployment jobs targeting environments, which carry approvals and checks (branch control, business hours, exclusive lock, Azure Monitor alerts, REST/Function gates), replacing classic release gates.

Microsoft focuses new development on YAML, and organisation/project settings can disable creation of classic build and release pipelines. Classic still works, and a few things map differently (for example release variables per stage, manual interventions, deployment groups vs environment VM resources), so migration needs some redesign rather than a pure export.

How it works

  1. Inventory classic pipelines; group them by pattern.
  2. Build shared templates for each pattern (e.g. .NET web app to App Service).
  3. Export classic build to YAML (View YAML) as a starting point.
  4. Convert releases into multi-stage YAML with deployment jobs and environments.
  5. Move approvals and gates to environment checks.
  6. Run in parallel, then disable classic and block new ones.

Example

trigger: [main]
stages:
- stage: Build
  jobs:
  - job: build
    pool: { vmImage: ubuntu-latest }
    steps:
    - script: dotnet publish -c Release -o $(Build.ArtifactStagingDirectory)
    - publish: $(Build.ArtifactStagingDirectory)
      artifact: web
- stage: Prod
  dependsOn: Build
  jobs:
  - deployment: deploy
    environment: shop-prod          # approvals & checks configured here
    strategy:
      runOnce:
        deploy:
          steps:
          - task: AzureWebApp@1
            inputs: { azureSubscription: sc-prod, appName: app-shop-prod, package: $(Pipeline.Workspace)/web/**/*.zip }

Common mistakes

  • Converting 1:1 without introducing templates, recreating the sprawl.
  • Putting secrets in YAML instead of variable groups/Key Vault.
  • Forgetting to move approvals to environments and service connections.
  • Leaving classic pipelines enabled after migration.

How to answer in the interview

"Classic pipelines are configured in the UI, which is easy to start, but changes aren't versioned with the code, can't be reviewed in PRs and are hard to reuse. YAML pipelines are code in the repo, so they're versioned, reviewed, branched and rolled back like application code, and the pipeline for an old release matches its code. Templates and extends templates let a platform team standardise and govern pipelines, and multi-stage YAML with environments, approvals and checks replaces classic release gates. Microsoft builds new features for YAML and lets you disable new classic pipelines, so most teams migrate."

Likely follow-up questions

  • Migrate 100 release pipelines? Group by pattern, build templates, convert in waves, run in parallel.
  • What replaces deployment groups? Environments with VM resources.
  • What replaces task groups? Step templates.
