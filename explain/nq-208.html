When should you use PATCH instead of PUT?

REST & API Design · concept · levels mid

In one line

Use PATCH to change only some fields without sending (or knowing) the full resource; use PUT when the client sends the complete new state to replace it (idempotent but risks overwriting fields); PATCH uses JSON Merge Patch or JSON Patch, is not guaranteed idempotent, and should be combined with ETag/If-Match to avoid lost updates.

Detailed explanation

PUT semantics. The body is the entire representation. The server replaces what it has. If the client omits phone, the server should clear it. That is simple and idempotent, but it requires the client to have the full, current resource. If two clients edit different fields at once, each PUT overwrites the other's change: a lost update.

PATCH semantics (RFC 5789). The body describes changes to apply. Typical uses: updating an order status, a user's phone number, toggling a flag, or mobile clients that should not send large objects. Two standard formats:

  • JSON Merge Patch (RFC 7396, application/merge-patch+json): send a partial document. Present fields are set, null removes a field, absent fields are unchanged. Simple, but cannot express "set to null" separately from "remove", and arrays are replaced wholesale.
  • JSON Patch (RFC 6902, application/json-patch+json): an array of operations: add, remove, replace, move, copy, test. Precise and supports array element changes and test preconditions, but more complex.

Idempotency. A merge patch setting status to SHIPPED is effectively idempotent, but JSON Patch add to an array end is not. So PATCH is not guaranteed idempotent and should not be retried blindly.

Concurrency. Because PATCH modifies existing state, use optimistic concurrency: return an ETag (for example from a JPA @Version), require clients to send If-Match, and answer 412 Precondition Failed if the resource changed.

Implementing safely in Spring Boot. Do not bind the PATCH body directly onto the JPA entity, which allows mass assignment of fields like role or price. Use a dedicated DTO with optional fields (or JsonNullable from openapi-generator to distinguish absent from null), whitelist patchable fields, validate the merged result, and apply business rules (e.g. status transitions only along allowed paths).

How it works

  1. Client GETs the resource and its ETag.
  2. Client sends PATCH with only changed fields and If-Match.
  3. Server checks the version (else 412).
  4. Server applies allowed changes to the entity, validates the result.
  5. Server saves, returns 200 with the resource and new ETag.

Example

PATCH /users/42
Content-Type: application/merge-patch+json
If-Match: "7"

{ "phone": "+91-98450-00000", "nickname": null }
PATCH /users/42
Content-Type: application/json-patch+json

[ { "op": "test", "path": "/status", "value": "ACTIVE" },
  { "op": "replace", "path": "/email", "value": "asha@example.com" } ]
record UserPatch(Optional<String> phone, Optional<String> nickname) {}

@PatchMapping(path = "/users/{id}", consumes = "application/merge-patch+json")
ResponseEntity<UserDto> patch(@PathVariable long id, @RequestHeader("If-Match") String ifMatch,
                              @RequestBody UserPatch p) {
    User u = repo.findById(id).orElseThrow(NotFoundException::new);
    if (!ifMatch.equals("\"" + u.getVersion() + "\"")) return ResponseEntity.status(412).build();
    if (p.phone() != null) u.setPhone(p.phone().orElse(null));     // null field = absent
    if (p.nickname() != null) u.setNickname(p.nickname().orElse(null));
    validator.validate(u);
    User saved = repo.save(u);
    return ResponseEntity.ok().eTag("\"" + saved.getVersion() + "\"").body(UserDto.from(saved));
}

Common mistakes

  • Partial bodies sent with PUT, wiping data.
  • Binding PATCH JSON directly to entities (mass assignment).
  • Not distinguishing absent from null fields.
  • Retrying non-idempotent JSON Patch operations.
  • No concurrency control.

How to answer in the interview

"I use PATCH when the client only wants to change some fields, like an order status or a phone number, without sending or even knowing the whole resource. PUT is for when the client sends the complete new state and the server replaces it; it's idempotent and simple, but risks overwriting fields the client didn't mean to touch. PATCH bodies follow a format: JSON Merge Patch, a partial document where null removes a field, or JSON Patch, a list of operations. PATCH isn't guaranteed idempotent, so I combine it with ETag and If-Match to avoid lost updates, and in Spring I apply it through a DTO with whitelisted fields and validate the result."

Likely follow-up questions

  • How would you implement PATCH in Spring Boot safely? DTO with optional fields, whitelist, apply to the loaded entity, validate, version check via If-Match.
  • Merge Patch vs JSON Patch? Merge Patch is simpler; JSON Patch handles arrays and test preconditions.
  • Which status if the ETag doesn't match? 412 Precondition Failed.
