How would you design Terraform for an Azure hub-and-spoke network used by many application teams?

Terraform · design · levels mid, senior, lead

In one line

The platform team owns the hub (firewall, gateways, Bastion, central private DNS zones) in its own state; each application gets a spoke from a spoke vending module in a separate state, peered to the hub with routes through the firewall, central IPAM to avoid overlaps, and app teams deploying inside but not changing networking.

Detailed explanation

Hub-and-spoke centralises shared network services and security inspection while giving each application its own isolated VNet. The Terraform design should mirror ownership.

Hub state (platform team): the hub VNet, Azure Firewall or an NVA with firewall policy, VPN or ExpressRoute gateways, Azure Bastion, DNS Private Resolver, and the private DNS zones such as privatelink.blob.core.windows.net. Centralising those zones matters: if every spoke created its own zone, private endpoint name resolution would break across the organisation.

Spoke vending module: one call per application and environment, each in its own state (often in the application subscription). It creates the spoke VNet and subnets, peering in both directions (the hub side needs permissions in the hub subscription, typically via a second provider alias), route tables with 0.0.0.0/0 and cross-spoke traffic sent to the firewall's private IP, NSGs, and virtual network links to the central DNS zones. Per-spoke states keep blast radius small and let spokes be added without touching the hub's plan.

IP address management prevents overlapping ranges, which would make peering impossible. Options include IPAM pools in Azure Virtual Network Manager or a simple registry in code, such as a map of allocated CIDRs reviewed in PRs.

Boundaries: application teams deploy workloads into their spokes but cannot modify peering, routes or DNS links; Azure Policy and RBAC enforce it. Azure Verified Modules such as the hub networking pattern provide good building blocks.

How it works

  1. Platform state creates hub VNet, firewall, gateways, Bastion and DNS zones.
  2. A team requests a spoke with name, environment and size.
  3. IPAM allocates a non-overlapping CIDR.
  4. Spoke module creates VNet, subnets, NSGs and route tables to the firewall.
  5. It creates peering both ways and links to private DNS zones.
  6. App team deploys resources into the spoke subnets.

Example

module "spoke_orders_prod" {
  source  = "app.terraform.io/acme/spoke/azurerm"
  version = "~> 3.2"

  providers = {
    azurerm     = azurerm.orders_prod
    azurerm.hub = azurerm.hub
  }

  name               = "orders-prod"
  address_space      = ["10.42.0.0/22"]       # from IPAM
  hub_vnet_id        = data.azurerm_virtual_network.hub.id
  firewall_private_ip = "10.0.1.4"
  private_dns_zone_ids = var.central_private_dns_zone_ids
  subnets = {
    app = { cidr = "10.42.0.0/24" }
    pe  = { cidr = "10.42.1.0/24" }
  }
}

Common mistakes

  • One state containing the hub and every spoke.
  • Private DNS zones created per spoke, breaking resolution.
  • Overlapping CIDRs discovered only at peering time.
  • Forgetting the hub side of the peering or gateway transit settings.
  • Giving app teams rights to edit route tables.

How to answer in the interview

"The platform team owns the hub in its own state: firewall, gateways, Bastion and the central private DNS zones used for private endpoints. Each application gets a spoke from a vending module, in its own state, which creates the VNet, peers it with the hub, adds route tables sending traffic through the firewall, links the private DNS zones and applies NSGs. IPAM is central to avoid overlaps, through Virtual Network Manager IPAM or a registry in code. App teams deploy into their spokes but can't change peering or routes, and AVM modules give good building blocks."

Likely follow-up questions

  • How do spoke teams request firewall rules? PRs to a rules collection in the platform repo, applied by the platform pipeline.
  • Virtual WAN instead? Managed hub alternative when many regions and branches exist.
  • Why bidirectional peering? Each VNet needs its own peering resource for traffic to flow.
