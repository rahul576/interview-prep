Pods pass health checks, but about 3 percent of requests return 503 errors. How do you diagnose it?

Kubernetes · scenario · levels mid, senior

In one line

Intermittent 503s from "healthy" pods are usually a timing problem, not a broken app: most often the termination race between endpoint removal and SIGTERM, a readiness probe that lies, or a keep-alive timeout mismatch between the load balancer and the app. Find the pattern in the ingress logs first, then fix that cause.

Detailed explanation

Health checks show that a pod is up when they run, not what happens in the seconds when pods start, stop or move, which is where a steady few-percent error rate usually comes from. So the first question is correlation: do the 503s cluster around deployments, scale-down, autoscaler consolidation or node drains?

The classic cause is the termination race. When a pod is deleted, the kubelet sends SIGTERM in parallel with the EndpointSlice update that kube-proxy, the ingress controller and cloud load balancers must pick up. Propagation takes up to several seconds, so traffic still reaches a process that has stopped listening. The fix is a preStop sleep of 5-15 seconds, an app that finishes in-flight requests after SIGTERM, and a long enough terminationGracePeriodSeconds.

The second family is start-up: a readiness probe that passes before caches, pools or warm-up are done. The third is keep-alive mismatch: if the app closes idle connections after 5 seconds but the load balancer reuses them for 60, some requests land on just-closed connections. The app's idle timeout must be longer than the load balancer's. Others are too few replicas or OOMKilled pods.

How it works

  1. Plot 503s over time against deploy, scale and drain events.
  2. Read ingress or load balancer logs: which upstream pod answered, upstream status, "connection reset" or "no live upstreams".
  3. If errors hit terminating pods, add a preStop delay and graceful SIGTERM handling.
  4. If errors hit new pods, make readiness check real dependencies and add a startupProbe.
  5. If errors are random, compare idle and keep-alive timeouts along the chain.
  6. Check restarts and OOMKilled events with kubectl get pods and kubectl describe.

Example

spec:
  terminationGracePeriodSeconds: 45
  containers:
  - name: api
    lifecycle:
      preStop:
        sleep:
          seconds: 10      # let endpoints and LBs stop sending traffic
    readinessProbe:
      httpGet: { path: /ready, port: 8080 }
      periodSeconds: 5

Common mistakes

  • Treating "pods are healthy" as proof the platform is fine without looking at upstream logs.
  • A preStop sleep longer than the grace period, so the app is SIGKILLed mid-request.
  • Readiness probes that only check that the process listens.
  • App keep-alive timeout shorter than the load balancer idle timeout.

How to answer in the interview

"I'd correlate the 503s with deployments, scaling and drains, and read ingress logs to see which upstream pod returned them. If they hit terminating pods, it's the endpoint-removal race, so I'd add a preStop sleep and graceful SIGTERM handling. If they hit new pods, readiness passes too early. If random, I'd check that the app's keep-alive timeout exceeds the load balancer's. Then I'd verify with a load test during a rolling restart."

Likely follow-up questions

  • How would you verify the fix before production? Run a constant load test in staging while doing kubectl rollout restart and scale-down; expect zero 5xx.
  • Why can't Kubernetes remove the pod from endpoints first? Endpoint updates are eventually consistent across many independent components; there is no global barrier.
  • What about long-lived connections like WebSockets? Drain them actively on SIGTERM and give a longer grace period.
