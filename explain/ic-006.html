How do Terraform outputs work, and what does sensitive = true do?

Infrastructure as Code · concept · levels entry

In one line

Outputs expose values after apply to people, scripts (terraform output -json) and parent modules; sensitive = true redacts the value in CLI output but it is still stored in plain text in the state.

Detailed explanation

An output block declares a value the configuration exposes, such as a load balancer DNS name, a VPC ID or a database endpoint. In a root module, outputs are printed at the end of terraform apply and can be read later with terraform output, or in machine-readable form with terraform output -json or terraform output -raw name, which is how scripts and pipelines consume them. In a child module, outputs are the module's return values: the parent references them as module.network.vpc_id. Other configurations can also read root outputs through terraform_remote_state.

Marking an output sensitive = true tells Terraform to show (sensitive value) instead of the value in plan and apply output. Terraform tracks sensitivity through expressions: if an output is derived from a sensitive variable or a sensitive resource attribute, Terraform requires you to mark the output sensitive too, otherwise it errors. This prevents accidental leakage into CI logs.

What sensitive does not do is encrypt anything. The value is still written to the state file in plain text, and terraform output -json or terraform output -raw will still print it. That is why the state backend must be encrypted, access-controlled and audited, and why the better pattern for secrets is to keep them out of Terraform outputs altogether: store them in a secret manager and let applications read them at runtime.

How it works

  1. Terraform evaluates output expressions after apply.
  2. Values are stored in the state's outputs section.
  3. Root outputs are printed; sensitive ones are redacted.
  4. terraform output -json returns all outputs, including sensitive values, for automation.
  5. Parent modules read child outputs as module.<name>.<output>.

Example

output "alb_dns_name" {
  value       = aws_lb.app.dns_name
  description = "Public DNS name of the load balancer"
}

output "db_password" {
  value     = random_password.db.result
  sensitive = true
}
terraform output alb_dns_name
terraform output -json | jq -r '.alb_dns_name.value'
terraform output -raw db_password   # still prints the secret: protect access

Common mistakes

  • Believing sensitive = true encrypts the value or keeps it out of state.
  • Passing secrets between pipeline stages through outputs printed in logs.
  • Exposing too many outputs, creating hidden coupling with consumers.
  • Outputs without descriptions in shared modules.

How to answer in the interview

"Outputs are the values a configuration exposes after apply: people see them at the end of apply or with terraform output, scripts use terraform output -json, and in modules they're how a parent gets values from a child. Marking an output sensitive hides it in CLI and plan output, and Terraform propagates that flag so derived values must be sensitive too. But it doesn't encrypt anything: the value is still in plain text in the state, and output -json still shows it. So the state backend has to be encrypted and locked down, and for real secrets I prefer keeping them in a secret manager instead of passing them around as outputs."

Likely follow-up questions

  • How should a pipeline pass a database password to an application safely? Store it in a secret manager and grant the app's identity read access; pass only the secret's ARN or name.
  • What is the sensitive() function? It marks any expression as sensitive, like the output argument.
  • Can outputs depend on resources explicitly? Yes, outputs support depends_on for hidden dependencies.
