Trace how an HTTPS request from the internet reaches a pod in a Kubernetes cluster.

Kubernetes · concept · levels senior, lead

In one line

DNS resolves to a cloud load balancer (from a LoadBalancer Service), which forwards to the ingress controller or Gateway pods; they terminate TLS and route by host and path to a Service, whose virtual IP is translated by kube-proxy (iptables/IPVS/nftables) or eBPF to a ready pod IP from EndpointSlices, delivered over the CNI network.

Detailed explanation

1. DNS. shop.example.com resolves to the address of a cloud load balancer, or to an anycast/CDN edge in front of it.

2. Cloud load balancer. Created by the cloud controller manager (or the AWS Load Balancer Controller) for the ingress controller's Service of type LoadBalancer. An L4 load balancer forwards TCP to nodes on a NodePort, or directly to pod IPs in "IP target" mode on VPC-native CNIs.

3. Ingress controller / Gateway. Pods such as NGINX-based controllers, Envoy Gateway, Traefik or a cloud gateway implementation read Ingress or Gateway API (Gateway + HTTPRoute) objects. They terminate TLS using a certificate in a Secret, commonly issued and renewed by cert-manager via ACME, then match the host and path and choose a backend Service. Many controllers send traffic directly to endpoint pod IPs, bypassing the Service virtual IP.

4. Service and kube-proxy. If traffic goes to the Service ClusterIP, kube-proxy rules (iptables, IPVS or nftables) on the node, or eBPF programs with Cilium, rewrite the destination to one of the endpoints in the Service's EndpointSlices, which contain only pods passing readiness probes.

5. CNI network. The packet travels to the pod's node via an overlay (VXLAN/Geneve) or native VPC routing (AWS VPC CNI, Azure CNI), enters the pod's network namespace through a veth pair, and reaches the container port.

Responses return the same way; with SNAT along the path, the pod may see a node IP rather than the client IP, which is what externalTrafficPolicy: Local or proxy protocol / X-Forwarded-For headers address.

How it works

  1. Client → DNS → load balancer IP.
  2. LB → node port or ingress pod IP.
  3. Ingress/Gateway: TLS termination, host/path routing.
  4. Service → endpoint selection by kube-proxy or eBPF.
  5. CNI delivers to the pod; only ready pods are endpoints.

Example

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: shop, namespace: shop }
spec:
  parentRefs: [{ name: public-gw, namespace: infra }]
  hostnames: ["shop.example.com"]
  rules:
    - matches: [{ path: { type: PathPrefix, value: /api } }]
      backendRefs: [{ name: api, port: 80 }]

Common mistakes

  • Forgetting readiness, so traffic reaches pods that are not ready.
  • Losing client IPs through SNAT without forwarding headers.
  • Creating a load balancer per Service instead of sharing an ingress or gateway.

How to answer in the interview

"DNS resolves the hostname to a cloud load balancer, created by a LoadBalancer Service for the ingress controller. The load balancer forwards to the ingress controller pods, or a Gateway API implementation, which terminates TLS with a certificate often issued by cert-manager and routes by host and path to a backend Service. The Service is a stable virtual IP; kube-proxy's iptables or IPVS rules, or eBPF with Cilium, pick one of the ready endpoints from EndpointSlices. The packet then travels over the CNI network into the pod's namespace. Only pods passing readiness are endpoints."

Likely follow-up questions

  • What is externalTrafficPolicy: Local? Only nodes with local endpoints receive traffic, preserving the client IP and avoiding an extra hop, at the risk of uneven load.
  • Ingress or Gateway API? Gateway API is the more expressive successor, with role separation between infrastructure and app teams.
  • Where can TLS terminate? At the cloud LB, at the ingress, or end-to-end at the pod or mesh sidecar.
