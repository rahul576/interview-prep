What is the transactional outbox pattern, and why is it needed?

Data & Storage Design · concept · levels entry, mid, senior

In one line

The outbox pattern writes the business change and the event into the same database transaction, then a relay (or CDC) publishes the event, which removes the dual-write problem.

Detailed explanation

When a service saves an order and then publishes OrderCreated to Kafka, there are two systems and no shared transaction. If the DB commit succeeds but the publish fails (or the pod crashes in between), downstream services never hear about the order. If you publish first and the DB transaction then rolls back, they hear about an order that doesn't exist. Retrying doesn't fully fix it, because you can't atomically do both.

The outbox solves it with one atomic write: insert the order and a row in an outbox table in one transaction. A separate relay reads unsent outbox rows and publishes them, marking them sent. With change data capture (Debezium reading the WAL/binlog), no polling is needed and ordering follows commit order.

How it works

  1. BEGIN; INSERT INTO orders …; INSERT INTO outbox(id, aggregate_id, type, payload) …; COMMIT;
  2. Relay polls outbox (or Debezium streams it) and publishes to the broker, keyed by aggregate_id to preserve per-entity order.
  3. Mark rows as published, or delete them after a retention period.
  4. Consumers deduplicate by event id because delivery is at least once.

Example

CREATE TABLE outbox (
  id UUID PRIMARY KEY,
  aggregate_id TEXT NOT NULL,
  event_type TEXT NOT NULL,
  payload JSONB NOT NULL,
  created_at TIMESTAMPTZ DEFAULT now(),
  published_at TIMESTAMPTZ
);

Debezium's outbox event router can route rows to topics by event_type automatically.

Common mistakes

  • Publishing inside the transaction (broker call can succeed and DB roll back).
  • Consumers that aren't idempotent.
  • Letting the outbox table grow forever.
  • Parallel relays that publish out of order for the same entity.

How to answer in the interview

"Updating the database and publishing an event are two separate writes, so one can fail. With the transactional outbox, I write the event into an outbox table in the same transaction as the business data. A relay, ideally Debezium reading the transaction log, publishes it to Kafka. Delivery is at least once, so consumers deduplicate by event ID."

Likely follow-up questions

  • How do you keep per-entity order? Key messages by aggregate ID; one partition per key.
  • Polling vs CDC? Polling is simpler; CDC has lower latency and load.
  • What about the inbox pattern? Consumers store processed IDs in their own DB in the same transaction as their update.
