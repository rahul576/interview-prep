What are virtual threads, and how do they differ from platform threads?

Modern Java (11-21) · concept · levels mid, senior

In one line

A platform thread wraps one OS thread (heavy, limited to thousands, so we pool them); a virtual thread (final in Java 21) is a lightweight JVM-managed thread that runs on a small pool of carrier threads and is unmounted when it blocks, so you can have millions of them for I/O-bound work.

Detailed explanation

Platform threads (new Thread(...) before Java 21) map 1:1 to operating system threads. Each reserves a large stack (often around 1 MB of address space by default), creation and context switches go through the kernel, and a server realistically handles a few thousand. That is why servlet containers use thread pools of, say, 200 threads. In the thread-per-request model, each request holds a thread for its whole duration, even while it is just waiting 300 ms for a database. When all 200 are waiting, new requests queue, even though the CPU is idle. The usual escape was asynchronous/reactive code, which is efficient but harder to write, debug and profile.

Virtual threads keep the simple blocking style but make threads cheap. They are ordinary java.lang.Thread objects managed by the JVM. Their stacks live on the heap as small, growable chunks, so creating one costs about as much as creating an object. The JVM mounts a virtual thread on a carrier (a platform thread in a ForkJoinPool) to run it. When the code performs a blocking operation the JDK supports, such as socket I/O, Thread.sleep, BlockingQueue.take or a ReentrantLock, the JVM unmounts it, saving its stack, and the carrier runs another virtual thread. When the I/O completes, the virtual thread is scheduled again.

The result: throughput of I/O-bound services scales with the number of concurrent tasks rather than pool size. Virtual threads are not faster per operation and do not help CPU-bound work; the number of cores still limits that. They should not be pooled: create one per task.

How it works

  1. Task starts on a new virtual thread (cheap heap object).
  2. Scheduler mounts it on a free carrier thread.
  3. Blocking call: stack frames are saved to the heap, carrier released.
  4. I/O completes: thread becomes runnable, remounted (maybe on another carrier).
  5. Task finishes; the object is garbage collected.

Example

Thread vt = Thread.ofVirtual().name("order-", 0).start(() -> callInventory());
Thread pt = Thread.ofPlatform().start(() -> crunchNumbers());

try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {
    IntStream.range(0, 100_000).forEach(i ->
        ex.submit(() -> { Thread.sleep(Duration.ofSeconds(1)); return i; }));
}   // 100k concurrent sleeps finish in about a second

Common mistakes

  • Expecting CPU-heavy work to get faster.
  • Pooling virtual threads in a fixed pool.
  • Forgetting downstream limits (DB connections) still cap concurrency.
  • Assuming every blocking call unmounts (some native calls pin the carrier).

How to answer in the interview

"A platform thread is a thin wrapper around an OS thread: heavyweight, expensive to create, and you only get a few thousand, so we pool them. A virtual thread, final since Java 21, is a lightweight thread managed by the JVM. Lots of virtual threads run on a small pool of carrier platform threads; when one blocks on I/O, the JVM unmounts it, saves its stack to the heap and gives the carrier to another virtual thread, then resumes it when the I/O completes. So I can have millions and keep writing simple blocking thread-per-request code that scales like async code. It doesn't speed up CPU-bound work, and I never pool them."

Likely follow-up questions

  • How many carrier threads does the default scheduler use? By default as many as available processors, tunable with jdk.virtualThreadScheduler.parallelism.
  • Are virtual threads daemon threads? Yes, always.
  • Do they replace reactive programming? For most request/response services, yes; reactive still suits streaming and backpressure.
