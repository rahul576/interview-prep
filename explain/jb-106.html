What is the difference between submit() and execute()?

Concurrency · concept · levels mid, senior

In one line

execute(Runnable) (from Executor) returns nothing; submit(...) (from ExecutorService) accepts a Runnable or Callable and returns a Future. The key practical difference: with submit, exceptions are captured in the Future and are silently lost if nobody calls get().

Detailed explanation

Executor is the minimal interface with a single method, execute(Runnable): "run this sometime". ExecutorService extends it with lifecycle methods and submit, which wraps the task in a FutureTask and returns it as a Future. Through the Future you can wait (get), poll (isDone), cancel (cancel(true) interrupts it) or read the result. For a submitted Runnable, get() returns null.

The more important difference is exception handling. With execute, if the task throws, the exception propagates out of the worker thread's run, reaches the thread's UncaughtExceptionHandler (by default printed to System.err), and in a ThreadPoolExecutor the worker thread dies and is replaced. The failure is at least visible.

With submit, the FutureTask catches the exception and stores it. It is only rethrown, wrapped in ExecutionException, when someone calls future.get(). If you fire and forget with submit, a failure leaves no trace: no log, no stack trace. This is a common cause of background jobs that "silently stop working". The uncaught-exception handler never sees it.

So: use execute for fire-and-forget work where you want failures to surface via the handler (but still log inside the task), and submit when you need a result, cancellation or to wait, and then always inspect the Future. CompletableFuture with whenComplete/exceptionally is a cleaner alternative for asynchronous error handling.

How it works

  1. execute(task): the pool runs task.run() directly on a worker.
  2. Exception escapes, hits the UncaughtExceptionHandler, worker is replaced.
  3. submit(task): the pool wraps it in FutureTask and runs that.
  4. FutureTask.run() catches any Throwable and stores it as the outcome.
  5. future.get() throws ExecutionException with the original as getCause().

Example

ExecutorService pool = Executors.newFixedThreadPool(2);

pool.execute(() -> { throw new IllegalStateException("boom-1"); });
// Stack trace printed by the uncaught exception handler

Future<?> f = pool.submit(() -> { throw new IllegalStateException("boom-2"); });
// Nothing printed! The exception is stored in f

try {
    f.get();
} catch (ExecutionException e) {
    log.error("Task failed", e.getCause());   // boom-2 surfaces here
}

// Safer fire-and-forget: log inside the task, or use CompletableFuture
CompletableFuture.runAsync(this::syncJob, pool)
    .whenComplete((v, ex) -> { if (ex != null) log.error("syncJob failed", ex); });

Common mistakes

  • Using submit and ignoring the Future, losing all errors.
  • Expecting an UncaughtExceptionHandler to catch errors from submitted tasks.
  • Calling get() without a timeout and blocking forever.
  • Forgetting to unwrap ExecutionException.getCause() when logging.

How to answer in the interview

"execute comes from the Executor interface, takes a Runnable and returns nothing. submit comes from ExecutorService, takes a Runnable or Callable and returns a Future I can use to get the result, wait or cancel. The important difference is exceptions: with execute the exception escapes to the thread's uncaught exception handler and gets printed or logged. With submit it's captured inside the Future and only rethrown wrapped in ExecutionException when I call get. If nobody calls get, the failure is silently swallowed, which is a common source of lost errors in background jobs."

Likely follow-up questions

  • How would you make sure exceptions from submitted tasks are always logged? Wrap tasks with a try/catch that logs, override ThreadPoolExecutor.afterExecute to inspect Futures, or use CompletableFuture with whenComplete.
  • What does cancel(true) do? Marks the Future cancelled and interrupts the running thread if the task has started.
  • What is invokeAll? Submits a collection of Callables and waits for all, returning their Futures.
