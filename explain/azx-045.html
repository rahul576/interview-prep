Compare Microsoft-hosted agents, self-hosted agents, scale set agents and Managed DevOps Pools.

Azure DevOps & Pipelines · concept · levels mid, senior

In one line

Microsoft-hosted agents: a fresh VM per job, zero maintenance, but no private network access and no persistent cache; self-hosted: full control and private access but you patch and scale them; VMSS agents: Azure DevOps autoscales your scale set; Managed DevOps Pools: Microsoft-managed pools with VNet injection, custom images, standby and stateful options.

Detailed explanation

Microsoft-hosted agents (ubuntu-latest, windows-latest, macOS) give a clean VM with many tools preinstalled for every job, then discard it. That's great for isolation and zero maintenance, but the VMs have fixed sizes, run on public networks (no access to private endpoints or on-prem), can't keep caches or Docker layers between jobs, and image updates can change tool versions unexpectedly.

Self-hosted agents run the agent on your own VMs, containers or Kubernetes pods. You choose hardware, tools and network location, so they can reach private resources and keep caches warm. But you own patching, security hardening, scaling and cleanup, and a stateful agent can carry state, secrets or malware between jobs.

Azure VM Scale Set agents were the first managed middle ground: you provide a VMSS and image; Azure DevOps scales it up and down, optionally tearing down machines after each use. You still manage the scale set and image.

Managed DevOps Pools (generally available since late 2024) are the newer service: Microsoft runs the agent infrastructure in your subscription context, you choose VM sizes, Azure Marketplace or custom Compute Gallery images (including the Microsoft-hosted-like images), VNet injection for private access, stateless (fresh agent per job) or stateful agents with persistent caches, standby agents on a schedule for fast starts, and autoscaling. They're usually the best choice when pipelines need private networking or bigger machines.

Choose on network access, speed (warm caches, standby), cost, security isolation, and maintenance capacity.

How it works

  1. Public builds, simple tools → Microsoft-hosted.
  2. Private network or larger VMs → Managed DevOps Pools.
  3. Special hardware or on-prem → self-hosted.
  4. Untrusted code (forks) → stateless, isolated pools.
  5. Monitor queue times and utilisation; tune standby and max agents.

Common mistakes

  • Stateful agents shared between trusted and untrusted pipelines.
  • Self-hosted agents running as admin with broad network reach.
  • Never updating self-hosted images.
  • Ignoring parallel job licensing when adding agents.

How to answer in the interview

"Microsoft-hosted agents give a fresh VM per job with no maintenance, perfect for isolation, but they can't reach private networks or keep caches. Self-hosted agents give full control and private access, but we patch, secure and scale them. VM scale set agents let Azure DevOps autoscale a scale set we manage. Managed DevOps Pools are the newer option: Microsoft manages the agents, we pick sizes and custom images, inject them into our VNet, choose stateless or stateful agents and keep standby agents for fast starts. When pipelines need private network access, I usually choose Managed DevOps Pools."

Likely follow-up questions

  • Prevent secrets leaking on stateful agents? Use stateless agents for untrusted work, clean workspaces, separate pools per trust level.
  • Do Managed DevOps Pools need parallel jobs? Yes, self-hosted parallel job licensing still applies.
  • Cost driver? VM runtime; standby agents cost money while idle.
