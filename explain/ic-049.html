How do you decide how to split Terraform state?

Infrastructure as Code · concept · levels mid

In one line

Split state to limit blast radius: by environment and account first, then by layer (network, data, application) according to change frequency and team ownership; smaller states plan faster, but too many tiny states create dependency and boilerplate overhead.

Detailed explanation

A single state for everything is simple at first, but every plan refreshes every resource, one lock blocks all teams, any mistake can affect the whole estate, and everyone needs permissions for everything. Splitting addresses these problems; the question is where to cut.

Blast radius is the main reason. A bad apply, a provider bug or a corrupted state then affects only one component. Production and non-production must never share a state, and states usually align with accounts or subscriptions, which are also security boundaries.

Layers by change frequency and lifecycle. Foundational resources such as VPCs, transit gateways, DNS zones and IAM baselines change rarely and are high-risk; shared data stores such as databases and buckets with data are long-lived and must be protected; application stacks like services, queues and alarms change daily. Putting them in separate states means daily deploys never plan against the network, and protective permissions can differ.

Ownership. Map states to teams. The platform team owns network and clusters; each product team owns its application states. Clear ownership determines who reviews and who has apply permissions.

Performance and contention. Smaller states refresh and plan faster and reduce lock waits.

The opposite extreme. Hundreds of micro-states, one per resource, mean many cross-state references (remote state, data lookups, parameter stores), manual ordering of applies, duplicated backend and provider boilerplate, and harder refactoring, because moved blocks don't work across states. Aim for components that are cohesive: things that change together and are owned by the same team live together. Tools like Terragrunt or HCP Terraform Stacks help manage many states when needed.

How it works

  1. Separate by environment and account.
  2. Within each, split by layer: foundation, data, application.
  3. Align with team ownership and pipelines.
  4. Connect states through outputs, data sources or parameter stores.
  5. Revisit boundaries as the system grows; split with removed/import blocks or state mv.

Example

live/
  prod/
    network/          # VPC, subnets, TGW, DNS  (platform team, rare changes)
    eks-cluster/      # cluster, node groups    (platform team)
    data/orders-db/   # RDS, backups            (orders team, prevent_destroy)
    apps/orders-api/  # ECS service, ALB rules  (orders team, daily)
  dev/
    network/ ...
# apps/orders-api reads from network via a contract
data "aws_ssm_parameter" "private_subnets" {
  name = "/platform/network/prod/private_subnet_ids"
}

Common mistakes

  • Prod and dev in the same state.
  • One monolithic state that takes 20 minutes to plan.
  • One state per resource, with fragile chains of dependencies.
  • Database and frequently deployed app code in the same state with broad permissions.

How to answer in the interview

"I split state mainly to limit blast radius, so a bad apply or a corrupted state only affects one part. The natural first boundaries are environment and account: never prod and dev in one state. Then layers with different change frequency and ownership: networking and DNS that rarely change, shared data stores, and application stacks that change daily and belong to product teams. Smaller states also plan faster and reduce lock contention. But hundreds of tiny states create lots of cross-state dependencies, ordering problems and boilerplate, so I aim for components that match how teams work."

Likely follow-up questions

  • Should a database and the application that uses it share a state? Usually not: the database is long-lived and protected, the app changes daily; separate states with narrower permissions are safer.
  • How do you split an existing state? removed/import blocks or terraform state mv to a new state, verified by empty plans.
  • How do you order applies across states? Pipeline dependencies, Terragrunt dependencies or Stacks.
