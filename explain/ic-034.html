What are dynamic blocks in Terraform, and when should you use them?

Infrastructure as Code · concept · levels mid

In one line

A dynamic block generates repeated nested blocks (such as ingress rules or setting blocks) from a collection with for_each and a content body; useful in reusable modules, but overuse hurts readability, and separate resources are often clearer.

Detailed explanation

Some resources define parts of themselves with nested blocks rather than arguments, for example ingress {} and egress {} inside an aws_security_group, setting {} in an Elastic Beanstalk environment, or rule {} in a WAF. Normal for_each repeats a whole resource; to repeat a nested block inside one resource, you use a dynamic block.

Syntax: dynamic "ingress" { for_each = var.ingress_rules content { ... } }. The label is the name of the nested block to generate. Inside content, the iterator is named after the label by default, so you access ingress.key and ingress.value; the iterator argument renames it. You can also use dynamic blocks to make an optional nested block: for_each = var.logging_enabled ? [1] : [].

They shine in reusable modules, where callers pass a list of rules or settings and the module should not hard-code how many there are.

The downsides: dynamic blocks hide the actual configuration behind loops, making code and reviews harder, and plans on large nested-block resources are noisy. A security group with 30 inline rules is one resource; changing one rule often shows the whole set of nested blocks being modified because the provider tracks them as a set, which makes it hard to see what actually changed. Many providers now offer separate resources for the repeated items, for example aws_vpc_security_group_ingress_rule and aws_vpc_security_group_egress_rule, each rule then a resource with its own address, combined with for_each. That yields smaller, clearer diffs and lets different modules add rules to the same group. Do not mix inline rules and separate rule resources for the same group: they fight each other.

HashiCorp's guidance is to use dynamic blocks sparingly, mainly when building modules, not to hide simple static configuration.

How it works

  1. Terraform evaluates the for_each collection.
  2. For each element, it emits one nested block with the content body.
  3. The iterator exposes key and value.
  4. An empty collection produces no blocks.
  5. The provider receives the expanded blocks like hand-written ones.

Example

variable "ingress_rules" {
  type = list(object({ port = number, cidr = string, description = string }))
}

resource "aws_security_group" "web" {
  name   = "web"
  vpc_id = var.vpc_id

  dynamic "ingress" {
    for_each = var.ingress_rules
    content {
      from_port   = ingress.value.port
      to_port     = ingress.value.port
      protocol    = "tcp"
      cidr_blocks = [ingress.value.cidr]
      description = ingress.value.description
    }
  }
}

# Often clearer: one resource per rule
resource "aws_vpc_security_group_ingress_rule" "web" {
  for_each          = { for r in var.ingress_rules : "${r.port}-${r.cidr}" => r }
  security_group_id = aws_security_group.web.id
  from_port         = each.value.port
  to_port           = each.value.port
  ip_protocol       = "tcp"
  cidr_ipv4         = each.value.cidr
}

Common mistakes

  • Dynamic blocks for static configuration that is clearer written out.
  • Nesting dynamic blocks several levels deep.
  • Mixing inline rules and standalone rule resources on the same security group.
  • Forgetting that the iterator name is the block label, not each.

How to answer in the interview

"Some resources have repeating nested blocks, like ingress rules in a security group. A dynamic block generates them from a collection: dynamic ingress with for_each over var.ingress_rules and a content block using ingress.value. That's useful in reusable modules where callers pass a list. But overusing them makes code hard to read and review, so I use them only when needed, and where the provider offers separate resources, such as aws_vpc_security_group_ingress_rule, I prefer those: each rule has its own address and the diffs are much smaller."

Likely follow-up questions

  • Why can one big security group with dynamic rules produce noisy plans? The rules are one set attribute of one resource, so any change shows the set being rewritten.
  • How do you make a nested block optional? for_each = var.enabled ? [1] : [].
  • Can dynamic blocks generate meta-arguments like lifecycle? No, only provider-defined nested blocks.
