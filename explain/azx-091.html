How do you secure an Azure OpenAI or Foundry deployment in an enterprise?

Azure AI & Foundry · concept · levels mid, senior

In one line

Secure Azure OpenAI or Foundry with private endpoints and public access disabled, Entra ID with managed identities and API keys disabled, least-privilege roles such as Cognitive Services OpenAI User, a gateway for auth, quotas and logging, clear data handling commitments, plus content filters, diagnostic logs and Defender for AI.

Detailed explanation

Network: create private endpoints for the resource in a spoke VNet, link the privatelink.openai.azure.com / privatelink.cognitiveservices.azure.com (and services.ai.azure.com for Foundry) private DNS zones, and set public network access to disabled. Applications reach it through VNet integration (App Service, Container Apps, AKS). For Foundry agents, use the network-injected or private networking options so tools and storage stay private too. Control outbound traffic with a firewall.

Identity: applications authenticate with Entra ID tokens via managed identities, and local (API key) authentication is disabled (disableLocalAuth: true). Keys are long-lived bearer secrets that leak into config files and logs, cannot be scoped per app, and do not show who called; disabling them matters even inside a private network, because network position is not identity.

Authorization: Cognitive Services OpenAI User lets an app call models only; Cognitive Services OpenAI Contributor or Foundry project roles manage deployments; owners and admins are few and use PIM.

Gateway: API Management in front centralises authentication (validating client tokens), per-team token quotas, logging of prompts and token usage, semantic caching and regional failover.

Data handling: prompts and completions are not used to train foundation models and are not shared with OpenAI. Microsoft may store data temporarily for abuse monitoring; organisations with sensitive data can apply for modified abuse monitoring. Stored data can be encrypted with customer-managed keys.

Monitoring: keep content filters on, send diagnostic logs to Log Analytics, enable Defender for Cloud threat protection for AI services to alert on jailbreak attempts, credential theft or data leakage patterns, and apply Azure Policy to enforce private endpoints and disabled keys.

How it works

  1. Deploy with public access disabled and private endpoints.
  2. Disable local auth; assign roles to managed identities.
  3. Route apps through APIM with token validation and quotas.
  4. Enable diagnostics, Defender for AI and content filters.
  5. Enforce with Azure Policy across subscriptions.

Example

resource ai 'Microsoft.CognitiveServices/accounts@2024-10-01' = {
  name: 'aoai-prod'
  location: 'swedencentral'
  kind: 'OpenAI'
  sku: { name: 'S0' }
  properties: {
    customSubDomainName: 'aoai-prod'
    publicNetworkAccess: 'Disabled'
    disableLocalAuth: true
  }
}
from azure.identity import DefaultAzureCredential, get_bearer_token_provider
token_provider = get_bearer_token_provider(DefaultAzureCredential(),
                                           "https://cognitiveservices.azure.com/.default")

Common mistakes

  • Private endpoint created but public access still enabled.
  • API keys shared in app settings across environments.
  • Giving apps Contributor so they could also delete deployments.
  • Logging full prompts with personal data without access controls.

How to answer in the interview

"On the network side I use private endpoints, disable public access and reach it from VNet-integrated apps. Apps authenticate with Entra ID and managed identities, and I disable API keys so there's nothing to leak or rotate. Roles are least privilege, like Cognitive Services OpenAI User for calling models. API Management centralises auth, per-team quotas, logging and failover. In the security review I explain that prompts aren't used for training and that modified abuse monitoring exists for sensitive data. Content filters stay on, and I monitor diagnostics and Defender for AI alerts."

Likely follow-up questions

  • Why disable keys inside a private network? Insiders or compromised hosts can still reuse a key; tokens give identity and audit.
  • How do you enforce this at scale? Azure Policy for disableLocalAuth and private endpoints.
  • Which identity for a pipeline? A workload identity federated service connection with only deployment rights.
