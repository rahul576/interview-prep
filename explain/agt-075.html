Do self-reflection and critique loops actually improve agent results?

AI Agents & AIOps · concept · levels mid, senior

In one line

Reflection helps when it is grounded in an external signal such as tests, compilers, validators or retrieved sources; pure self-critique without new information gives limited and inconsistent gains; a separate critic can help; it adds cost and latency, so adopt it only where evaluations show benefit.

Detailed explanation

Reflection, or self-critique, asks the model to review its own output, find mistakes and revise, sometimes over several rounds. It sounds like it should always help, but research and practice show mixed results.

It works best with an external, objective signal. A coding agent that runs the tests, reads the failing assertion and fixes the code improves dramatically, because it is reacting to new information it did not have before. The same applies to compiler errors, schema validation failures, linter output, SQL EXPLAIN results, or checking claims against retrieved sources.

Pure self-critique, simply asking "check your answer and improve it", has limited gains. Models often confirm their own answers, make cosmetic or random changes, or even turn correct answers into wrong ones when pressured to find problems. Gains tend to appear on tasks where checking is easier than generating.

A separate critic can help: different instructions, an explicit checklist of criteria, or a different, stronger model, as in the evaluator-optimizer pattern. The critic should produce specific, actionable feedback and a pass/fail decision, with a maximum number of rounds. Every round adds tokens, cost and latency, so reflection should be introduced only where evaluations show it improves results, and preferably grounded in real checks rather than "think again".

How it works

  1. Generate an initial output.
  2. Run external checks (tests, validators, retrieval) where possible.
  3. If checks fail, feed specific errors back for revision.
  4. Optionally, a critic applies a checklist and returns pass/fail with reasons.
  5. Stop on pass or after N rounds; log iterations.
  6. Compare success and cost with and without the loop on an eval set.

Example

def write_sql(question, max_rounds=3):
    sql = generator(question, schema)
    for _ in range(max_rounds):
        errors = validate_sql(sql, schema)                    # parse, unknown columns, EXPLAIN cost
        errors += critic_checklist(question, sql)             # joins, filters, aggregation, time zone
        if not errors:
            return sql
        sql = generator(question, schema, previous=sql, feedback=errors)
    raise NeedsHumanReview(sql, errors)

Common mistakes

  • Adding "reflect and improve" loops everywhere without measuring.
  • Unlimited rounds that burn tokens.
  • Vague critic prompts producing generic feedback.
  • Using the same model and prompt as both author and judge.

How to answer in the interview

"The evidence is mixed. Reflection helps a lot when there's an external signal: failing tests, compiler errors, a schema validator or sources to check against, because the model reacts to new, objective information, which is why coding agents that run tests do so well. Pure self-critique without new information gives limited gains and can even make correct answers worse. A separate critic with a checklist or a different model helps more. It adds cost and latency, so I only add it where evaluations show it improves results."

Likely follow-up questions

  • Critic for SQL agent? Parse and dry-run checks plus a checklist on joins, filters and aggregations.
  • How many rounds? Usually one or two; returns diminish fast.
  • When skip it? Latency-sensitive, low-risk tasks.
