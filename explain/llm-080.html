A government agency needs an LLM assistant that runs fully on-premises. How would you design it?

LLMOps & RAG · design · levels senior, lead

In one line

Serve evaluated, appropriately licensed open-weight models on local GPUs using Kubernetes with vLLM or TensorRT-LLM behind an internal gateway, bring everything in through an air-gapped, scanned and signed supply chain, provide knowledge through local RAG with permission filtering via the agency's identity provider, audit all access by data classification, and plan capacity while setting honest quality expectations.

Detailed explanation

Models. With no external APIs, choose open-weight models (Llama, Mistral, Qwen, Gemma families and others) through evaluation on the agency's tasks and languages, and check licences (some restrict use or require conditions) and the provenance acceptable to the government (some agencies restrict models by origin). Often one strong general model plus a small fast model for classification and routing, and an embedding and reranker model for RAG.

Serving. GPU servers (on-prem clusters with data-centre GPUs) running Kubernetes with the GPU operator, and a serving engine such as vLLM, TensorRT-LLM (with Triton) or SGLang, offering continuous batching, paged KV cache and quantisation. An internal gateway in front handles authentication, per-team quotas, routing between models, logging and an OpenAI-compatible API for applications.

Supply chain. Air-gapped or tightly controlled: model weights, container images, Python packages and drivers are downloaded on a connected staging network, scanned (malware, vulnerabilities), checksums verified, signed, and transferred through a controlled process into internal registries and mirrors. Use safetensors formats, never pickle-based files with code execution, and disable remote code options.

Knowledge. Local RAG: ingestion of agency document systems, internal search (OpenSearch or similar) with vectors, and permission filtering using the agency's IdP/AD groups, respecting classification levels; some classified data may require separate, isolated deployments.

Security and audit. SSO for users, mTLS between services, encryption at rest, audit logs of prompts, responses and document access according to classification and retention rules, SOC monitoring, and compliance with the relevant national security frameworks.

Capacity and expectations. Size GPUs from expected concurrency, tokens per request and latency SLOs, plus redundancy. Be honest that open models may lag frontier models on some tasks; design use cases accordingly and plan regular model refreshes.

How it works

  1. Requirements: use cases, users, classification levels, languages.
  2. Evaluate and approve models; import via secure supply chain.
  3. Deploy K8s GPU cluster, vLLM, gateway, observability.
  4. Build RAG ingestion with ACLs and classification metadata.
  5. Integrate IdP, audit logging, monitoring.
  6. Load test; pilot; scale; schedule model updates.

Example

# vLLM deployment excerpt (weights from internal registry, no internet)
containers:
  - name: vllm
    image: registry.agency.local/ai/vllm-openai:pinned
    args: ["--model", "/models/llama-3.3-70b-instruct-awq",
           "--tensor-parallel-size", "2",
           "--max-model-len", "32768"]
    env:
      - { name: HF_HUB_OFFLINE, value: "1" }
    resources:
      limits: { nvidia.com/gpu: 2 }
    volumeMounts:
      - { name: models, mountPath: /models, readOnly: true }

Common mistakes

  • Promising frontier-level quality from smaller open models.
  • Pulling models or packages from the internet at runtime.
  • Ignoring licence terms of open-weight models.
  • Building RAG without classification-aware permissions.

How to answer in the interview

"Without hosted APIs, I'd evaluate open-weight models like Llama, Mistral, Qwen or Gemma on the agency's tasks and languages and check their licences. They'd run on local GPUs in a Kubernetes cluster with vLLM or TensorRT-LLM behind an internal gateway for auth, quotas and logging. Everything, weights, images and packages, comes through an air-gapped supply chain where it's scanned, signed and mirrored internally. Knowledge comes from local RAG over agency documents with permission filtering from their identity provider and classification levels. All usage is audited, capacity is sized from expected concurrency, and I'd be honest about where open models lag frontier ones."

Likely follow-up questions

  • Updating models air-gapped? Scheduled evaluation and import process through the same scanned, signed pipeline.
  • Multiple classification levels? Separate deployments or strict isolation per level.
  • High availability? Multiple replicas across nodes, spare GPU capacity, tested failover.
