How does Spring's proxy-based transaction management work?

Spring Framework · concept · levels mid, senior

In one line

A TransactionInterceptor in an AOP proxy reads the method's transaction attributes, calls PlatformTransactionManager.getTransaction() which joins, suspends or creates a transaction per propagation, binds resources to the thread via TransactionSynchronizationManager, and commits or rolls back after the call; hence self-invocation, private methods and other threads are not covered.

Detailed explanation

Proxy creation. @EnableTransactionManagement (automatic in Spring Boot) registers an advisor made of a TransactionAttributeSource (which reads @Transactional annotations) and a TransactionInterceptor. The auto-proxy creator wraps every bean with matching methods in a proxy, CGLIB by default in Boot.

Starting. On each call, the interceptor looks up the TransactionAttribute for the method (propagation, isolation, timeout, readOnly, rollback rules, which manager). It calls getTransaction(definition) on the PlatformTransactionManager. The manager checks the thread for an existing transaction. Depending on propagation it joins it (REQUIRED, SUPPORTS, MANDATORY), suspends it by unbinding its resources and starts a new one (REQUIRES_NEW, NOT_SUPPORTED), creates a savepoint (NESTED) or throws. For a new transaction, JpaTransactionManager creates an EntityManager, begins the transaction, obtains the JDBC connection, applies isolation and read-only flags, and binds the EntityManagerHolder and ConnectionHolder to the thread with TransactionSynchronizationManager, a set of ThreadLocal maps.

Participating. Spring Data repositories use a shared EntityManager proxy, and JdbcTemplate uses DataSourceUtils.getConnection(). Both look up the thread-bound resource first, so they automatically participate without any parameters.

Finishing. After the target returns, the interceptor calls commit(); if a matching exception was thrown, rollback() (or marks rollback-only if it is just a participant). Registered synchronizations run (beforeCommit, afterCommit, afterCompletion, used by @TransactionalEventListener), resources are unbound, and a suspended outer transaction is resumed.

Pitfalls. Because the transaction lives in the proxy and the thread: this.method() calls skip the interceptor; private methods can't be proxied; and work on another thread, for example @Async, CompletableFuture.supplyAsync, a parallel stream or a reactive scheduler, finds no thread-bound resources and runs in its own (or no) transaction.

How it works

  1. Caller → proxy → TransactionInterceptor.
  2. Attributes resolved; getTransaction() joins, suspends or begins.
  3. Resources bound to the current thread.
  4. Target method runs; repositories use the bound resources.
  5. Commit or rollback; synchronizations fire; resources unbound; outer resumed.

Example

@Transactional
public void recalculate(List<Long> ids) {
    ids.parallelStream()                       // ForkJoinPool worker threads:
       .forEach(id -> repo.updateScore(id));   // NOT in this transaction
}

@Transactional
public void recalculateSafely(List<Long> ids) {
    ids.forEach(id -> repo.updateScore(id));   // same thread, same transaction
}
TransactionSynchronizationManager (per thread)
  resources: { DataSource -> ConnectionHolder, EMF -> EntityManagerHolder }
  synchronizations: [ TransactionalEventListener adapters ... ]
  currentTransactionReadOnly / isolation / name

Common mistakes

  • Parallel streams or @Async inside a transactional method.
  • Self-invocation or private methods.
  • Mixing two transaction managers without specifying which one.
  • Expecting ThreadLocal binding to work in reactive code (use ReactiveTransactionManager).

How to answer in the interview

"For @Transactional beans Spring creates a proxy with a TransactionInterceptor. On each call it reads the attributes and calls getTransaction on the PlatformTransactionManager, which, depending on propagation, joins the current transaction, suspends it or starts a new one, opening a connection or EntityManager and binding it to the thread through TransactionSynchronizationManager. Repositories and JdbcTemplate find that thread-bound resource and participate automatically. After the method returns or throws, the interceptor commits or rolls back and unbinds. So self-invocation and private methods aren't intercepted, and work on another thread, like @Async or a parallel stream, doesn't join the transaction."

Likely follow-up questions

  • Why doesn't a parallel stream share the transaction? Worker threads have no thread-bound connection.
  • How do reactive transactions work? ReactiveTransactionManager stores state in the Reactor Context.
  • Two transaction managers? @Transactional("ordersTxManager") or transactionManager attribute.
