How do Ansible templates work?

Configuration Management · concept · levels entry

In one line

The template module renders a Jinja2 file on the control node with each host's variables and facts, copies the result to the host, reports changed only when the output differs (so it can notify a handler), and can validate the file before replacing it.

Detailed explanation

Configuration files usually differ per host or environment: server names, ports, memory sizes, lists of backends. Instead of keeping many copies, you keep one Jinja2 template, typically templates/nginx.conf.j2 in a role, and let Ansible render it. Rendering happens on the control node, using all variables available for that host: inventory and group_vars, role defaults, facts, registered results and magic variables like inventory_hostname, groups and hostvars.

Templates support expressions ({{ nginx_port }}), filters ({{ name | upper }}, {{ value | default('x') }}, {{ list | join(',') }}), loops ({% for host in groups['app'] %}), conditionals ({% if enable_tls %}) and comments ({# ... #}). A common pattern is generating an upstream block listing every host in a group using hostvars to read their IP addresses from facts.

The module compares the rendered content with the file on the target. If they are the same it reports ok; if not, it writes the file and reports changed, which is exactly when it should notify a handler to reload the service. Useful options: owner, group, mode, backup: true to keep the previous version, and validate, which runs a command against the temporary file (%s) and only replaces the real file if the command succeeds, for example nginx -t -c %s or visudo -cf %s. Adding {{ ansible_managed }} at the top warns humans not to edit the file by hand.

How it works

  1. Ansible collects variables and facts for the host.
  2. It renders the .j2 template on the control node.
  3. It transfers the result to a temporary file on the host.
  4. If validate is set, it runs the check command.
  5. It replaces the destination only if content differs, then reports changed and notifies handlers.

Example

# {{ ansible_managed }}
upstream app {
{% for host in groups['app'] %}
    server {{ hostvars[host]['ansible_facts']['default_ipv4']['address'] }}:{{ app_port }};
{% endfor %}
}
server {
    listen {{ nginx_port }};
    server_name {{ server_name }};
{% if enable_tls %}
    ssl_certificate /etc/ssl/{{ server_name }}.crt;
{% endif %}
}
- name: Render nginx site
  ansible.builtin.template:
    src: site.conf.j2
    dest: /etc/nginx/conf.d/site.conf
    mode: "0644"
    validate: nginx -t -c /etc/nginx/nginx.conf -p /etc/nginx/ -g 'include %s;'
  notify: Reload nginx

Common mistakes

  • Referencing facts of hosts that were not gathered in this run (hostvars empty).
  • Restarting the service unconditionally instead of via handlers.
  • No validation, so a broken config takes the service down on reload.
  • Complex logic inside templates that belongs in variables or filters.

How to answer in the interview

"The template module takes a Jinja2 file, usually from the role's templates folder, renders it on the control node with that host's variables and facts, and copies the result to the target. So one nginx.conf.j2 produces the right server names, ports and upstreams for every environment. Inside I can use loops, for example one upstream line per host in the app group via hostvars, plus conditionals and filters. The task only reports changed when the rendered output differs, which is when it notifies a handler to reload. And the validate option, like nginx -t, checks the new file before it replaces the old one."

Likely follow-up questions

  • How would you generate a config listing all hosts in the database group? Loop over groups['db'] and read each host's address from hostvars.
  • template vs copy? copy transfers files as-is; template renders Jinja2 first.
  • Why might hostvars facts be missing? Facts for those hosts weren't gathered; gather them or use fact caching.
