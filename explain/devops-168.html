Developers complain that getting a new service into production takes three weeks. How do you fix it?

Platform Engineering · scenario · levels lead

In one line

Map the value stream to find where the three weeks are waiting, then remove the waits with a self-service golden path, automated environments and access, and policy as code instead of manual tickets, and measure lead time before and after.

Detailed explanation

When it takes three weeks to get a new service live, the actual work is usually a few hours. The rest is queue time: waiting for a repository, a pipeline, a DNS entry, a firewall rule, database credentials, a security review or a change advisory board. Guessing which step is slow leads to automating the wrong thing, so start with evidence.

Value stream mapping with a team that recently went through it lists every step from "we need a new service" to "serving production traffic", noting process time versus wait time, the team responsible and the hand-off mechanism. Often 90% or more is waiting, and much of it is tickets between four or five teams.

The fix is to turn hand-offs into self-service: a golden path template that creates the repo, CI/CD pipeline, container registry, Kubernetes namespace, infrastructure via Terraform modules, DNS, certificates, dashboards and alerts in one go. Access and secrets come from group membership and workload identity rather than tickets. Manual approvals are replaced by automated policy-as-code guardrails (OPA, Kyverno, Checkov, security scanning in the pipeline), keeping human review only for genuinely risky changes, such as new public endpoints or new categories of personal data. This keeps security and compliance happy because controls are enforced every time, with an audit trail.

How it works

  1. Value stream mapping workshop with one or two recent teams.
  2. Rank steps by wait time; pick the top three.
  3. Agree target design with the owning teams (network, security, DBAs).
  4. Build the golden path template and automate provisioning.
  5. Replace approvals with policy checks; define the exceptions that still need review.
  6. Measure lead time for new services and adoption; iterate.

Example

Before (15 working days)                  After (target < 1 day)
Repo request ticket        2 d wait  ->   Template creates repo          2 min
Pipeline setup by DevOps   3 d wait  ->   Pipeline from template         auto
Namespace + quota ticket   2 d wait  ->   GitOps tenant PR, auto-merged  10 min
Firewall/DNS tickets       4 d wait  ->   Terraform modules + policy     30 min
Security review meeting    4 d wait  ->   Pipeline scans + policy gate   auto,
                                          manual review only if flagged

Common mistakes

  • Automating without first measuring where the time goes.
  • Building the template alone without the network and security teams.
  • Keeping manual approvals "just in case" after adding automated checks.
  • Making the golden path mandatory rather than better.
  • Not measuring before, so improvement cannot be shown.

How to answer in the interview

"I'd start by mapping the value stream with a team that recently did it: every step from repo creation to production, and how long each one waits. Usually most of the three weeks is waiting on tickets for repos, pipelines, DNS, firewall rules, database access and security reviews. Then I'd remove the waits: a self-service golden path template that creates the repo, pipeline, infrastructure, namespace and observability automatically, access through groups and workload identity, and policy-as-code guardrails instead of manual approvals, keeping human review for genuinely risky changes. I'd measure lead time for a new service before and after, aiming for under a day."

Likely follow-up questions

  • Security insists on manually reviewing every service? Co-design the automated controls with them, start with a pilot and keep review for flagged risk.
  • How do you get teams to adopt it? Make it faster than the old way and support early adopters closely.
  • What if teams need something the template lacks? Escape hatches and contribution to the template, inner-source style.
