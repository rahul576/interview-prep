What is the difference between a servlet Filter and a Spring HandlerInterceptor?

Spring Framework · concept · levels mid, senior

In one line

A servlet Filter works at the container level, before the DispatcherServlet, for every request, and can wrap request and response; a HandlerInterceptor is Spring MVC-specific, runs after the handler is chosen so it knows the controller method, and offers preHandle, postHandle and afterCompletion.

Detailed explanation

Filters are part of the Jakarta Servlet specification. They form a chain around the whole servlet, so they see every request, including static resources, error dispatches and requests that never reach Spring MVC. A filter receives ServletRequest and ServletResponse and decides whether to call chain.doFilter. Crucially it can replace them with wrappers, for example ContentCachingRequestWrapper to read the body for logging, a response wrapper to compress output, or adding headers. Typical uses: security (Spring Security is a filter chain), CORS, request and response logging, correlation ids and MDC, compression, rate limiting, encoding. In Spring Boot, extend OncePerRequestFilter and register it as a bean or through FilterRegistrationBean to set order and URL patterns.

Interceptors belong to Spring MVC. They are registered via WebMvcConfigurer.addInterceptors and run inside the DispatcherServlet once the HandlerMapping has selected a handler. They therefore receive the handler object, usually a HandlerMethod, so you can read the controller class, method and its annotations. Hooks:

  • preHandle: before the controller; return false to stop.
  • postHandle: after the controller, before view rendering (limited for @ResponseBody, as the body is already written).
  • afterCompletion: always at the end, with any exception.

Typical uses: checks based on custom annotations on controller methods, per-handler metrics, locale or tenant resolution, adding model attributes for views. Interceptors cannot swap the request object for the chain, so body caching or wrapping belongs in a filter. In WebFlux the equivalent is WebFilter.

How it works

  1. Container passes the request through filters in order.
  2. The last filter calls the DispatcherServlet.
  3. HandlerMapping chooses the handler and its interceptors.
  4. preHandle, controller, postHandle, afterCompletion run inside the dispatcher.
  5. Control returns outward through the filters, which can post-process the response.

Example

@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
class CorrelationIdFilter extends OncePerRequestFilter {
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String id = Optional.ofNullable(req.getHeader("X-Correlation-Id")).orElse(UUID.randomUUID().toString());
        MDC.put("correlationId", id);
        res.setHeader("X-Correlation-Id", id);
        try { chain.doFilter(req, res); } finally { MDC.remove("correlationId"); }
    }
}

@Component
class FeatureFlagInterceptor implements HandlerInterceptor {
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) throws Exception {
        if (handler instanceof HandlerMethod hm && hm.hasMethodAnnotation(BetaFeature.class) && !flags.betaOn()) {
            res.sendError(404);
            return false;
        }
        return true;
    }
}

Common mistakes

  • Implementing authentication in an interceptor alongside Spring Security.
  • Reading the body in an interceptor and breaking @RequestBody later.
  • Using a plain Filter that runs twice on error dispatches instead of OncePerRequestFilter.
  • Forgetting filter order relative to the security chain.

How to answer in the interview

"A servlet Filter works at the container level, before the DispatcherServlet, for every request, even static resources and ones Spring MVC never handles. It can wrap the request or response, for example to cache the body for logging, so I use filters for security, CORS, compression, correlation ids and request logging; Spring Security itself is a filter chain. A HandlerInterceptor is Spring MVC-specific and runs after the handler has been chosen, so it knows which controller method will run and can read its annotations. It has preHandle, postHandle and afterCompletion, which I use for per-handler checks, locale or metrics."

Likely follow-up questions

  • Why can an interceptor not easily read the request body twice? The input stream is consumed once; only a filter can wrap it in a caching wrapper earlier.
  • What is OncePerRequestFilter? A base class guaranteeing one execution per request, even across forwards and error dispatches.
  • WebFlux equivalent? WebFilter and HandlerFilterFunction.
