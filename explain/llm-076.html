How does tool calling work at the message level in LLM APIs?

LLMOps & RAG · concept · levels mid, senior

In one line

The request includes tool definitions (name, description, JSON Schema parameters); the model replies with a tool call (name, JSON arguments, call ID) and a stop reason indicating tool use; the application executes the tool (the model never runs code), returns a tool result message linked to the call ID, and loops until a final answer, with support for parallel calls, tool choice options and mandatory argument validation.

Detailed explanation

Tool calling (function calling) is a message protocol, not code execution by the model.

1. Request. The application sends the conversation plus a tools array. Each tool has a name, a description (which the model relies on to decide when to use it) and a JSON Schema for its parameters.

2. Model decision. The model may answer in text or emit one or more tool calls. In Anthropic's Messages API these are tool_use content blocks with id, name and input, with stop_reason: "tool_use"; in OpenAI's Chat Completions they are tool_calls with id, function.name and function.arguments (a JSON string), with finish_reason: "tool_calls". The Responses API uses function_call output items. Formats differ, the concept is the same.

3. Execution by the application. Your code parses and validates the arguments against the schema and business rules, checks the user's permissions, executes the real function (database query, HTTP call) with its own credentials, and handles errors.

4. Tool result. The output is appended as a tool result message (tool_result block with tool_use_id, or a role: "tool" message with tool_call_id), together with the assistant's tool call message, so the model can match results to calls. Errors are returned as results too, so the model can correct itself.

5. Loop. The model continues: more tool calls or a final answer. The application caps the number of iterations.

Options. Parallel tool calls in one turn (execute concurrently, return all results), tool choice settings (auto, required/any, a specific tool, none), and strict schema modes in some APIs that constrain arguments to the schema.

Security. Arguments are model output, therefore untrusted; models can produce wrong IDs, or be steered by prompt injection into harmful values. Validate, authorise and require confirmation for impactful actions.

How it works

  1. Send messages + tool definitions.
  2. Receive tool call(s) with IDs and arguments.
  3. Validate, authorise, execute.
  4. Append assistant tool-call message and tool results.
  5. Call the model again; repeat until final text or step limit.

Example

{"role": "assistant", "content": [
  {"type": "tool_use", "id": "toolu_01", "name": "get_order_status",
   "input": {"order_id": "A-77812"}}
]}

{"role": "user", "content": [
  {"type": "tool_result", "tool_use_id": "toolu_01",
   "content": "{\"status\": \"shipped\", \"carrier\": \"DHL\", \"eta\": \"2026-11-24\"}"}
]}

Common mistakes

  • Trusting model-provided user IDs or skipping permission checks.
  • Vague tool descriptions, causing wrong tool choice.
  • Returning huge raw results that blow the context.
  • No iteration limit in the loop.

How to answer in the interview

"The request includes tool definitions: a name, a description and a JSON schema for parameters. If the model decides it needs a tool, it returns a tool call instead of text, with the tool name, JSON arguments and an ID, and the stop reason says tool use. The model never executes anything; my application validates the arguments, checks permissions, runs the real function with its own credentials, and sends the output back as a tool result linked to the call ID. The model continues until it gives a final answer. APIs support parallel calls and forcing or disabling tools, and I always validate arguments because they're untrusted model output."

Likely follow-up questions

  • Invalid arguments? Return a descriptive error as the tool result so the model can retry; cap retries.
  • Long-running tools? Return a job ID and a status tool, or run asynchronously.
  • How many tools? Keep the set focused; use tool search or routing for large catalogues.
