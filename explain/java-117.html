What is structured concurrency in modern Java and why does it matter?

Concurrency · concept · levels senior, lead

In one line

Structured concurrency treats a group of related concurrent subtasks as one unit of work bounded by a code block: with StructuredTaskScope you fork subtasks, join, and on failure the scope cancels siblings and propagates the error, so no thread outlives its parent; it pairs with virtual threads and is still a preview API (reworked in Java 25).

Detailed explanation

With an ExecutorService or CompletableFuture, the relationship between a request and the tasks it spawns is only in the programmer's head. If one subtask fails, the others keep running and waste resources; if the parent is cancelled, children may leak; thread dumps show unrelated threads with no parent-child structure. This is "unstructured" concurrency, the threading equivalent of goto.

Structured concurrency applies the block structure of sequential code to threads: subtasks start inside a scope and must finish before the scope closes. The benefits:

  • Error propagation: if a subtask fails, the scope can cancel (interrupt) the remaining ones and rethrow.
  • Cancellation: if the parent is interrupted, all children are cancelled.
  • No leaks: try-with-resources guarantees no subtask outlives the block.
  • Observability: JSON thread dumps show the task hierarchy.
  • Readability: the code looks like sequential code.

It is designed for virtual threads: each fork starts a new virtual thread by default, so forking per subtask is cheap.

Status. It has been a preview API since Java 21 (JEP 453), repeatedly refined. In Java 25 (JEP 505) the API changed: instead of subclassing ShutdownOnFailure/ShutdownOnSuccess, you call StructuredTaskScope.open() with an optional Joiner policy, for example Joiner.awaitAllSuccessfulOrThrow() (default), anySuccessfulResultOrThrow() or allSuccessfulOrThrow(). It still requires --enable-preview, and the API may change before finalisation. It works together with ScopedValue, whose bindings are inherited by forked subtasks.

How it works

  1. Open a scope in try-with-resources.
  2. fork each subtask; each runs in its own virtual thread.
  3. join() waits according to the Joiner policy.
  4. On failure, remaining subtasks are cancelled and join throws.
  5. Read results from the Subtask handles; closing the scope guarantees all threads finished.

Example

// Java 25 preview API: javac --release 25 --enable-preview
Dashboard load(String id) throws InterruptedException {
    try (var scope = StructuredTaskScope.open()) {        // default: all must succeed
        Subtask<User> user = scope.fork(() -> userClient.find(id));
        Subtask<List<Order>> orders = scope.fork(() -> orderClient.byUser(id));

        scope.join();          // throws FailedException if any subtask failed;
                               // the other subtask is cancelled automatically
        return new Dashboard(user.get(), orders.get());
    }
}

Common mistakes

  • Calling Subtask.get() before join().
  • Assuming the API is final; it needs --enable-preview and may change.
  • Quoting the Java 21 ShutdownOnFailure API as current.
  • Using it for CPU-heavy parallelism instead of I/O fan-out.

How to answer in the interview

"Structured concurrency treats a group of related tasks running in different threads as a single unit of work whose lifetime is bounded by a code block. With StructuredTaskScope I fork subtasks, for example fetching a user and their orders in parallel, then join; if one fails, the scope cancels the others and propagates the error, and no thread outlives the block. It makes concurrent code read like sequential code and fits naturally with virtual threads. It's still a preview API: it's been previewing since Java 21, and Java 25 reworked it around StructuredTaskScope.open and Joiner policies, so it needs --enable-preview."

Likely follow-up questions

  • How is it different from CompletableFuture.allOf? allOf doesn't cancel siblings on failure or bound task lifetimes.
  • What does a Joiner do? Defines the completion policy, such as all must succeed or first success wins.
  • How does context flow? ScopedValue bindings are inherited by forked subtasks.
