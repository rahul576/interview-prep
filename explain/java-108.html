What are access modifiers in Java and what does each allow?

Core Java & OOP · concept · levels entry

In one line

Java has four access levels: public (everywhere), protected (same package plus subclasses), package-private (no modifier, same package only) and private (only inside the declaring class).

Detailed explanation

Access modifiers are Java's main tool for encapsulation. They decide which other code can see a class, field, constructor or method, and therefore which parts of your code are a public contract and which are free to change.

  • public: visible to any code that can see the enclosing class. Use it for the API you deliberately support.
  • protected: visible inside the same package and to subclasses in other packages. A subtle point: a subclass in another package can only access the protected member through its own type (or a subtype), not through an arbitrary instance of the parent.
  • package-private (default, no keyword): visible only inside the same package. It is underrated; it is a great way to keep helper classes and test seams internal to a feature package.
  • private: visible only inside the top-level class that encloses the declaration. Nested classes in the same top-level class can see each other's private members.

Top-level classes can only be public or package-private. Members of interfaces are implicitly public (Java 9+ also allows private interface methods for sharing code between default methods). Since Java 9, the module system adds a further layer: even a public class is not accessible outside its module unless its package is exported in module-info.java.

The rule of thumb is least privilege: make fields private, expose behaviour through methods, and widen access only when there is a real need.

How it works

  1. The compiler checks every member access against the declared modifier and the location of the caller.
  2. private: allowed only within the same top-level class body.
  3. package-private: allowed if the caller is in the same package (same name and same class loader at runtime).
  4. protected: package rule plus subclass access through the subclass's own references.
  5. public: allowed everywhere, subject to module exports.
  6. The JVM re-checks access at link time, and reflection respects it unless setAccessible(true) is permitted.

Example

package com.shop.billing;

public class Invoice {
    private final List<Line> lines = new ArrayList<>();   // internal state
    protected BigDecimal taxRate() { return new BigDecimal("0.18"); } // hook for subclasses
    void recalculate() { /* package-private: used by BillingService only */ }
    public BigDecimal total() { /* public contract */ return BigDecimal.ZERO; }
}

Common mistakes

  • Thinking protected means "subclasses only"; it also opens access to the whole package.
  • Making fields public or protected "for convenience", which freezes the internal representation.
  • Forgetting that package-private exists and making helpers public.
  • Assuming a public class is usable outside its module without an export.

How to answer in the interview

"Java has four levels. Public is visible everywhere, protected is visible in the same package and to subclasses even in other packages, default or package-private is visible only inside the package, and private only inside the class. I follow least privilege: private fields, a small public API, package-private for internal helpers, and protected only for deliberate extension points. Since Java 9, modules add another boundary, because a package must be exported before its public types are usable by other modules."

Likely follow-up questions

  • Can a top-level class be private or protected? No; only public or package-private. Nested classes can use all four.
  • Can an overriding method reduce visibility? No; it can keep or widen it, never narrow it.
  • Does private stop reflection? Not fully; setAccessible can bypass it, though modules restrict that.
