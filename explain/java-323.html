Compare offset pagination and cursor (keyset) pagination.

REST & API Design · concept · levels mid, senior

In one line

Offset pagination (LIMIT/OFFSET, page numbers) is simple and allows jumping to any page, but is slow for deep pages and unstable under inserts; cursor/keyset pagination (WHERE (sort_key, id) > last_seen) is fast at any depth and stable, but allows no random page jumps and needs a unique, indexed sort key.

Detailed explanation

Offset pagination. The client asks for ?page=500&size=20, which becomes ORDER BY created_at DESC LIMIT 20 OFFSET 10000. Easy to implement (Spring Data Pageable does it), and UIs can show "page 1 2 3 ... 50". Problems:

  • Performance: the database must produce and discard the first 10,000 rows. Deep pages become slower and slower.
  • Consistency: if a new row is inserted at the top while a user moves from page 1 to page 2, everything shifts by one, so an item appears twice; a deletion causes one to be skipped.
  • Total count queries (COUNT(*)) for "page X of Y" are expensive on big tables.

Keyset (cursor) pagination. Instead of a position, remember the last row seen. The next page query is: WHERE (created_at, id) < (:lastCreatedAt, :lastId) ORDER BY created_at DESC, id DESC LIMIT 20. With an index on (created_at, id), the database seeks directly to the position, so page 1 and page 10,000 cost the same. New inserts do not shift results, so there are no duplicates or gaps. The API returns an opaque cursor (often Base64 of the sort values, optionally signed) and the client passes it back: ?after=eyJjIjoi....

Trade-offs: you cannot jump to page 37; navigation is next/previous. The sort must be on columns with a unique tie-breaker (id), otherwise rows with equal timestamps can be lost. Changing sort order means a different cursor type. Spring Data supports this with ScrollPosition/Window (Spring Data 3.1+).

When to use which. Offset for small datasets and admin screens needing page numbers; keyset for feeds, infinite scroll, public APIs, large tables and data exports.

How it works

  1. Offset: compute OFFSET = page × size; DB skips rows.
  2. Keyset: client sends cursor = last row's sort values.
  3. Query uses a range condition on an index.
  4. Response includes next cursor; absent cursor means last page.

Example

-- offset
SELECT * FROM orders ORDER BY created_at DESC, id DESC LIMIT 20 OFFSET 10000;

-- keyset
SELECT * FROM orders
WHERE (created_at, id) < ('2026-11-01 10:15:00', 98231)
ORDER BY created_at DESC, id DESC
LIMIT 20;

Common mistakes

  • Keyset on a non-unique column without a tie-breaker.
  • Missing composite index, so keyset is still slow.
  • Exposing raw, tamperable cursors where that matters.
  • Running COUNT(*) on every request of a huge table.

How to answer in the interview

"Offset pagination turns a page number into LIMIT and OFFSET. It's simple and lets you jump to any page, but the database still has to walk past all the skipped rows, so deep pages are slow, and inserts between requests cause duplicates or skipped items. Keyset or cursor pagination remembers the last seen sort key and queries WHERE created_at and id are less than the cursor, using a composite index, so it's fast at any depth and stable under inserts, but you can't jump to an arbitrary page. It needs a unique tie-breaker like id. I use cursors for feeds and large public APIs, offsets for small admin lists."

Likely follow-up questions

  • How do you encode a cursor so clients cannot tamper with it? Base64 the sort values and sign them with an HMAC, or encrypt them.
  • How do you support previous page with keyset? Reverse the comparison and order, then reverse the results.
  • How does Spring Data support keyset? ScrollPosition.keyset() with Window<T> results.
