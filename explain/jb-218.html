How do microservices communicate with each other?

Microservices · concept · levels mid, senior

In one line

Microservices talk synchronously via REST or gRPC (caller waits) or asynchronously via events and commands on Kafka or RabbitMQ, found through service discovery and load balancing behind an API gateway, with timeouts, retries, circuit breakers, explicit contracts and propagated auth and trace context.

Detailed explanation

Synchronous request-response. REST over HTTP with JSON is the most common style: universal, easy to debug, described with OpenAPI. In Spring you call it with RestClient, WebClient, declarative HTTP interfaces (@HttpExchange) or OpenFeign. gRPC uses HTTP/2 and Protocol Buffers: compact binary messages, generated typed clients, streaming and deadlines, which makes it attractive for high-volume internal calls. The caller waits, so it is simple but couples availability and latency.

Asynchronous messaging. A service publishes events ("OrderPlaced", something happened) or commands ("SendInvoice", please do something) to a broker. Kafka suits event streams with retention and replay; RabbitMQ suits task queues and routing; cloud options include SQS/SNS, Azure Service Bus and Google Pub/Sub. Consumers process independently, which decouples services and absorbs spikes, but introduces eventual consistency, duplicates and ordering concerns. Events should be published reliably with the outbox pattern and consumed idempotently.

Finding each other. Services call logical names, not IPs. On Kubernetes, Services and DNS provide discovery and load balancing; elsewhere, registries like Eureka or Consul with client-side load balancing. External traffic enters through an API gateway; a service mesh (Istio, Linkerd) can add mTLS, retries and telemetry to east-west calls.

Cross-cutting requirements. Every synchronous call needs timeouts, limited retries with backoff for idempotent operations, circuit breakers and bulkheads (Resilience4j). Contracts are explicit and versioned: OpenAPI, protobuf files, or event schemas in a schema registry, verified by contract tests. Each call propagates the user or service token (OAuth2 token relay or client credentials) and the W3C trace context, so security and tracing work end to end.

How it works

  1. Decide per interaction: need an answer now (sync) or react later (async)?
  2. Sync: resolve name via discovery, call with timeout and resilience policies.
  3. Async: write event to outbox, relay to broker, consumers react.
  4. Propagate auth token and traceparent header in both cases.
  5. Verify contracts in CI.

Example

// Declarative HTTP interface (Spring 6+)
@HttpExchange("/customers")
interface CustomerClient {
    @GetExchange("/{id}") Customer get(@PathVariable String id);
}

@Bean
CustomerClient customerClient(RestClient.Builder builder) {
    RestClient rc = builder.baseUrl("http://customer-service").build(); // K8s DNS name
    return HttpServiceProxyFactory.builderFor(RestClientAdapter.create(rc))
            .build().createClient(CustomerClient.class);
}

// Async: publish an event others react to
kafkaTemplate.send("orders.events", orderId, new OrderPlaced(orderId, total));

Common mistakes

  • Long synchronous call chains for one user action.
  • No timeouts or circuit breakers.
  • Events without schemas or versioning.
  • Dropping trace context and auth when crossing async boundaries.

How to answer in the interview

"There are two styles. Synchronous request-response with REST, using RestClient or Feign, or gRPC for efficient internal calls; it is simple but the caller depends on the callee being up. And asynchronous messaging with events or commands on Kafka or RabbitMQ, which decouples services and absorbs spikes, at the cost of eventual consistency. Services find each other through Kubernetes Services or Eureka, with an API gateway at the edge. Every sync call gets timeouts, retries and circuit breakers; contracts are explicit with OpenAPI or a schema registry; and the auth token and trace context are propagated on every hop."

Likely follow-up questions

  • REST call or event? Event if the caller does not need the result and others merely react; REST if a response is needed now.
  • When choose gRPC over REST? High-volume internal calls, strict typed contracts, streaming.
  • What does a service mesh add? mTLS, traffic policies, retries and telemetry without application code.
