How do you expose applications from AKS, and what ingress options exist?

Azure Kubernetes (AKS) · concept · levels mid, senior

In one line

Expose AKS apps with a Service of type LoadBalancer (public or internal Azure Load Balancer) for layer 4, and for HTTP use an ingress or Gateway API controller: the application routing add-on (managed NGINX) or Application Gateway for Containers with WAF; optionally put Front Door in front, and manage TLS with cert-manager or Key Vault.

Detailed explanation

Service type LoadBalancer: the Azure cloud provider creates a rule on the cluster's Azure Load Balancer (Standard SKU) with a public IP, or an internal load balancer with a private IP when you add the annotation service.beta.kubernetes.io/azure-load-balancer-internal: "true". This is layer 4, one IP per service, suitable for TCP/UDP or simple exposure. ClusterIP services remain internal to the cluster.

Ingress controllers provide layer 7 routing (host and path), TLS termination and a single entry point for many services:

  • The application routing add-on is a Microsoft-managed NGINX ingress controller integrated with Azure DNS and Key Vault certificates. Note that the upstream community ingress-nginx project announced its retirement, so check the add-on's current support status and roadmap, which moves towards Gateway API.
  • Application Gateway for Containers (AGC) is the successor to AGIC. It is an Azure-managed layer 7 load balancer outside the cluster, configured from Kubernetes using the Gateway API or Ingress resources, with traffic splitting, header routing and WAF integration.
  • Self-managed controllers such as Traefik, Envoy Gateway or Istio's gateway are also options.

The Gateway API (Gateway, HTTPRoute resources) is the modern Kubernetes standard, more expressive than Ingress and role-oriented.

For global traffic, Azure Front Door can sit in front of regional ingress, adding WAF, caching and multi-region failover, ideally using Private Link to an internal load balancer.

TLS: use cert-manager with Let's Encrypt or an internal CA, or certificates stored in Key Vault and synced via the add-on or the Secrets Store CSI driver.

How it works

  1. Deploy the app with a ClusterIP Service.
  2. Install or enable an ingress or Gateway API controller.
  3. Controller receives a public or internal IP from Azure.
  4. Define Ingress or HTTPRoute rules for hosts and paths.
  5. Attach TLS certificates from cert-manager or Key Vault.
  6. Optionally front with Front Door and WAF; restrict origin access.

Example

Internal-only service and an HTTPRoute via Gateway API:

apiVersion: v1
kind: Service
metadata:
  name: internal-api
  annotations:
    service.beta.kubernetes.io/azure-load-balancer-internal: "true"
spec:
  type: LoadBalancer
  selector: { app: internal-api }
  ports: [{ port: 443, targetPort: 8443 }]
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: shop, namespace: shop }
spec:
  parentRefs: [{ name: public-gateway, namespace: infra }]
  hostnames: ["shop.example.com"]
  rules:
    - matches: [{ path: { type: PathPrefix, value: /api } }]
      backendRefs: [{ name: shop-api, port: 80 }]

Common mistakes

  • One public LoadBalancer service per microservice, wasting IPs and lacking WAF.
  • Exposing internal APIs publicly instead of using internal load balancers.
  • Manually managed certificates that expire.
  • Not locking origins so traffic can bypass Front Door.
  • Ignoring the lifecycle status of the chosen ingress controller.

How to answer in the interview

"A Service of type LoadBalancer creates a rule on the Azure Load Balancer, public by default or internal with an annotation for private apps. For HTTP traffic I use an ingress or Gateway API controller: the managed application routing add-on based on NGINX, or Application Gateway for Containers, the successor to AGIC, which adds layer 7 routing and WAF and supports the Gateway API, which I see as the future direction. For global apps, Front Door sits in front with WAF and failover, connected privately to the cluster. TLS certificates come from cert-manager with Let's Encrypt or from Key Vault through the add-on integration."

Likely follow-up questions

  • How would you restrict an internal API to only the corporate network? Internal load balancer or private ingress, reachable over ExpressRoute or VPN, plus NSGs.
  • Ingress versus Gateway API? Gateway API is more expressive and role-oriented; Ingress is simpler and older.
  • How do you do canary releases at the ingress? Weighted backends in HTTPRoute or a service mesh.
