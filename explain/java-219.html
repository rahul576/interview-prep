What are the states of a Java thread?

Concurrency · concept · levels entry

In one line

Thread.State has six values: NEW, RUNNABLE (running or ready), BLOCKED (waiting for a monitor), WAITING (indefinite wait/join/park), TIMED_WAITING (sleep or timed waits) and TERMINATED; these appear in thread dumps and are how you diagnose contention and hangs.

Detailed explanation

  • NEW: the Thread object exists but start() has not been called.
  • RUNNABLE: after start(). The JVM does not distinguish "running on a CPU" from "ready and waiting for the OS scheduler"; both are RUNNABLE. Importantly, a platform thread blocked in native I/O (reading a socket) is also reported as RUNNABLE, because from the JVM's view it is executing native code.
  • BLOCKED: waiting to acquire a monitor to enter a synchronized block or method, or to re-enter one after wait(). Only intrinsic locks produce BLOCKED.
  • WAITING: waiting indefinitely for another thread: Object.wait() without timeout, Thread.join() without timeout, or LockSupport.park(). Since ReentrantLock, CountDownLatch, BlockingQueue.take and friends use park, a thread waiting on them shows WAITING (parking), not BLOCKED.
  • TIMED_WAITING: the same but with a timeout: Thread.sleep, wait(ms), join(ms), parkNanos, tryLock(timeout), poll(timeout).
  • TERMINATED: run() has returned or thrown.

A thread can't go back to NEW, and calling start() twice throws IllegalThreadStateException. You can read the state with getState(), but it is a snapshot for monitoring, not for synchronisation.

Diagnosis with jcmd <pid> Thread.print or jstack:

  • Many threads BLOCKED "waiting to lock <0x...>" on the same monitor → lock contention; find the thread "locked <0x...>".
  • Many WAITING (parking) in a pool's getTask → idle workers, normal.
  • Many WAITING on a connection pool → pool exhaustion.
  • High CPU with RUNNABLE threads in the same frame → hot loop.

Virtual threads report the same states; a parked virtual thread is WAITING.

How it works

  1. new Thread() → NEW.
  2. start() → RUNNABLE.
  3. Contended synchronized → BLOCKED → RUNNABLE on acquisition.
  4. wait/join/park → WAITING or TIMED_WAITING → RUNNABLE on notify, unpark or timeout.
  5. run ends → TERMINATED.

Example

Thread t = new Thread(() -> {
    try { Thread.sleep(500); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
});
System.out.println(t.getState()); // NEW
t.start();
Thread.sleep(50);
System.out.println(t.getState()); // TIMED_WAITING
t.join();
System.out.println(t.getState()); // TERMINATED

Common mistakes

  • Saying there is a separate RUNNING state.
  • Expecting threads waiting on ReentrantLock to show BLOCKED.
  • Thinking socket I/O shows as WAITING.
  • Using getState() for control flow.

How to answer in the interview

"A thread is NEW after creation and before start. After start it's RUNNABLE, which covers both running and ready to run. It's BLOCKED while waiting to acquire a monitor for synchronized. It's WAITING when it calls wait, join or park without a timeout, and TIMED_WAITING for sleep or the timed versions. Finally it's TERMINATED when run completes. These states appear in thread dumps, which is how I diagnose contention: many threads BLOCKED on the same monitor point to a hot lock."

Likely follow-up questions

  • State during blocking socket I/O? RUNNABLE for a platform thread, since it's in native code.
  • Waiting on ReentrantLock? WAITING (parking), not BLOCKED.
  • Can you restart a TERMINATED thread? No; create a new one.
