Traffic increased but the HPA is not scaling the deployment up. What do you check?

Kubernetes · scenario · levels mid, senior

In one line

Start with kubectl describe hpa: an unknown metric points to metrics-server, an adapter or missing resource requests; ScalingLimited means maxReplicas; scaled-but-Pending pods mean no node capacity; and a service bottlenecked elsewhere may simply be scaling on the wrong metric.

Detailed explanation

The HPA runs a control loop (every 15 seconds by default): it reads metrics, computes desired = ceil(current × currentValue / target), and updates the Deployment's replicas. Each step can fail, and kubectl describe hpa shows where. Its conditions are AbleToScale, ScalingActive (are metrics available?) and ScalingLimited (are we capped by min or max?).

If the current metric shows <unknown>, ScalingActive is False. For CPU and memory that means metrics-server is down or the APIService is unavailable, or the containers have no resource requests, because utilisation targets are a percentage of the request. Every container in the pod needs a request, including sidecars. For custom or external metrics, the Prometheus Adapter or KEDA may be failing or the query returns nothing.

If ScalingLimited is True because of maxReplicas, the HPA is doing its job; the ceiling is too low. If replicas increased but new pods are Pending, the bottleneck is node capacity: check the cluster autoscaler or Karpenter, quotas and node group limits.

The subtle case is the wrong metric. An IO-bound service waiting on a database, or one limited by a thread or connection pool, shows low CPU while its latency soars, so it never crosses a CPU target. Scaling on requests per second, in-flight requests, queue depth or latency via custom metrics is better. Also check behavior settings: a long scaleUp.stabilizationWindowSeconds or restrictive policies delay scale-up.

How it works

  1. kubectl describe hpa: current vs target, conditions, events.
  2. Unknown metric: check metrics-server/adapter and container requests.
  3. At max: raise maxReplicas if downstream capacity allows.
  4. Pods Pending: investigate node autoscaling and quotas.
  5. Metric does not reflect load: switch to RPS, concurrency or queue metrics.
  6. Review the behavior stabilization and policies.

Example

kubectl describe hpa checkout
#  cpu: <unknown>/70%
#  ScalingActive  False  FailedGetResourceMetric  missing request for cpu in container istio-proxy
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: checkout }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: checkout }
  minReplicas: 4
  maxReplicas: 40
  metrics:
    - type: Pods
      pods:
        metric: { name: http_requests_in_flight }
        target: { type: AverageValue, averageValue: "20" }
  behavior:
    scaleUp: { stabilizationWindowSeconds: 0 }

Common mistakes

  • Missing CPU requests on sidecar containers.
  • Scaling IO-bound services on CPU.
  • Ignoring that the database cannot handle more replicas.
  • maxReplicas set years ago and never revisited.

How to answer in the interview

"I start with kubectl describe hpa, which shows current versus target metrics and the AbleToScale, ScalingActive and ScalingLimited conditions. If the metric is unknown, metrics-server or the adapter isn't working, or a container lacks resource requests, which utilisation targets need. If ScalingLimited is true, we're at maxReplicas. If the HPA scaled but pods are Pending, it's node capacity, so I check the cluster autoscaler or Karpenter. And often the metric is wrong: an IO-bound service shows low CPU under heavy load, so I'd scale on requests in flight or queue depth instead."

Likely follow-up questions

  • Why might scaling up make it worse? More replicas mean more connections and load on a struggling database or downstream, deepening the outage.
  • How fast can HPA react? Seconds plus metric delay and pod startup; pre-scale for known peaks.
  • When to use KEDA? For event-driven scaling on queues, streams or external metrics, including scale to zero.
