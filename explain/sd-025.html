What is change data capture, and which problems does it solve in system design?

Data & Storage Design · concept · levels entry, mid, senior

In one line

Change data capture reads the database's transaction log and streams every row change (insert/update/delete) in commit order, so caches, search indexes, warehouses and other services stay in sync without dual writes or polling.

Detailed explanation

Every serious database already records changes in a log for durability and replication: PostgreSQL's WAL (via logical decoding), MySQL's binlog, SQL Server's CDC tables, MongoDB's oplog/change streams. CDC tools such as Debezium (on Kafka Connect), AWS DMS, Azure Data Factory or Fivetran read that log and emit change events.

Benefits: changes are captured even if the application forgets or crashes, ordering matches commits, load on the DB is low compared with polling queries, and you can rebuild derived systems by replaying.

Cautions: events expose the internal schema, so consumers are coupled to table structure; schema changes must be managed (schema registry); delivery is at least once; and initial snapshots of big tables need planning.

How it works

  1. Enable logical replication / binlog in row format.
  2. Connector takes an initial snapshot, then tails the log.
  3. Each change becomes an event (before, after, op, source position) on a Kafka topic per table.
  4. Sinks/consumers update Elasticsearch, Redis, the warehouse, or other services.
  5. Offsets are stored so the connector resumes after restarts.

Example

{"op":"u","before":{"id":42,"status":"PENDING"},
 "after":{"id":42,"status":"PAID"},
 "source":{"table":"orders","lsn":123456789}}

Common mistakes

  • Using raw table CDC as public domain events (couples everyone to your schema).
  • Forgetting that long-running replication slots retain WAL and fill the disk.
  • Not handling deletes/tombstones in sinks.
  • No plan for schema evolution.

How to answer in the interview

"CDC tails the database transaction log, typically with Debezium into Kafka, giving an ordered stream of row changes. I use it to keep search indexes, caches and the warehouse in sync, to implement the outbox pattern and to migrate databases with little downtime. For events other teams consume I prefer outbox-based domain events over raw table changes, to avoid coupling them to my schema."

Likely follow-up questions

  • Why prefer outbox events for integration? Stable, intentional contracts instead of internal tables.
  • What's the risk with Postgres replication slots? WAL piles up if the consumer stops.
  • How do you migrate a DB with CDC? Snapshot + stream to the new DB, verify, then cut over.
