What is the difference between stateless and stateful stream operations?

Java 8+ Features · concept · levels senior, lead

In one line

Stateless operations (filter, map, flatMap, peek) process each element independently, while stateful ones (sorted, distinct, limit, skip) need information about other elements, so they may buffer data, cost memory, act as barriers in parallel streams and can break on infinite streams.

Detailed explanation

A stateless intermediate operation decides what to do with an element using only that element. filter tests it, map transforms it, flatMap expands it. These operations stream data element by element with constant memory, work on infinite streams, and parallelise trivially because chunks need no coordination.

A stateful operation must remember something about elements it has already seen, or must see elements it hasn't seen yet:

  • sorted must consume the entire upstream before emitting the first element: O(n) memory, and on an infinite stream it never finishes.
  • distinct must keep a set of every element seen, so memory grows with the number of unique elements. In ordered parallel streams it must also preserve the first occurrence.
  • limit(n) and skip(n) must count elements. Sequentially that's cheap, but on an ordered parallel stream they must know which elements are the first n in encounter order, requiring buffering and coordination across chunks.

In parallel pipelines stateful operations act as barriers: the pipeline may need to complete one phase before the next, reducing the speed-up. Calling unordered() can relax distinct, limit and skip when order isn't needed.

A separate but related rule: the lambdas you pass should be stateless and non-interfering. A lambda that mutates a shared counter or list produces race conditions in parallel and unpredictable results even sequentially, since the library may reorder or skip calls.

How it works

  1. Stateless stages forward each element immediately to the next sink.
  2. Stateful stages keep internal buffers or sets.
  3. sorted collects all elements at end-of-input, sorts, then emits.
  4. In parallel, stateful stages may force full evaluation of upstream chunks before continuing.

Example

// Stateless: constant memory, works on infinite stream
Stream.iterate(1, i -> i + 1).filter(i -> i % 2 == 0).map(i -> i * i).limit(5).toList();

// Stateful sorted on infinite stream: never terminates
// Stream.iterate(1, i -> i + 1).sorted().limit(5).toList();

// distinct remembers all seen ids
List<String> uniqueCustomers = orders.stream().map(Order::customerId).distinct().toList();

// Parallel with order relaxed
long count = bigList.parallelStream().unordered().distinct().count();

// Stateful lambda: wrong
List<Integer> seen = new ArrayList<>();
nums.parallelStream().filter(n -> seen.add(n)).count();   // race condition

Common mistakes

  • Calling sorted() early on huge streams instead of near the end or in the database.
  • Using distinct on large data without considering memory.
  • Using limit on ordered parallel streams and expecting speed-ups.
  • Confusing stateful operations with stateful lambdas.

How to answer in the interview

"A stateless operation like filter, map or flatMap handles each element independently, so data streams through element by element and parallelises easily. A stateful operation like sorted, distinct, limit or skip needs information about other elements. sorted has to buffer the whole stream before emitting anything, and distinct remembers every element seen, which costs memory. In parallel streams they act as barriers and need coordination, which reduces the speed-up, and sorted on an infinite stream never finishes. Separately, the lambdas themselves should be stateless to stay correct in parallel."

Likely follow-up questions

  • Why is limit() expensive on an ordered parallel stream? It must find the first n elements in encounter order across chunks, buffering and coordinating.
  • How can unordered() help? It lets distinct/limit take any elements, avoiding order bookkeeping.
  • Is peek stateful? No, but it is meant only for debugging.
