How do Azure Front Door caching, rules and the WAF work together to protect and speed up a web application?

Azure · concept · levels mid, senior

In one line

Azure Front Door terminates TLS at Microsoft's global edge (anycast), caches static content close to users, applies a rules engine for redirects, rewrites and routing, and enforces a WAF policy (managed rules, bot protection, custom and rate-limit rules); with Premium, origins are reached over Private Link so they are not public.

Detailed explanation

Front Door (Standard and Premium tiers; the classic tier is being retired) is a global Layer 7 entry point. Users resolve your hostname to an anycast address and connect to the nearest of hundreds of edge locations. TLS terminates there with managed or your own certificates, and Front Door forwards over the Microsoft backbone, reusing warm connections, to the best origin in an origin group based on health probes, latency and priority/weight. That alone cuts latency, and it gives instant global failover.

Caching is configured per route: you can enable caching, choose how query strings affect the cache key, enable compression, and respect or override origin Cache-Control. Static assets served from the edge reduce origin load drastically. Purge invalidates content after deployments.

The rules engine (rule sets attached to routes) evaluates conditions like path, header, device or geography and performs actions: HTTP-to-HTTPS redirects, URL rewrites, request and response header changes, cache overrides and route overrides that send /api/* to a different origin group.

The WAF policy sits at the edge, so attacks are dropped before reaching you. Premium includes the Microsoft default rule set (OWASP-style protections for SQL injection, XSS and more) and the bot manager rule set; custom rules handle geo-filtering, IP allow/deny and rate limiting. Start in detection mode, tune exclusions, then switch to prevention.

How it works

  1. Client → anycast → nearest edge; TLS terminated.
  2. WAF evaluates custom and managed rules.
  3. Rules engine applies redirects, rewrites, header and route overrides.
  4. Cache hit → response from edge; miss → request to origin.
  5. Origin chosen by health and latency; Premium uses Private Link to the origin.
  6. Response cached per route settings and returned.

Example

resource rateRule 'Microsoft.Network/FrontDoorWebApplicationFirewallPolicies@2024-02-01' = {
  name: 'wafShop'
  location: 'global'
  sku: { name: 'Premium_AzureFrontDoor' }
  properties: {
    policySettings: { mode: 'Prevention', enabledState: 'Enabled' }
    customRules: { rules: [ {
      name: 'LimitLogin', priority: 10, ruleType: 'RateLimitRule'
      rateLimitThreshold: 100, rateLimitDurationInMinutes: 1, action: 'Block'
      matchConditions: [ { matchVariable: 'RequestUri', operator: 'Contains', matchValue: [ '/login' ] } ]
    } ] }
  }
}

Common mistakes

  • Leaving origins publicly reachable so attackers bypass Front Door.
  • Caching personalised responses because the cache key ignores cookies or auth.
  • Turning WAF prevention on without tuning, blocking real users.
  • Forgetting to purge or version static assets after release.

How to answer in the interview

"Front Door is a global edge entry point: users hit the nearest edge via anycast, TLS terminates there and traffic travels over Microsoft's backbone to the healthiest origin. I enable caching and compression per route for static content, use the rules engine for HTTPS redirects, header rewrites and sending API paths to a separate origin group, and attach a WAF policy with the managed rule set, bot protection, geo and rate-limit rules. On Premium I connect origins through Private Link and disable their public access, so nothing can bypass Front Door."

Likely follow-up questions

  • How do you stop origin bypass without Private Link? Restrict to the AzureFrontDoor.Backend service tag and check the X-Azure-FDID header.
  • Front Door vs Application Gateway? Global edge vs regional, in-VNet load balancer; often used together.
  • How to cache safely for logged-in users? Cache only static or public routes; bypass cache for authenticated APIs.
