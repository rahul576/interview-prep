What is configuration drift, and how do you detect it?

Infrastructure as Code · concept · levels entry

In one line

Drift is when real infrastructure no longer matches the code, usually from manual changes, hotfixes or other tools; detect it with terraform plan / plan -refresh-only run on a schedule, then fix by updating the code or reapplying, and restrict manual access.

Detailed explanation

Drift appears when something other than the pipeline changes infrastructure: an engineer opens a security group port in the console during an incident, a script changes an instance type, another tool adds tags, or an autoscaler changes desired capacity. The code says one thing, reality says another, and the next person to apply may unknowingly revert an important hotfix or be surprised by unrelated changes in their plan.

Terraform detects drift naturally: every plan refreshes real attributes from the provider APIs and compares them with the configuration, so drift appears as proposed changes. terraform plan -refresh-only shows only what has changed outside Terraform, without proposing configuration changes, and terraform apply -refresh-only accepts those values into state. Exit codes make automation easy: terraform plan -detailed-exitcode returns 0 for no changes, 2 for changes and 1 for errors.

Good teams run scheduled drift detection, for example nightly pipeline jobs per state, and alert to Slack or create a ticket when the plan is not empty. HCP Terraform and similar platforms offer built-in drift detection. Drift only matters for attributes Terraform manages; resources created entirely outside Terraform are not seen unless you scan the account with other tools such as AWS Config.

Each detected drift must be resolved deliberately: if the change was intentional, update the code (and possibly import resources); if not, reapply to revert it. Long term, prevent it by limiting console write access in production, using break-glass roles that are audited, and making the pipeline the normal path for changes.

How it works

  1. Scheduled job runs terraform plan -detailed-exitcode per state.
  2. Exit code 2 → drift or pending changes → alert with the plan.
  3. Triage: intentional or accidental?
  4. Update code via PR, or reapply to revert.
  5. Review who has write access to prevent recurrence.

Example

# GitHub Actions nightly drift check
on:
  schedule: [{ cron: "0 3 * * *" }]
jobs:
  drift:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init -input=false
      - run: |
          set +e
          terraform plan -refresh-only -detailed-exitcode -input=false
          code=$?
          if [ $code -eq 2 ]; then echo "Drift detected"; exit 1; fi
          exit $code

Common mistakes

  • Never running plans unless code changes, so drift accumulates silently.
  • Blindly applying and reverting a necessary incident hotfix.
  • Using ignore_changes to hide drift that should be fixed.
  • Leaving broad console admin access in production.

How to answer in the interview

"Drift is when real infrastructure diverges from the code, typically from manual console changes during incidents, scripts or other tools. Terraform shows it on every plan because it refreshes real attributes, and plan -refresh-only shows only the outside changes. I run scheduled plans, nightly in CI with -detailed-exitcode, and alert when the plan isn't empty. Each drift is resolved on purpose: update the code if the change was intentional, or reapply to revert it. And I reduce the cause by restricting manual write access to production and using audited break-glass roles."

Likely follow-up questions

  • How do you handle attributes that change legitimately outside Terraform? lifecycle ignore_changes for those specific attributes, like an autoscaled desired_count.
  • What does apply -refresh-only do? Updates state to match reality without changing infrastructure.
  • How do you find resources not managed by Terraform at all? Cloud inventory tools like AWS Config or tag audits.
