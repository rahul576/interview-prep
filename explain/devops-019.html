Explain Docker networking modes and how volumes work.

Docker · concept · levels mid, senior

In one line

Containers use the default bridge network (NAT, -p to publish), user-defined bridges with DNS by container name, host mode (no network isolation), overlay for multi-host, or none; for data, volumes (Docker-managed, persistent), bind mounts (host paths) and tmpfs survive beyond, or avoid, the ephemeral writable layer.

Detailed explanation

Networking drivers:

  • Default bridge (bridge/docker0): each container gets a private IP on a virtual bridge; outbound traffic is NATed via the host; inbound access requires publishing ports with -p 8080:80. Containers here can reach each other by IP but not by name; that only worked through the legacy --link.
  • User-defined bridge: created with docker network create. Docker's embedded DNS (127.0.0.11) resolves container names and aliases, networks are isolated from each other, and containers can be connected or disconnected on the fly. Compose creates one per project, which is why services reach each other as db or redis.
  • Host: the container uses the host's network stack directly, with no NAT and no port mapping, for maximum performance or many ports, at the cost of isolation and port conflicts. Full support is on Linux.
  • Overlay: spans multiple Docker hosts with VXLAN, used by Swarm services.
  • none disables networking (macvlan/ipvlan attach to the physical network).

Storage: the container's writable layer is lost when the container is removed and is slow for heavy writes. So:

  • Named volumes (-v pgdata:/var/lib/postgresql/data or --mount type=volume) are managed by Docker under its data directory, independent of host layout, easy to back up, and pre-populated from the image path on first use. Right for databases and persistent app data.
  • Bind mounts (-v $(pwd)/src:/app/src) map a host path, great for live code reload and config files in development, but tied to the host's directory layout and file permissions.
  • tmpfs mounts keep data in memory only, for scratch or sensitive temporary files.

How it works

  1. docker network create appnet → bridge with DNS.
  2. Containers join with --network appnet and resolve each other by name.
  3. Only the public entry point publishes a port to the host.
  4. Stateful containers mount named volumes; dev containers bind-mount source.

Example

docker network create appnet
docker volume create pgdata
docker run -d --name db --network appnet \
  -e POSTGRES_PASSWORD=secret -v pgdata:/var/lib/postgresql/data postgres:17
docker run -d --name api --network appnet -p 8080:8080 \
  -e DB_HOST=db -v "$(pwd)/config:/app/config:ro" shop-api:1.4.2
docker exec api getent hosts db      # resolves via embedded DNS

Common mistakes

  • Expecting name resolution on the default bridge.
  • Publishing database ports to 0.0.0.0 when only other containers need them.
  • Storing database data in the container's writable layer.
  • Bind-mount permission issues with non-root container users.

How to answer in the interview

"By default containers join the bridge network, a private virtual network with NAT, and I publish ports with -p. On a user-defined bridge, which Compose creates automatically, containers resolve each other by name through Docker's embedded DNS. Host mode uses the host's network stack directly, overlay spans multiple hosts as in Swarm, and none disables networking. For storage, the writable layer is ephemeral, so persistent data goes into named volumes, which Docker manages and which survive container removal, while bind mounts map host paths and are handy for development and config files. tmpfs is for in-memory scratch data."

Likely follow-up questions

  • Why can't two containers on the default bridge resolve names? The default bridge has no embedded DNS; use a user-defined network.
  • Back up a volume? Run a temporary container mounting it and tar the contents.
  • Volume vs bind mount in production? Volumes; bind mounts couple you to the host.
