How do you handle DNS and TLS certificate validation in Terraform, for example with ACM or App Service certificates?

Terraform · concept · levels mid, senior

In one line

For DNS-validated certificates such as ACM, create the validation records from the certificate's domain_validation_options with for_each, use an aws_acm_certificate_validation resource that waits until issued, and make listeners reference the validation resource; handle DNS zones in other accounts or providers with provider aliases.

Detailed explanation

Public certificate authorities must verify that you control a domain. With DNS validation, the CA gives you a record (a CNAME for ACM) and checks that it exists. Terraform can do the whole flow in one apply.

ACM flow. aws_acm_certificate with validation_method = "DNS" returns domain_validation_options, one entry per domain or SAN, with the record name, type and value. A for_each over those options creates the records in Route 53. Then aws_acm_certificate_validation takes the certificate ARN and the record FQDNs and waits until ACM reports the certificate as issued. The load balancer listener references aws_acm_certificate_validation.this.certificate_arn, not the certificate resource directly; that creates a dependency so the listener is only created after the certificate is valid. Certificates for CloudFront must be in us-east-1, which also needs a provider alias.

Azure patterns are similar in spirit: App Service managed certificates require a custom domain binding verified with a TXT asuid record and a CNAME or A record; Front Door managed certificates require a _dnsauth TXT record with a validation token exposed by the custom domain resource. Terraform creates those records from the resource attributes and then the binding.

Cross-boundary DNS. The zone often lives in a central networking account, another subscription or an external provider like Cloudflare. Use a provider alias with credentials for that zone, or a separate DNS provider in the same configuration.

Renewal. ACM and managed certificates renew automatically as long as the validation records remain and the domain still resolves.

How it works

  1. Request the certificate with DNS validation.
  2. Read validation records from the resource attributes.
  3. Create records in the right zone using for_each and an alias provider if needed.
  4. Wait for issuance with the validation resource.
  5. Reference the validated certificate in listeners or bindings.
  6. Keep records in place for automatic renewal.

Example

resource "aws_acm_certificate" "api" {
  domain_name               = "api.example.com"
  subject_alternative_names = ["www.api.example.com"]
  validation_method         = "DNS"
  lifecycle { create_before_destroy = true }
}

resource "aws_route53_record" "validation" {
  provider = aws.dns   # zone in the shared networking account
  for_each = {
    for o in aws_acm_certificate.api.domain_validation_options : o.domain_name => o
  }
  zone_id = var.zone_id
  name    = each.value.resource_record_name
  type    = each.value.resource_record_type
  records = [each.value.resource_record_value]
  ttl     = 60
  allow_overwrite = true
}

resource "aws_acm_certificate_validation" "api" {
  certificate_arn         = aws_acm_certificate.api.arn
  validation_record_fqdns = [for r in aws_route53_record.validation : r.fqdn]
}

resource "aws_lb_listener" "https" {
  # ...
  certificate_arn = aws_acm_certificate_validation.api.certificate_arn
}

Common mistakes

  • Referencing the certificate ARN directly, so the listener is created before issuance and fails.
  • Deleting validation records after issuance, breaking renewal.
  • Using a list instead of a map for validation records, causing churn.
  • Requesting CloudFront certificates outside us-east-1.

How to answer in the interview

"With ACM, the certificate resource with DNS validation exposes domain_validation_options, the CNAME records proving ownership. I create those in Route 53 with for_each, then an aws_acm_certificate_validation resource that waits until the certificate is issued. The listener references the validation resource's ARN, so it only uses the certificate once valid. Azure is similar, with TXT or CNAME records for App Service or Front Door managed certificates. The zone often lives in another account or in Cloudflare, so I use a provider alias. Renewal is automatic as long as the records stay."

Likely follow-up questions

  • What if validation records are deleted? Renewal fails and the certificate eventually expires.
  • Why create_before_destroy on certificates? A replacement must exist before the old one is detached from listeners.
  • Wildcard plus apex? They share one validation record; key the map by domain carefully.
