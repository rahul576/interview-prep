What are the ACID properties of relational databases?

Databases & SQL · concept · levels entry

In one line

ACID means Atomicity (all or nothing), Consistency (constraints hold before and after), Isolation (concurrent transactions do not see each other's partial work, controlled by isolation levels) and Durability (committed changes survive crashes, through the write-ahead log).

Detailed explanation

Atomicity: a transaction is indivisible. If any statement fails, or the system crashes mid-way, all its changes are undone. A bank transfer never debits one account without crediting the other.

Consistency: every committed transaction leaves the database in a valid state according to its rules: primary keys, foreign keys, unique, check and not-null constraints, and triggers. If a statement would violate a constraint, it fails and the transaction can roll back. Application-level rules are only guaranteed if they are encoded as constraints or carefully enforced in transactions.

Isolation: concurrent transactions should behave as if run one after another. Full serializability is expensive, so SQL defines levels that allow certain anomalies:

  • Read Uncommitted: dirty reads possible (PostgreSQL treats it as Read Committed).
  • Read Committed: no dirty reads, but non-repeatable reads and phantoms. Default in PostgreSQL, Oracle, SQL Server.
  • Repeatable Read: rows read stay the same; MySQL InnoDB's default. PostgreSQL's implementation is snapshot isolation, which also prevents phantoms.
  • Serializable: equivalent to some serial order; implemented with SSI in PostgreSQL or locking elsewhere, may abort transactions with serialization failures that must be retried.

Most engines use MVCC: readers see a snapshot of row versions, so reads do not block writes.

Durability: once commit succeeds, the change is permanent. The database writes changes to the write-ahead log (WAL)/redo log and flushes it to disk before acknowledging; data files are updated later, and after a crash the log is replayed. Replication to another node adds protection against losing the machine.

How it works

  1. BEGIN starts a transaction and assigns a snapshot or transaction id.
  2. Changes create new row versions and log records.
  3. Locks or MVCC rules control what other transactions see.
  4. Constraints are checked during statements or at commit.
  5. COMMIT flushes the log and makes versions visible; ROLLBACK discards them.
  6. Crash recovery redoes committed and undoes uncommitted work.

Example

SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
BEGIN;
UPDATE stock SET qty = qty - 1 WHERE sku = 'LAMP-01' AND qty > 0;
INSERT INTO order_item(order_id, sku, qty) VALUES (991, 'LAMP-01', 1);
COMMIT;

Common mistakes

  • Defining consistency as "replicas agree", which is CAP consistency.
  • Assuming Serializable is the default.
  • Not retrying serialization failures at higher isolation levels.
  • Thinking ACID protects against lost updates in read-modify-write code without locking or versioning.

How to answer in the interview

"ACID describes reliable transactions. Atomicity: all operations succeed or none do, so a transfer never debits without crediting. Consistency: each transaction moves the database between valid states, respecting constraints and foreign keys. Isolation: concurrent transactions don't see each other's intermediate changes, and isolation levels from read committed to serializable trade strictness for concurrency; most databases implement this with MVCC. Durability: once committed, data survives crashes because the write-ahead log is flushed to disk before the commit returns."

Likely follow-up questions

  • Which anomalies does each level prevent? Read Committed stops dirty reads, Repeatable Read stops non-repeatable reads, Serializable stops phantoms and write skew.
  • What is a lost update? Two transactions read, modify and write the same value; one overwrites the other.
  • What is write skew? Two transactions read overlapping data and update different rows, breaking an invariant; only Serializable prevents it.
