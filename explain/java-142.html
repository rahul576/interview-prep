How should passwords and sensitive data be stored?

Security · concept · levels mid, senior

In one line

Hash passwords with a slow, adaptive, salted algorithm such as Argon2id or bcrypt (via Spring's PasswordEncoder), never plain text, encryption or fast hashes; encrypt other sensitive data at rest with keys held in a KMS, and minimise and restrict access to it.

Detailed explanation

Passwords are special because you never need to read them back, only check them. So they should be hashed, not encrypted: encryption is reversible, and whoever steals the key gets every password. Fast hashes like MD5, SHA-1 or SHA-256 are also wrong, because GPUs can compute billions per second, making brute force and dictionary attacks cheap.

A password hashing function is deliberately slow and tunable. Argon2id (memory-hard, OWASP's first choice), bcrypt, scrypt and PBKDF2 (for FIPS environments) all take a work factor. Each password gets a unique random salt, stored with the hash, so identical passwords produce different hashes and precomputed rainbow tables are useless. An optional pepper, a secret kept outside the database, adds protection if only the DB leaks. In Spring Security, PasswordEncoderFactories.createDelegatingPasswordEncoder() stores hashes as {bcrypt}$2a$10$..., so you can change algorithms later and still verify old hashes.

Other sensitive data such as personal data, bank details or API tokens must often be readable, so it is encrypted: TLS in transit, and at rest with disk or database encryption plus, for the most sensitive fields, application-level (envelope) encryption. Keys live in a KMS or HSM (AWS KMS, Azure Key Vault, Google Cloud KMS, Vault Transit), not in config files, and are rotated. Equally important: collect less data, mask it in logs, tokenise card numbers (PCI DSS), restrict access by least privilege and audit it.

How it works

  1. On registration, generate a random salt and hash the password with the chosen work factor.
  2. Store the encoded string (algorithm, parameters, salt, hash) in one column.
  3. On login, re-hash the input with the stored parameters and compare in constant time.
  4. When the policy changes, re-hash on the next successful login.
  5. For other data, encrypt with a data key that is itself encrypted by a KMS master key.

Example

@Bean
PasswordEncoder passwordEncoder() {
    // stores e.g. {bcrypt}$2a$10$... and can still verify older formats
    return PasswordEncoderFactories.createDelegatingPasswordEncoder();
}

// registration
user.setPasswordHash(passwordEncoder.encode(rawPassword));

// login is handled by DaoAuthenticationProvider calling passwordEncoder.matches(raw, stored)
// if UserDetailsPasswordService is implemented, Spring upgrades outdated hashes automatically

Common mistakes

  • Encrypting passwords "so support can see them".
  • Using SHA-256 with or without a single global salt.
  • A work factor so low it is fast, or never increased.
  • Encryption keys stored next to the data or committed to Git.
  • Logging request bodies that contain passwords or card numbers.

How to answer in the interview

"Passwords are never stored in plain text, encrypted, or hashed with MD5 or SHA-256, because fast hashes can be brute forced on GPUs. I use a slow adaptive algorithm such as Argon2id or bcrypt through Spring Security's DelegatingPasswordEncoder, which adds a unique salt per password and a work factor I can increase over time, and records the algorithm so I can migrate. Other sensitive data that must be read back is encrypted at rest with keys from a KMS like AWS KMS or Azure Key Vault, with rotation, least-privilege access and audit logs, and I mask it in logs."

Likely follow-up questions

  • How would you upgrade the hashing algorithm for existing users? Re-hash on next successful login using the delegating encoder; optionally wrap old hashes in the new algorithm.
  • What is a pepper? A secret added to all hashes and kept outside the DB, for example in a KMS.
  • Hashing vs encryption? Hashing is one-way for verification; encryption is reversible with a key.
