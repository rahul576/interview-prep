What is CORS, and how do you configure it correctly in Spring Boot?

Security · concept · levels mid, senior

In one line

CORS lets a server relax the browser's same-origin policy with Access-Control-Allow- headers, often after a preflight OPTIONS request; in Spring configure a CorsConfigurationSource with explicit origins (never with credentials) and enable it in the security filter chain. It is not an access-control mechanism for the server.

Detailed explanation

An origin is scheme + host + port. The same-origin policy stops JavaScript on https://app.example.com from reading responses from https://api.example.com. CORS (Cross-Origin Resource Sharing) is how the API says "this origin may read my responses".

For simple requests (GET, HEAD or POST with simple content types and headers) the browser sends the request with an Origin header and only lets the script read the response if Access-Control-Allow-Origin matches. For other requests, such as a PUT, a JSON Content-Type or an Authorization header, the browser first sends a preflight: OPTIONS with Access-Control-Request-Method and Access-Control-Request-Headers. The server answers with allowed origins, methods and headers and optionally Access-Control-Max-Age to cache the result. If cookies or credentials are sent, the response must have Access-Control-Allow-Credentials: true and an exact origin; browsers reject a wildcard in that case.

In Spring MVC you can use @CrossOrigin or a WebMvcConfigurer, but with Spring Security the preflight has no credentials and could be rejected with 401 before reaching MVC. So you call http.cors(...) and provide a CorsConfigurationSource bean; the CorsFilter then handles preflights early in the chain.

Remember what CORS is not: it only restricts browsers. curl, Postman or another server ignore it, so the API still needs proper authentication and authorization, and CORS does not replace CSRF protection.

How it works

  1. Browser script calls the API from another origin.
  2. For non-simple requests, the browser sends a preflight OPTIONS.
  3. The CorsFilter matches the origin against configuration and replies with allow headers.
  4. The browser sends the real request; the response also carries Access-Control-Allow-Origin.
  5. If headers are missing or wrong, the browser blocks the script from reading the response.

Example

@Bean
CorsConfigurationSource corsConfigurationSource() {
    CorsConfiguration c = new CorsConfiguration();
    c.setAllowedOrigins(List.of("https://app.example.com"));
    c.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE"));
    c.setAllowedHeaders(List.of("Authorization", "Content-Type"));
    c.setAllowCredentials(true);
    c.setMaxAge(Duration.ofHours(1));
    UrlBasedCorsConfigurationSource src = new UrlBasedCorsConfigurationSource();
    src.registerCorsConfiguration("/api/**", c);
    return src;
}

@Bean
SecurityFilterChain chain(HttpSecurity http) throws Exception {
    http.cors(Customizer.withDefaults())
        .authorizeHttpRequests(a -> a.anyRequest().authenticated());
    return http.build();
}

Common mistakes

  • allowedOrigins("*") together with credentials, which fails or is dangerously loosened with patterns.
  • Configuring CORS only in MVC so Spring Security blocks the preflight.
  • Reflecting any Origin header back without checking it.
  • Thinking CORS protects the API from non-browser clients.
  • Adding CORS headers both at the gateway and in the service, producing duplicates.

How to answer in the interview

"Browsers enforce the same-origin policy, so a page from one origin cannot read API responses from another unless the server allows it with CORS headers. For non-simple requests such as PUT or JSON with an Authorization header, the browser first sends a preflight OPTIONS and checks the allowed origins, methods and headers. In Spring Boot I define a CorsConfigurationSource with the specific frontend origins, never a wildcard when credentials are used, and enable it with http.cors in the security chain so preflights are not rejected. CORS is a browser rule, not server security; the API still authenticates every call."

Likely follow-up questions

  • Why does a CORS error sometimes appear only in production? Different origin or port, a proxy or gateway stripping headers, or a 401/500 response without CORS headers.
  • Does CORS prevent CSRF? No; simple cross-site requests can still be sent; use CSRF tokens or SameSite cookies.
  • How to reduce preflight overhead? Set Access-Control-Max-Age, or serve the API on the same origin.
