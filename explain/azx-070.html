Your AKS clusters use the managed NGINX ingress from the application routing add-on. What do you need to plan, and what are the options?

Azure Kubernetes (AKS) · scenario · levels mid, senior

In one line

The upstream Ingress NGINX project was retired in March 2026 and Microsoft's security patches for the application routing add-on's NGINX only run until November 2026, so you must migrate now, preferably to the add-on's Gateway API mode (Istio-based Envoy gateways) or to Application Gateway for Containers, running both side by side and shifting traffic gradually.

Detailed explanation

The application routing add-on gave AKS a managed NGINX ingress controller, with DNS and Key Vault certificate integration. It was built on the community Ingress NGINX project, which the Kubernetes project retired in March 2026: no new releases, bug fixes or security patches. Microsoft committed to critical security patches for the add-on's NGINX only until November 2026. Since we are at the end of that window, any cluster still on it is effectively running an unsupported, internet-facing component, which is a security and compliance risk.

Options:

  • Application routing in Gateway API mode (Microsoft's recommended path): the add-on deploys a managed, Istio-based control plane that only manages Envoy gateways for Gateway and HTTPRoute resources (no sidecar mesh required). Newer AKS Automatic clusters use it by default.
  • Application Gateway for Containers: an Azure-managed layer 7 load balancer driven by Gateway API or Ingress, with WAF.
  • Another Gateway API implementation such as Envoy Gateway, Traefik or a vendor controller, which you then operate yourself.

The hard part is not the controller but the NGINX-specific annotations: rewrites, regex paths, configuration-snippet, auth-url, rate limiting, CORS, session affinity and custom timeouts. Gateway API covers many of these natively (path rewrites, header modification, weighted backends), but snippets and Lua-based tricks need redesign or policy resources.

How it works

  1. Inventory: list all Ingress objects, ingress classes and annotations across clusters.
  2. Choose the target and enable it alongside NGINX.
  3. Convert Ingresses to Gateway/HTTPRoute, using tools like ingress2gateway as a starting point, and review manually.
  4. Test each route in staging: TLS, headers, redirects, timeouts, large uploads, WebSockets.
  5. Shift DNS or traffic gradually per host, watching errors and latency.
  6. Remove NGINX and its annotations once traffic is fully moved.

Example

# Find NGINX-specific annotations to plan the conversion
kubectl get ingress -A -o json | jq -r '.items[] | .metadata.namespace + "/" + .metadata.name + " " +
  ((.metadata.annotations // {}) | keys | map(select(startswith("nginx.ingress"))) | join(","))'
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: shop, namespace: shop }
spec:
  parentRefs: [{ name: public-gw, namespace: gateways }]
  hostnames: ["shop.contoso.com"]
  rules:
  - matches: [{ path: { type: PathPrefix, value: /api } }]
    filters:
    - type: URLRewrite
      urlRewrite: { path: { type: ReplacePrefixMatch, replacePrefixMatch: / } }
    backendRefs: [{ name: shop-api, port: 80 }]

Common mistakes

  • Assuming "managed add-on" means Microsoft will keep it supported forever.
  • Converting manifests automatically without testing annotation behaviour.
  • Big-bang cutover of all hosts at once.
  • Forgetting TLS certificates, DNS automation and WAF rules tied to the old controller.

How to answer in the interview

"Ingress NGINX upstream was retired in March 2026, and Microsoft only patches the add-on's NGINX until November 2026, so I'd treat this as an urgent migration. The recommended path is the application routing add-on in Gateway API mode, which runs an Istio-based control plane managing Envoy gateways; Application Gateway for Containers is the other main option. I'd inventory every Ingress and its NGINX annotations, convert them to HTTPRoutes with tooling plus manual review, run both controllers side by side, shift DNS host by host, and finally remove NGINX."

Likely follow-up questions

  • Hardest annotations? configuration-snippet, server-snippet, regex rewrites, external auth and custom rate limiting.
  • Does Istio mode need a sidecar mesh? No, it manages gateways only.
  • How do you roll back? Keep NGINX running and switch DNS back until the cutover is confirmed.
