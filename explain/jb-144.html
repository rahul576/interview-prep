What is a composite index? How does column order affect it?

Databases & SQL · concept · levels mid, senior

In one line

A composite index is one index on several columns, sorted by the first column, then the second, and so on, so it serves queries through the leftmost prefix rule; put equality columns first and range or sort columns last.

Detailed explanation

Think of a phone book sorted by last name and then first name. Finding "Sharma, Priya" is fast, finding all Sharmas is fast, but finding everyone called Priya means reading the whole book. A B-tree index on (customer_id, created_at) works the same way: entries are ordered by customer_id, and within each customer by created_at.

The leftmost prefix rule follows: the index supports filters on customer_id, or on customer_id and created_at, but not on created_at alone.

Column order rules of thumb:

  • Equality predicates first (customer_id = ?, status = ?).
  • Then the range or ORDER BY column (created_at > ?, ORDER BY created_at DESC). Once the engine hits a range, columns after it cannot be used to narrow the search, only filtered.
  • Adding the selected columns (or INCLUDE columns) makes it a covering index, enabling an index-only scan.

So WHERE customer_id = ? ORDER BY created_at DESC LIMIT 20 with an index on (customer_id, created_at) reads exactly 20 index entries with no sort. With (created_at, customer_id) the engine would have to scan by date and filter for the customer, which is much worse.

How it works

  1. The index stores tuples (col1, col2, ..., row pointer) in sorted order.
  2. The engine descends the tree using the leading equality values.
  3. Within that range, the next column is already sorted, enabling range scans and ordered reads.
  4. A range on a column stops further index navigation for later columns.
  5. If all needed columns are in the index, the table is not touched.

Example

CREATE INDEX idx_orders_cust_created ON orders (customer_id, created_at DESC);

-- Uses index fully, no sort
SELECT id, total FROM orders WHERE customer_id = 42 ORDER BY created_at DESC LIMIT 20;
-- Uses leading column
SELECT count(*) FROM orders WHERE customer_id = 42;
-- Cannot seek on the index (no leading column)
SELECT * FROM orders WHERE created_at > now() - interval '1 day';

-- Covering version (PostgreSQL)
CREATE INDEX idx_orders_cov ON orders (customer_id, created_at DESC) INCLUDE (total);

Common mistakes

  • Creating separate single-column indexes and expecting them to act like a composite.
  • Putting the range column first.
  • Adding a composite index that duplicates the prefix of an existing one.
  • Forgetting that functions on a column (DATE(created_at)) prevent index use.

How to answer in the interview

"A composite index is a single index on several columns, sorted by the first column and then by the next within it, like a phone book by last name and first name. Because of that, the leftmost prefix rule applies: an index on customer id and created at helps queries filtering by customer, or customer and date, but not date alone. I put equality columns first and range or sort columns last, so WHERE customer id equals something ORDER BY created at DESC reads just the needed entries with no sort. If I include the selected columns, it becomes a covering index and avoids table lookups."

Likely follow-up questions

  • Would (created_at, customer_id) work for that query? Poorly; it must scan by date and filter customers, and cannot avoid the sort for one customer.
  • Can the database combine two single-column indexes? Yes, with bitmap or index merge, but it is usually slower than one composite index.
  • Does column order matter for pure equality on both columns? Less so; choose the order that also serves other queries.
