What logging drivers does Docker support, and how do you centralise container logs?

Docker · concept · levels mid

In one line

The logging driver decides where container stdout/stderr go: default json-file, more efficient local, or remote drivers like syslog, journald, fluentd, awslogs, gcplogs, set per container or in daemon.json; a robust pattern is local files with rotation plus an agent (Fluent Bit, Vector) shipping to Elasticsearch or Loki.

Detailed explanation

Containers should log to stdout and stderr, and Docker captures those streams. The logging driver determines what happens next. json-file is the default: each line is stored as JSON with a timestamp in a file on the host, readable with docker logs, but with no rotation unless configured. local uses a compact binary format and rotates by default, so it is a better default for new hosts. journald and syslog hand logs to the host's logging system. fluentd, gelf, awslogs (CloudWatch), gcplogs, splunk and others send logs directly to a remote collector.

You set the driver per container with --log-driver and --log-opt, in Compose with the logging key, or as the default in /etc/docker/daemon.json (applies to new containers only).

Remote drivers have trade-offs. By default delivery is blocking: if the destination is slow or down, writes to stdout block and the application stalls. mode=non-blocking with max-buffer-size uses a ring buffer instead, dropping messages when it is full. Since Docker 20.10, dual logging keeps a local cache so docker logs works with remote drivers, but older setups lost it.

For these reasons a common robust architecture is to keep json-file or local with rotation and run a node-level agent such as Fluent Bit, Vector or Promtail/Alloy that tails the files, adds metadata (container name, labels) and ships to Elasticsearch/OpenSearch, Loki or a SaaS. Kubernetes does exactly this. Structured JSON application logs make parsing reliable.

How it works

  1. App writes to stdout/stderr.
  2. The container shim passes the streams to dockerd's logging driver.
  3. The driver writes locally or sends to a remote endpoint.
  4. An agent tails local files, enriches and buffers.
  5. The backend indexes logs for search and alerts.

Example

{
  "log-driver": "local",
  "log-opts": { "max-size": "20m", "max-file": "5" }
}
docker run -d --log-driver fluentd \
  --log-opt fluentd-address=127.0.0.1:24224 \
  --log-opt mode=non-blocking --log-opt max-buffer-size=4m \
  --log-opt tag=orders registry.local/orders:1.4

Common mistakes

  • json-file without rotation, filling disks.
  • Blocking remote drivers that freeze apps when the log backend is down.
  • Logging to files inside the container instead of stdout.
  • Unstructured multiline stack traces that the pipeline splits into many events.

How to answer in the interview

"The logging driver decides where stdout and stderr go. The default json-file writes JSON files on the host; local is more compact with rotation built in. Other drivers send to syslog, journald, fluentd, CloudWatch with awslogs or Google Cloud Logging, set per container or globally in daemon.json. Remote drivers can block the application if the destination is slow unless you use non-blocking mode. So I usually keep a local driver with rotation and run an agent like Fluent Bit or Vector that ships the files with metadata to Elasticsearch or Loki, with apps logging structured JSON."

Likely follow-up questions

  • What if the remote destination is down? Blocking mode stalls the app; non-blocking drops messages when the buffer fills.
  • Does docker logs work with remote drivers? Yes since 20.10 via dual logging, unless disabled.
  • How do you handle multiline stack traces? Log JSON or configure multiline parsing in the agent.
