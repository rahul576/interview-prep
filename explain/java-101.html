What is the difference between == and equals() in Java?

Core Java & OOP · concept · levels entry

In one line

For primitives, == compares values; for objects, == compares references (same object in memory), while equals() compares logical content as defined by the class. Watch out for the string pool and the Integer cache, which make == look correct by accident.

Detailed explanation

== on primitives (int, double, char, boolean...) compares the actual values: 5 == 5 is true.

== on references asks "do these two variables point to the same object?" It never looks inside the objects. Two different Customer objects with identical fields are not ==.

equals() is a method defined on Object. Its default implementation is identity, exactly like ==. Classes with value semantics override it: String, the wrapper types (Integer, Long), BigDecimal, LocalDate, collections and records all compare content. Your own classes should override equals (and hashCode) if two instances with the same data should be considered equal.

Pitfall 1: the string pool. String literals are interned, so "abc" == "abc" is true because both refer to the same pooled object. But a string created at runtime (new String("abc"), read from input, built by concatenation of non-constants, substring) is a different object, so == returns false even though the text is the same. Always use equals (or equalsIgnoreCase) for strings.

Pitfall 2: the Integer cache. Autoboxing uses Integer.valueOf, which returns cached instances for -128 to 127 (the upper bound is configurable). So Integer a = 127, b = 127; a == b is true, but with 128 it is false. Code that compares boxed values with == passes tests with small ids and fails in production. Long, Short, Byte and Character have similar caches.

Other details: comparing a boxed and a primitive value with == unboxes, which throws NullPointerException if the wrapper is null. BigDecimal.equals considers scale (2.0 vs 2.00 are not equal), so use compareTo for numeric equality. Enums can safely be compared with == because each constant is a singleton. Use Objects.equals(a, b) to handle nulls.

How it works

  1. a == b with primitives: compare the bits of the values.
  2. a == b with references: compare the references (identity).
  3. a.equals(b): virtual call to the class's equals, which may compare fields.
  4. Literals and small boxed values may share instances, making == misleadingly true.
  5. Objects.equals(a, b) checks identity, then nulls, then a.equals(b).

Example

String s1 = "order";
String s2 = "order";
String s3 = new String("order");
System.out.println(s1 == s2);          // true  (same pooled literal)
System.out.println(s1 == s3);          // false (different objects)
System.out.println(s1.equals(s3));     // true  (same content)

Integer a = 127, b = 127;
Integer c = 128, d = 128;
System.out.println(a == b);            // true  (Integer cache)
System.out.println(c == d);            // false (separate objects)
System.out.println(c.equals(d));       // true

System.out.println(new BigDecimal("2.0").equals(new BigDecimal("2.00")));        // false
System.out.println(new BigDecimal("2.0").compareTo(new BigDecimal("2.00")) == 0); // true

Status st = Status.PAID;
if (st == Status.PAID) { /* fine for enums */ }

Common mistakes

  • Comparing strings with ==.
  • Comparing Integer or Long ids with ==.
  • Calling name.equals("x") when name may be null (use "x".equals(name) or Objects.equals).
  • Using BigDecimal.equals for amounts that differ only in scale.

How to answer in the interview

"For primitives, == compares values. For objects, == compares references, so it's true only when both variables point to the same object. equals compares logical content, and classes like String, Integer and records override it to compare the value. A common pitfall is comparing strings with ==, which seems to work for literals because of the string pool but fails for strings created at runtime. Another is Integer: values between -128 and 127 come from a cache, so == looks correct only in that range. So for objects I use equals, or Objects.equals when nulls are possible, and == only for primitives and enums."

Likely follow-up questions

  • Why does new Integer(127) == new Integer(127) return false? new always creates two distinct objects, bypassing the cache; the constructor is deprecated for removal, so use Integer.valueOf.
  • Can you compare enums with ==? Yes; each enum constant is a single instance, and == is also null-safe.
  • What does intern() do? Returns the canonical pooled instance of a string, so interned equal strings are ==.
