What are Ansible Galaxy and collections?

Configuration Management · concept · levels entry

In one line

Ansible Galaxy is the hub for sharing roles and collections; collections bundle modules, plugins and roles under a namespace (such as amazon.aws, community.general), installed from a pinned requirements.yml with ansible-galaxy and used via fully qualified names.

Detailed explanation

Since Ansible 2.10, the project is split into ansible-core, which contains the engine and the ansible.builtin modules, and collections that contain almost everything else. A collection is a versioned package with a namespace.name, for example amazon.aws (EC2, S3 and other AWS modules plus the aws_ec2 inventory plugin), azure.azcollection, kubernetes.core, ansible.posix, community.general or community.postgresql. It can contain modules, plugins (inventory, lookup, filter, callback), roles and playbooks.

Ansible Galaxy (galaxy.ansible.com) is the public distribution hub. Red Hat's Automation Hub offers certified content for subscribers, and companies often run a private Automation Hub or Galaxy NG for internal collections. The ansible community package bundles a curated set of collections, but serious projects declare exactly what they need.

Dependencies go into requirements.yml with pinned versions, including roles from Galaxy or Git. Installing with ansible-galaxy collection install -r requirements.yml (or ansible-galaxy install -r for both roles and collections) in CI, in execution environments and on developer laptops ensures everybody runs the same module code. Collections can be installed into a project-local path via collections_path.

In playbooks, use fully qualified collection names (FQCN) like amazon.aws.ec2_instance or ansible.builtin.copy. FQCNs remove ambiguity when two collections ship a module with the same short name, document where a module comes from, and are enforced by ansible-lint.

How it works

  1. Declare collections and roles with versions in requirements.yml.
  2. ansible-galaxy downloads them from Galaxy, Automation Hub or Git.
  3. They are installed to collections_path / roles_path.
  4. Playbooks reference modules by FQCN.
  5. Upgrades happen by editing versions and testing.

Example

# requirements.yml
collections:
  - name: amazon.aws
    version: "9.1.0"
  - name: community.general
    version: ">=10.0.0,<11.0.0"
  - name: https://git.acme.local/platform/acme.base.git
    type: git
    version: v2.3.0
roles:
  - name: geerlingguy.docker
    version: "7.4.1"
ansible-galaxy install -r requirements.yml -p ./vendor
ansible-galaxy collection list
- name: Launch instance
  amazon.aws.ec2_instance:
    name: web-01
    instance_type: t3.small
    image_id: "{{ ami_id }}"

Common mistakes

  • Relying on whatever collection versions happen to be installed on a machine.
  • Using short module names, causing ambiguity and lint failures.
  • Installing collections globally on CI agents shared by many projects.
  • Pulling roles from Galaxy without reviewing their code and maintenance status.

How to answer in the interview

"Ansible Galaxy is the public hub for sharing Ansible content, and companies often run a private Automation Hub. Content comes as collections, which bundle modules, plugins and roles under a namespace, like amazon.aws, community.general or kubernetes.core; since 2.10 most modules live in collections rather than core. Each project lists its dependencies in requirements.yml with pinned versions and installs them with ansible-galaxy in CI and locally, so everybody runs the same module versions. In tasks I always use fully qualified names like amazon.aws.ec2_instance."

Likely follow-up questions

  • Why use fully qualified collection names? No ambiguity between collections, clear provenance, lint-friendly and future-proof.
  • What is an execution environment? A container image with ansible-core, collections and Python deps, built with ansible-builder.
  • How do you publish an internal collection? ansible-galaxy collection build and publish to a private hub or install from Git.
