What are the trade-offs of very long context windows, and how do you manage context in an application?

LLMOps & RAG · concept · levels mid, senior

In one line

Long contexts (hundreds of thousands to millions of tokens) are powerful but raise cost and latency and can degrade quality ("lost in the middle", distraction); manage context deliberately with retrieval, summarising or trimming history, condensing tool results and careful placement, an approach called context engineering.

Detailed explanation

Many frontier models now accept around 200K tokens, some 1 million or more, enough for a whole contract set or codebase in one call.

Costs. Every input token is billed and processed on every call. A 300K-token prompt sent ten times in a conversation is 3 million input tokens. Prefill time grows with length, so time to first token rises from sub-second to tens of seconds, and attention cost grows with sequence length. Prompt caching softens this for stable prefixes, but not for content that changes.

Quality. Research such as "Lost in the Middle" showed models use information at the beginning and end of the context better than the middle, and needle-in-a-haystack scores overstate real reasoning across long inputs: multi-hop questions that require combining several distant facts degrade more. Irrelevant content also distracts the model and can increase hallucination, and in agent loops, accumulated tool outputs and stale reasoning pollute later steps ("context rot").

Context engineering treats the window as a scarce budget and decides what the model sees each turn:

  • Retrieval selects the most relevant chunks instead of stuffing entire collections.
  • Conversation memory: keep recent turns verbatim, summarise older ones, and store durable facts separately.
  • Tool results: return concise, structured results; truncate logs; let the agent fetch details on demand.
  • Placement: clear instructions at the start (system prompt), key documents near the question, and a restatement of the task after long documents.

When to use long context deliberately: one-off deep analysis where everything may matter (due diligence on a document set, cross-file code refactoring), when chunking would destroy structure, or when retrieval quality is poor. For repeated queries over a large corpus, retrieval is usually cheaper, faster and often more accurate.

How it works

  1. Define a token budget per call.
  2. Fixed part: system prompt and tools (cached).
  3. Dynamic part: retrieved chunks ranked and trimmed to budget.
  4. History: recent turns plus a running summary.
  5. Monitor tokens per call, cost and quality as conversations grow.

Example

def build_context(question, history, budget=24_000):
    msgs = [system_prompt()]                                   # stable, cached
    msgs += summarise_if_needed(history, keep_last=6)         # running summary + recent turns
    chunks = rerank(question, hybrid_search(question, k=40))[:8]
    msgs.append(user_msg(format_chunks(chunks) + "\n\nQuestion: " + question))
    return trim_to_budget(msgs, budget)

Common mistakes

  • Stuffing whole knowledge bases into every request because "it fits".
  • Letting agent context grow unbounded with raw tool output.
  • Putting the key instruction in the middle of a huge document.
  • Trusting needle-in-a-haystack benchmarks as proof of long-context reasoning.

How to answer in the interview

"Long windows are great for analysing big documents or codebases, but every token is paid for and processed on every call, so cost and time to first token rise, unless caching applies. Quality can also drop: models under-use information in the middle and get distracted by irrelevant content. So I treat context as a scarce resource, which is what people now call context engineering: retrieve only relevant chunks, summarise or trim old history, condense tool results, and place instructions clearly at the start and key content near the question. Long context suits one-off deep analysis; for repeated queries, retrieval is usually cheaper and better."

Likely follow-up questions

  • When choose long context over retrieval? One-off analysis where everything may matter or chunking breaks structure.
  • How to summarise history safely? Keep facts, decisions and open tasks; drop chit-chat; test for lost information.
  • Does caching remove the cost? Reduces it for stable prefixes, not for changing content.
