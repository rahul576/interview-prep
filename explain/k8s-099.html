What is the difference between Kustomize overlays and Helm values, and how do you combine them?

Kubernetes · concept · levels mid, senior

In one line

Helm is a templating package manager with values and versioned releases; Kustomize patches plain YAML with overlays and has no templating; many teams render Helm charts and patch the output with Kustomize.

Detailed explanation

A Helm chart contains templates written in Go templating with conditionals, loops and helpers, plus a values.yaml of defaults. You install it as a release with your own values, and Helm records the release history so you can upgrade and roll back. Charts are versioned and distributed through repositories or OCI registries, which makes Helm the standard way to ship third-party software like ingress controllers, cert-manager or databases.

Kustomize is built into kubectl (kubectl apply -k). You keep ordinary YAML in a base and create overlays per environment that apply strategic-merge or JSON patches, change image tags and replica counts, add labels and namespaces, and generate ConfigMaps and Secrets with hash suffixes. There is no logic; what you see is what gets applied, which makes reviews easy. The limitation is that you can only change what you can patch, and there is no release concept.

They combine well. Use Helm for vendor charts and Kustomize for the last mile: settings the chart's values do not expose, such as an extra annotation or a sidecar. You can do this with Kustomize's helmCharts field (with --enable-helm), with a Helm post-renderer that pipes rendered manifests through Kustomize, or in Argo CD and Flux, which support both. For in-house applications, Kustomize overlays or one simple shared internal chart is usually enough.

How it works

  1. Helm: chart templates + values → rendered manifests → tracked release.
  2. Kustomize: base YAML + overlay patches → final manifests.
  3. Combined: Helm renders the chart, Kustomize patches the result.
  4. GitOps tool applies the output to the cluster.

Example

# overlays/prod/kustomization.yaml
helmCharts:
  - name: ingress-nginx
    repo: https://kubernetes.github.io/ingress-nginx
    version: 4.11.3
    releaseName: ingress
    namespace: ingress
    valuesFile: values-prod.yaml
patches:
  - target: { kind: Deployment, name: ingress-ingress-nginx-controller }
    patch: |-
      - op: add
        path: /spec/template/metadata/annotations/example.com~1team
        value: platform
kubectl kustomize --enable-helm overlays/prod | kubectl apply -f -

Common mistakes

  • Turning an in-house chart into a maze of if blocks for every possible option.
  • Forking a vendor chart instead of patching its output.
  • Duplicating whole manifests per environment instead of overlays.
  • Forgetting that Kustomize's Helm support needs --enable-helm.

How to answer in the interview

"Helm is a package manager: a chart has Go templates and default values, you install it as a versioned release with your own values, and Helm tracks upgrades and rollbacks, which makes it ideal for distributing software. Kustomize has no templating; you keep plain YAML in a base and overlays apply patches, image tags, replicas and labels per environment, which is very readable. I combine them by using Helm for third-party charts and patching the rendered output with Kustomize, through the helmCharts field or a post-renderer, while our own apps use Kustomize overlays or one simple internal chart."

Likely follow-up questions

  • What makes a Helm chart hard to maintain? Excessive conditionals and values, deep helper nesting, and no tests or schema for values.
  • Does Argo CD keep Helm release history? No; it renders with helm template and applies, so rollback goes through Git.
  • How do you validate values? A values.schema.json in the chart.
