How do you improve MCP server performance and latency for interactive agents?

MCP Servers · concept · levels mid, senior

In one line

Every tool call adds latency to every agent step, so measure per tool, cache tool lists and slow-changing data with TTL hints, pool downstream connections, combine multi-step operations into one tool, stream progress for slow work, and deploy near the host and its dependencies.

Detailed explanation

Interactive agents run in loops: think, call a tool, read the result, think again. A tool that takes two seconds called eight times in a task adds sixteen seconds, and slow tools have second-order effects: models may time out, retry, or switch to a worse approach. Performance work therefore starts with per-tool latency measurement, broken down into server processing and downstream dependency time.

Caching is the cheapest win. Tool lists rarely change, so clients should not re-fetch them every turn; newer protocol revisions add caching hints such as a TTL on list results so clients know how long they are valid. On the server side, cache expensive lookups such as schemas, catalogs or permission checks.

Connection management matters because many servers create a new HTTP client per call. Use connection pooling and keep-alive to downstream APIs and databases.

Tool design often has the biggest impact. A model round trip (the model reading results and deciding the next call) usually costs more than the API call itself, often a second or more. A single get_order_with_shipping_status tool beats three chained low-level tools. Returning compact results also reduces tokens the model must read.

For unavoidably slow operations, send progress notifications or use tasks so the client is not left waiting blindly. Finally, place the server in the same region as the host and the systems it calls.

How it works

  1. Trace a realistic task and attribute time to model calls, MCP calls and downstream calls.
  2. Cache static data (tool lists, schemas) with explicit TTLs; cache expensive reads server-side.
  3. Reuse pooled HTTP and database connections.
  4. Merge chained calls into task-level tools; trim result payloads.
  5. Use progress notifications or tasks for operations over a few seconds.
  6. Co-locate server, host and downstream systems; re-measure.

Example

import httpx
from cachetools import TTLCache

http = httpx.AsyncClient(timeout=5.0, limits=httpx.Limits(max_keepalive_connections=50))
schema_cache = TTLCache(maxsize=256, ttl=3600)

async def get_order_overview(order_id: str):
    # one tool instead of get_order + get_shipment + get_invoice
    order, shipment, invoice = await asyncio.gather(
        http.get(f"{ORDERS}/orders/{order_id}"),
        http.get(f"{SHIPPING}/shipments?order={order_id}"),
        http.get(f"{BILLING}/invoices?order={order_id}"),
    )
    return summarise(order.json(), shipment.json(), invoice.json())

Common mistakes

  • Optimising server CPU while model round trips dominate total task time.
  • Returning huge JSON payloads that slow the next model call.
  • Creating a new client or database connection per tool call.
  • Blocking silently for 60 seconds, so the host times out and retries.

How to answer in the interview

"Agents call tools in loops, so every extra second multiplies, and slow tools make models retry or give up. I start by measuring latency per tool and per downstream dependency. Then caching: tool lists and slow-changing data like schemas are cached with TTL hints, and the server caches expensive lookups. Downstream calls use connection pooling. The biggest win is usually tool design: combining a multi-step operation into one tool removes model round trips, which are typically slower than the API calls. For slow operations I stream progress or use tasks rather than blocking. And I deploy the server in the same region as the host and the systems it calls."

Likely follow-up questions

  • Why do model round trips dominate? Each one means generating and reading tokens, typically hundreds of milliseconds to seconds.
  • How big should results be? As small as the task needs; paginate or summarise large data.
  • Parallel tool calls? Many hosts let models issue independent calls in parallel, which helps if the server handles concurrency.
