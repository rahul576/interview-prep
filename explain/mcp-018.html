What changed architecturally in the 2026-07-28 MCP revision?

MCP Servers · concept · levels senior, lead

In one line

The 2026-07-28 revision makes the core stateless: no initialize handshake or Mcp-Session-Id; version and capabilities travel in each request's _meta, a discovery method exposes support up front, servers no longer send requests to clients (using input-required results instead), and Tasks, MCP Apps and other features move to extensions under a formal feature lifecycle.

Detailed explanation

Earlier revisions were connection-oriented: a handshake negotiated capabilities, HTTP servers could keep sessions, and servers could send requests back to clients (sampling, elicitation, roots). That made remote servers awkward to scale: sessions pinned clients to replicas, and bidirectional requests required long-lived streams. According to the reference material for this question, the 2026-07-28 revision restructures the protocol around statelessness.

No handshake, no sessions. The initialize/initialized exchange and the Mcp-Session-Id header are removed. Instead, each request carries its protocol version and the client capabilities relevant to it in request metadata (the _meta field). A discovery method lets clients check supported versions and server capabilities in advance, and its results can be cached. Any replica can serve any request, so servers scale horizontally behind ordinary load balancers and suit serverless platforms.

No server-to-client requests. When a server needs more input mid-operation, it returns an input-required result describing what it needs; the client gathers the answer (for example from the user) and retries the request with the answers. This pattern is called multi round-trip requests. Change notifications such as list changes move to a long-lived subscription stream that clients open when they want them.

Extensions and lifecycle. Tasks for long-running work moves from core to an official extension. An extensions framework lets optional features, including MCP Apps for interactive interfaces, evolve outside the core and be negotiated via capabilities. A feature lifecycle (active, deprecated, removed) with minimum deprecation windows governs change; sampling, roots and logging are deprecated.

Consequence for server authors: state must be explicit, via handles stored server-side and passed as tool arguments, and side-effecting tools must be idempotent, since dropped requests are simply re-issued.

How it works

  1. Client optionally calls discovery and caches versions and capabilities.
  2. Each request includes _meta with protocol version and client capabilities.
  3. Server processes it independently on any replica.
  4. If input is needed, server returns input-required; client retries with answers.
  5. Clients wanting notifications open a subscription stream.

Example

{"jsonrpc":"2.0","id":"r-91","method":"tools/call","params":{
  "name":"deploy_service","arguments":{"service":"checkout"},
  "_meta":{"protocolVersion":"2026-07-28","clientCapabilities":{"elicitation":{}}}}}

Common mistakes

  • Keeping per-connection in-memory state and expecting it to survive.
  • Non-idempotent write tools in a world of re-issued requests.
  • Assuming every client supports the new revision immediately.
  • Treating deprecated features as removed.

How to answer in the interview

"The 2026-07-28 revision makes the core stateless. The initialize handshake and Mcp-Session-Id are gone; each request carries its protocol version and client capabilities in _meta, and there's a discovery method to check support up front. Without sessions, any replica can handle any request, so remote servers scale behind ordinary load balancers. Servers no longer send requests to clients; if they need input they return an input-required result and the client retries with the answers. Notifications move to a subscription stream. Tasks became an official extension, alongside an extensions framework, MCP Apps, and a formal feature lifecycle with deprecation windows."

Likely follow-up questions

  • How does a server keep state without sessions? Explicit handles returned by tools and stored in a database or cache.
  • What happens to old clients? Servers can support older versions; clients negotiate or fall back.
  • Why remove server-to-client requests? They needed long-lived bidirectional channels, which hurt scaling and simplicity.
