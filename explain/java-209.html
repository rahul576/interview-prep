Why should you use BigDecimal for money, and what are its pitfalls?

Core Java & OOP · concept · levels entry, mid

In one line

Use BigDecimal (or integer minor units) for money because binary floating point cannot represent most decimal fractions exactly; its pitfalls are constructing from double, missing scale and RoundingMode on division, and equals comparing scale.

Detailed explanation

double and float are IEEE 754 binary floating-point numbers. Values like 0.1 or 0.2 have no exact binary representation, so 0.1 + 0.2 gives 0.30000000000000004. Over thousands of transactions, interest calculations or currency conversions, these tiny errors accumulate and produce totals that do not reconcile, which is unacceptable in finance, billing and tax.

BigDecimal represents a number as an arbitrary-precision unscaled integer plus a scale (digits after the decimal point), so 12.34 is exactly 1234 × 10^-2. Arithmetic is exact for addition, subtraction and multiplication, and you control rounding explicitly.

The pitfalls:

  • Constructor from double: new BigDecimal(0.1) captures the binary error (0.1000000000000000055511...). Use new BigDecimal("0.10") or BigDecimal.valueOf(0.1), which goes through the double's shortest string form.
  • Division: a.divide(b) throws ArithmeticException for non-terminating results like 1/3. Always pass a scale and RoundingMode, or a MathContext. Finance usually uses HALF_EVEN (banker's rounding) or what the regulator specifies, and rounds at defined points, not after every step.
  • equals vs compareTo: new BigDecimal("2.0").equals(new BigDecimal("2.00")) is false because scale differs; compareTo returns 0. This also affects HashSet and HashMap keys; normalise with setScale or stripTrailingZeros.
  • Immutability: amount.add(x) returns a new object; forgetting to assign the result is a common bug.
  • Performance: slower than primitives; usually irrelevant, but for very high volume, storing minor units in a long (paise, cents) is a common alternative, with the currency's minor-unit count from java.util.Currency.

In databases use NUMERIC/DECIMAL(19,4)-style columns, not FLOAT, and carry the currency alongside the amount (a Money value object or the JSR 354 Moneta library).

How it works

  1. Parse amounts from strings or integer minor units.
  2. Add, subtract and multiply exactly.
  3. Divide or apply percentages with an explicit scale and rounding mode.
  4. Round to the currency's scale at defined business points.
  5. Compare with compareTo, persist as DECIMAL.

Example

BigDecimal price = new BigDecimal("199.99");
BigDecimal gst   = price.multiply(new BigDecimal("0.18"))
                        .setScale(2, RoundingMode.HALF_EVEN);       // 36.00

// Split 100 rupees among 3 fairly
BigDecimal total = new BigDecimal("100.00");
BigDecimal share = total.divide(BigDecimal.valueOf(3), 2, RoundingMode.DOWN); // 33.33
BigDecimal remainder = total.subtract(share.multiply(BigDecimal.valueOf(3)));  // 0.01
// give the extra paisa to the first person: 33.34, 33.33, 33.33

Common mistakes

  • new BigDecimal(0.1) instead of the String constructor or valueOf.
  • divide without a rounding mode.
  • Using equals to compare amounts.
  • Rounding intermediate results too early, or never rounding at all.
  • Storing money as double in entities or FLOAT in SQL.

How to answer in the interview

"Double is binary floating point, so 0.1 can't be represented exactly and sums drift, which is unacceptable for money. BigDecimal stores an unscaled integer plus a scale, so decimal arithmetic is exact. The pitfalls are: create it from a String or valueOf, never new BigDecimal of a double; division needs an explicit scale and rounding mode like HALF_EVEN or it can throw; and equals compares scale, so 2.0 and 2.00 aren't equal, so I use compareTo. An alternative for high volume is storing minor units as a long, like paise. When splitting amounts I allocate the remainder explicitly so the parts always add up."

Likely follow-up questions

  • How would you split 100 rupees among three people fairly? Floor each share to 33.33 and distribute the leftover paisa deterministically.
  • What is HALF_EVEN? Rounds ties to the nearest even digit, reducing cumulative bias.
  • What SQL type do you use? DECIMAL/NUMERIC with fixed precision and scale.
