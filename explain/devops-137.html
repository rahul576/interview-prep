An application cannot connect to a database on another host. How do you troubleshoot network connectivity?

Networking · scenario · levels mid, senior

In one line

Work up the layers: confirm DNS resolves correctly, test TCP reachability to the port (timeout points to firewalls, security groups or routing, refused points to nothing listening), check the server is listening on the right interface, then look at TLS and authentication if the connection succeeds.

Detailed explanation

Start by reading the exact error from the application; it often tells you the layer ("could not translate host name", "connection timed out", "connection refused", "SSL error", "password authentication failed").

DNS: run dig or nslookup from the app host (or pod) to check the hostname resolves, and to the expected IP: private versus public address, stale record after a migration, split-horizon zones.

Reachability: nc -vz host 5432 or curl -v telnet://host:5432. The result type matters:

  • Timeout: packets are being silently dropped: a security group, NSG, NACL, host firewall, missing route, unpeered VPC, or the host is down.
  • Connection refused: the host answered with a TCP RST: reachable, but no process listens on that port/interface, or a firewall actively rejects.
  • No route to host: routing or ARP issue, or an ICMP reject.

Server side: ss -tlnp shows whether PostgreSQL listens on 0.0.0.0:5432 or only 127.0.0.1:5432 (listen_addresses, bind-address for MySQL). Check the host firewall (nft list ruleset, ufw status) and DB access rules such as PostgreSQL's pg_hba.conf.

Network path: in the cloud check security group inbound rules (source = app's SG or CIDR), NACLs (stateless, so ephemeral return ports too), route tables, VPC peering or transit gateway routes, and private endpoints. Tools such as AWS Reachability Analyzer or Azure Network Watcher help, as do VPC flow logs (REJECT entries).

Above TCP: if the TCP connection succeeds, the problem is TLS (certificate, required SSL mode), authentication, database name, connection limits (max_connections) or the app's connection pool. App and DB logs show these.

How it works

  1. Read the error message and identify the layer.
  2. Resolve the hostname from the client host.
  3. Test the TCP port from the client.
  4. On the server, check listening address and local firewall.
  5. Check cloud firewalls, routes and flow logs.
  6. If TCP works, check TLS, credentials and DB logs.

Example

# from the app host or pod
dig +short db.internal.example.com
nc -vz -w 3 db.internal.example.com 5432
# on the DB host
ss -tlnp | grep 5432
sudo grep -E "^listen_addresses" /etc/postgresql/16/main/postgresql.conf
# once TCP works
psql "host=db.internal.example.com dbname=app user=app sslmode=require" -c "select 1"

Common mistakes

  • Using ping as proof; ICMP is often blocked.
  • Testing from your laptop instead of the app's actual network location.
  • Forgetting that NACLs need return-traffic rules.
  • Looking at network rules when the error is really authentication.

How to answer in the interview

"I work up the layers. First DNS: does the name resolve to the expected IP from the app host. Then I test the port with nc or curl. A timeout usually means something drops traffic: a security group, NSG, firewall or missing route. Connection refused means the host is reachable but nothing listens, so I check on the server with ss that the database listens on the right interface, not only localhost. I check routing and peering between networks and flow logs. If TCP connects, the problem is higher up, like TLS or credentials, which the app and database logs show."

Likely follow-up questions

  • Timeout versus refused? Timeout means packets are dropped silently; refused means a TCP RST came back, so the host is reachable but the port is closed.
  • Why does it work from one subnet but not another? Different route tables, NACLs or security group sources.
  • What are VPC flow logs useful for? Showing whether traffic was accepted or rejected at the network interface.
