When should you use a framework like LangChain, LlamaIndex or LangChain4j instead of calling a provider SDK directly?

LLMOps & RAG · concept · levels mid, senior

In one line

Use frameworks (LangChain, LlamaIndex, LangChain4j, Spring AI) for fast prototyping and ready-made integrations such as loaders, splitters, vector stores, agents and memory; prefer direct provider SDKs when you need control, transparency, fewer dependencies and easy tuning, since abstractions can hide prompts and frameworks change quickly; often prototype with a framework and keep core paths simple.

Detailed explanation

What frameworks give you. LangChain (Python/TypeScript) and LangGraph for agent workflows; LlamaIndex, strongest for data ingestion, indexing and retrieval; LangChain4j and Spring AI for Java. They provide document loaders, text splitters, dozens of vector store and model integrations, retrieval chains, tool calling, memory, output parsers and tracing hooks. For a prototype or proof of concept, you can wire a RAG pipeline in an afternoon, and connectors for obscure sources save real effort.

The costs.

  • Hidden behaviour. Chains may construct prompts you never see, add extra LLM calls (query rewriting, compression), or truncate context silently. Debugging requires digging into framework internals.
  • Dependencies and churn. Large dependency trees, frequent releases and historically many breaking changes or deprecations; upgrades can become projects.
  • Abstraction lag. New provider features (prompt caching options, citations, new tool types, reasoning settings) appear in SDKs first; frameworks follow later or expose them awkwardly.
  • Performance tuning is harder when you don't control batching, concurrency and retries.

Direct SDKs. Modern provider SDKs already support streaming, tool use, structured outputs and retries well. Calling them directly gives full control and transparency over exactly what is sent, fewer dependencies and easier performance work. A RAG pipeline is not much code: embed, search, build prompt, call model.

Pragmatic approach. Prototype with a framework to learn quickly. For production, keep framework parts that add real value (loaders, splitters, a vector store client, or LangGraph for complex stateful agents) and implement core request paths with direct SDK calls behind your own small interface, which also keeps provider switching possible. Instrument everything so prompts are visible regardless.

How it works

  1. Prototype with a framework; measure quality.
  2. Identify which components add value vs obscure behaviour.
  3. Implement the hot path directly with SDKs behind an interface.
  4. Keep useful framework utilities (ingestion, parsers).
  5. Pin versions; trace actual prompts.

Example

# Direct SDK RAG core: everything sent is visible
import anthropic
client = anthropic.Anthropic()

def answer(question: str) -> str:
    chunks = search(question, top_k=5)
    context = "\n\n".join(f"[S{i}] {c.text}" for i, c in enumerate(chunks, 1))
    msg = client.messages.create(
        model=MODEL_ID,
        max_tokens=600,
        system="Answer only from the sources. Cite as [S1].",
        messages=[{"role": "user", "content": f"{context}\n\nQuestion: {question}"}],
    )
    return msg.content[0].text

Common mistakes

  • Adopting a heavy framework for a single API call.
  • Shipping prototypes with framework defaults no one has inspected.
  • Not pinning framework versions.
  • Rewriting everything from scratch when a framework's loaders would do.

How to answer in the interview

"Frameworks like LangChain, LlamaIndex, LangChain4j and Spring AI give abstractions for loaders, splitters, vector stores, agents and memory, which make prototyping fast and provide many connectors; LlamaIndex is particularly good for ingestion and retrieval. The downside is that abstractions can hide prompts and extra calls, add many dependencies and change quickly. Direct SDKs give full control and transparency, and modern SDKs handle tools, structured output and streaming well. I usually prototype with a framework, keep the parts that add real value, and move core paths to direct SDK calls behind our own small interface."

Likely follow-up questions

  • What to keep from a framework? Loaders, splitters, vector store clients, possibly graph-based agent orchestration.
  • Java choice? Spring AI for Spring Boot apps; LangChain4j for broader feature sets or non-Spring apps.
  • Provider lock-in? A thin internal interface or gateway, not necessarily a framework.
