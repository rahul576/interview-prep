Which identities does an AKS cluster use, and how does it pull images from ACR?

Azure Kubernetes (AKS) · concept · levels mid, senior

In one line

An AKS cluster uses a cluster (control plane) identity to manage Azure resources like load balancers and disks, a kubelet identity on nodes to pull images from ACR (granted AcrPull, which --attach-acr does for you), and applications use separate workload identities; prefer user-assigned identities with least privilege.

Detailed explanation

Cluster identity: AKS acts on your behalf when you create a LoadBalancer Service, a PVC or a public IP. It needs rights on the node resource group (MC_...), and with custom networking Network Contributor on the subnet or VNet, plus rights on any private DNS zone or route table you bring. In the past a service principal was used; today it is a managed identity, system-assigned or user-assigned.

Kubelet identity: a managed identity assigned to the node VM Scale Sets. The kubelet uses it to pull images. Granting AcrPull on the registry to this identity lets every node pull without image pull secrets. az aks update --attach-acr myacr creates that role assignment automatically (you need Owner or User Access Administrator rights on the registry to do so).

Neither identity is for applications. Any pod on a node could potentially reach the node identity through the instance metadata endpoint, so giving the kubelet identity rights to Key Vault, Storage or databases effectively gives those rights to every workload on the cluster. Applications use workload identities: a user-assigned managed identity federated with a Kubernetes service account via the cluster's OIDC issuer, each holding only the permissions that application needs.

User-assigned identities for the cluster and kubelet are preferable: you create them and their role assignments before the cluster (for example in Terraform), and they survive cluster recreation, so a rebuilt cluster can pull images immediately. When bringing your own kubelet identity, the cluster identity needs Managed Identity Operator on it.

How it works

  1. Create user-assigned identities for control plane and kubelet.
  2. Grant control plane identity Network Contributor on the subnet.
  3. Grant kubelet identity AcrPull on ACR.
  4. Create the cluster referencing both identities.
  5. Create workload identities per app with federated credentials.

Example

az identity create -g rg-id -n id-aks-cp
az identity create -g rg-id -n id-aks-kubelet
az role assignment create --assignee $KUBELET_PRINCIPAL_ID --role AcrPull --scope $ACR_ID

az aks create -g rg-apps -n aks-prod \
  --assign-identity $CP_ID --assign-kubelet-identity $KUBELET_ID \
  --enable-oidc-issuer --enable-workload-identity

az aks check-acr -g rg-apps -n aks-prod --acr myacr.azurecr.io

Common mistakes

  • Granting the kubelet identity Key Vault or Storage access for apps.
  • Using system-assigned identities and losing role assignments on rebuild.
  • Image pull secrets with admin ACR credentials instead of AcrPull.
  • Forgetting Network Contributor on a custom subnet, breaking load balancers.

How to answer in the interview

"There are two platform identities. The cluster identity lets AKS manage Azure resources like load balancers, public IPs and disks, so it needs rights on the node resource group and subnet. The kubelet identity is on the nodes and pulls images, so I give it AcrPull, which attach-acr does automatically. Applications never use those; they get workload identities federated with service accounts, each with least privilege. I use user-assigned identities so role assignments exist before the cluster and survive recreation."

Likely follow-up questions

  • Why is a broad kubelet identity risky? Any pod on the node can potentially use it, so it becomes cluster-wide access.
  • How do you debug pull failures? az aks check-acr, events with ErrImagePull, and checking network access to ACR.
  • Private ACR? Use a private endpoint and DNS resolution from the node subnet.
