How do Terraform version constraints work, and which ones do you use for Terraform, providers and modules?

Terraform · concept · levels entry, mid, senior

In one line

Constraints use =, !=, >=, <= and the pessimistic ~>, which lets only the rightmost specified part increase; set required_version for Terraform, required_providers with source and version in root modules, looser minimums in reusable modules, and rely on the lock file for exact reproducibility.

Detailed explanation

A version constraint defines the allowed range; the .terraform.lock.hcl file records the exact selected provider versions and hashes. Both matter: constraints control upgrades, the lock file makes every run identical.

Operators: = 1.14.0 exact, != 5.31.0 exclude a known broken release, >= 4.0, < 5.0 a range. The pessimistic operator ~> is the most used: ~> 5.40 allows 5.40 up to any 5.x but not 6.0; ~> 5.40.1 allows only patch releases 5.40.x. Major versions often contain breaking changes (AzureRM 3 to 4, AWS 5 to 6), so blocking them by default is sensible.

Where to put them:

  • Root configurations (what you apply): required_version for the Terraform CLI, such as ~> 1.14.0 or >= 1.14, < 2.0, and required_providers with the full source address (hashicorp/azurerm) and a constraint like ~> 4.10. Commit the lock file.
  • Reusable modules: declare only minimum versions they need (>= 4.0) and avoid tight upper bounds, because Terraform must find one provider version satisfying every module in the tree. A module pinned to ~> 4.10.0 blocks all consumers from upgrading.
  • Module versions use the same syntax in module blocks for registry sources; Git sources use ?ref=v1.2.0 tags.

Upgrades are then deliberate: change constraints if needed, run terraform init -upgrade, review the lock file diff and plan.

How it works

  1. Terraform collects constraints from root and all child modules.
  2. It intersects them for each provider.
  3. If a lock file exists, it uses the locked version if it satisfies the constraints.
  4. Otherwise, or with -upgrade, it selects the newest matching version.
  5. It records the version and hashes in the lock file.

Example

terraform {
  required_version = "~> 1.14.0"
  required_providers {
    azurerm = {
      source  = "hashicorp/azurerm"
      version = "~> 4.10"
    }
    random = {
      source  = "hashicorp/random"
      version = ">= 3.6"
    }
  }
}

module "network" {
  source  = "app.terraform.io/acme/network/azurerm"
  version = "~> 2.3"
}

Common mistakes

  • Tight upper bounds in shared modules causing unsolvable constraint conflicts.
  • No lock file committed, so "the same code" uses different providers.
  • Unbounded >= in root modules, silently pulling a new major version.
  • Forgetting the source address and getting the wrong provider namespace.

How to answer in the interview

"Constraints use =, not-equals, ranges and the pessimistic operator, which lets only the rightmost part increase: tilde-greater 5.40 allows any 5.x from 5.40 but not 6.0. In root modules I set required_version for Terraform and required_providers with the source and a pessimistic constraint like 4.10 for azurerm. Reusable modules only declare minimums so they don't block consumers. The lock file, which I commit, pins the exact versions; constraints just define the allowed upgrade range."

Likely follow-up questions

  • Why avoid upper bounds in modules? All modules must agree on one provider version; tight bounds create conflicts.
  • How do you upgrade? init -upgrade, review lock diff and plans, usually via Renovate PRs.
  • Do module versions get locked? No, only providers are in the lock file; pin module versions explicitly.
