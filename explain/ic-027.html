What is privilege escalation (become) in Ansible?

Configuration Management · concept · levels entry

In one line

become runs tasks as another user, usually root via sudo; set it per play or task, change the target with become_user and the mechanism with become_method, supply passwords via --ask-become-pass or vault, and apply least privilege.

Detailed explanation

Ansible connects over SSH as a normal, unprivileged user, which is good security practice: no root SSH logins. Many tasks still need elevated rights: installing packages, editing files in /etc, managing services. Privilege escalation handles this.

become: true on a play, block or task makes Ansible run the module through sudo as root by default. become_user changes the target user, for example postgres to run psql commands or app to deploy files as the application user. become_method changes the mechanism: sudo (default), su, doas, pbrun, runas on Windows and others. These can also be set in the inventory or ansible.cfg, or with --become/-b on the command line.

If sudo requires a password, provide it with --ask-become-pass (-K), or store ansible_become_password encrypted with Vault per host or group. For automation accounts, a sudoers rule that allows NOPASSWD is common; ideally restricted to what automation needs, though in practice Ansible executes temporary Python modules, so tightly restricting commands is hard and the automation account effectively has broad rights. Protecting that account's SSH keys and auditing its use is therefore important.

Following least privilege, escalate only the tasks that need it rather than putting become: true on everything. Files created by escalated tasks are owned by the become user (often root) unless you set owner/group/mode explicitly. Becoming an unprivileged user from another unprivileged user involves temporary file permission problems; Ansible handles this with POSIX ACLs (setfacl) where available, or configuration options otherwise.

How it works

  1. Ansible connects as ansible_user via SSH.
  2. For tasks with become, it wraps the module command with the become method.
  3. sudo prompts are answered with the become password if needed.
  4. The module runs as become_user.
  5. Results return over the same connection.

Example

- hosts: db
  become: false
  tasks:
    - name: Install PostgreSQL (needs root)
      ansible.builtin.package:
        name: postgresql
      become: true

    - name: Create application database as postgres user
      community.postgresql.postgresql_db:
        name: orders
      become: true
      become_user: postgres

    - name: Deploy config owned by app
      ansible.builtin.template:
        src: app.conf.j2
        dest: /etc/app/app.conf
        owner: app
        group: app
        mode: "0640"
      become: true
ansible-playbook site.yml -K          # prompts for sudo password

Common mistakes

  • become: true on every play by habit.
  • Forgetting owner/group, leaving root-owned files the app cannot read.
  • Storing the become password in plain text in inventory.
  • Allowing root SSH login instead of using become.

How to answer in the interview

"Ansible connects over SSH as a normal user, and become escalates privileges for tasks that need it, by default with sudo to root. I can set become: true for a play or just specific tasks, change the target with become_user, for example the postgres user for database commands, and change the mechanism with become_method, like su or doas. If sudo needs a password I use --ask-become-pass or a vaulted variable; automation users often have a dedicated sudoers rule. I follow least privilege and only escalate the tasks that need it, and set owner and mode explicitly on files."

Likely follow-up questions

  • Why might a file created with become end up owned by root? The task ran as root; set owner/group or use become_user.
  • become vs remote_user? remote_user is who you log in as; become_user is who you act as afterwards.
  • How do you escalate on Windows? become_method: runas.
