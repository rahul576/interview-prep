Compare online, real-time inference with batch inference. How do you choose?

MLOps · concept · levels entry, mid, senior

In one line

Online (real-time) inference scores each request as it arrives behind an API within a tight latency budget; batch inference scores many records on a schedule and stores the results. Choose by how fresh the prediction must be, whether the input only exists at request time, and the latency and cost budget, with streaming inference as a middle ground.

Detailed explanation

With online inference, a client calls a REST or gRPC endpoint and waits for the answer, typically within tens of milliseconds. Fraud checks during payment, search ranking and recommendations on a page work this way. The system needs fresh features at request time (often from an online feature store), scalable serving with autoscaling, high availability, and careful latency engineering. Every millisecond and every replica costs money, and failures are user-visible.

With batch inference, a scheduled job scores a large set of entities, for example nightly churn scores for every customer, and writes them to a table or key-value store that applications read. It is cheaper and simpler: large compute is used efficiently, jobs are easy to retry, and nothing is on the user's critical path. The price is staleness: predictions can be hours old, and you can only score entities you know about in advance.

The deciding questions are: how quickly does the world change relative to the decision, and does the key input exist only at request time (the basket contents, the transaction amount, the search query)? If decisions can wait or inputs change slowly, batch wins. Streaming inference consumes events from Kafka or Kinesis and scores them within seconds, giving near-real-time freshness without a synchronous API. Many production systems are hybrids: heavy scores precomputed in batch, combined with a light real-time adjustment.

How it works

  1. Define the decision, its latency budget and how stale a prediction may be.
  2. Check whether essential inputs are known in advance or only at request time.
  3. For batch: schedule a job, score all entities, write results with model version, serve by lookup.
  4. For online: deploy an endpoint, fetch online features, score per request, autoscale on traffic.
  5. For streaming: consume events, score them, publish results to a topic or store.
  6. Monitor latency (online) or freshness and job completion (batch).

Example

A retailer precomputes nightly "propensity to buy" scores per customer, but adjusts ranking with the live session:

# batch: nightly job writes customer_id -> base_score to Redis
base = redis.hget("propensity", customer_id) or DEFAULT_SCORE

# online: light model combines base score with request-time context
features = {"base": float(base), "cart_value": cart.total, "items_viewed": session.views}
score = realtime_model.predict([list(features.values())])[0]

Common mistakes

  • Building a real-time endpoint when a nightly table would meet the business need.
  • Batch-scoring decisions that depend on request-time inputs, so predictions ignore the most important signal.
  • Forgetting a default for entities missing from the batch output (new customers).
  • Not storing the model version and scoring time with batch results.

How to answer in the interview

"Online inference scores each request synchronously behind an API, usually within tens of milliseconds, so it needs fresh features, autoscaling and high availability; fraud checks at payment are the classic case. Batch inference scores everything on a schedule and writes results to a table, which is much cheaper and easier to retry, but the predictions can be hours old. I choose by asking how fresh the prediction must be and whether the key input only exists at request time. If the decision can wait, batch wins. Streaming inference from Kafka sits in between, and I often combine a batch base score with a small real-time adjustment."

Likely follow-up questions

  • How do you serve a batch-scored model that needs some real-time context? Look up the precomputed score and combine it with request-time features in a lightweight online model or rule layer.
  • What happens to new entities in batch scoring? Use a fallback score or trigger on-demand online scoring.
  • How do you monitor batch inference? Job success, freshness SLAs, row counts and score distribution per run.
