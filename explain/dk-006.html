What is the difference between docker exec and docker attach?

Docker · concept · levels entry

In one line

docker exec starts a new, additional process inside a running container (e.g. docker exec -it web sh), leaving the main process untouched; docker attach connects your terminal to the main process (PID 1) streams, where Ctrl+C can stop the container and Ctrl+P Ctrl+Q detaches safely.

Detailed explanation

docker exec asks the runtime to launch another process in the same namespaces and cgroups as the running container: same filesystem, network, environment (plus anything you add with -e) and user (override with -u). Typical uses are a debugging shell (docker exec -it web sh) or a one-off client command (docker exec db psql -U app). When the exec'd process ends, nothing happens to the container; the main process keeps running. You can only exec into a running container.

docker attach does not create anything. It connects your terminal's stdin, stdout and stderr to the container's main process, the one started by docker run. You see exactly what that process prints and your keystrokes go to it. That matters: pressing Ctrl+C sends SIGINT to PID 1 (with the default signal proxying), and if it exits, the container stops. To leave without stopping, use the detach sequence Ctrl+P, Ctrl+Q, which works when the container was started with -it (customisable with --detach-keys).

For debugging, exec is almost always what you want; attach is mainly useful for interactive programs started as the main process, like a REPL or a console-based app.

Minimal images (distroless, scratch) contain no shell, so docker exec … sh fails. Alternatives: docker debug in recent Docker Desktop versions, running a tools container that shares the target's namespaces (docker run --pid container:web --network container:web nicolaka/netshoot), or kubectl debug with an ephemeral container in Kubernetes.

How it works

  1. exec: runtime spawns process → joins container namespaces → runs → exits independently.
  2. attach: client connects to existing PID 1 streams via the daemon.
  3. Detach keys disconnect the client without signalling the process.

Example

docker run -d --name web nginx:1.27
docker exec -it web sh              # new shell; exit leaves nginx running
docker exec web nginx -t            # validate config
docker exec -e DEBUG=1 -u 0 web env | grep DEBUG
docker attach web                   # see nginx's stdout; Ctrl+C would stop it
docker run --rm -it --network container:web --pid container:web nicolaka/netshoot

Common mistakes

  • Using attach to "get a shell" and killing the service with Ctrl+C.
  • Making manual fixes via exec in production that disappear on the next deploy.
  • Expecting exec to work on a stopped container.

How to answer in the interview

"docker exec starts a new process inside an already running container, like docker exec -it web sh for a shell or docker exec db psql to run a client; when I leave, the container keeps running. docker attach doesn't start anything; it connects my terminal to the container's main process, PID 1. Ctrl+C there goes to the main process and may stop the container, while Ctrl+P then Ctrl+Q detaches safely if it was started with a terminal. For debugging I almost always use exec, and for images without a shell I use a debug container that shares the target's namespaces."

Likely follow-up questions

  • No shell in the image? docker debug, a sidecar tools container sharing namespaces, or kubectl debug.
  • Run exec as root? docker exec -u 0, if the runtime allows it.
  • Can you exec into a stopped container? No; start it or docker cp files out.
