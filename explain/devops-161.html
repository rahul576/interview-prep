What strategies help with large monorepos in Git and CI?

Git · concept · levels mid, senior

In one line

Large monorepos stay fast with partial, shallow and sparse clones, affected-only builds using graph-aware tools (Bazel, Nx, Gradle, Turborepo) with remote caching, CODEOWNERS for ownership, Git LFS for big binaries and clear module boundaries.

Detailed explanation

A monorepo makes atomic cross-project changes and shared tooling easy, but at scale two things get slow: Git itself and CI.

On the Git side, shallow clone (--depth 1) fetches only recent history, fine for CI jobs that just build. Partial clone (--filter=blob:none) fetches file contents lazily, so developers keep history without downloading every blob. Sparse checkout materialises only the directories you work on. core.fsmonitor, the commit-graph and git maintenance (bundled by scalar) keep status fast. Git LFS keeps large binaries out of normal history, where every version would bloat every clone forever.

On the CI side, build only what is affected. Simple setups use path filters (paths: in GitHub Actions, rules: changes: in GitLab). Better, a graph-aware tool such as Bazel, Nx, Turborepo or Gradle computes which projects depend on the changed files and reuses outputs from a remote build cache.

Governance matters too. CODEOWNERS maps directories to teams so the right reviewers are required. Enforced module boundaries (Nx tags, Bazel visibility) stop everything depending on everything, which would make affected-detection useless.

How it works

  1. Developers clone with partial clone and sparse checkout for their area.
  2. CI uses shallow or partial clones and restores build caches.
  3. The build tool diffs against the merge base and computes affected targets.
  4. Only those targets are built and tested, with remote cache hits for the rest.
  5. CODEOWNERS assigns reviewers; boundaries are checked in CI.
  6. Large binaries are stored via LFS.

Example

# Developer setup
git clone --filter=blob:none --sparse https://github.com/acme/platform.git
cd platform
git sparse-checkout set services/payments libs/common

# CI: test only affected projects (Nx)
npx nx affected -t lint test build --base=origin/main --head=HEAD
# .github/CODEOWNERS
/services/payments/  @acme/payments-team
/libs/common/        @acme/platform-team

Common mistakes

  • Running the full build and test suite for every change.
  • Path filters that miss shared library dependencies, so breakages slip through.
  • Committing large binaries directly into Git.
  • No ownership rules, so reviews go to random people or nobody.
  • Shallow clones in jobs that need history (for example changelog or affected detection).

How to answer in the interview

"There are two problems: Git performance and CI time. For Git, partial clone and sparse checkout for developers, shallow clones in CI, and Git LFS for binaries. For CI, build only what changed: path filters at minimum, ideally Nx, Bazel or Gradle computing affected projects with a remote build cache. CODEOWNERS sets ownership per directory, and enforced module boundaries keep the dependency graph clean, which makes affected builds effective."

Likely follow-up questions

  • Monorepo pros and cons? Pros: atomic changes, shared tooling, easy reuse; cons: tooling investment, scale, coarse access control.
  • How does a remote build cache work? Outputs are stored keyed by a hash of inputs; identical inputs anywhere reuse the result.
  • How do you version services in a monorepo? Per-project tags or release tools such as Changesets, with independent deploy pipelines.
