How do you find and fix workloads that use API versions removed in the next Kubernetes release?

Kubernetes · concept · levels mid, senior

In one line

Read the deprecated API migration guide and release notes, scan sources (Git manifests, Helm charts) with pluto or kubent, find actual callers with the apiserver_requested_deprecated_apis metric and audit logs, fix the source, not just live objects, handle Helm release history with helm mapkubeapis, and make the check a CI gate.

Detailed explanation

Kubernetes serves each resource through one or more API versions (v1beta1, v1). Deprecated versions keep working for a period, then are removed in a specific release, after which requests using them fail with "no matches for kind". Examples from history: extensions/v1beta1 Ingress and Deployments (removed 1.16/1.22), policy/v1beta1 PodDisruptionBudget and PodSecurityPolicy (1.25), autoscaling/v2beta2 HPA (1.26), flowcontrol.apiserver.k8s.io/v1beta3 (1.32).

An important subtlety: objects already in etcd are not broken. The API server converts them and serves them through the current version; kubectl get shows them fine. What breaks is anything that sends the old version: a manifest in Git, a Helm chart template, a CI script, an old operator, a Terraform provider. So the work is about sources and clients.

Steps:

  1. Know what's removed in the target version from the official deprecation guide.
  2. Static scanning: pluto detect-files on repositories and rendered Helm or Kustomize output; pluto detect-helm for installed releases; kubent also inspects the cluster.
  3. Runtime evidence: the metric apiserver_requested_deprecated_apis (labels for group, version, resource, removed_release) shows what is still being called; audit logs with the k8s.io/deprecated annotation reveal who called (user agent, service account). Responses also carry a warning header that kubectl prints.
  4. Fix the sources in Git and charts, bump operator and chart versions, redeploy.
  5. Helm releases: Helm stores each release's rendered manifest in a Secret. If it contains a removed API, the next helm upgrade fails because Helm cannot map the old object. The helm mapkubeapis plugin rewrites those stored manifests to supported versions.
  6. Prevent regressions: run pluto or kubeconform with the target version in CI.

How it works

  1. Determine target version's removals.
  2. Scan Git and Helm; list findings.
  3. Check metrics and audit logs for live callers.
  4. Update manifests, charts, operators; redeploy.
  5. Fix Helm history; add CI gate; then upgrade.

Example

pluto detect-files -d ./deploy --target-versions k8s=v1.35.0 -o wide
helm template ./charts/api | pluto detect - --target-versions k8s=v1.35.0
kubectl get --raw /metrics | grep apiserver_requested_deprecated_apis
helm mapkubeapis orders --namespace shop --dry-run
helm mapkubeapis orders --namespace shop
# CI gate (GitHub Actions)
- run: kustomize build overlays/prod | pluto detect - --target-versions k8s=v1.35.0

Common mistakes

  • Checking only live objects with kubectl and declaring victory.
  • Forgetting third-party charts and operators.
  • Discovering the Helm history problem during the production upgrade.
  • No CI check, so old API versions are reintroduced by copy-paste.

How to answer in the interview

"I start from the deprecated API migration guide for the target version. Then I scan the sources, Git manifests and rendered Helm charts, with pluto or kubent, and check what's actually being called with the apiserver_requested_deprecated_apis metric and audit logs, which also catches operators and CI scripts. Live objects are served in the new version by the API server, so the real fix is updating Git and charts. Helm is a special case: stored release manifests with removed APIs break upgrades, and helm mapkubeapis fixes them. Finally I add a CI gate."

Likely follow-up questions

  • How do you prevent new removed-API usage? pluto or kubeconform against the next version in CI, plus policy rules.
  • Why do live objects look fine? The API server stores and serves them through supported versions.
  • Who called the deprecated API? Audit logs with the deprecation annotation and user agent.
