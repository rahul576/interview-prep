What is a multi-stage Docker build, and why use it?

Docker · concept · levels mid, senior

In one line

A multi-stage build uses several FROM stages in one Dockerfile: early stages contain the SDK, compilers and build tools, and the final stage starts from a small runtime image (JRE, slim, distroless) and uses COPY --from to take only the built artifact, giving smaller, faster, more secure images.

Detailed explanation

Before multi-stage builds, teams either shipped the whole JDK, Maven, source code and caches in production images (hundreds of megabytes and many CVEs) or maintained separate "builder" Dockerfiles and shell scripts to copy artifacts between them. Multi-stage builds solve this inside one Dockerfile.

Each FROM starts a new stage, optionally named with AS. A build stage can use a heavy image such as maven:3.9-eclipse-temurin-21 to compile code and run mvn package. The final stage starts fresh from a minimal image like eclipse-temurin:21-jre, an Alpine image or a distroless image, and copies only what's needed with COPY --from=build /src/target/app.jar /app/app.jar. Everything else (compilers, source code, test tools, dependency caches) stays in the discarded stages and never reaches the final image.

Benefits:

  • Size: a Java service can drop from 700+ MB to under 200 MB; a Go binary on scratch or distroless/static can be a few megabytes. Smaller images pull and start faster.
  • Security: fewer packages means a smaller attack surface and fewer CVEs to patch; no build tools for an attacker to use.
  • Simplicity: one Dockerfile, reproducible builds in CI and locally.

With BuildKit, stages the final target does not depend on are skipped, and independent stages run in parallel. You can build a specific stage with --target, for example a test stage in CI that runs unit tests, without producing the runtime image.

How it works

  1. Stage build: full SDK, copy dependency manifest, download dependencies, copy source, compile.
  2. Optional stage test: run tests from the build stage.
  3. Final stage: minimal runtime base, non-root user.
  4. COPY --from=build brings in only the artifact.
  5. Only the final stage's layers are in the pushed image.

Example

FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /src
COPY pom.xml .
RUN mvn -q dependency:go-offline
COPY src ./src
RUN mvn -q package -DskipTests

FROM build AS test
RUN mvn -q test

FROM gcr.io/distroless/java21-debian12:nonroot
COPY --from=build /src/target/app.jar /app/app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
docker build --target test .         # CI: run tests
docker build -t orders:1.4.2 .       # final runtime image

Common mistakes

  • Copying the whole build directory instead of only the artifact.
  • Using the SDK image as the final stage "temporarily".
  • Forgetting runtime dependencies (CA certificates, timezone data, shared libraries) in very minimal bases.
  • Not naming stages, making COPY --from=0 fragile.

How to answer in the interview

"A multi-stage build uses several FROM stages in one Dockerfile. The first stage has everything needed to build, for example Maven and a JDK to run mvn package. The final stage starts from a small runtime image, like a JRE or distroless image, and uses COPY --from=build to take only the jar. Compilers, source, caches and test tools never reach the final image, so it's much smaller, pulls and starts faster, and has a smaller attack surface with fewer CVEs. With BuildKit, independent stages run in parallel, and I can target an intermediate stage with --target test to run tests in CI."

Likely follow-up questions

  • What are distroless images? Images with only the app runtime and its libraries, no shell or package manager; secure but harder to debug.
  • How do you debug a distroless container? Use a :debug variant in test, or attach a debug container sharing its namespaces, or kubectl debug.
  • Can you copy from an external image? Yes, COPY --from=nginx:1.27 /etc/nginx/nginx.conf /tmp/.
