Design a real-time fraud detection system with a tight latency budget.

MLOps · design · levels mid, senior, lead

In one line

Split a tight latency budget (for example 50 to 100 ms) across feature lookup, inference and decision; compute behavioural features from Kafka events with Flink into an online feature store like Redis; serve a lightweight model plus a rules engine; define a fallback when components fail; and close the loop with delayed labels, logging and monitoring.

Detailed explanation

Card authorisation gives the fraud check a small slice of the end-to-end time, so the design starts from the budget. Example: 10 ms for request parsing and enrichment, 15 ms for feature lookups, 15 ms for inference, 10 ms for rules and decision, leaving headroom for p99.

Features come from two sources. Request features are in the payment itself: amount, merchant category, country, device, channel. Behavioural features—spend in the last hour, number of new devices this week, distance from last transaction, merchant risk—are computed continuously from transaction events in Kafka by a streaming engine such as Flink, and written to an online feature store (Redis, Aerospike, or a managed feature store) for single-digit-millisecond lookups. The same definitions produce offline training data, avoiding skew.

The model is usually gradient boosting (XGBoost, LightGBM) or a compact neural network, served in-process or as a nearby service, perhaps via ONNX Runtime. A rules engine sits alongside for hard business rules, regulatory constraints and fast reaction to new attack patterns without retraining. The output is approve, decline or step-up authentication (3-D Secure, OTP) or manual review.

Resilience: if the model or feature store is down or slow, a timeout triggers a fallback—rules only, with an agreed risk appetite—rather than blocking payments.

Feedback loop: every decision is logged with features and model version. Delayed labels (chargebacks, confirmed fraud, analyst decisions) arrive over weeks and feed retraining. Monitoring covers latency, score distribution, decline rates and fraud loss.

How it works

  1. Payment request arrives at the fraud service.
  2. Parallel lookup of behavioural features from the online store.
  3. Model scores request plus features.
  4. Rules engine combines score and rules into a decision.
  5. Decision returned; event and features logged to Kafka.
  6. Labels joined later for training and monitoring.

Example

Budget: 80 ms p99
 Payment API ──► Fraud service ─┬─► Redis feature store (MGET, 5 ms) ◄── Flink ◄── Kafka txns
                                ├─► LightGBM via ONNX Runtime (in-process, 3 ms)
                                └─► Rules engine (2 ms) ─► approve / decline / step-up
 Timeout 60 ms -> fallback: rules only
 Decisions + features ─► Kafka ─► lake ─► labels (chargebacks, 30-90 days) ─► retraining

Common mistakes

  • No explicit latency budget per component.
  • Computing behavioural features with heavy SQL at request time.
  • No fallback, so a feature store outage blocks payments.
  • Training on features computed differently from serving.

How to answer in the interview

"I'd start with the budget, say 50 to 100 ms, split across feature lookup, inference and decision. Request features come with the payment; behavioural features like spend in the last hour are computed continuously from Kafka by Flink into an online store like Redis. A gradient boosting model served in-process scores it, and a rules engine handles hard rules and new attack patterns. If the model or store is unavailable, a rules-only fallback applies. Decisions and features are logged, delayed chargeback labels feed retraining, and we monitor latency, scores and fraud rates."

Likely follow-up questions

  • How do you test a new fraud model safely here? Shadow scoring in the same service, then a canary with guardrails.
  • Why keep a rules engine? Instant reaction to new patterns, explainability and regulatory rules.
  • How do you prevent skew? Same streaming definitions for online and offline features.
