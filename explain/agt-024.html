An agent often picks the wrong tool for a task. What do you change?

AI Agents & AIOps · scenario · levels mid, senior

In one line

Analyse traces to see which tools are confused, then rewrite descriptions with when and when-not-to-use guidance, merge or remove overlapping tools, reduce the tools in context (scoping, tool search or a routing step), add few-shot examples, and measure tool-selection accuracy in evals before and after.

Detailed explanation

Tool selection is a classification problem the model solves from names and descriptions alone. Wrong choices usually mean the descriptions do not give it enough to discriminate, or there are simply too many similar options.

Start with data. From traces, find which tools are confused with which and in what situations, and build a small evaluation set of tasks labelled with the correct tool. This turns "it often picks wrong" into "it picks search_documents instead of search_knowledge in 30 percent of HR policy questions".

Descriptions are the most common fix. Two tools that sound alike need precise scopes: what each does, which data it covers, what it returns, and when not to use it, pointing to the alternative ("for HR policies, use search_policies instead"). Names should be specific: search_hr_policies, not search2.

Overlap: if two tools really do similar things, merge them with a parameter or remove one. Fewer, well-separated tools beat many overlapping ones.

Too many tools degrade selection and consume context. Give each agent only the tools relevant to its role; for large catalogues, use tool search (the model searches for tools and loads definitions on demand, which some providers now support natively) or a routing step that classifies the task and loads the right subset.

Examples: few-shot examples in the system prompt, or usage examples inside tool definitions, showing correct choices for tricky cases help a lot.

Finally, measure tool-selection accuracy and end-to-end task success before and after each change. If complex selection still fails, a stronger model or splitting into specialised agents may be justified.

How it works

  1. Collect traces with wrong tool choices; label correct tools.
  2. Build a tool-selection eval set.
  3. Rewrite names and descriptions; add when-not-to-use guidance.
  4. Merge or remove overlapping tools.
  5. Scope tool sets per agent; add tool search or routing for large sets.
  6. Add few-shot examples; re-run evals and compare.

Example

{
  "before": [
    {"name": "search_documents", "description": "Search documents."},
    {"name": "search_knowledge", "description": "Search the knowledge base."}
  ],
  "after": [
    {"name": "search_hr_policies",
     "description": "Search official HR policies (leave, expenses, travel, benefits). Use for questions about company rules. Do NOT use for product or technical docs; use search_product_docs."},
    {"name": "search_product_docs",
     "description": "Search product manuals, API docs and release notes. Do NOT use for HR or internal policies."}
  ]
}

Tool-selection accuracy on 120 labelled tasks: 71 percent before, 94 percent after.

Common mistakes

  • Adding ever more tools for edge cases.
  • Fixing selection by making the system prompt longer and longer.
  • Generic names like query or helper.
  • No labelled eval set, so changes are judged by impressions.
  • Ignoring that tool definitions themselves consume context.

How to answer in the interview

"First I analyse traces to see which tools get confused and when, and build a small eval set of tasks with the correct tool. Usually descriptions are the issue: two tools sound similar, so I rewrite them to say exactly what each covers and when not to use it, pointing to the alternative, and I make names specific. Overlapping tools are merged or removed. Too many tools in context hurt selection, so each agent only sees what its role needs, with tool search or a routing step for large catalogues. Few-shot examples for tricky cases help. Then I measure selection accuracy before and after every change, and sometimes a stronger model is the answer."

Likely follow-up questions

  • When to split into specialised agents? When tool sets are large and fall into distinct domains with different instructions.
  • What is tool search? The model searches a tool catalogue and loads only relevant tool definitions on demand.
  • Can the model choose no tool? Yes, and descriptions should make clear when answering directly is correct.
