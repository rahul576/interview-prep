How would you add caching to a Spring Boot service using Redis, and how do you keep it consistent?

Caching · concept · levels mid, senior

In one line

Use cache-aside via the Spring Cache abstraction (@Cacheable, @CacheEvict, @CachePut) backed by Redis with a TTL per cache, a JSON serializer and a bounded eviction policy; keep it consistent by updating the DB first then evicting, with short TTLs or event/CDC-driven invalidation, and protect against stampedes.

Detailed explanation

Pattern. With cache-aside, the application reads Redis first; on a miss it loads from the database and populates the cache. Writes go to the database, then the key is deleted rather than updated, which avoids racing writers putting stale values in. If Redis is down, the service degrades to DB speed instead of failing.

Spring setup. Add spring-boot-starter-data-redis and spring-boot-starter-cache, enable @EnableCaching, and configure a RedisCacheManager with:

  • a JSON serializer (GenericJackson2JsonRedisSerializer) instead of JDK serialization, which is fragile and insecure;
  • a TTL per cache (products 10 minutes, exchange rates 1 minute);
  • a key prefix per service and version, so deployments with changed classes don't read incompatible entries.

@Cacheable("products") caches return values; @CacheEvict removes on update/delete; @CachePut writes the new value. Remember these are proxy-based: self-invocation inside the same bean bypasses caching, and @CacheEvict runs after the method by default.

Memory. Set maxmemory and an eviction policy such as allkeys-lru or allkeys-lfu in Redis, so the cache stays bounded.

Consistency. Cache-aside gives eventual consistency: a brief window of staleness exists. Tighten it with:

  • evict after the transaction commits (@TransactionalEventListener(phase = AFTER_COMMIT) or a transaction-aware cache manager), otherwise a reader can repopulate the old value before commit;
  • short TTLs as a safety net;
  • event-driven invalidation via domain events or change data capture (Debezium reading the DB log) when other services write the same data;
  • delayed double delete for hot keys;
  • never cache data that must be strongly consistent (balances at payment time).

Stampede protection. When a hot key expires, many requests hit the DB at once. Use @Cacheable(sync = true) (per-instance coalescing), distributed locks or single-flight refresh, TTL jitter, and stale-while-revalidate or pre-warming for very hot keys. Cache null/not-found results briefly to stop penetration.

Monitor hit ratio, latency, evictions and memory through Micrometer metrics.

How it works

  1. Request calls a @Cacheable method; the proxy computes the key.
  2. Redis hit: return the cached value.
  3. Miss: invoke the method, load from DB, store with TTL.
  4. Update: write DB, commit, then evict the key.
  5. TTL and eviction policies bound staleness and memory.

Example

@Configuration @EnableCaching
class CacheConfig {
    @Bean RedisCacheManager cacheManager(RedisConnectionFactory cf) {
        var base = RedisCacheConfiguration.defaultCacheConfig()
            .serializeValuesWith(RedisSerializationContext.SerializationPair
                .fromSerializer(new GenericJackson2JsonRedisSerializer()))
            .prefixCacheNameWith("catalog:v2:")
            .entryTtl(Duration.ofMinutes(10));
        return RedisCacheManager.builder(cf).cacheDefaults(base)
            .withCacheConfiguration("rates", base.entryTtl(Duration.ofMinutes(1)))
            .transactionAware().build();
    }
}

@Service
class ProductService {
    @Cacheable(cacheNames = "products", key = "#id", sync = true)
    public ProductDto get(long id) { return repo.findDto(id).orElseThrow(); }

    @Transactional
    @CacheEvict(cacheNames = "products", key = "#cmd.id")
    public void update(UpdateProduct cmd) { repo.apply(cmd); }
}
redis-cli CONFIG SET maxmemory-policy allkeys-lru

Common mistakes

  • Using JDK serialization for cached values.
  • No TTL, so stale data lives forever.
  • Updating the cache instead of evicting, causing races.
  • Evicting before the transaction commits.
  • Expecting caching on self-invocation or on private methods.

How to answer in the interview

"I use cache-aside: read Redis first, on a miss load from the database and populate the cache. In Spring that's the cache abstraction with @Cacheable on reads and @CacheEvict or @CachePut on writes, backed by a RedisCacheManager with a JSON serializer and per-cache TTLs, and Redis configured with maxmemory and allkeys-lru. For consistency I write the database first and then evict after commit, accepting brief staleness; where stronger consistency is needed I use short TTLs or event-driven invalidation through CDC. Against stampedes I use sync = true or locking and jittered TTLs, and I monitor the hit ratio."

Likely follow-up questions

  • When would you choose a local cache like Caffeine instead of Redis? For small, read-heavy, rarely changing data where sub-millisecond reads matter and per-instance staleness is fine; often as an L1 in front of Redis.
  • Why evict rather than update on writes? Concurrent writers can otherwise leave an older value in the cache.
  • What is cache penetration? Repeated misses for non-existent keys; cache null results briefly or use a Bloom filter.
