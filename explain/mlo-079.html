How do you version models and their APIs so that consumers do not break?

MLOps · concept · levels mid, senior

In one line

Separate the model version (changes every retrain) from the API contract version (what consumers integrate with): compatible retrains ship behind the same API, breaking changes to inputs, outputs or score meaning get a new API version run in parallel, enforced with schema validation and communicated with deprecation timelines.

Detailed explanation

Consumers care about the contract: request fields, response fields, label values and what the score means. They don't care that the model was retrained, as long as the contract holds. Coupling the two means every retrain forces consumer changes, or, worse, retrains silently break consumers.

Compatible changes (same inputs, same output format, same meaning) are deployed behind the existing endpoint, say /v1/score, using canary or blue-green. The response includes model_version for traceability.

Behavioural changes inside a compatible contract still need communication. If the new model's scores are distributed differently, a consumer's hard-coded threshold of 0.7 may suddenly approve twice as many cases. Mitigate by calibrating scores so meaning is stable, by returning a decision or band rather than a raw score, and by announcing distribution shifts with before and after statistics.

Breaking changes need a new version, /v2/score: a new required feature, removed or renamed output fields, new label sets, or a change in score semantics (probability of fraud versus risk tier). v1 and v2 run in parallel during a migration window, with usage metrics per version, and v1 is deprecated on a published timeline (headers such as Deprecation and Sunset).

Enforcement: request and response schemas (OpenAPI, Pydantic, Protobuf) and the model signature (for example MLflow signatures) are validated at the endpoint, so a missing or mistyped feature fails with a clear 4xx error instead of producing a garbage prediction. Contract tests in CI check that a new model matches the API schema.

How it works

  1. Define the API contract (OpenAPI or Protobuf) and version it semantically.
  2. Store model signatures in the registry and check compatibility in CI.
  3. Deploy compatible model versions behind the same API with canary.
  4. Publish release notes on output distribution changes.
  5. For breaking changes, launch v2 alongside v1 and track consumer migration.
  6. Sunset v1 after the deprecation period.

Example

class ScoreRequestV1(BaseModel):
    customer_id: str
    amount: condecimal(ge=0)
    country: constr(min_length=2, max_length=2)
class ScoreResponseV1(BaseModel):
    score: confloat(ge=0, le=1)       # calibrated probability, meaning fixed for v1
    decision: Literal["approve", "review", "decline"]
    model_version: str                # e.g. "fraud-2026-11-14.3"

@app.post("/v1/score", response_model=ScoreResponseV1)
def score(req: ScoreRequestV1): ...

Common mistakes

  • Tying the URL to the model version (/model-42/predict), forcing consumers to change each retrain.
  • Changing score meaning without a version bump.
  • No input validation, so missing features become zeros.
  • Removing old versions without usage data or notice.

How to answer in the interview

"I separate the model version from the API contract. A retrain with the same inputs and outputs is deployed behind the same API version, so consumers don't change anything, but I tell them about significant shifts in score distributions, because their thresholds may depend on them, and I keep scores calibrated. A change in required inputs, output fields, labels or score meaning is breaking and gets a v2 running in parallel with v1 during migration. The endpoint validates requests against the schema and model signature, responses include the model version, and deprecations follow a published timeline."

Likely follow-up questions

  • Why can a better model break a consumer? Different score distributions shift outcomes at fixed downstream thresholds even if accuracy improved.
  • How do you know who still uses v1? Per-version request metrics and client identifiers.
  • Raw score or decision? Returning a decision or band plus score decouples consumers from model changes.
