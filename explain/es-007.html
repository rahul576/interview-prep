Your Elasticsearch cluster is in red status. What do you do?

Elasticsearch · scenario · levels mid, senior

In one line

Red means at least one primary shard is unassigned (some data is unavailable). Yellow means only replicas are unassigned. Find the shard with _cat/shards, ask _cluster/allocation/explain why, fix the cause (lost node, disk watermark, allocation rules, corruption), and restore from a snapshot if the primary data is gone. Then add alerts.

Detailed explanation

Cluster health is the worst state of any index:

  • Green: all primaries and replicas are assigned.
  • Yellow: all primaries are assigned, but some replicas aren't. Data is fully available, but redundancy is reduced.
  • Red: at least one primary is unassigned. Searches on that index return partial results, and writes to the affected shard fail.

Diagnose systematically:

  1. GET _cluster/health?level=indices shows which indices are red.
  2. GET _cat/shards?v&h=index,shard,prirep,state,unassigned.reason,node lists the unassigned shards and their reasons.
  3. GET _cluster/allocation/explain (optionally for a specific shard) gives the exact reason each node refused allocation.
  4. Check _cat/nodes (did a node leave?) and _cat/allocation (disk usage).

Common causes and fixes:

  • A node left (crash, OOM, network, restart) holding the only copy, with replicas set to 0 or also lost. Bring the node back. Its on-disk shard data is then reused.
  • Disk watermarks: at the low watermark (85% by default) no new shards are allocated to the node. At high (90%) shards are moved away. At flood stage (95%) indices get a read_only_allow_delete block (released automatically in recent versions once usage drops). Free space, add nodes, or delete old indices.
  • Allocation filtering or awareness rules, or cluster.routing.allocation.enable left as none after maintenance. Fix the settings.
  • Too many retries: after 5 failed allocations, Elasticsearch stops trying. Fix the cause, then POST _cluster/reroute?retry_failed=true.
  • Corrupted shard or lost data. Restore the index from a snapshot. As a last resort, allocate_stale_primary (accepting possible data loss) or allocate_empty_primary (losing all data in that shard) via the reroute API. Use these only deliberately.

Afterwards, run a post-mortem and add prevention: replicas of at least 1, alerts on disk, node count and health, regular snapshots via SLM, and capacity headroom.

How it works

  1. Find the red indices and the unassigned primaries.
  2. Run allocation explain to get the reason.
  3. Fix the infrastructure (node, disk, settings).
  4. Retry the allocation, and watch recovery with _cat/recovery.
  5. If the data is unrecoverable, restore from a snapshot.
  6. Add alerts and fix the root cause.

Example

GET _cluster/health?level=indices
GET _cat/shards?v&h=index,shard,prirep,state,unassigned.reason&s=state
GET _cluster/allocation/explain
{ "index": "orders-2026.11", "shard": 0, "primary": true }
GET _cat/allocation?v
PUT _cluster/settings { "persistent": { "cluster.routing.allocation.enable": "all" } }
POST _cluster/reroute?retry_failed=true
POST _snapshot/s3_repo/nightly-2026.11.20/_restore { "indices": "orders-2026.11" }

Common mistakes

  • Jumping to allocate_empty_primary and losing data unnecessarily.
  • Treating yellow and red as equally urgent.
  • Running production with zero replicas.
  • Having no snapshots, or never testing restores.
  • Ignoring disk usage until flood stage blocks writes.

How to answer in the interview

"Red means at least one primary shard is unassigned, so some data is unavailable. Yellow only means replicas are missing. I'd check cluster health to find the red index, use cat shards to see which shards are unassigned and why, and then the allocation explain API for the exact reason. Typical causes are a node that left the cluster holding the only copy, disks above the watermark, allocation settings left disabled after maintenance, or a corrupted shard. I'd bring the node back or free disk space and retry the allocation. If the primary data is really lost, I'd restore that index from a snapshot. Afterwards I'd make sure replicas, snapshots and disk alerts are in place."

Likely follow-up questions

  • Disk watermarks? Low (85%) stops new allocation, high (90%) moves shards away, flood stage (95%) makes indices read-only.
  • Why is a single-node cluster yellow? Replicas can't share a node with their primary.
  • Unassigned after a rolling restart? Allocation was left disabled. Re-enable it with cluster.routing.allocation.enable: all.
