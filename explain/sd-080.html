Design a platform that lets AI agents call internal tools and APIs safely, for example using MCP servers.

AI & ML System Design · design · levels senior, lead

In one line

A safe agent platform has a tool registry (often MCP servers), an agent runtime with step/time/cost limits, per-user delegated authorization with least privilege, human approval for risky actions, prompt-injection defences and output validation, sandboxed execution and complete audit logs.

Detailed explanation

Agents turn LLM output into actions, so the risk moves from "wrong text" to "wrong action". The platform must assume the model can be confused or manipulated.

Tools: teams publish tools with clear names, descriptions, JSON schemas and risk levels; the Model Context Protocol (MCP) standardises discovery and invocation, so agents can use tools from many teams through one interface.

Identity: the agent acts on behalf of a user with delegated OAuth tokens and the user's permissions, never a god-mode service account. The underlying APIs enforce authorization as they would for the user.

Risk tiers: read-only tools run freely; write tools may need confirmation; irreversible or high-impact actions (payments, deletions, external emails, production changes) require human approval with a clear diff of what will happen.

Prompt injection: documents, web pages and tool outputs may contain instructions. Treat them as data: mark untrusted content, never let it grant permissions, constrain tool arguments with schemas and allow-lists, and validate outputs before execution.

Limits & sandboxing: max steps, time and tokens; code execution in isolated sandboxes; network egress allow-lists.

Audit: every prompt, tool call, argument, result and approval logged with user and agent identity.

How it works

  1. User request → agent runtime loads allowed tools for that user.
  2. Loop: model proposes tool call → policy engine checks (schema, risk, permissions) → approval if needed → execute via MCP with user token → result back (marked untrusted).
  3. Stop on goal, limits or policy denial.
  4. Logs → audit store; evaluations before granting new tools.

Example

{ "tool": "refund_payment", "risk": "high", "requires_approval": true,
  "input_schema": { "type": "object",
    "properties": { "payment_id": {"type": "string"}, "amount": {"type": "number", "maximum": 500} },
    "required": ["payment_id", "amount"] } }

Common mistakes

  • Shared service accounts with broad permissions for agents.
  • Letting retrieved content act as instructions.
  • No limits (runaway loops and costs).
  • Approvals that show the model's summary instead of the actual action.

How to answer in the interview

"Tools are registered with schemas and risk levels, exposed via MCP servers. The runtime runs the agent loop with step, time and cost limits. Agents act with the user's delegated identity and least privilege, so normal API authorization applies. Risky or irreversible actions need human approval, tool outputs are treated as untrusted to resist prompt injection, arguments are validated, code runs in sandboxes, and everything is audit-logged."

Likely follow-up questions

  • Evaluate before write access? Scenario test suites, red-teaming, shadow mode with proposed actions reviewed.
  • Why MCP? One standard protocol for tools across models and clients.
  • Data exfiltration risk? Egress allow-lists, DLP checks on outputs.
