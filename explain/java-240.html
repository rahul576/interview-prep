What are suppressed exceptions in try-with-resources?

Exceptions · concept · levels entry, mid

In one line

In try-with-resources, if the body throws and then close() also throws, the close exception is added as a suppressed exception to the primary one instead of replacing it; you read them with getSuppressed(), and resources close in reverse order.

Detailed explanation

Before Java 7, cleanup was written in finally. If the try body threw an exception and then close() in finally also threw, the second exception replaced the first one. The real cause, for example a failed SQL statement, vanished, and logs showed only "connection already closed". Writing correct nested try/finally blocks for several resources was tedious and error-prone.

Java 7 introduced try-with-resources for anything implementing AutoCloseable, and with it suppressed exceptions (Throwable.addSuppressed and getSuppressed). The rules:

  • Resources declared in the header are closed automatically when the block exits, normally or exceptionally.
  • They are closed in reverse order of declaration, so a statement closes before its connection.
  • If the body threw, any exception from close() is attached to the body's exception as suppressed; the body's exception remains the primary one that propagates.
  • If the body completed normally and close throws, the close exception becomes the primary exception.
  • If several closes throw, all are added as suppressed.
  • Catch and finally clauses attached to the statement run after the resources are closed.

Stack traces print suppressed exceptions under a Suppressed: heading. Since Java 9 you can also use an effectively final variable declared earlier: try (conn) { ... }. You can use addSuppressed yourself when writing aggregate cleanup code.

How it works

  1. Each resource is initialised in order; if one fails to initialise, the ones already opened are closed.
  2. The body runs.
  3. On exit, resources are closed in reverse order.
  4. A close exception is suppressed into the primary exception if one exists, otherwise it becomes primary.
  5. Then catch and finally blocks run.

Example

class Res implements AutoCloseable {
    private final String name;
    Res(String name) { this.name = name; }
    public void close() { throw new IllegalStateException("close failed: " + name); }
}

try (Res a = new Res("A"); Res b = new Res("B")) {
    throw new RuntimeException("body failed");
} catch (RuntimeException e) {
    System.out.println(e.getMessage());                // body failed
    for (Throwable s : e.getSuppressed())
        System.out.println("suppressed: " + s.getMessage()); // close failed: B, then A
}

Common mistakes

  • Logging only e.getMessage() and missing the suppressed failures.
  • Assuming catch runs before resources are closed.
  • Wrapping a resource-producing call so the real resource is not declared in the header and never closed.
  • Catching an exception and rethrowing a new one without the cause, losing suppressed info.

How to answer in the interview

"With try-with-resources, resources are closed automatically in reverse order of declaration. If the body throws and then close also throws, the close exception doesn't replace the original: it's added to the primary exception as a suppressed exception, so the root cause survives. You can get them with getSuppressed, and stack traces print them under Suppressed. That fixes the old finally pattern, where a failing close silently masked the real error. If the body succeeds and only close fails, that close exception becomes the primary one."

Likely follow-up questions

  • In what order are multiple resources closed? Reverse order of declaration.
  • Does catch run before or after close? After all resources are closed.
  • Can you suppress exceptions manually? Yes, with Throwable.addSuppressed.
