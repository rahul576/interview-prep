How does TreeSet work internally, and how does it maintain sorted order?

Collections · concept · levels mid

In one line

A TreeSet is backed by a TreeMap, a red-black tree (self-balancing BST) that places elements using compareTo or a Comparator, keeps height O(log n) through rotations and recolouring, and yields sorted order via in-order traversal; duplicates are decided by compare == 0, not equals.

Detailed explanation

TreeSet<E> holds a NavigableMap<E, Object>, by default a TreeMap, and stores each element as a key with a dummy value, just as HashSet uses HashMap. The ordering comes from the elements' natural ordering (Comparable.compareTo) or from a Comparator passed to the constructor.

A binary search tree keeps smaller keys in the left subtree and larger ones in the right. Inserting walks from the root, comparing at each node, until it finds an empty spot. If any comparison returns 0, the element is considered already present and is not added. An in-order traversal (left, node, right) therefore visits elements in ascending order, which is how iteration is sorted.

A plain BST can degenerate into a linked list if you insert sorted data. A red-black tree prevents that by colouring nodes red or black and enforcing rules: the root is black, no red node has a red child, and every path from a node to its leaves has the same number of black nodes. After an insert or delete, violations are fixed with recolouring and left/right rotations. These rules guarantee the height is at most about 2 log2(n), so add, remove and contains are O(log n) in the worst case.

Because it is ordered, TreeSet implements NavigableSet: first, last, floor, ceiling, higher, lower, pollFirst, headSet, tailSet, subSet and descendingSet. Null is not allowed with natural ordering. It is not thread safe; ConcurrentSkipListSet is the concurrent alternative.

How it works

  1. add(e) → TreeMap.put(e, PRESENT).
  2. Start at root; compare; go left if negative, right if positive.
  3. Comparison 0: already present, return false.
  4. Insert new red leaf.
  5. Rebalance with recolouring and rotations up the tree.
  6. Iteration: in-order walk using successor links.

Example

TreeSet<Integer> scores = new TreeSet<>(List.of(70, 85, 92, 60));
scores.first();            // 60
scores.ceiling(80);        // 85 (smallest >= 80)
scores.floor(80);          // 70 (largest <= 80)
scores.headSet(85);        // [60, 70]
scores.descendingSet();    // [92, 85, 70, 60]

TreeSet<Employee> bySalary =
    new TreeSet<>(Comparator.comparing(Employee::salary)
                            .thenComparing(Employee::id)); // tie-breaker!

Common mistakes

  • Comparator on one field only, so different objects with equal values are dropped.
  • Inserting objects that aren't Comparable without a Comparator (ClassCastException).
  • Mutating fields used by the comparator after insertion.
  • Adding null with natural ordering.

How to answer in the interview

"A TreeSet is backed by a TreeMap, which is a red-black tree, a self-balancing binary search tree. Each element is placed by comparing it, with compareTo or the Comparator given to the constructor: smaller to the left, larger to the right. After inserts and deletes it rebalances by recolouring and rotations, so the height stays logarithmic, giving log n add, remove and contains, and an in-order traversal returns sorted order. Duplicates are detected by compare returning zero, not equals. It also offers navigation like floor, ceiling, headSet and tailSet."

Likely follow-up questions

  • Why can TreeSet treat unequal objects as duplicates? If the comparator returns 0, it considers them the same.
  • Why red-black instead of AVL? Fewer rotations on update, slightly less strict balance; good all-round.
  • Concurrent sorted set? ConcurrentSkipListSet.
