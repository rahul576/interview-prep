How does Karpenter differ from the Cluster Autoscaler?

Kubernetes · concept · levels senior, lead

In one line

The Cluster Autoscaler resizes predefined node groups with fixed instance types; Karpenter reads pending pods' requirements and provisions right-sized nodes directly from a wide set of instance types (including spot), and continuously consolidates to cut cost, usually faster and with far less node-group management.

Detailed explanation

The Cluster Autoscaler (CA) is the long-standing, provider-neutral autoscaler. It works on node groups such as AWS Auto Scaling Groups, Azure VM Scale Sets or GKE node pools. When pods are Pending it simulates which group could fit them and increases that group's desired size; when nodes stay underused it drains and removes them. Every group has a fixed shape, so to offer many instance types, GPUs, zones and spot you end up maintaining many groups, and scaling goes through the cloud's group API, which adds latency.

Karpenter removes the node-group layer. It batches unschedulable pods by their constraints (requests, selectors, affinity, topology spread, tolerations) and calls the cloud API directly to launch the cheapest instance that fits, usually in under a minute. You describe what is allowed in a NodePool (instance families, sizes, zones, spot or on-demand, limits) and provider settings in a node class (on AWS an EC2NodeClass for AMI, subnets, security groups).

Its other big feature is disruption: consolidation removes empty nodes and replaces underused ones with cheaper combinations, drift replaces nodes that no longer match the NodePool, and expiration recycles old nodes. Karpenter began on AWS and now also has an Azure provider (behind AKS node auto-provisioning); the CA still supports the most providers.

How it works

  1. Pod becomes Pending because no node fits.
  2. Karpenter batches pending pods and computes their combined constraints.
  3. It picks instance types allowed by the NodePool, preferring the cheapest that fit.
  4. It launches the node directly and binds the pods once the node is ready.
  5. Over time, consolidation repacks pods and removes surplus nodes, within disruption budgets.

Example

apiVersion: karpenter.sh/v1
kind: NodePool
metadata: { name: general }
spec:
  template:
    spec:
      requirements:
      - { key: karpenter.sh/capacity-type, operator: In, values: [spot, on-demand] }
      - { key: karpenter.k8s.aws/instance-category, operator: In, values: [c, m, r] }
      nodeClassRef: { group: karpenter.k8s.aws, kind: EC2NodeClass, name: default }
      expireAfter: 720h
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 5m
    budgets:
    - nodes: "10%"
  limits: { cpu: "1000" }

Common mistakes

  • Pods without resource requests, so Karpenter sizes nodes wrongly.
  • No disruption budgets or PDBs, so consolidation churns critical pods.
  • Allowing only one or two instance types, losing spot availability.
  • Running CA and Karpenter on the same nodes.

How to answer in the interview

"The Cluster Autoscaler scales predefined node groups up and down, and each group has fixed instance types, so you manage many groups to get flexibility. Karpenter looks directly at pending pods' requirements and launches right-sized nodes from a broad set of instance types, including spot, which is faster and removes most node-group management. It also consolidates continuously, replacing underused nodes with cheaper ones, and handles drift and node expiry. I'd control that with disruption budgets, PDBs and the do-not-disrupt annotation."

Likely follow-up questions

  • Which disruption controls would you configure? NodePool budgets (percentage and schedules), consolidateAfter, expireAfter, PDBs and karpenter.sh/do-not-disrupt on sensitive pods.
  • How does Karpenter handle spot interruptions? It watches interruption notices via a queue and cordons and drains the node in advance.
  • When stay on the CA? Clouds without a Karpenter provider, or strictly uniform node groups.
