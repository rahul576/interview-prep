What Spring Boot test slices exist, and when do you use each?

Testing · concept · levels mid, senior

In one line

Spring Boot test slices load only one layer of the context: @WebMvcTest (controllers + MockMvc), @WebFluxTest, @DataJpaTest (repositories), @JsonTest, @RestClientTest and more, while @SpringBootTest loads everything; replace beans with @MockitoBean (which superseded @MockBean in Boot 3.4) and keep configurations uniform to benefit from context caching.

Detailed explanation

A full application context can take seconds to start and pulls in every dependency. Slices use auto-configuration filters to include only the beans relevant to one layer, so tests start faster and failures point to that layer.

  • @WebMvcTest(Controller.class): controllers, @ControllerAdvice, converters, filters and Spring Security; provides MockMvc (and MockMvcTester with AssertJ since Boot 3.4). Services must be supplied as mocks. Use it for mapping, validation, status codes, JSON shape and security rules.
  • @WebFluxTest: the reactive equivalent with WebTestClient.
  • @DataJpaTest: entities, repositories, Flyway/Liquibase and a TestEntityManager; each test is transactional and rolled back. By default it replaces the DataSource with an embedded database; with Testcontainers and @ServiceConnection (or @AutoConfigureTestDatabase(replace = NONE)) you test against the real engine. Also @DataJdbcTest, @DataMongoTest, @DataRedisTest.
  • @JsonTest: Jackson configuration, with JacksonTester to assert serialised JSON.
  • @RestClientTest: a RestClient/RestTemplate-based client with MockRestServiceServer.
  • @SpringBootTest: the full context, optionally with a real server (webEnvironment = RANDOM_PORT) for integration tests.

@MockitoBean and @MockitoSpyBean (Spring Framework 6.2) replace a bean in the context with a Mockito mock or spy; Boot's @MockBean was deprecated in 3.4 and removed in Boot 4.

Context caching: Spring caches contexts by their configuration key. Every distinct combination of mock beans, properties or profiles creates a new context, so many slightly different test classes mean many startups and a slow suite.

How it works

  1. The slice annotation imports a limited set of auto-configurations.
  2. Component scanning is filtered to that layer's stereotypes.
  3. Missing dependencies are provided via @MockitoBean or @Import.
  4. The context is built once per unique configuration and cached.
  5. Test utilities (MockMvc, TestEntityManager, JacksonTester) are injected.

Example

@DataJpaTest
@Testcontainers
class OrderRepositoryTest {
    @Container @ServiceConnection
    static PostgreSQLContainer<?> pg = new PostgreSQLContainer<>("postgres:16");

    @Autowired OrderRepository repo;

    @Test
    void findsOpenOrdersForCustomer() {
        repo.save(new Order(7L, Status.OPEN));
        repo.save(new Order(7L, Status.CLOSED));
        assertThat(repo.findByCustomerIdAndStatus(7L, Status.OPEN)).hasSize(1);
    }
}

@JsonTest
class OrderJsonTest {
    @Autowired JacksonTester<OrderDto> json;
    @Test void writesIsoDates() throws Exception {
        assertThat(json.write(sampleDto())).extractingJsonPathStringValue("$.createdAt")
            .isEqualTo("2026-01-10T10:00:00Z");
    }
}

Common mistakes

  • Using @SpringBootTest where a slice would do.
  • Expecting services to be injected in @WebMvcTest without mocking them.
  • Each test class mocking a different set of beans, creating dozens of contexts.
  • Relying on the embedded database in @DataJpaTest and missing dialect issues.

How to answer in the interview

"Slices load just one layer, so tests are faster and focused. WebMvcTest loads the controller layer with MockMvc and security, with services mocked; DataJpaTest loads repositories and migrations and rolls back each test, and I point it at Testcontainers rather than an embedded database. JsonTest checks Jackson serialisation and RestClientTest checks HTTP clients against a mock server. SpringBootTest loads the whole context for real integration tests. I replace beans with MockitoBean, which superseded MockBean from Boot 3.4, and keep mock and property combinations consistent so Spring can cache and reuse contexts."

Likely follow-up questions

  • Why do many @MockitoBean combinations slow the suite? Each unique set changes the context cache key, forcing a new context startup.
  • Is @DataJpaTest transactional? Yes, every test rolls back by default.
  • How do you include an extra bean in a slice? Use @Import with the configuration or component.
