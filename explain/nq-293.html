How do Jenkins pipelines work?

DevOps & CI/CD · concept · levels entry

In one line

A Jenkins pipeline is pipeline as code in a Jenkinsfile stored in the repository; the declarative syntax (pipeline, agent, environment, stages, steps, post) describes the flow, the controller schedules runs on agents, runs are triggered by webhooks, schedules or manually (with multibranch jobs per branch and PR), and credentials, plugins and shared libraries supply the rest.

Detailed explanation

Pipeline as code: the Jenkinsfile lives with the application code, so changes to the build are versioned, reviewed and branch-specific, unlike job configuration clicked together in the UI.

Declarative structure:

  • pipeline { } the root block.
  • agent where to run: any agent, a labelled node, a Docker container or a Kubernetes pod (Kubernetes plugin) that is created per build and discarded.
  • environment variables, including credentials bound with credentials('id').
  • options such as timeouts, build discarding and timestamps.
  • stages containing stage('Build'), each with steps like sh, junit or archiveArtifacts; when conditions and parallel blocks.
  • post actions on always, success, failure: publish test reports, notify Slack, clean workspace.

Architecture: the controller stores configuration, receives triggers, schedules builds and shows results; agents do the actual work, keeping the controller safe and scalable. Running builds on the controller itself is discouraged.

Triggers: webhooks from GitHub or GitLab, SCM polling, cron (triggers { cron('H 2 * * *') }), upstream jobs or manual runs with parameters. Multibranch pipelines and GitHub organisation folders discover branches and pull requests automatically and create a job for each.

Reuse and security: shared libraries hold common steps across teams; the credentials store keeps secrets masked in logs; hundreds of plugins integrate tools, which also means plugin updates must be managed.

How it works

  1. Commit a Jenkinsfile to the repository.
  2. Create a multibranch pipeline pointing at the repo.
  3. Webhook notifies Jenkins on push or PR.
  4. Controller allocates an agent and checks out the code.
  5. Stages run in order; reports and artifacts are recorded.
  6. post sends notifications and cleans up.

Example

pipeline {
  agent { kubernetes { yamlFile 'ci/pod.yaml' } }
  options { timeout(time: 30, unit: 'MINUTES') }
  environment { REGISTRY_CREDS = credentials('ecr-push') }
  stages {
    stage('Build') { steps { sh './mvnw -B -DskipTests package' } }
    stage('Test')  { steps { sh './mvnw -B verify' } }
    stage('Deploy dev') {
      when { branch 'main' }
      steps { sh './deploy.sh dev' }
    }
  }
  post {
    always  { junit '**/target/surefire-reports/*.xml' }
    failure { slackSend channel: '#orders-ci', message: "Build failed: ${env.BUILD_URL}" }
  }
}

Common mistakes

  • Building on the controller.
  • Hard-coding secrets in the Jenkinsfile.
  • Copy-pasting the same pipeline across repos instead of a shared library.
  • Unmaintained plugins creating security holes.

How to answer in the interview

"A Jenkins pipeline defines build, test and deploy as code in a Jenkinsfile in the repository, so it's versioned and reviewed. Declarative syntax has a pipeline block with an agent, often a Kubernetes pod, environment variables, stages like Build, Test and Deploy with steps, and a post section for reports and notifications. The controller schedules runs on agents. Builds are triggered by GitHub webhooks, schedules or manually, and multibranch pipelines create jobs per branch and pull request. Credentials come from the credentials store, and shared libraries reuse logic across teams."

Likely follow-up questions

  • Declarative vs scripted? Declarative is structured and validated; scripted is full Groovy, more flexible but harder to maintain.
  • Why agents? Isolation, scalability and controller security.
  • How do you handle secrets? Credentials store or an external vault, bound to steps and masked in logs.
