How do you secure networking for an Azure App Service application?

Azure · concept · levels mid, senior

In one line

Secure App Service by treating inbound and outbound separately: inbound via private endpoint (public access disabled) or a WAF gateway with access restrictions (service tag plus Front Door ID header); outbound via VNet integration with route all through a firewall or NAT gateway; and harden with no FTP/basic auth, HTTPS/TLS 1.2+, managed identities.

Detailed explanation

App Service is a multi-tenant PaaS, so its networking features are split by direction, which is a common source of confusion.

Inbound (who can reach the app):

  • Private endpoint: gives the app (and its SCM/Kudu site) a private IP in your VNet with a privatelink.azurewebsites.net DNS zone. You then disable public network access, so only VNet, peered or on-premises clients via VPN/ExpressRoute can reach it.
  • Public but protected: put Azure Front Door or Application Gateway with WAF in front. Use access restrictions to allow only the AzureFrontDoor.Backend service tag plus a check of the X-Azure-FDID header for your Front Door instance (the service tag alone includes everyone's Front Door), or the App Gateway subnet. With Front Door Premium, use Private Link to the origin and disable public access entirely.
  • Restrict the SCM site separately.

Outbound (what the app can reach):

  • VNet integration connects the app's outbound traffic to a delegated subnet, so it can reach private endpoints of SQL, Storage, Key Vault, and on-premises systems. It does not make the app reachable inbound.
  • With route all (outbound internet traffic routed through the VNet, now default for new apps), UDRs send traffic to Azure Firewall for filtering and logging, or a NAT gateway provides stable, dedicated egress IPs for partner allow-lists.

Hardening: disable FTP and basic authentication for SCM/FTP publishing (deploy via pipelines using Entra ID), enforce HTTPS only and minimum TLS 1.2 (1.3 supported), use managed identities and Key Vault references instead of connection strings with secrets, and disable remote debugging. For full single-tenant isolation, an App Service Environment v3 deploys into your VNet.

How it works

  1. Decide exposure: internal only, or public through WAF.
  2. Inbound: private endpoint + disable public access, or access restrictions to the gateway.
  3. Outbound: VNet integration on a delegated subnet; route all enabled.
  4. UDR 0.0.0.0/0 to firewall, or NAT gateway for egress IPs.
  5. Private endpoints and DNS for dependencies.
  6. Disable FTP/basic auth; HTTPS only; managed identity.

Example

az webapp vnet-integration add -g rg-app -n app-orders --vnet vnet-spoke --subnet snet-appsvc-out
az webapp config set -g rg-app -n app-orders --ftps-state Disabled --min-tls-version 1.2
az resource update -g rg-app --namespace Microsoft.Web --resource-type basicPublishingCredentialsPolicies \
  --parent sites/app-orders -n scm --set properties.allow=false
az webapp config access-restriction add -g rg-app -n app-orders --priority 100 \
  --service-tag AzureFrontDoor.Backend --http-header x-azure-fdid=<front-door-id>

Common mistakes

  • Believing VNet integration makes the app private inbound.
  • Allowing the Front Door service tag without checking the FDID header.
  • Forgetting private DNS for dependencies, so traffic goes public.
  • Leaving SCM site open or basic auth enabled.

How to answer in the interview

"On App Service, inbound and outbound are separate. For inbound, I either use a private endpoint and disable public access, or, for public apps, put Front Door or Application Gateway with WAF in front and lock the app down with access restrictions to the gateway's service tag and our Front Door ID header. For outbound, VNet integration lets the app reach private endpoints of databases and Key Vault, and with route all, traffic goes through Azure Firewall or a NAT gateway for control and stable IPs. I also disable FTP and basic auth, enforce HTTPS and TLS 1.2+, and use managed identities."

Likely follow-up questions

  • Why doesn't VNet integration make the app private? It only handles outbound traffic; inbound needs a private endpoint.
  • When use App Service Environment? Single-tenant isolation, very high scale or strict compliance.
  • How to restrict Kudu? Separate SCM access restrictions or the private endpoint covers both.
