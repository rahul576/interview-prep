What is transaction propagation? Explain REQUIRED, REQUIRES_NEW, and SUPPORTS.

Spring Boot · concept · levels senior, lead

In one line

Propagation decides what a transactional method does when it is called while a transaction may already exist: REQUIRED joins or creates one, REQUIRES_NEW suspends the outer and starts an independent one, and SUPPORTS joins if present, otherwise runs without a transaction.

Detailed explanation

Services call other services, so a transactional method is often called from inside another transaction. Propagation is the rule that tells the PlatformTransactionManager whether to reuse, suspend or refuse the existing transaction.

REQUIRED is the default. If a transaction exists, the method joins it; otherwise a new one starts. Inner and outer work form one unit: they commit together or roll back together. If an inner REQUIRED method throws, the shared transaction is marked rollback-only, even if the outer method catches the exception.

REQUIRES_NEW always suspends the current transaction and starts a brand-new physical transaction on a second connection. It commits or rolls back on its own, independently of the outer one. This suits an audit log or failure record that must survive even when the business transaction fails. The cost is an extra connection per nested level: under load, if every request holds one connection and waits for a second, the pool can be exhausted and threads deadlock waiting on each other.

SUPPORTS joins a transaction if one exists, otherwise runs non-transactionally. It fits read-only helpers that can be called from both contexts.

The other options are MANDATORY (must already be in a transaction, else exception), NEVER (exception if a transaction exists), NOT_SUPPORTED (suspends any transaction and runs without one) and NESTED (a savepoint inside the existing transaction, supported by DataSourceTransactionManager and, for JDBC access, JpaTransactionManager).

How it works

  1. The outer method starts a transaction (REQUIRED) and binds connection A to the thread.
  2. An inner method with REQUIRED finds the bound transaction and simply participates.
  3. An inner method with REQUIRES_NEW suspends A, opens connection B and starts a new transaction.
  4. When the inner REQUIRES_NEW method finishes, B commits or rolls back and A is resumed.
  5. SUPPORTS checks for a bound transaction and runs inside it, or without one.

Example

@Service
class PaymentService {
    @Transactional                                   // REQUIRED
    public void pay(Order o) {
        try { gateway.charge(o); }
        catch (PaymentException e) {
            auditService.recordFailure(o, e);       // survives the rollback
            throw e;
        }
    }
}

@Service
class AuditService {
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void recordFailure(Order o, Exception e) { auditRepo.save(new Audit(o, e)); }
}

Common mistakes

  • Calling the REQUIRES_NEW method on this, so the proxy is bypassed and no new transaction starts.
  • Using REQUIRES_NEW everywhere and exhausting the connection pool.
  • Expecting a caught inner exception under REQUIRED not to affect the outer commit.
  • Confusing NESTED (savepoint, same connection) with REQUIRES_NEW (separate transaction).

How to answer in the interview

"Propagation defines what happens when a transactional method is called while a transaction may already exist. REQUIRED, the default, joins it or creates one, so everything commits or rolls back together. REQUIRES_NEW suspends the outer transaction and runs an independent one; I use it for audit entries that must be saved even if the business operation fails, keeping in mind it needs a second connection. SUPPORTS joins if there is a transaction and otherwise runs without one, which suits read helpers. There are also MANDATORY, NEVER, NOT_SUPPORTED and NESTED, which uses savepoints."

Likely follow-up questions

  • Inner REQUIRED throws and the outer catches it? The transaction is rollback-only, so the outer commit throws UnexpectedRollbackException.
  • NESTED vs REQUIRES_NEW? NESTED rolls back to a savepoint but commits with the outer; REQUIRES_NEW commits independently.
  • Why can REQUIRES_NEW deadlock a pool? Each request holds one connection and waits for another; with a small pool all threads wait.
