How do you debug Terraform when something behaves unexpectedly?

Infrastructure as Code · concept · levels entry

In one line

Read the error and provider message first, inspect state with terraform state list/show, evaluate expressions in terraform console, compare with the real resource and its permissions, and use TF_LOG=DEBUG/TRACE with TF_LOG_PATH for API-level detail.

Detailed explanation

Most Terraform failures are not Terraform bugs but provider API errors: missing IAM permissions (AccessDenied, AuthorizationFailed), names already taken, quota limits, invalid combinations of settings, eventual consistency (a role not yet visible), or an organisation policy blocking an action (SCPs, Azure Policy). The error usually names the resource address, the API call and the reason, so reading it carefully, including the provider's original message and request ID, solves most problems.

For unexpected plans, compare what Terraform believes with reality. terraform state list shows which addresses Terraform manages, so you can spot duplicates or a resource missing after a refactor. terraform state show <address> prints the recorded attributes, which you compare with the cloud console or CLI. terraform plan -refresh-only separates drift from code changes. Unexpected replacements usually point to a force-new attribute; perpetual diffs to normalisation issues such as JSON policy formatting or list ordering.

For expression problems, terraform console is the best tool: it loads the configuration and state and lets you evaluate var.x, local.y, module.z.output, or a for expression interactively, which is ideal for debugging for_each maps, merge, try or cidrsubnet. Temporary outputs serve a similar purpose.

For deep problems, TF_LOG=DEBUG or TRACE logs Terraform core and provider activity, including HTTP requests and responses to cloud APIs; TF_LOG_PROVIDER and TF_LOG_CORE target one side, TF_LOG_PATH writes to a file, and TF_LOG=JSON gives structured logs. These logs can contain credentials, tokens and secret values, so they must be handled carefully. Finally, check versions: a provider upgrade or known GitHub issue often explains odd behaviour.

How it works

  1. Read the error: address, API, reason.
  2. Check identity and permissions (aws sts get-caller-identity).
  3. Inspect state and real resources.
  4. Evaluate expressions in console.
  5. Enable debug logs and reproduce if still unclear.

Example

terraform state list | grep aws_iam_role
terraform state show 'aws_iam_role.app'
aws sts get-caller-identity

terraform console
> local.subnets_by_az
> { for k, v in var.services : k => v.port if v.public }
> cidrsubnet("10.0.0.0/16", 4, 2)

TF_LOG=DEBUG TF_LOG_PATH=./tf-debug.log terraform plan
grep -n "HTTP Request" tf-debug.log | head

Common mistakes

  • Jumping to TF_LOG=TRACE before reading the actual error.
  • Running with the wrong credentials or account.
  • Editing state by hand instead of using state commands.
  • Sharing debug logs that contain secrets.

How to answer in the interview

"First I read the error carefully; most failures are provider API errors like missing IAM permissions, a name already taken or a quota, and the message says which. For unexpected plans, terraform state list shows what Terraform manages and state show what it recorded for a resource, which I compare with the real resource. terraform console lets me evaluate variables, locals and functions interactively, perfect for debugging for_each maps. If that's not enough, TF_LOG=DEBUG or TRACE with TF_LOG_PATH logs every API request and response, which I treat as sensitive."

Likely follow-up questions

  • Why should TF_LOG output never be shared publicly? It may include tokens, secrets and account details from API calls.
  • How do you debug a perpetual diff? Compare state show with config, check normalisation, check provider issues.
  • What if state lists a resource that no longer exists? Refresh removes it, or terraform state rm after confirming.
