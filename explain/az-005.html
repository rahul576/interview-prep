Explain Azure virtual networking: VNets, subnets, NSGs, peering, private endpoints and service endpoints.

Azure · concept · levels mid

In one line

A VNet is a private network split into subnets; NSGs filter traffic; VNet peering connects networks, often in hub-and-spoke; a private endpoint gives a PaaS service a private IP in your VNet, while a service endpoint keeps the public endpoint but restricts it to chosen subnets.

Detailed explanation

A virtual network (VNet) is a regional, isolated network with one or more private address spaces, divided into subnets. Some services require dedicated subnets (for example Azure Firewall, VPN gateways, Application Gateway, Bastion), and some PaaS services use subnet delegation. Plan non-overlapping address ranges early, because they must not clash with on-premises or other VNets you will peer with.

Network security groups (NSGs) are stateful allow and deny rules on source, destination, port and protocol, evaluated by priority and attached to subnets or NICs. Default rules allow traffic within the VNet and deny inbound internet traffic.

VNet peering connects two VNets over the Microsoft backbone with low latency, in the same region or globally. Peering is not transitive, so in a hub-and-spoke design, spokes connect to a hub that contains shared services: Azure Firewall, VPN or ExpressRoute gateways, DNS resolvers and Bastion. Spoke-to-spoke traffic goes through the firewall using user-defined routes. Azure Virtual WAN is a managed alternative for large hub networks.

For PaaS services such as Storage, SQL or Key Vault there are two options. A service endpoint extends the subnet's identity to the service so its firewall can allow only that subnet; traffic uses the Microsoft backbone but the service still has a public IP. A private endpoint (Azure Private Link) creates a network interface with a private IP from your subnet for a specific resource; you can then disable public network access entirely, and it works from peered VNets and on-premises. It requires private DNS zones (such as privatelink.blob.core.windows.net) so the normal hostname resolves to the private IP.

How it works

  1. Plan address spaces; create hub and spoke VNets with subnets.
  2. Peer each spoke to the hub; deploy firewall and gateways in the hub.
  3. Attach NSGs to subnets with least-privilege rules.
  4. Create private endpoints for PaaS services in a spoke subnet.
  5. Link private DNS zones to the VNets (or use a central DNS resolver).
  6. Disable public network access on the PaaS services.

Example

az network private-endpoint create -g rg-app -n pe-sqlorders \
  --vnet-name vnet-spoke-app --subnet snet-private-endpoints \
  --private-connection-resource-id <sql-server-id> \
  --group-id sqlServer --connection-name sqlorders-conn
az network private-dns zone create -g rg-dns -n privatelink.database.windows.net
az network private-dns link vnet create -g rg-dns \
  -z privatelink.database.windows.net -n link-spoke-app \
  -v <spoke-vnet-id> -e false

Common mistakes

  • Overlapping address spaces that block future peering.
  • Assuming peering is transitive.
  • Creating private endpoints without fixing DNS.
  • Leaving public network access enabled after adding a private endpoint.
  • Overly broad NSG rules such as allowing any source.

How to answer in the interview

"A VNet is an isolated private network split into subnets, and NSGs are stateful allow and deny rules on subnets or NICs. VNets connect through peering, which is not transitive, so I usually use hub and spoke, where the hub holds shared services like Azure Firewall, VPN or ExpressRoute gateways and DNS. For PaaS services, a private endpoint gives the service a private IP in my VNet through Private Link, so I can disable the public endpoint completely, but I need private DNS zones so names resolve to that IP. A service endpoint keeps the public endpoint and just restricts it to selected subnets. For data services I prefer private endpoints."

Likely follow-up questions

  • Why do private endpoints often break DNS, and how do you fix it? Clients still resolve the public IP; link private DNS zones or use Azure DNS Private Resolver with conditional forwarding from on-premises.
  • How do spokes talk to each other? Through the hub firewall with user-defined routes, or Virtual WAN.
  • What is an application security group? A way to group NICs by role and use them in NSG rules.
