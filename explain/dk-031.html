Explain the components behind Docker: dockerd, containerd, runc and the OCI standards.

Docker · concept · levels mid

In one line

dockerd provides the Docker API, builds, networks and volumes; containerd manages images and container lifecycle; a shim per container keeps it running; runc is the low-level runtime that creates the process; the OCI image and runtime specifications make all of it interoperable.

Detailed explanation

Docker was split into components so each could be reused and standardised. At the top, dockerd exposes the Docker Engine API used by the CLI and Compose. It handles the developer-facing features: BuildKit builds, Docker networking (bridge, overlay, embedded DNS), volumes, logging drivers, Swarm and registry authentication.

For running containers, dockerd talks to containerd, a CNCF graduated project and a daemon in its own right. containerd pulls and stores image content (increasingly also for Docker itself through the containerd image store), unpacks layers into snapshots, and manages the container lifecycle. Kubernetes uses containerd directly through its CRI plugin, without dockerd.

For each container, containerd starts a shim (containerd-shim-runc-v2). The shim calls runc, which reads an OCI runtime bundle (a root filesystem plus config.json), creates the namespaces, configures cgroups, capabilities and seccomp, and starts the process, after which runc exits. The shim stays as the parent, holds stdio and reports the exit status, so containers keep running when containerd or dockerd restart. runc can be swapped for crun, gVisor (runsc) or Kata Containers for different isolation.

The Open Container Initiative defines the image specification (manifests, layers, config), the runtime specification (bundle format and lifecycle) and the distribution specification (registry API). Because Docker builds OCI-compliant images, they run on containerd, CRI-O, Podman or any cloud service.

How it works

  1. CLI calls dockerd's API.
  2. dockerd asks containerd to create a container from an image.
  3. containerd prepares a snapshot and an OCI bundle.
  4. containerd starts a shim, which invokes runc.
  5. runc sets up isolation, execs the process and exits; the shim monitors it.

Example

ps -ef --forest | grep -E 'dockerd|containerd|shim' | head
# containerd's own CLI, Docker uses the "moby" namespace
sudo ctr -n moby containers list
runc --version
docker info --format '{{.DefaultRuntime}}'

Common mistakes

  • Thinking Kubernetes stopped supporting Docker images when dockershim was removed.
  • Believing dockerd must stay up for containers to run (with live-restore and shims it need not).
  • Confusing containerd (high-level) with runc (low-level).
  • Not knowing alternative runtimes exist for stronger isolation.

How to answer in the interview

"dockerd is the Docker daemon that exposes the API and handles high-level features like builds, networking, volumes and logging. It delegates execution to containerd, which manages image storage and container lifecycle and is also what Kubernetes uses directly. For each container containerd starts a shim and calls runc, the low-level runtime that sets up namespaces, cgroups and the root filesystem and starts the process; the shim keeps the container running even if containerd restarts. The OCI image and runtime specs standardise the format and how runtimes start containers, so Docker images run anywhere."

Likely follow-up questions

  • Why could Kubernetes remove dockershim without breaking images? Images are OCI-standard and containerd runs them directly.
  • What is crun? A faster runc alternative written in C.
  • What does gVisor change? It intercepts syscalls in a user-space kernel for stronger isolation.
