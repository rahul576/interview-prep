How do you test a Spring Boot application? Describe your unit and integration testing approach.

Testing · concept · levels entry, mid

In one line

I follow the test pyramid: many fast JUnit 5 + Mockito + AssertJ unit tests, slice tests (@WebMvcTest, @DataJpaTest) for framework layers, and fewer @SpringBootTest integration tests against real dependencies with Testcontainers, plus WireMock and contract tests for other services, all running in CI.

Detailed explanation

Testing a Spring Boot application is about putting each test at the cheapest level that can catch the bug.

Unit tests cover business logic in services and domain classes with no Spring context. Dependencies come in through the constructor and are mocked with Mockito; assertions use AssertJ. Each test follows given-when-then and checks one behaviour, including edge cases and failures. They run in milliseconds, so there are hundreds or thousands.

Slice tests start only part of the context. @WebMvcTest loads one controller with MockMvc (or MockMvcTester since Boot 3.4) to check request mapping, validation, JSON and error handling, with services replaced by @MockitoBean. @DataJpaTest checks repositories, custom queries and mappings, ideally against a real database via Testcontainers rather than H2, because H2 hides dialect differences.

Integration tests with @SpringBootTest start the whole application and use Testcontainers for PostgreSQL, Kafka or Redis, often via @ServiceConnection. External HTTP APIs are stubbed with WireMock so failures and timeouts can be simulated. Between services, consumer-driven contract tests (Pact or Spring Cloud Contract) replace most end-to-end testing.

A handful of end-to-end smoke tests run after deployment. Everything runs in CI on every pull request, with JaCoCo coverage as a signal rather than a target.

How it works

  1. Write unit tests alongside each service class; mock collaborators.
  2. Add @WebMvcTest tests for controller contracts and validation.
  3. Add @DataJpaTest tests for non-trivial queries against Testcontainers.
  4. Write a few @SpringBootTest flows covering wiring, transactions and messaging.
  5. Stub third-party APIs with WireMock; verify inter-service contracts.
  6. Run in CI, reuse containers and Spring contexts to keep the build fast.

Example

@WebMvcTest(OrderController.class)
class OrderControllerTest {
    @Autowired MockMvc mvc;
    @MockitoBean OrderService service;

    @Test
    void returns404WhenOrderMissing() throws Exception {
        given(service.find(42L)).willThrow(new OrderNotFoundException(42L));
        mvc.perform(get("/orders/42"))
           .andExpect(status().isNotFound())
           .andExpect(jsonPath("$.code").value("ORDER_NOT_FOUND"));
    }
}

@SpringBootTest
@Testcontainers
class OrderFlowIT {
    @Container @ServiceConnection
    static PostgreSQLContainer<?> db = new PostgreSQLContainer<>("postgres:16");
    // ... call the service, assert DB state
}

Common mistakes

  • Using @SpringBootTest for everything, making the suite slow.
  • Testing against H2 and discovering SQL problems in production.
  • Mocking so heavily that tests only restate the implementation.
  • Creating many unique context configurations, which defeats Spring's context caching.

How to answer in the interview

"I follow the test pyramid. Most tests are plain JUnit 5 unit tests with Mockito and AssertJ, written given-when-then, covering business rules and edge cases without starting Spring. For the framework layers I use slices: WebMvcTest with MockMvc for controllers, and DataJpaTest for repositories. Then a smaller set of SpringBootTest integration tests runs against real PostgreSQL and Kafka in Testcontainers, so behaviour matches production, with WireMock for external APIs and contract tests between our services. It all runs in CI on every pull request, and I keep it fast by reusing containers and Spring contexts."

Likely follow-up questions

  • How do you keep integration tests fast? Singleton containers, a shared context configuration, parallel test forks and running only slices where possible.
  • Why Testcontainers over H2? Same engine as production, so dialect, constraints and migrations are really tested.
  • What is @MockitoBean? The Spring Framework 6.2 replacement for @MockBean, which replaces a bean in the test context with a Mockito mock.
