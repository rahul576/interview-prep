When does an object become eligible for garbage collection? Explain GC roots and reference types.

JVM & Performance · concept · levels mid, senior

In one line

An object is eligible for GC when it is unreachable from every GC root (thread stack locals, static fields, active threads, JNI references); tracing means cycles do not prevent collection; soft, weak and phantom references let objects be collected while still being referred to; and System.gc() is only a hint.

Detailed explanation

Java collectors use tracing, not reference counting. They start from GC roots and mark everything reachable by following references. Roots include local variables and parameters in active stack frames of all threads, static fields of loaded classes, live Thread objects, objects held by JNI global references, monitors currently held, and some JVM-internal references. Anything not reached is garbage, regardless of how many references it still has from other garbage.

Because of tracing, circular references are fine. If an Order refers to its Customer and the Customer refers back to the Order, but nothing reachable points to either, both are collected. Reference counting would leak that cycle.

"Eligible" does not mean "collected now". The object is reclaimed whenever the collector next processes the region it lives in, which could be milliseconds or much later (old-generation objects are collected less often).

Reference types in java.lang.ref refine reachability:

  • Strong: normal references; keep objects alive.
  • SoftReference: cleared only when the JVM needs memory, before throwing OOM. Historically used for memory-sensitive caches, though a bounded cache like Caffeine is more predictable.
  • WeakReference: cleared at the next GC once no strong references remain. WeakHashMap uses weak keys, useful for metadata attached to objects you do not own.
  • PhantomReference: get() always returns null; it is enqueued after the object is finalised and is used for post-mortem cleanup of native resources. java.lang.ref.Cleaner (Java 9) builds on this and replaces deprecated finalize().

System.gc() requests a collection but the JVM may ignore it (-XX:+DisableExplicitGC), and in HotSpot it usually triggers an expensive full GC. Code must never depend on it.

How it works

  1. GC starts from roots: stacks, statics, threads, JNI handles.
  2. It marks every object reachable via strong references.
  3. Softly reachable objects are cleared if memory is tight; weakly reachable ones are cleared.
  4. Unmarked objects' memory is reclaimed by sweeping, copying or compaction.
  5. Phantom references to collected objects are enqueued for cleanup.

Example

Order a = new Order(); Customer c = new Customer();
a.customer = c; c.lastOrder = a;     // cycle
a = null; c = null;                  // both now unreachable -> both eligible

Map<Key, Meta> meta = new WeakHashMap<>(); // entry disappears when Key is unreachable

WeakReference<byte[]> ref = new WeakReference<>(new byte[1024]);
System.gc();                         // only a hint
System.out.println(ref.get());       // likely null, not guaranteed

// Cleaner for native resources
private static final Cleaner CLEANER = Cleaner.create();
CLEANER.register(this, () -> nativeFree(handle)); // action must not reference 'this'

Common mistakes

  • Believing cycles cause leaks in Java.
  • Setting every local to null "to help the GC".
  • Relying on finalize() or System.gc() for cleanup.
  • Thinking a removed object is gone when a listener list or static map still holds it.

How to answer in the interview

"An object becomes eligible for garbage collection when it's unreachable from all GC roots. Roots include local variables on thread stacks, static fields of loaded classes, active threads and JNI references. Because the JVM traces reachability instead of counting references, circular references between unreachable objects don't prevent collection. Reference types refine this: soft references are cleared only under memory pressure, weak references at the next GC, as in WeakHashMap, and phantom references are used for cleanup after collection, which is what Cleaner builds on. System.gc is only a hint and should never be relied on."

Likely follow-up questions

  • Why might a removed listener still cause a memory leak? If it was never unregistered, the event source's listener list strongly references it from a root.
  • Why was finalize() deprecated? Unpredictable timing, performance cost, resurrection bugs; use Cleaner or try-with-resources.
  • Are soft references a good cache? Rarely; eviction is unpredictable and causes GC spikes; use a bounded cache.
