How should MCP servers handle secrets and credentials for downstream systems?

MCP Servers · concept · levels mid, senior

In one line

Keep secrets out of shared config files and Git; prefer per-user OAuth tokens stored securely server-side, take unavoidable service credentials from a secret store (Key Vault, Secrets Manager, Vault) via workload identity, rotate and scope them, and never return secrets in tool results, errors or logs.

Detailed explanation

MCP servers sit between an AI agent and powerful downstream systems, so how they hold credentials largely decides how bad a compromise can be.

The most common mistake is with local servers: API keys pasted into the env block of a host config file, which then gets committed to a repo, synced to cloud storage or shared in a chat. Local secrets should come from the OS keychain or a secret manager CLI at launch, and tokens should be fine-grained and least-privilege.

For remote servers, the best model is per-user OAuth. Each user authorizes the server against the downstream system, and the server stores the resulting refresh tokens server-side, encrypted, keyed to the user. Every action then uses that user's permissions, and revocation is per user. Where the downstream supports it, token exchange avoids storing long-lived tokens at all.

Sometimes a service credential is unavoidable, such as a database password or a vendor API key. It belongs in a secret store such as Azure Key Vault, AWS Secrets Manager or HashiCorp Vault, fetched at runtime using workload identity (managed identity, IAM role, Kubernetes service account federation), so there is no bootstrap secret. Credentials are rotated regularly and scoped narrowly.

Finally, output hygiene. Anything a tool returns enters the model's context, where it may be repeated to the user, stored in conversation history, sent to other tools or exfiltrated through prompt injection. Tools must never return secrets, and the server must scrub downstream error messages (connection strings, stack traces with keys) before returning them, and redact secrets from logs.

How it works

  1. User connects the server; OAuth flow yields a refresh token for the downstream.
  2. Server encrypts it with a KMS key and stores it per user.
  3. For service credentials, the pod's workload identity reads the secret from the vault at startup and on rotation.
  4. Each tool call uses the user's delegated token or the scoped service credential.
  5. Results and errors pass through a redaction filter before returning and logging.

Example

from azure.identity import DefaultAzureCredential
from azure.keyvault.secrets import SecretClient

vault = SecretClient("https://mcp-kv.vault.azure.net", DefaultAzureCredential())
db_password = vault.get_secret("orders-db-readonly").value   # workload identity, no stored key

def safe_error(exc):
    msg = str(exc)
    msg = re.sub(r"(password|pwd|token|secret)=[^;\s]+", r"\1=***", msg, flags=re.I)
    return tool_error(f"Database query failed: {msg[:200]}")

Common mistakes

  • Tokens in mcp.json checked into a repository.
  • One shared admin key used by the server for all users.
  • Returning raw exception messages containing connection strings.
  • Never rotating service credentials because "it might break something".

How to answer in the interview

"Secrets should never sit in shared host config files or Git, which is a common mistake with local servers. For remote servers, the best model is per-user OAuth: users authorize the server against the downstream system, and the server stores the refresh tokens securely server-side, encrypted and tied to the user, so each action uses that user's permissions. Service-level credentials, when unavoidable, come from a secret store like Key Vault, Secrets Manager or Vault, accessed via workload identity, rotated and narrowly scoped. Tools must never return secrets in results or logs, because anything in a result enters the model context and could be exposed or exfiltrated, so I also scrub downstream error messages."

Likely follow-up questions

  • Why is a secret in a tool result worse? The model may repeat it, send it to another tool, or leak it via injection.
  • How rotate without downtime? Support two active credentials and reload from the vault on change.
  • Local server secrets? OS keychain or secret manager CLI, injected at launch.
