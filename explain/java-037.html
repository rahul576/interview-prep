How do you handle a business transaction that spans multiple microservices?

Microservices · concept · levels senior, lead

In one line

Avoid two-phase commit; model the business transaction as a saga of local transactions coordinated by choreography or orchestration, undo with compensating transactions, publish reliably with the transactional outbox, and make every participant idempotent.

Detailed explanation

In a monolith, "create order, charge card, reserve stock" is one ACID transaction. With a database per service, it spans several databases. Distributed two-phase commit (XA) could make it atomic, but it couples services' availability, holds locks while waiting for the coordinator, blocks if the coordinator fails, is slow, and is poorly supported by Kafka, many NoSQL stores and cloud databases. So microservices accept eventual consistency instead.

A saga is a sequence of local transactions. Each step commits in its own service and then triggers the next with an event or command. Because committed steps cannot be rolled back, failures are handled by compensating transactions that semantically undo earlier work: refund the payment, release the reservation, cancel the order. Compensations must themselves be retryable and idempotent, and some actions (sending an email) can only be compensated with another action (an apology email).

Coordination comes in two styles. Choreography: services listen to each other's events (OrderCreated → payment, PaymentCompleted → inventory); good for short flows but the overall process is implicit. Orchestration: a central orchestrator, built with a state machine or a workflow engine such as Temporal, Camunda or AWS Step Functions, sends commands and tracks state; clearer for complex flows with timeouts and compensations.

Reliability details make or break sagas. The transactional outbox writes the event into an outbox table in the same local transaction, avoiding dual writes. Delivery is at least once, so participants are idempotent. Because there is no isolation between steps, use semantic locks (status PENDING), commutative updates or re-reading values to handle anomalies.

How it works

  1. Order service creates order PENDING + outbox event.
  2. Payment service charges the card, emits PaymentCompleted or PaymentFailed.
  3. Inventory reserves stock, emits StockReserved or StockUnavailable.
  4. On success, order becomes CONFIRMED.
  5. On failure, compensations run in reverse: refund, then cancel order.
  6. Timeouts trigger compensation if a participant never replies.

Example

// Orchestrated saga with Temporal (simplified)
public class OrderSagaImpl implements OrderSaga {
    private final PaymentActivities payment = Workflow.newActivityStub(PaymentActivities.class, opts);
    private final InventoryActivities inventory = Workflow.newActivityStub(InventoryActivities.class, opts);

    public void placeOrder(Order order) {
        Saga saga = new Saga(new Saga.Options.Builder().build());
        try {
            String chargeId = payment.charge(order.id(), order.total());
            saga.addCompensation(payment::refund, chargeId);
            inventory.reserve(order.id(), order.lines());
            saga.addCompensation(inventory::release, order.id());
        } catch (ActivityFailure e) {
            saga.compensate();       // runs compensations in reverse order
            throw e;
        }
    }
}

Common mistakes

  • Treating compensations as an afterthought or making them non-idempotent.
  • Publishing events with dual writes instead of an outbox.
  • Ignoring the lack of isolation (another request sees intermediate states).
  • Huge choreographed flows nobody can follow.

How to answer in the interview

"I avoid distributed two-phase commit because it couples availability, holds locks across services and is poorly supported by brokers. Instead I use a saga: a sequence of local transactions where each step publishes an event or command that triggers the next. If a step fails, earlier steps are undone with compensating transactions, like refunding the payment and cancelling the order. For short flows choreography works; for complex ones I prefer an orchestrator, for example Temporal. Events are published through a transactional outbox and every participant is idempotent because delivery is at least once."

Likely follow-up questions

  • How would you compensate an order-payment-inventory saga? If stock fails: refund payment, mark order cancelled, notify the customer; all idempotent and retried.
  • What is a pivot transaction? The step after which the saga can only go forward, so later steps must be retryable.
  • How do you handle a participant that never answers? A timeout in the orchestrator triggers retries and then compensation.
