How do you write a reliable Kubernetes operator?

Kubernetes · concept · levels mid, senior, lead

In one line

An operator is a CRD (your domain API) plus a controller that reconciles it; build it with Kubebuilder or Operator SDK on controller-runtime, keep reconcile idempotent, report progress in status conditions with observedGeneration, use owner references and finalizers for cleanup, requeue with backoff, enable leader election, and test with envtest.

Detailed explanation

Operators encode operational knowledge (provisioning, backup, upgrades) as software following the controller pattern.

API design: the CRD has a spec (desired, written by users) and a status subresource (observed, written only by the controller). Use OpenAPI validation, defaults and CEL validation rules in the CRD so bad input is rejected at admission. Keep the API declarative ("version: 17") rather than imperative ("upgradeNow: true").

Reconcile logic:

  • Read the custom resource from the informer cache; if gone, return.
  • Compute the desired child objects (StatefulSet, Services, Secrets, PDB) and create or patch them, preferably with server-side apply and a fixed field manager. Never "always create".
  • Reconcile must be idempotent and level-based: it may run any number of times, after restarts or for unrelated events. Don't store state only in memory; derive it from the cluster or persist it in status.
  • Report progress in status.conditions (Ready, Progressing, Degraded) and status.observedGeneration, so users and tools know whether the latest spec has been processed.

Lifecycle: set owner references (SetControllerReference) on children, so Kubernetes garbage-collects them and changes to children trigger reconciles via Owns(). For external resources (a cloud database, DNS record, bucket), add a finalizer; on deletion, clean up externally, then remove the finalizer.

Robustness: return errors to requeue with exponential backoff; use RequeueAfter for polling slow external operations rather than blocking; run several replicas with leader election so only one reconciles; emit Events and metrics, and read from the cache rather than the API.

Testing and versioning: unit-test pure functions, use envtest (a real API server and etcd without nodes) for reconcile tests, and run end-to-end tests in kind. Evolve CRDs with new versions and conversion webhooks, keeping one storage version.

How it works

  1. Scaffold project and CRD types with Kubebuilder.
  2. Controller watches the CR and owned resources.
  3. Reconcile: fetch, handle deletion and finalizer, apply children, update status.
  4. Errors → requeue with backoff; long operations → RequeueAfter.
  5. Deploy with leader election, RBAC from markers, metrics and webhooks.

Example

func (r *PGReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    var pg dbv1.PostgresCluster
    if err := r.Get(ctx, req.NamespacedName, &pg); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err)
    }
    if !pg.DeletionTimestamp.IsZero() {
        if err := r.deleteBackupsBucket(ctx, &pg); err != nil { return ctrl.Result{}, err }
        controllerutil.RemoveFinalizer(&pg, finalizer)
        return ctrl.Result{}, r.Update(ctx, &pg)
    }
    if controllerutil.AddFinalizer(&pg, finalizer) {
        if err := r.Update(ctx, &pg); err != nil { return ctrl.Result{}, err }
    }
    sts := r.desiredStatefulSet(&pg)
    if err := ctrl.SetControllerReference(&pg, sts, r.Scheme); err != nil { return ctrl.Result{}, err }
    if err := r.Patch(ctx, sts, client.Apply, client.FieldOwner("pg-operator"), client.ForceOwnership); err != nil {
        return ctrl.Result{}, err
    }
    meta.SetStatusCondition(&pg.Status.Conditions, metav1.Condition{Type: "Ready", Status: "True", Reason: "Reconciled", ObservedGeneration: pg.Generation})
    pg.Status.ObservedGeneration = pg.Generation
    return ctrl.Result{}, r.Status().Update(ctx, &pg)
}

Common mistakes

  • Imperative, non-idempotent reconcile logic.
  • Writing spec from the controller or status from users.
  • Blocking reconcile for minutes waiting on external systems.
  • Missing finalizers, leaking cloud resources on delete.

How to answer in the interview

"An operator is a CRD defining a domain API, like a PostgresCluster, plus a controller that reconciles it. I build it with Kubebuilder or Operator SDK on controller-runtime, which gives informers, caching and work queues. Reconcile must be idempotent: read the resource, compute desired children, create or patch them, and report progress in status conditions with observedGeneration, never keeping state only in memory. Children get owner references for garbage collection, and finalizers handle external cleanup. Errors requeue with backoff, slow work uses RequeueAfter, replicas use leader election, and I test reconcile logic with envtest."

Likely follow-up questions

  • How do you version a CRD schema? Add a new version, conversion webhook, migrate storage version, deprecate the old one.
  • Why observedGeneration? Shows whether status reflects the latest spec.
  • When not to write an operator? When Helm or plain manifests with GitOps already handle the lifecycle.
