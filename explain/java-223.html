What is false sharing, and how do you avoid it?

Concurrency · concept · levels senior, lead

In one line

False sharing happens when threads on different cores write different variables that share one CPU cache line (typically 64 bytes), so the cache-coherence protocol keeps invalidating the line and the cores fight over it; avoid it with padding, @Contended, or structures like LongAdder that already spread updates.

Detailed explanation

CPUs don't move single bytes between memory and caches; they move cache lines, usually 64 bytes (128 on some ARM chips). Coherence protocols like MESI guarantee that only one core can hold a line in a modified state. When core 1 writes to a line, copies in other cores are invalidated; when core 2 then writes, it must fetch the line back and invalidate core 1's copy.

If two threads write logically independent variables, for example counterA updated by thread 1 and counterB by thread 2, that happen to sit next to each other in memory, they still share a line. Each write ping-pongs the line between cores. There is no data sharing, hence false sharing, but throughput can drop by an order of magnitude, and adding threads makes it worse instead of better. Typical victims: arrays of per-thread counters, adjacent volatile fields and queue head/tail indexes.

Avoiding it:

  • Padding: insert unused fields so each hot variable occupies its own line. The JVM may reorder fields, so manual padding is fragile.
  • @jdk.internal.vm.annotation.Contended: the JVM adds padding around the field or class. It is internal to the JDK; application code must use --add-exports java.base/jdk.internal.vm.annotation=ALL-UNNAMED and -XX:-RestrictContended, so it's rarely used outside libraries. The JDK itself uses it in Thread, ForkJoinPool, Striped64 and ConcurrentHashMap counter cells.
  • LongAdder / LongAccumulator: spread updates over padded @Contended cells and sum on read.
  • Thread-local accumulation: each thread counts locally and merges at the end.
  • Space array elements apart (e.g. index × 8 or 16 for longs).

How it works

  1. Two hot fields share one 64-byte line.
  2. Core 1 writes field A → line Modified in core 1, invalidated elsewhere.
  3. Core 2 writes field B → must fetch the line, invalidates core 1.
  4. Repeat millions of times: memory-bus traffic, stalls.
  5. Padding puts A and B on different lines, so writes stay local.

Example

// Problem: adjacent slots updated by different threads
long[] perThread = new long[THREADS];          // perThread[t]++ in a hot loop

// Fix 1: spread slots onto separate lines (8 longs = 64 bytes)
long[] padded = new long[THREADS * 8];          // use padded[t * 8]++

// Fix 2: let the JDK do it
LongAdder hits = new LongAdder();               // padded internal cells
hits.increment();
long total = hits.sum();
# Detect with hardware counters (Linux)
perf c2c record -- java -jar app.jar
perf c2c report      # shows cache lines with heavy cross-core HITM traffic

Common mistakes

  • Assuming more threads always means more throughput for shared counters.
  • Manual padding that the JVM reorders or that misses object headers.
  • Using @Contended without the required JVM flags.

How to answer in the interview

"CPUs cache memory in lines, typically 64 bytes. False sharing happens when two threads write different variables on the same line: each write invalidates the line in the other core's cache through the coherence protocol, so the cores keep fighting over it even though they share no data, which badly slows down things like per-thread counters. I avoid it by padding so hot variables sit on separate lines, by the @Contended annotation that the JDK uses internally, or by using LongAdder, which already spreads updates across padded cells."

Likely follow-up questions

  • How do you detect false sharing? Hardware counters such as perf c2c (HITM events), JMH scaling tests where throughput drops as threads increase, or async-profiler cache-miss profiling.
  • Why is it called "false"? The threads don't share data, only the cache line.
  • Does it affect reads? Mostly writes; read-only sharing of a line is fine.
