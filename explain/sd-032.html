Design a metrics monitoring and alerting system like Datadog or Prometheus.

Classic Design Problems · design · levels senior, lead

In one line

A monitoring system collects metrics via agents (push) or scraping (pull), buffers through a queue, stores them in a compressed time-series database with downsampling and retention tiers, controls label cardinality, and runs a highly available alerting engine.

Detailed explanation

Scale example: 100,000 hosts × 500 metrics every 10 s = 5M points/s. Each series is identified by metric name plus labels (http_requests_total{service="cart",code="500"}). Storage is optimised for appending points and reading ranges: timestamps compressed with delta-of-delta, values with XOR (Gorilla encoding), giving ~1–2 bytes per point.

Pull (Prometheus) makes target health obvious (scrape fails = target down) and avoids overloading the server; push (Datadog agent, OTLP) suits short-lived jobs and firewalled hosts. Many systems combine both.

The number one scaling risk is cardinality: adding user_id as a label turns one series into millions, exploding memory and index size. Enforce limits and use logs/traces for high-cardinality data.

Alerting must be more reliable than what it monitors: evaluate rules close to data, deduplicate and group alerts, support silences and routing, and alert on symptoms (SLO burn rates).

How it works

  1. Agents/scrapers collect → gateway → Kafka (buffer, replay).
  2. Ingesters write to the TSDB (sharded by series hash), with replication.
  3. Compaction and downsampling (10 s → 1 min → 1 h); old blocks to object storage.
  4. Query layer fans out across shards for dashboards.
  5. Rule evaluator → Alertmanager → PagerDuty/Slack.

Example

- alert: CheckoutHighErrorBurn
  expr: (sum(rate(http_requests_total{service="checkout",code=~"5.."}[5m]))
        / sum(rate(http_requests_total{service="checkout"}[5m]))) > 14.4 * 0.001
  for: 2m

Common mistakes

  • Unbounded label values.
  • Keeping full-resolution data forever.
  • Alerting on every cause (CPU 80%) instead of user-facing symptoms.
  • Monitoring stack sharing failure domains with production.

How to answer in the interview

"Agents push, or Prometheus pulls, metrics into an ingestion tier buffered by Kafka. A sharded, replicated time-series DB stores compressed points, downsamples older data and tiers it to object storage. I'd guard label cardinality strictly. Alerting evaluates SLO-based rules and routes through deduplication and silencing, and it runs independently so it still works when production is unhealthy."

Likely follow-up questions

  • Monitor the monitoring? A small independent watchdog/dead-man's switch alert.
  • Long-term storage? Thanos, Cortex/Mimir with object storage.
  • Push vs pull? Pull for service discovery and liveness; push for ephemeral jobs.
