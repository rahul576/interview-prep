What is the difference between Amazon RDS and Amazon Aurora?

Cloud (AWS) · concept · levels mid

In one line

RDS runs standard engines (PostgreSQL, MySQL, MariaDB, Oracle, SQL Server, Db2) on instances with EBS storage, while Aurora is AWS-built, MySQL- and PostgreSQL-compatible, with a distributed storage layer keeping six copies across three AZs, up to 15 low-lag replicas, fast failover, cloning, Global Database and Serverless v2.

Detailed explanation

RDS manages provisioning, patching, backups and failover for standard engines. Each instance uses EBS storage (gp3 or io2). Multi-AZ keeps a synchronous standby in another AZ for failover (typically one to two minutes), and Multi-AZ DB clusters add two readable standbys. Read replicas use the engine's asynchronous replication, so lag can grow under load. RDS supports more engines and versions, and for small or steady workloads it is usually cheaper.

Aurora separates compute from storage. The cluster volume is a distributed, self-healing log-structured storage service that writes six copies across three AZs, tolerates loss of an AZ plus one copy, and grows automatically to 128 TiB (more for newer versions). Because writes ship redo log records rather than full pages, I/O is efficient. Up to 15 Aurora Replicas read the same shared volume, so replica lag is usually milliseconds, and failover to a replica typically completes in under a minute, faster with RDS Proxy or the AWS JDBC wrapper.

Aurora-only features: fast cloning (copy-on-write, minutes for a multi-terabyte database), Backtrack for MySQL to rewind in place, Global Database with storage-level replication to up to five secondary regions, typically under a second of lag and fast managed failover, Serverless v2 scaling in 0.5 ACU steps (and down to zero for idle clusters on supported versions), I/O-Optimized storage for I/O-heavy workloads, zero-ETL integrations and Aurora DSQL as a separate distributed SQL option.

The trade-off is cost and compatibility: Aurora instances cost more, standard storage bills I/O, and some engine features or versions differ from community PostgreSQL or MySQL.

How it works

  1. Writer instance receives transactions.
  2. RDS: data pages written to EBS, replicated to standby or replicas.
  3. Aurora: redo records sent to six storage nodes; quorum of four confirms the write.
  4. Aurora readers read the shared volume with tiny lag.
  5. On failure, a replica is promoted and the cluster endpoint moves.

Example

aws rds create-db-cluster --db-cluster-identifier orders \
  --engine aurora-postgresql --engine-version 16.4 \
  --serverless-v2-scaling-configuration MinCapacity=0.5,MaxCapacity=32 \
  --master-username app --manage-master-user-password \
  --storage-encrypted

aws rds create-db-instance --db-instance-identifier orders-writer \
  --db-cluster-identifier orders --engine aurora-postgresql \
  --db-instance-class db.serverless

Common mistakes

  • Choosing Aurora for a tiny dev database where RDS is much cheaper.
  • Forgetting I/O charges on Aurora Standard for I/O-heavy workloads.
  • Treating read replicas as a high-availability substitute in RDS.
  • Assuming every PostgreSQL extension works identically on Aurora.

How to answer in the interview

"RDS runs standard engines like PostgreSQL, MySQL, Oracle and SQL Server on instances with EBS storage, and Multi-AZ keeps a standby. Aurora is AWS-built and MySQL or PostgreSQL compatible, but replaces storage with a distributed, self-healing volume that keeps six copies across three AZs and grows automatically. That gives up to 15 replicas with millisecond lag, failover usually under a minute, fast cloning, Backtrack for MySQL, Global Database and Serverless v2. Aurora often costs more for small workloads, and RDS supports more engines."

Likely follow-up questions

  • When pick Aurora Serverless v2? Variable or spiky load, many dev databases, or unpredictable growth.
  • When is I/O-Optimized worth it? When I/O charges exceed about a quarter of the Aurora bill.
  • How do Global Database failovers work? Promote a secondary region; managed switchover keeps zero data loss for planned moves.
