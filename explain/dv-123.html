How do you handle secrets and credentials in CI/CD pipelines?

DevOps & CI/CD · concept · levels entry, mid

In one line

Secrets never go in code or pipeline YAML: use the CI platform's encrypted, masked secret store at minimum, prefer short-lived credentials via OIDC federation, keep application secrets in an external vault, and apply least privilege, rotation and secret scanning.

Detailed explanation

CI/CD systems are high-value targets: they hold credentials that can deploy to production, and they run code from many contributors and third-party actions or plugins. A leaked cloud key from a pipeline can mean full account compromise, so secrets handling is layered.

Layer 1: never commit secrets. Anything in Git history is effectively permanent and is copied into every clone. Secret scanning (GitHub push protection, gitleaks, trufflehog) blocks commits containing keys.

Layer 2: the CI secret store. GitHub Actions secrets, GitLab CI/CD variables, Jenkins credentials and Azure DevOps variable groups encrypt values, mask them in logs and can be scoped to protected branches or environments, so a pull request from a fork cannot read production secrets. Environment-level secrets with required reviewers add an approval gate.

Layer 3: no long-lived cloud keys. With OIDC federation, the CI platform issues a signed identity token for each job, and AWS, Azure or GCP exchanges it for short-lived credentials for a specific role. The cloud trust policy can restrict this to a particular repository, branch or environment. Nothing is stored that could leak or need rotation.

Layer 4: an external vault for application secrets: HashiCorp Vault, AWS Secrets Manager, Azure Key Vault or GCP Secret Manager. Pipelines or the running application fetch them at deploy or run time, for example via the Kubernetes External Secrets Operator, with access audited and rotation automated.

Finally, least privilege per pipeline, pinned third-party actions, and a clear process for rotation and leaks.

How it works

  1. Developer pushes code; secret scanning rejects anything that looks like a key.
  2. The job requests an OIDC token from the CI platform.
  3. The cloud provider validates the token's claims and returns temporary role credentials.
  4. The job deploys; logs mask any secret values.
  5. The application reads its database password from the vault at runtime.
  6. Secrets rotate on schedule; access is logged.

Example

# GitHub Actions: deploy to AWS without stored keys
permissions:
  id-token: write
  contents: read
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/gh-deploy-orders
          aws-region: eu-west-1
      - run: aws ecs update-service --cluster prod --service orders --force-new-deployment

The IAM role's trust policy only accepts tokens whose sub is repo:acme/orders:environment:production.

Common mistakes

  • Secrets in YAML, Dockerfiles or .env files committed to Git.
  • Printing secrets in logs with echo or debug mode.
  • One admin key shared by every pipeline.
  • Exposing secrets to pull requests from forks.
  • Never rotating credentials.

How to answer in the interview

"Secrets never go in code or pipeline files, and secret scanning blocks accidental commits. The minimum is the CI platform's secret store, encrypted, masked in logs and scoped to protected branches or environments. Better is to remove long-lived cloud keys entirely with OIDC federation, so each job gets short-lived credentials for a narrowly scoped role. Application secrets live in a vault such as Vault, Secrets Manager or Key Vault and are fetched at deploy or run time. Each pipeline gets least privilege, and secrets are rotated regularly."

Likely follow-up questions

  • A secret was pushed to a public repo: what now? Revoke and rotate it immediately, check logs for misuse, then clean history.
  • Why is OIDC better than stored keys? Credentials are short-lived, scoped per job and never stored.
  • How do you protect secrets from malicious pull requests? Don't expose secrets to fork pull requests; require approval for workflows from outside contributors.
