What are S3 replication and Object Lock used for?

Cloud (AWS) · concept · levels mid

In one line

S3 Replication (Cross-Region or Same-Region) copies objects automatically to another bucket, requiring versioning, for DR, compliance, latency and log aggregation, while Object Lock enforces WORM retention in governance or compliance mode to protect data against deletion and ransomware.

Detailed explanation

Replication is configured on the source bucket with rules filtered by prefix or tag, an IAM role S3 assumes, and a destination bucket, which can be in another region (CRR), the same region (SRR) or another account. Both buckets must have versioning enabled. By default only new objects written after the rule exists replicate; S3 Batch Replication copies existing objects or retries failed ones. You can change the storage class on the destination (for example Glacier for a backup copy), change ownership to the destination account, replicate SSE-KMS objects with permission on the destination key, and optionally replicate delete markers. Replication Time Control (RTC) gives a 15-minute SLA for 99.99 percent of objects with metrics. Replication is asynchronous, and replicas do not chain unless configured.

Use cases: disaster recovery in another region, data residency copies, lower latency for users elsewhere, aggregating logs from many accounts into a central bucket, and keeping a production copy in a test account.

Object Lock stores object versions in write once, read many mode. A retention period prevents a version from being deleted or overwritten until a date. Governance mode lets principals with s3:BypassGovernanceRetention override it; compliance mode cannot be shortened or removed by anyone, including the root user, until it expires. Legal holds block deletion indefinitely until removed. Object Lock requires versioning and can now be enabled on existing buckets. It satisfies regulations like SEC 17a-4 and protects backups from ransomware or an attacker with admin access.

How it works

  1. Enable versioning on source and destination.
  2. Create a replication rule with role, filter and destination.
  3. New object versions replicate asynchronously; status shows on each object.
  4. Enable Object Lock with a default retention on the backup bucket.
  5. Deletes create delete markers; locked versions cannot be removed before expiry.

Example

{
  "Role": "arn:aws:iam::111122223333:role/s3-replication",
  "Rules": [{
    "ID": "dr-copy", "Status": "Enabled", "Priority": 1,
    "Filter": {"Prefix": "backups/"},
    "DeleteMarkerReplication": {"Status": "Disabled"},
    "Destination": {
      "Bucket": "arn:aws:s3:::dr-backups-eu-central-1",
      "Account": "444455556666",
      "StorageClass": "GLACIER_IR",
      "AccessControlTranslation": {"Owner": "Destination"},
      "ReplicationTime": {"Status": "Enabled", "Time": {"Minutes": 15}},
      "Metrics": {"Status": "Enabled", "EventThreshold": {"Minutes": 15}}
    }
  }]
}
aws s3api put-object-lock-configuration --bucket dr-backups-eu-central-1 \
  --object-lock-configuration '{"ObjectLockEnabled":"Enabled",
   "Rule":{"DefaultRetention":{"Mode":"COMPLIANCE","Days":35}}}'

Common mistakes

  • Expecting existing objects to replicate without Batch Replication.
  • Replicating delete markers to the DR bucket, so mistakes propagate.
  • Testing with compliance mode and long retention, then being unable to delete test data.
  • Forgetting KMS permissions on the destination key.

How to answer in the interview

"S3 replication automatically copies objects to another bucket, in another region with CRR or the same region with SRR, optionally to another account and storage class. Both buckets need versioning; only new objects replicate by default, and Batch Replication handles existing ones. Replication Time Control adds a 15-minute SLA. I use it for DR, residency, latency and central log aggregation. Object Lock adds WORM retention: governance mode can be overridden by privileged users, compliance mode by nobody, not even root, which protects backups and audit records against ransomware."

Likely follow-up questions

  • Why keep backups in a separate account with Object Lock? A compromised production account cannot delete or encrypt them.
  • Is replication a backup? Not alone; deletions or corruption can replicate, so combine with versioning and locks.
  • What is a legal hold? A lock without an end date, removed only explicitly by an authorised user.
