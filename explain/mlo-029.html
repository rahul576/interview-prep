How do you validate data in ML pipelines before it reaches training or serving?

MLOps · concept · levels mid, senior

In one line

Validate data before training or serving with schema checks, value expectations (ranges, nulls, uniqueness, categories, row counts), and distribution checks against a reference, using Great Expectations, Pandera, Soda or TFX Data Validation; fail or quarantine bad data and alert owners, backed by data contracts.

Detailed explanation

Data validation is the cheapest place to catch problems: a model trained on broken data fails silently, producing plausible but wrong predictions, and the cost grows the further bad data travels.

Schema checks come first: expected columns, data types, required fields and nullable flags. An upstream rename or type change is caught immediately instead of causing a confusing failure later.

Expectations on values: numeric ranges (age between 0 and 120), null rates below a limit, uniqueness of keys, allowed categories, referential integrity with dimension tables, timestamp sanity, and row counts compared with previous runs (a source sending half its records is a silent killer).

Distribution checks compare statistics—means, quantiles, category frequencies, PSI—with a reference dataset, catching subtle shifts such as a unit change from kilograms to grams that still passes range checks.

Tools express checks as code and produce reports: Great Expectations, Pandera (dataframe schemas in Python), Soda, dbt tests for warehouse models, and TensorFlow Data Validation. Checks run on training data, on feature pipelines and on incoming serving data.

The key design decision is severity. Critical checks fail the pipeline or quarantine the batch so it never reaches training or the online feature store, and alert the data owner. Warning checks log and notify. Data contracts with upstream producers—schema, semantics, freshness and change process—reduce surprises at the source.

How it works

  1. Define schema and expectations per dataset, versioned in Git.
  2. Run validation as the first pipeline step after ingestion.
  3. Compare distributions to a reference window.
  4. On critical failure, stop and quarantine; on warning, continue and notify.
  5. Publish validation results to dashboards for trend tracking.
  6. Route alerts to the owning producer team.

Example

import pandera as pa
from pandera import Column, Check

schema = pa.DataFrameSchema({
    "customer_id": Column(str, unique=True),
    "age": Column(int, Check.in_range(18, 110)),
    "country": Column(str, Check.isin(["IN", "GB", "DE", "US"])),
    "monthly_spend": Column(float, Check.ge(0), nullable=True),
})
schema.validate(df, lazy=True)   # collects all failures before raising
assert df["monthly_spend"].isna().mean() < 0.02, "null rate too high"

Common mistakes

  • Validating only schema, not values or distributions.
  • Checks that only warn, so bad data still trains a model.
  • Validating training data but not serving inputs.
  • Alerting the ML team for problems only the producer can fix.

How to answer in the interview

"Data validation is the cheapest place to catch problems, because a model trained on broken data fails silently. I check schema first, then expectations like ranges, null rates, uniqueness, allowed categories and row counts versus previous runs, then distributions against a reference to catch things like unit changes. Tools like Great Expectations, Pandera or Soda express these as code. Critical failures stop the pipeline or quarantine the batch so it never reaches training or the online store, and alert the data owner. Data contracts with upstream teams prevent many surprises."

Likely follow-up questions

  • Who should fix a failed data check? The data producer owns the fix; the ML team owns protecting the model.
  • How do you set thresholds? From historical variation, tightened over time.
  • What is a data contract? An agreed schema, semantics, quality and change process between producer and consumer.
