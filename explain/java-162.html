A query that used to take 50 milliseconds now takes 5 seconds. How do you fix it?

Databases & SQL · scenario · levels mid, senior

In one line

Treat it as a plan regression: compare the execution plan with EXPLAIN ANALYZE, then look for a missing or unusable index, stale statistics after data growth, lock contention, or a query pattern that no longer scales, fix it and verify the new plan.

Detailed explanation

A query that was fast and became 100 times slower usually changed in one of a few ways. First, I confirm the facts: is it slow every time or only sometimes, did a deployment, schema change or data load happen, and is the database itself overloaded? Slow query logs, pg_stat_statements or the APM trace show the exact statement and its parameters.

Then I read the plan with EXPLAIN (ANALYZE, BUFFERS) (or EXPLAIN ANALYZE in MySQL 8). Typical findings:

  • Sequential/full scan where an index scan used to happen: the index is missing, or is no longer usable because the column is wrapped in a function (lower(email)), there is an implicit type cast (comparing a varchar column with a numeric parameter), or a leading wildcard LIKE '%x'.
  • Estimated vs actual rows far apart: statistics are stale after data growth, so the optimizer picked a nested loop over millions of rows. Fix with ANALYZE.
  • Data growth: the table went from 100 thousand to 50 million rows, so a plan that was fine is now terrible, or OFFSET pagination became deep.
  • Not the plan at all: the query is waiting on locks held by another transaction, visible in pg_stat_activity or performance_schema.

How it works

  1. Reproduce with real parameters and capture timing.
  2. Run EXPLAIN (ANALYZE, BUFFERS) and find the most expensive node.
  3. Compare estimated and actual row counts; refresh statistics if they diverge.
  4. Check index usage and sargability of predicates.
  5. Check waits and locks during the slow period.
  6. Apply one fix (index, rewrite, keyset pagination, fewer columns), then re-run the plan and measure.

Example

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, total FROM orders
WHERE customer_id = 42 AND created_at > now() - interval '30 days'
ORDER BY created_at DESC LIMIT 20;
-- Seq Scan on orders (rows=48,000,000) ... 5,100 ms

CREATE INDEX CONCURRENTLY idx_orders_cust_created
    ON orders (customer_id, created_at DESC);
ANALYZE orders;
-- Index Scan using idx_orders_cust_created ... 0.9 ms

Common mistakes

  • Adding indexes blindly without reading the plan.
  • Running plain EXPLAIN and trusting estimates instead of actual numbers.
  • Forgetting that CREATE INDEX without CONCURRENTLY blocks writes on a big table.
  • Ignoring lock waits and blaming the query.
  • Fixing in staging with a tiny dataset where the plan differs.

How to answer in the interview

"I'd first find the exact statement and parameters from the slow query log or pg_stat_statements and check whether anything changed, like a deployment or a big data load. Then I'd run EXPLAIN ANALYZE with buffers and look at the most expensive step. Usually it's a full scan because an index is missing or unusable, for example a function on the column or a type mismatch, or the row estimates are far off because statistics are stale after growth, which ANALYZE fixes. I'd also check whether the query is actually waiting on locks. Then I'd apply a targeted fix, such as a composite index created concurrently or keyset pagination, and confirm the new plan and latency."

Likely follow-up questions

  • How do you add an index to a 500-million-row table without downtime? CREATE INDEX CONCURRENTLY in Postgres, or online DDL/gh-ost/pt-online-schema-change in MySQL, during low traffic.
  • What is a sargable predicate? One the engine can match against an index, with the bare column compared to a value.
  • Why would a parameterised query get a bad plan? A generic or cached plan chosen for one parameter value can be poor for skewed values.
