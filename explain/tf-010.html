What does known after apply mean, and why do you get the error that count or for_each depends on values that cannot be determined until apply?

Terraform · concept · levels entry, mid, senior

In one line

"Known after apply" marks attributes, like IDs or assigned IPs, that only exist once the provider creates the object; count and for_each must be known at plan time, so deriving them from such values fails, and the fix is to use static keys from configuration with unknown values only in the map's values.

Detailed explanation

During plan, Terraform evaluates every expression. Some values cannot be known yet: the ID of a subnet that does not exist, the IP a cloud assigns, an ARN with a generated suffix. Terraform represents them as unknown values and shows them as (known after apply). Unknowns propagate: anything computed from an unknown is also unknown. For normal arguments that is fine; the provider receives the real value during apply.

count and for_each are different. They determine how many instances exist and what their addresses are (aws_route_table_association.private["a"]). Terraform must know the full set of instances to build the graph and show you a plan, so these expressions must be fully known at plan time. If you write for_each = toset(aws_subnet.private[*].id) in the same configuration that creates the subnets, the set of keys is unknown, and Terraform stops with "The for_each value depends on resource attributes that cannot be determined until apply". The same happens with count = length(data.x.items) when the data source is deferred, or with values from a module whose inputs are unknown.

The clean fix is to use keys that come from configuration: a map whose keys are static names ("a", "b", "c" or subnet names) and whose values may be unknown. Terraform only needs the keys at plan time; the values can be resolved during apply. Alternatively, iterate over the same input map that created the subnets. Workarounds exist: apply once with -target to create the dependency first, or split the configuration into two states. Both add operational friction, so stable keys are preferred.

How it works

  1. Plan evaluates expressions; provider-computed attributes become unknown.
  2. Unknowns flow into dependent expressions.
  3. For count/for_each, Terraform requires known lengths or keys.
  4. If unknown, planning fails with the error.
  5. With static keys, instances are planned; unknown values are filled during apply.

Example

# Fails: keys are subnet IDs, unknown at plan time
resource "aws_route_table_association" "bad" {
  for_each       = toset(aws_subnet.private[*].id)
  subnet_id      = each.value
  route_table_id = aws_route_table.private.id
}

# Works: keys come from configuration, values may be unknown
resource "aws_subnet" "private" {
  for_each   = var.private_subnets          # { a = "10.0.1.0/24", b = "10.0.2.0/24" }
  vpc_id     = aws_vpc.main.id
  cidr_block = each.value
}

resource "aws_route_table_association" "good" {
  for_each       = aws_subnet.private          # keys "a", "b" are known
  subnet_id      = each.value.id
  route_table_id = aws_route_table.private.id
}

Common mistakes

  • Using generated IDs, names with random suffixes or ARNs as for_each keys.
  • Using count with lists whose length comes from another resource's output.
  • Making -target two-step applies a permanent workflow.

How to answer in the interview

"Some attributes, like an ID or an IP the cloud assigns, only exist after the provider creates the object, so the plan shows them as known after apply and treats them as unknown values. That's fine for normal arguments, but count and for_each decide how many instances exist and what their addresses are, so they must be known at plan time. If I build for_each keys from generated IDs in the same configuration that creates them, Terraform can't plan and raises this error. The fix is static keys from configuration, like a map keyed by subnet name with the IDs as values. Two-step applies with -target or splitting the configuration work, but stable keys are cleaner."

Likely follow-up questions

  • How does a map with static keys and unknown values avoid it? Only keys determine instance addresses; values can stay unknown until apply.
  • Why prefer for_each over count? Stable keys avoid shifting indexes and unwanted replacements.
  • Do Stacks help? Yes, they can defer components with unknown inputs to a later step.
