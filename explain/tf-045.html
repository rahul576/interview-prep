Your company is considering moving from Terraform to OpenTofu. What do you evaluate and how would you migrate?

Terraform · scenario · levels mid, senior, lead

In one line

Evaluate licensing (Terraform under BSL since 2023 vs OpenTofu under MPL 2.0 in the Linux Foundation), compatibility and feature divergence, the registry, tooling and support ecosystem, then migrate one configuration at a time, requiring a clean plan before switching CI.

Detailed explanation

In August 2023 HashiCorp moved Terraform from MPL 2.0 to the Business Source License, which restricts offering competing products. The community forked the last MPL version as OpenTofu, now a Linux Foundation project. For most internal users the BSL is not prohibitive, so the questions are strategic: legal comfort, vendor independence and features.

Compatibility: OpenTofu reads Terraform state, uses the same HCL language and the same providers (served from its own registry, which mirrors the common providers). But the projects have diverged. OpenTofu has added things such as client-side state encryption, early variable evaluation (variables in backend and module source blocks) and for_each on provider blocks. Terraform has added Stacks, list resources with terraform query, actions and deeper HCP Terraform integration. If you depend on HCP Terraform workspaces, Sentinel policies or Terraform-only features, migration is harder.

Ecosystem: check CI actions, linters, security scanners, Atlantis or other automation platforms, private module registries, and whether support contracts or consultants are tied to one tool. Then check your current Terraform version: migration is simplest from versions close to the fork, and OpenTofu publishes version-specific migration guides; newer Terraform-only syntax must be removed first.

The migration itself should be boring: one configuration at a time, switch the binary in a branch, tofu init, tofu plan, require no changes, back up state, then switch CI.

How it works

  1. Decide drivers: licence, cost, independence, features.
  2. Inventory Terraform versions, HCP usage, policy tooling and Terraform-only features.
  3. Run a pilot on a non-production configuration.
  4. Back up state; run tofu init and tofu plan; require a clean plan.
  5. Switch that configuration's pipeline; repeat in waves.
  6. Decide whether to adopt OpenTofu-only features, which makes going back harder.

Example

terraform state pull > backup-pre-tofu.tfstate   # safety copy
tofu init        # re-downloads providers from the OpenTofu registry
tofu plan        # expect: No changes. Your infrastructure matches the configuration.

Common mistakes

  • Treating it as a drop-in swap without a clean plan per configuration.
  • Migrating while also upgrading providers, mixing two sources of change.
  • Adopting state encryption immediately, then struggling to roll back.
  • Ignoring HCP Terraform or Sentinel dependencies.

How to answer in the interview

"The main driver is licensing: Terraform moved to the BSL in 2023, OpenTofu is the MPL fork in the Linux Foundation. I check compatibility first: OpenTofu reads Terraform state and uses the same providers and syntax, but they have diverged, with OpenTofu adding state encryption and early evaluation, and Terraform adding Stacks, query and HCP features. I review our versions, HCP usage, policy tooling and support. Then I migrate one configuration at a time: switch the binary in a branch, init and plan, require no changes, and only then switch CI."

Likely follow-up questions

  • What makes going back hard? OpenTofu-only features such as state encryption and early evaluation syntax.
  • Do providers differ? Same provider binaries, different registry hostnames.
  • Is the BSL a problem for internal use? Generally not; it targets competing commercial offerings.
