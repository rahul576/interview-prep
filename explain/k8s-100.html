What happens in Kubernetes from the moment you run kubectl apply on a Deployment until the pods are running?

Kubernetes · concept · levels entry, mid

In one line

kubectl apply goes through authentication, authorisation and admission at the API server, is stored in etcd, then the Deployment and ReplicaSet controllers create pods, the scheduler binds them to nodes, the kubelet starts them via the container runtime and CNI, and readiness adds them to Service endpoints.

Detailed explanation

Kubernetes is a set of independent control loops that react to changes in the API server; no component calls another directly. Understanding that chain is what lets you debug where a rollout stops.

The API server first authenticates the caller (certificate, token or OIDC), then authorises the request with RBAC. Mutating admission (webhooks, defaults, Pod Security labels) can modify the object, schema validation runs, then validating admission (policies such as Kyverno, Gatekeeper or ValidatingAdmissionPolicy) can reject it. The Deployment is persisted in etcd.

The Deployment controller in kube-controller-manager sees the new object and creates a ReplicaSet with a pod-template hash. The ReplicaSet controller creates the desired number of Pod objects, which pass admission again and have no nodeName yet. The scheduler filters nodes on resource requests, taints and tolerations, affinity and volume topology, scores the remainder and binds each pod to a node.

The kubelet on that node sees the bound pod and calls the container runtime (containerd or CRI-O) through CRI: create the pod sandbox, the CNI plugin assigns an IP and sets up networking, volumes are mounted, images pulled, init containers run, then app containers start. Startup and readiness probes run; once ready, the EndpointSlice controller adds the pod IP to the Service, and kube-proxy or the CNI dataplane routes traffic to it.

How it works

  1. API server: authenticate, authorise, mutate, validate, store in etcd.
  2. Deployment controller creates a ReplicaSet.
  3. ReplicaSet controller creates Pods (unscheduled).
  4. Scheduler filters, scores and binds pods to nodes.
  5. Kubelet + runtime + CNI create sandbox, network, volumes, containers.
  6. Readiness passes; EndpointSlices updated; traffic flows.

Example

kubectl apply -f deploy.yaml
kubectl get rs -l app=web                # ReplicaSet created
kubectl get pods -l app=web -o wide      # NODE column filled after scheduling
kubectl get events --sort-by=.lastTimestamp | tail
# Scheduled  -> Pulling -> Pulled -> Created -> Started
kubectl get endpointslices -l kubernetes.io/service-name=web

Common mistakes

  • Thinking kubectl talks to nodes directly.
  • Saying the scheduler starts containers (it only binds).
  • Forgetting admission webhooks, which often explain rejected or modified objects.
  • Assuming a Running pod receives traffic before readiness passes.

How to answer in the interview

"kubectl sends the manifest to the API server, which authenticates me, authorises with RBAC, runs mutating and validating admission and stores the Deployment in etcd. The Deployment controller creates a ReplicaSet and the ReplicaSet controller creates pod objects without a node. The scheduler filters nodes by requests, taints and affinity, scores them and binds each pod. The kubelet on that node asks the container runtime to create the sandbox, the CNI gives it an IP, volumes are mounted, images pulled and containers started. When readiness passes, the pod is added to the Service's EndpointSlices and gets traffic."

Likely follow-up questions

  • Where do you look if pods are created but never get a node? The scheduler's FailedScheduling events in kubectl describe pod.
  • What if the ReplicaSet exists but no pods? Admission or quota rejected them; check ReplicaSet events.
  • What does the kubelet report back? Pod status and conditions, written to the API server.
