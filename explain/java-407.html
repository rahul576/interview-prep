What is the CAP theorem, and how does PACELC refine it?

Databases & SQL · concept · levels mid, senior

In one line

CAP says that during a network partition a distributed system must choose consistency (linearizable reads) or availability (every node answers); PACELC adds that else, when there is no partition, you still trade latency against consistency.

Detailed explanation

CAP, proposed by Eric Brewer and proven by Gilbert and Lynch, uses precise definitions: Consistency means linearizability, every read sees the latest completed write; Availability means every request to a non-failing node gets a non-error response; Partition tolerance means the system keeps operating when messages between nodes are lost. In a real network partitions happen, so partition tolerance is not optional, and the real question is behaviour during a partition.

A CP system refuses or blocks some requests on the minority side to avoid serving stale or conflicting data. ZooKeeper, etcd and Consul (consensus via ZAB/Raft), HBase, and MongoDB with majority write and read concerns behave this way. An AP system keeps answering on both sides and reconciles later; Cassandra and DynamoDB with eventually consistent reads, and Riak, are classic examples. Many systems are tunable per request, so "CP or AP" describes a configuration rather than a product.

CAP says nothing about the normal case, which is most of the time. PACELC (Daniel Abadi) fills that gap: if Partition, choose A or C; Else, choose Latency or Consistency. Synchronous replication or quorum reads give consistency but add round trips; reading from the nearest replica is fast but may be stale. Cassandra and DynamoDB are PA/EL by default; consensus-based stores and Spanner-style databases are PC/EC.

How it works

  1. Data is replicated across nodes.
  2. A partition splits nodes that cannot communicate.
  3. A CP design lets only the majority side (or the leader) accept operations.
  4. An AP design lets all sides accept operations and resolves conflicts afterwards (last-write-wins, vector clocks, CRDTs).
  5. Without a partition, the system still chooses between waiting for replicas (consistency) and answering locally (latency).

Example

Cassandra, RF=3:
  CONSISTENCY ONE      -> fast, available with 2 replicas down, may read stale   (A / L)
  CONSISTENCY QUORUM   -> 2 of 3 must answer, read-your-writes with QUORUM writes (C)

PostgreSQL primary + async replica:
  read from primary    -> consistent
  read from replica    -> lower load, possibly stale (replication lag)

Common mistakes

  • Saying you "pick two of three" as if CA were a real option for a distributed system.
  • Mixing up CAP consistency with ACID consistency.
  • Labelling a product permanently CP or AP when its behaviour is configurable.
  • Ignoring the latency trade-off that applies all the time, not only during failures.

How to answer in the interview

"CAP says that when the network partitions, a distributed system must choose between consistency, meaning every read sees the latest write, and availability, meaning every node still responds. Partitions are inevitable, so it's really a choice about failure behaviour. CP systems like etcd or ZooKeeper reject requests on the minority side; AP systems like Cassandra or DynamoDB with eventual reads keep answering and reconcile later. PACELC adds that even without a partition, you trade latency against consistency, because synchronous replication or quorums cost round trips. In practice I choose per operation, for example quorum reads for balances and local reads for feeds."

Likely follow-up questions

  • Where does a single Postgres primary with async replicas sit? Writes are CP-like (primary unreachable means no writes); replica reads favour latency and can be stale.
  • What is linearizability? Operations appear to take effect atomically at one point in time, in real-time order.
  • How do AP systems resolve conflicts? Last-write-wins timestamps, vector clocks or CRDTs.
