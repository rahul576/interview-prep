How do CodePipeline, CodeBuild and CodeDeploy work together?

Cloud (AWS) · concept · levels mid

In one line

CodePipeline orchestrates the release as stages (source, build, test, approval, deploy), CodeBuild runs builds and tests in managed containers from a buildspec.yml, and CodeDeploy deploys to EC2/on-premises, ECS or Lambda with in-place, blue/green, canary or linear strategies and automatic rollback.

Detailed explanation

CodePipeline models the workflow as ordered stages of actions. A source stage triggers on changes in GitHub, GitLab or Bitbucket through CodeConnections (formerly CodeStar Connections), on an S3 object or an ECR image push. CodeCommit is no longer offered to new customers, so new projects use an external Git host. Artifacts pass between stages through an encrypted S3 artifact bucket. Stages can include manual approvals, parallel actions, and invoke Lambda, Step Functions or CloudFormation deployments. V2 pipelines add triggers filtered by branch, tag or file path, pipeline variables, and stage-level rollback conditions.

CodeBuild runs each build in a fresh managed container image, or your custom image, with compute sizes from small to GPU, plus Lambda-based and reserved fleets. A buildspec.yml defines install, pre_build, build and post_build phases, environment variables and secrets from Parameter Store or Secrets Manager, artifacts and reports (JUnit, coverage). It scales without build servers and bills per minute, and can run in your VPC to reach private resources.

CodeDeploy handles deployments. For EC2/on-premises, an agent runs an appspec.yml with lifecycle hooks (BeforeInstall, AfterInstall, ApplicationStart, ValidateService) in place or blue/green with Auto Scaling groups. For ECS, it shifts ALB traffic between blue and green target groups. For Lambda, it shifts alias weights between versions. Predefined configs like Canary10Percent5Minutes or Linear10PercentEvery1Minute control traffic shifting, and CloudWatch alarms trigger automatic rollback.

All three use IAM service roles, so no long-lived credentials live in the pipeline.

How it works

  1. Developer merges to main; CodeConnections triggers the pipeline.
  2. Source artifact is stored in S3.
  3. CodeBuild builds, tests and pushes an image to ECR.
  4. Optional manual approval for production.
  5. CodeDeploy shifts traffic gradually, running validation hooks.
  6. Alarms during the bake time trigger automatic rollback.

Example

# buildspec.yml
version: 0.2
phases:
  pre_build:
    commands:
      - aws ecr get-login-password | docker login --username AWS --password-stdin $REPO
  build:
    commands:
      - docker build -t $REPO:$CODEBUILD_RESOLVED_SOURCE_VERSION .
      - docker push $REPO:$CODEBUILD_RESOLVED_SOURCE_VERSION
  post_build:
    commands:
      - printf '{"ImageURI":"%s"}' $REPO:$CODEBUILD_RESOLVED_SOURCE_VERSION > imageDetail.json
artifacts:
  files: [imageDetail.json, appspec.yaml, taskdef.json]

Common mistakes

  • No rollback alarms, so canaries shift fully even when errors rise.
  • Over-privileged pipeline roles that can modify anything in the account.
  • Building different artifacts per environment instead of promoting one.
  • Assuming CodeCommit is available for new accounts.

How to answer in the interview

"CodePipeline orchestrates the release as stages: source from GitHub through CodeConnections, S3 or ECR, then build and test, approvals and deployment, with artifacts passed through S3. CodeBuild runs builds and tests in managed containers defined by a buildspec.yml, scaling without build servers. CodeDeploy deploys to EC2 or on-premises, ECS or Lambda, in place or blue/green, with canary or linear traffic shifting, and rolls back automatically when CloudWatch alarms fire. Each piece uses IAM roles, so there are no stored keys."

Likely follow-up questions

  • How does a CodeDeploy canary for Lambda work? It shifts a percentage of alias traffic to the new version, waits, checks alarms and hooks, then shifts the rest.
  • How deploy to multiple accounts? Pipeline in a tooling account assumes deployment roles in target accounts.
  • Why promote the same artifact? What was tested is exactly what reaches production.
