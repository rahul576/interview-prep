Compare rolling, blue-green and canary deployments.

DevOps & CI/CD · concept · levels mid, senior

In one line

Rolling replaces instances gradually without extra capacity, blue-green switches traffic between two full environments for instant rollback at higher cost, and canary sends a small percentage of traffic to the new version first to limit blast radius; feature flags decouple deploy from release in all of them.

Detailed explanation

Rolling deployment: instances are replaced a few at a time, for example Kubernetes' default RollingUpdate with maxSurge and maxUnavailable. It needs little or no extra capacity and is simple. But old and new versions run side by side during the rollout, so both must be compatible with the same database and API contracts, and rollback is another rollout, which takes time. Readiness probes are essential so traffic only reaches healthy pods.

Blue-green deployment: two identical environments, blue (live) and green (idle). You deploy to green, test it fully, then switch traffic at the load balancer, DNS or Kubernetes Service selector. Rollback is instant: switch back. Costs: roughly double infrastructure during the release, and database changes need care because both versions may use the same database; use backward-compatible expand and contract migrations. Long-lived sessions and caches may need warm-up.

Canary release: the new version receives a small share of traffic, such as 5%, while you monitor error rate, latency and business metrics. If healthy, increase to 25%, 50%, 100%; if not, abort with minimal user impact. This gives the smallest blast radius and real production validation, but needs traffic splitting (service mesh, ingress or gateway weights, Argo Rollouts, Flagger) and good observability, ideally with automated analysis.

Feature flags complement all three: code is deployed dark, then features are enabled for internal users, a percentage or specific customers, and turned off instantly without redeploying.

How it works

  1. Rolling: update the Deployment; pods replaced in batches with readiness checks.
  2. Blue-green: deploy green, test, switch the Service selector, keep blue for rollback.
  3. Canary: deploy canary, route 5%, analyse metrics, step up or abort.
  4. Flags: deploy with feature off; enable gradually.

Example

apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata: { name: orders }
spec:
  replicas: 10
  strategy:
    canary:
      steps:
      - setWeight: 5
      - pause: { duration: 10m }
      - analysis: { templates: [{ templateName: error-rate }] }
      - setWeight: 50
      - pause: { duration: 10m }
  selector: { matchLabels: { app: orders } }
  template:
    metadata: { labels: { app: orders } }
    spec: { containers: [{ name: orders, image: registry/orders:1.8.0 }] }

Common mistakes

  • Blue-green with a breaking database migration, making rollback impossible.
  • Canary without metrics, so nobody can tell if it's healthy.
  • Missing readiness probes in rolling updates.
  • Using flags but never cleaning them up.

How to answer in the interview

"Rolling replaces instances a few at a time; it needs no extra capacity, but old and new run side by side and rollback is another rollout. Blue-green keeps two environments, deploys to the idle one, tests it and switches traffic, so rollback is instant, but it doubles infrastructure during release and needs backward-compatible database migrations. Canary sends a small share, say 5%, to the new version, watches error rate and latency, and increases gradually, limiting blast radius, but needs traffic splitting and good metrics, for example with Argo Rollouts. Feature flags decouple deploy from release in all cases."

Likely follow-up questions

  • DB changes in blue-green? Expand and contract: add compatible changes first, remove old columns after both versions are done.
  • When is rolling enough? Low-risk internal services with good tests and probes.
  • Automated canary analysis? Compare canary metrics to baseline and abort automatically on degradation.
