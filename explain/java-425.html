Design a distributed unique ID generator.

System Design · design · levels senior, lead

In one line

A distributed ID generator must be unique, ideally time-sortable and coordination-free at high throughput: UUID v4 is random but hurts index locality, UUID v7 adds a time prefix and is a good default, Snowflake packs timestamp + machine ID + sequence into 64 bits, and ticket servers hand out ID ranges; all time-based schemes must handle clock skew.

Detailed explanation

Clarify requirements: global uniqueness, size (64-bit fits a long and indexes better than 128-bit), roughly time-ordered (good for B-tree insert locality and pagination), throughput (e.g. 100k IDs/s), no single point of failure, and whether IDs may reveal creation time or volume.

UUID v4: 122 random bits, no coordination, practically collision-free. But random keys scatter inserts across a B-tree, causing page splits and poor cache locality, especially as a clustered primary key in InnoDB. They are also 16 bytes.

UUID v7 (RFC 9562, 2024): a 48-bit Unix millisecond timestamp followed by random bits. Still 128 bits and coordination-free, but time-ordered, so inserts append to the right side of the index. A strong default today; Java libraries and many databases (e.g. PostgreSQL 18's uuidv7()) support it.

Snowflake (Twitter): 64 bits = 1 sign bit + 41-bit millisecond timestamp (custom epoch, about 69 years) + 10-bit worker ID (1,024 nodes) + 12-bit sequence (4,096 IDs per ms per node). Compact and sortable, but needs unique worker IDs (assigned via config, ZooKeeper, or Kubernetes StatefulSet ordinal) and careful clock handling: if the clock moves backwards, wait or refuse, otherwise duplicates are possible. Variants: Sonyflake, Instagram's DB-based scheme.

Ticket server / segment allocation: a database sequence hands out ranges (e.g. 1,000 IDs) to each instance, which serves them from memory (Meituan Leaf-segment, Flickr ticket servers). Simple and dense, but depends on the DB for refills (pre-fetch the next segment) and IDs are not strictly time-ordered across instances.

How it works

  1. Snowflake node gets a unique worker ID at startup.
  2. On each request: read current millis.
  3. If same millis as last, increment sequence; on overflow, spin until the next millisecond.
  4. If time < last (clock moved back), wait until caught up or throw.
  5. Compose (ts - epoch) << 22 | worker << 12 | seq.

Example

public final class Snowflake {
    private static final long EPOCH = 1_704_067_200_000L; // 2024-01-01T00:00:00Z
    private final long workerId; private long lastTs = -1, seq = 0;

    public Snowflake(long workerId) {
        if (workerId < 0 || workerId > 1023) throw new IllegalArgumentException();
        this.workerId = workerId;
    }

    public synchronized long nextId() {
        long ts = System.currentTimeMillis();
        if (ts < lastTs) throw new IllegalStateException("Clock moved backwards by " + (lastTs - ts) + " ms");
        if (ts == lastTs) {
            seq = (seq + 1) & 4095;
            if (seq == 0) while ((ts = System.currentTimeMillis()) <= lastTs) Thread.onSpinWait();
        } else seq = 0;
        lastTs = ts;
        return ((ts - EPOCH) << 22) | (workerId << 12) | seq;
    }
}

Common mistakes

  • Random UUID v4 as a clustered primary key on a huge table.
  • Duplicate worker IDs after autoscaling.
  • Ignoring NTP clock adjustments.
  • Exposing sequential IDs publicly, leaking business volume.
  • Assuming time-ordered IDs are strictly ordered across nodes.

How to answer in the interview

"First the requirements: unique, ideally time-sortable for index locality, high throughput without coordination. UUID v4 needs no coordination but is 128 bits and random, which fragments B-tree indexes. UUID v7 adds a millisecond timestamp prefix and is my default today. If I need 64-bit IDs, I'd use Snowflake: 41 bits of timestamp, 10 bits of worker ID and 12 bits of sequence, with unique worker IDs assigned at startup and refusing or waiting if the clock moves backwards. A ticket server handing out ranges is a simpler alternative."

Likely follow-up questions

  • Why are random UUIDs poor InnoDB keys? InnoDB clusters rows by primary key; random inserts cause page splits, fragmentation and larger secondary indexes.
  • How to assign worker IDs? StatefulSet ordinals, ZooKeeper/etcd leases, or a DB table with leases.
  • Sorting across nodes? Only roughly by millisecond; not a substitute for causal ordering.
