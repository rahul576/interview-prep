What are the methods of the Object class, and which ones do you usually override?

Core Java & OOP · concept · levels entry

In one line

Object provides equals, hashCode, toString, getClass, clone, finalize and the monitor methods wait, notify, notifyAll; in practice you override equals and hashCode together and toString, and avoid clone and finalize.

Detailed explanation

Every class extends java.lang.Object, directly or indirectly, so these methods exist on every object.

  • equals(Object): logical equality. The default is reference equality (this == obj). Override for value objects.
  • hashCode(): an int used by hash-based collections. Must be consistent with equals: equal objects must have equal hash codes.
  • toString(): a readable representation. The default is ClassName@hexHash, which is useless in logs.
  • getClass(): returns the runtime Class object; it is final.
  • clone(): protected; creates a field-by-field (shallow) copy if the class implements Cloneable, otherwise throws CloneNotSupportedException. The design is widely regarded as broken: it bypasses constructors, is shallow by default, conflicts with final fields and uses a marker interface that does not declare the method.
  • finalize(): called by the GC before reclaiming an object. It is deprecated for removal (JEP 421, Java 18) because timing is unpredictable and it hurts GC performance. Use try-with-resources or java.lang.ref.Cleaner.
  • wait(), notify(), notifyAll(): final methods for coordinating threads on an object's monitor; must be called while holding that object's lock (inside synchronized). Modern code prefers java.util.concurrent (locks with conditions, queues, latches).

Records (Java 16) generate equals, hashCode and toString automatically, which removes most of the boilerplate for value types.

How it works

  1. A class inherits all Object methods by default.
  2. Collections call equals and hashCode to find and compare elements.
  3. String concatenation, loggers and debuggers call toString.
  4. Threads call wait to release the monitor and sleep until notified.
  5. The GC may call finalize (if still enabled) at an unpredictable time.

Example

public final class Money {
    private final BigDecimal amount;
    private final String currency;

    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Money m)) return false;
        return amount.compareTo(m.amount) == 0 && currency.equals(m.currency);
    }
    @Override public int hashCode() { return Objects.hash(amount.stripTrailingZeros(), currency); }
    @Override public String toString() { return amount + " " + currency; }
}
// Or simply: record Money(BigDecimal amount, String currency) {}

Common mistakes

  • Overriding equals but not hashCode, breaking HashMap and HashSet.
  • Writing equals(Money other), which overloads instead of overrides; use @Override.
  • Relying on finalize for closing files or connections.
  • Calling wait or notify without holding the lock, causing IllegalMonitorStateException.

How to answer in the interview

"Object gives every class equals, hashCode, toString, getClass, clone, finalize and the monitor methods wait, notify and notifyAll. I regularly override equals and hashCode together for value objects and entities used as keys, and toString for readable logs; for simple value types I use records, which generate all three. I avoid clone because it's shallow and bypasses constructors, so I prefer copy constructors or factory methods. finalize is deprecated for removal, so cleanup is done with try-with-resources or a Cleaner. wait and notify are final and low level; I usually use java.util.concurrent instead."

Likely follow-up questions

  • Why is clone() considered broken? Shallow copy, no constructor call, Cloneable doesn't declare clone, and final fields can't be reassigned.
  • Why must wait be called in a loop? Because of spurious wakeups and changed conditions.
  • Which Object methods are final? getClass, wait, notify and notifyAll.
