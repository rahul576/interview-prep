Design an event-driven order processing system on AWS.

Cloud (AWS) · design · levels senior

In one line

An order API stores the order and its OrderPlaced event atomically (DynamoDB Streams or a transactional outbox), EventBridge fans the event out to one SQS queue per consumer, idempotent Lambda or ECS consumers process it with DLQs, and a Step Functions saga coordinates payment and inventory with compensations, all traced end to end.

Detailed explanation

Ingestion: API Gateway (or an ALB) receives the order, a Lambda or ECS service validates it, applies an idempotency key from the client so retries do not create duplicates, stores the order with status PENDING and returns 202 Accepted with the order ID.

Reliable publishing: writing to the database and then calling PutEvents is a dual write; if the second call fails, the event is lost. Instead, use DynamoDB Streams on the orders table, with EventBridge Pipes turning new items into events, or in RDS an outbox table written in the same transaction and relayed by a poller or CDC (for example DMS or Debezium). Delivery is at least once.

Fan-out: EventBridge rules route OrderPlaced to separate SQS queues for payment, inventory, notifications and analytics. Each queue buffers bursts, scales its consumers independently and has its own dead-letter queue, so a broken email service never blocks payments. SNS plus SQS is an alternative for very high throughput.

Consumers on Lambda or ECS must be idempotent, keyed on order ID and event ID (Powertools idempotency with a DynamoDB table works well), use partial batch responses, and alarm on DLQ depth and queue age.

Coordination: payment and inventory must succeed together. A Step Functions Standard workflow orchestrates the saga: reserve inventory, charge payment, confirm the order; if payment fails, run compensating steps such as releasing stock and cancelling the order, then emit OrderFailed. Choreography with events is possible, but orchestration is easier to observe.

Observability: X-Ray or OpenTelemetry tracing across API, EventBridge, SQS and Lambda, structured logs with order ID, business metrics like orders per minute and failure rate, and archive and replay on the bus for recovery.

How it works

  1. Client POSTs the order with an idempotency key.
  2. Order stored; stream or outbox emits OrderPlaced to EventBridge.
  3. Rules deliver to per-service SQS queues.
  4. A Step Functions saga reserves stock and charges payment.
  5. Failures trigger compensations and an OrderFailed event.
  6. Notification and analytics consumers react independently.

Example

# SAM snippet: rule to a queue, consumer with DLQ
InventoryQueue:
  Type: AWS::SQS::Queue
  Properties:
    VisibilityTimeout: 180
    RedrivePolicy: {deadLetterTargetArn: !GetAtt InventoryDLQ.Arn, maxReceiveCount: 5}
OrderPlacedRule:
  Type: AWS::Events::Rule
  Properties:
    EventBusName: orders
    EventPattern: {source: [com.shop.orders], detail-type: [OrderPlaced]}
    Targets: [{Arn: !GetAtt InventoryQueue.Arn, Id: inventory}]
InventoryFn:
  Type: AWS::Serverless::Function
  Properties:
    Handler: inventory.handler
    Runtime: python3.13
    Events:
      Q: {Type: SQS, Properties: {Queue: !GetAtt InventoryQueue.Arn,
          FunctionResponseTypes: [ReportBatchItemFailures]}}

Common mistakes

  • Dual writes without an outbox or stream, silently losing events.
  • One shared queue for all consumers, coupling their failures.
  • Non-idempotent consumers charging a card twice on redelivery.
  • No compensation path, leaving stock reserved for failed payments.

How to answer in the interview

"The order API behind API Gateway validates the request, stores the order and publishes OrderPlaced. To avoid losing events when the write succeeds but publishing fails, I write the order and event atomically, using DynamoDB Streams or an outbox table, and relay to EventBridge. Rules fan out to separate SQS queues for payment, inventory, notifications and analytics, so each scales and fails independently. Consumers are idempotent on the order ID, with DLQs and alarms. Payment and inventory form a saga orchestrated by Step Functions with compensations, and tracing covers the whole flow."

Likely follow-up questions

  • Payment succeeds but inventory fails? The saga refunds or voids the payment and marks the order failed, or backorders per business rules.
  • Why SQS between EventBridge and consumers? Buffering, retries, DLQs and controlled concurrency per consumer.
  • How preserve order per customer? FIFO queues with message group ID per order or customer where needed.
