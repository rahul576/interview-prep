How do you choose the number of shards and replicas for an index?

Elasticsearch · concept · levels mid, senior

In one line

Primary shard count is fixed at creation (change it with split, shrink or reindex). Size shards at roughly 10–50 GB (and under about 200 million documents), avoid oversharding, use replicas (usually 1) for HA and read throughput (changeable at any time), and for time-series data use data streams with ILM rollover so each backing index stays well sized.

Detailed explanation

Primary shards split the data. Each is a Lucene index that can live on a different node, so more primaries means more parallelism for indexing and larger total capacity. Routing is hash(_routing) % number_of_primary_shards, which is why the number can't change without rewriting data. The _split API (to a multiple of the current count), _shrink (to a factor), or _reindex are the ways out.

Sizing guidance (Elastic's current recommendations):

  • Aim for 10–50 GB per shard. Search-heavy indices often prefer the lower end, logs the upper end.
  • Keep each shard below about 200M documents.
  • Avoid huge numbers of small shards. Each shard has overhead (heap for metadata, file handles, cluster state, a search thread per shard per query). The old rule "20 shards per GB of heap" has been replaced in recent versions by per-shard field-mapping overhead guidance, but the principle stands: fewer, well-sized shards.

Too few shards means very large shards: slow recovery and relocation, and limited parallelism. Too many (oversharding) means wasted memory and slower searches, because one query fans out to hundreds of tiny shards, each with fixed overhead.

Replicas are full copies of each primary on different nodes. They give high availability (a replica is promoted if a primary's node fails) and extra read capacity. They can be changed at any time (number_of_replicas), and 1 is typical. A single-node cluster can't allocate replicas, which is why its health shows yellow.

Time-series data (logs, metrics, events): don't create one giant index. Use data streams with ILM rollover at a max primary shard size (for example 50 GB) or age (for example 1 day). Each backing index then has a predictable size, and old indices move to warm or cold tiers or are deleted cheaply.

How it works

  1. Estimate the data size, growth and retention.
  2. Primaries ≈ expected index size ÷ target shard size (for example 300 GB ÷ 30 GB = 10).
  3. Spread the shards evenly across data nodes.
  4. Replicas = 1 (raise them for read-heavy workloads or stricter HA).
  5. For time series, use a data stream with rollover on max_primary_shard_size.
  6. Monitor _cat/shards and adjust with split, shrink or reindex if needed.

Example

PUT _ilm/policy/logs-policy
{ "policy": { "phases": {
    "hot":    { "actions": { "rollover": { "max_primary_shard_size": "50gb", "max_age": "1d" } } },
    "delete": { "min_age": "30d", "actions": { "delete": {} } } } } }

PUT _index_template/logs-app
{ "index_patterns": ["logs-app-*"], "data_stream": {},
  "template": { "settings": { "number_of_shards": 2, "number_of_replicas": 1,
                              "index.lifecycle.name": "logs-policy" } } }

Common mistakes

  • One index per day per tenant with 5 shards each, which creates thousands of tiny shards.
  • Planning to "just change the shard count later" without knowing about split, shrink or reindex.
  • Setting replicas to 0 in production for ingest speed and then forgetting to restore them.
  • Uneven shard distribution creating hot nodes.

How to answer in the interview

"The number of primary shards is fixed at creation because documents are routed by a hash modulo that number. Changing it needs split, shrink or reindex. I aim for shard sizes of roughly 10 to 50 gigabytes and avoid lots of tiny shards, because each shard costs memory and cluster-state overhead, and a query fans out to every shard. Replicas give high availability and read throughput, can be changed any time, and one is typical. For logs and events I use data streams with ILM rollover by size or age, so each backing index stays well sized and retention is just deleting old indices."

Likely follow-up questions

  • A query hitting 2,000 shards? Huge fan-out overhead, coordinating node pressure and higher latency. Reduce the shards or narrow the indices searched.
  • Custom routing? Route by tenant id so a query hits one shard, but watch for hot shards.
  • Why is a single node yellow? Replicas can't be allocated on the same node as their primary.
