What is the difference between abstraction and encapsulation?

Core Java & OOP · concept · levels entry, mid

In one line

Abstraction hides complexity by exposing what an object does through a simple contract (interfaces, abstract classes); encapsulation hides internal state by bundling data with its methods and restricting access so invariants are protected.

Detailed explanation

The two are often confused because both "hide" something, but they work at different levels.

Abstraction is a design-level idea. You decide which operations matter to the caller and hide how they are carried out. A PaymentGateway interface with charge(amount, card) lets the checkout service ignore whether the implementation calls Stripe, Razorpay or a bank API. In Java you achieve abstraction with interfaces, abstract classes, and well-chosen method signatures. It reduces cognitive load and lets implementations change without affecting callers, which is also what makes dependency injection and mocking work.

Encapsulation is an implementation-level idea. A class keeps its fields private and offers methods that operate on them, so all state changes go through code that can validate input and maintain invariants. A BankAccount doesn't expose balance as a public field; it exposes deposit and withdraw, which reject negative amounts and overdrafts. Encapsulation lets you change the internal representation, say from double to BigDecimal, without breaking callers.

A useful slogan: abstraction hides complexity, encapsulation hides data. They work together: an interface provides abstraction, and the implementing class encapsulates its state.

A frequent interview trap is "a class with getters and setters for every field is encapsulated". Technically the fields are private, but if anyone can set any value, the invariants are not protected. Real encapsulation favours behaviour methods ("tell, don't ask") and immutable objects.

How it works

  1. Identify the operations a client needs; define them as an interface or abstract type.
  2. Clients depend only on that abstraction.
  3. Implementations keep fields private.
  4. All state changes go through methods that validate and enforce rules.
  5. Return copies or unmodifiable views, never internal mutable collections.

Example

public interface PaymentGateway {               // abstraction: what, not how
    PaymentResult charge(Money amount, CardToken card);
}

public class BankAccount {                      // encapsulation: state + rules
    private BigDecimal balance = BigDecimal.ZERO;
    private final List<Txn> history = new ArrayList<>();

    public void withdraw(BigDecimal amount) {
        if (amount.signum() <= 0) throw new IllegalArgumentException("positive only");
        if (balance.compareTo(amount) < 0) throw new InsufficientFundsException();
        balance = balance.subtract(amount);
        history.add(Txn.debit(amount));
    }
    public List<Txn> history() { return List.copyOf(history); } // no leaking internals
}

Common mistakes

  • Defining encapsulation as "private fields plus getters and setters".
  • Returning mutable internal collections from getters.
  • Creating interfaces with one implementation that just mirror the class, adding no real abstraction.
  • Mixing up the two definitions.

How to answer in the interview

"Abstraction is about design: exposing what an object does and hiding how, so callers depend on a simple contract. In Java that's interfaces and abstract classes; for example a PaymentGateway interface hides whether we call Stripe or a bank. Encapsulation is about implementation: bundling data with the methods that operate on it and restricting direct access with private fields, so every change goes through methods that validate and protect invariants, like withdraw refusing an overdraft. In short, abstraction hides complexity, encapsulation hides internal state."

Likely follow-up questions

  • Is a class with public getters and setters for every field really encapsulated? Only weakly; invariants aren't protected and the representation leaks.
  • Interface or abstract class for abstraction? Interface by default; abstract class when sharing state or code.
  • How do records relate? They're transparent data carriers, deliberately encapsulating little.
