How does the Kubernetes controller pattern work, and why is it described as level-triggered?

Kubernetes · concept · levels mid, senior

In one line

A controller runs a reconcile loop: watch the desired state in the API, observe the actual state, take the next action to close the gap, repeat. It is level-triggered because it acts on the current state, not on individual events, so missed events or restarts don't matter; it uses informers, work queues with retries, and idempotent actions.

Detailed explanation

Kubernetes has no central orchestrator issuing commands. Instead, dozens of controllers each own one concern: the Deployment controller manages ReplicaSets, the ReplicaSet controller manages pods, the EndpointSlice controller tracks Service backends, the node controller handles unhealthy nodes. Each compares the spec (desired) with the world (actual) and acts, writing results to status.

Edge-triggered systems react to events: "a pod was deleted, so create one". If an event is lost, the system is wrong forever. Level-triggered systems look at the current level: "I want 3 pods and see 2, so create 1". The event is just a hint to look again. If the controller crashes, misses notifications or two events collapse into one, the next reconcile still sees the difference and fixes it. Controllers also run periodic resyncs as a safety net. This design is why Kubernetes self-heals and tolerates partial failures and why multiple controllers can cooperate without coordination.

Internally (client-go, controller-runtime):

  • Informers list and watch resources, maintaining a local cache so reads don't hit the API server, and call handlers on add, update or delete.
  • Handlers push only a key (namespace/name) into a rate-limited work queue, which deduplicates keys, so ten updates cause one reconcile.
  • Workers pop keys, read the latest object from the cache, and reconcile. Errors re-queue the key with exponential backoff.
  • Because reconcile may run many times for the same state, every action must be idempotent: "create if missing, patch if different" rather than "always create". Optimistic concurrency (resourceVersion conflicts) handles races.

How it works

  1. Informer watches objects and updates the cache.
  2. Change → key enqueued (deduplicated).
  3. Worker reads current desired and actual state.
  4. Computes the difference; creates, updates or deletes as needed.
  5. Updates status; returns success or error.
  6. Error or pending work → requeue with backoff.

Example

func (r *Reconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    var app v1.App
    if err := r.Get(ctx, req.NamespacedName, &app); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err)
    }
    deploy := desiredDeployment(&app)                       // compute desired child
    if _, err := controllerutil.CreateOrUpdate(ctx, r.Client, deploy, func() error {
        return controllerutil.SetControllerReference(&app, deploy, r.Scheme)
    }); err != nil {
        return ctrl.Result{}, err                           // requeue with backoff
    }
    return ctrl.Result{}, nil
}

Common mistakes

  • Writing logic that depends on the specific event type.
  • Non-idempotent actions, creating duplicates on each reconcile.
  • Calling the API directly instead of the informer cache, overloading it.
  • Storing state only in memory, lost on restart.

How to answer in the interview

"Every controller runs a reconcile loop: it watches desired state in the API server, observes actual state, and takes the next step to make them match, then repeats. It's level-triggered because it acts on current state rather than individual events, so if it misses an event or restarts, the next reconcile still sees the difference and fixes it. Internally, informers cache objects and push keys into a rate-limited work queue with retries and backoff. Because reconcile can run many times for the same object, every action must be idempotent, like create if missing instead of always create."

Likely follow-up questions

  • What if reconcile isn't idempotent? Duplicate resources, repeated external side effects, endless churn.
  • Why enqueue keys, not objects? Deduplication and always reading the latest state.
  • What are resyncs? Periodic re-enqueueing of all objects as a safety net.
