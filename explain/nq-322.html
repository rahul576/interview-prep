What is the difference between serverless computing and managing your own infrastructure?

Cloud (AWS) · concept · levels mid

In one line

With serverless the provider runs, patches and scales the servers (even to zero), and you pay per use. Managing your own infrastructure (VMs, Kubernetes) gives full control and is often cheaper for steady high load, but your team owns capacity, patching and operations.

Detailed explanation

"Serverless" means there are no servers you manage. Examples are FaaS like AWS Lambda, Azure Functions and Google Cloud Functions/Run, plus serverless containers like Fargate and Cloud Run. Managed serverless data services such as DynamoDB, S3, Aurora Serverless and SQS also count. You deploy code or a container image. The platform handles provisioning, OS patching, high availability and automatic scaling, and billing follows actual requests and execution time.

The benefits are fast delivery, no idle cost for spiky or low-traffic workloads, built-in fault tolerance and a smaller ops burden. The trade-offs are:

  • cold starts, which add latency when new instances spin up (mitigated with provisioned concurrency or SnapStart for Java)
  • limits on execution time (15 minutes for Lambda), memory, payload size and concurrency
  • less control over runtime, networking and tuning
  • harder local testing and debugging across many managed pieces
  • stronger vendor lock-in
  • per-request pricing that can become expensive at constantly high throughput

Own infrastructure means EC2/VMs, on-prem servers, or a Kubernetes cluster (even a managed one like EKS/AKS). You choose the OS, JVM flags, sidecars and network topology. You get predictable performance with no cold starts, can run long-lived processes and stateful workloads, and can use reserved or spot capacity to make steady workloads cheaper. The cost is people: capacity planning, autoscaling configuration, patching, security hardening, upgrades and on-call.

Most real systems are hybrid. Core high-throughput services run on Kubernetes, while event glue, scheduled jobs and spiky APIs run on Lambda.

How it works

  1. Estimate the traffic shape: spiky or idle suits serverless, flat and high suits provisioned capacity.
  2. Check constraints: latency SLOs, execution time, state, special hardware.
  3. Compare total cost: compute bill plus the engineering time spent on operations.
  4. Consider team skills and how much lock-in you accept.
  5. Start serverless for new event-driven parts, and move hot paths to containers if cost or latency demands it.

Example

# Serverless: a scheduled report job, zero cost when idle
Resources:
  NightlyReport:
    Type: AWS::Serverless::Function
    Properties:
      Runtime: java21
      Handler: com.acme.Report::handle
      MemorySize: 1024
      Timeout: 300
      Events:
        Nightly: { Type: Schedule, Properties: { Schedule: "cron(0 2 * * ? *)" } }

Common mistakes

  • Assuming serverless is always cheaper, which ignores high steady throughput.
  • Ignoring cold starts for latency-sensitive Java APIs.
  • Unbounded Lambda concurrency exhausting database connections (use RDS Proxy).
  • Treating Kubernetes as "free" and forgetting the platform team cost.

How to answer in the interview

"With serverless, like Lambda, Fargate or DynamoDB, the provider manages servers, patching and scaling, even down to zero, and I pay only for usage. That's great for spiky or event-driven workloads and lets the team focus on code. The trade-offs are cold starts, execution limits, less control and more lock-in. Running our own VMs or Kubernetes gives full control and predictable performance, and it's often cheaper for steady high-volume traffic, but we own capacity planning, patching and on-call. In practice I'd mix them: core services on Kubernetes, and event handlers and scheduled jobs on Lambda."

Likely follow-up questions

  • Which workloads would you move to serverless? Scheduled jobs, webhooks, file processing and low-traffic internal APIs.
  • How do you reduce Java cold starts? SnapStart, provisioned concurrency, smaller dependencies, or GraalVM native images.
  • Is Kubernetes on EKS serverless? No. The control plane is managed, but you still run the nodes, unless you use Fargate profiles.
