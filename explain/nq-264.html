Why is GROUP BY required for this aggregation?

Databases & SQL · concept · levels entry

In one line

Aggregates collapse rows: without GROUP BY, SUM(o.amount) returns one grand total for everyone, so GROUP BY is what splits the rows into one group per customer per year and makes SUM run separately for each.

Detailed explanation

An aggregate function like SUM, COUNT or AVG turns a set of rows into a single value. The question is always: which set? Without a GROUP BY, the set is the entire filtered result, so SELECT SUM(o.amount) FROM orders gives one number, the total revenue of all customers in all years.

The report needs revenue per customer per year. GROUP BY c.customer_id, EXTRACT(YEAR FROM o.order_date) tells the database to partition the rows into buckets that share the same customer and year, run SUM within each bucket, and return one row per bucket.

There is also a correctness rule. If you write SELECT c.name, SUM(o.amount) without grouping, standard SQL rejects it: there are thousands of names but only one sum, so which name should appear? Mixing aggregated and non-aggregated columns therefore requires GROUP BY. (Old MySQL versions without ONLY_FULL_GROUP_BY returned an arbitrary name, a silent bug.)

GROUP BY also enables HAVING, which filters groups after aggregation, for example keeping only customers with more than 10,000 revenue in a year. WHERE cannot do that because it runs before the sums exist. If you want per-group totals without collapsing rows, use a window function: SUM(amount) OVER (PARTITION BY customer_id).

How it works

  1. Rows are produced by FROM/JOIN and filtered by WHERE.
  2. GROUP BY assigns each row to a group by its key values.
  3. Aggregates are computed per group.
  4. HAVING removes groups that fail a condition on aggregates.
  5. SELECT outputs one row per remaining group.

Example

-- One number for everything
SELECT SUM(amount) FROM orders;

-- One row per customer per year, only big spenders
SELECT customer_id,
       EXTRACT(YEAR FROM order_date) AS yr,
       SUM(amount) AS revenue
FROM orders
GROUP BY customer_id, EXTRACT(YEAR FROM order_date)
HAVING SUM(amount) > 10000;

-- Keep every order row, add the customer total alongside
SELECT order_id, customer_id, amount,
       SUM(amount) OVER (PARTITION BY customer_id) AS customer_total
FROM orders;

Common mistakes

  • Trying to filter on SUM(...) in WHERE instead of HAVING.
  • Selecting non-grouped columns next to aggregates.
  • Grouping by too many columns (like order_id), so each group is one row and nothing is aggregated.
  • Forgetting window functions when you need detail rows plus totals.

How to answer in the interview

"SUM collapses rows into one value. Without GROUP BY it would sum the whole join and return a single total for all customers and all years. We need a total per customer per year, so GROUP BY splits the rows into groups with the same customer and year and computes the SUM for each, giving one row per group. And in standard SQL I can't select the customer name next to an aggregate without grouping, because the database wouldn't know which name to show."

Likely follow-up questions

  • How do you keep only customers with more than 10,000 revenue in a year? HAVING SUM(o.amount) > 10000.
  • What is the difference between WHERE and HAVING? WHERE filters rows before grouping; HAVING filters groups after.
  • How do you get totals without losing detail rows? A window function with PARTITION BY.
