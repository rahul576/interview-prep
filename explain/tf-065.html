What do you look for when reviewing a Terraform pull request?

Terraform · concept · levels mid, senior

In one line

Review the plan, not just the code: hunt for destroys and replacements, then security (public exposure, IAM scope, encryption), blast radius, code quality (modules, naming, variables, pinned versions), state-safe refactors with moved/import/removed blocks, and cost and tags.

Detailed explanation

Terraform code can look harmless while the plan does something dangerous. Renaming a resource label, changing a for_each key or touching a force-new argument can replace a database. So I always open the plan output (posted to the PR by CI) alongside the diff.

1. Destroys and replacements first. Every - and -/+ needs a reason. Stateful resources (databases, disks, storage, Key Vaults, DNS zones) get extra scrutiny: why is it being replaced, is there a backup, could a moved block avoid it?

2. Security. Anything becoming public (public IPs, public_network_access_enabled = true, storage containers), firewall or security group rules opening 0.0.0.0/0, IAM policies or role assignments with wildcards or broad scopes like Owner at subscription level, encryption, TLS or logging disabled. Policy-as-code catches much of this, but humans check intent.

3. Blast radius. Which state and environment is affected? Has it gone through dev and test first? Is this one large change that should be split?

4. Code quality. Approved modules instead of raw copies, consistent naming and tags, variables rather than hard-coded IDs, pinned module and provider versions, descriptions and validation on variables, no secrets in code.

5. Refactors. Moves and renames must use moved, adoption uses import blocks, removal from management uses removed; a refactor should produce a plan with no real changes.

6. Cost and tags. Estimated cost change (Infracost or similar), right-sized SKUs, and tags supporting cost allocation.

How it works

  1. Read the PR description: intent and environments.
  2. Read the plan summary; list every destroy and replacement.
  3. Check security-relevant changes in the plan and code.
  4. Confirm blast radius and rollout order.
  5. Review code quality and refactor blocks.
  6. Check cost estimate and tags; approve or request changes.

Example

# Quick reviewer helper on a saved plan
terraform show -json tfplan | jq -r '
  .resource_changes[]
  | select(.change.actions | index("delete"))
  | "\(.change.actions | join("/"))  \(.address)"'
# delete/create  azurerm_postgresql_flexible_server.main   <- ask why

Common mistakes

  • Approving based on the code diff alone.
  • Skimming long plans and missing a single replacement.
  • Ignoring "update in-place" on security attributes.
  • Allowing renames without moved blocks.
  • Rubber-stamping because CI is green.

How to answer in the interview

"I always review the plan together with the code, because the plan shows what will really happen. First destroys and replacements, especially stateful resources like databases or disks, and I ask why. Then security: anything becoming public, wide firewall rules, wildcard IAM, encryption or logging disabled. I check blast radius, which environment and state, and whether it went through lower environments first. For code quality I look for approved modules, naming, tags, variables instead of hard-coded values and pinned versions. Refactors must use moved, import or removed blocks. Finally cost changes and tags."

Likely follow-up questions

  • What would make you block a small-looking PR? A single replacement of a stateful resource or a new public exposure.
  • How can CI help? Flag destroys automatically, run policy checks and cost estimates.
  • Who should review? The owning team plus platform or security for sensitive resources.
