Your security team asks how you will prevent a third-party MCP server from exfiltrating company data. What is your answer?

MCP Servers · scenario · levels senior, lead

In one line

A third-party server sees whatever the model puts in tool arguments, so prevention means limiting exposure: vet the server and operator, practise data minimisation, don't combine it with sensitive servers in one session, route it through a gateway with DLP and egress controls, add contractual controls, and monitor and audit its traffic.

Detailed explanation

The honest answer to the security team starts with the threat model. A third-party MCP server receives the tool arguments the model generates, and the model generates them from its whole context. A remote server runs on someone else's infrastructure, where you cannot see what it logs or keeps; a local one runs code on your machines. Both can also influence the model through descriptions and results. So "prevention" is about controlling what can reach it.

1. Vet the server and operator. Who runs it, where data is processed and stored, retention, sub-processors, certifications such as SOC 2 or ISO 27001, breach history. For local servers, review and pin the code and run it sandboxed with restricted egress.

2. Data minimisation. The server's tools should take narrow, structured parameters, not free-text fields where the model can paste anything. Only the context its task needs should be available.

3. Session separation. Do not enable the third-party server in the same session as servers holding confidential data. If the model never sees customer records in that session, it cannot copy them into a tool call, whether accidentally or through prompt injection.

4. Technical controls. Route remote third-party servers through the MCP gateway with DLP inspection of outbound arguments (blocking or redacting personal data, secrets, classified markers), use scoped credentials, and restrict network egress for local servers.

5. Contractual controls. A data processing agreement, no training on our data, retention limits, audit rights, breach notification.

6. Monitoring. Log all calls to the server, review samples, alert on DLP hits, and recertify periodically.

How it works

  1. Security review and contract before enablement.
  2. Server registered as "external" tier in the internal registry.
  3. Host policy: external-tier servers not allowed in sessions with confidential-tier servers.
  4. All traffic through the gateway; DLP on arguments, logging of every call.
  5. Periodic review of logs and vendor status.

Example

server: acme-analytics-mcp
tier: external
gateway:
  dlp:
    block: [customer_email, iban, national_id, api_key]
    action: reject_and_alert
session_policy:
  cannot_combine_with_tiers: [confidential, restricted]
contract: { dpa: signed, retention_days: 30, training_on_data: false }

Common mistakes

  • Promising that prompt instructions will stop data leaving.
  • Approving a vendor without checking where data is processed.
  • Generic query or notes string parameters.
  • Mixing CRM and external servers in one agent profile.

How to answer in the interview

"I'd explain that a third-party server receives whatever the model sends in tool arguments, and a remote one runs on someone else's infrastructure, so prevention is about limiting exposure. First, vet the server and operator: who runs it, where data is processed, retention, certifications, and for local servers review and pin the code. Second, data minimisation: narrow structured parameters, and we don't enable it in sessions with sensitive servers, so the model can't copy confidential content into its calls. Third, technical controls: a gateway with DLP on outbound arguments, egress restrictions and scoped credentials. Fourth, contractual controls like a DPA. And finally we monitor and audit its traffic and review it regularly."

Likely follow-up questions

  • Test that data cannot flow? Red-team sessions with seeded canary data and injection attempts, checking gateway logs.
  • Why session separation? The model can only leak what is in its context.
  • What if the vendor refuses a DPA? Do not approve it for anything beyond public data.
