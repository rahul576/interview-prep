Design a production release of a web app with Azure Pipelines that supports approvals, smoke tests and fast rollback.

Azure DevOps & Pipelines · scenario · levels mid, senior

In one line

Build once and promote the same artifact; production stage targets an environment with approvals, branch control and business hours, deploys to a staging slot, runs smoke tests against the slot, swaps into production (with warm-up), watches Azure Monitor/App Insights via a post-deployment check, and rolls back by swapping back.

Detailed explanation

Build stage: compile, test and publish one artifact (zip or container image tag). Every later stage downloads that same artifact, so production runs exactly what was tested.

Test/staging stages: deploy to lower environments with integration and end-to-end tests.

Production stage: a deployment job targets the prod environment with checks: approval by release managers, branch control (main only), business hours, exclusive lock, and an Azure Monitor alerts check that blocks deployment if production is already unhealthy.

Slots: App Service deployment slots (Standard tier and above) are live apps with their own hostname. Deploy to the staging slot, which has production configuration except slot-specific ("sticky") settings such as feature flags pointing at test data. Use Application Initialization (applicationInitialization in web.config or the warm-up path) so the slot is warm.

Smoke tests: hit the staging slot's URL: /health, key APIs, a synthetic user journey with Playwright. If they fail, the pipeline stops and production is untouched.

Swap: AzureAppServiceManage@0 swaps staging into production. App Service applies production settings to the staging instances, warms them up, then switches routing, so there's no downtime. Swap with preview applies settings first so you can validate before completing.

Post-release verification: a post-deployment step or check watches Application Insights failure rates, latency and alerts for 10-15 minutes.

Rollback: the previous version is now in the staging slot, so rollback is swapping back, which takes seconds. Database changes must be backward compatible (expand/contract) for this to be safe.

How it works

  1. Build → artifact.
  2. Deploy to test, run tests.
  3. Prod checks pass → deploy to staging slot.
  4. Smoke tests on slot URL.
  5. Swap → monitor.
  6. Failure → swap back.

Example

- stage: Prod
  jobs:
  - deployment: web
    environment: shop-prod
    strategy:
      runOnce:
        deploy:
          steps:
          - task: AzureWebApp@1
            inputs: { azureSubscription: sc-prod, appName: app-shop, deployToSlotOrASE: true,
                      resourceGroupName: rg-shop, slotName: staging, package: '$(Pipeline.Workspace)/web/*.zip' }
          - script: ./smoke.sh https://app-shop-staging.azurewebsites.net
          - task: AzureAppServiceManage@0
            inputs: { azureSubscription: sc-prod, Action: 'Swap Slots', WebAppName: app-shop,
                      ResourceGroupName: rg-shop, SourceSlot: staging }
        on:
          failure:
            steps:
            - task: AzureAppServiceManage@0
              inputs: { azureSubscription: sc-prod, Action: 'Swap Slots', WebAppName: app-shop,
                        ResourceGroupName: rg-shop, SourceSlot: staging }

Common mistakes

  • Rebuilding for production instead of promoting the artifact.
  • Breaking database migrations that make swap-back impossible.
  • Sticky settings misconfigured so the slot talks to production queues during tests.
  • No warm-up, causing cold-start errors right after swap.

How to answer in the interview

"The build produces one artifact that's promoted unchanged. The production stage targets an environment with approval, branch control and business-hour checks. It deploys to a staging slot with production config, runs smoke tests against the slot URL, and if they pass swaps it into production, which warms instances first so there's no downtime. After the swap, a gate watches Application Insights failure rates and Azure Monitor alerts. Rollback is just swapping back, because the previous version sits in the staging slot, as long as our database changes are backward compatible."

Likely follow-up questions

  • What makes swaps unsafe? Non-backward-compatible schema changes, sticky settings, cold starts, in-flight sessions.
  • Canary instead? Slot traffic routing percentages, or Front Door weights.
  • Containers on AKS? Blue-green with services or canary with a mesh instead of slots.
