How do you connect on-premises networks or several cloud networks securely?

Networking · design · levels senior, lead

In one line

Use site-to-site IPsec VPN for quick, cheaper connectivity, dedicated links (Direct Connect, ExpressRoute, Interconnect) for bandwidth, latency and compliance, peering for a few VNets/VPCs and hub-and-spoke with Transit Gateway or Virtual WAN at scale, all built on non-overlapping CIDRs, BGP routing, hybrid DNS and least-privilege rules.

Detailed explanation

Site-to-site VPN: encrypted IPsec tunnels over the internet between an on-prem VPN device and a cloud VPN gateway. Quick to set up and inexpensive, but bandwidth is limited per tunnel (around 1.25 Gbps on AWS) and latency varies with the internet. Use two tunnels (and ideally two customer devices) for redundancy, and BGP for dynamic route exchange and failover.

Dedicated connectivity: AWS Direct Connect, Azure ExpressRoute, Google Cloud Interconnect provide private circuits via colocation facilities or partners: high bandwidth (1-100 Gbps), consistent latency, lower data transfer costs and often a compliance requirement. They're not encrypted by default, so add MACsec or IPsec over the link where needed. Design for resilience with two connections at different locations, or keep a VPN as backup.

Cloud-to-cloud networks: VPC/VNet peering is simple, low-latency and non-transitive, so it fits a handful of networks; full meshes don't scale. Hub-and-spoke with AWS Transit Gateway, Azure Virtual WAN or a hub VNet with Azure Firewall, or GCP Network Connectivity Center centralises routing, inspection (firewalls in the hub), shared services and controlled egress; route tables and segments separate prod from non-prod. Multi-cloud links use VPNs or partner interconnects between providers.

Foundations:

  • Non-overlapping CIDR plan across all clouds and on-prem; overlaps force NAT and break routing.
  • Routing: BGP, route propagation, summarisation and preventing unwanted transit.
  • DNS: hybrid resolution with Route 53 Resolver endpoints, Azure DNS Private Resolver, or conditional forwarders, so on-prem resolves cloud private zones and vice versa.
  • Private endpoints (PrivateLink, Private Endpoint, Private Service Connect) to reach managed services and SaaS without public exposure.
  • Least access: security groups, NSGs and firewalls allow only the flows each workload needs; log flows; zero-trust access for users instead of flat network access.

How it works

  1. Allocate CIDRs centrally across environments.
  2. Build a hub with transit gateway or Virtual WAN, firewall and DNS resolvers.
  3. Attach spoke VPCs or VNets with segmented route tables.
  4. Connect on-prem via Direct Connect or ExpressRoute plus VPN backup, using BGP.
  5. Configure hybrid DNS forwarding and private endpoints.
  6. Apply firewall policies and monitor flows and tunnel health.

Example

resource "aws_ec2_transit_gateway" "hub" {
  description                     = "org hub"
  default_route_table_association = "disable"
  default_route_table_propagation = "disable"
}
resource "aws_vpn_connection" "onprem" {
  customer_gateway_id = aws_customer_gateway.dc1.id
  transit_gateway_id  = aws_ec2_transit_gateway.hub.id
  type                = "ipsec.1"
  static_routes_only  = false          # BGP
}
resource "aws_ec2_transit_gateway_vpc_attachment" "prod_app" {
  transit_gateway_id = aws_ec2_transit_gateway.hub.id
  vpc_id             = aws_vpc.prod_app.id
  subnet_ids         = aws_subnet.tgw[*].id
}

Common mistakes

  • Overlapping CIDRs discovered only when connecting.
  • Single VPN tunnel or a single dedicated circuit without backup.
  • Forgetting DNS, so connectivity works by IP but not by name.
  • Flat routing that lets every spoke reach every other spoke.

How to answer in the interview

"For a quick, cheaper link I'd use a site-to-site IPsec VPN with two tunnels and BGP. For high bandwidth, stable latency or compliance I'd use Direct Connect or ExpressRoute, ideally redundant or with a VPN as backup. Between cloud networks, peering works for a few, but at scale I'd build hub and spoke with Transit Gateway or Virtual WAN to centralise routing, inspection and egress. It all depends on a non-overlapping CIDR plan. I'd also design hybrid DNS, use private endpoints for managed services, and restrict routes and firewall rules to what each workload needs."

Likely follow-up questions

  • What if two networks have overlapping ranges? Routing becomes ambiguous; you need NAT, PrivateLink-style service exposure or re-addressing.
  • Is Direct Connect encrypted? Not by default; use MACsec or IPsec over it.
  • Why is peering non-transitive a problem? A can't reach C through B, so meshes grow quadratically.
