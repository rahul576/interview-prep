What are the ACID properties of a database transaction?

Databases & SQL · concept · levels entry, mid

In one line

ACID is the set of guarantees a database transaction gives: Atomicity (all or nothing), Consistency (constraints always hold), Isolation (concurrent transactions do not corrupt each other) and Durability (committed data survives crashes).

Detailed explanation

A transaction groups several statements into one logical unit of work, such as moving money between two accounts. ACID describes what the database promises about that unit.

Atomicity means either every statement takes effect or none does. If the credit fails after the debit, the database rolls back the debit using its undo information. The application never sees half a transfer.

Consistency means a transaction takes the database from one valid state to another. Primary keys, foreign keys, unique, check and not-null constraints are enforced, and a transaction that would break them is rejected. Note that business invariants beyond declared constraints (for example "balance must never go negative" if there is no check constraint) remain the application's responsibility.

Isolation means concurrent transactions behave as if they ran in some order. In practice databases offer isolation levels (Read Uncommitted, Read Committed, Repeatable Read, Serializable) that trade strictness for concurrency, implemented with locks or MVCC snapshots. PostgreSQL and Oracle default to Read Committed; MySQL InnoDB defaults to Repeatable Read.

Durability means once COMMIT returns, the change survives a crash or power loss. Databases achieve this with a write-ahead log (WAL) or redo log that is flushed (fsync) to disk before the commit is acknowledged; data pages can be written lazily later and rebuilt from the log on recovery.

How it works

  1. The client starts a transaction (BEGIN, or Spring's @Transactional).
  2. Each change is recorded in the WAL/redo log and in undo/MVCC versions.
  3. Locks or row versions keep other transactions from seeing uncommitted data.
  4. Constraints are checked per statement or at commit (deferred constraints).
  5. On COMMIT, the log is flushed to durable storage, then success is returned.
  6. On error or ROLLBACK, undo information restores the previous state; after a crash, recovery replays the log.

Example

BEGIN;
UPDATE account SET balance = balance - 500 WHERE id = 1;
UPDATE account SET balance = balance + 500 WHERE id = 2;
-- if either fails, ROLLBACK undoes both
COMMIT;  -- WAL flushed: survives a crash from here on
@Transactional
public void transfer(long from, long to, BigDecimal amt) {
    accounts.debit(from, amt);
    accounts.credit(to, amt);   // exception here rolls back the debit
}

Common mistakes

  • Confusing ACID consistency (constraints) with CAP consistency (latest value on every replica).
  • Assuming every database runs at Serializable by default.
  • Catching an exception inside @Transactional and swallowing it, so the transaction commits a partial result.
  • Forgetting that settings like synchronous_commit = off weaken durability.

How to answer in the interview

"ACID is what makes a transaction trustworthy. Atomicity means all or nothing: in a transfer, both the debit and the credit happen or neither does, thanks to rollback. Consistency means constraints such as foreign keys and uniqueness always hold after a commit. Isolation means concurrent transactions don't interfere, and the strength of that is tuned through isolation levels, usually implemented with MVCC. Durability means once commit returns the data survives a crash, because the write-ahead log is flushed to disk first. In Spring I get these through @Transactional, and I'm careful about the isolation level the database actually uses."

Likely follow-up questions

  • How do microservices give up ACID across services? They use local transactions plus sagas, the outbox pattern and idempotent consumers for eventual consistency.
  • What is MVCC? Readers see a consistent snapshot of row versions, so reads do not block writes.
  • Which anomalies does Read Committed allow? Non-repeatable reads and phantoms, plus lost updates without explicit locking.
