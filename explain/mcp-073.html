Sensitive customer data appeared in a tool call to an external analytics MCP server. How could it have happened, and how do you investigate?

MCP Servers · scenario · levels mid, senior

In one line

The model fills tool arguments from its context, so customer data present in the conversation can be copied into another tool's arguments, innocently or via prompt injection, especially with broad free-text parameters; investigate with traces and audit logs, then add structured schemas, DLP on arguments, data minimisation and session separation.

Detailed explanation

How it happens. Models do not have data-flow boundaries. If a CRM tool returned a customer's name, email and order history earlier in the conversation, or a user pasted a spreadsheet, that data is simply text in the context. When the model later calls an external analytics tool with a parameter like query, notes or context, it may include that data because it seems helpful: "analyse churn for Jane Doe, jane@example.com, who cancelled order 1234". This is an innocent path.

The malicious path is prompt injection: some content in context, perhaps a support ticket or web page, instructed the model to send the data to the analytics tool, which the attacker can observe. Either way, broad free-text parameters are the enabler, and having an external server in the same session as sensitive data is the precondition.

Investigation.

  1. Find the call in gateway or audit logs: exact arguments, time, user, session.
  2. Pull the conversation trace: what the user asked, which tool results preceded the call, and whether any content looks like injected instructions.
  3. Check which approvals were shown and whether the user approved with the data visible.
  4. Determine scope: how many calls, how many customers, and what the vendor retains.
  5. Engage privacy or legal: request deletion from the vendor, assess notification obligations under GDPR or similar.

Mitigation. Tighten the analytics tool's schema to structured parameters (metric, date range, segment IDs) with no free text; add DLP checks on outbound arguments at the gateway; separate sessions so external servers never coexist with sensitive data; minimise what the CRM tool returns; and show full arguments in approvals for external tools.

How it works

  1. CRM tool returns customer PII into context.
  2. Model calls analytics.run_query(query="… jane@example.com …").
  3. Gateway forwards to external server; data leaves.
  4. After the fix: schema has no free-text field; DLP blocks emails; policy prevents CRM and external analytics in one session.

Example

{
  "name": "run_churn_report",
  "inputSchema": {
    "type": "object",
    "properties": {
      "metric":   { "type": "string", "enum": ["churn_rate", "retention", "ltv"] },
      "from":     { "type": "string", "format": "date" },
      "to":       { "type": "string", "format": "date" },
      "segment":  { "type": "string", "enum": ["smb", "mid_market", "enterprise"] }
    },
    "required": ["metric", "from", "to"],
    "additionalProperties": false
  }
}

Common mistakes

  • Blaming the user without looking at the trace.
  • Fixing only the prompt.
  • Forgetting to ask the vendor to delete the data.
  • Keeping additionalProperties open so the model can add free fields.

How to answer in the interview

"The model fills tool arguments from its context, so if customer data was in the conversation, from a CRM result or a pasted document, it can be copied into another tool's arguments. That can be innocent, because the model thought it helped the analytics query, especially with broad free-text parameters like notes or query, or malicious, via prompt injection. I'd investigate with the conversation trace and audit logs: what was in context, which tool results preceded the call, the exact arguments and the approvals shown. Then mitigate: structured parameters, DLP on outbound arguments at the gateway, not mixing external servers with sensitive data in one session, and notifying affected parties if required."

Likely follow-up questions

  • Why do structured parameters help? Enums and typed fields leave no place to paste arbitrary text.
  • Was it a breach? Depends on data, vendor contract and jurisdiction; involve privacy counsel.
  • Detect it earlier? DLP alerts at the gateway on PII in external tool arguments.
