What is code execution with MCP, and why do some teams prefer it to direct tool calls?

MCP Servers · concept · levels mid, senior

In one line

With code execution with MCP, the host exposes MCP tools as functions in a sandboxed code environment and the model writes code that calls them, so tool definitions load on demand and intermediate data is processed in code instead of in the context, cutting tokens sharply at the cost of needing secure sandboxing.

Detailed explanation

In the classic pattern, the model calls one tool, the full result enters its context, it reasons, calls the next tool, and so on. For data-heavy work, for example reading a 10,000-row spreadsheet, filtering it and updating matching CRM records, that means huge results passing through the model twice: once when read and once when written back. All tool definitions are also loaded up front.

Code execution changes the shape of the work. The host generates a small API wrapper for each MCP server, for instance a TypeScript or Python module per server with one function per tool, placed in a file tree. The model explores the tree, reads only the definitions it needs, and writes a script that calls the tools, loops, filters, joins and transforms data, and prints only a short final result. That result is all that returns to the model. Anthropic and others have reported very large token reductions for such tasks.

There are further benefits. Sensitive intermediate data can stay in the sandbox and never enter the model context; control flow such as loops and retries is executed reliably by code rather than by many model turns; and scripts can be saved as reusable skills. The trade-off is serious infrastructure: a secure sandbox with process isolation, CPU, memory and time limits, restricted network egress, no host credentials, and monitoring. For simple tasks with one or two small tool calls, direct tool calling is simpler and fine.

How it works

  1. Host generates function wrappers for each connected MCP server's tools.
  2. The model lists available servers and reads only relevant tool files.
  3. It writes code that calls those functions and processes the data.
  4. The code runs in an isolated sandbox; wrappers route calls to the MCP servers.
  5. Only the final small output (or an error) returns to the model.

Example

import { getSheet } from "./servers/gdrive";
import { updateRecord } from "./servers/salesforce";

const rows = await getSheet({ sheetId: "abc123" });          // 10,000 rows, stay in sandbox
const overdue = rows.filter(r => r.status === "overdue");
for (const r of overdue) {
  await updateRecord({ objectType: "Account", id: r.accountId, data: { flag: "overdue" } });
}
console.log(`Updated ${overdue.length} accounts`);           // only this reaches the model

Common mistakes

  • Running model-written code without real isolation.
  • Giving the sandbox broad network access or real credentials.
  • Assuming data in the sandbox is safe while logs print it anyway.
  • Using code execution for trivial tasks where it adds latency and complexity.

How to answer in the interview

"Instead of the model calling tools one at a time with every result flowing through its context, the host exposes MCP tools as functions, say a TypeScript API, and the model writes code that uses them. The code runs in a sandbox, does the looping and filtering, and returns only a small result. Definitions are loaded on demand by reading files for each server. For data-heavy tasks this cuts tokens dramatically and keeps sensitive intermediate data out of the context. The cost is a properly secured sandbox with isolation, resource limits and network restrictions."

Likely follow-up questions

  • What new risks does it introduce? Sandbox escape, data exfiltration via network, resource abuse, and prompt-injected code; mitigate with isolation and egress control.
  • Does it replace tool calling? No; it complements it for heavy tasks.
  • How are approvals handled? Sensitive tools still require confirmation, enforced in the wrapper or server.
