How would you optimize a JPA application that generates thousands of SQL queries?

Spring Data & JPA · scenario · levels senior, lead

In one line

Measure first (SQL logging, Hibernate statistics, query-count tests), then remove N+1 selects with JOIN FETCH, entity graphs or batch fetching, use DTO projections for reads, enable JDBC batching with sequence ids for writes, add caching and disable open-session-in-view.

Detailed explanation

Thousands of queries per request almost always mean the ORM is loading data row by row. The classic cause is N+1: one query loads 500 orders, then accessing order.getCustomer() or order.getItems() in a loop fires one query per order. Eager to-one associations make it worse because they load even when unused.

Measuring comes first, because guesses waste time. Turn on hibernate.generate_statistics, log SQL with a proxy like datasource-proxy or p6spy, or look at the APM trace, and count queries per endpoint. Then lock in the improvement with tests that assert a maximum query count.

Fixes for reads:

  • JOIN FETCH or @EntityGraph loads associations in the same query for that use case.
  • hibernate.default_batch_fetch_size (for example 50) or @BatchSize makes lazy collections load in batches with IN (...), turning N+1 into N/50+1.
  • DTO projections select only the needed columns and skip the persistence context, ideal for list and report endpoints.
  • Pagination, and avoid fetching collections together with pagination (Hibernate then paginates in memory).

Fixes for writes: set hibernate.jdbc.batch_size, order_inserts and order_updates, use SEQUENCE ids (IDENTITY disables insert batching), and for huge imports use bulk JPQL updates or plain JDBC.

Structure: disable spring.jpa.open-in-view so lazy loading cannot happen silently in controllers or JSON serialisation; cache reference data in the second-level cache or Spring Cache.

How it works

  1. Enable query counting and find the endpoints with the most SQL.
  2. Read the logged SQL to identify repeated patterns (same SELECT with different ids).
  3. Choose a fetch plan per use case: fetch join, entity graph or batch fetching.
  4. Replace entity loading with projections for read-only views.
  5. Enable JDBC batching and sequence ids for bulk writes.
  6. Add query-count assertions in tests so regressions fail CI.

Example

spring:
  jpa:
    open-in-view: false
    properties:
      hibernate:
        default_batch_fetch_size: 50
        jdbc.batch_size: 50
        order_inserts: true
        order_updates: true
        generate_statistics: true   # in test/staging
@EntityGraph(attributePaths = {"customer", "items"})
@Query("select o from Order o where o.status = :status")
List<Order> findWithDetails(@Param("status") Status status);

Common mistakes

  • Making everything EAGER to "fix" lazy exceptions, which multiplies queries.
  • Fetch-joining several collections at once, causing a Cartesian product or MultipleBagFetchException.
  • Optimising without measuring, or only measuring in production.
  • Leaving open-session-in-view on, hiding lazy loading in the view layer.

How to answer in the interview

"First I measure: SQL logging or Hibernate statistics, or datasource-proxy, to count queries per request and see the repeated patterns. Usually it's N+1 from lazy associations in loops, so I define a fetch plan per use case with JOIN FETCH or an entity graph, or set default_batch_fetch_size so collections load in batches. Read-heavy endpoints get DTO projections. For writes I enable JDBC batching with ordered inserts and a sequence generator. I disable open-session-in-view, cache reference data, and add tests that assert the query count so the problem can't come back."

Likely follow-up questions

  • How do you test for N+1? Use datasource-proxy or Hibernate statistics in a test and assert the statement count for an endpoint.
  • JOIN FETCH vs batch fetching? Fetch join is one query for a known use case; batch fetching is a global safety net.
  • Why not just add a second-level cache? It hides the problem and does not help queries returning collections.
