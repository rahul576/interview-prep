How would you define a base image strategy for an organisation with hundreds of services?

Docker · design · levels lead

In one line

Have a platform team own a small catalogue of approved, hardened base images per language, rebuilt automatically on upstream patches, tested, versioned, signed and shipped with SBOMs; services pin them and get updates through Renovate/Dependabot PRs, while admission policies and dashboards enforce and measure adoption.

Detailed explanation

With hundreds of services, every team picking its own FROM line means hundreds of different OS versions, inconsistent CA certificates and proxy settings, and a CVE response that requires chasing every team. A base image strategy turns that into a supply chain problem with a single owner.

The catalogue should be small: a minimal OS base (distroless, Wolfi/Chainguard-style or slim Debian/UBI), plus runtime images such as Java 21 JRE, Node 22 and Python 3.12/3.13, perhaps with build variants. Each is hardened: non-root user by default, minimal packages, company CA certificates, timezone data, standard labels, and optional observability agents.

Automation is essential. A pipeline rebuilds the images whenever the upstream base or a package gets a security fix (and on a weekly schedule anyway), runs smoke and compatibility tests, scans them, signs them with cosign, attaches an SBOM and provenance, and publishes them with a changelog under both a dated version tag and a moving major tag.

Consumption: service Dockerfiles pin a version or digest. Renovate (or Dependabot) opens PRs when a new base version is out, so patching hundreds of services becomes reviewing and merging bot PRs, ideally auto-merged when tests pass. Governance: admission policies (Kyverno, Gatekeeper) or CI checks allow only approved bases in production, and dashboards show per-team adoption, image age and open CVEs. Exceptions follow a documented process.

How it works

  1. Define the catalogue and ownership (platform/security team, SLAs for patching).
  2. Build pipeline: upstream change → rebuild → test → scan → sign → SBOM → publish.
  3. Teams reference registry/base/java-21-jre:2026.11.2 or a digest.
  4. Renovate opens PRs; CI rebuilds and tests services.
  5. Admission control verifies signature and allowed base; dashboards track drift.

Example

FROM registry.example.com/base/java-21-jre:2026.11.2@sha256:9b1e...
COPY --chown=app:app target/app.jar /app/app.jar
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
{
  "extends": ["config:recommended"],
  "packageRules": [
    { "matchDatasources": ["docker"],
      "matchPackagePrefixes": ["registry.example.com/base/"],
      "automerge": true, "pinDigests": true }
  ]
}

Common mistakes

  • Too many "approved" images, which recreates the sprawl.
  • Rebuilding bases but never updating the services that use them.
  • Floating latest tags, so nobody knows which base is running.
  • Making bases so heavy (agents, shells, tools) that they become a security risk.

How to answer in the interview

"I'd have a platform team own a small catalogue of hardened base images, a minimal OS base and runtimes like Java, Node and Python, non-root by default with company certificates included. They're rebuilt automatically whenever upstream patches land and at least weekly, then tested, scanned, signed with cosign and published with SBOMs. Services pin a version or digest, and Renovate opens PRs when a new version appears, so patching hundreds of services becomes merging bot PRs, mostly auto-merged after tests. Admission policies allow only approved bases in production, and dashboards show adoption and image age per team, with an exception process for genuine special needs."

Likely follow-up questions

  • A team needs a library the base lacks? They extend the base in their own Dockerfile, or request it; if many teams need it, add a variant.
  • How fast should critical CVEs be patched? Define SLAs, for example 48 hours for critical; automation makes that achievable.
  • Tag or digest pinning? Digest pinning with Renovate updating both is the most reproducible.
