How would you handle retries and failures in an asynchronous message-processing workflow?

Cloud (AWS) · scenario · levels mid

In one line

Classify errors: retry transient ones with exponential backoff and jitter up to a limit, and send permanent ones straight to a DLQ with the reason. Make every consumer idempotent, and track workflow state for compensation, alerting and redrive.

Detailed explanation

In asynchronous systems failures are normal. Networks blip, downstream services throttle, and some messages are simply invalid. The design question is how to recover automatically from the first kind without endlessly reprocessing the second.

Transient errors include timeouts, connection resets, HTTP 429/503 and database deadlocks. These usually succeed later, so retry them with exponential backoff (1 s, 2 s, 4 s, ...) plus jitter, under a cap and a maximum number of attempts. There are several mechanisms:

  • queue redelivery via the visibility timeout (SQS) or nack/requeue (RabbitMQ)
  • delayed retry queues or topics (Kafka orders.retry.1m, orders.retry.10m)
  • in-process retries for very short blips (Resilience4j)

Permanent errors include schema validation failures, unknown customers and business rule violations. Retrying them only wastes capacity and blocks partitions. Route them straight to a dead-letter queue or error topic with metadata: the error, stack trace, attempt count and original offset.

Retries and redeliveries mean at-least-once delivery, so consumers must be idempotent. Use a processed-message table, upserts, or idempotency keys on downstream calls. For multi-step workflows, persist the state of each step. When a later step fails permanently, a saga runs compensating actions (refund, release stock) or raises a manual task.

How it works

  1. The consumer receives a message and checks its idempotency key.
  2. It processes the message. If successful, it commits or acks and records the key.
  3. On a transient error with attempts below max: requeue with a delay of min(cap, base * 2^n) randomised.
  4. On a permanent error, or once attempts are exhausted: publish to the DLQ with the reason and ack the original.
  5. A DLQ alarm fires. An operator inspects, fixes the data or code, and redrives.
  6. Dashboards show retry rate, DLQ depth and consumer lag.

Example

@RetryableTopic(attempts = "4",
    backoff = @Backoff(delay = 1000, multiplier = 2.0, random = true),
    exclude = {ValidationException.class})          // permanent: skip retries
@KafkaListener(topics = "orders")
public void onOrder(OrderEvent e) {
    if (processed.exists(e.eventId())) return;       // idempotency
    service.handle(e);
    processed.save(e.eventId());
}

@DltHandler
public void toDlt(OrderEvent e, @Header(KafkaHeaders.EXCEPTION_MESSAGE) String err) {
    alerting.notify(e.eventId(), err);
}

Common mistakes

  • Retrying everything, including validation errors, forever.
  • Immediate retries without backoff, which hammer a struggling dependency.
  • DLQs nobody monitors and no tool to redrive.
  • Non-idempotent consumers creating duplicate payments or emails.
  • Blocking a Kafka partition with in-place retries for minutes.

How to answer in the interview

"First I classify errors. Transient ones like timeouts or throttling get retried with exponential backoff and jitter, using redelivery, delayed retry queues or retry topics, up to a maximum number of attempts. Permanent ones like invalid data go straight to a dead-letter queue with the reason. DLQs have alarms and redrive tooling. Because retries create duplicates, every consumer is idempotent, deduplicating on a message or business id. I persist workflow state so a permanent failure can trigger compensation or a manual follow-up, and I monitor error rates and DLQ size."

Likely follow-up questions

  • Why add jitter? Without it, many clients retry at the same moments and create synchronised load spikes. Jitter spreads them out.
  • Poison message? A message that always fails. Max attempts plus a DLQ stops it from blocking the queue or partition.
  • How do you redrive safely? Fix the cause first, replay at a controlled rate, and rely on idempotency.
