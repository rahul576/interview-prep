What are the first-level and second-level caches in Hibernate?

Spring Data & JPA · concept · levels mid, senior

In one line

The first-level cache is the persistence context, always on and scoped to one session/transaction, guaranteeing one instance per row; the second-level cache is optional, shared across sessions (Ehcache, Infinispan, Hazelcast via JCache) for read-mostly data, plus an optional query cache, with staleness and invalidation as the main risks.

Detailed explanation

First-level cache. Every Hibernate Session (JPA EntityManager) has a persistence context, a map from entity type and id to the managed instance. In Spring it normally lives for one transaction. Calling find(Order.class, 42) twice returns the same instance with only one SELECT, and a query returning that row also returns the existing instance. This guarantees identity (== works within the session) and repeatable reads of entities at the application level, and it is the basis of dirty checking. You cannot switch it off; you manage it with flush(), clear() and detach(), which matters in batch jobs where it grows without bound. Note that JPQL queries still hit the database; only lookups by id are served from it.

Second-level cache (L2). Optional, configured per entity with @Cache/@Cacheable and a provider: Ehcache 3, Infinispan, Hazelcast or others through JCache (JSR-107). It is shared by all sessions in the SessionFactory, so a second transaction can load an entity by id without a query. It stores dehydrated entity state, not instances. Concurrency strategies define consistency: READ_ONLY (immutable data, fastest), NONSTRICT_READ_WRITE, READ_WRITE (soft locks), TRANSACTIONAL (JTA). Collections can be cached separately.

Query cache. Caches the ids returned by a query for given parameters, combined with the entity L2 cache. It is invalidated whenever any table involved changes, so it only helps for rarely changing data.

Concerns. The L2 cache is only kept consistent for changes made through Hibernate in the same cluster-aware cache. Native SQL updates, bulk updates, other services or database scripts writing the same tables leave stale entries. With multiple application instances you need a distributed or invalidating cache (Infinispan/Hazelcast cluster) or per-node caches with short TTLs. Memory, warm-up and debugging add complexity. That's why I use it selectively, for reference data like countries, currencies or product categories, and often prefer an application-level cache (Spring @Cacheable with Redis or Caffeine) where I control keys, TTLs and invalidation.

How it works

  1. em.find(Product, 7): check persistence context (L1).
  2. Miss: check L2 region for Product#7 if enabled.
  3. Miss: SELECT from database, put into L2 and L1.
  4. Update via Hibernate: L2 entry invalidated or updated per strategy at commit.
  5. New transaction: L1 empty, L2 hit avoids the query.

Example

@Entity
@Cacheable
@org.hibernate.annotations.Cache(usage = CacheConcurrencyStrategy.READ_ONLY, region = "country")
public class Country {
    @Id String code;
    String name;
}
spring:
  jpa:
    properties:
      hibernate:
        cache:
          use_second_level_cache: true
          use_query_cache: false
          region.factory_class: jcache
        javax.cache.provider: org.ehcache.jsr107.EhcacheCachingProvider
      jakarta.persistence.sharedCache.mode: ENABLE_SELECTIVE

Common mistakes

  • Enabling L2 for frequently updated entities.
  • Turning on the query cache everywhere.
  • Ignoring other writers (services, scripts) to the same tables.
  • Expecting JPQL queries to be served from the first-level cache.

How to answer in the interview

"The first-level cache is the persistence context, scoped to a session or transaction and always on: loading the same entity twice returns the same instance without another query, which guarantees identity. The second-level cache is optional and shared across sessions, provided by Ehcache, Infinispan or Hazelcast through JCache, and suits read-mostly reference data. There is also a query cache. The concerns are stale data and invalidation, especially with multiple instances or other systems writing to the database, so I use it selectively and often prefer an application-level cache."

Likely follow-up questions

  • Why is L2 risky when another service writes the tables? Hibernate doesn't see those writes, so cached entries go stale.
  • Which concurrency strategy? READ_ONLY for immutable data, READ_WRITE for occasionally updated data.
  • L2 vs Spring @Cacheable? L2 caches entities by id transparently; @Cacheable caches any method result with your own keys and TTLs.
