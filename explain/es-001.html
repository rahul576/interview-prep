What is Elasticsearch and how does it store and search data?

Elasticsearch · concept · levels entry, mid

In one line

Elasticsearch is a distributed search and analytics engine built on Apache Lucene. It stores JSON documents in indices, analyses text into terms in an inverted index for fast full-text search, uses doc values for sorting and aggregations, spreads data across shards with replicas, and is near real-time (searchable after a refresh, every 1 s by default).

Detailed explanation

You send JSON documents to an index (roughly a table). Elasticsearch infers or applies a mapping (the field types) and indexes each field according to its type.

  • Inverted index. For text fields, an analyzer tokenises and normalises the content ("Quick Brown Foxes" becomes quick, brown, fox). The inverted index maps each term to a postings list of the documents (and positions) containing it, like the index at the back of a book. A query for "fox" looks up one term instead of scanning every document. Relevance is scored with BM25.
  • Doc values. A columnar, on-disk structure per field, used for sorting, aggregations and scripting on keyword, numeric and date fields.
  • _source. The original JSON is stored too, so it can be returned and reindexed.

Distribution. Each index is split into primary shards. Each shard is a full Lucene index, distributed across nodes, and each primary can have replica copies on other nodes for high availability and extra read capacity. A search fans out to one copy of every shard, each shard returns its top hits, and the coordinating node merges them.

Near real-time. Lucene writes new documents into in-memory buffers. A refresh (default every 1 s, though idle indices may skip refreshes until searched) creates a new searchable segment. Durability comes from the translog (write-ahead log) and periodic flushes (Lucene commits). Segments are immutable. Updates are delete-plus-reindex, and background merges compact them.

Typical uses: product and site search, log and observability analytics (the ELK stack), security analytics, and more recently vector or hybrid search. OpenSearch is the AWS-led fork with very similar concepts.

How it works

  1. PUT /products/_doc/1 {json}: routed to a shard by hash(_id) % primaries.
  2. The primary indexes it and writes the translog, then replicates to the replicas.
  3. A refresh makes it searchable within about a second.
  4. A search query goes to the coordinating node, fans out to the shards, each shard scores its top N, and the results are merged and fetched.
  5. Merges and flushes run in the background.

Example

PUT /products/_doc/42
{ "name": "Wireless Noise Cancelling Headphones", "brand": "Acme", "price": 129.99 }

GET /products/_search
{
  "query": { "match": { "name": "noise cancelling" } },
  "aggs":  { "brands": { "terms": { "field": "brand.keyword" } } }
}

Common mistakes

  • Using it as the primary system of record without a source of truth for reindexing.
  • Expecting immediate read-after-write search visibility (it is near real-time).
  • Relying on dynamic mappings in production.
  • Creating huge numbers of tiny indices and shards.

How to answer in the interview

"Elasticsearch is a distributed search and analytics engine built on Lucene. Data is stored as JSON documents in indices. Text fields are run through analyzers into terms and stored in an inverted index, which maps each term to the documents containing it, so full-text search is fast and BM25 ranks the results. Other fields use doc values for sorting and aggregations. Each index is split into shards, which are Lucene indexes, with replicas for availability and read throughput. It's near real-time: new documents become searchable after a refresh, every second by default."

Likely follow-up questions

  • Why not a primary database? Weaker transactional guarantees, no multi-document ACID transactions, and mapping changes need reindexing. Keep a source of truth.
  • Refresh versus flush? Refresh makes data searchable. Flush commits segments to disk and trims the translog.
  • How are updates done? Mark the old document deleted and index the new version. Merges reclaim the space.
