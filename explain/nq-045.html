How do parallel streams work internally?

Java 8+ Features · concept · levels mid, senior

In one line

A parallel stream recursively splits its source with Spliterator.trySplit(), runs each chunk as a fork/join task in the common ForkJoinPool (with work stealing), and combines the partial results up the task tree using the reduction or collector combiner.

Detailed explanation

Every stream source provides a Spliterator, an iterator that can also split itself. When a parallel pipeline's terminal operation runs, the framework wraps it in a task (internally classes such as ReduceTask or ForEachTask, built on CountedCompleter). The task calls trySplit() on the spliterator: if it returns a new spliterator, the task forks a child for one half and continues splitting the other. Splitting stops when chunks are small enough, based on the estimated size divided by a multiple of the pool's parallelism.

Each leaf task runs the entire pipeline (filter, map, and so on) over its chunk sequentially and produces a partial result: a partial sum, a partial list, or a partial map. As tasks complete, results are merged up the tree using the combiner: the third argument of reduce, or the collector's combiner() function, for example addAll for lists or a map merge for groupingBy.

The tasks run in ForkJoinPool.commonPool(), whose default parallelism is number of cores minus one; the thread that calls the terminal operation also participates, so all cores are used. Each worker has its own deque; it pushes and pops its own tasks at one end, and idle workers steal from the other end of busy workers' deques. That balances load without a central queue.

Performance depends heavily on the source. ArrayList, arrays and IntStream.range know their size and split in constant time into equal halves. LinkedList must be walked to split, Stream.iterate is inherently sequential, and I/O-based sources like BufferedReader.lines() split poorly. HashSet and HashMap split reasonably but unevenly. Ordered operations add coordination costs, because partial results must be kept in order.

How it works

  1. Terminal operation creates the root task for the pipeline.
  2. trySplit() is called recursively; children are forked into worker deques.
  3. Each leaf processes its chunk through all stages sequentially.
  4. Idle workers steal tasks to keep all cores busy.
  5. Partial results are combined pairwise via the combiner.
  6. The caller receives the final merged result.

Example

// reduce with identity, accumulator and combiner makes the merge step visible
int totalLength = words.parallelStream()
    .reduce(0,
            (partial, word) -> partial + word.length(), // within a chunk
            Integer::sum);                             // merging chunks

// Splitting quality:
List<Integer> array = new ArrayList<>(data);   // splits in O(1), balanced
List<Integer> linked = new LinkedList<>(data); // must traverse to split

System.out.println(ForkJoinPool.commonPool().getParallelism()); // e.g. 7 on 8 cores

Common mistakes

  • Believing each element gets its own thread.
  • Using a combiner that is not consistent with the accumulator in reduce.
  • Parallelising over LinkedList or Stream.iterate.
  • Ignoring that the common pool is shared by the whole JVM.

How to answer in the interview

"A parallel stream asks the source Spliterator to split itself. trySplit is called recursively until the chunks are small enough, and each chunk becomes a fork/join task in the common ForkJoinPool, whose parallelism is cores minus one, with the calling thread helping too. Each task runs the whole pipeline over its chunk and produces a partial result, and those are combined up the tree with the reduce combiner or the collector's combiner. Workers have their own deques and idle ones steal tasks from busy ones, which balances load. How well it performs depends on splitting: ArrayList, arrays and ranges split cheaply and evenly, while LinkedList, iterate or I/O sources do not."

Likely follow-up questions

  • Why does a parallel stream over a LinkedList perform badly? It cannot split in constant time; it must traverse nodes, producing unbalanced, expensive splits.
  • What is a CountedCompleter? A fork/join task type that triggers completion when all child tasks finish, used inside stream implementations.
  • Can you write your own Spliterator? Yes, implementing tryAdvance, trySplit, estimateSize and characteristics.
