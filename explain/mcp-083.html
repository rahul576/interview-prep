Models rarely choose your MCP server tools correctly. How do you improve it?

MCP Servers · scenario · levels mid, senior

In one line

Treat poor tool selection as a usability problem for the model and measure it: run realistic tasks with traces, then rename tools clearly, rewrite descriptions (what, when, when not), merge overlapping tools, simplify schemas with enums and examples, return steering errors, reduce tool overload with filtering or tool search, and re-evaluate after each change.

Detailed explanation

Models choose tools based almost entirely on names, descriptions and schemas. If those are vague, overlapping or written for humans who already know the system, models guess. The fix is iterative and evidence-driven.

Measure first. Build a set of 20 to 50 realistic tasks with the expected tool (and ideally expected arguments). Run them through the host with tracing and record: which tool was chosen instead, which arguments were wrong, where the model asked the user unnecessarily or gave up.

Common fixes:

  • Names that state action and object: search_customer_orders instead of query or orders_v2.
  • Descriptions that explain what the tool does, when to use it, when not to, and how it relates to similar tools: "Use for order status questions. For refunds use create_refund."
  • Fewer, distinct tools. Merge tools that differ only slightly (get_order_by_id, get_order_by_number) into one with a clear parameter; remove rarely useful ones.
  • Simpler input schemas: fewer parameters, enums instead of free strings, sensible defaults, format hints such as dates, and examples in parameter descriptions.
  • Helpful errors that steer: "No order found. If you have an email, use search_customer_orders."

Context overload. If the host loads hundreds of tools from many servers, selection degrades from sheer volume and similar names across servers. Use tool filtering per agent profile, or tool search / deferred loading, where the model searches for relevant tools instead of seeing all of them.

Re-run the evaluation after every change; description edits can fix one task and break another.

How it works

  1. Collect real user requests from logs; label expected tools.
  2. Run the eval suite; compute selection accuracy and argument accuracy.
  3. Inspect failures in traces; group by cause.
  4. Change names, descriptions, schemas or tool set.
  5. Re-run; keep the change only if overall scores improve.
  6. Add the eval to CI so regressions are caught.

Example

{
  "name": "search_customer_orders",
  "description": "Find a customer's orders and their current status. Use for questions like 'where is my order' or 'what did I buy last month'. Do not use for refunds (use create_refund) or invoices (use get_invoice).",
  "inputSchema": {
    "type": "object",
    "properties": {
      "customer_email": { "type": "string", "format": "email" },
      "status": { "type": "string", "enum": ["open", "shipped", "delivered", "returned", "any"], "default": "any" },
      "since": { "type": "string", "format": "date", "description": "e.g. 2026-10-01" }
    },
    "required": ["customer_email"]
  }
}

Common mistakes

  • Tweaking descriptions without a baseline measurement.
  • Tool names reflecting internal service names, not user tasks.
  • Many near-duplicate tools across versions.
  • Ignoring the impact of other servers loaded in the same host.

How to answer in the interview

"I treat it as a usability problem for the model and measure it. I collect realistic tasks and run them with traces to see what the model actually does: which tool it picks instead, which arguments it gets wrong, where it gives up. Then the usual fixes: names that state the action and object, like search_customer_orders instead of query; descriptions that say what the tool does, when to use it and when not to; merging overlapping tools; simpler schemas with enums, defaults and examples; and errors that steer to the right tool. If the host loads many tools from other servers, sheer volume hurts selection, so tool filtering or tool search helps. And I re-run the evaluation after every change."

Likely follow-up questions

  • Build a small eval set? Real anonymised requests labelled with expected tool and arguments, including negative cases.
  • How many tools is too many? No fixed number, but accuracy usually drops as similar tools multiply.
  • Do examples in descriptions help? Yes, especially for argument formats.
