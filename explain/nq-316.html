How can you control the number of concurrent Lambda executions?

Cloud (AWS) · scenario · levels mid

In one line

Control concurrency with reserved concurrency on the function (cap across all triggers), maximum concurrency on the SQS event source mapping, batch size and batching window, FIFO message groups, API Gateway throttling and usage plans for HTTP, and account-level quotas; size these by what the downstream system can sustain; provisioned concurrency controls warmth, not limits.

Detailed explanation

Each lever acts at a different point:

  • Reserved concurrency: a hard ceiling on concurrent executions of a function regardless of trigger, and a guarantee of capacity. Excess synchronous calls get throttling errors; queue and async events are retried.
  • Maximum concurrency (SQS ESM): limits how many concurrent invocations a specific queue mapping creates, without throttling-induced retries. Different queues feeding one function can get different limits.
  • Batch size and batching window: more messages per invocation means fewer concurrent invocations for the same throughput, and allows bulk database writes.
  • FIFO message groups: each group is processed in order, one batch at a time, so the number of active groups caps parallelism.
  • Event sources like Kinesis or DynamoDB Streams: concurrency per shard via the parallelization factor.
  • API Gateway: stage and method throttling (rate and burst) and usage plans per API key limit incoming request rate before Lambda.
  • Account quota: regional ceiling for all functions.
  • Provisioned concurrency pre-warms instances; it does not cap concurrency unless combined with reserved concurrency.

Sizing: start from the bottleneck. If the database allows 50 connections and other apps need 10, allow about 40 for Lambda; with RDS Proxy pooling you can multiplex more safely. Then check throughput: concurrency multiplied by (batch size divided by processing time) must exceed the arrival rate, or the queue grows, which is acceptable if latency requirements allow.

How it works

  1. Identify the downstream limit (connections, API quota).
  2. Set ESM maximum concurrency or reserved concurrency to fit.
  3. Tune batch size and window for efficiency.
  4. Throttle entry points with API Gateway.
  5. Monitor throttles, queue age and downstream saturation.
  6. Adjust based on measured throughput.

Example

# AWS SAM
OrderWorker:
  Type: AWS::Serverless::Function
  Properties:
    ReservedConcurrentExecutions: 50
    Events:
      Orders:
        Type: SQS
        Properties:
          Queue: !GetAtt OrdersQueue.Arn
          BatchSize: 25
          MaximumBatchingWindowInSeconds: 2
          ScalingConfig: { MaximumConcurrency: 40 }
          FunctionResponseTypes: [ReportBatchItemFailures]

Common mistakes

  • Only one lever applied, at the wrong layer.
  • Forgetting other consumers of the database connection pool.
  • Large batches with no partial failure reporting.
  • Assuming provisioned concurrency limits scale.

How to answer in the interview

"There are several levers. Reserved concurrency caps how many instances of a function run across all triggers. For SQS, maximum concurrency on the event source mapping limits the concurrent invocations the poller creates, without throttling errors. Batch size and batching window decide how much work each invocation does. With FIFO queues, the number of message groups limits parallelism. For HTTP, API Gateway throttling and usage plans limit request rates, and the account quota is the global ceiling. I choose the values from what the downstream system can sustain, for example the database connection pool, and monitor throttles and queue age."

Likely follow-up questions

  • Size concurrency for a database with 50 connections? Reserve some for other apps, cap Lambda around 40, or use RDS Proxy.
  • What if the queue keeps growing? Increase batch size, optimise processing or raise limits if downstream allows.
  • Throttling for async invocations? Lambda retries internally for up to six hours by default.
