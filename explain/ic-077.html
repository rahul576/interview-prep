How do you prevent accidental destructive infrastructure changes?

Infrastructure as Code · design · levels senior

In one line

Layer defences: highlight destroy/replace in plans with extra approval in production, policy checks that block deletes of protected types, prevent_destroy plus cloud deletion protection and locks, separate stricter states for high-risk resources, and backups with tested restores as the last line.

Detailed explanation

Destructive accidents happen in ordinary ways: a refactor without moved blocks, a changed count, a provider upgrade, a reviewer skimming a 900-line plan, or someone running terraform destroy in the wrong directory. No single control catches all of these, so you stack several.

Visible plans. The pipeline parses terraform show -json and summarises resource_changes by action: create, update, delete, replace (delete plus create). Deletes and replaces are shown at the top of the PR comment, and if any exist in production the pipeline requires an additional approval from the owning team or a senior engineer.

Policy as code. OPA/Conftest or Sentinel rules on the plan deny deletion or replacement of protected types, such as databases, KMS keys and key vaults, DNS zones, stateful buckets and IAM identity providers, unless an explicit exception (a label on the PR or an allow-list entry) is present.

In code and in the cloud. lifecycle { prevent_destroy = true } makes Terraform error on any plan destroying that resource, but only while the block exists in code. Cloud-side protection guards independently: RDS and DynamoDB deletion protection, EC2 termination protection, S3 Object Lock or MFA delete, Azure resource locks (CanNotDelete), GCP deletion_protection fields. Removing them is a visible, separate change.

Isolation. Rarely changed, high-impact resources (core network, DNS, data stores, KMS) live in separate states with stricter apply roles and approvers, so a busy application stack cannot touch them.

Recovery. Backups, point-in-time recovery, bucket versioning and tested restores bound the damage if everything else fails.

How it works

  1. Plan saved and converted to JSON.
  2. Summary job counts deletes/replaces; posts them prominently.
  3. Policy evaluates protected types; denies unless exception.
  4. Production apply with deletes requires a second approval.
  5. Cloud protections block anything that slips through.

Example

package terraform.protect

protected := {"aws_db_instance", "aws_kms_key", "aws_route53_zone", "aws_s3_bucket"}

deny contains msg if {
  rc := input.resource_changes[_]
  protected[rc.type]
  "delete" in rc.change.actions
  msg := sprintf("%s would be deleted or replaced; requires exception", [rc.address])
}
DELETES=$(jq '[.resource_changes[] | select(.change.actions | index("delete"))] | length' plan.json)
[ "$DELETES" -gt 0 ] && echo "needs-destructive-approval=true" >> "$GITHUB_OUTPUT"

Common mistakes

  • Relying only on prevent_destroy, which vanishes if the resource block is deleted.
  • Approving plans by reading only the summary line.
  • Database, network and app in one state with one role.
  • Backups that have never been restored.

How to answer in the interview

"I layer it. The pipeline highlights destroy and replace actions from the plan JSON and requires an extra approval when there are any in production. Policy as code on the plan blocks deleting or replacing protected types like databases, key vaults, DNS zones and stateful buckets unless there's an explicit exception. In code I use prevent_destroy, and in the cloud deletion protection, termination protection and resource locks, which still work if someone removes the code. High-risk resources live in separate states with stricter permissions. And backups with tested restores limit the damage if something still goes wrong."

Likely follow-up questions

  • How would you design an approval rule only for destructive changes? Parse the plan JSON for delete actions and route to a protected environment requiring approval.
  • Does prevent_destroy protect against a deleted resource block? No; cloud-side protection does.
  • What about terraform destroy by hand? No human write credentials to production; only pipeline roles.
