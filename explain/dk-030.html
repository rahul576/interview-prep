How do you build and tag an image and push it to a registry?

Docker · concept · levels entry

In one line

Build with docker build -t registry/repo:tag ., add more names with docker tag, authenticate with docker login (or a cloud helper), and docker push uploads only layers the registry lacks; tag with immutable versions such as the commit SHA.

Detailed explanation

The image name tells Docker where it will be pushed. myregistry.example.com/team/orders:1.4.0 contains the registry host, the repository path and the tag; without a host the image goes to Docker Hub. The final argument of docker build is the build context, the directory sent to the builder; a .dockerignore keeps it small.

One image can carry many names. docker tag adds another reference to the same image ID, for example the git commit SHA plus a semantic version for releases. Before pushing you authenticate: docker login for generic registries, aws ecr get-login-password | docker login --password-stdin for Amazon ECR, az acr login for Azure, or a token for GHCR. Credentials are stored in ~/.docker/config.json, ideally through a credential helper.

docker push uploads the manifest and the layers. Because layers are content-addressed, the registry checks which digests it already has and only receives the missing ones; base image layers can even be mounted across repositories. That is why the second push of a new version is fast: usually only the application layer changed.

In CI, each build gets an immutable tag, typically the commit SHA, and releases get a version tag. Avoid relying on latest, and consider enabling tag immutability in the registry so a tag can never be overwritten. With docker buildx build --push you build and push in one step, including multi-platform images.

How it works

  1. Build reads the Dockerfile and context and creates layers.
  2. The image is tagged with one or more references.
  3. Login obtains a token for the registry.
  4. Push sends the manifest's layer list; the registry reports missing blobs.
  5. Missing layers are uploaded, then the manifest is written under the tag.

Example

SHA=$(git rev-parse --short HEAD)
IMG=myregistry.example.com/team/orders
docker build -t $IMG:$SHA .
docker tag $IMG:$SHA $IMG:1.4.0
echo "$REG_TOKEN" | docker login myregistry.example.com -u ci --password-stdin
docker push $IMG:$SHA
docker push $IMG:1.4.0

Common mistakes

  • Pushing only latest, so you cannot tell what is deployed or roll back.
  • Passing passwords with -p on the command line, visible in shell history and process lists.
  • A huge build context because there is no .dockerignore.
  • Rebuilding for every environment instead of promoting the same image.

How to answer in the interview

"I build with docker build -t registry/team/orders:1.4.0 ., where the name includes the registry, repository and tag and the dot is the build context. docker tag adds more names to the same image, for example the commit SHA. I log in with docker login, or with cloud helpers like aws ecr get-login-password or az acr login, using --password-stdin. docker push uploads only the layers the registry doesn't have yet. In CI every build gets an immutable tag like the commit SHA, releases get a semantic version, and I avoid relying on latest."

Likely follow-up questions

  • Why are later pushes faster? Unchanged layers already exist in the registry and are skipped.
  • What is tag immutability? A registry setting that prevents overwriting existing tags.
  • How do you push multi-arch images? docker buildx build --platform ... --push.
