What are common Terraform anti-patterns you have seen, and how would you fix them?

Terraform · concept · levels mid, senior, lead

In one line

Common anti-patterns are a giant single state, copy-pasted code instead of modules, over-abstracted wrapper modules, local applies and manual console changes, secrets in code or tfvars, and heavy provisioners; fix them with split states, opinionated modules, pipeline-only applies, secret stores and proper configuration tools.

Detailed explanation

One giant state. An entire organisation in one state means plans take many minutes, locks block everyone, every change has a huge blast radius and permissions cannot be separated. Split by ownership, lifecycle and environment: network, shared platform, each application, each environment. Use removed and import blocks to move resources without recreating them.

Copy-paste. The same 400 lines duplicated in dev, test and prod drift apart; a fix applied in one is forgotten in others. Use a shared module with per-environment inputs, or one configuration with per-environment variable files and states.

Over-abstraction. The opposite failure: wrapper modules that expose every provider argument through dozens of variables and add no decisions. They are harder to use than the raw resource and break with every provider change. Good modules encode decisions: secure defaults, naming, diagnostics, and expose a small, intentional interface.

Process anti-patterns. Engineers running apply from laptops, unreviewed, with personal credentials, and manual changes in the console that cause drift. Fix with pipeline-only applies with OIDC identities, read-only human access to production, break-glass procedures and drift detection.

Security. Secrets hard-coded in .tf files or committed tfvars. Use a secret store, sensitive variables, generated passwords, ephemeral resources and write-only arguments where supported, and secret scanning in CI.

Provisioners. Long remote-exec scripts to configure servers are fragile and make Terraform a poor configuration manager. Build images (Packer), use cloud-init, configuration management or Kubernetes and GitOps instead.

How it works

  1. Identify symptoms: slow plans, frequent drift, inconsistent environments.
  2. Prioritise by risk: secrets and manual applies first.
  3. Introduce pipelines, OIDC and drift detection.
  4. Extract modules from copy-paste; simplify wrappers.
  5. Split large states incrementally with import and removed blocks.
  6. Replace provisioners with images or cloud-init.

Example

Before                                 After
live/                                   modules/app-service/      (opinionated, versioned)
  everything.tf   (4,000 resources)     live/
  terraform.tfvars (contains secrets)     network/prod/   (state)
                                          orders/dev/     (state, uses module v1.3)
                                          orders/prod/    (state, uses module v1.3)

Common mistakes

  • Splitting states without defining interfaces between them.
  • Replacing copy-paste with modules nobody versions.
  • Banning laptop applies without providing a working pipeline first.
  • Fixing everything at once instead of incrementally.

How to answer in the interview

"The most common is one giant state for everything, which makes plans slow and every change risky; I split by ownership, lifecycle and environment. The opposite is copy-pasted code across environments instead of a shared module. Then over-abstracted wrapper modules that expose every argument and add only indirection; good modules encode decisions. Process anti-patterns are local applies and console changes, fixed with pipeline-only applies and drift detection. Security: secrets in code or tfvars. And heavy provisioners, which belong in images, configuration management or Kubernetes."

Likely follow-up questions

  • How would you convince a team to split a state? Show plan duration, lock contention and blast radius, then migrate one slice as a pilot.
  • How big should a state be? Small enough for fast plans and one owning team.
  • Are provisioners ever okay? As a last resort for small bootstrap steps.
