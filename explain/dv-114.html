What is an Ingress and an Ingress controller in Kubernetes?

Kubernetes · concept · levels entry, mid

In one line

An Ingress is a Kubernetes object holding HTTP/HTTPS routing rules by host and path; it does nothing alone, so an Ingress controller (Traefik, HAProxy, a cloud controller such as the AWS Load Balancer Controller, and others) implements it, letting many services share one load balancer with TLS termination. New designs increasingly use the Gateway API.

Detailed explanation

Exposing every service with type: LoadBalancer gives each its own cloud load balancer and public IP: expensive, and with no HTTP routing. An Ingress solves this at L7: one entry point, rules such as api.example.com/orders → orders:80 and /users → users:80, and TLS certificates referenced from Secrets.

The Ingress resource is just configuration in the API. An Ingress controller watches Ingress objects (filtered by ingressClassName) and configures a real proxy: an in-cluster proxy such as Traefik, HAProxy, Contour or NGINX-based controllers, or a cloud load balancer such as AWS ALB or Azure Application Gateway. Behaviour beyond host and path (rewrites, rate limits, auth, canary weights) relies on controller-specific annotations, which is why Ingress YAML is rarely portable.

For TLS, cert-manager watches Ingresses or Certificates and obtains certificates automatically from Let's Encrypt using ACME, storing them in Secrets and renewing them before expiry.

An important 2026 change: the community ingress-nginx controller, once the most common choice, has been retired (best-effort maintenance ended in March 2026, so no more fixes). Teams running it are migrating to other controllers, and the Gateway API (GatewayClass, Gateway, HTTPRoute) is the more expressive, role-oriented successor with built-in header matching and traffic weights.

How it works

  1. Install a controller and its IngressClass.
  2. Controller gets an external IP through a LoadBalancer Service or cloud LB.
  3. You create an Ingress with hosts, paths and a TLS Secret.
  4. Controller translates rules into proxy configuration.
  5. Requests hit the LB, are matched by host and path, and forwarded to Service endpoints.
  6. cert-manager keeps the TLS Secret valid.

Example

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod
spec:
  ingressClassName: traefik
  tls:
  - hosts: [api.example.com]
    secretName: api-example-tls
  rules:
  - host: api.example.com
    http:
      paths:
      - { path: /orders, pathType: Prefix, backend: { service: { name: orders, port: { number: 80 } } } }
      - { path: /users,  pathType: Prefix, backend: { service: { name: users,  port: { number: 80 } } } }

Common mistakes

  • Creating Ingress objects with no controller installed.
  • Missing or wrong ingressClassName when several controllers exist.
  • Relying heavily on annotations, making migration painful.
  • Still running the retired ingress-nginx controller in production.

How to answer in the interview

"An Ingress is a resource with HTTP routing rules by host and path, plus TLS settings. It doesn't do anything by itself: an Ingress controller such as Traefik, HAProxy or a cloud controller like the AWS Load Balancer Controller watches it and configures a proxy or load balancer. That lets many services share one entry point instead of a LoadBalancer each. TLS is usually automated with cert-manager and Let's Encrypt. Since the community ingress-nginx project was retired in 2026, new work typically goes to the Gateway API, which is more expressive and portable."

Likely follow-up questions

  • How do you canary with Ingress? Controller-specific weight annotations; with Gateway API, backendRefs weights in an HTTPRoute.
  • Ingress vs LoadBalancer Service? L7 routing for many services vs one L4 load balancer per service.
  • What does pathType do? Prefix, Exact or ImplementationSpecific matching semantics.
