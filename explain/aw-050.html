Compare API Gateway REST APIs and HTTP APIs, and how you secure and throttle them.

Cloud (AWS) · concept · levels mid

In one line

HTTP APIs are cheaper, faster and simpler (Lambda/HTTP proxies, JWT authorizers, CORS, VPC links), while REST APIs add usage plans and API keys, request validation and mapping, caching, WAF, and private or edge endpoints; secure them with IAM, JWT/Cognito or Lambda authorizers and protect backends with throttling and quotas.

Detailed explanation

HTTP APIs cost roughly 70 percent less per request and add less latency. They cover most proxy use cases: routes to Lambda, HTTP backends and some AWS services, private integrations to ALBs, NLBs or Cloud Map through VPC links, native JWT authorizers for Cognito or any OIDC provider, IAM and Lambda authorizers, automatic deployments and CORS.

REST APIs are the older, richer product: usage plans with API keys for per-client throttling and quotas, request validation against models, mapping templates (VTL) to transform requests and responses, response caching, direct AWS WAF association, resource policies, private API endpoints reachable only through interface VPC endpoints, edge-optimised endpoints, canary release settings and X-Ray tracing. Both support custom domains with ACM certificates and mutual TLS.

Authentication: IAM authorization (SigV4) suits service-to-service calls and cross-account access; Cognito user pools or JWT authorizers validate user tokens and scopes; Lambda authorizers implement custom logic like API tokens or tenant checks, with result caching. API keys identify clients for usage plans but are not a security mechanism on their own.

Throttling uses a token bucket: an account-level regional limit (10,000 requests per second by default, with bursts), then stage and route (method) limits, and for REST APIs per-usage-plan rate, burst and daily or monthly quotas. Exceeding a limit returns 429 Too Many Requests, protecting backends. WAF adds rate-based rules per IP.

How it works

  1. Client calls the custom domain over TLS.
  2. WAF (REST) or edge rules filter malicious traffic.
  3. The authorizer validates IAM signature, JWT or custom token.
  4. Throttling and quota checks run; excess requests get 429.
  5. The integration forwards to Lambda, an HTTP backend or VPC link.
  6. Response returns, optionally cached and logged.

Example

Per-partner quotas on a REST API:

aws apigateway create-usage-plan --name partner-gold \
  --api-stages apiId=a1b2c3,stage=prod \
  --throttle rateLimit=50,burstLimit=100 \
  --quota limit=1000000,period=MONTH
aws apigateway create-api-key --name acme-corp --enabled
aws apigateway create-usage-plan-key --usage-plan-id up123 \
  --key-id k456 --key-type API_KEY

Common mistakes

  • Treating API keys as authentication.
  • Picking REST APIs by default and paying more for unused features.
  • No throttling, so one client can overload a database behind Lambda.
  • Lambda authorizers without result caching, adding latency and cost to every call.

How to answer in the interview

"HTTP APIs are cheaper and faster and cover most needs: Lambda and HTTP backends, JWT authorizers, CORS and VPC links. REST APIs add usage plans with API keys and quotas, request validation and transformation, caching, WAF and private endpoints. For security I use IAM for service-to-service, JWT or Cognito authorizers for users, and Lambda authorizers for custom logic. Throttling applies at account, stage and route level, plus per usage plan on REST APIs, and returns 429 to protect the backend."

Likely follow-up questions

  • How give each partner its own quota? REST API usage plans with one API key per partner, combined with real auth.
  • How expose an internal API privately? REST private endpoint via interface VPC endpoint, or HTTP API with VPC link behind internal routing.
  • What does a 429 mean for clients? Retry with exponential backoff and jitter.
