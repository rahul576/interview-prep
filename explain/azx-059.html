How do you pass values between steps, jobs and stages in Azure Pipelines?

Azure DevOps & Pipelines · concept · levels mid, senior

In one line

Within a job use task.setvariable; across jobs mark it isOutput=true, give the step a name, add dependsOn, and map it with $[ dependencies.Job.outputs['step.var'] ]; across stages use $[ stageDependencies.Stage.Job.outputs['step.var'] ]; these need runtime expressions because values don't exist at compile time.

Detailed explanation

Same job: a script emits a logging command: echo "##vso[task.setvariable variable=imageTag]1.4.2". Subsequent steps in that job can use $(imageTag). The variable is not visible in the setting step itself, only after it.

Another job in the same stage:

  1. Mark it as output: ##vso[task.setvariable variable=imageTag;isOutput=true]1.4.2.
  2. Give the step a name: (e.g. setTag), because the reference uses the step name.
  3. The consuming job declares dependsOn: Build and maps the variable: imageTag: $[ dependencies.Build.outputs['setTag.imageTag'] ].

Another stage: the consuming stage dependsOn the producing stage, and the job maps: $[ stageDependencies.BuildStage.Build.outputs['setTag.imageTag'] ]. Stage-level conditions can use dependencies.BuildStage.outputs['Build.setTag.imageTag']. For deployment jobs, the output path includes the lifecycle hook and resource name, e.g. outputs['Deploy_web.setTag.imageTag'] for runOnce (the job name prefixed), which trips many people.

Why runtime expressions? Azure Pipelines has three syntaxes:

  • ${{ }} template expressions: evaluated at compile time, before any job runs, so they can't see values produced by jobs.
  • $( ) macro syntax: replaced just before a task runs, from variables known at that point.
  • $[ ] runtime expressions: evaluated at runtime for variable definitions and conditions; required to read dependencies and stageDependencies.

Secrets: add issecret=true to mask; secret outputs still need explicit mapping. For large data, use pipeline artifacts instead of variables.

How it works

  1. Producing step emits setvariable with isOutput.
  2. Agent records the output for the job.
  3. Consumer declares dependsOn.
  4. Runtime expression resolves the value at job start.
  5. Steps use the mapped variable as $(name).

Example

stages:
- stage: BuildStage
  jobs:
  - job: Build
    steps:
    - bash: echo "##vso[task.setvariable variable=imageTag;isOutput=true]$(Build.BuildId)-$(git rev-parse --short HEAD)"
      name: setTag
- stage: Deploy
  dependsOn: BuildStage
  jobs:
  - job: Release
    variables:
      imageTag: $[ stageDependencies.BuildStage.Build.outputs['setTag.imageTag'] ]
    steps:
    - script: echo "Deploying $(imageTag)"

Common mistakes

  • Forgetting name: on the producing step.
  • Missing dependsOn, so the dependency context is empty.
  • Using ${{ }} to read outputs.
  • Wrong path for deployment job outputs.

How to answer in the interview

"Within a job, a step uses the task.setvariable logging command and later steps read it normally. To use it in another job, I add isOutput=true, give the step a name, add dependsOn, and map it with a runtime expression like dependencies.Build.outputs['setTag.imageTag']. Across stages it's stageDependencies with stage, job, step and variable names. It must be a runtime $[ ] expression because the value doesn't exist when the pipeline compiles; template expressions run before any job. Secrets add issecret=true."

Likely follow-up questions

  • Why can't template expressions read outputs? They're evaluated at compile time before jobs run.
  • Deployment job outputs? Prefix with the job or hook name, e.g. <job>.<step>.<var>.
  • Large values? Use pipeline artifacts.
