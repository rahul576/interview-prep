What is the difference between SQS and SNS?

Cloud (AWS) · concept · levels entry

In one line

SQS is a message queue: messages are stored durably (up to 14 days) and consumers poll, with each message processed by one consumer; SNS is publish-subscribe: a message to a topic is pushed to all subscribers (SQS, Lambda, HTTP, email, SMS) and not stored; combined, they give the fan-out pattern.

Detailed explanation

SQS (Simple Queue Service) decouples a producer from a consumer. The producer sends a message; SQS stores it redundantly; one of possibly many consumers polls (ideally with long polling), receives it, processes it and deletes it. While being processed the message is hidden for the visibility timeout; if the consumer crashes, it reappears and is retried. After a number of failed receives it moves to a dead-letter queue. Retention is configurable from one minute to 14 days (default 4 days). Standard queues give near-unlimited throughput with at-least-once delivery and best-effort ordering; FIFO queues give ordering per message group and exactly-once processing within a deduplication window. Queues absorb spikes: if 10,000 orders arrive in a minute, workers process them at their own rate.

SNS (Simple Notification Service) is pub/sub. Publishers send a message to a topic; SNS immediately pushes a copy to every subscription: SQS queues, Lambda functions, HTTP/S endpoints, email, SMS or mobile push. SNS does not keep messages for later; if delivery fails it retries per the delivery policy and can send failures to a DLQ. Subscription filter policies let each subscriber receive only messages matching attributes. SNS FIFO topics exist for ordered fan-out to FIFO queues.

The fan-out pattern combines them: an OrderPlaced event is published once to an SNS topic, which delivers it to separate SQS queues for billing, shipping and analytics. Each consumer gets its own durable buffer, retries independently and scales separately, and adding a new consumer means adding a subscription without touching the producer.

How it works

  1. SQS: producer SendMessage, consumer ReceiveMessage, processes, DeleteMessage.
  2. Failure: message reappears after the visibility timeout; repeated failure goes to a DLQ.
  3. SNS: producer Publish to a topic.
  4. SNS pushes to every subscription, applying filter policies.
  5. Fan-out: subscriptions are SQS queues, each with its own consumers.

Example

aws sns create-topic --name order-events
aws sqs create-queue --queue-name billing-orders
aws sns subscribe --topic-arn arn:aws:sns:eu-west-1:123456789012:order-events \
  --protocol sqs --notification-endpoint arn:aws:sqs:eu-west-1:123456789012:billing-orders \
  --attributes '{"RawMessageDelivery":"true"}'

aws sns publish --topic-arn arn:aws:sns:eu-west-1:123456789012:order-events \
  --message '{"orderId":"A-1001","total":59.90}'

The billing queue also needs a queue policy allowing the topic to send messages.

Common mistakes

  • Using SNS alone when consumers may be offline, losing messages.
  • Visibility timeout shorter than processing time, causing duplicates.
  • Non-idempotent consumers with standard queues.
  • No dead-letter queue.

How to answer in the interview

"SQS is a queue: producers send messages, SQS stores them durably for up to 14 days, and consumers poll and process them, each message handled by one consumer. That decouples services and absorbs spikes. SNS is pub/sub: a message published to a topic is pushed immediately to all subscribers, SQS queues, Lambdas, HTTP endpoints, email or SMS, and it isn't stored for later. They're often combined in fan-out: an OrderPlaced event goes to an SNS topic, which delivers copies to separate SQS queues for billing, shipping and analytics, each processing at its own pace with its own retries and DLQ."

Likely follow-up questions

  • When EventBridge instead of SNS? For content-based routing rules, many targets, SaaS sources, schema registry, archive and replay.
  • How do you handle duplicates? Make consumers idempotent or use FIFO deduplication.
  • What is long polling? ReceiveMessage waits up to 20 seconds for messages, reducing empty responses and cost.
