When should you NOT use parallel streams?

Java 8+ Features · concept · levels senior, lead

In one line

Avoid parallel streams for small data, blocking I/O, side effects or shared mutable state, poorly splittable sources (LinkedList, Stream.iterate), order-dependent stateful operations, and in servers where everything competes for the shared ForkJoinPool common pool; always measure first.

Detailed explanation

Parallel streams split the source with a Spliterator, process chunks on worker threads of the common ForkJoinPool (sized to cores minus one by default), then merge results. That overhead is only worth paying for large, CPU-bound, independent work on sources that split cheaply and evenly, such as arrays, ArrayList, IntStream.range.

When not to use them:

  • Small data sets or cheap per-element work: splitting, task scheduling and merging cost more than the work itself. A rough heuristic is the "NQ model": N elements times Q cost per element must be large (often quoted above ~10,000).
  • Blocking I/O (HTTP, JDBC, files) inside the pipeline: it ties up the few common-pool threads, starving every other parallel stream and CompletableFuture default tasks in the JVM. Use an executor, virtual threads or reactive clients instead.
  • Side effects / shared mutable state: adding to an ArrayList from forEach is a race condition; use collectors.
  • Poorly splittable sources: LinkedList, Stream.iterate, BufferedReader.lines() split badly.
  • Ordered stateful operations: limit, skip, sorted, distinct, findFirst on ordered streams require coordination; forEachOrdered serialises output.
  • Servers: per-request parallelism multiplies across concurrent requests, all sharing one pool, so latency becomes unpredictable. The server already parallelises across requests.

Also beware of boxing costs, contention on synchronised resources, and non-associative reductions, which give wrong results in parallel.

How it works

  1. parallel() sets a flag on the pipeline.
  2. At the terminal op the source is recursively split into tasks.
  3. Tasks run on common-pool workers (and the calling thread).
  4. Partial results are combined; ordered ops add synchronisation.

Example

// Good candidate: large array, CPU-bound, no shared state
long primes = LongStream.rangeClosed(2, 50_000_000).parallel()
    .filter(Primes::isPrime).count();

// Bad: blocking I/O on the common pool
List<Price> prices = skus.parallelStream()
    .map(sku -> pricingClient.fetch(sku))        // HTTP call blocks a pool thread
    .toList();

// Better for I/O-bound work (Java 21)
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<Price>> futures = skus.stream()
        .map(sku -> exec.submit(() -> pricingClient.fetch(sku))).toList();
}

// Bad: race condition
List<String> out = new ArrayList<>();
names.parallelStream().map(String::trim).forEach(out::add);   // not thread-safe

Common mistakes

  • Turning on parallel() as a free speed-up without benchmarking (use JMH).
  • Doing network or database calls inside parallel streams.
  • Mutating shared collections instead of collecting.
  • Expecting deterministic order from forEach in parallel.

How to answer in the interview

"Parallel streams only pay off for large CPU-bound workloads on easily splittable sources like arrays or ArrayList. I avoid them for small data sets, where splitting and merging overhead outweighs the work; for blocking I/O, which ties up the shared common pool; for side effects or shared mutable state, which aren't thread-safe; and for poorly splittable sources like LinkedList or Stream.iterate. In server applications every request would compete for the same ForkJoinPool common pool, so one request can slow others. I always measure with a proper benchmark before using them."

Likely follow-up questions

  • How do you run a parallel stream on a custom ForkJoinPool? Submit the terminal operation inside customPool.submit(() -> stream.parallel()...).get(); this relies on implementation behaviour, so prefer explicit executors.
  • What size is the common pool? By default available processors minus one, configurable via java.util.concurrent.ForkJoinPool.common.parallelism.
  • Why must reductions be associative? Partial results are combined in arbitrary groupings.
