Design a payment processing service.

System Design · design · levels senior, lead

In one line

A payment service requires idempotency keys on every request, models payments as an explicit state machine, records money in an immutable double-entry ledger, integrates gateways with timeouts, retries, signed webhooks and daily reconciliation, and stays mostly out of PCI DSS scope via tokenisation.

Detailed explanation

Payments are about correctness under failure. Networks time out, users double-click, gateways send duplicate webhooks. The design must ensure no double charge, no lost money, and an auditable trail.

Idempotency: clients send an Idempotency-Key header. The service stores the key with the request hash and the response; a retry with the same key returns the stored result instead of charging again. A unique constraint makes this race-safe. The same key is passed to the gateway, which most providers (Stripe, Adyen, Razorpay) support.

State machine: CREATED -> AUTHORISED -> CAPTURED -> (PARTIALLY_)REFUNDED, with FAILED, CANCELLED and an important UNKNOWN/PENDING state for timeouts. Transitions are validated (no refund before capture) and persisted with history, using optimistic locking.

Ledger: balances are never "updated in place". Each movement is a double-entry journal: debits equal credits across accounts (customer, merchant payable, fees, gateway clearing). The ledger is append-only; corrections are new entries. Balances are derived and always reconcile.

Gateway integration: calls use timeouts and retries only when safe (with idempotency). Asynchronous results arrive via webhooks, verified by signature and processed idempotently. A reconciliation job compares internal records with provider settlement reports daily, flagging mismatches.

Security: never store raw card numbers; use the provider's hosted fields or tokenisation so card data never touches our servers (reducing PCI scope, e.g. to SAQ A). Encrypt data, restrict access, audit everything, and add fraud checks and 3-D Secure where required.

How it works

  1. POST /payments with Idempotency-Key -> insert key (unique) or return stored response.
  2. Create payment CREATED, call gateway authorise with a token.
  3. Success -> AUTHORISED, ledger entries for the hold; failure -> FAILED.
  4. Timeout -> PENDING; resolve via gateway status query or webhook.
  5. Capture on shipment -> CAPTURED, ledger moves funds to merchant payable.
  6. Nightly reconciliation against settlement files.

Example

CREATE TABLE ledger_entries (
  id          bigserial PRIMARY KEY,
  journal_id  uuid    NOT NULL,           -- groups the balanced entries
  account     text    NOT NULL,           -- e.g. 'customer:42', 'merchant:7:payable'
  direction   text    NOT NULL CHECK (direction IN ('DEBIT','CREDIT')),
  amount      numeric(19,4) NOT NULL CHECK (amount > 0),
  currency    char(3) NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);
-- Capture of 1000 INR: two rows with the same journal_id
-- DEBIT  gateway:clearing      1000.00 INR
-- CREDIT merchant:7:payable    1000.00 INR

Common mistakes

  • Retrying a charge after a timeout without an idempotency key.
  • Storing balances as a mutable column with no history.
  • Using floating-point types for money.
  • Trusting webhooks without signature verification.
  • Storing card numbers and dragging the whole system into PCI scope.

How to answer in the interview

"Every request carries an idempotency key, stored with the response, so retries never double charge, and I pass it to the gateway too. Payments follow an explicit state machine, created, authorised, captured, refunded or failed, plus a pending state for unknown outcomes. Money is recorded in an append-only double-entry ledger so balances always reconcile. Gateway calls have timeouts, results come via signature-verified webhooks processed idempotently, and a daily job reconciles against settlement reports. Card data is tokenised by the provider so we stay mostly out of PCI scope, and everything is audited."

Likely follow-up questions

  • Gateway timed out, unknown result? Mark pending, query the gateway by idempotency key or wait for the webhook; never blindly re-charge.
  • Why double-entry? Every movement balances, making errors detectable and audits simple.
  • Multi-currency? Store amounts in minor units with currency; FX as explicit ledger entries.
