How do you handle spot or preemptible node interruptions for workloads on Kubernetes?

Kubernetes · concept · levels senior, lead

In one line

Handle spot interruptions by detecting the notice and draining fast (Karpenter interruption handling, AWS Node Termination Handler or the provider's integration), and by putting only fault-tolerant, diversified, gracefully-stopping workloads on spot, with an on-demand base for critical replicas.

Detailed explanation

Spot (AWS), Spot VMs (Azure) and Spot or preemptible VMs (GCP) are much cheaper because the provider can reclaim them. Notice is short: about two minutes on AWS, roughly 30 seconds on Azure and GCP. AWS also sends a rebalance recommendation earlier when a pool is at elevated risk.

The cluster must react inside that window. Karpenter watches an SQS queue of interruption events, cordons and drains the node and launches a replacement; the AWS Node Termination Handler does the cordon and drain for managed node groups; GKE and AKS integrate with their own preemption signals and the kubelet's graceful node shutdown. Pods then receive SIGTERM and must stop quickly, so terminationGracePeriodSeconds must fit within the notice.

Workload choice matters most. Good spot candidates are stateless services with several replicas, CI runners, and batch jobs that checkpoint progress. Databases, stateful singletons and controllers with long shutdowns stay on on-demand nodes, enforced with taints, tolerations and node affinity. Diversify across many instance types and zones, because reclaims usually hit one capacity pool at a time, and keep enough on-demand capacity that critical replicas survive even if all spot disappears. PDBs and topology spread constraints stop all replicas landing on the same spot pool.

How it works

  1. Provider issues the interruption notice (or rebalance recommendation).
  2. Handler (Karpenter, NTH, cloud integration) cordons the node.
  3. Node is drained; pods get SIGTERM and shut down gracefully.
  4. Controllers reschedule pods; the autoscaler launches replacement capacity.
  5. Batch jobs resume from their last checkpoint.

Example

apiVersion: karpenter.sh/v1
kind: NodePool
metadata: { name: spot-general }
spec:
  template:
    spec:
      requirements:
        - { key: karpenter.sh/capacity-type, operator: In, values: ["spot"] }
        - { key: karpenter.k8s.aws/instance-category, operator: In, values: ["c","m","r"] }
        - { key: topology.kubernetes.io/zone, operator: In, values: ["eu-west-1a","eu-west-1b","eu-west-1c"] }
      taints:
        - { key: spot, value: "true", effect: NoSchedule }

Common mistakes

  • Allowing only one or two instance types, so a single pool reclaim removes everything.
  • Grace periods longer than the interruption notice.
  • Running all replicas of a critical service on spot.
  • Long batch jobs with no checkpointing that restart from zero.

How to answer in the interview

"Spot nodes can be reclaimed with about two minutes' notice on AWS and around thirty seconds on Azure and GCP, so something must catch that notice, cordon and drain the node: Karpenter's interruption handling, the AWS node termination handler or the provider integration. Then pods need fast graceful shutdown. I only put fault-tolerant work on spot: stateless services with several replicas, CI runners and checkpointing batch jobs. Databases and singletons stay on on-demand nodes using taints and affinity. I diversify instance types and zones, keep an on-demand base for critical replicas and use PDBs and topology spread."

Likely follow-up questions

  • What if many spot nodes are reclaimed at the same moment? PDBs cannot stop involuntary loss, so the on-demand base and diversification carry the load while the autoscaler refills, possibly falling back to on-demand.
  • How do you checkpoint batch work? Save progress to object storage regularly and make jobs resumable and idempotent.
  • Spot for GPU training? Yes with frequent checkpoints, but capacity is scarcer.
