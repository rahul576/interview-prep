Design a feature flag and dynamic configuration service.

Classic Design Problems · design · levels entry, mid, senior

In one line

A feature-flag service stores flags with targeting rules, ships the full config to SDKs that evaluate locally from memory, streams changes (SSE/WebSockets, polling fallback), uses deterministic hashing for percentage rollouts, falls back to last-known or safe defaults, and keeps an audit log and kill switches.

Detailed explanation

Flags decouple deploy from release: code ships dark, then turns on for 1%, 10%, 100% of users, or just for internal staff, and can be turned off instantly without a deploy.

Performance rule: evaluating a flag must not be a network call. SDKs download all flag rules at startup, keep them in memory, and evaluate in microseconds. Updates arrive via a streaming connection within seconds.

Percentage rollouts must be sticky: hash flagKey + userId into 0–99 and enable if below the percentage. The same user always gets the same answer, and increasing 10% → 20% keeps the original 10% enabled.

Resilience: if the flag service is down, SDKs continue with the last config (persisted locally) or compiled-in defaults. The flag service is never in the critical path.

Governance: audit log (who changed what, when), approvals for production, and flag lifecycle management so flags get removed.

How it works

  1. Admin UI → flag store (DB) → publish change.
  2. Streaming edge (or CDN-hosted JSON) → SDKs update in memory.
  3. App: if (flags.isEnabled("new-checkout", user)) → local evaluation.
  4. Exposure events (sampled) → analytics for experiments.

Example

function bucket(flagKey, userId) {
  const h = murmurhash3(`${flagKey}:${userId}`);
  return h % 100;                    // 0..99
}
enabled = rule.percentage > bucket("new-checkout", user.id);

Common mistakes

  • Remote call per evaluation.
  • Random (non-sticky) percentage assignment.
  • Flags that never get cleaned up.
  • Using flags for long-term configuration of entitlements without governance.

How to answer in the interview

"Flags and their targeting rules live centrally with an audit log. SDKs fetch the whole configuration, evaluate locally from memory and receive updates over a stream, so there's no latency cost and no hard dependency. Percentage rollouts hash the user ID with the flag key so assignment is sticky. If the service is unreachable, SDKs use the last known config or safe defaults, and kill switches let us disable a feature instantly."

Likely follow-up questions

  • Clean up old flags? Expiry dates, stale-flag reports, linters, tickets on creation.
  • Server vs client-side SDKs? Client SDKs get evaluated results only (don't leak rules).
  • Experiments? Log exposures and analyse metrics per variant.
