How do you monitor the quality of an LLM application in production?

LLMOps & RAG · concept · levels mid, senior

In one line

Monitor production with end-to-end tracing of every request, user feedback (explicit and implicit), online evaluation of sampled traffic with automated judges, operational metrics (latency, errors, cost), safety signals, and topic drift analysis, with alerts on quality drops and cost spikes.

Detailed explanation

Traditional monitoring tells you whether the service is up; it cannot tell you whether answers are good. LLM applications fail quietly: a provider model update, a stale index or a prompt change can degrade quality while every HTTP status is 200.

Tracing is the foundation. For each request capture input, rewritten query, retrieved chunks and scores, the final prompt (or prompt version and variables), model name and version, tool calls, output, token counts, latency per stage and cost. Store it with privacy controls: PII redaction, access control and limited retention.

User signals:

  • Explicit: thumbs up/down, ratings, comments. Sparse and skewed towards unhappy users.
  • Implicit: copying the answer, accepting or heavily editing a generated draft, rephrasing and retrying, abandoning the session, escalating to a human agent, reopening a ticket. These are more plentiful and often more honest.

Online evaluation. Sample, for example, 2-5% of traffic and score it with judges for groundedness, relevance, refusal appropriateness and policy compliance. Plot trends by feature, model version and prompt version.

Operational metrics. Latency percentiles including time to first token, error and rate-limit rates, fallback usage, tokens and cost per request and per feature.

Safety. Content filter hits, detected prompt injection attempts, PII in outputs, guardrail trigger rates.

Drift. Cluster incoming questions by embedding and track topic distribution over time; new clusters often show gaps in the knowledge base or new product issues.

How it works

  1. Instrument with OpenTelemetry-compatible tracing.
  2. Capture feedback events linked to trace IDs.
  3. Run sampled online judges asynchronously.
  4. Build dashboards per feature and version.
  5. Alert on quality score drops, error spikes and cost anomalies.
  6. Triage weekly; feed failures into the evaluation set.

Example

Dashboard: Support assistant (last 7 days)
  Requests                 182,400
  p95 latency / TTFT       4.1 s / 0.9 s
  Thumbs down rate         6.2%   (prompt v12: 5.1%, v13: 8.4%)  <- investigate
  Escalation rate          11%
  Groundedness (sampled)   0.93
  Cost per conversation    $0.021
  Injection attempts       312 blocked
  New topic cluster        "eSIM activation" (+4% of queries)

Common mistakes

  • Only infrastructure metrics, no quality signals.
  • Logging raw prompts with personal data indefinitely.
  • Relying solely on thumbs feedback.
  • Dashboards without breakdown by prompt and model version.

How to answer in the interview

"Every request is traced end to end: inputs, retrieved context, prompt version, model, tool calls, outputs, tokens, latency and cost, with redaction and retention limits. Quality comes from user signals, both explicit ratings and implicit ones like retries, edits, copies and escalations, plus online evaluation where judges score a sample of traffic for groundedness and relevance. Operational dashboards cover latency, errors, rate limits and cost per feature, and safety monitoring tracks filter hits and injection attempts. I also cluster user questions to spot drift. Alerts fire on quality drops or cost spikes, and failures flow back into the evaluation set."

Likely follow-up questions

  • Most reliable implicit signal? Task-specific: escalation or retry rate for support; edit distance for drafting.
  • Sampling rate for judges? Enough for stable trends per segment, balanced against judge cost.
  • Provider silently updates the model? Pinned versions plus online eval trends catch it.
