What is Testcontainers, and why is it useful?

Testing · concept · levels mid, senior

In one line

Testcontainers starts real dependencies (PostgreSQL, Kafka, Redis, LocalStack and more) in throwaway Docker containers from your tests, so integration tests run against the same engine and version as production, isolated and repeatable, with Spring Boot @ServiceConnection wiring them in automatically.

Detailed explanation

Before Testcontainers, integration tests used in-memory substitutes such as H2 or embedded Kafka, or a shared test database. In-memory databases differ from production: different SQL dialect, missing features (JSONB, ON CONFLICT, window functions, specific index types), different locking and constraint behaviour, and Flyway migrations that may not even run. Shared databases cause tests to interfere with each other and depend on whoever touched the data last.

Testcontainers is a library (Java originally, now also Go, .NET, Node, Python) that talks to Docker, pulls an image, starts a container on a random port, waits until it is ready using a wait strategy (log line, port, health check) and gives the test the connection details. When tests finish, the Ryuk sidecar removes containers even if the JVM crashes. Modules exist for most databases, Kafka (including the Apache Kafka native image), Redis, Elasticsearch, RabbitMQ, LocalStack for AWS, Keycloak, MockServer and generic containers or Docker Compose.

JUnit 5 integration: @Testcontainers with @Container fields manages the lifecycle (static fields are shared by a class). Spring Boot 3.1+ adds @ServiceConnection, which reads the container's host and port and configures the DataSource, Kafka or Redis connection without manual properties; @DynamicPropertySource covers other cases. You can also run the application locally with containers via SpringApplication.from(...).with(TestConfig.class).

Speed: start containers once per JVM using the singleton pattern (static containers in a base class), enable reusable containers for local development, keep the Spring context cached and use small images. CI needs a Docker-compatible runtime or Testcontainers Cloud.

How it works

  1. Test starts → Testcontainers connects to the Docker daemon.
  2. Image pulled (cached afterwards) and container started on a random port.
  3. Wait strategy confirms readiness.
  4. @ServiceConnection injects connection details into Spring.
  5. Migrations run; tests execute against the real service.
  6. Ryuk removes containers at the end.

Example

@SpringBootTest
@Testcontainers
class OrderIntegrationTest {

    @Container @ServiceConnection
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16-alpine");

    @Container @ServiceConnection
    static KafkaContainer kafka = new KafkaContainer("apache/kafka-native:3.8.0");

    @Autowired OrderService orders;
    @Autowired OrderRepository repo;

    @Test
    void persistsOrderWithJsonbAttributes() {
        orders.place(new PlaceOrder(7L, Map.of("gift", "true")));
        assertThat(repo.findByCustomerId(7L)).singleElement()
            .extracting(Order::attributes).isEqualTo(Map.of("gift", "true"));
    }
}

Common mistakes

  • Starting new containers for every test class, making the suite slow.
  • Using latest image tags instead of pinning the production version.
  • Hard-coding ports instead of reading the mapped port.
  • Forgetting that CI agents need Docker access.

How to answer in the interview

"Testcontainers is a library that starts real dependencies like PostgreSQL, Kafka or Redis in throwaway Docker containers during tests and cleans them up afterwards. Instead of H2 or mocks, I test against the same database engine and version as production, so I catch dialect differences, migration problems, constraints and broker configuration early. Each run is isolated and repeatable on any machine with Docker. The JUnit extension manages the lifecycle, and in Spring Boot I just annotate the container with ServiceConnection. To keep it fast I use singleton containers shared across tests and a cached Spring context."

Likely follow-up questions

  • How to keep a Testcontainers suite fast in CI? Singleton containers, cached images, one shared context, parallel forks.
  • Why not H2? Different SQL dialect and behaviour, so tests pass where production fails.
  • What is Ryuk? A helper container that deletes test containers when the session ends.
