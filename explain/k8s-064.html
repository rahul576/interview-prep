Deployments start failing with toomanyrequests errors when pulling public images. What is happening and how do you fix it?

Kubernetes · scenario · levels entry, mid, senior

In one line

toomanyrequests is the Docker Hub pull rate limit; nodes behind one NAT IP share the anonymous quota and exhaust it during scale-ups. Short-term, authenticate pulls and use IfNotPresent; properly, use a pull-through cache or mirror approved images into a private registry referenced by digest.

Detailed explanation

Docker Hub limits pulls for unauthenticated clients per source IP, and for free accounts per user, over a time window; paid plans have much higher limits. The exact numbers have changed over time, so check Docker's current policy rather than relying on memory. In a cluster, private nodes reach the internet through a NAT gateway, so dozens or hundreds of nodes appear as one IP. A normal day may stay under the limit, but a node pool scale-up, a cluster upgrade replacing all nodes, or a CI burst pulls the same images many times at once and hits it. Pods then fail with ErrImagePull / ImagePullBackOff and the message toomanyrequests.

Short-term fixes: authenticate to Docker Hub with an organisation account via imagePullSecrets (or node-level credentials), and make sure imagePullPolicy is IfNotPresent with immutable tags so nodes reuse cached images. Note that using :latest implies Always.

The real fix is to stop depending on Docker Hub at runtime. A pull-through cache (ECR pull-through cache rules, ACR cache rules, Artifact Registry remote repositories, Harbor proxy cache) fetches once and serves all nodes. Better still, copy approved base and third-party images into your private registry as part of a controlled process: scan them, sign them, version them, and reference them by digest. This also protects against upstream images being changed, deleted or compromised. Containerd can be configured with registry mirrors for docker.io so existing manifests still work.

How it works

  1. Confirm the error text in pod events.
  2. Add authenticated pulls to stop the immediate failures.
  3. Check imagePullPolicy and avoid latest.
  4. Create a pull-through cache or mirror in your cloud registry.
  5. Rewrite image references (or configure containerd mirrors).
  6. Add a policy that only allows approved registries.

Example

# ECR pull-through cache for Docker Hub
aws ecr create-pull-through-cache-rule --ecr-repository-prefix dockerhub \
  --upstream-registry-url registry-1.docker.io \
  --credential-arn arn:aws:secretsmanager:eu-west-1:111122223333:secret:ecr-pullthroughcache/dockerhub

# image reference becomes
# 111122223333.dkr.ecr.eu-west-1.amazonaws.com/dockerhub/library/nginx@sha256:...

Common mistakes

  • Using :latest everywhere, forcing pulls on every start.
  • Fixing only CI, not cluster nodes.
  • Relying on public images that can change underneath you.
  • Forgetting init containers and sidecars that also pull from Docker Hub.

How to answer in the interview

"toomanyrequests is Docker Hub's rate limit. In a cluster all nodes usually leave through one NAT gateway, so they share one IP and hit the anonymous limit fast, especially when many new nodes pull at once. Short-term I authenticate pulls with an organisation account and use IfNotPresent with immutable tags. The proper fix is not depending on Docker Hub at runtime: a pull-through cache in ECR, ACR or Harbor, or better, copying approved images into our private registry where they're scanned, signed and referenced by digest. That also protects us if an upstream image changes or disappears."

Likely follow-up questions

  • Why is latest risky beyond rate limits? Different nodes may run different code, rollbacks are impossible, and changes arrive unreviewed.
  • Pull-through cache vs mirroring? Cache is automatic and lazy; mirroring is controlled and lets you scan and approve first.
  • How do you enforce approved registries? An admission policy (Kyverno, Gatekeeper) rejecting other registries.
