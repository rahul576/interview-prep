How should you protect the AWS root account?

Cloud (AWS) · concept · levels entry

In one line

The root user has unrestricted access that IAM policies cannot limit, so protect it with a strong unique password, MFA (ideally phishing-resistant hardware keys), no access keys, a secured contact email, alerts on any root sign-in, and use it only for the few tasks that require it.

Detailed explanation

The email and password used to create an AWS account become the root user. It can close the account, change billing and support plans, delete any resource and restore IAM access, and identity-based IAM policies do not apply to it. In AWS Organizations, service control policies can restrict member account root users, but not the management account's root.

Protection combines strong authentication with rare use. Use a long unique password in a vault. Enable MFA (AWS now enforces it for root in most cases) and register at least two devices, preferably FIDO2 security keys or passkeys. Delete any root access keys. Put the root email on a protected company mailbox or distribution list, because whoever controls that email can reset the password.

Daily work goes through IAM Identity Center or federated least-privilege roles, with break-glass roles for emergencies. CloudTrail records root activity, an EventBridge rule on root sign-ins alerts the security team, and Security Hub flags missing root MFA.

In multi-account setups, centralised root access management in Organizations lets you remove member account root credentials entirely and run the few privileged root tasks centrally.

How it works

  1. Set a strong unique password and register multiple MFA devices.
  2. Remove all root access keys.
  3. Move the root email to a protected shared mailbox.
  4. Set up SSO and admin roles for daily work.
  5. Alert on any root login via CloudTrail and EventBridge.
  6. In Organizations, centralise root management and remove member root credentials.

Example

  "source": ["aws.signin"],

  "detail": { "userIdentity": { "type": ["Root"] } }
}

This EventBridge pattern sends an SNS alert to the security channel whenever the root user signs in. Typical root-only tasks: changing account settings such as the root email, closing the account, restoring a misconfigured S3 bucket policy that denies everyone, and certain billing and support plan changes.

Common mistakes

  • Using root for daily administration.
  • Root access keys in scripts or CI.
  • A single MFA device kept by one person who leaves.
  • Root email tied to a personal or ex-employee mailbox.
  • No alerting on root use.

How to answer in the interview

"Root has full access that IAM can't restrict, so I lock it down: a long unique password in a vault, MFA with more than one hardware key, no access keys, and the root email on a protected company mailbox. Root is only used for the few tasks that need it, like closing the account. Everything else goes through IAM Identity Center and least-privilege roles, and an EventBridge alert on CloudTrail notifies security of any root sign-in. In Organizations I'd centrally remove member account root credentials."

Likely follow-up questions

  • Which tasks need root? Changing root account settings, closing the account, restoring a locked-out bucket policy, some billing and support plan changes.
  • Can SCPs restrict root? Yes for member accounts, not for the management account.
  • What if root MFA is lost? Use the account recovery process through the root email and phone verification.
