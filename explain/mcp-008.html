What is the difference between a protocol error and a tool execution error in MCP, and why does it matter?

MCP Servers · concept · levels mid, senior

In one line

Protocol errors are JSON-RPC error responses for bad requests (unknown tool, invalid params) and are usually handled by the client; tool execution errors are normal results with isError: true that are shown to the model so it can self-correct, which only works with helpful, safe error text.

Detailed explanation

MCP distinguishes two failure categories because they need different handling.

Protocol errors concern the request itself: an unknown tool name, arguments that fail schema validation, a malformed message or a server crash while processing the protocol. They are returned as standard JSON-RPC error responses with codes such as -32601 (method not found) or -32602 (invalid params). The client typically handles them: logging, showing a technical error, or treating the server as faulty. They may never reach the model, so the model cannot learn from them.

Tool execution errors occur when the request was valid and the tool ran, but the operation failed: the downstream API returned 404, a rate limit was hit, a business rule was violated ("cannot cancel a shipped order"), or a date was in the wrong format for the backend. These are returned as a successful JSON-RPC response whose result has isError: true and content describing the problem.

The difference matters because execution errors go back into the model's context. A capable model reads "start_date must be YYYY-MM-DD; you sent 20/11/2026" and retries correctly, or reads "customer not found; use search_customers with a partial name" and calls the right tool. That self-correction loop makes agents far more robust, but only if the text is specific and actionable. Stack traces, SQL statements and internal hostnames waste tokens, rarely help the model, and leak internal details that an attacker could exploit via prompt injection.

How it works

  1. Client sends tools/call.
  2. Server checks tool exists and validates params; if not → JSON-RPC error.
  3. Server executes; on domain failure → result with isError: true and a clear message.
  4. Host passes execution errors to the model; protocol errors usually stay with the client.
  5. Model decides: retry with fixed input, call another tool, or explain to the user.

Example

{"jsonrpc":"2.0","id":3,"error":{"code":-32602,"message":"Invalid params: 'priority' must be one of low, medium, high"}}

{"jsonrpc":"2.0","id":4,"result":{
  "isError": true,
  "content":[{"type":"text","text":"Could not create ticket: project 'PAYMNT' does not exist. Valid projects: PAY, OPS, WEB. Retry with one of these."}]}}

Common mistakes

  • Throwing exceptions for business failures, turning them into opaque protocol errors.
  • Returning raw stack traces or SQL in error content.
  • Vague messages like "Error occurred" that give the model nothing to act on.
  • Marking failures with isError: false and hiding the problem in prose.

How to answer in the interview

"Protocol errors are JSON-RPC error responses for problems with the request itself, like an unknown tool or invalid arguments, and the client usually handles them; the model may never see them. Tool execution errors happen when the tool ran but the operation failed, like not found or a rate limit, and they come back as a normal result with isError true. That matters because execution errors are shown to the model, so it can self-correct: fix a date format or call a search tool first. That only works if the message is specific and actionable, not a stack trace, which would also leak internals."

Likely follow-up questions

  • Good error for a failed create_ticket? What failed, why, valid values or next step, and whether retrying makes sense.
  • Should schema validation failures be protocol errors? By the spec typically yes, though some SDKs return them as tool errors so the model can fix arguments.
  • How do you log errors? Full details in server logs with a correlation id; short safe text to the model.
