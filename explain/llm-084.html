What is context engineering, and why has it become a key LLM engineering skill?

LLMOps & RAG · concept · levels mid, senior

In one line

Context engineering is designing everything the model sees on each call (instructions, retrieved knowledge, memory, tool definitions and tool results) so it is relevant, well ordered and compact, because context quality now drives quality, cost and latency more than prompt wording.

Detailed explanation

Early LLM work focused on prompt engineering: finding the right phrasing for a single request. Modern applications are multi-step agents that call tools, retrieve documents and run for dozens of turns. In those systems the model's behaviour depends far more on what is in the context window at each step than on any one sentence of the prompt. Context engineering is the discipline of deciding that content deliberately.

The context has several components: system instructions, examples, retrieved knowledge from RAG, conversation history, longer-term memory, tool definitions and the results of earlier tool calls. Each competes for a finite budget. More is not better: models degrade when relevant facts are buried among irrelevant ones (sometimes called context rot or the lost-in-the-middle effect), and every token costs money and latency.

Good practice therefore focuses on relevance and ordering over quantity. Retrieve only chunks that help, and rerank them. Put stable content (instructions, tool definitions) first so prompt caching works. Compress or summarise long histories and verbose tool outputs, and drop stale information. Present data in clear structures such as tagged sections or JSON. In multi-agent systems, sub-agents get isolated, focused contexts for their subtask and return a short summary, rather than inheriting everything the orchestrator knows. And because these choices are subtle, they are validated with evaluations, cost and latency measurements, not intuition.

How it works

  1. Define what the model needs for this step: goal, constraints, relevant facts, available actions.
  2. Assemble a stable prefix: system prompt, tool definitions, examples (cacheable).
  3. Add dynamic content: retrieved and reranked chunks, relevant memory, recent turns.
  4. Compact: summarise older turns, trim tool outputs to essential fields, remove duplicates.
  5. For subtasks, spawn sub-agents with a fresh, minimal context and collect summaries.
  6. Measure with evals, token counts and latency; iterate.

Example

def build_context(task, history, user):
    return [
        system_prompt(version="agent-v7"),            # stable, cached
        tool_definitions(enabled_for(task)),          # only tools this task needs
        memory.lookup(user, task, k=5),               # durable facts and preferences
        rerank(retrieve(task.query, k=30))[:6],       # few, highly relevant chunks
        summarise(history[:-6]),                      # compressed older turns
        *history[-6:],                                # recent turns verbatim
    ]

Common mistakes

  • Stuffing the whole context window "because it fits", which hurts accuracy and cost.
  • Putting dynamic data before the system prompt, breaking prompt caching.
  • Returning raw, verbose tool output (full JSON, HTML) into the context.
  • Letting every sub-agent see the full conversation.
  • Changing context strategy without running evaluations.

How to answer in the interview

"Context engineering is deciding what goes into the model's context for every call. In agents, that matters more than prompt wording, because the context includes instructions, retrieved documents, history, memory, tool definitions and tool results, and they all compete for a limited budget. I aim for relevance rather than volume: retrieve and rerank a few good chunks, keep stable instructions first so caching works, summarise long histories and trim tool outputs, and give sub-agents isolated, focused contexts. Since every choice affects quality, cost and latency, I measure changes with evaluations rather than judging by feel."

Likely follow-up questions

  • How would you decide what an agent remembers between sessions? Store durable, user-confirmed facts and preferences with provenance and expiry, not raw transcripts.
  • Is a huge context window a replacement for RAG? No; long contexts cost more, are slower and still dilute attention.
  • How do you compress tool output? Return only needed fields, summarise server-side, or store full data and pass a reference.
