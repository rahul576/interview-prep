Why is data quality so important for AI systems, including LLM applications?

AI/ML & GenAI · concept · levels entry, mid

In one line

Models learn whatever is in their data, errors and biases included, so garbage in, garbage out: label quality caps supervised accuracy, RAG answers are only as good as the documents, and investing in cleaning, deduplication, ownership and governance often beats changing the model.

Detailed explanation

Machine learning extracts patterns from examples, and it cannot tell a real pattern from a data error. In supervised learning, wrong or inconsistent labels set a ceiling on accuracy: if annotators disagree 15 percent of the time, no model will reliably beat that agreement. Missing or under-represented groups lead to poor performance for those groups. Leakage, duplicates across train and test, and stale data create misleadingly good offline results.

The same applies to LLM applications. A RAG assistant retrieves and quotes your documents, so duplicates crowd out useful results, outdated versions produce wrong answers confidently, contradictory policies make answers inconsistent, and badly parsed PDFs (broken tables, headers mixed into text, scanned pages with no OCR) mean the right information never reaches the model. Missing metadata, such as owner, effective date and audience, prevents filtering. Even the best model cannot fix a knowledge base that is wrong. For fine-tuning, low-quality or inconsistent examples teach bad habits, and a few hundred excellent examples beat thousands of mediocre ones.

Successful AI teams therefore treat data as a product: clear ownership of each source, cleaning and deduplication, documentation (data sheets, lineage), automated quality checks in pipelines (schema, null rates, distributions, freshness), versioning, labelling guidelines with inter-annotator agreement checks, and governance of what data may be used (consent, personal data, licences). Monitoring in production catches upstream changes. In many projects, fixing data yields larger gains than switching to a bigger model.

How it works

  1. Inventory sources and assign owners.
  2. Profile data: duplicates, missing values, outdated or conflicting content.
  3. Clean, deduplicate and standardise; fix parsing of documents.
  4. Add quality checks and freshness monitoring to pipelines.
  5. Review labels and documents regularly; measure model impact of data fixes.

Example

# Near-duplicate and stale document check before indexing for RAG
import numpy as np
emb = embed([d.text for d in docs])
sim = emb @ emb.T
dupes = [(docs[i].id, docs[j].id) for i, j in zip(*np.where(np.triu(sim, 1) > 0.95))]
stale = [d.id for d in docs if (today - d.last_reviewed).days > 365]
print(len(dupes), "near-duplicate pairs;", len(stale), "docs not reviewed in a year")

Common mistakes

  • Swapping models repeatedly when the real issue is bad data.
  • Indexing every document version for RAG.
  • Ignoring label disagreement and annotation guidelines.
  • No owner for data sources, so nobody fixes problems.

How to answer in the interview

"Models learn whatever is in the data, including its errors and biases, so garbage in, garbage out. Inconsistent labels cap a classifier's accuracy and missing groups mean poor performance for them. With LLM apps it's the same: a RAG assistant is only as good as its documents, so duplicates, outdated versions, contradictions and badly parsed PDFs produce wrong answers even with the best model. So I invest in cleaning, deduplication, ownership, quality checks in pipelines and governance. Often improving data beats changing the model."

Likely follow-up questions

  • Finding contradictory documents before RAG? Cluster by topic with embeddings, then have an LLM or reviewer compare pairs for conflicting statements.
  • How do you measure label quality? Inter-annotator agreement and audits of disagreements.
  • What data quality checks run in pipelines? Schema, null rates, ranges, distribution shifts and freshness.
