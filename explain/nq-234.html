How would you design reliable communication between multiple downstream systems?

Microservices · design · levels senior, lead

In one line

Make communication reliable by using asynchronous durable messaging where possible, and for synchronous calls timeouts, retries with exponential backoff and jitter for idempotent operations, circuit breakers, bulkheads, fallbacks, plus idempotency, correlation ids, monitoring and contract tests.

Detailed explanation

Start by asking whether the caller really needs an immediate answer. Anything that can wait, such as notifying a CRM, updating search or sending invoices, should go through durable messaging (Kafka, RabbitMQ, SQS). The downstream system can be slow or down and simply catch up later. Use dead-letter queues for poison messages, with tooling to inspect and replay them, and publish via the outbox so events are never lost.

For calls that must be synchronous, protect yourself:

  • Timeouts on connect and read, set from the dependency's p99 and smaller than your own caller's deadline. Default client timeouts are often infinite.
  • Retries only for transient errors (timeouts, 503, connection resets) and only for idempotent or idempotency-keyed operations, with exponential backoff and jitter and a low maximum, at one layer only.
  • Circuit breakers open when error or slow-call rates exceed a threshold, failing fast instead of piling up threads.
  • Bulkheads: separate thread pools or semaphores per dependency, so one slow system cannot exhaust everything.
  • Fallbacks: cached data, defaults or a degraded feature.

Resilience4j provides all of these in Spring Boot. Every request and message carries a correlation id and trace context (OpenTelemetry) so failures can be followed across systems. Monitor latency, error rate, breaker state and consumer lag, with alerts. Finally, prevent integration breakage with consumer-driven contract tests (Pact or Spring Cloud Contract) in CI.

How it works

  1. Classify each integration: sync or async, critical or optional.
  2. Async: outbox, durable topic/queue, idempotent consumer, DLQ, replay.
  3. Sync: timeout, then retry with backoff, inside a circuit breaker and bulkhead.
  4. Provide fallbacks for optional data.
  5. Propagate correlation ids and traces; dashboard and alert.
  6. Contract tests guard API changes.

Example

resilience4j:
  circuitbreaker:
    instances:
      inventory:
        failureRateThreshold: 50
        slowCallDurationThreshold: 2s
        waitDurationInOpenState: 30s
  retry:
    instances:
      inventory:
        maxAttempts: 3
        waitDuration: 200ms
        enableExponentialBackoff: true
        enableRandomizedWait: true
  bulkhead:
    instances:
      inventory:
        maxConcurrentCalls: 20

Common mistakes

  • Retrying non-idempotent POSTs, causing duplicate payments.
  • Retries at the client, gateway and mesh at once (retry storms).
  • One shared pool for all downstream calls.
  • DLQs nobody monitors.

How to answer in the interview

"First I decide what really needs to be synchronous; anything that can wait goes through Kafka or a queue with an outbox, idempotent consumers and a dead-letter queue, so a slow system doesn't block us. For synchronous calls, every client has strict timeouts, retries only for transient errors on idempotent operations with exponential backoff and jitter, a circuit breaker to fail fast and a bulkhead per dependency, all with Resilience4j, plus fallbacks like cached data. Every call carries a correlation id, I monitor latency, errors and queue lag, and consumer-driven contract tests catch breaking changes before release."

Likely follow-up questions

  • Which operations would you never retry automatically? Non-idempotent ones without an idempotency key, like charging a card, and client errors such as 400 or 409.
  • Circuit breaker states? Closed, open (fail fast), half-open (trial calls).
  • How do you handle a DLQ? Alert, inspect the cause, fix, then replay messages idempotently.
