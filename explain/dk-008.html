How do you clean up unused containers, images, volumes and networks?

Docker · concept · levels entry

In one line

Remove specific items with docker rm / docker rmi, clean in bulk with docker container|image|volume|network|builder prune or docker system prune (add -a for all unused images, --volumes for volumes), check usage first with docker system df, and be careful: pruned volumes mean deleted data.

Detailed explanation

Docker hosts and CI agents accumulate junk quickly: exited containers, dangling images (untagged layers left behind when a tag moves to a new build), old tagged images, unused networks, orphaned volumes and, often the biggest, BuildKit build cache.

Targeted removal:

  • docker rm name removes a stopped container (-f stops and removes a running one; -v also removes its anonymous volumes).
  • docker rmi image:tag (or docker image rm) removes an image; it fails if a container still uses it.
  • docker volume rm name, docker network rm name.

Prune commands remove everything unused of one type:

  • docker container prune: all stopped containers.
  • docker image prune: dangling images only; -a removes every image not used by at least one container.
  • docker volume prune: unused volumes; in recent Docker versions only anonymous ones by default, with -a to include unused named volumes.
  • docker network prune, docker builder prune (build cache).
  • docker system prune: stopped containers, unused networks, dangling images and dangling build cache in one go; -a extends to all unused images and cache; --volumes adds volumes.

Most accept --filter "until=24h" or label filters, and -f to skip the confirmation prompt.

docker system df (and -v for detail) shows how much space images, containers, volumes and build cache use, and how much is reclaimable, so you know what to target.

Volumes deserve caution: they hold database files, uploads and state. A volume "unused" because its container is currently stopped will be deleted by prune, permanently. Back up first and prefer explicit docker volume rm.

How it works

  1. docker system df → see where space goes.
  2. Remove stopped containers so their images become unused.
  3. Prune images (dangling, or all unused with -a) and build cache.
  4. Review volumes explicitly before deleting.
  5. Automate safe pruning with age filters.

Example

docker system df
docker container prune -f
docker image prune -a -f --filter "until=168h"     # unused images older than 7 days
docker builder prune -f --keep-storage 20GB
docker volume ls -f dangling=true                  # review before deleting
docker system prune -f                             # safe default: no volumes

CI agent cron job:

0 3 * * * docker system prune -af --filter "until=48h" && docker builder prune -af --filter "until=48h"

Common mistakes

  • Running docker system prune -a --volumes -f on a server with stopped database containers.
  • Pruning only images while the build cache holds most of the space.
  • Never cleaning CI agents until builds fail with "no space left on device".

How to answer in the interview

"For individual items I use docker rm for containers and docker rmi for images. For bulk cleanup there are prune commands: container prune for stopped containers, image prune for dangling images, or with -a every image not used by a container, plus volume, network and builder prune. docker system prune does containers, networks, dangling images and build cache in one go; -a widens it to all unused images and --volumes includes volumes. I check docker system df first to see where space goes. I'm careful with volumes, because they hold data and pruning is permanent. On CI agents I schedule prune with an age filter."

Likely follow-up questions

  • Automate cleanup on CI agents? Scheduled prune with until filters, build cache limits, or ephemeral agents.
  • What is a dangling image? An untagged image, usually left after rebuilding a tag.
  • Why can't I remove an image? A container, even a stopped one, still references it.
