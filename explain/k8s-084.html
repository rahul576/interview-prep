Which recent Kubernetes changes from versions 1.33 to 1.36 matter most for operating clusters today?

Kubernetes · concept · levels mid, senior, lead

In one line

The changes that matter most: native sidecars (GA 1.33), Dynamic Resource Allocation (GA 1.34), in-place pod resize (GA 1.35), growing AI and batch features (pod-level resources, early gang scheduling), the retirement of community Ingress NGINX pushing teams to Gateway API, and removals such as cgroup v1 that must be planned before upgrading.

Detailed explanation

Native sidecar containers (GA in 1.33) are init containers with restartPolicy: Always. They start before the main containers and stay running, and they are terminated after the main containers. This fixes long-standing problems: meshes and log shippers starting too late, Jobs never completing because the sidecar kept running, and shutdown ordering.

Dynamic Resource Allocation (GA in 1.34) replaces "count of opaque devices" with ResourceClaims, DeviceClasses and ResourceSlices, selecting GPUs and other devices by attributes with CEL and allowing sharing. It is the foundation for modern GPU scheduling.

In-place pod resize (GA in 1.35) lets CPU and memory requests and limits change via the resize subresource without recreating the pod, subject to the container's resize policy. That makes VPA much less disruptive and helps start-up-heavy apps that need extra CPU only at boot.

For AI and batch: pod-level resources (a resource budget for the whole pod, beta in recent releases) and the first workload-aware / gang scheduling work in the scheduler, alongside ecosystem tools like Kueue and JobSet.

Networking: the Kubernetes community retired Ingress NGINX, with maintenance ending in March 2026, so clusters relying on it should migrate to a Gateway API implementation (Envoy Gateway, Istio, Cilium, cloud gateways, NGINX Gateway Fabric) or another supported controller. The Ingress API itself still exists, but Gateway API is where development happens.

Removals and deprecations: cgroup v1 support is deprecated and being removed from the kubelet, so nodes must run cgroup v2; the legacy Endpoints API is deprecated in favour of EndpointSlices; container runtime versions have support cut-offs. Before every upgrade, check release notes and deprecated APIs with tools such as kubent or pluto, and test on a non-production cluster. Always confirm details for your exact version in the official changelog, especially for 1.36.

How it works

  1. Read release notes and deprecation guide for each minor version.
  2. Scan manifests and Helm charts for deprecated APIs.
  3. Check node OS for cgroup v2 and runtime versions.
  4. Plan Ingress NGINX migration to Gateway API.
  5. Adopt native sidecars and in-place resize where they help.
  6. Pilot DRA for GPU workloads.

Example

# native sidecar: init container that keeps running
spec:
  initContainers:
    - name: log-shipper
      image: registry.example.com/fluent-bit:3
      restartPolicy: Always
  containers:
    - name: app
      image: registry.example.com/app:2.0
stat -fc %T /sys/fs/cgroup/        # cgroup2fs means cgroup v2
kubectl patch pod app-0 --subresource resize -p '{"spec":{"containers":[{"name":"app","resources":{"requests":{"cpu":"2"}}}]}}'

Common mistakes

  • Upgrading without checking deprecated APIs.
  • Old node images still on cgroup v1.
  • Staying on an unmaintained ingress controller.
  • Assuming every feature is enabled by default on managed services.

How to answer in the interview

"Several recent changes affect daily operations. Native sidecars went GA in 1.33, so meshes and log agents start before and stop after the app and Jobs complete properly. DRA went GA in 1.34, giving attribute-based GPU allocation. In-place pod resize went GA in 1.35, so CPU and memory can change without recreating pods, which makes VPA practical. Pod-level resources and early gang scheduling help AI workloads. The community Ingress NGINX project was retired in March 2026, so we're moving to Gateway API. And cgroup v1 is going away, so nodes must be on cgroup v2. Before each upgrade I check release notes and deprecated APIs."

Likely follow-up questions

  • What would you adopt first? Gateway API migration if on Ingress NGINX (security risk), then native sidecars, then in-place resize with VPA.
  • How do you find deprecated APIs? kubent, pluto, and API server deprecated-API request metrics.
  • Why does cgroup v2 matter? Better resource accounting, memory QoS and PSI, and v1 support is being removed.
