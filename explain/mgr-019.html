How would you modernise a ten-year-old Java monolith while the business keeps shipping features?

Leadership & Management · managerial · levels senior, lead

In one line

Modernise incrementally: understand the pain points and goals, build a safety net (characterisation tests, CI/CD, observability), upgrade the platform (supported Java LTS and Spring Boot), restructure into a modular monolith, extract services only where justified with the strangler fig, and agree a shared roadmap with product that shows value at each step.

Detailed explanation

A ten-year-old monolith usually still makes money, so the business cannot stop for a rewrite. Big-bang rewrites notoriously take longer than planned, chase a moving target and often fail. The interviewer wants a lead who modernises while shipping, reducing risk at each step.

Goals first: what hurts? Slow and risky releases, an unsupported Java 8 runtime with security issues, scaling limits, slow builds, difficulty hiring for old frameworks. The goals define what "modern" means and how you measure success (lead time, incident rate, build time, cost).

Safety net: before changing structure, add characterisation tests around critical behaviour, a reliable CI/CD pipeline with automated tests, and observability (metrics, logs, traces). This makes every later step safer.

Platform upgrade: moving to a supported Java LTS (21 or 25) and current Spring Boot 3.x (which requires the javax to jakarta namespace migration) is often the biggest quick win: security patches, performance, virtual threads, and easier hiring. Tools like OpenRewrite automate much of the migration. Containerise for consistent deployment.

Restructure: turn the "big ball of mud" into a modular monolith with explicit module boundaries aligned to business domains, enforced by Spring Modulith or ArchUnit tests. Untangle shared tables per module. Then extract services only where there is a clear reason (independent scaling, a different release cadence, team ownership), using the strangler fig pattern with a gateway routing traffic gradually.

Balance with the roadmap: agree with product a share of capacity, pair modernisation with features in the same area ("we are building the new pricing feature in the new module"), and show results regularly.

How it works

  1. Interview stakeholders; define goals and baseline metrics.
  2. Add characterisation tests, CI/CD and observability.
  3. Upgrade Java and Spring Boot incrementally with OpenRewrite.
  4. Define modules; enforce boundaries with tests.
  5. Extract one well-bounded module as a service if justified.
  6. Track metrics and report progress each quarter.

Example

<!-- OpenRewrite: automate the Spring Boot 3 / Jakarta / Java 21 migration -->
<plugin>
  <groupId>org.openrewrite.maven</groupId>
  <artifactId>rewrite-maven-plugin</artifactId>
  <version><!-- current release --></version>
  <configuration>
    <activeRecipes>
      <recipe>org.openrewrite.java.spring.boot3.UpgradeSpringBoot_3_5</recipe>
      <recipe>org.openrewrite.java.migrate.UpgradeToJava21</recipe>
    </activeRecipes>
  </configuration>
  <dependencies>
    <dependency>
      <groupId>org.openrewrite.recipe</groupId>
      <artifactId>rewrite-spring</artifactId>
      <version><!-- current release --></version>
    </dependency>
  </dependencies>
</plugin>
// ArchUnit/Spring Modulith-style boundary test
@Test
void modulesRespectBoundaries() {
    ApplicationModules.of(ShopApplication.class).verify();
}

Common mistakes

  • Proposing a full rewrite with a feature freeze.
  • Extracting microservices before adding tests and observability.
  • Staying on an unsupported Java version because "it works".
  • Splitting into services that still share one database.
  • Doing modernisation invisibly, without business buy-in.

How to answer in the interview

"I'd start by understanding the pain points and goals, slow releases, scaling limits, security or hiring, because they define what modernisation means. I'd avoid a big-bang rewrite. First a safety net: characterisation tests, a reliable CI/CD pipeline and observability. Then upgrade the platform to a supported Java LTS and current Spring Boot, using OpenRewrite to automate much of it, which is often the biggest quick win. Next I'd restructure into a modular monolith with enforced boundaries and extract services only where there's a strong reason, using the strangler fig. I'd agree a roadmap with product so modernisation ships alongside features and shows value at each step."

Likely follow-up questions

  • Which module to extract first? One with clear boundaries, few dependencies, and a real reason such as different scaling or release cadence.
  • How do you justify the cost? Baseline metrics like lead time, incidents and security exposure, with improvements reported each quarter.
  • No tests at all? Start with characterisation tests on the riskiest flows and test any code you touch.
