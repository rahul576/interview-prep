What is Amazon DynamoDB, and when would you use it?

Databases & SQL · concept · levels mid

In one line

Amazon DynamoDB is AWS's fully managed, serverless key-value and document database: tables keyed by a partition key (plus optional sort key) give single-digit millisecond latency at virtually any scale, with on-demand or provisioned capacity, GSIs/LSIs, Streams, TTL, global tables and transactions, best for known access patterns, not ad hoc queries.

Detailed explanation

Data model: a table holds items (up to 400 KB each) with attributes. The primary key is either a partition key alone or a partition key plus sort key. DynamoDB hashes the partition key to place data on internal partitions and scales them automatically. Items with the same partition key form an item collection sorted by sort key, so Query can fetch "all orders for customer 42 in November" efficiently with key conditions such as begins_with or BETWEEN.

Indexes: Global secondary indexes (GSIs) have their own partition and sort key, are eventually consistent and can be added any time. Local secondary indexes (LSIs) share the partition key with a different sort key, must be defined at table creation, and support strongly consistent reads.

Capacity: on-demand mode charges per request and scales instantly, good for unpredictable traffic; provisioned mode with auto scaling is cheaper for steady load.

Features: data replicated across three Availability Zones; eventually consistent reads by default with optional strongly consistent reads; ACID transactions (TransactWriteItems/TransactGetItems) over up to 100 items; DynamoDB Streams for change events (often triggering Lambda); TTL to expire items automatically; global tables for multi-region active-active replication.

When to use: high-scale workloads with well-known access patterns: sessions, shopping carts, user profiles, IoT and device state, leaderboards, idempotency keys, and serverless backends with Lambda and API Gateway. Avoid it for ad hoc querying, joins, complex reporting or analytics (export to S3 and query with Athena instead), or when access patterns are still unclear, because changing them later can require new indexes or data migration.

How it works

  1. List access patterns before designing the table.
  2. Choose partition and sort keys so each pattern is a GetItem or Query.
  3. Add GSIs for other patterns.
  4. Pick capacity mode and enable PITR, TTL and Streams as needed.
  5. Use conditional writes for optimistic concurrency and idempotency.
  6. Monitor throttling and hot keys with CloudWatch.

Example

// AWS SDK for Java v2 (enhanced client)
@DynamoDbBean
public class Order {
    private String pk;   // "CUSTOMER#42"
    private String sk;   // "ORDER#2026-11-21#991"
    private BigDecimal total;
    @DynamoDbPartitionKey public String getPk() { return pk; }
    @DynamoDbSortKey      public String getSk() { return sk; }
    // other getters/setters...
}

DynamoDbTable<Order> table = enhanced.table("shop", TableSchema.fromBean(Order.class));
PageIterable<Order> nov = table.query(QueryConditional.sortBeginsWith(
    Key.builder().partitionValue("CUSTOMER#42").sortValue("ORDER#2026-11").build()));

Common mistakes

  • Designing tables like relational schemas, then needing joins.
  • Low-cardinality or skewed partition keys causing throttling.
  • Using Scan with filters as a query mechanism.

How to answer in the interview

"DynamoDB is AWS's fully managed, serverless NoSQL database for key-value and document data. I define a table with a partition key and optionally a sort key, and DynamoDB distributes the data automatically, giving single-digit millisecond latency at virtually any scale, with on-demand or provisioned capacity. It replicates across availability zones, and offers global tables for multi-region, TTL for expiry, Streams for change events and ACID transactions over up to 100 items, with GSIs and LSIs for extra access patterns. I'd use it for high-scale workloads with known access patterns, like sessions, carts, IoT data or Lambda backends, and avoid it where I need ad hoc queries, joins or complex reporting."

Likely follow-up questions

  • What is single-table design? Storing multiple entity types in one table with generic keys so related items are fetched in one Query.
  • GSI vs LSI? GSI: any keys, added anytime, eventually consistent; LSI: same partition key, defined at creation, supports strong reads.
  • How do you prevent overwriting concurrent updates? Conditional writes with a version attribute.
