Design an in-memory rate limiter class for a single service instance.

Low-Level Design · design · levels mid, senior

In one line

Expose a tryAcquire(key) interface, implement a token bucket per key with time-based refill, store buckets in a ConcurrentHashMap via computeIfAbsent, make each bucket update thread-safe (synchronized or CAS), evict idle keys, and inject a clock for testing.

Detailed explanation

An in-memory limiter is appropriate for a single instance or as a local first line of defence. The API should be small and abstract: boolean tryAcquire(String key) (optionally with a permit count), so the implementation can switch to a sliding window or a Redis-backed version later.

Token bucket: each key has a capacity (max burst) and a refill rate (tokens per second). Instead of a background thread adding tokens, use lazy refill: on each call, compute elapsed time since the last refill, add elapsed * rate tokens capped at capacity, then consume one if at least one is available. This is O(1) per call and needs no timers.

Concurrency: the map is a ConcurrentHashMap, and computeIfAbsent ensures exactly one bucket per key even under races. Each bucket's refill-and-consume must be atomic: either synchronized on the bucket (simple and fast enough, as contention is per key) or pack state into an AtomicLong/AtomicReference and use a compare-and-set loop for a lock-free version.

Memory: keys like user IDs or IPs are unbounded, so idle buckets must be evicted, for example using a Caffeine cache with expireAfterAccess, or a periodic sweep. A full bucket that has been idle can be safely dropped because recreating it gives the same state.

Testability: inject a Clock or a LongSupplier for nanoTime so tests can advance time deterministically. Use System.nanoTime() (monotonic) rather than wall-clock time.

How it works

  1. tryAcquire(key) gets or creates the bucket.
  2. Lock the bucket (or CAS loop).
  3. now = clock.nanos(); tokens = min(capacity, tokens + (now - last) * ratePerNano); last = now.
  4. If tokens >= 1: decrement, return true; else return false.
  5. Cache evicts buckets not accessed for, say, 10 minutes.

Example

public interface RateLimiter { boolean tryAcquire(String key); }

public final class TokenBucketRateLimiter implements RateLimiter {
    private final double capacity, refillPerNano;
    private final LongSupplier nanoClock;
    private final Cache<String, Bucket> buckets = Caffeine.newBuilder()
            .expireAfterAccess(Duration.ofMinutes(10)).build();

    public TokenBucketRateLimiter(double capacity, double perSecond, LongSupplier nanoClock) {
        this.capacity = capacity; this.refillPerNano = perSecond / 1_000_000_000d; this.nanoClock = nanoClock;
    }

    @Override public boolean tryAcquire(String key) {
        return buckets.get(key, k -> new Bucket(capacity, nanoClock.getAsLong())).tryConsume();
    }

    private final class Bucket {
        private double tokens; private long last;
        Bucket(double tokens, long now) { this.tokens = tokens; this.last = now; }
        synchronized boolean tryConsume() {
            long now = nanoClock.getAsLong();
            tokens = Math.min(capacity, tokens + (now - last) * refillPerNano);
            last = now;
            if (tokens >= 1) { tokens -= 1; return true; }
            return false;
        }
    }
}
// Usage: new TokenBucketRateLimiter(20, 5, System::nanoTime)

Common mistakes

  • A global lock for all keys, serialising every request.
  • Check-then-act on the map (get then put) creating duplicate buckets.
  • A background refill thread per key.
  • Using System.currentTimeMillis(), which can jump backwards.
  • Unbounded maps that leak memory.

How to answer in the interview

"I'd define a RateLimiter interface with tryAcquire(key). The implementation is a token bucket per key with capacity and refill rate, refilled lazily: on each call I add tokens for the elapsed time, capped at capacity, then consume one if available. Buckets live in a ConcurrentHashMap or Caffeine cache created with computeIfAbsent, and each bucket's update is synchronized, or a CAS loop if I need lock-free. Idle keys expire after access, and I inject a nano clock so tests can control time."

Likely follow-up questions

  • Ten instances? Move state to Redis with an atomic Lua script, or split the limit per instance as an approximation.
  • Lock-free version? Encode tokens and timestamp in an immutable state object and update with AtomicReference.compareAndSet.
  • Why not Guava RateLimiter? It is per-limiter, blocking-oriented and not keyed; Bucket4j or Resilience4j fit better.
