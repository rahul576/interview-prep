What is the program counter (PC) register?

JVM & Performance · concept · levels mid

In one line

The program counter (PC) register is a small per-thread area that holds the address of the JVM bytecode instruction currently being executed, so the thread knows what to run next and can resume after a context switch; it is undefined during native methods and is the only runtime area with no OutOfMemoryError.

Detailed explanation

The JVM specification defines several runtime data areas; the PC register is the smallest. Every JVM thread has its own. At any moment a thread executes the code of exactly one method, its current method. If that method is a Java method, the PC register contains the address (in practice an index or pointer into the method's bytecode) of the instruction being executed. After each instruction it advances, or jumps for branches, loops, method calls, returns and exception handlers.

Why per thread? Many threads run concurrently and the OS scheduler constantly switches them on and off CPU cores. Each thread is at a different point in different methods. When a thread is paused and resumed, the JVM must know exactly where it stopped; a shared register would be overwritten by other threads. Per-thread PC registers, together with per-thread stacks, give each thread an independent execution context.

Native methods. When a thread executes a native method (C/C++ via JNI), the spec says the PC register value is undefined, because the code is not bytecode; the CPU's own instruction pointer tracks native execution.

No OutOfMemoryError. The register is tiny and fixed in size (large enough for a return address or native pointer), so it can never run out of memory. Every other runtime area (heap, stacks, method area, native stacks) has defined OOM or overflow conditions.

In HotSpot. The interpreter keeps the bytecode pointer (often called bcp) in a CPU register or frame slot; JIT-compiled code uses the hardware instruction pointer, and the JVM maps back to bytecode indexes for stack traces and deoptimisation. That mapping is why stack traces can show line numbers for compiled code.

How it works

  1. A thread is created with its own PC register.
  2. Calling a Java method sets the PC to the method's first instruction.
  3. Each executed instruction advances or jumps the PC.
  4. On a context switch, the thread's PC is preserved.
  5. On return, execution continues at the caller's saved position.
  6. During native methods the PC is undefined.

Example

javap -c Counter.class
public int next();
  Code:
     0: aload_0
     1: dup
     2: getfield      #7   // Field count:I
     5: iconst_1
     6: iadd
     7: putfield      #7
    10: aload_0
    11: getfield      #7
    14: ireturn

The numbers 0, 1, 2, 5... are bytecode offsets. A thread executing next() has its PC at one of them. If it is pre-empted after offset 6 and another thread runs next() concurrently, each thread still resumes from its own PC, which is also why count++ is not atomic.

Common mistakes

  • Confusing the JVM PC register with the CPU's hardware register.
  • Thinking it is shared among threads.
  • Claiming it can throw OutOfMemoryError.
  • Forgetting it is undefined for native methods.

How to answer in the interview

"The program counter register is a small per-thread memory area in the JVM. For a thread executing a Java method it holds the address of the bytecode instruction currently being executed, so the JVM knows what to run next and where to resume after the thread is switched out and back in by the scheduler. Each thread needs its own because threads run independently at different points in different methods. When the thread is executing a native method, the value is undefined. It's tiny and fixed in size, so it's the only runtime data area for which the specification defines no OutOfMemoryError."

Likely follow-up questions

  • Why must each thread have its own PC register? Threads execute independently and are pre-empted at arbitrary points; each must resume exactly where it stopped.
  • What does it hold during native code? Undefined; native execution uses the CPU instruction pointer.
  • How do stack traces get line numbers? Frames record bytecode indexes, mapped to lines via the class's line number table.
