Which basic Docker Compose commands do you use?

Docker · concept · levels entry

In one line

The everyday Compose commands are docker compose up -d, down (with -v to delete volumes), ps, logs -f, exec, build, pull, restart and up --scale.

Detailed explanation

Docker Compose manages a whole application of several containers described in compose.yaml. Modern Compose is the docker compose plugin (v2), written with a space, replacing the old Python docker-compose binary. All commands act on a project, named after the directory by default or set with -p.

docker compose up -d creates networks and volumes, builds images that are missing, and starts every service detached. Without -d you see all logs interleaved in the foreground, which is handy during development. up is also how you apply changes: it recreates only containers whose configuration or image changed. docker compose down stops and removes the containers and default network; down -v also removes named volumes, which deletes database data, so use it carefully. docker compose stop only stops containers and keeps them for a later start.

For inspection, ps shows state and health, logs -f api follows one service's logs (--tail 100 limits history), and exec db psql -U app runs a command inside a running container while run --rm api pytest starts a new one-off container. build rebuilds images, pull fetches newer image versions, restart api restarts one service, and up -d --scale worker=3 runs several replicas of a service that does not publish a fixed host port. config prints the fully merged configuration, which is great for debugging overrides, and watch can sync code changes in development.

How it works

  1. Compose reads compose.yaml plus overrides and .env.
  2. It computes the desired containers, networks and volumes for the project.
  3. It calls the Docker API to create or update what differs.
  4. Containers are labelled with the project and service name.
  5. Later commands find resources through these labels.

Example

docker compose up -d --build          # build and start everything
docker compose ps                     # state and health
docker compose logs -f --tail 100 api # follow one service
docker compose exec db psql -U app    # shell into running db
docker compose run --rm api pytest    # one-off container
docker compose up -d --scale worker=3
docker compose config                 # merged, resolved config
docker compose down                   # keep volumes

Common mistakes

  • Running down -v on a dev database and losing data unexpectedly.
  • Using exec when the service is not running (use run instead).
  • Scaling a service that publishes a fixed host port, causing port conflicts.
  • Still writing the obsolete version: key and docker-compose binary in new projects.

How to answer in the interview

"I start everything with docker compose up -d, which builds missing images and starts the services in the background; without -d I see the logs in the foreground. docker compose down stops and removes containers and networks, and -v also deletes the named volumes, so the data. For day-to-day work I use ps for status, logs -f for one service, exec to run a command inside a running container and run --rm for one-off tasks. build and pull refresh images, restart restarts a service, and up --scale worker=3 runs multiple instances. docker compose config shows the merged file when overrides confuse me."

Likely follow-up questions

  • Difference between stop and down? stop keeps containers; down removes containers and networks.
  • exec vs run? exec uses an existing container; run creates a new one.
  • How do you apply a config change? Run up -d again; Compose recreates only changed services.
