How does ConcurrentHashMap support concurrent updates?

Collections · concept · levels mid, senior

In one line

Since Java 8, ConcurrentHashMap does lock-free volatile reads, inserts into empty bins with CAS, locks only the head node of one bin for other writes, resizes cooperatively with helper threads, offers atomic compute/merge methods, forbids nulls, and tracks size with striped counters.

Detailed explanation

The map is a volatile Node[] table of bins. Each node's val and next are volatile, so a reader always sees a fully published node.

Reads. get computes the hash, reads the bin with a volatile array read (tabAt), and walks the chain or tree. No lock is taken, so reads never block, even while another thread writes to the same bin.

Writes to an empty bin. putVal tries casTabAt(table, i, null, newNode). If the CAS succeeds, the insert is done without any lock. If it fails, another thread got there first and the loop retries.

Writes to an occupied bin. The writer does synchronized (firstNode) and then appends, replaces or removes within that bin only. Threads writing to different bins proceed in parallel; with a good hash and many bins, contention is low. Like HashMap, long bins are converted into TreeBins (red-black trees).

Resizing. When the table needs to grow, a new table is allocated and bins are transferred in strides. A moved bin is marked with a ForwardingNode; readers follow it to the new table, and other writing threads that encounter it help transfer remaining bins, so resizing is spread across threads instead of stopping the world.

Atomic compound operations. putIfAbsent, computeIfAbsent, computeIfPresent, compute, merge and replace(k, old, new) run atomically per key, removing check-then-act races.

Size. Counts are kept in a baseCount plus CounterCell[] (LongAdder style) to avoid a single contended counter, so size() and mappingCount() are estimates during concurrent updates. Null keys and values are forbidden to keep get unambiguous.

How it works

  1. Hash → bin index.
  2. Bin empty → CAS insert.
  3. Bin is ForwardingNode → help resize, retry.
  4. Otherwise synchronized on head node → update chain/tree.
  5. Add to striped counter; maybe start a resize.

Example

ConcurrentHashMap<String, LongAdder> views = new ConcurrentHashMap<>();
views.computeIfAbsent(url, k -> new LongAdder()).increment();

ConcurrentHashMap<String, Integer> stock = new ConcurrentHashMap<>();
stock.merge("SKU-1", -1, Integer::sum);                 // atomic decrement
stock.computeIfPresent("SKU-1", (k, v) -> v <= 0 ? null : v); // remove at zero

long approx = stock.mappingCount();                     // estimate under load

Common mistakes

  • Using get then put instead of merge/compute.
  • Treating size() as exact during concurrent writes.
  • Long-running or re-entrant functions inside compute.
  • Trying to store null to mean "unknown".

How to answer in the interview

"Since Java 8 ConcurrentHashMap is a table of bins. Reads take no locks and rely on volatile reads, so they never block. A write to an empty bin uses compare-and-swap; a write to a non-empty bin synchronises only on that bin's first node, so threads updating different bins run in parallel. Long chains become trees. Resizing is incremental and other writers help move bins. Compound actions are atomic through putIfAbsent, computeIfAbsent, compute and merge, so I avoid check-then-act races. It forbids nulls, and size uses striped counters, so it's an estimate under concurrency."

Likely follow-up questions

  • Why no null values? get returning null must mean absent; otherwise you'd need a non-atomic containsKey.
  • Are iterators fail-fast? No, weakly consistent.
  • What are the bulk operations? forEach, search, reduce with a parallelism threshold.
