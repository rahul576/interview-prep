How do you manage Entra ID applications, service principals and their secrets with Terraform safely?

Terraform · concept · levels mid, senior

In one line

Use the azuread provider for app registrations, service principals, groups and role assignments, run it with a tightly controlled identity with Graph permissions, prefer federated identity credentials over secrets, and when secrets are unavoidable rotate them with overlap and store them in Key Vault, remembering they land in state.

Detailed explanation

The azuread provider manages Microsoft Entra ID objects: azuread_application, azuread_service_principal, groups and memberships, app roles and azuread_app_role_assignment. Because these objects live in the directory, not in a subscription, Azure RBAC roles like Owner do not help; the Terraform identity needs Microsoft Graph application permissions such as Application.ReadWrite.OwnedBy (only apps it owns) or a directory role like Application Administrator. These are powerful — an identity that can add credentials to apps can impersonate them — so that pipeline needs strict approvals, a separate state and limited people.

The best secret is no secret. Federated identity credentials (azuread_application_federated_identity_credential) let GitHub Actions, Azure DevOps, Kubernetes workload identity or another cloud exchange their own OIDC token for an Entra token, with no client secret to leak or rotate. Managed identities do the same for Azure-hosted workloads.

When a client secret is unavoidable (for example a third-party SaaS integration), create it with azuread_application_password and drive rotation with a time_rotating resource. Its ID goes in rotate_when_changed, so Terraform creates a new password when the period passes. To avoid outages, keep two overlapping passwords — create the new one before the old expires — and write the value to Key Vault where consumers read it. Since the secret value is stored in state, the backend must be encrypted and access-restricted.

How it works

  1. A dedicated pipeline identity with scoped Graph permissions runs the identity state.
  2. Terraform creates the application, service principal and owners.
  3. For CI/CD or workloads, add federated credentials matching the issuer and subject.
  4. For unavoidable secrets, create passwords with an end date and time_rotating.
  5. Store the secret in Key Vault; consumers read the latest version.
  6. Remove old passwords after consumers switch.

Example

resource "azuread_application" "api" {
  display_name = "orders-api"
  owners       = [data.azuread_client_config.current.object_id]
}

resource "azuread_service_principal" "api" {
  client_id = azuread_application.api.client_id
}

resource "azuread_application_federated_identity_credential" "gh" {
  application_id = azuread_application.api.id
  display_name   = "github-main"
  issuer         = "https://token.actions.githubusercontent.com"
  subject        = "repo:org/orders:ref:refs/heads/main"
  audiences      = ["api://AzureADTokenExchange"]
}

resource "time_rotating" "secret" { rotation_days = 90 }

resource "azuread_application_password" "partner" {
  application_id      = azuread_application.api.id
  rotate_when_changed = { rotation = time_rotating.secret.id }
}

Common mistakes

  • Giving the pipeline Global Administrator because Graph permissions are confusing.
  • Creating long-lived client secrets for GitHub Actions instead of federation.
  • Rotating by replacing the only secret, causing an outage until consumers update.
  • Leaving the state backend readable by many people while it contains secrets.

How to answer in the interview

"I use the azuread provider for applications, service principals, groups and app role assignments. The identity running it needs Microsoft Graph permissions like Application.ReadWrite.OwnedBy or Application Administrator, which are powerful, so that pipeline is tightly controlled. Wherever possible I avoid secrets with federated identity credentials, so GitHub Actions or Kubernetes workload identity authenticate without a client secret. If a secret is unavoidable, I create it with azuread_application_password, rotate it with time_rotating, keep an overlap window, and store it in Key Vault for consumers. Since the secret ends up in state, the state must be protected."

Likely follow-up questions

  • How do you avoid an outage on rotation? Keep two valid passwords, publish the new one to Key Vault, let consumers pick it up, then remove the old.
  • Why OwnedBy instead of ReadWrite.All? It limits the pipeline to applications it created.
  • Managed identity or app registration? Managed identity for Azure-hosted workloads; app registrations for external or multi-tenant use.
