Terraform plans in a large configuration take 20 minutes. How do you speed them up?

Infrastructure as Code · scenario · levels senior

In one line

Slow plans usually mean too many resources in one state, each refreshed with API calls that hit rate limits; the real fix is splitting the state, with short-term help from tuned -parallelism, removing slow data sources and the plugin cache, while -refresh=false and -target are emergency tools only.

Detailed explanation

During plan, Terraform first refreshes every resource in state: the provider calls the cloud API to read its current attributes. A configuration with 5,000 resources means at least 5,000 API calls, often several per resource. Cloud APIs throttle (AWS returns throttling errors, the provider backs off and retries), so the plan becomes a long queue of retries. Data sources that list many objects, large for_each expressions and slow backends add more time.

Diagnose first. TF_LOG=debug or trace with timestamps shows which resource types are slow and whether throttling occurs. Count resources with terraform state list | wc -l.

Structural fix: split the state. Break the configuration into components along ownership and change frequency (network, cluster, data stores, each service). Migration uses removed blocks (with destroy = false) in the old stack and import blocks in the new one, or state mv between state files, verified by clean plans on both sides. Smaller states also reduce blast radius and lock contention.

Short-term tuning.

  • -parallelism (default 10) can be raised if the API tolerates it; too high causes more throttling.
  • Replace expensive data sources (for example listing all AMIs or all subnets) with direct references or outputs.
  • Plugin cache (TF_PLUGIN_CACHE_DIR) and a provider mirror avoid downloading providers every run.

Use with care. -refresh=false skips reading real state, so the plan can miss drift and make wrong decisions. -target plans a subset but ignores dependencies outside it and leaves the state partially applied; Terraform itself warns it is for exceptional situations.

How it works

  1. Measure: resource count, time per type, throttling in logs.
  2. Quick wins: parallelism, data sources, plugin cache, runner location.
  3. Design the split into components with clear interfaces.
  4. Migrate with removed/import blocks; verify clean plans.
  5. Pipelines plan only components whose files changed.

Example

export TF_PLUGIN_CACHE_DIR="$HOME/.terraform.d/plugin-cache"
TF_LOG=debug terraform plan -parallelism=20 -out tfplan 2> plan.log
grep -c "Throttling" plan.log
terraform state list | cut -d. -f1-2 | sort | uniq -c | sort -rn | head

Common mistakes

  • Making -refresh=false or -target part of the normal pipeline.
  • Raising parallelism so far that throttling gets worse.
  • Splitting state without a plan for shared outputs.
  • Ignoring the root cause and buying faster runners.

How to answer in the interview

"Plan time grows with the number of resources, because Terraform refreshes each one with API calls and providers hit rate limits. A 20-minute plan almost always means the state is too big, so the real fix is splitting it into smaller components with clear ownership, migrating with removed and import blocks and checking for clean plans. Short-term I'd check logs for throttling, tune parallelism, replace data sources that list lots of objects, and use the plugin cache. Refresh false and target make plans faster but hide drift and dependencies, so they're only for emergencies."

Likely follow-up questions

  • Why is routine use of -target dangerous? It ignores dependencies outside the target and leaves the configuration only partially applied.
  • How big should a state be? No fixed number; small enough for fast plans and one owning team.
  • Does refresh-only help? It shows drift without proposing changes, not faster plans.
