How are resources released when a virtual thread completes execution?

Modern Java (11-21) · concept · levels senior, lead

In one line

When a virtual thread finishes, it is unmounted, its carrier returns to the scheduler, and the thread object, its heap-stored stack chunks and ThreadLocal values become garbage collected; your own resources (connections, files, locks, permits) still need try-with-resources or finally.

Detailed explanation

A virtual thread never owned an OS thread, so there is nothing to give back to the operating system. When its run method completes, normally or with an exception, the continuation terminates and the JVM unmounts it. The carrier thread is immediately free to mount the next runnable virtual thread from the ForkJoinPool queue.

What remains is plain heap memory: the Thread object, the stack chunk objects that held its frames while unmounted, and its ThreadLocal map. Once nothing references them (no one holds the Thread or a Future keeping the result), the garbage collector reclaims them like any other objects. That is why creating and finishing millions of virtual threads is cheap: there is no kernel call and no pool bookkeeping, just allocation and GC. One subtle benefit: because each task gets a fresh thread, ThreadLocal values do not leak into the next task, a classic bug with pooled platform threads.

The JVM does not know about application-level resources the code acquired:

  • JDBC connections borrowed from HikariCP must be closed to return to the pool.
  • Files, sockets and HTTP response bodies must be closed.
  • ReentrantLocks must be unlocked and semaphore permits released, or other threads block forever.
  • Spans, MDC entries and similar context should be cleaned up.

So the usual discipline applies: try-with-resources for AutoCloseables and finally for locks and permits. At the task-group level, an ExecutorService in try-with-resources waits for all its tasks; structured concurrency additionally cancels sibling tasks on failure so none are left running.

How it works

  1. Task returns or throws; uncaught exceptions go to the handler.
  2. Continuation ends; JVM unmounts the virtual thread.
  3. Carrier picks up the next virtual thread.
  4. Thread object, stack chunks and ThreadLocals become unreachable.
  5. GC reclaims memory; application resources were closed by your code.

Example

try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {
    for (long id : ids) {
        ex.submit(() -> {
            permits.acquire();
            try (Connection c = dataSource.getConnection();
                 PreparedStatement ps = c.prepareStatement("UPDATE orders SET synced = true WHERE id = ?")) {
                ps.setLong(1, id);
                ps.executeUpdate();
            } finally {
                permits.release();     // never leak a permit
            }
            return null;
        });
    }
}   // waits for all tasks

Common mistakes

  • Thinking the JVM closes connections or files when the thread ends.
  • Releasing locks or permits outside finally.
  • Holding references to finished threads or futures, delaying GC.
  • Relying on ThreadLocal cleanup instead of explicit resource handling.

How to answer in the interview

"When a virtual thread finishes, the JVM unmounts it and its carrier goes straight back to the scheduler to run other virtual threads; nothing goes back to the OS because no OS thread was created for it. The thread object and its stack chunks, which live on the heap, become unreachable and the garbage collector reclaims them along with its ThreadLocals. What the JVM doesn't release are my own resources, like database connections, files, locks or semaphore permits, so I still use try-with-resources and finally blocks. And an ExecutorService in try-with-resources waits for its tasks before closing."

Likely follow-up questions

  • Why are virtual threads cheap to create and destroy? They are heap objects with small growable stacks; no kernel calls or pooling.
  • What happens to an uncaught exception? It goes to the uncaught exception handler; with a Future it's wrapped in ExecutionException.
  • Do ThreadLocals leak with virtual threads? Not across tasks, since each task has a new thread, but they cost memory while it lives.
