An App Service or VM workload makes many outbound calls and starts failing with intermittent connection timeouts. You suspect SNAT port exhaustion. How do you confirm and fix it?

Azure · scenario · levels mid, senior, lead

In one line

Outbound internet connections from resources without their own public IP share a limited pool of SNAT ports; confirm exhaustion with SNAT metrics or App Service Diagnose and solve problems, then fix it with connection reuse (pooling, keep-alive), a NAT Gateway, and private endpoints so Azure service traffic skips SNAT.

Detailed explanation

Source NAT maps each outbound flow (private IP and port) to a public IP and a SNAT port. A port is consumed per unique destination IP and port, and after a connection closes it stays reserved for a while (TCP TIME_WAIT / idle timeout) before reuse. Load balancer outbound rules, default outbound access, and App Service multi-tenant workers all give each instance a pre-allocated, limited number of ports, often only a few hundred to around 1,000 depending on configuration. An app that opens a new connection per request to the same API quickly runs out; new connections then wait and time out, typically intermittently and under load, which is the classic symptom.

The application fix is usually the most important. In .NET, creating new HttpClient() per request opens a new socket each time and leaves sockets in TIME_WAIT; use IHttpClientFactory or a single static HttpClient with SocketsHttpHandler pooling. Database drivers should use connection pools, and HTTP keep-alive should be on.

Infrastructure fixes: a NAT Gateway on the subnet allocates ports dynamically on demand, with 64,512 ports per public IP and up to 16 public IPs (about one million ports). App Service can use it through VNet integration with outbound routing through the VNet. Private endpoints (or service endpoints) for SQL, Storage, Key Vault and others keep that traffic off SNAT entirely. Note that Azure is retiring default outbound access for new VNets, so an explicit outbound method is now best practice anyway.

How it works

  1. Check symptoms: intermittent timeouts to external endpoints, correlated with load.
  2. App Service: Diagnose and solve problems → "SNAT Port Exhaustion" detector.
  3. Load balancer: SNAT Connection Count (filter state = Failed) and Allocated/Used SNAT Ports metrics.
  4. Fix code: pooled clients, keep-alive, avoid per-request connections.
  5. Add NAT Gateway to the subnet; use private endpoints for Azure PaaS.
  6. Re-measure and alert on failed SNAT connections.

Example

// Bad: new socket per request
// using var client = new HttpClient();

// Good: pooled connections via IHttpClientFactory
builder.Services.AddHttpClient("payments", c =>
    c.BaseAddress = new Uri("https://api.payments.example"))
  .ConfigurePrimaryHttpMessageHandler(() => new SocketsHttpHandler {
      PooledConnectionLifetime = TimeSpan.FromMinutes(5),
      MaxConnectionsPerServer = 50 });

Common mistakes

  • Scaling out instead of fixing connection reuse (each instance still exhausts its own pool).
  • Assuming the issue is in the remote API because timeouts look like its fault.
  • Adding public IPs to the load balancer without understanding port allocation.
  • Leaving SQL and Storage traffic on public endpoints through SNAT.

How to answer in the interview

"Intermittent outbound timeouts under load make me suspect SNAT port exhaustion, because each instance only has a limited number of SNAT ports per destination. I'd confirm with the SNAT exhaustion detector in App Service or the failed SNAT connection metrics on the load balancer. The first fix is in code: reuse connections with pooling and keep-alive, for example IHttpClientFactory instead of a new HttpClient per call. Then I'd attach a NAT Gateway, which allocates ports dynamically with about 64,000 per public IP, and use private endpoints for Azure services so they don't use SNAT at all."

Likely follow-up questions

  • Why is a new HttpClient per request harmful? Each opens a new socket and SNAT port, and closed sockets linger in TIME_WAIT, so ports are not reused.
  • Does NAT Gateway work with a load balancer's outbound rules? NAT Gateway takes precedence for outbound from that subnet.
  • How do you get stable egress IPs for allow-listing? NAT Gateway public IPs or a firewall.
