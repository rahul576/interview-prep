How do you make agent behaviour reproducible enough to debug and test?

AI Agents & AIOps · concept · levels mid, senior

In one line

Make agents debuggable by recording full traces (inputs, model outputs, tool calls and results, versions), replaying runs with recorded tool results, pinning model, prompt and tool versions, using low temperature or seeds where appropriate, deterministic test fixtures, and statistical evaluation over multiple runs.

Detailed explanation

Agents are non-deterministic: sampling, model updates, changing tool data and timing all alter behaviour. Perfect determinism is impossible, but debugging and testing need enough repeatability to answer "why did it do that?" and "did my change fix it?".

Recording is the foundation. Each run stores a full trace: the user input, system prompt version, every model request and response including tool calls, every tool result, errors, timestamps, and the exact versions of model, prompts, tools and configuration. Without this, a production failure is just an anecdote.

Replay uses the recording. Feed the recorded tool results back instead of calling real systems, so you can re-run the agent up to the failing step, then test a changed prompt, tool description or model at exactly that point, without touching production. Some frameworks support forking from a checkpoint for this.

Pinning: production uses a specific dated model version rather than a moving alias, versioned prompts stored in source control or a prompt registry, and versioned tool schemas. Changes become deliberate releases.

Reducing variation: lower temperature for structured steps, and seeds where the provider supports them, reduce randomness, though most providers describe seeds as best-effort and some reasoning models do not expose temperature at all.

Deterministic environments: tests run against fixtures, a sandbox repository at a fixed commit, a seeded database, mocked APIs with fixed responses and a frozen clock.

Because some variance remains, evaluation is statistical: run each scenario several times, compare success rates and confidence intervals between versions, and look at failure clusters rather than single runs.

How it works

  1. Log every run with all inputs, outputs, tool results and versions.
  2. Store traces with a run ID, redacting sensitive data.
  3. To debug, replay with recorded tool results up to the failing step.
  4. Fork at that step with the changed prompt or model; compare.
  5. Pin versions in production; release changes deliberately.
  6. Evaluate changes with multiple runs on fixed fixtures.

Example

class ReplayTools:
    """Returns recorded tool results instead of calling real systems."""
    def __init__(self, trace):
        self.results = iter([s for s in trace["steps"] if s["type"] == "tool_result"])

    def __call__(self, name, args):
        step = next(self.results)
        assert step["tool"] == name, f"Diverged: expected {step['tool']}, got {name}"
        return step["result"]

trace = load_trace("run_2026-05-14_8f31")
agent = build_agent(model=trace["versions"]["model"], prompt=load_prompt("support", "v42"))
agent.run(trace["input"], tools=ReplayTools(trace), stop_at_step=7)

Common mistakes

  • Using a moving model alias in production.
  • Logging only final answers, so failures cannot be reconstructed.
  • Debugging against live systems whose data has since changed.
  • Concluding a fix works from one successful run.
  • Keeping full traces with personal data indefinitely.

How to answer in the interview

"Agents are non-deterministic, so I make them reproducible enough. Every run records a full trace: inputs, every model response, every tool call and result, and the versions of model, prompts and tools. With that I can replay a failed run, feeding back the recorded tool results, and test a changed prompt or model exactly at the failing step without touching real systems. Production pins model, prompt and tool versions. For structured steps I lower temperature and use seeds where supported. Tests run against deterministic fixtures like a sandbox repo or mocked APIs. Since some randomness remains, I evaluate statistically, running each scenario several times and comparing success rates."

Likely follow-up questions

  • Storing traces without keeping sensitive data forever? Redact at capture, encrypt, restrict access and apply short retention with longer retention for metadata.
  • What if the replay diverges? Divergence itself is informative; continue live in a sandbox from that point.
  • Seeds guarantee determinism? No, they are best-effort; infrastructure changes can still alter outputs.
