What is the difference between static and instance members, and when are static blocks executed?

Core Java & OOP · concept · levels entry, mid

In one line

Static members belong to the class (one shared copy), instance members belong to each object; static methods have no this and cannot directly use instance state; a static block runs once, when the class is initialised, typically on first active use.

Detailed explanation

Instance fields live in each object on the heap: two Order objects have their own id and total. Instance methods run in the context of an object, with this available.

Static fields exist once per class (per class loader), shared by all instances and accessible without creating an object: Order.count or constants like Math.PI (static final). Static methods belong to the class too. Because there is no object, they cannot access instance fields or call instance methods directly, nor use this or super; they can only work with parameters and static state. Static methods are not overridden; a subclass method with the same signature hides it, and the call is resolved at compile time by the reference type. Good uses: pure utility functions (Math.max, List.of), factory methods (Order.of(...)), and constants.

Static initialiser blocks (static { ... }) contain code that runs once when the class is initialised. Class initialisation is lazy: it happens on the first active use, such as creating an instance, calling a static method, reading a non-constant static field, or Class.forName. Static field initialisers and static blocks run in textual order. Referencing a compile-time constant (static final int MAX = 10) does not trigger initialisation because the value is inlined. If a static block throws, the class fails with ExceptionInInitializerError and later uses get NoClassDefFoundError. The JVM guarantees initialisation is thread-safe, which is the basis of the lazy holder idiom for singletons.

Design concerns: mutable static state is effectively a global variable. It is shared between all threads (needs synchronisation), survives across tests (order-dependent test failures), makes dependency injection and mocking hard, and can cause memory leaks in application servers that redeploy class loaders. Prefer instance members and injected singleton beans; keep static for constants and stateless helpers.

How it works

  1. Class loading: the class bytes are loaded and linked.
  2. Initialisation on first active use: static fields and static blocks run, top to bottom, once.
  3. Each new allocates instance fields, runs instance initialisers and the constructor.
  4. Static methods are invoked on the class (invokestatic), with no receiver.
  5. Instance methods are invoked on an object, with dynamic dispatch.

Example

public class Order {
    private static final Map<String, BigDecimal> TAX_RATES;   // one per class
    private static int created;                                // shared counter (not thread-safe)

    static {                                                   // runs once at class init
        TAX_RATES = Map.of("IN", new BigDecimal("0.18"), "UK", new BigDecimal("0.20"));
        System.out.println("Order class initialised");
    }

    private final String id;                                   // per object
    private final String country;

    public Order(String id, String country) {
        this.id = id; this.country = country; created++;
    }

    public BigDecimal taxRate() { return TAX_RATES.get(country); }   // instance uses static: OK

    public static int createdCount() {
        // return id.length();   // compile error: no instance in a static context
        return created;
    }
}

new Order("o1", "IN");   // prints "Order class initialised" (first use), then constructs
new Order("o2", "UK");   // static block does not run again

Common mistakes

  • Using mutable static fields as a cache or global state shared across threads.
  • Thinking static blocks run when the class file is compiled or at JVM start.
  • Calling static methods through instances, suggesting polymorphism that does not exist.
  • Heavy work or I/O in static blocks, causing hard-to-debug initialisation errors.

How to answer in the interview

"Static fields and methods belong to the class, so there's one shared copy no matter how many objects exist, while instance members belong to each object. Static methods can't access instance fields or use this directly, because there's no object. A static block runs once, when the class is initialised, which happens lazily on first active use, like creating an instance or calling a static method, and it's used to set up static state. I keep static for constants, factory methods and stateless utilities, because mutable static state hurts testability and thread safety."

Likely follow-up questions

  • In what order are static blocks, instance initialisers and constructors executed? Static initialisers once, superclass first, at class initialisation; then for each object: superclass constructor chain, instance field initialisers and instance blocks in textual order, then the constructor body.
  • Can a static method be overridden? No; a same-signature static method in a subclass hides it.
  • Is static class initialisation thread-safe? Yes; the JVM locks initialisation, which the holder idiom relies on.
