Explain Amazon ECS: clusters, task definitions, services, and Fargate versus EC2 launch types.

Cloud (AWS) · concept · levels mid

In one line

In ECS a task definition is the container blueprint, a task is a running copy, a service keeps a desired count of tasks healthy behind a load balancer, a cluster groups capacity, and the launch type or capacity provider decides whether that capacity is Fargate (serverless) or EC2 instances you manage.

Detailed explanation

A task definition is a versioned JSON document with one or more containers: image, CPU and memory, port mappings, environment variables, secrets from Secrets Manager or Parameter Store, logConfiguration (usually awslogs or FireLens), health checks, and the network mode (awsvpc gives each task its own ENI and IP). It also names two IAM roles: the task execution role, which ECS itself uses to pull the image from ECR, fetch secrets and write logs, and the task role, which the application code uses to call AWS services.

A task is one running instantiation. A service maintains the desired count, replaces failed or unhealthy tasks, spreads them across availability zones, registers them with an ALB or NLB target group, and runs deployments: rolling updates controlled by minimum healthy and maximum percent, with a deployment circuit breaker for automatic rollback, or blue/green through CodeDeploy. Service Auto Scaling adjusts the count from CloudWatch metrics. Standalone tasks suit batch jobs, often started by EventBridge.

A cluster is a logical boundary for tasks and their capacity. With Fargate, AWS provides isolated compute per task; you pay per vCPU and GB per second and never patch hosts. Fargate Spot cuts costs for interruptible work. With the EC2 launch type, tasks run on container instances in an Auto Scaling group with the ECS agent, managed through a capacity provider that scales the group. You manage AMIs and patching, but gain cheaper capacity at high utilisation, Savings Plans or Reserved Instances, GPUs, and special instance types. ECS Managed Instances is a newer middle option where AWS manages the EC2 hosts for you.

How it works

  1. Register a task definition revision referencing an ECR image.
  2. Create a service with a desired count, subnets, security groups and a target group.
  3. The scheduler places tasks on Fargate or EC2 capacity across AZs.
  4. Tasks pass health checks and are registered with the load balancer.
  5. A new revision triggers a rolling or blue/green deployment; failures roll back.

Example

{
  "family": "orders-api",
  "networkMode": "awsvpc",
  "requiresCompatibilities": ["FARGATE"],
  "cpu": "512", "memory": "1024",
  "executionRoleArn": "arn:aws:iam::111122223333:role/ecsTaskExecutionRole",
  "taskRoleArn": "arn:aws:iam::111122223333:role/orders-api-task",
  "containerDefinitions": [{
    "name": "api",
    "image": "111122223333.dkr.ecr.eu-west-1.amazonaws.com/orders-api:1.4.2",
    "portMappings": [{"containerPort": 8080}],
    "secrets": [{"name": "DB_PASSWORD",
      "valueFrom": "arn:aws:secretsmanager:eu-west-1:111122223333:secret:orders-db"}],
    "logConfiguration": {"logDriver": "awslogs", "options": {
      "awslogs-group": "/ecs/orders-api", "awslogs-region": "eu-west-1",
      "awslogs-stream-prefix": "api"}}
  }]
}

Common mistakes

  • Putting application permissions on the execution role instead of the task role.
  • Using the latest tag, so revisions do not identify what actually runs.
  • Forgetting a NAT gateway or VPC endpoints, so Fargate tasks in private subnets cannot pull images.
  • No circuit breaker, so a bad image loops forever during deployment.

How to answer in the interview

"A task definition describes the containers: image, CPU and memory, ports, environment and secrets, logging, plus the task role and execution role. A task is a running copy. A service keeps the desired count running across AZs, replaces failed tasks, registers them with a target group and handles rolling or blue/green deployments with rollback. The cluster is the logical group of capacity. With Fargate, AWS provides compute per task, so there are no instances to patch; with EC2, I run and patch the instances myself, which can be cheaper at scale and is needed for GPUs or special instance types."

Likely follow-up questions

  • Task role versus task execution role? The execution role is used by ECS to pull images, read secrets and ship logs; the task role is assumed by the application code.
  • How does ECS autoscale? Service Auto Scaling changes task count; capacity providers scale EC2 instances to fit.
  • Why awsvpc mode? Each task gets its own ENI, IP and security group, which Fargate requires.
