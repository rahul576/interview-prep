How do you use tags, naming conventions and resource locks in Azure governance?

Azure · concept · levels entry, mid, senior

In one line

Use a consistent naming convention (resource type, workload, environment, region, instance), tags for metadata like owner, cost centre and environment, enforce both through IaC and Azure Policy, and protect critical resources with CanNotDelete locks, using ReadOnly sparingly because it breaks normal operations.

Detailed explanation

Naming: names are often immutable and must be unique (some globally, like storage accounts), so define a pattern early. The Cloud Adoption Framework suggests a resource type abbreviation plus workload, environment, region and instance, for example rg-orders-prod-weu, app-orders-prod-weu-001, or stordersprodweu001 for storage, which allows no hyphens and has a 24-character limit. Good names tell you at a glance what something is, where it lives and which environment it belongs to.

Tags carry metadata names cannot: owner, costCenter, application, environment, dataClassification, criticality. They drive cost allocation in Cost Management, automation (shutdown schedules, backup tiers) and ownership during incidents. Tags are not inherited by default from resource groups or subscriptions (Cost Management can apply tag inheritance for cost reporting, but the resources themselves are not tagged), so you enforce them.

Enforcement: put naming and tagging in shared Terraform or Bicep modules, so teams get them by default, and back that with Azure Policy: deny resources missing required tags, modify to inherit costCenter from the resource group, and audit naming patterns.

Resource locks apply at subscription, resource group or resource scope and override RBAC, even for Owners. CanNotDelete allows reads and changes but blocks deletion: good for production databases, Terraform state storage, hub networking and Key Vaults. ReadOnly blocks all control-plane writes and some POST operations, which can break things: listing storage account keys, scaling an App Service plan, adding a VM to a backup policy or even some portal views. Locks also apply to the platform's own operations in some cases, so test them.

How it works

  1. Publish a naming and tagging standard (CAF-based).
  2. Implement it in IaC modules with variables for workload/env/region.
  3. Assign policies: required tags (deny), tag inheritance (modify), naming (audit).
  4. Remediate existing resources.
  5. Apply CanNotDelete locks on critical resources via IaC.
  6. Report on tag compliance and costs per tag.

Example

locals {
  name = "${var.workload}-${var.env}-${var.region_short}"
  tags = { owner = var.owner, costCenter = var.cost_center, environment = var.env }
}
resource "azurerm_storage_account" "state" {
  name = substr(replace("st${local.name}001", "-", ""), 0, 24)
  # ...
  tags = local.tags
}
resource "azurerm_management_lock" "state" {
  name       = "no-delete"
  scope      = azurerm_storage_account.state.id
  lock_level = "CanNotDelete"
}

Common mistakes

  • Assuming resources inherit resource group tags automatically.
  • ReadOnly locks on storage accounts, breaking key listing and apps.
  • Free-text tag values (Prod, production, PRD) ruining reports.
  • Locks that block Terraform destroy in pipelines with no documented process.

How to answer in the interview

"I follow a Cloud Adoption Framework style naming convention with type, workload, environment, region and instance, and use tags for owner, cost centre, environment and data classification, which drive cost reports and automation. Both are built into our IaC modules and enforced with Azure Policy, deny for missing required tags and modify to inherit tags from the resource group. Critical resources like production databases and state storage get CanNotDelete locks. I'm careful with ReadOnly locks because they block operations like listing storage keys or scaling."

Likely follow-up questions

  • Why enforce tag inheritance by policy? Resources don't inherit tags; without policy, reports miss them.
  • Can locks stop an Owner? Yes, until the lock is removed, which itself is audited.
  • Allowed tag values? Use policy parameters with allowed lists.
