What is KRaft, and why did Kafka remove ZooKeeper?

Kafka · concept · levels mid, senior

In one line

KRaft is Kafka's built-in Raft-based metadata quorum: controller nodes store cluster metadata in an internal log, replacing ZooKeeper, which was removed entirely in Kafka 4.0, giving simpler operations, faster failover and more partitions.

Detailed explanation

Before KRaft, Kafka depended on Apache ZooKeeper to store metadata (topics, partitions, ISR, configs, ACLs) and to elect a single controller broker. That meant running and securing a second distributed system, and the controller had to load the full state from ZooKeeper on failover, which could take minutes on clusters with hundreds of thousands of partitions. Metadata propagation to brokers was also slow and a source of subtle inconsistency.

With KRaft (Kafka Raft), a small quorum of controllers (usually 3 or 5) runs a Raft protocol over an internal __cluster_metadata log. One controller is the active leader; the others are hot standbys with the full state already in memory, so failover is near-instant. Brokers replicate the metadata log like any other topic and apply changes as events, which scales to millions of partitions far better than ZooKeeper watches. Nodes can run in dedicated controller mode (recommended for production) or combined mode for small or dev clusters.

Timeline: KRaft became production-ready in 3.3, ZooKeeper mode was deprecated in 3.5, 3.9 is the last 3.x release that supports ZooKeeper and the migration, and Kafka 4.0 (March 2025) removed ZooKeeper completely. Existing ZooKeeper clusters must first migrate to KRaft on a 3.x bridge release (ideally 3.9), using the dual-write migration mode, and only then upgrade to 4.x.

How it works

  1. Format storage with a cluster ID: kafka-storage.sh format.
  2. Controllers form a Raft quorum and elect an active controller.
  3. Metadata changes are appended to __cluster_metadata and committed by majority.
  4. Brokers fetch and apply metadata deltas.
  5. If the active controller dies, a standby wins the election and continues.

Example

# dedicated controller
process.roles=controller
node.id=1
controller.quorum.bootstrap.servers=c1:9093,c2:9093,c3:9093
controller.listener.names=CONTROLLER
# broker
process.roles=broker
node.id=101
kafka-metadata-quorum.sh --bootstrap-server b1:9092 describe --status

Common mistakes

  • Running an even number of controllers.
  • Using combined mode for large production clusters.
  • Trying to upgrade a ZooKeeper cluster directly to 4.0.
  • Forgetting tools that still talk to ZooKeeper (old scripts, --zookeeper flags).

How to answer in the interview

"KRaft is Kafka's own consensus layer based on Raft. A quorum of controller nodes keeps cluster metadata in an internal metadata log instead of ZooKeeper, and brokers replicate that log. Kafka 4.0 removed ZooKeeper entirely. The benefits are one system to run and secure, near-instant controller failover because standbys already hold the state, faster startup and support for far more partitions. For an existing cluster you migrate to KRaft on a 3.x bridge release like 3.9 before upgrading to 4."

Likely follow-up questions

  • How many controllers? Three tolerates one failure; five tolerates two for large or critical clusters.
  • Dedicated or combined mode? Dedicated in production to isolate metadata from data load.
  • What does the migration look like? Controllers in migration mode dual-write to ZooKeeper, brokers roll over, then ZooKeeper is removed.
