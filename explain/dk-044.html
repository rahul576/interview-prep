What are distroless and scratch images, and when would you use them?

Docker · concept · levels mid

In one line

Distroless images contain only the application runtime (plus CA certificates and timezone data) with no shell or package manager; scratch is a completely empty base suited to static binaries such as Go or Rust; both cut the attack surface but make debugging harder.

Detailed explanation

Traditional base images carry a whole operating system userland: shell, coreutils, package manager and hundreds of libraries. The application uses only a fraction, but every package is a potential CVE to triage and a tool an attacker can use after a compromise.

Distroless images, maintained by Google (gcr.io/distroless/...) and similar projects such as Chainguard images, strip this down to what a runtime needs: glibc, ca-certificates, tzdata, /etc/passwd entries for a nonroot user, and optionally a language runtime (Java, Python, Node.js). There is no shell and no package manager, so docker exec sh fails, shell-form CMD is impossible, and scanner reports shrink dramatically.

scratch is the special empty image; FROM scratch starts with nothing at all. It fits statically linked binaries, typically Go built with CGO_ENABLED=0 or Rust with musl. The final image is just the binary, often under 20 MB. You must add anything the binary needs yourself: CA certificates for HTTPS, timezone data if it uses local times, a non-root user entry, and writable directories.

The trade-off is debuggability. Without a shell you cannot inspect files or run curl inside the container. Remedies are the :debug variants of distroless images (which add BusyBox), running a debug container sharing the target's namespaces (docker run --pid container:x --network container:x), or Kubernetes ephemeral containers with kubectl debug. Observability through logs and metrics becomes more important.

How it works

  1. Build the app in a full SDK stage.
  2. Copy the binary or artifact into distroless or scratch.
  3. Copy required support files (certificates, tzdata) for scratch.
  4. Run as a non-root numeric user with exec-form ENTRYPOINT.
  5. Debug through debug variants or ephemeral containers.

Example

FROM golang:1.23 AS build
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 go build -o /app ./cmd/server

FROM scratch
COPY --from=build /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
COPY --from=build /usr/share/zoneinfo /usr/share/zoneinfo
COPY --from=build /app /app
USER 65532:65532
ENTRYPOINT ["/app"]
kubectl debug -it pod/api-7d9 --image=busybox:1.36 --target=api

Common mistakes

  • Forgetting CA certificates in scratch, causing "x509: certificate signed by unknown authority".
  • Using shell-form CMD or entrypoint scripts with distroless.
  • Building Go with CGO enabled and then failing on scratch due to missing libc.
  • Assuming no shell means no vulnerabilities; runtimes and app dependencies still need scanning.

How to answer in the interview

"Distroless images contain only what the application needs at runtime, like a JRE or Python runtime, CA certificates and timezone data, but no shell, package manager or utilities. scratch is the empty image, which works for statically linked binaries such as Go or Rust, so the final image is just the binary. Both give a tiny attack surface and far fewer CVEs, and an attacker has no shell to use. The trade-off is debugging: I can't exec into a shell, so I use the debug variants with BusyBox or Kubernetes ephemeral debug containers."

Likely follow-up questions

  • What files might a scratch Go service still need? CA certificates, tzdata, passwd entry, writable temp dir.
  • Can you run shell scripts in distroless? No, unless using a debug variant.
  • Distroless vs Alpine? Alpine has a shell and apk; distroless has neither.
