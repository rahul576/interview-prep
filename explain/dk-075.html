How do you debug a container that has no shell or tools inside (distroless)?

Docker · concept · levels senior

In one line

When a distroless or scratch container has no shell, bring the tools to it instead of putting them in the image: use a :debug image variant temporarily, attach a debug container that shares its namespaces (--pid/--network container:<name>), use kubectl debug ephemeral containers in Kubernetes, and inspect from outside with logs, docker inspect, docker cp and exit codes.

Detailed explanation

Distroless images (for example gcr.io/distroless/java21-debian12) and scratch images contain only the application and its runtime libraries: no shell, no package manager, no curl. That is good for security and size, but docker exec -it app sh simply fails with "executable file not found".

The key idea is that a container is just a process in a set of Linux namespaces. Another container can join those namespaces. With --pid container:app the debug container sees the target's processes; with --network container:app it shares its network stack, so localhost:8080 is the app itself and ss, tcpdump and curl see exactly its traffic. Images like nicolaka/netshoot or busybox provide the toolbox. Through /proc/<pid>/root in a shared PID namespace you can even browse the target's filesystem (with sufficient privileges).

In Kubernetes, kubectl debug adds an ephemeral container to a running pod without restarting it; --target shares the process namespace of a specific container. It can also copy a pod with a different image, or start a debug pod on a node.

Many problems need no shell at all: docker logs, docker inspect (exit code, OOMKilled flag, env, mounts), docker cp to pull files out, and docker diff. Distroless also publishes :debug tags with a busybox shell, useful in test environments only.

How it works

  1. Check the basics: docker logs, docker inspect --format '{{.State.ExitCode}} {{.State.OOMKilled}}'.
  2. Start a toolbox container joining the target's PID and network namespaces.
  3. Inspect processes, connections, DNS and the filesystem via /proc/1/root.
  4. In Kubernetes, use kubectl debug -it pod --image=busybox --target=app.
  5. Copy files out with docker cp or kubectl cp (the latter needs tar in the container, so prefer the debug container).

Example

docker run --rm -it --pid container:orders --network container:orders \
  --cap-add SYS_PTRACE nicolaka/netshoot
# inside: ps aux; ss -tlnp; curl -s localhost:8080/actuator/health; ls /proc/1/root/app

kubectl debug -it orders-7d9f-abc12 --image=nicolaka/netshoot --target=orders
docker cp orders:/app/config/application.yaml ./application.yaml

Common mistakes

  • Adding bash and curl to the production image "just in case".
  • Deploying :debug tags to production and forgetting them.
  • Forgetting --target with kubectl debug, so the process list is not visible.
  • Ignoring the cheap clues: exit code 137 usually means OOM kill or SIGKILL.

How to answer in the interview

"Distroless images have no shell, so instead of adding tools to the image I bring a toolbox to the container. With Docker I start a debug container like netshoot that joins the target's PID and network namespaces, so I can see its processes, its listening ports and test localhost exactly as the app sees it, and browse its filesystem through /proc/1/root. In Kubernetes I use kubectl debug to add an ephemeral container with --target. Before that I check logs, exit codes and docker inspect for OOM kills, and I can docker cp files out. Distroless :debug variants exist, but only for test environments."

Likely follow-up questions

  • How do you inspect the filesystem of a running distroless container? Shared PID namespace plus /proc/<pid>/root, docker cp, or docker export.
  • Do ephemeral containers restart the pod? No; they are added to the running pod and cannot be removed until the pod is deleted.
  • What does exit code 137 mean? Killed by SIGKILL (128 + 9), often the OOM killer.
