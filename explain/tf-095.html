What does the message Objects have changed outside of Terraform mean in a plan?

Terraform · concept · levels mid, senior

In one line

"Objects have changed outside of Terraform" means the refresh found differences between state and the real objects; it is informational drift reporting, and what matters is whether the proposed changes will revert any of it.

Detailed explanation

Before computing a plan, Terraform refreshes: it reads every managed object from the provider APIs and compares it with the last recorded state. If attributes differ, the plan output shows a section titled "Note: Objects have changed outside of Terraform" listing those differences, followed by the normal "Terraform will perform the following actions" section.

The note itself changes nothing. It explains why the plan might contain actions, and it also shows drift that will not cause actions. Many entries are harmless: computed attributes the platform updates on its own (timestamps, etags, latest versions), tags added by Azure Policy or AWS Config, autoscaler-managed counts, or default values the API fills in after creation.

The important question is what the proposed changes section does with that drift. If someone scaled an instance group in the console from 3 to 6, the note shows 6, and the plan proposes setting it back to 3. Applying would silently undo that person's change — possibly a hot-fix during an incident.

So I treat the section as a review aid. For unexpected drift I find out who changed what (activity logs, CloudTrail) and decide: codify it by updating the configuration, revert it by applying, or ignore it with lifecycle { ignore_changes } if another system legitimately owns that attribute. To accept legitimate changes into state without changing infrastructure, terraform apply -refresh-only records the current real values.

How it works

  1. terraform plan refreshes all resources from the provider.
  2. Differences from state are listed under "Objects have changed outside of Terraform".
  3. Terraform compares the refreshed state with the configuration.
  4. Actions needed to match configuration appear in the proposed changes.
  5. You decide to codify, revert, ignore or accept with -refresh-only.

Example

Note: Objects have changed outside of Terraform

  # azurerm_linux_web_app.api has changed
  ~ resource "azurerm_linux_web_app" "api" {
      ~ tags = {
          + "CostCenter" = "1234"    # added by Azure Policy
        }
    }

Terraform will perform the following actions:
  # azurerm_linux_web_app.api will be updated in-place
  ~ tags = {
      - "CostCenter" = "1234" -> null
    }
lifecycle {
  ignore_changes = [tags["CostCenter"]]
}

Common mistakes

  • Ignoring the section entirely and reverting someone's emergency fix.
  • Assuming the note means Terraform will change those objects.
  • Running apply -refresh-only without reviewing what is being accepted.
  • Overusing ignore_changes so real drift is hidden.

How to answer in the interview

"During refresh Terraform compares its state with what the APIs return. When something differs, the plan shows 'objects have changed outside of Terraform' before the proposed changes. It's informational — it explains detected drift, which may or may not lead to actions. Many entries are harmless, like computed values or tags added by policy. The key is whether the proposed changes will revert any of it, for example scaling back a value someone changed by hand. I investigate unexpected drift, codify or revert it, use ignore_changes for attributes another system owns, and use a refresh-only apply to accept legitimate changes."

Likely follow-up questions

  • How can you reduce harmless noise? ignore_changes for externally managed attributes, and set defaults explicitly in code.
  • How do you detect drift regularly? A scheduled plan with -detailed-exitcode that alerts on exit code 2.
  • What is -refresh=false? Skips refresh for speed; risky because plans are based on stale state.
