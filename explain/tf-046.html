Terraform wants to destroy a subnet, but the destroy fails because something is still using it. How do you handle destroy ordering problems?

Terraform · scenario · levels mid, senior

In one line

A destroy fails when something Terraform does not know about still uses the resource, such as NICs or load balancers created by Kubernetes, or when a dependency is missing from the graph; clean up external objects first and express ordering with references or depends_on.

Detailed explanation

Terraform destroys resources in reverse dependency order: dependents first, then the things they depend on. That works only if the graph is complete and Terraform owns everything attached. Two situations break it.

External objects. Kubernetes creates cloud resources on its own: a Service of type LoadBalancer creates a load balancer rule and frontend IP in the subnet, persistent volumes create disks, ingress controllers create application gateways or ALBs. Other teams may also have attached VMs, private endpoints or NICs. Terraform has never heard of them, so when it tries to delete the subnet, the cloud API refuses with "InUseSubnetCannotBeDeleted" or "DependencyViolation". Deleting the cluster before its services also orphans those load balancers, which then block the subnet forever.

Missing graph edges. If the AKS cluster uses a route table attached to its subnet, but the code never references the association, Terraform may delete the route or NSG association while the cluster still needs it, or try to destroy them in parallel. Implicit references create edges; when the relationship is not visible in arguments, depends_on adds it.

Investigation is straightforward: read the error message, which usually names the blocking resource ID, and look it up in the portal or CLI. Then decide whether it should be cleaned up first, imported into Terraform, or moved to a separate state that is destroyed earlier.

How it works

  1. Destroy runs in reverse dependency order.
  2. The API rejects deletion because an unknown object is attached.
  3. Identify the blocker from the error and the cloud console.
  4. Remove external objects first: Kubernetes services, Helm releases, PVCs.
  5. Add references or depends_on so Terraform orders the rest correctly.
  6. Re-run destroy and verify nothing remains.

Example

# Teardown script for an ephemeral environment
kubectl delete svc --all-namespaces --field-selector spec.type=LoadBalancer
helm uninstall ingress-nginx -n ingress
kubectl delete pvc --all -A
terraform destroy -auto-approve
resource "azurerm_kubernetes_cluster" "main" {
  # ...
  depends_on = [azurerm_subnet_route_table_association.aks]
}

Common mistakes

  • Destroying the cluster before Kubernetes-managed load balancers, leaving orphans.
  • Manually deleting random resources until destroy passes, without understanding why.
  • Overusing depends_on instead of real attribute references.
  • Mixing resources managed by Kubernetes or another team into the same subnet without documenting it.

How to answer in the interview

"Destroy fails when something Terraform doesn't know about is still attached, typically network interfaces or load balancers that Kubernetes created for LoadBalancer services, or resources from another team. The other cause is a missing dependency in the graph, so Terraform deletes things in the wrong order. I read the error, which names the blocking object, and find it in the console. Then I clean up external objects first, such as deleting services or uninstalling Helm releases before destroying the cluster, and add references or depends_on so the order is correct next time."

Likely follow-up questions

  • How do you make teardown reliable in automation? A pre-destroy step that removes Kubernetes-managed resources, then destroy, then a tag-based sweeper for leftovers.
  • Why not import the Kubernetes load balancer? Kubernetes would keep changing it; ownership would conflict.
  • What about deletion locks? Locks or prevent_destroy also block destroy and must be removed deliberately.
