What is the difference between an S3 bucket policy, an IAM policy and an ACL?

Cloud (AWS) · concept · levels entry

In one line

An IAM policy attaches to an identity and says what it can do; a bucket policy is a resource-based policy on the bucket with a Principal, able to grant cross-account or service access and enforce rules; ACLs are a legacy mechanism, disabled by default with Bucket owner enforced; access needs an Allow and no explicit Deny, and Block Public Access overrides public grants.

Detailed explanation

S3 access can be granted from two directions. An IAM policy (identity-based) is attached to a user, group or role: "this role may s3:GetObject on reports-bucket/*". It is the natural way to give your own workloads and people access, and it has no Principal because the principal is whoever holds the policy.

A bucket policy (resource-based) is attached to the bucket and includes a Principal: another AWS account, a specific role, a service such as CloudFront (with a condition on the distribution ARN), or *. It is used for cross-account access, for service access, and for bucket-wide guardrails applying to every caller, such as denying requests that are not over TLS (aws:SecureTransport = false), requiring a specific KMS key, or restricting access to a VPC endpoint (aws:SourceVpce).

ACLs (access control lists) are the original S3 permission system, granting coarse read/write to accounts or groups per bucket or object. Since April 2023, new buckets default to Object Ownership = Bucket owner enforced, which disables ACLs entirely so the bucket owner owns every object and access is controlled only by policies. AWS recommends keeping ACLs disabled.

Evaluation: within the same account, an Allow in either the IAM policy or the bucket policy is enough. Cross-account, both sides must allow: the caller's IAM policy and the bucket policy. An explicit Deny anywhere wins. Block Public Access, at account and bucket level, overrides any policy or ACL that would make data public, and it is enabled by default for new buckets.

How it works

  1. A request arrives for s3:GetObject on an object.
  2. S3 checks Block Public Access for public grants.
  3. It evaluates SCPs, identity policies, bucket policy (and ACLs if enabled).
  4. Explicit Deny: rejected.
  5. Same account: one Allow suffices; cross-account: both sides must Allow.

Example

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowAnalyticsAccountRead",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::222222222222:role/analytics-reader" },
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": ["arn:aws:s3:::reports-bucket", "arn:aws:s3:::reports-bucket/*"]
    },
    {
      "Sid": "DenyInsecureTransport",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": ["arn:aws:s3:::reports-bucket", "arn:aws:s3:::reports-bucket/*"],
      "Condition": { "Bool": { "aws:SecureTransport": "false" } }
    }
  ]
}

The analytics account must also give analytics-reader an IAM policy allowing those actions.

Common mistakes

  • Re-enabling ACLs for new designs.
  • Granting cross-account access in the bucket policy only, forgetting the caller's IAM policy.
  • "Principal": "*" without conditions.
  • Disabling Block Public Access to "fix" an access problem.

How to answer in the interview

"An IAM policy is attached to an identity and says what that user or role can do in S3. A bucket policy is a resource-based policy on the bucket itself, with a Principal, so it can grant access to other accounts or services like CloudFront and enforce rules for everyone, such as requiring HTTPS or a particular KMS key. ACLs are the legacy mechanism; new buckets use Bucket owner enforced, which disables them, and that's what I'd keep. A request succeeds when something allows it and nothing explicitly denies it, cross-account needs both sides to allow, and Block Public Access overrides public grants."

Likely follow-up questions

  • Grant another account read access to one bucket? Bucket policy allowing their role, plus an IAM policy in their account; KMS key policy too if SSE-KMS.
  • Why disable ACLs? Simpler, policy-only access and the bucket owner owns all objects.
  • How do you find publicly accessible buckets? IAM Access Analyzer for S3 and Security Hub checks.
