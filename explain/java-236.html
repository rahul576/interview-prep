What are the pitfalls of Collectors.toMap and how do you handle duplicates?

Java 8+ Features · concept · levels mid, senior

In one line

Collectors.toMap throws IllegalStateException on duplicate keys unless you provide a merge function, throws NullPointerException for null values, and returns an unordered HashMap unless you pass a map supplier; use groupingBy when several values per key are expected.

Detailed explanation

The two-argument form toMap(keyMapper, valueMapper) assumes keys are unique. As soon as two elements produce the same key, it fails with IllegalStateException: Duplicate key ... (attempted merging values ...). This often passes tests with small data and breaks in production. The fix is the three-argument form with a BinaryOperator merge function that decides what to do: keep the first (a, b) -> a, keep the latest (a, b) -> b, keep the max by some field, or combine like Integer::sum or BigDecimal::add.

Null values are a second trap. toMap accumulates via Map.merge semantics (and the unique-key accumulator explicitly checks for null), so a value mapper that returns null throws NullPointerException, even though HashMap itself allows null values. Filter nulls out first, map them to a sentinel or Optional, or collect with a manual collect(HashMap::new, (m, e) -> m.put(...), Map::putAll).

Ordering: the default result is a HashMap with no ordering guarantee. The four-argument overload adds a map supplier: LinkedHashMap::new keeps encounter order, TreeMap::new sorts by key, EnumMap for enum keys. For unmodifiable results use Collectors.toUnmodifiableMap (also rejects nulls). For concurrent collection in parallel streams there is toConcurrentMap.

If a key naturally has several values, toMap with a merge function is the wrong tool; groupingBy with a downstream collector expresses the intent better.

How it works

  1. For each element, compute key and value.
  2. If the key is absent, put the value (null check first).
  3. If present, call the merge function or throw if none was supplied.
  4. The map supplier determines the concrete map type.

Example

// Fails if a customer has two orders:
// Map<String, Order> m = orders.stream().collect(toMap(Order::customerId, o -> o));

// Latest order per customer
Map<String, Order> latest = orders.stream().collect(Collectors.toMap(
    Order::customerId,
    Function.identity(),
    BinaryOperator.maxBy(Comparator.comparing(Order::createdAt)),
    LinkedHashMap::new));

// Total value per customer
Map<String, BigDecimal> totals = orders.stream().collect(
    Collectors.toMap(Order::customerId, Order::total, BigDecimal::add, TreeMap::new));

// Multiple values per key: use groupingBy
Map<String, List<Order>> byCustomer = orders.stream()
    .collect(Collectors.groupingBy(Order::customerId));

Common mistakes

  • Omitting the merge function on data that can contain duplicates.
  • Value mappers that may return null (e.g. an optional email field).
  • Relying on iteration order of the default HashMap.
  • Using (a, b) -> a silently when duplicates indicate a data bug that should fail loudly.

How to answer in the interview

"toMap throws IllegalStateException on duplicate keys unless I pass a merge function, such as keeping the first, the latest, or summing values. It also throws NullPointerException if the value mapper returns null, even though HashMap allows nulls, because of how it merges. The default result is a HashMap with no order, so I use the four-argument overload with LinkedHashMap or TreeMap when order matters. If several values per key are expected, groupingBy is the better collector."

Likely follow-up questions

  • How would you build a map from customer id to their latest order? toMap with BinaryOperator.maxBy(comparing(Order::createdAt)).
  • What does toUnmodifiableMap do differently? Returns an unmodifiable map and rejects null keys and values.
  • When would you use toConcurrentMap? For unordered parallel streams to avoid merging partial maps.
