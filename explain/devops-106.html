What is the difference between immutable artifact promotion and rebuilding per environment?

CI/CD Tools · concept · levels mid, senior

In one line

Immutable artifact promotion means build once and move the exact same artifact, identified by version or digest, through dev, staging and production, injecting configuration per environment; rebuilding per environment risks shipping a binary that was never tested.

Detailed explanation

In the rebuild model, each environment gets its own build. Even from the same commit the output can differ: a dependency range resolves to a newer version, the base image node:22 changed overnight, or a build flag differs. Production then runs an artifact that never passed your tests, and debugging is harder because you cannot be sure which bits are running.

In the promotion model, the pipeline builds once, typically on merge to main, producing an immutable artifact such as a container image or JAR. It gets a never-reused tag such as the commit SHA, and for images the digest (sha256:...), a content hash that is truly immutable. The artifact goes to dev, then staging, then production; "promotion" just changes which version each environment points to, often via a commit to a GitOps repository.

This requires separating configuration from the build (twelve-factor style): URLs, flags and credentials come from environment variables, ConfigMaps, Secrets or a parameter store at deploy or run time. Benefits: test results really apply to production, rollback means redeploying the previous digest, audits trace exactly which build is where, and signatures (for example Sigstore cosign) and SBOMs attach to one artifact.

How it works

  1. CI builds the artifact once from a commit.
  2. It is tagged with an immutable identifier (SHA, version) and pushed; registry tag immutability is enabled.
  3. The artifact is signed and scanned, and its digest is recorded.
  4. Deploy to dev with dev config; run tests.
  5. Promote the same digest to staging, then production, changing only config.
  6. Rollback redeploys a previous digest.

Example

# GitOps: environments reference the same image digest
# envs/staging/values.yaml
image:
  repository: 123456789012.dkr.ecr.eu-west-1.amazonaws.com/orders
  digest: sha256:4f1c9a7e...   # built once from commit 9f2e1ab
config:
  DB_HOST: orders-staging.internal

# envs/prod/values.yaml  (promotion = copy the digest)
image:
  repository: 123456789012.dkr.ecr.eu-west-1.amazonaws.com/orders
  digest: sha256:4f1c9a7e...
config:
  DB_HOST: orders-prod.internal

Comparison

Promote one artifactRebuild per environment
What reaches prodExactly what was testedA new, untested build
Drift riskNone from the buildDependencies, base images, tools
RollbackRedeploy previous digestRebuild old code, hope it matches
ConfigInjected at deploy/run timeOften baked in

Common mistakes

  • Using mutable tags such as latest or staging, so the "same tag" is not the same image.
  • Baking environment URLs or secrets into the image.
  • Separate branches per environment, each rebuilt independently.

How to answer in the interview

"I build once and promote. The pipeline builds one container image, tags it with the commit SHA and records its digest. That exact digest goes to dev, staging and production; only configuration changes, injected through environment variables, ConfigMaps or a secrets store. Rebuilding per environment lets dependencies or base images drift, so production runs something that never passed tests. With immutable digests, rollback is redeploying the previous digest and auditing is trivial."

Likely follow-up questions

  • Why avoid latest in production? It is mutable and unpredictable, so you cannot know or reproduce what runs, and rollback is unclear.
  • How do you handle environment-specific frontend config? Load it at runtime from a config endpoint or injected file instead of build-time variables.
  • Where do promotion approvals happen? In the CD tool or as a reviewed pull request to the GitOps repo for the production environment.
