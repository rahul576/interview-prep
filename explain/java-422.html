Design a chat application like WhatsApp for one-to-one and group messaging.

System Design · design · levels senior, lead

In one line

A WhatsApp-style chat keeps persistent WebSocket connections to gateway servers, tracks presence (which gateway holds which user), assigns per-conversation sequence numbers, stores messages in a write-optimised store partitioned by conversation, routes via a broker, and handles offline delivery, push notifications, receipts and idempotent sends.

Detailed explanation

Connections: each client keeps a long-lived WebSocket (or MQTT, which WhatsApp historically used a variant of) to a gateway/connection server. A single tuned server can hold hundreds of thousands of connections, so the fleet holds millions. A presence/session service (Redis) maps userId -> gatewayId and tracks last seen.

Sending: the client sends a message with a client-generated message ID. The chat service checks membership, assigns a monotonic sequence number per conversation (ordering is only needed within a conversation, not globally), persists it, and acks to the sender (single tick). Persist before ack so nothing acknowledged is lost.

Storage: a write-heavy, append-mostly workload suits Cassandra/ScyllaDB or HBase, with partition key = conversation ID and clustering by sequence, so fetching recent messages of a chat is one partition scan. Large group partitions may be bucketed by time.

Routing: the service publishes to a broker (Kafka, or a direct gateway-to-gateway RPC using the presence map). The recipient's gateway pushes the message over its socket. If the recipient is offline, the message waits in storage (per-user inbox of undelivered message IDs) and a push notification goes through APNs/FCM; on reconnect, the client syncs from its last received sequence number.

Receipts: delivered and read receipts are small messages flowing back the same path. Groups fan out per member (small groups) with a members list cached. Media is uploaded to object storage via presigned URLs, and only a reference is sent. With end-to-end encryption (Signal protocol), the server only stores ciphertext.

How it works

  1. Client connects via WebSocket, authenticates, presence registers its gateway.
  2. Sender submits {clientMsgId, convId, body}.
  3. Service dedupes on clientMsgId, assigns seq, writes to Cassandra, acks the sender.
  4. Lookup recipient gateways; deliver, or enqueue offline and send push.
  5. Recipient acks delivery -> delivered receipt to sender; later read receipt.
  6. On reconnect, client requests messages with seq > lastSeen per conversation.

Example

CREATE TABLE messages (
  conversation_id uuid,
  bucket          int,          -- e.g. month, keeps partitions bounded
  seq             bigint,
  message_id      uuid,         -- client-generated, for idempotency
  sender_id       uuid,
  body            blob,         -- ciphertext if E2E encrypted
  sent_at         timestamp,
  PRIMARY KEY ((conversation_id, bucket), seq)
) WITH CLUSTERING ORDER BY (seq DESC);

Common mistakes

  • Using HTTP polling instead of persistent connections.
  • Global ordering with timestamps from client clocks.
  • Acking the sender before the message is durably stored.
  • No client message ID, so retries create duplicates.
  • Sending media bytes through the chat servers.

How to answer in the interview

"Clients keep WebSocket connections to gateway servers, and a presence service in Redis records which gateway each user is on. When a message arrives, the chat service dedupes on the client message ID, assigns a sequence number per conversation, stores it in Cassandra partitioned by conversation, and acks the sender. It's routed via a broker to the recipient's gateway; if they're offline it waits in storage and we send a push through APNs or FCM, and the client syncs from its last sequence on reconnect. Receipts flow back the same way, groups fan out per member, and media goes to object storage."

Likely follow-up questions

  • End-to-end encryption? Signal protocol: keys on devices, server stores ciphertext and distributes public key bundles; groups use sender keys.
  • Multi-device? Each device has its own connection and encryption session; fan out per device.
  • Large groups of 1,000? Fan out asynchronously, cache membership, or use fan-out-on-read for very large channels.
