How does systemd manage services? How do you troubleshoot a service that will not start?

Linux · concept · levels entry, mid

In one line

systemd runs services from unit files that define the command, user, environment, dependencies and restart policy; you manage them with systemctl and troubleshoot with systemctl status and journalctl -u, checking permissions, ports, config syntax and dependencies.

Detailed explanation

systemd is PID 1 on almost every modern distribution. A service unit (/etc/systemd/system/myapp.service) describes what to run in ExecStart, as which User and Group, with which Environment or EnvironmentFile, in which WorkingDirectory, and how to recover: Restart=on-failure with RestartSec. Ordering and dependencies are separate concepts: After= only orders startup, while Requires= or Wants= pull another unit in. After=network-online.target plus Wants=network-online.target is the usual way to wait for networking. The [Install] section with WantedBy=multi-user.target lets systemctl enable start it at boot.

systemd also places each service in its own cgroup, so it tracks every child process and can apply limits such as MemoryMax= and CPUQuota=, and hardening options like ProtectSystem=strict, NoNewPrivileges=yes and PrivateTmp=yes.

When a service will not start, systemctl status myapp shows the state (failed, activating, auto-restart), the exit code and the last log lines. journalctl -u myapp -b gives full logs for this boot, and -f follows them. Common causes: the binary or config is not readable by the service user, the port is already in use (ss -tulpn), a config syntax error (many apps have a -t test flag, like nginx -t), a missing EnvironmentFile, wrong Type= (for example forking for a process that does not fork), or a dependency such as a database not being ready. After editing a unit, run systemctl daemon-reload; if restarts hit the start limit, systemctl reset-failed clears it.

How it works

  1. systemd reads unit files and builds a dependency graph.
  2. systemctl start launches ExecStart in a dedicated cgroup.
  3. stdout and stderr go to the journal.
  4. On exit, the Restart= policy decides whether to restart.
  5. enable links the unit into a target for boot.

Example

# /etc/systemd/system/orders.service
[Unit]
Description=Orders API
Wants=network-online.target
After=network-online.target

[Service]
User=orders
EnvironmentFile=/etc/orders/env
ExecStart=/opt/orders/bin/orders --config /etc/orders/config.yaml
Restart=on-failure
RestartSec=5
MemoryMax=1G

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload && sudo systemctl enable --now orders
systemctl status orders
journalctl -u orders -b --no-pager | tail -50

Common mistakes

  • Forgetting daemon-reload after editing a unit.
  • Thinking After= also creates a dependency.
  • Testing the command as root while the service runs as another user.
  • Editing vendor units in /usr/lib instead of using systemctl edit drop-ins.

How to answer in the interview

"systemd manages services through unit files that describe the command, user, environment, dependencies such as After and Requires, and restart policies like Restart on-failure. I use systemctl start, stop and enable, and systemctl status for the state and recent logs. To troubleshoot, journalctl -u with the service name shows the full logs. Typical causes are file permissions for the service user, a port already in use, a config syntax error, a missing environment file or a dependency not ready. After editing a unit I run daemon-reload. systemd also gives each service a cgroup, so I can set limits."

Likely follow-up questions

  • How would you limit a service's memory? Set MemoryMax= in the unit or a drop-in; systemd enforces it with cgroups.
  • What is a drop-in? An override file created by systemctl edit that changes settings without editing the original unit.
  • What are systemd timers? A cron alternative with journal logging and dependency support.
