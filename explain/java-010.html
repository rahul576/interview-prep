How does ConcurrentHashMap differ from Hashtable or Collections.synchronizedMap?

Collections · concept · levels mid, senior

In one line

Hashtable and Collections.synchronizedMap guard every call with one lock for the whole map, while ConcurrentHashMap uses CAS and per-bin locking, non-blocking reads, weakly consistent iterators and atomic compound operations, and it rejects null keys and values.

Detailed explanation

Hashtable is a legacy class whose methods are all synchronized. Collections.synchronizedMap(map) wraps any map and synchronises every method on a single mutex. In both cases only one thread can touch the map at a time, so under contention threads queue up and throughput collapses. Worse, iterating still requires the caller to hold the lock manually, otherwise you can get ConcurrentModificationException.

ConcurrentHashMap was designed for concurrency. In Java 7 it used segments (lock striping). Since Java 8, a write to an empty bin uses a compare-and-swap, and a write to an occupied bin synchronises only on the first node of that bin. Threads writing to different bins proceed in parallel, and reads take no lock at all, relying on volatile reads. Resizing is incremental and other writers help transfer bins.

Its iterators are weakly consistent: they never throw ConcurrentModificationException and may or may not reflect updates made during iteration. It forbids null keys and values, because in a concurrent map get returning null must unambiguously mean "absent". Most importantly it offers atomic compound operations such as putIfAbsent, computeIfAbsent, compute and merge, which make check-then-act logic safe.

How it works

  1. get reads the volatile table and bin without locking.
  2. put into an empty bin: CAS the new node in.
  3. put into an occupied bin: synchronized on the head node only.
  4. Long bins become trees, like HashMap.
  5. size() uses striped counters, so it is an estimate under concurrent updates.

Example

ConcurrentMap<String, LongAdder> hits = new ConcurrentHashMap<>();

void record(String page) {
    hits.computeIfAbsent(page, k -> new LongAdder()).increment(); // atomic
}

// Unsafe check-then-act, even on ConcurrentHashMap:
// if (!map.containsKey(k)) map.put(k, v);

Common mistakes

  • Thinking containsKey followed by put is atomic because the map is concurrent.
  • Using synchronizedMap and iterating without holding its lock.
  • Relying on size() as an exact value during heavy writes.
  • Doing slow work inside computeIfAbsent, which holds the bin lock.

How to answer in the interview

"Hashtable and synchronizedMap put a single lock around the whole map, so only one thread works at a time and contention kills throughput. ConcurrentHashMap since Java 8 uses CAS for empty bins and locks only the head node of a bin, so writers to different bins run in parallel and readers never block. Its iterators are weakly consistent and don't throw ConcurrentModificationException. It rejects nulls to avoid ambiguity, and it gives atomic operations like computeIfAbsent and merge, which is what I use instead of check-then-act."

Likely follow-up questions

  • Is containsKey then put safe? No, it is a race; use putIfAbsent or computeIfAbsent.
  • Why no nulls? You couldn't distinguish "absent" from "mapped to null" between two calls.
  • How did Java 7 differ? It used 16 segments, each with its own ReentrantLock.
