How would you design a backend API that supports 10,000 concurrent users?

System Design · design · levels senior, lead

In one line

10,000 concurrent users is about not holding resources per user: stateless services scaled horizontally behind a load balancer, deliberately sized thread and connection pools (or virtual threads), caching and read replicas to protect the database, queues for heavy work, plus rate limiting, load testing, autoscaling and observability.

Detailed explanation

First translate "10,000 concurrent users" into requests per second. If each active user makes a request every 10 seconds, that is about 1,000 RPS; with 100 ms average latency, Little's Law (concurrency = throughput x latency) gives about 100 requests in flight. That is modest; the danger is slow dependencies that stretch latency and multiply in-flight work.

Stateless services: no in-memory sessions; use JWTs or a session store in Redis, so any instance can serve any request. Run several replicas across zones behind a load balancer, with Kubernetes HPA autoscaling on CPU or RPS.

Threading and pools: classic Spring MVC uses a Tomcat thread per request (default max 200). For I/O-heavy endpoints, Java 21 virtual threads (spring.threads.virtual.enabled=true in Spring Boot 3.2+) remove the thread bottleneck, or use WebFlux. But the database connection pool (HikariCP) is the real limit: size it per instance so that instances x poolSize stays below what the database can handle. Set timeouts on every outbound call.

Database protection: it is usually the bottleneck. Add proper indexes, keep transactions short, use caching (Caffeine locally, Redis shared) for hot reads, read replicas for read-heavy traffic, and pagination everywhere.

Async work: reports, emails and exports go to a queue (Kafka, RabbitMQ, SQS) processed by workers, so requests return quickly.

Protection and proof: rate limiting per user, circuit breakers on dependencies, a CDN for static assets. Validate with load tests (Gatling, k6, JMeter) at 2-3x expected peak, and monitor p95/p99 latency, error rate, saturation, pool usage.

How it works

  1. Estimate RPS and in-flight requests with Little's Law.
  2. Make services stateless; deploy 3+ replicas with autoscaling.
  3. Configure Tomcat/virtual threads, Hikari pool and timeouts.
  4. Add caching, indexes, read replicas.
  5. Move heavy work to queues.
  6. Load test, find the bottleneck, fix, repeat.
  7. Dashboards and alerts on latency percentiles and saturation.

Example

spring:
  threads:
    virtual:
      enabled: true          # Spring Boot 3.2+, Java 21+
  datasource:
    hikari:
      maximum-pool-size: 20  # x 6 pods = 120 < DB max_connections
      connection-timeout: 2000
  data:
    redis:
      timeout: 200ms
server:
  tomcat:
    connection-timeout: 5s

Common mistakes

  • Equating concurrent users with concurrent requests without doing the maths.
  • Huge connection pools per instance that overwhelm the database.
  • Sticky in-memory sessions blocking horizontal scaling.
  • No timeouts, so a slow dependency exhausts all threads.
  • Never load testing before launch.

How to answer in the interview

"Ten thousand concurrent users is mainly about not holding resources per user. I'd keep services stateless, with sessions in tokens or Redis, and scale horizontally behind a load balancer with Kubernetes autoscaling. In each instance I'd size thread and connection pools deliberately, or use virtual threads for I/O-heavy endpoints, with timeouts everywhere. The database is usually the bottleneck, so caching, read replicas, indexes and short transactions. Heavy work goes to a queue. I'd protect it with rate limiting, prove it with Gatling or k6 load tests and monitor p95 and p99 latency."

Likely follow-up questions

  • Estimating instances and connections? Little's Law for in-flight requests, per-instance throughput from load tests, and DB capacity divided across instances.
  • Virtual threads and pinning? Avoid long synchronized blocks around I/O on older JDKs; JDK 24 removed most pinning.
  • WebFlux or virtual threads? Virtual threads keep blocking code simple; WebFlux suits streaming and backpressure.
