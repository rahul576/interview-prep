How do Spring application events work, and when would you use them?

Spring Framework · concept · levels mid, senior

In one line

A bean publishes an event with ApplicationEventPublisher and @EventListener methods receive it, synchronously in the same thread and transaction by default; @Async makes listeners asynchronous and @TransactionalEventListener runs them after commit. Events decouple modules inside one app but are in-memory, not durable like Kafka.

Detailed explanation

Application events implement the observer pattern inside the Spring container. The publisher does not know who is listening: OrderService publishes OrderPlaced, and the email, loyalty and analytics components each react. Adding a new reaction means adding a listener, not editing OrderService. Events can be any object; records work well.

Synchronous by default: publishEvent calls each listener in turn on the publisher's thread. Listeners join the publisher's transaction, and an exception in a listener propagates to the publisher and can roll back its work. Order listeners with @Order. Listeners can filter with SpEL (condition = "#event.total > 100") and can return a new event to chain.

@Async listeners run on a task executor so the publisher is not slowed down, but they no longer share the transaction and exceptions are not propagated.

@TransactionalEventListener binds the listener to a transaction phase, by default AFTER_COMMIT: the welcome email is sent only if the user row really committed; if the transaction rolls back, the listener never runs. Other phases: BEFORE_COMMIT, AFTER_ROLLBACK, AFTER_COMPLETION. Note that in AFTER_COMMIT the original transaction is finished, so database writes in the listener need REQUIRES_NEW or should be async.

Limits: events live only in memory in one JVM. If the app crashes after commit but before the listener runs, the event is lost, and other services never see it. For important cross-service events, use the transactional outbox: write the event to a table in the same transaction, then relay it to Kafka or RabbitMQ. Spring Modulith builds on application events with an event publication registry that persists events and retries incomplete ones, plus externalisation to brokers.

How it works

  1. Publisher calls publisher.publishEvent(new OrderPlaced(...)).
  2. The multicaster finds matching listeners by event type.
  3. Plain listeners run immediately on the same thread.
  4. Transactional listeners are registered as synchronisations and run at the chosen phase.
  5. Async listeners are submitted to an executor.

Example

public record UserRegistered(long userId, String email) {}

@Service
class UserService {
    private final UserRepository repo;
    private final ApplicationEventPublisher events;
    UserService(UserRepository repo, ApplicationEventPublisher events) { this.repo = repo; this.events = events; }

    @Transactional
    public void register(NewUser u) {
        User saved = repo.save(new User(u.email()));
        events.publishEvent(new UserRegistered(saved.getId(), saved.getEmail()));
    }
}

@Component
class WelcomeMailListener {
    @Async
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    void on(UserRegistered e) { mail.sendWelcome(e.email()); }
}

@Component
class AuditListener {
    @EventListener   // synchronous, same transaction
    void on(UserRegistered e) { audit.record("USER_REGISTERED", e.userId()); }
}

Common mistakes

  • Sending emails in a plain @EventListener that fires even if the transaction later rolls back.
  • Using events as a replacement for a message broker between services.
  • Assuming listeners are asynchronous by default.
  • Writing to the database in an AFTER_COMMIT listener without a new transaction.

How to answer in the interview

"A component publishes an event through ApplicationEventPublisher, and any bean method with @EventListener for that type receives it. By default listeners run synchronously in the same thread and transaction, so they can roll it back. Adding @Async makes them asynchronous. @TransactionalEventListener runs the listener only after commit, so I send the welcome email only if the user was really saved. I use events to decouple modules inside one application, like in a modular monolith. But they're in-memory, not durable like Kafka: if the app crashes, they're lost. For important cross-service events I use the outbox pattern, or Spring Modulith's persistent event publication registry."

Likely follow-up questions

  • How does Spring Modulith improve on plain application events? It persists event publications, retries incomplete ones, and can externalise events to Kafka or AMQP.
  • Can a listener stop the publisher's transaction? A synchronous listener throwing an exception can, which may or may not be desired.
  • How do you test events? @RecordApplicationEvents with ApplicationEvents, or Modulith's Scenario.
