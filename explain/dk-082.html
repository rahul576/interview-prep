How do you govern container usage across many teams without blocking them?

Docker · design · levels lead

In one line

Govern container usage with a paved road (templates, approved base images, shared pipelines that are compliant by default), policies as code checked in CI and admission control (Kyverno, OPA Gatekeeper), rolled out audit-first, then enforce, with a clear exception process and per-team scorecards.

Detailed explanation

Governance fails when it means tickets, manual approvals and a security team saying "no". Teams then work around it. It succeeds when the compliant path is also the easiest path.

Paved road: the platform team provides service templates (Backstage or cookiecutter), approved base images, a shared CI pipeline that builds, scans, signs and publishes images, and Helm charts or Kustomize bases with sensible defaults: non-root, resource requests and limits, probes, labels. A team using the defaults is compliant without thinking about it.

Policy as code: rules are versioned code, reviewed like any other change. In CI, tools such as hadolint, Trivy, Conftest or Checkov check Dockerfiles, images and manifests early, when fixing is cheap. In clusters, admission controllers (Kyverno, OPA Gatekeeper, or Kubernetes ValidatingAdmissionPolicy with CEL) enforce the essentials: images only from approved registries, verified signatures, no critical CVEs, non-root, no privileged pods or hostPath, resource limits present.

Rollout: new policies start in audit/warn mode, violations appear on dashboards and in PR comments, teams get a deadline, then the policy switches to enforce. A documented, time-limited exception (a PolicyException resource with an owner and expiry) handles genuine edge cases.

Visibility: scorecards per team show compliance, image age and vulnerabilities, which drives improvement through transparency rather than blocking.

How it works

  1. Define a small set of must-have rules with security and teams.
  2. Build them into templates and pipelines first.
  3. Add CI checks for fast feedback.
  4. Deploy admission policies in audit mode; publish reports.
  5. Enforce after the deadline; manage exceptions with expiry.
  6. Review policies and scorecards regularly.

Example

apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: { name: restrict-registries }
spec:
  validationFailureAction: Audit      # switch to Enforce after the grace period
  background: true
  rules:
    - name: approved-registry
      match: { any: [ { resources: { kinds: [Pod] } } ] }
      validate:
        message: "Images must come from registry.example.com"
        pattern:
          spec:
            containers:
              - image: "registry.example.com/*"

Common mistakes

  • Enforcing new policies on day one and breaking deployments.
  • Hundreds of rules nobody understands, instead of a few that matter.
  • Policies only in the cluster, so developers learn about violations at deploy time.
  • Permanent exceptions with no owner or expiry.

How to answer in the interview

"I'd make the right way the easy way: templates, approved base images and a shared pipeline that already build, scan and sign correctly, plus chart defaults with non-root and resource limits. The rules themselves are policy as code: checked in CI for early feedback and enforced in clusters with Kyverno or Gatekeeper, for example only approved registries, signed images, non-root and limits. Every new policy starts in audit mode, teams see violations on dashboards and get time to fix them, then we enforce, with a time-limited exception process for real edge cases. Scorecards per team make progress visible without us becoming a bottleneck."

Likely follow-up questions

  • How do you roll out a mandatory policy without outages? Audit first, report, give a deadline, enforce in non-prod, then prod.
  • Kyverno vs Gatekeeper? Kyverno uses YAML policies and can mutate/verify images easily; Gatekeeper uses Rego and is very flexible.
  • How do you measure success? Compliance percentage, image age, CVE counts and lead time not getting worse.
