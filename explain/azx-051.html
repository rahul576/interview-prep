A build pipeline takes 40 minutes and developers are frustrated. How do you speed it up?

Azure DevOps & Pipelines · scenario · levels mid, senior

In one line

Measure first (run timeline), then attack the biggest steps: cache dependencies (Cache task keyed on lock files), parallelise independent jobs, build only what changed (path filters), use Docker layer/registry caching, split slow tests across agents, and use faster or warm agents (Managed DevOps Pools with standby and persistent caches).

Detailed explanation

Optimising without data wastes effort. The run timeline shows duration per stage, job and step; Pipeline analytics shows trends and failure rates. Typically two or three steps dominate: dependency restore, Docker build, tests or waiting for an agent.

Common wins:

  • Dependency caching: the Cache@2 task restores ~/.npm, ~/.nuget/packages, ~/.m2 or pip caches with a key built from the lock file hash, plus restoreKeys fallbacks. Restoring 2 GB of packages from scratch every run is often minutes.
  • Parallel jobs: unit tests, linting, SAST and container build don't depend on each other; split them into jobs that run simultaneously (needs enough parallel jobs).
  • Build only what changed: path filters or an "affected" script in monorepos; skip docs-only changes.
  • Docker: order Dockerfile layers so dependency installation comes before copying source, use BuildKit with --cache-from/--cache-to a registry cache, and multi-stage builds to keep images small.
  • Tests: split test suites across parallel agents (parallel: 4 with test slicing), move slow end-to-end tests to a later stage or nightly, and fix or quarantine flaky tests that cause reruns.
  • Agents: Microsoft-hosted agents start cold and are relatively small. Managed DevOps Pools with larger SKUs, standby agents and stateful agents keep caches and Docker layers warm, cutting startup and restore time. Also check queue time.
  • Shallow checkout: fetchDepth: 1 for large repos.

Set a target (for example under 10 minutes for PR builds) and track it.

How it works

  1. Collect step durations over several runs.
  2. Fix the largest contributor first.
  3. Add caching keyed on lock files.
  4. Restructure into parallel jobs.
  5. Optimise Docker and tests.
  6. Upgrade agents; re-measure and repeat.

Example

variables:
  npm_config_cache: $(Pipeline.Workspace)/.npm
steps:
- checkout: self
  fetchDepth: 1
- task: Cache@2
  inputs:
    key: 'npm | "$(Agent.OS)" | package-lock.json'
    restoreKeys: 'npm | "$(Agent.OS)"'
    path: $(npm_config_cache)
- script: npm ci
- script: |
    docker buildx build --cache-from type=registry,ref=acrprod.azurecr.io/web:cache \
      --cache-to type=registry,ref=acrprod.azurecr.io/web:cache,mode=max -t web:$(Build.BuildId) .

Common mistakes

  • Caching without the lock file in the key, causing stale or wrong builds.
  • Caching node_modules instead of the package manager cache.
  • Parallelising without enough parallel jobs, so jobs just queue.
  • Deleting tests instead of moving or fixing them.

How to answer in the interview

"First I'd measure with the run timeline, which usually shows two or three steps dominating. Then: cache dependencies with the Cache task keyed on the lock file, run independent work like unit tests, linting and scans as parallel jobs, and use path filters so a monorepo only builds what changed. For containers I'd order Dockerfile layers well and use registry-based BuildKit caching. Slow suites get split across agents, with heavy end-to-end tests later or nightly. Finally, agents: larger, warm agents in Managed DevOps Pools with standby and persistent caches can save many minutes."

Likely follow-up questions

  • Keep caches from causing wrong builds? Key on lock files and OS, use npm ci, never cache build outputs blindly.
  • Measure improvement? Pipeline analytics duration trends, p50 and p90.
  • Test splitting? Distribute tests by historical duration across parallel jobs.
