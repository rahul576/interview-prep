Which data foundations does AIOps need to work well?

AI Agents & AIOps · concept · levels mid, senior

In one line

AIOps needs consistent telemetry (OpenTelemetry, common labels), a service catalog with dependency topology, central change and deployment events, incident history with root causes, runbooks and ownership data, and good data quality and retention.

Detailed explanation

AIOps tools correlate signals across systems, so the most important property of the data is that it can be joined. If one tool labels a service checkout, another checkout-svc and a third uses a pod name, no model can link them reliably. Instrumenting metrics, logs and traces with OpenTelemetry and semantic conventions for service.name, deployment.environment, service.version and region creates that common language.

A service catalog (such as Backstage) provides ownership, tiering and on-call routing; a dependency topology, ideally derived automatically from traces or a service mesh, tells the system which components affect which. Change events from CI/CD, GitOps, feature flag systems and config management must be recorded centrally with timestamps and service labels, because changes are the most common trigger of incidents and the strongest correlation signal.

Incident history with linked alerts, timelines, root causes and resolutions provides training examples for correlation and similarity search. Runbooks and ownership data let assistants suggest steps and people. Finally, data quality and retention: gaps in collection, high-cardinality chaos and seven-day retention make seasonality learning impossible. That is why many AIOps projects begin with an observability clean-up.

How it works

  1. Standardise resource attributes and naming through OpenTelemetry.
  2. Register every service in a catalog with owner and tier.
  3. Derive topology from traces; keep it updated automatically.
  4. Emit change events from every deployment and flag change.
  5. Store incidents in structured form with linked alerts and causes.
  6. Set retention long enough for seasonality (several weeks at least).

Example

# OpenTelemetry resource attributes applied to every signal
resource:
  attributes:
    service.name: checkout
    service.namespace: shop
    service.version: 4.12.0
    deployment.environment.name: prod
    cloud.region: eu-west-1
---
# Change event emitted by the pipeline
event: deployment
service: checkout
version: 4.12.0
environment: prod
time: 2026-11-20T10:14:03Z
commit: a1b2c3d

Common mistakes

  • Buying an AIOps product to compensate for poor data.
  • Inconsistent service names across tools.
  • Deployments not recorded as events.
  • Incident records as free text without linked alerts or causes.

How to answer in the interview

"AIOps is only as good as its data. First consistent telemetry, using OpenTelemetry with common labels for service, environment, version and region so signals can be joined. Then a service catalog with ownership and a dependency topology, ideally derived from traces. Change and deployment events must be recorded centrally, since changes cause most incidents. Incident history with root causes provides learning examples, and runbooks and ownership let assistants suggest steps and people. And data quality and retention matter, so many AIOps projects really start with cleaning up observability."

Likely follow-up questions

  • Fix first in a messy company? Consistent service naming and deployment events.
  • Topology manual or automatic? Automatic from traces; manual goes stale.
  • Retention needed? Weeks to months for seasonality; summaries for longer.
