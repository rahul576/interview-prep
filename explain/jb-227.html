What is the difference between centralized and decentralized configuration?

Microservices · concept · levels mid, senior

In one line

Centralised configuration keeps settings for all services in one managed store (Spring Cloud Config, Consul, a central ConfigMap repo, Azure App Configuration), giving consistency, auditing and runtime refresh but creating a critical dependency; decentralised configuration keeps config with each service, giving autonomy but risking drift; secrets go to a vault either way.

Detailed explanation

Centralised. A config server or store holds configuration for many services and environments, often backed by Git for history and review. Examples: Spring Cloud Config Server, Consul KV, AWS AppConfig / Parameter Store, Azure App Configuration, or a central GitOps repository rendering Kubernetes ConfigMaps. Services fetch their config at startup (spring.config.import=configserver:) and some values can refresh at runtime (@RefreshScope, Spring Cloud Bus, or watching ConfigMaps). Benefits: one place to change shared values such as a feature flag or an endpoint, consistent settings across services, audit trail and approvals, environment comparison, and dynamic changes without redeploys.

The risks: the config service becomes a critical dependency. If it is down when pods start, services may fail to boot unless they use fail-fast with retries, local defaults or cached config. Centralisation also introduces coupling: teams depend on a shared repository and process, and a bad central change can break many services at once. Runtime refresh can create inconsistent state if not all beans refresh cleanly.

Decentralised. Each service owns its configuration in its own repository and deployment manifests, injected at deploy time as environment variables, mounted files or Helm values. This fits twelve-factor and team autonomy: the service and its config are versioned and released together, with no runtime config server. The downsides are duplicated values across services, configuration drift between environments or services, and no single view.

Many organisations mix both: service-specific config lives with the service; truly shared settings and feature flags (via a flag platform such as LaunchDarkly, Unleash or OpenFeature-compatible tools) are centralised. Secrets (passwords, API keys) are never committed to either; they come from HashiCorp Vault, AWS Secrets Manager, Azure Key Vault or sealed/external secrets in Kubernetes.

How it works

  1. Define config ownership: service-local vs shared.
  2. Centralised: service starts → imports from config server → optional refresh.
  3. Decentralised: CI/CD renders env vars/ConfigMaps from the service repo.
  4. Secrets injected from a vault at runtime.
  5. Changes go through review and are audited.

Example

# Centralised: client side
spring:
  application:
    name: order-service
  config:
    import: "optional:configserver:http://config-server:8888"
  cloud:
    config:
      fail-fast: true
      retry:
        max-attempts: 10
---
# Decentralised: values from the service's own Helm chart
env:
  - name: ORDERS_MAX_ITEMS
    value: "50"
  - name: DB_PASSWORD
    valueFrom: { secretKeyRef: { name: orders-db, key: password } }  # synced from Vault

Common mistakes

  • Secrets in the config Git repository.
  • No fallback when the config server is unavailable at startup.
  • Overusing runtime refresh for settings that need a restart.
  • Copy-pasting shared values into dozens of services.

How to answer in the interview

"Centralised configuration puts settings for all services in one store, like Spring Cloud Config backed by Git or Azure App Configuration. Services load it at startup and can refresh at runtime, which gives consistency, auditing and one place to change shared values, but the config server becomes a critical dependency and teams become coupled. Decentralised configuration keeps each service's config in its own repository and deployment, injected as environment variables, which keeps teams autonomous but risks drift and duplication. I usually keep service config with the service, centralise only shared settings and feature flags, and always keep secrets in a vault."

Likely follow-up questions

  • What if the config server is down at startup? Fail fast with retries, or start with cached or default config if safe; run it highly available.
  • How does @RefreshScope work? Beans are recreated with new values after a refresh event.
  • Feature flags vs configuration? Flags change behaviour per user or segment at runtime and need a dedicated system.
