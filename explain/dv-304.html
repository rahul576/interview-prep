A critical CVE is announced in a library used across many services. How do you respond?

DevSecOps · scenario · levels mid, senior

In one line

Find affected services fast from SBOM/SCA inventory, assess exploitability and exposure to prioritise, patch by bumping, rebuilding and redeploying through the normal pipeline, mitigate meanwhile (WAF rules, config flags, disabling features), and communicate and track to closure, then learn.

Detailed explanation

Incidents like Log4Shell (2021) and the xz-utils backdoor (2024) showed that speed depends on preparation.

1. Scope. The first question is "where do we use it?" Organisations with SBOMs stored in Dependency-Track or an SCA platform (Snyk, GitHub dependency graph) can query by package and version across every repository, image and running cluster in minutes. Also check transitive dependencies, base images, vendor products and SaaS suppliers.

2. Assess. Read the advisory: affected versions, attack vector, preconditions, whether exploitation is happening (CISA KEV, vendor notes, EPSS). Then rank services by exposure: internet-facing and handling sensitive data first, internal batch jobs later. A CVSS 9.8 that requires a disabled feature may be lower priority than a 7.5 being actively exploited on your public API.

3. Mitigate. Where patching takes time: WAF rules blocking exploit patterns, configuration or JVM flags that disable the vulnerable feature, network egress restrictions, turning off a feature flag, or isolating the service.

4. Patch. Bump the dependency (Renovate/Dependabot can open PRs across repos), rebuild images on patched base images, run tests and redeploy through the standard pipeline. Fast, automated pipelines are a security control: teams that deploy daily patch in hours.

5. Verify and close. Re-scan running images, confirm versions in production, check logs for signs of exploitation before the patch, and rotate secrets if compromise is possible. Track every service on a board until done.

6. Learn. Post-incident review: how long did discovery take, which services were slow, what to automate.

How it works

  1. Declare incident; assign lead; open tracker.
  2. Query SBOM inventory for affected components.
  3. Prioritise by exploitability and exposure.
  4. Apply mitigations to top-priority services.
  5. Patch, rebuild, redeploy; verify in production.
  6. Communicate status; review afterwards.

Example

# Find which stored SBOMs contain the vulnerable component
grype sbom:./sboms/orders-api.cdx.json --only-fixed --fail-on critical
# Or query across all running images in a cluster
kubectl get pods -A -o jsonpath='{..image}' | tr ' ' '\n' | sort -u \
  | xargs -I{} trivy image --quiet --severity CRITICAL --vuln-type library {}

Scenario: a critical RCE in a JSON library. Dependency-Track shows 23 services; 4 are public. WAF rules go live within an hour, the 4 public services are patched by evening and the rest within two days.

Common mistakes

  • Searching repositories by hand because there is no inventory.
  • Prioritising purely by CVSS score.
  • Declaring done without verifying what actually runs in production.

How to answer in the interview

"I'd treat it as an incident. First, scope: with SBOMs in Dependency-Track or an SCA tool, I can query which services and images contain the vulnerable version within minutes. Then I prioritise by exploitability and exposure, internet-facing and sensitive services first. Where patching takes time, I mitigate with WAF rules, config flags or disabling the feature. Teams bump the dependency, rebuild and redeploy through the normal pipeline, which is why fast pipelines matter. I verify what's running, check for signs of exploitation, keep stakeholders updated, track every service to closure and run a review to respond faster next time."

Likely follow-up questions

  • How do SBOMs speed this up? They turn discovery into a query instead of a manual search.
  • No patch available yet? Mitigations, isolation, monitoring for exploitation, vendor follow-up.
  • How to communicate? Regular status updates with scope, risk, ETA and what users need to do.
