You updated a ConfigMap but the application still uses the old values. Why, and how do you handle config changes properly?

Kubernetes · scenario · levels entry, mid, senior

In one line

It depends on how the ConfigMap is consumed: environment variables are read only at container start; mounted volumes update eventually (but subPath mounts never); and the app may not reload files anyway. Handle changes with a rollout: rollout restart, a checksum annotation, or immutable, versioned ConfigMaps.

Detailed explanation

A ConfigMap is just an API object; changing it does not touch running containers directly. What happens depends on the consumption path:

  • Env vars (env.valueFrom.configMapKeyRef or envFrom): resolved by the kubelet once when the container starts. A running process's environment never changes, so the pod keeps old values until it is recreated.
  • Volume mounts: the kubelet periodically syncs projected files, using an atomic symlink swap. The delay is the kubelet sync period plus its cache TTL, often up to a minute or two. The files change, but the application must watch or re-read them; many frameworks read config once at start-up.
  • subPath mounts: mount a single file into an existing directory, bypassing the symlink mechanism, so they are never updated.

So "I changed the ConfigMap and nothing happened" is expected. The robust approach is to treat config like code and roll it out:

  • kubectl rollout restart deployment/orders creates new pods with new values, respecting rolling update settings and readiness.
  • Better, a checksum annotation in the pod template, such as checksum/config: <sha256 of the config>; Helm templates do this with sha256sum, and Kustomize's configMapGenerator appends a content hash to the name (orders-config-7g9k2m) and rewrites references. Any change alters the template, triggering a normal rolling update.
  • Immutable, versioned ConfigMaps (immutable: true plus a new name per version) mean old pods keep the old version, new pods get the new one, a bad config rolls out gradually with readiness protection, and rollback simply returns to the previous ReplicaSet. Immutable objects also reduce kubelet watch load.

Hot reloading suits log levels or flags, but it changes all pods at once.

How it works

  1. Config change committed to Git.
  2. Generator or template produces a new name or checksum.
  3. Pod template changes → Deployment creates a new ReplicaSet.
  4. New pods start with new config and must pass readiness.
  5. Old ReplicaSet scaled down; rollback reverts to old config.

Example

# kustomization.yaml
configMapGenerator:
- name: orders-config
  files: [app.yaml]
  options:
    immutable: true
# Helm deployment template
spec:
  template:
    metadata:
      annotations:
        checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}
kubectl rollout restart deployment/orders -n shop

Common mistakes

  • Expecting env vars to update in running pods.
  • Using subPath and wondering why the file never changes.
  • Editing a ConfigMap in place in production with no rollout or rollback path.
  • Hot-reloading a bad config into every pod simultaneously.

How to answer in the interview

"It depends on how the ConfigMap is consumed. Env vars are read only when the container starts, so they never change in a running pod. Mounted files are updated by the kubelet eventually, but subPath mounts never update, and even updated files don't help if the app reads them only at start-up. So I trigger a rollout when config changes: rollout restart, or better a checksum annotation in the pod template, which Helm and Kustomize generate. Even safer is immutable, versioned ConfigMaps, so bad config rolls out gradually like code and can be rolled back."

Likely follow-up questions

  • Why is hot-reloading everywhere at once dangerous? A bad value hits all pods instantly with no readiness gate or gradual rollout.
  • Do Secrets behave the same? Yes, same rules for env vars, volumes and subPath.
  • What does Reloader do? A controller that restarts workloads when referenced ConfigMaps or Secrets change.
