Design the backend for an online multiplayer game with matchmaking and real-time play.

Classic Design Problems · design · levels senior, lead

In one line

A multiplayer game backend uses a matchmaking service (skill, party, latency), allocates a dedicated authoritative game server per match (e.g. Agones), runs gameplay over UDP with client prediction and server reconciliation, deploys regionally, keeps profiles and inventory in durable storage, and invests in anti-cheat and peak scaling.

Detailed explanation

There are two very different halves. The meta-game (accounts, friends, inventory, store, leaderboards) is a classic web backend: stateless services, databases, caches. The real-time match is stateful, latency-critical and short-lived, and runs on dedicated game servers.

Matchmaking places players in a queue with attributes: skill rating (Elo, Glicko, TrueSkill), party size, mode and measured ping to each region. A matchmaking function forms balanced matches and widens criteria over time so nobody waits forever. Open Match is an open-source framework for this; cloud options also exist.

When a match is formed, an allocator reserves a dedicated game server from a warm fleet; Agones on Kubernetes manages fleets of game-server pods with "Ready/Allocated" states. Players get the IP and port plus a session token.

Gameplay uses UDP (often with a reliability layer for important messages) because a late packet is worse than a lost one. The server is authoritative: clients send inputs, not positions. Clients use prediction to move immediately, interpolation to smooth other players, and the server reconciles; techniques like lag compensation handle hit detection.

Regional deployment keeps round-trip times low. Persistent data, especially purchases, uses transactional storage; match results are written via events at match end.

How it works

  1. Player logs in, client pings regions, enters the matchmaking queue.
  2. Matchmaker forms a match, requests a server allocation in the best region.
  3. Agones returns a Ready server; players connect over UDP with a token.
  4. Server simulates at a fixed tick rate (e.g. 30-60 Hz), broadcasts state snapshots.
  5. At match end, the server publishes results; services update ratings, progress and rewards.
  6. The server shuts down and the fleet autoscaler replaces it.

Example

apiVersion: "allocation.agones.dev/v1"
kind: GameServerAllocation
spec:
  selectors:

        agones.dev/fleet: arena-eu-west
        mode: ranked-5v5
  metadata:
    labels:
      match-id: m-7f31c2

Common mistakes

  • Trusting the client with positions, damage or currency.
  • Using TCP for fast-paced gameplay, causing head-of-line stalls.
  • Spinning up servers on demand with no warm buffer, so matches wait minutes.
  • Writing every in-match event to the database synchronously.
  • Ignoring launch-day peaks.

How to answer in the interview

"I'd split it into meta-services and real-time servers. Players join a matchmaking queue that groups them by skill, party size and latency, widening criteria over time. When a match forms, we allocate a dedicated, authoritative game server from a warm fleet managed by Agones in the nearest region. Gameplay runs over UDP; clients send inputs, use prediction and interpolation, and the server reconciles. Profiles, inventory and purchases are in durable transactional storage, updated from match-end events. Anti-cheat relies on server authority plus detection, and fleets are pre-warmed for launches."

Likely follow-up questions

  • Game server crashes mid-match? Detect via health checks, void or restore from periodic snapshots, compensate players.
  • How do you balance wait time and match quality? Gradually relax skill and latency windows; track both metrics.
  • Peer-to-peer instead? Cheaper, but exposes IPs and makes cheating easier; fine for casual co-op.
