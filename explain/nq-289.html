How are automated tests integrated into a CI/CD pipeline?

DevOps & CI/CD · scenario · levels mid

In one line

Tests are pipeline gates: unit tests on every commit and PR, integration tests with Testcontainers in CI, reports and coverage thresholds via JaCoCo and the Sonar quality gate, then smoke, API, end-to-end and performance tests after deployment; any failure stops promotion, tests are parallelised, and flaky tests are fixed, not ignored.

Detailed explanation

The test pyramid guides placement: many fast unit tests, fewer integration tests, very few slow end-to-end tests.

On every PR:

  • Unit tests (mvn test, Surefire): seconds to minutes, must pass.
  • Integration tests (mvn verify, Failsafe) using Testcontainers to start real PostgreSQL, Kafka or Redis in Docker, so tests run against real dependencies rather than in-memory substitutes.
  • Contract tests (Spring Cloud Contract, Pact) for APIs between services.
  • Reports: JUnit XML published to the CI UI; JaCoCo coverage sent to SonarQube, whose quality gate might require at least 80% coverage on new code.

After deployment to an environment:

  • Smoke tests: health endpoints and a few critical calls.
  • API and end-to-end tests: REST Assured, Postman/Newman, Playwright or Cypress for UI.
  • Performance tests in staging with JMeter, Gatling or k6, compared with baseline thresholds.

Keeping it fast and reliable: parallel stages and test sharding, caching dependencies, running expensive suites nightly when appropriate. Flaky tests erode trust; quarantine them with a ticket, fix root causes (timing, shared state, order dependence) and track the flake rate.

How it works

  1. PR: compile, unit tests, integration tests, coverage.
  2. Quality gate evaluates coverage and issues.
  3. Merge: artifact built and deployed to test environments.
  4. Post-deploy smoke and API tests verify the running service.
  5. Staging: end-to-end and performance tests.
  6. Failure at any stage blocks promotion and notifies the team.

Example

@SpringBootTest
@Testcontainers
class OrderRepositoryIT {
    @Container @ServiceConnection
    static PostgreSQLContainer<?> db = new PostgreSQLContainer<>("postgres:16");

    @Autowired OrderRepository repo;

    @Test void savesOrder() {
        assertThat(repo.save(new Order("ORD-1")).getId()).isNotNull();
    }
}

Common mistakes

  • Retrying flaky tests until green and moving on.
  • Coverage targets on the whole legacy codebase instead of new code.
  • Running end-to-end tests for everything, making the pipeline slow.
  • Tests that pass locally but depend on shared environments in CI.

How to answer in the interview

"Tests are stages that gate progress. On every pull request we run unit tests with Surefire and integration tests with Failsafe and Testcontainers, so we test against a real Postgres or Kafka. Results are published as JUnit reports, JaCoCo coverage goes to SonarQube, and the quality gate requires, say, eighty percent on new code. After deploying to an environment, smoke and API tests run against the live service, and in staging we run end-to-end and performance tests with Gatling. Any failure stops promotion. We parallelise to keep it fast, and flaky tests are quarantined and fixed, not ignored."

Likely follow-up questions

  • How do you deal with flaky tests? Quarantine with ownership, find root cause, track flake rate.
  • Why Testcontainers over H2? Real database behaviour, SQL dialect and constraints.
  • What is a contract test? Verifies provider and consumer agree on the API.
