Which product-processing operations are suitable for parallel execution?

Coding Exercises · scenario · levels senior, lead

In one line

Suitable for parallel: independent, CPU-bound per-product work on large collections (price calculations into new objects, filtering by computed rules) and associative aggregations (sum, count, min/max, groupingByConcurrent); unsuitable: ordered output, shared mutable updates, I/O or database calls per element, and small lists.

Detailed explanation

parallelStream() splits the source into chunks, processes them on the common ForkJoinPool (by default roughly one thread per CPU core minus one, plus the caller), and combines partial results. It helps only when the work saved by using more cores outweighs the cost of splitting, scheduling and merging.

Good candidates — all three conditions hold:

  • Large data: hundreds of thousands or millions of products. A common rule of thumb is that the number of elements times the cost per element must be large (Doug Lea's "N × Q" guidance).
  • Independent, CPU-bound work per element: computing discounted or taxed prices into new objects, evaluating complex pricing rules, scoring or filtering by computed criteria, parsing.
  • Associative, stateless combination: sum, count, min, max, summaryStatistics, toList, and grouping — preferably groupingByConcurrent, which writes into one ConcurrentHashMap instead of merging many maps.
  • Splittable sources: ArrayList, arrays and ranges split well; LinkedList and I/O-based streams split poorly.

Poor candidates:

  • Order-dependent work: forEachOrdered, sorted, limit and findFirst on ordered streams force coordination and reduce or eliminate gains.
  • Shared mutable state: updating the same objects, adding to an external ArrayList, or incrementing a shared counter causes race conditions or contention.
  • Blocking I/O: calling a pricing REST API or database per product blocks the common pool, which is shared JVM-wide (including other parallel streams and some CompletableFuture usage), starving unrelated work; throughput is limited by the remote service, not CPUs. Use async clients, batching, or an executor sized for I/O — for example virtual threads (Java 21) with structured concurrency.
  • Small lists: thread coordination overhead dominates.
  • In application servers, many requests already use all cores, so parallel streams can hurt overall throughput.

Always benchmark with realistic data and load before switching.

How it works

  1. The source is split into chunks via its Spliterator.
  2. Chunks are processed on ForkJoinPool worker threads.
  3. Each chunk produces a partial result.
  4. Partial results are combined with the collector's combiner.
  5. Gains appear only when per-chunk work far exceeds this overhead.

Example

// good: large list, CPU-bound, new objects, associative aggregation
List<Product> repriced = catalogue.parallelStream()
        .map(p -> p.withPrice(pricingEngine.compute(p)))   // pure CPU work
        .toList();

double stockValue = catalogue.parallelStream()
        .mapToDouble(p -> p.price() * p.stock())
        .sum();

ConcurrentMap<String, Long> perCategory = catalogue.parallelStream()
        .collect(Collectors.groupingByConcurrent(Product::category, Collectors.counting()));

// bad: shared mutable list and blocking I/O
List<Product> out = new ArrayList<>();
catalogue.parallelStream().forEach(out::add);                  // race condition
catalogue.parallelStream().map(p -> pricingApi.fetch(p.id()))  // blocks common pool
        .toList();

// better for I/O: virtual threads
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<Price>> fs = catalogue.stream()
            .map(p -> exec.submit(() -> pricingApi.fetch(p.id()))).toList();
}

Common mistakes

  • Assuming parallel is always faster.
  • Collecting into a non-thread-safe external collection.
  • Doing network or database calls in parallel streams.
  • Using parallel streams inside request handling on a busy server.

How to answer in the interview

"Good candidates are operations where each product is processed independently and the work is CPU-bound on a large collection, say hundreds of thousands of products: computing discounted or taxed prices into new objects, filtering by computed rules, and associative aggregations like totals, counts, min or max, or grouping with groupingByConcurrent. Poor candidates are anything needing strict order, updating shared mutable objects or an external list, calls to a database or remote service per product, which block the common pool, and small lists where overhead dominates. I always benchmark before choosing parallel."

Likely follow-up questions

  • Why is calling a pricing REST API from a parallel stream a bad idea? It blocks the shared common pool and is limited by the remote service; use async calls or virtual threads.
  • Can you use a custom pool? Submitting the stream inside a custom ForkJoinPool works in practice but is an implementation detail; prefer explicit executors.
  • Why groupingByConcurrent? It avoids merging many per-thread maps.
