How do you package and distribute an MCP server to other teams or users?

MCP Servers · concept · levels mid, senior

In one line

Distribute local servers through package managers (npm with npx, PyPI with uvx) or container images, offer one-click desktop bundles, prefer a remote hosted server with OAuth for organisations, publish metadata to the MCP Registry or an internal registry, and ship signed, pinned versions.

Detailed explanation

How you distribute a server decides how easy it is to adopt, how fast fixes reach users, and how much risk users take on. The options trade convenience against control.

Package managers are the most common channel for local servers. A host config runs npx -y @acme/mcp-server or uvx acme-mcp-server, which downloads and starts the package on demand. This is easy, but unpinned commands silently pick up new versions. Container images work both locally, started with docker run -i over stdio, and remotely, and they isolate the server from the user's machine with a defined runtime. Desktop bundles (for example the MCP Bundle format, .mcpb, previously called DXT) package the server, its runtime dependencies and a manifest that declares required configuration, so a user can install it with a click.

For organisations, a remote server over Streamable HTTP with OAuth is usually best: users add a URL, there is nothing to install or patch on laptops, credentials stay server-side and the owning team controls rollouts. For discovery, the official MCP Registry holds metadata that points to where the package or remote endpoint lives; it does not host code, and enterprises often run their own sub-registry with only approved entries.

Because an MCP server's tool descriptions go straight into the model's context, an update can change agent behaviour or even inject instructions. That makes signed releases, provenance attestations and version pinning more important than for an ordinary library.

How it works

  1. Build and test the server; publish it to npm or PyPI and/or as a container image with a fixed tag and digest.
  2. Sign artefacts (npm provenance, Sigstore/cosign for images).
  3. Optionally build a desktop bundle with a manifest of required settings.
  4. Publish a server.json entry to the MCP Registry or internal registry.
  5. Document a pinned install snippet; consumers update deliberately after reviewing changes.

Example

{
  "mcpServers": {
    "acme-local": {
      "command": "npx",
      "args": ["-y", "@acme/mcp-server@2.3.1"]
    },
    "acme-container": {
      "command": "docker",
      "args": ["run", "-i", "--rm", "ghcr.io/acme/mcp-server@sha256:3f1c..."]
    },
    "acme-remote": {
      "type": "http",
      "url": "https://mcp.acme.example/mcp"
    }
  }
}

Common mistakes

  • Publishing install instructions with @latest or no version at all.
  • Asking users to paste long-lived API keys into shared config files.
  • Shipping a local server to hundreds of employees when a remote server would be easier to govern.
  • Treating the registry as a security review; it lists servers, it does not vet them.

How to answer in the interview

"For local servers the usual channels are npm, run by hosts with npx, and PyPI, run with uvx, plus container images that work locally over stdio or as remote deployments and give better isolation. Desktop hosts also support installable bundles with a manifest, so non-developers get one-click install. For an organisation I'd normally prefer a remote server with OAuth: people just add a URL, there's nothing to update locally and credentials stay server-side. I'd publish metadata to the MCP Registry or our internal registry so it's discoverable. And I always publish signed releases and tell consumers to pin versions, because a server update changes what the model reads."

Likely follow-up questions

  • Why is pinning especially important here? An update can change tool descriptions and behaviour that the model trusts automatically.
  • Does the MCP Registry host packages? No, it stores metadata pointing to npm, PyPI, OCI images or remote URLs.
  • How do you roll out a breaking change? New major version, deprecation notice, and keep old tool names working for a period.
