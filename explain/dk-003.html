How does port mapping with -p work in Docker?

Docker · concept · levels entry

In one line

-p host:container publishes a container port on the host (e.g. -p 8080:80 → localhost:8080 reaches port 80 inside), optionally bound to an interface like 127.0.0.1; -P publishes all EXPOSEd ports to random host ports; docker port shows mappings, and a taken host port causes "address already in use".

Detailed explanation

Each container has its own network namespace and a private IP on a Docker network. A service listening on port 80 inside is reachable from other containers on that network, but not from the host's external interfaces until you publish it.

-p [ip:]hostPort:containerPort[/protocol] asks Docker to forward traffic. On Linux this uses iptables/nftables NAT rules. Variants:

  • -p 8080:80 → all host interfaces, port 8080 → container 80.
  • -p 127.0.0.1:5432:5432 → only reachable from the host itself; safer for databases and admin UIs.
  • -p 53:53/udp → UDP instead of TCP.
  • -p 80 → container port 80 to a random host port.
  • -p 8000-8010:8000-8010 → ranges.

-P (capital) publishes every port declared with EXPOSE in the image to random high ports. docker port name or docker ps shows the actual mapping.

Port conflicts: a host port can be bound by only one process. If another container or a local service already uses 8080, docker run fails with "bind: address already in use"; choose another host port. The container port can be the same in many containers because each has its own namespace.

Security note: Docker's NAT rules are inserted before many host firewall rules, so on Linux a published port can be reachable from the internet even if UFW appears to block it. On a cloud VM, publishing a database with -p 5432:5432 may expose it publicly unless the security group or firewall blocks it. Bind to 127.0.0.1 or keep it unpublished and use a Docker network.

How it works

  1. App listens on a port inside the container (on 0.0.0.0, not 127.0.0.1).
  2. -p creates NAT rules from host IP:port to container IP:port.
  3. Client connects to host:port → forwarded to the container.
  4. Other containers on the same network use the container port directly.

Example

docker run -d --name web -p 8080:80 nginx:1.27
curl -I http://localhost:8080
docker run -d --name db -p 127.0.0.1:5432:5432 -e POSTGRES_PASSWORD=dev postgres:17
docker run -d --name tmp -P nginx:1.27
docker port tmp            # 80/tcp -> 0.0.0.0:32768
docker run -d -p 8080:80 httpd   # fails: port is already allocated

Common mistakes

  • App inside the container listening on 127.0.0.1, so the published port gives "connection reset".
  • Reversing the order (it is host first, container second).
  • Publishing database ports on all interfaces on a cloud VM.
  • Thinking EXPOSE alone makes a port reachable.

How to answer in the interview

"Containers have their own network namespace, so a service on port 80 inside isn't reachable from outside until I publish it. -p host:container does that: docker run -p 8080:80 nginx forwards host port 8080 to container port 80, so I open localhost:8080. By default it binds on all host interfaces; -p 127.0.0.1:8080:80 restricts it to local access, which I use for databases. Capital -P publishes every exposed port to random host ports, and docker port shows the mapping. If the host port is already used, the run fails with address already in use."

Likely follow-up questions

  • Why is a published DB port risky on a cloud VM? It may be exposed to the internet, and Docker's iptables rules can bypass UFW.
  • Do containers on the same network need -p? No, they use the container port directly.
  • "Connection reset" on a mapped port? The app is likely bound to localhost inside the container.
