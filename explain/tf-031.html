After upgrading a provider major version, the plan wants to replace dozens of resources. What do you do?

Terraform · scenario · levels mid, senior

In one line

Do not apply. Major provider versions rename arguments, change defaults, split resources or change ForceNew behaviour; read the upgrade guide, adapt the code (explicit settings, moved blocks or state migration), iterate until the plan shows only intended changes, and roll out through lower environments first with pinned versions.

Detailed explanation

A plan full of replacements after a provider upgrade almost never means the infrastructure really needs rebuilding. It means the code no longer describes the existing objects in the way the new provider expects. Replacing dozens of resources could cause outages and data loss, so the plan is a signal to work, not to approve.

Typical reasons, documented in each provider's upgrade guide:

  • Renamed or removed arguments, for example deprecated attributes finally removed.
  • Changed defaults: a value you never set is now defaulted differently, so Terraform wants to change it, sometimes with forced replacement.
  • Resources split into several, as happened with the AWS provider's S3 bucket refactor (versioning, encryption, lifecycle as separate resources) or AzureRM's split of azurerm_virtual_machine into Linux and Windows types.
  • Changed ForceNew rules or new validation.

The process: pin providers so upgrades only happen deliberately, via a pull request that bumps the version constraint and .terraform.lock.hcl. Read the upgrade guide and changelog. Run the plan and go through it resource by resource. Set changed defaults explicitly to their current values. Migrate to new resource types with moved blocks where the provider supports cross-type moves, or with removed plus import blocks otherwise. Remove deprecated settings. Iterate until the plan shows no changes, or only intended ones. Then roll out in dev, then staging, then production, comparing plans at each step.

For many root modules, upgrade gradually: modules first, then root configurations in batches, with Renovate PRs and CI plans per configuration.

How it works

  1. Bump provider version in a branch; terraform init -upgrade.
  2. Read the upgrade guide; run plan.
  3. Classify every replace or update in the plan.
  4. Adjust code, add moved/removed/import blocks.
  5. Repeat until plan is clean; apply in lower environments first.
  6. Merge lock file; promote to production.

Example

terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"        # was "~> 5.0"; bumped deliberately in this PR
    }
  }
}
terraform init -upgrade
terraform plan -out=tfplan | tee plan.txt
grep -E "must be replaced|forces replacement" plan.txt

Common mistakes

  • Unpinned providers, so a major version arrives in a random pipeline run.
  • Applying replacements "because the provider says so".
  • Upgrading production first.
  • Upgrading Terraform and several providers at the same time.

How to answer in the interview

"I stop and don't apply. Major provider versions often rename arguments, change defaults, split one resource into several or change which arguments force replacement, so a plan full of replacements usually means the code needs adapting, not that the infrastructure needs rebuilding. I read the upgrade guide and changelog, go through the plan resource by resource, set changed defaults explicitly, move to new resource types with moved blocks or state migration, and remove deprecated settings, until the plan shows only intended changes, ideally none. I upgrade in a lower environment first, with the provider pinned and the lock file committed, so the upgrade is a deliberate pull request."

Likely follow-up questions

  • Splitting a large upgrade across many root modules? Batch by risk, Renovate PRs per configuration, CI plans, and a tracking dashboard.
  • Can you roll back a provider upgrade? Only if state schemas were not upgraded; otherwise restore state, so test first.
  • Why not upgrade Terraform at the same time? One change at a time makes diffs explainable.
