How do you control startup order and readiness in Docker Compose?

Docker · concept · levels mid

In one line

depends_on alone only orders container start; add a healthcheck and condition: service_healthy to wait for readiness, condition: service_completed_successfully for one-off jobs such as migrations, and still make apps retry connections.

Detailed explanation

A Postgres container "starts" in a fraction of a second, but the database needs several more seconds to initialise and accept connections. With a plain depends_on: [db], Compose starts db first and api immediately after, so the API often fails its first connection attempt and crashes.

Compose's long-form depends_on supports conditions. service_started is the default ordering. service_healthy waits until the dependency's healthcheck reports healthy, for example pg_isready for Postgres, redis-cli ping for Redis, or an HTTP health endpoint for another API. service_completed_successfully waits until a one-off container exits with code 0, perfect for a migration or seed job that must finish before the application starts. Options like restart: true restart dependants when the dependency is restarted by Compose, and required: false makes a dependency optional.

This is start-up ordering, not resilience. Databases restart, networks blip and dependencies are redeployed while the app is running. Applications should therefore retry connections with exponential backoff and expose their own readiness. That matters even more outside Compose: Kubernetes has no depends_on; it uses readiness probes, init containers and application retries instead, so code that only works because of Compose ordering breaks there.

How it works

  1. Compose builds a dependency graph from depends_on.
  2. It starts services without dependencies first.
  3. For service_healthy, it polls the dependency's health status.
  4. For service_completed_successfully, it waits for exit code 0.
  5. Only then are dependent services started; a failed condition aborts up.

Example

services:
  db:
    image: postgres:16
    environment: { POSTGRES_PASSWORD: dev }
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 3s
      retries: 10
  migrate:
    image: flyway/flyway:10
    command: -url=jdbc:postgresql://db:5432/postgres -user=postgres -password=dev migrate
    volumes: ["./db/migrations:/flyway/sql"]
    depends_on:
      db: { condition: service_healthy }
  api:
    build: .
    depends_on:
      db: { condition: service_healthy }
      migrate: { condition: service_completed_successfully }

Common mistakes

  • Assuming depends_on waits for readiness.
  • Old wait-for-it.sh hacks instead of healthchecks.
  • Healthchecks that pass before the service truly accepts work.
  • Apps that crash on the first failed connection instead of retrying.

How to answer in the interview

"depends_on on its own only orders container start, so the API may start while the database is still initialising. I give the database a healthcheck like pg_isready and declare depends_on with condition service_healthy, so the API starts only when the database is healthy. For one-off jobs like migrations I use service_completed_successfully, so the API waits until the migration container exits with zero. Even so, the application should retry connections with backoff, because dependencies restart later too, and Kubernetes has no depends_on at all."

Likely follow-up questions

  • How would you run migrations before the API? A migrate service with service_completed_successfully.
  • What replaces depends_on in Kubernetes? Readiness probes, init containers and retries.
  • What if the healthcheck never passes? docker compose up fails and reports the unhealthy dependency.
