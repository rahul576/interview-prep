What guardrails do you put around an LLM application?

LLMOps & RAG · concept · levels mid, senior

In one line

Guardrails are checks around the model, in code, not just prompt instructions: on input (prompt injection, jailbreaks, abuse, off-topic requests, PII redaction) and on output (harmful content, groundedness, schema validation, secret or system-prompt leakage, business rules), using tools like NeMo Guardrails, Guardrails AI, Llama Guard and provider safety filters, with graceful fallbacks and escalation.

Detailed explanation

Instructions in a system prompt are suggestions the model usually follows; guardrails are enforcement. They are implemented as deterministic code, classifiers or small models that run before and after the main model call.

Input guardrails:

  • Prompt injection and jailbreak detection, for example Azure AI Content Safety Prompt Shields, Llama Prompt Guard-style classifiers or provider filters.
  • Abuse and spam: rate limits, toxicity classifiers.
  • Scope/topic restriction: a banking assistant should decline medical or legal advice; a lightweight classifier or embedding-based router detects out-of-scope requests.
  • PII detection and redaction (Microsoft Presidio, cloud DLP services) before data reaches a third-party model, when policy requires it.

Output guardrails:

  • Harmful or inappropriate content filters, such as Llama Guard or provider content safety.
  • Groundedness checks against retrieved sources for factual answers.
  • Schema validation of structured output, with retry on failure.
  • Leakage: system prompt overlap, secrets, internal URLs, other customers' data.
  • Business rules: never promise refunds above a limit, never quote unapproved prices, required disclaimers.

Frameworks: NVIDIA NeMo Guardrails (programmable dialogue rails), Guardrails AI (validators on outputs), Llama Guard models, plus the content safety filters built into Azure OpenAI, Bedrock Guardrails and Vertex AI.

When triggered: respond gracefully (a safe message, a clarifying question, or handoff to a human), log the event for review, and tune thresholds using false positive and false negative rates.

How it works

  1. Request -> input checks (injection, scope, PII, abuse).
  2. Blocked -> safe message or escalation; else -> model.
  3. Response -> output checks (safety, groundedness, schema, leakage, rules).
  4. Failed -> regenerate, redact, or fall back.
  5. Log all triggers; review samples; tune.

Example

def guarded_answer(msg, user):
    if shields.injection_score(msg) > 0.8:
        return SAFE_REFUSAL
    if not scope_classifier.in_scope(msg):
        return "I can help with account and card questions only."
    msg = presidio_redact(msg)
    out = llm(msg)
    if not schema_ok(out) or leaks_system_prompt(out) or violates_rules(out):
        log_guardrail(user, msg, out)
        return handoff_to_agent(user)
    return out

Common mistakes

  • Relying only on "do not..." instructions in the prompt.
  • Guardrails so strict that legitimate users are blocked constantly.
  • No logging of triggers, so thresholds are never tuned.
  • Checking input only, not output.

How to answer in the interview

"Guardrails are checks in code around the model, not just prompt instructions. On input I detect prompt injection and jailbreaks, abuse, off-scope requests and redact personal data where policy requires. On output I filter harmful content, check groundedness against sources, validate structured output against schemas, block leakage of system prompts or secrets, and enforce business rules like refund limits. Tools include NeMo Guardrails, Guardrails AI, Llama Guard and the provider safety filters. When something triggers, the user gets a graceful fallback or a human, and every trigger is logged so we can tune false positives."

Likely follow-up questions

  • Avoid blocking legitimate requests? Measure false positive rates on real traffic, tune thresholds, prefer clarifying questions over hard refusals.
  • Latency cost? Run input checks in parallel with the main call; use small classifiers.
  • Streaming output? Check incrementally or buffer sentences before release.
