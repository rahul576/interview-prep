Why do LLMs struggle with tasks like exact arithmetic or counting, and how do applications compensate?

AI/ML & GenAI · concept · levels mid, senior

In one line

LLMs predict tokens rather than run arithmetic algorithms, and tokenisation hides individual digits and characters, so exact maths and counting are error-prone; applications compensate with calculator or code-execution tools, SQL for counts and aggregates, deterministic code for business calculations and validation of numeric outputs.

Detailed explanation

A language model generates the most likely next token given context. For "2 + 2" that is reliable because the pattern is everywhere, but for multiplying two seven-digit numbers, summing 200 values from a pasted table or computing a compound percentage, the model has no built-in arithmetic unit; it approximates, producing plausible-looking but wrong numbers, often with high confidence.

Tokenisation compounds this. Text is split into subword tokens, so "strawberry" may be two or three tokens and a number like 1234567 may be split into chunks like "123", "456", "7" depending on the tokenizer. The model doesn't directly see individual letters or digits, which is why counting letters in a word, reversing strings, counting words precisely or aligning digit columns is surprisingly hard. Long contexts make counting rows or occurrences unreliable too.

Reasoning models and step-by-step reasoning help significantly, since writing out intermediate steps breaks a calculation into small, more reliable pieces, but they still do not guarantee correctness, and they cost more tokens.

Robust applications therefore don't ask the model to do the maths. They give it tools: a calculator function or a sandboxed code-execution environment (Python) where it writes and runs code; SQL or API queries for counts, sums, averages and growth rates over real data rather than pasting a table into the prompt; and deterministic business code for taxes, prices, discounts, interest and invoices. The model's role is understanding the question, choosing the right tool, writing the query, and explaining results. Any number that matters is computed or validated in code, and financial or billing figures must never depend on the model's own arithmetic.

How it works

  1. The user asks a numeric question.
  2. The model decides it needs data or calculation and calls a tool (SQL, calculator, code sandbox).
  3. The tool computes exact results deterministically.
  4. The model explains the results in words, citing the figures returned.
  5. The application validates numbers (recomputes or checks consistency) before display.

Example

tools = [{
    "name": "run_sql",
    "description": "Run a read-only SQL query on the analytics warehouse",
    "input_schema": {"type": "object", "properties": {"query": {"type": "string"}},
                     "required": ["query"]},
}]
# Model generates, for "What was revenue growth last quarter?":
# SELECT SUM(CASE WHEN quarter='2026-Q3' THEN revenue END) /
#        SUM(CASE WHEN quarter='2026-Q2' THEN revenue END) - 1 AS growth FROM revenue_by_quarter;
# The application executes it with a read-only role and returns the exact value.

Common mistakes

  • Pasting a large CSV into the prompt and asking for totals.
  • Letting the model compute prices or invoice amounts.
  • Assuming a reasoning model is always numerically correct.
  • Giving the SQL tool write permissions.

How to answer in the interview

"LLMs generate likely tokens; they don't execute arithmetic, so large calculations can be plausible but wrong. Tokenisation hides individual digits and letters, which makes counting characters or digits surprisingly hard. Reasoning helps but doesn't guarantee correctness. So I give the model tools: a calculator or code sandbox for maths, SQL for counts and aggregates over real data, and deterministic code for business calculations like tax and pricing. Any important number is computed or validated in code, never trusted from the model alone."

Likely follow-up questions

  • Designing "what was our revenue growth last quarter?" Text-to-SQL on a semantic layer with a read-only role, exact computation in the database, and the model explaining the result with the query shown.
  • Why can't models count letters reliably? Tokens group several characters, so letters aren't directly visible.
  • How do you validate generated SQL? Read-only access, allow-listed tables, query limits and tests on known questions.
