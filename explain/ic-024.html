What do Ansible check mode and diff mode do?

Configuration Management · concept · levels entry

In one line

--check runs a dry run where modules report what they would change without changing anything, and --diff shows before/after content; useful for review and drift detection, but limited by module support and tasks depending on earlier changes.

Detailed explanation

Check mode asks each module to evaluate the current state and report whether it would change it, without acting. Diff mode makes modules that support it, like template, copy, lineinfile and file, print a unified diff of what would change. Run together, ansible-playbook site.yml --check --diff lets you see exactly what a playbook would do to production before running it for real, which is ideal for change reviews and for gaining confidence in an inherited playbook.

Run on a schedule, check mode turns Ansible into a drift detector: any task that reports "changed" in check mode means a host no longer matches the code. Because changed counts appear in the play recap, a CI job can parse them or use a callback to alert.

The limits are important:

  • Module support: modules that don't support check mode are skipped. command and shell cannot know what an arbitrary command would do, so they skip unless creates/removes let them decide.
  • Dependent tasks: if task 1 would install a package and task 2 configures it, task 2 may fail or report misleading results because the package was not really installed. Registered results from skipped tasks are also missing.
  • Overrides: check_mode: false on a task forces it to run for real even in check mode, useful for read-only commands whose output later tasks need; check_mode: true forces a task to always be a dry run. The variable ansible_check_mode lets tasks behave differently.
  • diff: false on a task hides sensitive content from diffs.

How it works

  1. Each module receives a check-mode flag.
  2. Supporting modules compute the difference and return changed/ok without acting.
  3. Unsupported modules are skipped.
  4. With --diff, modules return before/after content.
  5. The recap summarises what would change per host.

Example

ansible-playbook site.yml -i inventory/prod --check --diff --limit web
- name: Read current app version (safe, needed by later tasks)
  ansible.builtin.command: /opt/app/bin/app --version
  register: app_version
  changed_when: false
  check_mode: false

- name: Render secrets file
  ansible.builtin.template:
    src: secrets.env.j2
    dest: /etc/app/secrets.env
  diff: false

Common mistakes

  • Treating a clean check run as proof the real run will succeed.
  • Forgetting check_mode: false on read-only commands, breaking later tasks in check mode.
  • Showing secret file contents in diffs in CI logs.
  • Assuming shell tasks were validated when they were actually skipped.

How to answer in the interview

"With --check, a playbook does a dry run: modules report what they would change but change nothing, and --diff shows before and after content of files and templates. Together they let me review the effect on production before running it, and running them on a schedule makes Ansible a drift detector. The limits are that modules must support check mode, so shell and command tasks are skipped unless guarded, and tasks that depend on earlier changes can give misleading results because those changes didn't happen. I set check_mode: false on read-only tasks whose output is needed."

Likely follow-up questions

  • How would you use check mode in a CI pipeline? Run --check --diff on pull requests against staging/prod inventories and post the summary for review; schedule nightly runs for drift.
  • How do you hide secrets from diffs? diff: false and no_log: true on those tasks.
  • What is ansible_check_mode? A boolean telling tasks whether they run in check mode.
