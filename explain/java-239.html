What is the Java HttpClient, and how does it compare with older approaches?

Java 8+ Features · concept · levels mid, senior

In one line

java.net.http.HttpClient (standard since Java 11) is a modern, immutable, thread-safe client with HTTP/2, WebSocket, a fluent builder, and both synchronous send and asynchronous sendAsync (returning CompletableFuture); it replaces the clumsy HttpURLConnection, and should be created once and reused with timeouts configured.

Detailed explanation

Before Java 11 the JDK offered HttpURLConnection, a blocking, stateful API designed for HTTP/1.1 in the 1990s: awkward stream handling, poor error handling, no HTTP/2, and confusing connection reuse. Teams usually pulled in Apache HttpClient or OkHttp instead.

The new client is built from three types: HttpClient (configuration and connection pool), HttpRequest (immutable request built with a builder) and HttpResponse<T> with BodyHandlers (ofString, ofInputStream, ofFile, discarding) and BodyPublishers for request bodies. It negotiates HTTP/2 by default with fallback to HTTP/1.1, supports WebSocket, redirects policy, proxies, authenticators and custom SSLContext. sendAsync returns a CompletableFuture<HttpResponse<T>>, so you can fire many requests concurrently and compose results. Since Java 21 HttpClient implements AutoCloseable.

Because the client is immutable and thread-safe and holds the connection pool and selector threads, create one instance per configuration and reuse it; a new client per request wastes connections, TLS handshakes and threads. Always set a connectTimeout on the client and a request timeout; there is no default timeout. In Spring applications, RestClient (Spring 6.1) or WebClient are typical, and RestClient can use JdkClientHttpRequestFactory to run on top of this client. With virtual threads, the simple synchronous send scales well.

How it works

  1. Build a shared HttpClient with version, timeouts, redirect policy and executor.
  2. Build an HttpRequest with URI, headers, method, body publisher and timeout.
  3. Call send (blocking) or sendAsync (non-blocking).
  4. A BodyHandler converts the response body into the desired type.
  5. Check status codes yourself; non-2xx responses are not exceptions.

Example

private static final HttpClient CLIENT = HttpClient.newBuilder()
    .version(HttpClient.Version.HTTP_2)
    .connectTimeout(Duration.ofSeconds(3))
    .followRedirects(HttpClient.Redirect.NORMAL)
    .build();

HttpRequest req = HttpRequest.newBuilder(URI.create("https://api.example.com/orders/42"))
    .header("Accept", "application/json")
    .timeout(Duration.ofSeconds(5))
    .GET()
    .build();

HttpResponse<String> resp = CLIENT.send(req, HttpResponse.BodyHandlers.ofString());
if (resp.statusCode() != 200) throw new IllegalStateException("HTTP " + resp.statusCode());

CompletableFuture<String> async = CLIENT
    .sendAsync(req, HttpResponse.BodyHandlers.ofString())
    .thenApply(HttpResponse::body);

Common mistakes

  • Creating a new HttpClient per request.
  • No request timeout, so a slow server hangs threads.
  • Treating 4xx/5xx as exceptions; they're normal responses to check.
  • Reading huge bodies with ofString instead of streaming.

How to answer in the interview

"The java.net.http HttpClient, standard since Java 11, replaced HttpURLConnection. It supports HTTP/2 and WebSocket, has fluent builders, and offers a synchronous send and an async sendAsync that returns a CompletableFuture. The client is immutable and thread-safe and holds the connection pool, so I create it once and reuse it, and I always configure connect and request timeouts. In Spring I usually use RestClient or WebClient, and RestClient can run on top of the JDK client."

Likely follow-up questions

  • Why is creating a new HttpClient per request bad? It discards pooled connections and threads, forcing new TCP and TLS handshakes.
  • Does it throw on HTTP 500? No, you inspect statusCode().
  • How do you add retries? Wrap calls with a library like Resilience4j or Spring Retry, with backoff and idempotency in mind.
