A CI pipeline takes 35 minutes and developers start bypassing it. How do you speed it up?

CI/CD Tools · scenario · levels mid, senior

In one line

I speed up a slow pipeline by measuring first, then applying caching, parallelism and test sharding, fail-fast ordering, building only what changed and faster runners, aiming for a pull-request feedback loop of under about ten minutes.

Detailed explanation

When CI takes 35 minutes, developers merge with failing checks, batch changes into huge pull requests or ask for bypasses. Pipeline speed is therefore a quality issue, not cosmetics.

The first step is measurement: duration per job and step over a few weeks, the critical path, and queue time waiting for runners. The culprit is often surprising: 8 minutes of npm ci, a Docker build that never hits its layer cache, or one serial E2E suite.

Then the usual fixes. Caching: dependency caches keyed on the lock file, Docker layer caching with a sensible Dockerfile order and BuildKit cache exports, and remote build caches for Gradle, Bazel or Nx. Parallelism: lint, unit tests and scans as independent jobs, and large suites sharded across runners using timing data. Fail fast: cheap checks first. Do less: in a monorepo, test only affected projects, and move slow end-to-end suites to a merge queue, main or nightly. Infrastructure: bigger or autoscaled runners and images with tools preinstalled.

Flaky tests need separate handling: quarantine, track and fix them, because retries hide real failures.

How it works

  1. Collect job durations and queue times; identify the critical path.
  2. Fix caching: dependencies, Docker layers, build tool caches.
  3. Split into parallel jobs and shard long test suites.
  4. Reorder so lint and unit tests fail within a few minutes.
  5. Build and test only affected components; move slow suites later in the flow.
  6. Right-size runners and remove queue time.
  7. Keep a duration dashboard and treat regressions as bugs.

Example

# GitHub Actions: cached deps and four test shards
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix: { shard: [1, 2, 3, 4] }
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npx jest --shard=${{ matrix.shard }}/4

Result in a real case: dependency cache (-6 min), Docker layer cache (-7 min), four shards (-9 min), E2E moved to merge queue (-6 min): 35 down to about 8 minutes.

Common mistakes

  • Optimising by guesswork instead of data.
  • Simply adding retries, which hides flaky tests and adds time.
  • Dropping important tests rather than moving them later.
  • Ignoring queue time, which can exceed run time.

How to answer in the interview

"First I'd measure job by job, including queue time, to find the critical path. Then the standard wins: cache dependencies and Docker layers, run independent jobs in parallel and shard tests, and put lint and unit tests first so failures come back in minutes. In a monorepo I'd only test affected services, and slow end-to-end tests could move to a merge queue. I'd also right-size runners. My target is under ten minutes for pull requests, tracked on a dashboard so it doesn't creep back."

Likely follow-up questions

  • How do you handle flaky tests? Detect them from history, quarantine with an owner and deadline, fix the root cause; don't blanket-retry.
  • What is a merge queue? It tests each change against the latest main before merging, so slower checks run once per merge, not every push.
  • How do you split tests evenly? Use timing data from previous runs to balance shards by duration, not file count.
