How is an application deployed to development, staging, and production environments?

DevOps & CI/CD · scenario · levels mid

In one line

Build once and promote the same artifact through dev, staging and production; keep environment-specific config and secrets outside the image (profiles, Helm values, config server, secret managers); deploy automatically to dev, gated to staging and production; use rolling, blue-green or canary strategies; and verify with smoke tests, monitoring and rollback.

Detailed explanation

Same artifact: the image tested in staging is the exact one deployed to production, identified by tag or digest. Rebuilding per environment risks different dependencies or code.

Configuration: what differs between environments, such as URLs, pool sizes, feature flags and replica counts, lives in Spring profiles, Helm values files (values-dev.yaml, values-prod.yaml), Kustomize overlays, a config server or ConfigMaps. Secrets come from Vault, AWS Secrets Manager or Azure Key Vault, injected at runtime (for example External Secrets Operator).

Promotion flow:

  • Dev: automatic after merge to main, followed by smoke tests.
  • QA/staging: after automated tests pass, often automatic or one click; end-to-end and performance tests run here.
  • Production: after approval or a change ticket, sometimes within a release window, or automatically when guardrails are mature.

With GitOps, promotion is a commit updating the image tag in the environment's folder, which Argo CD or Flux syncs, giving an audit trail and easy rollback.

Strategies: rolling updates with readiness probes by default; blue-green to switch traffic instantly and back; canary to expose a small percentage of users first, using Argo Rollouts or a service mesh.

Verification: smoke tests, then monitoring of error rate, latency and saturation against SLOs, with automated or one-click rollback. Database migrations must be backward compatible (expand and contract) so old and new versions can run together.

How it works

  1. Merge builds and publishes one versioned image.
  2. Auto-deploy to dev; smoke tests.
  3. Promote to staging; full automated test suites.
  4. Approval or gate for production.
  5. Progressive rollout with health checks.
  6. Monitor; roll back on SLO breach.

Example

gitops-repo/
  orders/dev/values.yaml      image.tag: 3f9c2ab   (auto-updated by CI)
  orders/staging/values.yaml  image.tag: 3f9c2ab   (promotion PR, auto-merged after tests)
  orders/prod/values.yaml     image.tag: 1e77d10   (promotion PR needs approval)
helm upgrade --install orders ./chart -f values-prod.yaml --set image.tag=3f9c2ab --atomic --timeout 10m

Common mistakes

  • Different builds per environment.
  • Secrets in values files or images.
  • Staging that differs heavily from production.
  • Non-backward-compatible schema changes deployed with code.

How to answer in the interview

"We build the artifact once and promote that same image through environments, so what was tested is what goes live. Differences live outside the image: Spring profiles, Helm values per environment, and secrets from Vault or a cloud secret manager. Dev deploys automatically after merge; staging after automated tests pass; production after an approval or change ticket. In Kubernetes, Helm or Argo CD apply it with rolling updates, or blue-green and canary for risky changes. Each deployment is followed by smoke tests and monitoring of errors and latency, with automated or one-click rollback."

Likely follow-up questions

  • Database schema changes? Flyway or Liquibase with expand and contract, backward-compatible migrations.
  • Blue-green vs canary? Full switch with instant rollback versus gradual exposure with metric analysis.
  • How do you roll back in GitOps? Revert the commit; Argo CD syncs the previous version.
