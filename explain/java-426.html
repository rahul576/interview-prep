How would you design a file upload service that handles large files reliably?

System Design · design · levels senior, lead

In one line

Large uploads go directly to object storage via presigned URLs using multipart/resumable uploads, with metadata in a database, asynchronous scanning and processing triggered by completion events, limits enforced in the upload policy, and downloads served via CDN with signed URLs.

Detailed explanation

Streaming multi-gigabyte files through application servers ties up threads, memory and bandwidth, and a failure at 95% means starting again. The modern pattern makes the app a control plane only.

Presigned URLs: the client calls POST /uploads with filename, size and content type. The API authorises the user, creates a metadata record (PENDING), and returns presigned URLs for S3 multipart upload (or Azure Blob SAS with block blobs, or GCS resumable uploads). The client uploads parts (e.g. 8-100 MB each) in parallel directly to storage; failed parts are retried individually, and uploads can resume after a network drop. On completion the client calls CompleteMultipartUpload (or the API does) with the part ETags.

Validation and limits: presigned URLs expire quickly; a presigned POST policy can enforce max size and content type, and the object key is server-generated (tenant/user/uuid), never the user's filename. Configure lifecycle rules to abort incomplete multipart uploads after a day so orphaned parts do not cost money.

Async processing: a storage event (S3 Event Notifications -> SQS/EventBridge) triggers workers: malware scanning, verifying actual file type by magic bytes, checksums, thumbnails or transcoding. Until processing passes, the file stays in a quarantine prefix and status is PROCESSING; then AVAILABLE or REJECTED.

Downloads: served via CDN with signed URLs or cookies with short expiry, after an authorisation check in the API.

How it works

  1. Client: POST /uploads {name, size, type}.
  2. API: auth, quota check, create record, initiate multipart, return part URLs.
  3. Client uploads parts in parallel, retrying failures, then completes.
  4. Storage event -> queue -> scanner and processors.
  5. Metadata updated to AVAILABLE; event published for other services.
  6. Download: API checks permission, returns a short-lived CDN signed URL.

Example

CreateMultipartUploadResponse mpu = s3.createMultipartUpload(b -> b
        .bucket("uploads-quarantine").key(key).contentType(contentType));

List<URL> partUrls = IntStream.rangeClosed(1, partCount).mapToObj(n ->
        presigner.presignUploadPart(r -> r
            .signatureDuration(Duration.ofMinutes(15))
            .uploadPartRequest(p -> p.bucket("uploads-quarantine").key(key)
                                     .uploadId(mpu.uploadId()).partNumber(n)))
        .url()).toList();

fileRepo.save(new FileRecord(fileId, ownerId, key, size, Status.PENDING, mpu.uploadId()));
return new UploadInstructions(fileId, mpu.uploadId(), partUrls);

Common mistakes

  • Proxying large files through the API servers.
  • Using the client's filename as the storage key (overwrites, path tricks).
  • Making files available before scanning.
  • Long-lived or public URLs for private files.
  • Forgetting to clean up incomplete multipart uploads.

How to answer in the interview

"The application never streams large files itself. The client asks the API for presigned URLs and uploads directly to S3 using multipart upload, so parts upload in parallel and only failed parts retry. The API stores metadata like owner, size, type and status. When the upload completes, an S3 event triggers asynchronous virus scanning, type validation and thumbnails, after which the file becomes available. Size and type limits are enforced in the presigned policy and keys are server-generated. Downloads go through a CDN with short-lived signed URLs after an authorisation check."

Likely follow-up questions

  • Preventing access to others' files? Server-side ownership check before issuing signed URLs; private buckets; per-tenant prefixes.
  • Resuming after app restart? Store uploadId; ListParts shows completed parts.
  • Deduplication? Content hash (SHA-256) computed client-side or after upload.
