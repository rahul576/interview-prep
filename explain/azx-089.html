Your production chatbot on Azure OpenAI returns 429 Too Many Requests at peak times. How do you fix it?

Azure AI & Foundry · scenario · levels mid, senior

In one line

A 429 means the deployment exceeded its TPM or RPM quota (and TPM counts the requested max_tokens); fix it by retrying with backoff honouring retry-after, raising capacity (quota, Global deployments, APIM load balancing across regions), cutting tokens, and using provisioned throughput for steady peaks.

Detailed explanation

Each deployment has a quota in tokens per minute (TPM) and a derived requests per minute (RPM) limit. The service estimates token usage when the request arrives, using prompt tokens plus max_tokens (or the default), and rejects requests once the per-minute budget is used. So a chatbot sending max_tokens: 4000 for 300-token answers consumes its quota more than ten times faster than necessary.

Immediate fixes:

  • Client retries with exponential backoff and jitter, honouring the retry-after / retry-after-ms headers. The OpenAI SDKs do this with max_retries. Never retry in a tight loop; it makes throttling worse.
  • Right-size max_tokens to realistic answer lengths.

Capacity:

  • Request a quota increase in the portal.
  • Move to Global Standard (or Data Zone) deployments, which have much higher limits.
  • Put Azure API Management in front as an AI gateway: a backend pool of deployments in several regions or resources, with circuit breakers that skip a backend after 429s, plus token limit policies per consumer so one noisy client cannot starve the rest.

Reduce demand: shorter system prompts, fewer and smaller retrieved chunks, conversation history summarisation, prompt caching for stable prefixes, semantic caching at the gateway for repeated questions, and routing simple requests to a smaller model with its own quota.

Steady peaks: provisioned throughput with spillover gives guaranteed capacity.

How it works

  1. Check metrics: which deployment, TPM vs RPM, which client.
  2. Ensure clients back off correctly.
  3. Lower max_tokens and prompt size.
  4. Add capacity through quota, Global deployments or multiple backends behind APIM.
  5. Add per-consumer token limits and caching.
  6. Consider PTUs for predictable baseline.

Example

from openai import AzureOpenAI
client = AzureOpenAI(azure_endpoint=ENDPOINT, azure_ad_token_provider=token_provider,
                     api_version="2024-10-21", max_retries=5)   # backoff honours retry-after

resp = client.chat.completions.create(
    model="chat-global",
    messages=messages,
    max_tokens=500,           # realistic, not 4000
)
<!-- APIM: limit tokens per subscription -->
<azure-openai-token-limit counter-key="@(context.Subscription.Id)"
    tokens-per-minute="20000" estimate-prompt-tokens="true" />

Common mistakes

  • Retrying immediately without backoff, amplifying the problem.
  • Huge max_tokens values "just in case".
  • One deployment for every app, so batch jobs starve the chatbot.
  • Treating 429 as an outage rather than a capacity design issue.

How to answer in the interview

"A 429 means we hit the deployment's TPM or RPM quota, and TPM counts the requested max_tokens, not just actual tokens. First, clients must retry with exponential backoff honouring retry-after. Then I add capacity: a quota increase, a Global Standard deployment with higher limits, or API Management as an AI gateway balancing across deployments in several regions with failover on 429. I also cut tokens: shorter prompts, less context, realistic max_tokens, caching and smaller models for simple requests. For steady peaks, provisioned throughput with spillover."

Likely follow-up questions

  • Why does a high max_tokens hurt? Quota is reserved using max_tokens, so fewer requests fit per minute.
  • How to isolate tenants? Separate deployments or APIM token limits per subscription.
  • What about streaming? It improves perceived latency but not quota usage.
