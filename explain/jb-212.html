How would you design an API that processes millions of records?

System Design · design · levels senior, lead

In one line

Treat it as an asynchronous job: the client uploads input to object storage, the API returns 202 Accepted with a job ID and status endpoint, background workers process in chunks (Spring Batch or queue consumers) that are idempotent and restartable, partial failures go into an error report, and results come via download link, pagination or webhook.

Detailed explanation

A synchronous HTTP request cannot reliably process millions of records: gateways time out after 30-60 seconds, memory explodes if the whole payload is buffered, and a failure halfway leaves the client unsure what happened.

Input: instead of a giant JSON body, the client uploads a file (CSV, JSON Lines, Parquet) to S3 or Azure Blob via a presigned URL, or provides a reference. Then POST /jobs {inputUrl, type} creates a job record (QUEUED) and returns 202 Accepted with Location: /jobs/{id}.

Processing: workers stream the input (never load it fully) and process it in chunks of, say, 1,000 records, with batched database writes (JDBC batch, COPY). Spring Batch provides exactly this: chunk-oriented steps, commit intervals, skip/retry policies, and a job repository that records progress so a failed job restarts from the last committed chunk. For massive scale, split the file into partitions and fan out to multiple workers via a queue (Kafka, SQS) or Spring Batch partitioning.

Idempotency: retries must not duplicate data: use upserts on natural keys or record a processed-chunk checkpoint. Partial failures (invalid rows) are written to an error file with row number and reason rather than failing the whole job; a threshold can abort if errors exceed, say, 5%.

Results: clients poll GET /jobs/{id} (status, progress %, counts), receive a webhook when done, and download results or the error report via a signed URL. Support cancellation with a flag checked between chunks.

How it works

  1. Client gets a presigned URL and uploads the file.
  2. POST /jobs -> job row QUEUED -> message to queue -> 202 Accepted.
  3. Worker claims job, streams file, processes chunks, commits each with progress update.
  4. Invalid records go to an error report; transient errors retry.
  5. On completion: status COMPLETED/COMPLETED_WITH_ERRORS, results file written, webhook sent.
  6. Crash -> job restarts from last checkpoint.

Example

@PostMapping("/jobs")
ResponseEntity<JobView> submit(@RequestBody @Valid JobRequest req) {
    Job job = jobService.create(req.inputUrl(), req.type());    // status QUEUED, publishes message
    return ResponseEntity.accepted().location(URI.create("/jobs/" + job.id())).body(JobView.of(job));
}

@Bean
Step importStep(JobRepository repo, PlatformTransactionManager tx,
                FlatFileItemReader<CustomerRow> reader, ItemProcessor<CustomerRow, Customer> processor,
                JdbcBatchItemWriter<Customer> upsertWriter) {
    return new StepBuilder("import", repo)
        .<CustomerRow, Customer>chunk(1000, tx)
        .reader(reader).processor(processor).writer(upsertWriter)
        .faultTolerant().skip(ValidationException.class).skipLimit(10_000)
        .retry(TransientDataAccessException.class).retryLimit(3)
        .build();
}

Common mistakes

  • Accepting millions of records in one synchronous request.
  • Loading the whole file into memory.
  • One giant transaction that rolls back everything on one bad row.
  • Non-idempotent inserts that duplicate on restart.
  • No progress visibility for the client.

How to answer in the interview

"A synchronous request can't handle millions of records, so I make it an asynchronous job. The client uploads the file to object storage, then the API returns 202 Accepted with a job ID and a status endpoint. Background workers fed through a queue stream the input and process it in chunks with batched writes, using Spring Batch so each chunk commits independently and the job restarts from the last checkpoint. Processing is idempotent with upserts, bad rows go into an error report, and clients poll status or get a webhook, then download results."

Likely follow-up questions

  • Cancelling a running job? Set a CANCEL_REQUESTED flag checked between chunks; stop gracefully and report progress.
  • Scaling to faster processing? Partition the input and process partitions in parallel workers.
  • Ordering requirements? Partition by key so related records go to the same worker.
