How should human approvals work for MCP tool calls without causing approval fatigue?

MCP Servers · design · levels mid, senior

In one line

Make approvals risk-based: auto-approve read-only calls from trusted servers, confirm side effects, show the exact action, full arguments and target system, use thresholds (amount, environment) to escalate, avoid blanket "always allow" for destructive tools, and log every decision, because approval fatigue makes people click yes blindly.

Detailed explanation

Approvals are a key safety control in MCP hosts, but they only work if people actually read them. If an agent asks for confirmation on every file read and search, users see dozens of prompts per task, learn that the answer is always "yes", and start approving without looking. At that point the approval is worse than useless: it gives false assurance and shifts blame to the user.

The answer is to spend approvals where risk is. Read-only tools from trusted servers can be auto-approved, or approved once per session. Tools with side effects, such as sending messages, modifying data, spending money, deleting anything or touching production, require confirmation.

The prompt itself must be informative. Show the exact action, the full arguments (the recipient and message body, the SQL statement, the amount and account) and the target system and server, not just a tool name like execute. Allow the user to edit before approving.

Thresholds make approvals proportional: a refund under 20 euros or a change in a dev environment may proceed automatically, while larger amounts or production changes need approval, and the highest-risk actions need a second approver (four-eyes).

Hosts should not offer "always allow" for destructive tools, or should scope it narrowly (this tool, this argument pattern, this session). Every approval and denial is logged with user, time and arguments for audit. For unattended runs, approvals become queued proposals that a human reviews later.

How it works

  1. Each tool is classified: read, write, destructive, financial, external-communication.
  2. Policy maps class plus context (environment, amount, recipient domain) to auto, confirm or dual approval.
  3. Host renders confirmations with full arguments and target.
  4. User approves, edits or denies; decision is logged.
  5. Metrics track prompts per task and approval rates to detect fatigue.

Example

approval_policy:
  - match: { annotations.readOnlyHint: true, server_trust: trusted }
    action: auto
  - match: { tool: payments.refund, args.amount_lte: 20 }
    action: auto
  - match: { tool: payments.refund }
    action: confirm
  - match: { environment: prod, class: destructive }
    action: dual_approval
    always_allow: false

Common mistakes

  • Prompting for every call, including harmless reads.
  • Showing only the tool name, not arguments.
  • "Always allow" buttons on delete or send tools.
  • Trusting tool annotations like readOnlyHint from untrusted servers.

How to answer in the interview

"Approvals only protect people if they read them, so they have to be risk-based. Read-only tools from trusted servers are auto-approved, while tools with side effects, sending messages, changing data, spending money or touching production, need confirmation. The prompt shows the exact action, full arguments like the recipient and message text or the SQL, and the target system, not just a tool name. Thresholds help: a small refund or a dev change can proceed, larger amounts or production need approval or even a second approver. I avoid blanket always-allow for destructive tools. If users see dozens of prompts per task they click yes blindly, which is worse than fewer meaningful prompts. All approvals are logged."

Likely follow-up questions

  • Unattended overnight runs? Queue proposed actions as PRs or tickets for morning review.
  • Can you trust annotations? Only from trusted servers; they are hints, not guarantees.
  • How do you measure fatigue? Prompts per task, time to approve, near-100% approval rates.
