Your container exits immediately after starting. How do you find out why?

Docker · scenario · levels entry

In one line

A container lives only as long as its main process, so check the exit code with docker ps -a, read docker logs, inspect CMD/ENTRYPOINT with docker inspect, and reproduce interactively with --entrypoint sh.

Detailed explanation

"Exits immediately" has two very different causes. Either the main process crashed (an error, a missing file, a failed connection), or it finished normally because nothing is keeping it in the foreground. Docker does not care whether the process is a server; when PID 1 exits, the container stops.

First, docker ps -a shows the status and exit code. Code 0 points to "finished normally", 1 or other small codes to an application error, 127 to "command not found", 126 to "not executable", 137 to SIGKILL (often an OOM kill), and 139 to a segfault. Second, docker logs shows what the process wrote to stdout and stderr before it died; this works on stopped containers. Typical messages are a missing environment variable, a database that cannot be reached, a permission error on a mounted volume, or a typo in the command.

For the "finished normally" case, look at how the process starts: a script that launches the service with & or a daemonising service such as nginx without daemon off; returns immediately, and running bash without -it exits because there is no terminal. docker inspect shows the effective Entrypoint, Cmd, environment, mounts and State.OOMKilled. Finally, start the image with a shell instead of the real command, docker run -it --entrypoint sh image, and run the start command by hand to see the error in context. Architecture mismatches (an amd64 image on arm64) show up as "exec format error".

How it works

  1. docker ps -a and note the exit code.
  2. docker logs <id> for the last output.
  3. docker inspect for command, env, mounts, OOMKilled.
  4. Override the entrypoint with a shell and run the command manually.
  5. Fix the Dockerfile or configuration and rebuild.

Example

docker ps -a --filter name=api --format '{{.Status}}'
# Exited (1) 3 seconds ago
docker logs api
docker inspect -f '{{.Config.Entrypoint}} {{.Config.Cmd}} {{.State.OOMKilled}}' api
docker run -it --rm --entrypoint sh registry.local/api:1.4
/ # /entrypoint.sh java -jar /app.jar

Common mistakes

  • Adding tail -f /dev/null to keep the container alive instead of fixing the foreground process.
  • Restarting repeatedly without reading the logs.
  • Ignoring the exit code, which narrows the cause instantly.
  • Forgetting the image may have no shell (distroless); use a debug variant.

How to answer in the interview

"A container lives only as long as its main process. First I run docker ps -a to see the exit code and docker logs to see what it printed before dying, often a missing environment variable, a failed database connection or a typo. A very common cause is that the main process finished on purpose, for example the script started the service in the background, or the command was bash without a terminal. I check CMD and ENTRYPOINT with docker inspect, also whether it was OOM killed, and then run the image with --entrypoint sh to execute the start command manually and see the error directly."

Likely follow-up questions

  • What do 0, 1, 137 and 143 mean? Success, app error, SIGKILL or OOM, SIGTERM.
  • How do you debug a distroless image? Use the :debug variant or attach a debug container sharing its namespaces.
  • What is "exec format error"? The binary is built for another CPU architecture.
