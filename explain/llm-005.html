Compare popular LLM serving engines such as vLLM, TGI, TensorRT-LLM, SGLang, Ollama and llama.cpp.

LLMOps & RAG · concept · levels mid, senior

In one line

vLLM is the default high-throughput open GPU server, TensorRT-LLM gives peak NVIDIA performance at build complexity, SGLang excels at prefix reuse and structured generation, TGI is Hugging Face's server now in maintenance mode, and llama.cpp/Ollama serve quantised GGUF models locally on CPUs and Apple silicon; choose by hardware, models, performance and operations.

Detailed explanation

vLLM: PagedAttention, continuous batching, chunked prefill, prefix caching, speculative decoding, multi-LoRA, many quantisation formats, tensor/pipeline/expert parallelism and an OpenAI-compatible API. Supports NVIDIA, AMD, Google TPU and other accelerators, and gets new open models quickly. It is my default for self-hosting because it balances performance, breadth and ease of use.

TensorRT-LLM (NVIDIA): compiles or optimises models with fused kernels, in-flight batching, FP8 and FP4 on recent GPUs, and is commonly served through Triton Inference Server or NVIDIA's NIM containers and Dynamo framework. It often achieves the best latency and throughput on NVIDIA hardware, but involves more build and configuration steps per model and GPU type, and is NVIDIA-only.

SGLang: a fast engine with RadixAttention for automatic prefix reuse across requests, efficient constrained decoding for JSON and grammars, and strong performance for agentic and multi-call workloads; widely used for large models such as DeepSeek-style mixture-of-experts.

Hugging Face TGI: one of the first production servers, with Rust routing and good Hub integration. Hugging Face put it in maintenance mode in 2025 and points users to vLLM and SGLang, so I would not pick it for new projects.

llama.cpp: C/C++ inference for GGUF quantised models (2 to 8-bit) on CPUs, Apple Metal, CUDA and Vulkan, ideal for laptops, edge and air-gapped boxes. Ollama wraps it with model pulling, a local API and simple management, great for developers but not designed for high-concurrency serving.

How to choose: target hardware; models and quantisation formats supported; required features (LoRA, structured output, long context); measured throughput and latency on your traffic; and operational fit (Kubernetes support, metrics, upgrades, community).

How it works

  1. List hardware and models you must run.
  2. Shortlist engines that support them.
  3. Benchmark with your prompt/output length distribution and concurrency.
  4. Compare TTFT, inter-token latency, goodput and cost per million tokens.
  5. Factor in operational effort and pick, keeping an OpenAI-compatible interface for portability.

Example

vllm serve mistralai/Mistral-7B-Instruct-v0.3 --port 8000
python -m sglang.launch_server --model-path Qwen/Qwen2.5-7B-Instruct --port 30000
ollama run llama3.1:8b
./llama-server -m model-Q4_K_M.gguf -c 8192 --port 8080

Common mistakes

  • Picking an engine from a vendor benchmark with different workloads.
  • Running Ollama as a production multi-user backend.
  • Choosing TensorRT-LLM without NVIDIA expertise in the team.
  • Starting new projects on a maintenance-mode server.

How to answer in the interview

"vLLM is my default for GPU self-hosting: PagedAttention, continuous batching, broad model and quantisation support and an OpenAI-compatible server. TensorRT-LLM from NVIDIA usually gives the best performance on NVIDIA GPUs but needs a more involved build, often behind Triton. SGLang is very fast with strong prefix caching and structured generation, which suits agent workloads. TGI was an early production server but is now in maintenance mode. For local, CPU or Apple silicon use, llama.cpp runs GGUF quantised models and Ollama wraps it nicely. I choose by hardware, models, measured performance and operational effort."

Likely follow-up questions

  • Benchmark fairly? Same model, precision, hardware, realistic length distribution and concurrency; compare goodput at SLO.
  • Why keep an OpenAI-compatible API? Swap engines or providers without client changes.
  • Where does Triton fit? A model server that hosts TensorRT-LLM and other backends.
