When do you choose Bash versus Python versus Go for automation?

Scripting · concept · levels mid, senior

In one line

Use Bash as glue for short command orchestration, Python for complex logic, APIs, data handling and tests, and Go for single static binaries, CLIs, Kubernetes controllers and performance-sensitive agents; decide by maintainability, error handling, testing and who maintains it.

Detailed explanation

Bash is everywhere and ideal for gluing commands together: a CI step, a container entrypoint, file shuffling, calling kubectl or terraform a few times. It has no real data structures beyond arrays and associative arrays, string-based error handling, and many traps (quoting, word splitting, set -e exceptions). Beyond roughly a hundred lines, or once you parse JSON, retry API calls or need tests, Bash becomes fragile.

Python is the default for "real" automation: cloud SDKs like boto3, the Azure SDK and Google Cloud libraries, rich JSON, YAML and HTTP handling, proper exceptions, and testing with pytest. It reads well for teams with mixed experience. The trade-offs are runtime and dependency management: you need the right interpreter and packages, solved with virtual environments, uv or pipx, or a container image.

Go compiles to a single static binary with no runtime dependencies, starts instantly, cross-compiles easily and has strong concurrency. It is the language of the Kubernetes ecosystem, so operators and controllers (controller-runtime, client-go), CLIs distributed to many users, and agents running on thousands of hosts are natural fits. It is more verbose for quick tasks.

The decision is less about the language than about maintainability: who will own it, how errors are handled, whether it needs tests, how it is distributed, and what the team already knows. Whatever the choice, scripts should be idempotent, logged and version-controlled.

How it works

  1. Estimate size and complexity: a few commands or real logic?
  2. Check needs: APIs, data parsing, concurrency, distribution.
  3. Consider the team's skills and the maintainer.
  4. Pick Bash, Python or Go accordingly.
  5. Add linting, tests and CI regardless of choice.

Example

# Bash: glue in a CI step
set -euo pipefail
terraform -chdir=infra plan -out=plan.tfplan
terraform -chdir=infra show -json plan.tfplan > plan.json
# Python: logic plus a cloud API
import boto3
ec2 = boto3.client("ec2")
for r in ec2.describe_instances(Filters=[{"Name": "tag:env", "Values": ["dev"]}])["Reservations"]:
    for i in r["Instances"]:
        if "owner" not in {t["Key"] for t in i.get("Tags", [])}:
            print("untagged owner:", i["InstanceId"])

Common mistakes

  • Growing a Bash script to 800 lines with JSON parsing in sed.
  • Writing a Go program for a three-line task.
  • Shipping Python tools without pinned dependencies.
  • Choosing a language nobody else on the team can maintain.

How to answer in the interview

"Bash is ideal as glue for short scripts orchestrating commands, like a CI step, but beyond about a hundred lines it gets fragile because error handling and data structures are weak. Python is my choice for complex logic, cloud APIs with boto3 or the Azure SDK, JSON parsing and tested code. Go suits tools that should ship as a single static binary, CLIs, Kubernetes operators and performance-sensitive agents. The deciding factors are maintainability, error handling, tests, distribution and who will maintain it."

Likely follow-up questions

  • What makes an automation script safe to run twice? Idempotency: check current state before changing, use declarative APIs and unique request IDs.
  • How do you distribute Python tools? Pinned dependencies with pipx or uv, or a container image.
  • When do you replace a script with Terraform or Ansible? When it manages infrastructure state that a declarative tool can own.
