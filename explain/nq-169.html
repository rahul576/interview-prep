What is the role of volatile in Java memory visibility?

JVM & Performance · concept · levels mid, senior

In one line

volatile gives a field visibility and ordering guarantees under the Java Memory Model: a write to it happens-before every later read of it, but it does not make compound actions like count++ atomic.

Detailed explanation

The Java Memory Model (JMM) allows compilers, the JIT and CPUs to keep values in registers or caches and to reorder reads and writes, as long as a single thread cannot tell. Across threads this means one thread may never see another thread's update, or may see writes in a surprising order. The JMM only guarantees visibility when there is a happens-before relationship, created by locks, thread start/join, final fields, concurrent collections, or volatile.

For a volatile field, the JMM says a write happens-before every subsequent read of that same field. The JVM implements this with memory barriers: reads cannot be served from a stale register, and ordinary reads and writes cannot be reordered across the volatile access in a way that breaks the guarantee. A powerful consequence is piggybacking: everything the writer did before the volatile write becomes visible to a thread that reads the new value. That is why a volatile ready flag can safely publish an object that was fully built before the flag was set.

What volatile does not give is atomicity of read-modify-write sequences. count++ is a read, an add and a write; two threads can read the same value and both write n+1. For that you need synchronized, a Lock, or AtomicInteger/LongAdder. Reads and writes of volatile long and double are, however, guaranteed atomic.

How it works

  1. Thread A writes normal fields (builds the config object).
  2. Thread A writes the volatile field (release semantics).
  3. Thread B reads the volatile field and sees the new value (acquire semantics).
  4. Because of happens-before, B also sees all of A's earlier writes.
  5. Without volatile, B could loop forever on a cached value or see a half-initialised object.

Example

class Worker implements Runnable {
    private volatile boolean running = true;   // visibility for stop signal
    private volatile Config config;            // safe publication

    public void stop() { running = false; }
    public void reload(Config c) { config = c; } // c fully built before this write

    public void run() {
        while (running) {                      // always reads latest value
            process(config);
        }
    }
}

// NOT thread-safe even if volatile:
volatile int hits;
void hit() { hits++; }           // use AtomicInteger.incrementAndGet() instead

Double-checked locking for a lazy singleton is also only correct when the instance field is volatile.

Common mistakes

  • Using volatile for counters or check-then-act logic.
  • Thinking volatile is only about "CPU caches"; reordering by the JIT matters just as much.
  • Making a reference volatile and assuming the object's later mutations are visible; only writes before the volatile write are published.
  • Forgetting volatile in double-checked locking.

How to answer in the interview

"Under the Java Memory Model, threads may see stale values and operations may be reordered unless there is a happens-before relationship. Declaring a field volatile creates one: a write to it happens-before every later read of that field, so readers always see the latest value, and also everything the writer did before that write. That makes it ideal for stop flags and for safely publishing an immutable object. It does not make count++ atomic, so for counters I use AtomicInteger or LongAdder, and for multi-field invariants a lock."

Likely follow-up questions

  • What is safe publication? Making an object visible to other threads only after full construction, via volatile, final fields, locks or concurrent collections.
  • Why does double-checked locking need volatile? Without it, another thread may see a non-null reference to a partially constructed object.
  • volatile vs AtomicInteger? Atomic adds CAS-based atomic read-modify-write on top of volatile semantics.
