What is a race condition, and how can it occur?

Concurrency · concept · levels entry

In one line

A race condition occurs when the correctness of a result depends on the timing or interleaving of threads accessing shared data; typical forms are read-modify-write (count++) and check-then-act (if absent, put), fixed by making the compound action atomic.

Detailed explanation

The scheduler can pause a thread between any two instructions and run another. When several threads touch shared mutable data, some interleavings produce wrong results. Because the bad interleaving is rare, race conditions often pass tests and appear only under production load.

Read-modify-write. count++ compiles to three steps: read count, add one, write it back. Thread A reads 5, thread B reads 5, both write 6: one increment is lost. Bank balances (balance = balance - amount) suffer the same problem, which can create money out of thin air or allow overdrafts.

Check-then-act. The decision is based on an observation that may be out of date by the time you act. if (!map.containsKey(k)) map.put(k, v) lets two threads both see "missing" and both insert. Lazy initialisation (if (instance == null) instance = new Service()) can create two singletons. Checking a file exists and then opening it is a time-of-check to time-of-use (TOCTOU) race.

Note the difference from a data race, a Java Memory Model term for conflicting accesses not ordered by happens-before. They overlap but are not identical: a program can be free of data races (every access is synchronised) yet still contain a race condition if a compound action spans two separate synchronised calls.

Fixes: make the whole compound action atomic. Use synchronized or a Lock around it, atomic classes (AtomicInteger.incrementAndGet, compareAndSet), or atomic methods of concurrent collections (putIfAbsent, computeIfAbsent, merge). For lazy singletons use the holder idiom or an enum. In databases, use conditional updates, row locks or optimistic locking.

How it works

  1. Two threads share mutable state.
  2. Each performs a multi-step operation (read then write, or check then act).
  3. The scheduler interleaves the steps.
  4. One thread acts on stale information and overwrites or duplicates the other's work.
  5. Making the steps atomic removes the harmful interleavings.

Example

class Counter {
    private int count;
    void increment() { count++; }                 // race: read-add-write
}

Counter c = new Counter();
try (var pool = Executors.newFixedThreadPool(8)) {
    for (int i = 0; i < 100_000; i++) pool.execute(c::increment);
}
System.out.println(c.count);                      // often < 100000

// Fixes
AtomicInteger safe = new AtomicInteger();
safe.incrementAndGet();                            // atomic CAS

ConcurrentHashMap<String, Session> sessions = new ConcurrentHashMap<>();
sessions.computeIfAbsent(userId, Session::new);   // atomic check-then-act

Common mistakes

  • Believing volatile fixes count++.
  • Using a thread-safe map but doing containsKey then put separately.
  • Assuming a test passing once proves there is no race.
  • Locking the write but not the read that decides it.

How to answer in the interview

"A race condition happens when the correctness of a result depends on the unpredictable interleaving of threads using shared data. The classic example is count++, which is really read, add one, write back, so two threads can both read 5 and both write 6, losing an update. Another is check-then-act, like containsKey followed by put, where two threads both see the key missing. Lazy singleton creation and balance updates have the same problem. I fix it by making the compound action atomic: synchronized or a Lock, AtomicInteger.incrementAndGet, or atomic methods like ConcurrentHashMap.computeIfAbsent."

Likely follow-up questions

  • How would you reproduce a race condition in a test? Run many threads hammering the operation, start them together with a CountDownLatch, repeat many times, and assert the total; tools like jcstress help for low-level cases.
  • What is the difference between a race condition and a data race? A data race is unsynchronised conflicting access in JMM terms; a race condition is any timing-dependent bug, which can exist even without data races.
  • How do databases avoid lost updates? Conditional updates, SELECT ... FOR UPDATE, or optimistic locking with a version column.
