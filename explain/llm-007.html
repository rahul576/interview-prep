How do you autoscale LLM inference on Kubernetes, and why is CPU a poor scaling signal?

LLMOps & RAG · concept · levels senior, lead

In one line

Scale LLM inference on engine metrics such as queue depth, running requests, KV cache utilisation or TTFT via KEDA or custom-metric HPA, not CPU, because GPU-bound pods show flat CPU; and because GPU nodes and model loading take minutes, keep warm capacity, scale early, and use load-aware gateways.

Detailed explanation

An LLM server's work happens on the GPU. The CPU only handles HTTP, tokenisation and scheduling, so CPU usage stays low and barely moves as load doubles: a CPU-based HPA never fires, or fires for the wrong reasons. Even GPU utilisation is a weak signal: it shows 100 percent busy at moderate load while latency keeps climbing as batches grow and queues form.

Better signals come from the serving engine. vLLM exports Prometheus metrics such as vllm:num_requests_waiting, vllm:num_requests_running, KV cache usage and TTFT histograms; TGI, SGLang and Triton expose similar ones. Scale out when waiting requests stay above zero, KV cache usage approaches 90 percent, or p95 TTFT approaches its SLO. Wire them into KEDA with a Prometheus scaler, or an HPA with custom metrics via Prometheus Adapter.

The hard part is slow scale-up. A new GPU node can take several minutes to provision (if capacity is available at all), the container image is often many gigabytes, and loading 20 to 150 GB of weights plus engine warmup adds more. A reactive autoscaler therefore arrives after the spike. Countermeasures: warm replicas for normal peaks, lower thresholds, schedule-based pre-scaling, placeholder pods holding spare GPU nodes, and fast model loading from node-local caches. Priority classes and admission control keep interactive traffic ahead of batch jobs during spikes, and overflow can go to a hosted API.

Routing matters too. Round-robin load balancing sends requests to busy replicas while others are free, and ignores which replica already has a matching prefix cached. Inference gateways, such as the Kubernetes Gateway API Inference Extension, llm-d's scheduler, or NVIDIA Dynamo's router, pick endpoints by queue length, KV utilisation and prefix-cache affinity.

How it works

  1. Engine exports queue, running and KV metrics.
  2. Prometheus scrapes them; KEDA evaluates thresholds.
  3. KEDA raises replicas; pending pods trigger GPU node provisioning.
  4. New pods load weights from cache and pass readiness only when serving.
  5. Gateway routes by load and prefix affinity; scale-down uses long stabilisation windows.

Example

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata: { name: llm-chat }
spec:
  scaleTargetRef: { name: vllm-llama70b }
  minReplicaCount: 2
  maxReplicaCount: 12
  cooldownPeriod: 900
  triggers:
    - type: prometheus
      metadata:
        serverAddress: http://prometheus:9090
        query: sum(vllm:num_requests_waiting{deployment="vllm-llama70b"})
        threshold: "5"

Common mistakes

  • CPU-based HPA for GPU workloads.
  • Scaling to zero for latency-sensitive chat.
  • Aggressive scale-down that removes warm GPUs minutes before the next peak.
  • Plain round-robin load balancing across replicas.

How to answer in the interview

"An LLM server spends its time on the GPU, so CPU barely changes with load, and even GPU utilisation saturates early while latency keeps getting worse. I scale on engine metrics instead: requests waiting, running requests, KV cache utilisation or TTFT nearing the SLO, exported by vLLM to Prometheus and used through KEDA or a custom-metrics HPA. Because a GPU node and model loading can take many minutes, I keep warm replicas, scale earlier at lower thresholds, cache weights on nodes and prioritise interactive traffic. And I use a load-aware inference gateway that routes by queue and prefix cache."

Likely follow-up questions

  • Spike while nodes start? Queue with priorities, shed batch traffic, degrade to a smaller model or overflow to an API.
  • Why long scale-down windows? Re-acquiring GPUs is slow and capacity may vanish.
  • What is prefix-aware routing? Sending requests with the same prefix to the replica that already caches it.
