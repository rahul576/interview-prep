Which tools do you use to troubleshoot network connectivity?

Networking · concept · levels entry, mid

In one line

Work up the layers: ping and traceroute/mtr for reachability and path, dig/nslookup for DNS, nc/telnet/curl for ports and HTTP, ss for listening sockets on the server, and tcpdump/Wireshark to see actual packets.

Detailed explanation

  • ping sends ICMP echo requests: basic reachability and round-trip time. Many cloud security groups and firewalls block ICMP, so no reply doesn't prove the host is down.
  • traceroute / tracepath / mtr show each router hop and where packets are lost or delayed. mtr combines ping and traceroute continuously and is great for intermittent packet loss. traceroute -T -p 443 uses TCP when ICMP or UDP probes are filtered.
  • dig / nslookup verify DNS: which IP a name resolves to, from which resolver, TTLs and errors like NXDOMAIN or SERVFAIL.
  • nc (netcat) tests a TCP port: nc -vz host 5432. telnet does similarly where installed. curl -v shows DNS resolution, TCP connect, the TLS handshake and certificate, request and response headers and status codes; curl --resolve tests a specific IP without changing DNS; -w prints timing breakdowns. openssl s_client inspects certificates and TLS in detail.
  • ss -tulpn (or netstat) on the server shows listening sockets and owning processes; a service bound to 127.0.0.1 is not reachable from outside. ip addr and ip route check interface addresses and routes.
  • tcpdump captures packets: whether SYNs arrive, whether SYN-ACKs or RSTs are sent back, and DNS queries. Save with -w and open in Wireshark for analysis.
  • Cloud tools add visibility: VPC flow logs, AWS Reachability Analyzer, Azure Network Watcher; in Kubernetes, kubectl exec or an ephemeral debug container such as nicolaka/netshoot with all these tools.

The key is to test from the same place as the failing client (same host, pod or subnet), because security rules and DNS differ by location.

How it works

  1. Resolve: dig the hostname.
  2. Reach: ping or mtr to the IP (knowing ICMP may be blocked).
  3. Port: nc or curl to the service port.
  4. Server: ss to check listening; check local firewall.
  5. Packets: tcpdump on both sides to see where traffic stops.

Example

dig +short api.internal
mtr -rwc 20 10.0.2.15
nc -vz -w 3 10.0.2.15 8443
curl -sv --resolve api.internal:8443:10.0.2.15 https://api.internal:8443/health
sudo ss -tlnp | grep 8443                                  # on the server
sudo tcpdump -ni eth0 'tcp port 8443 and tcp[tcpflags] & (tcp-syn|tcp-rst) != 0'
kubectl debug -it pod/web --image=nicolaka/netshoot

Common mistakes

  • Concluding a host is down because ping fails.
  • Testing from a laptop rather than the affected network.
  • Not checking the listening address.
  • Running tcpdump without filters on busy hosts.

How to answer in the interview

"I work up the layers. ping checks basic reachability, knowing ICMP is often blocked, and traceroute or mtr show the path and where packets drop. dig or nslookup check DNS. To test a port I use nc -vz or telnet, and for HTTP curl -v shows the TLS handshake, headers and status. On the server, ss -tulpn shows whether the service listens and on which interface, because a service bound to localhost isn't reachable from outside. If it's still unclear, tcpdump shows whether packets arrive and what comes back, and I can open the capture in Wireshark."

Likely follow-up questions

  • Firewall drop versus closed port? A drop gives a timeout with no response; a closed port returns a TCP RST, so "connection refused" immediately.
  • How do you debug from inside a Kubernetes pod without tools? kubectl debug with an ephemeral netshoot container.
  • What does mtr add over traceroute? Continuous per-hop loss and latency statistics.
