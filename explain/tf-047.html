Your scheduled drift detection should alert when production differs from code. How do you build it?

Terraform · scenario · levels mid, senior

In one line

Run a scheduled plan per production state with read-only credentials, use -detailed-exitcode (exit code 2 means changes), combine a normal plan and a refresh-only plan, alert with a summary, and triage each drift: revert or codify.

Detailed explanation

Drift is any difference between code and reality. It comes from manual portal changes, scripts, policies or autoscalers, and from merged code that was never applied. A nightly pipeline detects it before it surprises the next deployment.

The key mechanism is terraform plan -detailed-exitcode: exit code 0 means no changes, 1 means an error, 2 means the plan contains changes. The job can then distinguish "clean", "broken" and "drifted" without parsing text.

Two plan types answer different questions. A normal plan shows everything an apply would do, including unapplied code changes. A refresh-only plan (-refresh-only) only shows how real objects differ from the last state, which isolates changes made outside Terraform. Running both tells you whether the problem is unapplied code or out-of-band change.

The job should use a read-only identity (for example Reader on the subscription plus state read access) and should never have apply rights; a detector that can apply could revert an emergency fix or be abused. On drift it posts to the team channel or opens a ticket with a summary from terraform show -json: which resources, which attributes. Then someone triages: an intentional change is codified in a PR; an unintended one is reverted with a normal reviewed apply. HCP Terraform health assessments provide built-in drift detection if you use that platform.

How it works

  1. Scheduler triggers per state (matrix of production stacks).
  2. init with read-only backend access; plan -refresh-only -detailed-exitcode.
  3. Optional second normal plan to catch unapplied code.
  4. Exit 2: build a summary from the JSON plan.
  5. Alert or create a ticket with owners and resource list.
  6. Triage: codify or revert; track recurring sources of drift.

Example

set +e
terraform plan -refresh-only -detailed-exitcode -lock=false -out=drift.plan
rc=$?
set -e
if [ "$rc" -eq 2 ]; then
  terraform show -json drift.plan \
    | jq -r '.resource_drift[] | "\(.address): \(.change.actions | join(","))"' > drift.txt
  ./notify-teams.sh "Drift in prod-network" drift.txt
elif [ "$rc" -eq 1 ]; then
  exit 1
fi

Common mistakes

  • Giving the drift job write credentials.
  • Alerting on noisy perpetual diffs until people ignore the channel.
  • Only running a normal plan and confusing unapplied code with manual drift.
  • Holding the state lock during long scheduled plans; use -lock=false for read-only checks.
  • No owner for triage, so alerts pile up.

How to answer in the interview

"I schedule a nightly plan for each production state with read-only credentials. With -detailed-exitcode, exit code 2 means changes, 1 means error, so the job can tell drift from failure. I use a refresh-only plan to isolate out-of-band changes, and sometimes a normal plan to catch merged but unapplied code. When drift is found, the job posts a summary built from terraform show -json to the team channel or a ticket. Someone triages it: codify it if it was intentional, or revert it with a reviewed apply. HCP Terraform has this built in as health assessments."

Likely follow-up questions

  • Why should the drift job never apply? It could revert an emergency fix and is a high-value credential.
  • How do you cut noise? Fix perpetual diffs and use ignore_changes only for legitimately external attributes.
  • Where is drift in the JSON? In resource_drift for refresh-only results, resource_changes for planned changes.
