How do you manage multiple environments and clusters with kubectl and Kustomize safely?

Kubernetes · concept · levels mid, senior

In one line

Work safely across clusters by making the current context obvious (kubeconfig contexts, kubectx/kubens, a prompt showing the cluster), separating environments by cluster and namespace, keeping one Kustomize base with per-environment overlays, and removing manual changes from production through GitOps and read-only human access.

Detailed explanation

kubectl talks to whatever current context in the kubeconfig points to: a combination of cluster, user and default namespace. The biggest operational risk is not YAML errors but running a correct command against the wrong cluster, for example a delete meant for staging that hits production. So safety starts with visibility and friction: tools such as kubectx and kubens to switch deliberately, a shell prompt (kube-ps1, Starship) showing context and namespace in red for production, separate kubeconfig files per environment loaded via KUBECONFIG instead of one giant file, and never relying on a default namespace in scripts.

For manifests, Kustomize avoids copy-pasting YAML. A base holds the common Deployment, Service and config; each overlay (dev, staging, prod) patches only what differs: replicas, resource requests, image tag, ingress host, ConfigMap values. Because overlays are small, reviewers see exactly what is different in production. kubectl kustomize or kustomize build renders the result so you can diff it.

Within a cluster, namespaces separate teams and environments, with RBAC, quotas and NetworkPolicies per namespace. For production, the strongest control is to stop humans changing it directly: GitOps tools such as Argo CD or Flux apply what is merged in Git, humans get read-only roles by default, and break-glass write access is time-limited and audited.

How it works

  1. One kubeconfig per cluster; contexts named clearly (prod-eu, staging-eu).
  2. Prompt shows context and namespace; production coloured red.
  3. Repository has base/ and overlays/<env>/.
  4. Pull request changes an overlay; CI renders and diffs it.
  5. Argo CD or Flux syncs the overlay to the matching cluster.
  6. Humans use view roles in prod; emergency access via an audited elevation.

Example

apps/orders/
  base/        deployment.yaml service.yaml kustomization.yaml
  overlays/
    staging/   kustomization.yaml   (replicas: 2)
    prod/      kustomization.yaml   (replicas: 6, higher limits)
# overlays/prod/kustomization.yaml
resources: [../../base]
namespace: orders-prod
replicas:
- { name: orders, count: 6 }
images:
- { name: orders, newTag: "1.42.0" }
kubectl diff -k overlays/prod --context prod-eu   # always name the context explicitly

Common mistakes

  • One kubeconfig with every cluster and production as the default context.
  • Scripts that omit --context and -n.
  • Duplicated YAML per environment that silently drifts.
  • Admin credentials for everyone in production.

How to answer in the interview

"kubectl works on the current kubeconfig context, so the main danger is acting on the wrong cluster. I make the context visible with kubectx, kubens and a prompt that turns red for production, keep kubeconfigs separate, and always pass the context explicitly in scripts. Manifests use a Kustomize base with small overlays per environment, so differences are explicit and reviewable. Namespaces separate teams within a cluster. In production, changes go through GitOps with Argo CD or Flux, and humans have read-only access by default with audited break-glass access."

Likely follow-up questions

  • What if someone ran kubectl delete in the wrong cluster? GitOps re-syncs declared resources; restore data from backups or Velero; then review access and add guard rails.
  • Kustomize or Helm? Kustomize for in-house apps with small differences; Helm for packaged third-party software; they can be combined.
  • How do you prevent drift? GitOps with self-heal and alerts on out-of-sync resources.
