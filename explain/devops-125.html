Compare Loki with the ELK stack for log management.

Observability & SRE · concept · levels mid, senior

In one line

ELK (Elasticsearch, Logstash, Kibana) indexes the full text of every log line for fast arbitrary search and analytics at high storage and operational cost; Grafana Loki indexes only labels and stores compressed chunks in object storage, making it much cheaper and simpler but slower for unstructured full-text search; choose by query needs and budget.

Detailed explanation

ELK / Elastic Stack: logs are shipped by Beats (Filebeat), Elastic Agent or Fluent Bit, optionally parsed by Logstash or ingest pipelines, and stored in Elasticsearch (or OpenSearch, the open-source fork), which builds an inverted index over the content and fields. Kibana provides search (KQL, Lucene, ES|QL), dashboards, alerting and security analytics. Strengths: fast full-text search over any word, rich aggregations, field-level analytics, SIEM use cases. Costs: indexing makes storage several times larger than raw logs, ingestion is CPU- and memory-heavy, and running clusters means managing shards, mappings, JVM heap, index lifecycle management (hot, warm, cold, frozen tiers) and upgrades.

Loki: indexes only a small set of labels per stream (namespace, app, pod, level), like Prometheus. Log content is stored as compressed chunks in object storage (S3, GCS, Azure Blob). Queries in LogQL first select streams by labels, then filter content (|= "error", | json | status >= 500) by scanning chunks in parallel, and can produce metrics (rate, count_over_time). Strengths: low storage cost, simple operations, native Grafana integration and correlation with Prometheus metrics and Tempo traces using the same labels. Weaknesses: needle-in-haystack searches over long ranges scan a lot of data; high-cardinality labels (user IDs) hurt performance badly. Newer Loki versions add structured metadata and bloom filters to speed some searches.

Shippers: for Loki, Grafana Alloy (successor to Promtail, which is deprecated) or Fluent Bit; for ELK, Filebeat/Elastic Agent, Logstash or Fluent Bit. The OpenTelemetry Collector can feed both.

Decision: Loki for cost-effective operational logs in Kubernetes, troubleshooting alongside metrics and traces. Elasticsearch/OpenSearch when you need heavy ad-hoc full-text search, analytics on log fields, security use cases or long investigations. Many organisations run both, or use a managed service.

Keeping logs useful and affordable: structured JSON logs, consistent levels, trace IDs, sampling or dropping debug and health-check noise at the shipper, and tiered retention.

How it works

  1. Applications log to stdout as structured JSON.
  2. A shipper on each node tails logs and adds labels or metadata.
  3. ELK: documents are parsed and indexed; Loki: streams by labels, chunks to object storage.
  4. ELK queries hit the inverted index; Loki selects streams then scans chunks.
  5. Retention policies age data to cheaper tiers or delete it.

Example

sum by (app) (rate({namespace="checkout"} | json | level="error" [5m]))
{app="payments"} |= "timeout" | json | duration_ms > 2000 | line_format "{{.trace_id}} {{.msg}}"
Kibana KQL:  service.name:"payments" and message:"timeout" and http.response.status_code >= 500

Common mistakes

  • High-cardinality labels in Loki.
  • Running Elasticsearch without ILM, letting indices grow until disks fill.
  • Unstructured logs that can't be filtered.
  • Keeping debug logs for months.

How to answer in the interview

"ELK indexes the full text of every log line in Elasticsearch, so arbitrary searches and analytics are fast, but it needs a lot of storage, memory and operational effort. Loki only indexes labels like namespace, app and level and keeps compressed chunks in object storage, so it's much cheaper and simpler, but queries select by labels and then scan content with LogQL in Grafana. Shippers are Fluent Bit or Grafana Alloy for Loki, Filebeat or Logstash for ELK. I'd choose Loki for cost-effective operational logs in Kubernetes, and Elasticsearch or OpenSearch when heavy search, analytics or security use cases matter."

Likely follow-up questions

  • How do you keep logs useful and affordable? Structured logs with trace IDs, drop noise at the shipper, sensible levels and tiered retention.
  • Why are high-cardinality labels bad in Loki? Each label combination is a stream; too many streams create tiny chunks and a huge index.
  • What replaced Promtail? Grafana Alloy.
