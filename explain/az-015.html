Explain the structure of a YAML pipeline in Azure Pipelines.

Azure DevOps & Pipelines · concept · levels entry, mid

In one line

An azure-pipelines.yml file defines triggers, then stages → jobs → steps; jobs run on Microsoft-hosted or self-hosted agents, configuration comes from variables, variable groups and templates, and deployment jobs target environments with approvals and checks.

Detailed explanation

Triggers decide when the pipeline runs: trigger for CI on branch pushes (with branch and path filters), pr for pull request validation in GitHub repos (Azure Repos uses branch policy build validation instead), schedules for cron runs, and resources triggers when another pipeline or container image completes.

The hierarchy is stages, jobs and steps. A stage is a major phase, such as Build, Test, DeployDev or DeployProd; stages run in sequence by default, and dependsOn and condition allow fan-out and conditional logic. A job is a unit that runs on one agent; jobs in a stage can run in parallel. Steps are the commands within a job: tasks (prebuilt actions such as AzureCLI@2, Docker@2) or scripts (script, bash, pwsh).

Agents: Microsoft-hosted agents are fresh VMs for each job, with common tools preinstalled; self-hosted agents run on your own VMs, scale sets or containers, needed for private network access, custom tooling or caching. Managed DevOps Pools offer Microsoft-managed agents that can join your VNet.

Variables can be defined inline, at different scopes, from variable groups in the Library (optionally linked to Key Vault), or as runtime parameters. Secret variables are masked in logs. Templates (template:) let you reuse stages, jobs, steps and variables across pipelines, and extends templates enforce a standard structure for security.

Deployment jobs (deployment:) target an environment, which records deployment history and carries approvals and checks: manual approvals, business-hours checks, required templates, Azure Monitor queries or exclusive locks.

How it works

  1. A push or PR fires the trigger.
  2. Azure DevOps expands templates and evaluates conditions.
  3. Stages run in dependency order; jobs are dispatched to agents.
  4. Each job checks out code and runs steps.
  5. Artifacts are published and consumed by later stages.
  6. Deployment jobs wait for environment checks, then deploy.

Example

trigger:
  branches: { include: [main] }
variables:
  - group: orders-common
stages:
  - stage: Build
    jobs:
      - job: build
        pool: { vmImage: ubuntu-latest }
        steps:
          - script: dotnet test --configuration Release
          - task: PublishPipelineArtifact@1
            inputs: { targetPath: out, artifact: app }
  - stage: DeployProd
    dependsOn: Build
    jobs:
      - deployment: deploy
        environment: orders-prod      # approvals and checks configured here
        strategy:
          runOnce:
            deploy:
              steps:
                - template: templates/deploy-webapp.yml
                  parameters: { appName: orders-api }

Common mistakes

  • Copy-pasting YAML across repos instead of templates.
  • Plain-text secrets in YAML.
  • Using regular jobs for deployments, losing environment history and checks.
  • Overusing self-hosted agents without hardening or patching them.
  • Not pinning task major versions.

How to answer in the interview

"An azure-pipelines.yml defines triggers for branches, PRs or schedules. The pipeline has stages, such as build, test and deploy; each stage has jobs that run on agents, either Microsoft-hosted or self-hosted in our network; and each job has steps, which are tasks or scripts. Variables and variable groups, optionally linked to Key Vault, hold configuration and secrets, and templates let us reuse stages and steps across repositories, with extends templates enforcing standards. Deployments use deployment jobs targeting environments, which carry approvals and checks like manual approval or business hours before production, plus a deployment history."

Likely follow-up questions

  • How would you share one standard pipeline across fifty repositories? A central template repository referenced via resources.repositories and extends, with required-template checks.
  • Microsoft-hosted or self-hosted agents? Hosted for simplicity; self-hosted or Managed DevOps Pools for private network access.
  • How do you pass data between stages? Pipeline artifacts or output variables via stageDependencies.
