Docker builds in CI have become very slow. How do you speed them up?

Docker · scenario · levels senior

In one line

Speed up slow CI Docker builds by first measuring each step (--progress=plain), then fixing layer order, adding a remote BuildKit cache for ephemeral runners, using cache mounts for package managers, shrinking the build context and running independent stages in parallel.

Detailed explanation

Most slow builds are not slow because of compilation; they are slow because nothing is cached. Three patterns cause almost all of it. First, a Dockerfile that does COPY . . before installing dependencies, so every code change invalidates the cache and reinstalls the whole dependency tree. Second, ephemeral CI runners that start with an empty local cache, so even a perfect Dockerfile rebuilds everything. Third, package managers re-downloading the same artifacts on every run.

BuildKit (the default builder, driven by docker buildx) solves these well. Cache export/import (--cache-to / --cache-from) stores layer cache in a registry or the CI provider's cache (for example type=gha on GitHub Actions), so a fresh runner reuses previous layers. mode=max also exports intermediate stages of multi-stage builds. Cache mounts (RUN --mount=type=cache) keep ~/.m2, ~/.npm or pip caches between builds without baking them into the image.

Other wins: a strict .dockerignore so you don't upload .git, node_modules or test data as context; multi-stage builds where independent stages (frontend and backend) build in parallel; and larger or persistent runners, or a shared remote BuildKit builder, for the heaviest builds.

How it works

  1. Run docker buildx build --progress=plain and note per-step times and CACHED markers.
  2. Reorder: copy lock files, install dependencies, then copy source.
  3. Add --cache-from/--cache-to pointing at a registry or CI cache.
  4. Add --mount=type=cache to dependency install steps.
  5. Tighten .dockerignore and check the "transferring context" size.
  6. Re-measure and compare against a baseline over several runs.

Example

# syntax=docker/dockerfile:1
FROM node:22-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci

FROM deps AS build
COPY . .
RUN npm run build
docker buildx build \
  --cache-from type=registry,ref=registry.example.com/web:buildcache \
  --cache-to type=registry,ref=registry.example.com/web:buildcache,mode=max \
  -t registry.example.com/web:${GIT_SHA} --push .

Common mistakes

  • Optimising blindly without measuring which step is slow.
  • COPY . . at the top of the Dockerfile.
  • Using --no-cache in CI "to be safe" on every build.
  • Forgetting mode=max, so multi-stage intermediate layers are never cached.
  • Huge build contexts because .dockerignore is missing.

How to answer in the interview

"I'd start by measuring: buildx build --progress=plain shows the time of every step and whether it hit the cache. Usually the cause is one of three things: dependencies reinstalled on every code change because of layer order, ephemeral runners with no cache, or package managers downloading everything again. So I copy the lock file and install dependencies before copying source, export BuildKit cache to the registry or CI cache with --cache-to and --cache-from, and use cache mounts for npm or Maven. Then I trim the context with .dockerignore and split independent work into parallel stages. Finally I compare build times over a week of runs to prove the gain."

Likely follow-up questions

  • How do you prove the improvement? Track p50/p90 build duration and cache hit rate in CI metrics before and after, over many runs.
  • Registry cache vs CI cache? Registry cache is portable across runners and providers; CI caches are convenient but size-limited and scoped per branch.
  • Why do cache mounts not bloat the image? Their contents are kept by the builder, not written into the layer.
