What happens if an exception is thrown inside a static initializer?

Exceptions · concept · levels mid, senior

In one line

If a static initialiser throws, the JVM wraps it in ExceptionInInitializerError on first use, marks the class erroneous, and every later use throws NoClassDefFoundError, so keep static init free of risky work.

Detailed explanation

Class initialisation (running static field initialisers and static {} blocks) happens once, on the first active use of a class. The JVM spec says that if initialisation completes abruptly with an exception, the class is put into an erroneous state permanently for that class loader. There is no retry.

What you see:

  1. First access: the original exception (say a NullPointerException or IllegalStateException from parsing a config file) is wrapped in ExceptionInInitializerError, whose getCause() holds the real problem. If the original was already an Error, it is rethrown as is.
  2. Every later access from any thread: NoClassDefFoundError: Could not initialize class com.shop.Config. Since JDK 17 (JDK-8048190), this error's cause includes an ExceptionInInitializerError describing the original failure, which helps; on older JDKs the cause was missing.

This is confusing in production: the jar is clearly on the classpath, yet the log full of NoClassDefFoundError comes from requests minutes after the real failure. You have to scroll back to the first error. A checked exception cannot even be thrown directly from a static block, which tempts people to wrap and rethrow as runtime exceptions.

Because a broken class can't recover until the JVM (or class loader) is restarted, avoid risky work in static initialisation: reading files, network calls, connecting to databases, parsing environment variables without defaults. Prefer lazy initialisation (holder idiom, memoised supplier), dependency injection of configuration, or explicit startup code that fails fast with a clear message.

How it works

  1. Thread triggers class initialisation; the JVM takes the class's init lock.
  2. Static initialisers run in textual order.
  3. An exception is thrown; the JVM records the class as erroneous.
  4. The first caller gets ExceptionInInitializerError.
  5. Later callers get NoClassDefFoundError without re-running the initialiser.

Example

class Config {
    static final int TIMEOUT = Integer.parseInt(System.getenv("TIMEOUT_MS")); // NPE/NFE if unset
}

try { System.out.println(Config.TIMEOUT); }
catch (ExceptionInInitializerError e) { System.out.println("1st: " + e.getCause()); }
try { System.out.println(Config.TIMEOUT); }
catch (NoClassDefFoundError e) { System.out.println("2nd: " + e.getMessage()); }
// 1st: java.lang.NumberFormatException: Cannot parse null string: null
// 2nd: Could not initialize class Config

Common mistakes

  • Debugging the NoClassDefFoundError as a classpath problem.
  • Catching ExceptionInInitializerError and continuing to use the class.
  • Placing database or HTTP clients in static fields initialised eagerly.
  • Swallowing the original exception inside the static block.

How to answer in the interview

"If a static initialiser throws, the JVM wraps the exception in ExceptionInInitializerError on that first use and marks the class as erroneous for the life of the class loader. Every later attempt to use the class throws NoClassDefFoundError 'Could not initialize class', which is confusing because the class file is there; the real cause is the first error in the logs. Newer JDKs attach that original cause. So I keep static initialisation trivial, and for anything that can fail, like reading config or connecting to services, I use lazy initialisation or dependency injection and fail fast at startup with a clear message."

Likely follow-up questions

  • Why does NoClassDefFoundError appear for a class that is clearly on the classpath? Its earlier static initialisation failed, leaving it unusable.
  • Can a static block throw a checked exception? Not directly; it must be caught or wrapped.
  • How do you recover? Fix the cause and restart the JVM or reload the class loader.
