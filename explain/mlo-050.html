How do you serve many models efficiently on shared GPU infrastructure?

MLOps · concept · levels senior, lead

In one line

Share GPUs by running multi-model servers like Triton with dynamic batching, partitioning GPUs with MIG (isolated slices) or time-slicing (no isolation), and using ModelMesh-style dynamic loading for large fleets of rarely used models, while managing noisy neighbours, GPU memory limits and isolation.

Detailed explanation

A dedicated GPU per model is wasteful when most models are small or lightly used: a single model may use 5 percent of an A100 or H100 most of the day.

Multi-model servers. NVIDIA Triton loads several models on the same GPU, runs them concurrently with configurable instance groups, and applies dynamic batching per model to raise throughput. Ray Serve and KServe's multi-model serving can also co-locate models. LLM engines like vLLM can serve multiple LoRA adapters on one base model, a powerful pattern for many fine-tuned variants.

GPU partitioning. Multi-Instance GPU (MIG) on A100, H100 and newer data-centre GPUs splits one GPU into up to seven isolated instances with dedicated memory and compute slices, giving predictable performance and fault isolation—good for multi-tenant serving and notebooks. Time-slicing (via the NVIDIA device plugin) lets several pods share a GPU in turns, with no memory or performance isolation; cheap but risky for latency-sensitive workloads. MPS allows concurrent kernels from multiple processes with partial isolation.

Dynamic loading. For thousands of models, such as one per customer, KServe ModelMesh (or similar) keeps frequently used models in memory, loads rare ones on demand from storage and evicts by LRU, packing models densely across a pool of servers.

Trade-offs. Noisy neighbours raise tail latency; GPU memory limits cause eviction, cold loads or out-of-memory errors; weaker isolation between teams (security and fault blast radius); and more complex capacity planning and cost attribution. Dedicated GPUs remain right for high-traffic, latency-critical or very large models.

How it works

  1. Profile each model: memory, throughput, traffic pattern, latency SLO.
  2. Group small, compatible models onto shared multi-model servers.
  3. Choose MIG profiles for isolation needs; time-slicing for dev and batch.
  4. Use dynamic loading for long-tail model fleets.
  5. Enable dynamic batching and monitor GPU utilisation and memory.
  6. Reserve dedicated GPUs for top-traffic or critical models.

Example

# Triton model_repository/ (one server, one GPU)
ranker/       config.pbtxt -> instance_group [{count: 2, kind: KIND_GPU}], dynamic_batching {}
embedder/     config.pbtxt -> max_batch_size: 64, dynamic_batching {max_queue_delay_microseconds: 2000}
toxicity/     config.pbtxt -> instance_group [{count: 1, kind: KIND_GPU}]
# Kubernetes pod requesting a MIG slice of an H100
resources:
  limits:
    nvidia.com/mig-1g.10gb: 1

Common mistakes

  • Time-slicing GPUs for latency-critical production models.
  • Packing models without checking combined GPU memory.
  • No per-model metrics on shared servers, hiding noisy neighbours.
  • One GPU per tiny model.

How to answer in the interview

"Giving every model its own GPU wastes money. I'd use multi-model servers like Triton to load several models per GPU with dynamic batching, and partition big GPUs with MIG into isolated slices where predictable performance matters, using time-slicing only for dev or batch work. For large fleets, like a model per customer, ModelMesh-style dynamic loading keeps popular models in memory and loads rare ones on demand. The trade-offs are noisy neighbours, GPU memory limits and weaker isolation, so critical high-traffic models keep dedicated GPUs."

Likely follow-up questions

  • How do you decide which models deserve dedicated GPUs? High traffic, strict latency SLOs, large memory or strong isolation requirements.
  • MIG vs time-slicing? MIG isolates memory and compute; time-slicing just shares turns.
  • How to serve many fine-tuned LLMs? Multi-LoRA serving on a shared base model.
