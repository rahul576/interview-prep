How do you design Log Analytics workspaces, and how do you query logs with KQL?

Azure · concept · levels mid, senior

In one line

Use as few Log Analytics workspaces as practical (split only for region/data residency, compliance or billing), control access with resource-context and table-level RBAC, ingest via diagnostic settings and Azure Monitor Agent with DCRs, query with KQL pipelines, and control cost with table plans (Analytics, Basic, Auxiliary), retention and ingestion-time filtering.

Detailed explanation

Every extra workspace makes correlation harder, because queries, workbooks and alerts must span workspaces. Microsoft's design guidance is therefore to start with one workspace and add more only for real reasons: data sovereignty (keep EU data in an EU region), separate tenants, distinct billing owners, or strong separation of security data (often Microsoft Sentinel's workspace). Many organisations end up with a central workspace per region or per environment.

Access is handled without separate workspaces through resource-context access: a user who can read a resource can query that resource's logs, so an app team sees only its own data. Table-level RBAC restricts sensitive tables such as SigninLogs or security events.

Data arrives through diagnostic settings on resources (often deployed at scale by Azure Policy deployIfNotExists), the Azure Monitor Agent with data collection rules (DCRs) for VMs, and Application Insights for apps. DCRs can also transform data at ingestion, dropping noisy columns or rows before you pay for them.

KQL reads like a pipeline: a table, then operators like where, extend, summarize, project, join, render. Always filter on TimeGenerated early. For cost, each table has a plan: Analytics for frequently queried, alertable data; Basic for high-volume troubleshooting logs with cheaper ingestion and pay-per-query; Auxiliary for very low-cost, rarely queried audit or verbose data. Retention is set per table, with long-term retention beyond interactive retention.

How it works

  1. Decide workspace boundaries (region, compliance, billing).
  2. Use resource-context RBAC; add table-level RBAC for sensitive data.
  3. Enforce diagnostic settings via policy; deploy AMA and DCRs for VMs.
  4. Apply ingestion transformations to drop noise.
  5. Set table plans and retention per table.
  6. Build workbooks and alerts on KQL queries.

Example

// Top failing operations in the last hour
AppRequests
| where TimeGenerated > ago(1h) and Success == false
| summarize failures = count() by Name, ResultCode
| top 10 by failures

// Slowest dependencies for one service
AppDependencies
| where TimeGenerated > ago(24h) and AppRoleName == "orders-api"
| summarize p95 = percentile(DurationMs, 95), calls = count() by Target, Name
| order by p95 desc

Common mistakes

  • One workspace per application, making cross-service correlation painful.
  • Sending verbose debug logs into the Analytics plan.
  • Queries without a time filter scanning months of data.
  • Giving everyone workspace-wide Reader instead of resource-context access.

How to answer in the interview

"I keep workspaces few, usually central per region or environment, and split only for data residency, compliance or billing. Access is via resource-context RBAC so teams see logs of their own resources, plus table-level RBAC for sensitive tables. Logs come from diagnostic settings enforced by policy and the Azure Monitor Agent with data collection rules. I query with KQL, for example AppRequests filtered to the last hour and failures, summarised by name. For cost, I use Basic or Auxiliary plans for noisy, rarely queried tables, per-table retention and DCR transformations."

Likely follow-up questions

  • Slowest dependencies query? AppDependencies summarised by percentile(DurationMs, 95) per target.
  • Can you alert on Basic logs? Not with standard log alerts; keep alerting data in Analytics.
  • Commitment tiers? Discounted daily ingestion levels for predictable volumes.
