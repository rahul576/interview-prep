How do you run Terraform in an air-gapped or restricted network environment?

Terraform · concept · levels mid, senior

In one line

In an air-gapped network Terraform cannot reach the public registry, so you provide a filesystem mirror (built with terraform providers mirror) or a network mirror, point the CLI at it with a provider_installation block, source modules from a private registry or Git server, and keep lock file hashes verifying packages.

Detailed explanation

Normally terraform init downloads providers from registry.terraform.io and modules from the registry or GitHub. Restricted networks block that, so you bring the dependencies inside and tell Terraform where they are.

Filesystem mirror. On a connected machine, terraform providers mirror -platform=linux_amd64 ./mirror reads your configuration and downloads every required provider for the chosen platforms into a directory with the expected layout. You scan it, transfer it through your approved process and place it on build agents or a shared volume.

Network mirror. An internal HTTPS server that implements the provider network mirror protocol; artifact repositories such as Artifactory and Nexus can act as one, proxying or hosting providers centrally. This scales better than copying directories to every agent.

CLI configuration. In .terraformrc (or the file named by TF_CLI_CONFIG_FILE) a provider_installation block lists the mirror and, importantly, excludes direct installation so nothing tries the internet. The provider source addresses in code stay the same (hashicorp/azurerm), so configurations remain portable.

Modules come from a private module registry (Terraform Enterprise, Artifactory) or an internal Git server with tagged versions.

Integrity is preserved: the .terraform.lock.hcl checksums still verify that mirrored packages are the genuine releases. Generate hashes for every platform you use with terraform providers lock. For remote execution, Terraform Enterprise or HCP Terraform agents run inside the restricted network.

How it works

  1. On a connected host, run terraform providers mirror for required platforms.
  2. Scan and transfer the mirror through the approved channel.
  3. Host it as a filesystem path or network mirror.
  4. Configure provider_installation on agents and developer machines.
  5. Point module sources to the internal registry or Git.
  6. Commit the lock file with hashes for all platforms.

Example

# /etc/terraform/terraform.rc  (TF_CLI_CONFIG_FILE)
provider_installation {
  network_mirror {
    url = "https://artifacts.corp.local/terraform/providers/"
  }
  direct {
    exclude = ["registry.terraform.io/*/*"]
  }
}
terraform providers mirror -platform=linux_amd64 -platform=darwin_arm64 ./mirror
terraform providers lock -platform=linux_amd64 -platform=darwin_arm64 \
  -fs-mirror=./mirror

Common mistakes

  • Leaving direct enabled, causing long timeouts when Terraform tries the internet.
  • Mirroring only one platform, breaking developers on other operating systems.
  • Lock files with hashes for a single platform.
  • No process for updating providers, so versions become years old.

How to answer in the interview

"In an air-gapped network Terraform can't download from the public registry, so I use a mirror. Either a filesystem mirror created with terraform providers mirror for the platforms we need, transferred inside, or a network mirror served by something like Artifactory or Nexus. The provider_installation block in the CLI config points Terraform to the mirror and disables direct downloads. Modules come from a private registry or internal Git. The lock file hashes still verify the packages are genuine, and Terraform Enterprise or agents can run remote operations inside the network."

Likely follow-up questions

  • How do you update providers safely? A regular, scanned import of new versions, then Renovate-style PRs and plans.
  • Do provider source addresses change? No, the mirror serves the same addresses.
  • Where does the CLI config live? .terraformrc, terraform.rc on Windows, or TF_CLI_CONFIG_FILE.
