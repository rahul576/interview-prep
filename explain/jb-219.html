What is synchronous versus asynchronous communication?

Microservices · concept · levels mid, senior

In one line

In synchronous communication the caller waits for the response (REST, gRPC), creating temporal coupling; in asynchronous communication it sends a message and continues (queues, events), gaining decoupling and buffering at the cost of eventual consistency and complexity.

Detailed explanation

The key question is: does the caller need the result before it can continue?

Synchronous communication means a request-response exchange where the caller waits for the answer, for example GET /prices/42 over REST or a gRPC call. Its strengths are simplicity, immediate results and easy error handling: you know straight away whether it worked. Its weakness is temporal coupling: the callee must be available right now, and its latency becomes part of yours. In a chain A → B → C → D, latencies add up and failure probabilities compound; a slow service blocks threads in all its callers, which can cascade. That is why synchronous calls need timeouts, retries with backoff, circuit breakers and bulkheads.

Asynchronous communication means the sender puts a message on a queue or topic and carries on; one or more consumers process it later. The broker buffers traffic spikes, consumers can be down temporarily without losing messages, failures can be retried automatically, and new consumers can subscribe without changing the producer. The trade-offs: eventual consistency (the effect happens later), harder debugging across hops, ordering and duplicate handling (idempotent consumers), dead-letter queues, schema management and running a broker.

An important subtlety: a non-blocking client (WebClient, CompletableFuture, virtual threads) is not the same as asynchronous communication. It frees the calling thread, but it is still request-response with temporal coupling: if the callee is down, the request still fails. True async communication goes through an intermediary that stores the message.

Rule of thumb: sync for queries and steps a user is waiting for (price, availability, login); async for background reactions and workflows (send email, update search index, analytics, fulfilment).

How it works

  1. Sync: client sends request → waits → receives response or timeout.
  2. Async: producer publishes message → broker stores it → producer continues.
  3. Consumer pulls or receives message when ready → processes → acks.
  4. Results of async work are reported by events, status endpoints or notifications.

Example

// Synchronous: user waits for availability
Availability a = restClient.get().uri("http://inventory/stock/{sku}", sku)
        .retrieve().body(Availability.class);

// Asynchronous: confirmation email happens later
rabbitTemplate.convertAndSend("notifications", "email.order-confirmation",
        new SendOrderConfirmation(orderId, customerEmail));
return ResponseEntity.accepted().build();   // 202, work continues in background

Common mistakes

  • Confusing non-blocking I/O with asynchronous messaging.
  • Using async for queries and then building polling hacks.
  • Assuming async means "fire and forget" with no failure handling.
  • Synchronous fan-out to many services in one request.

How to answer in the interview

"Synchronous means the caller sends a request and waits for the response, as with REST or gRPC. It is simple and gives an immediate answer, but creates temporal coupling: the callee must be up, latency accumulates along the chain and one slow service can block threads in all its callers. Asynchronous means publishing a message to a queue or topic and continuing; consumers process it later. That decouples availability, buffers spikes and allows retries, but brings eventual consistency, harder debugging, ordering and duplicate handling. I choose sync when the user needs an answer now and async for background reactions like notifications."

Likely follow-up questions

  • Is calling a REST API with WebClient asynchronous communication? No; it is non-blocking I/O but still synchronous request-response with temporal coupling.
  • How do you return an async result to a user? 202 Accepted with a status URL, WebSocket/SSE or a notification.
  • What is request-reply over messaging? Async transport with a reply queue and correlation id; still logically waiting for a response.
