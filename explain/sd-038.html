Design a digital wallet with a ledger that never loses or creates money.

Classic Design Problems · design · levels senior, lead

In one line

Model money with a double-entry, append-only ledger (every transfer debits one account and credits another), update balances atomically in strongly consistent transactions, use idempotency keys on every transfer, and reconcile with external providers daily.

Detailed explanation

Correctness beats everything. Double-entry means each movement is recorded twice with opposite signs; the sum over all accounts is always zero, so any bug shows up as an imbalance. Entries are immutable: you never update or delete; mistakes are corrected with reversal entries, giving a complete audit trail regulators expect.

Balances can be computed by summing entries (slow at scale) or stored as a materialised balance column updated in the same transaction as the entries, with a constraint or check against going negative. This requires serializable isolation or row locks on the accounts involved (lock in a consistent order to avoid deadlocks).

Every transfer request carries an idempotency key, so retries never move money twice. If accounts live on different shards, use a saga with a pending/hold state (debit into a suspense account, then credit), never a half-applied transfer.

External systems (banks, card networks, UPI) are reconciled daily: compare your ledger with their settlement files and investigate breaks.

How it works

  1. POST /transfers {from, to, amount, idempotency_key}.
  2. Transaction: check key; lock both accounts (ordered by ID); verify funds; insert two entries; update balances; store key + result.
  3. Return result; publish event via outbox.
  4. Nightly: reconciliation, ledger sum = 0 check.

Example

transfer_id  account     amount
T1           alice       -500.00
T1           bob         +500.00     (sum = 0)

Common mistakes

  • Floating-point money (use integers in minor units or decimal types).
  • Updating balances without entries (no audit trail).
  • Editing historical entries.
  • Non-idempotent transfer APIs.

How to answer in the interview

"I'd build a double-entry ledger: each transfer writes a debit and a credit that sum to zero, entries are append-only and corrections are reversals. Balances update atomically with the entries in a serializable transaction or with ordered row locks, with a non-negative check. Every request has an idempotency key. Cross-shard transfers use a saga with a holding state, and we reconcile against banks daily."

Likely follow-up questions

  • Cross-shard transfer? Saga via suspense/clearing account, each step idempotent.
  • High-volume hot account (merchant)? Split into sub-accounts, aggregate asynchronously.
  • Currency conversion? Separate entries per currency with an FX account.
