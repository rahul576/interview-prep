How do you secure communication between microservices?

Security · design · levels senior, lead

In one line

Assume the internal network is hostile (zero trust): encrypt and authenticate every hop with mutual TLS (often automated by a service mesh), add application-level identity through token propagation, token exchange or client credentials, restrict reachability with network policies, and manage secrets with rotation.

Detailed explanation

Old perimeter thinking said "inside the firewall is safe". In practice one compromised pod or a misconfigured route gives an attacker the run of the network, so each service must authenticate its callers and decide what they may do.

Transport identity: mTLS. In ordinary TLS only the server presents a certificate. With mutual TLS both sides do, so the receiver knows which workload is calling, and all traffic is encrypted. Managing certificates by hand is painful, so a service mesh (Istio, Linkerd, Cilium) issues short-lived certificates bound to the workload identity (SPIFFE IDs, usually based on the Kubernetes service account), rotates them automatically and enforces mTLS in sidecars or node proxies. Mesh authorization policies then say, for example, "only the checkout service may call payments on POST /charges".

Application identity: tokens. mTLS tells you which service is calling, not on whose behalf. When acting for a user, the caller propagates the user's access token, or better uses OAuth 2.0 Token Exchange (RFC 8693) to get a token with a narrower audience for the downstream service. For background jobs with no user, the service uses the client credentials grant with narrow scopes. The receiver validates the token like any resource server.

Network and secrets: Kubernetes NetworkPolicies, private subnets and security groups limit who can even connect (default deny). Secrets and keys live in a vault or cloud secret manager, preferably replaced by workload identity, and rotate automatically. Finally, log and monitor service-to-service calls and denials.

How it works

  1. Each workload gets an identity (service account) and a mesh-issued certificate.
  2. Every connection uses mTLS; plaintext is rejected (STRICT mode).
  3. Mesh policies allow only the expected caller-callee pairs.
  4. Requests carry a user token (propagated or exchanged) or a client-credentials token.
  5. The receiving service validates the token and applies its own authorization.
  6. Network policies block unexpected connections; access is logged.

Example

apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata: { name: default, namespace: shop }
spec:
  mtls: { mode: STRICT }
---
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata: { name: payments-allow-checkout, namespace: shop }
spec:
  selector: { matchLabels: { app: payments } }
  action: ALLOW
  rules:
    - from:
        - source: { principals: ["cluster.local/ns/shop/sa/checkout"] }
      to:
        - operation: { methods: ["POST"], paths: ["/charges"] }

Common mistakes

  • No authentication between services because they are "internal".
  • Sharing one static API key across all services.
  • Forwarding a broad user token everywhere instead of exchanging it.
  • mTLS in PERMISSIVE mode forever after migration.
  • Long-lived certificates rotated by hand.

How to answer in the interview

"I assume the internal network isn't trusted. First, every call uses mutual TLS so both sides prove their identity and traffic is encrypted; a service mesh like Istio or Linkerd issues and rotates the certificates and enforces authorization policies about which service may call which. Second, application-level identity: when acting for a user I propagate the token or, better, exchange it for a narrower one; for background calls I use client credentials tokens with tight scopes, validated by the receiver. Third, I limit reachability with Kubernetes NetworkPolicies and private networks. Secrets live in a vault with rotation, and service-to-service traffic is logged and monitored."

Likely follow-up questions

  • What is token exchange and when would you use it? Swapping one token for another with a different audience or reduced scope, when calling downstream on a user's behalf.
  • mTLS without a mesh? Possible with Spring Boot SSL bundles and an internal CA, but rotation is harder.
  • What is SPIFFE? A standard for workload identities (spiffe://...) used by meshes and SPIRE.
