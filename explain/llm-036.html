What is GraphRAG, and when is it better than plain vector RAG?

LLMOps & RAG · concept · levels senior, lead

In one line

GraphRAG uses an LLM at indexing time to extract entities and relationships into a knowledge graph, clusters them into communities with summaries, and answers multi-hop and corpus-wide ("global") questions better than plain vector RAG, at a much higher indexing cost and complexity.

Detailed explanation

Plain vector RAG finds chunks similar to the question. That is ideal for local, factual lookups ("what is the refund period for product X?") because the answer sits in one or two chunks. It struggles when the answer requires connecting facts spread across documents ("which suppliers are linked to delayed projects?") or summarising the whole corpus ("what are the main themes in these complaints?"), because no single chunk is similar to the question and top-k retrieval only sees a sliver of the data.

GraphRAG, popularised by Microsoft Research's open-source project, adds a graph-building stage. An LLM reads every chunk and extracts entities (people, suppliers, projects) and relationships ("supplies", "delayed by"), with descriptions. A community detection algorithm such as Leiden groups densely connected entities hierarchically, and the LLM writes a summary per community.

At query time there are two main modes. Local search starts from entities mentioned in the question and walks their neighbourhood, combining graph facts with source chunks, which suits multi-hop questions. Global search maps the question over community summaries and reduces partial answers, which suits thematic questions over the whole dataset.

The costs are real: indexing needs LLM calls over the entire corpus, often many times the cost of embedding it; extraction quality varies; and updating the graph as documents change is harder than upserting vectors. Many production systems therefore use a hybrid: vector or hybrid search for most questions, graph traversal when relationships matter.

How it works

  1. Chunk documents as usual.
  2. LLM extracts entities, relationships and claims per chunk.
  3. Merge duplicate entities; build the graph.
  4. Detect communities; generate community summaries at several levels.
  5. Query: local search over entity neighbourhoods, or global map-reduce over summaries.
  6. Generate the answer with references to chunks and entities.

Example

// After extraction into a graph database, a multi-hop question becomes a traversal
MATCH (s:Supplier)-[:SUPPLIES]->(c:Component)<-[:USES]-(p:Project {status:"delayed"})
RETURN s.name, collect(DISTINCT p.name) AS delayed_projects

Common mistakes

  • Adopting GraphRAG for a lookup-style FAQ bot.
  • Not budgeting indexing cost before running on the full corpus.
  • Ignoring entity resolution, producing duplicate nodes.
  • Not evaluating against a plain RAG baseline.

How to answer in the interview

"Plain RAG retrieves similar chunks, which is great for specific lookups but weak for questions that connect facts across documents or summarise a whole corpus. GraphRAG uses an LLM during indexing to extract entities and relationships into a graph, groups them into communities and summarises them. Local search traverses relationships for multi-hop questions; global search uses community summaries for thematic ones. It costs far more to index and is harder to keep updated, so I'd use it only when the questions really need relationships, usually alongside vector retrieval."

Likely follow-up questions

  • Is it worth the cost? Pilot on a subset; compare answer quality on multi-hop and global questions against plain RAG.
  • Alternatives? Lighter variants, or a curated knowledge graph from structured data.
  • Handling updates? Incremental extraction for changed documents, periodic re-summarisation.
