What is the difference between stack and heap memory in Java?

JVM & Performance · concept · levels entry

In one line

The stack is per thread and holds frames with local variables, primitives and references, freed automatically when a method returns; the heap is shared by all threads, holds the objects themselves and is managed by the garbage collector; exhausting them gives StackOverflowError and OutOfMemoryError respectively.

Detailed explanation

Every thread gets its own stack when it is created. Each method call pushes a frame containing the method's local variables, its parameters, an operand stack for intermediate values, and information to return to the caller. Primitive locals (int count = 5) live directly in the frame. For objects, the frame holds only a reference. When the method returns, its frame is popped, which instantly frees the memory: no garbage collection involved. Stack memory is small (commonly around 512 KB to 1 MB per platform thread, set with -Xss), fast, and thread-confined, so local variables are inherently thread-safe.

The heap is a single large area shared by all threads. Every object created with new, every array, and the fields inside objects (including primitive fields) live there. It is sized with -Xms and -Xmx and managed by the garbage collector, which reclaims objects that are no longer reachable. Because it is shared, objects on the heap can be seen by multiple threads and need proper synchronisation if mutated.

Errors. Infinite or very deep recursion keeps pushing frames until the stack is full: StackOverflowError. Too many live objects (a leak or an undersized heap) fill the heap: OutOfMemoryError: Java heap space.

Nuances. Static fields belong to the class but the values they reference are on the heap. String literals are interned in the string pool, which since Java 7 is on the heap. The JIT's escape analysis can avoid heap allocation for objects that never leave a method, by breaking them into scalar values, but that is an optimisation, not part of the language model. Virtual threads (Java 21) keep their stacks as heap objects when parked, which is why millions of them are affordable.

How it works

  1. Thread starts; the JVM allocates its stack.
  2. A method call pushes a frame with locals and references.
  3. new allocates the object on the heap; the frame stores its reference.
  4. Method returns; the frame is popped immediately.
  5. If no references remain, the object becomes garbage for the next GC.

Example

void placeOrder() {
    int qty = 3;                        // primitive in the frame (stack)
    Order order = new Order("SKU-1", qty); // reference on stack, Order object on heap
    process(order);                     // new frame; same reference passed by value
}                                       // frame popped; Order collectable if unreferenced

int depth(int n) { return depth(n + 1); } // StackOverflowError

List<byte[]> hog = new ArrayList<>();
while (true) hog.add(new byte[1_000_000]); // OutOfMemoryError: Java heap space

Common mistakes

  • Saying "primitives always live on the stack"; primitive fields of objects live on the heap.
  • Saying objects are passed by reference; Java passes references by value.
  • Increasing -Xss to hide unbounded recursion.
  • Assuming escape analysis guarantees stack allocation.

How to answer in the interview

"Each thread has its own stack holding a frame for every method call, with local variables, primitives and references to objects. A frame is freed as soon as the method returns, so stack memory is fast and needs no garbage collection, and it's thread-confined. The objects themselves live on the heap, which is shared by all threads and managed by the garbage collector. Deep or infinite recursion exhausts the stack and throws StackOverflowError, while too many live objects exhaust the heap and throw OutOfMemoryError. For example in Order o = new Order(), o is on the stack and the Order is on the heap. Escape analysis can sometimes avoid the heap allocation, but that's a JIT optimisation."

Likely follow-up questions

  • Where are string literals stored? In the string pool, which lives on the heap since Java 7.
  • Are local variables thread-safe? The variables are, because each thread has its own stack; the objects they reference may not be.
  • Where do static fields live? They are associated with the class; the objects they point to are on the heap.
