How do you see the resource usage of running containers?

Docker · concept · levels entry

In one line

Use docker stats for live CPU, memory, network and block I/O per container, docker top for processes inside a container, docker system df for disk, and cAdvisor or Prometheus for history and alerting.

Detailed explanation

Docker exposes the cgroup accounting the kernel already keeps for each container. docker stats streams a table with CPU %, memory usage versus limit, memory %, network I/O, block I/O and the number of PIDs. Passing a container name restricts it, --no-stream prints a single snapshot for scripts, and --format produces custom columns. If you started the container with --memory, the limit column shows that value; without a limit it shows the host's total memory.

docker top <container> lists the processes running inside a container with host-side PIDs, useful to see whether a worker spawned too many children. For disk, docker system df reports space taken by images, containers, volumes and the build cache. docker inspect shows the configured limits (HostConfig.Memory, NanoCpus).

These commands only show the present moment on one host. For trends, capacity planning and alerting you need metrics collection: cAdvisor exports per-container metrics, the Docker daemon can expose a Prometheus metrics endpoint, and node exporters plus Grafana dashboards show history. In Kubernetes the same data comes from the kubelet and metrics-server (kubectl top).

The memory number from docker stats often differs from what the application reports. Docker reports cgroup usage minus some page cache, while a JVM reports heap, and the kernel also counts native memory, thread stacks and file cache in the cgroup.

How it works

  1. The kernel accounts CPU, memory and I/O per cgroup.
  2. dockerd reads these counters through the runtime.
  3. docker stats calculates rates and percentages and refreshes them every second.
  4. Limits come from the container's HostConfig.
  5. Metrics exporters scrape the same counters for long-term storage.

Example

docker stats --no-stream --format "table {{.Name}}\t{{.CPUPerc}}\t{{.MemUsage}}\t{{.PIDs}}"
docker top api
docker system df -v
docker inspect -f '{{.HostConfig.Memory}} {{.HostConfig.NanoCpus}}' api

Common mistakes

  • Reading memory % without having set a limit, so the % is against host RAM.
  • Comparing docker stats memory directly with JVM heap usage.
  • Relying on docker stats for monitoring instead of collecting historical metrics.
  • Forgetting disk usage, which is a more common outage cause than CPU.

How to answer in the interview

"For a quick live view I use docker stats, which shows CPU, memory used against the limit, network and block I/O for each container; with --no-stream I get a snapshot for scripts. docker top shows the processes inside a container, and docker system df shows disk used by images, containers, volumes and build cache. Limits only show if I set them with --memory and --cpus. Because these are point-in-time views, for real monitoring I collect container metrics with cAdvisor or the Docker metrics endpoint into Prometheus and graph and alert in Grafana."

Likely follow-up questions

  • Why might docker stats memory differ from the app's view? It counts the whole cgroup, including native memory and some cache, not just heap.
  • How do you get the same in Kubernetes? kubectl top pod via metrics-server, Prometheus for history.
  • What does high CPU throttling look like? Latency rises; check cpu.stat throttled counters in cAdvisor metrics.
