When would you use sandboxed runtimes such as gVisor or Kata Containers?

Docker · design · levels lead

In one line

Standard containers share the host kernel, so for untrusted or multi-tenant workloads you add a stronger boundary: gVisor intercepts system calls in a user-space kernel, while Kata Containers run each pod in a lightweight VM with its own kernel; both cost some performance, compatibility and money.

Detailed explanation

Namespaces, cgroups, seccomp and capabilities restrict what a container can do, but every container still makes system calls into the same host kernel. A kernel vulnerability (there are several container escapes every year) can let a malicious workload break out to the host and to every other tenant on it. For your own trusted services that risk is acceptable with good hardening; for code you don't control it may not be.

gVisor (by Google, runtime runsc) puts an application kernel called the Sentry, written in Go, between the app and the host. The Sentry implements Linux system calls itself and uses only a small, filtered set of host system calls. The attack surface on the real kernel shrinks dramatically. It is used in GKE Sandbox and Google Cloud Run's first generation environment. Trade-offs: overhead for syscall-heavy and I/O-heavy workloads, and not every syscall or /proc feature is supported.

Kata Containers run each pod in a lightweight virtual machine (QEMU, Cloud Hypervisor or Firecracker) with its own guest kernel, while still looking like a normal container to Kubernetes through containerd. That gives hardware-virtualisation isolation with better syscall compatibility, at the cost of extra memory per pod, slower start than plain containers and a need for virtualisation support (nested virtualisation or bare-metal nodes in the cloud). Firecracker itself powers AWS Lambda and Fargate.

Typical use cases: running customer-supplied code, CI jobs from forks, notebooks, plug-in systems, and multi-tenant platforms where tenants must not reach each other.

How it works

  1. Install the sandbox runtime on selected nodes and register it with containerd.
  2. Create a Kubernetes RuntimeClass naming the handler (runsc, kata).
  3. Untrusted pods set runtimeClassName; others use the default runc.
  4. Use node pools, taints and scheduling so sandboxed pods land on capable nodes.
  5. Benchmark and test compatibility before rollout.

Example

apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata: { name: gvisor }
handler: runsc
---
apiVersion: v1
kind: Pod
metadata: { name: tenant-job }
spec:
  runtimeClassName: gvisor
  containers:
    - name: job
      image: registry.example.com/tenant/job:42

Common mistakes

  • Believing seccomp and non-root alone make hostile code safe.
  • Sandboxing everything, including trusted high-throughput services, and paying the overhead everywhere.
  • Not testing compatibility (some syscalls, GPUs, /proc features).
  • Forgetting network isolation; a sandbox doesn't stop network access.

How to answer in the interview

"Normal containers share the host kernel, so a kernel exploit can escape to the host and other tenants. Sandboxed runtimes add a stronger boundary. gVisor runs a user-space kernel, the Sentry, that implements system calls itself so the workload barely touches the host kernel. Kata Containers run each pod in a lightweight VM with its own kernel, giving VM-level isolation behind a container interface. I'd use them for untrusted code: customer workloads, forked CI jobs, multi-tenant platforms. The costs are overhead for syscall- or I/O-heavy apps, some compatibility gaps and more resources, so in Kubernetes I'd apply them only to selected pods with a RuntimeClass."

Likely follow-up questions

  • How do you sandbox only some pods? A RuntimeClass plus runtimeClassName on those pods, scheduled to nodes with the runtime installed.
  • gVisor or Kata for databases? Neither ideally; I/O-heavy trusted workloads run better on runc.
  • What is Firecracker? A minimal VMM for microVMs, used by Lambda and Fargate, and usable as a Kata hypervisor.
