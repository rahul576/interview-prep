What does an MCP gateway do, and do you always need one?

MCP Servers · concept · levels mid, senior

In one line

An MCP gateway is a proxy giving one entry point in front of many MCP servers, centralising authentication and authorization, routing and aggregation, tool filtering, rate limits, logging, audit and data protection; you do not need one for a single local server, but it becomes very useful at scale.

Detailed explanation

Once an organisation runs many remote MCP servers, built by different teams and vendors, each one would otherwise implement its own token validation, logging, rate limiting and policy. A gateway pulls these cross-cutting concerns into one place, much as an API gateway does for REST APIs.

Authentication and authorization. The gateway integrates with the enterprise IdP, validates tokens and decides which users, groups and agents can reach which servers and even which individual tools. Backend servers can trust the gateway's identity headers or receive exchanged tokens.

Routing and aggregation. Clients connect to one URL, and the gateway routes requests to the right backend. Many gateways can aggregate several servers into one virtual server, filter tools (hide write tools for some groups), and rename or namespace tools to avoid collisions.

Traffic control. Per-user, per-agent and per-tool rate limits and quotas protect backends and costs.

Security inspection. The gateway can scan arguments and results for sensitive data (DLP), secrets, or known injection patterns, and can pin and diff tool definitions to detect changes.

Observability. Central logs, audit trails and metrics give security teams one view of all agent tool usage.

In the stateless protocol revision, standard headers such as Mcp-Method and Mcp-Name expose the method and tool name, so gateways can route and rate-limit without parsing JSON bodies. Products include cloud API management offerings with MCP support and dedicated MCP gateways.

The gateway introduces its own risk: it is a high-value target and a potential single point of failure, holding visibility into all traffic and often privileged credentials.

How it works

  1. Client connects to https://mcp-gw.corp/… and authenticates via the IdP.
  2. Gateway validates the token and looks up policy for user, client and target server.
  3. It filters the tool list returned to the client by policy.
  4. On tools/call, it checks rate limits, runs DLP on arguments, forwards to the backend.
  5. It inspects the result, logs the call and returns it.

Example

routes:
  - path: /crm
    backend: https://crm-mcp.internal/mcp
    allow_groups: [support, sales]
    hide_tools: [delete_contact]
    rate_limit: { per_user: 60/min }
  - path: /github
    backend: https://api.githubcopilot.com/mcp/
    allow_groups: [engineering]
policies:
  dlp: { block: [credit_card, iban], redact_logs: [email] }
  tool_definition_pinning: true

Common mistakes

  • Deploying a gateway for one or two servers, adding latency and complexity for little benefit.
  • Running the gateway without high availability.
  • Passing user tokens through the gateway to backends instead of proper token handling.
  • Treating DLP pattern matching as complete protection.

How to answer in the interview

"An MCP gateway is a proxy between clients and many MCP servers, giving one entry point. It centralises authentication with the enterprise IdP and authorization policy, so we decide which users and agents can reach which servers and tools. It routes requests, can aggregate servers into one virtual server, filters or renames tools, applies rate limits and quotas, and can inspect traffic for sensitive data or injection patterns. It also gives central logging and audit for the security team. In the stateless revision, the Mcp-Method and Mcp-Name headers let gateways route and rate-limit without parsing bodies. You don't need one for a single local server, but with many remote servers and teams it's very useful. The trade-off is that it becomes a critical, high-value component."

Likely follow-up questions

  • New risk introduced? A single point of failure and a high-value target with visibility into everything.
  • Gateway vs host policy? Host policy controls the client; the gateway controls the server side regardless of client.
  • Does it replace server authorization? No; servers still enforce per-user data access.
