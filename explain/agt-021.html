How do you control the cost of agentic applications?

AI Agents & AIOps · concept · levels mid, senior

In one line

Control agent cost by measuring cost per completed task, enforcing budgets and step limits, routing simple steps to cheaper models, reducing context (compaction, concise tools, prompt caching), avoiding needless multi-agent fan-out, and building better tools that cut steps.

Detailed explanation

Agents can cost ten to a hundred times more than a single model call, because each step resends a growing context and long runs include many steps. Cost control starts with the right metric: cost per successfully completed task, including retries, failed runs and escalations, not cost per call. An agent that is cheap per call but needs 40 steps, or fails half the time, is expensive.

Budgets and limits cap the worst case: maximum steps, tokens and dollars per run, plus daily budgets per user and tenant, enforced by the runtime.

Model choice: use a strong model for planning and hard reasoning, and smaller, faster models for simple sub-steps like classification, extraction or summarising a tool result. A router can pick the model by task difficulty. Reasoning effort or thinking budgets, where providers offer them, can also be tuned per step.

Context is the main cost driver. Prompt caching of stable prefixes, the system prompt and tool definitions, gives large discounts on cached input tokens with major providers. Compaction and clearing old tool outputs keep histories short. Concise tool results with only the needed fields and pagination prevent context floods. Avoid loading huge documents when retrieval of the relevant part suffices.

Multi-agent fan-out multiplies tokens; use it only when evals show it pays off. Batch APIs cut cost for non-interactive workloads.

Often the best saving is better tools: one tool that performs what previously took five steps reduces cost, latency and error rates simultaneously. Finally, dashboards show cost per task by agent version, model and task type, so regressions are caught.

How it works

  1. Instrument token usage and cost per step and per run.
  2. Compute cost per successful task by type and version.
  3. Set budgets per run, user and tenant.
  4. Enable prompt caching; compact context; trim tool outputs.
  5. Route simple steps to smaller models.
  6. Replace multi-step patterns with higher-level tools; re-measure.

Example

Support agent, before and after optimisation (1,000 tasks)

                          Before        After
Avg steps per task        14            6     (new get_order_summary tool)
Avg input tokens/step     38k           9k    (compaction + trimmed results)
Cached share of input     0%            70%   (stable system prompt + tools)
Model for summarising     large         small
Success rate              81%           86%
Cost per successful task  $0.92         $0.14

Common mistakes

  • Tracking cost per call instead of per successful task.
  • Putting variable content before stable content, breaking prompt caching.
  • Using the largest model for every step.
  • Tools that return full records when two fields are needed.
  • Multi-agent designs without a cost comparison.

How to answer in the interview

"Agents can cost ten or a hundred times more than a single call because every step resends a growing context. I measure cost per completed task, including failures and retries, and set budgets and step limits per run and per user. A strong model handles planning and hard steps, while cheaper models handle simple sub-steps like summarising or classifying. Context is the biggest driver, so I use prompt caching for system prompts and tool definitions, compaction, and concise tool results. Multi-agent fan-out multiplies tokens, so it has to earn its place. Often the biggest win is better tools: one tool that replaces five steps cuts cost and errors. Dashboards show cost per task by agent version."

Likely follow-up questions

  • Budget for tasks with widely varying difficulty? Tiered budgets by task class, with escalation or approval to extend the budget for hard cases.
  • How does prompt caching work? Providers reuse computation for an identical prompt prefix, charging less for cached tokens.
  • When to use batch APIs? Offline workloads like nightly classification where latency doesn't matter.
