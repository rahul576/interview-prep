Describe a reference architecture for production LLM applications in an enterprise.

LLMOps & RAG · design · levels senior, lead

In one line

An enterprise LLM reference architecture has an application/agent layer, a central LLM gateway (routing, quotas, fallbacks, caching, logging), a model layer of hosted APIs and self-hosted models, a permission-aware data and retrieval layer, shared safety services, and cross-cutting observability, evaluation and governance.

Detailed explanation

Without a shared architecture, every team integrates models differently, duplicates safety work, leaks keys and cannot report spend. A layered design gives each team freedom at the top while the platform handles cross-cutting concerns.

The application layer contains user-facing apps and agents: orchestration logic (frameworks or plain code), versioned prompts, tool integrations and MCP connections to internal systems. Teams own this layer.

All model traffic goes through a central LLM gateway (for example LiteLLM, Kong or Envoy AI gateway, a cloud provider's gateway, or in-house). It offers one API, authentication per application, routing between models, quotas and budgets per team, fallbacks when a provider fails, response and prompt caching, and central logging of usage and cost.

Behind it the model layer mixes hosted APIs from approved providers with self-hosted open models on GPU infrastructure (vLLM, KServe on Kubernetes) for sensitive or high-volume workloads.

The data and retrieval layer provides ingestion pipelines, chunking and embedding, vector and hybrid search, and access to business data, all enforcing the end user's permissions so RAG never reveals documents a user could not open.

Safety services, shared by all apps, include PII detection and redaction, prompt-injection detection, content moderation and output validation.

Across layers: observability (OpenTelemetry tracing of prompts, tool calls and tokens, cost dashboards), evaluation pipelines in CI and on production samples, and governance: model approvals, data policies, risk assessments and audit trails.

How it works

  1. A request enters an app or agent, which builds context and calls the gateway.
  2. The gateway authenticates, applies quotas and safety checks, and routes to a model.
  3. Retrieval and tools fetch data with the user's identity and permissions.
  4. Responses pass output guardrails before reaching the user.
  5. Traces, tokens and costs are recorded; samples flow into evaluations.

Example

[Web / Chat / IDE apps]  [Agents + MCP servers]
            |                    |
        +---------- LLM Gateway ----------+  authN, routing, quotas, fallback, cache, logs
        |               |                 |
  Hosted model APIs   Self-hosted (vLLM on K8s GPUs)
            
  Retrieval: ingestion -> embeddings -> hybrid index (ACL-aware)
  Safety: PII redaction | injection detection | moderation
  Cross-cutting: OpenTelemetry traces, cost, evals in CI, model registry, audit

Common mistakes

  • Apps calling providers directly with shared keys, so no cost attribution or control.
  • RAG indexes built with a service account that ignores document permissions.
  • Each team building its own guardrails differently.
  • No evaluation pipeline, so model upgrades are untested.
  • Over-building the platform before any real use case exists.

How to answer in the interview

"I'd describe it in layers. The application layer has apps and agents with orchestration, versioned prompts and MCP connections to internal systems. All model calls go through a central LLM gateway that handles authentication, routing, quotas per team, fallbacks, caching and logging. Behind it, hosted APIs from approved providers plus self-hosted open models for sensitive or high-volume work. A retrieval layer with ingestion and hybrid search enforces user permissions. Shared safety services do PII detection, injection detection and moderation. Across everything: tracing and cost tracking, evaluations in CI and production, and governance for approvals and audit."

Likely follow-up questions

  • Which layer first for a company starting out? The gateway, because it gives control of keys, cost and logging immediately.
  • Build or buy the gateway? Usually adopt an existing one and extend it.
  • How do you enforce permissions in RAG? Store ACLs as metadata and filter at query time by the user's groups.
