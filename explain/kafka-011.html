What are log compaction and retention policies in Kafka?

Kafka · concept · levels mid, senior

In one line

Kafka's delete cleanup policy removes old segments by time (retention.ms) or size (retention.bytes), while the compact policy keeps at least the latest value per key, with tombstones (null values) deleting keys; compaction suits changelogs, state and CDC.

Detailed explanation

A partition's log is stored as segments on disk. Only closed (non-active) segments are eligible for cleanup, which is why a topic can briefly hold data older than its retention.

With cleanup.policy=delete (the default), the broker deletes whole segments whose newest record is older than retention.ms (7 days by default) or when the partition exceeds retention.bytes. This is the right model for event streams like clicks or logs, where old events lose value.

With cleanup.policy=compact, the log cleaner threads periodically rewrite segments, keeping only the most recent record for each key. The topic becomes a durable snapshot of current state: a new consumer reading from the beginning rebuilds the latest value of every key without replaying full history. To delete a key, a producer writes a tombstone, a record with that key and a null value. The tombstone itself is retained for delete.retention.ms (24 hours by default) so slow consumers see the deletion, then removed. Compaction does not guarantee only one value per key at any moment; the active segment and uncleaned "dirty" portion still hold older versions, controlled by min.cleanable.dirty.ratio and min.compaction.lag.ms.

Typical uses: Kafka Streams changelog topics for state stores, __consumer_offsets itself, CDC topics from Debezium (latest row per primary key), and reference data such as customer profiles or configuration. You can combine both with cleanup.policy=compact,delete, keeping the latest value per key but also dropping anything older than retention, which is useful for windowed state.

How it works

  1. Producer writes keyed records; segments roll by size or time.
  2. Cleaner picks partitions with a high dirty ratio.
  3. It builds an offset map of the latest offset per key.
  4. It copies segments, dropping superseded records.
  5. Tombstones remain for delete.retention.ms, then disappear.

Example

kafka-topics.sh --bootstrap-server broker:9092 --create --topic customer-profile \
  --partitions 12 --replication-factor 3 \
  --config cleanup.policy=compact \
  --config min.compaction.lag.ms=60000 \
  --config delete.retention.ms=86400000
# delete customer 42
echo "42:" | kafka-console-producer.sh --bootstrap-server broker:9092 \
  --topic customer-profile --property parse.key=true --property key.separator=: --property null.marker=

Common mistakes

  • Producing null keys to a compacted topic (the broker rejects them).
  • Expecting compaction to be immediate.
  • Setting delete.retention.ms too low so consumers miss tombstones.
  • Using compaction when consumers actually need full history.

How to answer in the interview

"The delete policy drops old segments once they exceed retention.ms or retention.bytes, which suits normal event streams. The compact policy instead keeps at least the latest value for each key, cleaning older ones in the background, so the topic acts like a table of current state. A record with a null value is a tombstone that removes the key after delete.retention.ms. I use compaction for Kafka Streams changelogs, CDC topics and reference data, and you can combine compact and delete when you want both."

Likely follow-up questions

  • Why must compacted topics have keys? Compaction is per key; keyless records are rejected.
  • Does compaction preserve order? Yes, offsets keep their order; only superseded records are removed.
  • When are segments eligible? Only closed segments; tune segment.ms for faster cleanup.
