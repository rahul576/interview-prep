What is the difference between String, StringBuilder and StringBuffer?

Core Java & OOP · concept · levels entry

In one line

String is immutable; StringBuilder is mutable and unsynchronised (the default for building text); StringBuffer is the older synchronised equivalent, rarely needed today.

Detailed explanation

String objects cannot change after creation. Every "modification" such as concat, replace or toUpperCase returns a new String. Immutability is a feature: strings can be shared safely across threads, cached in the string pool, used as stable HashMap keys (the hash code is cached), and trusted in security-sensitive places like class names and file paths.

StringBuilder (Java 5) holds a resizable internal buffer. append, insert, reverse and deleteCharAt modify it in place, and toString() produces the final String. Appends are amortised O(1); when capacity runs out it grows (roughly doubling) and copies once.

StringBuffer (Java 1.0) has the same API but every method is synchronized. That makes single operations thread-safe, but in practice builders are almost always local variables used by one thread, so the locking is pure overhead. Also, a sequence of calls on a shared buffer is still not atomic, so synchronisation at method level rarely gives the safety people expect.

For simple one-line concatenation like "Hello " + name + "!", just use +: the compiler optimises it (via StringConcatFactory since Java 9). The builder matters when you concatenate across loop iterations, because each s += x creates a new String and copies everything built so far, which is O(n²). For joining with separators, String.join, StringJoiner or Collectors.joining are clearer.

How it works

  1. A String literal or new String creates an immutable value backed by a byte array.
  2. A StringBuilder allocates a buffer (default capacity 16, or what you pass).
  3. Each append writes into the buffer, growing it when needed.
  4. toString() copies the content into a new String.
  5. StringBuffer does the same while acquiring its monitor on every call.

Example

// Bad: O(n^2) copying
String csv = "";
for (Order o : orders) csv += o.id() + ",";

// Good
StringBuilder sb = new StringBuilder(orders.size() * 12);
for (Order o : orders) sb.append(o.id()).append(',');
String result = sb.toString();

// Often best
String joined = orders.stream().map(o -> String.valueOf(o.id()))
                      .collect(Collectors.joining(","));

Common mistakes

  • Using += inside loops over large inputs.
  • Choosing StringBuffer "to be safe" for local variables.
  • Sharing a StringBuilder between threads.
  • Comparing builders with equals (it is identity-based; compare toString() or use compareTo).

How to answer in the interview

"String is immutable, so every change produces a new object; that's what makes strings safe to share, cache in the pool and use as map keys. StringBuilder is mutable and not synchronised, so it's the fast choice for building strings, especially in loops. StringBuffer is the legacy synchronised version; since builders are almost always local to one thread, I basically never need it. For simple expressions I just use plus because the compiler optimises it, but in a loop I use a StringBuilder or Collectors.joining."

Likely follow-up questions

  • Why is String concatenation in a loop slow? Each iteration copies all previous characters into a new String, giving quadratic work.
  • Why is String final? To guarantee immutability and security.
  • Does StringBuilder override equals? No, it uses identity equality.
