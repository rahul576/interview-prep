An agent keeps calling the same tool with the same arguments in a loop. How do you diagnose and fix it?

AI Agents & AIOps · scenario · levels mid, senior

In one line

Open the trace and see what the agent observed after each call: loops usually come from ambiguous or unchanged tool results, non-actionable errors, missing information or tool relationships, or unclear completion criteria; fix the tools, descriptions and instructions, and add runtime loop detection with step limits as a safety net.

Detailed explanation

Repeating the same call with the same arguments is the agent's way of saying "I don't understand what happened". The diagnosis therefore starts from the model's point of view: read the trace step by step and look at exactly what it received.

Common causes:

  • Ambiguous results: an empty list without explanation looks like a failure, so the agent retries. "No orders found for this customer in the last 90 days" is clear.
  • Truncated or unchanged output: the tool returns the first 50 lines each time, and the needed information is on line 400, so the agent asks again hoping for more. Pagination parameters and "more results available: use page=2" fix this.
  • Non-actionable errors: "Error: request failed" gives no hint, so the model retries the same call.
  • Missing information: the tool needs a customer ID that another tool provides, but neither description mentions the relationship.
  • Unclear completion criteria: the agent does not know when it is done, so it keeps verifying.
  • Side-effect confusion: an action succeeded but the response did not say so, so the agent repeats it, which is dangerous for non-idempotent tools.

Fixes go to the root: make results explicit, including empty and already-done states; write errors that suggest the next step; describe relationships between tools ("use find_customer first to get customer_id"); state completion criteria in the instructions.

In the runtime, add loop detection: hash tool name plus arguments and, after two or three repeats, inject a hint such as "you already called this with identical arguments; the result was X" or stop the run. Step limits remain the final safety net. Then turn the failing trace into a regression test.

How it works

  1. Find the looping run's trace; locate the first repeat.
  2. Read the observation preceding each repeat.
  3. Classify the cause: ambiguous result, error, missing info, completion.
  4. Fix the tool output, error message, description or instructions.
  5. Add loop detection with a hint, then a stop.
  6. Add the scenario to the eval suite; verify the fix over several runs.

Example

Trace excerpt (before fix):
step 4  search_tickets(query="VPN outage", status="open")  -> []
step 5  search_tickets(query="VPN outage", status="open")  -> []
step 6  search_tickets(query="VPN outage", status="open")  -> []

Fixed tool result:
{"ok": true, "count": 0,
 "message": "No open tickets match 'VPN outage'. 3 closed tickets match; use status='any' to include them, or create_ticket if this is a new issue."}

Runtime hint injected on 2nd identical call:
"You already called search_tickets with identical arguments and got 0 results. Choose a different action."

Common mistakes

  • Only raising the step limit.
  • Adding "do not repeat yourself" to the prompt without fixing the tool output.
  • Empty results without explanation.
  • Ignoring that repeated non-idempotent calls may have side effects.
  • Not adding a regression test.

How to answer in the interview

"I open the trace and look at what the agent saw after each call, because loops usually mean it didn't understand the result. Typical causes are an ambiguous result, like an empty list without saying 'no matches', a truncated output that never changes, a generic error that gives no hint, a missing ID that another tool provides but nothing points there, or instructions that don't say when the task is done. I fix those: explicit results including empty and already-done states, errors that suggest the next step, descriptions that explain how tools relate, and clear completion criteria. In the runtime, loop detection flags repeated identical calls and injects a hint or stops, with step limits as a final safety net."

Likely follow-up questions

  • Test that catches loop regressions? A scenario with the triggering fixture, run several times, asserting no repeated identical calls and a step count below a threshold.
  • Is a loop ever legitimate? Polling a job status is, but it should be a dedicated wait tool with backoff.
  • What if the model is the problem? Compare with a stronger model on the same trace; often tool clarity still matters more.
