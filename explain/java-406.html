What is the difference between partitioning and sharding, and how do you choose a shard key?

Databases & SQL · concept · levels senior, lead

In one line

Partitioning splits a big table into pieces inside one database, while sharding spreads data across multiple database servers; a good shard key has high cardinality, spreads load evenly and keeps most queries on a single shard.

Detailed explanation

Partitioning (for example PostgreSQL declarative partitioning or MySQL partitioning) divides a table by range, list or hash of a key. The table still looks like one table, and the engine uses partition pruning to scan only relevant partitions. It is mainly a manageability and query-pruning tool: dropping a month of old data becomes DROP PARTITION instead of a huge DELETE. It does not add CPU, memory or disk beyond one server.

Sharding puts subsets of rows on separate database instances, each with its own resources, to scale write throughput and storage horizontally. Something must route queries: the application, a proxy such as Vitess, or the database itself (Citus, MongoDB, Cassandra, DynamoDB).

Choosing the shard key is the most important and least reversible decision:

  • High cardinality so data can be split finely (user id, not country).
  • Even distribution of both data and traffic, avoiding hot shards (a celebrity user, a big tenant).
  • Query locality: most queries and transactions include the key, so they stay on one shard. In multi-tenant SaaS, tenant_id is often ideal.
  • Stability: the key value should not change.

Placement strategies are range (simple, but hot spots on recent data), hash / consistent hashing (even, but range scans touch all shards) and a directory lookup (flexible, but another component). Cross-shard joins, global unique constraints, distributed transactions and rebalancing are hard, so I exhaust query tuning, vertical scaling, caching, read replicas and partitioning first.

How it works

  1. Measure whether one primary really cannot handle the data or write load.
  2. Analyse the main access patterns to find a key present in most queries.
  3. Check distribution of that key for skew.
  4. Choose placement: hash with many logical shards mapped to fewer physical nodes.
  5. Build routing, and handle cross-shard reporting through a warehouse or scatter-gather.
  6. Plan rebalancing by moving logical shards between nodes.

Example

-- Partitioning within one PostgreSQL instance
CREATE TABLE orders (id BIGINT, tenant_id BIGINT, created_at DATE, total NUMERIC)
  PARTITION BY RANGE (created_at);
CREATE TABLE orders_2026_11 PARTITION OF orders
  FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');

-- Sharding with Citus: distribute by tenant across worker nodes
SELECT create_distributed_table('orders', 'tenant_id');

Common mistakes

  • Sharding by a low-cardinality key such as country or status.
  • Sharding by a timestamp, so all new writes hit one shard.
  • Choosing a key that most queries do not include, forcing scatter-gather.
  • Fixing shard count to physical servers with no logical shards for rebalancing.

How to answer in the interview

"Partitioning splits a table inside one database, for example by month, which gives partition pruning and cheap archiving but no extra hardware. Sharding spreads rows across several database servers to scale writes and storage. For the shard key I want high cardinality, an even spread of data and traffic, and locality, meaning most queries and transactions include it, so tenant id or user id are typical. Cross-shard queries, transactions and rebalancing are painful, so I'd use consistent hashing or a directory with many logical shards, and I'd only shard after vertical scaling, replicas, caching and partitioning are exhausted."

Likely follow-up questions

  • What if you shard by country? Few, very uneven shards; one big country becomes a hotspot you cannot split.
  • How do you rebalance? Move logical shards between nodes, or use consistent hashing so only a fraction of keys move.
  • How do you run a report across shards? Scatter-gather for small queries, otherwise replicate into a data warehouse.
