Explain the structure of a docker-compose file.

Docker · concept · levels entry

In one line

A compose.yaml is YAML whose main top-level key is services (each with image or build, ports, environment, volumes, depends_on, healthcheck), plus top-level volumes, networks, and optionally configs and secrets.

Detailed explanation

The Compose Specification defines the file format; the old top-level version: field is obsolete and ignored. The preferred filename is compose.yaml, though docker-compose.yml still works.

Under services, every key is a service name that also becomes its DNS name on the project network. A service uses either image to run an existing image or build (with context, dockerfile, target and args) to build one; with both, the build result is tagged with that image name. Common keys are ports to publish ports ("127.0.0.1:5432:5432"), environment or env_file for configuration, volumes for named volumes or bind mounts, command and entrypoint overrides, restart policies, healthcheck, resource limits under deploy.resources, and depends_on. depends_on alone only orders start-up, so combine it with condition: service_healthy and a healthcheck to wait until a database is really ready.

Top-level volumes declares named volumes such as pgdata, which persist independently of containers. Top-level networks declares custom networks; if you declare none, Compose creates a default network per project and all services can reach each other by name. profiles mark optional services, and variable interpolation (${TAG:-latest}) reads values from the shell or a .env file. Extension fields (x-common:) with YAML anchors remove duplication.

How it works

  1. Compose loads the file, overrides and .env and interpolates variables.
  2. It creates the project network(s) and named volumes.
  3. It builds or pulls images for each service.
  4. It starts services in dependency order, waiting for conditions.
  5. Services resolve each other by service name on the network.

Example

services:
  api:
    build: { context: ., target: runtime }
    image: registry.local/api:${TAG:-dev}
    ports: ["8080:8080"]
    env_file: .env.api
    depends_on:
      db: { condition: service_healthy }
    restart: unless-stopped
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_pw
    secrets: [db_pw]
    volumes: [pgdata:/var/lib/postgresql/data]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      retries: 10
volumes:
  pgdata:
secrets:
  db_pw: { file: ./secrets/db_pw.txt }

Common mistakes

  • Relying on depends_on without a healthcheck.
  • Publishing database ports to 0.0.0.0 on shared machines.
  • Committing passwords inside environment.
  • Using container IPs instead of service names.

How to answer in the interview

"A compose file is YAML with a few top-level keys. services is the main one: each service has either image or build, plus ports, environment or env_file, volumes, command, restart policy, a healthcheck and depends_on. I combine depends_on with condition service_healthy so the API waits until the database is really ready. Top-level volumes declares named volumes such as pgdata, and networks declares custom networks; by default all services share one project network and reach each other by service name. I use .env interpolation for values like image tags and keep secrets out of the file."

Likely follow-up questions

  • How do you handle dev versus prod differences? Override files, multiple -f files and profiles.
  • Is the version key needed? No, it is obsolete in the Compose Specification.
  • How do you avoid repetition? x- extension fields with YAML anchors.
