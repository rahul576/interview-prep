What is the difference between findFirst() and findAny()?

Java 8+ Features · concept · levels mid, senior

In one line

Both are short-circuiting terminal operations returning an Optional: findFirst returns the first element in encounter order (deterministic), while findAny may return any element, which is the same in sequential streams usually but cheaper and nondeterministic in parallel.

Detailed explanation

Encounter order is the order a stream's source defines: a List or array has one, a HashSet does not. findFirst respects that order: on an ordered stream it always returns the element that would come first, regardless of how the work is split.

findAny is explicitly allowed to return any element of the stream. In a sequential stream the current implementation returns the first element it sees, so the result usually equals findFirst, but you must not rely on that; the specification permits otherwise.

The difference matters in parallel streams. With findFirst, worker threads may find matches in different chunks, but the result must be the one earliest in encounter order, so the framework has to coordinate: a later chunk's match can't be returned until earlier chunks have finished or been proven empty. With findAny, whichever worker finds a match first wins and the others are cancelled, so it is faster, but different runs may return different elements. You can also call unordered() to relax ordering constraints for other operations.

Both return Optional.empty() for an empty stream. If the found element is null, both throw NullPointerException, because Optional can't contain null. Filter nulls first (filter(Objects::nonNull)) if the source may contain them.

Rule of thumb: use findFirst when the order is meaningful, like "the earliest pending order"; use findAny when any match is acceptable, like "is there any available seat, give me one".

How it works

  1. The pipeline runs until a matching element reaches the terminal stage.
  2. Sequential: the first element arriving ends the stream.
  3. Parallel findAny: first result from any thread completes and cancels others.
  4. Parallel findFirst: keeps the leftmost result, waiting for earlier chunks.

Example

List<Integer> nums = IntStream.rangeClosed(1, 1_000).boxed().toList();

Optional<Integer> first = nums.parallelStream()
    .filter(n -> n % 7 == 0)
    .findFirst();                // always 7

Optional<Integer> any = nums.parallelStream()
    .filter(n -> n % 7 == 0)
    .findAny();                  // could be 7, 504, 875... varies between runs

Seat seat = seats.stream()
    .filter(Seat::isAvailable)
    .findAny()
    .orElseThrow(NoSeatsException::new);

// Stream.of("a", null).findFirst();   // NPE: Optional can't hold null

Common mistakes

  • Assuming findAny always returns the first element.
  • Using findFirst in parallel when order doesn't matter, paying for coordination.
  • Expecting deterministic results from findFirst on unordered sources like HashSet.
  • Ignoring the NPE when the matched element is null.

How to answer in the interview

"Both are short-circuiting terminal operations returning an Optional. findFirst returns the first element in the stream's encounter order, so it's deterministic. findAny can return any matching element. In a sequential stream they normally give the same element, but the difference matters in parallel: findFirst has to coordinate between threads to respect encounter order, which costs performance, while findAny returns whatever a worker finds first, cheaper but nondeterministic. I use findFirst when order matters and findAny when I just need some match."

Likely follow-up questions

  • What happens if the element found by findFirst is null? It throws NullPointerException.
  • What is encounter order? The order defined by the source, e.g. list index order.
  • What does unordered() do? Removes the ordering constraint, allowing cheaper parallel execution.
