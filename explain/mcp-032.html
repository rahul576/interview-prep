How do you keep state across tool calls when the MCP protocol is stateless?

MCP Servers · concept · levels mid, senior

In one line

Without protocol sessions, keep state explicit: a tool that starts something stores state server-side (database or shared cache) and returns a handle; later tools accept the handle as an argument; handles are unguessable, scoped to the authenticated user, validated on every call and expiring.

Detailed explanation

The 2026-07-28 revision removed protocol sessions, and even before that, relying on in-memory session state broke as soon as a server ran on more than one replica, restarted, or sat behind a load balancer without sticky routing. Many workflows still need state: building a report section by section, a shopping cart, a multi-step migration plan, a database transaction preview.

The recommended pattern is explicit handles:

  1. A tool that starts a stateful workflow, such as create_draft_report or open_cart, creates the state server-side in a database or a shared cache like Redis, and returns an identifier (report_id: "rpt_7Hc9…") in its result.
  2. Subsequent tools, such as add_section(report_id, …) or checkout(cart_id), take the handle as an argument. Any replica can load the state and continue.
  3. The model passes handles naturally, because they appear in the conversation as tool results. Descriptions should mention them: "Use the report_id returned by create_draft_report".

This is the same idea as REST resources, and it makes state visible, debuggable and durable.

Security matters, because a handle is effectively a capability:

  • Unguessable: random, high-entropy ids (e.g. 128-bit), never sequential integers, which allow enumeration (IDOR) attacks.
  • Scoped to the user: store the owner with the state and check on every call that the caller's authenticated identity matches. Never trust the handle alone.
  • Expiring: TTLs clean up abandoned state and limit exposure.
  • Validated: unknown or expired handles return a clear, actionable error.

How it works

  1. start_* tool → generate random id → save {owner, data, expires_at} → return id.
  2. Later call with id → load → verify owner = caller → apply change → save.
  3. Expiry via TTL (Redis EX) or a cleanup job.
  4. Errors guide the model: "report_id expired; call create_draft_report again".

Example

@mcp.tool()
def create_draft_report(title: str) -> dict:
    """Start a new draft report. Returns report_id for add_section and publish_report."""
    rid = "rpt_" + secrets.token_urlsafe(16)
    redis.set(f"draft:{rid}", json.dumps({"owner": current_user().id, "title": title, "sections": []}),
              ex=86400)
    return {"report_id": rid, "expires_in_hours": 24}

@mcp.tool()
def add_section(report_id: str, heading: str, body: str) -> dict:
    """Add a section to a draft created with create_draft_report."""
    raw = redis.get(f"draft:{report_id}")
    if not raw:
        raise ToolError("Unknown or expired report_id. Call create_draft_report again.")
    draft = json.loads(raw)
    if draft["owner"] != current_user().id:
        raise ToolError("You do not have access to this report.")
    draft["sections"].append({"heading": heading, "body": body})
    redis.set(f"draft:{report_id}", json.dumps(draft), keepttl=True)
    return {"report_id": report_id, "sections": len(draft["sections"])}

Common mistakes

  • Per-process dictionaries holding state across calls.
  • Sequential or guessable handles.
  • Checking only that the handle exists, not who owns it.
  • No expiry, so drafts accumulate forever.

How to answer in the interview

"In the stateless revision there are no protocol sessions, and in-memory session state broke anyway once servers scaled across replicas. So I make state explicit: a tool that starts something, like create_draft_report, stores the state server-side in a database or Redis and returns a handle. Later tools such as add_section take that handle as an argument, so any replica can load the state. The model passes handles naturally because they're in the conversation. Handles must be unguessable, bound to the authenticated user and checked on every call, and expire so abandoned state is cleaned up."

Likely follow-up questions

  • Security issue with sequential handles? Enumeration: another user guesses ids and accesses others' state (IDOR), unless ownership is checked.
  • Database or cache? Cache for short-lived drafts; database for anything valuable or long-lived.
  • What if the model loses the handle? Provide a list_my_drafts tool.
