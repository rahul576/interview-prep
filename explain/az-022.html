How would you deploy a containerised app to AKS with Azure DevOps across dev, test and prod?

Azure DevOps & Pipelines · design · levels mid, senior

In one line

CI builds, tests, scans and pushes an image to ACR with an immutable tag; a multi-stage YAML pipeline promotes the same image through dev, test and prod environments with approvals and checks, deploying via Helm or, preferably, GitOps (Flux or Argo CD), with smoke tests after each stage.

Detailed explanation

Build once, deploy many is the core principle. The CI stage compiles and runs unit tests, builds the Docker image, runs image scanning (for example Microsoft Defender for Containers, Trivy) and pushes it to Azure Container Registry tagged with the commit SHA or build ID, never latest. Optionally the image is signed (Notation) and an SBOM is produced. This exact image is promoted to every environment, so what you tested is what reaches production.

CD stages are deployment jobs targeting Azure DevOps environments (dev, test, prod). Each environment can have approvals and checks: automatic for dev, test gated on integration tests, prod gated on manual approval, business hours and branch control (only main). Environments record deployment history per image.

Deployment mechanics:

  • Push-based: the pipeline uses helm upgrade --install (or the HelmDeploy/KubernetesManifest tasks) with per-environment values files, authenticating to AKS through a workload identity federation service connection and Entra-integrated kubeconfig.
  • GitOps (pull-based, my preference): the pipeline only updates the image tag in a config repository (or opens a PR for prod). Flux (available as the AKS GitOps extension) or Argo CD in the cluster syncs the desired state. This gives an audit trail in Git, drift correction, easy rollback by reverting a commit, and no cluster credentials in the pipeline.

Configuration differs per environment (replicas, resource limits, endpoints, feature flags) through values files or Kustomize overlays, while secrets come from Key Vault via the CSI driver and workload identity. Smoke tests and health checks run after each deployment; Kubernetes rolling updates with readiness probes, or progressive delivery (Argo Rollouts, Flagger), limit the blast radius.

How it works

  1. PR validation: build and unit tests.
  2. Main branch: build image, scan, push to ACR with SHA tag.
  3. Deploy to dev automatically; run smoke tests.
  4. Deploy to test after integration tests pass.
  5. Prod approval, then deploy the same image.
  6. Verify health; roll back by redeploying the previous tag or reverting Git.

Example

stages:
  - stage: Build
    jobs:
      - job: image
        pool: { vmImage: ubuntu-latest }
        steps:
          - task: Docker@2
            inputs:
              containerRegistry: sc-acr
              repository: shop/orders-api
              command: buildAndPush
              tags: $(Build.SourceVersion)
  - stage: Prod
    dependsOn: Build
    jobs:
      - deployment: helm
        environment: orders-prod
        pool: { vmImage: ubuntu-latest }
        strategy:
          runOnce:
            deploy:
              steps:
                - task: HelmDeploy@1
                  inputs:
                    connectionType: Azure Resource Manager
                    azureSubscriptionEndpoint: sc-aks-prod-wif
                    azureResourceGroup: rg-aks-prod
                    kubernetesCluster: aks-prod
                    command: upgrade
                    chartType: FilePath
                    chartPath: charts/orders-api
                    releaseName: orders-api
                    namespace: orders
                    valueFile: charts/orders-api/values-prod.yaml
                    arguments: --set image.tag=$(Build.SourceVersion) --atomic --wait

Common mistakes

  • Rebuilding the image per environment.
  • Using latest or mutable tags.
  • Secrets in values files.
  • No approval or branch control for production.
  • Not running post-deployment checks, so failures are found by users.

How to answer in the interview

"The CI stage builds and tests the code, builds the Docker image, scans it, and pushes it to Azure Container Registry tagged with the commit SHA. A multi-stage YAML pipeline then deploys the same image to dev, test and prod, each an Azure DevOps environment with checks, and manual approval plus branch control before prod. Deployment uses Helm with per-environment values files, or preferably GitOps: the pipeline updates the image tag in a config repo and Flux, available as an AKS extension, or Argo CD syncs it. The same artifact is promoted and never rebuilt, secrets come from Key Vault via workload identity, and smoke tests run after each deployment."

Likely follow-up questions

  • How would you add automated rollback if health checks fail? helm --atomic, or progressive delivery with Argo Rollouts or Flagger analysing metrics.
  • Why GitOps over push deployments? Git audit trail, drift correction and no cluster credentials in CI.
  • How do you handle database migrations? A separate, backward-compatible migration job before rollout.
