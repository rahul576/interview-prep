Design a tamper-evident audit logging system for a regulated financial application.

Classic Design Problems · design · levels senior, lead

In one line

A tamper-evident audit log captures structured who/what/when/where/outcome events through reliable ingestion, stores them append-only and write-once (WORM), links them with hash chains or Merkle trees anchored externally, and lives in a separate account with retention and read-only auditor access.

Detailed explanation

Regulators (and incident responders) need to trust that the audit trail is complete and unaltered. "Tamper-proof" is impossible, but tamper-evident is achievable: any modification or deletion can be detected.

What to record: actor (user, service, impersonation), action, resource, timestamp from a trusted clock, source IP/device, request ID, outcome, and before/after values for data changes. Use a fixed schema so events are searchable.

Reliability: losing events is itself a compliance failure. Applications write audit events via the transactional outbox or a durable local buffer into Kafka or Kinesis; for critical operations (payments, permission changes) the action fails if the audit record cannot be written.

Immutability: store in WORM storage such as S3 Object Lock in compliance mode or Azure immutable blob storage with a locked time-based retention policy, so not even root administrators can delete objects before retention ends.

Detection: each record includes the hash of the previous record (hash chain), or batches form a Merkle tree whose root is digitally signed and periodically anchored externally (another account, a timestamping authority, or a ledger database). Verification recomputes hashes; any edit, insertion or deletion breaks the chain.

Separation of duties: the audit store sits in a separate cloud account with its own admins, so a compromised app or engineer cannot erase traces.

How it works

  1. Application emits a structured event with a sequence number and writes it via outbox.
  2. A collector consumes the stream, assigns per-stream sequence numbers and computes hash = SHA256(prev_hash || event).
  3. Every N minutes, a Merkle root over the batch is signed with a KMS/HSM key and stored separately.
  4. Batches land in Object Lock storage with 7-year retention.
  5. An indexed read-only copy (OpenSearch) serves auditor queries.
  6. A scheduled verifier recomputes chains and alerts on gaps or mismatches.

Common mistakes

  • Writing audit logs to the same database the application can update and delete.
  • Fire-and-forget logging that silently drops events under load.
  • Hash chaining without external anchoring, so an attacker can rewrite the whole chain.
  • Logging sensitive data (full card numbers, passwords) into an immutable store you can never clean.

How to answer in the interview

"Every relevant action produces a structured event: who, what, which resource, when, from where and the outcome, with before and after values. Events go through an outbox into Kafka so nothing is lost, and critical operations fail if auditing fails. Storage is write-once, like S3 Object Lock in compliance mode, in a separate account. I hash-chain records and periodically sign Merkle roots and anchor them externally, so any change or deletion is detectable. Retention follows regulation, often seven years, and auditors get a read-only, searchable index."

Likely follow-up questions

  • How do you prove nothing was deleted? Contiguous sequence numbers plus a verifiable hash chain and signed, externally anchored roots.
  • How do you handle GDPR erasure in an immutable log? Store personal data by reference or encrypted with per-subject keys that can be destroyed.
  • How do you keep it fast to search? A separate indexed copy; the WORM store remains the source of truth.
