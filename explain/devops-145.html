At 3 a.m., API latency spikes tenfold. Walk me through your investigation.

Troubleshooting · scenario · levels senior, lead

In one line

Scope the problem on dashboards, correlate with recent changes, follow traces to the slow dependency, check saturation (CPU throttling, memory/GC, pools, locks, throttling), and mitigate first — roll back, scale, fail over or shed load — before root cause analysis.

Detailed explanation

At 3 a.m. the goal is to restore service quickly and safely, not to find the perfect explanation. I acknowledge the page, open the incident channel and say I am investigating, so others know.

Scope. Dashboards answer: which endpoints and services, since when exactly, all regions or one, all customers or one tenant, and are error rates rising too. The latency percentiles (p50 vs p99) tell me whether everything is slow or only a tail. A sharp step at a precise minute points to a change; a gradual climb points to load or accumulation.

Correlate with changes. Most incidents follow a change: deployments, config or feature flag changes, infrastructure changes, certificate or secret rotation, a traffic spike or bot, a batch job, or a dependency incident on a cloud status page.

Follow the request. Distributed traces for slow requests show where time goes: the database, a cache miss storm, an external API, or DNS. Database metrics show slow queries, lock waits and connection counts.

Check saturation. The USE method — utilisation, saturation, errors — across CPU and CPU throttling from container limits, memory and GC pauses, thread and connection pools, queue depth, disk IO, and API throttling (429s) from cloud services.

Mitigate. Roll back the suspect deployment or flag, scale out, fail over to another region, enable caching or shed load with rate limits. Communicate impact and ETA. After recovery, preserve evidence and run a blameless postmortem for the root cause.

How it works

  1. Acknowledge, open the incident channel, assign roles if it is big.
  2. Scope: services, endpoints, regions, start time, errors.
  3. Correlate with deploys, flags, config, traffic and provider status.
  4. Use traces to locate the slow hop.
  5. Check saturation signals for the suspect component.
  6. Mitigate, verify recovery on dashboards, communicate.
  7. Root cause analysis and postmortem later.

Example

kubectl rollout history deploy/checkout -n shop
kubectl top pods -n shop --sort-by=cpu
kubectl rollout undo deploy/checkout -n shop      # if the 02:40 deploy is the suspect
histogram_quantile(0.99, sum by (le, route) (rate(http_request_duration_seconds_bucket[5m])))
sum by (pod) (rate(container_cpu_cfs_throttled_periods_total[5m]))

Common mistakes

  • Diving into one theory before scoping the impact.
  • Making several changes at once, so you cannot tell what fixed it.
  • Spending an hour on root cause while users are still affected.
  • Not communicating, so others start parallel uncoordinated fixes.

How to answer in the interview

"I open dashboards to scope it: which endpoints and services, since when, one region or all, and are errors rising. Then I correlate with changes — deploys, config or flag changes, traffic spikes, or a provider incident. Traces show which dependency is slow, often the database or an external API. I check saturation: CPU and throttling, memory and GC, connection pools, queues and database locks. I mitigate first — roll back, scale out, fail over or shed load — while updating the incident channel, and do root cause analysis after recovery in a blameless postmortem."

Likely follow-up questions

  • Latency high but CPU and memory normal? Check CPU throttling, pool exhaustion, lock waits, downstream latency, DNS and network.
  • How do you choose between rollback and scaling? If it correlates with a change, roll back; if with traffic, scale or shed load.
  • What goes into the postmortem? Timeline, impact, root cause, detection gaps and actions with owners.
