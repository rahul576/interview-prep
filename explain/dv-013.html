Which ports and protocols should a DevOps engineer know?

Networking · concept · levels entry

In one line

Know the daily ones: 22 SSH, 80 HTTP, 443 HTTPS, 53 DNS, plus SMTP 25/587, NTP 123, database and messaging ports (5432 PostgreSQL, 3306 MySQL, 6379 Redis, 27017 MongoDB, 9092 Kafka) and Kubernetes (6443 API server, 10250 kubelet, 2379-2380 etcd); understand well-known versus ephemeral ports and check with ss -tulpn.

Detailed explanation

A port is a 16-bit number (0-65535) identifying a process endpoint on a host; together with IP and protocol (TCP or UDP) it forms a socket. Knowing default ports speeds up troubleshooting and firewall design.

Core: 22/TCP SSH (also SFTP, Git over SSH); 80/TCP HTTP; 443/TCP HTTPS and 443/UDP for HTTP/3 (QUIC); 53/UDP and TCP DNS; 123/UDP NTP; 25/TCP SMTP between mail servers and 587/TCP submission with STARTTLS (465 for implicit TLS); 3389 RDP; 389/636 LDAP/LDAPS; 161/UDP SNMP; 514 syslog.

Data and messaging: 5432 PostgreSQL, 3306 MySQL/MariaDB, 1433 SQL Server, 1521 Oracle, 6379 Redis, 27017 MongoDB, 9200 Elasticsearch/OpenSearch HTTP, 9092 Kafka, 5672 RabbitMQ (15672 management UI), 2181 ZooKeeper.

Kubernetes and cloud-native: 6443 kube-apiserver, 2379-2380 etcd client/peer, 10250 kubelet API, 10257 controller manager and 10259 scheduler, 30000-32767 NodePort range, 8472/UDP VXLAN for some CNIs; observability: 9090 Prometheus, 9100 node exporter, 3000 Grafana, 4317/4318 OTLP gRPC/HTTP.

Port ranges: well-known 0-1023 (binding needs root or CAP_NET_BIND_SERVICE on Linux), registered 1024-49151, and ephemeral ports used as client source ports for outbound connections (Linux default 32768-60999, see net.ipv4.ip_local_port_range; IANA suggests 49152-65535). Ephemeral ports matter for stateless NACLs, which must allow return traffic to them, and for port exhaustion on busy proxies or NAT gateways.

Checking: ss -tulpn lists listening TCP/UDP sockets with processes (netstat -tulpn on older systems); lsof -i :5432 shows who holds a port. Remotely, nc -vz host port or nmap tests reachability. Default ports are conventions: services can run anywhere, and moving SSH off 22 is obscurity, not security.

How it works

  1. A server process binds to IP:port and listens.
  2. A client connects from an ephemeral source port to that port.
  3. Firewalls and security groups allow or block by port and protocol.
  4. Return traffic goes back to the client's ephemeral port.

Example

sudo ss -tulpn | grep -E ":22|:443|:5432"
sudo lsof -i :8080
nc -vz db.internal 5432
cat /proc/sys/net/ipv4/ip_local_port_range     # 32768 60999
nmap -p 22,80,443,5432 10.0.1.25

Common mistakes

  • Opening 22 or database ports to 0.0.0.0/0.
  • Forgetting UDP for DNS and QUIC, or TCP for DNS.
  • Ignoring ephemeral ports in stateless NACL rules.
  • Assuming a service uses its default port without checking.

How to answer in the interview

"Daily I use 22 for SSH, 80 and 443 for HTTP and HTTPS, and 53 for DNS over UDP and TCP. Others are 25 and 587 for SMTP, 123 for NTP, and databases like 5432 PostgreSQL, 3306 MySQL, 6379 Redis, 27017 MongoDB and 9092 Kafka. In Kubernetes, 6443 is the API server, 10250 the kubelet and 2379 etcd. Ports below 1024 are well known and need privileges to bind, and clients use ephemeral ports for outgoing connections. To see what's listening I use ss -tulpn, and I open only the needed ports to specific sources."

Likely follow-up questions

  • How do you check from your laptop whether 5432 is reachable? nc -vz host 5432 or psql; a timeout suggests a firewall drop, refused suggests nothing listening.
  • Why can't a non-root process bind to 80? Ports below 1024 are privileged; grant CAP_NET_BIND_SERVICE or use a proxy.
  • What is port exhaustion? Running out of ephemeral ports for outbound connections, common on NAT gateways and busy proxies.
