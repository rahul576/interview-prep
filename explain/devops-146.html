A deployment is stuck: new pods stay in Pending or ImagePullBackOff. How do you fix it?

Troubleshooting · scenario · levels mid, senior

In one line

Run kubectl describe pod and read the events: Pending means the scheduler cannot place the pod (resources, taints, affinity, unbound PVC, quota), ImagePullBackOff means the node cannot pull the image (wrong tag, registry auth, network); use rollout status and rollout undo to protect users while fixing it.

Detailed explanation

A rollout gets stuck because new pods never become Ready, and with the default RollingUpdate strategy the old ReplicaSet keeps serving, so users are often unaffected — but the deployment will eventually exceed progressDeadlineSeconds and report failure.

Pending pods have not been scheduled, and the scheduler records why in the events, for example 0/6 nodes are available: 3 Insufficient cpu, 3 node(s) had untolerated taint. Causes:

  • Insufficient resources: requests too large or cluster full; the cluster autoscaler may be adding nodes, or hitting max size or cloud quota.
  • Taints without matching tolerations, such as dedicated GPU or system pools.
  • Node affinity, nodeSelector or pod anti-affinity rules nothing satisfies.
  • An unbound PersistentVolumeClaim: no matching StorageClass, or a zonal disk in another zone.
  • A ResourceQuota or LimitRange in the namespace; this shows on the ReplicaSet events (exceeded quota), as pods are never created.

ImagePullBackOff / ErrImagePull means the kubelet failed to pull:

  • The tag or digest does not exist (typo, image not pushed yet, wrong registry path).
  • Authentication: missing imagePullSecret, expired secret, or missing AcrPull/ECR permission for the node or workload identity.
  • Network: nodes cannot reach the registry because of a firewall, private endpoint DNS or proxy.
  • Registry rate limits, such as Docker Hub's anonymous limits.

kubectl rollout status shows progress; kubectl rollout undo restores the previous ReplicaSet if needed while the fix is made.

How it works

  1. kubectl get pods to see status.
  2. kubectl describe pod <name> and read events at the bottom.
  3. For Pending, compare requests with node capacity, taints, affinity, PVC and quota.
  4. For image errors, verify the image reference, pull secrets and registry reachability.
  5. Fix the manifest or environment; or rollout undo if production is at risk.
  6. Confirm with rollout status.

Example

kubectl describe pod checkout-7c9f-abcde -n shop | sed -n '/Events/,$p'
#  Warning  Failed  kubelet  Failed to pull image "acr.io/shop/checkout:1.4.l": not found

kubectl describe rs -n shop | grep -i quota
kubectl get pvc -n shop
kubectl rollout status deploy/checkout -n shop --timeout=2m
kubectl rollout undo deploy/checkout -n shop

Common mistakes

  • Looking at application logs for a pod that never started.
  • Deleting pods repeatedly instead of reading the events.
  • Missing quota errors because they appear on the ReplicaSet, not the pod.
  • Using mutable latest tags, making pulls unpredictable.

How to answer in the interview

"I start with kubectl describe pod and read the events. For Pending, the scheduler tells me why: insufficient CPU or memory because requests are too big or the cluster is full, taints without tolerations, affinity rules nothing satisfies, an unbound PVC, or a namespace quota, which shows on the ReplicaSet. For ImagePullBackOff, either the tag doesn't exist, the registry needs credentials through an imagePullSecret or workload identity, or the nodes can't reach the registry. I watch rollout status, and if production is at risk I use rollout undo while fixing it."

Likely follow-up questions

  • How do you prevent a tag typo reaching production? Build once, deploy the CI-produced digest, and verify the image exists in a pipeline step.
  • What is CrashLoopBackOff, by contrast? The image started but the container keeps exiting; check logs with --previous.
  • Why might autoscaling not help Pending pods? Max nodes reached, cloud quota, or a request larger than any node size.
