Why might you use forEach() instead of map() to apply a discount?

Coding Exercises · concept · levels mid

In one line

Use forEach when the goal is a side effect — updating existing objects in place, such as entities to be saved — because map is meant to return transformed values; mutating inside map is misleading and depends on a terminal operation, so with immutability prefer map to new objects.

Detailed explanation

The Stream API distinguishes transformations from actions. map(Function<T,R>) is an intermediate operation whose contract is: for each element, produce a value that flows to the next stage. It is expected to be stateless and non-interfering, and ideally free of side effects. forEach(Consumer<T>) is a terminal operation designed precisely for side effects: it returns nothing and exists to do something with each element.

So if the task is "apply a 15% discount to these existing Product objects" — for example JPA entities that the transaction will flush, or objects other parts of the program hold references to — the honest code is:

products.stream().filter(cond).forEach(p -> p.setPrice(p.getPrice() * 0.85));

Writing map(p -> { p.setPrice(...); return p; }) followed by collect technically works, but it has problems:

  • It misleads readers: map suggests a new value, yet the original objects changed.
  • Without a terminal operation, nothing runs, because intermediate operations are lazy; the discount silently never happens.
  • With peek or certain short-circuiting terminals, the mutation may run for only some elements.
  • It breaks the assumption that the pipeline is safe to run in parallel.

If no stream operations are needed, products.forEach(...) (Iterable.forEach) or products.replaceAll(...) (for replacing elements of a mutable list) are even simpler.

When immutability matters — records, value objects, shared data, concurrency — the better design is map returning new objects with the discounted price and collecting them into a new list.

How it works

  1. Decide: are you changing existing objects, or producing new ones?
  2. Changing existing objects → forEach with setters.
  3. Producing new values → map returning new instances, then collect.
  4. Replacing elements in a mutable list → replaceAll.

Example

// side effect on existing mutable entities: forEach
products.stream()
        .filter(p -> p.getCategory().equals("Electronics"))
        .forEach(p -> p.setPrice(p.getPrice() * 0.85));

// misleading: mutation hidden in map, and does nothing without a terminal op
products.stream().map(p -> { p.setPrice(p.getPrice() * 0.85); return p; });

// immutable alternative: map to new objects
List<Product> discounted = products.stream()
        .map(p -> new Product(p.getName(), p.getCategory(), p.getPrice() * 0.85, p.getStock()))
        .toList();

// replace elements of a mutable list in place
products.replaceAll(p -> p.withPrice(p.getPrice() * 0.85));

Common mistakes

  • Mutating state inside map or filter lambdas.
  • Forgetting that a pipeline without a terminal operation does nothing.
  • Using stream().forEach where list.forEach is simpler.
  • Updating shared mutable objects from a parallel stream.

How to answer in the interview

"map is meant to produce a new value for each element that flows into the next stage. If my goal is to change existing Product objects, say entities that will be saved, that's a side effect, and forEach is the operation designed for side effects: filter, then forEach calling setPrice. Doing the mutation inside map and returning the same object works, but it's misleading, it breaks the expectation that map is pure, and it doesn't run at all without a terminal operation. If immutability matters, I'd use map to create new objects instead."

Likely follow-up questions

  • Would List.forEach or replaceAll be simpler? Yes: list.forEach for setters without filtering, replaceAll to swap elements for new objects.
  • What does peek do? A debugging hook; it should not be used for business side effects.
  • Is forEach ordered? Not on parallel streams; use forEachOrdered if order matters.
