How do BuildKit cache mounts and build secrets work?

Docker · concept · levels mid

In one line

BuildKit's RUN --mount=type=cache keeps package caches (Maven, npm, pip, Go) between builds without putting them in the image, and RUN --mount=type=secret exposes a secret only during that one step, passed with docker build --secret, never stored in layers or history.

Detailed explanation

Classic Dockerfiles had two pains. Dependency installs re-downloaded everything whenever the layer cache was invalidated, for example after a single change in pom.xml. And private dependencies needed credentials, which people passed with ARG or COPY and then deleted, but the secret remained in an earlier layer or the image history.

BuildKit, the default builder in current Docker, adds mounts for individual RUN instructions. A cache mount attaches a persistent directory managed by the builder: RUN --mount=type=cache,target=/root/.m2 mvn package lets Maven reuse its local repository across builds even when the layer itself must be rebuilt. The cache is not part of the image, so it adds no size. The same works for /root/.npm, /root/.cache/pip, /go/pkg/mod or apt caches (with sharing=locked). Cache mounts are local to the builder, so a fresh CI runner starts empty unless you persist the builder state.

A secret mount makes a file (default /run/secrets/<id>) or, in newer versions, an environment variable available only while that RUN executes. It is not written to any layer, not visible in docker history, and not part of the cache key. You provide it at build time with --secret id=npmrc,src=$HOME/.npmrc or --secret id=token,env=GH_TOKEN. For Git over SSH there is a similar --mount=type=ssh with --ssh default, which forwards your SSH agent.

How it works

  1. The Dockerfile declares the mount on a RUN instruction.
  2. BuildKit attaches the cache directory or secret file for that step only.
  3. The command runs and may populate the cache.
  4. The resulting layer is snapshotted without the mount contents.
  5. Next build, the cache mount is reattached with its previous contents.

Example

# syntax=docker/dockerfile:1
FROM node:22-slim AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm \
    --mount=type=secret,id=npmrc,target=/root/.npmrc \
    npm ci --omit=dev

FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /src
COPY . .
RUN --mount=type=cache,target=/root/.m2 mvn -q package -DskipTests
docker build --secret id=npmrc,src=$HOME/.npmrc -t web:1.0 .

Common mistakes

  • Passing tokens with ARG, which leak into history.
  • Expecting cache mounts to survive on ephemeral CI runners.
  • Pointing the cache mount at a different directory than the tool actually uses.
  • Copying the secret into the image in a later step "for convenience".

How to answer in the interview

"BuildKit adds special mounts to RUN. RUN --mount=type=cache,target=/root/.m2 mvn package keeps the Maven repository in a persistent builder cache between builds without putting it into the image, so dependencies aren't downloaded again; the same works for npm, pip or Go modules. RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci makes a secret available only during that step, and it's never written to a layer or the history. I pass it with docker build --secret id=npmrc,src=... This replaces unsafe patterns like copying credentials in and deleting them later."

Likely follow-up questions

  • How do you use BuildKit cache in fresh CI runners? Export layer cache to a registry or GHA cache, or keep a persistent builder.
  • What about SSH keys for private Git? RUN --mount=type=ssh with docker build --ssh default.
  • Is the secret part of the cache key? No, so changing it does not invalidate the cache.
