How can AI help with root cause analysis during incidents, and what are its limits?

AI Agents & AIOps · concept · levels senior, lead

In one line

AI helps root cause analysis by combining telemetry, topology, changes and incident history faster than people, and LLM agents run diagnostic queries and summarise ranked hypotheses with evidence; but correlation is not causation, outputs must be verified, and quality depends on data and context.

Detailed explanation

During an incident, responders juggle dashboards, logs, traces, deploy history and chat. AI shortens this search. Statistical methods find which components became anomalous first and follow the dependency graph to the most likely source. Change correlation links symptoms to deployments, feature flags and configuration updates, which cause a large share of production incidents. Similarity search over past incidents surfaces previous root causes and fixes for matching symptoms.

LLM-based agents go further: they call tools to run PromQL or KQL queries, search logs, inspect traces, describe Kubernetes objects and diff recent commits, then write a summary with ranked hypotheses, each backed by links to the evidence.

The limits matter. Correlation is not causation: a deployment that happened just before the outage may be innocent. LLMs can sound confident while wrong, misread graphs or invent connections, so every claim must cite evidence and humans verify before acting. Results also depend on data quality: missing traces, inconsistent service labels, no change records or short retention make analysis weak. Novel failure modes, with no history to compare against, are where AI helps least.

How it works

  1. Incident opens with affected services and timeframe.
  2. Detect which signals deviated first and map them on the topology.
  3. Pull changes in the window before onset.
  4. Agent runs targeted queries to test each hypothesis.
  5. Retrieve similar past incidents and resolutions.
  6. Present ranked hypotheses with evidence links; responders confirm or reject.

Example

Hypotheses for INC-2291 (checkout p99 latency 4x since 14:07)
1. [High] payments-api v3.18 deployed 14:03 — new retry config; payments call rate 3x (query link)
2. [Medium] Redis cache hit ratio dropped 92% → 61% at 14:06 (graph link)
3. [Low] Node pressure on pool-b — only 2 of 14 pods affected (kubectl describe excerpt)
Similar: INC-1870 (retry storm after timeout change), fixed by rollback

Common mistakes

  • Acting on the top hypothesis without checking the evidence.
  • Giving the AI no change data, then wondering why it misses deploy-related causes.
  • Treating "no hypothesis found" as "no problem".
  • Not measuring whether suggestions were right.

How to answer in the interview

"AI is good at combining many sources quickly: it finds which components went anomalous first, follows dependencies, correlates with deployments and config changes, and finds similar past incidents. LLM agents can actually run the diagnostic queries and return ranked hypotheses with evidence. But correlation isn't causation and LLMs can be confidently wrong, so I treat outputs as hypotheses that must cite evidence, and humans verify them. And it's only as good as the data: without traces, consistent labels and change records, the analysis is weak."

Likely follow-up questions

  • How do you measure if it helps? Responders rate suggestions; compare time to identify cause.
  • Where does AI RCA fail most? Novel failures and systems with poor telemetry.
  • Should it see code? Read access to recent diffs is very useful for change-related incidents.
