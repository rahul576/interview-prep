What are Ansible facts?

Configuration Management · concept · levels entry

In one line

Facts are details Ansible gathers about each host at play start via the setup module (OS, IPs, CPU, memory, disks), exposed as ansible_facts for use in conditionals and templates; disable, subset or cache them to speed up runs.

Detailed explanation

Before running tasks, a play by default executes the setup module on every host (gather_facts: true). It returns a large JSON document describing the machine: distribution, distribution_version, os_family, kernel, architecture, hostname, fqdn, network interfaces and default_ipv4, processor_vcpus, memtotal_mb, mounts, and more. These are available as ansible_facts['name']. For historical reasons they are also injected as top-level variables like ansible_os_family, but the ansible_facts[...] form is clearer and is the recommended style.

Facts let one playbook adapt to different hosts. You can pick the package manager with when: ansible_facts['os_family'] == 'Debian', size a JVM heap from memtotal_mb in a template, bind a service to default_ipv4.address, or build an upstream list from other hosts' facts through hostvars.

Gathering costs time, especially on large fleets or slow links, so you can tune it: gather_facts: false for plays that don't need facts; gather_subset (for example ['!all', 'network']) to collect only parts; and fact caching (fact_caching = jsonfile or redis with a timeout) combined with gathering = smart, so facts are reused across runs and remain available for hosts not contacted in the current run.

You can also add custom local facts: executable or INI/JSON files in /etc/ansible/facts.d/*.fact on the host appear under ansible_local, and set_fact creates facts during a run (with cacheable: true to persist them in the cache).

How it works

  1. Play starts; setup runs on each host unless disabled.
  2. The JSON result is stored as ansible_facts for that host.
  3. Tasks and templates read facts like any variable.
  4. With caching, facts are stored and reused until the timeout.
  5. ansible_local adds custom facts from facts.d files.

Example

ansible web01 -m ansible.builtin.setup
ansible web01 -m ansible.builtin.setup -a "filter=ansible_distribution*"
- hosts: all
  gather_facts: true
  tasks:
    - name: Install on Debian family
      ansible.builtin.apt:
        name: chrony
      when: ansible_facts['os_family'] == 'Debian'

    - name: Install on RedHat family
      ansible.builtin.dnf:
        name: chrony
      when: ansible_facts['os_family'] == 'RedHat'
# ansible.cfg
[defaults]
gathering = smart
fact_caching = jsonfile
fact_caching_connection = /tmp/ansible_facts
fact_caching_timeout = 7200

Common mistakes

  • Gathering full facts on thousands of hosts for plays that never use them.
  • Disabling facts and then referencing them, causing undefined variable errors.
  • Relying on stale cached facts after hardware or IP changes.
  • Mixing ansible_os_family and ansible_facts['os_family'] inconsistently.

How to answer in the interview

"Facts are what Ansible learns about each host at the start of a play by running the setup module: OS and distribution, kernel, IP addresses, CPU count, memory, disks, hostname, available under ansible_facts. They let one playbook adapt, for example 'when os_family is Debian' to choose apt or dnf, or sizing a JVM heap from total memory in a template. Since gathering takes time, for big fleets I disable it when not needed, gather only subsets, or turn on fact caching in JSON files or Redis. And custom local facts can be added through facts.d on the host."

Likely follow-up questions

  • How do you see all facts for one host? ansible <host> -m setup, optionally with filter=.
  • What is gathering = smart? Only gather if facts aren't already cached.
  • How do you use another host's facts? hostvars['db01']['ansible_facts'][...], provided they were gathered or cached.
