terraform plan fails with Error acquiring the state lock. What do you do?

Terraform · scenario · levels entry, mid, senior

In one line

The lock is held by another active run or a crashed or cancelled run that never released it; read the lock info (ID, who, when, operation), check running pipelines and ask, and only if it is definitely stale use terraform force-unlock <ID>; never remove a lock while a run is applying.

Detailed explanation

Error acquiring the state lock means the backend refused to give this run the lock, because a lock already exists. Either another engineer or pipeline is genuinely running plan or apply on the same state right now, or a previous run died without releasing it: a CI job was cancelled or hit its timeout, a runner was killed.

The error message includes lock info: the lock ID, the path, who created it (user and host), the operation (OperationTypeApply, OperationTypePlan), the Terraform version and when it was created. Check the CI system for running jobs on that state, ask in the team channel, and look at the user and time: a lock from a pipeline that finished hours ago, or from a runner that no longer exists, is very likely stale.

If the run is still active, wait, or retry with -lock-timeout=10m so Terraform waits for the lock. If you are sure it is stale, run terraform force-unlock <LOCK_ID> from a correctly initialised working directory; it only removes the lock, not changes. On Azure you can also break the blob lease in the portal or with az storage blob lease break.

Why caution matters: if another run is really applying, removing its lock allows two writers. Both read the same state version and the last one to write wins, so resources created by the other run vanish from state, leading to duplicates or orphans. Frequent stale locks indicate that pipeline timeouts or cancellations kill Terraform; fix those, and serialise runs per state.

How it works

  1. Terraform tries to acquire the lock; backend reports it is held.
  2. Read the lock info from the error.
  3. Check CI and colleagues for an active run.
  4. Active: wait or use -lock-timeout.
  5. Stale: terraform force-unlock <ID>, then plan to verify state.
  6. Fix the root cause (timeouts, concurrency).

Example

Error: Error acquiring the state lock
Lock Info:
  ID:        6f1c2b7e-3d1a-4c8e-9b0f-1a2b3c4d5e6f
  Path:      acme-tfstate-prod/network/terraform.tfstate
  Operation: OperationTypeApply
  Who:       runner@gha-runner-42
  Version:   1.14.0
  Created:   2026-11-21 07:12:44 UTC
terraform force-unlock 6f1c2b7e-3d1a-4c8e-9b0f-1a2b3c4d5e6f
terraform plan    # confirm state matches reality after the crashed apply

Common mistakes

  • Force-unlocking without checking who holds the lock.
  • Running with -lock=false to get past the error.
  • Not checking state consistency after a crashed apply.

How to answer in the interview

"The error means someone else holds the lock: another engineer or pipeline is running plan or apply on the same state, or a previous run crashed or was cancelled and never released it. The message gives the lock ID, who created it, when and which operation. First I check whether that run is still active in CI and ask the person; if it is, I wait. Only if I'm sure the lock is stale, like a runner killed hours ago, do I run terraform force-unlock with the ID, or break the blob lease on Azure, then plan to verify state. Removing a lock during a real apply can cause two writers and corrupted state. Repeated stale locks mean pipeline timeouts need fixing."

Likely follow-up questions

  • Pipelines queue instead of fail? CI concurrency groups per state, -lock-timeout, or HCP Terraform run queues.
  • What does force-unlock change? Only the lock, not state or resources.
  • After a crashed apply? Run a plan and look for missing or duplicate resources.
