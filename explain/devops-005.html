What is the difference between git merge and git rebase? When would you avoid rebase?

Git · concept · levels entry

In one line

git merge combines branches with a merge commit and preserves true history; git rebase replays commits on a new base for a linear history but rewrites commit hashes, so avoid rebasing shared branches others have pulled.

Detailed explanation

Imagine feature branched from main at commit B, and main has since moved to D.

Merge: git checkout feature && git merge main (or merging feature into main) creates a new merge commit with two parents. Nothing existing is rewritten, so the history shows exactly what happened and when branches diverged. It is safe on shared branches. The downside is a noisier log with many merge commits, especially if people merge main into their branches repeatedly.

Rebase: git checkout feature && git rebase main takes the feature commits, temporarily removes them, moves the branch to D and replays each commit on top. The result is a linear history as if you had started from D. But each replayed commit is a new commit with a new hash. If someone else already pulled the old commits, their history now diverges, and you must force push, which can overwrite their work.

Golden rule: do not rebase branches that others are using (main, release branches, shared feature branches). Rebasing your own local or personal branch is fine and common: keep it up to date with git pull --rebase or git rebase main, and use interactive rebase (git rebase -i) to squash fixup commits and tidy messages before opening a pull request. Then merge via the PR (merge commit, squash or rebase-merge, depending on team policy).

Conflicts: with merge you resolve all conflicts once in the merge commit. With rebase you may resolve them commit by commit as each one is replayed (git rebase --continue, or --abort to give up). git rerere can remember resolutions.

When you must force push your own branch, use --force-with-lease, which refuses to overwrite the remote if someone pushed commits you have not seen.

How it works

  1. Merge: find common ancestor, combine changes, create a commit with two parents.
  2. Rebase: find common ancestor, save your commits as patches.
  3. Reset branch to the new base.
  4. Re-apply each patch, creating new commits; stop on conflicts.
  5. Push: normal for merge; --force-with-lease for rebased branches.

Example

# Keep my feature branch current with a linear history
git fetch origin
git switch feature/login
git rebase origin/main          # resolve conflicts, then: git rebase --continue
git rebase -i origin/main       # squash "fix typo" commits
git push --force-with-lease

# Merging a shared branch: no history rewrite
git switch main
git merge --no-ff release/2.4

Common mistakes

  • Rebasing main or a shared branch and force pushing.
  • Using --force instead of --force-with-lease.
  • Endless "Merge branch main into feature" commits cluttering history.
  • Panicking mid-rebase instead of using git rebase --abort.

How to answer in the interview

"Merge combines branches with a merge commit that has two parents, preserving the true history, though the log can get noisy. Rebase replays my commits on top of another branch, giving a clean linear history, but it rewrites history because the hashes change. So I avoid rebasing shared or public branches others have pulled, since it forces a force push and breaks their history. My workflow is to rebase my own feature branch on main and squash with interactive rebase, then merge through a pull request. With rebase, conflicts may need resolving commit by commit."

Likely follow-up questions

  • What does --force-with-lease protect against? Overwriting remote commits someone else pushed since your last fetch.
  • Recover from a bad rebase? git reflog to find the old commit and git reset --hard to it.
  • Squash merge vs rebase merge? Squash makes one commit per PR; rebase merge keeps individual commits linearly.
