How do you deploy containers on AWS without managing servers? Compare Fargate, App Runner and Lambda containers.

Cloud (AWS) · concept · levels mid

In one line

Fargate runs ECS tasks or EKS pods without managing EC2 while you keep full control of the container platform, App Runner turns an image or repository into a scaled HTTPS service with almost no configuration, and Lambda container images run event-driven functions up to 10 GB that scale per request with a 15-minute limit.

Detailed explanation

Fargate is a compute engine for ECS and EKS. You still define task definitions or pod specs, services, VPC networking, load balancers, IAM roles and scaling rules; AWS provisions and patches the isolated compute per task. Billing is per second for vCPU and memory, with Fargate Spot for interruptible work and Graviton support. It suits long-running services, workers and batch tasks needing full control over networking, sidecars and deployment strategies, but each task has fixed CPU and memory and you pay while idle unless scaled down.

App Runner is a fully managed web service platform: point it at an ECR image or a source repository, and it builds, deploys, load balances with TLS, auto scales on concurrent requests per instance, and gives you an HTTPS URL with custom domains. It can connect to a VPC for private resources. The trade-offs are fewer configuration options, HTTP request-response workloads only, limited networking and observability controls, and slower feature evolution; check current regional availability and service status before standardising on it.

Lambda container images let you package functions with your own tooling as OCI images up to 10 GB, using AWS base images or the Runtime Interface Client. They keep Lambda's model: event triggers from API Gateway, SQS, EventBridge or S3, scaling per request to thousands of concurrent environments, pay per millisecond, up to 10 GB memory and a 15-minute maximum duration, with possible cold starts.

The decision trades control vs simplicity, traffic pattern (steady, spiky, event-driven), runtime limits, networking needs and cost at the expected volume.

How it works

  1. Build an image and push it to ECR.
  2. Fargate: create a task definition and ECS service behind an ALB.
  3. App Runner: create a service from the image with scaling settings.
  4. Lambda: create a function with PackageType Image and attach triggers.
  5. Monitor cost and latency; move workloads as patterns change.

Example

# Lambda from a container image
aws lambda create-function --function-name resize-image \
  --package-type Image \
  --code ImageUri=111122223333.dkr.ecr.eu-west-1.amazonaws.com/resize:1.2 \
  --role arn:aws:iam::111122223333:role/resize-lambda \
  --memory-size 2048 --timeout 60

# App Runner from an image
aws apprunner create-service --service-name internal-api \
  --source-configuration '{"ImageRepository":{"ImageIdentifier":
    "111122223333.dkr.ecr.eu-west-1.amazonaws.com/api:3.0",
    "ImageRepositoryType":"ECR","ImageConfiguration":{"Port":"8080"}},
    "AuthenticationConfiguration":{"AccessRoleArn":"arn:aws:iam::111122223333:role/apprunner-ecr"}}'

Common mistakes

  • Running long jobs in Lambda that hit the 15-minute limit.
  • Using Fargate for very spiky, low-volume APIs and paying for idle tasks.
  • Choosing App Runner and later needing networking or deployment features it lacks.
  • Ignoring cold starts for large Lambda images on latency-sensitive paths.

How to answer in the interview

"Fargate runs ECS tasks or EKS pods without EC2: I still define services, networking and load balancers, but AWS provides and patches the compute, billed per second. App Runner is the simplest: give it an image or repo and it builds, deploys, load balances, scales on concurrent requests and gives me an HTTPS URL, with fewer options. Lambda runs container images up to 10 GB as functions, scaling per request with event triggers, scale to zero and a 15-minute limit. I choose by how much control I need, traffic pattern, runtime limits and cost."

Likely follow-up questions

  • Which for a simple internal API with spiky traffic? Lambda behind API Gateway or a function URL, or App Runner if it must be a long-running web server.
  • Fargate or EC2 for ECS? Fargate for less ops; EC2 for GPUs, high utilisation savings or daemon-heavy setups.
  • How reduce Lambda image cold starts? Smaller images, provisioned concurrency, or SnapStart for supported runtimes.
