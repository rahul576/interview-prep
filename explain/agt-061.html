Build an on-call assistant that answers questions using runbooks and past incidents. How would you design it?

AI Agents & AIOps · design · levels mid, senior

In one line

Build a RAG assistant over runbooks, postmortems, incident tickets and chat summaries tagged with service, symptom, date and resolution metadata, retrieve with alert context and hybrid search, answer with steps and citations, keep content fresh by flagging stale runbooks, and add read-only live-data tools.

Detailed explanation

On-call engineers often handle services they did not build. The knowledge they need exists, scattered across runbooks, old postmortems, ticket comments and incident chat threads, but finding it at 2 a.m. is slow. An assistant can bring it to them.

Ingestion: index runbooks, postmortems, incident tickets, summarised incident channels (raw chat is too noisy) and service docs. Chunk by section and attach metadata: service, component, symptoms, error messages, alert names, date, resolution and author. Retrieval: when an alert fires or someone asks a question, use the alert context (service, alert name, error text) as the query and filter. Use hybrid search, combining keyword (BM25) with vectors, because exact error strings and alert names matter, then re-rank.

Answers give concrete steps with citations so engineers can open the source, plus "similar incident INC-1870 was resolved by …". Freshness is a real problem: show document dates, flag runbooks not reviewed in, say, six months, and ask for feedback after incidents ("did this runbook help?"). Finally, read-only tools for live data let the assistant check whether the current state matches runbook assumptions, such as "the runbook says check replica lag; current lag is 0 s".

How it works

  1. Ingest sources on change; chunk by headings; attach metadata.
  2. Summarise incident channels into structured records.
  3. On alert or question: build query from context, filter by service.
  4. Hybrid retrieve, re-rank, take top sections.
  5. Generate an answer with steps, citations and dates.
  6. Optional live checks; collect feedback and flag stale docs.

Example

Alert: OrdersQueueLagHigh (orders-worker, prod)
Assistant:
1. Check consumer pods are running and not throttled — Runbook "orders-worker" §2 (reviewed 2026-09-14)
2. If lag grows with normal pod health, check orders-db write latency — §4
Similar: INC-2033 (2026-07-02) same alert; cause: DB index lock during migration; fix: paused migration
Live check: consumers 12/12 ready, DB write p99 840 ms (normal 40 ms) → step 2 likely relevant

Common mistakes

  • Indexing raw chat logs full of noise and speculation.
  • Pure vector search missing exact error codes.
  • No dates or review status on answers.
  • No way to report wrong or outdated content.

How to answer in the interview

"I'd build RAG over runbooks, postmortems, incident tickets and summarised incident channels, each chunk tagged with service, symptoms, error messages, date and resolution. When an alert fires, the alert context drives retrieval, with hybrid search because exact error strings matter. The answer gives concrete steps with citations and mentions how similar incidents were resolved. Because operational content goes stale fast, I show dates, flag runbooks that haven't been reviewed and collect feedback after incidents. Read-only tools let it check live state against the runbook."

Likely follow-up questions

  • Keeping runbooks current? Review dates, ownership, and updates as postmortem action items.
  • Access control? Respect source permissions at retrieval time.
  • Evaluate quality? Replay past alerts and check retrieved sections.
