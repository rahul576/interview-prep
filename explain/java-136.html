How do you make an API safe against duplicate requests, for example in payments?

REST & API Design · design · levels senior, lead

In one line

Require clients to send an Idempotency-Key per logical operation; the server atomically records the key (unique constraint or Redis SET NX) before processing, stores the response, returns that same response for repeats, handles concurrent in-flight duplicates, scopes keys per client and expires them after a TTL.

Detailed explanation

Duplicate requests are normal: a mobile app times out and retries, a user double-clicks Pay, a gateway retries on 502. For a payment, processing twice means charging twice. Since POST is not idempotent, we make it idempotent at the application level.

Client side. The client generates a unique key (UUID) for each logical operation, such as "pay order 123", and reuses the same key for every retry. It sends it in a header, commonly Idempotency-Key (an IETF draft standardises this header; Stripe popularised it).

Server side.

  1. Claim the key atomically before doing work: insert a row (client_id, key, request_hash, status=IN_PROGRESS) with a unique constraint, or SET key value NX EX 86400 in Redis. Only one request can win.
  2. If the insert succeeds, process the payment, then store the status code and response body with the key and mark it COMPLETED.
  3. If the key already exists and is COMPLETED, return the stored response without processing.
  4. If it is IN_PROGRESS (a concurrent duplicate), return 409 Conflict (or 425/429 with Retry-After), or wait briefly and then return the result.
  5. If the same key arrives with a different request body (hash mismatch), reject with 422 or 409: it is a client bug.

Scope and expiry. Keys are unique per client or merchant, not globally, and expire after e.g. 24 hours. For crash safety, an IN_PROGRESS record older than a timeout can be retried or reconciled.

Downstream. Pass an idempotency key to the payment provider too, so a retry after a timeout towards the provider does not charge twice. Inside the system, a unique constraint on business identifiers (one payment per order) is a second line of defence, and consumers of events dedupe by event id.

For ten instances, the key store must be shared: the database (simplest and transactional with the payment) or Redis.

How it works

  1. Request with key arrives.
  2. Atomic insert/claim; losers read existing record.
  3. Winner processes and stores the response.
  4. Repeats get the stored response; in-flight repeats get 409.
  5. Keys expire after TTL.

Example

CREATE TABLE idempotency_keys (
  client_id    VARCHAR(64),
  idem_key     VARCHAR(64),
  request_hash CHAR(64) NOT NULL,
  status       VARCHAR(16) NOT NULL,
  response     JSONB,
  created_at   TIMESTAMPTZ DEFAULT now(),
  PRIMARY KEY (client_id, idem_key)
);
@PostMapping("/payments")
ResponseEntity<?> pay(@RequestHeader("Idempotency-Key") String key, @RequestBody PayRequest req) {
    String hash = sha256(req);
    Optional<IdemRecord> existing = store.tryClaim(clientId(), key, hash); // INSERT ... ON CONFLICT DO NOTHING
    if (existing.isPresent()) {
        IdemRecord r = existing.get();
        if (!r.hash().equals(hash)) return ResponseEntity.unprocessableEntity().build();
        if (r.inProgress()) return ResponseEntity.status(409).build();
        return r.toResponse();
    }
    PaymentResult result = payments.charge(req, key);      // provider idempotency key too
    store.complete(clientId(), key, 201, result);
    return ResponseEntity.status(201).body(result);
}

Common mistakes

  • Check-then-insert without atomicity (race between instances).
  • Storing keys in local memory with multiple instances.
  • Not storing the response, so repeats behave differently.
  • Ignoring a different body reusing the same key.
  • No expiry, so the table grows forever.

How to answer in the interview

"Clients send an idempotency key header, unique per logical operation and reused on retries. The server claims the key atomically before processing, with a unique constraint in the database or SET NX in Redis, so with ten instances only one request wins. After processing it stores the status and response with the key, and any repeat gets exactly that stored response instead of a second charge. If a duplicate arrives while the first is still running, I return 409 or make it wait. Keys are scoped per client, tied to a hash of the request body, and expire after something like 24 hours. I also pass an idempotency key to the payment provider and keep a unique constraint per order."

Likely follow-up questions

  • Where would you store idempotency keys for a service with ten instances? In a shared store: the database, ideally in the same transaction as the payment, or Redis.
  • What if the server crashes mid-processing? The IN_PROGRESS record times out and is reconciled with the provider before retrying.
  • Who generates the key? The client, so retries carry the same key.
