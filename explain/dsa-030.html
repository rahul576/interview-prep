What is Big-O notation? Compare O(1), O(log n), O(n), O(n log n) and O(n^2) with examples.

DSA: Algorithms & DP · concept · levels entry

In one line

Big-O describes an upper bound on how time or space grows with input size n, ignoring constants and lower-order terms. In order of growth: O(1) (array index, hash lookup), O(log n) (binary search), O(n) (single scan), O(n log n) (efficient sorting) and O(n²) (nested loops over all pairs). Also consider space, worst versus average case, and amortised cost.

Detailed explanation

Big-O lets us compare algorithms independently of hardware. Saying an algorithm is O(f(n)) means that for large enough n, its cost is at most c·f(n) for some constant c. Constants are dropped (3n + 10 is O(n)), and only the dominant term counts (n² + n is O(n²)). Strictly, Big-O is an upper bound, Ω a lower bound and Θ a tight bound. In interviews "Big-O" usually means the tight worst case.

The common classes, with roughly what n = 1,000,000 means:

  • O(1), constant: array[i], HashMap.get (average), pushing onto a stack. 1 step.
  • O(log n), logarithmic: halving each step, as in binary search, balanced BST/TreeMap operations, and heap push/pop. About 20 steps.
  • O(n), linear: one pass, such as finding the max, summing, or a linear search. 10⁶ steps.
  • O(n log n): merge sort, TimSort, heap sort, building from sorted runs. About 2×10⁷.
  • O(n²), quadratic: nested loops over all pairs, bubble or insertion sort, naive duplicate detection. 10¹², which is infeasible. Quadratic code typically becomes painfully slow somewhere around 10⁴–10⁵ elements.
  • Beyond: O(2ⁿ) (all subsets) and O(n!) (all permutations) are only feasible for tiny n.

Space complexity counts extra memory: a hash map of n entries is O(n), and recursion depth counts too (O(h) for tree DFS).

Cases and amortisation:

  • Worst versus average: quicksort is O(n log n) on average but O(n²) worst case. HashMap.get is O(1) average, and O(log n) worst case in Java 8+ thanks to treeified buckets.
  • Amortised: ArrayList.add is usually O(1). Occasionally the backing array grows by about 1.5x and copies everything (O(n)). Since growth is geometric, the total copying over n adds is O(n), so each add is O(1) amortised.

Big-O ignores constants. For small n, or cache-friendly code, a "worse" algorithm can be faster in practice. Insertion sort beats merge sort on tiny arrays, which is why hybrids exist.

How it works

  1. Identify the input size(s): n, or m and n for two inputs.
  2. Count how the loops and recursion scale: sequential parts add, nested parts multiply.
  3. Halving gives log n. Branching recursion gives exponential cost unless memoised.
  4. Keep the dominant term and drop the constants.
  5. State the time and the extra space, plus the case (worst, average, amortised).

Example

int first(int[] a)            { return a[0]; }                       // O(1)
int find(int[] sorted, int x) { return Arrays.binarySearch(sorted, x); } // O(log n)
int max(int[] a)  { int m = a[0]; for (int v : a) m = Math.max(m, v); return m; } // O(n)
void sort(int[] a)            { Arrays.sort(a); }                    // O(n log n)
boolean hasDup(int[] a) {                                            // O(n^2)
    for (int i = 0; i < a.length; i++)
        for (int j = i + 1; j < a.length; j++)
            if (a[i] == a[j]) return true;
    return false;
}
// hasDup with a HashSet: O(n) time, O(n) space -> the classic time/space trade-off

Common mistakes

  • Treating O(n + m) as O(n) when the two inputs are independent.
  • Calling list.contains or String concatenation inside a loop "O(n)", when it is O(n²) overall.
  • Forgetting recursion stack space.
  • Confusing amortised with average case.

How to answer in the interview

"Big-O describes an upper bound on how running time or memory grows as the input grows, ignoring constants and lower-order terms. O(1) is constant, like an array index or a hash map lookup. O(log n) halves the problem each step, like binary search. O(n) is a single pass. O(n log n) is efficient comparison sorting, like merge sort or TimSort. O(n squared) comes from nested loops over all pairs, which becomes impractical around a hundred thousand elements. I always state space complexity too, and whether I mean worst case, average or amortised. ArrayList add, for example, is amortised O(1)."

Likely follow-up questions

  • Why is ArrayList add amortised O(1)? Geometric growth means the total copy cost over n adds is O(n).
  • Big-O versus Big-Theta? O is an upper bound, Θ is a tight bound, Ω is a lower bound.
  • Complexity of HashMap get? O(1) on average, O(log n) worst case with treeified buckets (Java 8+).
