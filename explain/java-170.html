How do you handle API versioning and backward compatibility between microservices?

Microservices · concept · levels senior, lead

In one line

Make changes additive and backward compatible by default, have consumers act as tolerant readers, introduce a new version (URI or header) only for unavoidable breaking changes, catch breaks with contract tests in CI, and deprecate old versions with timelines and usage monitoring.

Detailed explanation

Independent deployment only works if a provider can release without breaking its consumers. The first rule is backward compatibility: add new optional fields, new endpoints, new enum values only if consumers handle unknowns; never remove, rename or change the type or meaning of a field, never make an optional input mandatory. Postel's principle applies on the consumer side as the tolerant reader: ignore unknown fields (Jackson FAIL_ON_UNKNOWN_PROPERTIES=false, which Spring Boot already sets), read only what you need, and handle missing optional data. For events, a schema registry with a compatibility mode (backward or full) enforces the same rule automatically.

When a breaking change is unavoidable, introduce a new version and run old and new side by side. Options: URI versioning (/v2/orders), simple and visible, widely used for public APIs; header or media-type versioning (Accept: application/vnd.acme.order.v2+json), keeping URIs stable; for events, a new event type or topic. Internally, the provider often maps both versions onto one domain model. Spring Framework 7 also added first-class API versioning support to request mappings, which makes header or path versioning easier to wire.

To prevent accidents, run consumer-driven contract tests with Pact or Spring Cloud Contract in CI: consumers publish expectations, and the provider build fails if it breaks them; can-i-deploy checks gate releases. OpenAPI diff tools flag breaking spec changes in pull requests.

Finally, deprecate deliberately: announce a timeline, add Deprecation and Sunset headers, document migration, and monitor usage per client (client id in the token or a header, gateway metrics) so you know when v1 traffic reaches zero.

How it works

  1. Propose a change; check if it is additive.
  2. If additive: ship, consumers ignore unknown fields.
  3. If breaking: add v2 alongside v1.
  4. Contract tests and OpenAPI diff verify compatibility in CI.
  5. Mark v1 deprecated with Sunset date; notify owners.
  6. Track v1 calls per client; remove when zero.

Example

@RestController
@RequestMapping("/api")
class OrderController {
    @GetMapping("/v1/orders/{id}")
    OrderV1 v1(@PathVariable UUID id, HttpServletResponse res) {
        res.setHeader("Deprecation", "true");
        res.setHeader("Sunset", "Wed, 31 Mar 2027 23:59:59 GMT");
        return mapper.toV1(service.find(id));
    }
    @GetMapping("/v2/orders/{id}")
    OrderV2 v2(@PathVariable UUID id) { return mapper.toV2(service.find(id)); }
}

Common mistakes

  • Bumping the version for every small change.
  • Renaming a field "because it is cleaner".
  • Strict deserialisation that fails on new fields.
  • Removing v1 without knowing who still calls it.

How to answer in the interview

"My default is that every change is additive and backward compatible: add optional fields, never remove, rename or change meanings. Consumers are tolerant readers that ignore unknown fields. When a breaking change is unavoidable, I add a new version, usually /v2 in the path or a header, run both side by side and migrate consumers. Contract tests with Pact or Spring Cloud Contract in CI catch accidental breaks before deployment, and a schema registry does the same for events. Old versions get a deprecation timeline with Sunset headers, and I monitor usage per client to know when removal is safe."

Likely follow-up questions

  • How do you find who still calls v1? Gateway or service metrics tagged by client id from the token or a client header.
  • Is adding an enum value safe? Only if consumers handle unknown values; otherwise treat it as breaking.
  • Consumer-driven contracts vs OpenAPI? OpenAPI describes the API; contracts verify what real consumers actually rely on.
