What is chaos engineering, and how would you introduce it safely?

Observability & SRE · concept · levels senior, lead

In one line

Chaos engineering is the practice of deliberately injecting failures in a controlled experiment, with a hypothesis about steady state, a limited blast radius and abort conditions, to discover weaknesses before real outages do.

Detailed explanation

Distributed systems fail in ways nobody designed for: a slow dependency, a lost availability zone, DNS that stops resolving, a full disk. Chaos engineering, popularised by Netflix's Chaos Monkey, flips the approach from "hope it works" to "prove it works". It is not random destruction; it is the scientific method applied to resilience.

Each experiment starts by defining the steady state in business metrics, such as orders per minute or checkout success rate, then a hypothesis: "if one database replica fails, checkout success stays above 99%". You inject the fault, observe, and compare. If the hypothesis holds, confidence increases; if not, you found a weakness cheaply, with engineers watching, rather than at 3 a.m.

Introducing it safely is the real interview topic. Prerequisites are good observability (otherwise you cannot see the impact) and basic resilience patterns already in place. Then you grow maturity gradually: tabletop exercises, staging experiments, then production with a tiny blast radius (one pod, one percent of traffic, one zone), during working hours, with the on-call team informed, automatic stop conditions tied to alarms, and a quick rollback. Popular tools are Chaos Mesh and LitmusChaos (both CNCF projects for Kubernetes), AWS Fault Injection Service (FIS) with CloudWatch stop conditions, Azure Chaos Studio and Gremlin.

How it works

  1. Get buy-in and agree rules: scope, hours, communication, who can abort.
  2. Define steady-state metrics and a written hypothesis.
  3. Pick the smallest meaningful fault and blast radius.
  4. Configure abort conditions on SLO or alarm thresholds.
  5. Run the experiment, observe dashboards, stop if needed.
  6. Hold a short review, file fixes, and repeat, eventually automating experiments in CI or on a schedule.

Example

apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata: { name: payments-db-latency, namespace: payments }
spec:
  action: delay
  mode: one
  selector:
    labelSelectors: { app: payments-api }
  delay: { latency: "300ms", jitter: "50ms" }
  direction: to
  target:
    mode: all
    selector:
      labelSelectors: { app: payments-db }
  duration: "10m"

Common mistakes

  • Starting in production without observability or abort conditions.
  • Running experiments without telling the on-call team.
  • Testing only pod kills, never latency, DNS or dependency failures.
  • Finding weaknesses but never fixing them.
  • Treating it as a one-off game day instead of a continuous practice.

How to answer in the interview

"Chaos engineering means running controlled experiments that inject failures, like killing pods, adding latency or failing a dependency, to find weaknesses before customers do. Every experiment starts with a steady-state metric and a hypothesis, for example checkout success stays above 99 percent if a replica dies. To introduce it safely I make sure observability is good, start in staging, then move to production with a tiny blast radius, during working hours, with automatic stop conditions and the on-call team informed. Tools like Chaos Mesh, Litmus, AWS FIS or Gremlin help. The value comes from the follow-up: game days that turn findings into fixes."

Likely follow-up questions

  • First experiment for a payments service? Add latency to its main dependency and verify timeouts, retries and fallbacks keep the SLO.
  • How do you convince management? Frame it as cheaper, scheduled discovery of outages, and show results from staging first.
  • Chaos versus load testing? Load testing checks capacity; chaos tests behaviour when components fail.
