When would you choose a managed Kubernetes service such as EKS, AKS or GKE over self-managed Kubernetes?

Kubernetes · design · levels mid, senior, lead

In one line

In the cloud, choose managed Kubernetes (EKS, AKS, GKE) for a provider-run control plane and etcd, SLA, easier upgrades and native integrations; choose self-managed for on-premises, edge, air-gapped or special control-plane needs. Either way, shared responsibility: nodes, add-ons, security and workloads remain yours.

Detailed explanation

Running a control plane well means operating etcd (quorum, backups, defragmentation, disk latency), securing and scaling API servers, rotating certificates, upgrading every few months across a supported version window, and being on call for all of it. For most companies this is undifferentiated work. Managed services run it for you, offer an uptime SLA (on paid tiers), and integrate with the cloud: IAM and workload identity (EKS Pod Identity or IRSA, AKS Workload Identity, GKE Workload Identity Federation), load balancers, CSI storage drivers, autoscaling and monitoring. Upgrades become a command or an automatic channel.

Self-managed (kubeadm, Rancher RKE2, OpenShift, Talos, k3s for edge) makes sense when there is no cloud provider: on-premises data centres, edge sites, air-gapped or sovereign environments, or when you need control-plane configuration a provider does not allow, such as custom admission plugins, API server flags or specific etcd setups. Some organisations also self-manage for portability or licensing, but that is a deliberate investment in a platform team.

Shared responsibility is often misunderstood. With a managed service you still own: node OS images and node upgrades, version upgrades (just easier), add-ons (ingress or Gateway controllers, cert-manager, CNI configuration), network design and IP planning, RBAC and security settings, backups of your data, and all workloads.

Fully managed modes such as GKE Autopilot, EKS Auto Mode and AKS Automatic go further: the provider also manages nodes, scaling and many defaults, often with per-pod pricing, at the cost of less control (restricted privileged workloads, limited node customisation).

How it works

  1. Define requirements: location, compliance, scale, team skills.
  2. Cloud with no special needs: managed service.
  3. On-prem, edge, air-gapped: self-managed distribution.
  4. List what stays yours: nodes, add-ons, security, networking, workloads.
  5. Automate upgrades and node rotation either way.

Example

# managed: control plane upgrade is one command
az aks upgrade -g rg-prod -n prod-aks --kubernetes-version 1.34
# self-managed: you run each step yourself
sudo kubeadm upgrade plan
sudo kubeadm upgrade apply v1.34.2

Common mistakes

  • Assuming managed means no operations work.
  • Falling behind on versions until forced upgrades.
  • Self-managing for "control" without a team to support it.
  • Ignoring the SLA tier and its cost.

How to answer in the interview

"For most teams in the cloud I'd choose EKS, AKS or GKE. The provider runs and scales the control plane and etcd, provides an SLA and easy upgrades, and integrates with IAM and workload identity, load balancers and storage. Running control planes yourself needs real skills and on-call time that rarely differentiate the business. Self-managed with kubeadm, RKE2, OpenShift or Talos makes sense on-premises, at the edge, air-gapped, or when I need control-plane settings the provider doesn't allow. Either way it's shared responsibility: nodes, add-ons, security, networking and workloads stay with us."

Likely follow-up questions

  • What does Autopilot or AKS Automatic take away? Node management and sizing; you lose node customisation, privileged workloads and some flexibility.
  • What does the SLA cover? API server availability, not your workloads.
  • Hybrid options? Azure Arc, EKS Anywhere, GKE on-prem editions manage clusters outside the cloud.
