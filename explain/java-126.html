How do you handle exceptions and validation globally in a Spring Boot REST API?

Spring Boot · concept · levels entry, mid

In one line

Handle errors in one @RestControllerAdvice with @ExceptionHandler methods, validate DTOs with Bean Validation and @Valid, return a consistent ProblemDetail (RFC 9457) body with correct status codes, and log details server-side with a correlation id instead of leaking stack traces.

Detailed explanation

Without central handling, each controller has its own try/catch blocks and clients get inconsistent formats, or the default whitelabel or error JSON with internal details. @RestControllerAdvice (@ControllerAdvice + @ResponseBody) applies to all controllers; its @ExceptionHandler methods catch specific exception types and turn them into responses. Spring picks the handler for the most specific exception type.

Validation uses Jakarta Bean Validation (Hibernate Validator via spring-boot-starter-validation). Annotate DTO fields with @NotBlank, @Size, @Email, @Positive, @Pattern, and put @Valid on the @RequestBody parameter. Invalid input then throws MethodArgumentNotValidException before the controller body runs. For @RequestParam and @PathVariable constraints, Spring 6.1+ performs built-in method validation and throws HandlerMethodValidationException; with @Validated on a class, ConstraintViolationException is raised instead.

For the response shape, Spring Framework 6 provides ProblemDetail, which implements RFC 9457 Problem Details (successor of RFC 7807): type, title, status, detail, instance, plus custom properties such as a list of field errors. Extending ResponseEntityExceptionHandler gives ProblemDetail responses for Spring MVC's own exceptions too, or set spring.mvc.problemdetails.enabled=true.

Status codes: 400 for malformed input or validation errors, 404 not found, 409 conflicts, 422 for business rule violations if your API uses it, 500 for unexpected errors with a generic message. Log the full exception server-side with the trace id, and return that id so support can find it.

How it works

  1. Request DTO is deserialised and validated.
  2. Validation or business exceptions propagate out of the controller.
  3. The ExceptionHandlerExceptionResolver finds the matching @ExceptionHandler.
  4. The handler builds a ProblemDetail with status and details.
  5. The response is serialised as application/problem+json; the exception is logged.

Example

public record CreateUser(@NotBlank @Size(max = 50) String name, @Email @NotBlank String email) {}

@PostMapping("/users")
ResponseEntity<UserDto> create(@Valid @RequestBody CreateUser req) { ... }

@RestControllerAdvice
class GlobalErrors extends ResponseEntityExceptionHandler {

    @Override
    protected ResponseEntity<Object> handleMethodArgumentNotValid(MethodArgumentNotValidException ex,
            HttpHeaders headers, HttpStatusCode status, WebRequest request) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, "Validation failed");
        pd.setProperty("errors", ex.getBindingResult().getFieldErrors().stream()
            .map(f -> Map.of("field", f.getField(), "message", f.getDefaultMessage())).toList());
        return ResponseEntity.badRequest().body(pd);
    }

    @ExceptionHandler(UserNotFoundException.class)
    ProblemDetail notFound(UserNotFoundException ex) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
    }

    @ExceptionHandler(Exception.class)
    ProblemDetail unexpected(Exception ex) {
        log.error("Unhandled error", ex);
        return ProblemDetail.forStatusAndDetail(HttpStatus.INTERNAL_SERVER_ERROR, "Unexpected error");
    }
}

Common mistakes

  • Forgetting @Valid, so constraints never run.
  • Catch-all handlers returning ex.getMessage() that may expose SQL or internals.
  • Returning 500 for validation errors.
  • Different error formats from different services.

How to answer in the interview

"I centralise it in a @RestControllerAdvice with @ExceptionHandler methods, so each exception type maps to one response: not found to 404, validation to 400, conflicts to 409, anything unexpected to 500. Request DTOs carry Bean Validation annotations like @NotBlank and @Size, and @Valid on the request body makes invalid input fail before any business logic runs. The error body is always a ProblemDetail, the RFC 9457 format that Spring 6 supports, including a list of field errors. I never return stack traces; I log the full error with a correlation id and return that id to the client."

Likely follow-up questions

  • How would you return all field validation errors in one response? Collect getFieldErrors() from the binding result into a ProblemDetail property.
  • Why extend ResponseEntityExceptionHandler? It already maps Spring MVC exceptions (415, 405, malformed JSON) to ProblemDetail.
  • Where do business validations go? In the service layer, throwing domain exceptions mapped by the advice.
