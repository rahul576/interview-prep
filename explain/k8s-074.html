An important Deployment was deleted in production and nobody admits doing it. How do you find out what happened?

Kubernetes · scenario · levels mid, senior

In one line

The API server audit log records who (user or service account), what (verb, resource, name), when and from where (source IP, user agent); search for the delete on that Deployment, and remember the culprit is often automation (GitOps prune, Helm, an operator, CI), then fix RBAC and change management without blame.

Detailed explanation

Kubernetes audit logging is configured on the API server with an audit policy; on managed clusters you enable it and it ships to CloudWatch Logs (EKS control plane logging), Azure Monitor diagnostic settings (kube-audit or kube-audit-admin on AKS) or Cloud Audit Logs (GKE). Each event includes verb, objectRef (resource, namespace, name), user.username and groups, impersonatedUser, sourceIPs, userAgent and timestamps. If auditing was not enabled, the evidence may simply not exist, which is itself a finding.

Search for verb=delete, objectRef.resource=deployments, the name and namespace, around the time the Deployment disappeared. The userAgent is revealing: argocd-application-controller, Helm/3.x, kubectl/v1.34 or a Terraform provider. A ServiceAccount username like system:serviceaccount:argocd:argocd-application-controller means GitOps did it.

Automation is the usual answer. Argo CD or Flux pruned it because the manifest was removed or renamed in Git, or a path changed. Helm removed it because a template condition turned it off in the new values. An operator reconciled its owned resources. A CI job using a cluster-admin service account ran a cleanup script. Then check Git history and controller logs to see the triggering change. Kubernetes garbage collection can also delete objects whose ownerReferences point to a deleted owner.

Use the findings constructively: least-privilege RBAC so humans cannot delete in production, prune safeguards such as Argo CD Prune=false or Delete=false sync options for critical resources, admission policies protecting labelled objects, and all changes through reviewed GitOps PRs.

How it works

  1. Confirm when it disappeared (monitoring, events, Argo CD history).
  2. Query audit logs for delete on that object.
  3. Read user, groups, source IP and user agent.
  4. If automation, find the Git commit, Helm revision or controller log.
  5. Restore from Git; then apply RBAC, prune protection and policy fixes.
  6. Blameless review and change-management improvement.

Example

// AKS audit logs in Log Analytics
AKSAudit
| where Verb == "delete" and ObjectRef.resource == "deployments"
| where ObjectRef.name == "checkout" and ObjectRef.namespace == "shop"
| project TimeGenerated, User.username, SourceIps, UserAgent
# self-managed: JSON audit log on the control plane
jq 'select(.verb=="delete" and .objectRef.resource=="deployments" and .objectRef.name=="checkout")
    | {ts: .requestReceivedTimestamp, user: .user.username, ua: .userAgent, ip: .sourceIPs}' /var/log/kubernetes/audit.log

Common mistakes

  • Auditing not enabled until after the incident.
  • Assuming a human did it.
  • Shared admin credentials, making identity meaningless.
  • Punishing people instead of fixing access.

How to answer in the interview

"The API server audit log records every request with the user or service account, verb, resource, time, source IP and user agent, if auditing is enabled; managed clusters ship it to CloudWatch, Azure Monitor or Cloud Logging. I'd search for a delete on that deployment around the time it vanished. Often it isn't a person: Argo CD pruning after the manifest left Git, a Helm upgrade that dropped it, an operator, or a CI job with a powerful account. I'd check Git history and controller logs. The goal is learning, so I'd tighten RBAC, protect critical resources from pruning and route changes through GitOps."

Likely follow-up questions

  • Which audit level? Metadata for most resources, RequestResponse only for sensitive writes, None for noisy reads like events and health checks.
  • Why are shared accounts bad here? The audit log shows the account, not the person.
  • Can you prevent prune deletes? Argo CD sync options and resource annotations, plus policy.
