How do you make long-running agents durable so they survive crashes and restarts?

AI Agents & AIOps · concept · levels senior, lead

In one line

Make long-running agents durable by persisting state after every step (checkpoints), using durable execution engines such as Temporal or Azure Durable Functions, resuming from the last checkpoint, making side-effecting tools idempotent, running on queues and workers, and modelling human or external waits as persisted pauses with timeouts.

Detailed explanation

An agent investigating an incident, migrating a codebase or onboarding a customer may run for hours or days and wait for human approvals. Processes crash, pods are rescheduled, and deployments restart services. If the agent's state lives only in process memory and the model context, a restart means starting over: repeating expensive model calls and, worse, repeating side effects.

The foundation is checkpointing: after each step, persist the messages, plan, tool calls and results, and intermediate artefacts to a database or object store, keyed by a run or thread ID. LangGraph checkpointers (for example Postgres) do this per graph step; other frameworks have similar session stores.

Durable execution engines go further. Temporal, Azure Durable Functions, AWS Step Functions and similar services record each activity's result in an event history; after a crash, the workflow replays deterministically from that history and continues exactly where it stopped. Model calls and tool calls become activities with their own retries and timeouts. This turns an agent loop into a resilient workflow.

Replays and retries mean a step may execute more than once, so tools with side effects must be idempotent, typically with an idempotency key derived from run ID and step number, so a retried "create invoice" returns the existing invoice.

Runs should be driven by queues and stateless workers, not long-lived in-memory processes, so any worker can pick up a run. Waiting for human approval or a slow external system is a persisted pause: the workflow sleeps until a signal or timer, with timeouts and escalation, consuming no threads.

How it works

  1. Start a run with an ID; store initial state.
  2. Each model or tool call is a durable step with retries and timeout.
  3. After each step, persist state and results.
  4. Side-effecting tools use idempotency keys.
  5. Approvals and external waits are signals with timers.
  6. On crash, a worker resumes from the last checkpoint or event history.

Example

# Temporal workflow (Python SDK) wrapping an agent loop
@workflow.defn
class IncidentAgent:
    def __init__(self):
        self.approved = None

    @workflow.signal
    def approve(self, ok: bool):
        self.approved = ok

    @workflow.run
    async def run(self, incident_id: str):
        state = await workflow.execute_activity(load_context, incident_id,
                    start_to_close_timeout=timedelta(minutes=2))
        for step in range(30):
            action = await workflow.execute_activity(call_model, state,
                        start_to_close_timeout=timedelta(minutes=3))
            if action.kind == "final":
                return action.text
            if action.needs_approval:
                await workflow.wait_condition(lambda: self.approved is not None,
                                              timeout=timedelta(hours=4))
            state = await workflow.execute_activity(run_tool, action,
                        start_to_close_timeout=timedelta(minutes=5))  # tool uses idempotency key

Common mistakes

  • Keeping run state only in memory or only in the model context.
  • Non-idempotent tools that duplicate actions on retry.
  • Blocking threads while waiting hours for approval.
  • No timeouts on human waits, so runs hang forever.
  • Non-deterministic code inside replayed workflow logic.

How to answer in the interview

"A long-running agent can't live only in a process's memory. I persist its state after every step, messages, plan, tool results and artefacts, as checkpoints, which frameworks like LangGraph support. For stronger guarantees I run the loop on a durable execution engine like Temporal or Durable Functions, where each model and tool call is an activity and the workflow resumes exactly where it stopped after a crash. Because steps may be retried or replayed, side-effecting tools use idempotency keys. Work runs on queues and workers, and waits for human approval are persisted pauses with timeouts rather than blocked threads."

Likely follow-up questions

  • What state must never be only in the model context? Completed side effects, IDs of created resources, approvals and the plan.
  • Why must workflow code be deterministic in Temporal? Because it is replayed from history; non-deterministic work belongs in activities.
  • How do you resume after a model version change? Pin the version per run or make the state model-agnostic so a new model can continue.
