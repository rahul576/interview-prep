Why should the Terraform state file never be committed to Git?

Infrastructure as Code · concept · levels entry

In one line

The state file contains secrets in plain text and needs locking, which Git cannot provide; keep it in an encrypted, versioned, locked remote backend and add .tfstate to .gitignore.

Detailed explanation

Terraform state maps each resource address to the real object and stores every attribute Terraform knows about it. That routinely includes sensitive data: database master passwords, generated random_password results, private keys from tls_private_key, access keys, connection strings. Marking values sensitive only hides them in CLI output; in state they are plain JSON. Committing state therefore leaks secrets to everyone with repository access, to every fork and clone, and forever in history, because deleting the file later does not remove old commits.

The second problem is concurrency. Terraform expects one writer at a time, protected by a lock. Git has no locking: two engineers on different branches can both apply, each pushing a state that knows only about their own changes. The state diverges from reality, resources become orphaned or get recreated, and resolving a merge conflict in a large JSON state with serial numbers and lineage is practically impossible to do correctly. Git also makes it easy to apply with a stale state pulled days ago.

The answer is a remote backend: S3 (with native lockfile locking in recent Terraform versions, or the older DynamoDB table), Azure Storage with blob leases, Google Cloud Storage, or HCP Terraform. The backend should have encryption at rest (ideally with a customer-managed key), versioning so a corrupted state can be rolled back, restricted access to the pipeline role and a few admins, and access logging.

How it works

  1. Configure a backend block; run terraform init -migrate-state to move existing local state.
  2. Each plan/apply acquires a lock, reads state remotely, writes it back, releases the lock.
  3. Versioning keeps previous states for recovery.
  4. .gitignore excludes .tfstate, .tfstate.* and .terraform/.

Example

terraform {
  backend "s3" {
    bucket       = "acme-tfstate-prod"
    key          = "network/terraform.tfstate"
    region       = "eu-west-1"
    encrypt      = true
    kms_key_id   = "alias/tfstate"
    use_lockfile = true
  }
}

Common mistakes

  • Committing state "just for the first setup" and leaving it in history.
  • A state bucket readable by every developer.
  • No versioning, so a bad write cannot be undone.
  • Running applies against local copies of a remote state.

How to answer in the interview

"Two reasons. First, state holds every attribute Terraform knows, often including database passwords, private keys and tokens in plain text, so committing it leaks secrets to everyone with repo access, permanently in history. Second, Git has no locking: two people applying from different branches overwrite each other, state drifts from reality, and merge conflicts in state JSON are almost impossible to resolve safely. So state lives in a remote backend like S3 with locking, Azure Storage, GCS or HCP Terraform, encrypted, versioned and restricted, and tfstate files are in .gitignore."

Likely follow-up questions

  • How would you recover if state with secrets was already pushed? Rotate every secret in it first, migrate state to a remote backend, then purge history (git filter-repo) and force-push, accepting clones may still have it.
  • What if a lock is stuck? Confirm no run is active, then terraform force-unlock <id>.
  • How do you roll back a corrupted state? Restore a previous object version from the versioned bucket.
