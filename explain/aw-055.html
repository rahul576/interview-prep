How do you upload and download large objects efficiently with S3, and what consistency does S3 provide?

Cloud (AWS) · concept · levels mid

In one line

Use multipart upload (parallel, retryable parts, required above 5 GB) and byte-range GETs for large objects, Transfer Acceleration for distant clients, spread load across prefixes for higher request rates, and rely on S3's strong read-after-write consistency for all operations since December 2020.

Detailed explanation

A single PUT can upload at most 5 GB; objects up to 50 TB need multipart upload: CreateMultipartUpload, then UploadPart for parts of 5 MiB to 5 GiB (up to 10,000 parts), uploaded in parallel and retried individually, then CompleteMultipartUpload. AWS recommends it from around 100 MB. The AWS CLI, SDK transfer managers and the AWS Common Runtime (CRT) clients do this automatically with tuned concurrency. Incomplete uploads keep their parts stored and billed, so add a lifecycle rule to abort them after a few days.

For downloads, byte-range GETs request ranges in parallel and allow resuming failed transfers; CRT clients do this too. S3 Transfer Acceleration routes traffic over the CloudFront edge network and AWS backbone, which helps users far from the bucket's region; use its speed comparison tool to verify benefit. For very large one-off moves, DataSync or Snowball fit better.

Request rates: each prefix supports at least 3,500 PUT/COPY/POST/DELETE and 5,500 GET/HEAD requests per second, and S3 partitions automatically as load grows. Spread hot workloads across many prefixes; there is no limit on prefixes. Expect brief 503 Slow Down errors while S3 scales, so use retries with backoff. For latency-critical access, S3 Express One Zone offers single-digit millisecond reads.

Consistency: since December 2020, S3 provides strong read-after-write consistency for new objects, overwrites, deletes and LIST operations, at no cost. Concurrent writers to the same key still follow last-writer-wins, and conditional writes (If-None-Match, If-Match) prevent overwrites.

How it works

  1. Client splits a 20 GB file into 100 MB parts.
  2. CreateMultipartUpload returns an upload ID.
  3. Parts upload in parallel; failed parts retry alone.
  4. CompleteMultipartUpload assembles the object atomically.
  5. Readers immediately see the new object; downloads use parallel range GETs.

Example

aws configure set default.s3.multipart_threshold 100MB
aws configure set default.s3.multipart_chunksize 100MB
aws configure set default.s3.max_concurrent_requests 20
aws s3 cp big-backup.tar s3://backups/2026/11/big-backup.tar

aws s3api get-object --bucket backups --key 2026/11/big-backup.tar \
  --range bytes=0-104857599 part0.bin

Common mistakes

  • Single-stream uploads of multi-gigabyte files over flaky networks.
  • No lifecycle rule, paying for orphaned multipart parts.
  • Sequential, date-only key prefixes hammered by one hot workload.
  • Assuming S3 is still eventually consistent and adding needless sleeps.

How to answer in the interview

"For big files I use multipart upload: parts upload in parallel and retry individually; it is required above 5 GB and recommended from about 100 MB, and the CLI and SDK transfer managers handle it. I add a lifecycle rule to abort incomplete uploads. Downloads use parallel byte-range GETs, and Transfer Acceleration helps distant clients. Each prefix handles at least 3,500 writes and 5,500 reads per second, so I spread keys across prefixes. Since December 2020 S3 has strong read-after-write consistency for PUTs, overwrites, deletes and listings."

Likely follow-up questions

  • Why a lifecycle rule for incomplete multipart uploads? Orphaned parts are invisible in listings but billed indefinitely.
  • How prevent two writers overwriting the same key? Use conditional writes with If-None-Match or If-Match.
  • When use presigned URLs? To let clients upload or download directly without AWS credentials.
