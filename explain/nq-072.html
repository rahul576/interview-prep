How would you optimize a stream pipeline that performs multiple operations?

Coding Exercises · scenario · levels senior, lead

In one line

Measure first, then filter early, avoid unnecessary stateful operations (sorted, distinct), use short-circuiting terminals, primitive streams to avoid boxing, compute several aggregates in one pass (teeing, summaryStatistics, groupingBy with downstream), avoid side effects, and go parallel only when justified.

Detailed explanation

Measure before optimising. For lists of a few hundred or thousand items, a stream pipeline takes microseconds; the database call that loaded them dominates. Use a profiler or JMH benchmarks to find real hot spots. Readability usually matters more than micro-gains.

Order of operations. Put cheap, selective filter steps first, so expensive map operations (parsing, calculations, object creation) and sorting see fewer elements. Order filters by selectivity and cost.

Stateful operations. sorted and distinct must buffer elements (sorted needs all of them) and cost O(n log n) or extra memory. Skip them if the result does not need order or uniqueness; if you need only the top few, sorted().limit(k) is fine but a heap or max may be cheaper.

Short-circuiting. anyMatch, allMatch, noneMatch, findFirst and limit stop as soon as the answer is known. filter(...).count() > 0 or collecting a list and checking isEmpty() processes everything unnecessarily.

Primitive streams. mapToInt, mapToLong, mapToDouble avoid creating wrapper objects; sum, average and summaryStatistics work directly on primitives.

One pass instead of many. Streaming the same list five times to compute count, total, min, max and average is wasteful. Use summaryStatistics() / summarizingDouble, Collectors.teeing (Java 12) to combine two collectors in one pass, or groupingBy with a downstream collector instead of grouping then re-streaming each group.

Avoid side effects and debugging leftovers such as peek with logging in hot paths; they cost time and complicate parallelism.

Parallel streams only for large, CPU-heavy, independent work on splittable sources (ArrayList, arrays), and always benchmarked. A loop is also a legitimate optimisation for very hot code.

How it works

  1. Profile and benchmark to confirm the pipeline is a bottleneck.
  2. Reorder: selective filters before expensive maps.
  3. Remove unneeded sorted/distinct; use short-circuiting terminals.
  4. Switch to primitive streams for numeric work.
  5. Merge multiple passes into one combined collector.
  6. Benchmark again; consider parallel or a loop if still hot.

Example

// before: three passes, boxing, sorting not needed
long count = products.stream().filter(p -> p.getStock() > 0).count();
double total = products.stream().filter(p -> p.getStock() > 0)
        .map(Product::getPrice).reduce(0.0, Double::sum);
Product max = products.stream().filter(p -> p.getStock() > 0)
        .sorted(Comparator.comparingDouble(Product::getPrice).reversed())
        .findFirst().orElseThrow();

// after: one pass for count/sum, primitive stats
DoubleSummaryStatistics s = products.stream()
        .filter(p -> p.getStock() > 0)
        .mapToDouble(Product::getPrice)
        .summaryStatistics();

// teeing: total value and most expensive product in one pass
record Summary(double total, Optional<Product> top) {}
Summary summary = products.stream()
        .filter(p -> p.getStock() > 0)
        .collect(Collectors.teeing(
                Collectors.summingDouble(Product::getPrice),
                Collectors.maxBy(Comparator.comparingDouble(Product::getPrice)),
                Summary::new));

boolean anyOut = products.stream().anyMatch(p -> p.getStock() == 0);  // short-circuits

Common mistakes

  • Optimising without measuring.
  • Sorting the whole list to find one element.
  • Multiple passes over the same data for related aggregates.
  • Switching to parallel streams for small lists or I/O-bound work.

How to answer in the interview

"First I measure, since streams over a few hundred items are rarely the bottleneck. Then I put cheap, selective filters first so expensive maps and sorting see fewer elements, avoid sorted or distinct unless needed because they're stateful and buffer everything, and use short-circuiting terminals like anyMatch or findFirst instead of collecting and checking. I use primitive streams like mapToDouble to avoid boxing, and avoid streaming the same list many times by using a combined collector like Collectors.teeing, summaryStatistics or groupingBy with a downstream collector. I avoid side effects and peek in hot code, and consider parallel only for large CPU-heavy work, after benchmarking."

Likely follow-up questions

  • How does Collectors.teeing help? It feeds each element to two collectors and merges their results, so two aggregates need one pass.
  • How do you benchmark reliably? JMH, with warm-up iterations, to avoid JIT and dead-code effects.
  • Is a for loop faster than streams? Sometimes slightly in hot code; the difference rarely matters elsewhere.
