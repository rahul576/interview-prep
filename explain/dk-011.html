What does EXPOSE do in a Dockerfile? Does it publish the port?

Docker · concept · levels entry

In one line

EXPOSE only documents the port(s) the app listens on as image metadata; it does not publish anything to the host, which still needs -p (or -P, which publishes all exposed ports to random host ports); containers on the same network can talk on any port regardless.

Detailed explanation

EXPOSE 8080 (or EXPOSE 8080/tcp 5353/udp) records in the image config that the application is expected to listen on those ports. It is a contract and a hint, nothing more:

  • It does not open firewall rules, does not make the port reachable from outside, and does not even make the app listen; the application must bind the port itself (on 0.0.0.0).
  • To reach the service from the host or the outside world you must publish: docker run -p 8080:8080 image, or -P to map every exposed port to a random high host port (shown by docker port).

Inside Docker networks EXPOSE is not required at all. Two containers on the same user-defined network reach each other by name on whatever port the service listens on (http://api:8080), whether or not it was exposed. Published ports are only for traffic entering from outside the Docker network.

Why still use it? Documentation and tooling:

  • People reading the Dockerfile or docker inspect see the intended port immediately.
  • -P relies on it.
  • Docker Desktop, some PaaS platforms, Compose tooling and IDE integrations use it to suggest or auto-configure port mappings.
  • It signals intent to reviewers: an image exposing 22 or 2375 deserves questions.

Kubernetes ignores EXPOSE; the pod spec's containerPort is likewise mostly informational, and Services do the actual routing.

How it works

  1. EXPOSE writes ExposedPorts into the image config.
  2. docker run without -p: port reachable only from the container's networks.
  3. -p host:container: NAT rule from host to container port.
  4. -P: each exposed port mapped to a random host port.

Example

FROM nginx:1.27
EXPOSE 80
docker build -t site .
docker inspect -f '{{json .Config.ExposedPorts}}' site    # {"80/tcp":{}}
docker run -d --name s1 site              # not reachable from host
docker run -d --name s2 -P site && docker port s2        # 80/tcp -> 0.0.0.0:32771
docker run -d --name s3 -p 8080:80 site   # http://localhost:8080
docker network create web && docker network connect web s1
docker run --rm --network web curlimages/curl -s http://s1:80 | head -n 3   # works without -p

Common mistakes

  • Believing EXPOSE makes a service publicly reachable.
  • Forgetting -p and blaming the firewall.
  • Exposing a port that differs from what the app actually listens on.
  • Publishing internal-only service ports to the host "because they are exposed".

How to answer in the interview

"EXPOSE only documents which port the application in the image listens on; it's metadata in the image config. It doesn't publish the port or open anything on the host, so the service is unreachable from outside until I run it with -p, or -P, which publishes all exposed ports to random host ports. Containers on the same user-defined network can reach each other on any port anyway, by container name. I still add EXPOSE because it tells people and tools like Docker Desktop how the image is meant to be used."

Likely follow-up questions

  • How do two containers talk without published ports? Same user-defined network, by container or service name and port.
  • Does Kubernetes use EXPOSE? No; Services and containerPort define networking.
  • UDP ports? EXPOSE 53/udp and -p 53:53/udp.
