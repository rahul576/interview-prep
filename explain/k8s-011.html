Explain Kubernetes RBAC: Roles, ClusterRoles, bindings and service accounts.

Kubernetes · concept · levels entry, mid

In one line

RBAC grants verbs on resources in apiGroups: a Role is namespaced, a ClusterRole is cluster-wide; a RoleBinding grants a role within one namespace and a ClusterRoleBinding across the cluster, to users, groups or service accounts. Apply least privilege and verify with kubectl auth can-i.

Detailed explanation

Every API request is authenticated (who are you) and then authorised (may you do this). RBAC is the standard authoriser. It is purely additive: there are no deny rules, so permissions are the union of all bindings.

A rule lists apiGroups ("" for core, apps, batch...), resources (pods, deployments, subresources like pods/log or pods/exec), optional resourceNames, and verbs (get, list, watch, create, update, patch, delete, plus special verbs like impersonate, bind, escalate).

  • Role: rules valid in its namespace.
  • ClusterRole: rules for cluster-scoped resources (nodes, PVs, namespaces), non-resource URLs, or reusable namespaced permissions.
  • RoleBinding: grants a Role or ClusterRole to subjects, only inside that namespace. Binding the built-in view, edit or admin ClusterRole per namespace is the common pattern.
  • ClusterRoleBinding: grants a ClusterRole everywhere. Use sparingly.

Subjects are users and groups (from OIDC, cloud IAM mappings or certificates; Kubernetes has no user objects) and ServiceAccounts, the identities pods use to call the API with projected tokens.

Some permissions are more powerful than they look: create pods in a namespace lets you mount any Secret or service account there; get secrets reveals credentials; pods/exec gives shells; escalate, bind and impersonate let you gain other roles.

How it works

  1. Request arrives with an identity (user, groups or service account).
  2. Authoriser collects all bindings matching the subject.
  3. Checks if any rule allows verb + resource + namespace.
  4. Allowed → admission → stored; otherwise 403 Forbidden.

Example

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { name: deployer, namespace: shop }
rules:
- apiGroups: [apps]
  resources: [deployments]
  verbs: [get, list, watch, patch, update]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { name: ci-deployer, namespace: shop }
roleRef: { apiGroup: rbac.authorization.k8s.io, kind: Role, name: deployer }
subjects:
- { kind: ServiceAccount, name: ci, namespace: shop }
kubectl auth can-i delete pods -n shop --as=system:serviceaccount:shop:ci   # no
kubectl auth can-i --list -n shop --as=alice@example.com

Common mistakes

  • Giving CI or operators cluster-admin.
  • Wildcards (*) for resources or verbs.
  • Using ClusterRoleBindings when a namespaced RoleBinding would do.
  • Forgetting that create pods implies access to Secrets.

How to answer in the interview

"RBAC rules list API groups, resources and verbs. A Role holds rules in one namespace; a ClusterRole is cluster-wide and can cover cluster-scoped resources like nodes. A RoleBinding grants a Role or ClusterRole to subjects within a namespace, and a ClusterRoleBinding grants it across the cluster. Subjects are users and groups from the identity provider, or service accounts that pods use. I follow least privilege: bind view or edit per namespace, avoid wildcards, never give cluster-admin to CI, and check permissions with kubectl auth can-i --as."

Likely follow-up questions

  • Why is create pods nearly equal to reading all Secrets? A pod can mount any Secret in its namespace and print it.
  • How do you audit RBAC? kubectl auth can-i --list, tools like rbac-lookup or rakkess, and API audit logs.
  • What are aggregated ClusterRoles? Roles built from others by label, for example CRD permissions added to edit.
