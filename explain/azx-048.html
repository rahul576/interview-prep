How do you deploy Bicep or ARM templates safely from a pipeline, and what are deployment stacks?

Azure DevOps & Pipelines · concept · levels mid, senior

In one line

Deploy Bicep safely by linting and validating in CI, running what-if to preview create/modify/delete, gating production on an approval of the what-if output, deploying with workload identity federation, and using deployment stacks to manage resources as a group, clean up removed resources (actionOnUnmanage) and protect them with deny settings.

Detailed explanation

CI stage: az bicep build (or bicep lint) catches syntax errors and linter rules (no hard-coded secrets, use parameters, secure outputs). az deployment group validate checks the template against the target scope, catching invalid property values and some policy violations. Many teams add PSRule for Azure or Checkov for best-practice rules.

Preview: az deployment group what-if (or sub, mg, tenant scopes) shows a colour-coded diff: Create, Modify (with property changes), Delete (only in Complete mode or with stacks), NoChange, Ignore. The pipeline publishes it as an artifact or summary, and the production stage's environment approval asks a reviewer to approve based on it, much like reviewing a Terraform plan.

Deploy: with a service connection using workload identity federation, typically incremental mode at resource group scope.

The classic problem: incremental mode never deletes resources removed from the template, so orphans accumulate. Complete mode deletes anything not in the template in that resource group, which is dangerous and only works at resource group scope.

Deployment stacks (Microsoft.Resources/deploymentStacks, GA) solve this. A stack tracks the resources it manages. When you remove a resource from the template and update the stack, actionOnUnmanage decides whether to detach it (leave it, unmanaged) or delete it, separately for resources, resource groups and management groups. Deny settings (denyDelete or denyWriteAndDelete) create deny assignments so managed resources can't be changed or deleted outside the stack, even by Owners, with excluded principals (the pipeline identity) and excluded actions.

How it works

  1. PR: lint, build, validate, policy-as-code checks.
  2. Main: what-if against each environment; publish output.
  3. Approval on prod environment, reviewing what-if.
  4. Deploy (or update stack) with OIDC service connection.
  5. Stack deletes or detaches removed resources; deny settings protect the rest.

Example

az bicep lint --file main.bicep
az deployment group what-if -g rg-orders-prod -f main.bicep -p prod.bicepparam
az stack group create -n orders-prod -g rg-orders-prod \
  --template-file main.bicep --parameters prod.bicepparam \
  --action-on-unmanage deleteResources \
  --deny-settings-mode denyDelete \
  --deny-settings-excluded-principals <pipeline-identity-object-id> --yes

Common mistakes

  • Approving deployments without anyone reading the what-if.
  • Using Complete mode on shared resource groups.
  • Deny settings without excluding the deployment identity.
  • Ignoring what-if noise until reviewers stop trusting it.

How to answer in the interview

"In CI I lint and build the Bicep and validate it against the target scope. Before deploying, what-if shows what will be created, modified or deleted, like a Terraform plan; the pipeline publishes it and the production approval is based on that output. Deployment uses an OIDC service connection in incremental mode. Deployment stacks manage the resources as a group: when something is removed from the template, actionOnUnmanage detaches or deletes it, which fixes the orphan problem of incremental mode, and deny settings like denyDelete protect managed resources from changes outside the stack, even by owners."

Likely follow-up questions

  • What-if noise? Some properties show false changes; keep API versions current, use --exclude-change-types and document known noise.
  • Stacks vs Terraform state? Stacks track resources in Azure itself, no state file.
  • Complete mode risk? Deletes anything in the resource group not in the template.
