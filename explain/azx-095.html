Azure retires the model version your application uses, and after an automatic upgrade its answers change. How should you have prepared and how do you respond?

Azure AI & Foundry · scenario · levels mid, senior

In one line

Model versions have retirement dates and deployments have a version upgrade policy; prepare by pinning versions, choosing the policy deliberately, tracking notices and keeping a regression evaluation suite; test the new version in a parallel deployment before switching gradually, and if answers already changed, compare, re-route and fix prompts.

Detailed explanation

Azure OpenAI models come in versions (for example gpt-4.1 version 2025-04-14). Each version has a published retirement date. A deployment's version upgrade option decides what happens:

  • OnceNewDefaultVersionAvailable: auto-update when Microsoft changes the default version.
  • OnceCurrentVersionExpired: stay on the version until it retires, then auto-update.
  • NoAutoUpgrade: never upgrade; the deployment stops working at retirement.

An unplanned upgrade can change tone, verbosity, refusal behaviour, JSON formatting, tool-calling patterns and latency, even if overall quality is "better". Applications that parse output, rely on exact formats or use prompts tuned for one model are most fragile.

Preparation:

  • Pin the version in production and set the upgrade option consciously (usually "once current version expired" plus your own planned migration well before).
  • Track retirement notices (Azure Service Health, model lifecycle pages) in your backlog.
  • Maintain a regression evaluation suite: representative prompts with expected behaviour, format validators, tool-call checks, safety tests.
  • Months ahead, create a parallel deployment with the new model or version, run the suite, compare quality, format, safety, latency and cost, adjust prompts and parsing, then shift traffic gradually via a gateway with the ability to switch back.

If it already happened: confirm with traces which version served the changed answers, run the suite to quantify the regression, route traffic to another deployment with an acceptable model (for example a different region still on a supported version, or the new recommended model with adjusted prompts), and fix prompts or parsers quickly. Afterwards, add the incident's cases to the suite.

How it works

  1. Inventory deployments with model versions and retirement dates.
  2. Set upgrade options deliberately.
  3. Create a candidate deployment with the new version.
  4. Run the regression suite and compare.
  5. Fix prompts and parsing; canary traffic via gateway.
  6. Cut over and remove the old deployment before retirement.

Example

az cognitiveservices account deployment list -g rg-ai -n aoai-prod \
  --query "[].{name:name, model:properties.model.name, version:properties.model.version, upgrade:properties.versionUpgradeOption}" -o table

az cognitiveservices account deployment create -g rg-ai -n aoai-prod \
  --deployment-name chat-candidate --model-name gpt-4.1 --model-format OpenAI \
  --model-version "2025-04-14" --sku-name GlobalStandard --sku-capacity 50

Common mistakes

  • Leaving production on auto-update to the default version.
  • Discovering retirement dates from an outage.
  • Comparing only "does it look fine" instead of running a suite.
  • Strict parsers without schema validation or structured outputs.

How to answer in the interview

"Model versions have retirement dates, and deployments have an upgrade policy like auto-update to default or no auto-upgrade. I pin the version in production, track retirement notices and keep a regression suite. Months before retirement I deploy the new version in parallel and run the suite, comparing quality, format, safety, latency and cost, especially JSON output and tool calling, which often change subtly. Then I adjust prompts and switch traffic gradually through the gateway. If an automatic upgrade already changed answers, I quantify it with the suite, route traffic to an acceptable deployment and fix prompts quickly."

Likely follow-up questions

  • Most fragile logic? Output parsing, exact formats, tool-call sequences and prompts relying on quirks.
  • How to reduce fragility? Structured outputs with JSON schemas, validation and retries.
  • Who owns tracking retirements? The platform team, with alerts to each app owner.
