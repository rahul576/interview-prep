What is the difference between a livelock, starvation and a deadlock?

Concurrency · concept · levels mid, senior

In one line

In a deadlock threads are blocked forever waiting on each other; in a livelock threads are active but make no progress because they keep reacting to each other; in starvation a thread never gets the resource because others keep winning.

Detailed explanation

All three are liveness failures: the program is not wrong in what it computes, it just stops making progress for some or all threads.

A deadlock needs four conditions at once (the Coffman conditions): mutual exclusion, hold and wait, no pre-emption, and a circular wait. Typical Java case: thread A locks account 1 then wants account 2, thread B locks account 2 then wants account 1. Both are BLOCKED and a thread dump shows "Found one Java-level deadlock". Nothing recovers on its own.

A livelock is the polite version: threads are not blocked, they are running, but each reacts to the other in a way that undoes progress. Two threads that each tryLock() both locks, fail, release, and retry at exactly the same interval can keep colliding forever. CPU is high, throughput is zero. Retry storms between services are the distributed equivalent.

Starvation affects one thread or a class of tasks: the system as a whole progresses, but a particular thread never gets the lock, CPU or pool slot. Causes include unfair locks where newcomers barge ahead, a constant stream of readers starving a writer on a read-write lock, low thread priorities, or long tasks hogging a small pool.

Remedies differ: global lock ordering or tryLock with timeout for deadlocks; randomised backoff (jitter) for livelocks; fair locks, separate pools, bounded work and time limits for starvation.

How it works

  1. Deadlock: A holds L1 and waits for L2; B holds L2 and waits for L1; circular wait, both blocked.
  2. Livelock: A and B both detect a conflict, both back off for the same time, both retry, conflict again.
  3. Starvation: a scheduler or lock keeps choosing other threads, so one thread waits indefinitely.
  4. Detection: thread dumps (jcmd <pid> Thread.print) show BLOCKED cycles for deadlocks; high CPU with no progress hints at livelock; long-waiting threads and growing latency for a subset of work hint at starvation.
  5. Prevention: break one Coffman condition, add jitter, or add fairness and isolation.

Example

// Deadlock fix: always lock in a global order (by id)
void transfer(Account a, Account b, long amount) {
    Account first  = a.id() < b.id() ? a : b;
    Account second = a.id() < b.id() ? b : a;
    synchronized (first) {
        synchronized (second) {
            a.withdraw(amount);
            b.deposit(amount);
        }
    }
}

// Livelock fix: randomised backoff when tryLock fails
long backoff = ThreadLocalRandom.current().nextLong(1, 20);
Thread.sleep(backoff);

Common mistakes

  • Calling every hang a deadlock without checking thread states.
  • Fixing a deadlock with tryLock retries but without jitter, creating a livelock.
  • Turning on fair locks everywhere; fairness costs throughput significantly.
  • Ignoring starvation of writers in read-heavy ReentrantReadWriteLock usage.

How to answer in the interview

"A deadlock is when threads wait on each other forever, each holding a lock the other needs, so they are all blocked. A livelock is when threads are not blocked but keep reacting to each other, like two threads that both back off and retry at the same moment, so CPU is busy but nothing progresses. Starvation is when one thread never gets the lock or CPU because others keep winning, for example with unfair locks or a flood of readers. I fix deadlocks with consistent lock ordering or tryLock with timeouts, livelocks with randomised backoff, and starvation with fair locks or separate pools."

Likely follow-up questions

  • Can virtual threads starve platform threads? Not directly, but virtual threads run on a small carrier pool, so pinned or CPU-hogging virtual threads can starve other virtual threads; and many virtual threads can starve a shared resource like a connection pool.
  • How does the JVM detect deadlocks? ThreadMXBean.findDeadlockedThreads() and thread dumps detect monitor and ownable-synchronizer cycles.
  • Can a single thread deadlock? With non-reentrant locks, yes, for example re-acquiring a StampedLock write lock it already holds.
